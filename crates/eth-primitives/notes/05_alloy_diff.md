# W005 — Alloy code tour: divergences vs `eth-primitives` / `eth-rlp`

Compared against `alloy-primitives 1.6.1`, `alloy-rlp 0.3`, and the `alloy-rs/rlp` `main`
branch source. Every divergence below was *observed* — either from reading the upstream
source or from a compile/test failure this week — not assumed.

Verdict column: **keep** = our choice is better or deliberately different; **adopt** = we
should move toward alloy; **watch** = fine today, revisit on a trigger.

---

## D1. `Encodable::length` — alloy has a scratch-encode default, we have none

**Alloy** (`crates/rlp/src/encode.rs`):

```rust
pub trait Encodable {
    fn encode(&self, out: &mut dyn BufMut);

    #[inline]
    fn length(&self) -> usize {
        let mut out = Vec::new();
        self.encode(&mut out);
        out.len()
    }
}
```

**Ours** (`eth-rlp/src/encode.rs`): `length` is a *required* method. No default.

This is the single most consequential divergence. Alloy's default body is exactly the
anti-pattern our W005 R4 forbids: any impl that forgets `length` silently gets an O(n)
allocating scratch encode, and nothing tells you. Our `length_does_not_call_encode` and
`derive_rlp_length_is_arithmetic_not_encode` tests exist to catch that class; with alloy's
default, those tests can only ever cover the impls someone remembered to write.

**Verdict: keep.** And note upstream agrees — `alloy-rs/rlp#14`, the proposed API redesign,
specifies `fn rlp_len_raw(&self) -> usize;` with the inline comment *"Important: no
default!!"*. We arrived at alloy's intended fix before they shipped it.

## D2. `u8: Encodable` — alloy implements it, we deliberately do not

Alloy's `uint_impl!` macro covers `u8, u16, u32, u64, u128, usize` plus the `NonZero`
variants. We stop at `u16` and never implement `u8`.

The consequence is `Vec<u8>`. In alloy, `u8: Encodable` plus the blanket
`impl<T: Encodable> Encodable for Vec<T>` means a `Vec<u8>` encodes as an RLP **list** of
one-byte strings, while `&[u8]` and `Bytes` encode as a **string**. Two spellings of "some
bytes", two different wire formats, no compiler error between them.

Our omission is what makes `impl Encodable for Vec<u8>` (string) and
`impl<T: Encodable> Encodable for Vec<T>` (list) coexist without overlapping — the comment
at `encode.rs:123` states this. `Vec<u8>` is unambiguously a string.

**Verdict: keep.** This is a genuine correctness improvement, and it is why our
`vec_u8_is_a_string` / `vec_u64_is_a_list` pair can both pass. Cost: no `u8` scalar
encoding, which nothing needs — a lone byte is a `[u8; 1]`.

## D3. `Decodable` object safety — alloy uses a `Sized` supertrait, we use a method bound

**Alloy**: `pub trait Decodable: Sized { fn decode(buf: &mut &[u8]) -> Result<Self>; }`

**Ours**: `pub trait Decodable { fn decode(buf: &mut &[u8]) -> Result<Self, Error> where Self: Sized; }`

Functionally near-identical for callers, but not byte-for-byte. Moving the bound to the
method rather than the trait keeps the trait itself object-safe — which is what our
`encodable_is_object_safe` test pins. Alloy's `Decodable` can never be a trait object.

**Verdict: keep**, but this is real drift from "drop-in compatible" (W005 Tue R4). It does
*not* break the `signatures_match_alloy_rlp` compat test, because that test asserts both
traits are implemented for the same types, not that the declarations are textually equal.

## D4. `Address` is a newtype upstream, a type alias here

**Alloy**: `Address` is generated by `wrap_fixed_bytes!` — a distinct
`struct Address(pub FixedBytes<20>)`.

**Ours**: `pub type Address = FixedBytes<20>` (`address.rs:5`).

Cost, paid this week: in `etherscanlite/src/boundary.rs`, `Address` needs its own
conversion impl rather than riding the blanket one over `FixedBytes<N>`, because the inner
array sits one level deeper on the alloy side (`alloy.0 .0`). More importantly, an alias
gives no type safety — nothing stops a `B256` being passed where an `Address` is expected
if the widths ever coincide, and `impl Address { ... }` blocks are really
`impl FixedBytes<20>`, so `Address::ZERO` would collide with a generic
`FixedBytes<N>::ZERO` if we ever added one. That collision is why `B256::ZERO` does not
exist today and the tests say `FixedBytes([0u8; 32])`.

**Verdict: adopt**, but not this week — it touches every downstream signature. Trigger:
before W9 (`TxEnvelope`), where `Address` and `B256` appear in the same struct and a
mix-up would be a consensus bug rather than a compile error.

## D5. `U256` is not a mirror at all — it is alloy's own type

`eth-primitives/src/uint.rs:1` is `pub use ruint::aliases::U256;`. Alloy's `U256` is the
same alias from the same crate. There is exactly one `ruint 1.18.0` in our dependency
graph, so **`eth_primitives::U256` and `alloy_primitives::U256` are literally the same
type** — verified by `cargo tree -p etherscanlite -i ruint`.

Two consequences, both discovered while building the boundary:

1. The `U256` conversion in `boundary.rs` is the identity function. The "boundary" for our
   single widest-used integer type does not exist; an alloy `U256` can flow anywhere in
   the application and no isolation grep will ever see it.
2. If the two crates ever version-skew on `ruint`, that identity impl becomes a genuine
   type error overnight, in code that has worked for months.

**Verdict: watch, decide before W6.** Options are (a) newtype it and pay the arithmetic
forwarding, (b) accept the coupling and pin `ruint` exactly, or (c) accept it and delete
the fake conversion so the coupling is honest rather than disguised. Doing nothing is the
one option that is actively misleading, because the identity impl *looks* like a boundary.

## Alloy-rlp signature confirm (W005 Sat, 3-line backstop)

Read `alloy-rs/rlp` `main`, `crates/rlp/src/{encode,decode}.rs`, against `eth-rlp/src/`.

1. **`Encodable::encode(&self, out: &mut dyn BufMut)` — exact match.** Same receiver, same
   `dyn` erasure, same `bytes::BufMut`.
2. **`Encodable::length(&self) -> usize` — signature matches; `Decodable::decode(buf: &mut &[u8])`
   matches.** Drift is in the *declarations around them*: alloy gives `length` a
   scratch-encode default (D1), makes `Decodable` a `Sized` supertrait (D3), and returns a
   `Result<T>` alias where we spell `Result<T, Error>`.
3. **`decode_exact` confirmed present upstream** as
   `pub fn decode_exact<T: Decodable>(bytes: impl AsRef<[u8]>) -> Result<T>`; ours takes
   `&[u8]` rather than `impl AsRef<[u8]>`. **Error variants differ**: alloy splits
   canonicity into `LeadingZero` / `NonCanonicalSingleByte` / `NonCanonicalSize` where we
   have one `NonCanonical`; we add `TrailingBytes`; alloy's `Custom(&str)` is our
   `Custom(&'static str)`.

No blocking drift. D1 and D3 are deliberate and defensible; the `Error` variant split is
worth adopting if we ever need to tell a user *which* canonicity rule they broke.
