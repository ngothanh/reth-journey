  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: a single-symbol matching engine maxes out one CPU core. Scaling to 1000s of symbols requires partitioning state so each symbol's book is owned by exactly one shard (one core). Naïve sharding using `Arc<RwLock<SymbolShard>>` + general-purpose allocator destroys both correctness goals (single-writer-per-symbol) AND perf goals (lock-free hot path, NUMA-local memory). The correct design is thread-per-core: each shard's data is *single-threaded by construction*, accessed through a mailbox.

  - **Requirements** — write in `crates/matching-engine/notes/65_shard_design.md`:
    - R1. `SymbolShard` owns its `OrderBook`, `EventLog`, risk impl, and broadcast sender. No `Arc`, no `RwLock` around it.
    - R2. `Engine.shards: Box<[SymbolShard]>` where `len = num_shards` (not num_symbols). Typically `num_shards = num_cores` or `num_NUMA_local_cores`.
    - R3. **Symbol routing**: `route(&symbol) -> shard_id` via `hash(symbol) % num_shards`. Stable mapping; rebalance is offline-only at v0.5.
    - R4. **Single-writer per shard**: only the owning shard's task processes orders for its symbols. No cross-shard locking on the book; cross-shard work flows through the runtime mailbox.
    - R5. **NUMA-local memory**: each shard's `OrderBook`, `EventLog`, and per-call scratch buffers live on the same NUMA node as the shard's pinned core. Verified by `numastat -p <pid>` showing ≥95% local hits.
    - R6. **Linear scaling**: 8-shard aggregate throughput ≥ 6× single-shard throughput. (1.0× linear is unrealistic due to allocator + scheduler overhead; 6× is the practical floor.)
    - R7. **Per-shard budget**: 1 M orders/sec/shard sustained; p99 ≤ 10 µs per shard (matches the W63 v0.5 single-symbol baseline).
    - R8. **Zero allocations on dispatch**: `MatchCommand` reuses a per-shard mailbox slab; no per-order alloc on the routing path.

  - **Design walk-through** — answer each in your design doc; no peeking at LMAX Disruptor or CME Globex docs until Phase 3:
    - D1. Why `Box<[SymbolShard]>` and NOT `Vec<Arc<RwLock<SymbolShard>>>`? What's the ownership contract that lets you remove the locks?
    - D2. The mailbox pattern: each shard has a `cross_shard::Channel<MatchCommand>` (W60 primitive). The submit flow is: `engine.submit(order)` → `route(order.symbol) → shard_id` → `channel[shard_id].send(MatchCommand::Submit(order))`. Where does the shard's task LIVE? (Hint: a runtime task pinned to a core; it loops over `channel.recv()`.)
    - D3. NUMA allocation: write the per-shard init flow. The shard's task starts, learns its core, looks up the NUMA node via `numa_node_of_cpu(core_id)`, allocates `OrderBook` + `EventLog` on that node via `numa_alloc_onnode`. Why must the alloc happen on the SHARD's task, not on the engine constructor's thread?
    - D4. Hot-symbol problem: BTC-USDT routes to shard 5; 80% of volume hits shard 5; other shards idle. What's the v0.5 mitigation? (Hint: pre-split into virtual sub-symbols.) The v1.0 plan? (Hint: dynamic resharding with drain protocol.)
    - D5. Cancel routing: `cancel(order_id)` needs to know which shard owns the order. Embed `shard_id` in the OrderId's reserved bits (top 6 bits = shard_id, lower bits = sequence)? Or a global `OrderId → shard_id` map? Trade-offs.
    - D6. Cross-shard concerns: an account is long BTC on shard 3 and short ETH on shard 7. Cross-margin check requires data from BOTH shards. Who computes it at v0.5? (Hint: per-symbol margin only; deferred to a separate risk-shard process at W90+.)
    - D7. **Pre-mortem #1 (the Arc<RwLock<>> trap)**: write the 4-step trace showing that `Arc<RwLock<SymbolShard>>` adds ~10 ns CAS per access × 1 M/sec = 10 ms/sec of pure sync overhead per shard, even when there's NO contention. Then add the cross-shard Arc-clone ping-pong scenario.
    - D8. **Pre-mortem #2 (NUMA tax)**: write the 5-step trace where Engine::new allocates all shards on node-0, then shards 4-7 pin to node-1 cores. Compute the per-access penalty (200 ns cross-node vs 5 ns local) and the throughput hit on the affected shards.
  - **Output**: `notes/65_shard_design.md` with R1–R8, D1–D8, the mailbox topology diagram, and the NUMA-aware init flow.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  - **When `8_shard_linear_scaling` reports ~3.2× (vs the 6× target) and `numa_local_alloc_verified` shows ~40% local hits on shards 4-7:**
    - Symptom: aggregate throughput grows sub-linearly with shard count. `perf c2c` flags 30-60% of cache lines as cross-NUMA-node fetches; shards 4-7 measure half the throughput of shards 0-3.
    - Why: at the default Rust allocator, `Engine::new` allocates all shards on the thread that called `new` — likely node-0. When shard-7 pins to a core on node-1, every `book` mutation crosses the NUMA interconnect: ~200 ns vs ~5 ns L1 — a 40× tax on the critical path.
    - Fix: per-shard NUMA-local allocation. In the shard's init code (running on its own pinned task), look up `numa_node_of_cpu(core_id)`, allocate `OrderBook`, `EventLog`, and scratch buffers via `numa_alloc_onnode(size, node_id)` (libnuma). Alternative: install a per-shard allocator bound to the NUMA node via the `Allocator` API. Hot fields MUST live on the local node — verify with `numastat -p <pid>`.
    - Cost avoided: ~195 ns per touched cache line; at 1 M order/sec/shard × ~3 cache lines/order ≈ 600 ns/order ≈ 60% of the per-order budget. Reclaims linear scaling.
    - Muscle: in a pinned thread-per-core design, every allocation on the hot path must be NUMA-local to the owning shard; allocator on the calling thread is *wrong*. Reapplies at: W74 matching-engine `replication.rs` (raft state per shard), W77 messaging-aeron term buffer (subscriber-local), W85 marketdata-kernelbypass RX queue allocation, W95 mini-db per-shard memtable.

  - **When `per_shard_p99_under_10us` reports p99 ≈ 35 µs and `dispatch_zero_alloc` flags ~1 M allocs/sec:**
    - Symptom: per-shard p99 is 3.5× over budget; flame graph shows `Arc::clone` + `RwLock::write` at ~30% CPU.
    - Why: you wrapped `SymbolShard` in `Arc<RwLock<_>>` "just in case". Every access pays atomic CAS on `read()`/`write()` (~10 ns uncontended) on EVERY order. At 1 M orders/sec that's 10 µs/sec of pure synchronization work that does nothing — and Arc refcount inc/dec adds ~10 ns each. Cross-thread Arc decrements cause cache-line ping-pong if a different shard ever holds a clone.
    - Fix: own `SymbolShard` *by value* inside the per-shard task. The shards live as `Box<[SymbolShard]>` owned by the engine but each shard's data is touched only by its owning task. Cross-shard work goes through `runtime::submit_to(shard_id, FnOnce)` (W60 primitive) — the runtime's mailbox is the synchronization point, not the shard itself. Add the `arc_rwlock_compile_fail` test to prevent regression.
    - Cost avoided: ~10 ns CAS + ~10 ns Arc refcount per access; at 1 M order/sec/shard ≈ 20 ms/sec of removed sync overhead per shard. Eliminates the lock as a scalability ceiling.
    - Muscle: thread-per-core = single-owner-by-design; reaching for `Arc<RwLock<_>>` is a smell that the ownership model is wrong. The mailbox is the synchronization boundary. Reapplies at: W74 raft-backed engine per shard, W77 aeron subscriber state, W83 ledger-deterministic per-shard SM, W95 mini-db memtable.

  - **When `skewed_workload_isolation` shows shards 1-7 throughput drops by 40% when shard 5 is hot:**
    - Symptom: with 80% volume to one symbol on shard 5, other shards' throughput tanks. Expected isolation; got coupling.
    - Why: the shared cross-shard channel uses a single bounded MPMC queue; when shard 5's mailbox saturates, the producer's enqueue blocks (or contends) and slows the routing path for all other shards.
    - Fix: each shard owns its OWN cross-shard channel (W60 primitive). The producer (gateway thread) hashes to `shard_id`, picks `channel[shard_id]`, and sends — no shared queue. Shard 5's mailbox saturation only blocks NEW orders for symbols on shard 5; orders for symbols on shards 1-7 land in their own mailboxes, unaffected.
    - Muscle: per-shard isolation requires per-shard channels — shared queues couple unrelated shards. Reapplies at: W74 matching-engine per-shard raft log, W77 aeron per-Image flow, W85 marketdata per-subscriber socket.

  - **When `cross_shard_cancel_routes_correctly` shows some cancels lost on a 1k-order test:**
    - Symptom: a cancel for OrderId=4711 arrives at shard 2, but the order lives on shard 5 — cancel silently dropped.
    - Why: your `cancel(order_id)` routes via a separate hash (e.g., `hash(order_id) % num_shards`), but the order was originally routed by `hash(symbol)`. The two hashes don't agree.
    - Fix: per D5, embed `shard_id` in OrderId's high bits at creation. When the engine generates an OrderId for a new order, the top bits encode the shard_id that owns it. `cancel(order_id)` extracts `shard_id` directly from the OrderId — no symbol lookup, no hash mismatch.
    - Muscle: identifier design IS routing design; encode the routing key into the identifier so lookups don't require a map. Reapplies at: W74 raft per-shard request IDs, W83 ledger AccountId → shard mapping.

  - **When `submit_p50_under_500ns` reports ~2 µs:**
    - Symptom: submit path is 4× over budget. Flame graph shows ~30% in `ahash::RandomState::new()` + `hash_one()`.
    - Why: you constructed a fresh `ahash::RandomState` on each `route()` call. The state-init alloc + RNG seed costs ~1.5 µs per call.
    - Fix: hold the `ahash::RandomState` (or simpler: a fixed-seed hasher like `FxHasher`) as a field on `Engine`; reuse across calls. The route becomes 1 hash op (~50 ns) + 1 modulo (~5 ns) + 1 channel push (~50 ns) ≈ 100-200 ns p50.
    - Muscle: any hot-path hasher must be CONSTRUCTED ONCE per engine, not per call. Reapplies at: every engine-level hash routing in this project.

  - **5-year failure mode** (write in `notes/65_shard_followup.md` after green): when v2.0 ships dynamic resharding (drain + transfer of a symbol from one shard to another mid-trading), the static `symbol_to_shard` map becomes a stale view during the transfer window. State the migration: add an epoch field to the routing decision; orders carry their routing epoch; the shard rejects orders with stale epoch + bounces them back to the gateway for re-route. Trigger: first hot-symbol that production can't handle by manual split.

**Wednesday — Proposal draft + consensus-bft prevote**

- [ ] Draft small design proposal for reth evm. (~30 min)
- [ ] **Build**: `crates/consensus-bft/src/prevote.rs` — prevote phase. 2f+1 prevotes for a value advance the validator
  to precommit. (~total 215 min across 3 phases)
  - 🔧 **Why this matters**: prevote is the first vote phase — validators announce their provisional choice. Collecting 2f+1 same-value prevotes is the trigger that updates the validator's `valid_value` (Tendermint Annex A) and moves it to precommit. Get the threshold check wrong and you either (a) advance prematurely on < 2f+1, breaking safety, or (b) hang on perfectly-good 2f+1, breaking liveness. Get the VoteSet data structure wrong (unbounded `Vec<Prevote>`) and you've shipped a DoS vector — Byzantine validators spam votes until you OOM. Downstream: W65 Sat precommit reuses the same VoteSet shape; W68 v0.5 ship gated on this; W73 BLS variant collapses N prevotes into 1 aggregated signature, but the indexing model stays.

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: at n=21 validators × 3 phases × ~1 round/block × ~1 block/sec, steady-state vote ingest is ~63 votes/sec/replica; under view-change burst or Byzantine spam, ~500 votes/sec. The VoteSet must (a) detect equivocation (same validator votes for two different values in the same (h,r)), (b) maintain a per-value tally so threshold checks are O(1), (c) bound memory under adversarial spam, (d) zero-alloc in steady state.

  - **Requirements** — write in `crates/consensus-bft/notes/65_prevote_design.md`:
    - R1. `Prevote { height, round, value_hash: Option<Hash>, validator, signature }` is the wire type. `value_hash = None` means "prevote nil".
    - R2. **2f+1 same-value trigger**: when 2f+1 prevotes are collected for the SAME value V at round R, set `valid_value = V`, `valid_round = R`. If currently in `Step::Prevote`, cast `Precommit(V)` and transition to `Step::Precommit`.
    - R3. **2f+1 total without majority**: if 2f+1 prevotes are collected for round R but no single value has 2f+1 → cast `Precommit(nil)`.
    - R4. **Equivocation detection**: if a second prevote from the same validator at the same (h,r) with a different value_hash arrives, record evidence (do NOT replace the first vote). Equivocation evidence is slashable in v1.0.
    - R5. **Slot-indexed VoteSet**: per (h, r, step), exactly `n` slots indexed by `ValidatorId`. Insert by slot index, not push. Second vote from same validator → equivocation flag, NOT a second slot.
    - R6. **Bounded memory**: total VoteSet memory ≤ `MAX_ROUNDS_IN_FLIGHT × 3 × n × sizeof(Prevote)` known at compile time. Eviction: on commit of height H, drop all entries with `h < H - RETAIN_WINDOW`.
    - R7. **Zero alloc on steady-state vote intake**: VoteSet is a pre-allocated arena; vote insert never visits the allocator.
    - R8. **Running per-value tally**: `per_value_count: [u8; MAX_DISTINCT_VALUES_PER_RR]` incremented on insert; threshold check is O(1) compare, not O(n) scan.

  - **Design walk-through** — answer each in your design doc; no peeking at tendermint-rs `vote_set.go` until Phase 3:
    - D1. Sketch `Prevote`. Why `value_hash: Option<Hash>` not `Option<Value>`? (Hint: ~200 B/vote at hash, ~kB+/vote at value — bandwidth matters at n=21.)
    - D2. VoteSet shape. Pick ONE:
      (a) `AHashMap<(h, r, step), Vec<Prevote>>` (naïve),
      (b) `[[[Option<Prevote>; MAX_VALIDATORS]; 3]; MAX_ROUNDS]` (fixed 3D array, slot-indexed),
      (c) `BTreeMap<(h, r, step), [Option<Prevote>; n]>` (sorted height, slot-indexed within).
      Justify against R5, R6, R7.
    - D3. Per-value tally: a `BTreeMap<Hash, u8>` per (h,r) updated incrementally. Why a `BTreeMap` and not `AHashMap`? (Determinism; spec allows traversal in tests.) Or pick a `[u8; 21]` indexed by validator-id mapped through a tiny lookup — what's the trade-off?
    - D4. Threshold formula: `quorum = 2 * (n / 3) + 1` where `f = floor((n-1)/3)`. Compute for n ∈ {1, 4, 7, 10, 21}. When does the formula tighten the threshold (i.e., n = 3f+1 exactly vs n = 3f+2)?
    - D5. Equivocation handling: when you detect "same validator, same (h,r), different value", what do you store as evidence? (Hint: both signed votes — the cryptographic proof of misbehavior.) Where does the evidence live (memory, disk)?
    - D6. Eviction: write the on-commit cleanup in 4 numbered steps. What's `RETAIN_WINDOW` (hint: enough to handle replay of stragglers; 64 rounds is typical)?
    - D7. **Pre-mortem #1 (unbounded Vec)**: write the 5-step trace where Byzantine validators flood prevotes for distinct (synthetic) heights, each round's `Vec` grows unboundedly, replica OOM. Quantify: at 500 votes/sec adversarial × 200 B/vote × 1 hour = ?
    - D8. **Pre-mortem #2 (threshold-check storm)**: at n=21, naïve `count = votes.iter().filter(|v| v.value == target).count()` is O(n) per check, called on every insert → O(n²) per round = 441 ops at n=21, 10k ops at n=100. Compute the cost; identify the fix from R8.
  - **Output**: `notes/65_prevote_design.md` with R1–R8, D1–D8, VoteSet shape decision recorded with rationale.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  - **When `vote_set_zero_alloc_on_insert` reports ~7 allocs per round and `vote_set_bounded_under_spam` causes OOM at 5 minutes of adversarial flood:**
    - Symptom: heap profile shows `Vec<Prevote>` allocations dominating; replicas RSS climbs from 100 MB to 2 GB during the spam test. Eventually OOM. ~7 mallocs/round (each ~50 ns) on the vote ingest path.
    - Why: naïve `votes: AHashMap<(Height, Round, Step), Vec<Prevote>>` allocates a fresh `Vec` per round, pushes votes as they arrive, and never frees until view-change. Under sustained burst, the structure grows unbounded; Byzantine spam turns this into a DoS vector.
    - Fix: pre-allocate `VoteSet` as a per-(h, r, step) **fixed-capacity slot array** indexed by `ValidatorId` (1-to-1 mapping). Insert by index, not push; second vote from same validator with different content → flag equivocation, do NOT append a second slot. Eviction: on commit of height H, drop all (h, _, _) slots with `h < H - RETAIN_WINDOW`. Total memory bound: `MAX_ROUNDS_IN_FLIGHT × 3 × n × sizeof(Prevote)` — known at compile time.
    - Cost avoided: ~7 mallocs/round eliminated; closes the unbounded-growth DoS vector; ~350 ns/round per `Vec::push` chain removed.
    - Muscle: any per-round protocol state should be bounded by `n × max_rounds_in_flight` and slot-indexed by `ValidatorId`; never use unbounded `Vec` on the consensus hot path. Reapplies at: W65 precommit VoteSet (same shape), W68 lock.rs POL detection (same vote indexing), W74 VSR PrepareOk BitSet (same idea — already correct), W83+ ledger replication.

  - **When `bench_threshold_check_o1` reports ~250 ns per check at n=21:**
    - Symptom: each threshold check takes ~250 ns; at n=21 with 21 inserts per round each triggering a check, that's ~5 µs/round of pure tally scanning. At n=100 (federated consortium scenario), it's ~30 ms/round — catastrophic.
    - Why: `has_2f1_prevotes_for_value` re-scans the entire vote set on each insertion (O(n) per check, O(n²) per round).
    - Fix: maintain a running `per_value_count: BTreeMap<Hash, u8>` per (h, r) updated incrementally as votes arrive. Insert → `count.entry(value).and_modify(|c| *c += 1).or_insert(1)`. Threshold check → O(1) compare against `quorum = 2 * (n/3) + 1`. Bounded: at most `n+1` distinct values per (h, r) (each validator votes one value or nil).
    - Cost avoided: O(n) → O(1) per insert; at n=21 saves ~12 µs/vote, ~250 µs/round; at n=100 saves ~300 µs/vote, ~30 ms/round (catastrophic-to-acceptable).
    - Muscle: aggregate counts maintained incrementally beat scan-on-query whenever the query is hotter than the aggregation. Reapplies at: W65 precommit VoteSet (same shape), W67 raft match-index aggregation, W73 fork_choice descendant-of count, W74 VSR PrepareOk BitSet `count_ones`.

  - **When `equivocation_detected_and_evidenced` shows the first vote silently replaced by the second:**
    - Symptom: Byzantine sends Prevote(V) then Prevote(V'); the test expected to see two votes in evidence, got just the second (the first was overwritten in the slot).
    - Why: your slot-indexed VoteSet overwrites on duplicate insert from the same validator. The slot index is per-validator, and the second vote took the slot.
    - Fix: on insert, BEFORE writing the slot, check `if slot.is_some() && slot.unwrap().value_hash != incoming.value_hash`. If true: this is equivocation — push BOTH votes onto an `evidence: Vec<EquivocationProof>` log (off the hot path), do NOT overwrite the slot. The first vote remains the validator's "vote of record" for this (h, r); the equivocation is for slashing.
    - Muscle: equivocation evidence MUST preserve both conflicting votes — overwriting one destroys the proof. Reapplies at: W65 precommit equivocation, W68 lock.rs evidence collection, W74 raft (less common but possible during leader change).

  - **When `prevote_2f1_split_value_precommits_nil` shows the node committing V instead of nil:**
    - Symptom: 4-node, votes are {V, V', nil, V} — node 3's view shows 2 votes for V, 1 for V', 1 for nil; total = 4. The node should see "2f+1 total without single-value majority" and precommit nil; instead it precommits V (which only has 2/4 = below 2f+1=3).
    - Why: your threshold check on insertion returns "has 2f+1 for value V" as soon as the total count for V reaches the THRESHOLD. But you need to check: (a) total votes ≥ 2f+1 AND (b) the per-value count for V ≥ 2f+1 EQUALS 2f+1, not just "total reached". V has 2 votes (< 3); the check is wrong.
    - Fix: the two checks are independent. (a) `if let Some(v) = self.per_value_count.iter().find(|(_, c)| **c >= quorum) { /* 2f+1 same-value → precommit v */ }` (b) `else if self.total_votes_at(h, r) >= quorum { /* 2f+1 total mixed → precommit nil */ }`. The same-value check must precede the mixed check.
    - Muscle: BFT threshold logic has TWO conditions per phase — same-value-quorum and total-quorum — they trigger different precommit values. Reapplies at: W65 precommit (mirror), W68 ship test.

  - **When `slot_indexed_no_duplicate_slot` shows the slot incrementing the per-value count on each duplicate insert:**
    - Symptom: same validator votes for V five times; the per-value count for V is now 5 (when it should be 1). The 2f+1 threshold trips on a single validator's spam.

  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: precommit is on the commit path — every µs added here is user-observed finality latency. Naïve implementations (a) commit on 2f+1 of ANY mix instead of 2f+1 of SAME value (safety bug), (b) fsync each vote to the WAL "for durability" (latency catastrophe), (c) re-scan the vote set on every insertion to check thresholds (O(n²) hot path), (d) forget to set locked_value when casting precommit (subsequent-round safety hole).

    - R2. **Commit predicate**: 2f+1 precommits for the SAME value V at round R → COMMIT V at height H. Reset round to 0; reset locked state; advance height.
    - R3. **2f+1 mixed → round advance**: 2f+1 total precommits without a single-value majority → set the precommit timer; on timeout advance to round R+1.
    - R4. **Lock-on-precommit invariant**: when a validator casts `Precommit(V)` (not nil), it ATOMICALLY sets `locked_value = V, locked_round = round`. Subsequent rounds prevote `locked_value` unless valid_round release fires.

    - R6. **Single fsync per commit**: the commit certificate (2f+1 signed precommits for V) is fsync'd ONCE to the WAL; individual precommit votes are buffered in memory and NEVER fsync'd individually.
    - R7. **O(1) threshold check**: running per-value tally on each insert; threshold check is a single compare, not an O(n) scan.
    - R8. **Latency budget**: ≤ 300 ms WAN block-time at n=21; ≤ 1 ms LAN at n=4. p99 commit latency dominated by network RTT, NOT disk.

  - **When `commit_cert_fsync_once_per_commit` reports ~210 fsync calls for 10 commits and `commit_latency_lan_under_1ms` reports ~20 ms p99:**

    - Fix: **group-commit on precommit votes** — buffer incoming votes in memory, fsync ONCE when the 2f+1 threshold trips (forming the commit certificate). The commit certificate IS the durable record; individual votes need not survive a crash (replicas re-vote after recovery via the standard view-change path). Wire into the W26 `GroupCommit` primitive — same shape. For equivocation evidence (rare, off the hot path), use a separate group-commit lane.
