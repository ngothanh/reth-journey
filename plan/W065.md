- [ ] [HFT] **Build**: `crates/matching-engine/src/shard.rs` —
  `SymbolShard { book: OrderBook, wal: wal::Wal, event_tx: broadcast::Sender<MatchEvent> }`.
  `Engine { shards: HashMap<Symbol, Arc<Mutex<SymbolShard>>> }`. (~150 min)
  - **Why (MAX DETAIL — concurrency)**: Multi-symbol is where the engine actually scales — single-symbol bench numbers are nice but production has 1000s of symbols. With runtime-thread-per-core v0.5 shipped (W60), we PIN each symbol-shard to a core, no locks needed within a shard. Inheritance: matching-engine reuses runtime's cross_shard, NUMA, det_test.
  - *Back-of-envelope* (bar c): target **≥1 M orders/sec/shard** at P99 ≤5 µs single-symbol (1 cmd ≈ ~5 ns dispatch + ~50 ns hash route + ~500 ns L2-book mutation on warm cache). Aggregate target: **≥8M/sec at 8 shards (linear scaling)**. Per-order budget: ≤1 µs. Implications: (a) **zero allocations on dispatch** — `MatchCommand` reuses a per-shard mailbox slab; (b) **shard memory NUMA-local** — `numa_alloc_onnode` for each shard's `OrderBook + EventLog`, miss-from-other-node ≈ ~200 ns vs local ~5 ns L1 (40× penalty, see perf pitfall #1); (c) **`Arc<RwLock<SymbolShard>>` introduces a CAS per access** — must be eliminated for v0.5 single-owner (see perf pitfall #2); (d) per-shard `EventLog` + book stays in L1 (≤32 KiB working set per shard at warm symbol — see perf pitfall on cache locality below).
  - **Read first**: LMAX Disruptor single-writer principle; CME Globex's per-product sharding; runtime W60 cross_shard channel.
  - **Design**:
    ```rust
    pub struct SymbolShard {
        pub symbol: Symbol,
        pub book: OrderBook,
        pub event_log: EventLog,
        pub event_tx: tokio::sync::broadcast::Sender<MatchEvent>,
        pub risk: Box<dyn RiskCheck>,
        pub seq: u64,
    }

    pub struct Engine {
        pub shards: Arc<[Arc<RwLock<SymbolShard>>]>,  // size = num_shards (NOT num_symbols)
        pub symbol_to_shard: ahash::AHashMap<Symbol, usize>,
        pub runtime: Arc<runtime_thread_per_core::Runtime>,
    }

    impl Engine {
        pub fn route(&self, symbol: &Symbol) -> usize {
            *self.symbol_to_shard.get(symbol).unwrap_or_else(|| {
                // Hash routing: shard_id = hash(symbol) mod num_shards
                let h = ahash::RandomState::new().hash_one(symbol);
                &((h as usize) % self.shards.len())
            })
        }

        pub fn submit(&self, order: Order) -> Result<(), _> {
            let shard_id = self.route(&order.symbol);
            // Cross-shard via runtime: send to shard_id's mailbox
            self.runtime.submit_to(ShardId(shard_id), Box::new(move || {
                let shard = self.shards[shard_id].write();
                shard.process(order);
            }));
            Ok(())
        }
    }
    ```
    **Invariants**:
    - Per-symbol single-writer: only the owning shard processes any order for that symbol. No cross-shard locking on the book.
    - Symbol-to-shard mapping is STABLE — moving a symbol to another shard requires drain + transfer (rebalance).
    - Engine.shards length = num_shards (typically = num_cores or num_NUMA_local_cores), NOT num_symbols.
    - Cross-shard concerns: per-account risk (cross-margin across symbols) handled by separate risk shard (W90+ ledger integration).
  - **Build steps** (granular):
    1. (~25 min) SymbolShard with book + event log + risk per shard.
    2. (~30 min) Engine with symbol_to_shard routing.
    3. (~25 min) Runtime integration: each shard runs as a runtime task pinned to a core.
    4. (~30 min) Submit path: hash-route → submit_to shard's mailbox → shard dequeues → process.
    5. (~20 min) Cancel path: same routing (cancel for OrderId requires knowing its symbol — embed symbol in OrderId's reserved bits, OR maintain global OrderId → shard map).
    6. (~20 min) Tests: 16 symbols across 8 shards, 100k orders/symbol; verify all process correctly; throughput scales linearly with shard count.
  - **Pitfalls** (named, concurrency-critical):
    - *Symbol rebalance during live trading*: moving symbol X from shard 3 to shard 5 mid-trading: in-flight orders for X arrive at shard 3 → stale. **Symptom**: orders lost or processed against wrong book version. **Fix v0.5**: rebalance offline only (stop, persist, resume on new shard). **Fix v1**: drain protocol with epoch markers (W74+).
    - *Cross-symbol cross-margin requires cross-shard*: account A long BTC on shard 3, short ETH on shard 7 → which shard checks margin? **Fix**: dedicated risk-shard (separate process) computes cross-margin from event broadcast; either approves order pre-trade OR liquidates post-fill. v0.5: per-symbol margin only.
    - *Hot symbol overloads shard*: BTC-USDT routes to shard 5; 80% of volume goes through shard 5. **Symptom**: shard 5 saturates, others idle. **Fix v0.5**: manual override of routing for hot symbols (split BTC-USDT into BTC-USDT.0 and BTC-USDT.1, pre-shard). **Fix v1**: dynamic resharding (W74+).
    - *Lock contention via RwLock*: even with single-writer per shard, RwLock around SymbolShard introduces atomic-cmpxchg per access. **Fix**: shard owned by ONE task at a time; no Arc<RwLock<_>> needed if runtime guarantees single-execution-per-shard.
  - **Test scenarios**:
    - 16 symbols × 100k orders/symbol across 8 shards: linear scaling vs 1-shard baseline.
    - Skewed: 80% volume to one symbol; verify others not blocked.
    - Cross-symbol cancel: cancel order across many symbols; verify each routes to correct shard.
  - **Acceptance**: 8-shard throughput ≥ 6× single-shard (linear scaling within shadowing of contention).
  - **Downstream**: W66 perpetuals layer is per-symbol (no cross-shard impact); W90+ ledger handles cross-symbol via separate process.
  - **Expect to hit (perf) #1 — cross-NUMA-node memory access on the hot path (bar (c) violation)**: at default Rust allocator, `Engine::new` allocates all shards on the thread that called `new` — likely node-0. When shard-7 pins to a core on node-1, every `book` mutation crosses the NUMA interconnect: ~200 ns vs ~5 ns L1, a 40× tax on the critical path. Symptom: `perf c2c` flags 30-60% of cache lines as cross-node fetches; throughput on shards 4-7 measures half of shards 0-3 despite identical workloads.
    - Fix: per-shard NUMA-local allocation via `libnuma`'s `numa_alloc_onnode(size, node_id)` or a per-shard `Allocator` impl bound to the shard's NUMA node (looked up via `numa_node_of_cpu(core_id)`). Hot fields (`book.bids`, `book.asks`, `event_log`) MUST live on the local node — verify with `numastat -p <pid>` showing >95% local hits.
    - Cost avoided: ~195 ns per touched cache line; at 1 M order/sec/shard × ~3 cache lines/order, ≈ 600 ns/order ≈ 60% of the per-order budget for cross-shard accesses. Reclaims linear-scaling.
    - Muscle: in a pinned thread-per-core design, every allocation on the hot path must be NUMA-local to the owning shard; allocator on the calling thread is *wrong*. Reapplies at: W74 matching-engine `replication.rs` (raft state per shard), W77 messaging-aeron term buffer (subscriber-local), W85 marketdata-kernelbypass RX queue allocation, W95 mini-db per-shard memtable.
  - **Expect to hit (perf) #2 — `Arc<RwLock<SymbolShard>>` on a single-owner shard (bar (c) violation)**: even though only one task touches each shard (runtime guarantee), wrapping in `Arc<RwLock<_>>` adds an unconditional atomic CAS on `read()`/`write()` (~10 ns uncontended) on EVERY access. At 1 M orders/sec that's 10 µs/sec of pure synchronization work that does nothing — and far worse, the `Arc` refcount inc/dec on `.clone()` patterns adds ~10 ns each, plus cross-thread Arc decrements cause cache-line ping-pong if a different shard ever holds a clone.
    - Fix: own `SymbolShard` *by value* inside the per-shard task; no `Arc`, no `RwLock`. Cross-shard work goes through `runtime::submit_to(shard_id, FnOnce)` (W60 primitive) — the runtime's mailbox is the synchronization point, not the shard itself. The shard's data is single-threaded by construction.
    - Cost avoided: ~10 ns CAS + ~10 ns Arc refcount per access; at 1 M order/sec/shard, ≈ 20 ms/sec of removed sync overhead per shard. Eliminates the lock as a scalability ceiling.
    - Muscle: thread-per-core = single-owner-by-design; reaching for `Arc<RwLock<_>>` is a smell that the ownership model is wrong. The mailbox is the synchronization boundary. Reapplies at: W74 raft-backed engine per shard, W77 aeron subscriber state, W83 ledger-deterministic per-shard SM, W95 mini-db memtable.

- [ ] **Build**: `crates/consensus-bft/src/prevote.rs` — prevote phase. 2f+1 prevotes for a value advance the validator
  to precommit. (~150 min)
  - **Why**: Prevote is the first vote phase. Validators announce their PROVISIONAL choice. Collecting 2f+1 same-value prevotes locks the validator on that value for the round.
  - *Back-of-envelope* (bar c): VoteSet is the message-rate hot data structure. At n=21 validators × 3-phase × ~1 round/block × 1 block/sec, steady-state ingest is ~63 votes/sec/replica; under view-change churn or burst, peaks at ~500 votes/sec. Per-vote: ed25519 verify ≈ 50 µs (batched ≈ 6 µs, see W64 perf #1), HashMap insert ≈ 30 ns, threshold check ≈ ~5 ns. **VoteSet memory bounded by `2 × n × MAX_IN_FLIGHT_ROUNDS`** (e.g., 21 × 16 = 336 vote slots × ~200 B/vote = 67 KiB — fits L2). **Zero allocations in steady state** — VoteSet is a pre-allocated arena (cap = `n × max_rounds_in_flight`), votes occupy fixed slots, eviction reuses slots; never `Vec::push` on the hot path.
  - **Design**:
    ```rust
    pub struct Prevote {
        pub height: u64,
        pub round: u32,
        pub value_hash: Option<Hash>,  // None = nil
        pub validator: NodeId,
        pub signature: Signature,
    }

    impl BftState {
        pub fn handle_prevote(&mut self, pv: Prevote) -> Result<(), _> {
            if pv.height != self.height { return Err(WrongHeight); }
            // Detect equivocation: same (height, round, validator) but different value
            if let Some(existing) = self.votes.find_prevote(pv.height, pv.round, pv.validator) {
                if existing.value_hash != pv.value_hash {
                    self.evidence.add_equivocation(pv.validator, existing, pv.clone());
                }
            }
            self.votes.add_prevote(pv.clone());

            // Check thresholds
            let total = self.validators.len();
            let threshold = 2 * (total / 3) + 1;  // 2f+1 where f = floor((N-1)/3)
            if let Some(value) = self.votes.has_2f1_prevotes_for_value(pv.height, pv.round) {
                // 2f+1 prevotes for a value → enter precommit with value
                self.valid_value = Some(value);
                self.valid_round = Some(pv.round);
                if self.step == Step::Prevote {
                    self.cast_precommit(Some(value));
                    self.step = Step::Precommit;
                }
            } else if self.votes.count_prevotes(pv.height, pv.round) >= threshold {
                // 2f+1 prevotes total, but no single value has majority → precommit nil
                self.cast_precommit(None);
                self.step = Step::Precommit;
            }
            Ok(())
        }
    }
    ```
    **Invariants**:
    - 2f+1 prevotes for SAME value V at round R → validator updates valid_value to V (Tendermint Annex A).
    - 2f+1 prevotes total (any mix of values + nil) without single-value majority → precommit nil.
    - Equivocation (two prevotes from same validator at same height/round) recorded as evidence.
  - **Build steps**:
    1. (~25 min) Prevote type with sig.
    2. (~25 min) VoteSet: per (h, r, step), bucket by validator; track total + per-value counts.
    3. (~30 min) handle_prevote with equivocation detection + threshold checks.
    4. (~30 min) Advance to precommit on 2f+1.
    5. (~25 min) Tests: 4-node, valid prevote round → all 4 precommit; 1 Byzantine prevotes nil → 3 honest still precommit value.
    6. (~15 min) Equivocation test: Byzantine sends two prevotes same (h,r); evidence captured.
  - **Pitfalls**: equivocation hash-based dedup must verify sig before adding; spoofed prevotes from non-validator must reject.
  - **Acceptance**: 4-node 1-Byzantine BFT simulation: commit per height in expected time.
  - **Downstream**: Sat precommit; W68 v0.5 ship.
  - **Expect to hit (perf) #1 — `Vec<Prevote>` per (height, round) growing unbounded (bar (c) violation)**: naive `votes: AHashMap<(Height, Round, Step), Vec<Prevote>>` allocates a fresh `Vec` per round, pushes votes as they arrive, and never frees until view-change. Under sustained 100-round bursts (network partition + heal), the `Vec` grows by `2n` per round × 21 validators × ~200 B/vote = ~4 KiB/round × 100 rounds = 400 KiB churn, with `Vec::push` re-allocating geometrically (~7 mallocs/round each ~50 ns). At adversarial burst (Byzantine spam) the structure unbounded grows to OOM. Symptom: heap profile shows VoteSet allocations dominating; replicas RSS climbs under partition heal.
    - Fix: pre-allocate `VoteSet` as a per-(h,r,step) **fixed-capacity ring buffer** of `n` slots indexed by `ValidatorId` (1-to-1 mapping). Insert by index, not push; second vote from same validator with different content → flag equivocation, do NOT append a second slot. Eviction: when committing height H, drop all `(h, _, _)` slots with `h < H - retain_window`. Total memory bound: `MAX_ROUNDS × 3 × n × sizeof(Prevote)` — known at compile time.
    - Cost avoided: ~7 mallocs/round eliminated; eliminates unbounded growth under adversarial spam (DoS vector closed); ~350 ns/round per `Vec::push` chain removed.
    - Muscle: any per-round protocol state should be bounded by `n × max_rounds_in_flight` and slot-indexed by `ValidatorId`; never use unbounded `Vec` on the consensus hot path. Reapplies at: W65 precommit VoteSet (same shape), W68 lock.rs POL detection (same vote indexing), W74 VSR PrepareOk BitSet (same idea — already correct), W83+ ledger replication.

- [ ] **Build**: `crates/consensus-bft/src/precommit.rs` — precommit phase. 2f+1 precommits commits the block. (~150 min)
  - **Why**: Precommit is the binding vote — 2f+1 precommits = COMMIT. The validator's lock state updates here; locked_value/locked_round used in subsequent rounds.
  - *Back-of-envelope* (bar c): precommit is on the **commit path** — its latency is the user-observed block-finality latency. Budget: ≤300 ms WAN, ≤1 ms LAN. Threshold check (`has_2f1_precommits_for_value`) runs on EVERY incoming precommit; at n=21 with bursty arrival it fires up to ~21 times per round. Naive `O(n)` per-value tally on each insert = O(n²) per round total — fine at n=21 (~441 ops), catastrophic at n=100 (10k ops). **Maintain a running per-value tally** so threshold check is O(1) (see perf pitfall below). Lock-state transition on commit is the *single fsync point* — appending the commit certificate to wal costs 50-1000 µs NVMe; this MUST be the only wal write per round (no per-vote fsync — that would multiply latency by `2n`).
  - **Design**:
    ```rust
    pub struct Precommit {
        pub height: u64,
        pub round: u32,
        pub value_hash: Option<Hash>,
        pub validator: NodeId,
        pub signature: Signature,
    }

    impl BftState {
        pub fn handle_precommit(&mut self, pc: Precommit) -> Result<(), _> {
            if pc.height != self.height { return Err(WrongHeight); }
            // Equivocation detection (same as prevote)
            if let Some(existing) = self.votes.find_precommit(pc.height, pc.round, pc.validator) {
                if existing.value_hash != pc.value_hash {
                    self.evidence.add_equivocation(pc.validator, existing, pc.clone());
                }
            }
            self.votes.add_precommit(pc.clone());

            // 2f+1 precommits for same value → COMMIT
            if let Some(value) = self.votes.has_2f1_precommits_for_value(pc.height, pc.round) {
                self.commit_block(value);
                self.height += 1;
                self.round = 0;
                self.step = Step::Propose;
                self.locked_value = None;
                self.locked_round = None;
                self.on_enter_propose();
                return Ok(());
            }
            // 2f+1 total precommits (mix) → advance round
            let threshold = 2 * (self.validators.len() / 3) + 1;
            if self.votes.count_precommits(pc.height, pc.round) >= threshold && self.step == Step::Precommit {
                // Set timer; on timeout, advance round
                self.set_timer(Step::Propose, self.precommit_timeout);
            }
            Ok(())
        }

        pub fn lock(&mut self, value: Hash, round: u32) {
            self.locked_value = Some(value);
            self.locked_round = Some(round);
        }
    }
    ```
    **Invariants**:
    - On 2f+1 precommits for V → COMMIT V, advance height. Locked state reset.
    - When validator casts precommit V (not nil), it sets locked_value = V, locked_round = round.
    - Subsequent rounds: validator prevotes for locked_value unless valid_round rule allows release.
  - **Build steps**:
    1. (~30 min) Precommit type + sig.
    2. (~30 min) handle_precommit with commit check.
    3. (~30 min) lock/unlock transitions.
    4. (~30 min) Tests: 4-node, all precommit V → commit V. 3 precommit V, 1 precommit nil → still commit (3 ≥ 2f+1).
    5. (~30 min) Round-advance test: 4-node, 2 precommit V, 2 precommit nil → no commit; round advances; new proposer.
  - **Pitfalls** (named):
    - *Commit on 2f+1 ANY (not same value)*: 2 commit V, 2 commit V' → no commit; advance round. **Symptom**: false commit. **Fix**: explicit same-value check.
    - *Lock-release missed*: validator stays locked on stale value through many rounds. **Symptom**: liveness loss. **Fix**: valid_round mechanism releases lock when newer round shows 2f+1 prevotes for new value.
    - *Lock not set on precommit*: validator precommits V but doesn't lock → can precommit V' next round → safety violation. **Symptom**: 2 validators commit different values. **Fix**: lock-set is atomic with precommit-cast.
  - **Acceptance**: 4-node 1-Byzantine BFT runs 10 heights without safety violation; commits average ≤ 2 rounds.
  - **Downstream**: W68 v0.5 ship; W73 v1.0 includes HotStuff-style linearity.
  - **Expect to hit (perf) #1 — per-vote `fsync` on the commit path (bar (c) violation)**: naive implementation appends each incoming Precommit to wal and fsyncs to ensure durability before increasing the tally. At n=21, that's ~21 fsyncs/round × 50-1000 µs NVMe each = 1-20 ms per round of pure fsync stall — burning 30-99% of the 300 ms WAN budget on disk waits while messages from late validators arrive. Symptom: P99 commit latency tracks fsync time, not network RTT; `iostat -x 1` shows the wal device pinned at ~21 IOPS during commit bursts.
    - Fix: **group-commit on precommit votes** — buffer incoming votes in memory, fsync ONCE when the 2f+1 threshold trips (forming the commit certificate). The commit certificate IS the durable record; individual votes need not survive a crash (replicas re-vote after recovery via the standard view-change path). Wire it into the W26 `GroupCommit` primitive — same pattern. For paranoid mode (do-not-lose-evidence), separately journal *equivocation* evidence (rare, off the hot path) with its own group-commit lane.
    - Cost avoided: ~(2n-1) fsyncs per round × 50-1000 µs each ≈ 1-20 ms/round; brings commit latency down to ~250 µs RTT + ~50 µs fsync = 300 µs (LAN) or ~250 µs RTT + 50 µs fsync = ~300 ms WAN bound now dominated by network not disk.
    - Muscle: never fsync per-message on a hot path; fsync per *decision* and reconstruct messages via group-commit. Reapplies at: W67 raft AppendEntries commit (same pattern — fsync per-quorum not per-entry), W68 lock.rs (lock-state change fsync once), W74 matching-engine raft (commit-cert fsync), W83+ ledger VSR PrepareOk batching, W92 ledger VOPR scenarios reuse this exact disk-discipline pattern.
  - **Expect to hit (perf) #2 — O(n) per-value scan on every precommit insert (bar (c) violation)**: `has_2f1_precommits_for_value` that re-tallies the full vote set on each insertion is O(n); called O(n) times per round → O(n²). At n=21 that's ~441 ops (~13 µs); at n=100 (federated consortium) it's ~10k ops (~300 µs) — visible at P99 even on LAN. Worse: it touches the entire vote set on each call, so the cache footprint scales linearly.
    - Fix: maintain a running `per_value_count: AHashMap<Hash, u8>` (or a fixed-cap array indexed by value-hash-low-byte for small vote sets) updated incrementally as votes arrive. Insert → `count[value] += 1`; threshold check → O(1) compare against `quorum`. Bounded: at most `n+1` distinct values per (h,r) (each validator can vote one value or nil).
    - Cost avoided: O(n) → O(1) per insert; at n=21 saves ~12 µs/vote, ~250 µs/round; at n=100 saves ~300 µs/vote, ~30 ms/round (catastrophic-to-acceptable).
    - Muscle: aggregate counts maintained incrementally beat scan-on-query whenever the query is hotter than the aggregation. Reapplies at: W65 prevote VoteSet (same pattern — running tally), W67 raft AppendEntries match-index aggregation, W73 fork_choice descendant-of count, W74 VSR PrepareOk BitSet `count_ones`.
