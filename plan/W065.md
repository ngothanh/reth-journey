  - *Mental model*: partition engine state so each symbol's `OrderBook` is owned by exactly one shard (one pinned core), touched by exactly one task. Cross-shard work flows through the runtime mailbox, never through a lock on the book. Single-writer-by-construction — the same discipline as an LMAX ring per symbol.

  - *Contract* (signature-level — NEVER the body):
    ```rust
    pub struct SymbolShard { book: OrderBook, event_log: EventLog, risk: RiskState, bcast: BroadcastSender }
    // SymbolShard is NOT Sync and is never wrapped in Arc/RwLock by the engine.
    pub struct Engine { shards: Box<[SymbolShard]>, hasher: FxBuildHasher, num_shards: u32, runtime: Runtime }
    impl Engine {
        pub fn submit(&self, order: Order) -> Result<(), SubmitErr>; // route + mailbox push, never touches a book directly
        pub fn cancel(&self, id: OrderId) -> Result<(), SubmitErr>;  // shard_id read from OrderId high bits
        fn route(&self, symbol: &Symbol) -> u32;                     // hash(symbol) % num_shards, stable
    }
    ```

  - *Back-of-envelope*: budget is 1 M orders/sec/shard, p99 ≤ 10 µs (W63 v0.5 single-symbol baseline). Submit routing path = 1 hash (~30-50 ns FxHash on a short symbol) + 1 modulo (~5 ns) + 1 channel push (~50 ns) ≈ 100-150 ns p50 — that leaves ~9.85 µs for actual matching. Two reference points, kept distinct: L1 access ~0.5 ns; NUMA-local main-mem ~100 ns; cross-NUMA-node fetch ~200 ns (Jeff-Dean main-mem 100 ns × ~2 for interconnect) = **400× cliff vs L1** / **~2× tax vs local main-mem** (the cliff that bites the hot path is the 100 ns local → 200 ns remote step on a book mutation that misses L1/L2). At ~3 cache lines touched/order, NUMA-blind allocation costs ~600 ns/order ≈ 60% of the per-order budget — that is the perf cliff this Build must avoid. `Arc<RwLock>` adds ~10 ns CAS + ~10 ns refcount per access = 20 ms/sec of pure sync waste per shard at 1 M/sec.

  - **Requirements** R1..R8 — write in `crates/matching-engine/notes/65_shard_design.md`:
    - R1. `SymbolShard` owns its `OrderBook`, `EventLog`, risk impl, and broadcast sender by value. No `Arc`, no `RwLock` around it. `SymbolShard: !Sync`.
    - R2. `Engine.shards: Box<[SymbolShard]>` where `len = num_shards` (not num_symbols). Typically `num_shards = num_cores` or `num_NUMA_local_cores`.
    - R3. **Symbol routing**: `route(&symbol) -> shard_id` via `hash(symbol) % num_shards`. Stable mapping; rebalance is offline-only at v0.5. Hasher constructed ONCE per `Engine`.
    - R4. **Single-writer per shard**: only the owning shard's task processes orders for its symbols. No cross-shard locking on the book; cross-shard work flows through the runtime mailbox (per-shard channel, W60 primitive).
    - R5. **NUMA-local memory**: each shard's `OrderBook`, `EventLog`, and per-call scratch buffers live on the same NUMA node as the shard's pinned core. Verified by `numastat -p <pid>` showing ≥95% local hits.
    - R6. **Linear scaling**: 8-shard aggregate throughput ≥ 6× single-shard throughput. (1.0× linear is unrealistic; 6× is the practical floor.)
    - R7. **Per-shard budget**: 1 M orders/sec/shard sustained; p99 ≤ 10 µs per shard.
    - R8. **Zero allocations on dispatch**: `MatchCommand` reuses a per-shard mailbox slab; no per-order alloc on the routing path. OrderId encodes shard_id in its high bits.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `route_hash_stable` reports a different `shard_id` on each call:**
    - Symptom: `route("BTC-USDT")` returns 3, then 7, then 1 — assertion fails on the second call.
    - Why: you constructed `ahash::RandomState::new()` (random per-process seed, actually re-seeded per call) inside `route()`. A randomly-seeded hasher is non-stable across calls.
    - Fix: hold a **fixed-seed** hasher (`FxBuildHasher` or `RandomState::with_seeds(const,...)`) as an `Engine` field; reuse across calls.
    - Cost avoided: routing correctness (a wrong shard means a lost order) — not a perf card, a correctness card.
    - Muscle: routing must be deterministic — a routing hasher is fixed-seed and engine-scoped, never random-per-call. Reapplies at: W74 raft per-shard request routing, W83 ledger AccountId → shard mapping.

  - **(SENIOR) When `submit_p50_under_200ns` reports ~250-400 ns p50 (and a wider p99):**
    - Symptom: submit path p50 ~250-400 ns — cleanly OVER the 200 ns bound and ~2-3× the ~150 ns target. Flame graph shows ~40% in `RandomState::new` + keyed-init (`hash_one` re-deriving its keys from a freshly-seeded state every call); if the naive impl boxed the hasher, an extra ~10% sits in `__rust_alloc`/`__rust_dealloc` and the p99 blows past 300 ns from allocator jitter.
    - Why: you constructed a fresh hasher on each `route()` call. `RandomState::new()` is not free at hot-path scale: the process-global atomic counter read + address reads + per-call keyed-hashing setup land the WHOLE route at ~250-400 ns p50 — comfortably above the 200 ns bound even with NO heap alloc. A `Box<dyn Hasher>` variant adds a real ~50 ns heap alloc/free on top, pushing the tail past the 300 ns p99 bound.
    - Fix: hold the hasher (fixed-seed `FxBuildHasher`) as a field on `Engine`; reuse. Route becomes ~30-50 ns hash + ~5 ns modulo + ~50 ns push ≈ 100-150 ns p50, well under 200 ns / 300 ns.
    - Cost avoided: ~100-250 ns/submit of redundant hasher-state init removed (the per-call `RandomState::new()` route is 250-400 ns; the reused-hasher route is 100-150 ns — a ~150 ns/submit saving, more if the naive impl boxed the hasher); at 1 M submits/sec that's ~100-250 µs/sec reclaimed (**bar (c) violation** when shipped — submit eats budget that belongs to matching). Allocs/submit: 0 → 0 for the `RandomState::new()` reach (it does not allocate, but still busts the latency bound); 1 → 0 only if the naive impl used a boxed hasher.
    - Muscle: any hot-path hasher is CONSTRUCTED ONCE per engine, not per call. Reapplies at: every engine-level hash routing in this project; W74 raft routing, W95 mini-db shard routing.

  - **(SENIOR) When `dispatch_zero_alloc` flags ~1 M allocs/sec:**
    - Symptom: heaptrack tags ~1 alloc/order on the dispatch path; the zero-alloc assertion fails.
    - Why: `MatchCommand::Submit(order)` boxes the order (or the channel allocates a node per send) on every dispatch.
    - Fix: use a pre-allocated per-shard mailbox slab (W60 bounded channel writes into a ring slot by value, no node alloc). `MatchCommand` is a `Copy`/small POD enum, not a `Box`.
    - Cost avoided: ~50 ns malloc/order × 1 M/sec = 50 ms/sec; closes allocator jitter on the hot path (**bar (c) violation** — allocator in the inner loop). Allocs: 1/order → 0.
    - Muscle: the dispatch path is static-memory — pre-allocate the mailbox slab; never `Box` per message. Reapplies at: W77 aeron term buffer, W85 marketdata RX queue, W92 ledger VOPR message pool.

  - **(EXPERT) When `per_shard_p99_under_10us` reports p99 ≈ 35 µs and the flame graph shows `Arc::clone` + `RwLock::write` at ~30% CPU:**
    - Symptom: per-shard p99 3.5× over budget; `Arc::clone`/`RwLock::write` dominate.
    - Why: you wrapped `SymbolShard` in `Arc<RwLock<_>>` "just in case". Every access pays atomic CAS on `read()`/`write()` (~10 ns uncontended) on EVERY order; Arc refcount inc/dec adds ~10 ns each; cross-thread decrements ping-pong the refcount cache line.
    - Fix: own `SymbolShard` **by value** inside the per-shard task. Shards live as `Box<[SymbolShard]>`; each shard's data is touched only by its owning task. Cross-shard work goes through `runtime::submit_to(shard_id, FnOnce)` (W60) — the mailbox is the synchronization point, not the shard. Add `arc_rwlock_compile_fail` to lock the invariant.
    - Cost avoided: ~20 ns sync/access × 1 M/sec ≈ 20 ms/sec removed per shard (**bar (c) violation** — lock on the critical path). Eliminates the lock as a scalability ceiling.
    - Muscle: thread-per-core = single-owner-by-design; reaching for `Arc<RwLock<_>>` is a smell that the ownership model is wrong — the mailbox is the synchronization boundary. Reapplies at: W74 raft-backed engine per shard, W77 aeron subscriber state, W83 ledger-deterministic per-shard SM, W95 mini-db memtable.

  - **(EXPERT) When `8_shard_linear_scaling` fails clause (b) — node-1 shards (4-7) at ~0.5× node-0 shards — and `numa_local_alloc_verified` shows ~40% local hits on shards 4-7:**
    - Symptom: on the 2-NUMA host the parity clause fires first (node1_min ~0.5× node0_min, < the 0.9× floor); aggregate may also dip toward ~3.2× (vs 6×). `perf c2c` flags 30-60% of cache lines as cross-NUMA-node fetches; shards 4-7 measure half the throughput of shards 0-3. (On a single-NUMA box the test SKIPs, so this failure only surfaces where it is real.)
    - Why: at the default Rust allocator, `Engine::new` allocates all shards on the thread that called `new` — likely node-0. When shard-7 pins to a core on node-1, every `book` mutation that misses cache crosses the interconnect: ~200 ns cross-node vs ~100 ns NUMA-local main-mem — a ~2× tax on every cache-missing access (and ~400× vs the ~0.5 ns L1 hit it should have been) on the critical path.
    - Fix: per-shard NUMA-local allocation. In the shard's init code (running on its own pinned task), look up `numa_node_of_cpu(core_id)`, allocate `OrderBook`, `EventLog`, and scratch via `numa_alloc_onnode(size, node_id)` (libnuma), or install a per-shard allocator bound to the node via the `Allocator` API. Verify with `numastat -p <pid>`.
    - Cost avoided: ~100 ns per touched cache line that crosses the interconnect (200 ns remote − 100 ns local); at 1 M orders/sec/shard × ~3 cache-missing lines/order ≈ 300-600 ns/order ≈ 30-60% of the per-order budget (**bar (c) violation** — cross-NUMA fetch in the hot path). Reclaims linear scaling.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  - **(NEWBIE) When `two_v_two_nil_advances_round` hangs forever — no round advance:**
    - Symptom: 2 nodes precommit V, 2 precommit nil; total = 4 ≥ quorum 3; no value has majority. Expected: timer fires, round advances. Actual: hang.
    - Why: you didn't set the precommit timer when 2f+1 total precommits arrive without a single-value majority; the state machine sits in `Step::Precommit`.
    - Fix: after the same-value-majority check fails, `if self.votes.count_precommits(h, r) >= quorum && self.step == Step::Precommit { self.set_timer(Step::Propose, self.precommit_timeout) }`. On expiry, advance round.
    - Cost avoided: liveness-class — without the timer the validator stalls forever (block production halts).
    - Muscle: BFT round-advance requires explicit timers — no commit AND 2f+1 total mixed = timer-driven retry. Reapplies at: W68 lock.rs round transition, W73 view change.

  - **(SENIOR) When `bench_threshold_check_constant_time` reports ~250 ns/check at n=21 (and ~30 ms/round at n=100):**
    - Symptom: each check O(n); at n=21, ~5 µs/round of scanning; at n=100, ~30 ms/round.
    - Why: `has_2f1_precommits_for_value` re-tallies the full vote set per insertion → O(n²)/round.
    - Fix: running `per_value_count: BTreeMap<Hash, u8>` per (h,r), updated incrementally; threshold check is O(1) compare. Mirror of the W65-Wed prevote fix.
    - Cost avoided: O(n) → O(1)/insert; saves ~250 µs/round at n=21, ~30 ms/round at n=100 (**bar (c) violation** — O(n²) on the commit path).
    - Muscle: aggregate counts maintained incrementally beat scan-on-query when the query is hotter than the aggregation. Reapplies at: W65 prevote VoteSet, W67 raft match-index aggregation, W73 fork_choice descendant count, W74 VSR PrepareOk `count_ones`.

  - **(SENIOR, **bar (c)**) When `commit_cert_fsync_once_per_commit` reports ~210 fsyncs for 10 commits and `commit_latency_lan_under_1ms` reports ~20 ms p99:**
    - Symptom: at n=21, ~21 fsyncs/round × 10 commits = ~210. `iostat -x 1` shows the WAL device pinned at ~21 IOPS during commit bursts; p99 tracks fsync time, not network RTT.
    - Why: naïve impl appends each incoming Precommit to the WAL and fsyncs to "ensure durability before increasing the tally". At n=21 × 50-1000 µs/fsync = 1-20 ms/round of pure fsync stall.
    - Fix: **group-commit on precommit votes** — buffer in memory, fsync ONCE when the 2f+1 threshold trips (forming the commit certificate). The certificate IS the durable record; individual votes need not survive a crash (replicas re-vote after recovery via view-change). Wire into the W26 `GroupCommit` primitive. Equivocation evidence (rare) uses a separate group-commit lane.
    - Cost avoided: ~(2n-1) fsyncs/round × 50-1000 µs ≈ 1-20 ms/round; commit latency drops to ~250 µs RTT + ~50 µs fsync ≈ 300 µs LAN (**bar (c) violation** — fsync per message on the finality path).
    - Muscle: never fsync per-message on a hot path; fsync per *decision* and reconstruct messages via group-commit. Reapplies at: W67 raft AppendEntries commit, W68 lock.rs (lock-state change fsync once), W74 matching-engine raft, W83+ ledger VSR PrepareOk batching, W92 ledger VOPR.

  - **(EXPERT) When `lock_persists_into_next_round` shows the validator prevoting X (new proposal) instead of locked V:**
    - Symptom: validator cast Precommit(V) at round 1, then in round 2 received Proposal(X) and prevoted X — ignoring its lock. This is the COMPOSITION of precommit (this Build) and prevote (W65 Wed).
    - Why: lock-on-precommit didn't fire (`locked_value` stayed `None`), OR the round-2 prevote logic (W65 Wed) doesn't check the lock first.
    - Fix: ensure R4 — the precommit-cast site SETS `locked_value` before returning. Confirm the prevote handler (W65 Wed Phase-3 #equivocation card / lock-priority) checks lock first. Both phases must agree on the lock contract.
    - Cost avoided: a missed lock lets a later round prevote a different value → potential double-commit (safety).
    - Muscle: the lock invariant spans prevote AND precommit — both phases must honor it. Reapplies at: every BFT lock-respecting code path; W68 integration, W73 HotStuff lock-on-prepareQC.

  - **(EXPERT, **bar (c)** safety) When `byzantine_precommit_split_no_double_commit` / `safety_10_heights_with_byzantine` show two honest validators committed different values:**
    - Symptom: 4-node 1-Byzantine; Byzantine sends inconsistent precommits to subgroups; honest {0,1} commit V while {2,3} commit V'. Agreement broken.
    - Why: either (a) commit predicate wrong (commit on 2f+1 ANY instead of SAME), OR (b) lock-on-precommit missing — validator 2 cast Precommit(V) at round 1 without locking, then cast Precommit(V') at round 2.
    - Fix: enforce R2 — commit only on `per_value_count[V] >= quorum`, never on `total >= quorum`. Enforce R4 — when casting any non-nil precommit, ATOMICALLY set locked_value/locked_round in the same block BEFORE broadcasting. Reproduce the failing trace; confirm both fixes.
    - Cost avoided: a double-commit is a chain fork — the worst BFT failure (**bar (c)** — deterministic-sim must catch this before ship).
    - Muscle: BFT safety = (commit predicate) AND (lock invariant) — both must hold; either alone is insufficient. Reapplies at: W68 BFT safety integration test, W73 HotStuff variant, W74 VSR safety.
