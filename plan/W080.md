    ```rust
    pub struct FixSession {
        pub session_id: SessionId,        // (BeginString, SenderCompID, TargetCompID)
        pub state: SessionState,
        pub seq_out: u64,                  // next outgoing MsgSeqNum
        pub seq_in: u64,                   // next expected incoming MsgSeqNum
        pub heartbeat_interval: Duration,
        pub last_sent: Monotonic,
        pub last_received: Monotonic,
        pub outbound_log: Vec<FixMessage>, // for resend
    }
    pub enum SessionState { Disconnected, LogonSent, LoggedIn, ResendRequested { from: u64, to: u64 }, LogoutSent }
    pub enum FixMessage {
        Logon { sender: CompId, target: CompId, heartbt_int: u16, reset_seq: bool, seq: u64 },
        Heartbeat { test_req_id: Option<String>, seq: u64 },
        TestRequest { test_req_id: String, seq: u64 },
        ResendRequest { begin_seq: u64, end_seq: u64, seq: u64 },
        SequenceReset { new_seq: u64, gap_fill: bool, seq: u64 },
        Logout { reason: Option<String>, seq: u64 },
        Application(AppMsg),  // NewOrderSingle, ExecutionReport, etc.
    }
    impl FixSession {
        pub fn handle_incoming(&mut self, msg: FixMessage) -> Result<Vec<FixMessage>> {
            // 1. Validate MsgSeqNum:
            //    - == seq_in → process normally, seq_in++
            //    - > seq_in → gap detected, send ResendRequest(seq_in, msg.seq-1)
            //    - < seq_in → if PossDupFlag, accept; else: serious error, terminate session
            // 2. State machine transitions...
        }
        pub fn handle_resend_request(&mut self, req: ResendRequest) -> Vec<FixMessage> {
            // Walk outbound_log, replay messages in [begin_seq, end_seq] with PossDupFlag=Y
            // Admin messages (heartbeat, etc.) skipped via SequenceReset(gap_fill=true)
        }
        pub fn tick(&mut self, now: Monotonic) -> Vec<FixMessage> {
            // Send Heartbeat if last_sent > heartbeat_interval
            // Send TestRequest if last_received > heartbeat_interval * 1.2
            // Force logout if last_received > heartbeat_interval * 2.4
        }
    }
    ```
    **Invariants**: (i) `MsgSeqNum` is strictly monotonic per direction. (ii) Lost gap → ResendRequest, NOT silent drop. (iii) Re-sent messages carry `PossDupFlag=Y`. (iv) Admin messages (Heartbeat, TestRequest) are NOT re-sent — replaced by `SequenceReset(GapFillFlag=Y)`. (v) Session state must persist across restarts — sequence numbers durable.
  - **Back-of-envelope**: target 100k msg/s session throughput, P99 parse+dispatch <2 µs. FIX wire is tag=value SOH-delimited ASCII — parse cost dominated by integer-from-ASCII conversion (~10 ns/field) and SOH scanning. A typical NewOrderSingle has ~20 fields = ~200 ns parse + ~50 ns dispatch + ~100 ns app handler = ~350 ns/msg → 2.8M msg/s theoretical. Realistic: ~50 ns variability per field (some tags require lookup in a tag-table); add cache misses on cold session state (~100 ns total) = ~500 ns/msg = 2M msg/s. The 100k msg/s target is comfortable. seq_out durability: `wal::append` on every send = ~1 µs (group commit amortizes ~10 sends per fsync), so seq durability is the limit at ~10k msg/s sustained unless group-commit batches aggressively. Outbound log retention: keep last 100k messages in a ring (~6 MB at 64 B/msg) for resend; older messages → SequenceReset(GapFill).
  - **Build steps**: 1. (~30 min) Message types + FIX wire codec (tag=value SOH-delim). 2. (~30 min) Session state machine. 3. (~40 min) `handle_incoming` — gap detection + ResendRequest emission. 4. (~30 min) `handle_resend_request` — outbound log walk + gap-fill admin elision. 5. (~30 min) Heartbeat + TestRequest timeout logic. 6. (~20 min) Logout flush — drain pending writes before sending Logout. 7. (~Tue tests.)
  - **Pitfalls** (named, 5):
    - *Sequence-number gap recovery*: **Symptom**: subscriber missed message 100, app sends 101..200; subscriber receives 101 (seq_in=100), should ResendRequest(100, 100) — but unbounded ResendRequest can flood. **Fix**: ResendRequest covers small range (100, 0=infinity allowed by spec but never in practice — bound to 999); recipient gap-fills admins, replays app messages. Cap retransmits.
    - *Paired-session ordering*: **Symptom**: client+server each have own sequence space; deadlock if both wait for the other's resend. **Fix**: per FIX 4.4 §4.5.1: "If both parties simultaneously have lost messages, the resends must be processed in the order they are received, NOT batched." Document idiomatic state machine.
    - *Logout flush*: **Symptom**: send Logout, peer's reply (ack) crosses our outgoing app msgs in flight → app msgs lost (peer already considers session closed). **Fix**: on Logout intent, stop accepting new app sends; flush outbound queue; THEN send Logout; await peer's Logout ack with timeout; then close TCP.
    - *Session-reset on Logon*: **Symptom**: Logon(reset_seq=true) silently resets seq_out to 1 — but only if both sides agree (Tag 141 in both directions). Asymmetric reset = catastrophe (Knight Capital pattern). **Fix**: server validates Tag 141 on Logon; rejects if asymmetric; logs alert.
    - *Durability of seq_out*: **Symptom**: app crash between sending app message and persisting seq_out → restart sends with same seq, peer rejects ("expected N+1, got N"). **Fix**: persist seq_out BEFORE sending message via wal::Sequencer. Recovery on startup reads last persisted seq_out + 1.
  - **Expect to hit (perf) #1 — `wal::append` + fsync per outbound message (bar (c) violation)**: naive "persist seq_out before sending" calls `wal.append(seq).then(wal.fsync())` per message — fsync is ~5 ms on consumer SSD, ~100 µs on enterprise NVMe with write-back-cache disabled. Even on NVMe, 100 µs × 100k msg/s = 100% CPU on fsync — and disk IOPS budget (1M IOPS on top NVMe) gets eaten by one session. Symptom: session throughput caps at 10k msg/s; `iostat` shows fsync dominating; multiple parallel sessions DON'T help (fsync serializes at the disk). Fix: group commit — collect outbound sends into a batch (10 ms window OR 64 messages, whichever first), single wal append + single fsync covers the whole batch. Each message's "ack to sender" waits for the group commit. Latency: P99 send-to-ack ~10 ms (group window) — acceptable for FIX (institutional traders expect ms-grade); throughput climbs to 100k msg/s on a single NVMe. Alternative: io_uring's `IORING_FSYNC` op with `IOSQE_IO_LINK` chains fsyncs; cuts overhead by ~50%. Cost avoided: ~100 µs/msg → ~1 µs/msg amortized = ~100× throughput improvement. Muscle: durability syscalls amortize over BATCHES, never per-element — the W26 WAL group-commit principle is the load-bearing optimization for any durability-bound throughput. Reapplies at: W80 ledger journal commit, W83 archive recorder fsync policy, W89 ledger v1.0 io_uring fsync batching, W92 ledger v1.0 SHIP throughput target.
  - **Expect to hit (perf) #2 — `format!`/`String::push_str` in FIX wire encoder (bar (c) violation)**: a typical first-draft FIX encoder is `let msg = format!("8=FIX.4.4\u{01}9={}\u{01}35={}\u{01}..", body_len, msg_type, ...)` — each `format!` allocates a `String` (~100 ns malloc + ~200 ns format machinery + ~30 ns drop = ~330 ns/msg of pure allocator/formatting overhead). At 100k msg/s, 33 ms/sec of pure encode cost; with multiple sessions, allocator becomes the bottleneck (jemalloc arena lock). Worse: `format!` for integer-to-ASCII (e.g., the body-length tag) uses the full `Display` machinery (~50 ns) when a hand-rolled `itoa`-style integer→buffer is ~5 ns. Symptom: `perf` flame graph shows `core::fmt::write` and `__libc_malloc` dominating outbound; throughput caps at 30k msg/s. Fix: encode directly into a `bufpool::PooledBuf` (W12-W14) via a hand-written encoder: `buf.write_tag(8); buf.write_value(b"FIX.4.4"); buf.write_soh();` etc. Use `itoa::Buffer` (~5 ns/integer) for numeric fields. The buffer is recycled after sending. Cost avoided: ~330 ns/msg × 100k msg/s = 33 ms/sec; eliminates allocator contention; 6× total throughput improvement. Muscle: FIX/text-wire encoders are bar-(c) hot paths — `format!` is forbidden; pre-allocated buffer + hand-coded field writers are mandatory. Reapplies at: W80 ledger JSON-rpc encoder (if any), W82 v1.5 SHIP audit (asserts no `format!` in matching hot path), W84 archive metadata encoder.

- [ ] [NEW v2 aeron v0.7] **Build**: `crates/messaging-aeron/src/multicast.rs` — UDP multicast publisher: IGMP join,
  TTL, source filter. (~120 min)
  - **Why**: Multicast is the *throughput multiplier* of market-data fan-out — publisher sends ONE packet, network duplicates to N subscribers. CME's GS-MDP, Nasdaq's ITCH UDP, NYSE's Pillar all use multicast. Without multicast, fanning out to 1000 subscribers = 1000 packets emitted. With it = 1 packet (network does the rest). Tier-A exchange backbone.
  - **Read first**: Aeron `MulticastUdpChannelTransport.java`. IETF RFC 1112 (IP Multicast). IGMPv2/v3 RFC 3376. CME MDP 3.0 multicast group layout doc. Cloudflare blog "How Multicast Works".
  - **Design**:
    ```rust
    pub struct MulticastPublication {
        pub socket: UdpSocket,
        pub group: SocketAddrV4,            // multicast addr (224.0.0.0/4)
        pub interface: Ipv4Addr,             // outbound IF
        pub ttl: u32,                        // multicast TTL (defaults: 1 = LAN only, 32 = same site)
        pub log_buffer: LogBuffer,            // same term buffer abstraction
    }
    pub struct MulticastSubscription {
        pub socket: UdpSocket,
        pub group: SocketAddrV4,
        pub interface: Ipv4Addr,
        pub source: Option<Ipv4Addr>,       // SSM: filter by source
    }
    impl MulticastPublication {
        pub fn create(group: SocketAddrV4, iface: Ipv4Addr, ttl: u32) -> Result<Self> {
            let socket = UdpSocket::bind((iface, 0))?;
            socket.set_multicast_ttl_v4(ttl)?;
            socket.set_multicast_if_v4(&iface)?;
            socket.set_multicast_loop_v4(false)?;   // don't loop back to self
            Ok(MulticastPublication { socket, group, /* ... */ })
        }
        pub fn offer(&self, frame: &[u8]) -> Result<()> {
            self.socket.send_to(frame, self.group)?;
            Ok(())
        }
    }
    impl MulticastSubscription {
        pub fn create(group: SocketAddrV4, iface: Ipv4Addr, source: Option<Ipv4Addr>) -> Result<Self> {
            let socket = UdpSocket::bind((Ipv4Addr::UNSPECIFIED, group.port()))?;
            socket.set_reuse_port(true)?;
            // Join group
            if let Some(src) = source {
                // IGMPv3 SSM: join (src, group)
                socket.join_multicast_v4_with_source(&group.ip(), &iface, &src)?;
            } else {
                // IGMPv2 ASM: join group
                socket.join_multicast_v4(&group.ip(), &iface)?;
            }
            Ok(MulticastSubscription { socket, group, interface: iface, source })
        }
    }
    ```
    **Invariants**: (i) Multicast addresses in 224.0.0.0/4. Avoid 224.0.0.0/24 (link-local reserved). Production typically 239.0.0.0/8 (admin-scoped). (ii) TTL bounds geographic reach: 1=LAN, 32=site, 64=region. (iii) `set_multicast_loop_v4(false)` on publisher — don't receive own packets. (iv) Subscriber must `IP_ADD_MEMBERSHIP` (IGMP) on the correct interface; multi-NIC hosts choose explicitly.
  - **Back-of-envelope**: multicast is a **throughput multiplier** — publisher sends 1 packet, network duplicates to N subscribers. Publisher cost is INDEPENDENT of N (vs unicast = N × per-packet cost). 1 pub + 10 subs at 1M pps unicast = 10M packets emitted ≈ 10 Gbps wire (limit on 1 Gbps NIC; saturates 10 GbE). 1 pub + 10 subs at 1M pps multicast = 1M packets emitted ≈ 1 Gbps wire on publisher side; switch duplicates to each subscriber on the egress port (zero CPU on publisher). LAN P99 latency target <50 µs: per-packet path = userspace send (~1 µs) + kernel UDP layer (~500 ns) + NIC transmit (~5 µs depending on NIC) + switch forwarding (~1-3 µs Cisco/Arista LAN) + receiver kernel (~500 ns) + userspace recv (~1 µs) = ~10-20 µs ideal; tail covers occasional NIC queue depth, IGMP overhead. IGMP join cost: ~1-3 ms one-time per group join (router needs to update mcast routing table); negligible at steady state. TTL choice matters for COST: TTL=1 stays on LAN switch (no router); TTL=2+ traverses router (router does PIM/MSDP processing — adds ~5-10 µs and may rate-limit). For HFT exchange feeds, ALL subscribers are on the same VLAN as the publisher — TTL=1 is optimal.
  - **Build steps**: 1. (~25 min) Publication setup (socket opts). 2. (~30 min) Subscription with `join_multicast_v4`. 3. (~25 min) SSM optional path with `join_multicast_v4_with_source` (W81 builds this further). 4. (~20 min) Integration with term buffer — multicast publication uses same LogBuffer abstraction. 5. (~20 min) Smoke test: 1 pub, 5 subs, all on loopback (lo's multicast must be enabled: `ip link set lo multicast on`).
  - **Pitfalls** (named, 4):
    - *IGMP cloud-env support*: **Symptom**: deploy to AWS / GCP / Azure → IGMP not supported by default; multicast doesn't work. **Fix**: document — multicast is for on-prem / colo (where you control the switch). Cloud needs overlay (e.g., AWS Transit Gateway multicast, or app-layer fan-out). For testing, use `lo` interface.
    - *Kernel route-table interaction*: **Symptom**: multicast packet drops because routing table doesn't have a route for the multicast group. **Fix**: explicit `ip route add 239.0.0.0/8 dev eth0` or rely on `IP_MULTICAST_IF` socket option which bypasses routing.
    - *Multi-NIC interface ambiguity*: **Symptom**: host has eth0 (frontend) and eth1 (mcast backbone); IGMP joins on eth0 by default → no traffic received. **Fix**: explicit `setsockopt(IP_MULTICAST_IF, eth1.addr)` on subscription. Test with multi-NIC fixture.
    - *TTL too low*: **Symptom**: TTL=1, packet doesn't cross router → 0 subscribers on another VLAN receive. **Fix**: configure TTL appropriately for deployment topology; document the default and how to bump.
  - **Expect to hit (perf) #1 — `set_multicast_loop_v4(true)` (default) causes self-receive (bar (c) violation)**: by default, multicast sockets receive their own packets (loopback enabled). Publisher's `send_to` thus delivers a copy back into the kernel's recv queue for the same socket — at 1M pps, that's 1M extra packets/sec processed by the publisher's recv path = 100% CPU on a useless self-copy. Worse: the publisher's kernel allocates a sk_buff per loop-back packet (~256 B + struct overhead = ~1 KB allocation/pkt = ~1 GB/s allocator churn). Symptom: publisher CPU saturates at 1M pps despite emitting only 1M packets; `netstat -su` InDgrams matches OutDgrams; bench shows publisher unable to scale past 800k pps. Fix: `socket.set_multicast_loop_v4(false)` at construction — explicit in the design code already. Verify with `getsockopt(IP_MULTICAST_LOOP)`. For test scenarios where you DO want to receive own packets, use a separate subscription socket. Cost avoided: ~1M packet copies/sec; ~1 GB/s allocator churn; restores publisher to N-independent emit rate (the WHOLE POINT of multicast). Muscle: every default socket option is a potential bar-(c) violation — audit `getsockopt` for `IP_MULTICAST_LOOP`, `SO_REUSEADDR`, `TCP_NODELAY`, `IP_TOS` at startup. Reapplies at: W81 SSM subscription option audit, W82 Image socket option audit, W85+ marketdata-kernelbypass AF_XDP socket options.
  - **Test scenarios**: (a) 1 publisher, 1 subscriber on loopback → receives. (b) 1 publisher, 10 subscribers same group → all receive same packets (1 packet emitted, 10x delivered). (c) SSM: subscriber filters by source IP → only matching source's traffic. (d) Cross-host (if testbed available): publisher on host A, subscribers on hosts B+C → IGMP join propagates, both receive.
  - **Acceptance**: 1 pub + 10 subs, throughput identical to 1 pub + 1 sub (bandwidth multiplied at the switch, not at publisher). P99 latency LAN < 50 µs. Inheritance: term_buffer (same abstraction), bufpool.
  - **Downstream**: W81 SSM (Source-Specific Multicast) filter enrichment. W82 Image module integrates multi-source loss-detector per multicast group. Tier-A interview: "how does CME MDP-3 fan out to thousands of subs?" → multicast + SSM + this exact pattern.

- [ ] **Build**: `crates/ledger-deterministic/src/state_machine.rs` —
  `StateMachine { accounts: BTreeMap<u128, Account>, ... }`. `apply(op: Op) -> Result<OpResult>` is deterministic: no
  `time::wall()`, no `rand`, no f64. Only `time::Monotonic` is allowed and only for instrumentation, never for logic. (~150 min)
  - **Why**: This is the bar-(c) ledger's load-bearing axiom. Every later layer (VOPR W87-88, static-mem W89, io_uring W89, VSR replication W91-92) ASSUMES that `apply(op_stream)` yields a bit-reproducible state across runs, machines, and architectures. One float, one syscall, one allocator-dependent iteration order, and the determinism story collapses — and with it the entire ledger-deterministic v1.0 deliverable.
  - **Back-of-envelope**: target P99 apply <10 µs (v0.5), <3 µs (v0.7), <1 µs (v1.0). A typical Transfer touches 2 accounts (debit + credit lookup + balance check + balance update). With `BTreeMap<u128, Account>`: 2 × O(log N) lookup ≈ 2 × 200 ns at N=1M accounts (cold cache) ≈ 400 ns + 2 balance updates ≈ 50 ns = ~500 ns/op (v0.5 budget met). v1.0 target requires moving to a `FixedMap<AccountId, Account>` (open-addressed, pre-sized at ledger creation), reducing lookup to ~50 ns each = ~150 ns/op. The `BTreeMap` iteration ordering is what makes v0.5 deterministic; the `FixedMap` must equally be order-deterministic (open-addressing with fixed seed is OK). NO syscall in apply (~300 ns each — would blow the v0.7 budget single-handed); NO `Box<dyn>` in op dispatch (vtable ~5 ns + indirect ~5 ns ≈ 10 ns penalty per op; at 1M ops/s = 10 ms/sec). Apply MUST be allocation-free at v1.0 — every Op carries its own pre-allocated result buffer.
  - **Pitfalls** (named, 3):
    - *HashMap iteration order leaks*: **Symptom**: `state_hash()` iterates `accounts.values()` via `HashMap` (insertion-order-randomized) → two machines with same op stream produce different hashes. **Fix**: BTreeMap (sorted) or FixedMap with stable iteration; lint `disallowed-types` bans `std::collections::HashMap` in the module.
    - *Allocator-dependent op order*: **Symptom**: an Op carries `Vec<Item>` whose construction allocator order affects internal layout → cross-machine divergence even if state_hash is sorted. **Fix**: Ops use only `repr(C)` types with no heap inner storage; if collections needed, use `ArrayVec`.
    - *Wall-clock leak via tracing*: **Symptom**: `tracing::info!("apply at {}", Instant::now())` works fine in development but generates a different timestamp each run → if the timestamp ever enters the state (e.g., logged into Account's last_update), determinism breaks. **Fix**: tracing spans must be `cfg(not(determinism))`-gated; only `SeqClock` (op-counter-driven) reaches state.
  - **Expect to hit (perf) #1 — `f64` arithmetic in `apply` (bar (c) violation, correctness AND perf)**: a typical first-pass implementation of a per-balance percentage fee, interest accrual, or stop-trigger comparison uses `let fee = balance as f64 * 0.0025;` — and (i) IEEE-754 division/multiplication is non-deterministic across arches (x86 default rounding mode vs aarch64; aarch64 fma vs x86 separate mul+add), (ii) float ops are ~10-30 cycles ≈ 5-10 ns each vs ~1 ns for integer add. At 1M ops/s × 3 float ops/op = ~30 ms/sec of float overhead PLUS undetectable cross-machine divergence. Symptom: 3-machine VOPR test (W87) discovers a 1-tick discrepancy in <0.01% of scenarios; debugger struggles because the divergence is in the LSB of an `f64`. Fix: integer math throughout — represent percentages as `fee_bps: u32` (basis points), compute `fee = (balance * fee_bps as u64) / 10_000`. Use `q64.64` fixed-point for any ratio that needs more precision. Compile-time lint: `clippy::float_arithmetic` denied at crate level. Cost avoided: ~30 ms/sec of float compute + cross-machine determinism preserved (the catastrophic case). Muscle: deterministic state machine = integer math only, full stop. Reapplies at: W81 circuit breaker bps math, W82 v1.5 SHIP audit (no floats in matching), W87 VOPR cross-machine reproducibility property, W92 ledger v1.0 SHIP audit.
  - **Expect to hit (perf) #2 — `Op::Transfer { .. }` enum dispatch via `match` with cold branches (bar (c) violation)**: the `Op` enum has 3 variants (CreateAccount, Transfer, Lookup); the workload is 90% Transfer (hot), 9% Lookup (warm), 1% CreateAccount (cold). A naive `match` compiles to a jump table, but the CPU's branch predictor learns the discriminant pattern poorly if op streams interleave types — each mispredict ~5 ns. At 1M ops/s with 10% misprediction = ~500 µs/sec wasted; under adversarial input (alternating types), 50% mispredict = ~2.5 ms/sec. Symptom: bench shows wildly varying throughput depending on op-type mix; `perf stat` shows BR_MISP elevated on the apply hot path. Fix: (a) sort the `match` arms by frequency — CPU's static predictor assumes "first arm taken"; put `Transfer` first. (b) For predictable patterns, the discriminant load + branch is cache-resident — ensure the `Op` struct is `repr(u8)` with discriminant at offset 0 (one cache line for the tag). (c) For extreme cases, separate `apply_transfer`, `apply_lookup`, `apply_create_account` and dispatch via a function-pointer table sorted by frequency. Cost avoided: ~5 ns × 100k mispredicts/s ≈ 500 µs/sec; under adversarial mix, ~2.5 ms/sec. Muscle: enum dispatch in a hot loop must order arms by observed frequency; type-pun structs put the discriminant at offset 0. Reapplies at: W74 matching-engine MatchCommand dispatch, W77 NAK message-type dispatch, W82 Image frame-type dispatch, W87 VOPR scenario action dispatch.
