## Tuesday — Design + io_uring impl

- [ ] consensus-engine cross-subsystem feature design. (~30 min)
- [ ] **Build**: `crates/marketdata-kernelbypass/src/io_uring.rs` — `IoUringReceiver` using `io_uring` crate directly.
  Submit-queue / completion-queue patterns. Multi-shot read with fixed buffers. (~total 3.5 hrs across 3 phases)
  - 🔧 **Why this matters**: io_uring is "modern Linux" ingress — amortizes syscall cost; SQPOLL eliminates io_uring_enter from hot path; multi-shot recv + pre-registered buffers = zero copies, zero allocs per packet. Should beat epoll 2-5× at 10M+ pps. Downstream: feed_handler default Transport on Linux; ledger v1.0 io_uring journal reuses ring patterns.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **Requirements** — write in `crates/marketdata-kernelbypass/notes/86_io_uring_design.md`:
    - R1. One multi-shot recv per socket — kernel keeps writing CQEs until cancelled.
    - R2. Provided-buffer ring is the ONLY allocation source — fixed at startup.
    - R3. `ProvidedBuf` Drop returns buffer to ring (RAII).
    - R4. Never copy: bytes live in registered buffer until consumed.
    - R5. 10M pps single-thread loss-free.
    - R6. 2-5× lower CPU than epoll at 5M pps.
    - R7. Min kernel 5.19 (IORING_FEAT_FAST_POLL + IORING_OP_RECV_MULTISHOT); probe at startup; document.

  - **Design walk-through**:
    - D1. Sketch IoUringTransport + ProvidedBuf<'a>.
    - D2. **Pre-mortem (one SQE per recv):** treat io_uring like epoll — submit SQE → submit() → wait CQE → submit again. Each cycle ~250 ns `io_uring_enter`. At 50M pps = 12.5 sec/sec syscall. Walk through multi-shot.
    - D3. **Pre-mortem (CQE payload copy):** extract buf_id then `buf.to_vec()` = 1500 B × 50M = 75 GB/sec memcpy; exceeds L3 bandwidth. Walk through borrow via `ProvidedBuf<'a>`.
    - D4. **Pre-mortem (SQE overflow):** `io_uring_submit()` fails with -EBUSY when SQ full. Size SQ ≥ 2× CQE batch; respect `IORING_FEAT_NODROP`.
    - D5. **Pre-mortem (kernel-version compat):** kernel 5.10 doesn't have multi-shot recv, build fails at runtime. Probe `io_uring_register_probe()` at startup; fallback to single-shot.
    - D6. **Pre-mortem (Provided-buffer leak):** forgot to return buf_id; ring drains to 0. RAII Drop; assertion `buf_id <= ring_capacity`.
    - D7. **Pre-mortem (SQPOLL CPU burn):** core stays at 100% even idle. SQPOLL only for high-rate; for low-rate use cooperative mode.

  - **Output**: `notes/86_io_uring_design.md` with R1–R7 + D1–D7.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  - **When `io_uring_multi_shot_single_sqe_per_socket` reports per-packet SQE submit:**
    - Symptom: bench shows 4M pps ceiling; profile shows `io_uring_enter` at ~95% CPU.
    - Why: implementing recv as "submit SQE → submit() → wait CQE → submit again" — treating io_uring like epoll. Each submission cycle ~250 ns `io_uring_enter`. At 50M pps = 12.5 sec/sec.
    - Fix: submit ONE `IORING_OP_RECV_MULTISHOT` SQE per socket at startup; kernel emits CQE per packet WITHOUT resubmission until `CQE_F_MORE` clears (buffer exhaustion or close). With `IORING_SETUP_SQPOLL`, hot path is zero syscalls in steady state — userspace just drains CQ ring.
    - Cost avoided: ~250 ns × 50M = 12.5 sec/sec → ~5 ns/packet wake-write; 30-50× win.
    - Muscle: io_uring's perf model is "submit job that keeps emitting CQEs"; treating each CQE as one-shot is the foot-gun. Reapplies at: W90 io_uring journal group-commit (one fsync-link chain), W89 AF_XDP RX-ring (ring IS multi-shot mechanism), W90 ledger v1.0 io_uring journal.

  - **When `io_uring_zero_copy_via_provided_buf` reports memcpy of CQE payload:**
    - Symptom: `__memcpy_avx2` dominates profile; cache pollution evicts matching-engine's hot state; throughput plateaus.
    - Why: extracting `cqe.flags >> 16` for buf_id, then `let frame: Vec<u8> = buf.to_vec()` "to make ownership easier" — 1500 B × 50M = 75 GB/sec memcpy.
    - Fix: `ProvidedBuf<'a> { ring: &'a BufRingProvided, buf_id: u16, len: u16 }` borrows; `AsRef<[u8]>` reads through ring directly. Drop returns buf_id to `io_uring_buf_ring_add()`. Document lifetime: ProvidedBuf<'a> cannot outlive next recv_batch cycle for that buffer.
    - Cost avoided: 1500 B × 50M = ~75 GB/s memcpy eliminated; L1/L2 cache footprint freed; P99 latency drops 5-10× because cache misses dominate tail.
    - Muscle: in any "kernel writes into buffer" architecture (io_uring provided buffers, AF_XDP UMEM, RDMA registered memory), buffer IS the data — never copy. Reapplies at: W89 UmemFrame<'a>, W90 io_uring journal write-fixed buffers, W77 messaging-aeron term buffer slots, W82 MBO feed publication slots.

  - **5-year failure mode** (write in `notes/86_io_uring_followup.md`): when zero-copy networking via DMABUF / RDMA reaches commodity, io_uring's provided buffers become wrong layer (kernel still copies to UMEM). Migration: AF_XDP / DPDK takes over receive; io_uring stays for submission queue + fsync batching.

  `ItchParser` (NASDAQ ITCH 5.0 subset), `FixParser` (FIX 4.4 binary subset). (~total 2.5 hrs across 3 phases)
  - 🔧 **Why this matters**: ITCH (US equities/futures: NASDAQ ITCH 5.0, ICE iMpact, CME MDP) + FIX (FX/cross-asset) are dominant wire formats. Building both forces generalization beyond one format's idioms. Downstream: W87 Tue feed_handler.rs wires Transport → FeedParser → messaging-aeron Publication; matching-engine v1.5 ingests via publication.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **Requirements** — write in `crates/marketdata-kernelbypass/notes/86_parse_design.md`:
    - R1. Parse is zero-copy where possible — symbols/ids borrow from `bytes`.
    - R2. `bytes_consumed` returned so caller can advance buffer over multi-message frames.
    - R3. On parse error, parser internal state resettable — call `reset()` to recover at next frame boundary.
    - R4. All numeric fields use fixed-precision integers (no float — VOPR replay requires bit-determinism).
    - R5. ≥30M ITCH msg/s single-thread; <500 ns P99 per ITCH message.
    - R6. Parse 100M ITCH messages from capture file with 0 errors.
    - R7. Allocator-free per-message.
    - R8. FIX tag dispatch via match jump-table (not HashMap — non-deterministic iter order).

  - **Design walk-through**:
    - D1. Sketch FeedParser trait with GAT `type Event<'a>` + ItchParser + FixParser.
    - D2. **Pre-mortem (String/Vec in ItchEvent):** owned `symbol: String` allocates per event; at 30M msg/s = 30M mallocs/sec = 1.5 sec/sec malloc + 240 MB/sec memcpy. Walk through GAT `symbol: &'a [u8; 8]` borrowing from input bytes.
    - D3. **Pre-mortem (HashMap dispatch on FIX tag):** `let value = fields.get(&tag)` over HashMap built per message; HashMap::insert ~30 ns; 20-tag dict per message at 5M msg/s = 3 sec/sec hash math + non-deterministic iter order (breaks VOPR replay). Walk through stack-allocated FixMessage struct + match jump-table.
    - D4. **Pre-mortem (Big- vs little-endian):** ITCH big-endian always; mix-up → prices look like garbage. Const generic assert in build.
    - D5. **Pre-mortem (FIX SOH inside message):** SOH (\x01) appears in repeating-group field; naive scanner breaks. Respect declared body length (tag 9).
    - D6. **Pre-mortem (multi-message frame boundary):** UDP datagram contains 3 ITCH messages; parser stops at first. Caller loops while `bytes_consumed < bytes.len()`.

  - **Output**: `notes/86_parse_design.md` with R1–R8 + D1–D6.

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

  - **When `parse_itch_event_borrows_symbol` fails with owned `String`:**
    - Symptom: profile shows `String` allocation per event; at 30M msg/s = 30M mallocs/sec ≈ 1.5 sec/sec pure malloc + 240 MB/sec memcpy.
    - Why: `AddOrder { symbol: String, ... }` allocates + copies symbol per event.
    - Fix: `ItchEvent<'a>` GAT — `symbol: &'a [u8; 8]` borrows from ingress `bytes: &'a [u8]` buffer. Lifetime tied to io_uring `ProvidedBuf<'a>` / AF_XDP `UmemFrame<'a>`. Numeric fields are `Copy` (`u32`, `u64`, `[u8; 8]`); no String, no Vec anywhere in event hierarchy.
    - Cost avoided: ~50 ns malloc + 8 B memcpy per event; at 30M msg/s = ~1.5 sec/sec reclaimed.
    - Muscle: in any wire-format parser destined for deterministic/latency-bound consumer, event types are GAT-borrowed views over input buffer — never owned. Reapplies at: W87 FeedHandler::run_once event encoding, W74 matching-engine order-event ingestion, W77 messaging-aeron FragmentHandler, W88 ledger VOPR op-stream encoding.

  - **When `parse_fix_no_hashmap_dispatch` reports HashMap usage:**
    - Symptom: per-message HashMap allocation + 20 hash inserts + lookup; ~3 sec/sec hash math at 5M msg/s; downstream VOPR replay at W88 fails because HashMap iter is non-deterministic.
    - Why: implementing FIX `tag=value` dispatch as `let value = fields.get(&tag)` over HashMap<u16, &[u8]>; HashMap::insert ~30 ns + initial allocation; DefaultHasher non-deterministic across runs.
    - Fix: parse FIX tag-by-tag in STREAM ORDER into stack-allocated FixMessage struct with `Option<&'a [u8]>` fields for each known tag. Branch via `match tag { 35 => ..., 49 => ..., ... }` (jump table, ~2 ns). Unknown tags skipped OR into small `ArrayVec<(u16, &'a [u8]), 8>` overflow. No HashMap, no allocation, deterministic.
    - Cost avoided: ~30 ns/tag × 20 tags = 600 ns/message dispatch overhead; ~50 ns malloc/message; plus determinism debt eliminated (W88 VOPR replay requires bit-identical parse output across runs).
    - Muscle: jump-tabled `match` on small known tag set beats HashMap at every scale AND preserves determinism. Reapplies at: W74 matching-engine order-type dispatch, W92 ledger op-type dispatch, W94 exec-vm opcode dispatch, W87 ITCH message-type dispatch.

  - **5-year failure mode** (write in `notes/86_parse_followup.md`): when SBE (Simple Binary Encoding) becomes dominant over FIX 4.4, the tag-dispatch parser becomes wrong abstraction. Migration: SBE schema-driven parser with same borrow-from-buffer discipline.
