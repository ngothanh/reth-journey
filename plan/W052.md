**Monday — Kademlia paper + p2p scaffold**

- [ ] Read Maymounkov & Mazières Kademlia paper. (~90 min)
  - **Why**: Kademlia is the most-deployed peer-discovery DHT (BitTorrent Mainline, IPFS, Ethereum's discv4/discv5, libp2p). Tier-A HFT IC bar (c) — this `p2p` crate is the Layer-4 substrate inherited by consensus-raft (W56+), consensus-bft (W64+), messaging-aeron (W76+ discovery only). Mastery of XOR metric, k-bucket update rule, and FIND_NODE iterative-lookup is interview-load-bearing for distributed systems roles.
  - **Read first**: Maymounkov & Mazières "Kademlia: A Peer-to-peer Information System Based on the XOR Metric" (2002), §2.1 (XOR metric), §2.2 (node state — k-buckets), §2.3 (Kademlia protocol — FIND_NODE / FIND_VALUE / STORE / PING), §2.4 (refinements: parallel lookups α=3, bucket splitting), §4 (security: Sybil mitigations are absent — note this).
  - **Design** (high-level, paper-mapped):
    ```text
    Node identity: 160-bit ID (we use B256 = 256-bit for SHA3 alignment).
    Distance(a, b) := a XOR b, treated as integer.
    Routing table: 256 buckets (one per bit of ID space). Bucket i holds nodes whose distance from self is in [2^i, 2^(i+1)).
    Bucket capacity: k = 20 (Kademlia paper default).
    Lookup parameter: α = 3 (parallelism).
    ```
    **Invariants** (from paper):
    - XOR is a *valid* metric: d(x,x)=0; d(x,y)=d(y,x); d(x,y) ≤ d(x,z) ⊕ d(z,y).
    - Bucket-i invariant: every node in bucket-i shares exactly i leading bits with self.
    - LRU eviction: oldest peer at head of bucket; if bucket full and oldest still responds to PING, NEW peer is dropped (paper §2.2 — counter-intuitive but resists eclipse).
    - FIND_NODE returns k closest peers to target; iterative lookup queries α at a time, terminates when no closer peer found in a round.
  - **Build steps** (just reading today; build starts Tue):
    1. (~30 min) Read §2 of paper. Sketch on whiteboard: 4 nodes with IDs 0000, 0011, 1100, 1111; compute pairwise XOR distance.
    2. (~15 min) Read libp2p `kad-dht` overview docs (https://github.com/libp2p/specs/tree/master/kad-dht). Note libp2p's deviations: 20-byte IDs (SHA-256 truncated), reuse of TCP for transport.
    3. (~15 min) Read Ethereum discv4 RLPx spec (devp2p/discv4.md). Note ethereum uses Keccak256(pubkey) for NodeID, includes endpoint-verification (sender = receiver's view of remote IP).
    4. (~15 min) Read sigp/discv5 Rust impl (https://github.com/sigp/discv5/blob/master/src/kbucket.rs). Note `KBucketsTable` design.
    5. (~15 min) Map onto your design: 256-bit IDs (vs 160-bit Kademlia paper), k=20, α=3. Note you'll need PING-before-evict logic.
  - **Pitfalls** (named, distributed-systems):
    - *Eclipse attack*: attacker creates many node IDs near victim, monopolizes victim's view. **Symptom**: victim sees only attacker-controlled peers. **Fix**: (1) require ID = H(pubkey) with proof-of-work or stake binding; (2) limit per-IP-subnet entries per bucket (e.g. max 2 per /24); (3) random refresh of buckets to detect freshness. Eth discv5 implements all three.
    - *Bucket poisoning via PING-spam*: paper says PING-then-evict — but attacker spamming PINGs to keep stale entries alive blocks new peers. **Symptom**: routing table never refreshes. **Fix**: PING reply must be unsolicited-recent (within e.g. 5s of receiving the ping), AND the PING is rate-limited per-source.
    - *ID-mapping skew*: if node-IDs aren't uniformly random (e.g., chosen by user with vanity prefix), some buckets overpopulate and others starve. **Symptom**: poor lookup performance, certain ID ranges unreachable. **Fix**: enforce ID = H(pubkey); reject vanity-mined keys via PoW difficulty.
    - *NAT-induced asymmetric reachability*: A reachable→B but B unreachable→A (NAT). Adding B to A's bucket pollutes lookups. **Symptom**: lookups time out frequently. **Fix**: endpoint-verification handshake (discv4 ENDPOINTPROOF) — B must echo A's seen-from address before A adds B.
  - **Test scenarios** (to design now, build Wed-Thu):
    - XOR-distance property: `forall a, b, c: d(a, c) ≤ d(a, b) + d(b, c)` (triangle inequality holds under XOR-as-int).
    - Bucket invariant: for each peer in bucket-i, MSB(peer XOR self) is bit i.
    - Eclipse-resistance: insert 100 peers all sharing 252 leading bits with self; verify only k=20 end up in bucket-252 (others rejected or distributed).
  - **Acceptance**: paper notes committed; design doc `notes/p2p_kademlia_design.md` covers XOR metric, k-bucket structure, FIND_NODE iterative algorithm, PING-before-evict, eclipse-mitigation strategy.
  - **Downstream**: every later p2p week reads this doc; W56+ raft uses p2p for peer discovery; W64+ bft same; W76+ aeron discovery same. Bar (c) for L4 substrate.

**Tuesday — `p2p::peer` + node identity**

- [ ] **Build**: `crates/p2p/src/peer.rs` — `PeerId(B256)` derived from public key. `Multiaddr` wrapper. `PeerStore` LRU
  of last-seen peers. (~105 min)
  - **Why**: PeerId derivation is load-bearing for Sybil resistance. If you let users pick IDs, attackers grind vanity IDs to occupy specific k-buckets near victims. Binding ID = H(pubkey) AND requiring ECDSA-signed handshake (W54 Noise) closes that surface.
  - **Read first**: discv5 `crates/discv5/src/node_info.rs` for `NodeId` derivation pattern; Ethereum's ENR spec (EIP-778).
  - **Design**:
    ```rust
    pub struct PeerId(pub B256);  // = keccak256(secp256k1 uncompressed pubkey || ed25519 ed_pubkey)

    impl PeerId {
        pub fn from_secp256k1_pubkey(pk: &[u8; 64]) -> Self {
            Self(keccak256(pk))
        }
        pub fn distance(&self, other: &PeerId) -> U256 {
            U256::from_be_bytes(*(self.0 ^ other.0).as_ref())
        }
        pub fn leading_zeros_xor(&self, other: &PeerId) -> u32 {
            self.distance(other).leading_zeros()  // for bucket index
        }
    }

    pub struct Multiaddr(pub bytes::Bytes);  // /ip4/.../tcp/...

    pub struct PeerStore {
        peers: lru::LruCache<PeerId, PeerInfo>,
        capacity: usize,
    }
    pub struct PeerInfo {
        pub addrs: smallvec::SmallVec<[Multiaddr; 2]>,
        pub last_seen: time::HybridLogicalClock,
        pub successful_pings: u32,
        pub failed_pings: u32,
    }
    ```
    **Invariants**:
    - PeerId is irreversibly tied to pubkey. No setter — only constructors from pubkey bytes.
    - `distance` is total ordering; uniqueness modulo self-distance=0.
    - PeerStore is LRU: full capacity → eviction of least-recently-seen.
    - `last_seen` uses HybridLogicalClock for monotonic-across-restarts ordering.
  - **Build steps** (granular):
    1. (~15 min) `PeerId` newtype on B256. Constructors: `from_secp256k1_pubkey(&[u8; 64])`, `from_ed25519_pubkey(&[u8; 32])`. No `From<B256>` impl (forces derivation path).
    2. (~15 min) `distance` and `leading_zeros_xor` methods. Tests on hand-crafted pairs.
    3. (~15 min) `Multiaddr` wrapper around `Bytes`. Parse `/ip4/127.0.0.1/tcp/30303` via simple recursive-descent (or pull in `multiaddr` crate if happy with dep).
    4. (~20 min) `PeerStore` using `lru::LruCache<PeerId, PeerInfo>`. Methods: `record_seen(peer, addr)`, `record_ping_success(peer)`, `record_ping_failure(peer)`, `evict_failed_above_threshold(failed_max)`.
    5. (~15 min) `PeerInfo` with `last_seen: HybridLogicalClock`. Update via `hlc.advance(received_at)`.
    6. (~15 min) Tests: insert 10k peers into 1k-capacity store, verify LRU eviction; verify distance returns 0 for self.
    7. (~10 min) Property test: `PeerId::distance` symmetry, triangle inequality.
  - **Pitfalls** (named):
    - *PeerId from a raw 32-byte buf accepts adversarial IDs*: providing `PeerId::from_bytes(&[u8; 32])` lets attacker forge any ID. **Symptom**: ID forgery → eclipse attack. **Fix**: omit such a constructor; only pubkey-derivation constructors. If serialization needs a `from_bytes`, gate it behind `#[cfg(test)]` or feature `unsafe-test-utils`.
    - *Multiaddr parsing too lenient*: accepting unknown protocol bytes silently lets attacker inject garbage transports. **Symptom**: panic later on transport dispatch. **Fix**: strict parser, reject unknown protocol IDs with explicit error.
    - *PeerStore LRU thrash under churn*: under heavy lookup miss, LRU evicts good peers. **Symptom**: bucket re-discovery wastes RTTs. **Fix**: add a "sticky" tier for peers above ping-success threshold; only evict from non-sticky tier.
  - **Test scenarios**:
    - 10k random pubkeys → 10k distinct PeerIds (no collision in 256-bit space — verify with hashset).
    - PeerStore capacity-1000, insert 10k: post-insert size = 1000, oldest peers gone, newest kept.
    - PING-failure threshold: peer with 5 failed pings (no successes) is removable; 5 failed + 100 successes is not.
  - **Acceptance**: tests green; property tests for distance symmetry/triangle hold (10k random pairs).
  - **Downstream**: Wed (routing table consumes PeerId distance); W54 (Noise handshake binds pubkey ↔ PeerId); W56+ (raft peer set is `Vec<PeerId>`).

**Wednesday — `p2p::kademlia` routing table**

- [ ] **Build**: `crates/p2p/src/kademlia/table.rs` — `RoutingTable { buckets: [KBucket; 256] }`. K-bucket eviction with
  last-seen ordering. (~105 min)
  - **Why**: The k-bucket data structure is Kademlia's core. Correctness here decides whether your DHT is eclipse-resistant or trivially defeated. The eviction policy (PING-then-evict-if-no-reply) is counter-intuitive but mathematically motivated — Maymounkov & Mazières §4.1.
  - **Read first**: Kademlia paper §2.2 + §4.1; sigp/discv5 `src/kbucket/bucket.rs::Bucket` impl (Rust reference quality).
  - **Design**:
    ```rust
    use arrayvec::ArrayVec;

    const K: usize = 20;            // bucket size
    const N_BUCKETS: usize = 256;   // bit-positions of B256

    pub struct KBucket {
        // Front = least-recently-seen (eviction candidate); back = most recently seen.
        peers: ArrayVec<KBucketEntry, K>,
        replacement_cache: ArrayVec<KBucketEntry, K>,  // candidates waiting for slot
        pending_eviction: Option<PendingEviction>,
    }

    pub struct KBucketEntry {
        pub peer: PeerId,
        pub addrs: smallvec::SmallVec<[Multiaddr; 2]>,
        pub last_seen: HybridLogicalClock,
        pub status: PeerStatus,  // Connected | Disconnected | PendingPing
    }

    pub struct PendingEviction {
        evictee: PeerId,
        challenger: KBucketEntry,
        ping_sent_at: Instant,
    }

    pub struct RoutingTable {
        local_id: PeerId,
        buckets: Box<[KBucket; N_BUCKETS]>,  // boxed: 256 * sizeof(KBucket) is big
    }
    ```
    **Invariants**:
    - bucket index `i = leading_zeros_xor(self, peer)` (range 0..256). Peer is in bucket-i iff first i bits of XOR are zero.
    - Within a bucket: peers sorted by last_seen ascending (front = oldest, back = newest).
    - K-bucket NEVER auto-evicts the oldest peer. On full-bucket-insert: PING oldest; if oldest replies, drop NEW peer; if oldest fails, evict.
    - `replacement_cache` holds challengers during PING-pending state (so concurrent inserts during PING are not lost).
  - **Build steps** (granular):
    1. (~15 min) `KBucket` skeleton with ArrayVec<_, 20>. Define `KBucketEntry` and `PeerStatus`.
    2. (~20 min) `RoutingTable::new(local_id)`: allocate `Box::new([KBucket::new(); 256])`. Note: `KBucket` must impl `Copy` or use array init macro (`std::array::from_fn(|_| KBucket::new())`).
    3. (~20 min) `RoutingTable::add_peer(&mut self, entry)`: compute bucket, if not full → push back; if full → produce a `BucketAction::PingOldest` event (caller is responsible for sending PING).
    4. (~15 min) `RoutingTable::on_ping_reply(&mut self, peer)`: move peer to back of bucket; if pending_eviction had this peer as evictee, cancel the eviction and DROP the challenger (paper-spec).
    5. (~15 min) `RoutingTable::on_ping_timeout(&mut self, peer)`: evict the peer from front; promote replacement_cache head into bucket.
    6. (~10 min) `RoutingTable::closest_peers(&self, target: PeerId, n: usize) -> Vec<KBucketEntry>`: scan adjacent buckets outward starting from `target_bucket_idx`, collect ≤ n.
    7. (~10 min) Tests: insert 21 peers same bucket → 21st triggers PING event; PING reply preserves oldest; PING timeout evicts.
  - **Pitfalls** (named, distributed):
    - *Pending-PING race*: peer A is being pinged (pending_eviction). Concurrent ADD_PEER for B (same bucket) → loses B if not queued. **Symptom**: dropped peers under load. **Fix**: `replacement_cache` holds pending adds; on resolution, drain into bucket.
    - *Subnet collision pollution*: 100 peers from same /24 fill a bucket. Easy eclipse vector. **Symptom**: attacker on one IP/24 dominates one bucket. **Fix**: per-bucket subnet cap (e.g., max 2 entries per /24, max 8 per /16). discv5 implements this.
    - *Bucket-split asymmetry*: when self-bucket fills, paper says split it; other buckets just reject. Mis-implementing split leaves the table unable to grow near self. **Symptom**: lookups near self degrade. **Fix**: our 256-bucket scheme dodges this (one bucket per leading-zero count), no split needed.
    - *NUMA-style hot bucket*: bucket-0 (max distance) gets all-far peers — dominates inserts. **Symptom**: bucket-0 thrashes while bucket-255 stays empty. **Fix**: this is expected; ID-space uniformity makes it OK over time.
  - **Test scenarios** (adversarial):
    - Insert 30 peers to same bucket: 20 in bucket, 10 in replacement_cache, no PING events from 21st onward (because we hold replacement_cache).
    - Subnet-cap: 5 peers from `192.168.1.0/24` → only 2 admitted to bucket, 3 rejected with `SubnetCapReached` error.
    - PING-flood: send 1000 PINGs from one peer in 1s; verify rate-limit kicks in, peer is throttled.
    - Property: forall (table, peer): if peer is in `table`, then `table.closest_peers(peer, 1)` returns peer itself.
  - **Acceptance**: bucket invariant verified via property test (peer in bucket-i iff XOR-leading-zeros = i); subnet-cap test green; concurrent-insert-during-PING test green.
  - **Downstream**: Thu FIND_NODE uses `closest_peers`; W56+ raft consumes routing table for peer dialing; eclipse-resistance properties hold for entire L4 stack.

**Thursday — `p2p::kademlia` FIND_NODE**

- [ ] **Build**: `crates/p2p/src/kademlia/protocol.rs` — FIND_NODE, FIND_VALUE, STORE, PING RPCs. Parallel α=3 lookups. (~105 min)
  - **Why**: Iterative-lookup with α=3 parallelism is THE distinguishing feature of Kademlia. It converges in O(log n) hops with high probability, tolerates Byzantine peers (returns from non-faulty peers dominate), and handles churn gracefully. Getting α-parallel-with-deduplication correct is interview gold for distributed systems.
  - **Read first**: Kademlia paper §2.3 (FIND_NODE algorithm), §2.4 (refinements); discv5 spec; sigp/discv5 `src/query/find_node_query.rs`.
  - **Design**:
    ```rust
    pub enum KadRpc {
        Ping { id: B256, sender: PeerId },
        Pong { id: B256, target: PeerId },
        FindNode { id: B256, target: PeerId },
        Nodes { id: B256, peers: Vec<KBucketEntry> }, // up to k peers, closest to target
        FindValue { id: B256, key: B256 },
        Value { id: B256, data: Bytes },
        Store { id: B256, key: B256, data: Bytes },
    }

    pub struct FindNodeQuery {
        target: PeerId,
        // candidates sorted by distance(target, peer); status tracks lookup state
        candidates: BTreeMap<U256 /*distance*/, QueryCandidate>,
        in_flight: HashMap<PeerId, Instant>,
        responded: HashSet<PeerId>,
        alpha: usize,     // 3
        k: usize,         // 20
        timeout: Duration, // 5s per RPC
    }

    enum QueryStatus { NotQueried, InFlight, Responded, Failed }
    ```
    **Invariants**:
    - At all times, at most α in-flight FIND_NODE RPCs.
    - Lookup terminates when: (1) we've queried the k closest known peers and no closer peer appeared in last round, OR (2) all candidates exhausted.
    - Responses dedup: peer X returned in multiple responses doesn't trigger multiple queries.
    - Once a peer responds (success or timeout), update routing table (`on_ping_reply` or `on_ping_timeout`).
  - **Build steps** (granular):
    1. (~15 min) Define `KadRpc` enum + RLP encoding via `eth-network-codec` derive. Request-id `B256` for matching responses to outstanding requests.
    2. (~15 min) `FindNodeQuery::new(target, alpha, k, seed_peers)`: insert seed_peers into `candidates` BTreeMap keyed by distance.
    3. (~20 min) `FindNodeQuery::next_round(&mut self) -> Vec<PeerId>`: pull α candidates not yet queried, mark InFlight, return for transport-layer to dispatch.
    4. (~20 min) `FindNodeQuery::on_response(&mut self, from: PeerId, peers: Vec<KBucketEntry>)`: merge `peers` into `candidates`; mark `from` Responded; if no candidate strictly closer than k-th-best, mark `complete = true`.
    5. (~15 min) `FindNodeQuery::on_timeout(&mut self, peer: PeerId)`: mark Failed; do NOT remove from `candidates` (it's still in our routing table; we just lost contact this round).
    6. (~10 min) Termination logic: `is_complete()` returns true iff no in-flight AND no NotQueried that's closer than k-th candidate.
    7. (~10 min) Tests: simulated network of 100 nodes, run FIND_NODE; verify hops ≤ log2(100) + 3 (paper bound with α).
  - **Pitfalls** (named, distributed):
    - *Lost-update on parallel response*: two responses arrive simultaneously, both insert same peer; if not deduplicated, query stalls or repeats. **Symptom**: extra RPCs, slower convergence. **Fix**: `candidates` keyed by distance, NOT by peer; insert checks for existing peer first.
    - *Byzantine peer returns fake peers far from target*: malicious peer returns 20 peers it claims are close but are actually 10 buckets away. **Symptom**: query terminates without finding target. **Fix**: validate response — every returned peer's distance to target must be < returner's distance to target (otherwise drop the response).
    - *RPC ID confusion*: if `KadRpc::Pong.id` collides with `FindNodeQuery.id`, response routes to wrong query. **Symptom**: state machine wedges. **Fix**: per-RPC fresh `B256` request-id; request-table maps id → query handle.
    - *Timeout cascade*: 5s per RPC × α=3 × log(n) hops = potentially minutes for unreachable target. **Symptom**: lookups feel "hung". **Fix**: parallel-friendly progress — once any of α in-flight returns, immediately fire next; don't wait for all α. discv5 calls this "incremental progress".
  - **Test scenarios** (adversarial):
    - 100-node sim: random FIND_NODE; verify ≤ 10 hops, ≤ 30 RPCs.
    - Byzantine: 10 of 100 nodes return random peers far from target; verify lookup still succeeds.
    - Churn: during lookup, kill 20% of in-flight peers; verify lookup completes via timeout fallback.
    - Eclipse attempt: 50 peers all sharing 250 leading bits with self; verify FIND_NODE to random target still escapes the cluster.
  - **Acceptance**: 100-node sim converges in log n hops; Byzantine 10% drop tolerated; eclipse 50-cluster does not trap.
  - **Downstream**: W56 raft uses FIND_NODE for peer-set discovery; W64 bft same; W76 aeron same. The α=3 + dedup pattern recurs in W82+ gossip-sub.

**Saturday — `p2p::gossip` skeleton**

- [ ] **Build**: `crates/p2p/src/gossip.rs` — `GossipBroadcast<T: Encodable>` with `Vec<PeerId>` fan-out, lazy push (
  IHAVE/IWANT). Inspired by Plumtree but simpler. (~105 min)
  - **Why**: Gossip is how Raft/BFT/blockchain peers exchange transactions and votes when there's no central broker. Epidemic broadcast guarantees probabilistic O(log n) latency with O(log n) per-node bandwidth — vs naive flood's O(n). Plumtree (Leitão et al. 2007) extends gossip with lazy-push to limit redundant fan-out.
  - **Read first**: Plumtree paper "Epidemic Broadcast Trees" (Leitão, Pereira, Rodrigues, 2007); libp2p-gossipsub spec (gossipsub-v1.1.md).
  - **Design**:
    ```rust
    pub struct GossipBroadcast<T: Encodable + Decodable> {
        peers: SmallVec<[PeerId; 16]>,    // active broadcast peers (eager push)
        lazy_peers: SmallVec<[PeerId; 32]>, // additional peers (lazy IHAVE only)
        seen: lru::LruCache<B256, ()>,    // message-id → seen flag
        pending: backpressure::Queue<T>,   // bounded outbound queue
        fanout: usize,                     // 6-8 typical
        ihave_interval: Duration,          // 1s
    }

    pub enum GossipMsg<T> {
        Have(B256),       // "I have message-id"
        Want(B256),       // "Send me message-id"
        Message(T),
    }
    ```
    **Invariants**:
    - seen-cache size ≥ window of expected concurrent message-ids (e.g., 10k). LRU eviction acceptable; consequence is re-receiving stale messages occasionally.
    - Eager-push fan-out is FIXED (`fanout` peers); lazy-push to remaining peers via periodic IHAVE.
    - Message-id is content-hash (B256 = keccak256 of canonical encoding).
  - **Build steps** (granular):
    1. (~15 min) `GossipBroadcast` skeleton with peer lists, seen-cache (lru = 10k entries).
    2. (~15 min) `publish(msg)`: compute id = keccak256(rlp(msg)), insert into seen, fan-out to `peers[0..fanout]`.
    3. (~20 min) `on_message(from, msg)`: if id in seen → no-op; else insert seen, deliver to app callback, forward to `peers - {from}`.
    4. (~15 min) `tick()` every `ihave_interval`: send `Have(id)` summaries to lazy_peers for recently-seen msgs.
    5. (~15 min) `on_have(from, id)`: if id NOT in seen, respond with `Want(id)`; from sends Message in next round.
    6. (~10 min) Peer-score: penalize peers that send invalid msgs (high seen-but-malformed rate); eject if score < threshold.
    7. (~15 min) Tests: 10 peers, publish 1 msg, every peer receives within 3 rounds.
  - **Pitfalls** (named, distributed):
    - *Gossip amplification*: each peer forwards to fanout=8 peers → quadratic explosion. **Symptom**: BW DoS on small networks. **Fix**: seen-cache deduplicates; ensure dedupe happens BEFORE forward decision.
    - *Lazy-push starvation*: peer with low IHAVE rate never receives. **Symptom**: certain peers persistently lag. **Fix**: tick must run on a real timer (W58 timer wheel); not driven by message arrival.
    - *Eclipse on gossip*: if attacker controls all `fanout` peers, victim's publish goes nowhere. **Symptom**: silent message loss. **Fix**: rotate `peers` periodically (e.g., 1/10 replaced per minute via Kademlia random walk); ensure fanout drawn from multiple buckets.
