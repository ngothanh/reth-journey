- [ ] Read Maymounkov & Mazières Kademlia paper. (~90 min)
  - **Why**: Kademlia is the most-deployed peer-discovery DHT (BitTorrent Mainline, IPFS, Ethereum's discv4/discv5, libp2p). Tier-A HFT IC bar (c) — this `p2p` crate is the Layer-4 substrate inherited by consensus-raft (W56+), consensus-bft (W64+), messaging-aeron (W76+ discovery only). Mastery of XOR metric, k-bucket update rule, and FIND_NODE iterative-lookup is interview-load-bearing for distributed systems roles.
  - **Read first**: Maymounkov & Mazières "Kademlia: A Peer-to-peer Information System Based on the XOR Metric" (2002), §2.1 (XOR metric), §2.2 (node state — k-buckets), §2.3 (Kademlia protocol — FIND_NODE / FIND_VALUE / STORE / PING), §2.4 (refinements: parallel lookups α=3, bucket splitting), §4 (security: Sybil mitigations are absent — note this).
  - **Design** (high-level, paper-mapped):
    ```text
    Node identity: 160-bit ID (we use B256 = 256-bit for SHA3 alignment).
    Distance(a, b) := a XOR b, treated as integer.
    Routing table: 256 buckets (one per bit of ID space). Bucket i holds nodes whose distance from self is in [2^i, 2^(i+1)).
    Bucket capacity: k = 20 (Kademlia paper default).
    Lookup parameter: α = 3 (parallelism).
    ```
    **Invariants** (from paper):
    - XOR is a *valid* metric: d(x,x)=0; d(x,y)=d(y,x); d(x,y) ≤ d(x,z) ⊕ d(z,y).
    - Bucket-i invariant: every node in bucket-i shares exactly i leading bits with self.
    - LRU eviction: oldest peer at head of bucket; if bucket full and oldest still responds to PING, NEW peer is dropped (paper §2.2 — counter-intuitive but resists eclipse).
    - FIND_NODE returns k closest peers to target; iterative lookup queries α at a time, terminates when no closer peer found in a round.
  - **Build steps** (just reading today; build starts Tue):
    1. (~30 min) Read §2 of paper. Sketch on whiteboard: 4 nodes with IDs 0000, 0011, 1100, 1111; compute pairwise XOR distance.
    2. (~15 min) Read libp2p `kad-dht` overview docs (https://github.com/libp2p/specs/tree/master/kad-dht). Note libp2p's deviations: 20-byte IDs (SHA-256 truncated), reuse of TCP for transport.
    3. (~15 min) Read Ethereum discv4 RLPx spec (devp2p/discv4.md). Note ethereum uses Keccak256(pubkey) for NodeID, includes endpoint-verification (sender = receiver's view of remote IP).
    4. (~15 min) Read sigp/discv5 Rust impl (https://github.com/sigp/discv5/blob/master/src/kbucket.rs). Note `KBucketsTable` design.
    5. (~15 min) Map onto your design: 256-bit IDs (vs 160-bit Kademlia paper), k=20, α=3. Note you'll need PING-before-evict logic.
  - **Pitfalls** (named, distributed-systems):
    - *Eclipse attack*: attacker creates many node IDs near victim, monopolizes victim's view. **Symptom**: victim sees only attacker-controlled peers. **Fix**: (1) require ID = H(pubkey) with proof-of-work or stake binding; (2) limit per-IP-subnet entries per bucket (e.g. max 2 per /24); (3) random refresh of buckets to detect freshness. Eth discv5 implements all three.
    - *Bucket poisoning via PING-spam*: paper says PING-then-evict — but attacker spamming PINGs to keep stale entries alive blocks new peers. **Symptom**: routing table never refreshes. **Fix**: PING reply must be unsolicited-recent (within e.g. 5s of receiving the ping), AND the PING is rate-limited per-source.
    - *ID-mapping skew*: if node-IDs aren't uniformly random (e.g., chosen by user with vanity prefix), some buckets overpopulate and others starve. **Symptom**: poor lookup performance, certain ID ranges unreachable. **Fix**: enforce ID = H(pubkey); reject vanity-mined keys via PoW difficulty.
    - *NAT-induced asymmetric reachability*: A reachable→B but B unreachable→A (NAT). Adding B to A's bucket pollutes lookups. **Symptom**: lookups time out frequently. **Fix**: endpoint-verification handshake (discv4 ENDPOINTPROOF) — B must echo A's seen-from address before A adds B.
  - **Test scenarios** (to design now, build Wed-Thu):
    - XOR-distance property: `forall a, b, c: d(a, c) ≤ d(a, b) + d(b, c)` (triangle inequality holds under XOR-as-int).
    - Bucket invariant: for each peer in bucket-i, MSB(peer XOR self) is bit i.
    - Eclipse-resistance: insert 100 peers all sharing 252 leading bits with self; verify only k=20 end up in bucket-252 (others rejected or distributed).
  - **Acceptance**: paper notes committed; design doc `notes/p2p_kademlia_design.md` covers XOR metric, k-bucket structure, FIND_NODE iterative algorithm, PING-before-evict, eclipse-mitigation strategy.

  - **When `peer_store_record_seen_no_alloc` reports ~200k allocs/sec:**
    - Symptom: `dhat` shows ~200k `PeerInfo`-sized allocs/sec under the bench; criterion p99 climbs from ~80 ns to ~200 ns; allocator-lock contention bleeds into unrelated threads.

    - Fix: `lru::LruCache::get_mut(&peer)` returns `&mut PeerInfo` in-place; mutate fields directly. Only fall through to `put` when `peer` was absent.
    - Cost avoided: ~50 ns malloc + ~50 ns dealloc + SmallVec spill (~50 ns + 32-byte cache line) per call ≈ **100–150 ns saved per record_seen**; at 200k/s that's ~30 ms/s CPU and a ~2× p99 collapse.

  - **Design**:
    ```rust
    pub struct PeerId(pub B256);  // = keccak256(secp256k1 uncompressed pubkey || ed25519 ed_pubkey)

    impl PeerId {
        pub fn from_secp256k1_pubkey(pk: &[u8; 64]) -> Self {
            Self(keccak256(pk))
        }
        pub fn distance(&self, other: &PeerId) -> U256 {
            U256::from_be_bytes(*(self.0 ^ other.0).as_ref())
        }
        pub fn leading_zeros_xor(&self, other: &PeerId) -> u32 {
            self.distance(other).leading_zeros()  // for bucket index
        }
    }

    pub struct Multiaddr(pub bytes::Bytes);  // /ip4/.../tcp/...

    pub struct PeerStore {
        peers: lru::LruCache<PeerId, PeerInfo>,
        capacity: usize,
    }
    pub struct PeerInfo {
        pub addrs: smallvec::SmallVec<[Multiaddr; 2]>,
        pub last_seen: time::HybridLogicalClock,
        pub successful_pings: u32,
        pub failed_pings: u32,
    }
    ```
    **Invariants**:
    - PeerId is irreversibly tied to pubkey. No setter — only constructors from pubkey bytes.
    - `distance` is total ordering; uniqueness modulo self-distance=0.
    - PeerStore is LRU: full capacity → eviction of least-recently-seen.
    - `last_seen` uses HybridLogicalClock for monotonic-across-restarts ordering.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: a naive routing table evicts the newest peer on full-bucket (since "newest = least proven"), which is the OPPOSITE of correct — established peers are the eclipse-resistant ones. The 360 KB table must stay in L2 (~256 KB-1 MB) on hot lookups; ballooning to `Vec<>` doubles `closest_peers` latency and burns L3 bandwidth.

  - **Requirements** — write in `crates/p2p/notes/52_routing_table_design.md`:
    - R1. 256 buckets, each `ArrayVec<KBucketEntry, K=20>` — capacity known at compile time, zero alloc on steady-state `add_peer`.
    - R2. Bucket invariant: peer is in bucket-i iff `leading_zeros_xor(self, peer) == i`. Property-test verifies for all inserted peers.
    - R3. Eviction policy: on full bucket, return `BucketAction::PingOldest` (caller dispatches the PING); on reply → drop challenger; on timeout → evict oldest, promote challenger from `replacement_cache`.
    - R4. `replacement_cache: ArrayVec<KBucketEntry, K>` holds challengers during PING-pending state — concurrent inserts during PING are not lost.
    - R5. Subnet cap: ≤ 2 entries per /24 IPv4 prefix per bucket; ≤ 8 per /16. Rejection on exceeded cap with `P2pError::SubnetCapReached`.
    - R6. `closest_peers(&self, target, out: &mut ArrayVec<KBucketEntry, K>)` — caller-owned output buffer, zero alloc on the hot path. Touches at most 5 adjacent buckets (~100 entries scanned).
    - R7. `add_peer` budget: ≤ 50 ns on the bucket-has-space path. `closest_peers` budget: ≤ 1 µs.
    - R8. Total table size: ~360 KB (256 × 20 × 72 B); must fit in L2. Verified with `size_of::<RoutingTable>()` const-assert.

    const K: usize = 20;            // bucket size
    const N_BUCKETS: usize = 256;   // bit-positions of B256

    pub struct KBucket {
        // Front = least-recently-seen (eviction candidate); back = most recently seen.
        peers: ArrayVec<KBucketEntry, K>,
        replacement_cache: ArrayVec<KBucketEntry, K>,  // candidates waiting for slot
        pending_eviction: Option<PendingEviction>,
    }

    pub struct KBucketEntry {
        pub peer: PeerId,
        pub addrs: smallvec::SmallVec<[Multiaddr; 2]>,
        pub last_seen: HybridLogicalClock,
        pub status: PeerStatus,  // Connected | Disconnected | PendingPing

        evictee: PeerId,
        challenger: KBucketEntry,
        ping_sent_at: Instant,
    }

    pub struct RoutingTable {
        local_id: PeerId,
        buckets: Box<[KBucket; N_BUCKETS]>,  // boxed: 256 * sizeof(KBucket) is big

**Thursday — `p2p::kademlia` FIND_NODE**

- [ ] **Build**: `crates/p2p/src/kademlia/protocol.rs` — FIND_NODE, FIND_VALUE, STORE, PING RPCs. Parallel α=3 lookups. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: iterative lookup with α=3 parallelism is THE distinguishing feature of Kademlia. It converges in O(log n) hops with high probability, tolerates Byzantine peers (returns from non-faulty peers dominate), and handles churn gracefully. W56 raft uses FIND_NODE for peer-set discovery; W64+ bft same; W76+ aeron same; the α-parallel-with-dedup pattern recurs in W82+ gossip-sub mesh maintenance.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: serial lookups take O(log n) × RTT — minutes on WAN. Pure flood is O(n) bandwidth. α-parallel dedup converges in `log n` hops with `α × log n` RPCs and tolerates ~1/3 Byzantine returns. Without dedup the candidate set explodes; without proper termination the lookup never stops.

  - **Requirements** — write in `crates/p2p/notes/52_protocol_design.md`:
    - R1. `KadRpc` enum: `Ping/Pong/FindNode/Nodes/FindValue/Value/Store`. Request-id `B256` for matching responses to outstanding requests.
    - R2. `FindNodeQuery` maintains α-bounded in-flight set; dedup candidates by PeerId; sort by XOR distance to target.
    - R3. Termination: lookup completes when no in-flight remains AND no NotQueried candidate is strictly closer than the k-th-best known peer.
    - R4. Byzantine guard: every returned peer's distance to target MUST be < returner's distance to target; otherwise drop the response.
    - R5. Per-response work ≤ 5 µs; per-lookup CPU ≤ 50 µs (the wall-clock budget is dominated by RPC RTT, but state-machine cost matters at 1k lookups/s).
    - R6. Zero alloc on the hot decode path: the codec writes decoded peers into a borrowed `ArrayVec<KBucketEntry, K>` scratch buffer in the query struct, not a fresh `Vec`.
    - R7. Candidate set uses `HashMap<PeerId, QueryCandidate>` for dedup + a separately maintained `ArrayVec<(U256, PeerId), K>` sorted top-K — NOT a `BTreeMap` keyed by distance.
    - R8. Request-id collision rate: <1 in 2^120; per-RPC fresh `B256` request-id; request-table maps id → query handle.

  - **Design walk-through**:
    - D1. Why HashMap + ArrayVec sorted top-K instead of BTreeMap keyed by distance? Compute the cost: BTreeMap insert is O(log n) cache-cold pointer chases × node-alloc; HashMap insert is O(1). Top-K refresh is O(k log k) ≈ 90 compares once per round; cheap.

  - **Design**:
    ```rust
    pub enum KadRpc {
        Ping { id: B256, sender: PeerId },
        Pong { id: B256, target: PeerId },
        FindNode { id: B256, target: PeerId },
        Nodes { id: B256, peers: Vec<KBucketEntry> }, // up to k peers, closest to target
        FindValue { id: B256, key: B256 },
        Value { id: B256, data: Bytes },
        Store { id: B256, key: B256, data: Bytes },
    }

    pub struct FindNodeQuery {
        target: PeerId,
        // candidates sorted by distance(target, peer); status tracks lookup state
        candidates: BTreeMap<U256 /*distance*/, QueryCandidate>,
        in_flight: HashMap<PeerId, Instant>,
        responded: HashSet<PeerId>,
        alpha: usize,     // 3
        k: usize,         // 20
        timeout: Duration, // 5s per RPC
    }

    enum QueryStatus { NotQueried, InFlight, Responded, Failed }
    ```
    **Invariants**:
    - At all times, at most α in-flight FIND_NODE RPCs.
    - Lookup terminates when: (1) we've queried the k closest known peers and no closer peer appeared in last round, OR (2) all candidates exhausted.
    - Responses dedup: peer X returned in multiple responses doesn't trigger multiple queries.
    - Once a peer responds (success or timeout), update routing table (`on_ping_reply` or `on_ping_timeout`).
  - **Build steps** (granular):
    1. (~15 min) Define `KadRpc` enum + RLP encoding via `eth-network-codec` derive. Request-id `B256` for matching responses to outstanding requests.
    2. (~15 min) `FindNodeQuery::new(target, alpha, k, seed_peers)`: insert seed_peers into `candidates` BTreeMap keyed by distance.
    3. (~20 min) `FindNodeQuery::next_round(&mut self) -> Vec<PeerId>`: pull α candidates not yet queried, mark InFlight, return for transport-layer to dispatch.
    4. (~20 min) `FindNodeQuery::on_response(&mut self, from: PeerId, peers: Vec<KBucketEntry>)`: merge `peers` into `candidates`; mark `from` Responded; if no candidate strictly closer than k-th-best, mark `complete = true`.
    5. (~15 min) `FindNodeQuery::on_timeout(&mut self, peer: PeerId)`: mark Failed; do NOT remove from `candidates` (it's still in our routing table; we just lost contact this round).
    6. (~10 min) Termination logic: `is_complete()` returns true iff no in-flight AND no NotQueried that's closer than k-th candidate.
    7. (~10 min) Tests: simulated network of 100 nodes, run FIND_NODE; verify hops ≤ log2(100) + 3 (paper bound with α).

    - *Lost-update on parallel response*: two responses arrive simultaneously, both insert same peer; if not deduplicated, query stalls or repeats. **Symptom**: extra RPCs, slower convergence. **Fix**: `candidates` keyed by distance, NOT by peer; insert checks for existing peer first.
    - *Byzantine peer returns fake peers far from target*: malicious peer returns 20 peers it claims are close but are actually 10 buckets away. **Symptom**: query terminates without finding target. **Fix**: validate response — every returned peer's distance to target must be < returner's distance to target (otherwise drop the response).

    - *Timeout cascade*: 5s per RPC × α=3 × log(n) hops = potentially minutes for unreachable target. **Symptom**: lookups feel "hung". **Fix**: parallel-friendly progress — once any of α in-flight returns, immediately fire next; don't wait for all α. discv5 calls this "incremental progress".
    - **Expect to hit (perf) #1 — `BTreeMap<U256, QueryCandidate>` re-balances under churn; `HashMap` would skip the log(N) (bar (c) violation)**: a `BTreeMap` keyed by distance gives ordered traversal "for free," but every insert/remove is O(log N) with cache-cold node pointers (each BTreeMap node ~64 bytes, heap-allocated).       - Cost avoided: ~50 ns + heap alloc per insert × 20 inserts/response × 10k responses/s ≈ ~10-15 ms/s CPU + ~200k allocs/s eliminated.
      - Muscle: when the access pattern is "frequent insert + dedup, infrequent top-K read," HashMap + cheap sort beats BTreeMap. BTreeMap is the right tool when you scan ranges, not when you upsert.

  - 🔧 **Why this matters**: gossip is how Raft (W56+)/BFT (W64+)/blockchain peers exchange transactions and votes when there's no central broker. Epidemic broadcast guarantees probabilistic O(log n) latency with O(log n) per-node bandwidth — vs naive flood's O(n). Plumtree (Leitão et al. 2007) extends gossip with lazy-push to limit redundant fan-out. Get the dedup + encode-once discipline wrong and a hot peer burns 70 MB/s on allocator churn alone.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: at 10k msgs/s × fanout=8, a naive `for peer in peers { send(msg.clone()) }` allocates 80k 1-KB clones/s = 80 MB/s allocator churn AND re-hashes the message ID on every receive. Without dedup-before-forward, the network amplifies into quadratic explosion.

  - **Requirements** — write in `crates/p2p/notes/52_gossip_design.md`:
    - R1. `GossipBroadcast<T: Encodable + Decodable>` with eager-push fanout=8 + lazy-push to remaining peers via periodic IHAVE.
    - R2. seen-cache (`lru::LruCache<B256, ()>`) sized for ≥ `expected_rate × max_propagation_delay × safety_factor` (10k entries default at 10k msg/s and 100ms hop latency).
    - R3. Message-id = `keccak256(raw_inbound_bytes)` — computed BEFORE decode; duplicates dropped without decoding the payload.
    - R4. Forward path encodes the message ONCE to `bytes::Bytes`; fanout sends `Bytes::clone` (refcount bump ~10 ns), never a deep clone.
    - R5. Peer-score: penalize peers whose `invalid_msg_count / total_msg_count > threshold`; eject from active peer set when score < cutoff.
    - R6. `publish(msg)` and `on_message(from, raw_bytes)` budgets: ≤ 1 µs end-to-end (fast path); ≤ 5 µs slow path (encode + fanout).
    - R7. `tick()` runs on the timer wheel (W58) at `ihave_interval=1s`, not driven by message arrival — required to break starvation.
    - R8. Eclipse resistance: rotate `peers` set periodically (1/10 replaced per minute via Kademlia random walk).

  - **Design walk-through**:
    - D1. Why hash raw wire bytes for the dedup key, not the decoded value?   - **When `fanout_zero_deep_clone` reports ~70k allocs/s and `bench_publish_under_1us` p50 = 3 µs:**

    - Why: `self.send_to_peer(*peer, GossipMsg::Message(m.clone()))` invoked 7 times per forward = 7 × deep clone of 1 KB msg → ~7 KB allocator churn per forward × 10k forwards/s = 70 MB/s.
    - Fix: encode the message ONCE into a `Bytes` (or `Arc<Bytes>` if you need detachable lifetime); fanout sends `Bytes::clone` (a refcount bump ~10 ns) instead of a deep clone. Transport accepts `&Bytes` and writes through.
    - Cost avoided: ~50 ns malloc + 80 ns memcpy per fanout × 7 ≈ ~900 ns saved per forward; at 10k forwards/s ≈ 9 ms/s CPU + ~70 MB/s allocator pressure eliminated.

  - **When `dedup_drops_before_decode` reports `Decodable::decode` called 1000 times for 1000 duplicates:**
    - Symptom: `perf record` shows `rlp::encode` and `rlp::decode` hot in the receive path despite ostensibly only seeing dups; transient encode-buffer allocs spike.
    - Why: msg_id is computed as `keccak256(rlp_encode(decoded_msg))` — the path decodes, then re-encodes, then hashes. The dedup-key derivation does ~700 ns of redundant work on every receive, including duplicates.
    - Fix: hash the raw inbound bytes BEFORE decoding (`msg_id = keccak256(&raw_bytes)`). The codec layer keeps the frame buffer alive long enough for the hash; only decode when `seen.insert(msg_id, ())` returns `None` (new).
    - Cost avoided: ~200 ns hash + ~100 ns encode-buffer alloc per inbound msg × 10k/s ≈ ~3 ms/s CPU; additionally avoids the ~500 ns decode cost on duplicates (saves ~5 ms/s more).
    - Muscle: derive the dedup key from the wire bytes, not from the decoded value. Codec lifecycle is "frame in → id check → decode-if-new"; never "frame in → decode → re-encode → id check." **Reapplies at**: W56 raft AppendEntries dedup (use frame hash, not entry-by-entry re-hash), W64+ bft block-proposal id from raw bytes, W76+ aeron fragment-id for image dedup.

    - Fix: external timer-wheel (W58) drives `tick()` every `ihave_interval`. GossipBroadcast exposes a `pub fn tick(&mut self)` that the runtime calls.
    - Muscle: time-driven behavior MUST be driven by a clock source, not by event traffic. **Reapplies at**: W56 raft election timeout, W58 timer wheel itself, W76+ aeron heartbeat.

    - Memory: seen-cache 10k entries × (B256 + ()) ≈ 320 KB ≈ fits in L2; cache itself 1k msg payload × ~1 KB = 1 MB, lives in L3. Hash collisions are < 1 in 2^128 so dedup is exact.
  - **Read first**: Plumtree paper "Epidemic Broadcast Trees" (Leitão, Pereira, Rodrigues, 2007); libp2p-gossipsub spec (gossipsub-v1.1.md).
  - **Design**:
    ```rust
    pub struct GossipBroadcast<T: Encodable + Decodable> {
        peers: SmallVec<[PeerId; 16]>,    // active broadcast peers (eager push)
        lazy_peers: SmallVec<[PeerId; 32]>, // additional peers (lazy IHAVE only)
        seen: lru::LruCache<B256, ()>,    // message-id → seen flag
        pending: backpressure::Queue<T>,   // bounded outbound queue
        fanout: usize,                     // 6-8 typical
        ihave_interval: Duration,          // 1s
    }

    pub enum GossipMsg<T> {
        Have(B256),       // "I have message-id"
        Want(B256),       // "Send me message-id"
        Message(T),
    }
    ```
    **Invariants**:
    - seen-cache size ≥ window of expected concurrent message-ids (e.g., 10k). LRU eviction acceptable; consequence is re-receiving stale messages occasionally.
    - Eager-push fan-out is FIXED (`fanout` peers); lazy-push to remaining peers via periodic IHAVE.
    - Message-id is content-hash (B256 = keccak256 of canonical encoding).
  - **Build steps** (granular):
    1. (~15 min) `GossipBroadcast` skeleton with peer lists, seen-cache (lru = 10k entries).
    2. (~15 min) `publish(msg)`: compute id = keccak256(rlp(msg)), insert into seen, fan-out to `peers[0..fanout]`.
    3. (~20 min) `on_message(from, msg)`: if id in seen → no-op; else insert seen, deliver to app callback, forward to `peers - {from}`.
    4. (~15 min) `tick()` every `ihave_interval`: send `Have(id)` summaries to lazy_peers for recently-seen msgs.
    5. (~15 min) `on_have(from, id)`: if id NOT in seen, respond with `Want(id)`; from sends Message in next round.
    6. (~10 min) Peer-score: penalize peers that send invalid msgs (high seen-but-malformed rate); eject if score < threshold.
    7. (~15 min) Tests: 10 peers, publish 1 msg, every peer receives within 3 rounds.
  - **Pitfalls** (named, distributed):
    - *Gossip amplification*: each peer forwards to fanout=8 peers → quadratic explosion. **Symptom**: BW DoS on small networks. **Fix**: seen-cache deduplicates; ensure dedupe happens BEFORE forward decision.
    - *Lazy-push starvation*: peer with low IHAVE rate never receives. **Symptom**: certain peers persistently lag. **Fix**: tick must run on a real timer (W58 timer wheel); not driven by message arrival.
    - *Eclipse on gossip*: if attacker controls all `fanout` peers, victim's publish goes nowhere. **Symptom**: silent message loss. **Fix**: rotate `peers` periodically (e.g., 1/10 replaced per minute via Kademlia random walk); ensure fanout drawn from multiple buckets.
    - *Seen-cache too small*: if 10k msgs/sec arrive and cache is 10k, churn makes dedup fail. **Symptom**: amplification returns. **Fix**: size cache for `expected_rate × max_propagation_delay × safety_factor`.
    - **Expect to hit (perf) #1 — clone `T` per fanout peer (bar (c) violation)**: `self.send_to_peer(*peer, GossipMsg::Message(m.clone()))` invoked 7 times per forward = 7 × clone of 1 KB msg → 7 KB allocator churn per forward, 70 × 7 = ~490k allocs/s on a busy peer. **Symptom**: `perf top` shows `__GI___libc_malloc` and `memcpy` in the top 3; backpressure trips spuriously because send queues fill with redundant clones.
      - Fix: encode the message ONCE into a per-peer `Arc<Bytes>` (or pre-encoded `bytes::Bytes` from the encode pool); fanout sends the `Arc::clone` (a refcount bump, 1 atomic increment ≈ 10 ns) instead of a deep clone. The transport layer accepts `Bytes`/`Arc<Bytes>` and writes through.
      - Cost avoided: ~50 ns malloc + 1 KB memcpy (~80 ns L1 throughput) per fanout × 7 = ~900 ns saved per forward; at 10k forwards/s ≈ 9 ms/s CPU + ~70 MB/s allocator pressure eliminated.
      - Muscle: any "broadcast same payload to N recipients" must encode-once-arc-clone-N, never clone-N. The transport must accept `Arc<Bytes>` or equivalent.
      - **Reapplies at**: W56 raft AppendEntries fanout (encode once, send to N-1 followers), W64+ bft proposal broadcast, W76+ aeron multicast publication, W77+ aeron MBO feed.
    - **Expect to hit (perf) #2 — `msg_id = keccak256(rlp(msg))` re-hashes the msg on every receive (bar (c) violation)**: the dedup path computes the id by RLP-encoding the msg then hashing — but the msg already arrived as bytes on the wire and was decoded. Re-encoding it just to hash burns ~200 ns + a transient buffer. **Symptom**: `perf record` shows `rlp::encode` is hot in the receive path despite ostensibly never being called there.
      - Fix: hash the raw inbound bytes BEFORE decoding (`msg_id = keccak256(&raw_bytes)`). The decoder writes into a borrowed buffer that the codec layer already owns; the id stays valid for the lifetime of the frame.
      - Cost avoided: ~200 ns hash + ~100 ns transient encode-buffer alloc per inbound msg × 10k/s = ~3 ms/s CPU + allocator pressure. Additionally collapses the deserialize-then-discard for duplicates: spotted-seen → drop without decoding the payload at all (saves the entire decode cost on duplicate, ~500 ns more on a 1 KB msg).
      - Muscle: derive the dedup key from the wire bytes, not from the decoded value. The codec lifecycle is "frame in → id check → decode-if-new"; never "frame in → decode → re-encode → id check."
      - **Reapplies at**: W56 raft AppendEntries dedup (use frame hash, not entry-by-entry re-hash), W64+ bft block-proposal id from raw bytes, W76+ aeron fragment-id for image dedup.
  - **Test scenarios**:
    - 100-node sim, publish 1 msg → 100% delivery within 5 ticks.
    - 10% Byzantine peers (forward random garbage): peer-score evicts them within 60s.
    - Eclipse: victim's fanout peers all sinkhole; verify lazy-push via IHAVE rescues delivery within 2× ihave_interval.
  - **Acceptance**: 100-node delivery 100%; Byzantine eviction works; latency p95 ≤ log2(N) × hop-latency.
