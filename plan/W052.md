  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

  - **(SENIOR) When `tick_runs_on_timer_not_message` fails:**
    - Symptom: pause ingress; `tick()` never fires; lazy_peers never get IHAVE; eclipse recovery breaks.
    - Why: tick scheduled inside `on_message` ("after handling a message, maybe tick"). No messages → no tick.
    - Fix: external timer-wheel (W58) drives `pub fn tick(&mut self)` every `ihave_interval`.
    - Cost avoided: eclipse window on idle/low-traffic peers — security.
    - Muscle: time-driven behavior MUST be driven by a clock source, not event traffic. **Reapplies at**: W52 KademliaNode refresh (Fri), W56 raft election timeout, W58 timer wheel, W76+ aeron heartbeat.
  - **(SENIOR) When `byzantine_peer_evicted_under_60s` keeps the byzantine peer:**
    - Symptom: garbage-forwarding peer stays in `peers` indefinitely; legitimate traffic crowded out.
    - Why: peer-score never updates on `invalid_msg_decode` failure; no eject threshold.
    - Fix: `on_message` increments `peer.invalid_count` on decode failure; `tick()` computes `invalid/total` and ejects above threshold (e.g. 20% sustained 30 s).
    - Cost avoided: a slow bandwidth-DoS (garbage crowds out real traffic) — liveness.
    - Muscle: scoring is a feedback loop; no eject mechanism = score collects dust. **Reapplies at**: W56 raft peer-health, W64+ bft validator scoring.
  - **(EXPERT, perf — bar (c) violation) When `dedup_drops_before_decode` reports `decode` called 1000× for 1000 dups:**
    - Symptom: `perf record` shows `rlp::encode`/`rlp::decode` hot in the receive path despite "only seeing dups"; transient encode-buffer allocs spike.
    - Why: `msg_id = keccak256(rlp_encode(decoded_msg))` — decode, re-encode, then hash: ~700 ns redundant work on every receive incl. duplicates.
    - Fix: hash raw inbound bytes BEFORE decoding (`msg_id = keccak256(&raw_bytes)`); only decode when `seen.insert(msg_id, ())` returns `None`.
    - Cost avoided: ~200 ns hash + ~100 ns encode-buffer alloc per inbound × 10k/s ≈ ~3 ms/s CPU + ~500 ns decode avoided per dup (~5 ms/s more). **(bar (c) violation.)**
    - Muscle: derive the dedup key from the wire bytes, not the decoded value; lifecycle is "frame in → id check → decode-if-new". **Reapplies at**: W56 raft AppendEntries dedup (frame hash), W64+ bft block-proposal id from raw bytes, W76+ aeron fragment-id.
  - **(EXPERT, perf — bar (c) violation) When `fanout_zero_deep_clone` reports ~70k allocs/s and `bench_publish_under_1us` p50 = 3 µs:**
    - Symptom: `perf top` shows `__GI___libc_malloc` + `memcpy` top-3; backpressure trips spuriously because send queues fill with redundant clones; alloc-lock contention bleeds across threads.
    - Why: `send_to_peer(*peer, GossipMsg::Message(m.clone()))` × 7/forward = 7 deep clones of 1 KB ⇒ ~7 KB churn/forward × 10k/s = 70 MB/s (the §D6 chain).
    - Fix: encode ONCE into `Bytes` (or `Arc<Bytes>`); fan-out sends `Bytes::clone` (refcount bump ~10 ns). Transport accepts `&Bytes` and writes through.
    - Cost avoided: ~50 ns malloc + ~80 ns memcpy per fanout × 7 ≈ ~900 ns/forward; at 10k/s ≈ 9 ms/s CPU + ~70 MB/s allocator pressure eliminated. **(bar (c) violation.)**
    - Muscle: any "broadcast same payload to N recipients" must encode-once-arc-clone-N, never clone-N. **Reapplies at**: W56 raft AppendEntries fanout, W64+ bft proposal broadcast, W76+ aeron multicast publication, W77+ aeron MBO feed.
