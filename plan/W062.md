- [ ] **Build**: `crates/consensus-raft/src/membership.rs` — joint-consensus membership change (C_old → C_old,new →
  C_new). Tested with one-at-a-time member additions. (~150 min)
  - **Why (MAX DETAIL)**: Adding/removing nodes from a running Raft cluster is the #1 production-bug area. The naive "just update peer list" approach causes split-brain when nodes have inconsistent membership views. Joint consensus (Ongaro §6) requires BOTH old and new configurations to form majority during transition — provably safe.
  - **Read first**: Ongaro §6 (Cluster membership changes); Ongaro thesis §4 (refined single-server changes for simpler impl); etcd `raft/raft.go::applyConfChange`.
  - **Design**:
    ```rust
    pub enum ConfState {
        Stable(Vec<NodeId>),
        Joint { old: Vec<NodeId>, new: Vec<NodeId> },
    }

    impl<S> RaftState<S> {
        pub fn propose_membership_change(&mut self, change: ConfChange) -> Result<(), _> {
            // 1. Append C_old,new as special log entry
            let joint = match (&self.conf, &change) {
                (ConfState::Stable(old), ConfChange::AddNode(n)) => {
                    let mut new = old.clone(); new.push(*n);
                    ConfState::Joint { old: old.clone(), new }
                }
                (ConfState::Stable(old), ConfChange::RemoveNode(n)) => {
                    let new: Vec<_> = old.iter().filter(|x| *x != n).copied().collect();
                    ConfState::Joint { old: old.clone(), new }
                }
                _ => return Err(MembershipChangeInProgress),
            };
            let entry = LogEntry { term: ..., index: ..., command: encode_conf(&joint), ... };
            self.log.append(entry)?;
            // 2. On commit of joint entry → apply joint state; start replicating to BOTH C_old and C_new
            // 3. Once joint entry committed, propose C_new entry
            // 4. On commit of C_new entry → apply C_new, drop C_old
            Ok(())
        }

        fn quorum_check_under_joint(&self, indices: &HashMap<NodeId, u64>) -> u64 {
            match &self.conf {
                ConfState::Stable(nodes) => quorum_of(indices, nodes),
                ConfState::Joint { old, new } => {
                    // Both must form majority
                    quorum_of(indices, old).min(quorum_of(indices, new))
                }
            }
        }
    }
    ```
    **Invariants**:
    - During Joint state, an entry is committed iff replicated to majority of BOTH C_old AND C_new.
    - Only ONE membership change in flight at a time.
    - Removal of a non-voter: simpler — but we still treat as full join-consensus for uniformity.
  - **Build steps**:
    1. (~25 min) ConfState enum + ConfChange variants.
    2. (~30 min) propose_membership_change; encode joint as special LogEntry::ConfChange variant.
    3. (~30 min) On commit, update self.conf via state-machine apply path.
    4. (~30 min) `quorum_check_under_joint` overrides regular quorum during transition.
    5. (~25 min) Test: 3-node cluster, add 4th node; verify joint config commits; then C_new commits; then cluster operates as 4-node.
    6. (~10 min) Test: chain remove (drop 4th) → 3-node again.
  - **Pitfalls** (named, distributed):
    - *Two changes in flight*: starting C2 before C1 commits → undefined state. **Symptom**: split-brain on partition. **Fix**: explicit `MembershipChangeInProgress` rejection if joint state already active.
    - *Removed node still serving*: removed leader continues serving until learns of change. **Symptom**: stale data reads. **Fix**: leader steps down explicitly on applying its own removal; clients re-dial.
    - *Forgetting to replicate to new node BEFORE commit*: leader commits via OLD quorum, new node never receives entries. **Symptom**: new node has empty log when transition completes. **Fix**: leader starts replicating to new node IMMEDIATELY upon joint entry append (not commit). Use catch-up phase to ensure new node has near-current state before promoting to voter.
  - **Test scenarios**:
    - 3-node → add 4th → verify joint state, then C_new, then 4-node operates. 1000-entry replication after change.
    - 3-node → remove leader → new leader elected from {n2, n3} → continues.
    - Partition during joint: 2/4 each side. Neither side has majority of BOTH C_old (3-node) and C_new (4-node) until heal.
  - **Acceptance**: 4 membership changes (add, add, remove, remove) chain successfully; no split-brain.
  - **Downstream**: W67+ raft v1.0; W74+ matching-engine running on Raft uses this for shard rebalance.

- [ ] [HFT] **Build**: matching-engine emits `Fill` events through a `tokio::sync::broadcast` channel for downstream
  market-data fan-out. Channel uses `backpressure::BackpressureStrategy::DropOldest` for slow subscribers. (~150 min)
  - **Why**: Fills must broadcast to: market-data feed (public), risk service (per-account aggregation), settlement service (clearing), audit log. Each consumer has different latency tolerance; DropOldest ensures slow consumers don't backpressure the engine.
  - **Design**:
    ```rust
    pub struct FillBroadcaster {
        tx: tokio::sync::broadcast::Sender<Fill>,
        subscribers: AHashMap<SubscriberId, Subscription>,
    }
    impl FillBroadcaster {
        pub fn emit(&self, fill: Fill) {
            let _ = self.tx.send(fill);  // ok if no receivers; slow receivers drop oldest naturally in tokio's bcast
        }
    }
    ```
    **Invariants**:
    - Sender is `Send + Sync`; many subscribers.
    - tokio bcast's queue-per-receiver: slow receivers see lag-count, can detect drops.
    - DropOldest semantics: when receiver lags > capacity, oldest queued msgs are dropped; receiver gets `RecvError::Lagged(n)`.
  - **Build steps**:
    1. (~20 min) `FillBroadcaster::new(capacity)`.
    2. (~30 min) Wire into match_order: every Fill emits via broadcast.
    3. (~30 min) Subscriber API: `subscribe() -> Receiver<Fill>`.
    4. (~30 min) Latency-tolerance tests: 100 subscribers, 10% slow (artificially); engine throughput stays at 1M/s.
    5. (~40 min) Subscriber that wants ZERO drops uses backpressure-aware path (separate fan-out via cross_shard channel with reliable strategy).
  - **Pitfalls**: defaults make all subscribers drop-tolerant; reliable subscribers (e.g., settlement) must use different path with explicit ack.
  - **Acceptance**: 1M/s emit throughput regardless of subscriber count or speed; slow subscriber observes Lagged correctly.
  - **Downstream**: W85+ marketdata reads from this; W90+ ledger reads from reliable-path variant.
