- [ ] **Build**: `crates/consensus-raft/src/membership.rs` — joint-consensus membership change (C_old → C_old,new →
  C_new). Tested with one-at-a-time member additions. (~150 min)
  - **Why (MAX DETAIL)**: Adding/removing nodes from a running Raft cluster is the #1 production-bug area. The naive "just update peer list" approach causes split-brain when nodes have inconsistent membership views. Joint consensus (Ongaro §6) requires BOTH old and new configurations to form majority during transition — provably safe.
  - *Back-of-envelope*: membership changes are *not* on the matching-engine submit hot path — they happen rarely (~1/hour at most in a stable cluster, ~10/hour during rebalance events). However, the *quorum check* runs on every AppendEntries commit-advance, which IS on the hot path (~100k AppendEntries acks/sec at 100k commits/sec ÷ 100-batch). So `quorum_check_under_joint` budget: **≤ 50 ns** per call. The Stable case is just `quorum_of(indices, nodes)` — a `Vec` sort/median (~100 ns for 5 nodes) — *already over budget*. Optimization (deferred to W67): cache the quorum threshold and compute via partial sort. For Joint case: two `quorum_of` calls + a `.min()` — ~200 ns; only paid during the rare transition window. **Membership is correctness-first, perf-secondary** — but the steady-state quorum check is hot.
  - **Read first**: Ongaro §6 (Cluster membership changes); Ongaro thesis §4 (refined single-server changes for simpler impl); etcd `raft/raft.go::applyConfChange`.
  - **Design**:
    ```rust
    pub enum ConfState {
        Stable(Vec<NodeId>),
        Joint { old: Vec<NodeId>, new: Vec<NodeId> },
    }

    impl<S> RaftState<S> {
        pub fn propose_membership_change(&mut self, change: ConfChange) -> Result<(), _> {
            // 1. Append C_old,new as special log entry
            let joint = match (&self.conf, &change) {
                (ConfState::Stable(old), ConfChange::AddNode(n)) => {
                    let mut new = old.clone(); new.push(*n);
                    ConfState::Joint { old: old.clone(), new }
                }
                (ConfState::Stable(old), ConfChange::RemoveNode(n)) => {
                    let new: Vec<_> = old.iter().filter(|x| *x != n).copied().collect();
                    ConfState::Joint { old: old.clone(), new }
                }
                _ => return Err(MembershipChangeInProgress),
            };
            let entry = LogEntry { term: ..., index: ..., command: encode_conf(&joint), ... };
            self.log.append(entry)?;
            // 2. On commit of joint entry → apply joint state; start replicating to BOTH C_old and C_new
            // 3. Once joint entry committed, propose C_new entry
            // 4. On commit of C_new entry → apply C_new, drop C_old
            Ok(())
        }

        fn quorum_check_under_joint(&self, indices: &HashMap<NodeId, u64>) -> u64 {
            match &self.conf {
                ConfState::Stable(nodes) => quorum_of(indices, nodes),
                ConfState::Joint { old, new } => {
                    // Both must form majority
                    quorum_of(indices, old).min(quorum_of(indices, new))
                }
            }
        }
    }
    ```
    **Invariants**:
    - During Joint state, an entry is committed iff replicated to majority of BOTH C_old AND C_new.
    - Only ONE membership change in flight at a time.
    - Removal of a non-voter: simpler — but we still treat as full join-consensus for uniformity.
  - **Build steps**:
    1. (~25 min) ConfState enum + ConfChange variants.
    2. (~30 min) propose_membership_change; encode joint as special LogEntry::ConfChange variant.
    3. (~30 min) On commit, update self.conf via state-machine apply path.
    4. (~30 min) `quorum_check_under_joint` overrides regular quorum during transition.
    5. (~25 min) Test: 3-node cluster, add 4th node; verify joint config commits; then C_new commits; then cluster operates as 4-node.
    6. (~10 min) Test: chain remove (drop 4th) → 3-node again.
  - **Pitfalls** (named, distributed):
    - *Two changes in flight*: starting C2 before C1 commits → undefined state. **Symptom**: split-brain on partition. **Fix**: explicit `MembershipChangeInProgress` rejection if joint state already active.
    - *Removed node still serving*: removed leader continues serving until learns of change. **Symptom**: stale data reads. **Fix**: leader steps down explicitly on applying its own removal; clients re-dial.
    - *Forgetting to replicate to new node BEFORE commit*: leader commits via OLD quorum, new node never receives entries. **Symptom**: new node has empty log when transition completes. **Fix**: leader starts replicating to new node IMMEDIATELY upon joint entry append (not commit). Use catch-up phase to ensure new node has near-current state before promoting to voter.
  - **Test scenarios**:
    - 3-node → add 4th → verify joint state, then C_new, then 4-node operates. 1000-entry replication after change.
    - 3-node → remove leader → new leader elected from {n2, n3} → continues.
    - Partition during joint: 2/4 each side. Neither side has majority of BOTH C_old (3-node) and C_new (4-node) until heal.
  - **Expect to hit (perf) #1 — `quorum_of` allocates a `Vec` for sorting on every commit-advance (bar (c) violation)**: the natural impl of `quorum_of(indices, nodes)` collects `indices` into a temporary `Vec<u64>`, sorts, returns the median. At 100k commit-advances/sec (100k AppendEntries acks ÷ 1-per-ack), that's 100k `Vec::new` + `Vec::push×N` + `Vec::sort` + `Vec::drop` per second. For 5-node cluster that's 100k × ~5 × 8 B vec = ~4 MB/sec of allocator churn just for membership tracking on a hot path.
    - Fix: pre-allocate a per-leader `quorum_scratch: [u64; MAX_CLUSTER_SIZE]` (or `SmallVec<[u64; 16]>`) reused across calls. The sort is in-place on the fixed array; the median is `scratch[n/2]` after sort. For a 5-node cluster, sort is ~20 ns (5-element insertion sort beats `sort_unstable` for tiny N). Even better: maintain a sorted `BTreeSet<u64>` of match_index values that updates on each ack (insert new + remove old = ~100 ns); median is O(1) via `iter().nth(n/2)`.
    - Cost avoided: ~50 ns alloc + ~50 ns dealloc + ~30 ns memcpy per check × 100k/sec = ~13 ms/sec saved; eliminates allocator visits from the commit-advance path; brings the hot path into the ≤ 50 ns budget.
    - Muscle: tiny-array operations on a hot path should use stack arrays / SmallVec, never `Vec::new` per call. Reapplies at: W74 matching-engine TIF arrival list, W77 aeron Image active-publication list, W83 ledger pending-transfers per-batch.
  - **Acceptance**: 4 membership changes (add, add, remove, remove) chain successfully; no split-brain; `quorum_check_under_joint` benched at ≤ 100 ns Stable / ≤ 200 ns Joint; heaptrack shows zero allocs in the commit-advance steady state.
  - **Downstream**: W67+ raft v1.0; W74+ matching-engine running on Raft uses this for shard rebalance.

- [ ] [HFT] **Build**: matching-engine emits `Fill` events through a `tokio::sync::broadcast` channel for downstream
  market-data fan-out. Channel uses `backpressure::BackpressureStrategy::DropOldest` for slow subscribers. (~150 min)
  - **Why**: Fills must broadcast to: market-data feed (public), risk service (per-account aggregation), settlement service (clearing), audit log. Each consumer has different latency tolerance; DropOldest ensures slow consumers don't backpressure the engine.
  - *Back-of-envelope*: at 1 M fills/sec/symbol × N subscribers (typically 4: marketdata, risk, settlement, audit), naive per-subscriber send = N × 1 M = 4 M sends/sec. Each `tokio::sync::broadcast::Sender::send` is ~50-100 ns including the per-receiver clone of the message (copy + atomic refcount on the slot). For `Fill` (~64 B after W60 layout fix), per-send memcpy is ~10 ns. Per-call overhead with N=4 subscribers ≈ ~200-400 ns/fill — eats half of the v1.0 per-fill budget (~1 µs). Bar (c): broadcast must encode-once and ship by reference (Arc'd `Fill`) — fan-out is ~N atomic-refcount bumps (~2 ns × N), not N memcpys.
  - **Design**:
    ```rust
    pub struct FillBroadcaster {
        tx: tokio::sync::broadcast::Sender<Fill>,
        subscribers: AHashMap<SubscriberId, Subscription>,
    }
    impl FillBroadcaster {
        pub fn emit(&self, fill: Fill) {
            let _ = self.tx.send(fill);  // ok if no receivers; slow receivers drop oldest naturally in tokio's bcast
        }
    }
    ```
    **Invariants**:
    - Sender is `Send + Sync`; many subscribers.
    - tokio bcast's queue-per-receiver: slow receivers see lag-count, can detect drops.
    - DropOldest semantics: when receiver lags > capacity, oldest queued msgs are dropped; receiver gets `RecvError::Lagged(n)`.
  - **Build steps**:
    1. (~20 min) `FillBroadcaster::new(capacity)`.
    2. (~30 min) Wire into match_order: every Fill emits via broadcast.
    3. (~30 min) Subscriber API: `subscribe() -> Receiver<Fill>`.
    4. (~30 min) Latency-tolerance tests: 100 subscribers, 10% slow (artificially); engine throughput stays at 1M/s.
    5. (~40 min) Subscriber that wants ZERO drops uses backpressure-aware path (separate fan-out via cross_shard channel with reliable strategy).
  - **Pitfalls**: defaults make all subscribers drop-tolerant; reliable subscribers (e.g., settlement) must use different path with explicit ack.
  - **Expect to hit (perf) #1 — `tokio::sync::broadcast` clones `Fill` per receiver (bar (c) violation)**: `tokio::sync::broadcast<Fill>` clones the message into each receiver's slot — at 4 receivers × 1 M fills/sec × ~10 ns memcpy per clone = ~40 ms/sec/shard pure memcpy overhead. Worse, the broadcast channel uses an internal `Mutex` for the slot ring head; under N receivers it can contend on the lock.
    - Fix: wrap each fill in `Arc<Fill>` at emit time (~10 ns alloc, BUT amortized via a per-shard pre-allocated Arc-slab for Fills); broadcast `Arc<Fill>` instead of `Fill`. Per-receiver delivery is now an atomic refcount bump (~2 ns) + a slot store. For a high-throughput marketdata path, replace `tokio::sync::broadcast` with the W11 bounded MPMC ring (single-producer-multi-consumer variant) keyed by `Arc<Fill>` — no mutex, lock-free, ~20 ns per fan-out regardless of N.
    - Cost avoided: ~10 ns × N memcpy per fill → ~2 ns × N refcount bump; ~40 ms/sec/shard at N=4 → ~8 ms/sec; eliminates the broadcast channel's internal mutex contention; removes per-receiver allocator visits.
    - Muscle: fan-out broadcast must share by Arc, not memcpy — same lesson as W59 raft replication (Arc'd payload to N followers). Reapplies at: W77 aeron multicast (shared payload to N subscribers via term buffer), W85 marketdata UDP multicast, W90 ledger event broadcast.
  - **Expect to hit (perf) #2 — DropOldest semantics under burst cause subscriber synchronization storm (bar (c) violation, subtle)**: when a slow subscriber lags, `tokio::broadcast` drops messages and the next `recv()` returns `RecvError::Lagged(n)`. Naive subscriber code on Lagged calls `recv()` again immediately — but the channel internally is contending with the producer + other subscribers; rapid re-recv during a backlog produces a thundering-herd: all subscribers re-poll the channel head atomic simultaneously, invalidating each other's cache lines. Symptom: marketdata subscriber's recv latency spikes from ~50 ns to ~5 µs during fast-market bursts.
    - Fix: on `RecvError::Lagged`, subscriber backs off with an exponential delay (start ~1 µs, max ~100 µs) before re-recv; OR (better) the subscriber's recv-loop holds a small per-subscriber slot ring (W11 SPSC pattern) which the producer fans into — broadcast becomes "producer writes one Arc, each subscriber pulls from their dedicated ring". This eliminates the shared atomic contention entirely.
    - Cost avoided: ~5 µs subscriber p99 during burst → ~50 ns steady; eliminates the cross-subscriber cache-coherence storm.
    - Muscle: multi-consumer broadcast over a shared atomic gets worse with more subscribers — fan out via per-subscriber dedicated channels for steady latency. Reapplies at: W77 aeron Image (per-subscriber state), W85 marketdata per-subscriber UDP socket.
  - **Acceptance**: 1M/s emit throughput regardless of subscriber count or speed; slow subscriber observes Lagged correctly; **per-fill broadcast overhead ≤ 50 ns at N=4 subscribers** (verified by criterion); subscriber recv p99 ≤ 100 ns during burst.
  - **Downstream**: W85+ marketdata reads from this; W90+ ledger reads from reliable-path variant.
