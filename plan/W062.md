  - 🔧 **Why this matters**: adding/removing nodes from a running Raft cluster is the #1 production-bug area in consensus systems. The naive "just update peer list" approach causes split-brain when nodes have inconsistent membership views; multiple production Raft incidents (TiKV 2018, etcd 2019) trace to this. Joint consensus (Ongaro §6) requires BOTH old and new configurations to form majority during transition — provably safe. Downstream: W67 (raft v1.0 ship gate), W74 (matching-engine on Raft uses this for shard rebalance), W84 (ledger leader-failover during rolling restart), W92 (VSR also uses joint-consensus shape for view changes).

  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: a cluster that swaps configurations atomically (the naive "update peer list everywhere at once") can split: some nodes use C_old to form quorum, others use C_new; both think they have a leader; you have two committed logs and divergent state machines. Joint consensus solves this by FORCING any commit during transition to satisfy BOTH old and new quorums — making split-brain physically impossible because no candidate can win an election under both quorums on different sides of a partition.

  - **Requirements** — write in `crates/consensus-raft/notes/62_membership_design.md`:
    - R1. `ConfState` has two variants: `Stable(Vec<NodeId>)` and `Joint { old, new }`. Joint is a *transient* state between two Stables.
    - R2. **At most one membership change in flight**: attempting `propose_membership_change` while already in Joint state returns `Err(MembershipChangeInProgress)`.
    - R3. **Joint commit rule**: in Joint state, an entry commits iff replicated to majority of BOTH `old` AND `new`. The quorum check is `min(quorum_of(indices, old), quorum_of(indices, new))`.
    - R4. **Catch-up before voter promotion**: when adding a node, leader replicates to it IMMEDIATELY on appending the joint entry (not on commit). The new node is a non-voting learner until it has caught up to within ~10 entries of the leader's log.
    - R5. **Self-removal step-down**: a leader that applies its own removal must step down (transition to follower) and refuse further client writes. Clients re-dial to discover the new leader.
    - R6. **Quorum-check hot path budget**: `quorum_check_under_joint` runs on every AppendEntries commit-advance (~100k/sec). Budget ≤ 100 ns Stable, ≤ 200 ns Joint. Zero allocations in steady state.
    - R7. **Partition safety**: any 2-vs-3-vs-4 partition during Joint state leaves NO side able to commit until the partition heals. Verify via property test.
    - R8. **Chained changes**: 4 sequential changes (add, add, remove, remove) all complete; cluster never observes split-brain.

  - **Design walk-through** — answer each in your design doc; no peeking at etcd `applyConfChange` or TiKV until Phase 3:
    - D1. Write the state-transition diagram: Stable(C_old) → Joint(C_old, C_new) → Stable(C_new). Which event triggers each transition? (Hint: the proposal of and commit of a special log entry.)
    - D2. Encode the joint config as a `LogEntry::ConfChange(ConfState)` special variant. Why log it (vs an out-of-band RPC)? (Hint: log replication IS the consensus path; everything that affects safety must flow through it.)
    - D3. The `quorum_of(indices: &HashMap<NodeId, u64>, nodes: &[NodeId]) -> u64` helper: the natural impl collects indices into a `Vec<u64>`, sorts, returns the median. What's the alloc cost per call at 100k calls/sec for a 5-node cluster? (Compute the back-of-envelope; bar-(c) violation looms.)
    - D4. The match_index tracking: each follower has an index; the leader sees N of them. Should the data structure be `HashMap<NodeId, u64>`, `[(NodeId, u64); MAX]`, `BTreeMap<NodeId, u64>`, or a sorted `BTreeSet<u64>` keyed by index? Each has a different update-cost vs median-cost trade-off. Pick one and justify against R6.
    - D5. New-node catch-up: when does the leader send the new node its first AppendEntries? (Hint: immediately upon appending the joint entry to its own log — NOT on commit.) Why this specific timing? What goes wrong if it waits for commit?
    - D6. Self-removal: write the step-down flow in 5 numbered steps. What's the very first thing the leader does upon applying a `RemoveNode(self)` entry? What does it return to in-flight client write requests?
    - D7. **Pre-mortem #1 (split-brain)**: write the 7-step trace where a leader proposes a membership change, partitions immediately, the old-side commits via C_old quorum, the new-side elects a new leader and commits via C_new quorum, partition heals, two logs diverge. Identify exactly which Joint-consensus rule prevents this trace from being possible.
    - D8. **Pre-mortem #2 (quorum-alloc storm)**: walk through what happens at 100k commits/sec when `quorum_of` allocates a `Vec`. Compute the allocator pressure; estimate the latency hit on AppendEntries commit-advance.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  - **When `bench_quorum_check_stable_under_100ns` reports ~250 ns and `quorum_check_zero_alloc` flags 100k allocs/sec:**
    - Symptom: heaptrack shows ~100k `Vec::with_capacity` + dealloc/sec attributable to `quorum_of`. p99 is ~250 ns, 2.5× over the 100 ns budget. At 100k commit-advances/sec, that's ~13 ms/sec/leader just for membership tracking.
    - Why: the natural impl of `quorum_of` collects indices into a temporary `Vec<u64>`, sorts, takes the median, drops the Vec. Each commit-advance allocates and frees ~5 × 8 B = 40 B + Vec header.
    - Fix: pre-allocate a per-leader `quorum_scratch: SmallVec<[u64; 16]>` (or fixed `[u64; MAX_CLUSTER_SIZE]`). The check copies indices into scratch (~5 × 8 B memcpy, ~10 ns), sorts in-place (5-element insertion sort, ~20 ns), reads median (~2 ns), clears scratch (no dealloc). Total ~35-50 ns. Even better for R6: maintain a sorted `BTreeSet<u64>` of `match_index` values that updates incrementally on each ack — insert new + remove old = ~100 ns once per ack, median is O(1) per check.
    - Cost avoided: ~100 ns alloc/dealloc per check × 100k/sec = ~10 ms/sec; brings hot path under budget.
    - Muscle: tiny-array operations on a hot path use stack arrays / SmallVec, never `Vec::new` per call. Reapplies at: W74 matching-engine TIF arrival list, W77 aeron Image active-publication list, W83 ledger pending-transfers per-batch.

  - **When `partition_during_joint_no_commit` shows the old-side committing entries:**
    - Symptom: under a {2,2} partition during Joint state, the side that retains 2-of-3 old quorum commits new entries — the test expected no commit until heal.
    - Why: your `quorum_check_under_joint` returned `quorum_of(indices, old)` when in Joint, not `min(old, new)`. The Joint commit rule isn't enforced — you've reduced to the C_old quorum during transition, which is exactly what Ongaro §6 forbids.

Re-run the partition test; the old-side has 2-of-3 old (satisfied) but 2-of-4 new (NOT satisfied — needs 3); commit blocks. Heal lets new-node catch up; both quorums satisfied; commit advances.
    - Muscle: Joint consensus's "both quorums" rule is THE thing that prevents split-brain — any reduction (just-old or just-new) is a safety bug. Reapplies at: W84 ledger leader-failover, W92 VSR view change.

  - **When `new_node_replicated_before_commit` shows the new node receiving its first AE only AFTER the joint entry commits:**
    - Symptom: the test captures AE traffic; the new node's first AE arrives AFTER the joint entry's commit. By then, the new node has an empty log but C_new requires it as a voter — its match_index is 0, blocking all future commits.
    - Why: you only added the new node to the replication set when the joint entry COMMITTED. The new node missed everything before that point and now stalls the cluster.
    - Fix: the leader's replication-target set updates when it APPENDS the joint entry to its own log (a local event), NOT when the entry commits (a quorum event). The new node receives AEs immediately; by the time the joint entry commits, the new node likely has the entry too — its match_index advances on its own ack.
    - Muscle: replication-target membership tracks the LEADER'S applied state, not the cluster's committed state — leaders project the future to bootstrap catch-up. Reapplies at: W74 shard rebalance, W92 VSR new replica join.

  - **When `removed_leader_steps_down` shows the old leader still accepting writes after applying its removal:**
    - Symptom: client writes succeed against the removed leader; ghost commits happen because the leader still thinks it leads. Stale reads ensue.
    - Why: applying `RemoveNode(self)` updated `conf` but didn't transition the leader role. The leader keeps sending AEs to a cluster that no longer includes it; no one acks; nothing commits but reads still return its local state.
    - Fix: in the state-machine apply path, special-case `ConfChange::RemoveNode(id) if id == self.id`: (1) set role to Follower, (2) reset leader_id to None, (3) fail in-flight client writes with `NotLeader`, (4) stop sending AEs. Clients re-dial and discover the new leader via the standard rejection path.
    - Muscle: a node applying its own removal MUST step down immediately — staying as leader is silent data corruption. Reapplies at: W74 shard reassignment, W84 ledger leader rotation.

  - **When `chain_four_changes_no_split_brain` deadlocks on the 2nd `RemoveNode` step:**
    - Symptom: chain runs Add, Add, Remove cleanly; the second Remove proposes and the cluster gets stuck — no commits advance.
    - Why: removal of an already-removed node, OR an out-of-date local view, OR the Joint→Stable transition didn't fire because the C_new entry never appended. Likely cause: R2's "one change in flight" check used the wrong predicate (e.g., checked Stable→Joint but not Joint→Stable). The chain wedges on a stale Joint state.
    - Fix: define "in flight" precisely: a change is in flight from the moment `propose_membership_change` appends the joint entry until the SUBSEQUENT C_new entry COMMITS. Once C_new commits, the next change is allowed. Encode this as a state on the leader; assert in `propose` against it.
    - Muscle: "one change in flight" is a 4-state machine (Idle, JointProposed, JointCommitted, NewProposed), not a 2-state — name the transitions explicitly. Reapplies at: W84 multi-step leader rotations, W92 chained VSR view changes.

  - 🔧 **Why this matters**: fills must broadcast to multiple consumers — market-data feed (public), risk service (per-account aggregation), settlement service (clearing), audit log. Get this wrong and the matching engine stalls under slow-consumer pressure (one slow subscriber freezes the engine, p99 goes to seconds, exchange offline).   #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: a matching engine producing 1 M fills/sec/symbol fanned to N consumers naïvely (one memcpy per consumer per fill) burns ~10 ns × N memcpy per fill = ~40 ms/sec/shard pure copy at N=4. Worse, a slow consumer that backpressures the engine freezes matching entirely. The solution: (a) share fills by `Arc<Fill>` (one alloc, N refcount bumps), (b) drop-oldest semantics so slow consumers self-degrade without blocking the producer, (c) per-subscriber slot rings to eliminate cross-subscriber atomic contention during burst.

  - **Requirements** — write in `crates/matching-engine/notes/62_broadcast_design.md`:
    - R1. A `FillBroadcaster` type with `emit(&self, fill: Fill)` and `subscribe() -> FillSubscription` API.
    - R2. **Producer never blocks**: `emit` is non-blocking; if any subscriber's ring is full, the OLDEST message in that ring is dropped (not the new one).
    - R3. **Share by Arc, not by clone**: fills are wrapped in `Arc<Fill>` at emit time once. Fan-out to N subscribers is N atomic refcount bumps (~2 ns each), not N memcpys (~10 ns each).
    - R4. **Lag observability**: a subscriber that dropped messages observes a `Lagged(n)` signal on its next recv, so downstream consumers (settlement, audit) can detect and react.
    - R5. **Reliable path for critical subscribers**: a separate `subscribe_reliable() -> ReliableSubscription` API for consumers that require zero-drop (settlement, audit). Reliable subscribers DO apply backpressure but through a SEPARATE channel; never on the broadcast path.
    - R6. **Per-fill broadcast budget**: ≤ 50 ns per fill at N=4 subscribers (verified by criterion). Subscriber recv p99 ≤ 100 ns during burst.
    - R7. **Engine throughput unaffected by subscriber count**: 1 M fills/sec maintained whether N=1 or N=100 or any subscriber is artificially slow.
    - R8. **Zero alloc on emit steady state**: the `Arc<Fill>` itself can come from a per-shard slab pool that recycles; emit makes 0 allocator calls in steady state.

  - **Design walk-through** — answer each in your design doc; no peeking at LMAX Disruptor or aeron until Phase 3:
    - D1. Pick the broadcast primitive shape:
      (a) `tokio::sync::broadcast<Fill>` (memcpy per receiver),
      (b) `tokio::sync::broadcast<Arc<Fill>>` (refcount per receiver, still shared mutex on slot ring),
      (c) Custom W11 SPMC ring per subscriber (one shared atomic published seq per emit, each subscriber owns its read-cursor and ring slots).
      Justify against R3, R6, R7.
    - D2. Compute the cost-per-fill for each shape at N=4: (a) 4 × 10 ns memcpy + mutex; (b) 4 × 2 ns refcount + mutex; (c) 1 × atomic store + 4 × atomic load (per-subscriber, no shared atomic on read). Which lands under the 50 ns budget?
    - D3. `Arc<Fill>` slab: write the recycling design. When a subscriber finishes with an Arc, where does it go? (Hint: Arc's drop already returns memory to allocator; for true zero-alloc you need a pre-allocated pool of Arc payloads.) For v0.5, is "Arc::new on emit" acceptable, given that Arc alloc is amortized over N=4 deliveries?
    - D4. Drop-oldest semantics: when subscriber S's ring is full, who drops what — producer dropping for S, or S dropping its own oldest on next read? Which gives the producer's non-blocking guarantee? Which is easier to instrument with `Lagged(n)`?
    - D5. Reliable subscription path: name the separate primitive. (Hint: a bounded MPMC queue with backpressure; settlement's commit-ack flows BACK to a separate ack stream, never blocks emit.) Where does the reliable subscriber's pressure surface — directly on emit, or on a separate worker that drains a buffer?
    - D6. Lagged signal: what type carries it? (Hint: `Result<Arc<Fill>, RecvError::Lagged(u64)>`.) How does a subscriber recover after Lagged — re-sync from current head, or skip ahead with a "I missed n events" annotation?
    - D7. **Pre-mortem #1 (memcpy storm)**: write the 3-step trace where shape (a) `tokio::sync::broadcast<Fill>` is used at N=10 subscribers; compute the per-shard memcpy cost (10 × 10 ns × 1 M/sec); explain why it breaches budget.
    - D8. **Pre-mortem #2 (thundering herd)**: write the 4-step trace where 4 subscribers all retry `recv` simultaneously after a Lagged event under shape (b); explain the cross-subscriber cache-coherence storm; identify which shape from D1 prevents it.
  - **Output**: `notes/62_broadcast_design.md` with R1–R8, D1–D8, shape decision recorded with cost numbers.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `bench_emit_n4_under_50ns` reports ~250 ns and `engine_throughput_invariant_with_n_subscribers` fails at N=16:**
    - Symptom: emit cost scales linearly with N at ~50 ns per added subscriber. At N=16 the engine throughput collapses below 1 M/sec.
    - Why: you used `tokio::sync::broadcast<Fill>` — the broadcast channel clones the `Fill` value (~10 ns memcpy at ~64 B per fill) into each receiver's slot. At N=4 that's ~40 ns just for memcpys; the channel's internal mutex on the slot-ring head adds ~10-50 ns contention; total ~250 ns.
    - Fix: change the broadcast item type to `Arc<Fill>`. Producer constructs one `Arc::new(fill)` (~10 ns alloc, amortized over N deliveries), and the broadcast channel ships the Arc by clone (an atomic refcount bump ~2 ns × N). Per-fill total: ~10 ns alloc + ~2 ns × N + ~10 ns channel overhead = ~30 ns at N=4. For v1.0 (post W77 muscle), replace tokio broadcast with a custom SPMC ring (one shared `published_seq: AtomicU64` + per-subscriber ring slot of `Arc<Fill>`); fan-out becomes 1 atomic store + N atomic loads — no shared mutex.
    - Cost avoided: ~10 ns × N memcpy per fill → ~2 ns × N refcount; ~40 ms/sec/shard at N=4 → ~8 ms/sec; eliminates the broadcast channel's internal mutex; removes per-receiver allocator visits.
    - Muscle: fan-out broadcast must share by Arc, not memcpy — same lesson as W59 raft replication (Arc'd payload to N followers). Reapplies at: W77 aeron multicast (shared payload via term buffer), W85 marketdata UDP multicast, W90 ledger event broadcast.

  - **When `bench_subscriber_recv_under_burst_100ns` reports ~5 µs p99 during burst:**
    - Symptom: recv p99 spikes from ~50 ns steady-state to ~5 µs during a burst — 100× over budget. `perf` shows cache-misses concentrated in the broadcast channel's slot-ring atomics.
    - Why: even with `Arc<Fill>`, `tokio::sync::broadcast` uses a SHARED slot-ring head. When a subscriber sees `Lagged`, naive subscriber code calls `recv()` again immediately — N subscribers all hammering the same atomic invalidate each other's cache lines (MESI ping-pong). The thundering-herd manifests as a 100× recv latency spike during fast-market bursts.
    - Fix: per-subscriber slot rings. Producer emits to ONE shared published-seq, and each subscriber's recv consults its OWN ring + read-cursor (W11 SPSC pattern). The only cross-subscriber atomic is the published-seq, which is read-only on the subscriber side. Cache lines stay subscriber-local; recv p99 stays ~50 ns regardless of N or burst rate. On `Lagged`, the subscriber backs off briefly (~1-10 µs exponential) before resyncing — but the resync reads its own ring, not a contested atomic.
    - Cost avoided: ~5 µs subscriber p99 → ~50 ns; eliminates the cross-subscriber cache-coherence storm.
    - Muscle: multi-consumer broadcast over a SHARED atomic gets worse with more subscribers — fan out via per-subscriber dedicated rings/slots for steady latency. Reapplies at: W77 aeron Image (per-subscriber state), W85 marketdata per-subscriber UDP socket.

  - **When `slow_subscriber_does_not_block_producer` deadlocks at 50k fills:**
    - Symptom: emit blocks after the broadcast channel's slot ring fills up; the slow subscriber's slot has 1024 unread messages, the producer waits to make room.
    - Why: you used a backpressure-applying primitive (e.g., `tokio::sync::mpsc` with full-channel block, or `tokio::sync::broadcast` configured without overflow semantics). The producer is now hostage to the slow subscriber.
    - Fix: configure overflow behavior to drop-oldest at the slot-ring level — when the producer would block, instead advance the slot-ring's write cursor over the oldest unread message; the slow subscriber's read cursor falls behind, and its next `recv` returns `Lagged(n)`. With per-subscriber rings (Fix from previous card), each subscriber's overflow is isolated — the producer never blocks on any subscriber.
    - Muscle: a producer that can be blocked by a slow consumer is a fault domain leak — the engine MUST be insulated by drop-oldest semantics on every broadcast channel. Reapplies at: W77 aeron flow control, W85 UDP fan-out.

  - **When `reliable_subscriber_no_drops` shows drops in the reliable path:**
    - Symptom: the reliable subscriber (settlement) observes Lagged events — but the contract says it MUST see every fill.
    - Why: you wired the reliable subscriber through the same drop-oldest broadcast as the unreliable ones. Reliable subscribers must use a SEPARATE primitive (a bounded MPMC queue with backpressure-via-ack, never drop).
    - Fix: emit fans into TWO sinks: (1) the unreliable broadcast (drop-oldest, all marketdata/risk/audit subscribers), and (2) a reliable bounded MPMC queue (capacity sized for the largest tolerable settlement-lag, e.g., 1M slots ~ 1 sec at 1 M fills/sec). The reliable queue's full-condition propagates via a SEPARATE backpressure signal (e.g., "halt new orders" at the gateway), NEVER back to the matching engine's emit.
    - Muscle: reliable and unreliable fan-out are different primitives — never share the channel; always pair the reliable queue with an out-of-band backpressure signal at the system boundary. Reapplies at: W90 ledger event broadcast (reliable for clearing), W92 VSR replica notification.

  - **When `bench_emit_zero_alloc_steady_state` shows ~1 M Arc allocs/sec:**
    - Symptom: heaptrack flags 1 M `Arc::new` allocations/sec attributable to emit. Each ~30 ns; ~30 ms/sec/shard.
    - Why: every `Arc::new(fill)` calls the global allocator. Even though Arc lets us share, the allocation itself is on the hot path.
    - Fix v0.5: accept the cost — Arc alloc amortizes over N=4 deliveries, so per-delivery it's ~7.5 ns. Document the trade-off. Fix v1.0: pre-allocate an Arc slab (a pool of `Arc<MaybeUninit<Fill>>` payloads). Emit takes one from the pool (~5 ns), initializes the fill, broadcasts. On the Arc's strong-count → 0, return the payload to the pool instead of dropping. This requires custom Arc-pool plumbing; defer to W77 / W85.
