**Tuesday — Raft membership Build (heavy day: this is the week's deepest exercise)**

- [ ] **Build**: `crates/consensus-raft/src/membership.rs` — joint-consensus membership change (C_old → C_old,new → C_new). (~total 230 min across 3 phases)
  - 🔧 **Why this matters**: mirrors etcd `applyConfChange` / raft-rs `Configuration::enter_joint`. Adding/removing nodes from a running Raft cluster is the #1 production-bug area in consensus systems — the naive "just update the peer list" causes split-brain when nodes hold inconsistent membership views (TiKV 2018, etcd 2019 both trace incidents here). Joint consensus (Ongaro §6) requires BOTH old and new configurations to form a majority during the transition — provably no candidate can win under both quorums across a partition. **Your first attempt WILL fail ≥3 tests below**: the natural `quorum_of` allocates a Vec per call (blows the bar-(c) hot-path budget), the natural Joint commit rule reduces to one quorum (split-brain), and the natural "one change in flight" predicate is a 2-state guard where the truth is a 4-state machine. The debug session IS the lesson. Downstream: W67 (v1.0 ship gate), W74 (shard rebalance), W84 (ledger leader-failover during rolling restart), W92 (VSR view changes reuse the joint shape).

  - *Mental model*: a cluster that swaps configurations atomically can split — some nodes form quorum under C_old, others under C_new, both elect a leader, two logs diverge. Joint consensus inserts a transient `Joint{old,new}` config in which EVERY commit must satisfy BOTH quorums, making split-brain physically impossible: no candidate can win an election under both quorums on different sides of a partition. The `Joint` state is a transient bridge between two `Stable` states, entered and left by committing a special log entry.

  - *Contract* (signature-level only — never the body):
    ```rust
    pub enum ConfState { Stable(Vec<NodeId>), Joint { old: Vec<NodeId>, new: Vec<NodeId> } }
    pub enum ConfChange { AddNode(NodeId), RemoveNode(NodeId) }
    pub enum LogEntry { /* ... */ ConfChange(ConfState) }
    pub enum MembershipError { MembershipChangeInProgress, NotLeader }
    impl RaftNode {
        pub fn propose_membership_change(&mut self, c: ConfChange) -> Result<(), MembershipError>;
        fn quorum_check_under_joint(&self, indices: &HashMap<NodeId, u64>) -> u64; // returns committable index
    }
    ```

  - *Back-of-envelope* (bar (c)): `quorum_check_under_joint` runs on every AppendEntries commit-advance (~100k/sec/leader). A natural `Vec<u64>` collect+sort costs ~50 ns malloc (Jeff-Dean ~50 ns/alloc) + ~5×8 B copy + sort + ~30 ns free ≈ **~100-250 ns/call AND 1 alloc/call**. At 100k/sec that's **~10-25 ms/sec/leader and 100k allocs/sec** — pure overhead, allocator-pressure cliff. Target: a stack `[u64; MAX]` or incrementally-maintained sorted structure → **~35-50 ns, 0 allocs**. The cliff: **alloc path ~2.5× over budget + GC-class allocator pressure vs zero-alloc scratch**.

  - **Requirements** R1..R8 — write in `crates/consensus-raft/notes/62_membership_design.md`:
    - R1. `ConfState` has two variants: `Stable(Vec<NodeId>)` and `Joint { old, new }`. Joint is a *transient* state between two Stables.
    - R2. **At most one membership change in flight**: `propose_membership_change` while already mid-transition returns `Err(MembershipChangeInProgress)`.
    - R3. **Joint commit rule**: in Joint state, an entry commits iff replicated to a majority of BOTH `old` AND `new`: `min(quorum_of(indices, old), quorum_of(indices, new))`.
    - R4. **Catch-up before voter promotion**: a newly-added node receives AppendEntries IMMEDIATELY on the leader appending the joint entry (local event), and is a non-voting learner until within ~10 entries of the leader's log.
    - R5. **Self-removal step-down**: a leader applying its own removal transitions to Follower and refuses further client writes (`NotLeader`); clients re-dial to discover the new leader.
    - R6. **Quorum-check hot-path budget**: ≤100 ns Stable, ≤200 ns Joint, **0 allocations steady state** (bar (c)).
    - R7. **Partition safety**: any 2-vs-3-vs-4 partition during Joint leaves NO side able to commit until the partition heals.
    - R8. **Chained changes**: 4 sequential changes (add, add, remove, remove) all complete; cluster never observes split-brain.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `propose_change_in_stable_creates_joint` reports `ConfState::Stable` instead of `Joint`:**
    - Symptom: after `propose_membership_change(AddNode(n4))` the state is still `Stable([1,2,3])` (or already `Stable([1,2,3,4])`) — never `Joint`.
    - Why: the natural reach is to mutate the peer list directly (`self.conf = Stable(new_list)`) — the "just update the peer list" bug. There is no transient Joint config, so D7's split-brain trace is now reachable; the test catches the missing bridge state.
    - Fix: `propose_membership_change` must compute `C_new` from the change, build `ConfState::Joint { old: C_old, new: C_new }`, and append it as a `LogEntry::ConfChange(Joint{..})` — it does NOT touch `self.conf` directly. The leader leaves Joint only when the subsequent `Stable(C_new)` entry commits.
    - Cost avoided: a one-line "update peer list" shortcut that reintroduces the entire split-brain class — green compile, latent corruption.
    - Muscle: every membership transition goes through a logged transient Joint config — direct peer-list mutation is the bug. Reapplies at: W84 ledger leader rotation, W92 VSR view-change config entry.

  - **(NEWBIE) When `chain_four_changes_no_split_brain` deadlocks on the 2nd `RemoveNode` step:**
    - Symptom: chain runs Add, Add, Remove cleanly; the second Remove proposes and the cluster wedges — no commits advance.
    - Why: R2's "one change in flight" check used the wrong predicate (a 2-state `is_joint` bool that only guards Stable→Joint, not Joint→Stable). The chain stalls on a stale Joint state — the C_new entry never appended, so the machine never returned to Idle.
    - Fix: define "in flight" precisely as the D9 4-state machine — a change is in flight from `propose` appending the joint entry until the subsequent C_new entry COMMITS; only then is the next change allowed. Encode it as `enum ChangePhase { Idle, JointProposed, JointCommitted, NewProposed }` on the leader and assert against it in `propose`.
    - Cost avoided: a wedged cluster (availability outage); the test goes from hang to green.
    - Muscle: "one change in flight" is a 4-state machine, not a 2-state bool — name the transitions explicitly. Reapplies at: W84 multi-step ledger leader rotations, W92 chained VSR view changes.

  - **(SENIOR) When `removed_leader_steps_down` shows the old leader still accepting writes after applying its removal:**
    - Symptom: client writes succeed against the removed leader; ghost commits and stale reads ensue.
    - Why: applying `RemoveNode(self)` updated `conf` but did not transition the role. The leader keeps sending AEs to a cluster that excludes it; no one acks, nothing commits, but local reads still return.
    - Fix: special-case `ConfChange::RemoveNode(id) if id == self.id` in the apply path: (1) role → Follower, (2) leader_id → None, (3) fail in-flight client writes with `NotLeader`, (4) stop sending AEs. Clients re-dial via the standard rejection path.
    - Cost avoided: silent data corruption (ghost commits); not "slow" — a correctness hole.
    - Muscle: a node applying its own removal MUST step down immediately. Reapplies at: W74 shard reassignment, W84 ledger leader rotation.

  - **(SENIOR) When `new_node_replicated_before_commit` shows the new node's first AE arriving only AFTER the joint entry commits:**
    - Symptom: the new node's first AE arrives after the joint entry's commit; its log is empty but C_new requires it as a voter — `match_index` 0 blocks all future commits.
    - Why: the leader added the new node to the replication set on COMMIT (a quorum event) instead of on APPEND (a local event). The new node missed everything before commit and now stalls the cluster.
    - Fix: update the leader's replication-target set when it APPENDS the joint entry to its own log, not when the entry commits. The new node receives AEs immediately and likely has the entry by commit time; its `match_index` advances on its own ack.
    - Cost avoided: a stalled cluster post-membership-change (availability outage).
    - Muscle: replication-target membership tracks the LEADER'S applied state, not the cluster's committed state — leaders project the future to bootstrap catch-up. Reapplies at: W74 shard rebalance, W92 VSR new-replica join.

  - **(EXPERT) When `partition_during_joint_no_commit` shows the old-side committing entries:**
    - Symptom: under a {2,2} partition during Joint, the side retaining 2-of-3 old quorum commits new entries — the test expected no commit until heal.
    - Why: `quorum_check_under_joint` returned `quorum_of(indices, old)` in the Joint arm, not `min(old, new)` — exactly the D6(b) anti-shortcut. You reduced to the C_old quorum during transition, which Ongaro §6 forbids.
    - Fix: in the Joint arm return `quorum_of(indices, old).min(quorum_of(indices, new))`. The old-side has 2-of-3 old (ok) but 2-of-4 new (needs 3 — blocked); commit stalls until heal lets the new node catch up.
    - Cost avoided: split-brain / divergent committed logs — the worst-class consensus bug, not a perf miss.
    - Muscle: Joint consensus's "both quorums" rule is THE split-brain guard — any reduction (just-old or just-new) is a safety bug. Reapplies at: W84 ledger leader-failover, W92 VSR view change.

  - **(EXPERT, perf) When `bench_quorum_check_stable_under_100ns` reports ~250 ns and `quorum_check_zero_alloc` flags 100k allocs/sec (bar (c) violation):**
    - Symptom: heaptrack/alloc-shim shows ~100k `Vec::with_capacity` + dealloc/sec attributable to `quorum_of`; p99 ~250 ns, 2.5× over the 100 ns budget. At 100k commit-advances/sec that's ~13 ms/sec/leader just for membership tracking.
    - Why: the natural `quorum_of` collects indices into a temporary `Vec<u64>`, sorts, takes the median, drops the Vec — ~5×8 B + Vec header allocated and freed per commit-advance. This is the D8 alloc-storm.
    - Fix: maintain an incrementally-sorted `BTreeSet<u64>` (or a per-leader `[u64; MAX_CLUSTER]` scratch sorted in-place by a 5-element insertion sort, ~20 ns). With BTreeSet, each ack does insert-new + remove-old (~100 ns once per ack) and the median is O(1) per check; with the scratch array, the check is ~10 ns memcpy + ~20 ns sort + ~2 ns read = ~35-50 ns, **0 allocs**.
    - Cost avoided: **~100 ns alloc/dealloc per check × 100k/sec ≈ 10 ms/sec/leader, plus 100k allocs/sec of allocator pressure (bar (c) violation)** → under budget, zero-alloc.
    - Muscle: tiny-array ops on a hot path use stack arrays / SmallVec / incremental structures, never `Vec::new` per call. Reapplies at: W74 matching-engine TIF arrival list, W77 aeron Image active-publication list, W83 ledger pending-transfers per-batch.

  - **#### 5-year failure mode** (write in `crates/consensus-raft/notes/62_membership_followup.md` after green): when v2.0 supports learners-as-voters (Raft §6 extension: a caught-up learner can be promoted with a single-entry config change, no joint state), the joint-consensus path becomes the fallback rather than the default. TRIGGER: the operational SLA "rebalance latency ≤ 1 s" can't be met by the two-round-trip Joint path under WAN latency. Migration (1 line): add a `PromoteLearner(NodeId)` single-entry change when the learner's `match_index` is within ε of the leader; fall back to Joint otherwise.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  Ordered newbie → expert.

  - **(NEWBIE) When `slow_subscriber_does_not_block_producer` deadlocks at ~1k fills:**
    - Symptom: emit blocks once a subscriber's channel fills; the slow subscriber has 1024 unread messages and the producer waits for room.
    - Why: you used a backpressure-applying primitive (`tokio::sync::mpsc` with full-channel block, or broadcast without overflow semantics). The producer is now hostage to the slowest consumer.
    - Fix: drop-oldest at the ring level — when emit would block, advance the write cursor over the oldest unread slot; the slow subscriber's read cursor falls behind and its next `recv` returns `Lagged(n)`. With per-subscriber rings, each subscriber's overflow is isolated; emit never blocks on anyone.
    - Cost avoided: a slow consumer freezing matching (p99 → seconds, exchange offline) — a fault-domain leak, not "slow".
    - Muscle: a producer that a slow consumer can block is a fault-domain leak — insulate the engine with drop-oldest on every broadcast path. Reapplies at: W77 aeron flow control, W85 UDP fan-out.

  - **(SENIOR) When `emit_arrives_at_n_subscribers_same_arc` fails Arc::ptr_eq:**
    - Symptom: all 4 subscribers receive equal-valued but pointer-distinct `Fill`s.
    - Why: you parameterized `broadcast<Fill>` — the channel clones the `Fill` value into each receiver's slot (memcpy), so each gets its own copy.
    - Fix: change the item type to `Arc<Fill>`; construct one `Arc::new(fill)` at emit, ship it by clone (atomic refcount bump). All receivers share the same allocation.
    - Cost avoided: ~10 ns × N memcpy/fill → ~2 ns × N refcount; ~40 ms/sec/shard at N=4 → ~8 ms/sec.
    - Muscle: fan-out broadcast must share by Arc, not memcpy. Reapplies at: W77 aeron multicast (shared term buffer), W85 marketdata UDP multicast, W90 ledger event broadcast.

  - **(EXPERT) When `reliable_subscriber_no_drops` shows drops in the reliable path:**
    - Symptom: the settlement (reliable) subscriber observes Lagged events — but its contract is every fill, in order.
    - Why: you wired the reliable subscriber through the same drop-oldest broadcast as the unreliable ones (D6(c) anti-shortcut).
    - Fix: emit fans into TWO sinks — (1) the unreliable drop-oldest broadcast (marketdata/risk/audit), (2) a reliable bounded MPMC queue (sized for the largest tolerable settlement lag, e.g. 1 M slots ≈ 1 sec at 1 M/sec). The reliable queue's full-condition propagates via a SEPARATE signal ("halt new orders" at the gateway), never back to emit.
    - Cost avoided: lost settlement/audit records — a correctness/compliance hole, not a perf miss.
    - Muscle: reliable and unreliable fan-out are different primitives — never share the channel; pair the reliable queue with an out-of-band backpressure signal at the system boundary. Reapplies at: W90 ledger event broadcast (reliable for clearing), W92 VSR replica notification.

  - **(SENIOR) When `lagged_subscriber_recovery_resyncs` returns the missed messages instead of the current head:**
    - Symptom: after a `Lagged(n)`, the slow subscriber's next `recv` returns the OLDEST surviving message in the ring, then walks forward through the backlog — it never reaches the live head, so it stays permanently behind under sustained load.
    - Why: `recv` advanced the read-cursor by one slot on `Lagged` instead of snapping it to the producer's `published_seq`. Drop-oldest dropped the data but the cursor still points into the overwritten region, so the subscriber replays whatever now occupies those slots.
    - Fix: on detecting lag (read-cursor more than `ring_len` behind `published_seq`), set `read_cursor = published_seq - ring_len + 1` (the oldest still-valid slot) and return `Lagged(skipped)`; the NEXT recv then returns the current head. Recovery is O(1), not O(backlog).
    - Cost avoided: a subscriber that never catches up under sustained load — a monotonically-growing latency leak, not a one-time miss.
    - Muscle: lag recovery snaps the cursor to the live window in O(1); never replay the dropped backlog. Reapplies at: W77 aeron Image resync after gap, W85 marketdata subscriber UDP gap recovery.

  - **(EXPERT, perf) When `bench_emit_n4_under_50ns` reports ~250 ns and `engine_throughput_invariant_with_n_subscribers` collapses at N=16 (bar (c) violation):**
    - Symptom: emit cost scales ~50 ns per added subscriber; at N=16 engine throughput drops below 1 M/sec.
    - Why: `tokio::sync::broadcast<Fill>` memcpys ~64 B/receiver (~10 ns × N) and serializes on its internal slot-ring head mutex (~10-50 ns contention); ~250 ns total at N=4.
    - Fix: ship `Arc<Fill>` (one ~30 ns alloc amortized over N, then ~2 ns × N refcount + ~10 ns channel ≈ ~30 ns at N=4). For v1.0 (post-W77 muscle) replace tokio broadcast with the custom per-subscriber SPMC ring (one shared `published_seq` store + N per-subscriber loads, no shared mutex) — fan-out cost decouples from N.
    - Cost avoided: **~10 ns×N memcpy → ~2 ns×N refcount; ~40 ms/sec/shard → ~8 ms/sec at N=4; eliminates the channel's internal mutex and per-receiver allocator visits (bar (c) violation)**.
    - Muscle: fan-out broadcast shares by Arc and avoids a shared mutex on the publish path. Reapplies at: W77 aeron multicast, W85 marketdata UDP multicast, W90 ledger event broadcast.

  - **(EXPERT, perf) When `bench_subscriber_recv_under_burst_100ns` reports ~5 µs p99 during burst (bar (c) violation):**
    - Symptom: recv p99 spikes from ~50 ns steady to ~5 µs during a burst — 100× over budget; `perf` shows cache-misses concentrated on the broadcast channel's slot-ring atomics.
    - Why: even with `Arc<Fill>`, `tokio::sync::broadcast` uses a SHARED slot-ring head. On `Lagged`, naive subscribers immediately re-`recv()`; N subscribers hammering one atomic invalidate each other's cache lines (MESI ping-pong) — the D8 thundering herd.
    - Fix: per-subscriber slot rings (W11 SPSC). The producer stores one shared `published_seq`; each subscriber's recv reads its OWN ring + read-cursor. The only cross-subscriber atomic is `published_seq`, read-only on the subscriber side; cache lines stay subscriber-local; recv p99 ~50 ns regardless of N or burst. On `Lagged`, the subscriber backs off (~1-10 µs exponential) then resyncs against its OWN ring, not a contested atomic.
    - Cost avoided: **~5 µs subscriber p99 → ~50 ns (100× cliff); eliminates the cross-subscriber cache-coherence storm (bar (c) violation)**.
    - Muscle: multi-consumer broadcast over a SHARED atomic gets worse with more subscribers — fan out via per-subscriber dedicated rings for steady latency. Reapplies at: W77 aeron Image (per-subscriber state), W85 marketdata per-subscriber UDP socket.

  - **(EXPERT, perf) When `bench_emit_zero_alloc_steady_state` shows ~1 M Arc allocs/sec:**
    - Symptom: alloc shim flags 1 M `Arc::new`/sec attributable to emit, ~30 ns each, ~30 ms/sec/shard.
    - Why: every `Arc::new(fill)` calls the global allocator — sharing solves copies, not the allocation itself.
    - Fix v0.5: accept it — Arc alloc amortizes over N=4 deliveries (~7.5 ns/delivery); document the trade-off. Fix v1.0: pre-allocated Arc slab (pool of `Arc<MaybeUninit<Fill>>`); emit takes one (~5 ns), inits, broadcasts; on strong-count → 0 return the payload to the pool. Defer the pool to W77/W85.
    - Cost avoided: ~30 ms/sec/shard of allocator time at v1.0; at v0.5 a documented, bounded debt.
    - Muscle: Arc alloc on a hot path is a measured debt — decide v0.5 vs v1.0 and document. Reapplies at: W77 aeron payload slab, W85 marketdata Arc pool, W90 ledger event payload pool.
