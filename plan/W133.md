This is a career/relocation week, not a Build week. There is no crate, no upstream mirror, and no engineered trap-test arc — manufacturing one would be padding. Every item below instead carries an explicit artifact file + an Output line that proves it done, and the two decision/judgement items (Tuesday rig-fate, Friday exit) carry a hardened-acceptance pass criterion and a mental model of why the item exists now. The week's job: leave the current employer clean and well-documented, lock the operations-rig fate so the runtime-hours target survives the move, and arrive at next week's relocation (W134) with a packed, paperwork-complete, zero-loose-ends state. Wednesday/Thursday are deliberately the lightest days of the week — the ramp-down buffer absorbing any spillover from Monday hand-offs or Tuesday logistics.

- [ ] Artifact: `offboarding/handoff.md` (private, in current-employer repo or personal notes). Write the knowledge-transfer doc your successor/team needs: the systems you own, where each lives, the 3-5 non-obvious gotchas only you know (the "load-bearing tribal knowledge"), open threads with owner + next action, and credentials/access to be rotated or transferred. Cross-check against the employer's off-boarding policy for any mandated sections. (~90 min)
  - 🎯 Hardened acceptance: `offboarding/handoff.md` covers every system you own (a teammate could find and operate each from the doc alone), names ≥3 non-obvious gotchas, and lists every open thread with an explicit owner + next-action; zero items tagged `TODO` or `???` remain.
  - *Mental model*: the hand-off doc is the one artifact that converts "graceful departure" from an intention into a verifiable state — it is also the reference your former colleagues will cite when an internal referral comes up later, so its quality is a direct input to the W120 warm-network channel. A clean hand-off is the precondition for W134 arrival: you cannot start the new role with a clear head while fielding "how does X work?" pings.
  - Output: `offboarding/handoff.md` exists meeting the hardened-acceptance criteria; a teammate (or a self-review with fresh eyes) confirms each owned system is operable from the doc alone.

  - Output: `git log -1 --oneline` shows the Monday hand-off commit.

**Tuesday — Operations rig: fate decision (gate for the 4000-hours target)**

- [ ] Artifact: `ops/rig_fate_decision.md` (private). Record the decision among the three options with the gate reasoning written down, not assumed: Option A — ship the rig to destination (capture logistics + cost + customs risk); Option B — keep at home (requires the existing remote-management runbook to be sufficient for unattended operation); Option C — shut down, archive data, restart at destination on cloud VMs (capture archive plan + cloud-cost estimate). Write the chosen option, the one-line reason, and the explicit consequence for the runtime-hours target at the top of the file. (~40 min)
  - 🎯 Hardened acceptance: `ops/rig_fate_decision.md` opens with `Decision: Option <A/B/C> — <one-line reason>` and `Runtime-hours impact: <reachable / at-risk / lost> — <why>`; all three options have their cost/risk captured (so the decision is a comparison, not a default); if Option B, the file links the remote-management runbook section that makes unattended operation safe.
  - *Mental model*: the rig exists to accumulate the 4000+ runtime hours by M36 (bar-(c) substrate evidence) — relocation is the moment that target is most likely to silently die, because a powered-off rig in a packed-up apartment stops counting hours without anyone deciding it should. Writing the decision down (rather than letting the move decide by default) is what keeps the milestone honest. Current lean: Option B (keep at home) — the rig was built for paper-trade; if the new firm uses real production infra, the home rig becomes a personal sandbox, and continuing runtime hours remotely keeps 4000-by-M36 reachable. But the lean is not the decision — the file must show the comparison.
  - Output: `ops/rig_fate_decision.md` exists meeting the hardened-acceptance criteria; the runtime-hours impact line is filled.
- [ ] Commit notes (private). (~10 min)
  - Output: `git log -1 --oneline` shows the Tuesday rig-decision commit.

**Friday — Last day at current employer: exit**

  - Output: `offboarding/exit_log.md` exists meeting the hardened-acceptance criteria; off-boarding checklist fully ticked; `git log -1 --oneline` shows the Friday exit commit.

**Saturday — Pre-relocation prep: execute the checklist**

- [ ] Artifact: tick through `relocation/checklist.md` (the Thursday list) — execute packing tasks and do the final paperwork verification: every document physically present and in-date, every deadline-bound form submitted with lead time, address/account changes scheduled. Mark each item done/blocked; for any blocked item write the unblock action + deadline. (~40 min)
  - 🎯 Hardened acceptance: every item in `relocation/checklist.md` is tagged `[done]` or `[blocked: <unblock action> by <date>]` — no item left untouched; all paperwork in the "must-have for entry" category is `[done]` and verified in-date, with zero blocked items in that category.

  - Output: `relocation/checklist.md` fully tagged with zero untouched and zero must-have-category blocked items; `git log -1 --oneline` shows the Saturday prep commit.
