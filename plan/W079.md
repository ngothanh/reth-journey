- [ ] **Build**: `crates/messaging-aeron/src/subscription.rs` — multi-subscriber fan-out over term buffer. Each
  subscriber has its own position cursor. Slow subscribers don't block fast ones (configurable: lag-tolerant or kicked). (~105 min)
  - **Why**: True multi-subscriber fan-out is the *defining feature* of pub-sub messaging. Aeron achieves it with **a single shared term buffer + N independent position cursors** — no per-subscriber data copies. Slow subscribers either lag (and risk eviction) or block publishers (configurable). Demonstrates Layer-4 pub-sub at HFT performance levels.
  - **Read first**: Aeron `Image.java` (per-subscriber view of a publication), `Subscription.java`, `ImagePoller.java`. LMAX Disruptor "MultipleConsumer" pattern.
  - **Design**:
    ```rust
    pub struct Subscription {
        pub stream_id: i32,
        pub images: Vec<Image>,                          // one per remote publication source
    }
    pub struct Image {
        pub session_id: i32,
        pub position: AtomicI64,                          // this image's read cursor
        pub log_buffer: Arc<LogBuffer>,                    // shared with publication
        pub loss_detector: LossDetector,                   // from W78
    }
    impl Image {
        pub fn poll<F: FnMut(&[u8], FrameInfo)>(&self, fragment_limit: usize, mut handler: F) -> usize {
            let mut consumed = 0;
            while consumed < fragment_limit {
                let pos = self.position.load(Acquire);
                let term_offset = (pos as usize) & (TERM_LEN - 1);
                let term_id = ((pos as usize) / TERM_LEN) as i32;
                let header = self.log_buffer.read_frame_header(term_id, term_offset);
                if header.length <= 0 { break; }     // no more frames yet
                let payload = self.log_buffer.read_payload(term_id, term_offset, header.length as usize);
                handler(payload, FrameInfo { position: pos, ..header.into() });
                self.position.store(pos + align_up(header.length, FRAME_ALIGN) as i64, Release);
                consumed += 1;
            }
            consumed
        }
    }
    pub struct LagPolicy {
        pub max_lag_bytes: i64,                           // beyond which subscriber is kicked
        pub policy: LagAction,
    }
    pub enum LagAction {
        BlockPublisher,                                    // MinStrategy via flow control
        EvictSlow,                                          // remove laggard
    }
    ```
    **Invariants**: (i) Each Image has its own position; reads are read-only against the shared log. (ii) Subscriber poll does NOT free term-buffer slots — only term rotation does. (iii) Position is monotonically non-decreasing. (iv) Multi-subscriber on same Subscription = multiple Images, each independent.
  - **Back-of-envelope**: target 1M msg/s with 4 subscribers, each P99 < 5 µs. Each `Image::poll` is single-threaded per subscriber on a dedicated core (thread-per-core model from runtime v0.5, W57). Per-poll cost: `position.load(Acquire)` ~5 ns + `read_frame_header` (1 cache line) ~5 ns + handler dispatch ~10 ns + `position.store(Release)` ~5 ns = ~25 ns/msg base. memcpy of payload (typical 64-256 B) ~10-30 ns. Total ~50 ns/msg → 20M msg/s theoretical single-image throughput. 4 subscribers × 1M msg/s = 4M msg/s aggregate — well within budget. Each Image's `position: AtomicI64` MUST be on its own cache line (`CachePadded`) so subscribers don't ping-pong each other's positions. Lag detection: subscribing requires reading every other Image's position — N² in worst case, but N is small (typically <16); a tight `for` loop over a 16-element array is L1-resident, ~50 ns total. Status-message broadcast: 1/sec/sub via Aeron StatusMessage = trivial.
  - **Build steps**: 1. (~20 min) Subscription + Image types. 2. (~30 min) `Image::poll` with framing/alignment. 3. (~25 min) Multi-source: one Image per remote session_id; poll round-robins across Images. 4. (~20 min) Lag policy: monitor max_position vs min_position; if diff > max_lag_bytes, evict slowest. 5. (~10 min) Connection to flow_control (W77 Tue): subscriber sends StatusMessage with its position. (~Tests.)
  - **Pitfalls** (named, 3):
    - *Cross-subscriber HOL*: **Symptom**: one slow subscriber blocks publisher (MinStrategy) → other fast subscribers also throttled. **Fix**: configurable per-subscription via LagPolicy. Most HFT deployments choose EvictSlow with monitoring.
    - *Position-cursor regression*: **Symptom**: subscriber's local Image.position somehow regresses (programming bug, replay confusion) → re-reads frames → duplicate delivery. **Fix**: assertion `new_pos > old_pos` on every `store`; panic-on-debug.
    - *Term-boundary frame split*: **Symptom**: poll reads a frame at term-boundary; second half is in next term but reader doesn't roll over. **Fix**: poll detects PAD frame (last frame in term, fills to end) and rolls cursor to next term explicitly. Test with frames straddling boundary.
  - **Expect to hit (perf) #1 — handler closure boxed per poll (bar (c) violation)**: `Image::poll<F: FnMut(&[u8], FrameInfo)>` looks zero-cost, but a caller that writes `image.poll(64, Box::new(move |bytes, info| { ... }))` boxes the closure for each call — ~100 ns malloc + indirect call overhead. Worse, if `F` captures heap state like `Arc<Mutex<HashMap>>`, the closure becomes a fat pointer and every dispatch is L1-cache-cold. Symptom: 1M msg/s bench drops to 200k msg/s when the handler is non-trivial; flame graph shows `__libc_malloc` and `Box::drop` in the inner loop. Fix: pass the closure by reference and use static dispatch via the generic `F: FnMut` — Rust monomorphizes per call site, no allocation. Forbid `Box<dyn FnMut>` on the poll signature; if dynamic dispatch is unavoidable, use a typed enum dispatcher (avoids the box). The Image's caller should be a long-lived task on the runtime, registered ONCE, not creating a fresh closure per poll. Cost avoided: ~100 ns/poll × 1M polls/s = ~100 ms/sec of allocation overhead; eliminates closure-state cache misses. Muscle: hot-path callbacks are static-dispatched generics or typed enums — never `Box<dyn>`. Reapplies at: W79 MBO feed publish handler, W83 runtime reactor task dispatcher, W84 archive replay iterator handler, W92 ledger v1.0 apply callback.
  - **Test scenarios**: (a) 3 subscribers on 1 publication, all fast → each reads independently, no contention. (b) 1 slow + 2 fast, MaxStrategy + EvictSlow → after timeout, slow evicted; fast continue. (c) 1 slow + 2 fast, MinStrategy → all throttled to slow's rate. (d) Term rotation while polling → cursor follows correctly.
  - **Acceptance**: bench: 1M msg/s with 4 subscribers, each P99 < 5 µs. Subscription poll: zero allocations on hot path. Inheritance: term_buffer, flow_control, loss_detector.
  - **Downstream**: W79 matching-engine wires market-data fan-out via subscription.rs — each market-data consumer is one subscriber. W82 Image module is enriched with loss-detector + reorder buffer. Interview: "compare Aeron multi-subscriber to Kafka consumer groups" — Aeron is broadcast (all read all), Kafka is partition-sharded.
- [ ] [NEW v2] **Build**: `crates/matching-engine/src/mbo_feed.rs` — every order event (Add/Cancel/Trade) published to
  messaging-aeron + recorded via mmap-queue. (~3 hrs)
  - **Why**: MBO (Market-By-Order) is the *highest-fidelity market data feed* — every individual order event published. Consumers can reconstruct the full book and any aggregated MBP (Market-By-Price). Coinbase, dYdX, every modern HFT venue ships MBO. Composes matching-engine + messaging-aeron + mmap-queue into one demonstrable Layer-5 surface.
  - **Read first**: Coinbase Pro MBO API doc. CME MDP 3.0 specification (MBO via Tag 269). Databento MBO format. ITCH 5.0 (Nasdaq's MBO protocol).
  - **Design**:
    ```rust
    #[derive(Clone, Debug, serde::Serialize)]
    pub enum MboEvent {
        Add { order_id: OrderId, side: Side, px: Price, qty: u64, ts: SeqTime },
        Cancel { order_id: OrderId, ts: SeqTime },
        Modify { order_id: OrderId, new_qty: u64, ts: SeqTime },  // iceberg refresh, etc.
        Trade { taker: OrderId, maker: OrderId, px: Price, qty: u64, ts: SeqTime },
        Clear { sym: Symbol, reason: ClearReason, ts: SeqTime },  // halt, error reset
    }
    pub struct MboFeed {
        pub publisher: Arc<IpcPublication>,           // or UdpPublication for off-host
        pub archive: Option<ArchiveRecorder>,          // optional mmap-queue recording
        pub seq: AtomicU64,                            // monotonic seq, increments per event
    }
    impl MboFeed {
        pub fn publish(&self, event: MboEvent) -> Result<()> {
            let seq = self.seq.fetch_add(1, AcqRel);
            let envelope = MboEnvelope { seq, event };
            let bytes = bincode::serialize(&envelope)?;
            self.publisher.offer(&bytes)?;
            if let Some(arc) = &self.archive {
                arc.record_fragment(&bytes, seq as i64)?;
            }
            Ok(())
        }
    }
    // Engine integration
    impl Engine {
        fn after_match(&mut self, taker: OrderId, fills: &[Fill]) {
            for f in fills {
                self.mbo.publish(MboEvent::Trade { taker, maker: f.maker, px: f.px, qty: f.qty, ts: self.clock.now() });
                if f.maker_remaining == 0 {
                    /* maker fully filled — implicit cancel emitted? venue choice */
                }
            }
        }
    }
    ```
    **Invariants**: (i) Every order-book mutation has a corresponding MBO event published, in the order it occurred. (ii) `seq` is monotonic across all events. (iii) MBO consumers reconstruct an order book bit-identical to engine's internal book (modulo presentation). (iv) Iceberg events publish ONLY visible portions — Add(display_qty), Modify(refresh_display_qty), never hidden total. (v) Under raft replication, MBO publish is part of the deterministic apply; every replica publishes identical event stream.
  - **Back-of-envelope**: target 1M MBO events/s, P99 publish <1 µs. Per-event cost: `seq.fetch_add` ~10 ns + serialize via `bincode::serialize_into` direct-to-aeron-slot ~50 ns + aeron `offer()` ~100 ns + optional `archive.record_fragment` ~200 ns (mmap-queue append). Total ~360 ns/event on the fast path, ~600 ns with archive — well under 1 µs budget. At 1M events/sec, archive writes 200 MB/s sustained — bandwidth-bound on cheap SSD (500 MB/s) is fine; on NVMe (3 GB/s) trivial. Archive write is on the SAME thread as publish (no async hop) to preserve the seq-ordering invariant; if write becomes a bottleneck, batch flush every N events into the underlying mmap-queue Cycle (W83). Memory: each MBO event is ~64 B serialized; at 1M evt/s × 60 s = 4 GB/min of stream — Archive rotation cycle of 1 hr per file = 240 GB/hr/symbol — disk planning requirement, documented as ops note. Note: at-least-once semantics during replay (replica restart) means consumer dedup by `seq` is non-negotiable.
  - **Build steps**: 1. (~25 min) MboEvent enum + envelope. 2. (~30 min) MboFeed::publish hot path (zero-alloc). 3. (~40 min) Engine integration hooks: after_match, on_add, on_cancel, on_iceberg_refresh, on_stop_trigger, on_auction_uncross. 4. (~30 min) Sequencing across event types — define canonical ordering (e.g., Cancel-due-to-trade FOLLOWS Trade event). 5. (~30 min) Iceberg interaction: visible Add/Modify only (cite W76 invariant). 6. (~25 min) Tests.
  - **Pitfalls** (named, 4):
    - *Event ordering under recovery*: **Symptom**: replica restarts mid-apply, replays from wal — emits MBO again for events already published. Consumers see duplicates. **Fix**: MBO publish is part of state-machine `apply`, after wal-durable, before "replied to client" — at-least-once but consumers must dedupe via `seq`. Alternative: track `mbo_published_seq` per replica in metadata; skip on replay. Document chosen semantics.
    - *MBO vs MBP equivalence*: **Symptom**: consumer aggregates MBO into MBP, but iceberg refresh events leak hidden inventory → MBP shows phantom depth. **Fix**: refresh emits `Cancel(old_visible)` + `Add(new_visible)` not `Modify(total)`. Property test: MBO replay → MBP aggregate equals engine's MBP snapshot.
    - *Restart resync*: **Symptom**: late-joining consumer needs snapshot of current book — pure MBO stream from genesis is infeasible. **Fix**: periodic Snapshot events on the MBO stream (every N seconds or every term rotation); consumer subscribes from a Snapshot then plays forward. Aeron Archive's ReplayMerge pattern.
    - *Determinism across replicas*: **Symptom**: replicas publish events in slightly different orders → consumer reads different sequences from different replicas under failover. **Fix**: events are tagged with `seq` and `op_num`; consumer dedupes by `seq`. Replicas using same engine deterministically emit same sequence.
  - **Expect to hit (perf) #1 — `bincode::serialize` allocates Vec per event (bar (c) violation)**: as written, `let bytes = bincode::serialize(&envelope)?;` allocates a fresh `Vec<u8>` for every event — ~150 ns malloc + 80 ns serialize + 30 ns drop = ~260 ns/event of allocator overhead. At 1M evt/s, ~260 ms/sec of pure malloc; jemalloc arena contention saturates above ~500k allocs/sec/thread. Worse: each Vec lives <1 µs (offer copies it into the term buffer), so it's pure churn. Symptom: heaptrack flags MBO publish at 1M allocs/sec; bench shows 400k evt/s instead of 1M target. Fix: call aeron's `try_claim(size)` to get an `&mut [u8]` slot in the term buffer, then `bincode::serialize_into(&mut slot, &envelope)?` — serializes directly into the destination, zero allocations. For fixed-shape events (Add/Cancel/Trade), use a `repr(C)` struct and `ptr::write` for ~30 ns serialize (skips bincode's variant-encoding overhead). Cost avoided: ~260 ns × 1M evt/s = ~260 ms/sec of allocation; eliminates allocator contention. Muscle: ALWAYS serialize-into a pre-claimed slot, never `serialize` then `offer(&bytes)`. This is the W77 transport_ipc pitfall re-stated for the MBO emit layer — the principle applies at every layer of a bar-(c) emit chain. Reapplies at: W80 ledger journal record, W83 archive frame write, W84 archive replay slot reads, W92 ledger v1.0 apply-result emit.
  - **Expect to hit (perf) #2 — archive write blocks MBO publish (bar (c) violation)**: serial path `publisher.offer(&bytes)?; archive.record_fragment(&bytes, seq)?;` means archive's mmap-queue append (~200 ns including potential page-fault) is in the critical path; if a page fault hits (every 1 MiB of stream = once per ~15k events at 64 B/event), latency spikes to ~3 µs — 3× over P99 budget. Worse: if the archive Cycle is rotating (W83 rotation atomic rename + symlink swap), the publisher pauses. Symptom: P99.9 publish latency shows 1-3 µs spikes correlated with archive page faults; rotation events visible as 50 µs blackouts. Fix: (a) archive recording lives on a SEPARATE thread (the pretoucher-paired worker from W77); publisher's offer() writes to a small SPSC ring; archive thread drains the ring asynchronously. (b) pretoucher (W77) keeps archive pages warm so page-fault tail vanishes. (c) Cycle rotation is signaled to publisher via flag, publisher continues writing into mmap during rotation (rotation completes async). Cost avoided: 1-3 µs P99.9 spikes eliminated; rotation no longer pauses publish; pretoucher saves ~3 µs/15k events of page-fault tail. Muscle: durability is ASYNCHRONOUS to publish — the publisher's job is to emit to the in-memory ring; durability workers consume the ring on their own thread. This is W77 Mon's pretouch principle taken end-to-end. Reapplies at: W83 archive recorder design (the ring is the publisher's only synchronous obligation), W92 ledger v1.0 io_uring (submission ring is the publisher's only synchronous obligation, completions arrive async).
  - **Test scenarios** (Tue): (a) 100k orders → MBO stream has 100k events in correct order. (b) Iceberg 1000-lot/100-display → 11 Add(100)+10 Cancel(0)+10 Add(100) pattern (visible only). (c) Cancel mid-trade → events Trade then Cancel sequenced correctly. (d) Stop trigger → Cancel(stop_id) + Add(new_market_id) + Trade events. (e) Auction uncross → batch Trade events at clearing_px. (f) Property: replay MBO → reconstruct order book matches engine's snapshot.
  - **Acceptance**: bench: publish 1M MBO events/s, P99 < 1 µs publish. MBO→book reconstruction 1:1 invariant in 1k random scenarios. Inheritance: messaging-aeron (Publication), mmap-queue (ArchiveRecorder), bufpool.
  - **Downstream**: W82 v1.5 SHIP audit confirms MBO in inheritance. W80 FIX 4.4 (Mon-Tue) uses MBO as the source of ExecutionReports (35=8) per session. Tier-A interview: "design a market-data feed" → MBO this exact way + MBP aggregation downstream.

- [ ] [HFT] **Build**: matching-engine market-data fan-out now goes via `messaging-aeron::Publication`. Subscribers
  receive L2 deltas over IPC for in-process clients, UDP unicast for out-of-process. (~150 min)
  - **Why**: This is the *seam* where Layer-5 matching-engine meets Layer-4 messaging-aeron — replacing the placeholder in-process channel with the real messaging substrate. Demonstrates end-to-end composition. Same MBO events flow via IPC to in-process risk engines (<1 µs) AND UDP unicast to off-host strategy boxes (<50 µs LAN).
  - **Read first**: own MboFeed (Mon), IpcPublication (W77 Fri), UdpTransport (W78 Tue). Coinbase WebSocket-vs-FIX docs for "two-channel fan-out" framing.
  - **Design**:
    ```rust
    pub struct MarketDataFanout {
        pub ipc_pubs: AHashMap<Symbol, Arc<IpcPublication>>,        // in-process subs
        pub udp_pubs: AHashMap<Symbol, Arc<UdpPublication>>,         // out-of-process subs
    }
    impl Engine {
        pub fn emit(&self, event: MboEvent) -> Result<()> {
            let bytes = bincode::serialize(&event)?;
            if let Some(ipc) = self.fanout.ipc_pubs.get(&event.symbol()) {
                ipc.offer(&bytes)?;       // <1 µs
            }
            if let Some(udp) = self.fanout.udp_pubs.get(&event.symbol()) {
                udp.offer(&bytes)?;       // <50 µs LAN
            }
            Ok(())
        }
    }
    ```
    **Invariants**: (i) Same MboEvent payload sent over both transports — consumers can pick. (ii) IPC and UDP publications share the same session_id+stream_id pattern (consumer transport-agnostic). (iii) Per-symbol publications avoid head-of-line blocking across symbols.
  - **Back-of-envelope**: target 100k events/s sustained with 10 IPC + 10 UDP subs, P99 IPC <2 µs, P99 UDP loopback <10 µs. IPC path = ~360 ns/event (W79 Mon MBO budget) + ~100 ns per IPC publication lookup in AHashMap (~50 ns hash + ~50 ns lookup) = ~460 ns. UDP path = serialize once + sendmmsg batched = ~500 ns/event + ~100 ns lookup ≈ 600 ns. At 100k evt/s × 20 subs (max replication factor at this stage) = 2M ops/s aggregate; budget allows 500 ns/op so ~1 ms/sec headroom. The KEY architectural choice: per-symbol publications avoid HOL — if BTC stalls a subscriber, ETH publication continues independently. Memory: 1 publication per symbol × ~100 symbols × ~64 MiB term buffer × 3 terms = 19 GB RAM upper bound — hugepage-backed shm is mandatory at this scale.
  - **Build steps**: 1. (~30 min) MarketDataFanout struct + per-symbol publication registry. 2. (~40 min) Hook into Engine.apply path — every MBO event flows here. 3. (~35 min) Wire raft-replicated apply: each replica emits to its OWN fanout (separate session_id) — consumers identify primary via consensus metadata. 4. (~25 min) Subscriber accept handshake: client sends subscribe(symbol), driver maps to publication. 5. (~20 min) Bench: round-trip latency IPC vs UDP loopback vs UDP LAN.
  - **Pitfalls** (named, 3):
    - *Cross-symbol HOL*: **Symptom**: BTC symbol's term buffer fills (slow subscriber), blocks ETH symbol's publish too if shared publication. **Fix**: separate Publication per symbol (or per-symbol-group). Bench memory usage with 100 symbols.
    - *Replica fanout duplication*: **Symptom**: in raft setup, all 3 replicas publish MBO → consumers see 3x events. **Fix**: only leader publishes externally (UDP/IPC fanout). Backups generate same MBO internally for state but don't ship to wire. On view-change, new leader resumes fanout from last-published-seq (carried in raft metadata).
    - *Subscriber overhead*: **Symptom**: 1000 subscribers each subscribe to same symbol via UDP unicast → 1000x bandwidth. **Fix**: when N > threshold (e.g., 10), switch symbol to multicast (W80 work). For v1.5 SHIP, multicast is W80; ship unicast first.
  - **Expect to hit (perf) #1 — `AHashMap::get(&symbol)` per event is the bottleneck (bar (c) violation)**: each MBO event calls `self.fanout.ipc_pubs.get(&event.symbol())` AND `self.fanout.udp_pubs.get(&event.symbol())` — two hashmap lookups × ~50-100 ns = ~150 ns per event. Worse, the hashmap layout depends on insertion order, so two adjacent symbols on the wire may hit different cache lines (~7 ns L2 fetch each). At 1M evt/s, ~150 ms/sec of pure lookup overhead — and the symbol is usually the SAME symbol several events in a row (event batches from a single match). Symptom: bench shows lookup time dominating per-event latency; cache misses on the hashmap nodes visible in `perf c2c`. Fix: index publications by an interned `SymbolId: u16` (perfect-hash from symbol name at registration time), stored in a `[Option<Arc<IpcPublication>>; MAX_SYMBOLS]` — direct array index, ~1 ns load. Caller passes `event.symbol_id` (already cached on the Order/Match path from earlier weeks), not `event.symbol_string`. The W74 matching-engine already has symbol→shard sharding via this interning; reuse the symbol table here. Cost avoided: ~150 ns/event × 1M evt/s = ~150 ms/sec; eliminates cache-cold map node access. Muscle: small fixed key spaces should be array-indexed, not hashmap-indexed — hashmaps are for unbounded key spaces, arrays for bounded enumerable ones (W76 SymbolId, W80 LedgerId). Reapplies at: W80 ledger account index by AccountId, W81 circuit breaker per-symbol state, W82 v1.5 SHIP audit (asserts no AHashMap in per-event path), W84 archive replay symbol filter.
  - **Test scenarios**: (a) In-process subscriber + 1 out-of-process via UDP loopback → both receive same event stream. (b) 10 UDP subscribers → all converge. (c) Failover: leader killed; new leader resumes fanout from last seq; subscribers see no gap (raft state-transfer + MBO catch-up via Archive). (d) Bench: emit + IPC delivery P99 < 2 µs end-to-end.
  - **Acceptance**: 100k events/s sustained with 10 IPC subs + 10 UDP subs, P99 IPC < 2 µs, P99 UDP loopback < 10 µs. Inheritance: matching-engine consumes messaging-aeron, bufpool, time. Layer composition demonstrable.
  - **Downstream**: W80 adds multicast publisher → enables N>>10 subscribers efficiently. W82 v1.5 SHIP audit captures this seam in the inheritance ratio. Tier-A interview: "explain your matching engine's fan-out architecture from order match to off-host strategy" — this is the answer.
