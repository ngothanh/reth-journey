On reserve (a new account's position/margin state lands on this shard), if `current + reserve_size > budget`, apply a policy (BackpressureRetry: reject + signal upstream so the account routes to a colder shard / triggers rebalance; or FlushNow: spill cold account state to the position SST and retry). (~150 min across 3 phases)
  - 🔧 **Why this matters**: this is the **convergence-cell substrate** (§3 row 9). The v1.0 capacity target is **~100k accounts / 2 instruments / ~1M orders/s** (§4A); at that scale `risk-engine` recomputes margin **per mark tick across all accounts**, sharded by account on `runtime-thread-per-core`. The §4A back-of-envelope: 100k accounts × 10 ticks/s = 1M recomputes/s → with 16 account-shards = ~62.5k/s/shard ≈ 62ms/s/shard (comfortable for *incremental* margin) — **but only if each shard's hot account/position state stays in its own heap and never OOMs the process.** Thread-per-core gives each shard its own heap but ONE shared OS address space: a single account-shard's margin/position memtable growing unbounded OOM-kills *all* shards, taking the whole replica down (and under VSR that's a node loss, W103). The four traps: (1) **flush-and-retry write-amplification cascade** — FlushNow spilling cold accounts under a position-churn burst triggers compaction that itself eats memory and thrashes; (2) **cross-shard budget false-sharing / shared atomic counter** — a single shared `AtomicU64` total re-introduces the cross-core contention the account-shard model exists to kill (and `risk-engine` is bar (c) — this defeats the per-mark-tick budget); (3) **integer-overflow / off-by-one at the budget boundary** — `current + reserve_size` can wrap or admit the one account that tips OOM; (4) **the budget that never fires** — a too-loose check a naive test passes without exercising backpressure. Downstream: **W97** (module moves into the scaffolded crate), **W98** (the **incremental-margin** delta path + local-applied-state reads interact with the budget trigger), **W99** (v1.0 + zero-alloc audit + `latency-lab` p99.99), **W103+** (account-shard store under 3-node VSR). State plainly: a first-attempt impl will fail ≥1 Phase-2 test below, and the debug session is the lesson.

  #### Phase 1 — Problem, prediction, design (~35 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/risk-engine/notes/95sat_budget_prediction.md`:
    - P1: which primitive will you reach for to track per-account-shard footprint? (exact import line — e.g. `use std::sync::atomic::AtomicU64;` vs a plain `u64` field on the `!Send` account-shard).
    - P2: predict the cost of one budget check on the **per-mark-tick reserve path**, in ns (target: effectively free — single load + compare + predictable branch — because at 1M recomputes/s any non-trivial cost blows the §4A budget).
    - P3: predict the concurrent outcome if two account-shards each tick a *shared* total counter on every reserve (what does MESI do to that line? — and why is this fatal specifically for `risk-engine` at 100k accounts?).
    - P4: derive-correctness — what does `current + reserve_size` do at `u64::MAX - 8` with an 8KB account state? (overflow prediction).
    - P5: **list every Phase-2 test you predict your first attempt will fail.** Compare to reality after the tests run.
  - *Mental model*: a per-account-shard memory budget is a *local admission controller* — each account-shard owns its account/position/margin byte-count and decides, with **no cross-shard coordination**, whether to admit a new account's state, backpressure (route it to a colder shard / trigger rebalance), or spill cold accounts to SST. It exists because thread-per-core gives each account-shard its own heap but one shared OS address space: a single runaway shard OOM-kills all of them — and under VSR (W103) that's a node loss the cluster must tolerate, so keeping it from happening is cheaper than recovering from it.
  - *Contract* (write the signatures, never the bodies):
    ```rust
    pub enum BudgetPolicy { BackpressureRetry, FlushNow }       // BackpressureRetry default
    pub enum Admission { Admitted, Backpressure, Flushed }      // returned by try_reserve
    pub struct AccountShardBudget {
        budget_bytes: u64,        // max(1.5GiB, 7% of total) by default
        used_bytes: u64,          // PLAIN field — owned by the single account-shard writer, NOT shared
        policy: BudgetPolicy,
    }
    impl AccountShardBudget {
        pub fn with_default_for_host(total_bytes: u64, shards: u32) -> Self; // max(1.5GiB, 7%)
        pub fn try_reserve(&mut self, reserve_size: u64) -> Admission;       // per-account-state admit (hot path)
        pub fn release(&mut self, freed: u64);                               // on spill/close
        pub fn used(&self) -> u64;
    }
    ```
  - *Back-of-envelope*: the reserve check must vanish into the per-mark-tick recompute cost. Single-writer `used_bytes` lives in L1 of the owning core → load 0.5ns + add + compare + **predictable** branch (~1ns total, no mispredict in steady state). Contrast: a *shared* `AtomicU64` total ticked by 16 account-shards → the line ping-pongs (MESI invalidate ~40–100ns *per* contended tick) — a **40–100× cliff** on a path that should be ~1ns, and at 1M recomputes/s (§4A) that cliff alone is the difference between meeting and missing the p99.99 budget `latency-lab` reports at W99. Budget math: 16 shards × `max(1.5GiB, 7% of 16GiB=1.12GiB)` = 16 × 1.5GiB = 24GiB reserved on a 16GiB host → **the default over-commits**; on small hosts the `7%` arm wins, on large hosts the `1.5GiB` floor wins — the `max` is doing real work and the test must hit both arms.
  - **Requirements** R1..R7 — write in `crates/risk-engine/notes/95sat_budget_design.md`:
    - R1: default budget = `max(1.5 * 2^30, total_bytes * 7 / 100)` per account-shard, integer math (no `0.07_f64`).
    - R2: `try_reserve` is single-writer — `used_bytes` is a plain field, never an atomic shared across account-shards (single-writer principle; bar (c) for the convergence cell).
    - R3: on `current + reserve_size > budget`: `BackpressureRetry` → return `Backpressure`, do NOT mutate `used_bytes` (caller routes the account to a colder shard / triggers rebalance); `FlushNow` → caller spills cold account state to SST, then `release()`, then retry.
    - R4: `try_reserve` never overflows: checked/saturating add at the boundary so `u64::MAX`-class inputs reject rather than wrap.
    - R5: a single account whose state is larger than the whole budget is rejected deterministically (not infinite-flush-loop).
    - R6: `used()` after a sequence of reserves/releases equals the exact net reserved bytes (conservation).
    - R7: budget enforcement holds under sustained load — no account-shard's `used()` ever exceeds `budget_bytes` (the safety invariant the bench asserts; under VSR this prevents a node-killing OOM).
  - **Design walk-through** D1..D5 — answer in the design doc; no peeking at Seastar source until Phase 3:
    - D1: property table for the footprint counter — {plain `u64` on `!Send` account-shard | `AtomicU64` shared | `AtomicU64` per-shard CachePadded}: columns Sync? / per-mark-tick reserve ns / cross-core traffic / fits single-writer principle / survives 100k-account scale. (Answer: plain field wins — single writer, and it's the only option that holds the §4A budget.)
    - D2: enumerate the over-budget policies and when each is legal (BackpressureRetry default — there's an upstream router that can place the account elsewhere; FlushNow only when there's no upstream to signal, e.g. a VSR-log replay path rehydrating account state that MUST make progress, W103).
    - D3: **Pre-mortem (load-bearing)** — write the EXACT bad interleaving for FlushNow under a position-churn burst:
      ```
      t0 account-shard near budget; mark tick → burst of position updates across many accounts
      t1 try_reserve over budget → FlushNow → spill coldest accounts → new position SST
      t2 SST count crosses compaction trigger → compaction starts, allocates input/output buffers
      t3 burst continues; reserve over budget again → FlushNow again → more SSTs
      t4 compaction memory + freshly-rehydrated hot accounts both grow → RSS climbs DESPITE spilling → OOM (thrash) → under VSR this is a NODE LOSS the cluster must now tolerate
      ```
      If you can't write this trace, you can't prove BackpressureRetry-as-default (route to a colder shard) prevents it.
    - D4: **Anti-shortcut audit** — name the obvious reach and why it's wrong HERE:
      - "Use one shared `AtomicU64` for the whole venue store's memory" → wrong: re-introduces cross-shard contention the account-shard model exists to kill, and at 1M recomputes/s it's the dominant cost (single-writer principle).
      - "Use `f64` for the 7% math" → wrong: float div on the config path is fine, but rounding makes the budget non-reproducible across hosts and the boundary test flaky; integer `*7/100`. (And `risk-engine` bans `f64` in the apply/recompute path anyway — cross-arch determinism under VSR, §3 row 21.)
      - "Just `current + reserve_size > budget`" → wrong: wraps at `u64::MAX`, admitting the OOM account (R4).
    - D5: integer-overflow boundary — pick checked vs saturating add and justify (saturating: `u64::MAX`-class input saturates above budget → rejected, no panic, no wrap).
  - **Output**: `crates/risk-engine/notes/95sat_budget_design.md` with R1..R7, D1..D5, and the D3 bad-interleaving sketch.

  fn default_budget_uses_max_of_floor_and_percent() {
      // small host: 8 GiB → 7% = 0.56 GiB < 1.5 GiB floor → floor wins
      let small = AccountShardBudget::with_default_for_host(8 << 30, 1);
      assert_eq!(small.budget_bytes, 1_536u64 << 20, "expected 1.5GiB floor (1,610,612,736 bytes)");
      // big host: 100 GiB → 7% = 7 GiB > 1.5 GiB floor → percent wins
      let big = AccountShardBudget::with_default_for_host(100 << 30, 1);
      assert_eq!(big.budget_bytes, (100u64 << 30) * 7 / 100, "percent arm not applied on big host");
  }

  // (SENIOR) NEGATIVE-CONTROL / boundary: the check must FIRE, and conservation must hold.
  // A too-loose `>=` vs `>` or a forgotten release breaks this. Proves the budget is actually enforced.
  #[test]
  fn try_reserve_enforces_and_conserves() {
      let mut b = AccountShardBudget { budget_bytes: 1000, used_bytes: 0, policy: BudgetPolicy::BackpressureRetry };
      assert_eq!(b.try_reserve(600), Admission::Admitted);
      assert_eq!(b.used(), 600);
      assert_eq!(b.try_reserve(600), Admission::Backpressure, "second 600 over 1000 budget must backpressure (route to colder shard)");
      assert_eq!(b.used(), 600, "backpressured account must NOT mutate used_bytes");
      b.release(600);
      assert_eq!(b.used(), 0, "conservation: release must restore exact bytes");
      assert_eq!(b.try_reserve(600), Admission::Admitted, "after release the same account now fits");
  }

  // (SENIOR) OVERFLOW boundary: `current + reserve_size` near u64::MAX must REJECT, not wrap-admit.
  #[test]
  fn try_reserve_does_not_overflow_admit() {
      let mut b = AccountShardBudget { budget_bytes: 1_000_000, used_bytes: u64::MAX - 8, policy: BudgetPolicy::BackpressureRetry };
      // naive `used + reserve > budget` wraps to a tiny value < budget → wrongly Admitted (the OOM account).
      assert_eq!(b.try_reserve(64), Admission::Backpressure,
          "wrapping add admitted an over-budget account — OOM bug (node loss under VSR)");
      assert_eq!(b.used(), u64::MAX - 8, "rejected account must not mutate used");
  }

  // (SENIOR) FlushNow must not infinite-loop on an account whose state is bigger than the whole budget.
  #[test]
  fn oversized_account_is_rejected_not_flush_looped() {
      let mut b = AccountShardBudget { budget_bytes: 1000, used_bytes: 0, policy: BudgetPolicy::FlushNow };
      // 2000 > 1000 even on an empty shard: spilling frees nothing useful → must reject, not loop.
      assert_eq!(b.try_reserve(2000), Admission::Backpressure,
          "account larger than the whole shard budget must be rejected deterministically");
  }

  // (EXPERT) CROSS-PRIMITIVE trap: compose with the account-shard substrate (runtime-thread-per-core).
  // Each account-shard owns its OWN AccountShardBudget (single writer). This test fails if you "simplify"
  // to one shared atomic total — the type then must be Send+Sync AND the safety invariant leaks across shards.
  #[test]
  fn per_shard_account_budgets_are_independent_single_writer() {
      // 16 independent account-shard budgets; saturating ONE shard must not change another's `used`.
      let mut shards: Vec<AccountShardBudget> = (0..16)
          .map(|_| AccountShardBudget { budget_bytes: 1000, used_bytes: 0, policy: BudgetPolicy::BackpressureRetry })
          .collect();
      // hammer account-shard 0 to its budget
      for _ in 0..10 { let _ = shards[0].try_reserve(100); }
      assert_eq!(shards[0].used(), 1000, "account-shard 0 should be full");
      assert_eq!(shards[5].used(), 0, "account-shard 5 must be UNAFFECTED — no cross-shard coupling");
      // NOTE: a Vec of per-shard AtomicU64 budgets would ALSO compile and pass these independence
      // asserts — so this test alone does not forbid atomics. The anti-shared-atomic guarantee is
      // enforced by the bench below (size_of ≤ 32 + the ops/s band at 100k-account scale); the SINGLE
      // shared-atomic-total variant is what fails there (MESI bounce drops the per-mark-tick rate).
      // Keep used_bytes a plain field owned by the !Send account-shard writer (single-writer principle).
  }

  // (EXPERT) NEGATIVE-CONTROL bench: the budget check must be ~free on the per-mark-tick reserve path AND
  // the bench must actually measure reserves (layout assertion so it fails fast if it measured nothing).
  // criterion bench in benches/account_budget.rs:
  //   assert!(std::mem::size_of::<AccountShardBudget>() <= 32, "budget bloated — would not stay hot in L1");

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)
  Ordered failure cards, newbie first, expert last — the ladder you actually walk.

  - **(NEWBIE) When `default_budget_uses_max_of_floor_and_percent` reports the small-host budget = 0.56GiB:**
    - Symptom: assertion fails — you returned `total * 7 / 100` and forgot the floor.
    - Why: Seastar's rule is `max(1.5GiB, 7%)`; the 7% arm only wins on large hosts. On an 8GiB box 7% is below the floor.
    - Fix: `budget_bytes = core::cmp::max(1_610_612_736, total_bytes * 7 / 100)` (1.5GiB = `1536 << 20`).
    - Cost avoided: on a small dev box every account-shard gets a starvation-sized memtable → constant spilling → write-amp → the per-mark-tick recompute reads cold-from-SST account state → blows the §4A latency budget. Functional bug, not just slow.
    - Muscle: when a spec says `max(floor, ratio)`, both arms are load-bearing — test the regime where each wins. Reapplies at: W98 incremental-margin watermark thresholds, W99 risk-engine sizing config, W103 capstone account-shard sizing under VSR.

  - **(SENIOR) When `try_reserve_enforces_and_conserves` reports `used() == 1200` after a backpressure:**
    - Symptom: a backpressured account still incremented `used_bytes`.
    - Why: you mutated `used_bytes` *before* the over-budget check, or used `>=`/`>` inconsistently, so the rejected account leaked into the counter.
    - Fix: compute `would_use` first, branch, and only commit `used_bytes = would_use` on the Admitted arm.
    - Cost avoided: a leaking counter drifts upward forever → false backpressure on a half-empty account-shard → accounts wrongly routed away / rebalance churn with no OOM to explain it.
    - Muscle: an admission counter must be mutated only on the admit arm — check-then-commit, never commit-then-check. Reapplies at: W11 backpressure semaphore, W98 incremental-margin write-set sizing, W74 matching-engine order-count limits.

  - **(SENIOR) When `try_reserve_does_not_overflow_admit` reports `Admitted`:**
    - Symptom: a 64-byte account state at `used = u64::MAX-8` was admitted.
    - Why: `used + reserve > budget` wrapped past `u64::MAX` to a tiny value that compared below budget — the classic integer-overflow admit, which here admits the exact account that OOMs the shard.
    - Fix: `used_bytes.checked_add(reserve).map_or(true, |t| t > budget_bytes)` (or `saturating_add`) so overflow → reject.
    - Cost avoided: silent OOM-kill of the whole thread-per-core process (every account-shard dies) — under VSR (W103) that's a node loss the cluster must now recover from. 0 cycles to add a `checked_add`; catastrophic if omitted.
    - Muscle: any `a + b > limit` on a budget/counter is an overflow trap — use checked/saturating add. Reapplies at: W34 bloom bit-index math, W42 txn id space, W85 runtime-thread-per-core queue depth caps, W103 VSR op-number budget.

  - **(SENIOR) When `oversized_account_is_rejected_not_flush_looped` hangs / loops:**
    - Symptom: FlushNow spills, frees ~0 useful (the account itself is the giant), retries, spills again — infinite loop on an account bigger than the whole budget.
    - Why: FlushNow assumes spilling always frees enough to fit the new account; an account larger than the whole budget never fits.
    - Fix: before spilling, if `reserve_size > budget_bytes` reject immediately (`Backpressure`); only spill when freeing cold accounts could plausibly admit.
    - Cost avoided: a hung account-shard wedges its core forever (thread-per-core = those accounts' margin stops recomputing → liquidations miss → §4A correctness failure). Liveness bug.
    - Muscle: a spill-to-make-room loop needs a progress guard — if even an empty target can't fit, reject. Reapplies at: W98 incremental-margin buffer admission, W103 VSR-replay rehydration sizing.

  - **(EXPERT, perf) When `per_shard_account_budgets_are_independent_single_writer` forces `AccountShardBudget: Sync` / shard 5 changes:**
    - Symptom: you "simplified" to one shared `AtomicU64` total; now the type must be `Send + Sync`, and the bench rate drops below 1e7 ops/s under 16-thread contention.
    - Why: a shared atomic ticked by every account-shard on every reserve ping-pongs one cache line across all 16 cores — MESI invalidate-on-write serializes the per-mark-tick hot path.
    - Fix: keep `used_bytes` a **plain `u64` field** owned by the single account-shard writer (the `!Send` shard task from `runtime-thread-per-core`). Per-account-shard budgets are independent by construction — no shared atomic, no cross-shard coupling.
    - Cost avoided: 40–100ns MESI bounce *per reserve* × 16 cores vs ~1ns single-writer L1 access — a 40–100× hot-path regression on the convergence cell at 1M recomputes/s, which is exactly the §4A budget `latency-lab` checks at W99. This defeats the `runtime-thread-per-core` substrate `risk-engine` is built on.
    - Muscle: per-account-shard state is single-writer — never reach for a shared atomic to track per-shard footprint; the absence of the atomic IS the optimization. Reapplies at: W85 runtime-thread-per-core per-shard counters, W74 matching-engine per-symbol book, W98 per-account-shard incremental-margin accumulator, W103 capstone account-shard control block.

  - **(EXPERT, perf) When the criterion bench in `benches/account_budget.rs` reports a rate below 1e8 ops/s or `size_of::<AccountShardBudget>() > 32`:**
    - Symptom: bench rate too low, or the struct grew (e.g. you boxed the policy, or added a `Mutex`).
    - Why: a `Box<dyn Policy>` or a `Mutex<u64>` on `used_bytes` adds a pointer-chase / lock acquire (~25ns) to a path that should be a load+compare; struct bloat spills it out of one cache line.
    - Fix: `policy` as a plain `enum` (1 byte, branch-predicted), `used_bytes` a plain field; keep `AccountShardBudget` ≤ 32 bytes so the whole budget fits in half a cache line and stays hot.
    - Cost avoided: ~25ns lock vs ~1ns check on every reserve → a 25× tax on a path hit 1M times/s; struct spill adds an L1 miss (7ns) per check.
    - Muscle: the hot-path admission struct must fit in a cache line and use no locks/heap — measure `size_of` in the bench as a layout guard. Reapplies at: W74 order struct, W85 shard task control block, W98 incremental-margin accumulator.
