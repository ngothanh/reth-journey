(~150 min across 3 phases)
  - 🔧 **Why this matters**: mirrors Seastar's documented per-shard memory reservation — the discipline that lets ScyllaDB run thread-per-core with no cross-shard heap sharing. mini-db inherits per-shard memtables from `runtime-thread-per-core` v1.0 (W84); *without* an explicit budget a hot shard's memtable grows unbounded → OOM, killing the whole process (one heap per shard, but one address space). The four traps: (1) **flush-and-retry write-amplification cascade** — FlushNow under a write burst triggers compaction churn that itself eats memory and thrashes; (2) **cross-shard budget false-sharing / shared atomic counter** — composing the budget with the shard substrate, a single shared `AtomicU64` total re-introduces cross-core contention the per-shard model exists to avoid; (3) **integer-overflow / off-by-one at the budget boundary** — `current + insert_size` can wrap or admit the one insert that tips OOM; (4) **the budget that never fires** — a too-loose check that a naive test passes without ever exercising backpressure. Downstream consumers: **W97** (module moves into the scaffolded crate), **W98** (memtable flush + GC interact with the budget trigger), **W99** (per-shard sharding stub), **W100** (v1.0 SHIP + inheritance-ratio audit). State plainly: a first-attempt impl will fail ≥1 Phase-2 test below, and the debug session is the lesson.

  #### Phase 1 — Problem, prediction, design (~35 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/mini-db/notes/95sat_budget_prediction.md`:
    - P1: which primitive will you reach for to track per-shard footprint? (exact import line — e.g. `use std::sync::atomic::AtomicU64;` vs a plain `u64` field on the `!Send` shard).
    - P2: predict the cost of one budget check on the insert hot path, in ns (target: it must be effectively free — a single load + compare + predictable branch).
    - P3: predict the concurrent outcome if two cores each tick a *shared* total counter on every insert (what does MESI do to that line?).
    - P4: derive-correctness — what does `current + insert_size` do at `u64::MAX - 8` with an 8KB insert? (overflow prediction).
    - P5: **list every Phase-2 test you predict your first attempt will fail.** Compare to reality after the tests run.
  - *Mental model*: a per-shard memory budget is a *local admission controller* — each shard owns its memtable byte-count and decides, with no cross-shard coordination, whether to admit an insert, backpressure, or flush. It exists because thread-per-core gives each shard its own heap but one shared OS address space: a single runaway shard OOM-kills all of them.
  - *Contract* (write the signatures, never the bodies):
    ```rust
    pub enum BudgetPolicy { BackpressureRetry, FlushNow }
    pub enum Admission { Admitted, Backpressure, Flushed }      // returned by try_reserve
    pub struct ShardBudget {
        budget_bytes: u64,        // max(1.5GiB, 7% of total) by default
        used_bytes: u64,          // PLAIN field — owned by the single shard writer, NOT shared
        policy: BudgetPolicy,
    }
    impl ShardBudget {
        pub fn with_default_for_host(total_bytes: u64, shards: u32) -> Self; // max(1.5GiB, 7%)
        pub fn try_reserve(&mut self, insert_size: u64) -> Admission;        // hot path
        pub fn release(&mut self, freed: u64);                               // on flush
        pub fn used(&self) -> u64;
    }
    ```
  - *Back-of-envelope*: insert hot path budget = the check must vanish into the insert cost. Single-writer `used_bytes` lives in L1 of the owning core → load 0.5ns + add + compare + **predictable** branch (~1ns total, no mispredict in steady state). Contrast: a *shared* `AtomicU64` total ticked by 16 cores → the line ping-pongs (MESI invalidate ~40-100ns *per* contended tick) — a **40-100× cliff** on a path that should be ~1ns. Budget math: 16 shards × `max(1.5GiB, 7% of 16GiB=1.12GiB)` = 16 × 1.5GiB = 24GiB reserved on a 16GiB host → **the default over-commits**; on small hosts the `7%` arm wins, on large hosts the `1.5GiB` floor wins — the `max` is doing real work and the test must hit both arms.
  - **Requirements** R1..R7 — write in `crates/mini-db/notes/95sat_budget_design.md`:
    - R1: default budget = `max(1.5 * 2^30, total_bytes * 7 / 100)` per shard, computed without floating point (integer math, no `0.07_f64`).
    - R2: `try_reserve` is single-writer — `used_bytes` is a plain field, never an atomic shared across shards.
    - R3: on `current + insert_size > budget`: `BackpressureRetry` → return `Backpressure`, do NOT mutate `used_bytes`; `FlushNow` → caller flushes, then `release()` is called, then reserve retried.
    - R4: `try_reserve` never overflows: use checked/saturating add at the boundary so `u64::MAX`-class inputs reject rather than wrap.
    - R5: a single insert larger than the whole budget is rejected deterministically (not infinite-flush-loop).
    - R6: `used()` after a sequence of reserves/releases equals the exact net reserved bytes (conservation).
    - R7: budget enforcement holds under sustained load — no shard's `used()` ever exceeds `budget_bytes` (the safety invariant the bench asserts).
  - **Design walk-through** D1..D5 — answer in the design doc; no peeking at Seastar source until Phase 3:
    - D1: property table for the footprint counter — {plain `u64` on `!Send` shard | `AtomicU64` shared | `AtomicU64` per-shard CachePadded}: columns Sync? / hot-path ns / cross-core traffic / fits single-writer principle. (Answer: plain field wins — single writer.)
    - D2: enumerate the over-budget policies and when each is legal (BackpressureRetry default; FlushNow only when backpressure has no upstream to signal, e.g. WAL-replay path that must make progress).
    - D3: **Pre-mortem (load-bearing)** — write the EXACT bad interleaving for FlushNow under burst:
      ```
      t0 shard near budget; burst of writes arrives
      t1 try_reserve over budget → FlushNow → flush memtable → new SST
      t2 SST count crosses compaction trigger → compaction starts, allocates input/output buffers
      t3 burst continues; reserve over budget again → FlushNow again → more SSTs
      t4 compaction memory + new memtable both grow → total RSS climbs DESPITE flushing → OOM (thrash)
      ```
      If you can't write this trace, you can't prove BackpressureRetry-as-default prevents it.
    - D4: **Anti-shortcut audit** — name the obvious reach and why it's wrong HERE:
      - "Use one shared `AtomicU64` for the whole DB's memory" → wrong: re-introduces cross-shard contention the per-shard model exists to kill (single-writer principle).
      - "Use `f64` for the 7% math" → wrong: float div 10-30 cyc on the config path is fine, but rounding makes the budget non-reproducible across hosts and the boundary test flaky; use integer `*7/100`.
      - "Just `current + insert_size > budget`" → wrong: wraps at `u64::MAX`, admitting the OOM insert (R4).
    - D5: integer-overflow boundary — pick checked vs saturating add and justify (saturating: `u64::MAX`-class input saturates above budget → rejected, no panic, no wrap).
  - **Output**: `crates/mini-db/notes/95sat_budget_design.md` with R1..R7, D1..D5, and the D3 bad-interleaving sketch.

  #### Phase 2 — Write the failing tests (~50 min)
  Each test is engineered so a common naive impl FAILS it. Annotate the tier. Put these in `crates/mini-db/src/per_shard_memory_budget.rs` `#[cfg(test)]` and one criterion bench.

  ```rust
  // (NEWBIE) ANTI-SHORTCUT trap: the `max(1.5G, 7%)` rule must hit BOTH arms.
  // A naive `total * 7 / 100` (forgetting the 1.5GiB floor) passes on a big host, fails on a small one.
  #[test]
  fn default_budget_uses_max_of_floor_and_percent() {
      // small host: 8 GiB → 7% = 0.56 GiB < 1.5 GiB floor → floor wins
      let small = ShardBudget::with_default_for_host(8 << 30, 1);
      assert_eq!(small.budget_bytes, 1_536u64 << 20, "expected 1.5GiB floor (1,610,612,736 bytes)");
      // big host: 100 GiB → 7% = 7 GiB > 1.5 GiB floor → percent wins
      let big = ShardBudget::with_default_for_host(100 << 30, 1);
      assert_eq!(big.budget_bytes, (100u64 << 30) * 7 / 100, "percent arm not applied on big host");
  }

  // (SENIOR) NEGATIVE-CONTROL / boundary: the check must FIRE, and conservation must hold.
  // A too-loose `>=` vs `>` or a forgotten release breaks this. Proves the budget is actually enforced.
  #[test]
  fn try_reserve_enforces_and_conserves() {
      let mut b = ShardBudget { budget_bytes: 1000, used_bytes: 0, policy: BudgetPolicy::BackpressureRetry };
      assert_eq!(b.try_reserve(600), Admission::Admitted);
      assert_eq!(b.used(), 600);
      assert_eq!(b.try_reserve(600), Admission::Backpressure, "second 600 over 1000 budget must backpressure");
      assert_eq!(b.used(), 600, "backpressured insert must NOT mutate used_bytes");
      b.release(600);
      assert_eq!(b.used(), 0, "conservation: release must restore exact bytes");
      assert_eq!(b.try_reserve(600), Admission::Admitted, "after release the same insert now fits");
  }

  // (SENIOR) OVERFLOW boundary: `current + insert_size` near u64::MAX must REJECT, not wrap-admit.
  #[test]
  fn try_reserve_does_not_overflow_admit() {
      let mut b = ShardBudget { budget_bytes: 1_000_000, used_bytes: u64::MAX - 8, policy: BudgetPolicy::BackpressureRetry };
      // naive `used + insert > budget` wraps to a tiny value < budget → wrongly Admitted (the OOM insert).
      assert_eq!(b.try_reserve(64), Admission::Backpressure,
          "wrapping add admitted an over-budget insert — OOM bug");
      assert_eq!(b.used(), u64::MAX - 8, "rejected insert must not mutate used");
  }

  // (SENIOR) FlushNow must not infinite-loop on an insert bigger than the whole budget.
  #[test]
  fn oversized_insert_is_rejected_not_flush_looped() {
      let mut b = ShardBudget { budget_bytes: 1000, used_bytes: 0, policy: BudgetPolicy::FlushNow };
      // 2000 > 1000 even on an empty shard: flushing frees nothing useful → must reject, not loop.
      assert_eq!(b.try_reserve(2000), Admission::Backpressure,
          "insert larger than budget must be rejected deterministically");
  }

  // (EXPERT) CROSS-PRIMITIVE trap: compose with the per-shard substrate (runtime-thread-per-core).
  // Each shard owns its OWN ShardBudget (single writer). This test fails if you "simplify" to one
  // shared atomic total — the type then must be Send+Sync AND the safety invariant leaks across shards.
  #[test]
  fn per_shard_budgets_are_independent_single_writer() {
      // 16 independent shard budgets; saturating ONE shard must not change another's `used`.
      let mut shards: Vec<ShardBudget> = (0..16)
          .map(|_| ShardBudget { budget_bytes: 1000, used_bytes: 0, policy: BudgetPolicy::BackpressureRetry })
          .collect();
      // hammer shard 0 to its budget
      for _ in 0..10 { let _ = shards[0].try_reserve(100); }
      assert_eq!(shards[0].used(), 1000, "shard 0 should be full");
      assert_eq!(shards[5].used(), 0, "shard 5 must be UNAFFECTED — no cross-shard coupling");
      // NOTE: a Vec of per-shard AtomicU64 budgets would ALSO compile and pass these independence
      // asserts — so this test alone does not forbid atomics. The anti-shared-atomic guarantee is
      // enforced by the bench below (size_of ≤ 32 + the ops/s band); the SINGLE shared-atomic-total
      // variant is what fails there (MESI bounce drops the rate). Keep used_bytes a plain field
      // owned by the !Send shard writer (single-writer principle).
  }

  // (EXPERT) NEGATIVE-CONTROL bench: the budget check must be ~free on the hot path AND the bench must
  // actually measure inserts (layout assertion so it fails fast if it measured nothing).
  // criterion bench in benches/budget.rs:
  //   assert!(std::mem::size_of::<ShardBudget>() <= 32, "ShardBudget bloated — would not stay hot in L1");
  //   bench try_reserve in a tight loop; assert measured rate lands in 1e8..2e9 ops/s/thread
  //   (single load+add+compare+predictable-branch). A rate below 1e7 means an atomic/mutex crept in.
  ```
  Negative-control: the bench's `size_of` + ops/s-band assertion proves it measures the real hot path; the overflow + oversized + conservation tests are the "test-the-test" that the budget genuinely fires.

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)
  Ordered failure cards, newbie first, expert last — the ladder you actually walk.

  - **(NEWBIE) When `default_budget_uses_max_of_floor_and_percent` reports the small-host budget = 0.56GiB:**
    - Symptom: assertion fails — you returned `total * 7 / 100` and forgot the floor.
    - Why: Seastar's rule is `max(1.5GiB, 7%)`; the 7% arm only wins on large hosts. On an 8GiB box 7% is below the floor.
    - Fix: `budget_bytes = core::cmp::max(1_610_612_736, total_bytes * 7 / 100)` (1.5GiB = `1536 << 20`).
    - Cost avoided: on a small dev box every shard gets a starvation-sized memtable → constant flushing → write-amp. Functional bug, not just slow.
    - Muscle: when a spec says `max(floor, ratio)`, both arms are load-bearing — test the regime where each wins. Reapplies at: W98 GC watermark thresholds, W100 mini-db sizing config, W14 bufpool capacity sizing.

  - **(SENIOR) When `try_reserve_enforces_and_conserves` reports `used() == 1200` after a backpressure:**
    - Symptom: a backpressured insert still incremented `used_bytes`.
    - Why: you mutated `used_bytes` *before* the over-budget check, or used `>=`/`>` inconsistently, so the rejected insert leaked into the counter.
    - Fix: compute `would_use` first, branch, and only commit `used_bytes = would_use` on the Admitted arm.
    - Cost avoided: a leaking counter drifts upward forever → false backpressure on a half-empty shard → throughput collapse with no OOM to explain it.
    - Muscle: an admission counter must be mutated only on the admit arm — check-then-commit, never commit-then-check. Reapplies at: W11 backpressure semaphore, W98 MVCC write-set sizing, W74 matching-engine order-count limits.

  - **(SENIOR) When `try_reserve_does_not_overflow_admit` reports `Admitted`:**
    - Symptom: a 64-byte insert at `used = u64::MAX-8` was admitted.
    - Why: `used + insert > budget` wrapped past `u64::MAX` to a tiny value that compared below budget — the classic integer-overflow admit, which here admits the exact insert that OOMs the shard.
    - Fix: `used_bytes.checked_add(insert).map_or(true, |t| t > budget_bytes)` (or `saturating_add`) so overflow → reject.
    - Cost avoided: silent OOM-kill of the whole thread-per-core process (every shard dies). 0 cycles to add a `checked_add`; catastrophic if omitted.
    - Muscle: any `a + b > limit` on a budget/counter is an overflow trap — use checked/saturating add. Reapplies at: W34 bloom bit-index math, W42 txn id space, W84 runtime-thread-per-core queue depth caps.

  - **(SENIOR) When `oversized_insert_is_rejected_not_flush_looped` hangs / loops:**
    - Symptom: FlushNow flushes an empty memtable, frees ~0, retries, flushes again — infinite loop on an insert bigger than the budget.
    - Why: FlushNow assumes flushing always frees enough to fit the insert; an insert larger than the whole budget never fits.
    - Fix: before flushing, if `insert_size > budget_bytes` reject immediately (`Backpressure`); only flush when freeing the memtable could plausibly admit.
    - Cost avoided: a hung shard wedges its core forever (thread-per-core = that symbol/keyspace is dead). Liveness bug.
    - Muscle: a flush-to-make-room loop needs a progress guard — if even an empty target can't fit, reject. Reapplies at: W14 bufpool eviction-to-fit, W98 compaction input sizing, W100 range-scan buffer admission.

  - **(EXPERT, perf) When `per_shard_budgets_are_independent_single_writer` forces `ShardBudget: Sync` / shard 5 changes:**
    - Symptom: you "simplified" to one shared `AtomicU64` total; now the type must be `Send + Sync`, and the bench rate drops below 1e7 ops/s under 16-thread contention.
    - Why: a shared atomic ticked by every shard on every insert ping-pongs one cache line across all 16 cores — MESI invalidate-on-write serializes the hot path.
    - Fix: keep `used_bytes` a **plain `u64` field** owned by the single shard writer (the `!Send` shard task from runtime-thread-per-core). Per-shard budgets are independent by construction — no shared atomic, no cross-shard coupling.
    - Cost avoided: 40-100ns MESI bounce *per insert* × 16 cores vs ~1ns single-writer L1 access — a 40-100× hot-path regression on the most frequent operation in the DB (bar (b) crate, but this defeats the runtime-thread-per-core substrate it inherits). Cost: ~96 cache-line bounces/100k inserts → benchmarked as a flat throughput ceiling regardless of shard count.
    - Muscle: per-shard state is single-writer — never reach for a shared atomic to track per-shard footprint; the absence of the atomic IS the optimization. Reapplies at: W84 runtime-thread-per-core per-shard counters, W74 matching-engine per-symbol book, W98 per-shard MVCC sequence, W65 Disruptor per-producer cursor.

  - **(EXPERT, perf) When the criterion bench in `benches/budget.rs` reports a rate below 1e8 ops/s or `size_of::<ShardBudget>() > 32`:**
    - Symptom: bench rate too low, or the struct grew (e.g. you boxed the policy, or added a `Mutex`).
