**Tuesday — mini-db: raft wire-up**

- [ ] **Build**: `crates/mini-db/src/raft_replicated.rs` — `RaftKv` wraps `MiniDb`. Submits `KvCommand` enum (Put, Delete, TxnBatch) through `consensus_raft::RaftNode`; apply() mutates local MiniDb deterministically. (~total 3.5 hrs across 3 phases)
  - 🔧 **Why this matters**: this is the inheritance principle's strongest demonstration — distributed mini-db with virtually no new code. consensus-raft (W67 v1.0) provides log replication + leader election + safety; mini-db provides the state machine. The "thin layer" pattern is exactly TiKV's architecture (TiKV = RocksDB + Raft + range-sharding + Coprocessor). If raft_replicated.rs grows past ~600 LOC, you're reimplementing something. Downstream consumers: W99 Wed sharding router (consumes RaftKv per shard), W100 chaos suite (kills 1 of 3 replicas per shard), W100 blog cites this as the "TiKV-pattern" example.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: distributed state machine requires deterministic apply across replicas; any nondeterminism (Instant::now, iteration over HashMap, concurrent apply) diverges state — silent corruption that surfaces only at snapshot ship time. The wrapper layer must be thin (no reimplemented logic) and the apply function rigorously deterministic.

  - **Requirements** (write in `crates/mini-db/notes/99tue_raftkv_design.md`):
    - R1. `KvCommand::{Put, Delete, TxnBatch}` serialized via bincode; deterministic across replicas.
    - R2. `apply()` is strictly deterministic — NO Instant::now(), NO HashMap iteration, NO concurrent state access. All timestamps come from log entry payload.
    - R3. `apply()` runs in log-index order, single-threaded per partition. Concurrency comes from sharding only.
    - R4. `snapshot()` captures consistent point via mini-db's MVCC; ships versions ≤ snapshot ts + applied_lsn.
    - R5. `restore()` wipes data dir and rehydrates from snapshot + applied_lsn; raft replays from applied_lsn+1.
    - R6. Linearizable read via `raft.read_index()` (Raft §6.4); leader confirms quorum heartbeat, then reads local.
    - R7. 3-node cluster sustains ≥ 30 k put/sec (down from single-node 500 k due to raft commit cost).
    - R8. Linearizable read P99 ≤ 1 ms.
    - R9. Replica determinism: replay same log on 3 fresh mini-db instances; manifest hashes byte-identical for 1M-op log.
    - R10. raft_replicated.rs ≤ 600 LOC native (inheritance principle).
    - R11. Cross-shard txn returns `Err(CrossShardNotSupported)` for v0.5; document as v1.0+ work.

  - **Design walk-through** — answer each; no peeking at TiKV `raftstore/src/store/peer.rs::apply` or etcd `etcdserver/server.go::applyAll` until Phase 3:
    - D1. Deterministic apply: list 5 sources of nondeterminism that could leak in. (a) Instant::now, (b) HashMap iteration order (not random in Rust but unstable across recompiles), (c) RNG, (d) thread-local state, (e) IO timing of underlying DB. Fix each: ts from log payload; BTreeMap; deterministic RNG seeded by log index; no thread-locals; mini-db apply is sync.
    - D2. WAL fsync redundancy: raft log is durable; mini-db's WAL fsync on followers is redundant overhead. v0.5 keeps it for simplicity; v0.7 optimization is `sync_log=false` on followers (TiKV pattern). What's the cost of redundancy? (~30 µs per apply.)
    - D3. Read-index protocol (Raft §6.4): leader receives Read; broadcasts heartbeat to quorum; on majority response, reads local state at the current applied_lsn. Why not just read local? (Stale read possible — leader may have lost leadership.)
    - D4. Snapshot during apply: raft decides to snapshot mid-apply, sees partial state. Fix: serialize apply and snapshot via state machine lock; snapshot() captures via mini-db's MVCC snapshot (ships versions ≤ snapshot ts).
    - D5. applied_lsn persistence: must be atomic with the apply itself. Where stored? (Inside the mini-db checkpoint — same fsync barrier.) What if applied_lsn persists but mini-db state doesn't (or vice versa)? (Either way, recovery replays from last_consistent point; idempotent apply makes this safe.)
    - D6. KvCommand::TxnBatch carries `commit_ts`; apply opens a txn with that ts, applies all ops, commits. Why is commit_ts proposer-supplied, not apply-time-generated? (Apply-time = nondeterministic; proposer-supplied = deterministic across replicas.)
    - D7. **Pre-mortem (load-bearing)**: write the 6-step sequence where replica A applies entry I and persists applied_lsn=I but mini-db state crash-corrupts; on restart, raft replays I+1 onward; state diverges silently from replicas B, C. What invariant prevents? (Applied_lsn INSIDE mini-db checkpoint; either both persist or neither.)

  - **Output**: `notes/99tue_raftkv_design.md` with R1–R11 + D1–D7 + determinism checklist + read-index sequence diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~110 min)

  - **When `proptest_replica_determinism_1m_ops` fails with diverged manifest hashes on iteration 5234**:
    - Symptom: 3 replicas applied same log; replica A hash != replica B hash. Counterexample shrinks to a TxnBatch with 3 ops.
    - Why: apply path used `Instant::now()` to stamp records; replica A applied at 100ns; replica B at 105ns; mini-db's HLC integrated different ts.
    - Fix: ALL ts come from log entry payload. KvCommand::Put carries `ts: u64`; apply uses that ts, never wall clock. KvCommand::TxnBatch carries `commit_ts: u64`; txn.commit_at(commit_ts) uses that exactly.
    - Muscle: deterministic apply requires ZERO wall-clock dependencies in the SM; all temporal info travels in the log. Reapplies at: W100 chaos under crash-restart, every Raft-backed system.

  - **When `test_apply_lsn_persisted_with_state` shows double-apply after restart**:
    - Symptom: applied 100 entries; crash after apply but before persisting applied_lsn; restart replays from 0; entries 0..N applied twice; state corrupted.
    - Why: applied_lsn was tracked in separate file, not atomically committed with mini-db state.
    - Fix: applied_lsn persisted INSIDE the mini-db checkpoint (same fsync barrier). On restart, raft reads applied_lsn from mini-db; replays only entries > applied_lsn. Atomicity ensured by mini-db's own commit.
    - Muscle: dual persistence (lsn + state) is fragile; embed lsn in state itself. Reapplies at: W92 ledger replica state, every Raft SM.

  - **When `test_no_instant_now_in_apply` finds an Instant::now in metrics code**:
    - Symptom: grep hits `metrics::APPLY_LATENCY.observe(start.elapsed())` inside apply().
    - Why: metrics instrumentation is non-determinism-safe (observation, not state change) — but if any downstream metric is read back into the SM, it becomes determinism-breaking.
    - Fix: metrics are pure observers; never read back into SM. Mark apply path with `#[cfg(not(deterministic_apply))]` for metrics; on deterministic test profile, metrics elided.
    - Muscle: metrics are external-facing; never let them feed back into state. Reapplies at: W82 matching-engine apply, W92 ledger apply.

  - **When `test_thin_layer_loc_under_600` reports raft_replicated.rs at 1200 LOC**:
    - Symptom: tokei shows 1200 LOC; ~600 over budget; inheritance ratio drops.
    - Why: re-implemented raft batching, re-implemented snapshot serialization, re-implemented read-index protocol.
    - Fix: delegate to `consensus_raft::RaftNode::propose/read_index/snapshot/restore`. Local code is just KvCommand definition + StateMachine trait impl. If consensus_raft doesn't expose what you need, add it THERE.
    - Muscle: inheritance ratio is the audit's metric; LOC budget forces delegation. Reapplies at: every CAPSTONE wrapper module.

  - **When `bench_3_node_throughput_30k_per_sec` reports 5 k/sec**:
    - Symptom: 3-node cluster delivers 5 k/sec puts (target 30 k); ~6× under.
    - Why: every apply fsyncs mini-db WAL on every follower (redundant — raft log is durable). Also: apply is per-entry, not batched.
    - Fix: (a) on followers, set `wal::SyncMode::Never` (raft log is durability source); (b) batch apply — consensus_raft v1.0 exposes batched apply; group N entries per fsync barrier.
    - Cost avoided: ~25 µs/apply × 100k apply/sec = ~2.5 sec/sec wasted on redundant fsync; throughput goes 5k → 30k.
    - Muscle: layered durability is redundant; pick ONE source of truth per layer. Reapplies at: W82 matching-engine + raft, every Raft-backed DB.

  - **5-year failure mode** (write in `notes/99tue_raftkv_followup.md`): when single-shard throughput exceeds 100 k/sec (high-end NVMe + io_uring), Raft apply becomes single-threaded bottleneck. Migration: parallel apply for non-conflicting entries (TiKV's apply-by-region pattern, scaled to per-key-range). Trigger: P99 apply latency > 5 ms.

  - **Reference material**: TiKV `components/raftstore/src/store/peer.rs::apply`, `fsm/apply.rs::ApplyFsm`; etcd `etcdserver/server.go::applyAll`; Ongaro thesis Ch5 (read-index, lease reads); `crates/consensus-raft/src/lib.rs`.

**Wednesday — mini-db: sharding stub**

- [ ] **Build**: `crates/mini-db/src/sharding.rs` — consistent-hash shard router, fixed N-shard cluster. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: with N raft groups (one per shard) you get N× throughput at the cost of cross-shard txn complexity. Consistent hash keeps impl tiny; range-sharding would require rebalancing (out of scope v0.5). Downstream: W100 tags v1.0 with this; chaos suite tests shard failure isolation.

  #### Phase 1 — Requirements + design (~25 min)

  - **Requirements** (write in `notes/99wed_sharding_design.md`): (R1) shard count fixed at cluster bootstrap, no resharding; (R2) hash uses stable seed (ahash with explicit seed) so all clients agree on routing; (R3) cross-shard ops merge client-side with NO transactional guarantees; (R4) 4-shard cluster ≥ 100 k put/sec (linear scaling vs single-shard); (R5) cross-shard scan within 2× single-shard time; (R6) put distribution ±10% across shards under random keys; (R7) multi-shard scan globally ordered via k-way merge (lsm_core::MergeIterator); (R8) shard failure: per-shard timeout; scan returns `Err(ShardUnavailable { shard })`.

  - **Design questions**: (D1) ahash vs jump-consistent: ahash simpler, jump-consistent handles resharding. v0.5 picks ahash (no resharding). (D2) Hash-first-then-mod: why? (Sequential keys would all land on one shard with raw modulo; hash randomizes.) (D3) **Pre-mortem**: client A uses seed 42, client B uses default seed; same key routes to different shards; writes invisible to B's reads. What guard prevents? (Seed in cluster config; router panics on construction without explicit seed.)

  #### Phase 2 — Failing tests

  - [ ] `test_shard_distribution_even` — 100 k random keys across 4 shards; assert ±10% balance.
  - [ ] `bench_4_shard_linear_scaling` — 4-shard ≥ 100 k put/sec.
  - [ ] `test_cross_shard_scan_globally_ordered` — multi-shard scan; results in ascending key order.
  - [ ] `test_shard_failure_returns_err` — kill one shard's raft quorum; put on that shard's key returns Err; put on healthy shard succeeds.
  - [ ] `test_hash_seed_required` — router construction without explicit seed panics.
  - [ ] `test_sequential_keys_hash_distributed` — sequential keys 0..1M; assert distribution ±10% (not all on shard 0).
  - [ ] `bench_cross_shard_scan_under_2x_single` — multi-shard scan vs single-shard; assert ≤ 2× slower.

  #### Phase 3 — Failure cards

  - **When `test_sequential_keys_hash_distributed` shows 90% on shard 0**: Symptom: sequential keys land mostly on shard 0; load skewed. Why: code did `key.as_u64() % N` instead of `hash(key) % N`. Fix: hash first (ahash randomizes), THEN modulo. Add per-shard QPS metric for ops visibility.

  - **When `test_cross_shard_scan_globally_ordered` shows out-of-order results**: Symptom: scan emits key 50 then key 10; merge isn't k-way sorted. Why: code concatenated per-shard scan results sequentially. Fix: use `lsm_core::MergeIterator` (k-way); each shard's iterator feeds in; result globally ordered.

  - **When `test_shard_failure_returns_err` hangs forever**: Symptom: one shard's raft has no quorum; scan hangs. Why: no per-shard timeout. Fix: per-shard timeout; scan returns `Err(ShardUnavailable { shard })`; caller retries or accepts partial. Document partial-scan semantics in API.

  - **5-year failure mode**: when shard count must change (cluster growth), no online resharding. Migration: jump-consistent hashing + backfill migration tool. Trigger: per-shard CPU > 80%.
