  - **Read first**:

      (ApplyFsm — the canonical "raft log → state machine" applier).
    - etcd `server/etcdserver/server.go` (EtcdServer.applyAll loop).
    - Diego Ongaro thesis Chapter 5 (Client interaction) — read-index, lease reads, linearizable reads.
    - `crates/consensus-raft/src/lib.rs` (your `RaftNode` API — propose/apply/snapshot).
    - `crates/consensus-raft/src/state_machine.rs` (StateMachine trait you exposed).
  - **Design**: ```rust
    use crate::Db;
    use crate::engine::EngineConfig;
    use consensus_raft::{RaftNode, RaftConfig, NodeId, LogEntry, ProposalResult};
    use serde::{Serialize, Deserialize};

    #[derive(Serialize, Deserialize, Clone)]
    pub enum KvCommand {
        Put { key: Bytes, value: Bytes },
        Delete { key: Bytes },
        TxnBatch { ops: Vec<KvCommand>, commit_ts: u64 },  // for MVCC commit
    }

    pub struct RaftKv {
        raft: RaftNode<KvStateMachine>,
        node_id: NodeId,
    }

    pub struct KvStateMachine {
        db: Db,
        applied_lsn: AtomicU64,
    }

    impl consensus_raft::StateMachine for KvStateMachine {
        type Command = KvCommand;
        type Output = KvOutput;

        fn apply(&mut self, entry: &LogEntry<Self::Command>) -> Result<Self::Output> {
            match &entry.command {
                KvCommand::Put { key, value } => self.db.put(key, value)?,
                KvCommand::Delete { key } => self.db.delete(key)?,
                KvCommand::TxnBatch { ops, commit_ts } => {
                    // Atomic-batched apply — open a txn, apply all ops, commit at commit_ts
                    let txn = self.db.begin_with_ts(*commit_ts);
                    for op in ops { /* dispatch */ }
                    txn.commit_at(*commit_ts)?;
                }
            }
            self.applied_lsn.store(entry.index, Ordering::Release);
            Ok(KvOutput::Applied)
        }

        fn snapshot(&self) -> Result<Vec<u8>> {
            // Flush mini-db memtable, return manifest + applied_lsn
            let manifest = self.db.checkpoint()?;
            Ok(bincode::serialize(&(manifest, self.applied_lsn.load(Ordering::Acquire)))?)
        }

        fn restore(&mut self, snap: &[u8]) -> Result<()> {
            let (manifest, lsn): (Manifest, u64) = bincode::deserialize(snap)?;
            self.db.restore_from(manifest)?;
            self.applied_lsn.store(lsn, Ordering::Release);
            Ok(())
        }
    }

    impl RaftKv {
        pub fn put(&self, k: &[u8], v: &[u8]) -> Result<()> {
            let cmd = KvCommand::Put { key: k.into(), value: v.into() };
            match self.raft.propose(cmd).await? {
                ProposalResult::Committed(_) => Ok(()),
                ProposalResult::NotLeader(hint) => Err(Error::NotLeader(hint)),
                ProposalResult::Timeout => Err(Error::Timeout),
            }
        }

        pub fn get(&self, k: &[u8]) -> Result<Option<Bytes>> {
            // Linearizable read via read-index (Raft §6.4)
            self.raft.read_index().await?;
            // Now safe to read local state — leader has confirmed it's still leader at this index.
            self.raft.state_machine().db.get(k)
        }
    }
    ```
    **Invariants**:
    - `apply()` is **deterministic** — same input on every replica yields same state. No `Instant::now()`, no
      iteration over HashMaps (use BTreeMap), no nondeterministic concurrency in apply. Commit ts is supplied
      by the proposer and travels in the log entry.
    - `apply()` runs in **log-index order**, single-threaded per partition. Concurrency comes from sharding.
    - WAL fsync within mini-db is REDUNDANT for committed entries (raft log is the durability source). But for the
      MVP, keep mini-db's WAL — disabling it is a v0.7 optimization (TiKV does sync_log=false on follower).
    - Read uses read-index protocol for linearizability (or lease-read for performance if quorum is healthy).
    - Snapshots are taken periodically to bound recovery time; snapshot transfer ships compacted mini-db state.
  - **Build steps**:
    1. (~20 min) `KvCommand` enum + serde + bincode roundtrip test.
    2. (~25 min) `KvStateMachine` impl with `apply` dispatching to `Db::put/delete/begin`.
    3. (~20 min) `apply` MUST be deterministic — replace any `Instant::now()` with `commit_ts` from log entry;
       assert via property test that two replicas applying same log yield byte-identical SST contents (compare
       manifest hashes).
    4. (~25 min) `snapshot/restore` — write the mini-db checkpoint + applied_lsn, restore wipes the data dir
       and rehydrates.
    5. (~25 min) Linearizable `RaftKv::get` via raft's `read_index()` (leader confirms heartbeat, then reads
       local).
    6. (~25 min) Test: 3-node cluster (in-memory transport), 100k puts, kill leader mid-batch, new leader takes
       over, all puts eventually applied; reads on new leader return latest.
    7. (~10 min) Document the "thin layer" LOC count — target ≤ 600 LOC for raft_replicated.rs.
  - **Pitfalls** (named, deep):
    - *Nondeterministic apply*: **Symptom**: apply uses `SystemTime::now()` to stamp records; replica A applies at
      t=100, replica B at t=101 → state divergence; raft detects on snapshot ship and refuses. **Fix**: ALL
      ts come from log entry payload (proposer-supplied); test with proptest that applies the same log on 3
      replicas and compares manifest hashes.
    - *Double-apply after restart*: **Symptom**: replica crashes after applying entry I but before persisting
      applied_lsn; on restart, raft replays from last_persisted_lsn → I, applying I twice. **Fix**:
      `applied_lsn` is persisted INSIDE the mini-db checkpoint (same fsync barrier); on restart, raft skips
      entries ≤ applied_lsn. Atomicity ensured by mini-db's own commit.
    - *Snapshot during apply*: **Symptom**: raft decides to take a snapshot mid-apply, sees partial state. **Fix**:
      raft serializes apply and snapshot via state machine lock; snapshot() captures a consistent point via
      mini-db's MVCC (call `db.snapshot()` then ship versions ≤ that ts).
    - *Cross-shard txn*: **Symptom**: caller calls `Db::txn` that spans keys from shards 0 and 1 — no 2PC, txn
      semantically broken. **Fix**: scope v0.5 to single-shard txns; sharding router (Wed) rejects multi-shard
      with `Err(CrossShardNotSupported)`. v1.0+ would add Percolator-style 2PC (TiKV reference).
    - *Hot shard*: **Symptom**: one shard handles 90% of traffic, raft leader on that shard is bottleneck. **Fix**:
      v0.5 just instrument `SHARD_QPS_HIST`; v1.0 would add dynamic split (out of scope, document in DESIGN.md).
    - *Leader flapping*: **Symptom**: under load, heartbeat misses cause re-election every few seconds; client
      sees Err(NotLeader) bursts. **Fix**: tune raft election timeout up (consensus-raft already exposes
      config); add jittered backoff in `RaftKv::put` retry; PreVote enabled (W67 v1.0 has it).
    - *Apply-side blocking*: **Symptom**: apply() does a synchronous Db::put that fsyncs WAL → apply throughput
      tanks → log grows unbounded → snapshots more frequent → death spiral. **Fix**: batch apply (raft v1.0
      should support batched apply); disable mini-db WAL fsync on followers (raft log is durable already).
  - **Test scenarios** (adversarial):
    - 3-node cluster, 100k puts, kill leader mid-batch, verify convergence.
    - Replica determinism: replay same log on 3 fresh mini-db instances, compare manifest hash.
    - Snapshot-then-restore: take snapshot at index 50k, wipe replica, restore, replay from 50k, state matches.
    - Cross-shard rejection: txn spanning two shards returns CrossShardNotSupported.
    - Read-index correctness: T1 writes K=1; T2 reads K from any replica via `get`; sees 1 (not stale).
    - Hot shard: 95% writes to one shard, observe `SHARD_QPS_HIST` skew; mini-db doesn't deadlock.
  - **Acceptance**:
    - 3-node cluster sustains ≥ 30k put/sec (down from single-node 500k due to raft commit cost — expected).
    - Linearizable reads via read_index ≤ 1 ms P99.
    - Replica determinism test passes for 1M-op log.
    - `raft_replicated.rs` ≤ 600 LOC native (inheritance principle).
  - **Downstream**: W99 Wed sharding router consumes RaftKv per shard; W100 chaos kills 1 of 3 replicas per shard
    and asserts convergence; cite this design in W100 blog post as the "TiKV-pattern" example.

**Wednesday — mini-db: sharding stub**

- [ ] **Build**: `crates/mini-db/src/sharding.rs` — consistent-hash shard router, fixed N-shard cluster. NOT a research
  project — minimum viable. (~75 min)
  - **Why**: With N raft groups (one per shard) you get N× throughput at the cost of cross-shard txn complexity.
    Consistent hash keeps the implementation tiny; range-sharding would require rebalancing (out of scope v0.5).
    TiKV uses range-sharding for spatial locality on scans, but mini-db's primary workload is point ops, so hash
    is fine.
  - **Read first**: Karger et al. 1997 "Consistent Hashing"; DynamoDB paper §4.2 (partitioning); etcd `pkg/proxy/`
    (proxy → shard pattern); TiKV `components/pd/` (placement driver — explicitly note we're NOT building this,
    it's static); Ketama hash for jump-consistent reference.
  - **Design**: ```rust
    pub struct ShardRouter {
        shards: Vec<Arc<RaftKv>>,         // fixed N, no rebalancing
        hasher: ahash::RandomState,
    }
    impl ShardRouter {
        pub fn shard_for(&self, key: &[u8]) -> usize {
            let h = self.hasher.hash_one(key);
            (h % self.shards.len() as u64) as usize
        }
        pub async fn put(&self, key: &[u8], value: &[u8]) -> Result<()> {
            self.shards[self.shard_for(key)].put(key, value).await
        }
        pub async fn get(&self, key: &[u8]) -> Result<Option<Bytes>> {
            self.shards[self.shard_for(key)].get(key).await
        }
        pub async fn scan(&self, /* ... */) -> Result<MergedScan<'_>> {
            // Scan across ALL shards, merge results — expensive, document.
            let scans: Vec<_> = futures::future::try_join_all(
                self.shards.iter().map(|s| s.scan(lower.clone(), upper.clone()))
            ).await?;
            Ok(MergedScan::new(scans))
        }
    }
    ```
    **Invariants**: shard count is FIXED at cluster bootstrap (no resharding); hash uses a stable seed (ahash with
    explicit seed) so all clients agree on routing; cross-shard ops (multi-shard scan) merge results
    client-side, no transactional guarantees across shards.
  - **Build steps**: 1. (~10 min) `ShardRouter` skeleton with hash; 2. (~15 min) `shard_for` with seeded ahash;
    3. (~20 min) Put/get routing through corresponding `RaftKv`; 4. (~20 min) Multi-shard scan via merge of
    per-shard iterators (uses lsm-core's MergeIterator pattern); 5. (~10 min) Test: 100k puts across 4 shards,
    verify even distribution (±10%); single-key get round-trips.
  - **Pitfalls** (named):
    - *Hash seed drift*: **Symptom**: client A uses seed 42, client B uses default — same key routed to different
      shards, writes invisible. **Fix**: seed in cluster config (e.g., env `MINIDB_HASH_SEED=42`); router panics
      on construction without seed.
    - *Skewed shard distribution*: **Symptom**: workload uses sequential keys, modulo-N puts them all on one
      shard. **Fix**: hash first (ahash randomizes), THEN mod. Above design already does this. Add metric for
      per-shard QPS.
    - *Multi-shard scan correctness*: **Symptom**: scan emits results out of order because merge isn't k-way
      sorted. **Fix**: use `lsm_core::MergeIterator` (already k-way); each shard's iterator feeds in; result is
      globally ordered.
    - *Shard failure*: **Symptom**: one shard's raft group has no quorum, scan hangs forever. **Fix**: per-shard
      timeout; scan returns Err(ShardUnavailable { shard }) and caller can retry or accept partial. Document
      partial-scan semantics.
  - **Test scenarios**: 100k puts spread across 4 shards, distribution ±10%; multi-shard scan returns globally
    ordered results; one shard offline → put on offline key returns Err, put on healthy shard succeeds.
  - **Acceptance**: 4-shard cluster ≥ 100k put/sec (linear scaling vs single-shard); cross-shard scan completes
    within 2× single-shard time.
  - **Downstream**: W100 tags v1.0 with this in scope; chaos suite tests shard failure isolation; v2 vector-db
    would mirror this pattern but stops at single-node (per scope).
