  #### Phase 1 — Problem, prediction, design (~60 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `notes/99tue_raftkv_prediction.md`:

    - P3. Predicted outcome of "two replicas apply the identical 1M-op log on fresh `MiniDb` instances" —

  - *Mental model*: `RaftKv` is a **deterministic finite state machine** driven by a totally-ordered command
    log. Raft owns ordering + durability + leadership; the SM's only job is: given the same command sequence,
    produce byte-identical state on every replica, forever. Any non-determinism = silent split-brain that only
    surfaces at snapshot-ship time.

  - *Contract* (signatures only — never the body):
    ```rust
    #[derive(Serialize, Deserialize, Clone, PartialEq)]
    enum KvCommand {
        Put    { key: Vec<u8>, val: Vec<u8>, ts: u64 },          // ts is PROPOSER-supplied
        Delete { key: Vec<u8>, ts: u64 },
        TxnBatch { ops: Vec<KvOp>, commit_ts: u64 },             // commit_ts PROPOSER-supplied
    }
    trait StateMachine {                                          // consensus-raft's SM hook
        fn apply(&mut self, index: u64, cmd: &KvCommand) -> Result<(), ApplyError>;
        fn snapshot(&self) -> Result<Snapshot, SnapErr>;
        fn restore(&mut self, snap: Snapshot) -> Result<(), SnapErr>;
        fn applied_lsn(&self) -> u64;                             // read from INSIDE the checkpoint
    }
    struct RaftKv { node: RaftNode<KvCommand>, db: MiniDb }
    impl RaftKv {
        fn put(&self, k: Vec<u8>, v: Vec<u8>) -> Result<(), RaftKvError>;     // proposer stamps ts here
        fn read(&self, k: &[u8]) -> Result<Option<Vec<u8>>, RaftKvError>;     // via node.read_index()
    }
    enum RaftKvError { CrossShardNotSupported, NotLeader, Timeout }
    ```

  - *Back-of-envelope* (bar (b), but the numbers gate R7): single-node `MiniDb` put ≈ 2 µs (≈ 500 k/sec) when
    WAL fsync is group-committed. Raft commit adds one network round-trip to quorum (~150 µs LAN) + the
    follower-side WAL fsync. If every follower *also* fsyncs the mini-db WAL per entry (~25 µs) on top of the
    raft-log fsync, durability is paid **twice** — the cliff is fsync-per-entry (≈ 25 µs ⇒ ≈ 40 k apply/sec
    ceiling) vs batched/never-on-follower (≈ raft commit-bound). Target: 3-node ≥ 30 k put/sec (R7), read-index
    P99 ≤ 1 ms (R8).

  - **Requirements** R1..R11 — write in `notes/99tue_raftkv_design.md`:
    - R1. `KvCommand::{Put, Delete, TxnBatch}` serialized via bincode; byte-deterministic across replicas.
    - R2. `apply()` is strictly deterministic — NO `Instant::now()`, NO `SystemTime::now()`, NO `HashMap`
      iteration, NO RNG, NO thread-local read, NO concurrent SM access. All temporal info from the log payload.
    - R3. `apply()` runs in strict log-index order, single-threaded per partition. Concurrency comes from
      sharding only (Wednesday), never from within one SM.
    - R4. `snapshot()` captures a consistent point via mini-db's MVCC; ships versions ≤ snapshot ts together
      with `applied_lsn`.
    - R5. `restore()` wipes the data dir, rehydrates from snapshot + `applied_lsn`; raft replays from
      `applied_lsn + 1`.
    - R6. Linearizable read via `raft.read_index()` (Raft §6.4): leader confirms a quorum heartbeat, *then*
      reads local state at the current `applied_lsn`.
    - R7. 3-node cluster sustains ≥ 30 k put/sec (down from single-node ~500 k due to raft commit cost).
    - R8. Linearizable read P99 ≤ 1 ms.
    - R9. Replica determinism: replay the same log on 3 fresh `MiniDb` instances; manifest hashes
      byte-identical for a 1M-op log.
    - R10. `raft_replicated.rs` ≤ 600 LOC native (inheritance principle — delegate, don't re-implement).
    - R11. Cross-shard txn returns `Err(CrossShardNotSupported)` for v0.5; documented as v1.0+ work.

  - **Design walk-through** D1..D7 — answer in `notes/99tue_raftkv_design.md`; **no peeking** at TiKV
    `raftstore/.../peer.rs::apply` or etcd `applyAll` until Phase 3:
    - D1. Determinism table — enumerate the 5 non-determinism sources and the fix for each:

      | Source | Leaks via | Deterministic fix |
      |---|---|---|
      | wall clock | `Instant::now()` / `SystemTime::now()` in apply | ts from log payload (`KvCommand.ts`) |
      | map order | `HashMap` iteration (stable within a run, not across recompiles) | `BTreeMap` for any iterated state |
      | RNG | any `rand` call | seed from `index` (deterministic) or forbid |
      | thread-local | reading TLS in apply | none — apply must be a pure function of (state, cmd) |
      | IO timing | underlying DB does timing-dependent work | mini-db apply is synchronous + value-deterministic |

    - D2. WAL fsync redundancy: the raft log is already durable, so a follower fsyncing mini-db's WAL per
      entry is redundant. v0.5 keeps it for simplicity; the v0.7 optimization is `sync_log=false` on followers
      (TiKV pattern). Cost of the redundancy: ~25 µs per apply (one extra fsync). State it explicitly here — it
      is the perf trap that surfaces in Phase 2's throughput bench.
    - D3. Read-index protocol (Raft §6.4): leader receives Read → broadcasts a heartbeat to quorum → on
      majority ACK, reads local state at the current `applied_lsn`. Why not just read local immediately?
      (Leader may have *silently* lost leadership; a bare local read returns stale/forked data — not
      linearizable.)
    - D4. Snapshot during apply: if raft decides to snapshot mid-apply it can observe partial state. Fix:
      serialize apply and snapshot through the SM lock; `snapshot()` captures via mini-db's MVCC snapshot
      (ships versions ≤ snapshot ts), so it sees a consistent point even while apply continues.
    - D5. `applied_lsn` persistence: must be atomic with the apply itself. Where stored? (INSIDE the mini-db
      checkpoint — same fsync barrier.) What if `applied_lsn` persists but mini-db state doesn't, or vice
      versa? (Either way recovery replays from the last consistent point; *idempotent* apply makes the overlap
      safe — but only if the two share one fsync barrier.)
    - D6. `KvCommand::TxnBatch` carries `commit_ts`; apply opens a txn *at that ts*, applies all ops, commits.
      Why is `commit_ts` proposer-supplied, not generated at apply time? (Apply-time = each replica picks its
      own clock = non-deterministic. Proposer-supplied = identical across replicas.)
    - D7. **Pre-mortem (load-bearing)** — write the EXACT 6-step bad trace:
      1. Replica A applies entry I, mutates mini-db state in memory.
      2. A persists `applied_lsn = I` to its sidecar file (separate fsync).
      3. Power loss before mini-db's own checkpoint fsync lands.
      4. On restart A reads `applied_lsn = I` from the sidecar → tells raft "replay from I+1".
      5. But mini-db state is at I-1 (the I-th mutation was lost) → entry I is silently *skipped*.
      6. A's state now permanently diverges from B and C; surfaces only when A ships a snapshot at LSN J>I.
      Invariant that prevents it: `applied_lsn` lives INSIDE the mini-db checkpoint — both persist under one
      fsync barrier or neither does. If you can't write this trace, you can't prove D5 fixes it.

  - **Output**: `notes/99tue_raftkv_design.md` with R1–R11, D1–D7, the D1 determinism table, the D7 6-step
    bad-trace, and a read-index sequence diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~110 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `test_no_instant_now_in_apply` finds an `Instant::now` in metrics code:**
    - Symptom: scan hits `metrics::APPLY_LATENCY.observe(start.elapsed())` inside `apply()`.
    - Why: a *metric observation* is non-determinism-safe by itself, but it tempts you to read the value back
      into the SM; and even pure, it makes the static guard fail and trains the wrong habit.
    - Fix: metrics are pure observers, never read back into the SM; gate them
      `#[cfg(not(deterministic_apply))]` so the deterministic test profile elides them entirely.
    - Muscle: metrics are external-facing; never let an observation feed back into state. Reapplies at: W82
      matching-engine apply, W92 ledger apply, W100 chaos-soak metrics.

  - **(SENIOR) When `proptest_replica_determinism_1m_ops` diverges (replica A hash ≠ B), shrinking to a 3-op TxnBatch:**
    - Symptom: 3 replicas applied the identical log; A's manifest hash ≠ B's; counterexample is a small TxnBatch.
    - Why: apply stamped records with `Instant::now()`; A applied at 100 ns, B at 105 ns; mini-db's HLC folded
      a different ts into the version, so the materialized versions differ byte-wise.
    - Fix: ALL ts come from the log payload. `Put`/`Delete` carry `ts: u64`; `TxnBatch` carries
      `commit_ts: u64`; apply calls `txn.commit_at(commit_ts)` — never the wall clock.
    - Muscle: a deterministic SM has ZERO wall-clock dependencies; all temporal info travels in the log.
      Reapplies at: W100 chaos crash-restart, W92 ledger-deterministic apply, every Raft-backed system.

  - **(SENIOR) When `test_thin_layer_loc_under_600` reports `raft_replicated.rs` at 1200 LOC:**
    - Symptom: tokei shows 1200 LOC, ~600 over budget; the v0.5 inheritance ratio drops below 0.70.
    - Why: you re-implemented raft batching, snapshot serialization, and the read-index protocol inside the
      wrapper instead of calling the W67 crate.
    - Fix: delegate to `consensus_raft::RaftNode::{propose, read_index, snapshot, restore}`; local code is only
      the `KvCommand` definition + the `StateMachine` impl. If consensus-raft doesn't expose what you need, add
      it THERE, not here.
    - Muscle: the inheritance ratio is the audit's metric; a hard LOC budget forces delegation over copy-paste.
      Reapplies at: W100 mini-db v1.0 audit, W104 vector-db wrapper, every CAPSTONE wrapper module.

  - **(EXPERT) When `test_apply_lsn_persisted_with_state` shows double-apply (or a skipped entry) after restart:**
    - Symptom: crash after the in-memory apply but before persisting the sidecar `applied_lsn`; restart replays
      from 0; entries 0..N apply twice (or, in the mirror failure, one entry is skipped) → state corrupted.
    - Why: `applied_lsn` was tracked in a *separate* file, not committed atomically with mini-db state — the
      exact D7 pre-mortem.
    - Fix: persist `applied_lsn` INSIDE the mini-db checkpoint (same fsync barrier). On restart raft reads
      `applied_lsn` from mini-db and replays only entries > it. Apply is idempotent, so the at-most-one-overlap
      window is safe.
    - Muscle: dual persistence (lsn + state) is fragile; embed the cursor in the state it tracks, under one
      fsync barrier. Reapplies at: W92 ledger replica state, W100 chaos crash-restart, every Raft SM.

  - **(EXPERT) When `test_leader_kill_recovery` loses an "acked" put across failover (cross-primitive):**
    - Symptom: a put the client saw acked is absent on all survivors after the new leader takes over.
    - Why: `put()` returned success on *local* propose acceptance, before the entry was committed to a quorum;
      the old leader had it only locally and crashed before replication — classic premature-ack.
    - Fix: `put()` must await `RaftNode::propose().await_committed()` (quorum commit) before returning Ok;
      only quorum-committed entries may be reported acked.
    - Muscle: an ack means *durably replicated to quorum*, never *accepted locally* — the ack boundary is the
      correctness boundary. Reapplies at: W100 chaos failover assertions, W74 matching-engine raft replication.

  - **(EXPERT, perf — bar (b)-optional, gates R7) When `bench_3_node_throughput_30k_per_sec` reports ~5 k/sec:**
    - Symptom: the 3-node cluster delivers ~5 k put/sec against a 30 k target — ~6× under.
    - Why: every apply fsyncs mini-db's WAL on every follower (redundant — the raft log is already the
      durability source), and apply is per-entry rather than batched.
    - Fix: (a) on followers set `wal::SyncMode::Never` (raft log is the single durability source); (b) batch
      apply — consensus-raft v1.0 exposes batched apply; group N entries per fsync barrier.
    - Cost avoided: ~25 µs/apply (one redundant fsync) × ~100 k apply/sec ≈ 2.5 fsync-seconds burned per
      wall-second; throughput moves ~5 k → ~30 k. (Not a bar violation — mini-db is bar (b) — but it gates R7.)
    - Muscle: layered durability is redundant; pick ONE source of truth per layer and turn the rest off.
      Reapplies at: W82 matching-engine + raft, W100 chaos throughput floor, every Raft-backed DB.

  - *Mental model*: the router is a **pure, stateless function** `key → shard_id` that *every* client must
    compute identically. If two clients disagree on routing (different hash seed), writes become invisible to
    each other's reads — a silent partition with no error.
  - *Contract*:
    ```rust
    struct ShardRouter { n: usize, seed: u64, shards: Vec<RaftKv> }
    impl ShardRouter {
        fn new(shards: Vec<RaftKv>, seed: u64) -> Self;          // PANICS if seed unset / default
        fn route(&self, key: &[u8]) -> usize;                    // ahash(seed, key) % n
        fn scan(&self, range: Range<Vec<u8>>) -> Result<MergeIterator<'_>, ScanErr>; // k-way merged, ordered
    }
    enum ScanErr { ShardUnavailable { shard: usize } }
    ```
  - *Back-of-envelope*: ahash of a 32-byte key ≈ low tens of ns (negligible vs the ~150 µs raft commit it
    routes to). The cliff is *load skew*: raw `key % N` on sequential keys puts ~100% on one shard ⇒ that
    shard's raft group saturates while N-1 sit idle ⇒ effective throughput = single-shard, defeating the whole
    design. Hash-first flattens the distribution to ±10%.

  - **Requirements** R1..R8 — write in `notes/99wed_sharding_design.md`:
    - R1. Shard count fixed at cluster bootstrap; no online resharding in v0.5.
    - R2. Hash uses a stable explicit seed (ahash with explicit seed) so all clients agree on routing.
    - R3. Cross-shard ops merge client-side with NO transactional guarantees (documented).
    - R4. 4-shard cluster ≥ 100 k put/sec (≈ linear vs the 30 k single-shard floor).
    - R5. Cross-shard scan within 2× single-shard time.
    - R6. Put distribution ±10% across shards under random keys.
    - R7. Multi-shard scan globally ordered via `lsm_core::MergeIterator` (k-way merge).
    - R8. Shard failure: per-shard timeout; scan returns `Err(ShardUnavailable { shard })` (no hang).

  - **Design walk-through** D1..D3 — answer in the design doc; no peeking at TiKV `pd` routing until Phase 3:
    - D1. Primitive table — ahash-mod vs jump-consistent-hash:

      | Option | Resharding | Code size | Distribution | v0.5 choice |
      |---|---|---|---|---|
      | `ahash(seed,key) % N` | none (changing N reshuffles all keys) | tiny | even | ✅ (no resharding in scope) |
      | jump-consistent-hash | minimal key movement on N change | moderate | even | v1.0+ (when resharding needed) |

    - D2. Hash-first-then-mod: why not raw modulo? (Sequential / monotonic keys with raw `%N` all collapse to
      one shard; hashing first decorrelates the key from the shard, flattening the load.)
    - D3. **Pre-mortem (load-bearing)** — write the exact bad trace: client A constructs the router with
      `seed=42`; client B accidentally uses the ahash default seed; the SAME key routes to different shards;
      A's write lands on shard 1, B reads shard 3 and sees nothing — a silent split with no error surfaced.
      Guard: the seed lives in the cluster config and `ShardRouter::new` panics on construction if the seed is
      unset/default, so the misconfiguration fails loudly at startup, not silently at read time.

  - **Output**: `notes/99wed_sharding_design.md` with R1–R8, the D1 primitive table, and the D3 bad-trace.

  #### Phase 3 — Make the tests pass, one failure at a time (~25 min)

  - **(NEWBIE) When `test_sequential_keys_hash_distributed` shows 90% on shard 0:**
    - Symptom: sequential keys land mostly on shard 0; histogram wildly skewed; throughput collapses to single-shard.
    - Why: the route did `key.as_u64() % N` — monotonic keys map straight to consecutive shards, and a hot
      contiguous key range hammers one shard.
    - Fix: `ahash(seed, key) % N` — hash first (decorrelates key from shard), THEN modulo.
    - Muscle: never `% N` on a structured key; hash it first or accept hotspotting. Reapplies at: W104
      vector-db segment routing, W100 chaos load-balance assertions.

  - **(SENIOR) When `test_cross_shard_scan_globally_ordered` returns key 50 before key 10:**
    - Symptom: scan emits keys out of global order; per-shard runs are sorted but the union isn't.
    - Why: code concatenated per-shard scan results sequentially (shard0 then shard1 …) instead of merging.
    - Fix: feed each shard's sorted iterator into `lsm_core::MergeIterator` (k-way merge); the union is globally
      ordered in one pass.
    - Muscle: ordered union of sorted sources = k-way merge, never concatenation. Reapplies at: W104 vector-db
      multi-segment scan, W40 lsm-core compaction merge.

  - **(SENIOR) When `test_shard_failure_returns_err` hangs forever (caught by the 5 s harness timeout):**
    - Symptom: shard 2 has no quorum; the scan blocks on it indefinitely; the negative-control timeout fires.
    - Why: no per-shard timeout — the router waits on a dead raft group with no deadline.
    - Fix: per-shard deadline; on expiry return `Err(ShardUnavailable { shard })`; caller retries or accepts a
      partial result. Document partial-scan semantics in the API.
    - Muscle: every cross-node fan-out needs a per-target deadline; a missing deadline is a liveness bug, not a
      perf one. Reapplies at: W100 chaos partial-availability tests, W104 vector-db distributed scan.
