         (i) **"Walk me through how a Transfer commits in your ledger."**
             Client request → leader's `submit()` → encode as VsrOp → `replica.client_request()` → Prepare to backups → backups append to log (wal-durable) → PrepareOk back → leader quorum-acks → `state_machine.apply()` → static-mem Transfer pool allocates from pre-sized buffer → SM updates Account balances + invariant check → journal-iouring writes record (group-commit batch) → fsync barrier passes → reply to client. The amortized P99 at 100k Transfers/s is <1µs per record post-batching.

   12. **The "every dep was a deliberate choice" justification log** (record in `notes/ledger_v1_dep_choices.md`):
       - **time v0.5 over std::time**: monotonic-only abstraction prevents wall-clock from leaking into apply path. std::time::SystemTime is banned via clippy.
       - **wal v0.5 over RocksDB / sled / mdbx**: wal v0.5 is OUR primitive; consuming it is the inheritance principle. Embedded DBs would bring their own WAL + recovery, defeating the layering.
       - **recovery v0.5 separated from wal v0.5**: recovery is the replay logic; wal is the durable log. Decoupling allows recovery to evolve (e.g., parallel replay in v2.0) without touching wal.
       - **txn v0.5 separated from state_machine**: snapshot iterators (txn) are reusable; state_machine logic is ledger-specific. The split mirrors TigerBeetle's separation.
       - **runtime-thread-per-core v1.0 over tokio**: thread-per-core eliminates Send/Sync ceremony + lets us pin replica to core. tokio's work-stealing scheduler is anti-pattern for deterministic apply.
       - **consensus-vsr v1.0 over consensus-raft v1.0 for THIS crate**: VSR's view-change is single-round-trip; Raft's randomized election has unbounded tail. TigerBeetle uses VSR; we follow.
       - **mmap-queue v0.5 for outbound events**: zero-copy SPSC queue; matching engine's MBO emission feeds it; ledger consumes for cross-process settlement event delivery.
       - **bufpool v1.0 for VSR wire**: VSR message buffers must be reused; allocating per-message is alloc-on-hot-path violation.
       - **messaging-aeron v0.7 for Archive**: TigerBeetle uses its own archive format; we use Aeron Archive for the same role — durable, replayable event log fan-out.

    - **Why**: block-stm's storage backend is the multi-version concurrent data structure. Each storage slot can have multiple in-flight versions (one per executing tx); validation determines which is canonical. Without MVCC, parallel exec degenerates to locking. Mirror Aptos's `mvhashmap.rs` and the block-stm paper's "Estimate / Value / NoEntry" lifecycle.
    - *Back-of-envelope* (target: per-`read(key, tx_idx)` < 100 ns on a versioned slot with ≤8 versions; sustains the W91 per-tx RwSet budget of ~3-4 µs/tx):
      Per `read`: DashMap shard lookup (~30 ns avg under low contention) + BTreeMap range scan walking backward from tx_idx (~5 ns per node × log(K) nodes for K versions; K=8 → ~15 ns) + Entry-variant match (`Estimate`/`Value`/`Removed`) ≈ 2 ns. Total ~50 ns ✓. Per `write`: shard lookup + BTreeMap insert (~30 ns + ~20 ns) ≈ 50 ns. Per-slot memory budget: 8 versions × ~40 B per Entry = ~320 B; at 16k slots touched per block = ~5 MB per block — fits in L2. The MAX_VERSIONS=256 cap (W94 dep choice) is a safety net; actual mainnet blocks rarely exceed 8 versions per slot. Critical perf line: `dashmap::DashMap::get(...)` uses a hash → shard pick → bucket walk; at default 32 shards under USDC-heavy load, the hot-key shard becomes a serialization point (W91 perf #2).
    - **Read first**: Aptos `aptos-core/aptos-mvhashmap/src/lib.rs` (MVHashMap); block-stm paper §4 "Multi-Version Data Structure"; PostgreSQL's MVCC for general principles.
    - **Design**:
      ```rust
      pub struct VersionedMemory {
          slots: DashMap<StorageKey, VersionedSlot>,
      }
      pub struct VersionedSlot {
          versions: BTreeMap<u32, Entry>,    // key = tx_idx, sorted
      }
      pub enum Entry {
          Estimate { incarnation: u32 },             // tx idx is in-progress; read should treat as dependency
          Value { incarnation: u32, value: StorageValue },
          Removed { incarnation: u32 },
      }
      impl VersionedMemory {
          pub fn read(&self, key: &StorageKey, tx_idx: u32) -> ReadResult;
          pub fn write(&self, key: &StorageKey, tx_idx: u32, incarnation: u32, value: StorageValue);
          pub fn mark_estimate(&self, key: &StorageKey, tx_idx: u32, incarnation: u32);
          pub fn remove(&self, key: &StorageKey, tx_idx: u32);
      }
      pub enum ReadResult { Value(StorageValue, Version), DependsOn(u32 /*tx_idx*/), NoEntry }
      ```
      **Invariants**: (i) tx_idx N's read sees the highest committed/estimate at tx_idx M where M < N; (ii) Estimate is a DEPENDENCY signal — caller must wait or re-execute later; (iii) writes preserve full version history during exec, GC happens after block finalization; (iv) reads are O(log K) where K = versions per slot.
    - **Build steps**: 1. (~15 min) `VersionedSlot` BTreeMap setup with Entry enum. 2. (~30 min) `read(key, tx_idx)` walks BTreeMap.range(..tx_idx).rev(), returns first Value/Removed; if hits Estimate, returns DependsOn(its_tx_idx). 3. (~30 min) `write(key, tx_idx, incarnation, value)` inserts Entry::Value, replacing earlier (tx_idx, incarnation) or coexisting with other tx_idx entries. 4. (~25 min) `mark_estimate` flips Value→Estimate to invalidate later readers (used when tx is re-scheduled). 5. (~25 min) `remove(key, tx_idx)` for SLOAD-of-deleted semantics + GC. 6. (~25 min) GC pass: after block finalized, retain only the highest-tx_idx Value per slot, drop the rest. 7. (~15 min) `Snapshot` API: read-only view at a frozen tx_idx for parent state. 8. (~15 min) thread-safety: DashMap top-level + RwLock<VersionedSlot> per slot (or use crossbeam_skiplist for lock-free).
    - **Pitfalls**: *Version-chain growth*: **Symptom**: hot key has 100 versions per block, memory explodes. **Fix**: cap versions per slot at MAX_VERSIONS (e.g. 256); on overflow, escalate to sequential exec. *GC of obsolete versions*: **Symptom**: GC runs concurrently with next block exec, races. **Fix**: GC ONLY between blocks (sync barrier). *Snapshot-isolation anomalies*: **Symptom**: phantom-read across slot scans. **Fix**: scans take a tx_idx snapshot; all reads within that scan use it. *Estimate-deadlock*: **Symptom**: tx A's Estimate is dependency for tx B; tx B's Estimate is dependency for tx A. **Fix**: by construction tx_idx ordering means this can't happen — but assert in debug.
  - **Expect to hit (perf) #1 — `BTreeMap<u32, Entry>::range(..tx_idx).rev().next()` allocates a temporary iterator (bar (c)-ish violation)**: each `read` constructs a `Range` iterator over the BTreeMap, walks to find the highest version < tx_idx. The iterator's internal state (current node + ancestor stack) is allocated on the stack — but reversing the range (`rev()`) flips the walk direction and on some Rust versions allocates a small heap buffer (~16-32 B per call). At 1000 txs/block × ~50 reads/tx × 250-block/sec stress = 12M `read()`s/sec × ~30 ns potential heap = ~360 ms/sec. Worse: BTreeMap range iter has a non-trivial constant cost (~30 ns even without allocation) due to node traversal.
    - Fix: per-slot `versions: ArrayVec<VersionEntry, MAX_VERSIONS>` (sorted by `tx_idx` ascending), not `BTreeMap`. `read(tx_idx)` does a **binary search** for `tx_idx`, walks backward to find the first `Committed` (skipping `Estimate`). Binary search ≈ ~10 ns for K=8 versions; walk-back ≈ ~2 ns. Total ~12 ns vs ~30+ ns. Sorted-insert on `write` ≈ ~15 ns (binary search + ArrayVec memmove).
    - Cost avoided: ~20 ns/read × 12M reads/sec = ~240 ms/sec reclaimed. The headline 8-core speedup (≥2×, W94 SHIP gate) depends on this — BTreeMap's constant-factor overhead is what caps speedup at ~1.5× in a naive port of the block-stm paper.
    - Muscle: in tight read-path data structures with small K, contiguous-sorted-array + binary search beats BTreeMap and HashMap. The L1-cache-friendliness compounds: ArrayVec lives in one or two cache lines; BTreeMap nodes scatter across pages. Reapplies at: W92 ledger v1.0 state_hash sorted-iterate (already sorted-array shape), W82 matching-engine PriceLevel order queue (sorted by time, fixed shape), W89 ledger FixedMap (the W003 perf #3 reapplication).
  - **Expect to hit (perf) #2 — `Estimate` returned to reader instead of `DependsOn` (bar (c) violation: correctness AND perf)**: implementing `read` as "walk versions, return whatever the highest one is, whether Value or Estimate." Reader treats the Estimate as a real value, commits using it. Later that Estimate gets invalidated (its producing tx re-executes with different output) — but the reader has already committed using the stale Estimate. Result: validation phase doesn't detect the stale read, **block exec result diverges from sequential**. The W94 SHIP determinism gate (100/100 blocks byte-identical) fails.
    - Fix: `enum ReadResult { Value(StorageValue, Version), DependsOn(u32), NoEntry }`. On `Entry::Estimate { incarnation }`, return `DependsOn(its_tx_idx)`; caller (the block-stm scheduler) either (a) waits for that tx to complete and re-tries, or (b) records the dependency in its RwSet so validation will re-check after the dependency commits. Estimate value is **never** exposed to a reader as a concrete value.
    - Cost avoided: not headline perf (the DependsOn path adds ~50 ns scheduler-side); but **correctness** under parallel exec — without it, the determinism gate cannot pass and v1.5 is unshippable. Also: re-executions caused by Estimate→Value flips happen ~5-10× more without this discipline (reader committed on stale Estimate → invalidated → entire pipeline of downstream txs re-executes), so the perf cost of NOT having DependsOn is actually ~5 ms/block in cascading re-exec.
    - Muscle: in any MVCC-style "value in flight" system, the `InFlight` / `Estimate` state is **not** a value — it's a dependency edge in the tx-graph. Treating it as a value is the load-bearing correctness mistake. Reapplies at: W88 ledger VOPR `Pending` Transfer (not counted in `DoubleEntrySumZero` until Posted), W74 matching-engine pending-cancel order (not visible to matching algo until acked), W90 consensus-vsr Prepare (not committed until f+1 PrepareOks).
    - **Test scenarios**: parallel exec 1000 txs, 10% conflicts → versions per slot avg < 5; correctness: parallel result byte-identical to sequential. Stress: 1000 txs all writing same slot → MAX_VERSIONS triggers, falls back to sequential. Property test: ANY tx_idx schedule yields canonical post-state.
    - **Acceptance**: round-trip parallel exec equal to sequential on Ethereum block trace samples (W94 bench uses real block traces).
    - **Downstream**: W93 optimistic executor consumes this; W94 SHIP gates on this.
