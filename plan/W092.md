- [NEW v2] **Build (DEEPEST tier — concurrent MVCC data structure)**: `crates/exec-vm/src/parallel/versioned_memory.rs` — MVCC-style versioned key-value store; a tx reads the highest committed version < its tx_idx, or surfaces an in-flight write as a dependency edge. (~total 4h across 3 phases)
  - 🔧 **Why this matters**: this is block-stm's storage backend (Aptos `aptos-mvhashmap`, paper §4) — the multi-version concurrent map that lets K txs hold concurrent versions per slot; validation picks the canonical one. The 2 load-bearing traps: (1) **Estimate (in-flight write) is a dependency edge, NOT a value** — treating it as a value silently diverges parallel from sequential (a *correctness* bug that no single-thread test catches); (2) **per-read latency** — a naive `BTreeMap`-per-slot is correct but its node-scatter + iterator-construction cost (~30 ns constant) caps the 8-core speedup at ~1.5×, missing the W94 ≥2× gate (a *bar (c)* violation). Downstream: W93 optimistic executor, W94 exec-vm v1.5 SHIP, W91-Fri RwSet (this is the storage behind it). First-attempt impls fail ≥1 Phase-2 test below; the debug session IS the lesson.

  #### Phase 1 — Problem, prediction, design (~70 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/exec-vm/notes/92thu_versioned_memory_prediction.md` (compare to reality after Phase 2 tests run):
    - **P1** — the primitive you'd reach for per-slot version storage (write the exact import line, e.g. `use std::collections::BTreeMap;` vs `use arrayvec::ArrayVec;`).
    - **P2** — predicted per-read latency at K=8 versions, in ns, for your P1 choice. (Reality: BTreeMap ~80-150 ns; ArrayVec ~12 ns.)
    - **P3** — predicted concurrent-first-call outcome: under a USDC-heavy block where every write hits one DashMap shard, what is your effective parallelism? (1, K, or somewhere between?)
    - **P4** — derive-correctness prediction: when tx 2 reads a slot where tx 1 has an *in-flight* (Estimate) write, what should `read()` return — the older committed value, or something else?
    - **P5** — list EVERY Phase-2 test you predict your first attempt will fail. (If you predict zero, you have not understood the Estimate trap.)
  - *Mental model*: a per-slot stack of versions keyed by writer tx_idx; a reader at tx_idx N wants the highest *committed* version < N, but an *in-flight* version < N is a dependency it must surface, not consume.
  - *Contract* (signature-level — NEVER the body):
    ```rust
    pub struct VersionedMemory { slots: DashMap<StorageKey, VersionedSlot> }
    enum Entry { Estimate { incarnation: u32 },
                 Value { incarnation: u32, value: U256 },
                 Removed { incarnation: u32 } }
    enum ReadResult { Value(U256, Version), DependsOn(TxIdx), NoEntry }
    impl VersionedMemory {
        fn read(&self, key: StorageKey, tx_idx: TxIdx) -> ReadResult;
        fn write(&self, key: StorageKey, tx_idx: TxIdx, inc: u32, v: U256) -> Result<(), MaxVersionsExceeded>;
        fn mark_estimate(&self, key: StorageKey, tx_idx: TxIdx);
        fn snapshot(&self, tx_idx_max: TxIdx) -> Snapshot<'_>;
        fn gc_block_boundary(&self);   // sync barrier only
    }
    ```
  - *Back-of-envelope (bar c)*: per-tx budget from W91 ≈ 3-4 µs at 50 reads/tx ⇒ **per-read budget < 100 ns**. DashMap shard lookup ~30 ns (one main-mem hop, ~100 ns worst, ~30 ns amortized-hot) + version walk + variant match. At K=8 the walk must cost ≤15 ns. **Cliff ratio**: ArrayVec binary-search+walk ~12 ns vs BTreeMap range-iter ~30-150 ns = up to **12×**; over 12M reads/s (1000 tx × 50 reads × 240 blocks/s) the ~20 ns/read BTreeMap tax = **~240 ms/s** of wall-clock, which is exactly what caps the 8-core speedup below the W94 ≥2× gate.
  - **Requirements** R1..R10 — write in `crates/exec-vm/notes/92thu_versioned_memory_design.md`:
    - R1. `VersionedMemory { slots: DashMap<StorageKey, VersionedSlot> }`; per-slot `versions: ArrayVec<VersionEntry, MAX_VERSIONS=256>` sorted by tx_idx ascending.
    - R2. `read(key, tx_idx)` returns highest `Value` entry < tx_idx, OR `DependsOn(producing_tx)` if an `Estimate` < tx_idx is the highest entry, OR `NoEntry`.
    - R3. `Entry::{Estimate, Value, Removed}`; `Estimate` is NEVER returned as a `Value` to a reader.
    - R4. Per-read P50 ≤50 ns, P99 ≤100 ns on a slot with ≤8 versions.
    - R5. Per-write P99 ≤100 ns; sorted-ArrayVec insert via binary search + memmove.
    - R6. `MAX_VERSIONS=256` cap; on overflow return `Err(MaxVersionsExceeded)`; caller escalates the block to sequential exec.
    - R7. GC runs ONLY at block boundary (sync barrier); retains exactly the highest-tx_idx `Value` per slot.
    - R8. Parallel exec result byte-identical to sequential on sampled Ethereum block traces (the W94 determinism gate).
    - R9. `snapshot(tx_idx_max)`: read-only view filtered to versions < tx_idx_max (parent-state access).
    - R10. Thread-safety: DashMap shards; per-slot writes serialized; reads lock-free or short-lock.
  - **Design walk-through** D1..D11 — answer in the design doc; no peeking at `aptos-mvhashmap` or block-stm §4 until Phase 3:
    - D1. Primitive property table — fill it: `BTreeMap<u32,Entry>` (Sync via lock? range-iter latency? allocs on `.rev()`? blocking?) vs `ArrayVec<VersionEntry,256>` (latency? allocs? cache-line span?) vs `Vec<VersionEntry>` (alloc-on-grow? capacity churn?).
    - D2. Per-read budget at K=8 / K=64 (hot block) / K=256 (MAX). At K=256 the walk ~200 ns > budget → escalate.
    - D3. Entry lifecycle + why `incarnation` exists: write → `Value`; tx re-scheduled → `mark_estimate` → `Estimate`; re-execute → `Value`, `incarnation++`. `incarnation` distinguishes stale from current; the reader's RwSet captures `(tx, incarnation)` and the validator checks both.
    - D4. read() walking strategy: binary-search tx_idx, walk backward; first `Value` → `Value`; first `Estimate` → `DependsOn`; first `Removed` → `NoEntry`. Why NOT "skip Estimate and keep walking to a Value"? — answer in prose (this is the trap).
    - D5. `DependsOn` semantics: caller either (a) waits for the producer and retries, or (b) records the dependency in RwSet for re-validation. (a) better low-conflict; (b) better high-conflict.
    - D6. write() ordering: sorted by tx_idx via binary search; if `(tx_idx, incarnation)` present → replace in place.
    - D7. GC discipline: block-boundary only (concurrent GC races readers); any `Estimate` surviving GC = a tx that didn't finalize = bug, drop + loud-log.
    - D8. snapshot API: parent state at block N = post-state of N-1, locked at `tx_idx_max=0` of block N.
    - D9. **Cross-primitive cooperation (load-bearing)**: under a USDC-heavy block all writes hit one DashMap shard's lock → effective parallelism = 1. The W91-Fri hot-key classification (per-key RwLock bypass) must compose with this. Describe how versioned_memory cooperates: hot keys get their own slot path so the shard lock is not the serialization point.
    - D10. **Pre-mortem (load-bearing) — write the EXACT 6-step bad interleaving** where Estimate-as-Value diverges parallel from sequential: `USDC.balanceOf(Alice)`; tx 1 writes 90 as Estimate (in-flight); tx 2 reads, treats Estimate as value, commits 80; tx 1 invalidates, re-executes, writes 85; tx 2 already committed 80 on a phantom read. Parallel → 80; sequential (tx1=85 then tx2=75) → 75. **If you can't write this trace, you can't prove your design prevents it.** Fix: reader treats Estimate as `DependsOn`.

  #### Phase 3 — Make the tests pass, one failure at a time (newbie → expert)

  - **(NEWBIE) When `read_returns_dependson_not_skipped_committed` returns `ReadResult::Value(50, _)`:**
    - Symptom: read at tx_idx=6 returns `Value(50)` (the committed at tx 2) instead of `DependsOn(5)`.
    - Why: `read` walks backward, *skips* the `Estimate` at tx 5, returns the next `Value`. Naive "find latest committed" instead of "return the first entry seen, surfacing Estimate as a dependency edge."
    - Fix: return the FIRST entry walking backward — `Value` → `Value`, `Estimate` → `DependsOn(tx_idx)`, `Removed` → `NoEntry`. Never skip an Estimate.
    - Cost avoided: a *correctness* divergence (parallel ≠ sequential); the W94 determinism gate fails, and re-executions cascade ~5-10× (reader commits on a phantom Estimate → invalidated → downstream txs invalidate). (bar (c) violation — wrong result, not merely slow.)
    - Muscle: in any MVCC/optimistic system, the in-flight/Estimate state is a **dependency edge, not a value** — consuming it is the load-bearing correctness mistake. Reapplies at: W93 optimistic executor read-resolution, W88 ledger VOPR `Pending` Transfer (excluded from DoubleEntrySumZero until Posted), W74 matching-engine pending-cancel (invisible until acked), W90 consensus-vsr Prepare (uncommitted until f+1 PrepareOks).

  - **(NEWBIE) When `max_versions_overflow_returns_err_not_panic` panics:**
    - Symptom: writing the 257th version panics (`ArrayVec: capacity exceeded`) — executor down.
    - Why: no MAX_VERSIONS guard; `ArrayVec::push` past capacity panics.
    - Fix: `if slot.versions.is_full() { return Err(MaxVersionsExceeded { key, count: slot.versions.len() }); }`; caller re-schedules the block for sequential exec.
    - Cost avoided: a service-down panic vs a normal escalation path; one hot DeFi slot would crash every parallel block touching it.
    - Muscle: hot-path bounded collections need an explicit overflow ERROR + a fallback path; capacity-exceeded is normal control flow, never a panic. Reapplies at: W91-Fri RwSet `MAX_READS/MAX_WRITES`, W92 ledger `MAX_INFLIGHT` pool, W14 bufpool exhaustion.

  - **(SENIOR) When `gc_retains_only_highest_committed` leaves >1 entry:**
    - Symptom: after GC the slot has 3 entries (highest Value + 2 stray Estimates).
    - Why: GC drops only old `Value`s, not `Estimate`s. But an Estimate at GC time = a tx that didn't finalize before the block boundary = a bug that should not survive.
    - Fix: GC retains exactly one entry — highest-tx_idx `Value`. Any surviving Estimate → loud-log + drop; add a `debug_assert` during exec that all txs finalize before the boundary.
    - Cost avoided: stale Estimates leaking into the next block → phantom DependsOn edges → spurious re-executions next block.
    - Muscle: GC at a sync barrier = clean slate; in-flight state surviving the barrier is a correctness signal, not garbage to silently keep. Reapplies at: W92 ledger snapshot GC, W82 matching-engine session-end cleanup, W47 epoch-gc reclaim boundary.

  - **(EXPERT) When `parallel_result_byte_identical_to_sequential` minimizes to a counterexample block:**
    - Symptom: property test shrinks to a ~10-tx block; parallel post-state differs by one slot.
    - Why (ranked): (1) Estimate-as-Value (the NEWBIE card above); (2) write-ordering — a later tx's write landed before an earlier tx's in the sorted ArrayVec; (3) over-eager GC dropped a `Value` still needed by a live snapshot.
    - Fix: bisect by root cause — Estimate → apply the DependsOn fix; ordering → `debug_assert!(slot.is_sorted_by_key(|e| e.tx_idx))` on every insert; GC → make GC respect active snapshots.
    - Cost avoided: parallel-exec correctness; "looks right under typical load" is not a proof — the counterexample is ground truth. (bar (c) violation if it ships — silently wrong block exec.)
    - Muscle: parallel-exec correctness is property-testable against a sequential oracle; trust the minimized counterexample over intuition. Reapplies at: W94 v1.5 SHIP correctness gate, W91-Fri RwSet validation, W104 mini-db CAPSTONE concurrent-compaction equivalence.

  - **(EXPERT, perf — bar (c) violation) When `read_under_100ns_at_k8` reports ~80-150 ns at K=8:**
    - Symptom: per-read P50 ~80 ns, P99 ~150 ns — over the 100 ns budget. Profile: ~30 ns in `BTreeMap` range-iter + ~20 ns iterator construction (and `.rev()` allocates ~16-32 B on some rustc versions).
    - Why: per-slot `versions: BTreeMap<u32, Entry>`; each `read` builds a `Range` iterator and walks scattered nodes — non-trivial constant cost regardless of K.
    - Fix: per-slot `versions: ArrayVec<VersionEntry, 256>` sorted ascending; `read` does binary-search (~10 ns at K=8) + walk-back (~2 ns) = ~12 ns.
    - Cost avoided: ~20 ns/read × 12M reads/s = **~240 ms/s** reclaimed; the BTreeMap constant tax caps the 8-core speedup at ~1.5×, missing the W94 ≥2× gate. (bar (c) violation — disqualifies the W94 SHIP.)
    - Muscle: for tight read-path structures with small K, contiguous sorted-array + binary search beats BTreeMap/HashMap — L1-friendliness compounds (ArrayVec in 1-2 cache lines; BTreeMap nodes scatter across pages). Reapplies at: W92 ledger `state_hash` sorted-iterate, W82 matching-engine `PriceLevel` order queue, W89 FixedMap (W003 perf #3 reapplied), W104 mini-db memtable small-range scan.

  - **(EXPERT, negative-control) When `read_bench_physically_plausible` reports p50 <3 ns or throughput >5e8/s:**
    - Symptom: the latency bench shows sub-L1 numbers — the read got constant-folded out of the loop.
    - Why: LLVM hoisted the `read(K, 8)` (loop-invariant inputs) out of the loop; the bench measured nothing, so `read_under_100ns_at_k8` "passed" by accident.
    - Fix: `black_box` both the key and the result each iteration; vary the reader tx_idx so the call is not loop-invariant.
    - Cost avoided: a green latency gate that proves nothing — the BTreeMap regression would ship undetected. (bar (c) violation — the gate is the thing that protects the bar.)
    - Muscle: every perf gate needs a paired negative-control that fails when the bench measures a no-op; a too-fast result is a broken bench, not a fast impl. Reapplies at: every criterion bench in the plan (W004 CachePadded ping-pong, W90 io_uring journal, W94 8-core speedup gate).

  - **(EXPERT, loom) When `loom_versioned_memory_must_be_slow` finishes in <100 ms:**
    - Symptom: the loom model returns near-instantly — it explored ~1 interleaving.
    - Why: the reader/writer don't actually share loom atomics/locks (real `std` types used under `#[cfg(loom)]`), so loom sees no interleaving points.
    - Fix: gate the shared state behind `#[cfg(loom)] use loom::sync::{Arc, RwLock}; ... #[cfg(loom)] use loom::sync::atomic::*;` so every shared access is a loom exploration point.
    - Cost avoided: a loom test that "passes" while exploring nothing — the torn/partial-version race ships unverified.
    - Muscle: a lock-free/short-lock custom structure needs loom verification AND a slow-negative-control proving loom explored a real state space. Reapplies at: W004 AtomicHash, W11 bounded MPMC, W37 skiplist, W90 consensus-vsr message handlers.
