  - *Mental model*: a `MemTable` is a **write-hot sorted in-memory container with tombstone semantics** that
    freezes and flushes to an SSTable when it crosses a size threshold. A delete is an *insert of a Tombstone*,
    never a removal — the tombstone must outlive the key so it can suppress the same key in older levels until the
    deepest compaction elides it.
  - *Contract* (signatures only — never the body):
    ```rust
    pub type Key = Bytes;
    pub enum ValueOrTombstone { Value(Bytes), Tombstone }
    pub struct SizeShards { shards: [CachePadded<AtomicUsize>; 16] }
    pub struct MemTable { skip_list: SkipMap<Key, ValueOrTombstone>, size: SizeShards }
    impl MemTable {
        pub fn put(&self, k: Key, v: Bytes);          // inserts Value
        pub fn delete(&self, k: Key);                  // inserts Tombstone — NEVER remove
        pub fn get(&self, k: &[u8]) -> Option<ValueOrTombstone>;
        pub fn approximate_size(&self) -> usize;       // lazy sum of shards
        pub fn scan(&self, lower: Bound<&[u8]>, upper: Bound<&[u8]>) -> MemTableIterator; // holds EBR guard
        pub fn freeze(self) -> Arc<MemTable>;          // immutable handoff for flush
    }
    ```
  - *Back-of-envelope* (bar (b) — sizing the two cliffs so we know which design choices are load-bearing, not a
    sub-µs latency budget):
    - **Value-clone cliff**: `Value(Vec<u8>)` clone = malloc (~50 ns) + memcpy of N bytes (1 KB ≈ 1 µs at ~1
      GB/s/core). `Value(Bytes)` clone = one Arc refcount bump ≈ **3 ns** (an L1-resident atomic increment).
      Cliff ratio at 1 KB ≈ `1 µs / 3 ns ≈ 300×`. At 1 M put/sec × 1 KB the `Vec` path moves **~1 GB/sec**
      through malloc+memcpy — the allocator, not the skiplist, becomes the bottleneck.
    - **Counter-contention cliff**: a single `AtomicUsize::fetch_add` under contention costs a cache-line
      ping-pong ≈ **~100 ns** (cross-core RFO, main-mem class) per bump; 16 threads serialize on that one line →
      ~10 M bumps/sec ceiling regardless of how fast the skiplist is. Sharded across 16 `CachePadded` counters,
      each thread hits its own line (~25 ns uncontended fetch_add) → contention disappears. Lazy O(16) sum at
      flush time is ~16 cache reads ≈ amortized free (flush fires once per ~64 MB of writes).
  - *Anti-shortcut audit* — name the tempting-but-wrong move (each is exactly what a Phase-2 test below traps):
    - **Use `Value(Vec<u8>)` because "it owns its bytes and clones cleanly".** Wrong HERE: the LSM clones values
      on every read and on flush; owned `Vec` makes each clone a malloc+memcpy. → trapped by
      `memtable_value_type_is_bytes_not_vec` + `bench_memtable_put_no_per_op_alloc`.
    - **Model the size as one `AtomicUsize` and slap `CachePadded` on it to "fix contention".** Wrong HERE:
      `CachePadded` fixes *false* sharing (neighbors on the same line); the contention here is *true* sharing —
      every thread writes the *same* counter. → trapped by `bench_memtable_16_threads_scales`.
    - **Implement `delete(k)` as `skip_list.remove(k)` because "delete means remove".** Wrong HERE: removal
      destroys the suppression signal; the same key in an older SSTable resurfaces. → trapped by
      `memtable_delete_returns_tombstone_not_none`.
    - **Model the payload as `Option<Bytes>` (None = deleted).** Wrong HERE: `None` is indistinguishable from
      "key never existed at this level"; a tombstone is a *positive* assertion of deletion that must be flushed
      and merged. → trapped by `memtable_delete_returns_tombstone_not_none` + the merge-iterator tie-break (Tue).

  - **Requirements** — write in `crates/lsm-core/notes/38_memtable_design.md`:
    - R1. `put(k, v)` inserts `Value(Bytes)` into the SkipMap; `delete(k)` inserts `Tombstone`.
    - R2. **Tombstone semantics**: deletes are inserts of a `Tombstone` variant; they suppress lower-level reads
      until the tombstone is elided at the deepest compaction level. `get` returns `Some(Tombstone)`, never `None`,
      for a deleted key still resident in the memtable.
    - R3. **Value type is `Bytes` (Arc-backed)** — zero-copy clone; `Value(Vec<u8>)` is forbidden.
    - R4. **Size counter is sharded** — `SizeShards { shards: [CachePadded<AtomicUsize>; 16] }`; thread-id
      hash picks the shard for bumps. Flush threshold check sums all shards lazily.
    - R5. ≥ 1 M put/sec single-thread; ≥ 5 M/sec aggregate at 16 threads (beats `Arc<RwLock<BTreeMap>>` by
      ≥ 2× at 4 threads).
    - R6. Scan is bounded-cost; long flush scans operate on a frozen (immutable) memtable handoff to avoid
      stalling writers.
    - R7. Zero allocations on put after the one skiplist-node alloc (the single malloc per put inherited from W37).

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  Ordered newbie → expert: the ladder you actually walk.

  - **(SENIOR) When `memtable_delete_returns_tombstone_not_none` reports `None`:**
    - Symptom: after `delete(k)`, `get(k)` returns `None`; W39's flush test later reports ghost reads (an older
      SSTable still serves `k`).
    - Why: you implemented `delete` as a SkipMap `remove` (or modeled the payload as `Option<Bytes>`). Removal
      destroys the suppression signal — the memtable no longer "knows" lower levels must be shadowed for `k`.
    - Fix: tombstone is a value *variant*, never a remove. `delete(k)` calls `skip_list.insert(k, Tombstone)`.
      Flush writes the `Tombstone`; the SSTable reader returns it; the query layer reads `Tombstone` as "deleted"
      and stops the LSM lookup chain at this level.
    - Muscle: in an LSM, a tombstone is a first-class *positive* value, not absence-of-value; deletes are inserts.
      Reapplies at: W39 SSTable writer (must serialize the tombstone variant), W40 STCS compaction (tombstone
      retention/elision rules), W95 `mini-db` query path (chain-stop on tombstone).
  - **(EXPERT) When `bench_memtable_put_no_per_op_alloc` reports 2 allocations per put:**
    - Symptom: at 1 M put/sec the allocator counter shows ~2 M allocs/sec; flamegraph dominated by `malloc` and
      `__memcpy_avx_unaligned`. Throughput plateaus at ~500 k/sec from allocator contention. (`bench_..._band_is_plausible`
      also drops *below* the 3e6 floor — a useful confirmation the band test bites.)
    - Why: the value variant is `Value(Vec<u8>)`, so every put copies the caller's buffer (or re-allocs from a
      slice). At 1 M put/sec × 1 KB ≈ 1 GB/sec of malloc traffic → the allocator + heap fragmentation become the
      bottleneck even though the skiplist is fast.
    - Fix: `Value(Bytes)` (`bytes::Bytes`, Arc-backed) — zero-copy clone. Callers pass `Bytes` from already-shared
      buffers (Tokio reads, RPC bodies); for owned-then-shared, `Bytes::from(vec)` is one move + Arc-bump (~3 ns).
      The Tombstone variant is a no-payload tag — free.
    - Cost avoided: at 1 KB × 1 M put/sec ≈ **1 GB/sec of malloc+memcpy+free** → ~1–3 CPU-seconds/sec recovered +
      heap fragmentation eliminated; clone cost drops from ~1 µs to ~3 ns (≈300×).
    - Muscle: value types in hot containers use Arc-backed clones (`Bytes`, `Arc<[u8]>`), not owned `Vec<u8>`.
      Reapplies at: W39 SSTable block value, W42 `txn` write-set, W74 matching-engine order payload, W77 aeron
      frame payload.
  - **(EXPERT) When `bench_memtable_16_threads_scales` reports the counter as the bottleneck (16-thread throughput
    ≤ 2× single-thread):**
    - Symptom: 16-thread bench plateaus at ~2 M put/sec (vs ≥ 5 M expected); flamegraph shows `size.fetch_add`
      dominating. Adding `CachePadded` to the single `AtomicUsize` does NOT help.
    - Why: `CachePadded` cures *false* sharing (independent data sharing a line). Here it's *true* sharing — every
      thread writes the same counter, so the line ping-pongs (RFO ≈ ~100 ns/bump) and 16 threads serialize on it.
    - Fix: per-thread size shards summed lazily. `SizeShards { shards: [CachePadded<AtomicUsize>; 16] }`; a
      thread-id hash picks the shard index; `fetch_add` hits the thread's own line (~25 ns uncontended). The flush
      check does one O(16) sum (cheap, rare).
    - Cost avoided: ~100 ns/bump cross-core ping-pong → ~25 ns local fetch_add; lifts the 16-thread ceiling from
      ~2 M to ≥ 5 M put/sec (≈2.5–3×).
    - Muscle: counter sharding is the canonical fix for "the atomic on the hot path *is* now the hot path";
      `CachePadded` ≠ contention cure. Reapplies at: W74 matching-engine fill-counter, W77 aeron position
      publishing, W95 `mini-db` per-shard size accounting.

    becomes mainstream, the memtable can be a persistent log instead of in-memory; flush becomes a pointer flip
    instead of a copy. **Trigger** (measurable): PMem random-write latency drops below DRAM + the WAL fsync cost.
    **Migration** (1 line): introduce a `PMemMemTable` variant behind a feature flag; `freeze()` becomes a
    metadata commit rather than a scan-and-copy.

  #### Phase 1 — Problem, prediction, design (~50 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/lsm-core/notes/38_iterator_prediction.md` BEFORE any code:
    - P1. The exact trait you'll derive/impl for `HeapEntry` ordering (`#[derive(PartialOrd)]` vs hand-written
      `impl Ord`) and which `cmp` field order you'll write. Predict which Phase-2 test the derive choice fails.
    - P2. Predicted warm 4-way merge output rate (M output/sec) and the 10-way rate — within 2×.
    - P3. **Tie-break prediction**: with source 0 = memtable (newest), if you write the tie-break as
      `source_idx` *descending*, predict what `merge_tombstone_from_newer_source_wins` observes (which value emits).
    - P4. Derive-correctness: does `#[derive(PartialOrd)]` on `HeapEntry` give a *total* order? Predict the heap's
      behavior on a pair whose `partial_cmp` you assume can never be `None`.
    - P5. **List every Phase-2 test you predict your first attempt will fail.** Compare to reality after tests run.
  - *Mental model*: a `MergeIterator` **merges N sorted streams into one sorted output**, and on equal keys keeps
    the *newest* (lowest `source_idx`). The subtlety is the tie-break direction — getting it wrong is silent
    because the data still flows; only a deleted key's reappearance reveals it.
  - *Contract* (signatures only — never the body):
    ```rust
    pub trait KvIterator {
        fn key(&self) -> &[u8];                 // panics if !is_valid
        fn value(&self) -> &ValueOrTombstone;
        fn is_valid(&self) -> bool;
        fn next(&mut self);
        fn seek(&mut self, target: &[u8]);
    }
    struct HeapEntry<I> { key: Bytes, source_idx: usize, iter: I }
    impl<I> Ord for HeapEntry<I> { /* by key asc, then source_idx asc */ }   // hand-written, NOT derived
    pub struct MergeIterator<I: KvIterator> { heap: BinaryHeap<Reverse<HeapEntry<I>>>, current: Option<HeapEntry<I>> }
    impl<I: KvIterator> KvIterator for MergeIterator<I> { /* ... */ }
    ```
  - *Back-of-envelope* (bar (b) — sizing the merge so we pick a heap, not why it must be sub-µs): a binary heap of
    N entries does `log2(N)` comparisons per `next()`. N = 4 → 2 cmps; N = 100 → ~7 cmps. Each cmp is a couple of
    `memcmp` on short keys, branch-predictable when streams are long — call it ~5–10 ns/`next()` warm for N = 4.
    50 M output/sec ⇒ ~20 ns budget/output, comfortably met by an L1-resident heap with **zero allocation after
    construction**. Implication: the heap must be built once and re-pushed in place; any per-`next()` `Box`/`Vec`
    growth blows the budget. The 10× cliff is not latency but *correctness*: a reversed tie-break costs 0 ns and
    silently resurrects deleted keys.
  - *Anti-shortcut audit* — each is what a Phase-2 test below traps:
    - **`#[derive(PartialOrd, Ord)]` on `HeapEntry` and "trust the field order".** Wrong HERE: a careless derive
      (or `PartialOrd`-only) can leave the order partial or in the wrong field order; the heap silently drops rows.
      → trapped by `merge_ord_not_partialord` + `merge_two_streams_sorted_output`.
    - **Pop the winner and move on (don't touch the other equal-key entries).** Wrong HERE: the duplicates stay in
      the heap and re-emit on the next pop. → trapped by `merge_advance_past_equal_no_duplicates`.
    - **Push every inner iter into the heap after `seek`, valid or not.** Wrong HERE: exhausted iters pop and
      `key()` panics. → trapped by `merge_seek_filters_exhausted_iters`.

  - **Requirements** — write in `crates/lsm-core/notes/38_iterator_design.md`:
    - R1. `MergeIterator` wraps a min-heap over `HeapEntry { key, source_idx, iter }`.
    - R2. Output is strictly sorted ascending by key.
    - R3. **Tie-break: lower `source_idx` wins** — source 0 = memtable (newest); higher idx = older levels.
      Equal-key entries with higher idx are advanced past silently (not emitted).
    - R4. **`Ord` implemented by hand** (not `#[derive(PartialOrd)]`-only) — both `key` and `source_idx` are total.
    - R5. **Advance-past-equal discipline** — after emitting one entry for key K, every other heap entry with key K
      is advanced (`next`) and re-pushed (or discarded if exhausted).
    - R6. Tombstones flow through unchanged — the caller is responsible for suppression downstream.
