- [ ] **Build**: `crates/lsm-core/src/memtable.rs` —
  `MemTable { skip_list: concurrent::SkipMap<Key, ValueWithTombstone>, size: AtomicUsize }`. Consumes the lock-free
  concurrent skiplist built in W37 (mirror of `crossbeam-skiplist`, EBR-backed). Skyzh's `Arc<RwLock<BTreeMap>>`
  design from tutorial Day 1 is the baseline you must beat under ≥4 concurrent writers; if your skiplist doesn't
  win at 4 threads, EBR overhead is mistuned (revisit W37 Fri bench). (~150 min)
  - **Why**: The memtable is the LSM's write-side hot path; every put goes through it. RocksDB and the academic LSM literature consistently pick a concurrent skiplist as the memtable structure because: (a) sorted iteration for flush; (b) O(log N) ops with no global lock; (c) bounded fanout makes EBR reclamation cheap. The tombstone-bearing value type is key — deletes don't remove from the memtable, they insert a tombstone that suppresses lower-level reads.
  - *Back-of-envelope*: **target ≥ 1 M put/sec single-thread, ≥ 5 M/sec aggregate at 16 threads** (skiplist + sharded size counter). Per put: skiplist insert ≈ ~200 ns at n=1 M warm (W37 numbers); size shard bump ≈ ~10 ns. Tombstone is one bit inside `ValueOrTombstone` — no extra allocation. Memtable size threshold (typically 256 MB) triggers freeze → flush; the rotated immutable memtable is what W39 Wednesday flushes. Steady state: zero allocations after the skiplist node alloc (one malloc per put — see W37 perf pitfall on inline-tower layout).
  - **Read first**: `mini-lsm` Week 1 Day 1; RocksDB `memtable/skiplistrep.cc`; the W37 `concurrent::skiplist` you just built.
  - **Design**:
    ```rust
    pub enum ValueOrTombstone {
        Value(Bytes),
        Tombstone,
    }
    pub struct MemTable {
        list: concurrent::SkipMap<Key, ValueOrTombstone>,
        size: SizeShards, // 16 shards of AtomicUsize, sum on flush check
        id: MemtableId,
    }
    impl MemTable {
        pub fn put(&self, key: Key, val: Bytes);
        pub fn delete(&self, key: Key);
        pub fn get(&self, key: &[u8]) -> Option<ValueOrTombstone>;
        pub fn scan(&self, range: impl RangeBounds<Key>) -> MemtableIter<'_>;
    }
    ```
    **Invariants**:
    - Per-key, the most recent write (put or tombstone) is observed by get.
    - Tombstone is not erased from the memtable; it must be flushed to L0 to suppress older SSTables.
    - size is a lower bound (sharded counter, summed only when needed).
  - **Build steps**:
    1. (~25 min) Type plumbing: Key = `Bytes`, Value enum, sized accounting via `mem::size_of_val(key) + size_of_val(val)`.
    2. (~50 min) `put`/`delete`: insert into the SkipMap (delete inserts `Tombstone`); bump size shard chosen by thread-id hash.
    3. (~30 min) `get`: SkipMap lookup; return inner Option.
    4. (~30 min) `scan`: range iterator over SkipMap; yields (key, ValueOrTombstone) pairs.
    5. (~15 min) Tests as listed below.
  - **Pitfalls**:
    - *Atomic counter as bottleneck*: under the LSM write path, `size: AtomicUsize` becomes the hot atomic. **Symptom**: 16-thread benches plateau on the counter, not the skiplist. **Fix**: per-thread/per-shard size; sum lazily. **Reapplies at**: matching-engine fill counter (W74), aeron position publishing (W77).
    - *Forgotten tombstone semantics*: implementing `delete` as a SkipMap remove loses the suppression signal — older SSTable still serves the key. **Symptom**: ghost reads after delete. **Fix**: tombstone is a value variant, never a remove.
    - *Iterator stalls writers*: a long-running scan holds an EBR guard, preventing memtable rotation. **Symptom**: write stalls. **Fix**: scan documented as bounded-cost; long flush scans operate on a frozen (immutable) memtable handoff.
  - **Test scenarios**:
    - 10k puts + 10k deletes interleaved; scan returns only put-only-not-deleted keys (after tombstone suppression).
    - Concurrent: 4 threads, 100k mixed ops; final state matches a single-thread reference.
    - Property: tombstones survive flush (verified in W39 SSTable writer test).
  - **Acceptance**:
    - 4-thread mix bench beats `Arc<RwLock<BTreeMap>>` by ≥2x.
    - Inheritance ratio: consumes `concurrent`, `bufpool` for size shards.
  - **Downstream**: W39 flush_memtable_to_l0 reads from this; W40 STCS compaction merges flushes; W95 mini-db memtable layer.
  - **Expect to hit (perf) #1 — `Value(Vec<u8>)` allocates per put (bar (c) violation)**: declaring the value variant as `Value(Vec<u8>)` instead of `Value(Bytes)` means every put either copies the caller's buffer or re-allocates from a slice. At 1 M put/sec with 1 KB avg value, that's ~1 GB/sec of malloc traffic — the allocator (and downstream heap fragmentation) becomes the bottleneck even though the skiplist itself is fast.
    - Fix: `Value(Bytes)` (`bytes::Bytes`, Arc-backed). Zero-copy clone. Callers pass `Bytes` from already-shared buffers (Tokio reads, RPC bodies). For owned-then-shared, `Bytes::from(vec)` is one move + Arc-bump, ~30 ns. Tombstone variant is a no-payload enum tag — free.
    - Cost avoided: at 1 KB values × 1 M put/sec ≈ 1 GB/sec of malloc + free → ~1-3 seconds of CPU/sec recovered + heap fragmentation eliminated.
    - Muscle: value types in hot containers use Arc-backed clones (`Bytes`, `Arc<[u8]>`), not owned `Vec<u8>`. Reapplies at: W39 SSTable block value, W42 `txn` write-set, W74 matching-engine order payload, W77 aeron frame payload.
  - **Expect to hit**: under the LSM write path, the memtable's `size: AtomicUsize` is bumped on every insert.
    On 16-thread bench, the atomic counter becomes the bottleneck — CachePadded on `size` doesn't help because
    the contention is *on the counter itself*, not false-sharing.
    **Fix**: per-thread size shards; sum lazily when the flusher needs the total. **Muscle**: counter sharding
    is the canonical fix for "atomic on a hot path is now the hot path." **Reapplies at**: matching-engine
    fill-counter (W74), messaging-aeron position publishing (W77).

**Tuesday — `lsm-core` merge iterator**

- [ ] **Build**: `crates/lsm-core/src/iterator.rs` — `MergeIterator<I: KvIterator>` k-way merge via a min-heap over (
  key, source_idx, value). Tie-break by source_idx (newer wins). (~150 min)
  - **Why**: LSM reads must merge across the memtable + all L0 + per-level SSTables. K-way merge with a binary heap is O(log k) per output element; the alternative (cascading 2-way merge) is O(k) and dominates for k>4. The merge iterator is the reusable primitive used everywhere reads cross sorted streams: query path, compaction, snapshot iteration. Tie-break ordering is consensus-critical for LSM semantics: newer source wins, so tombstones from L0 correctly suppress values in L1.
  - *Back-of-envelope*: k-way merge via binary heap = O(log k) per output element. **Target: ≥ 50 M output/sec on warm 4-way merge** (memtable + 3 SSTs in L0/L1); ≥ 20 M/sec on 10-way merge (L0 fan-out scenarios at compaction). Per step: heap pop + source advance ≈ ~20 ns; equal-key suppression adds amortized ~5 ns. **Zero allocations after heap construction**. Heap size = number of sources (typically 4-10); fits entirely in L1. The same primitive powers reads (query path) AND writes (compaction merge stream) — the per-op cost compounds.
  - **Read first**: RocksDB `iterator/merging_iterator.cc`; `mini-lsm` Week 1 Day 2.
  - **Design**:
    ```rust
    pub trait KvIterator {
        fn key(&self) -> &[u8];
        fn value(&self) -> &ValueOrTombstone;
        fn next(&mut self) -> Result<bool>;
        fn is_valid(&self) -> bool;
    }
    pub struct MergeIterator<I: KvIterator> {
        heap: BinaryHeap<HeapEntry<I>>,
        // source_idx is the tiebreaker: lower idx = newer.
        current: Option<HeapEntry<I>>,
    }
    struct HeapEntry<I: KvIterator> { source_idx: u32, iter: I }
    // Ord impl: compare by key asc; then by source_idx asc (newer wins on equal key).
    ```
    **Invariants**:
    - Output is sorted strictly ascending by key.
    - On equal keys across sources, only the lowest-source_idx entry is emitted; others are advanced past silently.
    - Tombstones are emitted (caller decides to suppress).
  - **Build steps**:
    1. (~25 min) Trait `KvIterator` + adapter for `MemtableIter`.
    2. (~50 min) Heap entry comparator: min-heap on (key, source_idx).
    3. (~40 min) `next` core loop: pop min; record key; advance all entries with same key; only the kept (lowest-idx) result is yielded.
    4. (~25 min) `seek(key)`: each source seeks; rebuild heap.
    5. (~10 min) Tests as below.
  - **Pitfalls**:
    - *Tie-break direction wrong*: if source 0 is oldest (not newest), tombstones don't suppress and stale data wins. **Symptom**: deleted keys reappear. **Fix**: document and enforce — source 0 = memtable (newest); higher idx = older levels.
    - *Heap entry comparison via PartialOrd*: PartialOrd allows None comparisons → heap behavior undefined. **Symptom**: missing rows in output. **Fix**: implement `Ord` directly; `key` and `source_idx` are both total.
    - *Forgotten advance-past-equal*: leaving non-kept equal-key entries in the heap will re-emit them on next `pop`. **Symptom**: duplicate keys in output. **Fix**: on equal key, advance the inner iterator and re-push to heap.
    - *Iterator validity check after seek*: post-seek some iterators are exhausted; pushing exhausted ones into heap will pop garbage. **Fix**: filter `is_valid()` before push.
  - **Test scenarios**:
    - Merge 4 sorted streams of 1k each, with overlapping keys; output is 1k unique keys with newer-source values winning.
    - Tombstone test: source 0 has tombstone for key K; sources 1-3 have values for K; output emits tombstone, value is suppressed.
    - Property: merge of N streams equals merge of any partition.
  - **Acceptance**: 4-way merge of 1M total keys < 100ms; output strictly sorted; tombstone suppression correct.
  - **Downstream**: W39 SST read path (multi-block merge); W40 STCS compaction (merge tiered SSTables); W42 txn snapshot reads.

**Thursday — Zstd compression in reth + lsm-core block design**

- [ ] How reth uses compression. (~30 min)
- [ ] **Build**: `crates/lsm-core/src/block.rs` — `Block { offsets: Vec<u16>, data: Bytes, restart_interval: u16 }`.
  Restart-point compression (LevelDB-style). (~150 min)
  - **Why**: SSTable blocks are 4-32KB chunks of sorted KV pairs. To shrink storage and reduce I/O, adjacent keys share a common prefix; only the diff from the prior key is stored. "Restart points" mark every Nth key as full (no prefix elision), enabling binary search within the block. This is the LevelDB/RocksDB block format and is the workhorse compaction primitive.
  - *Back-of-envelope*: 4-32 KB block; restart_interval typically 16. **Target: ≥ 100 k entries/sec encode, ≥ 1 M entries/sec decode (iter)** on 1 KB-key workload. Per-entry encode: 3× varint (~5 ns) + memcpy (~20 ns for 1 KB value). Per-entry decode: 3× varint + prefix-restore ≈ ~30 ns warm. Compression ratio with restart_interval=16: typically **3-5× for sorted keys with shared prefixes** (user-id prefixed, timestamp prefixed). Seek-within-block: O(log restart_count) compare + O(restart_interval) linear ≈ ~200 ns warm.
  - **Read first**: LevelDB `table/block_builder.cc`; RocksDB `table/block_based/block_builder.cc`.
  - **Design**:
    ```rust
    pub struct BlockBuilder {
        buf: BytesMut,           // accumulated key entries
        restarts: Vec<u16>,      // offsets of full-key entries
        last_key: BytesMut,
        counter: u16,            // entries since last restart
        restart_interval: u16,
    }
    pub struct Block { bytes: Bytes }
    // Entry encoding: varint(shared_prefix_len) + varint(unshared_len) + varint(value_len) + unshared_key_bytes + value
    ```
    **Invariants**:
    - Entries in a block are key-sorted.
    - Every `restart_interval` entries is a "full" entry (shared=0).
    - Block trailer is `restarts.len() : u32` + `restarts : [u32; N]`.
  - **Build steps**:
    1. (~30 min) Encoder: prefix-compute, varint-encode tuple, append.
    2. (~30 min) Restart bookkeeping; emit full key when counter==interval or block empty.
    3. (~40 min) Decoder iterator: scan entries, restoring full keys by sharing.
    4. (~30 min) Seek-within-block: binary search on restart points; linear scan within restart group.
    5. (~20 min) Tests + bench.
  - **Pitfalls**:
    - *Varint overflow*: keys >65k bytes break u16-based varint. **Symptom**: silent truncation, decoder reads wrong length. **Fix**: u32 varints throughout, or assert max key size.
    - *Seek correctness on prefix-shared keys*: binary search comparing partially decoded keys (with prefix elided) is wrong. **Symptom**: missed reads. **Fix**: search operates on restart-point full keys; linear scan with full reconstruction within group.
    - *Restart interval too small*: 1 = no compression; too large (>64) = expensive seek. **Fix**: default 16, tunable.
  - **Test scenarios**:
    - Encode 1k keys with common prefix; block bytes < 1/4 raw size.
    - Round-trip: encode + decode → equal.
    - Seek to random target: O(log N) restart compare + O(restart_interval) linear, returns correct entry.
  - **Acceptance**: encode 100k entries < 50ms; decode iter 1M entries < 100ms.
  - **Downstream**: W39 SST builder consumes Block; W40 compaction reads SST blocks.
