This is a career landing week, not a Build week. There is no crate, no upstream mirror, and no engineered trap-test arc — manufacturing one would be padding. The week's job is to convert the first weeks at the new firm into recorded, reviewable artifacts: a written 30/60/90 success contract, a codebase-map document, a logged question budget, and a first merged PR. Every item below carries an explicit artifact file + an Output line that proves it done; the two learning/maintenance items (Tuesday codebase deepening, Saturday Reth/Tempo) carry a hardened-acceptance pass criterion and a mental model of why the item exists now. Personal-project maintenance is deliberately capped — your scarcest resource this month is onboarding bandwidth, and the highest-leverage move is shipping internally, not extending the portfolio.

**Monday — Manager 1:1**

- [ ] Artifact: `onboarding/30_60_90.md`. In the first 1:1, ask your manager directly: "What does success look like at 30, 60, and 90 days?" Capture the answer verbatim, then translate each into a concrete, checkable criterion (e.g. "60d: owns one service end-to-end" → "60d: I can deploy + roll back service X without supervision"). Record who owns each criterion and how it will be measured at review time. (~30 min)
  - 🎯 Hardened acceptance: `onboarding/30_60_90.md` has exactly three dated horizons (30/60/90), each with ≥2 criteria, each criterion phrased as an observable outcome (not "learn the codebase" but "merged ≥3 PRs touching service X"); every criterion tagged with its owner and its measurement. No vague aspirations survive the translation pass.
  - *Mental model*: a manager's unspoken success bar is the single largest source of first-90-days anxiety and the most common cause of a quiet bad-fit signal. Writing it down in the first 1:1 converts an ambiguous expectation into a contract you can self-audit against weekly — and it feeds directly into W136's mid-month self-review, where you check progress against these exact lines. Asking on day one also signals seriousness, which is itself a positive first-impression artifact.
  - Output: `onboarding/30_60_90.md` exists with three horizons × ≥2 owned, measurable criteria each; `grep -c '^- ' onboarding/30_60_90.md` ≥ 6.
- [ ] Commit + log. (~10 min)
  - Output: `git log -1 --oneline` shows the Monday 1:1 commit referencing `onboarding/30_60_90.md`.

**Tuesday — Codebase deepening**

- [ ] Artifact: `onboarding/codebase_map.md`. Whatever the first project/service is, build a map you can navigate from memory: the top-level module boundaries, the request/data flow through the system, the build + test + deploy commands, and the 3-5 files you'd touch most. Be a sponge — the goal this month is breadth of orientation, not depth of mastery. Record open questions inline as `Q:` lines to feed Thursday's question budget. (~30 min)
  - 🎯 Hardened acceptance: `codebase_map.md` documents (a) ≥3 named module/service boundaries with one line each on responsibility, (b) one end-to-end data/request flow traced through ≥3 of those boundaries, (c) the exact build/test/run commands you ran yourself (not copied from a wiki untested), and (d) ≥3 `Q:` open-question lines. Every command listed must have actually been executed locally this week.
  - *Mental model*: the fastest way to stop being a net drain in month one is a private map that lets you answer "where does X live?" without interrupting a teammate. Tracing one real data flow end-to-end teaches more architecture than reading ten design docs, because it forces you to discover the gaps the docs paper over — and those gaps become Thursday's high-value questions while your "new person" budget is still highest.
  - Output: `onboarding/codebase_map.md` exists meeting all four acceptance clauses; build/test commands recorded were run locally (terminal history confirms).
- [ ] Commit + log. (~10 min)
  - Output: `git log -1 --oneline` shows the Tuesday codebase-map commit.

**Wednesday — Continue**

- [ ] Artifact: `onboarding/codebase_map.md` (extend). Continue the orientation pass: resolve ≥1 of yesterday's `Q:` lines by reading code (not asking yet — save asks for Thursday), and add a "first-PR candidates" section listing 2-3 small, safe, shippable changes you spotted (typo, missing test, stale doc, small refactor). These become Friday's PR shortlist. (~30 min)
  - 🎯 Hardened acceptance: ≥1 prior `Q:` line is now resolved (struck through with a one-line answer + the file/commit that answered it), and a "first-PR candidates" section lists 2-3 changes, each with the file path and a one-line scope estimate confirming it is genuinely small.
  - *Mental model*: resolving your own questions by reading source before escalating builds the judgment that separates "asks good questions" from "asks lazy questions" — and it pre-stocks Friday's PR shortlist so the first-merge isn't a last-minute scramble. A merged PR in week one is mostly a function of having scouted a safe target early.
  - Output: `onboarding/codebase_map.md` shows ≥1 resolved `Q:` and a 2-3 item first-PR-candidates section with file paths.
- [ ] Commit + log. (~10 min)
  - Output: `git log -1 --oneline` shows the Wednesday continuation commit.

**Thursday — Ask many questions**

- [ ] Artifact: `onboarding/questions_log.md`. The stupid-questions budget is highest in week 2-3 — spend it deliberately. Batch the unresolved `Q:` lines from your codebase map and ask them (in the right channel, batched not drip-fed). Log each: question, who/where asked, the answer, and whether it revealed a doc gap worth a PR. (~30 min)
  - 🎯 Hardened acceptance: `questions_log.md` records ≥3 asked questions, each with {question, channel/person, answer, doc-gap? yes/no}; ≥1 answer is converted into either a `codebase_map.md` correction or a new first-PR candidate. Questions are batched into ≤2 interactions, not scattered across the day.
  - *Mental model*: the "new person" license to ask basic questions decays fast — by month two the same question reads as inattention. Cashing it in now, batched and logged, both accelerates your ramp and turns answers into reusable artifacts (map corrections, doc-gap PRs) instead of one-off Slack messages that vanish. Logging also lets you spot patterns: repeated questions in one area signal where the docs (and your eventual contribution) are weakest.
  - Output: `onboarding/questions_log.md` has ≥3 logged Q&A entries, ≥1 converted to a map fix or PR candidate.
- [ ] Commit + log. (~10 min)
  - Output: `git log -1 --oneline` shows the Thursday questions-log commit.

**Friday — First merged PR at new firm**

- [ ] Artifact: the PR itself + `onboarding/first_pr.md`. Pick one item from Wednesday's first-PR-candidates shortlist — small but it ships. Follow the firm's PR-review and CI conventions (consult their CONTRIBUTING / PR template, lookup-when-stuck). Record in `onboarding/first_pr.md`: the PR link, what it changed, the review turnaround, and any convention you tripped on (so it's a one-time lesson). (~30 min)
  - 🎯 Hardened acceptance: a real internal PR is opened (and merged, or at minimum approved + queued) against the new firm's repo; `onboarding/first_pr.md` records the PR URL, the diff scope in one line, CI status, and ≥1 firm-specific convention learned. A draft that never opens does not count — the deliverable is a shipped change, however small.
  - *Mental model*: the first merged PR is the credibility inflection point of month one — it proves you can navigate the build, the review process, and the CI gauntlet, and it converts you from "new hire" to "contributor" in the team's mental model. Keeping it small de-risks the first exposure to their conventions; the point is the round-trip through their process, not the size of the diff. This is the concrete artifact that retires the backup-job milestone gate (W24-30): a paid, shipped contribution at the destination firm.
  - Output: `onboarding/first_pr.md` records a merged-or-approved internal PR URL + scope + CI status + ≥1 convention learned.
- [ ] Commit + log. (~10 min)
  - Output: `git log -1 --oneline` shows the Friday first-PR commit referencing `onboarding/first_pr.md`.

**Saturday — Personal projects: light maintenance**

- [ ] Artifact: `outreach/log_reth_reviews.md` (extend). One Reth PR review from the open queue — keep the portfolio presence alive without cutting into onboarding bandwidth. Pick a PR in an area you already know (storage/exec/consensus), leave one substantive, specific review comment, and log it: PR link, area, the substantive point you raised. (~150 min)
  - 🎯 Hardened acceptance: exactly one Reth PR reviewed with ≥1 substantive comment (a correctness/perf/design point, not a nit), logged in `outreach/log_reth_reviews.md` with PR link + area + the point raised. "LGTM" without a substantive comment does not satisfy the acceptance.
  - *Mental model*: month one at the new firm is when your open-source visibility is most at risk of going dark — a single substantive review per week keeps the Reth relationship warm and your name in the contributor graph at near-zero cost, which is the inbound channel the entire career arc was built on. Reviewing (not authoring) is the right tool now: it is bounded, asynchronous, and demonstrates judgment without competing with the firm's deadlines.
  - Output: `outreach/log_reth_reviews.md` has a new entry with the Saturday PR link + area + substantive point; `git log -1 --oneline` (in the plan repo) shows the review logged.
- [ ] [Tempo] Artifact: `notes/tempo_maintenance_log.md` (extend). If Tempo is still in maintenance mode, one focused skim: check the issue/PR queue for anything touching your prior contributions, and recall (from memory, before opening docs) the 1-2 Tempo features most relevant to your new firm's work. Log: what changed since last skim, ✓/✗/~ on the feature recall, and whether any item needs follow-up. (~30 min)
  - 🎯 Hardened acceptance: `notes/tempo_maintenance_log.md` records the date, ≥1-2 features recalled from memory and tagged ✓/✗/~ against the live source, and an explicit "no action needed" or a follow-up item. A ✗ on a long-decayed feature is expected and is the signal of what to re-cement, not a failure.
  - *Mental model*: Tempo is in maintenance mode now, so the goal is decay-detection, not deepening — a brief recall-then-verify loop surfaces what you've forgotten before it embarrasses you in a maintainer thread, and confirms nothing in your prior contributions has regressed. Capping it at 30 min keeps maintenance from crowding out the firm's first-month ramp, which is this month's actual priority.
  - Output: `notes/tempo_maintenance_log.md` has a dated entry with feature recall tags + a no-action/follow-up decision.
- [ ] Commit + log. (~10 min)
  - Output: `git log -1 --oneline` shows the Saturday maintenance commit covering the Reth review + Tempo skim.
