- [ ] **Build**: `crates/wal/src/segment.rs` — `Segment` is an mmap-backed file with header
  `{ magic, version, segment_id, first_lsn }`, body of length-prefixed records, footer `{ last_lsn, checksum }`. Default
  segment size 64 MiB. Pre-allocated. (~105 min)
  - **Why**: Segment files are the *durability granule*. They're pre-allocated (fallocate) so writes never need to extend the file (avoiding metadata fsync). Bounded size enables truncation (rotate old segments out of disk). Mmap lets the kernel coalesce dirty pages; explicit msync gives commit barriers. This layout is canon in WAL design — used by RocksDB, Aeron Archive, Chronicle Queue, Postgres.
  - **Read first**: Aeron Archive `aeron-archive/src/main/java/io/aeron/archive/Archive.java` for segment-file rotation; RocksDB `db/log_writer.cc` for header/record framing; Chronicle Queue `chronicle-queue/src/main/java/net/openhft/chronicle/queue/impl/single/SingleChronicleQueueStore.java`. Linux `man 2 fallocate` and `man 2 madvise`.
  - **Design**:
    ```rust
    pub struct Segment {
        path: PathBuf,
        file: File,                     // RW-opened, fallocated to 64 MiB
        mmap: MmapMut,                  // shared mmap, MAP_SHARED
        header: SegmentHeader,          // first 64 bytes of mmap
        write_offset: AtomicUsize,      // tail pointer (relative to body start)
        first_lsn: Lsn,                 // immutable after header init
        last_durable_lsn: AtomicU64,    // updated after each msync
    }
    #[repr(C)]
    pub struct SegmentHeader {
        magic: [u8; 8],                 // b"WALSEG01"
        version: u32,
        flags: u32,
        segment_id: u64,
        first_lsn: u64,
        body_offset: u32,               // = 64
        body_len: u32,                  // = 64 MiB - 64 - footer
        _reserved: [u8; 24],
    }
    pub struct RecordFrame {
        len: u32,                       // record body length
        crc32: u32,                     // CRC32C over (lsn, kind, payload)
        lsn: u64,                       // monotonically increasing
        kind: u8,
        _pad: [u8; 7],
        // payload follows: len bytes
    }
    ```
    **Invariants**:
    - Segment file size == declared size at all times after creation (pre-allocated).
    - `write_offset` only advances; never rewinds.
    - `first_lsn <= every record's lsn < first_lsn + body_len / min_record_size`.
    - On open, magic byte sequence must match; if not, segment is junk/wrong-version → reject.
    - Body region is initialized to zeros at fallocate-time; a zero `len` field marks EOF/tail.
  - **Build steps**:
    1. (~15 min) `SegmentHeader` `#[repr(C)]` + `as_bytes` / `from_bytes` helpers. Use `bytemuck::Pod`.
    2. (~15 min) `Segment::create(dir, segment_id, first_lsn, size)` — open file, `set_len`, `fallocate(FALLOC_FL_KEEP_SIZE | FALLOC_FL_PUNCH_HOLE)` for sparse-then-fill OR straight `set_len` and write header.
    3. (~15 min) `Segment::open(path)` — mmap, validate header magic, infer `write_offset` by scanning records OR reading footer if intact.
    4. (~20 min) `Segment::append(record: &[u8]) -> Option<Lsn>` — bump `write_offset` atomically (CAS), write frame header + body, return `None` if not enough space (caller rotates).
    5. (~15 min) `Segment::msync(&self, range: Range<usize>) -> io::Result<()>` — flush a sub-range; default to `MS_SYNC`.
    6. (~15 min) `Segment::scan(&self) -> SegmentIter` — iterator over records; stops at zero-len frame or checksum mismatch.
    7. (~10 min) Tests: open existing segment, append until full, reopen, scan all records back.
  - **Pitfalls**:
    - *Pre-allocation cost*: `fallocate` on a 64 MiB file can take 50-200 ms on slow disks. **Symptom**: segment-rotate stalls writers. **Fix**: pre-allocate the NEXT segment in the background while still writing the current one. Maintain a 2-deep ready-pool.
    - *Torn writes at segment boundary*: a record written half here, half mmap-out-of-bounds. **Symptom**: panic/SIGBUS on read-back. **Fix**: `append` rejects records that wouldn't fit entirely; caller advances to the next segment.
    - *mmap vs write() coherence on Linux*: writing via mmap then reading via `read(2)` on the same fd can return stale data on some kernels. **Symptom**: scanner misses just-written records on rare configurations. **Fix**: always read from mmap, never via fd; document the constraint.
    - *Magic-byte version skew*: bumping format breaks all existing segments. **Symptom**: open fails on upgrade. **Fix**: version field in header; runtime upgrade path migrates segment-by-segment.
    - *Atomic write_offset under contention*: many producers race on `compare_exchange`. **Symptom**: live-lock under N>32 producers. **Fix**: use `fetch_add` with reservation: each producer reserves `len + frame_overhead`, then writes into its reserved range; reservations succeed monotonically.
    - *Reserved-but-unwritten window*: producer reserves space then crashes before writing. **Symptom**: scan sees garbage at that offset. **Fix**: CRC-on-record + zero-init body; scanner treats CRC mismatch on a non-zero-len frame as torn-write tail.
  - **Test scenarios**:
    - Append 1M small records (32 bytes each); reopen; scan returns all 1M in order.
    - Append until segment is exactly full; next append returns `None`.
    - Crash injection: SIGKILL the process at random offsets; reopen, scan returns all records up to the last *complete* CRC-valid frame.
    - Concurrency: 16 producer threads × 100k records each; `write_offset` ends at exact expected value, no overlap, no gaps.
    - Adversarial: open a file with wrong magic → error, not panic.
  - **Acceptance**:
    - Append throughput single-threaded ≥ 1 M records/sec (32-byte payload).
    - Concurrent append (16 threads) ≥ 5 M records/sec aggregate.
    - Crash-recovery property test passes 1000 random fault injections.
  - **Downstream**: Tuesday's group-commit consumes `Segment::append`; Wednesday's replay consumes `scan`; W27 storage-trie wal integration; W29 recovery analysis/redo walks segments; W64 raft uses identical layout for replicated log; W80 ledger reuses pre-allocation + group-commit pattern.
- [ ] **Build**: `crates/wal/src/record.rs` — `WalRecord { lsn: u64, kind: RecordKind, payload: Bytes }`. RecordKind
  enum (Insert, Update, Delete, Begin, Commit, Abort, Checkpoint). (~105 min)
  - **Why**: The record is the *unit of durability*. Its fields are dictated by the recovery algorithm — ARIES needs `lsn`, `prev_lsn`, `tx_id`, `kind`, `payload`, `undo_next_lsn` for CLRs. Get this struct wrong and W29 recovery is unbuildable. The discriminated union of RecordKind is the only place where future record types (e.g. compensation, checkpoint) can be added without breaking older readers (forward compat via reserved kind bits).
  - **Read first**: ARIES paper §3 ("Log Records"); PostgreSQL `src/include/access/xlogrecord.h`; RocksDB `db/log_writer.h`; etcd `wal/wal.go` (the etcd WAL is a simpler model worth contrasting).
  - **Design**:
    ```rust
    #[repr(u8)]
    pub enum RecordKind {
        // Tx control
        Begin       = 0x01,
        Commit      = 0x02,
        Abort       = 0x03,
        // Data
        Insert      = 0x10,
        Update      = 0x11,
        Delete      = 0x12,
        // Recovery
        Checkpoint  = 0x20,
        CLR         = 0x21,  // Compensation Log Record (ARIES undo)
        EndCheckpoint = 0x22,
        // Reserved for forward compat
        _Reserved   = 0xFF,
    }
    pub struct WalRecord {
        pub lsn: Lsn,                   // monotonically increasing
        pub kind: RecordKind,
        pub tx_id: Option<TxId>,        // None for non-tx records (e.g. Checkpoint)
        pub prev_lsn: Option<Lsn>,      // ARIES: chain within a tx
        pub undo_next_lsn: Option<Lsn>, // ARIES: only set on CLRs
        pub payload: Bytes,
    }
    ```
    **Invariants**:
    - `lsn` is strictly monotonic across all records in a wal.
    - For a given `tx_id`, the chain `current.prev_lsn -> prev.lsn` walks all records of that tx in reverse.
    - First record of a tx has `prev_lsn = None`; Commit/Abort has `prev_lsn = last_data_record`.
    - CLRs always have `undo_next_lsn` set; non-CLRs have it as `None`.
    - `payload` semantics depend on `kind`: Insert/Update payload = `(table_id, key, value)`; Delete = `(table_id, key, old_value_for_undo)`; Checkpoint = serialized DPT+TT.
  - **Build steps**:
    1. (~10 min) `RecordKind` enum with explicit discriminants; `TryFrom<u8>` rejecting unknown.
    2. (~15 min) `WalRecord` struct + builder.
    3. (~20 min) Wire format: serialize to a `bytes::BytesMut` with: lsn(8), kind(1), flags(1), tx_id(8|0), prev_lsn(8|0), undo_next(8|0), payload_len(4), payload. `flags` encodes which optional fields are present.
    4. (~20 min) Deserialize symmetric; reject unknown kinds with `RecordError::UnknownKind`.
    5. (~15 min) Encoder/decoder benchmarked: ≥ 10 M records/sec single-threaded encode.
    6. (~15 min) Property tests: encode → decode → encode byte-identical for any `WalRecord` value.
    7. (~10 min) Forward-compat test: write a record with reserved kind, decode with older parser → returns `Skipped`, not error.
  - **Pitfalls**:
    - *Tx_id None vs zero*: if you use `u64 = 0` as "no tx", tx_id 0 collides. **Symptom**: a Checkpoint record looks like it belongs to tx 0. **Fix**: `Option<TxId>` with explicit flag bit.
    - *Enum repr*: forgetting `#[repr(u8)]` lets the compiler choose; switching toolchains shifts discriminants. **Symptom**: old segments unreadable after toolchain update. **Fix**: explicit `#[repr(u8)]` + explicit discriminant numbers.
    - *Bytes vs Vec<u8>*: storing payload as `Vec<u8>` means every group-commit allocates. **Symptom**: alloc traffic dominates wal cost. **Fix**: `Bytes` (Arc-backed) so callers can pass shared slices.
    - *Backward-incompatible field add*: adding `tx_id` later without flag bit breaks segment readers. **Symptom**: nothing decodes after upgrade. **Fix**: `flags: u16` bitmap; flag bit per optional field; new fields = new flag bits.
    - *Variable encoding pitfalls*: varint for lengths sounds appealing but costs CPU on hot path. **Symptom**: parse throughput drops 30%. **Fix**: stick with fixed-size little-endian.
  - **Test scenarios**:
    - 1M random records: encode+decode round-trip; byte-identical.
    - Adversarial: truncated record (last 5 bytes missing) → decoder returns `Truncated`, not panic.
    - Forward-compat: future-kind record (0xFE) → decoder skips with diagnostic.
    - ARIES chain: 100 records of a single tx; walking prev_lsn chain yields all 100 in reverse.
  - **Acceptance**:
    - Inheritance ratio ≥ 0.9 vs ARIES record schema.
    - Encode ≥ 10 M rec/s; decode ≥ 5 M rec/s.
  - **Downstream**: every wal user; W29 ARIES analysis pass walks records via this schema; W64 raft replication packages these into AppendEntries RPCs; W80 ledger uses the same record header.

**Tuesday — `wal` group commit + [NEW] `concurrent::SegQueue` build**

- [ ] **Build**: `crates/concurrent/src/queue/seg_queue.rs` — `SegQueue<T>` unbounded MPMC, linked segments of N=32
  slots. Head and tail are `CachePadded<AtomicPtr<Segment>>`. Each segment carries a per-slot seq (same Vyukov idea as
  the bounded channel, per-segment). Memory reclamation: simple atomic refcount per segment for now; once `epoch-gc`
  lands W33, swap to `Guard::defer_destroy`. (~150 min)
  - **Expect to hit #1**: current segment fills. Multiple producers race to allocate the next segment. Naive: each
    allocates its own, all CAS the `next` pointer, only one wins — losers leak their `Box`.
    **Fix**: try `next.load(Acquire)` first; allocate only on null; on CAS failure, `Box::from_raw` your loser and
    drop it explicitly.
  - **Expect to hit #2**: consumer pops the last item of segment S. S is now empty. Who frees it? If you `Box::drop`
    while a producer still holds a stale `head` reference, UAF.
    **Fix**: refcount: producers and consumers bump on linkage, decrement on departure. Only refcount-zero segments
    are freed. (W33+: migrate to `Guard::defer_destroy`; refcount becomes redundant.)
  - **Expect to hit #3**: segment `next` pointer stored `Relaxed`. Consumer follows non-null `next` and reads slot 0
    of the new segment, expecting initialized memory — but on weak hardware, the producer's seg-header init may not
    be visible yet. UAF or torn read.
    **Fix**: `next.store(new, Release)`; readers `next.load(Acquire)`.
  - **Muscle**: "who owns the node, when does it die" is the central question of every lock-free DS. Refcount
    answers it eagerly; EBR answers it lazily by epoch. Today you build the refcount answer so you have a baseline
    to bench against EBR in W33. **Reapplies at**: skiplist node reclamation (W37, via EBR), matching-engine order
    pool (W74).
- [ ] **Build**: `crates/wal/src/group_commit.rs` —
  `GroupCommit { pending: SegQueue<(WalRecord, oneshot::Sender<Lsn>)>, fsync_signal: Notify }`. Background fsync
  thread drains every 10 µs or 1024 records. Producers fan in lock-free; the fsync thread is the single consumer. (~150 min)
  - **Why**: A single fsync costs 50-1000 µs on NVMe. At 100k records/sec naïvely, that's 100k fsyncs/sec — impossible. Group commit amortizes: 100k records → 1k batches → 1k fsyncs/sec, each carrying 100 records. The pattern is canonical: PostgreSQL `XLOG_BUFFER_FLUSH`, Aeron `ConductorAgent`, Chronicle Queue's `TextWire`. Mistakes here are correctness bugs (durability lost) or latency bugs (caller waits 10 ms for an fsync).
  - **Read first**: PostgreSQL `src/backend/access/transam/xlog.c` (`XLogFlush`, `XLogBackgroundFlush`); RocksDB `db/db_impl/db_impl_write.cc` (the `WriteBatch` group); your own `concurrent::SegQueue` from earlier today. Also the Aeron paper §4 on batched-publication.
  - **Design**:
    ```rust
    pub struct GroupCommit {
        pending: SegQueue<Pending>,
        durable_lsn: AtomicU64,             // monotonic high-water mark
        durable_notify: Notify,             // wakes waiters when durable_lsn advances
        shutdown: AtomicBool,
        config: GroupCommitConfig,          // { max_batch, max_delay_us, fsync_mode }
    }
    struct Pending {
        record: WalRecord,
        // Fast path: caller awaits a Notify gated on durable_lsn >= record.lsn.
        // No oneshot in steady state — Notify + atomic is cheaper.
    }
    
    impl GroupCommit {
        pub async fn append(&self, record: WalRecord) -> Lsn {
            let lsn = record.lsn;  // assigned by upstream Lsn allocator
            self.pending.push(Pending { record });
            // Wait until durable_lsn >= lsn.
            loop {
                if self.durable_lsn.load(Acquire) >= lsn { return lsn; }
                self.durable_notify.notified().await;
            }
        }
        
        // Run on a dedicated thread (NOT on the executor) to avoid blocking the runtime.
        fn flush_loop(&self, segment: &mut Segment) {
            let mut batch: Vec<WalRecord> = Vec::with_capacity(self.config.max_batch);
            loop {
                // Drain up to max_batch OR wait up to max_delay_us
                while let Some(p) = self.pending.try_pop() {
                    batch.push(p.record);
                    if batch.len() >= self.config.max_batch { break; }
                }
                if batch.is_empty() { thread::sleep(Duration::from_micros(self.config.max_delay_us)); continue; }
                // Serialize+append all records under one segment write.
                for r in &batch { segment.append(r.encode()); }
                segment.msync(..).expect("fsync");
                // Advance durable watermark to the max LSN in the batch.
                let max_lsn = batch.iter().map(|r| r.lsn).max().unwrap();
                self.durable_lsn.store(max_lsn, Release);
                self.durable_notify.notify_waiters();
                batch.clear();
            }
        }
    }
    ```
    **Invariants**:
    - `durable_lsn` is monotonically increasing.
    - For any LSN L, `append(record_with_lsn_L)` returns only after the fsync that covers L completes.
    - The fsync thread is the *unique* fsync caller — never call fsync from producers.
    - On graceful shutdown, all pending records are durably written before exit.
  - **Build steps**:
    1. (~15 min) `Pending` struct + `GroupCommitConfig`.
    2. (~25 min) `append` API using `durable_notify`. Test against a mocked Segment that records all msyncs.
    3. (~30 min) `flush_loop` background driver: pop batch, append to segment, msync, advance watermark, notify.
    4. (~20 min) Wire up the Lsn allocator: a separate `AtomicU64` `next_lsn`; producers `fetch_add` to claim.
    5. (~15 min) Shutdown sequence: set `shutdown`, drain pending, final flush, join thread.
    6. (~15 min) Tests: 16 producers × 10k records → all durable, watermark monotone.
    7. (~10 min) Bench: throughput vs batch_size at 1, 8, 64, 1024.
    8. (~20 min) Pitfall scenario tests (cancel-mid-flight, drop-sender, shutdown-mid-batch).
  - **Pitfalls**:
    - *Cancelled producer doesn't see durability*: the previous design used `oneshot::Sender<Lsn>`; if the caller cancels (drops the receiver), the fsync thread sends into a dead channel and the record is silently durable but the caller doesn't know. **Symptom**: replicas diverge from primary because cancelled writes ARE durable. **Fix**: durability is observed via the monotonic `durable_lsn` watermark, NOT a per-call oneshot. The oneshot becomes a *fast-path notification only*, never the source of truth.
    - *Tail latency spike on big batches*: a batch of 10k records takes 10× longer to fsync than 1k. Caller of the first record waits for all 10k. **Symptom**: tail latency p99.9 spikes 100×. **Fix**: cap batch size; preemptively start an fsync when batch ≥ `early_flush_threshold`, even if `max_delay_us` not yet elapsed.
    - *Spinning fsync thread*: `while try_pop().is_some()` without backoff burns 100% CPU on idle. **Symptom**: idle wal still consumes one core. **Fix**: park the thread on a `Condvar` keyed off "pending non-empty"; producers signal. Or use the SegQueue's own pop-blocking-wait variant.
    - *Lsn allocation races*: if Lsn is assigned at fsync-thread side (instead of at producer side), reordering across cancellation breaks invariants. **Symptom**: lsn gaps after crash. **Fix**: producer assigns Lsn via `fetch_add` BEFORE pushing; ordering is producer-arrival order.
    - *Cross-segment batch*: a batch may span two segments if the first segment fills mid-batch. **Symptom**: half the batch in seg N, half in seg N+1, fsync only seg N → seg N+1 records lost on crash. **Fix**: fsync thread detects segment full, msyncs current seg before rotating, then continues batch on new seg.
    - *Backpressure overflow*: producers push faster than fsync drains. SegQueue grows unbounded → OOM. **Symptom**: process killed under sustained burst. **Fix**: `BoundedQueue` instead of `SegQueue`, or `pending_count` atomic with a soft cap; producers block on `await Notify` when above threshold.
  - **Test scenarios**:
    - 16 producer threads × 100k records → durable_lsn = 1.6M; all records visible on reopen.
    - Producer cancels mid-append: assert that the record's Lsn either (a) IS durable AND watermark advances past it, or (b) was never claimed (cancel before Lsn assignment).
    - Crash injection: SIGKILL at random offsets during 1M sustained writes; on reopen, durable_lsn reflects all records that returned from append before SIGKILL.
    - Throughput at batch sizes 1 / 8 / 64 / 1024: expect log-linear scaling up to disk IOPS limit.
    - Adversarial: shutdown with 1k pending — all 1k still durable post-shutdown.
  - **Acceptance**:
    - Append throughput: ≥ 500k records/sec with batch=1024 on NVMe; ≥ 50k records/sec with batch=1 (single-record durability).
    - p99 append latency ≤ 2ms at 100k/sec sustained.
    - Crash-recovery property test passes 1000 random fault injections (TigerBeetle VOPR-style if you have time).
    - SegQueue bench: ≥ 2× faster than `Mutex<Vec<T>>` baseline at 4+ producers.
  - **Downstream**: W29 recovery analysis/redo replays segments produced here; W64 raft AppendEntries persistence; W74 matching-engine order-log; W80 ledger entry log; W83 aeron archive uses same group-commit pattern; W95 mini-db CAPSTONE re-derives the algorithm.
  - **Expect to hit**: under heavy load, producer drops its oneshot sender mid-flight (caller cancelled). The fsync
    thread reads `Some((record, dead_sender))`; sending on a dead oneshot is silently lost. Caller can't tell if its
    record was durable.
    **Fix**: producer's drop path enqueues a "best-effort durable" record; durability is observed via a monotonic
    LSN watermark, not the oneshot. The oneshot becomes a *fast-path optimization*, not the source of truth.

**Wednesday — `wal` checksums + replay**

- [ ] **Build**: `crates/wal/src/checksum.rs` — CRC32C per record + per-segment-footer rollup. (~105 min)
  - **Why**: Storage hardware silently corrupts. SSDs (especially under power loss) flip bits and reorder writes. The only protection: end-to-end checksums on every record, verified on read. CRC32C (Castagnoli polynomial) is hardware-accelerated on x86 (SSE4.2 `crc32` instruction) and ARMv8 (CRC32C insn) → 10+ GB/s/core. Use it everywhere; reject anything stronger as overkill or anything weaker (CRC32-IEEE) as obsolete.
  - **Read first**: RocksDB `util/crc32c.cc` (SIMD-vectorized impl); SQLite `tool/showwal.c` (checksum verification on replay); Aeron `aeron-driver` for per-frame CRC. Linux kernel `lib/libcrc32c.c`.
  - **Design**:
    ```rust
    /// Hardware-accelerated CRC32C on supported platforms; software fallback otherwise.
    pub fn crc32c(data: &[u8]) -> u32 {
        #[cfg(all(target_arch = "x86_64", target_feature = "sse4.2"))]
        { unsafe { crc32c_hw(data) } }
        #[cfg(not(all(target_arch = "x86_64", target_feature = "sse4.2")))]
        { crc32c_sw(data) }
    }
    pub struct SegmentChecksum {
        rollup: u32,         // running combine of all record CRCs (XOR or polynomial-combine)
        count: u32,
    }
    impl SegmentChecksum {
        pub fn update(&mut self, record_crc: u32) { self.rollup = crc32c_combine(self.rollup, record_crc, RECORD_LEN); self.count += 1; }
    }
    ```
    **Invariants**:
    - Record CRC covers EVERYTHING except the CRC field itself (lsn, kind, flags, prev_lsn, payload).
    - On read, CRC mismatch → record is corrupt → stop scanning (treat as tail truncation).
    - Segment footer rollup matches `crc32c_combine` of all records' CRCs — detects whole-record drops.
    - CRC32C polynomial is `0x1EDC6F41` (Castagnoli), NOT `0xEDB88320` (IEEE).
  - **Build steps**:
    1. (~10 min) Cargo feature `simd` gated by `target_feature = "sse4.2"`; otherwise software table-based impl.
    2. (~20 min) Software CRC32C with the slice-by-8 algorithm (RocksDB's `Slice8`).
    3. (~15 min) Hardware impl using `std::arch::x86_64::_mm_crc32_u64` in 8-byte chunks.
    4. (~20 min) `crc32c_combine` — Mark Adler's formula for combining CRCs of contiguous blocks. Lifted from zlib.
    5. (~15 min) Wire into wal: encoder computes per-record CRC; segment footer writes rollup on segment-close.
    6. (~15 min) Tests: known vectors (`b"123456789"` → `0xE3069283`).
    7. (~10 min) Bench: ≥ 8 GB/s/core on x86_64 with SSE4.2.
  - **Pitfalls**:
    - *Wrong polynomial*: using IEEE (CRC32) instead of CRC32C silently passes for short inputs but diverges from spec. **Symptom**: incompat with industry tools that expect Castagnoli. **Fix**: explicit polynomial constant; test vectors from RFC 3720.
    - *CRC over uninitialized bytes*: if record struct has padding, CRC depends on padding bytes → flaky. **Symptom**: same record produces different CRCs on different runs. **Fix**: `#[repr(C)]` with explicit padding zeroed at construction; or CRC over the serialized byte form, not the struct.
    - *CRC inside vs outside of compression*: if you ever compress records, CRC the *uncompressed* bytes (end-to-end). **Symptom**: corrupt-but-decompresses payload undetected. **Fix**: CRC at record creation, store alongside compressed bytes.
    - *SSE4.2 detection at compile vs runtime*: `target_feature` is compile-time. A binary built with SSE4.2 won't run on older CPUs. **Symptom**: SIGILL on old hardware. **Fix**: runtime detection via `is_x86_feature_detected!("sse4.2")` + function dispatch.
  - **Test scenarios**:
    - Known vectors from RFC 3720 + iSCSI test suite.
    - Random 1 GB buffer: software impl matches hardware impl.
    - Bit-flip in a 1 KiB record: CRC detects 100% of single-bit, all 2-bit-burst, and ≥99.999% of random multi-bit.
    - Bench: throughput on a 64 MiB segment ≥ 8 GB/s.
  - **Acceptance**:
    - Inheritance ratio ≥ 0.95 vs RocksDB `crc32c.cc`.
    - Bench targets met.
  - **Downstream**: W26 replay (Wed afternoon) uses these to detect tail truncation; W29 recovery treats CRC mismatch as "end of safe replay"; every other wal-using crate inherits.
- [ ] **Build**: `crates/wal/src/replay.rs` — `Replayer<'a, S: SegmentStream>` yields `Result<WalRecord, ReplayError>`.
  Stops cleanly at the first checksum mismatch (partial-tail handling). (~105 min)
  - **Why**: Replay is the *only* code that runs after a crash. Its job: produce every record the application durably appended, in order, and STOP cleanly at the partial-tail (the in-flight record at crash time). Any deviation = silent data loss (under-replay) or panic (over-replay reading uninitialized bytes). This is the single most-tested module in any durable storage system.
  - **Read first**: ARIES paper §4 (analysis pass); RocksDB `db/log_reader.cc` (especially the "RecycledLogReader" mode); etcd `wal/wal.go::ReadAll`; SQLite WAL replay in `src/wal.c`.
  - **Design**:
    ```rust
    pub struct Replayer<'a, S: SegmentStream> {
        segments: S,                       // iter over Segment in (first_lsn) order
        current: Option<SegmentIter<'a>>,  // record iter within the current segment
        last_yielded_lsn: Option<Lsn>,
        state: ReplayState,
    }
    enum ReplayState {
        Healthy,
        ClosedAtTailTruncation { last_good_lsn: Lsn, bytes_skipped: usize },
        FatalCorruption(ReplayError),
    }
    impl<'a, S> Iterator for Replayer<'a, S> {
        type Item = Result<WalRecord, ReplayError>;
        fn next(&mut self) -> Option<Self::Item> {
            // 1. If current iter has more records → yield it (after CRC verify + monotonicity check).
            // 2. If current iter ends with a CRC mismatch in the FINAL position → log tail-trunc, return None.
            // 3. If CRC mismatch in middle of a segment → ReplayError::CorruptMiddle. Fatal.
            // 4. If iter exhausted, advance to next segment; verify segment_id continuous, first_lsn matches.
        }
    }
    ```
    **Invariants**:
    - LSNs yielded are strictly increasing.
    - Stop point is at most the first corrupted byte; everything before is guaranteed valid.
    - Tail truncation is a *clean exit*, not an error.
    - Middle-of-segment corruption is *fatal* (operator intervention required).
    - Segment boundary integrity: segment N+1's `first_lsn = segment N's last_lsn + 1`. Gaps → fatal.
  - **Build steps**:
    1. (~15 min) `SegmentStream` trait: provides segments in ascending first_lsn order; tested with both fs-backed (real) and in-memory mock.
    2. (~25 min) `Replayer::next` body — the CRC + monotonicity + boundary-continuity checks.
    3. (~20 min) Distinguish "tail truncation" (last record of last segment) from "middle corruption" (any earlier).
    4. (~15 min) `ReplayError` variants: `CrcMismatch`, `NonMonotonicLsn`, `SegmentGap`, `MissingSegment`, `BadMagic`.
    5. (~15 min) Side-channel: `replay.diagnostics()` returning `ReplayState` after iteration finishes.
    6. (~15 min) Tests: tail-trunc, mid-trunc, perfect, gap detection.
  - **Pitfalls**:
    - *Treating tail-trunc as error*: replay halts with an Err result; caller bails out instead of resuming. **Symptom**: every crash forces operator intervention. **Fix**: tail-trunc = `Ok(None)` from iterator + state inspection.
    - *Reading past EOF on mmap*: scanner that doesn't bound-check can SIGBUS on a hole. **Symptom**: crash during replay (the worst time!). **Fix**: every record-read bounds-checks against segment body length; treat OOB as tail-trunc.
    - *Forgetting segment boundary*: walker that ignores segment ID assumes records continue across segment files. **Symptom**: gap between seg N and seg N+1 (missing seg) yields silently incorrect order. **Fix**: assert `seg_n.last_lsn + 1 == seg_n+1.first_lsn`; fail loudly.
    - *Recycled-segment confusion*: if segments are reused (truncate + overwrite), an old segment's tail may have valid CRCs from a previous generation. **Symptom**: replay continues into stale data and re-applies old txs. **Fix**: include `epoch` or `generation` field in segment header AND every record header; mismatched generation → tail-trunc.
    - *Reentrant replay*: replay called twice without rewinding the segment cursor. **Symptom**: second call returns `None` immediately. **Fix**: `Replayer::reset` for testing only; production uses one-shot.
  - **Test scenarios**:
    - Happy path: 10k records across 3 segments, replay yields exactly 10k in order.
    - Tail-trunc: truncate the last segment file by 27 bytes mid-record → replay yields N-1 records, state = `ClosedAtTailTruncation`.
    - Mid-corruption: flip a bit in segment 2's record 500 → replay yields seg1 + seg2[0..499], returns `Err(CrcMismatch)` on record 500.
    - Gap: delete segment 2 → replay yields seg1, returns `Err(SegmentGap)`.
    - Generation skew: forge a record with old `generation` → replay treats as tail-trunc.
    - Property: for any (records, truncate_offset), replay yields the longest prefix of valid records up to truncate_offset.
  - **Acceptance**:
    - Pass 1000 random corruption injections without false positives or false negatives.
    - Inheritance ratio ≥ 0.85 vs RocksDB `log_reader.cc`.
    - Replay throughput: ≥ 1 GB/sec on 64 MiB segments (mmap-backed).
  - **Downstream**: W29 ARIES analysis pass wraps `Replayer`; W64 raft follower replays leader's wal via this interface; recovery v0.5 (W30) integrates as the read side.

- [ ] **Build**: `crates/wal/src/lib.rs` — `Wal { dir: PathBuf, segments: Vec<Segment>, ... }` public API:
  `append(record) -> Future<Lsn>`, `replay() -> Replayer`, `checkpoint(lsn)`, `truncate_below(lsn)`. (~105 min)
  - **Why**: The public `Wal` is the single facade users interact with — they should never touch Segment/Record/Replay directly. Encapsulation gives you freedom to refactor internals (e.g. swap mmap for io_uring in W40+) without breaking 6+ downstream crates. The API surface is small but the *contract* (what guarantees the wal offers) is dense.
  - **Read first**: PostgreSQL `src/include/access/xlog.h` (`XLogInsert`, `XLogFlush`, `CreateCheckPoint`); RocksDB `db/db_impl/db_impl_open.cc` (the recovery sequence). Chronicle Queue's public `ChronicleQueue` interface for contrast.
  - **Design**:
    ```rust
    pub struct Wal {
        dir: PathBuf,
        active_segment: RwLock<Arc<Segment>>,
        sealed_segments: RwLock<BTreeMap<SegmentId, Arc<Segment>>>,
        next_lsn: AtomicU64,
        next_segment_id: AtomicU64,
        group_commit: Arc<GroupCommit>,
        config: WalConfig,
    }
    pub struct WalConfig {
        pub segment_size: usize,           // default 64 MiB
        pub max_batch: usize,              // default 1024
        pub max_delay_us: u64,             // default 10
        pub fsync_mode: FsyncMode,         // Always | EveryNms(N) | Never
        pub retain_after_checkpoint: usize, // keep N segments past last checkpoint for streaming
    }
    impl Wal {
        pub async fn open(dir: PathBuf, config: WalConfig) -> Result<Self, OpenError>;
        pub async fn append(&self, kind: RecordKind, payload: Bytes) -> Result<Lsn, AppendError>;
        pub fn replay(&self) -> Replayer<'_, FsSegmentStream>;
        pub async fn checkpoint(&self, durable_state_lsn: Lsn) -> Result<(), Error>;
        pub async fn truncate_below(&self, lsn: Lsn) -> Result<(), Error>;
        pub async fn close(self) -> Result<(), Error>;
    }
    ```
    **Invariants**:
    - `open` scans directory, validates each segment's header, sets `next_lsn` to max(last_lsn) + 1.
    - `append` is the ONLY way LSNs are minted; LSNs are gap-free within a single `open`/`close` cycle.
    - `checkpoint` writes a Checkpoint record AND remembers the "min recoverable LSN" so `truncate_below` knows what's safe to drop.
    - `truncate_below(lsn)` only removes segments whose `last_lsn < lsn` AND `last_lsn < last_checkpoint_lsn - retain_after_checkpoint`.
    - At all times, `active_segment` is mmap'd and writable; sealed segments are read-only.
  - **Build steps**:
    1. (~15 min) `Wal::open` — directory scan, header validation, set up GroupCommit, recover next_lsn.
    2. (~20 min) `Wal::append` — assign Lsn, hand off to GroupCommit, return when durable.
    3. (~15 min) Segment rotation: on `Segment::append` returns `None`, seal current and open a fresh one.
    4. (~15 min) `checkpoint(durable_state_lsn)` — write Checkpoint record + persist `min_recover_lsn` to a control file (`MANIFEST` or sidecar).
    5. (~15 min) `truncate_below(lsn)` — remove sealed segments whose last_lsn < lsn AND safe per retention.
    6. (~15 min) `close` — quiesce GroupCommit, fsync, drop mmaps.
    7. (~10 min) Tests: open empty, open with crashed tail, append + replay, checkpoint + truncate, close + reopen.
  - **Pitfalls**:
    - *Open-time LSN recovery off-by-one*: scanning the last segment and setting `next_lsn = last_lsn + 1` is wrong if last segment is empty. **Symptom**: gap in LSN after restart. **Fix**: if active segment is empty, `next_lsn = active.first_lsn`; else `next_lsn = active.last_appended + 1`.
    - *Truncate races with replay*: a follower replaying segments concurrent with truncation. **Symptom**: replay sees a deleted segment mid-iter. **Fix**: truncate takes an exclusive RwLock; replay holds a shared lock. Or replay snapshots the segment list at start.
    - *Checkpoint vs append race*: a checkpoint record itself is an append; concurrent appends interleave. **Symptom**: checkpoint LSN doesn't correspond to a clean DPT/TT snapshot. **Fix**: checkpoint takes a "fuzzy" snapshot (DPT/TT collected before the checkpoint write), records the LSN window; ARIES tolerates fuzzy checkpoints.
    - *Disk full*: append succeeds enqueueing but fsync fails. **Symptom**: caller thinks durable, isn't. **Fix**: GroupCommit propagates fsync errors back to the durable_lsn waiters via a `Result<Lsn, FsyncError>`-shaped notify.
    - *Mmap and unlink*: deleting a sealed segment while a reader has it mmap'd is fine on Linux (refcounted vma) but undefined on macOS. **Symptom**: SIGBUS on macOS. **Fix**: explicit munmap before unlink; reference-count segment readers.
  - **Test scenarios**:
    - Open-recover from a wal with 100k records across 5 segments + crash mid-101001 → `next_lsn = 100001` AND the 101001th record is NOT present.
    - Append 10k records, checkpoint at 5000, truncate below 5000 → 5000 oldest records gone, 5001..10000 intact.
    - Checkpoint while 100k appends in flight: all 100k either succeed before checkpoint OR are visible after; no lost writes.
    - Reopen after `close`: all durable records replayable, no extra junk.
    - Disk-full simulation: fsync returns `ENOSPC` → append future resolves with `AppendError::OutOfDiskSpace` for the affected batch; subsequent appends fail fast.
  - **Acceptance**:
    - End-to-end open-append-replay-checkpoint-close round trip in CI.
    - Inheritance ratio ≥ 0.85 vs RocksDB `db_impl_open.cc` recovery sequence.
    - Sustained throughput ≥ 200 MB/s in a 16-producer test on NVMe.
