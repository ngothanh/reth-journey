- [ ] **Build**: `crates/wal/src/segment.rs` — `Segment` is an mmap-backed file with header
  `{ magic, version, segment_id, first_lsn }`, body of length-prefixed records, footer `{ last_lsn, checksum }`. Default
  segment size 64 MiB. Pre-allocated. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: segment files are the *durability granule*. Pre-allocated via `fallocate` so writes
    never extend the file (avoiding metadata fsync). Bounded size enables truncation (rotate old segments out
    of disk). Mmap lets the kernel coalesce dirty pages; explicit msync gives commit barriers. This layout is
    canon in WAL design — RocksDB, Aeron Archive, Chronicle Queue, Postgres all use the same shape.
    Downstream: Tuesday group-commit consumes `Segment::append`; Wednesday replay consumes `scan`; W27
    storage-trie WAL integration; W29 recovery; W64 raft replicated log; W80 ledger.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: durable append-only logging requires (a) atomic append per
    record under multi-producer contention, (b) crash detection so partial-tail records are identified, (c)
    bounded file size for retention, (d) fast scan on reopen. A naive `File::write_all + fsync` per record
    burns ~1ms per record on NVMe — 1k records/sec ceiling. Mmap + atomic offset claim + group commit gives
    ≥1M records/sec single-thread.

  - **Requirements** — write in `crates/wal/notes/26_segment_design.md`:
    - R1. `Segment` holds `path`, `file`, `mmap: MmapMut`, `header: SegmentHeader`, `write_offset:
      AtomicUsize`, `first_lsn: Lsn`, `last_durable_lsn: AtomicU64`.
    - R2. `SegmentHeader` is `#[repr(C)]` with `magic: [u8;8]` (`b"WALSEG01"`), `version: u32`, `flags:
      u32`, `segment_id: u64`, `first_lsn: u64`, `body_offset: u32 (=64)`, `body_len: u32`, padding.
    - R3. Segment file size == declared size at all times after creation (pre-allocated via fallocate).
    - R4. `write_offset` only advances; never rewinds. Atomic `fetch_add` is the reservation primitive.
    - R5. On open, magic byte sequence must match; if not, reject (junk/wrong-version).
    - R6. Body region initialized to zeros at fallocate; a zero `len` field marks EOF/tail.
    - R7. `append(record) -> Option<Lsn>` returns `None` if not enough space (caller rotates), else
      writes frame header + body + advances offset.
    - R8. `scan() -> SegmentIter` stops at zero-len frame OR checksum mismatch — both signal tail.
    - R9. Throughput: ≥1M records/sec single-thread (32-B payload); ≥5M/sec aggregate at 16 producers.
    - R10. Crash-recovery: 1000 random SIGKILL fault injections; reopen + scan returns all records up to
      last complete CRC-valid frame.

  - **Design walk-through** — answer each:
    - D1. fallocate cost: ~50-200ms per 64MiB file on slow disks. Where does this cost go on the hot
      path? (Hint: 2-deep ready-pool — pre-allocate the NEXT segment in the background.)
    - D2. Multi-producer offset claim: `fetch_add(len + frame_overhead)` returns the reserved start.
      What about producers that crash after reserving but before writing? (Hint: CRC + zero-init body
      → scanner treats CRC mismatch on non-zero-len frame as torn-write tail.)
    - D3. Torn writes at segment boundary: producer reserves N bytes but the reservation pushes past
      `body_len`. What does append do? (Hint: bounds-check BEFORE the reservation succeeds; on overflow,
      return None.)
    - D4. mmap-vs-write coherence: writing via mmap, reading via `read(2)` on the same fd can return
      stale data on some Linux kernels. Pick one access path — which?
    - D5. Pre-mortem: the reserved-but-unwritten window. A producer wins the `fetch_add` then is
      preempted/crashes. Reader sees zeros (or stale bytes). What's the recovery rule?

  - **Output**: `notes/26_segment_design.md` with R1–R10 + D1–D5 + frame layout diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

  - **When `concurrent_append_16_producers_no_loss` reports overlapping writes:**
    - Symptom: two threads' records partially overwrite each other. Final scan shows 1.55M records
      instead of 1.6M with garbled bytes at the overlap zone.
    - Why: `write_offset` used `compare_exchange` in a loop; under high contention, two threads observe
      the same offset, both compute their frame, both call `mmap[start..end].copy_from_slice(...)`.
      The CAS only protects the offset bump, not the write region.
    - Fix: use `fetch_add` as a reservation — `let start = write_offset.fetch_add(frame_size, Acquire);`
      atomically reserves a non-overlapping range. Then write into `mmap[start..start+frame_size]`
      without further synchronization (each producer's range is disjoint).
    - Muscle: lock-free append-only logs use `fetch_add` for reservation, not CAS-loop; reservation
      ranges are disjoint by construction. Reapplies at: W30 mmap-queue cycle.rs claim, W31 mmap-queue
      term buffer, W77 aeron Publication.

  - **When `crash_injection_tail_truncation` reads past the partial record into garbage:**
    - Symptom: scan returns the 10k valid records PLUS some garbage records (CRC errors logged but
      iteration continued).
    - Why: scan continued past the first CRC-mismatch frame instead of stopping. The "tail
      truncation" rule (R8) wasn't implemented.
    - Fix: in `SegmentIter::next`, on CRC mismatch, return `None` (end iteration). Distinguish in a
      `state()` accessor: `CleanEnd | TailTruncation { at: usize }`. Caller decides whether truncation
      is normal (crash recovery) or fatal (mid-segment corruption).
    - Muscle: an append-only scanner stops at the first integrity violation; never "skips and
      continues" because skipping admits an attacker who corrupts mid-segment to swallow data.
      Reapplies at: W26 replay.rs, W30 ARIES analysis, W30 mmap-queue ExcerptCursor.

  - **When `bench_single_thread_1m_per_sec` reports 300k/sec:**
    - Symptom: append latency is ~3.3 µs (300k/sec); target was ≤1µs (≥1M/sec). 3× too slow.
    - Why: `msync(MS_SYNC)` was called after every append; group commit not yet integrated. Each msync
      is ~2-3µs even on NVMe.
    - Fix: append does NOT msync. msync is the group-commit thread's job (Tuesday's
      `GroupCommit::flush_loop`). The segment's `last_durable_lsn` advances only when group-commit
      msyncs. For now, write a separate `flush_test` bench that confirms throughput when msync is
      separated.
    - Cost avoided: ~2.5 µs per append; at 1M ops/sec, 2.5 sec/sec of CPU reclaimed.
    - Muscle: durability is amortized across many records (group commit); never per-record fsync on
      the append hot path. Reapplies at: W26 group_commit.rs, W80 ledger journal.

  - **When `append_until_full_returns_none` returns `Some(lsn)` on the overflow attempt:**
    - Symptom: after the segment is exactly full, one more `append` returns `Some(lsn)` but the
      record's bytes spill past `body_len` into footer / out-of-bounds territory. SIGBUS on
      subsequent reads.
    - Why: the bounds check used `>=` instead of `>`. The reservation succeeded because `write_offset
      <= body_len` was true; then the write spilled.
    - Fix: bounds check is `if reserved_start + frame_size > body_len { return None; }`. Decrement
      `write_offset` back (or use CAS with a guard); rotation is the caller's responsibility.
    - Muscle: bounds-check the FULL reservation (start + size) against the limit, not just the start;
      then atomically refuse if it doesn't fit. Reapplies at: W30 mmap-queue claim, W31 term-buffer.

  - **5-year failure mode** (write in `notes/26_segment_followup.md` after green): when persistent
    memory (PMem/CXL.mem) becomes common, the mmap-then-msync model collapses — PMem is byte-addressable
    and durable, no msync needed. State the migration: a `SegmentBackend` trait abstracts the
    durability mechanism; `MmapNvmeBackend` and `PmemBackend` impls. Trigger: PMem capacity > 10× DRAM
    available at server-class price points.
- [ ] **Build**: `crates/wal/src/record.rs` — `WalRecord { lsn: u64, kind: RecordKind, payload: Bytes }`. RecordKind
  enum (Insert, Update, Delete, Begin, Commit, Abort, Checkpoint). (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: the record is the *unit of durability*. Its fields are dictated by the recovery
    algorithm — ARIES needs `lsn`, `prev_lsn`, `tx_id`, `kind`, `payload`, `undo_next_lsn` for CLRs. Get this
    struct wrong and W29 recovery is unbuildable. The discriminated union of RecordKind is the only place
    where future record types can be added without breaking older readers (forward compat via reserved kind
    bits). Downstream: every wal user; W29 ARIES analysis walks records via this schema; W64 raft AppendEntries;
    W80 ledger; W83 aeron archive.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: log-records must be (a) self-describing (lsn + kind + length
    in the header so a scanner can skip records it doesn't understand), (b) forward-compatible (unknown
    record kinds skipped, not errored), (c) ARIES-ready (prev_lsn chain for tx undo, undo_next_lsn for
    CLR idempotence), (d) zero-allocation on the encode/decode hot path (payload is `Bytes`, header is
    fixed-layout).

  - **Requirements** — write in `crates/wal/notes/26_record_design.md`:
    - R1. `WalRecord { lsn, kind, tx_id: Option<TxId>, prev_lsn: Option<Lsn>, undo_next_lsn: Option<Lsn>,
      payload: Bytes }`.
    - R2. `RecordKind` is `#[repr(u8)]` with explicit discriminants: Begin=0x01, Commit=0x02, Abort=0x03,
      Insert=0x10, Update=0x11, Delete=0x12, Checkpoint=0x20, CLR=0x21, EndCheckpoint=0x22.
    - R3. `lsn` is strictly monotonic across all records in a wal.
    - R4. For a given `tx_id`, the chain `current.prev_lsn → prev.lsn` walks all records of that tx in
      reverse. First record of a tx has `prev_lsn = None`.
    - R5. CLRs always have `undo_next_lsn = Some(_)`; non-CLRs have it as `None`.
    - R6. Wire format is FIXED-SIZE little-endian: lsn(8) + kind(1) + flags(1) + tx_id(8|0) +
      prev_lsn(8|0) + undo_next(8|0) + payload_len(4) + payload. `flags` bitmap encodes which optional
      fields are present.
    - R7. Decoder rejects unknown kinds with `RecordError::UnknownKind` BUT a record with a future
      `flags` bit set passes through (forward compat at flag granularity).
    - R8. `payload: Bytes` (Arc-backed) — never `Vec<u8>` — so callers pass slices without allocating.
    - R9. Encode ≥10M rec/s, decode ≥5M rec/s single-thread.
    - R10. Round-trip: encode → decode → encode is byte-identical for any `WalRecord` value.

  - **Design walk-through** — answer each:
    - D1. Why `Option<TxId>` not `TxId = 0` for "no tx"? (Hint: tx_id 0 would collide with a real
      Checkpoint or system record.)
    - D2. Forward-compat strategy: a flag bit per optional field means adding a new field tomorrow
      doesn't break today's decoder. Sketch the flags layout.
    - D3. Varint vs fixed-size: varint saves bytes for small LSNs but costs ~30% decode throughput.
      Which does wal pick? (Hint: fixed.)
    - D4. Enum dispatch on hot path: `match record.kind` over 10 variants — does the compiler emit a
      jump table or a chain of comparisons? How do you verify? (Hint: `cargo asm`.)
    - D5. Pre-mortem: name the scenario where forgetting `#[repr(u8)]` causes old segments to become
      unreadable after a toolchain bump.

  - **Output**: `notes/26_record_design.md` with R1–R10 + D1–D5 + the wire-format byte diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  - **When `tx_id_none_vs_zero_distinguished` reports `Some(0)` instead of `None`:**
    - Symptom: encoding `WalRecord { tx_id: None, ... }` and decoding yields `tx_id: Some(0)`.
    - Why: encoder wrote `0u64` for the tx_id slot regardless of None vs Some; decoder reads 8 bytes
      always. No flag bit distinguishes "absent" from "present-but-zero".
    - Fix: `flags: u8` bitmap, bit 0 = "tx_id present"; if bit clear, encoder skips the 8 bytes and
      decoder reads 0 bytes for tx_id, returning None. Same scheme for prev_lsn and undo_next_lsn.
    - Muscle: optional fields in fixed-layout wire formats require a presence flag, never a sentinel
      value — sentinels collide. Reapplies at: W21 RLP `#[rlp(trailing)]`, W67 raft AppendEntries
      versioned fields.

  - **When `verify_jump_table_emitted_on_kind_dispatch` reports a 10-instruction `cmp` chain:**
    - Symptom: `cargo asm` shows `cmp 0x01; je L_begin; cmp 0x02; je L_commit; ...` — chain of
      comparisons.
    - Why: discriminants are sparse (0x01, 0x02, 0x03, 0x10, 0x11, ..., 0x22) — the compiler can't
      emit a dense jump table over a 256-entry array; the gap from 0x03 to 0x10 is too large.
    - Fix: TWO options — (a) renumber discriminants densely (0x01..0x09) so the compiler emits a jump
      table; (b) keep sparse discriminants but write an explicit `static DISPATCH: [fn(&[u8]) -> Result<_>;
      256]` lookup. (a) is simpler; (b) preserves the human-readable groupings.
    - Cost avoided: ~5 ns/decode in branch-mispredict; at 5M decode/sec, 25ms/sec CPU reclaimed; matters
      most at recovery startup (cold caches).
    - Muscle: enum dispatch on a hot path benefits from frequency-ordered + dense discriminants OR
      explicit function-pointer dispatch tables; verify in asm. Reapplies at: W42 txn operation
      dispatch, W74 matching-engine order-type match, W77 aeron frame-type dispatch.

  - **When `forward_compat_unknown_flag_bit_decodes` fails with `Err(UnknownFlag)`:**
    - Symptom: setting `flags |= 0x80` (an unallocated bit) makes the decoder error.
    - Why: decoder validates that `flags & !KNOWN_FLAGS == 0`; future flag bits trip this.
    - Fix: decoder reads ONLY the known flag bits; ignores higher bits. The forward-compat contract:
      old code skips unknown flag bits silently, but must NOT skip unknown KIND bits (those alter
      record semantics).
    - Muscle: forward compat at flag granularity = ignore unknown flag bits; at kind granularity =
      error on unknown kinds. The two ARE different. Reapplies at: W21 RLP `#[rlp(trailing)]` (extra
      fields skipped, missing mandatory errors), W67 raft compatibility.

  - **When `bench_encode_10m_per_sec` reports 4M/sec:**

    - Why: each encode allocates a fresh `BytesMut::with_capacity(...)` — allocator overhead dominates.
    - Fix: encoder takes `&mut impl BufMut` from the caller; callers pool. Re-bench.
    - Cost avoided: ~150ns/op alloc; at 10M ops/sec, 1.5sec/sec of CPU reclaimed.
    - Muscle: hot encoders always accept a caller-supplied buffer; allocating per-call defeats throughput.
      Reapplies at: W20 branch_compact.rs, W21 RLP encoders, W31 mmap-queue wire.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: a fixed-size bounded MPMC ring (Vyukov, W11) is the right shape
    when capacity is known and producers can backpressure. When capacity is open-ended (durability queues,
    log-streaming) you need an UNBOUNDED MPMC — linked segments of bounded rings, each segment internally
    Vyukov-style. The hard part is segment lifetime: who frees a segment when consumers move past it AND
    producers may still reference it?

  - **Requirements** — write in `crates/concurrent/notes/26_seg_queue_design.md`:
    - R1. `SegQueue<T>` with `push(T)` and `try_pop() -> Option<T>`. Unbounded.
    - R2. `head: CachePadded<AtomicPtr<Segment>>`, `tail: CachePadded<AtomicPtr<Segment>>` — separate cache
      lines (no producer/consumer false sharing).
    - R3. Each segment holds 32 slots; per-slot `seq: AtomicU64` (Vyukov scheme); per-segment `next:
      AtomicPtr<Segment>` linking to successor.
    - R4. `next.store(new, Release)` paired with `next.load(Acquire)` so consumers see initialized
      next-segment data.
    - R5. Multiple producers racing to allocate the next segment: only ONE wins the CAS; losers drop their
      Box explicitly (no leak).
    - R6. Reclamation: per-segment atomic refcount. Producers bump on follow-next; consumers bump on
      follow-next; both decrement on departure. Only refcount-zero segments freed.
    - R7. Throughput: ≥5M push/sec single-producer; ≥2M aggregate at 16 producers.
    - R8. Loom-green: 2-producer + 2-consumer harness, no torn reads, no UAF, no leaks.

  - **Design walk-through** — answer each:
    - D1. Why is "who owns the node, when does it die" the central question of every lock-free DS?
      Sketch the refcount answer vs the EBR (W33) answer.
    - D2. The Vyukov per-slot seq scheme — what values does seq take through the slot's lifecycle?
      (Hint: 0 = empty, slot_idx after push, slot_idx + 1 after pop.)
    - D3. Segment `next` pointer ordering: Relaxed store + Acquire load — what goes wrong on weak
      hardware? (Hint: producer's segment-header init isn't visible; consumer reads garbage.)
    - D4. Pre-mortem: write the UAF scenario where a producer holds a stale `tail` pointer to a freed
      segment in 5 numbered steps. What invariant prevents it?

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **When `concurrent_segment_alloc_no_leak` reports ~50 leaked Boxes after 16-producer burn-in:**
    - Symptom: dhat shows 50 unfreed `Box<Segment>` allocations.
    - Why: multiple producers race to allocate the next segment when current fills. Each allocates its
      own `Box::new(Segment::new())`, then CAS the `next` pointer. Only one wins; losers `Box::leak`
      their segment by simply returning.
    - Fix: try `next.load(Acquire)` FIRST — if non-null, another thread already wrote next; don't
      allocate. If null, allocate, CAS. On CAS failure, `unsafe { Box::from_raw(my_loser) }` then
      drop. The `from_raw` reclaims the heap; the explicit `drop` runs `Segment::drop`.
    - Muscle: in lock-free linked structures, every "I'll allocate the next node" path must reclaim
      its losing allocation; never let losers leak. Reapplies at: W37 skiplist tower extension, W74
      matching-engine order pool, W77 aeron Publication term-buffer linkage.

  - **When `loom_2p_2c_safe` reports a UAF in the consumer:**
    - Symptom: loom prints `[T1: consumer follows next ptr] → [T2: producer frees segment S after
      refcount drop] → [T1: dereferences freed S]`.
    - Why: consumer reads `next.load(Acquire)`, gets a pointer to segment S; bumps refcount; but the
      bump and load aren't atomic together — producer may decrement-and-free between them.
    - Fix: refcount bump uses a "tagged-CAS" pattern: load+CAS the segment's refcount, ensuring the
      pointer is still in the linked list. If the segment's refcount has already hit zero, retry from
      head/tail load. The simpler fix: never expose the pointer to the consumer until the refcount is
      already bumped (the producer that linked it pre-bumps).
    - Muscle: every "follow a pointer to a refcounted node" must atomically bump-while-still-linked;
      a separate load + bump opens a free-between-them window. Reapplies at: W33 EBR Atomic<T>
      protection, W37 skiplist tower walk, W74 matching-engine pool.

  - **When `consumer_following_next_sees_initialized` reads garbage values:**

- [ ] **Build**: `crates/wal/src/checksum.rs` — CRC32C per record + per-segment-footer rollup. (~total 140 min across 3 phases)

    >99.999% of random multi-bit errors. Per-record CRC localizes corruption to a record; per-segment
    footer rollup detects whole-record drops (a record was silently lost).

  #### Phase 3 — Make the tests pass, one failure at a time (~75 min)

  - **When `open_recover_after_crashed_tail` reports `next_lsn = 100000` instead of `100001`:**
    - Symptom: off-by-one; on restart, the next append reuses lsn 100000 which was the previous
      successful append.
    - Why: `next_lsn = last_appended` instead of `last_appended + 1`. Or worse: `next_lsn =
      active.first_lsn` when active segment had records (forgot to scan the active segment's records).
    - Fix: scan active segment's records via `Segment::scan()`; `next_lsn = max(last_record.lsn) + 1`.
      If active segment is empty, `next_lsn = active.first_lsn`.
    - Muscle: open-time LSN recovery scans the active segment to find the highest written LSN; "+1"
      is the next slot. Off-by-one here = duplicate LSNs after restart. Reapplies at: W29 ARIES
      analysis, W64 raft term restart.

  - **When `bench_replay_lockfree_under_contention` reports ~50ns per fetch instead of ~5ns:**
    - Symptom: replay throughput plateaus under writer load; `perf` shows lock contention on
      `sealed_segments`.
    - Why: `sealed_segments: RwLock<BTreeMap<SegmentId, Arc<Segment>>>` — every replay or random-access
      fetch takes a read lock. Even an RwLock's read-acquire is ~50ns.
    - Fix: `arc_swap::ArcSwap<BTreeMap<SegmentId, Arc<Segment>>>` for sealed segments. Writers (rotation,
      truncate) build a fresh BTreeMap and atomic-swap; readers do one atomic load (~5 ns).
    - Cost avoided: ~45ns/fetch; eliminates lock as scalability ceiling for replay-heavy workloads.
    - Muscle: read-mostly metadata maps use copy-on-write atomic swaps (arc-swap), not RwLock.
      Reapplies at: W14 bufpool page table, W42 txn schema versions, W74 matching-engine symbol list.

  - **When `checkpoint_concurrent_with_appends_no_loss` reports lost appends:**
    - Symptom: 100 of 100k appends are "lost" after checkpoint — present in pre-checkpoint state,
      absent in post-checkpoint replay.
    - Why: checkpoint took a "sharp" snapshot — paused appends, snapshotted DPT/TT, resumed. The
      paused appends queued in the group_commit queue with their old LSNs but their durability is
      gated on the pre-pause durable_lsn watermark.
    - Fix: fuzzy checkpoint — DPT/TT collected WITHOUT pausing appends; the checkpoint record carries
      `(begin_lsn, end_lsn)` defining a window of LSNs that "might or might not" be reflected. ARIES
      recovery's analysis pass tolerates fuzzy checkpoints by re-scanning the window.
    - Muscle: high-concurrency checkpoints must be fuzzy, not sharp; sharp checkpoints stall the wal
      and lose throughput. Reapplies at: W30 Checkpointer, W64 raft snapshot.

  - **When `disk_full_propagates_typed_error` reports a generic `Err(IoError)`:**
    - Symptom: caller can't distinguish "disk full" from "permission denied" from "fsync truly broken".
    - Why: group_commit's fsync error propagation collapsed all errors into a single variant.
    - Fix: enum `AppendError { OutOfDiskSpace, FsyncFailed { source }, ChannelClosed, ... }`. The
      caller can decide: OutOfDiskSpace → backoff and retry after operator action; FsyncFailed →
      escalate; ChannelClosed → wal is dead.
    - Muscle: typed errors at the boundary; collapsing all I/O errors into a single variant strips
      the caller of recovery affordances. Reapplies at: W42 txn errors, W67 raft errors.

    persistent memory mature, segment rotation + fallocate model becomes obsolete. Migration: a
    `WalBackend` trait abstracts open/append/replay/checkpoint; current `MmapWalBackend` lives alongside
    `IoUringWalBackend` and `PmemWalBackend`. Trigger: NVMe replaced by PMem.
