**Tuesday — Run fuzz, fix findings + [HFT] matching-engine: differential test against simple reference**

- [ ] Run fuzzer. Address crashes. (~30 min)
- [ ] [HFT] **Build**: `matching-engine/tests/diff_test.rs` — property test: random sequences of orders → compare
  matching-engine output to a slow-but-obviously-correct reference matcher (sorted Vec sweep). Must match exactly. (~150 min)
  - **Why (MAX DETAIL)**: Differential testing against a reference is THE gold standard for correctness. A naive matcher (no fancy data structures, sorted Vec sweep) is "obviously correct" — if there's a bug, it's in the fast impl. Property-based testing (proptest) generates adversarial sequences automatically.
  - *Back-of-envelope*: this is a CI gate, not a hot-path benchmark — the perf bar here is "CI runs in ≤ 10 minutes". 1000 sequences × ~100 orders × 2 implementations × ~10 µs/order (reference is slow on purpose) = ~2 seconds total — well within budget. But: **bit-determinism is the bar**. A non-deterministic data structure in either matcher (HashMap iteration order, float arithmetic, allocator-order-dependent comparison) causes spurious diff-test failures that take days to debug. The same HashMap-ban from W60 det_test applies here transitively — every type reachable from `match_order` must be HashMap-free (use `BTreeMap` / `IndexMap`).
  - **Read first**: proptest book; jepsen-style property-test patterns; TigerBeetle's reference-checker tests.
  - **Design**:
    ```rust
    fn reference_match(orders: &[Order]) -> Vec<Fill> {
        // Slow but obviously-correct:
        // Maintain bids/asks as sorted Vecs. Linear scan for best match. Re-sort after every change.
        let mut book = ReferenceBook::new();
        let mut fills = Vec::new();
        for o in orders {
            fills.extend(book.submit(o.clone()));
        }
        fills
    }

    proptest! {
        #[test]
        fn matching_matches_reference(
            orders in prop::collection::vec(arb_order(), 1..=100)
        ) {
            let fast = run_fast_matcher(&orders);
            let slow = reference_match(&orders);
            prop_assert_eq!(fast, slow);
        }
    }

    fn arb_order() -> impl Strategy<Value = Order> {
        // Generator: random side, price ∈ [1, 1000], qty ∈ [1, 1000], kind ∈ {Limit, Market, IOC, FOK, PostOnly}
        (
            any::<bool>(),
            1u64..1000,
            1u64..1000,
            arb_kind(),
        ).prop_map(|(side, price, qty, kind)| { /* construct Order */ })
    }
    ```
    **Invariants**:
    - For any sequence of N orders, fast.fills == slow.fills (byte-exact).
    - For any sequence, fast.book.snapshot() == slow.book.snapshot().
    - Sequence count: at least 1000 sequences of 1..100 orders; ideally 10k.
  - **Build steps**:
    1. (~30 min) ReferenceBook: trivial sorted-Vec impl. Don't bother with O(1) cancel; O(n) is fine.
    2. (~30 min) reference_match driver.
    3. (~30 min) proptest arb_order generator with all OrderKinds.
    4. (~20 min) Equality test on fills + final book state.
    5. (~25 min) Shrink: on mismatch, proptest shrinks to minimal failing sequence; debug against that.
    6. (~15 min) Run on CI: `cargo test --release diff_test` with 1k cases default.
  - **Pitfalls**:
    - *Non-deterministic ordering in HashMap*: fills returned in random order → false mismatch. **Fix**: sort fills by (taker_id, maker_id) before comparison.
    - *Float-precision drift in reference*: any float = bug. **Fix**: all-integer math.
    - *PostOnly cross-rejection mismatch*: fast and slow must agree on "would cross" definition. **Fix**: shared `would_cross()` helper.
  - **Expect to hit (perf) #1 — `AHashMap` (or worse, `HashMap`) reachable from match_order leaks nondeterminism into the diff-test (bar (c) / determinism violation)**: the W60 `order_index: AHashMap<OrderId, OrderRef>` is fast for the hot path but `AHashMap`'s iteration order is non-deterministic across builds (different hash seeds across compilation runs). If the diff-test ever iterates `order_index` (e.g., for "dump book state for comparison") it'll see different orderings across runs and fail spuriously. Same risk if `Fill` events are emitted in iteration order over a HashMap of pending fills.
    - Fix: lint-enforce — `cargo test diff_test` first runs a build step that greps the matching-engine src tree for `HashMap`/`AHashMap` reachable from `match_order` and fails CI if found (or wraps them in a `DetSafeMap` newtype that explicitly sorts on iter). Production code uses `IndexMap` (insertion-ordered) or `BTreeMap` (key-ordered) on any path that emits events or is reachable from the diff-test. For the W60 `order_index`, `IndexMap` is the right choice — it's just-as-fast on lookup, deterministic on iter.
    - Cost avoided: days of debug-hunt for spurious diff-test failures; bit-determinism preserved into W74 raft replication (any non-determinism here corrupts replicas).
    - Muscle: determinism rules transitively — every type reachable from a deterministic test must itself be deterministic. Reapplies at: W60 det_test (taught), W74 raft over matching-engine, W83 ledger-deterministic, W88 VOPR.
  - **Acceptance**: 1000 sequences green; minimal-failing-case (if any) <= 10 orders; CI lint passes (no HashMap reachable from match path); diff-test deterministic across 10 consecutive CI runs.
  - **Downstream**: v0.5 tag (Thu) requires diff-test green.

- [ ] [HFT] criterion bench: 1M orders/sec single-symbol throughput on a single core; target P99 matching latency <10
  µs (we will tighten to <5 µs by W74). (~60 min)
  - **Why**: This is the v0.5 quantitative bar. Without sub-10µs P99 single-core, the engine isn't competitive even at v0.5. **This is THE bar-(c) gate** — if P99 is over 10 µs at v0.5, the scope was wrong (see README v2 §"Bar policy": "missing the bar at v1.0 means the scope was wrong"). v0.5 establishes the regression baseline; every subsequent week's CI checks against it.
  - *Back-of-envelope*: at 1 M orders/sec, the wall-clock budget per order is 1 µs — but P99 budget is 10 µs (allows ~1% of orders to be 10× the median). This corresponds to a sustained 0.1 µs median + a long tail driven by: (a) rare allocator hiccups (~5-50 µs allocator rebalance), (b) BTreeMap node alloc on new price level (~5 µs spike, see W60 perf #1), (c) WAL fsync sync window (~10-50 µs, see W61 perf #2 — fsync must be deferred), (d) `SmallVec` spill on sweep orders (~50 ns × log2(N), see W61 perf #2). To hit P99 < 10 µs we need ALL of (a)-(d) addressed at v0.5; if any one is unaddressed it dominates P99 alone. Throughput perspective: 1 M/sec single-core = 1000 cycles/order on a 4 GHz CPU; ~250 cycles for the actual matching arithmetic + ~750 cycles for memory access / encode / event emission. **Cache line per `PriceLevel`**: each PriceLevel touched on every fill at that price; with W60 layout fixes, one `PriceLevel` (~32 B) + first Order (~64 B) = ~96 B = 1.5 cache lines per fill = ~10-15 ns L1 hit / ~50 ns L2 fetch worst case.
  - **Build steps**:
    1. (~20 min) criterion bench: pre-load 1k resting orders, then time 1M incoming orders (mix of limit at-price, taker, cancel).
    2. (~20 min) Latency histogram via hdrhistogram; record p50/p99/p99.9.
    3. (~20 min) Pin to one core; disable HT; pin allocator (mimalloc).
  - **Expect to hit (perf) #1 — P99 dominated by allocator tail despite all per-op work being zero-alloc (bar (c) violation)**: even after applying W58-W61 perf fixes (zero-alloc submit/encode/append), P99 still floats at ~5-20 µs because the *background* allocator-state evolves under churn — every ~10 sec, mimalloc rebalances its thread-cache → ~50 µs stall on whatever the shard thread is doing. Symptom: hdrhistogram shows p99.9 in the 50 µs range; the spike is periodic, not workload-correlated.
    - Fix: enforce *true* zero-allocation steady state — set up a CI step that runs the bench with `dhat`/`heaptrack` attached and FAILS if allocation rate exceeds ~10/sec during the steady-state phase (allow warm-up + setup). The fix path: every remaining allocator visit gets traced back to a struct that should be pre-allocated (`SmallVec` spill from W61, BTreeMap node from W60, event-log encode-scratch oversizing from W61). Iterate until allocation rate ≈ 0. For mimalloc: use `mi_option_set(mi_option_purge_delay, -1)` to disable purging during the bench window. For glibc malloc: switch to mimalloc or jemalloc (mandatory for bar-(c) crates).
    - Cost avoided: ~50 µs periodic spikes → < 1 µs steady; P99 from "passing-but-spiky" to "flat-line"; v0.5 becomes the regression baseline that W74 v1.0 (5 µs) and W82 v1.5 (1 µs) can tighten against without fighting allocator noise.
    - Muscle: bar-(c) "zero-allocation" means *measurably zero* in steady state — instrument and fail CI on regressions, don't trust eyeballed code review. Reapplies at: W74 matching-engine v1.0 bar-(c) gate, W83 ledger apply loop, W92 ledger v1.0 static-mem invariants, W110 chaos test SLO.
  - **Expect to hit (perf) #2 — CPU frequency scaling adds 30% noise to P99 (bar (c) violation, environmental)**: laptops and most servers default to dynamic CPU frequency scaling (turbo boost, power-saving steps). During a 1 M order/sec bench, the CPU transitions between P-states asynchronously — the bench thread sometimes runs at 2 GHz, sometimes at 4 GHz, and the transition itself takes ~50-200 µs. Symptom: P99 looks "okay" on a fresh-cold machine but spikes to 20-50 µs as the bench warms up the CPU and thermal-throttling kicks in; reproducibility across runs is ~30% (P99 varies 8-15 µs between runs of the same code).
    - Fix: standardize the bench environment — `cpupower frequency-set -g performance` (Linux) pins to max frequency; `taskset -c 2` pins to a specific core away from kernel work; disable HyperThreading on the bench core's sibling (or pin the sibling to idle); set `kernel.timer_migration=0` and `kernel.sched_min_granularity_ns` to large values to prevent scheduler interference. Document this environment in `MATCHING_BENCH.md`; CI runs on a dedicated bare-metal box (the W106+ ops rig) configured identically. Local bench-vs-CI numbers should match within 5%, not 30%.
    - Cost avoided: ~30% P99 variance across runs → ≤ 5% variance; restores ability to detect a true 5% regression (vs being lost in environmental noise); without this fix, the v1.0 5 µs gate is unmeasurable because the noise floor is higher than the target.
    - Muscle: bar-(c) latency targets require a controlled bench environment — CPU pinning, frequency-pinning, no HT siblings, no thermal headroom games. The infra setup is *part of the bar*, not separate from it. Reapplies at: W74 v1.0 5 µs gate, W82 v1.5 1 µs gate (extra-strict env required), W92 ledger v1.0 1 µs commit latency, W106+ ops rig calibration.
  - **Acceptance**: P99 < 10 µs; throughput ≥ 1M orders/sec; **allocation rate ≤ 10/sec steady state** (dhat-verified); **bench reproducibility ≤ 5% variance across 5 runs on the standardized env**; baseline numbers committed to `MATCHING_BENCH.md` for W74 to regress against.
