  #### Phase 3 — Make the tests pass, one failure at a time (~35 min)

  Ordered newbie → expert.

  - **(NEWBIE) When `run_one_never_panics_on_corpus` / a 30-sec fuzz run reports a crash backtracing into `MockHost::storage`:**
    - Symptom: libFuzzer writes `crash-<hash>`; the backtrace top frame is `MockHost::storage` (or `account`/`balance`) `unwrap()`/`todo!()`, not the interpreter.
    - Why: the mock host was treated as system-under-test, not as part of the harness — a missing-account/cold-slot read panicked. Every fuzz input that touches state "crashes," drowning the one real VM bug.
    - Fix: make `MockHost` total — every callback returns a deterministic default (`AccountInfo::default()`, `U256::ZERO`, empty code) and never panics; add `#![deny(clippy::unwrap_used)]` to the fuzz crate.
    - Muscle: the fuzz harness (host, decoder, setup) must be MORE robust than the system it fuzzes — a panic in the harness is a false bug that hides real ones. Reapplies at: W64 differential fuzz host, W74 raft fuzz harness, W88 VOPR environment.
  - **(SENIOR) When `harness_consumes_whole_slice` reports the two inputs reach identical states:**
    - Symptom: `[0x60,0x01]` and the 5-byte program produce the same gas/stack — the harness ignored the tail.
    - Why: the harness indexed a fixed prefix (`data[0]`, or `data.get(..1)`) instead of feeding the whole slice as bytecode — a stub left from scaffolding.
    - Fix: `Bytecode::new(data.to_vec())` over the ENTIRE slice; re-run; confirm distinct states.
    - Muscle: a fuzz target must consume all of its input or it can never explore — assert tail-sensitivity, don’t assume it. Reapplies at: W64 gas/call targets, W88 VOPR scenario decoder.
  - **(SENIOR) When `coverage_rises_in_smoke_run` reports `cov: 48` and flatlines:**
    - Symptom: 60-sec run; `cov:` stuck near 50 edges; no new corpus entries after the first second.
    - Why: even with the whole slice fed, an early `if data[0] > 0xf0 { return }` or a too-small `gas_limit` makes most inputs early-exit; the fuzzer can’t reach deep opcodes.
    - Fix: remove the early gate; set `gas_limit=1_000_000`; seed the corpus with a few valid PUSH/arith programs so the mutator has structure to grow from.
    - Muscle: coverage liveness is a hard acceptance gate — a green fuzz run with flat `cov:` is dead wiring, not a passing test. Reapplies at: W64 shape-aware targets, every fuzz target in the project.
  - **(SENIOR) When `reproduce_corpus_input_deterministic` reports two different outcomes for one input:**
    - Symptom: same bytes, two `run_one` calls, different gas_used or output.
    - Why: a `static mut`/lazy global in the interpreter (e.g. a cached precompile table, a thread-local scratch reused without reset) carries state across runs — non-reentrant.
    - Fix: reset/own all per-execution state inside `run_one`; no process-global mutable state reachable from the interpreter.
    - Muscle: a fuzz/differential target must be reentrant — process-global mutable state makes triage and differential comparison impossible. Reapplies at: W64 differential target (runs two VMs in one process), W74 raft, W88 VOPR.

  #### Phase 3 — Make the tests pass, one failure at a time (~55 min)

  Ordered newbie → expert.

  - **(NEWBIE) When `two_partitions_have_independent_offsets` reports a cross-partition offset collision:**
    - Symptom: partition 0 and partition 1 share an offset sequence; record at p1 gets offset 7 because the counter was global.
    - Why: the offset counter was a process-global `static AtomicU64` instead of a per-`Partition` field — Kafka offsets are per-partition by definition.
    - Fix: move the counter to a `Partition` field; assign on `append`; recover it per-partition from the `wal` tail.
    - Muscle: an address space that must be partition-local can never live in a process global — scope the counter to the partition. Reapplies at: W64 ISR per-partition high-watermark, W66 consumer-group per-partition committed offset, W84 projection.
  - **(SENIOR) When `offset_survives_restart` returns offset 0 after reopen:**
    - Symptom: reopening the partition restarts offsets at 0; the next append overwrites record 0.
    - Why: the next-offset wasn't recovered — the impl trusted an in-memory counter that died with the process, not the durable `wal` tail.
    - Fix: on open, scan the `wal` tail (+ segment manifest) to reconstruct the next offset; `append` continues from there.
    - Muscle: any monotonic counter that must survive restart is recovered from durable state, never re-initialized to 0. Reapplies at: W64 ISR high-watermark recovery, W84 projection checkpoint, W113 perp-dex-core read-side resume.
  - **(SENIOR) When `segment_roll_preserves_offset_continuity` reports a duplicated offset at a segment boundary:**
    - Symptom: the last record of segment N and the first of segment N+1 both report offset K; `read_from(K)` returns the wrong record.
    - Why: the roll opened the new segment and reset/re-read the offset from the segment instead of carrying the partition's running offset across the boundary — the torn-roll/off-by-one bug (D6).
    - Fix: the offset lives on the `Partition`, not the `Segment`; roll only swaps the storage segment, never the counter; recovery computes next-offset from the `wal` tail (not the segment manifest alone).
    - Muscle: segment boundaries are a storage detail, not an addressing detail — the offset must be continuous across rolls. Reapplies at: W64 ISR truncation-on-leader-change (KIP-101), W84 projection segment spanning.
  - **(SENIOR) When `read_from_is_zero_copy` shows allocations in the read path:**
    - Symptom: dhat traces 1000 allocs to `read_from` copying each record into a `Vec<u8>`.
    - Why: the impl copied out of the mmap instead of returning a borrowed slice — it didn't lean on `mmap-queue`'s zero-copy storage.
    - Fix: return `&[u8]` borrowed from the `mmap-queue` segment; tie the lifetime to the segment guard.
    - Muscle: when you inherit a zero-copy primitive, *forward its zero-copy property* — don't copy at the boundary. Reapplies at: W84 projection fan-out (consumers read borrowed slices), W113 read-side analytics plane.
  - **(EXPERT) When `forwards_durability_to_wal` finds a re-implemented durable-write loop in `segment.rs`:**
    - Symptom: the lint flags an `fsync`/durable-append loop inside `segment.rs`; `wal` is in `Cargo.toml` but unused on the append path.
    - Why: convenience — re-rolling a small append loop felt faster than wiring `wal`'s API. This is the "primitive twice" anti-pattern (RECONCILED_PLAN_v3 §3).
    - Fix: delete the loop; forward durability to `wal::append`; storage to `mmap-queue`; `log-distributed` only sequences + addresses.
    - Muscle: a composition crate forwards to inherited primitives — every re-implemented primitive is debt the W84 inheritance audit will charge back. Reapplies at: W64-66 ISR/consumer-group build-out, W84 v0.5, and the W97/W113 capstone inheritance audits.
  - **(EXPERT) When `recovery_is_deterministic_across_runs` produces two different recovered states:**
    - Symptom: same `wal`, 10 recoveries, two byte-different partition states.
    - Why: a `HashMap` iteration (e.g. over a partition→segment map) leaked into the recovery/manifest path; per-process hash-seed randomization reorders the manifest.
    - Fix: use a `BTreeMap` (key-ordered) for the partition→segment map; no HashMap iteration in recovery — the same determinism rule as W63 diff-test R3.
    - Muscle: recovery must be deterministic — every type reachable from it must be deterministic (no HashMap iteration). Reapplies at: W84 projection replay, W88 VOPR, the same rule taught in the matching-engine diff-test this week.
