- [ ] Run fuzzer. Address crashes. (~30 min)
- [ ] [HFT] **Build**: `matching-engine/tests/diff_test.rs` — property test: random sequences of orders → compare
  matching-engine output to a slow-but-obviously-correct reference matcher (sorted Vec sweep). Must match exactly. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: differential testing against an "obviously correct" reference is THE gold standard for matching-engine correctness — a naive sorted-Vec sweep is so simple it can't have subtle bugs, so any divergence between the fast and slow matcher MUST be in the fast one. This is the v0.5 ship gate (Thu): no diff-test green = no tag. Downstream: W74 raft-replicates this engine, and ANY non-determinism here corrupts replicas; W83 ledger reuses the diff-test pattern; W88 VOPR is built on top of the same determinism contract. A spurious diff-test failure (one that's not a real bug) costs days of debug-hunt — so the test itself must be bit-deterministic across runs.

  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: a fast matching engine has hundreds of micro-decisions per order (which side, which level, FOK pre-check, SmallVec inline-vs-spill). Unit tests cover obvious scenarios; adversarial sequences (PostOnly hitting an empty book; FOK racing IOC; 20-level sweep mid-cancel-storm) are infeasible to enumerate by hand. Property-based testing generates them mechanically. The reference matcher is the oracle — if it disagrees with the fast matcher on ANY sequence, the fast matcher is wrong.

  - **Requirements** — write in `crates/matching-engine/notes/63_diff_test_design.md`:
    - R1. A `ReferenceBook` implementing the same `submit` API as the production `OrderBook`, with intentionally trivial internals (sorted `Vec` of orders, linear scan, no indices).
    - R2. A proptest property `matching_matches_reference`: for any random sequence of 1..100 orders, the fast matcher's output `(fills, events, final_book_state)` equals the reference's, byte-exact.
    - R3. **Determinism floor**: no `HashMap`/`AHashMap` reachable from `match_order` may iterate its keys. Lookups OK; iteration NOT OK. Enforced by a CI lint that greps the source tree.
    - R4. **Float ban**: no `f32`/`f64` reachable from `match_order`. Enforced by `#![forbid(clippy::float_arithmetic)]` on the crate.
    - R5. **Shrinking**: on mismatch, proptest shrinks to a minimal failing sequence (≤ 10 orders ideally) so the debug-hunt has a small reproducer.
    - R6. **CI budget**: 1000 sequences runs in ≤ 10 minutes; PR CI uses 200 sequences (≤ 2 min), nightly uses 10k (≤ 100 min).
    - R7. **Reproducibility**: a fixed seed re-runs to the same sequence; the diff-test is byte-deterministic across 10 consecutive CI runs.
    - R8. **All TIFs covered**: the order generator emits every kind (`Limit`, `Market`, `IOC`, `FOK`, `PostOnly`) with realistic frequencies.

  - **Design walk-through** — answer each in your design doc; no peeking at TigerBeetle reference-checker until Phase 3:
    - D1. Sketch `ReferenceBook` in 20 lines. What's the data structure? (Hint: `Vec<Order>` for each side, sorted ascending for asks / descending for bids, re-sorted on every insert.) Why is "obviously correct" more important than "fast" here?
    - D2. The `submit(order)` method on ReferenceBook: write it as a 8-step sequential algorithm. No optimization — straight linear search for the best opposite-side order.
    - D3. proptest `arb_order` strategy: name the strategy's components (side, price range, qty range, kind weights). What's the right weighting for kinds? (Hint: production tape is ~80% Limit; the generator should reflect that.)
    - D4. Equality comparison: what's the canonical comparison shape? Compare `fills: Vec<Fill>` by? `events: Vec<MatchEvent>` by? `book_state` by? (Hint: sorted fills by (taker_id, maker_id); events as-is in order; book by canonical serialization.)
    - D5. Determinism floor (R3): name the 3 places in the production matcher where a HashMap iteration could sneak in (order_index, level lookup, event dedup). For each, name the deterministic substitute.
    - D6. Shrinking strategy: when the test fails, proptest tries smaller inputs. What's the right shrink for a `Vec<Order>` — drop the last element, halve the length, or remove arbitrary elements? Why does shrinking quality matter for debug time?
    - D7. **Pre-mortem #1 (spurious failure)**: write the 5-step trace where the diff-test fails NOT because of a real matching bug but because a HashMap iteration leaked into the fast matcher's snapshot path. The hash seed differs between two runs; the snapshot serialization differs; bytes diverge.
    - D8. **Pre-mortem #2 (race-condition false-positive)**: in v1.0 (W74 raft), the diff-test will run against a *concurrent* matcher under proptest. Name two ways a race could cause the diff-test to false-fail.
  - **Output**: `notes/63_diff_test_design.md` with R1–R8, D1–D8, ReferenceBook sketch, and the CI-lint plan.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  - **When `matching_matches_reference_property` fails on seq #847 with "fill.price 100 != 105":**
    - Symptom: proptest finds a sequence where the fast matcher emits a fill at price 105 but the reference emits 100. Shrinks down to: maker ask@100, taker buy Limit@105 qty 10.
    - Why: the fast matcher used `incoming.price` for `fill.price` instead of `maker.price` — the bug from W61 Phase 3 #1 (maker-price-not-taker-price) has regressed or was never fully fixed.
    - Fix: re-apply W61 Phase 3 fix — `fill.price = maker.price` always. Add `bench_typical_3_fill_order` from W61 to the regression suite. Add a debug_assert in the matcher: `debug_assert!(maker.price >= incoming.price)` for sells / `<=` for buys, depending on side. Run diff-test; expect green.
    - Muscle: a diff-test catches what unit tests miss — adversarial sequences expose the wrong-price bug even when handcrafted cases all happen to use price=limit. Reapplies at: W74 replicated matcher, W83 ledger MVCC, W88 VOPR.

  - **When `deterministic_across_10_runs` fails — runs 3 and 7 produce different "failed seed" outputs:**
    - Symptom: same code, same proptest seed, but two runs disagree on which sequence failed. Spurious nondeterminism.
    - Why: a HashMap iteration leaked into the snapshot path (R3 violation). The hash seed differs between runs (jemalloc / Rust's HashMap uses a random seed per process); the snapshot's byte order differs; the diff-test sees different "first divergence" points across runs.
    - Fix: enforce the lint (`lint_no_hashmap_in_match_path`). Audit every iter-over-HashMap call site in the matching crate. Replace with `BTreeMap` (key-ordered, deterministic) or `IndexMap` (insertion-ordered, deterministic). For `order_index` — keep AHashMap for lookups, but never iterate it; if you need a list of all orders, walk `book.bids`/`book.asks` (which are BTreeMaps) and collect.
    - Cost avoided: days of debug-hunt; bit-determinism preserved into W74 raft.
    - Muscle: determinism rules transitively — every type reachable from a deterministic test must itself be deterministic. Reapplies at: W60 det_test (taught), W74 raft over matching-engine, W83 ledger-deterministic, W88 VOPR.

  - **When `shrink_to_under_10_orders_on_failure` shrinks to 47 orders instead of ≤ 10:**
    - Symptom: the test passes (shrinking works) but the minimal repro is too large to be debuggable. 47 orders is not a clean reproducer.
    - Why: the proptest strategy for `Vec<Order>` uses default `shrink` which removes elements one-at-a-time. With dependencies between orders (e.g., the bug only manifests if a specific maker exists), shrinking can't make further progress.
    - Fix: customize the shrink — implement `Strategy<Value = Vec<Order>>` with `.prop_filter(|v| v.len() ≤ 100)` and explicit `prop_shrink` that tries (a) removing arbitrary elements, (b) reducing prices/qtys, (c) flipping sides. proptest's `prop::collection::vec` with default shrink is usually fine for ≤ 10 orders; if you see ≥ 20, the strategy needs custom shrink logic.
    - Muscle: shrinking quality IS debug time — invest in shrink for any property test that may fail on real bugs. Reapplies at: W88 VOPR property tests, every consensus property test.

  - **When `ci_budget_under_10_minutes` reports 38 min for 1000 sequences:**
    - Symptom: CI takes too long; PR turnaround degrades.
    - Why: the reference matcher is "slow on purpose" (linear scan, re-sort on every insert) — at 100 orders per sequence, each ref-match is O(n²) ≈ 10k ops. 1000 sequences × 10k ops × ~10 ns/op = 100 ms — that's fine. The actual cost is likely from proptest doing 10× as many cases as expected (e.g., shrinking on every "passing" case to ensure the strategy is shrink-correct), OR from running in debug mode.
    - Fix: (a) PR CI runs 200 sequences (nightly runs 10k). (b) Run diff-test in `--release` mode — `[profile.test] opt-level = 2` or specifically `cargo test --release diff_test`. (c) Verify proptest config: `Config { cases: 200, max_shrink_iters: 100, .. }` for PR CI.
    - Muscle: property test CI budget is a knob — separate fast PR cases from thorough nightly cases. Reapplies at: every property-test crate (W74, W83, W88).

  - **When `lint_no_hashmap_in_match_path` regresses after a future refactor:**
    - Symptom: someone adds `use std::collections::HashMap` deep in `match_order`'s call tree; CI catches it.
    - Why: this is the *intended* behavior — the lint exists exactly for this. The fix is to enforce the rule, not weaken the lint.
    - Fix: leave the lint in place. The author MUST replace HashMap with BTreeMap or IndexMap, OR justify with a `#[allow(deterministic_iter)]` and document that the path doesn't iterate. The reviewer's job is to confirm.
    - Muscle: lints encode invariants that the type system can't — once correct, they must NEVER be relaxed silently. Reapplies at: every bar-(c) determinism crate.

  - **5-year failure mode** (write in `notes/63_diff_test_followup.md` after green): when v2.0 adds cross-symbol matching (spreads), the ReferenceBook becomes a multi-book oracle and the proptest sequences span symbols. Single-symbol reference is no longer sufficient. State the migration: extend `arb_order` to emit cross-symbol orders; ReferenceBook becomes a `BTreeMap<Symbol, Book>` with the cross-symbol match logic mirrored as a separate function. Trigger: first cross-symbol order type lands.

  #### Phase 3 — Interpret the numbers when they miss, one failure at a time (~50 min)

  - **When `bench_v0_5_p99_9_under_50us` reports ~150 µs and `dhat_steady_state_alloc_rate` shows ~50 allocs/sec:**
    - Symptom: hdrhistogram shows p99.9 in the 100-200 µs range; the spike is periodic (~every 10 sec) and not workload-correlated. dhat traces the 50 allocs/sec to mimalloc's background purger.
    - Why: even after applying W58-W61 perf fixes (zero-alloc submit/encode/append), the *background* allocator-state evolves under churn — every ~10 sec, mimalloc rebalances its thread-cache → ~50-150 µs stall on whatever the shard thread is doing.
    - Fix: enforce *true* zero-allocation steady state. (a) Add a CI step running the bench with dhat/heaptrack that FAILS if allocation rate exceeds ~10/sec post-warmup. (b) Disable mimalloc purging during the bench window: `MIMALLOC_PURGE_DELAY=-1` (or `mi_option_set(mi_option_purge_delay, -1)`). (c) Trace every remaining allocator visit to a struct that should be pre-allocated — likely candidates from prior weeks: `SmallVec` spill (W61), BTreeMap node on new price level (W60), event-log encode-scratch oversize (W61). Iterate until rate ≤ 10/sec. For glibc malloc: switch to mimalloc or jemalloc (mandatory for bar-(c) crates).
    - Cost avoided: ~50-150 µs periodic spikes → < 1 µs steady; p99.9 from "passing-but-spiky" to "flat-line"; v0.5 becomes the regression baseline that W74 v1.0 (5 µs) and W82 v1.5 (1 µs) can tighten against without fighting allocator noise.
    - Muscle: bar-(c) "zero-allocation" means *measurably zero* in steady state — instrument and fail CI on regressions, don't trust eyeballed code review. Reapplies at: W74 matching-engine v1.0 bar-(c) gate, W83 ledger apply loop, W92 ledger v1.0 static-mem invariants, W110 chaos test SLO.

  - **When `reproducibility_5_runs_within_5pct` reports ~30% variance — runs report p99 between 8 and 15 µs:**
    - Symptom: same code, same host, 5 runs produce wildly different p99. Sometimes the v0.5 bar passes, sometimes it fails. CI flakes.
    - Why: dynamic CPU frequency scaling. During a 1 M order/sec bench, the CPU transitions between P-states asynchronously — bench thread runs at 2 GHz cold-start, jumps to 4 GHz turbo, drops to 3 GHz under thermal load. Each P-state transition takes ~50-200 µs. Thermal-throttling kicks in as the bench warms up; reproducibility tanks.
    - Fix: standardize the bench environment via the `tools/setup_bench_env.sh` from Phase 2. On Linux: `cpupower frequency-set -g performance` pins max frequency; `taskset -c 2` pins to an isolated core; `echo 0 > /sys/devices/system/cpu/cpu3/online` offlines core 2's SMT sibling; `kernel.timer_migration=0` and `kernel.sched_min_granularity_ns` set large to prevent scheduler interference. Document the environment in `MATCHING_BENCH.md`; CI runs on a dedicated bare-metal box (W106+ ops rig). Local bench-vs-CI numbers must match within 5%. macOS: document the limitation (no clean equivalent); bar-(c) numbers live on the Linux ops rig only.
    - Cost avoided: ~30% p99 variance → ≤ 5% variance; restores ability to detect a true 5% regression (vs being lost in environmental noise); without this fix, the v1.0 5 µs gate is unmeasurable because the noise floor is higher than the target.
    - Muscle: bar-(c) latency targets require a controlled bench environment — CPU pinning, frequency-pinning, no HT siblings, no thermal headroom games. The infra setup is *part of the bar*, not separate from it. Reapplies at: W74 v1.0 5 µs gate, W82 v1.5 1 µs gate (extra-strict env required), W92 ledger v1.0 1 µs commit latency, W106+ ops rig calibration.

  - **When `bench_v0_5_throughput_1m_per_sec` reports ~600k/sec (40% below target):**
    - Symptom: bench can't sustain 1 M orders/sec; throughput plateaus at ~600k.
    - Why: hypothesis A — criterion harness overhead dominates per-op cost (use `iter_custom` with N=10k+ batched orders). Hypothesis B — the workload mix has too many cancels (cancel path is slower than match path; reduce cancel ratio if the target is "submit throughput"). Hypothesis C — the WAL fsync isn't deferred (regression of W61 Phase 3 #2); fsync rate is too high.
    - Fix: check each hypothesis in order. A: bench harness — switch to `iter_custom` if not already; verify with `cargo flamegraph` that criterion overhead is < 10% of CPU. B: dial the mix to the realistic ~10% cancels; confirm target. C: instrument fsync rate; assert ≤ 350/sec at 1M ops/sec; if higher, regression in event_log path.
    - Muscle: throughput shortfalls have a small set of suspects — harness overhead, mix-misspecification, deferred-syscall regression. Audit each in order. Reapplies at: every throughput bench in the project.

  - **When `bench_v0_5_p99_under_10us` reports p99 = 9.8 µs (passes the bar but with no margin):**
    - Symptom: bar passes but the margin is < 5%. Any tiny regression in W64-W73 pushes it over.
    - Why: this isn't a failure — but it's a fragile pass. The threshold has no headroom for future weeks' additions (W66 perpetuals, W67 raft membership, etc).
    - Fix: document the slim margin in `v0_5_bench_results.md`. Set a CI alert at p99 ≥ 9 µs (warn but don't fail) so any regression is flagged early. The actual bar-fail line stays at 10 µs, but the alert at 9 µs gives early warning.
    - Muscle: a bar with no margin is debt — instrument an early-warning at 90% of the threshold so regressions are caught before they break the build. Reapplies at: every bar-(c) bench in the project.

  - **5-year failure mode** (write in `notes/63_v0_5_bench_followup.md` after green): when v2.0 ships ARM-native production hardware (Graviton 4+, Ampere Altra), the bench numbers from x86_64-linux are no longer the reference — ARM has different cache hierarchies (128 B effective L2 prefetch on Apple Silicon, 64 B on Graviton) and different P-state semantics. State the migration: run the bench on BOTH x86_64 and aarch64 ops rigs; record per-arch baselines; gate on the worse of the two. Trigger: production hardware migration.
