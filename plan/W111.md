**Monday — Identify hot spot**

- [ ] perf top under 1M orders/sec sustained load. Top 3 functions. (~30 min)
  - **Why**: at 1M orders/sec, every microsecond of P99 maps to ~$thousands/year in HFT terms; the matching engine is
    the *only* crate where the bar is *single-digit microseconds*, so micro-architectural awareness (cache lines,
    branch predict, TLB) is mandatory. Profiling without controlling for noise (turbo, hyperthreading, kernel sampling
    overhead) produces garbage flame graphs that send you optimizing the wrong function.
  - **Read first**: Brendan Gregg "Systems Performance" §4 (perf), §6 (CPUs); Intel Optimization Reference Manual
    §3.4 (cache + TLB); Cliff Click's lock-free hash-table talk (for top-of-book design later this week); LMAX
    Disruptor paper §3 (mechanical sympathy).
  - **Design** (profiling rig):
    ```bash
    # Pinning + isolation
    sudo cpupower frequency-set -g performance
    echo 1 | sudo tee /sys/devices/system/cpu/intel_pstate/no_turbo
    # Isolate cores 4-7 via kernel boot: isolcpus=4-7 nohz_full=4-7 rcu_nocbs=4-7
    taskset -c 4 ./matching-engine --shard 0 ...
    # Profile
    perf record -F 99 -p $(pidof matching-engine) -g --call-graph dwarf -- sleep 60
    perf script | inferno-flamegraph > flame.svg
    # Cache analysis
    perf stat -e cache-references,cache-misses,LLC-load-misses,dTLB-load-misses,branch-misses -p $PID -- sleep 30
    ```
    **Invariants**: (1) profile *only* with the production binary (`--profile release` + `lto = true` + `codegen-units
    = 1`); debug-info via `debug = "line-tables-only"`. (2) Always profile under sustained load *after* warmup
    (≥ 30s) — JIT-equivalent code-cache effects don't apply to AOT Rust, but kernel page-fault settling does. (3)
    Record the per-core C-state and frequency during the run for repeatability.
  - **Build steps**:
    1. (~5 min) Provision profiling: turbo off, governor performance, hyperthreading off (`echo off | sudo tee
       /sys/devices/system/cpu/smt/control`).
    2. (~10 min) Capture baseline: `perf stat` for 60s under feed at 500k orders/sec; record IPC, LLC-miss%,
       branch-miss%.
    3. (~10 min) `perf record` → flamegraph; identify top-3 self-time functions.
    4. (~5 min) For each top function, capture `perf annotate` to see which instruction within the hot loop is
       counting; expect either a load (cache miss) or a branch (misprediction).
  - **Pitfalls**:
    *NoisyNeighbor*: **Symptom**: P99 jumps 3x for 5min stretches in profile; root cause is `ksoftirqd` waking on
       same physical core. **Fix**: `isolcpus` + `nohz_full` + `rcu_nocbs` boot params; bind IRQs off the isolated
       cores via `/proc/irq/*/smp_affinity`.
    *MisleadingFlameWidth*: **Symptom**: `matchAndExecute` shows 60% width in flamegraph; you "fix" it; total time
       barely moves. Width was inclusive of children; actual self-time was elsewhere. **Fix**: read *icicle* graphs or
       differential flamegraphs; use `perf report --no-children`.
    *DebugBuildProfile*: **Symptom**: profile shows `<core::option::Option<T>>::unwrap` hot — only because release
       inlines that away; you're profiling the wrong binary. **Fix**: assert `target/release` + `lto=true` in the
       profile script; refuse to run on non-release.
    *SamplingSkew*: **Symptom**: `perf -F 99` aliases with a 10ms timer in the matching engine; certain functions
       under-represented. **Fix**: use a prime frequency (`-F 997`); cross-check with `-F 4001` and ensure top-3
       functions overlap.
  - **Test scenarios**: (a) compare flamegraph at 100k vs 500k vs 1M orders/sec — verify the top-3 functions shift
    sublinearly (otherwise you have a queueing-theory problem, not a CPU problem); (b) repeat with HT enabled vs
    disabled — quantify the impact; (c) run with feed deterministic seed re-used — verify top-3 stable across runs.
  - **Acceptance**: top-3 hot functions identified with self-time ± 5% repeatable across 3 runs same seed; IPC ≥ 2.0
    on the hot path (current baseline target); LLC-miss% < 5% — if higher, that's the priority for the week.
  - **Downstream**: drives the Tuesday/Wednesday redesigns (ring vs VecDeque, lock-free top-of-book); the same harness
    will be used in W111-Thursday's P99 bench and the post-tag regression watch.

**Tuesday — Order book tree comparison redux**

- [ ] We chose BTreeMap at W60. With profile data, consider replacing the per-price-level VecDeque with a fixed-size
  ring (cache-friendlier). (~30 min)
  - **Why**: VecDeque has two cache-unfriendly properties at HFT scale: (a) head/tail wraparound forces a branch on
    every `push_back` to test wrap-around, and (b) `len = 0` empty levels still hold an 8-byte allocation pointer +
    cap/len metadata (24B), bloating the BTreeMap node and causing extra cache lines per level traversal. A
    fixed-size ring per level (e.g. `[Order; 64]` with head/tail u8 indices in a single cache line) packs more orders
    per line and removes the heap indirection on the inner loop. False sharing on `head`/`tail` between threads is the
    classic foot-gun.
  - **Read first**: LMAX Disruptor `Sequence.java` (false-sharing padding via `@Contended`); `crossbeam-deque`
    `src/lib.rs` (their ring slot layout); Intel Optimization Reference §3.6.5 (cache-line packing); your own W60
    decision notes (the BTreeMap choice rationale — what was the asymmetry?).
  - **Design**:
    ```rust
    #[repr(align(64))]               // cache-line aligned
    struct PriceLevel {
        head: u8,                    // wraps modulo CAP
        tail: u8,
        len: u8,
        _pad0: [u8; 5],              // bring head/tail/len into single u64 read
        total_qty: u32,              // aggregate for top-of-book quick read
        _pad1: [u8; 4],
        orders: [Slot; 64],          // 64 × 24B = 1536B (24 cache lines but contiguous)
    }
    #[repr(C)]
    struct Slot {
        order_id: u64,                // 8
        qty: u32,                     // 4
        flags: u32,                   // 4
        ts_ns: u64,                   // 8 — total 24B
    }
    ```
    **Invariants**: (1) Slots occupy `[head..tail mod CAP]` always; CAP is a power of two so `idx & (CAP-1)` replaces
    modulo. (2) If level fills, *spillover* to a heap `Vec<Slot>` — log a metric `price_level_spill_total` so we can
    size CAP correctly. (3) Removing an order in the middle is O(1) via mark-tombstone + lazy compaction on the next
    full traversal — *do not* memmove during match.
  - **Build steps**:
    1. (~5 min) Define `PriceLevel` with `#[repr(align(64))]`; assert `std::mem::size_of::<PriceLevel>() % 64 == 0`
       in a `const_assert!`.
    2. (~10 min) Implement `push_back`, `pop_front`, `find_by_oid` (linear over CAP elements is fine — CAP=64 fits 1
       cache line of pointers if Slots were pointers, but with inline 24B Slots it's 24 cache lines worth — still
       prefetcher-friendly because sequential).
    3. (~5 min) Spillover: when `len == CAP`, allocate a `Vec<Slot>` overflow appended to the level.
    4. (~5 min) Update `matchAndExecute` hot loop to use `peek_head` (no branch on wrap because we use bitmask) +
       `pop_front`.
    5. (~5 min) Bench: A/B against `VecDeque` baseline at 500k orders/sec; expect ≥20% reduction in dTLB misses and
       ≥15% reduction in self-time of `matchAndExecute`.
  - **Pitfalls**:
    *FalseSharingHeadTail*: **Symptom**: 2 threads writing different sides (bid level vs ask level adjacent in memory)
       cause 10× cache-line ping-pong; latency *worse* than VecDeque. **Fix**: pad each `PriceLevel` to align(64) AND
       size to a multiple of 64; ideally pad to 128 on x86 (some prefetchers fetch line-pairs).
    *CAPTooSmallSpills*: **Symptom**: under cancel-storm one price level holds 5000 orders; spillover triggers heap
       allocations on every level traversal; metrics show `price_level_spill_total` growing linearly. **Fix**: choose
       CAP from production data (top-decile per-level depth) and emit alert if spill rate > 1%; consider a 2-level
       hierarchy (CAP=64 inline + CAP=512 overflow ring) before falling back to heap.
    *TombstoneAccumulation*: **Symptom**: lazy-tombstone compaction never triggers because the level is always partially
       drained; `len` reads stay accurate but the slot array fills with tombstones, hitting CAP early. **Fix**: on
       `pop_front`, eagerly skip leading tombstones; on `find_by_oid` failure ratio exceeding threshold, compact.
    *BranchOnWrap*: **Symptom**: switch from VecDeque didn't improve branch-miss% because the compiler couldn't prove
       CAP was a power of two. **Fix**: declare `const CAP: usize = 64;` and use `idx & (CAP - 1)` explicitly; verify
       in `cargo asm` that the modulo became an AND.
  - **Test scenarios**: (a) random ordered insert+match across 10k levels — verify `total_qty` matches sum of slots
    after every op; (b) 5000-order cancel-storm into a single level — verify spillover triggers and recovers without
    correctness loss; (c) interleaved cancel + add at head + match at head — verify head-pointer never goes
    backwards.
  - **Acceptance**: P99 single-symbol single-core at 500k orders/sec drops by ≥ 15% vs VecDeque baseline; LLC-miss%
    drops by ≥ 5pp; no correctness regression in the existing matching-engine VOPR suite.
  - **Downstream**: feeds Wednesday's lock-free top-of-book design (the new layout makes the head-slot ATOMIC-readable
    in a single load); the new size + alignment is documented in the M30 bar-(c) zero-alloc audit on the hot path.

**Wednesday — Lock-free price level**

- [ ] One bid + one ask per symbol at any time has 99% of contention. Consider a lock-free price level for the
  top-of-book. (~30 min)
  - **Why**: top-of-book is hit by *every* market-data tick and by *every* incoming aggressive order — at 1M orders/sec
    even a 100ns spinlock acquire dominates. If readers (quote dissemination, risk checks, internal subscribers) and
    writers (matching engine) contend on a `Mutex`, you see P99.9 spikes when the writer holds the lock through a
    full level traversal. A *lock-free seqlock* over the top-of-book (price + qty + side) lets readers complete in
    ~10ns and writers in ~30ns — and exposes a correctness property (readers may see torn reads and must retry,
    detected by the seqlock counter).
  - **Read first**: Linux kernel `include/linux/seqlock.h` (the canonical seqlock); Dmitry Vyukov's "Single Writer
    Principle" notes; `crossbeam-utils::atomic::AtomicCell` (when it falls back to Mutex — *avoid* that path);
    LMAX Disruptor `RingBuffer::next` (write-side claim sequence).
  - **Design** (single-writer, multi-reader seqlock over a top-of-book snapshot):
    ```rust
    #[repr(align(64))]
    pub struct TopOfBook {
        seq: AtomicU64,        // even = stable, odd = writer in flight
        bid_price: AtomicI64,  // packed: i32 ticks + i32 qty if we accept 4G qty
        bid_qty: AtomicU32,
        ask_price: AtomicI64,
        ask_qty: AtomicU32,
        _pad: [u8; 24],        // pad to 64B
    }
    impl TopOfBook {
        // Writer: matching engine main thread for this symbol shard.
        pub fn store(&self, snap: Snap) {
            let s = self.seq.fetch_add(1, Release);            // s becomes odd
            self.bid_price.store(snap.bid_price, Relaxed);
            self.bid_qty.store(snap.bid_qty, Relaxed);
            self.ask_price.store(snap.ask_price, Relaxed);
            self.ask_qty.store(snap.ask_qty, Relaxed);
            self.seq.store(s.wrapping_add(2), Release);        // back to even
        }
        // Reader: any thread.
        pub fn load(&self) -> Option<Snap> {
            loop {
                let s1 = self.seq.load(Acquire);
                if s1 & 1 == 1 { core::hint::spin_loop(); continue; }
                let snap = Snap {
                    bid_price: self.bid_price.load(Relaxed),
                    bid_qty:   self.bid_qty.load(Relaxed),
                    ask_price: self.ask_price.load(Relaxed),
                    ask_qty:   self.ask_qty.load(Relaxed),
                };
                let s2 = self.seq.load(Acquire);
                if s1 == s2 { return Some(snap); }
                // else retry — torn read.
            }
        }
    }
    ```
    **Invariants**: (1) Single writer per `TopOfBook` (one shard owns one symbol) — multiple writers require an
    upgrade to a CAS-based wait-free design and are forbidden. (2) `seq` even ↔ snapshot stable. (3) Reader retry is
    bounded: if a reader spins more than 16 iterations, it should yield (avoid livelock under writer thrash).
    (4) Memory ordering: writer uses `Release` on `seq`; reader uses `Acquire` on `seq` reads.
  - **Build steps**:
    1. (~5 min) Define the struct with `#[repr(align(64))]`; const-assert size is exactly 64B.
    2. (~10 min) Implement `store` and `load` per design above; add `debug_assert!` that the writer thread ID is
       constant (per-shard pinning).
    3. (~5 min) Wire matching-engine to call `store` after every level mutation that changes top-of-book.
    4. (~5 min) Wire quote-disseminator and risk-check fast-path to call `load` instead of grabbing the order-book
       mutex.
    5. (~5 min) Microbench: 1 writer + 8 readers, measure reader-load P99 and writer-store P99 — both should be sub-100ns.
  - **Pitfalls**:
    *MultiWriterUB*: **Symptom**: a second thread (e.g. cancel-via-fastpath) writes the top-of-book; readers
       intermittently see corrupted price/qty because both writers raise `seq` to odd simultaneously. **Fix**: route
       all writes through the single owning shard thread (channel + run-on-shard pattern); enforce with a debug-only
       per-instance `OnceCell<ThreadId>` panicking on second writer.
    *RelaxedOrderingTearReadOnNonX86*: **Symptom**: passes on x86 (TSO), tears on ARM64 in production — i64 store
       observed before the corresponding qty store. **Fix**: use `Release`/`Acquire` not `Relaxed` for the seq, and on
       architectures with weaker ordering, prefer a single packed `AtomicU128` if available, else accept the seqlock
       retry as the consistency mechanism (it already covers tear cases by design).
    *SpinForeverDOS*: **Symptom**: writer is preempted while `seq` is odd; readers spin forever on a busy core.
       **Fix**: bounded retry (e.g. 16 spins → exponential backoff → fall back to `Mutex` slow path that emits an alert
       metric `top_of_book_slow_path_total`); writer thread is real-time scheduled (`SCHED_FIFO`) to minimize chance.
    *PaddingHole*: **Symptom**: removed `_pad` field after "cleanup"; benchmark shows random 30% regression because
       struct now shares a cache line with adjacent fields and false-shares. **Fix**: hold the line — alignment +
       padding is *load-bearing*; cover with a layout-test that asserts size+alignment.
  - **Test scenarios**: (a) loom test (single-writer N-reader) for `store/load` — verify no reader returns inconsistent
    snap; (b) inject writer preemption (via `SIGSTOP` during the odd-seq window) — readers should bounded-retry +
    fall back, then resume correctly post-`SIGCONT`; (c) measure under 100% read load with no writer — readers should
    complete in a single iteration, P99 < 30ns.
  - **Acceptance**: read-side P99 ≤ 50ns single-thread, ≤ 100ns under 8-reader load; writer-side P99 ≤ 100ns; loom
    test green; no torn reads detected in a 1B-iteration stress run.
  - **Downstream**: dissemination + risk-check fast-paths consume `load()`; the seqlock pattern is documented in the
    matching-engine post and re-used in ledger-deterministic's read-only-snapshot reads.

**Thursday — Bench: P99 latency**

- [ ] Target <2µs P99 single-symbol single-core at 500k orders/sec. Current state captured. (~30 min)
  - **Why**: this is the *contract* against tier-A HFT performance for in-process matching; without a documented and
    repeatable bench result, the matching-engine claim is hand-wave. The bench also doubles as a regression watchdog:
    Phase 7+ tuning that pushes P99 above 2µs without a recorded reason is a stop-the-line.
  - **Read first**: `criterion-rs/criterion.rs` `src/measurement.rs` (sampling theory: how Criterion estimates
    confidence intervals); HdrHistogram-rs `src/lib.rs` (the histogram contract for P99 estimation — *not*
    simple `quantile_at`); LMAX Disruptor latency methodology doc.
  - **Design** (bench harness):
    ```rust
    // benches/single_symbol_p99.rs
    fn bench(c: &mut Criterion) {
        let mut g = c.benchmark_group("single_symbol_500k");
        g.throughput(Throughput::Elements(500_000));
        g.measurement_time(Duration::from_secs(30));
        g.sample_size(60);
        g.bench_function("matching_engine", |b| {
            b.iter_custom(|iters| {
                let mut hist = Histogram::<u64>::new_with_bounds(1, 10_000_000, 3).unwrap();
                let mut feed = SyntheticFeed::seeded(SEED, 500_000);
                let me = MatchingEngine::new();
                let warm = 50_000;
                for _ in 0..warm { me.process(&feed.next()); }   // warmup
                let start = Instant::now();
                for _ in 0..iters {
                    let msg = feed.next();
                    let t0 = nano();
                    me.process(&msg);
                    let dt = nano().wrapping_sub(t0);
                    hist.record(dt).unwrap();
                }
                eprintln!("P50={} P99={} P999={} ns",
                    hist.value_at_quantile(0.5), hist.value_at_quantile(0.99),
                    hist.value_at_quantile(0.999));
                start.elapsed()
            });
        });
    }
    ```
    **Invariants**: (1) Bench process is pinned to an isolated core; bench peer process (feed gen) on a different
    core, ideally a different NUMA node to model production layout. (2) Bench reports P50, P99, P999 from a *single*
    HdrHistogram over the run — never average per-iter P99s (that gives the wrong answer). (3) Bench seed is fixed
    and recorded in the result so historical comparison is apples-to-apples.
  - **Build steps**:
    1. (~5 min) Pre-bench provisioning script (turbo off, governor performance, SMT off, isolcpus on benchmark core).
    2. (~10 min) Implement the criterion bench with `iter_custom` + HdrHistogram capture.
    3. (~5 min) Record baseline: P50, P99, P999 to `bench/baseline.json`; commit.
    4. (~5 min) Add the bench to CI nightly with a 10% regression budget (fail if P99 worsens > 10% vs baseline).
    5. (~5 min) Document the bench protocol in `crates/matching-engine/BENCH.md` (host config + repro steps).
  - **Pitfalls**:
    *CoordinatedOmission*: **Symptom**: P99 looks great (1µs) but real-world traffic shows 50ms tail. Cause: the bench
       loop times only the *processing* of each message, never the *wait* if `process` blocks; under burst, the queue
       grows but each individual `process` is fast. **Fix**: HdrHistogram-rs `record_corrected_with_max_interval(...)`
       — accounts for coordinated omission by inflating samples when interval exceeds expected.
    *WarmupTooShort*: **Symptom**: P99 reported is dominated by first-touch page faults and L1-i misses. **Fix**:
       warmup of at least 50k iterations *before* histogram recording starts; verify warmup is sufficient by checking
       P50 stability across two runs (variance < 5%).
    *FeedRateMismatch*: **Symptom**: bench advertises 500k orders/sec but `iter_custom` runs as fast as possible —
       no pacing — so it's actually a "as fast as possible" bench. **Fix**: pace via `spin_sleep` to target the rate
       exactly; record actual achieved rate alongside P99.
    *NoiseFromOtherTracking*: **Symptom**: enabling `tracing` spans during bench inflates P99 by 200ns/op.
       **Fix**: compile the bench with `tracing` at `LevelFilter::OFF` and feature-flag the span emission out of the
       hot path; document in BENCH.md that benches must be run with `--no-default-features --features=bench`.
  - **Test scenarios**: (a) run on identical hardware twice with same seed — P99 within ± 3%; (b) run on identical
    hardware with feed-gen on same core (forcing context switches) — verify P99 degrades by ≥ 5× (sanity check
    isolation); (c) inject a 100µs sleep into a non-hot helper — verify the bench *fails* the regression budget.
  - **Acceptance**: P99 < 2µs at 500k orders/sec on the documented host config; P999 < 10µs; achieved rate within
    5% of target; baseline.json committed + CI nightly green for 7 consecutive runs before tagging v1.1.
  - **Downstream**: this baseline becomes the *acceptance gate* for any matching-engine PR; the result is cited in
    Blog #5/#7 and in the M30 HFT-crate-quality scorecard; it forms the proof for the runtime-thread-per-core
    contract documented at v2-seed phase.
