  #### Phase 1 — Problem, requirements, design (~15 min, no code yet)

  - **The problem this primitive solves**: a flamegraph captured under unconstrained noise is worse than
    no flamegraph — it points you at the wrong function. The 4 classic profiling lies are: (1) turbo
    boost active → IPC varies 30%+ across runs; (2) SMT enabled → sibling-hyperthread contention shows as
    "your" function being slow; (3) sampling frequency aliases with the workload period; (4) debug-build
    profiling shows `unwrap` hot because release would have inlined it away. Getting the profiling
    discipline right is the prerequisite for every optimization in Tue/Wed.

  - **Requirements** — write in `crates/matching-engine/notes/111_perf_profile_design.md`:
    - R1. Profile ONLY against `target/release` built with `lto=true`, `codegen-units=1`,
      `debug="line-tables-only"`. Profiling script asserts the binary path matches.
    - R2. Profiling rig provisioning: turbo off, governor `performance`, SMT off, `isolcpus` +
      `nohz_full` + `rcu_nocbs` on bench cores, IRQs bound off bench cores.
    - R3. Warmup ≥ 30 s of sustained load before sampling begins.
    - R4. Sampling frequency is prime (`-F 997` or `-F 4001`); cross-checked with two different
      prime frequencies to ensure top-3 functions agree.
    - R5. Capture: `perf stat -e cache-references,cache-misses,LLC-load-misses,dTLB-load-misses,
      branch-misses` for 60 s; `perf record -F 997 ... -g --call-graph dwarf` for 60 s; flamegraph via
      `inferno-flamegraph`; per-function `perf annotate`.
    - R6. Repeatability: top-3 self-time functions ± 5% across 3 runs with same seed.
    - R7. Acceptance gates: IPC ≥ 2.0 on hot path; LLC-miss% < 5%; if either misses, that's the
      priority focus for the week.

  - **Design walk-through** — answer each in your design doc; no peeking at Brendan Gregg's perf
    examples until Phase 3:

      core's `nr_running` stays at 1 during profile via `mpstat -P 4 1`.
    - Muscle: profile noise is almost always a bench-rig provisioning failure; fix the rig before
      blaming the code. Reapplies at: W111 Thu bench harness, W113 hot-path PR review.

  - **When `freq_997_vs_4001_agree_on_top3` shows disjoint top-3:**
    - Symptom: `-F 997` says [match_and_execute, push_back, find_by_oid]; `-F 4001` says
      [match_and_execute, total_qty_update, peek_head].

      (e.g. metric flush at 10 ms cadence). The hot function at one frequency is artifact, not signal.

    - Muscle: sampling artifacts hide in single-frequency profiles; always cross-validate with two
      primes. Reapplies at: W113 PR-review benchmarks, W120 regression detection.

  - **When `script_refuses_non_release_binary` profiles a debug binary anyway:**
    - Symptom: flamegraph shows `<core::option::Option<T>>::unwrap` at 25% self-time.
    - Why: profile script invoked the binary by name without verifying the build profile; it found
      `target/debug/matching-engine` first in PATH.
    - Fix: script does `file target/release/matching-engine | grep "not stripped"` AND parses the
      Rust build-id to confirm release profile. Refuses if anything mismatches.
    - Muscle: profiling discipline is a script invariant; never trust the user to remember.
      Reapplies at: W111 Thu bench, W120 production profile capture.

  - **When `ipc_meets_threshold_or_alert` shows IPC = 1.2:**
    - Symptom: per-cycle instruction throughput is half of what modern x86 can do; you're cache-bound,
      not compute-bound.
    - Why: hot path is dominated by L1/L2 cache misses on the order-book traversal (per-level VecDeque

    - Fix (this week): Tue's ring redesign collapses the indirection; Wed's seqlock removes lock
      contention. Both target IPC ≥ 2.0 as a side-effect.
    - Muscle: IPC < 2.0 on Skylake+ means memory-bound; cache-line-aware redesign is the lever.
      Reapplies at: W111 Tue ring, W113 hot-path PR optimization.

**Tuesday — Order book tree comparison redux**

- [ ] **Build**: `crates/matching-engine/src/price_level.rs` — replace per-level `VecDeque<Order>` with a fixed-size
  ring `PriceLevel { orders: [Slot; 64], head: u8, tail: u8, ... }` (cache-friendlier). (~total 60 min across 3 phases)
  - 🔧 **Why this matters**: VecDeque has two cache-unfriendly properties at HFT scale: (a) head/tail
    wraparound forces a branch on every `push_back`, and (b) `len = 0` empty levels still hold an
    8-byte allocation pointer + cap/len metadata (24B), bloating the BTreeMap node and causing extra
    cache lines per level traversal. A fixed-size ring (`[Order; 64]` with head/tail u8 indices in a
    single cache line) packs more orders per line and removes the heap indirection on the inner loop.
    Downstream consumers: W111 Wed lock-free top-of-book uses the new layout's head-slot for atomic
    single-load reads; W113+ matching-engine optimization PRs; M30 bar-(c) zero-alloc audit cites this
    layout.

  #### Phase 1 — Problem, requirements, design (~20 min, no code yet)

  - **The problem this primitive solves**: per-level `VecDeque` indirection adds a cache miss per level
    traversal; at 1 M orders/sec across thousands of price levels, that's the dominant cost. The ring
    fixes it but introduces classic foot-guns: false sharing on head/tail across adjacent levels,
    spillover when a level exceeds CAP, tombstone accumulation under cancel-heavy workloads.

  - **Requirements** — write in `crates/matching-engine/notes/111_price_level_design.md`:
    - R1. `PriceLevel` is `#[repr(align(64))]` and `size_of::<PriceLevel>() % 64 == 0`
      (`const_assert!`).
    - R2. CAP is a power of two (default 64); wrap-index is `idx & (CAP - 1)`; compiler proves modulo
      → AND in `cargo asm`.
    - R3. Slots occupy `[head..tail mod CAP]`; `len = (tail - head) mod CAP`.
    - R4. Spillover: when `len == CAP`, allocate a heap `Vec<Slot>` overflow appended to the level;
      emit `price_level_spill_total` counter.
    - R5. Middle-removal is O(1) via tombstone (set Slot.flags |= TOMBSTONE); lazy compaction on
      `pop_front` skips leading tombstones; full compaction triggered when tombstone ratio > 50%.
    - R6. `total_qty: u32` aggregate is kept in sync — top-of-book reads it in a single load without
      walking slots.
    - R7. Bench A/B vs VecDeque baseline: P99 drops ≥ 15%, LLC-miss% drops ≥ 5 pp, dTLB-miss drops
      ≥ 20%; no correctness regression in matching-engine VOPR suite.

  - **Design walk-through** — answer each in your design doc; no peeking at `crossbeam-deque`
    until Phase 3:
    - D1. Why u8 for head/tail (not usize)? What does it cost? (Hint: 1-byte vs 8-byte; cache-line
      packing.)
    - D2. Slot layout — 24 bytes. Why not pad to 32 (cache-line-aligned)? Trade-off.
    - D3. Cache-line analysis: `[Slot; 64]` × 24B = 1536 B = 24 cache lines per level. Hot fields
      (head, tail, total_qty) live in WHICH cache line? Why does it matter?
    - D4. False-sharing scenario: write the 4-step trace where two adjacent `PriceLevel` instances
      share a cache line, thread A writes head of level N, thread B writes head of level N+1, both
      see ping-pong. Convince yourself align(64) + size%64==0 prevents it.
    - D5. Spillover: when does heap allocation happen on the hot path? What's the metric you watch?
    - D6. Tombstone vs memmove: argue why tombstone+compact is better than memmove for matching
      semantics. (Hint: middle-removal happens during cancel, often clustered.)
    - D7. **Pre-mortem (the load-bearing question)**: write the 5-step trace where (a) you switch to
      ring, (b) `cargo asm` confirms ` idx & (CAP-1)` is a single AND, (c) bench shows zero
      improvement, (d) you discover `total_qty` is recomputed by walking slots every op, defeating
      the cache win. Convince yourself R6 catches this.
  - **Output**: `notes/111_price_level_design.md` with R1–R7, answers to D1–D7, the struct layout
    diagram with byte offsets, the cache-line walk.

  #### Phase 3 — Make the tests pass, one failure at a time (~25 min)

  - **When `wrap_compiles_to_and` finds `div` instead of `and` in asm:**
    - Symptom: `cargo asm` shows `div r8, 64` not `and r8, 63`.
    - Why: CAP was declared `let CAP: usize = 64;` (runtime value) not `const CAP: usize = 64;`;
      compiler couldn't prove it was a power of two.
    - Fix: `const CAP: usize = 64;` (or `const CAP: usize = 1 << 6;`). Add explicit `idx & (CAP - 1)`
      in the index expression. Verify in asm.
    - Muscle: compiler can prove power-of-two-AND only if the divisor is a compile-time `const`.
      Reapplies at: W113 hot-path optimization, W120 codegen review.

  - **When `no_false_sharing_adjacent_levels` shows 5× slowdown vs single-thread:**
    - Symptom: 2 threads, adjacent levels, wall-time = 5× single-thread; cache-coherence ping-pong.
    - Why: `PriceLevel` was 96 bytes — fit in 2 cache lines, but two adjacent instances overlap one
      cache line. Updates to head of level N and head of level N+1 both touch line K.
    - Fix: `#[repr(align(64))]` on `PriceLevel`; pad to next multiple of 64. Add a size assertion.
      On x86, consider padding to 128 (some prefetchers fetch line pairs).
    - Cost avoided: 4× wall-time at the matching hot path; THE classic HFT footgun.
    - Muscle: cache-line ownership is per 64-byte chunk; alignment + size-padding both required.
      Reapplies at: W111 Wed seqlock, W113 lock-free queue redesign.

  - **When `total_qty_in_sync` fails after 142 ops:**
    - Symptom: `total_qty` drifts from sum-of-slots after a Cancel op.
    - Why: Cancel set tombstone but forgot to subtract qty from `total_qty`.
    - Fix: Cancel (and pop and partial-fill) update `total_qty` atomically with the slot mutation.
      Wrap in a `mutate(|slots, total_qty| { ... })` closure that enforces the invariant.
    - Muscle: aggregate fields require disciplined update points; one missed path corrupts forever.
      Reapplies at: W111 Wed top-of-book qty, W113 order-book consistency.

  - **When `spillover_triggers_at_cap` shows OOM under cancel-storm:**
    - Symptom: under a 5000-order cancel storm into one level, spillover Vec grows unbounded; OOM.
    - Why: spillover always allocates and never compacts; tombstones accumulate in main ring;
      effective capacity stays at zero so every new order spills.
    - Fix: spillover triggers eager compaction of the main ring first (sweep tombstones, slide live
      slots to head=0). If still full after compaction, spillover. If spillover > 10% of CAP, emit
      alert metric `price_level_spill_alert_total`.
    - Muscle: spillover is the last resort; compaction comes first. Reapplies at: W104 segment
      tombstone compaction, W113 hot-path memory budget.

  - **When `p99_drops_15pct_vs_vecdeque_baseline` shows only 3% improvement:**
    - Symptom: ring is 3% faster; expected ≥ 15%.
    - Why: `match_and_execute` hot loop still calls `BTreeMap::get_mut` (per-level lookup) which is
      the dominant cost; the inner ring traversal was already < 10% of total.
    - Fix (defer to Wed): the BTreeMap traversal is the next layer. The ring redesign is a
      prerequisite to the lock-free top-of-book that bypasses BTreeMap entirely. Document this in
      the design doc; don't claim more improvement than measured.
    - Muscle: Amdahl's law — optimizing a 10% slice gives 10% max improvement; measure WHAT to
      optimize, don't assume. Reapplies at: W111 Wed top-of-book, W120 perf reviews.

    the hot path. Migration trigger: spill rate > 10% sustained. Name the redesign (2-tier ring:

**Wednesday — Lock-free price level**

- [ ] **Build**: `crates/matching-engine/src/top_of_book.rs` — lock-free seqlock-backed `TopOfBook` for single-writer,
  multi-reader access to top bid/ask. (~total 60 min across 3 phases)
  - 🔧 **Why this matters**: top-of-book is hit by *every* market-data tick and by *every* incoming
    aggressive order — at 1 M orders/sec even a 100 ns spinlock acquire dominates. If readers (quote
    dissemination, risk checks, internal subscribers) and writers (matching engine) contend on a
    `Mutex`, you see P99.9 spikes when the writer holds the lock through a full level traversal. A
    lock-free seqlock lets readers complete in ~10 ns and writers in ~30 ns — and exposes a
    correctness property (readers may see torn reads and must retry, detected by the seqlock counter).
    Downstream consumers: dissemination + risk-check fast-paths consume `load()`; the seqlock pattern
    is re-used in ledger-deterministic's read-only-snapshot reads; W120 PR-review documents the
    pattern as the matching-engine post.

  #### Phase 1 — Problem, requirements, design (~20 min, no code yet)

  - **The problem this primitive solves**: a `Mutex` over top-of-book serializes ALL readers behind the
    writer; under 1 M ops/sec with 8 readers (disseminator, 4 risk-checks, 2 internal subscribers, 1
    audit), Mutex acquire alone consumes ~800 ns/op of P99.9. Worse: when the writer holds the lock
    through a full level update, readers stall for the writer's entire critical section. Seqlock
    converts the contention pattern: writers are wait-free (no read-side spin), readers retry if they
    catch a write-in-flight. Single-writer multi-reader maps EXACTLY to matching-engine's per-shard
    threading model.

  - **Requirements** — write in `crates/matching-engine/notes/111_top_of_book_design.md`:
    - R1. Struct is `#[repr(align(64))]` + size exactly 64 B (`const_assert!`); no false sharing with
      adjacent symbols.
    - R2. Single writer per `TopOfBook` — enforced by debug-only `OnceCell<ThreadId>` panicking on
      second writer. Multi-writer requires CAS-based redesign and is OUT of scope.
    - R3. `seq` even = stable, odd = writer in flight. Reader retries if it saw odd OR if `seq` changed
      across the read.
    - R4. Memory ordering: writer uses `Release` on the closing `seq` store; reader uses `Acquire`
      on both `seq` loads. Fields between can be `Relaxed`.
    - R5. Reader retry is bounded — > 16 spins triggers `spin_loop` hint + exponential backoff. > 1024
      total retries triggers a slow-path `Mutex` fallback with metric `top_of_book_slow_path_total`.
    - R6. Read-side P99 ≤ 50 ns single-thread; ≤ 100 ns under 8-reader load. Writer-side P99 ≤ 100 ns.
    - R7. Loom test (single-writer N-reader) verifies no reader returns inconsistent snap across
      all interleavings.
    - R8. 1 B-iteration stress run shows zero torn reads.

  - **Design walk-through** — answer each in your design doc; no peeking at Linux
    `include/linux/seqlock.h` until Phase 3:
    - D1. Why even/odd seq? Walk through the 4-step write sequence (fetch_add → store fields →
      store back to even). Why fetch_add not store at the start?
    - D2. Why Release on closing seq and Acquire on reads? Walk through the bad reordering you'd
      see with Relaxed.
    - D3. Field layout: 4 atomic fields (bid_price, bid_qty, ask_price, ask_qty). How do they pack
      into 64 B with the 8-byte seq + padding? Draw the byte layout.
    - D4. Reader algorithm: write it out in pseudocode. Where's the retry loop? What's the bounded-
      spin policy?
    - D5. Why single-writer? List 3 reasons multi-writer requires a different design (not just bigger
      CAS); compute its cost.
    - D6. Slow-path fallback: when readers retry forever (writer SIGSTOP'd), what's the escape valve?
      Mutex fallback? Drop the read? Argue.
    - D7. **Pre-mortem (the load-bearing question)**: write the 8-step interleaving where (a) writer
      starts store (seq=1, odd), (b) writer stores bid_price, (c) reader observes seq=1, returns
      None (writer in flight), (d) writer SIGSTOP'd before completing, (e) seq stays at 1 forever,
      (f) all readers livelock. Convince yourself R5's bounded retry + slow-path saves you.
  - **Output**: `notes/111_top_of_book_design.md` with R1–R8, answers to D1–D7, byte-layout
    diagram, the writer-reader sequence chart, the pre-mortem trace.

  #### Phase 3 — Make the tests pass, one failure at a time (~25 min)

  - **When `loom_no_torn_read_single_writer_2_readers` reports a 5-step interleaving with inconsistent snap:**
    - Symptom: loom prints `[W: seq=1] [W: bid_price=100] [R1: seq=1 odd, retry] [R1: seq=2 even,

    - Why: writer used `Relaxed` ordering on field stores; reader's `Acquire` on the closing `seq`

    - Fix: writer's closing `seq.store(s+2, Release)`. Reader's `s2 = seq.load(Acquire)` then field
      reads. The Release/Acquire pair establishes happens-before from writer's field stores to
      reader's field reads — provided the seq check passes.
    - Muscle: seqlock correctness is the Release-on-close-seq paired with Acquire-on-load-seq;
      field ordering can be Relaxed because the seq check is the sync point. Reapplies at:
      W113 lock-free queue, W120 atomics audit.

  - **When `single_writer_enforced` doesn't panic on second writer:**
    - Symptom: two threads call `store()` simultaneously; readers intermittently see corrupted
      values; no panic.

    - Fix: add `#[cfg(debug_assertions)] writer_thread: OnceCell<ThreadId>`. First `store()` sets
      it; subsequent `store()` calls assert `*writer_thread.get().unwrap() == thread::current().id()`,
      panic otherwise. Production builds compile out the check.
    - Muscle: single-writer invariants need debug-time enforcement; production trusts the channel
      discipline. Reapplies at: W113 shard-thread invariants, W120 concurrency audit.

  - **When `slow_path_fallback_on_writer_preempt` livelocks the readers:**
    - Symptom: writer SIGSTOP'd; readers spin forever consuming 100% CPU.
    - Why: retry loop had no bound; spun on `seq odd` indefinitely.
    - Fix: counter inside the retry loop; after 16 spins, call `core::hint::spin_loop`. After 1024
      total retries, increment `top_of_book_slow_path_total` and acquire a backing `Mutex<Snap>` for
      this read. Writer's `store()` also writes to the backing Mutex AFTER the fast path (so the
      Mutex is the durable copy when fast path is jammed).
    - Muscle: every spin loop needs a bound + a fallback; unbounded spin is a livelock waiting.
      Reapplies at: W004 parker design, W113 lock-free queue retry.

  - **When `reader_p99_under_50ns_single_thread` shows 200 ns p99:**
    - Symptom: P99 is 4× target; profile shows the read of `bid_price` causes a cache miss.
    - Why: `TopOfBook` lives in a `Vec<TopOfBook>` whose allocator returned an unaligned address;
      `#[repr(align(64))]` was honored for stack but not for Vec slots because Vec doesn't honor
      `align_of::<T>()` past 8 bytes on some allocators.
    - Fix: store `TopOfBook` instances individually in `Box<TopOfBook>` OR use a custom `align_alloc`
      strategy. Verify with `assert!((self as *const _ as usize) % 64 == 0)` at construction.
    - Muscle: align-to-64 needs allocation-time verification; the type annotation alone is not
      enough on heap. Reapplies at: W111 Tue PriceLevel allocation, W113 cache-line-aware structs.

  - **When `one_billion_iter_stress_no_torn_reads` reports 47 torn reads:**
    - Symptom: 1 B iterations, 47 reads returned (bid_price, bid_qty) from different generations.
    - Why: writer's fetch_add + 4 stores + store cycle has a window where reader can see seq=odd,
      retry, see new seq=even on first load, then read stale bid_qty (writer's qty store hadn't
      committed to memory yet on weakly-ordered ARM).
    - Fix: writer's closing `seq.store(s+2, Release)` is sufficient — the Release ensures all prior
      Relaxed stores are ordered-before. Verify the 47 torn reads were actually pre-fix; if post-fix,
      look for a missing Release (e.g. on `total_qty` if added later).
    - Muscle: stress tests reveal weak-memory bugs invisible on TSO x86; always run on ARM as well.
      Reapplies at: W113 ARM CI gate, W120 cross-arch test matrix.

  - **5-year failure mode** (write in `notes/111_top_of_book_followup.md` after green): when symbols
    grow > 100k and per-symbol TopOfBook arrays exhaust L1 cache footprint, even cache-aligned reads
    miss. Migration trigger: working-set > 32 KB / core. Name the redesign (per-shard symbol
    partitioning so each shard's hot symbols fit in L1).

  #### Phase 1 — Problem, requirements, design (~15 min, no code yet)

  - **The problem this primitive solves**: latency benches lie in three classic ways. (1) Coordinated
    omission: you time only `process(msg)`, miss the queue wait; reported P99 is rosy, production P99
    is 50× worse. (2) Insufficient warmup: P99 captures first-touch page faults and L1-i misses, not
    steady-state. (3) Feed-rate mismatch: `iter_custom` runs as fast as possible, so you measured a
    fantasy "as fast as possible" mode, not 500k/sec sustained. Each lie produces a number you'll
    quote in interviews until you trace a production outage to it.

  - **Requirements** — write in `crates/matching-engine/notes/111_p99_bench_design.md`:
    - R1. Bench process is pinned to an isolated core (`isolcpus`); feed-gen on a different core,
      ideally a different NUMA node.
    - R2. Bench reports P50, P99, P999 from a SINGLE HdrHistogram aggregating all samples —
      never average per-iter P99s.
    - R3. Coordinated omission correction: HdrHistogram-rs `record_corrected_with_max_interval(expected
      = 2us)` so a queue stall inflates correctly.
    - R4. Warmup ≥ 50k iterations before histogram recording starts; warmup adequacy verified by
      P50 stability < 5% variance across 2 consecutive runs.
    - R5. Feed paced to 500k/sec exactly via `spin_sleep`; actual achieved rate within ±5% of target,
      recorded alongside P99.
    - R6. Bench compiled with `tracing` at `LevelFilter::OFF`; spans feature-flagged out via
      `--no-default-features --features=bench`.
    - R7. Bench seed is fixed and recorded in result JSON so historical comparison is apples-to-apples.
    - R8. CI nightly with 10% regression budget; baseline `bench/baseline.json` committed; failure
      blocks merge.
    - R9. Acceptance: P99 < 2 µs; P999 < 10 µs; achieved rate within 5% of target; 7 consecutive
      nightly greens before tagging v1.1.

  - **Design walk-through** — answer each in your design doc; no peeking at LMAX Disruptor latency
    methodology doc until Phase 3:

  #### Phase 3 — Make the tests pass, one failure at a time (~25 min)

  - **When `bench_uses_corrected_recording` shows `record` was called (not corrected):**
    - Symptom: bench code does `hist.record(dt)`; reported P99 is 1 µs; real-world P99 is 50 ms.
    - Why: coordinated omission — when the feed queues 100 messages in a 5 ms burst, the bench
      records each `process(msg)` at ~1 µs but never accounts for the queue wait of the LAST message
      (which sat 5 ms before being processed).
    - Fix: `hist.record_corrected_with_max_interval(dt, expected_interval_ns)` where
      `expected_interval_ns = 1_000_000_000 / 500_000 = 2_000`. HdrHistogram inflates samples whose
      gap exceeds expected by synthesizing the missing samples.
    - Muscle: latency benches under load REQUIRE coordinated-omission correction; uncorrected P99
      is fantasy. Reapplies at: W113 PR-review benches, W120 production SLO measurement.

  - **When `bench_achieved_rate_within_5pct` shows actual rate = 1.2 M/sec:**
    - Symptom: target was 500k; bench ran as fast as possible; HdrHistogram recorded 2 M samples
      in 10 s.
    - Why: bench used `b.iter(|| me.process(msg))` which runs as fast as possible.
    - Fix: bench uses `b.iter_custom(|iters| { for _ in 0..iters { spin_sleep::sleep(target_gap);
      ... } })`. Target gap is `Duration::from_nanos(1_000_000_000 / 500_000)` = 2 µs.
    - Cost: bench runtime is now bound by target rate, not CPU speed.
    - Muscle: rate-shaped benches are the only benches that match production conditions; "max
      throughput" benches measure a different quantity. Reapplies at: W106 synthetic feed pacing,
      W113 production-like bench design.

  - **When `bench_p50_stable_across_runs` shows variance = 18%:**
    - Symptom: P50 = 250 ns on run 1, 295 ns on run 2.
    - Why: warmup was 5k iters; first-touch page faults still happening into the histogram.
    - Fix: warmup ≥ 50k iters. Verify stability: run bench 3× and assert ≥ 2 of 3 are within 5%.
    - Muscle: warmup adequacy = stability across repeated runs; pick the warmup that stabilizes.
      Reapplies at: W111 Mon perf rig, W113 PR-review bench protocol.

  - **When `bench_compiled_without_tracing` finds `tracing` in cargo tree:**
    - Symptom: `cargo tree --bench single_symbol_p99` shows `tracing` as a dep; bench's hot path
      pays 200 ns/op for `info_span!()` macros.
    - Why: matching-engine's main code uses tracing; bench inherited that dep tree.
    - Fix: feature-flag tracing emission in the hot path: `#[cfg(feature = "trace")] info_span!(...);`.
      Bench profile uses `--no-default-features --features=bench` which excludes "trace".
    - Muscle: hot-path instrumentation is feature-gated; benches measure the production hot path,
      not the dev hot path. Reapplies at: W105 metric emit feature flags, W113 hot-path discipline.

  - **When `bench_regression_10pct_fails_ci` doesn't fail at 12% regression:**
    - Symptom: bench reports 12% P99 regression; CI marks green.
    - Why: comparison logic checked only `current_p99 > baseline_p99 * 1.1` but with floating-point
      it compared 2_250 ns > 2_200 ns and rounded.

      return Err(...) }`. Print both numbers + delta.
    - Muscle: regression gates need explicit thresholds with audit trail; never trust floating point
      comparison for budget enforcement. Reapplies at: W113 PR-review gates, W120 SLO regression.
