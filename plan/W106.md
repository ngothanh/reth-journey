  - *Mental model*: a `SyntheticPerpFeed` is a deterministic state machine — one seed in, byte-identical message stream out — that maintains a *shadow* of every open order **per instrument** so it can only emit referentially-valid Cancels/Executes, that interleaves **mark ticks** for BTC-PERP and ETH-PERP on a scheduled cadence (so the venue's per-mark-tick `risk-engine` recompute and the `liquidation-engine` trigger path are exercised), and that paces itself off a *synthetic clock* (not the wall clock) so timestamps are monotonic and reproducible. It exists because the §4A capacity + cross-margin-netting claims are only credible if the workload is realistic, multi-instrument, mark-tick-bearing, AND replayable.

  - *Contract* (signature-level only — NEVER the solution body):
    ```rust
    pub struct SyntheticClock(AtomicU64); // ts_ns, advance-only
    impl SyntheticClock {
        pub fn now(&self) -> u64;
        pub fn advance(&self, delta_ns: u64) -> u64; // returns new ts; never moves backward
    }
    pub struct OrderBookShadow { /* per-(instrument, account) open oids */ }
    impl OrderBookShadow {
        pub fn add(&mut self, inst: InstId, acct: AcctId, oid: u64);
        pub fn remove(&mut self, inst: InstId, oid: u64) -> bool;            // false = orphan
        pub fn pick_open(&self, inst: InstId, rng: &mut impl RngCore) -> Option<u64>;
    }
    pub struct MarkTickSched { /* next_tick_at per InstId, derived from SyntheticClock */ }
    pub struct SyntheticPerpFeed { /* clock, shadow, mark sched, sub-stream RNGs, config */ }
    impl SyntheticPerpFeed {
        pub fn new(seed: u64, cfg: &PerpFeedConfig) -> Self;  // cfg: 2 instruments, n_accounts, rate, mark_hz
        /// Fill `out` in place; returns bytes written. ZERO heap alloc per call.
        /// May emit an order message OR a scheduled MarkTick for an instrument.
        pub fn next_into(&mut self, out: &mut [u8]) -> usize;
    }
    ```
  - *Back-of-envelope* (bar (c) — Jeff-Dean numbers): target ~1M orders/s = **1 message every 1 µs = 1000 ns budget**. An ITCH-style AddOrder is ~36 bytes — encoding it into a caller buffer is a handful of `copy_nonoverlapping`s + a `to_be_bytes`, ~10–20 ns. That leaves headroom *only if the hot path allocates nothing*: one `malloc` ≈ 50 ns (5% of budget) and `format!("{inst}")` is a malloc + memcpy + UTF-8 work ≈ 80–120 ns (8–12% of budget) — at 1M/s that's **50–120M allocs/s**, thrashing the allocator and the L2 (~7 ns per cache-line eviction). The Cancel path must pick an open oid in O(1) amortized; `Vec::remove(idx)` shifts the tail (O(n)) — at 1M/s with a 10k-deep book that's a 10k-element memmove (~10 µs) **per Cancel**, 10× over budget. **Mark-tick consequence (the §4A convergence cell):** 100k accounts × 10 mark ticks/s = **1M margin recomputes/s** *if* the venue does naïve full recompute — ~1 CPU-second/second, which is exactly why W99's **incremental margin** is the hot path and full recompute is reserved for circuit-breaker/param-change. The feed must therefore drive mark ticks at the cfg cadence so this path is *measured* live, not assumed. Pacing cliff: `tokio::time::sleep` rounds up to the ~1 ms timer-wheel slot, so a requested 1 µs sleep actually sleeps ~1 ms = **1000× the intended pause**, capping throughput at ≈1000 msg/s.

  - **Requirements** R1..R11 — write in `crates/marketdata-kernelbypass/notes/106_perp_feed_design.md`:
    - R1. Deterministic for a fixed `seed: u64` — two runs produce byte-identical streams (verified by SHA-256 of the first 10M messages, mark ticks included).
    - R2. Timestamps `ts_ns` are monotonic-non-decreasing across the entire run, sourced from `SyntheticClock` (never the wall clock).
    - R3. `oid` is globally unique within a run (per-instrument counter + instrument prefix); `acct_id` ∈ `[0, n_accounts)`.
    - R4. Referential closed-world: every Cancel/Execute/Delete/Replace references an `oid` previously Added (for that instrument) and not yet Deleted; an end-of-run smoke check asserts zero orphan references — **including across the storm path**.
    - R5. Two instruments live (BTC-PERP, ETH-PERP); order volume split per config (default 60/40); account activity is Zipf(α=1.1) so a small set of accounts hold most open interest (the cross-margin netting stress).
    - R6. Message mix matches NASDAQ published ratios — 60% AddOrder, 15% Cancel, 15% Execute, 5% Replace, 5% Delete (tunable); **mark ticks are scheduled out-of-band** at `mark_hz` per instrument (default 10/s each), NOT counted in the order mix.
    - R7. Rate shaping: sustains `rate_target` orders/s to within ±2% over 10 s windows; busy-wait/`spin_sleep` below 1 ms (NEVER `tokio::time::sleep` on the hot path).
    - R8. **Mark-tick schedule**: each instrument emits a `MarkTick` every `1/mark_hz` of synthetic time; mark price is a deterministic correlated random walk (BTC/ETH ≈ 0.7 correlated, matching the §4A const-30%-haircut design assumption) so the venue's cross-margin netting actually has correlated positions to net.
    - R9. Storm injection: every ~60 s emit a 100k-order burst over 100 ms across both instruments; `storm_count_total` metric tracks them; storms go *through* the shadow (R4 holds under storm).
    - R10. Backpressure: when the venue (the consumer) stalls — e.g. a leader-shard margin recompute or a partial-liquidation cascade — the feed slows (bounded queue blocks/sheds); it never buffer-bloats unbounded.
    - R11. Sustains ~1M orders/s + 10 mark ticks/s/instrument for ≥60 min with all invariants holding, **zero heap allocation per message on the hot path** (verified by an allocation-counting test).

    fn closed_world_referential_check_under_storm_and_marks() {

            &PerpFeedConfig { storms: true, mark_hz: 10, ..Default::default() });

                }
            }
        }
