**Tuesday — consensus-bft v0.5 ship + Blog if ready**

- [ ] **Build**: `crates/consensus-bft/src/lock.rs` — locking on prevoted value across rounds (Tendermint locking). (~150 min)
  - **Why**: Tendermint's *locking* is the single mechanism that prevents a Byzantine adversary from forcing two correct validators to commit different blocks in the same height under partial synchrony. Without locking, a 1/3+ adversary can split votes and produce a fork. Bar (c) substrate for downstream BFT validator quorum.
  - *Back-of-envelope* (bar c): lock state is a small fixed struct (~64 B) checked on EVERY prevote / precommit handler — call rate scales with vote rate (W65 perf), ~63 calls/sec steady, ~500/sec burst. Per-check ≈ ~5 ns (one struct field compare + one optional unwrap). The **POL detection** (`has_pol_for(hash, lock_round)`) is the cost driver — naively it scans the VoteSet looking for `>2/3 prevotes` at any round `r > lock_round` for the target hash. Naive scan = O(rounds × n) = ~1k ops at typical burst; expected target ≤100 ns. **Lock-state transition fsync is one-shot** (lock change is rare — ~1/round at most), so fsync cost is absorbed by precommit group-commit (W65 precommit perf #1). **Zero allocations on the check path** — lock state lives on the replica stack/struct.
  - **Read first**: Tendermint Core `consensus/state.go::enterPrevote`/`enterPrecommit`/`tryFinalize` (≈L1500-L1800). Buchman-Kwon-Milosevic 2018 "Latest Gossip on BFT Consensus" §3 (locking rule + unlock rule). Cosmos SDK `tendermint/spec/consensus/consensus.md` (LOCK_STATE diagram).
  - **Design**:
    ```rust
    pub struct LockState {
        pub locked_round: Option<Round>,
        pub locked_block: Option<BlockHash>,
        pub valid_round: Option<Round>,
        pub valid_block: Option<BlockHash>,
    }
    pub enum Step { Propose, Prevote, Precommit, Commit }
    pub struct RoundState {
        pub height: u64,
        pub round: Round,
        pub step: Step,
        pub lock: LockState,
        pub prevotes: VoteSet,    // round -> hash -> Vec<Vote>
        pub precommits: VoteSet,
    }
    // Core rule
    fn try_prevote(&mut self, proposal: &Block) -> Vote {
        if let Some(lr) = self.lock.locked_round {
            // Only prevote for locked_block UNLESS there's POL (proof of lock change) at round > lr
            if proposal.hash != self.lock.locked_block.unwrap() && !self.has_pol_for(proposal.hash, lr) {
                return Vote::nil();  // prevote nil
            }
        }
        Vote::for_block(proposal.hash)
    }
    ```
    **Invariants**: (i) Once `locked_block = B at round r`, a correct validator NEVER prevotes for `B' != B` in round `r' > r` unless it sees `>2/3 prevotes` for `B'` in some round `r'' >= r` (the POL — Proof of Lock-change). (ii) `valid_block` is the most recent block with `>2/3 prevotes` (gets included in next round's proposal). (iii) A precommit at round `r` for block `B` locks the validator on `(r, B)`. (iv) A *nil* precommit unlocks (sets `locked_round = None`) — but the trickier rule: re-locking requires fresh POL.
  - **Build steps**: 1. (~20 min) `LockState` + `VoteSet { round -> hash -> BTreeMap<ValidatorId, Vote> }`. 2. (~30 min) `enter_prevote` — implement the rule above. 3. (~25 min) `enter_precommit` — only precommit if we see `>2/3` prevotes for the proposal in this round; if yes, set lock. 4. (~25 min) POL detection: `has_pol_for(hash, lock_round) = exists r' > lock_round s.t. prevotes[r'][hash].count > 2/3 * n`. 5. (~25 min) Unlock-on-nil-precommit. 6. (~25 min) Property tests below.
  - **Pitfalls** (named, 4):
    - *Lock without POL*: **Symptom**: validator unlocks too eagerly, signs conflicting precommits → slashable double-sign. **Fix**: only call `lock = None` on explicit nil-precommit gathering `>2/3`, never on local timeout alone. Audit every `lock = None` write site.
    - *Stale POL*: **Symptom**: validator uses stale prevote set from an old height (after height bump) to justify unlock. **Fix**: VoteSet keyed by `(height, round)`; clear on `enter_new_height`. Add a debug assert `vote.height == self.height` on every insert.
    - *Equivocation under nil*: **Symptom**: prevote-nil at round r, then prevote-block at round r (same round, contradictory) when proposal arrives late. **Fix**: gate `enter_prevote` with `self.step >= Step::Prevote` check — once you've prevoted for this round, never prevote again. Idempotency table keyed `(height, round)`.
    - *Lock-on-future-round*: **Symptom**: receive a precommit message for round r+5 while in round r, optimistically lock — but the round r+5 may never form. **Fix**: only set lock from *our own* precommit decision, never from observed remote votes. Remote votes update VoteSet only.
  - **Test scenarios**: (a) Adversarial proposer at round 0 sends block A to half, B to other half; verify no correct validator commits both. (b) Network partition for 2 rounds, heal — locked validators must converge on the locked block. (c) 4-node {1 Byzantine, 3 honest} — Byzantine double-signs prevote A and B → honest validators should detect via evidence module (W73). (d) Random fuzz: 100 scenarios with reordered/dropped/duplicated votes — no double-commit, ever.
  - **Acceptance**: property test `no_double_commit` passes 10k random schedules. `lock_consistency` invariant — at any time, if any honest validator has `locked_block = B at round r`, no other honest validator has `locked_block = B' != B at round r`. Bench: 1000 rounds at 4-node cluster in <2s.
  - **Downstream**: W73 fork-choice rule uses locked-block info to break ties (lock takes priority over freshness). W73 evidence.rs detects locking-rule violations as slashable. consensus-vsr v0.5 (W76) shares the *concept* but VSR has a different mechanism (view-numbers) — comparing the two is the M21 retrospective.
  - **Expect to hit (perf) #1 — O(rounds × n) POL scan on every prevote handler (bar (c) violation)**: naive `has_pol_for(hash, lock_round) = self.prevotes.iter().filter(|(r, _)| r > lock_round).any(|(_, votes)| votes_for(hash) > 2*n/3)` walks the entire VoteSet for every prevote. At burst (Byzantine spam, partition heal), with `max_rounds_in_flight = 16` and `n = 21` validators, that's ~336 ops per prevote × ~500 prevotes/sec = 168k ops/sec — visible at P99 even under burst. Symptom: `perf top` shows `has_pol_for` at 20% CPU during view-change churn; commit latency spikes from 1 ms to 50 ms.
    - Fix: maintain a **running `pol_index: AHashMap<Hash, Round>`** updated incrementally on each VoteSet insert — `pol_index[hash] = max(pol_index[hash], round)` whenever the running tally first crosses 2/3+1 (inherits the running-tally pattern from W65 precommit perf #2). POL check becomes O(1): `pol_index.get(hash).map_or(false, |&r| r > lock_round)`.
    - Cost avoided: O(rounds × n) → O(1) per check; saves ~336 ops × 5 ns = ~1.7 µs per prevote × 500/sec = ~850 µs/sec of CPU; eliminates the burst-time P99 spike entirely.
    - Muscle: cross-cutting "any past message satisfying X" queries should be maintained as a derived index updated on insert, not re-scanned on query. Reapplies at: W65 precommit threshold tally (already noted), W67 raft match-index aggregation, W73 fork_choice "highest-QC descendant of locked" query, W74 VSR PrepareOk quorum (BitSet `count_ones`).

- [ ] [NEW v2] **Build**: `crates/consensus-vsr/src/view.rs` — `View { view_num: u64, leader_id: ReplicaId, members: Vec<ReplicaId> }`. (~75 min)
  - **Why**: View is VSR's atomic unit of leadership. Every operation, every log entry, every message is stamped with a `view_num`. The leader-of-view-V is deterministic: `members[V % n]`. This eliminates Raft's randomized-timeout election liveness gap — view changes are deterministic round trips. This struct will be referenced from every other module; getting its identity semantics right is foundational.
  - *Back-of-envelope* (bar c): View is touched on EVERY message handler (Prepare, PrepareOk, Commit, StartViewChange, DoViewChange, Recovery) — typical hot-path rate ~30k op/s/replica (W74 target). Per-touch cost: ~3 ns (compare `view_num`, lookup leader via `members[view_num % n]`). View struct must be **≤ 1 cache line (64 B)** so the touch is one L1 fetch; with `MAX_REPLICAS = 7` and `ReplicaId = u8`, fixed-array layout fits in 8 (members) + 1 (count) + 8 (view_num) = 17 B — well under one line. **Fixed-array `[ReplicaId; MAX_REPLICAS]` not `Vec<ReplicaId>`** (Vec adds a pointer-chase to heap → ~10 ns L2 miss on first touch per call, scales linearly with cluster size; pointer-chase also blocks the prefetcher). **`Copy + Clone` cheap** — View is passed by value, never `Arc<View>` on the hot path.
  - **Read first**: Liskov-Cowling 2012 §3 (View definition) + Figure 2 (view-num ↔ leader rotation). TigerBeetle `vsr/replica.zig::view_for_op` (≈L500 — shows how view-num is recovered from log entry).
  - **Design**:
    ```rust
    pub type ViewNum = u64;
    pub type ReplicaId = u8;            // 1-byte: VSR clusters are small (3-5 replicas)
    pub const QUORUM_MIN: u8 = 1;        // f+1 where f = (n-1)/2

    #[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
    pub struct View {
        pub view_num: ViewNum,
        pub members: [ReplicaId; MAX_REPLICAS],   // sorted, deduplicated, length-prefixed elsewhere
        pub member_count: u8,
    }

    impl View {
        pub fn leader(&self) -> ReplicaId {
            self.members[(self.view_num as usize) % (self.member_count as usize)]
        }
        pub fn is_leader(&self, who: ReplicaId) -> bool {
            self.leader() == who
        }
        pub fn quorum(&self) -> u8 {
            (self.member_count / 2) + 1   // f+1 of n=2f+1
        }
        pub fn next_view(&self) -> View {
            View { view_num: self.view_num + 1, ..*self }
        }
    }
    ```
    **Invariants**: (i) `view_num` is monotonically non-decreasing per replica — `accept_view_bump(v)` requires `v >= self.current_view.view_num`. (ii) `members` is fixed for the cluster lifetime in v0.1 (reconfig comes in v1.0). (iii) `leader()` is a pure function — same view ⇒ same leader on every replica (deterministic). (iv) `quorum() == f+1` where `n == 2f+1`.
  - **Build steps**: 1. (~10 min) Type defs above + serde derives. 2. (~15 min) `View::leader`, `is_leader`, `quorum`, `next_view`. 3. (~15 min) `ViewNum` arithmetic helpers — wrap-on-overflow is unacceptable; use `checked_add` everywhere. 4. (~20 min) Unit tests: (a) leader rotates round-robin across n=3, n=5; (b) `quorum(3) == 2`, `quorum(5) == 3`; (c) overflow on `next_view` returns `Result`. 5. (~15 min) Property test: `forall v: View, View::from(v.to_bytes()).leader() == v.leader()` (round-trip).
  - **Pitfalls** (named, 3):
    - *View-num skip*: **Symptom**: replica observes `view_num = current + 5` from a malicious message, jumps directly — now the (current+1..current+5) view-leader replicas never get a chance to lead. **Fix**: accept the bump (VSR allows skipping forward, this is by design), but log a warning if skip > 1 in tests; in production, that's normal during partition heal.
    - *Off-by-one members*: **Symptom**: `members.len() = 4` (even) — VSR requires `n = 2f+1` (odd). Quorum math goes wrong. **Fix**: assertion at View construction: `member_count % 2 == 1`. Compile-time const `MAX_REPLICAS = 7` (TigerBeetle's actual max).
    - *Leader mismatch under reconfig*: **Symptom**: v0.1 ignores reconfig but later versions add it; if not careful, `leader()` depends on stale `members`. **Fix**: explicitly version-pin `View` — reconfig in v1.0 will introduce a new `View` major version + migration.
  - **Test scenarios**: (a) n=3 cluster: views 0,1,2,3,4,5 → leaders 0,1,2,0,1,2 (round-robin). (b) `view.quorum()` returns 2 for n=3, 3 for n=5. (c) Property: any two replicas with same `view_num` and same `members` compute the same `leader()`.
  - **Acceptance**: 100% line coverage on view.rs (it's small, ~80 LOC + tests). Property test 10k iterations. Zero `unwrap()` in production code paths.
  - **Downstream**: `normal.rs` (W74) reads `view.leader()` to decide proposer role. `view_change.rs` (W75) calls `next_view()` and threads view-num into every DoViewChange message. `replica.rs` owns `current_view: View` field.
  - **Expect to hit (perf) #1 — `members: Vec<ReplicaId>` heap-allocated on the hot path (bar (c) violation)**: the convenient signature `pub members: Vec<ReplicaId>` heap-allocates the member list (16 B for the Vec header + 8 B per-replica payload), forcing every `View` access into two cache fetches (the View struct + the heap allocation). At 30k op/s every handler reads `view.leader()` once → 60k cache fetches/sec instead of 30k; under contention with cross-shard `Vec` clones, this becomes the bottleneck before the protocol logic does. Symptom: `perf c2c` shows `View::leader` causing L2 misses; benchmarks show `view.leader()` slower than expected (~15 ns instead of ~3 ns).
    - Fix: **inline fixed-cap array**: `pub members: [ReplicaId; MAX_REPLICAS]` + `pub member_count: u8`. `MAX_REPLICAS = 7` (TigerBeetle's cap) so the array fits in 7 B. Whole `View` struct = `view_num: u64 (8) + members: [u8;7] + member_count: u8 = 17 B` — fits one cache line, `Copy`-able, no allocation. `View::leader()` becomes one register load + one mod = ~3 ns.
    - Cost avoided: ~10 ns L2 miss per `view.leader()` call eliminated; at 30k op/s/replica saves ~300 µs/sec of L2-fetch latency; eliminates allocator pressure (zero Vec allocs per View clone — and `View` is cloned per-message in some code paths).
    - Muscle: small-cap fixed-size collections on the hot path must be inline arrays, not `Vec`; the cap is design discipline (`MAX_REPLICAS = 7` is the TigerBeetle ceiling). Reapplies at: W66 margin Position array (already noted W66 perf #1), W74 VSR Log's per-op metadata, W74 raft prepare_ok BitSet (fixed-cap by validator count), W76 messaging-aeron subscriber list per term, W83+ ledger-deterministic per-shard transfer pool.
  - **Expect to hit (perf) #2 — `BTreeMap`/`HashMap` for `members → ReplicaId` lookup (bar (c) violation, scale-trap)**: a developer "improvement" — replacing the array indexing with `members.get(replica_id)` via a `HashMap<ReplicaId, ReplicaInfo>` — turns a O(1)/3-ns lookup into a hash + probe (~20-50 ns warm, ~200 ns cold). At cluster size n ≤ 7, the hash setup cost exceeds the savings from "more flexibility." Symptom: someone adds metadata-per-replica via a HashMap and the View hot path slows 5-10×; flame graph shows `ahash::AHasher::write` in `View::leader`.
    - Fix: at n ≤ 7, **linear scan an array beats every hash table** by 2-10×. If per-replica metadata is needed, attach it via a sibling fixed-cap array indexed by `ReplicaId as usize` — direct indexing, zero hash, zero probe. Don't reach for `HashMap` until n > 64; consensus clusters never hit that.
    - Cost avoided: ~17-47 ns per lookup (warm); at 30k op/s/replica saves ~500 µs - 1.4 ms/sec; eliminates hash collisions as a non-determinism vector for replay (different `RandomState` seeds across replicas give different iteration order → divergence; this is the same trap as W74 matching-engine perf-correctness pitfall #2).
    - Muscle: small-cap collections (n ≤ 64) on a hot path use direct-indexed arrays, never `HashMap`. The crossover point in the literature is around n=32-64 where linear scan + cache-friendliness wins over hashing. Reapplies at: W74 matching-engine determinism gate (BTreeMap over HashMap for ordered iteration), W76 messaging-aeron per-subscriber state (small, fixed cap), W83+ ledger per-shard account index (TigerBeetle uses fixed-cap arrays here too).
