**Tuesday — consensus-bft v0.5 ship (Build: Tendermint locking, bar c) + Tempo metrics**

- [ ] **Build**: `crates/consensus-bft/src/lock.rs` — Tendermint locking on prevoted value across rounds. (~total 165 min across 3 phases)
  - 🔧 **Why this matters**: locking is the single mechanism that stops a 1/3+ Byzantine adversary from forcing two correct validators to commit different blocks at the same height under partial synchrony — i.e. it is what makes the protocol *safe*. Mirror: Tendermint Core `consensus/state.go` enterPrevote/enterPrecommit/tryFinalize + BKM-2018 §3. The 4 traps: (1) a naive POL scan is O(rounds×n) on the per-prevote hot path (bar (c) violation); (2) unlocking on a local timeout instead of on a `>2/3` nil-precommit produces a slashable double-sign; (3) VoteSet not keyed by `(height, round)` lets stale prevotes justify a bad unlock; (4) locking from an *observed remote* precommit instead of your own decision lets a future-round that never forms pin your lock. **First-attempt impls fail ≥1 Phase-2 test below — the debug session is the lesson.** Downstream: W73 fork-choice tie-break reads `LockState` (lock beats freshness); W73 evidence.rs detects locking-rule violations as slashable; W76 consensus-vsr shares the *concept* (view-number) but a different mechanism — the M21 retro compares them.

  #### Phase 1 — Problem, prediction, design (~40 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `notes/68_lock_prediction.md`:

    - P5. List every Phase-2 test you predict your first attempt will fail. (Compared to reality after tests run.)
  - *Mental model*: `LockState` is a ~64-byte fixed struct checked on every prevote/precommit handler. A correct validator that locked `B` at round `r` never prevotes for `B'≠B` at round `r'>r` *unless* it sees a Proof-of-Lock-change (POL): `>2/3` prevotes for `B'` at some round. Locking turns "I might change my mind" into "I will only change my mind with a quorum's permission."
  - *Contract* (signature-level — never the body):
    ```rust
    pub struct LockState {
        pub locked_round: Option<Round>,
        pub locked_block: Option<BlockHash>,
        pub valid_round:  Option<Round>,
        pub valid_block:  Option<BlockHash>,
    }
    pub enum Step { Propose, Prevote, Precommit, Commit }
    pub struct RoundState {
        pub height: u64,
        pub round:  Round,
        pub step:   Step,
        pub lock:   LockState,
        pub prevotes:   VoteSet,   // keyed (height, round) -> hash -> BTreeMap<ValidatorId, Vote>
        pub precommits: VoteSet,
        pol_index: PolIndex,       // derived: hash -> highest round with >2/3 prevotes (see perf #1)
    }
    fn enter_prevote(&mut self, proposal: &Block) -> Vote;
    fn enter_precommit(&mut self, round: Round) -> Vote;
    fn has_pol_for(&self, hash: BlockHash, lock_round: Round) -> bool;
    fn on_vote(&mut self, v: Vote);  // updates VoteSet + pol_index incrementally
    ```
  - *Back-of-envelope* (bar c): `LockState` ~64 B, checked on EVERY prevote/precommit handler. Call rate scales with vote rate (W65): ~63 calls/sec steady, ~500/sec burst (partition heal / Byzantine spam). Per-check budget ≈ ~5 ns (one field compare + one optional unwrap), target ≤100 ns end-to-end. **POL detection is the cost driver.** Naive scan = O(rounds × n): at `n=21`, `max_rounds_in_flight=16` that is ~336 field touches × ~5 ns ≈ **1.7 µs per prevote**; × 500/sec = **~850 µs/sec of pure scan CPU** — visible at P99 during view-change churn (commit latency 1 ms → 50 ms). Cliff: O(rounds×n) ~1.7µs vs incremental-index O(1) ~3 ns = **~560× per check**. Lock-state transition fsync is one-shot (~1/round), absorbed by the precommit group-commit (W65 precommit perf #1). **Zero allocations on the check path** — lock state lives in the replica struct, not the heap.
  - **Requirements** R1..R7 — write in `notes/68_lock_design.md`:
    - R1. `LockState` is `Copy`, ≤64 B, lives inline in `RoundState` (no `Box`/`Arc`).
    - R2. `enter_prevote(proposal)`: if locked at round `lr` and `proposal.hash != locked_block` and `!has_pol_for(proposal.hash, lr)` → return `Vote::nil()`; else `Vote::for_block(proposal.hash)`.
    - R3. `enter_precommit(round)`: precommit for the proposal only if `>2/3` prevotes for it exist in *this* round; on doing so, set `lock = (round, hash)`. Otherwise precommit nil.
    - R4. **Unlock only on a `>2/3` nil-precommit gather** — never on a local timeout alone. Audit every `lock = None` write site.
    - R5. VoteSet keyed by `(height, round)`; cleared on `enter_new_height`; `debug_assert!(vote.height == self.height)` on every insert.
    - R6. **Idempotent prevote**: once `step >= Prevote` for `(height, round)`, `enter_prevote` is a no-op (returns the recorded vote) — never a second, contradictory prevote.
    - R7. **Lock is set only from our own precommit decision** (R3), never from an observed remote precommit. Remote votes update VoteSet/pol_index only.
    - R8. (perf) `has_pol_for` is O(1) via a derived `pol_index` updated on insert — NOT an O(rounds×n) scan.

  #### Phase 3 — Make the tests pass, one failure at a time (~65 min)
  Ordered newbie→expert. Each card is the ladder you actually walk.

  - **(NEWBIE) When `voteset_rejects_stale_height` does NOT panic (stale vote accepted):**
    - Symptom: inserting a height-10 vote after `enter_new_height(11)` succeeds; later POL math mixes heights.
    - Why: VoteSet keyed by `round` only, not `(height, round)`; no per-insert height assert.
    - Fix: key VoteSet by `(height, round)`, clear on `enter_new_height`, add `debug_assert!(v.height == self.height)` in `on_vote`.
    - Muscle: a per-height protocol state must be keyed by height and cleared on height bump — never let stale-height messages leak into current math. Reapplies at: W73 evidence windows, W74 VSR op-log per-view, W75 view_change DoViewChange batching.

  - **(SENIOR) When `prevote_idempotent_in_round` shows two different votes:**
    - Symptom: a late proposal in the same round produces a second, contradictory prevote (A then B).
    - Why: `enter_prevote` has no `step >= Prevote` guard; it re-runs the rule each call.
    - Fix: gate on `if self.step >= Step::Prevote { return self.recorded_prevote(); }`; advance `step` on first prevote; keyed by `(height, round)`.
    - Cost avoided: a self-equivocation (slashable) — and the network treats your two prevotes as Byzantine.
    - Muscle: each protocol step fires at most once per (height, round) — idempotency is a state-machine guard, not a comment. Reapplies at: W73 precommit step guard, W74 VSR `on_prepare` dedup, W75 DoViewChange single-send.

  - **(SENIOR) When `prevote_for_non_locked_requires_pol` returns a vote for B (not nil):**

      - Fix: linear scan / direct index an array beats every hash table at n≤7 by 2-10×; if per-replica metadata is needed, a sibling fixed-cap array indexed by `ReplicaId as usize`. Don't reach for `HashMap` until n>64; clusters never hit it. The lint enforces it.
      - Cost avoided: ~17-47 ns/lookup warm; at 30k op/s ~500 µs–1.4 ms/sec; eliminates hash-iteration non-determinism (same trap as W74 matching-engine determinism gate).
      - Muscle: small-cap collections (n≤64) on a hot path use direct-indexed arrays, never `HashMap` — crossover ~n=32-64. Reapplies at: W74 matching-engine determinism gate (BTreeMap over HashMap for ordered iteration), W76 aeron per-subscriber state, W83+ ledger per-shard account index.

    - **(SENIOR) When `even_member_count_rejected` shows the constructor accepted n=4:**
      - Symptom: View with n=4; `quorum()` returns 3 but VSR requires n=2f+1 (odd) — math structurally wrong.
      - Why: no assertion at construction.
      - Fix: `View::new` returns `Err(ViewError::EvenMembers)` if `member_count % 2 == 0` (or compile-time `View<const N>` const-asserting N odd).
      - Muscle: VSR's quorum math depends on n=2f+1 — enforce at construction, not at every quorum call. Reapplies at: every VSR module taking a View.

    - **(SENIOR) When `view_reject_skip_backward` shows a backward skip accepted:**
      - Symptom: current view 5; a message claiming view 3 downgrades the replica; a stale leader drives state.
      - Why: `accept_view_bump` didn't compare against current — the name says "bump" but allowed any value.
      - Fix: `accept_view_bump(v)` returns `Err` if `v < current`, Ok if `v >= current`.
      - Muscle: view-num is monotonically non-decreasing per replica — backward moves are violations/attacks. Reapplies at: W75 view_change, W76 recovery (a recovering replica still rejects backward view-num).

    - **(SENIOR) When `next_view_overflow_returns_err` panics on u64::MAX:**
      - Symptom: `View { view_num: u64::MAX }.next_view()` panics (debug) / wraps to 0 (release) — both wrong.
      - Why: `view_num + 1` instead of `checked_add`.
      - Fix: `self.view_num.checked_add(1).ok_or(ViewError::ViewOverflow)`. Document the 2^64-view cluster lifetime bound explicitly.
      - Muscle: arithmetic on a security-critical counter uses `checked_*` — overflow is real even for u64 over long deployments. Reapplies at: W74 op_num, W83 ledger timestamp.

    - **(EXPERT/cross-primitive) When `view_composed_in_message_no_false_layout` shows `Prepare` not `Copy` / oversized:**
      - Symptom: embedding View in `Prepare` makes `Prepare` non-`Copy` or pushes it past the single-buffer budget.
      - Why: View secretly held a `Vec`/`Arc`, so it isn't `Copy` and the message can't sit inline in a bufpool buffer.
      - Fix: once View is the inline-array `Copy` struct (first card), `Prepare` composes cleanly and stays inline.
      - Cost avoided: per-message heap indirection that would defeat bufpool zero-copy (~50 ns malloc + a cache miss per message).
      - Muscle: a hot-path value type must be `Copy`+inline so every type that composes it stays inline — `Copy` is a transitive zero-copy guarantee. Reapplies at: W74 Prepare/PrepareOk messages, W76 aeron term metadata, W83 ledger transfer record.
