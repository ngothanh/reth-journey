**Tuesday — consensus-bft v0.5 ship + Blog if ready**

- [ ] **Build**: `crates/consensus-bft/src/lock.rs` — locking on prevoted value across rounds (Tendermint locking). (~150 min)
  - **Why**: Tendermint's *locking* is the single mechanism that prevents a Byzantine adversary from forcing two correct validators to commit different blocks in the same height under partial synchrony. Without locking, a 1/3+ adversary can split votes and produce a fork. Bar (c) substrate for downstream BFT validator quorum.
  - *Back-of-envelope* (bar c): lock state is a small fixed struct (~64 B) checked on EVERY prevote / precommit handler — call rate scales with vote rate (W65 perf), ~63 calls/sec steady, ~500/sec burst. Per-check ≈ ~5 ns (one struct field compare + one optional unwrap). The **POL detection** (`has_pol_for(hash, lock_round)`) is the cost driver — naively it scans the VoteSet looking for `>2/3 prevotes` at any round `r > lock_round` for the target hash. Naive scan = O(rounds × n) = ~1k ops at typical burst; expected target ≤100 ns. **Lock-state transition fsync is one-shot** (lock change is rare — ~1/round at most), so fsync cost is absorbed by precommit group-commit (W65 precommit perf #1). **Zero allocations on the check path** — lock state lives on the replica stack/struct.
  - **Read first**: Tendermint Core `consensus/state.go::enterPrevote`/`enterPrecommit`/`tryFinalize` (≈L1500-L1800). Buchman-Kwon-Milosevic 2018 "Latest Gossip on BFT Consensus" §3 (locking rule + unlock rule). Cosmos SDK `tendermint/spec/consensus/consensus.md` (LOCK_STATE diagram).
  - **Design**:
    ```rust
    pub struct LockState {
        pub locked_round: Option<Round>,
        pub locked_block: Option<BlockHash>,
        pub valid_round: Option<Round>,
        pub valid_block: Option<BlockHash>,
    }
    pub enum Step { Propose, Prevote, Precommit, Commit }
    pub struct RoundState {
        pub height: u64,
        pub round: Round,
        pub step: Step,
        pub lock: LockState,
        pub prevotes: VoteSet,    // round -> hash -> Vec<Vote>
        pub precommits: VoteSet,
    }
    // Core rule
    fn try_prevote(&mut self, proposal: &Block) -> Vote {
        if let Some(lr) = self.lock.locked_round {
            // Only prevote for locked_block UNLESS there's POL (proof of lock change) at round > lr
            if proposal.hash != self.lock.locked_block.unwrap() && !self.has_pol_for(proposal.hash, lr) {
                return Vote::nil();  // prevote nil
            }
        }
        Vote::for_block(proposal.hash)
    }
    ```
    **Invariants**: (i) Once `locked_block = B at round r`, a correct validator NEVER prevotes for `B' != B` in round `r' > r` unless it sees `>2/3 prevotes` for `B'` in some round `r'' >= r` (the POL — Proof of Lock-change). (ii) `valid_block` is the most recent block with `>2/3 prevotes` (gets included in next round's proposal). (iii) A precommit at round `r` for block `B` locks the validator on `(r, B)`. (iv) A *nil* precommit unlocks (sets `locked_round = None`) — but the trickier rule: re-locking requires fresh POL.
  - **Build steps**: 1. (~20 min) `LockState` + `VoteSet { round -> hash -> BTreeMap<ValidatorId, Vote> }`. 2. (~30 min) `enter_prevote` — implement the rule above. 3. (~25 min) `enter_precommit` — only precommit if we see `>2/3` prevotes for the proposal in this round; if yes, set lock. 4. (~25 min) POL detection: `has_pol_for(hash, lock_round) = exists r' > lock_round s.t. prevotes[r'][hash].count > 2/3 * n`. 5. (~25 min) Unlock-on-nil-precommit. 6. (~25 min) Property tests below.
  - **Pitfalls** (named, 4):
    - *Lock without POL*: **Symptom**: validator unlocks too eagerly, signs conflicting precommits → slashable double-sign. **Fix**: only call `lock = None` on explicit nil-precommit gathering `>2/3`, never on local timeout alone. Audit every `lock = None` write site.
    - *Stale POL*: **Symptom**: validator uses stale prevote set from an old height (after height bump) to justify unlock. **Fix**: VoteSet keyed by `(height, round)`; clear on `enter_new_height`. Add a debug assert `vote.height == self.height` on every insert.
    - *Equivocation under nil*: **Symptom**: prevote-nil at round r, then prevote-block at round r (same round, contradictory) when proposal arrives late. **Fix**: gate `enter_prevote` with `self.step >= Step::Prevote` check — once you've prevoted for this round, never prevote again. Idempotency table keyed `(height, round)`.
    - *Lock-on-future-round*: **Symptom**: receive a precommit message for round r+5 while in round r, optimistically lock — but the round r+5 may never form. **Fix**: only set lock from *our own* precommit decision, never from observed remote votes. Remote votes update VoteSet only.
  - **Test scenarios**: (a) Adversarial proposer at round 0 sends block A to half, B to other half; verify no correct validator commits both. (b) Network partition for 2 rounds, heal — locked validators must converge on the locked block. (c) 4-node {1 Byzantine, 3 honest} — Byzantine double-signs prevote A and B → honest validators should detect via evidence module (W73). (d) Random fuzz: 100 scenarios with reordered/dropped/duplicated votes — no double-commit, ever.
  - **Acceptance**: property test `no_double_commit` passes 10k random schedules. `lock_consistency` invariant — at any time, if any honest validator has `locked_block = B at round r`, no other honest validator has `locked_block = B' != B at round r`. Bench: 1000 rounds at 4-node cluster in <2s.
  - **Downstream**: W73 fork-choice rule uses locked-block info to break ties (lock takes priority over freshness). W73 evidence.rs detects locking-rule violations as slashable. consensus-vsr v0.5 (W76) shares the *concept* but VSR has a different mechanism (view-numbers) — comparing the two is the M21 retrospective.
  - **Expect to hit (perf) #1 — O(rounds × n) POL scan on every prevote handler (bar (c) violation)**: naive `has_pol_for(hash, lock_round) = self.prevotes.iter().filter(|(r, _)| r > lock_round).any(|(_, votes)| votes_for(hash) > 2*n/3)` walks the entire VoteSet for every prevote. At burst (Byzantine spam, partition heal), with `max_rounds_in_flight = 16` and `n = 21` validators, that's ~336 ops per prevote × ~500 prevotes/sec = 168k ops/sec — visible at P99 even under burst. Symptom: `perf top` shows `has_pol_for` at 20% CPU during view-change churn; commit latency spikes from 1 ms to 50 ms.
    - Fix: maintain a **running `pol_index: AHashMap<Hash, Round>`** updated incrementally on each VoteSet insert — `pol_index[hash] = max(pol_index[hash], round)` whenever the running tally first crosses 2/3+1 (inherits the running-tally pattern from W65 precommit perf #2). POL check becomes O(1): `pol_index.get(hash).map_or(false, |&r| r > lock_round)`.
    - Cost avoided: O(rounds × n) → O(1) per check; saves ~336 ops × 5 ns = ~1.7 µs per prevote × 500/sec = ~850 µs/sec of CPU; eliminates the burst-time P99 spike entirely.
    - Muscle: cross-cutting "any past message satisfying X" queries should be maintained as a derived index updated on insert, not re-scanned on query. Reapplies at: W65 precommit threshold tally (already noted), W67 raft match-index aggregation, W73 fork_choice "highest-QC descendant of locked" query, W74 VSR PrepareOk quorum (BitSet `count_ones`).

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: a non-deterministic leader-election protocol (Raft with random timeouts) can stall under partial synchrony for unbounded time. VSR replaces random election with a deterministic function from view-num to leader. The View struct encodes that function. Done naïvely (Vec<ReplicaId> members, HashMap for metadata) the per-message touch cost spikes from 3 ns to 15-50 ns; multiplied by 30k ops/sec/replica, that's 1 ms/sec of pure cache-fetch overhead — before the protocol logic runs.

  - **Requirements** — write in `crates/consensus-vsr/notes/68_view_design.md`:
    - R1. `View { view_num: u64, members: [ReplicaId; MAX_REPLICAS], member_count: u8 }` — fixed-size, `Copy`-able, fits in ≤ 1 cache line.
    - R2. `MAX_REPLICAS = 7` (TigerBeetle's production max). `ReplicaId = u8` (clusters are small).
    - R3. **Deterministic leader**: `leader() = members[view_num % member_count]`. Pure function — same view + members ⇒ same leader on every replica.
    - R4. `quorum() = member_count / 2 + 1` (f+1 of n=2f+1). VSR requires odd member_count.
    - R5. **View-num monotonicity**: `accept_view_bump(v)` requires `v >= current.view_num`. Skips forward are allowed (partition-heal); skips backward are rejected.
    - R6. **Hot-path budget**: `view.leader()` ≤ 3 ns; View access is one L1 fetch.
    - R7. **No heap on hot path**: View is inline-array; no `Vec`, no `Box`, no `Arc<View>` for per-message touch.
    - R8. **No HashMap for members**: linear scan / direct index at n ≤ 7 beats hashing.

  #### Phase 3 — Make the tests pass, one failure at a time (~55 min)

  - **When `bench_view_leader_under_3ns` reports ~15 ns and `view_is_copy_no_alloc` flags allocations:**
    - Symptom: `view.leader()` is 5× over budget. Heaptrack shows ~30k `Vec` allocations/sec from View clones. `perf c2c` flags `View::leader` causing L2 misses.
    - Why: you wrote `pub members: Vec<ReplicaId>`. The Vec header is 24 B + 8 B per replica; every View access is two cache fetches (the View struct + the heap allocation). View clones (which happen per-message) allocate a fresh Vec each time.
    - Fix: **inline fixed-cap array**: `pub members: [ReplicaId; MAX_REPLICAS]` + `pub member_count: u8`. `MAX_REPLICAS = 7` (TigerBeetle's cap), `ReplicaId = u8`, so members = 7 B + count = 1 B + view_num = 8 B = 16 B — well under 1 cache line. Whole View is `Copy` (derive `Copy, Clone`). `View::leader()` becomes one register load (`members[view_num % member_count]`) + one mod = ~3 ns.
    - Cost avoided: ~10 ns L2 miss per `view.leader()` call eliminated; at 30k op/s/replica saves ~300 µs/sec; eliminates allocator pressure (zero Vec allocs per View clone).
    - Muscle: small-cap fixed-size collections on the hot path must be inline arrays, not `Vec`; the cap is design discipline (`MAX_REPLICAS = 7` is the TigerBeetle ceiling). Reapplies at: W66 margin Position array, W74 VSR Log's per-op metadata, W74 raft prepare_ok BitSet (fixed-cap by validator count), W76 messaging-aeron subscriber list per term, W83+ ledger-deterministic per-shard transfer pool.

  - **When `lint_no_vec_or_hashmap_in_view_rs` matches a `HashMap<ReplicaId, ReplicaInfo>` somewhere:**
    - Symptom: a developer "improved" the per-replica metadata storage by replacing array indexing with `members.get(&replica_id)` via a `HashMap<ReplicaId, ReplicaInfo>`. View hot path slows from 3 ns to 20-50 ns; flame graph shows `ahash::AHasher::write` in `View::leader`.
    - Why: at n ≤ 7, the hash setup cost (~10-30 ns) exceeds the savings from "more flexibility." Worse, HashMap's RandomState differs between replicas → iteration order differs → non-determinism vector for replay.
    - Fix: at n ≤ 7, **linear scan an array beats every hash table** by 2-10×. If per-replica metadata is needed, attach it via a sibling fixed-cap array indexed by `ReplicaId as usize` — direct indexing, zero hash, zero probe. Don't reach for `HashMap` until n > 64; consensus clusters never hit that. The lint enforces this.
    - Cost avoided: ~17-47 ns per lookup (warm); at 30k op/s/replica saves ~500 µs – 1.4 ms/sec; eliminates hash-iteration non-determinism (different `RandomState` seeds across replicas give different iteration order → divergence; same trap as W74 matching-engine determinism gate).
    - Muscle: small-cap collections (n ≤ 64) on a hot path use direct-indexed arrays, never `HashMap`. The crossover point is around n=32-64 where linear scan + cache-friendliness wins over hashing. Reapplies at: W74 matching-engine determinism gate (BTreeMap over HashMap for ordered iteration), W76 messaging-aeron per-subscriber state (small, fixed cap), W83+ ledger per-shard account index (TigerBeetle uses fixed-cap arrays here too).

  - **When `even_member_count_rejected` shows constructor accepted member_count=4:**
    - Symptom: View constructed with n=4 (even). Subsequent `quorum()` calls return 3 (n/2 + 1 = 3), but VSR requires n = 2f+1 (odd); the math is structurally wrong.
    - Why: no assertion at View construction.
    - Fix: `View::new(view_num, members) -> Result<Self, Error>` returns `Err` if `member_count % 2 == 0`. Optionally a stronger compile-time guarantee: `View<const N: usize>` typed by member count; const-assert N is odd.
    - Muscle: VSR's quorum math depends on n=2f+1 — enforce it at construction, not at every quorum call site. Reapplies at: every VSR module that takes a View.

  - **When `view_reject_skip_backward` shows backward skip accepted:**
    - Symptom: replica's `current_view.view_num = 5`; receives a message claiming `view_num = 3`; replica downgrades. Stale leader now drives state.
    - Why: `accept_view_bump` didn't compare against current. The function name implies "bump" but allows any value.
    - Fix: `accept_view_bump(v) -> Result<()>` returns `Err` if `v < self.current_view.view_num`; returns Ok if `v == current` (no-op) or `v > current` (legitimate bump). Add a `view_num` monotonicity property test.
    - Muscle: view-num is monotonically non-decreasing per replica — backward moves are protocol violations or attacks. Reapplies at: W75 view_change, W76 recovery (a recovering replica still rejects backward view-num).

  - **When `next_view_overflow_returns_err` shows panic on u64::MAX:**
    - Symptom: `View { view_num: u64::MAX, .. }.next_view()` panics with arithmetic overflow.
    - Why: `view_num + 1` wraps to 0 in release mode (silent), panics in debug. Either is wrong — VSR requires monotonicity.
    - Fix: `next_view(self) -> Result<View, Error>` uses `self.view_num.checked_add(1).ok_or(Error::ViewOverflow)`. Document: cluster lifetime is bounded by 2^64 views (effectively infinite at realistic rates, but the bound must be explicit).
    - Muscle: every arithmetic on a security-critical counter uses `checked_*` — overflow is a real concern even for u64 over long deployments. Reapplies at: W74 op_num, W83 ledger timestamp.
