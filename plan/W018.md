**Wednesday — revm-interpreter dispatch**

- [ ] Read revm-interpreter source. Study opcode dispatch. (~60 min)
  - **Why**: The opcode dispatcher is the throughput-critical loop. revm runs at ~250-300 M opcodes/sec single-threaded; the dispatcher accounts for ~20% of that headroom. Three strategies exist: `match` (Rust idiomatic, branch-predicted), function-pointer table (cache-friendly, indirect call), and tail-call/computed-goto (LLVM-only, fastest). Understanding which revm picks and why is a prereq for any perf PR.
  - **Read first**: revm `crates/interpreter/src/instruction_table.rs` (the `[InstructionFn; 256]` table layout) and `crates/interpreter/src/interpreter.rs` (the run loop). Compare with evmone's `evmone/lib/evmone/baseline.cpp` (computed-goto). Also read `crates/interpreter/src/opcode.rs` for opcode constants.
  - **Design**:
    ```rust
    pub type InstructionFn = fn(&mut Interpreter, &mut dyn Host);
    pub fn make_instruction_table<H: Host, SPEC: Spec>() -> [InstructionFn; 256] {
        let mut table: [InstructionFn; 256] = [invalid_opcode; 256];
        table[0x00] = stop;
        table[0x01] = add;
        // ... patch with SPEC::enabled() guards for fork-gated opcodes
        table
    }
    // Hot loop:
    loop {
        let opcode = bytecode[pc];
        table[opcode as usize](&mut interp, host);
        if interp.instruction_result != Continue { break; }
        pc += 1;
    }
    ```
    **Invariants**:
    - Table is `'static` for the lifetime of the spec; rebuilt once per spec change.
    - Every entry is non-null (default to `invalid_opcode` for unassigned bytes).
    - PC advance happens AFTER handler runs (handlers may have advanced PC via PUSH/JUMP).
  - **Build steps** (READING task, but mapping to design notes):
    1. (~15 min) Enumerate every dispatcher strategy revm has tried (search git log for "dispatch").
    2. (~15 min) Measure your match-based dispatcher vs revm's table — `perf stat -e branch-misses` on a 1M-opcode trace.
    3. (~20 min) Document in `notes/08_revm_diff.md`: where match wins (small handlers, hot CMOV) and where table wins (cold branches).
    4. (~10 min) Append to `EXEC_VM_PERF_BACKLOG.md` an item for W31+ tail-call experiment (nightly-only).
  - **Pitfalls** (for when you migrate exec-vm):
    - *Const-eval table construction*: building the table at runtime forces `Box` indirection. **Symptom**: indirect call + cache miss per opcode. **Fix**: `const fn` table builder where possible (Rust 1.79+).
    - *Fork-gating bloat*: storing one table per fork × accepted forks bloats icache. **Symptom**: cold-start regressions on full-node start. **Fix**: lazy-build per spec, cache in `OnceLock<HashMap<SpecId, &'static Table>>`.
    - *Function-ptr indirection vs match*: on AMD Zen 4, indirect call mispredict ≈ 13 cycles vs match's branch ≈ 1 cycle when hot. **Symptom**: regression after table refactor on hot uniform-distribution bench. **Fix**: keep `match` for the 10 hottest opcodes; table for the cold tail.
  - **Test scenarios**: this is a study task, but verify: your exec-vm's hot-loop assembly (from `cargo asm exec_vm::interpreter::run`) has ≤ 1 indirect call per opcode.
  - **Acceptance**: 2-page note `notes/dispatch_strategies.md` covering: match vs table vs tail-call, when each wins, what revm chose, what evmone chose, your benchmark numbers.
  - **Downstream**: W19 precompile dispatch reuses the same table pattern (256-entry function-pointer array indexed by precompile address byte); Phase 4 W53 Handler dispatch is structurally identical.

**Thursday — revm hot path + ADD trace**

- [ ] Trace ADD end-to-end through revm AND your exec-vm. Compare overhead. (~60 min)
  - **Why**: ADD is the simplest non-trivial opcode (no memory, no host) so the *only* overhead measured is dispatch + stack + gas. Any cycles found beyond `pop+pop+wrapping_add+push+gas-spend` are dispatcher overhead. This is the cleanest possible microbench.
  - **Read first**: revm `crates/interpreter/src/instructions/arithmetic.rs::add` (3 lines); your equivalent. Also read perf's `record/report` man page for the trace methodology.
  - **Design**:
    ```rust
    // Bench harness: ADD-only bytecode (PUSH1 1 PUSH1 1 ADD repeated 10_000 times)
    fn bench_add_loop(c: &mut Criterion) {
        let bytecode = make_add_loop(10_000);
        c.bench_function("add_loop", |b| b.iter(|| run(&bytecode)));
    }
    ```
    **Invariants**:
    - Each ADD iteration = 9 bytes of bytecode (PUSH1+1+PUSH1+1+ADD = 5 bytes; reuse via JUMPDEST loop = 9-byte cycle).
    - Throughput target: ≥ 50 ns / opcode (≥ 20 M opcodes/sec); revm hits ~3 ns / opcode.
  - **Build steps**:
    1. (~10 min) Write the ADD-only bench bytecode generator.
    2. (~15 min) Run criterion on revm baseline; record cycles/opcode via `perf stat`.
    3. (~15 min) Run criterion on your exec-vm; record same.
    4. (~10 min) `perf record` both; compare hot functions in `report`.
    5. (~10 min) Document deltas in `EXEC_VM_PERF_BACKLOG.md` with specific functions (e.g. "exec_vm::stack::Stack::push 8 cycles vs revm 2 cycles — investigate Box<[U256;1024]> page-touch").
  - **Pitfalls**:
    - *Background noise*: hyperthreading, turbo boost, frequency scaling. **Symptom**: 20% run-to-run variance. **Fix**: `taskset -c 2 cargo bench`, disable turbo (`sudo cpupower frequency-set -g performance`).
    - *Inlining boundaries*: criterion's `black_box` may pessimize too far. **Symptom**: bench is dominated by black_box, not your code. **Fix**: pass the bytecode in, return a checksum out.
    - *Cold icache on first iter*: bench includes JIT-like warmup. **Symptom**: first 100 iters slow. **Fix**: criterion handles warmup; verify in `report.html`.
  - **Test scenarios**:
    - Bench at three loop sizes (1k, 10k, 100k) to detect dispatch overhead vs scaling.
    - Repeat with PUSH-DUP-DUP-POP (pure stack) to isolate stack-op cost from arithmetic.
  - **Acceptance**: a markdown table in `EXEC_VM_PERF_BACKLOG.md` listing your 5 biggest perf gaps vs revm, each with `perf record` evidence (function name + sample %).
  - **Downstream**: W31+ tail-call dispatch work uses this baseline as the regression gate; W92 block-stm parallelism only helps if single-thread is competitive.
