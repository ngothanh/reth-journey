**Tuesday — revm-primitives + `Database` trait alignment**

- [ ] **Build**: `crates/exec-vm/src/db.rs` — make your `StateCache` implement a `Database` trait shaped exactly like `revm_primitives::Database`, so unmodified revm could run on your backend. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: mirrors `revm_primitives::Database` (the seam every revm host plugs into). Three traps that bite a Java/Kotlin reflex: (1) `Database::basic` returns `Result<Option<AccountInfo>, Error>` not `AccountInfo` — a missing account is `Ok(None)`, an I/O failure is `Err`, and conflating them silently treats a DB error as "empty account" → wrong state root; (2) the trait takes `&mut self` in revm (the DB caches), so a `&self` signature won't drop in; (3) `code_by_hash` must be separable from `basic` or every `EXTCODECOPY` re-reads the whole account. Naive first attempt fails ≥1 test below; the debug session is the lesson. Downstream: W31 persistent-MPT exec integration, W49 hardening, W53 Handler, W68 exec-vm v1.0.

  #### Phase 1 — Problem, prediction, design (~25 min, no code yet)
  - 🎯 **Pre-prediction prompt** — sealed answers in `notes/08_db_trait_prediction.md`:
    - P1: the exact trait signature you'd reach for first (write the 4 method lines verbatim, including `self` receiver and return types).
    - P2: predicted cost of one `basic(addr)` call when the account is cache-hot vs cold-from-MDBX (ns).
    - P3: what your `basic` returns for an account that has never existed — `Ok(None)`, `Ok(Some(empty))`, or `Err`? Commit to one.
    - P4: will `#[derive]`-ing nothing and hand-writing the impl change behavior vs revm's blanket impls? (correctness prediction)
    - P5: list every Phase-2 test you predict your first attempt fails.
  - *Mental model*: `Database` is the read side of the EVM's world-state — the interpreter pulls account/code/storage/blockhash through it and never knows whether it's RAM, MDBX, or a remote node.
  - *Contract*: four methods — `basic(&mut self, Address) -> Result<Option<AccountInfo>, E>`, `code_by_hash(&mut self, B256) -> Result<Bytecode, E>`, `storage(&mut self, Address, U256) -> Result<U256, E>`, `block_hash(&mut self, u64) -> Result<B256, E>`. Associated `type Error`. NEVER write the bodies in Phase 1.
  - *Back-of-envelope*: a mainnet block touches ~2-5k account/storage slots. At an L2-resident cache hit (~7 ns) that's ~35 µs of reads; if `basic` accidentally does a cold MDBX page fetch (~3-5 µs each) on every call the block read-phase balloons to 10-15 ms — a 300× cliff. So the hot path must be: cache hit returns in ~one L2 access, and a *missing* account must NOT trigger a DB round-trip per call.
  - **Requirements** R1..R5 in `notes/08_db_trait_design.md`: R1 four-method signature; R2 `&mut self` receiver (caches mutate); R3 `Ok(None)` = absent, `Err` = I/O fault — never merge them; R4 `code_by_hash` independent of `basic`; R5 associated `type Error: std::error::Error`.
  - **Design walk-through** D1..D3 in the design doc:
    - D1. Property table of receivers you could pick: `&self` (no cache mutation, forces interior mutability), `&mut self` (revm's choice), `Arc<Mutex<_>>` interior (lock per read — name the cost). Pick one and justify.
    - D2. **Pre-mortem (load-bearing):** write the 4-line trace where a transient MDBX read error is mapped to `Ok(None)`, the EVM reads the account as empty, `SLOAD` returns 0, the tx takes the wrong branch, and the computed state root diverges from mainnet — a consensus split from one `?`-vs-`unwrap_or_default` slip.
    - D3. **Anti-shortcut audit:** the "obvious" reach is `fn basic(&self, a: Address) -> AccountInfo` returning a default for missing accounts (Java `Map.getOrDefault` reflex). One line why it's wrong here: it erases the Ok(None)/Err distinction AND blocks revm's `&mut self` caching.
  - **Output**: `notes/08_db_trait_design.md` with R1..R5, D1..D3, the consensus-split interleaving sketch.

  #### Phase 3 — Make the tests pass, one failure at a time (~40 min)
  - **(NEWBIE) When `missing_account_is_ok_none_not_err_not_default` reports `Ok(Some(default))`:**
    - Symptom: `assert_eq!(.., None)` fails — you returned a zeroed `AccountInfo`.
    - Why: `Map::getOrDefault` reflex — you substituted a default for the absent key.
    - Fix: `self.accounts.get(&addr).cloned()` returns `Option`; wrap in `Ok`. Default only at the *call site* that wants EIP-161 empty-account semantics, never in the DB.
    - Cost avoided: a wrong state root on every block with a SELFDESTRUCT/empty-account edge (consensus split — correctness, not speed).
    - Muscle: a read trait reports presence faithfully; defaulting is a caller policy, not a storage behavior. Reapplies at: W31 MPMC-free state reads, W42 txn read-set, W68 exec-vm v1.0 host.
  - **(SENIOR) When `missing_account_is_ok_none_not_err_not_default` collapses Err into Ok(None):**
    - Symptom: `faulty.basic(...).is_err()` fails — a forced MDBX error came back as `Ok(None)`.
    - Why: `self.read(addr).ok()` or `unwrap_or_default()` swallowed the error into the Option.
    - Fix: propagate with `?`; only an explicit *miss* (key absent) becomes `Ok(None)`. Reserve `Ok(None)` for `get` returning `None`, never for a fallible read failing.
    - Cost avoided: a transient I/O fault silently mutating consensus state — the D2 interleaving (bar-(b) correctness violation; would be undetectable until a state-root mismatch days later).
    - Muscle: never `.ok()` a fallible storage read down to an Option — absence and failure are different. Reapplies at: W26 wal read, W30 recovery replay, W42 txn snapshot read.
  - **(NEWBIE) When `database_object_safe_with_mut_self` fails to compile:**
    - Symptom: `takes_db(&mut db)` — "the trait `Database` is not implemented" or receiver mismatch.
    - Why: you wrote `fn basic(&self, ...)`; revm's caching DB requires `&mut self`.
    - Fix: change all four receivers to `&mut self`; thread `&mut` through the call sites.
    - Cost avoided: a from-scratch re-impl at W53 when the real revm Handler refuses to accept your DB.
    - Muscle: copy the upstream receiver exactly when you intend to be drop-in compatible. Reapplies at: W53 Handler, W68 exec-vm v1.0.
  - **(SENIOR) When `code_by_hash_does_not_reload_account` shows extra account reads:**
    - Symptom: `account_read_count()` increments inside `code_by_hash`.
    - Why: you implemented `code_by_hash` as `basic(addr_owning_code)?.code` — coupling code to account.
    - Fix: keep a separate `code: HashMap<B256, Bytecode>`; `code_by_hash` hits only it.
    - Cost avoided: every `EXTCODECOPY`/`DELEGATECALL` re-reading a full account record — ~2-5× the reads on contract-heavy blocks.
    - Muscle: dedup hot lookups by their own key; don't tunnel them through a coarser record. Reapplies at: W34 bloom keying, W39 lsm-core block cache.
  - **(EXPERT / perf) When `hot_read_is_in_l2_band_and_far_cheaper_than_cold` shows hot ≈ cold (bar (c)-grade):**
    - Symptom: hot and cold reads are both ~3 µs; the `* 4` assertion fails.
    - Why: `basic` re-derives the MDBX cursor / re-decodes RLP on every call — there is no in-memory cache layer; "StateCache" caches nothing.
    - Fix: front the DB with a `HashMap<Address, AccountInfo>` populated on first touch; serve subsequent reads from it.
    - Cost avoided: ~3-5 µs × ~2-5k slots = 10-15 ms per block in the read phase vs ~35 µs cached — a 300× cliff on the block critical path.
    - Muscle: a cache that doesn't make the second access cheaper isn't a cache; assert the cliff, don't assume it. Reapplies at: W14 bufpool, W34 bloom, W39 lsm-core, W58 matching-engine book.

  #### 5-year failure mode

TRIGGER: revm major version bumps `Database` to return futures, or a stateless-client mandate.
