- [ ] **Build**: `crates/concurrent/src/skiplist/node.rs` — `Node` with variable-length tail (`tower` length =
  height). Tower entries are `epoch_gc::Atomic<Node>`. Custom `Drop` is empty (frees go through `defer_destroy`). (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: skiplist node layout is the cache-locality foundation for find/insert/delete.
    Wrong layout (two allocations, pointer-chase per tower access) doubles L1 misses on the hot path; W38

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: a skiplist node holds a key/value pair plus a tower of atomic
    pointers (variable length up to MAX_HEIGHT=12). The tower entries are read sequentially during
    find/insert/delete walks — they MUST be contiguous in memory with the header to avoid pointer-chase
    cache misses. Standard `struct + Box<[Atomic]>` layout introduces a hop per access.

  - **Requirements** — write in `crates/concurrent/notes/37_node_design.md`:
    - R1. ONE allocation per Node: header + variable tower length stored inline (no `Box<[...]>` indirection).
    - R2. Tower height generated once at allocation time; fixed for the node's lifetime. Geometric
      distribution p=0.5, MAX_HEIGHT=12.
    - R3. `tower(&self) -> &[Atomic<Node>]` returns a slice over the inline tail; `&` access is safe (atomic
      ops mutate without `&mut`).
    - R4. Custom `Drop` is empty — frees go through EBR's `defer_destroy`, not Drop.
    - R5. Layout computed via `Layout::for_value` + `extend`; total size = header_size + height × 8 B (each
      `Atomic<Node>` is one word).
    - R6. Node alloc ≤ 50 ns (one malloc per insert); tower access ≤ 5 ns/level warm L1.

  - **Design walk-through** — answer each; no peeking at `crossbeam_skiplist::node` until Phase 3:
    - D1. Why NOT `struct Node<K, V> { key: K, val: V, tower: Box<[Atomic<Node>]> }`? Cite the cache-miss
      cost. How many allocations does this layout cost per insert?
    - D2. Inline-tail layout: write the `#[repr(C)]` struct with a `tower: [Atomic<Node>; 0]` zero-length
      array marker. How does the allocator know the real size?
    - D3. `Layout::for_value` + `extend`: write the layout computation. What's the alignment requirement?
    - D4. Tower access: `unsafe fn tower(&self) -> &[Atomic<Node>] { slice::from_raw_parts(addr_of!(self.tower)
      as *const _, self.height) }`. What's the safety invariant?
    - D5. Height generation: `rng.next_u32().leading_zeros().min(MAX_HEIGHT)`. Why must this run ONCE before
      allocation, not on each retry?
    - D6. **Pre-mortem (load-bearing)**: write the retry-with-different-height interleaving — insert
      computes height 4, allocates node, CAS fails, retry computes height 7, but the node was allocated for
      height 4 — what corrupts? Then write the two-alloc layout's cache-miss trace on a 10-level tower walk.
  - **Output**: `notes/37_node_design.md` with R1–R6, D1–D6, both interleavings.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `node_single_allocation` reports 2 allocations per `Node::new`:**
    - Symptom: allocator counter shows 2 per node; bench p50 ~100 ns instead of ~50 ns. Asm shows two
      separate `malloc` calls.
    - Why: layout is `struct Node<K, V> { key: K, val: V, tower: Box<[Atomic<Node>]> }`. That's *two*
      allocations per node (the node + the tower box), plus a pointer chase on every tower access.
      crossbeam-skiplist allocates inline.
    - Fix: use `Layout::for_value` with `extend` to compute the combined layout (header + height × 8 B);
      allocate once via `alloc(layout)`. Expose `tower(&self) -> &[Atomic<Node>]` that returns a slice
      over the tail via `slice::from_raw_parts(addr_of!(self.tower) as *const _, self.height)`.
    - Muscle: lock-free node memory layout is a one-shot decision; the inline-tail pattern is the
      canonical Rust idiom for variable-length structs. Reapplies at: W38 memtable Node, W74
      matching-engine order pool, W101 vector-db sealed-segment header.

  - **When `node_height_fixed_across_retries` reports a mismatch (height changed mid-flight):**
    - Symptom: insert's first attempt allocates a 4-tall tower; CAS at level 3 fails; retry recomputes
      height as 7; the existing node has only 4 tower entries but the algorithm tries to write to
      tower[4..7] — buffer overrun, miri "out-of-bounds".
    - Why: tower height generation `rng.next_u32().leading_zeros()` ran inside the retry loop. Each retry
      gets a *different* height for the same key, changing the node footprint mid-flight.
    - Fix: generate height *once*, before allocation; height is fixed for the node's lifetime. Move the
      height generation OUT of the retry loop into the pre-loop setup.
    - Muscle: any per-node invariant (height, key, allocated size) computed during retry breaks the
      algorithm — derive once, use forever. Reapplies at: W74 matching-engine order pool allocation, W42
      txn Txn ID allocation (must be one-shot, not retry-derived).

  - **When `bench_tower_walk_warm_l1` shows 10 L1 misses on a 10-level walk:**
    - Symptom: per-walk L1 miss count ≈ tower height; tower access cost ~50 ns/level instead of ~5 ns.
    - Why: tower entries are behind a `Box<[Atomic<Node>]>` — each access is a pointer chase from the
      Node header to the Box's heap location, missing L1 on the second access pattern.
    - Fix: inline-tail layout (the R1/R5 fix above) places tower contiguously with the header. A 10-level
      walk hits one L1 miss (the first access fetches the line containing the header + first few tower
      entries; subsequent accesses are L1 hits).
    - Muscle: cache locality for variable-length structs requires inline tails, not `Box`. Reapplies at:
      W74 matching-engine order pool, W101 vector-db sealed-segment header.

  - **5-year failure mode** (write in `notes/37_node_followup.md` after green): when MAX_HEIGHT exceeds 16
    (workload with >2^16 entries), the inline tail may push Node size past a useful threshold for slab
    allocators. State the migration: switch to a two-tier layout (small inline for height ≤ 8, separate
    heap for taller); profile breakpoint.

**Wednesday — Concurrent skiplist `find` + `insert` + medium reth PR (in parallel)**

- [ ] **Build**: `crates/concurrent/src/skiplist/find.rs` —
  `find(key, &Guard) -> Position { preds: [Shared<Node>; H], succs: [Shared<Node>; H] }`. At each level, walk right
  until you find a node `>=` key, recording the (pred, succ) pair. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: `find` is the foundation for insert and delete; both call into it. The two race
    classes — marked-successor + stale-pred — are how every "cooperative cleanup" lock-free DS gets broken
    silently. Downstream W38 memtable reads, W42 txn snapshot reads, W74 matching-engine order traversal all
    depend on this being correct.

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: walk the skiplist top-down, level-by-level; at each level
    accumulate the (predecessor, successor) pair for the target key. The algorithm cooperates with concurrent
    deletes by helping unlink any marked nodes observed. Without help-unlink, dead nodes accumulate; without
    pred-validation between levels, stale traversals corrupt the result.

  - **Requirements** — write in `crates/concurrent/notes/37_find_design.md`:
    - R1. Returns `Position { preds, succs }`: arrays of `Shared<Node>` indexed by level [0..H).
    - R2. At each level i, walks right from `preds[i+1]` (or head if i = H-1) until `succs[i].key >= key`.
    - R3. **Marked successors are skipped**: a `succ` with the marker bit set in its `tower[i]` is
      cooperatively unlinked via CAS on `pred.tower[i]`. On CAS success at level 0, defer_destroy succ; on
      CAS failure, restart from the top level.
    - R4. **Pred validation between levels**: descending from level i to i-1, re-validate that `preds[i]`'s
      `tower[i-1]` still points where expected; on mismatch, restart from head.
    - R5. Runs under a Guard (the caller's). All atomic loads use `Acquire`; CAS uses `(Acquire, Acquire)`.
    - R6. ≥ 5 M find/sec single-thread on n=1 M warm; ≥ 500 k/sec cold.
    - R7. Amortized help-unlink cost ≤ 2 ns per find under steady load.

  - **Design walk-through** — answer each; no peeking at `crossbeam_skiplist::base::find` until Phase 3:
    - D1. Top-down walk: why start at level H-1 (top) instead of level 0? What does each level "skip"?
    - D2. Marker bit: which bit of the tower pointer encodes "this node is marked for deletion"? How do
      you check it (mask + compare)?
    - D3. Help-unlink CAS: write the operation. What's the expected value, what's the new value, what
      Ordering?
    - D4. Restart logic: under what conditions does `find` restart from level H-1 (vs continue at current
      level)? Enumerate the 3 restart triggers (marked-succ CAS fail; pred-validation fail; … name the
      third).
    - D5. Pred validation: write the check. Why is it necessary at level i-1 even though the pred from
      level i was just observed?
    - D6. **Pre-mortem (load-bearing)**: write the marked-successor accumulation interleaving — 1000 deletes
      mark nodes as removed without help-unlink; find walks past all 1000 markers on each call; per-find
      cost grows from ~200 ns to ~10 µs over 100k ops. Then write the stale-pred interleaving — pred
      observed at level i no longer linked at level i-1; walk starts from a node already removed at level
      i-1.
  - **Output**: `notes/37_find_design.md` with R1–R7, D1–D6, both interleavings.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `loom_find_help_unlink_progress` reports `find` cost growing with marked-node count:**
    - Symptom: 1000 marked nodes in the chain; each `find` walks past all 1000; cost grows linearly
      instead of staying O(log n).
    - Why: tagged-pointer marker bit on `tower[i]` indicates the node is logically deleted. `find` skips
      marked successors but does NOT help-unlink them — they accumulate.
    - Fix: when you observe `succ` marked, CAS `pred.tower[i]` to skip `succ`; on success, defer_destroy
      succ (if you're the unlinker at level 0); on failure, restart from the top level. Without
      help-unlink, dead nodes accumulate in the chain and `find` cost grows unboundedly.
    - Muscle: cooperative cleanup in lock-free DS is mandatory — readers MUST help unlinkers, otherwise
      readers' own cost amortizes the laziness of writers. Reapplies at: W42 MVCC version chain cleanup,
      W74 matching-engine cancelled-order cleanup.

  - **When `loom_find_stale_pred_restarts` reports a walk continuing past a stale pred (corruption):**
    - Symptom: T1 observed `pred → succ` at level i, descended to level i-1; T2 unlinked `pred → succ`
      at level i-1; T1's level-i-1 walk starts from a stale pred and traverses nodes already removed.
    - Why: stale-pred race. Every level descent must re-validate the pred from the upper level — without
      it, the pred may be gone at level i-1.
    - Fix: every level traversal validates that the pred from the upper level is still linked at this
      level (i.e., `pred.tower[i-1].load(Acquire)` still points where you expect). On mismatch, restart
      from the head.
    - Muscle: lock-free DS invariants must hold at *every* atomic observation point; observing an
      invariant at level i does not imply it holds at level i-1. Reapplies at: W42 MVCC version-chain
      traversal, W74 matching-engine order-book level descent.

  - **5-year failure mode** (write in `notes/37_find_followup.md` after green): when SIMD compare
    instructions allow batched key compares (e.g. AVX-512 for fixed-width keys), the per-level walk's
    inner compare loop can be 8-way vectorized. State the migration: gate via target-cpu detection; the
    scalar walk remains the portable fallback.
- [ ] **Build**: `crates/concurrent/src/skiplist/insert.rs` — bottom-up linking, CAS at each level. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: insert at level 0 is the linearization point — any subsequent find() either sees
    the key or doesn't, based on this one CAS. The bottom-up linking + retry-on-CAS-fail pattern is the

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: insert a new node into a skiplist atomically. The trick: there's
    no single CAS that links the new node at all levels — instead, level 0's CAS is the linearization point
    (commits the insert), and levels 1..H are lazy-linked. CAS failures restart from `find()` (NOT from where
    you left off, otherwise the pred is stale).

  - **Requirements** — write in `crates/concurrent/notes/37_insert_design.md`:
    - R1. Bottom-up linking: level 0 is the linearization point; levels 1..H follow.
    - R2. Level 0 CAS is `pred.tower[0].compare_exchange(succ, new_node, AcqRel, Acquire)`.
    - R3. Every CAS failure RESTARTS via `find()` — never reuses the stale pred/succ.
    - R4. Partial linking is acceptable: if levels 1..H race with a delete, leave them unlinked. Future
      inserts will help-link them.
    - R5. ≥ 1 M insert/sec single-thread on n=1 M warm.
    - R6. Aggregate scales sublinearly (top-level head is a contention hotspot — known limitation).

  - **Design walk-through** — answer each:

      top-down can't?

      success, Acquire failure?
    - D3. CAS failure scenarios: enumerate them (pred unlinked, succ changed, marked-bit set, …). For
      each, is the right response to retry `find()` or restart at top level?
    - D4. Lazy upper-level linking: if level 1 CAS fails, what do you do? (Hint: it's NOT to restart

    - D5. Top-level head contention: every tall-tower insert touches `head.tower[H-1]`. Why is this a

    - D6. **Pre-mortem (load-bearing)**: write the stale-pred-after-CAS-fail interleaving — insert
      observes (pred, succ); CAS fails because pred's tower changed; retry uses the same stale pred;

      but level 1 races a delete.

  - **When `insert_cas_fail_restarts_find` reports chain corruption (find returns garbage / cycle):**
    - Symptom: under contention, find returns a key that wasn't inserted; or `assert!(node.next() !=
      node)` fires (cycle in the chain).

      corrupt the chain.

      has `height` levels — most inserts settle quickly. Pseudocode: `loop { pos = find(key); if
      pos.preds[0].tower[0].cas(pos.succs[0], new_node, AcqRel, Acquire).is_ok() { break } }`.
    - Muscle: lock-free CAS retry must reacquire the predecessor state — never reuse a pred across a
      failed CAS. Reapplies at: W42 MVCC version chain extension, W74 matching-engine order
      placement, W11 MPMC head/tail enqueue.

    - Why: insert at level 0 succeeds (the linearization point), but link at level 1 races with a
      delete. If you bail out, the node is partially linked — find() observes it at level 0 only.
      Correctness is preserved (level 0 is the truth), but performance degrades because higher levels
      are sparse.

      inserts (when their find() walks past the partially-linked node, they help-link it). Add a unit

**Thursday — Concurrent skiplist `delete` + loom + skyzh MVCC Day 2-3 reading**

- [ ] **Build**: `crates/concurrent/src/skiplist/delete.rs` — two-phase: (a) **logical** mark — set the marker bit
  on `tower[0]` via CAS; (b) **physical** unlink — CAS each pred.tower[i] to bypass the marked node, top-down.
  After all levels unlinked, `Guard::defer_destroy(node)`. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: two-phase delete is the canonical lock-free deletion pattern. The mark is the
    linearization point; physical unlink is cooperative. Get the ABA case wrong → silent corruption; get the
    defer-destroy timing wrong → UAF in concurrent finds; get the EBR backlog wrong → unbounded memory under
    delete-heavy workloads (W38 memtable freeze is the canonical case).

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: deletion in a lock-free skiplist must be atomic with respect to
    every concurrent find/insert. Two phases: (1) **logical** mark on tower[0] = linearization point; (2)
    **physical** unlink top-down through tower levels = cooperative cleanup. `defer_destroy` only fires after
    physical unlink completes, otherwise concurrent finds at level i>0 UAF.

  - **Requirements** — write in `crates/concurrent/notes/37_delete_design.md`:
    - R1. Phase 1: CAS tower[0]'s low bit to 1 (the marker). Successful CAS = linearization point of this
      delete.
    - R2. Phase 2: top-down physical unlink via CAS on each `pred.tower[i]` (skip the marked node).
    - R3. **Race semantics on same-key concurrent delete**: both threads call `remove(k)`; only one wins
      the mark; the LOSER still returns the value it observed at `find()` time (not "not found").
    - R4. **`defer_destroy` fires only after the unlinker** (the thread that successfully CAS'd level 0's

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `delete_concurrent_same_key_both_return_value` reports the loser returns None:**
    - Symptom: 2 threads delete(k); one CAS wins; the loser's CAS fails; loser returns None instead of
      v. The user sees "key wasn't there" even though it was.
    - Why: you mark level 0 successfully, but another delete on the *same key* races. Both observe the
      unmarked state; one CAS wins, the other returns "not found" — but the loser is the user's
      `remove()` call, which should have returned the value. Your API loses data.
    - Fix: the loser still won a useful race — it observed the value at find() time. Return the value
      the loser saw. The mark is the linearization point of the *one* successful delete; both threads
      observed the same key existed before the linearization, so both return Some(v).
    - Muscle: in lock-free APIs, the "success" of a user-facing op is decoupled from "I won the CAS";
      observe-time is sufficient when the result is read-shaped. Reapplies at: W74 matching-engine
      order-cancel under partial-fill race, W42 txn read-then-decide.

  - **When `loom_delete_defer_destroy_after_unlink` reports a UAF on a concurrent find:**
    - Symptom: T1 marks node X, defer_destroys X; T2's find() is still traversing levels >0 through X;
      T2 derefs a freed Atomic.
    - Why: you `defer_destroy(node)` after marking but before all levels are physically unlinked. Some
      other thread's find() is still traversing levels >0 through this node. The defer fires (via EBR
      advance + bag drain); that thread now derefs a freed `Atomic`.
    - Fix: `defer_destroy` fires only after the *unlinker* (the thread that successfully CAS'd level 0's
      pred to bypass the marked node) completes. The marker (logical delete) does not free; only the
      unlinker does. Restructure: marking is "logical delete returns value"; unlinker is "all physical
      links removed → defer".
    - Muscle: in two-phase delete, only one of the two phases owns the free — and it's the one that
      proves no other reader holds the pointer. Reapplies at: W42 MVCC version-chain reclamation, W74
      matching-engine cancelled-order reclamation.

  - **When `loom_delete_aba_protection` reports CAS spuriously succeeding on recycled address:**
    - Symptom: T1 expects A in `pred.tower[i]`; A is unlinked, freed; allocator reuses A's address for
      B; T3 stores B in `pred.tower[i]`; T1's CAS expecting A succeeds because the bit pattern matches.
      Chain corruption.
    - Why: ABA on the tower entry. `pred.tower[i]` was `A`; A gets unlinked, freed, the allocator reuses
      the address for `B`; `pred.tower[i]` is now `B`. Your CAS expecting A succeeds because the bit
      pattern matches.
    - Fix: EBR is the answer — A cannot be reclaimed while any thread holds a guard pinned in A's
      epoch, and your `find()` runs under a guard. CAS won't observe a recycled address while the
      guard is live. This is the whole reason EBR exists; you'll feel it here for the first time.
      Verify: T1's find()'s guard pins A's epoch; T3 cannot allocate at A's address until the guard
      drops.
    - Muscle: lock-free DS invariants must hold at *every* atomic observation point. The two-phase
      delete is the canonical example. Reapplies at: matching-engine order cancel (W74 — partial fills
      + cancel race), all future lock-free maps.

  - **When `delete_heavy_workload_bounded_memory` reports RSS growing unboundedly:**
    - Symptom: 60 s sustained 100k delete/sec; RSS climbs from 1 GB to 5 GB; epoch-advance shows up at
      ~15% CPU in flamegraphs.
    - Why: every delete calls `Guard::defer_destroy(node)`. Under sustained delete (lsm-core memtable
      freeze iterating tombstones; TTL eviction scan; long-range delete in vector-db), the per-`Local`
      bag fills faster than EBR can advance epochs. Memory grows unboundedly; epoch-advance becomes a
      CPU hot-spot; eventually OOM under sustained delete load — silent until the box dies.
    - Fix: explicit `Guard::flush()` every ~1024 ops to force the bag to drain into the global queue;
      OR for known-quiesced-reader paths (memtable freeze barrier in W38), switch temporarily to
      synchronous `drop` since no other thread holds references.
    - Cost avoided: bounded memory under sustained delete; eliminates the silent OOM mode that
      delete-heavy workloads otherwise trigger; eliminates the epoch-advance CPU spike.
    - Muscle: EBR's reclamation is amortized — under skewed workloads (delete-heavy, scan-heavy) the
      amortization assumption breaks; always provide explicit drain hooks. Reapplies at: W38 lsm-core
      memtable freeze (the canonical drain case), W42 `txn` MVCC version reclamation, W74
      matching-engine order cancel under sustained churn.
