  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: every consensus type needs a single canonical wire format that
    round-trips with Geth / `alloy-rlp` / `ethereumjs` byte-for-byte. Two traits frame the contract: encode (in
    one pass, no scratch buffer) and decode (advancing the caller's cursor). Both must stay object-safe so
    downstream collections of heterogeneous encodables (W9 envelopes, W10 trie children) can be `&dyn Encodable`.

  - **Requirements** — write in `crates/eth-rlp/notes/05_encodable_design.md`:
    - R1. `Encodable` has `encode(&self, out: &mut dyn BufMut)` and `length(&self) -> usize`; both are
      object-safe.
    - R2. `length()` is computed *arithmetically* — no impl is permitted to encode into a scratch buffer to
      measure.
    - R3. `Decodable` has `decode(buf: &mut &[u8]) -> Result<Self, Error>` where `Self: Sized`; on `Ok` the
      cursor `*buf` points at the first byte AFTER what was consumed.
    - R4. The trait pair must mirror `alloy-rlp` signatures exactly (drop-in compatible).
    - R5. A blanket impl over `&T: Encodable` for any `T: Encodable` exists so containers don't need to own.
    - R6. The error type is a single enum (`UnexpectedString`, `UnexpectedList`, `Overflow`, `InputTooShort`,
      `NonCanonical`, `Custom(&'static str)`) — flat, no boxed errors.

  - **Design walk-through** — answer each in the design doc; no peeking at `alloy-rlp::lib.rs` until Phase 3:
    - D1. Why `&mut dyn BufMut` and not `<B: BufMut>(&self, out: &mut B)`? Walk through what fails to compile
      if `encode` is generic — write the exact `Box<dyn Encodable>` line that won't compile under the generic
      signature.
    - D2. Why does `decode` take `&mut &[u8]` not `&[u8]`? What's the alternative API (`(Self, &[u8])` tuple)
      and what makes the cursor-style ergonomic for nested decoders?
    - D3. Trait associated types vs free type parameters — does `Decodable::Error` need to be generic? Justify.
    - D4. Default-method opportunity: `length()` cannot have a sensible default (every type knows its own
      math), but `encode` could in theory call `length` to pre-allocate. Should it? Why or why not?
    - D5. Where does the `Error` enum live — same module as the traits, separate `error.rs`, or re-exported
      from `lib.rs`? Justify against alloy's layout.
    - D6. **Pre-mortem**: name the *exact* line of caller code that fails to compile if you choose generic
      `encode<B: BufMut>` instead of `dyn`. Write it down. If you can't write it, you don't yet understand
      object safety well enough to ship this trait.
  - **Output**: `notes/05_encodable_design.md` with R1–R6, D1–D6, the pre-mortem snippet.

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)

  - **When `encodable_dyn_object_safe` reports "the trait `Encodable` cannot be made into an object":**
    - Symptom: `error[E0038]: the trait Encodable cannot be made into an object … because method encode has
      generic type parameters`.
    - Why: a generic method parameter (`<B: BufMut>`) cannot be dispatched dynamically — `vtable` slots are
      monomorphized per concrete `B`, which isn't known at the trait-object site.
    - Fix: take `out: &mut dyn BufMut` instead of `out: &mut B`. The single dynamic dispatch per `put_u8` is
      hidden behind `bytes`' own machinery and well-amortized.
    - Muscle: a serialization trait that will appear behind `dyn` keeps its writer parameter as `dyn`,
      not generic. Reapplies at: W9 envelope `dyn Encodable`, W10 trie child iteration.

  - **When `length_does_not_call_encode` reports counter > 0:**
    - Symptom: your impl of `length()` for some composite type called `self.encode(&mut scratch); scratch.len()`.
      Counter increments; test fails.
    - Why: it's tempting to define `length` via the encode itself (DRY), but containers call `length()` *per
      child* to size their own header — that recurses to O(2^depth) encode work.
    - Fix: every `Encodable::length` is implemented as pure arithmetic — sum of children's `length()` plus
      header-bytes (`1 + length_of_length(payload_len)` for long form, `1` for short). No scratch buffer ever.
    - Muscle: encoded length is a *computed* property, never a *measured* one. Reapplies at: W6 Header encode,
      W9 TxEnvelope, every RLP type.

  - **When `decode_advances_cursor` reports cursor at position 0 after decode:**
    - Symptom: after `let v = u64::decode(&mut buf)?;` the slice `buf` still points at the same bytes; the
      next decode re-reads the value.
    - Why: your impl built the value but forgot `*buf = &buf[consumed..]`. The `&mut &[u8]` parameter is the
      whole point — it's how you tell the caller "I ate N bytes".
    - Fix: every `Decodable::decode` ends with `*buf = &buf[consumed..]` before `Ok(value)`. Compute `consumed`
      from the header + payload length you just read.
    - Muscle: a decoder's job is half "produce value", half "advance cursor". Reapplies at: W5 Wed list decode,
      W6 tx decode, W9 envelope decode.

  - **When `signatures_match_alloy_rlp` fails with a trait-bound mismatch:**
    - Symptom: `the trait alloy_rlp::Encodable is implemented for u64, but the trait eth_rlp::Encodable
      requires fn encode(&self, out: &mut dyn BufMut)` — alloy uses a different signature than yours.
    - Why: you diverged from alloy's exact API surface (perhaps you took `&mut Vec<u8>` instead of `dyn
      BufMut`, or returned `Result` instead of unit from `encode`).
    - Fix: re-align signatures byte-for-byte with `alloy-rlp v0.4`. The compat test exists so the divergence
      is caught at compile time, not in production when someone tries to swap implementations.
    - Muscle: mirroring a mature crate means *exact* signature match, not "spiritually similar". Reapplies at:
      W6 Header struct field order, W9 envelope encoding.

- [ ] **Build**: `crates/eth-rlp/src/header.rs` — Header { list, payload_length }. Test against ethereumjs fixtures. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: every RLP encode writes a Header then payload; every decode reads a Header first.
    A bug in this one type silently corrupts EVERY consumer downstream — W5 Tue scalars, W5 Wed `Vec<T>`, W6
    Header, W8 Receipt, W9 envelope, W10 trie. Canonicity bugs here are *consensus-split* bugs: two clients
    accepting different byte strings as the same value is how chains fork. Worth getting right slowly.

  #### Phase 1 — Problem, requirements, design (~25 min, no code yet)

  - **The problem this primitive solves**: RLP needs a length-prefix encoding that's unambiguous (so decode
    is canonical) and compact (so encode is cheap). The Header type is the 1- to 9-byte prefix that announces
    "string vs list" and "payload length". Get every boundary right — `0x7f/0x80`, `55/56`, leading-zero
    rejection — and the rest of RLP is mechanical.

  - **Requirements** — write in `crates/eth-rlp/notes/05_header_design.md`:
    - R1. `Header { list: bool, payload_length: usize }` is the in-memory representation.
    - R2. **Header-less case**: a single byte `< 0x80` IS its own complete encoding (no prefix written, no
      prefix consumed). Encode emits nothing; decode treats the byte itself as the value.
    - R3. **Short form**: payload `len ∈ [0, 55]` → prefix is `0x80 + len` (string) or `0xc0 + len` (list).
    - R4. **Long form**: payload `len >= 56` → prefix is `0xb7 + length_of_length(len)` (string) or
      `0xf7 + length_of_length(len)` (list), followed by `len` in big-endian.
    - R5. **Canonicity on decode**: reject (a) long form when payload would fit in short form (`len <= 55`);
      (b) length field with a leading zero byte; (c) overly-long length fields.
    - R6. Decode advances the caller's `&mut &[u8]` cursor past the prefix to the payload start. Header
      validation happens before any payload bytes are touched.

  - **Design walk-through** — answer each in the design doc; no peeking at `alloy-rlp::header.rs` until
    Phase 3:
    - D1. Write the byte ranges in a table: `[0x00..=0x7f]` is what? `[0x80..=0xb7]` is what? `[0xb8..=0xbf]`?
      `[0xc0..=0xf7]`? `[0xf8..=0xff]`? Cover all 256 first-byte values.
    - D2. The boundary value `55` appears in 2 places (short-form cap) and `56` in 2 places (long-form min).
      Identify a bug pattern where you'd write one as `<` and the other as `<=` and round-trip be wrong only
      for `len == 55` and `len == 56`.
    - D3. `length_of_length(len: usize) -> usize` returns the byte count needed to represent `len` in
      big-endian. What does it return for `len = 0`, `255`, `256`, `65535`, `65536`? Write the table.
    - D4. The header-less case is a *fixed point* — `0x7f.encode() = [0x7f]` and `[0x7f].decode() = (val=0x7f,
      remaining=[])`. Write 3 other byte values that exhibit the same fixed-point property, and 1 byte value
      that does NOT (e.g. `0x80`).
    - D5. Canonicity attack: an attacker submits `[0xb8, 0x01, 0x42]` which decodes as "long-form length-1
      string with payload `[0x42]`". A naive decoder accepts it. Walk through why this is a consensus split
      and what the canonical encoding of `0x42` actually is.
    - D6. **Pre-mortem**: write the 5-line decode interleaving where a malformed long-form header with a
      leading-zero length byte slips past your check. Where does the validation belong — before payload read
      or after?
  - **Output**: `notes/05_header_design.md` with R1–R6 + D1–D6 + the byte-range table from D1.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: RLP encodes only *strings* (byte sequences) and *lists* (sequences
    of values). Every primitive type — integers, addresses, hashes, byte vectors, `Bytes`, `bool` — must be
    mapped to one of those two. The mapping rules are subtle (integers are minimal-length, zero is empty,
    byte-vectors are strings not lists), and getting them wrong is a *consensus-split* bug, not just a perf
    bug.

  - **Requirements** — write in `crates/eth-rlp/notes/05_encodable_scalars_design.md`:
    - R1. Integers (`u8`–`u64`, `usize`, `U256`) encode as a *minimal big-endian byte slice* (no leading
      zeros), then RLP-encoded as a string.
    - R2. Integer `0` encodes as the **empty string** (`[0x80]`), NOT as `[0x00]`.
    - R3. `bool` encodes as the integer `0` or `1` (so `false` is `[0x80]`, `true` is `[0x01]`).
    - R4. `Vec<u8>`, `&[u8]`, `Bytes`, `String`, `[u8; N]` are RLP **strings** (one Header + payload bytes),
      NOT lists.
    - R5. `Address` (20 bytes) and `B256` (32 bytes) are encoded via their `[u8; N]` impl — straight strings.
    - R6. `length()` for each impl is pure arithmetic (no scratch encode).
    - R7. Decode round-trips every encode (every value V satisfies `decode(encode(V)) == V`); and decode
      rejects non-canonical inputs (`[0x00, 0x42]` as a u64, `[0x82, 0x00, 0x42]` as a u16 — both have
      a leading zero in the integer).
