- [ ] **Build**: `p2p::gossip` push path with bounded fanout (8 peers default), IHAVE pull-back. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: W52 Sat sketched gossip; this is the production push path that backs W56 raft votes, W64+ bft block proposals, and W76+ aeron control plane. Bounded fanout prevents amplification; IHAVE pull-back reduces redundant deliveries when peers already have the message. A naive `tick()` that walks the seen-LRU pegs a CPU on bookkeeping alone; an `app_deliver` that re-decodes the payload doubles raft's heartbeat cost across N peers.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: at 10k msgs/s × fanout=8 across 100 peers, the difference between "tick scans the LRU" and "tick reads a small recency ring" is the difference between 1% steady CPU and a periodic 1-Hz CPU spike that misses tail-latency SLOs. The difference between "app_deliver(&T)" and "app_deliver(id, raw, decoded)" is a 2× cost across the raft heartbeat handler.

  - **Requirements** — write in `crates/p2p/notes/55_gossip_push_design.md`:
    - R1. `publish(msg)`: compute id, insert into seen, app-deliver locally, fan out to `peers[..fanout]` (default 8).
    - R2. `on_recv(from, GossipMsg::Message(m))`: if id in seen → drop; else insert, app-deliver, fan out to `peers - {from}`.
    - R3. `on_recv(from, GossipMsg::Have(id))`: if id NOT in seen → respond with `Want(id)`.
    - R4. `on_recv(from, GossipMsg::Want(id))`: if id in `cache` → respond with `Message(payload)`; else drop (msg too old).
    - R5. `cache: lru::LruCache<B256, Bytes>` holds raw encoded msg bytes for Want responses; size = `seen_size × safety_factor` (at least 1000).
    - R6. `recent_ids: ArrayVec<B256, IHAVE_WINDOW=64>` ring populated by `publish`/`on_recv` directly — `tick()` reads it once per second, NOT by scanning the seen-LRU.
    - R7. `app_deliver(id: B256, raw: &[u8], decoded: &T)` — pass-through of pre-computed id + raw bytes + decoded value; consumer never re-decodes or re-hashes.
    - R8. Backpressure: per-peer bounded send queue via `backpressure::Queue`; `BackpressureStrategy::DropOldest` (newer msgs are more relevant).
    - R9. Peer-score: track `(delivered_first, delivered_dup, invalid_count)`; eject when `invalid > 0.1 * delivered_first`.
    - R10. Hot path budgets: ≤ 90 ns seen-msg fast path; ≤ 700 ns new-msg path (excluding network send + transport AEAD); tick CPU ≤ 1 ms.

  - **Design walk-through**:
    - D1. Recency ring vs LRU scan: at 1-Hz tick, scanning 10k LRU entries costs ~100 µs/s; reading a 64-entry ArrayVec costs ~0 µs. Compute the per-tick budget; why does the small absolute cost still matter? (Hint: per-tick spike breaks p99 latency promises to W56 raft.)
    - D2. `app_deliver` signature: write both versions. The bar-(b) `fn app_deliver(&T)` forces the consumer to compute its own id (re-encode + re-hash). The bar-(c) `fn app_deliver(id: B256, raw: &[u8], decoded: &T)` passes the work product through. Compute the saved cost at raft heartbeat scale (16-node cluster × 200 msg/s = 3200 deliveries/s × 700 ns = ~2 ms/s).
    - D3. cache sizing: a `Want(id)` from a slow peer arrives N seconds after `publish`. If `cache.len() < expected_rate × N`, the cache evicted the payload before the Want arrived → Want returns empty → peer never gets it (starvation). Compute size for 10k msg/s and 5s peer-slowness tolerance.
    - D4. Backpressure strategy: why DropOldest, not DropNew? (Hint: newer = more relevant for gossip; older votes for the same proposal are stale.) When is DropNew correct? (Hint: never in gossip; sometimes in WAL replay.)
    - D5. Peer-score: write the eject condition. What's `delivered_first` vs `delivered_dup`? (First arrival = useful contribution; dup arrival = wasted but harmless.) Why does an invalid msg cost more in score-weight than a dup?
    - D6. **Pre-mortem**: write the 3-step path from "tick walks seen-LRU" to "1-Hz CPU spike misses raft's 50-ms heartbeat SLO." This is the single load-bearing perf decision.
  - **Output**: `notes/55_gossip_push_design.md` with R1–R10 + answers to D1–D6 + sequence diagram for one publish→fan-out→IHAVE→Want→Message cycle.

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

  - **When `gossip_tick_no_lru_scan` reports samples in `LruCache::iter` and `gossip_tick_zero_alloc` shows ~32 allocs/tick:**
    - Symptom: 1-Hz timer fires and pegs ~1% CPU just on IHAVE accounting; under timer drift, ticks pile up; tail latency p99 spikes correlate with tick boundaries.
    - Why: a naive `tick()` walks `self.seen.iter()` (10k entries) to find "recent" ids, then allocates a fresh `Vec<B256>` per lazy peer for the IHAVE frame. 10k × ~10 ns scan = ~100 µs CPU; 32 × ~50 ns alloc = ~1.6 µs.
    - Fix: maintain `recent_ids: ArrayVec<B256, IHAVE_WINDOW>` populated by `publish`/`on_recv` directly (the call sites already touch each id). `tick()` reads this ring once, encodes ONE `IHave(ids)` frame into an `Arc<Bytes>`, fans out via `Arc::clone` to all lazy peers.
    - Cost avoided: ~100 µs/s scan + ~50 µs/s alloc = ~150 µs/s — small in % but removes a per-tick spike that breaks p99 SLOs.
    - Muscle: never scan a hashmap to "find recent things"; maintain the recency index alongside the lookup index. Cost of dual-index update is ~5 ns; cost of scan-on-read is per-call O(N). **Reapplies at**: W56 raft `last_log_term`/`last_log_index` queries (maintain as fields), W74 matching-engine `top_n_bids` (heap, don't sort), W76+ aeron `recent_subscribers_for_topic`.

  - **When `gossip_app_deliver_passes_id_and_raw` reports the wrong signature (consumer re-decodes):**
    - Symptom: `perf record` shows `T::decode` and `keccak256` each twice in the receive flame; raft heartbeat handler is 2× expected.
    - Why: `app_deliver(&T)` forces the consumer to re-derive what gossip already knows (id from frame hash, raw from wire).
    - Fix: signature becomes `app_deliver(&mut self, id: B256, raw: &[u8], decoded: &T)`. Gossip already decoded and computed the frame-hash id (W052 Sat perf #2); pass them through. Even better: expose `(id, raw)` as the primary callback so relay-only consumers can skip decoding entirely.
    - Cost avoided: ~500 ns decode + ~200 ns hash per inbound msg × 10k/s = ~7 ms/s CPU; on a 16-peer cluster, adds up across cores.
    - Muscle: layered codec architectures must pass the work product forward — never re-do an already-completed decode/hash in the layer above. **Reapplies at**: W56 raft `commit_index` advance, W64+ bft block-hash propagation, W77+ aeron `Image::fragment_handler` receives both raw and decoded.

  - **When `gossip_no_echo_to_sender` shows sender receives its own forward:**
    - Symptom: peer A publishes to B; B forwards to all 8 peers including A; A's seen-cache catches the dup but B's fanout slot is wasted on an echo.
    - Why: forwarding loop iterates `self.peers.iter()` without the `peer != from` filter.
    - Fix: explicit `for peer in self.peers.iter().filter(|p| **p != from).take(self.fanout)`. Ensure the filter is BEFORE `take`, not after (else the fanout target count is off by one).
    - Muscle: every broadcast-with-exclude needs the filter before the count limiter. Reapplies at: W56 raft AppendEntries to follower list (exclude self), W64+ bft proposal broadcast.

  - **When `gossip_backpressure_drops_oldest` drops the newest:**
    - Symptom: under sustained overload, a slow peer's queue keeps the oldest pending msg and drops every new arrival; peer never catches up because we're holding stale votes.
    - Why: `BackpressureStrategy::default()` is DropNew (the "fairness" default in many libraries).
    - Fix: explicit `backpressure::Queue::with_strategy(BackpressureStrategy::DropOldest)`. Gossip ALWAYS prefers the newer message — older votes for the same proposal are stale.
    - Muscle: backpressure policy is a per-channel decision; never use a library default for hot paths. Reapplies at: W56 raft AppendEntries queue (DropOldest), W76+ aeron Publication overflow (DropOldest for streams, DropNew for control).

  - **When `gossip_cache_resists_eviction_for_5s` shows 30% evictions of 5s-old msgs:**
    - Symptom: late-joining peer sends `Have(id)` for a msg from 5s ago; we respond `Want` (we don't have it cached); peer never receives; starvation.
    - Why: cache sized to seen-LRU size (10k entries) which churns at 10k/s sustained = full turnover every 1s.
    - Fix: `cache_size = expected_rate × peer_slowness_tolerance × safety_factor` (e.g., 10k × 5s × 2 = 100k entries). Trade memory (100k × 1 KB avg = 100 MB) for delivery completeness.
    - Muscle: cache sizing is workload-driven, never a copy-paste constant. Reapplies at: W56 raft log retention window, W76+ aeron term-buffer sizing.

  - **5-year failure mode** (write in `notes/55_gossip_push_followup.md` after green): when network scales to 10k peers (post-blockchain L2 mesh), the `recent_ids: ArrayVec<_, 64>` is too small (one second's worth of msgs); IHAVE frames become huge. Name the migration to a CountMinSketch-backed recency index with bounded memory and tunable false-positive rate.
  - *Back-of-envelope* (bar (c) — gossip is the data plane for raft/bft votes, tx mempool, block proposals):
    - Workload: 100-peer mesh, 10k msgs/s/node (tx-broadcast typical), fanout=8.
    - Inbound fast path (already-seen msg): wire decode of frame header ~50 ns → `seen.contains` lookup (LruCache hashmap) ~40 ns → return. **~90 ns/seen-msg**.
    - Inbound new msg: 90 ns dedup overhead + `app_deliver` callback (consumer-defined; budget 200 ns) + fanout to 7 peers × per-peer enqueue (~50 ns each, no per-peer clone if `Arc<Bytes>` from W052 Sat perf #1) ≈ **~700 ns end-to-end** (excluding network send).
    - Outbound: per-peer `backpressure::Queue::push` ≈ 30-50 ns uncontested CAS; on contended push ~100-150 ns.
    - IHAVE tick (every 1 s): summarize last-second seen-ids (~10k entries × 32 B id = 320 KB) — DON'T iterate the entire LRU each tick; maintain a separate ring of recent ids. Tick budget ≤ 1 ms (1 ms/1000 ms = 0.1% CPU).
    - At 10k msgs/s × 7 forwards × 700 ns ≈ 50 ms/s CPU = 5% on a single core. Goes red the moment fanout-clone returns or seen-check is heap-alloc'd.
  - **Read first**: W52 Sat enrichment; gossipsub-v1.1 spec §3 (mesh management).
  - **Design**:
    ```rust
    impl<T: Encodable + Decodable + Clone> GossipBroadcast<T> {
        pub fn publish(&mut self, msg: T) {
            let id = self.msg_id(&msg);
            self.seen.put(id, ());
            self.app_deliver(&msg);
            for peer in self.peers.iter().take(self.fanout) {
                self.send_to_peer(*peer, GossipMsg::Message(msg.clone()));
            }
        }
        pub fn on_recv(&mut self, from: PeerId, gmsg: GossipMsg<T>) {
            match gmsg {
                GossipMsg::Message(m) => {
                    let id = self.msg_id(&m);
                    if self.seen.contains(&id) { return; }
                    self.seen.put(id, ());
                    self.app_deliver(&m);
                    for peer in self.peers.iter().filter(|p| **p != from).take(self.fanout) {
                        self.send_to_peer(*peer, GossipMsg::Message(m.clone()));
                    }
                }
                GossipMsg::Have(id) => {
                    if !self.seen.contains(&id) {
                        self.send_to_peer(from, GossipMsg::Want(id));
                    }
                }
                GossipMsg::Want(id) => {
                    if let Some(m) = self.cache.get(&id) {
                        self.send_to_peer(from, GossipMsg::Message(m.clone()));
                    }
                }
            }
        }
    }
    ```
    **Invariants**:
    - Fanout fixed at 8 (configurable). Higher = faster propagation but more BW; lower = slower but cheaper.
    - Always exclude `from` when forwarding (don't echo).
    - IHAVE summaries piggybacked every 1s (W58 timer wheel will tick this).

  - **Pitfalls**:
    - *Cache too small*: Want arrives for evicted msg → no response → starvation. **Fix**: cache > seen size × safety factor.
    - *Backpressure drops new msgs first*: DropOldest is correct for gossip (newer = more relevant). DropNew would silence the latest update. **Fix**: use `BackpressureStrategy::DropOldest` explicitly.
    - *Fanout exclusion*: forgetting `peer != from` causes immediate echo + amplification. **Fix**: explicit filter.
    - **Expect to hit (perf) #1 — IHAVE tick iterates the entire seen-LRU (bar (c) violation)**: a naive `tick()` walks `self.seen.iter()` (10k entries) to find "recent" ids, then serializes them per-lazy-peer.       - Fix: maintain a separate ring `recent_ids: ArrayVec<B256, IHAVE_WINDOW>` (~64 entries) populated by `publish`/`on_recv` directly; tick reads this ring once, packages ONE pre-encoded `IHave(ids)` frame into an `Arc<Bytes>`, fans out via `Arc::clone` to all lazy peers.
      - Cost avoided: ~100 µs/s scan + 32 × ~50 ns alloc per tick = ~100 µs/s + ~50 µs/s ≈ ~150 µs/s; small in % but matters as fanout/tick-rate grows; importantly, removes a per-tick spike that breaks tail-latency SLOs.
      - Muscle: never scan a hashmap to "find recent things"; maintain the recency index alongside the lookup index. Cost of dual-index update is small (~5 ns); cost of scan-on-read is per-call O(N).
      - **Reapplies at**: W56 raft `last_log_term` / `last_log_index` queries (maintain as fields, don't scan log), W74 matching-engine `top_n_bids` (maintain a heap, don't sort price levels), W76+ aeron `recent_subscribers_for_topic`.
    - **Expect to hit (perf) #2 — `app_deliver` callback re-deserializes the inner payload (bar (c) violation)**: the gossip codec decodes `T` from the wire, calls `app_deliver(&T)`, the consumer (raft) then re-serializes `T` to compute its hash for its own dedup. Double decode + double hash. **Symptom**: `perf record` shows `T::decode` and `keccak256` each twice in the receive flame; raft heartbeat handler is 2× expected.
      - Fix: `app_deliver(id: B256, raw: &[u8], decoded: &T)` — the gossip layer ALREADY decoded `T` and computed `id` (frame hash, see W052 Sat perf #2). Pass them through; consumers reuse both. Even better: gossip exposes `raw + id` and lets the consumer choose whether to decode (some consumers, e.g., relay-only routers, never decode).
      - Cost avoided: ~500 ns decode + ~200 ns hash per inbound msg × 10k/s = ~7 ms/s CPU; on a 16-peer cluster it adds up across cores.
      - Muscle: layered codec architectures must pass the work product forward — never re-do an already-completed decode/hash in the layer above.
      - **Reapplies at**: W56 raft `commit_index` advance (already-computed indices propagate, don't re-walk log), W64+ bft block-hash propagation, W77+ aeron `Image::fragment_handler` receives both raw and decoded.
