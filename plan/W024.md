  - 🔧 **Why this matters**: this façade is the API that **every later bar-(c) bench calls**. Mirror: HdrHistogram's
    `Recorder`/`Histogram` snapshot split + Gil Tene's coordinated-omission `recordValueWithExpectedInterval`. The
    3 traps: (1) **CO correction off / absent** → the report lies about the tail (the single most common latency-bench
    bug, and the one that would discredit every downstream venue report); (2) **allocation on `record`** → the
    instrument perturbs the measured hot path (Heisenberg tax) and the histogram itself shows up in the flamegraph;
    (3) **runtime-calibrated `tsc_hz`** → two VOPR replicas fed identical TSC pairs produce *different* histograms,
    breaking the replay-determinism the whole venue core depends on. First-attempt impls fail ≥1 test below; the
    debug session is the lesson. Downstream consumers: W58 matching-engine ring bench, W82 v1.5 p99, W85 runtime
    cross-shard, W88/W92 ledger VOPR latency, W90 consensus-vsr, **W99 risk-engine per-mark-tick p99.99 at 100k
    accounts**, **W113 perp-dex-core v1.0 latency report**.

  #### Phase 1 — Problem, prediction, design (~50 min, no code yet)
  - 🎯 **Pre-prediction prompt** — sealed in `crates/latency-lab/notes/24fri_report_prediction.md` (these refine
    Monday's seed against the real module surfaces):
    - P1: the exact call sequence inside `record(tick_tsc, trade_tsc)` — list every step (and confirm none allocate).
    - P2: predicted self-overhead of `record` in ns (must stay ≤ the W22 ≤ ~20 ns budget) — and what dominates it.
    - P3: with a deterministic 1ms stall injected into a 1µs-cadence loop, predict raw p99.99 vs CO-corrected p99.99
      (give both, and the ratio).
    - P4: predicted `size_of::<Report>()` and whether `record` can ever grow the histogram after construction (must
      be No — static-mem).
    - P5: **list every Phase-2 test you predict your first attempt will fail.**
  - *Mental model*: a latency report is a *frozen measurement artifact*, not a live counter. `record` is the hot
    path (cheap, zero-alloc, non-perturbing); `snapshot` freezes; the frozen `Report` is what gets serialized,
    diffed across runs, and pasted into the W113 flagship-blog latency section. The deterministic `tsc_hz` is what
    lets the same workload on two replicas produce the same report — the property that makes a latency claim auditable.
  - *Contract*:
    ```rust
    pub struct Recorder { hist: hdr::Histogram, expected_interval_ns: u64, tsc_hz: u64 } // record path
    pub struct Report   { hist: hdr::Histogram, tsc_hz: u64, perf: Option<perf::Counters> } // frozen artifact
    impl Recorder {
        pub fn new(cfg: Config) -> Self;                         // pre-sizes hist [1ns,100s]; no alloc after this
        pub fn record(&mut self, tick_tsc: u64, trade_tsc: u64); // zero-alloc; CO-corrected by default
        pub fn record_raw(&mut self, tick_tsc: u64, trade_tsc: u64); // opt-out, for A/B demonstration only
        pub fn snapshot(&self) -> Report;                        // freezes the histogram
    }
    impl Report {
        pub fn p(&self, q: f64) -> u64;                          // percentile in ns, deterministic from tsc_hz
        pub fn tick_to_trade_summary(&self) -> Summary;          // p50/p99/p99.9/p99.99/max + samples + CO-omitted
        pub fn to_json(&self) -> String;                         // the serializable artifact
    }
    ```
  - *Back-of-envelope* (bar (c)): the `record` path = TSC subtract (~1 cycle) + ns convert (one mul + one shift,
    deterministic from stored `tsc_hz`) + HdrHistogram bucket index + counter increment (~few ns into a pre-sized
    array) + CO back-fill loop only when `delta > expected_interval` (bounded). Target self-overhead **≤ ~20 ns**,
    **0 bytes allocated**. CO correction adds cost ONLY on the rare slow sample (it back-fills the omitted samples
    that *would* have been recorded during the stall), so the common-case fast path stays ~few ns.
  - **Requirements** R1..R8 — write in `crates/latency-lab/notes/24fri_report_design.md`:
    - R1. `record` allocates **0 bytes** (verified by an allocation-counting global allocator in the test).
    - R2. CO correction is **on by default**; `record_raw` is the explicit opt-out; the default path back-fills
      omitted samples when `delta > expected_interval_ns`.
    - R3. `tsc_hz` is a **declared constant stored in `Report`**, never re-read from the OS per-process at report
      time → two `Report`s built from the same `(tick,trade)` TSC pairs + same `tsc_hz` serialize byte-identically.
    - R4. histogram is **static-mem**: pre-sized at `Recorder::new`; `record` never grows it; `size_of::<Recorder>`
      is constant w.r.t. sample count.
    - R5. self-overhead of `record` ≤ ~20 ns (measured via the `tsc` clock measuring itself — the W22 path).
    - R6. CO-corrected p99.99 ≥ ~1000× raw p99.99 under a deterministic 1ms-stall-into-1µs-loop injection.
    - R7. `perf` PMU counters are **optional**: on a host without `CAP_PERFMON`/non-Linux, `Report.perf == None`
      and the timing report still produces valid percentiles (no panic).
    - R8. `to_json()` round-trips: `Report::from_json(r.to_json()) == r` for percentiles and tsc_hz.
  - **Design questions** D1..D6 (the load-bearing one is D6):
    - D1. Recorder vs Report split — why two types? (Recorder is mutable + hot; Report is frozen + serializable.
      Sharing one type would invite recording into a "report" you've already published.)
    - D2. Where does the CO back-fill loop live, and why is it bounded? (In `record`, only when `delta >
      expected_interval`; bounded by `delta / expected_interval` — a 1ms stall in a 1µs loop back-fills ~1000
      synthetic samples, then stops. Unbounded back-fill on a pathological delta is itself a perturbation.)
    - D3. `tsc_hz` source — declared constant vs runtime calibration: why declared? (Runtime calibration injects
      non-determinism two VOPR replicas can't reproduce; the venue core's replay-determinism rule applies to the
      measurement leg too. Calibrate once *out of band*, store the constant.)
    - D4. static-mem sizing — what range + significant figures? (`[1ns, 100s]`, 3 sig-figs → ~a few KB, pre-sized;
      covers a 1ns floor to a 100s pathological stall without growth.)
    - D5. `perf` optionality — why must timing work without PMU? (Tick-to-trade *timing* is the deliverable; PMU
      counters (LLC-miss/false-sharing HITM) are enrichment for the W23 mechanical-sympathy story. A CI host or a
      laptop without `CAP_PERFMON` must still get a valid percentile report.)
    - D6. **Pre-mortem (load-bearing)** — write the EXACT 5-line trace where a downstream venue bench (say W99
      risk-engine) reports a beautiful p99.99 that is a *lie* because CO correction was silently off:
      ```
      1. W99 bench: record one tick-to-margin sample per intended mark tick
      2. a 2ms GIL/alloc/scheduler stall freezes the loop; ~2000 intended ticks are never attempted
      3. on resume, ONE 2ms sample is recorded among millions of ~1µs samples
      4. report.p(0.9999) -> ~1µs ("we hit the sub-tick budget!") -> pasted into the flagship blog
      5. production: 2000 margin checks each queued up-to-2ms -> a real liquidation fires 2ms late -> the moat leaks
      ```
      Which Friday test catches it? (R6's deterministic-stall test + the negative control proving raw ≠ corrected.)
  - **Output**: `crates/latency-lab/notes/24fri_report_design.md` with R1-R8, D1-D6, the CO-lie pre-mortem trace.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)
  Ordered newbie → expert.

  - **(NEWBIE) When `test_report_json_roundtrip` drops `tsc_hz`:**
    - Symptom: percentiles round-trip but `tsc_hz` is 0 / default after `from_json`.
    - Why: `tsc_hz` was treated as a derived runtime value, not a serialized field.
    - Fix: serialize `tsc_hz` explicitly in `to_json`; it is part of the report's identity (the ns conversion key).
    - Cost avoided: a deserialized report that silently re-converts with the wrong clock rate — wrong percentiles.
    - Muscle: anything the report's numbers DEPEND on must be IN the report. Reapplies at: W88 ledger VOPR report, W113 flagship-blog report artifact.

  - **(SENIOR) When `test_record_self_overhead_under_budget` reports ~120 ns/call:**
    - Symptom: 6× over the 20 ns budget; the instrument perturbs the very hot path it measures.
    - Why: `record` calls back into the OS for `tsc_hz` / does a syscall / formats a string per call.
    - Fix: precompute the ns conversion from the stored `tsc_hz` (a mul+shift); no syscall, no formatting on `record`.
    - Cost avoided: a measurement that changes the measurement — every downstream venue p99 inflated by the tool.
    - Muscle: the instrument must be cheaper than the thing measured; precompute everything off the hot path. Reapplies at: W58 matching ring bench, W99 risk-engine per-tick.

  - **(EXPERT) When `test_record_zero_alloc` shows growing allocation:**
    - Symptom: `ALLOC_BYTES` climbs across 1M `record` calls; the histogram shows up in the flamegraph.
    - Why: the histogram auto-grows its bucket array on out-of-range samples (HdrHistogram's `auto_resize`).
    - Fix: pre-size to `[1ns, 100s]` at `Recorder::new` with `auto_resize=false`; an out-of-range sample saturates
      to the max bucket (recorded as "≥100s") rather than allocating.
    - Cost avoided: allocator pressure + GC-like pauses ON the path you're trying to measure — the histogram becomes
      the tail it's reporting.
    - Muscle: static-mem on the hot path means pre-size and saturate, never grow. Reapplies at: W92 ledger static-mem invariants, W99 risk-engine zero-alloc audit, every bar-(c) recorder.

  - **(EXPERT) When `test_co_correction_unmasks_tail` shows corrected ≈ raw:**
    - Symptom: the corrected p99.99 is the same as raw — the 1ms stall shows as one sample, not ~1000.
    - Why: CO correction is off by default, or the back-fill compares against the wrong `expected_interval`.
    - Fix: default `record` to the CO path; on `delta > expected_interval_ns`, back-fill synthetic samples at
      `delta - k*expected_interval` for `k = 1..(delta/expected_interval)`; `record_raw` is the only opt-out.
    - Cost avoided: the worst class of latency bug — a report that *passes* while hiding the real tail; it would
      discredit every downstream venue latency claim (W113) the moment a reviewer injects a stall.
    - Muscle: coordinated omission is correctness, not a knob; correction is the default and the absence is the bug. Reapplies at: W88 ledger VOPR latency, W99 risk-engine p99.99, W113 perp-dex-core report.

  - **(EXPERT) When `test_report_replica_deterministic` shows two JSONs differing:**
    - Symptom: identical TSC pairs produce different reports across two builds in the same process.
    - Why: `record`/`snapshot` re-reads `tsc_hz` from `/proc/cpuinfo` or runs a calibration loop, so frequency
      scaling / scheduling makes the conversion non-deterministic.
    - Fix: capture `tsc_hz` ONCE as a declared constant in `Recorder::new` (out-of-band calibration), store it in
      `Report`, and convert deterministically from the stored value.
    - Cost avoided: a measurement leg that can't be VOPR-replayed — two replicas of the venue would report
      different latency for the same workload, breaking the replay-determinism the whole core rests on.
    - Muscle: push non-determinism to the edges — calibrate once, store the constant, convert deterministically. Reapplies at: W90 consensus-vsr, every cluster-VOPR latency report, W113.
