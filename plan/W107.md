  - *Mental model*: a deploy-verification harness is an *adversarial client* that hammers the service across the cutover and asserts the service never lied about being ready. It exists because "deploy succeeded" from the deployer's side and "no request was dropped" from the client's side are different claims, and only the second one matters for an uptime SLA.
  - *Contract*: `fn verify_zero_downtime(cfg: ProbeCfg) -> DowntimeReport` where `ProbeCfg { target: SocketAddr, rate_per_sec: u32, duration: Duration, trigger: Box<dyn FnOnce()> }` (the `trigger` invokes the actual deploy, e.g. shells out to `blue_green.sh`), and `DowntimeReport { sent: u64, ok: u64, refused: u64, server_err: u64, timed_out: u64, max_gap: Duration }`. Invariant the harness asserts: `refused + server_err + timed_out == 0`.
  - *Back-of-envelope* (treat with bar-(c) seriousness): the matching-engine handles ~1M orders/sec. A drain gap of even 50 ms drops ~50,000 orders. To *detect* a 50 ms gap the probe must keep a request in flight continuously — at a probe rate of 1000 req/sec (one every 1 ms), a 50 ms gap = ~50 consecutive failures, unmissable; at 10 req/sec (one every 100 ms) a 50 ms gap has a ~50% chance of falling entirely between two sends and being *invisible*. Cliff ratio: probe-period 1 ms vs 100 ms = 100× difference in detection probability for the same real outage. A `tokio::time::sleep`-paced loop has a ~1 ms floor on Linux, so the inter-send jitter itself is ~1 ms — fine at 1000 req/s, fatal if you naively try 100k req/s.
  - **Requirements** R1..R6 — write in `crates/ops-deploy/notes/107_verify_design.md`:
    - R1. Continuous coverage: the probe keeps ≥1 request in flight at all times during the deploy window — no sampling holes. Asserted by R6's gap metric.
    - R2. `DowntimeReport` distinguishes `refused` (connect failed) / `server_err` (5xx) / `timed_out` (no response within `req_timeout`) — never collapses them, because each maps to a different runbook fix.
    - R3. The deploy `trigger` fires at a *known* point in the probe stream so the report can attribute failures to the cutover vs ambient noise.
    - R4. `max_gap` = the longest wall-clock interval with zero successful responses. Pass criterion: `max_gap < req_timeout` AND `refused + server_err + timed_out == 0`.
    - R5. The harness itself adds zero false negatives: a deliberately-broken deploy (kill old instance, never start new) MUST produce a non-zero `refused` count (negative control — see Phase 2).
    - R6. v2 hook: the report includes `vsr_view_changes_during` and `mmap_cycle_rolls_during` (read from ops-monitoring counters before/after) and asserts both are 0 — a deploy that triggered a view-change or a cycle-roll is not zero-impact even if no request was dropped.

  #### Phase 3 — Make the tests pass, one failure at a time (~45 min)
  Ordered failure cards, newbie first.
  - **(NEWBIE) When `detects_a_60ms_drain_gap` reports `max_gap=0ms` and `refused=0`:**
    - Symptom: the 60 ms outage is invisible; the report says every request succeeded.
    - Why: the probe loop does `client.get(); sleep(100ms);` — the 60 ms dead window falls entirely inside one `sleep`, so no request was ever in flight during the outage. The sampling period (100 ms) is coarser than the event (60 ms).
    - Fix: drive the probe at `rate_per_sec` with a fixed-deadline schedule (`next_send += period`), period = 1 ms at 1000 req/s, so a request is always either in flight or about to be — coverage, not sampling. Compute `max_gap` from successful-response timestamps, not from send timestamps.
    - Cost avoided: detecting vs missing a 50 ms drain that drops ~50,000 orders on the matching-engine — the difference between a real uptime SLA and a fictional one.
    - Muscle: to *detect* an event of duration D, your probe period must be ≪ D, and you must measure gaps between *successes*, not attempts. Reapplies at: W108 chaos fault-detection probe, W109 runbook health-check interval sizing, M30 uptime-audit scrape interval.
  - **(SENIOR) When `classifies_failure_kinds_distinctly` reports `refused=N, server_err=0`:**
    - Symptom: 503 responses are counted as `refused`.
    - Why: the probe treats any `Result::Err` from the client as "refused", but a 503 is `Ok(response)` with a 5xx status — the error/status distinction was collapsed at the `match`.
    - Fix: match on `Ok(resp)` → branch on `resp.status().is_server_error()` → `server_err`; `Err(e)` → branch on `e.is_connect()` → `refused` else `timed_out`. Three buckets, three runbook actions.
    - Cost avoided: a runbook that can't tell "new instance never started" (rollback) from "new instance is up but erroring" (roll forward / fix config) — wrong remediation under outage pressure.
    - Muscle: in a verification harness, *failure taxonomy is the product* — collapsing failure kinds destroys the signal. Reapplies at: W108 chaos failure-classification, W109 runbook decision tree, W126 systems-design interview (failure-mode taxonomy questions).
  - **(SENIOR) When `real_blue_green_deploy_triggers_no_view_change` passes `refused==0` but fails `vsr_view_changes_during==1`:**
    - Symptom: zero requests dropped, but a VSR view-change fired during the restart.
    - Why: the W105 script restarts the leader without a clean stepdown, so killing it forces the cluster into an election — invisible to a request-counting probe, but it pauses the cluster for the election timeout.
    - Fix: read `vsr_view_changes_total` from ops-monitoring before/after the trigger and assert delta 0; on failure, the *script* needs `stepdown-if-leader` before restart (W105 R-clause). The harness's job is to *surface* it, which it now does.
    - Cost avoided: an election pause (hundreds of ms of cluster unavailability) that a naive probe rates "zero downtime".
    - Muscle: zero-downtime is multi-dimensional — dropped requests AND consensus stability AND no spurious resource events. Measure all the dimensions your bar-(c) crate cares about. Reapplies at: W108 chaos blast-radius assertions, M30 audit deploy-impact ledger.
  - **(EXPERT) When `negative_control_broken_deploy_is_caught` reports `refused=0` for a killed service:**
    - Symptom: the harness gives a clean bill of health to a deploy that permanently killed the service — the test that's supposed to *prove the harness can fail* doesn't fail.
    - Why: the probe swallowed connection errors (e.g. an inner `let _ = client.get();` or a retry-until-success wrapper that masks refusals), so a dead server still produces an all-green report.
    - Fix: every probe outcome MUST land in exactly one bucket; remove all retry/`unwrap_or_default` masking from the probe path. The negative control now fails the harness loudly when the harness is blind.
    - Cost avoided: shipping a verification tool that *cannot detect an outage* — worse than no tool, because it manufactures false confidence in the M30 uptime claim.
    - Muscle: a test that cannot fail tests nothing — every verification tool needs a negative control proving it catches the thing it claims to catch. Reapplies at: W108 chaos drill "did the fault actually inject?", W109 runbook dry-run validation, W121 flagship blog (claims must be falsifiable).

  #### Phase 1 — Problem, prediction, design (~30 min, no code yet)

    - P2: predict what that naive alert does on a 30-second blip of 100% errors (flaps? pages? correct?).

  - *Mental model*: a burn-rate alert measures how fast you're spending your error budget, over two time windows simultaneously — a short window to catch fast burns without flapping, a long window to catch slow burns before the budget is gone. It exists because a single fixed threshold is always either too twitchy or too sleepy.
  - *Contract*: `fn eval(&self, short: Window, long: Window) -> AlertState` returning `Ok | Warn | Page`, where the alert fires only when *both* the short-window and long-window burn rates exceed the threshold for that severity (the AND is the anti-flap mechanism).
  - *Back-of-envelope*: a 99.9% SLO over 30 days = 43.2 min of allowed downtime/month. A 14.4× burn rate over a 1-hour window consumes 2% of the monthly budget in that hour — page now. A 6× burn over 6 hours = 5% budget — page. A 1× burn = exactly on budget — no alert. The window lengths come straight from the SRE table; the math is "burn_rate × window / SLO_period = budget_fraction_consumed".
  - **Requirements** R1..R4 — write in `crates/ops-monitoring/notes/107_slo_design.md`:
    - R1. Two-window AND: `Page` requires short-window burn ≥ threshold AND long-window burn ≥ threshold (anti-flap).
    - R2. Fast burn caught quickly: a sustained 14.4× burn pages within the short window (≤ minutes), not hours.
    - R3. Slow burn caught eventually: a sustained low burn that will exhaust the budget pages before the budget is gone, via the long window.
    - R4. No flap on a transient blip shorter than the short window — the AND with the long window suppresses it.
  - **Design walk-through** D1..D3 (no peeking at the SRE source until Phase 3):
    - D1. Property table: single-threshold alert vs single-burn-rate alert vs multi-window multi-burn-rate (flap-prone? slow-burn-blind? complexity?). Pick from R1+R4.
    - D2. **Pre-mortem (load-bearing):** write the 4-line sequence where a single-threshold alert pages 40 times in an hour on a flapping dependency (alert fatigue → real page ignored). Show the two-window AND collapses it to 0 pages.
    - D3. **Anti-shortcut audit:** the obvious reach is `if error_rate > slo_target { page }` — wrong HERE because it pages on any blip above target regardless of budget burn rate, training operators to ignore the pager.
  - **Output**: `crates/ops-monitoring/notes/107_slo_design.md` with R1..R4, D1..D3, the alert-fatigue sequence.

  - **(NEWBIE) When `transient_blip_does_not_page` reports `Page`:**

    - Why: `eval` ORs the windows (or uses only the short window), so any short spike crosses the threshold.

  - **(SENIOR) When `slow_burn_pages_before_budget_exhausted` reports `Ok`:**
    - Symptom: a 6× burn over 2 days never pages until the budget is already spent.
    - Why: only a short fast-burn window was implemented; a 6× burn never crosses the high fast-burn threshold (which is tuned for 14.4×).
    - Fix: add the lower-multiple / longer-window tier from the SRE table (e.g. 6× over 6h → Page; 3× over 24h → Warn).
    - Muscle: one window catches one burn speed; an SLO needs a *ladder* of (rate, window) pairs. Reapplies at: W109 multi-tier alert policy, W113 SLO design for live trading.
  - **(EXPERT) When `negative_control_fast_burn_pages_within_minutes` reports `Ok`:**
