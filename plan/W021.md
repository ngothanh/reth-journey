**Monday — `eth-rlp` extension: trie-friendly node encoding**

- [ ] Lookup-only (skip unless Phase-1 design gets stuck): yellow paper §C Hex-Prefix table + alloy-trie `nodes` rustdoc — for the 4-row HP table and the 17-slot branch layout only. (~20 min)

- [ ] **Build**: `crates/eth-rlp/src/trie.rs` — `encode_compact_path`, `encode_leaf_node`, `encode_extension_node`, `encode_branch_node`, and the `ChildRef` enum. (~total 165 min across 3 phases)
  - 🔧 **Why this matters**: MPT nodes have three shapes (branch, extension, leaf), each with its own RLP
    serialization including a 1-byte Hex-Prefix (HP / "compact path") byte that intermixes structural info
    (leaf vs extension; even- vs odd-length nibble path) into the first byte. Mirrors `alloy_trie::nodes`.
    First-attempt impls reliably fail ≥1 test below — the four traps are: (1) the odd-nibble case stuffs the
    leading nibble into the prefix byte while the even case pads with `0x00` (the parity asymmetry), (2) the
    inline-vs-hash threshold is **strict** `< 32`, (3) the branch list is **17** slots not 16, (4) the
    single-nibble round-trip where the prefix byte IS the whole payload. The debug session walking these IS the
    lesson. Centralizing here means eth-trie, storage-trie (W23-24, W31-32) and mini-db (W95) all route through
    one HP table — a parity bug fixed once is fixed everywhere. Downstream: W22 eth-stage, W31-32 persistent
    MPT + proof verifier, W66 tempo-tx-envelope.

  #### Phase 1 — Problem, prediction, design (~45 min, no code yet)

  - 🎯 **Pre-prediction prompt (do this BEFORE reading Phase 2)** — write sealed answers in
    `crates/eth-rlp/notes/21_trie_rlp_prediction.md`. Compare to reality after tests run:
    - P1. The exact import line you'd reach for the RLP list header (predict it before checking):
      `use alloy_rlp::Header;` — yes/no, and what method emits the list prefix?
    - P2. Predict the encoded bytes for `encode_compact_path([3, 7, 5], is_leaf=false)` — write the 2 bytes.
    - P3. Predict the byte length of `encode_branch_node([all None; 16], None)` decoded element COUNT.
    - P4. Predict: for a child whose full RLP encoding is exactly 32 bytes, does the branch inline it or hash it?

      miss is `compact_path_odd_*` and `round_trip` at length 1 — did you predict those?
  - *Mental model*: HP encoding is a 4-bit-packing scheme that smuggles two booleans (is_leaf, is_odd) into the
    top nibble of byte 0, then packs the nibble path two-per-byte. It exists because RLP has no native nibble
    type, and the trie must distinguish leaf from extension nodes that are otherwise structurally identical.
  - *Contract* (signature-level — NEVER the body):
    ```rust
    pub enum ChildRef { Inline(Bytes), Hash(B256) }   // Inline iff child RLP len < 32, strictly
    pub fn encode_compact_path(nibbles: &[u8], is_leaf: bool, out: &mut dyn BufMut);
    pub fn encode_leaf_node(path: &[u8], value: &[u8], out: &mut dyn BufMut);
    pub fn encode_extension_node(path: &[u8], child: &ChildRef, out: &mut dyn BufMut);
    pub fn encode_branch_node(children: &[Option<ChildRef>; 16], value: Option<&[u8]>, out: &mut dyn BufMut);
    ```
  - *Back-of-envelope* (bar (b) — informational, not gated): the HP encode is pure byte-shuffling, ~one pass
    over `nibbles.len()/2` bytes, no alloc if `out` is pre-sized. The load-bearing cost is NOT speed — it is
    **consensus byte-identity**: a single wrong prefix byte produces a well-formed RLP list whose keccak hash
    diverges from mainnet, and the node is silently rejected by every other client. Cliff: correct vs off-by-one
    parity = byte-identical vs total state-root divergence (a binary correctness cliff, not a perf gradient).
  - **Requirements** R1..R9 — write in `crates/eth-rlp/notes/21_trie_rlp_design.md`:
    - R1. `encode_compact_path(nibbles, is_leaf, out)` writes the HP-prefix byte then packed nibble pairs.
    - R2. HP flag nibble (yellow paper §C): `0x0` = extension/even, `0x1` = extension/odd, `0x2` = leaf/even,
      `0x3` = leaf/odd. The flag occupies the HIGH nibble of byte 0.
    - R3. `encode_leaf_node(path, value, out)` writes a 2-element RLP list `[compact_path, value]`.
    - R4. `encode_extension_node(path, child, out)` writes a 2-element RLP list `[compact_path, child_ref]`.
    - R5. `encode_branch_node(children, value, out)` writes a **17-element** RLP list: 16 child slots + 1 value
      slot. Absent children/value encode as `0x80` (RLP empty string).
    - R6. `ChildRef::Inline` iff the child's full RLP encoding is **strictly** `< 32` bytes; else `::Hash` (keccak).
    - R7. Nibbles within a byte: MSB-first. `(byte >> 4, byte & 0x0F)` is the pair, in that order.
    - R8. Round-trip: `encode(decode(bytes)) == bytes` for every node shape at nibble lengths 0, 1, 2, 31, 32, 33, 64.
    - R9. Pass `ethereum/tests::TrieTests::{trietest, trieanyorder}` byte-identical.
  - **Design walk-through** D1..D6 — answer in the design doc; do NOT open alloy-trie source until Phase 3:
    - D1. Write the HP-prefix-byte formula from `(is_leaf, odd)`. What is byte 0 for `is_leaf=true, [3,7,5]` (odd)?
    - D2. The even case appends `0x00` padding into the low nibble of byte 0 (prefix is the whole first byte); the
      odd case stuffs the FIRST path nibble into the low nibble of byte 0. Why asymmetric? (Hint: nibbles are 4
      bits; an odd count leaves one stray nibble that has nowhere to pair, so it rides in the prefix byte.)
    - D3. Why strictly `< 32` not `<= 32`? (Hint: 32 = keccak output size; at exactly 32 both inline and hash
      occupy 32 bytes — ambiguous, so spec forces hash to break the tie.)
    - **D4. Pre-mortem (load-bearing)** — write the EXACT bad trace for the even/odd off-by-one that yields
      INTERMITTENT state-root divergence:
      ```
      path [3,7,5] (odd, len 3), is_leaf=true
      naive: push prefix 0x30, then pack pairs starting at nibble[0]:
             0x30, (3<<4|7)=0x37, (5<<4|0)=0x50   → 3 bytes [0x30, 0x37, 0x50]
      correct: stuff nibble[0] into prefix low nibble: 0x30|0x3 = 0x33,
             then pack from nibble[1]: (7<<4|5)=0x75 → 2 bytes [0x33, 0x75]
      blocks with EVEN-length paths still hash correctly → "works on my testnet"
      blocks with ODD-length paths diverge → fails on mainnet at random heights
      ```
      Mainnet has both parities in ~equal proportion, so the bug looks "intermittent" — that's why it survives a
      naive test suite and detonates in production.
    - **D5. Anti-shortcut audit** — name the obvious reach and why it's wrong HERE:
      - "Hand-roll the RLP list header (`if len<=55 {0xc0+len} else {...}`)" → wrong: the near-55-byte boundary
        and the long-form length-of-length prefix are exactly where hand-rolls drift from alloy. Use `Header::encode`.
      - "Compare `child.len() <= 32`" → wrong: strict `<` (D3). The `<=` reach passes 31-byte tests, fails at 32.
      - "Treat the odd leading nibble as a normal data nibble" → wrong: it must ride in the prefix byte (D2).
    - D6. RLP list header: use `alloy_rlp::Header { list: true, payload_length }.encode(out)`. What breaks if you
      hand-roll it near the 55-byte boundary? (Answer in doc.)
  - **Output**: `crates/eth-rlp/notes/21_trie_rlp_design.md` with R1–R9, D1–D6, the 4-row HP table, and the
    bad-interleaving sketch from D4.

  #### Phase 3 — Make the tests pass, one failure at a time (~75 min)

  Ordered newbie→expert — the ladder you actually walk.

  - **(NEWBIE) When `branch_node_is_17_element_list` decodes to 16 elements:**
    - Symptom: branch RLP decodes as a 16-element list; expected 17.
    - Why: encoder omitted the 17th "value at this branch" slot (almost always empty in modern Ethereum, but
      spec-required by yellow paper §C).
    - Fix: always emit the 17th slot, defaulting to `0x80` (RLP empty) when no value present.
    - Muscle: every branch node has 17 RLP slots even when the 17th is always empty in practice; omitting it is a
      non-canonical encoding other clients reject. Reapplies at: W23-24 storage-trie node codec, W31 persistent
      MPT, W32 proof verification.
  - **(SENIOR) When `compact_path_odd_extension` produces `[0x10, 0x37, 0x50]` (3 bytes, wrong):**
    - Symptom: encoder emits prefix `0x10` then packs from nibble[0], giving 3 bytes; expected 2 bytes `[0x13, 0x75]`.
    - Why: the first nibble (`3`) must be stuffed into the LOW 4 bits of the prefix byte, not treated as a normal
      data nibble. Prefix becomes `(flag<<4) | nibbles[0]` = `0x10 | 0x03 = 0x13`.
    - Fix: `if odd { out.push((flag << 4) | nibbles[0]); pack(&nibbles[1..], out) } else { out.push(flag << 4); pack(nibbles, out) }`
      — note the slice from index 1 in the odd branch.
    - Cost avoided: silent INTERMITTENT state-root divergence (passes even-path testnet, fails odd-path mainnet) —
      the single hardest trie bug to diagnose because it correlates with no obvious input property.
    - Muscle: HP's odd case stuffs the leading nibble into the prefix byte; even case pads `0x00`. The asymmetry
      is THE bug to defend against. Reapplies at: W31 persistent MPT key encoding, W32 proof verifier path
      assembly, W95 mini-db trie index.
  - **(SENIOR) When `round_trip_every_nibble_length` fails on length 1 (single nibble):**
    - Symptom: `[5]` → encode `[0x35]` (correct prefix) → decode → `[]` (empty); round-trip is `[5]→[0x35]→[]`.
    - Why: decoder reads the prefix, sees odd-leaf, then expects further data bytes — finds none, returns empty.
      The case "the low nibble of the prefix IS the only nibble" is unhandled.
    - Fix: in the decoder, after extracting prefix flag, if `odd && no_remaining_bytes` then the single nibble is
      `prefix & 0x0F` — return `[prefix & 0x0F]`. Add explicit tests at lengths 1, 3, 5, 63.
    - Muscle: HP decode must handle the single-nibble case where the prefix byte is the entire payload. Reapplies
      at: W31 persistent MPT key decode, W32 proof verifier.
  - **(EXPERT) When `embedded_child_exactly_32_bytes_hashed` reports a 32-byte raw inline instead of a hash:**
    - Symptom: branch at the boundary (child encoded len = 32) contains the child's raw bytes; expected the keccak hash.
    - Why: encoder used `<=` instead of `<`. The two interpretations agree for ALL sizes except exactly 32.
    - Fix: `if child.encoded_len() < 32 { ChildRef::Inline(bytes) } else { ChildRef::Hash(keccak256(bytes)) }`.
      Keep tests at both 31 and 32 to nail the boundary.
    - Cost avoided: consensus break at exactly the 32-byte child case — rare in random data, common in real tries
      (many node encodings cluster near 32 bytes), so it survives unit tests and fails on mainnet replay.
    - Muscle: the inline-vs-hash threshold is strict-`<`-32; off-by-one breaks consensus only at the boundary.
      Reapplies at: W23-24 storage-trie embedding, W31 persistent MPT, W32 proof verification.
  - **(EXPERT) When `fixture_loader_actually_loads_nodes` fails (zero cases / all-zero roots):**
    - Symptom: loader returns `len()==0` or every `expected_root == B256::ZERO`.
    - Why: fixture path resolution or JSON field name wrong; the harness silently parsed nothing, so the "real"
      test passes vacuously.
    - Fix: resolve the `ethereum/tests` submodule path at compile time (`env!("CARGO_MANIFEST_DIR")` + relative),
      assert the parsed case count and a non-zero root.
    - Muscle: a fixture/bench/loom test that can pass on empty input proves nothing — always pair it with a
      test-the-test negative control. Reapplies at: every fixture-driven suite (W32 proof fixtures, W42 block
      fixtures), and every criterion/loom harness in bar (c) weeks (W26 wal, W58 matching-engine).

  - **(SENIOR) When `decoder_missing_trailing_yields_none` panics with "expected 20 items, got 15":**
    - Symptom: decoder treats trailing fields as mandatory; a 15-element frontier list fails against a 20-field struct.
    - Why: codegen emits `assert!(list.len() == total_field_count)` instead of a range check.

      `let observed = list.len().checked_sub(mandatory_count).filter(|&n| n <= trailing_count).ok_or(TooManyItems)?;`
      read `mandatory_count` items normally, read `observed` trailings, default the remaining `trailing_count - observed`.
    - Muscle: a trailing-aware decoder accepts a length RANGE (mandatory ≤ len ≤ total), not an exact length.
      Reapplies at: W42 block-import header codec, W67 raft AppendEntries with versioned fields, W64 RPC types.
  - **(SENIOR) When `encoder_rejects_none_before_some` does NOT panic and produces ambiguous bytes:**
    - Symptom: encoder emits `base_fee` slot as `0x80` (empty) and `withdrawals_root` as a real B256; decoder
      reads back BOTH as `None` (the empty slot looks like "missing from end"), silently corrupting data.
    - Why: encoder walks fields linearly with no "no holes" check.
    - Fix: before emitting, scan trailings in declaration order; if a `Some`/non-default follows a `None`/default,
      `panic!("#[rlp(trailing)] field {} is Some but preceding {} is None — unrepresentable on wire", a, b)`.
    - Muscle: positional optional wire formats require a "no holes" invariant; the encoder MUST panic on a hole,
      never silently corrupt. Reapplies at: W42 block-import header encoding, W64 RPC response building.
  - **(EXPERT) When `compile_fail_trailing_on_non_option_no_default` does NOT fail to compile:**
    - Symptom: `#[rlp(trailing)] foo: NonDefaultType` compiles; the load-bearing compile-time guard is missing.
    - Why: the derive emits no trait-bound assertion for trailing fields.
    - Fix: for each trailing field, codegen
      `const _: fn() = || { fn assert_impl<T: TrailingCompatible>() {} assert_impl::<#field_type>(); };`
      where `TrailingCompatible` has blanket impls for `Option<T>` and `T: Default`.
    - Muscle: derive macros enforce field-level bounds at the call site via codegen'd `const _: fn() = ...`
      helpers; absent helper = aspirational bound. Reapplies at: every derive needing field-level bounds (W5
      RlpEncodable, W4 SimpleEncode).

  - 🔧 **Why this matters**: a plain min/avg/max throws away the tail, and the tail IS the product for a maker
    (one slow quote = one missed fill = adverse selection). HdrHistogram solves "record billions of samples,
    query any quantile, lose ≤ X% precision, allocate nothing on record" via a **bucket / sub-bucket** layout:
    the value range is split into power-of-two **buckets** (the exponent), each subdivided into `2^k`
    **sub-buckets** (the mantissa). This is bar (c): the record path runs *inside* the hot path it measures, so
    it must be zero-alloc and static-mem — every later bar-(c) bench (W26 wal, W58 matching, W99 risk-engine
    p99.99, W113 perp-dex-core) records into this. First-attempt impls reliably fail ≥1 test below — the four
    traps are: (1) the bucket index uses `leading_zeros` and the **first** bucket is special (no implicit
    leading bit), (2) `value_at_quantile` must report the bucket's UPPER bound (lossy-high), not its midpoint,
    or downstream p99 is optimistic, (3) the record path silently `Vec::push`-grows (allocation inside the hot
    path = measuring your own malloc), (4) `merge` across per-shard histograms must be bucket-aligned (same
    config) or counts land in the wrong bucket. The debug session IS the lesson.

  - *Mental model*: an HdrHistogram is a **lossy-bucketed counter array** where bucket layout is logarithmic
    (constant *relative* precision across 9 orders of magnitude) and sub-buckets are linear within a bucket. The
    index function is `(exponent, mantissa)` derived from the value's bit pattern — the same trick a float uses.
    Record = increment one counter; query = walk buckets accumulating counts until the target quantile.
  - *Contract* (signature-level — NEVER the body):
    ```rust
    pub struct LatencyHistogram { counts: Box<[u64]>, cfg: HistConfig, total: u64, min: u64, max: u64 }
    pub struct HistConfig { lowest: u64, highest: u64, sig_figs: u8 }  // e.g. {1, 60_000_000_000, 3}
    impl LatencyHistogram {
        pub fn new(cfg: HistConfig) -> Self;                 // SOLE allocation point (counts array)
        pub fn record(&mut self, value: u64);                // zero-alloc; increments one bucket
        pub fn value_at_quantile(&self, q: f64) -> u64;      // returns bucket UPPER bound (lossy-high)
        pub fn merge(&mut self, other: &LatencyHistogram);   // requires identical HistConfig
        pub fn total_count(&self) -> u64;
    }
    ```
  - *Back-of-envelope* (bar (c) — this IS the gated budget): record = compute bucket index (a `leading_zeros` +
    a shift + a mask, ~3-5 cycles) + one array increment (~one cache line, ~5ns warm) = **single-digit
    nanoseconds, zero allocations, zero locks**. A 3-sig-fig histogram over 1ns..60s is ~`(buckets ~36) ×
    (sub-buckets 2048) × 8B` ≈ **~590 KB** static — paid once at `new`, fits L2/L3, never grows. Cliff: a
    `Vec::push` on record turns a 5ns record into a 50-200ns amortized record with periodic ms-scale realloc
    stalls — and those stalls land IN the measured distribution, fabricating a tail that isn't the system's.
  - **Requirements** R1..R8 — write in `crates/latency-lab/notes/21_hist_design.md`:
    - R1. `new(cfg)` is the **sole** allocation point; `counts` is a `Box<[u64]>` sized at construction, never resized.
    - R2. `record(value)` allocates **nothing**, takes **no lock**, and increments exactly one counter.
    - R3. Bucket index: bucket = position of the highest set bit above the sub-bucket window; sub-bucket = the
      next `sig_figs`-derived bits. The FIRST bucket is special (values below `2^sub_bucket_bits` have no implicit
      leading 1) — handle it explicitly.
    - R4. `value_at_quantile(q)` returns the **upper bound** of the bucket containing the q-th sample
      (lossy-HIGH) — never the midpoint or lower bound; downstream p99 must not be optimistic.
    - R5. Relative precision: for any recorded `v`, `|reported - v| / v <= 10^-sig_figs` (3 sig figs ⇒ ≤ 0.1%).
    - R6. `record(0)` and `record(cfg.highest + 1)` (overflow) are handled — clamp to highest bucket, never panic.
    - R7. `merge(other)` requires byte-identical `HistConfig`; counts add bucket-for-bucket; panic on config mismatch.
    - R8. `min`/`max`/`total_count` tracked exactly (these are NOT bucketed — they're the un-lossy summary).

  the coordinated-omission correction layered on `LatencyHistogram`. (~total 130 min across 3 phases)
  - 🔧 **Why this matters**: **coordinated omission** is the single most common way latency benchmarks lie. A
    load generator (or an in-process sampler) issues requests on a schedule; when the system stalls, the sampler
    *also* stalls — so the long requests that SHOULD have been issued during the stall are silently never
    recorded. The histogram then shows a beautiful p99 that omits exactly the worst behaviour. For a maker this
    is fatal: the stall is precisely the window where you're being adversely selected, and your benchmark erased
    it. `record_correct(v, expected_interval)` back-fills the omitted samples: if `v` exceeds the expected
    inter-arrival interval, it synthesizes the requests that would have queued behind it (`v - interval`,
    `v - 2*interval`, ...). This is bar (c) — it sits on the same hot-path record discipline as `hist.rs`. The
    three traps: (1) using measured *response* time instead of intended *service* time as the schedule, (2)
    off-by-one in the back-fill loop (double-counting the original sample), (3) treating CO correction as
    optional (it's the default for any scheduled/throughput bench; only free-running event timing is CO-immune).

  - *Mental model*: coordinated omission = "the measurement coordinates with the system's stalls, so it omits the

    queue that built up during a stall — turning one 100ms sample into the ~100k samples a real client backlog

  - *Contract* (signature-level — NEVER the body):
    ```rust
    impl LatencyHistogram {
        // record `value`, then if value > expected_interval, back-fill synthetic samples for the
        // requests that would have queued behind the stall: value-interval, value-2*interval, ...
        pub fn record_correct(&mut self, value: u64, expected_interval: u64);
    }
    ```
  - *Back-of-envelope* (bar (c) — gated): the common case `value <= expected_interval` is a single `record`
    (one branch + the ns-scale record from `hist.rs`). The rare stall case back-fills `value / interval`
    synthetic samples — bounded, zero-alloc (each is a plain `record`), and rare by construction (it only fires
    when the system actually stalled). Cliff: WITHOUT correction, one 100ms stall in 10k 1µs ops reports
    p99 ≈ 1µs (the stall is one sample, below the 99th percentile of 10001 samples). WITH correction it reports
    p99 in the tens-of-ms — a ~10000× difference on the exact number you'd quote in a latency report.
  - **Requirements** R1..R6 — write in `crates/latency-lab/notes/21_co_design.md`:
    - R1. `record_correct(v, interval)` always records `v` once (the real sample).
    - R2. If `v > interval`, back-fill synthetic samples at `v - interval, v - 2*interval, ...` down to (but not
      including) values `<= interval` — these are the omitted queued requests.
    - R3. If `v <= interval`, `record_correct` is exactly one `record` (no back-fill).
    - R4. The back-fill loop is **zero-alloc** (each synthetic sample is a `record` into the pre-sized array).
    - R5. The back-fill count is exactly `floor((v - 1) / interval)` synthetic samples (excludes the original,
      excludes values ≤ interval) — verified by a counting test (off-by-one is the bug).
    - R6. CO correction is documented as the **default** for scheduled/throughput benches; free-running
      event-pair timing (W22 rdtsc on a feed not under our schedule) explicitly opts OUT and uses plain `record`.
