  - 🔧 **Why this matters**: 2PC is the canonical atomic commit protocol across distributed participants. Get the failure semantics wrong and you have "in-doubt" transactions hanging participant resources forever — OR worse, asymmetric commit (some Committed, some Aborted on same tx_id), violating atomicity. Downstream: `ledger-deterministic` distributed mode uses 2PC for cross-shard transfers (W83+); consensus-vsr provides the durable log so coordinator failover is automatic; tier-A IC interview load-bearing — "walk me through 2PC failure modes" is a canonical question.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: a multi-shard transaction (e.g., transfer between accounts on different shards) must commit ATOMICALLY — all shards commit, or all abort. There is no atomic primitive that spans shards natively; 2PC builds one out of two rounds (Prepare gathering yes/no votes; Commit broadcasting the decision). Done wrong: in-doubt transactions (participants stuck Prepared forever), asymmetric commits (split decisions), or fsync-bound throughput collapse.

  - **Requirements** — write in `crates/txn/notes/72_2pc_design.md`:
    - R1. `TwoPhaseCoordinator` and `TwoPhaseParticipant` state machines with explicit phases: Coord {Init, Preparing, Committing, Aborting, Done}, Participant {Idle, Prepared, Committed, Aborted}.
    - R2. **Coordinator decision durability**: the Commit/Abort decision is logged to WAL BEFORE sent. Coordinator crash recovery reads the WAL and replays — never re-decides.
    - R3. **Participant Prepared durability**: a participant that voted Yes CANNOT unilaterally abort. The Prepared vote is fsync'd before the response is sent.
    - R4. **Idempotent message processing**: Commit/Abort can arrive multiple times; participant idempotently transitions and acks.
    - R5. **Timeout-driven abort**: coordinator timeout from Init/Preparing → Abort allowed. After logging Commit → no Abort, only retry-broadcast.
    - R6. **State-machine pool**: `CoordPool { slots: [TwoPhaseCoordinator; 1024], free: SmallVec<u16> }` and symmetric `ParticipantPool`. begin() acquires from pool (~10 ns), finalize() returns to pool. Zero alloc on hot path.
    - R7. **Group-commit fsync**: minimal fsync points = (a) coordinator's Commit/Abort decision + (b) participant's Prepared vote. Both batched via W26 GroupCommit. Fsync rate ≤ ~20/sec at 10k tx/sec target.
    - R8. **Throughput target**: ≥ 10k cross-shard tx/sec at p99 ≤ 10 ms.
    - R9. **No asymmetric commit**: 10k random schedules property test produces no run where same tx_id is both Committed and Aborted across participants.
    - R10. **In-flight cap**: max in-flight tx = pool size = 10k tx/sec × 100 ms typical commit time × safety factor 1.0 = ~1024.

  - **Design walk-through** — answer each in your design doc; no peeking at InnoDB XA or CockroachDB source until Phase 3:
    - D1. Sketch `Msg` enum (Prepare, PrepareOk, PrepareNo, Commit, Abort, Ack). Why does PrepareNo carry a reason?
    - D2. Coordinator's phase progression: write the 6 numbered steps from `begin(tx_id, parts)` to `Done`. Where are the durability barriers?
    - D3. Participant's phase progression: 5 numbered steps from `Idle` to `Committed` (or `Aborted`). Where is the durability barrier?
    - D4. **In-doubt resolution**: participant times out waiting for Commit/Abort after Prepared. What does it do? (Hint: CANNOT abort unilaterally; must wait + poll coordinator. Cooperative termination by querying peers is optional.)
    - D5. **Heuristic decision**: a human operator wants to "resolve" an in-doubt tx by guessing. Why is this dangerous? What API do we expose to prevent it?
    - D6. Pool sizing: 10k tx/sec × ~100 ms commit time = 1000 in-flight. Add safety factor; round up to power of 2. What's the pool size? What if it's exhausted?
    - D7. Group-commit boundary: when does the coordinator fsync? When does the participant fsync? Compute fsync rate at 10k tx/sec without batching, then with 1024-batch.
    - D8. **Pre-mortem #1 (alloc per tx)**: 5-step trace where `Box<TwoPhaseCoordinator>` per tx burns ~500 µs/sec of allocator at 10k tx/sec. Compute the impact.
    - D9. **Pre-mortem #2 (fsync per Prepare-ack)**: 5-step trace where coordinator fsyncs each incoming Prepare ack; at 10k tx/sec × 3 participants = 30k fsyncs/sec, exceeds NVMe capacity. Throughput collapses to ~500 tx/sec.
    - D10. **Pre-mortem #3 (asymmetric commit)**: 7-step trace where coordinator crashes between sending Commit to A and sending to B, restarts, "decides" Abort instead. A committed; B aborted. Identify the rule (R2) that prevents this.

  #### Phase 3 — Make the tests pass, one failure at a time (~85 min)

  - **When `dhat_zero_alloc_steady_state` reports ~10k allocs/sec and `bench_2pc_p99_under_10ms` shows p99.9 ≈ 100 µs spikes:**
    - Symptom: heaptrack flags ~10k mallocs/sec attributable to `Box::new(TwoPhaseCoordinator { ... })`. `perf record` shows `<jemalloc>::alloc` at 5-10% CPU during steady-state 2PC; tail latency p99.9 spikes during allocator's internal compaction.
    - Why: naïve `pub fn begin(tx_id, parts) -> Box<TwoPhaseCoordinator>` allocates a fresh coordinator (~120 B + heap metadata) per transaction. At 10k tx/sec that's 10k mallocs/sec × ~50 ns = ~500 µs/sec pure allocator work + dealloc on tx-end. Same shape for participant state.
    - Fix: per-shard pre-allocated state-machine pool: `CoordPool { slots: [TwoPhaseCoordinator; 1024], free: SmallVec<u16> }`. `begin()` pops a free slot (~10 ns), `finalize()` pushes back. Bound = pool size (1024 ≈ throughput × commit-time × safety). Participant pool symmetric. Memory NUMA-local (inherits W65 shard fix). Zero allocations in steady state.
    - Cost avoided: ~500 µs/sec allocator overhead → 0; eliminates p99.9 alloc-related tail; bounds memory at pool size × ~200 B = ~200 KiB per shard (predictable, fits L2).
    - Muscle: any per-event state structure on a high-throughput hot path lives in a pre-allocated pool, not on the heap per event. Pool size = max in-flight = throughput × latency × safety factor. Reapplies at: W74 matching-engine `MatchCommand` reuse, W74 VSR Prepare message pool, W83+ ledger Transfer pre-sized pool (TigerBeetle exact pattern), W92 ledger v1.0 static-mem invariant.

  - **When `bench_2pc_10k_tx_per_sec` reports throughput saturating at ~500 tx/sec and `iostat -x 1` shows WAL device at 100% utilization with low IOPS:**
    - Symptom: throughput plateaus far below target. Latency p99 is dominated by disk wait.
    - Why: naïve per-Prepare-ack fsync at coordinator. Each Prepare ack received → coordinator logs ack state → fsync. At 10k tx/sec × 3 participants × 1 ack each = 30k fsyncs/sec. NVMe fsync ≈ 50-1000 µs → max ~1k/sec single-channel. The whole pipeline serializes behind disk.
    - Fix: only fsync at TWO points: (a) coordinator's Commit/Abort DECISION (once per tx, after gathering quorum acks — batched via W26 GroupCommit); (b) participant's Prepared vote (once per tx-participant — also batched). Intermediate ack-tracking is in-memory; durability of those acks is reconstructible from participants' Prepared votes after coordinator restart. Drops fsync count from ~30k/sec to ~2 per tx × 10k = 20k fsync calls/sec, batched at 1024-batch ≈ 20 actual fsyncs/sec on the WAL. Well within NVMe budget.
    - Cost avoided: ~99% reduction in fsync count; ~10 ms/tx commit latency saved; throughput unblocked from ~500 to ~10k tx/sec.
    - Muscle: in any multi-message protocol, identify the MINIMAL set of durable decision points (typically coordinator's commit decision + each participant's prepare-vote); everything else is in-memory reconstructible. Pair with group-commit. Reapplies at: W67 raft AppendEntries quorum, W74 matching-engine raft commit, W83+ ledger VSR PrepareOk batching, W92 ledger v1.0 io_uring submission ring.

  - **When `coordinator_crash_after_decision_log_recovers` shows the recovered coordinator sending Abort while the WAL says Commit:**
    - Symptom: WAL has `Decision::Commit`; restart code re-runs the "decide" logic and chooses Abort (because participant timeouts have fired since); coordinator sends Abort. A committed; B aborted. Atomicity violated.
    - Why: recovery re-executed decision logic instead of replaying the logged decision.
    - Fix: recovery code path is "READ THE WAL DECISION; SEND IT". Never re-decide. The WAL is the single source of truth post-crash. Add a debug assert in the recovery path: "current state at recovery must MATCH WAL-logged decision; if mismatch, panic — invariant violated".
    - Muscle: durable decisions are write-once authority — recovery is "load then act", not "re-evaluate". Reapplies at: W74 raft state-machine recovery, W83+ ledger checkpoint recovery, W92 VSR view-change recovery.

  - **When `in_doubt_participant_waits_for_coordinator` shows participant aborting unilaterally:**
    - Symptom: participant voted Yes, no Commit/Abort arrives within timeout, participant decides "I'll abort to free my resources". Later, coordinator recovery sends Commit. Participant now in Committed AND has already aborted ledger state. Asymmetric commit on the local shard.
    - Why: participant has a unilateral-abort timeout in its state machine.
    - Fix: remove the unilateral abort. After voting Yes, a participant stays in Prepared FOREVER until the coordinator (or its recovery peer) tells it what to do. The participant MAY query peers (cooperative termination) — if any peer has Aborted on this tx_id, safe to abort. But the participant cannot decide alone.
    - Muscle: in 2PC, voting Yes is a binding commitment — only the coordinator (or its successor) resolves; no participant timeout. Reapplies at: every distributed atomic commit (W83+, W92).

  - **When `commit_idempotent_multiple_deliveries` shows the participant double-applies the transaction:**
    - Symptom: 5 deliveries of Commit cause the participant to apply the transaction 5 times — ledger debits 5× the amount.
    - Why: the participant's `handle_commit` mutates state unconditionally; doesn't check current phase.
    - Fix: idempotency table. `handle_commit(tx_id)` checks current `phase`: if `Prepared` → apply, transition to `Committed`, ack; if `Committed` → just ack (no re-apply). Same for `Aborted`.
    - Muscle: every message handler in a protocol with unreliable transport is idempotent by phase check — repeat messages MUST be safe. Reapplies at: W67 raft AppendEntries idempotency, W74 matching-engine raft, W92 VSR Prepare idempotency.

  - **When `pool_exhaustion_returns_error` shows panic instead of clean Err:**
    - Symptom: at pool saturation, the 1025th `begin()` panics with "no free slots".
    - Why: pool was unwrapped without handling exhaustion.
    - Fix: `begin() -> Result<TxHandle, PoolExhausted>`. Caller backs off (load shedding at the boundary) or queues at a higher layer. The pool's bound IS the back-pressure signal.
    - Muscle: bounded resources surface back-pressure via Result, never panic. Reapplies at: every pool/queue in this project.

  - **5-year failure mode** (write in `notes/72_2pc_followup.md` after green): when v2.0 ships pipelined / parallel commits (CockroachDB's STAGING txn record), 2PC's serial decision pattern becomes a bottleneck. State the migration: introduce a STAGING phase where the coordinator pre-stages a tentative decision before gathering Prepares; participants can speculatively apply with rollback. Trigger: throughput requirement > 10k tx/sec at p99 < 5 ms.
