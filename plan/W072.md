  - *Mental model*: 2PC turns N independent shard-local atomic commits into ONE distributed atomic commit by adding a voting round. Phase 1 (Prepare) gathers unanimous yes/no votes; Phase 2 (Commit/Abort) broadcasts the single decision. The decision point — the coordinator durably logging Commit/Abort — is the instant atomicity becomes irrevocable. Everything before it can abort; nothing after it can.

  - *Contract* (signatures only — never the body):
    ```rust
    pub struct TxId(u64);
    pub enum Vote { Yes, No { reason: AbortReason } }
    pub enum Decision { Commit, Abort }
    pub enum Msg { Prepare{tx: TxId}, PrepareOk{tx: TxId}, PrepareNo{tx: TxId, reason: AbortReason},
                   Commit{tx: TxId}, Abort{tx: TxId}, Ack{tx: TxId} }
    pub enum CoordPhase { Init, Preparing, Committing, Aborting, Done }
    pub enum PartPhase  { Idle, Prepared, Committed, Aborted }

    impl CoordPool {
        pub fn begin(&mut self, tx: TxId, parts: &[ParticipantId]) -> Result<TxHandle, PoolExhausted>;
        pub fn on_msg(&mut self, h: TxHandle, m: Msg, wal: &mut Wal) -> CoordPhase; // drives the SM
        pub fn finalize(&mut self, h: TxHandle); // returns slot to pool
    }
    impl ParticipantPool {
        pub fn on_msg(&mut self, tx: TxId, m: Msg, wal: &mut Wal) -> (PartPhase, Option<Msg>);
        pub fn recover(&mut self, wal: &Wal); // replay Prepared votes — never re-vote
    }
    ```

  - *Back-of-envelope* (Jeff-Dean numbers; bar (c) cliff ratios):
    - Per-tx coordinator state ≈ 120 B. `Box::new` per tx = malloc ~50 ns + free ~50 ns = **100 ns/tx alloc tax**; at 10k tx/sec = **1 ms/sec of pure allocator CPU + p99.9 tail from compaction**. Pooled slot pop/push ≈ **10 ns** (L1-resident `SmallVec` index). Cliff: 100 ns alloc vs 10 ns pool = **10× per tx, plus the unbounded-tail cliff**.
    - NVMe fsync ≈ **50-1000 µs** (call it ~300 µs single-channel) → ceiling ~1-3k fsync/sec/channel. Naive fsync-per-Prepare-ack = 10k tx × 3 parts = **30k fsync/sec wanted vs ~1k available = 30× over budget → pipeline serializes behind disk, throughput collapses to ~500 tx/sec**. Group-commit batching 1024 tx/fsync → ~20 fsync/sec actual = **1500× fewer**.
    - Decision durability: 1 mutex/WAL append ≈ 25 ns; 2 durable points/tx (coord decision + part vote) × 10k = 20k logical appends/sec, batched into ~20 fsync/sec. p99 commit latency budget = 10 ms ⇒ in-flight = 10k tx/sec × 0.1 s commit-time = **1000 ⇒ pool size 1024 (next pow2)**.

  - **Requirements** R1..R10 — write in `crates/txn/notes/72_2pc_design.md`:
    - R1. `TwoPhaseCoordinator` / `TwoPhaseParticipant` state machines with explicit phases (CoordPhase / PartPhase above).
    - R2. **Coordinator decision durability**: the Commit/Abort decision is WAL-logged BEFORE it is sent. Crash recovery READS and REPLAYS the logged decision — never re-decides.
    - R3. **Participant Prepared durability**: a participant that voted Yes CANNOT unilaterally abort; the Prepared vote is fsync'd before the PrepareOk is sent.
    - R4. **Idempotent message processing**: Commit/Abort can arrive multiple times; the handler transitions by phase-check and acks each delivery without re-applying.
    - R5. **Timeout-driven abort**: coordinator timeout from Init/Preparing → Abort is allowed. After logging Commit → only retry-broadcast, never Abort.
    - R6. **State-machine pool**: `CoordPool { slots: [TwoPhaseCoordinator; 1024], free: SmallVec<u16> }` + symmetric `ParticipantPool`. `begin()` ≈ 10 ns, `finalize()` returns slot. Zero alloc on the hot path.
    - R7. **Group-commit fsync**: minimal fsync points = (a) coordinator decision + (b) participant Prepared vote, both batched via W26 GroupCommit. ≤ ~50 fsync/sec at 10k tx/sec.
    - R8. **Throughput target**: ≥ 10k cross-shard tx/sec at p99 ≤ 10 ms.
    - R9. **No asymmetric commit**: a deterministic schedule explorer over crash points produces no run where one `tx_id` is both Committed and Aborted across participants.
    - R10. **In-flight cap**: max in-flight = pool size 1024; the 1025th `begin()` returns `Err(PoolExhausted)`, never allocates or panics.

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `commit_idempotent_multiple_deliveries` reports `applied == 5`:**
    - Symptom: 5 deliveries of `Commit` apply the transaction 5× — ledger debits 5× the amount.
    - Why: `handle_commit` mutates state unconditionally; no phase-check against unreliable/retried transport.
    - Fix: phase-gate the handler — `if phase == Prepared { apply(); phase = Committed } ack();` and on `Committed` just ack, no re-apply.
    - Cost avoided: a correctness defect, not a perf one — but it is silent money loss in the ledger consumer.
    - Muscle: every handler over unreliable transport is idempotent by phase-check; repeats MUST be safe. Reapplies at: W67 raft AppendEntries idempotency, W74 matching-engine raft apply, W92 VSR Prepare idempotency.

  - **(SENIOR) When `pool_exhaustion_returns_error` panics with "no free slots" instead of returning `Err`:**
    - Symptom: the 1025th `begin()` panics at pool saturation.
    - Why: the free-list pop was `.unwrap()`-ed; exhaustion treated as impossible.
    - Fix: `begin() -> Result<TxHandle, PoolExhausted>`; caller sheds load or queues at a higher layer. The bound IS the back-pressure signal.
    - Cost avoided: a node crash under load-spike vs. graceful shedding.
    - Muscle: bounded resources surface back-pressure via `Result`, never panic. Reapplies at: every pool/queue in this project — W74 MatchCommand pool, W83+ ledger Transfer pool.

  - **(SENIOR) When `in_doubt_participant_waits_for_coordinator` shows the participant aborting unilaterally:**
    - Symptom: participant voted Yes, no decision arrives within timeout, it aborts to free resources; later the coordinator's recovery sends Commit → participant in Committed AND already-aborted ledger state. Asymmetric commit on the local shard.
    - Why: the participant state machine has a unilateral-abort timeout in `Prepared`.
    - Fix: remove the unilateral abort. After voting Yes the participant stays in `Prepared` until the coordinator (or its successor) resolves; it MAY query peers (cooperative termination) but cannot decide alone.
    - Cost avoided: a correctness/atomicity defect across shards.
    - Muscle: voting Yes is a binding commitment — only the coordinator or its successor resolves; no participant timeout. Reapplies at: every distributed atomic commit — W83+ ledger, W92 VSR.

  - **(SENIOR) When `coordinator_crash_after_decision_log_recovers` shows recovery sending Abort while the WAL says Commit (and `no_asymmetric_commit_under_crash_schedules` fires):**
    - Symptom: WAL holds `Decision::Commit`; restart re-runs the decide logic, picks Abort (participant timeouts fired meanwhile), sends Abort. A committed, B aborted — atomicity violated.
    - Why: recovery re-EXECUTED the decision logic instead of REPLAYING the logged decision.
    - Fix: recovery path = "READ the WAL decision; SEND it"; never re-decide. Add a debug assert: recovered state must MATCH the WAL-logged decision or panic (invariant violated).
    - Cost avoided: silent cross-shard atomicity violation — undetectable until reconciliation; the worst class of distributed bug.
    - Muscle: durable decisions are write-once authority — recovery is "load then act", not "re-evaluate". Reapplies at: W74 raft state-machine recovery, W83+ ledger checkpoint recovery, W92 VSR view-change recovery.

  - **(EXPERT, perf) Expect to hit (perf) #1 — per-tx `Box` allocation (bar (c) violation). When `dhat_zero_alloc_steady_state` reports ~10k allocs/sec and `bench_2pc_throughput_and_fsync_budget` shows p99.9 ≈ 100 µs spikes:**
    - Symptom: dhat flags ~10k mallocs/sec attributable to `Box::new(TwoPhaseCoordinator{..})`; `perf record` shows allocator at 5-10% CPU during steady state; p99.9 spikes during allocator compaction.
    - Why: `begin(...) -> Box<TwoPhaseCoordinator>` allocates ~120 B + metadata per tx; at 10k tx/sec = 10k mallocs + 10k frees/sec ≈ 1 ms/sec allocator CPU + unbounded tail.
    - Fix: pre-allocated pool `CoordPool { slots: [_; 1024], free: SmallVec<u16> }`; `begin()` pops a slot (~10 ns), `finalize()` pushes back; participant pool symmetric; NUMA-local (inherits W65 shard fix).
    - Cost avoided: ~1 ms/sec allocator CPU → 0; p99.9 alloc tail eliminated; memory bounded at 1024 × ~200 B ≈ 200 KiB/shard (fits L2, predictable).
    - Muscle: any per-event state on a high-throughput hot path lives in a pre-allocated pool sized = throughput × latency × safety, not on the heap per event. Reapplies at: W74 MatchCommand reuse + VSR Prepare pool, W83+ ledger Transfer pre-sized pool (TigerBeetle exact pattern), W92 ledger v1.0 static-mem invariant.

  - **(EXPERT, perf) Expect to hit (perf) #2 — fsync per Prepare-ack (bar (c) violation). When `bench_2pc_throughput_and_fsync_budget` plateaus at ~500 tx/sec with `iostat -x 1` showing the WAL device at 100% util, low IOPS:**
    - Symptom: throughput plateaus far below target; p99 dominated by disk wait; fsync counter ~30k/sec.
    - Why: coordinator fsyncs on each incoming Prepare ack → 10k tx × 3 parts = 30k fsync/sec; NVMe ceiling ~1-3k/sec single-channel; the pipeline serializes behind disk.
    - Fix: fsync at exactly TWO points — (a) coordinator's Commit/Abort decision (once/tx), (b) participant's Prepared vote (once/tx-part) — both batched via W26 GroupCommit. Intermediate ack-tracking is in-memory, reconstructible from participants' Prepared votes on recovery. ~30k → ~20 actual fsync/sec.
    - Cost avoided: ~1500× fewer fsyncs; ~10 ms/tx commit latency reclaimed; throughput unblocked ~500 → ~10k tx/sec.
    - Muscle: in any multi-message protocol, fsync only the MINIMAL durable decision points (coordinator decision + each participant vote); everything else is in-memory reconstructible. Pair with group-commit. Reapplies at: W67 raft AppendEntries quorum, W74 matching-engine raft commit, W83+ ledger VSR PrepareOk batching, W92 ledger io_uring submission ring.

  - **(EXPERT) When `loom_decision_log_then_send_no_reorder` reports a participant observing a send before the decision flag is durable:**
    - Symptom: loom finds an interleaving where the sender thread reads `decision_logged == true` and sends Commit before the logger thread's WAL append is visible.
    - Why: the durable-flag was a plain store/load (or `Relaxed`); the send is not ordered after the log.
    - Fix: `Release` store on the durable flag after the WAL append, `Acquire` load before the send; the send happens-after the durable log.
    - Cost avoided: a recovery that can't trust "sent ⇒ logged"; reintroduces the asymmetric-commit window under reordering — silent and only on weak-memory hardware (aarch64).
    - Muscle: a "durable then act" ordering needs a real acquire/release fence, not a plain flag — loom is how you prove it on weak memory. Reapplies at: W74 raft commit-index publish, W92 VSR view-change ordering.
