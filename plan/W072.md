- [ ] **Build**: `crates/txn/src/two_phase_commit.rs` — `TwoPhaseCoordinator` and `TwoPhaseParticipant`. Standard 2PC
  with Prepare / Commit messages and timeout-based abort. (~105 min)
  - **Why**: 2PC is the canonical atomic commit protocol across distributed participants. Get the failure semantics wrong and you have "in-doubt" transactions hanging participant resources forever, or worse, asymmetric commit (some yes, some no). Used by ledger-deterministic distributed-mode (Phase 5), txn cross-shard commits, and pattern-matched in interview ("walk me through 2PC failure modes").
  - **Read first**: InnoDB XA — `storage/innobase/handler/handler0alter.cc::ha_innobase::prepare()` shows the participant API. CockroachDB transaction protocol — `pkg/kv/kvserver/txnwait/queue.go` (their evolved version that pipelines parallel commits). Gray-Lampson 1989 "Granularity of Locks and Degrees of Consistency" §6 for the original 2PC framing.
  - **Design**:
    ```rust
    pub enum CoordPhase { Init, Preparing { acks: BitSet }, Committing, Aborting, Done }
    pub struct TwoPhaseCoordinator {
        pub tx_id: TxId,
        pub participants: Vec<ParticipantId>,
        pub phase: CoordPhase,
        pub log: WalHandle,           // durable decision log — survives coordinator crash
        pub timeout: Duration,
        pub started_at: Monotonic,
    }
    pub enum PartPhase { Idle, Prepared { vote: bool }, Committed, Aborted }
    pub struct TwoPhaseParticipant {
        pub tx_id: TxId,
        pub phase: PartPhase,
        pub coord: ParticipantId,
        pub local_log: WalHandle,
    }
    pub enum Msg {
        Prepare { tx_id: TxId, coord: ParticipantId },
        PrepareOk { tx_id: TxId, from: ParticipantId },
        PrepareNo { tx_id: TxId, from: ParticipantId, reason: AbortReason },
        Commit { tx_id: TxId },
        Abort { tx_id: TxId },
        Ack { tx_id: TxId, from: ParticipantId },
    }
    ```
    **Invariants**: (i) Coordinator's decision (commit/abort) is **logged before sent** — survives coordinator crash. (ii) Participant `Prepared` state is durable — participant CANNOT unilaterally abort after voting Yes. (iii) Coordinator timeout from `Init`/`Preparing` → Abort allowed. After logging Commit → no Abort, only retry. (iv) Idempotent message processing: Commit/Abort can arrive multiple times; participant idempotently transitions.
  - **Build steps**: 1. (~15 min) Types + serde. 2. (~25 min) Coordinator `begin(tx_id, parts)` → broadcast Prepare. 3. (~25 min) Participant `handle_prepare` — vote yes/no, durably log, reply. 4. (~25 min) Coordinator `handle_prepare_ok/no` — gather acks, decide, durably log Commit-or-Abort, broadcast. 5. (~15 min) Participant `handle_commit/abort` — durably log, apply or rollback, ack. 6. (~Tests Tue.)
  - **Pitfalls** (named, 4):
    - *Coordinator crash after Commit-log, before Commit-send*: **Symptom**: participants stuck in Prepared state forever ("in-doubt"). **Fix**: coordinator recovery reads its wal, finds Commit/Abort decision, resends to all participants. Participants reply idempotently. Without wal, recovery is impossible.
    - *Asymmetric commit*: **Symptom**: coordinator sends Commit to A, crashes, restarts and sends Abort to B → A committed, B aborted, invariant broken. **Fix**: coordinator's wal entry is the *single source of truth*. Recovery re-reads wal, sends the *logged decision* — never re-decides.
    - *Participant in-doubt resolution*: **Symptom**: participant times out waiting for Commit/Abort after Prepared — what to do? **Fix**: participant CANNOT abort unilaterally if it voted Yes. It must wait + poll coordinator (or coordinator's recovery peer if HA). Optional cooperative termination: query other participants — if any has Aborted, safe to abort.
    - *Heuristic decision risk*: **Symptom**: human operator manually resolves in-doubt by guessing → diverges from coordinator decision. **Fix**: forbid in code; expose only `coordinator-resolve(tx_id, decision)` admin API that requires coordinator-side confirmation.
  - **Test scenarios**: (covered Tuesday) (a) Happy path 3-participant commit. (b) Kill coordinator after sending Prepares — participants in Prepared, coordinator restarts, resolves all via wal. (c) Kill coordinator AFTER logging Commit, before sending — recovery completes commit. (d) Kill participant mid-Prepare — coordinator times out, aborts. (e) Network reorder: Commit arrives before Prepare-ack at same participant — must enqueue/handle.
  - **Acceptance**: property test `no_asymmetric_commit` — 10k random schedules, no run produces both Committed and Aborted on same tx_id across participants. Crash injection passes 100 iterations. Bench: 1k participants happy-path commit < 50ms.
  - **Downstream**: `ledger-deterministic` distributed mode uses 2PC to span cross-shard transfers (W83+). consensus-vsr provides the durable log (`wal`) — 2PC piggybacks on VSR-replicated log so coordinator failover is automatic. Interview load-bearing — answer "what does CockroachDB do differently?" → pipelined commits, parallel commits via STAGING txn record.
