**The v3 lock this week enforces (read before Monday):** there is **one log on the hot path** — the VSR-replicated order/event log (`consensus-vsr`, W74). `log-distributed` is **off** that hot path. It is two things at once: (a) a standalone Kafka-fidelity *learning artifact* (partitioned log, ISR, consumer groups, exactly-once, compaction) that proves you understand the distributed-log primitive end-to-end; and (b) the **read-side fan-out** — a *projection* that streams the committed VSR log to analytics/market-data/replica-read consumers. The projection carries **two staleness contracts** (the load-bearing §4A invariant): the **control/risk plane** reads **read-after-commit from local applied state on the leader shard** (no consensus round-trip, used by `risk-engine` W85); the **analytics plane** reads **best-effort bounded-staleness (≤500 ms / ≤1000 ops) + an op-number token**. A risk decision served from the analytics contract is a *correctness bug*, not a perf bug — the design must make that mistake impossible to write by accident. Every choice this week serves that lock so W85/W107/W103 slot in without a rewrite.

The artifact proves two things to a founding-eng reviewer: (i) you can build the distributed-log primitive (partition/ISR/consumer-group/EOS/compaction) to Kafka fidelity, and (ii) you understand *why the venue's hot path is the VSR log and Kafka is the off-path projection* — the resolution of "Kafka vs VSR" (§9).   - *Mental model*: the projection is a deterministic, read-only follower of the committed VSR log. Control/risk reads its **local applied state on the leader shard** (read-after-commit, the data is already there, ~0 round-trip). Analytics reads a **bounded-staleness snapshot** tagged with an op-token, so a caller can *know* how stale it is and refuse to use it for a control decision. Kafka concepts (partition, ISR, consumer-group, EOS, compaction) are the off-path learning artifact in the SAME crate; they are NOT the hot path.
  - *Contract*: `struct LogProjection { committed: ChunkedLog<Entry>, applied_op: u64 }`; two reader handles — `struct ControlReader<'p>(&'p LogProjection)` with `fn read_after_commit(&self, key: Key) -> (Value, OpNum)` (reflects `applied_op`, no round-trip), and `struct AnalyticsReader<'p>(&'p LogProjection)` with `fn read_bounded(&self, key: Key) -> (Value, OpToken, StalenessBound)` where `OpToken` lets the caller test freshness. `risk-engine` (W85) is wired ONLY a `ControlReader` — an analytics read is unreachable from risk code (R6). The projection has **no write API** (R3).
  - *Back-of-envelope* (bar (c)): off-path fan-out target 2M entries/s. A `Vec<Entry>` that reallocates under a 1M-entry burst = `malloc(1M×64 B = 64 MB) + memcpy + free` ≈ ~30 ms freeze → the fan-out stalls and the analytics staleness bound blows past 500 ms. Chunked 16k-entry segments = 0 reallocs, just a pointer push per segment. Control read = a local hashmap/btree lookup over applied state ≈ ~30 ns (no syscall, no consensus round-trip). Analytics read = same lookup + bundling the current op-token ≈ ~35 ns. Per-message offset fsync = ~1 ms/msg → caps at 1k msg/s; group-commit one fsync per offset batch = amortized ~µs/msg. Cliff: chunked (0 ns realloc) vs Vec doubling (~30 ms spikes) = the whole analytics-staleness budget.

    - R2. ISR (in-sync-replica) set tracked deterministically; shrink/grow ordered by `ReplicaId` (no HashMap iteration).
    - R3. **The projection has NO independent write API** — it only follows the committed VSR commit stream. Compile-time: no `fn append`/`fn write` on `LogProjection`.
    - R4. **Control/risk read = read-after-commit from local applied state on the leader shard**; returns `(Value, OpNum)`; no consensus round-trip.
    - R5. **Analytics read = bounded-staleness (≤500 ms / ≤1000 ops, metric not SLA) + op-number token**; returns `(Value, OpToken, StalenessBound)`.
    - R6. **A risk decision cannot be served from the analytics contract** — `risk-engine` is wired only a `ControlReader`; an analytics read is unreachable from risk code (type-level guard).
    - R7. Consumer-group offsets committed via group-commit (one fsync per batch), never per-message.
    - R8. Exactly-once: idempotent producer (PID, seq) on the Kafka-fidelity side; duplicate appends deduped at the edge.
    - R9. Log-compaction: keep latest value per key; tombstones honored; deterministic compaction order.
    - R10. Fan-out throughput ≥2M entries/s off-path; analytics staleness bound holds under a 1M-entry burst (no Vec realloc stall).
