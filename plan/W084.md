- [ ] [NEW v2] **Build**: bounded replay — `archive.replay(from: ArchiveOffset, to: ArchiveOffset) -> ReplayStream`. (~3 hrs)
  - **Why**: Replay is the operational counterpart of W83's recording: it's how late subscribers catch up, how VOPR scenarios re-derive state, and how ledger forensics rewinds. The "byte-identical to original publication" property is load-bearing — VOPR will fail-fast if replay diverges. Upstream Aeron's archive client exposes `replay(recordingId, position, length)`; we mirror the API.
  - **Read first**: Aeron `aeron-archive/src/main/java/io/aeron/archive/Archive.java` `ReplaySession`; `aeron-archive/src/main/cpp/client/AeronArchive.cpp` `replay()`.
  - **Design**:
    ```rust
    pub struct ArchiveOffset(u64);                 // monotonic, includes rotation index
    pub struct ReplayStream<'a> {
        cycle: &'a mmap_queue::Cycle,              // read-only mmap view
        cursor: ArchiveOffset,
        end: ArchiveOffset,
        scratch: ArrayVec<u8, MAX_FRAME>,          // reused per next()
    }
    impl Iterator for ReplayStream<'_> {
        type Item = Result<&[u8], ReplayErr>;
    }
    impl Archive {
        pub fn replay(&self, from: ArchiveOffset, to: ArchiveOffset) -> ReplayStream<'_>;
    }
    ```
    **Invariants**: (i) `replay(from, to)` yields exactly the frames in [from, to) — no skip, no dup, (ii) byte-identical to original publication bytes (including header), (iii) replay is read-only — never mutates Cycle; safe to run concurrent with recording, (iv) ArchiveOffset that falls between frame boundaries is rejected at construction.
  - **Back-of-envelope**: replay throughput target ≥1.5M frames/s on M2 NVMe. Per-frame cost: read length prefix (~5 ns L1 if mmap is hot) + verify CRC (~20 ns hardware crc32c on 256 B) + return slice into mmap (zero-copy, no memcpy) = ~30 ns/frame → 30M frames/s theoretical. Bottleneck is disk readahead, not CPU: sequential mmap read on NVMe ~3 GB/s = ~12M frames/s at 256 B. M2 NVMe ~7 GB/s = ~28M frames/s. The 1.5M target leaves 10× headroom — comfortable. madvise(MADV_SEQUENTIAL) on the mmap range hints the kernel to prefetch aggressively (saves ~50% page-fault tail). NO frame copies — `Iterator::Item = Result<&[u8], ReplayErr>` returns a slice INTO the mmap; caller must consume before next() invalidates. `scratch: ArrayVec<u8, MAX_FRAME>` exists only for the rare case where a frame straddles a rotation boundary (need to assemble from two files).
  - **Build steps**: 1. (~25 min) implement `ReplayStream::next()` reading length prefix + verifying CRC; advance cursor by frame-size. 2. (~25 min) handle term-buffer rotation: when cursor's rotation-index < end's rotation-index, transparently switch underlying Cycle file. 3. (~30 min) partial-frame boundary handling — if a frame is mid-write at `to`, stop short and return `Done`. 4. (~30 min) tail-of-recording vs hot-recording: if `to == LATEST`, follow recording head (poll on EOF). 5. (~30 min) write byte-identical test: record 1M frames in W83's Archive, replay 100k from offset N, byte-compare each frame against original publication's term buffer; require 0 byte-diff. 6. (~30 min) replay-out-of-bounds error path; replay-of-deleted-rotation error.
  - **Pitfalls**: *Position cursor accuracy*: **Symptom**: caller passes an "offset" that lands mid-frame, replay returns malformed bytes. **Fix**: snap offset to nearest frame boundary OR reject with `BadOffset`. *Partial frame at boundary*: **Symptom**: replay running concurrently with recording reads a frame whose `len` is set but payload not yet flushed. **Fix**: recorder writes payload before len (or uses `release` ordering on len store); reader uses `acquire` on len. *Cross-rotation cursor*: **Symptom**: `replay(from=X, to=Y)` where X and Y span rotation, reader holds the old file open after rotation, breaks. **Fix**: ReplayStream holds an `Arc<RotationIndex>` and on rotation, mmap the next file transparently. *Replay during retention purge*: **Symptom**: replay reading file F while retention thread deletes F. **Fix**: rotation index pins files referenced by active replays.
  - **Expect to hit (perf) #1 — frame memcpy into scratch buffer destroys zero-copy (bar (c) violation)**: a tempting `ReplayStream::next()` implementation reads `len` then `memcpy`s payload into `self.scratch` and returns `&self.scratch[..len]` — that's ~80 ns memcpy/frame at 256 B AVX2, plus the scratch buffer is now hot in L1 but the actual mmap data is being read sequentially (wasted L1 footprint). At 1.5M frames/s, ~120 ms/sec of pure memcpy overhead — replay throughput caps at ~10M frames/s instead of 30M. Symptom: bench shows 8M frames/s replay (above target but well below mmap bandwidth); flame graph shows `__memcpy_avx2_unaligned`. Fix: return `&[u8]` directly into the mmap — `let payload: &[u8] = unsafe { from_raw_parts(self.cycle.as_ptr().add(self.cursor.0 as usize + 8), len) };`. Zero-copy. Caller must NOT hold the slice across `next()` calls (lifetime of `'a` constrained to the iterator). The `scratch` buffer is ONLY used for the rare cross-rotation case. Cost avoided: ~80 ns/frame × 1.5M frames/s = ~120 ms/sec; restores L1 cache to mmap data. Muscle: replay is zero-copy by construction — the mmap IS the data, never a buffer to copy from. Reapplies at: W83 archive recording (write into mmap directly), W92 ledger v1.0 io_uring replay reads, W90 marketdata-kernelbypass receive (zero-copy AF_XDP).
  - **Expect to hit (perf) #2 — replay calls `madvise(MADV_SEQUENTIAL)` per next() (bar (c) violation)**: a "performance hint" pattern calls `madvise(ptr, page_size, MADV_SEQUENTIAL)` on each frame's page — but `madvise` is a syscall (~300 ns) and at 1.5M frames/s that's a constant ~450 ms/sec of pure syscall overhead, MORE than the actual replay work. Symptom: `strace -c` shows madvise dominating; replay throughput caps at 1M frames/s despite mmap being warm. Fix: call `madvise(MADV_SEQUENTIAL)` ONCE per Cycle file at ReplayStream construction (for the entire mmap range), not per-next(). Kernel maintains the hint internally — readahead behavior persists for the lifetime of the mmap. Cost avoided: ~300 ns × 1.5M = ~450 ms/sec of syscall; restores replay to NVMe-bandwidth-bound throughput. Muscle: this is the W77 Mon `madvise WILLNEED` lesson restated — kernel hints amortize over LARGE ranges, never per-element. Reapplies at: W84 cross-rotation file transition (madvise once per new file), W92 ledger v1.0 io_uring (register buffers ONCE, reuse forever).
  - **Test scenarios**: record 1M frames, kill recording mid-write, replay [0, 1M) → expect last partial frame omitted, prior 999,999 byte-identical. Replay concurrent with active recording at 500k QPS → no torn frames observed in 10s run. Property: for all (from, to) with from ≤ to ≤ recorded_position, `replay(from,to).collect()` == original_bytes[from..to].
  - **Acceptance**: 100k-frame replay byte-identical to original (0 diff); replay throughput ≥1.5M frames/s on M2 NVMe; W83 recording + W84 replay together pass the round-trip test gated on aeron v0.7 SHIP.
  - **Downstream**: VOPR scenarios (W87) inject crash + replay to verify state convergence; consensus-vsr uses replay for follower catch-up; ledger v1.0 uses replay for cold-restart from snapshot+tail.

- [ ] [NEW v2 runtime v1.0] **Build**: deterministic test harness extension — inject clock + ordering oracle,
  replay-equivalent across runs. (~90 min)
  - **Why**: This is the single most leverageable piece in the runtime crate. Without it, neither ledger VOPR (W87-W88) nor consensus-vsr VOPR can be deterministic — every async test would race differently. With it, ANY seed yields the same task interleaving + clock ticks + I/O completions across runs, making bugs reproducible. Mirror TigerBeetle's `simulator.zig` and Foundationdb's flow simulator.
  - **Read first**: TigerBeetle `lib/tigerbeetle/src/simulator.zig` (Time, Tick, ChannelChoice); MadSim Rust simulator `madsim/src/sim/runtime.rs`; loom (for choice points reference).
  - **Design**:
    ```rust
    pub struct DetHarness {
        seed: u64,
        rng: SmallRng,
        clock: SimClock,                      // monotonic ticks, advanced by caller
        order_oracle: TaskOrderOracle,        // chooses next runnable task
        io_oracle: IoCompletionOracle,        // chooses which inflight I/O completes next
        history: Vec<DetEvent>,               // for diff between runs
    }
    pub struct SimClock { now_ns: u64 }
    pub enum DetEvent { Spawn(TaskId), Tick(u64), Wake(TaskId), IoDone(IoId), Yield(TaskId) }
    impl DetHarness {
        pub fn run_until(&mut self, predicate: impl Fn(&Self) -> bool);
        pub fn assert_history_matches(&self, baseline: &[DetEvent]);
    }
    ```
    **Invariants**: (i) given identical `seed`, two runs produce identical `history`, (ii) `SimClock` cannot be queried directly by user code — must go through `clock.now()` which advances only by `tick()`, (iii) all "real" syscalls in this harness are mocked (no `read(2)`, `write(2)`, `poll(2)` reach the kernel), (iv) `order_oracle` is the ONLY source of nondeterminism — it's seeded.
  - **Back-of-envelope**: acceptance gate is "<10% wall-time vs production reactor for same simulated workload." Production reactor poll: ~50 ns/iter (W83 zero-alloc audit). DetHarness adds: (i) `clock.now()` call ~10 ns (memo'd `now_ns: u64`), (ii) `order_oracle::next()` ~50 ns (seeded shuffle over ~10 runnable tasks via PCG/Xoshiro PRNG ~5 ns + index lookup ~5 ns + bounds check ~5 ns = ~15 ns; PLUS history append ~30 ns), (iii) `io_oracle::next()` ~20 ns when no I/O outstanding, ~50 ns when servicing one = ~80 ns/poll budget added to ~50 ns base = ~130 ns/poll → 2.6× production cost. Over budget by 16×. Fix: minimize hot-path tracking — history only logs MAJOR events (Spawn, Wake) not every Tick (which would be a 30 ns append × 10M ticks/sec = 300 ms/sec of pure history append). Reserve detailed history to "trace mode" only, off by default; use seed-replay (rerun from seed) to reconstruct full history when needed. With trace mode off, DetHarness overhead drops to ~80 ns/poll = 60% over production — close to 10% gate with further tuning. 10M scenario runs/day target requires ~30 hr of DetHarness wall-time; the 10% gate keeps that under 33 hr/day per machine = 100% utilization budget; failure pushes to 70 hr/day = infeasible.
  - **Build steps**: 1. (~10 min) define `Reactor` trait abstraction so production reactor and DetReactor both satisfy it. 2. (~15 min) implement `SimClock` with monotonic ticks; ban `Instant::now()` in tested code via lint. 3. (~20 min) implement `TaskOrderOracle::next()` — given the runnable set, deterministically pick one (seeded shuffle). 4. (~15 min) implement `IoCompletionOracle::next()` — pick an in-flight I/O to complete, optionally with seeded latency. 5. (~15 min) implement history recording: every spawn/wake/tick/io-done appends to history. 6. (~10 min) write the replay-equivalence test: run scenario X with seed S twice → assert history vec equal. 7. (~5 min) wire bridge function `det_harness_for_vopr()` returning a configured DetHarness for ledger/vsr VOPR consumption.
  - **Pitfalls**: *Hidden real-time syscall*: **Symptom**: scenario diverges between runs because some library calls `Instant::now()` internally. **Fix**: clippy lint banning `Instant::now()` in `cfg(det_harness)`; runtime panic via shim if invoked. *Nondeterministic HashMap iteration*: **Symptom**: scheduling oracle picks differently because runnable set is HashMap-backed. **Fix**: use BTreeMap or stable-order Slab for runnable set; order oracle takes a stable iterator. *Bridge to production*: **Symptom**: code that compiles under both Reactor impls behaves subtly different in real runtime. **Fix**: shared test suite that runs under both; document trait contract precisely. *Wake-storm starvation*: **Symptom**: one task always wakes first, others starve in simulator. **Fix**: order_oracle re-shuffles entire runnable set each tick (or rotates).
  - **Expect to hit (perf) #1 — `Vec<DetEvent>::push` reallocates during long scenarios (bar (c) violation)**: history starts empty; long VOPR scenarios (10M ops) push 10M events into `Vec<DetEvent>` — Vec doubles capacity logarithmically (initial 0 → 4 → 8 → ... → 16M), each reallocation is `malloc(new_cap × 32 B) + memcpy(old_data) + free(old)` = ~50 ms at 16M capacity, blocking the entire scenario for that pause. At 10M scenarios/day, hit ~20 doublings per scenario × ~5 ms total = ~10 hr/day of pure realloc time across all scenarios. Symptom: scenario wall-time variance huge (some 2s, some 7s); `perf` shows `__memcpy_avx2` in 10% samples. Fix: pre-allocate history with capacity = expected event count at harness construction (`Vec::with_capacity(expected_events)`); for unknown bounds, use a chunked structure (`SegQueue`-style with 16k-event segments — no reallocation, just push a new segment when full). For the bar-(c) gate, also expose `history_mode: Off | Sparse | Full` — most VOPR runs need only event count + final hash, not the full event log. Cost avoided: ~10 hr/day of realloc; restores scenario throughput variance to <10%. Muscle: any "history" or "log" data structure on a determinism harness uses chunked segments, not Vec — reallocation is forbidden during runs. Reapplies at: W87 VOPR scenario log, W88 consensus-vsr VOPR run log, W92 ledger v1.0 SHIP VOPR scenarios.
  - **Expect to hit (perf) #2 — PRNG state in shared `Mutex<SmallRng>` (bar (c) violation)**: a naive harness exposes `rng()` via `Mutex<SmallRng>` so multiple test threads can share — but the harness is supposed to be SINGLE-THREADED (one scenario per thread; parallelism is across scenarios, not within). Mutex acquire on every random sample = ~25 ns uncontended + cache-line ping-pong if multiple cores ever touch it = ~100 ns under contention. Worse: under contention, the mutex serializes the PRNG, which makes order non-deterministic across runs if 2+ threads ever touch the same harness (defeating the determinism property). Symptom: history-equivalence test fails sporadically on multi-core builds; mutex contention shows in `perf lock`. Fix: PRNG is owned by the harness (no Mutex, no Arc) — the harness itself is `!Sync` to compile-time-prevent sharing. Each scenario runs on its OWN harness instance with its OWN seeded PRNG. Parallelism = N harnesses on N threads, each seeded differently. Cost avoided: 25 ns/sample under contention; eliminates the determinism-violating race; restores compile-time guarantees. Muscle: a deterministic harness is single-threaded by construction — `Send` is OK (move between threads), `Sync` is forbidden (no shared access). Reapplies at: W87 VOPR scenario PRNG, W88 consensus-vsr VOPR PRNG, W92 ledger v1.0 SHIP determinism property.
  - **Test scenarios**: spawn 100 tasks, sleep random durations, exchange messages; same seed → identical `history`. Inject "bug" (task that polls without yielding) → harness detects starvation via tick counter > N without progress. VOPR-bridge test: ledger VOPR scenario reproduces from seed S under DetHarness.
  - **Acceptance**: replay-equivalent under 100 random seeds × 1000-step scenarios; harness adds <10% wall-time vs production reactor for same simulated workload; W87-W88 VOPR successfully reproduces a real bug via seed-replay.
  - **Downstream**: ledger VOPR (W87) consumes this for runtime layer; consensus-vsr VOPR (W88) consumes for replica scheduling; matching-engine deterministic tests in M30+ rebuild on top.
