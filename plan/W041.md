- [ ] [NEW v2] **Build**: `crates/lsm-core/src/compaction/lcs.rs` — `LeveledCompactor { levels: Vec<Level>, fanout: u32 }`. Each level Lk has ~10× the size of L(k-1). (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: LCS is RocksDB's default and the standard for read-heavy workloads. The two perf
    pitfalls — overlap-as-linear-scan + manifest-fsync-per-SST — are the difference between a competitive LCS
    impl and a 300× slower one. Downstream W42 TWCS, W95 mini-db production tier all reuse the patterns.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: keep each level Lk to a target size = fanout^(k-1) × L1_target,
    with Lk's SSTs key-disjoint (k ≥ 1). A read touches at most one SST per level. Compaction picks one Lk
    SST + overlapping L(k+1) SSTs, merges, outputs multiple SSTs sized to L(k+1)'s target.

  - **Requirements** — write in `crates/lsm-core/notes/41_lcs_design.md`:
    - R1. Lk target size = fanout^(k-1) × L1_size_target.
    - R2. **Key-disjoint invariant** for k ≥ 1: SSTs within a level have non-overlapping key ranges.
    - R3. **L0 special case**: L0 allows overlaps; L0→L1 merge picks ALL overlapping L0 SSTs.
    - R4. **Range-tree overlap index** per level (BTreeMap keyed by first_key); O(log N) overlap query.
    - R5. **Batched manifest mutations**: one `CompactionResult { adds, removes }` record per compaction;
      one fsync covers the full atomic swap.
    - R6. Output SST sizes strictly bounded; split on threshold.
    - R7. Read amp ≤ 3 (warm bloom); write amp ≤ 10; space amp ≤ 1.1×.

  - **Design walk-through** — answer each:

    - D4. Range-tree overlap query: write the BTreeMap-based algorithm. Why `range(..end).next_back()`?
    - D5. Manifest batching: write the record format. Why one fsync per compaction event (not per SST)?

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  - **When `bench_lcs_overlap_query_under_300ns` reports ~90 µs per query:**
    - Symptom: pick-victim's overlap check walks 3000 SSTs × 30 ns = ~90 µs; scheduler CPU shows ~15-25%
      in flamegraphs, dominated by `keys_cmp`; foreground writes stall waiting for level-snapshot lock
      held across the scan.
    - Why: naively storing `Vec<SstReader>` per level and iterating to find overlapping SSTs is O(N) per
      query.
    - Fix: per-level **range-tree index** (BTreeMap keyed by `first_key`) with `range(..end).next_back()`
      to find the first overlapping SST in O(log N) (~7 cmps ≈ 200 ns at N=1000), then linear-forward
      until first_key > end. Build the index once per level mutation, not per query.
    - Cost avoided: ~90 µs → ~300 ns per overlap query = **~300× speedup**; compaction CPU drops below
      5%; foreground write tail latency p999 < 10 ms holds.
    - Muscle: "store data in the access pattern's shape" — range queries demand range trees, not vectors.
      Reapplies at: W42 LockManager wait-graph (range search over keyspace), W74 matching-engine
      price-level lookups (price-tree), W95 mini-db range scans across SSTs.

  - **When `bench_lcs_manifest_one_fsync_per_compaction` reports fsync count == 10 (one per output SST):**
    - Symptom: a 10-output compaction emits 10 fsyncs ≈ 50 ms; combined with 50-SST flushes (250 ms
      fsync per flush), the manifest fsync dominates ingest latency. Ingest shows sawtooth: ~50 MB/sec
      during flush, ~500 MB/sec between.
    - Why: every L0 flush calls `manifest.append(add_sst)` + fsync; a 256 MB memtable flush emits ~50
      SST records.
    - Fix: **batch manifest mutations** into one record per compaction event (all adds + removes in a
      single fsync). Append `CompactionResult { adds: [...], removes: [...] }` atomically; one fsync
      covers the full atomic swap. Reduces manifest fsyncs from O(SSTs) to O(1) per compaction.
    - Cost avoided: 250 ms → 5 ms per flush = **50× reduction**; ingest throughput recovers from
      sawtooth to flat ~400 MB/sec.
    - Muscle: "fsync count, not byte count, is the durability bottleneck" — batch every durability
      fence whose contents are atomic anyway. Reapplies at: W42 txn group commit, W74 matching-engine
      WAL batching, W80 ledger journal commit.

  - **When `lcs_l0_overlapping_merge_into_l1` reports only 1 L0 SST as input:**
    - Symptom: L0 has 5 overlapping SSTs; L0→L1 pick-victim grabs only 1; the other 4 remain unmerged;
      read amp at L0 grows.
    - Why: L0 special-cased wrong — L0 allows overlaps; treating it like Lk≥1 breaks the algorithm.
    - Fix: L0 merge picks ALL overlapping L0 SSTs into L1. The pick algorithm has two branches:
      `if level == 0 { all overlapping L0 + L1 in range }` vs `if level >= 1 { one Lk + L(k+1)
      overlapping }`.
    - Muscle: L0 is structurally different from L1+; any LCS implementation needs an explicit L0
      branch. Reapplies at: W42 TWCS active window special case, W95 mini-db.

  - **5-year failure mode** (write in `notes/41_lcs_followup.md` after green): when learned compaction
    selectors (ML-based victim picking) mature, the BTreeMap overlap index becomes input to a learned
    policy. State migration: keep range-tree as cold-start picker; learned policy as override.

- [ ] [NEW v2] **Build**: pick-victim: pick L0 → L1 if L0 has ≥4 SSTables OR L1 size > target. For Lk→L(k+1), pick file with most overlap. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: victim selection runs every compaction tick (~10-100 Hz). The score-recompute
    perf pitfall is the difference between 350 ns/tick and 350 µs/tick (1000×). Wrong tiebreaking → some
    levels starve. Downstream W42 LockManager wait-graph, W74 matching-engine reuse the
    incremental-maintenance pattern.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: pick the best Lk → L(k+1) victim every compaction tick. Two
    dimensions: which level needs attention (score = level_size / target), and which SST within that level
    minimizes wasted I/O (overlap ratio).

  - **Requirements** — write in `crates/lsm-core/notes/41_pickvictim_design.md`:
    - R1. Per-level score: `level_size / level_target`; level with highest score wins.
    - R2. **Cached per-level size** (`AtomicU64`) updated on add/remove SST; score lookup is one
      atomic load.
    - R3. Within candidate level, rank SSTs by overlap ratio = `overlapping_L(k+1)_bytes / victim_bytes`;
      pick lowest.
    - R4. **Tiebreak by SST age** (older first) — sequence number compare; ~1 ns.
    - R5. **No format!/alloc** in the hot path; per-tick budget ≤ 1 ms.
    - R6. **Snapshot levels for pick→run duration** — overlap estimate doesn't go stale against
      concurrent flush.
    - R7. Per-tick CPU at idle ≤ 0.01% on a 16-core box.

  - **Design walk-through** — answer each:
    - D1. Score computation: write the math. Why ratio (not absolute)?
    - D2. Cached size: where does the counter live? Who updates it (add SST → +=, remove SST → -=)?
    - D3. Overlap ratio: write the formula. Why "lowest" (not highest)?
    - D4. Tiebreak by age: write the comparison. Why does fairness need explicit tiebreaking?
    - D5. Snapshot for pick→run: how do you snapshot? Arc clone of level Vec? Cow?
    - D6. **Pre-mortem (load-bearing)**: write the score-recompute storm trace — 1000 SSTs × 7 levels ×
      50 ns = 350 µs per tick × 100 Hz = 35 ms/sec of pure CPU on score recomputation while idle. Then
      write the level-starvation trace — score weighting always picks L0 first; L2+ piles up.
  - **Output**: `notes/41_pickvictim_design.md` with R1–R7, D1–D6.

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  - **When `bench_cached_size_one_atomic_load` reports score lookup iterating all SSTs (~350 µs):**
    - Symptom: per-tick score computation walks every level + every SST × `sst.file_size()`; at 1000
      SSTs × 7 levels × 50 ns = ~350 µs per tick; during heavy compaction at 100 Hz tick that's ~35
      ms/sec of pure score recomputation. Scheduler CPU climbs to ~3-4% idle.
    - Why: pick-victim's "needs compaction" score per level is `level_size / level_target`; the naive
      impl iterates all SSTs in all levels every tick. Also takes the level read-lock, blocking flush.
    - Fix: **cached `AtomicU64` per-level size** updated by add/remove SST events; score lookup is one
      atomic load (~5 ns). Recompute only when the level mutates (add/remove SST → fetch_add/fetch_sub
      on the cached size). Per-tick cost drops from 350 µs to **~50 ns × 7 = 350 ns**.
    - Cost avoided: ~350 µs → ~350 ns = **~1000× speedup**; scheduler CPU drops to ~0.01% idle; no
      flush lock contention.
    - Muscle: "incremental maintenance over recomputation" — if a derived value changes on N events
      but is read M >> N times, update it eagerly on the writer not the reader. Reapplies at: W42
      deadlock-detector edge counts, W74 matching-engine order-book depth-at-best-price, W95 mini-db
      level statistics.

  - **When `pick_victim_returns_highest_score_level` reports L0 always winning even when L2 is
    starving:**
    - Symptom: L0 has 4 SSTs (score 1.0); L2 has 20× target (score 20.0); pick consistently returns
      L0; L2 keeps growing.
    - Why: always picking L0 — if L0 score is always highest (because L0 trigger is "≥4 SSTs"
      regardless of size), deeper levels starve. Data piles up at L2+ over time, read amp grows.
    - Fix: rotate or weight scores so all levels get attention. RocksDB's heuristic: L0 score is
      `max(num_sst_l0 / l0_trigger, l0_size / l0_size_target)`; L0 doesn't dominate unless one of
      those exceeds a deeper level's score. Add an explicit fairness check: if any level has score >
      2.0 (severely over), pick that one regardless.
    - Muscle: any multi-source scheduler needs a fairness check on top of the greedy heuristic;
      pure greedy starves the losers. Reapplies at: W42 TWCS level-vs-window scheduling, W74
      matching-engine fill-broadcast across symbols.

    pickers become available, the score-based heuristic is the input feature for an ML model. State
    migration: cached score → ML feature vector; ML output → victim choice.

  #### Phase 1 — Problem, requirements, design (~25 min, no code yet)

  - **The problem this primitive solves**: open victim Lk SST + overlapping L(k+1) SSTs as a merge stream;
    write output SSTs sized to L(k+1)'s target; atomic manifest swap; delete inputs. The hot path is the
    merge inner loop; per-KV alloc is forbidden.

  - **Requirements** — write in `crates/lsm-core/notes/41_lcs_execute_design.md`:
    - R1. Input set: victim Lk SST + ALL overlapping L(k+1) SSTs.
    - R2. MergeIterator yields `(&Key, &[u8])` borrowed from mmap'd input blocks — zero-copy.
    - R3. SstBuilder's block buffer is a single reusable 16 KB Vec; `extend_from_slice` from the merge
      output.
    - R4. Output SSTs split at L(k+1)'s target_sst_size; one SstBuilder per output.
    - R5. **Atomic manifest swap**: one CompactionResult record (remove inputs + add outputs); fsync; then
      delete input files.
    - R6. **Debug-build verification**: post-compaction, assert L(k+1) key-disjoint invariant holds.
    - R7. Zero per-KV allocation on the merge hot path.

  - **Design walk-through** — answer each:

    - D3. Block buffer reuse: where is the 16 KB Vec allocated? When is it flushed + reset?
    - D4. Atomic manifest swap: write the record format. Why one record (not separate add/remove)?

  #### Phase 3 — Make the tests pass, one failure at a time (~60 min)

  - **When `bench_execute_zero_per_kv_alloc` reports ~50 M allocations per compaction:**
    - Symptom: 50 M KVs compacted → 50 M malloc + 50 M free; allocator overhead ≈ 4 sec on a ~3 sec
      compaction; `samply` shows `malloc_zone_*` as dominant stack; merge-thread CPU 50% allocator +
      25% real work + 25% I/O.
    - Why: MergeIterator naively yields `(Key, Vec<u8>)` per step; SstBuilder takes owned Vec and
      copies into its block buffer. Two allocations per KV (the Vec from the input reader, the
      destructive append into builder block).
    - Fix: zero-copy merge — yield `(&Key, &[u8])` borrowed from the mmap'd input block, copy directly
      into SstBuilder's reusable block buffer via `extend_from_slice`. Block buffer is a single 16 KB
      `Vec<u8>` reused across all KVs; flush+reset on block boundary. Zero per-KV allocation.
    - Cost avoided: ~4 sec → ~0 sec per compaction = **2× compaction throughput**; merge-thread CPU
      drops to ~75% I/O-wait + 25% real work (vs 50/25/25 with alloc); P99.9 ingest tail latency
      stays flat.
    - Muscle: "the hot path allocates zero" — borrow from input until the boundary forces a copy;
      reuse output buffers across iterations. Reapplies at: W42 OCC read-set serialization, W74
      matching-engine MBO message construction, W77 messaging-aeron term-buffer writes, W80 ledger
      journal append.

  - **When `execute_atomic_manifest_swap` reports 20 fsyncs (10 adds + 10 removes):**
    - Symptom: 10-output compaction emits 10 add records + 10 remove records = 20 fsyncs; between
      records, partial state visible — recovery can see "outputs without removed inputs" → data
      duplicated.
    - Why: manifest update partial — removing inputs in one transaction but adding outputs in another
      creates a window where data is unreachable (or duplicated).
    - Fix: atomic record in manifest log. `CompactionResult { adds: [SstId; N], removes: [SstId; M] }`
      serialized as ONE record; one fsync covers the atomic swap.
    - Muscle: any "swap N for M" operation MUST be a single durable record; multi-record swaps have
      crash-windows. Reapplies at: W42 txn group commit, W74 matching-engine atomic order-state
      transition.
