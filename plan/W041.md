- [ ] [NEW v2] **Build**: `crates/lsm-core/src/compaction/lcs.rs` — `LeveledCompactor { levels: Vec<Level>, fanout: u32 }`. Each level Lk has ~10× the size of L(k-1). (~90 min)
  - **Why**: LCS (RocksDB default) trades higher write amp for far lower space amp and bounded read amp. Each level Lk has a target size 10×L(k-1); within Lk, SSTables have non-overlapping key ranges (except L0). A read touches at most one SST per level → read amp ~= number of levels (~7 for 1TB). Compaction always picks one Lk SST and merges it into the overlapping subset of L(k+1).
  - *Back-of-envelope*: LCS write amplification ≈ fanout × num_levels ÷ 2 = 10 × 7 / 2 ≈ **35× steady-state** (vs ~4× for STCS) — a single 1 KB key entry is rewritten ~35 times as it migrates from L0 to L6. Space amp ≈ 1.1× (one SST overlap window per level). **Read amp ≤ num_levels + 1** ≈ 7-8 SSTs probed per get; with bloom filter (10 bits/key, ~1% FPR per level) the expected bloom rejections drop disk fetches to ~1.07 SSTs/get. Compaction throughput ceiling: **NVMe write ≈ 1-3 GB/sec**, but writeAmp inflates this — 100 MB/sec ingest × 35× writeAmp = **3.5 GB/sec of compaction I/O**, saturating mid-tier NVMe. Implication: LCS bar-(c) crates must throttle ingest if the I/O budget is consumed; the level-by-level invariant check (key-disjoint) must be cheap (range-tree O(log N) per query, not O(N) scan).
  - **Read first**: RocksDB `db/compaction/leveled_compaction_picker.cc`; the "Leveled Compaction" doc on the RocksDB wiki.
  - **Design**:
    ```rust
    pub struct LeveledCompactor {
        levels: Vec<Level>,
        fanout: u32, // 10
        l0_trigger: u32, // 4: trigger L0->L1 at 4 L0 SSTs
        l1_size_target: u64, // e.g., 256 MB
    }
    pub struct Level {
        ssts: Vec<SstReader>, // sorted by first key (except L0)
    }
    ```
    **Invariants**:
    - For k ≥ 1, SSTs in Lk have non-overlapping key ranges (key-disjoint).
    - Lk target size = fanout^(k-1) * l1_size_target.
    - Compaction picks the single Lk SST with most overlap into L(k+1).
  - **Build steps**:
    1. (~20 min) Level type with key-range index for fast overlap query.
    2. (~30 min) Pick logic: L0 → L1 if ≥l0_trigger SSTs; Lk → L(k+1) if level size exceeds target.
    3. (~30 min) Run: open input + overlapping L(k+1) SSTs; merge; output multiple SSTs sized to target_sst_size.
    4. (~10 min) Verify post-condition: L(k+1) key-disjoint invariant holds.
  - **Pitfalls**:
    - *Overlap miss*: incorrect overlap detection leaves orphaned data. **Symptom**: read amp explodes (now multiple SSTs per level). **Fix**: range-tree index per level, validated post-compaction.
    - *L0 special-cased wrong*: L0 allows overlaps; treating it like Lk≥1 breaks the algorithm. **Fix**: L0 merge picks ALL overlapping L0 SSTs into L1.
    - *Output SST sizes drift*: forgetting to split output causes huge L1 files. **Symptom**: subsequent L1→L2 reads 2GB. **Fix**: target_sst_size enforced strictly; split on threshold.
    - **Expect to hit (perf) #1 — overlap query is linear scan (bar (c) violation)**: naively storing `Vec<SstReader>` per level and iterating to find overlapping SSTs is O(N) per query; at L4-L6 each level holds 100s-1000s of SSTs, so each pick-victim walks ~3000 SSTs × `cmp_keys ≈ 30 ns` = ~90 µs per overlap check, and pick runs on every compaction tick. Symptom: compaction scheduler thread shows up at ~15-25% CPU in flamegraphs, dominated by `keys_cmp`; foreground writes stall waiting for level-snapshot lock held across the scan.
      - Fix: per-level **range-tree index** (BTreeMap keyed by `first_key`) with `range(..end).next_back()` to find the first overlapping SST in O(log N) (~7 cmps ≈ 200 ns at N=1000), then linear-forward until first_key > end. Build the index once per level mutation, not per query.
      - Cost avoided: ~90 µs → ~300 ns per overlap query = **~300× speedup**; compaction CPU drops below 5%; foreground write tail latency p999 < 10 ms holds.
      - Muscle: "store data in the access pattern's shape" — range queries demand range trees, not vectors. Reapplies at: W42 LockManager wait-graph (range search over keyspace), W74 matching-engine price-level lookups (price-tree), W95 mini-db range scans across SSTs.
    - **Expect to hit (perf) #2 — manifest write per SST flush (bar (c) violation)**: every L0 flush calls `manifest.append(add_sst)` + fsync, and a 256 MB memtable flush emits ~50 SST records. At ~5 ms per fsync NVMe + ~50 records = **250 ms of manifest fsync per flush** — and this fsync is on the critical write path (foreground writers are blocked behind flush-finalize). Worse, the LCS L0→L1 compaction may produce 10 output SSTs, each generating an `add` + 1 `remove` record → 20 more fsyncs.
      - Fix: **batch manifest mutations** into one record per compaction event (all adds + removes in a single fsync). Append `CompactionResult { adds: [...], removes: [...] }` atomically; one fsync covers the full atomic swap. Reduces manifest fsyncs from O(SSTs) to O(1) per compaction.
      - Cost avoided: 250 ms → 5 ms per flush = **50× reduction**; ingest throughput recovers from a sawtooth pattern (~50 MB/sec during flush, ~500 MB/sec between) to flat ~400 MB/sec.
      - Muscle: "fsync count, not byte count, is the durability bottleneck" — batch every durability fence whose contents are atomic anyway. Reapplies at: W42 txn group commit, W74 matching-engine WAL batching, W80 ledger journal commit.
  - **Test scenarios**:
    - Random workload to 100M entries; verify key-disjoint invariant at every level after compaction.
    - Read-amp probe: 1000 random reads; count SSTs touched; ≤ num_levels.
  - **Acceptance**: read amp ≤ 3; write amp ≤ 10; space amp ≤ 1.1x.

- [ ] [NEW v2] **Build**: pick-victim: pick L0 → L1 if L0 has ≥4 SSTables OR L1 size > target. For Lk→L(k+1), pick file with most overlap. (~90 min)
  - **Why**: Victim selection determines write amp. RocksDB picks based on overlap ratio (fewer overlapping L(k+1) SSTs = less merge work) and age (older first, for fairness). The "most overlap" heuristic minimizes wasted I/O — compacting a victim that overlaps many L(k+1) SSTs blows up the read set; picking one that overlaps few is cheap.
  - *Back-of-envelope*: pick-victim runs every compaction tick (~10 Hz under steady write load). Per-tick budget ≤ **1 ms** to avoid stealing from foreground I/O credit. Score computation = scan all levels × per-level overlap ratio: at 7 levels × ~1000 SSTs/level × ~200 ns range-tree query = **~1.4 ms** — already over budget. The "score+rank" loop must amortize: cache per-level "compaction needed" score after each ingest; recompute only the level just mutated. Tiebreak by age: `AtomicU64` SST sequence numbers compare in **~1 ns**, no heap allocation. Critical: avoid `format!("level={}", k)` in the hot path — string formatting allocates and runs ~200 ns/call, blowing the tick budget at 7 calls/tick.
  - **Read first**: RocksDB `leveled_compaction_picker.cc::PickFileToCompact`.
  - **Build steps**:
    1. (~25 min) Per-level "needs compaction" score = level_size / level_target.
    2. (~30 min) Within candidate level, rank SSTs by overlap ratio = overlapping_L(k+1)_bytes / victim_bytes; pick lowest.
    3. (~25 min) Tiebreak by SST age (older first).
    4. (~10 min) Test: synthetic levels with crafted overlaps; verify victim choice.
  - **Pitfalls**:
    - *Always picking L0*: if L0 score is always highest, deeper levels starve. **Symptom**: data piles up at L2+ over time, read amp grows. **Fix**: rotate or weight scores so all levels get attention.
    - *Stale overlap estimate*: overlap measured against pre-compaction L(k+1); concurrent flush changes it. **Fix**: lock levels snapshot for the duration of pick→run.
    - **Expect to hit (perf) #1 — recompute scores from scratch every tick (bar (c) violation)**: pick-victim's "needs compaction" score per level is `level_size / level_target`; the naive impl iterates all SSTs in all levels every tick, summing `sst.file_size()` (each call ≈ 50 ns syscall-free metadata lookup). At 1000 SSTs × 7 levels × 50 ns = ~350 µs per tick — fine standalone, but during heavy compaction the scheduler ticks 100 Hz to react to flushes, pushing this to ~35 ms/sec of pure score recomputation. Symptom: scheduler CPU climbs to ~3-4% even when there's no compaction work to do (steady-state read load). Worse, the iteration takes the level read-lock, blocking flush.
      - Fix: **cached `AtomicU64` per-level size** updated by add/remove SST events; score lookup is one atomic load (~5 ns). Recompute only when the level mutates (add/remove SST → fetch_add/fetch_sub on the cached size). Per-tick cost drops from 350 µs to **~50 ns × 7 = 350 ns**.
      - Cost avoided: ~350 µs → ~350 ns = **~1000× speedup**; scheduler CPU drops to ~0.01% idle; no flush lock contention.
      - Muscle: "incremental maintenance over recomputation" — if a derived value changes on N events but is read M >> N times, update it eagerly on the writer not the reader. Reapplies at: W42 deadlock-detector edge counts, W74 matching-engine order-book depth-at-best-price, W95 mini-db level statistics.
- [ ] [NEW v2] **Build**: execute LCS: merge L0 files into L1; merge Lk file into overlapping L(k+1) files. (~60 min)
  - **Why**: Execute step is the I/O-heavy phase. For Lk→L(k+1) (k≥1), the workflow is: open victim SST + all overlapping L(k+1) SSTs as a merge stream; write output SSTs (sized to target); atomic manifest swap; delete inputs.
  - *Back-of-envelope*: execute is I/O-bound; **NVMe sequential read ≈ 3 GB/sec**, write ≈ 1-2 GB/sec, so a 256 MB victim + 2.56 GB overlapping L(k+1) = 2.8 GB read + 2.8 GB write ≈ **3-4 sec per compaction** (one task occupies one core + ~1 GB/sec disk). The merge inner loop is the hot path: per-KV `compare_keys` (~30 ns) + advance min-heap (~50 ns CAS-free single-thread) + write block-builder append (~100 ns). At 64-byte avg KV = ~50 M KVs over 3 sec = **~16 M KVs/sec/thread** — bounded by L2 cache pressure on the heap walk if heap size > 8 SSTs. The merge MUST NOT allocate per-KV (Vec<u8> for value copy ≈ 50 ns malloc + 30 ns free = 80 ns/op × 50M = 4 sec **of pure malloc**, doubling compaction time).
  - **Build steps**:
    1. (~20 min) Compute input set: victim + L(k+1) overlapping.
    2. (~25 min) MergeIterator over inputs; pump into chain of SstBuilders (split on target size).
    3. (~10 min) Atomic manifest update: remove inputs, add outputs.
    4. (~5 min) Verify L(k+1) key-disjoint invariant in debug builds.
  - **Pitfalls**:
    - *Output SST size drift*: forgetting to split at target_size produces giant L(k+1) files. **Fix**: SstBuilder enforces strict size cap.
    - *Manifest update partial*: removing inputs in one tx but adding outputs in another → window where data is unreachable. **Fix**: atomic record in manifest log.
    - **Expect to hit (perf) #1 — per-KV `Vec<u8>` value copy in merge (bar (c) violation)**: MergeIterator naively yields `(Key, Vec<u8>)` per step; SstBuilder takes owned Vec and copies into its block buffer. Two allocations per KV (the Vec from the input reader, the destructive append into builder block). At ~50 M KVs per compaction × 80 ns malloc/free per allocation = **4 sec of allocator overhead per compaction** — doubling compaction wall time and consuming ~25% of merge-thread CPU on `malloc_zone_*`/`free` (visible as the dominant allocator stack in `samply`).
      - Fix: zero-copy merge — yield `(&Key, &[u8])` borrowed from the mmap'd input block, copy directly into SstBuilder's reusable block buffer via `extend_from_slice`. Block buffer is a single 16 KB `Vec<u8>` reused across all KVs; flush+reset on block boundary. Zero per-KV allocation.
      - Cost avoided: ~4 sec → ~0 sec per compaction = **2× compaction throughput**; merge-thread CPU drops to ~75% I/O-wait + 25% real work (vs 50/25/25 with alloc); P99.9 ingest tail latency stays flat.
      - Muscle: "the hot path allocates zero" — borrow from input until the boundary forces a copy; reuse output buffers across iterations. Reapplies at: W42 OCC read-set serialization, W74 matching-engine MBO message construction, W77 messaging-aeron term-buffer writes, W80 ledger journal append.
