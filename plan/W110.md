**Thursday — Tuning pass: mini-db (bufpool capacity + WAL group-commit window)**

**Saturday — Saturation finder: where does matching-engine v1.0 break?**

- [ ] **Build**: `crates/matching-engine/benches/saturation_sweep.rs` — a rate-ramping saturation harness that drives the W106 synthetic feed into the engine at increasing order rates and locates the **breaking point** (the rate at which P99 leaves the SLA and queue depth runs away), recording the full latency-vs-rate curve. (~total 110 min across 3 phases)
  - 🔧 **Why this matters**: mirrors LMAX-Disruptor saturation/latency methodology. The naive "can it do 1M orders/sec?" question hides three traps that produce a *fantasy* breaking point: (1) **coordinated omission** — a closed-loop driver that waits for each response only ever measures service time, so it reports the engine "healthy" right up to the point it's actually 50× over SLA; (2) **open-loop without back-pressure accounting** — an unpaced driver saturates *itself* (the generator becomes the bottleneck) and you misattribute the cliff to the engine; (3) **single-rate sampling** — testing only at 1M/sec tells you pass/fail at one point, not *where the cliff is* or *how steep it is* (a soft knee vs a falling-off-a-table collapse have completely different operational headroom). First-attempt harnesses fail ≥1 test below and the debug session is the lesson. Downstream consumers: W111 Mon profiling runs *at* the sustained rate this finds is safe; W111 Thu's `single_symbol_p99.rs` reuses this harness's `spin_sleep` pacing core; W111 Fri's v1.1 tag cites the v1.0 saturation curve as the "before"; W92/W93 soaks use the located breaking point as the headroom budget.

  #### Phase 1 — Problem, prediction, design (~30 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/matching-engine/notes/110_saturation_prediction.md`:
    - P1: which driver shape you'd reach for first — write the exact loop (closed-loop `for msg { let r = engine.process(msg); record(r) }` vs open-loop paced producer + separate consumer). State the import you'd pace with (`std::thread::sleep` vs `spin_sleep::sleep` vs busy-spin on `time::now()`).
    - P2: predict the breaking-point rate for v1.0 (orders/sec) and the P99 *at* that rate (ns).
    - P3: predict what a *closed-loop* driver will report as the breaking point vs what the *true* (CO-corrected, paced) breaking point is — by what factor do they differ?
    - P4: predict the shape of the curve past the knee — soft (P99 climbs linearly) or hard (P99 hockey-sticks within a 5% rate increase)?
    - P5: list every Phase-2 test you predict your first attempt will fail. Compare to reality after the tests run.
  - *Mental model*: a saturation finder answers "where does it break and how badly", not "does it pass at rate X". It ramps the offered rate, measures CO-corrected service+wait latency at each step, and reports the rate where P99 crosses the SLA and where queue depth stops being bounded.
  - *Contract*: signature-level only —
    ```
    struct SweepConfig { start_rate: u64, step: u64, max_rate: u64, dwell: Duration, sla_p99_ns: u64 }
    struct RatePoint  { offered_rate: u64, achieved_rate: u64, p50_ns: u64, p99_ns: u64, p999_ns: u64, max_queue_depth: u64 }
    struct SweepResult { points: Vec<RatePoint>, knee_rate: u64, breaking_rate: u64 }
    fn run_sweep(engine: &mut MatchingEngine, feed: &mut SyntheticFeed, cfg: SweepConfig) -> SweepResult;
    ```
    Never the body.
  - *Back-of-envelope* (bar (c)): SLA P99 = 2µs/order. At 1M orders/sec the inter-arrival gap is 1000ns. Service time must sit well under that gap or the queue grows without bound (Little's law: a service time ≥ inter-arrival ⇒ unbounded wait). Pacing cost matters: `std::thread::sleep` has ~50-100µs granularity (useless for 1000ns gaps); `spin_sleep` busy-spins the tail to ~ns precision but burns a core. Recording cost matters: a `record()` that does `Vec::push` may `malloc` (~50ns) mid-measurement and pollute the sample — pre-size the histogram. The CO cliff: a closed-loop driver can report P99 = 1µs while the true paced P99 is 50µs+ once a burst queues — a **50× lie** (cold-vs-true ratio).
  - **Requirements** R1..R7 — write in `crates/matching-engine/notes/110_saturation_design.md`:
    - R1. Open-loop driver: a producer paces offered orders to `offered_rate` with `spin_sleep`; a separate path measures each order's *end-to-end* latency (enqueue timestamp → completion timestamp), NOT just `process()` service time.
    - R2. Coordinated-omission correction: latencies recorded via `hdrhistogram::record_corrected_with_max_interval(dt, expected = 1e9/offered_rate)` so a queued burst inflates the tail correctly.
    - R3. Per-rate dwell ≥ a configured `dwell` (default 10s) AFTER a warmup phase; the first `warmup` samples per rate are discarded.
    - R4. The harness records `achieved_rate` per step and flags any step where `achieved_rate < 0.95 × offered_rate` as *driver-bound* (the generator, not the engine, saturated) — those points are excluded from breaking-point logic with an explicit warning.
    - R5. `knee_rate` = the highest rate where P99 ≤ SLA; `breaking_rate` = the first rate where P99 > SLA *or* `max_queue_depth` grows monotonically across the dwell (runaway).
    - R6. Histogram is pre-sized (no `malloc` during the measured window); the recording path is allocation-free (verified by a counting allocator test).
    - R7. The full `SweepResult` is emitted as JSON (`bench/saturation_v1.0.json`) with the seed, rig state, and the curve, for W111/v1.1 comparison.
  - **Design walk-through** D1..D7 — answer in the design doc; no peeking at the Disruptor latency note until Phase 3:
    - D1. Primitive table: closed-loop vs open-loop vs replay-trace driver — columns: measures-queue-wait? back-pressure-honest? rate-accurate? simple? Pick open-loop and justify.
    - D2. Pacing primitive table: `thread::sleep` / `spin_sleep::sleep` / busy-spin on `time::now()` / token-bucket — columns: granularity, core-burn, jitter. Pick `spin_sleep` and state its cost.
    - D3. Why CO-correction changes the *breaking point* and not just the P99 number — show the rate at which an uncorrected curve and a corrected curve diverge.
    - D4. How `achieved_rate < offered_rate` is detected and why excluding driver-bound points is *required* (else you report the generator's limit as the engine's).
    - D5. Knee vs breaking-point: define both precisely; argue why ops needs the *knee* (headroom budget) more than the breaking-point (the cliff edge).
    - D6. **Pre-mortem (load-bearing):** write the exact 5-line bad trace where (a) you use a closed-loop driver, (b) it waits for each response so it self-paces to service-time, (c) the curve looks flat at P99=1µs up to 2M/sec, (d) production at 1M/sec sees P99=50µs because real arrivals don't wait, (e) you ship a 2× wrong headroom number. Convince yourself R1 + R2 prevent it.
    - D7. **Anti-shortcut audit:** the "obvious" reaches — `criterion`'s default `b.iter` (runs as-fast-as-possible, no rate control), `std::thread::sleep` for pacing (50µs granularity), `hist.record` (uncorrected), `Vec<u64>` of raw samples + sort-and-index for P99 (allocates + O(n log n) per query). One line each on why each is wrong HERE.
  - **Output**: `crates/matching-engine/notes/110_saturation_design.md` with R1..R7, D1..D7, the bad-interleaving sketch and the open-loop vs closed-loop divergence diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~30 min)
  Newbie failures first, expert last.

  - **(NEWBIE) When `knee_below_breaking_rate` reports `knee == breaking`:**
    - Symptom: both fields equal the same rate; the curve has no headroom band.
    - Why: knee was computed as "first rate where P99 > SLA" — the same predicate as breaking — instead of "last rate where P99 ≤ SLA".
    - Fix: `knee_rate = points.iter().rev().find(|p| p.p99_ns <= sla).map(|p| p.offered_rate)`; breaking is the *next* step up.
    - Cost avoided: shipping a headroom budget of 0 to W92/W93 soaks — the soak would run at the cliff edge and false-alarm constantly.
    - Muscle: knee and cliff are different operational quantities; define each by its own predicate. Reapplies at: W111 Thu P99 acceptance gate, W113 PR-review headroom checks.

  - **(SENIOR) When `paced_rate_within_5pct_of_offered` reports achieved = 18k/sec at offered = 500k/sec:**
    - Symptom: the harness can't reach the offered rate; achieved is ~28× too low.
    - Why: pacing used `std::thread::sleep(gap)` where `gap ≈ 2µs`, but `thread::sleep` has ~50-100µs granularity on Linux, so each "2µs" sleep is actually ≥ 50µs → max ~18k/sec.
    - Fix: pace with `spin_sleep::sleep(gap)` (busy-spins the sub-ms tail to ns precision) or a busy-spin on `time::now()` for the final microseconds.
    - Cost avoided: reporting the *generator's* 18k/sec ceiling as the *engine's* breaking point — a wrong-by-50× operational number.
    - Muscle: sub-millisecond pacing requires spin-sleep, never `thread::sleep`; check granularity before trusting a rate. Reapplies at: W111 Thu bench pacing core, W106 synthetic feed rate control.

  - **(SENIOR) When `closed_loop_vs_open_loop_diverge_past_knee` shows they AGREE (both P99 = 1µs at overload):**
    - Symptom: open-loop and closed-loop report the same flat P99 even at 2× the engine's service ceiling — the test fails because they don't diverge.
    - Why: the "open-loop" driver still awaited each response before submitting the next (it was secretly closed-loop), so it self-paced to service time and never queued a burst — classic coordinated omission.
    - Fix: decouple producer and consumer — the producer submits at `offered_rate` *regardless* of completions; latency is measured from the producer's enqueue timestamp, not from the consumer's dequeue. Now an overloaded engine lets the queue (and measured wait) grow.
    - Cost avoided: a 50× understated tail (1µs reported vs 50µs real) — quoting it in the v1.1 blog would be falsified by the first production trace. (bar (c) violation: a CO-blind latency claim disqualifies the matching-engine's bar.)
    - Muscle: open-loop latency = enqueue→complete measured independent of completion pacing; if your driver waits, it lies. Reapplies at: W111 Thu `single_symbol_p99.rs`, W120 production SLO measurement, W113 PR-review benches.

  - **(SENIOR) When `sweep_uses_corrected_recording` finds bare `record()`:**
    - Symptom: harness calls `hist.record(dt)`; curve looks flat far past the true knee.
    - Why: without CO-correction, a 5ms burst that queues 5000 orders records each at ~1µs service time and never accounts for the 5ms wait of the last one.
    - Fix: `hist.record_corrected_with_max_interval(dt, 1_000_000_000 / offered_rate)`; HdrHistogram synthesizes the missing samples for gaps exceeding the expected interval.
    - Cost avoided: the same 50× tail understatement, this time hidden inside a histogram that *looks* rigorous.
    - Muscle: any latency histogram fed under offered-rate load must use corrected recording. Reapplies at: W111 Thu bench, W120 SLO, W113 bench review.

  - **(SENIOR) When `driver_bound_steps_excluded` lets a generator-saturated step set the breaking point:**
    - Symptom: `breaking_rate` lands at exactly the rate where `achieved_rate` flatlined, even though P99 was still fine.
    - Why: breaking-point logic looked only at P99/queue and ignored that the *generator* couldn't keep up (achieved ≪ offered), so the generator's ceiling masqueraded as the engine's.
    - Fix: tag steps with `achieved_rate < 0.95 × offered_rate` as `driver_bound`, exclude them from knee/breaking computation, and emit a warning telling the operator to add generator cores.
    - Cost avoided: under-reporting engine capacity (claiming the engine breaks at the generator's limit) — leaves real headroom on the table and mis-sizes the soak.
    - Muscle: always separate "system under test saturated" from "load generator saturated"; check achieved-vs-offered every step. Reapplies at: W92/W93 soak harness, W111 Mon profiling load setup.

  - **(EXPERT) When `recording_path_is_allocation_free` reports 1,000,000 allocations:**
    - Symptom: counting allocator shows one `malloc` per recorded sample inside the measured window.
    - Why: samples were pushed into a `Vec<u64>` that re-allocated as it grew (and/or per-step `format!` for a debug log), so a ~50ns `malloc` landed in the middle of the latency measurement, fattening the tail it was trying to measure.
    - Fix: pre-size the HdrHistogram once (`Histogram::new_with_bounds(1, 60s_in_ns, 3)`), record directly into it (no intermediate Vec), and move all formatting/JSON-emit outside the measured window.
    - Cost avoided: ~50ns × (alloc frequency) injected into every sample — a self-inflicted tail that makes a healthy engine look broken (bar (c) violation: a measurement that allocates can't certify a zero-alloc hot path).
