**Wednesday — Build: incremental state root (Phase 1 + Phase 2)**

- [ ] **Build**: `crates/storage-trie/src/incremental_root.rs` — recompute the state root from a per-block changeset, re-hashing only dirty subtrees, byte-identical to a from-scratch root. (~total 300 min across 3 phases; Phase 1+2 today ~150 min, Phase 3 Thursday ~150 min)
  - 🔧 **Why this matters**: this mirrors `reth-trie`'s `IntermediateStateRootCalculator` — the single hottest computation in the node, run on EVERY block. A from-scratch root over ~250M mainnet accounts is O(N) keccaks (~10s); the changeset version touches only dirty subtrees (~50ms). Four traps make a naive first attempt WRONG, not just slow: (1) **dirty-set under-propagation** — you re-hash the dirty leaf but forget every ancestor up to the root must also re-hash, so the root is stale; (2) **sibling-hash staleness** — you cache a branch node's hash but a deep descendant changed under a *different* child, and you serve the stale cached parent; (3) **deletion ≠ zero** — a tombstone must COLLAPSE the branch (remove the child, possibly demote branch→leaf via extension merge), not store an empty value; (4) **canonical emission order** — the hash builder must receive paths in sorted nibble order or RLP framing differs and the root diverges. Each of (1)-(3) yields a root that is byte-wrong = a consensus split, not a perf bug. Downstream: storage-trie hot path (W43-44 v1.0), W42 `txn` emits this changeset, W91 `consensus-engine` STF re-derives and compares this exact root.

  - *Mental model*: an incremental root is a *fold up the trie* — start from the dirty leaves, recompute each ancestor branch hash using the (possibly cached) hashes of its 16 children, stop at the root. Unchanged subtrees contribute cached hashes; the saving is "don't re-keccak the 99.9% that didn't move."
  - *Contract* (signatures only — NEVER the body):
    ```rust
    pub struct IncrementalRoot<'a, S: TrieStorage> {
        prior_root: B256,
        // path -> Some(new account) | None (tombstone/delete)
        changeset: &'a BTreeMap<Nibbles, Option<Account>>,
        storage: &'a S,
    }
    impl<'a, S: TrieStorage> IncrementalRoot<'a, S> {
        pub fn new(prior_root: B256, changeset: &'a BTreeMap<Nibbles, Option<Account>>, storage: &'a S) -> Self;
        /// Byte-identical to StateRoot::from_scratch(post_state). Re-hashes only dirty subtrees.
        pub fn compute(&self) -> B256;
    }
    // upstream contract the storage must satisfy:
    pub trait TrieStorage {
        fn node(&self, path: &Nibbles) -> Option<TrieNode>; // cached child hash lookup
        fn account(&self, path: &Nibbles) -> Option<Account>;
    }
    ```
  - *Back-of-envelope* (bar (b), informational): one keccak ≈ ~200 ns (32-byte input). Full root over 1M leaves ≈ 1M leaf-keccaks + ~70k internal-node keccaks ≈ ~210M ns ≈ 0.21s; mainnet at 250M accounts ≈ ~50s. A changeset of 1k dirty leaves at depth ~7 touches ≤ 1k·7 ≈ 7k internal recomputes + 1k leaf hashes ≈ ~8k keccaks ≈ ~1.6 ms. Cliff ratio: ~50s vs ~1.6ms ≈ **30000×** — but ONLY if sibling hashes are reused from cache; one accidental full-subtree walk per dirty leaf erases the win (becomes O(N) again). The number to protect is "keccaks per block ∝ dirty leaves, not total leaves."
  - **Requirements** R1..R7 — write in `crates/storage-trie/notes/35_incremental_root_design.md`:
    - R1. `compute()` is **byte-identical** to a from-scratch root computed over the full post-state. This is the consensus contract.
    - R2. A path is re-hashed iff its subtree contains ≥1 dirty descendant (or is itself dirty). No unchanged subtree is re-hashed.
    - R3. The dirty set propagates to the ROOT: every ancestor of every dirty leaf is marked dirty and re-hashed (post-order).
    - R4. `None` (tombstone) DELETES the leaf and collapses the structure: a branch left with one child demotes to an extension/leaf; an empty branch is removed.
    - R5. Sibling (non-dirty) child hashes are read from the cache (`TrieStorage::node`), never recomputed.
    - R6. Nodes are emitted to the hash builder in canonical **sorted nibble order**; RLP framing of branch/extension/leaf matches the Yellow Paper.
    - R7. Empty changeset ⇒ `compute() == prior_root` exactly (no work, no drift).
  - **Design walk-through** D1..D6 — answer in the design doc; no peeking at `reth-trie` source until Phase 3:

    - D3. Walk the post-order fold for a concrete 3-leaf example: leaves at paths `0x1a`, `0x1b`, `0x2c`; mark dirty `0x1a`; show which branch nodes re-hash and which serve cached hashes.

Write the 4-5 line trace.
    - D5. **Pre-mortem #2 (deletion)** — write the trace where deleting the second-to-last child of a branch must trigger extension-merge: branch with children at nibbles 3 and 7; delete 7; branch now has one child → must collapse to `Extension(3) -> child` (or merge nibbles). Show the root that results vs the buggy "leave an empty 16-slot branch" root.
    - D6. **Anti-shortcut audit:** name the obvious reach for each motivation and one line why it's wrong HERE:
      - "Just recompute from scratch, it's simpler" → O(N) per block, 30000× too slow; the whole point is to NOT.
      - "Cache the prior root's branch hashes wholesale and only redo leaves" → violates R3/D4; ancestors of dirty leaves are stale.

  - 🧮 **Paper drill** — write in `crates/storage-trie/notes/35_incremental_root_drill.md`:
    - D-WALK on a 4-leaf MPT with leaves at paths `0x1a`, `0x1b`, `0x2c`, `0x2d` and a 2-key changeset `{0x1a → acct(7), 0x2c → acct(9)}`: hand-trace the incremental re-root — mark the dirty leaves, walk each up to the root collecting the ancestor branch nodes that re-hash (branch `0x1`, branch `0x2`, root), serve the cached hash for every untouched sibling (`0x1b`, `0x2d`), then independently re-hash the FULL post-state trie from scratch and show the two 32-byte roots are byte-identical. - [ ] **Build (Phase 3)**: make the W35 tests pass, one failure at a time. Ordered failure cards, newbie first. (~150 min)

  - **(NEWBIE) When `from_scratch_oracle_is_real` part-2 reports `compute() returned prior_root for a real change`:**
    - Symptom: `assert_ne!` fails — a non-empty changeset produced no root movement.
    - Why: `compute()` is still a stub returning `self.prior_root`; you wired nothing.
    - Fix: actually fold: load the dirty leaves, mark ancestors dirty, re-hash post-order.
    - Muscle: a negative-control catches the stub BEFORE the fuzz test lulls you (an identity stub passes `empty_changeset_is_identity`). Reapplies at: W37 lsm-core compaction (test-the-test the merged SSTable actually merged), W74 matching-engine fill (a no-op match must fail a control).

  - **(SENIOR) When `incremental_matches_from_scratch_100_changesets` diverges and the root is stale-high-up:**
    - Symptom: leaves correct, but root differs; the divergence is at a branch several levels ABOVE a dirty leaf.
    - Why: **dirty-set under-propagation** — you re-hashed the dirty leaf and its immediate parent but stopped; ancestors further up kept their prior cached hash (violates R3).
    - Fix: mark dirty up to the root — for every dirty path, insert all its proper prefixes into the dirty set; recompute strictly post-order so a parent never hashes before its changed children.
    - Muscle: a hash fold is only correct if dirtiness propagates to the ROOT; "recompute the leaf" is half the job. Reapplies at: W37 lsm-core level-merge (a merged key dirties its index block AND the manifest), W91 STF (a changed account dirties the state root all the way up).

  - **(SENIOR) When `unordered_changeset_still_canonical` reports `a != b`:**
    - Symptom: the same dirty paths in different insertion order yield different roots.
    - Why: you fed the hash builder in iteration order; branch/extension RLP framing depends on emission order (violates R6).
    - Fix: drive emission from a `BTreeMap`/sorted key list so the builder always sees nibble-sorted paths; the changeset container's order must NOT reach the builder.
    - Muscle: canonical encoding means the OUTPUT must be order-independent of the INPUT container — sort before you emit. Reapplies at: W36 snapshot file (entries written in canonical order), W37 SSTable (sorted-run invariant), W42 txn commit (deterministic apply order).

  - **(EXPERT) When `sibling_staleness_two_dirty_under_one_branch` diverges:**
    - Symptom: single-dirty-child cases pass; two-dirty-children-under-one-branch fails at exactly that branch.
    - Why: **sibling-hash staleness** — recomputing the branch, you read BOTH children's hashes from the cache, but both children were themselves dirtied this block, so the cache holds last-block hashes (violates R5/D4).
    - Fix: a branch reads a child's hash from cache ONLY if that child is not in the dirty set; for dirty children, use the freshly recomputed hash. Post-order traversal guarantees the fresh hash exists before the parent runs.
    - Muscle: "reuse the cached sibling hash" is correct only for NON-dirty siblings; a dirty child invalidates the cache for that slot. Reapplies at: W37 lsm-core (a recompacted child block invalidates its parent index entry), W43 storage-trie v1.0 multi-account batch, W91 STF batched account updates.

  - **(EXPERT) When `deletion_collapses_branch_to_extension` diverges:**
    - Symptom: updates and additions match from-scratch; any changeset with a deletion that empties a branch slot diverges.
    - Why: **deletion ≠ zero / no structural collapse** — you removed the leaf value but left a 16-slot branch with one remaining child (or stored `None` as an empty value), so the structure differs from a from-scratch trie which would emit an extension/leaf (violates R4/D5).
    - Fix: after applying a tombstone, if a branch is left with a single child, merge nibbles and demote branch→extension (or branch→leaf at the boundary); a fully-emptied branch is removed and its parent slot freed, propagating the collapse upward.
    - Muscle: trie deletion is STRUCTURAL — collapsing single-child branches is part of canonical form, not an optimization. Reapplies at: W36 snapshot rebuild (deleted accounts absent, not zeroed), W43 storage-trie v1.0 pruning, W100 mini-db tombstone compaction.

  - **(perf, bar (b)) When `criterion: incremental_beats_scratch` shows incremental ≈ scratch time:**
    - Symptom: bench shows no speedup; the node-cache hit/miss assertion shows misses ≈ total internal nodes.
    - Why: you walk the WHOLE trie to find dirty paths (a full DFS) instead of jumping straight to the dirty paths via the changeset keys — the traversal, not the hashing, went O(N).
    - Fix: iterate the changeset's sorted keys and descend ONLY those paths, collecting ancestors as you go; never enumerate non-dirty subtrees.
    - Cost avoided: a full DFS over 1M nodes ≈ 1M `TrieStorage::node` lookups (~70M ns at ~70ns/lookup) vs ~8k for the dirty paths — restores the ~30000× cliff the back-of-envelope promised; without it the "incremental" root is O(N) and the bar-(b) bench-regression CI would flag it.
    - Muscle: "incremental" must be incremental in the TRAVERSAL too, not just the hashing — drive from the changeset keys, never scan. Reapplies at: W37 lsm-core compaction (merge only overlapping ranges), W74 matching-engine (touch only the crossed price levels).

  - **5-year failure mode** (write in `crates/storage-trie/notes/35_incremental_root_followup.md` after green): when Ethereum migrates to Verkle (EIP-7864), keccak-on-MPT branches give way to a Pedersen vector commitment; the sibling-hash cache becomes a per-node commitment delta (`C' = C + (new-old)·G_i`) and deletion no longer collapses structure (256-ary, sparse). Measurable TRIGGER: the fork block where the state root algorithm switches; the from-scratch oracle must be re-derived against the Verkle reference. Migration: keep `IncrementalRoot`'s changeset-driven traversal (it transfers), swap the per-node combine function and drop the structural-collapse path.
