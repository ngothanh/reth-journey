**Wednesday — Crate: incremental root**

- [ ] Design incremental state root computation. (~30 min)
  - **Why**: A full state root recomputation over millions of accounts is O(N log N) and unworkable per block. Reth/geth maintain a *changeset* of dirty paths from the prior block and recompute only those subtrees, reusing the unmodified subtree hashes. This is the difference between a 10s recompute and a 50ms one.
  - **Read first**: `reth/crates/trie/trie/src/trie.rs::IntermediateStateRootCalculator` and the changeset application logic.
  - **Design**:
    ```rust
    pub struct IncrementalRoot {
        prior_root: B256,
        changeset: BTreeMap<Nibbles, Option<AccountChange>>, // path -> new value or tombstone
    }
    impl IncrementalRoot {
        pub fn compute(&self, storage: &impl TrieStorage) -> B256;
    }
    ```
    **Invariants**:
    - Result is byte-identical to a from-scratch root computation over the post-state.
    - Only paths whose subtree contains a dirty descendant are re-hashed.
  - **Build steps**:
    1. (~10 min) Walk dirty paths in sorted order; reuse cached child hashes for non-dirty siblings at each branch.
    2. (~10 min) Hash-builder feed: emit modified nodes in canonical order.
    3. (~10 min) Sanity test vs from-scratch: must match.
  - **Pitfalls**:
    - *Stale cached hash*: if you cache a node hash but a deeper descendant changed without invalidating the cache, the cached hash is wrong. **Symptom**: root diverges. **Fix**: invalidate cache by post-order propagation up from every dirty leaf.
  - **Test scenarios**: full vs incremental match across 100 random changesets.
  - **Acceptance**: 50x speedup on changesets ≤1% of trie size.
  - **Downstream**: storage-trie hot path on every block; W42 (txn commit emits changeset).
