**Monday — mini-db: linearizability checker + proptest oracle**

- [ ] **Build**: `crates/mini-db/tests/lin_checker.rs` + `crates/mini-db/tests/proptest_lin.rs` — a Wing-Gong linearizability checker plus the proptest oracle that feeds it random histories. (~135 min across 3 phases)
  - 🔧 **Why this matters**: mirrors Jepsen `knossos`/`elle` and Lowe's Wing-Gong tree search — the *only* evidence that lets you write "linearizable" on a résumé without lying. The four traps that bite a first attempt: (1) you check a *sequential trace against a HashMap* and call it linearizability — it is not, it proves nothing about concurrent histories; (2) you assume a single legal order exists, but a concurrent history has a *set* of legal linearizations and your checker must search them; (3) the HashMap model drifts from mini-db's real tombstone/MVCC semantics and you get false failures; (4) HLC timestamp ties make the "expected" order non-deterministic. Downstream: W104 vector-db reuses this checker for its segment-merge history; W112 blog cites it. A first attempt fails ≥2 tests below and the debug session IS the lesson.

  #### Phase 1 — Problem, prediction, design (~35 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `notes/100_lin_checker_prediction.md`:
    - P1: the exact checker entry point you'd reach for (`fn is_linearizable(history: &[Event], spec: impl Fn(&Op, &mut Model) -> Ret) -> bool` vs "just replay into a HashMap") and which std/crate types you'd import.
    - P2: predicted worst-case checker cost for a 200-op concurrent history (states explored) and whether it can blow up exponentially.
    - P3: predicted outcome of `lin_checker_rejects_stale_read` on a *naive sequential* replay — does it even fire?
    - P4: predict whether your HashMap model handles a `Delete` followed by a compaction (tombstone) the same way mini-db does.
    - P5 = list every Phase-2 test you predict your first attempt will fail. Compare to reality after tests run.
  - *Mental model*: a **history** is a list of overlapping `(invoke, ok/return)` events from N threads. A history is **linearizable** iff there exists a total order of the ops, consistent with real-time non-overlap, that a single-threaded sequential spec accepts. The checker *searches* for such an order (Wing-Gong: pick a minimal op, apply to model, recurse, backtrack). A HashMap-replay of a *sequential* trace tests nothing concurrent.
  - *Contract*: `enum Op { Put(u32,u32), Get(u32), Delete(u32) }`; `enum Ret { Unit, Val(Option<u32>) }`; `struct Event { thread: u8, op: Op, ret: Option<Ret>, t_invoke: u64, t_return: u64 }`; `fn is_linearizable(hist: &[Event]) -> Result<(), Counterexample>`; sequential spec is `HashMap<u32,u32>` applying Put/Delete and returning the read for Get.
  - *Back-of-envelope*: a concurrent history of n ops with k overlapping at any point → Wing-Gong explores up to k! orderings per frontier; for n=200, k≤4 keep it ~24 per step → tractable. If you DON'T bound concurrency (k=20) the search is 20! ≈ 2.4e18 → never finishes. So: bound to 4 threads × short windows. (bar (b): correctness-first; no ns budget required.)
  - **Requirements** R1..R6 — write in `notes/100_lin_checker_design.md`:
    - R1: checker accepts a concurrent history and returns Ok iff some legal linearization exists, else a `Counterexample` with the prefix that has no legal extension.
    - R2: real-time order is respected — if op A returns before op B is invoked, A precedes B in every candidate linearization.
    - R3: the sequential spec replicates mini-db's exact semantics: Put overwrites, Delete makes Get return None, Get returns last Put's value or None.
    - R4: tombstone-after-compaction must NOT change observable Get semantics (W98 invariant: tombstone GC respects `min_active_snapshot_ts`).
    - R5: HLC ties are broken deterministically by the logical counter, so the *checker* never depends on wall-clock tie order.
    - R6: proptest generates 4-thread histories on disjoint-and-overlapping key ranges, ≥1000 cases, soak via `MINIDB_LIN_CASES`.
  - **Design walk-through** D1..D5 — answer in the design doc; no peeking at `knossos` source until Phase 3:
    - D1: property table — primitive vs (proves concurrency? searches orders? backtracks? cost):
      | approach | concurrency? | searches orders? | backtracks? | cost |
      |---|---|---|---|---|
      | replay seq trace into HashMap | NO | no | no | O(n) |
      | sort by t_invoke, replay | NO (drops overlap freedom) | no | no | O(n log n) |
      | Wing-Gong tree search | YES | yes | yes | up to k! per frontier |
    - D2: enumerate where the naive HashMap replay silently passes a non-linearizable system (it can't see reorderings, so it accepts a stale read that a real checker rejects).
    - **D3. Pre-mortem (load-bearing):** write the EXACT 5-line bad history that a HashMap-replay accepts but a real checker rejects. Sketch:
      ```
      t0  T1 invoke Put(k,1)         t_invoke=0
      t1  T2 invoke Get(k) -> 0      t_invoke=1 t_return=2   (read OLD value)
      t2  T1 return Put ok           t_return=3
      // Put and Get overlap; Get returned 0 (pre-Put). Legal: linearize Get before Put. OK.
      // Now flip: T2 Get -> 1 at t_return=2 while T3 Get -> 0 at t_return=4 (later) => NO legal order. REJECT.
      ```
      If you can't write the rejected history, you can't prove your checker rejects it — that's the point.
    - **D4. Anti-shortcut audit:** "just use a HashMap and replay in invoke order" → wrong: it imposes ONE order and ignores that overlapping ops may legally reorder; it both false-passes and false-fails. "just sort by HLC ts" → wrong: HLC gives a *plausible* order, not the *only* legal one; a system can be linearizable to a different order.
    - D5: bound the search — cap overlap window to 4 concurrent ops; if frontier > 6, fail the *test config* (too wide to check), not the system.
  - **Output**: `notes/100_lin_checker_design.md` with R1..R6, D1..D5, the rejected-history sketch; `notes/100_lin_checker_prediction.md` sealed.

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)
  Ordered failure cards — newbie first, expert last.
  - **(NEWBIE) When `lin_checker_rejects_stale_read` reports `assert is_err()` failed (checker returned Ok):**
    - Symptom: the checker accepted a Get that returned a value older than a Put which committed before the Get was invoked.
    - Why: you wrote a HashMap-replay, not a linearizability checker — it never considers real-time order between non-overlapping ops, so it can't detect a stale read.
    - Fix: replace replay with Wing-Gong search that enforces R2 (a returned-before-invoked op must precede in every candidate order); a non-overlapping stale read then has no legal linearization.
    - Muscle: "replay into a model" proves sequential consistency of one order, never linearizability of a concurrent history. Reapplies at: W104 vector-db segment-merge history check, W108 ops-chaos invariant checker.
  - **(SENIOR) When `lin_checker_accepts_real_concurrent_history_rejects_tampered` rejects the REAL history:**
    - Symptom: a genuine mini-db run is reported non-linearizable.
    - Why: the sequential spec model drifted — e.g. it returns the *first* Put on a key instead of the *last-linearized* one, or it doesn't model overwrite.
    - Fix: make the spec model apply each op in the candidate order and return the model state at that point; Put overwrites, Get returns current, Delete clears (R3) — one rule per line, cited from DESIGN.md.
    - Muscle: a linearizability checker is only as correct as its sequential oracle; the oracle must match the system rule-for-rule. Reapplies at: W104 vector-db oracle, W108 chaos oracle.
  - **(SENIOR) When `lin_checker_respects_tombstone_under_active_snapshot` reports `Some(v) != None`:**
    - Symptom: snapshot read after delete+compaction observes None.
    - Why: the model deleted the key on `Delete`, ignoring that an active snapshot pins `min_active_snapshot_ts` so the pre-delete version is retained (W98).
    - Fix: model snapshot reads against the version visible at the snapshot's ts, not the latest; compaction must not drop a version below `min_active_snapshot_ts`.
    - Muscle: MVCC visibility is a function of (key, snapshot_ts), never "latest"; a model that forgets the snapshot ts will false-fail. Reapplies at: W104 vector-db snapshot reads, W72 txn 2PC visibility.
  - **(EXPERT) When `lin_checker_hlc_ties_deterministic` reports the verdict flips run-to-run:**
    - Symptom: same history yields Ok on some runs, Err on others.
    - Why: two ops share a physical HLC ts and your tie-break used `HashMap` iteration / wall clock instead of the HLC logical counter, so the candidate order is non-deterministic.
    - Fix: total-order events by `(physical_ts, logical_counter, thread_id)`; the logical counter is monotonic per the HLC contract (W6 time crate), removing the tie.
    - Muscle: any test that orders by a clock must use the *full* logical clock tuple, never the physical component alone. Reapplies at: W104 vector-db HLC ordering, W67 raft log-ts ordering.
  - **(EXPERT) When `proptest_checker_catches_injected_corruption` reports `caught < 950`:**
    - Symptom: the checker waves through corrupted histories.
    - Why: the search returns Ok on the *first* frontier that has any legal child instead of requiring the *whole* history to linearize; an early greedy match hides a later contradiction.
    - Fix: Wing-Gong must succeed only when the ENTIRE history is consumed; on a dead-end, backtrack and try the next minimal op before declaring Ok.
    - Muscle: a search-based checker that doesn't backtrack to completion is a false-positive generator — always pair it with an injected-corruption negative control. Reapplies at: every property-based correctness proof from W100 on (W104, W108).

      T_gc:   load min_ts (Relaxed) -> reads stale 5
      T_begin: store min_ts = 9 (Relaxed)  // new floor, but reordered after T_gc's load

    - Symptom: under some interleaving the active count stays > 0 after all snapshots drop.
    - Why: `Snapshot::drop` decrements with a non-atomic read-modify-write (load + store, not `fetch_sub`), so a concurrent begin's increment is lost.
    - Fix: use `fetch_add`/`fetch_sub` (a single atomic RMW) for `active_count`, never load-then-store.
    - Muscle: a count touched by multiple threads is a `fetch_*` RMW, never load+store — loom finds the lost update instantly. Reapplies at: W104 segment refcount, W67 raft term counter.
  - **(EXPERT) When `loom_txn_gc_never_prunes_live_version` reports `observed_floor > live ts`:**
    - Symptom: GC reads a `min_active_snapshot_ts` higher (or staler-low, per direction) than the live snapshot's floor.
    - Why: `min_active_snapshot_ts` is published with `Relaxed`, so the GC thread's load can be reordered before the begin's update — the D3 interleaving.
    - Fix: publish the floor with `Release` and have GC load it with `Acquire`; this establishes happens-before so GC never observes a floor that excludes a live snapshot.
    - Muscle: any value that gates a destructive action (GC/prune/free) across threads needs Release/Acquire, never Relaxed — Relaxed is for counters whose exact value never gates safety. Reapplies at: W104 vector-db segment GC, W30 recovery checkpoint pruning, epoch-gc reclaim (Layer-1).
  - **(EXPERT) When `loom_txn_commit_invisible_to_older_snapshot` reports the older snapshot saw the commit:**
    - Symptom: a snapshot taken before a commit observes the committed value.
    - Why: visibility compares `commit_ts <= snapshot_ts` with the wrong operator, or `commit_now` assigns a ts ≤ an existing snapshot's ts (clock not advanced before commit).
    - Fix: enforce `commit_ts = clock.tick()` strictly greater than any handed-out snapshot ts; visibility predicate is `version.commit_ts <= snap.ts` (strict for the boundary).
    - Muscle: MVCC isolation is a strict ts comparison with a strictly-advancing clock; an off-by-one in the comparator silently breaks snapshot isolation. Reapplies at: W104 vector-db MVCC reads, W72 txn 2PC commit ordering.

  ```rust
  // tests/chaos.rs
  // (SENIOR) The core durability invariant: only Ok-committed puts must survive.
  #[test]
  fn chaos_no_lost_committed_write() {
      let cluster = TestCluster::new_3_nodes().unwrap();
      let client = cluster.client();
      let writer = std::thread::spawn({ let c = client.clone(); move || {
          for i in 0..10_000u32 { let _ = c.put(&i.to_le_bytes(), &i.to_le_bytes()); } // may Err on leader change
      }});
      std::thread::sleep(std::time::Duration::from_millis(500));
      cluster.kill_leader();
      std::thread::sleep(std::time::Duration::from_millis(200));
      cluster.restart_killed();
      writer.join().unwrap();
      cluster.wait_converged(std::time::Duration::from_secs(30)).unwrap();
      for (k, v) in client.successful_puts() {       // ONLY Ok-committed
          assert_eq!(cluster.get(&k).unwrap().as_deref(), Some(v.as_slice()),
              "lost or torn a committed write {k:?}");
      }
  }

  // (EXPERT) Anti-shortcut trap: a put that returned Err(Timeout) may STILL be committed (D3 trace).
  // A test that asserts "Err => absent" must FAIL; this test proves we do NOT make that assertion.
  #[test]
  fn chaos_err_put_is_not_asserted_absent() {
      let cluster = TestCluster::new_3_nodes().unwrap();
      cluster.fail_point("after_commit_before_apply", "1*off->panic"); // crash after commit, before ack
      let client = cluster.client();
      let r = client.put(b"k", b"v");                 // returns Err(Timeout) but raft committed
      assert!(r.is_err());
      cluster.restart_killed();
      cluster.wait_converged(std::time::Duration::from_secs(30)).unwrap();
      // The key IS present — proving that asserting "Err => absent" would be a false failure.
      assert_eq!(cluster.get(b"k").unwrap().as_deref(), Some(b"v".as_slice()));
      assert!(!client.successful_puts().iter().any(|(k,_)| k == b"k"),
          "an Err'd put must NOT be in successful_puts()");
  }

  // (NEWBIE) Negative-control: failpoint teardown actually clears. After a test that sets a failpoint,
  // a fresh cluster must have NO active failpoints.
  #[test]
  fn chaos_failpoints_cleared_between_tests() {
      { let c = TestCluster::new_3_nodes().unwrap(); c.fail_point("before_append_wal", "panic"); drop(c); }
      let c2 = TestCluster::new_3_nodes().unwrap();
      assert!(c2.active_failpoints().is_empty(),
          "failpoint leaked across cluster instances -> next test runs against corrupted state");
  }

  // (SENIOR) Convergence is event-driven, not time-driven: under partition then heal, commit-index
  // must equalize across all 3 nodes (not just "sleep 2s and hope").
  #[test]
  fn chaos_converges_after_partition() {
      let cluster = TestCluster::new_3_nodes().unwrap();
      let client = cluster.client();
      cluster.partition(/*peer*/2, std::time::Duration::from_millis(200));
      for i in 0..1_000u32 { let _ = client.put(&i.to_le_bytes(), &i.to_le_bytes()); }
      cluster.wait_converged(std::time::Duration::from_secs(30)).unwrap();
      let idxs = cluster.commit_indices();
      assert!(idxs.iter().all(|&x| x == idxs[0]), "commit-index diverged across nodes: {idxs:?}");
  }
  ```

  #### Phase 3 — Make the tests pass, one failure at a time (~40 min)
  - **(NEWBIE) When `chaos_failpoints_cleared_between_tests` reports a leaked failpoint:**
    - Symptom: a fresh cluster reports an active failpoint set by a prior test.
    - Why: failpoints are process-global (the `failpoints` crate keeps them in a global registry); dropping the cluster doesn't clear them.
    - Fix: `TestCluster::drop` (or a teardown guard) calls `fail::cfg_clear()` / removes each registered failpoint by name (R4).
    - Muscle: any process-global injection must be cleared in a Drop guard, never relied on to reset itself. Reapplies at: W105 ops-monitoring metric registries, W108 ops-chaos fault injection.
  - **(SENIOR) When `chaos_converges_after_partition` reports diverged commit-indices:**
    - Symptom: nodes' commit-index never equalizes within the bound.
    - Why: `wait_converged` slept a fixed duration instead of polling, OR the partitioned peer's catch-up (snapshot install) exceeded the bound on slow CI.
    - Fix: poll commit-index every 50ms until equal-or-timeout; make the bound env-configurable (default 30s CI) per R3.
    - Muscle: convergence is an observed condition (poll the state), never a sleep; bounds must scale to the slowest CI. Reapplies at: W105 deploy health-checks, W108 chaos drills, W93 72hr soak.
  - **(SENIOR) When `chaos_no_lost_committed_write` reports a lost/torn committed write:**
    - Symptom: a key in `successful_puts()` is absent or has the wrong value after recovery.
    - Why: either `successful_puts()` records puts that returned before the commit-index advanced (so they weren't actually committed), or recovery replayed the WAL past a torn tail.
    - Fix: only record a put in `successful_puts()` after the client observes the raft commit-index ≥ the put's index; recovery must truncate at the last intact WAL frame (W30 recovery invariant).
    - Muscle: "committed" means commit-index advanced AND applied — record success only at that point, not at append. Reapplies at: W104 vector-db durability test, W30 recovery, W67 raft commit.
