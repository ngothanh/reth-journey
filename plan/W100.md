## Monday — `liquidation-engine`: margin-ratio trigger evaluator (the breach decision)

- [ ] [HFT] **Build (bar (c))**: `crates/liquidation-engine/src/trigger.rs` — `TriggerEvaluator` reads `risk-engine`'s committed margin state per mark tick and emits a `LiquidationCandidate` for every account whose **maintenance-margin ratio** has breached. Deterministic, zero-alloc, integer-only. (~total 230 min across 3 phases)
  - 🔧 **Why this matters**: this is the entry point of the backstop — the moat (§9: "insurance fund stubbed away kills the moat"; the trigger is what *feeds* the fund). It is the meeting point of all three lenses: `jeff-dean`-hard (fan-out a breach check across ~100k accounts per mark tick, sharing the incremental-margin hot path from `risk-engine` W98), `hft-review`-hard (zero-alloc, integer-only, sub-tick budget), and domain-hard (maintenance-margin ratio, partial vs full, isolated vs cross — *no spot analog*). Get the comparator wrong (`<` vs `<=`, or comparing the wrong margin) and you either liquidate solvent accounts (lawsuit) or miss insolvent ones (bad debt the fund must eat). Get a `f64` into the ratio and replicas diverge cross-arch — and because this rides the VSR log (W103), divergence is silent state corruption. Downstream: W101's fund waterfall begins where this trigger ends; W102's cascade detection counts triggers/sec from here; W108 cluster-VOPR searches for the schedule where triggers outrun the fund (the tripwire).

  - 🔧 **Decomposition prompt (silent test)**: this spec doesn't name primitives. The per-account breach scan needs zero-alloc; the candidate output needs a fixed-cap ring (never a `Vec` grown per tick); the cross-shard candidate mailbox needs MPMC; the per-shard breach counters need cache isolation; the mark price flows from `oracle-mark` as an *integer* input; the margin state is *read* from `risk-engine`'s local applied state (no consensus round-trip per read — §4A control-plane contract). The spec names none of them — your toolkit (W11 backpressure, W37 epoch-gc, `concurrent` ring, W98 incremental-margin reads) must combine to meet the acceptance. If dhat shows allocations, or the cross-replica candidate set diverges, or the per-tick p99.99 exceeds budget — your decomposition missed something.
  - 🎯 **Hardened acceptance for `liquidation-engine` v0.1 trigger evaluator**:
    - **Scope gate (v3)**: `trigger.rs` emits **only** `LiquidationCandidate { account, instrument, margin_ratio_bps, side }`. **No insurance-fund touch, no ADL, no socialized loss, no order emission** (that is Tuesday). CI grep asserts no `insurance`/`adl`/`socializ` identifier in `trigger.rs`.
    - **Correctness boundary**: an account breaches iff `equity_bps * 10_000 < maintenance_margin_bps * position_notional_bps` (strict `<`; equality is NOT a breach — a margin-call boundary account is solvent). Cross-margin: the breach is on the **portfolio** margin from `risk-engine` (BTC-PERP + ETH-PERP netted at the const-30%-haircut, W97), never per-isolated-instrument when the account is in cross mode.
    - **Determinism gate**: no `f64`/`f32`, no `Instant::now`/`SystemTime`, no `HashMap`/`AHashMap` iteration in the scan. Maintenance margin, equity, notional all integer bps. CI grep + clippy `disallowed-types` enforce.
    - **Throughput / scale**: evaluate ~100k accounts × 2 instruments per mark tick (10 ticks/s) sharing `risk-engine`'s **incremental** state (only re-check accounts whose margin moved since the last tick + a full sweep on circuit-breaker/param change); full-scan fallback ≤ the per-tick budget at the 100k target.
    - **Zero allocation on the scan path (dhat-verified)**: zero heap allocations across a 100k-account sweep; candidates written into a pre-sized ring (cap = max expected concurrent breaches, default 4096).
    - **Latency**: per-mark-tick breach scan p99 ≤ 200µs, p99.99 ≤ 1ms at 100k accounts (incremental); `latency-lab` report attached.
    - **Cross-replica byte-identical**: 100 random scenarios × 10k mark ticks — every replica's emitted candidate set (sorted canonical) matches at every tick. ZERO divergence.
    - **Cross-arch byte-identical**: x86 + aarch64 on the same mark-tick stream → identical candidate sets. No `f64` anywhere.
    - **5-year failure mode**: state one shift (per-instrument maintenance tiers à la Binance, or sub-account margin, or an oracle outage that freezes the mark) that would force a redesign.

  - *Mental model*: `TriggerEvaluator` is a **pure read-side fan-out**: it consumes `risk-engine`'s committed (VSR-applied) portfolio-margin state — read from **local applied state on the leader shard, no consensus round-trip** (§4A control-plane contract) — and a mark tick from `oracle-mark`, and emits the *set of accounts that breach maintenance margin*. It computes nothing about the book and touches no fund. It is `apply: (MarginState, MarkTick) → Set<LiquidationCandidate>` — a deterministic function the same on every replica.
  - *Contract* (signature only, never the body):
    ```rust
    pub struct TriggerEvaluator { /* reads risk-engine local applied state; pre-sized candidate ring */ }
    #[derive(Clone, Copy)]                                   // R-det: Copy, integer-only
    pub struct LiquidationCandidate {
        account: AccountId, instrument: InstrumentId,
        margin_ratio_bps: u32,        // equity / maintenance-requirement, in bps; integer
        side: Side,                   // which side of the position is underwater
    }
    impl TriggerEvaluator {
        // incremental: only re-checks accounts whose margin moved since last tick (W98 delta set)
        pub fn evaluate_tick(&mut self, mark: MarkTick, dirty: &DirtySet) -> &[LiquidationCandidate];
        pub fn evaluate_full(&mut self, mark: MarkTick) -> &[LiquidationCandidate]; // circuit-breaker/param change only
    }
    // NOTE (v3): NO fund, NO ADL, NO order emission here. Candidates → Tuesday's sizer → matching-engine.
    ```
  - *Back-of-envelope* (bar (c) — name the cost): target 100k accounts, 10 mark ticks/s, per-tick scan p99 ≤ 200µs.
    - Full-scan cliff: 100k accounts × ~50ns integer compare = **5ms/full-sweep**. At 10 ticks/s = 50ms/s if you full-scan every tick — fits *barely* single-thread, but blows the 200µs *per-tick* p99 budget (5ms ≫ 200µs). **Therefore incremental is mandatory** (mirrors §4A: incremental margin is not a fallback at this scale). Only accounts in `risk-engine`'s dirty set since the last tick are re-checked (~hundreds, not 100k); full-scan reserved for circuit-breaker/param change.
    - Candidate-collection alloc cliff: `Vec::push` reallocs on growth = ~log(n) mallocs/tick under a liquidation cascade × 10 ticks/s; under a crash cascade (thousands of breaches) that's thousands of mallocs/sec + cache pollution → p99 jitter exactly when you can least afford it. Pre-sized ring `[LiquidationCandidate; 4096]` = 0 allocs; overflow = a circuit-breaker signal (Tuesday consumes it), never a realloc.
    - Read-path cliff: a margin read via a consensus round-trip ≈ 1 RTT (~250µs) × dirty-set size = impossible per tick. Local applied state on the leader shard = ~L2 read ≈ 5ns. Cliff ≈ 50,000×. This is why the §4A control-plane contract is read-after-commit from *local applied state*, not a consensus read.

  - **The problem this primitive solves**: a matching engine with no liquidation backstop accumulates bad debt the moment a position goes underwater faster than the holder tops up margin. The trigger is the *detection* half of the backstop. Naïvely it introduces three failure categories: (a) **comparator error** — `<=` liquidates a solvent boundary account (legal/reputational disaster) or comparing isolated margin in cross mode misses a netted breach; (b) **non-determinism** — `f64` margin ratios diverge cross-arch on the VSR log; (c) **scan-cost collapse** — full-scanning 100k accounts every tick blows the per-tick budget. The fix: strict `<` on integer portfolio margin + incremental dirty-set scan + pre-sized candidate ring.

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `trigger_does_not_fire_at_exact_maintenance` fails (a boundary account got liquidated):**
    - Symptom: an account whose equity exactly equals the maintenance requirement emits a candidate.
    - Why: you wrote `equity <= maintenance` (or `ratio <= 1.0`); equality is the margin-call boundary, and a boundary account is solvent — liquidating it realizes an unnecessary loss.
    - Fix: strict `<` via integer cross-multiply: `equity_bps * 10_000 < maintenance_margin_bps * notional_bps`. Equality returns no candidate.
    - Cost avoided: liquidating solvent accounts → user lawsuits + reputational kill of the venue; and needless losses the W101 fund would then have to reason about.
    - Muscle: a liquidation trigger is *strict* `<` on the breach side; equality is solvent. Never `<=`. Reapplies at: W101 fund waterfall threshold, W102 cascade trigger, W119 ADL engage threshold.

  - **(NEWBIE) When `trigger_emits_candidates_only` / the grep CI fires on `fund`/`adl`:**
    - Symptom: the grep guard matches an `insurance`/`adl`/`emit_order` identifier in `trigger.rs`.
    - Why: the v2 `matching-engine` carried liquidation+fund+ADL inline; the reflex is to debit the fund "while we're here." That re-merges W101 into the detector.
    - Fix: `trigger.rs` returns `&[LiquidationCandidate]` and nothing else. The fund (W101) consumes candidates downstream; the order sizer (Tuesday) consumes them too. Delete any fund/order reference.
    - Cost avoided: a re-merged boundary that kills the W101 waterfall seam and the W108 cluster-VOPR tripwire invariant (the W117 bet-readiness gate depends on "no primitive twice").
    - Muscle: a crate's output type is its scope contract — a *pure candidate set* here, the fund is a separate stage. Reapplies at: W101 fund interface, W102 cascade interface, W103 capstone op union.

  - **(SENIOR) When `trigger_uses_netted_portfolio_margin_in_cross_mode` liquidates the hedge:**
    - Symptom: a long-BTC/short-ETH cross account is liquidated even though the netted portfolio is solvent.
