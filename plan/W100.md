**Monday — mini-db: comprehensive test suite**

- [ ] proptest: random op sequences must satisfy linearizability. (~45 min)
  - **Why**: Linearizability is the **gold standard** correctness property for a distributed kv store. A proptest
    that generates random op sequences and checks them against a sequential model is the same approach Jepsen uses
    (with knossos/elle checker). If mini-db survives 100k random sequences, you can claim "linearizable" with
    confidence on the resume.
  - **Read first**: Herlihy & Wing 1990 "Linearizability: A Correctness Condition for Concurrent Objects"; Kyle
    Kingsbury's Jepsen blog (especially the etcd/CockroachDB analyses); `proptest` book ch. 4 (state-machine
    testing); `knossos` Clojure library OR Rust `loom`-based linearizability checker; CockroachDB
    `pkg/kv/kvclient/kvcoord/testing_knobs.go` for inspiration.
  - **Design**: ```rust
    // tests/proptest_lin.rs
    use proptest::prelude::*;
    #[derive(Debug, Clone)]
    enum Op { Put(u32, u32), Get(u32), Delete(u32) }
    proptest! {
        #![proptest_config(ProptestConfig { cases: 1000, .. ProptestConfig::default() })]
        #[test]
        fn linearizable_single_thread(ops in proptest::collection::vec(any::<Op>(), 1..200)) {
            let db = MiniDb::open_tempdir();
            let mut model = std::collections::HashMap::<u32,u32>::new();
            for op in ops {
                match op {
                    Op::Put(k,v) => { db.put(&k.to_le_bytes(), &v.to_le_bytes()).unwrap(); model.insert(k,v); }
                    Op::Get(k) => {
                        let actual = db.get(&k.to_le_bytes()).unwrap()
                            .map(|b| u32::from_le_bytes(b.as_ref().try_into().unwrap()));
                        prop_assert_eq!(actual, model.get(&k).copied());
                    }
                    Op::Delete(k) => { db.delete(&k.to_le_bytes()).unwrap(); model.remove(&k); }
                }
            }
        }
    }
    // tests/lin_concurrent.rs — use loom or shuttle for true linearizability check.
    ```
    **Invariants**: each test owns a fresh tempdir Db; HashMap is the ground-truth sequential model; concurrent
    tests must use a checker that explores interleavings (loom for narrow tests, shuttle for broader).
  - **Build steps**: 1. (~10 min) Sequential proptest above; 2. (~15 min) Concurrent proptest with 4 threads doing
    random ops on disjoint key ranges, model is per-thread HashMap merged; 3. (~10 min) Loom/shuttle linearization
    check on a tiny txn_manager.commit interleaving (≤ 5 threads, ≤ 20 ops total — loom state space blows up);
    4. (~10 min) Run with `MINIDB_PROPTEST_CASES=10000` for soak.
  - **Pitfalls** (named):
    - *Model drift*: **Symptom**: HashMap model doesn't match mini-db's semantics (e.g., tombstone visibility) →
      false test failures. **Fix**: model must implement EXACTLY the same semantics including delete + put roll-up;
      cite each rule in a comment.
    - *Test flake from clock*: **Symptom**: HLC ts ties between two puts cause non-deterministic ordering, prop
      test fails 1/100 runs. **Fix**: HLC's logical-counter component breaks ties deterministically; if test
      still flakes, advance clock explicitly between ops in test mode.
    - *Loom blowup*: **Symptom**: state space exceeds 10M, test hangs. **Fix**: reduce ops to ≤ 20, threads to
      ≤ 3; use `loom::model::Builder` with explicit max_threads.
    - *Tombstone after compaction*: **Symptom**: random sequence puts → compactions → tombstones → model says
      Some, db says None. **Fix**: tombstone compaction respects min_active_snapshot_ts (W98 invariant); test
      with no active snapshots should still get correct semantics.
  - **Test scenarios**: 1000 random sequences single-thread; 100 concurrent 4-thread runs; soak 10k cases
    overnight.
  - **Acceptance**: 0 proptest failures in 10k cases; loom test green; documented in DESIGN.md as
    "linearizability evidence."
  - **Downstream**: claim this in resume + interview; the methodology mirrors Jepsen + CockroachDB's testing
    philosophy.

- [ ] Loom test for the txn_manager lock interactions. (~60 min)
  - **Why**: txn_manager has multiple atomics + locks (active-set, min_active_snapshot_ts, isolation enforcement).
    Loom systematically explores **all interleavings** of memory orderings under Rust's relaxed memory model.
    Catches ordering bugs that hardware-level testing on TSO x86 will never expose (but ARM/POWER will).
  - **Read first**: `loom` docs + the README example; tokio's loom test suite (e.g.,
    `tokio/tests/loom_*.rs`); Crossbeam's epoch-gc loom tests; `crates/txn/src/manager.rs` (your existing
    txn_manager from W42).
  - **Design**: ```rust
    // tests/loom_txn.rs
    #![cfg(loom)]
    use loom::sync::{Arc, atomic::AtomicU64, atomic::Ordering};
    use loom::thread;
    #[test]
    fn min_active_snapshot_monotone_under_concurrent_begin_drop() {
        loom::model(|| {
            let mgr = Arc::new(TxnManager::new());
            let observed = Arc::new(parking_lot::Mutex::new(vec![]));
            let t1 = thread::spawn({
                let mgr = mgr.clone(); let obs = observed.clone();
                move || {
                    let snap = mgr.snapshot();
                    obs.lock().push(("t1_snap", snap.ts()));
                    drop(snap);
                    obs.lock().push(("t1_drop", mgr.min_active_snapshot_ts()));
                }
            });
            let t2 = thread::spawn({
                let mgr = mgr.clone(); let obs = observed.clone();
                move || {
                    let snap = mgr.snapshot();
                    obs.lock().push(("t2_snap", snap.ts()));
                    drop(snap);
                }
            });
            t1.join().unwrap(); t2.join().unwrap();
            // Invariant: min_active_snapshot_ts never decreased; >= max(snap.ts) after all drops
            assert_invariants(&observed.lock());
        });
    }
    ```
    **Invariants** (under all interleavings): min_active_snapshot_ts is non-decreasing in steady state (until next
    snapshot reduces it via begin); active count never goes negative; commit_ts > all observed snap.ts of active
    snapshots at commit time.
  - **Build steps**: 1. (~15 min) Wire loom feature in txn crate's `[dev-dependencies]`; 2. (~15 min) Write the
    monotonicity test above; 3. (~15 min) Write a separate test for commit/abort ordering (commit visible to a
    snap created AFTER commit_ts); 4. (~15 min) Run `RUSTFLAGS="--cfg loom" cargo test --release -p mini-db
    loom_`, capture max state-space size.
  - **Pitfalls** (named):
    - *Loom test on non-loom-aware code*: **Symptom**: txn_manager uses `std::sync::Mutex` not `loom::sync::Mutex`,
      loom can't observe — tests pass trivially. **Fix**: txn_manager exports via `#[cfg(loom)] use loom::sync::*;
      #[cfg(not(loom))] use std::sync::*;` (the loom guidance pattern).
    - *State space explosion*: **Symptom**: 5 threads + 10 ops → 100M states, test never finishes. **Fix**: reduce
      threads to 2-3; use `loom::model::Builder::preemption_bound(3)` to limit exploration.
    - *Hidden Mutex<Vec<T>>*: **Symptom**: observed log uses parking_lot which loom doesn't intercept → false
      passing. **Fix**: even the observation log should use loom-aware sync, OR mark it as a fence/escape and
      verify the invariant via state-machine assertions, not observation order.
  - **Test scenarios**: monotonicity under begin/drop; commit visibility; race between GC and snapshot.
  - **Acceptance**: 2 loom tests green; max state space documented; CI runs them on release builds nightly.
  - **Downstream**: same loom pattern reused for vector-db W103 wal-recovery test; W104 ship documents loom
    coverage in DESIGN.md.

**Tuesday — mini-db: chaos test**

- [ ] Kill replicas mid-batch. Verify final convergence + linearizability. (~30 min)
  - **Why**: Chaos testing is the only way to find correctness bugs that don't show up under "happy path." Killing
    replicas mid-batch exercises: leader election under load, in-flight propose loss, partial WAL durability,
    recovery correctness. This is the canonical Jepsen approach.
  - **Read first**: Jepsen's etcd report (jepsen.io/analyses/etcd-3.4.3); CockroachDB Jepsen test harness in
    `pkg/jepsen/`; TiKV's `tests/failpoints/` suite; `failpoints` crate docs.
  - **Design**: ```rust
    // tests/chaos.rs
    fn chaos_kill_leader_during_batch() -> Result<()> {
        let cluster = TestCluster::new_3_nodes()?;
        let client = cluster.client();
        let writer = std::thread::spawn({
            let client = client.clone();
            move || {
                for i in 0..10_000u32 {
                    let k = format!("key-{}", i).into_bytes();
                    let v = format!("val-{}", i).into_bytes();
                    let _ = client.put(&k, &v); // may Err on leader change
                }
            }
        });
        std::thread::sleep(Duration::from_millis(500));
        cluster.kill_leader();  // fail_point active here
        std::thread::sleep(Duration::from_millis(200));
        cluster.restart_killed();
        writer.join().unwrap();
        // Convergence: wait for raft commit-index to match across nodes
        cluster.wait_converged(Duration::from_secs(10))?;
        // Verify: each successful put is readable; no put returned Ok but value missing
        for (k, v) in client.successful_puts() {
            let got = client.get(&k)?;
            assert_eq!(got.as_deref(), Some(v.as_slice()), "lost write {:?}", k);
        }
        Ok(())
    }
    ```
    **Invariants**: a put that returned `Ok(committed)` MUST be readable post-recovery; a put that returned `Err`
    may or may not be applied (uncertainty — client retries with idempotency token, out of scope v1.0); cluster
    converges within bounded time (election timeout + apply lag).
  - **Build steps**: 1. (~5 min) TestCluster harness wiring 3 RaftKv instances over in-process channels; 2. (~10
    min) failpoint integration for `inject_leader_crash`; 3. (~5 min) Successful-puts tracker on client; 4. (~5
    min) wait_converged using raft commit-index polling; 5. (~5 min) Three chaos scenarios: kill-leader,
    network-partition (drop messages for one peer for 200ms), kill-follower.
  - **Pitfalls** (named):
    - *Lost-write under Err*: **Symptom**: put returned Err(Timeout) but raft actually committed — verify scan
      finds the key. **Fix**: explicitly classify Err results; lost-write is acceptable, lost-commit is not.
    - *Convergence timeout too short*: **Symptom**: test flakes because catch-up takes > 10s on slow CI. **Fix**:
      configurable timeout via env var; default 30s on CI.
    - *Failpoint leak*: **Symptom**: test leaves failpoint active, next test sees corruption. **Fix**: tear-down
      hook removes all failpoints.
  - **Test scenarios**: leader-kill 100 trials, all converge; network partition 100 trials; follower-kill 100
    trials. Across all 300: zero lost-committed-writes.
  - **Acceptance**: chaos suite green at 300 trials in CI nightly; documented as "chaos-tested" in DESIGN.md.
  - **Downstream**: ops runbook (W105+) references this suite for production chaos days.

    WAL=$(tokei crates/wal/src --output json | jq '.Rust.code')

    TXN=$(tokei crates/txn/src --output json | jq '.Rust.code')
    BUFPOOL=$(tokei crates/bufpool/src --output json | jq '.Rust.code')
