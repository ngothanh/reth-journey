**Tuesday — Revm interpreter core (the hot loop)**

- [ ] **Annotate the revm interpreter execution loop** — file `notes/49_revm_interp_trace.md`. (~55 min)
  - *Mental model*: the interpreter loop is the single hottest path in any EVM — every gas-fee dollar Ethereum earns flows through this `while`. To beat revm on Saturday's perf PR (and W53/W59/W64) you must internalize its dispatch, gas tracking, and `InstructionResult` propagation exactly; otherwise your "optimization" will be slower because you reintroduce a bounds check LLVM had elided, or miss a branch hint.
  - *Mechanical model to absorb (do NOT rewrite)*:
    ```rust
    pub type Instruction<H> = fn(&mut Interpreter, &mut H);
    // hot loop, conceptually:
    loop {
      let opcode = bytecode[interpreter.instruction_pointer];
      interpreter.instruction_pointer += 1;            // post-increment: IP points to NEXT byte
      (instruction_table[opcode as usize])(&mut interpreter, host);
      if interpreter.instruction_result != InstructionResult::Continue { break; }
    }
    ```
    Load-bearing invariants to write into the trace doc:
    - `instruction_pointer` always points to the NEXT byte to fetch (post-increment semantics).
    - `Gas::remaining` is the SINGLE source of truth; every `record_cost` returns `bool`; the caller MUST set `InstructionResult::OutOfGas` on `false`.
    - `SharedMemory` lifetime is per-call-frame; memory grows only by bumping `memory.len()`, and growth gas is paid lazily on first access via `resize`.
    - JUMPDEST analysis is precomputed once at bytecode load into a `JumpTable: BitVec` — the single biggest perf insight in the EVM; a per-JUMP re-scan would be O(n²).
  - 🎯 **Hardened acceptance**: `notes/49_revm_interp_trace.md` has end-to-end call-chains (≥5 lines each) for ADD (`arithmetic::add` → `pop_top!` → `gas!(VERYLOW)` → write-back), JUMPI (`valid_jumpdest` against the precomputed `JumpTable` from `analysis.rs`), MLOAD (`resize_memory!` charges quadratic gas BEFORE any read — misordering = consensus bug), and CALL-frame setup. Doc states **from memory**: "what does `instruction_pointer` point to mid-execution?" (answer: the next byte). It also records **3 perf-backlog candidates** appended to `EXEC_VM_PERF_BACKLOG.md` (e.g. `Gas::record_cost` has no `#[cold]` on its `false`/OOG arm; `pop_top!` inline boundary; Stack-overflow path post-check could be `unreachable_unchecked`). Diff each against exec-vm's W17 dispatch and flag whether exec-vm uses `get_unchecked` indexing or not.
  - *Named pitfalls to capture in the trace (these are the trap seeds for Saturday)*:
    - **Stale instruction pointer on revert**: when a sub-call returns RETURN/REVERT, the parent frame's IP must be the byte AFTER the CALL opcode, not the CALL byte. Symptom: re-executes CALL forever, gas drains to 0. Mechanism: parent's `next_action` consumed via `take()`; IP advanced by the `gas!`-family macro before sub-call dispatch.
    - **Memory-growth gas underflow**: `(words² )/512 + 3·words` overflows if `words` not capped at `MEMORY_LIMIT`. Symptom: free memory → consensus fork. Fix: `Gas::record_memory_expansion` returns `bool` after a saturation check; on overflow return `MemoryOOG`.
    - **PUSH at end of bytecode**: PUSH32 with 5 bytes left must zero-extend, not panic. Fix: revm reads `bytecode.get(ip..ip+N)` with slice padding, never an unchecked index.
  - Self-test scenarios (run mentally against the trace, write expected results): `0x00` STOP → `Stop`, 0 gas; `PUSH1 5 PUSH1 6 ADD STOP` → top=11, gas=3+3+3+0; `PUSH1 0x10 PUSH1 0x00 MSTORE` → `memory.len()==32` + expansion gas; JUMPDEST-free `PUSH1 0x00 JUMP` → `InvalidJump`.
  - Lookup-when-stuck: `crates/interpreter/src/{interpreter.rs (Interpreter::run/step), instructions.rs (InstructionTable<H>, instruction_table::<H,SPEC>() builder), instructions/control.rs (JUMP/JUMPI/PC), gas.rs (Gas{limit,remaining,refunded,memoized_memory}, record_cost), analysis.rs (JUMPDEST BitVec)}`.

    ```rust

        fn env(&self) -> &Env;                                  // CfgEnv + BlockEnv + TxEnv
        fn load_account_delegated(&mut self, a: Address) -> Option<AccountLoad>;
        fn block_hash(&mut self, number: u64) -> Option<B256>;
        fn balance(&mut self, a: Address) -> Option<StateLoad<U256>>;
        fn code(&mut self, a: Address) -> Option<Eip7702CodeLoad<Bytes>>;
        fn sload(&mut self, a: Address, i: U256) -> Option<StateLoad<U256>>;

        fn log(&mut self, log: Log);
        fn selfdestruct(&mut self, a: Address, t: Address) -> Option<StateLoad<SelfDestructResult>>;
    }
    ```
    Load-bearing invariants for the map doc:

    - `sstore` returns `SStoreResult { original_value, present_value, new_value }` — required for EIP-3529 refund accounting.
    - revm splits `Host` (used inside the interpreter) from `DatabaseCommit` (used at frame finalization); exec-vm must preserve this split.

    pub trait Database {
        type Error: Debug;
        fn basic(&mut self, a: Address) -> Result<Option<AccountInfo>, Self::Error>;

  #### Phase 1 — Problem, prediction, design (~30 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `notes/49_perf_pr_prediction.md`:
    - P1: which backlog item you'll take (e.g. `#[cold]` on `Gas::record_cost`'s OOG/`false` arm; `#[inline]` boundary on `pop_top!`; `unreachable_unchecked()` on the post-checked Stack-overflow path) + the **exact import/attribute line** you'll add.

    - P3: predict whether LLVM **already** inlined/cold-marked the target (yes/no) — you will verify against the LLVM IR before claiming a win.
    - P4: predict the `mainnet-cap` outcome (does optimizing this path help, hurt via I-cache, or neutral?).
    - P5: **list every Phase-2 trap you predict your first attempt will trip** (e.g. "I'll report a win that's inside criterion's noise band"). Compare to reality after the benches run.
  - *Back-of-envelope* (bar-(c)-style numbers, because this is the EVM hot loop): the inner loop runs ~1 instruction per ~few ns; a single mispredicted branch ≈ **5 ns** and an unnecessary bounds-check ≈ **1-2 cycles + a possible mispredict**. A `transfer` tx executes O(10²) opcodes; mainnet-cap O(10⁶)+. So a 2 ns/opcode saving is ~0.2 µs on transfer but seconds across a mainnet replay — REAL only if it survives I-cache effects. The cold/hot cliff that matters: a `#[cold]` OOG arm moves rarely-taken code out of the hot I-cache line, but if the arm is actually taken often (adversarial OOG-heavy workload) you've added a forward-jump mispredict (~5 ns) on the common path — measure both workloads.
  - **Requirements** R1..R5 — write in `notes/49_perf_pr.md`:

  #### Phase 2 — Write the failing acceptance gates (~40 min)
  These are **acceptance gates engineered to fail a naive perf attempt**. Capture each as a checklist item in `notes/49_perf_pr.md` with the exact command + pass band; a naive attempt trips at least one. (No `rust` unit-test harness here — the "tests" are the measurement gates; encode the band assertions as a tiny script so a green run is unambiguous.)

      # parse criterion estimate; FAIL if median outside [1e6, 5e8] ops/s  → bench is dead
      ```

      cargo rustc --release -p revm-interpreter -- --emit=llvm-ir

      ```

  #### Phase 3 — Pass the gates, one failure at a time (~50 min)
  Ordered failure cards, newbie→expert — the ladder you actually walk. Each card names symptom, root cause, fix, cost avoided, and the muscle + Reapplies-at.
    - **(NEWBIE) When Gate A reports a `transfer` throughput of ~0 / NaN / 2e9+ ops/s:**
      - Symptom: criterion estimate is implausible (loop optimized away or counter mis-wired).
      - Why: the bench's `black_box` is missing so LLVM elided the interpreter call, or the iteration count divides by the wrong factor.
      - Fix: wrap the executed result in `std::hint::black_box(...)` and verify the per-op time is in the µs/iter range before trusting any delta.
      - Cost avoided: an entire PR built on a dead bench — hours of false signal and a credibility hit with the maintainer.
      - Muscle: never trust a bench you haven't sanity-banded; a number outside physical limits means the harness, not the code, changed. **Reapplies at: W59 evmone comparison, W64 revm perf PR, W110 matching-engine perf tuning.**
    - **(NEWBIE) When Gate D goes red after the change:**
      - Symptom: a revm state test fails in `--release` that was green before.
      - Why: an "optimization" altered behavior — e.g. `unreachable_unchecked()` placed before the bounds check instead of after, or a saturating-sub turned into wrapping.
      - Fix: revert to a behavior-preserving form; only apply `unreachable_unchecked()` AFTER the invariant is provably established by a prior check.
      - Cost avoided: a consensus fork shipped as a "perf win" — the worst possible EVM bug.
      - Muscle: a perf change that changes ANY observable output is not a perf change, it's a bug. Correctness gates run first. **Reapplies at: W53 complete opcodes, W64 perf PR, W84 full-stack integration.**
    - **(SENIOR) When Gate E shows the `transfer` delta sits inside the noise band:**
      - Symptom: median looks −3% on a casual run but the 30-sample pinned distribution overlaps baseline within 2σ.
      - Why: the casual run had turbo on / governor `ondemand` / no core pinning — variance swamped the effect.
      - Fix: pin the rig (governor `performance`, `taskset -c 2-3`, turbo off, ≥30 samples) BEFORE deciding; report mean ± stdev, never a single point estimate.
      - Cost avoided: ~2-5% of phantom "improvement" that a maintainer on a pinned box cannot reproduce → PR rejected, relationship cost (gates W53/W55/W64).
      - Muscle: a perf claim is a statistical claim — pin the rig and clear 2σ or it isn't real. **Reapplies at: W59 evmone, W64 perf PR, W86 marketdata-kernelbypass latency, W110 matching-engine tuning.**
    - **(SENIOR) When Gate B shows pre-IR == post-IR for the target symbol:**
      - Symptom: wall-clock looks flat and the LLVM IR for the annotated function is byte-identical before/after.
      - Why: LLVM had already inlined / cold-marked the target; your `#[inline(always)]`/`#[cold]` was redundant (P3 prediction was wrong).
      - Fix: pick a different backlog item where the IR actually changes — confirm the target was NOT inlined by reading the IR FIRST, then annotate.
      - Cost avoided: an empty PR that wastes the maintainer's review budget and teaches you nothing.
      - Muscle: an annotation that doesn't change the IR doesn't change anything — verify the compiler hadn't already done your job. **Reapplies at: W58 dispatch, W60 exec-vm hot path, W64 perf PR.**
      - *(bar-(c) lens)* Cost avoided here is opportunity cost; the genuine bar-(c) violation is the inverse — see the EXPERT card.
    - **(EXPERT) When Gate C regresses `mainnet-cap` while `transfer` improved (bar-(c)-style violation):**
      - Symptom: `transfer` is −3% but `mainnet-cap` is +1.5% (>2σ) after the change.
      - Why: you optimized a rare path (e.g. force-inlined a large helper or moved a `#[cold]` arm) and grew the hot-loop code footprint — I-cache pressure on the realistic opcode mix dominates the micro-win.
      - Fix: prefer changes that shrink or leave the hot-path code size unchanged; keep cold/rare code `#[cold]` and out-of-line; bench mainnet-cap LAST and treat it as veto.
      - Cost avoided: an **I-cache regression measured in ns/opcode across millions of opcodes** — net-negative throughput on real workloads despite a green microbench; a change that ships slower mainnet replay.
      - Muscle: the hot path is the COMMON path — optimize for the realistic instruction mix and let mechanical sympathy (I-cache footprint) veto microbench wins. **Reapplies at: W58 dispatch, W60 exec-vm hot path, W64 perf PR, W86 marketdata-kernelbypass, W110 matching-engine.**
