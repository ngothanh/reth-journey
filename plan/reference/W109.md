## Monday — Runbook: `perp-dex-core` VSR replica divergence (the single-log incident)

- [ ] Write `ops-runbooks/vsr-replica-divergence.md`. (~45 min)
  - **Triggering alert (W105)**: `VsrReplicaDivergence` — a replica's committed-state hash ≠ the leader's at the same `op_num`.
  - **Inherited fault class (W108)**: `NetworkPartition` + a delayed `KillProcess` of a replica mid-burst; optionally `ClockSkew` to surface a wall-clock leak.
  - **The five operator steps the runbook documents**:
    1. **Detect** — `curl :9100/metrics | grep vsr_committed_state_hash`; identify *which* replica diverged and at *which* `op_num`.
    2. **Isolate** — drain the diverged replica from the client-facing target pool BEFORE touching it (`ops-deploy drain`, W107). A diverged replica must never serve reads.
    3. **Capture** — snapshot its VSR `log/` segment + the last 5 s of `tracing` spans into the incident bundle. This *is* the postmortem corpus; a diverged replica is the most valuable artifact you will ever capture — capture it before you destroy it.
    4. **Reseed** — `consensus-vsr` `state_transfer` (`GetState`/`NewState`, W76) from a majority member. NOT a manual file copy: a copy races the live committed log and re-introduces the divergence.
    5. **Rejoin + verify** — re-add to the pool only after `vsr_committed_state_hash` matches the leader for 100 consecutive committed ops.
  - 🎯 **Hardened acceptance**: dry-run the runbook against W108's `minority-partition` canned scenario; the documented detect→isolate→reseed→verify path must bring the cluster-VOPR `ReplicaConvergence` assertion green within the scenario's convergence budget (≤500 ms view-change + `state_transfer` time). MTTR measured and recorded at the top of the runbook. A step referencing a command flag that does not exist (`ops-deploy drain --help` must show it) is a defect — verify every command literally against the W107 surface.
  - *Mental model*: this is the single most dangerous venue incident, and v3 makes it worse than the v2 raft version — because the VSR log is **one log carrying both the order book and the settlement journal**, a diverged replica that silently serves stale state can fill against a phantom book *and* report a phantom `SettlementId`/`finality_status`. The runbook exists NOW (W109) because W110 begins sustained operations on the live 3-node paper-trade rig; the first divergence will happen on a night when I am the only one awake. The reseed-via-`state_transfer`-not-file-copy step is the W108 Thursday "trust validated state, never bypass the validated runner" muscle applied to operations: a manual file copy is the operator equivalent of bypassing cluster-VOPR. **v3 vs v2**: this used to reseed via raft `InstallSnapshot`; the venue is VSR (`consensus-vsr`, §4A), so the primitive is `state_transfer` and the artifact is the VSR committed-log prefix, not a raft snapshot.
  - **Output**: `ops-runbooks/vsr-replica-divergence.md` exists; top of file has a measured MTTR from the dry-run; `grep -c "state_transfer" ops-runbooks/vsr-replica-divergence.md` ≥ 1 (the reseed primitive is named, not hand-waved); the file states explicitly that the diverged replica is captured BEFORE reseed (postmortem corpus discipline).

- [ ] 🔧 **Load-bearing pre-mortem (5-step trace, write in the same note)**: a half-asleep operator sees `VsrReplicaDivergence`, SSHes to the diverged node, and `scp`s the leader's `log/` over the diverged log to "fix it fast." Trace the consequence: (1) the leader is *still committing* during the copy, so the copied prefix is a moving target; (2) the diverged node now has a torn mix of old-diverged + partial-new bytes; (3) on restart its `vsr_committed_state_hash` matches *neither* the leader's old nor new state; (4) it rejoins the pool and serves a third phantom state — now there are *three* `SettlementId`→state mappings in flight; (5) the only recovery is to wipe it and `state_transfer` from scratch, having *lost the divergence artifact* you needed for the postmortem. The fix the runbook encodes: capture → drain → `state_transfer` (atomic, consistent-snapshot), never a live file copy.
- [ ] **Operator-error failure cards** (the 3am mistakes the runbook must prevent — label + Symptom/Why/Fix/Cost-avoided/Muscle), record in the runbook's "common mistakes" section:
  - **(NEWBIE) Restarting the diverged replica before draining it.** Symptom: the diverged replica restarts fast, rejoins, and immediately serves reads against the client pool. Why: restart feels like "fixing"; but a restart of a diverged replica reloads the *diverged* log — restart is not repair. Fix: drain from the pool FIRST (it must serve zero reads while diverged), then capture, then `state_transfer`. Cost avoided: filling client orders against a phantom book during the restart window. Muscle: isolate before you touch — drain precedes every repair action. Reapplies at: every venue incident this week.
  - **(SENIOR) Reseeding by file copy instead of `state_transfer`.** Symptom: the copy "works" but the replica diverges again within minutes. Why: a file copy races the live committed log; `state_transfer` takes a *consistent snapshot* at a known `op_num`. Fix: `consensus-vsr state_transfer` from a majority member only. Cost avoided: a re-divergence loop + a lost postmortem artifact. Muscle: trust validated state, never bypass the validated transfer path (the W108 Thursday muscle, operationalized).
  - **(EXPERT) Re-adding to the pool before 100 consecutive matching hashes.** Symptom: the reseeded replica looks healthy, gets re-added, then diverges once on a rare op. Why: a single hash match at rejoin time doesn't prove convergence; the residual `ClockSkew`/wall-clock leak surfaces only on a specific op. Fix: gate rejoin on 100 consecutive `vsr_committed_state_hash` matches against the leader. Cost avoided: a slow re-divergence that surfaces during the next cascade. Muscle: convergence is proven over a window, never a point.

## Tuesday — Runbook: VSR-log / settlement-journal WAL corruption (the venue store)

- [ ] Write `ops-runbooks/vsr-log-wal-corruption.md`. (~45 min)
  - **Triggering alert (W105)**: `WalChecksumMismatch` — a WAL frame's CRC ≠ recomputed CRC on replay, on the venue store's journal (the `wal`/`recovery` substrate consumed *inside* `perp-dex-core`, per §3/§4 "DB substrate built once, exercised inside the venue store").
  - **Inherited fault class (W108)**: `DiskFull` (torn write) + `KillProcess` (crash mid-fsync); optionally `DiskSlow` masking a partial write.
  - **The five operator steps the runbook documents**:
    1. **Stop the bleed** — halt the affected replica's writers; a corrupt journal must not be appended to, and the replica must already be drained (cross-link the Monday divergence runbook).
    2. **Locate the tear** — the `recovery` crate (W29–W30) already reports the first bad frame offset on replay; the runbook says where that log line lives, not how to write a parser.
    3. **Truncate-to-last-good** — `recovery` truncates the WAL at the last frame whose CRC validates; everything after the tear is lost-but-uncommitted by construction (the fsync barrier).
    4. **Verify the truncation point against the VSR commit point** — the last-good frame's `op_num` must be ≤ this replica's last *committed* `op_num` per the cluster. If it is lower, this replica is behind and MUST recover via `state_transfer` from a majority member, NOT proceed on its truncated local log. **A `SettlementId` is the VSR op-number** (§4A): silently proceeding past a committed op means an external client/chain holding that `SettlementId` sees `finality_status` flip — a correctness violation → escalate.
    5. **Restart + reconcile** — bring the replica up as a backup, let `state_transfer` close the gap, confirm `vsr_committed_state_hash` matches before re-adding to the pool.
  - 🎯 **Hardened acceptance**: dry-run against a synthetic torn-WAL fixture (truncate a known-good journal mid-frame with `dd`); the truncate-to-last-good path must recover the replica to a consistent local prefix, AND the verify-step must correctly route to `state_transfer` for the negative case where the tear is *before* the cluster's commit point (the runbook must NOT silently proceed on a stale local log — that would desync a `SettlementId`). MTTR + a "truncate-locally vs state-transfer" decision tree both present.
  - *Mental model*: WAL corruption is where the `recovery` crate (W29–W30) earns its keep — but the *operator* decision (truncate-and-rejoin vs state-transfer vs escalate) is not in the code, it's in this runbook. It exists now because the W106 live rig writes a real VSR journal continuously; a `DiskFull` torn write is a *when*, not an *if*. The v3 twist vs the v2 "mini-db WAL" runbook: there is no standalone DB to recover in isolation — the journal is the venue's *single hot-path log*, so the truncation point must be reconciled against the **cluster's VSR commit point**, and `SettlementId` semantics (§4A) make a wrong truncation an externally-visible finality bug, not just a local data-loss event. This is the W108 Wednesday "validate, don't silently fix" muscle: silently proceeding past a committed op is the operator version of silently re-sorting an out-of-order scenario.
  - **Output**: `ops-runbooks/vsr-log-wal-corruption.md` exists; contains an explicit "BEHIND COMMIT POINT → state_transfer, do NOT proceed locally" branch; `grep -iE "commit point|state_transfer|SettlementId" ops-runbooks/vsr-log-wal-corruption.md` returns the decision-point lines.
