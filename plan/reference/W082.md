  - *Mental model*: an `Image` is one subscriber's private view of one publisher's stream — a cursor that only moves forward, a detector that asks for what's missing, and a small staging area that remembers WHERE the late frames live (offset into the term buffer), never copies of the frames themselves. UDP gives out-of-order + lossy; the Image reconstructs an in-order, gap-free byte stream with bounded memory. In v3 the stream it carries is the **MBO projection of the committed VSR log** — so the in-order guarantee here is what lets a subscriber reconstruct the book byte-identically off the hot path.
  - *Contract* (signature-level only — never the body):
    ```rust
    pub struct Image { /* position: AtomicI64, loss_detector, reorder: ReorderBuffer, status: ImageStatus */ }
    pub enum ImageStatus { Active, Inactive }
    impl Image {
        pub fn on_frame(&mut self, term_id: i32, offset: i32, len: i32, seq: i64) -> OnFrameOutcome;
        pub fn poll<F: FnMut(&[u8])>(&mut self, handler: F, limit: usize) -> usize; // delivers in-order
        pub fn position(&self) -> i64;        // monotonic
        pub fn status(&self) -> ImageStatus;
    }
    pub enum OnFrameOutcome { Delivered, Staged, Gap { nak: Option<NakRange> }, Duplicate }
    // ReorderBuffer stages OFFSET-TRIPLES, not bytes:
    struct ReorderBuffer { buf: BTreeMap<i64, (i32 /*term_id*/, i32 /*offset*/, i32 /*len*/)>, bytes: usize, max_size_bytes: usize }
    ```
  - *Back-of-envelope* (Jeff-Dean numbers): target 10M msg/s = one frame every **100 ns**. In-order fast path must be a few L1/L2 touches (cursor read 0.5 ns + branch + term-buffer slice). At 5% loss, ~500k loss-events/s. If staging copies bytes: `malloc ~50 ns` + memcpy of 64–256 B → ~150 ns/frame × ~50k staged frames/s = **~7.5 ms/s of allocator work**, and the allocator tail lands in P99.9 (cold path 1–10 µs vs hot 100 ns = **10–100× cliff**). Offset-triple staging is a `BTreeMap` insert of 16 B inline-or-small (no heap copy) — keeps the loss path off the allocator. NAK over the wire is a `syscall ~300 ns` (sendto) — must be rate-limited by `nak_delay`, never per-frame.
  - **Requirements** R1..R9 — write in `notes/82_image_design.md`:
    - R1. Throughput ≥10M msg/s in-order delivery sustained 60s LAN at 128 B payload.
    - R2. Under 0% loss: in-order delivery P50 ≤100 ns, P99 ≤500 ns, P99.9 ≤2 µs.
    - R3. Under 5% loss: P50 ≤200 ns, P99 ≤50 µs (NAK+retransmit), P99.9 ≤200 µs, P99.99 ≤500 µs.
    - R4. Zero allocation on the reorder hot path under 5% loss (dhat) — staging uses offset-triple, NOT `Bytes`.
    - R5. Loom-green: position monotonicity (no rollback) + reorder drain correctness under adversarial out-of-order.
    - R6. NAK suppression: under repeated loss + retransmit, NO duplicate NAK inside a `nak_delay` window.
    - R7. Reorder buffer bounded: under a 1s blackout at 10M msg/s, caps at `max_size_bytes`; oldest dropped + NAK fires; never OOM.
    - R8. 100% application-level delivery for 1M messages with 5% uniform loss + 1% reorder + 0.1% duplicate.
    - R9. Graceful degradation under sustained 50% loss: Image marks `Inactive` + surfaces a typed error; never deadlock, never silent drop; transitions back to `Active` on the first valid new frame.
  - **Design walk-through** D1..D6 — answer in the design doc; no peeking at the upstream Aeron source until Phase 3:

    - D2. **Pre-mortem (load-bearing) — BTreeMap-with-`Bytes` allocates per out-of-order frame.** EXACT bad trace: `(1) recv seq=102 (gap, expected 100) → (2) reorder.buf.insert(102, frame.payload.clone()) → (3) clone() = Arc-bump + the underlying Bytes was a view into the term buffer, so to outlive the recv frame it heap-copies 128 B → (4) at 5% loss × 10M/s ≈ 50k inserts/s → 50k mallocs/s → (5) allocator coalescing tail of ~500 µs lands in P99.9.` If you can't write this trace you can't see why offset-triples win.
    - D3. **Pre-mortem — position rollback.** EXACT bad trace: `(1) drain advances position to 105 via position.store(105, Release) → (2) a concurrent late retransmit path computes new=103 from a stale local → (3) position.store(103, Release) → (4) consumer's next poll re-reads frames 103,104 → (5) duplicate delivery, silent.` Prevent with CAS + `new>old` guard.
    - D4. **Pre-mortem — loss-detector false positive.** EXACT bad trace: `(1) UDP reorders: 100 arrives, then 102, then 101 → (2) on 102, naive detector sees gap [101] → fires NAK immediately → (3) 101 arrives 5 µs later anyway → (4) retransmit of 101 also arrives → duplicate + wasted sendto syscalls → NAK storm.` Prevent by gating NAK behind `nak_delay` (W78) so the reorder window can self-heal.
    - D5. **Pre-mortem — reorder memory bomb.** EXACT bad trace: `(1) frame 100 lost permanently (sender gone) → (2) 101..∞ all arrive out-of-order, all staged waiting for 100 → (3) buf grows ~50 MB after 5s at 10M/s → (4) OOM.` Prevent with `max_size_bytes`; on overflow drop oldest + fire NAK.
    - D6. **Pre-mortem — inactive-timeout flap.** EXACT bad trace: `(1) publisher idle > timeout → status=Inactive → (2) publisher resumes, sends frame → (3) on_frame never re-checks status → stuck Inactive forever.` Prevent: any valid in-window frame transitions `Inactive→Active`.
    - **Anti-shortcut audit:** (a) `BTreeMap<_, Bytes>` — obvious, but `Bytes::clone` of a term-buffer view forces a heap copy (R4). (b) `position.store(Release)` — obvious for a counter, but offers no monotonic guard (R5). (c) NAK-on-first-gap — obvious, but conflates UDP reorder with loss (R6). (d) unbounded `BTreeMap` — obvious, but unbounded = memory bomb (R7).

  - [ ] `image_loom_position_monotonic` — **(EXPERT) cross-primitive trap.** `#[cfg(loom)]`; composes the position cursor with a late-retransmit writer; asserts the cursor never regresses under any interleaving. A blind `store(Release)` passes single-threaded tests, fails here. Exercises R5.
    ```rust
    #[cfg(loom)]
    #[test]
    fn image_loom_position_monotonic() {
        loom::model(|| {
            let img = std::sync::Arc::new(Image::loom_new());
            let high = img.position();
            let (a, b) = (img.clone(), img.clone());
            let t1 = loom::thread::spawn(move || a.try_advance(high + 2));
            let t2 = loom::thread::spawn(move || b.try_advance(high + 1)); // stale/late
            t1.join().unwrap(); t2.join().unwrap();
            // try_advance is a `new > old` guarded CAS loop, so the LARGER advance must
            // always win regardless of arrival order. A blind `position.store(new, Release)`
            // lands on high+1 in the interleaving where the stale t2 stores last — and that
            // is exactly the rollback this test exists to catch. Equality-to-MAX is what bites.
            assert_eq!(img.position(), high + 2,
                "a stale try_advance(high+1) must never overwrite an already-attempted high+2 — \
                 blind store(Release) lets the late/stale writer roll the cursor back to {}",
                img.position());
            // weaker floor (kept as a regression net): the cursor must never sink below high
            assert!(img.position() >= high, "cursor regressed below high-water");
        });
    }
    ```

  #### Phase 3 — Make the tests pass, one failure at a time (~110 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(SENIOR) When `image_zero_alloc_under_5pct_loss` reports `reorder hot path allocated 50000 blocks`:**
    - Symptom: dhat/heaptrack shows `BTreeMap`-attributed allocs spiking during loss events; P99.9 delivery latency carries a ~500 µs allocator tail per loss burst.
    - Why: `reorder.buf.insert(seq, frame.payload.clone())` stores owned `Bytes`. The payload was a zero-copy view into the term buffer; cloning it to outlive the recv frame forces a heap copy. 50k allocs/s × 64–256 B ≈ 10 MB/s allocator churn.
    - Fix: stage offset-triples — `BTreeMap<i64, (term_id, offset, len)>` — and read bytes back from the term buffer at drain time; W77's 3-term retention keeps them alive for `3 × TERM_LEN` after publication.
    - Cost avoided: **~150 ns/frame × 50k frames/s ≈ 7.5 ms/s allocator; eliminates the P99.9 allocator tail (bar (c) violation).**
    - Muscle: reorder/gap buffers stage POSITIONS, not data — the bytes already live in the retention window. Reapplies at: W78 NAK gap list (stage gap ranges), W83 ledger settle-over-aeron staging, W84 `log-distributed` projection cursor, W85 marketdata ingest staging.

  - **(SENIOR) When `image_nak_suppression_no_duplicate_in_window` reports `N duplicate NAKs`:**
    - Symptom: counter assertion fires; tcpdump shows a burst of identical NAKs for the same gap, plus duplicate retransmits arriving.
    - Why: detector NAKs on first observed gap, conflating benign UDP reorder with real loss; no suppression window.
    - Fix: gate the first NAK behind `nak_delay` (W78 `time`) and record a `last_nak_at` per gap; suppress repeat NAKs until `now - last_nak_at >= nak_delay`.
    - Cost avoided: eliminates a NAK storm = N× `sendto` syscalls (~300 ns each) + duplicate-retransmit bandwidth on the loss path (bar (c) violation under load).
    - Muscle: a loss-detector must distinguish reorder from loss with a timer; never NAK on first gap. Reapplies at: W78 NAK timer, W84 `log-distributed` consumer-lag NAK, W90 marketdata-kernelbypass gap recovery.

  - **(SENIOR) When `image_reorder_bounded_drops_oldest` reports `OOM / 50 MB after 5s blackout`:**
    - Symptom: reorder `bytes` grows unbounded under a permanent gap; RSS climbs ~50 MB after 5s at 10M/s.
    - Why: no overflow policy — every out-of-order frame behind a never-arriving gap is retained forever.
    - Fix: track `bytes` against `max_size_bytes`; on overflow, drop the oldest staged range and fire a NAK to recover it; document the loss-vs-memory trade-off.
    - Cost avoided: bounded RSS instead of OOM-kill (a bar (c) availability violation).
    - Muscle: any unbounded buffer is a memory bomb — explicit overflow policy is mandatory. Reapplies at: W83 ledger replica-lag, W84 `log-distributed` consumer backlog, W87 VOPR scenario log.

  - **(SENIOR) When `image_graceful_degradation_50pct_loss` deadlocks or stays `Inactive`:**
    - Symptom: under 50% loss Image either spins forever waiting on a gap, or after recovery never delivers again.
    - Why: missing typed degradation path + missing `Inactive→Active` re-arm on a fresh valid frame (D6 flap).
    - Fix: on sustained loss past a threshold, set `Inactive` + return a typed `ImageError::Degraded`; on the next in-window valid frame, transition back to `Active`.
    - Cost avoided: a wedged subscriber that silently stops delivering (availability + correctness violation).
    - Muscle: degradation is a first-class typed state, not an exception — and every terminal state needs an explicit re-arm edge. Reapplies at: W83 ledger replica-lag, W84 integration failover, W90 marketdata feed-down.

  - **(EXPERT) When `image_loom_position_monotonic` reports `a stale try_advance(high+1) must never overwrite an already-attempted high+2 — ... rolled back to high+1`:**
    - Symptom: a loom interleaving where the stale/late writer (`try_advance(high+1)`) stores LAST, so the terminal cursor lands on high+1 instead of the max high+2; the equality-to-max assertion fires. The consumer re-reads frames it already delivered (duplicate delivery, silent). The weaker `>= high` floor would have PASSED this same interleaving — that is precisely why the floor alone is too loose and the equality-to-max assertion is the one that traps the blind store.
    - Why: `position.store(new, Release)` with no monotonic guard — a stale late-retransmit writer unconditionally overwrites a higher value (D3 trace); store is last-writer-wins, not max-wins.
    - Fix: `position.compare_exchange(old, new, Release, Relaxed)` in a loop with a `new > old` guard; on a would-be rollback, drop the update (debug-assert in test builds).
    - Cost avoided: silent duplicate delivery that no single-threaded test catches — fails only under the race (bar (c) correctness violation).
    - Muscle: monotonic counters use guarded CAS, never a blind store. Reapplies at: W4 `AtomicCell` CAS, W74 VSR op_num cursor, W77 term-buffer tail, W83 ledger position.

  - **(EXPERT) When `image_loom_reorder_drain_correctness` reports out-of-order / skipped delivery:**
    - Symptom: under an adversarial loom schedule, the handler sees seq go backward or skip a staged frame.
    - Why: drain advances `position` and pops from the reorder map in two non-atomic steps; an interleaving observes a half-drained state.
    - Fix: make "advance position past contiguous staged run + pop that run" a single critical section per poll; the position is the only authority for what has been delivered.
    - Cost avoided: corrupted in-order guarantee — the whole point of `Image`, and the whole point of an MBO projection that must reconstruct the book byte-identically (bar (c) correctness violation).
    - Muscle: the contiguity check and the position advance are one transaction; never split the read-modify-write of the delivery cursor. Reapplies at: W74 VSR contiguous apply, W77 term reassembly, W84 `log-distributed` projection cursor.

  - **(EXPERT, negative-control) When `image_loom_takes_real_time` reports `loom model too cheap`:**
    - Symptom: the loom model finishes in ~2 ms — it explored a single interleaving, so a green run proves nothing.
    - Why: the work was wrapped in `loom::model` but the threads never touched a shared loom atomic (used `std::sync::atomic` by accident, or only one thread did work).
    - Fix: ensure both writers go through `loom::sync::atomic` on the SAME shared cell; verify ≥2 `loom::thread::spawn` and a contended atomic so the scheduler actually forks.
    - Cost avoided: a false-green loom suite — the most dangerous outcome, because it hides exactly the races loom exists to find.
    - Muscle: always test-the-test — a loom model that runs too fast explored nothing. Reapplies at: W4 loom CachePadded model, W74 VSR loom, W77 term-rotation loom.
