- [ ] **Build**: `crates/p2p/src/gossip.rs` — gossip push path with bounded fanout (8 peers default) + IHAVE/IWANT pull-back. (~total 150 min across 3 phases)
  - 🔧 **Why this matters**: mirrors `libp2p-gossipsub` mesh management; this is the production push path that backs **W56 raft votes/AppendEntries**, **W64 bft block proposals**, and **W76 aeron control plane**. Four specific traps your first attempt will hit: (1) `tick()` scans the seen-LRU to build IHAVE → a 1-Hz CPU spike that breaks raft's heartbeat p99; (2) `app_deliver(&T)` forces the consumer to re-decode + re-hash → 2× cost across the raft heartbeat handler; (3) forwarding without `peer != from` → immediate echo + amplification; (4) the IWANT cache sized to the seen-LRU → a late peer's Want hits an evicted payload → starvation. First-attempt impls fail ≥1 Phase-2 test below, and walking those failures IS the lesson. Bar (c): gossip is the data plane for votes/proposals, so the perf cards carry measured ns/cycles/allocs.

  - *Mental model*: gossip = **epidemic broadcast with dedup**. Each node forwards a never-before-seen message to a bounded random fanout; the message floods the mesh in O(log N) rounds. IHAVE/IWANT is the *anti-entropy* repair channel for peers the push path missed. Mirrors gossipsub's eager-push + lazy-pull split.
  - *Contract*:
    ```rust
    pub struct GossipBroadcast<T: Encodable + Decodable + Clone> {
        seen: lru::LruCache<B256, ()>,         // dedup index, size ~10k
        cache: lru::LruCache<B256, Bytes>,      // raw payloads for IWANT replies, size workload-driven
        recent_ids: ArrayVec<B256, IHAVE_WINDOW>, // recency RING for tick, NOT a scan of `seen`
        peers: Vec<PeerId>,
        fanout: usize,                          // default 8
        per_peer_tx: HashMap<PeerId, backpressure::Queue<Frame>>,
        score: HashMap<PeerId, PeerScore>,      // (delivered_first, delivered_dup, invalid)
    }
    impl<T> GossipBroadcast<T> {
        pub fn publish(&mut self, msg: T);
        pub fn on_recv(&mut self, from: PeerId, gmsg: GossipMsg<T>);
        pub fn tick(&mut self);                 // 1-Hz: emit ONE IHAVE frame from recent_ids
        fn app_deliver(&mut self, id: B256, raw: &[u8], decoded: &T); // pass-through, never re-decode
    }
    enum GossipMsg<T> { Message(T), Have(B256), Want(B256) }
    ```
  - *Back-of-envelope* (bar (c) — gossip is the data plane for raft/bft votes, tx mempool, block proposals):
    - Workload: 100-peer mesh, 10k msgs/s/node (tx-broadcast typical), fanout=8.
    - Inbound fast path (already-seen msg): wire decode of frame header ~50 ns → `seen.contains` hashmap lookup ~40 ns → return. **~90 ns/seen-msg**.
    - Inbound new msg: 90 ns dedup + `app_deliver` callback (consumer budget 200 ns) + fanout to 7 peers × ~50 ns enqueue (no per-peer clone if `Arc<Bytes>` from W52) ≈ **~700 ns end-to-end** (excl. network send).
    - Steady CPU: 10k msgs/s × 7 forwards × 700 ns ≈ 50 ms/s = **~5% of one core**. Goes red the moment fanout does a deep clone or seen-check heap-allocs.
    - IHAVE tick (1 Hz): scanning 10k LRU entries × ~10 ns = **~100 µs/tick scan** + ~32 fresh `Vec<B256>` allocs × ~50 ns = ~1.6 µs alloc. Reading a 64-entry `ArrayVec` = **~0 µs**. Cliff ratio: ~100 µs scan-on-read vs ~5 ns dual-index update = **~20000× per tick**.
  - **Requirements** R1..R10 — write in `crates/p2p/notes/55_gossip_push_design.md`:
    - R1. `publish(msg)`: compute id, insert into `seen` + `recent_ids` + `cache`, app-deliver locally, fan out to `peers[..fanout]`.
    - R2. `on_recv(from, Message(m))`: if id in `seen` → drop; else insert, app-deliver, fan out to `peers - {from}` (filter BEFORE take).
    - R3. `on_recv(from, Have(id))`: if id NOT in `seen` → respond `Want(id)`.
    - R4. `on_recv(from, Want(id))`: if id in `cache` → respond `Message(payload)`; else drop (too old).
    - R5. `cache: LruCache<B256, Bytes>` holds raw encoded bytes; size = `expected_rate × peer_slowness_tolerance × safety_factor` (≥1000).
    - R6. `recent_ids: ArrayVec<B256, IHAVE_WINDOW=64>` ring populated by `publish`/`on_recv` directly; `tick()` reads it once/sec, NEVER scans `seen`.
    - R7. `app_deliver(id: B256, raw: &[u8], decoded: &T)` — pass-through of pre-computed id + raw + decoded; consumer never re-decodes/re-hashes.
    - R8. Backpressure: per-peer bounded queue via `backpressure::Queue` with `BackpressureStrategy::DropOldest` (newer = more relevant) — explicit, not default.
    - R9. Peer-score `(delivered_first, delivered_dup, invalid)`; eject when `invalid > 0.1 * delivered_first`.
    - R10. Budgets: ≤90 ns seen-msg fast path; ≤700 ns new-msg path (excl. send + AEAD); tick CPU ≤1 ms.
  - **Design walk-through** D1..D6 — answer in the design doc; no peeking at libp2p-gossipsub source until Phase 3:
    - D1. **Primitive table** for the per-tick recency summary — fill: `LruCache::iter` (Sync? no; cost O(N)≈100 µs; allocs per-peer Vec; blocking? no) vs `ArrayVec<_,64>` ring (cost O(1); 0 allocs). Why the small absolute scan cost still matters → answer with the p99 argument.
    - D2. **app_deliver signature** — write both versions. bar-(b) `fn app_deliver(&T)` forces the consumer to recompute its own id (re-encode + re-hash). bar-(c) `fn app_deliver(id, raw, decoded)` passes the work product through. Compute saved cost at raft heartbeat scale (16-node × 200 msg/s = 3200 deliveries/s × 700 ns ≈ 2 ms/s).
    - D3. **cache sizing** — a `Want(id)` from a slow peer arrives N seconds after publish. If `cache.len() < rate × N`, the payload was evicted → empty Want → starvation. Compute size for 10k msg/s and 5 s slowness tolerance.
    - D4. **Backpressure strategy** — why DropOldest not DropNew for gossip? When is DropNew correct? (never in gossip; sometimes WAL replay).
    - D5. **Peer-score** — write the eject condition; define `delivered_first` (useful) vs `delivered_dup` (harmless waste); why an invalid msg weighs more than a dup.
    - D6. **Pre-mortem (load-bearing)** — write the EXACT 4-5 line trace from "tick walks seen-LRU" to "1-Hz CPU spike misses raft's 50-ms heartbeat SLO". If you can't write the bad trace you can't prove the ring fixes it.

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)
  Newbie failures first, expert last — the ladder you actually walk.

  - **(NEWBIE) When `gossip_no_echo_to_sender` shows the sender in the forward list:**
    - Symptom: peer A sends to B; B forwards to all peers including A; `sent_to.contains(&A)` is true and count is off by one.
    - Why: the forwarding loop is `self.peers.iter().take(fanout)` with no `peer != from` filter, OR the filter is placed AFTER `take` (so a slot is wasted on `from` then discarded, shrinking effective fanout).
    - Fix: `for peer in self.peers.iter().filter(|p| **p != from).take(self.fanout)` — filter BEFORE take.
    - Muscle: every broadcast-with-exclude needs the exclude filter BEFORE the count limiter. **Reapplies at**: W56 raft AppendEntries to follower list (exclude self), W64 bft proposal broadcast (exclude proposer), W76 aeron multicast subscriber fan-out.

  - **(NEWBIE) When `gossip_50_node_delivery_in_log_n` delivers to <50 nodes:**
    - Symptom: flood stalls at ~8 nodes (the publisher's direct fanout) and never reaches the rest.
    - Why: `on_recv(Message)` inserts into `seen` but the fanout branch is gated wrong — either it returns before forwarding, or it forwards only on `publish` not on relay.
    - Fix: on a *new* (not-in-seen) inbound message, BOTH app-deliver AND fan out to `peers - {from}`; relay is what makes it epidemic.
    - Muscle: epidemic broadcast requires every node to relay novel messages, not just the origin. **Reapplies at**: W56 raft log-entry propagation, W64 bft echo phase.

  - **(SENIOR) When `gossip_backpressure_drops_oldest` shows the newest msg dropped:**
    - Symptom: under overload a slow peer keeps msg 0 and drops msgs 1-9; peer holds stale votes and never catches up.
    - Why: `backpressure::Queue` was constructed with `BackpressureStrategy::default()`, which is DropNew (the "fairness" default in many libraries).
    - Fix: `backpressure::Queue::with_strategy(BackpressureStrategy::DropOldest)` — gossip ALWAYS prefers the newer message; older votes for the same proposal are stale.
    - Cost avoided: not ns but *correctness-as-liveness* — DropNew silently silences every latest update under load (a stalled follower in raft).
    - Muscle: backpressure policy is a per-channel decision; never inherit a library default on a hot path. **Reapplies at**: W56 raft AppendEntries queue (DropOldest), W76 aeron Publication overflow (DropOldest for streams, DropNew for control).

  - **(SENIOR) When `gossip_tick_no_lru_scan` reports samples in `LruCache::iter` and `gossip_tick_zero_alloc` shows ~32 allocs/tick (bar (c) violation):**
    - Symptom: the 1-Hz timer pegs ~1% CPU just on IHAVE accounting; under timer drift ticks pile up; p99 latency spikes correlate with tick boundaries; `perf` shows samples in `LruCache::iter`, dhat shows ~32 allocs/tick.
    - Why: naive `tick()` walks `self.seen.iter()` (10k entries) to find "recent" ids, then allocates a fresh `Vec<B256>` per lazy peer. 10k × ~10 ns scan = ~100 µs; 32 × ~50 ns alloc = ~1.6 µs.
    - Fix: maintain `recent_ids: ArrayVec<B256, IHAVE_WINDOW>` populated by `publish`/`on_recv` (the call sites already touch each id). `tick()` reads the ring once, encodes ONE `IHave(ids)` frame into an `Arc<Bytes>`, fans out via `Arc::clone` (no per-peer alloc).
    - Cost avoided: ~100 µs/s scan + ~50 µs/s alloc ≈ **~150 µs/s** CPU, AND removes a per-tick spike that breaks p99 SLOs **(bar (c) violation: a periodic spike on the vote data plane)**.
    - Muscle: never scan a hashmap to "find recent things" — maintain the recency index alongside the lookup index; dual-index update is ~5 ns, scan-on-read is O(N) per call. **Reapplies at**: W56 raft `last_log_term`/`last_log_index` (maintain as fields, don't scan the log), W74 matching-engine `top_n_bids` (maintain a heap, don't sort price levels), W76 aeron `recent_subscribers_for_topic`.

  - **(SENIOR) When `gossip_app_deliver_signature_is_pass_through` fails to reject `app_deliver(&T)` / `perf` shows double decode (bar (c) violation):**
    - Symptom: trybuild accepts the 1-param signature (contract too loose), OR at runtime `perf record` shows `T::decode` and `keccak256` each TWICE in the receive flame; raft heartbeat handler is 2× expected.
    - Why: `app_deliver(&T)` forces the consumer (raft) to re-derive what gossip already knows — id from the frame hash, raw from the wire — so it re-encodes + re-hashes.
    - Fix: trait signature is `fn app_deliver(&mut self, id: B256, raw: &[u8], decoded: &T)`. Gossip already decoded and computed the frame-hash id (W52 Sat); pass them through. Expose `(id, raw)` as the primary callback so relay-only consumers can skip decoding entirely.
    - Cost avoided: ~500 ns decode + ~200 ns hash per inbound × 10k/s = **~7 ms/s CPU**; on a 16-peer cluster it multiplies across cores **(bar (c) violation)**.
    - Muscle: layered codec architectures must pass the work product forward — never re-do an already-completed decode/hash in the layer above. **Reapplies at**: W56 raft `commit_index` advance (propagate computed indices, don't re-walk log), W64 bft block-hash propagation, W76 aeron `Image::fragment_handler` receives raw AND decoded.

  - **(EXPERT) When `gossip_cache_resists_eviction_for_5s` shows ~30% eviction of 5s-old msgs:**
    - Symptom: a late peer's `Have(id)` for a 5s-old msg gets a `Want`, but `cache.get(id)` is empty → no `Message` reply → peer starves.
    - Why: `cache` was sized to the seen-LRU size (10k); at 10k msg/s sustained the cache fully turns over every 1 s, so anything older than ~1 s is gone.
    - Fix: `cache_size = expected_rate × peer_slowness_tolerance × safety_factor` (10k × 5s × 2 = 100k entries ≈ 100 MB at 1 KB avg). Trade memory for delivery completeness.
    - Cost avoided: silent message starvation for slow peers — a liveness bug invisible to the happy-path delivery test.
    - Muscle: cache sizing is workload-driven, never a copy-paste constant; derive it from rate × tolerance. **Reapplies at**: W56 raft log-retention window (size to slowest-follower lag), W76 aeron term-buffer sizing.

  #### 5-year failure mode
  Write in `crates/p2p/notes/55_gossip_push_followup.md` after green: when the network scales to 10k peers (post-blockchain L2 mesh), `recent_ids: ArrayVec<_, 64>` holds <1 ms of msgs and IHAVE frames become huge or lossy. **Trigger**: measured IHAVE frame size > MTU, or recent_ids overflow rate > 1%/tick. **Migration (1-line)**: swap `recent_ids` for a CountMinSketch-backed recency index with bounded memory and a tunable false-positive rate.

  - **(NEWBIE) When `inner_revert_rolls_back_state_and_logs` shows `logs.len() == 2`:**
    - Symptom: balance restored but the inner LOG0 survived; receipt would carry a phantom log.
    - Why: `checkpoint_revert` popped/inverted journal entries but never truncated `self.logs`.
    - Fix: `self.logs.truncate(cp.log_i);` as the FIRST line of `checkpoint_revert`.
    - Muscle: a checkpoint snapshots EVERY mutable collection (journal AND logs AND transient); revert must roll back all of them. **Reapplies at**: W68 exec-vm receipt building, W66 tempo log handling.
  - **(SENIOR) When `outer_revert_undoes_committed_inner_frame` leaves the SSTORE applied:**
    - Symptom: after outer revert, `sload(X,1)` is still 7; the committed inner change is unreachable.
    - Why: `checkpoint_commit` did `self.journal.pop()` (dropped the frame) instead of merging it into the parent.
    - Fix: `let frame = self.journal.pop().unwrap(); self.journal.last_mut().unwrap().extend(frame); self.depth -= 1;`.
    - Muscle: commit promotes undo entries to the parent — never discard them, or outer reverts lose reach. **Reapplies at**: W56 raft log commit (committed entries stay until snapshot), W68 exec-vm CALL/CREATE commit.
  - **(EXPERT) When `three_level_revert_isolates_middle_frame` corrupts A's balance:**

    - Muscle: a checkpoint is an exact boundary — revert pops to it precisely, never one entry past. **Reapplies at**: W56 raft truncate-to-index, W68 exec-vm deep call stacks.
