**Friday (post-EthCC) — `runtime-thread-per-core` v0.5: cross-shard channel** [NEW v2]

- [ ] **Build**: `crates/runtime-thread-per-core/src/cross_shard.rs` — lock-free per-shard-pair MPMC channel via `concurrent::SegQueue`, typed-enum payload, CachePadded backpressure counters. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: cross-shard messaging IS the thread-per-core architecture — it mirrors Seastar's `smp::submit_to`. Without it shards can't cooperate; done badly you reintroduce locks and cache-line contention that kill scalability. Three traps wait here: (1) `Box<dyn FnOnce>` payload heap-allocs per submit (allocator-lock saturation), (2) the shared depth counter false-shares across cores (MESI ping-pong), (3) NUMA-oblivious routing saturates the UPI link. First-attempt impls fail ≥ 1 Phase-2 test below and the debug session is the lesson. Every Tier-A HFT IC bar-(c) question on TPC architecture eventually asks "how do you pass a message from shard 0 to shard 5 without lock contention?" Downstream: W58 matching-engine scaffold, W74 price-level counters, W85+ marketdata feed shards, W90+ ledger per-shard SM — a 50 ns/submit cliff item costs 30-50% of aggregate throughput.

  #### Phase 1 — Problem, prediction, design (~70 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `notes/57_cross_shard_prediction.md` BEFORE any code:
    - **P1** (primitive): the exact import line you'd reach for to hold the queue and the payload (predict `crossbeam_queue::SegQueue<Box<dyn FnOnce() + Send>>` if you're being naive — write what you'd actually type).
    - **P2** (latency): predict `submit_to` p50 same-NUMA uncontended in ns, and predict the same number once `Box<dyn FnOnce>` boxing is in the path. (Reality: ~30-50 ns typed vs ~90-130 ns boxed.)
    - **P3** (concurrent-first-call): predict the 16-shard all-to-all throughput ratio of a CachePadded `capacities` array vs a bare `Box<[AtomicUsize]>`. (Reality: ≥ 5×.)
    - **P4** (correctness): predict whether `Relaxed` on the capacity counter is sound for the backpressure trip, and whether `pop` needs `Acquire`. Justify in one line each.
    - **P5** (self-trap): **list every Phase-2 test you predict your first attempt will fail.** Compare to reality after the tests run; the gap is the lesson.
  - *Mental model*: a typed message bus between pinned per-core reactors. One SPSC-shaped lane per (sender, receiver) pair so neither push nor pop contends; a single padded depth gauge per receiver carries backpressure.
  - *Contract*:
    ```rust
    use crossbeam_queue::SegQueue;
    use crossbeam_utils::CachePadded;

    #[derive(Clone, Copy)] pub struct ShardId(pub usize);

    pub enum CrossShardOp { Order(Order), Cancel(CancelId), Subscribe(SubReq) /* sized to largest variant */ }
    pub struct TaskBox { pub op: CrossShardOp, pub return_to: Option<ShardId> }

    pub struct CrossShardChannel {
        queues: Box<[Box<[CachePadded<SegQueue<TaskBox>>]>]>, // queues[from][to]
        senders: usize,
        capacities: Box<[CachePadded<AtomicUsize>]>,          // per-receiver depth gauge
        threshold_high: usize, threshold_low: usize,
        sensors: Box<[Sensor]>,
    }
    impl CrossShardChannel {
        pub fn submit_to(&self, from: ShardId, to: ShardId, t: TaskBox) -> Result<(), Overflow>;
        pub fn drain_inbox(&self, me: ShardId) -> Vec<TaskBox>; // ≤ 64-msg batch
    }
    ```
    Never write the bodies here — that's Phase 3.
  - *Back-of-envelope* (bar (c) — target ≥ 10M msgs/s aggregate, p99 < 5 µs):
    - 16 shards × `CachePadded<SegQueue<TaskBox>>` matrix = 256 queues. Padded queue-state ≈ 128 B × 256 ≈ 32 KB; trivial.
    - `submit_to` uncontended same-NUMA: `capacities[to].fetch_add(Relaxed)` ≈ 5 ns + `SegQueue::push` (CAS on segment tail) ≈ 25-40 ns ⇒ **30-50 ns/submit**. Budget ≤ 100 ns ⇒ 10M ops/s/core ceiling.
    - `submit_to` cross-NUMA: counter + tail pointer live on receiver's node ⇒ cross-NUMA cache-line invalidation ~100-200 ns vs ~5 ns same-NUMA ⇒ **40× cliff** (ScyllaDB's measured UPI/Infinity-Fabric number). Hence the strict same-NUMA routing preference (drops to ~5M ops/s/core cross-NUMA).
    - `drain_inbox`: 1 reader, no pop contention ≈ 20 ns/pop × 64 batch ≈ **1.3 µs/drain**. At 100k drains/s/shard × 16 = ~2.1 ms/s aggregate overhead.
    - **50-ns cliff items** (false sharing on the depth counter, missing CachePadded on SegQueue, malloc in TaskBox) each cut aggregate throughput 30-50%.
  - **Requirements** R1..R8 — write in `crates/runtime-thread-per-core/notes/57_cross_shard_design.md`:
    - R1. NxN matrix of `SegQueue<TaskBox>`: one queue per (sender, receiver) pair. 16 shards = 256 queues.
    - R2. Single popper per receiver column → no cross-receiver pop contention; single pusher per (from, to) cell from the sender's thread → no cross-sender push contention.
    - R3. Per-receiver depth counter `capacities[to]: CachePadded<AtomicUsize>` for the backpressure trip — each counter on its own cache line (`size_of::<CachePadded<AtomicUsize>>() >= 64`, ideally 128 on x86-64). False sharing here costs the entire scaling target.
    - R4. `TaskBox` payload is a TYPED enum sum (`CrossShardOp`), NOT `Box<dyn FnOnce>`. Stack-allocated; zero per-submit heap alloc.
    - R5. `submit_to` budget: ≤ 100 ns same-NUMA uncontended (10M ops/s/core ceiling). Cross-NUMA ~5M ops/s/core accepted.
    - R6. `drain_inbox` budget: ≤ 1.5 µs/drain (64-msg batch cap) — the cap prevents shard starvation.
    - R7. Ordering: `Acquire` on pop, `Release` on push (matches SegQueue internals); `Relaxed` on the capacity counter is correct (eventual consistency for the trip).
    - R8. Backpressure hysteresis: trip on `depth >= threshold_high`; clear on `depth < threshold_low` (wide gap, e.g. 1024 / 512).
  - **Design walk-through** D1..D6 — answer in the design doc; no peeking at Seastar source until Phase 3:
    - D1. Property table of every payload choice — `Box<dyn FnOnce>` vs typed enum vs slab-index — columns: heap allocs/submit? dispatch cost (vtable vs branch)? Send-bound surface? variant-count flexibility? Conclude why typed enum wins on the hot path and exactly when `Box<dyn FnOnce>` wins (unbounded/unknown-at-compile-time variant set — never on a TPC hot path).
    - D2. Why one queue per (sender, receiver) pair, not N receiver queues? Walk the contention: N receiver queues ⇒ M senders contend `push` per receiver; NxN ⇒ 1 sender per cell, uncontended. Memory: 256 × ~128 B = 32 KB, trivial.
    - D3. False-sharing on `capacities`: 16 × `AtomicUsize` = 128 B packed in 2 cache lines; every increment from any shard invalidates other shards' lines. Compute the MESI-bounce: ~7 ns L2 fetch × 10M ops/s × 16 contended cores ≈ ~70 ms/s CPU. Padded: 16 × 128 B = 2 KB. (W004 muscle — write the fix from memory.)
    - D4. NUMA preference: shard 0 (NUMA0) → shard 8 (NUMA1) costs ~100-200 ns vs ~5 ns same-NUMA (40× cliff). Route by affinity: shards 0-7 on NUMA0, 8-15 on NUMA1; routing hash incorporates NUMA-locality.
    - D5. Batched drain (64-msg cap): walk the starvation scenario where one shard's inbox is gigantic — unbounded drain monopolizes the receiver's reactor turn, downstream shards miss heartbeats.
    - **D6. Pre-mortem (load-bearing):** write the EXACT 4-step interleaving from "default `Box<dyn FnOnce>` payload" to "throughput plateaus at ~1-2M msgs/s no matter how many shards." Then a second 4-line trace from "bare `Box<[AtomicUsize]>` counters" to "16-shard scaling regresses 3-5×." If you can't write the bad interleaving, you can't prove your design prevents it.
    - **D7. Anti-shortcut audit:** name the obvious reach for each motivation and one line on why it's wrong HERE — (a) "just box the closure, it's only a pointer" → it's a malloc + dealloc + vtable per submit at 10M ops/s; (b) "`Box<[AtomicUsize]>` is the idiomatic counter array" → packs 16 counters into 2 lines = false sharing; (c) "`Mutex<VecDeque>` per receiver is simpler" → 25 ns mutex + cross-sender contention defeats the per-pair design.
  - 🧮 **Paper drill** — write in `notes/57_cross_shard_drill.md`:
    - **D-HB** on the SPSC publish of one `TaskBox` from shard 0's pusher to shard 1's popper through `queues[0][1]`: two columns (sender / receiver). Draw PO edges; mark the `SegQueue::push` tail-CAS as the Release store and the `drain_inbox` `pop` as the Acquire load; draw the RA edge from the Release-push to the Acquire-pop; chain `TaskBox` write → the receiver's read of `op`. Verdict: does the popper observe the fully-written `TaskBox`? **Then the NEGATIVE:** weaken the `pop` to `Relaxed` (the R7-violating "Relaxed everywhere" case) and draw the interleaving where the receiver reads a half-published `TaskBox` / a stale slot — exactly the `loom_submit_drain_no_lost_msg` `got+got2 == 0` failure.
    - **D-RMW** on `capacities[1].fetch_add(1, Relaxed)` (push side) vs `fetch_sub(1, Relaxed)` (drain side): a 2-thread step table — row = step, columns = pusher / drainer / the counter value. Show the lost-update a plain `load; +1; store` would cause (two pushers both read depth=5, both store 6, true depth is 7), and the RMW that prevents it.   #### Phase 3 — Make the tests pass, one failure at a time (~95 min)

  Ordered newbie → expert; the ladder you actually walk.

  - **(NEWBIE) When `drain_bounded_to_64` returns 1000 msgs in one call:**
    - Symptom: a saturated inbox drains entirely; the receiver's reactor turn monopolizes; downstream shards miss their heartbeat tick.
    - Why: the `drain_inbox` loop has no `if drained.len() >= 64 { return drained; }` early-exit.
    - Fix: explicit batch cap inside the drain loop; remaining msgs picked up on subsequent reactor turns.
    - Cost avoided: one starving shard stalls the whole reactor — a latency-tail and liveness bug, not just slow.
    - Muscle: every reactor-side drain has a batch cap; unbounded drain is a starvation primitive. **Reapplies at**: W76+ aeron `Subscription::poll`, W84 runtime v1.0 reactor turn, W90+ ledger replica apply loop.

  - **(NEWBIE/SENIOR) When `capacities_each_on_own_cache_line` reports stride 8 (not ≥ 64) and `false_sharing_padded_vs_bare` shows ratio ~1.2× (not ≥ 5×):**
    - Symptom: stride assertion fails at 8 B; 16-shard scaling shows 3-5× regression; `perf stat -e cache-misses,cache-references` shows ~10-15% miss rate on the capacities array.
    - Why: `capacities: Box<[AtomicUsize]>` = 16 × 8 B = 128 B packed in 2 cache lines; every `submit_to(*, to=5)` invalidates the line holding `capacities[4..11]` on every other sender's core — MESI ping-pong dominates.
    - Fix: `capacities: Box<[CachePadded<AtomicUsize>]>` (crossbeam-utils `CachePadded`, or `#[repr(align(128))] struct PaddedCounter(AtomicUsize)`); each counter on its own cache line; mem cost 16 × 128 = 2 KB.
    - Cost avoided: ~7 ns L2 fetch per `fetch_add` × 10M ops/s × 16 contending cores ≈ ~70 ms/s CPU + the 3-5× throughput cliff (**bar (c) violation** — disqualifies the crate from its scaling bar). Green `cargo test`, RED bench.
    - Muscle: any atomic touched by multiple cores must be cache-line padded; the default `Box<[AtomicT]>` is a bar-(c) failure waiting to happen, and it hides inside matrices/arrays, not just structs. **Reapplies at**: W74 matching-engine per-symbol sequence counters, W76+ aeron `Publication::term_position`, W90+ ledger replica progress counters, W94 block-stm transaction-status atomics.

  - **(SENIOR) When `submit_zero_alloc` reports ~10M allocs/s and `bench_submit_under_100ns` p50 ≈ 200 ns:**
    - Symptom: `perf top` shows `__GI___libc_malloc` and the global allocator lock contending with the workload; throughput plateaus at ~1-2M msgs/s no matter how many shards; `dhat` shows ~50 ns malloc + ~30 ns dealloc per submit.
    - Why: every `submit_to` boxes the closure (`Box<dyn FnOnce>` payload) — 10M msgs/s aggregate = 10M allocs/s ≈ ~500 ms/s allocator CPU = saturation.
    - Fix: replace `Box<dyn FnOnce>` with `enum CrossShardOp { Order(Order), Cancel(CancelId), Subscribe(SubReq), .. }` sized to its largest variant, stack-allocated in `TaskBox`; handler dispatches via `match` (branch-predicted, no vtable). For genuinely variant-shaped tasks, a per-shard typed slab/`bufpool` (W14) pre-allocates `TaskBox`s and submit transfers a slab index, not a Box.
    - Cost avoided: ~50 ns malloc + ~30 ns dealloc per task × 10M ops/s ≈ ~800 ms/s CPU = full saturation eliminated; restores linear-scaling target (**bar (c) violation** when boxed). Same family as W003 Friday `rate_limit` `Box::pin` regression, at the shard-message layer.
    - Muscle: `Box<dyn FnOnce>` is convenient but mortal on the hot path; typed enums or slab-allocated boxes are the bar-(c) cure. **Reapplies at**: W58 matching-engine cross-symbol cancels, W76+ aeron `Publication::offer` (pre-allocated term-buffer slot, not Box), W83+ ledger op-log entries, W94 block-stm task queue.

  - **(SENIOR) When `backpressure_trips_and_clears` ping-pongs at ~10 kHz:**
    - Symptom: sensor flips trip/clear thousands of times/sec under sustained load; senders see a jittery backpressure signal.
    - Why: no hysteresis — `threshold_high == threshold_low` (or close); depth oscillates around the boundary.
    - Fix: wide gap, e.g. `threshold_high = 1024; threshold_low = 512;` — trip at 1024, clear only below 512.
    - Cost avoided: chatter forces senders to repeatedly re-route/retry — a self-inflicted throughput tax under exactly the load you most want to handle.
    - Muscle: every threshold-driven signal needs hysteresis; without it, every threshold-crossing produces chatter. **Reapplies at**: W74 matching-engine rate-limit, W76+ aeron flow control, W83+ ledger journal-pressure.

  - **(EXPERT) When `loom_submit_drain_no_lost_msg` reports `got + got2 == 0` or `== 2`:**
    - Symptom: loom finds an interleaving where the message is lost or double-delivered; or `loom_actually_explores` shows the run finished in < 100 ms (model explored nothing).
    - Why: `Relaxed` everywhere lets the `capacities` decrement on the drain side reorder across the `pop`, so a producer's `push` (Release) isn't observed by the consumer's `pop` (which must Acquire) — the SegQueue's own ordering is fine, but the *capacity bookkeeping* races and can drop or resurrect a slot.
    - Fix: `Acquire` on pop / `Release` on push for the queue handoff; keep `capacities` `Relaxed` but decrement it AFTER the Acquire-pop succeeds, never speculatively. Re-run loom until it explores ≥ 100 ms of interleavings.
    - Cost avoided: a once-per-billion lost cross-shard message = a silently dropped order or cancel in production (**bar (c) violation** — correctness, not perf).
    - Muscle: in a producer/consumer pair the handoff edge needs Release→Acquire; relaxed bookkeeping is only sound when it trails the synchronizing edge. **Reapplies at**: W11 bounded MPMC, W26 SegQueue/WAL group-commit, W84 runtime reactor, W90+ ledger log apply.

  - **(EXPERT) When `linear_scaling_to_16_shards` plateaus around 4 shards:**
    - Symptom: aggregate throughput hits a wall between 4 and 8 shards; adding more shards reduces per-shard throughput; `perf` shows UPI saturation.
    - Why: cross-NUMA UPI saturation — shards 0-7 on NUMA0, 8-15 on NUMA1; uniform-random routing produces 50% cross-NUMA traffic; the UPI link saturates ~3 GB/s.
    - Fix: shard placement matches the routing hash. matching-engine: `hash(symbol) mod N_SHARDS_PER_NUMA` keeps hot symbols on the originating socket. Control-plane uniform workloads: accept cross-NUMA cost; backpressure earlier via `threshold_high`.
    - Cost avoided: the cross-NUMA 40× per-message cliff applied to half your traffic — caps aggregate well below the 10M target (**bar (c) violation**).
    - Muscle: TPC's scaling assumption is "same-NUMA routing dominates"; a NUMA-oblivious hash breaks the assumption. **Reapplies at**: W74 matching-engine, W85+ marketdata, W90+ ledger.
