**Thursday — Build: snapshot EXPORT format (bar b, correctness)**

> **Day-load note**: Thursday = 50 (design) + 40 (tests) + 120 (Phase 3, may bleed to Fri AM) + 10 = ~3.7h. The export Build is bar (b) (no latency budget — the trap is consensus-correctness of the serialized image), so it's lighter than Friday's bar-(c) import.

- [ ] **Build**: `crates/storage-trie/src/snapshot/export.rs` + `src/snapshot/format.rs` — serialize the current trie state into a self-describing, checksummed snapshot file whose header carries `lsn_high`, such that a from-scratch state root over the EXPORTED data equals the live state root. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: this mirrors reth's `NippyJar`/`StaticFileProducer` segment writer and Erigon's `.seg` segment format. The export is the producer side of the snapshot-import≡checkpoint protocol; if the exported image is byte-wrong, every importer derives a wrong state root = a silent consensus split on every node that fast-syncs from it. Three traps make a naive first attempt WRONG, not slow: (1) **unsorted key emission** — you iterate the trie/DB in hash-map order, so two exports of the same state produce different bytes and a content-addressed/checksummed segment is non-reproducible (and a re-derived root over the unsorted dump diverges); (2) **checksum-before-payload ordering** — you write the header (with `lsn_high`) and checksum FIRST, then the payload, so a torn write leaves a valid-looking header over a truncated body and import accepts garbage; (3) **`lsn_high` captured from the wrong point** — you read the LSN AFTER iterating state instead of pinning a consistent snapshot LSN BEFORE iteration, so concurrent writers slip records between your `lsn_high` and the actual exported state (the export is "between" two LSNs and equivalent to no real checkpoint). Downstream: storage-trie v1.0 (W43-44) ships this; mini-db (W97-100) reuses the format; Friday's import consumes exactly these bytes.

  - *Mental model*: a snapshot export is a **deterministic, sorted, self-describing dump of (path → account) rows at one pinned LSN**, framed `[header(lsn_high, version) | sorted rows | offset index | footer(checksum)]`. Determinism (sorted order) + footer-last checksum are what make it reproducible and torn-write-detectable.
  - *Contract* (signatures only — NEVER the body):
    ```rust
    // format.rs
    #[repr(C)]
    pub struct SnapshotHeader {
        magic: [u8; 4],          // b"STSN"
        format_version: u16,     // bumped on layout change; import rejects mismatch
        lsn_high: Lsn,           // the checkpoint watermark this snapshot equals
        item_count: u64,
    }
    pub struct SnapshotFooter { checksum: u32 } // CRC32 over header+payload+index, written LAST
    pub const SNAPSHOT_MAGIC: [u8; 4] = *b"STSN";
    pub const SNAPSHOT_FORMAT_VERSION: u16 = 1;

    // export.rs
    pub struct SnapshotExporter<'a, S: TrieStorage> { storage: &'a S, lsn_high: Lsn }
    impl<'a, S: TrieStorage> SnapshotExporter<'a, S> {
        /// `lsn_high` MUST be pinned by the caller BEFORE state iteration (consistent snapshot point).
        pub fn new(storage: &'a S, lsn_high: Lsn) -> Self;
        /// Writes header → sorted [path|rlp(Account)] rows → offset index → footer(checksum).
        /// Returns bytes written. Caller fsyncs, THEN flips any watermark.
        pub fn write_to(&self, out: &mut impl Write) -> io::Result<u64>;
    }
    ```
  - *Back-of-envelope* (bar (b) — sizing the image, not a latency budget): one account row ≈ `path(32 B) + rlp(Account){nonce, balance, storageRoot 32 B, codeHash 32 B} ≈ ~110 B`. 100k accounts ≈ **~11 MB payload** + an `8 B/row` offset index (~800 KB) + 18 B header + 4 B footer. A 250M-account mainnet state ≈ **~27 GB** — implication: the format MUST stream (one row at a time, bounded buffer), never materialize the whole image in RAM, and the offset index is what lets import seek without scanning 27 GB.
  - *Anti-shortcut audit* — name the tempting-but-wrong move (each is exactly what a Phase-2 test below must fail on):
    - **Iterate state via `HashMap`/`std::collections::HashMap` order.** Wrong: non-deterministic byte output → checksum changes run-to-run, content-addressing breaks, re-derived root over the dump diverges. → trapped by `export_is_byte_reproducible` / `export_rows_sorted_by_path`.
    - **Write the checksum/header first, payload after.** Wrong: a torn write leaves a valid-looking 18-byte header over a truncated body; import can't detect it. → trapped by `export_footer_checksum_detects_truncation`.
    - **Capture `lsn_high = wal.current_lsn()` after the loop.** Wrong: concurrent writes land between iteration start and the LSN read; the image is not a consistent point-in-time → import installs a barrier that doesn't match the data. → trapped by `export_lsn_matches_pinned_snapshot_point`.

  - **Requirements** — write in `crates/storage-trie/notes/36_export_design.md`:
    - R1. `SnapshotHeader { magic, format_version, lsn_high, item_count }`, `#[repr(C)]`, written first; `magic == SNAPSHOT_MAGIC`.
    - R2. Rows emitted in **ascending `path` (nibble/byte) order**, each `[path | rlp(Account)]`; byte-for-byte reproducible for identical state.
    - R3. An **offset index** (one `u64` byte-offset per row) appended after the rows, enabling O(log n) seek on import.
    - R4. `SnapshotFooter { checksum: CRC32 }` over `header || rows || index`, written **LAST** after the payload is fully streamed.
    - R5. `lsn_high` is a constructor argument pinned by the caller BEFORE iteration (the exporter never reads the live LSN itself).
    - R6. `write_to` streams (bounded buffer); never collects all rows into a `Vec` first.
    - R7. Round-trip with Friday's import over a known fixture state reproduces the identical state root.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min, may bleed to Friday AM)
  Ordered newbie→expert.

  - **(NEWBIE) When `export_rows_sorted_by_path` reports non-ascending paths:**
    - Symptom: row paths come out `0x9.., 0x1.., 0x5..` — insertion/hash order, not sorted.
    - Why: you iterated the state via a `HashMap` (or unsorted DB cursor) and emitted rows as-they-came.
    - Fix: iterate via a sorted cursor / `BTreeMap` over `path`; emit in ascending nibble order.
    - Muscle: a serialized consensus/checksummed image MUST have a single canonical (sorted) byte order. Reapplies at: W39 lsm-core SSTable key order, W43 storage-trie v1.0 snapshot, W97 mini-db SSTable export.

  - **(SENIOR) When `export_is_byte_reproducible` reports differing bytes despite sorted rows:**
    - Symptom: rows sorted, yet the two buffers differ in a few scattered bytes (often inside the header).
    - Why: `SnapshotHeader` is `#[repr(C)]` but you wrote it via `as_bytes()` of the struct with **uninitialized padding** between fields, so stale stack bytes leak in.
    - Fix: serialize each header field explicitly (`out.write_all(&self.lsn_high.to_le_bytes())`...), never blit a padded `#[repr(C)]` struct; or `#[repr(C, packed)]` + zero-init.
    - Muscle: never `transmute`/blit a padded struct into a checksummed byte stream — padding is uninitialized and non-reproducible. Reapplies at: W39 lsm-core block header, W77 aeron term metadata, W97 mini-db page header.

  - **(SENIOR) When `export_footer_checksum_detects_truncation` accepts a truncated buffer:**
    - Symptom: you lop a byte off the end, import still says "valid."
    - Why: the checksum was computed/written in the header (leading), so the trailing truncation isn't covered.
    - Fix: stream the payload first, fold CRC32 as you go, write the 4-byte footer LAST; verify by recomputing over `buf[..len-4]` and comparing to the trailing 4 bytes.
    - Muscle: the integrity marker must be written LAST and cover everything before it, so a torn write is a short/missing footer. Reapplies at: W43 storage-trie snapshot, **Friday's import barrier ordering (this week)**, W97 mini-db manifest checksum.

  - **(EXPERT) When `export_lsn_matches_pinned_snapshot_point` finds rows written after `lsn_high`:**
    - Symptom: `lsn_high` is correct but some exported rows carry `written_lsn > lsn_high`; or `lsn_high` itself drifted to a later value.
    - Why: you read the LSN after iterating, and/or iterated the LIVE state instead of a read-snapshot pinned at `pinned` — concurrent writers leaked in.
    - Fix: pin the LSN from the same read-transaction that snapshots the state (`s.read_at(pinned)`); pass it in; never call `wal.current_lsn()` inside the exporter.
    - Muscle: a point-in-time image must be read through ONE consistent snapshot pinned BEFORE iteration; the watermark and the data must come from the same read-view. Reapplies at: W42 txn MVCC read-view, W67 raft snapshot install index, W83 ledger snapshot LSN, W97 mini-db checkpoint.

  - 🔧 **Why this matters**: this mirrors reth's static-file watermark flip + ARIES fuzzy-checkpoint install, and it is the CONSUMER side of Monday's "snapshot-import ≡ checkpoint-install" equivalence. It touches `recovery` (bar c): the barrier install + WAL truncation are on the durability critical path. Scope note (§5): this **Extends** the W30 `recovery::Checkpointer` by calling its existing `install_barrier` — it does NOT re-build the Checkpointer; the new code is the import driver + the atomicity ordering. Three traps make a naive first attempt CORRUPT STATE, not slow: (1) **truncate-before-barrier (or delete-before-flip)** — you truncate the WAL first, crash before installing the barrier, and recovery now replays from 0 over the imported state, double-applying (the classic ARIES "delete the log you still need" bug); (2) **redo starts at `lsn_high` not `lsn_high + 1`** — an off-by-one re-applies the last record already baked into the snapshot (idempotent records hide it; non-idempotent records, e.g. `balance += x`, double-apply); (3) **no format/version gate** — you import a `format_version=2` file into a v1 reader and silently misparse, installing a barrier over garbage. Plus the bar-(c) perf trap: importing 27 GB by reading the whole image into a `Vec` (heap) instead of mmap + sequential page-in. Downstream: storage-trie v1.0 (W43-44); mini-db fast-restore (W97-100) reuses this exact protocol; consensus-raft snapshot install (W67) and ledger restart (W83) inherit the truncate-after-barrier ordering.

  - *Back-of-envelope* (bar (c)): the import is **sequential I/O bound**. 27 GB mainnet snapshot at ~2 GB/s sequential NVMe ≈ **~13.5 s** of pure read — so the parse must NOT add allocation/copy per row. `read_to_end` into a `Vec` = one ~27 GB heap allocation (malloc of that size = mmap anyway, but you pay a full copy + can't start parsing until the whole read completes) vs **mmap + page-in on demand** = zero-copy, parse-as-you-fault, overlapped with I/O. The barrier install is **one fsync ≈ 0.5-2 ms** (NVMe flush) — cheap, but it MUST be ordered after the state fsync and before the truncate. The cliff: a per-row `Box`/`Vec` clone over 250M rows = 250M mallocs (~50 ns each) = **~12.5 s of pure allocator time** on top of the I/O — doubling import time. Static rule: parse rows by slicing the mmap, never by per-row heap copy.
  - *Anti-shortcut audit*:
    - **`std::fs::read` / `read_to_end` the whole snapshot into a `Vec<u8>`.** Wrong HERE: a 27 GB single allocation + full copy before any parse; defeats overlap and burns RAM. → trapped by `import_is_zero_copy_mmap` (perf, bar c).
    - **`checkpointer.install_barrier(lsn_high)` AFTER `wal.truncate_prefix(lsn_high)`.** Wrong HERE: a crash between them loses the log you still need → replay-from-0 double-applies. → trapped by `import_crash_after_truncate_before_barrier_is_safe`.
    - **Skip the `format_version` check ("it's our own file").** Wrong HERE: a future v2 file silently misparses into a barrier over garbage. → trapped by `import_rejects_version_mismatch`.

  #### Phase 3 — Make the tests pass, one failure at a time (~150 min)
  Ordered newbie→expert; the perf card is tagged (bar c violation).

  - **(NEWBIE) When `import_recovery_starts_at_lsn_high_plus_one` replays LSN 42:**
    - Symptom: recovery's first redo is LSN 42 — the exact record already baked into the snapshot — and a non-idempotent record double-applies.
    - Why: you installed the barrier as "redo from `lsn_high`" instead of "everything ≤ `lsn_high` is already applied."
    - Fix: `install_barrier(lsn_high)` means redo resumes at `lsn_high + 1`; the barrier LSN is the last-applied, not the next-to-apply.
    - Cost avoided: a double-applied `balance += x` = silent fund/state corruption (consensus split on a node syncing from this snapshot); no perf cost, pure correctness.
    - Muscle: a checkpoint/barrier LSN is the LAST-applied record; resume is barrier+1. Reapplies at: W42 txn commit LSN, W67 raft snapshot lastIncludedIndex, W83 ledger restart, W97 mini-db recovery start.

  - **(SENIOR) When `import_rejects_version_mismatch` mutates state before erroring:**
    - Symptom: import returns the right `Err` but `state_root` changed — you parsed/restored rows, THEN checked the version.
    - Why: validation happened after the restore loop, not before.
    - Fix: verify magic + checksum + format_version FIRST (header is at byte 0); only restore state after all three pass.
    - Cost avoided: a partially-restored state over a rejected import = neither old nor new = manual recovery; correctness, no perf cost.
    - Muscle: validate the whole envelope (magic/checksum/version) before mutating any durable state — fail-before-write. Reapplies at: W43 storage-trie snapshot load, W67 raft InstallSnapshot RPC, W97 mini-db manifest load.

  - **(EXPERT) When `import_crash_after_truncate_before_barrier_is_safe` corrupts on recovery (with a naive truncate-first impl):**
    - Symptom: with truncate-before-barrier, a crash in the gap leaves a durable barrier at LSN 0 but a WAL missing its [0..42] prefix → recovery either double-applies the surviving tail over the snapshot or aborts on a log hole.
    - Why: you GC'd the WAL prefix before the barrier that makes it redundant was durable — you deleted the log you still needed.
    - Fix: enforce the order **restore-fsync → install_barrier-fsync (commit point) → truncate**. The barrier's durability is the precondition for truncation; never reorder.
    - Cost avoided: a corrupt or unrecoverable database after a mid-import crash — the worst durability bug there is (silent data loss). (bar (c) violation: a durability primitive that double-applies/loses log on crash is disqualified, not merely slow.)
    - Muscle: in ARIES-style durability, never reclaim (truncate/GC) a log region until the checkpoint that supersedes it is itself durable — write-new → fsync → flip → delete-old. Reapplies at: W42 txn 2PC log GC, W67 raft log compaction after snapshot, W83 ledger truncation, **Thursday's export footer-last rule (this week)**, W97 mini-db WAL recycle.

  - **(EXPERT, perf) Expect to hit (perf) #1 — `import_is_zero_copy_mmap` reports O(rows) allocations (bar (c) violation):**
    - Symptom: 100k rows → ~100k+ allocations; the counting-allocator assert fires; on a 250M-row mainnet snapshot this adds ~12.5 s of allocator time on top of the ~13.5 s I/O (≈2× import time).
    - Why: you `read_to_end` into a `Vec` and then `to_vec()`/`Box` each parsed row, allocating per row.
    - Fix: `mmap` the snapshot read-only and parse each row by slicing into the mapped bytes (`&self.map[off..off+len]`), using the offset index to seek; keep a single bounded scratch buffer, zero per-row heap allocation.
    - Cost avoided: **~250M mallocs × ~50 ns ≈ 12.5 s** of pure allocator time + ~27 GB peak RSS from the full read-into-Vec; mmap pages in on demand and overlaps with I/O. (bar (c) violation.)
    - Muscle: on a sequential-I/O-bound import, parse by slicing an mmap — never per-record heap copy; allocation count must be O(1), not O(rows). Reapplies at: W39 lsm-core SSTable scan, W77 aeron term-buffer read, W90 marketdata feed replay, W97 mini-db compaction read path.
