    - *Mental model*: pre-size every memory location at startup; `apply()` never touches the global allocator. This is the TigerBeetle invariant that earns their reputation — predictable latency because there is no allocator tail, no OOM in steady state, no fragmentation under burst.

    - *Contract*: `TransferPool::new(N) -> Self` (one alloc); `acquire() -> Option<PooledTransfer<'_>>` O(1) zero-heap; `release` via RAII Drop. `AccountMap::new(N) -> Self` (one alloc); `get(&K)->Option<&V>`, `insert(K,V)->Result<(),MapFull>`, robin-hood, no rehash. Deterministic `BuildHasher` (unit struct, no per-process seed). NEVER the solution body.

    - *Back-of-envelope* (bar (c) — name the cost): a single `Box::new`/`HashMap::rehash`/`Vec::realloc` inside `apply()` injects ~50 ns (malloc) to ~10 ms (rehash storm) of allocator latency at unpredictable times. P99 commit jumps from <1 µs to **10+ ms** — a **10,000× violation** of v1.0's headline (P99 ≤ 1 µs single-shard). Jeff-Dean: malloc ~50 ns, mutex 25 ns, main-mem 100 ns, L2 7 ns; a SipHash `DefaultHasher` is ~27 ns/hash × 2 = 54 ns of the budget alone. Cliff ratio: cached-pool acquire ~10 ns vs allocator P99 spike ~10 ms = **1,000,000×**. Allocator-driven tail cannot be hedged; the only fix is to never allocate. The pool is the artifact that proves this discipline — and the capstone's `SettlementId`-finality claim depends on it.

    - **Requirements** — write in `crates/ledger-deterministic/notes/89mon_static_mem_design.md`:
      - R1. `TransferPool` allocates `Box<[MaybeUninit<Transfer>; MAX_TRANSFERS]>` (128 MB at 1 M × 128 B) **once** at startup; `acquire()`/`release()` is O(1) with **zero** heap touch.

      - R5. dhat audit reports **0 allocations** during a 1 M-Transfer apply loop (preamble allocs excluded).

    #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

    - **(NEWBIE) When `test_transfer_pool_zero_allocs_after_construction` reports N>0 allocs in the loop:**
      - Symptom: dhat fires with allocations attributed to `Vec::push`, `String::from`, or `Box::new` inside the apply path; counter shows ~1–3 allocs per iteration.
      - Why: a logging line, metric label, or error path constructs a `String` or `Vec`. `acquire()` itself might use `Vec<u32>` for the free-list (grows past capacity → realloc).
      - Fix: free-list is `ArrayVec<u32, N>` (no growth), error type is enum (no `String`), logging is `tracing::Span` with static labels. Re-run dhat; expect 0.
      - Cost avoided: ~50 ns malloc per iter eliminated, and (worse) the ~10 ms realloc/rehash P99 spike removed — **bar (c) violation** if left, since a single steady-state alloc disqualifies the crate (and would surface in the capstone as a settlement-commit tail).
      - Muscle: dhat is the enforcement; "zero allocs" is a CI gate, not aspiration. Reapplies at: W89 Tue FixedMap, W89 Wed VSR body, W89 Thu MessagePool, W90 io_uring registered buffers, W92 v1.0 SHIP audit, W99 risk-engine position table, W103 capstone settlement apply.

    - **(EXPERT) When `test_transfer_pool_maybeuninit_no_read_before_write` fires "encountered uninitialized memory":**
      - Symptom: miri reports a read of uninit bytes at the `&mut Transfer` returned by `acquire()`; usually because consumer code reads a field before writing.
      - Why: `MaybeUninit<Transfer>` slots are NOT zero-initialized — the byte pattern is whatever the allocator returned (or stale from a previous use). Returning `&mut` to an uninit slot lets the consumer's first read be UB.
      - Fix: `acquire()` always calls `slot.write(Transfer::default())` then returns `&mut *slot.as_mut_ptr()`. Verify the default ctor is cheap (~5 ns). Alternative: `release()` zeros on return — pick one, document.
      - Cost avoided: not a perf-headline but a **correctness budget** — reading uninit bytes is UB; ~5 ns init avoids a miri-only-visible silent-corruption class that costs days under VOPR replay.
      - Muscle: `MaybeUninit` is an unsafe contract; the init-before-read responsibility lives in the pool, not the consumer. Reapplies at: W89 Thu MessagePool's `acquire()` zero-pass, W82 matching-engine Order slot init, W90 io_uring buffer init.

    - **(EXPERT) When `test_account_map_robin_hood_bounds_probe_distance` reports max probe distance ~100+:**
      - Symptom: at load 0.5 the average probe is fine (~1.5) but max blows out to 80–150 slots; P99 lookup latency cliff at ~500 ns.
      - Why: you implemented linear probing without the robin-hood swap. Insert clusters when collisions occur and any clustering causes variance explosion at the tail.
      - Fix: in `insert()`, track `new_entry.probe_dist`; at each probe step, if `existing_slot.probe_dist < new_entry.probe_dist`, swap them and continue probing with the displaced entry. Property: max probe distance bounded by `O(log N)` ≈ 24 for 16 M slots.
      - Cost avoided: ~500 ns P99 lookup → ~50 ns (a 10× tail collapse); at 2 lookups/Transfer that reclaims ~900 ns of the 1 µs budget — **bar (c) violation** if left (P99 blows the headline).
      - Muscle: in hash tables on the bar-(c) hot path, variance matters more than mean. Robin-hood for the tail discipline; linear probing only acceptable when load factor is permanently low. Reapplies at: W74 matching-engine OrderId→Order map, W94 exec-vm storage-key probe, W90 consensus-vsr replica-state lookup, W99 risk-engine position-by-account lookup.

    - **(SENIOR) When `test_account_map_deterministic_hash_across_processes` fails with different bucket assignments:**
      - Symptom: process A hashes AccountId 0x1234 to bucket 5; process B hashes the same ID to bucket 9847. State_machine outputs match but timing leaks differ, breaking VOPR replay determinism — and the one-hot-path-log lock (replicas must be byte-identical).
      - Why: you used `std::collections::hash_map::DefaultHasher` (SipHash-1-3) which seeds its state from `RandomState` — randomized per-process.
      - Fix: build a `BuildHasherDefault` over Splitmix64 finalizer of `AccountId.as_u64()` (unit-struct hasher, no per-instance seed) OR BLAKE3-128 truncated to `u64`. Both deterministic, both ~3 ns, both adversarial-OK.
      - Cost avoided: ~27 ns/hash × 2 hashes/Transfer = ~54 ns P50; ~30 µs P99 cliff under adversarial input. VOPR replay is now byte+timing identical; the capstone can prove replica convergence.
      - Muscle: pick the hash function deliberately. `DefaultHasher` is wrong for any hot-path map; `HashMap` is wrong for any bar-(c) crate. Reapplies at: W89 Tue FixedMap hash, W94 exec-vm v1.5 storage-key hash, W92 ledger state_hash (BLAKE3), W74 matching-engine OrderId→Order lookup, W99 risk-engine.

    - **(SENIOR) When `test_account_map_no_rehash_returns_full_at_load_85` panics on rehash instead of returning `MapFull`:**
      - Symptom: at load 0.85, `insert()` hangs in an infinite robin-hood probe loop OR a rehash attempt allocates new bucket array (~10 ms latency spike).
      - Why: forgot the hard cap; `insert()` keeps probing until it finds an empty slot, which doesn't exist at load 1.0. OR you tried to "be helpful" and added a rehash path.
      - Fix: at top of `insert()`, `if self.len + self.tombstones >= (N * 85) / 100 { return Err(MapFull); }`. No rehash branch exists in the code at all.
      - Cost avoided: 10 ms rehash latency spike → 0 ns; eliminates the P99 cliff that would otherwise dominate the latency histogram. At 100 k Transfers/sec a single rehash drops throughput by 50%+ for the duration.
      - Muscle: bar (c) = static memory = no growable collections on the hot path. Acceptance is "dhat reports 0 allocs" not "we tried to minimize allocs." Reapplies at: every bar-(c) crate from W89 onward, including the W99 risk-engine and W103 capstone.

    - **(EXPERT) When `test_pooled_transfer_releases_on_panic` shows leaked slots after a panic-recovery test:**
      - Symptom: after running an apply loop that panics mid-Transfer 1000 times, pool's `in_use_count == 1000` instead of 0.
      - Why: `acquire()` returns a bare `&mut Transfer`; the apply caller is responsible for calling `release()`. On panic, the manual release is skipped.
      - Fix: wrap in RAII `PooledTransfer<'a> { pool: &'a TransferPool, slot_id: u32 }` with `Drop` calling `pool.release(self.slot_id)`. Panic unwind drops the local; pool count restored.
      - Cost avoided: not ns but availability — a 0.01% error-path leak rate exhausts a 1 M pool in ~27 days → hard service outage; RAII costs 0 ns on the happy path.
      - Muscle: pool-managed resources need RAII handles to survive panics; manual release is a leak waiting to happen. Reapplies at: W89 Thu MessagePool's `PooledMessage<'a>`, W82 matching-engine Order pool, W90 io_uring buffer pool, W77 messaging-aeron term-slot.

    - **(EXPERT) When `test_pooled_message_drop_zeros_header` shows `cluster_id == 0xDEADBEEF` after re-acquire:**
      - Symptom: a slot is acquired, written with sentinel bytes, dropped; re-acquired (same slot); the sentinel bytes are still there.
      - Why: `Drop` just pushed `slab_id` back to the free list without clearing the slot's contents. Stale bytes leak to the next acquire; if the next caller forgets to write a field, the previous caller's bytes ship.

    - **(EXPERT) When `test_pool_drop_on_panic` shows leaked slots after the unwind:**
      - Symptom: `catch_unwind` runs a closure that acquires a message then panics; after the closure, the pool's `in_flight == 1` instead of 0.

Panic unwind drops the local; pool count restored.
      - Cost avoided: not ns but availability — a recoverable panic that leaks a slot drains the pool over time → backpressure-stall → replica wedged; RAII costs 0 ns on the happy path.
      - Muscle: pool-managed resources need RAII handles to survive panics. Reapplies at: W89 Mon PooledTransfer, W82 matching-engine Order pool, W90 io_uring buffer pool, W77 term-slot.

    - **(SENIOR) When `test_per_destination_quota_isolates_partition` shows all destinations starved by a single partition:**

      - Why: the pool is global to the replica with no per-destination accounting; one partitioned dest can monopolize all slots.
