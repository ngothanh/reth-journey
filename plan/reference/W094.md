### Build 1 — read-only globals registry (the headline trap)

- [ ] **Build (bar (b) crate; perf gate is bar-(c)-class)**: `crates/exec-vm/src/parallel/globals.rs` — a per-block `ReadOnlyGlobals` registry so reads of block-level constants (`BLOCKHASH`, `COINBASE`, `TIMESTAMP`, `DIFFICULTY`/`PREVRANDAO`, `GASLIMIT`, `CHAINID`, `BASEFEE`) never enter `RwSet.reads` and thus never create conflict edges. (~total 110 min across 3 phases)
  - 🔧 **Why this matters**: mirrors Aptos block-stm's read-only-globals exemption — the single insight that turns block-stm from "theoretically correct, practically 0.5×" into ">2×". Traps: (1) every tx in any block reads `BLOCKHASH`+`COINBASE`, so if those reads are recorded, the validator sees N×N pseudo-conflicts and re-executes everything; (2) the obvious "skip recording" must STILL serve a consistent value to all tx_idx or determinism breaks; (3) `PREVRANDAO`/`DIFFICULTY` share an opcode slot post-Merge — classify by block context, not opcode number. Consumed by: W94 SHIP low-conflict speedup gate (blocked without this), W94 Build 2 (pool sees fewer re-exec rounds), consensus-engine v1.5+ default-on. **v3 note**: this is the *spine's* parallelism result — the same false-conflict-classification discipline reappears in the venue half at W74 matching-engine static reference data and W88 ledger VOPR read-only `lookup`. **First-attempt impls record the global reads and fail `globals_no_conflict_on_pure_dex_block` + the 8-core speedup bench — the debug session IS the lesson.**

In an optimistic-concurrency validator, a "read" only matters if a *later-versioned write* can invalidate it. These keys have no in-block writer, so the read can never go stale — recording it is pure pseudo-conflict noise.
  - *Contract*: `pub struct ReadOnlyGlobals { /* immutable after block prelude */ }` with `fn seed(prelude: &BlockEnv) -> Self`, `fn is_exempt(&self, key: &StorageKey) -> bool`, `fn value(&self, key: &StorageKey) -> Option<Value>`. `RwSet::record_read(key)` calls `globals.is_exempt(key)` first; if exempt, the read resolves via `globals.value(key)` and is NOT pushed into `reads`. NEVER write the body here.
  - *Back-of-envelope* (bar-(b) crate but the gate is perf-load-bearing): on a 250-tx block where every tx does 2 global reads, recording them creates ≈250×249 = ~62k pseudo-conflict edges; the validator re-executes the whole block ~k times → effective speedup collapses to **~0.5× (worse than sequential)**. `is_exempt` itself must be cheap: a fixed-set membership check on ≤8 keys = a linear scan over 8 `StorageKey` (≤8 × ~4ns compares = ~32ns) is fine vs the ~480µs/tx exec budget — DO NOT reach for a heap `HashSet` (one alloc + hash per check, cache-cold bucket walk ~100ns) when a `[StorageKey; 8]` stack array is faster and zero-alloc.

    - R3. An exempt read resolves to the SAME value for every tx_idx (consistency).
    - R4. An exempt read adds ZERO entries to `RwSet.reads` (no conflict edge).
    - R5. A non-exempt read of a key that *happens to equal* a global's numeric value is NOT exempted (classify by key identity/origin, not value).

  #### Phase 3 — Make the tests pass, one failure at a time (~30 min)
  Ordered failure cards, newbie first.
  - **(NEWBIE) When `globals_exempt_read_adds_no_conflict_edge` reports `reads = [coinbase_key]`:**
    - Symptom: the exempt read still landed in `RwSet.reads`.
    - Why: `record_read` pushed unconditionally; the exempt check was never wired before the push.
    - Fix: in `record_read_with_globals`, `if globals.is_exempt(&key) { return self.resolve_exempt(key, globals); }` BEFORE the `self.reads.push(...)`.
    - Cost avoided: ~62k pseudo-conflict edges per block → the difference between the feature working and not.
    - Muscle: in optimistic concurrency, the exemption check must guard the *recording* site, not post-filter. Reapplies at: W74 matching-engine static reference data (symbol metadata never conflicts), W88 ledger VOPR `lookup` op (read-only — never a conflict edge), W82 matching-engine STP exemption.
  - **(SENIOR) When `globals_value_consistent_across_tx_idx` returns two different values:**
    - Symptom: COINBASE read twice yields A then B.
    - Why: the holder stored a `&mut BlockEnv` or recomputed from a clock, so the value drifted between reads (R1/R3 violated).
    - Fix: `seed()` snapshots each constant into an owned, immutable `Value` once; `value()` returns a copy of the frozen snapshot.
    - Cost avoided: silent cross-tx determinism divergence — surfaces only in the byte-identical gate.
    - Muscle: a block-level constant is single-writer-at-prelude, immutable-after — freeze it, never recompute. Reapplies at: W92 versioned-memory Estimate immutability, W91 ledger op_num freeze, W82 matching-engine session-constant reference data.
  - **(SENIOR) When `globals_does_not_exempt_collision_slot` exempts a real slot:**
    - Symptom: a normal storage slot got `is_exempt == true`; its later write is dropped.
    - Why: exemption keyed on the numeric value or low bits instead of the (address, slot-class) identity.
    - Fix: classify by the *origin* of the read (opcode is BLOCKHASH/COINBASE/etc.) recorded at read time, not by the resulting key's value.
    - Cost avoided: a silently-ignored storage write → wrong state root (correctness, the worst class for a settlement chain).
    - Muscle: classify constants by provenance, not by value — value collisions are real. Reapplies at: W74 matching-engine reference-data classification, W88 ledger op-type tagging.
  - **(EXPERT) When `globals_no_conflict_on_pure_dex_block` reports `reexecutions = 61750`:**
    - Symptom: a conflict-free block re-executes ~N² times.
    - Why: composition gap — globals.rs is correct alone, but the W93 executor's validator reads `RwSet.reads`, which still contained globals because `record_read_with_globals` wasn't the path the executor called.
    - Fix: route the executor's SLOAD handler through `record_read_with_globals(key, &block_globals)`; thread `&ReadOnlyGlobals` into the per-tx exec context.
    - Cost avoided: ~62k pseudo-conflict edges → 0; re-execution count N²→0 on conflict-free blocks. This is the difference between the crate working and not.
    - Muscle: a correct component is inert unless the *caller* routes through it — wire the exemption at the only SLOAD site. Reapplies at: W93 executor read-resolution path, W92 versioned-memory read API, W91 rwset record sites.
  - **(EXPERT, perf — bar-(c)-class for this crate) When `bench_low_conflict_speedup_band` reports `speedup 0.52× < 2.0×`:**
    - Symptom: parallel is SLOWER than sequential on a conflict-free block.
    - Why: global reads recorded → N×N validation failures → whole-block re-execution dominates; the worker count makes it worse, not better.
    - Fix: the read-only-globals exemption (this whole Build); verify with `stats.reexecutions == 0`.
    - Cost avoided: speedup ~0.5× → ~2–3× on low-conflict blocks. The headline SHIP gate (8-core low-conflict ≥2.0×) is unreachable without it — **(bar (c) violation for this crate: the parallel feature is shippable-as-bar-b only if this holds).**
    - Muscle: in any optimistic-concurrency system, identify the block/session/init constants and exclude them from conflict tracking BEFORE tuning the scheduler. Reapplies at: W88 ledger VOPR `lookup`, W74 matching-engine static reference data, W82 matching-engine STP exemption, W92 versioned-memory read-only-base handling.

### Build 2 — long-lived worker pool (the hidden re-spawn trap)

- [ ] **Build (bar (b) crate; perf gate is bar-(c)-class)**: `crates/exec-vm/src/parallel/pool.rs` — a single process-lifetime worker pool the block-stm scheduler enqueues tx-exec tasks into, replacing per-block / per-validation-round `rayon::scope(...)` spawns. (~total 100 min across 3 phases)
  - 🔧 **Why this matters**: mirrors Aptos `BlockExecutor`'s reuse of one thread pool across blocks. Traps: (1) `rayon::scope` is cheap once but the block-stm validator re-enters it once *per re-execution round* — 5 rounds × ~50µs scope-setup on a 5ms block = ~5% overhead the optimizer can't elide (closures vary); (2) a fresh `ThreadPool::new` per block pays ~500µs cold pool materialization; (3) panic in a worker must not poison the pool for the next block. Consumed by: W94 SHIP speedup gate (the last ~5% to hold ≥2.0× on the median block, not just the lucky block), W93 executor (becomes the executor's task sink). **v3 note**: the "workers live for the process, tasks flow through a queue" pattern is the *same* discipline the venue half uses for `runtime-thread-per-core` (W85) shard threads and the W88 VOPR runner — the spine teaches it here at bar (b). **First-attempt impls call `rayon::scope` inside the validation loop and fail `pool_no_respawn_across_validation_rounds` + lose ~5% on the bench.**

    ```rust
        pub fn commit(self, commit_ts: OpNum) -> Result<(), TxnConflict>; // commit_ts = VSR op-number (R1)
    }
    // mvcc.rs
    pub fn gc_below(&self, watermark: OpNum);                     // collect versions no live reader needs (R4)
    // coprocessor.rs (lsm-core)
    pub fn scan_pushdown(&self, range: KeyRange, pred: &Predicate, at: OpNum) -> RowIter; // filter at the scan layer (R5)
    ```
  - *Back-of-envelope* (bar (b)): a snapshot read = one seek in the write CF to `(key, start_ts)` descending + one data CF point-get ≈ ~2 LSM lookups ≈ ~2 µs warm (bufpool-resident). The version-key encoding (`commit_ts` descending) makes "greatest commit_ts ≤ start_ts" a single forward seek, not a scan — the alternative (ascending + filter) reads every newer version (O(versions) wasted I/O). Coprocessor pushdown on a 10k-row block where a `qty > 1000` predicate selects 200: no-pushdown materializes + copies 10k rows across the boundary (~10k × ~64 B = 640 KB memcpy ≈ ~130 µs + alloc); pushdown evaluates the predicate at the block and crosses only 200 rows (~13 KB) — a ~50× reduction in boundary traffic. Cliff: pushdown (200 rows cross) vs no-pushdown (10k rows cross) = ~50× on the scan boundary.
  - **Requirements** R1..R8 — write in `crates/txn/notes/94_percolator_design.md`:
    - R1. **TSO = VSR commit point**: `commit_ts` is the VSR op-number of the commit record — NOT a wall clock, NOT a standalone TSO. `cargo tree`/a seam test shows no separate clock dependency (the W90 seed lock).
    - R2. **Version-key encoding**: data/write CF keys are `(user_key, commit_ts)` ordered so the latest committed version sorts adjacent; a snapshot read is one seek.
    - R3. **Snapshot-isolation read**: `get` at `start_ts` returns the version with the greatest `commit_ts ≤ start_ts`; a long reader sees a consistent snapshot while a writer commits newer versions (no torn read).
    - R4. **MVCC GC**: `gc_below(watermark)` collects every version below the watermark that no live reader needs; a version a live reader still needs is never collected.
    - R5. **Coprocessor pushdown**: `scan_pushdown` evaluates the predicate at the `lsm-core` scan layer; filtered rows never cross the call boundary; a counter proves ≥N rows skipped.
    - R6. **Differential identity**: the pushdown path returns rows *identical* to the no-pushdown path (filter-then-return == return-then-filter) for the same predicate.
    - R7. **Lock CF correctness**: a reader that encounters a lock for an uncommitted primary does not read the in-flight version (no dirty read); disjoint-write transactions both commit (no false write-skew abort).
    - R8. **Determinism**: the full MVCC timeline (versions + visibility) replays bit-identically across replicas because every `commit_ts` is a committed op-number.
