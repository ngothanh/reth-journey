- [ ] **Build**: `crates/storage-trie/src/mdbx/mmap_page_provider.rs` — `MmapPageProvider` returning `eth-storage-cache::Page` views over a `MAP_SHARED` file. (~total 200 min across 3 phases)
  - 🔧 **Why this matters**: mirrors libmdbx-rs's mmap'd `Environment` + memmap2 `MmapMut`. mmap converts page-table lookups into VFS reads on first touch, then RAM lookups thereafter — the only way to get sub-microsecond cold-page reads on a 100 GB database. But mmap is treacherous, and **a naive first attempt fails ≥3 of the tests below**: a bare `Vec<RwLock<()>>` of page locks corrupts under concurrent `grow` (cross-primitive trap), `MS_SYNC` makes the "fast" flush block for seconds (anti-shortcut, bar (c) violation), and lazy faulting makes a cold sequential scan 4× under target (anti-shortcut, bar (c) violation). The debug session IS the lesson. Downstream: W28 B-tree core sits atop this; W29 recovery replays through it; W30 mmap-queue reuses the flock+msync discipline; W31 persistent MPT; W95 mini-db reproduces.

  #### Phase 1 — Problem, prediction, design (~55 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/storage-trie/notes/27_mmap_prediction.md`:

    - P5: **list every Phase-2 test you predict your first attempt will fail.** Compare to reality after the tests run.
  - *Mental model*: `MmapPageProvider` is the single chokepoint where raw mmap hazards (SIGBUS, fault tail, write-back stalls, concurrent grow) are isolated behind a `Page` abstraction, so no caller above it ever touches a raw pointer or a syscall flag.
  - *Contract*:
    ```rust
    pub struct MmapPageProvider { /* file, MmapMut, page_count: AtomicUsize, dirty: BitVec, locks: [RwLock<()>; 256] */ }
    pub trait PageProvider {
        fn fetch(&self, pid: PageId) -> Result<PageRef<'_>>;          // R2: shared, bounds-checked
        fn modify<F: FnOnce(&mut Page)>(&self, pid: PageId, f: F) -> Result<()>; // R3: exclusive + dirty
        fn grow(&self, new_page_count: usize) -> Result<()>;          // R4: fallocate + remap
        fn flush(&self, dirty_only: bool) -> Result<()>;              // R5: msync(MS_ASYNC)
        fn flush_sync(&self) -> Result<()>;                           // R5: msync(MS_SYNC) barrier
    }
    impl MmapPageProvider { pub fn open(path: &Path, initial_size: usize) -> Result<Self>; } // R1
    ```
  - *Back-of-envelope* (bar (c)): page = 4 KiB. Warm fetch = pointer arith + a `RwLock` read = ~5-25 ns (mutex/rwlock ~25 ns). Cold fetch = minor page fault ~1 µs; major fault from disk = 100 µs-10 ms. Jeff-Dean: main mem 100 ns, syscall 300 ns, so a `read(2)`-per-page provider pays 300 ns trap × N pages — mmap amortises that to one fault per 4 KiB. **Cliff ratio**: warm 5 ns vs cold-from-disk 10 ms = **2,000,000×** — the whole design is about keeping the working set warm so you never pay the cliff in the hot path. msync(MS_SYNC) over 100 MiB at ~500 MB/s effective fsync = ~200 ms; MS_ASYNC schedules and returns in <1 µs — a **200,000× difference** on the same call.
  - **Requirements** R1..R10 — write in `crates/storage-trie/notes/27_mmap_design.md`:
    - R1. `open(path, initial_size)` opens or creates the backing file; maps `PROT_READ|PROT_WRITE`, `MAP_SHARED`.
    - R2. `fetch(pid) -> PageRef<'_>` returns a read-locked view; bounds-checked against `page_count`; out-of-range → `Err(OutOfBounds)`, never a raw OOB read.
    - R3. `modify(pid, F)` takes the exclusive stripe lock; runs `F(&mut Page)`; sets the dirty bit (`BitVec` of `AtomicU64`, one bit/page).
    - R4. `grow(new_page_count)` fallocates + remaps; Linux `mremap` (keeps mappings), macOS `munmap`+`mmap` fallback. **Must not invalidate the lock array.**
    - R5. `flush(dirty_only)` → `msync(MS_ASYNC)` fast path; `flush_sync()` → `msync(MS_SYNC)` barrier.
    - R6. Region size always a multiple of the system page size (query `sysconf(_SC_PAGESIZE)`, don't hardcode 4096 — aarch64 macOS is 16 KiB).
    - R7. SIGBUS protection: `flock(LOCK_EX)` at open; document single-process assumption in the crate doc.
    - R8. Throughput: ≥5 GB/s warm sequential read on NVMe (cold needs hints — see R9).
    - R9. Cold sequential scan must use `madvise(MADV_SEQUENTIAL)` + `MADV_WILLNEED`/`MAP_POPULATE`; p99 warm-page fetch ≤1 µs.
    - R10. Crash-test: 100 random SIGKILL injections; reopen finds each page in old OR new state, no torn 4 KiB writes.
  - **Design walk-through** D1..D6 — answer in the design doc; NO peeking at libmdbx-rs source until Phase 3:
    - D1. **Primitive property table**: enumerate the lock strategies — `Vec<RwLock<()>>` (grows with data), `[RwLock<()>; 256]` striped, `RwLock<Vec<RwLock<()>>>`, `DashMap`. Columns: survives `grow`? lock latency? memory? false-sharing risk?

    - D5. **Pre-mortem (load-bearing)** — write the EXACT 4-5 line bad interleaving for a plain `Vec<RwLock<()>>`:

  #### Phase 3 — Make the tests pass, one failure at a time (~95 min)
  Ordered failure cards — newbie first, expert last.

  - **(NEWBIE) When `fetch_bounds_checked` reads adjacent mmap bytes instead of erroring:**
    - Symptom: `fetch(page_count)` returns garbage from the page just past the mapped region instead of `Err(OutOfBounds)`.
    - Why: the impl computed `offset = pid * PAGE` and sliced the mmap with no `pid < page_count.load()` check.
    - Fix: bounds-check against `page_count.load(Acquire)` first; return `Err(OutOfBounds)` before any offset math.
    - Muscle: an mmap is a flat byte slab — bounds are *your* job, the hardware won't fault until you cross a page that's unmapped (which may be far past your logical end). Reapplies at: W28 B-tree node access, W30 mmap-queue index, W95 mini-db SSTable.

  - **(SENIOR) When `flush_sync_blocks_for_durability` returns in <1 µs over a 100 MiB dirty region:**
    - Symptom: `flush_sync()` over 100 MiB of dirty pages returns near-instantly (<1 µs) — yet a naive `read(2)`-on-the-same-fd check would have "passed" because the bytes are already coherent in the page cache.
    - Why: the trap is visibility-vs-durability. `flush_sync` was a no-op stub (`Ok(())`) or called `flush_async` (MS_ASYNC, which only schedules). A MAP_SHARED write is visible to a concurrent `read(2)` IMMEDIATELY via page-cache coherence (Monday Q4) with no msync at all — so visibility proves nothing about whether the bytes reached the platter. Only the blocking `msync(MS_SYNC)` syscall makes them durable, and that syscall takes measurable wall-clock over a large dirty region.
    - Fix: `flush_sync` → `msync(addr, len, MS_SYNC)` and check the return; only return `Ok` after the syscall completes. The 100 MiB dirty region then forces a multi-ms write-back, satisfying the `>1 ms` assertion; a stub stays sub-µs and fails.
    - Cost avoided: shipping a "durable" commit path that is actually a no-op — every crash after a "successful" `flush_sync` loses data, the worst silent storage bug, invisible to any in-process read because the page cache lies. (Confirm on-disk via the `--ignored` drop-cache pread check.)
    - Muscle: visibility (page-cache coherence, free) is NOT durability (msync(MS_SYNC), blocks for ms over a large region); never test durability with an in-process read — test it by the blocking syscall or a dropped-cache re-read. If your "sync" returns instantly it didn't sync. Reapplies at: W26 wal `fsync` group-commit, W29 recovery checkpoint barrier, W74 order-book snapshot.

  - **(EXPERT, cross-primitive) When `grow_under_contention_no_panic_no_uaf` trips miri OOB/UAF on `locks[pid]`:**
    - Symptom: miri reports out-of-bounds or use-after-free indexing `self.locks` inside a fetcher thread while `grow` ran.
    - Why: `locks` was a plain `Vec<RwLock<()>>`; `grow` reallocated it mid-fetch — the fetcher held an index into a freed/relocated buffer (exactly the D5 interleaving).
    - Fix: stripe locks into a FIXED `[RwLock<()>; 256]`, key by `pid % 256`. `grow` only bumps `page_count` (Release) + remaps the data; it never touches the lock array. (Alt: `RwLock<Vec<..>>` and grow under the outer lock — but that serialises every fetch behind grow; the stripe array is the bar (c) choice.)
    - Cost avoided: a use-after-free that miri catches but a green `cargo test` would ship — silent memory corruption under production grow.
    - Muscle: a lock array that must outlive a `grow` is fixed-size and striped, or grow-protected — a bare `Vec` of locks is a UAF waiting for the realloc. Reapplies at: W30 mmap-queue per-cycle locks, W42 txn LockManager stripes, W74 matching-engine per-symbol locks.

  - **(SENIOR, anti-shortcut, bar (c) violation) When `flush_async_returns_under_100us` takes ~200 ms:**
    - Symptom: the "fast" flush blocks ~200 ms over a 100 MiB dirty region.
    - Why: `flush` used `MS_SYNC` — which waits for every dirty page to hit the platter — instead of `MS_ASYNC`, which only schedules write-back.

  - **(NEWBIE) When `single_tx_100_inserts_commit_replays` recovers 0 records:**
    - Symptom: reopen + recovery finds none of the 100 inserts.
    - Why: `commit` never wrote (or never fsync'd) the commit record; recovery's analysis pass found no committed tx, so redo skipped everything.
    - Fix: `commit` appends a commit record AND `await_durable(commit_lsn)` before returning `Ok`; recovery treats only txs with a durable commit record as committed.

  - **(EXPERT, anti-shortcut) When `wal_record_durable_before_page_visible` finds page-visible BEFORE append:**
    - Symptom: the probe logs a page mutation timestamp earlier than the wal-append for the same LSN.
    - Why: a code path bypassed `WriteTransaction` and called `pool.fetch_exclusive(..).mutate()` directly before any wal append (the D1/D5a shortcut).
    - Fix: make page-mutation private to the txn module — `pool.modify`/`fetch_exclusive` is `pub(in crate::mdbx)`; the only public mutation entry is `WriteTransaction::insert`, which appends first. Visibility enforces the order the type system can't.
    - Cost avoided: a durable mutation with no log = unrecoverable corruption — the worst class of storage bug (silent, only surfaces on crash).
    - Muscle: an ordering invariant the type system can't express (op A before op B) is enforced by capability-hiding — make the dangerous op private to the one module that sequences it correctly. Reapplies at: W29 recovery (`pool.unsafe_apply` only callable by `recover`), W42 txn apply, W64 raft log apply.

  - **(EXPERT, cross-primitive) When `bufpool_eviction_respects_durable_lsn` flushes an undurable page:**
    - Symptom: a page with `pageLSN > durable_lsn` was written to mmap; a crash recovers half a tx (the D4 interleaving).
    - Why: the replacer picked the LRU dirty page without consulting the durability watermark — it stole an uncommitted page.
    - Fix: eviction predicate becomes "evict if clean, OR (dirty AND pageLSN <= durable_lsn); else SKIP." Share `durable_lsn` as `Arc<AtomicU64>` between wal and pool; the replacer reads it (Acquire) per candidate.
    - Cost avoided: a half-committed tx on disk with no log to undo it — silent corruption that only the 1000-run VOPR catches.
    - Muscle: the no-steal rule — never flush a page whose changes aren't yet durable; the buffer pool must consult the durability watermark before evicting. Reapplies at: W29 ARIES steal/no-steal variants, W42 txn manager, W95 mini-db checkpoint.

  - **(EXPERT) When `pagelsn_max_under_concurrent_commits` reports the first committer's LSN:**
    - Symptom: pageLSN = L1 (first to commit) even though tx2's mutation (L2 > L1) is the visible one — watermark lies low.
    - Why: pageLSN was set outside the page latch; tx1 set pageLSN=L1, then tx2 mutated under a new latch and set pageLSN=L2, but a reorder left the lower value (the D5c shortcut).
    - Fix: the pageLSN write happens under the SAME exclusive latch as the page mutation — both are one critical section; after unlock, pageLSN reflects the latest applied change.
    - Cost avoided: a pageLSN that under-reports → recovery redoes already-applied records (at best wasteful, at worst non-idempotent corruption).
    - Muscle: pageLSN and the page bytes update atomically under one latch — never release the latch between them. Reapplies at: W29 ARIES pageLSN consistency, W42 txn apply.

  - **(EXPERT) When `vopr_1000_crash_no_partial_tx` reports 12/1000 partial-tx trials:**
    - Symptom: 12 seeds leave some keys of tx-X visible and others not.
    - Why: a race where `last_lsn` advanced before `page.pageLSN` was set; recovery saw the page as "already at this LSN" and skipped a redo it should have done.
    - Fix: each (wal-append, page-apply, pageLSN-set) triple is atomic w.r.t. observability — `last_lsn` is published (Release) only after pageLSN is set; recovery redoes per-record independently from the durable wal, which holds every record.
    - Cost avoided: a 1.2% partial-tx rate — invisible in unit tests, fatal in production; only the seeded 1000-run VOPR surfaces it.
    - Muscle: every (log, apply, watermark) step must be atomic w.r.t. what a reader/recovery can observe; if a reader can see the wal record but not the page (or vice versa), recovery's invariants break. Reapplies at: W29 redo correctness, W64 raft entry apply, W92 ledger VOPR.
