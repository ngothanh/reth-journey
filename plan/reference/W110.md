## Saturday — Build: `staleness_probe` — prove the two §4A projection staleness contracts hold in production

- [ ] **Build (bar (b), bar-(c) measurement discipline)**: `crates/perp-dex-core/src/ops/staleness_probe.rs` — a live probe that continuously verifies the **two §4A projection staleness contracts**: (1) the **control/risk plane** serves **read-after-commit from local applied state on the leader shard** (a risk decision NEVER sees stale state), and (2) the **analytics plane** serves **best-effort bounded-staleness (≤500ms / ≤1000 ops) carrying an op-number token** (a metric, not an SLA). The probe emits the metrics the Tuesday dashboard and Monday alerts consume, and asserts contract-violation in CI. (~total 115 min across 3 phases)
  - 🔧 **Why this matters**: §4A acceptance #5 is one of the locked v1.0 interfaces — *two projection staleness contracts surfaced*, and crucially **a risk decision served from the analytics contract fails**. The capstone's correctness story depends on the control/risk plane being read-after-commit (no consensus round-trip; it reads local applied state on the leader shard) while the analytics plane is allowed to lag. If those two get conflated — if a risk/liquidation decision ever reads the bounded-staleness analytics projection — the venue can liquidate (or fail to liquidate) on stale state: a correctness violation that no latency benchmark would catch. This probe is the *production proof* that the contract holds, and the *regression gate* (W111's perf pass must not break it). The naive probe has three traps that produce a *false green*: (1) **coordinated omission** — a closed-loop probe that waits for each read only measures service time and reports the analytics lag as ~0 even when it's seconds behind under load; (2) **measuring the wrong plane** — probing the analytics endpoint and concluding "the control plane is fresh" (they are different read paths); (3) **op-number-token blindness** — checking wall-clock staleness but not verifying the analytics read carries a *correct* op-number token, so a stale read that *claims* to be fresh passes. First-attempt probes fail ≥1 test below; the debug session is the lesson. Downstream: W111's perf changes are gated on this probe staying green (the read-after-commit contract must survive the incremental-margin hot-path rework); W112 Blog #5 cites the contract demonstration; W113 v1.0 evidence includes the production staleness report.

  #### Phase 1 — Problem, prediction, design (~30 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/perp-dex-core/notes/110_staleness_prediction.md`:
    - P1: which read path does a *risk/liquidation* decision take, and which does an *analytics/dashboard* query take? Write the exact two call sites (the control-plane `read_local_applied(leader_shard)` vs the analytics-plane `read_projection() -> (rows, op_token)`). State, in one line, the §4A rule that separates them.
    - P2: predict the control-plane read staleness you'll measure (should be 0 ops behind by construction — read-after-commit from local applied state) and the analytics-plane staleness under sustained load (ops behind + ms behind). Two numbers each.
    - P3: predict what a *closed-loop* probe (waits for each read before issuing the next) will report as analytics lag vs the *true* open-loop lag under load — by what factor do they differ?
    - P4: predict whether a probe that reads ONLY the analytics endpoint can ever detect a control-plane staleness violation. Yes/no + why.
    - P5: list every Phase-2 test you predict your first attempt will fail. Compare to reality after the tests run.
  - *Mental model*: the probe is two independent measurements against two independent read paths. **Control/risk plane**: issue a known-committed op (capture its `op_number` at commit), then immediately read the control-plane endpoint on the *leader shard* and assert the read reflects state at ≥ that op_number — i.e. read-after-commit, *zero* ops behind, no consensus round-trip. A single violation is a correctness alarm. **Analytics plane**: read the projection endpoint, capture its `(rows, op_token)`, compare `op_token` against the leader's current `commit_num`, and record `ops_behind` + `ms_behind` as a *metric*; assert it stays within the ≤1000 ops / ≤500 ms *budget* (a budget breach is informational, not a page — but a budget breach is still recorded so W111's perf pass can't silently widen the lag).
  - *Contract* (signature-level only — never the body):
    ```rust
    struct ControlReadResult { op_number_seen: u64, committed_op_at_read: u64 } // must satisfy seen >= committed_at_issue
    struct AnalyticsReadResult { op_token: u64, leader_commit_num: u64, ms_behind: u64 }
    struct StalenessReport {
        control_violations: u64,        // MUST be 0 — read-after-commit invariant
        analytics_ops_behind_p99: u64,  // budget ≤ 1000 (metric, not SLA)
        analytics_ms_behind_p99: u64,   // budget ≤ 500 (metric, not SLA)
        samples: u64, seed: u64, rig_state: String,
    }
    fn probe_control_plane(cluster: &PerpDexCluster) -> ControlReadResult;   // read-after-commit on leader shard
    fn probe_analytics_plane(cluster: &PerpDexCluster) -> AnalyticsReadResult; // bounded-staleness + op token
    fn run_staleness_probe(cluster: &PerpDexCluster, cfg: ProbeConfig) -> StalenessReport;
    ```
  - *Back-of-envelope* (measurement-discipline, bar-(c)-grade): the control-plane read is *local applied state on the leader shard* — no network round-trip, so its staleness is structurally 0 ops (the only way it's >0 is a code bug routing the risk read to the wrong path). The analytics plane lags by the projection fan-out delay (W107): at ≤500ms budget and ~1M ops/s peak, ≤500ms could be up to ~500k ops if unthrottled — which is why the contract *also* caps ops-behind at ≤1000 (the tighter of the two binds). Probe cost: a `record()` that does `Vec::push` may `malloc` (~50ns) mid-measurement and pollute the analytics-lag sample — pre-size the histogram. The CO cliff: a closed-loop probe can report analytics lag = 0 while the true open-loop lag under load is 400ms — the lag is *hidden by the probe waiting*, exactly the failure mode that lets a perf regression widen the projection lag undetected.
  - **Requirements** R1..R7 — write in `crates/perp-dex-core/notes/110_staleness_design.md`:
    - R1. Two *distinct* read paths: `probe_control_plane` calls the exact endpoint risk/liquidation uses (local applied state, leader shard); `probe_analytics_plane` calls the exact endpoint dashboards/analytics use (the projection). The probe must NOT share a code path between them, or it can't catch a mis-route.
    - R2. **Control-plane invariant**: capture `op_number` at commit of a probe op; the control read must reflect state at ≥ that op_number with *zero* ops behind. Any deviation increments `control_violations` and is a hard CI failure.
    - R3. **Analytics-plane budget**: record `ops_behind` and `ms_behind`; assert p99 within ≤1000 ops AND ≤500 ms. A breach is recorded + alarmed as a *metric* (warn, not page), never silently dropped.
    - R4. **Op-number token verification**: the analytics read carries an `op_token`; the probe verifies the returned rows are consistent with that token (a read claiming token T must not contain an effect from an op > T) — catches a stale read that lies about its freshness.
    - R5. **Open-loop measurement**: the analytics-lag sampler does NOT wait for each read before issuing the next; lag is measured against the leader's *current* `commit_num` at sample time, so a queued/throttled projection inflates the recorded lag correctly (coordinated-omission-honest).
    - R6. **Allocation-free measured window**: histograms pre-sized; the sampling path allocates nothing during the measured window (verified by a counting allocator test). A probe that allocates can't certify a latency-sensitive contract.
    - R7. **Report emitted as JSON** (`bench/staleness_v1.0.json`) with seed, rig state, both planes' results — for the W111 before/after comparison and the W113 v1.0 evidence.
  - **Design walk-through** D1..D6 — answer in the design doc; no peeking at the W107 projection-fanout source until Phase 3:
    - D1. Two-path table: control-plane (read-after-commit, leader-shard-local, 0-round-trip) vs analytics-plane (projection, bounded-staleness, op-token). Columns: round-trip? staleness-allowed? page-on-breach? Justify why a risk decision MUST use the first.
    - D2. How the control-plane read achieves zero-ops-behind *without* a consensus round-trip (it reads the leader shard's *local applied state*, which is by definition at or ahead of any committed op the client just observed).

  - **(SENIOR) When `zone_map_skips_at_least_one_chunk_on_selective_predicate` reports 0 skips:**
    - Symptom: the selective `symbol = BTC` query scans all 3 chunks; the skip counter is 0; bench is slower than it should be.
    - Why: the scan ignored the per-chunk (min, max) zone map and unconditionally streamed every chunk.
    - Fix: before reading a chunk's data, test `pred ∩ [zone.min, zone.max] == ∅` → if so, skip and increment the skip counter; only materialize chunks that can match.

  - **(EXPERT, perf) Expect to hit (perf) #1 — `vectorized_filter_aggregate_beats_baseline_5x` reports ~2× (branch mispredict):**
    - Symptom: the bench shows ~2×, not ≥5×; `perf stat` shows a high `branch-misses` rate on the filter loop.
    - Why: the filter is a scalar per-row loop with a data-dependent `if row > x { keep }` → ~50% mispredict on random data → ~5 ns/row branch tax dominates (~50 ms over 10M rows), and the row-struct scan misses cache on every stride.
    - Fix: vectorized kernel — load a contiguous column chunk (L1/L2-resident), compare lanes with SIMD, blend into a selection mask with NO per-row branch; the loop is now bandwidth-bound (~1–2 ns/row). The contiguous column + no-branch is what unlocks the predicted ≥5×.
    - Cost avoided: the ~50 ms branch-mispredict tax + the row-stride cache misses — the entire gap to the ≥5× claim.
    - Muscle: a hot filter emits a mask and never branches per row; columnar layout keeps the scan L1-resident. Reapplies at: v0.7 SIMD aggregate, M31 join probe, any `latency-lab` kernel.

  - **(EXPERT, anti-shortcut) When `kernel_inner_loop_zero_alloc` reports 1M allocations:**
    - Symptom: the counting allocator shows one malloc per batch (or per row) inside the kernel.
    - Why: the output selection mask is a `Vec` grown by `push`, reallocating mid-loop (~50 ns each) on the analytics path.
    - Fix: pre-size the output `Bitmap`/mask once per batch (the batch length is known) and write into it; no growth inside the inner loop.
    - Cost avoided: a self-inflicted analytics-latency tail; an allocating kernel can't hold a tight bench band.
    - Muscle: kernel output buffers are pre-sized; the inner loop allocates nothing (hot-path discipline applies to analytics too). Reapplies at: v0.7 RLE output buffer, M31 join output, W111 perf-pass measurement.

  - **(SENIOR, cross-primitive) When `groupby_window_rollup_deterministic` shows different row orders:**
    - Symptom: two runs of the same group-by emit the rollup rows in different orders; an analytics diff "flakes."
    - Why: the group accumulators live in a `HashMap<(Symbol,Minute), Agg>` iterated in seed-randomized order.
    - Fix: `BTreeMap` keyed by `(Symbol, Minute)` (or sort the keys on emit) so the rollup is a deterministic function of the input.
    - Cost avoided: a non-reproducible analytics report — the same determinism discipline the hot path enforces, applied to the off-path rollup.
    - Muscle: any output-affecting aggregation uses deterministic key order. Reapplies at: v0.7 late-materialization join order, perp-dex-core analytics fan-out.
