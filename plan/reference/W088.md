## Monday–Tuesday — `ledger-deterministic` VOPR: multi-process scenario runner

- [ ] [HFT] **Build (bar (c))**: `crates/ledger-deterministic/src/vopr/runner.rs` — a multi-process VOPR runner: a long-lived worker pool (one fork+exec per core) executing scenarios fed as newline-delimited JSON over stdin, returning per-scenario `{seed, final_state_hash, outcome}` JSON on stdout. (~total 4 hrs across 3 phases)
  - 🔧 **Why this matters**: this is the machinery that *validates the entire capstone*. §4A acceptance #2 (3-node VSR survives crash/restart with no lost commits, proved by cluster-VOPR) and #7 (linearizability + replica convergence + insurance-fund tripwire never hit) are unreachable without it — and at W108 this exact runner is scaled from ledger-only to the whole venue. VOPR's bug-finding power scales linearly with scenarios/second, and a single in-process runner is doubly wrong: one panic kills the whole process (no fault isolation), AND a naïve `Command::new(self_exe)`-per-scenario design pays a ~5 ms fork+exec tax that becomes ~80% of wall-time. The two traps that bite first attempts: (1) **fork-per-scenario** instead of a long-lived pool; (2) **non-deterministic state-hash** (HashMap iteration / native-endian bytes) that silently forfeits cross-machine reproducibility — and with it the §4A "deterministic, replay-safe core" lock. A first attempt WILL fail `worker_pool_one_fork_at_startup` and `state_hash_cross_arch_deterministic`; the debug session is the lesson. Bar (c): VOPR-grade requires a documented, measured scenarios/day throughput. Downstream: W92 ledger v1.0 SHIP determinism gate (this exact runner), W90 consensus-vsr VOPR (plugs in Friday), **W108 perp-dex-core cluster-VOPR** (this runner over the whole venue).

  - 🔧 **Decomposition prompt (silent test)**: this spec doesn't name primitives. The worker pool needs fault isolation (processes, not threads); the result channel needs no shared memory (one JSON line per scenario); the canonical hash needs sorted iteration + explicit little-endian; the timeout path needs a deadline + SIGKILL + reap; the respawn path needs terminal-vs-transient discrimination. The spec names none of them — your toolkit from W5–W17 + the production primitives must combine to meet the acceptance. If the dhat/RSS report shows growth, or the cross-arch hash diverges, or throughput misses the band — your decomposition missed something specific.

  - *Mental model*: a VOPR runner is a work-stealing scheduler over a fixed pool of OS processes; each process is a deterministic sandbox that takes a seed and returns a canonical state hash. Fault isolation (a panicking scenario must not kill siblings) is the reason for processes over threads. The canonical hash is the *convergence oracle* — the single thing every replica and every machine must agree on; if it leaks non-determinism, the §4A deterministic-core lock is broken at the root.
  - *Contract* (signature only — never the body):
    ```rust
    pub struct Runner { workers: Vec<WorkerProc>, queue: VecDeque<Scenario> }
    pub struct WorkerProc { child: Child, stdin: BufWriter<ChildStdin>, stdout: BufReader<ChildStdout> }
    pub struct Scenario { seed: u64, op_count: u32, fault_script: FaultScript }
    pub struct ScenarioResult { seed: u64, final_state_hash: [u8; 32], outcome: Outcome }
    pub enum Outcome { Passed, Failed { assertion: String }, Timeout }
    impl Runner {
        pub fn spawn_pool(n_workers: usize) -> io::Result<Self>;   // fork+exec ONCE per worker
        pub fn run(&mut self, scenarios: Vec<Scenario>) -> Vec<ScenarioResult>;
    }
    pub fn hash_canonical(sm: &StateMachine) -> [u8; 32];          // single audited convergence oracle
    ```
  - *Back-of-envelope* (bar (c)): fork+exec ≈ 5 ms (page-table copy + linker + `_start`). At 100 scenarios/run, per-scenario spawn = 5 ms × 100 = **500 ms setup**; for 600 ms median scenarios that is ~80% setup tax — cliff ratio **spawn-once ~50 µs amortized vs spawn-per-scenario 5 ms = 100×**. Pipe IPC (JSON encode + `write` + decode) ≈ 10 µs/scenario, negligible vs scenario body. Target R5: 100 scenarios in <60 s on 8-core M2 ⇒ ≥140k scenarios/day per machine ⇒ 8-machine fleet ≥1M/day (the W108 cluster-VOPR coverage budget rides on this number).
  - **Requirements** R1..R9 — write in `crates/ledger-deterministic/notes/88_runner_design.md`:
    - R1. Each worker is a fresh process (`Command::new(self_exe)` with a `--vopr-worker` arg), NOT a thread.
    - R2. Seed S chosen in master → echoed in `ScenarioResult.seed`; re-runnable as `--replay --seed S`.
    - R3. `state_hash` canonical (W83 encoding) so the same seed → same hash on any machine.
    - R4. Workers communicate results via one JSON line on stdout — no shared memory.
    - R5. 100 scenarios in <60 s on 8-core M2 ⇒ ≥140k scenarios/day per machine.
    - R6. Per-scenario wall timeout (60 s) → SIGKILL the worker, record `Timeout`, respawn the worker slot.
    - R7. A panicking scenario is marked `Failed` on first panic and is NOT re-queued.
    - R8. Long-lived worker pool: one fork+exec per core at startup, NOT per scenario.
    - R9. Cross-arch `state_hash` deterministic: BLAKE3 over sorted-by-key, explicit-little-endian bytes.

      | strategy | per-scenario cost | fault isolation | determinism | startup cost |

    - D4. **Pre-mortem — HashMap/native-endian in state_hash:** `for (k,v) in sm.accounts.iter() { h.update(k.as_bytes()); h.update(&v.balance.to_ne_bytes()); }`.     - D7. **Pre-mortem — respawn loop:** a scenario that panics on replay gets re-queued → infinite loop. Mitigation: `Failed` scenarios are terminal, never re-queued (R7).

  #### Phase 3 — Make the tests pass, one failure at a time (~140 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `panicking_scenario_failed_not_requeued` reports `results.len() == 3`:**
    - Symptom: scenario 1 appears twice (or the runner hangs) — the panicking scenario was put back on the queue.
    - Why: the master treats a worker that died/returned error as "scenario not done" and re-queues it.
    - Fix: on a worker reporting `Failed`/exit, mark the scenario terminal and record the result; never re-enqueue. `Timeout` respawns the *worker* but the scenario is still terminal.
    - Cost avoided: an infinite respawn loop that pins a core at 100% and produces zero new coverage (a liveness bug in the test harness itself).
    - Muscle: in any retry/respawn scheduler, distinguish *transient* (respawn the executor) from *terminal* (record and move on); conflating them livelocks. Reapplies at: W90 consensus-vsr view-change (a crashed replica respawns; a poisoned op does not retry), W108 cluster-VOPR partition drills.
  - **(SENIOR) When `worker_pool_one_fork_at_startup_not_per_scenario` reports `forks == 100+`:**
    - Symptom: profile shows `clone3` + `execve` dominating; ~1k scenarios/min vs ~16k/min target; `forks` ≈ scenario count.
    - Why: runner written as "for each scenario: `Command::new(self_exe).spawn()`; write; await; collect." Each fork+exec ≈ 5 ms (page-table copy + dynamic-linker setup + `_start` init). 100 scenarios = 500 ms setup; for 600 ms scenarios that is ~80% setup tax.
    - Fix: `spawn_pool(n)` forks+execs N workers ONCE at startup (~50 µs amortized/worker over the day). Each worker reads newline-delimited `Scenario` JSON from stdin in a loop, runs it, writes `ScenarioResult` JSON, loops. Master keeps a work-stealing queue feeding `stdin` via `BufWriter`. Per-scenario IPC ≈ 10 µs.
    - Cost avoided: **~5 ms spawn × 100 scenarios = ~500 ms/run, ~80% throughput unlock (100× per-scenario)** — drives 100k → 1M scenarios/day (bar (c) violation otherwise: documented throughput misses the fleet target, and W108 cluster-VOPR coverage starves).
    - Muscle: in any "do N identical things in parallel" architecture, amortize setup once at startup, never per task. Reapplies at: W90 io_uring journal (ring constructed once, not per write), W82 matching-engine shard workers (per-symbol core-pinning once at startup), W77 messaging-aeron Conductor (one agent per shard, not per publication).
  - **(SENIOR) When `timeout_kills_worker_records_timeout_then_continues` hangs forever:**
    - Symptom: the test never returns; scenario 2 never runs.
    - Why: master does a blocking `child.wait()` / blocking `read_line` with no deadline, so an infinite-loop scenario blocks the whole pool slot indefinitely.
    - Fix: arm a per-scenario 60 s deadline (a timer thread or `poll`/`select` on the pipe with timeout); on expiry `kill(pid, SIGKILL)`, record `Outcome::Timeout`, then `waitpid` and respawn the worker slot.
    - Cost avoided: a single pathological scenario silently halting an overnight 10k-scenario CI run (zero coverage for the night, undetected).
    - Muscle: every blocking wait on an untrusted producer needs a deadline + kill path; "it'll finish eventually" is not a liveness guarantee. Reapplies at: W90 io_uring (submission with completion timeout), W74 consensus-vsr request timers, W108 cluster-VOPR stuck-cluster detection.
  - **(SENIOR) When `no_hashmap_audit` passes even with an injected `HashMap`:**
    - Symptom: the deny test's negative control fails — injecting `HashMap` does NOT trip `cargo deny`.
    - Why: `cargo-deny`'s `disallowed_types` only catches direct type references the lint pass sees; a transitive dep's `HashMap` or an aliased import slips through.
    - Fix: combine `cargo deny` `disallowed_types = ["std::collections::HashMap", "ahash::AHashMap", "fxhash::FxHashMap"]` with a CI `rg 'HashMap|HashSet' crates/ledger-deterministic/src/` audit script, AND keep the golden-hash test as the real backstop.
    - Cost avoided: a silent re-introduction of non-deterministic iteration that passes lint but breaks cross-machine replay (the determinism debt — exactly the §4A deterministic-core lock).
    - Muscle: a lint is only trustworthy once its negative control proves it bites; back determinism with a behavioral golden test, not a lint alone. Reapplies at: Friday's VSR `no_instant_now_leak` lint (below), W90 consensus-vsr v1.0, W92 ledger v1.0 determinism gate.
  - **(EXPERT) When `state_hash_cross_arch_deterministic` reports order-dependence or ARM≠x86:**
    - Symptom: same-machine hash varies by insertion order, OR x86 hash ≠ ARM golden; cumulative "1M scenarios" count fragments because reproduce-by-seed can't verify across machines.
    - Why: `accounts: HashMap` (run-random iteration) or `to_ne_bytes` (endian-dependent), or a nested `HashSet` field leaking order.
    - Fix: a single audited `hash_canonical(&sm)`: (a) `accounts: BTreeMap<AccountId, Account>` only; (b) BLAKE3 over sorted `(key, fixed-LE-value)` byte stream; (c) every integer via `to_le_bytes`, never `to_ne_bytes`; (d) cargo-deny + rg audit guards regressions; (e) cross-arch CI: x86 + ARM nodes produce identical hash for the same seed.
