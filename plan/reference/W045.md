**Why this week is light on Build arcs (but heavy on real engineering):** this is an **upstream-contribution week**, not a workspace-crate build week. The "Build" here is a *real feature in someone else's codebase*, shipped through a *real review process* — so the deliverable is not an engineered trap-test arc you control end-to-end, it is a merged-or-in-review PR that survives a maintainer's review bar. Per the curriculum's light-week rule, every item below therefore names its file/artifact + an Output line, folds references into the frontmatter, and carries a **🎯 Hardened acceptance** bar so "I worked on the PR" can never pass for "the PR is mergeable". The single biggest risk this week is **a PR that is technically correct but un-mergeable** — wrong scope (too big), missing tests, breaks back-compat, or no benchmark on a hot path. The hardened-acceptance bars below are written to catch each of those before a maintainer does. The current week was ~3h of vague one-liners; this rework loads it to the real ~25-30h an upstream storage PR actually costs.

  - Output: `notes/45_feature_design.md` exists with the signature, the back-compat verdict (one of: additive / default-method / sealed-extension / breaking-with-justification), and the rejection pre-mortem trace.

  - *Mental model*: every comment a maintainer has to leave is a round-trip that pushes the merge past this week. Pre-empting their review — running the same checks they will — is how a first-time-reviewer PR lands in one or two rounds. You did this self-audit discipline on `storage-trie` (W44 Tuesday security self-audit); apply the identical lens upstream.

  - 🎯 **Hardened acceptance**: `notes/45_self_review.md` has an explicit ✓/✗ for each of the 5 checklist items; every ✗ has a fix applied (so the committed state is all-✓) OR a one-line justification for why it's acceptable upstream; no new `unwrap`/`expect` survives on a fallible db/IO path without justification.
  - Output: `notes/45_self_review.md` shows 5 checklist verdicts all resolved to ✓ (or ✗-with-justification); `git grep -n 'unwrap()\|expect(' <changed-files>` shows no new occurrence on a fallible path, or each is annotated in the self-review.
- [ ] Commit + log (~10 min)

**Thursday — Tests (and benchmark, if the feature is on a hot path)**

- [ ] **Test**: add the feature's test(s) in the touched crate's `tests/` or `#[cfg(test)]` module — engineered to actually exercise the new path, not just compile it. (~120 min)
  - *Mental model*: an upstream maintainer's first question is "where's the test?" — a storage feature without a test that *would fail on the old code* is un-mergeable on sight. The test must be a genuine **regression guard**: revert your feature, the test must go red. A test that passes on `main` proves nothing and will be flagged.
  - 🎯 **Hardened acceptance**: the new test FAILS when run against the pre-feature code (verify by `git stash` of the impl, run test → RED, `git stash pop` → GREEN) — this is the negative-control "test-the-test" proof that the test guards the actual new behaviour; `cargo test -p <crate> <test_name>` is green with the feature; if the feature touches a stage's unwind, a test asserts the unwind reverts correctly (mirrors your W44 state-root-safety unwind==revert muscle).
  - Output: `cargo test -p <crate> <test_name>` green with feature; the same test RED after stashing the impl (record both run outputs in `notes/45_test_evidence.md`); for a stage feature, an unwind-revert assertion is present.
- [ ] **[hot path only] Benchmark**: if Monday flagged the feature as hot-path, add/extend a criterion bench in the crate's `benches/` and record the before/after numbers. (~45 min, skip if cold path)
  - *Mental model*: reth maintainers gate hot-path storage changes on "no regression" — claiming "it's fast" without a bench is the fastest way to stall a storage PR. A measured before/after (even "+2% within noise") pre-empts the request. Use Jeff-Dean anchors to sanity-check: a trie node read that should be a warm cache hit (~few ns) but shows ~100ns means you added a main-memory miss; a stage step that grew by a syscall (~300ns) means you added IO to the inner loop.
  - 🎯 **Hardened acceptance**: `cargo bench` produces a before (on `main`) and after (with feature) number for the touched operation; the delta is stated with its noise band; any regression > 5% has a written justification or a fix; the absolute number lands in a physically-plausible band (e.g. an in-memory trie op in the 10ns–1µs range, not 0ns and not 100µs — a result outside the band means the bench measures nothing).
  - Output: `notes/45_bench_evidence.md` records before/after with noise band; regression (if any) ≤ 5% or justified; the number is inside its plausible band.
- [ ] Commit + log (~10 min)
