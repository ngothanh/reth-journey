- [NEW v2] **exec-vm v1.5: optimistic concurrent executor (part 1)**
  - [ ] **Build**: `crates/exec-vm/src/parallel/executor.rs` — N worker threads consume tx queue, execute optimistically, validate against finalized prefix. On conflict, re-execute. (~3 hrs)
    - **Why**: with rwset (W91) and versioned memory (W92) in place, the executor is the orchestrator that makes block-stm a productive system. The pattern: N worker threads consume from a shared task queue alternating between Execution and Validation tasks. On conflict, validate fails; mark dependent txs `Estimate`; re-schedule. Mirror Aptos's `BlockStmExecutor::execute_v3`.
    - **Read first**: Aptos block-stm paper §5 "Scheduler"; Aptos `aptos-block-executor/src/scheduler.rs`; block-stm crate from Paradigm Reth PR.
    - **Design**:
      ```rust
      pub struct BlockExecutor {
          num_workers: usize,
          txs: Vec<EthTx>,
          rw_sets: Vec<Mutex<Option<RwSet>>>,        // per tx
          incarnations: Vec<AtomicU32>,              // per tx
          versioned: Arc<VersionedMemory>,
          scheduler: Arc<Scheduler>,
      }
      pub struct Scheduler {
          next_task: AtomicU64,                      // packed: kind | tx_idx | incarnation
          done_txs: AtomicU32,
          validation_idx: AtomicU32,
          execution_idx: AtomicU32,
      }
      pub enum Task { Exec { tx_idx, incarnation }, Validate { tx_idx, incarnation }, NoTask }
      impl BlockExecutor {
          pub fn execute_block(&mut self) -> BlockResult;
          fn worker_loop(&self);
      }
      ```
      **Invariants**: (i) txs are committed IN ORDER (block-stm preserves block ordering at COMMIT, not at execute); (ii) Validation tasks ALWAYS scheduled in order — validation_idx monotonic; (iii) any conflicted tx's incarnation increments; previous version marked Estimate; (iv) executor terminates when `validation_idx == num_txs` AND all txs validated against their final incarnation.
    - **Build steps**: 1. (~15 min) struct + worker thread spawn pinned to cores. 2. (~30 min) `Scheduler::next_task()` — atomic CAS on packed task; prefer Validate over Exec when validation_idx < execution_idx. 3. (~30 min) `worker_loop`: loop { match next_task { Exec → execute, Validate → validate, NoTask → spin/park }}. 4. (~30 min) execute tx: clone revm Database wrapping VersionedMemory + RwSet recorder; run revm; commit to versioned with (tx_idx, incarnation); store rw_set. 5. (~30 min) validate tx: replay rw_set.reads against VersionedMemory; if any read returns different version → fail; mark estimate on writes; bump incarnation; re-schedule exec. 6. (~20 min) termination: validation_idx reaches num_txs AND no estimates outstanding. 7. (~15 min) tail handling: when validation fails for tx N, ALL subsequent txs M > N that read N's writes are also re-validated (cascade). 8. (~10 min) finalize: in commit order, apply writes to canonical state.
    - **Pitfalls**: *Worker stall on hot key*: **Symptom**: all workers spinning on DependsOn for one slow tx. **Fix**: parking via condvar OR steal-from-validation; under high contention fall back to sequential. *Validation order*: **Symptom**: validate(N) runs while validate(N-1) is pending. **Fix**: monotonic validation_idx atomic; never validate N until N-1 validated. *Cascading re-execution*: **Symptom**: invalidating tx N cascades to N+1...N+10, each re-exec invalidates the next. **Fix**: cascade by bumping ALL dependents' incarnations atomically; document amortized cost. *Memory blowup*: **Symptom**: each tx's RwSet retained until block end. **Fix**: cap at MAX_TXS_PER_BLOCK (10k) + memory limit; fallback to sequential for outliers.
    - **Test scenarios**: 1000-tx synthetic block with 10% conflict rate → re-execute rate ≤ 12%; total wall time < 0.5× sequential (target speedup). 1000-tx all-conflict block → falls back gracefully; result still correct. Property: result matches sequential exec byte-identically for all conflict rates 0%-100%.
    - **Acceptance**: 1000-tx block @ 10% conflict, 4 workers: re-exec rate ≤ 12%, wall time ≤ 30% of sequential.
    - **Downstream**: W94 SHIP feature `parallel-evm` gates this on; bench in W94 compares to sequential on real block traces.
