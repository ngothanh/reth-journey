The four traps that sink a first attempt: **(1)** validation must complete in strict block order even though execution runs out-of-order — a naive shared `validation_idx` counter lets two workers validate (6) and (7) at once and the "finalized prefix" silently breaks; **(2)** writes flushed to canonical state during `execute` (instead of at `finalize`) make the *last parallel writer*, not the last block-order writer, win — a determinism violation that passes a low-conflict test by luck; **(3)** a `DependsOn(hot_key)` chain makes all 8 workers busy-spin re-fetching the same blocked task, so the 8-core run is SLOWER than sequential; **(4)** false sharing of the packed `next_task: AtomicU64` against `validation_idx`/`execution_idx` in a `repr(Rust)` struct caps CAS throughput and kills the speedup gate. **First-attempt impls fail ≥1 test below; the debug session IS the lesson.** Downstream: W94 v1.5 SHIP (`parallel-evm` feature gates on this; the speedup + determinism gates are graded here), W94 real-block-trace bench, W94 inheritance audit.

    - *Mental model*: `BlockExecutor` is the conductor. Workers play out-of-order (execute), but the score (validation + canonical commit) is replayed strictly in block order. Optimism = "assume no conflict, verify after"; the scheduler is what makes the verification cheap AND ordered. It is a pure function `execute_block: (&[Tx]) → BlockOutput` whose output must be byte-identical to a sequential oracle for ANY conflict rate.
    - *Contract* (signature-level only — NEVER the body):
      ```rust
      // scheduler.rs
      pub enum Task { Exec { tx_idx: u32, incarnation: u32 }, Validate { tx_idx: u32, incarnation: u32 }, NoTask, Done }
      pub struct Scheduler { /* packed CachePadded atomics + per-tx status */ }
      impl Scheduler {
          pub fn new(num_txs: u32) -> Self;
          pub fn next_task(&self) -> Task;                 // CAS-claimed; Validate(N) only if validation_idx==N
          pub fn finish_execution(&self, tx_idx: u32, inc: u32, wrote_new_paths: bool) -> Option<u32>; // first idx to re-validate
          pub fn finish_validation(&self, tx_idx: u32, inc: u32, aborted: bool);
          pub fn add_dependency(&self, txn: u32, blocking: u32) -> bool; // false if blocking already done (retry now)
          pub fn done(&self) -> bool;                      // validation_idx==num_txs && execution_idx==num_txs && no estimates
      }
      // executor.rs
      pub struct BlockExecutor { num_workers: usize, versioned: VersionedMemory, scheduler: Scheduler /* ... */ }
      impl BlockExecutor {
          pub fn execute_block(&self, txs: &[Tx]) -> BlockOutput; // entry; spawns pinned workers; finalize in block order
      }
      ```
    - *Back-of-envelope* (the speedup gate is the perf contract; every number must be falsifiable on the bench rig):
      Sequential baseline ≈ 480 µs/tx (W94 figure). At 8 workers, R6 targets wall ≤30% of sequential ⇒ ≥3.3× *or* the relaxed W94 SHIP gate ≥2× at low conflict. The coordination tax that eats this: a `next_task()` CAS is ~25–40 ns *uncontended*; under 8-worker contention with false sharing it balloons to **300–1000 ns** (cache-line ping-pong — L2 ~7 ns, cross-core L3/coherence ~40–80 ns, plus exponential CAS retry). At ~1000 tasks/block (1 exec + ~1 validate per tx), 8× re-fetch on a hot-key stall = ~16k CAS/block; 16k × 1 µs = **16 ms of pure scheduler spin** vs a ~60 ms wall budget = **27% of the budget burned on coordination**. Cliff: scheduler line *not* CachePadded vs CachePadded ≈ 1 µs vs 40 ns CAS = **25× on the contended path**. Finalize is sequential memcpy: 1000 txs × ~10 ns = 10 µs, negligible — *as long as it stays out of the parallel section* (trap #2).
    - **Requirements** R1..R10 — write in `crates/exec-vm/notes/93mon_executor_design.md`:
      - R1. `BlockExecutor { num_workers, txs, rw_sets, incarnations, versioned, scheduler }` orchestrates worker threads pinned to cores (CONSUME the `runtime-thread-per-core` affinity helper, W44/W85 — do NOT re-roll pinning).
      - R2. `Scheduler::next_task() -> Task::{Exec, Validate, NoTask, Done}` — atomic CAS on packed `next_task` state (kind | tx_idx | incarnation).
      - R3. Validation tasks ALWAYS dispatched in block order: `validation_idx` is monotonic; `Validate(N)` is returned ONLY when `validation_idx == N`. Execution tasks may run out-of-order.
      - R4. On validation failure for tx N: bump N's incarnation; mark N's writes in `versioned_memory` as `Estimate`; cascade-invalidate dependents M > N that read N's writes.
      - R5. Executor terminates when `validation_idx == num_txs` AND `execution_idx == num_txs` AND no `Estimate` entries outstanding.
      - R6. Per-block target: 1000-tx block @ 10% conflict, 8 workers → wall ≤30% of sequential; re-exec rate ≤12%. (Measured, two-track — this is the SHIP gate root.)
      - R7. Worker stall avoidance: on `DependsOn`, the worker registers the dependency and switches to a `Validate` task instead of spinning; under high contention escalate to sequential.
      - R8. Property: parallel result byte-identical to sequential for ANY conflict rate (0%–100%) — the W94 determinism gate.
      - R9. Memory cap: `MAX_TXS_PER_BLOCK = 10_000`; per-tx RwSet retained until block end; fall back to sequential for over-cap blocks.
      - R10. Commit order: ALL writes applied to canonical state in block order at `finalize` (never at `execute`). Per-task writes go to `versioned_memory` only.

      - D2. Worker loop skeleton: `loop { match scheduler.next_task() { Exec→…, Validate→…, NoTask→backoff/park, Done→break } }`. What is the backoff ladder on `NoTask` (spin_loop a few iters → `Backoff` → park on condvar)? What wakes parked workers (scheduler signals after each `finish_*`)?
      - D3. Execute task: wrap revm `Database` over `VersionedMemory + RwSet recorder`; run revm; commit writes to `versioned_memory` keyed by (tx_idx, incarnation); store rw_set; `finish_execution`. If a read hits an `Estimate` (a not-yet-final write of a lower tx), revm aborts with `DependsOn(M)` — worker does NOT commit, calls `add_dependency(N, M)`.
      - D4. Validate task: replay `rw_set.reads` against current `VersionedMemory`; for each (key, version_at_read) check the current store still returns that version; any mismatch ⇒ fail. On success `finish_validation(N, inc, aborted=false)` advances `validation_idx`. On fail ⇒ invalidate.
      - D5. Cascade invalidation. Naive: walk forward from N, re-mark each M>N. Smart: a reverse index `(key, version) → {tx_idx that read it}`; on N's invalidation, re-validate only readers of N's writes. State which you'll implement first and why (correctness-first: pessimistic walk; then optimize once green).
      - D6. Termination predicate (R5). What if a `DependsOn` chain looks like a deadlock? (By construction tx_idx ordering forbids cycles: N can only depend on M<N. `debug_assert!(blocking < txn)`.)
      - D7. Hot-key stall (the trap-3 scenario): 200/1000 txs all `DependsOn(tx 5)`. Naive: all workers re-fetch the same blocked task → busy spin. Fix: `add_dependency` parks the worker against `tx 5`; when 5's incarnation finishes, `resume_dependencies(5)` re-marks them ready and signals. If no useful `Validate` available, park on condvar; else switch to `Validate`.
      - D8. Sequential-fallback escalation: detect re-exec rate >50% mid-block; cancel parallel, drop `versioned_memory` writes, replay sequentially from the pre-block snapshot.
      - D9. Finalize phase: in block order tx 0..N, apply each tx's highest-incarnation Committed writes to canonical state. Why not write canonical during execute? (Parallel writes race; canonical must be single-writer + ordered.) ~10 ns memcpy/tx.
      - D10. **Pre-mortem (load-bearing) — write the EXACT 6-line bad interleaving** where a "passes-tests" executor lets tx 6 commit before tx 5's validation, violating R10:
        ```
        t0  worker A: execute(tx5)  — slow (cold storage read)
        t1  worker B: execute(tx6)  — fast; both write slot K
        t2  worker B: validate(tx6) PASSES (tx5 hasn't touched K yet)
        t3  worker B: FLUSH tx6's K=6 to CANONICAL   ← the bug: commit at execute/validate, not finalize
        t4  worker A: execute(tx5) finishes; writes K=5 to CANONICAL on top
        t5  result: canonical K=5, but later block-order is tx6 ⇒ WRONG (should be K=6)
        ```
        The rule that prevents it: **finalize runs ONCE at end, applying all writes in strict block order; per-task commit is to `versioned_memory` only** (R10). If you can't write this interleaving, you can't prove your finalize design prevents it — that's the point.

    #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

    Ordered failure cards, newbie first → expert last — the ladder you actually walk.

    - **(NEWBIE) When `test_commit_order_preserved` shows canonical K = some random value, not 99:**
      - Symptom: 100 txs write slot K with 0..99; canonical K ends up 42 (or whatever finished last in wall-clock), not 99.
      - Why: writes were flushed to canonical state during `execute`/`finish_validation`; parallel completion order ≠ block order, so the *last parallel writer* wins, not the last block-order writer (exactly the D10 interleaving).
      - Fix: writes go to `versioned_memory` only during execute (multi-version, keyed by tx_idx); add a `finalize()` pass that walks tx 0..N in block order and applies each tx's highest-incarnation Committed writes to canonical. Canonical never sees a parallel write.
      - Cost avoided: a silent consensus-fork-class bug — green low-conflict tests, divergent state on the one block that happens to conflict. (Determinism is the W94 SHIP gate; this failure is a SHIP blocker.)
      - Muscle: in any MVCC/optimistic executor the canonical apply is a single-writer ordered pass AFTER all execution+validation — never interleaved. Reapplies at: W94 v1.5 SHIP determinism gate, W92 versioned-memory commit, W74 matching-engine commit order, W83 ledger op_num apply, W103 capstone apply.

    - **(NEWBIE) When `test_max_txs_per_block_falls_back` deadlocks or OOMs on the 15k block:**
      - Symptom: executor either hangs or allocates unboundedly building per-tx RwSets for 15k txs.
      - Why: no `MAX_TXS_PER_BLOCK` guard; the multi-version store + reverse index grow past the static budget.
      - Fix: at `execute_block` entry, if `txs.len() > MAX_TXS_PER_BLOCK` run the sequential path directly; the parallel path assumes a bounded block.
      - Cost avoided: unbounded memory (versioned-memory ~40 B × versions × slots) — a static-memory-invariant violation if this fed a bar-(c) crate.
      - Muscle: every parallel data structure needs a static upper bound and a graceful sequential fallback past it. Reapplies at: W94 SHIP memory ceiling, W92 versioned-memory MAX_VERSIONS, W103 capstone block sizing.

    - **(SENIOR) When `test_validation_order_strictly_monotonic` fires — `validate(7)` started while `validate(6)` in flight:**
      - Symptom: instrumentation shows `validate(7) Start` before `validate(6) Finish`; cascade logic then operates on a wrong "finalized prefix".
      - Why: `next_task` dispatched Validate by reading a `validation_idx` counter without claiming it, so two workers both grabbed Validate(6) and Validate(7) at once.
      - Fix: `next_task()` returns `Validate(N)` ONLY if `validation_idx.load() == N`, claimed via CAS; `finish_validation` CAS-increments `validation_idx` only after success. A worker that sees `validation_idx` ahead of its candidate skips and re-fetches.
      - Cost avoided: a wrong-prefix re-validation cascade ⇒ either a determinism break or a livelock — both SHIP blockers.
      - Muscle: monotonic-counter discipline is the load-bearing invariant of block-stm validation; claim-then-advance, never read-then-act. Reapplies at: W94 SHIP determinism gate, W74 matching-engine op_num ordering, W83 ledger op_num, W92 versioned-memory version monotonicity.

    - **(SENIOR) When `proptest_parallel_byte_identical_to_sequential` minimizes to a ~10-tx 50%-conflict counterexample:**
      - Symptom: parallel post-state differs from the sequential oracle in one slot at conflict ≥50%.
      - Why: cascade-invalidation gap — when tx N was invalidated, a dependent M>N that read N's writes was NOT re-validated (the "only invalidate close-by txs" optimization), so a stale read committed.
      - Fix: first ship the *pessimistic* walk (re-validate all M>N on N's abort) to get green; then build the reverse index `(key, version) → readers` and re-validate exactly the dependents (`test_cascade_invalidation_only_dependents` then tightens it).
      - Cost avoided: a determinism violation that only appears under high conflict — invisible to low-conflict benches, fatal at SHIP.
      - Muscle: cascade-invalidation completeness is correctness, not an optimization; correctness-first (pessimistic), then narrow with a reverse index. Reapplies at: W94 SHIP determinism gate, W92 versioned-memory Estimate propagation.

    - **(SENIOR) When `test_1000_tx_block_10pct_conflict_under_30pct_sequential` reports wall = 60% of sequential (1.67×, target ≥3.3×):**
      - Symptom: 8-worker parallel is only ~1.67× faster than sequential.
      - Why: a composition of (a) `DependsOn` busy-spin, (b) pessimistic O(N) cascade re-validation overhead, (c) hot-key `versioned_memory`/DashMap contention (W92 perf cards), and possibly (d) scheduler false sharing.
      - Fix: apply each lever — workers park-and-switch on `DependsOn` (R7), reverse-index cascade (D5), hot-key bypass for top-1% slots (W92), CachePad the scheduler atomics. Re-bench; expect ~2–3× depending on conflict mix.
      - Cost avoided: the difference between a shippable feature and a slower-than-sequential novelty; no single lever delivers — the stack composes. (This is the SHIP speedup gate.)
      - Muscle: parallel-exec speedup is the *product* of many small fixes; profile, then attack the top of the flame graph. Reapplies at: W94 SHIP speedup gate, W82/W110 matching-engine perf tune, every multi-threaded perf workload.

    - **(EXPERT) When `test_worker_no_spin_on_dependson` shows ~80% spin-CPU:**
      - Symptom: 8 workers all return `DependsOn(tx 5)`, re-fetch the same blocked task in a tight loop; cores pinned at ~80% doing no work while tx 5 runs.
      - Why: the worker loop's `DependsOn` and `NoTask` branches just re-call `next_task()` immediately — busy spin.
      - Fix: on `DependsOn(M)`, `add_dependency(N, M)` parks N's worker against M (CONSUME `concurrent::Parker`/condvar — do NOT re-roll); when M's incarnation finishes, `resume_dependencies(M)` re-arms them and signals. Backoff ladder first (short `spin_loop`, then `Backoff`, then park) so short deps don't pay a park.
      - Cost avoided: 8 cores × ~80% wasted = the entire speedup budget; on a hot-key block this makes parallel SLOWER than sequential.
      - Muscle: spin for short waits, park-and-signal for hot/long dependencies; never spin on a dependency you can't resolve yourself. Reapplies at: W4 Parker/Backoff, W11 MPMC backpressure, W22 concurrent primitives, W74 matching-engine cross-thread handoff.

    - **(EXPERT, perf) When `scheduler_state_no_false_sharing` fails — `validation_idx` at offset 8, not ≥64/128:**
      - Symptom: layout assertion fails; the three hot atomics live in one or two cache lines.
      - Why: `Scheduler` is `repr(Rust)`; the compiler packs `next_task`, `validation_idx`, `execution_idx` tightly. Every CAS on one invalidates the other two across all 8 cores (MESI ping-pong).
      - Fix: wrap each hot atomic in `concurrent::CachePadded<AtomicU64>` and `#[repr(C)]` the struct so the padding is load-bearing-stable (W4 muscle).
      - Cost avoided: ~25× on the contended CAS path (~1 µs vs ~40 ns per back-of-envelope) ⇒ at ~16k CAS/block that is ~16 ms vs ~0.6 ms of coordination on a ~60 ms budget — caught by the bench, NEVER by `cargo test`.
      - Muscle: when padding is load-bearing, lock the layout — CachePadded + repr(C), and assert the offset so a refactor can't silently re-share. Reapplies at: W4 CachePadded, W11 MPMC ring, W65 Disruptor sequencer/cursor, W82 matching-engine order-book hot fields.

    - **(EXPERT, loom) When `loom_scheduler_no_lost_task_no_double_claim` reports a lost task (or `loom_scheduler_model_must_be_slow` returns in <100 ms):**
      - Symptom: under some interleaving a parked worker is never woken (the `add_dependency`/`resume_dependencies` race: dependency added *after* the producer already finished), so `done()` never becomes true; OR the loom model finishes instantly (it explored nothing).
      - Why: lost-wakeup — `add_dependency(N, M)` checks "is M done?" and parks, but M finishes between the check and the park, so the resume signal is missed.
      - Fix: `add_dependency` must return `false` (don't park, retry now) if M is already done *under the same lock/atomic that resume reads*; the check-and-park is one critical section. The slow-negative-control guards against a degenerate loom model (e.g. all atomics accidentally `SeqCst`-collapsed, or threads not actually spawned via `loom::thread`).
      - Cost avoided: a hang under production interleavings that the single-threaded test suite can never reach — the worst kind of bug (non-reproducible deadlock).
      - Muscle: any park/signal pair needs loom verification AND a slow-negative-control proving the model is non-degenerate; the check-and-park must be atomic. Reapplies at: W4 atomic-hash loom + slow-negative-control, W11 MPMC loom, W22 epoch-gc loom, W74 matching-engine VSR loom.
