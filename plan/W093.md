    #### Phase 1 — Problem, requirements, design (~70 min, no code yet)

    - **The problem this primitive solves**: optimistic concurrent execution requires careful scheduling: validation must complete in block order even though execution runs out-of-order; conflicts cascade (invalidating tx N forces re-validation of N+1, N+2, ...); workers must avoid spinning on hot dependencies. Get scheduling wrong and 8-core parallel exec is SLOWER than sequential due to coordination overhead.

    - **Requirements** — write in `crates/exec-vm/notes/93mon_executor_design.md`:
      - R1. `BlockExecutor { num_workers, txs, rw_sets, incarnations, versioned, scheduler }` orchestrates worker threads pinned to cores.
      - R2. `Scheduler::next_task() -> Task::{Exec, Validate, NoTask}` — atomic CAS on packed `next_task: AtomicU64` (kind | tx_idx | incarnation).
      - R3. Validation tasks ALWAYS scheduled in block order (validation_idx monotonic); execution tasks may run out-of-order.
      - R4. On validation failure for tx N: bump tx N's incarnation; mark writes in versioned_memory as Estimate; cascade-invalidate dependent txs M > N that read N's writes.
      - R5. Executor terminates when `validation_idx == num_txs` AND no estimates outstanding.
      - R6. Per-block target: 1000-tx block @ 10% conflict, 4 workers → wall time ≤ 30% of sequential; re-exec rate ≤ 12%.
      - R7. Worker stall avoidance: on DependsOn, worker switches to validation task instead of spinning; under high contention, escalate to sequential.
      - R8. Property: parallel exec result byte-identical to sequential for ANY conflict rate (0%-100%) — the W94 determinism gate.
      - R9. Memory cap: MAX_TXS_PER_BLOCK = 10k; per-tx RwSet retained until block end; fallback to sequential for outliers.
      - R10. Commit order: all writes applied to canonical state in block order at finalize (not at execute).

    - **Design walk-through** — answer each; no peeking at Aptos `aptos-block-executor/src/scheduler.rs` or block-stm paper §5 until Phase 3:
      - D1. Packed task atomic: `next_task: AtomicU64` packs (kind: 2 bits | tx_idx: 30 bits | incarnation: 32 bits). Why pack? (Single atomic CAS for full task state.) Why prefer Validate over Exec when validation_idx < execution_idx? (Validation is the critical path; finishing validation unblocks dependent re-exec.)
      - D2. Worker loop: `loop { match scheduler.next_task() { Exec → execute(tx_idx, inc), Validate → validate(tx_idx, inc), NoTask → park } }`. What's the back-off when NoTask returned briefly? (spin_loop a few iterations, then park on condvar.) What wakes parked workers? (Scheduler signals after each task completion.)
      - D3. Execute task: wrap revm `Database` over `VersionedMemory + RwSet recorder`; run revm; commit writes to versioned_memory with (tx_idx, incarnation); store rw_set; advance execution_idx. What if execute returns DependsOn(M)? (Worker abandons tx N, marks as "waiting on M", picks a different task.)
      - D4. Validate task: replay rw_set.reads against current VersionedMemory; for each (key, version_at_read) check current store returns same version; mismatch = fail. On success, advance validation_idx. On fail: invalidate.
      - D5. Cascade invalidation: when tx N invalidates, all M > N that read N's writes must also re-validate. Naive: walk forward from N, re-mark each. Smart: mark only those whose RwSets contain N's writes (need reverse index: per-(key, version) → tx_idxs that read it).
      - D6. Termination: `validation_idx == num_txs && estimates_count == 0`. What if a deadlocked DependsOn chain exists? (By construction tx_idx ordering prevents cycles; assert in debug.)
      - D7. Hot-key stall: 200/1000 txs all DependsOn(tx 5). Workers all idle waiting on 5. Fix: each worker, on DependsOn, checks scheduler.next_task() again; if a Validate is available, switch. If still nothing useful, park. After producer tx finishes, scheduler wakes parked workers.
      - D8. Sequential fallback escalation: detected when re-exec rate > 50% mid-block. Cancel parallel, restart sequentially. Memory cleanup: drop versioned_memory writes; replay from snapshot.
      - D9. Finalize phase: in block order, apply each tx's writes to canonical state. Why not write canonical during execute? (Parallel writes would race; canonical must be sequential.) Apply order in finalize: tx 0's writes, then 1, then 2, ..., then N. Each apply ~10 ns memcpy.
      - D10. **Pre-mortem (load-bearing)**: write the 6-step interleaving where a "passes-tests" executor allows tx N+1 to commit before tx N's validation completes, violating R10. Scenario: worker A executes tx 5; worker B executes tx 6; B's validation completes first (tx 5 still running); B's writes flushed to canonical state. Tx 5 finishes; turns out to write same slot; canonical now has B's write, then A's write applied on top, but their order was 5 then 6. What rule prevents? (Finalize phase runs ONCE at end, applying ALL writes in block order; per-task commit is to versioned_memory only.)

    - **Output**: `notes/93mon_executor_design.md` with R1–R10 + D1–D10 + scheduler state diagram + cascade invalidation algorithm + sequential-fallback escalation logic.

    #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

    - **When `test_validation_order_strictly_monotonic` fires with validate(7) running while validate(6) pending:**
      - Symptom: instrumentation log shows `validate(7) started` before `validate(6) completed`; cascade logic operates on wrong "finalized prefix" state.
      - Why: scheduler dispatches Validate tasks based on validation_idx counter; without strict ordering enforcement, two workers can both grab "Validate(idx=6)" and "Validate(idx=7)" simultaneously.
      - Fix: `scheduler.next_task()` returns Validate(N) ONLY if `validation_idx.load() == N`. Use atomic CAS to claim the next validate slot. After completion, CAS-increment validation_idx. Workers seeing validation_idx ahead of their task skip and pick next.
      - Muscle: monotonic counter discipline is the load-bearing invariant of block-stm validation; without it, the "finalized prefix" abstraction breaks. Reapplies at: W94 v1.5 SHIP determinism gate, W91 ledger op_num ordering, W74 matching-engine sequence number.

    - **When `proptest_parallel_byte_identical_to_sequential` fails on a 50%-conflict block:**
      - Symptom: at conflict rate 50%, parallel post-state differs from sequential in 1 slot. Counterexample minimizes to ~10 txs.
      - Why: likely cascade-invalidation gap — when tx N invalidates, dependents M > N were not all re-validated. Or commit-order bug at finalize.
      - Fix: build reverse index per `(key, version) → set of tx_idxs that read it`. On tx N invalidation, walk reverse index for each of N's writes; re-validate every dependent. Alternatively (simpler but less efficient): re-validate ALL txs > N. The simpler fix is correct but pessimistic; the smart fix is what makes the speedup gate.
      - Muscle: cascade-invalidation completeness is correctness-critical; "optimization for the common case" (only invalidate close-by txs) breaks under high-conflict. Reapplies at: W94 SHIP determinism gate, W92 versioned-memory.

    - **When `test_1000_tx_block_10pct_conflict_under_30pct_sequential` reports wall time 60% of sequential:**
      - Symptom: 4-worker parallel takes 60% of sequential time = 1.67× speedup (target ≥ 3.3×, since 30% sequential means ~3.3× speedup).
      - Why: combination of (a) worker stall on DependsOn, (b) cascade re-exec overhead from naive invalidation, (c) hot-key DashMap contention (W91 Fri perf #2).
      - Fix: apply each fix from W91/W92 perf cards. Workers switch to Validate on DependsOn (R7). Smart cascade via reverse index. Hot-key bypass for top 1% slots. Re-bench; expect speedup ~2-3× depending on conflict mix.
      - Muscle: parallel-exec speedup is the product of many small fixes; no single perf lever delivers; the whole stack must compose. Reapplies at: every parallel/multi-threaded perf workload.

    - **When `test_worker_no_spin_on_dependson` shows 80% CPU spinning:**
      - Symptom: 4 workers all returning DependsOn(tx 5) repeatedly; CPU at 80% spinning; tx 5 is taking a long time.
      - Why: worker loop's NoTask branch just spins; on DependsOn, worker re-fetches same task immediately.
      - Fix: on DependsOn(M), worker increments a `waiting_on[M]` counter and parks on condvar. When tx M finishes, scheduler signals condvar; all workers waiting on M wake. Add backoff: short spin (10 iters), then park.
      - Muscle: spin-wait is acceptable for short dependencies; for hot-key dependencies, park-and-signal. Reapplies at: W22 concurrent primitives, W11 MPMC.

    - **When `test_commit_order_preserved` shows wrong final value:**
      - Symptom: block has 100 txs all writing slot K with values 0..99; final canonical state has K=42 (or some random value), not K=99.
      - Why: writes flushed to canonical during execute, not finalize; parallel execution order ≠ block order, so wrong tx's write "wins".
      - Fix: writes go to versioned_memory during execute (multi-version, indexed by tx_idx). Finalize phase walks tx 0..N in order; for each, applies its highest-incarnation Committed writes to canonical state. Canonical state never sees parallel writes.
      - Muscle: parallel-exec must preserve commit ordering; the canonical apply happens AFTER all execution+validation. Reapplies at: every MVCC-style system (W92 versioned-memory, W94 v1.5 SHIP, W82 matching-engine commit order).

    - **5-year failure mode** (write in `notes/93mon_executor_followup.md` after green): when blocks routinely exceed 5000 txs (high-throughput L2), scheduler atomic CAS contention becomes the bottleneck. Migration: per-worker partial schedulers (worker N owns tx_idx % NUM_WORKERS); coordination only at validation_idx boundary. Trigger: scheduler CAS contention > 20% CPU in flame graph.
