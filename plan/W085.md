  - **Why**: This crate is the L4 ingestion-path primitive — the equivalent of Solarflare/Onload's userspace stack in OSS form. Three transports are scaffolded now (epoll = portable baseline, io_uring = batching syscalls, AF_XDP = zero-copy XDP) so that W86-W90 can fill them in incrementally with apples-to-apples benchmarks. Without all three transports baselined together, ranking results in W89 Friday's bench is impossible.
  - *Back-of-envelope* (the budget the scaffold must already respect at v0.1 — the bar-(c) v0.5 ship targets P99 ≤ 2 µs end-to-end):
    100M pps single-NIC saturation ⇒ **10 ns/packet inter-arrival**. A `recv(2)` syscall costs ~300 ns each → 30× over budget if called per-packet. Therefore **batched receive (`recv_batch`) is the only viable trait shape** — amortize ≥256 packets per syscall to get back to ~1.2 ns/packet syscall cost. AF_XDP RX descriptor read ≈ **250 ns/packet** (DMA-direct, no kernel stack); io_uring SQE submit ≈ **80 ns/op amortized** at SQ depth 256; epoll `recvmmsg` ≈ **600-800 ns/packet** at batch 32. The trait MUST allow zero-copy frames (lifetime-bound `Frame<'a>`) — a `Vec<u8>` per frame at 100M pps = 100M mallocs/sec = 5 seconds of pure malloc per second.
  - **Read first**: Linux `Documentation/networking/af_xdp.rst`, `man epoll(7)`, io_uring `Documentation/man/io_uring.7`; `tokio-uring/src/runtime/driver.rs` for transport-abstraction reference; OpenOnload's `cplane_api.h` for HFT context.
  - **Design**:
    ```rust
    pub trait Transport: Send {
        type Frame<'a>: AsRef<[u8]> where Self: 'a;
        fn recv_batch<'a>(&'a mut self, out: &mut ArrayVec<Self::Frame<'a>, N>) -> usize;
    }
    pub struct EpollTransport { fd: RawFd, ring: ArrayVec<u8, MTU>, /*...*/ }
    pub struct IoUringTransport { ring: IoUring, /*...*/ }
    pub struct AfXdpTransport { umem: Umem, rx_ring: RxRing, /*...*/ }
    pub trait FeedParser: Send {
        type Event;
        fn parse(&mut self, bytes: &[u8]) -> Result<Self::Event, ParseErr>;
    }
    pub struct FeedHandler<T: Transport, P: FeedParser, S: Sink> { /*...*/ }
    ```
    **Invariants**: (i) all three transports satisfy the same `Transport` trait so benchmarks are apples-to-apples, (ii) feature flags (`epoll` default, `io-uring`, `af-xdp`) gate kernel-version-dependent code, (iii) no transport allocs on hot path; UMEM/io_uring buffers are pre-registered at startup.

  - **Pitfalls**: *Feature combinatorial explosion*: **Symptom**: `--all-features` fails on macOS (no AF_XDP). **Fix**: AF_XDP/io_uring features gated `#[cfg(all(target_os = "linux", target_arch = "x86_64"))]`. *Trait `Send` boundary*: **Symptom**: `RxRing` is `!Send`, breaks Transport. **Fix**: explicit `+ Send` only where needed; per-thread transport instances. *Buffer ownership confusion*: **Symptom**: AF_XDP UMEM frames must be returned to kernel; user holds them too long. **Fix**: lifetime-bound `Frame<'a>` borrows from transport, transport reclaims on next `recv_batch`. *Hidden Linux deps in cross-build*: **Symptom**: `cargo build --target aarch64-apple-darwin` fails. **Fix**: `#[cfg(target_os = "linux")]` around the io_uring/af-xdp modules at the crate root.
  - **Expect to hit (perf) #1 — `recv(2)`-per-packet trait shape (bar (c) violation)**: a naive `Transport::recv(&mut self) -> Frame` API forces one syscall per packet. At 100M pps, that's 100M × ~300 ns = **30 seconds of syscall time per wall-clock second** — physically impossible. The bug surfaces as throughput plateauing at ~3M pps regardless of which transport; flamegraph shows `__GI___libc_recv` consuming 95% of CPU.
    - Fix: design the trait around `recv_batch<'a>(&'a mut self, out: &mut ArrayVec<Frame<'a>, N>) -> usize` with N≥256. All three transports (epoll via `recvmmsg`, io_uring via multi-shot recv, AF_XDP via RX-ring drain) naturally batch. Single-frame `recv` is **not** part of the public API — it's a footgun.
    - Cost avoided: ~300 ns syscall × 256 = 76 µs amortized over 256 packets ≈ **0.3 µs syscall cost per packet**, vs 300 ns per single recv — a 100× syscall-amortization win at the trait level before any transport-specific optimization.
    - Muscle: in any kernel-bypass / batched-I/O API, batch belongs in the trait, not in an "optimization pass later." Adding batching after the fact requires changing every callsite. Reapplies at: W86 io_uring multi-shot recv, W89 AF_XDP RX-ring drain, W90 io_uring journal group-commit (ledger v1.0), W77 messaging-aeron term-buffer scan.
  - **Expect to hit (perf) #2 — `Vec<u8>` Frame allocates per-packet (bar (c) violation)**: a `type Frame = Vec<u8>` (or any owned-bytes shape) forces a heap allocation per received packet. At 50M pps that's 50M × ~50 ns malloc = **2.5 seconds of malloc per wall-clock second** + allocator lock contention with the rest of the process; visible as `jemalloc::malloc` dominating the flamegraph.
    - Fix: `type Frame<'a>: AsRef<[u8]> where Self: 'a` as a GAT. Frame borrows from the transport's pre-registered buffer (UMEM for AF_XDP, registered buffer ring for io_uring, `recv_buf` field for epoll); zero allocation per packet. Caller must consume Frames before the next `recv_batch` call — encoded in the lifetime.
    - Cost avoided: ~50 ns malloc + 1 cache line of allocator metadata per packet. At 50M pps = 2.5 sec/sec recovered, plus removed allocator-lock contention with the rest of the process (matching-engine, ledger).
    - Muscle: in any zero-copy data-plane API, the buffer is owned by the producer (transport), borrowed by the consumer. `Vec<u8>` in a hot-path API surface is **always** a bar-(c) violation. Reapplies at: W86 io_uring `ProvidedBuf<'a>`, W89 `UmemFrame<'a>`, W87 `FeedParser::Event<'a>` GAT, W77 messaging-aeron `Fragment<'a>`, W92 ledger Archive event borrows.
  - **Test scenarios**: compile matrix: default, +io-uring, +af-xdp, all-features (linux only); on macOS only default features compile. Stub trait impls return empty batches successfully.
  - **Acceptance**: `cargo check --all-features` on Linux passes; `cargo check` on macOS passes; module skeleton committed.

- [ ] **Build**: `crates/marketdata-kernelbypass/src/epoll.rs` — epoll-based receiver. Baseline for io_uring/AF_XDP
  comparisons. (~150 min)
  - **Why**: epoll is the lowest-common-denominator baseline. Production HFT shops don't use it for ingress — but having a working epoll Transport is essential for (i) portability/dev-loop on macOS via kqueue shim, (ii) apples-to-apples comparison in W89 Fri's bench (epoll vs io_uring vs AF_XDP), and (iii) a known-good correctness oracle for the other two transports.
  - *Back-of-envelope* (epoll target: ≥10M pps single-core, multi-receiver via SO_REUSEPORT ⇒ ~40M pps at 4 cores; baseline that AF_XDP must beat by 5-10× to justify the kernel-bypass complexity):
    Per-packet budget at 10M pps = **100 ns/packet**. `recv(2)` ≈ 300 ns → over budget by 3×. `recvmmsg(2)` at batch 32 ≈ 600-800 ns/batch ≈ **25 ns/packet** ✓ — batched syscall is the unlock. `epoll_wait` ≈ 1 µs amortized over the batch (edge-triggered, drain-fully). UDP socket copy from skb → userspace = 64 B header read at L1 ≈ 0.5 ns + 1500 B packet body read ≈ ~30 ns (cache-resident). Total: ~55 ns/packet — under budget if and only if (i) `recvmmsg` is used (not `recv`), (ii) edge-triggered drain prevents `epoll_wait` per packet, (iii) buffer is pre-allocated.
  - **Read first**: `man epoll(7)` (esp. EPOLLET edge-triggered semantics), tokio's `mio::Poll`, `man recvmmsg(2)` for batched recv.
  - **Design**:
    ```rust
    pub struct EpollTransport {
        epfd: RawFd,
        sockets: ArrayVec<RawFd, MAX_SOCKETS>,
        events: ArrayVec<epoll_event, MAX_EVENTS>,
        recv_buf: AlignedBox<[u8; MAX_FRAME * BATCH]>,
        msgvec: ArrayVec<mmsghdr, BATCH>,
    }
    impl Transport for EpollTransport {
        type Frame<'a> = &'a [u8];
        fn recv_batch<'a>(&'a mut self, out: &mut ArrayVec<&'a [u8], N>) -> usize { /*...*/ }
    }
    ```
    **Invariants**: (i) edge-triggered (EPOLLET) — drain socket fully on each notification; (ii) `recvmmsg` batches up to BATCH frames per syscall; (iii) buffers pre-allocated at construction, hot path alloc-free; (iv) frames borrow from receiver — lifetime tied to next `recv_batch` call.
  - **Build steps**: 1. (~10 min) `epoll_create1(EPOLL_CLOEXEC)` and socket setup helpers. 2. (~15 min) bind multicast socket via `setsockopt(IP_ADD_MEMBERSHIP)` + `SO_REUSEPORT` for multi-core scaling. 3. (~20 min) implement `recv_batch` calling `recvmmsg(epfd_sockets, msgvec, BATCH, MSG_DONTWAIT)`. 4. (~15 min) edge-trigger drain loop: `while recv_batch() == BATCH` keep going. 5. (~15 min) error handling: EAGAIN/EWOULDBLOCK = empty batch (normal), EINTR = retry, ECONNRESET = drop socket + log. 6. (~15 min) buffer recycle: caller's `out: &mut ArrayVec<&'a [u8], N>` cleared each call; frames re-overwritten next call. 7. (~20 min) criterion bench `bench_epoll`: send synthetic UDP at 1M, 5M pps from another process/thread; measure recv pps + p99 batch size. 8. (~15 min) integration with `feed_handler.rs` (later W87): epoll yields raw bytes, parser consumes. 9. (~15 min) docs/comments + clippy clean. 10. (~10 min) packet-loss instrumentation: `IP_RECVERR` for ENOBUFS detection.
  - **Pitfalls**: *EPOLLET starvation*: **Symptom**: high-priority socket starves low-priority. **Fix**: round-robin across sockets in events vector each iteration. *recvmmsg buffer aliasing*: **Symptom**: emitted `Frame<'a>` slices share memory; user copies them and corrupts on next call. **Fix**: document lifetime tightly + return `enumerate()` index that ties to msgvec slot. *ENOBUFS drop without detection*: **Symptom**: kernel drops UDP under load, app unaware. **Fix**: `setsockopt(IP_RECVERR)` + read errqueue periodically; export drop counter. *Multicast join on multi-NIC*: **Symptom**: joining on wrong NIC, no packets. **Fix**: bind explicit `ifindex` via `IP_ADD_MEMBERSHIP` mreqn struct.
  - **Expect to hit (perf) #1 — level-triggered `EPOLLIN` causing one `epoll_wait` per packet (bar (c) violation)**: forgetting `EPOLLET` (edge-triggered) means every readable byte triggers another `epoll_wait` round-trip. At 10M pps each `epoll_wait` is ~1 µs → 10 sec/sec of pure `epoll_wait` overhead. Throughput collapses to ~500k pps; flamegraph shows `epoll_wait` at 80% CPU.
    - Fix: `epoll_ctl(EPOLL_CTL_ADD, fd, EPOLLIN | EPOLLET)`; on each notification, **drain the socket fully** in a tight `while recvmmsg(...) == BATCH` loop until `EAGAIN`. One `epoll_wait` amortizes over thousands of packets in a burst.
    - Cost avoided: ~1 µs `epoll_wait` per drain instead of per packet. At 10M pps with ~256-packet bursts ≈ 40k `epoll_wait`/sec = 40 ms/sec; vs 10M/sec = 10 sec/sec — a **250× win**.
    - Muscle: edge-triggered + drain-fully is the only correct pattern at ingress scale. Reapplies at: W86 io_uring multi-shot recv (same drain-on-CQE_F_MORE pattern), W89 AF_XDP RX-ring (drain until consumer index == producer index), W77 messaging-aeron poll-fragment-handler loop.
  - **Expect to hit (perf) #2 — `recv_buf` allocated per `recv_batch` call (bar (c) violation)**: each `recv_batch` invocation `let mut buf = vec![0u8; MAX_FRAME * BATCH]` allocates 64 KB on the hot path. At 100k batches/sec = **100k × 50 ns malloc + 64 KB zero-fill (~10 µs each) = ~1 sec/sec just zeroing the buffer**. Throughput plateaus; profile shows `memset` in the top 3.
    - Fix: `recv_buf: AlignedBox<[u8; MAX_FRAME * BATCH]>` as a field on `EpollTransport`, allocated **once** in `new()`. Each `recv_batch` reuses it; old contents are overwritten by the kernel via `recvmmsg`'s `msgvec[i].msg_iov` pointing into the same buffer. Document the `Frame<'a>` lifetime: valid only until the next `recv_batch` call.
    - Cost avoided: 64 KB zero-fill + 50 ns malloc per batch. At 100k batches/sec ≈ ~1 sec/sec reclaimed; plus the cache-warmth win from reusing the same physical pages every call (TLB-resident, L2-resident).
