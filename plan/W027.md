**Thursday — Page provider over mmap + `bufpool` integration**

- [ ] Implement MmapPageProvider returning eth_storage_cache::Page views. (~120 min)
  - **Why**: Mmap converts page-table lookups into VFS reads on first touch, then RAM lookups thereafter. This is the *only* way to get sub-microsecond cold-page reads on a 100 GB database. But mmap is treacherous (SIGBUS on truncation, page-fault tail latency, dirty-page write-back stalls). MmapPageProvider isolates these hazards behind a Page abstraction so callers never touch raw mmap.
  - **Read first**: reth `crates/storage/libmdbx-rs/src/transaction.rs` for cursor-over-mmap. Linux `man 2 mmap`, `man 2 madvise`, `man 2 mlock`. Compare with sled's `IoBuf` (write-through) for an explicit non-mmap design. CMU 15-445 lecture on "buffer pool vs mmap" (Andy Pavlo's argument against mmap is critical reading).
  - **Design**:
    ```rust
    pub struct MmapPageProvider {
        file: File,
        mmap: MmapMut,              // PROT_READ | PROT_WRITE, MAP_SHARED, MAP_POPULATE optional
        page_size: usize,           // 4 KiB default
        page_count: AtomicU64,      // grows via remap
        page_locks: Vec<RwLock<()>>,// per-page lock array sized to current page_count
    }
    impl PageProvider for MmapPageProvider {
        type PageRef<'a> = MmapPageRef<'a>;
        fn fetch(&self, pid: PageId) -> Result<Self::PageRef<'_>, FetchError> {
            // 1. Acquire shared lock on page_locks[pid].
            // 2. Compute offset = pid * page_size.
            // 3. Return slice into mmap.
        }
        fn modify<F>(&self, pid: PageId, f: F) -> Result<(), ModifyError>
            where F: FnOnce(&mut Page) -> Result<(), ModifyError>;
    }
    pub struct MmapPageRef<'a> { slice: &'a [u8], _guard: RwLockReadGuard<'a, ()> }
    ```
    **Invariants**:
    - Mmap region size is always a multiple of system page size (typically 4 KiB).
    - Page boundaries align with system page boundaries (otherwise faults split records).
    - A page is either being read (shared lock held) OR written (exclusive lock held), never both.
    - MAP_POPULATE pre-faults all pages at mmap time — trades startup latency for steady-state predictability.
    - Growth: `mremap` doubles the file size; existing mappings remain valid (Linux preserves vma).
  - **Build steps**:
    1. (~20 min) `MmapPageProvider::open(path, initial_size)` — open file, fallocate, mmap with PROT_R/W and MAP_SHARED.
    2. (~15 min) `madvise(MADV_RANDOM)` or `MADV_SEQUENTIAL` hint based on workload (default RANDOM for DB).
    3. (~20 min) `fetch(pid)` returning a read-locked Page view; bounds-check pid against page_count.
    4. (~20 min) `modify(pid, F)` with exclusive lock; dirty-tracking via a `BitVec<AtomicU64>` (one bit per page).
    5. (~20 min) `grow(new_page_count)` — fallocate the file, `mremap` if Linux, fallback to munmap+mmap on macOS.
    6. (~15 min) `flush(dirty_only)` — `msync(MS_ASYNC)` for fast path, `msync(MS_SYNC)` for durable commit.
    7. (~10 min) Tests: 10k pages, random read/write pattern, verify content after reopen.
  - **Pitfalls**:
    - *SIGBUS on file truncation*: another process truncates the file out from under you → SIGBUS on access. **Symptom**: process crash mid-operation. **Fix**: `flock(LOCK_EX)` exclusive file lock; document single-process assumption.
    - *Mmap vs write() coherence*: writing via fd then reading via mmap (or vice versa) can see stale data on some kernels. **Symptom**: missing data on reopen. **Fix**: pick one access path. For wal+mmap, the wal owns the fd; mmap is read-only mirror, OR mmap owns the fd, wal updates via mmap.
    - *Page-fault tail latency*: cold pages on disk take 100 µs - 10 ms to fault in. **Symptom**: p99.9 latency spike under random workloads. **Fix**: `madvise(MADV_WILLNEED)` for upcoming pages; MAP_POPULATE if you can absorb startup time; consider userspace cache (bufpool) layered above mmap.
    - *Dirty-page write-back storm*: kernel decides to flush 100 MiB of dirty pages → blocks all I/O on the device. **Symptom**: 500 ms latency spike every ~30s. **Fix**: tune `dirty_ratio` and `dirty_background_ratio`; explicit `msync` at known points to amortize.
    - *NUMA effects*: mmap may allocate physical pages on a remote NUMA node. **Symptom**: 30% throughput loss on cross-socket access. **Fix**: `mbind(MPOL_BIND, ...)` to local node OR `madvise(MADV_HUGEPAGE)` to consolidate into THP.
    - *Lock array sizing on growth*: `page_locks` must grow with page_count. **Symptom**: panic on accessing locks[pid] for newly-grown range. **Fix**: lock array stored as `RwLock<Vec<RwLock<()>>>` with grow-in-place; OR use a sharded approach (256 locks, stripe by pid % 256).
  - **Test scenarios**:
    - Random workload: 1M fetches across 100k pages, all return correct content.
    - Crash injection: SIGKILL during a write; reopen, verify page either has old value OR new value (no torn write).
    - Grow under contention: 8 threads writing while a 9th grows the file; no panics, growth visible after fence.
    - macOS path: same tests on macOS (uses munmap+mmap fallback).
    - madvise hint comparison: SEQUENTIAL vs RANDOM throughput on sequential scan workload.
  - **Acceptance**:
    - Throughput: ≥ 5 GB/s sequential read on NVMe.
    - p99 latency on warm pages ≤ 1 µs.
    - Crash-test passes 100 random fault injections.
  - **Downstream**: W28 B-tree core sits atop this; W31 persistent MPT uses it; W95 mini-db reproduces this layer.
- [ ] Wire `bufpool::BufferPool<MmapPageProvider>` as the L1 cache in front of MDBX. Pinned pages survive eviction;
  dirty pages are written back to mmap on flush. (~45 min)
  - **Why**: mmap leaves caching to the kernel, which is a black box you can't tune. BufferPool gives you userspace control: pin hot pages (the trie's top 3 levels), evict cold ones (deep trie tails). Andy Pavlo's "Are You Sure You Want to Use MMAP" makes this argument for OLTP databases; you're applying it to a derived (state-root) workload that has even more predictable hotness.
  - **Read first**: bufpool's own docs from W14 weeks; CMU 15-445 lecture on buffer pool replacement (LRU-K, Clock, 2Q); reth's `crates/storage/db/src/transaction.rs` for tx-level page pinning.
  - **Design**:
    ```rust
    pub struct BufferPool<P: PageProvider> {
        provider: Arc<P>,
        frames: Vec<Frame>,                 // fixed-size slab
        page_table: DashMap<PageId, FrameIdx>,
        replacer: ClockReplacer,            // O(1) eviction approximation
        config: BufferPoolConfig,
    }
    pub struct Frame {
        page_id: AtomicU64,                 // !0 = empty
        pin_count: AtomicU32,
        dirty: AtomicBool,
        data: UnsafeCell<[u8; PAGE_SIZE]>,
        latch: RwLock<()>,
    }
    impl<P> BufferPool<P> {
        pub fn fetch_shared(&self, pid: PageId) -> Result<PageGuard<'_>, Error>;
        pub fn fetch_exclusive(&self, pid: PageId) -> Result<PageGuardMut<'_>, Error>;
        pub fn pin(&self, pid: PageId);     // force-keep regardless of replacement policy
        pub fn unpin(&self, pid: PageId);
        pub fn flush_all_dirty(&self) -> Result<(), Error>;
    }
    ```
    **Invariants**:
    - A frame's `pin_count > 0` → cannot be evicted.
    - `dirty == true` → must `provider.modify(...)` before reuse.
    - Page table is the single source of truth for "is this page in cache" — readers consult it under DashMap shard lock.
    - On eviction, dirty pages are flushed via `provider.modify`; clean pages dropped.
  - **Build steps**:
    1. (~10 min) `Frame` slab pre-allocated (`Vec::with_capacity(N)`); never resized after init.
    2. (~10 min) Page table = `DashMap<PageId, FrameIdx>` — sharded for concurrent lookups.
    3. (~10 min) ClockReplacer: circular list of frames, "second chance" bit, O(1) amortized eviction.
    4. (~5 min) `fetch_shared` / `fetch_exclusive` returning RAII guards that auto-unpin on drop.
    5. (~5 min) `flush_all_dirty` for checkpoint integration.
    6. (~5 min) Tests: pin/unpin, eviction under contention, dirty flush.
  - **Pitfalls**:
    - *Pin-leak*: forgotten unpin → frame can never be evicted. **Symptom**: cache fills, every fetch falls through to provider. **Fix**: RAII guards with `Drop` impl; lint for manual unpin.
    - *Eviction during fetch*: concurrent thread evicts the frame you're about to read from. **Symptom**: race condition, panic on Drop of empty frame. **Fix**: `fetch` increments pin_count BEFORE reading the frame; CAS-loop until success.
    - *Dirty page write-back stall*: a single eviction triggers a 1 ms msync. **Symptom**: every cache miss is slow. **Fix**: background writer drains dirty pages asynchronously; eviction policy prefers clean frames.
    - *Phantom dirty bit*: page modified then frame evicted then re-fetched; the new fetch's dirty bit starts false even though disk page is "real" dirty (not yet flushed). **Symptom**: msync at checkpoint misses pages. **Fix**: dirty bit lives on the *PAGE TABLE entry*, not the frame; transfers across eviction.
  - **Test scenarios**:
    - 1M fetch/release cycle on 1k pages; cache hit rate > 99% with N=2k frames.
    - Adversarial: pin all frames → next fetch returns `Error::NoEvictionTarget`.
    - Dirty-pin pattern: 100 pages dirtied + pinned; flush_all_dirty completes without touching the others.
  - **Acceptance**:
    - Hit latency ≤ 100 ns; miss latency ≤ 10 µs warm-disk.
    - Inheritance ratio ≥ 0.8 vs bufpool reference shape.
  - **Downstream**: W28 B-tree uses BufferPool to access pages; W31 storage-trie MPT navigates via BufferPool; W42 ExecutionStage reads state through it.

**Friday — mmap wrapper + `wal` write path**

- [ ] mmap-backed file wrapper with safe remap on growth. (~30 min)
- [ ] **Build**: storage-trie's write transaction now appends to `wal::Wal` BEFORE updating mmap pages. WAL-first means
  crash recovery is well-defined. (~105 min)
  - **Why**: "Write-Ahead Logging" is the foundational rule of crash-safe storage: a change is durably recorded in the log *before* the in-place mutation. Violating this turns crashes into corruption. The protocol: (1) append log record, (2) await durability LSN, (3) mark page dirty, (4) periodic checkpoint persists pages. On crash, replay the log forward from last checkpoint LSN.
  - **Read first**: ARIES paper §1-3 (the WAL protocol); PostgreSQL's WAL semantics (`src/backend/access/transam/xlog.c` for the protocol; `src/backend/access/heap/heapam.c` for the WAL-then-modify pattern); your own wal facade from W26.
  - **Design**:
    ```rust
    pub struct WriteTransaction<'a> {
        wal: &'a Wal,
        pool: &'a BufferPool<MmapPageProvider>,
        tx_id: TxId,
        my_first_lsn: Option<Lsn>,
        my_last_lsn: Option<Lsn>,
        dirty_pages: HashMap<PageId, Lsn>,    // pageLSN tracking
        state: TxState,                       // Active | Preparing | Committed | Aborted
    }
    impl<'a> WriteTransaction<'a> {
        pub async fn insert(&mut self, table: TableId, key: &[u8], val: &[u8]) -> Result<(), Error> {
            // 1. Acquire exclusive page latch via pool.
            // 2. Build a WalRecord { kind: Insert, tx_id, prev_lsn: self.my_last_lsn, payload: (table, key, val) }.
            // 3. wal.append(...).await → returns Lsn L.
            // 4. Mutate the page; set page.pageLSN = L.
            // 5. self.my_last_lsn = Some(L).
        }
        pub async fn commit(self) -> Result<(), Error> {
            let l = self.wal.append(RecordKind::Commit, ...).await?;
            // Pages may still be dirty in memory — that's fine; durability is in wal.
        }
    }
    ```
    **Invariants** (THE WAL RULE):
    - For every page modification at LSN L: `wal contains record with lsn L AND that record is durable BEFORE the page write is visible to other readers`.
    - `page.pageLSN >= max(lsn of all changes applied to page)`.
    - Commit record's LSN > all data record LSNs of that tx.
    - On recovery: redo every record with `record.lsn > page.pageLSN` to that page.
  - **Build steps**:
    1. (~15 min) `WriteTransaction` struct + `TxId` allocator (atomic counter).
    2. (~25 min) `insert` body following the 5-step protocol; assert wal.append happens BEFORE page mutation.
    3. (~15 min) `update` and `delete` analogous; both record old value in payload for undo.
    4. (~15 min) `commit` writes Commit record; abort writes Abort record.
    5. (~10 min) Page-LSN bookkeeping: every modified page header carries `pageLSN: u64`.
    6. (~15 min) Crash-injection test: kill mid-tx → on reopen, see no partial effects.
    7. (~10 min) Concurrency test: 16 txs interleaving; all serializable.
  - **Pitfalls**:
    - *Wal append AFTER page write*: classic. Crash between page-write and wal-append loses durability. **Symptom**: replay can't recover the change because it's not in wal. **Fix**: code review every write site; centralize via the WriteTransaction methods only.
    - *Forgetting pageLSN update*: page mutated but pageLSN stale. **Symptom**: replay re-applies, doubling effects. **Fix**: mutate pageLSN in the SAME exclusive-latched region; never expose page.modify_data without modify_lsn.
    - *Concurrent commits with shared dirty pages*: two txs modify page P, both commit; which wal record's LSN belongs to P's pageLSN? **Symptom**: pageLSN inconsistent across re-runs. **Fix**: pageLSN is `max(both LSNs)`; under exclusive latch, last writer wins.
    - *Async-await across page latches*: holding an exclusive latch across `wal.append.await` blocks every concurrent tx on that page. **Symptom**: throughput collapses to single-writer. **Fix**: short critical section — append wal, get LSN, THEN take latch and apply.
    - *Buffer pool flush before commit*: pool eviction policy must respect pageLSN ≥ durable_lsn. **Symptom**: page evicted (flushed to mmap) with changes from an uncommitted tx → crash recovers half a tx. **Fix**: BufferPool's eviction queries wal's durable_lsn; only flushes pages where `pageLSN <= durable_lsn`.
  - **Test scenarios**:
    - Single tx, 100 inserts, commit: replay finds all 100.
    - Tx aborted mid-flight: replay sees Begin..Abort, undoes (W29 wires undo).
    - Crash between page-write and wal-append: should be IMPOSSIBLE by construction.
    - Crash after wal-append, before page-write: replay redoes the change.
    - Crash after Commit record: replay redoes; tx visible.
    - 8 concurrent txs interleaved: every tx is either fully visible or fully gone after replay (atomicity).
  - **Acceptance**:
    - 1000 random crash-injection runs → recovery never produces partial txs.
    - Inheritance ratio ≥ 0.8 vs PostgreSQL XLog pattern.
  - **Downstream**: W29 recovery analysis pass walks pageLSN; W30 undo pass consumes the prev_lsn chain; W64 raft replicates this wal across nodes; W74 matching-engine reuses for order-book persistence.

- [ ] **Test phá**: `crates/wal/tests/silent_corruption.rs` — adversarial harness simulating 3 real-world storage fault classes documented by TigerBeetle: (a) single-bit flip in a wal record's data, (b) whole-sector corruption (zero-fill or random-fill), (c) misdirected write (data for LSN N lands in sector for LSN M). Verify wal's checksum + hash-chain catches all three; document any class your wal silently corrupts. (~180 min)
  - 🔧 **Decomposition prompt**: W26 shipped wal v0.1 with record-level checksums. The threat model that justified those checksums lives in TigerBeetle's safety doc — they cite specific industry numbers (0.031% SSD/yr silent corruption, 1.4% enterprise HDD/yr) and the design's response (immutable hash-chained records that detect AND localize corruption). The checksums you wrote ought to defend against all three fault classes; today's test PROVES it by injecting each fault into a fresh wal file and asserting recovery detects it. Without this test, the checksums are aspirational. The test will be reused at W30 (recovery 3-pass ARIES — must also detect), W31 (mmap-queue same fault model), W92 (ledger v1.0 — Protocol Aware Recovery requires it).
  - 🎯 **Hardened acceptance**:
    - **3 fault injectors**, each parameterizable: `flip_random_bit(file, count)` (1-3 bits), `zero_sector(file, sector_idx)` (4KB or filesystem block), `misdirect_write(file, src_lsn, dst_lsn)` (swap two sectors). All work on a wal directory after `wal.append + sync` and before `wal.replay`.
    - **3 detection tests**, one per fault: write 1000 records, sync, inject fault at random offset (use a seeded PRNG so test is reproducible), call `Wal::replay`. Assertion: replay either (a) returns a CorruptionDetected error pointing to the corrupt LSN, OR (b) recovers cleanly using a redundant copy (if you have one — wal v0.1 likely does not). Silent acceptance of corrupted data = test fails.
    - **Hash-chain extension** (if missing from v0.1): if your wal records don't already chain (each record header includes prev record's checksum), add it now. Without the chain, misdirected-write between sectors with valid individual checksums is silently accepted. Tigerbeetle hash-chains for exactly this reason.
    - **Architecture-uniform**: tests pass on both `x86_64-unknown-linux-gnu` and `aarch64-apple-darwin`. The corruption model is HW-independent.
    - **Cited industry numbers** in test doc-comments: "TigerBeetle docs report 0.031% SSD/yr silently return corrupt data and 0.023% SSD/yr misdirect I/O — these tests model exactly those failure rates as if compressed into a single test run."
    - **5-year failure mode**: when NVMe drives uniformly support PI (Protection Information) / T10-DIF, the bit-flip class becomes drive-detected before the OS sees the read; the misdirected-write class still needs application checksumming + hash-chain because PI doesn't cover LBA. State the migration: PI-aware wal opens with `O_PI` flag (Linux 6.x+) and trusts drive-level bit-flip detection while keeping hash-chain for misdirection.
  - *Mental model*: storage faults are NOT just "the disk is dead." Silent corruption + misdirected I/O happen at measurable rates on healthy drives — TigerBeetle's documented stats turn an "edge case" worry into a design requirement. A wal that doesn't detect these silently accepts garbage; the hash chain is what makes the detection *complete* (single checksum on each record is insufficient: a misdirected write of two valid records swaps them with intact-per-record checksums, undetectable without chaining).
  - *Source*: https://docs.tigerbeetle.com/concepts/safety/ (storage fault rates: 0.031% SSD/yr, 0.023% misdirected, 1.4% enterprise HDD); TigerBeetle's Protocol Aware Recovery design (https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vsr.md mentions WAL corruption tolerance).
  - **Expect to hit #1 — single-record checksum without hash chain misses misdirected write**: the test injector swaps sectors holding LSN-50 and LSN-100. Each record's checksum validates against its own bytes (the swap preserved each record intact); wal replay accepts both → records are returned out of order under the wrong LSNs. Symptom: test (c) fails — replay doesn't detect the misdirection.
    - Fix: each record's header includes `prev_checksum` (the previous record's checksum). On replay, after validating the current record, also validate `prev_checksum` matches the previous record's actual checksum. A misdirected write breaks the chain — detected within one record of the swap.
    - Cost avoided: silent acceptance of misdirected writes; an entire class of corruption the per-record checksum cannot catch.
    - Muscle: per-record checksums catch corruption WITHIN a record but not BETWEEN records. Hash-chaining catches misdirection. Both are needed. Reapplies at: W30 recovery ARIES log (chain commits), W31 mmap-queue records, W83 ledger v0.5 journal, W92 ledger v1.0 (Protocol Aware Recovery — required).
  - **Expect to hit #2 — fault injector misses the offset of the actual record bytes**: a `flip_random_bit` that flips at offset `random() % file_size` may hit segment metadata (header, EOF marker, padding) instead of record payload. Symptom: test passes for the wrong reason — corruption was in metadata, wal aborted before reaching record validation; or test is flaky depending on PRNG.
    - Fix: every injector takes a `record_range: Range<u64>` argument computed from wal's known record-payload byte offsets; the test asserts the injector lands inside the range. Add a sanity assertion: after injection, the file's metadata-section bytes are still intact.
    - Muscle: a fault injector that doesn't know where to inject is a randomness test, not a fault-class test. Reapplies at: W30 recovery fault-injection harness, W31 mmap-queue corruption tests, W92 VOPR fault injection.
