**Thursday — Page provider over mmap + `bufpool` integration**

- [ ] **Build**: `crates/storage-trie/src/mmap_page_provider.rs` — `MmapPageProvider` returning eth_storage_cache::Page views. (~total 160 min across 3 phases)
  - 🔧 **Why this matters**: mmap converts page-table lookups into VFS reads on first touch, then RAM lookups
    thereafter. This is the only way to get sub-microsecond cold-page reads on a 100 GB database. But mmap
    is treacherous — SIGBUS on truncation, page-fault tail latency, dirty-page write-back stalls.
    `MmapPageProvider` isolates these hazards behind a Page abstraction so callers never touch raw mmap.
    Downstream: W28 B-tree core sits atop this; W31 persistent MPT uses it; W95 mini-db reproduces.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: a 100 GB database can't live in RAM; reading via `read(2)`
    burns 1+ syscall per page (40+ ns just for the trap). Mmap turns page reads into ordinary memory
    accesses (warm: ~5 ns; cold: ~100 µs for a faulted-in page). The cost is treachery — SIGBUS on
    truncation, unpredictable tail latency on cold pages, write-back stalls. The provider isolates this.

  - **Requirements** — write in `crates/storage-trie/notes/27_mmap_page_provider_design.md`:
    - R1. `MmapPageProvider::open(path, initial_size)` opens or creates a backing file; mmap'd with
      `PROT_READ | PROT_WRITE | MAP_SHARED`.
    - R2. `fetch(pid) -> PageRef<'_>` returns a read-locked view; bounds-checked against `page_count`.
    - R3. `modify(pid, F)` takes exclusive lock; runs `F(&mut Page)`; tracks dirty bit in
      `BitVec<AtomicU64>` (one bit per page).
    - R4. `grow(new_page_count)` fallocates + remaps; Linux uses `mremap` (keeps mappings); macOS
      falls back to `munmap + mmap`.
    - R5. `flush(dirty_only)` calls `msync(MS_ASYNC)` for fast path; `flush_sync` uses `MS_SYNC`.
    - R6. Mmap region size always a multiple of system page size (4 KiB typical).
    - R7. SIGBUS protection: `flock(LOCK_EX)` exclusive file lock; document single-process assumption.
    - R8. Throughput: ≥5 GB/s sequential read on NVMe.
    - R9. p99 latency on warm pages ≤1 µs.
    - R10. Crash-test: 100 random SIGKILL injections; reopen finds each page in old OR new state, no
      torn writes.

  - **Design walk-through** — answer each:
    - D1. SIGBUS on truncation — what's the threat model, what's the defense?
    - D2. Page-fault tail latency: cold pages take 100 µs - 10 ms to fault in. Mitigation? (Hint:
      MAP_POPULATE, MADV_WILLNEED, userspace cache via bufpool.)
    - D3. Dirty-page write-back storms: kernel flushes 100 MiB at once → 500ms stall. Mitigation?
      (Hint: explicit msync at known points; tune `dirty_ratio`.)
    - D4. NUMA effects: 30% throughput loss on cross-socket. Mitigation? (Hint: mbind to local node.)
    - D5. Pre-mortem: scenario where `page_locks: Vec<RwLock<()>>` grow operation panics under
      concurrent fetch.

  - **Output**: `notes/27_mmap_page_provider_design.md` with R1–R10 + D1–D5 + grow protocol.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)

  - **When `grow_under_contention_no_panic` panics with index-out-of-bounds on `page_locks[pid]`:**
    - Symptom: a fetcher thread accesses `page_locks[pid]` where pid is in the newly-grown range;
      Vec doesn't have a slot for it yet.
    - Why: `page_locks` was a plain `Vec<RwLock<()>>`; grow re-allocates the Vec mid-fetch.
    - Fix: use a sharded approach — 256 fixed locks, stripe by `pid % 256`. Lock cost is the same;
      grow doesn't touch the lock array. OR: `RwLock<Vec<RwLock<()>>>` and grow under the outer lock.
    - Muscle: lock arrays that grow with the underlying data need either sharding (fixed-size) or
      lock-protected growth. Bare `Vec` of locks corrupts under concurrent grow. Reapplies at: W74
      matching-engine per-symbol locks, W30 mmap-queue per-cycle.

  - **When `concurrent_truncation_does_not_sigbus` reports SIGBUS:**
    - Symptom: a second process truncated the file; the first process's mmap region is now
      unbacked; access triggers SIGBUS.
    - Why: no flock; nothing prevents concurrent truncation.
    - Fix: `flock(LOCK_EX)` on open; second open returns EWOULDBLOCK. Document single-process
      assumption in the crate-level doc.
    - Muscle: mmap-based storage assumes exclusive process access; enforce via flock at open. Reapplies
      at: W26 wal segment, W30 mmap-queue cycle.

  - **When `bench_5gb_per_sec_sequential` reports 1.2 GB/s:**
    - Symptom: sequential scan is 4× slower than target; profiler shows time in page faults.
    - Why: pages are being faulted in on demand; cold-cache scan pays ~10ms latency per ~1024-page
      batch of faults.
    - Fix: `madvise(MADV_SEQUENTIAL)` hint AND `MAP_POPULATE` at open if startup latency is
      acceptable; otherwise issue `MADV_WILLNEED` for upcoming pages.
    - Cost avoided: 4× throughput cliff on cold-scan workloads.
    - Muscle: mmap's lazy faulting is the default; sequential workloads need explicit hints. Reapplies
      at: W31 persistent MPT scans, W95 mini-db SSTable reads.

  - **When `flush_msync_async_returns_fast` returns in 5 seconds:**
    - Symptom: flush takes 5s instead of <100µs.
    - Why: `MS_SYNC` was used instead of `MS_ASYNC`. MS_SYNC waits for the IO to complete.
    - Fix: `MS_ASYNC` for the fast path; expose `flush_sync()` for explicit commit barriers.
    - Muscle: msync flags are explicit; MS_SYNC blocks until durable, MS_ASYNC schedules and returns.
      Use the right one per use case. Reapplies at: W30 mmap-queue index.rs (best-effort), W26 segment.

- [ ] **Build**: wire `bufpool::BufferPool<MmapPageProvider>` as the L1 cache in front of MDBX. Pinned pages survive eviction;
  dirty pages are written back to mmap on flush. (~total 65 min across 3 phases)
  - 🔧 **Why this matters**: mmap leaves caching to the kernel, a black box you can't tune. `BufferPool` gives
    userspace control — pin hot pages (the trie's top 3 levels), evict cold ones (deep trie tails). Andy
    Pavlo's "Are You Sure You Want to Use MMAP" makes this argument for OLTP databases; the same applies to

  #### Phase 1 — Problem, requirements, design (~20 min, no code yet)

  - **The problem this primitive solves**: the kernel's page cache makes good general-purpose decisions
    but terrible workload-specific ones (it evicts hot trie roots under memory pressure; it doesn't know
    your access pattern). A userspace buffer pool pins the hot working set and evicts via a policy you
    control (Clock, LRU-K, 2Q).

  - **Requirements** — write in `crates/storage-trie/notes/27_bufpool_layer_design.md`:
    - R1. `BufferPool<P: PageProvider>` with frames slab, page table, replacer.
    - R2. `fetch_shared(pid) -> PageGuard` returns RAII shared guard; pin_count++ on guard creation.
    - R3. `fetch_exclusive(pid) -> PageGuardMut` similarly exclusive.
    - R4. `pin(pid)` / `unpin(pid)` for explicit pin control (e.g. trie roots).
    - R5. RAII Drop auto-unpins on guard drop; never leaks pins.
    - R6. Frame `pin_count > 0` → cannot be evicted.
    - R7. Dirty bit lives on the PAGE TABLE entry, not the frame — survives eviction.
    - R8. Hit latency ≤100 ns; miss latency ≤10 µs warm-disk.
    - R9. Frame slab pre-allocated; never resized after init (zero hot-path alloc).

  - **Design walk-through** — answer each:
    - D1. Why DashMap for the page table vs RwLock<HashMap>?
    - D2. ClockReplacer vs LRU-K: tradeoffs.
    - D3. Pre-mortem: pin-leak from a panic-with-guard scenario.

  - **Output**: `notes/27_bufpool_layer_design.md` with R1–R9 + D1–D3.

  - **When `dirty_bit_survives_eviction` reports the bit cleared after eviction:**
    - Symptom: re-fetched page has `dirty == false` even though the original mutation was never flushed.
      Checkpoint then misses the page → data loss on crash.

      for another page, the dirty bit was overwritten.

      is internal state to the BufferPool, but the page-table's view is the source of truth.
    - Muscle: per-frame state survives the frame's lifetime only; metadata that must outlive the frame
      goes on the page-table entry. Reapplies at: W28 B-tree free list, W31 persistent MPT version
      tracking.

  - **When `fetch_share_pin_unpin_via_drop` reports pin_count==2 after one drop:**
    - Symptom: pin_count doesn't decrement on guard drop.
    - Why: guard's `Drop` impl was never written — the guard was a plain struct.
    - Fix: implement `Drop` on `PageGuard` to decrement pin_count. The whole point of RAII is the
      Drop impl; without it, every API consumer must manually unpin.

**Friday — mmap wrapper + `wal` write path**

- [ ] mmap-backed file wrapper with safe remap on growth. (~30 min)
- [ ] **Build**: storage-trie's write transaction now appends to `wal::Wal` BEFORE updating mmap pages. WAL-first means
  crash recovery is well-defined. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: Write-Ahead Logging is the foundational rule of crash-safe storage — a change
    is durably recorded in the log BEFORE the in-place mutation. Violating this turns crashes into
    corruption. Protocol: (1) append log record, (2) await durability LSN, (3) mark page dirty, (4)
    periodic checkpoint persists pages. Downstream: W29 recovery analysis walks pageLSN; W30 undo consumes
    prev_lsn chain; W64 raft replicates wal; W74 matching-engine reuses for order-book persistence.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: in-place page mutation with no log = "the new state is on disk
    but the old state isn't" with no way to recover from crash mid-write. WAL flips the order: the
    record exists durably (in wal) BEFORE the mutation is visible. Recovery replays records whose lsn
    exceeds the page's pageLSN.

  - **Requirements** — write in `crates/storage-trie/notes/27_writetx_design.md`:
    - R1. `WriteTransaction { wal, pool, tx_id, my_first_lsn, my_last_lsn, dirty_pages: HashMap<PageId,
      Lsn>, state }`.
    - R2. `insert(table, key, val)`: append WAL record, await durable lsn L, apply page mutation, set
      `page.pageLSN = L`.
    - R3. **THE WAL RULE**: for every page modification at LSN L, wal contains record with lsn L AND
      that record is durable BEFORE the page write is visible to other readers.
    - R4. `page.pageLSN >= max(lsn of all changes applied to page)`.
    - R5. Commit record's LSN > all data record LSNs of that tx.
    - R6. On recovery, redo every record with `record.lsn > page.pageLSN` to that page.
    - R7. BufferPool's eviction respects pageLSN ≥ durable_lsn — only flush pages whose pageLSN is
      durable (otherwise crash recovers half a tx).
    - R8. 1000 random crash-injection runs → recovery never produces partial txs.

  - **Design walk-through** — answer each:
    - D1. Why does wal.append happen BEFORE page mutation, not after? (Hint: crash between page-write
      and wal-append loses durability.)
    - D2. Holding a page latch across `wal.append.await` blocks every concurrent tx. Solution? (Hint:
      short critical section — append wal, get LSN, THEN take latch and apply.)
    - D3. Two txs modify the same page; both commit; what's the page's pageLSN? (Hint: max of both
      LSNs; under exclusive latch, last writer wins.)
    - D4. Pre-mortem: a "forget to update pageLSN" bug; what's the corruption shape after recovery?

  - **Output**: `notes/27_writetx_design.md` with R1–R8 + D1–D4 + the 5-step protocol diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~75 min)

  - **When `crash_between_pagewrite_and_walappend_impossible` reports the bad order DID happen:**
    - Symptom: instrumentation logs a page mutation timestamp earlier than the wal.append timestamp
      for the same lsn.
    - Why: a code path bypassed the WriteTransaction abstraction and called `pool.modify` directly
      before issuing the wal append.
    - Fix: page mutation API is ONLY exposed via WriteTransaction methods; bare `pool.modify`
      access is private to the txn module. Visibility enforces the order.
    - Muscle: an invariant the type system can't express (ordering of two distinct ops) requires
      visibility-based capability hiding. Reapplies at: W29 recovery (only recover can call
      `pool.unsafe_apply`), W64 raft log apply.

  - **When `bufpool_eviction_respects_durable_lsn` reports a page evicted with pageLSN > durable_lsn:**
    - Symptom: a page with uncommitted (non-durable) changes was flushed to mmap. Crash recovers a
      half-tx.
    - Why: BufferPool's eviction policy didn't query wal's durable_lsn — it just picked the
      least-recently-used clean OR dirty page.
    - Fix: eviction policy: "if dirty AND pageLSN > durable_lsn, SKIP this frame (try another)".
      Track durable_lsn via an Arc<AtomicU64> shared with wal; pool reads it on each eviction.
    - Muscle: the "no-steal" rule (don't evict uncommitted pages) is foundational to WAL safety;
      buffer pool must consult the durability watermark before flushing. Reapplies at: W29 ARIES
      analysis (steal policy variants), W42 txn manager, W95 mini-db.

  - **When `pagelsn_max_under_concurrent_commits` reports pageLSN = first committer's LSN:**
    - Symptom: two txs commit; pageLSN is the LSN of the first to commit, but the second's mutations
      are visible (last writer wins). Mismatch.
    - Why: pageLSN was set INSIDE the page mutation but the page latch was released between txs;
      first tx set pageLSN=L1, second tx mutated again and set pageLSN=L2, but the order in time was
      reverse.
    - Fix: pageLSN update happens under the SAME exclusive latch as the page mutation; both
      operations atomic per critical section. After unlocking, pageLSN reflects the latest mutation.
    - Muscle: pageLSN and page-data updates are atomic per critical section; never let a writer
      release the latch between them. Reapplies at: W29 ARIES (page-LSN consistency), W42 txn
      apply.

  - **When `vopr_1000_crash_no_partial_tx` reports 12 of 1000 trials with partial tx:**
    - Symptom: 12 trials have a state where some keys from tx-X are visible but not others; tx-X is
      half-applied.
    - Why: crash occurred between two `pool.modify` calls within the same tx; wal had the records
      but the second page mutation hadn't happened yet. Replay should redo, but replay didn't see
      the first mutation as "not yet applied" because its pageLSN was already higher.
    - Fix: WAL-then-modify must be atomic per record (R3). If a tx is multi-record, recovery's redo
      pass walks each record independently; the WAL has both records; replay applies both. The bug
      was likely a race where `my_last_lsn` was updated before `page.pageLSN` was set.
    - Muscle: every (wal append, page apply) pair must be atomic w.r.t. observability; if a reader
      can see the wal record but not the page mutation, replay's invariants break. Reapplies at:
      W29 redo correctness, W64 raft entry apply.

  - **5-year failure mode** (write in `notes/27_writetx_followup.md` after green): when MVCC-style
    multi-version pages replace in-place mutation, WAL becomes the version log + redo is just
    "promote highest visible version". State the migration: a `WriteBackend` trait abstracts WAL+InPlace
    vs MVCC versions. Trigger: when read-write contention dominates throughput.

The checksums you wrote ought to defend against all three fault classes; today's test PROVES it by injecting each fault into a fresh wal file and asserting recovery detects it. Without this test, the checksums are aspirational. The test will be reused at W30 (recovery 3-pass ARIES — must also detect), W31 (mmap-queue same fault model), W92 (ledger v1.0 — Protocol Aware Recovery requires it).
  - 🎯 **Hardened acceptance**:
    - **3 fault injectors**, each parameterizable: `flip_random_bit(file, count)` (1-3 bits), `zero_sector(file, sector_idx)` (4KB or filesystem block), `misdirect_write(file, src_lsn, dst_lsn)` (swap two sectors). All work on a wal directory after `wal.append + sync` and before `wal.replay`.

Assertion: replay either (a) returns a CorruptionDetected error pointing to the corrupt LSN, OR (b) recovers cleanly using a redundant copy (if you have one — wal v0.1 likely does not). Silent acceptance of corrupted data = test fails.
    - **Hash-chain extension** (if missing from v0.1): if your wal records don't already chain (each record header includes prev record's checksum), add it now. Without the chain, misdirected-write between sectors with valid individual checksums is silently accepted. Tigerbeetle hash-chains for exactly this reason.
    - **Architecture-uniform**: tests pass on both `x86_64-unknown-linux-gnu` and `aarch64-apple-darwin`. The corruption model is HW-independent.
    - **Cited industry numbers** in test doc-comments: "TigerBeetle docs report 0.031% SSD/yr silently return corrupt data and 0.023% SSD/yr misdirect I/O — these tests model exactly those failure rates as if compressed into a single test run."

  - *Mental model*: storage faults are NOT just "the disk is dead." Silent corruption + misdirected I/O happen at measurable rates on healthy drives — TigerBeetle's documented stats turn an "edge case" worry into a design requirement. A wal that doesn't detect these silently accepts garbage; the hash chain is what makes the detection *complete* (single checksum on each record is insufficient: a misdirected write of two valid records swaps them with intact-per-record checksums, undetectable without chaining).
  - *Source*: https://docs.tigerbeetle.com/concepts/safety/ (storage fault rates: 0.031% SSD/yr, 0.023% misdirected, 1.4% enterprise HDD); TigerBeetle's Protocol Aware Recovery design (https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vsr.md mentions WAL corruption tolerance).

Symptom: test (c) fails — replay doesn't detect the misdirection.

    - Cost avoided: silent acceptance of misdirected writes; an entire class of corruption the per-record checksum cannot catch.
