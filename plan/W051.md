**Monday — Missing arithmetic: SDIV, SMOD, ADDMOD, MULMOD, EXP, SIGNEXTEND**

- [ ] **Build**: `crates/exec-vm/src/instructions/arithmetic.rs` (+ helpers `i256_div`/`i256_mod` in same file) — the six missing arithmetic opcodes, differential-tested against revm. (~total 240 min across 3 phases)
  - 🔧 **Why this matters**: mirrors `revm-interpreter/src/instructions/arithmetic.rs`. Signed-division and modular-exponentiation opcodes are where a large share of historical EVM consensus divergences live. Four traps you WILL hit: (1) `INT_MIN / -1` panics natively but the EVM contract is "no trap, return INT_MIN"; (2) `(a+b) % m` overflows U256 for ADDMOD; (3) EXP gas coefficient changed at EIP-160 (Spurious Dragon — NOT Tangerine) so a hard-coded 50, or a gate on the wrong fork, mis-charges every pre-Spurious-Dragon replay; (4) SIGNEXTEND with `b ≥ 31` must short-circuit BEFORE any shift or an adversarial `b = U256::MAX` shift-overflows. State plainly: your first attempt will panic on the INT_MIN vector and diverge on the fork-boundary EXP gas — those two debug sessions ARE the lesson. Downstream: W53 (test-vector run depends on these green), W63 (fuzz target reuses the differential harness), W64 (revm perf-PR area).

  #### Phase 1 — Problem, prediction, design (~60 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/exec-vm/notes/51_arith_prediction.md` BEFORE any code:
    - P1. The exact import/primitive you'll reach for signed division — native `i128` cast, `ruint::I256`, or a manual U256 sign-flip? Write the exact line. Predict which Phase-2 test that choice fails.
    - P2. Predicted result of `SDIV(INT_MIN, -1)` if you naively write `I256::from(a) / I256::from(b)` with no guard. (Panic? wrap? trap?) Within one word.
    - P3. Predicted result of `ADDMOD(U256::MAX, U256::MAX, 7)` computed as `(a + b) % m` in U256 arithmetic vs the correct answer. State both numbers.
    - P4. EXP gas: predict `gas(EXP, base=2, exp=256)` on Tangerine vs on Spurious Dragon. (Coefficient differs — EIP-160 activates at Spurious Dragon, so Tangerine still uses 10.) State both, and state which fork the coefficient flips at.
    - P5. **List every Phase-2 test you predict your first attempt will fail.** Compare to reality after tests run.
  - *Mental model*: these opcodes are pure stack→stack U256 transforms with a fixed gas charge; "signed" is a *reinterpretation* of the same 256-bit word (two's-complement), not a separate type. The EVM's defining rule is **total functions — no opcode faults on arithmetic edge cases** (div-by-zero → 0, INT_MIN/-1 → INT_MIN, mod-by-0 → 0). A native Rust impl that traps where the EVM returns a value is a consensus divergence.
  - *Contract* (signatures only — never the body):
    ```rust
    fn sdiv<H: Host>(interp: &mut Interpreter, _: &mut H);   // gas::LOW (5)
    fn smod<H: Host>(interp: &mut Interpreter, _: &mut H);   // gas::LOW (5)
    fn addmod<H: Host>(interp: &mut Interpreter, _: &mut H); // gas::MID (8)
    fn mulmod<H: Host>(interp: &mut Interpreter, _: &mut H); // gas::MID (8)
    fn exp<H: Host>(interp: &mut Interpreter, _: &mut H);    // dynamic: 10 + COST*bytes(exp)
    fn signextend<H: Host>(interp: &mut Interpreter, _: &mut H); // gas::LOW (5)
    // pure helpers (total, never panic):
    fn i256_div(a: I256, b: I256) -> I256;  // b==0 -> 0; MIN/-1 -> MIN
    fn i256_mod(a: I256, b: I256) -> I256;  // b==0 -> 0
    ```
    Note `pop_top!(interp, op1, op2)` pops 2 but exposes the second slot as `&mut` for in-place write (one fewer push). EXP reads `spec_id` from `interp` to fork-gate the gas coefficient.
  - *Back-of-envelope* (bar (b) — correctness-sizing, not a latency budget): each opcode is one U256 op (~a few ns) — the cost that matters is *gas*, not wall-clock. The trap surface is entirely the edge-case branches and the U512 intermediate for ADDMOD/MULMOD. ADDMOD via U512 promote = 2× the limbs (4 u64 → 8 u64) for the intermediate; `U256::add_mod`/`mul_mod` (ruint) avoid the promote with a fused reduction — note which path you take in the design doc, but do NOT optimize here (this is correctness gap-fill; perf belongs to W64).
  - *Anti-shortcut audit* — name the tempting-but-wrong move (each is exactly what a Phase-2 test below must fail on):
    - **`I256::from(a) / I256::from(b)` with no guards.** Wrong: panics on `MIN / -1`, panics/UB on `/ 0`. → trapped by `sdiv_int_min_over_minus_one_no_panic` + `sdiv_by_zero_is_zero`.
    - **`(a + b) % m` in U256 for ADDMOD.** Wrong: `a + b` overflows U256 when the sum ≥ 2²⁵⁶, silently wrong. → trapped by `addmod_no_u256_overflow`.
    - **Hard-code `EXP_BYTE_COST = 50`.** Wrong: the EIP-160 repricing landed at SPURIOUS DRAGON (block 2,675,000), NOT Tangerine Whistle/EIP-150 (block 2,463,000); pre-Spurious-Dragon the coefficient is 10. Hard-coding 50 over-charges the entire Tangerine→Spurious-Dragon window AND every earlier fork, and replaying those blocks diverges. (Gating on Tangerine instead of Spurious Dragon is the same bug shifted by one fork — also wrong.) → trapped by `exp_gas_spurious_dragon_boundary`.
    - **`if b < 31` then shift, evaluated AFTER computing the shift amount.** Wrong: `b = U256::MAX` makes the shift amount astronomically large → shift-overflow panic before the guard. → trapped by `signextend_huge_index_no_panic`.

  - **Requirements** — write in `crates/exec-vm/notes/51_arith_design.md`:
    - R1. `i256_div(a, b)`: `b==0 → 0`; `a==MIN && b==-1 → MIN`; else `a / b`. Total, never panics.
    - R2. `i256_mod(a, b)`: `b==0 → 0`; else `a % b`. Total, never panics. SMOD sign follows the dividend.
    - R3. `addmod`: `m==0 → 0`; else `(a + b) mod m` computed WITHOUT U256 overflow (U512 intermediate or `U256::add_mod`).
    - R4. `mulmod`: `m==0 → 0`; else `(a * b) mod m` computed WITHOUT U256 overflow (U512 intermediate or `U256::mul_mod`).
    - R5. `exp`: `gas = 10 + EXP_BYTE_COST * byte_len(exp)` where `byte_len(exp) = 32 - leading_zero_bytes(exp)`, and `EXP_BYTE_COST = if spec >= SPURIOUS_DRAGON { 50 } else { 10 }` (EIP-160 repriced at Spurious Dragon, NOT Tangerine). Result = `base.pow(exp)` mod 2²⁵⁶ (U256 wrapping pow).
    - R6. `signextend`: `b ≥ 31 → input unchanged`; else sign-extend from bit `(b+1)*8 - 1`. Guard on `b ≥ 31` BEFORE any shift.
    - R7. Differential harness `differential_opcode(op, n_random)` runs N random U256 inputs through exec-vm AND revm and asserts identical output AND identical gas.
  - **Design walk-through** D1..D5 — answer in the design doc; no peeking at revm source until Phase 3:

  #### Phase 2 — Write the failing tests (~60 min)
  Each test is engineered so a common naive impl FAILS it. Tier-annotated.
  - [ ] **(NEWBIE) anti-shortcut** `sdiv_int_min_over_minus_one_no_panic` — the naive `I256::from(a)/I256::from(b)` panics; the contract returns INT_MIN. Exercises R1.
    ```rust
    #[test]
    fn sdiv_int_min_over_minus_one_no_panic() {
        let int_min = U256::from(1) << 255;            // two's-complement MIN
        let minus_one = U256::MAX;                      // -1
        let out = run_opcode(SDIV, &[int_min, minus_one]); // no panic
        assert_eq!(out, int_min, "SDIV(MIN, -1) must be MIN (no trap), got {out:#x}");
    }
    ```
  - [ ] **(NEWBIE)** `sdiv_by_zero_is_zero` — `SDIV(5, 0) == 0` (no fault). Exercises R1.
  - [ ] **(NEWBIE)** `smod_by_zero_is_zero` + `smod_sign_follows_dividend` — `SMOD(-7, 3) == -1` (sign of dividend), `SMOD(x, 0) == 0`. Exercises R2.
  - [ ] **(SENIOR) anti-shortcut** `addmod_no_u256_overflow` — the naive `(a+b)%m` in U256 produces the wrong answer; assert the correct U512-reduced result. Exercises R3.
    ```rust
    #[test]
    fn addmod_no_u256_overflow() {
        let max = U256::MAX;
        // (2^256-1 + 2^256-1) mod 7 = (2^257-2) mod 7 = 2.
        // (2^256 ≡ 2 mod 7 since 256 mod 3 = 1, ord(2)=3; so MAX ≡ 1, a+b ≡ 2.)
        // Naive U256 a+b wraps to 2^256-2 first, so its (a+b)%7 differs — that is the trap.
        let out = run_opcode(ADDMOD, &[max, max, U256::from(7)]);
        assert_eq!(out, U256::from(2),
            "ADDMOD must reduce the TRUE sum mod m via a wider intermediate; U256 (a+b)%m wraps");
        // Second, non-symmetric modulus so the trap can't hinge on one small-m residue.
        // m = 2^200 - 75 (prime). TRUE residue = 10808639105689190398 (0x95fffffffffffffe);
        // the naive wrapped sum 2^256-2 reduces to 5404319552844595198 — a DIFFERENT value, so this also bites.
        let big_m = (U256::from(1) << 200) - U256::from(75);
        assert_eq!(run_opcode(ADDMOD, &[max, max, big_m]), U256::from(10808639105689190398u64),
            "ADDMOD over a large non-symmetric modulus: U512 reduction != wrapped-U256 reduction");
        assert_eq!(run_opcode(ADDMOD, &[max, max, U256::ZERO]), U256::ZERO, "mod 0 -> 0");
    }
    ```
  - [ ] **(SENIOR)** `mulmod_no_u256_overflow` — `MULMOD(MAX, MAX, MAX) == 1`; `MULMOD(x, y, 0) == 0`. Exercises R4.
  - [ ] **(SENIOR) anti-shortcut** `exp_gas_spurious_dragon_boundary` — same `EXP(2, 256)` charges DIFFERENT gas on Tangerine vs Spurious Dragon, SAME result. The repricing is EIP-160 (Spurious Dragon, block 2,675,000), NOT Tangerine/EIP-150 — so Tangerine still uses coefficient 10. A hard-coded coefficient, or a gate on the wrong (Tangerine) fork, fails this. Exercises R5.
    ```rust
    #[test]
    fn exp_gas_spurious_dragon_boundary() {
        let exp = U256::from(256);
        // Tangerine still uses the OLD coefficient (10): EIP-150 did not touch EXP.
        let (out_t, gas_t) = run_with_gas(SpecId::TANGERINE,       EXP, &[U256::from(2), exp]);
        // Spurious Dragon applies EIP-160: coefficient 50.
        let (out_s, gas_s) = run_with_gas(SpecId::SPURIOUS_DRAGON, EXP, &[U256::from(2), exp]);
        assert_eq!(out_t, out_s, "result is fork-independent (2^256 mod 2^256 = 0)");
        // byte_len(256) = 2 bytes. Tangerine: 10 + 10*2 = 30. Spurious Dragon: 10 + 50*2 = 110.
        assert_eq!(gas_t, 30,  "Tangerine EXP_BYTE_COST=10 (EIP-160 not yet active)");
        assert_eq!(gas_s, 110, "Spurious Dragon EXP_BYTE_COST=50 (EIP-160)");
    }
    ```
  - [ ] **(EXPERT) anti-shortcut** `signextend_huge_index_no_panic` — `SIGNEXTEND(U256::MAX, x)` must return `x` unchanged with NO shift-overflow panic. Exercises R6.
    ```rust
    #[test]
    fn signextend_huge_index_no_panic() {
        let x = U256::from(0xABCDu64);
        let out = run_opcode(SIGNEXTEND, &[U256::MAX, x]); // adversarial b; must short-circuit before shift
        assert_eq!(out, x, "b >= 31 returns input unchanged; no 1 << huge");
        // and the real sign-extend still works:
        assert_eq!(run_opcode(SIGNEXTEND, &[U256::ZERO, U256::from(0xFFu64)]), U256::MAX,
            "byte 0 with high bit set sign-extends to all-ones");
    }
    ```
  - [ ] **(SENIOR) negative-control (test-the-test)** `differential_harness_catches_known_bug` — proves the differential harness actually bites. Inject a deliberately-broken `i256_div` (drop the MIN/-1 guard) behind a `#[cfg(test_broken_sdiv)]` and assert `differential_opcode(SDIV, 10_000)` REPORTS a divergence (panics or mismatches) under that cfg, and runs clean without it. If the broken impl passes, the harness is feeding constants, not random inputs — fix the RNG seed coverage before trusting any green run. Annotate: the harness must exercise the INT_MIN and `/0` vectors within its 10k draws (seed them explicitly so coverage is guaranteed, not probabilistic).

  #### Phase 3 — Make the tests pass, one failure at a time (~110 min)
  Newbie failures first, expert last.
  - **(NEWBIE) When `sdiv_int_min_over_minus_one_no_panic` panics with `attempt to divide with overflow`:**
    - Symptom: process panics mid-opcode; under replay this reproducibly diverges from revm's "return MIN".
    - Why: native two's-complement division traps on `MIN / -1` because the mathematically-correct `2²⁵⁵` is unrepresentable as a signed 256-bit value.
    - Fix: explicit early-return `if a == I256::MIN && b == I256::MINUS_ONE { return I256::MIN; }` inside `i256_div`, before the division.
    - Muscle: EVM arithmetic is TOTAL — every native trap (`/0`, `MIN/-1`, shift-overflow) must be replaced by the spec's defined value. Reapplies at: W53 complete-opcode parity, W63 fuzz (the fuzzer finds these instantly), W64 revm-perf (the guard must stay branch-predictable).
  - **(NEWBIE) When `sdiv_by_zero_is_zero` / `smod_by_zero_is_zero` panic instead of returning 0:**
    - Symptom: `/0` panic; revm returns 0.
    - Why: no div-by-zero guard.
    - Fix: `if b == I256::ZERO { return I256::ZERO; }` first.
    - Muscle: same totality invariant — div/mod by zero is a VALUE (0), not a fault. Reapplies at: W53, W63.
  - **(SENIOR) When `addmod_no_u256_overflow` returns the wrong residue:**
    - Symptom: small-input ADDMOD passes; large-input (sum ≥ 2²⁵⁶) silently wrong. Differential fuzz lights up only on big draws.
    - Why: `(a + b) % m` computed `a + b` in U256, which wrapped mod 2²⁵⁶ before the mod-m reduction.
    - Fix: promote to U512 for the sum (`a.widening_add(b)`) then reduce, or use ruint's `U256::add_mod(a, b, m)` which fuses the wide add + reduction.
    - Muscle: any `(op then mod)` where `op` can overflow the type needs a WIDER intermediate before reduction. Reapplies at: W53 MULMOD parity, W64 (when you try to drop the U512 promote for speed, this test guards correctness).
  - **(SENIOR) When `exp_gas_spurious_dragon_boundary` charges 110 gas on Tangerine (or 30 on Spurious Dragon):**
    - Symptom: result correct, gas wrong on one side of the fork; re-executing a Tangerine→Spurious-Dragon-window block (or earlier) over-charges and the block's `gasUsed` diverges.
    - Why: `EXP_BYTE_COST` hard-coded (50), OR gated on the wrong fork (`SpecId::TANGERINE`) — EIP-160's repricing actually activates at SPURIOUS_DRAGON, so a Tangerine gate flips the cost one fork too early.
    - Fix: `let cost = if spec.is_enabled_in(SpecId::SPURIOUS_DRAGON) { 50 } else { 10 };` and `gas = 10 + cost * byte_len(exp)`.
    - Muscle: any gas constant a hard fork repriced MUST be `spec.is_enabled_in(..)`-gated to the CORRECT fork — never a literal, and never the neighboring fork (off-by-one-fork is a real consensus bug). Reapplies at: W53 (every repriced opcode: SLOAD Berlin, CALL Tangerine), W54 precompile gas, W64.
  - **(EXPERT) When `signextend_huge_index_no_panic` panics on `1 << huge`:**
    - Symptom: panic / UB on `1 << ((b+1)*8)` when `b = U256::MAX`; the real-input case never even runs.
    - Why: the `b ≥ 31` guard was evaluated AFTER computing the shift amount/mask, so the overflowing shift happened first.
    - Fix: branch `if b >= U256::from(31) { return input; }` as the FIRST statement, before any shift or mask is computed.
    - Muscle: guard adversarial inputs BEFORE the operation they'd overflow, not after — order of the bounds check is load-bearing. Reapplies at: W52 p2p length-prefix bounds, W53 BYTE/shift edges, W63 fuzz (max-value inputs are the first thing the fuzzer tries).
  - **(SENIOR) When `differential_harness_catches_known_bug` stays green under the broken-sdiv cfg:**
    - Symptom: the deliberately-broken `i256_div` does not produce a reported divergence.
    - Why: the 10k random draws never hit `MIN/-1` or `/0` — the harness is statistically blind to the exact inputs that matter.
    - Fix: seed the corpus with the known edge vectors explicitly so every run covers them deterministically; randomness supplements, never replaces, the hand-picked traps.
    - Muscle: a differential/fuzz harness must SEED its known-hard vectors — never trust random draws to find a measure-zero bug. Reapplies at: W63 cargo-fuzz corpus seeding, W64 perf-regression guard inputs.

**Tuesday — Missing bitwise: BYTE, SHL, SHR, SAR (EIP-145)**

- [ ] **Build**: `crates/exec-vm/src/instructions/bitwise.rs` — the four missing bitwise opcodes, differential-tested and fork-gated. (~total 230 min across 3 phases)
  - 🔧 **Why this matters**: mirrors `revm-interpreter/src/instructions/bitwise.rs`. SHL/SHR/SAR (EIP-145, Constantinople) and BYTE have non-obvious edges: shift-by-≥256 must saturate (not overflow-panic), SAR is arithmetic (sign-preserving) while SHR is logical, and BYTE indexes big-endian ("byte 0 is the MOST-significant byte"). Three traps you WILL hit: (1) passing an uncapped `shift.as_limbs()[0]` to `<<` panics in debug / is UB in release when shift > limb width; (2) SAR on a positive number looks correct so the sign-preservation bug hides until you test a negative; (3) BYTE's `31 - idx` mirror is easy to drop. State plainly: your first attempt will panic on the shift-by-256 vector and silently mis-handle SAR of a negative — those are the lessons. Downstream: W53 (test vectors), W60 (SAR branch-predictor note for the hot path), W63 (fuzz), W64 (perf).

  #### Phase 1 — Problem, prediction, design (~55 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/exec-vm/notes/51_bitwise_prediction.md` BEFORE any code:
    - P1. The exact expression you'll use for the shift amount. Do you extract `shift.as_limbs()[0]` before or after the `>= 256` cap? Predict which Phase-2 test the wrong order fails.
    - P2. Predicted result of `SAR(4, 0x80…00)` (negative input). Sign-preserving or zero-fill? State the hex.
    - P3. Predicted result of `BYTE(0, 0xAB_00…00)` and `BYTE(31, 0x…00_CD)`. State both bytes.
    - P4. Pre-Constantinople, what does opcode `0x1B` (SHL) do? (Valid? InvalidOpcode? gas charged?)
    - P5. **List every Phase-2 test you predict your first attempt will fail.** Compare to reality after tests run.
  - *Mental model*: these are pure U256 bit transforms with `gas::VERYLOW`. The only subtlety is *saturation* (shift ≥ width → all-zero or, for SAR-negative, all-one) and *sign awareness* (SAR reinterprets the word as signed). BYTE is a big-endian byte select. EIP-145 added SHL/SHR/SAR at Constantinople; before that those byte values were undefined → InvalidOpcode.
  - *Contract* (signatures only — never the body):
    ```rust
    fn byte<H: Host>(interp: &mut Interpreter, _: &mut H); // gas::VERYLOW
    fn shl<H: Host>(interp: &mut Interpreter, _: &mut H);  // gas::VERYLOW, EIP-145
    fn shr<H: Host>(interp: &mut Interpreter, _: &mut H);  // gas::VERYLOW, EIP-145
    fn sar<H: Host>(interp: &mut Interpreter, _: &mut H);  // gas::VERYLOW, EIP-145
    ```
    `pop_top!(interp, shift_or_idx, value)` — second slot is the in-place result. SHL/SHR/SAR are registered in the instruction table only for `spec >= CONSTANTINOPLE`; pre-fork the slot is the InvalidOpcode handler.
  - *Back-of-envelope* (bar (b)): each is a single-cycle-class bit op (~ns). The only correctness-relevant cost is the saturating branch on `shift >= 256`. SAR adds one sign-test branch — note (do NOT optimize) that this branch is data-dependent and a future W60 hot-path pass may want it branch-light; that is backlog, not this week.
  - *Anti-shortcut audit* — name the tempting-but-wrong move (each is a Phase-2 trap):
    - **`*value << shift.as_limbs()[0]` with no cap.** Wrong: when shift ≥ 256 the limb value is huge → shift-overflow panic/UB. → trapped by `shl_shr_saturate_at_256`.
    - **Use Rust `>>` on the unsigned U256 for SAR.** Wrong: that's a LOGICAL shift; SAR must be arithmetic — convert to I256 first. → trapped by `sar_negative_preserves_sign`.
    - **`value.byte(idx)` directly.** Wrong: ruint's `byte()` is LSB-first; EVM BYTE is MSB-first → must mirror with `31 - idx`. → trapped by `byte_big_endian_index`.
    - **Register SHL/SHR/SAR for all specs.** Wrong: pre-Constantinople they must be InvalidOpcode. → trapped by `shl_invalid_pre_constantinople`.

  - **Requirements** — write in `crates/exec-vm/notes/51_bitwise_design.md`:
