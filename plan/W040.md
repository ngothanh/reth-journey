**Monday — STCS theory + implementation start**

- [ ] **Build**: `crates/lsm-core/src/compaction/stcs.rs` — Size-Tiered Compaction Strategy: trigger when a tier
  has ≥4 similarly-sized SSTs; merge them via `MergeIterator` into one or more next-tier SSTs sized to target.
  (~total 230 min across 3 phases)
  - 🔧 **Why this matters**: STCS is the canonical LSM compaction baseline (mirrors mini-lsm
    `SizeTieredCompactionController` + RocksDB universal compaction). Four traps make naive STCS fail *silently*:
    (1) cascading storm — a single merged output immediately re-triggers compaction; (2) tombstone resurrection —
    eliding a delete-marker above a level that still holds the value resurrects a deleted key (silent data
    corruption, consensus-divergent in `mini-db`); (3) flush race — a flush that lands mid-compaction is dropped
    as if it were a compaction input (lost write); (4) manifest/file-delete ordering — deleting input files
    before fsyncing the manifest leaves dangling refs after a crash. **Your first attempt will fail ≥1 Phase-2
    test below — the debug session is the lesson.** Reused at: W41 LCS execute, W42 TWCS within-window merge,
    W95/W100 mini-db.

  - *Mental model*: STCS is a **garbage collector for the write path** — it trades read amplification (fewer
    overlapping SSTs to merge-read) for write amplification (rewriting data). A "tier" is a bucket of SSTs of
    similar size; when a bucket overflows, you fold it down a level. The manifest is the **single source of
    truth** for which SSTs are live — files on disk are just cache that the manifest authorizes.
  - *Contract*: the signature-level interface — NEVER the body:
    ```rust
    pub struct StcsController { threshold: usize, size_ratio_tolerance: f64, max_sst_size: u64 }
    pub struct CompactionTask { pub level: usize, pub inputs: Vec<SstId>, pub into_level: usize }
    impl StcsController {
        /// Snapshot-based: scans an immutable LevelsSnapshot, returns None if no tier qualifies.
        pub fn pick(&self, levels: &LevelsSnapshot) -> Option<CompactionTask>;
        /// Runs the merge; returns the new SSTs (NOT yet committed to the manifest).
        pub fn execute(&self, task: &CompactionTask, store: &SstStore) -> Result<Vec<SstMeta>>;
    }
    ```
    Note: `pick` and `execute` are **split** so the scheduler (Tuesday) can snapshot at pick time and commit
    atomically after execute — this split is load-bearing for the flush-race and crash-safety tests.
  - *Back-of-envelope* (bar (b), but the I/O math drives the design): a 4×64 MB tier merge reads 256 MB and
    writes 256 MB. At ~500 MB/s sequential SSD that is ~0.5 s of pure I/O per merge; `MergeIterator` heap
    `pop`/`push` is ~log₂(4)=2 comparisons per key ≈ a handful of branch-predictable ns/key — I/O dominates,
    CPU does not. **Cliff**: if output is a single 256 MB SST and the next tier's target is also 256 MB, the
    output instantly re-qualifies → unbounded re-merge of the SAME 256 MB (write amp → ∞, the storm).
  - **Requirements** R1..R8 — write in `crates/lsm-core/notes/40_stcs_design.md`:
    - R1. Trigger: a tier has ≥ `threshold` (=4) SSTs within `size_ratio_tolerance` (=0.5, i.e. largest ≤ 1.5× smallest in the run).
    - R2. Run: N-way `MergeIterator` over input SSTs (newest input = `source_idx 0`, wins ties); emit one or
      more `into_level` SSTs.
    - R3. **Tombstone elision** only when compacting INTO the deepest live level; at any shallower target,
      tombstones survive into the output.
    - R4. **No cascading storm**: each output SST respects `max_sst_size`; a merge that exceeds it splits into
      multiple outputs.
    - R5. **Atomic manifest update**: remove inputs + add outputs in ONE manifest record; fsync; only THEN
      delete input files on disk.
    - R6. **Flush-race safety**: `pick` snapshots the levels; `execute`/commit remove EXACTLY the snapshotted
      `SstId`s — never "all SSTs currently in the tier".
    - R7. Write amp ≤ N (=4) per merge; transient space amp ≤ 2×.
    - R8. Crash-safe under kill-9 at any instant: recovery sees pre-compaction state OR fully-committed
      post-compaction state, never a torn state.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  Ordered newbie→expert — the ladder you actually walk.

  - **(NEWBIE) When `stcs_compaction_preserves_logical_content` reports a stale value for a duplicated key:**
    - Symptom: `key "K": merged STCS lost newest value` — the merge emitted an OLD value for a key present in
      multiple inputs.
    - Why: `MergeIterator` tie-break uses the wrong direction — older SST's `source_idx` won the tie, so the
      stale value shadowed the fresh one.
    - Fix: assign `source_idx` newest-first (0 = newest input) and break ties to the lowest `source_idx`; on a
      key collision, advance the loser without emitting.
    - Muscle: in any N-way merge of versioned data, the tie-break direction IS the correctness contract — pin
      it with a test, not a comment. Reapplies at: W41 LCS execute, W95 mini-db read-path merge.

  - **(SENIOR) When `stcs_no_cascading_storm` reports a single output / immediate re-trigger:**
    - Symptom: `single huge output (no split) → storm`, or `pick` immediately returns `Some` on post-merge
      levels.
    - Why: the merge emits one output regardless of size; a 256 MB output into a 256 MB-target tier instantly
      re-qualifies, re-merging the same bytes forever (write amp → ∞).
    - Fix: `SstBuilder` tracks running size; on reaching `max_sst_size` it finishes the current SST and opens
      the next, so a big merge yields multiple right-sized outputs that do NOT re-qualify.
    - Muscle: compaction output sizing must respect destination-tier targets — never accept a single huge
      output. Reapplies at: W41 LCS execute, W42 TWCS within-window compaction.

  - **(SENIOR) When `stcs_tombstone_survives_intermediate_level` reports `None`-via-resurrection (value comes back):**
    - Symptom: after delete, querying K returns the L3 value — the tombstone was elided at L2 even though L3
      still held K.
    - Why: tombstone elision is too eager — dropping a delete-marker above a level that still holds the value
      makes the old value visible again (resurrection; in `mini-db` this is consensus-divergent corruption).
    - Fix: elide ONLY when compacting INTO the deepest non-empty level (simple, safe default); the
      range-overlap optimization (elide when no deeper level overlaps the key range) is a later, carefully-
      invarianted refinement — not now.
    - Muscle: tombstone elision is correctness-critical; "deepest only" is the safe default, range-checks are an
      opt-in optimization with proof obligations. Reapplies at: W41 LCS execute, W95 mini-db deletion semantics.

  - **(SENIOR) When `stcs_flush_race_no_lost_writes` reports the 5th SST disappearing:**
    - Symptom: `5th SST removed as if it were a compaction input` — `s5` is gone and `late_key` is lost.
    - Why: commit removed "all SSTs currently in the tier" rather than the snapshotted input set; the flush
      that landed after `pick` got swept up and dropped.
    - Fix: `CompactionTask` captures the exact `SstId`s at `pick` time; commit removes EXACTLY `task.inputs`
      and adds the outputs — concurrent flushes are untouched and feed a future compaction.
    - Muscle: any background coordinator racing foreground producers must capture an immutable input set at
      task-pick time and act only on it. Reapplies at: W41 LCS pick-victim, W42 deadlock-detector graph build,
      W74 matching-engine background snapshot.

  - **(EXPERT) When `stcs_crash_mid_compaction_recovery` reports dangling manifest refs (`FileNotFound`):**
    - Symptom: crash between input-delete and manifest-fsync → restart → manifest still lists deleted inputs →
      `SstReader::open` fails `FileNotFound`.
    - Why: cleanup (file delete) ran before publish (durable manifest record), so the durable record points at
      bytes that no longer exist.
    - Fix: order the commit as build outputs → manifest append (remove inputs + add outputs) → **manifest
      fsync** → delete input files; a crash between fsync and delete leaves orphan input files that a startup
      sweep reclaims (correct, recoverable), never a dangling ref.
    - Muscle: in any "publish + cleanup" sequence, the durable publish record comes BEFORE the cleanup; orphans
      are recoverable, dangling refs are not. Reapplies at: W26 WAL group-commit + segment delete, W39 flush +
      WAL truncate, W42 txn commit + undo-log discard.

    ```rust
        signal: Arc<Notify>,                     // levels poke this when they may need attention
        credit: CreditFlowControl,               // W11: reserves foreground budget
        per_level: HashMap<usize, Arc<Mutex<()>>>, // ≤1 task per level
        cascade_budget: usize,                   // ≤K next-level checks per cycle
    }

        pub fn spawn(self, store: SstStore, controller: StcsController) -> SchedulerHandle;
        pub fn shutdown(handle: SchedulerHandle); // set flag, drain current task, join
    }
    ```
  - *Back-of-envelope / Back-of-envelope* (the perf budget that drives the perf card): a single 4×64 MB merge
    is ~0.5 s of I/O (256 MB read + 256 MB write at ~500 MB/s). A 16-writer foreground load wants p999 < 10 ms.
    If compaction is allowed to consume 100% of disk bandwidth, a foreground write that needs the disk queues
    behind ~0.5 s of compaction I/O → p999 ≈ **100+ ms** (the sawtooth). Reserving ~70% of credit for
    foreground caps compaction's queue-jump to a fraction of one SST's I/O → p999 stays single-digit ms.
    **Cliff: 100 ms (unreserved) vs <10 ms (reserved) ≈ 10× tail blowup.**

    - Symptom: each merge overflows the next level → the scheduler greedily picks it → infinite cascade, CPU

    - Why: greedy pick of every signaled level with no per-cycle budget; cascades stack depth-first.
    - Fix: cap ≤ K tasks per scheduler cycle; round-robin signaled levels so subsequent cascades queue for the

      DoS-shaped failure mode. Reapplies at: W42 deadlock-detector cascade, W74 matching-engine fill-broadcast.

      latency saws up under each burst and recovers — the pattern that blows SLO budgets.
    - Why: the scheduler picks greedily under a single low credit threshold; a burst kicks off multiple merges
      back-to-back, each consuming disk credit faster than writes replenish, so a foreground write queues behind
      ~0.5 s of compaction I/O.

      foreground; compaction consumes only excess; START a new task only above HIGH, pause/yield below LOW.
      Compaction is best-effort relative to production writes.
    - Cost avoided: **~90 ms of tail latency per burst (p999 100 ms → <10 ms ≈ 10× tail reduction);** ~0.5 s of
      disk-queue head-of-line blocking removed from the write path each burst.
    - Muscle: background I/O priority must respect a *reserved* foreground budget — never let background consume
      all available bandwidth. Reapplies at: W42 txn background vacuum, W74 matching-engine background snapshot,
      W76 aeron archive recording.
