**Monday — STCS theory + implementation start**

- [ ] **Build**: `crates/lsm-core/src/compaction/stcs.rs` — Size-Tiered. Trigger when level i has ≥4 similarly-sized
  SSTs. Merge them via MergeIterator into level i+1. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: STCS is the canonical LSM compaction baseline. Tombstone elision at the wrong
    level resurrects deleted keys (silent corruption); compaction races flush silently drop writes;
    manifest-fsync-after-delete ordering loses data on crash. W41 LCS, W42 TWCS, W95 mini-db all reuse these
    patterns.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: when N similarly-sized SSTs accumulate, merge them into one larger
    SST at the next level. Sounds simple — but the four pitfalls (cascading storm, tombstone resurrection,
    flush race, file-delete ordering) are how STCS implementations fail silently.

  - **Requirements** — write in `crates/lsm-core/notes/40_stcs_design.md`:
    - R1. Trigger: level i has ≥ threshold (=4) SSTs within size ratio tolerance.
    - R2. Run: N-way MergeIterator over input SSTs (newest source_idx = 0); output one or more L(i+1) SSTs
      sized to L(i+1)'s target.
    - R3. **Tombstone elision** only at the deepest level — at any other level, tombstones survive into
      L(i+1).
    - R4. **No cascading storm**: output respects L(i+1)'s target SST size; split into multiple outputs if
      needed.
    - R5. **Atomic manifest update**: remove inputs + add outputs in ONE manifest record; fsync; only then
      delete input files.
    - R6. **Flush race safety**: snapshot levels at task pick time; new flushes go to a future compaction.
    - R7. Write amp ≤ N (=4); space amp ≤ 2× transient.
    - R8. Crash-safe at kill-9 at any point: recovery sees pre-compaction state OR fully-committed
      post-compaction state.

  - **Design walk-through** — answer each:
    - D1. The pick_compaction algorithm: scan levels, find ≥ threshold similar-sized SSTs. What's
      "similar" (size_ratio_tolerance = 0.5)?
    - D2. Tombstone elision rule — write it. When is "the deepest level" knowable (is L7 always
      deepest, or is it dynamic)?
    - D3. The cascading-storm trace: 4 × 64 MB SSTs merge into one 256 MB output at L(i+1); L(i+1)'s
      target is 256 MB, so it now exceeds threshold and re-triggers immediately. How does splitting
      output into multiple SSTs prevent this?
    - D4. Flush race: T1 picks a compaction task (4 L0 SSTs); T2 (flush) adds a 5th L0 SST mid-task.
      What does T1 do with the 5th SST?
    - D5. Manifest ordering: write the 5-step sequence. Why must file delete come AFTER manifest
      fsync?
    - D6. **Pre-mortem (load-bearing)**: write the tombstone-resurrection trace — eliding tombstone
      at L1 while L2 still has the value; query sees the value after the delete should have
      suppressed it.
  - **Output**: `notes/40_stcs_design.md` with R1–R8, D1–D6.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **When `stcs_no_cascading_storm` reports immediate re-compaction:**
    - Symptom: after 4 × 64 MB compaction, L(i+1) now has ≥4 similar-sized SSTs immediately;
      compaction re-triggers; storm.
    - Why: merging 4×64MB = 256MB output; if L(i+1) target is 256MB, this fills L(i+1) and
      immediately re-triggers compaction (cascade).
    - Fix: output respects L(i+1)'s target SST size; split into multiple outputs. The SstBuilder
      tracks current SST size; on threshold, finishes current SST, opens next.
    - Muscle: compaction output sizing must respect destination-level targets; never accept a single
      huge output. Reapplies at: W41 LCS execute, W42 TWCS within-window compaction.

  - **When `stcs_tombstone_survives_intermediate_level` reports None (tombstone elided too early):**
    - Symptom: insert + delete K; compaction to L2 (not deepest); query K returns the value from L3
      (resurrection). Tombstone was elided at L2 even though L3 still held the value.
    - Why: tombstone elision too eager — eliding a tombstone at L1 while L2 still holds the value
      causes resurrection.
    - Fix: only elide at the deepest level OR confirm no overlap range in lower levels. Simple
      policy: elide ONLY when compacting INTO the deepest level. Conservative: elide only when the
      key range has no representation in any deeper level.
    - Muscle: tombstone elision is consensus-critical; the rule "deepest only" is the safe default;
      complex range-checks are an optimization with careful invariants. Reapplies at: W41 LCS
      execute, W95 mini-db deletion semantics.

  - **When `stcs_flush_race_no_lost_writes` reports the 5th L0 SST disappearing:**
    - Symptom: T2 flush adds the 5th SST during T1's compaction; T1's manifest update removes the 5th
      as if it were an input; data loss.
    - Why: flush adds to L0 while compaction reads L0; the new flush is missing from compaction
      inputs.
    - Fix: snapshot levels at task pick time; new flushes go to a future compaction. T1's
      CompactionTask captures the exact SstIds of inputs at pick time; T1's manifest update removes
      EXACTLY those, not "all L0 SSTs".
    - Muscle: any background coordinator that races foreground producers must capture an immutable
      input set at task-pick time. Reapplies at: W41 LCS pick-victim, W42 deadlock detector graph
      build.

  - **When `stcs_crash_mid_compaction_recovery` reports phantom SST references after restart:**
    - Symptom: kill -9 between input file delete and manifest fsync; on restart, manifest still
      references the deleted inputs; SstReader::open fails with FileNotFound.
    - Why: input deletion before manifest fsync — deleting input SST files before manifest sync →
      recovery sees deleted refs in manifest.
    - Fix: manifest fsync first, file delete second. The sequence: build outputs → manifest append
      (remove inputs + add outputs) → manifest fsync → delete input files. If crash between manifest
      fsync and file delete, recovery sees a manifest pointing at the outputs (correct) + orphan
      input files on disk (cleaned up by a startup sweep).
    - Muscle: in any "publish + cleanup" sequence, publish (durable record) comes BEFORE cleanup.
      Reapplies at: W26 WAL group commit + segment delete, W39 flush + WAL truncate.

  - **5-year failure mode** (write in `notes/40_stcs_followup.md` after green): when learned/adaptive
    compaction strategies (ML-tuned per workload) become available, STCS becomes a "starting policy"
    overridden by per-table learned tuner. State the migration: STCS as cold-start default;
    `LearnedCompactor` trait wrapper.

**Tuesday — Compaction scheduler**

- [ ] **Build**: `crates/lsm-core/src/compaction/scheduler.rs` — background thread runs compaction picks. Throttling via
  the same `backpressure::CreditFlowControl` matching-engine will use. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: background compaction must not starve foreground writes. The dual-watermark
    credit pattern (perf pitfall) is the difference between sawtooth p99 and flat p99. W41 LCS scheduler, W42
    txn background vacuum, W74 matching-engine background snapshot all reuse the same pattern.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: compaction is I/O-heavy; running it inline tanks write latency.
    Decouple: writers signal "level may need attention", scheduler picks tasks under a credit budget so
    compaction can never starve foreground writes. The credit math + dual-watermark logic is the production
    detail.

  - **Requirements** — write in `crates/lsm-core/notes/40_scheduler_design.md`:
    - R1. Background thread loops on `signal.notified().await`; picks tasks; checks credit; runs.
    - R2. **At most one task per level concurrently** — `HashMap<level, Arc<Mutex<()>>>` enforces no
      overlap.
    - R3. **Dual-watermark credit**: reserve 70% for foreground writes; compaction consumes only excess.
      Only START new task when foreground credit ≥ HIGH; pause / yield when foreground < LOW.
    - R4. **Cascade rate-limit**: each compaction task triggers ≤ K next-level checks per cycle; prevents
      runaway storms.
    - R5. **Startup cleanup**: scan for orphaned `.tmp` files (from prior crash mid-compaction); delete
      those older than manifest's max committed SstId.
    - R6. Graceful shutdown: set flag; drain current task; join. No orphaned files.
    - R7. Write tail latency p999 < 10 ms under sustained compaction load.

  - **Design walk-through** — answer each:
    - D1. The scheduler loop: write the pseudocode. What's the signal vs credit interaction?
    - D2. Per-level concurrency lock: why per-level, not global? When does the per-level
      granularity matter?
    - D3. Dual-watermark credit: write the math. What's HIGH (e.g. 70%)? What's LOW (e.g. 30%)?
      What happens between?
    - D4. Cascade rate-limit: write the policy. Why round-robin across levels?
    - D5. Startup cleanup: enumerate the orphan classes (`.tmp` files, dangling input refs in
      manifest, partial manifest record). What does cleanup do for each?
    - D6. **Pre-mortem (load-bearing)**: write the compaction-starves-write burst trace — burst of
      L0 flushes; scheduler kicks off multiple compactions; credit consumed faster than writes
      replenish; write p99 spikes to ~100 ms (sawtooth).
  - **Output**: `notes/40_scheduler_design.md` with R1–R7, D1–D6.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **When `bench_scheduler_p999_under_10ms_under_load` reports sawtooth p99 spiking to ~100 ms:**
    - Symptom: under burst load (many L0 flushes simultaneously), write p99 spikes to ~100 ms,
      then recovers; pattern repeats. The sawtooth latency that breaks SLO budgets.
    - Why: the scheduler picks tasks greedily under a low-water credit threshold; when many L0
      flushes arrive simultaneously (burst from a write spike), compaction kicks off multiple
      tasks back-to-back, each consuming credit faster than writes can replenish.
    - Fix: dual-watermark priority-band credit allocation (W11 backpressure pattern). Reserve ~70%
      of credit for foreground writes; compaction consumes only "excess" credit. Only START a new
      compaction when foreground credit is above HIGH water; pause / yield when foreground drops
      below LOW. Treat compaction as Borg-style "best-effort" relative to "production" writes.
    - Cost avoided: p99 stays at steady ~ms instead of ~100 ms during bursts; flat-line latency
      replaces sawtooth.
    - Muscle: background I/O priority must respect a **reserved** budget for foreground work;
      never let background consume all available bandwidth. Reapplies at: W42 `txn` background
      vacuum, W74 matching-engine background snapshot, W76 aeron archive recording.

  - **When `scheduler_no_cascade_storm` reports infinite cascade (100% CPU, no write progress):**
    - Symptom: each compaction triggers next-level overflow → infinite cascade. 100% CPU on
      compaction, no progress on writes.
    - Why: scheduler greedily picks every signaled level; no rate-limit; cascades stack.
    - Fix: rate-limit cascade depth per cycle; round-robin across levels. Each scheduler cycle
      processes at most K tasks; subsequent cascades queue for next cycle. Round-robin ensures no
      one level monopolizes the scheduler.
    - Muscle: any cascading workflow must have a rate-limit + fairness policy; greedy cascade is a
      DoS-shaped failure mode. Reapplies at: W42 deadlock detector cascade, W74 matching-engine
      fill-broadcast.

  - **When `scheduler_startup_removes_orphan_tmp` reports the orphan persists:**
    - Symptom: kill scheduler mid-compaction leaves `<sst_id>.sst.tmp`; restart; the tmp file
      remains; over time the disk fills.
    - Why: shutdown leaves .tmp files — if shutdown kills mid-compaction, tmp SSTs accumulate.
    - Fix: cleanup pass on startup removes orphaned .tmp files older than manifest's max id. The
      manifest's max-committed SstId is the cutoff: any `.tmp` for SstId ≤ max is a known orphan
      (its compaction crashed before manifest commit); any `.tmp` for SstId > max is a future
      compaction's in-flight work (don't delete — but the scheduler restart will handle it).
    - Muscle: any "rename-on-commit" pattern must have a startup orphan-sweep keyed on the
      manifest's max committed ID. Reapplies at: W26 WAL segment orphans, W77 aeron archive
      segment orphans.

  - **5-year failure mode** (write in `notes/40_scheduler_followup.md` after green): when learned
    schedulers (RL-based task selection) become available, the dual-watermark credit becomes a
    fallback; learned tuner picks based on observed workload. State the migration: keep credit as
    safety net; learned tuner overrides task selection within credit envelope.
