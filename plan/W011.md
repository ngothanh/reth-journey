- [ ] **Refactor**: `crates/eth-network-codec/src/connection.rs` — `Connection<S>` with phantom states
  Disconnected/Handshaking/Established. (~60 min)
  - *Mental model*: a peer connection moves through a fixed lifecycle — disconnected → handshaking → established —
    and only certain operations are legal in each state (you can't `send_message` before the handshake). Type-state
    encodes that state machine in the *type parameter* `S`, so an illegal call is a compile error, not a runtime
    `if state != Established { panic }`. The state markers are zero-sized; they exist only at the type level.
  - *Contract*: `Connection<S> { stream: Framed<…>, _state: PhantomData<S> }`, generic over a state marker. Three
    zero-sized marker types `Disconnected`, `Handshaking`, `Established` (empty structs/enums). Transitions are
    *consuming* methods that change `S`: `Connection<Disconnected>::connect(addr) -> Connection<Handshaking>`,
    `Connection<Handshaking>::complete(self) -> Connection<Established>`. State-specific operations are `impl`
    blocks gated on `S`: `send_message`/`recv_message` live only on `impl Connection<Established>`. A sealed marker
    trait (`ConnectionState`, sealed so outside crates can't add states) bounds `S`.
  - *Refactor, roughly*: (1) define the three marker types + sealed `ConnectionState` trait; (2) make `Connection`
    generic over `S: ConnectionState` with a `PhantomData<S>` field; (3) move each existing method into the `impl`
    block for the state where it is legal; (4) make every transition take `self` by value and return the new-state
    `Connection`. Deciding which methods belong to which state — and proving the illegal ones no longer compile —
    is the real exercise.
  - **Expect to hit #1 — `PhantomData<S>` field forgotten / unused-parameter error**: you make `Connection<S>`
    generic but store nothing of type `S`. Symptom: `error[E0392]: parameter S is never used` — the compiler
    rejects a type parameter that appears nowhere in the body.
    - Fix: add a `_state: PhantomData<S>` field (zero-sized, costs nothing at runtime) so `S` is "used".
    - Muscle: a type parameter that exists only at the type level still needs a `PhantomData` to anchor it.
      Reapplies at: W22 `eth-stage` trait skeleton, W42 `txn` state markers.
  - **Expect to hit #2 — illegal transition still compiles**: you keep `send_message` as an inherent method on
    `Connection<S>` (any `S`) instead of gating it. Symptom: the bug the whole pattern is meant to kill —
    `Connection<Disconnected>::send_message` compiles fine; you only catch it at runtime.
    - Fix: put state-specific methods in `impl Connection<Established> { … }` blocks, never in a generic `impl<S>`;
      write a `compile_fail` doctest that proves `send` on a `Disconnected` connection is rejected.
    - Muscle: type-state only protects you if each operation lives in exactly the state-specific `impl` block.
      Reapplies at: W22 staged-sync stage transitions, W73 Engine API payload-status states.
  - **Expect to hit #3 — transition borrows instead of consumes**: `complete(&mut self)` mutates in place, so the
    old `Connection<Handshaking>` is still usable after the handshake finishes. Symptom: code holds a stale
    `Handshaking` handle and calls handshake-only methods on an already-established connection — the state machine
    no longer reflects reality.
    - Fix: every transition takes `self` *by value* and returns the new `Connection<NextState>`; the old handle is
      moved out and can't be touched.
    - Muscle: a type-state transition must consume the old state so it can't alias the new one. Reapplies at: W42
      `txn` 2PL lock-state transitions, W73 Engine API state progression.
  - **Expect to hit #4 — open marker trait lets outsiders forge states**: `ConnectionState` is a public trait with
    no seal, so a downstream crate `impl ConnectionState for EvilState` and slips an unintended state into
    `Connection`. Symptom: your exhaustive `impl` coverage has a hole you never wrote; invariants assumed over "the
    three states" silently break.
    - Fix: seal the trait — `mod private { pub trait Sealed {} }`, `ConnectionState: private::Sealed`, impl `Sealed`
      only for your three markers.
    - Muscle: a marker trait that defines a closed set of states must be sealed. Reapplies at: W22 `eth-stage`
      stage set, W42 `txn` isolation-level markers.

- [ ] **Build**: `crates/eth-trie/src/hashed_state.rs` — HashedPostState mirroring reth_trie. (~105 min)
  - *Mental model*: after a block executes you have a set of changed accounts and storage slots, keyed by *plain*
    address/slot. The trie, however, is keyed by `keccak256` of those keys. `HashedPostState` is that change set
    re-keyed into hashed space — the exact shape the trie walker consumes to recompute the state root. It is a
    *diff*, not a full state: only what the block touched.
  - *Contract*: `HashedPostState { accounts: HashMap<B256, Option<Account>>, storages: HashMap<B256, HashedStorage>
    }` keyed by hashed address. `Option<Account>` distinguishes an updated account (`Some`) from a *destroyed* one
    (`None` → must be removed from the trie). `HashedStorage { wiped: bool, slots: HashMap<B256, U256> }` keyed by
    hashed slot; `wiped` flags a `SELFDESTRUCT`/recreate that clears the whole storage subtrie. Key methods:
    `from_plain_state(changes)` (hashes plain keys in), `extend(other)` (merge a later block's diff over this one),
    `construct_prefix_sets()` (the changed-key set the trie walker needs).
  - *from_plain_state, roughly*: (1) for each changed account, `keccak256(address)` → insert into `accounts`;
    (2) for each changed slot, `keccak256(slot)` → insert into the account's `HashedStorage`; (3) carry the
    destroyed/wiped flags through. Step 2 — getting wipe semantics right when an account is destroyed *and*
    recreated in the same diff — is the real exercise.
  - **Expect to hit #1 — hashing keys at the wrong layer**: you key the maps by plain `Address`/slot and hash only
    when handing data to the trie. Symptom: two call sites hash inconsistently, or `extend` merges a plain-keyed and
    a hashed-keyed map — entries that should collide don't, and the state root is wrong with no panic.
    - Fix: `HashedPostState` is hashed-keyed *by construction*; the only place plain→hashed happens is
      `from_plain_state`, at the boundary.
    - Muscle: pick one key space for a type and convert exactly once, at the constructor. Reapplies at: W20
      `eth-trie` walker, W31 persistent MPT, W35 state commitment.
  - **Expect to hit #2 — destroyed account vs zero-balance account**: you model "account gone" as
    `Some(Account::default())` instead of `None`. Symptom: a self-destructed account stays in the trie as an empty
    account; its hashed-key leaf is never deleted, and the state root diverges from Geth's.
    - Fix: `None` in the `accounts` map means *delete the trie leaf*; `Some(acct)` means *upsert*. The trie walker
      branches on exactly that.

  `CreditFlowControl { credits: AtomicU64, low_water: u64, high_water: u64 }` — used by messaging-aeron flow control AND
  matching-engine inbound queue. (~150 min)
  - *Mental model*: credit-based flow control is the opposite of "push then drop" — a sender may only send while
    it holds credits. The receiver *grants* credits as it drains its buffer; the sender *consumes* one per message.
    Watermarks add hysteresis: the receiver replenishes credits in a batch when the count falls to `low_water`, and
    a sender is throttled until credits climb back toward `high_water`. This is `messaging-aeron`'s flow control and
    `matching-engine`'s inbound admission control.
  - *Contract*: `CreditFlowControl { credits: AtomicU64, low_water: u64, high_water: u64 }`. Sender side:
    `fn try_acquire(&self) -> bool` — atomically take one credit if available. Receiver side:
    `fn release(&self, n: u64)` — return credits after draining; `fn should_grant(&self) -> bool` — true when
    `credits <= low_water`, the cue to top up toward `high_water`. All state lives in the one `AtomicU64`; no lock.
  - *try_acquire, roughly*: (1) load `credits`; (2) if `0`, fail; (3) CAS `credits → credits - 1`; (4) on CAS
    failure, *reload* and retry. The retry-on-fresh-load — never decrementing a value you didn't just observe —
    is the real exercise.
  - *Back-of-envelope*: `try_acquire` is on the *send* hot path — every producer call. Target: **one atomic
    op (~10 ns)**, no CAS retry under normal load. `release` is called per drained item or batched —
    equally hot. Watermark check `should_grant` is a cheap atomic load + compare (~5 ns). All state in one
    `AtomicU64`, so check + decrement happen in one CAS — but that one atomic is the scalability ceiling;
    under N producers it scales as O(N²) (see perf pitfall below). For W76 messaging-aeron, where
    per-stream credit is checked at thousands of pubs/sec across many publishers, this matters.
  - **Expect to hit #1 — check-then-act race on credits**: `try_acquire` does `if credits.load() > 0 {
    credits.fetch_sub(1) }`. Two senders both see `1`, both `fetch_sub`, and the counter wraps to `u64::MAX`.

    credit; flow control silently disabled. x86 may hide it; Apple Silicon surfaces it fast.
    - Fix: make acquire one atomic step — a `fetch_update`/CAS loop that only decrements the *exact* value it just
      loaded, and fails (no decrement) when that value is `0`.

    - Fix: two distinct thresholds — only *start* granting when `credits <= low_water`, and grant up to
      `high_water` in one batch; the `low..high` gap is the hysteresis band that absorbs the chatter.
    - Muscle: a replenish-on-threshold control needs two watermarks (a band), never one, or it oscillates.
