- [ ] **Refactor**: `crates/eth-network-codec/src/connection.rs` — `Connection<S>` with phantom states
  Disconnected/Handshaking/Established. (~60 min)
  - *Mental model*: a peer connection moves through a fixed lifecycle — disconnected → handshaking → established —
    and only certain operations are legal in each state (you can't `send_message` before the handshake). Type-state
    encodes that state machine in the *type parameter* `S`, so an illegal call is a compile error, not a runtime
    `if state != Established { panic }`. The state markers are zero-sized; they exist only at the type level.
  - *Contract*: `Connection<S> { stream: Framed<…>, _state: PhantomData<S> }`, generic over a state marker. Three
    zero-sized marker types `Disconnected`, `Handshaking`, `Established` (empty structs/enums). Transitions are
    *consuming* methods that change `S`: `Connection<Disconnected>::connect(addr) -> Connection<Handshaking>`,
    `Connection<Handshaking>::complete(self) -> Connection<Established>`. State-specific operations are `impl`
    blocks gated on `S`: `send_message`/`recv_message` live only on `impl Connection<Established>`. A sealed marker
    trait (`ConnectionState`, sealed so outside crates can't add states) bounds `S`.
  - *Refactor, roughly*: (1) define the three marker types + sealed `ConnectionState` trait; (2) make `Connection`
    generic over `S: ConnectionState` with a `PhantomData<S>` field; (3) move each existing method into the `impl`
    block for the state where it is legal; (4) make every transition take `self` by value and return the new-state
    `Connection`. Deciding which methods belong to which state — and proving the illegal ones no longer compile —
    is the real exercise.
  - **Expect to hit #1 — `PhantomData<S>` field forgotten / unused-parameter error**: you make `Connection<S>`
    generic but store nothing of type `S`. Symptom: `error[E0392]: parameter S is never used` — the compiler
    rejects a type parameter that appears nowhere in the body.
    - Fix: add a `_state: PhantomData<S>` field (zero-sized, costs nothing at runtime) so `S` is "used".
    - Muscle: a type parameter that exists only at the type level still needs a `PhantomData` to anchor it.
      Reapplies at: W22 `eth-stage` trait skeleton, W42 `txn` state markers.
  - **Expect to hit #2 — illegal transition still compiles**: you keep `send_message` as an inherent method on
    `Connection<S>` (any `S`) instead of gating it. Symptom: the bug the whole pattern is meant to kill —
    `Connection<Disconnected>::send_message` compiles fine; you only catch it at runtime.
    - Fix: put state-specific methods in `impl Connection<Established> { … }` blocks, never in a generic `impl<S>`;
      write a `compile_fail` doctest that proves `send` on a `Disconnected` connection is rejected.
    - Muscle: type-state only protects you if each operation lives in exactly the state-specific `impl` block.
      Reapplies at: W22 staged-sync stage transitions, W73 Engine API payload-status states.
  - **Expect to hit #3 — transition borrows instead of consumes**: `complete(&mut self)` mutates in place, so the
    old `Connection<Handshaking>` is still usable after the handshake finishes. Symptom: code holds a stale
    `Handshaking` handle and calls handshake-only methods on an already-established connection — the state machine
    no longer reflects reality.
    - Fix: every transition takes `self` *by value* and returns the new `Connection<NextState>`; the old handle is
      moved out and can't be touched.
    - Muscle: a type-state transition must consume the old state so it can't alias the new one. Reapplies at: W42
      `txn` 2PL lock-state transitions, W73 Engine API state progression.
  - **Expect to hit #4 — open marker trait lets outsiders forge states**: `ConnectionState` is a public trait with
    no seal, so a downstream crate `impl ConnectionState for EvilState` and slips an unintended state into
    `Connection`. Symptom: your exhaustive `impl` coverage has a hole you never wrote; invariants assumed over "the
    three states" silently break.
    - Fix: seal the trait — `mod private { pub trait Sealed {} }`, `ConnectionState: private::Sealed`, impl `Sealed`
      only for your three markers.
    - Muscle: a marker trait that defines a closed set of states must be sealed. Reapplies at: W22 `eth-stage`
      stage set, W42 `txn` isolation-level markers.

- [ ] **Build**: `crates/concurrent/src/channel/bounded.rs` — Vyukov-style MPMC bounded channel. Power-of-2 capacity;
  per-slot `seq: AtomicUsize`; `head` and `tail` cursors each in `CachePadded` (W4 Mon). Producers CAS-then-write the
  slot; consumers CAS-then-read. (~75 min)
  - *Back-of-envelope*: this ring is the substrate for inter-shard messaging (W30 runtime), the matching-engine
    command bus (W58/W63), and aeron's per-publication queue (W77). Target: **send/recv ≈ 30 ns uncontended**,
    scaling near-linearly to ~16 producers/consumers. Power-of-2 capacity → mask index (`idx & (cap-1)`), no
    `%`. Per-slot `AtomicUsize` seq = ~10 ns CAS. Head and tail cursors live in **separate cache lines**
    (`CachePadded<AtomicUsize>` each, W4 Mon — see perf pitfall #5 below). Capacity 1024 → ring + headers
    ≈ 32 KB, fits L1 if hot. Steady-state: zero allocations after construction, zero syscalls (Parker is
    cold-path only).
  - **Expect to hit #1**: you'll accept any capacity. Modulo via `%` produces aliasing when capacity isn't
    power-of-2. Loom fails with "slot N holds two values" within seconds.
    **Fix**: assert power-of-2 in `new()`; use `idx & (cap - 1)` mask, never `%`.
  - **Expect to hit #2**: producer writes the slot data **before** bumping the seq counter, but uses `Relaxed` on
    the counter store. On Apple Silicon (weakly ordered), the consumer observes the counter bump *before* the data
    write and reads uninit. x86 hides this in 100k runs — that's the trap.
    **Fix**: store seq with `Release`; consumer loads seq with `Acquire`. Test under loom (`Acquire`-`Release`
    model, not `SeqCst`).
  - **Expect to hit #3**: two producers observe the same `tail`, both CAS. Loser increments seq and writes to the
    next slot — but it reused the *stale* tail index. Data ends up in the wrong slot.
    **Fix**: every CAS failure restarts from a fresh load. Never reuse the stale observation.
  - **Expect to hit #4**: `recv()` on empty without `Parker`. You'll either burn CPU spinning forever, or add a
    `Mutex<Condvar>` and rediscover the lost-wakeup bug at scale.
    **Fix**: the `Parker` you built in W4 Thu plugs in here. Producer signals via `Unparker` after successful send;
    consumer parks after observing empty.
  - **Muscle**: per-slot sequence-counter dance is the universal lock-free queue. **Reapplies at**: WAL group-commit
    (W26, but unbounded → SegQueue), matching-engine command bus (W63), messaging-aeron term rotation (W77, where
    per-term seq plays the same role).
  - **Expect to hit (perf) #5 — head and tail in the same cache line (bar (c) violation)**: declaring
    `struct Ring { head: AtomicUsize, tail: AtomicUsize, buf: ... }` without padding puts head and tail on
    the same 64 B cache line. Every `send` touches `tail`, every `recv` touches `head` — they false-share;
    each op invalidates the *other* core's cached line. Symptom: criterion bench shows producer throughput
    drops 30-70% the instant a consumer runs on a different core.
    - Fix: `#[repr(C)] struct Ring { head: CachePadded<AtomicUsize>, tail: CachePadded<AtomicUsize>, buf:
      ... }` (W4 Mon). Verify with `offset_of!` that `tail - head ≥ 128`.
    - Cost avoided: 30-70% throughput restoration under producer+consumer contention; eliminates cross-core
      MESI ping-pong on the cursor pair.
    - Muscle: producer and consumer cursors on a lock-free queue **must** be in separate cache lines — the
      canonical CachePadded case. Reapplies at: W26 SegQueue head/tail, W65 Disruptor claim/cursor, W74
      raft term+index pair, W77 aeron term rotation counter pair.

- [ ] **Build**: `crates/eth-trie/src/hashed_state.rs` — HashedPostState mirroring reth_trie. (~105 min)
  - *Mental model*: after a block executes you have a set of changed accounts and storage slots, keyed by *plain*
    address/slot. The trie, however, is keyed by `keccak256` of those keys. `HashedPostState` is that change set
    re-keyed into hashed space — the exact shape the trie walker consumes to recompute the state root. It is a
    *diff*, not a full state: only what the block touched.
  - *Contract*: `HashedPostState { accounts: HashMap<B256, Option<Account>>, storages: HashMap<B256, HashedStorage>
    }` keyed by hashed address. `Option<Account>` distinguishes an updated account (`Some`) from a *destroyed* one
    (`None` → must be removed from the trie). `HashedStorage { wiped: bool, slots: HashMap<B256, U256> }` keyed by
    hashed slot; `wiped` flags a `SELFDESTRUCT`/recreate that clears the whole storage subtrie. Key methods:
    `from_plain_state(changes)` (hashes plain keys in), `extend(other)` (merge a later block's diff over this one),
    `construct_prefix_sets()` (the changed-key set the trie walker needs).
  - *from_plain_state, roughly*: (1) for each changed account, `keccak256(address)` → insert into `accounts`;
    (2) for each changed slot, `keccak256(slot)` → insert into the account's `HashedStorage`; (3) carry the
    destroyed/wiped flags through. Step 2 — getting wipe semantics right when an account is destroyed *and*
    recreated in the same diff — is the real exercise.
  - **Expect to hit #1 — hashing keys at the wrong layer**: you key the maps by plain `Address`/slot and hash only
    when handing data to the trie. Symptom: two call sites hash inconsistently, or `extend` merges a plain-keyed and
    a hashed-keyed map — entries that should collide don't, and the state root is wrong with no panic.
    - Fix: `HashedPostState` is hashed-keyed *by construction*; the only place plain→hashed happens is
      `from_plain_state`, at the boundary.
    - Muscle: pick one key space for a type and convert exactly once, at the constructor. Reapplies at: W20
      `eth-trie` walker, W31 persistent MPT, W35 state commitment.
  - **Expect to hit #2 — destroyed account vs zero-balance account**: you model "account gone" as
    `Some(Account::default())` instead of `None`. Symptom: a self-destructed account stays in the trie as an empty
    account; its hashed-key leaf is never deleted, and the state root diverges from Geth's.
    - Fix: `None` in the `accounts` map means *delete the trie leaf*; `Some(acct)` means *upsert*. The trie walker
      branches on exactly that.
    - Muscle: "absent" and "present-but-empty" are different states — encode them in the type, not by convention.
      Reapplies at: W20 trie deletion, W31 MPT leaf removal.
  - **Expect to hit #3 — `extend` merges storage shallowly / loses the wipe flag**: merging a later block's diff,
    you overwrite `storages` per account-key but ignore that the later diff may carry `wiped: true`. Symptom: a
    block that wipes then re-populates storage merges to a storage map that still contains pre-wipe slots.
    - Fix: `extend` merges per account; when the incoming `HashedStorage.wiped` is set, *clear* the existing slot
      map first, then apply the incoming slots over it.
    - Muscle: merging diffs means honoring delete/wipe markers, not just unioning the live entries. Reapplies at:
      W31 multi-block MPT updates, W79 reorg state-diff merge.
- [ ] **Build**: TrieUpdates struct. (~105 min)
  - *Mental model*: `HashedPostState` is the *input* to a trie recompute; `TrieUpdates` is the *output* — the set
    of intermediate trie nodes that changed (and the ones that were removed) so they can be persisted to the DB
    without rewriting the whole trie. It's the trie's own change set, keyed by node *path* (nibble prefix).
  - *Contract*: `TrieUpdates { account_nodes: HashMap<Nibbles, BranchNodeUpdate>, removed_nodes: HashSet<Nibbles>,
    storage_tries: HashMap<B256, StorageTrieUpdates> }`. `Nibbles` is the packed nibble-path key of a node;
    `removed_nodes` are paths whose node no longer exists. `StorageTrieUpdates` is the same shape for one account's
    storage subtrie, plus an `is_deleted` flag for a wiped subtrie. Key methods: `extend(other)` (compose two
    update sets), `into_sorted()` (yield nodes in path order for sequential DB writes).
  - **Expect to hit #1 — a path in both `account_nodes` and `removed_nodes`**: a node is updated then later
    deleted (or vice versa) and ends up in both collections. Symptom: the DB-write step inserts and deletes the
    same path; final order decides the outcome — flaky, write-order-dependent corruption.
    - Fix: make insert-at-path and remove-at-path mutually exclusive — inserting a path removes it from
      `removed_nodes` and vice versa; assert the invariant in `extend`.
    - Muscle: an update set must keep "written" and "removed" key sets disjoint. Reapplies at: W26 `wal` redo/undo
      records, W31 MPT node persistence.
  - **Expect to hit #2 — `extend` is not last-writer-wins per path**: composing block N's updates with block N+1's,
    you union the maps and a `HashMap::insert` clash keeps an arbitrary node. Symptom: a node touched by both
    blocks persists the *older* version; the on-disk trie lags one block.
    - Fix: `extend` applies `other` *over* `self` — `other`'s node at a path wins, and `other`'s removals win.
    - Muscle: composing ordered diffs is last-writer-wins, and the "writer" is the later diff. Reapplies at: W31
      multi-block trie commit, W79 reorg.
  - **Expect to hit #3 — unsorted nodes cause random-access DB writes**: you persist `account_nodes` by iterating
    the `HashMap` directly. Symptom: writes hit the MDBX/B-tree in hash order, not key order — page splits and
    cache misses everywhere; commit throughput is far below sequential-write speed.
    - Fix: `into_sorted()` returns nodes ordered by `Nibbles` path so the DB sees a sequential, append-friendly
      write pattern.
    - Muscle: bulk writes to an ordered store must be pre-sorted by key. Reapplies at: W27 `storage-trie::mdbx`
      writes, W28 B-tree bulk load, W39 SSTable build.

- [ ] **Build**: `crates/backpressure/Cargo.toml` workspace member. Depends on `time` + `concurrent`. (~20 min)
- [ ] **Build**: `crates/backpressure/src/strategy.rs` — move `BackpressureStrategy` enum from eth-network-codec.
  Variants: `DropOldest`, `DropNewest`, `Block`, `BlockWithTimeout(Monotonic)`, `Spill { dst: Box<dyn SpillSink> }`. (~45 min)
  - *Mental model*: when a bounded queue is full, *something* must give — the strategy is the *policy* for what.
    `BackpressureStrategy` is that policy as a closed enum: drop the oldest item, drop the newest, block the
    producer, block with a deadline, or spill overflow somewhere else. The queue is the mechanism (the MPMC built
    Tuesday); this enum picks the behavior.
  - *Contract*: `enum BackpressureStrategy { DropOldest, DropNewest, Block, BlockWithTimeout(Monotonic),
    Spill { dst: Box<dyn SpillSink> } }`, where `Monotonic` is the W6 `time` crate's monotonic duration type. One
    method — `fn on_full<T>(&mut self, queue: &mut impl Queue<T>, item: T) -> Outcome<T>` (or similar) — applies
    the policy and reports what happened (accepted / dropped / would-block). Carries no queue itself.
  - *Back-of-envelope*: `on_full` is called whenever a producer hits a full queue — on a bursty source, the
    common case, not the exception. Target: single match + at most one indirection (Spill variant only).
    Drop/Block variants compile to a couple of conditional moves (~2-5 ns). The strategy is *not* on the
    steady-state path of a non-full queue — that's accept-and-return, no strategy invocation. Optimizing
    `on_full` itself is secondary; **the perf trap is the `Box<dyn>` in the `Spill` variant** (see perf
    pitfall below).
  - **Expect to hit #1 — `#[derive(Clone)]`/`Copy` on the enum**: the `Spill` variant holds a `Box<dyn SpillSink>`,
    which is neither `Copy` nor (usually) `Clone`. Symptom: `error: the trait Clone is not implemented for
    Box<dyn SpillSink>` the moment you derive `Clone` for the whole enum.
    - Fix: don't derive `Copy`/`Clone`; if a clone is genuinely needed, require `SpillSink: Clone` via a
      `dyn-clone`-style helper, or hand the strategy around by `&mut`.
    - Muscle: a trait-object field makes the whole enum lose the auto-derives the simple variants would allow.
      Reapplies at: W14 `bufpool` policy enum, W76 messaging-aeron flow-control config.
  - **Expect to hit #2 — moving the dropped item out cleanly**: `DropOldest` must evict and *return* (or drop) the
    old item; `on_full` consumes `item` by value. Symptom: borrow-checker fights — "cannot move out of `item`
    because it is borrowed", or you accidentally drop the new item when you meant the old one.
    - Fix: make `on_full` take `item: T` by value and return an `Outcome<T>` that carries whichever item was
      evicted, so ownership is explicit at every branch.
    - Muscle: a policy that may drop one of two values must make ownership of the loser explicit in its return
      type. Reapplies at: W11 Thu MPMC overflow path, W76 aeron drop accounting.
  - **Expect to hit (perf) #1 — `Box<dyn SpillSink>` vtable call on every Spill (bar (c) violation)**: the
    `Spill { dst: Box<dyn SpillSink> }` variant dispatches through a vtable on every call — ~5 ns extra per
    call vs a direct call, *plus* LLVM cannot inline the spill body across the dyn boundary. For a
    Spill-strategy queue under burst, hundreds of vtable jumps/sec on the overflow hot path.
    - Fix: for monomorphic use sites (matching-engine, aeron), be generic over `S: SpillSink` instead of
      `Box<dyn>`. Keep the `Box<dyn>` variant for the dynamic / config-driven case (W14 `bufpool`) but
      document the perf trade-off in `DESIGN.md`.
    - Cost avoided: ~5 ns per call + enables LLVM to inline the spill body (often 5-10× total speedup on
      tight `spill()` impls).
    - Muscle: `dyn` is the price of runtime polymorphism — pay it where you need it, not by default.
      Reapplies at: W14 `bufpool` policy enum, W26 `wal` sink, W76 aeron flow-control config.
- [ ] **Build**: `crates/backpressure/src/sink.rs` — `SpillSink` trait: where to dump on overflow (used by
  messaging-aeron W76 to spill to disk via wal). (~105 min)
  - *Mental model*: the `Spill` strategy needs somewhere to put overflow items so they aren't lost. `SpillSink` is
    that destination, abstracted — an in-memory ring today, a `wal`-backed disk file at W76 — so the queue doesn't
    care where overflow goes. It's the "overflow drain" interface.
  - *Contract*: `trait SpillSink: Send` with `fn spill(&mut self, bytes: &[u8]) -> Result<(), SpillError>` (push
    one overflow item) and `fn drain(&mut self) -> Option<Vec<u8>>` (pull a spilled item back when the queue has
    room). Object-safe — it is used as `Box<dyn SpillSink>` inside the `Spill` variant. Ship one concrete impl now
    (e.g. `VecSpillSink`); W76 adds the `wal` impl.
  - *Back-of-envelope*: every `spill()` is by definition during burst, not steady state. Target: ≤ 200 ns per
    spill (disk-backed impls hand off to a background writer asynchronously — synchronous I/O is hundreds of
    µs, way too slow for the spill hot path). Steady state: zero spill calls. **The critical bar: `spill()`
    must not allocate** — if an impl does `Vec::from(bytes)` per call, a 10 k-item burst allocates 10 k Vecs
    and crushes the allocator on the *exact* path designed to absorb pressure cheaply (see perf pitfall).
  - **Expect to hit #1 — non-object-safe trait**: you add a generic method (`fn spill<T: Serialize>(…)`) or a
    `Self`-returning method. Symptom: `error: the trait SpillSink cannot be made into an object` — the `Box<dyn
    SpillSink>` in `strategy.rs` fails to compile.
    - Fix: keep every method non-generic and `Self`-free; spill *bytes* (`&[u8]`), and let callers serialize before
      the boundary.
    - Muscle: a trait used behind `dyn` must stay object-safe — no generic methods, no `Self` returns. Reapplies
      at: W26 `wal` sink trait, W76 aeron spill-to-disk.
  - **Expect to hit #2 — spill order not preserved on drain**: `drain` returns items in a different order than
    they were spilled (e.g. a LIFO `Vec::pop`). Symptom: under a `Spill` strategy, items come back out of order;
    a FIFO queue silently becomes partly LIFO and downstream sequencing breaks.
    - Fix: decide and document the contract — for a FIFO queue, `SpillSink` must be FIFO too (`VecDeque`, not
      `Vec::pop`); test spill-then-drain preserves order.
    - Muscle: an overflow buffer must preserve the ordering guarantee of the queue it backs. Reapplies at: W26
      `wal` replay order, W76 aeron in-order spill replay.
  - **Expect to hit (perf) #1 — per-spill `Vec` allocation (bar (c) violation)**: the trait signature
    `spill(&mut self, bytes: &[u8])` invites every impl to `Vec::from(bytes)` to take ownership. Under burst
    (10 k overflow items/sec), that's **10 k Vec allocations/sec** on the *overflow* hot path — the exact
    path designed to absorb pressure cheaply.
    - Fix: design impls to use a pre-allocated ring or arena. `VecSpillSink` holds a fixed-size
      `VecDeque<Vec<u8>>` with per-slot pre-allocated buffers; `spill` does `slot.clear();

      into an `mmap`'d region — even cheaper.
    - Cost avoided: ~50 ns malloc + cache pollution per spill; at 10 k spills/sec → ~500 µs/sec
      reclaimed per Spill-strategy queue.

      the impl can avoid the copy — or provide a pre-allocated buffer pool at construction. Reapplies at:

- [ ] **Build**: `crates/backpressure/src/credit.rs` —
  `CreditFlowControl { credits: AtomicU64, low_water: u64, high_water: u64 }` — used by messaging-aeron flow control AND
  matching-engine inbound queue. (~150 min)
  - *Mental model*: credit-based flow control is the opposite of "push then drop" — a sender may only send while
    it holds credits. The receiver *grants* credits as it drains its buffer; the sender *consumes* one per message.
    Watermarks add hysteresis: the receiver replenishes credits in a batch when the count falls to `low_water`, and
    a sender is throttled until credits climb back toward `high_water`. This is `messaging-aeron`'s flow control and
    `matching-engine`'s inbound admission control.
  - *Contract*: `CreditFlowControl { credits: AtomicU64, low_water: u64, high_water: u64 }`. Sender side:
    `fn try_acquire(&self) -> bool` — atomically take one credit if available. Receiver side:
    `fn release(&self, n: u64)` — return credits after draining; `fn should_grant(&self) -> bool` — true when
    `credits <= low_water`, the cue to top up toward `high_water`. All state lives in the one `AtomicU64`; no lock.
  - *try_acquire, roughly*: (1) load `credits`; (2) if `0`, fail; (3) CAS `credits → credits - 1`; (4) on CAS
    failure, *reload* and retry. The retry-on-fresh-load — never decrementing a value you didn't just observe —
    is the real exercise.
  - *Back-of-envelope*: `try_acquire` is on the *send* hot path — every producer call. Target: **one atomic
    op (~10 ns)**, no CAS retry under normal load. `release` is called per drained item or batched —
    equally hot. Watermark check `should_grant` is a cheap atomic load + compare (~5 ns). All state in one
    `AtomicU64`, so check + decrement happen in one CAS — but that one atomic is the scalability ceiling;
    under N producers it scales as O(N²) (see perf pitfall below). For W76 messaging-aeron, where
    per-stream credit is checked at thousands of pubs/sec across many publishers, this matters.
  - **Expect to hit #1 — check-then-act race on credits**: `try_acquire` does `if credits.load() > 0 {
    credits.fetch_sub(1) }`. Two senders both see `1`, both `fetch_sub`, and the counter wraps to `u64::MAX`.
    Symptom: under load, credit count suddenly explodes to a huge number — every sender thinks it has unlimited
    credit; flow control silently disabled. x86 may hide it; Apple Silicon surfaces it fast.
    - Fix: make acquire one atomic step — a `fetch_update`/CAS loop that only decrements the *exact* value it just
      loaded, and fails (no decrement) when that value is `0`.
    - Muscle: load-then-modify on an atomic is not atomic — collapse check-and-decrement into one CAS. Reapplies
      at: W11 Tue MPMC cursor CAS, W26 SegQueue claim, W37 skiplist CAS, W65 Disruptor sequence claim.
  - **Expect to hit #2 — watermark oscillation (no hysteresis)**: you grant credits whenever `credits < high_water`
    and stop the moment it reaches `high_water`. Symptom: the count chatters right around `high_water` — grant /
    consume / grant / consume — producing a burst of tiny grant messages instead of one batch; throughput sawtooths.
    - Fix: two distinct thresholds — only *start* granting when `credits <= low_water`, and grant up to
      `high_water` in one batch; the `low..high` gap is the hysteresis band that absorbs the chatter.
    - Muscle: a replenish-on-threshold control needs two watermarks (a band), never one, or it oscillates.
      Reapplies at: W14 `bufpool` refill, W34 `bloom`/pruning trigger, W76 aeron credit grant batching.
  - **Expect to hit #3 — wrong memory ordering on the credit counter**: you use `Relaxed` for both `try_acquire`
    and `release`, but a released credit also *publishes* the buffer space it represents. Symptom: a sender
    acquires a credit and writes into a slot the receiver hasn't actually finished draining — a data race on the
    slot; loom/miri flags it, x86 doesn't.
    - Fix: `release` (which makes buffer space visible) stores with `Release`; `try_acquire`'s successful CAS uses
      `Acquire` (or `AcqRel`) so the slot it just "won" is observed only after the receiver's drain is visible.
    - Muscle: a credit counter that gates access to a buffer carries a happens-before edge — `Release` on grant,
      `Acquire` on take. Reapplies at: W11 Tue MPMC seq counter, W26 `wal` group-commit publish, W65 Disruptor
      cursor.
  - **Expect to hit #4 — credit leak / over-release**: a sender that fails *after* `try_acquire` never returns its
    credit, or `release` is called with a count larger than was consumed and `credits` exceeds `high_water`.
    Symptom: either credits slowly bleed to zero and senders permanently stall, or the count drifts above
    `high_water` and the watermark logic never triggers.
    - Fix: pair every `try_acquire` with a guaranteed `release` (an RAII `CreditGuard` that releases on `Drop`);
      clamp `release` so `credits` never exceeds `high_water`.
    - Muscle: a credit is a resource — acquire and release must be balanced, ideally by RAII. Reapplies at: W14
      `bufpool` buffer lease, W42 `txn` lock acquire/release, W76 aeron credit accounting.
  - **Expect to hit (perf) #1 — single-`AtomicU64` contention under N producers (bar (c) violation)**: every
    producer hammers one `AtomicU64`. At N=16 producers, throughput collapses to ~1/N² of single-threaded —
    classic single-line contention. Symptom: criterion bench scales linearly to 2-4 threads, plateaus, then
    *decreases* with more threads as MESI traffic dominates.
    - Fix: shard the credit. **Per-shard credit counters** under runtime-thread-per-core (W30): each shard
      has its own credit pool, replenished from a global pool only when local drops below `low_water`. Local
      `try_acquire` is uncontended (~5 ns). Cross-shard rebalance is the rare path. Same pattern as Java's
      `LongAdder` vs `AtomicLong`.
    - Cost avoided: linear scaling vs O(N²) collapse; at 16 producers, ~10× throughput recovery; eliminates
      MESI ping-pong on the credit cache line.
    - Muscle: a single atomic counter is a scalability ceiling — shard it the moment N exceeds 2-4 threads.
      Reapplies at: W30 runtime per-shard counters, W42 `txn` MVCC version (sharded), W76 aeron per-stream
      flow control.
