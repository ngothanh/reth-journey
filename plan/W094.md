  - **Expect to hit (perf) #1 — read-only globals (`COINBASE`, `BLOCKHASH`, `TIMESTAMP`) treated as conflict-tracked (bar (c) violation, headline kill)**: every tx in a block reads `BLOCKHASH` and `COINBASE`. If those reads are recorded in RwSet, every tx "conflicts" with every other tx that "wrote" them (no one writes them within a block — they're per-block constants). The validator sees N×N pseudo-conflicts, re-executes everything, and **speedup goes to ~0.5× even on a DEX-pure low-conflict block**. The fix is not "tune the scheduler" — it's recognizing block-level constants as a class.
    - Fix: per-block "read-only globals" registry — a `FixedSet<StorageKey>` populated at block-prelude with the keys of `BLOCKHASH`, `COINBASE`, `TIMESTAMP`, `DIFFICULTY`, `GASLIMIT`, `CHAINID`, etc. RwSet's `record_read(key)` checks the registry first; if hit, the read does **not** enter `reads` (no conflict edge added). Reads to these keys go directly to a pre-seeded `Value` entry visible to all tx_idx.
    - Cost avoided: speedup recovery from ~0.5× → ~2-3× on low-conflict blocks — the headline SHIP gate (`8-core low-conflict speedup ≥2.0×`) is unattainable without this. Without the read-only globals classification, block-stm is theoretically correct but practically useless.
    - Muscle: in any optimistic-concurrency system, identify the "constants" (block-level, session-level, immutable-after-init) and exclude them from conflict tracking. Reapplies at: W94 hot-key classification (extension: per-block frequency analysis), W88 ledger VOPR `lookup` op (read-only — never conflicts with any other op), W74 matching-engine static reference data (symbol metadata, never conflicts with order flow), W82 matching-engine STP exemption rules.
  - **Expect to hit (perf) #2 — `rayon::scope` worker startup cost amortized across small block (bar (c) violation, hidden)**: each block exec spawns `rayon` workers via `rayon::scope(|s| ...)`. The first call materializes the thread-pool (~500 µs on cold startup); subsequent calls have ~50 µs scope-setup cost (cross-thread queue init, work-item enqueue). For a small block (~50 txs, sequential exec ~24 ms), 50 µs scope-setup = 0.2% overhead — fine. For a tiny block (~10 txs, sequential ~5 ms), 50 µs = 1% — still fine. But if `rayon::scope` is called **per validation phase** (i.e., re-execution loop), the 50 µs accumulates: 5 re-exec rounds × 50 µs = 250 µs added to a 5 ms block = **5% overhead per worker scope spawn**, and the optimizer can't elide it because the worker closures vary.
    - Fix: a single long-lived thread pool (rayon's global pool initialized at exec-vm startup; or a hand-built `crossbeam_channel::bounded` pool of N workers). The block-stm scheduler enqueues tx-exec tasks via a non-blocking `Sender`; workers in a `recv()` loop pick them up. Per-block setup: 0 ns (workers already running). Re-execution: just enqueue another task — ~5 ns per enqueue.
    - Cost avoided: ~250 µs/block scope-setup → ~0 ns. On the bench rig: ~5% throughput recovery; combined with perf #1 above, makes the ≥2× speedup gate achievable consistently rather than "on the median block."
    - Muscle: any "spawn workers, do work, join" pattern is a perf trap if called inside a hot loop. Worker pools live for the process lifetime; tasks flow through queues. Reapplies at: W88 VOPR runner (workers spawned once at startup, scenarios flow via stdin), W90 io_uring journal (the ring is set up once, writes flow per-call), W82 matching-engine shard threads (per-symbol shards pinned at startup, orders flow via submit_to).

         (i) **"Walk me through how a single tx executes in your parallel EVM."**
             Worker pool picks next tx_idx N. Worker creates RwSet for incarnation 0. Executes tx, recording all SLOAD into reads (with Version observed) and SSTORE into writes (tagged (N, 0)). On completion, transitions tx to Validation. Validator re-runs reads against current MultiVersionStore; if any read's Version is stale (someone wrote higher version after we read), conflict detected → re-execute at incarnation 1. Repeat until validation passes; then tx is Committed.

N+1 is re-executed at incarnation+1; new read sees N's write. Cost: one wasted exec per conflict. Worst case (all-write-same-key): degenerates to sequential. Mitigation: hot-key classification + sequential fallback.

   11. **The "every dep was a deliberate choice" justification log** (record in `notes/exec_vm_v1_5_dep_choices.md`):
       - **exec-vm v1.0 as base, NOT a fork**: v1.5 is the SAME crate with a feature flag, not a parallel-evm crate. Why: avoids divergence; sequential path is always available; CI runs both.
       - **dashmap over std::sync::Mutex<HashMap>**: dashmap's bucket-level locking is essential for hot-key contention. Mutex<HashMap> would serialize ALL slot accesses.
       - **rayon over manual thread pool**: rayon's work-stealing handles the dynamic re-execution well; manual pool would require its own scheduler. Cost: rayon's panic semantics need careful handling — wrap in catch_unwind.
       - **BTreeMap per slot over crossbeam_skiplist**: BTreeMap is simpler; profiling showed slot-level lock contention was already low after dashmap. Keep complexity bounded.
       - **MAX_VERSIONS = 256**: bounded memory; pathological blocks fall back to sequential. 256 chosen empirically — covers 99.9% of mainnet blocks.
