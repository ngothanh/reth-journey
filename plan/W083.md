- [ ] [HFT] Polish ledger-deterministic: snapshot/restore + replay test. 1M transfers, crash mid-batch, recovery yields
  byte-identical state. (~45 min)
  - **Why**: ledger v0.5 is the deterministic-SM baseline. v0.7 will layer VOPR on top; v1.0 will layer static-mem + io_uring + VSR. The byte-identical-recovery property is the load-bearing axiom: every later module assumes `apply(op_stream)` after crash produces the SAME state hash regardless of when the crash happened. Mirror TigerBeetle: their `state_machine.zig` apply is intentionally allocation-free + clock-free so the WAL replay always converges.
  - **Read first**: TigerBeetle `lib/tigerbeetle/src/state_machine.zig` — esp. `commit()` and `prefetch()` separation; `lib/tigerbeetle/src/lsm/forest.zig` for snapshot pinning semantics.
  - **Design**:
    ```rust
    pub trait StateMachine {
        type Op: Sized + 'static;
        type Result: Sized + 'static;
        fn apply(&mut self, op: &Self::Op) -> Self::Result;
        fn snapshot(&self, sink: &mut dyn Write) -> io::Result<()>;
        fn restore(&mut self, src: &mut dyn Read) -> io::Result<()>;
        fn state_hash(&self) -> [u8; 32];
    }
    pub struct LedgerSM {
        accounts: FixedMap<AccountId, Account>, // open-addressed, capacity-bound
        journal_seq: u64,                       // monotonic op counter
    }
    ```
    **Invariants**: (i) `apply` is total (no panics, no allocs), (ii) `apply` is pure of wall-clock — any time-like input must be in `op`, (iii) `state_hash()` is canonical (order-independent for accounts, journal_seq included).
  - **Back-of-envelope**: v0.5 target P99 apply <10 µs; recovery 1M ops <2s on M2 → 2 µs/op replay (faster than apply because no fsync). Per-op fast-path: Transfer = 2× FixedMap lookup (~50 ns each cache-warm at N=10k accounts) + balance check (~5 ns) + 2× balance update (~10 ns) = ~120 ns SM apply; + wal append/fsync amortized via group commit ~3 µs/op = ~3.5 µs total → comfortable under 10 µs. state_hash for 1M accounts: BLAKE3 over sorted (id, balance, version) tuples ≈ 1M × 48 B = 48 MB hashed at 3 GB/s = ~16 ms. Snapshot at every 100k ops costs ~16 ms but saves 100k op replay (~200 ms) on recovery — net win. Memory budget at v0.5: 1M accounts × 80 B Account = 80 MB; FixedMap load factor 0.7 → 115 MB heap. Pre-allocated at startup; no growth during apply.
  - **Build steps**: 1. (~5 min) freeze the `Op` enum: `CreateAccount {id, init_bal}`, `Transfer {from,to,amt}`, `Lookup {id}`. 2. (~10 min) write the byte-identical-recovery harness: drive 1M Transfers, kill at random sequence k, replay WAL, assert `state_hash_pre_crash == state_hash_post_restore`. 3. (~10 min) add the snapshot-then-replay variant: snapshot at seq k/2, crash, restore-from-snap + replay tail. 4. (~10 min) wire `state_hash` (BLAKE3 over sorted (id, balance, version) tuples + journal_seq). 5. (~10 min) capture proptest seed on failure for re-run.
  - **Pitfalls**: *HashMap-iteration nondeterminism*: **Symptom**: snapshot diff between machines despite identical op stream. **Fix**: never iterate `std::collections::HashMap` in state_hash — sort keys or use BTreeMap/FixedMap with stable order. *SystemTime leak*: **Symptom**: replay diverges between runs on same machine. **Fix**: ban `Instant::now()`/`SystemTime::now()` in `apply`; clock must be in `op`. *Allocator fragmentation*: **Symptom**: identical ops, identical hash, but different `RSS` causing OOM differently across replicas. **Fix**: pre-size every Vec/HashMap at construction; deny `Box<dyn ...>` on hot path.
  - **Expect to hit (perf) #1 — `state_hash` allocates a fresh `Vec<(id, balance, version)>` to sort (bar (c) violation)**: naive `let mut tuples: Vec<_> = self.accounts.iter().map(|(k, v)| (*k, v.balance, v.version)).collect(); tuples.sort(); blake3(tuples)` allocates 1M × 32 B = 32 MB on every state_hash call. If state_hash is called per-op-batch for VOPR (W87) at 10 batches/sec = 320 MB/sec allocator churn. Worse: `.collect()` reallocates as Vec grows from initial capacity (typically several doublings = ~3× total bytes touched). Symptom: heaptrack shows 32 MB Vec spikes per state_hash; VOPR scenarios slow 4× due to allocator pressure. Fix: pre-allocate a `tuples: Vec<(u64, u64, u64)>` once at SM construction with capacity = max_accounts; `state_hash` calls `tuples.clear()` + `extend(iter)` + `sort()` + `blake3(tuples.as_slice())`. Zero allocs in steady state. Or use a FixedMap with sorted iteration (`BTreeMap`) for O(1) sorted iter, no sort step. Cost avoided: 32 MB/call × 10 calls/sec = 320 MB/sec churn → 0 alloc; restores VOPR scenario throughput. Muscle: hash/checksum operations on collections reuse a pre-allocated scratch buffer — never `.collect()` inside the hash function. Reapplies at: W84 archive replay checksum, W87 VOPR property check (computes state_hash 10M times/scenario), W92 ledger v1.0 SHIP audit (state_hash must be zero-alloc).
  - **Expect to hit (perf) #2 — recovery replay re-fsyncs each op (bar (c) violation)**: design says "recovery replay throughput ≥10× apply throughput (recovery is fast)" — but a naive recovery loop calls `sm.apply(op); wal.append(op); wal.fsync();` per op (treating replay like fresh apply) → recovery is at SAME speed as apply (~300 µs/op with fsync), so 1M ops = 5 min recovery — failing the <2s target by 150×. Symptom: kill -9 + restart of a 1M-op ledger takes minutes; production failover SLA blown. Fix: recovery NEVER writes wal (the wal is what it's reading FROM) — it just `sm.apply(op)` for each entry. No fsync, no append. 1M ops × 120 ns SM apply = 120 ms total — comfortably under 2s. The crash-recovery harness should explicitly disable wal writes during replay; assert `wal.append_count_during_recovery == 0`. Cost avoided: ~300 µs/op → ~120 ns/op = 2500× speedup; recovery time drops from minutes to milliseconds. Muscle: replay/recovery paths skip durability (the data is already durable in the source) — read-only sweep of the apply logic. Reapplies at: W84 archive replay (reads, never writes back), W87 VOPR recovery scenarios, W88 consensus-vsr follower catch-up, W92 ledger v1.0 SHIP recovery test.
  - **Test scenarios**: 1M Transfer stream with seed-controlled RNG; crash at uniformly random k ∈ [0,1M); after restore, replay rest; property: pre/post hashes match for ALL k. Adversarial: snapshot taken DURING write of `accounts[X]` should never observe torn-write (snapshot must drain in-flight first).
  - **Acceptance**: 100/100 random crash points yield identical state_hash; snapshot size O(active_accounts); recovery wall-time <2s for 1M ops on M2.
  - **Downstream**: v0.7 VOPR (W87) reuses this `StateMachine` trait as the system-under-test; v1.0 (W89-W92) wraps `apply` in static-mem pools + io_uring journal + VSR replication.

- [ ] [NEW v2] **Build**: `crates/messaging-aeron/src/archive.rs` — stream recording layer: every published frame is
  also written to `mmap-queue::Cycle`. (~3 hrs)
  - **Why**: Aeron Archive is the on-disk, replayable history that distinguishes Aeron from a pure in-memory bus. Without it, a late subscriber (or a forensic replay) has nothing to read; with it, we can rewind from any byte offset. Upstream Aeron's Archive uses a separate process; we co-locate recording into the Publication's `offer()` hot-path because we already own `mmap-queue::Cycle` and the extra mmap-store cost is amortized.
  - **Read first**: Aeron `aeron-archive/src/main/java/io/aeron/archive/Archive.java` — esp. RecordingWriter and term-buffer scan; `aeron-archive/src/main/cpp/client/AeronArchive.cpp` for client-side recording API.
  - **Design**:
    ```rust
    pub struct ArchiveRecorder<'a> {
        cycle: &'a mut mmap_queue::Cycle,           // append-only persistent log
        recording_id: u64,                          // (stream_id << 32) | session_id
        last_position: AtomicU64,                   // matches Publication term position
    }
    impl ArchiveRecorder<'_> {
        pub fn on_frame(&mut self, term_offset: u64, frame: &[u8]) -> Result<(), ArchiveErr>;
    }
    pub struct ArchiveOffset(u64); // monotonic across rotations
    ```
    **Invariants**: (i) frame written to mmap-queue BEFORE Publication's term-position advances (so a subscriber's tail can't observe a frame whose recording is incomplete), (ii) `ArchiveOffset` strictly monotonic across term-buffer rotations, (iii) crash mid-record leaves a tail that recovery::truncate can recover from cleanly.
  - **Back-of-envelope**: acceptance gate is "≤15% overhead to offer() P99." Publish baseline ~360 ns (W79 MBO budget); 15% = 54 ns extra → archive frame write budget ~50 ns. Cost: mmap-queue Cycle is a pre-allocated mmap with append cursor; append = (i) bounds check (~1 ns), (ii) memcpy frame payload (~30 ns for 256 B at L1 bandwidth), (iii) write length+crc header (~10 ns), (iv) AtomicU64 cursor advance (~5 ns) = ~46 ns budget MET. crc32c at hardware-accelerated `_mm_crc32_u64` ≈ 8 B/cycle ≈ 30 ns for 256 B. Lag gauge sample rate: 1/100 µs = 10 kHz → cheap. fsync policy: `WriteThrough` = ~5 ms fsync per batch × batched 100 frames per 1ms tick → 5% throughput tax (acceptable for VOPR scenarios); `WriteBack` = 0 fsync (relies on kernel writeback every 30s) → 0 tax but window of data loss on crash. Rotation: 1 GiB Cycle file rotates every ~30 sec at 30M frames/s (or every hour at 100k frames/s); rotation is atomic rename + symlink swap (~1 ms) — pre-create next file in background to avoid in-line cost.
  - **Build steps**: 1. (~20 min) thread `Option<&mut ArchiveRecorder>` through `Publication::offer()`; gate via `with_archive` builder. 2. (~30 min) implement `on_frame` writing `[recording_id|term_offset|len|payload|crc32]` into Cycle. 3. (~20 min) crc verification stub + tail-truncation on corrupted tail. 4. (~30 min) write the recording-lag gauge: lag = publication_position - archive_position; export via `metrics`. 5. (~30 min) implement term-buffer-rotation handoff: on rotate, emit `RecordingDescriptor` sentinel record. 6. (~30 min) fsync policy: choose `WriteThrough` (call fsync per batch, default 1ms) vs `WriteBack` (rely on kernel writeback) — feature flag. 7. (~20 min) retention rotation: when Cycle reaches max bytes, rotate to next file, update descriptor index.
  - **Pitfalls**: *Recording lag*: **Symptom**: archive_position falls behind publication_position under burst, late subscriber sees a gap. **Fix**: backpressure publication on archive lag > N MB (use `backpressure` crate). *Fsync policy mismatch*: **Symptom**: claimed durability but crash loses last 5ms. **Fix**: document policy explicitly; for VOPR scenarios mandate WriteThrough. *Retention rotation race*: **Symptom**: subscriber replaying across rotation boundary reads stale file. **Fix**: rotation atomic via rename + symlink swap; recorder publishes new descriptor before deleting old. *Partial-frame at boundary*: **Symptom**: crash mid-write leaves N-byte trailing fragment, replay reads garbage. **Fix**: framed length prefix + tail crc; truncate to last valid frame on open.
  - **Expect to hit (perf) #1 — software crc32c instead of hardware `_mm_crc32_u64` (bar (c) violation)**: a typical first-pass uses the `crc32c` Rust crate's portable software impl: ~1 GB/s = ~250 ns for 256 B frame. Hardware-accelerated `CRC32` (SSE4.2 / aarch64 CRC) is ~12 GB/s = ~20 ns for 256 B — 12× faster. At 1M frames/sec, software crc costs 250 ms/sec; hardware 20 ms/sec — frees 230 ms/sec of a critical-path core. Symptom: archive recording adds ~30% overhead to offer() instead of 15%; CPU flamegraph shows ~20% in crc32c software. Fix: gate on `target_feature = "sse4.2"` (x86) or `target_feature = "crc"` (aarch64) and use the intrinsic via `std::arch::x86_64::_mm_crc32_u64` / `std::arch::aarch64::__crc32d`. The `crc32fast` and `crc32c` crates auto-detect at runtime; pre-select at compile time for bar (c). Cost avoided: ~230 ns/frame × 1M frames/s = ~230 ms/sec; restores offer() within the 15% archive-overhead budget. Muscle: any hot-path hash/checksum on a bar-(c) crate uses the hardware accelerator — don't rely on the library's runtime detection. Reapplies at: W83 ledger journal crc32c, W84 archive replay verify, W92 ledger v1.0 io_uring buffer crc. Also: BLAKE3 should use `blake3` crate's AVX-512 path on AMD/Intel server chips (~6 GB/s vs ~1 GB/s scalar).
  - **Expect to hit (perf) #2 — pretoucher absent from archive Cycle file (bar (c) violation)**: archive writes ~200 MB/s sustained; the Cycle's mmap grows past page boundaries every 4 KiB / 256 B/frame = every 16 frames. Each new page triggers a minor page fault ~1 µs in the publisher's offer() critical path. At 1M frames/sec, every 16 µs there's a ~1 µs page-fault spike — P99 latency tail dominated by faults. The W77 Mon Pretoucher exists EXACTLY for this; archive Cycle MUST register itself with a Pretoucher worker thread. Symptom: archive-enabled offer() P99.9 shows 3-5 µs spikes every 16 µs; P99 fine but P99.9 fails the 15% overhead acceptance gate. Fix: when creating the ArchiveRecorder, spawn a Pretoucher with `pretouch_ahead = 64 pages` paired to the recorder's current tail (read from `last_position`). The pretouch worker stays ahead of the writer by 256 KiB, faulting pages on a background thread. Cost avoided: ~1 µs page-fault spike eliminated from offer() critical path; restores P99.9 budget. Muscle: any growing mmap on a bar-(c) write path MUST be paired with a pretoucher — the W77 Mon principle is non-negotiable. Reapplies at: W92 ledger v1.0 io_uring journal (uses io_uring's pre-registered buffers + pretoucher for the journal file), W90 marketdata-kernelbypass AF_XDP UMEM pretouch.
  - **Test scenarios**: write 1M frames, kill -9 mid-rotation, restart, verify exactly N valid frames recovered with no torn frame; concurrent reader at rotation boundary sees gapless stream; lag-gauge alarms when recorder paused for >100ms.
  - **Acceptance**: recording adds ≤15% overhead to `offer()` p99; archive_position lag <1ms at 1M frame/s sustained; W84 replay byte-identical to original publication.
  - **Downstream**: W84 Wed `archive.replay()` reads this Cycle; ledger v0.7 VOPR (W87-W88) uses Archive as the persistent journal for replication scenarios; consensus-vsr v1.0 uses it as the cross-replica WAL.

- [ ] [NEW v2 runtime v1.0] **Build**: zero-alloc audit on Reactor::poll() — every hot path replaced with pre-allocated
  buffers. (~120 min)
  - **Why**: runtime-thread-per-core v1.0 ships next week (W85 Thu). For "bar (c) VOPR-grade" the reactor poll loop MUST be allocation-free so memory pressure cannot starve a hot core nor introduce nondeterminism into replays. TigerBeetle's runtime is allocation-free by construction; mirror that. The audit is the gate, not a stylistic check.
  - **Read first**: `crates/runtime-thread-per-core/src/reactor.rs` — current Reactor::poll(); also Glommio's `local_executor.rs::run_one_task()` for reference of how a thread-per-core executor stays alloc-free.
  - **Design**:
    ```rust
    pub struct Reactor {
        ready: ArrayVec<TaskId, 4096>,            // bounded ready queue
        timer_wheel: HierarchicalWheel<32, 8>,    // pre-allocated buckets
        io_completions: ArrayVec<Completion, 256>, // matches io_uring CQE batch
        scratch: ScratchBuffer,                   // reused per iteration
    }
    impl Reactor {
        pub fn poll(&mut self) -> PollOutcome { /* must not alloc */ }
    }
    ```
    **Invariants**: (i) `poll()` invokes ZERO `alloc::alloc` (verified by `dhat` heap counter delta = 0), (ii) every container is bounded by const generics or arena, (iii) error paths use `&'static str` codes, never `format!`/`String::from`.
  - **Back-of-envelope**: `Reactor::poll()` runs in a tight loop, 10M+ iterations/sec on a hot core. Single `malloc` (~50 ns minimum, ~200 ns under contention) × 10M = ~500 ms to 2 s/sec of pure allocator overhead — saturates one core entirely. One `format!` in an error path (~300 ns including drop) × 100k errors/sec = ~30 ms/sec. The "zero-alloc audit" target is 0 allocs per poll, verified by `dhat`. Under that, poll() consists of: (i) check timer wheel for due tasks (~10 ns L1 array load), (ii) check io_completions ring (~10 ns SPSC dequeue), (iii) check ready queue (~5 ns ArrayVec pop), (iv) dispatch chosen task's `Future::poll` (~variable, but the runtime layer adds ~20 ns of indirection). Total runtime overhead per task wakeup: ~50 ns. The 4000+ runtime-hour target by M36 means accumulated allocs over 4000 hr × 3600 s × 10M polls/s = 1.4e14 polls — any leak >0.001/poll is detectable; any growth pattern (slow leak) is catastrophic.
  - **Build steps**: 1. (~15 min) instrument `dhat` heap profiler around 10M iterations of `poll()`; record baseline alloc count. 2. (~20 min) audit all `Box<dyn Future>` sites; replace with enum-dispatched `TaskFuture` (use `enum_dispatch` or hand-written enum). 3. (~20 min) audit `format!`/`String` in error paths; replace with `&'static str` error codes. 4. (~20 min) audit Vec growth on hot path — replace with `ArrayVec` or pre-grown Vec with capacity check. 5. (~20 min) audit closures captured by `Box<dyn FnOnce>`; convert to typed closures or `SmallBox<dyn FnOnce, 64>`. 6. (~15 min) re-run dhat; expect delta=0 over 10M iterations. 7. (~10 min) commit a regression guard test: assert `dhat::alloc_count_delta() < 10` over 1M poll iterations.
  - **Pitfalls**: *Hidden alloc via trait object*: **Symptom**: `tracing::event!` macro internally Box-es spans. **Fix**: gate hot-path tracing behind `cfg(not(release_alloc_audit))` or use `tracing::span_enabled!` shortcut. *format! in error*: **Symptom**: passes happy-path audit, fails under fault injection because error path formats. **Fix**: hold a static `&'static str` table or use `thiserror` with no string interp. *Closure-capture box*: **Symptom**: `spawn(move || ...)` boxes the future when type is opaque. **Fix**: spawn via `spawn_typed::<MyFut>(fut)` with concrete type or rely on enum-dispatch. *Drop-glue alloc*: **Symptom**: dropping a Task leaks via boxed drop. **Fix**: ensure Tasks use a slab+index identity, never own boxed drop glue.
  - **Expect to hit (perf) #1 — `tokio::spawn`-shaped API forces `Box<dyn Future>` (bar (c) violation)**: a "convenience" `spawn(future: impl Future + 'static)` signature compiles to `Box::new(future)` because the runtime stores tasks heterogeneously in a single queue — every spawn = ~100 ns malloc + ~200 ns wrapping = ~300 ns/spawn. At 100k spawns/sec (realistic for a busy reactor), 30 ms/sec of pure spawn allocation. Worse: the heap-allocated future is dropped via `Box<dyn Drop>` which is another indirect call + free. Symptom: `dhat` reports 100k allocs/sec attributed to `spawn`; profile shows `__libc_malloc` + `__libc_free` 10%+ of runtime CPU. Fix: typed-task design — spawn takes a `T: Future + 'static` and stores it in a slab indexed by concrete type. The runtime exposes ONE TaskFuture enum that wraps all known futures (via `enum_dispatch` or hand-written enum). Generic tasks live in their own typed slabs. NO `Box<dyn Future>` anywhere; the slab is the heap-allocated container, amortized once at startup. Glommio and Seastar use this pattern. Cost avoided: ~300 ns/spawn × 100k spawns/s = ~30 ms/sec; eliminates the spawn-allocator hotspot. Muscle: a thread-per-core runtime stores futures in typed slabs, not `Box<dyn>` — generic `tokio::spawn` is the bar-(b) pattern, NOT bar-(c). Reapplies at: W84 deterministic harness task storage, W85 runtime v1.0 SHIP audit, W90 marketdata-kernelbypass task pool.
  - **Expect to hit (perf) #2 — `dhat` profile-build skew vs release-build (bar (c) violation)**: `dhat-rs` requires recompilation with `--features dhat-heap`; the resulting binary has different inlining decisions, allocator routing, and LLVM optimizations than the release build — a profile that shows "0 allocs in poll()" under dhat may show 100 allocs/poll under `cargo build --release` due to debug-only inlining of helper closures. Symptom: dhat audit passes; production bench shows alloc count >0; bisecting reveals release-build inlines a helper that allocates. Fix: run dhat audit in `--release` mode with `[profile.release.package.dhat-heap] opt-level = 0` to keep dhat instrumentation lightweight while keeping the rest of the code optimized. Pair with a `criterion`-style alloc counter baked into the test binary (using `std::alloc::Global` with a custom counting allocator) — same binary, same optimization profile, just counts. Run both for cross-validation. Cost avoided: undetected alloc regressions that pass dhat but fail production — exactly the trap the SHIP gate is designed to catch. Muscle: profile tools must run on PRODUCTION builds; never trust a debug-build audit. Reapplies at: W82 v1.5 SHIP perf gate, W84 archive replay perf bench, W85 runtime v1.0 SHIP audit, W92 ledger v1.0 SHIP audit.
  - **Test scenarios**: 1M `poll()` iterations under `dhat-rs` → assert `total_allocs <= 10` (preamble only). Stress: 10 concurrent producer-tasks + 10 consumer-tasks + timer-heavy load; alloc count stays bounded.
  - **Acceptance**: dhat report: 0 allocations attributable to `Reactor::poll` over 1M iterations; CI guard catches regression.
  - **Downstream**: required for W85 Thu v1.0 SHIP; matching-engine v1.5 and ledger-deterministic v0.5+ all run on top of this reactor.
