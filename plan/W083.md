  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)

  - **When `ledger_state_hash_zero_alloc` reports 32 MB Vec spikes:**
    - Symptom: heaptrack shows 32 MB Vec spikes per state_hash; VOPR scenarios slow 4× due to allocator pressure.
    - Why: `let mut tuples: Vec<_> = self.accounts.iter().map(...).collect(); tuples.sort(); blake3(tuples)` allocates 1M × 32 B = 32 MB on every call. `.collect()` reallocates as Vec grows (several doublings = ~3× total bytes touched).
    - Fix: pre-allocate `tuples: Vec<(u64, u64, u64)>` once at SM construction with `capacity = max_accounts`; state_hash calls `tuples.clear() + extend(iter) + sort() + blake3(tuples.as_slice())`. Zero allocs in steady state. Or use FixedMap/BTreeMap with sorted iteration for O(1) sorted iter, no sort step.
    - Cost avoided: 32 MB/call × 10 calls/sec = 320 MB/sec churn → 0 alloc; restores VOPR scenario throughput.
    - Muscle: hash/checksum operations on collections reuse pre-allocated scratch buffer — never `.collect()` inside hash function. Reapplies at: W84 archive replay checksum, W87 VOPR property check (computes state_hash 10M times/scenario), W92 ledger v1.0 SHIP audit.

  - **When `ledger_recovery_under_2s_for_1m_ops` reports 5 minutes:**
    - Symptom: kill -9 + restart of 1M-op ledger takes minutes.
    - Why: recovery treats replay like fresh apply (`sm.apply(op); wal.append(op); wal.fsync()` per op) → recovery at SAME speed as apply (~300 µs/op with fsync); 1M ops = 5 min vs <2s target by 150×.
    - Fix: recovery NEVER writes wal (wal is what it's reading FROM) — just `sm.apply(op)` for each entry. No fsync, no append. 1M ops × 120 ns SM apply = 120 ms total — under 2s. Crash-recovery harness explicitly disables wal writes; assert `wal.append_count_during_recovery == 0`.
    - Cost avoided: ~300 µs/op → ~120 ns/op = 2500× speedup.
    - Muscle: replay/recovery paths skip durability (data already durable in source) — read-only sweep of apply logic. Reapplies at: W84 archive replay (reads, never writes back), W87 VOPR recovery scenarios, W88 consensus-vsr follower catch-up, W92 ledger v1.0 SHIP recovery test.

  - **5-year failure mode** (write in `notes/83_polish_followup.md`): when ledger reaches 1B accounts, state_hash recomputation becomes 32 GB; need incremental hash (Merkle tree). Migration: state_hash trait abstraction; flat sort impl + incremental Merkle impl.

- [ ] [NEW v2] **Build**: `crates/messaging-aeron/src/archive.rs` — stream recording layer: every published frame is
  also written to `mmap-queue::Cycle`. (~total 4 hrs across 3 phases)
  - 🔧 **Why this matters**: Aeron Archive distinguishes Aeron from pure in-memory bus — on-disk replayable history. Without it: no late subscriber, no forensic replay. Downstream: W84 archive.replay; ledger v0.7 VOPR uses Archive as persistent journal; consensus-vsr v1.0 uses as cross-replica WAL.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **Requirements** — write in `crates/messaging-aeron/notes/83_archive_design.md`:
    - R1. Frame written to mmap-queue BEFORE Publication's term-position advances (subscriber's tail can't observe a frame whose recording is incomplete).
    - R2. `ArchiveOffset` strictly monotonic across term-buffer rotations.
    - R3. Crash mid-record leaves tail recoverable via recovery::truncate.
    - R4. Recording adds ≤15% overhead to offer() P99.
    - R5. Archive position lag <1 ms at 1M frame/s sustained.
    - R6. W84 replay byte-identical to original publication.
    - R7. Hardware-accelerated crc32c (`_mm_crc32_u64` x86 / `__crc32d` aarch64) on hot path.
    - R8. Pretoucher (W77) paired with archive Cycle to keep next-page warm.

  - **Design walk-through**:
    - D1. Sketch ArchiveRecorder + ArchiveOffset.
    - D2. **Pre-mortem (software crc32c):** ~250 ns for 256 B frame at ~1 GB/s portable impl. Hardware: ~20 ns (12× faster). At 1M frames/sec, software = 250 ms/sec vs hardware 20 ms/sec. Walk through `target_feature` gating.
    - D3. **Pre-mortem (pretoucher absent):** archive Cycle grows past pages every 16 frames; page-fault ~1 µs in publisher's offer critical path. P99.9 spikes every 16 µs. Walk through pretoucher pairing.
    - D4. **Pre-mortem (recording lag):** archive_position falls behind publication_position under burst → late subscriber sees gap. Backpressure publication on archive lag > N MB.
    - D5. **Pre-mortem (fsync policy):** claimed durability but crash loses last 5ms. Document policy explicitly; for VOPR scenarios mandate WriteThrough.
    - D6. **Pre-mortem (retention rotation race):** subscriber replaying across rotation boundary reads stale file. Rotation atomic via rename + symlink swap; recorder publishes new descriptor before deleting old.
    - D7. **Pre-mortem (partial frame at boundary):** crash mid-write leaves N-byte trailing fragment, replay reads garbage. Framed length prefix + tail crc; truncate to last valid frame on open.

  - **Output**: `notes/83_archive_design.md` with R1–R8 + D1–D7.

  - **When `archive_crc32c_uses_hardware_accelerator` reports 250 ns for 256 B:**
    - Symptom: archive recording adds ~30% overhead instead of 15%; CPU flamegraph shows ~20% in crc32c software.
    - Why: `crc32c` Rust crate's portable software impl: ~1 GB/s = ~250 ns for 256 B vs hardware (~12 GB/s = ~20 ns).
    - Fix: gate on `target_feature = "sse4.2"` (x86) or `target_feature = "crc"` (aarch64); use intrinsic via `std::arch::x86_64::_mm_crc32_u64` / `std::arch::aarch64::__crc32d`. `crc32fast` and `crc32c` crates auto-detect at runtime; pre-select at compile time for bar (c).
    - Cost avoided: ~230 ns/frame × 1M frames/s = ~230 ms/sec; restores offer() within 15% archive-overhead budget.
    - Muscle: any hot-path hash/checksum on bar-(c) crate uses hardware accelerator — don't rely on library's runtime detection. Reapplies at: W83 ledger journal crc32c, W84 archive replay verify, W92 ledger v1.0 io_uring buffer crc. BLAKE3 should use AVX-512 path on server chips.

  - **When `archive_pretoucher_eliminates_p99_9_page_fault_spike` reports 3-5 µs spikes:**
    - Symptom: archive-enabled offer() P99.9 shows 3-5 µs spikes every 16 µs; P99 fine but P99.9 fails 15% overhead acceptance gate.
    - Why: archive writes ~200 MB/s; Cycle mmap grows past page boundaries every 4 KiB / 256 B/frame = every 16 frames; each new page = minor page fault ~1 µs in publisher's offer critical path.
    - Fix: when creating ArchiveRecorder, spawn Pretoucher (W77) with `pretouch_ahead = 64 pages` paired to recorder's current tail. Pretouch worker stays ahead of writer by 256 KiB, faulting pages on background thread.
    - Cost avoided: ~1 µs page-fault spike eliminated from offer() critical path; restores P99.9 budget.
    - Muscle: any growing mmap on bar-(c) write path MUST be paired with pretoucher — W77 Mon principle is non-negotiable. Reapplies at: W92 ledger v1.0 io_uring journal, W90 marketdata-kernelbypass AF_XDP UMEM pretouch.

- [ ] [NEW v2 runtime v1.0] **Build**: zero-alloc audit on Reactor::poll() — every hot path replaced with pre-allocated
  buffers. (~total 3 hrs across 3 phases)
  - 🔧 **Why this matters**: runtime v1.0 ships W85 Thu. Bar-(c) VOPR-grade requires Reactor::poll allocation-free so memory pressure can't starve hot core or introduce nondeterminism into replays. TigerBeetle's runtime is allocation-free by construction. Downstream: matching-engine v1.5, marketdata v0.5, messaging-aeron v0.7, ledger v0.5 all run on top.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **Requirements** — write in `crates/runtime-thread-per-core/notes/83_zero_alloc_design.md`:
    - R1. `poll()` invokes ZERO `alloc::alloc` (verified by dhat heap counter delta = 0).
    - R2. Every container bounded by const generics or arena.
    - R3. Error paths use `&'static str` codes, never `format!`/`String::from`.
    - R4. `dhat` total_allocs ≤10 over 1M poll iterations (preamble only).
    - R5. CI guard catches regression.
    - R6. spawn API uses typed-slab, NOT `Box<dyn Future>`.

  - **Design walk-through**:
    - D1. Sketch Reactor with ArrayVec + HierarchicalWheel + ScratchBuffer.
    - D2. **Pre-mortem (tokio::spawn pattern):** `spawn(future: impl Future + 'static)` compiles to `Box::new(future)` because runtime stores tasks heterogeneously in single queue. Every spawn = ~300 ns. Walk through typed-task design with concrete-type slabs + TaskFuture enum.
    - D3. **Pre-mortem (dhat profile vs release build skew):** dhat-rs needs recompile with `--features dhat-heap`; different inlining/allocator routing/LLVM than release. Profile shows "0 allocs" under dhat but 100 allocs/poll under release. Walk through running dhat in release mode + custom counting allocator for cross-validation.
    - D4. **Pre-mortem (hidden alloc via trait object):** `tracing::event!` macro internally Box-es spans. Gate hot-path tracing behind `cfg(not(release_alloc_audit))`.
    - D5. **Pre-mortem (format! in error):** passes happy-path audit, fails under fault injection because error path formats. Static `&'static str` table or `thiserror` with no string interp.

  - **Output**: `notes/83_zero_alloc_design.md` with R1–R6 + D1–D5.

  #### Phase 3 — Make the tests pass, one failure at a time (~95 min)

  - **When `reactor_no_box_dyn_future_in_spawn` reports 100k allocs/sec:**
    - Symptom: dhat reports 100k allocs/sec attributed to `spawn`; profile shows `__libc_malloc` + `__libc_free` 10%+ of runtime CPU.
    - Why: `spawn(future: impl Future + 'static)` compiles to `Box::new(future)` (~300 ns/spawn). Heap-allocated future dropped via `Box<dyn Drop>` = another indirect call + free.
    - Fix: typed-task design — spawn takes `T: Future + 'static` and stores in slab indexed by concrete type. Runtime exposes ONE TaskFuture enum wrapping all known futures (via `enum_dispatch` or hand-written). Generic tasks live in their own typed slabs. NO `Box<dyn Future>` anywhere; slab is heap-allocated container amortized at startup. Glommio + Seastar use this pattern.
    - Cost avoided: ~300 ns/spawn × 100k spawns/s = ~30 ms/sec; eliminates spawn-allocator hotspot.
    - Muscle: thread-per-core runtime stores futures in typed slabs, not `Box<dyn>` — generic `tokio::spawn` is bar-(b) pattern, NOT bar-(c). Reapplies at: W84 deterministic harness task storage, W85 runtime v1.0 SHIP audit, W90 marketdata-kernelbypass task pool.

  - **When `reactor_dhat_release_mode_matches_custom_counter` reports mismatch:**
    - Symptom: dhat audit passes (0 allocs); production bench shows alloc count >0; bisecting reveals release-build inlines a helper that allocates.
    - Why: dhat-rs recompilation with `--features dhat-heap` has different inlining/allocator routing/LLVM than release build. Profile shows "0 allocs" under dhat but 100 allocs/poll under release.
    - Fix: run dhat audit in `--release` mode with `[profile.release.package.dhat-heap] opt-level = 0` to keep dhat instrumentation lightweight while keeping rest of code optimized. Pair with `criterion`-style alloc counter baked into test binary (using `std::alloc::Global` with custom counting allocator) — same binary, same optimization profile, just counts. Run both for cross-validation.
    - Cost avoided: undetected alloc regressions that pass dhat but fail production.
    - Muscle: profile tools must run on PRODUCTION builds; never trust debug-build audit. Reapplies at: W82 v1.5 SHIP perf gate, W84 archive replay perf bench, W85 runtime v1.0 SHIP audit, W92 ledger v1.0 SHIP audit.

  - **5-year failure mode** (write in `notes/83_zero_alloc_followup.md`): when WASM-compiled futures become deployment target, the typed-slab approach needs to accommodate WASM ABI. Migration: enum dispatch via wasm-bindgen.
