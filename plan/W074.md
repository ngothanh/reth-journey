  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: a single-process matching engine has one fault domain — one machine fails, exchange offline. Replication via raft makes the engine survive single-node failures but introduces TWO new categories of failure: (a) non-determinism (any wall-clock, HashMap iteration, or f64 use causes replicas to diverge silently), (b) replication-latency collapse (per-command AppendEntries is RTT-bound; throughput falls 12×). The fix: a determinism gate (banned types via clippy + grep CI) + batched AppendEntries.

  - **Requirements** — write in `crates/matching-engine/notes/74_replication_design.md`:
    - R1. `RaftBackedEngine` wraps the W67 single-process Engine; submits incoming commands via `raft.propose()`; receives `apply(index, cmd)` callbacks on every replica.
    - R2. `MatchCommand` enum: NewOrder, Cancel, ApplyFunding, LiquidationStep, ADLStep, AdvanceClock. Each variant is `Copy` (no String, no Vec inside).
    - R3. **Determinism gate**: no `Instant::now()`, no `SystemTime`, no `rand::thread_rng`, no `HashMap`/`AHashMap` iteration, no `f64` in the apply path. CI grep enforces.
    - R4. **Contiguous apply**: `apply(index)` requires `index == self.applied_index + 1`; gap or duplicate is a panic. Raft guarantees no gaps post-install_snapshot.
    - R5. **SequenceClock**: replaces wall-clock; advances only on `AdvanceClock` commands embedded in the log.
    - R6. **Batched AppendEntries**: leader buffers proposals in a `Vec<MatchCommand>` (cap 1024), flushes when full OR after `batch_timeout` (~1 ms).
    - R7. **Group-commit fsync**: leader fsyncs once per AppendEntries batch; follower fsyncs once per AppendEntries ack.
    - R8. **Zero alloc on apply**: `MatchCommand` reused from a per-shard pool of 16384.
    - R9. **Throughput**: ≥ 50k cmd/sec replicated at 3 replicas, p99 commit ≤ 5 ms.
    - R10. **Single-shard non-replicated**: ≥ 1 M orders/sec/shard (inherits from W65).
    - R11. **Cross-replica byte-identical**: 100 random scenarios × 10k commands; every replica's state hash matches at every commit point.
    - R12. **Cross-arch byte-identical**: x86 + ARM replicas on same log → same state hash.
    - R13. **Replay-snapshot invariant**: `snapshot_of(apply(empty, log[0..N])) == apply(empty, log[0..N]).serialize()`.

  - **When `bench_3_replica_throughput_50k_per_sec` reports ~4k cmd/sec and `bench_p99_commit_under_5ms` shows p99 ≈ RTT floor:**
    - Symptom: throughput pegs at ~4k cmd/sec (1/RTT × leader cores). p99 latency = round-trip latency floor regardless of CPU. Matching-engine v1.0 fails throughput acceptance by 12×.
    - Why: naïve `submit(cmd)` → `raft.propose(cmd).await` → AppendEntries × (n-1) followers per command. At 50k cmd/sec × 2 followers = 100k AppendEntries/sec × ~250 µs RTT = ~25 s/sec of wall-clock RTT pipelined — impossible on a single channel.
    - Fix: **batched AppendEntries** — leader buffers incoming proposals in a `Vec<MatchCommand>` (cap 1024), flushes when full OR after `batch_timeout` (~1 ms). One AppendEntries carries 1-1024 commands; ack covers the batch. At 50k cmd/sec × ~1 ms batch = ~50 cmds/batch × 1k AppendEntries/sec × ~250 µs RTT = ~250 ms/sec wall-clock RTT pipelined (achievable with W67 pipelining). Clients see ~1 ms batch-fill latency + ~250 µs RTT + ~50 µs fsync ≈ 1.3 ms p50, well under 5 ms p99.
    - Cost avoided: ~12× throughput; ~5 ms p99 budget reclaimed; tail-latency cost of batching bounded by `batch_timeout`.
    - Muscle: any replication protocol on a high-throughput path must batch over a small time window (~1-10 ms); per-event AppendEntries/Prepare is always RTT-bound. Reapplies at: W74 VSR Prepare batching (Tue this week), W67 raft AppendEntries, W83+ ledger VSR PrepareOk batching, W92 ledger v1.0 io_uring submission ring.

  - **When `dhat_apply_path_zero_alloc` reports ~150k allocs/sec and `bench_p99_commit_under_5ms` shows erratic p99 (5-10× p50):**
    - Symptom: heaptrack shows MatchCommand-related allocations dominating. p99 apply latency is erratic; long-tail latency on apply correlates with allocator compaction events.
    - Why: even with integer-only / BTreeMap discipline (correctness pitfalls), the apply path still allocates if MatchCommand variants carry `String symbol` or `Vec<TimeInForce>`-like fields. At 50k apply/sec × ~3 small allocations = ~150k mallocs/sec ≈ 7.5 ms/sec allocator overhead + cache pollution + jitter.
    - Fix: every MatchCommand variant is `Copy` (or at worst `Clone` with inline arrays). `Symbol = [u8; 8]` not String; `OrderId = u64`; no `Vec<_>` inside commands — fixed-cap inline arrays only. Command struct stays under one cache line (~64 B). Apply path becomes alloc-free. Reuse via a per-shard pool of 16384 `MatchCommand` slots.
    - Cost avoided: ~7.5 ms/sec allocator overhead → 0; restores predictable p99 apply latency; aligns with "no allocations in steady state."
    - Muscle: every type that traverses a deterministic SM apply path is `Copy` (or carefully-`Clone`'d from a pool); never `String`, never `Vec<_>`. Static-mem discipline (TigerBeetle's headline). Reapplies at: W74 VSR Op/Prepare/PrepareOk wire types, W83+ ledger Transfer/Account (`Transfer = [u8; 128]` fixed), W92 ledger v1.0 static-mem invariant, W88 VOPR replay scenarios.

    - Fix: ban `Instant`/`SystemTime` imports from matching-engine via clippy `disallowed-types`. Add CI grep step: `grep -rn 'Instant\|SystemTime' crates/matching-engine/src/ && exit 1`. Replace any necessary timestamps with SequenceClock-derived values.
    - Muscle: any non-deterministic clock source in a replicated SM is a divergence vector — lint-enforce the ban. Reapplies at: W83+ ledger, W92 VSR replicated commit.

  - **When `cross_arch_state_hash_identical` shows divergence between x86 and ARM:**
