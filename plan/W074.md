  - *Back-of-envelope* (bar (c) — name the cost): target 50k cmd/sec replicated, p99 commit ≤5ms.
    - Per-cmd Prepare cliff: 1 RTT ≈ 250µs loopback. `1 / 250µs = 4000 cmd/sec` ceiling on one in-flight Prepare — **4k vs 50k = 12.5× short** before you write a line of matching logic. Batching N=50 cmds/Prepare reclaims it: `50 × 4000 = 200k cmd/sec` headroom.
    - Apply-path alloc cliff: malloc ≈ 50ns. `String symbol + Vec<TIF>` ≈ 3 allocs/cmd × 50k/sec × 50ns = **7.5ms of allocator wall-clock per second of trading** + cache pollution → p99 jitter. `Copy` command = 0 allocs, ~64B (one cache line), memcpy ≈ 4ns.
    - fsync cliff: one fsync ≈ 1ms (SSD). Per-cmd fsync at 50k/sec = impossible; group-commit one fsync per Prepare batch = 1k fsync/sec ≈ 1ms/batch amortized over 50 cmds = 20µs/cmd.

  - **The problem this primitive solves**: a single-process matching engine has one fault domain — one machine fails, exchange offline. Replication via VSR makes the engine survive single-node failures AND gives the order log, settlement journal, and replicated SM a *single* canonical sequence. But it introduces THREE new failure categories: (a) non-determinism (any wall-clock, HashMap iteration, or f64 use causes replicas to diverge silently); (b) replication-latency collapse (per-command Prepare is RTT-bound; throughput falls ~12×); (c) **scope creep** (the temptation to put funding/liquidation logic into `MatchCommand` because "it's already replicated here" — which would re-merge the crates v3 deliberately split). The fix: a determinism gate (banned types via clippy + grep CI) + batched Prepare + a hard `MatchCommand` scope gate.
