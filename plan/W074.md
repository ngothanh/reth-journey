  - *Mental model*: `RaftBackedEngine` turns the W67 single-process matching Engine into a **replicated deterministic state machine** — the raft log is the single source of truth, and every replica that applies the same prefix of the log reaches byte-identical state. The engine stops being "a server"; it becomes "a pure function `apply: (State, Command) → State` that the raft log drives in lockstep across N machines."
  - *Contract*: the signature-level interface (NEVER the body):
    ```rust
    pub struct RaftBackedEngine { /* wraps W67 Engine + consensus_raft::RaftNode + SequenceClock + per-shard pool */ }
    impl RaftBackedEngine {
        pub fn submit(&self, cmd: MatchCommand) -> Result<CommandId, SubmitError>;   // leader: enqueue → batched propose
        fn apply(&mut self, index: u64, cmd: MatchCommand);                          // every replica: contiguous, det.
        pub fn state_hash(&self) -> [u8; 32];                                         // canonical, sorted, for cross-replica cmp
    }
    #[derive(Clone, Copy)]                                                            // R2: every variant Copy
    pub enum MatchCommand { NewOrder(NewOrder), Cancel(CancelOrder), ApplyFunding(Funding),
                            LiquidationStep(Liq), ADLStep(Adl), AdvanceClock(SeqTick) }
    ```
  - *Back-of-envelope* (bar (c) — name the cost): target 50k cmd/sec replicated, p99 commit ≤5ms.
    - Per-cmd AppendEntries cliff: 1 RTT ≈ 250µs loopback. `1 / 250µs = 4000 cmd/sec` ceiling on one in-flight channel — **4k vs 50k = 12.5× short** before you write a line of matching logic. Batching N=50 cmds/AppendEntries reclaims it: `50 × 4000 = 200k cmd/sec` headroom.
    - Apply-path alloc cliff: malloc ≈ 50ns. `String symbol + Vec<TIF>` ≈ 3 allocs/cmd × 50k/sec × 50ns = **7.5ms of allocator wall-clock per second of trading** + cache pollution → p99 jitter. `Copy` command = 0 allocs, ~64B (one cache line), memcpy ≈ 4ns.
    - fsync cliff: one fsync ≈ 1ms (SSD). Per-cmd fsync at 50k/sec = impossible; group-commit one fsync per batch = 1k fsync/sec ≈ 1ms/batch amortized over 50 cmds = 20µs/cmd.

  - **The problem this primitive solves**: a single-process matching engine has one fault domain — one machine fails, exchange offline. Replication via raft makes the engine survive single-node failures but introduces TWO new categories of failure: (a) non-determinism (any wall-clock, HashMap iteration, or f64 use causes replicas to diverge silently), (b) replication-latency collapse (per-command AppendEntries is RTT-bound; throughput falls 12×). The fix: a determinism gate (banned types via clippy + grep CI) + batched AppendEntries.

  - **Requirements** — write in `crates/matching-engine/notes/74_replication_design.md`:
    - R1. `RaftBackedEngine` wraps the W67 single-process Engine; submits incoming commands via `raft.propose()`; receives `apply(index, cmd)` callbacks on every replica.
    - R2. `MatchCommand` enum: NewOrder, Cancel, ApplyFunding, LiquidationStep, ADLStep, AdvanceClock. Each variant is `Copy` (no String, no Vec inside).
    - R3. **Determinism gate**: no `Instant::now()`, no `SystemTime`, no `rand::thread_rng`, no `HashMap`/`AHashMap` iteration, no `f64` in the apply path. CI grep enforces.
    - R4. **Contiguous apply**: `apply(index)` requires `index == self.applied_index + 1`; gap or duplicate is a panic. Raft guarantees no gaps post-install_snapshot.
    - R5. **SequenceClock**: replaces wall-clock; advances only on `AdvanceClock` commands embedded in the log.
    - R6. **Batched AppendEntries**: leader buffers proposals in a `Vec<MatchCommand>` (cap 1024), flushes when full OR after `batch_timeout` (~1 ms).
    - R7. **Group-commit fsync**: leader fsyncs once per AppendEntries batch; follower fsyncs once per AppendEntries ack.
    - R8. **Zero alloc on apply**: `MatchCommand` reused from a per-shard pool of 16384.
    - R9. **Throughput**: ≥ 50k cmd/sec replicated at 3 replicas, p99 commit ≤ 5 ms.
    - R10. **Single-shard non-replicated**: ≥ 1 M orders/sec/shard (inherits from W65).
    - R11. **Cross-replica byte-identical**: 100 random scenarios × 10k commands; every replica's state hash matches at every commit point.
    - R12. **Cross-arch byte-identical**: x86 + ARM replicas on same log → same state hash.
    - R13. **Replay-snapshot invariant**: `snapshot_of(apply(empty, log[0..N])) == apply(empty, log[0..N]).serialize()`.

One AppendEntries carries 1-1024 commands; ack covers the batch. Clients see ~1 ms batch-fill latency + ~250 µs RTT + ~50 µs fsync ≈ 1.3 ms p50, well under 5 ms p99.
