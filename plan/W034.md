**Monday — Bloom theory + design**

- [ ] Re-read mini-lsm bloom section. Read "Cache, Hash, and Space-Efficient Bloom Filters" (Putze et al.). FPR math: m
  bits, k hashes, n insertions → fpr ≈ (1 - e^(-kn/m))^k. (~45 min)
- [ ] **Build**: `crates/bloom/Cargo.toml` workspace member. Deps: `time` (for instrumentation only). (~20 min)
- [ ] **Build**: `crates/bloom/src/classic.rs` — `BloomFilter { bits: BitVec, k: u8, hasher_seeds: [u64; 4] }` with
  `with_fpr_at_capacity(fpr, n)` constructor. (~75 min)
  - **Why**: A bloom filter trades false positives for a tiny memory footprint, which is what makes LSM SSTable reads fast (skip 99% of SSTables that don't contain the key). The math is unforgiving — under-provision bits or hashes and FPR spikes, over-provision and you waste cache. Closed-form: `m = -n*ln(p) / (ln(2))^2`, `k = (m/n)*ln(2)`. The implementation craft is in the hash function: k independent hashes from 2 base hashes via Kirsch-Mitzenmacher double-hashing.
  - *Back-of-envelope*: at p=0.01 and n=1 M keys → m ≈ 9.6 Mbits ≈ **1.2 MiB** (fits in L2 on most cores); k = round(9.6 × ln 2) ≈ 7 probes per query. **Target negative `contains` ≤ 50 ns**, positive ≤ 80 ns (positive may probe all 7 bits before short-circuit; negative short-circuits on first 0 — usually 1-2 probes). Per probe: 2× xxhash3 (~3 ns each warm = ~6 ns total amortized via double-hashing — only 2 base hashes for k probes) + k× (mul + shift + bit-extract) ≈ ~25 ns total at k=7. **The bit-load dominates if bits straddle cache lines** — random probes into a 1.2 MiB array hit ~7 different cache lines per query (~7 × 7 ns L2 = ~50 ns) — this is the perf floor and what drives the block-bloom variant (perf pitfall #2). **Zero allocations on contains**: bit slice is owned `BitVec`; probe positions computed in registers. At 5 M get/sec for W39 SSTable read, bloom cost ≈ ~250 ms/sec — must be ≤ 5% of CPU budget.
  - **Read first**: Putze et al. "Cache, Hash, and Space-Efficient Bloom Filters"; RocksDB `util/bloom_impl.h` (block-bloom variant). Cassandra `BloomFilter.java`.
  - **Design**:
    ```rust
    pub struct ClassicBloom {
        bits: BitVec,
        m: u64,        // total bits
        k: u8,         // hashes per key
        seed0: u64,
        seed1: u64,
    }
    impl ClassicBloom {
        pub fn with_fpr_at_capacity(fpr: f64, n: u64) -> Self;
        pub fn insert(&mut self, key: &[u8]);
        pub fn contains(&self, key: &[u8]) -> bool;
    }
    ```
    **Invariants**:
    - `contains` returns true for every inserted key (no false negatives).
    - Measured FPR <= 1.2x target FPR at design capacity.
    - All k bit positions derived deterministically from key (insert and contains agree).
  - **Build steps**:
    1. (~15 min) Sizing math: `m = ceil(-n*ln(p) / ln(2)^2)`; `k = max(1, round(m/n * ln(2)))`.
    2. (~30 min) Double-hashing: `h1 = xxhash(key, seed0)`, `h2 = xxhash(key, seed1)`; then `pos_i = (h1 + i*h2) mod m` for i in 0..k. Cite Kirsch-Mitzenmacher 2006.
    3. (~20 min) `insert` sets bits; `contains` checks AND of bits.
    4. (~10 min) FPR self-test: insert n, query n*10 non-existent, measure.
  - **Pitfalls**:
    - *k too small from rounding*: `k = round(m/n * ln(2))` can be 0 if n>m; clamp to ≥1. **Symptom**: 100% FPR. **Fix**: `max(1, k)`.
    - *Modulo bias*: `pos % m` introduces non-uniformity when m is not a power of 2. **Symptom**: hot bits → higher FPR. **Fix**: use multiply-shift (Lemire 2016) or pick m as power-of-2.
    - *Insert/contains hash disagreement*: contains uses different seeds than insert (e.g., loading from disk lost the seeds). **Symptom**: false negatives — silently lose data. **Fix**: seeds are part of the filter's serialized header.
  - **Expect to hit (perf) #1 — k probes scatter across k cache lines (bar (c) violation)**: a "classic" flat bloom of m bits laid out as one contiguous `BitVec` puts each of the k probe positions on a *different* random cache line. At k=7 and a 1.2 MiB filter (larger than L1), each negative `contains` incurs ~7 cache misses ≈ ~50 ns L2 / ~700 ns DRAM (cold). At 5 M get/sec the LSM read path bottlenecks on bloom alone (~3.5 sec/sec CPU cold), and the filter never wins back the SSTable I/O it was supposed to save.
    - Fix: **block-bloom** layout (RocksDB-style) — partition bits into 64-byte blocks (one cache line each); for each key, all k probes land in the SAME block via `block_idx = h1 % num_blocks; for i in 0..k { bit = (h1 + i*h2) % 512 in that 64-byte block }`. One cache line touched per `contains`, regardless of k. FPR penalty: ~10-15% higher than flat for the same memory (Putze et al. show this is bounded); CPU win: ~7× on contains.
    - Cost avoided: ~7 cache misses → 1 per contains; at 5 M get/sec, ~3 sec/sec CPU reclaimed cold; positive contains on warm L1 stays ≤ 25 ns (one cache line, k bit-tests). The bloom cost stays inside the 5% budget for W39 SSTable read.
    - Muscle: probabilistic filters whose probe count exceeds 1-2 MUST use a block layout that keeps all probes within one cache line; flat bloom is only acceptable for k ≤ 2 (e.g., quotient filters with k=1). Reapplies at: W39 SSTable bloom filter block (already uses block-bloom variant), W95 mini-db CAPSTONE filter block, W101 vector-db filtered-search bitmap (which uses a similar block-tile structure).
  - **Expect to hit (perf) #2 — scalar bit-test loop instead of hardware popcount/test for cardinality + serialization (bar (c) violation)**: bloom support operations (cardinality estimate via "fraction of bits set", union, intersection) loop over `bits.iter().filter(|b| *b).count()` — at 9.6 Mbits, that's ~10 M iterations × ~1 ns/iter = ~10 ms per cardinality call. Same for serialization byte counting and "is this filter saturated?" diagnostics. These get called at flush/compaction time (W39 SSTable build), making the LSM background a CPU hotspot.
    - Fix: cast `bits.as_raw_slice()` to `&[u64]` and call `_mm_popcnt_u64`/`u64::count_ones` per word — hardware popcount on x86 (POPCNT, ~1 cycle/word) and aarch64 (`CNT`, ~3 cycles/word) processes 64 bits/op. At 9.6 Mbits = 150 K u64 words, ~150 µs vs ~10 ms — **~60× speedup**. The Rust intrinsic `u64::count_ones()` autovectorizes to POPCNT on `target_cpu=native` or with `is_x86_feature_detected!("popcnt")` runtime detection.
    - Cost avoided: ~10 ms → ~150 µs per cardinality; ~60× cardinality / union / intersection speedup; eliminates the LSM compaction CPU spike at filter-merge time (W39 Tuesday).
    - Muscle: bitwise operations over arrays MUST go through `u64`-wise hardware intrinsics (`count_ones`, `leading_zeros`, AVX2 `_mm256_and_si256`); the per-bit loop is correctness-only and disqualifies bar (c). Reapplies at: W39 SSTable bloom union for L0→L1 compaction merge, W101 vector-db roaring-bitmap intersection, W95 mini-db CAPSTONE filter merge during compaction.
  - **Test scenarios**:
    - 1M insert, 10M lookup of disjoint set: measured FPR within 1.2x of design.
    - Zero false negatives: insert N, query all N; all return true.
    - Determinism: same key+seeds always probes same k bits.
  - **Acceptance**: 1M inserts < 200ms; measured FPR ≤ 1.2x design at p=0.01.
  - **Downstream**: W39 SSTable filter block (consume directly); storage-trie pruning index; vector-db filtered search (W101).

**Tuesday — Counting bloom + Reth pruning code**

- [ ] **Build**: `crates/bloom/src/counting.rs` — `CountingBloom` with u4 or u8 counters. Supports deletion. (~75 min)
  - **Why**: Classic bloom can't delete — a 1-bit set by multiple keys can't be safely cleared. Counting bloom uses small counters (4-bit typical) at each position; deletion decrements. Cost: 4-8x memory vs. classic. Used in pruning indices where deletions are common (storage-trie's pruner needs to remove pruned keys from the "still-present" filter).
  - *Back-of-envelope*: same m, k as classic; **memory cost: 4× (u4 packed) or 8× (u8) the classic bit count**. For n=1 M at p=0.01: ~4.8 MiB (u4) or ~9.6 MiB (u8) — neither fits in L2; u4 stays in L3, u8 spills to DRAM partially. **Target negative `contains` ≤ 80 ns, insert ≤ 100 ns, remove ≤ 100 ns**. Per probe: 2× xxhash (~6 ns amortized over k) + k× (byte-load + nibble-extract for u4: ~3 ns / direct byte load for u8: ~2 ns) + k× (compare/increment/decrement). u4 packing adds ~2 ns/probe for the nibble shift; under storage-trie pruner's delete-heavy workload, that cost is paid on every prune. **Zero allocations on insert/remove/contains**; the counter `Vec<u8>` is owned at construction. Block-bloom layout (same as classic perf #1) cuts cache-line touches to 1 per op — critical because counting bloom is bigger than classic and crosses L2.
  - **Read first**: Fan et al. "Summary cache: a scalable wide-area Web cache sharing protocol" (Sec 4); Cassandra `BloomFilter.java` counting variant.
  - **Design**:
    ```rust
    pub struct CountingBloom {
        counters: Vec<u8>, // packed u4 pairs OR plain u8
        m: u64, k: u8,
        seeds: (u64, u64),
    }
    impl CountingBloom {
        pub fn insert(&mut self, key: &[u8]);
        pub fn remove(&mut self, key: &[u8]); // requires prior insert
        pub fn contains(&self, key: &[u8]) -> bool;
    }
    ```
    **Invariants**:
    - Counter saturation: at max (15 for u4) further inserts are silently dropped; remove of saturated stays saturated.
    - `contains` returns true iff all k counters are > 0.
    - Caller must not remove a key never inserted (counter underflow corrupts the filter).
  - **Build steps**:
    1. (~25 min) Counter storage: `Vec<u8>` of m/2 bytes for u4 packing (two counters per byte).
    2. (~25 min) `insert` increments k positions, clamping at MAX.
    3. (~15 min) `remove` decrements k positions; debug-assert > 0 pre-decrement.
    4. (~10 min) Test: insert + remove + contains round-trip; no false negatives.
  - **Pitfalls**:
    - *Underflow on remove*: removing a never-inserted key wraps 0→255 (or 15). **Symptom**: false negatives on real keys probing that bit. **Fix**: API contract or saturation; document.
    - *Saturation drift*: u4 saturates at 15; after >15 collisions, removes can never bring it to 0. **Symptom**: false positive rate increases over time. **Fix**: use u8 if expected collisions > 15; size m accordingly.
    - *Packed u4 atomicity*: concurrent insert/remove on neighboring counters racy. **Symptom**: lost updates. **Fix**: u8 if shared; or external locking; or atomic-u8 with CAS.
  - **Expect to hit (perf) #1 — u4 nibble extract via division/modulo on the hot path (bar (c) violation)**: implementing `get_counter(i) -> u8` as `let byte = counters[i / 2]; if i % 2 == 0 { byte & 0xF } else { byte >> 4 }` puts a div + mod on the hot probe path. While LLVM often canonicalizes `% 2` to AND, it does NOT always strength-reduce `i / 2` when `i` is a non-constant u64 — that's a ~10-cycle integer div per probe (~3 ns) and at k=7 probes × 5 M contains/sec ≈ ~100 ms/sec of pure div. Worse, the branch on parity is unpredictable for random keys → ~5 ns mispredict per probe.
    - Fix: replace div/mod with bit ops — `let byte = counters[i >> 1]; let shift = (i & 1) << 2; let nibble = (byte >> shift) & 0xF;` — ~1 cycle each, branchless. Compiler may already do this on `i / 2`, but `i >> 1` makes the intent explicit and immune to compiler-version regressions. Verify with `cargo asm` once.
    - Cost avoided: ~3 ns/probe div + ~5 ns/probe branch mispredict → ~50 ns/contains saved at k=7; ~250 ms/sec at 5 M contains; restores counting-bloom probe cost to ~2× classic (instead of ~4× with div/branch).
    - Muscle: integer division by power-of-2 MUST be `>> log2(n)`; modulo by power-of-2 MUST be `& (n-1)`; never trust the compiler to strength-reduce on non-constant divisors. Reapplies at: W37 skiplist height computation (`height & (max_height - 1)`), W77 aeron term-id `% term_length` → mask, W101 vector-db PQ codebook index lookup.
  - **Expect to hit (perf) #2 — saturation check via branchy `if counter < 15` on every insert (bar (c) violation)**: the per-probe insert `if c < 15 { counters[i] += 1 }` adds a branch that mispredicts on saturated buckets — under storage-trie's long-tail prune workload (some hot bits hit 15 quickly), the mispredict rate climbs to ~10-20% and every insert pays ~5 ns. The downstream effect: pruner throughput drops 2-3× once the filter is "warm" with saturation in the heavy-hit corners.
    - Fix: branchless saturating add — `counters[i] = (counters[i] + 1).min(15);` or with bit-twiddle: `let c = counters[i]; counters[i] = c + ((c < 15) as u8);` — the compiler emits a CMOV/CSEL (~1 cycle, no branch) instead of a conditional jump. Same trick for saturating decrement: `c - ((c > 0) as u8)`.
    - Cost avoided: ~5 ns/probe mispredict at saturation; at k=7 × 1 M insert/sec ≈ ~35 ms/sec at moderate saturation, ~70 ms/sec at high saturation; smooth perf curve as the filter fills.
    - Muscle: any "clamp/saturate" on the hot path MUST be branchless (CMOV/CSEL via `.min()`, `.max()`, or `as u8` casts); explicit `if` branches are correctness-only. Reapplies at: W11 backpressure credit clamp, W74 matching-engine price-band clamp, W77 aeron flow-control window clamp, W11 bounded-MPMC ring full-check.
  - **Test scenarios**:
    - Insert 100k, remove 100k; filter empty (all counters 0).
    - Stress: insert N, remove N-1, contains the last is true.
  - **Acceptance**: round-trip correctness; bench ~80% slower than classic (acceptable).
  - **Downstream**: storage-trie pruner (Thursday); cache-invalidation indices in mini-db (W95).

**Wednesday — Scalable bloom + storage-trie pruning design**

- [ ] **Build**: `crates/bloom/src/scalable.rs` — `ScalableBloomFilter` chains classic filters with tightening FPR (
  Almeida et al.). Grows without rebuild. (~75 min)
  - **Why**: A classic bloom must be sized for the *expected* capacity n. When you don't know n ahead of time (streaming inserts, unknown workload), you either over-size (memory waste) or hit FPR collapse beyond n. Scalable bloom (Almeida 2007) chains slices: each new slice has 2x the size and FPR/2 of the prior, so the aggregate FPR stays bounded under unlimited growth. Cost: contains() probes every slice → O(slices) lookup.
  - *Back-of-envelope*: `contains` cost ≈ S × (classic contains) where S = number of slices. After 10× capacity growth at growth_factor=2: S ≈ log2(10) ≈ 4 slices; at 100×: S ≈ 7. **Target negative contains ≤ 200 ns at S=4, ≤ 400 ns at S=7**. Per slice: one block-bloom probe ≈ ~25 ns (warm L1, block layout from Monday perf #1) — so S=4 → ~100 ns, S=7 → ~175 ns. Memory: geometric series, ~2× the largest slice (slice S dominates because of 2× growth). For target_fpr=0.01 at 10 M inserts, total memory ≈ ~24 MiB across all slices — exceeds L2, lives in DRAM/L3. **Zero allocations on contains**; insert allocates a new slice ~once per 2× growth (amortized ~1/n alloc cost, negligible). The OR-short-circuit on contains is the primary perf lever — see perf pitfall #1.
  - **Read first**: Almeida et al. "Scalable Bloom Filters" 2007. Cassandra has historically resisted this in favor of recompacting; the win for ScalableBloom is in long-lived in-memory indices where rebuild is too costly.
  - **Design**:
    ```rust
    pub struct ScalableBloom {
        slices: Vec<ClassicBloom>,
        target_fpr: f64,    // aggregate FPR budget
        growth_factor: u32, // 2 by default
        tightening: f64,    // 0.5 by default
        current_count: u64,
    }
    impl ScalableBloom {
        pub fn insert(&mut self, key: &[u8]);
        pub fn contains(&self, key: &[u8]) -> bool; // OR across slices
    }
    ```
    **Invariants**:
    - `contains` true iff ANY slice's `contains` is true.
    - Slice i has FPR `target_fpr * (1 - tightening^i) / (1 - tightening)` (aggregate fits target_fpr).
    - New slice created when current slice reaches its design capacity.
  - **Build steps**:
    1. (~20 min) Slice budgeting: capacity per slice doubles; FPR per slice halves.
    2. (~25 min) Insert: try current slice; if at capacity, allocate new slice with tightened parameters; insert there.
    3. (~15 min) Contains: short-circuit OR across slices.
    4. (~15 min) Test: insert 10M, aggregate FPR within 1.2x target.
  - **Pitfalls**:
    - *Geometric memory growth*: by slice 10 the filter is 1024x the initial size. **Symptom**: OOM on long-running streams. **Fix**: bound max slices or cap with eviction strategy.
    - *Per-slice seed drift*: slices share seeds → adversarial input can target multiple slices simultaneously. **Symptom**: degenerate FPR. **Fix**: derive per-slice seeds from a master + slice index.
    - *Contains hot path*: probing 10 slices means 10x classic-bloom cost; for read-heavy workloads, scalable bloom may be the wrong choice. **Fix**: profile; consider periodic compaction (rebuild a sized classic from current contents).
  - **Expect to hit (perf) #1 — slice probe order increases positive-contains latency (bar (c) violation)**: probing slices in INSERTION order (oldest first) means a positive hit on slice S (the newest, where the most recent inserts live) requires probing all S-1 prior slices first. Under a "recent-bias" workload (cache-of-recent, append-mostly streams), positive contains is ~S× classic cost — at S=7, that's ~175 ns per positive vs ~25 ns for a sized classic. The storage-trie pruner's "is this key still present?" check hits the newest slice ~70% of the time; reversing the order saves ~150 ns per check at scale.
    - Fix: probe slices in REVERSE order (newest first) with OR-short-circuit. The aggregate FPR is unchanged (OR is commutative), but the hit-latency distribution skews toward 1 probe instead of S. Implement as `self.slices.iter().rev().any(|s| s.contains(key))`. Document the "recent-bias" assumption — if the workload is uniform, reverse vs forward is a wash, but no workload is worse off with reverse.
    - Cost avoided: ~150 ns per positive at S=7 under recent-bias; at 5 M get/sec storage-trie pruner ≈ ~750 ms/sec CPU saved on positive lookups; eliminates the "newer = slower" anti-pattern.
    - Muscle: chained probabilistic structures with short-circuit OR MUST probe the most-likely-hit branch first. Same lesson recurs in: W39 SSTable level-walk (L0 → L_max, but probe newest L0 SSTs first), W37 skiplist tower descent (top-down — already correct), W77 aeron multicast Image lookup (most-recent term first).
  - **Expect to hit (perf) #2 — geometric growth makes slice S the only cache-warm slice; cold slices dominate negatives (bar (c) violation)**: at S=7 with growth_factor=2, slice 7 is 64× larger than slice 0 — slice 0-3 are tiny enough to fit in L2 (always warm), but slice 4-7 are DRAM-resident. A negative contains MUST probe ALL S slices before returning false; under any miss-heavy workload (storage-trie pruner asking "have we already pruned this?" — most answers are NO), every negative pays ~S × DRAM latency ≈ ~700 ns. At 5 M neg/sec that's ~3.5 sec/sec CPU on negatives — the filter's whole advantage over a B-tree evaporates.
    - Fix: keep a *summary* bloom across all slices — a single small block-bloom (~64 KB, always L2-resident) that's the OR of every slice's "key was ever inserted" signal. `contains` first probes the summary; if 0, return false (1 cache line touched). Only on summary=1 do we probe slices. Trade-off: summary's FPR caps the aggregate at summary_fpr (must be ≤ target); maintaining the summary is one extra insert per main insert (~25 ns amortized, paid once).
    - Cost avoided: negative contains drops from ~S × DRAM = ~700 ns to ~10 ns (one warm L2 probe); at 5 M neg/sec, ~3.4 sec/sec CPU reclaimed; restores the scalable bloom's value prop (≤ B-tree negative cost).
    - Muscle: chained filters where most queries are negative need a *summary* / *header* filter that short-circuits in one cache line; without it, the chained design's worst-case dominates. Reapplies at: W39 SSTable level-skip filter (per-level summary bloom to avoid probing every L_i SST), W101 vector-db segment manager (per-segment summary), W95 mini-db CAPSTONE compaction filter.
  - **Test scenarios**:
    - Insert 10M unique with target_fpr=0.01; measured aggregate FPR ≤ 0.012.
    - No false negatives across 10M.
  - **Acceptance**: aggregate FPR within tolerance over 100x design capacity.
  - **Downstream**: storage-trie pruning (Thursday); long-lived dedup indices in vector-db (W101).
