- [ ] Re-read mini-lsm bloom section. Read "Cache, Hash, and Space-Efficient Bloom Filters" (Putze et al.). FPR math: m

- [ ] **Build**: `crates/bloom/src/classic.rs` — `BloomFilter { bits: BitVec, k: u8, hasher_seeds: [u64; 4] }` with
  `with_fpr_at_capacity(fpr, n)` constructor. (~total 110 min across 3 phases)
  - 🔧 **Why this matters**: every LSM read path (W39 SSTable filter block, W95 mini-db CAPSTONE) starts with a
    bloom probe. The math is unforgiving — under-provision bits or hashes and FPR spikes; over-provision and you
    waste cache. The block-bloom layout decision (perf pitfall) determines whether bloom probe cost is ≤5% of
    CPU budget or eats 35% of it; downstream consumers inherit the choice.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: probabilistic set membership with tiny memory footprint, used to skip
    99% of SSTable reads that would otherwise be wasted. Wrong sizing → FPR collapse. Wrong layout → cache-line
    scatter dominates. Wrong hash → biased bits → silent FPR degradation under specific workloads.

  - **Requirements** — write in `crates/bloom/notes/34_classic_design.md`:
    - R1. `with_fpr_at_capacity(fpr, n)` sizes via closed form: `m = ceil(-n*ln(p)/ln(2)^2)`, `k = max(1,
      round(m/n*ln(2)))`. The `max(1, k)` is load-bearing — `round()` can yield 0 for sparse cases.
    - R2. No false negatives: every inserted key returns `true` on `contains`.
    - R3. Measured FPR ≤ 1.2 × design FPR at design capacity (1 M inserts, 10 M disjoint lookups).
    - R4. Determinism: identical key + seeds → identical k bit positions across runs (no per-call randomness).
    - R5. **Block-bloom layout**: all k probes for one key land in the same 64-byte block (one cache line per
      `contains`, regardless of k).
    - R6. **Hardware popcount** for cardinality / union / intersection — `u64::count_ones()` per word, not a
      per-bit loop.
    - R7. Seeds serialize with the filter — a deserialized filter MUST probe identical positions to the
      original.

  - **Design walk-through** — answer each:
    - D1. The closed-form math: derive `m` and `k` from target FPR `p` and `n` keys. What does `k=0` mean?
      Why is `max(1, k)` necessary (cite a concrete case where `round(...)` yields 0)?
    - D2. Kirsch-Mitzenmacher double-hashing: from 2 base hashes `h1, h2`, generate `k` indices via `pos_i =
      (h1 + i*h2) mod m`. Why is this acceptably independent? What's the FPR penalty vs `k` independent hashes
      (cite KM 2006)?
    - D3. **Block-bloom layout (load-bearing for perf)**: contrast a flat `BitVec[0..m]` with 64-byte blocks
      `[Block; m/512]`. For each `contains`, where do the k probes land? How many cache lines touched?
    - D4. Modulo bias: `pos % m` for non-power-of-2 `m` is biased. What's the fix (Lemire 2016 multiply-shift)?
      When does this matter (k > 5 + adversarial input)?
    - D5. The block layout's FPR penalty: ~10-15% worse than flat for the same memory. Justify the trade.
    - D6. **Pre-mortem (load-bearing)**: write the workload where flat-bloom collapses (random key probes into
      1.2 MiB filter; k=7 cache misses per probe at 5 M ops/sec = 3.5 sec/sec CPU). Then write what changes
      with block-bloom.
  - **Output**: `notes/34_classic_design.md` with R1–R7, D1–D6, the flat vs block bench projection.

  #### Phase 3 — Make the tests pass, one failure at a time (~55 min)

  - **When `classic_fpr_within_tolerance` reports 100% FPR:**
    - Symptom: every disjoint lookup returns `true`; the filter is degenerate.
    - Why: `k` was rounded to 0 (e.g. `n > m` because callers passed a too-tight FPR for the alloc budget),
      and you didn't clamp. `k=0` means no bits set per insert; `contains` always returns the empty `and` =
      `true`.
    - Fix: `k = max(1, round(m/n * ln(2)))`. Document the impossible-FPR case as a sizing error and consider
      returning `Err` from `with_fpr_at_capacity` if `m/n` is degenerate.
    - Muscle: closed-form sizing must clamp at the degenerate boundaries. Reapplies at: W34 counting bloom
      sizing, W101 vector-db PQ codebook sizing.

  - **When `bench_block_bloom_one_cacheline_per_contains` reports ~7 cache misses per `contains` (instead of
    the expected ~1):**
    - Symptom: `perf stat` shows ~7 LLC-loads per negative `contains` on the 1.2 MiB filter; cliff vs the
      target is ~7×.
    - Why: flat `BitVec` layout — each of the k probe positions is computed independently of the others, so
      they scatter across k random cache lines.
    - Fix: **block-bloom** layout (RocksDB-style) — partition bits into 64-byte blocks (one cache line each);
      for each key, derive `block_idx = h1 % num_blocks`, then all k probes land in the SAME block via `for i
      in 0..k { bit = (h1 + i*h2) % 512 in that 64-byte block }`. One cache line touched per `contains`,
      regardless of k. FPR penalty: ~10-15% higher than flat for the same memory (Putze et al. show this is
      bounded); CPU win: ~7× on contains.
    - Cost avoided: ~7 cache misses → 1 per contains; at 5 M get/sec, ~3 sec/sec CPU reclaimed cold; positive
      contains on warm L1 stays ≤ 25 ns (one cache line, k bit-tests). The bloom cost stays inside the 5%
      budget for W39 SSTable read.
    - Muscle: probabilistic filters whose probe count exceeds 1-2 MUST use a block layout that keeps all
      probes within one cache line; flat bloom is only acceptable for k ≤ 2 (e.g., quotient filters with k=1).
      Reapplies at: W39 SSTable bloom filter block (already uses block-bloom variant), W95 mini-db CAPSTONE
      filter block, W101 vector-db filtered-search bitmap (which uses a similar block-tile structure).

  - **When `bench_cardinality_hardware_popcount` reports ~10 ms instead of ~200 µs:**
    - Symptom: `cardinality()` over 9.6 Mbits takes ~10 ms; flamegraph shows ~10 M iterations through
      `bits.iter().filter(...).count()`.
    - Why: scalar bit-by-bit loop. Each iteration is ~1 ns; at 9.6 M bits = 10 ms.
    - Fix: cast `bits.as_raw_slice()` to `&[u64]` and call `u64::count_ones()` per word — hardware popcount on
      x86 (POPCNT, ~1 cycle/word) and aarch64 (`CNT`, ~3 cycles/word) processes 64 bits/op. At 9.6 Mbits = 150
      K u64 words, ~150 µs vs ~10 ms — **~60× speedup**. The Rust intrinsic `u64::count_ones()`
      autovectorizes to POPCNT on `target_cpu=native` or with `is_x86_feature_detected!("popcnt")` runtime
      detection.
    - Cost avoided: ~10 ms → ~150 µs per cardinality; ~60× cardinality / union / intersection speedup;
      eliminates the LSM compaction CPU spike at filter-merge time (W39 Tuesday).
    - Muscle: bitwise operations over arrays MUST go through `u64`-wise hardware intrinsics (`count_ones`,
      `leading_zeros`, AVX2 `_mm256_and_si256`); the per-bit loop is correctness-only and disqualifies bar
      (c). Reapplies at: W39 SSTable bloom union for L0→L1 compaction merge, W101 vector-db roaring-bitmap
      intersection, W95 mini-db CAPSTONE filter merge during compaction.

  - **When `classic_serialization_round_trip` reports false negatives after deserialization:**
    - Symptom: serialize filter, deserialize, query an inserted key — returns `false`. Silent data loss.
    - Why: seeds were regenerated on deserialization (or defaulted) — different seeds → different probe
      positions → bits checked in the wrong places.
    - Fix: seeds are part of the filter's serialized header. Persist `(m, k, seed0, seed1)` alongside the bit
      array; require them on deserialize.
    - Muscle: any hash-based primitive's seeds are part of its identity — serialize them. Reapplies at: W34
      counting/scalable bloom serialization, W101 vector-db PQ centroids.

  - **5-year failure mode** (write in `notes/34_classic_followup.md` after green): when AVX-512 VPOPCNTQ
    + bit-shuffle becomes universally available, the per-word popcount becomes a 512-bit vector op (~1
    cycle per 8 words); a 9.6 Mbit cardinality could drop from 150 µs to ~20 µs. State the migration: gate
    AVX-512 path via runtime detection; keep scalar+popcount as the portable fallback.

**Tuesday — Counting bloom + Reth pruning code**

- [ ] **Build**: `crates/bloom/src/counting.rs` — `CountingBloom` with u4 or u8 counters. Supports deletion. (~total 110 min across 3 phases)
  - 🔧 **Why this matters**: classic bloom can't delete. Storage-trie pruner (Thursday) needs the
    "still-present" filter to shrink as pruned keys are removed; without deletion support, the filter
    saturates and FPR climbs unboundedly. Counting bloom's perf-pitfall pair (u4 nibble extract, branchy
    saturation) is the difference between ~80% slower than classic (acceptable) and ~4× slower (broken).

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: counting bloom enables `remove(key)` by storing small counters
    instead of bits — `insert` increments, `remove` decrements, `contains` checks all counters > 0. The catch
    is the per-probe overhead: nibble extraction (u4 packing for memory) and saturation handling (preventing
    counter overflow/underflow corruption). Both must be branchless.

  - **Requirements** — write in `crates/bloom/notes/34_counting_design.md`:
    - R1. `insert(key)` increments k counter positions; `remove(key)` decrements; `contains(key)` checks all
      k counters > 0.
    - R2. Counter saturation at MAX (15 for u4, 255 for u8): further inserts at saturated buckets are silent
      no-ops; removes of saturated stay saturated (no underflow).
    - R3. **Underflow protection**: removing a key never inserted is a debug-panic; release-mode it's a
      saturating decrement at 0.
    - R4. **u4 nibble extract is branchless** — bit ops (`>> 1`, `& 1` shift) only; no div, no mod, no parity
      branch on the hot path.
    - R5. **Saturation check is branchless** — CMOV/CSEL via `.min()` / `.max()` / `as` casts; no `if c < 15`
      conditional.
    - R6. Block-bloom layout inherited from classic — one cache line per op.
    - R7. Round-trip correctness: insert N, remove N; filter is empty (all counters 0).

  - **Design walk-through** — answer each:
    - D1. u4 packing — two counters per byte. Write the bit layout: which 4 bits hold counter[2i], which
      hold counter[2i+1]?
    - D2. The branchless u4 extract: `let byte = counters[i >> 1]; let shift = (i & 1) << 2; let nibble =
      (byte >> shift) & 0xF;` — explain each line. Why is `i >> 1` better than `i / 2` (compiler-version
      regression resistance)?
    - D3. Branchless saturating add: write the two formulations — `min()` vs bit-twiddle — and identify which
      generates CMOV vs CSEL on x86 / aarch64.
    - D4. Why u4 (not u8)? Memory: u4 = m/2 bytes; u8 = m bytes. For the pruner's 1 M entries at p=0.01: u4
      ≈ 4.8 MiB (L3-resident), u8 ≈ 9.6 MiB (DRAM-spilling). The 2× win matters; the saturation drift at
      counter=15 is the trade.
    - D5. Concurrent insert/remove safety: u4 packing makes two neighboring counters share a byte. Document
      the policy: this filter is **single-threaded** by default; multi-thread requires u8 + AtomicU8 CAS.
    - D6. **Pre-mortem (load-bearing)**: under what workload does the div/mod pitfall fire (random key
      probes, k=7, 5 M ops/sec)? Compute the wasted CPU. Same for the saturation branch under skewed-hot
      workload.
  - **Output**: `notes/34_counting_design.md` with R1–R7, D1–D6.

  #### Phase 3 — Make the tests pass, one failure at a time (~55 min)

  - **When `bench_counting_branchless_nibble_extract` shows ~50 ns/contains and asm contains `div` instructions:**
    - Symptom: bench reports ~50 ns/contains vs ~25 ns target; `cargo asm` shows `idiv` (x86) / `udiv`
      (aarch64) on the nibble extract path.
    - Why: `get_counter(i) -> u8` implemented as `let byte = counters[i / 2]; if i % 2 == 0 { byte & 0xF }
      else { byte >> 4 }` puts a div + mod on the hot probe path. While LLVM often canonicalizes `% 2` to
      AND, it does NOT always strength-reduce `i / 2` when `i` is a non-constant u64 — that's a ~10-cycle
      integer div per probe (~3 ns) and at k=7 probes × 5 M contains/sec ≈ ~100 ms/sec of pure div. Worse,
      the branch on parity is unpredictable for random keys → ~5 ns mispredict per probe.
    - Fix: replace div/mod with bit ops — `let byte = counters[i >> 1]; let shift = (i & 1) << 2; let nibble
      = (byte >> shift) & 0xF;` — ~1 cycle each, branchless. Compiler may already do this on `i / 2`, but
      `i >> 1` makes the intent explicit and immune to compiler-version regressions. Verify with `cargo
      asm` once.
    - Cost avoided: ~3 ns/probe div + ~5 ns/probe branch mispredict → ~50 ns/contains saved at k=7; ~250
      ms/sec at 5 M contains; restores counting-bloom probe cost to ~2× classic (instead of ~4× with
      div/branch).
    - Muscle: integer division by power-of-2 MUST be `>> log2(n)`; modulo by power-of-2 MUST be `& (n-1)`;
      never trust the compiler to strength-reduce on non-constant divisors. Reapplies at: W37 skiplist
      height computation (`height & (max_height - 1)`), W77 aeron term-id `% term_length` → mask, W101
      vector-db PQ codebook index lookup.

  - **When `bench_counting_branchless_saturation` shows variable throughput depending on saturation level:**
    - Symptom: under a uniform workload throughput is ~stable; under a skewed-hot workload (some buckets
      saturate at 15 within 1k inserts), throughput drops 2-3× and stays there.
    - Why: `if c < 15 { counters[i] += 1 }` adds a branch that mispredicts on saturated buckets — under
      storage-trie's long-tail prune workload (some hot bits hit 15 quickly), the mispredict rate climbs to
      ~10-20% and every insert pays ~5 ns.
    - Fix: branchless saturating add — `counters[i] = (counters[i] + 1).min(15);` or with bit-twiddle: `let
      c = counters[i]; counters[i] = c + ((c < 15) as u8);` — the compiler emits a CMOV/CSEL (~1 cycle, no
      branch) instead of a conditional jump. Same trick for saturating decrement: `c - ((c > 0) as u8)`.
    - Cost avoided: ~5 ns/probe mispredict at saturation; at k=7 × 1 M insert/sec ≈ ~35 ms/sec at moderate
      saturation, ~70 ms/sec at high saturation; smooth perf curve as the filter fills.
    - Muscle: any "clamp/saturate" on the hot path MUST be branchless (CMOV/CSEL via `.min()`, `.max()`, or
      `as u8` casts); explicit `if` branches are correctness-only. Reapplies at: W11 backpressure credit
      clamp, W74 matching-engine price-band clamp, W77 aeron flow-control window clamp, W11 bounded-MPMC
      ring full-check.

  - **When `counting_saturation_no_underflow` reports false negatives on the heavily-saturated bucket:**
    - Symptom: insert 30 times (saturates at 15), remove 30 times → counter wraps 0 → 255 (u8) or 0 → 15
      (u4); subsequent `contains` for real keys probing that bit returns `false`.
    - Why: remove of a saturated counter (where some inserts were silently dropped) eventually decrements
      past 0; without saturating-on-decrement, the counter wraps.
    - Fix: saturating decrement at 0 (use `saturating_sub(1)` or `c - ((c > 0) as u8)`); document that
      saturated buckets cannot be fully cleared — this is the inherent drift of u4 counters.
    - Muscle: any counter that can saturate at the top must saturate at the bottom too — wrapping is
      silent corruption. Reapplies at: W11 backpressure credit, W77 aeron flow-control window.

  - **5-year failure mode** (write in `notes/34_counting_followup.md` after green): when AVX-512 mask
    registers + ternary logic ops mature, both the u4 extract and the saturation can become 16-wide vector
    ops; bench expectation collapses by ~16×. State the migration: gate AVX-512 via runtime detection;
    scalar+CMOV path remains the portable fallback.

**Wednesday — Scalable bloom + storage-trie pruning design**

- [ ] **Build**: `crates/bloom/src/scalable.rs` — `ScalableBloomFilter` chains classic filters with tightening FPR (
  Almeida et al.). Grows without rebuild. (~total 110 min across 3 phases)
  - 🔧 **Why this matters**: storage-trie pruner (Thursday) and vector-db dedup index (W101) hit streaming
    workloads where you don't know `n` ahead of time. Without a scalable design, you either over-size (waste)
    or hit FPR collapse beyond design capacity. The two perf pitfalls (probe order + summary filter)
    determine whether scalable bloom is competitive with a B-tree on negative lookups or 10× worse.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: chain classic filters with geometrically tightening FPR; new
    inserts go into a new slice when the current saturates. Aggregate FPR stays bounded; `contains` is OR
    across slices. Costs: O(S) per contains where S grows as log(capacity / initial); under skewed
    workloads (recent-bias positive, miss-heavy negative) the order matters dramatically.

  - **Requirements** — write in `crates/bloom/notes/34_scalable_design.md`:
    - R1. `insert` adds to the current slice; on saturation, allocate a new slice with 2× capacity and
      0.5× FPR (Almeida tightening).
    - R2. `contains` returns true iff ANY slice contains; aggregate FPR ≤ target across S slices.
    - R3. **Probe order is newest-first** — `self.slices.iter().rev().any(|s| s.contains(key))`. OR is
      commutative; order affects latency distribution only.
    - R4. **Summary filter** — a single small block-bloom (~64 KB, L2-resident) that's the OR of every
      slice's "ever inserted" signal; `contains` first probes the summary for short-circuit.
    - R5. Per-slice seeds derive from `master_seed + slice_index` — slices must NOT share seeds (adversarial
      input could target multiple).
    - R6. Bounded slice count — cap at `max_slices` (e.g. 32); past that, return `Err` or trigger
      rebuild-into-classic.
    - R7. No false negatives across 10 M inserts at design capacity.

  - **Design walk-through** — answer each:
    - D1. Almeida math: derive per-slice FPR for target aggregate FPR = 0.01 over S slices with tightening
      = 0.5. Show that the geometric series of per-slice FPRs sums to target.
    - D2. The 2× growth: at S = 7, slice 0 is sized for `n0` keys, slice 7 for `64*n0`. What's the total
      memory as a multiple of slice 7's size? Why does slice S dominate the footprint?
    - D3. Newest-first probe order — for a "recent-bias" workload (most queries hit recent inserts), what's
      the average # of slices probed per positive contains? Compare to oldest-first.
    - D4. The summary filter — sketch its sizing. Why is its FPR a CAP on the aggregate (must be ≤ target)?
    - D5. Per-slice seeds — write the derivation: `slice_seed_0 = master_seed_0 ^ slice_index`,
      `slice_seed_1 = master_seed_1 ^ slice_index`. Why is plain `master_seed + i` weaker than XOR?
    - D6. **Pre-mortem (load-bearing)**: write the workload where oldest-first probe order collapses
      (recent-bias, S=7, 5 M ops/sec). Compute wasted CPU. Then write the workload where no-summary
      collapses (miss-heavy, S=7, DRAM-resident slices).
  - **Output**: `notes/34_scalable_design.md` with R1–R7, D1–D6.

  #### Phase 3 — Make the tests pass, one failure at a time (~55 min)

  - **When `bench_scalable_recent_bias_newest_first` reports ~7 slices probed per positive contains:**
    - Symptom: under recent-bias workload, positive `contains` averages ~S slices probed; positive
      latency ≈ S × per-slice cost ≈ ~175 ns vs ~25 ns for a sized classic.
    - Why: probing slices in INSERTION order (oldest first) means a positive hit on slice S (the newest,
      where the most recent inserts live) requires probing all S-1 prior slices first. Under a
      "recent-bias" workload (cache-of-recent, append-mostly streams), positive contains is ~S× classic
      cost — at S=7, that's ~175 ns per positive vs ~25 ns for a sized classic. The storage-trie
      pruner's "is this key still present?" check hits the newest slice ~70% of the time; reversing the
      order saves ~150 ns per check at scale.
    - Fix: probe slices in REVERSE order (newest first) with OR-short-circuit. The aggregate FPR is
      unchanged (OR is commutative), but the hit-latency distribution skews toward 1 probe instead of
      S. Implement as `self.slices.iter().rev().any(|s| s.contains(key))`. Document the "recent-bias"
      assumption — if the workload is uniform, reverse vs forward is a wash, but no workload is worse
      off with reverse.
    - Cost avoided: ~150 ns per positive at S=7 under recent-bias; at 5 M get/sec storage-trie pruner
      ≈ ~750 ms/sec CPU saved on positive lookups; eliminates the "newer = slower" anti-pattern.
    - Muscle: chained probabilistic structures with short-circuit OR MUST probe the most-likely-hit
      branch first. Same lesson recurs in: W39 SSTable level-walk (L0 → L_max, but probe newest L0
      SSTs first), W37 skiplist tower descent (top-down — already correct), W77 aeron multicast Image
      lookup (most-recent term first).

  - **When `bench_scalable_miss_heavy_summary_short_circuit` reports ~7 cache lines touched per negative:**
    - Symptom: under miss-heavy workload (95% negative), each negative `contains` probes all S slices;
      with slices 4-7 DRAM-resident, total ~700 ns per negative. At 5 M neg/sec ≈ ~3.5 sec/sec CPU.
    - Why: at S=7 with growth_factor=2, slice 7 is 64× larger than slice 0 — slices 0-3 are tiny enough to
      fit in L2 (always warm), but slices 4-7 are DRAM-resident. A negative contains MUST probe ALL S
      slices before returning false; under any miss-heavy workload (storage-trie pruner asking "have we
      already pruned this?" — most answers are NO), every negative pays ~S × DRAM latency ≈ ~700 ns. The
      filter's whole advantage over a B-tree evaporates.
    - Fix: keep a *summary* bloom across all slices — a single small block-bloom (~64 KB, always
      L2-resident) that's the OR of every slice's "key was ever inserted" signal. `contains` first
      probes the summary; if 0, return false (1 cache line touched). Only on summary=1 do we probe
      slices. Trade-off: summary's FPR caps the aggregate at summary_fpr (must be ≤ target);
      maintaining the summary is one extra insert per main insert (~25 ns amortized, paid once).
    - Cost avoided: negative contains drops from ~S × DRAM = ~700 ns to ~10 ns (one warm L2 probe); at
      5 M neg/sec, ~3.4 sec/sec CPU reclaimed; restores the scalable bloom's value prop (≤ B-tree
      negative cost).
    - Muscle: chained filters where most queries are negative need a *summary* / *header* filter that
      short-circuits in one cache line; without it, the chained design's worst-case dominates.
      Reapplies at: W39 SSTable level-skip filter (per-level summary bloom to avoid probing every L_i
      SST), W101 vector-db segment manager (per-segment summary), W95 mini-db CAPSTONE compaction
      filter.

  - **When `scalable_per_slice_seed_independence` reports correlated FPR between slices:**
    - Symptom: adversarial input crafted to hit slice 0's specific probe pattern also hits slice 1's
      with higher-than-expected rate; aggregate FPR for the adversarial input is 10× design.
    - Why: per-slice seeds share entropy — e.g. all slices use `master_seed` directly; or `master + i`
      where the +i offset preserves linear structure. Adversarial keys can hit multiple slices'
      probes.
    - Fix: derive per-slice seeds from a hash of `(master_seed, slice_index)` — e.g. `slice_seed =
      xxh3(master_seed, slice_index)`. Each slice's seeds are independent random-looking.
    - Muscle: any chained probabilistic structure needs cryptographic-quality per-slice keying,
      otherwise adversarial input concentrates collisions. Reapplies at: W101 vector-db PQ codebook
      seeding, W95 mini-db CAPSTONE filter seeding.
