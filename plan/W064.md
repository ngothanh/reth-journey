- [ ] **Build**: `crates/consensus-bft/src/lib.rs` with module headers: `propose.rs`, `prevote.rs`, `precommit.rs`,
  `lock.rs`, `evidence.rs`. (~150 min)
  - **Why**: BFT (Tendermint-style) has 3 vote phases: propose → prevote → precommit. Each phase needs 2f+1 votes (out of 3f+1 nodes). Lock state ensures safety across rounds; evidence captures Byzantine misbehavior for slashing.
  - **Design** (Tendermint state machine):
    ```text
    For each height H, sequence of rounds R = 0, 1, 2, ...
    Round R:
      Phase 1: PROPOSE
        - Proposer for round R = (H + R) mod N
        - Broadcasts Proposal { height: H, round: R, value, valid_round }
        - All validators wait propose_timeout
      Phase 2: PREVOTE
        - Each validator broadcasts Prevote { height, round, hash_of_value or nil }
        - On collecting 2f+1 prevotes for same value V:
            - validator locks on V (locked_value = V, locked_round = R)
            - moves to PRECOMMIT phase with V
        - On collecting 2f+1 prevotes for nil OR timeout: prevote nil, advance phase
      Phase 3: PRECOMMIT
        - Each validator broadcasts Precommit { height, round, hash_of_value or nil }
        - On collecting 2f+1 precommits for same value V:
            - COMMIT V at height H. Advance to height H+1.
        - On timeout: precommit nil, advance round
    ```
    ```rust
    pub struct BftState {
        pub height: u64,
        pub round: u32,
        pub step: Step,                   // Propose | Prevote | Precommit | Commit
        pub locked_value: Option<Hash>,
        pub locked_round: Option<u32>,
        pub valid_value: Option<Hash>,
        pub valid_round: Option<u32>,
        pub validators: Vec<NodeId>,
        pub votes: VoteSet,                // per (height, round, step) → votes
    }
    ```
    **Invariants** (BFT safety, paper §4):
    - **Validity**: committed value must be proposed by SOME validator in SOME round.
    - **Agreement**: no two correct validators commit different values at same height (provable assuming < f Byzantine).
    - **Liveness**: assuming < f Byzantine and bounded message delay, eventually some height commits.
    - **Lock semantics**: once a validator locks on V at round R, it cannot precommit any V' ≠ V at later rounds UNLESS it sees 2f+1 prevotes for V' (lock-release rule).

    - *Fork-choice tie-break*: two proposers in same round (shouldn't happen but...). **Symptom**: split prevotes. **Fix**: only one proposer per (height, round) per deterministic formula; reject other proposals.
    - *View-change DoS*: Byzantine validators repeatedly cause round advance without commit. **Symptom**: liveness loss. **Fix**: exponential-backoff on propose_timeout; eventually network synchrony restored.
    - *Lock-release wrong*: releasing lock prematurely → safety violation. **Symptom**: 2 nodes commit different values. **Fix**: STRICTLY require 2f+1 prevotes for new value before unlocking.

  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: in a Byzantine setting, you cannot trust any single validator's proposal — yet exactly one validator per (height, round) must propose, and all honest validators must agree on the proposal hash to make progress. The propose phase establishes the candidate value AND the validity rules that let honest validators safely prevote. Done naïvely (per-message ed25519 verify, sequential broadcasts), the phase eats your entire block-time budget before the network speaks.

  - **Requirements** — write in `crates/consensus-bft/notes/64_propose_design.md`:
    - R1. `Proposal { height, round, value, valid_round: i32, signature }` is the wire type. `valid_round = -1` means "first proposal at this height", else "I saw 2f+1 prevotes for `value` at round `valid_round`."
    - R2. **Deterministic proposer selection**: `proposer_for(height, round, validators) = validators[(height + round) % n]`. Exactly one valid proposer per (h, r); other proposals rejected.
    - R3. **Lock priority**: when handling a proposal, the validator prevotes its `locked_value` if locked AND the proposal disagrees, EXCEPT when the proposal's `valid_round` exceeds the validator's `locked_round` (Tendermint Annex A lock-release).
    - R4. **Block-time budget**: n=4 validators (committee LAN) → 1 s per height; n=21 validators (geo-WAN) → 300 ms per height. Round = 1 propose + n prevote + n precommit = O(n²) messages.
    - R5. **Batched sig verify**: ed25519 verify is done in batches of 8-32 messages via `ed25519-dalek::verify_batch` (~6 µs/msg amortized vs ~50 µs single). Single `verify` calls on the hot path are forbidden.
    - R6. **Single-serialize broadcast**: the proposal bytes are serialized ONCE into a pooled `Arc<Bytes>` and scattered to all peers via `sendmmsg(2)` or equivalent. Never re-encode per peer.
    - R7. **Zero-alloc steady state**: proposal + vote messages reuse pre-allocated buffers from a per-validator pool (cap = 2 × n × max_in_flight_rounds ≈ 256 at n=21).
    - R8. **Safety preserved under Byzantine proposer**: with f Byzantine out of 3f+1, honest validators commit at most one value per height; safety verified by a model test.

  - **Design walk-through** — answer each in your design doc; no peeking at tendermint-rs `proposal.go` until Phase 3:
    - D1. Sketch `Proposal`. Why `valid_round: i32` not `Option<u32>`? (Hint: wire compatibility with the Tendermint spec; -1 is the sentinel.)
    - D2. Write `proposer_for` in 1 line. Why round-robin and not "elect by stake" for v0.1? When would you switch?
    - D3. `on_enter_propose` flow: 5 numbered steps from "round starts" to "vote timer set". What does the proposer do that a non-proposer doesn't?
    - D4. `handle_proposal` flow: 6 numbered steps from "RPC arrives" to "vote sent". The lock-priority rule (R3) is the trickiest — write the 3-case dispatch (no lock → prevote value; lock matches → prevote value; lock differs → check valid_round).
    - D5. Why is per-message ed25519 verify catastrophic at n=21? Compute: 441 messages/round × 50 µs = ? Compare to the 300 ms block-time budget.
    - D6. Batched verify integration: when does the verifier flush? (Hint: when batch fills OR a timeout fires.) What's the right batch size? (Hint: 8-32; trade-off latency vs throughput.)
    - D7. Broadcast plan: write the `broadcast_proposal` pseudocode. How does it avoid the N serializes / N syscalls? (Hint: `sendmmsg(2)` on Linux; `gather_send` shim on macOS.)
    - D8. **Pre-mortem #1 (verify storm)**: write the 5-step trace at n=21 where per-message verify dominates a 300 ms round. Compute the failure mode.
    - D9. **Pre-mortem #2 (lock-override attack)**: write the 7-step trace where a Byzantine proposer + 2 colluding validators try to trick an honest locked validator into prevoting a different value. Identify which rule (R3 + valid_round mechanism) defeats the attack.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  - **When `bench_verify_batched_under_10us_per_msg` reports ~50 µs per message:**
    - Symptom: bench shows ~50 µs per message even though it's labeled "batched". `perf record` shows `ed25519::verify` at >70% of CPU; `n_21_round_under_300ms` fails because verify alone eats ~22 ms/round.
    - Why: you called `ed25519_dalek::verify` once per message instead of `verify_batch`. The "batched" was aspirational; the code path is still single-message.
    - Fix: replace single-verify call sites with a `VerifyQueue` that accumulates up to 32 messages (or until a 1 ms flush timer fires) and calls `ed25519_dalek::verify_batch(&pubkeys, &msgs, &sigs)`. Amortized cost drops to ~6 µs/msg. Add the `lint_no_single_verify_in_hot_path` lint to CI to prevent regressions. For v1.0 (W73), swap ed25519 for BLS aggregate (n prevotes → 1 verify); the `VerifyQueue` abstraction stays the same.
    - Cost avoided: ~44 µs per message; at n=21 saves ~19 ms/round → ~70 ms of round-trip latency back in budget; brings n=21 round under 300 ms.
    - Muscle: any per-message crypto on a hot path must be batched or aggregated; never single-message in steady state. Reapplies at: W65 prevote / precommit (same verify hot path), W67 consensus-raft AppendEntries (HMAC batching), W73 evidence verify (batch on intake), W74 matching-engine raft signatures, W83+ ledger-deterministic VSR PrepareOk batching.

  - **When `bench_broadcast_one_syscall` reports 21 syscalls and 21 RLP encodes per proposal:**
    - Symptom: `strace` shows 21 sequential `sendto` calls per propose; broadcast latency ~6 µs scales linearly with cluster size. RLP encode runs 21 times for identical bytes.
    - Why: naive `for peer in self.validators { self.network.send(peer, prop) }` issues N separate syscalls and N separate serializes.
    - Fix: serialize ONCE into a pooled `Arc<Bytes>` (Arc-backed so each peer share gets a cheap refcount bump). Then use `sendmmsg(2)` on Linux (one syscall, up to N messages) or a `gather_send` shim on macOS. The proposal bytes are immutable across recipients — share them. Pool the buffer; never allocate per-propose.
    - Cost avoided: (n-1) syscalls (~300 ns each) + (n-1) RLP encodes (~200 ns each) = at n=21, ~10 µs saved per round, plus eliminates allocator churn (20 small `Vec`s/round → 0).
    - Muscle: "broadcast" = serialize once, scatter; never serialize-per-peer. Reapplies at: W65 prevote/precommit broadcast, W67 raft AppendEntries to followers, W74 matching-engine MBO fan-out, W76 messaging-aeron multicast publication.

  - **When `honest_prevotes_locked_value_when_proposal_differs` shows the validator prevoting the proposal's value (NOT its lock):**
    - Symptom: locked validator receives a proposal for a different value at a later round with `valid_round = -1` (no prior majority); test expected `Prevote(L)` but got `Prevote(X)`. Safety violated — if this trace runs in production, two honest validators could commit different values.
    - Why: your `handle_proposal` checked the proposal's validity (signature, proposer correctness) but didn't enforce the lock-priority rule. The code path is: signature OK → cast `Prevote(p.value)` — bypassing the locked_value check.
    - Fix: in `handle_proposal`, after signature/proposer checks, the dispatch is: (1) if `locked_value.is_none() || locked_value == Some(p.value)` → `Prevote(p.value)`; (2) else if `p.valid_round > locked_round` AND we have evidence of 2f+1 prevotes for `p.value` at round `p.valid_round` → unlock + `Prevote(p.value)`; (3) else → `Prevote(nil)`. The order matters: lock check FIRST, valid-round-release SECOND.
    - Muscle: BFT lock semantics are the safety floor — every code path that emits a prevote must check the lock first, never the proposal value first. Reapplies at: W65 prevote phase, W68 ship test, W73 BLS-aggregated prevote.

  - **When `byzantine_proposer_no_safety_violation` reports two honest validators committed different values at height 47:**
    - Symptom: 4-node sim, v1 Byzantine; at height 47 v0 and v3 commit value A while v2 commits value B. Safety provably violated.
    - Why: either (a) the lock-release rule is wrong (releasing without 2f+1 evidence), (b) the proposer-selection differs across honest validators (e.g., differs because one validator updated `validators` slice mid-round), or (c) the valid_round check accepts unverified claims.
    - Fix: walk the rule again. R3 (Annex A): unlock ONLY if you have direct evidence — you SAW the 2f+1 prevotes for the new value at the claimed valid_round. A proposer's CLAIM of `valid_round = R` is not sufficient evidence; you check your own vote-set at round R. If you don't have 2f+1 there, prevote nil. Reproduce the failing trace; pinpoint the rule that was bypassed.
    - Muscle: safety in BFT comes from the lock-release rule — every shortcut that "trusts the proposer" is a safety bug waiting for a Byzantine adversary. Reapplies at: W68 BFT safety test, W73 BLS variant must preserve identical lock semantics.

  - **When `propose_zero_alloc_steady_state` reports ~50 allocs per proposal:**
    - Symptom: heaptrack traces ~50 allocs/propose; at 1 proposal/sec/round and 21 nodes, that's ~1k allocs/sec just for propose flow.
    - Why: each `Proposal` construction allocates `Signature` (`Vec<u8>`), the `Bytes` envelope allocates a fresh buffer, and the broadcast iterator clones the validator list. Steady-state alloc rate is non-zero.
    - Fix: pre-allocate per-validator pools for: (a) signature buffers (fixed size 64 B), (b) serialized proposal buffers (Arc<Bytes> pool of ~256 slots), (c) the broadcast routing table (a `&[NodeId]` reference, not a clone). All allocations migrate from per-propose to per-init.
    - Muscle: bar-(c) consensus paths are zero-alloc in steady state — pool every recurring allocation. Reapplies at: W65 vote pools, W67 raft RPC pools, W74 raft over matching-engine.

  - **5-year failure mode** (write in `notes/64_propose_followup.md` after green): when v1.0 ships BLS aggregate signatures (W73), the `VerifyQueue` abstraction collapses — N prevotes for the same value aggregate into ONE signature, ONE verify call. State the migration: replace `ed25519::verify_batch` calls with `bls::aggregate_verify`; the queue becomes a per-(height, round, value) accumulator. Trigger: W73 BLS dependency lands; HotStuff/Diem-style consensus becomes viable.
