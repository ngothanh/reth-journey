    - State machine (the design you must NOT change later without a note):
      ```text
      Height H, rounds R = 0,1,2,...
        PROPOSE   : proposer = validators[(H+R) % n] broadcasts Proposal{H,R,value,valid_round}; others wait propose_timeout
        PREVOTE   : broadcast Prevote{H,R, hash|nil}; 2f+1 same-value V → lock(V,R), go PRECOMMIT(V); 2f+1 nil/timeout → prevote nil
        PRECOMMIT : broadcast Precommit{H,R, hash|nil}; 2f+1 same-value V → COMMIT V at H, go H+1; timeout → precommit nil, advance R
      ```
      ```rust
      pub struct BftState {
          pub height: u64,
          pub round: u32,
          pub step: Step,                 // Propose | Prevote | Precommit | Commit
          pub locked_value: Option<Hash>,
          pub locked_round: Option<u32>,
          pub valid_value: Option<Hash>,
          pub valid_round: Option<u32>,
          pub validators: Vec<NodeId>,
          pub votes: VoteSet,             // per (height, round, step) → votes
      }
      ```
    - **Invariants** (paper §4 — record verbatim in the lib.rs module doc so W65/W68 don't re-derive):
      - *Validity*: a committed value was proposed by some validator in some round.
      - *Agreement*: no two correct validators commit different values at the same height (holds while Byzantine < f+1, i.e. ≤ f).
      - *Liveness*: with ≤ f Byzantine and bounded delay, some height eventually commits.
      - *Lock semantics*: once locked on V at round R, a validator cannot precommit V'≠V at a later round UNLESS it directly sees 2f+1 prevotes for V' (the lock-release rule — the safety floor, trap-tested Saturday).

  #### Phase 1 — Problem, prediction, design (~60 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/consensus-bft/notes/64_propose_prediction.md`:
    - P1. The primitive you'd reach for to verify a proposal's signature (exact import line). Predict its single-call latency in µs.
    - P2. Predicted `sendto`/`sendmmsg` syscall count for a naive `for peer in validators { send }` broadcast at n=21.
    - P3. Predicted outcome when a locked validator (locked on L at round 1) receives a proposal for X≠L at round 2 with `valid_round = -1`: will your first `handle_proposal` prevote L or X?
    - P4. Predicted steady-state allocations per proposal (signature buffer? Bytes envelope? validator-list clone?).
    - P5. **List every Phase-2 test you predict your first attempt will FAIL.** Compare to reality after the tests run.

  - *Mental model*: `propose.rs` establishes the single candidate value for a (height, round) and the validity rules that let honest validators safely prevote it. Exactly one validator proposes per (h,r); everyone else verifies and prevotes under the lock rule.

  - *Contract* (signature-level — never the body):
    - `pub struct Proposal { height: u64, round: u32, value: Hash, valid_round: i32, signature: Sig }`
    - `pub fn proposer_for(height: u64, round: u32, validators: &[NodeId]) -> NodeId`
    - `fn on_enter_propose(&mut self) -> Option<Proposal>`  (Some if I'm the proposer)
    - `fn handle_proposal(&mut self, p: &Proposal) -> Result<Prevote, ProposeError>`  (`ProposeError::WrongProposer`, `::BadSig`)
    - `fn broadcast_proposal(&self, p: &Proposal, peers: &[NodeId])`  (serialize once, scatter)

  - *Back-of-envelope* (bar (c), Jeff-Dean):
    - n=4 LAN committee → ~1 s/height budget; n=21 geo-WAN → ~300 ms/height.
    - Messages/round = 1 propose + n prevote + n precommit ≈ O(n²) on full gossip; verifies/round at n=21 ≈ 441.
    - Single ed25519 `verify` ≈ 50 µs; `verify_batch`(32) ≈ 6 µs/msg amortized → **cliff ratio ≈ 8×** on the verify path. At n=21: 441×50 µs = ~22 ms single vs ~2.6 ms batched. The 22 ms alone is 7% of a 300 ms round; do it on the wrong path and round-trips stack to a timeout.
    - Per-peer `sendto` ≈ 300 ns syscall + ~200 ns RLP encode; at n=21 naive = ~10.5 µs + 20 small `Vec` allocs/round vs one `sendmmsg` + 0 allocs.

  - **Requirements** R1–R8 — write in `crates/consensus-bft/notes/64_propose_design.md`:
    - R1. `Proposal { height, round, value, valid_round: i32, signature }` is the wire type. `valid_round = -1` = "first proposal at this height"; else "I saw 2f+1 prevotes for `value` at round `valid_round`."
    - R2. **Deterministic proposer**: `proposer_for(h, r, v) = v[(h + r) % n]`. Exactly one valid proposer per (h,r); other proposals → `WrongProposer`.
    - R3. **Lock priority**: when handling a proposal, prevote `locked_value` if locked AND the proposal disagrees, EXCEPT when the proposal's `valid_round > locked_round` AND you directly hold 2f+1 prevotes for `value` at `valid_round` (Annex A lock-release). Lock check FIRST, valid-round release SECOND.
    - R4. **Block-time budget**: n=4 → 1 s/height; n=21 → 300 ms/height. A round is O(n²) messages.
    - R5. **Batched sig verify**: ed25519 verify runs in batches of 8-32 via `verify_batch` (~6 µs/msg amortized). Single `verify` on the hot path is forbidden.
    - R6. **Single-serialize broadcast**: proposal bytes serialized ONCE into a pooled `Arc<Bytes>`, scattered via `sendmmsg(2)` (Linux) / `gather_send` shim (macOS). Never re-encode per peer.
    - R7. **Zero-alloc steady state**: proposal + vote messages reuse pre-allocated per-validator pools (cap ≈ 2 × n × max_in_flight_rounds ≈ 256 at n=21).
    - R8. **Safety under Byzantine proposer**: with f Byzantine of 3f+1, honest validators commit ≤1 value/height; verified by a model test.

  - **Design walk-through** D1–D9 — answer in the design doc; no peeking at tendermint-rs `proposal.go` until Phase 3:
    - D1. Sketch `Proposal`. Why `valid_round: i32` not `Option<u32>`? (Wire-compat with the Tendermint spec; -1 is the sentinel.)
    - D2. Write `proposer_for` in 1 line. Why round-robin, not stake-weighted, for v0.1? When would you switch?
    - D3. `on_enter_propose`: 5 numbered steps from "round starts" to "vote timer set". What does the proposer do that a non-proposer doesn't?
    - D4. `handle_proposal`: 6 numbered steps from "RPC arrives" to "vote sent". Write the lock-priority 3-case dispatch (no lock → prevote value; lock matches → prevote value; lock differs → check valid_round). **Order: lock check before value check.**
    - D5. Why is per-message verify catastrophic at n=21? Compute 441 × 50 µs vs the 300 ms budget.
    - D6. Batched-verify integration: when does the verifier flush? (Batch fills OR a flush timer fires.) Right batch size? (8-32; latency vs throughput.)
    - D7. **Anti-shortcut audit** (load-bearing) — for each motivation name the "obvious" reach and why it is wrong HERE:
      - verify → `dalek::verify` per message — wrong: 8× the amortized cost, blows the round budget.
      - broadcast → `for peer { net.send(peer, prop) }` — wrong: N syscalls + N encodes; use `sendmmsg` + `Arc<Bytes>`.
      - buffers → `Proposal { sig: Vec<u8>, .. }` fresh each time — wrong: per-propose allocs; pool fixed-size sig + Bytes.
      - lock check → "trust the proposer's valid_round claim" — wrong: a CLAIM is not evidence; check your own vote-set (safety).
