      pub struct BftState {
          pub height: u64,
          pub round: u32,
          pub step: Step,                 // Propose | Prevote | Precommit | Commit

          pub locked_round: Option<u32>,
          pub valid_value: Option<Hash>,

          pub validators: Vec<NodeId>,

  - *Mental model*: a `Segment` is an immutable-once-rolled, append-only data file plus a *sparse* offset index. Appends are O(1) at the tail (ride `wal`'s buffered+fsync path); reads are `index.floor(offset)` (binary search the sparse index) → then a bounded forward scan within the segment to the exact record. The index trades a little read-scan for a lot of memory. **This whole atom is off the hot path** — its job is faithful Kafka mechanics + clean reuse of `wal`/`mmap-queue`, not sub-tick latency.

  - *Contract* (signature-level — never the body):
    ```rust
    pub struct RecordOffset(pub u64);          // logical offset within the partition
    pub struct BytePosition(pub u64);          // physical byte position within the segment file
    pub struct Segment { /* base_offset, data (wal-backed), index: OffsetIndex, ... */ }
    pub struct OffsetIndex { /* sparse: Vec<(RecordOffset, BytePosition)>, interval_bytes */ }
    impl Segment {
        pub fn create(dir: &Path, base_offset: RecordOffset) -> Result<Segment, LogError>;
        pub fn append(&mut self, record: &[u8]) -> Result<RecordOffset, LogError>;   // returns the assigned offset
        pub fn read(&self, offset: RecordOffset) -> Result<Option<Bytes>, LogError>; // None if past tail
        pub fn flush(&mut self) -> Result<(), LogError>;                             // delegates to wal group-commit
        pub fn size_bytes(&self) -> u64;
    }
    impl OffsetIndex {
        pub fn maybe_append(&mut self, offset: RecordOffset, pos: BytePosition, bytes_since_last: u64);
        pub fn lookup(&self, offset: RecordOffset) -> (RecordOffset, BytePosition); // floor entry (binary search)
    }
    ```

  - *Back-of-envelope* (bar (c), but **off-hot-path** — the budget is throughput + memory, not sub-tick latency):
    - `wal`-backed append with group-commit ≈ ~1 µs/record amortized (the W26 baseline) → ≥ ~1 M records/s single-partition single-thread. A naive **per-record fsync** ≈ ~10 ms/record → ~100 records/s (a 10,000× cliff — the same group-commit lesson as W97 `put`, do NOT re-learn it the hard way).
    - **Sparse vs dense index** over 1 GiB of 256 B records ≈ 4 M records. Dense index (12 B/entry: u32 rel-offset + u32 rel-pos packed, ~8 B Kafka-style) = 4 M × 8 B = **~32 MiB**. Sparse at 4 KiB interval = 1 GiB / 4 KiB = 256 K entries × 8 B = **~2 MiB** — a **~16× memory win** for a worst-case ~4 KiB forward scan on read (~1 µs at memory bandwidth). This is the Kafka design choice; reproduce it, don't "improve" it into a dense index.
    - `seek` = binary search 256 K entries (~18 compares × ~3 ns = ~54 ns) + forward scan ≤ 4 KiB (~1 µs cold page, ~100 ns warm). Read is index-bounded, never a full-segment scan.

  - **Requirements** R1–R8 — write in `crates/log-distributed/notes/64_segment_design.md`:

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  Ordered newbie → expert.

  - **(NEWBIE) When `partition_rolls_and_reads_across_boundary` returns `None` for records near the roll:**
    - Symptom: records appended just before/after a roll read back as `None`; `segment_count() ≥ 2` so the roll happened, but routing misses them.
    - Why: `read`'s segment lookup used `<` where it needed `<=` (or vice-versa) at the `[base_offset, next_offset)` boundary — the off-by-one from D6.
    - Fix: route by binary search for the segment with `base_offset <= offset < next_offset`; the active segment's upper bound is its current `next_offset`. Add the exact boundary record to the regression set.
    - Cost avoided: silent invisibility of records straddling every roll — at 1 M records/segment that's one lost record per million, intermittent and brutal.
    - Muscle: roll-boundary routing is a half-open-interval problem — get the comparator exactly right and test the boundary record explicitly. Reapplies at: W65 replica catch-up at the roll, W84 retention deletion boundary.

  - **(EXPERT) When `roll_never_splits_a_record` reports a record of length ≠ 256:**
    - Symptom: the 256 B record is split — part in the sealed segment, part in the new one; `read` returns a truncated payload.
    - Why: the roll check ran *after* starting to write the record (or after a partial frame write) instead of before.
    - Fix: check `active.size_bytes() + frame_len > segment_bytes` BEFORE writing; if true, seal + open a new segment, THEN write the whole record into the new segment. Roll is always at a record boundary.
    - Cost avoided: cross-segment record corruption — unrecoverable, since neither segment holds a valid frame.
    - Muscle: roll BEFORE the overflowing write, never mid-record. Reapplies at: W84 compaction segment boundaries, every segmented log.

  - **(SENIOR) When `lint_no_mutex_on_active_segment` finds a `Mutex<Segment>`:**
    - Symptom: the lint flags a `Mutex`/`RwLock` wrapping the active segment; `append` takes `&self`.
    - Why: the "make it thread-safe" reflex wrapped the segment in a lock instead of relying on the thread-per-core shard's single-writer ownership.
    - Fix: `append(&mut self)`; the partition is owned by exactly one `runtime-thread-per-core` shard (W30/W44), which is the sole writer — ordering and exclusivity come free, no lock, no contention.
    - Cost avoided: lock contention on the append path + the cache-line bouncing a lock causes — and a "no primitive twice" violation (re-implementing the shard's single-writer property).
    - Muscle: single-writer ordering is the thread-per-core shard's job; never bolt a lock onto a per-shard-owned structure. Reapplies at: W65 per-partition shard, W74 matching-engine per-symbol shard, W97+ venue store sharding.

  - **(EXPERT) When `roll_boundaries_deterministic` reports different segment counts across runs:**
    - Symptom: two identical 5000-append runs roll at different points → different segment counts.
    - Why: the roll path consulted `Instant::now()`/`SystemTime` (or a HashMap iteration leaked a non-deterministic order) instead of the deterministic size threshold + the injected `time::Clock`.
    - Fix: the size-roll path uses only `size_bytes` (deterministic); the age-roll uses the injected `time::Clock` (W6), mockable in tests. No wall-clock, no HashMap iteration in the roll decision.
    - Cost avoided: non-deterministic segment boundaries break the W65 replica-follow diff and the W84 projection-equality check (replicas would seal at different offsets → false divergence).
    - Muscle: determinism extends to roll boundaries — inject the clock, ban wall-clock + HashMap iteration in any decision a replica must reproduce. Reapplies at: W65 replica-follow, W84 projection equality, W88 VOPR (origin discipline).

  - **(EXPERT, perf) When `append_zero_alloc_except_at_rolls` reports allocations spread across appends, not clustered at rolls:**
    - Symptom: heaptrack shows ~1 alloc/append even in the no-roll window.
    - Why: the partition cloned the record into a new buffer before forwarding to `Segment::append`, instead of passing the slice through to the segment's pooled (`mmap-queue`-backed) frame writer.
    - Fix: forward the `&[u8]` to `Segment::append` (which rides `mmap-queue` pools from Wed); the only allowed allocations are at roll points (new `Segment`).
    - Cost avoided: per-append malloc under a 1 M/s stream + allocator contention. **(bar (c) discipline — off-hot-path append loop stays zero-alloc.)**
    - Muscle: the partition forwards to the pooled segment writer; it does not re-buffer. Reapplies at: W84 batch append, W97 mini-db substrate store.
