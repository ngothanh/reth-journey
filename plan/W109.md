**Monday — Runbook: matching-engine replica divergence**

- [ ] Write `ops-runbooks/matching-engine-replica-divergence.md`. Triggering alert (W105): `RaftReplicaDivergence` (replica's committed-log hash ≠ leader's at the same index). Inherited fault class (W108): `NetworkPartition` + delayed `KillProcess` of a replica mid-burst. Structure: (1) **Detect** — `curl :9100/metrics | grep raft_committed_hash`; identify which replica diverged.   - *Mental model*: this is the single most dangerous HFT incident — a diverged replica that silently serves stale order-book state can fill against a phantom book. **Tuesday — Runbook: mini-db WAL corruption**

- [ ] Write `ops-runbooks/mini-db-wal-corruption.md`. Triggering alert (W105): `WalChecksumMismatch` (a WAL frame's CRC ≠ recomputed CRC on replay). Inherited fault class (W108): `DiskFull` (torn write) + `KillProcess` (crash mid-fsync). Structure: (1) **Stop the bleed** — halt writers; a corrupt WAL must not be appended to. (2) **Locate the tear** — `recovery` crate's replay (W29-W30) already reports the first bad frame offset; the runbook says where that log line lives, not how to write a parser. (3) **Truncate-to-last-good** — `recovery` truncates the WAL at the last frame whose CRC validates; everything after the tear is lost-but-uncommitted by construction (the fsync barrier). (4) **Verify the truncation point** — the last-good frame's LSN must be ≤ the last *acknowledged* commit; if it's lower, data that was ack'd to a client is gone → escalate, do not silently proceed. (5) **Restart + reconcile** — bring mini-db up read-only first; confirm checkpoint LSN consistency before allowing writes. (~40 min)
  - 🎯 **Hardened acceptance**: dry-run against a synthetic torn-WAL fixture (truncate a known-good WAL mid-frame with `dd`); the runbook's truncate-to-last-good path must recover mini-db to a consistent state AND the verify-step must correctly *refuse* a fixture where the tear is before an acknowledged commit (negative case — the runbook must catch data loss, not paper over it). MTTR + "data-loss decision tree" both present.
  - *Mental model*: WAL corruption is where the recovery crate (W29-W30) earns its keep — but the *operator* decision (truncate vs escalate) is not in the code, it's in this runbook. It exists now because the W106 live rig writes a real WAL; a `DiskFull` torn write is a *when*, not an *if*. The "verify truncation point ≤ last ack'd commit" step is the W108 Wednesday "validate, don't silently fix" muscle applied to operations: silently truncating past an ack'd commit is the operator version of silently sorting an out-of-order scenario.
  - **Output**: `ops-runbooks/mini-db-wal-corruption.md` exists; contains an explicit "DATA LOSS — ESCALATE" branch (the runbook must encode the case where truncation would discard acknowledged data); `grep -i "last.good\|acknowledged" ops-runbooks/mini-db-wal-corruption.md` returns the decision-point lines.
- [ ] Commit (`ops-runbooks/mini-db-wal-corruption.md`). (~10 min)

**Wednesday — Runbook: vector-db OOM (HNSW graph)**

- [ ] Write `ops-runbooks/vector-db-oom.md`. Triggering alert (W105): `VectorDbRssHigh` (RSS > 85% of cgroup limit) → `VectorDbOomKilled` (cgroup OOM-killer fired). Inherited fault class (W108): `Resource` (memory exhaustion). Structure: (1) **Confirm it's HNSW, not a leak** — `vector-db` exposes `hnsw_graph_bytes` + `quantizer_bytes` (W101-W104); the runbook says which metric distinguishes "graph legitimately grew" from "unbounded segment accumulation". (2) **Immediate relief** — switch query path to the SQ/PQ-quantized index (W102) which is ~4-8× smaller; degrades recall, not availability. (3) **Root-cause** — unmerged segments (W104 segment manager) holding duplicate vectors; trigger a manual segment merge. (4) **Right-size** — recompute the graph memory budget: `N_vectors × M_neighbors × 4 bytes + quantizer`; if the cgroup limit is genuinely too small, document the new limit and the `ops-deploy` change (W107) rather than fighting the OOM-killer. (~40 min)
  - 🎯 **Hardened acceptance**: dry-run against a fixture that loads vectors until RSS crosses the alert threshold; the "switch to quantized index" relief step must demonstrably reduce RSS below the threshold WITHOUT a restart (availability preserved), and the back-of-envelope memory formula must predict the observed `hnsw_graph_bytes` within ±20% (if the formula is wrong, the right-sizing step is guesswork). MTTR recorded.
  - *Mental model*: vector-db (W101-W104) is a single-node capstone with an unbounded-by-default graph; HNSW memory grows with both vector count and `M`. The runbook exists now because the live rig from W106 onward will accumulate vectors continuously. The "quantized index gives relief without restart" step is the operational payoff of having built SQ/PQ in W102 — the runbook makes that latent capability into a documented incident lever.
  - **Output**: `ops-runbooks/vector-db-oom.md` exists; contains the explicit memory formula `N × M × 4 + quantizer`; `grep -i "quantiz\|segment merge" ops-runbooks/vector-db-oom.md` returns the two relief levers.

**Thursday — Runbook: monitoring stack down + Alertmanager routing**

- [ ] Write `ops-runbooks/monitoring-stack-down.md`. Triggering alert (W105): the meta-alert `DeadMansSwitch` (a heartbeat that fires when Prometheus *stops* scraping — the absence of all other alerts is itself the signal). Inherited fault class (W108): `KillProcess` of the Prometheus/Grafana process; `NetworkPartition` between the SUT and the monitoring host. Structure: (1) **Recognize the silence** — no alerts for 5 min when the rig is live is NOT "everything is fine", it's "we're blind"; the `DeadMansSwitch` is what catches this. (2) **Triage which layer** — Prometheus down (no scrape) vs Grafana down (scrape OK, view gone) vs exporter down (W105 exporter on the SUT crashed). The runbook gives the one-liner that distinguishes each (`curl :9090/-/healthy`, `:3000/api/health`, `:9100/metrics`). (3) **Restore scraping first** — Grafana can wait; losing the scrape means losing the data that proves what happened. (4) **Backfill gap** — document the data-gap window in the incident log so later analysis doesn't misread the hole as "system idle". (~30 min)
  - 🎯 **Hardened acceptance**: dry-run by killing the Prometheus process on the rig; the `DeadMansSwitch` must fire within its configured window AND the runbook's triage one-liners must each correctly identify the killed layer (test all three: kill Prometheus, kill Grafana, kill the exporter separately). The runbook is the ONE runbook that must work when monitoring itself is down — so it must not depend on a dashboard to execute. MTTR recorded.
- [ ] Add the **Alertmanager routing audit** to the same runbook: a table mapping every W105 alert → its `receiver` → the runbook it links to. Confirm every fault class in the W108 `Fault` enum has both an alert and a runbook (8 of 8). This closes the inheritance loop: fault → alert → runbook. (~30 min)
  - 🎯 **Hardened acceptance**: the alert→runbook table is complete — `grep -c '.md' ops-runbooks/monitoring-stack-down.md` ≥ 4 (every runbook written this week is linked) AND every W108 `Fault` variant name appears in the table (`for v in KillProcess NetworkPartition LatencyInject DiskFull ClockSkew DiskSlow Drop Resource; do grep -q "$v" ops-runbooks/monitoring-stack-down.md || echo "MISSING $v"; done` prints nothing).
