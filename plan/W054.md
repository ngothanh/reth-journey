  - *Mental model*: a pure function `(input: &Bytes, gas) -> PrecompileResult` that recovers the signer address from an ECDSA signature, returning the 32-byte left-padded address on success and **empty bytes** (not an error) on any malformed input.
  - *Contract*: `pub fn ec_recover(input: &Bytes, gas_limit: u64) -> PrecompileResult`. `GAS_COST = 3000` constant. Input is `msg[32] ‖ v[32] ‖ r[32] ‖ s[32]`, right-zero-padded to 128 bytes if short. Output on success: `[0u8;12] ‖ address[20]`; on any failure: empty `Bytes` with full gas charged.
  - *Back-of-envelope* (bar (b), correctness-first): one `recover_from_prehash` is ~50-100 µs of k256 scalar work — dominated by curve ops, not parsing. Not a hot path (one per signature-bearing tx), so correctness/consensus-safety, not ns, is the budget. The cost of a wrong answer is a **chain fork**, not a slow block.
  - **Requirements** R1..R6 — write in `crates/exec-vm/notes/54_ecrecover_design.md`:
    - R1. Gas is constant 3000, charged whether the signature is valid or not.
    - R2. On any invalid input: return `Ok(PrecompileOutput::new(3000, Bytes::new()))` — empty bytes, NEVER `Err`. The caller checks `returndatasize == 0`.
    - R3. `v ∈ {27, 28}` ONLY. `v=0/1` (compact) rejected; `v ≥ 35` (tx-sig with chain_id) rejected — that encoding is valid only for transaction signatures, not this precompile.
    - R4. `r, s ∈ (0, n)` where `n` = secp256k1 group order. `r=0`, `s=0`, `r≥n`, `s≥n` → empty (no panic).
    - R5. Output = `keccak256(uncompressed_pubkey_without_0x04_prefix)[12..32]` left-padded to 32 bytes (12 zero bytes ‖ 20-byte address).
    - R6. Input shorter than 128 bytes is RIGHT-padded with zeros (Yellow Paper §I); never left-padded.
  - **Design walk-through** D1..D5 — answer in the design doc; no peeking at revm until Phase 3:
    - D1. Enumerate the recovery primitives (`k256::ecdsa::VerifyingKey::recover_from_prehash`, `secp256k1::recover`, `libsecp256k1`). Property table: bounds-checks r,s? panics on r=0? low-s required?

    - D3. **Pre-mortem (load-bearing):** write the exact 4-line trace where a high-s signature OR a v=1 acceptance lets the same message recover under two distinct signatures — the malleability that historically forked impls. If you can't write it, you can't prove R3/R4 prevent it.
    - D4. Padding direction: take a known-good 128-byte signature, truncate to the 96-byte prefix `[msg‖v‖r]` (drop `s`). Write BOTH parses side by side: right-pad → `s` slot is zero (→ R4 reject → empty); left-pad → the 96 bytes shift into the high `r`/`s` slots and the `msg` slot zero-fills, yielding a *different, non-empty* (or differently-rejected) recovery. The recovered address is the observable discriminator — name it.
    - D5. Address derivation: confirm the pubkey is 64 bytes (uncompressed, 0x04 prefix stripped), hashed, and the LOW 20 bytes taken — write the off-by-prefix bug that returns wrong addresses for every signature.

  - [ ] `ecrecover_short_input_right_padded` *(SENIOR, cross-primitive)* — built from a KNOWN-GOOD 128-byte signature `[MSG ‖ V27 ‖ R ‖ S]` whose recovery is `EXPECTED_ADDR`. Two short inputs exercise both padding directions with **distinguishable, observable** outcomes — the test asserts the recovered bytes, not merely `is_empty()`:
    1. **Truncated case** (drops `s`): the 96-byte prefix `[MSG ‖ V27 ‖ R]`. Right-padding to 128 zero-fills the `s` slot → `s=0`, fails R4 → deterministic EMPTY. A left-padding impl shifts the 96 bytes into the high slots (`MSG→r`, `V27→s`-low... actually `r`/`s`), leaving `msg`'s slot zero and producing a *different* recovery (a non-empty wrong address OR a different rejection), so the two impls diverge observably.
    2. **Positive companion** (shorter, recovers a specific address): a second short input `SHORT2` (e.g. `[MSG ‖ V27 ‖ R_partial]`, exactly `len < 128`) crafted so RIGHT-padding lands the bytes in the correct field boundaries and recovers `EXPECTED_ADDR2`, while LEFT-padding lands them in different fields and recovers a provably different address. Assert the exact expected address for the right-pad impl AND assert the left-pad impl would NOT produce it.
    ```rust
    #[test]
    fn ecrecover_short_input_right_padded() {
        // Case 1: 96-byte truncation drops `s`. Right-pad => s=0 => empty (R4).
        let truncated = &FULL_VALID_INPUT[..96]; // MSG ‖ V27 ‖ R, s missing
        let out = ec_recover(&Bytes::copy_from_slice(truncated), 3000).unwrap();
        assert!(out.bytes.is_empty(),
            "right-pad zero-fills s => s=0 => R4 reject => empty; got {} bytes", out.bytes.len());

        // The naive LEFT-pad impl on the SAME 96 bytes lands them in high slots
        // (msg-slot becomes zero), recovering a DIFFERENT, non-empty result.
        let left = left_pad_to_128(truncated);
        let left_out = ec_recover(&Bytes::copy_from_slice(&left), 3000).unwrap();
        assert_ne!(left_out.bytes, out.bytes,
            "left-pad must diverge from right-pad here — if they match, the test does not trap padding direction");

        // Case 2: positive companion — right-pad recovers a SPECIFIC known address.
        let out2 = ec_recover(&SHORT2_INPUT, 3000).unwrap(); // len < 128, right-pads into valid fields
        assert_eq!(&out2.bytes[12..32], EXPECTED_ADDR2.as_slice(),
            "right-pad must recover EXPECTED_ADDR2; observing recovered bytes, not just emptiness");
        // and the left-pad of the same bytes recovers something else (or empty) — never EXPECTED_ADDR2:
        let left2 = left_pad_to_128(&SHORT2_RAW);
        let left2_out = ec_recover(&Bytes::copy_from_slice(&left2), 3000).unwrap();
        assert_ne!(&left2_out.bytes.get(12..32), &Some(EXPECTED_ADDR2.as_slice()),
            "left-pad must NOT recover EXPECTED_ADDR2 — padding direction is observable in the recovered address");
    }
    ```

  #### Phase 3 — Make the tests pass, one failure at a time (~40 min)
  - **(NEWBIE) When `ecrecover_mainnet_vector_matches` returns the wrong address:**
    - Symptom: recovered address differs from the vector by every byte.
    - Why: the uncompressed pubkey still carries its `0x04` prefix when hashed, or you took `keccak256(pk)[0..20]` instead of `[12..32]`.
    - Fix: strip the prefix (`to_encoded_point(false).as_bytes()[1..]`), `keccak256` the 64 bytes, take bytes `[12..32]`.
    - Muscle: an Ethereum address is the LOW 20 bytes of `keccak256(64-byte pubkey)`. **Reapplies at: W66 tempo-evm-ext P256 address derivation, W74 matching-engine order-sig recovery.**
  - **(SENIOR) When `ecrecover_v_must_be_27_or_28` accepts `v=0/1`:**
    - Symptom: v=0 and v=1 recover an address instead of returning empty.
    - Why: you derived `recovery_id = v & 1` (libsecp256k1 compact form) instead of gating on the exact set {27,28}.
    - Fix: `if v != 27 && v != 28 { return Ok(empty(3000)); } let recid = v - 27;`.
    - Muscle: the precompile's v-domain is {27,28} only — compact (0/1) and tx-sig (35+) encodings are a *different* contract; accepting them mints replayable signatures. **Reapplies at: W66 P256 precompile (its own y-parity domain), W74 order-sig validation.**
  - **(SENIOR) When `ecrecover_r_or_s_out_of_range_empty_no_panic` panics on r=0:**
    - Symptom: `Signature::from_scalars` (or k256 recovery) panics mid-precompile → the EVM run aborts → consensus fork.
    - Why: no explicit `0 < r < n && 0 < s < n` pre-check; some k256 versions panic on a zero scalar.
    - Fix: explicit pre-check `r != 0 && r < N && s != 0 && s < N` before constructing the signature; on violation return empty.
    - Muscle: precompiles must be TOTAL functions — every input maps to a defined output, never a panic; a panic in consensus code is a fork. **Reapplies at: W56 raft message decode (never panic on a peer's bytes), W64+ bft vote validation.**
  - **(SENIOR) When `ecrecover_short_input_right_padded` recovers the WRONG address (or the wrong case is non-empty):**
    - Symptom: the 96-byte truncated case is non-empty (you recovered something instead of EMPTY), AND/OR the positive companion's `out2.bytes[12..32]` differs from `EXPECTED_ADDR2` — your output matches the LEFT-pad branch, not the right-pad branch. The two padding directions land the same bytes in different `(msg,v,r,s)` slots, so the recovered address is the observable discriminator.
    - Why: you left-padded the short input (`padded[128-len..].copy_from_slice(input)`), shifting `msg`/`v`/`r` into the high `r`/`s` slots and zero-filling the low `msg` slot — a structurally different (and for case 1, valid-looking) parse.
    - Fix: `let mut padded = [0u8;128]; padded[..input.len()].copy_from_slice(input);` — copy at offset 0 (right-pad with zeros), so the truncated case zero-fills `s` (→ s=0 → R4 empty) and the companion lands bytes in the correct field boundaries (→ EXPECTED_ADDR2).
    - Muscle: EVM precompile inputs right-pad with zeros (Yellow Paper §I); left-padding silently corrupts field boundaries — and the corruption is *observable in the recovered address*, so the test must assert the bytes, never just emptiness. **Reapplies at: W-all precompiles (modexp/blake2f length handling), W66 P256 input parse.**
  - **(NEWBIE) When `ecrecover_gas_charged_on_failure` reports 0 gas on invalid input:**
    - Symptom: invalid signatures consume 0 gas.
    - Why: you returned `Err(OutOfGas)` or a 0-gas output on the failure branch.
    - Fix: every failure branch returns `Ok(PrecompileOutput::new(3000, Bytes::new()))`.
    - Muscle: constant-gas precompiles charge whether they succeed or fail — refunding-on-fail is a free-spam DoS. **Reapplies at: Sat KZG (50k charged on verify-fail), Fri blake2f, W66 P256.**
