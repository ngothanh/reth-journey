- [NEW v2] **ledger v1.0: io_uring journal writes (part 1)**
  - [ ] **Build**: replace `journal::write_record()` with io_uring submission ring. Group commit via SQE batching. (~3 hrs)
    - **Why**: journal-write throughput is the load-bearing latency of the entire ledger. Pre-v1.0, `journal::write_record()` is `pwrite(2) + fsync(2)` — that's a syscall per record + a flush per record. Group-commit via io_uring batches N records into one SQE batch with a single fsync at the end. Mirrors TigerBeetle's group-commit + their use of `O_DIRECT | O_DSYNC` semantics. Target: 100k Transfers/sec sustained, p99 < 100μs.
    - *Back-of-envelope* (target: **100k Transfers/sec sustained, journal P99 < 100 µs single-record; post-group-commit P99 < 1 µs amortized** — the TigerBeetle-class headline number):
      Baseline `pwrite + fsync`: each `fsync` on consumer NVMe is ~50-100 µs (forces device flush). At 100k/s × ~75 µs = 7.5 sec/sec — physically impossible without batching. Group-commit math: 256 records per fsync at sustained 100k/s = 390 fsyncs/sec × ~75 µs = ~30 ms/sec ✓ (~3% disk-flush overhead). Per-record amortized fsync cost = 75 µs / 256 = **~290 ns/record**. SQE submit cost ≈ 80 ns/op amortized (W86's perf #1 — SQPOLL eliminates `io_uring_enter` from hot path); `write_fixed` payload memcpy 4 KB → ~80 ns at 50 GB/s L1 BW. Total amortized P99 per record ≈ 290 + 80 + 80 = **~450 ns**, with batch-fill horizon `flush_horizon_us = 50µs` adding tail variance. Post-batching P99 < 1 µs is achievable; pre-batching baseline blows budget by ~100×.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/journal.zig` (esp. `write_prepare()` and `_callback_write_prepare()`); LSM-tree's "group commit" idea; PostgreSQL's wal_writer.c.
    - **Design**:
      ```rust
      pub struct IoUringJournal {
          ring: IoUring,                            // separate ring from network
          fd: RawFd,                                // journal file
          tail_offset: u64,
          pending: ArrayVec<PendingWrite, 256>,     // group-commit batch
          flush_horizon_us: u32,                    // 50us default
      }
      pub struct PendingWrite { offset: u64, buf_id: u32, len: u32, completion_tx: oneshot::Sender<()> }
      pub struct JournalBuf {                      // pre-registered fixed buffers
          buf: Box<[u8; JOURNAL_BUF_SIZE]>,
          buf_id: u32,
      }
      impl IoUringJournal {
          pub fn write_record(&mut self, rec: &Record) -> impl Future<Output = io::Result<()>>;
          pub fn poll_completions(&mut self);      // call frequently
      }
      ```
      **Invariants**: (i) `O_DIRECT | O_DSYNC` for true durability; (ii) writes are sector-aligned (4KB on most NVMe); (iii) group commit: pending writes accumulate up to `flush_horizon_us` or 256 records, whichever first; (iv) `completion_tx` resolves only after fsync barrier passes; (v) WAL durability point = last completed `IORING_OP_FSYNC` not the last write.
    - **Build steps**: 1. (~15 min) construct a dedicated `IoUring` (separate from network ring) with SQ depth 256, fixed buffers registered. 2. (~20 min) journal file open with `O_DIRECT | O_APPEND | O_DSYNC | O_CLOEXEC`; pre-allocate 1GB. 3. (~25 min) implement `write_record`: pack record into next free JournalBuf (sector-aligned padding), submit IORING_OP_WRITE_FIXED at tail_offset. 4. (~25 min) group-commit ticker: every `flush_horizon_us` (or pending count ≥ 32), submit IORING_OP_FSYNC linked AFTER the writes with `IOSQE_IO_LINK`. 5. (~25 min) `poll_completions` drains CQ, matches `user_data` → PendingWrite → signal completion_tx. 6. (~20 min) ordering invariant: `IOSQE_IO_DRAIN` on fsync ensures no overlap with new writes; record durability point precisely. 7. (~20 min) recovery path: on restart, scan tail for partial last batch, truncate to last fsync'd offset. 8. (~25 min) bench: 100k Transfers/s sustained, measure p99 latency from `write_record.await`. 9. (~15 min) error paths: ENOSPC, EIO — what to do (panic + alert; ledger cannot proceed without journal).
    - **Pitfalls**: *SQE ordering*: **Symptom**: fsync issued before all writes complete; durability lie. **Fix**: explicit `IOSQE_IO_LINK` chain OR fsync with `IORING_FSYNC_DATASYNC` flag + correct sequencing. *Completion polling rate*: **Symptom**: poll_completions called too rarely; CQ overflows. **Fix**: schedule poll on every reactor iteration; size CQ = 4× SQ. *Drain semantics*: **Symptom**: IOSQE_IO_DRAIN halts pipeline; throughput collapses. **Fix**: don't DRAIN every fsync — only on shutdown OR when crossing 1GB file boundary. *Group-commit latency cliff*: **Symptom**: single-record write waits 50μs for batch fill; p99 inflated. **Fix**: opportunistic immediate fsync if pending == 0 and rate is low; configurable. *Direct I/O alignment*: **Symptom**: EINVAL because buf not 4KB-aligned. **Fix**: `Box::new_zeroed()` with `#[repr(align(4096))]` JournalBuf. *Buf-fixed exhaustion*: **Symptom**: out of registered buffers under burst. **Fix**: size = 2× SQ; backpressure caller via `BackPressure` error when exhausted.
  - **Expect to hit (perf) #1 — `fsync`-per-record collapses throughput (bar (c) violation, headline)**: the naive implementation submits one IORING_OP_WRITE + one IORING_OP_FSYNC per `write_record`. Each fsync forces the device flush ~50-100 µs → 100k/s × 75 µs = 7.5 sec/sec → throughput collapses to ~13k/s (vs the 100k/s target). Profile shows `io_uring_enter` returning frequently to wait on fsync completion.
    - Fix: group-commit with `IOSQE_IO_LINK`. Accumulate writes in `pending: ArrayVec<PendingWrite, 256>`; on either (a) `pending.len() >= 256` or (b) `now - first_pending_at >= flush_horizon_us (50 µs)`, submit the SQE batch: N writes chained via `IOSQE_IO_LINK` to a single trailing IORING_OP_FSYNC. The completion of the fsync CQE signals durability for **all N writes** simultaneously — fire each `completion_tx.send(())` together. Per-record amortized fsync cost = 75 µs / 256 ≈ 290 ns.
    - Cost avoided: per-record fsync (75 µs) → per-batch fsync (75 µs / 256 = 290 ns/record) — a **~260× win on the headline metric**. Drives the 100k/s sustained throughput; without group-commit, the SHIP target is unattainable.
    - Muscle: in any "must-fsync" durability path, batch the fsyncs. The latency-horizon (50 µs) is the cost paid by single-record writers to amortize across the batch; opportunistic immediate fsync when `pending.len() == 0` and rate is low keeps P99 acceptable for low-rate workloads. Same pattern: PostgreSQL `commit_delay`, RocksDB `WriteBatch`, Kafka `linger.ms`. Reapplies at: W77 messaging-aeron flow-control batched ACK, W92 ledger v1.0 SHIP throughput gate (the W90 work is the load-bearing piece), W100 mini-db CAPSTONE WAL group-commit.
  - **Expect to hit (perf) #2 — `Box::new_zeroed::<[u8; 4096]>()` returns 8-byte-aligned heap memory, `O_DIRECT` `write` returns `EINVAL` (bar (c) violation: outright fails)**: `O_DIRECT` requires the user buffer's address, length, and file offset all be aligned to the device's logical block size (typically 4 KB on NVMe). The Rust allocator returns 8-byte-aligned memory by default; `Box::new_zeroed::<[u8; 4096]>()` is **4 KB long** but its start address is not guaranteed 4 KB aligned. First write returns `EINVAL`; bench shows zero throughput, with cryptic kernel-side error.
    - Fix: define `#[repr(C, align(4096))] struct JournalBuf([u8; JOURNAL_BUF_SIZE]);` then `Box::new(JournalBuf([0u8; JOURNAL_BUF_SIZE]))`. The `repr(align(4096))` forces the allocator to return a 4 KB-aligned address. Verify with `debug_assert!(buf.as_ptr() as usize % 4096 == 0);`. The file offset is also 4 KB-aligned by writing at `tail_offset` (also a multiple of 4 KB — pad records as needed). Register the buffer via `io_uring_register_buffers` once at startup so the kernel can pin it (further perf win on subsequent `write_fixed`).
    - Cost avoided: works at all (no `EINVAL`); plus the io_uring `write_fixed` pin removes one page-table walk per write (~10 ns/op) and enables the kernel to skip the user-buffer-validation phase entirely.
    - Muscle: any `O_DIRECT` I/O path requires aligned buffers + aligned offsets + aligned lengths — the kernel does not auto-fix; it `EINVAL`s. Use `#[repr(align(N))]` on the wrapping struct; never assume default allocator alignment. Reapplies at: W92 ledger v1.0 SHIP io_uring durability test, W100 mini-db SSTable write path (SSTables also use O_DIRECT for predictable cache control), W82 matching-engine durable command log (if O_DIRECT).
    - **Test scenarios**: 1M Transfers @ 100k/s for 10s → p50 < 30μs, p99 < 100μs, no fsync error. Crash mid-batch (SIGKILL the process): on restart, journal tail truncated to last fsync, replay state matches. Concurrent reader of journal during writes: never sees torn record.
    - **Acceptance**: 100k Transfers/s sustained on consumer NVMe; p99 < 100μs; recovery byte-identical; dhat = 0 allocs.
    - **Downstream**: ledger v1.0 SHIP (W92) gates on this; VSR v1.0 (W90 Thu) journal is wrapped by this; mini-db (W95+) WAL pattern reuses.

- [NEW v2] **consensus-vsr v1.0: reconfiguration (part 1)**
  - [ ] **Build**: `crates/consensus-vsr/src/reconfig.rs` — add/remove replica via Reconfiguration messages, view change for new config. (~3 hrs)
    - **Why**: a v1.0 consensus protocol cannot ship without membership change. Static membership is a toy. Reconfiguration is also where the most subtle bugs live: quorum during transition, log-truncation safety, joint-quorum during overlap. VSR's reconfiguration is more elegant than Raft's joint-consensus — it leverages view change to atomically swap configs.
    - *Back-of-envelope* (reconfig completion target: **<5s for 3→4 add** — state-transfer dominates; normal-op latency unchanged after commit):
      Reconfig is a rare event (operational, ~minutes-to-days apart), so its **wall-clock cost is acceptable**; what matters is (a) **normal-op latency is unaffected** before and after — the commit step that atomically swaps config must add zero ns to steady-state apply, and (b) **safety holds during transition** — no double-leadership, no committed-op loss. The 5s figure is dominated by state-transfer: 1 GB journal × ~200 MB/s sustained TCP = ~5s. The reconfig op itself flows through the normal Prepare/Commit pipeline (~500 µs commit latency P99) — negligible. After commit, the config swap is a single `self.config = new_config;` write — ~1 ns. The "atomic-switch at op N+1" property is **load-bearing for safety**, and structurally it's a one-line write — there's no spinlock, no joint-quorum window, no overlap state to maintain. This is VSR's elegance over Raft's joint-consensus.
    - **Read first**: Liskov-Cowling 2012 VSR paper §5 "Reconfiguration"; TigerBeetle `lib/tigerbeetle/src/vsr/replica.zig` — search for `ReconfigurationRequest`; Raft Chap 4 (joint consensus) for contrast.
    - **Design**:
      ```rust
      pub struct Configuration {
          replicas: ArrayVec<ReplicaId, MAX_REPLICAS>,
          epoch: u32,                              // monotonic config version
      }
      pub enum ReconfigCommand {
          AddReplica { replica: ReplicaId, init_state_hash: [u8; 32] },
          RemoveReplica { replica: ReplicaId },
      }
      // Reconfiguration is a special op committed via the same log as normal ops.
      // Once committed at op N, all replicas from op N+1 onward operate under new config.
      pub struct VsrReplica {
          config: Configuration,
          pending_reconfig: Option<(OpNum, ReconfigCommand)>,
          /* ... */
      }
      ```
      **Invariants**: (i) reconfig op committed via SAME path as normal ops (requires quorum of OLD config); (ii) atomic switch at op N+1 — no joint quorum, no overlap window; (iii) joining replica must catch up via state-transfer (snapshot + journal replay) BEFORE acknowledging at new view; (iv) leaving replica halts apply AT op N (not N+1); (v) any subsequent view-change uses NEW config quorum.
    - **Build steps**: 1. (~15 min) ReconfigCommand serialization into VsrMessage. 2. (~25 min) admin-API endpoint `add_replica`/`remove_replica` that submits ReconfigCommand op. 3. (~25 min) commit handler: when op type=Reconfig commits, update `self.config` atomically. 4. (~30 min) view-change interaction: new leader uses op-history to derive correct config at each op. 5. (~30 min) joining replica flow: receive snapshot (state_hash matches `init_state_hash`), replay journal tail, send "Joined" message, only then participates in quorum. 6. (~25 min) leaving replica flow: receive `Leave` signal at op N, finish replicating up to N, then halt; persist a `Tombstone` so on restart replica refuses to participate. 7. (~30 min) tests: 3-replica cluster, add 4th, verify quorum is 3-of-4 after commit; remove one, verify 2-of-3. 8. (~20 min) Reconfiguration messages use MessagePool from W89.
    - **Pitfalls**: *Quorum during transition*: **Symptom**: between proposing add and committing add, where's quorum? **Fix**: VSR says quorum stays OLD until the reconfig op commits — that's the magic. Test: kill old-quorum minority during transition; cluster still progresses. *Log truncation safety*: **Symptom**: leaving replica truncates log past the reconfig op; later joins and replays incomplete log. **Fix**: persistent Tombstone in journal — replica refuses to re-join old cluster. *Joining replica races*: **Symptom**: joiner receives state-transfer, then a Prepare at op N+5, applies it before its predecessor N+4. **Fix**: joiner buffers all post-state-transfer messages until at op N (state-transfer's end-op) and only then enters Normal status. *Concurrent reconfigs*: **Symptom**: two AddReplica racing. **Fix**: only one outstanding reconfig op at a time (enforced by leader). *State-hash mismatch on join*: **Symptom**: joiner thinks state_hash X, leader sees Y. **Fix**: joiner requests snapshot from leader and verifies hash before participating.
  - **Expect to hit (perf) #1 — branching on `config.epoch` in every normal-op message handler (bar (c) violation, soft)**: post-reconfig, every `on_prepare`/`on_prepare_ok`/`on_commit` handler grows a branch like `if msg.config_epoch != self.config.epoch { reject }`. Each branch is ~1 ns predicted, ~5 ns mispredicted; at 90k messages/sec × ~3 hot branches = ~3 ns × 270k = ~1 µs/sec — negligible in absolute terms but accumulates as protocol grows.
    - Fix: encode `config_epoch` as the top 32 bits of `op_num` (which is already on every message); compare via single `u64` mismatch test inside the existing op-num ordering check. Or: process the config_epoch check **once** at message-decode entry (one branch), then proceed through the normal handlers unaware. The discipline is "add no branches to the steady-state apply path for features that fire rarely."
    - Cost avoided: small absolute (~1 µs/sec) but precedent-setting: feature accretion is the bar-(c) death spiral. Each "I'll just add one branch" decision adds ~1-5 ns; after 50 such decisions, the apply path is 200 ns slower than v1.0 — a 20% regression by paper cuts.
    - Muscle: every conditional on the hot path must justify its budget contribution. Use compile-time generics (`<C: ConfigCheckMode>`) or message-decode-time validation to keep the hot loop branch-clean. Reapplies at: W82 matching-engine pre-trade risk checks (each new check class adds a branch — must measure), W94 exec-vm v1.5 parallel-vs-sequential code paths (feature flag is compile-time gate, not runtime branch), W92 ledger v1.0 SHIP P99 regression check (CI fails if apply path latency creeps > +5% across releases).
  - **Expect to hit (perf) #2 — state-transfer copies 1 GB through user-space twice (bar (c) violation: reconfig time SLA)**: implementing state-transfer as "leader reads snapshot file into `Vec<u8>` → encodes into VSR Message body chunks → sends → joiner decodes chunks into `Vec<u8>` → writes to local snapshot file." 1 GB × 2 user-space copies × ~5 GB/s memcpy = ~400 ms just on memcpy; plus ~5s network transfer. With kernel-bypass send/recv, the memcpys dominate the wall-clock variance.
    - Fix: state-transfer uses `sendfile(2)` (or `IORING_OP_SPLICE` if io_uring) on the sender side — kernel copies snapshot file → socket with **zero user-space touch**. Receiver uses `splice(2)` from socket → snapshot file. Both at near-line-rate (~200 MB/s sustained TCP on consumer hardware; ~5 GB/s on bonded 40G). Per-byte cost on the user-space side: ~0 ns (data never enters userspace). Application-layer chunking + state-hash gossip happens out-of-band over the slow path.
    - Cost avoided: ~400 ms memcpy time → ~0 ms; reduces reconfig completion from ~5.4s to ~5.0s (state-transfer is now network-bound, not CPU-bound). Plus the L2/L3 cache pollution from copying 1 GB through userspace is avoided — adjacent replicas don't see their hot working sets evicted during reconfig.
    - Muscle: any bulk transfer of file data to/from another machine uses `sendfile`/`splice` — never read-into-user + write. Reapplies at: W92 ledger v1.0 snapshot transfer, W100 mini-db CAPSTONE SSTable replication (between nodes), W82 matching-engine snapshot transfer to a new raft follower.
    - **Test scenarios**: 3-replica → add 4th → 4 replicas all converged via post-reconfig 100 ops; remove a replica during normal traffic → cluster of 2 continues, no data loss; chaos: add-remove-add rapid sequence with concurrent client load.
    - **Acceptance**: all reconfig integration tests green; documented procedure for live add/remove.
    - **Downstream**: v1.0 SHIP gates on this; ops-deployment (W105+) uses this for rolling upgrades.
