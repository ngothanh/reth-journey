    #### Phase 1 — Problem, requirements, design (~70 min, no code yet)

    - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/ledger-deterministic/notes/90mon_io_uring_journal_prediction.md` (compare to reality after Phase 2 tests run):
      - P1. The primitive you'd reach for first: the exact submission API line you'd write for one record (`io_uring_prep_write` + `io_uring_prep_fsync`? a `tokio::fs::File::sync_all().await` per record?). Name the crate (`io-uring` raw vs `tokio-uring`).
      - P2. Predicted sustained throughput of your *first* (per-record-fsync) attempt in k/s, and the predicted per-record P99 in µs.
      - P3. Predicted outcome of the first `O_DIRECT` write with a `Box<[u8; 4096]>` buffer (success? which errno?).
      - P4. Predicted moment your code fires `completion_tx` (on write CQE or on fsync CQE?) — and whether that prediction is durably correct.
      - P5. **List every Phase-2 test you predict your first attempt will fail.** (Honest list — compared line-by-line after the run; the gap is the lesson.)

    - *Mental model*: the journal is the single durability authority for the ledger — nothing is "committed" until its bytes survive a power cut. fsync is the only operation that proves that, and it is the slowest thing in the path; the entire design exists to amortize one fsync over many records without ever lying about durability.

    - *Contract*: `IoUringJournal::open(path, ring_depth) -> io::Result<Self>`; `fn write_record(&self, rec: &Record) -> oneshot::Receiver<io::Result<Offset>>` (returns immediately; the receiver resolves only after the batch's fsync CQE); `fn recover(path) -> io::Result<(Self, Offset)>` (returns the durable tail). No `&mut self` on the write path — single-writer task owns the ring.

    - *Back-of-envelope* (bar (c)): NVMe fsync ≈ 75 µs (≈ 150 k cycles @ 2 GHz); `io_uring_enter` syscall ≈ 300 ns; memcpy of a 256 B record ≈ 50 ns; malloc ≈ 50 ns. Per-record-fsync ceiling = 1 / 75 µs = **13.3 k/s** — the cliff. Group-commit at batch=256: one 75 µs fsync amortizes to **75 µs / 256 ≈ 290 ns/record** + 80 ns SQE submit + 80 ns memcpy ≈ **450 ns/record → ~2.2 M/s ceiling**, target 100 k/s with huge headroom. **Cliff ratio: 13 k/s vs 2.2 M/s = ~165× on the headline metric.** Zero-alloc requirement: at 100 k/s, one malloc/record = 100 k × 50 ns = 5 ms/sec of pure allocator (~0.5% CPU) AND tail-latency landmines — pre-register buffers, 0 allocs in the loop.

    - **The problem this primitive solves**: durability requires fsync; fsync is expensive (~75 µs on NVMe). Per-record fsync caps throughput at ~13 k/s. Group-commit amortizes one fsync over 256 records: per-record cost drops to ~290 ns. io_uring `IOSQE_IO_LINK` chains writes + fsync into a single submission so completion of the fsync CQE signals durability for all N writes simultaneously.

    - **Requirements** — write in `crates/ledger-deterministic/notes/90mon_io_uring_journal_design.md`:
      - R1. `IoUringJournal` opens journal file with `O_DIRECT | O_APPEND | O_DSYNC | O_CLOEXEC`; pre-allocates 1 GB.
      - R2. Group-commit batches up to 256 records OR `flush_horizon_us = 50` µs (whichever first); single `IORING_OP_FSYNC` trails the batch via `IOSQE_IO_LINK`.
      - R3. Sustained throughput ≥ 100 k Transfers/sec on consumer NVMe.
      - R4. Per-record amortized P99 < 1 µs post-batching (75 µs / 256 ≈ 290 ns/record fsync amortized + 80 ns SQE submit + 80 ns memcpy).
      - R5. Journal buffers are `#[repr(C, align(4096))]` (O_DIRECT requires 4 KB-aligned address+length+offset); pre-registered via `io_uring_register_buffers` for `write_fixed`.
      - R6. `completion_tx: oneshot::Sender<()>` resolves only after the batch's fsync CQE returns — no early-ack lies.
      - R7. Crash recovery: on restart, scan journal tail; truncate to last fsync'd offset; replay state matches pre-crash byte-for-byte.
      - R8. dhat reports 0 allocations during a 1 M-record sustained write loop.
      - R9. Opportunistic immediate fsync when `pending.len() == 0` and rate is low — keeps single-record P99 acceptable for low-rate workloads.
      - R10. Backpressure: when registered-buffer pool exhausted, return `Err(BackPressure)` — never block.

    - **Design walk-through** — answer each; no peeking at TigerBeetle `journal.zig::write_prepare` or PostgreSQL `wal_writer.c` until Phase 3:
      - D1. Why `O_DIRECT | O_DSYNC` and not just `O_DSYNC`? (O_DIRECT bypasses page cache; O_DSYNC ensures hardware durability; together = "data is on the device, not in any cache".) What does `O_DIRECT` require of every write (alignment 3-way)?
      - D2. Group-commit math: at 100 k/s with 256-record batches = 390 fsyncs/sec × 75 µs = 30 ms/sec disk-flush overhead (~3%). At 32-record batches = 3125 fsyncs/sec × 75 µs = 234 ms/sec (~23%). Why is 256 the right batch size? At 1024? (Memory + latency cliff.)
      - D3. `flush_horizon_us = 50 µs`: derivation. Below the budget P99 < 100 µs single-record. Single-record writer waits up to 50 µs for batch fill — that's the worst-case P99 contribution. What's the P99 if batch fills before 50 µs? (Sum of in-flight write + fsync ≈ 75 µs single fsync + memcpy ≈ 80 ns; P99 ~75 µs.)
      - D4. `IOSQE_IO_LINK` semantics: chain N writes + 1 fsync so the kernel processes them in order; fsync CQE doesn't return until all linked writes finish. Why is this superior to issuing writes separately then a barrier-fsync? (One syscall vs N+1; ordering guaranteed by kernel.)
      - D5. SQE/CQE sizing: SQ = 256 (matches batch size), CQ = 4× SQ = 1024 (avoids overflow under burst). Why is CQ overflow catastrophic? (Lost completions = lost durability ack = correctness bug.)
      - D6. SQPOLL mode: kernel polls SQ tail in a dedicated thread; userspace doesn't syscall to submit. Cost: one kernel thread always running. Benefit: ~250 ns/op saved (no `io_uring_enter`). When does SQPOLL pay off? (≥1 k SQE/sec sustained.)
      - D7. Buffer alignment: Rust allocator returns 8-byte alignment by default. `Box::new_zeroed::<[u8; 4096]>()` is 4 KB long but NOT 4 KB-aligned in address. `O_DIRECT` returns EINVAL on first write. How does `#[repr(C, align(4096))] struct JournalBuf([u8; N]);` fix this? Verify with what assertion?
      - D8. Recovery flow: SIGKILL mid-batch; on restart, what's in the file? (Last fsync'd offset + zero-to-many incomplete writes after.) How does scan-and-truncate work? (Read tail forward; find first record with bad checksum or torn header; truncate file to previous valid offset; document the durability point.)
      - D9. **Pre-mortem (load-bearing)**: write the 5-step interleaving where a "passes-tests" group-commit silently loses data. Scenario: writes A, B, C submitted as a linked batch with trailing fsync; CQE for write A returns, code signals completion_tx_A, then power-loss before fsync CQE. What did the client think? (A is durable.) What's true? (A may or may not be on disk.) Fix: completion_tx fires only on fsync CQE, never on write CQE.

    - **Output**: `notes/90mon_io_uring_journal_design.md` with R1–R10 + D1–D9 + the linked-SQE chain diagram + recovery flowchart.

    #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

    Ordered newbie → expert — the ladder you actually walk.

    - **(EXPERT) Expect to hit (perf) #1 — per-record fsync (bar (c) violation): `bench_io_uring_journal_100k_per_sec_sustained` reports ~13 k/s (vs 100 k/s target):**
      - Symptom: throughput cap ~13 k/s = 1/75 µs; sustained writes choke at one-fsync-per-record.
      - Why: naive implementation submits one `IORING_OP_WRITE` + one `IORING_OP_FSYNC` per `write_record`. Each fsync forces device flush ~75 µs.
      - Fix: group-commit with `IOSQE_IO_LINK`. Accumulate writes in `pending: ArrayVec<PendingWrite, 256>`. On either (a) `pending.len() >= 256` or (b) `now - first_pending_at >= 50 µs`, submit SQE batch: N writes chained via `IOSQE_IO_LINK` to a single trailing `IORING_OP_FSYNC`. Fire each `completion_tx.send(())` together on fsync CQE.
      - Cost avoided: per-record fsync (75 µs) → per-batch fsync (290 ns/record amortized) — a **~260× win** on the headline metric. Without group-commit, the SHIP target is unattainable.
      - Muscle: in any "must-fsync" durability path, batch the fsyncs. The latency-horizon (50 µs) is the cost paid by single-record writers to amortize across the batch. Same pattern: PostgreSQL `commit_delay`, RocksDB `WriteBatch`, Kafka `linger.ms`. Reapplies at: W77 messaging-aeron flow-control batched ACK, W92 v1.0 SHIP throughput gate, W100 mini-db CAPSTONE WAL group-commit.

    - **(SENIOR) When `test_journal_buf_4kb_aligned` fires `assertion failed: buf.as_ptr() as usize % 4096 == 0`:**
      - Symptom: JournalBuf address ends in `0x008` or similar; first `O_DIRECT` write returns `EINVAL` with cryptic kernel message.
      - Why: `Box::new_zeroed::<[u8; 4096]>()` is 4 KB long but Rust allocator returns 8-byte alignment by default. O_DIRECT requires 4 KB-aligned address AND length AND file offset; the address violates.
      - Fix: define `#[repr(C, align(4096))] struct JournalBuf([u8; JOURNAL_BUF_SIZE]);` then `Box::new(JournalBuf([0u8; JOURNAL_BUF_SIZE]))`. The `repr(align(4096))` forces the allocator to return a 4 KB-aligned address. Verify with `debug_assert!(buf.as_ptr() as usize % 4096 == 0);`. File offset is also 4 KB-aligned (writes at `tail_offset` which is a multiple of 4 KB; pad records as needed). Register the buffer via `io_uring_register_buffers` once at startup.
      - Cost avoided: works at all (no `EINVAL`); plus `write_fixed` removes one page-table walk per write (~10 ns/op) and skips user-buffer-validation entirely.
      - Muscle: any `O_DIRECT` I/O requires aligned buffers + offsets + lengths — the kernel does not auto-fix, it `EINVAL`s. Use `#[repr(align(N))]` on the wrapping struct; never assume default allocator alignment. Reapplies at: W92 v1.0 SHIP io_uring durability test, W100 mini-db SSTable write path, W82 matching-engine durable command log.

    - **(EXPERT) When `test_completion_fires_after_fsync_not_write` shows completion_tx fired on write CQE:**
      - Symptom: a write CQE returns and your code fires `completion_tx.send(())` immediately; client thinks the write is durable; power-loss test loses data.
      - Why: the write CQE only confirms the data reached the kernel/device buffer; it does NOT confirm fsync. fsync is a separate barrier; durability is only guaranteed after the fsync CQE.
      - Fix: track `pending_writes_in_current_batch: ArrayVec<PendingWrite, 256>`. On each write CQE: increment a counter; do NOT fire completion_tx. On fsync CQE: drain ALL pending writes in this batch, firing their completion_tx. Use the `user_data` field of the fsync SQE to carry a batch ID.
      - Cost avoided: this is a *correctness* (data-loss) bug, not slowness — silent loss of every record acked between the last write CQE and a power cut. (bar (c) violation — durability is the crate's reason to exist.)
      - Muscle: durability is the LAST barrier in a chain, not any individual write. The completion-signal moment is the fsync CQE, full stop. Reapplies at: W92 v1.0 SHIP power-loss test, W100 mini-db WAL flush, W77 messaging-aeron persistent term.

    - **(EXPERT) When `test_crash_recovery_truncates_to_last_fsync` fails byte-comparison after restart:**
      - Symptom: pre-crash state hash != post-recovery state hash; recovery replayed too far OR too short.
      - Why: scan algorithm either (a) trusted the file size at face value (includes torn writes past last fsync), or (b) truncated too aggressively (lost durable writes before the last fsync).
      - Fix: scan tail forward from last known fsync offset (persisted in a separate metadata file). For each record, verify checksum + length; first failure = truncate point. Persist new tail offset. Document: "WAL durability point = last completed IORING_OP_FSYNC, not the last write."
      - Cost avoided: correctness — phantom-reads of un-acked data OR loss of acked data; both disqualify a ledger. (bar (c) violation.)
      - Muscle: recovery semantics must precisely match durability semantics; what was acked is what must replay, nothing more, nothing less. Reapplies at: W92 ledger snapshot recovery, W100 mini-db recovery, W82 matching-engine command-log replay.

    - **(SENIOR) When `test_group_commit_batches_up_to_256` shows fsync count ~1000 (one per write):**
      - Symptom: bench reports throughput correctly hits 100 k/s; but instrumentation shows ~1000 fsync CQEs for 1000 writes — group-commit didn't batch.
      - Why: code path is correct conceptually but the batch flush trigger is buggy — `pending.len() >= 256` check is on the wrong side of submission, OR `flush_horizon_us` fires per-record instead of per-batch.
      - Fix: batch state machine: `first_pending_at: Option<Instant>` set on first push; flush trigger checks `pending.len() >= 256 || (now - first_pending_at? >= 50 µs)`. After flush, reset `first_pending_at = None`. Instrument and assert.
      - Cost avoided: ~1000 fsyncs vs ~4 = 996 × 75 µs = ~75 ms of wasted device flush per 1000 records; collapses the 165× group-commit win even though the headline bench *looks* green by luck. (bar (c) violation.)
      - Muscle: batch state machines need explicit first-timer state, not "deadline relative to most-recent push". Reapplies at: W77 messaging-aeron flow-control, W92 ledger group-commit, W100 WAL group-commit.

    - **5-year failure mode** (write in `notes/90mon_io_uring_journal_followup.md` after green): when `IORING_OP_FUTEX_WAIT`/`URING_CMD` and direct NVMe submission (bypassing block layer) stabilize, the fsync barrier can become a hardware command (~5 µs instead of 75 µs). Migration: replace `IORING_OP_FSYNC` with `URING_CMD` carrying NVMe FLUSH. Trigger: kernel 6.10+ with NVMe device direct-submit support; 256-batch fsync cost > 50% of total CPU.

- [NEW v2] **consensus-vsr v1.0: reconfiguration (part 1)**
  - [ ] **Build**: `crates/consensus-vsr/src/reconfig.rs` — add/remove replica via Reconfiguration messages; atomic config swap at op N+1 via view change. (~total 4 hrs across 3 phases)
    - 🔧 **Why this matters**: a v1.0 consensus protocol cannot ship without membership change — static membership is a toy. Reconfiguration is also where the subtlest bugs live: quorum during transition, log-truncation safety, joint-quorum overlap. VSR's reconfiguration is more elegant than Raft's joint-consensus — it leverages the commit-then-swap pattern to atomically change configs. Downstream consumers: W90 Thu VSR v1.0 SHIP (gates on reconfig tests), W105+ ops deployment (rolling upgrades).

    #### Phase 1 — Problem, requirements, design (~70 min, no code yet)

    - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/consensus-vsr/notes/90wed_reconfig_prediction.md` (compare to reality after Phase 2 tests run):
      - P1. The primitive you'd reach for to represent membership: the exact type you'd declare (`Vec<ReplicaId>`? `ArrayVec<ReplicaId, MAX_REPLICAS>`? an `Arc<RwLock<Config>>` you'd swap under lock?). Name why a lock on the config is the wrong instinct here.
      - P2. Predicted reconfig completion time for a 3→4 add on a 1 GB journal, in seconds, AND what dominates it (network? memcpy? fsync?).
      - P3. Predicted concurrent-first-call outcome: leader receives Add(D) and Add(E) in the same view simultaneously — what is the *naive* outcome, and is it safe?
      - P4. Predicted state-transfer cost: how many bytes of user-space memcpy will your *first* impl do for the 1 GB snapshot, and at what GB/s?
      - P5. **List every Phase-2 test you predict your first attempt will fail.** (Compared line-by-line after the run.)

    - *Mental model*: reconfiguration is "change the membership set without ever having two configs both believe they can form a quorum." VSR gets this for free by making the config change *just another committed op*: everyone swaps atomically at the op that follows the committed Reconfig op, so there is never a joint window to reason about.

    - *Contract*: `fn propose_reconfig(&mut self, cmd: ReconfigCommand) -> Result<OpNum, ReconfigError>` (leader-only; `Err(ReconfigInProgress)` if one is outstanding); `Configuration { replicas: ArrayVec<ReplicaId, MAX_REPLICAS>, epoch: u32 }`; the config swap is a single `self.config = new_config` write inside the commit handler of the Reconfig op — no lock, no joint set. View-change must reject any candidate advertising a stale `config.epoch`.

    - *Back-of-envelope* (bar (c)): config-epoch check on the hot path = ~1 ns/branch; at 3 handlers × 90 k msg/s = ~270 µs/sec — small but precedent-setting (feature-accretion death spiral). State-transfer: 1 GB snapshot, naive = 2 user-space copies × 5 GB/s memcpy = **~400 ms pure memcpy** + L2/L3 pollution evicting neighbours' hot sets; `sendfile`/`splice` = **~0 ns/byte on the app side**, leaving transfer network-bound at ~200 MB/s consumer TCP → ~5 s for 1 GB. **Cliff: ~400 ms CPU-bound memcpy → ~0 ms app CPU (transfer becomes wire-bound).**

    - **The problem this primitive solves**: Static membership requires fleet downtime to add/remove a replica. Reconfiguration must preserve safety (no double-leadership, no committed-op loss) AND liveness (cluster keeps making progress) during transition. VSR achieves both by piggybacking on its existing op-commit pipeline: the reconfig command is just another op; once committed, all replicas atomically swap at op N+1.

    - **Requirements** — write in `crates/consensus-vsr/notes/90wed_reconfig_design.md`:
      - R1. `Configuration { replicas: ArrayVec<ReplicaId, MAX_REPLICAS>, epoch: u32 }` — monotonic epoch tracks reconfig version.
      - R2. `ReconfigCommand` is serialized into a normal `VsrMessage` (Add/Remove variants); committed via the SAME Prepare/PrepareOk/Commit pipeline as ledger ops.
      - R3. Quorum during proposal: OLD config quorum agrees to the reconfig op; only on commit does the config swap. No joint-quorum window.
      - R4. Atomic switch at op N+1: on commit of reconfig op at op N, `self.config = new_config` is a single write; from N+1 onward, all messages use new config quorum.
      - R5. Joining replica catches up via state-transfer (snapshot + journal replay) BEFORE participating in quorum; sends "Joined" only after at op N (the reconfig op).
      - R6. Leaving replica halts apply at op N (not N+1); persists a Tombstone so on restart it refuses to re-join old cluster.
      - R7. Normal-op apply latency unchanged before vs after reconfig — config check is one branch at message-decode entry, not per-handler.
      - R8. State-transfer uses `sendfile(2)` / `splice(2)` — zero user-space copy of the 1 GB snapshot.
      - R9. Only one outstanding reconfig op at a time (leader enforces); concurrent reconfig requests serialized.
      - R10. Reconfig completion <5 s for 3→4 add on 1 GB journal (state-transfer dominates at ~200 MB/s sustained TCP).

    - **Design walk-through** — answer each; no peeking at Liskov-Cowling 2012 §5 or TigerBeetle `vsr/replica.zig::ReconfigurationRequest` until Phase 3:
      - D1. Quorum during transition: write the 5-step Prepare → PrepareOk → Commit flow with N=3 cluster proposing Add. Which 2 replicas must ack? (OLD quorum.) When does the new replica count toward quorum? (After Commit, from op N+1.) Why does this avoid Raft's joint-consensus overhead?
      - D2. Atomic-switch property: what makes the config swap "atomic"? (Single `self.config = new_config` write at end of commit handler; no spinlock; no joint window.) What if a Prepare for op N+1 arrives before commit of op N? (Buffered; processed under whichever config holds at apply time.)
      - D3. Joining replica flow: leader sends snapshot bytes; joiner installs; joiner needs to know the op-num at which snapshot was taken. How does joiner verify (state_hash, op_num) match leader's claim? Why does joiner buffer messages during state-transfer instead of applying them?
      - D4. Leaving replica flow: at op N (the Remove op), leaving replica acks but doesn't apply anything past N. Persists Tombstone. On restart, replica reads Tombstone first thing; refuses to enter Normal status. Why is the Tombstone load-bearing? (Without it, a leaving replica restarted into old config could form a rogue quorum with a partitioned subset.)
      - D5. View-change interaction: post-reconfig at op N, what config does a new leader use for op N+10? (New config, from op N+1 onward.) How does new leader derive the right config? (Replay op history; the Reconfig commit at op N is the source of truth.)
      - D6. Config-check on hot path: post-reconfig, every message handler could check `msg.config_epoch == self.config.epoch`. Cost: ~1 ns predicted × 3 handlers × 90 k msg/s = ~270 µs/sec. Negligible? Yes, but precedent-setting — feature accretion is the bar-(c) death spiral. How do you check ONCE at message-decode, not 3× per handler? Encode `config_epoch` in the message header; reject at decode if mismatch.
      - D7. State-transfer at 200 MB/s: naive impl reads snapshot into `Vec<u8>`, encodes into VsrMessage body chunks, sends, receiver decodes, writes file. 1 GB × 2 user-space copies × ~5 GB/s memcpy = 400 ms just on memcpy. Why does `sendfile(2)` (or `IORING_OP_SPLICE`) eliminate this? (Kernel copies file→socket without user-space touch; ~0 ns per byte on the application side.)
      - D8. Concurrent reconfigs: leader receives two AddReplica requests simultaneously. What if both get accepted? (Quorum forms for op N=Add(A) and N=Add(B); the SECOND becomes op N+1 once N commits — only if it survives the config change.) Better: leader rejects the second until the first commits. How?
      - D9. **Pre-mortem (load-bearing)**: write the 6-step interleaving where a "passes tests" reconfig silently violates safety. Scenario: 3-replica cluster proposes Add(D). Replicas A, B commit. C is partitioned. C comes back online thinking it's still in old 3-replica config; tries to elect itself as leader at higher view-num. What stops it? (Tombstone? No — C didn't leave.) Hint: epoch-gated view-num — view-change protocol must reject any candidate whose advertised config epoch is stale.

    - **Output**: `notes/90wed_reconfig_design.md` with R1–R10 + D1–D9 + state diagram of the config-swap flow + Tombstone persistence design.

    - **(SENIOR) Expect to hit (perf) #1 — user-space copy of the snapshot (bar (c) violation): `test_state_transfer_uses_sendfile_no_user_copy` shows ~1 GB of read/write syscalls:**
      - Symptom: strace reports 250 k read+write calls for the 1 GB snapshot; reconfig completion 5.4 s; CPU saturated at ~80% during transfer.
      - Why: naive impl: leader reads snapshot file into `Vec<u8>`, encodes into VsrMessage body chunks, sends; joiner decodes, writes file. 1 GB × 2 user-space copies × ~5 GB/s memcpy = ~400 ms pure memcpy. Plus the L2/L3 cache pollution evicts adjacent replicas' hot working sets.
      - Fix: state-transfer uses `sendfile(2)` (or `IORING_OP_SPLICE` if io_uring) on sender side — kernel copies snapshot file → socket with zero user-space touch. Receiver uses `splice(2)` from socket → snapshot file. Both at near-line-rate (~200 MB/s sustained TCP on consumer hardware; ~5 GB/s on bonded 40G). Application-layer chunking + state-hash gossip happens out-of-band over the slow path.
      - Cost avoided: ~400 ms memcpy → ~0 ms; reduces reconfig completion from ~5.4 s to ~5.0 s (state-transfer now network-bound, not CPU-bound). Plus L2/L3 cache pollution avoided.
      - Muscle: any bulk transfer of file data to/from another machine uses `sendfile`/`splice` — never read-into-user + write. Reapplies at: W92 ledger snapshot transfer, W100 mini-db CAPSTONE SSTable replication, W82 matching-engine snapshot to new raft follower.

    - **(SENIOR) Expect to hit (perf) #2 — hot-path branch accretion (bar (c) violation): `test_normal_apply_latency_unchanged_post_reconfig` shows ~5% P99 regression:**
      - Symptom: pre-reconfig commit P99 = 480 µs; post-reconfig = 504 µs; +5% creep.
      - Why: every `on_prepare`/`on_prepare_ok`/`on_commit` handler grew a `if msg.config_epoch != self.config.epoch { reject }` branch. ~1 ns predicted × 3 handlers × 90 k msg/s = ~270 µs/sec real cost; but combined with branch-mispredicts on the rare reconfig path = ~5 ns × occasional × N msgs = visible P99 noise.
      - Fix: encode `config_epoch` as top 32 bits of `op_num` (already on every message); compare via single `u64` mismatch test inside the existing op-num ordering check. OR process the config_epoch check ONCE at message-decode entry (one branch), then proceed through normal handlers unaware. Discipline: "add no branches to the steady-state apply path for features that fire rarely."
      - Cost avoided: small absolute (~1 µs/sec) but precedent-setting. Feature accretion is the bar-(c) death spiral — 50 "I'll just add one branch" decisions = 200 ns regression = 20% paper-cut.
      - Muscle: every conditional on the hot path must justify its budget contribution. Use compile-time generics or message-decode-time validation to keep the hot loop branch-clean. Reapplies at: W82 matching-engine pre-trade risk checks, W94 exec-vm v1.5 parallel-vs-sequential paths, W92 ledger v1.0 SHIP P99 regression check (CI fails on +5% creep).

    - **(EXPERT) When `test_joining_replica_buffers_during_state_transfer` shows joiner applying op N+5 before op N+4:**
      - Symptom: joiner installs snapshot at op N; receives Prepare for op N+5 from leader; applies it; later receives op N+4; out-of-order apply violates state-machine determinism.
      - Why: joiner enters Normal status as soon as snapshot installed; doesn't buffer post-state-transfer messages until at op N.
      - Fix: joiner state machine: `SyncStatus { StateTransfer { target_op_num }, Catchup { buffered: ArrayVec<VsrMessage, 1024> }, Normal }`. During StateTransfer, ignore Prepares. After install, transition to Catchup; buffer incoming Prepares; replay journal up to `target_op_num`; only then drain buffered Prepares in order and transition to Normal.
      - Cost avoided: correctness — out-of-order apply forks the joiner's state machine from the cluster (divergent state_hash forever). (bar (c) violation — determinism is the ledger's contract.)
      - Muscle: state-transfer boundary requires explicit buffer-then-replay phase; never apply out-of-order. Reapplies at: W100 mini-db follower catchup, W92 ledger replica join.

    - **(SENIOR) When `test_leaving_replica_tombstone_persisted` shows replica restarts into Normal status:**
      - Symptom: RemoveReplica completes; SIGKILL leaving replica; restart; replica re-enters cluster as if nothing happened; potential rogue quorum risk.
      - Why: Tombstone was written to a regular file but not fsync'd; or the startup check happens after Normal status entry, not before.
      - Fix: Tombstone is written via the journal (group-commit, fsync'd) at the moment RemoveReplica commits. On startup, BEFORE any other init, scan journal for Tombstone; if present, exit with `Err(ReplicaTombstoned)` and operator-friendly message.
      - Cost avoided: correctness — a restarted leaving replica + a partitioned subset can form a rogue quorum (split-brain double-leadership). (bar (c) violation.)
      - Muscle: durability-critical state (Tombstone) goes through the durability path (journal + fsync); startup checks happen FIRST, before any cluster participation. Reapplies at: W100 mini-db node demotion persistence, W82 matching-engine session tombstone.

    - **(EXPERT) When `test_concurrent_reconfig_serialized` shows two reconfig ops committing simultaneously:**
      - Symptom: leader accepts Add(D) and Add(E) within the same view; both proceed through Prepare/Commit; cluster ends in undefined state (4-replica? 5-replica? mismatched configs across replicas?).
      - Why: leader doesn't track `pending_reconfig`; treats reconfig ops as independent.
      - Fix: `VsrReplica` state: `pending_reconfig: Option<OpNum>`. On AddReplica/RemoveReplica request, leader checks `if pending_reconfig.is_some() { return Err(ReconfigInProgress); }`. Set on Prepare; clear on Commit. Subsequent requests queue or reject at admin API.
      - Cost avoided: correctness — overlapping config changes leave replicas with mismatched membership sets (no coherent quorum), a permanent split. (bar (c) violation.)
      - Muscle: reconfig ops are special; only one outstanding at a time per cluster. Document in admin API + runbook. Reapplies at: W100 mini-db reconfig API, W82 matching-engine session reconfig.
