  - *Mental model*: cross-margin is "the portfolio's risk is **less than the sum of its legs'** risk, because the legs partly offset." A long BTC-PERP and a short ETH-PERP partly hedge (BTC and ETH co-move at ≈0.7), so the portfolio needs less margin than two isolated positions. The engine's job: compute that offset, then **under-credit it** (keep only 70% of the raw offset — the const 30% haircut) so it is conservative by construction. v0.5 is the *shape*, not the scale: get the netting math and the determinism right; W97 scales it to 100k accounts via incremental margin. The crate is a pure function `margin(portfolio, mark) → (IM, MM, margin_ratio)` — it reads state, computes a number, never mutates the book or liquidates.

  - *Contract* (signature only — NEVER the body):
    ```rust
    pub struct CrossMarginAccount {
        positions: [Position; MAX_INSTRUMENTS],   // fixed-cap, Copy, deterministic iteration (R1)
        n: u8,
        equity: Notional,                         // integer bps/cents, never f64 (R3)
    }
    #[derive(Clone, Copy)] pub struct Position { instrument: InstrumentId, signed_qty: i64, /* lots */ }
    #[derive(Clone, Copy)] pub struct MarginResult { im: Notional, mm: Notional, ratio: Bps } // ratio = equity / mm
    impl CrossMarginAccount {
        /// Pure: reads positions + the already-committed mark; returns margin. No mutation, no liquidation.
        pub fn margin(&self, marks: &MarkSet) -> MarginResult;          // the convergence-cell hot path
        pub fn isolated_im(&self, marks: &MarkSet) -> Notional;         // baseline: sum of per-leg IM (no netting)
        pub fn netting_offset(&self, marks: &MarkSet) -> Notional;      // raw offset BEFORE the haircut
    }
    pub const NETTING_HAIRCUT_BPS: Bps = Bps(3000); // const 30% — DECLARED MODEL PARAM, not per-seed random (§4A)
    // NOTE (v3): no liquidate(), no apply_funding(), no compute_mark(). Margin in, margin-ratio out.
    ```
  - *Back-of-envelope* (bar (c) — name the cost): v0.5 target = correctness + the *shape* of the hot path; the 100k-account scale is W97. But the design must already be alloc-free and integer-only so W97 only adds the incremental delta, not a rewrite.
    - Per-account recompute cost: 2 instruments × (notional mult ≈ 2ns + IM-rate mult ≈ 2ns) + 1 netting-offset subtract ≈ 1ns + 1 haircut mult ≈ 1ns ≈ **~10ns/account, 0 allocs** if `Copy` + integer. At W97's 100k accounts × 10 mark ticks/s = **1M recomputes/s × ~10ns = ~10ms/s single-threaded** — fits one core for *full* recompute at this tiny instrument count, BUT at per-trade mark cadence it blows the budget → W97 incremental margin is mandatory (§4A back-of-envelope). v0.5 records the number so W97 starts from a measured baseline.
    - Alloc cliff: a `HashMap<InstrumentId, Position>` per account = 1+ malloc/account × 100k = 100k mallocs/recompute → impossible at per-tick cadence + non-deterministic iteration. Fixed `[Position; MAX_INSTRUMENTS]` = 0 allocs, deterministic order.
    - Determinism cliff: `f64` netting math → x86 FMA ≠ ARM Neon rounding → replicas diverge → cluster-VOPR (W108) red. Integer bps/cents only.

  - **The problem this primitive solves**: a perp venue that charges **isolated** margin (sum of per-leg requirements) over-collateralizes any hedged portfolio — a long-BTC/short-ETH book pays as if both legs were naked, so traders defect to venues with portfolio margin. Cross-margin credits the offset. But it introduces THREE failure categories the v1.0 lock pre-empts: (a) **non-determinism** — `f64` netting or `HashMap` iteration diverges replicas (the VSR cluster must agree bit-identically, §3 row 21); (b) **over-crediting** — a too-generous netting credit means the account is under-margined when correlation breaks toward 1 in a crash (so the **haircut under-credits by construction**); (c) **scope creep** — the temptation to "just liquidate here since we already know the ratio," which re-merges `liquidation-engine` into `risk-engine`. The fix: integer-only deterministic math + a **declared const haircut** (not a per-seed random) + a hard scope gate (margin in, ratio out, no liquidation).

  - **Requirements** — write in `crates/risk-engine/notes/90mon_cross_margin_design.md`:
    - R1. `CrossMarginAccount` holds positions in a fixed `[Position; MAX_INSTRUMENTS]` (Copy, deterministic iteration); no `HashMap`, no `Vec` in the margin path.
    - R2. `margin(&self, marks)` is **pure** — reads positions + marks, returns `MarginResult`; never mutates, never liquidates, never computes funding.
    - R3. **Integer-only math**: notionals in cents, rates/haircut in bps; no `f64`/`f32` anywhere in the margin path. CI clippy `disallowed-types = ["f64","f32"]`.
    - R4. **Isolated baseline**: `isolated_im(marks)` = Σ |signed_qty × mark × im_rate| over legs — the no-netting reference. Cross-margin IM **must** be ≤ isolated IM for any non-degenerate hedged portfolio (or netting is hollow — §4A acceptance #1).
    - R5. **Netting offset**: `netting_offset(marks)` computes the raw risk offset between opposing-direction legs (the part correlation would cancel). v0.5: a single cross-instrument pair term (BTC↔ETH); generalizes in v1.5.
    - R6. **Const 30% haircut (declared model param)**: credited offset = `netting_offset × (10000 − NETTING_HAIRCUT_BPS) / 10000` = 70% of raw. `NETTING_HAIRCUT_BPS` is a compile-time/config **declared parameter**, NOT randomized per VOPR seed (§4A — randomizing injects non-determinism + reframes the question).
    - R7. **Conservative invariant**: cross IM ≥ a hard floor (never credit more than the offset; never go negative); under-credits, never over-credits.
    - R8. **Margin ratio**: `ratio = equity / mm` in bps; this is the *only* output the downstream `liquidation-engine` (W100) consumes — the margin/liquidation boundary.
    - R9. **Read source (the §4A control/risk-plane contract)**: positions + marks are read from the leader shard's **local applied committed state** (read-after-commit, no consensus round-trip per read), NEVER from a `log-distributed` bounded-staleness projection. A margin computed from a stale mark is a correctness bug.
    - R10. **Zero alloc**: dhat reports 0 allocations across 1M `margin()` calls.
    - R11. **Cross-arch byte-identical**: x86 + aarch64 produce identical `MarginResult` for the same portfolio + marks (integer math; no f64).
    - R12. **Scope gate (v3)**: `risk-engine/src/` contains no liquidation/ADL/insurance/funding-formula identifier (CI grep). The crate computes margin; it does not act on it.
    - R13. **Review trigger wired (v1.5 seam)**: a documented trigger — replace the const haircut with rolling empirical correlation when ANY of: (a) an instrument with materially different correlation is added (RWA-perp vs crypto-perp); (b) VOPR shows 30% too loose; (c) the v1.5 RWA milestone. Recorded in the design doc, not "never."

  #### Phase 3 — Make the tests pass, one failure at a time (~135 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(SENIOR) Expect to hit (perf/correctness) #1 — netting hollow (bar (c) violation of §4A acceptance #1): `test_cross_margin_strictly_below_isolated` fails, cross IM == isolated IM:**
    - Symptom: `margin().im` equals `isolated_im()` exactly; no offset credited; the crate computes a *correct* but *hollow* margin.
    - Why: the first draft computes per-leg IM and sums it — it never looks at the *relationship* between legs. A single-instrument or per-leg engine cannot net.

    - Cost avoided: this is the **principal artifact's reason to exist** — a hollow netting engine fails the M24 checkpoint, the §4A acceptance #1, and the founding-engineer narrative ("cross-margin has no spot analog"). Not slowness — *the* domain-correctness bar.
    - Muscle: portfolio margin is a property of the *portfolio*, never the sum of per-leg properties. Reapplies at: W97 incremental margin (delta on the portfolio offset), W99 v1.0, W103 capstone acceptance #1.

  - **(SENIOR) When `test_haircut_credits_exactly_70pct` shows 100% credited (no haircut):**
    - Symptom: `test_cross_margin_strictly_below_isolated` passes but this exact-value test shows the full raw offset was credited.
    - Why: the netting math credited `offset × 1.0` — the conservative haircut was forgotten ("the empirical offset is right, why discount it?").

    - *Mental model*: reconfiguration is "change the membership set without ever having two configs both believe they can form a quorum." VSR gets this for free by making the config change *just another committed op*: everyone swaps atomically at the op following the committed Reconfig op, so there is never a joint window.

    - *Contract*: `fn propose_reconfig(&mut self, cmd: ReconfigCommand) -> Result<OpNum, ReconfigError>` (leader-only; `Err(ReconfigInProgress)` if one outstanding); `Configuration { replicas: ArrayVec<ReplicaId, MAX_REPLICAS>, epoch: u32 }`; the swap is a single `self.config = new_config` write inside the commit handler of the Reconfig op — no lock, no joint set. View-change rejects any candidate advertising a stale `config.epoch`.

    - *Back-of-envelope* (bar (c)): config-epoch check on the hot path = ~1 ns/branch; at 3 handlers × 90 k msg/s = ~270 µs/sec — small but precedent-setting. State-transfer: 1 GB snapshot, naive = 2 user-space copies × 5 GB/s memcpy = **~400 ms pure memcpy** + cache pollution; `sendfile`/`splice` = **~0 ns/byte app-side**, leaving transfer network-bound at ~200 MB/s consumer TCP → ~5 s for 1 GB. **Cliff: ~400 ms CPU-bound memcpy → ~0 ms app CPU.**

    - **The problem this primitive solves**: static membership requires fleet downtime to add/remove a replica. Reconfiguration must preserve safety (no double-leadership, no committed-op loss) AND liveness during transition. VSR achieves both by piggybacking on the op-commit pipeline: the reconfig command is just another op; once committed, all replicas atomically swap at op N+1.

    - **Requirements** — write in `crates/consensus-vsr/notes/90tue_reconfig_design.md`:
      - R1. `Configuration { replicas: ArrayVec<ReplicaId, MAX_REPLICAS>, epoch: u32 }` — monotonic epoch tracks reconfig version.
      - R2. `ReconfigCommand` serialized into a normal `VsrMessage` (Add/Remove); committed via the SAME Prepare/PrepareOk/Commit pipeline as venue ops.
      - R3. Quorum during proposal: OLD config quorum agrees to the reconfig op; only on commit does the config swap. No joint-quorum window.
      - R4. Atomic switch at op N+1: on commit of reconfig op at op N, `self.config = new_config` is one write; from N+1 onward, new-config quorum.
      - R5. Joining replica catches up via state-transfer (snapshot + journal replay) BEFORE participating in quorum; sends "Joined" only after op N.
      - R6. Leaving replica halts apply at op N; persists a Tombstone so on restart it refuses to re-join the old cluster.
      - R7. Normal-op apply latency unchanged before vs after reconfig — config check is one branch at message-decode entry, not per-handler.
      - R8. State-transfer uses `sendfile(2)`/`splice(2)` — zero user-space copy of the 1 GB snapshot.
      - R9. Only one outstanding reconfig at a time (leader enforces); concurrent requests serialized.
      - R10. Reconfig completion < 5 s for 3→4 add on a 1 GB journal (state-transfer dominates at ~200 MB/s sustained TCP).

    - **Design walk-through** — answer each; no peeking at Liskov-Cowling 2012 §5 or TigerBeetle `ReconfigurationRequest` until Phase 3:
      - D1. Quorum during transition: write the 5-step Prepare → PrepareOk → Commit flow with N=3 proposing Add. Which 2 replicas must ack? (OLD quorum.) When does the new replica count? (After Commit, op N+1.) Why does this avoid Raft's joint-consensus overhead?
      - D2. Atomic-switch: what makes the swap "atomic"? (Single `self.config = new_config` at end of commit handler; no spinlock; no joint window.) What if a Prepare for op N+1 arrives before commit of op N? (Buffered; processed under whichever config holds at apply time.)
      - D3. Joining flow: leader sends snapshot bytes; joiner installs; joiner needs the op-num at which the snapshot was taken. How does it verify `(state_hash, op_num)`? Why buffer messages during state-transfer instead of applying?
      - D4. Leaving flow: at op N (Remove), the leaving replica acks but applies nothing past N; persists Tombstone; on restart reads Tombstone first, refuses Normal status. Why is the Tombstone load-bearing? (Without it, a restarted leaving replica + a partitioned subset can form a rogue quorum.)
      - D5. View-change interaction: post-reconfig at op N, what config does a new leader use for op N+10? (New config, from N+1.) How does it derive it? (Replay history; the Reconfig commit at op N is the source of truth.)
      - D6. Config-check on the hot path: ~1 ns × 3 handlers × 90 k msg/s = ~270 µs/sec — negligible but precedent-setting (feature-accretion death spiral). How do you check ONCE at message-decode, not 3× per handler? (Encode `config_epoch` in the message header; reject at decode.)
      - D7. State-transfer at 200 MB/s: naive reads snapshot into `Vec<u8>`, encodes, sends, receiver decodes, writes file = 1 GB × 2 copies × ~5 GB/s = 400 ms memcpy. Why does `sendfile(2)`/`IORING_OP_SPLICE` eliminate this? (Kernel copies file→socket; ~0 ns/byte app-side.)
