## Monday — newPayload implementation + [NEW v2] consensus-vsr ViewChange protocol

- [ ] Implement newPayload V3 handler in consensus-engine. (~120 min)
- [ ] [NEW v2] **Build**: `crates/consensus-vsr/src/view_change.rs` — primary suspected dead → backup sends
  StartViewChange → DoViewChange with log/op_num → new primary sends StartView with merged log. (~3 hrs)
  - **Why**: ViewChange is the *correctness-critical* path of VSR — when normal operation breaks (leader crashed/partitioned), this is the protocol that restores liveness without losing committed ops. It's also the most-likely-to-be-buggy module in any consensus implementation; TigerBeetle's VOPR finds most regressions here. Bar (c).
  - **Read first**: Liskov-Cowling 2012 §5 (View Change). TigerBeetle `vsr/replica.zig::on_start_view_change`, `on_do_view_change`, `on_start_view`. Diego Ongaro's thesis Chapter 4 (Raft equivalent — useful contrast).
  - **Design**:
    ```rust
    pub struct ViewChangeReplica {
        pub id: ReplicaId,
        pub view: View,                       // the NEW view-num we're targeting
        pub status: ReplicaStatus,            // == ViewChange
        pub last_normal_view: ViewNum,        // highest view-num we were in Normal status
        pub log: Log,                          // carry over from Normal
        pub op_num: u64,
        pub commit_num: u64,
        pub start_view_change_acks: BitSet,   // replicas that have started VC
        pub do_view_change_msgs: AHashMap<ReplicaId, DoViewChange>,  // collected by new leader
    }
    pub struct StartViewChange {
        pub view_num: ViewNum,
        pub from: ReplicaId,
    }
    pub struct DoViewChange {
        pub view_num: ViewNum,
        pub log: Log,                         // full log of sender
        pub last_normal_view: ViewNum,
        pub op_num: u64,
        pub commit_num: u64,
        pub from: ReplicaId,
    }
    pub struct StartView {
        pub view_num: ViewNum,
        pub log: Log,                         // merged log chosen by new leader
        pub op_num: u64,
        pub commit_num: u64,
    }
    impl ViewChangeReplica {
        // 1. Any replica suspects primary dead → bump view, send StartViewChange to all
        pub fn start_view_change(&mut self, new_view: ViewNum) {
            assert!(new_view > self.view.view_num);
            self.view.view_num = new_view;
            self.status = ReplicaStatus::ViewChange;
            self.broadcast(StartViewChange { view_num: new_view, from: self.id });
        }
        // 2. Collect f+1 StartViewChange acks → send DoViewChange to NEW leader
        pub fn on_start_view_change(&mut self, m: StartViewChange) {
            if m.view_num < self.view.view_num { return; }
            if m.view_num > self.view.view_num { self.start_view_change(m.view_num); }
            self.start_view_change_acks.insert(m.from as usize);
            if self.start_view_change_acks.count_ones() as u8 >= self.view.quorum() {
                let new_leader = self.view.leader();
                self.send_to(new_leader, DoViewChange {
                    view_num: self.view.view_num,
                    log: self.log.clone(),
                    last_normal_view: self.last_normal_view,
                    op_num: self.op_num,
                    commit_num: self.commit_num,
                    from: self.id,
                });
            }
        }
        // 3. New leader collects f+1 DoViewChange → pick the one with highest last_normal_view (tiebreak: highest op_num) → adopt its log
        pub fn on_do_view_change(&mut self, m: DoViewChange) -> Option<StartView> {
            self.do_view_change_msgs.insert(m.from, m);
            if self.do_view_change_msgs.len() < self.view.quorum() as usize { return None; }
            let best = self.do_view_change_msgs.values()
                .max_by_key(|m| (m.last_normal_view, m.op_num))
                .unwrap();
            self.log = best.log.clone();
            self.op_num = best.op_num;
            self.commit_num = self.do_view_change_msgs.values().map(|m| m.commit_num).max().unwrap();
            Some(StartView { view_num: self.view.view_num, log: self.log.clone(), op_num: self.op_num, commit_num: self.commit_num })
        }
        // 4. Backups receive StartView → adopt log, transition to Normal
        pub fn on_start_view(&mut self, m: StartView) {
            assert!(m.view_num >= self.view.view_num);
            self.log = m.log;
            self.op_num = m.op_num;
            self.commit_num = m.commit_num;
            self.status = ReplicaStatus::Normal;
            self.last_normal_view = m.view_num;
            // transition: into_normal()
        }
    }
    ```
    **Invariants**: (i) Log-merge rule: pick DoViewChange with highest `last_normal_view`; tiebreak `op_num`; tiebreak `from`. (ii) `commit_num` of new view ≥ max of all collected `commit_num`s — committed ops preserved. (iii) View-num is monotonic per replica — never bump backward. (iv) Status transitions are linear: Normal → ViewChange → Normal (no skipping).
  - **Build steps**: 1. (~25 min) Types + transport. 2. (~30 min) `start_view_change` + broadcast. 3. (~30 min) `on_start_view_change` quorum accumulation. 4. (~40 min) `on_do_view_change` log-merge logic — the hardest part. 5. (~30 min) `on_start_view` adoption + transition to Normal. 6. (~25 min) Wal persistence: `view_num` must be durably bumped *before* sending StartViewChange (else replica restart could re-vote in old view). 7. (~Tue Test.)
  - **Pitfalls** (named, 4):
    - *View-change livelock*: **Symptom**: all replicas restart simultaneously, each bumps view, none commits — no one is "Normal" long enough to make progress. **Fix**: exponential-backoff before triggering view change. Plus: replicas that observe a higher view from a peer jump to it immediately (catch-up). TigerBeetle calls this "view change skip".
    - *Log-merge wrong*: **Symptom**: chosen log lacks an op that was committed in a prior view → committed op lost = safety violation. **Fix**: the `last_normal_view` tiebreak is critical — replicas that didn't participate in the latest Normal view may have stale logs; their messages are dominated. Property test: any committed op in any prior view must survive in the merged log.
    - *View-num skip safety*: **Symptom**: replica receives DoViewChange for view+5, processes it without checking it's currently in view+5's ViewChange — picks merged log without quorum-protocol completion. **Fix**: DoViewChange handler verifies `self.view.view_num == m.view_num && self.status == ViewChange`. Out-of-view msgs trigger view-bump but don't directly mutate log.
    - *Primary flapping under partition*: **Symptom**: network flaps cause repeated view-changes; throughput collapses. **Fix**: stable-leader heuristic — backups give the current leader a grace period (`view_change_timeout` >> `prepare_timeout`) before suspecting; only escalate after sustained silence.
  - **Test scenarios** (Tue): (a) Kill primary at view 0, all 3 replicas converge to view 1 with same log prefix. (b) Kill primary mid-Prepare (some replicas have op N, some don't) → log-merge correctly chooses the one with op N. (c) Sequential primary-kills: kill v0 leader → view 1 leader → view 2 leader → cluster still has all committed ops. (d) All replicas restart simultaneously → exactly one becomes leader within bounded time (no livelock).
  - **Acceptance**: view-change completion < 100ms (3 replicas, loopback). Safety property: no committed op lost across 1k random partition/kill scenarios. Liveness property: view change completes within 5s under any single-fault scenario. Inheritance: time (timeouts), wal (durable view_num), p2p.
  - **Downstream**: W76 state_transfer.rs handles the case where a lagging replica's log can't be merged because it was offline for >1 view. ledger-deterministic relies on view-change for its leader-failover SLA. Interview: "walk me through VSR view change vs Raft leader election" — VSR is deterministic (round-trip), Raft is randomized (timeouts).

- [ ] [NEW v2] **Build**: `crates/matching-engine/src/stp.rs` — STP modes: CancelOldest (remove resting), CancelNewest
  (reject incoming), DecrementBoth (cancel min(qty)). Configurable per-account. (~3 hrs)
  - **Why**: Self-Trade Prevention stops an account from trading with itself, which would (a) incur unnecessary fees and (b) violate wash-trade rules at most regulated exchanges (FINRA Rule 5210, SEC Rule 17a-3). Every Tier-A exchange (CME, NYSE, Nasdaq, Binance Futures, dYdX) ships STP. Interview-load-bearing: candidates are asked to enumerate the 3+ modes and explain edge cases with partial fills.
  - **Read first**: CME Rulebook §526 "Trade Cancellation" + STP modes table. Nasdaq INET STP docs (CB/CN/CO mnemonics). Binance Futures "STP modes" API doc. QuickFIX/J's `quickfix.fix44.NewOrderSingle` `TradeRegulatoryAccounts(1666)` field carrying STP mode wire-side.
  - **Design**:
    ```rust
    #[derive(Clone, Copy, PartialEq, Eq, Debug)]
    pub enum StpMode {
        Disabled,
        CancelOldest,         // CO: remove the resting order, fill incoming against next
        CancelNewest,         // CN: reject incoming, leave resting
        DecrementBoth,        // DB: cancel min(resting.qty, incoming.qty) on both
        CancelBoth,           // CB: cancel resting fully + reject incoming
    }
    pub struct StpPolicy {
        pub mode: StpMode,
        // Optional: per-account override. Default applies if not in map.
        pub account_overrides: AHashMap<AccountId, StpMode>,
    }
    impl Engine {
        fn check_stp(&self, incoming: &Order, resting: &Order) -> StpAction {
            if incoming.account != resting.account { return StpAction::Trade; }
            let mode = self.stp_policy.for_account(incoming.account);
            match mode {
                StpMode::Disabled => StpAction::Trade,
                StpMode::CancelOldest => StpAction::CancelResting { resting_id: resting.id },
                StpMode::CancelNewest => StpAction::RejectIncoming { reason: "STP" },
                StpMode::DecrementBoth => {
                    let qty = incoming.remaining.min(resting.remaining);
                    StpAction::DecrementBoth { qty }
                }
                StpMode::CancelBoth => StpAction::CancelBothFully,
            }
        }
    }
    pub enum StpAction {
        Trade,                                          // no STP, proceed normally
        CancelResting { resting_id: OrderId },
        RejectIncoming { reason: &'static str },
        DecrementBoth { qty: u64 },
        CancelBothFully,
    }
    ```
    **Invariants**: (i) STP check runs *before* match-and-fill — never produces a trade between same-account orders. (ii) `DecrementBoth` qty is deterministic = `min(remaining)`, never produces a self-trade. (iii) STP modes are per-order (carried in order metadata) OR per-account (account override) — explicit precedence: order's mode > account override > exchange default. (iv) STP actions are part of the `MatchCommand` apply path; deterministic across replicas.
  - **Build steps**: 1. (~25 min) Types + StpPolicy with account overrides. 2. (~35 min) `check_stp` returning `StpAction`. 3. (~40 min) Wire into matching loop: before each price-level cross, call `check_stp`; act per result. 4. (~30 min) Handle partial fills: if incoming's first match is STP-rejected, try next resting; if all resting at that price level are same-account, drop to next price. 5. (~30 min) Iceberg interaction: STP applies to total qty, not just display (an iceberg's hidden portion is still "same account"). 6. (~20 min) Tests.
  - **Pitfalls** (named, 4):
    - *STP under partial fill*: **Symptom**: incoming partially fills against external order, then meets self-resting → STP triggers but state of incoming is mid-fill — `DecrementBoth` qty calc must use *current remaining*, not original. **Fix**: `incoming.remaining` recomputed at each step; STP action references current state. Test: 100-lot incoming, 30 lots fill external, then 40-lot self-resting + DecrementBoth → 40 cancelled on both, incoming has 30 remaining.
    - *STP under hidden iceberg*: **Symptom**: incoming meets visible 100-lot of own iceberg (whose hidden portion is 900 lots). DB cancels 100 of each; iceberg refreshes 100 more from hidden; cycle. **Fix**: STP examines the iceberg's TOTAL remaining (visible + hidden), not just display qty. Or: CO mode cancels the entire iceberg. Document the chosen semantics — CME does the former, Nasdaq the latter.
    - *Cross-leg STP for combo orders*: **Symptom**: pair-trade (buy leg A + sell leg B) where same account has resting in B → STP on B leg but A leg fills → orphaned position. **Fix**: combos check STP across all legs atomically; if any leg STP-rejects, whole combo rejected. Out of scope for v1.5 (single-leg only); document as W82+ TODO.
    - *STP-via-self-cross-aggregator*: **Symptom**: account uses two API keys (or two child accounts) to try to bypass STP. **Fix**: account hierarchy — STP groups can be configured per-master-account, all child accounts share the STP namespace. v1.5 ships only flat account_id; W82 documents this design extension.
  - **Test scenarios** (Thu): (a) Same account buy + sell, CO mode → resting cancelled, incoming fills next-best. (b) Same account, CN mode → incoming rejected, resting untouched. (c) Same account, DB 100+50 → both decrement 50; resting 0, incoming 50 → continue matching incoming. (d) Same account, CB mode → resting full-cancel, incoming reject. (e) Different accounts → Trade as normal. (f) Iceberg hidden interaction (per chosen semantics). (g) Replicated determinism: same event stream → same outcomes across 3 raft replicas.
  - **Acceptance**: <50ns STP check on hot path (single lookup). Property test: 10k random orders with mixed accounts, no same-account trade produced. Inheritance: AHashMap (account overrides), bufpool. Cross-replica determinism via raft test.
  - **Downstream**: W76 iceberg.rs interacts with STP (decision: CME-style, exposing total). W80 FIX 4.4 session reads STP mode from tag 7928 (CME STP code) on incoming orders. W82 matching v1.5 SHIP audit confirms STP is in the inheritance audit (uses Engine + raft replication). Interview answer: "STP has 3-4 industry-standard modes; modes are configured per-account or per-order; partial fills and iceberg interactions are the edge cases."
