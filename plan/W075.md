  #### Phase 1 — Problem, requirements, design (~80 min, no code yet)

  - **The problem this primitive solves**: a primary failure cannot be left to "best-effort" recovery — committed ops MUST survive the leader transition or the entire ledger is a lie. Naive leader-election (vote for whoever asks first) loses committed ops the instant the previous leader's log was acknowledged by f+1 replicas but only one of them participates in the next view. ViewChange's quorum-collection + log-merge rule is the load-bearing safety mechanism.

  - **Requirements** — write in `crates/consensus-vsr/notes/75_view_change_design.md`:
    - R1. `start_view_change(new_view)` is monotonic — never re-enters a view-num ≤ current.
    - R2. A replica accepts `DoViewChange` only when `status == ViewChange && view_num == m.view_num` — out-of-view msgs trigger a view-bump but never directly mutate log.
    - R3. The log-merge rule on the new leader picks the DoViewChange with the **highest `last_normal_view`**; tiebreak: highest `op_num`; tiebreak: lowest `from` id (deterministic).
    - R4. `commit_num` of the new view ≥ max of all collected `commit_num`s — committed ops MUST be preserved.
    - R5. View-num must be durably persisted (wal-flushed) **before** sending StartViewChange — else a restart could re-vote in the old view.
    - R6. Status transitions are linear: `Normal → ViewChange → Normal`. No skipping; no parallel ViewChange instances.
    - R7. View-change completion ≤100 ms (3 replicas, loopback); cluster survives any single-fault scenario within 5 s (liveness).
    - R8. No committed op lost across 1000 random partition/kill scenarios (safety property test).

  #### Phase 3 — Make the tests pass, one failure at a time (~140 min)

  - **When `log_merge_picks_highest_last_normal_view` reports the wrong replica's log was chosen:**
    - Symptom: test asserts merged log == R1's (last_normal_view=5, op_num=100); actual merged log == R2's (last_normal_view=4, op_num=200) — picked because R2 had MORE ops.
    - Why: a naive log-merge rule `max_by_key(|m| m.op_num)` chooses the longest log. But R2's longer log was built in an OLDER Normal view (4) — R2 missed the view-5 Normal phase where op_num=100 was *committed*. Picking R2's log loses that committed op (safety violation).
    - Fix: rule is `max_by_key(|m| (m.last_normal_view, m.op_num))` — primary sort by `last_normal_view`, only tiebreak by `op_num` WITHIN the same Normal view. Tiebreak again by `from` id for determinism.
    - Muscle: in any quorum-based log merge, the participants that were in the most-recent Normal view dominate; messages from replicas with stale `last_normal_view` are subordinate even if their logs are longer. Reapplies at: W76 state_transfer (when to ship snapshot vs log-suffix), W87 VOPR safety-property generator, W90+ ledger-deterministic leader transition.

  - **When `do_view_change_rejected_when_status_normal` reports the log got mutated:**
    - Symptom: replica was `Normal`; received `DoViewChange { view_num: 0 }`; log changed.
    - Why: handler didn't gate on `status == ViewChange && view_num == m.view_num`. DoViewChange handling assumes the receiver has already broadcast StartViewChange and collected quorum — without that protocol context, applying the message is a quorum-bypass.
    - Fix: `on_do_view_change` first check: `if self.status != ViewChange || self.view.view_num != m.view_num { handle_out_of_view(m); return; }`. Out-of-view DoViewChange triggers a view-bump (R1) but does NOT touch the log.
    - Muscle: every message handler in a quorum protocol must validate the recipient's current phase matches the message's expected phase. Reapplies at: W76 state_transfer (snapshot only valid in Normal), W87 VOPR fuzzer (drive messages into wrong phases as a coverage strategy).

  - **When `view_num_durably_persisted_before_send` reports the broadcast preceded the flush:**
    - Symptom: wal trace shows `[flush_to_disk(view=1)]` *after* the `[send(StartViewChange{view=1})]` to peers.
    - Why: the bump-and-send is implemented as `self.view.view_num += 1; self.broadcast(...)` without an awaited flush in between. On a crash between send and flush, the replica restarts in view 0 — and a peer that received the StartViewChange may have already advanced to view 1; replica re-votes incorrectly.
    - Fix: `self.view.view_num += 1; self.wal.flush_view_num(self.view.view_num).await; self.broadcast(...);`. The flush is on the critical path; the broadcast is gated on the flush completing.
    - Muscle: any externally-observable state change in a consensus protocol must be durable *before* it goes on the wire. Reapplies at: W76 commit_num durability, W80 ledger journal entry, W89 ledger v1.0 io_uring fsync ordering.

  - **When `livelock_resolved_under_simultaneous_restart` deadlocks (no leader within 5 s):**
    - Symptom: all 3 replicas perpetually bump view; logs show `view 1 → 2 → 3 → 4...` on all of them; no one stays in Normal long enough to commit anything.
    - Why: every replica's `start_view_change` triggers a `start_view_change_timeout` on peers; peers respond by bumping their own view; cycle.
    - Fix: (a) randomized exponential backoff on view-change trigger (each replica waits `base_timeout × 2^attempt + jitter(0..base_timeout)`); (b) "view-change skip" — a replica observing a peer's view > its current view jumps directly to that view without participating in the lower views (collapses concurrent attempts into one); (c) stable-leader heuristic — backups give the current leader `view_change_timeout >> prepare_timeout` (e.g. 5× longer) before suspecting.
    - Muscle: every quorum-based protocol with a "leader-suspect" trigger needs randomized backoff AND a view-skip rule, or simultaneous suspicion turns into livelock. Reapplies at: W76 state_transfer concurrent requests, W87 VOPR partition-storm scenarios, W90+ ledger live-cluster ops.

  - **When `no_committed_op_lost_under_random_partitions` finds a counterexample:**
    - Symptom: scenario seed=42, action sequence `[partition(R1), kill(R2), restart(R3), unpartition(R1), kill(R3)]` ends with op N=87 missing from R1 and R3 despite being committed at view 5 by R2 before death.
    - Why: probably one of: (a) commit_num tiebreak rule missed a path (the bug is in `max` over commit_nums); (b) wal-flush ordering let a replica restart with stale view_num; (c) log-merge rule under simultaneous DoViewChange + StartView arrival isn't atomic.
    - Fix: capture the seed; replay deterministically; bisect by adding state-dump after each action; identify which invariant breaks. Three likely candidates — fix as in the cards above. If the bug is novel, document and add to the property-test suite as a regression.
    - Muscle: property tests find the bugs your hand-written tests miss; treat any property-test failure as the spec being incomplete, not the test being wrong. Reapplies at: W87 VOPR fuzzer (this is exactly the same testing discipline at scale), W92 ledger v1.0 SHIP audit.

  - **5-year failure mode** (write in `notes/75_view_change_followup.md` after green): when generalized consensus (Heidi Howard's flexible Paxos / Egalitarian Paxos) becomes mature in Rust, the VSR-specific log-merge rule generalizes to "quorum intersection over an arbitrary quorum-system." Migration: extract the log-merge as a trait `QuorumMerge`, keep VSR as one implementation, add EPaxos as another. Trigger: a workload where VSR's strict primary makes per-shard throughput a bottleneck.

  - **Design**:
    ```rust
    pub struct ViewChangeReplica {
        pub id: ReplicaId,
        pub view: View,                       // the NEW view-num we're targeting
        pub status: ReplicaStatus,            // == ViewChange
        pub last_normal_view: ViewNum,        // highest view-num we were in Normal status
        pub log: Log,                          // carry over from Normal
        pub op_num: u64,
        pub commit_num: u64,
        pub start_view_change_acks: BitSet,   // replicas that have started VC
        pub do_view_change_msgs: AHashMap<ReplicaId, DoViewChange>,  // collected by new leader
    }
    pub struct StartViewChange {
        pub view_num: ViewNum,
        pub from: ReplicaId,
    }
    pub struct DoViewChange {
        pub view_num: ViewNum,
        pub log: Log,                         // full log of sender
        pub last_normal_view: ViewNum,
        pub op_num: u64,
        pub commit_num: u64,
        pub from: ReplicaId,
    }
    pub struct StartView {
        pub view_num: ViewNum,
        pub log: Log,                         // merged log chosen by new leader
        pub op_num: u64,
        pub commit_num: u64,
    }
    impl ViewChangeReplica {
        // 1. Any replica suspects primary dead → bump view, send StartViewChange to all
        pub fn start_view_change(&mut self, new_view: ViewNum) {
            assert!(new_view > self.view.view_num);
            self.view.view_num = new_view;
            self.status = ReplicaStatus::ViewChange;
            self.broadcast(StartViewChange { view_num: new_view, from: self.id });
        }
        // 2. Collect f+1 StartViewChange acks → send DoViewChange to NEW leader
        pub fn on_start_view_change(&mut self, m: StartViewChange) {
            if m.view_num < self.view.view_num { return; }
            if m.view_num > self.view.view_num { self.start_view_change(m.view_num); }
            self.start_view_change_acks.insert(m.from as usize);
            if self.start_view_change_acks.count_ones() as u8 >= self.view.quorum() {
                let new_leader = self.view.leader();
                self.send_to(new_leader, DoViewChange {
                    view_num: self.view.view_num,
                    log: self.log.clone(),
                    last_normal_view: self.last_normal_view,
                    op_num: self.op_num,
                    commit_num: self.commit_num,
                    from: self.id,
                });
            }
        }
        // 3. New leader collects f+1 DoViewChange → pick the one with highest last_normal_view (tiebreak: highest op_num) → adopt its log
        pub fn on_do_view_change(&mut self, m: DoViewChange) -> Option<StartView> {
            self.do_view_change_msgs.insert(m.from, m);
            if self.do_view_change_msgs.len() < self.view.quorum() as usize { return None; }
            let best = self.do_view_change_msgs.values()
                .max_by_key(|m| (m.last_normal_view, m.op_num))
                .unwrap();
            self.log = best.log.clone();
            self.op_num = best.op_num;
            self.commit_num = self.do_view_change_msgs.values().map(|m| m.commit_num).max().unwrap();
            Some(StartView { view_num: self.view.view_num, log: self.log.clone(), op_num: self.op_num, commit_num: self.commit_num })
        }
        // 4. Backups receive StartView → adopt log, transition to Normal
        pub fn on_start_view(&mut self, m: StartView) {
            assert!(m.view_num >= self.view.view_num);
            self.log = m.log;
            self.op_num = m.op_num;
            self.commit_num = m.commit_num;
            self.status = ReplicaStatus::Normal;
            self.last_normal_view = m.view_num;
            // transition: into_normal()
        }
    }
    ```
    **Invariants**: (i) Log-merge rule: pick DoViewChange with highest `last_normal_view`; tiebreak `op_num`; tiebreak `from`. (ii) `commit_num` of new view ≥ max of all collected `commit_num`s — committed ops preserved. (iii) View-num is monotonic per replica — never bump backward. (iv) Status transitions are linear: Normal → ViewChange → Normal (no skipping).
  - **Build steps**: 1. (~25 min) Types + transport. 2. (~30 min) `start_view_change` + broadcast. 3. (~30 min) `on_start_view_change` quorum accumulation. 4. (~40 min) `on_do_view_change` log-merge logic — the hardest part. 5. (~30 min) `on_start_view` adoption + transition to Normal. 6. (~25 min) Wal persistence: `view_num` must be durably bumped *before* sending StartViewChange (else replica restart could re-vote in old view). 7. (~Tue Test.)
  - **Pitfalls** (named, 4):
    - *View-change livelock*: **Symptom**: all replicas restart simultaneously, each bumps view, none commits — no one is "Normal" long enough to make progress. **Fix**: exponential-backoff before triggering view change. Plus: replicas that observe a higher view from a peer jump to it immediately (catch-up). TigerBeetle calls this "view change skip".
    - *Log-merge wrong*: **Symptom**: chosen log lacks an op that was committed in a prior view → committed op lost = safety violation. **Fix**: the `last_normal_view` tiebreak is critical — replicas that didn't participate in the latest Normal view may have stale logs; their messages are dominated. Property test: any committed op in any prior view must survive in the merged log.
    - *View-num skip safety*: **Symptom**: replica receives DoViewChange for view+5, processes it without checking it's currently in view+5's ViewChange — picks merged log without quorum-protocol completion. **Fix**: DoViewChange handler verifies `self.view.view_num == m.view_num && self.status == ViewChange`. Out-of-view msgs trigger view-bump but don't directly mutate log.
    - *Primary flapping under partition*: **Symptom**: network flaps cause repeated view-changes; throughput collapses. **Fix**: stable-leader heuristic — backups give the current leader a grace period (`view_change_timeout` >> `prepare_timeout`) before suspecting; only escalate after sustained silence.
  - **Test scenarios** (Tue): (a) Kill primary at view 0, all 3 replicas converge to view 1 with same log prefix. (b) Kill primary mid-Prepare (some replicas have op N, some don't) → log-merge correctly chooses the one with op N. (c) Sequential primary-kills: kill v0 leader → view 1 leader → view 2 leader → cluster still has all committed ops. (d) All replicas restart simultaneously → exactly one becomes leader within bounded time (no livelock).
  - **Acceptance**: view-change completion < 100ms (3 replicas, loopback). Safety property: no committed op lost across 1k random partition/kill scenarios. Liveness property: view change completes within 5s under any single-fault scenario. Inheritance: time (timeouts), wal (durable view_num), p2p.
  - **Downstream**: W76 state_transfer.rs handles the case where a lagging replica's log can't be merged because it was offline for >1 view. ledger-deterministic relies on view-change for its leader-failover SLA. Interview: "walk me through VSR view change vs Raft leader election" — VSR is deterministic (round-trip), Raft is randomized (timeouts).

    - Symptom: incoming had 100 original, 30 filled, 70 remaining; DB met 40-lot resting; expected `incoming.remaining = 70 - 40 = 30`; actual `incoming.remaining = 100 - 40 = 60` (used original).
    - Why: `check_stp` was passed the `Order` struct's `original_qty` field instead of computing `remaining` from the current match-loop state. Partial fills accumulate in a separate `filled` counter; `remaining = original - filled`, and STP must use `remaining`.
    - Fix: STP signature is `check_stp(incoming_remaining: u64, resting_remaining: u64, incoming_acct, resting_acct, policy)` — explicit params, no struct hiding stale state. The match-loop computes `incoming.original_qty - incoming.filled` at each cross attempt.
    - Muscle: any rule that depends on "current state" of a mid-flight order must read the state explicitly, never trust a struct field that was snapshot at order entry. Reapplies at: W76 iceberg refresh qty calc, W77 stop trigger qty (uses current_qty), W80 ledger transfer (current balance, not original).

  - **When `stp_replicated_determinism_3replica` reports replica 2 produced different fills than replicas 1 and 3:**
    - Symptom: same input event stream, replica 2's `account_overrides` was rebuilt during a config-reload; HashMap iteration order changed; an account-mode lookup that does `policy.account_overrides.iter().find(...)` returned a different first match.
    - Why: AHashMap's iteration order depends on insertion sequence + hash seed. Two replicas with identical state can have different iteration orders if they were built differently (e.g., one from snapshot, one from log replay).
    - Fix: STP lookup is `policy.account_overrides.get(&account_id)` — direct keyed lookup, no iteration. If iteration is needed (config dump), sort first. CI lint: `disallowed-methods` for `HashMap::iter()` in deterministic modules.
    - Muscle: deterministic state machines never iterate hash-based collections; lookups are by-key. Reapplies at: W80 ledger state_machine, W82 v1.5 SHIP audit, W87 VOPR cross-machine reproducibility.

  - **When `stp_check_under_50ns_hot_path` reports 180 ns/op:**
    - Symptom: bench reports 180 ns/call (~4× over budget); flame graph shows `AHashMap::get` taking 150 ns under cold cache (~3 cache misses + hash compute).
    - Why: `account_overrides: AHashMap<AccountId, StpMode>` — fine for cold path, but on the hot match loop each lookup pays hash + bucket walk; under cold cache (account_id never seen recently), 3 misses × ~50 ns = 150 ns.
    - Fix: intern AccountId as `u16` (perfect-hash from account registration time); store overrides in `[Option<StpMode>; MAX_ACCOUNTS]` — direct array index, ~1 ns L1 load. The W74 matching-engine already has symbol interning via this exact pattern; reuse the AccountId table.
    - Cost avoided: ~150 ns × 1M orders/sec = ~150 ms/sec; restores cache residency on the override table.
    - Muscle: small fixed key spaces are array-indexed, not hashmap-indexed. Reapplies at: W76 iceberg account lookup, W79 MBO subscriber registry, W80 ledger account lookup, W82 v1.5 SHIP audit (asserts no AHashMap in per-event path).

  - **When `stp_iceberg_cme_style_total_check` reports only visible 100 affected (not 1000):**
    - Symptom: configured for CME-style (total-based STP) but iceberg's hidden 900 not touched.
    - Why: STP receives `resting.display_remaining` (visible-only) from the price-level iterator. The match loop is iterating the *display layer*; the hidden portion lives in a sidecar (W76 iceberg state).
    - Fix: when `policy.iceberg_mode == TotalBased`, STP looks up `iceberg_state.get(resting.id).map(|i| i.total_remaining).unwrap_or(resting.display_remaining)`. Document the lookup as a per-event cost (~30 ns AHashMap hit OR ~1 ns array hit if iceberg-id is interned).
    - Muscle: STP semantics for icebergs are venue-specific; the policy flag must thread all the way to the qty source. Reapplies at: W76 iceberg.rs (the symmetric side — iceberg's match-loop interaction), W79 MBO publish (hidden never leaks).

  - **When `stp_property_no_self_trade_in_10k_random` finds a same-account trade:**
    - Symptom: proptest seed=… produces a trade with `taker.account == maker.account`; the case is some multi-leg edge (combo order, or a partial fill that re-enters the book via re-queue).
    - Why: STP check was at the top of `check_stp` only; if the match loop re-enters with a refreshed iceberg or a re-queued partial, the second entry skipped the check.
    - Fix: STP check is the FIRST step of every match attempt (`fn try_match(incoming, resting) -> StpAction → MatchAction`); not at the top of the outer loop, but at the top of every per-cross iteration. Add a defense-in-depth `debug_assert!(trade.taker_account != trade.maker_account)` on every produced trade.
    - Muscle: a "must never happen" property is enforced at the boundary where it could happen, not at the start of the outer call. Reapplies at: W77 stop trigger (every per-trigger check), W80 ledger transfer (assert ledger-id match at write site, not entry).

  - **5-year failure mode** (write in `notes/75_stp_followup.md` after green): when account hierarchies (master + child accounts) become first-class, STP groups need to span sibling accounts. Migration: `StpGroupId` lookup replaces direct account-id compare; one indirection. Trigger: a customer requests prevention across two API keys they own.

  - **Design**:
    ```rust
    #[derive(Clone, Copy, PartialEq, Eq, Debug)]
    pub enum StpMode {
        Disabled,
        CancelOldest,         // CO: remove the resting order, fill incoming against next
        CancelNewest,         // CN: reject incoming, leave resting
        DecrementBoth,        // DB: cancel min(resting.qty, incoming.qty) on both
        CancelBoth,           // CB: cancel resting fully + reject incoming
    }
    pub struct StpPolicy {
        pub mode: StpMode,
        // Optional: per-account override. Default applies if not in map.
        pub account_overrides: AHashMap<AccountId, StpMode>,
    }
    impl Engine {
        fn check_stp(&self, incoming: &Order, resting: &Order) -> StpAction {
            if incoming.account != resting.account { return StpAction::Trade; }
            let mode = self.stp_policy.for_account(incoming.account);
            match mode {
                StpMode::Disabled => StpAction::Trade,
                StpMode::CancelOldest => StpAction::CancelResting { resting_id: resting.id },
                StpMode::CancelNewest => StpAction::RejectIncoming { reason: "STP" },
                StpMode::DecrementBoth => {
                    let qty = incoming.remaining.min(resting.remaining);
                    StpAction::DecrementBoth { qty }
                }
                StpMode::CancelBoth => StpAction::CancelBothFully,
            }
        }
    }
    pub enum StpAction {
        Trade,                                          // no STP, proceed normally
        CancelResting { resting_id: OrderId },
        RejectIncoming { reason: &'static str },
        DecrementBoth { qty: u64 },
        CancelBothFully,
    }
    ```
    **Invariants**: (i) STP check runs *before* match-and-fill — never produces a trade between same-account orders. (ii) `DecrementBoth` qty is deterministic = `min(remaining)`, never produces a self-trade. (iii) STP modes are per-order (carried in order metadata) OR per-account (account override) — explicit precedence: order's mode > account override > exchange default. (iv) STP actions are part of the `MatchCommand` apply path; deterministic across replicas.
  - **Build steps**: 1. (~25 min) Types + StpPolicy with account overrides. 2. (~35 min) `check_stp` returning `StpAction`. 3. (~40 min) Wire into matching loop: before each price-level cross, call `check_stp`; act per result. 4. (~30 min) Handle partial fills: if incoming's first match is STP-rejected, try next resting; if all resting at that price level are same-account, drop to next price. 5. (~30 min) Iceberg interaction: STP applies to total qty, not just display (an iceberg's hidden portion is still "same account"). 6. (~20 min) Tests.
  - **Pitfalls** (named, 4):
    - *STP under partial fill*: **Symptom**: incoming partially fills against external order, then meets self-resting → STP triggers but state of incoming is mid-fill — `DecrementBoth` qty calc must use *current remaining*, not original. **Fix**: `incoming.remaining` recomputed at each step; STP action references current state. Test: 100-lot incoming, 30 lots fill external, then 40-lot self-resting + DecrementBoth → 40 cancelled on both, incoming has 30 remaining.
    - *STP under hidden iceberg*: **Symptom**: incoming meets visible 100-lot of own iceberg (whose hidden portion is 900 lots). DB cancels 100 of each; iceberg refreshes 100 more from hidden; cycle. **Fix**: STP examines the iceberg's TOTAL remaining (visible + hidden), not just display qty. Or: CO mode cancels the entire iceberg. Document the chosen semantics — CME does the former, Nasdaq the latter.
    - *Cross-leg STP for combo orders*: **Symptom**: pair-trade (buy leg A + sell leg B) where same account has resting in B → STP on B leg but A leg fills → orphaned position. **Fix**: combos check STP across all legs atomically; if any leg STP-rejects, whole combo rejected. Out of scope for v1.5 (single-leg only); document as W82+ TODO.
    - *STP-via-self-cross-aggregator*: **Symptom**: account uses two API keys (or two child accounts) to try to bypass STP. **Fix**: account hierarchy — STP groups can be configured per-master-account, all child accounts share the STP namespace. v1.5 ships only flat account_id; W82 documents this design extension.
  - **Test scenarios** (Thu): (a) Same account buy + sell, CO mode → resting cancelled, incoming fills next-best. (b) Same account, CN mode → incoming rejected, resting untouched. (c) Same account, DB 100+50 → both decrement 50; resting 0, incoming 50 → continue matching incoming. (d) Same account, CB mode → resting full-cancel, incoming reject. (e) Different accounts → Trade as normal. (f) Iceberg hidden interaction (per chosen semantics). (g) Replicated determinism: same event stream → same outcomes across 3 raft replicas.
  - **Acceptance**: <50ns STP check on hot path (single lookup). Property test: 10k random orders with mixed accounts, no same-account trade produced. Inheritance: AHashMap (account overrides), bufpool. Cross-replica determinism via raft test.
