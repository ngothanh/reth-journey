  - *Mental model*: ViewChange is VSR's leader-election + log-reconciliation protocol. Unlike Raft (randomized timeouts, vote-for-newest-term), VSR is deterministic round-trip: every replica that participated in the most-recent Normal view contributes its log; the new leader picks the *most-recent-Normal* log, not the *longest* log. That single distinction is the safety mechanism. **v3**: it is also the protocol under which `SettlementId` identity must survive — op-numbers are interpreted relative to their `snapshot_epoch` (§4A), so a view-change must never renumber a committed op out from under a client holding its id.
  - *Contract* (signature-level only — never the body):
    ```rust
    pub fn start_view_change(&mut self, new_view: ViewNum);            // monotone bump + broadcast
    pub fn on_start_view_change(&mut self, m: StartViewChange);        // accumulate acks, send DoViewChange at quorum
    pub fn on_do_view_change(&mut self, m: DoViewChange) -> Option<StartView>; // new leader merges at quorum
    pub fn on_start_view(&mut self, m: StartView);                     // backups adopt merged log → Normal
    // Quorum = f+1 of 2f+1. For 3 replicas (f=1), quorum = 2.
    ```
  - *Back-of-envelope* (bar (c)): target view-change completion ≤100 ms (R7). The protocol is one logical round-trip: StartViewChange broadcast → f+1 DoViewChange → StartView. On loopback, network is ~1–5 µs/hop; the dominant cost is the **wal fsync of `view_num`** before the StartViewChange goes on the wire — a real `fdatasync` is ~300 µs–10 ms on commodity SSD (syscall 300 ns + device flush). So the 100 ms budget is fsync-bound, not CPU-bound: two fsyncs (view-bump on the suspector, merged-log durable on the new leader) dominate. Cliff: if you skip the fsync to "go fast" you trade ~1 ms latency for a committed-op loss on the next crash — a bar-(c) **correctness** violation. **v3 cost translation**: that "committed op" is a settled trade; the loss is real customer funds discrepancy on failover.
  - **Requirements** R1..R9 — write in `crates/consensus-vsr/notes/75_view_change_design.md`:
    - R1. `start_view_change(new_view)` is monotonic — never re-enters a view-num ≤ current.
    - R2. A replica accepts `DoViewChange` only when `status == ViewChange && view_num == m.view_num` — out-of-view msgs trigger a view-bump but never directly mutate log.
    - R3. The log-merge rule picks the `DoViewChange` with the **highest `last_normal_view`**; tiebreak: highest `op_num`; tiebreak: lowest `from` id (deterministic).
    - R4. `commit_num` of the new view ≥ max of all collected `commit_num`s — committed ops MUST be preserved.
    - R5. `view_num` is durably wal-flushed **before** sending StartViewChange — else a restart re-votes in the old view.
    - R6. Status transitions are linear: `Normal → ViewChange → Normal`. No skipping; no parallel ViewChange instances.
    - R7. View-change completion ≤100 ms (3 replicas, loopback); cluster survives any single fault within 5 s (liveness).
    - R8. No committed op lost across 1000 seeded random partition/kill scenarios (safety property).
    - R9. **v3 — op-number stability across view-change**: an `op_num` that was committed before the view-change occupies the same `(snapshot_epoch, op_num)` coordinate after the merged `StartView` is adopted. The merge re-orders/extends *uncommitted* suffixes only; the committed prefix is never renumbered. (This is what makes `SettlementId` survival free — §4A.)

  #### Phase 3 — Make the tests pass, one failure at a time (~140 min)

  Newbie failures first, expert last — the ladder you actually walk. Read each card *after* you see the failure.

  - **(NEWBIE) When `do_view_change_rejected_when_status_normal` reports the log got mutated:**
    - Symptom: replica was `Normal`; received `DoViewChange{view_num:0}`; `r.log != before`.
    - Why: the handler didn't gate on `status == ViewChange && view_num == m.view_num`. DoViewChange assumes the receiver already broadcast StartViewChange and reached quorum; applying it without that context is a quorum-bypass.
    - Fix: first line of `on_do_view_change`: `if self.status != ViewChange || self.view.view_num != m.view_num { self.handle_out_of_view(&m); return None; }` — out-of-view triggers a view-bump (R1) but never touches the log.
    - Cost avoided: a silent safety violation (committed-op divergence) that no latency metric would catch — green `cargo test` on the happy path, RED only under partition. **(bar (c) violation.)** In venue terms: a settlement op committed on one replica diverges from the cluster.
    - Muscle: every handler in a quorum protocol must validate the recipient's current phase matches the message's expected phase. Reapplies at: W76 state_transfer (snapshot only valid in Normal), W90 consensus-vsr v1.0, W103+ perp-dex-core cluster-VOPR (driving messages into wrong phases is a coverage strategy).

  - **(NEWBIE) When `view_num_strictly_monotonic` lets the view go backward:**
    - Symptom: after `start_view_change(5); start_view_change(3)`, `view_num == 3`.
    - Why: `start_view_change` assigned `self.view.view_num = new_view` unconditionally.

    - Cost avoided: re-entering an abandoned view re-collects stale DoViewChange messages → can resurrect a superseded log.
    - Muscle: every monotone counter in a protocol guards its own bump. Reapplies at: W76 op_num monotonicity, W80 oracle-mark mark-sequence numbers, W90 consensus-vsr commit_num.
