  - 🎯 **Pre-prediction prompt (do this BEFORE reading Phase 2)** — write sealed answers in `crates/consensus-vsr/notes/75_view_change_prediction.md`; compare to reality after tests run:

    - P5. List every Phase-2 test name you predict your first attempt will fail. The delta to reality is the lesson.
  - *Mental model*: ViewChange is VSR's leader-election + log-reconciliation protocol. Unlike Raft (randomized timeouts, vote-for-newest-term), VSR is deterministic round-trip: every replica that participated in the most-recent Normal view contributes its log; the new leader picks the *most-recent-Normal* log, not the *longest* log. That single distinction is the safety mechanism. Used by ledger-deterministic for leader failover.
  - *Contract* (signature-level only — never the body):
    ```rust
    pub fn start_view_change(&mut self, new_view: ViewNum);            // monotone bump + broadcast
    pub fn on_start_view_change(&mut self, m: StartViewChange);        // accumulate acks, send DoViewChange at quorum
    pub fn on_do_view_change(&mut self, m: DoViewChange) -> Option<StartView>; // new leader merges at quorum
    pub fn on_start_view(&mut self, m: StartView);                     // backups adopt merged log → Normal
    // Quorum = f+1 of 2f+1. For 3 replicas (f=1), quorum = 2.
    ```
  - *Back-of-envelope* (bar (c)): target view-change completion ≤100 ms (R7). The protocol is one logical round-trip: StartViewChange broadcast → f+1 DoViewChange → StartView. On loopback, network is ~1-5 µs/hop; the dominant cost is the **wal fsync of `view_num`** before the StartViewChange goes on the wire — a real `fdatasync` is ~300 µs–10 ms on commodity SSD (syscall 300 ns + device flush). So the 100 ms budget is fsync-bound, not CPU-bound: two fsyncs (view-bump on the suspector, merged-log durable on the new leader) dominate. Cliff: if you skip the fsync to "go fast" you trade ~1 ms latency for a committed-op loss on the next crash — a bar-(c) **correctness** violation, not a perf one.
  - **Requirements** R1..R8 — write in `crates/consensus-vsr/notes/75_view_change_design.md`:
    - R1. `start_view_change(new_view)` is monotonic — never re-enters a view-num ≤ current.
    - R2. A replica accepts `DoViewChange` only when `status == ViewChange && view_num == m.view_num` — out-of-view msgs trigger a view-bump but never directly mutate log.
    - R3. The log-merge rule picks the `DoViewChange` with the **highest `last_normal_view`**; tiebreak: highest `op_num`; tiebreak: lowest `from` id (deterministic).
    - R4. `commit_num` of the new view ≥ max of all collected `commit_num`s — committed ops MUST be preserved.
    - R5. `view_num` is durably wal-flushed **before** sending StartViewChange — else a restart re-votes in the old view.
    - R6. Status transitions are linear: `Normal → ViewChange → Normal`. No skipping; no parallel ViewChange instances.
    - R7. View-change completion ≤100 ms (3 replicas, loopback); cluster survives any single fault within 5 s (liveness).
    - R8. No committed op lost across 1000 seeded random partition/kill scenarios (safety property).

Candidates: `Vec<DoViewChange>`, `AHashMap<ReplicaId, DoViewChange>`, `BTreeMap<ReplicaId, DoViewChange>`, `[Option<DoViewChange>; N]` indexed by replica id, `BitSet` for acks.
    - D3. **Dx Pre-mortem #1 (log-merge, load-bearing):** write the EXACT 5-line interleaving where merging by "highest `op_num`" instead of "highest `last_normal_view`" loses a committed op.     - D4. **Pre-mortem #2 (view-num skip):** write the trace where `DoViewChange{view=7}` arrives at a replica still in view 2 with `status=Normal`, and naive `self.view=7; self.log=m.log` bypasses quorum. Why is "set view, install log" wrong here?

  #### Phase 3 — Make the tests pass, one failure at a time (~140 min)

  Newbie failures first, expert last — the ladder you actually walk. Read each card *after* you see the failure.

  - **(NEWBIE) When `do_view_change_rejected_when_status_normal` reports the log got mutated:**
    - Symptom: replica was `Normal`; received `DoViewChange{view_num:0}`; `r.log != before`.
    - Why: the handler didn't gate on `status == ViewChange && view_num == m.view_num`. DoViewChange assumes the receiver already broadcast StartViewChange and reached quorum; applying it without that context is a quorum-bypass.
    - Fix: first line of `on_do_view_change`: `if self.status != ViewChange || self.view.view_num != m.view_num { self.handle_out_of_view(&m); return None; }` — out-of-view triggers a view-bump (R1) but never touches the log.
    - Cost avoided: a silent safety violation (committed-op divergence) that no latency metric would catch — green `cargo test` on the happy path, RED only under partition. **(bar (c) violation.)**
    - Muscle: every handler in a quorum protocol must validate the recipient's current phase matches the message's expected phase. Reapplies at: W76 state_transfer (snapshot only valid in Normal), W87 VOPR fuzzer (driving messages into wrong phases is a coverage strategy), W90 consensus-vsr v1.0.

  - **(NEWBIE) When `view_num_strictly_monotonic` lets the view go backward:**
    - Symptom: after `start_view_change(5); start_view_change(3)`, `view_num == 3`.
    - Why: `start_view_change` assigned `self.view.view_num = new_view` unconditionally.
    - Fix: guard `if new_view <= self.view.view_num { return; }` (or `assert!` in debug + early-return in release).
    - Cost avoided: re-entering an abandoned view re-collects stale DoViewChange messages → can resurrect a superseded log.
    - Muscle: every monotone counter in a protocol guards its own bump. Reapplies at: W76 op_num monotonicity, W90 consensus-vsr commit_num, W80 ledger sequence numbers.

  - **(SENIOR) When `log_merge_picks_highest_last_normal_view` picks the wrong replica's log:**
    - Symptom: test expects merged `op_num == 100` (R1, `last_normal_view=5`); actual `200` (R2, `last_normal_view=4`) — chosen because R2 had MORE ops.
    - Why: naive `max_by_key(|m| m.op_num)` picks the longest log. But R2's longer log was built in an OLDER Normal view (4); R2 missed view 5 where op 100 was *committed*. Picking R2 loses that committed op (safety violation). (A "keep-first-DVC" impl is also wrong and now caught — R2 arrives first in the test but must lose.)
    - Fix: `max_by_key(|m| (m.last_normal_view, m.op_num, std::cmp::Reverse(m.from)))` — primary sort on `last_normal_view`, tiebreak `op_num` only within the same Normal view, then `from` id for determinism.
    - Cost avoided: a committed op silently dropped on every leader transition — the canonical "ledger is a lie" bug. **(bar (c) violation.)**
    - Muscle: in any quorum-based log merge, participants from the most-recent Normal view dominate; stale-`last_normal_view` logs are subordinate even when longer. Reapplies at: W76 state_transfer (ship snapshot vs log-suffix), W87 VOPR safety generator, W90+ ledger-deterministic leader transition.

  - **(SENIOR) When `commit_num_preserved_across_view_change` drops below 42:**
    - Symptom: merged `commit_num` equals the *new leader's* commit_num (say 80), not the cluster max (100).
    - Why: commit_num was copied from the winning DoViewChange's `commit_num` instead of `max` over all collected.
    - Fix: `self.commit_num = self.do_view_change_msgs.values().map(|m| m.commit_num).max().unwrap();` — independent of which log won the merge.
    - Cost avoided: a committed-and-acknowledged op falls back to "uncommitted" → a client that saw an ack loses durability. **(bar (c) violation.)**
    - Muscle: log-suffix selection and commit-point selection are two separate `max`es. Reapplies at: W76 state_transfer, W90 consensus-vsr v1.0 audit.

  - **(EXPERT) When `view_num_durably_persisted_before_send` reports broadcast preceded the flush:**
    - Symptom: trace shows `Send(1)` at index < `FlushView(1)`.
    - Why: `self.view.view_num += 1; self.broadcast(...)` has no awaited flush between. On a crash in that window, the replica restarts in the old view while a peer already advanced — the restarted replica re-votes incorrectly.
    - Fix: `self.view.view_num += 1; self.wal.flush_view_num(self.view.view_num).await; self.broadcast(...);` — the flush is on the critical path, the broadcast is gated on it.
    - Cost avoided: ~300 µs–10 ms added latency per view-change (the fsync) vs a committed-op loss on the next crash — you pay the ms, never the loss. **(bar (c) violation.)**
    - Muscle: any externally-observable state change in a consensus protocol must be durable *before* it goes on the wire. Reapplies at: W76 commit_num durability, W80 ledger journal entry, W89 io_uring fsync ordering, W90 consensus-vsr v1.0.

  - **(EXPERT) When `livelock_resolved_under_simultaneous_restart` never converges (view-bump count runs away):**
    - Symptom: all 3 replicas perpetually bump view (`v1→v2→v3…`); no one stays Normal long enough to commit; bump count >> 6.
    - Why: every `start_view_change` triggers peers' suspect-timeout; peers bump their own view; cycle. Fixed timeouts make all three fire together forever.
    - Fix: (a) randomized exponential backoff `base × 2^attempt + jitter(0..base)`; (b) **view-skip** — a replica observing a peer view > its current jumps straight to that view (collapses concurrent attempts into one); (c) stable-leader grace: backups give the leader `view_change_timeout >> prepare_timeout` (≈5×) before suspecting.
    - Cost avoided: total throughput collapse to 0 ops/s during the storm — a liveness failure, not a slowdown. **(bar (c) violation.)**
    - Muscle: every "leader-suspect" trigger needs randomized backoff AND a view-skip rule, or simultaneous suspicion livelocks. Reapplies at: W76 state_transfer concurrent requests, W87 VOPR partition-storm, W90+ ledger live-cluster ops.

  - **(EXPERT) When `view_change_loom_no_committed_op_lost` reports op 100 lost OR `view_change_loom_test_must_be_slow` finishes in <100 ms:**
    - Symptom: either loom finds an interleaving where `on_start_view` adopting an earlier merged log races `on_do_view_change` and op 100 vanishes, OR the loom test finishes too fast (negative control fires).
    - Why (lost op): the merge result was published to shared state before commit_num/log were updated together — a torn merge visible to a concurrent `on_start_view`. Why (too fast): atomics imported from `std` not `loom`, so loom explored a single interleaving.
    - Fix: make the merge result installation a single critical section (hold the lock across log + op_num + commit_num assignment); gate concurrency imports via `#[cfg(loom)] use loom::sync::{Arc, Mutex};` and `#[cfg(not(loom))] use std::sync::{Arc, Mutex};`. Keep `view_change_loom_test_must_be_slow` to prove loom actually ran.
    - Cost avoided: a non-deterministic safety hole that only manifests under real multi-core scheduling — invisible to single-threaded tests. **(bar (c) violation.)**
    - Muscle: a multi-step state install in a shared-mutable consensus replica is atomic-as-a-unit, and every loom model gets a slow-negative-control. Reapplies at: W76 state_transfer install, W87 VOPR cross-machine reproducibility, W90 consensus-vsr v1.0.

  - **(SENIOR) When `no_committed_op_lost_under_random_partitions` finds a counterexample:**
    - Symptom: seed=42, actions `[partition(R1), kill(R2), restart(R3), unpartition(R1), kill(R3)]` end with committed op 87 missing from R1 and R3.
    - Why: usually one of the bugs above firing on a path the hand-written tests missed — stale view_num on restart (R5), torn merge (loom card), or commit_num `max` missed a path (R4).
    - Fix: capture the seed; replay deterministically; bisect with a state-dump after each action; map the broken invariant to the matching card above. If genuinely novel, document and freeze the seed as a regression case.
    - Cost avoided: shipping a consensus bug to a paper-trade soak (W92) where it costs a 24h re-run, or worse to ledger v1.0. **(bar (c) violation.)**
