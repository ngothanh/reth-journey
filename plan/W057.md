  - 🔧 **Why this matters**: cross-shard messaging IS the thread-per-core architecture. Without it, shards can't cooperate; with it done badly, you reintroduce locks and cache-line contention that kill scalability. Seastar's `submit_to` is the canonical pattern. Every Tier-A HFT IC bar-(c) question on TPC architecture eventually asks: "How do you pass a message from shard 0 to shard 5 without lock contention?" W60 matching-engine, W76+ aeron control plane, W85+ marketdata feed shards, W90+ ledger per-shard SM all depend on this primitive — a 50 ns/submit cliff item costs 30-50% of aggregate throughput.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: shared-memory + locks scale linearly with cores up to ~8, then collapse at the cache-line bouncing wall. Per-shard-pair queues eliminate cross-sender + cross-receiver contention; the remaining shared atomic (the depth counter) is the false-sharing trap. `Box<dyn FnOnce>` on every submit is the hidden allocator-lock trap.

  - **Requirements** — write in `crates/runtime-thread-per-core/notes/57_cross_shard_design.md`:
    - R1. NxN matrix of `SegQueue<TaskBox>` queues: one queue per (sender, receiver) pair. 16 shards = 256 queues.
    - R2. Single popper per receiver column → no cross-receiver contention on pop. Single pusher per (sender, receiver) cell from the sender's thread → no cross-sender contention on push.
    - R3. Per-receiver depth counter `capacities[to]: AtomicUsize` for backpressure trip; each counter CACHE-LINE-PADDED (`#[repr(align(128))]`) — false sharing here costs the entire scaling target.
    - R4. `TaskBox` payload uses a TYPED enum sum (`enum CrossShardOp { Order, Cancel, Subscribe, ... }`), NOT `Box<dyn FnOnce>`. Stack-allocated; no per-submit heap alloc.
    - R5. `submit_to(from, to, op)` budget: ≤ 100 ns same-NUMA uncontended (sets ~10M ops/s/core ceiling). Cross-NUMA degrades to ~5M ops/s/core — accepted; the strict same-NUMA routing preference compensates.
    - R6. `drain_inbox(me)` budget: ≤ 1.5 µs per drain (64-msg batch); batch limit prevents shard starvation.
    - R7. Memory ordering: `Acquire` on pop, `Release` on push — matches crossbeam's internal SegQueue use; `Relaxed` on capacity counter is correct (eventual consistency for backpressure trip).
    - R8. Backpressure hysteresis: trip on `depth >= threshold_high`; clear on `depth < threshold_low`.

  - **Design walk-through**:
    - D1. Why one queue per (sender, receiver) pair instead of N receiver queues (each receiver has one)? Walk the contention: with N receiver queues, M senders contend on `push` per receiver. With NxN, push has 1 sender per cell — uncontended. Memory cost: 256 queues × ~64 B = 16 KB; trivial.
    - D2. Why typed enum vs `Box<dyn FnOnce>`? Compute the allocator cost: 10M ops/s × ~50 ns malloc + ~30 ns dealloc = ~800 ms/s CPU = ~80% of one core. Typed enum is stack-allocated (zero alloc); dispatch is `match` (branch-predicted, no vtable). When does `Box<dyn FnOnce>` actually win? (Hint: when the variant count is unbounded or unknown at compile time — never on the hot path of a TPC runtime.)
    - D3. False-sharing on `capacities`: 16 × `AtomicUsize` = 128 B packed in 2 cache lines. Every increment from any shard invalidates other shards' cache lines. Compute the MESI-bounce cost: ~7 ns L2 fetch × 10M ops/s × 16 contended cores = ~70 ms/s CPU. Padded version: 16 × 128 B = 2 KB; trivial. (W004 muscle.)
    - D4. NUMA preference: shard 0 (NUMA0) submitting to shard 8 (NUMA1) costs ~100-200 ns vs ~5 ns same-NUMA (40× cliff). How do you route by affinity? (Hint: shards 0-7 on NUMA0, 8-15 on NUMA1; routing hash incorporates NUMA-locality.)
    - D5. Batched drain (64-msg cap): why bounded? Walk the starvation scenario where one shard's inbox is gigantic — unbounded drain monopolizes the receiver's reactor turn, downstream shards miss heartbeats.
    - D6. **Pre-mortem (load-bearing)**: write the 4-step path from "default `Box<dyn FnOnce>` payload" to "throughput plateaus at ~1-2M msgs/s no matter how many shards." This is THE cliff item.

    - Symptom: aggregate throughput hits a wall between 4 and 8 shards; adding more shards reduces per-shard throughput.
    - Why: cross-NUMA UPI saturation. Shards 0-7 on NUMA0; shards 8-15 on NUMA1; uniform-random routing produces 50% cross-NUMA traffic; UPI link saturates at ~3 GB/s.

  - **When `backpressure_trips_and_clears` ping-pongs:**
    - Symptom: sensor flips trip/clear at 10 kHz under sustained load; senders see jittery backpressure signal.
    - Why: no hysteresis — `threshold_high == threshold_low` (or close); depth oscillates around the boundary.
    - Fix: `threshold_high = 1024; threshold_low = 512;` — wide gap. Sensor trips at 1024, only clears below 512.
    - Muscle: every threshold-driven signal needs hysteresis; without it, every threshold-crossing produces a chatter. Reapplies at: W74 matching-engine rate-limit, W76+ aeron flow control, W83+ ledger journal-pressure.

  - **Design**:
    ```rust
    use crossbeam_queue::SegQueue;
    use backpressure::{Sensor, BackpressureStrategy};

    pub struct CrossShardChannel {
        // queues[i][j] = inbox for messages from shard i to shard j
        queues: Box<[Box<[SegQueue<TaskBox>]>]>,
        senders: usize,  // = num_shards
        capacities: Box<[AtomicUsize]>,  // per-receiver depth gauge
        threshold_high: usize,           // backpressure trigger
        threshold_low: usize,            // backpressure release
        sensors: Box<[Sensor]>,
    }

    pub struct TaskBox {
        pub task: Box<dyn FnOnce() + Send + 'static>,
        pub return_to: Option<ShardId>,  // for request-response patterns
    }

    impl CrossShardChannel {
        pub fn submit_to(&self, from: ShardId, to: ShardId, task: TaskBox) -> Result<(), Overflow> {
            let depth = self.capacities[to.0].fetch_add(1, Relaxed);
            if depth >= self.threshold_high {
                self.capacities[to.0].fetch_sub(1, Relaxed);
                self.sensors[from.0].trip();  // mark backpressure
                return Err(Overflow);
            }
            self.queues[from.0][to.0].push(task);
            Ok(())
        }

        pub fn drain_inbox(&self, me: ShardId) -> Vec<TaskBox> {
            let mut drained = Vec::with_capacity(64);
            for from in 0..self.senders {
                while let Some(t) = self.queues[from][me.0].pop() {
                    self.capacities[me.0].fetch_sub(1, Relaxed);
                    drained.push(t);
                    if drained.len() >= 64 { return drained; }  // bounded batch
                }
            }
            if self.capacities[me.0].load(Relaxed) < self.threshold_low {
                self.sensors[me.0].clear();
            }
            drained
        }
    }
    ```
    **Invariants**:
    - One queue PER (sender, receiver) pair → no cross-sender contention on push.
    - Receiver shard is sole popper from its column → no cross-receiver contention on pop.
    - `capacities[to]` is the single shared atomic counter per receiver — `Relaxed` ordering OK because we only need eventual consistency for backpressure trip.
    - Cache-line padding: each `SegQueue` should be on its own cache line (use `#[repr(align(128))]` wrappers).

  - 🔧 **Why this matters**: NUMA pinning is the single most impactful TPC optimization on dual-socket boxes (typical HFT hardware: 2× EPYC 7763 = 2 NUMA nodes, 128 cores each). Cross-NUMA memory access is 2-3× slower than local; for an L3 miss, cross-NUMA is ~200 ns vs ~80 ns local. ScyllaDB attributes 30%+ throughput gains to NUMA awareness alone. W60 matching-engine pins shards by symbol-hash with NUMA awareness; W85+ marketdata pinned by feed; W90+ ledger pinned per account-shard — get pinning wrong here and ALL downstream consumers inherit a 30% steady-state loss.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: the default Rust allocator + the default Linux scheduler are both NUMA-oblivious. A shard pinned to NUMA0 but whose heap pages live on NUMA1 (because a setup thread on NUMA1 first-touched them) pays the cross-NUMA tax on EVERY access — 30%+ throughput loss confirmed by ScyllaDB. Worse: kernel auto-balancing silently undoes your pinning every minute.

  - **Requirements** — write in `crates/runtime-thread-per-core/notes/57_numa_design.md`:
    - R1. `initialize_numa() -> Result<NumaTopology>` queries libnuma, logs nodes + CPUs per node, falls back to single-node when libnuma unavailable.
    - R2. `bind_shard(cfg: &ShardConfig)` does (a) CPU affinity via `sched_setaffinity` to `cfg.pinned_cpu`, (b) memory bind via `numa_set_membind` to `cfg.numa_node`, (c) heap allocation via `numa_alloc_onnode(size, node)` OR per-shard `mimalloc` arena pinned to the local node.
    - R3. Per-shard arena allocator: each shard's worker thread, immediately after bind, switches to a local-NUMA arena. Default global allocator is FORBIDDEN on the hot path.
    - R4. Cross-NUMA accesses minimized via topology-aware shard placement (shards 0..N/2 on NUMA0, N/2..N on NUMA1; configurable).
    - R5. `numa_balancing` sysctl set to `0` at startup (or documented as a deployment requirement); `set_mempolicy(MPOL_BIND, mask)` makes pages immovable.
    - R6. THP (Transparent Huge Pages) explicitly disabled for the runtime process via `prctl(PR_SET_THP_DISABLE)` OR pre-bind THEN allocate.
    - R7. Bind cost: ≤ 50 µs per shard at startup; zero runtime cost after binding.
    - R8. Verification: `/proc/<pid>/numa_maps` shows ≥ 95% of a shard's pages on its assigned node.

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

  - **When `shard_pages_on_local_numa` shows ~50% pages on remote NUMA and bench p99 is 4-6× expected:**
    - Symptom: `/proc/<pid>/numa_maps` shows ~50% of a shard's pages on the remote NUMA; benchmark p99 4-6× expected; `perf stat -e mem_load_uops_retired.l3_miss_remote_dram` shows >50% remote DRAM hits.
    - Why: default Rust system allocator allocates on the calling thread's NUMA node, but a shard that touches data allocated by a setup thread on the wrong NUMA pays cross-NUMA tax forever. Worse: glibc's allocator may interleave across nodes "for balance."
    - Fix: switch to `mimalloc` or `jemalloc` with per-shard arenas + NUMA-affinity policy. Each shard's worker thread, immediately after `bind_shard`, calls `mi_heap_new_in_arena(numa_arena_id)` (mimalloc) or sets `je_mallctl("thread.arena", ...)` (jemalloc). All shard-private allocations route to the local arena. For genuinely shared structures (cross-shard messages), use a separately-tracked arena.
    - Cost avoided: ~100-200 ns per remote-DRAM access × ~10M memory ops/s/shard = ~1-2 s/s CPU worth of stall (~30-50% throughput, matching ScyllaDB's number). THE single largest TPC win on dual-socket hardware.
    - Muscle: every "general-purpose" tool (default allocator, default scheduler, default fs cache policy) is NUMA-oblivious by default. On bar-(c) HFT hardware, every layer must be made NUMA-aware explicitly: allocator first, scheduler second, network stack third. **Reapplies at**: W60+ matching-engine per-symbol allocator, W83+ ledger static-mem pools per replica, W90+ ledger io_uring SQ buffer placement, W94 block-stm worker-local memory.

  - **When `numa_balancing_disabled` shows it's enabled and bench degrades within 60 seconds:**
    - Symptom: benchmark shows great numbers for 60 seconds then degrades; `cat /proc/<pid>/status | grep numa` shows page migrations climbing; `dmesg` may show automatic balancing decisions; cross-NUMA traffic spikes.
    - Why: Linux's automatic NUMA balancing periodically scans process memory, detects "this page is accessed mostly from NUMA1 but lives on NUMA0," and migrates it. For a TPC runtime that you JUST pinned via libnuma, this is destructive: pages bounce; cross-NUMA traffic spikes.
    - Fix: at startup, write `0` to `/proc/sys/kernel/numa_balancing` (root, or done by ops via sysctl); document the deployment requirement. Belt-and-suspenders: call `set_mempolicy(MPOL_BIND, mask)` per thread which makes pages immovable.
    - Cost avoided: the entire 30% NUMA-pinning win, which auto-balancing erodes within a minute of steady-state.
    - Muscle: pinning is a 2-party contract — your code says "these pages live here" AND the kernel must agree to not move them. Document the sysctl + the rationale; auto-features eat hand-tuning silently. ScyllaDB's deployment docs explicitly mandate this. **Reapplies at**: W83+ ledger production deployment, W90+ marketdata-kernelbypass AF_XDP page placement, W107+ ops-deploy k8s manifest must set this on the node.

  - **When `thp_disabled_for_process` reports THP enabled and pages on wrong NUMA:**
    - Symptom: 2 MB huge pages allocated on the setup thread's NUMA stay on that NUMA after bind; the `numa_alloc_onnode` call after bind fragments and writes to different pages than expected.
    - Why: THP allocates the huge page eagerly when first touched; bind happens later; page placement is already committed.
    - Fix: `prctl(PR_SET_THP_DISABLE, 1, 0, 0, 0)` immediately at process startup BEFORE any allocation. Alternatively, ensure bind happens BEFORE first allocation in every shard.
    - Muscle: huge pages and NUMA bind interact pessimistically; disable THP or sequence allocations carefully. Reapplies at: every TPC-style production deployment.

  - **When `cross_numa_bench_2x_slower` shows ratio ~1.1× (not ≥ 1.8×):**

    - Muscle: NUMA optimizations require host-level cooperation; cloud-VM deployments need explicit numa-passthrough config. Reapplies at: W83+ production deployment, W107+ k8s manifest review.

  - **When `default_allocator_forbidden_on_hot_path` finds `Vec::with_capacity` on a hot path:**
    - Symptom: scan or clippy lint catches a `Vec::with_capacity(n)` inside the shard's per-tick loop.
    - Why: convenience — a temporary buffer that "should be cheap."
    - Fix: use the shard's arena (`shard.arena.alloc_vec::<T>(capacity)`) or a pre-allocated `Vec` reused across ticks.
    - Muscle: arena allocation isn't optional once you've decided on per-shard NUMA isolation; one rogue global alloc invalidates the discipline. Reapplies at: every TPC-style hot path.

  - *Back-of-envelope* (bar (c) — NUMA effects dominate every cross-shard hot path on dual-socket boxes):
    - Local-NUMA L3 hit: **~30-50 ns** (vs L1 ~0.5 ns, L2 ~7 ns). Remote-NUMA L3 hit: **~100-200 ns**. Remote-NUMA DRAM: **~200-300 ns** vs local DRAM ~80 ns. The 2-3× cliff is the same across all access types.
    - Cross-NUMA atomic RMW (e.g., `fetch_add` on a counter owned by a remote NUMA's cache): ~100-200 ns vs ~5 ns same-NUMA ⇒ **30-40× cliff**. This is why W057 Fri's `capacities` array MUST be either per-NUMA partitioned or CachePadded.
    - Heap allocation on the wrong NUMA: first-touch policy means pages are allocated on the NUMA that first writes them. If the allocator thread runs on NUMA1 but the consumer shard runs on NUMA0, EVERY access is cross-NUMA. **30%+ throughput loss** confirmed by ScyllaDB's measurements.
    - `bind_shard` cost: one-time at startup (~10-50 µs sched_setaffinity + a few syscalls). Zero runtime cost after binding.
    - Memory budget: 16 shards × ~64 MB/shard local heap = 1 GB; both NUMA nodes should have ≥ 32 GB RAM for headroom. The arena allocator (mimalloc/jemalloc) handles per-shard isolation.
    - HFT-grade bare metal (2-socket EPYC, ~128 cores total) gets the full 30% win; cloud VMs with virtual NUMA may not — measure with `numactl --hardware` and `/proc/<pid>/numa_maps`.
