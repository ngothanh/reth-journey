**Friday (post-EthCC) — runtime-thread-per-core v0.5: cross-shard channel** [NEW v2]

- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/cross_shard.rs` — lock-free MPMC channel per shard pair via concurrent::SegQueue. Backpressure via `backpressure` crate. (~150 min)
  - **Why (MAX DETAIL — bar c)**: Cross-shard messaging IS the thread-per-core architecture. Without it, shards can't cooperate; with it done badly, you reintroduce locks and cache-line contention that kill scalability. Seastar's `submit_to` is the canonical pattern. Every Tier-A HFT IC bar (c) question on TPC architecture eventually asks: "How do you pass a message from shard 0 to shard 5 without lock contention?"
  - *Back-of-envelope* (bar (c) — cross-shard is on the matching-engine + market-data hot path; target ≥ 10M msgs/s aggregate):
    - 16 shards × `SegQueue<TaskBox>` queue matrix = 256 queues. Per-queue baseline mem ≈ 200 B (Michael-Scott head/tail + first segment) = ~50 KB total queue-state; with `CachePadded` to 128 B alignment ⇒ ~32 KB padded; trivial.
    - `submit_to` cost (uncontended, same-NUMA): `capacities[to].fetch_add(Relaxed)` = ~5 ns (uncontended atomic) + `SegQueue::push` = ~25-40 ns (CAS on segment tail). Total ≈ **30-50 ns/submit uncontested**.
    - `submit_to` (cross-NUMA, dual-socket): the atomic counter + the SegQueue's tail pointer live on the receiver's NUMA node. Cross-NUMA cache-line invalidation: ~100-200 ns vs ~5 ns same-NUMA ⇒ **40× cliff**. ScyllaDB's measured number; matches Intel UPI / AMD Infinity Fabric latency.
    - `drain_inbox`: 1 reader, no contention on pop. ~20 ns/pop × 64 batch = ~1.3 µs/drain. At 100k drains/s/shard × 16 shards = ~2.1 ms/s aggregate batch overhead.
    - Target: 10M msgs/s aggregate at p99 < 5 µs. Budget per submit_to ≤ 100 ns (gives 10M ops/s/core ceiling on a single shard's sender threads). Cross-NUMA pushes this to ~5M ops/s/core — hence the strict same-NUMA routing preference.
    - 50-ns cliff items (false sharing on capacity counter, lack of CachePadded on SegQueue, malloc in TaskBox) each cut aggregate throughput by 30-50%.
  - **Read first**:
    - Seastar `src/core/reactor.cc` `smp::submit_to`; `include/seastar/core/sharded.hh`
    - ScyllaDB blog: "How ScyllaDB's CPU Scheduler Solves Performance Problems" (sharded data flow)
    - crossbeam `SegQueue` source — unbounded MPMC via Michael-Scott style linked list of segments
    - crossbeam `ArrayQueue` — bounded MPMC; alternative if you want backpressure-by-block
  - **Design**:
    ```rust
    use crossbeam_queue::SegQueue;
    use backpressure::{Sensor, BackpressureStrategy};

    pub struct CrossShardChannel {
        // queues[i][j] = inbox for messages from shard i to shard j
        queues: Box<[Box<[SegQueue<TaskBox>]>]>,
        senders: usize,  // = num_shards
        capacities: Box<[AtomicUsize]>,  // per-receiver depth gauge
        threshold_high: usize,           // backpressure trigger
        threshold_low: usize,            // backpressure release
        sensors: Box<[Sensor]>,
    }

    pub struct TaskBox {
        pub task: Box<dyn FnOnce() + Send + 'static>,
        pub return_to: Option<ShardId>,  // for request-response patterns
    }

    impl CrossShardChannel {
        pub fn submit_to(&self, from: ShardId, to: ShardId, task: TaskBox) -> Result<(), Overflow> {
            let depth = self.capacities[to.0].fetch_add(1, Relaxed);
            if depth >= self.threshold_high {
                self.capacities[to.0].fetch_sub(1, Relaxed);
                self.sensors[from.0].trip();  // mark backpressure
                return Err(Overflow);
            }
            self.queues[from.0][to.0].push(task);
            Ok(())
        }

        pub fn drain_inbox(&self, me: ShardId) -> Vec<TaskBox> {
            let mut drained = Vec::with_capacity(64);
            for from in 0..self.senders {
                while let Some(t) = self.queues[from][me.0].pop() {
                    self.capacities[me.0].fetch_sub(1, Relaxed);
                    drained.push(t);
                    if drained.len() >= 64 { return drained; }  // bounded batch
                }
            }
            if self.capacities[me.0].load(Relaxed) < self.threshold_low {
                self.sensors[me.0].clear();
            }
            drained
        }
    }
    ```
    **Invariants**:
    - One queue PER (sender, receiver) pair → no cross-sender contention on push.
    - Receiver shard is sole popper from its column → no cross-receiver contention on pop.
    - `capacities[to]` is the single shared atomic counter per receiver — `Relaxed` ordering OK because we only need eventual consistency for backpressure trip.
    - Cache-line padding: each `SegQueue` should be on its own cache line (use `#[repr(align(128))]` wrappers).

    5. (~20 min) `drain_inbox` with batch limit (64 msgs/turn) to prevent shard starvation.

  - **Pitfalls** (named, concurrency-critical):
    - *Cross-NUMA write fan-out*: shard 0 (NUMA node 0) submits to shard 8 (NUMA node 1) at high rate → QPI/UPI saturation → throughput drops below same-NUMA. **Symptom**: 4× regression on dual-socket boxes. **Fix**: per-NUMA submission batching; or simply place shards 0-7 on NUMA0 and 8-15 on NUMA1 and route by affinity hint.
    - *False sharing on capacity atomic*: 16 capacity atomics packed in 64 bytes → every increment from any shard invalidates other shards' cache lines. **Symptom**: 10× throughput drop with 16 shards. **Fix**: `#[repr(align(128))] struct PaddedCounter(AtomicUsize);` — one cache line per counter.
    - *NUMA imbalance under skewed traffic*: hot symbol routes 90% of cross-shard traffic to shard 5. Shard 5 NUMA node congests. **Symptom**: tail latency spikes. **Fix**: monitoring + manual shard rebalance (W57 NUMA pinning helps); long-term auto-rebalance is W74+.
    - *SegQueue unbounded growth*: under sustained overload, capacity atomic helps but `SegQueue` itself can grow unboundedly between checks. **Symptom**: OOM. **Fix**: capacity check is per-PUSH, BEFORE allocation. Alternative: use `ArrayQueue` (bounded ring buffer); more contention but no growth.
    - *Memory ordering bug on drain*: using Relaxed everywhere allows reordering across `pop` boundary → stale capacity reading → backpressure fails to clear. **Symptom**: shard stuck in backpressure state. **Fix**: `Acquire` on pop, `Release` on push (matches crossbeam's internal use).
    - **Expect to hit (perf) #1 — `TaskBox::task: Box<dyn FnOnce() + Send>` heap-allocates per submit (bar (c) violation)**: every `submit_to` requires boxing the closure (~50 ns malloc + vtable setup); at 10M msgs/s aggregate = 10M allocs/s = ~500 ms/s of allocator CPU = saturation. **Symptom**: `perf top` shows `__GI___libc_malloc` and the global allocator lock contend with the actual workload; throughput plateaus at ~1-2M msgs/s no matter how many shards you add.
      - Fix: avoid `dyn FnOnce` on the hot path. Use a typed `enum CrossShardOp { Order(Order), Cancel(CancelId), Subscribe(SubReq), … }` — a sum type sized to its largest variant (a few hundred bytes), stack-allocated in `TaskBox`. The cross-shard handler dispatches via `match` (no vtable, branch-predicted). For genuinely variant-shaped tasks, a per-shard typed slab/`bufpool` (W14) pre-allocates `TaskBox`s and the submit transfers ownership of a slab index, not a Box.
      - Cost avoided: ~50 ns malloc + ~30 ns dealloc per task × 10M ops/s = ~800 ms/s CPU = full saturation eliminated. Restores the linear-scaling target.
      - Muscle: `Box<dyn FnOnce>` is convenient but mortal on the hot path; typed enums or slab-allocated boxes are the bar-(c) cure. This is the exact `Box::pin` family of bug from W003 Friday's `rate_limit` regression, expressed at the shard-message layer.
      - **Reapplies at**: W60 matching-engine cross-symbol cancels via shard messaging, W76+ aeron `Publication::offer` (uses pre-allocated term buffer slot, not Box), W83+ ledger op-log entries via static-mem pool, W94 block-stm task queue.
    - **Expect to hit (perf) #2 — `capacities: Box<[AtomicUsize]>` without per-element CachePadded → false sharing (bar (c) violation)**: 16 × `AtomicUsize` = 128 B, packed into 2 cache lines; every `submit_to(*, to=5)` invalidates the cache line holding capacities[4]..capacities[11] on EVERY other sender's core. **Symptom**: 16-shard all-to-all bench shows ~3-5× regression vs theoretical near-linear scaling; `perf stat -e cache-misses,cache-references` reveals the storm.
      - Fix: `#[repr(align(128))] struct PaddedCounter(AtomicUsize);` (or `CachePadded<AtomicUsize>` from crossbeam-utils); store as `Box<[PaddedCounter; N_SHARDS]>`. Each counter on its own cache line. Memory cost: 16 × 128 B = 2 KB (was 128 B); negligible.
      - Cost avoided: ~7 ns L2 fetch (cache miss from MESI invalidation) per `fetch_add` × 10M ops/s shared across cores = up to ~70 ms/s CPU + the cliff in throughput (the 3-5× regression). This is the false-sharing cost the W004 CachePadded item teaches.
      - Muscle: any atomic touched by multiple cores must be cache-line padded; the default `Box<[AtomicT]>` is a bar-(c) failure waiting to happen. Verify with `mem::size_of::<PaddedCounter>() >= 64` (ideally 128 for x86-64 prefetcher behavior).
      - **Reapplies at**: W74 matching-engine per-symbol sequence counters, W76+ aeron `Publication::term_position` (must be padded), W90+ ledger replica progress counters, W94 block-stm transaction-status atomics.
  - **Test scenarios** (adversarial):
    - 8 shards × 100k msgs/shard all-to-all → total_received = total_sent (800k), latency p99 < 5 µs.

**Saturday — Travel home + runtime-thread-per-core v0.5: pinning + NUMA** [NEW v2]

- [ ] Rest. (~5 min)
- [ ] [NEW v2] **Build**: extend Shard with NUMA-aware allocation; use `libnuma` crate. Each shard's heap on its local NUMA node. (~90 min)
  - **Why (MAX DETAIL — bar c)**: NUMA pinning is the single most impactful TPC optimization on dual-socket boxes (typical HFT hardware: 2× EPYC 7763 = 2 NUMA nodes, 128 cores each). Cross-NUMA memory access is 2-3× slower than local; for an L3 cache miss, cross-NUMA can be 200ns vs 80ns local. ScyllaDB attributes 30%+ throughput gains to NUMA awareness alone. Bar (c) — interview-load-bearing.
  - *Back-of-envelope* (bar (c) — NUMA effects dominate every cross-shard hot path on dual-socket boxes):
    - Local-NUMA L3 hit: **~30-50 ns** (vs L1 ~0.5 ns, L2 ~7 ns). Remote-NUMA L3 hit: **~100-200 ns**. Remote-NUMA DRAM: **~200-300 ns** vs local DRAM ~80 ns. The 2-3× cliff is the same across all access types.
    - Cross-NUMA atomic RMW (e.g., `fetch_add` on a counter owned by a remote NUMA's cache): ~100-200 ns vs ~5 ns same-NUMA ⇒ **30-40× cliff**. This is why W057 Fri's `capacities` array MUST be either per-NUMA partitioned or CachePadded.
    - Heap allocation on the wrong NUMA: first-touch policy means pages are allocated on the NUMA that first writes them. If the allocator thread runs on NUMA1 but the consumer shard runs on NUMA0, EVERY access is cross-NUMA. **30%+ throughput loss** confirmed by ScyllaDB's measurements.
    - `bind_shard` cost: one-time at startup (~10-50 µs sched_setaffinity + a few syscalls). Zero runtime cost after binding.
    - Memory budget: 16 shards × ~64 MB/shard local heap = 1 GB; both NUMA nodes should have ≥ 32 GB RAM for headroom. The arena allocator (mimalloc/jemalloc) handles per-shard isolation.
    - HFT-grade bare metal (2-socket EPYC, ~128 cores total) gets the full 30% win; cloud VMs with virtual NUMA may not — measure with `numactl --hardware` and `/proc/<pid>/numa_maps`.
  - **Read first**: Linux numactl manual; libnuma man pages; ScyllaDB's `src/core/memory.cc` (numa-aware allocator); Brendan Gregg's "NUMA on Linux" articles.
  - **Design**:
    ```rust

    }
    pub struct NumaNode {

    }
    ```

    **Invariants**:
    - Each shard pinned to ONE CPU on its NUMA node. No migration.
    - Shard's heap pages allocated on its local NUMA node (via `numa_alloc_onnode` or `mbind`).
    - Cross-shard messages MAY cross NUMA — that's the price; minimize via topology-aware routing.
    - Initialization happens ONCE at startup; runtime cannot change NUMA binding.
  - **Build steps** (granular):
    1. (~15 min) Add `libnuma-sys` (or `numactl`) crate; feature-gate `numa` (not all platforms support it).
    2. (~20 min) `initialize_numa()`: query topology, log nodes + CPUs per node, fall back to single-node if libnuma unavailable.
    3. (~20 min) `bind_shard(cfg)`: cpu affinity via `core_affinity::set_for_current`; memory bind via `numa_set_membind`.
    4. (~15 min) Per-shard heap allocator: use jemalloc with NUMA hint, OR `numa_alloc_onnode(size, node)` for explicit slabs.
    5. (~10 min) Bench: same-NUMA cross-shard latency vs cross-NUMA: expect 2× difference.
    6. (~10 min) Document topology auto-detection: shards 0..N/2 on node0, N/2..N on node1; configurable override.
  - **Pitfalls** (named, OS-critical):
    - *NUMA-unaware allocator*: default Rust allocator (system malloc) may interleave pages across NUMA nodes (`/proc/sys/kernel/numa_balancing = 1` enables auto-migration which can also hurt). **Symptom**: 30% throughput drop on dual-socket. **Fix**: per-shard arena via `mimalloc` with NUMA-affinity flag, OR explicit `numa_alloc_onnode`.
    - *NUMA imbalance*: shard 5 (NUMA0) gets 70% of work, shard 12 (NUMA1) idle. **Symptom**: NUMA0 cores saturate while NUMA1 cool. **Fix**: monitor per-shard utilization; rebalance by routing hash function. matching-engine W74+ implements this.
    - *Cross-NUMA write fan-out*: shard 0 (NUMA0) writes to 7 shards on NUMA1 → UPI link saturation. **Symptom**: throughput cliff at certain fan-out levels. **Fix**: prefer same-NUMA routing; for unavoidable cross-NUMA, batch writes to amortize UPI cost.
    - *False NUMA report under hypervisor*: VM with single virtual NUMA node but 2 physical → libnuma reports 1 node, app skips pinning, but underlying scheduler still migrates. **Symptom**: best efforts wasted. **Fix**: log warning if VM detected; document deployment requirement (bare metal or properly-configured guest).
    - *THP (Transparent Huge Pages) misbinding*: huge pages allocated on remote NUMA before bind takes effect. **Symptom**: bench shows local-bind but pages remote. **Fix**: disable THP for the runtime process (`prctl(PR_SET_THP_DISABLE)`) OR pre-bind THEN allocate.
    - **Expect to hit (perf) #1 — global allocator interleaves pages across NUMA nodes (bar (c) violation)**: the default Rust system allocator allocates on the calling thread's NUMA node, but a shard that touches data allocated by a setup thread on the wrong NUMA pays the cross-NUMA tax on every access. Worse: glibc's allocator may interleave across nodes for "balance." **Symptom**: `numa_maps` shows ~50% of a shard's pages on the remote NUMA; benchmark p99 4-6× expected; `perf stat -e mem_load_uops_retired.l3_miss_remote_dram` shows >50% remote DRAM hits.
      - Fix: switch to `mimalloc` or `jemalloc` with per-shard arenas + NUMA-affinity policy. Concretely: each shard's worker thread, immediately after `bind_shard`, calls `mi_heap_new_in_arena(numa_arena_id)` (mimalloc) or sets `je_mallctl("thread.arena", ...)` (jemalloc). All shard-private allocations route to the local arena. For genuinely shared structures (cross-shard messages), use a separately-tracked arena.
      - Cost avoided: ~100-200 ns per remote-DRAM access × ~10M memory ops/s/shard = ~1-2 s/s CPU worth of stall (= ~30-50% throughput, matching ScyllaDB's number). This is THE single largest TPC win on dual-socket hardware.
      - Muscle: every "general-purpose" tool (default allocator, default scheduler, default fs cache policy) is NUMA-oblivious by default. On bar-(c) HFT hardware, every layer must be made NUMA-aware explicitly. Allocator first, scheduler second, network stack third.
      - **Reapplies at**: W60+ matching-engine per-symbol allocator, W83+ ledger static-mem pools per replica, W90+ ledger io_uring SQ buffer placement, W94 block-stm worker-local memory.
    - **Expect to hit (perf) #2 — kernel auto-balancing (`numa_balancing=1`) silently undoes your pinning (bar (c) violation)**: Linux's automatic NUMA balancing periodically scans process memory, detects "this page is accessed mostly from NUMA1 but lives on NUMA0," and migrates it. For a TPC runtime that you JUST pinned via libnuma, this is destructive: pages bounce; cross-NUMA traffic spikes; perf is worse than not pinning at all. **Symptom**: benchmark shows great numbers for 60 seconds then degrades; `cat /proc/<pid>/status | grep numa` shows page migrations climbing; `dmesg` may show automatic balancing decisions.
      - Fix: at startup, write `0` to `/proc/sys/kernel/numa_balancing` (root, or done by ops via sysctl); document deployment requirement. Alternatively, call `set_mempolicy(MPOL_BIND, mask)` per thread which makes pages immovable to the bound node.
      - Cost avoided: the entire 30% NUMA-pinning win, which auto-balancing erodes within a minute of steady-state.
      - Muscle: pinning is a 2-party contract — your code says "these pages live here" AND the kernel must agree to not move them. Document the sysctl + the rationale; auto-features eat hand-tuning silently. ScyllaDB's deployment docs explicitly mandate this.
      - **Reapplies at**: W83+ ledger production deployment (same sysctl), W90+ marketdata-kernelbypass AF_XDP page placement, W107+ ops-deploy k8s manifest must set this on the node.
  - **Test scenarios**:
    - Bind shard 0 to NUMA0, shard 8 to NUMA1; allocate 1GB heap each; verify via `/proc/<pid>/numa_maps` that pages live on correct node.
    - Cross-NUMA bench: send 1M msgs from shard 0 to shard 8 (cross-NUMA) vs shard 0 to shard 1 (same-NUMA); same-NUMA should be ≥ 1.8× faster.
    - Imbalance simulation: route 90% traffic to NUMA0; observe NUMA1 idle in metrics; verify rebalance recommendation surfaces.
  - **Acceptance**: page placement verified via numa_maps; cross-vs-same NUMA bench delta ≥ 1.5×; topology auto-detect works on dual-socket dev box.
  - **Downstream**: W60 matching-engine pins shards by symbol-hash with NUMA awareness; W85+ marketdata pinned by feed; W90+ ledger pinned per account-shard.
