**Monday — Journaling design**

- [ ] Read revm-interpreter journal module. Revert semantics. (~45 min)
  - **Why**: Journaling is the EVM's transactional memory: every state mutation is recorded into an undo log so REVERT (and exceptional halts like OOG) can rewind to a prior checkpoint. Get this wrong and you get a consensus fork OR a quadratic-blowup DoS (e.g., adversarial deeply-nested CALL with REVERT-on-exit). Mastery here is interview-load-bearing for both EVM and database (txn/wal) contexts — exec-vm's `JournaledState` is the bridge from EVM semantics to txn isolation.
  - **Read first**:
    - `crates/context/src/journaled_state.rs` — `JournaledState { state, transient_storage, depth, journal: Vec<Vec<JournalEntry>>, spec, warm_preloaded_addresses }`
    - `crates/context-interface/src/journaled_state.rs` — the trait surface
    - `JournalEntry` enum: ~12 variants (AccountWarmed, AccountLoaded, StorageWarmed, StorageChanged, BalanceTransfer, NonceChange, AccountCreated, AccountDestroyed, CodeChange, TransientStorageChange, AccountTouched)
  - **Design**:
    ```rust
    pub struct JournaledState {
        pub state: EvmState,                              // HashMap<Address, Account>
        pub transient_storage: TransientStorage,          // (Address, U256) -> U256
        pub depth: usize,                                  // current call depth
        pub journal: Vec<Vec<JournalEntry>>,              // outer Vec indexed by depth
        pub spec: SpecId,
        pub warm_preloaded_addresses: HashSet<Address>,   // EIP-2930 + coinbase + tx.from/to
    }

    pub enum JournalEntry {
        AccountWarmed { address: Address },
        AccountDestroyed { address, target, was_destroyed, had_balance },
        AccountTouched { address },
        BalanceTransfer { from, to, balance },
        NonceChange { address },
        AccountCreated { address },
        StorageWarmed { address, key },
        StorageChanged { address, key, had_value },
        TransientStorageChange { address, key, had_value },
        CodeChange { address },
    }
    ```
    **Invariants**:
    - `journal[d]` holds entries created at depth `d`. On `checkpoint()`, push empty `Vec` (new frame); on `commit()`, drain `journal.pop()` into `journal.last_mut()` (merge into parent); on `revert()`, drain and APPLY in reverse to undo.
    - Each `JournalEntry` records the PRE-change state, not the new value. Undo = restore pre-change.
    - Transient storage (EIP-1153) is journaled like regular storage: REVERT rolls it back; commit folds into parent.
    - Warm-set is journaled: a sub-call warming address X must NOT leak warmth back to parent on revert.
  - **Build steps** (granular):
    1. (~10 min) Open journaled_state.rs. Find `checkpoint()` — note it returns `JournalCheckpoint { log_i, journal_i }` (TWO indices: one into the global log buffer, one into the journal vec).
    2. (~10 min) Read `journal_revert`. Walk through how each `JournalEntry` variant is undone. Note `AccountDestroyed` has `was_destroyed: bool` — restoring deletes the destroy flag iff previously alive.
    3. (~10 min) Read `BalanceTransfer` undo: reads `from` and `to`, restores `from.balance += balance; to.balance -= balance`. Note this means storing the DELTA suffices (not absolute pre-state).
    4. (~10 min) Read `StorageChanged` undo: restores `had_value` (the pre-change value) — confirms entry stores PRE state, not POST.
    5. (~5 min) Map exec-vm's W17 journal sketch (or absence thereof) to this design. List gaps.
  - **Pitfalls** (named):
    - *Warm-leak across revert*: forgetting to journal `AccountWarmed`/`StorageWarmed` causes warm state to persist past revert. **Symptom**: gas cheaper than spec; mainnet-cap diff vs revm. **Fix**: every `load_account`/`sload` that flips `is_cold` MUST push a `Warmed` entry.
    - *Double-undo on commit*: confusing commit (merge into parent) with revert (apply undo). **Symptom**: on commit, balance changes get undone. **Fix**: commit DRAINS journal[d] into journal[d-1] (extend), NEVER applies undo logic.
    - *AccountDestroyed-then-recreated*: EIP-6780 (Cancun) restricts SELFDESTRUCT to same-tx-create accounts. The journal entry must include `was_destroyed: bool` for proper undo. **Symptom**: revert after SELFDESTRUCT leaves account in inconsistent destroyed state. **Fix**: `AccountDestroyed { was_destroyed }` flag; undo restores prior status.
    - *Transient-storage half-journaled*: tload doesn't need journaling (read-only) but tstore does. Forgetting splits causes either O(n) read-journal overhead OR missing rollback. **Symptom**: TSTORE survives REVERT. **Fix**: journal ONLY in tstore.
  - **Test scenarios**:
    - SSTORE slot=1 value=42, REVERT: storage[1] = pre-change value (0 if first-time).
    - Sub-call warms address X then REVERTs; parent SLOAD on X must charge cold (2100).
    - SELFDESTRUCT then sub-call CREATE2 at same address; outer REVERT: both undone.
    - TSTORE within sub-call that REVERTS: TLOAD in parent returns 0.
  - **Acceptance**: annotated journal trace `notes/revm_journal_trace.md`; gap list for exec-vm has every missing JournalEntry variant.
  - **Downstream**: W55 (exec-vm journaling parity build), W62 (storage-trie integration uses BundleState diffs derived from journal), W74+ (matching-engine reuses pattern: per-order undo log into wal::Wal).

**Tuesday — Nested checkpoints**

- [ ] Study nested call handling. (~30 min)
  - **Why**: Each CALL/CREATE pushes a new journal frame; depth can reach 1024 (EIP-150 stack limit). Nested-checkpoint correctness is where ~half of EVM consensus bugs historically lived (DAO fork notwithstanding). Critical to internalize for exec-vm + downstream txn isolation (W47+ txn crate has analogous nested-savepoint semantics).
  - **Read first**:
    - `crates/handler/src/frame.rs` — `EthFrame::run`, the per-frame checkpoint dance
    - `crates/context/src/journaled_state.rs::checkpoint`, `commit`, `revert` triplet
    - Note CREATE2 collision check uses `state.contains_key(addr)` PRE-checkpoint
  - **Design**:
    ```rust
    impl JournaledState {
        pub fn checkpoint(&mut self) -> JournalCheckpoint {
            let cp = JournalCheckpoint {
                log_i: self.logs.len(),         // logs are also rolled back
                journal_i: self.journal.len(),
            };
            self.journal.push(Vec::new());     // new sub-frame
            self.depth += 1;
            cp
        }

        pub fn checkpoint_commit(&mut self) {  // sub-call succeeded
            let entries = self.journal.pop().unwrap();
            if let Some(parent) = self.journal.last_mut() {
                parent.extend(entries);         // merge upward; do NOT undo
            }
            self.depth -= 1;
        }

        pub fn checkpoint_revert(&mut self, cp: JournalCheckpoint) {
            // truncate logs back to pre-checkpoint
            self.logs.truncate(cp.log_i);
            // pop sub-frame and apply each entry in reverse
            while self.journal.len() > cp.journal_i {
                let entries = self.journal.pop().unwrap();
                for entry in entries.into_iter().rev() {
                    self.revert_entry(entry);
                }
            }
            self.depth -= 1;
        }
    }
    ```
    **Invariants**:
    - `checkpoint`/`commit` pair OR `checkpoint`/`revert` pair — never interleaved across frames.
    - Logs (LOG0..LOG4 emissions) ALSO roll back: `cp.log_i` truncate is mandatory.
    - Reverse-order undo: a single frame may have `BalanceTransfer { from: A, to: B }` then `BalanceTransfer { from: B, to: C }`. Undoing in original order would leave B with negative balance briefly (still works for u256, but reverse is canonical).
  - **Build steps** (granular):
    1. (~5 min) Sketch the call tree of a `tx → A.calls(B) → B.calls(C){REVERT} → A.calls(D)`. Verify B's changes are gone but D's commit.
    2. (~10 min) Read CREATE2 path: collision check uses pre-checkpoint state lookup. Critical because CREATE2 to existing-account is REVERT, not silent overwrite.
    3. (~5 min) Read CALL: gas-forwarded amount obeys 63/64 rule (EIP-150). Verify revm's call subroutine applies this BEFORE checkpoint.
    4. (~5 min) Note the depth=1024 cap: exceeding returns InstructionResult::CallTooDeep, no checkpoint pushed. Important for memory bound on journal Vec.
    5. (~5 min) Diff exec-vm's W17 call-frame impl: confirm checkpoint precedes any mutation and revert truncates logs.
  - **Pitfalls** (named):
    - *Checkpoint before gas-transfer*: if you checkpoint AFTER transferring value to sub-call's address, revert undoes the wrong thing. **Symptom**: sub-call OOG drops value into the void. **Fix**: checkpoint THEN transfer THEN dispatch.
    - *Logs survive REVERT*: forgetting to truncate `self.logs` leaves LOG0 emissions visible in receipt. **Symptom**: indexers see ghost events. **Fix**: `JournalCheckpoint { log_i, .. }` and truncate in revert.
    - *CREATE collision permits redeploy*: CREATE at existing address must REVERT with full gas burn, NOT silent overwrite. EIP-684. **Symptom**: malicious overwrite. **Fix**: check `account.code_hash != KECCAK_EMPTY || account.nonce > 0` pre-checkpoint.
    - *Quadratic journal under deep recursion*: 1024-deep call stack with N entries per frame = O(1024*N) memory. Adversarial contracts can blow heap. **Symptom**: OOM on certain pathological contracts. **Fix**: cap per-frame entries via global gas — gas limit naturally bounds entries, so just ensure `Vec<JournalEntry>` uses `with_capacity(8)` to avoid reallocs; trust gas accounting.
  - **Test scenarios**:
    - A→B(REVERT)→A.continue: A's state pristine, B's logs gone, B's value-transfer reversed.
    - A→B→C(REVERT)→B.continue→B.commit: C reverted, B's other changes committed.
    - 1025-deep call: returns CallTooDeep before any checkpoint pushed; no Vec growth.
    - CREATE at existing code-having address: returns CreateCollision, all parent gas-forwarded gas consumed.
  - **Acceptance**: nested-call trace `notes/revm_nested.md` covers commit-merge, revert-undo, log-truncate, CREATE collision; exec-vm gap list adds `checkpoint_commit` if missing.
  - **Downstream**: W55 (exec-vm checkpoint/commit/revert build); W47-revisit (txn crate's `SAVEPOINT` operates on this exact pattern — inheritance ratio target ≥ 80%); W74+ (matching-engine's deterministic event-log uses per-order checkpoint for adversarial rejection).

**Wednesday — State access patterns**

- [ ] Read state management in revm. (~45 min)
  - **Why**: `State<DB>` is the persistent-data-structure layer wrapping `Database`. It batches per-block changes into a `BundleState` (the COW-style change log) for downstream reorg handling. Understanding it is required for W62 storage-trie integration AND for any state-snapshot work in mini-db (W95+).
  - **Read first**:
    - `crates/database/src/states/state.rs` — `State<DB> { cache, database, transition_state, bundle_state, use_preloaded_bundle, block_hashes }`
    - `crates/database/src/states/cache.rs` — `CacheState { accounts: HashMap<Address, CacheAccount>, contracts: HashMap<B256, Bytecode> }`
    - `crates/database/src/states/bundle_state.rs` — `BundleState { state, contracts, reverts, state_size, reverts_size }`
  - **Design**:
    ```rust
    pub struct State<DB> {
        pub cache: CacheState,                    // in-memory per-block
        pub database: DB,                          // underlying KV (MDBX)
        pub transition_state: Option<TransitionState>, // current-tx deltas
        pub bundle_state: BundleState,            // block-level diff
        pub use_preloaded_bundle: bool,
        pub block_hashes: BTreeMap<u64, B256>,    // EIP-2935 prep
    }

    pub struct BundleState {
        pub state: HashMap<Address, BundleAccount>,
        pub contracts: HashMap<B256, Bytecode>,
        pub reverts: Reverts,                     // per-tx revert log
        // ...
    }
    ```
    **Invariants**:
    - `transition_state` accumulates DURING tx exec; on tx commit, merged into `bundle_state` and cleared.
    - `BundleAccount` distinguishes `original_info` (DB-loaded baseline) from `info` (current). Reorg replay reads `original_info`.
    - Copy-on-write: an account never read from DB has no `CacheAccount`. First read populates lazily.
  - **Build steps** (granular):
    1. (~10 min) Trace SLOAD path through 4 layers: JournaledState (per-tx WIP) → State<DB>.cache (per-block) → bundle_state.contracts (committed) → DB (durable).
    2. (~10 min) Read `BundleState::apply_transitions`: per-tx merge logic. Note `Reverts` is `Vec<Vec<(Address, AccountRevert)>>` — outer Vec indexed by tx-in-block.
    3. (~10 min) Compare COW-via-HashMap to a true HAMT/persistent map: revm chose mutable HashMap + journal log (simpler, faster for unblamed paths, but no structural sharing across forks). Note for mini-db: if you need multi-version snapshots, you need HAMT (W95+).
    4. (~5 min) Read `state_root_with_updates` if present: how BundleState exports `HashedPostState` for trie computation.
    5. (~10 min) Diff exec-vm: W31+ storage-trie owns the trie. exec-vm's state should expose a similar BundleState-like diff for storage-trie consumption.
  - **Pitfalls** (named):
    - *Bundle-merge order*: applying tx-N's transitions before tx-(N-1)'s commit produces wrong reverts. **Symptom**: reorg replay deviates. **Fix**: transitions merge per-tx, in order; `BundleState::apply_transitions_and_create_reverts(transitions, status)` is the only entry point.
    - *contract dedup*: same bytecode deployed at two addresses must dedupe via `code_hash`. **Symptom**: 2× memory. **Fix**: BundleState's `contracts: HashMap<B256, Bytecode>` keyed by hash, not address.
    - *Preloaded bundle stale*: `use_preloaded_bundle = true` reuses bundle from prior block; if block reverts mid-import, must reset. **Symptom**: ghost state. **Fix**: explicit `take_bundle()` between blocks; never reuse implicitly.
  - **Test scenarios**: tx1 writes slot=1, tx2 in same block reads slot=1: tx2 sees tx1's value via transition_state (not from DB).
  - **Acceptance**: 4-layer-cache document; exec-vm gap list adds `BundleState` analogue if missing.
  - **Downstream**: W55 exec-vm journaling; W62 exec-vm × storage-trie BundleState handoff; W95+ mini-db snapshot semantics.

  - **Why**: Drop-in compatibility with revm's `Database` trait lets exec-vm reuse the entire revm tooling ecosystem (test-vector runners, foundry harnesses, reth's MDBX integration) WITHOUT a translation layer. A misaligned trait signature kills future-you's velocity for the entire phase 4-5 stretch.

    // exec-vm/src/host.rs — target shape after refactor:
    pub trait ExecVmHost {
        type Db: Database;  // associated type, NOT generic on Host
        fn env(&self) -> &Env;
        fn db(&mut self) -> &mut Self::Db;

    - associated `type Db` lets downstream pick MDBX or InMemoryDB without trait-object overhead.
    - Method shapes (signature byte-for-byte) match revm's `Host`: `fn sload(&mut self, addr, key) -> Option<StateLoad<U256>>` — `Option` not `Result`; `StateLoad` not bare `U256`.
  - **Build steps** (granular):

    4. (~5 min) Add doc-test: `let _: Box<dyn Host<Db = revm::db::InMemoryDB>> = Box::new(MyExecVmHost::new());`.
    5. (~5 min) Add compile-fail test: differing signature on `sload` rejected.
  - **Pitfalls** (named):
    - *Type-alias drift*: aliasing `pub type Database = MyDb;` instead of re-exporting the TRAIT breaks downstream. **Symptom**: revm crate can't be linked. **Fix**: `pub use revm::primitives::Database;` for the trait, never aliasing the concrete type.

**Saturday — Interpreter loop refactor**

- [ ] Consolidate match-based dispatch from W9 + W17 into `interpreter/dispatch.rs`. Set up W58 jump-table swap. (~45 min)
  - **Why**: W58 plans to A/B match-dispatch vs jump-table vs computed-goto. The bench is only valid if the dispatch primitive is isolated behind a clean module boundary. Doing this consolidation NOW (single-file, all opcodes routed through one entry point) makes W58's swap trivial.
  - **Read first**: revm `crates/interpreter/src/instructions.rs` — the `instruction_table::<H, SPEC>()` constructor.
  - **Design**:
    ```rust
    // exec-vm/src/dispatch.rs
    pub type Instruction<H> = fn(&mut Interpreter, &mut H);
    pub type InstructionTable<H> = [Instruction<H>; 256];

    pub trait Dispatch<H> {
        fn run(&mut self, host: &mut H);
    }

    pub struct MatchDispatch;
    pub struct JumpTableDispatch<H>(pub InstructionTable<H>);

    impl<H: Host> Dispatch<H> for MatchDispatch {
        fn run(&mut self, host: &mut H) {
            // existing match-based loop, lifted from W9/W17 instructions.rs
        }
    }
    ```
    **Invariants**:
    - Single source of truth for opcode semantics: `fn op_add(&mut Interpreter, &mut H)` defined ONCE; both MatchDispatch (via `OpCode => op_add(self, host)`) and JumpTableDispatch (via `table[0x01] = op_add`) reference the same fn.
    - No dispatcher owns gas/stack — those live on `Interpreter`. Dispatch is pure routing.
  - **Build steps** (granular):
    1. (~10 min) Create `exec-vm/src/dispatch.rs`; declare `Dispatch` trait + `MatchDispatch` impl.
    2. (~15 min) Migrate `interpreter::run`'s match-arm body into `MatchDispatch::run`. Confirm all opcodes route through the same per-fn pattern.
    3. (~10 min) Make each opcode a standalone `fn op_xxx<H: Host>(&mut Interpreter, &mut H)` — feed-forward for W58 jump-table.
    4. (~5 min) `cargo bench --bench opcode_throughput`: confirm no perf regression (within 1σ noise).
    5. (~5 min) Add module doc: "W58 will introduce `JumpTableDispatch`; no changes to op_* fns needed."
  - **Test scenarios**: existing W17 opcode-suite runs green; bench harness still produces stable numbers.
  - **Acceptance**: all opcodes implemented as free `fn op_xxx<H>(...)`; one `MatchDispatch` impl; W58 stub TODO comment added.
