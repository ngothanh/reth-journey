  - *Mental model*: a circuit breaker is a per-symbol finite state machine (`Trading → Limit → Halt → Auction → Trading`) gated by a rolling reference price; it exists to convert a fat-finger / flash-crash cascade into a survivable pause. It runs on the same hot path as order matching, so every per-trade operation must be O(1) and float-free.
  - *Contract*:
    ```rust
    pub enum BreakerState { Trading, Limit { since_seq: u64 }, Halt { until_seq: u64 }, Auction }
    pub struct CircuitBreaker { /* per-symbol */ }
    impl CircuitBreaker {
        pub fn new(band_bps: u32, window: Duration, min_samples: u32) -> Self;
        /// Called once per trade on the matching hot path. Returns the post-trade state.
        pub fn on_trade(&mut self, price: u64, seq: u64, ts: MonotonicNanos) -> BreakerState;
        pub fn reference(&self) -> u64;       // current rolling reference price, integer
        pub fn band(&self) -> (u64, u64);     // (lower, upper) absolute price bounds, integer
    }
    ```
    Never write the body in Phase 1 — only the signatures + trait bounds (`time::MonotonicNanos`, no `SystemTime`).
  - *Back-of-envelope*: matching engine target ~1M trades/s/symbol-shard; per-trade budget for the breaker check ≤100 ns (it shares the budget with the match itself). A naive `samples.iter().sum()` over a 100-sample window = ~100 elements × (load ~7ns L2 + add) ≈ 300+ ns per trade — already 3× over budget, and at 1M/s that is ~300 ms of CPU per wall-second spent re-summing. Incremental running-sum maintenance is ~2 loads + 1 add + 1 div ≈ 5 ns. Cliff ratio: ~300 ns re-sum vs ~5 ns incremental = **60× per trade**. Float division (`10-30 cyc` ≈ 3-10 ns) additionally costs determinism, not just time.
  - **Requirements** R1..R8 — write in `crates/matching-engine/notes/81_circuit_breaker_design.md`:
    - R1. Reference is a rolling aggregate over the configured window (adapts to trend, not frozen at session open).
    - R2. Limit-state is a soft warning; a *sustained* 15s at-or-beyond-band → `Halt` fires (not a single tick).
    - R3. `Trading → Limit → Halt → Auction → Trading` transitions are deterministic and total (no implicit states).
    - R4. ALL band/reference math is integer (bps via u64): `band = ref * bps / 10_000`, round half-to-even. No `f64` anywhere on the path.
    - R5. `on_trade` ≤100 ns P99 on the hot path.
    - R6. Same trade stream → byte-identical halt sequence across 3 replicas and across x86_64/aarch64 (10k random scenarios).
    - R7. The rolling aggregate is maintained incrementally (running sum + count), NOT re-aggregated per trade.
    - R8. Minimum-sample gate: below `min_samples` (e.g. 5) in window, fall back to a long-term reference (prior session close); do not apply a tight band to sparse data.

      | `VecDeque<(seq, u64)>` + running_sum | O(1) ~5ns | 0 | ok if integer | evict-front, push-back |
      | f64 EWMA | O(1) ~5ns | 0 | **fails R4/R6** | float divergence |
      | median over window | O(log N) | 0 | ok if integer | robust to spikes; more cost |
    - D3. **Dx. Pre-mortem (load-bearing — compute_mean re-sums entire window):** write the 4-5 line trace: `on_trade` → `compute_mean` → `samples.iter().map(|(_,px)| px).sum::<u64>() / count` → at N=100 that is 100 loads + adds + a cold-cache walk on the ring → ~300 ns × 1M trades/s = ~300 ms/wall-s spent summing. If you can't see why this re-walks the whole window every single trade, you can't see why R7 demands incremental maintenance.
    - D4. **Pre-mortem (float drift in bps math):** `band = ref as f64 * bps as f64 / 10_000.0` → IEEE-754 rounding differs by compiler/arch → replica A halts at trade 5012, replica B at 5013 → the deterministic SM diverges and consensus rejects.   #### Phase 3 — Make the tests pass, one failure at a time (~140 min)

  Newbie failures first, expert last.

  - **(NEWBIE) When `breaker_single_tick_above_band_does_not_halt` reports `Halt` after one tick:**
    - Symptom: a single trade above the band immediately returns `Halt`.
    - Why: the FSM halts on the band-breach predicate directly instead of on a *sustained* duration in `Limit`.
    - Fix: `Halt` only when `now - limit.since >= 15s` while continuously at/over band; recover to `Trading` if price re-enters band before then.
    - Cost avoided: spurious halts on ordinary single-print spikes (kills the venue's continuous market).
    - Muscle: a breaker is a *dwell-time* FSM, not a level comparator — separate "at limit" from "halted." Reapplies at: W78 auction trigger dwell, W90 consensus-vsr view-change timeout (sustained-not-instant), W108 ops-chaos alert debounce.

  - **(SENIOR) When `breaker_min_sample_threshold_low_volume` reports a spurious trip:**
    - Symptom: a low-volume symbol (1-2 samples) trips on a 1% move.
    - Why: the reference is recomputed from 1-2 samples, so the band is essentially `last_px ± tiny`; ordinary spread fills breach it.
    - Fix: gate on `count >= min_samples`; below it use the long-term reference (prior session close), not the tight current window.
    - Cost avoided: nuisance halts on illiquid names (operational + regulatory cost).
    - Muscle: rolling-window primitives need a sample-count gate; sparse data needs a fallback path. Reapplies at: W77 flow-control under low traffic, W82 Image rx-rate under low volume, W110 perf metrics on cold symbols.

  - **(EXPERT) When `breaker_slow_grind_one_directional_still_trips` stays `Trading` through a 22% climb:** (reference-drift trap from D5)
    - Symptom: 20 trades each +1% climb the price ~22% total, but the final state is `Trading` — the breaker never trips on the exact slow cascade it exists to catch.
    - Why: a *mean* (or EWMA) reference chases the price one step behind, so the upper band rises with it and the per-trade `px` is always inside `(ref, ref·(1+bps))` — never breached.
    - Fix: cap the reference move-rate (±2%/window) or use a median reference; the band must lag the move, not track it. A slew-capped reference falls behind the grind within a few steps and the climbing `px` breaches it.
    - Cost avoided: the breaker silently fails to catch the exact slow-cascade it exists for — a flash-crash-by-a-thousand-cuts runs to completion unhalted.
    - Muscle: a reference that adapts as fast as the signal it guards is no guard — bound its slew rate. Reapplies at: W82 Image rx-rate EWMA slew, W110 adaptive perf thresholds.

  - **(EXPERT, perf — bar (c) violation) When `breaker_per_trade_check_under_100ns` reports ~300 ns/trade:**
    - Symptom: bench shows ~300 ns/trade; flame graph attributes it to `compute_mean` re-summing the window; `breaker_compute_mean_is_incremental_not_resum` shows the 1M window costs ~100× the 8 window.
    - Why: `self.samples.iter().map(|(_,px)| px).sum::<u64>() / count` is O(N) per trade — ~100 loads + a cold ring walk.
    - Fix: maintain `running_sum: u128` (`+= px` on push, `-= evicted` on evict); `mean = (running_sum / count) as u64` is O(1) ≈ 5 ns.
    - Cost avoided: ~295 ns/trade × 1M trades/s ≈ **~295 ms of CPU per wall-second** — disqualifies the breaker from the matching hot path (bar (c) violation).
    - Muscle: any rolling-window aggregate queried per-event is maintained incrementally — never re-aggregate inside a hot loop. Reapplies at: W77 flow-control rolling sum, W82 Image rolling rx-rate, W83 archive rolling write-rate, W84 deterministic-harness rolling event-count.

  - **(EXPERT, determinism — bar (c) violation) When `breaker_replica_determinism_x_arch` reports divergent halt-seq:**
    - Symptom: 3 in-process runs match, but the x86_64 golden hash ≠ the aarch64 CI hash; replicas halt at different seqs.
    - Why: `band = ref as f64 * bps / 10_000.0` introduces IEEE-754 rounding that differs by arch/FMA-contraction.
    - Fix: integer-only `band = ref * bps / 10_000` (u128 intermediate, round half-to-even); ban `f64` from the module (`#![forbid(...)]`-style review note + a grep test).
    - Cost avoided: a non-deterministic state machine — consensus/replication rejects the diverging replica (silent split-brain). (bar (c) violation: determinism is the crate's contract.)
    - Muscle: deterministic state machines forbid floats and wall-clocks on the decision path. Reapplies at: W78 auction tie-break, W80 ledger SM, W83 ledger v0.5, W87 VOPR, W90 consensus-vsr.

  - **(EXPERT, cross-primitive) When `breaker_halt_expires_triggers_auction_then_resume` lets a stop fill into a halted book:** (halt/stop-ladder race from D6)
    - Symptom: under composition with the order book's `stop_ladder`, a stop triggered the same tick as `Halt` produces a fill while `Halt`.
    - Why: `Halt` set the breaker state but did not freeze the stop ladder; the ladder's triggered orders still flowed to matching.
    - Fix: on `Halt` entry, freeze `stop_ladder`; convert pending triggers to orders *queued for the reopening auction*, not live market orders.
    - Cost avoided: an executed trade during a regulatory halt (an actual rule violation, not just a bug).
    - Muscle: a state that gates one component must gate every component reading shared state on the same tick — halt is global, not local. Reapplies at: W82 v1.5 SHIP halt-resume, W84 full-stack integration halt propagation.

    ```rust
        pub fn change_source(&mut self, new_source: Ipv4Addr) -> io::Result<()>; // control-plane only, NOT hot-path failover
        pub fn ssm_active(&self) -> bool; // false if downgraded to ASM (IGMPv2)
    }
    pub struct AbFeed { a: SsmSubscription, b: SsmSubscription } // both live, dedup by seq
    ```
  - *Back-of-envelope*: kernel hashes the (group, source) tuple against the socket's include-list per received packet — ~50 ns L1-resident for a single-source filter, ~10 ns to drop a mismatch. Without SSM (ASM): the subscriber receives every source and filters in userspace — at 10M unwanted pps × ~3 µs receive+drop = ~30 s of CPU per wall-second (impossible — >100% CPU). Cliff: SSM is the difference between handling 1 feed and being buried under 10 on a shared group. Failover via `leave`+`join`: ~3-5 ms IGMPv3 reconvergence — at 1M pps that is **~3,000-5,000 packets dark** per failover. Therefore failover must be pre-staged (parallel A/B), not control-plane.
  - **Requirements** R1..R6 — write in `crates/messaging-aeron/notes/81_ssm_design.md`:
    - R1. `join` rejects a group outside `232.0.0.0/8` (IETF SSM reservation) — outside that range it isn't SSM.
    - R2. Source filtering happens in the kernel; userspace never sees off-source packets.
    - R3. `ssm_active()` reports `false` (loudly + a metric) if the platform/switch downgraded to ASM (IGMPv2), never silently.
    - R4. `change_source` is a control-plane op (first connect / operator swap) — NOT the steady-state failover path.
    - R5. A/B failover is pre-staged: two parallel `SsmSubscription`s, app-layer dedup by sequence, primary-pointer swap on loss — zero dark time.
    - R6. SSM provides source-*plausibility*, not authentication; spoofed source IPs pass the filter (document the limit; layer MACsec/encryption for integrity).
  - **Design walk-through** D1..D4:
    - D1. Sketch `SsmSubscription` + `AbFeed`. Where does dedup state live?
    - D2. **Primitive table**: `join_multicast_v4_with_source` (SSM) vs `join_multicast_v4` (ASM) vs userspace filter — Sync? per-pkt cost? spoof-resistant? affordable at 10 sources?
    - D3. **Dx. Pre-mortem (load-bearing — failover gap):** trace the bad sequence: A-feed loss detected at seq N → `leave(A)` → IGMPv3 leave/join roundtrip with switch (~3-5 ms) → `join(B)` → during the gap, **zero** packets arrive → at 1M pps ~5k messages lost → consumer's loss-detector fires a NAK storm on resume → reorder buffer overflows. This is why R5 demands pre-staged parallel feeds.
    - D4. **Dy. Anti-shortcut audit:** (a) `leave`+`join` for failover → multi-ms dark gap, fails R5 (bar (c) violation); (b) plain `join_multicast_v4` (ASM) "because it's simpler" → no source filter, fails R1/R2 and invites spoofing; (c) trusting the join succeeded without checking `ssm_active()` → silent ASM downgrade, fails R3.

    ```rust
    pub struct JournaledStateMachine<S: StateMachine> { wal: Wal, sm: S, next_seq: u64 }

        pub fn apply(&mut self, op: Op) -> Result<S::Output>; // wal append+fsync BEFORE sm.apply
    ```

    - Symptom: ~8k ops/s; `iostat` shows fsync queue-depth 1; `vmstat` shows idle CPU.
    - Why: `append; fsync()` per op — one 100 µs NVMe fsync per op caps throughput at 10k ops/s with the CPU idle.
    - Fix: group commit — accumulate 32 ops OR 100 µs, one `append_batch + fsync` covers the batch; results held in a pending queue until the batch fsync completes; pipeline the next batch against the in-flight fsync.
    - Cost avoided: ~100 µs/op → ~3 µs/op amortized = ~30× throughput. (bar (c) violation: misses the P99 budget.)
    - Muscle: every durability primitive on a bar (c) hot path uses group commit. Reapplies at: W80 FIX seq-out persistence, W83 archive recorder fsync policy, W92 ledger v1.0 io_uring fsync batching.

  - **(EXPERT, perf — bar (c) violation) When `journal_no_alloc_on_apply_hot_path` reports nonzero allocs:**
    - Symptom: dhat shows ~1 alloc/op attributed to the journal write; the allocator arena lock dominates `perf`; throughput plateaus ~300k ops/s.
    - Why: `bincode::serialize(&rec)?` returns a fresh `Vec` per op.
    - Fix: `wal::Sequencer::reserve(size) -> &mut [u8]`; `bincode::serialize_into(&mut slot, &rec)?`; compute crc32c in-place on the slot bytes. For v1.0 the slot lives in an io_uring-registered buffer.
    - Cost avoided: ~50 ns/op × 1M ops/s = ~50 ms/wall-s + allocator contention. (bar (c) violation: allocation on the hot path.)
    - Muscle: durability writes claim a pre-allocated slot and serialize in place — never serialize-then-append. Reapplies at: W77 IPC transport, W79 MBO publish, W83 archive recorder, W92 ledger v1.0.

  - **(SENIOR, perf — bar (c) violation) When `journal_recovery_throughput_10x_apply_no_fsync` reports equal speed (or nonzero fsync/append):**
    - Symptom: a 1M-op ledger takes minutes to recover; `CountingFsyncWal` shows fsyncs/appends during recovery; failover SLA blown.
    - Why: the recovery loop calls `sm.apply; wal.append; wal.fsync` per op — it treats replay like fresh apply.
    - Fix: recovery is read-only — just `sm.apply(op)` per record, no append, no fsync. Assert `fsync_count == 0 && append_count == 0` during recovery.
    - Cost avoided: ~100 µs/op → ~120 ns/op = ~800× speedup; recovery drops from minutes to ~120 ms. (bar (c) violation: failover SLA.)
    - Muscle: replay/recovery paths skip durability — the data is already durable in the source; recovery is a read-only sweep of apply logic. Reapplies at: W84 archive replay, W87 VOPR recovery, W88 consensus-vsr follower catch-up, W92 ledger v1.0 recovery.
