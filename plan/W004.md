  - *Mental model*: pad any `T` up to the target's cache-line size so adjacent `CachePadded<T>` never share
    a line. Used wherever two threads write to neighboring atomics — false sharing eats lock-free
    throughput.

  - *Back-of-envelope*: false-sharing a producer/consumer counter pair regresses MPMC throughput **30-70%**
    under contention (head + tail in the W11 Vyukov ring). One `CachePadded<AtomicU64>` costs 120 B on
    aarch64-apple-darwin (8 B payload + 120 B pad) or 56 B on x86_64-linux — paid once at construction,
    recovered every microsecond of runtime. Cache-coherency traffic on a contested line: ~7 ns L2 fetch per
    MESI invalidation; the fix is to separate the lines, not "be cleverer" with atomics. LMAX Disruptor
    paper: 26M ops/s padded vs 5.3M unpadded for 1P-1C unicast on x86_64 (~4.9× cliff).

  - **Requirements** — write in `crates/concurrent/notes/04_cache_padded_design.md`:
    - R1. `pub struct CachePadded<T> { value: T }` wrapped with `#[repr(C, align(N))]` where N is
      target-dependent: 128 on aarch64-apple-darwin, 64 on x86_64-linux. The `align` MUST be `cfg`-gated.
    - R2. `Deref<Target = T>` + `DerefMut<Target = T>` so callers write `*counter.fetch_add(1, …)` not
      `*counter.value.fetch_add(…)`.
    - R3. `CachePadded::new(value)` const fn (W11 MPMC needs `const fn` ring construction).
    - R4. `unsafe impl<T: Send> Send` + `unsafe impl<T: Sync> Sync` (passthrough — wrapper adds no extra
      access).
    - R5. The padded SIZE is `mem::size_of::<CachePadded<T>>() == N` whenever `size_of::<T>() ≤ N`. A type
      `T` larger than `N` must still align to `N` but does not shrink.
    - R6. Documented anti-shortcut: a doc comment naming three reaches that DON'T work — `Box<T>` (allocator
      doesn't promise cache-line alignment), `[u8; 64]` field for hand-padding (`repr(Rust)` may reorder),
      `std::cell::UnsafeCell<T>` (no padding at all). Reader needs to know what the wrapper does that the
      reach doesn't.

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)

  Read each card *after* you've seen the failure. Each card describes the exact symptom + why + fix +
  cost-avoided + muscle. The order below is **newbie failures first, expert failures last** — match the
  ladder you'll actually walk.

  - **(NEWBIE) When `cache_padded_align_matches_target` reports `expected 128, got 64` on aarch64:**
    - Symptom: assertion fails on aarch64-apple-darwin with `assertion left == right failed: left: 64,
      right: 128`.
    - Why: you used `#[repr(align(64))]` hardcoded — the textbook x86 cache-line value. On Apple Silicon
      the L2 prefetcher pulls **128-byte pairs**, so adjacent counters at 64 B still false-share.
    - Fix: cfg-gate the constant:
      ```rust
      #[cfg(target_arch = "aarch64")] #[repr(C, align(128))] pub struct CachePadded<T> { value: T }
      #[cfg(not(target_arch = "aarch64"))] #[repr(C, align(64))] pub struct CachePadded<T> { value: T }
      ```
      Yes, two struct definitions gated by cfg. The `align` attribute takes a literal, not a constant.
    - Cost avoided: ~30% throughput on contested head/tail on aarch64; on x86, ~50% wasted L1 budget per
      counter if you over-pad to 128.
    - Muscle: cache-line size is a target-dependent constant — never hardcode one platform's value, never
      pad past the target's line width. Reapplies at: W11 MPMC head/tail cursor pair, W58 matching-engine
      `PriceLevel` best/bid pair, W65 Disruptor claim/cursor pair, W77 messaging-aeron term rotation
      counters.

  - **(SENIOR) When `cache_padded_pins_offset_in_struct` reports `Pair.b at offset 8` instead of ≥64:**
    - Symptom: assertion fails — your `CachePadded<AtomicU64>` declared `align(128)` correctly, but
      `offset_of!(Pair, b)` is 8 (i.e., `b` is packed right after the 8-byte `value` of `a`, ignoring the
      120-byte tail padding).
    - Why: the enclosing `struct Pair` is `repr(Rust)`. Rust is free to reorder + omit padding between
      fields; it puts `b` at offset 8 because that's the next aligned position. The `align(128)` on
      `CachePadded` controls the *outer* type's alignment when placed standalone, but inside a
      `repr(Rust)` struct the compiler can pack regardless.
    - Fix: add `#[repr(C)]` to every struct where padding is load-bearing. `repr(C)` forces declaration
      order + standard C padding rules — the trailing pad on `a` now exists in the struct, pushing `b` to
      offset 128.
    - Cost avoided: silent re-introduction of false sharing (the 30-70% regression returns); test-suite
      green, criterion bench-diff RED — caught only by the perf test, never by `cargo test`.
    - Muscle: when padding is load-bearing, lock the layout — `repr(C)` is non-negotiable on any struct
      whose fields' relative positions matter. Reapplies at: W11 MPMC ring struct (head + tail + ring),
      W58 matching-engine order book multi-counter struct, W77 aeron term metadata, W65 Disruptor
      sequencer/cursor pair, every load-bearing layout-pin assertion in the codebase.

  - **(SENIOR) When `cache_padded_pins_offset_under_repr_rust_FAILS_TO_COMPILE` succeeds (compiles
    cleanly):**
    - Symptom: `trybuild` reports the test compiled — you expected a compile error from the const-assert.
    - Why: you never added the const-assert, OR you added it but in the wrong place (inside the struct
      definition where `offset_of!` can't see the full struct yet). The compile-fail discipline is
      aspirational without the actual `const _: () = assert!(...)` line.
    - Fix: every layout-load-bearing struct gets a sibling `const _: () = assert!(offset_of!(S,
      last_hot) - offset_of!(S, first_hot) >= CACHE_LINE);` after the struct declaration. Place it in the
      same module so it runs in const eval at every build.
    - Cost avoided: the senior failure above slipping into a release build — `cargo test` green, perf
      bench RED, debugging session takes a day instead of a compile error.
    - Muscle: a type-system invariant exists ONLY when a const-assert (or compile_fail test) proves it. No
      invariant without proof. Reapplies at: W11 MPMC ring offset-pin, W58 matching-engine layout-pin,
      every `repr(C)` decision documented as a const-assert.

  - **(NEWBIE→SENIOR) When `cache_padded_deref_compiles_naturally` passes but the bench code is full of
    `.inner()` calls:**
    - Symptom: tests green, ergonomics rotten. The bench's hot path reads `counter.inner().fetch_add(1,
      Relaxed)` instead of `counter.fetch_add(1, Relaxed)` — a clue you shipped an accessor instead of
      `Deref`.
    - Why: you wrote `pub fn inner(&self) -> &T { &self.value }` because it felt like a normal Rust API.
      It IS a normal API; it's just one that makes every hot-path call site 40% longer.
    - Fix: `impl<T> Deref for CachePadded<T> { type Target = T; fn deref(&self) -> &T { &self.value } }`
      and likewise `DerefMut`. Remove `.inner()`. Re-run the bench — call sites collapse.
    - Cost avoided: no perf cost, but every downstream consumer pays the keystroke tax forever. The cost
      is in your future-week velocity.
    - Muscle: when a single-field wrapper exists ONLY to add a layout property, use `Deref` so the
      wrapper is invisible at the call site. Reapplies at: every Layer-1 wrapper primitive (W4 Sealed<T>,
      W11 type-state Block, W42 LockGuard).

  - **(EXPERT) When `cache_padded_bare_pingpong_regresses_no_less_than_3x` reports ratio = 1.0±0.1:**
    - Symptom: bench says padded is the same speed as bare. Threshold (≥3×) fails. You think the wrapper
      is broken; it's not.
    - Why: option (a) — you forgot `repr(C)` on `PaddedPair`; padding got reordered (re-run the offset
      test). Option (b) — both threads landed on SMT siblings of the same physical core; they share L1, no
      MESI ping-pong, no cliff to measure. Option (c) — you tested both `fetch_add` calls targeting the
      same atomic (e.g. `pair.a` in both threads); both arms now measure the same uncontested op.
    - Fix: (a) `repr(C)` and re-run the offset test; (b) `core_affinity` crate or document the
      requirement; (c) print `&pair.a as *const _ as usize` and `&pair.b as *const _ as usize` from each
      thread — they MUST differ.
    - Cost avoided: shipping a "padded" claim that's actually measuring nothing.
    - Muscle: a perf bench whose two arms differ by one type wrapper MUST include a layout assertion +
      thread placement check; otherwise the cliff measurement silently lies. Reapplies at: W11 MPMC
      head/tail bench, W58 matching-engine L1 publish bench, W65 Disruptor sequence bench, W77 aeron term
      rotation bench.

  - **(EXPERT) When `cache_padded_bench_physically_plausible_negative_control` reports ops/sec ≥ 10^9:**
    - Symptom: bench claims 5 × 10^9 ops/sec — physically impossible (best L1 atomic is ~3 ns/op =
      3 × 10^8/sec). The perf test above reported a green ratio because both arms got elided to the same
      nothing.
    - Why: `fetch_add` results aren't observed; LLVM proves the counter is dead and removes the work.
    - Fix: `black_box(counter.fetch_add(1, Relaxed))` and assert at end-of-bench that `counter.load() ==
      expected_per_thread * thread_count`. The end-state assertion forces the writes to be observed.
    - Cost avoided: shipping a perf claim built on a bench that measures nothing. The worst class of perf
      bug — silently green, silently meaningless.
    - Muscle: every microbench gets a sanity-range negative control. If the numbers are physically
      impossible, the bench is broken — don't trust the ratio. Reapplies at: every criterion bench in
      `concurrent/`, every matching-engine hot-path bench from W58.

  - **(EXPERT, deferred) When `cache_padded_cross_primitive_inside_seqlock_separates_seq_from_payload`
    fires on Tuesday after building ChainHead:**
    - Symptom: Monday's CachePadded tests all green. Tuesday's ChainHead build composes `struct ChainHead
      { seq: CachePadded<AtomicU64>, payload: (B256, u64) }`. The cross-primitive test fires:
      `seq_addr.abs_diff(payload_addr) = 8`.
    - Why: ChainHead is `repr(Rust)` and the compiler reordered `payload` to right after `seq.value`
      ignoring the 120 B tail. The Monday primitive is correct in isolation; the Tuesday composition is
      where the lesson lands.
    - Fix: `#[repr(C)] struct ChainHead { … }`. Re-run; the test now passes. The senior failure repeats
      ONE LEVEL UP — the lesson Monday taught for CachePadded reapplies to every struct that contains
      CachePadded.
    - Cost avoided: another silent false-sharing regression hidden behind correct unit tests, only
      detectable under contention.
    - Muscle: layout invariants are transitive — if `CachePadded` is `repr(C, align(N))`, every struct
      that holds a `CachePadded` field must also be `repr(C)` for the alignment to matter. A wrapper's

  - **(NEWBIE) When `cache_padded_anti_shortcut_box_does_not_pad` (ignored demo) fails to find a

    - Symptom: you ran the demo manually expecting at least one Box pair within 64 B; closest pair was

  - **When `chain_head_load_never_returns_torn_pair_under_contention` reports a torn pair after a few
    seconds:**
    - Symptom: panic with `torn pair: observed (hash_X, number_Y), legal set […]` where the hash is
      from one tuple and the number from another.
    - Why: your reader copies the payload but doesn't re-check the seq counter after the copy. The
      writer's update straddled the read window; nothing rejected the torn copy.
    - Fix: reader implements the full 5-step dance: (1) load seq (Acquire); (2) odd→retry; (3) copy
      payload; (4) load seq (Acquire); (5) compare with step 1, retry on mismatch.
    - Cost avoided: silent consensus bugs ("impossible tips" that show up at 1 in 10^7 reads — rare,
      load-dependent, "can't reproduce in dev").
    - Muscle: a SeqLock makes a multi-word read *appear* atomic via retry, not via locking. The
      retry is mandatory. Reapplies at: W58 matching-engine L1 best-bid/ask, W77 messaging-aeron
      term rotation, W65 Disruptor cursor.

      `compiler_fence(Acquire)` between the first seq read and the payload load to pin the order.

      backoff. Under a hot writer, the seq is perpetually changing; the reader's tight loop never
      converges and burns 100% CPU.
    - Fix: drive the retry loop with a `Backoff` (built later today): `let backoff = Backoff::new();
      loop { … if seq2 == seq1 { return; } backoff.spin(); }`. After ~10 spins, Backoff escalates
      to `yield_now`, giving the writer a chance to complete a cycle.

    - Muscle: SeqLock removes reader blocking, not writer exclusivity, and the payload itself must
      be race-free. Reapplies at: W58 matching-engine single-writer L1, W65 Disruptor single-producer

    yield the scheduler (~1-10 µs context switch — give the lock-holder a chance to make progress),
    then park (futex/condvar, ~300 ns + wakeup latency). Every lock-free retry loop drives a

    then yield, then park. A spin that burns past ~1 µs has lost — the lock-holder almost certainly
    isn't on the same core; yield.

  - **When `parker_park_actually_blocks_until_unpark` reports `park returned in <1ms`:**
    - Symptom: assertion `park_elapsed >= Duration::from_millis(40)` fails; spawned thread's park
      returned in single-digit milliseconds instead of waiting the full 50 ms before unpark fires.
    - Why: most likely bug #2 — `park` does `swap(PARKED, …)` and then calls
      `atomic_wait::wait(&state, EMPTY)`. After the swap, state IS PARKED, not EMPTY. The futex's
      value-check sees state ≠ expected and returns *immediately without sleeping*. park returns,
      consumer thinks it was unparked, in reality it just bypassed the syscall entirely. (Less
      common: missing wait call altogether.)
    - Fix: gate `wait` on the value state is ACTUALLY at, not what you wish it was — after a CAS
      to PARKED, the call must be `atomic_wait::wait(&state, PARKED)`. The futex now correctly
      blocks until state changes away from PARKED.
    - Muscle: futex_wait's expected-value argument must match the atomic's current value at
      entry — pass the value you JUST stored, not the value you started from. Reapplies at: W26
      WAL ack wait, W11 MPMC `recv` block, every futex-based primitive.

  - **When `parker_park_unpark_cycles_repeatable` fails on cycle 1 (cycle 0 passes, cycle 1+ returns
    instantly):**

      assertion fails with `cycle 1 returned in 0ms — state machine didn't reset`.
    - Why: park used `swap(PARKED, …)` instead of CAS. On cycle 0 (state=EMPTY → swap → state=PARKED,
      previous was EMPTY, wait → block → wake → return without resetting state). State is left as
      PARKED. On cycle 1, swap(PARKED) on PARKED returns PARKED → matches the "already parked"
      arm → returns instantly. State machine is one-shot, not repeatable.
    - Fix: (a) `park`'s first op is CAS `EMPTY → PARKED`, not swap — preserves NOTIFIED if pre-set,
      and never silently re-publishes PARKED. (b) After consuming a wake, `park` must `store(EMPTY)`
      to reset state — otherwise the next park sees stale PARKED.
    - Muscle: a state machine that isn't explicitly reset will get stuck in its terminal state. CAS
      preserves information; swap destroys it. Reapplies at: W11 MPMC slot state machine, W26 WAL
      frame state, W42 LockManager waiter.

  - **When `parker_unpark_before_park_is_consumed_then_blocks_next_cycle` fails on the second park:**
    - Symptom: first cycle (pre-notify + park) returns instantly as expected; second cycle's

      NOTIFIED. Second park's `swap(PARKED)` finds state already PARKED, returns instantly.
    - Fix: same as above (CAS, then store EMPTY on consume).

      reordered AFTER the NOTIFIED store. Consumer wakes, reads NOTIFIED, reads payload — but
      payload's write hasn't propagated yet.
    - Fix: change `swap(NOTIFIED, Ordering::Acquire)` → `swap(NOTIFIED, Ordering::Release)` (or
      `AcqRel` if you also need to acquire consumer-side writes — for Parker, you don't). The
      Release flushes prior writes before NOTIFIED becomes visible; consumer's Acquire on the
      load pairs to establish happens-before.
    - Muscle: an unpark/notify primitive's *store* of the wake signal must be Release for the
      consumer's reads of producer data to be valid. Acquire on a swap leaves the store Relaxed

    - Fix: `park` is internally a loop. After the syscall returns, re-load `state`. If `NOTIFIED`,

      when zero were expected.
    - Why: `unpark` unconditionally calls the wake syscall even when state is EMPTY (no one parked).
    - Fix: `unpark`'s first op is CAS `EMPTY → NOTIFIED`. If the previous state was EMPTY, no consumer
      was parked; return — no syscall. Only if previous was PARKED do you transition PARKED → EMPTY and
      call the wake syscall.
    - Cost avoided: ~295 ns/op (60× cliff); at 1 M unparks/sec that's ~300 ms/sec on hot producers.

    - Why: `unpark`'s CAS doesn't distinguish "wake a parked consumer" from "leave a notification for
