- [ ] **Build**: `crates/eth-primitives/src/atomic_hash.rs` — OnceLock<B256> lazy hash cache. `Sealable` trait. (~75 min)
  - *Mental model*: a block header's `keccak256` hash is expensive (~1µs) and immutable once the header is fixed.
    Compute it once, on first request, and cache it — every later `.hash()` is a pointer-load. This is reth's
    `SealedHeader` pattern: the hash is a memoized property, not a stored field.
  - *Contract*: `Sealable` is a trait with `fn hash_slow(&self) -> B256` (the actual keccak, named `_slow` to flag
    cost) and a provided `fn hash(&self) -> B256` that reads-or-fills a cache. The cache itself is a
    `OnceLock<B256>` field on the wrapper type; `get_or_init` runs `hash_slow` exactly once across all threads.
  - **Expect to hit #1 — caching a mutable value**: you put `OnceLock<B256>` on a type whose fields can still
    change after sealing. Symptom: `.hash()` returns a hash that no longer matches the (now-mutated) contents — a
    silent consensus bug, no panic.
    - Fix: only cache on a type that is immutable-by-construction (the `Sealed`/`SealedHeader` wrapper, W4 Wed);
      never expose `&mut` to the wrapped value.
    - Muscle: memoize only what is immutable; a cache over mutable state is a correctness bug. Reapplies at: W4 Wed
      `Sealed<T>`, W6 `SealedHeader`.
  - **Expect to hit #2 — `OnceCell` instead of `OnceLock`**: you reach for `once_cell::Cell` / `std::cell::OnceCell`,
    which is `!Sync`. Symptom: the header type stops being `Sync`; sharing a `SealedHeader` across threads fails to
    compile (`OnceCell<B256>` is not `Sync`).
    - Fix: use `std::sync::OnceLock` (thread-safe, `get_or_init` is internally synchronized) for any cache on a
      shared type.
    - Muscle: a lazy cache on a `Sync` type must use a `Sync` cell. Reapplies at: W4 Wed `Sealed<T>`, W11 type-state
      header.
- [ ] **Build**: `crates/eth-primitives/src/chain_head.rs` — `ChainHead { hash, number }` protected by SeqLock. (~75 min)
  - *Mental model*: the canonical chain tip (`hash` + `number`) is written by exactly one thread (the engine) and
    read constantly by many (RPC, peers). A `SeqLock` lets readers run fully lock-free: they snapshot the data and
    re-check a sequence counter; if a write straddled the read, they retry. No reader ever blocks a writer.
  - *Contract*: `ChainHead` holds an `AtomicU64` sequence counter plus the two payload fields. Writer:
    `fn store(&self, head: (B256, u64))`. Reader: `fn load(&self) -> (B256, u64)`. The sequence is even when stable,
    odd mid-write.
  - *SeqLock, roughly*: writer — (1) bump seq to odd (`Release`); (2) write payload fields; (3) bump seq to even
    (`Release`). Reader — (1) read seq (`Acquire`); (2) if odd, retry; (3) copy payload; (4) read seq again
    (`Acquire`); (5) if it changed, retry. Getting the fences right so step 3-of-reader can't be reordered around
    the seq reads is the real exercise.
  - **Expect to hit #1 — torn read of multi-word payload**: `hash` is 32 bytes, `number` 8 — they can't be read
    atomically as one unit, so a reader can see a new `hash` with an old `number`. Symptom: occasional
    impossible tips (a hash from block N paired with number N-1); rare, load-dependent, "can't reproduce."
    - Fix: that is exactly what the seq counter catches — re-read seq *after* copying the payload and retry on any
      change; never trust a payload copy that straddled a seq bump.
    - Muscle: a SeqLock makes a multi-word read *appear* atomic by retry, not by locking. Reapplies at: W58
      matching-engine L1 best-bid/ask, W77 messaging-aeron term rotation.
  - **Expect to hit #2 — payload load hoisted above the seq read**: with `Relaxed` ordering (or no fence) the
    compiler/CPU reorders the payload reads to *before* the first seq read, so the validation window doesn't
    actually cover the copy. Symptom: torn reads slip through even though the retry logic "looks correct"; miri/loom
    flags a data race.
    - Fix: first seq read is `Acquire`, second seq read is `Acquire`, writer's seq bumps are `Release`; the payload
      copy is fenced between two `Acquire` loads. Consider `compiler_fence`/`fence(Acquire)` to pin the order.
    - Muscle: a SeqLock is correct only if the payload access is provably fenced *between* the two seq reads.
      Reapplies at: W58 L1 publishing, W65 Disruptor cursor.
  - **Expect to hit #3 — writer not exclusive / non-atomic payload writes**: two writers race, or the payload
    fields are plain (non-atomic) and written while a reader copies them — that copy is a data race even with the
    seq dance. Symptom: UB; miri/loom reports a data race on the payload bytes themselves.
    - Fix: SeqLock assumes a *single* writer (enforce it — `&mut self` writer or a guard); store payload in
      `AtomicU64`s / `AtomicU32`s (or use `MaybeUninit` + atomic-fenced copy) so the read-side copy is not UB.
    - Muscle: SeqLock removes reader blocking, not writer exclusivity, and the payload itself must still be
      race-free. Reapplies at: W58 matching-engine single-writer L1, W65 Disruptor single-producer claim.
  - **Expect to hit #4 — reader livelock under a hot writer**: a writer updating in a tight loop can keep the seq
    perpetually odd / always-changing, so a reader's retry loop never converges. Symptom: a reader thread spins at
    100% CPU and never returns under a write-heavy workload.
    - Fix: bound retries with a `Backoff` (W4 Tue) — `spin_loop` then `yield_now`; SeqLock is designed for
      read-heavy / rare-write traffic, so also document that assumption.
    - Muscle: lock-free retry loops still need a backoff and a workload assumption. Reapplies at: W11 bounded MPMC
      retry, W37 skiplist CAS retry.

  - **Expect to hit #1**: you'll pick `align(64)` (the textbook x86 cache line). On Apple Silicon (your dev machine)
    the L2 prefetcher pulls **128-byte pairs**, so producer/consumer counters still false-share. Bench shows ~30%

    **Fix**: align(128) on aarch64-apple-darwin; align(64) on x86_64-linux. cfg-gate.
  - **Expect to hit #2**: you put `CachePadded<AtomicU64>` inside a struct without `repr(C)`. Rust reorders fields
    and your padding ends up wedged between unrelated members. False-sharing returns.
    **Fix**: force `repr(C)` on any struct where padding is load-bearing.
  - **Muscle**: cache-line padding is **target-dependent and layout-dependent**. **Reapplies at**: matching-engine

- [ ] **Build**: `crates/concurrent/src/backoff.rs` — adaptive `Backoff { step: Cell<u32> }` mirror of
  `crossbeam-utils`. `spin()` escalates `core::hint::spin_loop()` → `thread::yield_now()` → park over ~10 steps. (~75 min)
  - **Expect to hit #1**: tight `while !ready.load(Relaxed) {}` without `hint::spin_loop()` (PAUSE on x86). 100% CPU
    on the waiter *and* slower wake-ups, because SMT siblings are starved.
    **Fix**: every busy wait calls `hint::spin_loop()` per iteration.
  - **Expect to hit #2**: pure exponential spin works on a CAS retry (transient contention) but **fails** on
    structural contention (a writer holding a lock for 1ms). The spinner starves the holder.
    **Fix**: escalate to `yield_now` then park — never spin indefinitely.
  - **Muscle**: spin loops are a 3-stage ladder — `hint::spin_loop` → `yield_now` → block. **Reapplies at**: bounded
    MPMC retry (W11), SegQueue retry (W26), skiplist CAS retry (W37), term-buffer claim spin (W77).
- [ ] **Build**: `crates/concurrent/src/atomic_cell.rs` — `AtomicCell<T: Copy>` with fast path for
  `size_of::<T>() == 8 && align_of::<T>() == 8` (transmute to AtomicU64); spinlock fallback otherwise. (~75 min)
  - **Expect to hit #1**: `struct S { a: u8, b: u64 }` is `Copy` and 16 bytes — but transmuting it to bytes exposes
    padding that is uninitialized. `cargo +nightly miri test` fires "encountered uninitialized memory."
    **Fix**: zero-initialize via `MaybeUninit::zeroed()` then write field-by-field; or require
    `Pod`-trait callers.
  - **Expect to hit #2**: you write the fast path for ≤8 bytes but never test the slow path (spinlock fallback).

    test for both `T = u64` and `T = [u8; 16]`.
  - **Muscle**: every `unsafe` invariant needs both a static assertion AND a test that exercises the gated branch.
    **Reapplies at**: SegQueue per-slot writes (W26), epoch-gc `Atomic<T>` (W33).
- [ ] **Build**: `crates/concurrent/src/parker.rs` — `Parker` + `Unparker` pair. State machine:
  `EMPTY` ⟷ `PARKED` ⟷ `NOTIFIED`. (~75 min)
  - **Expect to hit #1**: the classic **lost wakeup**. Wrong sequence: check flag → flag false → call `park`.
    Between check and park, `unpark` fires and sets `NOTIFIED`; your `park` doesn't first check for `NOTIFIED`,
    so you sleep forever. Loom finds this in <100 iterations.
    **Fix**: `park` first CAS `EMPTY → PARKED`; if CAS fails because state is `NOTIFIED`, return immediately.
  - **Expect to hit #2**: spurious wakeups (Linux futex, macOS dispatch). If your `park` isn't in a loop, you wake
    on noise and proceed as if `unpark` was called.
    **Fix**: caller wraps `parker.park()` in `while !condition { parker.park() }`.
  - **Muscle**: every blocking primitive needs `state + wait`. Never just `wait`. The state must be CAS'd before
    sleeping; the wait loop must re-check on every wake. **Reapplies at**: bounded MPMC `recv` block-on (W11), WAL
    group-commit oneshot ack (W26), every channel you'll ever write.

**Wednesday — Variance + PhantomData via `Sealed<T>`**

- [ ] Watch Crust of Rust: Subtyping and Variance. (~75 min)
- [ ] **Build**: `crates/eth-primitives/src/sealed.rs` — `Sealed<T> { inner, hash: OnceLock<B256> }`. (~75 min)
  - *Mental model*: `Sealed<T>` is the generic, reusable wrapper behind W4 Tue's `atomic_hash` exercise — it pairs
    any `Sealable` value with its memoized hash and makes the value immutable-by-construction, so the cached hash
    can never go stale. This is reth's `SealedHeader` / `Sealed<H>`.
  - *Contract*: `Sealed<T> { inner: T, hash: OnceLock<B256> }`. Constructors: `Sealed::new(inner)` (lazy hash) and
    `Sealed::new_unchecked(inner, hash)` (caller supplies a precomputed hash). Accessors: `fn hash(&self) -> B256`
    (fills the `OnceLock` via `Sealable::hash_slow`), `fn inner(&self) -> &T`, `fn into_inner(self) -> T` — but no
    `&mut T` accessor, ever. `Deref<Target = T>` for ergonomic field reads.
  - **Expect to hit #1 — leaking `&mut` to `inner`**: you add a `fn inner_mut(&mut self) -> &mut T` or derive
    something that exposes it; now the inner value can mutate after the hash is cached. Symptom: `.hash()` returns a
    hash that disagrees with the current `inner` — a silent consensus split, no panic.
    - Fix: `Sealed` exposes only shared access; mutation means `into_inner()`, change, re-`new()` (re-seal).
    - Muscle: an immutable wrapper must not have a single mutable escape hatch. Reapplies at: W6 `SealedHeader`, W11
      type-state block.
  - **Expect to hit #2 — `PartialEq`/`Hash` derived over the `OnceLock`**: `#[derive(PartialEq, Hash)]` on `Sealed`
    includes the `hash` field, so two `Sealed` wrapping equal `inner` compare unequal when one has computed its
    hash and the other hasn't. Symptom: a `HashSet<Sealed<T>>` stores duplicates; equality is non-deterministic.
    - Fix: hand-write `PartialEq`/`Hash` to delegate to `inner` only (or to the hash only) — never mix the cache
      cell into identity.
    - Muscle: a memoization cell is not part of a type's identity — exclude it from `Eq`/`Hash`. Reapplies at: W6
      `SealedHeader` equality, W11 type-state header.

**Thursday — Unsafe + miri via `BytesMut::reserve`**

- [ ] Read Nomicon chapters on aliasing, UB. (~75 min)
- [ ] **Build**: `crates/eth-primitives/src/bytes_mut.rs` — `BytesMut`. reserve + extend_from_slice with raw pointer
  arithmetic. `BytesMut::freeze` to Bytes. (~75 min)
  - *Mental model*: a growable byte buffer you build by hand from a raw allocation — `ptr`, `len`, `cap` — instead
    of leaning on `Vec`. It is the write-side scratch buffer for RLP/wire encoding; `freeze()` converts the
    finished buffer into an immutable, cheaply-cloneable `Bytes`. This is `bytes::BytesMut` in miniature.
  - *Contract*: `BytesMut { ptr: NonNull<u8>, len: usize, cap: usize }`. `fn reserve(&mut self, additional: usize)`
    ensures `cap - len >= additional`, reallocating if needed. `fn extend_from_slice(&mut self, src: &[u8])`
    reserves then `ptr::copy_nonoverlapping` the bytes and bumps `len`. `fn freeze(self) -> Bytes` hands the
    allocation to an immutable owner. Manage the allocation via `std::alloc::{alloc, realloc, dealloc}` + `Layout`.
  - *reserve, roughly*: (1) if `cap - len >= additional`, return; (2) compute a new capacity (grow geometrically,
    e.g. `max(cap*2, len+additional)`); (3) build `Layout` for old and new sizes; (4) `realloc` (or `alloc` if
    `cap == 0`); (5) check for null and store the new `NonNull` + `cap`. Step 3-4 — getting `Layout` exactly
    matching every alloc/realloc/dealloc — is the real exercise.
  - **Expect to hit #1 — `Layout` mismatch between alloc and dealloc**: you `alloc` with one `Layout` but `dealloc`
    (in `Drop`) or `realloc` with a `Layout` built from a different size/align. Symptom: heap corruption — miri
    reports "incorrect layout on deallocation"; in release, intermittent crashes far from the real cause.
    - Fix: the `Layout` passed to `dealloc`/`realloc` must describe the *current* allocation exactly — store enough
      to reconstruct it (`cap` + a fixed `align`); a zero-`cap` buffer must never be `dealloc`'d.
    - Muscle: every `dealloc`/`realloc` `Layout` must byte-for-byte match the `alloc` that produced the pointer.
      Reapplies at: W26 `wal` segment buffers, W38 `lsm-core` memtable arena.
  - **Expect to hit #2 — writing into uninitialized capacity / wrong copy length**: `extend_from_slice` does
    `ptr::copy_nonoverlapping(src, ptr.add(len), n)` but with the wrong `n`, or reads `&buf[..cap]` treating
    reserved-but-unwritten bytes as initialized. Symptom: miri fires "using uninitialized memory" or "pointer out
    of bounds"; out of miri, garbage bytes appear past `len`.
    - Fix: only ever read `[0..len]`; copy exactly `src.len()` bytes to `ptr.add(len)` and bump `len` by the same
      amount; `len <= cap` is an invariant to assert.
    - Muscle: capacity past `len` is uninitialized — never read it, and `len` advances only by bytes actually
      written. Reapplies at: W26 `wal` append, W38 SSTable block builder.
  - **Expect to hit #3 — dangling pointer after realloc**: you hold an old `*const u8` / slice into the buffer
    across a `reserve` that reallocates; the old block is freed and the pointer dangles. Symptom: use-after-free —
    miri "pointer to freed allocation"; in release, corrupted reads or crashes.
    - Fix: never retain a raw pointer or slice across a call that may `reserve`/grow; re-derive from `self.ptr`
      after any potential reallocation.
    - Muscle: any raw pointer into a growable buffer is invalidated by a reallocation. Reapplies at: W10 trie node
      buffer, W26 `wal` segment growth, W38 memtable arena.
  - **Expect to hit #4 — `freeze` double-free / aliasing the allocation**: `freeze` builds a `Bytes` from
    `self.ptr` but `BytesMut`'s own `Drop` still runs and frees the same block — or both share it without
    refcounting. Symptom: double-free (miri: "deallocating already-deallocated"); or `Bytes` reads freed memory.
    - Fix: `freeze` must *move* ownership — consume `self` and `mem::forget` it (or use `ManuallyDrop`) so only the
      new `Bytes` owns and frees the allocation.
    - Muscle: transferring ownership of a raw allocation means exactly one `Drop` must run for it. Reapplies at: W5
      `Bytes` in RLP, W26 `wal` buffer handoff.

**Friday — Macros via `b256!` + `SimpleEncode` derive**

- [ ] Read R4R ch7 + Little Book of Rust Macros. (~75 min)
- [ ] **Build**: `crates/eth-primitives/src/macros.rs` — `b256!`, `address!` const macros. (~75 min)
  - *Mental model*: `b256!("0xdead…")` / `address!("0x…")` turn a hex string *literal* into a `B256` / `Address`
    constant at compile time — no runtime parse, no `unwrap`. A malformed literal must be a *compile* error. These
    mirror `alloy-primitives`' `b256!`/`address!`.
  - *Contract*: `macro_rules!` macros taking a string-literal token; they expand to a `const` expression of the
    right fixed-byte type. Hex decoding runs in a `const fn` so the whole thing is usable in `const`/`static`
    context. Accept an optional `0x` prefix.
  - **Expect to hit #1 — runtime parse instead of const eval**: the macro expands to `B256::from_hex(s).unwrap()`,
    which runs at startup and can panic. Symptom: a bad literal compiles fine and panics at runtime; the value
    can't be used in a `const`/`static`.
    - Fix: decode in a `const fn` (loop over bytes, match hex nibbles) so an invalid literal fails *compilation*
      and the result is a true compile-time constant.
    - Muscle: a literal macro must fail at compile time, not run time. Reapplies at: W5 `b256!` in RLP fixtures, W6
      genesis-hash constants.
  - **Expect to hit #2 — wrong length silently truncated/padded**: a hex string that isn't exactly `2*N` chars is
    truncated or zero-padded instead of rejected. Symptom: `b256!("0xdead")` yields a mostly-zero hash that "works"
    until a fixture mismatch much later.
    - Fix: `const`-assert the decoded length equals the target byte width (e.g. `assert!(len == 32)`); a wrong
      length is a compile error.
    - Muscle: a fixed-width literal macro must reject any input of the wrong length. Reapplies at: W5 fixed-array
      RLP literals, W6 `B256` header fields.
- [ ] **Build**: `crates/eth-primitives-derive/` proc-macro crate (syn + quote). `#[derive(SimpleEncode)]` placeholder
  for Week 5's RlpEncodable. (~45 min)
  - *Mental model*: the first proc-macro crate — a separate workspace member compiled as a compiler plugin. This
    week it just generates a trivial `SimpleEncode` impl; W5 grows it into the real `RlpEncodable`/`RlpDecodable`.
    The point today is the *scaffold*: a working `#[derive]` you can extend.
  - *Contract*: a crate with `[lib] proc-macro = true` and `syn` + `quote` + `proc-macro2` deps. One
    `#[proc_macro_derive(SimpleEncode)]` fn: parse the input `TokenStream` into a `syn::DeriveInput`, iterate the
    struct's named fields, and `quote!` an `impl SimpleEncode for S` that emits each field in declaration order.
  - **Expect to hit #1 — `proc-macro = true` crate exporting non-macro items**: you try to put the `SimpleEncode`
    *trait* itself, or test code, in the proc-macro crate. Symptom: "`proc-macro` crate types currently cannot
    export any items other than `#[proc_macro]`…" — the crate refuses to compile.
    - Fix: the trait lives in `eth-primitives`; the proc-macro crate exports only the derive macro and depends on
      nothing else of yours (derived code refers to the trait by absolute path).
    - Muscle: a proc-macro crate is macros-only — traits and types live in the normal crate. Reapplies at: W5
      `RlpEncodable` derive, W11 type-state derive.
  - **Expect to hit #2 — unhygienic / non-absolute paths in generated code**: the `quote!` output names
    `SimpleEncode` or `out` bare, so it breaks unless the caller has the exact import in scope. Symptom: the derive
    works in your test module but fails in any crate that imported things differently — "cannot find trait".
    - Fix: refer to items by absolute path in `quote!` (`::eth_primitives::SimpleEncode`); generate fresh binding
      names so they can't collide with the user's identifiers.
    - Muscle: generated code must name every external item by absolute path and never assume the caller's imports.
      Reapplies at: W5 `RlpEncodable`/`RlpDecodable` derive, W11 type-state derive.
  - **Expect to hit #3 — unhandled non-struct / tuple-struct input**: `syn::DeriveInput` can also be an enum, a
    union, or a tuple struct; indexing `.fields` assuming named fields panics inside the macro. Symptom: a
    `#[derive(SimpleEncode)]` on the wrong shape produces an opaque compiler-internal panic, not a clear error.
    - Fix: `match` on `Data`/`Fields`; for unsupported shapes emit a real diagnostic via `syn::Error::to_compile_error`.
    - Muscle: a derive macro must report unsupported input shapes as a clean compile error, never panic.
      Reapplies at: W5 RLP derive (enum support), W11 type-state derive.
