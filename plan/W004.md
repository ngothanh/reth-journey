- [X] **Build**: `crates/concurrent/src/cache_padded.rs` — `CachePadded<T>` mirror of `crossbeam-utils`.
  `#[repr(align(128))]` wrapper. A layout primitive — fits today's layout-audit theme. (~75 min)
  - *Mental model*: pad any `T` up to the target's cache-line size so adjacent `CachePadded<T>` never share a
    line. Used wherever two threads write to neighboring atomics — false sharing eats lock-free throughput.
  - *Back-of-envelope*: false-sharing a producer/consumer counter pair regresses MPMC throughput **30-70%**
    under contention (head + tail in the W11 Vyukov ring). One `CachePadded<AtomicU64>` costs 120 B on
    aarch64-apple-darwin (8 B payload + 120 B pad) or 56 B on x86_64-linux — paid once at construction,
    recovered every microsecond of runtime. Cache-coherency traffic on a contested line: ~7 ns L2 fetch per
    MESI invalidation; the fix is to separate the lines, not "be cleverer" with atomics.
  - **Expect to hit (perf) #1 — wrong cache-line size for target (bar (c) violation)**: `align(64)` is the
    textbook x86 value, but on Apple Silicon the L2 prefetcher pulls **128-byte pairs**, so producer/consumer
    counters still false-share. Symptom: a Vyukov MPMC bench shows ~30% throughput regression on
    aarch64-apple-darwin vs unpadded baseline — the regression "shouldn't" exist if you only know x86.
    - Fix: `align(128)` on aarch64-apple-darwin; `align(64)` on x86_64-linux. `cfg`-gate the constant;
      document the policy in a module-level comment.
    - Cost avoided: ~30% throughput on contended head/tail; ~7 ns L2 fetch per cross-thread access on the
      wrong-aligned line; MESI ping-pong eliminated on hot counters.
    - Muscle: cache-line size is a target-dependent constant — never hard-code one platform's value.
      Reapplies at: W11 MPMC head/tail cursor pair, W58 matching-engine `PriceLevel` best/bid pair, W65
      Disruptor claim/cursor pair, W77 messaging-aeron term rotation counters.
  - **Expect to hit (perf) #2 — `repr(Rust)` reorders the padding away (bar (c) violation)**:
    `CachePadded<AtomicU64>` inside a struct without `repr(C)`. Rust reorders fields and your padding ends up
    wedged between unrelated members; false-sharing returns silently — passes unit tests, regresses *only*
    under contention.
    - Fix: force `#[repr(C)]` on any struct where padding is load-bearing; pin layout with
      `const _: () = assert!(std::mem::offset_of!(S, tail) - std::mem::offset_of!(S, head) >= 128);` if
      paranoid.
    - Cost avoided: full re-introduction of false sharing (30-70% throughput regression); silent — caught
      only by criterion bench-diff, never by `cargo test`.
    - Muscle: when padding is load-bearing, lock the layout — `repr(C)` is non-negotiable. Reapplies at:
      W11 MPMC ring struct (head + tail + ring), W58 matching-engine order book multi-counter struct, W77
      aeron term metadata, W65 Disruptor sequencer/cursor pair.

**Tuesday — Atomics via `SealedHeader` hash cache + `ChainHead` SeqLock + `Backoff`**

- [X] **Build**: `crates/eth-primitives/src/atomic_hash.rs` — OnceLock<B256> lazy hash cache. `Sealable` trait. (~75 min)
  - *Mental model*: a block header's `keccak256` hash is expensive (~1µs) and immutable once the header is fixed.
    Compute it once, on first request, and cache it — every later `.hash()` is a pointer-load. This is reth's
    `SealedHeader` pattern: the hash is a memoized property, not a stored field.
  - *Contract*: `Sealable` is a trait with `fn hash_slow(&self) -> B256` (the actual keccak, named `_slow` to flag
    cost) and a provided `fn hash(&self) -> B256` that reads-or-fills a cache. The cache itself is a
    `OnceLock<B256>` field on the wrapper type; `get_or_init` runs `hash_slow` exactly once across all threads.
  - **Expect to hit #1 — caching a mutable value**: you put `OnceLock<B256>` on a type whose fields can still
    change after sealing. Symptom: `.hash()` returns a hash that no longer matches the (now-mutated) contents — a
    silent consensus bug, no panic.
    - Fix: only cache on a type that is immutable-by-construction (the `Sealed`/`SealedHeader` wrapper, W4 Wed);
      never expose `&mut` to the wrapped value.
    - Muscle: memoize only what is immutable; a cache over mutable state is a correctness bug. Reapplies at: W4 Wed
      `Sealed<T>`, W6 `SealedHeader`.
  - **Expect to hit #2 — `OnceCell` instead of `OnceLock`**: you reach for `once_cell::Cell` / `std::cell::OnceCell`,
    which is `!Sync`. Symptom: the header type stops being `Sync`; sharing a `SealedHeader` across threads fails to
    compile (`OnceCell<B256>` is not `Sync`).
    - Fix: use `std::sync::OnceLock` (thread-safe, `get_or_init` is internally synchronized) for any cache on a
      shared type.
    - Muscle: a lazy cache on a `Sync` type must use a `Sync` cell. Reapplies at: W4 Wed `Sealed<T>`, W11 type-state
      header.

- [X] **Build**: `crates/eth-chain-state/src/chain_head.rs` — `ChainHead { hash, number }` protected by SeqLock. (~75 min)
  - *Layering note*: ChainHead is **shared cross-thread state**, not a pure data type — it lives in
    `eth-chain-state`, not `eth-primitives`. `alloy-primitives` (the mirror target) has no sync deps; the new
    crate preserves that discipline by keeping coordination out of `eth-primitives`.
  - *Mental model*: the canonical chain tip (`hash` + `number`) is written by exactly one thread (the engine) and
    read constantly by many (RPC, peers). A `SeqLock` lets readers run fully lock-free: they snapshot the data and
    re-check a sequence counter; if a write straddled the read, they retry. No reader ever blocks a writer.
  - *Contract*: `ChainHead` holds an `AtomicU64` sequence counter plus the two payload fields. Writer:
    `fn store(&self, head: (B256, u64))`. Reader: `fn load(&self) -> (B256, u64)`. The sequence is even when stable,
    odd mid-write.
  - *SeqLock, roughly*: writer — (1) bump seq to odd (`Release`); (2) write payload fields; (3) bump seq to even
    (`Release`). Reader — (1) read seq (`Acquire`); (2) if odd, retry; (3) copy payload; (4) read seq again
    (`Acquire`); (5) if it changed, retry. Getting the fences right so step 3-of-reader can't be reordered around
    the seq reads is the real exercise.
  - *Back-of-envelope*: hot-read use case — RPC + peer threads call `load()` constantly. Target read latency
    **~5-10 ns** uncontended (one atomic load + one branch); ~20-50 ns including one retry under a write
    burst. Implications: zero allocations, zero locks, **seq counter and payload in separate cache lines**
    (one cross-thread invalidation = ~7 ns per read otherwise). One writer (the engine thread), no writer
    contention. Payload is 40 B (B256 + u64) — crosses a 64 B line if laid out naively, must be padded or
    aligned. This is the exact pattern reused at W58 matching-engine L1 best-bid/ask (target P99 < 1 µs).
  - **Expect to hit #1 — torn read of multi-word payload**: `hash` is 32 bytes, `number` 8 — they can't be read
    atomically as one unit, so a reader can see a new `hash` with an old `number`. Symptom: occasional
    impossible tips (a hash from block N paired with number N-1); rare, load-dependent, "can't reproduce."
    - Fix: that is exactly what the seq counter catches — re-read seq *after* copying the payload and retry on any
      change; never trust a payload copy that straddled a seq bump.
    - Muscle: a SeqLock makes a multi-word read *appear* atomic by retry, not by locking. Reapplies at: W58
      matching-engine L1 best-bid/ask, W77 messaging-aeron term rotation.
  - **Expect to hit #2 — payload load hoisted above the seq read**: with `Relaxed` ordering (or no fence) the
    compiler/CPU reorders the payload reads to *before* the first seq read, so the validation window doesn't
    actually cover the copy. Symptom: torn reads slip through even though the retry logic "looks correct"; miri/loom
    flags a data race.
    - Fix: first seq read is `Acquire`, second seq read is `Acquire`, writer's seq bumps are `Release`; the payload
      copy is fenced between two `Acquire` loads. Consider `compiler_fence`/`fence(Acquire)` to pin the order.
    - Muscle: a SeqLock is correct only if the payload access is provably fenced *between* the two seq reads.
      Reapplies at: W58 L1 publishing, W65 Disruptor cursor.
  - **Expect to hit #3 — writer not exclusive / non-atomic payload writes**: two writers race, or the payload
    fields are plain (non-atomic) and written while a reader copies them — that copy is a data race even with the
    seq dance. Symptom: UB; miri/loom reports a data race on the payload bytes themselves.
    - Fix: SeqLock assumes a *single* writer (enforce it — `&mut self` writer or a guard); store payload in
      `AtomicU64`s / `AtomicU32`s (or use `MaybeUninit` + atomic-fenced copy) so the read-side copy is not UB.
    - Muscle: SeqLock removes reader blocking, not writer exclusivity, and the payload itself must still be
      race-free. Reapplies at: W58 matching-engine single-writer L1, W65 Disruptor single-producer claim.
  - **Expect to hit (perf) #4 — reader livelock + 100% CPU under a hot writer (bar (c) violation)**: a writer
    updating in a tight loop keeps the seq perpetually odd / always-changing, so a reader's retry loop never
    converges. Symptom: a reader thread spins at 100% CPU and never returns under a write-heavy workload.
    - Fix: bound retries with a `Backoff` (built next) — `spin_loop` then `yield_now`; SeqLock is designed
      for read-heavy / rare-write traffic, so also document that assumption in a `//!`.
    - Cost avoided: 100% CPU per stuck reader (worst case); the backoff ladder caps spin to ~10 iterations
      (~50 ns) before yielding, vs unbounded spin.
    - Muscle: lock-free retry loops still need a backoff and a workload assumption. Reapplies at: W11
      bounded MPMC retry, W37 skiplist CAS retry, W58 matching-engine L1 read under hot updates.
  - **Expect to hit (perf) #5 — seq counter shares a cache line with the payload (bar (c) violation)**:
    putting `seq: AtomicU64` and `(hash, number)` in one struct lays them in the same 64 B cache line on x86
    (or straddles two on aarch64). Every payload write invalidates the reader's cached copy of `seq`, so
    each read pays an extra cache fetch on the *first* seq load — the seq dance was supposed to be free in
    the no-write window.
    - Fix: lay out as `struct ChainHead { #[repr(align(128))] seq: AtomicU64, _pad: [u8; 120], payload: …
      }` with explicit padding, or wrap `seq` in `CachePadded<AtomicU64>` and the payload in
      `CachePadded<(B256, u64)>`. Verify with `offset_of!`.
    - Cost avoided: ~7 ns L2 fetch on every read in steady state (the seq load that "should" hit L1 but
      doesn't because the line keeps being invalidated by the writer); doubles to ~14 ns under
      cross-socket scenarios.
    - Muscle: in a SeqLock, the seq counter and the payload must live in *separate* cache lines from each
      other and from any other hot data. Reapplies at: W58 matching-engine L1 best-bid/ask SeqLock, W65
      Disruptor cursor (the seq IS the cursor), W77 aeron term rotation seq.
- [X] **Build**: `crates/concurrent/src/backoff.rs` — adaptive `Backoff { step: Cell<u32> }` mirror of
  `crossbeam-utils`. `spin()` escalates `core::hint::spin_loop()` → `thread::yield_now()` → park over ~10 steps. (~75 min)
  - 🔧 **Decomposition prompt (foundational — no prior drills to silently test yet, but every drill W5–W17
    + every production crate from W11 onward will REUSE this Backoff)**: ship it correctly here or ship the
    bug everywhere downstream. The acceptance below is tight because W11 MPMC retry, W26 group commit wait,
    W37 skiplist CAS retry, W42 LockManager waiter, W74 matching-engine apply-loop idle all silently demand
    this primitive at this quality.
  - 🎯 **Hardened acceptance**:
    - **Per-stage cost (measured, falsifiable)**: spin step ≤3 cycles (`PAUSE`/`YIELD` only); yield step
      ≤10µs (one context switch); park step ≤500ns entry + variable wake. Measure each with criterion.
    - **Ladder behavior under simulated contention**: under transient contention (CAS retries every ~10 ns),
      Backoff stays in spin stage; under structural contention (lock held >1ms), Backoff escalates to yield
      then park within 10 calls. Document the transition thresholds and justify from /hft-review §1.
    - **Latency distribution under burst-then-idle workload**: p50 wake from spin = single CAS retry cost
      (~10ns); p99 wake from yield = ~10µs; p99 wake from park = ≤1µs after unpark.
    - **CPU utilization at idle**: under 0 contention sustained 60s, CPU usage <1% (no busy-spin tax).
    - **No SMT pipeline starvation**: every spin iteration MUST call `core::hint::spin_loop()` — verified by
      asm inspection (`cargo asm`) showing PAUSE/YIELD instruction.
    - **5-year failure mode**: state one shift (256+ cores, RISC-V Zihintpause, single-core deployment)
      that would change the ladder thresholds.
  - *Mental model*: a 3-stage waiting ladder — burn ~1-100 ns spinning (hopeful CAS-retry case), then yield
    the scheduler (~1-10 µs context switch — give the lock-holder a chance to make progress), then park
    (futex/condvar, ~300 ns + wakeup latency). Every lock-free retry loop drives a `Backoff` — no exceptions.
  - *Back-of-envelope*: `hint::spin_loop()` ≈ 1-3 cycles on x86 (PAUSE) / ~1 cycle on aarch64 (YIELD).
    `thread::yield_now()` ≈ 1-10 µs (context switch into kernel). Parking via futex ≈ 300 ns to enter plus
    wakeup latency (~500 ns - 5 µs). The ladder budget: spin ≤ ~100 ns total time, then yield, then park. A
    spin that burns past ~1 µs has lost — the lock-holder almost certainly isn't on the same core; yield.
  - **Expect to hit (perf) #1 — busy-wait without `hint::spin_loop()` (bar (c) violation)**: tight
    `while !ready.load(Relaxed) {}` without `hint::spin_loop()`. Symptom: 100% CPU on the waiter, *and*
    slower wake-ups because SMT siblings are starved (the spinner hogs the pipeline).
    - Fix: every busy-wait body calls `core::hint::spin_loop()` per iteration. On x86 this is PAUSE
      (releases the pipeline to SMT siblings + hints the branch predictor); on aarch64 it's YIELD.
    - Cost avoided: ~30-50% wake-up latency improvement on SMT machines; eliminates 100% CPU on stuck
      waiters; restores pipeline bandwidth to the other hyperthread.
    - Muscle: `hint::spin_loop()` is the cheapest line in a busy-wait — always include it. Reapplies at:
      W11 MPMC CAS retry, W26 SegQueue retry, W37 skiplist CAS retry, W77 term-buffer claim spin.
  - **Expect to hit (perf) #2 — unbounded spin starves the lock-holder (bar (c) violation)**: pure
    exponential spin works on CAS retry (transient contention, ~10 ns away). It **fails** on structural
    contention (a writer holding a lock for 1 ms, or descheduled by the OS): the spinner steals the same
    core's CPU time the lock-holder needs to make progress — deadlock-shaped livelock.
    - Fix: escalate. After N spins (~10), `thread::yield_now()`. After M yields (~10), park via the W4 Thu
      `Parker`. Never spin indefinitely.
    - Cost avoided: ~∞ wall-clock under structural contention; restores correctness when the holder is on
      the same core.
    - Muscle: spin loops are a **3-stage ladder** — `hint::spin_loop` → `yield_now` → block. Reapplies at:
      W11 MPMC `recv` block, W26 WAL group-commit ack, W37 skiplist, W42 `txn` lock contention.

- [ ] **Build**: `crates/eth-primitives/src/sealed.rs` — `Sealed<T> { inner, hash: OnceLock<B256> }`. (~75 min)
  - *Mental model*: `Sealed<T>` is the generic, reusable wrapper behind W4 Tue's `atomic_hash` exercise — it pairs
    any `Sealable` value with its memoized hash and makes the value immutable-by-construction, so the cached hash
    can never go stale. This is reth's `SealedHeader` / `Sealed<H>`.
  - *Contract*: `Sealed<T> { inner: T, hash: OnceLock<B256> }`. Constructors: `Sealed::new(inner)` (lazy hash) and
    `Sealed::new_unchecked(inner, hash)` (caller supplies a precomputed hash). Accessors: `fn hash(&self) -> B256`
    (fills the `OnceLock` via `Sealable::hash_slow`), `fn inner(&self) -> &T`, `fn into_inner(self) -> T` — but no
    `&mut T` accessor, ever. `Deref<Target = T>` for ergonomic field reads.
  - **Expect to hit #1 — leaking `&mut` to `inner`**: you add a `fn inner_mut(&mut self) -> &mut T` or derive
    something that exposes it; now the inner value can mutate after the hash is cached. Symptom: `.hash()` returns a
    hash that disagrees with the current `inner` — a silent consensus split, no panic.
    - Fix: `Sealed` exposes only shared access; mutation means `into_inner()`, change, re-`new()` (re-seal).
    - Muscle: an immutable wrapper must not have a single mutable escape hatch. Reapplies at: W6 `SealedHeader`, W11
      type-state block.
  - **Expect to hit #2 — `PartialEq`/`Hash` derived over the `OnceLock`**: `#[derive(PartialEq, Hash)]` on `Sealed`
    includes the `hash` field, so two `Sealed` wrapping equal `inner` compare unequal when one has computed its
    hash and the other hasn't. Symptom: a `HashSet<Sealed<T>>` stores duplicates; equality is non-deterministic.
    - Fix: hand-write `PartialEq`/`Hash` to delegate to `inner` only (or to the hash only) — never mix the cache
      cell into identity.
    - Muscle: a memoization cell is not part of a type's identity — exclude it from `Eq`/`Hash`. Reapplies at: W6
      `SealedHeader` equality, W11 type-state header.

**Thursday — Unsafe + miri via `BytesMut` + `Parker`**

- [ ] **Build**: `crates/eth-primitives/src/bytes_mut.rs` — `BytesMut`. reserve + extend_from_slice with raw pointer
  arithmetic. `BytesMut::freeze` to Bytes. (~75 min)
  - *Mental model*: a growable byte buffer you build by hand from a raw allocation — `ptr`, `len`, `cap` — instead
    of leaning on `Vec`. It is the write-side scratch buffer for RLP/wire encoding; `freeze()` converts the
    finished buffer into an immutable, cheaply-cloneable `Bytes`. This is `bytes::BytesMut` in miniature.
  - *Contract*: `BytesMut { ptr: NonNull<u8>, len: usize, cap: usize }`. `fn reserve(&mut self, additional: usize)`
    ensures `cap - len >= additional`, reallocating if needed. `fn extend_from_slice(&mut self, src: &[u8])`
    reserves then `ptr::copy_nonoverlapping` the bytes and bumps `len`. `fn freeze(self) -> Bytes` hands the
    allocation to an immutable owner. Manage the allocation via `std::alloc::{alloc, realloc, dealloc}` + `Layout`.
  - *reserve, roughly*: (1) if `cap - len >= additional`, return; (2) compute a new capacity (grow geometrically,
    e.g. `max(cap*2, len+additional)`); (3) build `Layout` for old and new sizes; (4) `realloc` (or `alloc` if
    `cap == 0`); (5) check for null and store the new `NonNull` + `cap`. Step 3-4 — getting `Layout` exactly
    matching every alloc/realloc/dealloc — is the real exercise.
  - **Expect to hit #1 — `Layout` mismatch between alloc and dealloc**: you `alloc` with one `Layout` but `dealloc`
    (in `Drop`) or `realloc` with a `Layout` built from a different size/align. Symptom: heap corruption — miri
