    - R7. Allocation-free + float-free apply path.

  - **Design walk-through**:
    - D1. Sketch AuctionBook + UncrossingResult + uncross signature.

- [ ] [NEW v2 mmap-queue v0.5] **Build**: integration test with messaging-aeron Archive — mmap-queue stores recorded
  stream. (~60 min)
  - **Why**: Aeron Archive records every message published on a stream to durable storage for later replay. Mapping Archive's storage layer onto our mmap-queue (which has Cycles = time-bounded segments) provides bounded retention + fast replay. Demonstrates how Layer-4 (messaging-aeron) composes with Layer-3 (mmap-queue) — exact pattern Chronicle Queue + Real Logic ship together.
  - **Read first**: Aeron Archive `RecordingSession.java`, `ReplayMerge.java`. Chronicle Queue `SingleChronicleQueue.java` for the cycle-rotation pattern.
  - **Design**:
    ```rust
    // In messaging-aeron crate, behind feature `archive` flag
    pub struct ArchiveRecorder {
        pub stream_id: i32,
        pub queue: Arc<MmapQueue>,         // from mmap-queue v0.5
        pub current_cycle: CycleId,
    }
    impl ArchiveRecorder {
        pub fn record_fragment(&mut self, frame: &[u8], position: i64) -> Result<()> {
            // Each Aeron frame → one mmap-queue entry tagged with (stream_id, position)
            self.queue.append(QueueEntry::new(self.stream_id, position, frame))?;
            Ok(())
        }
        pub fn replay(&self, from_position: i64, to_position: i64) -> impl Iterator<Item = ArchiveFrame> {
            self.queue.range(from_position..=to_position)
                .map(|entry| ArchiveFrame { position: entry.position(), data: entry.bytes() })
        }
    }
    ```
    **Invariants**: (i) Recorded frames are byte-for-byte the same as published frames (zero-copy). (ii) `position` is monotonic across cycle rotation — mmap-queue's cycle key maps to Aeron position. (iii) Cycle rotation (e.g., daily) bounds disk usage; old cycles deletable without affecting current.
  - **Build steps**: 1. (~15 min) ArchiveRecorder struct + queue handle. 2. (~20 min) `record_fragment` — append to queue with position tag. 3. (~15 min) `replay` — queue range iterator. 4. (~10 min) Integration test: publish 100 messages → record to queue → replay → bit-identical bytes.
  - **Pitfalls** (named, 2):
    - *Cycle rotation race*: **Symptom**: position rolls over cycle boundary; replay misses frames at the cycle edge. **Fix**: queue's cycle index has overlap (slight) — `range()` spans cycles transparently. Cycle metadata stores first/last position to enable efficient seek.
    - *Disk full*: **Symptom**: archive writes faster than cycle reaper; disk fills, recorder blocks → propagates back to publisher → flow control. **Fix**: monitor disk free; alert when < 10%; archive recorder backpressures via flow control (subscriber-style position).
  - **Test scenarios**: (a) 100k messages recorded, replayed → bit-identical. (b) Force cycle rotation mid-recording; replay spans cycles. (c) Replay with `from_position` in old cycle (deleted) → returns error gracefully.
  - **Acceptance**: record throughput ≥1M msg/s. Replay matches published. Inheritance: mmap-queue, bufpool.
  - **Downstream**: W82 v1.5 SHIP audit confirms ledger / matching-engine can record via this for compliance audit. Tier-A interview: "how would you architect a tamper-evident audit log?" → archive + mmap-queue with checksum chain.

  - 🔧 **Why this matters**: UDP transport is how aeron talks across hosts. `sendmmsg/recvmmsg` batches I/O cuts syscalls 100×. MTU-aware fragmentation prevents IP-layer fragmentation. Tier-A interview baseline. Downstream: W78 Wed NAK protocol uses transport_udp; W82 Image layers reorder atop this.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: 1M+ pps target. Per-packet `sendto` caps at ~1M pps (~1 µs syscall + socket-layer). `sendmmsg(64)` amortizes to ~80 ns/pkt = 12M pps theoretical. MTU-aware fragmentation prevents IP-layer fragmentation (unpredictable, breaks ordering).

  - **Requirements** — write in `crates/messaging-aeron/notes/78_transport_udp_design.md`:
    - R1. Outgoing frames ≤ MTU; larger fragmented at Aeron level (BEGIN/MIDDLE/END flags).
    - R2. `set_dont_fragment(true)` — IP layer NEVER fragments; `frame > pmtu` returns EMSGSIZE.
    - R3. Batched send/recv — every syscall amortized over 64 packets typical.
    - R4. `SO_REUSEPORT` for multi-receiver load-balancing.
    - R5. `SO_RCVBUF=8MB` (`net.core.rmem_max` configured); monitor `UdpDrops` counter.
    - R6. Throughput ≥1M pps single-thread; P99 <5 µs.
    - R7. Zero allocations on hot path (pre-allocated recv buffer pool).
    - R8. Path-MTU conservative: 1300 across WAN to absorb VLAN/VPN overhead.

  - **Design walk-through**:
    - D1. Sketch UdpTransport struct + open/send_batch/recv_batch signatures.
    - D2. **Pre-mortem (per-packet sendto):** loop `socket.send_to` per frame = 1 syscall/pkt × 1000 = 1 ms of syscall. Walk through sendmmsg.
    - D3. **Pre-mortem (recv buffer per packet):** `let mut buf = vec![0u8; 1500]` per recv = 200 ns malloc + 50 ns memset = 250 ns/pkt allocator overhead. At 1M pps = 250 ms/sec. Walk through pre-allocated `RecvBufferPool`.
    - D4. **Pre-mortem (MTU mismatch across hops):** assumed 1500, intermediate VPN has 1400 → DF + oversize = drop. PMTUD or conservative MTU (1300 WAN).
    - D5. **Pre-mortem (recvmmsg blocking):** forgot MSG_DONTWAIT → call blocks until N packets arrive; latency tail in low-traffic mode. Always MSG_DONTWAIT + spin/poll.
    - D6. **Pre-mortem (SO_RCVBUF undersized):** burst overflows kernel buffer; silent UDP drops only visible via `netstat -su`. RCVBUF=8MB + rmem_max documented as ops requirement.

## Wednesday — Crate: fork choice + messaging-aeron NAK protocol

- [ ] Implement consensus-engine fork choice processing. (~120 min)
- [ ] **Build**: `crates/messaging-aeron/src/nak.rs` — gap detection by sequence number, NAK back to publisher, replay
  from term buffer's recovery slot. (~total 2.5 hrs across 3 phases)
  - 🔧 **Why this matters**: UDP doesn't guarantee delivery. Aeron uses NAKs (vs TCP-style ACKs) — receiver reports MISSING ranges, publisher retransmits. Minimizes bandwidth; keeps publisher state minimal. NAK storms are real production incidents. Downstream: W79 multi-sub NAK suppression coalesces across subs; W82 Image integrates LossDetector per-sub. Bar (c).

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: 1M+ pps UDP with 1-5% loss; in-order delivery needed. NAK-based recovery: receiver detects gap by seq comparison; after `nak_delay` (covers UDP reorder), NAKs publisher; publisher retransmits from term buffer (3-term retention).

  - **Requirements** — write in `crates/messaging-aeron/notes/78_nak_design.md`:
    - R1. `highest_seen` monotonic; out-of-order frames are gap-fills, not regressions.
    - R2. Gap detection waits `nak_delay` (default 60ms) before first NAK (reordering tolerance).
    - R3. Retransmit publisher state IS the term buffer; frames accessible for `3 × TERM_LEN` of data.
    - R4. NAK storm suppression: publisher dedupes by gap range; coalesces NAKs within `coalesce_window`; retransmits ONCE.
    - R5. Exponential backoff on retransmits per gap (1ms, 2ms, ..., cap 1s); after N attempts, drop subscriber.
    - R6. Out-of-window NAK → publisher replies ResetSession → subscriber re-establishes (full state transfer).
    - R7. Hot recv path bypasses BTreeMap for in-order frames (99.9%+ of frames) — only gap branch enters map.
    - R8. Under 5% loss, zero application-level loss with NAK recovery; retransmit overhead <10% extra bandwidth.

  - **Design walk-through**:
    - D1. Sketch LossDetector + GapState + NakAction enums.
    - D2. **Pre-mortem (BTreeMap lookup on hot path):** `on_frame` calls `self.gaps.entry(...)` which is O(log N) BTreeMap walk on EVERY frame; 99.9% of frames in-order (no gap). At 1M pps × ~50 ns = ~50 ms/sec cold-cache traversal. Walk through fast-path check.
    - D3. **Pre-mortem (NAK storm):** large loss → 100 NAKs from 100 subs for same gap → publisher melts. Coalesce + retransmit once.
    - D4. **Pre-mortem (NAK vs retransmit infinite loop):** subscriber NAKs, publisher retransmits, retransmit lost en-route, subscriber NAKs again. Exponential backoff per gap; cap attempts.
    - D5. **Pre-mortem (head-of-line during recovery):** NAK pending; subscriber blocks consumption of all subsequent frames. Subscriber buffers in-order frames after gap; delivers post-fill (reorder buffer in image.rs W82).
    - D6. **Pre-mortem (out-of-term NAK):** NAK for frame rotated out of term buffers → no source for retransmit. Publisher replies ResetSession; subscriber re-establishes.

  - **Output**: `notes/78_nak_design.md` with R1–R8 + D1–D6.

    - Symptom: NAK-disabled bench shows 2M pps; NAK-enabled bench shows 600k pps; flame graph dominated by `BTreeMap::range` / `BTreeMap::entry`.
