- [ ] [NEW v2] **Build**: `crates/matching-engine/src/auction.rs` — uncrossing algorithm: find single clearing price
  that maximizes traded volume, ties broken by minimum imbalance. (~3 hrs)
  - **Why**: Auctions (opening, closing, halt-resumption) are how equity exchanges concentrate liquidity at moments of price discovery. The *uncrossing algorithm* — find single price maximizing traded volume — is the heart of NYSE Open/Close, Nasdaq Cross, halt auctions, and IPO openings. Interview-load-bearing: candidates draw the supply/demand curve and walk through tie-breaks.
  - **Read first**: NYSE Rule 7.35 (opening auction methodology). Nasdaq Opening/Closing Cross specification. CFA Institute reading on price-discovery auctions. Compare Eurex Frankfurt auction (continuous → call → continuous transitions).
  - **Design**:
    ```rust
    pub struct AuctionBook {
        pub buys: BTreeMap<Price, u64>,      // px → cumulative buy qty at or above
        pub sells: BTreeMap<Price, u64>,     // px → cumulative sell qty at or below
        pub market_buys: u64,                // unpriced; willing at any price
        pub market_sells: u64,
        pub reference_px: Price,             // last continuous trade, used for tiebreak
    }
    pub struct UncrossingResult {
        pub clearing_px: Price,
        pub matched_qty: u64,
        pub imbalance: i64,                  // signed: + buy excess, - sell excess
        pub residual_buys: u64,              // unfilled buys after auction
        pub residual_sells: u64,
    }
    impl AuctionBook {
        pub fn uncross(&self) -> UncrossingResult {
            // 1. Walk all candidate prices (union of unique px from buys + sells)
            // 2. For each px: tradable = min(cum_buy_at_or_above(px), cum_sell_at_or_below(px))
            // 3. Max tradable wins. On tie: min |imbalance|. On further tie: closer to reference_px. On further tie: lower price.
            let candidates: Vec<Price> = self.buys.keys().chain(self.sells.keys()).copied().collect();
            candidates.into_iter().map(|px| {
                let cb = self.cum_buy_at_or_above(px) + self.market_buys;
                let cs = self.cum_sell_at_or_below(px) + self.market_sells;
                let tradable = cb.min(cs);
                let imb = (cb as i64) - (cs as i64);
                UncrossingResult { clearing_px: px, matched_qty: tradable, imbalance: imb,
                                   residual_buys: cb - tradable, residual_sells: cs - tradable }
            })
            .max_by(|a, b| {
                a.matched_qty.cmp(&b.matched_qty)
                    .then_with(|| b.imbalance.abs().cmp(&a.imbalance.abs()))  // min imbalance
                    .then_with(|| {
                        let da = (a.clearing_px.0 as i64 - self.reference_px.0 as i64).abs();
                        let db = (b.clearing_px.0 as i64 - self.reference_px.0 as i64).abs();
                        db.cmp(&da)  // closer to reference wins
                    })
                    .then_with(|| b.clearing_px.0.cmp(&a.clearing_px.0))  // lower price wins
            })
            .unwrap()
        }
    }
    ```
    **Invariants**: (i) Clearing price is in `[best_bid, best_ask]` *of the auction book*, not necessarily of the continuous book. (ii) Matched qty is *exactly* equal to traded volume — every matched lot fills against the opposite side at clearing_px. (iii) Tie-break rules are deterministic and totally ordered; no ambiguity. (iv) Market orders fill before priced orders at clearing_px.
  - **Back-of-envelope**: target 10k-order auction uncross <1 ms = 100 ns/order budget. Naive enumeration: for each candidate price (~N unique prices), compute `cum_buy_at_or_above + cum_sell_at_or_below` = O(N) per candidate × N candidates = O(N²). For N=10k, that's 100M ops × ~5 ns/op = 500 ms — 500× over budget. Optimized: precompute cumulative arrays in O(N) via single passes (one ascending sweep for buys cumulative-above, one descending for sells cumulative-below); then each candidate evaluation is O(1) = 10k × ~10 ns = 100 µs total — 10× under budget. The 1 ms ceiling absorbs occasional cache misses. NO floats — `f64` divisions in tie-break (~10-30 cycles each = ~3-10 ns) + non-deterministic across architectures (x86 vs aarch64 FP rounding differs at the bit level). Use integer math throughout: prices in `i64` (e.g., satoshis or ticks), volumes in `u64`, imbalance as `i128`. Auctions are RARE (open/close/halt-resumption = ~4/day per symbol), so an extra ms is acceptable — but determinism across replicas is non-negotiable, so the algorithm MUST be allocation-free + float-free.
  - **Build steps**: 1. (~25 min) AuctionBook + buy/sell aggregation. 2. (~40 min) Candidate price enumeration. 3. (~35 min) `tradable` computation at each px (cumulative; O(n) per candidate or O(n) total with running sums). 4. (~35 min) Tie-break logic — *get every rule right*; this is the bug magnet. 5. (~25 min) Output: clearing_px + matched_qty + imbalance. 6. (~20 min) Fill assignment (separate concern): at clearing_px, orders fill in price-time priority on each side; tested in Tue. (~Tue test.)
  - **Pitfalls** (named, 4):
    - *Imbalance calc wrong sign*: **Symptom**: imbalance reported as negative when buy-side has excess → indicative-imbalance feed wrong, traders confused. **Fix**: explicit `imbalance = buy_qty - sell_qty`; positive = buy excess. Property test against hand-calculated 3 examples.
    - *Reference-price rule omitted*: **Symptom**: two prices tie on volume AND imbalance; picker chooses arbitrarily → non-deterministic. **Fix**: third tie-break = closer to reference (last continuous price). NYSE rule precisely.
    - *Tie-break edge cases (no continuous trade yet)*: **Symptom**: opening auction has no reference price — `reference_px = 0` → falls to lowest-price rule. **Fix**: configure `reference_px` from prior session's close or indicative. Document fallback.
    - *Market-order-induced inversion*: **Symptom**: large market sells push clearing very low; large market buys push it high; both present → clearing can be at any price in tradable range. **Fix**: market orders fill first at clearing_px; clearing_px chosen by limit-order curve crossing point. Document and test.
  - **Expect to hit (perf) #1 — `f64` in tie-break breaks cross-replica determinism (bar (c) violation)**: the design code uses `(a.clearing_px.0 as i64 - self.reference_px.0 as i64).abs()` which is integer-safe, BUT a typical first-draft writes `let distance = (px - ref_px).abs() as f64;` to apply a percentage-weighted tiebreak — that introduces float division (~10-30 cycles ≈ 10 ns) AND non-reproducibility: x86 `divsd` and aarch64 `fdiv` round differently for denormal inputs, and the IEEE-754 `fma` (fused multiply-add) is enabled by default on aarch64 but not x86, producing different last-bit results. Symptom: 3-replica auction test passes on M2 + Linux x86 individually but DIVERGES when run on a heterogeneous cluster; clearing_px differs by 1 tick in <0.1% of cases — undetectable except via cross-platform property test. Fix: integer math only. `abs_diff(px, ref_px) as u128` then compare. If ratios needed, use fixed-point `q64.64` arithmetic. CI lints `disallowed-types` for `f32`/`f64` in deterministic modules (already pattern in W80 ledger SM). Cost avoided: cross-replica divergence (catastrophic correctness bug, not just perf); also saves ~10 ns/tie-break × ~10k candidates = ~100 µs per auction. Muscle: deterministic state machines forbid floats — there is NO acceptable float in a replicated apply path. Reapplies at: W80 ledger SM (`time::wall()` and `rand` already banned; extend to floats), W81 circuit breaker bps math, W87 VOPR scenario generator (PRNG must be deterministic), W88 consensus-vsr log merge tiebreak, W92 ledger v1.0 settlement math.

  - **Design**:
    ```rust
    // In messaging-aeron crate, behind feature `archive` flag
    pub struct ArchiveRecorder {
        pub stream_id: i32,
        pub queue: Arc<MmapQueue>,         // from mmap-queue v0.5
        pub current_cycle: CycleId,
    }
    impl ArchiveRecorder {
        pub fn record_fragment(&mut self, frame: &[u8], position: i64) -> Result<()> {
            // Each Aeron frame → one mmap-queue entry tagged with (stream_id, position)
            self.queue.append(QueueEntry::new(self.stream_id, position, frame))?;
            Ok(())
        }
        pub fn replay(&self, from_position: i64, to_position: i64) -> impl Iterator<Item = ArchiveFrame> {
            self.queue.range(from_position..=to_position)
                .map(|entry| ArchiveFrame { position: entry.position(), data: entry.bytes() })
        }
    }
    ```
    **Invariants**: (i) Recorded frames are byte-for-byte the same as published frames (zero-copy). (ii) `position` is monotonic across cycle rotation — mmap-queue's cycle key maps to Aeron position. (iii) Cycle rotation (e.g., daily) bounds disk usage; old cycles deletable without affecting current.
  - **Build steps**: 1. (~15 min) ArchiveRecorder struct + queue handle. 2. (~20 min) `record_fragment` — append to queue with position tag. 3. (~15 min) `replay` — queue range iterator. 4. (~10 min) Integration test: publish 100 messages → record to queue → replay → bit-identical bytes.

  - **Test scenarios**: (a) 100k messages recorded, replayed → bit-identical. (b) Force cycle rotation mid-recording; replay spans cycles. (c) Replay with `from_position` in old cycle (deleted) → returns error gracefully.
  - **Acceptance**: record throughput ≥1M msg/s. Replay matches published. Inheritance: mmap-queue, bufpool.

- [ ] **Build**: `crates/messaging-aeron/src/transport_udp.rs` — UDP socket pool, recvmmsg/sendmmsg batching, MTU-aware
  fragmentation. (~105 min)
  - **Why**: UDP transport is how aeron talks across hosts. `sendmmsg/recvmmsg` batch I/O cuts syscalls by 100x vs per-packet `send/recv` (the Linux network stack's defining HFT optimization). MTU-aware fragmentation prevents IP-layer fragmentation (which fragments packets unpredictably). Bar (c) — Tier-A interview baseline.
  - **Read first**: Aeron `UdpChannelTransport.java`. Linux `sendmmsg(2)`/`recvmmsg(2)` man pages. Cloudflare blog "How to receive a million packets per second" (the canonical baseline). Solarflare/Mellanox kernel-bypass docs for the next level (out of scope here).
  - **Design**:
    ```rust
    pub struct UdpTransport {
        pub socket: UdpSocket,                       // bound to local addr; connected to remote? sometimes not (multicast)
        pub send_batch: Vec<mmsghdr>,                 // pre-allocated batch headers
        pub recv_batch: Vec<mmsghdr>,
        pub mtu: usize,                                // default 1452 (1500 - IP - UDP - Aeron frame)
        pub send_buffers: Vec<BytesMut>,
        pub recv_buffers: Vec<BytesMut>,
    }
    pub struct OutgoingFrame {
        pub dest: SocketAddrV4,
        pub data: Bytes,
    }
    impl UdpTransport {
        pub fn open(local: SocketAddrV4, opts: UdpOpts) -> Result<Self> {
            let socket = UdpSocket::bind(local)?;
            socket.set_nonblocking(true)?;
            // SO_RCVBUF / SO_SNDBUF tuned: 8 MiB default (sysctl net.core.rmem_max may need bump)
            socket.set_recv_buffer_size(8 * 1024 * 1024)?;
            socket.set_send_buffer_size(8 * 1024 * 1024)?;
            // SO_REUSEPORT for multi-receiver load-balancing
            socket.set_reuse_port(true)?;
            // IP_PKTINFO for receiving dst addr (multicast usage)
            // Don't Fragment bit on outgoing — avoid IP-layer fragmentation
            socket.set_dont_fragment(true)?;
            Ok(UdpTransport { socket, /* ... */ })
        }
        pub fn send_batch(&mut self, frames: &[OutgoingFrame]) -> Result<usize> {
            assert!(frames.iter().all(|f| f.data.len() <= self.mtu));
            // Fill mmsghdr array, call sendmmsg(2)
            unsafe { libc::sendmmsg(self.socket.as_raw_fd(), self.send_batch.as_mut_ptr(), frames.len() as u32, 0) }
        }
        pub fn recv_batch(&mut self, out: &mut Vec<(SocketAddrV4, Bytes)>) -> Result<usize> {
            // recvmmsg(2) up to MAX_BATCH (e.g., 64) packets
            unsafe { libc::recvmmsg(self.socket.as_raw_fd(), self.recv_batch.as_mut_ptr(), 64, libc::MSG_DONTWAIT, ptr::null_mut()) }
        }
        pub fn fragment(&self, frame: &[u8]) -> Vec<Bytes> {
            // If frame > mtu, split into BEGIN/MIDDLE/END fragments with Aeron flags
            frame.chunks(self.mtu - FRAME_HEADER_LEN).enumerate().map(|(i, c)| {
                let flags = if i == 0 { BEGIN_FRAG } else { 0 } | if /*last*/ { END_FRAG } else { 0 };
                /* construct fragment */
            }).collect()
        }
    }
    ```
    **Invariants**: (i) Outgoing frames `<= mtu` — anything larger is fragmented at Aeron level (BEGIN/MIDDLE/END flags). (ii) `set_dont_fragment(true)` — IP layer never fragments; if `frame > pmtu`, send returns EMSGSIZE (we don't expect this since we control mtu). (iii) Batched send/recv — every syscall amortized over 64 packets typical. (iv) `SO_REUSEPORT` allows multi-receiver scaling.
  - **Back-of-envelope**: target 1M pkt/s single-thread = 1 µs budget/pkt. Per-packet `sendto(2)` ≈ 1 µs uncontended (syscall ~300 ns + socket-layer + driver ~500 ns + checksum ~100 ns) → 1M pps is the BARE limit. With `sendmmsg(2)` batching 64 packets per syscall: amortized syscall cost ~5 ns/pkt + per-packet socket processing ~500 ns = ~500 ns/pkt → 2M pps comfortably. Cloudflare's "1M pps" baseline blog uses identical techniques. RX side: `recvmmsg(2)` with `MSG_DONTWAIT` returns up to 64 packets per syscall; saturating budget is similar. SO_RCVBUF=8 MiB is sized for 1 GbE burst at ~80 ms (typical app pause); on 25 GbE bump to 64 MiB. NUMA: socket buffer should be allocated on the NIC's NUMA node (set thread affinity to NIC's CPU mask BEFORE `bind`). Without NUMA-locality, each packet recv pays ~50 ns extra QPI/UPI cross-socket fetch — 50 ns × 1M pps = 50 ms/sec of pure cross-socket traffic. MTU sizing: Aeron's 1452 = 1500 (Ethernet) - 20 (IP) - 8 (UDP) - 20 (Aeron frame header) — leaves zero room for VLAN tag (4 B) or VPN encap (~40 B IPsec); set 1300 for any cloud/WAN path.
  - **Build steps**: 1. (~20 min) Socket setup with SO_* tuning + DF bit. 2. (~25 min) sendmmsg wrapper — pre-allocated mmsghdr arrays, populate from OutgoingFrame batch. 3. (~25 min) recvmmsg wrapper + buffer pool. 4. (~20 min) Fragmentation: split frames at MTU boundary with BEGIN/MIDDLE/END flags. 5. (~15 min) Reassembly side: stub for now; W78 Wed NAK protocol handles full reordering. (~Sat bench.)
  - **Pitfalls** (named, 3):
    - *MTU mismatch across hops*: **Symptom**: assumed 1500 MTU; intermediate router has 1400 (e.g., VPN tunnel) → DF + oversize = drop. **Fix**: discover Path MTU via PMTUD (ICMP feedback) or configure conservatively (1300 across WAN). Document the default.
    - *recvmmsg blocking*: **Symptom**: forgot MSG_DONTWAIT → call blocks until N packets arrive; in low-traffic mode latency tail. **Fix**: always MSG_DONTWAIT + spin/poll loop in `MediaDriver` receiver thread.
    - *SO_RCVBUF undersized*: **Symptom**: burst arrives, kernel buffer overflows, packets silently dropped — only observable via `netstat -su` UdpDrops counter. **Fix**: set RCVBUF=8MB + `sysctl net.core.rmem_max` documented as ops requirement; monitor UdpDrops in metrics.
  - **Expect to hit (perf) #1 — per-packet `sendto` instead of `sendmmsg` (bar (c) violation)**: caller writes a loop `for frame in frames { socket.send_to(&frame.data, frame.dest)?; }` — that's one syscall per packet (~1 µs) × 1000 frames in a batch = 1 ms of pure syscall overhead, capping throughput at 1M pps single-thread. Worse: each `sendto` runs the full socket-layer path (UDP checksum, route lookup, neighbor lookup) independently, losing the kernel's batched-checksum optimization. Symptom: bench shows 800k-1M pps ceiling regardless of CPU; `perf top` reports `syscall_enter_sendto` + `udp_sendmsg` at 60%+ of CPU. Fix: pre-populate `[mmsghdr; 64]` once at startup; `sendmmsg(fd, headers, 64, 0)` sends all in one syscall (~5 µs total = ~80 ns/pkt amortized). Pair with `io_uring_submit` in W89 for 0-syscall hot path (submission ring). Cost avoided: ~1 µs/pkt → ~80 ns/pkt = ~12× speedup at 1M pps that's ~920 µs/sec of syscall overhead reclaimed. Muscle: every batchable I/O on a bar-(c) hot path uses the batched syscall variant (`sendmmsg`, `recvmmsg`, `io_uring`) — never per-element. Reapplies at: W78 NAK retransmit batch, W83 archive recorder batched writes, W84 io_uring replay reads, W89 ledger v1.0 journal io_uring submission.
  - **Expect to hit (perf) #2 — recv buffer allocated per packet (bar (c) violation)**: naive recv loop `let mut buf = vec![0u8; 1500]; socket.recv_from(&mut buf)?;` allocates 1500 B + zeroes it on every packet = ~200 ns malloc + ~50 ns memset = ~250 ns/pkt of pure allocator overhead. At 1M pps, ~250 ms/sec; allocator becomes the bottleneck under multi-thread contention. Symptom: heaptrack shows 1M allocs/sec of 1500-byte chunks attributed to recv; CPU profile shows `__memset_avx2` significant. Fix: pre-allocated `RecvBufferPool` with 256 × 2 KiB slots (cache-line aligned); `recvmmsg` writes directly into pool slots; after handler processes each packet, the slot returns to the pool. With io_uring (W89), the kernel writes directly into pre-registered buffers — zero copies on the recv path. Cost avoided: ~250 ns/pkt × 1M pps = ~250 ms/sec; eliminates allocator contention; restores L1 D-cache. Muscle: recv buffers are pre-allocated and pooled, never per-packet allocated — `bufpool` (W12-W14) exists for exactly this. Reapplies at: W78 NAK retransmit buffer reuse, W82 Image reorder buffer slots, W83 archive frame buffer reuse, W85+ marketdata-kernelbypass (which IS this principle taken to AF_XDP).
  - **Test scenarios** (W78 Sat): induce 5% loss via `tc qdisc add dev lo root netem loss 5%`, verify recv counts. Bench: 10M pkt/s send loopback. Verify no allocations in send/recv hot path.
  - **Acceptance**: bench: ≥1M packet/s single-thread, P99 < 5 µs. Inheritance: bufpool (recv buffers), no async runtime. zero allocs hot path.
  - **Downstream**: W78 Wed NAK protocol detects loss using sequence numbers in the frame headers; uses transport_udp to request retransmits. W79 multicast (W80) extends with IGMP. W82 Image (Aeron Image module) layers reorder buffer atop this.

- [ ] **Build**: `crates/messaging-aeron/src/nak.rs` — gap detection by sequence number, NAK back to publisher, replay
  from term buffer's recovery slot. (~105 min)
  - **Why**: UDP doesn't guarantee delivery. Aeron uses **negative acknowledgements** (NAKs) instead of positive (TCP-style) — receiver reports *missing* sequence ranges, publisher retransmits. This minimizes bandwidth (one ack per loss event, not per packet) and keeps publisher state minimal. Bar (c) — the protocol is delicate (NAK storms are real production incidents).
  - **Read first**: Aeron `LossDetector.java`, `NakHandlerImpl.java`, `RetransmitHandler.java`. PGM RFC 3208 (the IETF NAK-based protocol Aeron evolved from). Real-Logic blog on loss detection.
  - **Design**:
    ```rust
    pub struct LossDetector {
        pub highest_seen: i64,                 // monotonic frame position
        pub gaps: BTreeMap<i64, GapState>,     // gap_start → state
        pub nak_delay: Duration,               // detection → first NAK delay (avoid spurious)
        pub nak_retransmit_delay: Duration,    // between retransmits
    }
    pub struct GapState {
        pub end: i64,                          // inclusive
        pub detected_at: Monotonic,
        pub last_nak_sent: Option<Monotonic>,
        pub nak_count: u32,
    }
    pub enum NakAction {
        SendNak { from: i64, to: i64, term_id: i32 },
        Quiet,
    }
    impl LossDetector {
        pub fn on_frame(&mut self, frame_position: i64) {
            if frame_position == self.highest_seen + 1 {
                self.highest_seen = frame_position;
            } else if frame_position > self.highest_seen + 1 {
                // Gap detected
                self.gaps.entry(self.highest_seen + 1).or_insert(GapState {
                    end: frame_position - 1,
                    detected_at: Monotonic::now(),
                    last_nak_sent: None,
                    nak_count: 0,
                });
                self.highest_seen = frame_position;
            } else {
                // Backfill: this fills a gap
                self.fill_gap(frame_position);
            }
        }
        pub fn tick(&mut self, now: Monotonic) -> Vec<NakAction> {
            self.gaps.iter_mut()
                .filter_map(|(&start, st)| {
                    let elapsed_since_detect = now - st.detected_at;
                    let should_send = match st.last_nak_sent {
                        None if elapsed_since_detect >= self.nak_delay => true,
                        Some(last) if now - last >= self.nak_retransmit_delay => true,
                        _ => false,
                    };
                    if should_send {
                        st.last_nak_sent = Some(now);
                        st.nak_count += 1;
                        Some(NakAction::SendNak { from: start, to: st.end, term_id: 0 })
                    } else { None }
                })
                .collect()
        }
    }
    ```

    **Invariants**: (i) `highest_seen` is monotonic — out-of-order frames are gap-fills, not regressions. (ii) Gap detection waits `nak_delay` before first NAK (reordering tolerance). (iii) Retransmit publisher's state is the term buffer itself — frames remain accessible for `3 * TERM_LEN` of data (three-term rotation). After that, NAK is unrecoverable → consumer must request state transfer (out of scope).
  - **Back-of-envelope**: NAK gap recovery latency budget < 1 ms typical / < 10 ms tail. nak_delay default 60 ms (Aeron default) — covers ~95% of natural network reordering (Linux netem reorder distribution: median ~5 ms, P99 ~50 ms on LAN). First retransmit after first NAK: ~RTT (loopback ~10 µs, LAN ~50 µs, WAN ~10 ms) + processing time on publisher (~1 µs to look up frame in term buffer). On hot path: `on_frame` = 1 atomic compare on `highest_seen` (~5 ns) + branch (~1 ns) + BTreeMap insert on gap (rare, ~100 ns) = ~10 ns/frame in steady-state. NAK storm suppression: if 100 subscribers NAK the same gap within `coalesce_window` (say 1 ms), publisher should retransmit ONCE — sending 100× is bandwidth amplification (DDoS-shape). Retransmit rate cap: `max_retransmit_rate=10 MB/s` per publication caps damage; under sustained 5% loss at 100 Mb/s, retransmit overhead ~5 Mb/s = 50% of budget — leaves headroom.

  - **Pitfalls** (named, 4):
    - *NAK storm*: **Symptom**: large loss event → 100 NAKs from 100 subscribers for same gap → publisher melts under retransmit load. **Fix**: publisher dedupes by gap range — coalesce NAKs within `coalesce_window`, send retransmit *once*. Aeron uses MulticastReceiverProxy with NAK suppression.
    - *NAK against retransmit*: **Symptom**: subscriber NAKs, publisher retransmits but lost packet en-route, subscriber NAKs again, publisher retransmits → infinite loop. **Fix**: exponential backoff on retransmits per gap (1 ms, 2 ms, 4 ms, ..., cap 1 s); after N attempts, drop subscriber.
    - *Head-of-line during recovery*: **Symptom**: NAK pending; subscriber blocks consumption of all subsequent frames until gap fills → HOL. **Fix**: subscriber buffers in-order frames after gap; delivers in-order *after gap fills* (reorder buffer in `image.rs` W82). Configure max buffer size.
    - *Out-of-term NAK*: **Symptom**: NAK for a frame that's been rotated out of term buffers → no source for retransmit. **Fix**: publisher detects out-of-window NAK, replies with "ResetSession" — subscriber must re-establish (full state transfer). Log + metric.
  - **Expect to hit (perf) #1 — BTreeMap gap-state lookup on hot recv path (bar (c) violation)**: `on_frame` calls `self.gaps.entry(self.highest_seen + 1).or_insert(...)` which is O(log N) BTreeMap walk (~50 ns at N=100 gaps) on EVERY frame, but 99.9%+ of frames are in-order (no gap). At 1M pps recv rate, that's ~50 ms/sec of pure BTreeMap navigation for the no-gap case. Worse: the BTreeMap is cold cache (only touched on gap events) — each lookup pays ~3 cache misses × ~100 ns = ~300 ns under adversarial layout. Symptom: NAK-disabled bench shows 2M pps; NAK-enabled bench shows 600k pps; flame graph dominated by `BTreeMap::range` / `BTreeMap::entry`. Fix: fast-path the common case — `if frame_position == self.highest_seen + 1 { self.highest_seen = frame_position; return; }` BEFORE any map operation. Only enter the BTreeMap branch if a gap is observed (rare). For gap tracking, also consider a bounded `ArrayVec<GapState, MAX_GAPS>` since real gap counts are <10 typical, <100 worst-case. Cost avoided: ~50 ns/frame × 1M pps = ~50 ms/sec of cold BTreeMap traversal; restores L1 cache for the recv path. Muscle: a hot-path data structure must be ABSENT from the common path; lookups only happen on the rare branch. Reapplies at: W82 Image reorder buffer (same pattern: in-order common case bypasses BTreeMap), W83 archive recorder (in-order common case bypasses index), W84 deterministic harness event-history append (common case bypasses sorted insert).
