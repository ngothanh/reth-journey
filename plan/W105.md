  - *Mental model*: a process-owned metric *registry* + a set of **pre-resolved scalar handles** handed to each venue crate at construction, plus a tiny read-only HTTP surface (`/metrics`, `/health`, `/ready`) that **snapshots — never long-locks — the registry**. Measurement must not perturb the measured: the VSR apply loop and the risk recompute are bar (c), so the emit they call is one atomic add, zero allocations.
  - *Contract* (signature-level — never the body):
    - `PromExporter::install(cfg: ExporterCfg) -> Result<PromExporter, InstallError>` (instance-owned registry; global-default install is single-shot, returns `Err(AlreadyInstalled)` not a panic).
    - `fn registry(&self) -> &Registry`; `fn serve(self, addr: SocketAddr) -> JoinHandle<()>`.
    - hot-path handles handed out at construction (pre-resolved, no per-call label lookup):
      `fn vsr_commit_num(&self) -> &[IntGauge; MAX_REPLICAS]`, `fn risk_recompute_us(&self, mode: RecomputeMode) -> &Histogram`, `fn insurance_fund_tripwire(&self) -> &IntGauge`.
    - `BoundedLabelVec<N>::with_label_values(&[&str]) -> Result<&IntCounter, LabelTooMany>` (cardinality bounded by construction).
  - *Back-of-envelope* (bar (b) tooling on a bar (c)-adjacent path — name the cost): at 1M ops/sec on the VSR log, an `inc()` that allocates 16 B = **16 MB/s of allocator pressure on (or beside) the hot path** — malloc ~50 ns each is ~50 µs of stolen CPU per ms. A pre-resolved handle is one atomic add (~3 ns, 0 allocs). A `with_label_values` lookup hashes a `&[&str]` (~30–60 ns + the alloc). Scrape of 6k series text-encodes ~6k × ~80 B = ~480 KB; at memcpy ~10 GB/s that's ~48 µs of pure encode, so p99 < 10 ms is generous unless you hold a contended lock against the apply loop. **Cliff: pre-resolved 3 ns vs label-lookup+alloc ~80 ns = ~25× per metric write, on the measured hot path.**

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `metrics_endpoint_emits_text_format` returns an empty body:**
    - Symptom: GET `/metrics` is 200 but body has no `risk_recompute_us_bucket` line.
    - Why: you registered the histogram into a *different* registry than the one `serve()` gathers from (instance vs default).
    - Fix: `serve()` gathers from `self.registry()` — the same instance the handles were registered on.
    - Muscle: one registry per exporter instance; handles and the HTTP surface must share it. Reapplies at: Tuesday venue-crate wiring, W107 `/ready` probe, W108 drill metric reads.

  - **(SENIOR) When `install_into_default_registry_twice_returns_error` panics with `metric duplicated`:**
    - Symptom: second `install()` panics inside `Registry::register` — same name registered twice in the process-global default registry.
    - Why: code used `prometheus::default_registry()` (a `Lazy<Registry>` static) — fine for one process, broken under cargo test which runs integration binaries in one process.
    - Fix: `Registry::new()` inside each `PromExporter::install`; reserve the global for `main()`, guarded once by `OnceCell::set` which returns `Err` on second set.
    - Cost avoided: a flaky suite with silent cross-test metric bleed that hides a real venue regression.
    - Muscle: prefer instance-owned state over process-global; reserve globals for `main()`. Reapplies at: W106 deploy test isolation, W107 manifest singleton.

  - **(SENIOR) When `cardinality_lint_rejects_unbounded_labels` doesn't fire and `/metrics` grows to 50 MB:**
    - Symptom: looping `with_label_values(&[&format!("acct_{i}")]).inc()` produces 1M distinct series; the lint returns ok.
    - Why: lint walked the registry once at test end but nothing enforced a hard cap during use; the raw `IntCounterVec` permits unbounded growth — and at 100k accounts this is the *exact* mistake that bricks the venue's `/metrics`.
    - Fix: wrap critical families in `BoundedLabelVec<N>` whose `with_label_values` returns `Err(LabelTooMany)` past the cap; `assert_cardinality_bounded` runs in `#[cfg(test)]` after any metric-mutating test. Account/order/settlement identity is NEVER a label — it's a span event (Tuesday's trace bridge) or nothing.
    - Muscle: cardinality is a structural invariant — enforce in the type, not in code review. Reapplies at: W106 chaos metrics, W107 projection-lag labels.

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  - **(SENIOR) When `parallel_invocations_serialize_via_flock` finds both scripts run:**
    - Symptom: both deploys start restarting replicas; quorum is eventually lost and the venue stops committing.
    - Why: lock raced during bootstrap, or used a PID file (survives crashes → false "free").
    - Fix: first line — `exec 200>/var/lock/ops-deploy-${service}.lock; flock -n 200 || { echo "deploy in progress"; exit 1; }`. The FD is held for the script's lifetime.
    - Muscle: `flock` on an FD held for the process lifetime is the cheapest mutex; never a PID/flag-file. Reapplies at: W107 manifest writer lock, W109 cron-job locks.

  - **(SENIOR) When `vsr_leader_restarted_last_after_stepdown` restarts the leader first or without a confirmed view-change:**
    - Symptom: restart log shows `leader_a` first; the cluster sees a ~300 ms election gap on every deploy and a brief commit stall on the one hot-path log.
    - Why: per-replica loop iterated `[a, b, c]` without probing `/admin/role`, or it sent `/admin/stepdown` but proceeded before confirming a new leader was actually elected.
    - Fix: per iteration probe `/admin/role`; if `Leader`, POST `/admin/stepdown`, re-probe and assert `Backup` AND a higher `view_num` (proof the view-change completed), then restart; iterate backups-first, leader-last.
    - Cost avoided: a ~300 ms commit stall per release — visible as a settlement-finality spike on `settlement_finality_us`.
    - Muscle: stateful systems require explicit stepdown AND confirmation before destructive ops; assume order is wrong until probed. Reapplies at: W107 rolling-restart validation, W109 leader-handling runbook.

  - **(EXPERT, perf) When `socket_activation_continuous_connectivity` reports ~500 ms refused:**
    - Symptom: the long-lived connection drops; new connections see ~500 ms refused per node restart.
    - Why: the unit lacked `Sockets=perp-dex-core@%i.socket`, or the binary didn't inherit the FD — new binary binds a fresh socket and waits on TIME_WAIT drain.
    - Fix: (a) `.service` declares `Sockets=` with `FileDescriptorName=listener`; (b) binary uses `listenfd::ListenFd::from_env()` to inherit by name; (c) old binary closes its socket only after SIGTERM + new binary "ready".
    - Cost avoided: ~500 ms connection-refused per node × 3 nodes per deploy (~100× the ≤5 ms budget) — visible client errors during every release.
    - Muscle: socket activation needs systemd config AND binary cooperation; one without the other is a ~500 ms outage. Reapplies at: W106 restart scenarios, W109 zero-downtime SLA.

  - **(SENIOR) When `version_skew_aborts_before_any_restart` reports `restart_log` is `["leader_a","backup_b"]`:**
    - Symptom: deploy eventually returns `Err(VersionSkew{replica:"backup_c"})`, but by then two replicas were already swapped — and `backup_c`'s log replay then fails against swapped peers.
    - Why: preflight ran `--check-log-format-compat` only on the FIRST replica, assumed homogeneity, began the restart loop, and didn't reach `backup_c` until two nodes were swapped (fatal because a prior partial rollout left the cluster heterogeneous).
    - Fix: preflight is a SEPARATE full all-nodes pass — `--check-log-format-compat` on EVERY replica first; abort if ANY mismatch BEFORE the first `reload-or-restart`; the new binary also reads the on-disk VSR log format version and compares.
    - Muscle: preflight is a paranoid all-nodes barrier that completes before any mutation — check every node, never just the first, never interleave checks with restarts. Reapplies at: W107 format-skew checks, W109 version-matrix enforcement.

  - **(EXPERT) When `snapshot_epoch_renumber_aborts` fails because the deploy proceeds and an outstanding `SettlementId` stops resolving:**
    - Symptom: a client holding `SettlementId(snapshot_epoch=4, op_number=N, checksum)` calls `finality_status` after the deploy and gets `Pending`/not-found instead of `Final` — the new binary renumbered epochs.
    - Why: the new binary's snapshot/compaction logic chose a fresh `snapshot_epoch` numbering incompatible with outstanding ids; the §4A guarantee ("op-numbers are interpreted relative to their epoch, so a client holding a `SettlementId` is never invalidated") was violated by the upgrade itself.
    - Fix: preflight asserts epoch-scheme compatibility; reject the deploy with `Err(SettlementIdWouldInvalidate)`; require the new binary to preserve epoch interpretation for all outstanding ids (a migration that re-maps, never renumbers-and-drops).
    - Cost avoided: every external client / chain holding a `SettlementId` silently invalidated by a routine deploy — the most insidious settlement bug, and a direct §4A acceptance-#4 regression.
    - Muscle: an identity derived from consensus state (op-number + epoch) must survive every operational action including upgrades; treat its stability as a deploy invariant. Reapplies at: W107 settlement-id durability checks, W117 audit.

  - **(EXPERT) When `sigkill_midflight_resumes_safely` re-restarts backup_b on resume:**
    - Symptom: re-invocation runs from scratch; backup_b restarts twice; 2× disruption (and a window where 2/3 are bouncing).
    - Why: state file wasn't written atomically — the second invocation found partial JSON and assumed clean state.
    - Fix: every state update writes `deploy-state.json.tmp` + `fsync` + rename → `deploy-state.json`; on start, resume from the next pending replica; if present-but-invalid, refuse.
    - Muscle: resume safety = atomic state writes + explicit refuse on corrupt state; "guess and proceed" is how 2/3-node restarts happen. Reapplies at: W107 deploy crash recovery, W109 deploy state file.

  - **(EXPERT) When `100_deploys_p99_and_finality_unchanged` drifts +30% by deploy 80:**
    - Symptom: each deploy adds a few ms to p99; cumulative drift exceeds 10% well before 100.
    - Why: each deploy briefly causes a view-change + commit catch-up; proceeding before catch-up completes starts the next deploy under elevated `vsr_commit_lag`, which amplifies.
    - Fix: tighten the catch-up gate — `commit_num_delta == 0` for 3 consecutive polls before releasing the lock (~2 s/replica/deploy for stability).
    - Muscle: rolling-restart stability needs strict catch-up gates, not relaxed ones; cumulative VSR lag drift bites at scale. Reapplies at: W107 replay SLAs, W109 deploy gates.
