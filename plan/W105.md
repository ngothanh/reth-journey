- [ ] **Build**: `crates/ops-monitoring/src/prometheus.rs` — `PromExporter` wrapping the `prometheus` crate. Standard
  recorders bound at `/metrics`. (~75 min)
  - **Why**: ops-monitoring is the *only* feedback loop on v2 hot-path crates once they're in the field. A
    matching-engine running at 1M orders/sec is opaque without per-shard histograms; mmap-queue cycle-rolls and VSR
    view-changes are invisible without per-cycle / per-replica counters. The exporter is "load-bearing" because
    silent regressions on the rig invalidate the entire 2000-hr uptime claim at M30.
  - **Read first**: `tikv/raft-rs` `src/metrics.rs` (encoders pattern); `tokio-rs/tracing` `tracing-subscriber/src/registry/`;
    `prometheus/client_rust/src/registry.rs`; reth `crates/node-core/src/metrics/prometheus_exporter.rs:1-180`
    (hyper-based `/metrics` server + recorder install).
  - **Design**:
    ```rust
    pub struct PromExporter {
        registry: prometheus::Registry,
        // Per-system metric families (Vec-labelled to fan out).
        runtime_shard_busy: HistogramVec,   // labels: shard_id
        mmap_cycle_roll:    IntCounterVec,  // labels: stream_id, reason
        vsr_view_change:    IntCounterVec,  // labels: replica_id, new_view
        vopr_scenarios:     IntCounter,     // monotonic — cumulative bar-(c) audit signal
        bind_addr: SocketAddr,
    }
    impl PromExporter {
        pub fn install(cfg: PromConfig) -> Result<Arc<Self>, ExporterError>;
        pub fn serve(self: Arc<Self>) -> JoinHandle<()>;   // hyper 0.14 service at /metrics
    }
    ```
    **Invariants**: (1) Registry is process-global; double-install panics in debug, returns `AlreadyInstalled` in
    release (tests must isolate via separate registries). (2) Histogram buckets are fixed at install — runtime mutation
    of buckets corrupts cumulative histograms exported across scrapes. (3) Label cardinality bounded: `shard_id` ≤ 64,
    `replica_id` ≤ 16, `stream_id` ≤ 32 — never use unbounded labels like `order_id`.
  - **Build steps**:
    1. (~10 min) Crate scaffold + dep on `prometheus = "0.13"`, `hyper = "0.14"`, `tokio` w/ `rt-multi-thread`.
    2. (~15 min) Define `HistogramVec` / `IntCounterVec` constants with fixed bucket layouts: shard busy buckets
       `[0.5us, 1us, 2us, 5us, 10us, 50us, 100us, 500us, 1ms, 10ms]`.
    3. (~20 min) `install()` — build registry, register all families, store in `OnceCell<Arc<PromExporter>>`.
    4. (~20 min) `serve()` — hyper service: `/metrics` (text-encode registry), `/health` (200 OK), `/ready` (depends on
       all systems reporting at least once).
    5. (~10 min) Smoke test: install, increment counter, scrape `/metrics`, assert text contains label.
  - **Pitfalls**:
    *DoubleRegister*: **Symptom**: process panics on second `install()` during integration test with two ledger
       instances. **Fix**: per-instance `Registry` (don't use `default_registry()`); pass `&Registry` into each system's
       metric constructors.
    *UnboundedLabel*: **Symptom**: `/metrics` payload grows to 50MB after a few hours; Prometheus scrape times out.
       **Fix**: lint via custom test that asserts `metric_families.iter().all(|m| m.get_metric().len() < 1024)`.
    *HistogramBucketChange*: **Symptom**: Grafana shows P99 collapse to 0 after a redeploy with new buckets.
       **Fix**: version histogram metric *names* (`shard_busy_us_v2`) when changing buckets so Prometheus treats them
       as distinct series.
    *RecorderOrdering*: **Symptom**: metrics observed *before* `install()` are silently dropped. **Fix**: call
       `install()` first in `main()` *before* any system constructor; assert with `Recorder::installed()` guard.
  - **Test scenarios** (adversarial): (a) two threads racing `install()` — only one wins, other gets `AlreadyInstalled`;
    (b) scrape `/metrics` concurrently with high-frequency `inc()` calls — text encoder must not deadlock; (c) drop the
    hyper server while a scrape is in flight — connection closes cleanly, no panic in background task.
  - **Acceptance**: scrape latency P99 < 10ms with 5k active series; zero allocations on the increment path (verified
    via `dhat` heap profile).
  - **Downstream**: every Phase 6 ops crate (`ops-deploy`, `ops-chaos`, `ops-runbooks`) consumes the same registry;
    M30 bar-(c) audit reads `vopr_scenarios` as the cumulative-VOPR-count gate.
- [ ] **Build**: `crates/ops-monitoring/src/tracing_bridge.rs` — tracing → OTLP exporter. (~75 min)
  - **Why**: Prometheus gives you scalars and histograms — it doesn't show *which order* caused the 2ms tail, or *which
    raft round* triggered a view-change. tracing-opentelemetry lets you cross-correlate spans across crates (e.g. an
    order span starts in `marketdata-kernelbypass`, propagates through `aeron`, lands in `matching-engine`, settles in
    `ledger-deterministic`). Without this bridge, on-call debugging of tail latency in production is guesswork.
  - **Read first**: `tokio-rs/tracing` `tracing-opentelemetry/src/layer.rs:1-300` (Span <-> OtelContext mapping);
    `open-telemetry/opentelemetry-rust` `opentelemetry-otlp/src/exporter/tonic/mod.rs` (gRPC client);
    reth `crates/tracing/src/lib.rs` (layer composition pattern, env-filter wiring).
  - **Design**:
    ```rust
    pub struct TracingBridge {
        tracer: opentelemetry::sdk::trace::Tracer,
        sampler: ParentBased<TraceIdRatioBased>,  // 1% sample by default; 100% on errors
        exporter_task: JoinHandle<()>,
    }
    impl TracingBridge {
        pub fn init(cfg: TracingConfig) -> Result<Arc<Self>, BridgeError>;
        pub fn shutdown(self) -> Result<(), BridgeError>;   // flush batch then close
    }
    // Subscriber layer stack: EnvFilter -> fmt::Layer (stderr) -> tracing-opentelemetry::layer().with_tracer(...)
    ```
    **Invariants**: (1) Shutdown is *blocking* — must drain the batch span processor or traces are lost on SIGTERM.
    (2) Span IDs propagate across crate boundaries via `tracing::Span::current().context()`. (3) Sampling decision is
    made at the root span and inherited by children — never re-sample mid-trace.
  - **Build steps**:
    1. (~10 min) Add deps `opentelemetry = "0.21"`, `opentelemetry-otlp = "0.14"`, `tracing-opentelemetry = "0.22"`,
       `tracing-subscriber = { version = "0.3", features = ["env-filter"] }`.
    2. (~20 min) Build the tracer: `opentelemetry_otlp::new_pipeline().tracing().with_exporter(...).install_batch(...)`.
    3. (~15 min) Compose subscriber: `Registry::default().with(EnvFilter::from_default_env()).with(fmt_layer).with(otel_layer)`.
    4. (~15 min) Wire shutdown into signal-handler so SIGTERM flushes before exit (BatchSpanProcessor needs `force_flush`).
    5. (~15 min) Smoke test: emit a span, attach an `order_id` field, verify it lands in jaeger UI (or a stub OTLP receiver
       in tests via `tonic`).
  - **Pitfalls**:
    *MissingFlush*: **Symptom**: SIGTERM during a burst loses the last ~5s of traces — exactly the spans you wanted.
       **Fix**: call `bridge.shutdown()` in `Drop` of a top-level guard and in the signal handler; verify with
       `tokio::test` that aborts mid-emit.
    *SamplerExplosion*: **Symptom**: when sampling jumps from 1% to 100% during incident, OTLP collector OOMs.
       **Fix**: cap effective span rate (`RateLimitedSampler` wrapping `ParentBased`) at e.g. 50k spans/sec.
    *FieldCardinality*: **Symptom**: attaching `order_id` as a span attribute blows up the trace backend (Jaeger Cassandra
       index, Tempo block size). **Fix**: only attach high-cardinality fields on error paths; use events not attributes for
       per-order data; verify Tempo block size remains < 100MB.
    *CrossCrateContextLoss*: **Symptom**: spans from `aeron` show no parent — they're orphaned root spans. **Fix**: when
       crossing a tokio-task or channel boundary, *manually* propagate `tracing::Span::current()` via
       `instrument(span.clone())` on the spawned future.
  - **Test scenarios**: (a) inject a 10-deep span tree and verify all levels show parent-child in the exporter stub;
    (b) drop the OTLP collector — bridge must continue (drop spans, log a warning) without blocking app threads;
    (c) shutdown under load — final flush completes within 5s deadline.
  - **Acceptance**: zero-blocking on the application thread (BatchSpanProcessor offloads); export latency tolerates
    a 10s collector outage without dropping spans inflight in the bounded queue.
  - **Downstream**: ops-chaos uses span IDs to correlate "fault inject at T" with "view-change observed at T+δ"; the
    M30 bar-(c) audit cross-references `vopr_scenarios` counter with the trace of the offending scenario.

- [ ] **Build**: `ops-deploy/scripts/blue_green.sh` — blue/green deployment via systemd socket activation. (~75 min)
  - **Why**: rolling restart of a stateful 3-replica raft cluster is the *single most likely* source of correctness bugs
    in production. Naive `systemctl restart` of all three replicas kills quorum; a `systemctl restart matching-engine`
    on the *leader* without first stepping down causes a 200-500ms latency cliff; a *version-skew* deploy can corrupt
    the WAL if a new replica writes a record an old replica can't replay. Blue/green via socket activation lets the
    new binary bind the listening socket before the old binary releases — *zero-downtime* on a single host, but the
    raft-cluster ordering is still load-bearing.
  - **Read first**: `man systemd.socket` (sections "Triggering" + "FileDescriptorName="); `tikv-rs` deploy scripts
    (their leader-step-down sequence); `etcd-io/etcd` `tools/etcd-tester` (rolling-restart harness, especially the
    "wait for quorum" probe).
  - **Design** (shell + small Rust helper):
    ```bash
    # blue_green.sh <service> <new_binary>
    # 1. preflight: SHA256 binary, verify cargo-dist signature
    # 2. for each replica in stepdown_order:
    #      probe role via /admin/role (must be Follower or step-down via /admin/stepdown)
    #      systemctl reload-or-restart <service>@<replica_id>.service
    #      wait_for_health <replica_id> (poll /ready, timeout 30s)
    #      wait_for_in_sync <replica_id> (poll raft commit index vs cluster max, timeout 60s)
    # 3. assert post: quorum size unchanged, no replica left behind
    ```
    **Invariants**: (1) Never restart a replica without first verifying the cluster has a healthy leader on *another*
    node. (2) Never restart *two* replicas simultaneously in a 3-node cluster (would lose quorum). (3) Version-skew
    window must be ≤ 1 minor version — enforced by a `version_compat_matrix.toml` consulted in preflight.
  - **Build steps**:
    1. (~10 min) systemd unit templates: `matching-engine@.service` with `Sockets=matching-engine@%i.socket` so the
       socket survives the binary swap.
    2. (~15 min) `/admin/role` and `/admin/stepdown` HTTP endpoints in matching-engine (tiny axum router on a private
       port).
    3. (~25 min) `blue_green.sh` core loop: stepdown_order = [followers..., leader_last]; per-replica probe + restart.
    4. (~15 min) Health probe helper: poll `/ready` with exponential backoff; fail-fast if any replica is unreachable.
    5. (~10 min) Post-deploy verifier: query each replica's commit index, assert max-min ≤ 1 (allow one round of lag).
  - **Pitfalls**:
    *RestartTwoAtOnce*: **Symptom**: parallel ansible/k8s pushes restart 2/3 replicas in the same second; cluster
       loses quorum; pending writes stall 60s+. **Fix**: serialize via a flock on a shared deploy lockfile; reject
       deploys when raft cluster size is 3 and any replica is not `Healthy`.
    *StaleSocketFD*: **Symptom**: new binary inherits an FD pointing to the *previous* listening socket — clients see
       connection-refused for ~5ms. **Fix**: use systemd's `FileDescriptorName=` and call `sd_listen_fds_with_names()`
       in matching-engine's bootstrap path (via the `listenfd` crate); verify socket FD matches expected fd-name.
    *VersionSkewWAL*: **Symptom**: new replica writes a WAL record with a new format-version byte; old replicas replay
       it as garbage on the next restart. **Fix**: every WAL record carries a `format_version: u16` header; old binary
       refuses-to-replay anything with a version > its compile-time max; deploy script asserts all replicas pass
       `--check-format-compat` before proceeding.
    *JWTRotationMidDeploy*: **Symptom**: rotating the inter-replica JWT signing key mid-rolling-restart leaves one
       replica unable to authenticate to the others. **Fix**: two-phase rotation — distribute new key as *verifier*
       first (all replicas accept both old and new), wait for full propagation, *then* rotate the signer; never
       interleave with binary rollout.
  - **Test scenarios** (adversarial): (a) inject a 30s pause between step-down and restart of the leader — verify a
    new leader is elected and the deploy continues against the new follower; (b) kill the deploy script mid-restart
    (e.g. SIGKILL) — next invocation must detect a half-restarted state and resume safely; (c) deploy a binary that
    crashes on bind — script must fall back and re-promote the prior version's socket.
  - **Acceptance**: 100 consecutive blue/green deploys against a 3-replica matching-engine cluster under 10k orders/sec
    load, with P99 latency unchanged ±10% and zero ledger reconciliation drift across all 100 deploys.
  - **Downstream**: ops-chaos uses `blue_green.sh` as a chaos primitive ("deploy mid-burst" scenario); the W107
    rolling-restart validation explicitly exercises this script; M30 bar-(c) audit cites successful blue/green count
    as evidence of operational maturity.
