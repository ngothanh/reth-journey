  #### Phase 3 — Make the tests pass, one failure at a time (~51 min)

  Ordered newbie→expert — the ladder you actually walk.

  - **(NEWBIE) When `metrics_endpoint_emits_text_format` returns an empty body:**
    - Symptom: GET `/metrics` is 200 but body has no `shard_busy_us_bucket` line.
    - Why: you registered the histogram into a *different* registry than the one `serve()` gathers from (instance vs default).
    - Fix: `serve()` gathers from `self.registry()` — the same instance the handles were registered on.
    - Muscle: one registry per exporter instance; handles and the HTTP surface must share it. Reapplies at: W106 ops-chaos metric wiring, W107 `/ready` probe wiring.

  - **(SENIOR) When `install_into_default_registry_twice_returns_error` panics with `metric duplicated`:**
    - Symptom: second `install()` panics inside `Registry::register` — same name registered twice in the process-global default registry.
    - Why: code used `prometheus::default_registry()` (a `Lazy<Registry>` static) — fine for one process, broken under cargo test which runs integration binaries in one process.
    - Fix: `Registry::new()` inside each `PromExporter::install`; reserve the global for `main()`, guarded once by `OnceCell::set` which returns `Err` on second set.
    - Cost avoided: flaky test suite — silent cross-test metric bleed that hides real failures.
    - Muscle: prefer instance-owned state over process-global; reserve globals for `main()` only. Reapplies at: W106 ops-chaos test isolation, W107 manifest singleton.

  - **(SENIOR) When `cardinality_lint_rejects_unbounded_labels` doesn't fire and `/metrics` grows to 50 MB:**
    - Symptom: looping `with_label_values(&[&format!("order_{i}")]).inc()` produces 1M distinct series; the lint returns ok.
    - Why: lint walked the registry once at test end but nothing enforced a hard cap during use; the raw `IntCounterVec` permits unbounded growth.
    - Fix: wrap critical families in a `BoundedLabelVec<N>` newtype whose `with_label_values` returns `Err(LabelTooMany)` past the cap; `assert_cardinality_bounded` runs in `#[cfg(test)]` after any metric-mutating test.
    - Muscle: cardinality is a structural invariant — enforce in the type, not in code review. Reapplies at: W106 ops-chaos chaos metrics, W107 manifest version labels.

  - **(SENIOR) When `bucket_change_requires_new_metric_name` shows p99 collapsing to 0 after a "redeploy":**
    - Symptom: v1 buckets → v2 buckets under the same metric name; Grafana `histogram_quantile(0.99,…)` returns 0.
    - Why: new bucket boundaries have no historical cumulative counts at the old `le` values the quantile function interpolates across.
    - Fix: bucket changes require a NEW metric name (`shard_busy_us_v2`); old name lingers until consumers migrate. Document `bucket_versioning.md`.
    - Muscle: metric names are an API contract; semantic change (buckets/units/label-set) ⇒ new name. Reapplies at: W105 Thursday Grafana dashboards, W109 production metric stability.

  - **(EXPERT, perf) When `inc_path_allocates_zero_bytes` reports +16 MB across 1M calls:**
    - Symptom: `dhat` shows ~16 B/call in `with_label_values`; profile points at `String::from` / `Vec<&str>` in the prometheus crate's label hashing.
    - Why: each `inc()` does `counter_vec.with_label_values(&["shard_0"])`, allocating a `Vec<&str>` and hashing per call.
    - Fix: pre-resolve at construction — `let shard: [IntCounter; 64] = std::array::from_fn(|i| vec.with_label_values(&[&i.to_string()]));`. Hot path is `shard[id].inc()` — pure atomic.
    - Cost avoided: 16 B/inc × 1M/s = ~16 MB/s allocator pressure adjacent to the bar-(c) hot path; pre-resolution is 0 B, ~3 ns/inc (~25× faster per write).
    - Muscle: pre-resolve handles outside the hot loop; hash-by-label belongs in setup, not the loop. Reapplies at: W105 Tuesday per-shard counter wiring, W106 ops-chaos counter init.

  - **(EXPERT, perf) When `scrape_p99_under_10ms_at_5k_series` reports p99 = 45 ms:**
    - Symptom: scrape time grows super-linearly with series count.
    - Why: encoder cloned the whole metric map per scrape or re-sorted O(n²); or `/metrics` re-registered handles per request.
    - Fix: `registry.gather()` once → `TextEncoder::encode(&families, &mut buf)` into a reused `Vec<u8>`; register handles at startup only.
    - Cost avoided: a 45 ms scrape every 15 s competing for the app's cache/CPU — measurement perturbing the measured.
    - Muscle: scrape is a bounded read with a reused buffer; never allocate-per-scrape or re-register. Reapplies at: W109 production scrape SLOs.

  - **(EXPERT) When `concurrent_scrape_and_inc_no_deadlock` deadlocks under load:**
    - Symptom: ~5 s in, all threads block; tokio runtime parks; `check_deadlock()` reports a cycle.
    - Why: the hyper handler held a long `registry.gather()` under a `Mutex` that the `inc()` path also contends → circular wait.
    - Fix: `gather()` snapshots (the prometheus crate's gather is internally short-locked — verify in its source) and `encode()` runs outside any app lock; scrapes never hold a write-contended lock.
    - Muscle: scrapes are reads; a read must never hold a lock that writers contend on. Reapplies at: W106 ops-chaos scrape, W109 production scrape SLOs.
