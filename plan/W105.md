  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: a production system without metrics is a guessing game. With
    metrics but unbounded label cardinality, the metrics system collapses your monitoring stack. With
    metrics that allocate on the hot path, the act of measurement perturbs the thing being measured.
    PromExporter has to be (a) zero-allocation on `inc()` / `observe()`, (b) bounded in series cardinality
    by construction, (c) stable across redeploys so Grafana queries don't break, and (d) testable in
    isolation across multiple integration-test processes.

  - **Requirements** — write in `crates/ops-monitoring/notes/105_prometheus_design.md`:
    - R1. `install(cfg)` is idempotent in tests — second install with a *new* registry succeeds; second
      install with the *default* global registry returns `Err(AlreadyInstalled)` instead of panicking.
    - R2. Histogram bucket layouts are fixed at install. Mutating buckets at runtime is rejected at
      compile-time (they're `const`) and bucket changes across releases require a versioned metric name
      (e.g. `shard_busy_us_v2`).
    - R3. Label cardinality is bounded by construction — `shard_id` ≤ 64, `replica_id` ≤ 16, `stream_id`
      ≤ 32. A unit test asserts `metric_families.iter().all(|m| m.get_metric().len() < 1024)`.
    - R4. `inc()` / `observe()` on the hot path allocates zero heap bytes (verified via `dhat`).
    - R5. `serve()` exposes `/metrics` (text-encoded), `/health` (200 always), `/ready` (200 only when
      every registered system has reported at least once).
    - R6. Scrape latency p99 < 10 ms with 5k active series.
    - R7. Concurrent scrape vs `inc()` storm never deadlocks — text encoder takes a snapshot, not a long
      lock.

      Reapplies at: W106 ops-chaos test isolation, W107 manifest singleton.

  - **When `inc_path_allocates_zero_bytes` reports +1.6 MB allocation across 1 M calls:**
    - Symptom: `dhat` shows ~16 bytes/call allocation in `with_label_values`; profile points at
      `String::from` inside the prometheus crate's label hashing.
    - Why: every `inc()` call does `counter_vec.with_label_values(&["shard_0"])` which allocates a
      `Vec<&str>` and computes a hash on each call.
    - Fix: at construction time, pre-resolve the per-shard `IntCounter` handle: `let shard_counters:

      Hot path is `shard_counters[shard_id].inc()` — pure atomic, zero allocation.
    - Cost avoided: 1.6 MB/1 M inc — at 1 M orders/sec that's 1.6 MB/sec of allocator pressure on
      the hot path. With pre-resolution: 0 bytes, ~3 ns/inc.
    - Muscle: pre-resolve handles outside the hot loop; hash-by-label belongs in setup, not the loop.
      Reapplies at: matching-engine per-shard counter wiring (W105 Tue), W106 ops-chaos counter init.

  - **When `cardinality_lint_rejects_unbounded_labels` doesn't fire and `/metrics` grows to 50 MB:**
    - Symptom: a test that loops `counter.with_label_values(&[&format!("order_{i}")]).inc()` for 1 M
      iterations produces 1 M distinct series; lint helper returns ok.

      registry permits unbounded growth.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: without span correlation across processes, a tail latency
    incident becomes "guess which subsystem". With naive `info!()` logs in a microservice mesh, you have
    timestamps and no causality. With OTLP spans + W3C TraceContext propagation, you have a tree per
    request, the bridge between Prometheus alerts and the actual code path that caused them. The bridge
    must be (a) zero-blocking on application threads, (b) tolerant of collector outages without dropping
    in-flight spans, (c) sampling-stable so the same trace shows up coherently end-to-end, and
    (d) flushing on SIGTERM so the spans that explain a crash actually reach the backend.

  - **Requirements** — write in `crates/ops-monitoring/notes/105_tracing_bridge_design.md`:
    - R1. `init(cfg)` returns a guard whose `Drop` blocks on `BatchSpanProcessor::force_flush` with a
      deadline (default 5 s). SIGTERM handler invokes shutdown explicitly before exit.
    - R2. Application threads NEVER block on span emit — `tracing::info_span!()` enqueues to a bounded
      channel; the exporter task drains it. Backpressure: when queue full, oldest span dropped, counter
      `dropped_spans_total` incremented.
    - R3. Sampling decision happens AT THE ROOT SPAN only (`ParentBased<TraceIdRatioBased>`); children
      inherit. Mid-trace re-sampling is forbidden by the sampler choice.
    - R4. Effective span rate is capped (e.g. 50k spans/sec) via a `RateLimitedSampler` wrapper, so
      "incident mode" 100% sampling doesn't OOM the OTLP collector.
    - R5. Span attributes are bounded cardinality (no `order_id` as a top-level attribute); high-card
      fields live as span *events*, not attributes.
    - R6. Cross-crate context propagation: when a future is spawned across a tokio task boundary, the
      span context propagates via `.instrument(span.clone())`. A lint test catches `tokio::spawn(async
      {…})` that doesn't propagate.
    - R7. Collector outage tolerance: 10 s collector downtime doesn't lose any spans that fit in the
      bounded queue.

  - **Design walk-through** — answer each in your design doc; no peeking at `tracing-opentelemetry/src/layer.rs`
    or reth `crates/tracing/src/lib.rs` until Phase 3:
    - D1. Subscriber layer composition: list the layer stack from inner to outer. Why does `EnvFilter`
      go before `fmt::Layer` and OTLP layer? (Hint: filtering early avoids work in disabled spans.)
    - D2. Sampler choice: `AlwaysOn` vs `ParentBased<TraceIdRatioBased(0.01)>` vs `RateLimitedSampler`
      wrapper. Argue from R3 + R4 — which combo satisfies both?
    - D3. Span queue sizing: bounded channel of N spans. What's N? Compute from "expect 10k spans/sec,
      tolerate 10 s collector outage → N = 100k". Memory budget per span?
    - D4. Shutdown sequencing: SIGTERM handler must (a) stop accepting new spans, (b) drain the queue,
      (c) flush exporter, (d) close gRPC stream. What's the deadline budget for each step?
    - D5. Cross-task propagation: list 3 common patterns where context is lost (`tokio::spawn` without
      `instrument`, `mpsc::Receiver::recv` without manual context attach, raw thread::spawn). For each,
      name the fix.
    - D6. High-card field policy: `order_id` on a span attribute breaks Tempo block size (~100 MB
      threshold). What's the policy? (Hint: events not attributes; structured fields not span names.)
    - D7. **Pre-mortem (the load-bearing question)**: write the 6-step interleaving where SIGTERM during
      a burst loses the last 5 s of traces — the spans that would have explained why the process is
      shutting down. Show why `Drop` in a top-level guard + explicit signal handler invocation
      both have to be present.
  - **Output**: `notes/105_tracing_bridge_design.md` with R1–R7, answers to D1–D7, layer-stack diagram,

  - **When `sigterm_during_burst_loses_no_spans` reports ~5000 spans missing:**
    - Symptom: SIGTERM kills the process before BatchSpanProcessor's 5 s timer fires; in-queue spans
      never reach the OTLP exporter.
    - Why: Drop ran but `BatchSpanProcessor` only flushes on its periodic timer (default 5 s); without
      explicit `force_flush`, in-flight batches are abandoned at process exit.
    - Fix: top-level guard's `Drop` calls `tracer.shutdown()` which internally calls
      `BatchSpanProcessor::force_flush(deadline)`. SIGTERM handler ALSO calls `bridge.shutdown()` so
      the signal-handler path doesn't depend on Drop ordering.
    - Muscle: any batched exporter needs both Drop AND explicit signal-handler flush; don't trust Drop
      ordering across multiple guards. Reapplies at: W107 manifest writer shutdown, W109 production
      crash-dump signal handler.

  - **When `application_thread_never_blocks_on_emit` reports p99 = 20 ms:**
    - Symptom: `info_span!()` latency tail correlates exactly with collector network round-trip; the
      emit path is synchronously calling the exporter.
    - Why: subscriber layer was `SimpleSpanProcessor` (synchronous export per span) instead of
      `BatchSpanProcessor` (queues, exports on a background task).
    - Fix: `BatchSpanProcessor::builder(exporter).with_max_queue_size(100_000).build()`. Emit path
      becomes a channel send (~µs); export runs on a tokio task that's outside the app's hot threads.
    - Cost avoided: 19 ms p99 on the hot path; at 10k orders/sec, that's a 190-second-of-CPU-time-per-second
      pile-up. Without batching, the app can't keep up.
    - Muscle: any exporter on the hot path is wrong; always batch and offload. Reapplies at: W105
      Tuesday metric emit, W107 manifest write path.

  - **When `sampling_decision_stable_across_trace` reports 30 spans missing (the children of unsampled root):**
    - Symptom: 70 of 101 spans show up; the 30 missing are from a child task that lost the sampling
      decision.
    - Why: child task created a NEW root span instead of inheriting; `ParentBased` sampler decided
      independently and rolled the dice again.
    - Fix: ensure the spawned future's first span is created via `tracing::info_span!(parent: &parent_span,
      "child")` so the parent-child relationship is explicit. The `ParentBased` sampler then inherits
      the parent's sampling decision deterministically.
    - Muscle: parent linkage in tracing is explicit at span construction; never rely on "current span"
      across thread boundaries. Reapplies at: W106 ops-chaos span correlation, W109 production trace
      consistency.

  - **When `rate_limiter_caps_at_50k_per_sec` shows 180k spans delivered:**
    - Symptom: rate limiter is not engaged; exporter saturates the collector.
    - Why: `ParentBased<TraceIdRatioBased(0.01)>` is a sampling decision, not a rate cap. At 200k spans
      attempted with 100% effective ratio (incident mode), all 200k flow through.
    - Fix: wrap the chosen sampler with a `RateLimitedSampler { inner: parent_based, max_per_sec: 50_000 }`
      that returns `SamplingDecision::Drop` once the per-second budget is exhausted.
    - Muscle: sampling ratios and rate limits are orthogonal; you usually need both. Reapplies at: W106
      ops-chaos chaos-test sampling, W109 production incident-mode sampling.

  - **When `unpropagated_spawn_breaks_parent_chain` fails (i.e. child IS chained when it shouldn't be):**

    - Why: maybe a fancy "auto-instrument" wrapper layer was added that snapshots the current span at
      spawn time. That sounds nice but creates surprise — devs expect explicit `.instrument`.
    - Fix: do NOT add auto-instrumentation. The negative regression test is a documentation guarantee:
      "if you forget `.instrument`, your span is orphaned." Surface this in CI lint.
    - Muscle: explicit propagation is better than magic; magic context-propagation breaks subtly under
      `tokio::spawn_blocking` or `std::thread::spawn`. Reapplies at: W106 ops-chaos test spawn,
      W109 production span propagation discipline.

  - **When `collector_10s_outage_zero_loss` reports 7k spans dropped during outage:**

    - Why: queue capacity (1k spans) too small for the outage budget (10 s × 10k spans/sec = 100k spans).
    - Fix: queue capacity = `expected_rate * tolerance_window` + 50% headroom. For 10k spans/sec + 10 s

      pipeline. Reapplies at: W26 WAL queue, W104 segment write queue, W109 production queue SLAs.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: production restarts are the highest-correlation event with
    real outages. Most "incident reports" trace back to a deploy that violated one of three invariants:
    (a) restarted two replicas of a 3-node cluster simultaneously, losing quorum; (b) restarted the leader
    without graceful stepdown, causing a leader-election storm; (c) deployed a binary with WAL format
    skew, corrupting state on the next read. The script must enforce all three by construction, AND
    must be resumable after partial failure (deploys get killed too).

  - **Requirements** — write in `crates/ops-deploy/notes/105_blue_green_design.md`:
    - R1. The script NEVER restarts two replicas of a 3-node cluster simultaneously. Enforced via a
      shared `flock` on `/var/lock/ops-deploy-${service}.lock`.
    - R2. The script ALWAYS restarts followers first, leader last. Leader-restart is preceded by an
      explicit `/admin/stepdown` call + readback of the new leader before proceeding.

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)

  - **When `parallel_invocations_serialize_via_flock` finds both scripts run:**
    - Symptom: both deploys start restarting replicas; eventually quorum is lost and the test panics.
    - Why: lock acquisition used `flock --nonblock` and silently succeeded for the second instance
      because the first hadn't yet acquired (race in the script's bootstrap).
    - Fix: first line of the script is `exec 200>/var/lock/ops-deploy-${service}.lock; flock -n 200 ||
      { echo "deploy in progress"; exit 1; }`. The FD is held by the script process; second invocation
      finds it locked and exits immediately.
    - Muscle: flock on an FD held for the lifetime of the script is the cheapest mutex; never use a
      flag-file (PID file) — they survive crashes. Reapplies at: W107 manifest writer lock,
      W109 production cron-job locks.

  - **When `leader_restarted_last_after_stepdown` finds the leader was restarted first or without stepdown:**
    - Symptom: restart-order log shows leader_a restarted first; cluster sees a 500 ms leader-election
      gap.
    - Why: script's per-replica loop iterated in `[a, b, c]` order without first probing `/admin/role`.
    - Fix: per-iteration, probe `/admin/role` on the replica about to be restarted. If `Leader`,
      POST `/admin/stepdown` then poll `/admin/role` again — assert it's `Follower`, then proceed.
      Iterate from the BACK of the role-sorted list: followers first, leader last.
    - Muscle: stateful systems require explicit leader-step-down before destructive ops; assume order
      is wrong unless probed. Reapplies at: W107 rolling restart validation, W109 production runbook
      leader handling.

  - **When `socket_activation_continuous_connectivity` reports ~500 ms of connection-refused:**
    - Symptom: the long-lived TCP connection drops during restart; new connections see refused for
      half a second.
    - Why: systemd unit didn't have `Sockets=matching-engine@%i.socket`; OR the binary didn't call
      `sd_listen_fds_with_names()` to inherit the FD. Result: new binary binds a fresh socket and
      kernel has to drain TIME_WAIT before accepting.
    - Fix: (a) `matching-engine@.service` declares `Sockets=matching-engine@%i.socket` with
      `FileDescriptorName=metrics`. (b) Binary bootstrap uses `listenfd::ListenFd::from_env()` and
      asks for FD by name. (c) Old binary's shutdown closes its bound socket AFTER receiving SIGTERM
      and AFTER new binary signals "ready" (or systemd's socket-activation does this implicitly).
    - Muscle: socket activation needs both systemd config AND binary cooperation; one without the
      other is a 500 ms outage waiting. Reapplies at: W106 ops-chaos restart scenarios, W109 production
      zero-downtime SLA.

  - **When `sigkill_midflight_resumes_safely` re-restarts follower_b on resume:**
    - Symptom: re-invocation runs the full sequence from scratch; follower_b is restarted twice; cluster
      sees 2× the disruption.
    - Why: state file wasn't written atomically (rename), so the second invocation either didn't find
      it OR found a partial JSON and assumed clean state.
    - Fix: every state-update writes to `deploy-state.json.tmp` + `fsync` + rename → `deploy-state.json`.
      On script start, read state file; if present and valid, resume from the next pending replica. If
      present but invalid (CRC mismatch or JSON parse error), refuse to proceed and require operator
      to manually delete it (R6 case 2).
    - Muscle: resume safety = atomic state writes + explicit refuse on corrupt state; "guess and
      proceed" is how 2/3-replica restarts happen. Reapplies at: W107 manifest crash recovery,
      W109 production deploy state file.

  - **When `version_skew_aborts_preflight` proceeds anyway:**
    - Symptom: script restarts a replica with an incompatible new binary; WAL replay on the next
      restart fails.
    - Why: preflight ran `--check-format-compat` only on the FIRST replica, assumed homogeneity.
      In a partial-rollout scenario (a prior deploy left one replica behind), heterogeneity is real.
    - Fix: preflight invokes `--check-format-compat` on EVERY replica; aborts if ANY mismatch.
      Additionally, the new binary's `--check-format-compat` reads the current replica's WAL format
      version from disk and compares.
    - Muscle: preflight is paranoid — check every node, not the first one. Reapplies at: W107 raft
      format-skew checks, W109 production version matrix enforcement.

  - **When `100_deploys_p99_unchanged` shows p99 drifts +30% by deploy 80:**
    - Symptom: each deploy adds a few ms to p99; by the 100th iteration, total drift is well over 10%.
    - Why: each deploy briefly causes a leader-election + log catch-up; if the script proceeds before
      catch-up completes, the next deploy starts under elevated lag and amplifies.
    - Fix: tighten the catch-up gate: the "in-sync" probe must show `commit_index_delta == 0` (not
      ≤ 1) for 3 consecutive polls before releasing the lock. Costs ~2 s per replica per deploy in
      exchange for stability.
    - Muscle: rolling-restart stability needs strict catch-up gates, not relaxed ones; cumulative drift
      bites at scale. Reapplies at: W107 raft replay SLAs, W109 production deploy gates.

  - **5-year failure mode** (write in `notes/105_blue_green_followup.md` after green): when cluster
    size grows beyond 5 replicas (geographic distribution, multi-AZ), serial follower-restart becomes
    the bottleneck (each replica takes ~30 s, 5 replicas = 2.5 min deploy). Migration trigger: parallel
    follower restart within a "blast radius" (e.g. one AZ at a time). Name the new invariant
    (no two failure-domain peers restarted simultaneously) and how the lock structure evolves.
