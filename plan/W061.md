**Monday — EOF EIP deep re-read**

- [ ] Re-read EIP-3540, 3670. EOF container format. (~45 min)
  - **Why**: EOF (EVM Object Format) is the largest EVM change since The Merge — replacing the "everything-is-bytecode" mess with a structured container (magic + version + section table + code + data). Pre-deployment validation eliminates entire classes of bugs (invalid jumps, mid-PUSH JUMPDESTs). Critical for understanding upcoming mainnet (Prague?) hard forks. Citing Ipsilon repo + Reth EOF PRs ensures spec-current understanding.
  - **Read first**:
    - EIP-3540 (EOF container format), EIP-3670 (code validation), EIP-4200 (static relative jumps), EIP-4750 (functions: CALLF, RETF), EIP-5450 (stack validation)
    - github.com/ipsilon/eof (reference spec impl)
    - reth + revm open PRs touching `eof_*.rs`
  - **Design** (EIP-3540 format):
    ```text
    EOF1 container layout:
      magic:        2 bytes  0xEF 0x00
      version:      1 byte   0x01
      sections:     N entries of { kind: 1 byte, size: 2 bytes } each
      terminator:   1 byte   0x00
      section_data: concatenated bytes

    Section kinds:
      0x01 = type section (function signatures: input/output/max_stack)
      0x02 = code section (one entry per function)
      0x03 = data section (immutable data)
      0x04 = container section (subcontainers for CREATE3-style)

    Constraints:
      - exactly one type section
      - at least one code section (function 0 = entry point)
      - type section size = 4 × num_code_sections
      - data section optional
    ```
    ```rust
    pub struct EofContainer {
        pub magic: [u8; 2],
        pub version: u8,
        pub types: Vec<FunctionType>,    // one per code section
        pub code: Vec<Vec<u8>>,          // per function
        pub data: Vec<u8>,
    }
    pub struct FunctionType {
        pub inputs: u8,
        pub outputs: u8,
        pub max_stack: u16,
    }
    ```
    **Invariants**:
    - magic = `[0xEF, 0x00]` distinguishes EOF from legacy bytecode (legacy can't start with 0xEF — INVALID opcode).
    - version = 0x01 currently; future versions extend.
    - function 0's inputs = 0, outputs = 0x80 (sentinel for "main"); validated.
    - Pre-deployment validation REJECTS malformed containers — no runtime cost.
  - **Build steps (research today)**:
    1. (~15 min) Read EIP-3540 in full; sketch the byte layout.
    2. (~10 min) Read EIP-3670; note the per-opcode validation rules (no invalid opcodes, no truncated PUSH, JUMPDEST analysis embedded in container).
    3. (~10 min) Read EIP-5450; stack-overflow check moves from runtime to validation time.
    4. (~5 min) Note that EOF code can NOT use legacy JUMP/JUMPI — only static relative jumps (RJUMP, RJUMPI, RJUMPV, EIP-4200).
    5. (~5 min) Cross-reference to revm/reth open PRs to find production impl reference.
  - **Acceptance**: notes covering layout + validation + runtime semantics differences.

- [ ] [HFT] **Build**: `crates/matching-engine/src/match.rs` —
  `match_order(book: &mut OrderBook, incoming: Order) -> MatchResult`. Returns fills + remainder. Price-time priority. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: this is THE function — the matching logic that defines the exchange. Price-time priority (best-price first; FIFO within level) is THE rule that makes participants trust the venue. Determinism is non-negotiable: same orders in → same fills out, byte-exact, across replicas and replays. Every downstream consumer depends on this: W63 (v0.5 ship after diff test against a reference matcher), W65 (multi-symbol shard router calls this per symbol), W66 (perpetuals layers margin checks BEFORE match), W74 (raft replicates the input order stream and replays through `match_order` on followers — divergence here = consensus failure). Ship a fill-price bug or an FOK partial-commit bug and you wash-trade your users out of business.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: an order book without a matching function is just a sorted data structure. `match_order` is the *transition* that turns incoming demand into trades. Done wrong, you either (a) violate price-time priority and traders flee the venue, (b) leak non-determinism (HashMap iteration, f64 arithmetic) and break raft replication / VOPR replay, or (c) blow the latency budget by allocating on the hot path. The function must be byte-exact deterministic AND fit a 5 µs p99 budget at v1.0.

  - **Requirements** — write in `crates/matching-engine/notes/61_match_design.md`:
    - R1. **Price-time priority**: best opposite-side price matches first; within a level, makers fill in FIFO arrival order (oldest first).
    - R2. **Maker-price wins**: every `Fill.price` equals the resting maker's price, NEVER the incoming taker's limit. A buy@101 hitting an ask@100 fills at 100.
    - R3. **TIF semantics**: `Limit` rests remainder; `Market` cancels remainder; `IOC` cancels remainder with `IOCRemainder` reason; `FOK` is all-or-nothing (no partial commits); `PostOnly` rejects if it would cross any opposite-side level.
    - R4. **Single-writer**: function takes `&mut OrderBook` — only the symbol's owning shard calls it. No atomics, no locks inside; the only coordination with reader shards is the SeqLock on best bid/ask (W4 pattern).
    - R5. **Float-free**: every quantity, price, and arithmetic op uses integer types (`Qty`, `Price` as `u64`/`i64` newtypes). Any `f64` = wrong fills under different `-march`, divergent raft replicas.
    - R6. **Event-emitting**: every state transition emits a `MatchEvent` (Accepted, Filled, Cancelled, Rejected) into `result.events`. The event log is the source of truth (W61 Wed).
    - R7. **Hot-path budget**: typical 0-3-fill order ≤ 3 µs total; per-fill non-rare path ≤ 100 ns (best-level peek + arithmetic + push fill + emit event + maybe-pop level).
    - R8. **No alloc on common path**: `result.fills` and `result.events` use stack-resident storage sized for the p99 fill-count; only sweeping outliers spill to heap.

  - **Design walk-through** — answer each in your design doc; no peeking at LMAX/Nasdaq OUCH source until Phase 3:
    - D1. Sketch `MatchResult`. Should `fills` and `events` be `Vec<_>`, `SmallVec<[_; N]>`, or caller-provided `&mut Vec<_>` scratch? What's the right `N` if you go SmallVec — decide from the fill-count histogram you sketch (p50, p99, p99.9).
    - D2. Draw the Buy-side match loop as a 2-level loop (outer = levels, inner = orders in a level). What's the terminating condition for the outer loop? For the inner loop? When do you `break` outer vs inner? Write it as 6-8 numbered steps before writing code.
    - D3. Fill price: a buy@101 hits ask@100 — which price goes into `Fill.price`? Justify against R2. What's the trader incentive that this rule preserves?
    - D4. FOK pre-check: write the signature of `can_fill_completely(book: &OrderBook, order: &Order) -> bool`. This is a *read-only* dry walk of the book — it must not mutate. How do you avoid duplicating the match logic?
    - D5. `Fill` and `MatchEvent` layout: estimate `size_of::<Fill>()` and `size_of::<MatchEvent>()` after picking field types. Why does it matter? (Hint: `result.fills` for a 20-level sweep is ~20 × `size_of::<Fill>()` of inline storage; if Fill is 64 B, that's 1.3 KiB on the stack.)
    - D6. Order-type frequency: production tape shows ~80% Limit, ~15% Market, ~3% IOC, ~2% FOK/PostOnly. If you dispatch on `incoming.kind` inside the inner fill loop, the predictor mispredicts every order with a non-Limit kind. Where should the kind dispatch live (top of `match_order`? per-kind inner function?), and in what order should the match arms appear?
    - D7. **Pre-mortem #1 (the load-bearing question)**: write the 6-step interleaving where an FOK order partial-commits — i.e., starts filling, runs out of depth on level 3, leaves 2 fills committed and emits a `Cancelled(FOKUnfillable)` event. If you cannot write the bad interleaving, you do not yet understand R3 well enough to enforce it.
    - D8. **Pre-mortem #2 (determinism)**: name three places where a HashMap iteration or `f64` op would silently sneak in (e.g., `order_index` lookup, qty arithmetic, price comparison). For each, name the deterministic alternative.
  - **Output**: `notes/61_match_design.md` with R1–R8 + answers to D1–D8 + the loop sketch + the FOK interleaving. Stop and review before Phase 2.

  #### Phase 3 — Make the tests pass, one failure at a time (~105 min)

  - **When `maker_price_not_taker_price` reports `Fill.price == 105`:**
    - Symptom: assert fails: `assert_eq!(fill.price, 100)` got 105. Trader gets fills at their worst-case limit, not the maker's price.
    - Why: in the inner loop, you wrote `fill.price = incoming.price` instead of `fill.price = maker.price`. Price-time priority demands the resting order's price; the taker's limit is only a CEILING (for buys) / FLOOR (for sells), not the fill rate.
    - Fix: `fill.price = maker.price` always. Add a debug_assert in the inner loop: for Buys, `debug_assert!(maker.price <= incoming.price)`; for Sells, the inverse.
    - Muscle: in price-time priority, the maker (resting order) sets the price; the taker's limit only bounds whether the level qualifies. Reapplies at: W63 v0.5 differential test, W65 multi-symbol matcher, W74 raft replicated matcher.

  - **When `fok_unfillable_no_partial_commit` reports 2 fills + 1 Cancelled event:**
    - Symptom: the test sees committed fills BEFORE the FOKUnfillable event. The trader's account shows partial execution against a spec that promised all-or-nothing.
    - Why: you started filling first and only discovered depth was insufficient after committing — there's no rollback in a matching engine, so the half-filled state is now reality.
    - Fix: implement `can_fill_completely(&book, &order)` as a read-only dry walk BEFORE any mutation. Branch on its result: if `false`, emit a single `Cancelled(FOKUnfillable)` event and return; if `true`, proceed with the real match loop. The dry walk shares no state with the real loop — it's a parallel read.
    - Muscle: any all-or-nothing semantic must dry-run-then-commit; you cannot retroactively un-fill. Reapplies at: W66 perpetuals atomic-margin-check-then-trade, W83 ledger atomic-transfer, W74 raft "commit if quorum agrees" pattern.

  - **When `perf_stat_branch_mispredict_rate` reports ~20% misses:**
    - Symptom: `perf stat` shows ~20% branch-miss-rate on a mainnet-cap order tape; bench p99 is heavy-tailed by ~5 ns per misprediction × 1 M orders/sec = ~1 ms/sec wasted.
    - Why: you dispatched on `incoming.kind` inside the inner fill loop, OR your top-level match arms are alphabetical / arbitrary (FOK first, Limit last). The predictor learns nothing useful when ~80% of traffic is Limit but the predicted arm is FOK.
    - Fix: (a) reorder match arms by production frequency — `Limit` first, then `Market`, then IOC/FOK/PostOnly. (b) Hoist the kind dispatch OUT of the inner fill loop — dispatch ONCE at the top of `match_order` to a kind-specific inner function (`match_limit`, `match_market`, ...). The compiler can then specialize each path and may emit a jump table. Tag `match_fok`/`match_post_only` `#[cold]` so the predictor biases against them. Re-run `perf stat`; expect ≤ 5%.
    - Cost avoided: ~5 ns × 20% × 1 M = 1 ms/sec; restores predictor accuracy from ~80% to ~95%+; eliminates the inner-loop re-check.
    - Muscle: enum dispatch on a hot path must be frequency-ordered AND hoisted out of inner loops — `match` is not branch-predictor-aware by itself. Reapplies at: W58 exec-vm opcode dispatch (already taught), W74 matching-engine TIF dispatch, W77 aeron frame-type dispatch, W83 ledger op dispatch.

  - **When `bench_sweeping_20_level_p99` reports p99 ≈ 200 µs (4× over the 50 µs cap):**
    - Symptom: `bench_typical_3_fill_order` is clean (~3 µs p99), but the 20-level sweep has a heavy tail. Flame graph shows ~30% of CPU in `alloc::alloc` and `__rust_realloc`.
    - Why: `result.fills: SmallVec<[Fill; 4]>` spills to heap on the 5th fill. A 20-level sweep triggers ~4 capacity doublings (4 → 8 → 16 → 32), each ~50 ns alloc + ~30 ns memcpy of the inline-resident entries. Same shape for `result.events: SmallVec<[MatchEvent; 8]>` if you sized it small.
    - Fix: size SmallVec inline capacity for the p99 fill-count from D1's histogram — if 99% of orders produce ≤ 8 fills, use `SmallVec<[Fill; 16]>` (1 KiB inline). For the truly rare sweep ≥ 16 fills the spill is acceptable. Alternative for v1.0: caller-provided scratch — `match_order(book, incoming, &mut scratch.fills, &mut scratch.events)`; the shard reuses one `Vec` across all calls, so steady-state alloc rate = 0.
    - Cost avoided: ~200 ns × 4 spills × ~1% of orders × 1 M/sec ≈ 8 ms/sec; eliminates the dominant p99 contributor.
    - Muscle: small-vector inline capacity must be sized for p99, not p50 — otherwise the spill IS the p99. Reapplies at: W74 matching-engine TIF order list, W77 aeron Image's per-frame loss-detector, W83 ledger pending-transfer batch.

  - **When `differential_vs_reference_matcher` diverges at step 7000+ on a HashMap-iterated path:**
    - Symptom: reference and production agree for the first ~7k orders, then diverge silently. The diff shows different makers being matched at the same price level on the same tick.
    - Why: somewhere in the matching path, you iterated a `HashMap` (or used `f64` arithmetic). HashMap iteration is non-deterministic across runs even with same input; `f64` rounds differently under different `-march` levels.
    - Fix: audit every container in the match path — `book.asks` must be `BTreeMap`, `level.orders` must be `VecDeque` (FIFO), `order_index` may be `AHashMap` ONLY if used for `O(1)` lookup-by-id (never for iteration). Replace any `f64` with integer `Price`/`Qty` newtypes. Add `#![forbid(clippy::float_arithmetic)]` to the crate.
    - Muscle: any non-deterministic container or floating arithmetic in a replicated state machine breaks consensus silently. Reapplies at: W67 raft state-machine, W74 replicated matcher, W83 ledger MVCC.

  - **5-year failure mode** (write in `notes/61_match_followup.md` after green): when v2.0 adds cross-symbol atomic matching (e.g., spread orders that match BTC-PERP + BTC-SPOT atomically), `&mut OrderBook` is no longer sufficient — you need a transactional view across multiple books. - [ ] Implement EIP-4200 opcodes. (~120 min)
  - **Why**: Static relative jumps (RJUMP, RJUMPI, RJUMPV) replace legacy JUMP/JUMPI in EOF. The destination is a signed 16-bit offset embedded in the opcode — known at validation time → no runtime JUMPDEST check.
  - **Design**:
    ```rust
    fn rjump<H>(interp: &mut Interpreter, _: &mut H) {
        gas!(interp, BASE);  // 2 gas
        let offset = i16::from_be_bytes([interp.bytecode[interp.ip], interp.bytecode[interp.ip + 1]]);
        interp.ip = ((interp.ip + 2) as i32 + offset as i32) as usize;
    }
    fn rjumpi<H>(interp: &mut Interpreter, _: &mut H) {
        gas!(interp, VERYLOW);  // 4 gas
        pop!(interp, condition);
        if condition != U256::ZERO {
            let offset = i16::from_be_bytes([interp.bytecode[interp.ip], interp.bytecode[interp.ip + 1]]);
            interp.ip = ((interp.ip + 2) as i32 + offset as i32) as usize;
        } else {
            interp.ip += 2;
        }
    }
    fn rjumpv<H>(interp: &mut Interpreter, _: &mut H) {

    ```
    **Invariants**:
    - Offset relative to BYTE AFTER offset bytes (so offset=0 means fall-through).
    - All targets validated at deploy time → ip never lands mid-instruction.
    - No legacy JUMP/JUMPI in EOF → cleaner control flow analysis.

  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: a matching engine that mutates a book *in memory* with no log is a black hole — you cannot prove what trades happened, you cannot replay after a crash, you cannot replicate to a follower. The naïve fix (write a JSON blob per event with fsync) is correct but ~1000× too slow. The log must be (i) zero-alloc per append, (ii) batched-fsync for throughput, (iii) deterministic encoding so the bytes replay byte-exact, (iv) schema-evolvable so v2 can read v1 logs.

  - **Requirements** — write in `crates/matching-engine/notes/61_event_log_design.md`:
    - R1. Every state transition in `match_order` emits exactly one `LoggedEvent`: `OrderAccepted`, `OrderCancelled`, `OrderFilled`, `OrderRejected`, `Tick` (heartbeat).
    - R2. Sequence numbers `seq: u64` are monotonic and gap-free per symbol. On recovery, `next_seq = last_seq_in_wal + 1` — never reuse a seq.
    - R3. **Zero-alloc append on the hot path**: `event_log.append(&ev)` makes 0 allocations in steady state. Caller-owned `encode_scratch: Vec<u8>` is reused.
    - R4. **Group-commit fsync**: fsync is called once per batch (~10k events OR ~3 ms timer), NOT per append. v1.0 throughput target: ≥ 1 M events/sec append, fsync rate ≤ 350/sec under that load.
    - R5. **Replay determinism**: writing 10k random orders, reading the log, and applying to a fresh `OrderBook` produces a book with byte-exact identical state (SHA256 of canonical book serialization matches).
    - R6. **Replay throughput**: ≥ 10× append throughput (no fsync on the read path) — recovery of a 1-hour outage (~10 GB of WAL) completes in ≤ 100 s.
    - R7. **Schema evolution**: adding fields to a `LoggedEvent` variant must be backward-compatible. Old logs decode under new code with new fields = `None` / default.
    - R8. **Crash safety**: a crash mid-write loses ONLY un-fsynced events. Recovery walks the WAL up to the last valid frame; never partially decodes a torn frame.

  - **Design walk-through** — answer each in your design doc; no peeking at TigerBeetle / Disruptor until Phase 3:
    - D1. `LoggedEvent` enum: sketch each variant's fields. Why does `OrderFilled` carry `maker_remaining_after: Qty` redundantly (the replay could compute it)? (Hint: invariant verification at replay — replay asserts the computed value matches the logged value; divergence = bug or corruption.)
    - D2. Encoding format: RLP (compatible with W5+ stack), `bytemuck` raw bytes (fastest for internal events), or a custom framed format? Pick one and justify against R3 (zero-alloc) and R7 (schema evolution). What's the trade-off?
    - D3. Write the `append` signature. Does it take `&LoggedEvent` and return the bytes, or take `&LoggedEvent` + `&mut Vec<u8> scratch` and write into scratch? Which satisfies R3? Compare to W26 WAL and W59 raft append signatures — what's the pattern?
    - D4. Group-commit design: where does the batching live — inside `EventLog` (it buffers events and flushes on a timer/threshold) or outside (caller batches, calls `append` N times, then `fsync` once)? Which is more reusable for raft mode (W74) where fsync is replaced by quorum-ack?
    - D5. Sequence number recovery: on startup, how does `EventLog` know `next_seq`? Write the recovery walk in 5 steps. What happens if the last frame is torn (crash mid-write)?
    - D6. Replay API: should it be `fn replay<F: FnMut(LoggedEvent)>(&self, apply: F)` or an iterator `fn iter(&self) -> impl Iterator<Item = LoggedEvent>`? Which composes better with the diff-test harness (W63)?
    - D7. **Pre-mortem #1 (the fsync-per-event trap)**: write the 5-step trace of what happens when a developer "fixes durability" by calling `fsync()` inside `append()`. Compute the resulting throughput collapse from R4 numbers.
    - D8. **Pre-mortem #2 (schema break)**: write a 4-step trace where v2 code adds a non-Option field to `OrderFilled`, deploys, and then a node restarts and tries to replay its v1 log. Where does it fail? Now write the same trace where the new field is `Option<_>` at the end of the variant — does it still fail?

**Thursday — Functions (EIP-4750)**

- [ ] Implement CALLF, RETF, JUMPF in exec-vm. (~120 min)
  - **Why**: EOF functions (EIP-4750) replace the implicit "jump into the middle of code" pattern with explicit function-call semantics. CALLF pushes a return frame; RETF pops; JUMPF tail-calls (no return frame). Per-function stack validation (EIP-5450) is what enables removing runtime stack checks.
  - **Design**:
    ```rust
    pub struct ReturnStack {
        frames: SmallVec<[ReturnFrame; 16]>,  // max 1024 depth
    }
    pub struct ReturnFrame {
        pub return_ip: usize,
        pub return_section: u16,
        pub return_stack_floor: u16,
    }

    fn callf<H>(interp: &mut Interpreter, _: &mut H) {
        gas!(interp, 5);
        let target_section = u16::from_be_bytes([interp.bytecode[interp.ip], interp.bytecode[interp.ip + 1]]);
        // Push return frame
        interp.return_stack.push(ReturnFrame {
            return_ip: interp.ip + 2,
            return_section: interp.current_section,
            return_stack_floor: interp.stack_floor,
        });
        // Jump to target function
        interp.current_section = target_section;
        interp.ip = 0;
        // Update stack floor (per-function frame)
        let f = &interp.eof.types[target_section as usize];
        interp.stack_floor = interp.stack.len() - f.inputs as usize;
    }

    fn retf<H>(interp: &mut Interpreter, _: &mut H) {
        gas!(interp, 3);
        let Some(frame) = interp.return_stack.pop() else {
            interp.result = InvalidReturn; return;
        };
        interp.ip = frame.return_ip;
        interp.current_section = frame.return_section;
        interp.stack_floor = frame.return_stack_floor;
    }
    ```
    **Invariants**:
    - Return stack max depth 1024 (mirrors call stack depth).
    - JUMPF replaces tail-call: no return frame pushed; control transfers permanently.
    - Function outputs validated against type-section signature.
    - Stack-floor tracking prevents callee from popping caller's frame values.
  - **Build steps**:
    1. (~30 min) ReturnStack + ReturnFrame types.
    2. (~30 min) CALLF impl with input-validation against type section.
    3. (~20 min) RETF impl with output-validation.
    4. (~20 min) JUMPF impl (no return frame push).
    5. (~20 min) Tests: nested calls, recursion (within depth), invalid section index rejected at deploy.
  - **Pitfalls**: stack-floor management is the most error-prone; off-by-one allows function to read caller's locals.
  - **Acceptance**: EOF function reference vectors pass; deploy-time validation catches malformed section refs.

  - **The problem this primitive solves**: a matching engine without pre-trade risk lets a trader submit a $10 B order on a $10 balance — when the order fills, the exchange is liable for the negative position.
