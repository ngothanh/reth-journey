**Monday — EOF container model + validation design**

- [ ] **Build**: `crates/exec-vm/src/eof/container.rs` — `EofContainer` parser + header validator for the EOF1 container format (EIP-3540). (~total 180 min across 3 phases)
  - 🔧 **Why this matters**: EOF (EVM Object Format) is the largest EVM change since The Merge — replacing "everything-is-bytecode" with a structured container (magic + version + section table + code + data). The parser is the gate: a malformed container must be REJECTED at deploy time, not at runtime, so the executor can trust the bytes it dispatches on. Mirror: revm `interpreter::eof::EofHeader`. First-attempt parsers fail ≥1 test below (truncated section table read past end-of-buffer; accepting a container with zero code sections; off-by-one on the type-section-size invariant). The debug session IS the lesson. Downstream: W61 Tue (validation consumes this), W61 Wed/Thu (RJUMP/CALLF index into `code` sections), W68 (exec-vm v1.0 ships EOF).

  #### Phase 1 — Problem, prediction, design (~50 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/exec-vm/notes/61_eof_container_prediction.md`:
    - P1: the exact type you'd reach for to walk the byte buffer (`&[u8]` + cursor index? `bytes::Buf`? `std::io::Cursor`?) — write the import line.

    - P4: derive-correctness — will `#[derive(PartialEq)]` on `EofContainer` give byte-exact equality you can use in tests? Any field where derived eq is wrong (e.g. trailing capacity)?
    - P5: **list every Phase-2 test you predict your first attempt will fail.** Seal it; compare after Phase 2.
  - *Mental model*: an `EofContainer` is a self-describing, deploy-time-validated bytecode object. The header is a length-prefixed section table; the body is concatenated section data. Validation is a one-time cost that buys runtime trust (no JUMPDEST scan, no truncated-PUSH checks at execution).
  - *Contract*:
    ```rust
    pub struct EofContainer {
        pub version: u8,
        pub types: Vec<FunctionType>,    // one per code section
        pub code: Vec<Vec<u8>>,          // per function
        pub data: Vec<u8>,
    }
    pub struct FunctionType { pub inputs: u8, pub outputs: u8, pub max_stack: u16 }
    impl EofContainer {
        pub fn parse(raw: &[u8]) -> Result<Self, EofError>;
    }
    ```
    Header layout (EIP-3540): `magic: 0xEF00` (2B) · `version: 0x01` (1B) · section table of `{kind:1B, size:2B}` entries · `terminator: 0x00` (1B) · concatenated section data. Section kinds: `0x01` type, `0x02` code (one entry per function), `0x03` data, `0x04` container.
  - *Back-of-envelope* (bar (b), informational): parse is deploy-time, not hot-path — a 24 KiB max container parsed once per CREATE. Budget is generous (µs), but a panic on malformed input is a DoS vector, so correctness > speed. The single hot consequence: `code[section]` lookup at runtime must be `O(1)` index, not a scan — so store sections as `Vec<Vec<u8>>` indexable by section number.
  - **Requirements** R1..R6 — write in `crates/exec-vm/notes/61_eof_container_design.md`:
    - R1. `magic == [0xEF, 0x00]` and `version == 0x01`, else `Err(EofError::InvalidMagic/Version)`. Legacy bytecode can't start with `0xEF` (it's the INVALID opcode) — this is what distinguishes EOF.
    - R2. Exactly one type section; at least one code section; `type_section_size == 4 * num_code_sections` (each `FunctionType` is 4 bytes on the wire: 1+1+2). Else `Err(EofError::InvalidTypeSection)`.
    - R3. Function 0 (entry) has `inputs == 0`, `outputs == 0x80` (sentinel "non-returning main").
    - R4. **No read past end-of-buffer**: every section-size read and section-data slice is bounds-checked; a truncated buffer yields `Err(EofError::Truncated)`, never a panic.
    - R5. Sum of declared section sizes must equal the remaining buffer length after the header (no trailing bytes, no underflow).
    - R6. `parse` is alloc-bounded: at most one `Vec` per code section + one for data; no per-byte allocation.
  - **Design walk-through** D1..D4 — answer in the design doc; no peeking at revm `eof.rs` until Phase 3:
    - D1. Enumerate buffer-walk primitives (raw index, `Cursor`, `bytes::Buf`, `nom`) with a property table (bounds-checked? zero-copy slices? readability?). Pick one; justify against R4.
    - D2. Order of validation: do you validate the whole header THEN slice data, or interleave? Which catches a truncated section table earliest with the least wasted work?
    - D3. **Pre-mortem (load-bearing):** write the EXACT 4-line trace where a parser reads `size: u16` for a section, then slices `raw[offset..offset+size]` WITHOUT checking `offset+size <= raw.len()` — show the panic (or the silent out-of-bounds if you used `get_unchecked`). This is the bug R4 forbids.
    - D4. **Anti-shortcut audit:** the "obvious" reach is `raw[i]` indexing — name why it's wrong HERE (panics on malformed deploy input = DoS) and the safe alternative (`raw.get(i).ok_or(Truncated)?`).
  - 🧮 **Paper drill** — write in `notes/61_eof_container_drill.md`:
    - D-WALK on the smallest valid EOF1 container `EF00 01 01 0004 02 0001 0001 03 0001 00 00800000 00 AA`: hand-parse it byte by byte — magic (2B) → version (1B) → type-section header `{0x01, size=4}` → code-section header `{0x02, count=1, size=1}` → data header `{0x03, size=1}` → terminator `0x00` → type data `00 80 0000` (inputs=0, outputs=0x80, max_stack=0) → code `00` → data `AA`. Verify R5 (declared sizes sum = remaining bytes) and write the verdict (accept / reject + which `EofError`).
    - D-LAYOUT on the header byte-map: draw the offset table for that same container (offset → field → byte width), marking where the section-table region ends and concatenated section data begins. Mark the exact offset+size slice for `code[0]` and confirm an `O(1)` ordinal index lands on it (the contract Wed's RJUMP/Thu's CALLF rely on).
  - **Output**: `notes/61_eof_container_design.md` with R1..R6, D1..D4, the truncation bad-trace; plus `notes/61_eof_container_drill.md` with the worked paper drills.

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)
  - **(SENIOR) When `truncated_section_table_is_err_not_panic` reports a panic `index out of bounds: the len is 3 but the index is 3`:**
    - Symptom: `catch_unwind` returns `Err` — the parser panicked instead of returning `Err(Truncated)`.
    - Why: you read the section table with `raw[offset]` / `raw[offset..offset+2]` without checking the buffer has those bytes. Deploy input is attacker-controlled; a panic in `parse` is a remote DoS.
    - Fix: replace every `raw[i]` with `raw.get(i).copied().ok_or(EofError::Truncated)?` and every slice with a checked `raw.get(off..off+n).ok_or(Truncated)?`.
    - Muscle: parsing attacker-controlled bytes uses checked accessors only — `[]` indexing is a panic-on-malformed-input bug. Reapplies at: W61 Tue EOF code validation, W66 tempo-tx-envelope decode, W83 ledger transfer decode, W90+ event-log frame decode.
  - **(SENIOR) When `type_size_mismatch_rejected` passes a 2-section/size-4 container:**
    - Symptom: parse returns `Ok` for a container whose type section can't describe its code sections; runtime will index `types[1]` out of bounds later.
    - Why: you skipped the `type_section_size == 4 * num_code_sections` cross-check (R2); each `FunctionType` is 4 wire-bytes.
    - Fix: after counting code sections, assert `type_size == 4 * code_section_count` before slicing the type data.
    - Muscle: a length-prefixed multi-section format needs cross-section size invariants validated up-front, or a later index goes out of bounds. Reapplies at: W61 Wed RJUMPV table-length check, W83 ledger batch header.
  - **(EXPERT) When `parsed_code_indexable_for_rjump` fails because `code` isn't index-addressable:**
    - Symptom: Wed's RJUMP can't do `eof.code[section]` in `O(1)`; you stored sections in a `HashMap` keyed by section *kind*, collapsing all code sections under key `0x02`.
    - Why: section *kind* (type/code/data) is not the section *index*; multiple code sections share kind `0x02` but need ordinal addressing.
    - Fix: store `code: Vec<Vec<u8>>` indexed by code-section ordinal (0,1,2,…); keep kind only for parse-time dispatch.
    - Muscle: index by the access pattern the consumer needs (ordinal here), not by the field that was convenient at parse time. Reapplies at: W61 Thu CALLF target-section lookup, W74 matching-engine per-symbol book index.

- [ ] [HFT] **Build**: `crates/matching-engine/src/match.rs` —
  `match_order(book: &mut OrderBook, incoming: Order) -> MatchResult`. Returns fills + remainder. Price-time priority. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: this is THE function — the matching logic that defines the exchange. Price-time priority (best-price first; FIFO within level) is THE rule that makes participants trust the venue. Determinism is non-negotiable: same orders in → same fills out, byte-exact, across replicas and replays. Ship a fill-price bug or an FOK partial-commit bug and you wash-trade your users out of business.

  #### Phase 1 — Problem, prediction, design (~60 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/matching-engine/notes/61_match_prediction.md`:
    - P1: the container you'd reach for `book.asks` (BTreeMap? Vec sorted? skiplist?) and the per-level order list (`VecDeque`? `Vec`?) — write the import lines.
    - P2: predicted `size_of::<Fill>()` and `size_of::<MatchEvent>()` after picking field types; predicted inline-stack bytes for a 20-level sweep.
    - P3: predicted branch-mispredict rate if you `match incoming.kind` inside the inner fill loop on an 80%-Limit tape.
    - P4: derive-correctness — does `#[derive(PartialEq, Eq)]` on `MatchResult` give you a sound diff-test oracle? Any `f64` field that breaks `Eq`?
    - P5: **list every Phase-2 test you predict your first attempt will fail** (predict at least `maker_price_not_taker_price`, `fok_unfillable_no_partial_commit`, `perf_stat_branch_mispredict_rate`).
  - *Mental model*: an order book without a matching function is just a sorted data structure. `match_order` is the *transition* that turns incoming demand into trades — the pure state-transition function of a deterministic replicated state machine.
  - *Contract*: `pub fn match_order(book: &mut OrderBook, incoming: Order) -> MatchResult;` — `&mut OrderBook` (single-writer, the symbol's owning shard); returns `MatchResult { fills, events, remainder }`. No interior atomics/locks; the only cross-shard coordination is the SeqLock on best bid/ask (W4 pattern).
  - *Back-of-envelope* (bar (c)): target 1 M orders/sec/shard ⇒ ~1 µs budget per order steady-state, 5 µs p99 at v1.0. Per-fill non-rare path ≤ 100 ns = best-level peek (BTreeMap first-entry ~L1/L2, ~7 ns) + integer arithmetic (~1 ns) + push fill (~3 ns) + emit event (~3 ns) + maybe-pop level. The cliff: an alloc on the fill path is ~50 ns malloc + 50 ns free = 100 ns, i.e. it DOUBLES the per-fill cost (1× → 2×). A branch mispredict on kind dispatch is ~5 ns; at 20% miss × 1 M/s = 1 ms/s wasted. f64 div is 10-30 cycles AND non-deterministic across `-march` — disqualifying.
  - **Requirements** — write in `crates/matching-engine/notes/61_match_design.md`:
    - R1. **Price-time priority**: best opposite-side price matches first; within a level, makers fill in FIFO arrival order (oldest first).
    - R2. **Maker-price wins**: every `Fill.price` equals the resting maker's price, NEVER the incoming taker's limit. A buy@101 hitting an ask@100 fills at 100.
    - R3. **TIF semantics**: `Limit` rests remainder; `Market` cancels remainder; `IOC` cancels remainder with `IOCRemainder` reason; `FOK` is all-or-nothing (no partial commits); `PostOnly` rejects if it would cross any opposite-side level.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **(SENIOR) When `bench_noop_risk_overhead_zero_ns` reports ~15 ns of overhead and `verify_noop_risk_call_site_absent_in_asm` shows a `call` to a vtable slot (bar (c) violation):**
    - Symptom: `MatchingEngine<NoopRisk>` is ~15 ns slower per submit than the no-risk baseline. Disassembly shows `ldr x9, [vtable_ptr]; blr x9` — a vtable load + indirect call.
    - Why: you wrote `engine: MatchingEngine { risk: Box<dyn RiskCheck>, ... }` instead of `MatchingEngine<R: RiskCheck>`. Every submit pays vtable load (~5 ns + possible L1 miss) + indirect call (~3 ns + predictor-unknown). Worse: inlining is fully blocked, so the risk body never fuses with the submit path — that costs another ~5-10 ns via missing LLVM fold-and-prune.
    - Fix: parameterize: `pub struct MatchingEngine<R: RiskCheck> { risk: R, ... }`. Each symbol-shard's engine is its own concrete type. NoopRisk's body inlines to `Ok(())` and the compiler proves the branch is always-Ok — the call folds to nothing. FatFingerRisk inlines to 3-4 integer compares.
    - Cost avoided: ~10-20 ns/submit × 1 M/sec = 10-20 ms/sec/shard; NoopRisk literally becomes 0 cycles in the disassembly. **(bar (c) violation.)**
    - Muscle: dynamic dispatch via `Box<dyn>`/`&dyn` is a hot-path antipattern on bar-(c) crates — use generics or a closed enum. Reapplies at: W74 matching-engine TIF dispatch, W77 aeron flow-control strategy, W83 ledger op handler, W92 VSR message handler.

  - **(SENIOR) When `risk_rejection_is_alloc_free` reports allocations attributed to `RiskRejection::FatFinger` (bar (c) violation):**
    - Symptom: heaptrack shows ~10k `String` allocations on the rejection path, one per rejected order. Each ~30 ns.
    - Why: you defined `FatFinger { reason: String }` and constructed the reason as `format!("qty {} exceeds max {}", q, max)`. Every rejection pays an alloc.
    - Fix: replace `reason: String` with structured fields: `FatFinger { actual_qty: Qty, max_qty: Qty, actual_notional: u64, max_notional: u64 }`. Callers / observers can `Display`-format on demand (off the hot path). The hot path moves zero bytes other than the enum discriminant + a few u64s.
    - Cost avoided: ~30 ns × reject rate; removes the allocator from the reject path. **(bar (c) violation.)** Muscle: error variants on hot paths carry structured data, not pre-formatted strings — formatting is lazy. Reapplies at: every error type that lives on a per-call hot path (W74 raft error, W83 ledger reject, W92 VSR error).

  - **(SENIOR) When `risk_rejection_event_emitted_before_match` shows a `Filled` event preceding `Rejected`:**
    - Symptom: an order that should be risk-rejected ends up in the book and partially fills before risk catches it.
    - Why: `engine.submit` runs `match_order` first and `risk.check` second, or runs them concurrently. The risk check must be the FIRST step of the submit flow.
    - Fix: in `submit`, the canonical ordering is: (1) accept-event, (2) risk.check, (3) on Err → emit Rejected + return, (4) match_order, (5) book mutation. Add an integration test asserting this ordering at every submit path.
    - Cost avoided: correctness — a leaking-liability bug. Muscle: pre-trade checks gate the engine — if risk runs after any mutation, you've shipped a leaking-liability bug. Reapplies at: W66 perpetuals margin pre-check, W83 ledger pre-transfer check, W74 raft propose pre-validation.

  - **(SENIOR) When `bench_fat_finger_risk_under_50_ns` reports ~150 ns (bar (c) violation):**
    - Symptom: even with generics, the rejection path is 3× over budget.
    - Why: `FatFingerRisk::check` is doing more work than needed — perhaps loading a `HashMap` config per call, or formatting a debug log line, or running through a `Vec<Rule>` iterator instead of inline compares.
    - Fix: inline the 2-3 integer compares directly. `FatFingerRisk` should hold its limits as `u64` fields (no `HashMap`, no `Vec<Rule>`). The body is literally `if order.qty > self.max_qty { return Err(...) } if order.qty * order.price > self.max_notional { return Err(...) } Ok(())`. The compiler can constant-fold many cases when limits are known at engine-construction.
    - Cost avoided: ~100 ns/submit on the prod risk path. **(bar (c) violation.)** Muscle: hot-path predicates are inline integer compares, never config-driven rule engines. Reapplies at: W66 margin pre-check, W74 quorum check.

  - **(EXPERT) When `dyn_dispatch_regression_compile_fail` actually compiles (i.e., the negative test fails):**
    - Symptom: `MatchingEngine<Box<dyn RiskCheck>>` compiles fine — meaning the type parameter accepted a trait object and you've quietly reintroduced vtable dispatch through the back door.
    - Why: `Box<dyn RiskCheck>: RiskCheck` if you have a blanket impl `impl<T: ?Sized + RiskCheck> RiskCheck for Box<T>`. The generic parameter `R: RiskCheck` is satisfied by trait objects too.
    - Fix: either (a) remove the blanket impl on `Box<T: RiskCheck>` so the trait object doesn't satisfy `RiskCheck`, OR (b) add a marker supertrait `trait MonoRisk: RiskCheck + Sized {}` and bound `R: MonoRisk` on the engine. Document the choice in the design notes; the load-bearing test is that `MatchingEngine<Box<dyn RiskCheck>>` FAILS to construct.
    - Cost avoided: silent regression of the whole zero-cost-pluggability invariant. Muscle: a "no-vtable" invariant must be enforced by the type system, not by convention — otherwise it regresses silently. Reapplies at: every hot-path pluggability point (W74 transport, W83 storage backend).
