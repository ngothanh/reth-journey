**Monday — EOF EIP deep re-read**

- [ ] Re-read EIP-3540, 3670. EOF container format. (~45 min)
  - **Why**: EOF (EVM Object Format) is the largest EVM change since The Merge — replacing the "everything-is-bytecode" mess with a structured container (magic + version + section table + code + data). Pre-deployment validation eliminates entire classes of bugs (invalid jumps, mid-PUSH JUMPDESTs). Critical for understanding upcoming mainnet (Prague?) hard forks. Citing Ipsilon repo + Reth EOF PRs ensures spec-current understanding.
  - **Read first**:
    - EIP-3540 (EOF container format), EIP-3670 (code validation), EIP-4200 (static relative jumps), EIP-4750 (functions: CALLF, RETF), EIP-5450 (stack validation)
    - github.com/ipsilon/eof (reference spec impl)
    - reth + revm open PRs touching `eof_*.rs`
  - **Design** (EIP-3540 format):
    ```text
    EOF1 container layout:
      magic:        2 bytes  0xEF 0x00
      version:      1 byte   0x01
      sections:     N entries of { kind: 1 byte, size: 2 bytes } each
      terminator:   1 byte   0x00
      section_data: concatenated bytes

    Section kinds:
      0x01 = type section (function signatures: input/output/max_stack)
      0x02 = code section (one entry per function)
      0x03 = data section (immutable data)
      0x04 = container section (subcontainers for CREATE3-style)

    Constraints:
      - exactly one type section
      - at least one code section (function 0 = entry point)
      - type section size = 4 × num_code_sections
      - data section optional
    ```
    ```rust
    pub struct EofContainer {
        pub magic: [u8; 2],
        pub version: u8,
        pub types: Vec<FunctionType>,    // one per code section
        pub code: Vec<Vec<u8>>,          // per function
        pub data: Vec<u8>,
    }
    pub struct FunctionType {
        pub inputs: u8,
        pub outputs: u8,
        pub max_stack: u16,
    }
    ```
    **Invariants**:
    - magic = `[0xEF, 0x00]` distinguishes EOF from legacy bytecode (legacy can't start with 0xEF — INVALID opcode).
    - version = 0x01 currently; future versions extend.
    - function 0's inputs = 0, outputs = 0x80 (sentinel for "main"); validated.
    - Pre-deployment validation REJECTS malformed containers — no runtime cost.
  - **Build steps (research today)**:
    1. (~15 min) Read EIP-3540 in full; sketch the byte layout.
    2. (~10 min) Read EIP-3670; note the per-opcode validation rules (no invalid opcodes, no truncated PUSH, JUMPDEST analysis embedded in container).
    3. (~10 min) Read EIP-5450; stack-overflow check moves from runtime to validation time.
    4. (~5 min) Note that EOF code can NOT use legacy JUMP/JUMPI — only static relative jumps (RJUMP, RJUMPI, RJUMPV, EIP-4200).
    5. (~5 min) Cross-reference to revm/reth open PRs to find production impl reference.
  - **Acceptance**: notes covering layout + validation + runtime semantics differences.

- [ ] [HFT] **Build**: `crates/matching-engine/src/match.rs` —
  `match_order(book: &mut OrderBook, incoming: Order) -> MatchResult`. Returns fills + remainder. Price-time priority. (~150 min)
  - **Why (MAX DETAIL — matching internals)**: This is THE function — the matching logic. Price-time priority means: incoming buy matches at lowest ask first; within same level, oldest order fills first. Every fill emits a `Fill` event into the log. Determinism is non-negotiable.
  - *Back-of-envelope*: this is THE function. P99 budget at v1.0 = 5 µs; this function is the dominant path. Typical fill = best-ask level pop + maker remaining update + emit Fill + emit OrderFilled event + (rare) level empty → BTreeMap remove. **Per-fill budget: ~1 µs**; typical incoming order produces 0-3 fills, so the whole `match_order` call budget = ~3 µs leaving ~2 µs for risk + L1 publish + WAL append. Decompose 1 µs per fill: best-level peek (~10 ns L1 cached); `VecDeque::front_mut` (~5 ns); arithmetic on `Qty` (~5 ns); push `Fill` into `result.fills: SmallVec<[Fill; 4]>` (~10 ns if `SmallVec` capacity covers the fill count, ~100 ns + alloc if it spills to heap); push `MatchEvent` into `result.events: SmallVec<[MatchEvent; 8]>` (same); on full-fill: `level.orders.pop_front()` (~5 ns) + `order_index.remove` (~30 ns AHashMap) + (rare) `book.asks.remove(price)` (~50 ns BTreeMap rebalance + dealloc). Total non-rare path: ~80 ns/fill — well inside budget. **Killers**: SmallVec spill to heap on a many-fill incoming (e.g., a sweeping market order eating 20 levels — SmallVec<[Fill; 4]> spills 16 times, each ~50 ns alloc); `Fill` and `MatchEvent` are ~64 B and ~24 B respectively, so a 20-fill order is ~1.7 KiB of `result.fills` + ~480 B `result.events` — needs to fit the caller's pre-allocated scratch. **Float ban hardest here**: any `f64` in match logic = wrong fills under different `-march`, non-deterministic VOPR replay, divergent raft replication. **Single-writer invariant**: this function takes `&mut OrderBook` — only the symbol's owning shard ever calls it, so no atomics inside, no locks; the SeqLock on best_bid/ask (W4 pattern) is the *only* coordination point with reader shards.
  - **Read first**: Nasdaq's OUCH protocol; LSE's order-matching rulebook; "Order Matching Algorithms" survey papers.
  - **Design**:
    ```rust
    pub struct MatchResult {
        pub fills: SmallVec<[Fill; 4]>,
        pub remainder: Option<Order>,    // unfilled portion stays on book (if Limit) or returned (if IOC)
        pub events: SmallVec<[MatchEvent; 8]>,
    }

    pub struct Fill {
        pub maker_id: OrderId,
        pub taker_id: OrderId,
        pub price: Price,                // maker's price (price-time priority)
        pub qty: Qty,
        pub ts: Monotonic,
    }

    pub enum MatchEvent {
        Accepted(OrderId),
        Filled(Fill),
        Cancelled(OrderId, CancelReason),
        Rejected(OrderId, RejectReason),
    }

    pub fn match_order(book: &mut OrderBook, mut incoming: Order) -> MatchResult {
        let mut result = MatchResult::default();
        result.events.push(MatchEvent::Accepted(incoming.id));

        // PostOnly: reject if would cross
        if incoming.kind == OrderKind::PostOnly && would_cross(book, &incoming) {
            result.events.push(MatchEvent::Rejected(incoming.id, CrossRejected));
            return result;
        }

        // FOK: pre-check if entire qty can fill; else reject
        if incoming.kind == OrderKind::FOK && !can_fill_completely(book, &incoming) {
            result.events.push(MatchEvent::Cancelled(incoming.id, FOKUnfillable));
            return result;
        }

        // Match loop: iterate opposite-side levels in best-price order
        match incoming.side {
            Buy => {
                while incoming.remaining > 0 {
                    let Some((&best_ask_price, level)) = book.asks.iter_mut().next() else { break; };
                    if incoming.price < best_ask_price && incoming.kind == Limit { break; }  // can't cross more
                    while incoming.remaining > 0 {
                        let Some(maker) = level.orders.front_mut() else { break; };
                        let fill_qty = incoming.remaining.min(maker.remaining);
                        let fill = Fill {
                            maker_id: maker.id,
                            taker_id: incoming.id,
                            price: maker.price,
                            qty: fill_qty,
                            ts: incoming.ts,
                        };
                        maker.remaining -= fill_qty;
                        incoming.remaining -= fill_qty;
                        result.fills.push(fill.clone());
                        result.events.push(MatchEvent::Filled(fill));
                        if maker.remaining == 0 {
                            level.orders.pop_front();
                            book.order_index.remove(&maker.id);
                        }
                    }
                    if level.orders.is_empty() {
                        book.asks.remove(&best_ask_price);
                    }
                }
            }
            Sell => { /* mirror */ }
        }

        // Place remainder on book if Limit
        if incoming.remaining > 0 && incoming.kind == OrderKind::Limit {
            book.add_limit_order(incoming.clone());
            result.remainder = Some(incoming);
        } else if incoming.remaining > 0 && (incoming.kind == IOC || incoming.kind == Market) {
            result.events.push(MatchEvent::Cancelled(incoming.id, IOCRemainder));
        }
        result
    }
    ```
    **Invariants**:
    - Price-time priority: best-price wins at level boundary; FIFO within level.
    - Fill price = MAKER's price (the resting order's price); regardless of taker's limit price.
    - Maker remaining decreases by fill_qty; if 0 → remove from book.
    - Atomic-per-order: a match operation EITHER produces all its fills OR (on error) none — but in practice errors here are panics (invariant violations).
    - Event log captures EVERYTHING: accepted, filled, cancelled, rejected.
  - **Build steps** (granular):
    1. (~25 min) MatchResult, Fill, MatchEvent types.
    2. (~30 min) match_order main loop for Buy side.
    3. (~25 min) Mirror for Sell side.
    4. (~20 min) PostOnly cross check (`would_cross`).
    5. (~20 min) FOK pre-check (`can_fill_completely`).
    6. (~15 min) IOC remainder cancel emission.
    7. (~15 min) Tests: simple 1×1 match; 1×N (one taker takes 3 makers); partial fill of taker; FOK unfillable rejected.
  - **Pitfalls** (named, determinism-critical):
    - *Maker-price vs taker-price bug*: fill at incoming's limit price instead of resting maker's price violates price-time priority. **Symptom**: trader gets worse fills than spec. **Fix**: `fill.price = maker.price` always.
    - *FOK partial commit*: starting to fill, encountering insufficient depth → MUST roll back fills. **Symptom**: FOK partially filled (spec violation). **Fix**: dry-run `can_fill_completely` BEFORE any fill; only commit fills if pre-check passes.
    - *Zero-qty fill emission*: arithmetic produces fill_qty = 0; emitting an Event with qty 0 pollutes log. **Symptom**: noise; downstream confused. **Fix**: skip event if fill_qty == 0 (shouldn't happen, but defense in depth).
    - *Cancel during match*: cross-shard cancel arrives mid-match. **Symptom**: order partially filled then "cancelled". **Fix v0.5**: matching is atomic — cross-shard messages queue until match completes; no preemption.
    - *Self-trade (maker.owner == taker.owner)*: depending on exchange rules, may be allowed (with self-trade-prevention) or rejected. **Symptom**: wash trades. **Fix v0.5**: defer; W74 adds self-trade-prevention flag.
  - **Test scenarios**:
    - 1 maker @ 100 qty=10; taker buy @ 101 qty=10 → 1 fill at 100 qty 10; book empty.
    - 3 makers @ 100, 101, 102 qty=10 each; taker buy @ 103 qty=25 → 3 fills (10@100, 10@101, 5@102).
    - FOK qty=100 when book has total qty=50 → no fills; FOK cancelled.
    - PostOnly buy @ 99 when ask=98 → reject (would cross).
    - Diff-test against simple sorted-Vec reference matcher: 10k random sequences, byte-exact match.
  - **Expect to hit (perf) #1 — `match incoming.kind { Limit => ..., Market => ..., IOC => ..., FOK => ..., PostOnly => ... }` branch-mispredicts on every order (bar (c) violation)**: the match-loop body has multiple `if incoming.kind == OrderKind::Limit { ... }` checks interleaved with the fill loop. Order-type distribution is heavily skewed in production: typically ~80% Limit, ~15% Market, ~3% IOC, ~2% FOK/PostOnly. If the source-order of the match arms is alphabetical or arbitrary, the branch predictor mispredicts ~20% of orders → ~5 ns each → 1 ns/order amortized (1 M/sec = 1 ms/sec wasted). Worse, with the kind-check INSIDE the inner fill loop, every fill re-checks the kind unnecessarily.
    - Fix: (a) reorder match arms by frequency: `Limit` first, `Market` second, then IOC/FOK/PostOnly — so the predicted branch matches the common case; (b) hoist the kind-check OUT of the inner fill loop — dispatch once at the top of `match_order` to a kind-specific inner function (`match_limit`, `match_market`, etc.) and let the compiler specialize each. The `#[cold]` attribute on `match_fok`/`match_post_only` further hints the predictor. With the match arms ordered, the compiler can also emit a jump table (W58 dispatch muscle) rather than a tree of compares.
    - Cost avoided: ~5 ns × 20% × 1 M = 1 ms/sec; restores predictor accuracy from ~80% to ~95%+ on the order kind; eliminates the inner-loop re-check overhead.
    - Muscle: enum dispatch on a hot path must be frequency-ordered AND hoisted out of inner loops — `match` is not branch-predictor-aware by itself. Reapplies at: W58 exec-vm opcode dispatch (already taught), W74 matching-engine TIF dispatch, W77 aeron frame-type dispatch, W83 ledger op dispatch.
  - **Expect to hit (perf) #2 — `result.fills: SmallVec<[Fill; 4]>` spills to heap on sweeping market orders (bar (c) violation)**: `SmallVec<[Fill; 4]>` keeps the first 4 fills inline (no alloc) but the 5th fill triggers a heap allocation (~50 ns) and memcpy of the 4 inline entries to the heap (4 × 64 B = 256 B copy, ~30 ns). A market order sweeping 20 levels triggers ~4 spills (capacity doubling: 4 → 8 → 16 → 32) = ~200 ns wasted on allocs. Symptom: bench p99 has a heavy tail driven by "sweep" orders (single market orders that eat many levels); microbench of single-fill is clean but mixed workload has a long tail.
    - Fix: size `SmallVec<[Fill; 4]>` based on production-shape data — if 99% of orders produce ≤ 8 fills, use `SmallVec<[Fill; 16]>` (1 KiB inline) to cover the p99 case. For the truly rare sweeping case (≥ 16 fills), the spill is acceptable. Alternative: pre-allocate a per-shard `fill_scratch: Vec<Fill>` reused across `match_order` calls — `match_order` takes `&mut fill_scratch` as a parameter, writes fills into it, then the caller drains. This pattern (caller-provided scratch) eliminates all per-call allocator visits for the common path.
    - Cost avoided: ~50 ns alloc × ~4 spills × ~1% of orders × 1 M/sec = ~2 ms/sec saved (small), but eliminates the tail-latency contributor that dominates p99 (every spike traced via `perf` shows the same SmallVec resize). 
    - Muscle: small-vector inline capacity must be sized for p99, not p50 — otherwise the spill IS the p99. Reapplies at: W74 matching-engine TIF order list, W77 aeron Image's per-frame loss-detector, W83 ledger pending-transfer batch.
  - **Acceptance**: differential green; throughput ≥ 100k matches/sec single-core; **single-fill p99 ≤ 5 µs** (the v1.0 target — we want to see we're in the right ballpark at v0.5 already); sweeping 20-level market order p99 ≤ 50 µs (allows the spill but caps the tail); branch-mispredict-rate via `perf stat` ≤ 5% on a mainnet-cap order tape replay.
  - **Downstream**: W63 (v0.5 ship after diff test); W65 (multi-symbol); W66 (perpetuals adds margin checks before match).

        gas!(interp, BASE);  // 2 gas
        let offset = i16::from_be_bytes([interp.bytecode[interp.ip], interp.bytecode[interp.ip + 1]]);
        interp.ip = ((interp.ip + 2) as i32 + offset as i32) as usize;
    }

        pop!(interp, condition);

            interp.ip = ((interp.ip + 2) as i32 + offset as i32) as usize;
        } else {
            interp.ip += 2;
        }

- [ ] [HFT] **Build**: `crates/matching-engine/src/event_log.rs` — every order placed, cancel, fill, partial-fill emits
  a `MatchEvent` written via `wal::Wal`. Replay reconstructs full book state. (~150 min)
  - **Why (MAX DETAIL — determinism + recovery)**: The event log is the source of truth. The book is a projection. This separation enables: byte-exact replay (recovery, audit, debugging), state forks (test "what if order X cancelled?"), cross-DC replication via raft (W67+). TigerBeetle's design philosophy.
  - *Back-of-envelope*: at 1 M orders/sec each producing ~1-3 events (Accepted + 0-3 Filled + maybe Cancelled), event throughput target = **≥ 3 M events/sec/shard append throughput**. Per event encode (~50-100 B Order or ~64 B Fill) + WAL append memcpy (~50 ns) + AtomicU64 fetch_add for seq (~5 ns) = ~100-200 ns/event hot path; 3 M/sec = ~600 ms/sec — far over budget. So: **fsync is ABSOLUTELY batched** — 1 fsync per ~10k events (every ~3 ms) = ~50 µs fsync amortized over 10k events = 5 ns/event for the durability. Per-order durability latency: ~3 ms p99 (the fsync batch window), acceptable for v0.5 (W74 raft replication pushes durability to follower-acks, not local fsync). Replay throughput target: **10× append throughput** (~30 M events/sec, no fsync) to keep recovery time bounded — a 1-hour outage with 3 M events/sec means 10 GB of WAL to replay; at 30 M events/sec replay that's 100 sec. Per-event-encode must be **zero-alloc**: pre-allocated scratch buffer (W26 wal pattern + W59 raft pattern).
  - **Read first**: TigerBeetle `src/state_machine.zig` event log; QuickFIX recovery design; LMAX Disruptor whitepaper.
  - **Design**:
    ```rust
    pub struct EventLog {
        wal: wal::Wal,
        next_seq: u64,
    }
    #[derive(RlpEncodable, RlpDecodable)]
    pub enum LoggedEvent {
        OrderAccepted { seq: u64, order: Order },
        OrderCancelled { seq: u64, id: OrderId, reason: u8 },
        OrderFilled { seq: u64, fill: Fill, maker_remaining_after: Qty },
        OrderRejected { seq: u64, id: OrderId, reason: u8 },
        Tick { seq: u64, ts: Monotonic },  // heartbeat for liveness even when no orders
    }

    impl EventLog {
        pub fn append(&mut self, ev: LoggedEvent) -> Result<u64, _> {
            let seq = self.next_seq;
            self.next_seq += 1;
            let bytes = rlp::encode(&ev);
            self.wal.append(&bytes)?;
            Ok(seq)
        }
        pub fn fsync(&mut self) -> Result<(), _> { self.wal.fsync() }

        pub fn replay<F: FnMut(LoggedEvent)>(&self, mut apply: F) -> Result<u64, _> {
            for entry in self.wal.iter() {
                let ev: LoggedEvent = rlp::decode(&entry?)?;
                apply(ev);
            }
            Ok(self.next_seq)
        }
    }
    ```
    **Invariants**:
    - Sequence number `seq` monotonic and gap-free per symbol.
    - Every match emits BEFORE-state and AFTER-state implicitly: `maker_remaining_after` in OrderFilled lets replay verify book consistency.
    - WAL fsync called BEFORE returning success to client (durability).
    - Replay rebuilds book byte-exact: same sequence → same final state.
  - **Build steps** (granular):
    1. (~20 min) LoggedEvent enum with RLP derive.
    2. (~25 min) EventLog wraps wal::Wal; append/fsync/replay.
    3. (~30 min) Integrate into match_order: every accept/fill/cancel/reject → event.append.
    4. (~25 min) Replay function: read WAL, decode each event, apply to fresh OrderBook, verify state hash matches snapshot.
    5. (~30 min) Differential test: random sequence of 10k orders → log → replay → final book identical (SHA256 of book bytes match).
    6. (~20 min) Crash test: crash mid-sequence; recover; verify replay reaches last fsync'd seq, no further.
  - **Pitfalls**:
    - *Fsync per event kills throughput*: 100k orders/sec needs batched fsync. **Symptom**: 1k orders/sec. **Fix**: client-replication batches events; fsync once per batch.
    - *Replay state divergence*: same log → different book → bug. **Symptom**: rare data corruption. **Fix**: deterministic data structures (BTreeMap, not HashMap iter order); det_test harness (W60) catches.
    - *Schema evolution*: adding fields to LoggedEvent variants breaks replay of old logs. **Symptom**: prod can't read pre-upgrade log. **Fix**: only APPEND fields with `Option<_>`; never remove or reorder.
    - *Seq number reset on crash*: re-using a previously-used seq on restart corrupts log. **Symptom**: silent dup. **Fix**: on recovery, set `next_seq = last_seq_in_wal + 1`.
  - **Test scenarios**:
    - 10k orders → log → replay → state hash match.
    - Crash injection: 1k events, crash before fsync 999, recovery resumes at 999.
    - Schema-evolution: write log with v1; decode with v2 (which has extra Option field) → success, extra field = None.
  - **Expect to hit (perf) #1 — `rlp::encode(&ev)` returns a fresh `Vec<u8>` per event (bar (c) violation)**: the design as written calls `rlp::encode(&ev)` which allocates a new `Vec<u8>` per event. At 3 M events/sec/shard that's 3 M Vec allocs/sec — allocator melts. Even if the WAL append itself is zero-alloc, the encode-step gates the whole pipeline. Symptom: standalone WAL bench shows 5 M ops/sec; integrated bench drops to 300k/sec; flame graph shows `alloc::alloc` at 40% of CPU.
    - Fix: same pattern as W59 raft + W26 wal: pre-allocate a per-shard `encode_scratch: Vec<u8>` (capacity ~256 KiB), use an `Encodable::encode(&self, out: &mut Vec<u8>)` API that writes into the caller's buffer, then WAL append copies from the scratch buffer, then `encode_scratch.clear()`. For internal events (matching-engine's own log, not the public RLP tx-envelope), use `bytemuck` for `#[repr(C)]` event structs — `out.extend_from_slice(bytemuck::bytes_of(&ev))` is a ~30 ns memcpy. The W60 Order::encode_into design extends naturally to LoggedEvent::encode_into.
    - Cost avoided: ~50 ns alloc + ~50 ns dealloc per event × 3 M/sec = ~300 ms/sec saved per shard (huge); restores integrated throughput to standalone WAL capability; removes allocator from the steady-state hot path.
    - Muscle: this is the third site (W59, W60, now W61) of the same pattern — serialize-into, never serialize-returning. Once it's muscle memory, the pattern reapplies everywhere. Reapplies at: W74 raft RPC encode, W77 aeron term-buffer claim, W83 ledger transfer encode.
  - **Expect to hit (perf) #2 — per-event WAL fsync drops throughput 100× (bar (c) violation)**: the canonical bug — calling `event_log.fsync()` after every `append()` because "durability matters". One fsync = ~10-50 µs on NVMe. At 1 fsync per event × 1 M events/sec = ~10-50 sec/sec of fsync, i.e., 10-50× slower than wall-clock — the WAL can't keep up at all, throughput collapses to ~1k events/sec (one event per fsync cycle).
    - Fix: group commit (W26 wal pattern). Caller batches events; `event_log.fsync()` is called *after* a batch of ~10k events OR ~3 ms timer expires (whichever first). For raft-replicated mode (W74+), fsync is *replaced* by the follower-ack barrier — durability is in the cluster, not the local disk; local fsync runs lazily in background. Use io_uring `IORING_OP_FSYNC` (W58) for the fsync itself so the shard reactor never blocks.
    - Cost avoided: ~50 µs × 1 M/sec → ~50 µs × 100/sec = 500-1000× throughput recovery; this is *the* difference between 1k orders/sec and 1 M orders/sec.
    - Muscle: NEVER fsync per event on a high-throughput log — batch + amortize, then defer durability to a higher layer (replication) when possible. The fsync-per-event antipattern is the most common WAL mistake. Reapplies at: W59 raft log (already taught), W74 matching-engine commit, W83 ledger journal, W92 ledger io_uring fsync.
  - **Acceptance**: 1M event/sec append throughput; replay reaches 10x append throughput (no fsync); crash-recovery exact; heaptrack shows zero alloc-rate on `event_log.append` steady state; fsync rate ≤ 350/sec under 1 M ops/sec workload.

- [ ] Implement CALLF, RETF, JUMPF in exec-vm. (~120 min)
  - **Why**: EOF functions (EIP-4750) replace the implicit "jump into the middle of code" pattern with explicit function-call semantics. CALLF pushes a return frame; RETF pops; JUMPF tail-calls (no return frame). Per-function stack validation (EIP-5450) is what enables removing runtime stack checks.
  - **Design**:
    ```rust
    pub struct ReturnStack {
        frames: SmallVec<[ReturnFrame; 16]>,  // max 1024 depth
    }
    pub struct ReturnFrame {
        pub return_ip: usize,
        pub return_section: u16,
        pub return_stack_floor: u16,
    }

    fn callf<H>(interp: &mut Interpreter, _: &mut H) {
        gas!(interp, 5);
        let target_section = u16::from_be_bytes([interp.bytecode[interp.ip], interp.bytecode[interp.ip + 1]]);
        // Push return frame
        interp.return_stack.push(ReturnFrame {
            return_ip: interp.ip + 2,
            return_section: interp.current_section,
            return_stack_floor: interp.stack_floor,
        });
        // Jump to target function
        interp.current_section = target_section;
        interp.ip = 0;
        // Update stack floor (per-function frame)
        let f = &interp.eof.types[target_section as usize];
        interp.stack_floor = interp.stack.len() - f.inputs as usize;
    }

    fn retf<H>(interp: &mut Interpreter, _: &mut H) {
        gas!(interp, 3);
        let Some(frame) = interp.return_stack.pop() else {
            interp.result = InvalidReturn; return;
        };
        interp.ip = frame.return_ip;
        interp.current_section = frame.return_section;
        interp.stack_floor = frame.return_stack_floor;
    }
    ```
    **Invariants**:
    - Return stack max depth 1024 (mirrors call stack depth).
    - JUMPF replaces tail-call: no return frame pushed; control transfers permanently.
    - Function outputs validated against type-section signature.
    - Stack-floor tracking prevents callee from popping caller's frame values.
  - **Build steps**:
    1. (~30 min) ReturnStack + ReturnFrame types.
    2. (~30 min) CALLF impl with input-validation against type section.
    3. (~20 min) RETF impl with output-validation.
    4. (~20 min) JUMPF impl (no return frame push).
    5. (~20 min) Tests: nested calls, recursion (within depth), invalid section index rejected at deploy.
  - **Pitfalls**: stack-floor management is the most error-prone; off-by-one allows function to read caller's locals.
  - **Acceptance**: EOF function reference vectors pass; deploy-time validation catches malformed section refs.

- [ ] [HFT] **Build**: `crates/matching-engine/src/risk.rs` — `RiskCheck` trait with pre-trade check (balance, position
  limit, fat-finger). Default impl `NoopRisk` rejects nothing; production impl plugs in W63. (~150 min)
  - **Why**: Risk is the EXCHANGE'S liability boundary. A missing pre-trade check = exchange eats the loss when a trader's account goes negative. Trait-based design lets us swap NoopRisk (tests) with production risk (per-account balance, position limits, fat-finger threshold) without touching match logic.
  - *Back-of-envelope*: risk check is on the order-submit hot path, BEFORE matching. Budget at v1.0: **≤ 500 ns** (out of the 5 µs P99 total). At 1 M orders/sec/shard, that's 500 ns × 1 M = 500 ms/sec — half of a CPU core, but it's *necessary* CPU not wasted CPU. The check is per-account: balance + position + fat-finger threshold; per-account state lives in a shard-local cache (`AccountId → AccountState`). Single AccountState read ≈ ~7 ns (one cache miss to L2, then ~100 B record fits in 2 cache lines). Three comparisons + one branch ≈ ~5 ns. The killer is `&dyn RiskCheck` (trait object) — vtable dispatch ≈ ~5 ns + branch-mispredict + inhibits inlining. At 1 M calls/sec that's ~10-20 ns of *just dispatch overhead*. Bar (c): keep risk as a static-dispatch generic OR a monomorphized `enum RiskCheck` if the set is closed, NOT `Box<dyn>`.
  - **Design**:
    ```rust
    pub trait RiskCheck: Send + Sync {
        fn check(&self, order: &Order, book: &OrderBook) -> Result<(), RiskRejection>;
    }
    pub enum RiskRejection {
        InsufficientBalance { required: u64, available: u64 },
        PositionLimitExceeded { current: i64, max: i64 },
        FatFinger { reason: String },
        AccountFrozen,
    }
    pub struct NoopRisk;
    impl RiskCheck for NoopRisk {
        fn check(&self, _o: &Order, _b: &OrderBook) -> Result<(), RiskRejection> { Ok(()) }
    }
    ```
    **Invariants**:
    - Risk check is PRE-trade: called BEFORE match_order; if rejects, order never touches book.
    - Trait is Send + Sync for cross-shard usage (risk service may be on another shard).
    - Production check (W63+) integrates with ledger service for current balance.
  - **Build steps**:
    1. (~30 min) Trait + RiskRejection enum.
    2. (~30 min) NoopRisk default impl.
    3. (~30 min) `FatFingerRisk { max_qty_per_order, max_notional_per_order }` simple impl for testing.
    4. (~30 min) Integration into match flow: `engine.submit(order, risk: &dyn RiskCheck)` → if risk fails, emit Rejected event, return.
    5. (~30 min) Tests: NoopRisk passes everything; FatFingerRisk rejects huge orders.
  - **Pitfalls**: risk check itself slow → puts pressure on match latency. Solution: keep production risk impl per-shard with cached state; full check at deposit-time, lighter checks at order-time.
  - **Expect to hit (perf) #1 — `&dyn RiskCheck` vtable dispatch on the order hot path (bar (c) violation)**: the design uses `engine.submit(order, risk: &dyn RiskCheck)` — every submit pays a vtable load (~7 ns including likely cache miss on the first call after a vtable change) and an indirect call (~5 ns + branch-predictor unknown on first call). Inlining is *fully blocked* by the trait object — the risk check body cannot fuse with the call site, missing ~30% of LLVM optimization. At 1 M submits/sec the dispatch overhead alone is ~10-20 ns × 1 M = 10-20 ms/sec.
    - Fix v0.5: parameterize the engine over a generic risk parameter — `pub struct MatchingEngine<R: RiskCheck>` with `R` monomorphized at construction. Each symbol-shard's engine is its own concrete type; the compiler inlines `risk.check(&order, &book)` directly into the submit path. NoopRisk's body becomes `Ok(())` — the compiler can inline-and-fold it to nothing (zero-cost abstraction). Production risk impl benefits identically. Fix v1.0 (if dynamic risk swap is needed at runtime): use `enum Risk { Noop, FatFinger(FatFingerRisk), Production(ProductionRisk) }` — a single static match, no vtable, still inlinable per arm.
    - Cost avoided: ~10-20 ns/submit; ~20 ms/sec/shard; restores compiler inlining (often saving another ~5-10 ns per call through fold-and-prune); NoopRisk literally becomes zero cycles (the call site folds to nothing).
    - Muscle: dynamic dispatch via `Box<dyn>` / `&dyn` is a hot-path antipattern on bar-(c) crates — use generics or a closed enum. Reapplies at: W74 matching-engine TIF dispatch, W77 aeron flow-control strategy, W83 ledger op handler, W92 VSR message handler.
  - **Acceptance**: trait pluggable via generics (not vtable on hot path); FatFingerRisk demonstrates real rejection; NoopRisk default; NoopRisk on the hot path benched at ~0 ns overhead vs no-risk-check baseline (compiler folds it); FatFingerRisk benched at ≤ 50 ns (an integer compare + branch).
