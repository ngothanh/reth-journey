  - *Mental model*: LRU-K (O'Neil 1993) is the classic buffer-pool eviction policy. Plain LRU evicts the
    least-recently-used frame — but a single sequential scan can flush all hot pages out (the "scan
    resistance" failure). LRU-K tracks the K-th most-recent access per page (K=2 in practice); the page with
    the largest *backward K-distance* (time since K-th most-recent access) is evicted. This rewards pages
    with multiple accesses and penalizes one-shot scans.
  - *Back-of-envelope*: `touch()` and `evict_victim()` are on every page touch — at 100 k page touches/sec
    on a hot mini-db/storage-trie workload, eviction must be O(log n) at worst, **≤ 100 ns per touch**.
    Targets: O(log n) via BinaryHeap pop (~200 ns at n=10 k) OR O(1) via the LRU-K paper's bucket-list
    approach (one intrusive linked list per access-count tier). Hot path: **zero allocations per touch**.
  - *Contract*: `pub struct LruK<const K: usize>` (K=2). State: `Vec<FrameMeta>` indexed by `FrameId`; each
    `FrameMeta` carries `access_times: [Monotonic; K]` (ring of K stamps). Methods: `fn touch(&mut self, id:
    FrameId)` (record an access, rotate the ring), `fn evict_victim(&self, is_pinned: impl Fn(FrameId) -> bool)
    -> Option<FrameId>` (max backward-K-distance among unpinned frames), `fn insert(&mut self, id: FrameId)`
    (track a newly-loaded frame).
  - **Expect to hit #1 — evicting a pinned page (correctness)**: `evict_victim` returns the highest-K-distance
    page without consulting pin state. Symptom: a page in active use is evicted; the holder's pointer
    dangles or its data is reloaded into a different frame.
    - Fix: `evict_victim` MUST take the pin set as an explicit input; it returns `None` if every unpinned
      frame is in K=1 state (one-shot only). Never fall back to "evict the most-recently-pinned."
    - Muscle: an eviction policy and the pin set are coupled — never let the policy pick a pinned victim.
      Reapplies at: W26 wal segment retention, W42 `txn` MVCC version GC, W74 matching-engine order pool.
  - **Expect to hit #2 — backward-K-distance off-by-one (correctness)**: K=2 means the K-th most-recent
    access is the *second* most recent. Confusing it with "the K-th access ever" degrades LRU-K to LRU-1
    plus noise. Symptom: scan resistance fails — sequential scans still flush hot pages.
    - Fix: K-distance = `now - access_times[K-1]` where `access_times` is sorted newest-first. Pages with
      <K accesses have K-distance = `+∞` (always evicted first — single-touch pages are scan candidates).
      Test with a "scan then random" workload; LRU-K must keep the random-access frames hot.
    - Muscle: LRU-K's defining property is the K-th access — get the indexing right or it collapses to LRU.
      Reapplies at: W34 bloom counting policy, W42 `txn` MVCC retention.
  - **Expect to hit (perf) #1 — heap allocation on every touch (bar (c) violation)**: a naive impl rebuilds
    a `BTreeSet<(Monotonic, FrameId)>` priority on every touch — allocates + rebalances per access. At
    100 k touches/sec, 100 k allocations/sec on the hottest path in the pool.
    - Fix: pre-allocate everything. `Vec<FrameMeta>` indexed by `FrameId` (no allocations after pool
      construction); priority via BinaryHeap (one allocation at startup) OR O(1) intrusive bucket-list
      (nodes embedded in `FrameMeta`, splice on touch — zero alloc).
    - Cost avoided: ~50-200 ns per touch (allocation + tree rebalance); at 100 k touches/sec ≈ 5-20 ms/sec
      of CPU recovered.
    - Muscle: any hot eviction policy allocates once at construction; per-access work is O(1) amortized or
      O(log n) without heap traffic. Reapplies at: W42 `txn` lock graph, W34 bloom counter, W74
      matching-engine order pool.
  - **Expect to hit (perf) #2 — cold metadata thrashing the L1 cache (bar (c) violation)**: `FrameMeta` at
    ~32 B (2× Monotonic + counter + flags) × 10 k frames = 320 KB — fits L2, not L1. The eviction scan
    touches every frame's metadata, polluting L1 with cold fields.
    - Fix: separate hot from cold (SoA over AoS). Pack `(last_access, touch_count)` into a single 8 B word
      per frame (80 KB total — fits L1). Cold fields (file id, dirty bit, K-1th access) live in a separate
      Vec accessed only on eviction. Verify with `cargo flamegraph` that the hot path stays in L1.
    - Cost avoided: ~7 ns per touch (L1 vs L2 hit) at 100 k/sec ≈ 700 µs/sec; ~5× speedup of `evict_victim`
      (L1 vs memory on the scan).
    - Muscle: hot-path data lives in L1; cold metadata in L2/memory; separate by struct decomposition
      (SoA, not AoS, for hot fields). Reapplies at: W42 `txn` lock table, W74 matching-engine `PriceLevel`
      (price/qty hot, full order cold), W77 aeron subscriber state.
- [ ] **Build**: `crates/bufpool/src/pin.rs` — `PinnedPage<'a>` RAII guard. `pool.pin(page_id) -> PinnedPage<'a>`
  increments pin count; drop decrements. Pinned pages are evict-immune. (~105 min)
  - *Mental model*: pin tracking is the contract between *readers/writers of page contents* and *the
    eviction policy*. A holder of a `PinnedPage` is guaranteed the page's frame stays resident for the
    lifetime of the guard. The pin count is per-*frame* (not per-page — after eviction + reload, a page may
    live in a different frame). The `'a` lifetime ties the guard to the pool — Rust's borrow checker
    enforces that no pinned reference outlives the pool.
  - *Back-of-envelope*: pin/unpin is on every page touch — 100 k+ ops/sec on hot workloads. Targets:
    `pin()` ≈ **10 ns** (one atomic increment + a `DashMap` lookup), `unpin()` ≈ **10 ns** (atomic
    decrement via Drop). Critical: **pin-count operations MUST NOT serialize with the eviction policy** —
    they're the read-heavy fast path; eviction is the rare slow path. Decouple via per-frame `AtomicU64`
    (one cache line per frame for the hot fields).
  - *Contract*: `pub struct PinnedPage<'a> { pool: &'a BufferPool, frame_id: FrameId, page_id: PageId,
    _marker: PhantomData<&'a [u8]> }`. `Deref<Target = [u8]>` for read; `mark_dirty` API for write (no
    DerefMut — see correctness #1). `Drop` decrements the pin count. `pool.pin(page: PageId) ->
    Result<PinnedPage<'_>, NoFreeFrame>`. On miss, fault in via `P: PageProvider`.
  - **Expect to hit #1 — leaking a pin via `mem::forget` (correctness)**: `PinnedPage` held across code
    that `mem::forget`s (or `ManuallyDrop` without explicit `into_inner`); Drop never runs, pin count
    never decrements. Symptom: pin count climbs forever; pool eventually fills with "pinned" frames that
    aren't actually held; `NoFreeFrame` errors at runtime even though no one is holding the pages.
    - Fix: always treat `PinnedPage` as RAII — never `mem::forget`. If a controlled leak is genuinely
      needed (e.g. handing the page to FFI), provide an explicit `into_raw` / `from_raw` pair so the leak
      is intentional and recoverable.
    - Muscle: RAII guards must use Drop for cleanup; bypassing Drop is the leak pattern. Reapplies at:
      W26 wal segment readers, W42 `txn` lock guards, W74 matching-engine order references.
  - **Expect to hit #2 — pin-during-eviction race (correctness)**: thread A is mid-evict on frame F (chose
    it as victim, removed from page table); thread B pins page P which happens to map to frame F. B
    increments pin_count; A proceeds with eviction. Symptom: data race — B reads garbage from a frame
    being torn down.
    - Fix: eviction is a 2-phase commit. Phase 1: CAS `pin_count` from 0 → `MAX` (sentinel "evicting"). If
      CAS fails (someone pinned), abort and pick another victim. Phase 2: with sentinel set, no new pins
      succeed; safe to swap out the frame.
    - Muscle: any "remove a resource" op in a concurrent setting needs 2PC with a sentinel state to lock
      out new acquirers. Reapplies at: W26 wal segment unlink, W37 epoch-gc pointer reclamation, W42
      `txn` lock release.
  - **Expect to hit (perf) #1 — `Mutex<HashMap>` for the pin table (bar (c) violation)**: storing pin
    counts in `Mutex<HashMap<PageId, u32>>` serializes every pin/unpin behind one mutex. At 100 k pins/sec
    across 16 threads, the mutex is the single bottleneck — throughput plateaus at ~2-5 M ops/sec under
    contention regardless of how many cores you add.
    - Fix: pin count is `AtomicU64` *per frame*, in the same `Vec<FrameMeta>` used by `lru_k`. Atomic
      increment ≈ 10 ns uncontended; no mutex. Page→Frame mapping via `dashmap` (sharded concurrent map).
    - Cost avoided: ~40-200 ns per pin under contention vs ~10 ns atomic ≈ 5-20× speedup; at 100 k/sec
      contended that's ~20 ms/sec of one core recovered.
    - Muscle: per-resource counts use per-resource atomics, never a global mutex. Reapplies at: W26 wal
      segment refcount, W37 epoch-gc reference counting, W42 `txn` lock counts.
  - **Expect to hit (perf) #2 — false sharing between adjacent frames' pin counts (bar (c) violation)**:
    `Vec<AtomicU64>` packs 8 frames' pin counts per 64 B cache line. Two threads pinning two *different*
    frames whose counts share a line false-share — every increment invalidates the other thread's L1
    copy. Symptom: pin throughput drops 30-50% the moment two threads run on different cores.
    - Fix: `Vec<CachePadded<FrameMeta>>` where `FrameMeta` holds the hot atomics (pin_count, last_access).
      At 10 k frames × 128 B padded = 1.28 MB — fits L2, tolerable. Cold fields move to a parallel Vec.
    - Cost avoided: ~7 ns per cross-thread access on false-shared lines; 16-thread workload recovers
      15-30% throughput.
    - Muscle: any per-resource atomic touched by different threads needs cache-line isolation if
      adjacent. Reapplies at: W26 wal per-segment counters, W74 matching-engine per-symbol counters, W77
      aeron per-publication counters.
- [ ] **Build**: `crates/bufpool/src/dirty.rs` — `DirtyPageTracker` with a `HashSet<PageId>` and a counter. Marks pages
  for write-back. Wal (W26) drains the dirty set on group commit. (~105 min)
  - *Mental model*: the dirty-page tracker is the bridge between the buffer pool (in-memory state) and the
    durability layer (wal). Every write marks a page dirty; the wal's group-commit (W26) periodically
    drains the dirty set, fsyncs the corresponding pages, and clears them. Without an explicit dirty set
    you either flush every page (waste) or risk data loss (miss). The set is the **only** source of truth
    for "what needs flushing."
  - *Back-of-envelope*: `mark_dirty` is on every write — 10 k-100 k writes/sec on heavy workloads. Target:
    **O(1), ~20-50 ns** per mark. `drain` is rare (per group-commit, ~100/sec) but must yield all dirty
    pages in bulk. Steady-state set size ≈ write_rate × commit_interval ≈ 10 k × 10 ms = 100 pages.
  - *Contract*: `pub struct DirtyPageTracker { shards: [parking_lot::Mutex<HashSet<PageId>>; N], count:
    AtomicU64 }`. Methods: `fn mark_dirty(&self, page: PageId)` (insert into shard `page % N`);
    `fn drain(&self) -> Vec<PageId>` (snapshot all shards, clear; the snapshot is what gets flushed);
    `fn count(&self) -> u64` (atomic snapshot, lock-free, for backpressure decisions).
  - **Expect to hit #1 — page re-dirtied during flush silently loses durability (correctness)**: thread A
    drains the dirty set and starts fsyncing pages P1..P100. Thread B writes to P50 mid-fsync. After the
    flush completes, P50 is no longer in the dirty set — but B's write isn't yet durable. Symptom: a write
    the application thinks succeeded vanishes on crash.
    - Fix: `drain` snapshots the set atomically; subsequent writes mark a **new** set (double-buffer).
      Fsync operates on the snapshot; concurrent writes go to the new set. A page is "clean" only when
      its data was fsynced AND no later write has occurred since the drain.
    - Muscle: a flush-drain op must double-buffer; never let writes-during-flush silently clear dirty
      bits. Reapplies at: W26 wal group-commit, W42 `txn` write-set tracking, W80 ledger snapshot.
  - **Expect to hit (perf) #1 — `Mutex<HashSet>` contention on the hot write path (bar (c) violation)**:
    one `Mutex<HashSet<PageId>>` serializes every `mark_dirty` behind one lock. At 100 k writes/sec
    across 16 threads, throughput collapses from ~5 M/sec uncontended to 1-2 M/sec under contention.
    - Fix: shard. `[Mutex<HashSet<PageId>>; N]` where N = num_cores; key by `page_id.hash() % N`. Each
      thread mostly hits its own shard (low contention). For higher write rates: per-shard `Vec<PageId>`
      append-only (deduplicate at `drain` time) — eliminates HashSet rebalancing on the hot path.
    - Cost avoided: ~10× throughput on 16 threads; removes the single-mutex ceiling.
    - Muscle: any single global set/map on a hot write path is a scalability ceiling — shard it. Reapplies
      at: W26 wal pending queue (sharded via SegQueue), W42 `txn` write set, W74 matching-engine pending
      orders.
  - **Expect to hit (perf) #2 — `count()` requires the mutex (bar (c) violation)**: if `count()` returns
    `pages.lock().len() as u64`, the backpressure check (called per-op) serializes on the same mutex even
    when no mutation is needed. Symptom: backpressure check itself becomes the bottleneck.
    - Fix: maintain `count: AtomicU64` separately. `mark_dirty` does `if shard.insert(p) {
      count.fetch_add(1, Relaxed) }`; `drain` snapshots count and resets atomically.
    - Cost avoided: ~50 ns per `count()` (lock acquire + len) vs ~5 ns atomic load ≈ 10×; eliminates lock
      contention on the backpressure path.
    - Muscle: read-only summary state on a hot path lives in an atomic, never behind a lock. Reapplies
      at: W26 wal pending count, W14 bufpool free-frame count, W74 matching-engine order count.

    `Frame { page_id: AtomicU64, pin_count: AtomicU64, gen: AtomicU64, data: UnsafeCell<[u8; PAGE_SIZE]>

  - **Expect to hit #1 — pin-table lookup serialization (correctness blends into perf)**:
    `Mutex<HashMap<PageId, FrameId>>` for the page table serializes every pin lookup. At 100 k pins/sec,
    this is the bottleneck; the rest of the pool's lock-free design is wasted.
    - Fix: `dashmap::DashMap<PageId, FrameId>` (or a similar sharded concurrent map). Pin-hit path
      becomes lock-free shard-local lookup → atomic increment ≈ 30 ns. Pin-miss path still needs
      coordination so multiple threads don't double-load the same page — use a secondary
      `DashMap<PageId, Arc<tokio::sync::Mutex<LoadState>>>` for the load-coordination layer.
    - Muscle: concurrent map for the hot table; reserve mutexes for the rare coordination paths.
      Reapplies at: W26 wal segment lookup (sealed_segments BTreeMap behind RwLock), W42 `txn` lock
      table.
  - **Expect to hit (perf) #1 — eviction holds the LRU lock across I/O (bar (c) violation)**: on a full
    pool, pinning a missing page requires evict-then-load. Naive: hold `lru.lock()` through the whole
    sequence — including the ~200 µs disk read — serializing all OTHER pins behind it.
    - Fix: select victim under the lock (~50 ns), release the lock, then perform the load. Use the
      pin-count-sentinel pattern (`pin.rs` pitfall #2) to lock the frame for the load's duration. Other
      threads can pin other frames concurrently — the LRU lock is only held for the ~50 ns selection.
    - Cost avoided: at 100 k pins/sec all serializing behind one 200 µs I/O, effective throughput is
      ~5 ops/sec — releasing the lock recovers full concurrency, ~10⁴× improvement on the miss path.
    - Muscle: **never hold a hot-path lock across I/O** — release before the syscall, re-acquire only
      for the atomic state update after. Reapplies at: W26 wal append-during-fsync, W42 `txn` commit

  - **Expect to hit (perf) #2 — `flush_all` blocks writes (bar (c) violation)**: `flush_all` taking an

      duration) to ~50 ns (steady state).
    - Muscle: a flush operation MUST NOT block the write path — double-buffer or snapshot, fsync the
      snapshot off the hot path. Reapplies at: W26 wal group-commit (already does this), W42 `txn`
      commit, W80 ledger snapshot.
