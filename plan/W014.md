  pointer registry with `protect(p)`/`retire(p)`/`scan_and_reclaim()`. Workload: 4 threads each

  Constraints: no peek at `haphazard` crate, `folly::HazardPointers`, or `crossbeam_epoch` until COMPARE.
  - **Spec**: invariants for (a) pop never returns a freed node, (b) no node freed while protected, (c)
    eventually all retired nodes ARE freed (no leak). Predict the scan frequency tradeoff: too rare =
    leak; too frequent = scan cost dominates.
  - **Build**: Treiber first WITHOUT protection — verify with loom that the unprotected version exhibits
    UAF (use a drop-counter and a use-after-free poison check). Then add hazard pointers.
  - **Loom**: harness with 2 threads pushing+popping the same items; assert each item popped exactly once,
    each node freed exactly once after retirement. WITHOUT hazard pointers, this MUST fail; with, it MUST
    pass. Iterate orderings; max 3 attempts on each.
  - **Compare**: open `haphazard` crate source. Their per-thread record list vs your design. Why their
    `Domain` abstraction? Read the paper again — what edge cases did Michael consider that you didn't?
  - **Symptom card**: bug shape (pop dereferences node freed by concurrent pop); rule (lock-free reclamation
    requires PROTECTION — the reader's hazard slot must be set AND verified before dereference); reapplies

  - **Numbers**: predict pop latency overhead (~10-20 ns per protect; per-thread slot hits L1). Predict
    reclamation amortization (~1 scan per N retirements; per scan ~50 ns / hazard slot). At 4 threads,
    ~1000 ops/sec extra overhead from hazp vs unprotected — negligible vs the UAF prevention.
  - **5-year failure mode**: hazard pointers do NOT scale to data structures with many internal pointers
    (each requires its own slot); for skiplist tower walking, slot count grows. Trigger: W37 skiplist

- [ ] **Build**: `crates/bufpool/src/lru_k.rs` — `LruK<const K: usize>` (K=2) eviction policy. (~total 150 min across 3 phases)
  - 🔧 **Why this matters**: LRU-K (O'Neil 1993) is the canonical buffer-pool eviction; plain LRU is
    scan-vulnerable. Four traps: evicting pinned pages, backward-K-distance off-by-one, per-touch heap
    alloc, L1 thrashing from cold metadata. Downstream: every page-cache decision in W26 wal, W31 mmap-queue,
    W95 mini-db.

  #### Phase 1 — Problem, requirements, design (~30 min)

  - **Requirements** — write in `crates/bufpool/notes/14_lru_k_design.md`:
    - R1. `LruK<const K: usize>` with K=2.
    - R2. `Vec<FrameMeta>` indexed by `FrameId`; `FrameMeta { access_times: [Monotonic; K], …}`.
    - R3. `touch(id)`: rotates the K-ring; O(1).
    - R4. `evict_victim(is_pinned)`: max backward-K-distance among unpinned; takes pin set as input.
    - R5. Pages with <K accesses have K-distance = ∞ (evicted first; scan-resistance).
    - R6. Hot path = ZERO allocations per touch; pre-allocated Vec.
    - R7. Hot fields (last_access, touch_count) in 8B word per frame; cold elsewhere (SoA).
    - R8. ≤100ns per touch at 100k touches/sec.

  - **Design**:
    - D1. Walk through scan-then-random workload. LRU-K must keep random hot.
    - D2. **Pre-mortem**: contributor uses `BTreeSet<(Monotonic, FrameId)>`. What test catches?

  #### Phase 2 — Failing tests (~30 min)

  - [ ] `lru_k_evict_skips_pinned` — frame F1 pinned, F2 unpinned with higher K-distance; evict_victim
    returns F2 (NOT F1).
  - [ ] `lru_k_k_distance_uses_kth_access` — frame with 5 accesses; K=2; distance = `now - access[1]`.
  - [ ] `lru_k_scan_resistance` — 1000 sequential one-shot touches + 100 repeated touches on a "hot"
    page; hot page NOT evicted.
  - [ ] `lru_k_touch_no_alloc` — dhat: 10k touches after warm-up = 0 allocations.
  - [ ] `lru_k_touch_p50_under_100ns` — criterion: p50 ≤ 100ns.
  - [ ] `lru_k_evict_when_all_pinned_returns_none` — all frames pinned; evict_victim returns None.

  #### Phase 3 — One failure at a time (~90 min)

  - **When `lru_k_evict_skips_pinned` evicts pinned page:**
    - Symptom: holder's pointer dangles or data reloaded into different frame.
    - Why: evict_victim picked max-K-distance without consulting pin state.
    - Fix: evict_victim takes `is_pinned` as input; returns None if all unpinned are K=1.
    - Muscle: eviction policy and pin set are COUPLED — never let policy pick pinned. Reapplies at: W26
      wal segment retention, W42 txn MVCC GC, W74 matching-engine order pool.

  - **When `lru_k_scan_resistance` fails (scan flushes hot pages):**
    - Symptom: sequential scan evicts random-access hot pages — LRU-K collapsed to LRU-1.
    - Why: backward-K-distance off-by-one. Used "K-th access ever" not "K-th most recent".
    - Fix: K-distance = `now - access_times[K-1]` where access_times sorted newest-first. Pages with <K
      accesses get K-distance = ∞.
    - Muscle: LRU-K's defining property IS the K-th access. Reapplies at: W34 bloom counting, W42 MVCC
      retention.

  - **When `lru_k_touch_no_alloc` reports >0 allocations:**
    - Symptom: BTreeSet rebuilds on every touch; 100k allocs/sec on the hottest path.
    - Why: tree-based priority.
    - Fix: pre-allocate Vec<FrameMeta>; priority via BinaryHeap (1 alloc at startup) or O(1) intrusive
      bucket-list.
    - Muscle: hot eviction policy allocates once at construction; per-access is O(1) amortized.
      Reapplies at: W42 txn lock graph, W34 bloom counter, W74.

  - **5-year failure mode** (`notes/14_lru_k_followup.md`): when persistent memory blurs cache/storage,
    LRU-K becomes per-tier (DRAM tier + PMEM tier). Migration: parameterize over tier.
- [ ] **Build**: `crates/bufpool/src/pin.rs` — `PinnedPage<'a>` RAII guard. `pool.pin(page_id) -> PinnedPage<'a>`
  increments pin count; drop decrements. Pinned pages are evict-immune. (~total 150 min across 3 phases)
  - 🔧 **Why this matters**: pin tracking is the contract between readers/writers and eviction. Four traps:
    leaking via mem::forget, pin-during-eviction race, mutex-bottleneck, false-sharing. Downstream: W26
    wal, W42 txn locks, W74 matching-engine.

  #### Phase 1 — Requirements (~30 min)

  - R1. `PinnedPage<'a>` RAII guard; Drop decrements pin count.
  - R2. Pin count is `AtomicU64` PER FRAME (not in a shared mutex).
  - R3. Eviction is 2PC: CAS pin_count 0→MAX sentinel; if fails, pick another victim.
  - R4. Per-frame metadata `CachePadded<FrameMeta>` to avoid false sharing.
  - R5. Page→Frame mapping via DashMap (sharded concurrent map).
  - R6. Pin p50 ≤ 30ns; ZERO allocations on the hot path.
  - R7. Explicit `into_raw`/`from_raw` for intentional leaks (FFI).

  #### Phase 2 — Failing tests (~30 min)

  - [ ] `pin_drop_decrements_count` — `let p = pool.pin(id)?; let before = pool.pin_count(id); drop(p);
    let after = pool.pin_count(id); assert_eq!(after, before - 1);`.
  - [ ] `pin_during_eviction_race_safe` — loom: thread A evicts; thread B pins same frame; assert
    EITHER eviction completed and B got NoFreeFrame, OR B's pin succeeded and eviction aborted.
  - [ ] `pin_count_no_mutex_contention` — 16-thread throughput ≥10× single-thread.
  - [ ] `pin_count_no_false_sharing` — `offset_of!(Frame[i+1], pin_count) - offset_of!(Frame[i],
    pin_count) >= 128`.
  - [ ] `pin_latency_under_30ns_p50` — criterion: p50 ≤ 30ns.

  #### Phase 3 — One failure at a time (~90 min)

  - **When `pin_during_eviction_race_safe` finds B reading garbage:**
    - Symptom: data race; B reads from frame mid-tear-down.
    - Why: eviction read pin_count then proceeded; B incremented in between.
    - Fix: 2PC. CAS pin_count 0→MAX sentinel. If CAS fails, pick another victim. With sentinel set, no
      new pins succeed.
    - Muscle: "remove a resource" in concurrent setting needs 2PC with sentinel state. Reapplies at: W26
      wal segment unlink, W37 epoch-gc reclamation, W42 txn lock release.

  - **When `pin_count_no_mutex_contention` plateaus at N=4:**
    - Symptom: 16-thread throughput identical to 4-thread.
    - Why: Mutex<HashMap<PageId, u32>> for pin table.
    - Fix: AtomicU64 per FRAME in Vec<FrameMeta>. DashMap for PageId→FrameId mapping.
    - Muscle: per-resource counts use per-resource atomics. Reapplies at: W26 wal segment refcount, W37
      epoch-gc refcount, W42 lock counts.

  - **When `pin_count_no_false_sharing` shows delta < 128:**
    - Symptom: 16-thread pin throughput drops 30-50% vs ideal.
    - Why: `Vec<AtomicU64>` packs 8 counters per 64B line.
    - Fix: `Vec<CachePadded<FrameMeta>>`. Cold fields in parallel Vec.
    - Muscle: per-resource atomic touched by different threads needs cache-line isolation. Reapplies at:
      W26 wal per-segment counters, W74 matching per-symbol, W77 aeron per-publication.

  - **5-year failure mode** (`notes/14_pin_followup.md`): when async-await wraps everything, Drop-based
    RAII for pins doesn't compose with async (cancellation drops mid-await). Migration: async-aware
    PinHandle with explicit `unpin().await`.
- [ ] **Build**: `crates/bufpool/src/dirty.rs` — `DirtyPageTracker` with a `HashSet<PageId>` and a counter. Marks pages
  for write-back. Wal (W26) drains the dirty set on group commit. (~total 150 min across 3 phases)
  - 🔧 **Why this matters**: dirty tracker bridges buffer pool ↔ wal. Three traps: re-dirty during flush
    (lost durability), single-mutex bottleneck, count-requires-lock.

  #### Phase 1 — Requirements (~30 min)

  - R1. `DirtyPageTracker { shards: [Mutex<HashSet<PageId>>; N], count: AtomicU64 }`.
  - R2. `mark_dirty(page)`: shard by `page % N`; insert; if new, count.fetch_add(1).
  - R3. `drain()`: double-buffer; snapshot current set atomically; subsequent writes go to NEW set.
  - R4. `count() -> u64`: AtomicU64 load. No mutex.
  - R5. Mark_dirty p50 ≤ 50ns; ≥10× scaling at N=16.

  #### Phase 2 — Failing tests (~30 min)

  - [ ] `dirty_drain_double_buffer_durability` — thread A drains snapshot S1; thread B writes P50
    mid-fsync; assert P50 ends up in the next drain.
  - [ ] `dirty_mark_no_mutex_contention` — 16 threads marking; throughput ≥10× single-thread.
  - [ ] `dirty_count_lock_free` — `count()` doesn't acquire any mutex (instrument with a counting Mutex).
  - [ ] `dirty_mark_p50_under_50ns` — criterion p50 ≤ 50ns.

  #### Phase 3 — One failure at a time (~90 min)

  - **When `dirty_drain_double_buffer_durability` shows P50 NOT in next drain:**
    - Symptom: B's write vanishes on crash — wal fsynced S1 without P50; B's write cleared P50's dirty
      bit; subsequent drain doesn't see P50.
    - Why: single-buffer. drain cleared everything; B's mark_dirty after drain inserted into the
      already-cleared set but flush operated on the snapshot.
    - Fix: double-buffer. drain swaps in a new empty set atomically; the OLD set is the snapshot
      flushed; concurrent writes go to the new.
    - Muscle: flush-drain op MUST double-buffer; never let writes-during-flush silently clear dirty
      bits. Reapplies at: W26 wal group-commit, W42 txn write-set, W80 ledger snapshot.

  - **When `dirty_mark_no_mutex_contention` plateaus at N=4:**
    - Symptom: single Mutex<HashSet> serializes all writes.
    - Why: one global mutex.
    - Fix: shard. `[Mutex<HashSet>; N=num_cores]`; key by `page_id % N`. Per-shard append-only
      `Vec<PageId>` for highest throughput; dedup at drain.
    - Muscle: any global set on hot write path is scalability ceiling — shard it. Reapplies at: W26 wal
      pending queue, W42 txn write set, W74 matching pending orders.

  - **When `dirty_count_lock_free` shows mutex acquisition:**
    - Symptom: count() acquires shard mutex via .lock().len().
    - Why: count derived from set len.
    - Fix: maintain `AtomicU64` separately; increment in mark_dirty (only when set.insert returns
      true).
    - Muscle: read-only summary state on hot path lives in atomic, NEVER behind lock. Reapplies at:
      W26 wal pending count, W74 matching order count.

  - **5-year failure mode** (`notes/14_dirty_followup.md`): when persistent memory removes the dirty
    concept (write-through), this tracker becomes legacy. Migration: gate behind `#[cfg(disk_backed)]`.
