- [ ] **Build**: `crates/eth-consensus/src/receipt.rs` — Receipt + ReceiptEnvelope. RLP derive. (~total 210 min across 3 phases)
  - 🔧 **Why this matters**: receipts are the EXECUTION RESULT of each tx — every block's `receiptsRoot` is
    computed from them, every `eth_getTransactionReceipt` RPC returns one. Three traps: cumulative vs per-tx
    gas, fork-dependent status field, EIP-2718 framing. Each mismatch = consensus split. Downstream: W13 block
    validation, W49 revm execution loop, W77 STF validation.

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **Requirements** — write in `crates/eth-consensus/notes/08_receipt_design.md`:
    - R1. `struct Receipt { status: Eip658Value, cumulative_gas_used: u64, logs: Vec<Log>, bloom: Bloom }`
      with `#[derive(RlpEncodable, RlpDecodable)]`.
    - R2. `enum Eip658Value { Eip658(bool), PostState(B256) }` — fork-dependent (post-Byzantium = bool,
      pre = root).
    - R3. `cumulative_gas_used` is the BLOCK-CUMULATIVE counter through this tx, NOT per-tx delta.
    - R4. `enum ReceiptEnvelope { Legacy(Receipt), Eip2930(Receipt), Eip1559(Receipt), Eip4844(Receipt),
      Eip7702(Receipt) }`. EIP-2718 framing: typed = `type_byte || rlp(receipt)`.
    - R5. `receiptsRoot` hashes the typed envelope (including the type byte for typed receipts).
    - R6. `bloom` is the OR of all this receipt's logs' blooms (computed from `logs`, not stored
      separately).
    - R7. Round-trip mainnet fixtures across all envelope types.

  - **Design walk-through**:
    - D1. Walk through `cumulative_gas_used` for 3 txs in a block. Tx1 uses 21000, tx2 uses 50000, tx3
      uses 100000. What does receipt[2].cumulative_gas_used equal? What's tx2's per-tx gas?
    - D2. Pre-Byzantium vs post-Byzantium: walk through `Eip658Value` decode. Length-based dispatch?
    - D3. Typed envelope framing: walk through the encode for Eip1559. Outer = type byte + RLP(4-element
      list).
    - D4. Bloom is the OR of logs: walk through 3 logs. Each accrues bits; the receipt's bloom is the
      OR.
    - D5. **Pre-mortem**: contributor stores per-tx gas in `cumulative_gas_used`. What test catches?

  #### Phase 2 — Write the failing tests (~40 min)

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `receipt_cumulative_gas_is_block_total` returns per-tx deltas:**
    - Symptom: receipts have cumulative_gas = 21k, 50k, 100k (per-tx). Block-2's receiptsRoot mismatches
      mainnet starting at tx2.
    - Why: you stored `tx.gas_used` directly in the field.
    - Fix: the field is the RUNNING TOTAL through this tx. Compute as `prev_cumulative + this_tx_gas`.
      Per-tx gas is a DERIVED value (`this.cumulative - prev.cumulative`).
    - Muscle: a receipt stores a block-cumulative counter, NOT a per-tx delta. Reapplies at: W13 block
      validation, W49 revm execution loop, W77 STF validation.

  - **When `receipt_status_decode_by_length` errors on `[0xa0, …]` as "expected bool":**
    - Symptom: pre-Byzantium receipts fail to decode because you hard-coded the first field as a u8.
    - Why: you didn't model `Eip658Value` as a fork-dependent enum.
    - Fix: peek the encoded field length: 0-1 byte = `Eip658(bool)`, 32 bytes = `PostState(B256)`.
    - Muscle: a consensus field whose TYPE changed at a fork must be an enum, decoded by inspecting
      bytes. Reapplies at: W13 historical block replay, W7 EIP-7702 envelope.

  - **When `receipts_root_mainnet_block_15000000` mismatches for blocks with typed txs:**
    - Symptom: legacy-only blocks pass; mixed-type blocks fail.
    - Why: typed receipt framing wrong — you put the type byte INSIDE the RLP list as a 5th element.
    - Fix: typed envelope = `type_byte || rlp([status, gas, bloom, logs])`. Type byte is OUTSIDE the
      list, prepended.
    - Muscle: EIP-2718 framing prepends a raw type byte OUTSIDE the RLP payload — same as TxEnvelope.
      Reapplies at: W9 TxEnvelope, W13 receipts trie, W15 EIP-7685 requests.

  - **5-year failure mode** (write in `notes/08_receipt_followup.md` after green): when EIP-7691 or
    future ZK-rollup-friendly receipt formats land, `Eip658Value` may grow a third variant (e.g. proof
    commitment). State migration: `#[non_exhaustive]` enum, dispatch via type ID.

**Friday — `Log` + `Bloom`**

- [ ] Walk evm.codes — the top 20 opcodes — as hands-on prep for W009's interpreter. (~30 min)
- [ ] **Build**: `crates/eth-consensus/src/log.rs` — Log + bloom_filter(logs). Note: the Bloom filter here is a
  fixed-size 2048-bit Ethereum bloom. The general `bloom` crate (classic + counting + scalable) ships W34. (~total 210 min across 3 phases)
  - 🔧 **Why this matters**: every block's `logsBloom` field is computed from its logs; a single bit wrong
    means the header hash diverges (consensus split). Four traps: 11-bit extraction, big-endian bit
    ordering, OR-not-re-hash composition, and the maybe-vs-yes semantics. Downstream: W13 bloom validation,
    W34 `bloom` crate, W39 lsm-core SSTable bloom.

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **Requirements** — write in `crates/eth-consensus/notes/08_log_bloom_design.md`:
    - R1. `struct Log { address: Address, topics: Vec<B256>, data: Bytes }` with derive.
    - R2. `struct Bloom([u8; 256])` — fixed 2048 bits.
    - R3. `Bloom::accrue(&mut self, input: &[u8])`: keccak256(input), take 3 byte-pairs (bytes 0-1, 2-3,
      4-5), mask each to low 11 bits, set that bit position.
    - R4. Bit position big-endian over the 2048-bit field: `bytes[255 - bit/8] |= 1 << (bit % 8)`.
    - R5. `Log::bloom(&self) -> Bloom`: accrue address + all topics.
    - R6. `logs_bloom(logs) -> Bloom`: bitwise OR of all logs' blooms.
    - R7. Bloom match = "maybe present"; never "definitely present".

  - **Design walk-through**:
    - D1. Walk through `accrue(&[0xAA, 0xBB, …])` step by step. keccak gives 32 bytes; take byte-pairs;
      mask 11 bits; set bits.
    - D2. Big-endian bit order: walk through bit index 1500. Which byte, which bit?
    - D3. `Log::bloom` accrues N items (1 address + topics.len()). Each accrue sets 3 bits.
    - D4. **Pre-mortem**: contributor uses little-endian byte addressing. What test catches?

  #### Phase 2 — Write the failing tests (~40 min)

  - [ ] `bloom_accrue_address_matches_geth` — `Bloom::default().accrue(&addr.0)`; compare to a known
    address bloom from Geth. Exercises R3.
  - [ ] `bloom_bit_order_big_endian` — accrue an input known to set bit 1500; assert `bytes[255 - 1500/8]
    & (1 << (1500 % 8)) != 0`. Exercises R4.
  - [ ] `bloom_eleven_bit_mask` — accrue an input whose keccak gives `byte_pair = 0xFFFF`; assert bit
    index = `0x07FF = 2047`, not anything > 2047. Exercises R3.
  - [ ] `logs_bloom_is_or_not_rehash` — 3 logs; `logs_bloom([log1, log2, log3]) == log1.bloom() |
    log2.bloom() | log3.bloom()`. Exercises R6.
  - [ ] `block_logs_bloom_mainnet_block_15000000` — pull a known mainnet block; compute logsBloom from
    logs; matches header. Exercises R6 + R7.
  - [ ] `bloom_match_can_false_positive` — construct a bloom that has all bits the query expects, plus
    extras; assert match returns true but the underlying logs don't contain a match. Documents R7.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `bloom_accrue_address_matches_geth` mismatches:**
    - Symptom: your bloom is a valid 256-byte blob but never matches Geth.
    - Why: bit-index extraction wrong. You took the HIGH 11 bits, or 12 bits, or one byte not a pair.
    - Fix: `index = u16::from_be_bytes([h[2*i], h[2*i+1]]) & 0x07FF`. Exactly the low 11 bits of the
      i-th byte-pair.
    - Muscle: Ethereum bloom uses LOW 11 bits of each of the first 3 keccak byte-pairs — no other slice.
      Reapplies at: W13 block bloom, W34 `bloom` crate, W39 lsm-core SSTable bloom.

  - **When `bloom_bit_order_big_endian` finds the bit at `bytes[bit/8]` instead of `bytes[255 -
    bit/8]`:**
    - Symptom: right count of bits set, wrong positions. logsBloom is a byte-permutation of Geth's.
    - Why: you used little-endian byte addressing (`bytes[bit/8]`).
    - Fix: Ethereum numbers bits big-endian over the WHOLE 2048-bit field. `bytes[255 - bit/8] |= 1 <<
      (bit % 8)`. Or equivalently `bytes[256 - 1 - bit/8]`.
    - Muscle: bloom bit order is big-endian over the whole 2048-bit field, NOT per-byte little-endian.
      Reapplies at: W13 bloom cross-check, W34 bloom bit addressing.

  - **When `logs_bloom_is_or_not_rehash` produces a different result than the OR:**
    - Symptom: `logs_bloom([…])` differs from `log1.bloom() | log2.bloom() | log3.bloom()`. Block bloom
      mismatch.
    - Why: you re-hashed the logs' concatenated bytes instead of ORing their blooms.
    - Fix: `logs_bloom` = `logs.iter().fold(Bloom::default(), |acc, log| acc | log.bloom())`. Pure OR.
    - Muscle: blooms compose by bitwise OR ONLY; aggregation never re-hashes. Reapplies at: W13 block
      bloom, W34 scalable bloom union, W39 lsm-core level bloom merge.

  - **5-year failure mode** (write in `notes/08_log_bloom_followup.md` after green): when log volume
    grows past 1M/block, the 2048-bit bloom saturates (most bits set; query becomes useless). State
    migration: a scalable bloom (W34) per-block tier with merge semantics. Trigger: when the FP rate
    on `eth_getLogs` exceeds 50% on hot blocks.
