- [ ] **Build**: `crates/eth-consensus/src/receipt.rs` — Receipt + ReceiptEnvelope. RLP derive. (~150 min)
  - *Mental model*: a receipt is the *result* of executing one transaction — it records whether the tx
    succeeded, how much cumulative gas the block had burned by the end of this tx, the logs it emitted, and
    the bloom of those logs. Receipts are RLP-encoded into the block's `receiptsRoot`; mismatching one byte
    is a consensus split. `ReceiptEnvelope` adds the EIP-2718 typed-transaction wrapper, exactly like
    `TxEnvelope` for transactions.
  - *Contract*: `struct Receipt { status: Eip658Value, cumulative_gas_used: u64, logs: Vec<Log>, bloom: Bloom }`
    deriving `RlpEncodable`/`RlpDecodable` (W5 Friday). `Eip658Value` is an enum — `Eip658(bool)` post-Byzantium
    or `PostState(B256)` pre-Byzantium. `enum ReceiptEnvelope { Legacy(Receipt), Eip2930(Receipt),
    Eip1559(Receipt), Eip4844(Receipt) }` with `encode_2718`/`decode_2718` that prepend/strip the 1-byte type
    id for non-legacy variants. Mirror `alloy-consensus::Receipt` + `ReceiptEnvelope` field-for-field.
  - *encode, roughly*: (1) compute the logs bloom (W34 / Friday's `log.rs` — for the receipt it is the OR of
    every log's bloom); (2) RLP a 4-element list `[status_or_root, cumulative_gas_used, bloom, logs]`; (3) for
    a typed envelope, prepend the EIP-2718 type byte *outside* the RLP list. Step 3's framing (typed byte is
    not part of the list payload, but `receiptsRoot` hashes the type byte + list together) is the real exercise.
  - **Expect to hit #1 — cumulative vs per-tx gas**: storing this tx's own `gas_used` in the
    `cumulative_gas_used` field. Symptom: `receiptsRoot` matches for the first tx in a block and diverges for
    every later one; per-receipt `gas_used` (a derived value) comes out wrong.
    - Fix: the field is the *running block total* through this tx; per-tx `gas_used` = this receipt's
      cumulative minus the previous receipt's cumulative (the first receipt's gas_used equals its cumulative).
    - Muscle: a receipt stores a block-cumulative counter, not a per-tx delta. Reapplies at: W13 block
      validation, W49 revm execution loop, W77 STF validation.
  - **Expect to hit #2 — status-vs-state-root field is fork-dependent**: hard-coding the first field as a
    `bool` status. Symptom: pre-Byzantium receipts (the field is a 32-byte post-state root, EIP-658 changed
    it to a 0/1 status) fail to decode, or decode a 32-byte root as a giant integer.
    - Fix: model the field as `Eip658Value` — RLP-decode by length: a 32-byte string is a `PostState` root,
      a 0/1 scalar is an `Eip658` status; encode each back to its original shape.
    - Muscle: a consensus field whose *type* changed at a fork must be an enum, decoded by inspecting the
      bytes. Reapplies at: W13 historical block replay, W7 EIP-7702 envelope.
  - **Expect to hit #3 — typed receipt: type byte inside vs outside the RLP list**: encoding an EIP-1559
    receipt as a 5-element list `[type, status, gas, bloom, logs]`, or hashing the bloom of one log instead
    of the OR of all logs. Symptom: `receiptsRoot` mismatch only for blocks containing typed txs; legacy-only
    blocks pass.
    - Fix: typed envelope = `type_byte ++ rlp([status, gas, bloom, logs])` — the type byte is concatenated
      *before* the 4-element list, never a list element; the receipt's `bloom` is `logs.iter().fold(...)`.
    - Muscle: EIP-2718 framing prepends a raw type byte outside the RLP payload — same shape as `TxEnvelope`.
      Reapplies at: W9 TxEnvelope encode, W13 receipts trie, W15 EIP-7685 requests.

**Friday — ME ch13 + `Log` + `Bloom`**

- [ ] ME ch13 full. Walk evm.codes top 20 opcodes. (~60 min)
- [ ] **Build**: `crates/eth-consensus/src/log.rs` — Log + bloom_filter(logs). Note: the Bloom filter here is a
  fixed-size 2048-bit Ethereum bloom. The general `bloom` crate (classic + counting + scalable) ships W34. (~150 min)
  - *Mental model*: a `Log` is one `LOG0..LOG4` event a contract emitted — an emitting `address`, up to 4
    indexed `topics`, and opaque `data`. The Ethereum bloom is a *fixed* 2048-bit (256-byte) filter that lets
    a light client ask "could this block contain a log touching address/topic X?" without downloading every
    log. It is not a tunable bloom — size, hash, and bit count are all fixed by the consensus spec.
  - *Contract*: `struct Log { address: Address, topics: Vec<B256>, data: Bytes }` deriving
    `RlpEncodable`/`RlpDecodable`. `struct Bloom([u8; 256])`. `Bloom::accrue(&mut self, input: &[u8])` ORs the
    3 bits for one item in; `Log::bloom(&self) -> Bloom` accrues the address + every topic; a free
    `logs_bloom(logs: &[Log]) -> Bloom` ORs every log's bloom together. Mirror `alloy-primitives::Bloom`.
  - *accrue, roughly*: (1) `keccak256(input)` → 32-byte hash; (2) take the first three big-endian *byte-pairs*
    of that hash (bytes 0-1, 2-3, 4-5); (3) for each pair, mask to its low 11 bits → a bit index in `0..2048`;
    (4) set that bit in the 256-byte array. Step 3 (correct 11-bit extraction *and* correct big-endian
    byte/bit addressing into the array) is the real exercise.
  - **Expect to hit #1 — bit-index extraction off by the wrong 11 bits**: taking the *high* 11 bits of each
    16-bit pair, or masking 12 bits, or using one byte instead of a pair. Symptom: your bloom is a valid
    256-byte blob but never matches Geth's `logsBloom`; `eth_getLogs`-style membership tests miss real logs.
    - Fix: index = `u16::from_be_bytes([h[2i], h[2i+1]]) & 0x07FF` — exactly the low 11 bits (`2^11 = 2048`).
    - Muscle: the Ethereum bloom uses the low 11 bits of each of the first three keccak byte-pairs — no other
      slice. Reapplies at: W13 block bloom validation, W34 `bloom` crate, W39 lsm-core SSTable bloom.
  - **Expect to hit #2 — big-endian bit ordering inside the byte array**: addressing bit `n` as
    `bytes[n/8]` bit `n%8` little-endian, i.e. bit 0 = LSB of byte 0. Symptom: the *right number* of bits are
    set but in mirrored positions; your `logsBloom` is a byte-permutation of Geth's and never matches.
    - Fix: Ethereum numbers bits MSB-first from the *end* — set `bytes[255 - n/8] |= 1 << (n % 8)` (or the
      equivalent `bytes[256 - 1 - n/8]`); verify against a known block's `logsBloom` hex.
    - Muscle: the bloom's bit order is big-endian over the whole 2048-bit field, not per-byte little-endian.
      Reapplies at: W13 bloom cross-check, W34 `bloom` crate bit addressing.
  - **Expect to hit #3 — block bloom is an OR, never a re-hash**: computing the block `logsBloom` by hashing
    all logs' bytes together, or by `accrue`-ing receipts instead of bitwise-ORing their blooms. Symptom:
    block-header `logsBloom` mismatch; the header hash diverges → consensus split.
    - Fix: the block bloom = bitwise OR of every receipt's bloom = bitwise OR of every log's bloom; OR is
      associative so receipt-level and log-level aggregation must agree — assert they do.
    - Muscle: blooms compose by bitwise OR only; aggregation never re-hashes. Reapplies at: W13 block bloom,
      W34 scalable bloom union, W39 lsm-core level bloom merge.
  - **Expect to hit #4 — treating a bloom hit as a definite hit**: a downstream filter assumes a set bit
    means the log is present. Symptom: `eth_getLogs`-style queries return false positives — a block whose
    bloom matches but contains no matching log — and any code that skips re-checking the actual logs is wrong.
    - Fix: a bloom match is "maybe present"; always re-scan the block's real logs to confirm. False negatives
      are impossible, false positives are expected.
    - Muscle: a bloom answers "definitely not" or "maybe" — never "definitely yes". Reapplies at: W34 `bloom`
      crate semantics, W39 lsm-core SSTable lookups, W41 LCS read path.
