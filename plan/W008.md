  - *Mental model*: a Receipt is the per-tx execution **result** committed to consensus; the block's

  - *Contract* (signatures only — never the body):
    ```rust
    struct Receipt { status: Eip658Value, cumulative_gas_used: u64, logs: Vec<Log>, bloom: Bloom }
    enum Eip658Value { Eip658(bool), PostState(B256) }
    enum ReceiptEnvelope { Legacy(Receipt), Eip2930(Receipt), Eip1559(Receipt), Eip4844(Receipt), Eip7702(Receipt) }
    impl ReceiptEnvelope { fn encode_2718(&self, out: &mut dyn BufMut); fn type_byte(&self) -> Option<u8>; }
    impl Receipt {
        fn from_logs(status: Eip658Value, cumulative_gas: u64, logs: Vec<Log>) -> Self;
        // Block-processing accumulator: derives cumulative_gas_used from the PREVIOUS receipt
        // plus THIS tx's gas. This is the only API that exercises the per-tx-vs-cumulative
        // distinction in code — `from_logs` takes cumulative directly and cannot trap it.
        fn for_tx(prev: Option<&Receipt>, this_tx_gas: u64, status: Eip658Value, logs: Vec<Log>) -> Self;
        //   ^ cumulative_gas_used = prev.map_or(0, |r| r.cumulative_gas_used) + this_tx_gas
    }
    fn receipts_root(receipts: &[ReceiptEnvelope]) -> B256;
    ```
  - *Back-of-envelope* (bar (b) — correctness-sizing, not a latency budget): `Bloom` is **256 B fixed**, so
    a receipt's own size is dominated by logs, not the bloom. Each log's bloom = `(1 address + topics.len())`
    keccaks × 3 bit-sets; the receipt bloom is the OR of its logs' blooms — so it is **derived from `logs`**,
    never stored independently. Implication: do NOT keep a second source of truth for `bloom`; recompute-or-cache
    from `logs` so the two can never disagree (a disagreement is a consensus split).
  - *Anti-shortcut audit* — name the tempting-but-wrong move (each is exactly what a Phase-2 test below must fail on):
    - **Store per-tx `tx.gas_used` in `cumulative_gas_used`.** Wrong: the field is the block-running total
      through this tx; per-tx gas is the *derived* delta. → trapped by `receipt_cumulative_gas_is_block_total`.
    - **Always prepend a type byte in `encode_2718`.** Wrong: legacy receipts have NO type byte (they encode
      as a bare RLP list `>= 0xc0`). → trapped by `receipt_envelope_legacy_no_type_byte`.
    - **Model `status` as a plain `u8`/`bool` and rely on `#[derive(RlpDecodable)]`.** Wrong: pre-Byzantium it
      is a 32-byte post-state root; it must be a length-dispatched enum. → trapped by `receipt_status_decode_by_length`.
    - **Put the type byte INSIDE the RLP list as a 5th element.** Wrong: EIP-2718 prepends a raw byte OUTSIDE
      the payload. → trapped by `receipts_root_mainnet_block_15000000`.

  - **Requirements** — write in `crates/eth-consensus/notes/08_receipt_design.md`:
    - R1. `struct Receipt { status: Eip658Value, cumulative_gas_used: u64, logs: Vec<Log>, bloom: Bloom }`
      with `#[derive(RlpEncodable, RlpDecodable)]`.
    - R2. `enum Eip658Value { Eip658(bool), PostState(B256) }` — fork-dependent (post-Byzantium = bool,

    - R3. `cumulative_gas_used` is the BLOCK-CUMULATIVE counter through this tx, NOT per-tx delta.

    - R6. `bloom` is the OR of all this receipt's logs' blooms (computed from `logs`, not stored

    - R7. Round-trip mainnet fixtures across all envelope types.

      is in-range.)
    - P4. Derive-correctness: does `logs_bloom` over 3 logs equal `log1|log2|log3` if you re-hash the
      concatenated log bytes? (No — predict why.)
    - P5. **List every Phase-2 test you predict your first attempt will fail.** Compare to reality after tests run.
  - *Mental model*: the block `logsBloom` is a 2048-bit probabilistic index over every log's address+topics;
    it answers "MAYBE present" so `eth_getLogs` can skip blocks cheaply. A single wrong bit diverges the
    header hash → consensus split.
  - *Contract* (signatures only — never the body):
    ```rust
    struct Log { address: Address, topics: Vec<B256>, data: Bytes }
    struct Bloom([u8; 256]);
    impl Bloom { fn accrue(&mut self, input: &[u8]); fn contains_input(&self, input: &[u8]) -> bool; }
    impl core::ops::BitOr for Bloom { type Output = Bloom; /* OR of the 256-byte arrays */ }
    impl Log { fn bloom(&self) -> Bloom; }
    fn logs_bloom(logs: &[Log]) -> Bloom;
    ```
  - *Back-of-envelope* (bar (b) — sizing the recompute cost so we know to cache): `Bloom` = **256 B fixed**.
    Each `accrue` = **1 keccak256 (~1 µs cold) + 3 byte-pair masks + 3 bit-sets**. A log with `(1 + topics.len())`
    items costs that many keccaks. A 1M-log block recomputing every log's bloom from scratch = **~1M keccaks ≈ 1 s**
    per pass — so the per-tx receipt bloom must be **cached at accrual time, not recomputed** on every
    `logs_bloom` aggregation. The aggregation itself is pure OR (256-byte SIMD-friendly), effectively free vs
    the keccaks.
  - *Anti-shortcut audit* — name the tempting-but-wrong move (each is exactly what a Phase-2 test below must fail on):
    - **Little-endian byte index `bytes[bit/8]`.** Wrong: Ethereum numbers bits big-endian over the whole
      2048-bit field. → trapped by `bloom_bit_order_big_endian`.
    - **Take the HIGH 11 bits, or 12 bits, or a single byte.** Wrong: it's the LOW 11 bits of each of the
      first 3 keccak byte-pairs. → trapped by `bloom_eleven_bit_mask` / `bloom_accrue_address_matches_geth`.
    - **Re-hash the concatenated logs' bytes to build the block bloom.** Wrong: aggregation is pure bitwise
      OR; it never re-hashes. → trapped by `logs_bloom_is_or_not_rehash`.

  - **Requirements** — write in `crates/eth-consensus/notes/08_log_bloom_design.md`:
    - R1. `struct Log { address: Address, topics: Vec<B256>, data: Bytes }` with derive.
    - R2. `struct Bloom([u8; 256])` — fixed 2048 bits.
    - R3. `Bloom::accrue(&mut self, input: &[u8])`: keccak256(input), take 3 byte-pairs (bytes 0-1, 2-3,
      4-5), mask each to low 11 bits, set that bit position.
    - R4. Bit position big-endian over the 2048-bit field: `bytes[255 - bit/8] |= 1 << (bit % 8)`.
    - R5. `Log::bloom(&self) -> Bloom`: accrue address + all topics.
    - R6. `logs_bloom(logs) -> Bloom`: bitwise OR of all logs' blooms.
    - R7. Bloom match = "maybe present"; never "definitely present".

  - **Design walk-through**:

      mask 11 bits; set bits.

    - D3. `Log::bloom` accrues N items (1 address + topics.len()). Each accrue sets 3 bits.
    - D4. **Pre-mortem**: contributor uses little-endian byte addressing. What test catches?

    ```rust
    #[test]
    fn logs_bloom_or_differs_from_rehash() {
        let logs = sample_three_logs();
        let by_or = logs.iter().fold(Bloom::default(), |a, l| a | l.bloom());
        // the naive "shortcut": hash the concatenated log bytes as if it were one input
        let mut by_rehash = Bloom::default();
        let mut concat = Vec::new();
        for l in &logs { concat.extend_from_slice(&l.address.0); for t in &l.topics { concat.extend_from_slice(&t.0); } }
        by_rehash.accrue(&concat);
        // If these were equal, the OR-vs-rehash test would be vacuous — assert they are NOT.
        assert_ne!(by_or.0, by_rehash.0,
            "OR-composition and re-hash produced the SAME bloom — the trap test cannot catch the shortcut");
        // and the correct one matches mainnet (cross-check against block_logs_bloom_mainnet test fixture)
        assert_eq!(by_or.0, expected_mainnet_logs_bloom().0);
    }
    ```
    This is the genuine negative-control: it fails LOUDLY if the byte-for-byte difference between the correct
    OR and the naive re-hash ever vanishes, proving the harness is live, not vacuously green.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `bloom_accrue_address_matches_geth` mismatches:**
    - Symptom: your bloom is a valid 256-byte blob but never matches Geth.
    - Why: bit-index extraction wrong. You took the HIGH 11 bits, or 12 bits, or one byte not a pair.
    - Fix: `index = u16::from_be_bytes([h[2*i], h[2*i+1]]) & 0x07FF`. Exactly the low 11 bits of the
      i-th byte-pair.
    - Muscle: Ethereum bloom uses LOW 11 bits of each of the first 3 keccak byte-pairs — no other slice.
      Reapplies at: W13 block bloom, W34 `bloom` crate, W39 lsm-core SSTable bloom.

  - **When `bloom_bit_order_big_endian` finds the bit at `bytes[bit/8]` instead of `bytes[255 -
    bit/8]`:**
    - Symptom: right count of bits set, wrong positions. logsBloom is a byte-permutation of Geth's.
    - Why: you used little-endian byte addressing (`bytes[bit/8]`).
    - Fix: Ethereum numbers bits big-endian over the WHOLE 2048-bit field. `bytes[255 - bit/8] |= 1 <<
      (bit % 8)`. Or equivalently `bytes[256 - 1 - bit/8]`.
    - Muscle: bloom bit order is big-endian over the whole 2048-bit field, NOT per-byte little-endian.
      Reapplies at: W13 bloom cross-check, W34 bloom bit addressing.

  - **When `logs_bloom_is_or_not_rehash` produces a different result than the OR:**
    - Symptom: `logs_bloom([…])` differs from `log1.bloom() | log2.bloom() | log3.bloom()`. Block bloom
      mismatch.
    - Why: you re-hashed the logs' concatenated bytes instead of ORing their blooms.
    - Fix: `logs_bloom` = `logs.iter().fold(Bloom::default(), |acc, log| acc | log.bloom())`. Pure OR.
    - Muscle: blooms compose by bitwise OR ONLY; aggregation never re-hashes. Reapplies at: W13 block
      bloom, W34 scalable bloom union, W39 lsm-core level bloom merge.

    on `eth_getLogs` exceeds 50% on hot blocks.
