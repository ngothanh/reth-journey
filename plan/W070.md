**Tuesday — Engine API spec preview (the EL's public RPC contract)**

- [ ] `notes/70_engine_api.md` — tabulate the Engine API method surface that `consensus-engine` must implement.
  One row per method: `engine_newPayloadV{1,2,3}`, `engine_forkchoiceUpdatedV{1,2,3}`, `engine_getPayloadV{1,2,3}`.
  For each: what the CL sends, what the EL returns (`PayloadStatus` / `ForkchoiceUpdatedResult`), and which
  hard-fork added/changed it (Paris/Shanghai/Cancun → withdrawals, blob gas). (~60 min)
  - *Mental model*: the Engine API *is* the consensus-engine crate's external contract. W75 will implement these
    exact method signatures; getting the version matrix right now means W75's contract section writes itself.
    The version suffixes are not cosmetic — V2 adds withdrawals, V3 adds blob versioned hashes; mixing them is a
    real failure class.
  - 🎯 Hardened acceptance: the table has ≥9 rows (3 methods × 3 versions) and each `newPayload` row names the
    payload field that version *added* (V2: `withdrawals`, V3: `blobGasUsed`/`excessBlobGas` + `versionedHashes`
    param). A table that lists methods without the per-version delta fails — the delta is the whole point.
  - *Anti-shortcut note*: resist copying the spec's full JSON schemas. Capture only the method → {input, output,
    fork} mapping. The schema lives in the spec; your note is the *index*.
- [ ] 🧮 **Paper drill (G9 — the survey week's by-hand artifact)** — write in `notes/70_engine_api_drill.md`: D-WALK one
  complete Engine API exchange by hand on concrete payloads (this is the domain drill a domain-only week still owes;
  it grounds Tuesday's method table in an executed trace, not a read one). (~25 min)
  - The 4-message trace, drawn as CL↔EL arrows with the EL's `head/safe/finalized` pointers redrawn after each message:
    1. CL→EL `engine_newPayloadV3(payload{blockNumber: 19_000_001, blockHash: 0xbeef…, parentHash: 0xaaaa…,
       blobGasUsed: 0, excessBlobGas: 0}, versionedHashes: [], parentBeaconBlockRoot: 0xcccc…)` — EL validates
       (parent `0xaaaa…` known, executes body, state root matches) but does NOT move head.
    2. EL→CL `{status: VALID, latestValidHash: 0xbeef…, validationError: null}`.
    3. CL→EL `engine_forkchoiceUpdatedV3(state{headBlockHash: 0xbeef…, safeBlockHash: 0xaaaa…,
       finalizedBlockHash: 0x9999…}, payloadAttributes: null)` — NOW draw head moving `0xaaaa…` → `0xbeef…`,
       safe → `0xaaaa…`, finalized → `0x9999…`.
    4. EL→CL `{payloadStatus: {status: VALID, latestValidHash: 0xbeef…}, payloadId: null}` (null because
       `payloadAttributes` was null — no block-building requested).
  - Then the status-transition NEGATIVE: rerun message 1 with `parentHash: 0xdddd…` the EL has never seen →
    EL answers `{status: SYNCING, latestValidHash: null}` and BUFFERS the payload (not a rejection — Thursday's
    reth buffering trap, met here on paper first); mark which message the CL must NOT get a VALID for until the
    parent arrives, and that head stays at `0xaaaa…` throughout.
  - **Output**: `notes/70_engine_api_drill.md` with the 4-message trace + pointer drawings + the SYNCING negative,
    closing with the invariant made concrete: "the EL never advances head except via `forkchoiceUpdated` —
    `newPayload` only validates or buffers."
- [ ] Commit notes (~10 min)
