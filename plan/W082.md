  #### Phase 1 — Problem, requirements, design (~70 min, no code yet)

  - **The problem this primitive solves**: UDP delivers out-of-order with loss; subscriber needs in-order delivery + loss recovery + bounded memory. Reorder buffer stages POSITIONS (not data — data lives in term buffer's retention).

  - **Requirements** (the 🎯 Hardened acceptance above restated):
    - R1. Throughput ≥10M msg/s in-order delivery sustained 60s LAN at 128 B payload.
    - R2. P50 ≤100 ns, P99 ≤500 ns, P99.9 ≤2 µs under 0% loss.
    - R3. Under 5% loss: P50 ≤200 ns, P99 ≤50 µs (NAK+retransmit), P99.9 ≤200 µs, P99.99 ≤500 µs.
    - R4. Zero allocation under 5% loss (dhat) — reorder uses offset-triple, NOT `Bytes`.
    - R5. Loom-green: position monotonicity (no rollback), reorder drain correctness under adversarial out-of-order.
    - R6. NAK suppression: under repeated loss + retransmit, NO duplicate NAK in <nak_delay window.
    - R7. Reorder buffer bounded: under prolonged 1s blackout at 10M msg/sec, caps at max_size_bytes; older dropped + NAK fires.
    - R8. 100% application delivery for 1M messages with 5% uniform loss + 1% reorder + 0.1% duplicate.
    - R9. Graceful degradation under sustained 50% loss: Image marks Inactive + surfaces typed error.

  - **Design walk-through**:
    - D1. Sketch Image + ReorderBuffer + ImageStatus.
    - D2. **Pre-mortem (BTreeMap with Bytes allocates per out-of-order frame):** `self.reorder_buffer.buf.insert(pos, payload)` stores owned Bytes (Arc-counted heap) — payload was zero-copy pointing into term buffer but now requires heap copy. At 5% loss, ~50k allocs/sec on 1M pps stream. P99.9 includes ~500 µs allocator tail per loss burst. Walk through offset-triple `BTreeMap<i64, (term_id, offset, len)>` — term buffer's 3-term retention keeps bytes alive.
    - D3. **Pre-mortem (position rollback):** reorder drain reduces position back below high-water due to bug → consumer re-reads frames. Assert `new_pos > old_pos` on every store.
    - D4. **Pre-mortem (loss-detector false positives):** out-of-order arrival (UDP reorder) flagged as gap → NAK storm even though packet eventually arrives. `nak_delay` (W78) gives reorder buffer time to fill gap.
    - D5. **Pre-mortem (reorder buffer memory bomb):** large gap + many out-of-order → reorder grows unbounded → OOM. Bound via max_size_bytes; on overflow, drop oldest + NAK fires.
    - D6. **Pre-mortem (inactive timeout flap):** publisher idle >timeout → Image marked Inactive → publisher resumes → Image stuck Inactive. Transition Inactive→Active on first new frame.

  - **Output**: `notes/82_image_design.md` with R1–R9 + D1–D6 + the in-order fast-path diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~110 min)

  - **When `image_zero_alloc_under_5pct_loss` reports 50k allocs/sec under loss:**
    - Symptom: heaptrack shows BTreeMap-attributed allocs spike during loss events; P99.9 delivery latency includes ~500 µs allocator tail per loss burst.
    - Why: `self.reorder_buffer.buf.insert(pos, payload)` stores owned `Bytes` (Arc-counted heap buffer). Payload was zero-copy pointing into term buffer; now requires heap copy to outlive recv frame. 50k allocs/s × ~64-256 B = ~10 MB/s allocator churn.
    - Fix: store reorder entries as raw byte offsets (`BTreeMap<i64, (term_id, offset, len)>`), not copies — term buffer's 3-term retention keeps bytes alive for `3 × TERM_LEN` after publication. Drain reads bytes directly from term buffer via offset triple. Zero copies, zero allocs.
    - Cost avoided: ~150 ns/frame × 50k loss-frames/s = ~7.5 ms/sec allocator; eliminates P99.9 tail.
    - Muscle: reorder buffers stage POSITIONS, not data — data already lives in term buffer's retention window. Reapplies at: W78 NAK gap list (stage gap ranges), W83 archive recorder (writes position+offset), W84 archive replay (returns slices into mmap).

  - **When `image_loom_position_monotonic` reports rollback:**
    - Symptom: loom interleaving where position regresses below high-water; consumer re-reads frames.
    - Why: store ordering: `position.store(new, Release)` without checking `new > old`.
    - Fix: `position.compare_exchange(old, new, Release, Relaxed)` with assertion `new > old`; on rollback attempt, panic-on-debug.
    - Muscle: monotonic counters use CAS with explicit guard, not blind store. Reapplies at: W77 term buffer tail, W79 subscription position, W83 archive position.

  - **When `image_reorder_bounded_drops_oldest` reports OOM under prolonged blackout:**
    - Symptom: reorder_buffer grows unbounded; ~50 MB after 5s blackout at 10M msg/s.
    - Why: no overflow policy.
    - Fix: bound via `max_size_bytes`; on overflow, drop oldest (with NAK firing to recover). Document trade-off.
    - Muscle: any unbounded buffer is a memory bomb; explicit overflow policy required. Reapplies at: W82 same pattern, W83 archive recorder lag, W87 VOPR scenario log.

  - **5-year failure mode** (write in `notes/82_image_followup.md`): when kernel-bypass AF_XDP becomes commodity for Aeron, Image's poll loop integrates with AF_XDP's UMEM ring directly. Migration: Image's `on_frame` consumes from UMEM slot; offset-triple semantic preserved.
  - 🎯 **Hardened acceptance for Image v0.7**:
    - **Throughput**: ≥10M msg/sec in-order delivery sustained 60s LAN at 128 B payload.
    - **Latency distribution under 0% loss**: in-order delivery p50 ≤100 ns, p99 ≤500 ns, p99.9 ≤2 µs.
    - **Latency distribution under 5% loss**: in-order delivery p50 ≤200 ns, p99 ≤50 µs (NAK+retransmit),
      p99.9 ≤200 µs, p99.99 ≤500 µs.
    - **Zero allocation under 5% loss (dhat)**: reorder staging uses offset-triple, not `Bytes`. ZERO
      heap allocations on the reorder hot path.
    - **Loom-green**: position monotonicity (no rollback), reorder drain correctness (frames delivered in
      order even with adversarial out-of-order arrival).
    - **NAK suppression correctness**: under repeated loss + retransmit, NO duplicate NAK in <nak_delay
      window — verified via counter assertion in test.
    - **Reorder buffer bounded**: under prolonged 1s blackout at 10M msg/sec, reorder buffer caps at
      max_size_bytes; older entries dropped + NAK fires; never OOM.
    - **End-to-end reliability under 5% loss**: 100% application-level delivery for 1M messages with 5%
      uniform packet loss + 1% reorder + 0.1% duplicate.
    - **Graceful degradation**: under sustained 50% loss (network failure scenario), Image marks Inactive
      and surfaces typed error; never deadlock, never silently drop.
    - **5-year failure mode**: state one shift (kernel-bypass via AF_XDP/DPDK, RDMA, encrypted msgs)
