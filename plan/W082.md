  - **Read first**: Aeron `Image.java` (full file). `LossDetector.java` (integrated into Image). `ImagePoller.java`. `Subscription.java::poll`.
  - **Design**:
    ```rust
    pub struct Image {
        pub correlation_id: i64,
        pub session_id: i32,
        pub stream_id: i32,
        pub source_identity: SocketAddrV4,       // for SSM + diagnostics
        pub initial_term_id: i32,
        pub log_buffer: Arc<LogBuffer>,            // per this image
        pub position: AtomicI64,                   // subscriber's read cursor
        pub loss_detector: LossDetector,           // from W78
        pub reorder_buffer: ReorderBuffer,         // out-of-order frames staged
        pub status: ImageStatus,
        pub eos_position: AtomicI64,               // end-of-stream marker if set
    }
    pub enum ImageStatus { Active, Inactive { since: Monotonic }, Closed }
    pub struct ReorderBuffer {
        pub buf: BTreeMap<i64, Bytes>,             // position → payload, awaiting in-order delivery
        pub max_size_bytes: usize,
    }
    impl Image {
        pub fn on_frame(&mut self, pos: i64, payload: Bytes) {
            self.loss_detector.on_frame(pos);
            if pos == self.position.load(Acquire) {
                self.deliver(&payload);
                // Drain reorder buffer if contiguous
                while let Some((&next_pos, _)) = self.reorder_buffer.buf.iter().next() {
                    if next_pos == self.position.load(Acquire) {
                        let payload = self.reorder_buffer.buf.remove(&next_pos).unwrap();
                        self.deliver(&payload);
                    } else { break; }
                }
            } else if pos > self.position.load(Acquire) {
                self.reorder_buffer.buf.insert(pos, payload);
            }
            // else: duplicate or pre-position, drop
        }
        pub fn poll<F: FnMut(&[u8])>(&self, fragment_limit: usize, handler: F) -> usize {
            /* iterate log_buffer at self.position, dispatch fragments */
        }
        pub fn tick(&mut self, now: Monotonic, transport: &UdpTransport) {
            // Send pending NAKs from loss_detector
            for action in self.loss_detector.tick(now) {
                if let NakAction::SendNak { from, to, term_id } = action {
                    transport.send_nak(self.source_identity, from, to, term_id);
                }
            }
            // Inactivity timeout → mark Inactive
        }
    }
    ```
    **Invariants**: (i) Frames delivered to consumer strictly in position order — reorder buffer staging. (ii) Position monotonically non-decreasing. (iii) Reorder buffer bounded; overflow drops oldest position (with NAK fired to recover). (iv) One Image per (publication source, stream) — subscribers fan out images via Subscription.images vec.
  - **Back-of-envelope**: target P99 in-order delivery <100 µs LAN under 5% loss. Loss event triggers NAK after nak_delay (~60 ms initial); retransmit RTT ~50 µs LAN; reorder buffer drains the staged frames after gap fills. Steady-state in-order path: `on_frame` ~20 ns (compare to position + match + dispatch); ReorderBuffer is BYPASSED entirely (the if/else early-return). Worst-case under 5% loss: ~50 frames staged in reorder buffer (1ms × 50k pps × 5%), BTreeMap insert/lookup ~50 ns each = ~2.5 µs reorder overhead per loss event — negligible. Reorder buffer max_size_bytes default 4 MiB = ~60k frames at 64 B; overflow only on prolonged blackout (>1s at 50k pps). The CRITICAL constraint: in-order frames MUST bypass the BTreeMap (which is cold-cached and ~300 ns lookup) — that's the W78 NAK gap-list fast-path principle re-applied at the Image layer.
  - **Build steps**: 1. (~25 min) Image type + status states. 2. (~30 min) ReorderBuffer with bounded size + insert/drain. 3. (~35 min) `on_frame` with in-order vs out-of-order branching + reorder drain. 4. (~25 min) `poll` for consumer fragment delivery from log_buffer + reorder. 5. (~25 min) `tick` for NAK driver + inactivity timeout. 6. (~10 min) Smoke test.
  - **Pitfalls** (named, 4):
    - *Position rollback*: **Symptom**: reorder buffer drain reduces position back below high-water mark due to programming bug → consumer re-reads frames. **Fix**: position can only `store` if `new > old`; assertion. Loom test.
    - *Loss-detector false positives*: **Symptom**: out-of-order arrival (UDP reorder) flagged as gap → NAK storm even though packet eventually arrives. **Fix**: `nak_delay` (W78) gives the reorder buffer time to fill the gap before NAKing. Tune nak_delay vs typical network reorder distribution.
    - *Reorder buffer memory bomb*: **Symptom**: large gap + many out-of-order frames → reorder_buffer grows unbounded → OOM. **Fix**: bound via `max_size_bytes`; on overflow, drop oldest (with NAK firing to recover); document trade-off.
    - *Inactive timeout flap*: **Symptom**: publisher idle for >inactivity_timeout → Image marked Inactive → publisher resumes → Image stuck Inactive. **Fix**: transition Inactive → Active on first new frame; metric for flap detection.
  - **Expect to hit (perf) #1 — `BTreeMap<i64, Bytes>` allocates a `Bytes` per out-of-order frame (bar (c) violation)**: when a frame arrives out-of-order, `self.reorder_buffer.buf.insert(pos, payload)` stores an owned `Bytes` (Arc-counted heap buffer) — the payload was originally pointing into the term buffer (zero-copy) but now requires a heap copy to outlive the recv frame. At 5% loss, ~50k allocs/sec on a 1M pps stream; each Bytes is ~64-256 B; ~10 MB/s of allocator churn. Worse: on drain, the Bytes is dropped (Arc decrement + dealloc ~50 ns) — the whole staging round-trip is ~150 ns/frame of allocator work. Symptom: heaptrack shows BTreeMap-attributed allocs spike during loss events; P99.9 delivery latency includes ~500 µs of allocator tail per loss burst. Fix: store reorder entries as raw byte offsets into the term buffer (`BTreeMap<i64, (term_id, offset, len)>`), not copies — the term buffer's three-term retention already keeps the bytes alive for `3 × TERM_LEN` after publication. Drain reads the bytes directly from the term buffer via the offset triple. Zero copies, zero allocs. Cost avoided: ~150 ns/frame × 50k loss-frames/s = ~7.5 ms/sec of allocator overhead; eliminates allocator-attributed P99.9 tail. Muscle: reorder buffers stage POSITIONS, not data — the data already lives in the term buffer's retention window. Reapplies at: W78 NAK gap list (stage gap ranges, not data), W83 archive recorder (writes position+offset, not full frame), W84 archive replay (returns slices into the mmap, not copies).
  - **Test scenarios**: (a) In-order delivery: all frames arrive in order → reorder buffer empty → direct deliver. (b) 5% reorder: frames arrive shuffled within window → reorder buffer assembles, delivers in order. (c) Loss + recovery: 1% loss → NAK fires after delay → publisher retransmits → reorder buffer drains. (d) Sustained 5% loss: throughput degrades gracefully; no application-level loss. (e) Reorder overflow: induce gap larger than buffer → oldest dropped + NAK recovers.
  - **Acceptance**: 5% UDP loss → 100% application delivery via NAK + reorder. Bench: P99 in-order delivery latency < 100 µs (LAN). Inheritance: loss_detector, term_buffer, transport_udp, bufpool.
