Downstream consumers that hang or corrupt if this is wrong: matching-engine shard routing (W58, W74), consensus-vsr cross-replica IPC (W68), messaging-aeron publication pinning (W77).   #### Phase 1 — Problem, prediction, design (~30 min, no code yet)

  - 🎯 **Pre-prediction prompt (BEFORE reading Phase 2)** — seal answers in `crates/runtime-thread-per-core/notes/44_submitto_prediction.md`:
    - P1. The channel primitive you'd reach for to deliver the result back to the caller (exact import line you'd type from memory — `tokio::sync::oneshot`? a hand-rolled atomic cell? `crossbeam::channel::bounded(1)`?).
    - P2. Predict cross-shard rtt p50 and p99 in ns for a 1-shard-to-1-shard ping (the wake path is: push to SegQueue + write eventfd + dest epoll wakeup + drain + run closure + send result + caller epoll wakeup). One number each.
    - P3. Predict the outcome of `submit_to(current_shard(), f).await` in your FIRST design — resolves, hangs, or panics? One word.
    - P4. Predict the heap allocation count per `submit_to` call in your first design. One number. (Hint: count the `Box`, the oneshot state box, the envelope.)
    - P5. List every Phase-2 test name you predict your first attempt will fail. May be empty; the delta is the lesson.

  - *Mental model*: a thread-per-core runtime pins one reactor per core and never shares mutable state across cores. `submit_to` is the only sanctioned way to run code on *another* core's reactor and get the result back — it ships a `Send` closure to the dest shard's inbox, the dest runs it on its own reactor, and the result returns over a oneshot the caller awaits on *its* reactor. No locks, no shared mutation: the closure runs single-writer on the dest core.

  - *Contract*:
    - `fn submit_to<F, R>(shard: ShardId, f: F) -> SubmitFut<R>` where `F: FnOnce() -> R + Send + 'static`, `R: Send + 'static`.
    - `SubmitFut<R>: Future<Output = Result<R, Shutdown>>` — polls the *caller's* reactor; wakes when the dest shard sends the result.
    - `fn current_shard() -> ShardId` — the shard the calling code is pinned to.
    - Capturing `!Send` data (e.g. `Rc<T>`) in `f` is a COMPILE error, not a runtime check.

  - *Back-of-envelope* (bar (c)): budget is p99 < 2µs cross-shard. The wake path costs: SegQueue push ~15ns, eventfd `write` syscall ~300ns, dest epoll wakeup + scheduler ~200ns, drain + closure ~50ns, result oneshot + caller epoll wakeup ~500ns ⇒ ~1.1µs p50, with syscalls dominating. **Cliff**: the local self-submit fast path (R3) skips both eventfd syscalls and both epoll wakeups — `spawn_local` is ~50ns vs ~1.1µs cross-shard = **~22× cliff**. A per-call `Box<dyn FnOnce>` adds ~50ns malloc + a cache-miss-prone heap deref on every RPC; at 5M RPC/s that's 250µs/s of pure allocator = a bar (c) violation the typed fast-path eliminates.

  - **Requirements** — write in `crates/runtime-thread-per-core/notes/44_submitto_design.md`:
    - R1. `F: FnOnce() -> R + Send + 'static`; `R: Send + 'static`.
    - R2. `SubmitFut<R>` polls the caller's local reactor; the wake fires from the remote shard via the result oneshot's `tx`.
    - R3. **Reentrant self-submit**: if `dest == current_shard()`, schedule `f` as a *local task* (no inbox round-trip, no eventfd).
    - R4. **Shutdown safety**: a dest-shard drain on shutdown resolves every pending `SubmitFut` to `Err(Shutdown)` — never silently dropped.
    - R5. Capturing `!Send` data is a compile error (type system enforces; no runtime check).
    - R6. Cross-shard rtt p99 < 2µs; clean shutdown; **zero heap alloc per call on the typed/common path** (the `Box<dyn FnOnce>` erased path is the v0.3 fallback, flagged for v0.5 typing).

  #### Phase 3 — Make the tests pass, one failure at a time (~40 min)

  Read each card *after* you've seen the failure. Ordered **newbie → expert**.

  - **(NEWBIE) When `submit_to_self_shard_resolves_not_deadlocks` times out:**
    - Symptom: the test hits the 1s harness timeout; `submit_to(current_shard(), f).await` never returns.
    - Why: the "uniform always-cross-shard" impl pushes the envelope to the *current* shard's own inbox. But the calling code is mid-event-loop-iteration; the inbox is only drained at the top of the *next* iteration, which never starts because the current `.await` suspended this iteration forever.
    - Fix: short-circuit when source == dest:
      ```rust
      if dest == current_shard() {
          let (tx, rx) = oneshot::channel();
          spawn_local(async move { let _ = tx.send(Ok(f())); });   // runs next loop turn
          return SubmitFut::from(rx);
      }
      ```
    - Cost avoided: ~22× the cross-shard path *and* an outright deadlock — but the real cost is a hang in production whenever a shard happens to route a message to itself (W58 matching-engine routes a self-symbol order through `shard_of(symbol)` which can be the current shard).
    - Muscle: any cross-thread RPC MUST short-circuit when source == destination; the "always cross-thread" path deadlocks the synchronous self-call. Reapplies at: W58 matching-engine shard routing, W67 consensus-raft self-replication, W77 messaging-aeron loopback publication.

  - **(SENIOR) When `submit_to_shutdown_mid_flight_returns_err_not_hang` hangs forever:**
    - Symptom: the 100 pending futures never resolve; `block_on` on each times out.
    - Why: shutdown race — the dest shard sets its exit flag and the thread returns while 100 envelopes still sit in its inbox. Their `tx` halves are dropped with no value sent, so every caller's `rx` waits on a wake that never comes.
    - Fix: shutdown protocol = (1) set shutting-down flag (rejects new envelopes); (2) drain the inbox; (3) for each pending envelope `tx.send(Err(Shutdown))`; (4) only then drop the executor.
    - Cost avoided: a permanently wedged matching-engine on graceful restart — every in-flight cross-shard order would block its caller's reactor.
    - Muscle: any RPC primitive must signal ALL pending callers on shutdown; never silently drop the result channel. Reapplies at: W58 matching-engine subscription shutdown, W42 txn manager shutdown, W68 consensus-vsr replica fencing.

  - **(EXPERT) When `submit_to_shutdown_no_uaf` reports a Miri use-after-free:**
    - Symptom: `cargo +nightly miri test` flags a read of freed memory inside the caller's final `rx` poll.
    - Why: lifecycle ordering — shutdown dropped the executor (and with it the oneshot `tx`'s shared state) *before* the caller polled `rx`. The "let oneshots' Drop wake the caller" shortcut sequences the free wrong.
    - Fix: in the shutdown protocol, step (3) `tx.send(Err(Shutdown))` *transfers ownership of the result into the rx-side state*; the caller then polls `rx` reading its own state, never the freed `tx` state. Drain + signal BEFORE drop, never the reverse.
    - Cost avoided: a UAF that is invisible in `cargo test` (passes), only caught by Miri/ASan; in production it's a sporadic segfault under shutdown — the worst kind of bug to triage. (bar (c) violation: a substrate primitive that can UAF disqualifies the crate from its bar.)
    - Muscle: shutdown ordering for resource lifecycles — drain + signal, THEN drop; the signal must move the result into the consumer's state, not leave it in the producer's. Reapplies at: W43 scheduler shutdown, W58 matching-engine graceful shutdown, W83 ledger snapshot drain.

  - **(EXPERT) Expect to hit (perf) #1 — `submit_to_zero_alloc_on_typed_path` reports 2+ allocs (bar (c) violation):**
    - Symptom: `AllocCounter` reports 2–3 allocations per typed RPC; the `<=1` assertion fails.
    - Why: the erased path boxes the closure (`Box<dyn FnOnce() + Send>`) AND boxes an envelope wrapper — two heap allocs on every call. The typed path can carry the message by value in a fixed enum variant and reuse a slab-backed oneshot.
    - Fix: add `submit_to_typed<M: CrossShardMsg, R>(shard, msg)`: the dest dispatches `M` through a static `match` (no `dyn`), the message rides inline in the inbox slot, and the oneshot state comes from a per-shard `Slab` (amortized zero-alloc). Keep `submit_to` (erased) for arbitrary closures; route all known message kinds through `submit_to_typed`.
    - Cost avoided: ~50ns malloc + a near-certain cache miss on the boxed closure deref, per call. At 5M RPC/s = ~250µs/s of pure allocator + ~5M extra cache misses/s. (bar (c) violation.)
    - Muscle: on a hot RPC path, erase types with `dyn`/`Box` only for the rare arbitrary case; give the common message kinds a typed, by-value, slab-backed path. Reapplies at: W58 matching-engine order-message dispatch, W68 consensus-vsr message enum, W77 messaging-aeron fixed-frame headers.

  - **(SENIOR) When `submit_to_cross_shard_rtt_p99_under_2us` reports p99 ≈ 4–8µs:**
    - Symptom: p99 lands above the 2µs ceiling (often 4–8µs) while still inside the plausible band's upper edge or just over it.
    - Why: per-call eventfd write + a fresh epoll registration, OR batching disabled — each RPC pays two syscalls and a full reactor wakeup with no amortization.
    - Fix: keep the eventfd persistently registered (level/edge-triggered, registered once at shard start, not per-call); coalesce: one eventfd write wakes a drain of the *whole* SegQueue, so N queued RPCs amortize to one wakeup.
    - Cost avoided: ~300ns syscall + ~200ns wakeup per RPC un-amortized; coalescing turns N RPCs' 2N syscalls into ~2.

  #### Phase 3 (continued) — cross_shard failure cards

  - **(EXPERT) When `cross_shard_no_lost_wake_loom` reports a message pushed but never consumed:**
    - Symptom: loom finds a schedule where `consumed == false` after both threads joined.
    - Why: lost wake — the producer's eventfd write was sequenced *before* the SegQueue push, so the consumer drained (saw empty), then the producer pushed, and no further wake ever came.
    - Fix: eventfd write happens AFTER the SegQueue push with Release ordering; the consumer's eventfd read happens BEFORE the drain with Acquire ordering — so any push the producer made before signalling is visible to the consumer's drain.
    - Cost avoided: a permanently stuck message = a hung future = a wedged cross-shard RPC; invisible until contention reorders the two ops. (bar (c) violation.)
    - Muscle: enqueue THEN signal (Release); read-signal THEN drain (Acquire) — a wake must be published after the data it announces. Reapplies at: W11 MPMC publish-then-bump-cursor, W26 WAL append-then-bump-commit, W58 matching-engine order-then-notify.

  - **(SENIOR) When `cross_shard_4shard_star_all_complete` reports `done < 3_000_000`:**
    - Symptom: the count is short by a small, run-varying number; each primitive's own tests pass.
