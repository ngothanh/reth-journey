- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/submit_to.rs` — `submit_to<F: FnOnce() -> R + Send>(shard: ShardId, f: F) -> Future<R>`. (~total 135 min across 3 phases)
  - 🔧 **Why this matters**: submit_to is the canonical cross-shard RPC. Reentrant deadlock is the classic
    bug (submit_to(self_shard) hangs). Shutdown race → orphan pending futures. W58+ matching-engine
    shard-per-symbol depends on this being right.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: invoke a Send closure on a specific shard; await the Send
    result on the caller's shard. The Future returned drives the caller's reactor; the wake fires
    when the destination shard completes the oneshot.

  - **Requirements** — write in `crates/runtime-thread-per-core/notes/44_submitto_design.md`:
    - R1. F: FnOnce() -> R + Send + 'static; R: Send + 'static.
    - R2. Future polls caller's local reactor; wake from remote shard via oneshot's tx.
    - R3. **Reentrant self-submit**: if dest == self, schedule as local task (no inbox round-trip).
    - R4. **Shutdown safety**: dest shard drain on shutdown; pending futures resolve to
      Err(Shutdown).
    - R5. Capturing !Send data is a compile error.
    - R6. rtt p99 < 2 µs; clean shutdown.

  - **Design walk-through** — answer each:
    - D1. The oneshot pattern: write `(tx, rx)`; how does rx integrate with the caller's local
      reactor?
    - D2. The cross-shard envelope: write the Send closure wrapper that captures `f` and `tx`.
    - D3. Reentrant detection: `if dest_shard == current_shard()`. Write the alternate path that
      schedules as local task. Why does the direct submit deadlock?
    - D4. Shutdown drain: write the protocol. Who pushes Err into pending oneshots?
    - D5. JoinHandle: how is it different from spawn_local's JoinHandle?
    - D6. **Pre-mortem (load-bearing)**: write the reentrant-deadlock trace — submit_to(self_shard,
      f) pushes to own inbox; current call is in an event-loop iteration that hasn't returned;
      drain doesn't fire; future blocks forever. Then write the shutdown-race trace where pending
      futures get no result.
  - **Output**: `notes/44_submitto_design.md` with R1–R6, D1–D6.

  #### Phase 3 — Make the tests pass, one failure at a time (~75 min)

  - **When `submit_to_self_shard_no_deadlock` hangs:**
    - Symptom: `submit_to(current_shard, f).await` never returns; the future blocks waiting on the
      oneshot; current event-loop iteration is the very call that submitted; drain doesn't fire.
    - Why: deadlock via reentrant submit — submit_to(self_shard, ...) blocks waiting for self to
      drain.
    - Fix: if dest == self, schedule as local task instead. `if dest_shard == current_shard() {
      spawn_local(async move { let r = f(); tx.send(r); }) } else { /* cross-shard path */ }`. The
      reentrant call now becomes a local spawn — runs on the next loop iteration.
    - Muscle: any cross-thread RPC must short-circuit when source == destination; the "always
      cross-thread" path deadlocks the synchronous self-call. Reapplies at: W58 matching-engine
      shard routing, W67 consensus-raft self-replication.

  - **When `submit_to_shutdown_mid_submit_returns_err` reports the future hanging forever:**
    - Symptom: 100 submits in flight; shutdown of dest shard; pending futures never resolve; caller
      blocked forever.
    - Why: shutdown race — dest shard exits before processing inbox. Pending oneshots are dropped
      without resolution.
    - Fix: shutdown drains inbox and resolves all pending futures with Err. Shutdown protocol: (1)
      set "shutting down" flag; (2) drain inbox; (3) for each pending envelope, `tx.send(Err(Shutdown))`;
      (4) drop the executor. Callers see Err and unblock.
    - Muscle: any RPC primitive must signal all pending callers on shutdown; never silently drop.
      Reapplies at: W58 matching-engine subscription shutdown, W42 txn manager shutdown.

  - **When `submit_to_shutdown_no_uaf` reports miri UAF:**
    - Symptom: shutdown drops the oneshot's tx before the caller's rx is polled; subsequent poll
      derefs a freed channel state.
    - Why: lifecycle ordering — shutdown drops resources in the wrong order.
    - Fix: shutdown protocol explicitly: (1) set flag; (2) drain inbox; (3) for each pending envelope,
      send Err — this transfers ownership of tx into the rx's state; (4) drop executor. rx holds the
      Err result; the caller polls it without touching freed memory.
    - Muscle: shutdown ordering for resource lifecycles — drain + signal BEFORE drop, never the
      reverse. Reapplies at: W43 scheduler shutdown, W58 matching-engine graceful shutdown.

  - **5-year failure mode** (write in `notes/44_submitto_followup.md` after green): when typed
    cross-shard channels mature (vs `Box<dyn FnOnce>`), the common-RPC path skips heap. State
    migration: introduce `submit_to_typed<M: CrossShardMsg, R>(shard, msg) -> R` for known message
    types; trigger when matching-engine has 5+ distinct cross-shard message kinds.

- [ ] [NEW v2] **Build (continued)**: `crates/runtime-thread-per-core/src/cross_shard.rs` — cross-shard channel correctness gate. SegQueue inbox per shard + eventfd wake. (~90 min)
  - **Why**: submit_to lives or dies on the cross-shard channel. Wrong here = silent corruption that won't surface until ledger VOPR at W83 catches it (or worse, runs hours and then catches it). The correctness gate today saves dozens of hours of false-positive VOPR triage later.
  - **Design**: per-shard `CrossShardInbox { queue: SegQueue<Box<dyn FnOnce()+Send>>, eventfd: RawFd }`. Caller pushes + writes 1 to eventfd; dest's reactor epoll-waits on eventfd, drains queue, runs closures.
  - **Build steps**: 1. (~15 min) `CrossShardInbox::new` with eventfd(EFD_NONBLOCK | EFD_CLOEXEC). 2. (~20 min) `push(f)` then `write(eventfd, &1u64)`. 3. (~20 min) `drain_all(&mut self)` called by reactor on eventfd ready: read eventfd to clear, drain SegQueue, run each closure. 4. (~25 min) loom test: 100 producers + 1 consumer + 1 SegQueue + eventfd — no lost messages, no double-wake livelock. 5. (~10 min) shutdown: drain on Drop, resolve pending futures to Err.
  - **Pitfalls (named, 3)**:
    - *Wake lost*: producer pushes after consumer's drain check, before consumer's epoll_wait → consumer sleeps forever holding a message. **Symptom**: hung future. **Fix**: eventfd write happens AFTER SegQueue push (memory order = Release); consumer's eventfd read happens BEFORE drain (Acquire).
    - *Eventfd counter overflow*: 64-bit counter saturates at 2^64-1 if producer floods + consumer never reads. **Symptom**: write returns EAGAIN. **Fix**: handle EAGAIN by retrying (the queue is in the SegQueue, the eventfd is just a wake; counter saturation doesn't lose messages).
    - *!Send capture in closure*: caller captures Rc<T> in submit_to closure. **Symptom**: compile error (compiler enforces). **Fix**: type system does the work — no runtime check needed.
  - **Test scenarios**: 1M push/drain cycles loom-checked; 4-shard star topology — every shard rpcs every other shard 1M times, all complete; shutdown mid-burst returns all pending as Err(Shutdown).
  - **Acceptance**: loom passes; 1M-rpc bench p99 < 2µs; shutdown clean.
