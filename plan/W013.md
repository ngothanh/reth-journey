**Monday — concurrency drill #17 (RwLock from scratch)**

- [ ] **Build (drill #17 of 28 — bar (c))**: `crates/concurrent/src/rwlock.rs` — `RwLock<T>` from scratch via the signed-int count protocol (+N = N readers, −1 = a writer, 0 = free). (~total 360 min across 3 phases)
  - 🔧 **Why this matters**: mirrors `parking_lot::RwLock`'s fast path. This is the reader/writer separation that W42 `txn` LockManager (shared = read, exclusive = write) and every `storage-trie` reader/writer split inherit. Three traps: (1) a Relaxed read-acquire lets a reader observe the writer's mutation mid-flight (torn read = consensus-fatal if it gates state); (2) `count` and `data` sharing a cache line false-shares the lock word against the protected payload (bar (c) violation); (3) the reader-count CAS itself becomes the contention point at high reader fan-out. First-attempt impls fail ≥1 Phase-2 test below; the debug session is the lesson.
    No peek at `std::sync::RwLock`, `parking_lot::RwLock`, or `crossbeam::sync::ShardedLock` until COMPARE.

    - P2. Predict read-acquire latency at zero contention (one uncontended CAS ≈ ~10 ns). Predict `size_of::<RwLock<u64>>()` if `count` and `data` share a struct without padding.
    - P3. Predict the concurrent-first-call outcome: 2 readers + 1 writer, writer flips a shared buffer `0xAA→0xBB`. With Relaxed read-acquire, can a reader see a half-flipped buffer? Yes/no + the interleaving.
    - P4. Predict aggregate read throughput at N=8 readers + 1 writer (writer rarely wins — name the convoy). Predict the `offset_of!` of `data` if you pad `count` with `CachePadded` (from W4).

  - *Mental model*: a single `AtomicI64` encodes the whole lock state — sign distinguishes reader-mode (positive count) from writer-mode (−1). No parking; spin on contention with the W8 `Backoff` ladder.
  - *Contract*: `#[repr(C)] pub struct RwLock<T> { count: CachePadded<AtomicI64>, data: UnsafeCell<T> }` — `repr(C)` is load-bearing: it forbids the field reordering that repr(Rust) would otherwise do, so the padded `count` deterministically lands first and `data` lands ≥64/128 B after it. `fn read(&self) -> ReadGuard<'_, T>`; `fn write(&self) -> WriteGuard<'_, T>`; `unsafe impl<T: Send + Sync> Sync for RwLock<T>`. Guards `Deref` (read) / `DerefMut` (write); `Drop` releases.
  - *Back-of-envelope* (bar (c)): read-acquire = 1 CAS ≈ 10 ns uncontended; under contention each failed CAS re-fetches the contested line ≈ 7 ns L2 / ~100 ns if cross-socket. If `count` and `data[0]` share a 64 B line, every reader's CAS invalidates the writer's payload line — false sharing adds 30-70% under contention. Cliff: uncontended read 10 ns vs convoyed write potentially unbounded (∞) — that ratio IS drill #18.
  - **Requirements** R1..R6 — write in `crates/concurrent/notes/13_rwlock_design.md`:
    - R1. At most one writer: write-acquire CASs `0 → -1`.
    - R2. When a writer holds (`count == -1`), no reader may enter: read-acquire CAS only when `count >= 0`.
    - R3. Readers compose: read-acquire CASs `count → count+1` (when `count >= 0`); release `fetch_sub(1)`.
    - R4. read-acquire CAS success must be **Acquire**; write-release store must be **Release** — the writer's mutation must happen-before every subsequent reader's load.
    - R5. `count` lives on its own cache line (`CachePadded`, W4) AND the struct is `#[repr(C)]` so the padded `count` deterministically precedes `data` (repr(Rust) may reorder and undo the padding) — reader-CAS traffic never invalidates `data`.
    - R6. `Send + Sync` only when `T: Send + Sync`; guards are `!Send` across await is irrelevant (no async).
  - **Design walk-through** D1..D5 — answer in the design doc; no peeking at `parking_lot` until Phase 3:
    - D1. Property table: `AtomicBool` (writer-only flag — can't count readers), `AtomicI64` (sign trick — chosen), `Mutex<i64>` (defeats the point), separate `AtomicU32` reader-count + `AtomicBool` writer-flag (two words → two CASes → torn state). Columns: Sync? latency? allocs? blocking?

    - D3. Anti-shortcut audit: "just use `AtomicBool` + a separate `AtomicUsize` counter" — wrong HERE because writer-acquire would need to atomically check flag==false AND count==0 across two words (TOCTOU); the single signed int makes it one CAS.
    - D4. Where does the synchronization edge live? Writer's release-store is the single edge that ALL readers' acquire-loads synchronize-with. Sketch the happens-before graph.
    - D5. Spin strategy: plug in W8 `Backoff` on CAS failure — predict CPU burn at 8 contending readers if you busy-spin with no backoff.

  - [ ] **(EXPERT — loom torn-read)** `rwlock_no_torn_read_under_loom` (`#[cfg(loom)]`): 1 writer flips an 8-byte buffer `0xAAAA… → 0xBBBB…`; 2 readers each assert the observed buffer is all-AA or all-BB, never mixed. A Relaxed read-acquire fails this — under loom a missing acquire/release edge surfaces as a **data-race abort** ("Concurrent load/store access" panic from loom), not a mixed value, because loom catches the race before it produces a torn observation.
    ```rust
    #[cfg(loom)]
    #[test]
    fn rwlock_no_torn_read_under_loom() {
        loom::model(|| {
            let lk = std::sync::Arc::new(RwLock::new([0xAAu8; 8]));
            let w = lk.clone();
            let h = loom::thread::spawn(move || { *w.write() = [0xBB; 8]; });
            let g = lk.read();
            let v = *g;
            assert!(v == [0xAA;8] || v == [0xBB;8], "torn read: {:?}", v);
            h.join().unwrap();
        });
    }
    ```
  - [ ] **(SENIOR — mutual exclusion)** `rwlock_writer_excludes_readers` (loom): while a writer holds, `count == -1` and no reader CAS succeeds; after release, a reader sees the new value. A `fetch_add` read-acquire (blind increment) lets a reader in during the write and fails this.
    ```rust
    #[cfg(loom)]
    #[test]
    fn rwlock_writer_excludes_readers() {
        loom::model(|| {
            let lk = std::sync::Arc::new(RwLock::new(0u64));
            let w = lk.clone();
            let h = loom::thread::spawn(move || {
                let mut g = w.write();
                // while we hold the write guard, raw count must read exactly -1
                assert_eq!(w.raw_count(), -1, "reader slipped in during write");
                *g = 42;
            });
            h.join().unwrap();
            assert_eq!(*lk.read(), 42, "reader did not observe post-release value");
        });
    }
    ```

  #### Phase 3 — Make the tests pass, one failure at a time (~150 min)
  - **(EXPERT) When `rwlock_no_torn_read_under_loom` reports a loom data-race abort (`Concurrent load/store access` at `data`):**
    - Symptom: loom panics with a concurrent-access / data-race report on the `data` cell on some interleaving (it does NOT surface a mixed `[AA,AA,BB,BB]` value — loom intercepts the race before the read materializes).
    - Why: read-acquire CAS used `Relaxed` success ordering, so the reader's load of `data` is not ordered after the writer's release-store — no happens-before edge, which loom flags as a race.
    - Fix: read-acquire CAS success = `Acquire`; write-release store = `Release` (R4). The writer's Release is the single edge all readers' Acquire synchronize-with.
    - Cost avoided: a torn read of a consensus-gating field = silent state divergence (bar (c) violation); no ns figure — correctness, not speed.
    - Muscle: a reader's acquire must pair with the writer's release; the writer establishes ONE synchronization edge for ALL readers. Reapplies at: W42 LockManager shared/exclusive acquire, W67 raft log-entry visibility, W74 matching-engine order-book reader.
  - **(SENIOR) When `rwlock_count_on_own_cache_line` reports `data at offset 8`:**
    - Symptom: `offset_of!(RwLock<u64>, data) == 8`, below the cache line.
    - Why: `count: AtomicI64` packs immediately before `data`; reader-CAS traffic on `count` invalidates the writer's payload line.
    - Fix: `#[repr(C)]` on `RwLock` + `count: CachePadded<AtomicI64>` (W4 primitive) so `data` deterministically lands ≥64/128 B after `count`.
    - Cost avoided: 30-70% read-throughput regression under contention; green `cargo test`, RED bench (bar (c) violation).
    - Muscle: the lock word and the protected payload must not share a line — pad the lock word. Reapplies at: W42 LockManager hot lock word, W58 matching-engine best-bid/ask, W65 Disruptor cursor.
  - **(SENIOR) When `rwlock_count_on_own_cache_line` STILL reports `data at offset 0` after adding `CachePadded`:**
    - Symptom: `offset_of!(RwLock<u64>, data) == 0` even though `count` is `CachePadded<AtomicI64>` (align 64/128) — the padded word landed AFTER `data`.
    - Why: the struct is still repr(Rust); Rust is free to reorder fields and placed the smaller `data` at offset 0 and the 64 B-aligned `count` after it, so `data` no longer sits behind the padding. Padding is load-bearing here but the layout isn't locked.
    - Fix: add `#[repr(C)]` to `RwLock` — repr(C) keeps declared field order, so the padded `count` stays first and `data` lands ≥64/128 B later.
    - Cost avoided: the same 30-70% false-sharing regression sneaks back in despite "correct" padding; green `cargo test`, RED bench (bar (c) violation).
    - Muscle: when padding is load-bearing, lock the layout — repr(C) is non-negotiable, padding alone does not pin offsets. Reapplies at: W004 CachePadded repr(C) lesson, W58 matching-engine order book, W65 Disruptor sequencer/cursor.
  - **(SENIOR) When `rwlock_writer_excludes_readers` lets a reader in during a write:**
    - Symptom: a reader's `count → count+1` CAS succeeds while `count == -1` (it CASs against a stale 0).
    - Why: read-acquire didn't guard on `count >= 0` before CAS, or used `fetch_add` (unconditional) instead of CAS.
    - Fix: read-acquire = loop `let c = count.load(Acquire); if c >= 0 && CAS(c, c+1, Acquire, Relaxed).is_ok() { break }` (R2/R3).
    - Cost avoided: writer/reader overlap = the torn-read class again; correctness.
    - Muscle: a reader must CAS conditionally on non-negative count, never blind-add. Reapplies at: W42 LockManager upgrade path.
  - **(NEWBIE) When `loom_actually_explores` finishes in <10 ms:**
    - Symptom: the negative control fails — loom returned instantly.
    - Why: the `loom` cfg/feature isn't enabled, so `loom::model` ran the closure once with std atomics.
    - Fix: `RUSTFLAGS="--cfg loom" cargo test --test rwlock_loom`; gate `use loom::sync::atomic` behind `cfg(loom)`.
    - Cost avoided: false confidence — a "passing" loom suite that explored nothing.
    - Muscle: always assert your verifier actually ran. Reapplies at: every `#[cfg(loom)]` suite W26 SegQueue, W42 txn.
  - **(SENIOR — perf) When `rwlock_read_throughput_band` lands at 2e6 reads/s (below band):**
    - Symptom: throughput an order of magnitude under the floor.
    - Why: busy-spin CAS with no backoff — contending readers thrash the line and burn CPU on retries.
    - Fix: insert W8 `Backoff::spin()` on CAS failure.
    - Cost avoided: ~10× read throughput + idle CPU burn (bar (c) violation).
    - Muscle: every spin loop needs an adaptive backoff. Reapplies at: W7 SpinMutex (drill #6) CAS-spin backoff, W42 LockManager waiter spin.

        let writes = Arc::new(AtomicU64::new(0));

        stop.store(true, Relaxed);
        w.join().unwrap(); for r in readers { r.join().unwrap(); }
        writes.load(Relaxed)
