Explicitly mapping their components to yours is how you convert "new codebase, zero context" into "known patterns, new names," which is the entire reason the inheritance-principle curriculum exists.
  - *Hardened acceptance, build proof*: you can state the exact command that builds + tests the repo (verified by reading their docs/CI, not run yet if write access is pending).

**Friday — Onboarding day 4: first small PR**

This is the same discipline as a negative-control test: prove the pipeline works on a trivial input before trusting it on a real one.
