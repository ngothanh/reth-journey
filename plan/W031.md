  - 🔧 **Why this matters**: the MPT separates two access patterns — content-addressed lookup (by 32-byte

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: backing the in-memory `eth_trie::TrieStorage` (W20) with MDBX
    requires careful handling of cursor lifetimes (don't escape the txn), path encoding (HP, no
    ambiguity), and write batching (dirty map + commit-time flush).

  - **Requirements** — write in `crates/storage-trie/notes/31_mdbx_trie_storage_design.md`:
    - R1. `MdbxTrieStorage<'tx>` holds `tx: &'tx mdbx::Transaction`, `nodes_by_hash` and `nodes_by_path`
      tables, `dirty: HashMap<Nibbles, Option<Node>>` (None = tombstone).
    - R2. `nodes_by_hash[keccak(node.rlp())] == nodes_by_path[path].rlp()` for every entry.
    - R3. Reads consult `dirty` BEFORE `nodes_by_path` (overlay semantics).
    - R4. Tombstones in `dirty` survive until commit; subsequent reads return None.
    - R5. Cursor returns OWNED `Vec<u8>` / `Bytes`, never borrows out of the storage layer (tx lifetime
      escape = UAF).
    - R6. HP path encoding (length-prefix + packed nibbles); no `[1,2]` vs `[1,2,0]` collisions.
    - R7. 10k round-trip latency <50ms p99 on dev SSD.

  - **Design walk-through**:
    - D1. Why two tables, not one? (Hint: content vs path access patterns.)
    - D2. Tombstones: why `Option<Node>` not separate `dirty + tombstoned` sets?
    - D3. Cursor escape: write the scenario where returning `&[u8]` from cursor causes UAF.
    - D4. Pre-mortem: missing HP encoding; how do `[1,2]` and `[1,2,0]` collide?

  - **Output**: `notes/31_mdbx_trie_storage_design.md` with R1–R7 + D1–D4 + table layouts.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)

  - **When `cursor_returns_owned_no_uaf` segfaults on tx drop:**
    - Symptom: process crashes after the tx is dropped; valgrind shows use-after-free on the bytes
      a cursor returned earlier.
    - Why: cursor's return type was `&'tx [u8]` borrowing into the mmap; the borrow outlives the tx.
    - Fix: return `Bytes` (Arc-backed) via `Bytes::copy_from_slice`. The copy is acceptable on a
      cold path; hot path retains the trade-off via a per-query lifetime annotation that
      forces drop before tx commit.
    - Muscle: MDBX cursor returns are tied to the tx lifetime; storage-layer APIs return OWNED
      bytes, never borrows. Reapplies at: W42 txn cursor results, W92 block-stm parallel reads.

  - **When `hp_encoding_no_collision` reports the two paths produce the same DB key:**
    - Symptom: `[1,2]` and `[1,2,0]` both encode to `0x12`; only one entry exists in the DB.
    - Why: encoder packs nibbles without a length prefix; the trailing zero nibble is indistinguishable
      from "no further nibbles".
    - Fix: HP encoding from yellow paper §C — first byte = flag (extension/leaf + odd-length) | first
      nibble if odd. Length is implicit in the byte count + odd flag. The two paths encode differently
      because `[1,2]` is even and `[1,2,0]` is odd (3 nibbles).
    - Muscle: variable-length nibble keys MUST use length-aware encoding; bare nibble packing
      collides. Reapplies at: W21 RLP trie encoders (already), W31 wire schema, W32 proof
      verification.

  - **When `hash_path_table_consistency` reports a mismatch on 8% of entries:**
    - Symptom: `nodes_by_hash[h]` and `nodes_by_path[p]` disagree on the node bytes for 8% of paths.
    - Why: commit() flushed `dirty` to `nodes_by_path` but forgot to update `nodes_by_hash` for
      modified-not-just-inserted nodes (the old hash still pointed to the old bytes).
    - Fix: commit() walks dirty entries: for each, delete the old hash entry (if it exists), then
      write the new path entry AND new hash entry atomically (one MDBX write tx).
    - Muscle: a derived index must be updated WHENEVER the source changes; partial updates leak old
      state. Reapplies at: W42 txn 2PC, W67 raft log compaction.

  - **5-year failure mode** (write in `notes/31_mdbx_trie_storage_followup.md` after green): when
    Verkle replaces MPT, the two-table model becomes obsolete (Verkle has one node type). State the
    migration: a `TrieBackend` trait. Trigger: Verkle activation.

**Tuesday — Wire `eth-trie::Node` to the table layout**

- [ ] **Build**: cursor-based read path + dirty-set write path against MDBX. (~total 60 min across 3 phases)
  - 🔧 **Why this matters**: MDBX cursors are zero-copy views into the memory-mapped B+tree.
    Repositioning is O(log N) the first time; subsequent `next()/prev()` is amortized O(1). The trie
    walker relies on this for hot range scans. Allocating per-node would dominate CPU; cursor reuse is
    the perf primitive. Downstream: W32 proof generation, W36 snapshot export.

  #### Phase 1 — Problem, requirements, design (~15 min, no code yet)

  - **The problem this primitive solves**: MDBX's cursor API is the lowest-cost way to walk a sorted
    range; the wrapper must preserve the zero-copy property while making the API safe.

  - **Requirements**:
    - R1. `TrieCursor<'tx>` wraps `mdbx::Cursor<'tx>` + `last_path: Option<Nibbles>` (monotonic invariant).
    - R2. `seek(p)` positions cursor; returns next-larger key if `p` not present (range semantics).
    - R3. `next_node()` advances cursor; returns `(Nibbles, Vec<u8>)` owned (no borrow escape).
    - R4. Writes stage in dirty map; commit drains in SORTED key order (MDBX perf invariant).
    - R5. Cursor mid-scan + write invalidates the cursor (MDBX rule); stage writes for post-scan flush.
    - R6. Mixed read+dirty: cursor sees the dirty entry via overlay logic.
    - R7. 100k seeks <500ms cold, <100ms warm.

  - **Design walk-through**:
    - D1. Cursor invalidation on write — what's the MDBX rule, why?
    - D2. Sorted batch writes — why does MDBX perform poorly on unsorted batches?
    - D3. Pre-mortem: scanning while writing; silent skipped keys.

  - **Output**: `notes/31_trie_cursor_design.md` with R1–R7 + D1–D3.

  #### Phase 3 — Make the tests pass, one failure at a time (~35 min)

  - **When `batch_commit_sorted_under_100ms` reports 600ms:**
    - Symptom: the sorted-batch test is 6× slower than expected.
    - Why: dirty map was a `HashMap`; commit's iteration order was random; MDBX thrashes the B+tree.
    - Fix: use `BTreeMap<Nibbles, Option<Node>>` for the dirty map — iteration is naturally sorted;
      MDBX writes hit consecutive pages.
    - Cost avoided: 5-10× write slowdown on large batches.
    - Muscle: any sorted-tree write workload benefits from pre-sorted batches; HashMap iteration order
      is the anti-pattern. Reapplies at: W42 txn batch commit, W67 raft AppendEntries batch.

  - **When `mixed_read_dirty_overlay` doesn't see the dirty entry:**
    - Symptom: cursor seek to `[2]`, next_node yields `[5]` instead of the staged `[3, ...]`.
    - Why: cursor walked MDBX only; overlay logic missing.
    - Fix: cursor wraps two iterators (MDBX cursor + sorted dirty iterator); merge them in lex order,
      preferring dirty on duplicate paths. Tombstones (None) suppress the underlying entry.
    - Muscle: stage-and-commit storage requires merge-iteration on reads; pure MDBX iteration misses
      staged writes. Reapplies at: W42 txn cursors, W92 block-stm pre-commit reads.

  - **When `cursor_next_yields_sorted` reports unsorted output:**
    - Symptom: cursor yields keys in insertion order, not sorted.
    - Why: the underlying MDBX table wasn't configured with the correct comparator (default is
      byte-lex over raw key bytes; HP-encoded nibbles need a specific comparator).
    - Fix: register the table with `MDBX_CREATE | MDBX_INTEGERKEY` (if keys fit) OR with a custom
      `MDBX_CMP_FUNC` matching nibble lex order. HP encoding's byte order corresponds to nibble
      order, so default may work — verify with a test that inserts in both orders.
    - Muscle: table comparator is part of the schema; mismatch silently corrupts ordering. Reapplies
      at: W42 txn schema, W67 raft log term-index.

  - **5-year failure mode**: when MDBX adds vectorized cursor advances (batch `next`), per-call
    overhead drops 10×; the wrapper should expose `next_batch(n)`.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: random-access cursors over append-only logs require a sparse
    index — full-scan is O(N); naive per-frame indexing is O(N) storage. Sparse (every 1024th frame
    indexed) gives O(log idx + sparsity) lookup with 8 bytes of index per 1024 frames.

  - **Requirements** — write in `crates/mmap-queue/notes/31_excerpt_design.md`:
    - R1. `ExcerptCursor<'a>` holds `&MmapQueue`, `cycle: u32`, `byte_offset: u64`, `index: u64`.
    - R2. `next_excerpt() -> Option<Excerpt<'_>>` — Acquire-load `len_and_meta`, bounds check, slice
      borrow, bump offset. ~10 ns warm.
    - R3. `move_to_index(idx)` — consult sparse index for nearest ≤ idx, linear-scan residual (≤1024
      frames). ~5-10 µs.
    - R4. `byte_offset` always at a frame boundary; `index` monotonic on next_excerpt.
    - R5. Cursor returns `Excerpt<'a> { payload: &'a [u8] }` — BORROWED, never owned bytes.
    - R6. Cross-cycle: cycle exhausted → advance `cycle += 1`, reset offset.
    - R7. Forward read ≥5M excerpts/sec on warm mmap.
    - R8. move_to_index ≤10 µs for idx within current cycle.

  - **Design walk-through**:
    - D1. Why is the sparse index sized at sparsity=1024? (Hint: ≤1024 frames residual scan; index
      fits in L2.)
    - D2. Torn-length read: writer publishes len mid-publish; reader sees garbage. Synchronization?
    - D3. Owned-bytes return type — what does it cost?
    - D4. Pre-mortem: move_to_index naive (scan from 0) — what's the latency cliff?

  #### Phase 1 — Problem, requirements, design (~20 min, no code yet)

  - **The problem this primitive solves**: a queue's wire format must be (a) bit-stable across
    architectures (LE), (b) atomic-publish (reader never sees torn frame), (c) zero-copy on decode (no
    per-frame allocation).

  - **Requirements** — write in `crates/mmap-queue/notes/31_wire_design.md`:
    - R1. `WireHeader` is `#[repr(C)]` with `len_and_meta: u32` + `type_id: u32` (8 bytes total).
    - R2. `len_and_meta`: bit 31 = meta-frame flag, bits 0-30 = payload length.
    - R3. Writer order: payload memcpy FIRST, then Release-store on `len_and_meta` LAST.
    - R4. Reader: Acquire-load `len_and_meta`; only proceed if `len != 0`.
    - R5. All multi-byte ints little-endian via `to_le_bytes`/`from_le_bytes`.
    - R6. `decode` returns BORROWS (`&'a WireHeader`, `&'a [u8]`), never `Vec<u8>`.
    - R7. `bytemuck::Pod` derive on `WireHeader` enforces no padding.
    - R8. Encode ≤5 ns, decode ≤5 ns.

  - **Design walk-through**:
    - D1. Why is `len_and_meta` the synchronization point, not a separate ready-flag?
    - D2. Endianness: writer on x86, reader on ARM — what could go wrong without `to_le_bytes`?
