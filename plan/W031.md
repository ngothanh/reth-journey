**Monday — `MdbxTrieStorage` design**

- [ ] Design table layout (state nodes by hash, intermediate nodes by Nibbles path). (~30 min)
- [ ] Implement `eth_trie::TrieStorage for MdbxTrieStorage` skeleton. (~120 min)
  - **Why**: The MPT separates two access patterns — content-addressed lookup (by 32-byte node hash) for proof verification and reorg-safe shared structure, and path-addressed lookup (by nibble prefix) for hot-path range scans and incremental root recomputation. Reth uses two MDBX tables (`TrieAccount` and `TrieStorage`) keyed by nibble path for the latter; the persistent layer must preserve both invariants without re-encoding nodes on each read.
  - **Read first**: `reth/crates/trie/db/src/trie.rs` (DatabaseTrie cursor logic) and `reth/crates/trie/trie/src/trie_cursor/mod.rs` (TrieCursor trait). Also `eth-trie::TrieStorage` trait in your W20 crate.
  - **Design**:
    ```rust
    pub struct MdbxTrieStorage<'tx> {
        tx: &'tx mdbx::Transaction,
        nodes_by_hash: mdbx::Table,   // B256 -> RLP node bytes
        nodes_by_path: mdbx::Table,   // Nibbles -> RLP node bytes
        dirty: HashMap<Nibbles, Option<Node>>, // None = tombstone
    }
    ```
    **Invariants**:
    - Every node materialized at `path` has hash matching its `keccak256(rlp)` entry in `nodes_by_hash`.
    - Tombstones in `dirty` survive until commit; reads consult `dirty` before `nodes_by_path`.
    - A read-only TrieStorage holds an MDBX read transaction for its entire lifetime (snapshot isolation).
  - **Build steps**:
    1. (~20 min) Define table layout in `mdbx_schema.rs`; key encoders for Nibbles (length-prefix + packed nibbles).
    2. (~40 min) `impl TrieStorage` — `get_node(path)` checks dirty then `nodes_by_path` cursor; `get_node_by_hash(h)` cursor on `nodes_by_hash`.
    3. (~40 min) `write_node(path, node)` populates `dirty`; `commit()` flushes dirty into both tables in one MDBX write tx.
    4. (~20 min) Property test: random insert/get round-trip; tombstones suppress prior values.
  - **Pitfalls**:
    - *Tx lifetime escape*: holding `&Node` returned from a cursor past the txn's end UAFs the MDBX mapping. **Symptom**: segfault during reorg replay. **Fix**: return owned `Vec<u8>` or `Bytes`; never expose borrows out of the storage layer.
    - *Path encoding ambiguity*: variable-length nibbles need a length prefix or a terminator; without it `[1,2]` and `[1,2,0]` collide. **Symptom**: spurious extension-node merges, root hash diverges. **Fix**: HP encoding (the same scheme as on-wire RLP MPT keys).
    - *Dirty-set miss on delete*: a delete that only removes from `nodes_by_path` without inserting a tombstone gets shadowed by stale data at commit. **Symptom**: deleted accounts reappear after reload. **Fix**: explicit `Option<Node>` in dirty map.
  - **Test scenarios**:
    - Insert 10k random (path, node) pairs, restart process, all read back.
    - Tombstone-after-insert: insert then delete same path; read returns `None` pre- and post-commit.
    - Hash table consistency: `nodes_by_path[p].rlp() = nodes_by_hash[keccak(node.rlp())]` for every entry.
  - **Acceptance**:
    - Inheritance ratio (storage-trie wires bufpool/wal/recovery/eth-trie): on track for ≥0.70 by W44.
    - 10k round-trip <50ms p99 on dev SSD.
  - **Downstream**: W32 (proof generation reads via this); W42 (txn wraps the write path); W44 (storage-trie v1.0 ships with this as the canonical backend).

**Tuesday — Wire `eth-trie::Node` to the table layout**

- [ ] Cursor-based read path + dirty-set write path against MDBX. (~45 min)
  - **Why**: MDBX cursors are zero-copy views into the memory-mapped B+tree. Re-positioning a cursor is O(log N) the first time, but subsequent `next()`/`prev()` is amortized O(1). The trie walker relies on this for hot range scans (subtree enumeration). Allocating per-node on every lookup would dominate CPU; cursor reuse is the perf primitive.
  - **Read first**: `libmdbx` `mdbx_cursor_get` doc (operations `MDBX_SET_RANGE`, `MDBX_NEXT`); reth's `reth/crates/storage/db/src/cursor.rs` wrapper.
  - **Design**:
    ```rust
    pub struct TrieCursor<'tx> {
        cur: mdbx::Cursor<'tx>,
        last_path: Option<Nibbles>, // monotonic invariant
    }
    impl TrieCursor<'_> {
        fn seek(&mut self, p: &Nibbles) -> Option<(Nibbles, Vec<u8>)>;
        fn next_node(&mut self) -> Option<(Nibbles, Vec<u8>)>;
    }
    ```
    **Invariants**:
    - Cursor reads always increment `last_path`; out-of-order seeks reset it.
    - A `seek` to a path that doesn't exist returns the next-larger key (range semantics).
  - **Build steps**:
    1. (~15 min) Wrap MDBX cursor; expose `seek` + `next_node`.
    2. (~20 min) Write path: stage in dirty map, single batched `put` per commit, sorted by path key.
    3. (~10 min) Verify cursor invalidates on write within the same txn (MDBX rule).
  - **Pitfalls**:
    - *Cursor-after-write*: writing in the middle of a cursor scan invalidates the cursor's position. **Symptom**: silent skipped keys or duplicate visits. **Fix**: stage all writes, flush in a separate phase post-scan.
    - *Forgetting to sort batched writes*: MDBX `put` performs best when keys are in sorted order; unsorted writes thrash the B+tree. **Symptom**: 5-10x write slowdown on large batches. **Fix**: sort dirty map before draining.
  - **Test scenarios**:
    - Scan all 256 single-nibble subtrees; cursor visits sorted order.
    - Mixed read + dirty: dirty insert at path P; cursor at P-1 then `next_node` sees the dirty entry (overlay logic).
  - **Acceptance**: 100k seeks in <500ms cold; <100ms warm.
  - **Downstream**: W32 proof generation calls `seek` heavily; W36 snapshot export iterates via this.

- [ ] [NEW v2] **Build**: `crates/mmap-queue/src/excerpt.rs` — `ExcerptCursor<'a>` with `next_excerpt()`, `move_to_index(idx: u64)`, `current_index()`. Forward + random-access. (~90 min)
  - **Why**: Chronicle Queue's ExcerptCursor is the "tape player" abstraction: forward-only fast path (`next_excerpt` is a single bounds check + length read + offset bump) with random-access escape hatch via a sparse index. The cursor is the API that downstream consumers (ledger replay, raft log scan) build on; getting its semantics right now avoids rewrites at W80 (ledger v0.5).
  - **Read first**: net.openhft `chronicle-queue/src/main/java/net/openhft/chronicle/queue/impl/single/SingleChronicleQueueExcerpts.java` — `StoreTailer::next` and `StoreTailer::moveToIndex`.
  - **Design**:
    ```rust
    pub struct ExcerptCursor<'a> {
        queue: &'a MmapQueue,
        cycle: u32,            // which per-day file
        byte_offset: u64,      // within cycle file
        index: u64,            // monotonic logical index
    }
    impl ExcerptCursor<'_> {
        pub fn next_excerpt(&mut self) -> Option<Excerpt<'_>>;
        pub fn move_to_index(&mut self, idx: u64) -> bool;
        pub fn current_index(&self) -> u64;
    }
    ```
    **Invariants**:
    - `byte_offset` is always at a frame boundary (start of `len: u32`).
    - `index` is monotonic on successful `next_excerpt`.
    - `move_to_index` either lands on a real frame and updates state, or returns false and leaves state unchanged.
  - **Build steps**:
    1. (~25 min) Cursor type + `next_excerpt`: read 4-byte length, validate `len <= max_frame`, return slice, bump `byte_offset += 4 + len`.
    2. (~35 min) `move_to_index`: consult sparse index (W31 Thu wire); seek to nearest checkpoint ≤ idx; linear scan from there.
    3. (~20 min) Roll across cycle boundaries (current cycle exhausted → advance `cycle += 1`, reset `byte_offset`).
    4. (~10 min) `current_index` accessor + Debug impl.
  - **Pitfalls**:
    - *Torn-length read*: reading `len` mid-write returns garbage. **Symptom**: oversized `len` triggers panic or stalls. **Fix**: writer publishes length via atomic store with Release; reader uses Acquire load.
    - *Off-by-one across cycle roll*: index N in cycle 5 vs cycle 6 boundary is a common bug. **Symptom**: cursor skips one excerpt or repeats one. **Fix**: per-cycle index is keyed by `(cycle, local_idx)`; logical index is `cycle * cycle_size + local_idx`.
    - *Mmap not advanced*: if writer extended the mapping but reader's view is stale, reader sees old length zero. **Fix**: poll file size or use `MAP_POPULATE` + remap; document as "tailer must remap on EOF".
  - **Test scenarios**:
    - Write 100k frames, cursor walks forward; equal count returned.
    - Random `move_to_index` 1k times; integrity check (CRC) on payload.
    - Concurrent writer + reader race: writer 1M frames, reader follows; reader never sees torn frame.
  - **Acceptance**: forward read >5M excerpts/sec on dev SSD; `move_to_index` <10μs for idx within current cycle.
  - **Downstream**: W34 mmap-queue v0.2; W80 ledger replay uses cursor for journal scan; W77 aeron archive replay.

- [ ] [NEW v2] **Build**: `crates/mmap-queue/src/wire.rs` — typed header (4-byte len + 4-byte type-id + payload). (~60 min)
  - **Why**: A typed wire schema lets multiple producers/consumers share one queue while disambiguating payload semantics. Chronicle Queue uses a 4-byte data/meta tag in the header high bits; we factor type-id explicitly so future evolution (versioned payloads, control frames) is non-breaking. The header layout is load-bearing for every downstream — once a frame format ships, you can never change it without a queue migration tool.
  - **Read first**: Chronicle Queue `WireType.java` + the `Header` excerpt format in the queue spec.
  - **Design**:
    ```rust
    #[repr(C)]
    pub struct WireHeader {
        // bit 31 = meta-frame flag; bits 0-30 = payload length
        pub len_and_meta: u32,
        pub type_id: u32, // application-defined
    }
    pub const META_MASK: u32 = 1 << 31;
    pub const LEN_MASK: u32 = !META_MASK;
    ```
    **Invariants**:
    - `len_and_meta` is always written last (publish via atomic Release store).
    - `type_id` is reserved by an application registry; type-id 0 is reserved for the "not yet written" sentinel.
  - **Build steps**:
    1. (~15 min) `repr(C)` struct + accessor methods (`is_meta`, `len`, `type_id`).
    2. (~20 min) `encode(buf, type_id, payload)` writes header then payload; final atomic Release publishes len.
    3. (~15 min) `decode(buf) -> Option<(WireHeader, &[u8])>` returns None if len is sentinel zero.
    4. (~10 min) Round-trip test.
  - **Pitfalls**:
    - *Big-endian/little-endian drift*: cross-arch consumers see different lengths. **Symptom**: reader on ARM sees 16M-len frame written by x86 1-byte payload. **Fix**: explicitly little-endian via `to_le_bytes`; assert at queue open.
    - *Padding/alignment*: `repr(C)` plus a `u32 + u32` gives 8 bytes natively; if you later add a `u8` field, compiler inserts 3 bytes of padding silently. **Symptom**: queue files written by new binary unreadable by old. **Fix**: `repr(C, packed)` with explicit byte slices, or version the header.
    - *Sentinel zero collision*: a real zero-byte payload looks like "not yet written". **Symptom**: reader spin-loops. **Fix**: zero-length payload is forbidden; use a meta-frame with len=0 + meta flag for empty markers.
  - **Test scenarios**:
    - Round-trip 100 payloads of varying type-ids.
    - Cross-endianness: write on x86, read with manual swap; should match.
  - **Acceptance**: header encode/decode <5ns.
  - **Downstream**: every Excerpt read; ledger record types (W80); raft log entry types (W67).
- [ ] [NEW v2] **Build**: `crates/mmap-queue/src/index.rs` — per-cycle index file: array of (index → byte_offset). Sparse: every 1024th excerpt. (~60 min)
  - **Why**: Random access in an append-only file requires a side index, but a dense index doubles I/O. Chronicle Queue's solution: sparse "every Nth excerpt" checkpoint; cursor seeks to the nearest checkpoint ≤ target then linear-scans the residual. Sparsity factor 1024 means ~8 bytes of index per 1024 excerpts, with ≤1024 frames of linear scan on `move_to_index`.
  - **Read first**: Chronicle Queue `IndexUpdater.java` (the index file is itself a mmap-backed array).
  - **Design**:
    ```rust
    pub struct CycleIndex {
        mmap: MmapMut,             // file: <cycle>.idx
        slots: &'static mut [u64], // sparse offsets
    }
    impl CycleIndex {
        pub fn record(&mut self, idx: u64, offset: u64);
        pub fn nearest(&self, idx: u64) -> (u64, u64); // (idx_floor, byte_offset)
    }
    ```
    **Invariants**:
    - `slots[i]` corresponds to excerpt index `i * 1024`; offset 0 means "not yet recorded".
    - Slot writes are monotonic (writer never decreases an offset).
  - **Build steps**:
    1. (~15 min) Create + open `<cycle>.idx`; mmap with `MAP_SHARED`; treat as `&mut [u64]`.
    2. (~20 min) `record`: only writes slot when `idx % 1024 == 0`; atomic Release store.
    3. (~15 min) `nearest`: binary search by `idx / 1024`; return slot value or fallback to (0, 0).
    4. (~10 min) Crash test: kill mid-record; on reopen, scan tail of cycle data to rebuild missing index entries.
  - **Pitfalls**:
    - *Index lags data*: writer crashes after writing frame but before updating index. **Symptom**: `move_to_index` lands at wrong offset. **Fix**: index is best-effort; recovery rescans last 1024 frames after the highest indexed slot.
    - *Slot torn-write*: 8-byte slot torn across page boundary on power loss. **Symptom**: 4-byte top is new, 4-byte bottom is old → garbage offset. **Fix**: align `slots` to 8 bytes; use atomic 64-bit stores; assume fsync semantics (most filesystems guarantee 8-byte atomicity).
  - **Test scenarios**:
    - 100k writes; `nearest(50_000)` returns `(49_152, offset_of_excerpt_49152)`.
    - Recovery: truncate index mid-record; reopen and verify rebuild.
  - **Acceptance**: `nearest` lookup <100ns; recovery rebuild <1s for 1M-excerpt cycle.
  - **Downstream**: ExcerptCursor `move_to_index`; W34 mmap-queue v0.2 adds index-of-indices.
