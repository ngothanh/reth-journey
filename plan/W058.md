**Tuesday — Jump table research + runtime-thread-per-core v0.5: io_uring backend** [NEW v2]

- [ ] Function pointer jump tables. (~30 min)
  - **Why**: Function-pointer jump table dispatch — `[fn(&mut Interpreter, &mut H); 256]` indexed by opcode — avoids match's branch-tree overhead. LLVM CAN generate jump tables from match, but only when arm count is high and contiguous; reality: revm's match generates a 200+ way branch tree, not a true jump.
  - **Read first**: revm-interpreter `instructions.rs::instruction_table` (production jump-table impl in revm); LLVM jump-table heuristics.
  - **Design**:
    ```rust
    pub type Instruction<H> = fn(&mut Interpreter, &mut H);
    pub type InstructionTable<H> = [Instruction<H>; 256];

    pub const fn instruction_table<H: Host, SPEC: Spec>() -> InstructionTable<H> {
        let mut table: InstructionTable<H> = [op_invalid; 256];
        table[0x00] = op_stop;
        table[0x01] = op_add;
        // ... 200+ ops
        table
    }

    fn run<H: Host>(interp: &mut Interpreter, host: &mut H, table: &InstructionTable<H>) {
        loop {
            let opcode = interp.bytecode[interp.ip] as usize;
            interp.ip += 1;
            table[opcode](interp, host);
            if interp.result != Continue { break; }
        }
    }
    ```
    **Invariants**:
    - Table is `const fn` evaluable at compile time per (Host, Spec) pair.
    - Unset slots default to `op_invalid` (consumes all gas, returns InvalidOpcode).
    - Each op fn signature is identical → uniform indirect-call cost.
  - **Build steps (research-only today)**:
    1. (~10 min) Document the 3 dispatch strategies: match-tree (revm/exec-vm current), jump-table (revm has both via macro), computed-goto (unsafe, asm-style).
    2. (~10 min) Predicted performance: jump-table has +1 branch-mispredict per op (indirect call vs direct branch), but no tree traversal. Per-op overhead: ~3 ns vs match's ~5 ns. Mainnet-cap wall-clock expected: -10 to -15%.
    3. (~5 min) Note that LLVM may inline op fn pointer when target known — disabled with `#[inline(never)]` on op fns to keep dispatch indirect (otherwise table effectively reverts to match).
    4. (~5 min) Tentative plan for Wed: implement, feature-flag `dispatch_jump_table`, A/B against Mon baseline.
  - **Acceptance**: design doc; perf prediction stated.
  - **Downstream**: Wed (implement); Thu (computed-goto research); Fri (bench).
- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/io_backend.rs` — alternative to epoll Reactor: io_uring submission/completion rings per shard. (~150 min)
  - **Why (MAX DETAIL — bar c)**: io_uring is Linux's modern async I/O — 2-4× throughput vs epoll for high-syscall workloads (fsync, small reads/writes), zero-copy with registered buffers, batched submission via SQE rings. Critical for the matching-engine WAL fsync path (W63+) and marketdata file persistence (W85+). Bar (c) — interview-load-bearing for any low-latency Linux work.
  - *Back-of-envelope*: every epoll-driven syscall costs ~300 ns (kernel boundary + context save/restore); a fsync per WAL commit is another ~10-50 µs to disk. **Target: ≥ 2× epoll throughput on a 4-shard 1M-fsync bench; per-op SQE submit ≤ 50 ns when SQ_POLL is engaged (no syscall).** At a 1M order/sec matching-engine target with one WAL fsync per batched commit, that's ~10k fsync/sec/shard — io_uring's batching collapses 10k syscalls/sec down to ~10/sec (one per CQE drain). On a fast NVMe, fsync itself is ~10 µs; without io_uring the syscall overhead alone (~300 ns × 10k = 3 ms/sec/shard) is a 0.3% CPU tax on a hot shard — small per shard, but compounds with epoll's per-event syscall on every read/write. SQ_POLL trades a dedicated kernel core for zero submit-side syscalls (worth it once shard mailbox depth > 100 ops/tick). **Zero allocations on the hot submit path**: SQE entries are pre-allocated ring slots; `user_data` cookies are `u64` (no heap); the `in_flight` map must be a `slab::Slab` keyed by ring index, NOT a `HashMap` (HashMap insert/remove = ~100 ns + alloc on grow).
  - **Read first**:
    - "Efficient IO with io_uring" by Jens Axboe (LWN article)
    - `io-uring` crate docs (https://docs.rs/io-uring)
    - liburing examples (`io_uring_setup`, `io_uring_submit`, `io_uring_wait_cqe`)
    - SQ_POLL kernel-thread mode (CAP_SYS_NICE required)
  - **Design**:
    ```rust
    use io_uring::{IoUring, opcode, types};

    pub struct UringBackend {
        ring: IoUring,
        registered_fds: Vec<RawFd>,         // for fixed-files
        registered_bufs: Vec<Vec<u8>>,      // for fixed-bufs
        in_flight: HashMap<u64, IoCompletion>, // user_data → completion handler
        next_user_data: AtomicU64,
        sq_poll: bool,
    }

    pub enum IoCompletion {
        Read { buf_id: u32, len: i32, waker: Waker },
        Write { buf_id: u32, len: i32, waker: Waker },
        Fsync { fd: RawFd, waker: Waker },
        Accept { listener: RawFd, waker: Waker },
        // ...
    }

    impl UringBackend {
        pub fn new(entries: u32, sq_poll: bool) -> io::Result<Self> {
            let mut builder = IoUring::builder();
            if sq_poll {
                builder.setup_sqpoll(2000);  // 2s idle before kernel thread sleeps
            }
            let ring = builder.build(entries)?;
            Ok(Self { ring, ..Default::default() })
        }

        pub fn submit_read(&mut self, fd: RawFd, buf: &mut [u8], offset: u64, waker: Waker) -> io::Result<u64> {
            let ud = self.next_user_data.fetch_add(1, Relaxed);
            let entry = opcode::Read::new(types::Fd(fd), buf.as_mut_ptr(), buf.len() as u32)
                .offset(offset)
                .build()
                .user_data(ud);
            unsafe { self.ring.submission().push(&entry)?; }
            self.in_flight.insert(ud, IoCompletion::Read { /* ... */, waker });
            Ok(ud)
        }

        pub fn poll(&mut self) -> usize {
            self.ring.submit().ok();  // kick the kernel
            let mut completed = 0;
            for cqe in self.ring.completion() {
                if let Some(comp) = self.in_flight.remove(&cqe.user_data()) {
                    comp.complete(cqe.result());
                    completed += 1;
                }
            }
            completed
        }
    }
    ```
    **Invariants**:
    - One IoUring per shard (sharing rings across threads requires synchronization → defeats TPC).
    - `user_data` is the cookie: must uniquely identify completion → handler. Reuse causes false completion.
    - SQ_POLL = kernel thread polls SQ ring → no syscall for submit → 50-200ns savings per op; cost: kernel CPU even when idle.
    - Fixed buffers (`register_buffers`) skip per-op mmap → ~30% faster.
    - Completion order ≠ submission order. Don't assume.

    1. (~20 min) Add `io-uring = "0.6"` dep. Feature-gate `io_uring` (Linux-only, kernel ≥ 5.11 for full features).
    2. (~30 min) `UringBackend::new` with optional SQ_POLL. Default ring size 4096.
    3. (~30 min) `submit_read`, `submit_write`, `submit_fsync`, `submit_accept` methods.
    4. (~25 min) `poll()` drains completions, dispatches via `IoCompletion`.
    5. (~25 min) Trait abstraction `IoBackend` so EpollReactor (W30 baseline) and UringBackend are interchangeable. Feature-flag selects.
    6. (~20 min) Integration with shard loop: shard `tick()` calls `backend.poll()` before draining mailbox.
  - **Pitfalls** (named, OS-critical):
    - *Buffer lifetime*: read SQE references buf pointer; if Rust drops the Vec before completion, kernel writes to freed memory. **Symptom**: silent corruption or SEGV. **Fix**: pin buffers (Box::leak for fixed buf OR keep Vec in `in_flight` map until completion).
    - *user_data collision*: AtomicU64 wraps at u64::MAX (only relevant after ~10^11 ops — but easy to assume infinite). **Symptom**: stale completion misroutes. **Fix**: u64 is fine for 10+ years at 1M ops/sec; document and move on.
    - *SQ overflow*: pushing when SQ ring full silently fails (`push` returns Err). **Symptom**: ops lost. **Fix**: check `push` result; if Err, `submit_and_wait(1)` to make room.
    - *Cross-shard fd sharing*: registering same fd in multiple shard rings → kernel ref-count works but completion can fire on wrong shard. **Symptom**: completion arrives on wrong runqueue. **Fix**: one fd → one shard's ring; route fd creation by hash.
    - *SQ_POLL CAP_SYS_NICE required*: without root or capability, setup fails. **Symptom**: process won't start in container. **Fix**: detect EPERM, fall back to non-poll mode; document deployment requirement.
    - *Kernel feature variation*: io_uring features evolve per kernel version. Probe via `io_uring_probe`. **Symptom**: opcode not supported, ENOTSUP errors. **Fix**: feature detection at startup; fall back to epoll for unsupported ops.
  - **Test scenarios**:
    - 1M small fsyncs across 4 shards: uring ≥ 2× epoll throughput.
    - Bench socket accept: uring accept-batching reduces accept-loop CPU by 50%.
    - SQ overflow simulation: pump 10x SQ capacity in single tick; verify no ops lost (some flushed via implicit submit).
    - Buffer-drop bug regression test: deliberately drop a buf reference before completion; valgrind catches use-after-free if pin-handling broken.
  - **Expect to hit (perf) #1 — `HashMap<u64, IoCompletion>` allocates and chains on the hot submit path (bar (c) violation)**: the design above uses `HashMap<u64, IoCompletion>` for in-flight lookup. Each `submit_*` does `insert` (~100 ns + occasional rehash + alloc); each `poll` drain does `remove` (~50 ns). At 1M ops/sec/shard that's 150 ms/sec of pure map overhead per shard, plus periodic GC-like pauses when the map rehashes. Symptom: bench shows io_uring "only" 30% faster than epoll instead of the 2× target; flame graph shows `hashbrown::raw::resize` and `alloc::alloc` in the top 5. The bar (c) violation is *not* that it's slow — it's that the hot submit path *allocates*.
    - Fix: `slab::Slab<IoCompletion>` indexed by `u32` slot id; `user_data` = `(slot_id as u64) << 32 | generation_counter` (generation prevents stale-CQE collisions after slot reuse). `Slab::insert` is O(1) amortized and zero-alloc once warmed; `remove` is O(1) and frees the slot without dealloc. Pre-grow the slab to ring depth at construction.
    - Cost avoided: ~150 ns per op + allocation jitter; ~150 ms/sec on a 1M-op shard; eliminates rehash pauses from the p99 tail (which can be 10-100 µs hiccups).
    - Muscle: any data structure on a bar-(c) hot path must be zero-allocation in steady state — `slab`/`SmallVec`/pre-sized arenas, never `HashMap`/`Vec::push`-on-grow. Reapplies at: W60 matching-engine `order_index` (replace `AHashMap` with intrusive index by W74), W74 lock-free price level node pool, W76 aeron term-buffer claim slot pool, W85 marketdata frame ring.
  - **Expect to hit (perf) #2 — `Box<dyn FnOnce + Send>` callback in IoCompletion forces a heap alloc per submit (bar (c) violation)**: the natural completion design is `enum IoCompletion { Read { waker, callback: Box<dyn FnOnce(i32) + Send> } }`. Every submit boxes a closure (~80 ns + 32-64 B heap alloc); under 1M ops/sec/shard, that's the allocator at ~1M boxes/sec/shard — heap fragmentation, allocator lock contention (even with mimalloc), and 30-100 µs GC-like stalls when the allocator rebalances thread caches.
    - Fix: completion routing is *typed*, not callback-based: `enum IoCompletion { Read { slot: SlotId, waker: Waker }, Write { slot }, Fsync { ack: AtomicWaker }, ... }`. The shard's `poll()` matches the variant and dispatches without a closure. For Future-based wakeups, store `AtomicWaker` inline (no Box). For shard-internal acks, store a `slab` slot id into the shard's per-feature ack table.
    - Cost avoided: ~80 ns alloc + ~16 B heap residency per in-flight op; under 100k in-flight, that's ~1.6 MB of fragmented heap that never gets cleanly returned to the OS. Removes one of the top three allocator hot-spots on a busy shard.
    - Muscle: `Box<dyn FnOnce>` is a hidden allocation on every call — on bar-(c) paths replace dyn-dispatch + boxing with a small typed enum and inline state. Reapplies at: W60 matching-engine event handler dispatch (typed `MatchEvent` not `Box<dyn Handler>`), W74 raft RPC completion (slab + variant), W76 aeron flow-control credit callback, W83 ledger op handler.
  - **Acceptance**: 4-shard fsync bench: uring ≥ 2× epoll; trait abstraction lets test infra select backend; flame graph shows **no `alloc::alloc` and no `HashMap::resize` in the submit/poll path**; criterion bench-diff shows steady p99 (no rehash hiccup).

- [ ] [HFT] Sketch in `notes/matching_engine_design.md`: data structures (price levels via RB-tree or skip list — decide
  W63), order ID generation, deterministic event log via wal, per-symbol shard plan. (~25 min)
  - **Why**: A design doc forces decisions BEFORE code commits to them. Decision points:
    - **Price-level structure**: RB-tree (BTreeMap, std) vs skip list (concurrent, harder). RB-tree wins for single-shard simplicity; skip list wins for concurrent updates. Per-symbol single-writer makes RB-tree the right v0.5 choice.

  - *Back-of-envelope* (the latency budget this whole crate must respect): **P99 single-symbol matching latency target: <10 µs at v0.5 (W63), <5 µs at v1.0 (W74), <2 µs at v1.5 (W82), <1 µs at v1.5 polish (M30).** Decompose the v1.0 5 µs budget: ~500 ns risk check (per-account balance cache lookup) + ~500 ns book traversal (BTreeMap::range with ~log2(price_levels) hops, ~7 hops × 50 ns L2 = 350 ns + ~150 ns overhead) + ~1 µs per fill (VecDeque pop_front + event log encode + WAL append byte-copy) + ~500 ns L1 quote publish (SeqLock store) + ~500 ns event broadcast (channel send) + ~2 µs slack. At 1 M orders/sec on one core, that's 1000 ns/order budget — so **anything that costs ≥100 ns on the hot path is a top-10 hot spot**. Jeff Dean budget killers: `malloc` (~50 ns + jitter), `mutex_lock` (~25 ns uncontended, ~µs contended), `cache miss` (~100 ns), `float div` (~10-30 cycles), `branch mispredict` (~5 ns). - [ ] Unsafe computed goto via asm. Portability tradeoffs. (~30 min)
  - **Why**: Computed goto (GCC's `&&label` syntax) lets you encode opcode dispatch as direct jumps embedded inline at the END of each opcode's body. Result: zero centralized loop, every op tail-jumps directly to the next. Predicts better than jump-table (each op has its own BTB entry → less aliasing). Used by CPython, V8, evmone-advanced. Rust has NO direct equivalent; closest is `#[inline(always)] tail-call` (unstable) or hand-written `asm!`.
  - **Read first**: CPython's `Python/ceval.c` `USE_COMPUTED_GOTOS` block; evmone-advanced `lib/evmone/advanced_execution.cpp::dispatch`; Eli Bendersky "Computed goto for efficient dispatch tables" article; Rust unstable `become` (RFC 3407) tail-call.
  - **Design** (Rust approximation):
    ```rust
    // Goal: each op fn ENDS with a jump directly to next op, not return to dispatcher.
    // Rust stable doesn't allow this. Options:
    //   1. become op_table[next_op](interp, host);  // unstable
    //   2. Manual asm!("jmp {}", in(reg) op_fn_ptr); // unsafe, x86-only
    //   3. Stay with jump-table; rely on LLVM tail-call optimization (lots of inlining).
    ```
    **Tradeoffs**:
    - **Portability**: option 2 (asm) ties exec-vm to x86_64. Loses ARM (M-series Macs, AWS Graviton).
    - **Maintenance**: each opcode body becomes inline-asm-wrapped; massive code-bloat.
    - **Realized speedup vs jump-table**: 5-10% on tight arithmetic loops; 0% on memory-heavy. Not worth the maintenance cost unless mainnet-cap shows ≥ 5% gain.
    - **Cargo culting risk**: CPython is interpreted bytecode; EVM is too. But CPython's win partly comes from minimizing intra-op variance, which doesn't map cleanly to EVM where gas-cost-tracking is uniform.
  - **Build steps (research only today)**:
    1. (~10 min) Read evmone-advanced dispatch. Understand the basic-block grouping trick (groups of opcodes share dispatch overhead).
    2. (~10 min) Read RFC 3407 (`become` for tail calls). Stable date unclear.
    3. (~5 min) Decide: SKIP computed-goto for v0.5; revisit when `become` stabilizes. Jump-table is the production dispatch path.
    4. (~5 min) Document decision in `EXEC_VM_DISPATCH.md`.
  - **Acceptance**: tradeoff doc committed; decision recorded; W64 perf PR doesn't pursue this avenue.
  - **Downstream**: W64 perf PR focuses on jump-table inlining + branch hints instead.

- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/timer.rs` — hashed timer wheel per shard. 1ms tick. (~120 min)
  - **Why (MAX DETAIL — bar c)**: Timer wheels are THE canonical data structure for O(1) timer insert/cancel/expire when you have many timers (10k+ in matching engine: GTC orders, IOC timeouts, P2P heartbeats, raft election timers). The naive priority-queue approach is O(log n) per op and O(n) cancel by ID — both prohibitive at scale. Varghese & Lauck "Hashed and Hierarchical Timing Wheels" (1987) is the foundational paper. Bar (c) — interview-load-bearing.
  - *Back-of-envelope*: matching-engine target = ≥ 10k active GTC timers per shard, ≥ 1k schedules/sec, p99 schedule + cancel ≤ 100 ns. Per-tick cost (every 1 ms): drain one level-0 slot ≈ amortized 1-5 entries × ~50 ns = 100-300 ns; cascade (every 64 ms): take next level-1 slot (~10-50 entries) × reschedule cost (~30 ns each) = 1-3 µs amortized per cascade, paid every 64 ms = ~50 ns/ms — invisible in the budget. **Critical: tick() runs in the shard reactor loop ~once per ms**, so it competes with order matching — must stay zero-alloc and ≤ 1 µs typical/≤ 10 µs cascade. `Box<dyn FnOnce>` per timer is the killer — see perf #1 below.
  - **Read first**:
    - Varghese & Lauck, "Hashed and Hierarchical Timing Wheels", SOSP 1987 (the paper)
    - Linux kernel `kernel/time/timer.c` (Cascading hierarchical wheel — production reference)
    - Netty `HashedWheelTimer` Java impl (widely-deployed reference)
    - tokio's `time::driver` source (single-wheel hierarchical)
  - **Design**:
    ```rust
    // Hierarchical hashed timer wheel. Like Linux: 5 levels of 64 slots.
    // Level 0: 64 slots × 1ms granularity → covers 0..64ms
    // Level 1: 64 slots × 64ms granularity → covers 64..4096ms
    // Level 2: 64 slots × 4096ms granularity → covers ~4s..262s
    // Level 3, 4: progressively coarser
    pub struct TimerWheel {
        levels: [Level; 5],
        current_tick: u64,          // counted in 1ms units since epoch
        tick_duration: Duration,
        timer_index: HashMap<TimerId, (LevelIdx, SlotIdx, usize /*position in slot*/)>,
        next_id: AtomicU64,
    }
    pub struct Level {
        slots: [Vec<TimerEntry>; 64],
        slot_mask: usize,           // 63
    }
    pub struct TimerEntry {
        id: TimerId,
        deadline: u64,              // absolute tick
        callback: Box<dyn FnOnce() + Send>,
    }
    ```
    **Invariants**:
    - All times in ticks (u64, 1ms each). Roll over after ~580M years.
    - Schedule: compute `delta = deadline - current_tick`; pick level by leading-zeros of delta; slot = `(deadline >> (6 * level)) & 63`.
    - Tick: advance level 0 by one slot; expire all entries in that slot. When level 0 wraps (every 64 ticks), cascade level 1: take next slot from level 1, RESHEDULE its entries into level 0 (now they're within 64ms).
    - Cancel: O(1) via timer_index lookup → slot remove (O(slot_size) typical).
  - **Build steps** (granular):
    1. (~20 min) `TimerWheel::new(tick_duration: Duration)` allocates 5 × 64 slots.
    2. (~25 min) `schedule(deadline: u64, callback) -> TimerId`: compute level from delta, slot from deadline bits, append to Vec, register in timer_index.
    3. (~20 min) `cancel(id: TimerId) -> bool`: lookup index, remove from slot Vec (swap-remove for O(1)).
    4. (~25 min) `tick(now: u64)`: advance current_tick; for each level wrap, cascade entries from level+1 down to level 0.
    5. (~20 min) Tests: 10k scheduled timers, advance time, verify all fire within 1 tick of deadline.
    6. (~10 min) Cancel under contention: schedule 1k, cancel 500 randomly, verify only 500 fire.
  - **Pitfalls** (named, data-structure):
    - *Cascade thrash*: every 64 ticks, level 1's next slot may contain 1000+ entries — reschedule overhead spikes. **Symptom**: periodic 1ms-resolution latency spike. **Fix**: amortized — average remains O(1); but for HFT critical path, use hierarchical wheel from W74 with 4 levels of 256 slots for smoother distribution.
    - *Far-future timer*: deadline > 580M years → overflow. Adversarial input. **Symptom**: timer never fires. **Fix**: cap deadline at u64::MAX / 2 with explicit error.
    - *Drift on tick miss*: if the shard's tick() isn't called for 5ms (e.g., long opcode), 5 ticks of timers fire all at once. **Symptom**: latency burst. **Fix**: in tick, loop `while current_tick < now { advance_one(); }` to catch up.
    - *Slot-removal cost*: cancel does swap-remove; if slot has 10k entries, swap-remove still O(1). But it updates timer_index for the swapped entry — easy to forget. **Symptom**: cancelled-but-still-fires bug or wrong-callback-fires bug. **Fix**: after swap-remove, update timer_index[swapped_id].
    - *Cross-shard schedule*: scheduling timer for another shard requires cross-shard message → reschedule overhead. **Symptom**: timer fires on wrong shard. **Fix**: per-shard wheel; cross-shard timer goes through cross_shard channel (W57).
  - **Test scenarios**:
    - 10k timers, deadlines uniform in [0, 60s], advance time: all fire within 1 tick of deadline.
    - Cancel 50% of timers; verify cancelled don't fire.
    - Pathological: 1000 timers all at deadline t=60000ms; tick 60000 fires all → verify single-tick throughput acceptable.
    - Tick miss: simulate 100ms gap in tick(); verify catch-up fires all elapsed timers in single tick() call.
  - **Expect to hit (perf) #1 — `Box<dyn FnOnce>` callback per timer entry (bar (c) violation)**: the design above stores `callback: Box<dyn FnOnce() + Send>` in every `TimerEntry`. Scheduling 10k GTC orders means 10k heap allocs at startup; under churn (1k schedules/sec), the allocator is paged on a hot shard. Worse, the timer wheel sits *inside the shard reactor loop* — every `tick()` may invoke 1-100 callbacks; each `FnOnce` call dereferences a Box (cache miss likely — ~100 ns) and then dispatches via vtable indirect call (another ~5 ns + branch mispredict). On a busy shard, that's ~10 µs of cascade latency per tick when the timer fires a burst — well over the ≤ 1 µs typical budget.
    - Fix: replace `callback: Box<dyn FnOnce()>` with a typed `payload: TimerPayload` enum: `enum TimerPayload { ExpireOrder { id: OrderId }, RaftElection { node: NodeId }, P2pIhave { peer: PeerId }, Keepalive { conn: ConnId } }`. The shard's tick handler matches on the variant and routes to the appropriate inline handler — zero vtables, zero boxes, dispatched as a `jmp` into the shard's main state machine. For exotic one-off timers, allocate from a per-shard `slab::Slab<BoxedTimer>` (so allocation is amortized once per shard, not per timer).
    - Cost avoided: ~16-32 B heap residency per timer × 10k = ~256 KiB heap fragmentation per shard eliminated; ~100 ns cache miss + ~5 ns vtable per fire eliminated (so ~10 µs cascade burst → ~500 ns); removes the allocator lock from a hot path that previously hit it 1k/sec.
    - Muscle: closures-by-Box are a "convenience tax" that bar-(c) cannot pay — replace `Box<dyn FnOnce>` with a typed enum routed to a state machine. Reapplies at: W60 matching-engine event handler (typed `MatchEvent` not `Box<dyn Handler>`), W74 raft RPC completion routing, W76 aeron flow-control event, W83 ledger transfer op dispatch.
  - **Expect to hit (perf) #2 — cascade thrash spikes p99 latency under burst load (bar (c) violation)**: the hierarchical design above cascades every 64 ticks; if level-1 slot N contains 1000+ entries (e.g., 1000 GTC orders all set with TIF = 60 s), a single cascade tick reschedules all of them at once — a 1000 × ~30 ns = 30 µs spike inside one `tick()` call. Inside a matching-engine reactor that targets ≤ 5 µs P99 matching latency, that 30 µs spike *is* the P99. Symptom: criterion-bench shows a periodic latency bump every ~64 ms; flame graph shows `Vec::push` in `level0.push_back` dominating during cascade ticks.
    - Fix: amortize the cascade across multiple ticks — split the cascade work over the next 64 level-0 ticks (move 1/64th of the slot's entries per tick). Alternative: use a coarser-granularity outer level (e.g., 256 slots × 16 ms granularity at level 1) so cascade slot sizes stay small in expectation. Or accept the spike for non-latency-critical timers (raft election, gossip) but route latency-critical timers (IOC expire, market-data heartbeat) to a separate fine-grain wheel.
    - Cost avoided: ~30 µs P99 spike every 64 ms → ≤ 1 µs steady; flat latency replaces sawtooth. Without this fix, p99 measurements are dominated by cascade aliasing, masking the real matching-path tail.
    - Muscle: amortization is necessary but not sufficient — under bar (c) the *amortized cost smoothing* matters more than the amortized average, because P99 is the bar. Reapplies at: W40 LSM compaction starvation (already pitfalled), W42 txn vacuum burst, W74 matching-engine snapshot pause, W83 ledger checkpoint stop-the-world.
