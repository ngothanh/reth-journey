**Tuesday — io_uring backend (runtime-thread-per-core v0.5) + jump-table research**

- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/io_backend.rs` — io_uring submission/completion rings per shard, an alternative to the W30 epoll Reactor. (~total 200 min across 3 phases)
  - 🔧 **Why this matters**: io_uring is Linux's modern async I/O — 2-4× throughput vs epoll on high-syscall workloads (fsync, small reads/writes), zero-copy with registered buffers, batched submission. Mirrors Seastar's reactor io_uring backend. The matching-engine WAL fsync path (W63+) and marketdata persistence (W85+) inherit it. Two traps disqualify the crate from bar (c): `HashMap<u64, IoCompletion>` on the submit path (allocates + rehash p99 hiccups) and `Box<dyn FnOnce>` per completion (1M boxes/s) — both forfeit the entire perf advantage and both are hidden behind "convenient" API shapes. **First-attempt impls fail `submit_zero_alloc`, `io_completion_no_box_dyn`, and `fsync_throughput_2x_epoll` — the debug session is the lesson.**

  #### Phase 1 — Problem, prediction, design (~60 min, no code yet)
  - 🎯 **Pre-prediction prompt (do this BEFORE reading Phase 2)** — write sealed answers in `crates/runtime-thread-per-core/notes/58_io_backend_prediction.md`:
    - P1. Name the in-flight-tracking container you'd reach for first, sight-unseen. Write the exact field declaration line (type + key + value).
    - P2. Predict the per-`submit_*` latency for your P1 container at 1M ops/s/shard (one number, ns) and predict the io_uring/epoll throughput ratio your first attempt will measure (one number).
    - P3. Predict what happens on the FIRST `submit_read` if the caller drops the `Vec<u8>` before the CQE arrives. One sentence.
    - P4. Predict whether `IoCompletion` will compile with a `Box<dyn FnOnce(i32) + Send>` field and what it costs per submit (one number, ns + bytes).
    - P5. List every Phase-2 test name you predict your first attempt will fail. The delta vs reality after tests run is the lesson.
  - *Mental model*: one io_uring per shard. `submit_*` pushes an SQE with a `user_data` cookie and parks a typed completion; the shard's `poll()` drains CQEs, matches the cookie to its completion slot, and fires the waker. Replaces the epoll syscall-per-event model with batched submit + (optionally) zero submit-side syscalls via SQ_POLL.
  - *Contract*: `trait IoBackend { fn submit_read(&mut self, fd, buf: Vec<u8>, off, Waker) -> SubmitResult; fn submit_write/submit_fsync/submit_accept(...); fn poll(&mut self) -> usize; }`. `EpollReactor` (W30) and `UringBackend` both impl it; feature-flag selects at compile time. `submit_*` returns a `u64` cookie; never a borrowed buffer.
  - *Back-of-envelope*: every epoll-driven syscall costs ~300 ns (kernel boundary + context save/restore). At a 1M order/sec matching target with one WAL fsync per batched commit ≈ **10k fsync/sec/shard**; epoll's syscall overhead alone is 300 ns × 10k = **3 ms/s/shard** of pure tax before fsync's ~10 µs/op disk work. io_uring batches submissions and SQ_POLL collapses 10k submit syscalls/sec → ~10/sec (one per CQE drain). **Target: ≥ 2× epoll on a 4-shard 1M-fsync bench; per-op SQE submit ≤ 50 ns with SQ_POLL; per-drained-CQE ≤ 30 ns.** Cliff: a `HashMap`+`Box<dyn>` design measures only ~1.3× epoll where 2× is achievable — the cookie map costs ~100 ns insert + ~50 ns remove = **150 ns/op = 150 ms/s/shard**, and 1M boxes/s × ~80 ns = **80 ms/s** + ~1.6 MB fragmented heap. Zero-alloc-on-the-hot-path is the load-bearing decision.
  - **Requirements** R1..R9 — write in `notes/58_io_backend_design.md`:
    - R1. One `IoUring` per shard; sharing rings across threads is FORBIDDEN (defeats TPC).
    - R2. `submit_*` for `read`/`write`/`fsync`/`accept`; each takes a `Waker`, returns a unique `u64` `user_data` cookie.
    - R3. `in_flight` MUST be `slab::Slab<IoCompletion>` indexed by `u32` slot id; NOT `HashMap`. `user_data = (slot_id as u64) << 32 | generation` for stale-CQE rejection after slot reuse.
    - R4. `IoCompletion` is a TYPED enum (`Read { slot, waker } | Write { slot, waker } | Fsync { ack: AtomicWaker } | Accept {..}`); NEVER `Box<dyn FnOnce>`.
    - R5. SQ_POLL optional (kernel thread polls SQ ring → zero submit syscall). Fallback to non-poll on missing CAP_SYS_NICE; never panic.
    - R6. Fixed buffers via `register_buffers` for hot read/write; per-op mmap FORBIDDEN on the hot path.
    - R7. Budgets: ≤ 50 ns per `submit_*` with SQ_POLL; ≤ 30 ns per drained CQE.
    - R8. Trait `IoBackend` abstracts the W30 epoll Reactor and `UringBackend`; feature-flag selects.
    - R9. Buffer lifetime: the `in_flight` slot OWNS the buffer (`Vec<u8>` or refcounted `Bytes`) for the whole in-flight duration; only freed on CQE drain. Passing a borrowed `&mut [u8]` is forbidden.
  - **Design walk-through** D1..D6 — answer in the design doc; no peeking at Seastar/liburing source until Phase 3:
    - D1. Property table for in-flight container: `HashMap` vs `slab::Slab` vs `Vec<Option<_>>` — Sync? insert latency? allocs-on-grow? rehash pause? Walk the cost: HashMap insert ~100 ns + occasional rehash + alloc → 150 ms/s/shard at 1M ops + 10-100 µs p99 hiccups; Slab insert O(1) zero-alloc once pre-grown to ring depth.
    - D2. Completion routing: typed enum (`match` → branch-predicted, zero alloc) vs `Box<dyn FnOnce(i32)>` (1M × ~80 ns = 80 ms/s + 32-64 B heap × 100k in-flight = ~1.6 MB fragmented). Write the enum.
    - D3. `user_data` cookie encoding: write `(slot_id << 32) | generation`. Why generation? A stale CQE from a cancelled op can arrive after the slot is reused → generation mismatch rejects it.
    - D4. SQ_POLL tradeoff: a dedicated kernel core spinning vs zero submit syscall (~300 ns/op saved). When worth it? (Hint: shard mailbox depth > 100 ops/tick AND a spare core.)
    - D5. Fixed buffers: `register_buffers` pins user memory, kernel skips mmap per op (~30% faster). Memory cost: pool sized for steady-state in-flight (e.g. 64 × 4 KB = 256 KB).
    - D6. **Pre-mortem (load-bearing):** write the EXACT 4-step path from "natural `HashMap<u64, IoCompletion>` + `Box<dyn FnOnce>` design" to "io_uring measures 1.3× epoll, not the 2× target." This is the bar-(c) decision the whole Build turns on.
    - D7. **Anti-shortcut audit:** for in-flight tracking the obvious reach is `HashMap<u64,_>` (alloc + rehash — wrong on hot path); for completion the obvious reach is `Box<dyn FnOnce>` (alloc per op — wrong); for buffers the obvious reach is `&mut [u8]` (UAF — wrong, kernel outlives the borrow). One line each on why it's wrong HERE.
  - **Output**: `notes/58_io_backend_design.md` with R1–R9, D1–D7, the 4-step pre-mortem, and a lifecycle diagram (submit → SQE push → kernel → CQE arrival → slot drain → waker fire).

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)
  Newbie failures first, expert last.
  - **(NEWBIE) When `io_completion_no_box_dyn` finds `Box<dyn FnOnce>` and `submit_zero_alloc` reports ~1M allocs/s:**
    - Symptom: at 1M ops/s/shard the allocator runs at ~1M boxes/sec — heap fragmentation, allocator-lock contention (even with mimalloc), 30-100 µs GC-like stalls on thread-cache rebalance.
    - Why: the natural completion design is `enum IoCompletion { Read { waker, callback: Box<dyn FnOnce(i32) + Send> } }`; every submit boxes a closure (~80 ns + 32-64 B heap).
    - Fix: TYPED routing — `enum IoCompletion { Read { slot, waker }, Write { slot, waker }, Fsync { ack: AtomicWaker }, .. }`; `poll()` matches the variant. For Future wakeups store `AtomicWaker` inline; for shard-internal acks store a slab slot id.
    - Cost avoided: ~80 ns alloc + ~16 B residency per in-flight op; ~1.6 MB fragmented heap under 100k in-flight; removes a top-3 allocator hot-spot **(bar (c) violation)**.
    - Muscle: `Box<dyn FnOnce>` is hidden per-call allocation — on bar-(c) paths replace dyn-dispatch + boxing with a small typed enum + inline state. **Reapplies at**: W60 matching-engine event-handler dispatch, W74 raft RPC completion, W76 aeron flow-control credit callback, W83 ledger op handler.
  - **(SENIOR) When `in_flight_uses_slab_not_hashmap` finds HashMap and `fsync_throughput_2x_epoll` reports ratio 1.3×:**
    - Symptom: io_uring only ~30% faster than epoll, not 2×; flame graph shows `hashbrown::raw::resize` + `alloc::alloc` in the top 5; periodic 10-100 µs p99 hiccups from rehash.
    - Why: `HashMap<u64, IoCompletion>` for in-flight lookup — `insert` ~100 ns + occasional rehash + alloc per `submit_*`; `remove` ~50 ns per drain. At 1M ops/s ≈ 150 ms/s of map overhead PLUS rehash pauses as p99 spikes.
    - Fix: `slab::Slab<IoCompletion>` indexed by `u32`; `user_data = (slot << 32) | generation`. `Slab::insert/remove` O(1) zero-alloc once warmed; pre-grow to ring depth at construction.
    - Cost avoided: ~150 ns/op + alloc jitter ≈ 150 ms/s/shard; eliminates rehash from the p99 tail **(bar (c) violation)**.
    - Muscle: any structure on a bar-(c) hot path must be zero-alloc in steady state — `slab`/`SmallVec`/pre-sized arena, never `HashMap`/`Vec::push`-on-grow. **Reapplies at**: W60 matching-engine `order_index` (intrusive index by W74), W74 lock-free price-level node pool, W76 aeron term-buffer claim-slot pool, W85 marketdata frame ring.
  - **(SENIOR) When `generation_rejects_stale_cqe` fires the wrong waker:**
    - Symptom: a cancelled op's stale CQE arrives after the slot is reused; the new op's waker fires with the OLD op's result.
    - Why: `user_data = slot_id` only; no generation; reuse collides.
    - Fix: 32-bit slot + 32-bit generation; generation increments on reuse; drain checks `(user_data >> 32) == slab[slot].generation`; mismatch → drop silently (log debug).
    - Cost avoided: a silent state-corruption class (no perf number — correctness). Avoids ~hours of "phantom completion" debugging.
    - Muscle: every slot-reuse design needs a generation counter, else stale notifications corrupt state. **Reapplies at**: W74 matching-engine order-slot reuse, W76 aeron term-buffer slot reuse.
  - **(EXPERT) When `buffer_lifetime_no_use_after_free` shows UAF under miri:**
    - Symptom: SEGV under valgrind, or silent corruption — the kernel wrote into a freed `Vec`.
    - Why: `submit_read(fd, &mut buf)` hands the buf pointer to the SQE; the caller drops the `Vec` before the CQE; the kernel writes freed memory.
    - Fix: the slot OWNS the buffer — `submit_read(fd, buf: Vec<u8>)` takes ownership, stores it in the slot, and the drain hands it back (channel / typed return).
    - Cost avoided: a use-after-free (undefined behaviour; potential RCE on a network-facing path) **(bar (c) violation — correctness, not slow)**.
    - Muscle: any async I/O the kernel writes to must OWN the buffer for the in-flight duration; a borrowed `&mut` is unsafe unless the lifetime is statically guaranteed to outlive completion. **Reapplies at**: W83 ledger journal write buffers, W90 aeron AF_XDP frame.
  - **(SENIOR) When `sq_poll_fallback_on_no_cap` panics in a container:**
    - Symptom: in Docker without CAP_SYS_NICE, `UringBackend::new(.., sq_poll: true)` panics with EPERM; the process won't start.
    - Why: `io_uring_setup` with `IORING_SETUP_SQPOLL` needs CAP_SYS_NICE (kernel ≥ 5.11) or root.
    - Fix: detect EPERM from setup → log warning, fall back to non-poll; document `--cap-add=SYS_NICE` deployment requirement.
    - Cost avoided: a deployment-time outage (no perf number — availability).
    - Muscle: kernel-feature-dependent code degrades gracefully; never assume privilege. **Reapplies at**: W57 NUMA pinning, W90 AF_XDP setup.

- [ ] **Build (research-only)**: `crates/exec-vm/notes/58_jump_table_design.md` — document the 3 dispatch strategies + jump-table design (no implementation code today). (~30 min)
  - 🔧 **Why this matters**: mirrors revm-interpreter `instruction_table`. A function-pointer table `[fn(&mut Interpreter, &mut H); 256]` indexed by opcode avoids match's 200-way branch tree. LLVM *can* lower a `match` to a jump table but only when arms are dense and contiguous — revm's reality is a branch tree, not a true jump. Bar (b): correctness + measurement. Feeds Wed (implement) + Fri (A/B).
  - **Design** (record in the doc):
    ```rust
    pub type Instruction<H> = fn(&mut Interpreter, &mut H);
    pub type InstructionTable<H> = [Instruction<H>; 256];
    pub const fn instruction_table<H: Host, SPEC: Spec>() -> InstructionTable<H> { /* table[op] = op_fn; default op_invalid */ }
    fn run<H: Host>(i: &mut Interpreter, h: &mut H, t: &InstructionTable<H>) {
        loop { let op = i.bytecode[i.ip] as usize; i.ip += 1; t[op](i, h); if i.result != Continue { break; } }
    }
    ```
    Invariants: table is `const fn` per (Host, Spec); unset slots = `op_invalid` (consume all gas, `InvalidOpcode`); identical op-fn signatures → uniform indirect-call cost; `#[inline(never)]` on op fns keeps dispatch indirect (else LLVM inlines and the table reverts to a match).
  - **Steps**: (1) document match-tree vs jump-table vs computed-goto; (2) predicted perf — jump-table adds +1 indirect-call mispredict/op (~3 ns) but drops tree traversal (~5 ns), so mainnet-cap −10 to −15%; (3) note the `#[inline(never)]` requirement; (4) tentative Wed plan: feature-flag `dispatch_jump_table`, A/B vs Mon baseline.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)
  - **(NEWBIE) When `timer_payload_no_box_dyn` finds `Box<dyn FnOnce>` and `bench_steady_tick_under_1us` reports ~10 µs:**
    - Symptom: 10k GTC orders = 10k heap allocs at startup; under 1k schedules/sec the allocator is paged on a hot shard. A cascade tick fires 1-100 callbacks; each derefs a Box (~100 ns cache miss) + vtable indirect (~5 ns + mispredict) → ~10 µs/tick, over the ≤ 1 µs budget.
    - Why: `callback: Box<dyn FnOnce() + Send>` in every `TimerEntry`.
    - Fix: `payload: TimerPayload` typed enum; the shard's tick handler matches the variant and routes to an inline handler — zero vtables/boxes, dispatched as a `jmp` into the shard state machine. Exotic one-offs allocate from a per-shard `slab::Slab<BoxedTimer>` (amortized once per shard).
    - Cost avoided: ~256 KiB fragmentation (16-32 B × 10k) + ~100 ns cache miss + ~5 ns vtable per fire (10 µs burst → ~500 ns); removes the allocator lock from a hot path **(bar (c) violation)**.
    - Muscle: closures-by-Box are a convenience tax bar (c) cannot pay — replace `Box<dyn FnOnce>` with a typed enum routed to a state machine. **Reapplies at**: W60 matching-engine event handler, W74 raft RPC completion routing, W76 aeron flow-control event, W83 ledger transfer-op dispatch.
  - **(EXPERT) When `cascade_amortized_no_p99_spike` shows a 30 µs spike every ~64 ms:**
    - Symptom: latency histogram shows periodic 30 µs spikes; flame graph shows `Vec::push` into `level0` dominating during cascade ticks; the matching-engine p99 is dominated by cascade aliasing.
    - Why: every 64 ticks a level-1 slot may hold 1000+ entries (1000 GTC TIF=60s); one cascade tick reschedules all at once → 1000 × ~30 ns = 30 µs inside one `tick()`. The matching engine targets ≤ 5 µs p99; this spike IS the p99.
    - Fix: amortize the cascade over the next 64 level-0 ticks (1/64 per tick). Alternative: coarser outer-level granularity (256 slots × 16 ms at level 1) keeps slots small; or route latency-critical timers (IOC, market-data heartbeat) to a separate fine-grain wheel.
    - Cost avoided: a 30 µs p99 spike every 64 ms → ≤ 1 µs steady; flat latency replaces sawtooth **(bar (c) violation)**.
    - Muscle: under bar (c) amortized cost SMOOTHING matters more than the amortized average — p99 IS the bar. **Reapplies at**: W40 LSM compaction starvation, W42 txn vacuum burst, W74 matching-engine snapshot pause, W83 ledger checkpoint stop-the-world.
  - **(SENIOR) When `swap_remove_updates_index` reports a stale index entry:**
    - Symptom: after cancelling X (which swap-removes Y into X's slot), a later `cancel(Y)` looks up Y's index → points to X's old position → removes the wrong entry (or no-ops).
    - Why: swap-remove moved Y but `timer_index[Y]` still points to Y's old position.
    - Fix: after `slot.swap_remove(pos)`, if a swap happened (`pos < slot.len()`), set `timer_index[slot[pos].id].pos = pos`.
    - Cost avoided: a cancelled-but-still-fires / wrong-timer-fires correctness bug.
    - Muscle: swap-remove on an indexed container must update the swapped element's index — trivial to forget. **Reapplies at**: the io_uring slab (this week), every slab-style index in the codebase.
  - **(SENIOR) When `tick_miss_catches_up` fires timers out of order:**
    - Symptom: a 100 ms gap → `tick(now)` fires all 100 ms of timers in slot-iteration order, not deadline order; downstream sees out-of-order events.
    - Why: catch-up implemented as "advance to now in one step"; processes whatever's in the now-slot.
    - Fix: `while self.current_tick < now { self.advance_one(); }` — one tick at a time, in order.
    - Cost avoided: out-of-order delivery (correctness — corrupts any deadline-ordered consumer).
    - Muscle: catch-up loops preserve event ordering; never collapse multiple ticks into one. **Reapplies at**: W56 raft tick-driven election timeout, W74 matching-engine.
  - **(EXPERT) When `cross_shard_timer_via_channel` compiles (should fail):**
    - Symptom: shard 0 calls `shard5.timer_wheel.schedule(..)` directly — cross-thread mutation; data race; UB.
    - Why: `timer_wheel` exposed publicly; no shard-isolation enforcement.
    - Fix: `TimerWheel` lives inside `Sharded<TimerWheel>` (W57); cross-shard timers go via `cross_shard.submit_to(shard5, TimerOp::Schedule(deadline, payload))`; the foreign shard's reactor handles it on its own thread.
    - Cost avoided: a cross-shard data race (UB) **(bar (c) violation — correctness)**.
    - Muscle: per-shard wheel is part of TPC discipline; cross-shard work goes through the channel always. **Reapplies at**: every per-shard structure (orderbook, peer-state, journal).
