**Tuesday — Jump table research + runtime-thread-per-core v0.5: io_uring backend** [NEW v2]

- [ ] Function pointer jump tables. (~30 min)
  - **Why**: Function-pointer jump table dispatch — `[fn(&mut Interpreter, &mut H); 256]` indexed by opcode — avoids match's branch-tree overhead. LLVM CAN generate jump tables from match, but only when arm count is high and contiguous; reality: revm's match generates a 200+ way branch tree, not a true jump.
  - **Read first**: revm-interpreter `instructions.rs::instruction_table` (production jump-table impl in revm); LLVM jump-table heuristics.
  - **Design**:
    ```rust
    pub type Instruction<H> = fn(&mut Interpreter, &mut H);
    pub type InstructionTable<H> = [Instruction<H>; 256];

    pub const fn instruction_table<H: Host, SPEC: Spec>() -> InstructionTable<H> {
        let mut table: InstructionTable<H> = [op_invalid; 256];
        table[0x00] = op_stop;
        table[0x01] = op_add;
        // ... 200+ ops
        table
    }

    fn run<H: Host>(interp: &mut Interpreter, host: &mut H, table: &InstructionTable<H>) {
        loop {
            let opcode = interp.bytecode[interp.ip] as usize;
            interp.ip += 1;
            table[opcode](interp, host);
            if interp.result != Continue { break; }
        }
    }
    ```
    **Invariants**:
    - Table is `const fn` evaluable at compile time per (Host, Spec) pair.
    - Unset slots default to `op_invalid` (consumes all gas, returns InvalidOpcode).
    - Each op fn signature is identical → uniform indirect-call cost.
  - **Build steps (research-only today)**:
    1. (~10 min) Document the 3 dispatch strategies: match-tree (revm/exec-vm current), jump-table (revm has both via macro), computed-goto (unsafe, asm-style).
    2. (~10 min) Predicted performance: jump-table has +1 branch-mispredict per op (indirect call vs direct branch), but no tree traversal. Per-op overhead: ~3 ns vs match's ~5 ns. Mainnet-cap wall-clock expected: -10 to -15%.
    3. (~5 min) Note that LLVM may inline op fn pointer when target known — disabled with `#[inline(never)]` on op fns to keep dispatch indirect (otherwise table effectively reverts to match).
    4. (~5 min) Tentative plan for Wed: implement, feature-flag `dispatch_jump_table`, A/B against Mon baseline.

- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/io_backend.rs` — alternative to epoll Reactor: io_uring submission/completion rings per shard. (~total 200 min across 3 phases)
  - 🔧 **Why this matters**: io_uring is Linux's modern async I/O — 2-4× throughput vs epoll for high-syscall workloads (fsync, small reads/writes), zero-copy with registered buffers, batched submission via SQE rings. Critical for the matching-engine WAL fsync path (W63+) and marketdata file persistence (W85+). Bar-(c) interview-load-bearing for any low-latency Linux work. `HashMap<u64, IoCompletion>` on the submit path or `Box<dyn FnOnce>` per completion forfeits the ENTIRE perf advantage — both are zero-alloc-discipline failures hidden by "convenient" API shapes.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: every epoll-driven syscall costs ~300 ns (kernel boundary + context save/restore); 10k fsync/sec/shard = 3 ms/s of pure syscall overhead before fsync's ~10 µs/op work. io_uring batches submissions and (with SQ_POLL) eliminates submit-side syscalls entirely — collapses 10k syscalls/sec to ~10/sec. The zero-alloc-on-the-hot-path discipline is load-bearing: a `HashMap` + `Box<dyn>` design measures ~30% faster than epoll where 2× is achievable.

  - **Requirements** — write in `crates/runtime-thread-per-core/notes/58_io_backend_design.md`:
    - R1. One `IoUring` per shard; sharing rings across threads is FORBIDDEN (defeats TPC).
    - R2. `submit_*` API methods for `read`, `write`, `fsync`, `accept`; all take a `Waker` and return a unique `u64` `user_data` cookie.
    - R3. `in_flight` storage MUST be a `slab::Slab<IoCompletion>` indexed by `u32` slot id; NOT `HashMap`. `user_data = (slot_id as u64) << 32 | generation_counter` for stale-CQE rejection after slot reuse.
    - R4. `IoCompletion` payload is a TYPED enum (`enum { Read { slot, waker }, Write { slot, waker }, Fsync { ack: AtomicWaker }, ... }`); NEVER `Box<dyn FnOnce>`.
    - R5. SQ_POLL mode optional (kernel-thread polls SQ ring → zero submit syscall). Fallback to non-poll on missing CAP_SYS_NICE.
    - R6. Fixed buffers via `register_buffers` for hot read/write paths; per-op mmap is FORBIDDEN on the hot path.
    - R7. Submit budget: ≤ 50 ns per `submit_*` with SQ_POLL engaged (no syscall path). Poll budget: ≤ 30 ns per drained CQE.
    - R8. Trait `IoBackend` abstracts epoll-backed Reactor (W30) and UringBackend so test infrastructure can pick. Feature-flag selects at compile time.
    - R9. Buffer lifetime: read SQE references buf pointer; the Rust Vec MUST outlive completion. `in_flight` slot OWNS the buf (or a refcounted Bytes); only freed on CQE drain.

  - **Design walk-through**:
    - D1. Why `slab::Slab` over `HashMap`? Walk the cost: HashMap insert is ~100 ns + occasional rehash + alloc; Slab insert is O(1) zero-alloc once warmed. At 1M ops/s/shard, that's 100 ms/s of pure map overhead PLUS rehash pauses that show as 10-100 µs p99 hiccups. Slab pre-grows to ring depth at construction.
    - D2. Why typed enum vs `Box<dyn FnOnce(i32)>` callback? Compute: 1M boxes/s × ~80 ns alloc = 80 ms/s + 32-64 B heap residency × 100k in-flight = ~1.6 MB fragmented heap. Typed enum dispatches via `match` (branch-predicted); zero alloc.
    - D3. `user_data` cookie design: write the encoding. Why `(slot_id << 32) | generation`? (Hint: stale CQE from a previously-cancelled op might arrive after the slot was reused; generation mismatch → reject.)
    - D4. SQ_POLL tradeoff: kernel thread polls the SQ ring → zero submit syscall (~300 ns saved per op). Cost: a dedicated kernel core spinning even when idle. When is SQ_POLL worth it? (Hint: when shard mailbox depth > 100 ops/tick AND core budget allows.)
    - D5. Fixed buffers vs per-op: `register_buffers` is a one-time setup that pins user memory and lets the kernel skip mmap on every op. ~30% faster on hot read/write. What's the memory cost? (Fixed-buf pool sized for steady-state in-flight, e.g. 64 × 4 KB = 256 KB.)
    - D6. **Pre-mortem**: write the 4-step path from "natural `HashMap<u64, IoCompletion>` + `Box<dyn FnOnce>` design" to "io_uring measures only 30% faster than epoll instead of 2× target." This is the load-bearing perf decision.
  - **Output**: `notes/58_io_backend_design.md` with R1–R9 + answers to D1–D6 + lifecycle diagram (submit → SQE push → kernel → CQE arrival → slot drain → waker fire).

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)

  - **When `in_flight_uses_slab_not_hashmap` finds HashMap and `fsync_throughput_2x_epoll` reports ratio 1.3×:**
    - Symptom: bench shows io_uring "only" 30% faster than epoll instead of the 2× target; flame graph shows `hashbrown::raw::resize` and `alloc::alloc` in the top 5; periodic 10-100 µs p99 hiccups from rehash.
    - Why: `HashMap<u64, IoCompletion>` for in-flight lookup. Each `submit_*` does `insert` (~100 ns + occasional rehash + alloc); each `poll` drain does `remove` (~50 ns). At 1M ops/s/shard that's 150 ms/s of pure map overhead PLUS rehash pauses showing as p99 spikes.
    - Fix: `slab::Slab<IoCompletion>` indexed by `u32` slot id; `user_data = (slot_id as u64) << 32 | generation_counter` (generation prevents stale-CQE collisions after slot reuse). `Slab::insert` is O(1) amortized and zero-alloc once warmed; `remove` is O(1) and frees the slot without dealloc. Pre-grow the slab to ring depth at construction.
    - Cost avoided: ~150 ns per op + allocation jitter; ~150 ms/s on a 1M-op shard; eliminates rehash pauses from p99 tail.
    - Muscle: any data structure on a bar-(c) hot path must be zero-allocation in steady state — `slab`/`SmallVec`/pre-sized arenas, never `HashMap`/`Vec::push`-on-grow. **Reapplies at**: W60 matching-engine `order_index` (replace AHashMap with intrusive index by W74), W74 lock-free price level node pool, W76 aeron term-buffer claim slot pool, W85 marketdata frame ring.

  - **When `io_completion_no_box_dyn` finds `Box<dyn FnOnce>` and `submit_zero_alloc` reports 1M allocs/s:**
    - Symptom: under 1M ops/s/shard, allocator is ~1M boxes/sec/shard — heap fragmentation, allocator-lock contention (even with mimalloc), 30-100 µs GC-like stalls when allocator rebalances thread caches.
    - Why: the natural completion design is `enum IoCompletion { Read { waker, callback: Box<dyn FnOnce(i32) + Send> } }`. Every submit boxes a closure (~80 ns + 32-64 B heap).
    - Fix: completion routing is TYPED, not callback-based: `enum IoCompletion { Read { slot: SlotId, waker: Waker }, Write { slot, waker }, Fsync { ack: AtomicWaker }, ... }`. Shard's `poll()` matches the variant and dispatches without closure. For Future-based wakeups, store `AtomicWaker` inline (no Box). For shard-internal acks, store a slab slot id into the shard's per-feature ack table.
    - Cost avoided: ~80 ns alloc + ~16 B heap residency per in-flight op; under 100k in-flight, ~1.6 MB fragmented heap that never gets cleanly returned to OS. Removes one of the top three allocator hot-spots on a busy shard.
    - Muscle: `Box<dyn FnOnce>` is hidden allocation per call — on bar-(c) paths replace dyn-dispatch + boxing with a small typed enum and inline state. **Reapplies at**: W60 matching-engine event handler dispatch, W74 raft RPC completion, W76 aeron flow-control credit callback, W83 ledger op handler.

  - **When `generation_rejects_stale_cqe` fires the wrong waker:**
    - Symptom: a cancelled op's stale CQE arrives after the slot has been reused for a new op; the new op's waker fires with the OLD op's result.
    - Why: `user_data = slot_id` only; no generation; reuse collides.
    - Fix: 32-bit slot + 32-bit generation. On slot reuse, generation increments; drain logic checks `(user_data >> 32) == self.slabs[slot].generation`; mismatch → drop silently (log debug).
    - Muscle: every slot-reuse design needs a generation counter; otherwise stale notifications corrupt state. Reapplies at: W74 matching-engine order slot reuse, W76+ aeron term-buffer slot reuse.

  - **When `buffer_lifetime_no_use_after_free` shows use-after-free under miri:**
    - Symptom: SEGV under valgrind, or silent corruption in production; the kernel wrote to a freed Vec.
    - Why: `submit_read(fd, &mut buf)` passes the buf pointer to SQE; the caller drops the Vec before CQE arrives; kernel writes to freed memory.
    - Fix: slot OWNS the buf — `submit_read(fd, buf: Vec<u8>)` takes ownership; stores in slot; CQE drain takes the buf back out and returns to caller (via channel or callback).
    - Muscle: any async I/O that the kernel writes to must own the buffer for the in-flight duration; passing a borrowed `&mut` is unsafe unless the lifetime is statically guaranteed. Reapplies at: W83+ ledger journal write buffers, W90+ aeron AF_XDP frame.

  - **When `sq_poll_fallback_on_no_cap` panics in a container:**
    - Symptom: in Docker without CAP_SYS_NICE, `UringBackend::new(sq_poll: true)` panics with EPERM; process won't start.
    - Why: `io_uring_setup` with `IORING_SETUP_SQPOLL` requires CAP_SYS_NICE (since kernel 5.11) or root.
    - Fix: detect EPERM from setup; log warning + fall back to non-poll mode; document deployment requirement (CAP_SYS_NICE or `--cap-add=SYS_NICE` in Docker).
    - Muscle: kernel-feature-dependent code degrades gracefully; never assume privilege. Reapplies at: W57 NUMA pinning, W90+ AF_XDP setup.

  - *Back-of-envelope*: every epoll-driven syscall costs ~300 ns (kernel boundary + context save/restore); a fsync per WAL commit is another ~10-50 µs to disk. **Target: ≥ 2× epoll throughput on a 4-shard 1M-fsync bench; per-op SQE submit ≤ 50 ns when SQ_POLL is engaged (no syscall).** At a 1M order/sec matching-engine target with one WAL fsync per batched commit, that's ~10k fsync/sec/shard — io_uring's batching collapses 10k syscalls/sec down to ~10/sec (one per CQE drain).   - **Design**:
    ```rust
    use io_uring::{IoUring, opcode, types};

    pub struct UringBackend {
        ring: IoUring,
        registered_fds: Vec<RawFd>,         // for fixed-files
        registered_bufs: Vec<Vec<u8>>,      // for fixed-bufs
        in_flight: HashMap<u64, IoCompletion>, // user_data → completion handler
        next_user_data: AtomicU64,
        sq_poll: bool,
    }

    pub enum IoCompletion {
        Read { buf_id: u32, len: i32, waker: Waker },
        Write { buf_id: u32, len: i32, waker: Waker },
        Fsync { fd: RawFd, waker: Waker },
        Accept { listener: RawFd, waker: Waker },
        // ...
    }

    impl UringBackend {
        pub fn new(entries: u32, sq_poll: bool) -> io::Result<Self> {
            let mut builder = IoUring::builder();
            if sq_poll {
                builder.setup_sqpoll(2000);  // 2s idle before kernel thread sleeps
            }
            let ring = builder.build(entries)?;
            Ok(Self { ring, ..Default::default() })
        }

        pub fn submit_read(&mut self, fd: RawFd, buf: &mut [u8], offset: u64, waker: Waker) -> io::Result<u64> {
            let ud = self.next_user_data.fetch_add(1, Relaxed);
            let entry = opcode::Read::new(types::Fd(fd), buf.as_mut_ptr(), buf.len() as u32)
                .offset(offset)
                .build()
                .user_data(ud);
            unsafe { self.ring.submission().push(&entry)?; }
            self.in_flight.insert(ud, IoCompletion::Read { /* ... */, waker });
            Ok(ud)
        }

        pub fn poll(&mut self) -> usize {
            self.ring.submit().ok();  // kick the kernel
            let mut completed = 0;
            for cqe in self.ring.completion() {
                if let Some(comp) = self.in_flight.remove(&cqe.user_data()) {
                    comp.complete(cqe.result());
                    completed += 1;
                }
            }
            completed
        }
    }
    ```
    **Invariants**:
    - One IoUring per shard (sharing rings across threads requires synchronization → defeats TPC).
    - `user_data` is the cookie: must uniquely identify completion → handler. Reuse causes false completion.
    - SQ_POLL = kernel thread polls SQ ring → no syscall for submit → 50-200ns savings per op; cost: kernel CPU even when idle.
    - Fixed buffers (`register_buffers`) skip per-op mmap → ~30% faster.
    - Completion order ≠ submission order. Don't assume.

**Thursday — Computed goto research**

- [ ] Unsafe computed goto via asm. Portability tradeoffs. (~30 min)
  - **Why**: Computed goto (GCC's `&&label` syntax) lets you encode opcode dispatch as direct jumps embedded inline at the END of each opcode's body. Result: zero centralized loop, every op tail-jumps directly to the next. Predicts better than jump-table (each op has its own BTB entry → less aliasing). Used by CPython, V8, evmone-advanced. Rust has NO direct equivalent; closest is `#[inline(always)] tail-call` (unstable) or hand-written `asm!`.
  - **Read first**: CPython's `Python/ceval.c` `USE_COMPUTED_GOTOS` block; evmone-advanced `lib/evmone/advanced_execution.cpp::dispatch`; Eli Bendersky "Computed goto for efficient dispatch tables" article; Rust unstable `become` (RFC 3407) tail-call.
  - **Design** (Rust approximation):
    ```rust
    // Goal: each op fn ENDS with a jump directly to next op, not return to dispatcher.
    // Rust stable doesn't allow this. Options:
    //   1. become op_table[next_op](interp, host);  // unstable
    //   2. Manual asm!("jmp {}", in(reg) op_fn_ptr); // unsafe, x86-only
    //   3. Stay with jump-table; rely on LLVM tail-call optimization (lots of inlining).
    ```
    **Tradeoffs**:
    - **Portability**: option 2 (asm) ties exec-vm to x86_64. Loses ARM (M-series Macs, AWS Graviton).
    - **Maintenance**: each opcode body becomes inline-asm-wrapped; massive code-bloat.
    - **Realized speedup vs jump-table**: 5-10% on tight arithmetic loops; 0% on memory-heavy. Not worth the maintenance cost unless mainnet-cap shows ≥ 5% gain.
    - **Cargo culting risk**: CPython is interpreted bytecode; EVM is too. But CPython's win partly comes from minimizing intra-op variance, which doesn't map cleanly to EVM where gas-cost-tracking is uniform.

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: a `BinaryHeap`-based timer queue is O(log n) per schedule/cancel and O(n) for cancel-by-id; at 10k timers, that's ~14 compares per op AND a linear cancel scan = ~200 µs/cancel. Timer wheel collapses to O(1) amortized. But naive `Box<dyn FnOnce>` callbacks per entry alloc 10k boxes at startup + heap-stress the wheel; cascade ticks with 1000+ entries spike p99 by 30 µs. Both are bar-(c) violations hidden in "convenient" APIs.

  - **Requirements** — write in `crates/runtime-thread-per-core/notes/58_timer_design.md`:
    - R1. Hierarchical hashed wheel: 5 levels of 64 slots; level i granularity = `(1 ms) × 64^i`. Level 0 covers 0..64 ms; level 4 covers ~580 M years. All times in u64 ticks (1 ms each).
    - R2. `schedule(deadline_ticks, payload)` returns `TimerId`; computes level from `delta = deadline - current_tick`, slot from `(deadline >> (6 * level)) & 63`.
    - R3. `cancel(id)` is O(1) via `timer_index: HashMap<TimerId, (LevelIdx, SlotIdx, position_in_slot)>` lookup → swap-remove from slot Vec.
    - R4. `tick(now_ticks)` advances `current_tick`; expires entries in level-0 slot; cascade level+1 when level-0 wraps.
    - R5. `TimerEntry` payload is TYPED enum (`enum TimerPayload { ExpireOrder { id }, RaftElection { node }, P2pIhave { peer }, Keepalive { conn }, ... }`); NEVER `Box<dyn FnOnce>`.
    - R6. Cascade work AMORTIZED across multiple ticks: split cascade slot's entries over the next 64 level-0 ticks (1/64 per tick); prevents the 30 µs cascade burst.
    - R7. Tick miss recovery: `tick(now)` loops `while current_tick < now { advance_one(); }` to catch up after a long opcode.
    - R8. Far-future cap: `deadline > u64::MAX / 2` rejected with explicit error.
    - R9. Hot path budgets: schedule ≤ 100 ns, cancel ≤ 100 ns, steady tick ≤ 1 µs, cascade tick (amortized) ≤ 1 µs.
    - R10. Slot Vec uses `Vec<TimerEntry>` (not `Box<TimerEntry>`); swap-remove on cancel; updates `timer_index` for the swapped entry.

  - **Design walk-through**:
    - D1. Hierarchical wheel layout: 5 levels × 64 slots. Write the schedule formula. Why 64 slots per level (= 6 bits)? (Hint: shift + mask = ~3 ns; smaller fanout = more cascades, larger = wasted slots.)
    - D2. Cascade mechanics: when level-0 wraps, take next level-1 slot, reschedule entries DOWN to level-0 (now within 64 ticks).   - **Design**:
    ```rust
    // Hierarchical hashed timer wheel. Like Linux: 5 levels of 64 slots.
    // Level 0: 64 slots × 1ms granularity → covers 0..64ms
    // Level 1: 64 slots × 64ms granularity → covers 64..4096ms
    // Level 2: 64 slots × 4096ms granularity → covers ~4s..262s
    // Level 3, 4: progressively coarser
    pub struct TimerWheel {
        levels: [Level; 5],
        current_tick: u64,          // counted in 1ms units since epoch
        tick_duration: Duration,
        timer_index: HashMap<TimerId, (LevelIdx, SlotIdx, usize /*position in slot*/)>,
        next_id: AtomicU64,
    }
    pub struct Level {
        slots: [Vec<TimerEntry>; 64],
        slot_mask: usize,           // 63
    }
    pub struct TimerEntry {
        id: TimerId,
        deadline: u64,              // absolute tick
        callback: Box<dyn FnOnce() + Send>,
    }
    ```
    **Invariants**:
    - All times in ticks (u64, 1ms each). Roll over after ~580M years.
    - Schedule: compute `delta = deadline - current_tick`; pick level by leading-zeros of delta; slot = `(deadline >> (6 * level)) & 63`.
    - Tick: advance level 0 by one slot; expire all entries in that slot. When level 0 wraps (every 64 ticks), cascade level 1: take next slot from level 1, RESHEDULE its entries into level 0 (now they're within 64ms).
    - Cancel: O(1) via timer_index lookup → slot remove (O(slot_size) typical).
  - **Build steps** (granular):
    1. (~20 min) `TimerWheel::new(tick_duration: Duration)` allocates 5 × 64 slots.
    2. (~25 min) `schedule(deadline: u64, callback) -> TimerId`: compute level from delta, slot from deadline bits, append to Vec, register in timer_index.
    3. (~20 min) `cancel(id: TimerId) -> bool`: lookup index, remove from slot Vec (swap-remove for O(1)).
    4. (~25 min) `tick(now: u64)`: advance current_tick; for each level wrap, cascade entries from level+1 down to level 0.
    5. (~20 min) Tests: 10k scheduled timers, advance time, verify all fire within 1 tick of deadline.
    6. (~10 min) Cancel under contention: schedule 1k, cancel 500 randomly, verify only 500 fire.
  - **Pitfalls** (named, data-structure):
    - *Cascade thrash*: every 64 ticks, level 1's next slot may contain 1000+ entries — reschedule overhead spikes. **Symptom**: periodic 1ms-resolution latency spike. **Fix**: amortized — average remains O(1); but for HFT critical path, use hierarchical wheel from W74 with 4 levels of 256 slots for smoother distribution.
    - *Far-future timer*: deadline > 580M years → overflow. Adversarial input. **Symptom**: timer never fires. **Fix**: cap deadline at u64::MAX / 2 with explicit error.
    - *Drift on tick miss*: if the shard's tick() isn't called for 5ms (e.g., long opcode), 5 ticks of timers fire all at once. **Symptom**: latency burst. **Fix**: in tick, loop `while current_tick < now { advance_one(); }` to catch up.
    - *Slot-removal cost*: cancel does swap-remove; if slot has 10k entries, swap-remove still O(1). But it updates timer_index for the swapped entry — easy to forget. **Symptom**: cancelled-but-still-fires bug or wrong-callback-fires bug. **Fix**: after swap-remove, update timer_index[swapped_id].
    - *Cross-shard schedule*: scheduling timer for another shard requires cross-shard message → reschedule overhead. **Symptom**: timer fires on wrong shard. **Fix**: per-shard wheel; cross-shard timer goes through cross_shard channel (W57).

    - Tick miss: simulate 100ms gap in tick(); verify catch-up fires all elapsed timers in single tick() call.
