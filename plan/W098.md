  - *Mental model*: an MVCC store keeps a **chain of timestamped versions per key**; a transaction reads against a frozen snapshot (a timestamp + a set of in-flight IDs to ignore) so readers never block writers, and validates at commit that no conflicting version landed in its window. It exists so 16 threads of mixed reads/writes get ACID isolation without a global lock.
  - *Contract* (signatures only — never the body):
    ```rust
    enum Iso { SnapshotIsolation, Serializable }
    struct Snapshot { ts: TxnId, running: RoaringTreemap /* BEGIN ids in-flight at capture; ignore their versions even if version.ts <= snapshot.ts */ }
    // Each committed version is keyed at (commit_ts, writer_begin_id) (R12): commit_ts is the visibility key,
    // writer_begin_id is what the running-set is checked against. The two are deliberately distinct facts.
    enum Versioned { Value(Bytes), Tombstone }   // mini-db-specific; the visibility filter is over THIS
    struct Txn { /* snapshot, write_set, read_set, iso, !Clone */ }
    impl Txn {
        fn begin(iso: Iso) -> Txn;                     // captures snapshot ts + running-set via TxnManager
        fn get(&mut self, key: &[u8]) -> Option<Bytes>;// write_set FIRST, then snapshot.read; SER records read_set
        fn put(&mut self, key: &[u8], val: Bytes);     // stages to write_set; never touches engine
        fn delete(&mut self, key: &[u8]);              // stages a Tombstone
        fn commit(self) -> Result<TxnId, TxnError>;    // CONSUMES self; OCC validate -> commit_ts -> WAL batch -> apply
        fn abort(self);
        #[cfg(test)] fn snapshot_ts(&self) -> TxnId;   // test-only: expose snapshot.ts for trap tests
        #[cfg(test)] fn running_contains(&self, id: TxnId) -> bool; // test-only: expose snapshot.running membership
    }
    impl Snapshot { fn read(&self, key: &[u8]) -> Option<Bytes>; } // walks chain newest->oldest, visibility filter
    impl MiniDb {
        #[cfg(test)] fn latest_version_ts(&self, key: &[u8]) -> TxnId; // test-only: the ts the newest committed version of `key` is KEYED at (== commit_ts per R12)
        #[cfg(test)] fn with_mock_hlc(clock: MockHlc) -> MiniDb;       // test-only: inject a clock so a test can force commit_ts
    }
    enum TxnError { WriteWriteConflict, ReadSetChanged, TxnTooOld }
    ```
  - *Back-of-envelope* (bar (b) — sizing the visibility walk + commit cost, so we know where the budget goes): a snapshot read walks the version chain newest→oldest until the first visible version. Cold chain entry = **main-memory ~100 ns**; a chain of depth D unGC'd costs **~D × 100 ns** — this is exactly why GC (Wed) is not optional: a 1000-deep chain is ~100 µs/read, a 1000× cliff over a 1-deep chain (~100 ns). The commit path is dominated by **one WAL fsync (~300 µs-1 ms on SSD, the whole budget)**; the OCC validation (a handful of `lsm::versions_for` lookups, ~100 ns each) and memtable apply (~50 ns/key) are noise beside fsync. Implication: batch all of a txn's writes into ONE `wal::Batch` = ONE fsync; never fsync per key.
  - *Anti-shortcut audit* — name the tempting-but-wrong move (each is exactly what a Phase-2 test below must fail on):
    - **Snapshot = `ts` alone (no running-set).** Wrong: a txn that was IN-FLIGHT at your snapshot instant but whose `commit_ts` later lands ≤ your `snapshot.ts` must still be ignored even after it commits — `version.ts ≤ snapshot.ts` makes its version falsely visible, because the ts bound alone cannot tell "committed before my snapshot" from "concurrent with my snapshot but committed at/below my snapshot ts". The running-set names exactly those concurrent writers by BEGIN id. Note `test_snapshot_isolation_basic` does NOT catch this (there the competing commit_ts > snapshot.ts, so `ts`-alone also returns None); the dedicated trap is → `test_snapshot_ignores_concurrent_lower_id_inflight_commit`, which FORCES the concurrent writer's commit_ts ≤ snapshot.ts (via MockHlc) and asserts it so the running-set is the only thing left that can exclude it.
    - **`get()` reads snapshot first, write_set never (or last).** Wrong: the txn's own uncommitted writes live only in `write_set`; snapshot.read sees committed versions only. → trapped by `test_read_your_own_writes`.
    - **OCC validates read-set freshness but skips write-write conflicts under SI.** Wrong: lost-update is prevented ONLY by the W-W check; read-set revalidation is a Serializable add-on. → trapped by `test_lost_update_aborts_under_si`.
    - **WAL: append each `Put` as its own record + fsync.** Wrong: a `kill -9` mid-loop leaves N of M keys durable with no `TxnCommit` marker → partial commit survives recovery. → trapped by `test_recovery_aborted_txn_state_lost`.
    - **Re-implement visibility/commit/WAL-batch logic natively in mvcc.rs.** Wrong: it's already in `txn::TxnManager` + `wal::Batch`; native re-impl blows the LOC budget and drops the inheritance ratio below 0.70. → trapped by `test_inheritance_loc_under_400`.

  - **Requirements** — write in `crates/mini-db/notes/98mon_mvcc_design.md`:
    - R1. `Txn::begin(iso) -> Txn` captures snapshot `ts` + `running` set; HLC-assigned begin id via `txn::TxnManager`.
    - R2. `Snapshot::read(key)` walks the version chain newest→oldest; a version is visible iff `version.ts ≤ snapshot.ts && !running.contains(version.writer_begin_id)`. Here `version.ts` is the version's COMMIT timestamp (R12) and `version.writer_begin_id` is the BEGIN id of the txn that wrote it; `running` holds the BEGIN ids in-flight at snapshot capture — so the two clauses test different facts and neither subsumes the other. (When a writer's commit_ts > every active snapshot's ts, the begin-id check is redundant; it bites ONLY when a concurrent writer's commit_ts landed ≤ a snapshot's ts, which is the running-set trap.)
    - R3. `Txn::get` checks `write_set` FIRST (read-your-own-writes), then `snapshot.read`; under Serializable, records the key + observed-version into `read_set`.
    - R4. `Txn::put/delete` stage to `write_set` (delete stages a `Tombstone`); never touch the engine before commit.
    - R5. `Txn::commit(self)` consumes self: OCC validation → HLC `commit_ts` → ONE `wal::Batch` (TxnBegin + writes + TxnCommit) → **fsync** → memtable apply → `txn_manager.commit`. WAL fsync BEFORE memtable apply.
    - R6. Recovery: a `TxnBegin` without a matching `TxnCommit` is aborted (its staged writes discarded).
    - R7. Lost-update (Postgres-style): T1 reads K=10, T2 reads K=10, T1 commits K=11, T2 commits K=11 — under SI exactly one commits; the other aborts with `WriteWriteConflict`.
    - R8. Write-skew (canonical SI anomaly): T1/T2 commit on disjoint write keys; under SI both commit (document as expected); under Serializable + read-set revalidation exactly one aborts with `ReadSetChanged`.
    - R9. 100k mixed read/write txns at 16 threads under SI: commit rate ≥ 95% on 1k-key (low-conflict), ≥ 70% on 100-key (medium-conflict).
    - R10. Inheritance: `mvcc.rs` ≤ 400 LOC native; delegates to `txn::TxnManager` + `lsm::versions_for` + `wal::append_batch` + `time::HlcClock`.
    - R11. Long-running txn doesn't block GC forever: `max_txn_age` aborts txns older than the threshold; next op returns `Err(TxnTooOld)`.
    - R12. **Version keying is by `commit_ts`, never by begin id.** When `commit(self)` applies a write, each new version is stamped with the txn's HLC `commit_ts` (assigned at validation time, R5), so `version.ts == commit_ts`. This is the load-bearing invariant the running-set trap depends on: it makes `running` (a set of BEGIN ids) genuinely orthogonal to the `ts ≤ snapshot.ts` bound (a comparison of COMMIT ts), so a concurrent lower-id txn whose `commit_ts ≤ snapshot.ts` can ONLY be excluded by the running-set, not by the ts bound. A first attempt that keys versions at the begin id instead collapses the two clauses and is exactly what `test_snapshot_ignores_concurrent_lower_id_inflight_commit` (via its `latest_version_ts` setup assertion) catches.

  - **Design walk-through** D1–D10 — answer each in the design doc; no peeking at Postgres `snapmgr.c` or CockroachDB `mvcc.go` until Phase 3:
    - D1. Snapshot semantics: `ts: TxnId` + `running: RoaringTreemap<TxnId>` (begin ids). Why BOTH? (Versions are keyed at commit_ts (R12); `ts` alone misses a txn that was IN-FLIGHT at snapshot capture but whose commit_ts later landed ≤ snapshot.ts — the running-set holds that writer's BEGIN id and says "ignore its versions even if their commit_ts ≤ snapshot.ts". This matches Postgres `xmin`/`xmax`/`xip[]` exactly: `xip[]` is begin ids, the visibility bound is commit ts.)
    - D2. HLC monotonicity: `commit_ts` MUST be > the snapshot ts of any active reader. `HlcClock::tick_logical()` guarantees this by bumping past `max(physical, last_observed)`. What is "lost update" in ts terms? (Two committed writes to the same key whose commit windows overlap a shared snapshot.)
    - D3. OCC validation: under SI, check write-write conflicts ONLY — for each key in `write_set`, is there any version with `ts ∈ (snapshot.ts, commit_ts]`? If yes, abort. Under Serializable, ALSO re-read every `read_set` key at commit time; abort on any change.
    - D4. WAL batch atomicity: TxnBegin + N Put/Delete + TxnCommit as ONE fsync. Why? (Recovery sees all-or-none; partial means aborted.) What if WAL fsync succeeds but memtable apply panics mid-loop? (Next get returns a mix of new/old — corruption. Mitigation: `memtable_put_versioned` is infallible after the WAL fsync.)
    - D5. Read-your-own-writes: `write_set` check is FIRST in `get()`. Why not always go to snapshot? (Snapshot read won't see this txn's own writes — they haven't been applied to the memtable yet.)
    - D6. Phantom reads: T1 scans, T2 inserts a new row, T1 re-scans, sees a phantom. SI does NOT prevent this — document. Predicate-locking or SSI (Cahill 2008) would, but is out of scope for v1.0.
    - D7. Write-skew (canonical SI anomaly): T1 reads A,B writes A; T2 reads A,B writes B. Both commit under SI (different keys, no W-W conflict). Under Serializable: T1's `read_set` includes B; T2 commits B; T1's revalidation re-reads B, sees the change, aborts.
    - D8. Commit consumes self: `pub fn commit(self) -> Result<TxnId, TxnError>` — caller can't reuse the Txn; `abort` likewise consumes. Make `Txn` `!Clone`. Why? (Prevents write-after-commit silent corruption — the type system, not a runtime check, enforces single-use.)
    - D9. Long-running txn: holds a running-set slot, pins `min_active_snapshot_ts`, blocks GC. After `max_txn_age` (e.g. 5 min) `txn_manager` aborts it; next op returns `Err(TxnTooOld)`.
    - D10. **Pre-mortem (load-bearing)** — write the EXACT 6-step interleaving where a missing read-set revalidation under Serializable admits write-skew, and the invariant "A+B ≥ 0" is broken:
      ```
      invariant: A + B >= 0, start A=1 B=1
      1. T1.begin(Serializable); reads A=1, B=1          (read_set = {A@v1, B@v1})
      2. T2.begin(Serializable); reads A=1, B=1          (read_set = {A@v1, B@v1})
      3. T1.put(A, 0)            (write_set = {A})        // T1 plans: A goes to 0, B still 1 -> sum 1, ok
      4. T2.put(B, -1)           (write_set = {B})        // T2 plans: A still 1, B goes -1 -> sum 0, ok
      5. T1.commit()  -> Ok      // W-W check: no other writer of A -> passes. read_set NOT revalidated -> bug
      6. T2.commit()  -> Ok      // W-W check: no other writer of B -> passes. read_set NOT revalidated -> bug
         RESULT: A=0, B=-1 -> sum = -1 -> invariant VIOLATED (a schedule impossible under any serial order)
      ```
      What test catches it? (`proptest_serializable_matches_sequential`: assert the committed result equals SOME sequential schedule's result; the above is impossible serially.)

  Each test is engineered so a common naive impl FAILS it. Tier annotated; the three required trap shapes are tagged.

  - [ ] **(SENIOR · negative-control / test-the-test)** `test_snapshot_isolation_basic` — proves a snapshot actually freezes the read view. T1 begins, then T2 puts K=1 and commits, then T1 reads K. Assert T1 sees the pre-T2 value (`None` here). A `ts`-alone snapshot that re-reads live state would return `Some(1)` and fail loudly — proving the test bites. Exercises R1, R2.
    ```rust
    #[test]
    fn test_snapshot_isolation_basic() {
        let db = MiniDb::open_tmp();
        let mut t1 = db.begin(Iso::SnapshotIsolation);     // snapshot frozen here
        let mut t2 = db.begin(Iso::SnapshotIsolation);
        t2.put(b"K", Bytes::from_static(b"1"));
        t2.commit().unwrap();                              // K=1 now committed at commit_ts > t1.snapshot.ts
        assert_eq!(t1.get(b"K"), None,
            "T1's snapshot was frozen before T2 committed; a ts-alone snapshot wrongly returns Some(1)");
    }
    ```
  - [ ] **(EXPERT · anti-shortcut)** `test_snapshot_ignores_concurrent_lower_id_inflight_commit` — the dedicated running-set trap: it isolates the ONE interleaving where `(ts, running)` and `ts`-alone diverge, and it **pins its own discriminating condition with an explicit setup assertion** so it cannot false-green. Versions are keyed at `commit_ts` (R12), so the trap can no longer ride on an unstated begin-id-relabeling: the test instead injects a `MockHlc` and FORCES T_a's `commit_ts ≤ T_b.snapshot.ts`, then asserts that fact (`db.latest_version_ts(b"K") <= t_b.snapshot_ts()`) BEFORE the final `get`. If any impl fails to make T_a's committed version land at a ts ≤ T_b.snapshot.ts, the test fails LOUDLY at the setup assert (a fail-to-setup, not a false green) rather than silently passing because a `ts`-alone filter happened to return `None`. With the discriminator pinned, the ONLY thing that can correctly exclude T_a's version is the running-set: a `ts`-alone filter (`version.ts ≤ snapshot.ts`) WRONGLY returns `Some("a")`; the correct `version.ts ≤ snapshot.ts && !running.contains(T_a.begin_id)` returns `None` because T_a's BEGIN id was in T_b's running-set at capture. This is the test the file's most-taught concept (snapshot needs `(ts, running)`, P1/D1/anti-shortcut bullet 1/card 2) actually depends on — `test_snapshot_isolation_basic` cannot catch it (there T_a's commit_ts > T_b.snapshot.ts, so `ts`-alone also returns None and passes). Exercises R1, R2, R12, D1.
    ```rust
    #[test]
    fn test_snapshot_ignores_concurrent_lower_id_inflight_commit() {
        // Inject a clock we control so we can FORCE T_a's commit_ts <= T_b.snapshot.ts.
        let mock = MockHlc::new();
        let db = MiniDb::with_mock_hlc(mock.clone());
        // T_a begins first: it gets the LOW begin id and stays in-flight.
        let mut t_a = db.begin(Iso::SnapshotIsolation);
        let a_begin = t_a.snapshot_ts();                    // T_a's BEGIN id, e.g. 10
        // T_b begins AFTER T_a, so T_b.snapshot.ts >= a_begin; crucially a_begin is in T_b's running-set.
        let t_b = db.begin(Iso::SnapshotIsolation);
        let b_snap = t_b.snapshot_ts();                     // e.g. 11
        assert!(b_snap >= a_begin, "T_b began after T_a");
        assert!(t_b.running_contains(a_begin),
            "T_a was in-flight when T_b began -> its BEGIN id must be in T_b's running-set");
        // Force T_a's commit_ts to fall AT OR BELOW T_b's snapshot ts. With a real HLC the commit_ts
        // would exceed b_snap; we pin the clock so the divergence condition (version.ts <= b_snap) holds.
        mock.set_next_commit_ts(b_snap);                    // T_a will commit AT b_snap
        t_a.put(b"K", Bytes::from_static(b"a"));
        t_a.commit().unwrap();
        // DISCRIMINATOR (fail-to-setup if violated): the version T_a wrote must be keyed at a ts <= b_snap,
        // otherwise a ts-alone filter would also return None and the trap would be vacuous.
        assert!(db.latest_version_ts(b"K") <= b_snap,
            "trap precondition broken: T_a's version is keyed at {} but must be <= T_b.snapshot.ts {} \
             (did you key versions at commit_ts per R12, and did set_next_commit_ts take effect?)",
            db.latest_version_ts(b"K"), b_snap);
        // With version.ts <= b_snap pinned, ONLY the running-set can exclude T_a:
        //   ts-alone filter  -> version.ts (<= b_snap) passes -> WRONGLY Some("a")
        //   (ts, running)    -> running.contains(T_a.begin_id) -> correctly None
        let mut t_b = t_b;
        assert_eq!(t_b.get(b"K"), None,
            "T_a was concurrent (in-flight, lower begin id) at T_b's begin; its version ts <= \
             T_b.snapshot.ts, so the ts bound CANNOT exclude it — only the running-set can. \
             A ts-alone snapshot wrongly returns Some(\"a\").");
    }
    ```

**Wednesday — mini-db GC (version reclamation)**

- [ ] **Build**: `crates/mini-db/src/gc.rs` — `GcWorker` runs every N seconds, drops versions older than `min_active_snapshot_ts`, coordinating with `txn_manager`'s active-set. (~total 2.5 hrs across 3 phases)
