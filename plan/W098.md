- [ ] **Build**: `crates/mini-db/src/mvcc.rs` — `Txn::begin() -> Snapshot` via `txn::TxnManager`. Each key-value pair carries an HLC timestamp. Snapshot Isolation with optional Serializable upgrade. (~total 3.5 hrs across 3 phases)
  - 🔧 **Why this matters**: **MVCC is the single most-interview-load-bearing module of the whole journey.** It's the answer to "how does your DB do concurrent reads/writes without locking the world?" at every staff-level systems interview. Snapshot Isolation via per-version HLC timestamps is the same pattern as Postgres, CockroachDB, TiKV, FoundationDB, Spanner — get it right here and you can explain any of them. Downstream consumers: W98 Tue snapshot isolation test, W98 Wed GC (consumes min_active_snapshot_ts), W99 raft path (commit submits wal::Batch through raft), W100 chaos suite + knossos linearizability, W102 vector-db txns.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: concurrent transactions need ACID without serializing the world. Per-key version chains tagged with HLC ts let readers see a consistent snapshot without blocking writers; OCC validation at commit detects conflicts; HLC ensures cross-shard ordering. The mistakes are subtle: phantoms under SI (allowed, document); write-skew under SI (allowed, document); lost-update under SI must abort (correctness); read-your-own-writes (must work).

  - **Requirements** (write in `crates/mini-db/notes/98mon_mvcc_design.md`):
    - R1. `Txn::begin(iso) -> Txn` captures snapshot ts + running-set; HLC-assigned begin id.
    - R2. `Snapshot::read(key)` walks version chain newest→oldest; visible iff `ts ≤ snapshot.ts && !running.contains(ts)`.
    - R3. `Txn::get` checks write_set FIRST (read-your-own-writes); then snapshot.read; for Serializable, adds key to read_set.
    - R4. `Txn::put/delete` stages to write_set; never touches engine before commit.
    - R5. `Txn::commit(self)` consumes self; OCC validation → HLC commit_ts → WAL batch (begin + writes + commit) → fsync → memtable apply → txn_manager.commit. WAL fsync BEFORE memtable.
    - R6. Recovery: TxnBegin without matching TxnCommit = aborted (state discarded).
    - R7. Lost-update test (Postgres-style): T1 reads K=10, T2 reads K=10, T1 commits K=11, T2 commits K=11 — T2 MUST abort under SI.
    - R8. Write-skew (SI anomaly): T1/T2 both commit on disjoint write keys; document as expected SI behavior; Serializable + read-set validation aborts one.
    - R9. 100k mixed read/write txns at 16 threads under SI: commit rate ≥ 95% on 1k-key workload (low conflict), ≥ 70% on 100-key (medium).
    - R10. Inheritance: mvcc.rs ≤ 400 LOC native; calls into txn::TxnManager + lsm::versions_for + wal::append_batch + time::HlcClock.
    - R11. Long-running txn doesn't block GC forever: `max_txn_age` aborts txns older than threshold.

  - **Design walk-through** — answer each; no peeking at Postgres `snapmgr.c` or CockroachDB `mvcc.go` until Phase 3:
    - D1. Snapshot semantics: `ts: TxnId` + `running: RoaringTreemap<TxnId>`. Why both? (ts alone misses txns that BEGAN before snapshot but committed after — their commit_ts ≤ snapshot.ts would falsely make them visible. Running-set captures "ignore these IDs even if ts ≤ snapshot.ts".) This matches Postgres xmin/xmax exactly.
    - D2. HLC monotonicity: commit_ts MUST be > snapshot ts of any active reader. HLC.tick_logical() guarantees this by bumping past max(physical, last_observed). What's "lost update"? (Two writes with same commit_ts on same key.)
    - D3. OCC validation: under SI, check write-write conflicts only (any version of K with ts in (snapshot.ts, commit_ts]? Abort.) Under Serializable, also re-read read-set at commit time; abort on any change.
    - D4. WAL batch atomicity: TxnBegin + N Put/Delete + TxnCommit as one fsync. Why? (Recovery either sees all-or-none; partial means aborted.) What if WAL fsync succeeds but memtable apply panics mid-loop? (Next get returns mix of new/old; bad. Mitigation: memtable_put_versioned is infallible after WAL.)
    - D5. Read-your-own-writes: write_set check is FIRST in get(). Why not always go to snapshot? (Snapshot read won't see this txn's own writes — they haven't been applied to memtable yet.)
    - D6. Phantom reads: T1 scans, T2 inserts new row, T1 re-scans, sees phantom. SI doesn't prevent. Document. Predicate-locking or SSI (Cahill 2008) would but out of scope v1.0.
    - D7. Write-skew (canonical SI anomaly): T1 reads A,B; writes A; T2 reads A,B; writes B. Both commit under SI. Why? (Different keys, no W-W conflict.) Under Serializable: T1's read_set includes B; T2 commits B; T1's validation re-reads B, sees change, aborts.
    - D8. Commit consumes self: `pub fn commit(self) -> Result<TxnId>` — caller can't reuse Txn. Abort same. Make Txn `!Clone`. Why? (Prevents write-after-commit silent corruption.)
    - D9. Long-running txn: holds running-set slot; pins min_active_snapshot_ts; GC can't reclaim. After `max_txn_age` (e.g., 5 minutes), txn_manager aborts; next op returns `Err(TxnTooOld)`.
    - D10. **Pre-mortem (load-bearing)**: write the 6-step interleaving where a missing read_set check in Serializable allows write-skew. T1 reads A=0, B=0; T1 writes A=1, planning commit; T2 reads A=0, B=0; T2 writes B=1, commits; T1 commits without re-reading B. Both commits succeed. Result: invariant "A+B=0" violated. What test catches? (Property: under Serializable, no schedule produces a result impossible under any sequential ordering.)

  - **Output**: `notes/98mon_mvcc_design.md` with R1–R11 + D1–D10 + visibility-filter pseudocode + commit-phase state diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~150 min)

  - **When `test_lost_update_aborts_under_si` shows both commits succeed:**
    - Symptom: T1 commits K=11; T2 commits K=11; both return Ok. The second commit should have aborted because T1's commit happened in T2's snapshot's "future window" but T2 wrote the same key.
    - Why: OCC validation didn't check write-write conflicts. The validator passes because at T2's snapshot ts (before T1's commit), there was no other version. But by T2's commit time, T1 had inserted a version at commit_ts > T2.snapshot.ts.
    - Fix: at commit, for each key in write_set, query lsm for any version with ts > snapshot.ts. If found, abort with `Err(WriteWriteConflict)`. Add the assertion to txn_manager.validate.
    - Muscle: SI's W-W conflict detection is the ONLY thing preventing lost-update. Reapplies at: every MVCC system, W99 raft replication.

  - **When `test_read_your_own_writes` returns NotFound:**
    - Symptom: txn.put(K, 1); txn.get(K) → None. Test fails.
    - Why: get() goes straight to snapshot.read which only sees committed versions; the local write is in write_set but get() doesn't check it.
    - Fix: get() FIRST checks write_set.lock().get(key); if present, return that value (including None for tombstone). Only if absent, fall through to snapshot.read.
    - Muscle: every txn API must respect intra-txn writes; the local stage is the source of truth within the txn. Reapplies at: W99 raft txn API, W102 vector-db txns.

  - **When `proptest_serializable_matches_sequential` finds a write-skew counterexample under Serializable:**
    - Symptom: 4-op sequence under Serializable produces result impossible under any sequential ordering — write-skew slipped through.
    - Why: Serializable validation re-reads only the keys present in read_set at the END of the txn. But if T1 read A,B and then wrote A, the read of B was "earlier" — what if T2 commits B between T1's read and T1's commit? T1's read_set has B; revalidation should detect.
    - Fix: re-read every key in read_set at commit time; for each, check current visible version vs version recorded at original read; mismatch = abort. Make sure read_set captures every get/scan key, not just direct gets.
    - Muscle: Serializable's read-set revalidation is the load-bearing anti-write-skew mechanism; partial coverage = partial isolation. Reapplies at: W99 raft Serializable, W100 chaos.

  - **When `test_recovery_aborted_txn_state_lost` shows partial commits surviving:**
    - Symptom: txn writes 10 ops, kill -9 mid-WAL append; recovery; get reveals 7 of 10 keys (the ones that made it to WAL before crash).
    - Why: WAL batch wasn't atomic — records appended individually; recovery treats each Put as committed even without TxnCommit marker.
    - Fix: WAL append_batch is atomic at the WAL layer (single fsync after all records or none). Recovery's analysis pass tracks active txns from TxnBegin; only Put/Delete with matching TxnCommit are redone; rest discarded.
    - Muscle: txn atomicity needs WAL batch + TxnCommit marker; partial records without commit marker are aborted. Reapplies at: W99 raft replication, W100 chaos crash mid-commit.

  - **When `test_inheritance_loc_under_400` reports mvcc.rs at 800 LOC:**
    - Symptom: tokei shows mvcc.rs at 800 LOC native; inheritance ratio drops below 0.70 at W100 audit.
    - Why: visibility logic duplicated from txn::TxnManager; commit flow re-implements WAL batching that wal::append_batch already does.
    - Fix: delegate to txn::TxnManager.snapshot_with_clock(), .validate(), .commit(), .abort(). Visibility filter inlined here (it's specific to mini-db's Versioned enum). WAL batch is wal::Batch::new() + push + append_batch.
    - Muscle: inheritance ratio is the audit's load-bearing metric; native LOC budget forces delegation. Reapplies at: every CAPSTONE module audit.

  - **5-year failure mode** (write in `notes/98mon_mvcc_followup.md`): when txn rates exceed 1M/sec, OCC abort rate climbs above 30% on contended keys (the classic OCC limitation). Migration: hybrid OCC+2PL — hot keys auto-detected use 2PL (no abort); cold keys use OCC (fast path). Trigger: TXN_ABORT_RATE > 15% for 24 hours.

  - **Reference material** (consult during Phase 3 review): Postgres `src/backend/utils/time/snapmgr.c` (GetSnapshotData), CockroachDB `pkg/storage/mvcc.go`, skyzh mini-lsm Week 3 MVCC chapter, Berenson et al. 1995 "A Critique of ANSI SQL Isolation Levels", Kung & Robinson 1981 OCC paper, `crates/txn/src/lib.rs` (W42), `crates/time/src/hlc.rs` (W6).

**Wednesday — mini-db GC**

- [ ] **Build**: `crates/mini-db/src/gc.rs` — `GcWorker` runs every N seconds, drops versions older than `min_active_snapshot_ts`. Coordinates with txn_manager's active-set. (~total 2.5 hrs across 3 phases)
  - 🔧 **Why this matters**: without GC the version chain grows unbounded; reads slow down (more chain to walk) and disk fills. Naive GC drops versions still referenced by long-running snapshots → spurious None returns. The `min_active_snapshot_ts` low-watermark protocol is the standard fix. Downstream consumers: W100 chaos tests run GC concurrent with kill -9; vector-db W101 inherits same pattern.

  #### Phase 1 — Problem, requirements, design (~40 min)

  - **Requirements** (write in `notes/98wed_gc_design.md`): (R1) GC drops versions with `ts < min_active_snapshot_ts` (strictly less; boundary safe to keep); (R2) watermark read atomically; (R3) GC may run concurrently with compaction (lsm-core serializes via its own lock); (R4) GC never drops a version visible to any active snapshot (proptest 1000 trials); (R5) GC reclaims ≥ 80% of obsolete versions within 2 cycles; (R6) CPU usage of GC thread < 15% under sustained load; (R7) GcWorker.shutdown() joins thread cleanly within 2× interval; (R8) leaked Snapshot (forgotten drop) detected via `max_snapshot_age` timeout; subsequent read returns Err.

  - **Design questions**: (D1) Watermark protocol: `txn_manager.min_active_snapshot_ts() -> u64` (u64::MAX if no active); GC uses Acquire load. New snapshot CAS-updates the atomic before observing it. Why? (Prevents GC dropping a version that snapshot about to take.) (D2) Tombstone reincarnation: if GC drops tombstone at ts=100 but older live at ts=50 (also below watermark) was preserved by prior snapshot now gone, a fresh snapshot at ts=160 sees the live ts=50 — key reappears. Fix? (Drop entire version chain prefix below watermark atomically; tombstone preserved iff any version-below preserved.) (D3) **Pre-mortem**: caller leaks Snapshot; min_active stuck forever; on-disk versions grow unbounded. What test catches? (Run with leaked Snapshot for 2× max_snapshot_age; assert next Snapshot.read returns Err(SnapshotTooOld).)

  #### Phase 3 — Failure cards

  - **When `test_gc_preserves_active_snapshot_versions` fails with NotFound from snapshot**: Symptom: snapshot at ts=50; insert up to ts=200; GC ran with watermark=150 (snapshot's ts=50 not registered); GC dropped versions ts<150 including the ones snapshot needs. Why: snapshot didn't register with txn_manager; min_active_snapshot_ts saw "no active" = u64::MAX, GC freed everything below current. Fix: Snapshot::new() registers ts in txn_manager's active-set BEFORE returning; Drop removes. min_active_snapshot_ts = active.iter().min().unwrap_or(u64::MAX). Muscle: RAII registration is non-negotiable for any reference-counted resource. Reapplies at: W97 Thu PinGuard, W100 chaos.

  - **When `test_tombstone_no_reincarnation_after_gc` shows resurrection**: Symptom: snapshot dropped; GC; tombstone at ts=100 dropped because watermark=150; older live at ts=50 also below watermark but preserved due to staggered GC; fresh get returns Some(old_value). Why: GC dropped tombstone and live separately; compaction filter doesn't atomically prune chain prefix. Fix: compaction filter operates on entire version chain per key; if dropping any version below watermark, drop ALL versions below watermark atomically (chain prefix). Tombstone presence in prefix = drop entire prefix. Muscle: tombstone semantics require atomic chain pruning; per-version drops break the invariant. Reapplies at: W97 Wed delete, W100 chaos under live snapshots.

  - **When `bench_gc_cpu_under_15pct` reports GC at 40% CPU**: Symptom: GC runs continuously; foreground reads/writes see bufpool eviction; throughput drops 30%. Why: no rate limiting; GC scans entire dataset every interval. Fix: GcWorker rate-limited via backpressure::Limiter; on high foreground load, extend sleep; per-cycle work budget (e.g., max 100k versions/cycle); incremental scan picks up where last cycle left off. Muscle: background GC must be a budgeted citizen, not a CPU hog. Reapplies at: every background worker (W99 raft compaction, W102 vector index merge).

  - **5-year failure mode**: when datasets exceed 1 TB on SSD, full-scan GC takes hours per cycle. Migration: per-SSTable compaction filter (already in lsm-core LCS/TWCS) handles inline GC; standalone GcWorker becomes coordinator. Trigger: GC cycle > 30 minutes.
