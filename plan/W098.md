  - *Mental model*: `IncrementalMargin` turns the per-mark-tick portfolio recompute from a **fan-out-and-sweep** (touch all 100k accounts every tick) into a **delta-on-change** (touch only the accounts whose positions or whose instruments' marks moved, and within each, recompute only the cheap O(instruments) netting term). It is the same shape as a TigerBeetle apply: state mutates in place from a small, deterministic delta — never recomputed from scratch on the hot path. Full recompute survives, but it is *quarantined* to circuit-breaker / parameter-change events, where the cost is paid once and amortized. The function it computes is *exactly* W97's margin formula; the only thing that changes is when and how cheaply.
  - *Contract*: signature-level interface (NEVER the body):
    ```rust
    #[derive(Clone, Copy)]                          // R3: every delta is Copy, ~one cache line
    pub struct MarginDelta {
        account: AccountId,                          // dense u32 index into the per-shard vec
        instrument: InstrumentId,                    // BTC-PERP | ETH-PERP (u8)
        // integer-only: signed position lots + mark in ticks; NO f64
        old_qty: i64, new_qty: i64,
        mark_ticks: i64,                             // CONSUMED from oracle-mark; never computed here
    }
    #[derive(Clone, Copy)]
    pub struct AccountMargin {                       // pre-allocated per account; mutated in place
        per_instrument_mm: [i64; MAX_INSTRUMENTS],   // running MM per leg, in quote bps
        portfolio_mm: i64,                           // = sum(legs) - 0.70 * netting_offset (W97)
    }
    pub struct IncrementalMargin { /* per-shard Vec<AccountMargin> + runtime-thread-per-core shards */ }
    impl IncrementalMargin {
        pub fn on_position_change(&mut self, d: MarginDelta);   // O(instruments) netting recompute, in place
        pub fn on_mark_tick(&mut self, instrument: InstrumentId, mark_ticks: i64); // delta over affected accounts only
        pub fn full_recompute(&mut self, reason: RecomputeReason);  // CIRCUIT-BREAKER / PARAM-CHANGE ONLY
        pub fn account_margin(&self, a: AccountId) -> AccountMargin; // read-after-commit (Tue): from local applied state
    }
    pub enum RecomputeReason { CircuitBreaker, ParamChange }   // NOT MarkTick — that would be the bug
    ```
  - *Back-of-envelope* (bar (c) — name the cost; this is §4A's own math, re-derived):
    - Full-recompute cliff: 100k accounts × 10 ticks/s × ~1µs/account = **1M recomputes/s ≈ 1 CPU-second/second single-threaded**. Shard-by-account over 16 cores = ~62.5k/s/shard ≈ 62ms/s/shard — *barely* fits at 10 ticks/s, and **does not fit** at per-trade mark cadence. This is exactly why incremental is mandatory, not optional.
    - Incremental win: a mark tick on ONE instrument moves the mark for that instrument's holders only; the per-account work is O(instruments)=O(2) netting recompute (~tens of ns), not a from-scratch portfolio build. A position change touches ONE account. So the per-tick fan-out is `(#accounts holding the moved instrument) × ~50ns`, and the netting term is the only non-linear part — recomputed from the account's 2 legs, never from history.
    - Apply-path alloc cliff: malloc ≈ 50ns. A `MarginDelta` carrying a `Vec<Leg>` or `String instrument` = ~2-3 allocs/apply × 1M/s × 50ns = **~100-150ms/s of allocator wall-clock — 10-15% of a core burned on malloc** + cache pollution + p99 jitter. `Copy` delta = 0 allocs, ~48B (under one cache line).
    - f64 cliff: NOT auto-FMA (rustc never contracts; plain IEEE-754 f64 mul/add is bit-identical on x86 and ARM) — the real vectors are platform-specific libm calls, an explicit `mul_add` from a perf refactor, `-C target-cpu`/fast-math flags, NaN payloads; and float accumulation over millions of incremental adds drifts from the full recompute IDENTICALLY on both arches — caught by the incremental==full equivalence oracle, not by cross-arch hashing alone. Integer bps only → 0 drift, by construction.

  - **The problem this primitive solves**: a portfolio-margin engine that recomputes every account on every mark tick has a compute cost that is *fundamentally wrong at scale* (§4A's "anti-pattern avoided: optimize later on an access pattern that is fundamentally wrong"). At the v1.0 target it pegs a core at 10 ticks/s and falls over completely at higher cadence. But making it incremental introduces THREE new failure categories: (a) **drift** — an incremental update that is not provably equal to the full recompute silently mis-margins accounts (a wrong margin → a wrong liquidation, the venue's most expensive bug); (b) **the netting trap** — the netting offset is non-linear in the per-instrument legs, so a naïve "delta the moved leg only" is *wrong*; the netting term must be recomputed from the account's full (small) leg set; (c) **recompute creep** — the temptation to "just full-recompute on every tick to be safe," which throws away the entire point and re-blows the budget. The fix: an equivalence invariant (incremental == full, proptest + cross-arch + VOPR), an O(instruments) netting recompute inside the delta, and a hard gate that full recompute fires ONLY on circuit-breaker / param-change.
