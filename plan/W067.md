- [ ] **Build**: `crates/consensus-raft/src/snapshot.rs` — InstallSnapshot RPC + log compaction. Snapshots stored as
  `wal::Segment`s with special type tag. (~150 min)
  - **Why**: Without compaction, the Raft log grows without bound — restart time becomes O(log_size), disk fills, and new replicas added to the cluster must stream every entry ever appended. InstallSnapshot is the *only* mechanism that lets the cluster bound recovery time and admit lagging or fresh replicas in O(snapshot_size). This is bar (c) — VOPR-grade — because matching-engine v1.0 (W74) replicates its order-book state through this exact pipeline; bugs here corrupt orders.
  - *Back-of-envelope* (bar c): snapshot of 100k state-machine entries → typical state ≈ 10-100 MiB serialized. Write throughput on NVMe ≈ ~1 GB/s, so write time ≈ ~10-100 ms; transfer over LAN at ~10 Gbps ≈ ~80 ms for 100 MiB; over WAN at ~100 Mbps ≈ ~8 s. **Snapshot creation MUST NOT block AppendEntries** — leader keeps committing while snapshot writes (see perf pitfall #2). Chunked transfer ≈ ~1 MiB chunks: at 1k chunks for 1 GiB snapshot, per-chunk transfer ≈ ~80 µs LAN + ~250 µs RTT for ack, so the *naive* sequential chunked transfer = 1000 × 330 µs = 330 ms (RTT-bound, not bandwidth-bound — see perf pitfall #1 on chunk pipelining). Per snapshot: ONE fsync at the end (group-commit on the snapshot segment) — NOT per-chunk. AppendEntries itself runs at the 25k entries/sec target: **batched fsync** every ~1024 entries or 10 ms, NOT per-entry (per-entry fsync at 50-1000 µs NVMe = max 1k entries/sec, blowing the target by 25×).
  - **Read first**: etcd-io/raft `raft/storage.go` (`Snapshot()`, `ApplySnapshot`), `raft/raft.go::handleInstallSnapshot` (≈L1850-L1920). Diego Ongaro's thesis §5.4 (Log Compaction) — the figure showing log_prefix → snapshot + log_suffix is the mental model. Skim TiKV's `raft-rs/src/raft.rs::handle_snapshot` for production hardening (snapshot truncation race fixes).
  - **Design**:
    ```rust
    pub struct Snapshot {
        pub last_included_index: u64,    // log index covered
        pub last_included_term: u64,     // term of that index (for log matching)
        pub config: ConfigState,          // membership at snapshot time
        pub state_bytes: Bytes,           // opaque state-machine bytes
    }
    pub struct InstallSnapshotReq {
        pub term: u64,
        pub leader_id: NodeId,
        pub snapshot: Snapshot,
        pub offset: u64,                  // for chunked transfer
        pub chunk: Bytes,
        pub done: bool,
    }
    // Storage extension
    impl WalStorage {
        fn install_snapshot(&self, snap: Snapshot) -> Result<()>;     // writes Segment{ tag: SNAPSHOT, .. }, then truncate log to (snap.last_included_index, ..]
        fn snapshot(&self) -> Result<Snapshot>;                       // load most-recent snapshot
        fn compact(&self, up_to: u64) -> Result<()>;                  // drop log entries <= up_to (must be <= last snapshot index)
    }
    ```
    **Invariants**: (i) `last_included_index <= commit_index` always — never snapshot uncommitted state. (ii) After `install_snapshot`, no log entry with index `<= last_included_index` survives. (iii) The very next log entry after install MUST have `index = last_included_index + 1` and term matched against `last_included_term` per Raft log-matching. (iv) `compact(N)` requires `N <= state_machine.applied_index` AND `N <= latest_snapshot_index`.
  - **Build steps**: 1. (~20 min) `Snapshot` + `InstallSnapshotReq/Resp` types + bincode/serde derives. 2. (~30 min) `WalStorage::install_snapshot` — write SNAPSHOT-tagged segment, fsync, then truncate prior segments. Order matters: snapshot durable BEFORE truncate. 3. (~25 min) `RaftNode::handle_install_snapshot` — accept if `term >= current_term`, reject if our `last_applied_index >= snap.last_included_index` (already ahead). 4. (~25 min) Chunked transfer loop (offset/done) — leader streams 1 MiB chunks. 5. (~25 min) Snapshot creation trigger: when `applied_index - first_log_index > SNAPSHOT_THRESHOLD` (default 10k entries), call `state_machine.snapshot()` then `storage.install_snapshot()` then `storage.compact()`. 6. (~25 min) Tests below.
  - **Pitfalls** (named, 4):
    - *Truncate-before-fsync*: **Symptom**: power-loss during install leaves no snapshot AND no log → unrecoverable replica. **Fix**: fsync the snapshot segment BEFORE truncating any old segment. Treat as 2-phase: (1) write snapshot durably, (2) write a "compaction marker" entry, (3) only then free old segments. Match etcd `MemoryStorage.ApplySnapshot` ordering.
    - *Apply-past-snapshot*: **Symptom**: state machine reapplies an entry that's logically inside the snapshot range → double-apply (e.g., duplicate order placement). **Fix**: after installing a snapshot, set `state_machine.last_applied = last_included_index` atomically and reject any apply call with `index <= last_applied`.
    - *Catch-up overshoot*: **Symptom**: lagging follower receives snapshot at index N, then leader sends AppendEntries starting at index M > N+1 → log gap, follower stuck in infinite reject loop. **Fix**: after a successful install, the follower must respond with `match_index = last_included_index`; leader's `next_index[follower] = last_included_index + 1`. Verify the nextIndex update path in `handle_install_snapshot_resp`.
    - *Snapshot-while-leader*: **Symptom**: leader creates snapshot, compacts log, then receives AppendEntriesResp from a slow follower referencing a now-compacted entry — leader needs to send InstallSnapshot but its snapshot is mid-write. **Fix**: hold a snapshot-creation lock; while creating, defer responses that would need pre-snapshot entries to a queue and drain after install completes.
  - **Test scenarios**: (a) crash power-loss inject `kill -9` between snapshot-write and log-truncate, restart, verify replica state. (b) 3-node cluster: stop node-3, append 50k entries, snapshot+compact, restart node-3 — must catch up via InstallSnapshot (verify log is compacted on leader BEFORE node-3 wakes). (c) Add a 4th node mid-flight while leader is creating snapshot — admission should not deadlock. (d) Snapshot during leader change: trigger election while a snapshot install is in progress to a follower.
  - **Acceptance**: bench: snapshot of 100k state-machine entries < 500ms write, < 200ms transfer over loopback. Coverage: state_machine_apply_idempotent property test passes 10k iterations. Inheritance: wal+recovery LOC consumed ≥ 60% of snapshot.rs LOC (snapshot is mostly wal segment plumbing).

  - **Expect to hit (perf) #1 — sequential chunked transfer (RTT-bound, not bandwidth-bound) (bar (c) violation)**: naive InstallSnapshot loop = `for chunk in snapshot.chunks(1 MiB) { send(chunk); await ack; }`. Each round trip ≈ ~250 µs LAN + ~80 µs send = 330 µs per chunk; at 1k chunks for a 1 GiB snapshot that's 330 ms — but the actual transfer time is only ~80 ms at 10 Gbps! 75% of the elapsed time is the follower-side wait for acks. Symptom: `iftop` shows the link at ~25% utilization; snapshot transfer time scales with chunk count, not bytes; new replica onboarding takes 4× longer than the link should allow.
    - Fix: **pipelined chunk transfer** with a sliding-window of N in-flight chunks (e.g., N=8 — like TCP windowing on top of TCP). Leader sends chunks 0..7 without waiting; ack on chunk K acknowledges all chunks ≤K (cumulative); leader advances window. Bound the window by available follower memory (e.g., 8 × 1 MiB = 8 MiB). Use `mmap-queue` (W31 v0.1) as the leader-side staging buffer; chunks are zero-copy reads from the mmap.
    - Cost avoided: 250 ms saved per 1 GiB snapshot (300% throughput improvement); at the 1000-runtime-hours-per-month VOPR test cadence (M27+), 4× faster catch-up = 4× more scenarios run per fixed budget.
    - Muscle: any chunked transfer over a network must pipeline the in-flight window; sequential ack-then-send is always RTT-bound. Reapplies at: W74 matching-engine raft AppendEntries (same pattern — pipeline AppendEntries, don't wait for each ack), W76 messaging-aeron NAK gap recovery, W83+ ledger VSR state-transfer (W76 stub), W90 marketdata-kernelbypass NIC RX.
  - **Expect to hit (perf) #2 — snapshot creation blocks leader's AppendEntries (bar (c) violation)**: naive `state_machine.snapshot()` holds the apply-loop mutex for 100-500 ms while serializing 100 MiB of state. During that window, the leader cannot apply new committed entries, so AppendEntries acks stall, follower commit_index falls behind, and a follower might trip its election timeout (typically 150-300 ms). Symptom: spurious leader election triggered every snapshot interval; client commit P99 latency spikes from 2 ms to 500 ms during snapshot creation.
    - Fix: **copy-on-write snapshot via `arc_swap` + structural sharing** (or fork+COW on the in-memory state if the SM allows it). The snapshot pass takes an atomic `Arc::clone()` of the current state (~10 ns), then serializes that immutable view on a background thread while the apply-loop continues mutating a fresh `Arc`. For state machines that don't tolerate full clone (large `BTreeMap`), use `im` crate's persistent data structures so the clone is O(1). Apply-loop never blocks; the snapshot completes asynchronously and atomically commits via `arc_swap::store`.
    - Cost avoided: ~100-500 ms of leader stall per snapshot eliminated; eliminates the spurious-election DoS vector entirely; reclaims P99 commit latency to ~2 ms during snapshot windows.
    - Muscle: long-running maintenance work (snapshot, compaction, defrag) on a hot data structure must run on a forked copy via Arc/COW; never under the apply-mutex. Reapplies at: W74 matching-engine `OrderBook::snapshot` (per-symbol, ~10 MiB each, same COW pattern), W83+ ledger VSR snapshot, W95 mini-db memtable freeze-to-SSTable (already CoW by design — confirms pattern), W100 mini-db CAPSTONE snapshot path.
