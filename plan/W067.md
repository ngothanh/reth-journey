  - 🔧 **Why this matters**: mirrors etcd `raft/storage.go` (`ApplySnapshot`/`CreateSnapshot`/`Compact`) + TiKV `raft-rs` `InstallSnapshot`. Without compaction, the Raft log grows without bound — restart time becomes O(log_size), disk fills, and new replicas added to the cluster must stream every entry ever appended. InstallSnapshot is the *only* mechanism that bounds recovery time and admits lagging or fresh replicas in O(snapshot_size). The 2-4 specific traps: (1) sequential small-chunk transfer is RTT-bound (~11% link utilization); (2) `snapshot()` under the apply-mutex stalls the leader → spurious elections; (3) truncate-before-fsync loses data on `kill -9`; (4) post-install stale `next_index`/`match_index` → reject-loop, and replay double-applies entries inside the snapshot range.   - *Mental model*: a snapshot is a state-machine checkpoint that lets Raft throw away the log prefix it summarizes. Compaction trades "replay the whole history" for "load one checkpoint + replay the suffix." Done wrong it loses data (truncate before durable) or stalls the leader (serialize under the apply lock).
  - *Contract* (signatures only — never the body):
    ```rust
    pub struct Snapshot { pub last_included_index: u64, pub last_included_term: u64,
                          pub config: ConfigState, pub state_bytes: Bytes }
    pub struct InstallSnapshotReq { pub term: u64, pub leader_id: NodeId, pub snapshot: SnapshotMeta,
                                    pub offset: u64, pub chunk: Bytes, pub done: bool }
    impl RaftNode {
        pub fn create_snapshot(&self) -> Snapshot;                 // COW: O(1) Arc clone, serialize off-loop
        pub fn install_snapshot(&mut self, req: InstallSnapshotReq) -> InstallSnapshotResp;
        pub fn compact(&mut self, up_to: u64) -> Result<(), CompactErr>; // requires up_to ≤ applied ≤ snap idx
    }
    ```
  - *Back-of-envelope* (bar (c)): chunk size = **64 KiB** (deliberately small so RTT, not send time, dominates — that is what makes pipelining win). 100 MiB / 64 KiB = **1600 chunks**. Per-chunk transfer at a same-region 2 GiB/s link = 64 KiB / 2 GiB/s ≈ **30 µs**, which is dwarfed by the **250 µs RTT** (syscall round-trip ≈ 300 ns × 2 + same-region network). So sequential cost per chunk ≈ 250 µs RTT + ~30 µs send ≈ **280 µs**; × 1600 = **~450 ms wall, while true bandwidth time at 2 GiB/s is 100 MiB / 2 GiB/s ≈ ~50 ms → ~11% link utilization, a ~9× cliff (RTT-bound, not bandwidth-bound)**. The window N that saturates the link = bandwidth-delay product / chunk = (250 µs × 2 GiB/s) / 64 KiB ≈ **8**, so N=8 turns the transfer bandwidth-bound (~50 ms + a few RTT of fill ≈ ~55 ms). [If chunks were 1 MiB instead, per-chunk send (~500 µs at 2 GiB/s) would already exceed the RTT and the transfer would be bandwidth-bound even sequentially — the cliff only exists for small chunks.] `Arc::clone` of the state root = ~10 ns (one atomic increment); serializing 100 MiB under the apply-mutex = ~200 ms of stall; follower election timeout 150-300 ms → the 200 ms stall TRIPS it. fsync ≈ 1-10 ms; group-commit must amortize it to ≤1k/sec at 25k entries/sec (25× batch).
  - **Requirements** — write in `crates/consensus-raft/notes/67_snapshot_design.md`:
    - R1. `Snapshot { last_included_index, last_included_term, config: ConfigState, state_bytes }` is the on-disk + wire format. Includes membership AT snapshot time (so a fresh replica learns the cluster shape from the snapshot).
    - R2. `InstallSnapshotReq { term, leader_id, snapshot, offset, chunk, done }` supports chunked transfer.
    - R3. **Durability ordering**: write snapshot segment + fsync BEFORE truncating any log entry. 2-phase: (1) write snapshot durably, (2) write a "compaction marker" entry, (3) free old segments. Matches etcd's `MemoryStorage.ApplySnapshot` ordering.
    - R4. **Invariants**:
      - `last_included_index ≤ commit_index` always — never snapshot uncommitted state.
      - After `install_snapshot`, NO log entry with `index ≤ last_included_index` survives.
      - Next log entry after install has `index = last_included_index + 1`; term matched against `last_included_term` per Raft log-matching.
      - `compact(N)` requires `N ≤ state_machine.applied_index` AND `N ≤ latest_snapshot_index`.
    - R5. **Pipelined chunk transfer**: 64 KiB chunks, sliding window of N in-flight chunks (default N=8, the bandwidth-delay product for 2 GiB/s × 250 µs RTT). Cumulative ack on chunk K acknowledges chunks ≤ K. Window bounded by follower memory (8 × 64 KiB = 512 KiB).
    - R6. **COW snapshot creation**: `state_machine.snapshot()` returns an `Arc` clone (~10 ns) of the current state; serialization happens on a background thread while the apply-loop continues. Use `arc_swap` + `im` persistent data structures so the clone is O(1).
    - R7. **Apply-loop non-blocking**: during snapshot of 100 MiB state, apply-loop continues at ≥ 80% of steady-state throughput.
    - R8. **Catch-up correctness**: after a successful install, follower responds with `match_index = last_included_index`; leader's `next_index[follower] = last_included_index + 1`.
    - R9. **Bench targets**: 100k-entry snapshot write < 500 ms; 100 MiB pipelined transfer (64 KiB chunks, N=8) over a same-region 2 GiB/s link < 80 ms (vs ~450 ms sequential — the cliff under test).

  #### Phase 3 — Make the tests pass, one failure at a time (~110 min)

  Ordered newbie→expert — the ladder you actually walk.

  - **(NEWBIE) When `catch_up_match_index_correct` shows the follower stuck in an infinite reject loop:**
    - Symptom: leader sends InstallSnapshot at index 30000 (success); leader then sends AppendEntries at index 50000; follower rejects ("log too short"); leader decrements next_index, retries; follower keeps rejecting all the way down.
    - Why: after a successful install, the follower's `match_index` wasn't updated; leader's `next_index[follower]` is stale at 50000 instead of 30001.
    - Fix: in `handle_install_snapshot_resp` (leader side), on success: `self.match_index[follower] = snap.last_included_index; self.next_index[follower] = snap.last_included_index + 1`. Update BOTH.
    - Cost avoided: O(50000) wasted reject round-trips per catch-up (~12.5 s at 250 µs RTT) → 0; the follower never converges otherwise.
    - Muscle: post-install, every replica index pointer (match, next, commit) must be re-grounded to the snapshot's last_included_index — partial updates cause reject-loops. Reapplies at: W74 matching-engine catch-up, W84 ledger replica join.

  - **(SENIOR) When `state_machine_apply_idempotent` finds a sequence where install_snapshot followed by replay of old log diverges:**
    - Symptom: after `install_snapshot(snap_at_1000)` followed by replay of log entries [500, 1500], the state machine applied entries 500-999 even though they're inside the snapshot range → double-apply (duplicate order placement, double-credit).
    - Why: the state_machine doesn't enforce `last_applied = last_included_index` atomically with install. The replay path iterates entries from index 0 without checking the snapshot boundary.
    - Fix: after installing a snapshot, set `state_machine.last_applied = last_included_index` ATOMICALLY (single field write). The apply path must check `if entry.index <= last_applied { skip }` before invoking the handler. The skip is the load-bearing defense.
    - Cost avoided: silent state corruption — green unit tests, RED proptest/VOPR; the kind of bug that double-fills an order at W74.
    - Muscle: in any "snapshot + log suffix" replay design, the apply path must filter entries against last_applied — once. Reapplies at: W74 matching-engine replay, W83+ ledger snapshot+wal recovery.

  - **(SENIOR) When `snapshot_durability_before_truncate` shows an unrecoverable replica after `kill -9`:**
    - Symptom: power-loss during install leaves no snapshot AND no log → replica panics on recovery with "no contiguous log from snapshot-index".
    - Why: you truncated old log segments BEFORE the new snapshot segment was fsync'd. Crash window: snapshot in OS page cache (not durable) + old log already freed = data loss.
    - Fix: 2-phase install. Phase 1: write snapshot segment, fsync, write a "compaction marker" entry referencing `last_included_index`, fsync the marker. Phase 2: only after both fsyncs return, truncate old log segments. The marker is the load-bearing artifact — recovery sees the marker and trusts the snapshot; without the marker, recovery treats the install as "did not happen" and the log is intact. Match etcd's ordering.
    - Cost avoided: total replica state loss (UAF-class for durability) — a `kill -9` at the wrong instant orphans the data; (bar (c) violation: a Layer-1/HFT replica that can lose committed state fails its bar).
    - Muscle: any "replace X with Y" durability pattern is 2-phase: (write Y + barrier) then (delete X). Reapplies at: W26 WAL segment rotation, W74 matching-engine commit-cert + truncate, W83+ ledger checkpoint.

  - **(EXPERT, perf #1 — bar (c) violation) When `snapshot_no_spurious_election` reports elections every 60 s + `bench_apply_throughput_during_snapshot` drops to ~0%:**
    - Symptom: every snapshot interval triggers a leader election; client commit p99 spikes from 2 ms to 500 ms; apply throughput collapses during the window.
    - Why: naïve `state_machine.snapshot()` holds the apply-loop mutex for 100-500 ms while serializing 100 MiB. During that window the leader can't apply committed entries, AppendEntries acks stall, a follower trips its 150-300 ms election timeout.
    - Fix: **copy-on-write snapshot via `arc_swap` + structural sharing** (`im` persistent maps). The snapshot pass takes `Arc::clone()` of the current state (~10 ns), serializes that immutable view on a background thread while the apply-loop mutates a fresh `Arc`; commit atomically via `arc_swap::store`. Apply-loop never blocks.
    - Cost avoided: **~100-500 ms of leader stall per snapshot eliminated** (the Arc clone is ~10 ns vs ~200 ms serialize-under-lock); removes the spurious-election DoS vector; reclaims P99 commit to ~2 ms. (bar (c) violation: a critical-path replica that self-DoSes on every snapshot fails its bar.)
    - Muscle: long-running maintenance (snapshot, compaction, defrag) on a hot structure must run on a forked copy via Arc/COW — never under the apply-mutex. Reapplies at: W74 matching-engine `OrderBook::snapshot` (per-symbol COW), W83+ ledger VSR snapshot, W95 mini-db memtable freeze-to-SSTable, W100 mini-db CAPSTONE snapshot path.

  - **(EXPERT, perf #2 — bar (c) violation) When `bench_chunk_transfer_pipelined` reports ~450 ms for 100 MiB and `iftop` shows ~11% link utilization:**
    - Symptom: 100 MiB needs only ~50 ms of true transfer at the 2 GiB/s same-region link, but elapsed wall is ~450 ms; new-replica onboarding takes ~9× longer than the link allows; the wait is at the follower-side ack.
    - Why: naïve loop = `for chunk in snapshot.chunks(64 KiB) { send(chunk); await ack; }`. With small 64 KiB chunks each round trip ≈ 250 µs RTT + ~30 µs send = ~280 µs, and the RTT dominates the send; × 1600 chunks = ~450 ms — RTT-bound, not bandwidth-bound. ~90% of wall is the follower-side ack wait, because the send-and-ack of each chunk never overlaps. (Pick small chunks deliberately: at 1 MiB the per-chunk send ~500 µs already exceeds the RTT and the loop is bandwidth-bound even sequentially — but 1 MiB chunks bloat follower buffers and lose the fine-grained back-pressure the windowed sender needs.)
    - Fix: **pipelined chunk transfer**, sliding window of N=8 in-flight chunks (N = bandwidth-delay product = 250 µs × 2 GiB/s / 64 KiB ≈ 8). Send 0..7 without waiting; cumulative ack on chunk K acknowledges ≤ K; advance window. Window covers the BDP so the link stays full → transfer becomes bandwidth-bound at ~50 ms + a few RTT of fill ≈ ~55 ms. Bound window by follower memory (8 × 64 KiB = 512 KiB). Stage leader-side through W31 `mmap-queue` v0.1 so chunks are zero-copy mmap reads.
    - Cost avoided: **~395 ms saved per 100 MiB (~450 ms → ~55 ms, ≈8× throughput); ~8× faster catch-up** → at the M27+ VOPR cadence (1000 runtime-hours/month), ~8× more scenarios per fixed budget. (bar (c) violation: ~11% link util on the catch-up path caps cluster recovery time.)
    - Muscle: any chunked transfer over a network must pipeline the in-flight window; sequential ack-then-send is always RTT-bound. Reapplies at: W74 matching-engine raft AppendEntries, W76 messaging-aeron NAK gap recovery, W83+ ledger VSR state-transfer, W90 marketdata-kernelbypass NIC RX.

  - **(EXPERT) When `snapshot_during_leader_change` deadlocks (loom/`loom_install_vs_apply_no_lost_commit` flags a lost commit):**
    - Symptom: election fires mid-InstallSnapshot; the snapshot-creation lock is held while the new leader's apply-loop waits on it → deadlock, or a committed entry in N+1..N+3 is dropped because `last_applied` raced the install.
    - Why: snapshot-creation lock taken without a defer-and-drain path on step-down; install and apply both mutate `last_applied` without a single-writer discipline.
    - Fix: single-writer the `last_applied`/install transition (only the apply task mutates it); on step-down, the in-flight install is abandoned, not blocked — the new leader re-issues. Defer-and-drain the snapshot lock.
    - Cost avoided: 25 ns mutex × correctness — a deadlock here freezes the whole replica (availability outage), or silently loses a committed entry (safety violation, the one thing Raft must never do).
    - Muscle: any state shared between a maintenance task and the hot loop needs a single-writer owner; step-down must abandon, never block. Reapplies at: W74 matching-engine leader change, W83+ ledger view change, W90 consensus-vsr view change.
