  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: a Raft log that grows without bound has two failure modes: (a) restart O(log) makes failover slow; (b) new replicas streaming the full log can take hours. Snapshots solve both by replacing log_prefix with a state-machine snapshot. Done naïvely (sequential chunk transfer, snapshot-blocks-apply, truncate-before-fsync) you ship three correctness bugs and a perf catastrophe. The correct pipeline is: COW snapshot + pipelined chunk transfer + 2-phase durable-then-truncate.

  - **Requirements** — write in `crates/consensus-raft/notes/67_snapshot_design.md`:
    - R1. `Snapshot { last_included_index, last_included_term, config: ConfigState, state_bytes }` is the on-disk + wire format. Includes membership AT snapshot time (so a fresh replica learns the cluster shape from the snapshot).
    - R2. `InstallSnapshotReq { term, leader_id, snapshot, offset, chunk, done }` supports chunked transfer.
    - R3. **Durability ordering**: write snapshot segment + fsync BEFORE truncating any log entry. 2-phase: (1) write snapshot durably, (2) write a "compaction marker" entry, (3) free old segments. Matches etcd's `MemoryStorage.ApplySnapshot` ordering.
    - R4. **Invariants**:
      - `last_included_index ≤ commit_index` always — never snapshot uncommitted state.
      - After `install_snapshot`, NO log entry with `index ≤ last_included_index` survives.
      - Next log entry after install has `index = last_included_index + 1`; term matched against `last_included_term` per Raft log-matching.
      - `compact(N)` requires `N ≤ state_machine.applied_index` AND `N ≤ latest_snapshot_index`.
    - R5. **Pipelined chunk transfer**: sliding window of N in-flight chunks (default N=8). Cumulative ack on chunk K acknowledges chunks ≤ K. Window bounded by follower memory (e.g., 8 × 1 MiB = 8 MiB).
    - R6. **COW snapshot creation**: `state_machine.snapshot()` returns an `Arc` clone (~10 ns) of the current state; serialization happens on a background thread while the apply-loop continues. Use `arc_swap` + `im` persistent data structures so the clone is O(1).
    - R7. **Apply-loop non-blocking**: during snapshot of 100 MiB state, apply-loop continues at ≥ 80% of steady-state throughput.
    - R8. **Catch-up correctness**: after a successful install, follower responds with `match_index = last_included_index`; leader's `next_index[follower] = last_included_index + 1`.
    - R9. **Bench targets**: 100k-entry snapshot write < 500 ms; 100 MiB transfer over loopback < 200 ms.

  - **Design walk-through** — answer each in your design doc; no peeking at etcd `raft/storage.go` or TiKV `raft-rs` until Phase 3:
    - D1. Sketch `Snapshot` and `InstallSnapshotReq`. Why does Snapshot carry the membership config? (Hint: a fresh replica needs to know who its peers are; the log alone wouldn't tell it.)
    - D2. Durability ordering: walk the 3 steps of R3. Where could a `kill -9` land that leaves no snapshot AND no log? What's the recovery rule that catches a partial install?
    - D3. Apply-past-snapshot defense: after installing a snapshot, what does the state machine do if a delayed apply call arrives for an index ≤ last_included_index?
    - D4. Catch-up after install: write the 4-step protocol from "leader detects follower needs InstallSnapshot" to "follower's match_index updated correctly".
    - D5. Snapshot-while-leader race: write the 5-step trace where the leader is mid-snapshot, a slow follower's AppendEntriesResp references a now-compacted entry, leader needs to send InstallSnapshot but its snapshot is mid-write. What's the fix? (Hint: snapshot-creation lock; defer-and-drain.)
    - D6. Chunk pipelining: compute the RTT-bound cost for a 1 GiB snapshot at 1 MiB chunks with 250 µs RTT, sequential. Now compute with a window of N=8. What N saturates a 10 Gbps link?
    - D7. COW snapshot: write the 4-step flow. What's the cost of `Arc::clone` for a 100 MiB state? When does the serialization actually serialize?
    - D8. **Pre-mortem #1 (RTT-bound chunks)**: 5-step trace where sequential chunk transfer uses ~25% of the link bandwidth.
    - D9. **Pre-mortem #2 (apply-loop block)**: 5-step trace where snapshot creation blocks the apply-loop for 200 ms, follower trips election timeout, spurious leader election fires.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  - **When `bench_chunk_transfer_pipelined` reports ~330 ms for 1 GiB and `iftop` shows ~25% link utilization:**
    - Symptom: 100 MiB takes ~80 ms of true transfer time (at 10 Gbps) but elapsed wall time is ~330 ms. New replica onboarding takes 4× longer than the link should allow; the wait is at the follower-side ack.
    - Why: naïve InstallSnapshot loop = `for chunk in snapshot.chunks(1 MiB) { send(chunk); await ack; }`. Each round trip ≈ ~250 µs LAN + ~80 µs send = 330 µs per chunk; at 1k chunks that's 330 ms — RTT-bound, not bandwidth-bound. 75% of elapsed time is follower-side wait.
    - Fix: **pipelined chunk transfer** with a sliding window of N in-flight chunks (N=8, like TCP windowing on top of TCP). Leader sends chunks 0..7 without waiting; cumulative ack on chunk K acknowledges chunks ≤ K; leader advances window. Bound the window by available follower memory (8 × 1 MiB = 8 MiB). Use `mmap-queue` (W31 v0.1) as the leader-side staging buffer; chunks are zero-copy reads from the mmap.
    - Cost avoided: ~250 ms saved per 1 GiB snapshot (300% throughput improvement); at the 1000-runtime-hours-per-month VOPR test cadence (M27+), 4× faster catch-up = 4× more scenarios run per fixed budget.
    - Muscle: any chunked transfer over a network must pipeline the in-flight window; sequential ack-then-send is always RTT-bound. Reapplies at: W74 matching-engine raft AppendEntries (same pattern), W76 messaging-aeron NAK gap recovery, W83+ ledger VSR state-transfer, W90 marketdata-kernelbypass NIC RX.

  - **When `snapshot_no_spurious_election` reports spurious elections every 60 s during snapshot windows:**
    - Symptom: every snapshot interval triggers a leader election; client commit p99 spikes from 2 ms to 500 ms.
    - Why: naïve `state_machine.snapshot()` holds the apply-loop mutex for 100-500 ms while serializing 100 MiB of state. During that window, the leader cannot apply new committed entries, so AppendEntries acks stall; followers' commit_index falls behind; a follower trips its election timeout (typically 150-300 ms).
    - Fix: **copy-on-write snapshot via `arc_swap` + structural sharing** (or fork+COW on the in-memory state). The snapshot pass takes an atomic `Arc::clone()` of the current state (~10 ns), then serializes that immutable view on a background thread while the apply-loop continues mutating a fresh `Arc`. For state machines that don't tolerate full clone (large `BTreeMap`), use `im` crate's persistent data structures so the clone is O(1). Apply-loop never blocks; the snapshot completes asynchronously and atomically commits via `arc_swap::store`.
    - Cost avoided: ~100-500 ms of leader stall per snapshot eliminated; eliminates the spurious-election DoS vector entirely; reclaims P99 commit latency to ~2 ms during snapshot windows.
    - Muscle: long-running maintenance work (snapshot, compaction, defrag) on a hot data structure must run on a forked copy via Arc/COW; never under the apply-mutex. Reapplies at: W74 matching-engine `OrderBook::snapshot` (per-symbol, ~10 MiB each, same COW pattern), W83+ ledger VSR snapshot, W95 mini-db memtable freeze-to-SSTable (already CoW by design), W100 mini-db CAPSTONE snapshot path.

  - **When `snapshot_durability_before_truncate` shows an unrecoverable replica after `kill -9`:**
    - Symptom: power-loss during install leaves no snapshot AND no log → replica panics on recovery with "no contiguous log from snapshot-index".
    - Why: you truncated old log segments BEFORE the new snapshot segment was fsync'd. Crash window: snapshot in OS page cache (not durable) + old log already freed = data loss.
    - Fix: 2-phase install. Phase 1: write snapshot segment, fsync, write a "compaction marker" entry referencing the snapshot's last_included_index, fsync the marker. Phase 2: only after both fsyncs return, truncate old log segments. The marker is the load-bearing artifact — recovery sees the marker and knows the snapshot is durable; without the marker, recovery treats the install as "did not happen" and the log is intact. Match etcd's ordering.
    - Muscle: any "replace X with Y" durability pattern is 2-phase: (write Y + barrier) then (delete X). Reapplies at: W26 WAL segment rotation, W74 matching-engine commit-cert + truncate, W83+ ledger checkpoint.

  - **When `catch_up_match_index_correct` shows the follower stuck in an infinite reject loop:**
    - Symptom: leader sends InstallSnapshot at index 30000 (success); leader then sends AppendEntries at index 50000; follower rejects ("log too short"); leader decrements next_index, retries; follower keeps rejecting all the way down.
    - Why: after a successful install, the follower's `match_index` wasn't updated; leader's `next_index[follower]` is stale at 50000 instead of 30001.
    - Fix: in `handle_install_snapshot_resp` (leader side), on success: `self.match_index[follower] = snapshot.last_included_index; self.next_index[follower] = snapshot.last_included_index + 1`. Update BOTH; the test `catch_up_match_index_correct` is the canary.
    - Muscle: post-install, every replica index pointer (match, next, commit) must be re-grounded to the snapshot's last_included_index — partial updates cause reject-loops. Reapplies at: W74 matching-engine catch-up, W84 ledger replica join.

  - **When `state_machine_apply_idempotent` finds a sequence where install_snapshot followed by replay of old log diverges:**
    - Symptom: after `install_snapshot(snap_at_1000)` followed by replay of log entries [500, 1500], the state machine applied entries 500-999 even though they're inside the snapshot range. Result: double-apply (duplicate order placement, double-credit, etc.).
    - Why: the state_machine doesn't enforce `last_applied = last_included_index` atomically with install. The replay path iterates entries from index 0 without checking the snapshot boundary.
    - Fix: after installing a snapshot, set `state_machine.last_applied = last_included_index` ATOMICALLY (single field write). The apply path must check `if entry.index <= last_applied { skip }` before invoking the state-machine handler. The skip is the load-bearing defense; without it, replay duplicates work.
    - Muscle: in any "snapshot + log suffix" replay design, the apply path must filter entries against last_applied — once. Reapplies at: W74 matching-engine replay, W83+ ledger snapshot+wal recovery.

- [ ] **Port + Đối chiếu**: `crates/consensus-raft/docs/kafka_isr_vs_raft.md` + a configurable `KafkaISRMode` for snapshot durability — Kafka's HW + ISR commits require ack from ALL current ISR (vs Raft's majority). Implement as opt-in for snapshot subsystem; document when each fits. (~150 min)
  - 🔧 **Decomposition prompt**: consensus-raft v1.0 tags Wednesday. Raft's majority-commit semantics work for log entries but underspecify snapshot durability (when can the leader truncate the log because the snapshot is "safe"?). Kafka's HW + ISR answers exactly this — a snapshot is safe when all current in-sync replicas have it; the slowest in-sync replica gates truncation. The KafkaISRMode config lets a deployer choose the snapshot durability model independently from the log replication model. Critical for matching-engine W74 (raft-replicated): under partial network partition, do you prefer faster snapshot truncation (Raft majority) or stronger snapshot durability (Kafka ISR)?
  - 🎯 **Hardened acceptance**:
    - **Design memo** comparing 3 commit semantics: (a) Raft majority (log + snapshot both = quorum); (b) Kafka ISR (commit = all current ISR ack); (c) hybrid (log = majority, snapshot = ISR — your default for this crate).
    - **Implementation**: `RaftConfig { snapshot_durability: SnapshotDurability { Majority, AllISR } }`. Default Majority (Raft-classic); AllISR is opt-in for matching-engine deployments preferring stronger snapshot durability.
    - **Test**: under 5-node cluster with 2 nodes slow (in ISR but lagging), AllISR mode blocks log truncation until both slow nodes ack snapshot; Majority mode truncates after 3 nodes ack. Both correct; the test demonstrates the trade-off.
    - **Cited URL**: https://developer.confluent.io/courses/architecture/data-replication/ (Kafka ISR semantics); https://raft.github.io/raft.pdf (Raft majority).
    - **5-year failure mode**: when flexible quorums (Heidi Howard's "flexible Paxos" / Kafka's own KIP-966) become standard, the Majority-vs-AllISR dichotomy generalizes to a tunable quorum size. State migration: `SnapshotDurability::Quorum(N)` parameterized.
  - *Source*: https://developer.confluent.io/courses/architecture/data-replication/; Kafka KIP-966 (Eligible Leader Replicas).
  - **Expect to hit #1 — AllISR mode that blocks forever on a hung replica**: a node that's "in ISR" but actually hung (network partition, GC pause, hardware failure) holds back snapshot truncation indefinitely. Symptom: log grows unbounded; disk fills.

    - Muscle: any "all-ack" commit semantics needs a timeout-driven membership protocol to prevent stuck-replica starvation. Reapplies at: W84+ ledger VSR (membership), W76 messaging-aeron flow control (slow-subscriber eviction).
