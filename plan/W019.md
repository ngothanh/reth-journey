  - 🔧 **Why this matters**: precompiles are gas-priced "syscalls" — fixed addresses (`0x01..0x0a`, plus Cancun
    additions) that execute native code instead of bytecode. ECRECOVER (`0x01`) is the single most-called
    precompile (every EOA tx verification path). Producing a recovered address that disagrees with any other
    client by ONE bit = your node forks. The trait shape locked in here is what W19 modexp/pairing reuse, what
    W74 matching-engine signature verification reuses, and what W83 ledger uses for tx-signing checks.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: bytecode that needs cryptographic primitives can't afford to run
    them in the EVM interpreter — secp256k1 recovery in EVM opcodes would burn millions of gas. The EVM
    short-circuits a small set of fixed addresses to native implementations with deterministic gas pricing.
    A precompile is therefore a (gas_cost, native_fn) pair gated by SpecId, called via the same CALL/STATICCALL
    machinery as ordinary contracts. The trait is small but the *contract* (what counts as success, what counts
    as failure) is dense — and consensus-critical.

  - **Requirements** — write in `crates/exec-vm/notes/19_precompile_design.md`:
    - R1. A `Precompile` trait with `run(&self, input: &[u8], gas_limit: u64) -> Result<PrecompileOutput, PrecompileError>`
      returning `(gas_used, bytes)`.
    - R2. A `PrecompileRegistry` keyed by `Address`, populated per `SpecId` (Frontier/Homestead/Byzantium/.../Cancun
      each mount a different set).
    - R3. ECRECOVER input is zero-padded to **exactly 128 bytes** when shorter, truncated when longer.
    - R4. Signature failure (bad r/s, bad v, recovery returns no pubkey) returns `Ok(empty bytes)` with
      **full 3000 gas charged**, NOT `Err`. Only `OutOfGas` is a real error.
    - R5. Successful output is **exactly 32 bytes**: 12 zero bytes + 20-byte address (big-endian).
    - R6. Post-Homestead: reject `s > secp256k1_order / 2` (EIP-2 malleability fix); pre-Homestead: accept
      both halves.
    - R7. Dispatcher integration: `CALL`/`STATICCALL` whose `to` is in `[0x01..0x0a]` (and Cancun
      additions) short-circuits into the registry instead of jumping into bytecode.

  - **Design walk-through** — answer each; no peeking at `revm/crates/precompile/src/secp256k1.rs` until Phase 3:
    - D1. Trait shape: `Precompile` as `dyn`-compatible object (Box<dyn Precompile>) vs `enum Precompile`
      with one variant per builtin. What does each cost at the call site? Which does revm pick and why?
    - D2. Registry storage: `BTreeMap<Address, Arc<dyn Precompile>>` vs static array indexed by low byte of
      address vs `phf` perfect-hash map. The set is tiny (~10) and lookup is on every CALL — what's the
      cheapest dispatch?
    - D3. SpecId gating: when SpecId changes (e.g. Byzantium activates `modexp` at `0x05`), how does the
      registry update? Build a fresh registry per block, or maintain one mutable registry? Justify based
      on hot-path latency vs build cost.
    - D4. Input padding: write the helper signature `fn pad_to_128(input: &[u8]) -> [u8; 128]`. Is it
      const? Does it allocate? If `input.len() > 128`, do you truncate or error?
    - D5. Crate choice: `k256` (pure-Rust, auditable) vs `secp256k1` (wraps libsecp256k1, 3-5× faster).
      Which does revm default to for production paths? What feature flag would let you swap without
      forking the precompile?
    - D6. Pre-mortem (the load-bearing question): write the bad interleaving / wrong-answer scenario in
      4-6 numbered steps where ECRECOVER returns `Err` on a bad signature (instead of `Ok(empty)`) and
      explain which mainnet contract pattern (e.g. EIP-712 typed-sig delegate paths, multisig recovery)
      breaks. If you cannot name the breaking pattern, you do not yet understand R4.

  - **Output**: `notes/19_precompile_design.md` with R1–R7 + answers to D1–D6 + the bad-signature scenario.

  #### Phase 3 — Make the tests pass, one failure at a time (~45 min)

  - **When `ecrecover_all_zero_input_returns_empty_ok` reports `Err(InvalidSignature)`:**
    - Symptom: assertion fails with `assertion failed: result.is_ok()`. The `secp256k1::recover` call
      returned an error and you propagated it as `PrecompileError::InvalidSignature`.
    - Why: bad signatures are NOT precompile errors. Specs say "valid signature → address, invalid →
      empty bytes, no error". Propagating errors causes any tx that calls ECRECOVER with a deliberately
      bad sig (common in EIP-712 delegate-paths and multisig recovery) to revert incorrectly.
    - Fix: only `PrecompileError::OutOfGas` is a real error. Wrap the recover call: on any failure,
      `return Ok(PrecompileOutput { gas_used: 3000, bytes: Bytes::new() })`. The 3000 gas is charged
      regardless of recovery success.
    - Muscle: precompile failure semantics are not Rust's `Result` semantics — read the spec, not the
      library's error enum. Reapplies at: W19 modexp/pairing (same `Ok(empty)` on invalid input), W83
      ledger ECRECOVER, W74 matching-engine sig verification.

  - **When `ecrecover_known_eip155_vector` recovers the WRONG address (off by ~half the test runs):**
    - Symptom: about 50% of test runs return a plausible-looking 20-byte address that doesn't match the
      expected one. The other 50% pass.
    - Why: input `v` is one of {27, 28} (Ethereum convention); the secp256k1 SDK's `recover_id` wants 0
      or 1. You passed `v` directly; the parity flips and you recover the wrong key.
    - Fix: `let recovery_id = (v - 27) as u8;` and reject any `v ∉ {27, 28}` with empty bytes (per R4).
      The EIP-155 chain-id-folded `v` is NOT used here — that lives in the tx-validation layer, not the
      precompile.
    - Muscle: cryptographic library APIs use 0/1 parity; Ethereum encodes 27/28 — normalize at the
      boundary. Reapplies at: W83 ledger sig recover, W74 matching-engine.

  - **When `ecrecover_high_s_rejected_post_homestead` returns an address instead of empty:**
    - Symptom: with `SpecId::Homestead`, a signature whose `s > n/2` recovers an address — but the
      pre-Homestead test (`SpecId::Frontier`) returns the same address. Both pass. The spec gate is missing.
    - Why: EIP-2 (Homestead activation) rejects malleable `s` values; pre-Homestead allowed both
      halves. You implemented one branch only.
    - Fix: inside ECRECOVER, after extracting `s`, compare against `SECP256K1_N_HALF`. If `s > n/2 AND
      spec_id >= HOMESTEAD`, return empty bytes. Pre-Homestead: skip the check.
    - Muscle: every consensus rule has a SpecId activation block; gate the check on the spec, not on
      the library version. Reapplies at: every EIP-gated change (EIP-150 gas, EIP-2929 access lists,
      EIP-3855 PUSH0).

  - **When `registry_dispatches_call_to_0x01` jumps into empty bytecode instead of the precompile:**
    - Symptom: the dispatcher reads bytecode at address `0x01` (none exists), returns immediately with
      an empty output, but **doesn't charge ECRECOVER gas**.
    - Why: the CALL/STATICCALL handler checks for precompiles AFTER it loads bytecode; if the bytecode
      lookup returns empty, it just returns. The precompile check needs to come FIRST.
    - Fix: in the CALL handler, before loading bytecode: `if let Some(precompile) =
      registry.get(&to_address) { return precompile.run(input, gas_limit); }`. Only then fall through
      to bytecode loading.
    - Muscle: precompile dispatch is a *short-circuit* before bytecode resolution; checking after
      bytecode lookup is the bug. Reapplies at: every precompile beyond `0x01` (modexp, pairing,
      Cancun's `0x0a`).

  - **When the bench (R-target ≥50k calls/sec) reports ~10k/sec:**
    - Symptom: `criterion` bench of ECRECOVER on `k256` shows ~100 µs/call. revm's baseline on
      `secp256k1` reports ~20 µs/call. You're 5× slower.
    - Why: `k256` is pure-Rust, auditable, slower. revm defaults to `secp256k1` (wraps libsecp256k1,
      hand-tuned assembly).
    - Fix: feature-flag both. Default `secp256k1` for production paths; expose `k256` behind
      `--features pure-rust` for environments that can't link a C library (no_std, audits).
    - Muscle: cryptographic primitives have a perf cliff between pure-Rust audit-friendly impls and
      native-asm-wrapped impls; the precompile is the wrong place to be ideologically pure. Reapplies
      at: W74 matching-engine BLS verification, W83 ledger schnorr verification.

  - **5-year failure mode** (write in `notes/19_precompile_followup.md` after green): when
    post-quantum precompiles (Dilithium, Falcon — already being prototyped for EIPs in 2026) ship at
    new addresses, the `Address → Arc<dyn Precompile>` map's static dispatch becomes a perf bottleneck
    (24+ precompiles, branch-prediction misses on the BTreeMap path). Migration: switch to a perfect
    hash function (`phf` crate) keyed on the low byte of the address. State the trigger condition
    (when precompile count exceeds 16, AND when ECRECOVER+modexp call rate exceeds 200k/sec sustained).
