  - 🔧 **Why this matters**: precompiles are gas-priced "syscalls" — fixed addresses (`0x01..0x0a`, plus Cancun
    additions) that execute native code instead of bytecode, mirroring `revm::precompile::Precompiles`. ECRECOVER
    (`0x01`) is the single most-called precompile (every EOA-tx and EIP-712 verification path). The 2-4 specific
    traps you WILL hit: (1) returning `Err` on a bad signature instead of `Ok(empty, 3000 gas)`; (2) passing
    Ethereum's `v ∈ {27,28}` straight into a library that wants recovery-id `0/1`, so half your vectors recover
    the wrong key; (3) forgetting the EIP-2 `s > n/2` SpecId gate so pre/post-Homestead behave identically; (4)
    checking the precompile registry AFTER bytecode load so the dispatcher returns empty without charging gas.
    Your first attempt fails at least the four trap tests below and the debug session is the lesson. Producing a
    recovered address that disagrees with any other client by ONE bit = your node forks. Reused by W54
    (modexp/pairing share `Ok(empty)` semantics + the registry), W68 (exec-vm v1.0 dispatch), W74
    (matching-engine sig verify), W83 (ledger tx-signing).

  #### Phase 1 — Problem, prediction, design (~30 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/exec-vm/notes/19_precompile_prediction.md`
    BEFORE any other phase; compare to reality after Phase-2 tests run:
    - P1. The primitive you'd reach for to do the recovery — exact import line (e.g.
      `use secp256k1::ecdsa::{RecoverableSignature, RecoveryId};` vs `use k256::ecdsa::...`).
    - P2. Predicted latency of one ECRECOVER on `secp256k1` (libsecp256k1-backed) vs `k256` (pure-Rust), in µs.
    - P3. Predicted outcome of `run([0u8; 128], 3000)` — does it return `Ok` or `Err`? What `gas_used`?
    - P4. Derive-correctness prediction: what does `PrecompileOutput` need to derive (`Clone`, `PartialEq`,
      `Debug`) for the assert-equality tests to compile, and will `Bytes` cooperate?
    - P5. **List every Phase-2 test you predict your first attempt will fail**, with a one-line reason each.
  - *Mental model*: a precompile is a `(gas_cost, native_fn)` pair gated by `SpecId`, dispatched by the same
    CALL/STATICCALL machinery as an ordinary contract but short-circuited before bytecode resolution. It exists
    because running secp256k1 recovery in EVM opcodes would burn millions of gas.
  - *Contract* (signature-level only — never the body):
    - `trait Precompile { fn run(&self, input: &[u8], gas_limit: u64) -> Result<PrecompileOutput, PrecompileError>; }`
    - `struct PrecompileOutput { gas_used: u64, bytes: Bytes }`
    - `enum PrecompileError { OutOfGas /* and ONLY OutOfGas as a real error for ECRECOVER */ }`
    - `struct PrecompileRegistry { /* keyed by Address, mounted per SpecId */ }` with
      `fn get(&self, addr: &Address) -> Option<&dyn Precompile>` and `fn new(spec: SpecId) -> Self`.
  - *Back-of-envelope* (bar (b), perf optional but worth predicting): ECRECOVER on libsecp256k1 ≈ 20 µs/call,
    on k256 pure-Rust ≈ 100 µs/call — a **5× cliff** that is pure crate choice, not algorithm. At mainnet
    ~40 ECRECOVER/block and 12 s/block, the recovery cost is negligible vs block time; the registry *lookup*
    (one `BTreeMap` probe ≈ 10-20 ns, or a static-array index ≈ L1 0.5 ns) runs on EVERY `CALL`, so the
    dispatch path — not the crypto — is where layout matters at scale.
  - **Requirements** R1..R7 — write in `crates/exec-vm/notes/19_precompile_design.md`:
    - R1. `Precompile::run(&self, input, gas_limit) -> Result<PrecompileOutput, PrecompileError>` returning
      `(gas_used, bytes)`.
    - R2. `PrecompileRegistry` keyed by `Address`, populated per `SpecId` (Frontier/Homestead/Byzantium/…/Cancun
      each mount a different set).
    - R3. ECRECOVER input is zero-padded to **exactly 128 bytes** when shorter, truncated when longer.
    - R4. Signature failure (bad r/s, bad v, recovery returns no pubkey) returns `Ok(empty bytes)` with the
      **full 3000 gas charged**, NOT `Err`. Only `OutOfGas` is a real error.
    - R5. Successful output is **exactly 32 bytes**: 12 zero bytes + 20-byte address (big-endian, keccak of pubkey).
    - R6. Post-Homestead: reject `s > secp256k1_order / 2` (EIP-2 malleability fix); pre-Homestead: accept both halves.
    - R7. Dispatcher integration: `CALL`/`STATICCALL` whose `to` is in `[0x01..0x0a]` (and Cancun additions)
      short-circuits into the registry **before** bytecode resolution.
  - **Design walk-through** D1..D8 — answer in the design doc; no peeking at
    `revm/crates/precompile/src/secp256k1.rs` until Phase 3:
    - D1. Trait shape: `Box<dyn Precompile>` vs `enum Precompile` with one variant per builtin. Property table:

  #### Phase 3 — Make the tests pass, one failure at a time (~45 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `ecrecover_all_zero_input_returns_empty_ok` reports `Err(InvalidSignature)`:**
    - Symptom: `result.expect(...)` panics — the `secp256k1::recover` call returned an error and you propagated it
      via `?` as a `PrecompileError`.
    - Why: bad signatures are NOT precompile errors. The spec says invalid → empty bytes, gas still charged. Only
      `OutOfGas` is a real error. Propagating the library `Err` makes any tx that calls ECRECOVER with a
      deliberately-bad sig (common in EIP-712 delegate paths and multisig recovery) revert incorrectly → consensus split.
    - Fix: never `?` the recover call. `match recover(...) { Ok(pk) => Ok(out_32(pk)), Err(_) => Ok(empty_3000()) }`.
    - Cost avoided: a chain fork (your node reverts a tx every other client accepts) — not "slow", *wrong*.
    - Muscle: precompile failure semantics ≠ Rust `Result` semantics; read the spec, not the library's error enum.
      Reapplies at: W54 modexp/pairing (same `Ok(empty)` on invalid input), W68 exec-vm dispatch, W83 ledger ECRECOVER.

  - **(NEWBIE) When `ecrecover_v_not_27_or_28_returns_empty` recovers an address for `v = 26`:**
    - Symptom: `out.bytes` is non-empty for `v = 26`; assertion `is_empty()` fails.
    - Why: you computed `recovery_id = v - 27` and got an underflow/wrap (or the library accepted a garbage id)
      instead of rejecting out-of-range `v` up front.
    - Fix: validate `v ∈ {27, 28}` BEFORE computing the recovery id; anything else → `Ok(empty_3000())`.
    - Cost avoided: accepting forged `v` values that recover attacker-chosen keys — a soundness bug.
    - Muscle: validate the encoding domain before handing bytes to crypto. Reapplies at: W54 pairing point
      validation, W74 matching-engine sig verify, W83 ledger.

  - **(SENIOR) When `ecrecover_known_eip155_vector` recovers the WRONG address (~half the vectors):**
    - Symptom: about 50% of crafted vectors return a plausible 20-byte address that doesn't match expected; the
      other 50% pass.
    - Why: Ethereum encodes `v ∈ {27, 28}`; the secp256k1 SDK's `RecoveryId` wants `0` or `1`. You passed `v`
      directly, so the parity flips and you recover the sibling key half the time.
    - Fix: `let recovery_id = (v - 27) as u8;` after the `{27,28}` check. The EIP-155 chain-id-folded `v` is NOT
      used here — that normalization lives in the tx-validation layer, not the precompile.
    - Cost avoided: 50% of EOA-tx and EIP-712 verifications recover the wrong signer — silent acceptance/rejection.
    - Muscle: crypto APIs use `0/1` parity, Ethereum encodes `27/28` — normalize at the boundary. Reapplies at:
      W74 matching-engine, W83 ledger sig recover.

  - **(SENIOR) When `ecrecover_gas_exactly_3000_succeeds` reports `Err(OutOfGas)`:**
    - Symptom: 3000 gas should succeed but errors; the 2999 test passes.
    - Why: off-by-one — you wrote `if gas_limit < ECRECOVER_GAS` as `<=` (or compared with `>`), rejecting the
      exact-cost case.
    - Fix: charge succeeds when `gas_limit >= ECRECOVER_GAS` (3000); error only when strictly less.
    - Cost avoided: rejecting every tx that supplies exactly the metered gas — a liveness bug at the gas boundary.
    - Muscle: gas checks are `>=`, not `>`; the exact-cost case must pass. Reapplies at: W54 every metered
      precompile, W68 opcode gas accounting.

  - **(SENIOR) When `ecrecover_high_s_spec_gated` returns the SAME result for Frontier and Homestead:**
    - Symptom: both `post.bytes` and `pre.bytes` are empty (or both non-empty) — the two assertions can't both hold.
    - Why: EIP-2 (`s > n/2` rejection) is implemented unconditionally or not at all; you keyed it on the library
      version or a `#[cfg]`, not on `spec_id`.
    - Fix: after extracting `s`, `if spec_id >= SpecId::HOMESTEAD && s > SECP256K1_N_HALF { return Ok(empty_3000()); }`.
      Pre-Homestead skips the check. One code path, gated by `spec_id`.
    - Cost avoided: a consensus split at the Homestead fork boundary (malleable sigs accepted/rejected wrongly).
    - Muscle: every consensus rule has a SpecId activation block — gate on the spec, not the library or `cfg`.
      Reapplies at: EIP-150 gas (W54), EIP-2929 access lists, EIP-3855 PUSH0, W68 fork-gated opcodes.

  - **(EXPERT) When `registry_dispatches_call_to_0x01` returns empty WITHOUT charging gas:**
    - Symptom: the CALL to `0x01` returns immediately with empty output and `gas_used == 0`; the precompile never ran.
    - Why: the CALL/STATICCALL handler checks for a precompile AFTER loading bytecode; bytecode at `0x01` is empty,
      so it returns before reaching the precompile branch.
    - Fix: short-circuit FIRST — `if let Some(p) = registry.get(&to) { return p.run(input, gas_limit); }` BEFORE any
      bytecode load.
    - Cost avoided: every ECRECOVER call silently no-ops with zero gas — total consensus divergence.
    - Muscle: precompile dispatch is a short-circuit *before* bytecode resolution; checking after is the bug.
      Reapplies at: W54 every address ≥ `0x02`, W68 exec-vm v1.0 dispatch, W74 (priority-queue short-circuit idea).

  - **(EXPERT, perf — optional for bar (b)) When the bench (R-target ≥50k calls/sec) reports ~10k/sec:**
    - Symptom: criterion bench of ECRECOVER on `k256` shows ~100 µs/call; revm's `secp256k1` baseline ≈ 20 µs/call.
    - Why: `k256` is pure-Rust and ~5× slower than libsecp256k1's hand-tuned assembly.
    - Fix: feature-flag both — default `secp256k1` on the production path, expose `k256` behind `--features
      pure-rust` for no_std / audit builds.
    - Cost avoided: ~80 µs/call (4× the budget) on the most-called precompile.
    - Muscle: crypto primitives have a perf cliff between audit-friendly pure-Rust and asm-wrapped native; the
      precompile is the wrong place to be ideologically pure. Reapplies at: W74 matching-engine BLS verify, W83
      ledger schnorr verify.

  #### 5-year failure mode

  Write in `crates/exec-vm/notes/19_precompile_followup.md` after green: when post-quantum precompiles (Dilithium,
