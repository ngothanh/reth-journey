This is a light interview-rehearsal week — no Build exercises. The deliverable is a set of **recorded, time-boxed mock answers** plus an honest skill audit. Each mock is graded against a hardened acceptance bar (a concrete pass criterion the recording must hit), not "felt OK". **Monday — Mock interview: matching engine deep**

- [ ] **Mock**: `notes/116_mock_matching_engine.md` (+ aloud recording `notes/116_mock_matching_engine.m4a`) — "explain your matching-engine design from order ingress to fill emission." 60-minute whiteboard-style, single take, no pausing to look things up. (~60 min)
  - 🎯 **Hardened acceptance**: the recording narrates the full path in order — ingress queue → sequencer (single-writer) → order-book data structure (price-level ladder + intrusive order lists) → match loop (price-time priority) → fill emission → downstream replication. Must name 3 concrete numbers: order-book lookup cost (O(1) best-bid/ask via cached top-of-book, not tree-walk), the per-order hot-path allocation count (target: 0 — orders pooled), and the single-writer rationale (no lock on the book = no 25ns mutex per match). A pass states WHY each choice beats the obvious alternative, not just what it is.
  - *Mental model*: this is the Tier-A HFT systems-design question. The matching engine (W58-W74) mirrors the LMAX Disruptor single-writer / mechanical-sympathy pattern. Interviewers probe whether you internalized *why* single-writer + zero-allocation beats a lock-per-order book — narrate the back-of-envelope (1M orders/s × <1µs budget ⇒ no mutex, no malloc in the loop), because that is the line that separates "built it" from "understands it".
  - *Source*: your own `crates/matching-engine/` design notes (W58 scaffold, W60 order-book draft, W63 v0.5, W65 multi-symbol shards, W74 raft-replicated v1.0).

**Tuesday — Mock interview: storage**

- [ ] **Mock**: `notes/116_mock_storage_trie.md` (+ recording `notes/116_mock_storage_trie.m4a`) — "walk me through your storage-trie design. Where does it differ from MDBX, and why?" 30-minute single take. (~30 min)
  - 🎯 **Hardened acceptance**: the answer must (1) describe the persistent MPT layout (path compression, node encoding) AND the MVCC layer, then (2) draw the explicit contrast table to MDBX — copy-on-write B+tree pages + single-writer-multi-reader MVCC in MDBX vs your design's choices — and (3) name at least one trade-off where you diverged ON PURPOSE and the cost it bought you (e.g. "I chose X; it costs Y on writes but buys Z on state-root recompute"). A vague "it's similar to MDBX but for tries" fails the bar.
  - *Mental model*: storage-trie (W27-W43) mirrors reth's MDBX-backed state layer. The interview trap here is the candidate who can describe their own code but cannot situate it against the upstream it inherits from. Knowing where you *differ from MDBX and why* proves the inheritance was deliberate, not accidental — exactly the "reusable production component mirroring an upstream module" principle.
  - *Source*: your own `crates/storage-trie/` notes (W27-W28 MDBX + B-tree, W29-W30 recovery + MVCC, W31-W32 persistent MPT, W33 path compression, W43 v1.0).

**Wednesday — Mock interview: distributed**

- [ ] **Mock**: `notes/116_mock_failover_invariants.md` (+ recording `notes/116_mock_failover_invariants.m4a`) — "how does your matching-engine handle leader failover? What invariants must hold across the transition?" 30-minute single take. (~30 min)
  - 🎯 **Hardened acceptance**: the answer must enumerate the failover invariants as a *list* — (I1) no committed fill is lost, (I2) no fill is emitted twice (exactly-once at the replicated boundary), (I3) the new leader's order book is byte-identical to the old leader's committed state, (I4) sequence numbers are monotonic across the leadership change. For EACH invariant, name the mechanism that enforces it (raft log replication + commit index, deterministic replay, fenced epoch/term to reject stale-leader writes). State the one interleaving that breaks if you skip the fence (old leader still writing after a new one is elected — split-brain double-fill).
  - *Mental model*: this composes matching-engine (W58-W74) with consensus-raft (W56-W67) — the W74 "raft-replicated matching-engine v1.0" is exactly this seam. The interviewer is testing whether you treat failover as a *correctness* problem (invariants + the bad interleaving that violates each) rather than a liveness afterthought. Naming the split-brain double-fill trace is the load-bearing answer.
  - *Source*: your own `crates/consensus-raft/` notes (W56 v0.1, W59 log replication, W62 membership, W67 v1.0) + `crates/matching-engine/` W74 integration.
- [ ] Commit notes (~10 min).
