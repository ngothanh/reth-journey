**Tuesday — mini-db engine composition root + read path (`get`)**

- [ ] **Build**: `crates/mini-db/src/engine.rs` — `Db { inner: Arc<EngineInner> }` composition root holding lsm-core + wal + txn_manager + bufpool + bloom_pool + clock + backpressure + gc_handle, with deterministic open/close ordering. (~total 3 hrs across 3 phases)
  - 🔧 **Why this matters**: engine is the composition root and the place the inheritance ratio lives or dies — if `EngineInner` holds field-level handles and only forwards, the wrapper stays thin. Mirror: RocksDB `DBImpl` (open in dependency order, close in reverse). The 3 traps here: (1) **out-of-order open** crashes (lsm-core registers SSTables in a not-yet-built bufpool); (2) **out-of-order close** segfaults (lsm-core's `Arc<BufferPool>` outlives pages held by gc); (3) **facade-level `Mutex`** serializes all reads. First-attempt impls fail ≥1 test below; the debug session is the lesson. Downstream consumers: kv.rs (`inner.lsm` + `inner.bloom_pool`), scan.rs (`inner.lsm`), W98 mvcc.rs (`inner.txn_manager` + `inner.clock`), W98 gc.rs (`inner.txn_manager.active_snapshots`), W99 raft_replicated.rs (wraps `Db`).

  - *Mental model*: an engine orchestrates ~8 independent primitives with strict dependency ordering at open and reverse ordering at close. The composition itself is the inheritance proof — it should read like a wiring diagram, not an algorithm.
  - *Contract*:
    ```rust
    pub struct Db { inner: Arc<EngineInner> }
    struct EngineInner {
        lsm: lsm_core::Lsm,
        wal: wal::Wal,
        txn_manager: txn::TxnManager,
        bufpool: Arc<bufpool::BufferPool>,
        bloom_pool: bloom::BloomPool,
        clock: time::HlcClock,
        backpressure: backpressure::Limiter,
        cfg: EngineConfig,
        gc_handle: Option<std::thread::JoinHandle<()>>,
    }
    impl Db {
        pub fn open(cfg: EngineConfig) -> Result<Db, Error>;
        pub fn close(self) -> Result<(), Error>;       // by value, explicit reverse-order drain
        pub fn get(&self, key: &[u8]) -> Result<Option<Bytes>, Error>;
    }
    ```
  - *Back-of-envelope* (bar (b), but the budget is the acceptance): empty-dir open is dominated by ~6 file `open(2)` syscalls (~300ns each) + lsm manifest read (~one 4KB page, ~5µs cold disk) → target **< 50 ms** with huge headroom; a 1 GB SST dataset adds manifest + bloom load → **< 500 ms**. `Db::get` on a *warm* bufpool: bloom check ~1 cache-line (~5ns) + memtable probe (~50-100ns) + bufpool page hit (~100ns) → microsecond-class. A facade `Mutex` adds ~25ns *and* serializes — the serialization, not the 25ns, is the disqualifier.
  - **Requirements** R1..R9 — write in `crates/mini-db/notes/97tue_engine_design.md`:
    - R1. `Db { inner: Arc<EngineInner> }` is the facade; `EngineInner` holds field-level handles only.
    - R2. `Db::open(cfg)` constructs in dependency order: **bufpool → wal → lsm-core → bloom_pool → txn_manager → gc**.
    - R3. `Db::close(self)` drains in **reverse**: gc, txn_manager, wal flush, lsm checkpoint, bufpool.
    - R4. **No `Mutex` on the `Db` facade** — internal primitives carry their own locking discipline.
    - R5. If `wal.has_uncommitted()`, route through `recovery::Recovery::recover` BEFORE returning from open.
    - R6. `Db::open` returns in < 50 ms on empty dir; < 500 ms on a 1 GB SSTable dataset.
    - R7. No panic and no leaked fds across 1000 open/close cycles (verified via `lsof`/`/proc/self/fd`).
    - R8. `HlcClock` is per-`Db` (not accidentally shared across test instances).
    - R9. `backpressure::Limiter` wraps write entry points; flood test confirms `Err(Backpressure)` past the limit.
  - **Design walk-through** D1..D6 (answer in the design doc; no peeking at RocksDB source until Phase 3):
    - D1. Why open order bufpool→wal→lsm-core? (lsm-core + wal register files in bufpool on open; bufpool must exist first.) What breaks if reversed?
    - D2. Why close in reverse? (lsm-core holds `Arc<BufferPool>`; if bufpool drops first, lsm-core's checkpoint flush hits dangling pages.)
    - D3. Why no `Mutex` on the facade? (Each primitive owns its own fine-grained lock; a `Db`-level `Mutex` serializes reads too.) How does `Arc<EngineInner>` give cheap cross-thread share without a lock?
    - D4. Recovery placement: AFTER all primitives constructed, BEFORE gc/backpressure tasks spawn, BEFORE any write accepted. Why all three?
    - D5. `HlcClock` per-`Db` vs process-singleton: with 2+ `Db` in one test process, per-`Db` gives isolation but leaves cross-`Db` op ordering undefined. Default per-`Db`; document.
    - D6. **Pre-mortem (load-bearing)** — write the EXACT 5-line trace where a forgotten `Db::close` leaks WAL fds:
      ```
      1. Db::open → wal opens "wal.log" fd=7
      2. test drops `db` without calling close(); Drop is best-effort log-only
      3. wal's Drop forgot to close fd=7 (relied on close() to do it)
      4. loop body repeats 1000×; fds 7,8,9,... accumulate
      5. open #1019 → open(2) returns EMFILE; ulimit hit; every later test fails
      ```
      What RAII pattern catches this? (wal's `Drop` must close its fd unconditionally; `close()` only adds *ordered* flush.)

  #### Phase 3 — Make the tests pass, one failure at a time (~100 min)
  Ordered newbie → expert.

  - **(NEWBIE) When `test_engine_open_close_idempotent` shows fd leak after ~1000 cycles:**
    - Symptom: `/proc/self/fd` (or `lsof -p`) shows accumulating WAL fds; open #~1019 returns `EMFILE`.
    - Why: `Db::close` flushes correctly, but the primitive's `Drop` relied on `close()` to release the fd, so the *dropped-without-close* path (and any error path in `open` that returns `Err` after acquiring fds) leaks.
    - Fix: every primitive's `Drop` closes its fds unconditionally; `open` uses acquire-then-fallible-then-on-err-drop (`?` with RAII guards), never "open fd, then maybe return Err and forget it".
    - Cost avoided: a ulimit crash ~hours into a long-running node (the leak is invisible in a 10-cycle test).
    - Muscle: `Drop` is the safety net; `close()` only adds *ordering*. Reapplies at: W98 gc handle teardown, W99 raft state fds, W100 SHIP 24h soak.

  - **(NEWBIE) When `test_engine_hlc_per_db_not_shared` shows Db A's clock jumping:**
    - Symptom: A's logical counter advances after B's 1000 writes, with no A traffic.
    - Why: `HlcClock` was a `static`/`lazy_static` process-global "for convenience", so all `Db` share it.
    - Fix: `clock: HlcClock` is a per-`EngineInner` field constructed in `open`.
    - Cost avoided: test-harness flakiness and, worse, cross-`Db` op-ordering coupling that masks real MVCC bugs in W98.
    - Muscle: per-instance state belongs in the instance, never in a `static`. Reapplies at: W98 MVCC snapshot ts, W100 multi-db chaos harness.

  - **(SENIOR) When `test_engine_open_under_50ms_empty_dir` reports ~300 ms on an empty dir:**
    - Symptom: empty dir, no data, yet open is slow.
    - Why: open eagerly preloads/warms structures (e.g. allocates the full bloom pool, or `fsync`s a fresh manifest) that an empty dir doesn't need.
    - Fix: lazy-init bloom pool to first SST; manifest write is a single small append, not a sync-per-field.
    - Cost avoided: 250 ms × every process restart — multiplied across test runs and deploys, real wall-clock waste.
    - Muscle: open cost should scale with data present, not with capacity configured. Reapplies at: W100 SHIP cold-start budget, W102 vector-db open.

  - **(SENIOR) When `test_engine_recovery_invoked_on_dirty_wal` shows recovery NOT called:**
    - Symptom: WAL has uncommitted records; open completes silently; new writes proceed; next crash loses the un-recovered data.
    - Why: the `wal.has_uncommitted()` check is missing, or runs *after* gc/writes are already live (race).
    - Fix: in `Db::open`, immediately after bufpool+wal+lsm-core are constructed, check `wal.has_uncommitted()`; if true run `recovery::Recovery::recover` synchronously; THEN spawn gc and start accepting writes.
    - Cost avoided: silent data loss — the worst class of bug, invisible until the second crash.
    - Muscle: recovery is a strict precondition for accepting writes; the ordering is deterministic, not best-effort. Reapplies at: W97 Fri recovery integration, W100 SHIP startup, W92 ledger startup.

  - **(SENIOR) When `test_engine_no_mutex_on_facade` reveals `Arc<Mutex<EngineInner>>`:**
    - Symptom: `size_of::<Db>()` > one pointer; `Db::get` asm shows a `lock` prefix; concurrent reads serialize.
    - Why: the "easy to share across threads" reflex wrapped the whole inner in one `Mutex`.
    - Fix: `Db { inner: Arc<EngineInner> }`; share via `Arc::clone`; each primitive's own fine-grained lock stands. If a *specific* sub-field needs interior mutability, use `parking_lot::RwLock` on that field only.
    - Cost avoided: collapse of read throughput from N-core parallel to single-threaded — a 10×+ regression on a read-heavy workload, with green correctness tests.
    - Muscle: facade-level locks serialize the whole API; granular per-primitive locking is the LSM standard. Reapplies at: W74 matching-engine façade, W98 mvcc snapshot access, every database engine.

  - **(EXPERT) When `test_engine_close_reverse_order` shows out-of-order drop:**
    - Symptom: drop log shows `bufpool` before `gc`; gc's last touch of bufpool reads freed pages (segfault under ASAN).
    - Why: relied on Rust struct-field `Drop` order (declaration order, top-to-bottom) for cross-primitive cleanup — fragile and silently wrong if fields are reordered.
    - Fix: explicit `Db::close(self)` taking `self` by value, draining in explicit reverse order: gc → txn_manager → wal flush → lsm checkpoint → bufpool. The `Drop` impl is a best-effort log-only fallback for when `close` is forgotten.
    - Cost avoided: a use-after-free at shutdown — intermittent, kill-dependent, and brutal to reproduce.
    - Muscle: shutdown ordering needs an explicit method; never trust `Drop` order for cross-primitive teardown. Reapplies at: W98 gc+txn teardown, W99 raft+Db shutdown, every multi-primitive composition.
