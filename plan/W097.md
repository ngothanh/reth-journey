  - 🔧 **Why this matters**: engine is the composition root.   #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: a database engine must orchestrate ~8 independent primitives with strict dependency ordering at open + reverse ordering at close. Get the order wrong and either startup crashes (lsm-core registers SSTables in not-yet-built bufpool) or shutdown segfaults (lsm-core's Arc<BufferPool> outlives buffer pages held by gc). The composition is the inheritance proof.

  - **Requirements** — write in `crates/mini-db/notes/97tue_engine_design.md`:
    - R1. `Db { inner: Arc<EngineInner> }` is the facade; `EngineInner` holds field-level handles to lsm, wal, txn_manager, bufpool, bloom_pool, clock, backpressure, cfg, gc_handle.
    - R2. `Db::open(cfg)` constructs primitives in dependency order: bufpool → wal → lsm-core → bloom_pool → txn_manager → gc.
    - R3. `Db::close(self)` drains in reverse order: gc, txn_manager, wal flush, lsm checkpoint, bufpool.
    - R4. NO mutex on the Db facade — internal primitives carry their own locking discipline.
    - R5. Recovery integration: if `wal.has_uncommitted()` is true, route through `recovery::Recovery::recover` BEFORE returning from open.
    - R6. `Db::open` returns in < 50 ms on empty dir; < 500 ms on 1 GB SSTable dataset.
    - R7. No panic in 1000-cycle open/close stress; no leaked fds (verified via `lsof` smoke).
    - R8. HlcClock is per-Db (not shared by accident across test instances) — prevents test harness drift.
    - R9. backpressure::Limiter is wired around write entry points; flood test confirms `Err(Backpressure)` returns past limit.

  - **Design walk-through** — answer each:
    - D1. Why is the open order bufpool first, then wal, then lsm-core? (lsm-core registers SSTables in bufpool on open; bufpool must exist; wal registers WAL files in bufpool too.) What goes wrong if reversed?
    - D2. Why must close be reverse order? (lsm-core has Arc<BufferPool>; if bufpool drops first, lsm-core's later flush hits dangling pages.)
    - D3. Why no Mutex on the Db facade? (Each primitive owns its own lock; wrapping with Db-level Mutex would serialize all ops including reads.) How does `Arc<EngineInner>` give cheap cross-thread share without lock?
    - D4. Recovery placement: BEFORE any new write is accepted; AFTER all primitives are constructed but BEFORE gc/backpressure tasks spawn. Why?
    - D5. HlcClock per-Db vs process-singleton: test harness has 2+ Db instances; per-Db means each has its own clock; advantages? (Test isolation.) Risks? (Cross-Db op ordering undefined.) Default: per-Db; document.
    - D6. **Pre-mortem**: write the 5-step interleaving where a forgotten `Db::close` call leaks WAL fds. After 1000 open/close cycles, the process hits ulimit; `lsof` shows accumulating fds. What RAII pattern catches this?

  - **Output**: `notes/97tue_engine_design.md` with R1–R9 + D1–D6 + open/close ordering diagram.

- [ ] **Build**: `crates/mini-db/src/kv.rs` — `get(key) -> Option<Value>` checks memtable → immutable memtables → SSTables level-by-level with bloom rejection FIRST. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: get() is the hottest read path. Bloom-filter false-positive cost dominates if bloom isn't consulted FIRST before SST disk read. Get this wrong, throughput tanks 10×. Downstream consumers: W98 mvcc.rs (wraps with snapshot-filtering), W100 chaos tests, W102 vector-db pulls payload via this API.

  #### Phase 1 — Problem, requirements, design (~25 min)

  - **The problem this primitive solves**: a textbook LSM read traverses memtable → SSTables. Memtable hits are cheap (in-RAM); SST hits cost disk I/O (~100 µs cold, ~5 µs warm bufpool). Bloom filter rejects "definitely-absent" keys with 1 cache-line read (~5 ns); skip the bloom, the disk read happens for every absent key. At ~99% absent rate (Zipfian workload), missing the bloom is a 10× throughput loss.

  - **Requirements** (write in `notes/97tue_kv_get_design.md`): (R1) bloom check ALWAYS before SST disk read; (R2) NO bloom on memtable (would hide writes); (R3) `Value::{Live(Bytes), Tombstone}` enum; `into_value()` collapses Tombstone → None; (R4) tombstone bytes never returned to caller as "real" value; (R5) get() returns in < 10 µs P50 / < 100 µs P99 on warm bufpool 1 GB dataset; (R6) bloom FP rate ≤ 1.5% at 10 bits/key; (R7) 100% recall on 100k random keys via proptest match against HashMap reference.

  - **Design questions**: (D1) Where exactly does the bloom check sit in the code? (Guard clause: `if !bloom.contains { continue; }` BEFORE any `sst.get`.) (D2) Why no bloom on memtable? (Writes go to memtable first; bloom would filter not-yet-flushed writes.) (D3) Memtable order: current first or immutable first? (Current first — has the newest writes.) (D4) **Pre-mortem**: write the 5-step interleaving where a code reorder puts `sst.get` before `bloom.contains` — disk I/O happens anyway, bloom is a no-op. What integration test catches this? (Mock disk read; assert not called for known-absent keys.)

**Wednesday — mini-db write path**

- [ ] **Build**: `crates/mini-db/src/kv.rs` — `put(key, value) -> Result<()>` writes WAL FIRST then memtable; group-commit honored; durability boundary. (~total 2.5 hrs across 3 phases)
  - 🔧 **Why this matters**: write path is the durability boundary. WAL-before-memtable ordering is a HARD invariant: if memtable is updated first and crash happens before fsync, recovery omits the write but in-process readers already saw it — linearizability silently broken. Downstream consumers: W98 MVCC (wraps with txn write-set staging), W99 raft path (appends via apply()).

  #### Phase 1 — Problem, requirements, design (~40 min)

  - **The problem**: durability requires fsync; per-op fsync caps throughput at ~100 ops/sec on consumer SSD (~10 ms/fsync). Group-commit amortizes one fsync across N puts (~1 µs/op at N=10k). But WAL must complete fsync BEFORE memtable insert visible to readers — else readers see uncommitted data that crash loses.

  - **Requirements** (write in `notes/97wed_kv_put_design.md`): (R1) order is strict: backpressure guard → HLC ts → WAL append → WAL fsync (group-commit-aware) → memtable insert. (R2) backpressure acquired BEFORE WAL (don't waste IO on a rejected request). (R3) timestamp from HLC, never `Instant::now()` (HLC needed for cross-node ordering in W99). (R4) `wal::SyncMode::Periodic` (group commit) hits ≥ 500 k puts/sec single-thread; `SyncMode::Always` ≥ 100 k. (R5) 32-thread put barrage of 1M keys; all readable post-commit. (R6) kill -9 mid-batch; recovery yields state matching fsynced LSN exactly. (R7) flood at 10× rate gets ~10% admit + 90% `Err(Backpressure)`. (R8) sync_up_to coalesces concurrent puts into one fsync via condvar.

  - **Design questions**: (D1) Why is order strict? Trace the bad interleaving: memtable_put → reader sees value → crash → WAL never fsynced → recovery loses → reader's snapshot lies. (D2) sync_up_to(lsn) semantics: not "fsync just my record" but "fsync everything up to and including lsn". Why? (Coalesces 1000 concurrent puts into 1 fsync — N=1000 amortization.) (D3) HLC monotone-nondecreasing: what if W99 raft path adjusts HLC backward based on remote ts? (Assert in lsm-core memtable_put: incoming ts ≥ last ts for key.) (D4) **Pre-mortem**: write the 5-step interleaving where a code reorder puts memtable_put BEFORE WAL append; reader thread sees value; SIGKILL; recovery; reader's value is gone. What integration test catches this? (kill -9 between memtable insert and WAL append in a fault injector.)

  #### Phase 1 — Problem, requirements, design (~50 min)

  - **The problem**: a merging iterator over memtable + per-level SSTables must (a) yield in key-ascending order, (b) de-dup by picking newest visible version per key, (c) filter tombstones, (d) respect snapshot ts, (e) survive concurrent compaction without reading freed pages. Each rule is independently testable; combined they form the keystone of mini-db reads.

  - **Requirements** (write in `notes/97thu_scan_design.md`): (R1) ascending key order, NO duplicates; (R2) tombstones skipped (not yielded as None/empty); (R3) `Bound::{Included, Excluded, Unbounded}` for both ends; convention: inclusive lower, exclusive upper (RocksDB); (R4) PinGuard via bufpool keeps SST pages pinned for scan lifetime — compaction skips/waits; (R5) snapshot filter: `scan_at(snap)` skips versions with ts > snap; (R6) reverse-range (lower > upper) returns `Err(InvalidRange)`, never infinite loop; (R7) 1M-key scan throughput ≥ 10M kv/sec (memory bound); 100% recall vs HashMap reference; (R8) concurrent compaction + scan stress 60 s: no crash, no missing/extra keys.

  - **Design questions**: (D1) Merge iter version ordering: (key ASC, ts DESC) — first version per key is the newest visible. Why? (Dedup happens implicitly: take first, skip until key changes.) (D2) Tombstone representation: `Versioned::Tombstone` vs `Versioned::Live(bytes)` at lsm-core layer — not empty-bytes vs non-empty. Why? (Empty bytes is a legitimate value.) (D3) PinGuard lifetime: tied to `'a` of Scan; compaction sees pinned files, skips or waits. What's the deadlock risk? (Long scan + active compaction = compaction stalls; cap scan lifetime or fall-back-pull from disk.) (D4) **Pre-mortem**: caller drops Scan mid-iteration after walking 50%; PinGuard releases; compaction proceeds; subsequent re-scan from same start point sees DIFFERENT keys (compaction merged). Is this correctness or expected? (Expected — scan is a point-in-time snapshot, not transactional unless `scan_at(snapshot)`.)

  #### Phase 3 — Failure cards

  - **When `test_scan_ascending_no_duplicates` reports key emitted twice**: Symptom: K=5 appears in scan output at positions 4 and 17 because L0 and L2 SSTs both contain it. Why: merge iterator emits all versions; Scan didn't dedup. Fix: Scan tracks `last_key: Option<Bytes>`; in next() loop, if k == last_key.as_ref(), continue (skip duplicates). Merge iter must emit (key ASC, ts DESC) so first version is newest. Muscle: merge iterator gives raw versions; Scan does dedup. Reapplies at: W98 MVCC scan, W102 vector-db enumeration.

  - **When `test_scan_skips_tombstones` returns Some((k, b""))**: Symptom: scan returns 100 results including tombstones as empty-bytes values. Why: tombstone represented as `Versioned::Live(empty_bytes)` instead of `Versioned::Tombstone`. Caller can't distinguish. Fix: at lsm-core layer, `Versioned` enum is `{Live(Bytes), Tombstone}`; Scan loop matches and `continue` on Tombstone. Muscle: tombstones are control data, never values; type enforces. Reapplies at: W97 Wed delete (same lesson).

  - **When `test_concurrent_compaction_scan_stress` panics with use-after-free**: Symptom: scan reads page that compaction freed; segfault or garbage value. Why: PinGuard not actually pinning; compaction proceeds blind to active scans. Fix: PinGuard increments refcount on SST files in scan range at construction; compaction checks refcount and skips pinned files (or waits). Decrement refcount on PinGuard::drop. Muscle: any long-lived iterator over GC'd storage needs pin-counting. Reapplies at: W98 MVCC snapshot, W100 chaos suite.

  - **When `test_scan_at_snapshot` returns fewer than 50 keys**: Symptom: snapshot captured at op 50; scan_at returns 30 keys instead of 50. Why: GC dropped some pre-snapshot versions; `min_active_snapshot_ts` wasn't respected; user's snapshot is "too old". Fix: GC consults `txn_manager.min_active_snapshot_ts()`; never drops versions newer than that. If user holds Snapshot beyond `gc_grace` (e.g., 1 hour), return `Err(SnapshotTooOld)` on scan_at. Document grace period.

**Friday — mini-db crash recovery via `recovery`**

- [ ] **Build**: `crates/mini-db/src/engine.rs` — `Db::open()` calls `recovery::Recovery::recover` (ARIES analysis → redo → undo) BEFORE accepting writes. (~total 3 hrs across 3 phases)
  - 🔧 **Why this matters**: recovery is THE durability proof. Mini-db's inheritance pitch fails if recovery has bugs — every module above stands on the assumption that on-disk state + WAL replay reconstructs the last fsynced consistent state. Downstream consumers: W98 MVCC commit/abort use same recovery primitives, W99 raft replica state-machine resync, W100 chaos suite tests this under aggressive kills.

  #### Phase 1 — Problem, requirements, design (~50 min)

  - **The problem**: a crash leaves on-disk SSTables + WAL tail. SSTables are at some LSN ≤ last_fsync. WAL tail has records LSN > last_applied that need redo, plus possibly aborted/uncommitted txns that need undo. ARIES 3-pass (analysis → redo → undo) is canonical; deviations introduce subtle data corruption.

  - **Requirements** (write in `notes/97fri_recovery_design.md`): (R1) recovery runs BEFORE any new write is accepted; sync, blocking, in Db::open; (R2) redo is idempotent (re-applying yields same state); (R3) undo only applied to uncommitted txns from analysis pass; (R4) `last_applied_lsn` from lsm manifest gates redo — never replay already-flushed records; (R5) torn-page on WAL tail classified as "tail truncation" (stop reading, truncate WAL); CRC failure in middle = real corruption (fail open with explicit error); (R6) abort-without-begin = log warning + skip (not panic); (R7) 100k WAL record recovery ≤ 2 sec on NVMe; (R8) running recover() twice produces same state (idempotent); (R9) 100-trial kill -9 stress: every re-open yields state = "all writes whose WAL fsync completed pre-crash"; (R10) periodic checkpoint writes manifest entry; recovery starts from checkpoint LSN.

  - **Design questions**: (D1) ARIES analysis pass: builds txn_table from begin-records forward; records dirty pages. What if WAL has "abort T1" without "begin T1"? (Log warning, skip — could be from rotated WAL segment.) (D2) Redo idempotency: re-applying a Put to memtable does what? (Same memtable_put with same ts; lsm-core memtable_put is idempotent on (key, ts).) (D3) Undo: only for txns active at crash time; reverses their effects to last savepoint. Why not just truncate WAL? (Future txns in WAL after the uncommitted may still be valid; granular undo preserves them.) (D4) `last_applied_lsn` from lsm manifest: how persisted? (At each L0 flush, manifest entry records the flushed LSN range; recovery starts from max(checkpoint_lsn, last_applied_lsn) + 1.) (D5) **Pre-mortem**: Db::open returns the handle, GC thread spawns and starts writes BEFORE recovery completes. What test catches? (Instrument with a counter that records "write accepted at time T" and "recovery completed at time T'"; assert T > T'.)

  #### Phase 3 — Failure cards

  - **When `test_recovery_no_double_replay` shows duplicate records**: Symptom: 10k records normal closed; re-open; get() returns Some(stale_value) for keys that were updated post-flush; recovery replayed already-flushed records on top of new ones. Why: `last_applied_lsn` not consulted; recovery starts from WAL beginning. Fix: `PageProvider::last_applied_lsn()` from lsm manifest; recovery starts from `max(checkpoint_lsn, last_applied_lsn) + 1`. Muscle: idempotency + LSN gating; never replay what's already on disk. Reapplies at: W99 raft replica resync, W100 chaos.

  - **When `test_recovery_torn_tail_truncates` panics on CRC fail**: Symptom: WAL last record's CRC bad; recovery panics with "WAL corrupted"; service stuck. Why: recovery treats any CRC fail as fatal. Fix: classify by position — CRC fail on the very last record = torn-page (truncate WAL, log info); CRC fail in middle = real corruption (return Err(WalCorrupted) with offset). Muscle: tail truncation is normal after crash; middle corruption is fatal. Distinguish. Reapplies at: W100 SHIP startup, W92 ledger recovery.

  - **When `test_recovery_no_writes_accepted_during` shows a write at T=50ms recovery at T=200ms**: Symptom: a write accepted during recovery; later overwritten by recovery's redo; data appears to silently disappear. Why: GC/backpressure tasks spawned before recovery completed. Fix: open() is strictly sequential: bufpool → wal → lsm-core → recovery (blocks) → THEN txn_manager, gc spawn. open() returns only after recovery complete. Muscle: recovery is a strict precondition; no concurrent operations until it returns. Reapplies at: W92 ledger v1.0 startup, every WAL-backed system.

  - **When `test_recovery_kill9_stress_100_trials` shows 1 trial with state mismatch**: Symptom: 99/100 trials green; 1 trial post-recovery state has a write that wasn't fsynced pre-crash. Why: the test's "fsynced subset" computation is wrong, OR there's a real bug in fsync ordering. Investigate: add an assertion at write path that returns the LSN ACTUALLY fsynced; compare to recovery's last LSN. Fix: depends on root cause; likely group-commit horizon issue (write A submitted, group-commit ticks for write B, fsync flushes both, but only B's completion fires — A appears unfsynced).
