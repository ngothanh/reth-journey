- [ ] **Build**: `crates/consensus-raft/src/log.rs` — `LogEntry { term, index, command, lsn: Lsn }`. Backed by
  `wal::Wal` for durability. (~150 min)
  - **Why**: The log is Raft's durability boundary. Every committed entry must be on disk before commit_index advances. The LSN field allows alignment with the underlying wal crate's positional addressing.
  - **Design**:
    ```rust
    pub struct LogEntry {
        pub term: u64,
        pub index: u64,
        pub command: Bytes,    // app-specific bytes
        pub lsn: Lsn,          // wal crate's Log Sequence Number
    }

    pub trait LogStorage {
        fn append(&mut self, entry: LogEntry) -> Result<Lsn, _>;
        fn append_batch(&mut self, entries: Vec<LogEntry>) -> Result<Lsn, _>;
        fn truncate_after(&mut self, index: u64) -> Result<(), _>; // conflict resolution
        fn entry(&self, index: u64) -> Result<Option<LogEntry>, _>;
        fn last_index(&self) -> u64;
        fn last_term(&self) -> u64;
        fn fsync(&mut self) -> Result<(), _>;
    }

    pub struct WalLogStorage {
        wal: wal::Wal,
        index_to_lsn: BTreeMap<u64, Lsn>,
        last_index: u64,
        last_term: u64,
    }
    ```
    **Invariants**:
    - `append` does NOT fsync; caller batches and calls `fsync()` once before reply.
    - `truncate_after(N)` removes entries N+1.., updates last_index/last_term to entry[N].
    - `last_index` and `last_term` cached for O(1) read (election-restriction check is hot).
    - Index gaps are impossible (sparse → corruption). Entries appended in order.
  - **Build steps**:
    1. (~20 min) Define LogEntry + LogStorage trait.
    2. (~40 min) WalLogStorage impl: append wraps wal::Wal::append; truncate uses wal's `truncate_to_lsn`.
    3. (~20 min) Crash-recovery: on open, scan wal, rebuild index_to_lsn map; verify no gaps.
    4. (~20 min) Tests: append 10k entries; crash; recover; verify last_index/last_term correct.
    5. (~30 min) Tests for truncate_after: append 10k, truncate at 5000, verify entry(5001) returns None and entry(5000) still readable.
    6. (~20 min) fsync batching: append_batch + fsync once is ≥ 10× faster than per-entry fsync. Microbench confirms.
  - **Pitfalls**:
    - *fsync per append*: kills throughput from 100k/s to 1k/s. **Symptom**: leader latency awful. **Fix**: batch via append_batch; fsync once before AppendEntries reply.
    - *Truncate gap*: truncate_after(N) but entry N missing → undefined state. **Fix**: explicit precondition check.
    - *Index/LSN drift*: rebuilding index_to_lsn after crash → off-by-one between durable and in-memory. **Fix**: replay from start of last segment, not from arbitrary offset.
  - **Test scenarios**: crash after append-no-fsync → recovery sees pre-append state; crash after fsync → recovery sees post-append state.
  - **Acceptance**: 100k entries durable + replayable in < 5s; truncate semantics correct.
  - **Downstream**: replication.rs (Thu) consumes; W67+ snapshot (compaction) on top.

**Wednesday — evmone advanced mode + runtime-thread-per-core v0.5: backpressure-aware scheduling** [NEW v2]

- [ ] Advanced interpreter with caching. (~30 min)
  - **Why**: evmone advanced mode is THE 2x speedup. Pre-analyzes bytecode into basic blocks (sequences without branches), pre-computes total gas + stack delta per block, then dispatches per-block instead of per-opcode. Validates jump destinations once.
  - **Read first**: evmone `lib/evmone/advanced_analysis.cpp::analyze`; "evmone fast EVM implementation" presentation (DevCon V or related talks).
  - **Design** (conceptual):
    ```text
    Bytecode → Analysis → Vec<BasicBlock>
    BasicBlock { gas_cost: u32, stack_delta: i32, stack_underflow_check: u8, code: Range<usize> }
    Dispatch per block: 1 gas check, 1 stack check, then run N opcodes.
    Cost: pre-analysis O(code_len); amortized over execution.
    Win: ~2× because per-block overhead replaces per-opcode overhead.
    ```
  - **Build steps**: read-only today.
    1. (~10 min) Walk `analyze()` in evmone source.
    2. (~10 min) Note the JUMPDEST validation pre-computed bitmap (revm has similar in `JumpTable`).
    3. (~10 min) Plan: exec-vm can adopt basic-block analysis incrementally — first ship analysis result as opaque `Analysis` struct attached to Bytecode; dispatch consumes it for jump validation; later add gas/stack pre-compute.
  - **Acceptance**: design notes captured; W64 perf-PR candidate noted.
- [ ] [NEW v2] **Build**: extend LocalExecutor to consult `backpressure` signal; pause shard if downstream queue full. (~150 min)
  - **Why**: Without backpressure-aware scheduling, a fast shard floods a slow downstream shard, eventually OOMing the queue OR forcing the cross-shard channel to drop. Backpressure-aware scheduling: when downstream sensor trips, the upstream shard PAUSES tasks producing to that downstream until pressure releases. Classic flow-control.
  - **Read first**: ScyllaDB's pause/resume of shard tasks; `backpressure` crate's Sensor + Strategy interface.
  - **Design**:
    ```rust
    pub struct LocalExecutor {
        // ... existing fields ...
        downstream_sensors: HashMap<ShardId, Arc<Sensor>>,
        paused_for: Option<ShardId>,         // currently paused due to this downstream
        ready_queue: VecDeque<TaskBox>,
        backpressure_queue: HashMap<ShardId, VecDeque<TaskBox>>, // tasks awaiting downstream
    }

    impl LocalExecutor {
        pub fn submit(&mut self, target: ShardId, task: TaskBox) {
            if self.downstream_sensors[&target].is_tripped() {
                self.backpressure_queue.entry(target).or_default().push_back(task);
                self.paused_for = Some(target);
            } else {
                self.ready_queue.push_back(task);  // local task
            }
        }
        pub fn tick(&mut self) {
            // Process ready_queue; on each task, check if any sensor cleared:
            for (sid, sensor) in &self.downstream_sensors {
                if !sensor.is_tripped() {
                    if let Some(q) = self.backpressure_queue.get_mut(sid) {
                        self.ready_queue.extend(q.drain(..));
                    }
                }
            }
            self.run_ready_queue();
        }
    }
    ```
    **Invariants**:
    - A task is in `backpressure_queue[D]` iff `D`'s sensor is tripped at submission time.
    - When sensor clears, ALL queued tasks for that downstream become ready.
    - No task processed while its downstream sensor is tripped.
    - Local tasks (no downstream dependency) NEVER backpressured.
  - **Build steps**:
    1. (~20 min) Extend LocalExecutor with sensor map + backpressure_queue.
    2. (~30 min) `submit()` with sensor check + routing.
    3. (~25 min) `tick()` drains backpressure_queue on sensor clear.
    4. (~30 min) Integration with cross_shard channel (W57): when channel's capacity > threshold_high, channel trips downstream's sensor; when < threshold_low, channel clears it. Hysteresis prevents thrash.
    5. (~25 min) Tests: 2-shard sim; shard 0 floods shard 1; verify shard 0 backpressures within 100ms; shard 1 drains; shard 0 resumes.
    6. (~20 min) Adversarial: pathological all-shards-flooding-all → verify no deadlock (no cycle in backpressure dependency graph because each task has at most 1 downstream).
  - **Pitfalls**:
    - *Backpressure deadlock*: A waits for B; B's queue has task that needs A's queue. Cycle. **Symptom**: cluster wedges. **Fix**: tasks can only have 1 downstream dependency; cycles avoided by design (cross-shard graph is a DAG per request).
    - *Sensor flicker thrash*: rapid trip/clear cycles → spurious queue drain/rebuild. **Symptom**: high overhead. **Fix**: hysteresis — high/low thresholds with gap (e.g., trip at 80%, clear at 50%).
    - *Starvation of slow shard*: fast shard's backpressure queue grows unboundedly. **Symptom**: OOM. **Fix**: backpressure_queue is itself bounded; when full, REJECT submission with error → caller decides (drop, retry, dead-letter).
  - **Acceptance**: 2-shard flood test exhibits steady-state without queue growth; no deadlocks under all-pairs flooding.
  - **Downstream**: matching-engine downstream (W60+) consumes; marketdata broadcast (W85+); ledger (W90+).

- [ ] **Build**: `crates/consensus-raft/src/replication.rs` — leader sends AppendEntries; followers persist via wal then
  ack; leader bumps commitIndex when majority replicates. (~150 min)
  - **Why (MAX DETAIL)**: Log replication is Raft's hot path. AppendEntries IS the heartbeat AND the data path. Getting `next_index/match_index` tracking right is hard — etcd had 3+ bugs here in first year.
  - **Read first**: Ongaro §5.3 (log replication); raft-rs `src/raft.rs::handle_append_entries`, `step_leader`.
  - **Design**:
    ```rust
    impl<S: StateMachine> RaftState<S> {
        /// Leader sends AppendEntries to one follower.
        pub fn send_append_entries(&mut self, peer: NodeId) {
            let Role::Leader { next_index, .. } = &self.role else { return };
            let prev_index = next_index[&peer] - 1;
            let prev_term = self.log.entry(prev_index).unwrap().map(|e| e.term).unwrap_or(0);
            let entries = self.log.entries_from(next_index[&peer], 100); // batch up to 100
            let rpc = AppendEntries {
                term: self.persistent.current_term,
                leader_id: self.node_id,
                prev_log_index: prev_index,
                prev_log_term: prev_term,
                entries,
                leader_commit: self.volatile.commit_index,
            };
            self.send(peer, RaftRpc::Append(rpc));
        }

        pub fn handle_append_entries(&mut self, rpc: AppendEntries) -> AppendEntriesReply {
            // term check (step down if higher, reject if lower)
            if rpc.term < self.persistent.current_term {
                return AppendEntriesReply { term: self.persistent.current_term, success: false,
                                              conflict_index: None, conflict_term: None };
            }
            if rpc.term > self.persistent.current_term {
                self.become_follower(rpc.term, Some(rpc.leader_id));
            }
            // Reset election timer
            if let Role::Follower { last_heartbeat, .. } = &mut self.role {
                *last_heartbeat = Instant::now();
            }
            // Log matching check
            let existing = self.log.entry(rpc.prev_log_index).unwrap();
            let log_ok = match existing {
                None if rpc.prev_log_index == 0 => true,  // empty log + prev=0 is OK
                Some(e) if e.term == rpc.prev_log_term => true,
                _ => false,
            };
            if !log_ok {
                // conflict optimization: return where our log diverges
                let conflict_index = self.log.last_index().min(rpc.prev_log_index);
                let conflict_term = self.log.entry(conflict_index).ok().flatten().map(|e| e.term);
                return AppendEntriesReply { term: self.persistent.current_term, success: false,
                                              conflict_index: Some(conflict_index), conflict_term };
            }
            // Truncate conflicting suffix and append new entries
            for (i, entry) in rpc.entries.iter().enumerate() {
                let idx = rpc.prev_log_index + 1 + i as u64;
                if let Some(existing) = self.log.entry(idx).unwrap() {
                    if existing.term != entry.term {
                        self.log.truncate_after(idx - 1).unwrap();
                        // append from i onwards
                        for e in &rpc.entries[i..] {
                            self.log.append(e.clone()).unwrap();
                        }
                        break;
                    }
                } else {
                    self.log.append(entry.clone()).unwrap();
                }
            }
            self.log.fsync().unwrap();  // CRITICAL: before reply

            // Update commit_index
            if rpc.leader_commit > self.volatile.commit_index {
                let last = self.log.last_index();
                self.volatile.commit_index = rpc.leader_commit.min(last);
            }
            self.apply_committed();

            AppendEntriesReply { term: self.persistent.current_term, success: true, conflict_index: None, conflict_term: None }
        }

        pub fn handle_append_entries_reply(&mut self, from: NodeId, reply: AppendEntriesReply) {
            let Role::Leader { next_index, match_index, .. } = &mut self.role else { return };
            if reply.term > self.persistent.current_term {
                self.become_follower(reply.term, None);
                return;
            }
            if reply.success {
                // entry at next_index..last_sent now replicated
                let last_sent = next_index[&from] - 1;  // before this call (need to track per-rpc)
                match_index.insert(from, last_sent);   // simplified; production tracks per-rpc
                next_index.insert(from, last_sent + 1);
                self.maybe_advance_commit();
            } else {
                // Fast backoff via conflict_index
                if let Some(ci) = reply.conflict_index {
                    next_index.insert(from, ci);
                } else {
                    // fallback decrement
                    let n = next_index.get_mut(&from).unwrap();
                    if *n > 1 { *n -= 1; }
                }
                // retry on next tick
            }
        }

        fn maybe_advance_commit(&mut self) {
            let Role::Leader { match_index, .. } = &self.role else { return };
            let mut indices: Vec<u64> = match_index.values().copied().collect();
            indices.push(self.log.last_index()); // self
            indices.sort_unstable();
            let n = indices.len();
            let majority = indices[n / 2]; // median = quorum
            // Per §5.4.2: only commit entries from CURRENT term via this rule
            if let Some(e) = self.log.entry(majority).unwrap() {
                if e.term == self.persistent.current_term && majority > self.volatile.commit_index {
                    self.volatile.commit_index = majority;
                    self.apply_committed();
                }
            }
        }
    }
    ```
    **Invariants**:
    - Followers FSYNC log before replying success. Without this, leader believes commit but follower might lose entries on crash.
    - Leader advances commit_index ONLY when:
      (a) majority of nodes have match_index ≥ N, AND
      (b) log[N].term == current_term (§5.4.2 — prevents committing entries from prior terms via this rule).
    - Conflict-index optimization: follower returns its `conflict_index` so leader fast-skips instead of decrementing one at a time.
  - **Build steps** (granular):
    1. (~30 min) `send_append_entries` with batch of 100 entries.
    2. (~40 min) `handle_append_entries` with log matching + truncate-conflicting + append + fsync.
    3. (~30 min) `handle_append_entries_reply` with success path + conflict-index fast backoff.
    4. (~20 min) `maybe_advance_commit` with §5.4.2 current-term guard.
    5. (~20 min) `apply_committed`: drains entries last_applied+1..commit_index into state_machine.
    6. (~10 min) Tests: leader appends to 1 follower; majority replicates; commit advances. Then kill follower, append more; commit stalls; recover follower, catches up.
  - **Pitfalls** (named, distributed):
    - *commit prior-term entries via majority rule alone*: paper §5.4.2 scenario — leader from later term commits an entry from earlier term via majority that is then overwritten. **Symptom**: committed data lost (rare, Figure 8 scenario). **Fix**: only commit via current-term entry; commit advances "free" through prior-term entries once a current-term entry passes quorum.
    - *Follower fsync omission*: success reply without fsync → leader thinks committed → if all replicas crash, data lost. **Symptom**: rare but catastrophic data loss. **Fix**: explicit fsync before reply.
    - *Stale AppendEntries during partition heal*: old leader's AppendEntries arrives at follower that's already at higher term. **Symptom**: confusion. **Fix**: term-check at start of handler (already in design).
    - *Log truncation on PRE-fsync data*: leader sends entries 100-200; follower fsyncs 100-150, then truncates 100-150 on next conflicting AppendEntries. Lost data? No — leader retains until majority match_index. **Fix**: leader's log is source of truth; follower truncations are safe because data still on leader.
    - *match_index regression*: bug allowing match_index[follower] to decrease (e.g., on retry). **Symptom**: commit progress oscillates. **Fix**: only set match_index from successful reply; never decrease.
  - **Test scenarios** (adversarial):
    - 5-node cluster, leader appends 1000 entries; ALL 5 commit within 50ms.
    - Partition 3-2: 3-node side leader commits; 2-node side stale. Reunite: 2-node side catches up via conflict-index fast-skip in O(1) RPC, not O(1000).
    - Crash leader mid-replication: new leader picks up entries replicated to majority; entries replicated only to minority MAY be overwritten by new leader.
    - Figure 8 scenario: replicated-but-not-committed prior-term entry — verify §5.4.2 prevents commit until current-term entry passes.
  - **Acceptance**: 1000-entry replication in 5-node cluster green; Figure 8 scenario rejected; partition heal converges in O(log) RPCs.
  - **Downstream**: W62 (membership), W67+ (raft v1.0 polish), W74+ (matching-engine over Raft replication).
