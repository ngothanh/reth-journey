  - 🔧 **Why this matters**: the log is Raft's durability boundary. Every committed entry must be on disk before commit_index advances. The LSN field aligns with the underlying wal crate's positional addressing. W56 election persistence, W67 snapshots, W74 matching-engine deterministic command log, W83+ ledger op log all depend on this primitive — `BTreeMap` index + per-append `Vec<u8>` alloc costs ~30% of leader CPU at 100k ops/s and is the canonical "convenient API" cliff.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: per-append fsync collapses throughput from 100k/s to 1k/s (canonical "hash-table-of-disaster" bug). `BTreeMap<u64, Lsn>` index allocates per-insert (~100 ns) and dominates the hot path. RLP encode that returns `Vec<u8>` allocates 100k mini-Vec/s. All three are bar-(c) violations hidden in obvious API shapes.

  - **Requirements** — write in `crates/consensus-raft/notes/59_log_design.md`:
    - R1. `LogEntry { term: u64, index: u64, command: Bytes, lsn: Lsn }`.
    - R2. `LogStorage` trait: `append`, `append_batch`, `truncate_after`, `entry`, `last_index`, `last_term`, `fsync`. `append` does NOT fsync; caller batches and calls `fsync()` once before reply.
    - R3. `WalLogStorage::index_to_lsn` is `VecDeque<Lsn>` keyed by `index - first_index`; NEVER `BTreeMap`.
    - R4. Append path encodes in-place into a per-shard `encode_scratch: Vec<u8>` reused across calls (capacity ~4 KiB, holds one batch). NEVER returns a fresh `Vec<u8>`.
    - R5. `last_index` and `last_term` cached as `u64` fields for O(1) read (election-restriction check is hot path).
    - R6. Index monotonic and dense; gaps impossible. `truncate_after(N)` updates `last_index = N`, removes entries N+1..
    - R7. Crash recovery: replay from start of LAST segment (not arbitrary offset); rebuild VecDeque; verify no gaps.
    - R8. Hot-path budgets: `append` ≤ 100 ns; `last_index()` ≤ 5 ns; `entry(idx)` ≤ 50 ns; `append_batch(100)` + `fsync()` ≤ 100 µs end-to-end on NVMe.

  - **Design walk-through**:
    - D1. Why is per-append fsync the canonical disaster? Walk the math: fsync ~10-50 µs; at 100k/s that's 1-5 seconds of fsync per second of work. Group commit (batch 100 + 1 fsync) restores 100k/s.
    - D2. `BTreeMap` vs `VecDeque` for `index_to_lsn`: since indices are STRICTLY MONOTONIC AND DENSE, BTreeMap is strictly worse than VecDeque. Compute the cost: BTreeMap insert is O(log n) cache-cold pointer chases + alloc per node; VecDeque push is amortized O(1) with no alloc once warmed. Pre-reserve to ~1 M entries (8 MB; fits in L3).
    - D3. Encode-into-buffer vs encode-returning-Vec: walk the alloc cost. The fix mirrors the W26 WAL `RecordFrame::encode(&mut BufMut)` API.
    - D4. `last_index`/`last_term` caching: election-restriction in `handle_request_vote` reads these on every RPC. If you scan the wal each time, you've shipped a quadratic election handler. Cache as fields; update on every append/truncate.
    - D5. Crash recovery: walk the post-crash state. If you replay from offset 0, recovery is O(log size); if you replay from the last segment's start, recovery is O(last segment) ≈ O(64 MB) ≈ ~100 ms. Document the WAL segment boundary.
    - D6. **Pre-mortem (load-bearing)**: write the 4-step path from "naive `BTreeMap<u64, Lsn>` + `Vec<u8>` encode return" to "30% of leader CPU spent in `alloc::alloc` and `BTreeMap::insert`."
  - **Output**: `notes/59_log_design.md` with R1–R8 + answers to D1–D6 + crash recovery state diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)

  - **When `index_to_lsn_is_vecdeque` finds BTreeMap and `bench_append_under_100ns` reports ~250 ns:**
    - Symptom: flame graph during a 100k-entry append bench shows `alloc::alloc` and `BTreeMap::insert` together at ~30% of CPU; leader p99 commit latency 5× the follower's.
    - Why: at 100k entries/sec, `index_to_lsn.insert` allocates a tree node on every call (~100 ns + heap fragmentation + cache miss on parent node ~7 ns). Since indices are strictly monotonic and dense in steady state, BTreeMap is strictly worse than `Vec`.
    - Fix: replace `index_to_lsn: BTreeMap<u64, Lsn>` with `index_to_lsn: VecDeque<Lsn>` keyed by `index - first_index` (track `first_index` separately). `append(lsn)` → `push_back(lsn)` (amortized O(1) with capacity reservation, zero per-call alloc once warmed). `truncate_after(idx)` → `truncate(idx - first_index + 1)`. `lookup(idx)` → `get(idx - first_index)`. Pre-reserve VecDeque to ~1 M entries at boot (8 B × 1 M = 8 MiB, fits in L3).
    - Cost avoided: ~100 ns per insert (~10 ms/s at 100k ops/s); eliminates allocator from append path; removes BTreeMap's per-insert 6-7 cache-line walk.
    - Muscle: when keys are dense + monotonic, `Vec`/`VecDeque` with a `first_index` offset is strictly better than tree map — BTreeMap is for sparse keys. **Reapplies at**: W67 raft snapshot index, W74 matching-engine event-log seq index, W83 ledger transfer log.

  - **When `append_no_fresh_vec_alloc` reports ~100k Vec allocs/s:**
    - Symptom: leader p99 commit latency 5× follower's because leader's encode allocates while follower's decode reads in place; allocator lock contention spikes under N writer threads; heap walks ~32 B per encoded entry (cache-cold each time).
    - Why: `append(entry)` encodes via `rlp::encode(&entry)` → returns `Vec<u8>` → memcpy into WAL. 100k entries/s = 100k mini-Vec allocs/s.
    - Fix: pre-allocate per-shard `encode_scratch: Vec<u8>` reused across calls (capacity 4 KiB, holds one batch). `append(entry)` calls `entry.encode(&mut encode_scratch)` (in-place encode via `Encodable::encode(&self, out: &mut dyn BufMut)` API), then WAL append copies from scratch, then `encode_scratch.clear()` (len=0, capacity preserved). Same pattern as W26 WAL `RecordFrame::encode`.
    - Cost avoided: ~50 ns alloc + ~50 ns dealloc per append = ~100 ns × 100k/s = 10 ms/s saved; allocator contention removed; encode writes hot-in-L1.
    - Muscle: serialization on bar-(c) hot path encodes INTO a caller-owned buffer, never RETURNS a fresh `Vec`. **Reapplies at**: W61 matching-engine event-log encode, W74 raft RPC encode, W77 aeron term-buffer claim+write, W83 ledger op encode.

  - **When `fsync_per_append_disaster_avoided` shows the wrong ratio:**
    - Symptom: throughput 1k/s instead of 100k/s; `iostat` shows 100% util at low queue depth.
    - Why: each `append` calls `wal.fsync()` internally "for safety."
    - Fix: `append` writes to wal buffer but does NOT fsync. Caller (replication.rs) accumulates a batch then explicitly `log.fsync()` once before sending AppendEntries reply. The wal layer also supports group-commit so multiple raft instances batching independently share one fsync.
    - Muscle: durability is a CALLER-CONTROLLED operation; primitives expose it explicitly, never bake it into append. Reapplies at: W56 raft persist, W83+ ledger journal.

  - **When `crash_recovery_no_gaps` finds an off-by-one drift:**
    - Symptom: post-crash `last_index = 9999` instead of 10000; entry 10000 in wal but not in index_to_lsn.
    - Why: rebuilding `index_to_lsn` after crash replayed from an arbitrary offset; missed a partial last entry.
    - Fix: replay from start of LAST SEGMENT (not arbitrary offset); validate entry checksums; stop on the first invalid; `last_index = highest valid index`.
    - Muscle: crash recovery's entry point is segment boundary, never an offset assumed safe. Reapplies at: W83+ ledger replay, W26 wal recovery.

  - **When `bench_last_index_under_5ns` reports ~200 ns:**
    - Symptom: election-restriction check (called per RequestVote) dominates RPC handler time.
    - Why: `last_index()` scans the wal each time instead of reading a cached field.
    - Fix: cache `last_index: u64` and `last_term: u64` as struct fields; update on every `append`/`truncate_after`.
    - Muscle: every hot-path read of a derivable quantity becomes a cached field. Reapplies at: W74 matching-engine `best_bid`/`best_ask` cached publication.

  - **5-year failure mode** (write in `notes/59_log_followup.md`): when SMR (shingled magnetic recording) or zoned storage devices become common in non-NVMe paths, sequential-only append plays nicely but truncate becomes expensive. Name the migration: how does `truncate_after` adapt to zoned semantics without breaking the LogStorage trait?
  - *Back-of-envelope*: matching-engine over Raft (W74) target = ≥ 100k commands/sec replicated; per-AppendEntries batch = 100 entries; per-batch fsync = ~10-50 µs on NVMe; **per-batch overhead budget ≤ 100 µs** (so end-to-end commit-from-leader-perspective ≤ 5 ms p99 — Raft's ~5× ms target). Per-entry encode: RLP-frame (~50 ns) + WAL append (~50 ns memcpy) + index_to_lsn `BTreeMap` insert (~100 ns). At 100k entries/sec single-thread that's ~20 ms/sec of pure log overhead — 2% of CPU, acceptable. **Critical: NO fsync per append — batch + single fsync** (per-append fsync drops throughput from 100k/sec to ~1k/sec, the canonical hash-table-of-disaster bug). The `index_to_lsn: BTreeMap<u64, Lsn>` grows unboundedly with the log; without truncation it OOMs after ~10 M entries (~32 B/entry × 10 M = 320 MiB). Snapshotting (W67) compacts it.
  - **Design**:
    ```rust
    pub struct LogEntry {
        pub term: u64,
        pub index: u64,
        pub command: Bytes,    // app-specific bytes
        pub lsn: Lsn,          // wal crate's Log Sequence Number
    }

    pub trait LogStorage {
        fn append(&mut self, entry: LogEntry) -> Result<Lsn, _>;
        fn append_batch(&mut self, entries: Vec<LogEntry>) -> Result<Lsn, _>;
        fn truncate_after(&mut self, index: u64) -> Result<(), _>; // conflict resolution
        fn entry(&self, index: u64) -> Result<Option<LogEntry>, _>;
        fn last_index(&self) -> u64;
        fn last_term(&self) -> u64;
        fn fsync(&mut self) -> Result<(), _>;
    }

    pub struct WalLogStorage {
        wal: wal::Wal,
        index_to_lsn: BTreeMap<u64, Lsn>,
        last_index: u64,
        last_term: u64,
    }
    ```
    **Invariants**:
    - `append` does NOT fsync; caller batches and calls `fsync()` once before reply.
    - `truncate_after(N)` removes entries N+1.., updates last_index/last_term to entry[N].
    - `last_index` and `last_term` cached for O(1) read (election-restriction check is hot).
    - Index gaps are impossible (sparse → corruption). Entries appended in order.

- [ ] Advanced interpreter with caching. (~30 min)
  - **Why**: evmone advanced mode is THE 2x speedup. Pre-analyzes bytecode into basic blocks (sequences without branches), pre-computes total gas + stack delta per block, then dispatches per-block instead of per-opcode. Validates jump destinations once.
  - **Read first**: evmone `lib/evmone/advanced_analysis.cpp::analyze`; "evmone fast EVM implementation" presentation (DevCon V or related talks).
  - **Design** (conceptual):
    ```text
    Bytecode → Analysis → Vec<BasicBlock>
    BasicBlock { gas_cost: u32, stack_delta: i32, stack_underflow_check: u8, code: Range<usize> }
    Dispatch per block: 1 gas check, 1 stack check, then run N opcodes.
    Cost: pre-analysis O(code_len); amortized over execution.
    Win: ~2× because per-block overhead replaces per-opcode overhead.
    ```

- [ ] [NEW v2] **Build**: extend LocalExecutor to consult `backpressure` signal; pause shard if downstream queue full. (~total 200 min across 3 phases)
  - 🔧 **Why this matters**: without backpressure-aware scheduling, a fast shard floods a slow downstream shard, OOMing the queue OR forcing the cross-shard channel to drop. Backpressure-aware scheduling: when downstream sensor trips, upstream PAUSES tasks producing to that downstream until pressure releases. W60 matching-engine downstream consumers, W85+ marketdata broadcast, W90+ ledger all inherit this primitive — a `HashMap` sensor lookup on the hot path is a 2.5% steady-state CPU tax; false-sharing on the sensor array collapses 16-shard scaling by 30-50%.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: the obvious `HashMap<ShardId, Sensor>` lookup adds ~25 ns of hashing per submit; at 1M submits/s/shard that's a 2.5% steady CPU tax on the HOTTEST path. Packing sensor `AtomicBool` flags without padding gives false-sharing classic: 16-shard flood test loses 30-50% throughput.

  - **Requirements** — write in `crates/runtime-thread-per-core/notes/59_backpressure_design.md`:
    - R1. `LocalExecutor` extended with `sensor_flags: Box<[CachePadded<AtomicBool>]>` indexed by `ShardId as usize`. NOT a HashMap.
    - R2. `submit(target, task)` fast path: `if !self.sensor_flags[target.0].load(Relaxed) { ready_queue.push_back(task); return; }` — one atomic load + branch + push.
    - R3. Each `CachePadded<AtomicBool>` on its own cache line; aarch64 uses align(128), x86_64 uses align(64). Verified with `size_of::<CachePadded<AtomicBool>>() == 128`.
    - R4. Slow path (sensor tripped): `backpressure_queue[target].push_back(task)`; `paused_for = Some(target)`.
    - R5. `tick()` checks all sensors; on transition tripped→clear, drains `backpressure_queue[target]` into `ready_queue`.
    - R6. Hysteresis: trip at `threshold_high` (e.g. 80% capacity); clear at `threshold_low` (50%). Wide gap prevents thrash.
    - R7. Tasks have at most 1 downstream dependency; the cross-shard graph is a DAG per request → no deadlock by construction.
    - R8. `backpressure_queue` itself is bounded; full → REJECT submission with `Err(Overflow)` so caller (matching engine, raft, etc.) decides drop/retry/dead-letter.
    - R9. Hot-path budgets: submit-fast-path ≤ 20 ns; submit-slow-path ≤ 100 ns; tick overhead per sensor ≤ 5 ns.

  - **Design walk-through**:
    - D1. Why `Box<[CachePadded<AtomicBool>]>` not `HashMap<ShardId, Sensor>`? Walk the cost: HashMap::get is ~20-30 ns (hash + probe + cache miss); Vec index is ~1 ns (single cache-line read). At 1M submits/s × ~25 ns saved = 25 ms/s/shard.
    - D2. CachePadded sizing: aarch64-apple-darwin's L2 prefetcher pulls 128 B lines; x86_64 uses 64 B. Why 128 across the board? (Hint: simplicity and worst-case safety; 1024 shards × 128 B = 128 KB is trivial.)
    - D3. Backpressure deadlock theorem: tasks have at-most-1 downstream → cross-shard graph is a tree per request → no cycle → no deadlock. Write the invariant; what would violate it?
    - D4. Hysteresis design: walk the chatter scenario without it. With trip=80%, clear=50%, hysteresis gap absorbs short bursts.
    - D5. Slow-path queue bounding: if backpressure_queue is unbounded, fast shard's queue grows infinitely → OOM. Bound it; reject on full; caller decides. Drop/retry/dead-letter is policy.
    - D6. **Pre-mortem**: write the 4-step path from "default HashMap<ShardId, Sensor> + unpadded AtomicBool" to "16-shard flood throughput regression of 30-50% AND 25 ms/s steady-state CPU tax."
  - **Output**: `notes/59_backpressure_design.md` with R1–R9 + answers to D1–D6 + sensor-state diagram (Clear → Tripped → Clear with thresholds).

    pub struct LocalExecutor {
        // ... existing fields ...
        downstream_sensors: HashMap<ShardId, Arc<Sensor>>,
        paused_for: Option<ShardId>,         // currently paused due to this downstream
        ready_queue: VecDeque<TaskBox>,
        backpressure_queue: HashMap<ShardId, VecDeque<TaskBox>>, // tasks awaiting downstream
    }

    impl LocalExecutor {
        pub fn submit(&mut self, target: ShardId, task: TaskBox) {
            if self.downstream_sensors[&target].is_tripped() {
                self.backpressure_queue.entry(target).or_default().push_back(task);
                self.paused_for = Some(target);
            } else {
                self.ready_queue.push_back(task);  // local task
            }
        }
        pub fn tick(&mut self) {
            // Process ready_queue; on each task, check if any sensor cleared:
            for (sid, sensor) in &self.downstream_sensors {
                if !sensor.is_tripped() {
                    if let Some(q) = self.backpressure_queue.get_mut(sid) {
                        self.ready_queue.extend(q.drain(..));
                    }
                }
            }
            self.run_ready_queue();
        }
    }
    ```

    - A task is in `backpressure_queue[D]` iff `D`'s sensor is tripped at submission time.
    - When sensor clears, ALL queued tasks for that downstream become ready.
    - No task processed while its downstream sensor is tripped.
    - Local tasks (no downstream dependency) NEVER backpressured.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: cloning 100-entry batches × 4 followers × 10 heartbeats/s = ~3 MiB/s memcpy AND heap fragmentation on the leader. `fsync` inside the follower's reactor blocks the entire shard (no matching, no heartbeat reply, no read) for ~10-50 µs (steady) up to 10+ ms (under load) — leader times out heartbeats → spurious election → cluster availability blip every few seconds.

    - R1. Leader `send_append_entries(peer)`: read `next_index[peer]`, batch up to 100 entries from log, encode ONCE into a per-peer scratch frame (or shared `Arc<Bytes>` if entries identical), dispatch.

    - R3. Follower `handle_append_entries(rpc)`:
      (a) term check (step down on higher; reject lower);
      (b) reset election timer;
      (c) log-matching check at `prev_log_index, prev_log_term` — return `conflict_index/term` on mismatch (§5.3 fast catchup);
      (d) truncate conflicting suffix; append new entries; **queue fsync** (does NOT block reactor);
      (e) reply success ONLY after fsync ack arrives.
    - R4. Follower fsync is ASYNC: append goes to wal buffer; fsync issued via io_uring (W58) OR via a separate fsync thread; reactor stays unblocked. Reply sent on fsync completion CQE.
    - R5. Leader-side commit: when majority's `match_index >= idx`, advance `commit_index = idx`. Apply [last_applied+1 .. commit_index] to state machine.
    - R6. Conflict-index optimization: follower returns `(conflict_index = first_index_of_term, conflict_term)`; leader skips next_index back to that point in one round instead of decrementing one at a time. Without this, O(log_len) RPC rounds to converge.
    - R7. Batch size 100 entries amortizes fsync — single fsync per batch = ~1.3 ms / 100 = 13 µs per-entry amortized commit latency.
    - R8. Hot-path budgets: leader send-side ≤ 30 µs per AppendEntries (encode + crypto + network submit); follower receive-side ≤ 30 µs (decode + log-match + append + fsync-queue); fsync ack ≤ 100 µs amortized.

    impl<S: StateMachine> RaftState<S> {
        /// Leader sends AppendEntries to one follower.
        pub fn send_append_entries(&mut self, peer: NodeId) {
            let Role::Leader { next_index, .. } = &self.role else { return };
            let prev_index = next_index[&peer] - 1;
            let prev_term = self.log.entry(prev_index).unwrap().map(|e| e.term).unwrap_or(0);
            let entries = self.log.entries_from(next_index[&peer], 100); // batch up to 100
            let rpc = AppendEntries {
                term: self.persistent.current_term,
                leader_id: self.node_id,
                prev_log_index: prev_index,
                prev_log_term: prev_term,
                entries,
                leader_commit: self.volatile.commit_index,
            };
            self.send(peer, RaftRpc::Append(rpc));
        }

        pub fn handle_append_entries(&mut self, rpc: AppendEntries) -> AppendEntriesReply {
            // term check (step down if higher, reject if lower)
            if rpc.term < self.persistent.current_term {
                return AppendEntriesReply { term: self.persistent.current_term, success: false,
                                              conflict_index: None, conflict_term: None };
            }
            if rpc.term > self.persistent.current_term {
                self.become_follower(rpc.term, Some(rpc.leader_id));
            }
            // Reset election timer
            if let Role::Follower { last_heartbeat, .. } = &mut self.role {
                *last_heartbeat = Instant::now();
            }
            // Log matching check
            let existing = self.log.entry(rpc.prev_log_index).unwrap();
            let log_ok = match existing {
                None if rpc.prev_log_index == 0 => true,  // empty log + prev=0 is OK
                Some(e) if e.term == rpc.prev_log_term => true,
                _ => false,
            };
            if !log_ok {
                // conflict optimization: return where our log diverges
                let conflict_index = self.log.last_index().min(rpc.prev_log_index);
                let conflict_term = self.log.entry(conflict_index).ok().flatten().map(|e| e.term);
                return AppendEntriesReply { term: self.persistent.current_term, success: false,
                                              conflict_index: Some(conflict_index), conflict_term };
            }
            // Truncate conflicting suffix and append new entries
            for (i, entry) in rpc.entries.iter().enumerate() {
                let idx = rpc.prev_log_index + 1 + i as u64;
                if let Some(existing) = self.log.entry(idx).unwrap() {
                    if existing.term != entry.term {
                        self.log.truncate_after(idx - 1).unwrap();
                        // append from i onwards
                        for e in &rpc.entries[i..] {
                            self.log.append(e.clone()).unwrap();
                        }
                        break;
                    }
                } else {
                    self.log.append(entry.clone()).unwrap();
                }
            }
            self.log.fsync().unwrap();  // CRITICAL: before reply

            // Update commit_index
            if rpc.leader_commit > self.volatile.commit_index {
                let last = self.log.last_index();
                self.volatile.commit_index = rpc.leader_commit.min(last);
            }
            self.apply_committed();

            AppendEntriesReply { term: self.persistent.current_term, success: true, conflict_index: None, conflict_term: None }
        }

        pub fn handle_append_entries_reply(&mut self, from: NodeId, reply: AppendEntriesReply) {
            let Role::Leader { next_index, match_index, .. } = &mut self.role else { return };
            if reply.term > self.persistent.current_term {
                self.become_follower(reply.term, None);
                return;
            }
            if reply.success {
                // entry at next_index..last_sent now replicated
                let last_sent = next_index[&from] - 1;  // before this call (need to track per-rpc)
                match_index.insert(from, last_sent);   // simplified; production tracks per-rpc
                next_index.insert(from, last_sent + 1);
                self.maybe_advance_commit();
            } else {
                // Fast backoff via conflict_index
                if let Some(ci) = reply.conflict_index {
                    next_index.insert(from, ci);
                } else {
                    // fallback decrement
                    let n = next_index.get_mut(&from).unwrap();
                    if *n > 1 { *n -= 1; }
                }
                // retry on next tick
            }
        }

        fn maybe_advance_commit(&mut self) {
            let Role::Leader { match_index, .. } = &self.role else { return };
            let mut indices: Vec<u64> = match_index.values().copied().collect();
            indices.push(self.log.last_index()); // self
            indices.sort_unstable();
            let n = indices.len();
            let majority = indices[n / 2]; // median = quorum
            // Per §5.4.2: only commit entries from CURRENT term via this rule
            if let Some(e) = self.log.entry(majority).unwrap() {
                if e.term == self.persistent.current_term && majority > self.volatile.commit_index {
                    self.volatile.commit_index = majority;
                    self.apply_committed();
                }
            }
        }
    }
    ```
    **Invariants**:
    - Followers FSYNC log before replying success. Without this, leader believes commit but follower might lose entries on crash.
    - Leader advances commit_index ONLY when:
      (a) majority of nodes have match_index ≥ N, AND
      (b) log[N].term == current_term (§5.4.2 — prevents committing entries from prior terms via this rule).
    - Conflict-index optimization: follower returns its `conflict_index` so leader fast-skips instead of decrementing one at a time.
  - **Build steps** (granular):
    1. (~30 min) `send_append_entries` with batch of 100 entries.
    2. (~40 min) `handle_append_entries` with log matching + truncate-conflicting + append + fsync.
    3. (~30 min) `handle_append_entries_reply` with success path + conflict-index fast backoff.
    4. (~20 min) `maybe_advance_commit` with §5.4.2 current-term guard.
    5. (~20 min) `apply_committed`: drains entries last_applied+1..commit_index into state_machine.
    6. (~10 min) Tests: leader appends to 1 follower; majority replicates; commit advances. Then kill follower, append more; commit stalls; recover follower, catches up.
  - **Pitfalls** (named, distributed):
    - *commit prior-term entries via majority rule alone*: paper §5.4.2 scenario — leader from later term commits an entry from earlier term via majority that is then overwritten. **Symptom**: committed data lost (rare, Figure 8 scenario). **Fix**: only commit via current-term entry; commit advances "free" through prior-term entries once a current-term entry passes quorum.
    - *Follower fsync omission*: success reply without fsync → leader thinks committed → if all replicas crash, data lost. **Symptom**: rare but catastrophic data loss. **Fix**: explicit fsync before reply.
    - *Stale AppendEntries during partition heal*: old leader's AppendEntries arrives at follower that's already at higher term. **Symptom**: confusion. **Fix**: term-check at start of handler (already in design).
    - *Log truncation on PRE-fsync data*: leader sends entries 100-200; follower fsyncs 100-150, then truncates 100-150 on next conflicting AppendEntries. Lost data? No — leader retains until majority match_index. **Fix**: leader's log is source of truth; follower truncations are safe because data still on leader.
    - *match_index regression*: bug allowing match_index[follower] to decrease (e.g., on retry). **Symptom**: commit progress oscillates. **Fix**: only set match_index from successful reply; never decrease.
  - **Test scenarios** (adversarial):
    - 5-node cluster, leader appends 1000 entries; ALL 5 commit within 50ms.
    - Partition 3-2: 3-node side leader commits; 2-node side stale. Reunite: 2-node side catches up via conflict-index fast-skip in O(1) RPC, not O(1000).
    - Crash leader mid-replication: new leader picks up entries replicated to majority; entries replicated only to minority MAY be overwritten by new leader.
    - Figure 8 scenario: replicated-but-not-committed prior-term entry — verify §5.4.2 prevents commit until current-term entry passes.
  - **Expect to hit (perf) #1 — `entries.clone()` on every AppendEntries broadcast (bar (c) violation)**: the design uses `let entries = self.log.entries_from(next_index[&peer], 100);` then ships `rpc.entries = entries` — typically cloning a `Vec<LogEntry>`. Every heartbeat to every follower clones the same 100 entries again. At 5-node cluster, 10 heartbeats/sec/follower, 100 entries/batch, 80 B/entry = 4 × 10 × 8 KiB = ~320 KiB/sec memcpy *just for heartbeat retransmits* (entries that already shipped). Worse, each clone allocates a new `Bytes` for `command`, fragmenting the heap on a leader that is supposed to be steady-state.
    - Fix: `LogEntry.command: Arc<[u8]>` (or `bytes::Bytes`, which is `Arc`-backed). `entries_from` returns `Vec<LogEntry>` but each `LogEntry::clone()` is now a refcount bump (~2 ns) not a memcpy. Even better: send `Cow<'a, [LogEntry]>` or wrap the RPC envelope in `Arc<AppendEntriesPayload>` shared across all follower destinations — encode once, ship the same encoded buffer to each follower socket (one encode, N socket writes).
    - Cost avoided: ~320 KiB/sec heartbeat memcpy at the 5-node steady state; scales linearly with cluster size (a 9-node cluster pays 8× the memcpy without this fix); removes the leader-side allocator churn that otherwise jitters commit p99.
    - Muscle: replication fan-out should encode once and share via `Arc` — never re-encode per recipient on the hot path. Reapplies at: W77 messaging-aeron multicast (encode once, ship to N subscribers), W85 marketdata fan-out, W83 ledger replication payload.
  - **Expect to hit (perf) #2 — follower fsync blocks the reactor (bar (c) violation)**: the design calls `self.log.fsync().unwrap()` *inside `handle_append_entries`*. fsync is ~10-50 µs on NVMe and **can spike to 10+ ms under load** (kernel flushes journal). During that fsync the follower's shard reactor is blocked — no other matching, no heartbeat reply, no incoming network read. Symptom: under burst load, follower fsync stalls cause the leader to timeout heartbeats → spurious leader election → cluster availability blip every few seconds.
    - Fix: route fsync through the W58 io_uring backend — submit `IORING_OP_FSYNC` and `await` the completion via the shard's `IoCompletion::Fsync { ack }`. The handler returns control to the reactor immediately; on CQE arrival, the deferred `handle_append_entries_after_fsync` posts the reply. (This is identical to the TigerBeetle journal design and the reason io_uring matters here.) For the fallback epoll backend, dispatch fsync onto a dedicated I/O thread + completion channel.
    - Cost avoided: ~10-50 µs blocked-reactor per AppendEntries → ~0 (deferred); eliminates spurious election storms under load; restores p99 commit ≤ 5 ms target (otherwise p99 floats to 50 ms+ under burst).
    - Muscle: blocking syscalls inside a thread-per-core reactor are correctness bugs for latency — they violate the run-to-completion model. Reapplies at: W74 matching-engine WAL commit (W63 io_uring path), W83 ledger journal fsync, W92 ledger io_uring throughout.
