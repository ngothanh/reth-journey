- [ ] **Build**: `crates/consensus-raft/src/log.rs` — `LogEntry { term, index, command, lsn: Lsn }`. Backed by
  `wal::Wal` for durability. (~150 min)
  - **Why**: The log is Raft's durability boundary. Every committed entry must be on disk before commit_index advances. The LSN field allows alignment with the underlying wal crate's positional addressing.
  - *Back-of-envelope*: matching-engine over Raft (W74) target = ≥ 100k commands/sec replicated; per-AppendEntries batch = 100 entries; per-batch fsync = ~10-50 µs on NVMe; **per-batch overhead budget ≤ 100 µs** (so end-to-end commit-from-leader-perspective ≤ 5 ms p99 — Raft's ~5× ms target). Per-entry encode: RLP-frame (~50 ns) + WAL append (~50 ns memcpy) + index_to_lsn `BTreeMap` insert (~100 ns). At 100k entries/sec single-thread that's ~20 ms/sec of pure log overhead — 2% of CPU, acceptable. **Critical: NO fsync per append — batch + single fsync** (per-append fsync drops throughput from 100k/sec to ~1k/sec, the canonical hash-table-of-disaster bug). The `index_to_lsn: BTreeMap<u64, Lsn>` grows unboundedly with the log; without truncation it OOMs after ~10 M entries (~32 B/entry × 10 M = 320 MiB). Snapshotting (W67) compacts it.
  - **Design**:
    ```rust
    pub struct LogEntry {
        pub term: u64,
        pub index: u64,
        pub command: Bytes,    // app-specific bytes
        pub lsn: Lsn,          // wal crate's Log Sequence Number
    }

    pub trait LogStorage {
        fn append(&mut self, entry: LogEntry) -> Result<Lsn, _>;
        fn append_batch(&mut self, entries: Vec<LogEntry>) -> Result<Lsn, _>;
        fn truncate_after(&mut self, index: u64) -> Result<(), _>; // conflict resolution
        fn entry(&self, index: u64) -> Result<Option<LogEntry>, _>;
        fn last_index(&self) -> u64;
        fn last_term(&self) -> u64;
        fn fsync(&mut self) -> Result<(), _>;
    }

    pub struct WalLogStorage {
        wal: wal::Wal,
        index_to_lsn: BTreeMap<u64, Lsn>,
        last_index: u64,
        last_term: u64,
    }
    ```
    **Invariants**:
    - `append` does NOT fsync; caller batches and calls `fsync()` once before reply.
    - `truncate_after(N)` removes entries N+1.., updates last_index/last_term to entry[N].
    - `last_index` and `last_term` cached for O(1) read (election-restriction check is hot).
    - Index gaps are impossible (sparse → corruption). Entries appended in order.
  - **Build steps**:
    1. (~20 min) Define LogEntry + LogStorage trait.
    2. (~40 min) WalLogStorage impl: append wraps wal::Wal::append; truncate uses wal's `truncate_to_lsn`.
    3. (~20 min) Crash-recovery: on open, scan wal, rebuild index_to_lsn map; verify no gaps.
    4. (~20 min) Tests: append 10k entries; crash; recover; verify last_index/last_term correct.
    5. (~30 min) Tests for truncate_after: append 10k, truncate at 5000, verify entry(5001) returns None and entry(5000) still readable.
    6. (~20 min) fsync batching: append_batch + fsync once is ≥ 10× faster than per-entry fsync. Microbench confirms.
  - **Pitfalls**:
    - *fsync per append*: kills throughput from 100k/s to 1k/s. **Symptom**: leader latency awful. **Fix**: batch via append_batch; fsync once before AppendEntries reply.
    - *Truncate gap*: truncate_after(N) but entry N missing → undefined state. **Fix**: explicit precondition check.
    - *Index/LSN drift*: rebuilding index_to_lsn after crash → off-by-one between durable and in-memory. **Fix**: replay from start of last segment, not from arbitrary offset.
  - **Test scenarios**: crash after append-no-fsync → recovery sees pre-append state; crash after fsync → recovery sees post-append state.
  - **Expect to hit (perf) #1 — `BTreeMap<u64, Lsn>` index allocates per-insert and dominates the hot path (bar (c) violation)**: at 100k entries/sec, `index_to_lsn.insert` allocates a tree node on every call (~100 ns + heap fragmentation + cache miss on the parent node ~7 ns). Flame graph during a 100k-entry append bench shows `alloc::alloc` and `BTreeMap::insert` together at ~30% of CPU. Since indices are *strictly monotonic and dense* in steady state, the BTreeMap is a strictly worse `Vec`.
    - Fix: replace `index_to_lsn: BTreeMap<u64, Lsn>` with `index_to_lsn: VecDeque<Lsn>` where `index_to_lsn[0]` corresponds to `first_index` (tracked separately). `append(lsn)` → `push_back(lsn)` (amortized O(1) with capacity reservation, zero per-call alloc once warmed). `truncate_after(idx)` → `truncate(idx - first_index + 1)`. `lookup(idx)` → `get(idx - first_index)`. Pre-reserve the VecDeque to ~1 M entries at boot (8 B × 1 M = 8 MiB, fits in L3).
    - Cost avoided: ~100 ns per insert (so ~10 ms/sec at 100k ops/sec); eliminates allocator from the append path; removes BTreeMap's per-insert 6-7 cache-line walk down the tree.
    - Muscle: when keys are dense + monotonic, a `Vec`/`VecDeque` with a `first_index` offset is strictly better than a tree map — `BTreeMap` is for sparse keys. Reapplies at: W67 raft snapshot index, W74 matching-engine event-log seq index, W83 ledger transfer log.
  - **Expect to hit (perf) #2 — RLP encode on every `append` allocates a fresh `Vec<u8>` (bar (c) violation)**: the natural `append(entry)` encodes the entry via `rlp::encode(&entry)` → returns `Vec<u8>` → memcpy into WAL. At 100k entries/sec that's 100k mini-Vec allocs/sec on a hot leader thread — allocator lock contention spikes under N writer threads, and the heap walks ~32 B per encoded entry (cache-cold each time). Symptom: leader p99 commit latency is 5× the follower's because the leader's encode allocates while the follower's decode reads in place.
    - Fix: pre-allocate a per-shard `encode_scratch: Vec<u8>` reused across calls (capacity 4 KiB, holds one batch). `append(entry)` calls `entry.encode(&mut encode_scratch)` (in-place encode via an `Encodable` trait that writes into a `&mut Vec<u8>`), then WAL append copies from the scratch buffer, then `encode_scratch.clear()` (sets `len=0`, capacity preserved). Same pattern as W26 WAL `RecordFrame` encode and the `eth-rlp` `Encodable::encode(&self, out: &mut dyn BufMut)` API.
    - Cost avoided: ~50 ns alloc + ~50 ns dealloc per append = ~100 ns × 100k/sec = 10 ms/sec saved; allocator contention removed; encode now writes hot-in-L1 (scratch buffer pinned).
    - Muscle: serialization on a bar-(c) hot path must encode *into* a caller-owned buffer, never *return* a fresh `Vec`. Reapplies at: W61 matching-engine event-log encode, W74 raft RPC encode, W77 aeron term-buffer claim+write, W83 ledger op encode.
  - **Acceptance**: 100k entries durable + replayable in < 5s; truncate semantics correct; **append path zero-alloc steady state** (verified via `dhat`/`heaptrack` showing zero alloc-rate during a 1M-entry append run, ignoring the warm-up); BTreeMap removed from index lookup; encode reuses scratch buffer.
  - **Downstream**: replication.rs (Thu) consumes; W67+ snapshot (compaction) on top.

**Wednesday — evmone advanced mode + runtime-thread-per-core v0.5: backpressure-aware scheduling** [NEW v2]

- [ ] Advanced interpreter with caching. (~30 min)
  - **Why**: evmone advanced mode is THE 2x speedup. Pre-analyzes bytecode into basic blocks (sequences without branches), pre-computes total gas + stack delta per block, then dispatches per-block instead of per-opcode. Validates jump destinations once.
  - **Read first**: evmone `lib/evmone/advanced_analysis.cpp::analyze`; "evmone fast EVM implementation" presentation (DevCon V or related talks).
  - **Design** (conceptual):
    ```text
    Bytecode → Analysis → Vec<BasicBlock>
    BasicBlock { gas_cost: u32, stack_delta: i32, stack_underflow_check: u8, code: Range<usize> }
    Dispatch per block: 1 gas check, 1 stack check, then run N opcodes.
    Cost: pre-analysis O(code_len); amortized over execution.
    Win: ~2× because per-block overhead replaces per-opcode overhead.
    ```
  - **Build steps**: read-only today.
    1. (~10 min) Walk `analyze()` in evmone source.
    2. (~10 min) Note the JUMPDEST validation pre-computed bitmap (revm has similar in `JumpTable`).
    3. (~10 min) Plan: exec-vm can adopt basic-block analysis incrementally — first ship analysis result as opaque `Analysis` struct attached to Bytecode; dispatch consumes it for jump validation; later add gas/stack pre-compute.
  - **Acceptance**: design notes captured; W64 perf-PR candidate noted.
- [ ] [NEW v2] **Build**: extend LocalExecutor to consult `backpressure` signal; pause shard if downstream queue full. (~150 min)
  - **Why**: Without backpressure-aware scheduling, a fast shard floods a slow downstream shard, eventually OOMing the queue OR forcing the cross-shard channel to drop. Backpressure-aware scheduling: when downstream sensor trips, the upstream shard PAUSES tasks producing to that downstream until pressure releases. Classic flow-control.
  - *Back-of-envelope*: shard tick rate ~10k-100k ticks/sec; `submit()` is called on every cross-shard event from matching-engine (one per fill broadcast → market-data shard, one per fill → risk shard). At 1 M fills/sec/shard, `submit()` is on the hottest of all paths — every nanosecond compounds. Target: **submit-fast-path ≤ 20 ns** when no sensor tripped (one atomic-load probe + branch + push); submit-slow-path (tripped) ≤ 100 ns (route into per-downstream queue). Sensor check must be a single `load(Relaxed)` on a `CachePadded<AtomicBool>` — anything more is a budget killer.
  - **Read first**: ScyllaDB's pause/resume of shard tasks; `backpressure` crate's Sensor + Strategy interface.
  - **Design**:
    ```rust
    pub struct LocalExecutor {
        // ... existing fields ...
        downstream_sensors: HashMap<ShardId, Arc<Sensor>>,
        paused_for: Option<ShardId>,         // currently paused due to this downstream
        ready_queue: VecDeque<TaskBox>,
        backpressure_queue: HashMap<ShardId, VecDeque<TaskBox>>, // tasks awaiting downstream
    }

    impl LocalExecutor {
        pub fn submit(&mut self, target: ShardId, task: TaskBox) {
            if self.downstream_sensors[&target].is_tripped() {
                self.backpressure_queue.entry(target).or_default().push_back(task);
                self.paused_for = Some(target);
            } else {
                self.ready_queue.push_back(task);  // local task
            }
        }
        pub fn tick(&mut self) {
            // Process ready_queue; on each task, check if any sensor cleared:
            for (sid, sensor) in &self.downstream_sensors {
                if !sensor.is_tripped() {
                    if let Some(q) = self.backpressure_queue.get_mut(sid) {
                        self.ready_queue.extend(q.drain(..));
                    }
                }
            }
            self.run_ready_queue();
        }
    }
    ```
    **Invariants**:
    - A task is in `backpressure_queue[D]` iff `D`'s sensor is tripped at submission time.
    - When sensor clears, ALL queued tasks for that downstream become ready.
    - No task processed while its downstream sensor is tripped.
    - Local tasks (no downstream dependency) NEVER backpressured.
  - **Build steps**:
    1. (~20 min) Extend LocalExecutor with sensor map + backpressure_queue.
    2. (~30 min) `submit()` with sensor check + routing.
    3. (~25 min) `tick()` drains backpressure_queue on sensor clear.
    4. (~30 min) Integration with cross_shard channel (W57): when channel's capacity > threshold_high, channel trips downstream's sensor; when < threshold_low, channel clears it. Hysteresis prevents thrash.
    5. (~25 min) Tests: 2-shard sim; shard 0 floods shard 1; verify shard 0 backpressures within 100ms; shard 1 drains; shard 0 resumes.
    6. (~20 min) Adversarial: pathological all-shards-flooding-all → verify no deadlock (no cycle in backpressure dependency graph because each task has at most 1 downstream).
  - **Pitfalls**:
    - *Backpressure deadlock*: A waits for B; B's queue has task that needs A's queue. Cycle. **Symptom**: cluster wedges. **Fix**: tasks can only have 1 downstream dependency; cycles avoided by design (cross-shard graph is a DAG per request).
    - *Sensor flicker thrash*: rapid trip/clear cycles → spurious queue drain/rebuild. **Symptom**: high overhead. **Fix**: hysteresis — high/low thresholds with gap (e.g., trip at 80%, clear at 50%).
    - *Starvation of slow shard*: fast shard's backpressure queue grows unboundedly. **Symptom**: OOM. **Fix**: backpressure_queue is itself bounded; when full, REJECT submission with error → caller decides (drop, retry, dead-letter).
  - **Expect to hit (perf) #1 — `HashMap<ShardId, Sensor>` lookup on every submit (bar (c) violation)**: the design above writes `self.downstream_sensors[&target].is_tripped()`. `HashMap::get` is ~20-30 ns (hash + probe + cache miss on bucket), so every cross-shard submit pays ~25 ns *just to look up the sensor* before the actual atomic-load. At 1 M submits/sec/shard, that's 25 ms/sec/shard wasted on hashing — equivalent to a 2.5% steady-state CPU tax on the hottest path in the runtime.
    - Fix: replace `HashMap<ShardId, Arc<Sensor>>` with `Vec<CachePadded<AtomicBool>>` indexed by `ShardId as usize`. Layout: one cache-line-padded sensor flag per shard, all sensors in a contiguous `Box<[CachePadded<AtomicBool>]>` sized at boot from `shard_count`. `submit_fast_path`: `if !self.sensor_flags[target.0 as usize].load(Relaxed) { self.ready_queue.push_back(task); return; }` — single atomic load, single branch, single push. The full `Arc<Sensor>` (with thresholds/hysteresis state) stays alongside but is only touched on the slow path (trip/clear transitions).
    - Cost avoided: ~25 ns per submit (so ~25 ms/sec/shard at 1 M submits/sec); the sensor flag now hits L1 cache reliably (one cache line per shard, fits in L1d at shard_count ≤ 1024); eliminates the HashMap's variable-latency lookup tail.
    - Muscle: when keys are small dense integers (shard IDs, opcode bytes, level indices), prefer `Vec<T>` over `HashMap<K, T>` — array indexing is one cache line, hash lookup is several. Reapplies at: W60 matching-engine `OrderBook` per-symbol lookup (use shard-local `Vec<OrderBook>`, not `HashMap<Symbol, OrderBook>`), W76 aeron per-publication state, W83 ledger account-cache.
  - **Expect to hit (perf) #2 — sensor flag false-shares with adjacent fields and tanks throughput (bar (c) violation)**: even after replacing HashMap with Vec, if `AtomicBool` flags are packed without padding, multiple flags share a single 64 B / 128 B cache line. Two shards on different cores both writing trip/clear transitions invalidate each other's L1 line on every transition — false sharing classic from W4. Symptom: under 16-shard flood test, throughput drops 30-50% vs single-shard despite "lock-free" path; `perf c2c` shows shared cache-line conflict on the sensor array.
    - Fix: wrap each flag in `crossbeam_utils::CachePadded<AtomicBool>` (or equivalent — W4 `CachePadded` muscle). On aarch64-apple-darwin use `align(128)`; on x86_64 use `align(64)`. Verify with `assert!(std::mem::size_of::<CachePadded<AtomicBool>>() == 128)` (or 64). Memory cost: 128 B × 1024 shards = 128 KiB — trivial.
    - Cost avoided: ~30-50% throughput regression under multi-shard flood (the false-sharing 30-70% range from W4); ~7 ns L2 fetch per cross-thread access eliminated; restores linear scaling with shard count.
    - Muscle: any flag that flips from multiple cores must live on its own cache line. Reapplies at: W4 (already taught), W60 matching-engine L1 best-bid/ask SeqLock counter, W74 lock-free price-level head pointer, W77 aeron term-rotation seq, W83 ledger account-version-counter.
  - **Acceptance**: 2-shard flood test exhibits steady-state without queue growth; no deadlocks under all-pairs flooding; submit-fast-path benched at ≤ 20 ns; 16-shard flood shows linear throughput (no false-sharing cliff).
  - **Downstream**: matching-engine downstream (W60+) consumes; marketdata broadcast (W85+); ledger (W90+).

- [ ] **Build**: `crates/consensus-raft/src/replication.rs` — leader sends AppendEntries; followers persist via wal then
  ack; leader bumps commitIndex when majority replicates. (~150 min)
  - **Why (MAX DETAIL)**: Log replication is Raft's hot path. AppendEntries IS the heartbeat AND the data path. Getting `next_index/match_index` tracking right is hard — etcd had 3+ bugs here in first year.
  - *Back-of-envelope*: matching-engine over Raft (W74) target = ≥ 100k commands/sec replicated with p99 commit latency ≤ 5 ms in a 5-node LAN cluster. Decompose 5 ms p99: leader encode + append + fsync (~100 µs) + network RTT (~500 µs LAN, ~50 µs DPDK) + follower decode + append + fsync (~100 µs) + ack round-trip (~500 µs) + leader commit + apply (~100 µs) ≈ ~1.3 ms typical; the 5 ms p99 absorbs fsync tail and ack jitter. **Batch size 100 entries amortizes the fsync** — a single fsync per batch of 100 means commit latency *per entry* is ~1.3 ms / 100 = 13 µs amortized. Per-AppendEntries-message encode: 100 entries × ~80 B/entry = ~8 KiB — fits in one MTU pair, no fragmentation. **Critical: leader `entries_from(next_index, 100)` must NOT clone the entries** — return `&[LogEntry]` or use a cheap-clone `Arc<LogEntry>` wrapper; cloning 100 × 80 B per heartbeat per follower per second (× 4 followers × ~10 heartbeats/sec/follower = 40 × 8 KiB = ~3 MiB/sec memcpy) is a noticeable CPU/cache tax.
  - **Read first**: Ongaro §5.3 (log replication); raft-rs `src/raft.rs::handle_append_entries`, `step_leader`.
  - **Design**:
    ```rust
    impl<S: StateMachine> RaftState<S> {
        /// Leader sends AppendEntries to one follower.
        pub fn send_append_entries(&mut self, peer: NodeId) {
            let Role::Leader { next_index, .. } = &self.role else { return };
            let prev_index = next_index[&peer] - 1;
            let prev_term = self.log.entry(prev_index).unwrap().map(|e| e.term).unwrap_or(0);
            let entries = self.log.entries_from(next_index[&peer], 100); // batch up to 100
            let rpc = AppendEntries {
                term: self.persistent.current_term,
                leader_id: self.node_id,
                prev_log_index: prev_index,
                prev_log_term: prev_term,
                entries,
                leader_commit: self.volatile.commit_index,
            };
            self.send(peer, RaftRpc::Append(rpc));
        }

        pub fn handle_append_entries(&mut self, rpc: AppendEntries) -> AppendEntriesReply {
            // term check (step down if higher, reject if lower)
            if rpc.term < self.persistent.current_term {
                return AppendEntriesReply { term: self.persistent.current_term, success: false,
                                              conflict_index: None, conflict_term: None };
            }
            if rpc.term > self.persistent.current_term {
                self.become_follower(rpc.term, Some(rpc.leader_id));
            }
            // Reset election timer
            if let Role::Follower { last_heartbeat, .. } = &mut self.role {
                *last_heartbeat = Instant::now();
            }
            // Log matching check
            let existing = self.log.entry(rpc.prev_log_index).unwrap();
            let log_ok = match existing {
                None if rpc.prev_log_index == 0 => true,  // empty log + prev=0 is OK
                Some(e) if e.term == rpc.prev_log_term => true,
                _ => false,
            };
            if !log_ok {
                // conflict optimization: return where our log diverges
                let conflict_index = self.log.last_index().min(rpc.prev_log_index);
                let conflict_term = self.log.entry(conflict_index).ok().flatten().map(|e| e.term);
                return AppendEntriesReply { term: self.persistent.current_term, success: false,
                                              conflict_index: Some(conflict_index), conflict_term };
            }
            // Truncate conflicting suffix and append new entries
            for (i, entry) in rpc.entries.iter().enumerate() {
                let idx = rpc.prev_log_index + 1 + i as u64;
                if let Some(existing) = self.log.entry(idx).unwrap() {
                    if existing.term != entry.term {
                        self.log.truncate_after(idx - 1).unwrap();
                        // append from i onwards
                        for e in &rpc.entries[i..] {
                            self.log.append(e.clone()).unwrap();
                        }
                        break;
                    }
                } else {
                    self.log.append(entry.clone()).unwrap();
                }
            }
            self.log.fsync().unwrap();  // CRITICAL: before reply

            // Update commit_index
            if rpc.leader_commit > self.volatile.commit_index {
                let last = self.log.last_index();
                self.volatile.commit_index = rpc.leader_commit.min(last);
            }
            self.apply_committed();

            AppendEntriesReply { term: self.persistent.current_term, success: true, conflict_index: None, conflict_term: None }
        }

        pub fn handle_append_entries_reply(&mut self, from: NodeId, reply: AppendEntriesReply) {
            let Role::Leader { next_index, match_index, .. } = &mut self.role else { return };
            if reply.term > self.persistent.current_term {
                self.become_follower(reply.term, None);
                return;
            }
            if reply.success {
                // entry at next_index..last_sent now replicated
                let last_sent = next_index[&from] - 1;  // before this call (need to track per-rpc)
                match_index.insert(from, last_sent);   // simplified; production tracks per-rpc
                next_index.insert(from, last_sent + 1);
                self.maybe_advance_commit();
            } else {
                // Fast backoff via conflict_index
                if let Some(ci) = reply.conflict_index {
                    next_index.insert(from, ci);
                } else {
                    // fallback decrement
                    let n = next_index.get_mut(&from).unwrap();
                    if *n > 1 { *n -= 1; }
                }
                // retry on next tick
            }
        }

        fn maybe_advance_commit(&mut self) {
            let Role::Leader { match_index, .. } = &self.role else { return };
            let mut indices: Vec<u64> = match_index.values().copied().collect();
            indices.push(self.log.last_index()); // self
            indices.sort_unstable();
            let n = indices.len();
            let majority = indices[n / 2]; // median = quorum
            // Per §5.4.2: only commit entries from CURRENT term via this rule
            if let Some(e) = self.log.entry(majority).unwrap() {
                if e.term == self.persistent.current_term && majority > self.volatile.commit_index {
                    self.volatile.commit_index = majority;
                    self.apply_committed();
                }
            }
        }
    }
    ```
    **Invariants**:
    - Followers FSYNC log before replying success. Without this, leader believes commit but follower might lose entries on crash.
    - Leader advances commit_index ONLY when:
      (a) majority of nodes have match_index ≥ N, AND
      (b) log[N].term == current_term (§5.4.2 — prevents committing entries from prior terms via this rule).
    - Conflict-index optimization: follower returns its `conflict_index` so leader fast-skips instead of decrementing one at a time.
  - **Build steps** (granular):
    1. (~30 min) `send_append_entries` with batch of 100 entries.
    2. (~40 min) `handle_append_entries` with log matching + truncate-conflicting + append + fsync.
    3. (~30 min) `handle_append_entries_reply` with success path + conflict-index fast backoff.
    4. (~20 min) `maybe_advance_commit` with §5.4.2 current-term guard.
    5. (~20 min) `apply_committed`: drains entries last_applied+1..commit_index into state_machine.
    6. (~10 min) Tests: leader appends to 1 follower; majority replicates; commit advances. Then kill follower, append more; commit stalls; recover follower, catches up.
  - **Pitfalls** (named, distributed):
    - *commit prior-term entries via majority rule alone*: paper §5.4.2 scenario — leader from later term commits an entry from earlier term via majority that is then overwritten. **Symptom**: committed data lost (rare, Figure 8 scenario). **Fix**: only commit via current-term entry; commit advances "free" through prior-term entries once a current-term entry passes quorum.
    - *Follower fsync omission*: success reply without fsync → leader thinks committed → if all replicas crash, data lost. **Symptom**: rare but catastrophic data loss. **Fix**: explicit fsync before reply.
    - *Stale AppendEntries during partition heal*: old leader's AppendEntries arrives at follower that's already at higher term. **Symptom**: confusion. **Fix**: term-check at start of handler (already in design).
    - *Log truncation on PRE-fsync data*: leader sends entries 100-200; follower fsyncs 100-150, then truncates 100-150 on next conflicting AppendEntries. Lost data? No — leader retains until majority match_index. **Fix**: leader's log is source of truth; follower truncations are safe because data still on leader.
    - *match_index regression*: bug allowing match_index[follower] to decrease (e.g., on retry). **Symptom**: commit progress oscillates. **Fix**: only set match_index from successful reply; never decrease.
  - **Test scenarios** (adversarial):
    - 5-node cluster, leader appends 1000 entries; ALL 5 commit within 50ms.
    - Partition 3-2: 3-node side leader commits; 2-node side stale. Reunite: 2-node side catches up via conflict-index fast-skip in O(1) RPC, not O(1000).
    - Crash leader mid-replication: new leader picks up entries replicated to majority; entries replicated only to minority MAY be overwritten by new leader.
    - Figure 8 scenario: replicated-but-not-committed prior-term entry — verify §5.4.2 prevents commit until current-term entry passes.
  - **Expect to hit (perf) #1 — `entries.clone()` on every AppendEntries broadcast (bar (c) violation)**: the design uses `let entries = self.log.entries_from(next_index[&peer], 100);` then ships `rpc.entries = entries` — typically cloning a `Vec<LogEntry>`. Every heartbeat to every follower clones the same 100 entries again. At 5-node cluster, 10 heartbeats/sec/follower, 100 entries/batch, 80 B/entry = 4 × 10 × 8 KiB = ~320 KiB/sec memcpy *just for heartbeat retransmits* (entries that already shipped). Worse, each clone allocates a new `Bytes` for `command`, fragmenting the heap on a leader that is supposed to be steady-state.
    - Fix: `LogEntry.command: Arc<[u8]>` (or `bytes::Bytes`, which is `Arc`-backed). `entries_from` returns `Vec<LogEntry>` but each `LogEntry::clone()` is now a refcount bump (~2 ns) not a memcpy. Even better: send `Cow<'a, [LogEntry]>` or wrap the RPC envelope in `Arc<AppendEntriesPayload>` shared across all follower destinations — encode once, ship the same encoded buffer to each follower socket (one encode, N socket writes).
    - Cost avoided: ~320 KiB/sec heartbeat memcpy at the 5-node steady state; scales linearly with cluster size (a 9-node cluster pays 8× the memcpy without this fix); removes the leader-side allocator churn that otherwise jitters commit p99.
    - Muscle: replication fan-out should encode once and share via `Arc` — never re-encode per recipient on the hot path. Reapplies at: W77 messaging-aeron multicast (encode once, ship to N subscribers), W85 marketdata fan-out, W83 ledger replication payload.
  - **Expect to hit (perf) #2 — follower fsync blocks the reactor (bar (c) violation)**: the design calls `self.log.fsync().unwrap()` *inside `handle_append_entries`*. fsync is ~10-50 µs on NVMe and **can spike to 10+ ms under load** (kernel flushes journal). During that fsync the follower's shard reactor is blocked — no other matching, no heartbeat reply, no incoming network read. Symptom: under burst load, follower fsync stalls cause the leader to timeout heartbeats → spurious leader election → cluster availability blip every few seconds.
    - Fix: route fsync through the W58 io_uring backend — submit `IORING_OP_FSYNC` and `await` the completion via the shard's `IoCompletion::Fsync { ack }`. The handler returns control to the reactor immediately; on CQE arrival, the deferred `handle_append_entries_after_fsync` posts the reply. (This is identical to the TigerBeetle journal design and the reason io_uring matters here.) For the fallback epoll backend, dispatch fsync onto a dedicated I/O thread + completion channel.
    - Cost avoided: ~10-50 µs blocked-reactor per AppendEntries → ~0 (deferred); eliminates spurious election storms under load; restores p99 commit ≤ 5 ms target (otherwise p99 floats to 50 ms+ under burst).
    - Muscle: blocking syscalls inside a thread-per-core reactor are correctness bugs for latency — they violate the run-to-completion model. Reapplies at: W74 matching-engine WAL commit (W63 io_uring path), W83 ledger journal fsync, W92 ledger io_uring throughout.
  - **Acceptance**: 1000-entry replication in 5-node cluster green; Figure 8 scenario rejected; partition heal converges in O(log) RPCs; AppendEntries hot-path zero-alloc per-recipient (verified via heaptrack); fsync deferred via io_uring (no blocked reactor under 100 burst commits).
  - **Downstream**: W62 (membership), W67+ (raft v1.0 polish), W74+ (matching-engine over Raft replication).

- [ ] [NEW v2] **Build**: per-shard counters (tasks executed, msgs sent, mailbox depth, queue stalls). Expose via prometheus. (~90 min)
  - **Why**: You can't optimize what you can't measure. Per-shard observability is non-negotiable for TPC debugging: balance issues, stall sources, backpressure spread, NUMA traffic. ScyllaDB ships extensive Prometheus metrics by default.
  - *Back-of-envelope*: counters increment on the hot path — every task execution, every cross-shard submit, every io_uring submit. At 1 M tasks/sec/shard, even a 1 ns per-counter cost ≈ 1 ms/sec/shard — and `prometheus::IntCounter::inc()` is ~5-10 ns (an atomic fetch_add on a SeqCst-by-default atomic, possibly with mutex inside the registry handle). **Target: each counter inc ≤ 2 ns on the hot path**, achieved via `IntCounter::inc` = `Relaxed` atomic-add on a `CachePadded<AtomicU64>` (no mutex, no allocations). Prometheus scrape (~1 Hz) does the formatting in the cold path — never on the per-event path.
  - **Read first**: `prometheus = "0.13"` crate (Rust client lib); ScyllaDB metrics taxonomy.
  - **Design**:
    ```rust
    pub struct ShardMetrics {
        pub tasks_executed: IntCounter,
        pub tasks_submitted_to_self: IntCounter,
        pub tasks_submitted_cross_shard: IntCounter,
        pub mailbox_depth: IntGauge,
        pub backpressure_stalls: IntCounter,
        pub io_uring_ops_submitted: IntCounter,
        pub io_uring_ops_completed: IntCounter,
        pub numa_local_pages: IntGauge,
        pub numa_remote_pages: IntGauge,
    }
    ```
    **Invariants**:
    - Counters monotonic; never decrement.
    - Gauges sampled (instantaneous); not summed across resets.
    - Per-shard labels: `shard="0"`, `numa_node="0"`.
    - No mutex on hot path: use atomics; lock-free counter increment.
  - **Build steps**:
    1. (~20 min) Define ShardMetrics with prometheus types.
    2. (~25 min) Wire into LocalExecutor `tick()`, cross_shard `submit_to`, backpressure trip/clear.
    3. (~20 min) Per-shard HTTP endpoint at `/metrics/shard/{id}` OR aggregate at `/metrics`.
    4. (~15 min) Grafana dashboard JSON committed for shard balance + stall rate visualization.
    5. (~10 min) Test: pump 1M tasks, scrape metrics, verify counter values match.
  - **Pitfalls**: prometheus encoding allocates strings → hot-path skip; use sampled metric pull (every 1s) not push.
  - **Expect to hit (perf) #1 — `prometheus` crate's `IntCounter::inc` uses SeqCst and pays ~10 ns on the hot path (bar (c) violation)**: the default `prometheus::IntCounter` is backed by `AtomicU64::fetch_add(1, Ordering::SeqCst)` under the hood (verify in the crate source). SeqCst on x86 is effectively a `lock add` (~5-10 ns) AND establishes a total memory ordering that prevents reordering of *unrelated* atomics — so it acts as a fence on every increment, pessimizing the rest of the shard's hot path. At 1 M ops/sec/shard × 5 counters per op ≈ 5 M counter incs/sec/shard ≈ 25-50 ms/sec/shard pure counter overhead, plus the lost reordering on adjacent atomics. Single-writer-per-shard means SeqCst is *strictly unnecessary*.
    - Fix: define a thin wrapper `pub struct ShardCounter(CachePadded<AtomicU64>)` with `inc(&self) { self.0.fetch_add(1, Ordering::Relaxed); }`. Prometheus scrape reads via `.load(Relaxed)` and reports the snapshot. Padding eliminates false sharing across the 10 counters laid out in `ShardMetrics`. If the `prometheus` crate's `Collector` trait is required, register a custom collector that exposes the underlying `Relaxed` atomic.
    - Cost avoided: ~8 ns per inc → ~2 ns (4× reduction); ~40 ms/sec/shard at 5 M incs/sec → ~10 ms/sec; eliminates the SeqCst fence-on-adjacent-atomics tax (which can spike unrelated SeqLock reads on a busy shard by hundreds of ns).
    - Muscle: instrumentation on a hot path must use `Relaxed` atomics — SeqCst is for synchronization, not counting. Reapplies at: W60 matching-engine throughput counters, W74 raft commit counter, W77 aeron published-frames counter, W83 ledger committed-transfers counter, W110 chaos test assertion-counter.
  - **Expect to hit (perf) #2 — counter array false-sharing across 10 metrics in one cache line (bar (c) violation)**: laying out 10 `AtomicU64` counters in a `struct ShardMetrics` without padding packs 8 of them in one cache line (8 × 8 B = 64 B). On a shard that increments multiple counters per event (e.g., `tasks_executed`, `tasks_submitted_to_self`, `mailbox_depth`), every inc invalidates the line for every concurrent reader (the scrape thread on another core). Symptom: bench shows the scrape thread "for free" sometimes degrades shard throughput by 5-10%.
    - Fix: each `AtomicU64` wrapped in `CachePadded` (W4 muscle); explicit `#[repr(C)]` on `ShardMetrics` so the compiler can't pack them. Verify with `assert_eq!(offset_of!(ShardMetrics, tasks_submitted_to_self) - offset_of!(ShardMetrics, tasks_executed), 128)`.
    - Cost avoided: 5-10% throughput regression during scrape; ~7 ns L2 fetch per inc when contended.
    - Muscle: when laying out a struct of counters that are written from a hot thread and read from another, each counter is its own cache line. Reapplies at: W4 `CachePadded` (already taught), W60 matching-engine stats, W77 aeron stats, every observability surface on bar-(c) crates.
  - **Acceptance**: 10 metrics exposed; dashboard renders; counter accuracy ≥ 99.99% (vs ground truth); counter inc benched at ≤ 2 ns; scrape-vs-no-scrape throughput delta < 1%.
  - **Downstream**: ops runbooks (W105+) consume these metrics; chaos tests (W110+) assert on them.
