  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)
  Ordered newbie → expert.
  - **(NEWBIE) When `append_does_not_fsync` / `fsync_per_append_disaster_avoided` show ~1k/s instead of 100k/s:**
    - Symptom: throughput 1k/s; `iostat` shows 100% util at low queue depth; ratio test fails.
    - Why: each `append` calls `wal.fsync()` internally "for safety"; fsync ~10-50 µs dominates.
    - Fix: `append` writes to wal buffer only; caller (replication.rs) batches then `log.fsync()` once before AppendEntries reply. wal supports group-commit so independent raft instances share one fsync.
    - Cost avoided: ~100× throughput (1k/s → 100k/s); ~10-50 µs syscall removed from per-entry path. **(bar (c) violation)** if shipped.
    - Muscle: durability is a CALLER-CONTROLLED op; primitives expose `fsync()` explicitly, never bake it into `append`. **Reapplies at**: W56 raft persist, W74 matching-engine WAL commit, W83+ ledger journal.
  - **(SENIOR) When `index_to_lsn_is_vecdeque` finds BTreeMap and `bench_append_under_100ns` reports ~250 ns:**
    - Symptom: flame graph over a 100k-entry append bench shows `alloc::alloc` + `BTreeMap::insert` at ~30% of CPU; leader p99 commit 5× the follower's.
    - Why: at 100k entries/s, `index_to_lsn.insert` allocates a tree node per call (~100 ns + frag + ~7 ns parent-node cache miss). Indices are strictly monotonic + dense, so `BTreeMap` is a strictly worse `Vec`.
    - Fix: `index_to_lsn: VecDeque<Lsn>` keyed by `index - first_index` (track `first_index`). `append` → `push_back` (amortized O(1), zero per-call alloc once warmed); `truncate_after(idx)` → `truncate(idx - first_index + 1)`; `lookup(idx)` → `get(idx - first_index)`. Pre-reserve ~1M at boot (8 MiB, fits L3).
    - Cost avoided: ~100 ns/insert (~10 ms/s at 100k ops/s); allocator out of append path; removes BTreeMap's 6-7 cache-line walk. **(bar (c) violation)**.
    - Muscle: dense + monotonic keys → `Vec`/`VecDeque` with `first_index` offset beats any tree map; `BTreeMap` is for sparse keys. **Reapplies at**: W67 raft snapshot index, W74 matching-engine event-log seq index, W83 ledger transfer log.
  - **(SENIOR) When `append_zero_alloc_steady_state` reports ~100k Vec allocs/s:**
    - Symptom: `dhat` shows one `Vec<u8>` alloc per append; allocator-lock contention spikes under N writer threads; heap walks ~32 B/entry (cache-cold each time).
    - Why: `append` encodes via `rlp::encode(&entry) → Vec<u8>` then memcpy into wal — 100k mini-Vec allocs/s.
    - Fix: per-shard `encode_scratch: Vec<u8>` (cap 4 KiB) reused; `entry.encode(&mut encode_scratch)` (in-place via `Encodable::encode(&self, out: &mut dyn BufMut)`), wal copies from scratch, then `encode_scratch.clear()` (len=0, capacity kept). Mirrors W26 `RecordFrame::encode`.
    - Cost avoided: ~50 ns alloc + ~50 ns dealloc/append = ~10 ms/s at 100k/s; allocator contention removed; encode hot-in-L1. **(bar (c) violation)**.
    - Muscle: bar (c) serialization encodes INTO a caller-owned buffer, never RETURNS a fresh `Vec`. **Reapplies at**: W61 matching-engine event-log encode, W74 raft RPC encode, W77 aeron term-buffer claim+write, W83 ledger op encode.
  - **(SENIOR) When `bench_last_index_under_5ns` reports ~200 ns:**
    - Symptom: election-restriction check (per RequestVote) dominates RPC handler time.
    - Why: `last_index()` scans the wal each call instead of reading a cached field.
    - Fix: cache `last_index: u64` and `last_term: u64` as struct fields; update on every `append`/`truncate_after`.
    - Cost avoided: ~195 ns per RequestVote; turns a quadratic election handler into O(1). **(bar (c) violation)** under election storms.
    - Muscle: every hot-path read of a derivable quantity becomes a cached field. **Reapplies at**: W74 matching-engine `best_bid`/`best_ask` cached publication.
  - **(SENIOR) When `crash_recovery_no_gaps` finds an off-by-one drift:**
    - Symptom: post-crash `last_index = 9999` not 10000; entry 10000 in wal but absent from `index_to_lsn`.
    - Why: rebuild replayed from an arbitrary offset, missing a partial last entry.
    - Fix: replay from start of LAST segment; validate entry checksums; stop on first invalid; `last_index = highest valid index`.
    - Cost avoided: silent data divergence between durable wal and in-memory index — a correctness hole, not just slow.
    - Muscle: crash recovery's entry point is a segment boundary, never an offset assumed safe. **Reapplies at**: W26 wal recovery, W83+ ledger replay.

It exists so a fast producer can't OOM a slow consumer — back-pressure as correctness.
  - *Contract*:
    ```rust
    // extends existing LocalExecutor
    pub fn submit(&mut self, target: ShardId, task: TaskBox) -> Result<(), Overflow>;
    pub fn tick(&mut self);                 // drains backpressure_queue[d] when sensor[d] clears
    fn trip(&self, d: ShardId);  fn clear(&self, d: ShardId);  // hysteresis-gated by caller
    // sensor flags: Box<[CachePadded<AtomicBool>]> indexed by ShardId as usize
    ```

At 1M fills/s/shard it's the hottest path — every ns compounds. **Target: fast-path ≤20 ns** (one `load(Relaxed)` on a `CachePadded<AtomicBool>` + branch + push); **slow-path ≤100 ns** (route into per-downstream queue). HashMap::get ~25 ns vs Vec index ~1 ns → ~25 ms/s/shard cliff. Unpadded flags: **30-50% throughput cliff** under 16-shard flood (MESI invalidation per transition).

  - **(SENIOR) When `leader_no_entries_clone_on_send` reports ~3 MiB/s memcpy:**
    - Symptom: `dhat` shows 4 × `clone(Vec<LogEntry>)` per heartbeat round; allocator-lock contention spikes; leader p99 commit 5× the follower's (leader clones while follower reads in place).

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)
  - **(NEWBIE) When `metrics_no_mutex_on_hot_path` / `bench_inc_under_2ns` report ~5 ns from a mutex:**
    - Symptom: ~5 ns/inc even with Relaxed; `grep` finds a `Mutex::lock` "to be safe".
    - Why: the counter wrapper locks before `fetch_add`, defeating lock-free.
    - Fix: remove the mutex; `inc` is purely `self.0.fetch_add(1, Relaxed)`. Single-writer-per-shard means no writer race; concurrent scrape readers are fine.
    - Cost avoided: ~25 ns mutex round-trip per inc.
    - Muscle: a lock-free counter needs no lock by definition; "to be safe" comments are red flags. **Reapplies at**: every TPC counter, W74 raft commit counter.
  - **(SENIOR) When `counter_uses_relaxed_not_seqcst` finds SeqCst (and `bench_inc_under_2ns` fails on aarch64):**
    - Symptom: `grep` finds `prometheus::IntCounter` (a `fetch_add(1, SeqCst)`). On the aarch64 dev box `bench_inc_under_2ns` shows the SeqCst `ldaddal` ~2.5-3 ns vs Relaxed `ldadd` ~2 ns. On x86 the inc bench shows NO delta (both `lock xadd`) — do not chase a phantom 4×; the x86 cost shows up in the next two cards instead.
    - Why: `prometheus::IntCounter::inc()` is `fetch_add(1, SeqCst)`. On aarch64 SeqCst forces the barriered `ldaddal`; on x86 `lock xadd` is identical for Relaxed and SeqCst, so the per-inc cost there is NOT the win.
    - Fix: `ShardCounter(CachePadded<AtomicU64>)` with `inc` = `fetch_add(1, Relaxed)`; scrape reads `.load(Relaxed)`. If the `prometheus` `Collector` trait is required, register a custom collector over the Relaxed atomic.
    - Cost avoided: aarch64 ~1 ns/inc (`ldaddal`→`ldadd`); on x86 the inc itself is unchanged — the real x86 savings (Arc-deref + fence-on-neighbors) are the next two cards. **(bar (c) violation)** on aarch64; on x86 see below.
    - Muscle: instrumentation counters use Relaxed — SeqCst is for synchronization, not counting; and the SeqCst→Relaxed win is ISA-dependent (real per-inc on aarch64, fence-on-neighbors on x86), never a flat "4×". **Reapplies at**: W60 matching-engine throughput counters, W74 raft commit counter, W77 aeron published-frames counter, W83 ledger committed-transfers, W110 chaos assertion-counter.
  - **(EXPERT, bar (c)) When `seqcst_fence_taxes_adjacent_seqlock_read` shows the SeqCst neighbor ~+3-6 ns slower (the real x86 trap):**
    - Symptom: on x86 the inc bench shows no Relaxed-vs-SeqCst delta, yet shard throughput still drops when `IntCounter` lives next to the W60 best-bid/ask SeqLock; `seqcst_fence_taxes_adjacent_seqlock_read` shows the seqlock read ~+3-6 ns slower with a SeqCst counter beside it.
    - Why: a SeqCst `fetch_add` is a full barrier; the compiler/CPU cannot let an UNRELATED neighboring atomic (the seqlock's two version loads) reorder across it, so the seqlock read is pessimized even though its own ordering is unchanged.
    - Fix: Relaxed `fetch_add` for the counter — it imposes no ordering on neighbors, so the adjacent SeqLock read keeps its ~3 ns fast path.
    - Cost avoided: ~3-6 ns per adjacent SeqLock read (at 1M reads/s on the publication path ≈ 3-6 ms/s/shard); this is the x86 manifestation of the SeqCst tax. **(bar (c) violation)**.
    - Muscle: a SeqCst RMW taxes the atomics AROUND it, not just itself — on x86 that, plus the registry Arc-deref, is the entire `IntCounter` cost. **Reapplies at**: W60 best-bid/ask SeqLock publication, W74 raft commit counter beside the apply cursor, W77 aeron seq counters.
  - **(SENIOR, bar (c)) When `IntCounter` adds a ~10 ns Arc-deref per inc (x86 and aarch64):**
    - Symptom: even after dropping to Relaxed, a `prometheus::IntCounter` handle still costs ~10 ns/inc more than a bare `CachePadded<AtomicU64>`; a flame graph shows a pointer chase + refcount touch before the add.
    - Why: `IntCounter` is an `Arc`-wrapped registry handle — every `inc` derefs the `Arc` (cold pointer chase ~10 ns) to reach the inner atomic.
    - Fix: hold the bare `CachePadded<AtomicU64>` inline in `ShardMetrics`; expose it to `prometheus` only via a custom `Collector` read at scrape time (cold path), so the hot inc touches no `Arc`.
    - Cost avoided: ~10 ns/inc (× 5M incs/s/shard ≈ 50 ms/s/shard) of registry-handle indirection. **(bar (c) violation)**.
    - Muscle: keep the hot-path atomic inline; push the library handle/registry to the cold scrape path. **Reapplies at**: W60 matching-engine stat handles, W74 raft metrics, every bar (c) observability surface.
  - **(SENIOR) When `counter_each_on_cache_line` shows offset 8 and `scrape_vs_no_scrape_under_1pct_delta` reports 5-10%:**

    - Why: 10 × `AtomicU64` = 80 B packed ~8/line; every inc invalidates the line for the scrape reader on another core.

    - Muscle: a struct of counters written hot + read by a scraper → each counter is its own cache line. **Reapplies at**: W4 (taught), W60 matching-engine stats, W77 aeron stats, every bar (c) observability surface.
