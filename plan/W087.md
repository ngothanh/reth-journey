  - [ ] **Build**: `crates/ledger-deterministic/src/vopr/op_gen.rs` — random ops: 70% Transfer, 20% Lookup, 10% CreateAccount. Seeded RNG for reproducibility. (~2 hrs)
    - **Why**: VOPR (Viewstamped Operation Replication-style simulator) is TigerBeetle's marquee bug-finding tool. The op-stream generator is the engine of the whole simulator: it produces realistic-but-adversarial workloads that exercise every code path. 70/20/10 mix mirrors a real ledger's hot loop (lookups + transfers dominate, account creation rare). Seeded RNG means a failure is reproducible exactly, which is the whole point.
    - *Back-of-envelope* (op_gen target: ≥1M ops/sec single-thread; budget = **1 µs/op** — the workload generator cannot be the bottleneck of a 100k-scenarios-per-machine-per-day rate):
      Per-op cost: `SmallRng::gen::<u32>` ≈ 5 ns (xoshiro256++ — integer-only, deterministic); weighted dispatch via cumulative-bucket `match` ≈ 2 ns; field fills (debit/credit/amount) ≈ 3 × 5 ns = 15 ns; total ~25 ns ✓ — under budget by 40×. The budget is generous because (i) the generator runs millions of times per day and must NOT become the simulator's bottleneck, (ii) it sits ahead of the SM's apply path which itself has a 1 µs budget (ledger v1.0 P99 ≤ 1 µs commit, single-shard). Any `thread_rng` call, `HashMap` use, or float math (a) blows the budget, AND (b) breaks bit-determinism — which forfeits VOPR's reason to exist.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/vopr.zig` — esp. `step()` and the workload generation; `lib/tigerbeetle/src/workload.zig`.
    - **Design**:
      ```rust
      pub struct OpGen {
          rng: SmallRng,                    // seeded SplitMix → SmallRng
          account_pool: ArrayVec<AccountId, 10_000>,
          op_count: u64,
          weights: OpWeights,
      }
      pub struct OpWeights { transfer: u8, lookup: u8, create: u8 } // sums to 100
      impl OpGen {
          pub fn new(seed: u64) -> Self;
          pub fn next_op(&mut self) -> ClientOp;
          pub fn seed(&self) -> u64;
      }
      pub enum ClientOp {
          CreateAccount { id: AccountId, ledger: u16, code: u16, /*...*/ },
          Transfer { id: TransferId, debit: AccountId, credit: AccountId, amount: u64, ledger: u16 },
          Lookup { id: AccountId },
      }
      ```
      **Invariants**: (i) given seed S, the entire op stream is byte-identical across runs (no system_time, no thread_rng), (ii) Transfer always picks debit ≠ credit from `account_pool`, (iii) CreateAccount appends to `account_pool` so future Transfers have valid targets, (iv) op_count monotonic — used as TransferId.
    - **Build steps**: 1. (~10 min) module skeleton `vopr/mod.rs` re-exporting op_gen + assertions + faults. 2. (~10 min) `OpGen::new(seed)` using `SmallRng::seed_from_u64(seed)`. 3. (~20 min) weighted dispatch: roll u8, branch on weights cumulative buckets — manual, no `rand_distr` to avoid alloc. 4. (~20 min) realistic Transfer: pick debit from `account_pool` uniform, credit different from debit; amount = 1 + rng.gen::<u32>() & 0xFFFF (small to avoid quick overflow). 5. (~10 min) realistic CreateAccount: ID = next monotonic, ledger/code/timestamp from rng but bounded. 6. (~15 min) edge-case generator (toggleable): empty Transfer (amount=0), self-transfer (rejected at SM layer), max-amount (u64::MAX/2 to test overflow guards). 7. (~10 min) "burst" workload mode: 99% Transfer 1% other for stress; mode field on OpGen. 8. (~10 min) export op-stream-to-file utility for golden-replay diffing. 9. (~15 min) tests: `op_gen(42).take(10000) == op_gen(42).take(10000)` byte-identical; weights converge to 70/20/10 ±1% over 1M ops.
    - **Pitfalls**: *Non-seeded inner RNG*: **Symptom**: even with `seed` param, op stream differs because `account_pool` shuffles via `thread_rng()`. **Fix**: ban `thread_rng`, all randomness via the single `SmallRng`. *Account-pool exhaustion*: **Symptom**: after 10k creates, can't grow further, Transfer keeps re-picking same pairs. **Fix**: `ArrayVec<_, 10_000>` is a hard cap; document that as the simulator's account scale; raise to 100k if scenarios need more. *Float in op generation*: **Symptom**: floats introduce platform variance (x86 vs ARM rounding). **Fix**: bias toward Bernoulli/uniform integer; no floats anywhere. *Empty pool early*: **Symptom**: first ops are Transfer but pool is empty. **Fix**: prime with N CreateAccount ops before generation, OR weight CreateAccount=100% until pool ≥ 100.
  - **Expect to hit (perf) #1 — `rand::thread_rng()` / `OsRng` in workload generation (bar (c) violation)**: any call to `thread_rng()` (lazy-initialized via OS-entropy `getrandom` syscall, ~300 ns), or `Vec::shuffle` via `thread_rng`, breaks BOTH the perf budget AND determinism. At 1M ops/s, even one `thread_rng` call per op = 300 ns × 1M = 30% of CPU on entropy; and the OS-entropy source guarantees different streams per run, **completely defeating VOPR replay**.
    - Fix: a **single** `SmallRng` (xoshiro256++) seeded at scenario start via `SmallRng::seed_from_u64(seed)`. All randomness — op-type roll, account selection, amount, fault-injection coin-flips — flows through `self.rng.gen::<u32>()`. Add a clippy lint `disallowed_methods = ["rand::thread_rng", "rand::random"]` to enforce.
    - Cost avoided: ~300 ns per spurious `thread_rng` resolution + the entire **determinism debt** (a single non-deterministic call invalidates W88's reproducer-by-seed contract; the whole VOPR investment becomes worthless).
    - Muscle: any deterministic-replay system has exactly ONE entropy source per scenario, owned, seeded from input. `thread_rng`, `OsRng`, `SystemTime::now()` are banned (cargo-deny / clippy). Reapplies at: W87 Tue assertions (must read SM deterministically), W87 Wed faults (fault coin-flips from same RNG), W88 runner (each worker's RNG seeded from the master seed), W90 consensus-vsr VOPR integration (replica clocks driven by SimClock from same seed), W92 ledger v1.0 SHIP determinism gate.
  - **Expect to hit (perf) #2 — `HashMap`/`BTreeMap` for account_pool (bar (c) violation: non-deterministic iteration + 100× the ArrayVec budget)**: implementing `account_pool: HashMap<AccountId, ()>` for "easy contains-check," then `pool.iter().nth(rng.gen_range(0..pool.len()))` to pick a Transfer debit. (a) `HashMap` iteration order is non-deterministic (random seed at startup) — same `seed` parameter, different op stream, **VOPR replay broken**. (b) Each `iter().nth(N)` walks N buckets = O(N) per pick at ~5 ns/bucket = 50 µs to pick from a 10k pool — 50× over the 1 µs/op budget.
    - Fix: `account_pool: ArrayVec<AccountId, 10_000>`. Pick: `pool[rng.gen_range(0..pool.len())]` — O(1), cache-friendly (single L1 read), bit-deterministic across runs and platforms. Membership-check (if needed) via a separate bounded `FixedMap` (W89 Tue's open-addressing table); but for op_gen, indexed pick is enough.
    - Cost avoided: ~50 µs/op pick → ~1 ns/op pick (a **50,000× win**); plus the **determinism debt** (same root cause as perf #1 but at the data-structure level — `HashMap` is the single most common source of accidental non-determinism in Rust deterministic-SM work).
    - Muscle: in deterministic-replay code, all "set-like" structures are sorted vectors / `ArrayVec` / `FixedMap` with explicit hash seed; `std::collections::HashMap` and `ahash::AHashMap` are cargo-deny-banned. Reapplies at: W87 Tue assertion suite (iterating accounts for invariant check), W89 Tue ledger AccountMap (FixedMap, the actual production version), W92 ledger v1.0 state_hash (sorted iteration over BTreeMap), W88 VOPR runner result aggregation (sorted-by-seed report).
    - **Test scenarios**: 1M ops at seed 42 — re-run, byte-identical; weight assertion (~70/20/10); long run (10M ops, seed 1..100) — no panics, no underflow. Property: replay by seed never diverges.
    - **Acceptance**: op_gen produces 1M ops/s on M2; identical streams under same seed; CI-bot can re-run a failed scenario from seed printed in log.

- [ ] **Build**: `crates/marketdata-kernelbypass/src/feed_handler.rs` — `FeedHandler<P: FeedParser, T: Transport>` glues
  receiver → parse → emit. Emit goes through `messaging-aeron::Publication`. (~105 min)
  - **Why**: feed_handler is the integration point that makes marketdata useful. The Transport (W85-W86) provides raw bytes; the FeedParser (W86 Sat) decodes them; the FeedHandler decides per-message what to do with the event (filter, transform, fan-out) and emits to messaging-aeron::Publication so matching-engine and ledger can subscribe. This is the W87 keystone: with this committed, marketdata is end-to-end and ready for v0.5 SHIP (W90 Tue).
  - *Back-of-envelope* (end-to-end target: **<2 µs P99** transport → parser → publication; budget split = ~500 ns transport recv (from W85/86) + ~500 ns parse (from W86 Sat) + ~500 ns publication.offer + ~500 ns slack for filter/stats/encode):
    The encode-then-publish step is the load-bearing latency multiplier. A naive `let buf = serialize(&event); publication.offer(&buf)` does (a) `serialize` allocates a `Vec<u8>` (~50 ns malloc + 100 ns serialize) then (b) `offer` copies that buf into the term buffer (~30 ns for a 64 B event) — total ~180 ns + alloc dependency. `publication.try_claim(N)` returns `&mut [u8]` pointing **into the term buffer**; encoding directly into it removes the malloc + the intermediate copy, dropping to ~30 ns total. Stats updates use `AtomicU64::fetch_add(Relaxed)` ≈ 3 ns each — fine; using `SeqCst` would cost 10-25 ns due to fence overhead. `last_ts_ns: AtomicU64` with `Ordering::Relaxed` because liveness watchdog tolerates ~ms staleness; SeqCst would buy nothing.
  - **Read first**: Aeron `aeron-archiver` agent loop, `crates/messaging-aeron/src/publication.rs` (your own W67-82 work), Onload's `ef_vi` event-handler pattern.
  - **Design**:
    ```rust
    pub struct FeedHandler<T: Transport, P: FeedParser, F: Filter> {
        transport: T,
        parser: P,
        filter: F,
        publication: messaging_aeron::Publication,
        scratch: ArrayVec<u8, MAX_FRAME>,
        stats: FeedStats,
    }
    pub trait Filter: Send {
        fn keep<E>(&self, ev: &E) -> bool;
    }
    impl<T, P, F> FeedHandler<T, P, F> {
        pub fn run_once(&mut self) -> Result<usize, FeedErr> { /* recv → parse → emit */ }
    }
    pub struct FeedStats {
        recv_packets: u64,
        parsed_events: u64,
        filter_dropped: u64,
        publish_failures: u64,
        last_ts_ns: u64,
    }
    ```
    **Invariants**: (i) one-pass over input bytes: no buffering between parse and publish, (ii) `Publication::offer` failures are NOT swallowed — backpressure surfaces upward, (iii) filter is the only place where events can be dropped — losses tracked, (iv) `last_ts_ns` monotonic for liveness watchdog.
  - **Build steps**: 1. (~10 min) struct + constructor with `with_filter` / `default_filter()`. 2. (~20 min) `run_once()` body: call `transport.recv_batch()`, for each raw frame call `parser.parse()` in a loop until `bytes_consumed == frame.len()`, for each event check `filter.keep()`, encode + publish via `publication.offer()`. 3. (~10 min) handle publication.offer() backpressure: on `BackPressured` increment stat + return; on `Closed` propagate error. 4. (~10 min) wire FeedStats updates inline (atomics for cross-thread read). 5. (~15 min) ergonomic constructor: `FeedHandler::<EpollTransport, ItchParser, AllowAll>::new(addr, pub)`. 6. (~10 min) drive-loop helper `run_forever(deadline)` that calls run_once() in tight loop until deadline. 7. (~10 min) liveness watchdog: separate thread checks `last_ts_ns` updated within 1s, panic-traces if stale. 8. (~10 min) feature-gate the Linux-only transports. 9. (~10 min) tests: synthetic feed → assert published events on a `Subscription`.
  - **Pitfalls**: *Backpressure cascade*: **Symptom**: publication slows, frames queue up in NIC ring, NIC drops, you blame the wrong layer. **Fix**: monitor publication backpressure stat AND NIC drop counter; alert correlates both. *Filter side-effect*: **Symptom**: `Filter` impl computes hashes, blowing latency budget. **Fix**: trait contract says filter MUST be pure + O(1). *Encode-then-copy*: **Symptom**: encoding event into publish buffer copies bytes twice. **Fix**: `publication.try_claim(N)` returns a writable slice; encode directly into it. *Parser state bleeding across run_once*: **Symptom**: edge case where parser keeps half-message state across calls. **Fix**: bounded the parser to consume only on FULL message; partial means wait for next batch.
  - **Expect to hit (perf) #1 — `serialize_to_vec` + `publication.offer(&buf)` instead of `try_claim` (bar (c) violation)**: the natural API is `let buf = encode(&event); publication.offer(&buf);` — but each call (a) allocates a fresh `Vec<u8>` (~50 ns), (b) serializes into it (~100 ns), (c) `offer` copies that buf into the term buffer slot (~30 ns memcpy), (d) drops the Vec on return (~10 ns). At 5M events/s = **5M × 190 ns = 950 ms/sec wasted on alloc+copy+drop** — collapses to ~5M events/s ceiling regardless of how fast Transport/Parser run.
    - Fix: `let claim = publication.try_claim(size_of_event)?; encode_into(&mut claim.bytes_mut(), &event); claim.commit();` — encoding writes **directly into the term buffer slot** (the bytes that the subscriber will read). Zero allocation, zero intermediate copy. Aeron's `try_claim` is precisely the API for this; using `offer` on a hot path is the foot-gun.
    - Cost avoided: ~190 ns/event (alloc + serialize-to-temp + memcpy + drop) → ~30 ns/event (in-place encode). At 5M events/s = **~800 ms/sec reclaimed**, lifting the ceiling from ~5M to ~30M events/s for this stage. End-to-end P99 drops from ~3 µs to ~1.5 µs because the alloc-dependency tail vanishes.
    - Muscle: in zero-copy publish APIs (Aeron `try_claim`, io_uring `IORING_OP_WRITE_FIXED` with registered buf, AF_XDP TX ring), encode directly into the target slot. The `&mut [u8]` claim slot IS the message. Reapplies at: W90 io_uring journal write-fixed (encode Record into pre-registered buf), W92 ledger Archive emission, W82 matching-engine MBO feed publication, W77 messaging-aeron publication itself (when added at v0.7).
  - **Expect to hit (perf) #2 — `AtomicU64` stats with `Ordering::SeqCst` (bar (c) violation, soft)**: writing `stats.recv_packets.fetch_add(1, SeqCst)` because "SeqCst is safe." Each `SeqCst` op on x86_64 inserts a `mfence` (~10-25 ns) and on ARM64 a `dmb ish` (~15-30 ns). At 5M events/s × 4-5 stats per event = 20-25M atomic ops/s × ~20 ns = **400-500 ms/sec** of pure fence overhead — visible as ~10-15% throughput regression with no apparent cause.
    - Fix: `Ordering::Relaxed` for monotonic counters (`recv_packets`, `parsed_events`, `filter_dropped`, `publish_failures`); they are observability-only and do not synchronize with other data. `last_ts_ns` also `Relaxed` (liveness watchdog tolerates ~ms staleness). Reserve `Acquire`/`Release` for actual synchronization (e.g., a "shutdown_requested" flag paired with reading committed state). Reserve `SeqCst` for the rare cases requiring total ordering across multiple atomics (almost never on the hot path).
    - Cost avoided: ~15-25 ns/atomic × 25M ops/s = **~400 ms/sec reclaimed**. On ARM (Apple Silicon dev box; ARM-based cloud) the win is larger because `dmb ish` is heavier than `mfence`.
    - Muscle: every atomic op has a memory-ordering choice; the default-to-SeqCst pattern is the single most common bar-(c) violation in well-meaning code. Reserve SeqCst for ops that need ordering across multiple atomics; use Relaxed for monotonic counters and observability. Reapplies at: W74 matching-engine sequence counter, W77 messaging-aeron term-buffer indices (Acquire/Release pair, not SeqCst), W92 ledger state-hash gossip counter, W82 MBO feed sequence number, W89 message-pool in-flight counter.
  - **Test scenarios**: synthetic ITCH generator → FeedHandler with publication → Subscription on another thread → assert event count matches. Inject backpressure (subscriber pauses) → publish_failures increments; resume → stats normalize. Inject parse error mid-stream → FeedHandler logs + skips, continues. Liveness watchdog fires if transport stalls.
  - **Acceptance**: 5M ITCH events/s through (epoll → ItchParser → publication) on M2 Pro Linux; subscriber receives 5M/s with zero gaps; stats exported via metrics crate.
  - **Downstream**: W90 Tue tag marketdata v0.5; W90 Wed integration test feeds matching-engine; later subscriptions on consensus-vsr (for replicated audit log).

- [NEW v2] **ledger VOPR: assertion engine (part 2)**
  - [ ] **Build**: `crates/ledger-deterministic/src/vopr/assertions.rs` — invariant checks: double-entry sum = 0, no neg balance, no overflow, journal ordering. (~3 hrs)
    - **Why**: VOPR's value is *not* random op generation alone — it's the assertion engine that turns "did it crash?" into "are invariants violated?". A bug can produce non-crashing wrong-state, which only assertion checks catch. Mirror TigerBeetle's `verify_account_balances()` invariant suite. These four invariants are the minimum: anything more nuanced (rate-limits, ledger ratios) can layer later.
    - *Back-of-envelope* (assertions run inside the scenario loop — target adds **≤5% wall-time overhead** when tiered correctly; budget 100k scenarios/day/machine = ~860 ms/scenario means assertion suite total ≤ 40 ms across the scenario):
      Per-op O(1) invariants (NoNegativeBalance, NoOverflow): ~10 ns each × 10k ops = 100 µs total — negligible. O(accounts) invariants (DoubleEntrySumZero): iterating 100k accounts at ~5 ns/account = 500 µs per run; if run every 1000 ops over a 10k-op scenario = 10 runs × 500 µs = 5 ms ✓. JournalOrdering replay: open journal, iterate seq, ~10 ns/record × 10k = 100 µs ✓. State-hash for replica-equality (W92): BLAKE3 over sorted-account-bytes ≈ 1 GB/s → 100k accounts × 64 B = 6.4 MB / 1 GB/s = ~6 ms per scenario ✓. Total assertion overhead ~12 ms / 860 ms = ~1.4% ✓. The tiering rule (cheap every-op, expensive every-1000) is what keeps it under budget.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/state_machine.zig` `verify_*` helpers; `lib/tigerbeetle/src/vopr.zig` step's assertion checks; double-entry accounting axioms.
    - **Design**:
      ```rust
      pub trait Invariant: Send {
          fn check(&self, sm: &LedgerSM, history: &OpHistory) -> Result<(), InvariantViolation>;
          fn name(&self) -> &'static str;
      }
      pub struct DoubleEntrySumZero;
      pub struct NoNegativeBalance;
      pub struct NoOverflow;
      pub struct JournalOrdering;
      pub struct AssertionRunner {
          invariants: Vec<Box<dyn Invariant>>,
          violation_log: Vec<InvariantViolation>,
      }
      pub struct InvariantViolation { pub name: &'static str, pub op_index: u64, pub detail: String }
      ```
      **Invariants checked**: (1) DoubleEntrySumZero: for the set of Transfer operations applied, `Σ debits == Σ credits` modulo `u64` wrap; (2) NoNegativeBalance: every Account.debit_amount ≤ Account.credit_amount + flags.credits_must_not_exceed_debits-rule-flipped; (3) NoOverflow: no Account balance saturated to MAX during the op stream (would silently lose data); (4) JournalOrdering: journal seq strictly monotonic + every replay-read returns same seq sequence.
    - **Build steps**: 1. (~10 min) module skeleton + `Invariant` trait. 2. (~25 min) `DoubleEntrySumZero` — iterate accounts, sum `debits - credits`, assert zero (accounting truism). Edge: pending vs posted distinction. 3. (~25 min) `NoNegativeBalance` — per account, given `flags`, derive max-allowed and check. 4. (~25 min) `NoOverflow` — track per-op deltas, check no `checked_add` would have returned None even if real op used `wrapping_add`. 5. (~25 min) `JournalOrdering` — open journal, iterate, assert seq strictly increases by 1; replay against a clone SM, assert state_hash equals. 6. (~20 min) `AssertionRunner::run_all` after each batch of N ops, collect violations. 7. (~15 min) cheap (every-op) vs expensive (every-N-op) invariant tiers — DoubleEntrySumZero is O(accounts), run every 1000 ops; NoNegativeBalance is O(1) per-op, run every-op. 8. (~10 min) human-readable violation report formatter (used by W88 runner).
    - **Pitfalls**: *False-positive on legitimate two-phase transfer*: **Symptom**: pending Transfer not yet posted; DoubleEntrySumZero fails. **Fix**: invariant operates on POSTED transfers only; pending lives in a separate counter that nets to zero. *Race in concurrent assertion*: **Symptom**: assertion reads SM while next op partially applied. **Fix**: assertions only run between apply() calls; SM apply is atomic. *Wrap-around invisibility*: **Symptom**: balance wraps u64, sum still equals zero, NoOverflow doesn't see it. **Fix**: NoOverflow checks `checked_add` not `wrapping_add` — separate guard from balance check. *Journal replay clobbers state hash*: **Symptom**: replay-clone SM differs because cloned SM allocator state differs. **Fix**: state_hash is canonical (sorted, allocator-independent).
  - **Expect to hit (perf) #1 — running every invariant every op (bar (c) violation)**: a naive `for inv in invariants { inv.check(sm, history)?; }` after every `apply()` call. DoubleEntrySumZero is O(accounts) ~500 µs at 100k accounts; running it after every op in a 10k-op scenario = **5 seconds per scenario** — collapses throughput from 100k scenarios/machine/day to ~1k/day, a **100× regression** that kills the simulator's bug-finding rate.
    - Fix: tier the invariants by cost. **Per-op (cheap, O(1)):** NoNegativeBalance, NoOverflow — checked at the SM boundary inline. **Every-N-ops (expensive, O(accounts) or O(history)):** DoubleEntrySumZero, JournalOrdering, state-hash gossip — checked every 1000 ops or at scenario end. The `AssertionRunner` schedules each invariant via its declared `frequency: AssertionFrequency` enum (`PerOp`, `EveryN(u32)`, `AtScenarioEnd`).
    - Cost avoided: ~5 sec/scenario → ~12 ms/scenario, a **400× speedup of the simulator's wall clock**. Drives the 1M-scenarios/day → 10M-scenarios/day scaling target (W88 v0.7 SHIP → M30 metric).
    - Muscle: in any "check invariants" subsystem, classify by complexity-class and frequency at the design step — not "run them all, profile later." Reapplies at: W94 exec-vm block-stm validation (per-tx O(reads) cheap; cross-tx O(N²) expensive — separate phases), W82 matching-engine pre-trade risk checks (per-order O(1); end-of-batch O(positions) reconciliation), W90 consensus-vsr view-change invariants (per-message vs per-view-transition).
  - **Expect to hit (perf) #2 — `Vec<Box<dyn Invariant>>` dynamic dispatch on the hot path (bar (c) violation)**: storing invariants as `Vec<Box<dyn Invariant>>` and calling `inv.check(...)` adds (i) a heap allocation per Box (~50 ns each at construction; one-shot, not hot-path — fine), (ii) a **vtable indirect call** per `check` (~3-5 ns + branch mispredict penalty ~5 ns on cold call), (iii) breaks inlining — the optimizer can't see through the trait object and inline the O(1) per-op invariants. At 10k ops × ~10 invariants × ~10 ns dynamic-dispatch overhead = ~1 ms per scenario in vtable indirection alone, but the bigger cost is **the lost inlining**: a NoNegativeBalance check that should be 3 ns (one load + one compare + one branch) becomes 30 ns through a vtable.
    - Fix: for the per-op invariants, use a **static enum** `enum CheapInvariant { NoNegativeBalance, NoOverflow, ... }` with a hand-written dispatch `match` that inlines. Cold/expensive invariants (DoubleEntrySumZero) can keep `Box<dyn Invariant>` — they're called rarely. The pattern is: **static-dispatch hot, dynamic-dispatch cold.**
    - Cost avoided: ~7-10 ns per per-op invariant check (saved from inlining + branch prediction) × 10k ops × 2 per-op invariants = ~200 µs/scenario. Small in absolute terms, but compounds with #1 above and matters at the 10M-scenarios/day scale (W88 v0.7).
    - Muscle: `Box<dyn Trait>` is for the cold path (registry, plugins); `enum + match` is for the hot path. Use both deliberately. Reapplies at: W77 messaging-aeron `FragmentHandler` (hot → static; subscription registry → dyn), W94 exec-vm opcode dispatch (already a hand-rolled jump table — same pattern), W82 matching-engine order-type dispatch.
    - **Test scenarios**: inject buggy `apply` that subtracts from debit but skips credit — DoubleEntrySumZero catches it within 1000 ops. Inject `wrapping_sub` on balance — NoNegativeBalance catches at first underflow. Reorder journal seq → JournalOrdering catches. Performance: assertion suite adds <5% wall-time when run every 1000 ops.
    - **Acceptance**: each invariant has a unit test that breaks it with a known-bad apply impl and confirms detection.
    - **Downstream**: W88 VOPR runner runs assertions after each scenario; consensus-vsr v1.0 VOPR (W88 Fri) reuses the trait with additional VSR invariants (quorum-stability, view monotonic).

With a **virtual clock** (`SimClock` advanced by the scheduler, not by wall-time), the same 100 ms p99 latency advances the simulated clock by 100 ms but consumes ~5 ns of wall time (just a counter increment). Same fault coverage, **20-million-× wall-clock speedup**. All four fault classes share this property: the fault is in the simulated state machine, not in real-time effects. The RNG for fault coin-flips is the SAME `SmallRng` from op_gen (perf #1 in Mon's op_gen) — single deterministic entropy source per scenario.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/simulator.zig` — esp. partition logic, the `network.zig` and `storage.zig` fault paths; Jepsen Maelstrom for protocol-fault model reference.
    - **Design**:
      ```rust
      pub trait Fault: Send {
          fn pre_op(&mut self, rng: &mut SmallRng, ctx: &mut SimCtx) -> FaultEffect;
          fn name(&self) -> &'static str;
      }
      pub enum FaultEffect { None, DropMessage, ReorderInflight, CrashRestart, DiskLatencyMs(u32) }
      pub struct NetworkPartition { drop_prob: f32 }
      pub struct MessageReorder { shuffle_buffer_size: usize }
      pub struct CrashRestart { mean_uptime_ops: u64 }
      pub struct SlowDisk { latency_p50_us: u32, latency_p99_us: u32 }
      pub struct FaultBudget { total: u32, per_kind: FxHashMap<&'static str, u32> }
      ```
      **Invariants**: (i) all faults seeded from same RNG as op_gen so reproducible, (ii) "fault budget" prevents the simulator from being all faults all the time — at most 1 fault per N ops, (iii) crash-restart preserves journal but invalidates in-memory state, (iv) faults compose: NetworkPartition + SlowDisk + CrashRestart can all be active concurrently.
    - **Build steps**: 1. (~10 min) `Fault` trait + `SimCtx` carrying refs to network sim + storage sim. 2. (~30 min) `NetworkPartition` — drop_prob × rng → drop message; supports partial partitions (drop only from set A to set B). 3. (~30 min) `MessageReorder` — buffer N in-flight messages, swap two random indices on each step. 4. (~40 min) `CrashRestart` — sample uptime ops geometrically, on trigger: snapshot SM via `snapshot()` write, then drop SM, recreate via `restore()`+journal replay; verify replay seq matches pre-crash. 5. (~30 min) `SlowDisk` — wrap journal writes with `tokio::time::sleep` (or simulator's clock advance); use log-normal sample for latency. 6. (~15 min) FaultBudget bookkeeping — increment per kind, hard cap. 7. (~15 min) docs on fault correlation: which combinations are "interesting" vs "physical impossibility".
    - **Pitfalls**: *Fault correlation explosion*: **Symptom**: NetworkPartition + CrashRestart + SlowDisk + Reorder all active → 99% of scenarios time out, 0 useful coverage. **Fix**: fault budget per scenario (≤3 active faults); document the matrix in a scenario YAML. *CrashRestart with hot data*: **Symptom**: snapshot mid-Transfer, restore sees inconsistent state. **Fix**: snapshot only at op boundaries (between apply calls). *SlowDisk causing scenario timeout*: **Symptom**: SlowDisk p99 = 100ms × 1M ops = 100k seconds. **Fix**: simulator clock is virtual — sleep advances virtual clock, not wall clock; cap virtual scenario duration. *Reorder without bound*: **Symptom**: reorder buffer grows unbounded, OOM. **Fix**: hard cap reorder buffer size; FIFO eviction.
  - **Expect to hit (perf) #1 — wall-clock `tokio::time::sleep` in SlowDisk (bar (c) violation, catastrophic)**: implementing `SlowDisk::pre_op` as `tokio::time::sleep(Duration::from_micros(latency_us)).await` "to simulate the latency." Each scenario does ~10k journal writes; at p99 = 1 ms slow-disk latency = **10 seconds wall-clock per scenario**. 100-scenarios-in-parallel rig = 100k seconds = 28 hours per 100-scenario sweep. The simulator becomes useless for bug-finding because the scenario rate collapses.
    - Fix: every fault operates on the **virtual `SimClock`**, never wall-clock. `SlowDisk::pre_op` does `sim_clock.advance(Duration::from_micros(latency_us))` — a `u64 += u64` operation costing ~1 ns. The journal write's `oneshot::Sender<()>` is parked in a min-heap keyed by `sim_clock + latency`; the scheduler advances the clock to the next event, fires the sender, and continues. The same fault coverage (latency-tail bugs, ordering bugs under slow disk) is exercised with **zero wall-clock cost**.
    - Cost avoided: 10 sec/scenario → ~10 µs/scenario for the same fault — a **million-fold speedup**, which is the difference between 100 scenarios/day/machine and 100k scenarios/day/machine. This is the design choice that lets VOPR reach 1M cumulative scenarios by W88 (the v0.7 SHIP target).
    - Muscle: deterministic simulators run on **virtual time** — real-time sleep belongs only to integration tests that exercise real I/O. The `SimClock` abstraction must be the *only* time source touched by faults and the SM. Reapplies at: W88 VOPR runner per-scenario timeout (wall-clock kill watchdog separate from in-sim clock), W88 consensus-vsr `VoprReplica::step()` (virtual clock injection), W90 ledger v1.0 io_uring journal in sim mode (group-commit horizon driven by sim_clock), W92 ledger v1.0 SHIP determinism gate (verifies no `Instant::now()` leak).
  - **Expect to hit (perf) #2 — `Vec<Message>` reorder buffer unbounded growth (bar (c) violation: memory + non-determinism)**: implementing `MessageReorder` as `buffer: Vec<Message>` that `Vec::push` per in-flight message and `swap_remove(rng.gen_range(0..len))` per pre_op. Under heavy partition + reorder mix, the buffer grows to 100k messages × 8 KB each = **800 MB per scenario** × 100 parallel scenarios = 80 GB RAM, OOM-kill. Worse: `Vec::push` can `realloc` → new pointer → invalidates any `&mut Message` reference; the message order becomes non-deterministic across reruns of the same seed (allocator-dependent reallocation point).
    - Fix: `buffer: ArrayVec<Message, MAX_REORDER>` with `MAX_REORDER = 256` per (from, to) pair. On full, FIFO-evict the oldest (mark as "dropped via reorder-buffer overflow," count via a stat). The bound is hard; the eviction is deterministic. Memory: 256 × 8 KB = 2 MB per pair × N-pairs — predictable, fits in pool.
    - Cost avoided: ~800 MB → 2 MB per pair (a 400× memory win allowing 100-scenarios-parallel on a 16 GB box vs needing a 2 TB box); plus the determinism debt (the **same seed** producing a different reorder pattern across reruns because of allocator state).
    - Muscle: every in-flight / pending / buffered collection in a deterministic SM is `ArrayVec<_, BOUND>` with explicit overflow policy, never `Vec` with unbounded `push`. Reapplies at: W88 VSR `SimNetwork` per-(from,to) queue, W89 ledger TransferPool free-list, W89 VSR message body `ArrayVec<u8, MAX_MESSAGE_BODY>`, W82 matching-engine in-flight order set, W94 exec-vm versioned-memory MAX_VERSIONS=256 cap.
