    #### Phase 1 — Problem, prediction, design (~45 min, no code yet)

    - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/ledger-deterministic/notes/87_op_gen_prediction.md`:
      - P1: the RNG you'd reach for, exact import line (most write `use rand::thread_rng;` — predict this).
      - P2: predicted ns/op for an account pick out of a 10k pool with your chosen data structure.
      - P3: predicted outcome of running `op_gen(42)` twice and comparing the first 10k ops — identical or not, and why.
      - P4: how the first few ops behave when the account pool starts empty (predict the panic/no-op).
      - P5: **list every Phase-2 test you predict your first attempt will fail.** Compare to reality after tests run.
    - *Mental model*: `OpGen` is a deterministic, infinite iterator of `ClientOp`s — a pure function of `(seed, op_count, account_pool)`. Given a seed it must emit the same byte stream on every machine, forever. It is the *single entropy source* the whole simulator borrows from.
    - *Contract*:
      ```rust
      pub enum ClientOp { CreateAccount { id: AccountId }, Transfer { id: TransferId, debit: AccountId, credit: AccountId, amount: u64 }, Lookup { id: AccountId } }
      pub struct OpWeights { pub transfer: u8, pub lookup: u8, pub create: u8 } // sums to 100
      pub struct OpGen { rng: SmallRng, account_pool: ArrayVec<AccountId, 10_000>, op_count: u64, weights: OpWeights, edge_cases: bool }
      impl OpGen { pub fn new(seed: u64, weights: OpWeights) -> Self; pub fn next_op(&mut self) -> ClientOp; }
      impl Iterator for OpGen { type Item = ClientOp; /* never None */ }
      ```
    - *Back-of-envelope*: target ≥1M ops/s single-thread → ≤1 µs/op (R6), but the generator must be FAR below that or it becomes the simulator bottleneck — budget ~50 ns/op. Account pick must be O(1): an `ArrayVec` index is one L1 read (~0.5 ns); a `HashMap::iter().nth(N)` is O(N) ≈ 10k buckets × ~5 ns = **50 µs — a 50,000× cliff** over the 1 ns indexed pick. One `thread_rng()` call = a `getrandom` syscall (~300 ns lazy-init) — at 1M ops/s that alone is ~30% of a core, and it *defeats replay*.
    - **Requirements** R1..R8 — write in `crates/ledger-deterministic/notes/87_op_gen_design.md`:
      - R1. Given seed S, the entire op stream is byte-identical across runs and machines.
      - R2. NO `SystemTime`, NO `thread_rng`/`OsRng` — ALL randomness via a single seeded `SmallRng`.
      - R3. Transfer always picks debit ≠ credit from `account_pool`.
      - R4. CreateAccount appends to `account_pool` so future Transfers have valid targets (Transfer/Lookup NEVER append).
      - R5. `op_count` monotonic — used directly as TransferId.
      - R6. ≥1M ops/sec single-thread (workload generator cannot be the simulator bottleneck).
      - R7. Account pool is `ArrayVec<AccountId, 10_000>` — hard bound, no heap growth.
      - R8. Edge-case generator (toggleable `edge_cases`): empty Transfer, self-transfer, max-amount — for the adversarial sweep.
    - **Design walk-through** D1..D7 — answer in the design doc; no peeking at TigerBeetle source until Phase 3:
      - D1. Sketch `OpGen` + `ClientOp` enum + `OpWeights`. Property table of RNG choices: `thread_rng` (Sync yes / 300 ns first-call / non-deterministic — REJECT), `OsRng` (syscall per call — REJECT), `StdRng` (deterministic but ~2× slower ChaCha), `SmallRng`/xoshiro256++ (deterministic, ~1 ns/u64 — PICK).
      - D2. Property table of pool data structure: `Vec<AccountId>` (O(1) index but heap-growable — REJECT for static-mem bar), `HashMap<AccountId,()>` (non-det iter + O(N) nth — REJECT), `ArrayVec<AccountId, 10_000>` (O(1) index, fixed, deterministic — PICK).
      - D3. **Pre-mortem (load-bearing) — thread_rng:** write the 4-line trace: run 1 seeds `thread_rng` from OS entropy → stream A; run 2 seeds from different entropy → stream B; `A != B`; W88 reproducer-by-seed contract is now a lie. At 1M ops/s a per-op `thread_rng()` is ~300 ns × 1M = 30% of a core burned on `getrandom`.
      - D4. **Pre-mortem (load-bearing) — HashMap pool:** write the 4-line trace: machine X hashes `AccountId` with seed h1, machine Y with seed h2 → `pool.iter().nth(K)` returns different account → divergent stream from same `seed` param. Plus `iter().nth(K)` is O(K) ≈ 50 µs at the 10k tail.
      - D5. **Pre-mortem — empty pool early:** first ops are Transfer but pool is empty → `gen_range(0..0)` panics. Prime with N CreateAccount ops, or force `weights.create = 100` until `pool.len() >= 100`.
      - D6. **Pre-mortem — pool exhaustion:** after 10k creates the `ArrayVec` is full; further CreateAccount must be dropped/converted to Transfer (never panic on push). Document 10k as the simulator's account scale.
      - D7. **Anti-shortcut audit:** (a) "just use `thread_rng`, it's ergonomic" → wrong: kills replay (R1/R2). (b) "`HashMap` for easy contains-check" → wrong: non-det iteration (R1) + O(N) pick (R6). (c) "`Vec` + `push`, it's fine" → wrong: heap growth violates the static-mem bar inherited at W89; use `ArrayVec` now so the type is already right.
    - **Output**: `crates/ledger-deterministic/notes/87_op_gen_design.md` with R1–R8, D1–D7, the two bad-stream traces.

    #### Phase 3 — Make the tests pass, one failure at a time (~105 min)

    Newbie failures first, expert last.

    - **(NEWBIE) When `op_gen_account_pool_grows_via_create_only` fails because early Transfers panic:**
      - Symptom: `gen_range(0..0)` panics on the first op; or pool grows on Transfer.
      - Why: pool starts empty and Transfer picks before any CreateAccount; or Transfer mistakenly appends a synthetic account.
      - Fix: prime the pool (force `create` weight to 100 until `pool.len() >= 100`); only CreateAccount appends.
      - Cost avoided: a crash on op 1 of every scenario — 100% scenario loss, not slow.
      - Muscle: a workload generator must establish its own preconditions before sampling from them. Reapplies at: W88 VOPR runner scenario warm-up, W89 ledger TransferPool seeding.

    - **(SENIOR) When `op_gen_no_thread_rng_no_systemtime` fires (and `op_gen_byte_identical_across_runs` flakes ~every 10th run):**
      - Symptom: cargo-deny/clippy fires on a transitive `rand::thread_rng`; same seed produces a different op stream sporadically.
      - Why: any `thread_rng()` lazy-inits from the OS-entropy `getrandom` syscall (~300 ns) and is seeded *differently every run* — it breaks BOTH perf AND determinism. OsRng/`SystemTime::now` are the same trap.
      - Fix: a SINGLE `SmallRng` (xoshiro256++) seeded at scenario start via `SmallRng::seed_from_u64(seed)`; every roll (op-type, account index, amount, later fault coin-flips) flows through `self.rng`. Enforce with clippy `disallowed_methods = ["rand::thread_rng","rand::random","std::time::SystemTime::now"]`.
      - Cost avoided: ~300 ns per spurious `thread_rng` **(bar (c) violation)** PLUS the entire determinism debt — one non-deterministic call invalidates the W88 reproducer-by-seed contract and the W92 SHIP gate.
      - Muscle: any deterministic-replay system has exactly ONE entropy source per scenario, owned and seeded from the input — `thread_rng`/`OsRng`/`SystemTime::now` are banned by lint, not by discipline. Reapplies at: W87 Tue assertions (read SM deterministically), W87 Wed faults (coin-flips from the same RNG), W88 runner (each worker RNG seeded from a master seed), W90 consensus-vsr VOPR (replica clocks from one `SimClock`), W92 ledger v1.0 SHIP determinism gate.

    - **(SENIOR) When `op_gen_account_pool_arrayvec_bounded` finds a HashMap (and `op_gen_byte_identical` diverges across machines):**
      - Symptom: same seed → different op stream across machines; pick latency spikes to ~50 µs.
      - Why: `account_pool: HashMap<AccountId,()>` for "easy contains-check", then `pool.iter().nth(rng.gen_range(0..len))` to pick. (a) HashMap iteration order depends on the per-process hash seed → non-deterministic; (b) `iter().nth(N)` is O(N) ≈ 50 µs from a 10k pool (50× over the 1 µs op budget).
      - Fix: `account_pool: ArrayVec<AccountId, 10_000>`; pick via `pool[rng.gen_range(0..pool.len())]` — O(1), single L1 read, bit-deterministic. If a contains-check is later needed, a separate bounded `FixedMap` (W89 Tue) — for op_gen the indexed pick is enough.
      - Cost avoided: ~50 µs/pick → ~1 ns/pick **(50,000× win, bar (c) violation when left as HashMap)** plus the determinism debt.
      - Muscle: in deterministic-replay code every "set-like" structure is a sorted vector / `ArrayVec` / `FixedMap` with an explicit hash seed; `std::collections::HashMap` and `ahash::AHashMap` are cargo-deny-banned. Reapplies at: W87 Tue assertion suite (iterating accounts), W89 Tue ledger AccountMap (FixedMap), W92 ledger v1.0 `state_hash` (sorted BTreeMap), W88 VOPR runner result aggregation (sorted-by-seed report).

    - **(EXPERT) When `op_gen_1m_ops_per_sec` lands below 5e6 ops/s:**
      - Symptom: bench reports ~2e6 ops/s; generator becomes the simulator bottleneck instead of the SM.
      - Why: per-op heap churn — building each `ClientOp` allocates (e.g. boxing, or a `String` account label), or `StdRng` (ChaCha20, ~2× SmallRng) chosen "for safety".
      - Fix: `ClientOp` is a `Copy` enum (all fixed-size fields, no `String`/`Box`); `SmallRng` for the stream; amount via `1 + (self.rng.next_u32() & 0xFFFF)` (cheap mask, small to avoid quick u64 overflow).
      - Cost avoided: ~500 ns/op → ~40 ns/op **(12× , bar (c) violation)**; keeps the generator <5% of total sim time.
      - Muscle: the test harness/generator must be an order of magnitude faster than the thing it tests, or it measures itself. Keep hot enum payloads `Copy` and allocation-free. Reapplies at: W88 VOPR runner inner loop, W82 matching-engine MBO replay generator.

  #### Phase 1 — Problem, prediction, design (~40 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/marketdata-kernelbypass/notes/87_feed_handler_prediction.md`:
    - P1: the publish call you'd reach for first (predict `publication.offer(&encoded_vec)`).
    - P2: predicted ns/event for your publish path (count malloc + serialize + memcpy + drop).
    - P3: predicted memory ordering you'd use for the recv/parsed/dropped counters (predict SeqCst).

    - P5: **list every Phase-2 test you predict your first attempt will fail.**
  - *Mental model*: a single-pass pump — for each frame, parse → filter → publish, with no buffer between parse and publish and no allocation on the hot path. The `Publication` term-buffer slot *is* the message.
  - *Contract*:
    ```rust
    pub trait Filter { fn keep(&self, ev: &MarketEvent) -> bool; } // pure, O(1), no alloc
    pub struct FeedStats { recv: AtomicU64, parsed: AtomicU64, dropped: AtomicU64, publish_failures: AtomicU64, last_ts_ns: AtomicU64 }
    pub struct FeedHandler<P: FeedParser, T: Transport, F: Filter> { transport: T, parser: P, filter: F, pub: messaging_aeron::Publication, stats: FeedStats }
    impl<...> FeedHandler<...> { pub fn run_once(&mut self) -> Result<usize, BackpressureError>; /* events published this poll */ }
    ```
  - *Back-of-envelope*: target 5M ITCH events/s → 200 ns/event total budget, P99 <2 µs end-to-end (R5). The `offer(&vec)` path costs ~50 ns malloc + ~100 ns serialize + ~30 ns memcpy + ~10 ns drop = **~190 ns/event of pure waste** → at 5M/s that is ~950 ms/sec, pinning the ceiling at ~5M. `try_claim` + encode-into the term buffer removes all of it (~30 ns memcpy only), lifting the ceiling to ~30M/s. Each SeqCst counter inserts an `mfence` (~10-25 ns x86) / `dmb ish` (~15-30 ns ARM); 5 stats × 5M/s × ~20 ns = ~400-500 ms/sec — Relaxed makes it ~free.
  - **Requirements** R1..R8 — write in `crates/marketdata-kernelbypass/notes/87_feed_handler_design.md`:
    - R1. One pass over input bytes: no buffering between parse and publish.
    - R2. `Publication::offer`/`try_claim` failure NOT swallowed — backpressure surfaces upward as `Err`.
    - R3. Filter is the ONLY place events can be dropped; drops counted.
    - R4. `last_ts_ns` monotonic for a liveness watchdog.
    - R5. End-to-end <2 µs P99 transport→parser→publication.
    - R6. Encode-into via `publication.try_claim`, NOT serialize-then-offer.
    - R7. Stats use `AtomicU64::fetch_add(Relaxed)` — monotonic observability counters need no fence.
    - R8. Filter is O(1) + pure (no side effects, no allocation).
  - **Design walk-through** D1..D7:
    - D1. Sketch `FeedHandler` + `Filter` trait + `FeedStats`. Property table: `offer(&[u8])` (alloc + copy), `try_claim`+encode_into (zero-alloc, claim is `&mut [u8]`), batch-then-publish (adds latency — REJECT for R1).
    - D2. **Pre-mortem (load-bearing) — serialize+offer:** trace one event through malloc(50)→serialize(100)→offer copies into term buffer(30)→Vec drop(10) = ~190 ns of avoidable work; multiply by 5M.
    - D3. **Pre-mortem (load-bearing) — SeqCst stats:** trace one `fetch_add(SeqCst)`: emits `mfence`; the CPU drains the store buffer; ~20 ns; × 25M atomic ops/s = ~0.5 s/sec gone, for counters nothing reads synchronously.
    - D4. **Pre-mortem — backpressure cascade:** publication slows → frames queue in NIC RX ring → NIC drops → you blame the parser. Surface `BackpressureError` AND read the NIC drop counter so the blame lands on the right layer.
    - D5. **Pre-mortem — filter side-effect:** a "filter" that computes a hash or logs blows the latency budget. The trait contract forbids it; enforce with a lint disallowing alloc in `keep`.
    - D6. **Pre-mortem — parser state bleed:** parser keeps half a message across `run_once` calls and emits garbage. Parser consumes only on a FULL message; a partial frame waits for the next poll.
    - D7. **Anti-shortcut audit:** (a) `offer(&encode(ev))` "is the simple API" → wrong: allocates per event (R6). (b) `SeqCst` "is always safe" → wrong: it is the most common bar-(c) violation; these counters synchronize nothing (R7). (c) `Box<dyn Filter>` "for flexibility" → wrong on the hot path: vtable + no inline; use a generic `F: Filter` param.

  - **(NEWBIE) When `feed_handler_liveness_watchdog_fires_on_stale_ts` never fires:**

      - Cost avoided: false post-restart violations that mask real crash-consistency bugs.
      - Muscle: a crash-consistency test must crash only at points the real system can crash — torn-write injection is a separate, explicit fault. Reapplies at: W90 ledger io_uring fsync-boundary crash, W92 ledger v1.0 recovery replay.

    #### Phase 1 — Problem, prediction, design (~45 min, no code yet)

    - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/ledger-deterministic/notes/87_canary_prediction.md`:

    - *Contract*:
      ```rust
      pub struct Canary { pub name: &'static str, pub inject: fn(&mut StateMachine), pub max_seeds: u32 }
      pub struct CanaryResult { pub name: &'static str, pub seeds_to_catch: Option<u32> } // None = MISSED
      pub fn run_canary(c: &Canary, seeds: impl Iterator<Item = u64>) -> CanaryResult;
      ```
    - *Back-of-envelope*: at ~10 µs/scenario (virtual time), running 1000 seeds per canary = ~10 ms wall; 5 canaries = ~50 ms. So the harness can sweep the whole kill-list every Sunday in well under a second of compute — the cost is *writing realistic canaries*, not running them.

      - R1. Kill-list (initial 5): off-by-one in Transfer apply (debit before credit check); double-spend (same transfer applied twice with stale dedup); replay (old transfer re-injected); partition-late-commit (op applied on the minority side after partition heal); snapshot-mid-burst (checkpoint advances past uncommitted in-flight transfers).
      - R2. Injector: each entry is a delta to the production code introducing the bug + a VOPR run + an assertion that VOPR catches it within `max_seeds` (K=100 initial target). If VOPR misses → harden the relevant invariant.
      - R3. Canaries must be *realistic* — informative only when K>1; aim for 10-1000 seeds-to-catch.
      - R4. Output `notes/vopr_kill_list.md`: a table of bug, injection delta, K-seed-to-catch, status (caught / hardening-required).
      - R5. Weekly cadence: 1 new canary OR re-run all existing every Sunday W95-W144; target ≥20 caught canaries by M36.
      - R6. A MISSED canary is a hard CI failure (it means an invariant gap), not a warning.
    - **Design walk-through** D1..D4:
      - D1. Sketch `Canary` + `CanaryResult` + the runner that streams seeds until the assertion suite fires or `max_seeds` is exhausted.
      - D2. **Pre-mortem (load-bearing) — trivial canary:** trace a boolean-flip canary: every seed produces an immediately-violating state → K=1 → the metric distinguishes nothing. The canary must hide in a rare path.
      - D3. **Pre-mortem — false "caught":** a canary "caught" because of an UNRELATED assertion (not the one guarding its bug class). Record WHICH invariant fired; require it to be the relevant one.
      - D4. **Anti-shortcut audit:** (a) "flip a flag, easy canary" → wrong: K=1, uninformative (R3). (b) "any assertion firing = caught" → wrong: must be the relevant invariant (D3). (c) "log a miss and move on" → wrong: a miss is a CI failure + invariant-hardening task (R6).

    #### Phase 3 — Make the tests pass, one failure at a time (~110 min)

    - **(EXPERT) When `canary_realistic_takes_more_than_one_seed` fails (K=1 for all):**
      - Symptom: every canary is caught on seed 1; the K-seed metric is meaningless.
      - Why: the canary flips a boolean that makes EVERY op violate (e.g. `valid_transfer = true` always) — any assertion fires immediately.
      - Fix: make canaries hide in rare paths — off-by-one only at the exact balance boundary; a partition that heals at a specific tick (1-in-10000 sequence). Tune so K lands in 10-1000.
      - Cost avoided: a false sense of coverage — a VOPR that only catches obvious bugs proves nothing about the subtle ones it was built for.
      - Muscle: a test's *sensitivity* is the deliverable; a canary that any seed catches measures the harness's existence, not its power. Reapplies at: W88 consensus-vsr canary (rare split-vote bug), W94 exec-vm block-stm conflict canary.

    - **(EXPERT) When `canary_all_caught_within_max_seeds` reports a MISS:**
      - Symptom: a planted bug runs 100 seeds and no assertion fires.
      - Why: there is no invariant guarding that bug class (e.g. replay-attack has no dedup invariant).
      - Fix: a miss is a signal — add/harden the invariant (here: a dedup invariant asserting each TransferId applies at most once), then re-run until caught. Record the hardening in the kill-list row.
      - Cost avoided: a real production bug of that class shipping undetected — the exact M30 risk the Register flags.
      - Muscle: a VOPR miss is not a test failure to silence — it is a discovered invariant gap to close; the kill-list is the audit trail. Reapplies at: W88 VSR canary misses, W92 ledger v1.0 SHIP gate (zero open misses required).
