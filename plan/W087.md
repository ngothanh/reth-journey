    - *Mental model*: `OpGen` is a deterministic, infinite iterator of `ClientOp`s — a pure function of `(seed, op_count, account_pool)`. Given a seed it must emit the same byte stream on every machine, forever. It is the *single entropy source* the whole simulator borrows from (op-type rolls today, fault coin-flips Wed, canary seed-sweeps Thu).
    - *Contract*:
      ```rust
      pub enum ClientOp { CreateAccount { id: AccountId }, Transfer { id: TransferId, debit: AccountId, credit: AccountId, amount: u64 }, Lookup { id: AccountId } }
      pub struct OpWeights { pub transfer: u8, pub lookup: u8, pub create: u8 } // sums to 100
      pub struct OpGen { rng: SmallRng, account_pool: ArrayVec<AccountId, 10_000>, op_count: u64, weights: OpWeights, edge_cases: bool }
      impl OpGen { pub fn new(seed: u64, weights: OpWeights) -> Self; pub fn next_op(&mut self) -> ClientOp; }
      impl Iterator for OpGen { type Item = ClientOp; /* never None */ }
      ```
    - *Back-of-envelope*: target ≥1M ops/s single-thread → ≤1 µs/op (R6), but the generator must be FAR below that or it becomes the simulator bottleneck — budget ~50 ns/op. Account pick must be O(1): an `ArrayVec` index is one L1 read (~0.5 ns); a `HashMap::iter().nth(N)` is O(N) ≈ 10k buckets × ~5 ns = **50 µs — a 50,000× cliff** over the 1 ns indexed pick. One `thread_rng()` call = a `getrandom` syscall (~300 ns lazy-init) — at 1M ops/s that alone is ~30% of a core, and it *defeats replay*.
    - **Requirements** R1..R8 — write in `crates/ledger-deterministic/notes/87_op_gen_design.md`:
      - R1. Given seed S, the entire op stream is byte-identical across runs and machines.
      - R2. NO `SystemTime`, NO `thread_rng`/`OsRng` — ALL randomness via a single seeded `SmallRng`.
      - R3. Transfer always picks debit ≠ credit from `account_pool`.
      - R4. CreateAccount appends to `account_pool` so future Transfers have valid targets (Transfer/Lookup NEVER append).
      - R5. `op_count` monotonic — used directly as TransferId.
      - R6. ≥1M ops/sec single-thread (the workload generator cannot be the simulator bottleneck).
      - R7. Account pool is `ArrayVec<AccountId, 10_000>` — hard bound, no heap growth.
      - R8. Edge-case generator (toggleable `edge_cases`): empty Transfer, self-transfer, max-amount — for the adversarial sweep.

    #### Phase 3 — Make the tests pass, one failure at a time (~105 min)

    Newbie failures first, expert last.

    - **(NEWBIE) When `op_gen_account_pool_grows_via_create_only` fails because early Transfers panic:**
      - Symptom: `gen_range(0..0)` panics on the first op; or the pool grows on Transfer.
      - Why: the pool starts empty and Transfer picks before any CreateAccount; or Transfer mistakenly appends a synthetic account.
      - Fix: prime the pool (force `create` weight to 100 until `pool.len() >= 100`); only CreateAccount appends.
      - Cost avoided: a crash on op 1 of every scenario — 100% scenario loss, not slow.
      - Muscle: a workload generator must establish its own preconditions before sampling from them. Reapplies at: W88 VOPR runner scenario warm-up, W89 ledger TransferPool seeding, W108 cluster-VOPR account warm-up.

    - **(SENIOR) When `op_gen_no_thread_rng_no_systemtime` fires (and `op_gen_byte_identical_across_runs` flakes ~every 10th run):**
      - Symptom: cargo-deny/clippy fires on a transitive `rand::thread_rng`; the same seed produces a different op stream sporadically.
      - Why: any `thread_rng()` lazy-inits from the OS-entropy `getrandom` syscall (~300 ns) and is seeded *differently every run* — it breaks BOTH perf AND determinism. `OsRng`/`SystemTime::now` are the same trap.
      - Fix: a SINGLE `SmallRng` (xoshiro256++) seeded at scenario start via `SmallRng::seed_from_u64(seed)`; every roll (op-type, account index, amount, later fault coin-flips, later canary seed-sweep) flows through `self.rng`. Enforce with clippy `disallowed_methods = ["rand::thread_rng","rand::random","std::time::SystemTime::now"]`.
      - Cost avoided: ~300 ns per spurious `thread_rng` **(bar (c) violation)** PLUS the entire determinism debt — one non-deterministic call invalidates the W88 reproducer-by-seed contract, the W92 SHIP gate, and the W108 cluster-VOPR reproducibility on which §4A acceptance #7 depends.
      - Muscle: any deterministic-replay system has exactly ONE entropy source per scenario, owned and seeded from the input — `thread_rng`/`OsRng`/`SystemTime::now` are banned by lint, not by discipline. Reapplies at: W87 Tue assertions (read the SM deterministically), W87 Wed faults (coin-flips from the same RNG), W88 runner (each worker RNG seeded from a master seed), W90 `consensus-vsr` VOPR (replica clocks from one `SimClock`), W92 ledger v1.0 SHIP determinism gate, W97 `risk-engine` per-tick recompute (no wall-clock), W108 cluster-VOPR.

    - **(SENIOR) When `op_gen_account_pool_arrayvec_bounded` finds a HashMap (and `op_gen_byte_identical` diverges across machines):**
      - Symptom: same seed → different op stream across machines; pick latency spikes to ~50 µs.
      - Why: `account_pool: HashMap<AccountId,()>` for "easy contains-check", then `pool.iter().nth(rng.gen_range(0..len))` to pick. (a) HashMap iteration order depends on the per-process hash seed → non-deterministic; (b) `iter().nth(N)` is O(N) ≈ 50 µs from a 10k pool (50× over the 1 µs op budget).
      - Fix: `account_pool: ArrayVec<AccountId, 10_000>`; pick via `pool[rng.gen_range(0..pool.len())]` — O(1), single L1 read, bit-deterministic. If a contains-check is later needed, a separate bounded `FixedMap` (W89 Tue) — for op_gen the indexed pick is enough.
      - Cost avoided: ~50 µs/pick → ~1 ns/pick **(50,000× win, bar (c) violation when left as HashMap)** plus the determinism debt.
      - Muscle: in deterministic-replay code every "set-like" structure is a sorted vector / `ArrayVec` / `FixedMap` with an explicit hash seed; `std::collections::HashMap` and `ahash::AHashMap` are cargo-deny-banned. Reapplies at: W87 Tue assertion suite (iterating accounts), W89 Tue ledger AccountMap (FixedMap), W92 ledger v1.0 `state_hash` (sorted BTreeMap), W88 VOPR runner result aggregation (sorted-by-seed report), W97 `risk-engine` account shard map.

    - **(EXPERT) When `op_gen_1m_ops_per_sec` lands below 5e6 ops/s:**
      - Symptom: bench reports ~2e6 ops/s; the generator becomes the simulator bottleneck instead of the SM.
      - Why: per-op heap churn — building each `ClientOp` allocates (e.g. boxing, or a `String` account label), or `StdRng` (ChaCha20, ~2× SmallRng) chosen "for safety".
      - Fix: `ClientOp` is a `Copy` enum (all fixed-size fields, no `String`/`Box`); `SmallRng` for the stream; amount via `1 + (self.rng.next_u32() & 0xFFFF)` (cheap mask, small to avoid quick u64 overflow).
      - Cost avoided: ~500 ns/op → ~40 ns/op **(12×, bar (c) violation)**; keeps the generator <5% of total sim time so it never masks the SM's real perf.
      - Muscle: the test harness/generator must be an order of magnitude faster than the thing it tests, or it measures itself. Keep hot enum payloads `Copy` and allocation-free. Reapplies at: W88 VOPR runner inner loop, W82 matching-engine MBO replay generator, W108 cluster-VOPR op driver.
