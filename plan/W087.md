    - 🔧 **Why this matters**: VOPR is TigerBeetle's marquee bug-finding tool. op-stream generator is engine of whole simulator — realistic-but-adversarial workloads exercising every code path. 70/20/10 mirrors real ledger (lookups + transfers dominate).     #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

    - **Requirements** — write in `crates/ledger-deterministic/notes/87_op_gen_design.md`:
      - R1. Given seed S, entire op stream byte-identical across runs.
      - R2. NO `system_time`, NO `thread_rng` — ALL randomness via single seeded `SmallRng`.
      - R3. Transfer always picks debit ≠ credit from `account_pool`.
      - R4. CreateAccount appends to `account_pool` so future Transfers have valid targets.
      - R5. `op_count` monotonic — used as TransferId.
      - R6. ≥1M ops/sec single-thread (workload generator cannot be simulator bottleneck).
      - R7. Account pool capped via `ArrayVec<AccountId, 10_000>` — hard bound, no growth.
      - R8. Edge-case generator (toggleable): empty Transfer, self-transfer, max-amount.

    - **Design walk-through**:
      - D1. Sketch OpGen + ClientOp enum + OpWeights struct.
      - D2. **Pre-mortem (thread_rng):** any `thread_rng()` call = `getrandom` syscall (~300 ns) + different stream per run → defeats VOPR replay. At 1M ops/s, even one such call/op = 30% CPU on entropy.
      - D3. **Pre-mortem (HashMap account_pool):** non-deterministic iteration order (different per-run hash seed) → same `seed` parameter produces different op stream. Plus `iter().nth(N)` is O(N) ≈ 50 µs for N=10k.
      - D4. **Pre-mortem (empty pool early):** first ops are Transfer but pool empty. Prime with N CreateAccount ops or weight CreateAccount=100% until pool ≥100.
      - D5. **Pre-mortem (account pool exhaustion):** after 10k creates, can't grow; Transfer keeps re-picking same pairs. ArrayVec<_, 10_000> is hard cap; document as simulator's account scale; raise if scenarios need more.
      - D6. Realistic Transfer: pick debit uniform from pool, credit different from debit; amount = 1 + rng.gen::<u32>() & 0xFFFF (small to avoid quick overflow).

    #### Phase 3 — Make the tests pass, one failure at a time (~110 min)

    - **When `op_gen_no_thread_rng_no_systemtime_lint` fires in dependency:**
      - Symptom: cargo-deny fires on transitive call to `rand::thread_rng`; deterministic replay fails sporadically; same seed produces different op stream every ~10th run.
      - Why: any `thread_rng()` call (lazy-init via OS-entropy `getrandom` syscall, ~300 ns) breaks BOTH perf AND determinism. OS-entropy guarantees different streams per run, defeating VOPR replay.
      - Fix: SINGLE `SmallRng` (xoshiro256++) seeded at scenario start via `SmallRng::seed_from_u64(seed)`. All randomness — op-type roll, account selection, amount, fault coin-flips — flows through `self.rng.gen::<u32>()`. clippy lint `disallowed_methods = ["rand::thread_rng", "rand::random"]` to enforce.
      - Cost avoided: ~300 ns per spurious thread_rng + entire determinism debt (one non-deterministic call invalidates W88 reproducer-by-seed contract).
      - Muscle: any deterministic-replay system has exactly ONE entropy source per scenario, owned, seeded from input. thread_rng, OsRng, SystemTime::now are banned. Reapplies at: W87 Tue assertions (must read SM deterministically), W87 Wed faults (coin-flips from same RNG), W88 runner (each worker's RNG seeded from master seed), W90 consensus-vsr VOPR (replica clocks driven by SimClock from same seed), W92 ledger v1.0 SHIP determinism gate.

    - **When `op_gen_account_pool_arrayvec_bounded` finds HashMap:**
      - Symptom: same seed produces different op stream across machines.
      - Why: `account_pool: HashMap<AccountId, ()>` for "easy contains-check", then `pool.iter().nth(rng.gen_range(0..pool.len()))` to pick debit. (a) HashMap iteration non-deterministic per startup; (b) iter().nth(N) is O(N) per pick at ~5 ns/bucket = 50 µs to pick from 10k pool (50× over 1 µs budget).
      - Fix: `account_pool: ArrayVec<AccountId, 10_000>`. Pick: `pool[rng.gen_range(0..pool.len())]` — O(1), cache-friendly (single L1 read), bit-deterministic. Membership-check (if needed) via separate bounded FixedMap (W89 Tue); for op_gen, indexed pick enough.
      - Cost avoided: ~50 µs/op pick → ~1 ns/op pick (50,000× win); plus determinism debt.
      - Muscle: in deterministic-replay code, all "set-like" structures are sorted vectors / ArrayVec / FixedMap with explicit hash seed; `std::collections::HashMap` and `ahash::AHashMap` are cargo-deny-banned. Reapplies at: W87 Tue assertion suite (iterating accounts), W89 Tue ledger AccountMap (FixedMap), W92 ledger v1.0 state_hash (sorted BTreeMap), W88 VOPR runner result aggregation (sorted-by-seed report).

  - **When `feed_handler_uses_try_claim_not_offer` reports allocator overhead:**
    - Symptom: bench shows 5M events/s ceiling regardless; profile shows malloc per event.
    - Why: `let buf = encode(&event); publication.offer(&buf);` allocates Vec per event (~50 ns malloc + 100 ns serialize + 30 ns memcpy + 10 ns drop = ~190 ns).
    - Fix: `let claim = publication.try_claim(size_of_event)?; encode_into(&mut claim.bytes_mut(), &event); claim.commit();` — encoding writes DIRECTLY into term-buffer slot. Zero allocation, zero intermediate copy.

Reapplies at: W90 io_uring journal write-fixed, W92 ledger Archive emission, W82 matching-engine MBO feed, W77 messaging-aeron publication itself.

  - **When `feed_handler_stats_use_relaxed_not_seqcst` reports SeqCst fence overhead:**
    - Symptom: ~10-15% throughput regression with no apparent cause; on ARM (Apple Silicon) the win is larger because `dmb ish` is heavier than x86 `mfence`.
    - Why: `stats.recv_packets.fetch_add(1, SeqCst)` because "SeqCst is safe". Each SeqCst op on x86_64 inserts `mfence` (~10-25 ns); on ARM64 `dmb ish` (~15-30 ns). At 5M events × 4-5 stats × ~20 ns = 400-500 ms/sec fence overhead.
    - Fix: `Ordering::Relaxed` for monotonic counters (recv_packets, parsed_events, filter_dropped, publish_failures); they are observability-only, do not synchronize with other data. `last_ts_ns` also Relaxed (liveness watchdog tolerates ms staleness). Reserve Acquire/Release for actual synchronization. Reserve SeqCst for rare total-ordering cases.
    - Cost avoided: ~15-25 ns/atomic × 25M ops/s = ~400 ms/sec reclaimed.
    - Muscle: every atomic op has memory-ordering choice; default-to-SeqCst is the single most common bar-(c) violation in well-meaning code. Reserve SeqCst for ops needing ordering across multiple atomics; use Relaxed for monotonic counters + observability. Reapplies at: W74 matching-engine sequence counter, W77 messaging-aeron term-buffer indices (Acquire/Release pair, not SeqCst), W92 ledger state-hash gossip counter, W82 MBO feed sequence number, W89 message-pool in-flight counter.

      - R4. JournalOrdering: journal seq strictly monotonic + every replay returns same seq sequence.

      - D4. **Pre-mortem (false-positive on legitimate two-phase transfer):** pending Transfer not yet posted; DoubleEntrySumZero fails. Invariant operates on POSTED only; pending lives in separate counter.
      - D5. **Pre-mortem (race in concurrent assertion):** assertion reads SM while next op partially applied. Assertions only run between apply() calls; SM apply atomic.
      - D6. **Pre-mortem (wrap-around invisibility):** balance wraps u64; sum still equals zero; NoOverflow doesn't see it. NoOverflow checks `checked_add` not `wrapping_add`.
