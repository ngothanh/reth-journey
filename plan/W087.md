- [NEW v2] **ledger VOPR: random op stream + assertion engine (part 1)**
  - [ ] **Build**: `crates/ledger-deterministic/src/vopr/op_gen.rs` — random ops: 70% Transfer, 20% Lookup, 10% CreateAccount. Seeded RNG for reproducibility. (~2 hrs)
    - **Why**: VOPR (Viewstamped Operation Replication-style simulator) is TigerBeetle's marquee bug-finding tool. The op-stream generator is the engine of the whole simulator: it produces realistic-but-adversarial workloads that exercise every code path. 70/20/10 mix mirrors a real ledger's hot loop (lookups + transfers dominate, account creation rare). Seeded RNG means a failure is reproducible exactly, which is the whole point.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/vopr.zig` — esp. `step()` and the workload generation; `lib/tigerbeetle/src/workload.zig`.
    - **Design**:
      ```rust
      pub struct OpGen {
          rng: SmallRng,                    // seeded SplitMix → SmallRng
          account_pool: ArrayVec<AccountId, 10_000>,
          op_count: u64,
          weights: OpWeights,
      }
      pub struct OpWeights { transfer: u8, lookup: u8, create: u8 } // sums to 100
      impl OpGen {
          pub fn new(seed: u64) -> Self;
          pub fn next_op(&mut self) -> ClientOp;
          pub fn seed(&self) -> u64;
      }
      pub enum ClientOp {
          CreateAccount { id: AccountId, ledger: u16, code: u16, /*...*/ },
          Transfer { id: TransferId, debit: AccountId, credit: AccountId, amount: u64, ledger: u16 },
          Lookup { id: AccountId },
      }
      ```
      **Invariants**: (i) given seed S, the entire op stream is byte-identical across runs (no system_time, no thread_rng), (ii) Transfer always picks debit ≠ credit from `account_pool`, (iii) CreateAccount appends to `account_pool` so future Transfers have valid targets, (iv) op_count monotonic — used as TransferId.
    - **Build steps**: 1. (~10 min) module skeleton `vopr/mod.rs` re-exporting op_gen + assertions + faults. 2. (~10 min) `OpGen::new(seed)` using `SmallRng::seed_from_u64(seed)`. 3. (~20 min) weighted dispatch: roll u8, branch on weights cumulative buckets — manual, no `rand_distr` to avoid alloc. 4. (~20 min) realistic Transfer: pick debit from `account_pool` uniform, credit different from debit; amount = 1 + rng.gen::<u32>() & 0xFFFF (small to avoid quick overflow). 5. (~10 min) realistic CreateAccount: ID = next monotonic, ledger/code/timestamp from rng but bounded. 6. (~15 min) edge-case generator (toggleable): empty Transfer (amount=0), self-transfer (rejected at SM layer), max-amount (u64::MAX/2 to test overflow guards). 7. (~10 min) "burst" workload mode: 99% Transfer 1% other for stress; mode field on OpGen. 8. (~10 min) export op-stream-to-file utility for golden-replay diffing. 9. (~15 min) tests: `op_gen(42).take(10000) == op_gen(42).take(10000)` byte-identical; weights converge to 70/20/10 ±1% over 1M ops.
    - **Pitfalls**: *Non-seeded inner RNG*: **Symptom**: even with `seed` param, op stream differs because `account_pool` shuffles via `thread_rng()`. **Fix**: ban `thread_rng`, all randomness via the single `SmallRng`. *Account-pool exhaustion*: **Symptom**: after 10k creates, can't grow further, Transfer keeps re-picking same pairs. **Fix**: `ArrayVec<_, 10_000>` is a hard cap; document that as the simulator's account scale; raise to 100k if scenarios need more. *Float in op generation*: **Symptom**: floats introduce platform variance (x86 vs ARM rounding). **Fix**: bias toward Bernoulli/uniform integer; no floats anywhere. *Empty pool early*: **Symptom**: first ops are Transfer but pool is empty. **Fix**: prime with N CreateAccount ops before generation, OR weight CreateAccount=100% until pool ≥ 100.
    - **Test scenarios**: 1M ops at seed 42 — re-run, byte-identical; weight assertion (~70/20/10); long run (10M ops, seed 1..100) — no panics, no underflow. Property: replay by seed never diverges.
    - **Acceptance**: op_gen produces 1M ops/s on M2; identical streams under same seed; CI-bot can re-run a failed scenario from seed printed in log.
    - **Downstream**: assertions (Tuesday) check invariants after each op; faults (Wednesday) inject between ops; runner (W88) drives this in parallel across 100 scenarios.

- [ ] **Build**: `crates/marketdata-kernelbypass/src/feed_handler.rs` — `FeedHandler<P: FeedParser, T: Transport>` glues
  receiver → parse → emit. Emit goes through `messaging-aeron::Publication`. (~105 min)
  - **Why**: feed_handler is the integration point that makes marketdata useful. The Transport (W85-W86) provides raw bytes; the FeedParser (W86 Sat) decodes them; the FeedHandler decides per-message what to do with the event (filter, transform, fan-out) and emits to messaging-aeron::Publication so matching-engine and ledger can subscribe. This is the W87 keystone: with this committed, marketdata is end-to-end and ready for v0.5 SHIP (W90 Tue).
  - **Read first**: Aeron `aeron-archiver` agent loop, `crates/messaging-aeron/src/publication.rs` (your own W67-82 work), Onload's `ef_vi` event-handler pattern.
  - **Design**:
    ```rust
    pub struct FeedHandler<T: Transport, P: FeedParser, F: Filter> {
        transport: T,
        parser: P,
        filter: F,
        publication: messaging_aeron::Publication,
        scratch: ArrayVec<u8, MAX_FRAME>,
        stats: FeedStats,
    }
    pub trait Filter: Send {
        fn keep<E>(&self, ev: &E) -> bool;
    }
    impl<T, P, F> FeedHandler<T, P, F> {
        pub fn run_once(&mut self) -> Result<usize, FeedErr> { /* recv → parse → emit */ }
    }
    pub struct FeedStats {
        recv_packets: u64,
        parsed_events: u64,
        filter_dropped: u64,
        publish_failures: u64,
        last_ts_ns: u64,
    }
    ```
    **Invariants**: (i) one-pass over input bytes: no buffering between parse and publish, (ii) `Publication::offer` failures are NOT swallowed — backpressure surfaces upward, (iii) filter is the only place where events can be dropped — losses tracked, (iv) `last_ts_ns` monotonic for liveness watchdog.
  - **Build steps**: 1. (~10 min) struct + constructor with `with_filter` / `default_filter()`. 2. (~20 min) `run_once()` body: call `transport.recv_batch()`, for each raw frame call `parser.parse()` in a loop until `bytes_consumed == frame.len()`, for each event check `filter.keep()`, encode + publish via `publication.offer()`. 3. (~10 min) handle publication.offer() backpressure: on `BackPressured` increment stat + return; on `Closed` propagate error. 4. (~10 min) wire FeedStats updates inline (atomics for cross-thread read). 5. (~15 min) ergonomic constructor: `FeedHandler::<EpollTransport, ItchParser, AllowAll>::new(addr, pub)`. 6. (~10 min) drive-loop helper `run_forever(deadline)` that calls run_once() in tight loop until deadline. 7. (~10 min) liveness watchdog: separate thread checks `last_ts_ns` updated within 1s, panic-traces if stale. 8. (~10 min) feature-gate the Linux-only transports. 9. (~10 min) tests: synthetic feed → assert published events on a `Subscription`.
  - **Pitfalls**: *Backpressure cascade*: **Symptom**: publication slows, frames queue up in NIC ring, NIC drops, you blame the wrong layer. **Fix**: monitor publication backpressure stat AND NIC drop counter; alert correlates both. *Filter side-effect*: **Symptom**: `Filter` impl computes hashes, blowing latency budget. **Fix**: trait contract says filter MUST be pure + O(1). *Encode-then-copy*: **Symptom**: encoding event into publish buffer copies bytes twice. **Fix**: `publication.try_claim(N)` returns a writable slice; encode directly into it. *Parser state bleeding across run_once*: **Symptom**: edge case where parser keeps half-message state across calls. **Fix**: bounded the parser to consume only on FULL message; partial means wait for next batch.
  - **Test scenarios**: synthetic ITCH generator → FeedHandler with publication → Subscription on another thread → assert event count matches. Inject backpressure (subscriber pauses) → publish_failures increments; resume → stats normalize. Inject parse error mid-stream → FeedHandler logs + skips, continues. Liveness watchdog fires if transport stalls.
  - **Acceptance**: 5M ITCH events/s through (epoll → ItchParser → publication) on M2 Pro Linux; subscriber receives 5M/s with zero gaps; stats exported via metrics crate.
  - **Downstream**: W90 Tue tag marketdata v0.5; W90 Wed integration test feeds matching-engine; later subscriptions on consensus-vsr (for replicated audit log).

- [NEW v2] **ledger VOPR: assertion engine (part 2)**
  - [ ] **Build**: `crates/ledger-deterministic/src/vopr/assertions.rs` — invariant checks: double-entry sum = 0, no neg balance, no overflow, journal ordering. (~3 hrs)
    - **Why**: VOPR's value is *not* random op generation alone — it's the assertion engine that turns "did it crash?" into "are invariants violated?". A bug can produce non-crashing wrong-state, which only assertion checks catch. Mirror TigerBeetle's `verify_account_balances()` invariant suite. These four invariants are the minimum: anything more nuanced (rate-limits, ledger ratios) can layer later.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/state_machine.zig` `verify_*` helpers; `lib/tigerbeetle/src/vopr.zig` step's assertion checks; double-entry accounting axioms.
    - **Design**:
      ```rust
      pub trait Invariant: Send {
          fn check(&self, sm: &LedgerSM, history: &OpHistory) -> Result<(), InvariantViolation>;
          fn name(&self) -> &'static str;
      }
      pub struct DoubleEntrySumZero;
      pub struct NoNegativeBalance;
      pub struct NoOverflow;
      pub struct JournalOrdering;
      pub struct AssertionRunner {
          invariants: Vec<Box<dyn Invariant>>,
          violation_log: Vec<InvariantViolation>,
      }
      pub struct InvariantViolation { pub name: &'static str, pub op_index: u64, pub detail: String }
      ```
      **Invariants checked**: (1) DoubleEntrySumZero: for the set of Transfer operations applied, `Σ debits == Σ credits` modulo `u64` wrap; (2) NoNegativeBalance: every Account.debit_amount ≤ Account.credit_amount + flags.credits_must_not_exceed_debits-rule-flipped; (3) NoOverflow: no Account balance saturated to MAX during the op stream (would silently lose data); (4) JournalOrdering: journal seq strictly monotonic + every replay-read returns same seq sequence.
    - **Build steps**: 1. (~10 min) module skeleton + `Invariant` trait. 2. (~25 min) `DoubleEntrySumZero` — iterate accounts, sum `debits - credits`, assert zero (accounting truism). Edge: pending vs posted distinction. 3. (~25 min) `NoNegativeBalance` — per account, given `flags`, derive max-allowed and check. 4. (~25 min) `NoOverflow` — track per-op deltas, check no `checked_add` would have returned None even if real op used `wrapping_add`. 5. (~25 min) `JournalOrdering` — open journal, iterate, assert seq strictly increases by 1; replay against a clone SM, assert state_hash equals. 6. (~20 min) `AssertionRunner::run_all` after each batch of N ops, collect violations. 7. (~15 min) cheap (every-op) vs expensive (every-N-op) invariant tiers — DoubleEntrySumZero is O(accounts), run every 1000 ops; NoNegativeBalance is O(1) per-op, run every-op. 8. (~10 min) human-readable violation report formatter (used by W88 runner).
    - **Pitfalls**: *False-positive on legitimate two-phase transfer*: **Symptom**: pending Transfer not yet posted; DoubleEntrySumZero fails. **Fix**: invariant operates on POSTED transfers only; pending lives in a separate counter that nets to zero. *Race in concurrent assertion*: **Symptom**: assertion reads SM while next op partially applied. **Fix**: assertions only run between apply() calls; SM apply is atomic. *Wrap-around invisibility*: **Symptom**: balance wraps u64, sum still equals zero, NoOverflow doesn't see it. **Fix**: NoOverflow checks `checked_add` not `wrapping_add` — separate guard from balance check. *Journal replay clobbers state hash*: **Symptom**: replay-clone SM differs because cloned SM allocator state differs. **Fix**: state_hash is canonical (sorted, allocator-independent).
    - **Test scenarios**: inject buggy `apply` that subtracts from debit but skips credit — DoubleEntrySumZero catches it within 1000 ops. Inject `wrapping_sub` on balance — NoNegativeBalance catches at first underflow. Reorder journal seq → JournalOrdering catches. Performance: assertion suite adds <5% wall-time when run every 1000 ops.
    - **Acceptance**: each invariant has a unit test that breaks it with a known-bad apply impl and confirms detection.
    - **Downstream**: W88 VOPR runner runs assertions after each scenario; consensus-vsr v1.0 VOPR (W88 Fri) reuses the trait with additional VSR invariants (quorum-stability, view monotonic).

- [NEW v2] **ledger VOPR: fault injection (part 1)**
  - [ ] **Build**: `crates/ledger-deterministic/src/vopr/faults.rs` — inject: network partition (drop msgs), message reorder (shuffle in-flight), crash restart (snapshot + reload), slow disk (artificial latency). (~3 hrs)
    - **Why**: ops + assertions catch logic bugs in a fault-free environment. Faults are where VOPR earns its reputation: most ledger bugs only manifest under correlated faults (partition + restart + reorder simultaneously). Mirror TigerBeetle's `simulator.zig` fault injection — they catch real, production bugs this way.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/simulator.zig` — esp. partition logic, the `network.zig` and `storage.zig` fault paths; Jepsen Maelstrom for protocol-fault model reference.
    - **Design**:
      ```rust
      pub trait Fault: Send {
          fn pre_op(&mut self, rng: &mut SmallRng, ctx: &mut SimCtx) -> FaultEffect;
          fn name(&self) -> &'static str;
      }
      pub enum FaultEffect { None, DropMessage, ReorderInflight, CrashRestart, DiskLatencyMs(u32) }
      pub struct NetworkPartition { drop_prob: f32 }
      pub struct MessageReorder { shuffle_buffer_size: usize }
      pub struct CrashRestart { mean_uptime_ops: u64 }
      pub struct SlowDisk { latency_p50_us: u32, latency_p99_us: u32 }
      pub struct FaultBudget { total: u32, per_kind: FxHashMap<&'static str, u32> }
      ```
      **Invariants**: (i) all faults seeded from same RNG as op_gen so reproducible, (ii) "fault budget" prevents the simulator from being all faults all the time — at most 1 fault per N ops, (iii) crash-restart preserves journal but invalidates in-memory state, (iv) faults compose: NetworkPartition + SlowDisk + CrashRestart can all be active concurrently.
    - **Build steps**: 1. (~10 min) `Fault` trait + `SimCtx` carrying refs to network sim + storage sim. 2. (~30 min) `NetworkPartition` — drop_prob × rng → drop message; supports partial partitions (drop only from set A to set B). 3. (~30 min) `MessageReorder` — buffer N in-flight messages, swap two random indices on each step. 4. (~40 min) `CrashRestart` — sample uptime ops geometrically, on trigger: snapshot SM via `snapshot()` write, then drop SM, recreate via `restore()`+journal replay; verify replay seq matches pre-crash. 5. (~30 min) `SlowDisk` — wrap journal writes with `tokio::time::sleep` (or simulator's clock advance); use log-normal sample for latency. 6. (~15 min) FaultBudget bookkeeping — increment per kind, hard cap. 7. (~15 min) docs on fault correlation: which combinations are "interesting" vs "physical impossibility".
    - **Pitfalls**: *Fault correlation explosion*: **Symptom**: NetworkPartition + CrashRestart + SlowDisk + Reorder all active → 99% of scenarios time out, 0 useful coverage. **Fix**: fault budget per scenario (≤3 active faults); document the matrix in a scenario YAML. *CrashRestart with hot data*: **Symptom**: snapshot mid-Transfer, restore sees inconsistent state. **Fix**: snapshot only at op boundaries (between apply calls). *SlowDisk causing scenario timeout*: **Symptom**: SlowDisk p99 = 100ms × 1M ops = 100k seconds. **Fix**: simulator clock is virtual — sleep advances virtual clock, not wall clock; cap virtual scenario duration. *Reorder without bound*: **Symptom**: reorder buffer grows unbounded, OOM. **Fix**: hard cap reorder buffer size; FIFO eviction.
    - **Test scenarios**: each fault individually with assertion suite — no false invariant violations under fault. Combined: NetworkPartition (10% drop) + CrashRestart (every 10k ops) + SlowDisk (p99 1ms) for 1M ops → all assertions pass. Specific bug regression: introduce a deliberate "lose-the-credit-on-crash" bug → CrashRestart + DoubleEntrySumZero catches it.
    - **Acceptance**: each fault type has a unit test demonstrating effect; runs 100 scenarios with random fault mix without false positives.
    - **Downstream**: W88 VOPR runner orchestrates scenarios with fault mixes; consensus-vsr VOPR adds NetworkPartition with quorum-bisection mode.
