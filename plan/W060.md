- [ ] Inline stack ops. While you're in the stack code, evaluate whether U256 push/pop or copy paths can benefit from

  `EXEC_VM_PERF_BACKLOG.md` for SIMD experimentation in W64. (~30 min)
  - **Why (hot path optimization technique)**: Stack ops are the highest-frequency operations in EVM execution (every opcode pushes/pops). Even 1ns savings per op × millions of ops = noticeable wall-clock. Inlining stack ops + branch hints can yield 5-10% on arith-heavy workloads.
  - **Design** (techniques to apply):
    ```rust
    // Cache-line layout: Stack uses Box<[U256; 1024]> aligned to 64-byte cache line.
    #[repr(align(64))]
    pub struct Stack {
        data: [U256; 1024],   // 32KB; resident in L1d at moderate depth
        len: usize,
    }

    #[inline(always)]
    pub fn push_unchecked(&mut self, value: U256) {
        unsafe { *self.data.get_unchecked_mut(self.len) = value; }
        self.len += 1;
    }

    #[inline(always)]
    pub fn push(&mut self, value: U256) -> Result<(), StackOverflow> {
        if unlikely(self.len >= 1024) { return Err(StackOverflow); }
        unsafe { *self.data.get_unchecked_mut(self.len) = value; }
        self.len += 1;
        Ok(())
    }
    ```
    **Invariants**:
    - Stack capacity hardcoded 1024 (EVM spec). Compile-time constant.
    - `len` always ≤ 1024.
    - `push_unchecked` only used when bounds proven by caller (e.g., immediately after pop2).
    - Branch hints: overflow path is `#[cold]`; happy path has no branch in best case.
  - **Build steps**:
    1. (~10 min) Add `#[repr(align(64))]` and verify stack fits in L1d (32KB).
    2. (~10 min) Add `#[inline(always)]` on push/pop/peek hot fns; verify via LLVM IR they actually inline (cargo rustc -- --emit=llvm-ir).
    3. (~5 min) Add `#[cold]` on error-return branches; use `std::hint::unlikely`.
    4. (~5 min) SIMD candidate noted in EXEC_VM_PERF_BACKLOG.md: MCOPY 32-byte aligned copies via `_mm256_loadu_si256`/`_mm256_storeu_si256`. Defer impl to W64.
  - **Pitfalls**:
    - *`#[inline(always)]` ignored*: LLVM may refuse if function too large. **Symptom**: zero perf gain. **Fix**: ensure fn body small (< 20 IR instructions); inspect LLVM IR.
    - *Stack alignment loss after Box::new*: heap allocator returns aligned-but-not-cache-aligned memory. **Fix**: explicit `#[repr(align(64))]` on struct guarantees field alignment regardless of allocator.
    - *Bounds-check elision lost*: `get_unchecked` requires `unsafe`; reviewers nervous. **Fix**: encapsulate in a single `Stack::push_unchecked(&mut self, v)` method with safety comment and a debug_assert.
  - **Acceptance**: arith_heavy bench improves ≥ 5%; SIMD candidate noted for W64.

- [ ] [HFT] **Build**: `crates/matching-engine/src/book.rs` —
  `OrderBook { bids: BTreeMap<Price, PriceLevel>, asks: BTreeMap<Price, PriceLevel> }`.
  `PriceLevel { orders: VecDeque<Order> }` for FIFO/price-time priority. (~150 min)
  - **Why (MAX DETAIL — matching-engine internals)**: This is HFT's core data structure. The book IS the matching engine. Every nanosecond here multiplies by millions of orders per second. The choice of BTreeMap (RB-tree) vs skip list vs sorted-array is debated; for v0.5 single-symbol, BTreeMap wins on simplicity and bench. LMAX Disruptor-style intrusive freelist will be added in W74+ when we go for sub-µs.
  - *Back-of-envelope*: v0.5 single-symbol target — **1 M orders/sec on one core; P99 matching latency ≤ 10 µs** (v1.0 W74 tightens to ≤ 5 µs, v1.5 to ≤ 1 µs). At 1 M ops/sec the budget is 1000 ns/order. Decompose: best-bid/ask peek = O(1) cached (~5 ns L1 load); BTreeMap `entry(price)` = ~50-100 ns (3-7 hops × ~7 ns L2, since price levels are pointer-chased and largely cache-cold) ← **this is the killer**; `VecDeque::push_back` of an `Order` = ~10 ns (assuming pre-reserved capacity); `order_index.insert` (AHashMap) = ~30-50 ns ← **the other killer**; recompute best_bid via `bids.keys().next_back()` = ~50 ns. Total cold-path: ~150-250 ns per add_limit_order — feasible BUT every allocation (BTreeMap node insert on new price level, AHashMap rehash) pushes into the µs regime. Cache-line analysis: `PriceLevel` carries `VecDeque<Order>` (24 B header + heap pointer) + `total_qty` (8 B) = 32 B — fits in half a cache line. `Order` itself is 88 B (~1.4 cache lines) — straddles. **Static-mem invariant for v1.0**: pre-allocate an `Order` slab + intrusive list nodes; replace `BTreeMap<Price, PriceLevel>` with an arena-backed skip list (W37 muscle) keyed on the integer price. **Float ban**: any `f64` arithmetic here (e.g., price-to-tick conversion) breaks determinism for VOPR replay AND for raft replication AND for cross-machine consensus — `Price` is `i64` fixed-point, full stop. **Best-bid/ask publishing**: cached `best_bid`/`best_ask` fields must be published via SeqLock (W4 `ChainHead` muscle) so the market-data shard and risk shard can read without coordinating with the writer — a `Mutex` here would add ~25 ns uncontended and µs+ contended on every read.
  - **Read first**: LMAX Disruptor whitepaper (Thompson et al.); TigerBeetle's `src/state_machine.zig` for deterministic event log; QuickFIX's order book; "Implementing High-Performance Matching Engines" (Bookstaber-style talk).
  - **Design**:
    ```rust
    pub struct OrderBook {
        pub symbol: Symbol,
        pub bids: BTreeMap<Price, PriceLevel>,  // ascending order; iterate `.rev()` for best bid first
        pub asks: BTreeMap<Price, PriceLevel>,  // ascending; iterate forward for best ask first
        pub order_index: AHashMap<OrderId, OrderRef>, // O(1) cancel lookup
        pub best_bid: Option<Price>,            // cached, recomputed on level change
        pub best_ask: Option<Price>,
        pub seq: u64,
    }

    pub struct PriceLevel {
        pub orders: VecDeque<Order>,            // FIFO time-priority
        pub total_qty: Qty,                     // cached sum; updated on add/cancel/fill
    }

    pub struct Order {
        pub id: OrderId,
        pub side: Side,
        pub price: Price,
        pub qty: Qty,
        pub remaining: Qty,
        pub ts: Monotonic,                       // arrival ts for tie-breaking (same price level FIFO)
        pub owner: AccountId,
        pub kind: OrderKind,                     // Limit, Market, IOC, FOK, PostOnly
    }

    pub struct OrderRef {
        pub price: Price,
        pub side: Side,
    }
    ```
    **Invariants**:
    - bids: best-bid = `bids.keys().next_back()`. asks: best-ask = `asks.keys().next()`.
    - Within PriceLevel: orders FIFO ordered (oldest first); fills consume from front.
    - `order_index` keys = currently-open orders only. Removed on full-fill or cancel.
    - `total_qty` of PriceLevel = sum of `order.remaining` for that level.
    - Sequence number `seq` monotonic; emitted on every event.
    - No order with `remaining == 0` exists in book (removed on full fill).
  - **Build steps** (granular):
    1. (~20 min) Cargo deps: `ahash` for FastHashMap, `parking_lot` for any internal locks (avoid in v0.5; single-writer).
    2. (~25 min) `OrderBook::new(symbol)`.
    3. (~30 min) `add_limit_order(order)`: lookup level (BTreeMap::entry), push to VecDeque, update order_index, recompute best_bid/best_ask if needed.
    4. (~30 min) `cancel(id) -> Result<CancelledOrder, NotFound>`: order_index lookup → BTreeMap entry → VecDeque scan + remove. PriceLevel becomes empty → remove from BTreeMap → recompute best.
    5. (~25 min) `peek_best_bid_ask() -> (Option<Price>, Option<Price>)`: O(1) via cached fields.
    6. (~15 min) Sanity tests: add 1000 orders, randomly cancel 500, verify book size = 500.
    7. (~5 min) Note for W74+: intrusive linked list (rather than VecDeque) eliminates O(level_size) scan on cancel; LMAX Disruptor-style ring buffer for event log.
  - **Pitfalls** (named, latency-critical):
    - *VecDeque cancel O(n)*: cancelling order at position 100 in level of 1000 is O(1000). **Symptom**: tail latency on cancel-heavy workloads. **Fix v0.5**: small price-levels (typical < 20 orders) keep this acceptable. **Fix v1**: intrusive doubly-linked list with stable position pointers (W74).
    - *BTreeMap allocator pressure*: std BTreeMap allocates per-node; under sustained insert/remove churn, allocator overhead dominates. **Symptom**: GC-like pauses (actually allocator pauses). **Fix v0.5**: tolerate; **fix v1**: arena allocator OR skip list with custom allocator (W74).
    - *Cached best_bid stale*: forgetting to recompute after level-becomes-empty leaves stale best_bid. **Symptom**: market orders fail to find liquidity. **Fix**: on level removal, recompute via `bids.keys().next_back()`.
    - *Order with remaining=0 in book*: fill-then-don't-remove leaves zombie. **Symptom**: ghost matching. **Fix**: post-fill, if remaining==0, remove from VecDeque AND order_index.
    - *Cross orders (post-only that would cross)*: PostOnly limit order at bid 100 when ask=99 must REJECT, not cross. **Symptom**: taker fees instead of maker. **Fix**: PostOnly check before insert.
  - **Test scenarios**:
    - 1000 random orders → no cross (book remains consistent: best_bid < best_ask).
    - Add then cancel: book empty.
    - Add 100 at price 100, fill 50 → level has 50 remaining (qty-wise), 1 order if all from same order or N orders shrunk by total 50.
    - PostOnly that would cross → reject; book unchanged.
  - **Expect to hit (perf) #1 — `BTreeMap<Price, PriceLevel>` allocates a tree node per new price level (bar (c) violation)**: every time an order arrives at a price not currently in the book, `bids.entry(price).or_insert_with(...)` calls `std::alloc::alloc` for a fresh BTreeMap node (~40-80 B node + ~50 ns alloc + ~7 ns parent-cache-line miss). In active markets, price levels churn — new highs/lows every second — so this allocator visit recurs ~100-1000/sec/symbol. Worse, BTreeMap *deallocates* on level removal (when the last order at a price cancels or fills), so allocator state oscillates → fragmentation → eventual ~5 µs p99 spike when the allocator does a thread-cache rebalance. Symptom: criterion bench shows otherwise-clean p50 ~500 ns with p99 spiking to 3-10 µs; flame graph shows `alloc::alloc`/`alloc::dealloc` in the matching path.
    - Fix v0.5: pre-warm BTreeMap with ~1000 placeholder price levels spanning the expected market range at boot (allocate them once, never free); on level becoming empty, *retain* the entry as an empty `PriceLevel` (so the BTreeMap node stays allocated). Fix v1.0 (W74): replace with a custom arena-backed skip list — node allocator is a per-shard `slab::Slab<SkipListNode>` (~10 ns reserve, zero global allocator), and freed nodes return to the slab for reuse. The skip list is also cache-friendlier than BTreeMap for narrow spreads (top-of-book skip list nodes stay hot in L1; BTreeMap walks a tree that touches cold internal nodes).
    - Cost avoided: ~50 ns allocator + ~50 ns dealloc per level transition = ~100 ns × ~500/sec churn = ~50 µs/sec saved (small) BUT eliminates the ~5 µs p99 spike (huge for the bar — p99 is the *whole* metric for HFT). Memory cost: ~1000 pre-warmed levels × ~80 B = ~80 KiB per symbol; for 100 symbols = ~8 MiB, fits in L3.
    - Muscle: structures on the bar-(c) hot path must never visit the global allocator after warm-up — pre-allocate, pre-warm, or arena. The price-level map is one of three Layer-5 places this lesson applies (the others are W74 `concurrent::SkipMap` price level, W83 ledger account map). Reapplies at: W74 lock-free price level, W77 aeron term-buffer rotation, W83 ledger `AccountId → Account` cache.
  - **Expect to hit (perf) #2 — `VecDeque<Order>` clones Order (88 B) on cancel-mid-level (bar (c) violation)**: cancel walks the level's `VecDeque` looking for the matching `OrderId`, then `remove(pos)` shifts the tail. For a level of 20 orders × 88 B = 1.7 KiB, the worst-case shift is ~1.7 KiB memmove (~50 ns) plus the linear scan (~5 ns × 20 = 100 ns). Symptom: cancel p99 on deep levels can exceed 1 µs — acceptable at v0.5 (per acceptance: "small levels < 20") but a cliff if any level ever exceeds 50 orders.
    - Fix v0.5: VecDeque is acceptable but verify the typical level depth via a production-shape replay (e.g., BitMEX trade tape). Document the < 20-order assumption and add a debug assertion. Fix v1.0 (W74): replace `VecDeque<Order>` with an intrusive doubly-linked list — `Order` carries `prev: NodeRef, next: NodeRef`; `OrderRef` in `order_index` holds the `NodeRef`; cancel is `O(1)` (unlink + return to slab) with no memmove. The intrusive design comes "free" from the W74 arena-backed slab.
    - Cost avoided: ~100-200 ns cancel scan + ~50 ns memmove → ~30 ns unlink; eliminates the per-cancel cache thrash from shifting 1.7 KiB of order bodies; brings cancel p99 from ~1 µs to ≤ 100 ns.
    - Muscle: any "delete by ID" on a hot path must be O(1) — index points directly to the in-structure node, not to a position-by-index. Same pattern is in linux kernel `list_del`, intrusive containers in Boost, and the W26 wal segment free-list. Reapplies at: W74 matching-engine intrusive level list, W76 aeron Publication state intrusive list, W83 ledger pending-transfers list.
  - **Acceptance**: 1M orders/sec single-symbol throughput on one core; cancel p99 < 1 µs (small levels); **steady-state allocator-rate ≤ 100 allocs/sec** (verified via `dhat`/`heaptrack` on a 1M-order run); criterion bench-diff confirms BTreeMap pre-warm eliminated allocator-spike tail.

- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/det_test.rs` — single-thread executor with injected clock, deterministic submit_to ordering. Enables matching-engine deterministic test. (~150 min)
  - **Why (MAX DETAIL)**: Deterministic execution is the magic ingredient for testing distributed/concurrent systems. TigerBeetle, FoundationDB, Aurora all use deterministic simulation. The same test seed produces the SAME run every time → reproducible bug reports, true bisection. For runtime-thread-per-core, this means: single-thread executor with injected clock + deterministic cross_shard ordering.
  - *Back-of-envelope*: this is the **VOPR substrate** — the same harness must drive ledger-deterministic's 10 M scenarios by M30. Target: ≥ 10k simulated ops/sec on a single test thread (slow is fine because we run it offline; but too slow = days-long CI). Each simulated op = ~1 step of clock advance + ~1 task dispatch (~500 ns); 10k/sec means ~100 µs/op — generous. **Critical: bit-identical replay across runs.** A single non-deterministic source (HashMap iteration order, `Instant::now()`, allocator pointer hash) breaks replay and breaks the entire VOPR investment. Bar (c) here is not "fast" — it's "reproducible to the bit, every run, every machine, every kernel". This means the data structures must be `BTreeMap`/`IndexMap`/`Vec`, NOT `HashMap`/`HashSet`; the RNG must be a seeded `ChaCha8Rng` not `thread_rng()`; the IO backend must be a `MockUring` that records SQE intents and injects completions at scheduled clock ticks (no real syscalls). The W92 VOPR (ledger) extends this with fault injection (network partition, message reorder, crash-restart) — but the determinism foundation is here.
  - **Read first**: FoundationDB's "Flow" simulation framework; TigerBeetle's `src/test/cluster.zig`; sled's `Db::tree::tests::stress`.
  - **Design**:
    ```rust
    pub struct DetExecutor {
        ready: BTreeMap<DetClock, VecDeque<TaskBox>>,  // ordered by virtual time
        cross_shard: HashMap<(ShardId, ShardId), VecDeque<TaskBox>>,
        clock: DetClock,
        shard_count: usize,
        shard_state: HashMap<ShardId, ShardLocalState>,
        rng: rand_chacha::ChaCha8Rng,
    }
    pub struct DetClock(pub u64);  // virtual nanoseconds

    impl DetExecutor {
        pub fn new(seed: u64, shard_count: usize) -> Self { ... }

        pub fn submit_to(&mut self, _from: ShardId, to: ShardId, task: TaskBox) {
            self.cross_shard.entry((_from, to)).or_default().push_back(task);
        }

        pub fn drain_cross_shard_to_ready(&mut self) {
            // Drain cross_shard inboxes in deterministic order: sort by (from, to);
            // for each pair, drain in FIFO order; assign each task a virtual deadline of clock + 1 ns.
            let mut keys: Vec<_> = self.cross_shard.keys().copied().collect();
            keys.sort();
            for k in keys {
                while let Some(t) = self.cross_shard.get_mut(&k).and_then(|q| q.pop_front()) {
                    self.ready.entry(DetClock(self.clock.0 + 1)).or_default().push_back(t);
                }
            }
        }

        pub fn step(&mut self) -> bool {
            self.drain_cross_shard_to_ready();
            let Some((&clk, _)) = self.ready.iter().next() else { return false };
            self.clock = clk;
            let mut q = self.ready.remove(&clk).unwrap();
            for t in q.drain(..) { (t.task)(); }
            true
        }

        pub fn run_until_idle(&mut self) {
            while self.step() {}
        }
    }
    ```
    **Invariants**:
    - Single-threaded; no real concurrency.
    - Clock advances ONLY when `ready` empties at current time.
    - cross_shard drain order is DETERMINISTIC (sorted keys, FIFO within pair).
    - RNG seeded; all random decisions reproducible.
    - No real I/O: timers, sockets, files all mocked.
  - **Build steps** (granular):
    1. (~25 min) DetExecutor struct + DetClock with `BTreeMap<DetClock, VecDeque<TaskBox>>` runqueue.
    2. (~30 min) `submit_to`, `submit_local`, `delay_until(clock)` methods.
    3. (~30 min) `drain_cross_shard_to_ready` with deterministic sort.
    4. (~25 min) `step()` and `run_until_idle()`.
    5. (~20 min) Mock IO backend: `MockUring` records SQE intents; completions injected at scheduled clock.
    6. (~20 min) Bridge to matching-engine: matching tests run on DetExecutor → byte-exact event log across runs.
  - **Pitfalls** (named):
    - *Hidden randomness via HashMap iteration order*: Rust's std HashMap iteration order is random per-run. **Symptom**: same seed produces different output. **Fix**: use `BTreeMap` OR `indexmap::IndexMap` everywhere on the runtime path.
    - *Real-time leak*: `std::time::Instant::now()` slips into runtime code via dep. **Symptom**: clock un-injectable. **Fix**: ALL time access goes through executor's clock; lint via grep for `Instant::now`.
    - *Real I/O leak*: `tokio::fs::write` slips in. **Symptom**: real disk write. **Fix**: mock backend at trait boundary; runtime trait `IoBackend` makes real-vs-mock pluggable.
    - *Allocator non-determinism*: allocator returns different pointers each run; if hashmaps key on pointer, non-deterministic iter. **Symptom**: rare. **Fix**: key only on values, never pointers.
  - **Test scenarios**:
    - Same-seed runs: hash final state → identical across 100 runs.
    - Different seeds: verify variation (sanity that seeding actually changes behavior).
    - Cross-shard ordering: 8 shards each submit 100 to shard 0; verify shard 0 receives in lex order of source-shard.
  - **Expect to hit (perf) #1 — `BTreeMap<DetClock, VecDeque<TaskBox>>` allocates per-clock-step (bar (c) violation, scaled-down: "VOPR violation" — bit-determinism is the bar here, not ns)**: the design uses `ready: BTreeMap<DetClock, VecDeque<TaskBox>>` and inserts a new entry every time a task is scheduled with a distinct deadline. At 10k ops/sec each scheduling a unique deadline, the BTreeMap allocates 10k tree nodes/sec and deallocates them on `step()` drain. Allocator nondeterminism is the killer here: the allocator's bookkeeping (free-list state, page placement) varies across runs — and even though the test code never reads allocator state, it can leak through if any structure keys on a pointer or hash. Symptom: same-seed runs produce SHA256s that *almost* match but differ in one event out of millions — the classic "Heisenbug" of deterministic-sim shops.
    - Fix: pre-allocate a fixed-size `Vec<(DetClock, TaskBox)>` heap (binary heap) sized at boot to the expected max-in-flight tasks (e.g., 1 M). All scheduling pushes/pops on this heap — zero global allocator visits after warm-up. For the `TaskBox` itself, intern into a slab keyed by index, so `TaskBox = SlabIndex` (just a u32). Confirm via a `dhat` run that allocator visits == 0 during the test body.
    - Cost avoided: ~50 ns per schedule (×10k/sec = ~500 µs/sec, negligible perf-wise) — BUT eliminates the only source of allocator nondeterminism that could leak into a seed-replay mismatch. The replay-bug rate goes from "1-in-100M ops flaky" to "0 ever".
    - Muscle: deterministic-simulation invariants require zero global allocator visits inside the simulated region — the allocator is a hidden source of nondeterminism. Same lesson is the heart of TigerBeetle's static-mem design. Reapplies at: W83 ledger-deterministic apply loop (zero alloc per op), W88 VOPR harness scenario stream, W92 VSR message pool.
  - **Expect to hit (perf) #2 — `std::collections::HashMap` accidentally re-introduced (bar (c) / determinism violation)**: someone adds `cross_shard: HashMap<(ShardId, ShardId), VecDeque<TaskBox>>` instead of `BTreeMap` (the design above already specifies BTreeMap but a future refactor "for speed" reverts). Rust's `HashMap` uses `RandomState` (SipHash with per-process random seed) → iteration order varies *every process start*. Symptom: tests pass in a single `cargo test` invocation but fail across `cargo test`s; CI green locally, red on the build server.
    - Fix: lint via a CI step that `grep -r "HashMap\|HashSet" crates/runtime-thread-per-core/src/det_test.rs` and fails if found. Use `indexmap::IndexMap` or `BTreeMap` exclusively in this file. For the matching-engine code under test, the same lint applies to any module reachable from the deterministic test (transitively).
    - Cost avoided: hundreds of debug-hours chasing seed-replay-mismatch ghost bugs — the kind of bug that takes weeks of futile bisection before someone notices the HashMap.
    - Muscle: in deterministic-test code, `HashMap` is a banned word — enforce by lint, not by review. Same applies to `Instant::now()`, `thread_rng()`, raw `std::time::*`. Reapplies at: W83 ledger apply loop, W88 VOPR core, W92 VSR replication, W110 chaos harness.

  - **Why**: The Order type is the matching engine's input/output. Field choices determine memory layout (hot cache line), event-log size (every order serialized to wal), and match semantics. Getting these right now saves W74+ rewrites.
  - *Back-of-envelope*: `Order` is the most-touched 88 B in the entire crate — it's stored in the book, copied into fill events, encoded into the WAL, broadcast over messaging-aeron, replicated via raft. **Target: ≤ 64 B (one cache line)** at v1.0 to fit a single L1 line per order. The current 88 B layout straddles 2 lines — every `level.orders.front()` read pulls 2 lines on the cancel/match path. **Static-mem invariant**: order pool is pre-allocated (W14 bufpool muscle) — `Order` is `Copy`-like (no Box, no Vec, no heap pointer) so it lives inline in the slab. Float ban (already noted) applies hardest here: `Price(i64)`, `Qty(u64)`, integer fixed-point throughout. `OrderId` is a single u64 — 8 B; the structured bit-layout (16 top + 32 mid + 16 low) means uniqueness across shards comes from layout, not coordination (zero cross-shard RPC for ID generation, ~0 ns "lock" cost).
  - **Design**:
    ```rust
    #[derive(Clone, Copy, Debug, RlpEncodable, RlpDecodable)]
    #[repr(C)]
    pub struct Order {
        pub id: OrderId,           // 8 bytes
        pub price: Price,          // 8 bytes (i64; signed for sentinels, or u64 + negative-disallowed)
        pub qty: Qty,              // 8 bytes (u64)
        pub remaining: Qty,        // 8 bytes
        pub ts: Monotonic,         // 8 bytes (u64 ns since epoch)
        pub owner: AccountId,      // 32 bytes (Address)
        pub side: Side,            // 1 byte
        pub kind: OrderKind,       // 1 byte
        pub flags: u16,            // 2 bytes (room for PostOnly, ReduceOnly, etc.)
        // total: 84 bytes; round to 88 with padding; fits in 2 cache lines
    }

    #[derive(Clone, Copy, Debug, PartialEq)]
    pub enum Side { Buy, Sell }

    #[derive(Clone, Copy, Debug, PartialEq)]
    pub enum OrderKind {
        Limit,          // sit on book at price
        Market,         // take liquidity until qty filled or book empty
        IOC,            // Immediate-or-Cancel: take whatever's available, cancel rest
        FOK,            // Fill-or-Kill: fill ENTIRE qty or cancel ALL
        PostOnly,       // Reject if would take (cross book)
    }

    pub struct OrderId(pub u64);   // top 16 = shard, mid 32 = epoch, low 16 = counter
    pub struct Price(pub i64);     // fixed-point e.g. 1e-8 USDC
    pub struct Qty(pub u64);       // fixed-point e.g. 1e-6 base asset
    pub struct Monotonic(pub u64);
    ```

    - `ts` from `time::HybridLogicalClock` (W4); strictly monotonic per shard.
    - OrderId structure: shard-id top bits ensures cross-shard uniqueness without coordination.
    - RLP-encoded for wal event log; layout stable across versions (use Option<_> for future fields).
    - Side and OrderKind are 1-byte enums with explicit discriminants — RLP-friendly.

    - *Floating-point prices*: f64 prices destroy determinism. **Symptom**: same input → different fills across machines. **Fix**: integer fixed-point (i64 × 1e-8); document precision.
    - *OrderId collision across shards*: if shard-id bits forgotten, two shards generate same ID. **Symptom**: cross-shard cancel hits wrong order. **Fix**: top-16 bits always shard_id.

  - **Expect to hit (perf) #1 — `Order` straddles two cache lines (88 B layout) (bar (c) violation)**: the v0.5 design totals 88 B per order. The matching hot path reads `level.orders.front_mut()` (one Order body) on every fill; an 88 B order pulls **2 cache lines** (~14 ns L2 fetch worst case for the second line) for every fill, even though most fill arithmetic only touches `id`, `price`, `qty`, `remaining` (40 B that should fit in one line). At 1 M fills/sec/core, the wasted second-line fetch is ~5-10 ns × 1 M = 5-10 ms/sec/core of pure memory-stall.
    - Fix: shrink `Order` to ≤ 64 B by (a) reducing `AccountId` from 32 B (Address) to 8 B (a per-shard slab index into an `account_table: Vec<AccountId>`), saving 24 B; (b) packing `Side` (1 b) + `kind` (3 b: 5 kinds → 3 bits) + `flags` (12 b) into a single `u16` (saves 2 B); (c) dropping `flags` to `u8` if room. Result: 8 (id) + 8 (price) + 8 (qty) + 8 (remaining) + 8 (ts) + 8 (account_idx) + 2 (side+kind+flags) + 6 (pad) = **56 B in one cache line, with 8 B headroom**. Verify with `assert_eq!(size_of::<Order>(), 64)` (or 56 + alignment to 64). The full `AccountId` is dereferenced via `account_table[order.account_idx as usize]` only on the rare audit/event path (not the hot match path).
    - Cost avoided: ~5-10 ns L2 fetch per fill (saving ~5-10 ms/sec/core at 1 M fills/sec); restores the matching hot path to single-cache-line touch on the Order body; also halves the WAL encode size per order (88 B → 56 B = ~36% smaller WAL files, lower fsync latency, more orders per io_uring SQE).
    - Muscle: a struct on a bar-(c) hot path must fit in one cache line — and if a field is rarely read, indirect through an index table rather than storing it inline. Reapplies at: W61 `Fill` struct (must also be ≤ 64 B), W74 lock-free price-level node, W76 aeron `Image` per-publication state, W83 ledger `Account` row (must fit two cache lines max).

Symptom: WAL append benched in isolation runs at 5 M/sec; integrated with `Order::encode` it drops to 800k/sec — the gap is allocator pressure from the derive output.

Reserve `out` capacity once at boot (e.g., 4 KiB scratch holds 64 Orders).
    - Cost avoided: ~50 ns alloc + ~50 ns dealloc per order × 1 M/sec = ~100 ms/sec saved; eliminates allocator lock contention; brings integrated WAL throughput from 800k/sec to ~3 M/sec (matching the WAL's standalone capability).
