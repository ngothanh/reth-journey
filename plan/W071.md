        pub interval: Duration,               // typically 1h or 8h
        pub interest_rate_per_interval: i64,  // bps × 1e6
        pub premium_cap_bps: i64,             // e.g. ±75 bps
        pub damper_bps: i64,                  // subtractor applied before clamp
    }
    pub struct FundingRate {
        pub rate_bps: i64,
        pub ts: Monotonic,
        pub samples_in_interval: u32, // # samples that contributed to THIS interval's twap
        pub evicted_count: u32,       // # samples this tick removed from the window
    }
    pub struct FundingCalculator { /* config + window + last_funding_at */ }
    impl FundingCalculator {
        pub fn new(cfg: FundingConfig) -> Self;
        pub fn sample(&mut self, now: Monotonic, mark: Price, index: Price);
        pub fn tick(&mut self, now: Monotonic) -> Option<FundingRate>;
        fn compute_twap(&self) -> i64;        // time-weighted, all-integer
    }

  - *Back-of-envelope* (bar (c)): sample rate ≈ 1/sec/symbol; tick rate ≈ 1/hour. Per-sample cost target ≤ 50 ns (window push + edge eviction), **0 allocations steady-state**. A 1h window at 1/sec holds 3600 samples × ~24 B = ~85 KiB — fits L2, spills L1 (32 KiB). `tick()` walks the whole window once/hour: ~3600 mul + 3600 add + 1 div ≈ 7200 ops × ~1 ns ≈ 7 µs — negligible per tick. The cost driver is per-sample churn: 1000 symbols × 1/sec = 1k samples/sec; naive `VecDeque::push_back` + `retain` eviction = O(n) shift + periodic `Vec::reserve` (~100 ns memcpy) ≈ 50 µs/sec aggregate. Cliff ratio: fixed ring (3 ns push) vs. reallocating deque on the grow tick (~1 µs) ≈ **300×** on the worst sample.

    - R1. All arithmetic integer (`i64`/`i128`); inherits W66 `SignedFrac` semantics. No `f64` anywhere.
    - R2. Sample timestamps strictly monotonic; `sample()` rejects/debug-asserts a non-monotonic `now`.
    - R3. TWAP is time-weighted: `twap = Σ(dt_i × premium_i) / Σ dt_i` where `dt_i = t_{i+1} − t_i` and the **last sample's `dt` runs to the window end** (`dt_last = window_end − t_last`), NOT equal-weight per sample. Denominator `Σ dt_i = window length`.
    - R4. The interval closing at `now` is half-open `[now − interval, now)`; a boundary sample at exactly `t = now` belongs to the NEXT interval ONLY (it is NOT counted in this interval and NOT evicted by the tick that closes at `now`). `FundingRate.samples_in_interval` counts the samples that fell in `[now − interval, now)`. After emitting, the tick advances the window to the next interval `[now, now + interval)` and evicts every sample with `ts < now`; `FundingRate.evicted_count` reports how many were removed — the boundary sample at `ts = now` is NOT `< now`, so it survives. This is the half-open vs. closed discriminator: a closed `[now − interval, now]` impl includes the boundary sample in `samples_in_interval` AND evicts it (`ts ≤ now`), so it can NEVER appear in interval #2.

    - R6. Steady-state path (`sample()`) allocates 0 bytes; the window is a fixed-capacity ring sized `interval/sample_period + slack`.
    - R7. Same `(sample*, tick)` event sequence on two instances ⇒ bit-identical `FundingRate` stream (replica determinism — the property the VSR cluster relies on when this op replays from the log).

  - **(SENIOR) `interval_boundary_is_half_open`** — fires on the off-by-one. **Why a twap-VALUE assert is the WRONG observation here (the prior-draft bug):** at a time-weighted boundary the boundary sample lands at exactly `t = now = 60s`, so its `dt = window_end − t = 0` — it carries ZERO time-weight in interval #1 whether the interval is half-open or closed. A closed `[0,60]` impl therefore produces the SAME `rate_bps = 50` as the half-open impl, and `assert_eq!(r1.rate_bps, 50)` passes for BOTH (G4 violation: the naive closed-interval impl passes by accident). The genuinely divergent properties are **membership/eviction** (does the boundary sample count in interval #1?) and **survival into interval #2** (a closed impl evicts it; a half-open impl keeps it). Assert on those, not on the rate:
    ```rust
    #[test]
    fn interval_boundary_is_half_open() {
        let mut f = FundingCalculator::new(cfg_interval(secs(60)));
        // ONE sample at t=0 (+50 bps), held the entire [0,60) window → time-weighted twap = 50.
        f.sample(ms(0), mark(100_050), index(100_000));      // belongs to interval [0,60)
        // Boundary sample at exactly t=60s (+500 bps) — under half-open [0,60) it belongs to the
        // NEXT interval ONLY: it must NOT be counted in interval #1 and must NOT be evicted by the
        // tick that closes at t=60s; it must SURVIVE into interval #2's window.
        f.sample(ms(60_000), mark(100_500), index(100_000)); // boundary sample → next interval ONLY
        let r1 = f.tick(ms(60_000)).expect("first interval closes");

        // (1) MEMBERSHIP — the discriminating property. dt=0 makes rate_bps identical for half-open
        //     and closed, so we assert the COUNT, which genuinely diverges:
        //       half-open [0,60): boundary sample is NOT in interval #1  → samples_in_interval == 1
        //       closed   [0,60]: boundary sample IS counted in interval #1 → samples_in_interval == 2
        assert_eq!(r1.samples_in_interval, 1,
            "boundary sample at t=60s must NOT be counted in interval #1 (got {}); \
             a closed-interval impl reports 2 here", r1.samples_in_interval);
        // (2) EVICTION — after emitting, the window advances to [60,120) and evicts ts < 60.
        //     Only the t=0 sample qualifies (0 < 60); the boundary sample at ts=60 is NOT < 60,
        //     so it survives. Half-open → exactly 1 eviction; a closed impl (ts ≤ 60) evicts both.
        assert_eq!(r1.evicted_count, 1,
            "tick closing at t=60s must evict only the t=0 sample, NOT the boundary sample (got {} evictions); \
             a closed-interval impl evicts both and reports 2", r1.evicted_count);

        // (3) SURVIVAL into interval #2 — the strongest, value-level proof that does NOT depend on
        //     dt=0. Interval #2 [60,120) must START from the +500 boundary sample. A closed impl
        //     consumed+evicted it in interval #1, so interval #2 would see an EMPTY window
        //     (tick returns the no-sample sentinel / a different rate), never the +500-led twap.
        f.sample(ms(120_000), mark(100_000), index(100_000)); // +0 bps at the next boundary
        let r2 = f.tick(ms(120_000)).expect("second interval closes");
        // half-open: +500 held [60,120) until the +0 sample at t=120 (dt=60s) → twap = 500.
        // closed:    boundary sample gone → interval #2 starts from the +0 sample only → twap = 0.
        assert_eq!(r2.rate_bps, 500,
            "interval #2 must START from the surviving +500 boundary sample (got {}); \
             a closed-interval impl evicted it and reports ~0", r2.rate_bps);
        assert_eq!(r2.samples_in_interval, 1,
            "only the +500 boundary sample should belong to interval #2 here");
    }
    ```
  - **(EXPERT, cross-primitive trap — W66 SignedFrac) `funding_rate_pins_integer_golden_under_summation_reorder`** — composes integer determinism with the calc. Two sub-asserts, each of which a hidden `f64` fails for a *different* reason — and crucially the input is engineered so float actually diverges (same-binary same-input float is deterministic, so we must attack non-associativity + float-vs-floor rounding, NOT replica identity):
    ```rust
    #[test]
    fn funding_rate_pins_integer_golden_under_summation_reorder() {
        // ---- Sub-assert A: float-vs-floor rounding ----
        // Stream engineered so Σ(dt×premium)/Σdt has a NON-EXACT integer quotient.
        // dt's: [7s @ +101 bps, 11s @ +103 bps, 13s @ +107 bps, 29s @ +109 bps], window=60s.
        // Σ(dt×premium) = 7*101 + 11*103 + 13*107 + 29*109 = 707 + 1133 + 1391 + 3161 = 6392.
        // Σdt = 60. 6392 / 60 = 106.533... → integer FLOOR-div = 106.
        // A naive f64 path computes 106.5333.. then casts/rounds: `as i64` truncates to 106 by
        // luck, but `.round()` (the "clean average" instinct) yields 107. We pin the integer
        // floor result so the rounding-up float path is caught:
        const GOLDEN: i64 = 106;
        let mut f = FundingCalculator::new(cfg_interval(secs(60)));
        f.sample(ms(0),      mark(100_101), index(100_000)); // +101 bps, held 7s
        f.sample(ms(7_000),  mark(100_103), index(100_000)); // +103 bps, held 11s
        f.sample(ms(18_000), mark(100_107), index(100_000)); // +107 bps, held 13s
        f.sample(ms(31_000), mark(100_109), index(100_000)); // +109 bps, held 29s → window end 60s
        assert_eq!(f.compute_twap(), GOLDEN,
            "twap must be integer floor of 6392/60 = 106; float .round() yields 107 (PINS float-vs-floor rounding)");

        // ---- Sub-assert B: float non-associativity under summation REORDER ----
        // Same logical samples, fed to instance `b` in a DIFFERENT insertion order.
        // The calculator re-sorts by ts internally (R2 monotonic), so the *logical* window is
        // identical — but a float accumulator that sums in arrival order would produce a
        // different last-bit than one summing in ts order. i128 accumulation is associative,
        // so the two MUST be bit-identical. (This is the property a same-binary f64 actually
        // violates: order-dependent rounding, NOT replica identity.)
        let samples = vec![ // (ts_ms, premium_bps)
            (0u64, 101i64), (7_000, 103), (18_000, 107), (31_000, 109),
        ];
        let mut shuffled = samples.clone();
        shuffled.reverse(); // arrival order reversed; ts re-sort inside makes logical window equal
        let ra = run_twap_in_order(&samples,  secs(60));
        let rb = run_twap_in_order(&shuffled, secs(60));
        assert_eq!(ra, rb,
            "twap diverged under summation reorder — non-associative f64 accumulation (PINS float non-associativity)");
        assert_eq!(sha256(&[ra]), sha256(&[rb])); // bit-for-bit (W103 VSR-log replay determinism gate)
    }
    ```
    where `run_twap_in_order(samples, window)` feeds the samples (in the given arrival order) into a fresh `FundingCalculator`, lets it re-sort by ts internally, and returns `compute_twap()`.

  - **The problem this primitive solves**: ADL is rare (insurance-fund exhaustion is a tail event) but `update_account` runs on EVERY position-changing fill — up to 1M/sec/shard. The naïve approach (`BinaryHeap` with lazy invalidation via a seq-num indirection map) is *correct* but memory-unbounded — stale entries accumulate forever. The fix is periodic compaction. The other naïve approach (returning a fresh `Vec<ADLEntry>` from `pop_highest_rank`) burns allocator on every cascade event.

  - *Back-of-envelope* (bar (c)): `update_account` ≤ 100 ns p99, 0 steady-state allocs. At 1M/sec a single per-call `Vec::reserve` (~100 ns) blows the budget; `BinaryHeap::push` past capacity reallocs (~100 ns + memcpy). Lazy invalidation without compaction: 1M updates/sec × accounts touching position ~10×/sec ⇒ ~32M stale entries/hour × ~40 B = **~1.3 GB** unbounded growth = OOM. Cliff ratio: pre-sized heap push (~20 ns) vs. realloc push (~120 ns) ≈ **6×**; bounded RSS (O(active_accounts)) vs. unbounded (O(time×rate)) = the difference between a 24h soak passing and an OOM-kill.

  - **Requirements** R1..R10 — write in `crates/liquidation-engine/notes/71_adl_design.md`:
    - R1. `ADLEntry { account, symbol, side, size, unrealized_pnl_pct, leverage_used, rank_score: i128, seq_num: u64 }` — `rank_score = pnl_pct × leverage_used`, recomputed on each position change.
    - R2. `ADLQueue` bucketed by symbol; each bucket a max-heap by `rank_score`, tiebreak on `account_id` for determinism.
    - R3. **Stale-entry handling**: indirection map `account → seq_num`; heap entries carry `seq_num`; pop ignores entries whose seq doesn't match the current map.
    - R4. **Deterministic pop order**: same event history ⇒ same pop sequence on every replica; tiebreak by `account_id` lex order.
    - R5. **Counter-side only**: liquidating a long ⇒ ADL pops SHORT counter-positions, and vice versa.
    - R6. **Periodic compaction**: when stale ratio exceeds threshold (`heap.len() > 2 × active_accounts`), rebuild; compaction runs on a background tick, not on `update_account`'s hot path.
    - R7. **Bounded memory**: total ≤ O(active_accounts × const), not O(time × update_rate).
    - R8. **Zero-alloc pop API**: `pop_highest_rank` writes into a caller-provided `&mut SmallVec<[ADLEntry; 32]>`; no fresh `Vec`.
    - R9. **Hot-path budget**: `update_account` ≤ 100 ns p99.
    - R10. **Cross-replica determinism**: same event stream on two replicas ⇒ byte-identical pop sequences (the property the VSR log relies on at W103; a divergent pop turns cluster-VOPR red).

Note explicitly that two identical heaps fed the identical stream in one binary do NOT diverge, so the determinism test must reorder insertion; identify the `(-rank_score, account_id)` total-order tiebreak as the fix.

    fn replica_pop_sequence_byte_identical_under_divergent_micro_order() {

        let mut c = ADLQueue::from_iter(base.iter().cloned()); // exercises compaction heapify

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **(SENIOR) When `update_account_invalidates_stale_entry` / `stale_entry_skipped_correctly` pops the old rank-100 entry:**
    - Symptom: A was rank 100, updated to rank 50; pop returns A-at-100 (the stale entry). Wrong account ADL'd.
    - Why: you stored an `ADLEntry` without a `seq_num`; pop just takes the heap top — the heap doesn't know the entry is obsolete.
    - Fix: each entry carries `seq_num`; maintain `account_seq: HashMap<AccountId, u64>` (or fixed-cap array). `update_account` bumps the seq and pushes a new entry; pop checks `entry.seq == account_seq[entry.account]`, discards on mismatch, pops again.
    - Cost avoided: the wrong (more-profitable, already-changed) account gets force-closed — a correctness + fairness failure, replica-visible on the VSR log (W103).
    - Muscle: heap entries that can be invalidated need a seq-num + indirection map; pop is a "skip-stale + return-valid" loop. Reapplies at: W82 matching order cancel-then-reinsert, W92 ledger pending-transfer revalidation.
  - **(SENIOR) When `counter_side_only` pops same-side entries:**
    - Symptom: ADL of a long pops other longs.
    - Why: no side filter in `pop_highest_rank`; the caller's `side_to_pop` was ignored.
    - Fix: bucket or filter by counter-side; the liquidation engine passes the side to pop (opposite the bankrupt position).
    - Cost avoided: force-closing the *same* side as the bankrupt position deepens the imbalance instead of offsetting it.
    - Muscle: ADL/netting always operates on the counter-side; thread the side through the API explicitly. Reapplies at: W102/W119 liquidation→ADL chain, W90 `risk-engine` cross-instrument netting, W92 ledger offsetting transfers.
  - **(EXPERT, anti-shortcut, bar (c)) When `bench_update_account_under_100ns` reports ~250 ns:**
    - Symptom: `update_account` 2.5× over budget; flame graph shows `BinaryHeap::push` reallocation events.
    - Why: the heap wasn't pre-allocated; each push past capacity triggers `Vec::reserve` (~100 ns + memcpy).
    - Fix: `BinaryHeap::with_capacity(max_active_positions × 4)` at construction — covers steady-state + stale until next compaction; verify no reallocations during the bench.
    - Cost avoided: **(bar (c) violation)** — ~150 ns/update × 1M/sec = ~150 ms/sec of allocator work, blowing the per-shard time budget.
    - Muscle: pre-allocate hot-path collections to steady-state size + slack. Reapplies at: W71 funding ring (Thursday, `oracle-mark`), W90 `risk-engine` per-account margin scratch, W92 ledger transfer batch.
  - **(EXPERT, anti-shortcut, bar (c)) When `pop_into_smallvec_zero_alloc` shows ~500 small allocs/sec during a cascade burst:**
    - Symptom: heaptrack flags ~25 µs/sec allocator churn during ADL cascades; allocator-lock contention if shards share an allocator.
    - Why: `pop_highest_rank(...) -> Vec<ADLEntry>` returns a fresh `Vec` each call; cascades fire bursty (10–50/sec).
    - Fix: signature `pop_highest_rank(&mut self, symbol, want_qty, side, out: &mut SmallVec<[ADLEntry; 32]>)`; `out.clear()` between calls; 0 steady-state allocs. W103's `Op::ADLStep` (on the VSR log) inherits this out-buffer shape.
    - Cost avoided: **(bar (c) violation)** — ~25 µs/sec churn + allocator contention during the exact moment (cascade) the engine can least afford it.
    - Muscle: returning `Vec<T>` from a > 1k/sec hot-path API is an allocation contract; prefer `&mut Out`-buffer in/out signatures. Reapplies at: W71 funding (Thursday confirms the pattern), W102 liquidation fill-events vec, W77 aeron batch publish, W90 marketdata parsed-events vec.
  - **(EXPERT, negative-control) When `memory_bounded_under_steady_load` shows RSS climbing 100 MB → 1.3 GB over 10 min:**
    - Symptom: matching-engine memory grows monotonically during steady-state trading; ~32M stale entries × ~40 B ≈ 1.3 GB after an hour; eventual OOM-kill, no crash before.
    - Why: naïve `update_account` calls `heap.push(e_new)` without removing `e_old`; the seq-num pop path skips stale entries (correct) but the memory never returns — lazy invalidation is correctness, not memory management.
    - Fix: **periodic compaction** — a background tick (e.g. 60 s) checks each bucket; if `heap.len() > 2 × active_accounts`, drain, filter to valid (matching-seq) entries, re-push into a fresh heap, swap atomically via the W67 `arc_swap` snapshot pattern so updates continue against the new heap while the old is dropped.
    - Cost avoided: **(bar (c) violation)** — bounds growth at O(active_accounts × const) vs. O(time × rate); avoids OOM-kill; restores the "deterministic memory footprint over 24h" invariant.
    - Muscle: any lazy-deletion structure (heap+invalidation map, skiplist marker bits, MVCC tombstones) needs an explicit compaction policy — laziness alone is unbounded. Reapplies at: W37 epoch-gc/skiplist, W82 matching OrderBook canceled-order cleanup, W77 aeron term-buffer cleanup, W97 `risk-engine`/venue-store LSM memtable→SSTable freeze (the DB substrate consumed inside `perp-dex-core`, not a standalone mini-db).
  - **(EXPERT, negative-control) When `replica_pop_sequence_byte_identical_under_divergent_micro_order` shows divergent SHA256 between `a`/`b` or `a`/`c`:**
    - Symptom: the SAME logical equal-rank events, inserted in account-ascending (`a`) vs account-descending (`b`) order, pop in different orders; and the `from_iter` heapify rebuild (`c`, the compaction path) reorders ties yet again. On the VSR log (W103) any of these divergences is a consensus failure / cluster-VOPR StateChecker red.
    - Why: `BinaryHeap`'s ordering of equal-key entries depends on insertion order and on heapify behavior — so feeding *different micro-orderings* of the same events (which different replicas/compaction passes genuinely produce) yields different pop sequences. Note the broken version of this test — two identical heaps fed the identical stream in one binary — would pass even with the unstable comparator, trapping nothing; the trap only bites when the insertion order diverges.
    - Fix: include `account_id` in the comparator as a secondary key — tuple `(-rank_score, account_id)`; lex order is total, so pop order is independent of insertion order and of heapify. With the total order, `a`, `b`, and the `from_iter`-rebuilt `c` are byte-identical.
    - Cost avoided: **(bar (c) violation)** — a single divergent ADL pop is a replica state-hash mismatch = halt + reconciliation.
    - Muscle: any sort key on a replicated hot path must be TOTALLY ORDERED — tiebreak on a deterministic secondary key (entity id, monotonic seq); and the determinism *test* must feed divergent insertion micro-orderings + a heapify-rebuild path, never two identical same-binary streams. Reapplies at: W82 matching FIFO at price level, W92 ledger transfer ordering, W90 consensus-vsr PrepareOk ordering, W103 every `Op` ordering on the VSR log.
