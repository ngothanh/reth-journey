- [ ] [HFT] **Build**: `crates/matching-engine/src/perps/funding.rs` — funding-rate calc via TWAP of (mark - index).
  Hourly tick. (~150 min)
  - **Why**: Funding is the *only* mechanism keeping a perpetual contract's mark price anchored to spot index. Get the TWAP wrong and traders pay the wrong rate — at scale, that's millions in PnL deltas per day. Tier-A HFT exchanges (Binance, Bybit, dYdX) all converge on TWAP-of-premium-index designs; this exercise builds the canonical algorithm.
  - *Back-of-envelope* (bar c): sample rate ≈ 1/sec/symbol (premium snapshot from book + index), tick rate ≈ 1/hour. Per-sample cost: ~50 ns (push to VecDeque + eviction of expired samples). At funding_interval = 1h with 1 sample/sec, the window holds 3600 samples × ~24 B/sample = ~85 KiB — fits L2 but not L1 (32 KiB). `tick()` runs `compute_twap` over this whole window once per hour: 3600 multiplies + 3600 adds + 1 divide = ~7200 ops × 1 ns = ~7 µs/tick — negligible. The cost driver is the **per-sample VecDeque churn**: at 1/sec × 1000 symbols/exchange = 1k samples/sec; with naive `VecDeque::push_back` + `drop_older_than`, that's ~50 ns × 1k = 50 µs/sec of allocator + bookkeeping. **TWAP and rate ALL integer** — inherits `SignedFrac { num: i128, denom: i128 }` from W66 contract perf #1; float would re-introduce the cross-replica determinism violation that matching-engine v1.0 (W74) explicitly forbids.
  - **Read first**: Binance funding-rate methodology whitepaper (premium-index + interest-rate clamp). dYdX v4 `protocol/x/perpetuals/keeper/funding.go` for a deterministic on-chain implementation. FTX's historic methodology doc is also good (RIP).
  - **Design**:
    ```rust
    pub struct FundingConfig {
        pub interval: Duration,                // typically 1h or 8h
        pub interest_rate_per_interval: i64,   // basis points * 1e6
        pub premium_cap_bps: i64,              // e.g., ±75 bps
        pub damper_bps: i64,                   // small subtractor before clamp
    }
    pub struct FundingCalculator {
        cfg: FundingConfig,
        premium_samples: VecDeque<(Monotonic, i64)>,  // (timestamp, mark - index in bps)
        last_funding_at: Monotonic,
    }
    impl FundingCalculator {
        pub fn sample(&mut self, now: Monotonic, mark: Price, index: Price) {
            let premium_bps = ((mark.0 - index.0) * 10_000) / index.0;
            self.premium_samples.push_back((now, premium_bps));
            self.drop_older_than(now - self.cfg.interval);
        }
        pub fn tick(&mut self, now: Monotonic) -> Option<FundingRate> {
            if now < self.last_funding_at + self.cfg.interval { return None; }
            let twap = self.compute_twap();
            let clamped = clamp(twap.saturating_sub(self.cfg.damper_bps), -self.cfg.premium_cap_bps, self.cfg.premium_cap_bps);
            let rate = clamped + self.cfg.interest_rate_per_interval;
            self.last_funding_at = now;
            Some(FundingRate { rate_bps: rate, ts: now })
        }
        fn compute_twap(&self) -> i64 { /* time-weighted average */ }
    }
    ```
    **Invariants**: (i) Sample timestamps are monotonic — never use wall-clock. (ii) TWAP weight is `(t_{i+1} - t_i)` × `premium_i` not equal-weight per sample. (iii) Funding rate is symmetric: a positive rate means longs pay shorts; the absolute settlement formula is `pnl = -rate * position_notional` for longs, `+` for shorts.
  - **Build steps**: 1. (~25 min) Types + serde. 2. (~30 min) Sample collection with eviction. 3. (~40 min) `compute_twap` — careful weighting; off-by-one on interval boundary is the classic bug. 4. (~30 min) `tick()` driven by an external scheduler (don't spawn timers inside — replicas demand determinism). 5. (~25 min) Tests: synthetic mark/index time-series → expected rate within 1 bp.
  - **Pitfalls** (named, 3):
    - *Equal-weight TWAP*: **Symptom**: when sampling is irregular (e.g., quiet periods), equal-weight average over-weights bursts. **Fix**: time-weighted: `twap = sum(dt_i * premium_i) / total_dt`. Verify with hand-computed 3-sample example.
    - *Interval boundary off-by-one*: **Symptom**: a sample exactly at `last_funding_at + interval` is included twice (in this interval and next). **Fix**: use half-open intervals `[start, end)`; document boundary policy in the comment block.
    - *Funding-at-restart drift*: **Symptom**: after replica restart, `last_funding_at = 0` → first tick immediately fires a (possibly stale-priced) funding. **Fix**: persist `last_funding_at` to wal; on recovery, restore. Don't fire `tick()` until `now - last_funding_at < 2 * interval`.
  - **Test scenarios**: (a) Constant mark = index → rate ≈ interest_rate only. (b) Mark 1% above index for full hour → rate clamped to cap. (c) Sparse samples (gaps) → time-weighting correctness. (d) Replica restart mid-interval → no double funding. (e) Cross-replica determinism: feed same sample stream to 2 calculators → identical rate output bit-for-bit.
  - **Acceptance**: bench: 10k sample()+tick() pairs < 1ms total. Determinism: 100 randomized inputs replayed across two instances produce identical rates. Inheritance: time::Monotonic + bufpool::VecDeque (if applicable).
  - **Downstream**: W74 matching-engine v1.0 raft-replication treats `FundingRate` as a `MatchCommand::ApplyFunding{rate, ts}` — must be deterministic across replicas, so the TWAP calc is a *follower-side replay*, not leader-only. Feeds `liquidation.rs` (today's Friday) — funding settlement may push a position below maintenance margin.
  - **Expect to hit (perf) #1 — `VecDeque<Sample>` reallocation on `drop_older_than` (bar (c) violation)**: naive `drop_older_than(cutoff)` uses `self.premium_samples.retain(|(t,_)| *t >= cutoff)` which is O(n) AND shifts the entire deque on every drop, defeating the ring-buffer optimization. Worse, if implemented as `while front_too_old { samples.pop_front() }`, each `pop_front` still touches the head pointer — fine — but if the deque's internal buffer grows from `push_back`, you're paying a `Vec::reserve` (potentially ~100 ns + memcpy) every ~hour. At 1000 symbols sampling 1/sec, that's ~50 µs/sec aggregate; at 8h funding intervals × 28800 samples-per-window, the deque's working set is ~700 KiB per symbol — drops out of L2 entirely on warm walk. Symptom: P99 funding tick latency spikes when many symbols tick simultaneously; allocator profile shows VecDeque buffer growth churn.
    - Fix: **pre-allocate a fixed-capacity ring buffer** at construction: `capacity = (funding_interval_secs / sample_interval_secs) + slack`. Use `arrayvec::ArrayVec<(Monotonic, i64), MAX_SAMPLES>` for compile-time fixed cap, or a hand-rolled `[Sample; MAX_SAMPLES] + head: u16` ring. Eviction is implicit (overwrite oldest when full). Memory bound: `1000 symbols × ~32 KiB/buffer = 32 MiB` — fits comfortably in NUMA-local memory. Zero allocations in steady state.
    - Cost avoided: ~50 µs/sec aggregate alloc churn eliminated; eliminates the spike when buffers grow; restores deterministic memory footprint (a property test invariant: "funding RSS doesn't grow over 24h of sampling").
    - Muscle: time-windowed sliding-window data structures get **fixed-cap pre-allocated ring buffers**, not `VecDeque`. The window size is *known* (TWAP interval). Reapplies at: W71 ADL queue (per-account history), W74 matching-engine `EventLog` (per-symbol fixed window for MBO replay), W77 messaging-aeron term buffer (already ring-by-design — confirms pattern), W83+ ledger transfer audit log, W90 marketdata-kernelbypass ITCH burst buffer.

- [ ] [HFT] **Build**: `crates/matching-engine/src/perps/liquidation.rs` — liquidation threshold check (maintenance
  margin breach). Partial liquidation. Insurance-fund hook. (~150 min)
  - **Why**: Liquidations are the *exchange's only protection* against bankrupt accounts dragging the system into clawbacks. A correct liquidation engine is the difference between "platform survives a black swan" and "platform pays out from its own pocket / socialized losses". Partial liquidation (not full) reduces market impact and avoids cascade failures.
  - *Back-of-envelope* (bar c): `check()` runs after every fill that affects a position; at 1M fills/sec/shard worst case, that's the call rate (typically every 10th fill touches a position with active leverage = ~100k/sec). Per-check budget ≤ 200 ns (within the 1 µs per-order budget after matching). `check()` math: `notional = |size| * mark` (1 mul), `maintenance = notional * mm_bps / 10_000` (1 mul + 1 div), `equity = margin + unrealized_pnl` (1 add) — ~10 ns of arithmetic. The cost driver is **reading mark price from the contract state** — naive `self.contracts.get(&symbol).unwrap().mark_price` is a HashMap lookup (~30-50 ns) + a pointer chase (~7 ns L2). On a hot symbol that's 50× the actual math. **Mark price must live in the per-shard `OrderBook` struct's hot region** so `check()` reads it inline. Pure function — no allocations, no I/O.
  - **Read first**: Bybit's "Auto-Deleveraging and Liquidation" docs. dYdX v4 `protocol/x/clob/keeper/liquidations.go`. Aave v3 health-factor framework (cross-protocol parallel — useful framing).
  - **Design**:
    ```rust
    pub struct Position {
        pub account: AccountId,
        pub symbol: Symbol,
        pub size: i64,                   // signed: + long, - short, in contract lots
        pub avg_entry: Price,
        pub margin: u64,                 // posted collateral, after MTM
        pub unrealized_pnl: i64,
    }
    pub struct LiquidationConfig {
        pub maintenance_margin_bps: u32,  // e.g., 50 bps = 0.5%
        pub partial_step_bps: u32,        // each tick reduces position by this % of size
        pub insurance_fund_id: AccountId,
    }
    pub enum LiquidationAction {
        None,
        Partial { reduce_qty: u64, mark: Price },
        Full { close_qty: u64, mark: Price },
        Bankrupt { shortfall: u64 },     // insurance fund absorbs; if exhausted → ADL
    }
    impl LiquidationEngine {
        pub fn check(&self, pos: &Position, mark: Price) -> LiquidationAction {
            let notional = pos.size.unsigned_abs() as u64 * mark.0;
            let maintenance = notional * self.cfg.maintenance_margin_bps as u64 / 10_000;
            let equity = pos.margin as i64 + pos.unrealized_pnl;
            if equity >= maintenance as i64 { return None; }
            // Try partial first
            let reduce = (pos.size.unsigned_abs() as u64 * self.cfg.partial_step_bps as u64) / 10_000;
            if reduce > 0 && self.would_partial_restore(pos, mark, reduce) {
                return Partial { reduce_qty: reduce, mark };
            }
            // Full liquidation
            if equity >= 0 { return Full { close_qty: pos.size.unsigned_abs() as u64, mark }; }
            Bankrupt { shortfall: (-equity) as u64 }
        }
    }
    ```
    **Invariants**: (i) `check()` is pure — no mutation, no I/O. Mutation happens in the consuming match-engine handler. (ii) Maintenance margin computed against mark (not last-trade or mid). (iii) `Partial` action MUST monotonically reduce |size| toward zero; never grow.
  - **Build steps**: 1. (~20 min) Types. 2. (~30 min) `check()` decision tree. 3. (~25 min) `would_partial_restore` simulation — fast-path math, no execution. 4. (~30 min) Insurance-fund debit logic + bankrupt path. 5. (~25 min) Hook into Engine: after every trade affecting a position, call `check()`. 6. (~20 min) Tests below.
  - **Pitfalls** (named, 3):
    - *Liquidation cascade*: **Symptom**: liquidating account A pushes price, which liquidates B, which pushes price, which liquidates C — death spiral. **Fix**: partial-only first pass; rate-limit liquidations to e.g. 1% of book depth per second; pause and let market absorb. Cite BitMEX 2018 "Liquidation Vortex" post-mortem.
    - *Mark vs. last-trade*: **Symptom**: a single bad print triggers cascade because using last-trade. **Fix**: mark = `index * (1 + funding_drift_clamp)` not last-trade. Stale-mark detection: if mark hasn't updated in N seconds, halt liquidations.
    - *Negative-equity ADL trigger missed*: **Symptom**: position closes for less than 0 equity → shortfall absorbed by exchange instead of insurance fund / ADL. **Fix**: explicit `Bankrupt` path — insurance fund first, only after exhaustion does ADL fire (W76 builds the ADL queue).
  - **Test scenarios**: (a) Healthy position → no action. (b) Margin exactly at maintenance → no action (strict less-than). (c) Below maintenance, partial restores → Partial. (d) Below maintenance, partial wouldn't restore → Full. (e) Equity negative → Bankrupt. (f) Mark-stale → liquidations paused (returns None with warning log).
  - **Acceptance**: deterministic — same Position+mark → same LiquidationAction across replicas. Bench: 10k positions checked in <100µs. Property test: monotone in mark price (worse mark ⇒ ≥severe action).
  - **Downstream**: W74 raft-replicated apply path includes `MatchCommand::LiquidationStep{account, qty, mark}` deterministically. W76 ADL queue (`adl.rs`) consumes `Bankrupt` actions when insurance fund is dry.
  - **Expect to hit (perf) #1 — mark-price fetch via `HashMap<Symbol, Contract>` per check (bar (c) violation)**: naive impl looks up the contract by symbol on every `check()` call: `engine.contracts.get(&symbol).map(|c| c.mark_price)`. That's ~30-50 ns hash + ~7 ns pointer-chase + ~7 ns deref = ~50 ns just to obtain `mark_price` — 25% of the 200 ns budget gone before the math runs. Worse, the symbol-keyed HashMap iterates in non-deterministic order on different replicas (W74 determinism gate trap — already cited in W66 perf #1). Symptom: `perf top` shows `<ahash::AHasher>::write_u64` in liquidation.rs; cross-replica state hash diverges if any code path iterates `contracts`.
    - Fix: in the shard-per-symbol design (W65), each shard OWNS exactly one symbol's contract. `mark_price` lives directly in the shard's hot struct: `SymbolShard { mark_price: Price, ... }` — read is one register/cache-line load (~3 ns L1). The `Engine` keeps a `[ShardId → Contract]` mapping but `check()` runs *inside* the shard's task and reads its own contract field. Cross-shard mark price isn't needed for liquidation (each position is per-symbol).
    - Cost avoided: ~47 ns per check; at 100k checks/sec saves ~5 ms/sec; removes the HashMap iteration determinism trap; reclaims 23% of the per-check budget.
    - Muscle: in thread-per-core shard designs, hot fields live in the shard's owning struct, never behind a map keyed by sharding key. The map is a *routing* artifact (lives in `Engine`), not a hot-path lookup. Reapplies at: W74 raft-backed engine per-shard state, W77 messaging-aeron per-publication subscriber list, W83+ ledger per-shard account map, W90 marketdata-kernelbypass per-NIC-RX-queue buffer.

- [ ] [HFT] **Build**: `crates/matching-engine/src/perps/adl.rs` — Auto-Deleveraging queue (rank by profit × leverage).
  Skeleton only; complete in Phase 5 (W74). (~150 min)
  - **Why**: ADL is the last line of defense when insurance fund is exhausted and a bankrupt position cannot be closed at a price ≥ bankruptcy price. Instead of socializing the loss, the exchange force-closes profitable counter-positions ranked by `profit × leverage`. This shifts the cost to those who can most afford it (highly profitable, highly leveraged). Tier-A interview question: "how does Bybit's ADL ranking differ from Binance's?"
  - *Back-of-envelope* (bar c): ADL fires *rarely* (insurance fund exhaustion is a tail event) but `update_account` runs on EVERY position-changing fill — call rate up to ~1M/sec/shard. Per-update budget ≤ 100 ns. `BinaryHeap::push` is O(log n) ≈ 7 ops at n=128 active positions per shard ≈ ~35 ns warm + occasional heap-grow malloc (~50 ns). The trap: **stale-entry invalidation via O(log n) `decrease_key`** is NOT supported by std `BinaryHeap` — naive impls leak invalidated entries indefinitely, growing the heap from O(n) to O(updates) → O(update_rate × time) → unbounded. At 1M updates/sec for 1 hour, that's 3.6 G stale entries; even at 32 B/entry that's 115 GB → OOM in minutes. **Pop is rare but must be O(log n)-amortized** (skip-then-pop on stale entries). Memory pre-allocated: `BinaryHeap::with_capacity(max_active_positions × ~4)` to absorb stale entries without realloc.
  - **Read first**: Bybit ADL docs (the canonical reference: rank by `(unrealized_pnl_pct × leverage_used)`). dYdX v4 has no ADL (insurance fund only); compare and contrast.
  - **Design**:
    ```rust
    pub struct ADLEntry {
        pub account: AccountId,
        pub symbol: Symbol,
        pub side: Side,                  // counter-side to liquidating position
        pub size: u64,
        pub unrealized_pnl_pct: i64,     // bps
        pub leverage_used: u32,           // bps
        pub rank_score: i128,             // = pnl_pct * leverage_used (recomputed on each tick)
    }
    pub struct ADLQueue {
        // Bucketed by symbol; each bucket sorted desc by rank_score
        buckets: AHashMap<Symbol, BinaryHeap<ADLEntry>>,
    }
    impl ADLQueue {
        pub fn update_account(&mut self, e: ADLEntry);  // O(log n)
        pub fn pop_highest_rank(&mut self, sym: Symbol, want_qty: u64) -> Vec<ADLEntry>;  // for force-close
        pub fn snapshot_for_replication(&self) -> Vec<ADLEntry>;  // deterministic order for raft apply
    }
    ```
    **Invariants**: (i) Rank score is recomputed *on every position change* — stale ranks must never be popped. (ii) `pop_highest_rank` is deterministic — ties broken by `account_id` lex order, not heap insertion order. (iii) Counter-side only: liquidating a long ⇒ ADL pops short counter-positions, vice versa.
  - **Build steps**: 1. (~25 min) Types. 2. (~35 min) Update path — invalidate old entry, insert new with fresh score. 3. (~40 min) `pop_highest_rank` with tiebreak. 4. (~25 min) `snapshot_for_replication` — sorted-vec output for deterministic raft serialization. 5. (~25 min) Tests. (Scaffold-only this week; complete deterministic apply in W74.)
  - **Pitfalls** (named, 3):
    - *Stale rank*: **Symptom**: account updates position size but old entry remains in heap with old rank — wrong account ADL'd. **Fix**: use an indirection map `account → seq_num`; heap entries carry seq_num; pop ignores entries whose seq doesn't match map.
    - *Tiebreak non-determinism*: **Symptom**: across replicas, BinaryHeap ordering of equal-rank entries differs → different accounts ADL'd → state divergence. **Fix**: heap comparator includes `account_id` as tiebreaker. Property test: feed same events two ways, get same pop order.
    - *Counter-side mistake*: **Symptom**: ADL pops same-side positions (e.g., longs forced to close when a long goes bankrupt) — economically wrong. **Fix**: explicit `side` filter in `pop_highest_rank`; unit test for both directions.
  - **Test scenarios**: (a) 100 positions ranked, top-3 highest rank popped. (b) Same rank, different account_id → deterministic tiebreak. (c) Update an account's position size → re-rank correctly. (d) Cross-replica: same event stream → same pop sequence bit-identical.
  - **Acceptance**: bench: 10k updates + 1k pops < 5ms. Determinism test 100 random schedules. Inheritance: bufpool::Vec, AHashMap.
  - **Downstream**: W74 wires `pop_highest_rank` into matching-engine deterministic apply: when `LiquidationAction::Bankrupt` returns and insurance is dry, raft-leader proposes `MatchCommand::ADLStep{symbol, counter_positions: Vec<ADLEntry>}`; replicas apply identically.
  - **Expect to hit (perf) #1 — unbounded heap growth from stale entries (bar (c) violation, OOM risk)**: naive `update_account(e)` calls `heap.push(e_new)` without removing `e_old`. At 1M updates/sec on an account that touches its position 10× per second, every second adds 9 stale entries; over an hour that's ~32M stale entries × ~40 B = ~1.3 GB heap. The heap's `count_ones`-style pop walks past these via the `account → seq_num` invalidation map (correct), but the *memory* never returns. Symptom: matching-engine RSS grows monotonically during steady-state trading; eventually OOM-killed; no crash before that, just creeping memory.
    - Fix: **periodic compaction** — when stale-entry ratio exceeds a threshold (e.g., `heap.len() > 2 × active_accounts`), rebuild the heap by draining and re-pushing only valid (matching seq_num) entries. Run compaction on a background tick, NOT on the hot `update_account` path. For the rebuild itself, swap the heap pointer atomically (`arc_swap` pattern from W67 perf #2) so updates continue against the new heap while the old is dropped.
    - Cost avoided: bounds memory growth at O(active_accounts) instead of O(time × update_rate); avoids OOM-kill; restores the "deterministic memory footprint over 24h" invariant.
    - Muscle: any lazy-deletion data structure (heap with invalidation map, skiplist with marker bits, MVCC with tombstones) needs an explicit compaction policy — laziness alone is unbounded. Reapplies at: W37 epoch-gc/skiplist (already noted — defer_destroy via EBR is the compaction), W74 matching-engine OrderBook canceled-order cleanup, W77 messaging-aeron term buffer cleanup, W95 mini-db memtable→SSTable freeze (compaction = freeze).
  - **Expect to hit (perf) #2 — heap allocation per `pop_highest_rank` result (bar (c) violation)**: `pop_highest_rank(sym, want_qty) -> Vec<ADLEntry>` returns a fresh `Vec` each call. ADL itself is rare, but the same pattern *will* show up at W74 in the deterministic apply path (`MatchCommand::ADLStep { victims: Vec<ADLEntry> }`); during high-volatility cascades, this fires bursty (10-50 times in a second). Each `Vec` allocation is ~50 ns + cache-line clear; at 50 pops/sec × ~10 entries returned = 500 small allocations/sec = ~25 µs/sec of churn — plus allocator-lock contention if shards share an allocator.
    - Fix: `pop_highest_rank(&mut self, sym, want_qty, out: &mut SmallVec<[ADLEntry; 32]>)` — caller provides a pre-allocated `SmallVec` (inline cap 32, spills to heap only if exceeded). `out.clear()` between calls. Zero allocations in steady state.
    - Cost avoided: ~25 µs/sec churn during ADL bursts; eliminates allocator contention; aligns with the W74 determinism gate's "no allocations in steady state" rule.
    - Muscle: returning `Vec<T>` from hot-path APIs is an allocation contract; prefer `&mut Out`-buffer in/out signatures for any function called >1k/sec. Reapplies at: W74 matching-engine fill-events vec, W77 messaging-aeron batch publish, W83+ ledger transfer batch apply, W90 marketdata-kernelbypass parsed-events vec.
