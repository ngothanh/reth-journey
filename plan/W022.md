  - 🔧 **Why this matters**: staged sync (Erigon's invention, adopted by reth) decomposes blockchain sync
    into ~12 idempotent, resumable, monotonic stages. Each stage has invariants the Pipeline depends on —
    advances by ≥1 block per execute, leaves DB consistent at every checkpoint, fully reverses on unwind.
    The trait is small but every method's contract is dense. Downstream: every concrete stage from W22

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: full-state sync is too big for a single transaction (hundreds
    of GB of state mutations per block on mainnet now-days). Staged sync splits the work into
    independent phases — each runs to completion before the next starts. The Stage trait codifies the
    invariants every phase must uphold: idempotent (re-running is safe), monotonic (progress never goes
    backward), resumable (crash mid-execute, restart, make progress), reversible (unwind is exact).

  - **Requirements** — write in `crates/eth-stage/notes/22_stage_trait_design.md`:
    - R1. `Stage<DB: Database>: Send + Sync` trait with `id`, `execute`, `unwind`, plus optional
      `pre_execute`/`post_execute` hooks.
    - R2. `id() -> StageId` enum: 12 variants matching reth (Headers, Bodies, SenderRecovery, Execution,
      MerkleExecute, AccountHashing, StorageHashing, IndexAccountHistory, IndexStorageHistory,
      TransactionLookup, MerkleUnwind, Finish).
    - R3. **Idempotency**: `execute(checkpoint=N, target=N)` is a no-op. Running same execute twice
      produces identical state.
    - R4. **Monotonicity**: `ExecOutput.checkpoint >= ExecInput.checkpoint` always.
    - R5. **Resumability**: if `execute` is killed mid-flight (SIGKILL), restarting with the same
      input must make forward progress (no infinite loop, no rewind).
    - R6. **Reversibility**: `unwind(N)` followed by `execute(target=N)` produces byte-identical state.
    - R7. Stage NEVER commits the transaction itself. Pipeline owns commit boundaries.
    - R8. `StageCheckpoint` persistence: each stage stores `(stage_id → block_number)` in a
      `StageCheckpoints` table; survives crashes.
    - R9. Trait signature is byte-identical to `reth-stages-api::Stage` (so a Stage written here drops
      into a reth fork without API translation).

  - **Design walk-through** — answer each:
    - D1. Why are `execute` and `unwind` `async`? (Hint: they may await on Database I/O — MDBX is sync
      but a wrapper can be async; future stages may await on network for headers.)
    - D2. The `done: bool` in `ExecOutput` — what does it mean precisely? (Hint: "no more work AT THIS
      TARGET", NOT "stage permanently done". Forgetting flips checkpoints.)
    - D3. ChangeSets — the index of "which keys this block changed" — make unwind O(blocks × keys/block)
      instead of O(state size). Why is this load-bearing for any stage that mutates state?
    - D4. `StageError` shape: what variants do you need to distinguish recoverable (retry) from fatal
      (operator escalation)? (Hint: `Database`, `Network`, `BlockNotFound`, `InvalidProgress`, `Fatal
      { kind, source }`.)
    - D5. Pre-mortem: write the scenario where a non-idempotent execute (writes that assume "table is
      empty") silently corrupts state on a crash-restart. Show the corruption trail.

  - **Output**: `notes/22_stage_trait_design.md` with R1–R9 + D1–D5 + the 12-stage list.

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

  - **When `mock_stage_idempotent_execute` reports diverged state on second execute:**
    - Symptom: first execute writes 100 keys; second execute (same input) writes them again, doubling
      counts in a "count blocks per address" sub-table.
    - Why: stage's write logic was `count += 1` (increment if key exists, insert otherwise) instead of
      `count = computed_value_for_block_range`. The first form depends on prior state — non-idempotent.
    - Fix: every stage write is `INSERT ... ON CONFLICT REPLACE` (set to the canonical value derived
      from the input range), never an increment that depends on what's already there. The DB tx is
      the only "memory" between executes; never read-modify-write within execute unless the read is
      itself a derived-from-input quantity.
    - Muscle: stage execute must be a pure function of `(input_range, prior_committed_state)`; any
      "increment" or "append-without-check" makes it non-idempotent. Reapplies at: every concrete
      stage (Execution, Hashing, MerkleExecute), W43 full pipeline run.

  - **When `mock_stage_reversible_round_trip` produces state ≠ single-shot baseline:**
    - Symptom: execute → unwind → execute final state differs from single-shot execute at some keys.
    - Why: unwind didn't fully clean the writes from the first execute — it removed direct entries
      but missed an index update (e.g. the "TxHashesByBlock" lookup wasn't deleted). The second execute
      then re-inserts cleanly but leaves a stale entry from the first run.
    - Fix: maintain an explicit ChangeSet per (stage, block) listing every key the stage touched;
      unwind walks the ChangeSet and reverts each key precisely. The ChangeSet IS the inverse function.
    - Muscle: reversible state machines maintain a per-step inverse log; without it, unwind is
      best-effort and accumulates drift. Reapplies at: ARIES UNDO (W30), W42 txn rollback, W92
      block-stm conflict resolution.

  - **When `trait_signature_matches_reth_byte_identical` reports a diff:**
    - Symptom: your trait has `Result<ExecOutput, StageError>`; reth has `Result<ExecOutput, StageError>`
      with a different shape on `StageError` (extra variants like `BlockNotFound` you omitted).
    - Why: convenient simplifications to the error enum diverge from the upstream surface.
    - Fix: copy reth's exact trait signature, including `StageError`. Idiomatic improvements live in
      INTERNAL helpers (private modules), never on the public trait. Pin the fixture as a CI guard.
    - Muscle: a mirror crate's PUBLIC API is reth's API; freedom for "clean Rust" lives in internals.
      Reapplies at: `eth-rlp` (alloy-rlp parity), `eth-consensus`, `consensus-engine` (Engine API), W26
      wal facade (RocksDB inheritance).

  - **When `mock_stage_resumable_after_kill` gets stuck on restart (no forward progress):**
    - Symptom: kill mid-execute, restart, execute returns `Ok(ExecOutput { checkpoint: 0, done: false
      })` repeatedly — making no progress.
    - Why: stage relied on in-memory state (e.g. a `seen: HashSet<BlockHash>`) that was lost on kill.
      On restart, it re-processes blocks 0..N to "rebuild" the set, but the rebuild itself doesn't
      advance the checkpoint.
    - Fix: every "rebuild" path within execute must produce monotone checkpoint advances on a clean
      schedule (advance checkpoint by 100 blocks at a time, even if you're just re-reading). Or:
      persist the seen-set to the DB so restart doesn't need rebuild.
    - Muscle: resumable stages persist all "memory" to the DB; in-memory caches that need rebuilding
      on restart must rebuild via monotone checkpoint advances, not stuck in-place. Reapplies at: W22
      Pipeline, W30 recovery, W43 mainnet sync.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: with stages defined in isolation, the system needs an
    orchestrator that drives them in order, persists progress between them, handles crash recovery via
    last-good-checkpoint lookup, and reacts to chain reorgs by unwinding everything to the common
    ancestor. Without the Pipeline, individual stages are useful but the sync pipeline isn't a system.

  - **Requirements** — write in `crates/eth-stage/notes/22_pipeline_design.md`:
    - R1. `Pipeline<DB>` registers stages in topological order via a builder.
    - R2. `run(target)` main loop: for each stage in order, read checkpoint, execute one batch, commit
      tx, persist checkpoint. Loop until all stages report `done == true` AND checkpoint == target.
    - R3. `unwind(target)` walks stages in **REVERSE order**, unwinding each.
    - R4. **Stage-N checkpoint ≤ Stage-N-1 checkpoint** at all times (topological monotonicity).
    - R5. Pipeline commits at stage boundaries ONLY — never mid-stage.
    - R6. On reorg event (from external `reorg_events` channel), pipeline aborts current stage's tx and
      enters unwind cycle to common ancestor.
    - R7. `PipelineEvent::{StageStarted, StageCompleted, UnwindStarted, UnwindCompleted, ReorgDetected}`
      broadcast for observability.
    - R8. Crash-simulation property test: 100 random fault injections (SIGKILL during commit, SIGKILL
      mid-stage, SIGKILL during unwind) all converge to a correct state on restart.

  - **Design walk-through** — answer each:
    - D1. The per-stage commit boundary: why must the tx commit fire between stages? (Hint: crash in
      stage K with stage K-1 uncommitted = state-root corruption + replay of K-1.)
    - D2. Reorg-during-stage-K: stage K is mid-execute. The stage's tx is uncommitted. What does the
      pipeline do? (Hint: just drop the tx; nothing was committed. Then unwind from K-1's checkpoint.)
    - D3. Cancellation safety: every `execute().await` must be cancellation-safe — dropping the future
      mid-execute leaves no committed state behind. How do you enforce this at the trait level?
    - D4. Unbounded memory: a naive ExecutionStage that holds all 10k blocks before commit OOMs. Who
      chunks? (Hint: the stage itself; Pipeline provides `target_chunk_size` hint.)
    - D5. Pre-mortem: write the scenario where pipeline commits stage K's tx but crashes BEFORE
      persisting checkpoint. What happens on restart?

  - **Output**: `notes/22_pipeline_design.md` with R1–R8 + D1–D5 + the run/unwind state diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~45 min)

  - **When `pipeline_kill_restart_byte_identical` produces diverged state:**
    - Symptom: kill during stage 3, restart, final state differs from baseline. Diff shows stage 2
      data is partially applied.
    - Why: pipeline committed stage 2's tx, then crashed before persisting stage 2's checkpoint to
      the StageCheckpoints table. On restart, stage 2 re-executes from checkpoint = 0, writing already-
      committed data again (non-idempotency exposed).
    - Fix: per-stage commit + checkpoint-persist must be ATOMIC. Two options: (a) write the checkpoint
      INSIDE the stage's own tx — so the commit covers both data and checkpoint; (b) use a 2PC-style
      "intent log" with explicit recovery. (a) is simpler and what reth uses.
    - Muscle: per-stage commit and checkpoint persist must be in the SAME tx; otherwise crash between
      them produces uncoordinated state. Reapplies at: W26 wal `checkpoint`, W30 recovery `Recovery::recover`.

  - **When `reorg_unwinds_stages_in_reverse` reports forward order:**
    - Symptom: `UnwindStarted` events fire as `[StageHeaders, StageBodies, StageExecution]` instead of
      `[StageExecution, StageBodies, StageHeaders]`.
    - Why: `unwind` walks `self.stages.iter()` forward instead of `.iter().rev()`.
    - Fix: `for stage in self.stages.iter().rev() { stage.unwind(...).await?; }`. The reverse order is
      load-bearing — unwinding bodies before execution would leave execution's reads pointing at
      nonexistent bodies.
    - Muscle: stage execute is topological-forward; unwind is topological-reverse. Reapplies at: W30
      recovery (ARIES UNDO walks records in reverse), W42 txn rollback.

  - **When `cancelled_execute_does_not_commit` reports commit ran:**
    - Symptom: dropping the execute future mid-poll causes the tx to commit via Drop's RAII pattern.
    - Why: the tx wrapper auto-commits on Drop instead of auto-aborting.
    - Fix: tx wrapper's Drop is `abort()`, not `commit()`. Commit requires explicit `tx.commit().await`.
      The async-cancellation safety property hinges on this RAII direction.
    - Muscle: in async cancellation, RAII Drop = abort-by-default. Commit is always explicit. Reapplies
      at: W26 wal `Wal::append` (drop on cancel doesn't commit), W42 txn `commit`/`rollback`.

  - **When `crash_during_commit_resumes_at_last_checkpoint` reports the wrong checkpoint after restart:**
    - Symptom: crash during stage 2's commit at byte 5 of an 8-byte checkpoint write — restart sees a
      garbled checkpoint value, possibly larger than committed data.
    - Why: checkpoint write isn't atomic on disk (8-byte write straddling a page boundary may tear).
      Restart reads the torn value as if it were valid.
    - Fix: stage checkpoints live in the same MDBX table the data writes go to — MDBX's COW B+tree
      makes the entire tx atomic (meta-page flip = all-or-nothing). Don't roll your own checkpoint
      file. If you must, write to `.tmp` + atomic rename + fsync directory.
    - Muscle: any "checkpoint" persisted outside the data tx is a torn-write hazard; co-locate
      checkpoint with data in the same atomic unit. Reapplies at: W26 wal `MANIFEST` (write-temp +
      rename), W30 ARIES checkpoint.

  - **5-year failure mode** (write in `notes/22_pipeline_followup.md` after green): when reth-style

    topological monotonicity (R4) relaxes to a DAG of dependencies. Migration: replace `Vec<Box<dyn

    Trigger: ExecutionStage moves to W92 block-stm (parallel within a stage), and MerkleStage starts
    running concurrently with HashingStage (different sub-tables).
