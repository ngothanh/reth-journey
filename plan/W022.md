  - *Mental model*: a `Stage` is an idempotent function from `(committed DB state, input block range)` to
    `(committed DB state, output checkpoint)` that can be safely re-run from its prior checkpoint after a crash,
    and exactly reversed by `unwind`. The trait codifies four invariants: idempotent, monotonic, resumable,
    reversible.
  - *Contract* (signature-level only — NEVER the body):
    ```rust
    pub trait Stage<DB: Database>: Send + Sync {
        fn id(&self) -> StageId;
        async fn execute(&mut self, provider: &DB, input: ExecInput) -> Result<ExecOutput, StageError>;
        async fn unwind(&mut self, provider: &DB, input: UnwindInput) -> Result<UnwindOutput, StageError>;
    }
    ```
    `ExecInput { target: BlockNumber, checkpoint: Option<StageCheckpoint> }`,
    `ExecOutput { checkpoint: StageCheckpoint, done: bool }`,
    `UnwindInput { unwind_to: BlockNumber, checkpoint: StageCheckpoint }`,
    `StageCheckpoint { block_number: BlockNumber }`.
  - *MockStage contract (PINNED — the tests below depend on it; a no-op mock is OUT of contract and the test
    suite is engineered to reject it)*: the `MockStage` used in Phase 2 is NOT free to be a do-nothing stub.
    `execute(checkpoint=cp, target=t)` MUST, for **each** block `n` in `(cp, t]`, write two pieces of
    per-block derived state into the `MemDb`:
    1. a canonical header row `Headers[n] = mock_header(n)` (the idempotent, replace-on-conflict write), AND
    2. bump a shared running counter `Counts[ADDR] += 1` where `ADDR` is one fixed key (the **intentionally
       naive** read-modify-write — this is the trap the idempotency test fires on).
    On success it returns `ExecOutput { checkpoint: StageCheckpoint::new(t), done: true }` for a single-batch
    mock. A correct (idempotent) implementation must change the `Counts[ADDR] += 1` increment into a canonical
    set — `Counts[ADDR] = (t - cp)` derived purely from the input range — so re-running yields the same value.
    Because the mock is REQUIRED to write `Counts[ADDR]` and `Headers[n]`, a stub that writes nothing or returns
    early is non-conformant and fails `mock_stage_idempotent_execute` and `mock_stage_monotonic_output` below.
    *Batched resume (PINNED for R5):* the test-only `execute_partial(input, stop_after)` processes blocks in
    batches, and after EACH batch's writes it durably commits `write_checkpoint(StageId::Execution,
    StageCheckpoint::new(last_block_in_batch))` in the SAME `MemDb` tx as that batch's `Headers` rows — so when
    it is interrupted after `stop_after` blocks, `read_checkpoint` returns the last completed batch boundary and
    `Headers` row-count equals that checkpoint. A mock that checkpoints only at completion (or holds progress in
    an in-memory cache) is non-conformant and fails `mock_stage_resumable_after_kill`. The harness exposes
    `MemDb::first_block_written_by(&mut stage)` (records the lowest block key the next `execute` writes) so the
    resume test can assert the restart's first processed block is `cp+1`, not `1`.
  - **Requirements** R1..R10 — write in `crates/eth-stage/notes/22_stage_trait_design.md`:
    - R1. `Stage<DB: Database>: Send + Sync` with `id`, `execute`, `unwind`.
    - R2. `StageId` enum, 12 variants matching reth (Headers, Bodies, SenderRecovery, Execution, MerkleExecute,
      AccountHashing, StorageHashing, IndexAccountHistory, IndexStorageHistory, TransactionLookup, MerkleUnwind,
      Finish). Order is load-bearing (Pipeline runs forward, unwinds reverse).
    - R3. **Idempotency**: `execute(checkpoint=N, target=N)` is a no-op; running the same `execute` twice yields
      byte-identical state.
    - R4. **Monotonicity**: `ExecOutput.checkpoint.block_number >= ExecInput.checkpoint`; `target < checkpoint`
      is `Err(StageError::InvalidProgress)`.
    - R5. **Resumability**: `execute` (and the test-only `execute_partial`) commits the checkpoint at EACH batch
      boundary inside the batch's own data tx, so a kill leaves a durable resume point reflecting the blocks
      already done. On restart the stage reads that persisted checkpoint and processes ONLY `(cp, target]` — it
      re-writes none of the already-done `(0, cp]` prefix (no rewind, no from-scratch re-run, no infinite loop).
      A stage that persists nothing and re-processes the whole range from 0 is NON-resumable and must fail
      `mock_stage_resumable_after_kill`.
    - R6. **Reversibility**: `unwind(to=M)` then `execute(target=N)` (M<N) yields byte-identical state to a
      single-shot `execute(target=N)`.
    - R7. Stage NEVER commits its own transaction; the Pipeline owns commit boundaries.
    - R8. `StageCheckpoint` persists in a `StageCheckpoints` table `(stage_id → block_number)`; survives crashes.
    - R9. Public trait signature is byte-identical to `reth-stages-api::Stage` (drops into a reth fork without a
      translation layer). Idiomatic improvements live in private internal helpers only.
    - R10. **MockStage write obligation (test-bearing)**: the `MockStage` test double's `execute(cp, t)` MUST
      write per-block derived state for every `n` in `(cp, t]` — `Headers[n] = mock_header(n)` AND a running
      `Counts[ADDR]` (initially the naive `+= 1` per block; the idempotent fix sets it to `t - cp`). It returns
      `checkpoint = StageCheckpoint::new(t)`. `execute_partial(input, stop_after)` does the same in batches but
      commits a checkpoint (co-located with that batch's `Headers` rows) at each batch boundary, so an
      interruption leaves a durable resume point. This makes a do-nothing stub non-conformant: the corruption in
      D5 is only reachable because the mock is FORCED to write state that a second `execute` can double-apply, and
      a checkpoint-only-at-completion mock is non-conformant because it cannot pass `mock_stage_resumable_after_kill`.
  - **Design walk-through** D1..D6 — answer in the design doc; no peeking at upstream bodies until Phase 3:
    - D1. Why are `execute`/`unwind` `async`? (MDBX is sync but the provider wrapper can be async; future
      stages await network for headers.) **NOTE — fixture is ground truth, not the sketch above**: the
      `*Contract*` block shows `async fn execute` for this exercise's pedagogy, but reth's real `Stage` is sync

      `tests/fixtures/reth_stage_trait.rs` is the parity oracle; diff your prediction against IT, and let
      `trait_signature_matches_reth` arbitrate the final public signature.
    - D2. `ExecOutput.done: bool` — what does it mean *precisely*? ("no more work AT THIS TARGET", NOT "stage
      permanently finished" — conflating these flips checkpoints.)
    - D3. ChangeSets — the per-block index of "which keys this block changed" — make `unwind` O(blocks ×
      keys/block) not O(state size). Why load-bearing for any state-mutating stage?
    - D4. `StageError` shape: which variants distinguish recoverable (retry) from fatal (operator escalate)?
      (`Database`, `Network`, `BlockNotFound`, `InvalidProgress`, `Fatal { kind, source }`.)
    - D5. **Pre-mortem (load-bearing)** — write the EXACT 4-5 line bad trace where a non-idempotent `execute`
      (a write that assumes "table is empty" or does `count += 1`) silently corrupts state on a crash-restart:
      ```
      t0: execute(target=100) writes keys, count[addr]=5; commits tx
      t1: CRASH before checkpoint persisted (checkpoint still =0)
      t2: restart -> execute(checkpoint=0, target=100) re-runs, count[addr]=5+5=10
      t3: state diverges from single-shot baseline (count[addr] should be 5)  <-- corruption
      ```
    - D6. **Anti-shortcut audit**: name the "obvious" reach for each motivation and why it's wrong HERE:

  #### Phase 2 — Write the failing tests (~35 min)

  Each test is engineered so a common naive impl FAILS it. Tier annotated. Use a `MockStage` over an in-memory
  `BTreeMap<Vec<u8>, Vec<u8>>` "DB" so state comparison is byte-exact.

  - [ ] **(NEWBIE) `mock_stage_idempotent_execute`** — exercises R3 + R10. Traps the `Counts[ADDR] += 1`
    read-modify-write. The key strengthening over a snapshot-equality check: it asserts on the SPECIFIC corrupted
    key after the second run, so a no-op `MockStage` (which would be trivially "idempotent" but writes nothing)
    is rejected — the test first proves the mock wrote the expected single-shot value, THEN proves re-running
    didn't double it.
    ```rust
    #[test]
    fn mock_stage_idempotent_execute() {
        let mut s = MockStage::new();
        let mut db = MemDb::new();
        // expected single-shot value: execute(0, 100) touches blocks 1..=100 => Counts[ADDR] == 100
        let expected_single_shot: u64 = 100;
        s.execute(&mut db, ExecInput { target: 100, checkpoint: Some(StageCheckpoint::new(0)) }).unwrap();
        // (a) the mock actually wrote the per-block derived state — rejects a do-nothing stub
        assert_eq!(db.get_u64("Counts/ADDR"), Some(expected_single_shot),
            "MockStage wrote no per-block Counts state — a no-op stub cannot pass an idempotency trap");
        assert_eq!(db.scan_table("Headers").count(), 100,
            "MockStage wrote no per-block Headers — execute did not process the (0,100] range");
        let after_first = db.snapshot();
        // re-run the SAME input; idempotent => Counts/ADDR stays 100 (NOT 200), snapshot unchanged
        s.execute(&mut db, ExecInput { target: 100, checkpoint: Some(StageCheckpoint::new(0)) }).unwrap();
        assert_eq!(db.get_u64("Counts/ADDR"), Some(expected_single_shot),
            "second execute doubled Counts/ADDR ({:?} != {}) — the `+= 1` read-modify-write is non-idempotent",
            db.get_u64("Counts/ADDR"), expected_single_shot);
        assert_eq!(db.snapshot(), after_first,
            "second execute with identical input changed state — execute is not idempotent");
    }
    ```

  - [ ] **(NEWBIE) `mock_stage_monotonic_output`** — exercises R4 + R10. Strengthened past a pure `>= cp`
    check (which a frozen no-op that returns `checkpoint = input.checkpoint` passes vacuously): for a
    single-batch mock, `out.checkpoint == target` exactly (the stage must have advanced TO the target), and when
    `target > cp` the checkpoint must STRICTLY advance. A do-nothing mock that returns `checkpoint = cp` is
    rejected on the very first strictly-greater target.
    ```rust
    #[test]
    fn mock_stage_monotonic_output() {
        let mut s = MockStage::new();
        let mut db = MemDb::new();
        let mut cp = 0u64;
        for target in [10u64, 50, 50, 200, 200, 1000] {
            let out = s.execute(&mut db, ExecInput { target, checkpoint: Some(StageCheckpoint::new(cp)) }).unwrap();
            // single-batch mock MUST land exactly on target — not freeze at cp, not overshoot
            assert_eq!(out.checkpoint.block_number, target,
                "single-batch mock did not advance to target: cp={} target={} got={} \
                 (a frozen no-op returning checkpoint=cp passes a bare `>= cp` check)",
                cp, target, out.checkpoint.block_number);
            // and when there is real work to do, the checkpoint must STRICTLY move forward
            if target > cp {
                assert!(out.checkpoint.block_number > cp,
                    "target {} > cp {} but checkpoint did not advance ({}): stage stalled / is a no-op",
                    target, cp, out.checkpoint.block_number);
            }
            // never backward
            assert!(out.checkpoint.block_number >= cp,
                "checkpoint went backward: {} -> {}", cp, out.checkpoint.block_number);
            cp = out.checkpoint.block_number;
        }
    }
    ```

  - [ ] **(SENIOR) `mock_stage_resumable_after_kill`** — exercises R5. Traps a stage that throws away all
    progress on crash and re-processes the whole range from scratch (the non-resumable behavior R5 forbids). The
    key strengthening over a bare "made some forward progress" check: it (1) asserts `execute_partial` durably
    persisted a partial checkpoint in `(0, 1000)` — a stage that persists NOTHING falls back to 0 and would
    silently pass a `> 0` check by re-running 0→1000 — and (2) asserts the restart resumes FROM that checkpoint,
    re-writing ZERO of the already-done `(0, cp]` blocks, so total `Headers` writes across both runs == 1000
    (not 1000 + the redone prefix). This makes the no-persistence / re-run-from-0 path genuinely unreachable for
    a passing solution; `execute_partial` MUST commit a checkpoint at each batch boundary, not only at completion.
    ```rust
    #[test]
    fn mock_stage_resumable_after_kill() {
        let mut db = MemDb::new();
        // first stage instance processes ~300 blocks, then is "killed" (dropped) mid-flight
        { let mut s = MockStage::new();
          let _ = s.execute_partial(&mut db, ExecInput { target: 1000, checkpoint: Some(StageCheckpoint::new(0)) }, /*stop_after*/ 300);
        } // s dropped — all in-memory caches gone; only the DB-persisted checkpoint survives

        // (1) execute_partial MUST have durably committed partial progress at a batch boundary.
        // No unwrap_or(0) fallback: a stage that persisted nothing is non-resumable and fails HERE,
        // before it can launder a from-scratch re-run into "forward progress".
        let cp = db.read_checkpoint(StageId::Execution)
            .expect("execute_partial persisted no checkpoint — stage is not resumable (rebuilds from scratch on crash)");
        assert!(cp.block_number >= 300 && cp.block_number < 1000,
            "resume point {} did not reflect the ~300 blocks processed before kill \
             (checkpoint must advance at each batch boundary, not only at completion)",
            cp.block_number);
        // count what the killed run already wrote — the restart must NOT re-write these blocks
        let blocks_before = db.scan_table("Headers").count();
        assert_eq!(blocks_before as u64, cp.block_number,
            "Headers written ({}) != persisted checkpoint ({}) — checkpoint and data are not committed together",
            blocks_before, cp.block_number);

        // (2) fresh instance restarts FROM the persisted checkpoint, not from 0
        let mut s2 = MockStage::new();
        let out = s2.execute(&mut db, ExecInput { target: 1000, checkpoint: Some(cp) }).unwrap();
        assert_eq!(out.checkpoint.block_number, 1000,
            "restart did not finish the range: cp={} -> {}", cp.block_number, out.checkpoint.block_number);

        // the restart must process ONLY (cp, 1000] — total Headers across both runs == 1000, not 1000 + redone prefix.
        // A throw-away-progress impl that re-ran 0->1000 would leave 1000 here only because cp was 0;
        // because (1) forced cp >= 300, a from-scratch restart would have re-touched (0, cp] and we'd see the
        // first restart-written block be 1, not cp+1.
        assert_eq!(db.scan_table("Headers").count() as u64, 1000,
            "Headers table has {} rows, expected exactly 1000 — restart re-processed already-done blocks (not a true resume)",
            db.scan_table("Headers").count());
        assert_eq!(db.first_block_written_by(&mut s2), cp.block_number + 1,
            "restart's first processed block was not cp+1 — it re-ran the (0, cp] prefix instead of resuming");
    }
    ```

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

  Newbie failures first, expert last.

  - **(NEWBIE) When `mock_stage_idempotent_execute` reports diverged state on the second execute:**
    - Symptom: `execute(0,100)` writes `Counts[ADDR]=100`; the second identical `execute(0,100)` yields
      `Counts[ADDR]=200` — the `get_u64("Counts/ADDR") == expected_single_shot` assertion fires with `Some(200)`.
    - Why: the mock's per-block write (R10) was `Counts[ADDR] += 1` (read-modify-write) instead of
      `Counts[ADDR] = (target - checkpoint)`. The `+=` form depends on prior committed state — re-running over
      the same range double-applies. (The `Headers[n]` write, by contrast, is already replace-on-conflict so it
      stays idempotent — only the counter corrupts.)
    - Fix: every stage write sets the canonical value derived from the input range (`Counts[ADDR] = target -
