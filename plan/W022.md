- [ ] **Build**: `crates/eth-stage/src/lib.rs` — Stage trait (id, execute, unwind) matching reth shape. (~105 min)
  - **Why**: Staged sync (Erigon's invention, adopted by reth) decomposes blockchain sync into ~12 idempotent, resumable, monotonic stages. Each stage has invariants the Pipeline depends on (advances by ≥1 block per execute, leaves DB consistent at every checkpoint, fully reverses on unwind). The trait is small but every method's contract is dense.
  - **Read first**: reth `crates/stages-api/src/stage.rs` (the `Stage` trait — 4 methods + 2 lifecycle hooks) and `crates/stages/stages/src/stages/headers.rs` (concrete example). Erigon's staged sync doc (mainnet Erigon README).
  - **Design**:
    ```rust
    #[async_trait]
    pub trait Stage<DB: Database>: Send + Sync {
        fn id(&self) -> StageId;
        /// Forward progress: from input.checkpoint to input.target.
        async fn execute(&mut self, provider: &mut DB::TxMut, input: ExecInput)
            -> Result<ExecOutput, StageError>;
        /// Reverse: revert state from current_checkpoint down to unwind_to.
        async fn unwind(&mut self, provider: &mut DB::TxMut, input: UnwindInput)
            -> Result<UnwindOutput, StageError>;
        /// Optional pre-/post-execute hooks for resource setup.
        async fn pre_execute(&mut self) -> Result<(), StageError> { Ok(()) }
        async fn post_execute(&mut self) -> Result<(), StageError> { Ok(()) }
    }
    pub struct ExecInput { pub checkpoint: BlockNumber, pub target: BlockNumber }
    pub struct ExecOutput { pub checkpoint: BlockNumber, pub done: bool }
    ```
    **Invariants**:
    - Stage is *idempotent*: running execute(checkpoint=N, target=N) is a no-op.
    - Stage is *monotonic*: output.checkpoint >= input.checkpoint, always.
    - Stage is *resumable*: if execute is killed mid-flight, restarting with same input must make progress.
    - Stage is *reversible*: unwind(N) followed by execute(target=N) restores state byte-identical.
    - Stage writes are committed atomically per execute call (the tx commit is at the Pipeline level, not the stage's choice).
  - **Build steps**:
    1. (~10 min) `StageId` enum: 12 variants matching reth (Headers, Bodies, SenderRecovery, Execution, MerkleExecute, AccountHashing, StorageHashing, IndexAccountHistory, IndexStorageHistory, TransactionLookup, Finish).
    2. (~25 min) `Stage` trait with the 4-method shape; `#[async_trait]`.
    3. (~20 min) `ExecInput`, `ExecOutput`, `UnwindInput`, `UnwindOutput` value types.
    4. (~15 min) `StageError` enum: `Database`, `Network`, `BlockNotFound`, `InvalidProgress`, `Fatal { kind, source }`.
    5. (~20 min) `StageCheckpoint` persistence: each stage stores `(stage_id → block_number)` in a `StageCheckpoints` table; survives crashes.
    6. (~15 min) Test scaffold: `MockStage` that fakes progress; verify invariants via property tests.
  - **Pitfalls**:
    - *Non-idempotent execute*: stage writes that depend on "what's already there" silently corrupt on retry. **Symptom**: 1 in 1000 sync restarts produces wrong state root. **Fix**: every write is `INSERT ... ON CONFLICT REPLACE`; every read tolerates already-written rows.
    - *Partial commits inside execute*: stage tries to checkpoint mid-batch with its own tx commit. **Symptom**: crash mid-execute leaves DB in tornado of partial commits — Pipeline assumed atomicity. **Fix**: stage uses the tx handed by Pipeline; only Pipeline commits.
    - *Unwind asymmetry*: an execute that runs O(blocks) but unwind that runs O(state) destroys reverse-sync. **Symptom**: unwind takes 8 hours for a 100-block revert. **Fix**: keep an *index* of writes per block (the "ChangeSets" in Erigon parlance) so unwind is O(unwound blocks × avg writes per block).
    - *Done flag misuse*: `done: bool` means "no more work AT THIS TARGET" not "stage permanently done". Forgetting flips checkpoints. **Symptom**: stage skipped on resume. **Fix**: integration test that runs execute repeatedly until `done = true`, asserts checkpoint == target.
  - **Test scenarios**:
    - MockStage with deterministic progress: simulate kill-restart at every block; final state matches no-kill run.
    - Property: for any (execute_sequence, unwind_sequence), final state is determined by *last* checkpoint, not path.
    - Adversarial: target < checkpoint → execute returns error (no backwards progress).
    - 100-block unwind of MockExecutionStage matches 100-block forward then "untouched" baseline.
  - **Acceptance**:
    - Inheritance ratio ≥ 0.9 vs reth `stage.rs` trait shape.
    - Property tests pass under proptest 1k cases.
  - **Downstream**: every concrete stage W22+ (HeaderStage, BodyStage, ExecutionStage, MerkleStage, HashingStage); W43 full pipeline run; W64 RPC reads from stage-produced indices.
- [ ] **Build**: Pipeline runner with checkpoint persistence via eth-storage-cache::StateCache. (~75 min)
  - **Why**: The Pipeline is the orchestrator that runs stages in topological order, drives them in batches, handles crash recovery, and propagates unwind on chain reorgs. Without it, stages are just isolated functions. The Pipeline's invariants (commit-after-each-stage, unwind-on-reorg) are what make staged sync correct under failure.
  - **Read first**: reth `crates/stages/stages-api/src/pipeline/mod.rs` — focus on `Pipeline::run` (the main loop) and `Pipeline::unwind` (the reorg path). Also `crates/stages/api/src/pipeline/progress.rs` for the checkpoint state machine.
  - **Design**:
    ```rust
    pub struct Pipeline<DB: Database> {
        stages: Vec<Box<dyn Stage<DB>>>,           // topologically ordered
        checkpoint_table: CheckpointStore<DB>,
        event_sender: broadcast::Sender<PipelineEvent>,
        max_block: Option<BlockNumber>,
    }
    impl<DB> Pipeline<DB> {
        pub async fn run(mut self, target: BlockNumber) -> Result<(), PipelineError> {
            loop {
                // 1. For each stage in order:
                //    - Read its checkpoint.
                //    - Execute one batch (target = min(self.target, prev_stage_checkpoint)).
                //    - Commit tx, persist checkpoint.
                //    - On reorg event, break to unwind.
                // 2. If all stages report done && checkpoint == target → return.
            }
        }
        pub async fn unwind(&mut self, target: BlockNumber) -> Result<(), PipelineError> {
            // Walk stages in REVERSE order, unwinding each to target.
        }
    }
    ```
    **Invariants**:
    - Stage N's checkpoint ≤ Stage N-1's checkpoint at all times.
    - Unwind is FIFO-reversed: last-to-finish-execute is first-to-unwind.
    - Pipeline only commits at stage boundaries (never mid-stage).
    - On reorg, all stages unwind together to the common ancestor before any executes forward.
  - **Build steps**:
    1. (~15 min) `Pipeline::builder` with `.add_stage(s)` registration.
    2. (~20 min) `run` main loop with per-stage execute + commit + checkpoint-persist sequence.
    3. (~15 min) `unwind` walking stages in reverse.
    4. (~10 min) Reorg detection hook: external `reorg_events` channel triggers an unwind cycle.
    5. (~10 min) `PipelineEvent::{StageStarted, StageCompleted, UnwindStarted, ...}` for observability.
    6. (~5 min) Tests: stages running with mock DB, simulated reorgs.
  - **Pitfalls**:
    - *Forgetting per-stage commit*: skipping commit between stages means a crash in stage K loses K-1's writes. **Symptom**: state-root corruption after crashes. **Fix**: explicit `tx.commit().await` after each stage's execute returns OK.
    - *Reorg during stage K*: stage K is mid-execute when reorg fires. Naive: cancel and restart. Real: stage K's tx is uncommitted, just abort the tx — then unwind from K-1's checkpoint. **Symptom**: deadlock or state corruption. **Fix**: each execute is cancellation-safe; cancelling does NOT commit.
    - *Mismatched checkpoint ordering*: if Stage 5 advances past Stage 4 (impossible per invariant), Pipeline picks up corrupt state. **Symptom**: silent data corruption. **Fix**: assert at top of each iteration that `checkpoint[N] <= checkpoint[N-1]`.
    - *Unbounded memory in stage*: stage that holds all 10k blocks in memory before commit OOMs. **Symptom**: OOM on big batch. **Fix**: stage's execute is responsible for chunking; Pipeline provides `target_chunk_size` hint.
  - **Test scenarios**:
    - Mock pipeline with 3 stages: run to block 1000, kill, restart — final state byte-identical.
    - Simulated reorg from block 500 to ancestor 480: pipeline unwinds stages 1-3 in reverse, executes forward to 500.
    - Stage 2 fails with `Fatal`: pipeline halts, returns error, does NOT advance.
    - Crash at random byte during stage 1 commit (use crash-simulator): re-run finds last committed checkpoint, resumes.
  - **Acceptance**:
    - Inheritance ratio ≥ 0.85 vs reth Pipeline.
    - Crash-simulation property test passes under 100 random fault injections.
  - **Downstream**: W43 full mainnet sync; W64 RPC waits for pipeline to advance; W92 block-stm slots inside ExecutionStage as the parallel block executor.
