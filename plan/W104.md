  - *Mental model*: the settlement boundary is **not** a settlement *system* — it is a thin **derivation** over a fact the VSR log already holds. The log committed the fills; `commit_num` says how far the commit point reached; `finality_status` is the single comparison `op_number ≤ commit_num` interpreted relative to the id's `snapshot_epoch`. This is the Spanner/TigerBeetle move: *don't store derivable state*. The "hybrid" in hybrid-CLOB means off-chain matching (the VSR log) + on-chain settle (the stub today, a real chain at v1.5) — but the *identity* that bridges the two halves is the op-number, which both halves can interpret without a shared mutable index.
  - *Contract* (signature-level only — NEVER the body):
    ```rust
    // Minted by W103; this week consumes + extends it.
    pub struct SettlementId { snapshot_epoch: u64, op_number: u64, checksum: u128 } // newtype; safe to expose externally
    pub enum FinalityStatus { Pending, Final, Reverted }   // Reverted unreachable in v1.0; the v1.5 slot
    pub trait SettleSink {                                  // the stub today; a real chain at v1.5
        fn submit(&self, batch: &[FillEvent], id: SettlementId);   // v1.0: no-op record; v1.5: tx to chain
    }
    pub struct SettleBoundary<S: SettleSink> { /* &commit_num (atomic), current_epoch, sink: S, ... */ }
    impl<S: SettleSink> SettleBoundary<S> {
        pub fn settle(&self, batch: &[FillEvent]) -> SettlementId;          // returns immediately; id = op position
        pub fn finality_status(&self, id: SettlementId) -> FinalityStatus;  // pure derivation; zero alloc
    }
    // NOTE (v3 §4A): NO `map: HashMap<SettlementId, FinalityStatus>`. Finality is derived, never stored.
    ```
  - *Back-of-envelope* (bar (c) — name the cost):
    - Derivation cliff: a side `HashMap<SettlementId, Status>` probe ≈ ~25 ns + a write-lock under the replicated invariant + 1 malloc on insert; at the analytics read rate (say 100k status checks/s) = ~2.5 ms/s of map overhead + a replicated mutable map the cluster must keep bit-identical. The comparison-against-`AtomicU64` path: `commit_num.load(Acquire)` ≈ ~1 ns, one branch, **0 allocs, no replicated auxiliary state**. Cliff ≈ 25× *and* it removes a whole class of divergence.
    - Idempotency cliff: minting a new id per `settle` call + a side dedup set = O(calls) memory growth + a replicated set. Keying idempotency on the op's `checksum` (already in the id) = O(1), free — a resubmit of an already-committed batch resolves to the same op position, no new proposal.
    - View-change cost: a side mapping table must be rebuilt or transferred on every view-change (state-transfer payload grows); the derivation path transfers **nothing extra** — `commit_num` and the log are already transferred by W76 state-transfer. Cliff = O(committed ops) of extra state-transfer per view-change vs zero.

  - **The problem this primitive solves**: a venue that stores settlement status as auxiliary state has THREE failure categories: (a) **replicated-non-determinism** — a mutable id→status map inside the VSR state machine must be bit-identical across replicas, and any `HashMap` iteration / wall-clock timestamp in it diverges them silently; (b) **two-sources-of-truth under view-change** — the side table and the log can disagree about what's committed after a leader failover; (c) **rewrite-trap** — an API shaped around "set the status" cannot accept an optimistic challenge window (where `Pending` lasts a real duration and `Reverted` is a legitimate transition) without breaking external callers. The fix is §4A's lock: identity = op-number, finality = derivation, status table = does-not-exist.
