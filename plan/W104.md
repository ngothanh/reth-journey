- [ ] **Build**: `crates/vector-db/src/segment.rs` — `SegmentManager` orchestrates sealed (immutable) and active
  (mutable) segments. Sealed segments are mmap'd snapshots; active is the current insert target. Merge policy

  - 🔧 **Why this matters**: a single HNSW graph degrades with churn (deletes leave tombstones, updates
    fragment adjacency). Segments let you build small, immutable graphs and federate search across them. This
    is **the Qdrant architecture** and the modern vector-db default. Without segments, deletes can't be
    reclaimed and search performance degrades over time. NET-NEW v2 feature; this is the terminal v0.5
    feature. Downstream consumers: W105+ ops runbook (Prometheus metrics `MERGE_QPS`, `SEGMENT_COUNT`,
    `TOMBSTONE_RATIO` come from THIS struct), W104 Wed v0.5 tag depends on this shipping green, W109
    production deploys reference segment lifecycle for capacity planning.

  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: a single mutable HNSW graph in a long-running database accumulates
    failure modes — tombstoned deletes that can't be reclaimed in place (HNSW edges reference them),
    fragmented adjacency from incremental updates, and a single point of write contention. Without
    segmentation you cannot: bound the cost of any one snapshot save, reclaim space from deletes, parallelize
    insert vs read, or roll forward on hardware failure of a partial segment. Lucene solved this in 2002,
    RocksDB in 2013, Qdrant in 2021 — the pattern is "tiered, immutable segments + background merge."

  - **Requirements** — write in `crates/vector-db/notes/104_segment_manager_design.md`:
    - R1. At any instant there is exactly ONE mutable segment (the "active") and N ≥ 0 immutable sealed
      segments. Inserts go only to active; reads federate across all.
    - R2. When the active segment exceeds `max_active_bytes` it is **sealed atomically** — a new active is
      installed, the old becomes sealed via `PersistedHnsw::save`. Concurrent inserts during sealing block
      ≤ 1 ms (no full write stall).
    - R3. `search(q, k, ef, filter)` returns top-k across ALL segments. Each segment contributes its local
      top-k; a global merge picks the global top-k. Recall vs a single-graph baseline is ≥ 99%.
    - R4. Federated search latency at 10 segments is ≤ 1.5× single-segment for the same total vector count
      (verified by criterion bench).
    - R5. Merge runs on a background thread, picks N candidates by tiered policy (size ratio +
      `merge_min_segments`), builds a new sealed segment, then atomically swaps `Vec<Arc<SealedSegment>>`
      contents — old segments stay live until last reader's Arc drops.
    - R6. A crash mid-merge leaves `.tmp` directories; recovery on `open()` sweeps and removes them; old
      segments remain authoritative. No partial-merge state is ever visible.
    - R7. `GlobalId = (segment_id, local_id)` — local IDs never collide across segments. `segment_id` is
      globally monotone.
    - R8. Old segment directories are GC'd only after a grace period (e.g., 30 s) past the last reader's
      drop; in-flight queries holding an Arc to the old segment finish cleanly.
    - R9. Merge throughput consumes ≤ 25% of one core in steady state; foreground search p99 latency
      regresses ≤ 10% during active merge.

  - **Design walk-through** — answer each in your design doc; no peeking at Qdrant `segment_manager.rs` or
    Lucene `IndexWriter` until Phase 3:
    - D1. Concurrency primitive for `active`: `RwLock<Arc<MutableSegment>>` vs `ArcSwap<MutableSegment>`?
      Argue trade-offs — RwLock is simpler but every insert acquires a read lock; ArcSwap is wait-free read.
      Which matters more for R2's "no stall"?
    - D2. `MutableSegment` vs `SealedSegment` types: what fields differ? Why is sealed `mmap` while active
      is fully in RAM? (Hint: think about read amplification vs write amplification.)
    - D3. Seal trigger: where in `insert()` do you check `size_bytes > max_active_bytes`? Atomically vs
      best-effort? What happens if two inserts trigger seal simultaneously?
    - D4. Federated top-k: each segment returns its top-k, then global merge picks top-k of those. Argue
      why this can miss the true top-k. What's the fanout fix and what cost does it add?
    - D5. Merge candidate selection: write the pseudocode for `pick_merge_candidates(sealed, config)` —
      tiered policy by size. What's the trigger for high-tombstone segments?
    - D6. Atomic swap of `Vec<Arc<SealedSegment>>`: do you `Vec::retain` + push under a `RwLock<Vec<…>>`,
      or build a new Vec and `ArcSwap` the whole vector? Argue from R5 (readers must not block during the
      swap) and R8 (old Arcs must remain valid).
    - D7. GC of `.tmp` and superseded segment dirs: when do you delete? (Hint: `Arc::strong_count` is a
      smell — use a grace timer + an "is anyone still using this generation" bitmap.)
    - D8. Mid-merge crash sequence: write the 6-step interleaving where merge has built `new_segment.tmp`
      but crashes before the Arc swap. What does `open()` see? What's the cleanup rule?
    - D9. **Pre-mortem (the load-bearing question)**: write the interleaving where (a) query thread T1
      clones `Arc<SealedSegment>` for segment S, (b) merge thread T2 removes S from the active vector,
      (c) GC thread T3 deletes S's on-disk dir while T1 is still mmap-reading vectors.bin. Show why your
      GC discipline must wait for refcount AND a grace period — refcount alone is racy because Drop runs
      AFTER the last read. If you cannot write the bad interleaving, you do not yet understand the GC
      sequencing well enough.
  - **Output**: `notes/104_segment_manager_design.md` with R1–R9, answers to D1–D9, sequence diagrams for
    insert-then-seal, federated search, merge swap, the pre-mortem interleaving.

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  - **When `concurrent_insert_during_seal_blocks_under_1ms` reports 50 ms blocked time:**
    - Symptom: inserter thread blocks for ~50 ms while seal copies the entire HnswGraph into the persist
      pipeline under a write lock.
    - Why: seal_active() held `self.active.write()` for the duration of `PersistedHnsw::save` — that's a
      ~50 ms write to disk and inserters wait for the lock.
    - Fix: split seal into two phases — (1) under write lock, atomically swap in a new `MutableSegment`
      and capture the OLD as a local Arc; release lock. (2) Outside the lock, persist the old segment
      and append to `sealed`. Inserters block only for the Arc swap (~µs).
    - Muscle: minimize critical section — hand off ownership inside the lock, do expensive work outside.
      Reapplies at: W107 manifest swap, W74 raft snapshot install.

  - **When `merge_swap_atomic_no_query_panic` panics with `Arc strong_count was 0` or miri reports UAF:**
    - Symptom: a query thread holding `Arc<SealedSegment>` panics when it tries to read `persisted.search()`
      because the underlying mmap was unmapped.
    - Why: GC code dropped the `Arc<SealedSegment>` AND immediately `std::fs::remove_dir_all` on its
      directory — but the SealedSegment's `Drop` runs after the last Arc release, and even after Drop the
      mmap kernel mapping is gone before the test's stale slice reads it. Worse: GC ran before the swap
      finished, so a query still held a logical reference.
    - Fix: GC is a two-stage commit — (1) on swap, push the superseded `Arc<SealedSegment>` plus its
      directory path into a `to_gc: VecDeque<(Arc<SealedSegment>, Instant)>`; (2) a separate GC tick
      checks each entry: if `Arc::strong_count == 1` (only we hold it) AND `now - queued_at > grace`,
      Drop the Arc, then remove the dir. NEVER remove the dir while any other Arc exists.
    - Muscle: GC of mmap-backed resources needs both refcount AND a grace timer; refcount alone races
      with `Drop` ordering of nested fields. Reapplies at: W104 segment GC, W107 manifest version GC,
      W108 replica file lifecycle.

  - **When `mid_merge_crash_recovers_clean` finds `.tmp` dirs left behind and `open()` errors:**
    - Symptom: after a kill-9 mid-merge, `open()` calls `SealedSegment::load` on the `.tmp` dir,
      mistakes its half-written `header.bin` as a real segment, returns `Err(CrcMismatch)`.
    - Why: recovery walked every subdirectory in segments/ assuming all are segments; the `.tmp`
      suffix wasn't filtered.
    - Fix: recovery (a) lists `segments/`, (b) for each entry, if name ends in `.tmp`, schedule it for
      `remove_dir_all` (best-effort), (c) only load entries whose `header.bin` parses + CRC verifies.
      Builds AGAINST `.tmp` and renames to final name only on swap success.
    - Muscle: convention "in-progress = `.tmp` suffix" is the cheapest crash-safe pattern; recovery's
      first move is sweep, not load. Reapplies at: W104 merge crash, W107 manifest crash recovery.

  - **When `federated_search_recall_within_1pct_of_single` reports recall=0.91 vs single's 0.95:**
    - Symptom: 4% recall regression after segmentation — the global top-k is missing nodes that were
      ranked #11 in their local segment but should have been #4 globally.
    - Why: federation fetched only top-k from each segment; if segment A's k=10 missed item X (X was 11th
      in A's local order), but X would be 4th globally, X is lost.
    - Fix: each segment fetches `top-(k * fanout)` where `fanout` defaults to 2; global merge picks top-k.
      Cost: ~2× per-segment search work, but only the post-merge merge is global.
    - Muscle: federated top-k requires per-shard overfetch; cost-of-overfetch beats cost-of-missed-recall.
      Reapplies at: W108 replica federated search, W104 search recall SLA.

  - **When `merge_steady_state_cpu_under_25pct` reports 80% CPU on merge:**
    - Symptom: merge thread saturates a core; foreground search p99 doubles.
    - Why: merge re-inserts vectors via `MutableSegment::insert` which runs the full HNSW assign-level
      RNG + neighbor selection at full speed; no rate limit.
    - Fix: merge thread runs through a `backpressure::Limiter` set to 25% of one core (e.g., sleep
      adaptively so the integral of CPU stays ≤ 25%). On a `runtime-thread-per-core` runtime, pin merge
      to a low-priority slot.
    - Cost avoided: ~50% foreground p99 regression during merge; ops-friendly.
    - Muscle: background work needs an explicit budget; uncapped reclaim threads always win the CPU race.
      Reapplies at: W26 WAL compaction, W104 merge, W108 replica catch-up.

  - **When `gc_waits_for_inflight_query_arc` deletes the dir despite the paused query:**
    - Symptom: paused query SIGBUSes on next mmap read because GC removed the dir under it.
    - Why: GC check used `Arc::strong_count == 1` but the query thread had cloned the Arc inside its own
      closure; the GC's bookkeeping vector held one ref, the query held another (strong_count = 2), but
      the GC's check incorrectly compared against 0.
    - Fix: GC's bookkeeping holds a `Weak<SealedSegment>` plus the dir path. On each tick, attempt
      `Weak::upgrade` — if it succeeds and `strong_count > 1`, the segment is still live AND others hold
      it. Only when `Weak::upgrade()` returns None (or strong_count is exactly the bookkeeping ref) AND
      grace elapsed do you `remove_dir_all`.
    - Muscle: GC of shared resources keeps Weak refs, not Strong — Strong holds the resource alive
      forever and corrupts the lifecycle. Reapplies at: W107 manifest GC, W108 replica GC.

  - **5-year failure mode** (write in `notes/104_segment_manager_followup.md` after green): when single-node
    write rate exceeds ~50k inserts/sec sustained, the single-active-segment bottleneck reappears (every
    insert contends on the `active` ArcSwap). Migration trigger: per-shard active segments keyed by ID
    hash, federated insert. Name the cross-shard invariant you'd lose (no global insert order; but vector
    DB semantics don't require it).

Test: insert 10k vectors, soft-delete 90%, search; verify recall stays reasonable (not zero results). Implement ACORN second-hop fallback when direct neighbors all filtered. (~180 min)
  - 🔧 **Decomposition prompt**: vector-db v0.5 ships today. The HNSW disconnection failure mode is documented by Qdrant but easy to miss because correctness tests typically don't soft-delete aggressively. Without an adversarial test + ACORN fallback, deployments with high churn (e.g. user-content embedding databases with frequent deletes) silently lose recall.
  - 🎯 **Hardened acceptance**:
    - **Test setup**: insert 10k 128-d vectors; soft-delete 90% (mark deleted, don't remove from graph); search 100 queries; assert recall@10 ≥ 0.5 (well below pre-delete 0.95 but well above 0 which would be the failure).
    - **ACORN fallback impl**: when a search's direct neighbors are ALL soft-deleted, explore second-hop neighbors. Implement as configurable `SearchOptions { acorn_fallback: bool }`; on by default.
    - **Bench**: ACORN-on vs ACORN-off recall + latency. Document: ACORN adds ~2-5× search latency in the high-delete scenario but recovers ~10× recall.
    - **Cited URL**: https://qdrant.tech/documentation/concepts/indexing/ (ACORN search section, v1.16+).
    - **5-year failure mode**: when HNSW alternatives (DiskANN, Vamana) become standard, the disconnection failure mode shifts. Migration: factor ACORN-style fallback out into a generic "tombstone-aware search" trait.
  - **Expect to hit #1 — soft-delete that's actually hard-delete from the graph**: the test "soft-deletes" by removing vectors from the index entirely. Symptom: graph isn't fragmented (just smaller); the test passes trivially because there's nothing to find via second-hop.
    - Fix: soft-delete = mark deleted in payload, keep vector + graph edges intact. Search filters out marked-deleted vectors at result-return time. The graph stays dense; the *filtered-result* density is what drops.
