**Wednesday — vector-db segment manager + v0.5 tag (FINAL)**

- [ ] **Build**: `crates/vector-db/src/segment.rs` — `SegmentManager` orchestrates sealed (immutable, mmap'd) and active (mutable, in-RAM) HNSW segments, federates search across them, and runs a background tiered-merge with crash-safe, GC-safe segment lifecycle. (~total 200 min across 3 phases)
  - 🔧 **Why this matters**: mirrors Qdrant `segment_manager.rs` + Lucene `IndexWriter`/`TieredMergePolicy`. A single mutable HNSW graph degrades with churn — tombstoned deletes can't be reclaimed in place (edges still reference them), incremental updates fragment adjacency, and one graph is a single write-contention point. Segments fix all three: small immutable graphs + background merge + federated search. The four specific traps a first attempt hits: (1) sealing under a write lock stalls inserts (R2), (2) GC frees an mmap dir while a query still holds an `Arc` → SIGBUS/UAF (R8), (3) federated top-k drops globally-relevant results because per-segment k is too small (R3), (4) a crash mid-merge leaves a half-written `.tmp` segment that recovery mistakes for real (R6). First-attempt impls fail ≥1 Phase-2 test below and the debug session IS the lesson. Downstream consumers: W105 ops-monitoring (`SEGMENT_COUNT`/`MERGE_QPS`/`TOMBSTONE_RATIO` gauges read from this struct), W107 capacity planning, W108 chaos drills (mid-merge crash + GC race), W109 runbooks.

  - *Mental model*: `SegmentManager` is the LSM-tree pattern applied to a vector index — append to one small mutable graph, freeze it to an immutable mmap'd snapshot when full, merge small frozen graphs in the background, and answer every query by federating across the live set. Lucene (2002), RocksDB (2013), Qdrant (2021) all converge here because immutable + tiered is the only shape that bounds snapshot cost, reclaims deletes, and parallelizes read vs write.
  - *Contract* (signature-level only — never the body):
    ```rust
    pub struct GlobalId { pub segment_id: u64, pub local_id: u32 }   // (R7) monotone segment_id, never collides
    pub struct SegmentConfig {
        pub max_active_bytes: usize,
        pub merge_min_segments: usize,
        pub merge_size_ratio: f32,
        pub tombstone_merge_ratio: f32,   // (R5) high-tombstone trigger
        pub gc_grace: Duration,           // (R8)
    }
    pub struct SegmentManager { /* active: ArcSwap<MutableSegment>, sealed: ArcSwap<Vec<Arc<SealedSegment>>>, ... */ }
    impl SegmentManager {
        pub fn open(dir: &Path, cfg: SegmentConfig, clock: Clock) -> io::Result<Self>;  // sweeps .tmp on open (R6)
        pub fn insert(&self, id: GlobalId, vec: &[f32]) -> io::Result<()>;              // active only; may seal (R2)
        pub fn search(&self, q: &[f32], k: usize, ef: usize, filter: &Filter) -> Vec<(GlobalId, f32)>; // federated (R3,R4)
        pub fn soft_delete(&self, id: GlobalId);                                        // tombstone, not removal
        // background: seal_active(), merge_tick(), gc_tick()
    }
    ```
  - *Back-of-envelope* (bar (b), correctness-leaning but quantified):
    - Seal cost: `PersistedHnsw::save` of a 1 MB active segment ≈ a 1 MB sequential write ≈ ~50 µs–1 ms on NVMe. If that runs *under the active write lock*, every concurrent inserter waits that long — R2 demands ≤ 1 ms, so the lock must NOT cover the disk write. The fix collapses the critical section to an `ArcSwap::store` ≈ ~50 ns (one atomic + one Arc bump).
    - Federated search: N segments each do an ef-search (~100 µs cold / ~5 µs warm at this scale) → N× the per-segment work, then a global merge of N×k candidates (cheap, k≤100). At N=10 the dominant cost is the 10 parallel-or-serial ef-searches; R4 budget is ≤ 1.5× single (which holds only if you search segments concurrently OR each segment is ~1/N the size).
    - GC race cost: an mmap'd segment dir removed under a live reader = SIGBUS (process death), not a slow path. This is the cliff: correct lifecycle = 0 cost; one missed refcount/grace check = process crash.
  - **Requirements** R1..R9 — write in `notes/104_segment_manager_design.md`:
    - R1. At any instant: exactly ONE mutable `active` + N ≥ 0 immutable `sealed`. Inserts → active only; reads federate across all.
    - R2. When active exceeds `max_active_bytes` it is **sealed atomically**; a new active is installed; the old is persisted via `PersistedHnsw::save`. Concurrent inserts during sealing block ≤ 1 ms (no full write stall).
    - R3. `search(q, k, ef, filter)` returns global top-k across ALL segments via per-segment local top-k + global merge. Recall vs single-graph baseline ≥ 99%.
    - R4. Federated search latency at 10 segments ≤ 1.5× single-segment for the same TOTAL vector count (criterion-verified).
    - R5. Merge runs on a background thread; picks candidates by tiered policy (size ratio + `merge_min_segments`, plus a tombstone-ratio trigger); builds a new sealed segment; atomically swaps the sealed set. Old segments stay live until last reader's Arc drops.
    - R6. A crash mid-merge leaves `.tmp` directories; `open()` sweeps and removes them; old segments remain authoritative. No partial-merge state is ever visible.
    - R7. `GlobalId = (segment_id, local_id)`; local IDs never collide across segments; `segment_id` is globally monotone.
    - R8. Superseded segment dirs are GC'd only after `gc_grace` past the last reader's drop; in-flight queries holding an Arc finish cleanly (no SIGBUS).
    - R9. Merge consumes ≤ 25% of one core in steady state; foreground search p99 regresses ≤ 10% during active merge.
  - **Design walk-through** D1..D9 — answer in the design doc; no peeking at Qdrant `segment_manager.rs` or Lucene `IndexWriter` until Phase 3:
    - **D1. Property table — primitive for `active`** (fill every cell):

      | candidate | read cost | write/swap cost | wait-free read? | seal-without-stall? |
      |---|---|---|---|---|
      | `RwLock<Arc<MutableSegment>>` | read-lock (~25 ns + contention) | write-lock + replace | no (writers block readers) | only if write held briefly |
      | `ArcSwap<MutableSegment>` | `load()` ~few ns, never blocks | `store()` ~atomic | yes | yes — swap is the whole CS |
      | `Mutex<MutableSegment>` | full lock per read | full lock | no | no — serializes inserts |

      Which satisfies R2's "no stall" with the smallest read cost? Argue it.
    - **D2.** `MutableSegment` (in-RAM HNSW, accepts inserts) vs `SealedSegment` (mmap'd `PersistedHnsw`, read-only): what fields differ, and why is sealed mmap while active is in RAM? (read-amplification vs write-amplification.)
    - **D3.** Seal trigger: where in `insert()` do you check `size_bytes > max_active_bytes`? Atomic vs best-effort? What if two inserts trigger seal simultaneously? (Hint: CAS the active pointer; loser observes the new active and retries.)
    - **D4.** Federated top-k: each segment returns its top-k, global merge picks top-k of those. Argue WHY this misses the true global top-k, name the overfetch fix, and the cost it adds.
    - **D5.** Write pseudocode for `pick_merge_candidates(sealed, config)` — tiered by size + a tombstone-ratio override. What triggers a high-tombstone segment to merge even when small?
    - **D6.** Atomic swap of the sealed set: `RwLock<Vec<…>>` with `retain`+push, OR build a new `Vec` and `ArcSwap` the whole vector? Argue from R5 (readers must not block during swap) and R8 (old Arcs stay valid).
    - **D7.** GC of `.tmp` and superseded dirs: when do you delete? (Hint: `Arc::strong_count` alone is a smell — Drop ordering of nested fields races the read; use Weak + a grace timer.)
    - **D8. Pre-mortem (load-bearing) — mid-merge crash:** write the EXACT 6-step interleaving where merge has built `new_segment.tmp` but `kill -9`s before the Arc swap. What does `open()` see? What's the cleanup rule? If you can't write it, you can't prove recovery is correct.
    - **D9. Pre-mortem (load-bearing) — GC/query race:** write the EXACT 5-line interleaving: (1) query T1 clones `Arc<SealedSegment>` for S, (2) merge T2 removes S from the sealed vector, (3) GC T3 `remove_dir_all(S.dir)` while T1 still mmap-reads `vectors.bin`. Show why GC must gate on refcount AND grace — refcount alone is racy because `Drop` runs AFTER the last read returns.
    - **Anti-shortcut audit** (name the obvious reach + why it's wrong HERE):
      - "Just use `RwLock<Arc<MutableSegment>>` for active" — every insert pays read-lock contention; under seal the write lock would have to cover the disk save → R2 stall. Wrong.
      - "Just `Vec::retain` + push under a `Mutex<Vec<Arc<SealedSegment>>>` for the swap" — readers iterating the vec block on the merge's mutation. Wrong; `ArcSwap<Vec<Arc<…>>>` gives wait-free reads.
      - "GC when `Arc::strong_count == 1`" — Drop of nested mmap field runs after the last read; strong_count==1 can be the bookkeeping ref while a query still has a clone. Wrong; use Weak + grace.
      - "Per-segment top-k = global k" — drops items ranked k+1 locally that are top-k globally. Wrong; overfetch.

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  Ordered failure cards, newbie failures first, expert last.

  - **(NEWBIE) When `insert_seals_when_active_exceeds_size` reports 0 sealed segments after 1.5 MB inserted:**
    - Symptom: active grew unboundedly; no seal ever fired.
    - Why: `insert()` never checked `size_bytes() > max_active_bytes`, or checked a stale cached size.
    - Fix: after each insert, compare live `active.load().size_bytes()` to `cfg.max_active_bytes`; if over, call `seal_active()`.
    - Muscle: a "freeze when full" policy needs the size check on the hot path, computed from live state, not a cached counter. Reapplies at: W26 WAL rollover, W31 mmap-queue segment roll, W112 mini-db memtable flush trigger.

  - **(NEWBIE) When `global_id_no_collision_across_segments` finds duplicate GlobalIds:**
    - Symptom: two vectors in different segments share `(segment_id, local_id)`.
    - Why: `local_id` reset to 0 per segment but `segment_id` wasn't bumped on seal (or was reused), so the pair repeats.
    - Fix: `segment_id` is a globally monotone counter bumped on every seal; `GlobalId` = `(that_id, per_segment_local)`. Never reuse a `segment_id`.
    - Muscle: globally-unique composite IDs need a monotone high part — never reset both halves. Reapplies at: W107 manifest version IDs, W112 mini-db SSTable IDs.

  - **(SENIOR) When `concurrent_insert_during_seal_blocks_under_1ms` reports ~50 ms blocked:**
    - Symptom: an inserter blocks ~50 ms while seal copies the whole HNSW graph into the persist pipeline under a lock.
    - Why: `seal_active()` held the active write lock for the duration of `PersistedHnsw::save` — a multi-µs-to-ms disk write — and inserters wait on that lock.
    - Fix: split seal into two phases — (1) inside the critical section, `ArcSwap::store` a fresh `MutableSegment` and capture the OLD as a local `Arc`; (2) OUTSIDE the lock, `PersistedHnsw::save(old)` then `ArcSwap`-append it to `sealed`. Inserters block only for the ~50 ns swap.
    - Cost avoided: ~50 ms × every concurrent inserter of stall; collapses to ~50 ns critical section.
    - Muscle: minimize the critical section — hand off ownership *inside* the lock, do the expensive work *outside*. Reapplies at: W26 WAL fsync-outside-lock, W74 raft snapshot install, W107 manifest swap.

  - **(SENIOR) When `federated_search_recall_within_1pct_of_single` reports recall 0.91 vs single 0.95:**
    - Symptom: 4% recall regression after segmentation; items ranked #11 in a local segment but #4 globally are lost.
    - Why: federation fetched only top-k per segment; an item that's local #(k+1) but global top-k is never surfaced to the global merge.
    - Fix: each segment fetches `top-(k × fanout)` (`fanout` defaults to 2); the global merge picks top-k of the overfetched candidates.
    - Cost avoided: ~4% recall loss (SLA breach); costs ~2× per-segment candidate work, but only the small global merge runs across all segments.
    - Muscle: federated top-k requires per-shard overfetch; cost-of-overfetch beats cost-of-missed-recall. Reapplies at: W108 replica federated search, W112 mini-db merged-iterator k-way merge bound.

  - **(SENIOR) When `tombstone_ratio_triggers_merge` never fires a merge:**
    - Symptom: a segment 40% tombstoned but small in bytes is never picked for merge; reclaim never happens.
    - Why: `pick_merge_candidates` keyed only on size tiers; tombstones don't inflate byte size, so the small dead-heavy segment is invisible to the policy.
    - Fix: add a tombstone-ratio override — if `segment.tombstone_ratio() > cfg.tombstone_merge_ratio`, force-elect it regardless of size tier.
    - Muscle: merge policy must trigger on *both* size and dead-fraction; size alone never reclaims a small, mostly-deleted segment. Reapplies at: W26 WAL compaction by garbage ratio, W112 mini-db TWCS/LCS dead-key trigger.

  - **(SENIOR) When `merge_swap_atomic_no_query_panic` panics with `Arc strong_count was 0` / miri reports UAF:**
    - Symptom: a query holding `Arc<SealedSegment>` SIGBUSes/panics reading `persisted.search()` because the mmap was unmapped mid-read.
    - Why: GC dropped the `Arc` and immediately `remove_dir_all`'d its dir; the SealedSegment's `Drop` (which unmaps) runs after the last Arc release, but the dir was already gone — and GC ran before the swap committed, so a query still held a logical ref.
    - Fix: two-stage commit — on swap, push `(Arc<SealedSegment>, queued_at)` into a `to_gc` queue; a separate `gc_tick` removes the dir ONLY when the segment has no live external Arc AND grace elapsed (see next card for the refcount mechanics). Never `remove_dir_all` while any other Arc exists.
    - Cost avoided: process death (SIGBUS) — not a slow path, a hard crash under every concurrent reader.
    - Muscle: GC of mmap-backed resources needs refcount AND a grace timer; refcount alone races `Drop` ordering of nested mmap fields. Reapplies at: W107 manifest version GC, W108 replica file lifecycle, W112 mini-db obsolete-SSTable deletion.

  - **(EXPERT) When `gc_grace_period_holds_old_dir` removes the dir immediately after swap (grace ignored):**
    - Symptom: dir gone the instant the swap commits; in-flight queries that started just before the swap can still SIGBUS.
    - Why: `gc_tick` deleted on `strong_count == 1` with no time gate; a query that loaded the old sealed set microseconds before the swap is mid-flight.
    - Fix: gate deletion on `now - queued_at > cfg.gc_grace` in addition to the refcount check; drive `now` from the injected `Clock` so the test can advance it.
    - Cost avoided: a rare-but-fatal SIGBUS window equal to max in-flight query duration.
    - Muscle: refcount answers "who holds it now"; grace answers "could someone have just grabbed it" — you need both. Reapplies at: W107 manifest GC grace, W108 replica retention window.

  - **(EXPERT) When `gc_waits_for_inflight_query_arc` deletes the dir despite the paused query (refcount mis-counted):**
    - Symptom: paused query SIGBUSes on next mmap read; GC removed the dir while the query's Arc was live.
    - Why: GC's bookkeeping held a *Strong* `Arc`, so `strong_count` was inflated by GC itself (bookkeeping ref + query ref + ...); the equality check `== 1` compared against the wrong baseline and mis-decided "nobody's using it."
    - Fix: GC bookkeeping holds a `Weak<SealedSegment>` + dir path. On each tick, `Weak::upgrade()`: if it returns `None`, no one holds it → if grace elapsed, `remove_dir_all`. If it upgrades, someone is still using it → skip. A Weak never inflates the strong count.
    - Cost avoided: SIGBUS under a paused/slow reader; also avoids the subtler bug where GC's own Strong ref keeps the segment alive forever (dir never reclaimed).
    - Muscle: GC of shared resources keeps **Weak** refs, not Strong — a Strong bookkeeping ref both corrupts the count and pins the resource. Reapplies at: W107 manifest GC, W108 replica GC, W112 mini-db SSTable cache eviction.

  - **(EXPERT) When `mid_merge_crash_recovers_clean` errors with `Err(CrcMismatch)` on open:**
    - Symptom: after kill-9 mid-merge, `open()` loads the half-written `.tmp` dir, mistakes its partial `header.bin` for a real segment, returns `CrcMismatch`.
    - Why: recovery walked every subdir under `segments/` assuming all are segments; the `.tmp` suffix wasn't filtered, and merge wrote in-place rather than to a `.tmp` staging dir.
    - Fix: merge builds into `<id>.tmp`, renames to `<id>` only on swap success. `open()` first sweeps (`remove_dir_all` best-effort) every `*.tmp` entry, THEN loads only entries whose `header.bin` parses + CRC verifies.
    - Cost avoided: a crash that bricks startup (DB won't open) vs clean self-heal.
    - Muscle: "in-progress = `.tmp` suffix; recovery sweeps before it loads" is the cheapest crash-safe convention. Reapplies at: W107 manifest crash recovery, W108 chaos crash drills, W112 mini-db compaction crash.

  - **(EXPERT) When `merge_steady_state_cpu_under_25pct` reports 80% CPU (and search p99 doubles):**
    - Symptom: merge thread saturates a core; foreground search p99 ~2×.
    - Why: merge re-inserts via `MutableSegment::insert` at full speed (full HNSW level-RNG + neighbor selection), with no rate limit; it wins the CPU race against foreground.
    - Fix: run merge through a `backpressure::Limiter` budgeted to 25% of one core (adaptive sleep so the CPU integral stays ≤ 25%); on a `runtime-thread-per-core` runtime, pin merge to a low-priority slot.
    - Cost avoided: ~50% foreground p99 regression during merge.
    - Muscle: background reclaim work needs an explicit CPU budget; an uncapped reclaim thread always wins the scheduler race. Reapplies at: W26 WAL compaction throttle, W108 replica catch-up throttle, W112 mini-db compaction rate limit.

  - **(EXPERT) When `federated_search_latency_within_1_5x` reports 4× (or the result lands outside the plausible band):**
    - Symptom: either 10-segment p50 is ~4× single (too slow), or p50 reads as ~5 ns (DCE'd — outside the [3 µs, 5 ms] band).
    - Why (slow): segments searched serially with full per-segment `ef` each → N× work. Why (DCE): the search result wasn't `black_box`'d so the optimizer hoisted it away.
    - Fix (slow): search segments concurrently (or scale `ef` per segment by ~1/N since each holds ~1/N the vectors); merge results once. Fix (DCE): `black_box(query)` AND `black_box(results)`.
    - Muscle: a federated latency budget needs per-shard work to shrink as shards grow; a bench needs both inputs and outputs black-boxed or it measures nothing. Reapplies at: W108 replica fan-out latency, W105 ops bench harness, W112 mini-db range-scan fan-in.

- [ ] **Extend**: `crates/vector-db/src/segment.rs` + `crates/vector-db/tests/hnsw_disconnection.rs` — ACORN tombstone-aware second-hop search: when a node's direct neighbors are ALL soft-deleted, explore second-hop neighbors so high-churn graphs don't silently lose recall. (~total 120 min across 3 phases)
  - 🔧 **Why this matters**: mirrors Qdrant's ACORN tombstone-aware search (docs v1.16+, https://qdrant.tech/documentation/concepts/indexing/). This is a genuine DELTA on top of the SegmentManager Build, not a rebuild: SegmentManager owns lifecycle; ACORN changes only the *traversal* when filters/tombstones starve a node's neighborhood. Qdrant documents this failure mode but it's easy to miss because correctness tests rarely soft-delete aggressively. Without it, high-churn deployments (user-content embedding DBs with frequent deletes) silently lose recall as graphs fragment. The single named trap: a "soft-delete" that actually hard-removes from the graph never fragments anything, so the test passes trivially and proves nothing. Downstream: W108 chaos drill (high-delete fault scenario), W115 blog cites it.
  - *Mental model*: HNSW recall depends on the greedy walk finding live neighbors at each hop. Tombstones don't remove edges (you can't reclaim in-place), so a node whose every direct neighbor is tombstoned becomes a recall dead-end — ACORN routes through the dead neighbors to their live second-hop neighbors, paying latency to recover recall.

  #### Phase 1 — Problem, prediction, design (~30 min, no code yet)
  - 🎯 **Pre-prediction prompt** — `notes/104_acorn_prediction.md`:
    - **P1**: predict recall@10 after soft-deleting 90% of a 10k graph with naive (direct-neighbor-only) search — write a number.
    - **P2**: predict the latency multiplier ACORN adds in the 90%-deleted scenario — write a number.
    - **P3** (load-bearing): if your "soft-delete" removes the vector from the graph entirely, what does the test prove? (Answer: nothing — that's the negative-control trap.)
  - *Contract*: `pub struct SearchOptions { pub acorn_fallback: bool /* default true */ }`; `search(q, k, ef, filter, opts)` — when expanding a frontier node whose live neighbors are empty after filtering, expand the tombstoned neighbors' neighbors (second hop) before giving up.
  - *Back-of-envelope*: at 90% tombstoned, ~90% of any node's neighbors are dead; direct-only search hits dead-ends and returns near-empty → recall ≈ 0. Second-hop multiplies the per-node expansion by ~M (16) in the worst neighborhood → ~2–5× search latency, recovering ~10× recall.
  - **Requirements** — `notes/104_acorn_design.md`: A1. soft-delete = mark deleted in payload, KEEP vector + edges. A2. results filter out tombstoned at return time. A3. when a frontier node's live neighbors are empty, traverse dead neighbors to their live second-hop. A4. `acorn_fallback: bool`, on by default. A5. recall@10 after 90% soft-delete ≥ 0.5 (vs ~0.95 pre-delete, vs ~0 without ACORN).
  - **Output**: `notes/104_acorn_design.md` with A1–A5 + the dead-end interleaving (frontier node → all neighbors tombstoned → second-hop recovery).
