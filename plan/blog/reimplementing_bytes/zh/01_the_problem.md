# 第 1 部分——一个字节从网线到程序的旅程

我们从一个很普通的程序说起：一个正在运行的以太坊节点。它打开一个 socket，而在另一端，全世
界都在往里送数据——新区块、交易、节点之间的消息。这个节点在最底层的工作，就是把这些字节读进
来，弄懂它们，然后要么存下来，要么转发给别的节点。

听着简单，但就在"把字节读进来"这一步，就藏着这整个系列都围绕着转的一个问题。我们会走得很
慢，因为后面的一切都从这里长出来。

## 字节不会整整齐齐地到达

当你从一个 socket 读数据时，数据不会以一个长度已知的漂亮整块到来。它是一小口一小口来的
——有时 40 字节，有时 1500 字节，看网络而定。一条完整的消息——比如一个区块头——可能得从五
六次这样的读取里拼起来。而且**在你几乎读完之前，你并不知道**这条消息有多长。

所以你需要一个地方来接：一块内存区域，你不停往里追加字节，它满了就**自己长大**。在 Rust 标
准库里，最接近的东西是 `Vec<u8>`——一个能增长的字节数组。你 `push` 字节进去，空间用完了它
就自动申请更多内存。

在这个系列里，我们把这个可写的"接收缓冲区"叫作 **`BytesMut`**（`Mut` 取自 *mutable*——可
变）。你可以把它大致想成一个 `Vec<u8>`：一个指向堆（heap）上某块内存的指针，外加两个数
字——已经写了多少字节（`len`），以及这块内存当前能容纳多少（`cap`，*capacity* 的缩写）。

```
BytesMut 正在接一个区块头，写了 7 字节，内存容量 1024：

   指针 ──────────► [ 68 65 61 64 65 72 21 · · · · · · · · ]
                    └─ 已写 7 字节 ─┘└─ 剩下的空位 ─┘
   len = 7
   cap = 1024
```

`BytesMut` 的关键点：它**可写**，而且它**会增长**。当你还在从 socket 读一条消息时，这正是
你需要的。

## 但一旦读完，`BytesMut` 反倒碍事了

假设消息已经读完了。现在你想拿它做什么？

- 交给解码器（decoder）去弄懂内容，
- 放进缓存（cache）待会儿查，
- 转发给另一个节点。

而且通常是**三件同时做**：同一个区块头，解码器留一份去解析，缓存留一份，发送队列留一份。

这时 `BytesMut` 变得碍事，有两个原因。

第一，它**可写**。消息一旦完整，我们*不想*再有人去改它。如果解码器和缓存都拿着同一个
`BytesMut`，其中一个不小心覆盖了它，另一个就读到坏数据。不可变（immutable）的数据是安全共
享的前提：没人能写，那么多个读者就永远不会撞车。

第二，让很多地方都拿着同一个 `BytesMut` 是**昂贵的**。`BytesMut` 拥有它的内存；要给三个地
方，唯一安全的办法是拷贝三份。而拷贝是有代价的——代价多大，本部分末尾就会看到。

换句话说，`BytesMut` 擅长*搭建*一条消息，却不擅长*共享*一条已经搭好的消息。

## `Bytes`：那个只读、可共享的句柄

所以我们需要第二个类型，用于后面这个阶段：消息已经做好，只需要被读取、被到处传递。我们把它
叫作 **`Bytes`**（没有 `Mut`——不可改）。

`Bytes` 是指向一堆字节的一个*只读句柄*。它具备我们需要的三个性质：

- **不可变**——没人能通过 `Bytes` 写入，所以共享是安全的；
- **克隆廉价**——多加一个持有它的地方几乎是免费的，不拷贝内容；
- **自我清理**——当最后一个持有它的地方放手时，内存自动被释放。

而把一个（做好的）`BytesMut` 变成一个（可共享的）`Bytes` 的那个操作，有个名字：**`freeze`
**——"冻结"。你停止写入，把缓冲区冻起来，从此它就只能被读。

```
   BytesMut  ──freeze──►  Bytes
   （可写，                （只读，
    正在搭建）              可共享）
```

一条入站消息的整个生命，画出来就是：

```
socket ──► BytesMut ──► freeze ──► Bytes ──► 解码器 / 缓存 / 转发
          （接收 &        （冻结）    （到处传递）
           增长）
```

现在我们有足够的词汇来问那个核心问题了。

## `freeze` 内部在做什么，以及它为什么可能非常慢

`freeze` 听起来像个无关痛痒的操作——只是把一个缓冲区从可写"改个标签"成只读。但整个接收路径
的性能就是在这里决定的，原因很简单：**每一条入站消息都要经过它。** 一个繁忙的节点每秒
`freeze` 几十万、几百万次。

问题是：`freeze` 运行时，它是否必须把缓冲区内容*拷贝*到一个新地方？

最朴素的实现**必须**。它分配一块新内存，把 `BytesMut` 里的每个字节拷贝过去，返回一个指向新
内存的 `Bytes`。我们来算算这次拷贝的代价。

假设一个区块头突发（burst）大约 1 MiB。现代硬件上内存拷贝（memcpy）的速度约 5 GiB/s。那么
拷贝 1 MiB 需要：

```
1 MiB ÷ 5 GiB/s ≈ 200 微秒
```

200 微秒听着不多，但那是 **CPU 干等着的 200 微秒**，除了把字节从一处搬到另一处什么也没干
——而且只是*一次* `freeze`。乘以每秒的消息数，你的节点就把相当一部分时间烧在了*重新拷贝*它
刚刚才读进来的数据上。

对于一个吞吐量就是一切的系统，每次 `freeze` 一次拷贝不是"还没优化"——它直接把这个设计踢出局。
所以我们立下一条硬性要求，而这整个系列就是为了守住它要付出什么代价的故事：

> `freeze` 必须在**常数**时间内完成，无论缓冲区多大。装着 payload 的那块内存**不能移动**；
> 唯一允许转移的是它的*所有权*——从 `BytesMut` 转到 `Bytes`。

"不移动内存，只转移所有权"是我们在剩下篇幅里要挖的思路。但在动手搭建之前，值得先问：为什么最
显而易见的做法*做不到*这一点？因为回答这个问题能揭示真正的问题在哪里。

## 尝试 #1：`Bytes` 包一个 `Vec<u8>`

第一个想法：`freeze` 干脆把缓冲区直接以 `Vec<u8>` 的形式返回。

这*确实*避开了拷贝——`Vec<u8>` 和 `BytesMut` 都是堆上一整块平坦的内存，所以 `Vec` 可以
"接管" `BytesMut` 的内存而不重新拷贝。在拷贝这件事上它成了。但它在另外两处坏掉，而正是这两处
塑造了后面的一切。

第一，`Vec<u8>` **可写**。我们又回到了 `BytesMut` 的问题：不保证内容不可变，所以无法安全共
享。

第二，`Vec<u8>` **克隆不廉价**。`Vec::clone()` 会拷贝整个内容。而"多个地方持有它"是家常便
饭。如果每一次"也持有"都是一次 memcpy，那我们只是把拷贝从 `freeze` *挪*到了 `clone`——并没
有把它杀掉。

尝试 #1 的教训：我们需要一个同时**不可变**、**克隆廉价**、且**能接管现有内存**的类型。这三
个性质就是给后面每个候选方案打分的标尺。

## 尝试 #2：`Bytes` 包一个 `Arc<[u8]>`

这几乎是每个 Rust 程序员的第二反射，也是很多现实设计的起点。

`Arc`（*Atomically Reference-Counted*，原子引用计数）是 Rust 处理"多个地方共同拥有一份数
据"的标准工具。它内部维护一个 **counter**（计数器），记录当前有多少地方持有。每次 `clone`
计数器加一；每当一份被丢弃，计数器减一；计数器归零时，数据自我释放。`Arc<[u8]>` 意思是"一个
字节数组，带引用计数"。

```rust
struct Bytes(Arc<[u8]>);
```

这立刻给了我们**三分之二**的必需性质：

- **不可变**——`Arc<[u8]>` 只出借一个只读视图，没人能写；
- **克隆廉价**——`clone` 只把计数器加一，不拷贝内容。这正是我们需要的"多个地方持有一条消
  息"。

而且它**能用**。最初的方案正是从这个设计起步的。问题只在第三个性质上才浮现——`freeze` 不能
拷贝——而要看清它为什么坏掉，得去看*内存的布局*。

### 为什么 `Arc<[u8]>` 在 `freeze` 时被迫拷贝

`Arc<[u8]>` 是**单独一块**内存，其中 counter 就*紧贴*在字节前面**融为一体**：

```
Arc<[u8]>:   [ counter | b0 b1 b2 ... bN ]
             └─ 头部 ──┘└──── payload ────┘
                单独一块
```

而 `BytesMut` 的缓冲区只有 payload，前面**没有 counter**：

```
BytesMut:    [ b0 b1 b2 ... bN ]
             └──── payload ────┘
```

这两种布局形状不同，永远对不上。要把 `BytesMut` 的缓冲区变成一个 `Arc<[u8]>`，你就得把
counter 放到当前指针*正前方*。但正前方那块内存**不属于你**——分配器（allocator）从没把它交
给你，往那儿写就会踩到程序的另一部分。你没法给一个已经分配好的块"事后补装"一个头部。

所以 `Arc::from(vec)` **被迫**：

1. 向分配器要一块 `counter + N` 大小的*新*块；
2. 把 N 个 payload 字节从旧缓冲区拷到新块；
3. 释放旧缓冲区。

第 2 步就是我们发誓要杀掉的 memcpy。而关键在于：它**不是代码 bug**，而是 `Arc<[u8]>` 这个
*形状*的必然后果。`Arc<[u8]>` 只懂一种拥有方式——引用计数——而这种方式要求 counter 活在与
payload *同一块*内存里。一个 counter 与 payload 融为一体的类型，**无法接管**一个已经分配在
别处的 payload。

用一句话概括，这是整个系列的枢纽：

> `Arc<[u8]>` 无法*接管*一块已有的内存区域。把字节放进 `Arc<[u8]>` 的唯一办法，是分配一块
> 新的再拷进去。但我们要的恰恰相反：一个直接指向*别人*内存的句柄（这里是 `BytesMut` 的缓冲
> 区），并接手清理它的责任。

## 当句柄指向"别人的内存"时，什么问题浮现了

一旦我们接受"一个句柄指向一块现有缓冲区"这个想法，一个新问题就冒出来了——一个 `Arc<[u8]>`
从来不必回答的问题。

`Arc<[u8]>` 永远知道一份被丢弃时该怎么办：减 counter，到零就释放。永远如此，没有例外——因为
它只有一种拥有方式。但一个自由指向的句柄，可能指向三种命运截然相反的内存：

- 它指向**编译进可执行文件里的一个常量**（比如程序里一个硬编码的字节串）。这块区域从没被分
  配过；放手时我们**什么都不能做**——释放它就是在释放我们并不拥有的内存。
- 它指向一个**刚从 `BytesMut` 接管来的缓冲区**。这块区域*被*分配过，且恰好有一个句柄拥有
  它；放手时我们必须释放。
- 它指向一个**被多处共享的区域**。这时需要一个 counter；谁最后放手，谁来释放。

这就是整个问题的核心矛盾，第一次被说出口：

> 同一个 `Bytes` 类型，却有三种不同的清理方式，而哪一种适用，只有在运行时、针对每一个具体的
> 值，才知道。

`Arc<[u8]>` 靠只支持*一种*清理纪律来绕开这个矛盾（代价是 `freeze` 的 memcpy）。我们没得绕：
我们需要三种全都*在一个类型里*——为了有零拷贝的 `freeze`（"独占"纪律）、廉价的 `clone`
（"共享"纪律），以及为固定字节常量不付任何代价（"static"纪律，用于硬编码的字节串，比如创世
常量或预编译合约的字节码）。

## 为什么不能干脆用三个独立类型

到这里你也许会想："那就做三个独立类型——`StaticBytes`、`OwnedBytes`、`SharedBytes`，各管
一种清理，让编译器去处理。"

就所有权而言，这其实是*正确*的做法——而且第 2 部分会看到，Rust 通常*希望*你正是这么干。它死
于一个完全不同的原因：**API 边界**。

看一个典型的消费字节的函数：

```rust
fn decode(data: Bytes) -> Header;
```

这个 `decode`——以及成百上千个像它一样的函数——必须*不管字节来自何处*都能吞下。如果有三个独
立类型：

- 你得把 `decode` 写三遍（或者把每个消费字节的函数都泛型化——数量爆炸）；
- 一个 `Vec<Bytes>` 装不下三种的混合；
- 一个在线程间发送 `Bytes` 的 channel 发不了混合；
- 一个带 `Bytes` 字段的结构体只能硬选三种之一，失去所有灵活性。

`Bytes` 底下的整套基础设施都隐含地假定只有**一个**类型。"一个类型"这条约束不是我们为了好玩
强加的——它来自*使用* `Bytes` 的那些代码。

而陷阱在于：一个类型意味着一个清理函数（`Drop`），也就是一个*固定*行为。而我们刚刚证明了需要
*三种*行为，在运行时按值挑选。"一个类型（由 API 强制）"与"三种清理（由零拷贝-freeze 加廉价
-clone 加免费常量强制）"之间的矛盾——这才是真正的问题。

## 那么第 2 部分要解决什么

总结一下，我们有三个方案，以及它们各自死掉的原因：

- `Vec<u8>`：做到了零拷贝 freeze，但不可变、且克隆要拷贝。
- `Arc<[u8]>`：不可变且克隆廉价，但 freeze 被迫 memcpy，因为 counter 与 payload 融为一
  体。
- 三个独立类型：做到了全部三种清理，但 API 边界要求单一类型。

浓缩成一个问题，这就是第 2 部分必须回答的：

> 怎样让单一的 `Bytes` 类型承载三种不同的清理行为，在运行时按值挑对——而读字节仍然像
> `Arc<[u8]>` 一样廉价？

"一个类型、多种行为、运行时挑选"这句话应该听着耳熟：这正是*动态分派（dynamic dispatch）*为
之而生的问题。第 2 部分会展示怎么正确地用它，以及一个同样重要的附带问题——为什么我们要搭的那
张分派表（vtable）恰好有*两个*槽，不多也不少。
