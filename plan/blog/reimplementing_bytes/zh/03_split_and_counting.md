# 第 3 部分——把"哪些字节"和"谁拥有"分开

第 2 部分留下一笔债。我们有了让一个 `Bytes` 类型承载三种清理的机制，却没回答那条要求的后一
半：读字节必须*快*。一个 `Bytes` 现在有四个字段——指针、长度、`data`、`vtable`——比只有一个
指针的 `Arc<[u8]>` 多得多。这"多"会不会让读变慢？

答案是不会，而*为什么*不会，是整个设计里最漂亮的想法。它也是让这个设计*胜过*一种更显而易见的
做法（我们会在末尾对比）的原因。

## 一个句柄回答两个毫不相干的问题

再看一遍 `Bytes`，注意它的四个字段其实分成两组，回答两个完全独立的问题。

第一个问题：*哪些字节？*——它们在哪儿，多长。由指针和长度回答。

第二个问题：*谁拥有？*——克隆或放手时要做什么。由 `data` 和 `vtable` 回答。

```rust
struct Bytes {
    ptr:    /* 指针 */,       // ┐ "哪些字节"
    len:    /* 长度 */,       // ┘
    data:   /* 8 个额外字节 */,// ┐ "谁拥有"
    vtable: /* 表指针 */,     // ┘
}
```

关键在于：字节内容*永远*只是一段裸字节，无论它来自常量、独占区域还是共享区域。没有什么"隐藏的
形状"需要以后去发现。所以指针和长度*完整地*回答了第一个问题，而第一个问题*永远不需要*第二个问
题的答案。

反过来则不对称：`clone` 和 `drop` 需要 `data`/`vtable`，但它们*也*需要指针和长度（去造新句
柄、去释放正确的地址）。所以"谁拥有"这组要读两组；而"哪些字节"这组只读它自己那组。正是这个不
对称是我们要利用的地方。

一个比方：指针和长度就像一本书的*书架位置和页数*。`data` 和 `vtable` 就像贴在封底的*借阅
卡*：谁借了这一本，归还时怎么处理。借阅卡不告诉你书里写了什么——而你读完整本书，一次都不用瞥那
张卡。

## 于是读就免费了

直接的后果：每个读操作——取内容、取长度、比较、哈希、打印——都只碰指针和长度。不查 `vtable`。
不按拥有种类分支。不碰 counter。取内容无非是"从这个指针，读这么多字节"——一行，而且*正是*
`Arc<[u8]>` 也编译成的样子。

这就是读之所以廉价的全部原因。新加的两个字段（`data`、`vtable`）在热路径上不花一分钱，只因为
热路径只读，而读的时候这两个字段是隐形的。灵活性的代价——一个类型背三种清理——被*全部*倒进
`clone` 和 `drop`，两个很少运行的*冷*操作；而它*不渗*进读，那个一直在跑的*热*操作。

这是一条到处都能用的设计原则，不只对 `Bytes`：当你为灵活性加状态时，把布局安排成让那份状态坐
在*热路径之外*。如果热路径被迫*去看*新状态——哪怕只是一次分支——那灵活性就把它的代价渗进了最贵
的地方。

## 为什么不干脆用一个 `enum`

到这里很多人会问：既然 Rust 有 `enum` 来表示"三者之一"，何必费劲搞 vtable 和函数指针？

```rust
enum Bytes {
    Static { /* ... */ },
    Owned  { /* ... */ },
    Shared { /* ... */ },
}
```

这条路是*对的*。它甚至*更安全*（不用写 `unsafe` 代码）。那真正的设计为什么不选它？

因为一个 `enum` 把那个区分用的标签（"谁拥有"问题）和数据（"哪些字节"问题）*放在一起*。每次
读，你都得对那个标签 `match`——一次分支——才能把指针和长度取出来，*尽管读字节和标签毫无关系*。
你在*每一次*问"哪些字节"时都为"谁拥有"买单。

而用我们这种扁平布局——指针和长度对三种方式都在同一个固定位置——读就直接取出来，没有分支。
`vtable` 指针则搁在一边，只被 `clone` 和 `drop` 碰。

这里的取舍是真实的，值得直说：选扁平布局意味着你放弃 `enum` 的静态安全（你写 `unsafe` 代码，
并亲手维护"`data` 必须与 `vtable` 匹配"这条不变式），换来无分支的读。对一个读操作在热循环里被
反复调用的类型，这个交换是值的。对一个很少读的类型，`enum` 才是正确的选择。知道自己在这个谱系
上处于哪里，是设计功力的一部分——不是任何时候"更快"都赢。

## 支撑性的思维方式：数释放次数

现在转到"谁拥有"这组，为两个最难的部分打地基。三种拥有方式听着不同，但它们其实只是对*同一个*
问题的三种回答：

> 这块内存被释放（`dealloc`）恰好几次，由谁来释放？

- 常量：释放 **0** 次。它从没被分配过；没借过的东西，还给谁。
- 独占区域：释放 **1** 次，由句柄自己在放手时释放。
- 共享区域：释放 **1** 次，由*最后一个*句柄在 counter 归零时释放。

正确的数字永远如上。而这正是把这个问题从口号变成工具的地方：*这个设计里的每一个 bug，都归结为
把这个数字数错了。* 该是 1 却数成 **0**，是内存泄漏。该是 1 却数成 **2**，是 double-free 或
use-after-free。贯穿第 4、5 部分，每当你拿不准"这里对不对"，你只需问：*对这块确切的内存，我
刚刚把那个数字弄成几了？*

从这个思维方式，两件要紧的事浮现出来。

## `Drop` 不清理结构体——它撤销一次分配

再看 `Bytes` 的四个字段：一个指针、一个数字、`data`（指针或数字）、`vtable`（一个静态引
用）。*没有一个字段拥有任何东西。* 你要是把 `impl Drop for Bytes` 块整个删掉，放手一个
`Bytes` 本来就已经是一次完美的空操作——结构体自己从栈上消失，不用谁帮忙。

那 `Drop` 存在是为了什么？*只*为了归还结构体所指向的那块堆内存。直觉常在这里出错：`Drop` 不是
用来"清理值本身"的——值会自己溶解。`Drop` 存在，唯一目的就是*撤销一次先前的分配*。要是从没分配
过，那就没什么可撤销。

这正是为什么常量的 `drop` 函数是一个*空*函数，而这个空是*对的*。一个字节常量从没被分配过，所
以它必须被释放 0 次，所以它的清理函数什么都不做。换句话说：没分配，就没 `Drop`。泄漏一个常量是
*对的*——不管你做什么，它都活整个程序那么久。

## 沉默的陷阱：关于 unsafe 代码最大的一课

独占区域的释放函数必须归还恰好*分配*了那么多字节，而不是*写入*了那么多。回想第 1 部分：一个
`BytesMut` 可能分配了 1024 字节，却只写了 7 个。释放时，分配器要回它当初给出的那个确切的
1024 字节的块——它按*分配的大小*匹配，不是按内容。

如果你不小心按写入的字节数（7）而不是分配的（1024）来归还，会怎样？

在 Linux 和 macOS 上，最终的释放会调到 C 的 `free(ptr)`——它只收*一个*参数，就是指针；它从
藏在块正前方的元数据里查出大小，然后*丢弃*你传进去的大小。结果：程序**不崩溃**。测试全过。跑
一千万次都过。在生产上跑两年都过。

但它是未定义行为（undefined behavior）。释放的契约要求释放时的大小等于分配时的大小。它爆炸的
那一天，是有人把默认分配器换成别的那一天——比如 `jemalloc` 或 `mimalloc`，这类分配器*信任*你
传的大小，用它来选桶（bucket）。它把那个 1024 字节的块归还进了 8 字节块的桶里；几千次分配之
后，程序的两个部分往同一块内存里写；于是你在一个完全不相干的地方得到堆损坏（heap
corruption），无从追查。

这是关于 unsafe 代码最该刻进脑子的一课，而且它与直觉相反：

> unsafe Rust 里可怕的 bug，不是那个崩溃的，而是那个*正确运行*的。来自安全 Rust 的直觉——"错
> 了就立刻 panic"——在这里被反转了：错误的默认状态是*沉默*。

抓住它的工具是 `miri`——一个不执行真正 `free`、而是*检查契约*的解释器：它记住分配时的大小，在
释放时比对，一旦不符就立刻在正确的那一行喊"incorrect layout on deallocation"。这也是为什么
任何身兼两职的字段——比如 `data`，一会儿是数字一会儿是指针——都必须就地注释、并用测试验证：错误
在运行时不会自己显形。

## 三种"简单"行为自己掉出来了

拿着"数释放次数"这个思维方式，四种行为里有三种自己浮现出来——而且妙就妙在*一点多线程都还没
碰*。这就是为什么你先把它们搭好；第 4、5 部分才是难的。

对**常量**，释放 0 次。造一个常量 `Bytes` 无非是造一个指向现有字节串的句柄，把 `vtable` 设
成常量表，`data` 留空。它的清理函数是空的。搞定。

对**独占区域**，这里我们终于杀掉第 1 部分的 memcpy。我们想让内存被释放 1 次，不是 2 次。问题
在于：旧的 `BytesMut` 被销毁时*会*释放内存（它有自己的清理）；然后新的 `Bytes` *也会*释放。
那就是 2——一次 double-free。要变成 1，我们必须不让 `BytesMut` 执行它的清理。

Rust 为此有个工具：`mem::forget`。名字听着像"删掉一个变量"，但它其实是一句声明：

> "我已经把这块内存交给别人了。别再执行我的清理。"

这正是零拷贝交接的*定义*：接收方接管发送方的内存（不拷贝），而一块内存恰好有一个清理者。缓冲区
本身纹丝不动；只是*释放它的责任*从 `BytesMut` 转到了 `Bytes`。所以 `freeze` 是这样走的：从
`BytesMut` 里读出指针 / 长度 / 分配大小；调 `mem::forget` 让 `BytesMut` 不再清理；然后造一
个指向那同一块缓冲区的独占 `Bytes`，`data` 装分配大小。

一个微妙之处：`mem::forget` *通常就是泄漏*——那才是它的主要（也是危险的）用途。这里它*不*泄
漏，只因为我们*先*把指针读出来、交给了 `Bytes`。`mem::forget` 不检查这一点；*你*得保证有人接
手。所以先读出、再 forget 的顺序是强制的；反过来的话编译器会拦住你（你已经把 `self` 交进
`forget` 了）。这很难写错——正是我们喜欢的那种代码。

还有独占区域的释放函数，如上所述：按从 `data` 读出的分配大小归还内存。记住那个沉默的陷阱——是
分配的，不是写入的。

## 我们有了什么，以及前方那堵墙

第 3 部分之后，我们有了一个对*三种里的两种*都能用的 `Bytes`，带一条免费的读路径，还没碰多线
程。常量的克隆是拷贝结构体，清理是空函数。独占区域的 `freeze` 是常数时间的交接——第 1 部分的
memcpy 死了，也就是我们在第 1 部分立下的硬性要求达成了——清理是按分配大小释放。"数释放次数"这
个思维方式已作为诊断工具备好。

恰好还剩一种行为：克隆一个独占区域。而它把一切搞砸。拿数数的思维方式试试：克隆一个独占区域，然
后让*两个*句柄都独占，那么两个都会释放——数出来是 2——double-free。

为什么这躲不掉，以及为什么它的出路逼出一件在 Rust 里非常反常的事——回头改写一个已经存在的值
——就是第 4 部分，也是整个系列最难的一部分。
