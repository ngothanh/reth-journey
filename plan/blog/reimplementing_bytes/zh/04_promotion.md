# 第 4 部分——那堵墙：当 clone 把一切搞砸

四种行为里三种做完了，而且简单得出乎意料。剩一种：克隆一个拥有独占内存区域的 `Bytes`。听着没
什么了不起。但整个设计就在这里撞墙，而这堵墙难，不是因为语法——它难，是因为它违背了一个我们写
Rust 时一直默默相信的假设。

我们在这一部分会走得很慢，因为你只要弄懂它，第 5 部分的一切（原子操作、CAS、内存序）就会变成
自然的推论，而不是一堆零散的概念。

## "独占"是一个承诺，不是一句描述

拿着第 3 部分"数释放次数"的思维方式，试最朴素的 clone：克隆一个独占区域，返回又一个独占区域，
就像我们拷贝一个常量那样。

设 `b1` 是一个独占的 `Bytes`，指向地址 `0xAAAA` 的内存。我们把它克隆成 `b2`。朴素的做法让
`b2` 也独占，也指向 `0xAAAA`——*同一块内存*。现在数一数：

```
b2 被放手 → 它是独占 → 释放 0xAAAA   ← 第 1 次
b1 被放手 → 它是独占 → 释放 0xAAAA   ← 第 2 次 💥
```

数出来是 2。double-free。为什么不能"聪明"一点来避免？

因为"独占"意味着"我是*唯一*的拥有者"。这不是一个描述状态的被动标签——它是一个*承诺*，释放函数
*信任*它才敢去释放。释放函数并不去查"还有没有别人持有"；它*假定*自己是唯一的，因为那是独占标签
的条款。

对比常量：我们随便拷贝一个常量，因为"没人拥有"翻倍还是"没人拥有"。但拷贝一个*单一拥有者*，就得
到*两个拥有者*，而两个都还戴着"唯一"的标签，两个都会去释放。

这里是关键，也是很多人栽跟头的地方：克隆这个动作*让 `b1`"我是唯一"的承诺变成了假的*——尽管我们
根本没碰 `b1`。仅仅是 `b2` 来到世上，就把 `b1` 变成了骗子。人们通常以为 `clone` 唯一的职责是
"造一份拷贝"。但在这里，`clone` 还有第二个、隐藏的职责：*修好原件的状态，让它不再自相矛盾。*
谁惹的祸，谁来收拾。

## 唯一的出路：升级到共享

没有安全的办法写出一个返回独占区域的 `clone`。要脱身，`b1` 必须*不再当唯一拥有者*。具体地说，
我们把两个句柄都挪到第三种拥有方式——共享，带 counter。这个过程叫 *promotion（升级）*，从独占
升级到共享。

我们分配一个装 counter 的小块——叫它 `Shared` 块——把它包进一个 `Arc`，让 `Arc` 负责原子计数
和归零释放。关键在于：这个 `Shared` 块只*指向* payload；payload 本身*纹丝不动*。所以这仍然是
零拷贝——我们没有重新拷贝那段字节，只是分配了一个用来计数的小小额外之处。

然后我们把 `b1` *和* `b2` 都挪到共享，两个都指向那个 `Shared` 块，counter 设为 2。

```
        payload（纹丝不动）
           ▲              ▲
           │              │
     b1: 共享        b2: 共享
           │              │
           └──► Shared ◄──┘      counter = 2
                (Arc)
```

现在重新数：每个句柄被放手时把 counter 减一。内存恰好被释放一次，就在 counter 归零时。数字回到
了 1。

注意一个以后要紧的细节：`Shared` 块必须记住所分配内存的*原始地址*，未必是句柄当前持有的那个指
针——因为取子片段会把句柄的指针往前推，但归还给分配器时，我们仍必须归还它当初给出的那个原始指
针。

## 升级是一条单行道

这里有一条状态链：

```
常量 ──────────────────────────────────────  （永不改变）

独占 ──(第一次 clone)──► 共享 ──(继续 clone)──► 共享 ──► ...
       promotion
       ◄─── 没有反方向 ───
```

为什么*共享永不回到独占*？因为一旦有两个或更多共享句柄，没有 counter 的话没有哪个句柄知道自己
是不是最后一个。要回到独占，你就得把 counter 丢掉——但丢掉它就失去了计数的能力，而如果还有两个
或更多句柄，那就是一个等着发生的 double-free。所以：一旦共享，永远共享。

（理论上，如果 counter 掉回 1，你*可以*降级回独占以避开原子操作的开销。真正的 `bytes` crate
不这么做——复杂度不值那点收益。这是一个值得记下的"*不*去做的决定"：有时好设计就是知道在哪里收
手。）

这也解释了一个名字。`b1` 的标签起初是"独占"，但它*可能会*变成"共享"。第 5 部分会看到这个标签无
法自我修复，所以 vtable 要带一个反映"可能会变"的名字——*promotable*，"可被升级的"。但这个名字
深层的原因是第 5 部分的一个技术约束；现在只需理解："独占"在这里的意思是"目前独自一个，但随时准
备变成共享"。

## 反常之处：回头改写一个已经存在的值

现在来到让这一部分*在概念上*难、而非代码上难的东西。

在普通 Rust 里，一个值的拥有方式在它*出生的那一刻就定死了*。一个生为 `Vec` 的 `Vec`，到死都是
`Vec`。一个生为 `Arc` 的 `Arc`。你从不把一个活着的值从一种拥有方式"转换"成另一种——你造一个*新
的*值，把旧的丢掉。

而这里完全不同。`b1` 生为独占，却在它*生命的中途被变成共享*，由*另一个值*——`b2`——在 `b2` 被
造出来的那一刻改变。`b1` 不是自己改的；它是*被* `b2` 改的。

正是这个反常之处，孕育了余下所有的复杂度。为了让 `clone`（正代表着造 `b2` 在运行）能修好
`b1`，它必须满足三条*互相独立*的要求。

第一条要求是必须有一条*通往* `b1` 字段的路。眼下，`clone` 运行时，它收到的 `b1` 的 `data` 是
一份*拷贝*——拷出来的 8 个字节。给那份拷贝赋一个新值，原来的 `b1` 毫不知情。要能修好 `b1`，
`clone` 必须收到一个*指向*真实字段的引用，而不是一份拷贝。

第二条要求是必须能*透过*那条路*写*。就算有了指向 `b1` 字段的引用，`clone` 也只有一个指向
`b1` 的*共享、只读*引用（因为 `clone` 在 Rust 里的签名是 `&self`）。透过只读引用写，是 Rust
默认*禁止*的。这需要一个特殊的机制。

第三条要求是必须在*多个线程同时做时也安全*。`Bytes` 将不得不能在线程间发送（第 5 部分会解释为
什么这是强制的）。到那时，两个线程可以都持有一个指向 `b1` 的引用，都调 `clone`，都试图升级它。
朴素地做，两个线程会分配两个 counter，其中一个被丢弃——泄漏，或者更糟。

这三条要求来自三个截然不同的世界——一条关于参数传递（拷贝还是引用），一条关于 Rust 的借用规则
（透过只读引用写），一条关于多线程的内存模型。它们彼此毫不知情。然而，如第 5 部分将展示的，三
条都指向 `data` 字段类型的*同一个*改动。

## 签名必须改

具体地说，vtable 里的函数必须从"把 `data` 当拷贝收"改成"收一个指向 `data` 的引用"。还有一个虽
小却有趣的细节：`clone` 函数收一个*共享*引用（只读，因为它是 `&self`），而 `drop` 函数拿到一
个*独占*引用（`&mut self`，因为一个值正被销毁时，肯定没有别的线程还持有它）。这个区别——"clone
拿共享，drop 拿独占"——听着不起眼，但在第 5 部分它有一个很具体的后果：`drop` 读 `data` 不需要
原子操作，而 `clone` 需要。

## 我们有了什么，第 5 部分解决什么

第 4 部分到此为止：克隆一个独占区域是 double-free，所以 *promotion*——把两个句柄都升级到共享
——是唯一的出路；我们分配一个带 counter 的 `Shared` 块，把两个句柄挪上去，payload 不动。升级是
单向的。而那个反常的核心：`clone` 必须*回头改写* `b1`——一个已经存在的值——因为克隆这个动作让
`b1` 的承诺变假了。

这个回写提出三条互相独立的要求：一条通往字段的路、透过只读引用写的能力、以及多线程安全。第 5
部分会展示这三条汇聚到单一的字段类型上，而每条要求都对应并发拼图的一块——interior mutability
（透过只读引用写）、CAS（竞争时挑出恰好一个胜者）、以及内存序（保证另一个线程*看见*刚被升级的东
西）。那是这个系列最抽象的一部分，我们会走得很慢。
