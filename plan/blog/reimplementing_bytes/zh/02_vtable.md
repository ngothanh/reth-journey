# 第 2 部分——一个类型，多种行为

第 1 部分结束在一个矛盾上。我们需要单一的 `Bytes` 类型（因为 API 边界要求如此），但这个类型
必须懂三种不同的清理内存的方式——常量什么都不做、独占区域释放、共享区域先计数再释放——而哪一种
适用，只有运行时才知道。这一部分去寻找让这成为可能的机制。

但在发明任何新东西之前，值得仔细看看 Rust *通常*是怎么解决这个问题的。因为你会发现，我们的设
计其实一点都不新——它只是照搬了 Rust 本来就在做的事，往下降了一层。

## 通常，"怎么清理"早就长在类型里

看三个熟悉的类型，注意是什么决定了它们各自如何被清理：

```rust
&'static [u8]   // 一个常量字节串，活整个程序那么久
Vec<u8>         // 一个我们拥有的字节数组
Arc<[u8]>       // 一个共享的字节数组，带 counter
```

当一个 `Vec<u8>` 离开作用域被销毁时，编译器会执行释放它内存的那段代码。当一个 `Arc<[u8]>`
被销毁时，编译器执行那段减 counter、仅在归零时才释放的代码。当一个 `&'static [u8]` 被销毁
时，编译器什么都不执行——它是对常量的引用，没什么可清理的。

值得注意的是：**你从来不用告诉编译器执行哪段代码。** 它看*类型*就知道。`Vec` 用 `Vec` 的办
法，`Arc` 用 `Arc` 的办法。这个决定在*编译期*就敲定了，而且是免费的——没有"运行时去问这是哪
种"的步骤，因为类型早已提前回答了。

换个说法：在 Rust 里，一个*类型*不只是数据的形状。它还*随身携带*一段子程序——怎么克隆、怎么
drop——由编译器查出来接进去。你可以把类型想成一张不可见的、静态的行为查找表。

Rust 之所以快，正因为此：每一种拥有方式都是它自己的类型，每一个清理决定在编译期就搞定，运行
中的程序不必思考。

而这也正是第 1 部分那个"三个独立类型"方案想利用的——让编译器替我们做。它之所以死，只因为 API
需要单一类型。所以现在，我们必须亲手去做编译器平时默默做的事——只不过在运行时做。

## 冲突：一个类型只有一个 `Drop`

"一个类型"这条约束，正面撞上了 Rust 把行为绑到类型上的方式。在 Rust 里，你用一个 `Drop` 块
来定义"一个值被销毁时会发生什么"：

```rust
impl Drop for Bytes {
    fn drop(&mut self) {
        // 现在这里该写什么？
    }
}
```

但这个块只为 `Bytes` 类型写*一次*。而你写不出一行对三种情况都正确的代码：

- 写"释放内存"，对独占区域是对的，但对常量就是在释放我们并不拥有的内存——程序崩溃。
- 写"什么都不做"，对常量是对的，但对独占区域就泄漏（leak）了——内存永远不被归还。
- 写"减 counter"，对共享区域是对的，但常量和独占区域根本没有 counter 可减。

没有哪一行*固定*的代码对三种都正确，因为哪一种适用只有运行时才知道，按值而定——这个 `b1` 是
常量，那个 `b2` 是独占，那个 `b3` 是共享。编译器无计可施了：它*按类型*挑行为，而我们只有一
个类型。

所以"挑哪种行为"这个决定，必须离开编译器、挪到运行时。问题是怎么挪。

## 思路：把"怎么清理"塞进值本身

既然编译器没法在编译期挑，那就让*值自己带上这个选择*。而要在运行时挑，用来挑的东西就必须是
*结构体里的数据*，而不是类型。

具体地说：我们取出"类型"隐形携带的那个东西——clone/drop 子程序——把它变成一个看得见的字段。在
Rust 里，"一个能存进变量的子程序"就是*函数指针*。所以我们把两个函数指针收进一张小表：

```rust
struct Vtable {
    clone: /* 指向 fn 的指针："克隆这一种，就跑这段" */,
    drop:  /* 指向 fn 的指针："drop 这一种，就跑这段" */,
}
```

（"Vtable"是这种表的传统叫法——*virtual table*，虚函数表。）

然后我们提前造三张这样的表，一种拥有方式一张，让它们活整个程序那么久：

```rust
static STATIC_VTABLE: Vtable = /* 常量风格的 clone, drop */;
static OWNED_VTABLE:  Vtable = /* 独占风格的 clone, drop */;
static SHARED_VTABLE: Vtable = /* 共享风格的 clone, drop */;
```

而每个 `Bytes` 值都带一个指针，指向这三张表之一：

```rust
struct Bytes {
    /* ... 字节在哪儿 ... */
    vtable: &'static Vtable,   // 这个指针决定了值的命运
}
```

现在 `Bytes` 的 `Drop` 函数只剩一件事：*读 `vtable` 字段，再调用其中的 `drop` 函数*。持有
`STATIC_VTABLE` 的值调进那个"什么都不做"的函数；持有 `OWNED_VTABLE` 的值调进"释放"函数。单
独一个 `impl Drop` 块，三种不同行为，各自在运行时按值挑对。正是我们要的。

对刚发生的事，最凝练的看法是：

> vtable *就是*类型，只不过从编译期这一层被降级成了一个运行时的值。三个类型
> `&'static [u8]`、`Vec<u8>`、`Arc<[u8]>` 并没有消失——它们变成了三个*值*
> `STATIC_VTABLE`、`OWNED_VTABLE`、`SHARED_VTABLE`，我们可以在运行时把它们赋给字段、比较、
> 调用。

### 其实你早就用过 vtable

如果你在 Rust 里写过 `&dyn 某个Trait`，你就用过 vtable——只不过是编译器替你造的表。一个
`&dyn Trait` 内部是一对指针：一个指向数据，一个指向该 trait 的方法表。你通过 `dyn` 调一个
方法时，程序在那张表里查出正确的函数，再调用它。这正是我们在手动搭的机制。

`dyn` 和我们所做的唯一区别：

- 用 `dyn` 时，每种情况是*不同的类型*（一个 `u64`、一个 `String`……），所以编译器知道给哪个
  类型造哪张表。
- 而在这里，三种情况*已经是同一个类型* `Bytes`。编译器没什么可区分的，造不了表——所以我们手
  动造，并亲手指定哪张表配哪个值，就在造出那个值的那一刻。

这给了我们一条以后能用的规则：什么时候该手写 vtable？恰好当*一个*类型需要*多种*行为、按值在
运行时挑选时。多个类型 → 用 `dyn`。一种行为 → 用普通函数。手写 vtable 恰好填补"一个类型、多
种行为、按值"这个空档。

## 为什么这张表恰好两个槽

这是任何设计这种类型的人都该答得上来的问题，因为它是检验你到底*懂*这个设计、还是只抄了的试金
石。我们从两个方向考察：为什么不*少于*两个，以及为什么不*多于*两个。

有一条简单的判定规则。一个函数槽只有当该操作的行为*随着谁拥有内存而改变*时，才配进 vtable。
如果一个操作不管什么拥有方式都做同样的事，把它放进 vtable 就毫无意义——更糟，是有害的，我们会
看到。

试着把 `Bytes` 能做的*一切*列出来，逐个问"它取决于拥有权吗"：

- 读出字节（取长度、取内容、比较、打印）：对三种方式，答案都是"看着指针和长度读就行"。*不*取
  决于拥有权。
- `clone`：常量拷贝整个结构体；独占区域必须做一件复杂的事（第 4 部分）；共享区域把 counter
  加一。*取*决于拥有权。
- `drop`：常量什么都不做；独占区域释放；共享区域减 counter。*取*决于拥有权。

恰好两个操作取决于拥有权。所以恰好两个槽：`clone` 和 `drop`。

为什么不*更少*？能把 `clone` 和 `drop` 合进一个槽吗？不能——它们是两个独立的操作，发生在两个
不同时刻（一个在复制句柄时，一个在放手句柄时），且谁的行为都推不出另一个。去掉 `drop` 槽，你
就不知道怎么释放；去掉 `clone` 槽，你就不知道怎么复制。每个都以自己的方式取决于拥有权，所以
每个都需要自己的槽。

而"读字节"那一半——为什么*没有*槽？因为它不取决于拥有权。指针和长度已经完整回答了"哪些字节"，
在三种方式下都一模一样。给它一个 vtable 槽，就意味着每次读都要付一次*间接函数调用*——为一个根
本不关心谁拥有什么的操作。这是第 3 部分的种子，但在这里已能看见：一个不取决于拥有权的操作被
*禁止*进 vtable，因为把它放进去会让热路径（hot path）为无谓的东西买单。

为什么不*更多*？有两个自然的反对意见。

第一，"加一个 `slice` 槽？"——因为取一个 `Bytes` 的子片段*看起来*取决于拥有权（对常量切片得
到常量；对独占区域切片得不到另一个独占区域，否则就是一块内存两个拥有者）。但 `slice` **能用
`clone` 表达**：取子片段无非是"复制句柄（好让 `clone` 处理拥有权那部分），再把指针和长度收窄
到子片段"。`clone` 早就知道怎么为三种方式正确地复制。一个*能从别的槽重建*的槽，不配占位。

第二，"全都塌进一个返回枚举、说明是哪种、再据此分支的槽？"——即一个返回种类的 `kind()` 函数，
然后 `clone` 和 `drop` 各自对它 `match`。这能用，但你分派了*两次*：一次间接调用（调
`kind`），*再*一次分支（`match`）。而函数指针的全部魅力恰恰在于*调用它本身就是分派*——一步。
再说这个枚举做法是*封闭*的：加第四种拥有方式意味着改代码库里*每一处* `match`；而用 vtable，你
只需加一张新的 `static` 表，别处一动不动。

总结：恰好两个槽，因为恰好两个操作取决于拥有权，且彼此推不出来。更少会失去能力；更多要么冗余
（能重建）要么慢（分派两次）。可带走的规则：一个槽配占位，当且仅当它取决于隐藏状态*且*不能从
别的槽重建。

（给好奇者的一条实务注记：真正的 `bytes` crate 有五个槽，不是两个。多出的三个都是*纯优化*——
每个都省下一次量过的拷贝。比如，对一个恰好独占的缓冲区"变成 `Vec`"，可以直接把内存交出去而不
拷贝——但前提是它能问"我现在独占吗？"，而这只有 vtable 知道。每个多出的槽都能从 `clone` 加
`drop` 重建；它们存在，是因为有人*量*出了一次值得省的拷贝。每个多出的槽都要付一次间接调用，所
以每个都得靠一个基准测试*挣得自己的座位*。这个用于学习的实现做两个——那是正确的最小集。）

## vtable 的同伴：一个数据字段

vtable 说了*怎么*克隆/drop。但"怎么"通常需要一份随行的*数据*。独占区域的释放函数需要知道分配
的区域有多长，好归还恰好那么多。共享区域的减计数函数需要知道 counter 在哪个地址。常量的函数什
么都不需要。

这份数据从哪儿来？我们再加一个字段，暂叫 `data`。它必须承载*三种不同的信息*，视 vtable 而
定：

- 对常量，`data` 不用；
- 对独占区域，`data` 装分配区域的长度——一个*数字*，不是地址；
- 对共享区域，`data` 装 counter 的*地址*——一个真正的指针。

时而是数字，时而是指针。没有哪个"正经的" Rust 类型能描述它。所以我们用最不成形的可用类型来声
明它：**`*mut ()`**。这是一个指向 `()`（Rust 的"空"类型）的*裸指针（raw pointer）*；换句话
说就是 C 的 `void*`：恰好 **8 字节**（在 64 位机上），在有人解释它之前不带任何含义。别把
`data` 读成"一个指针"；把它读成"8 个字节，含义待定"。对独占区域，我们把长度数字直接塞进这 8
个字节（一个穿着指针外衣的整数）；对共享区域，这 8 个字节是一个真正的地址。

`data` 和 `vtable` 永远成对而行：`data` 是本身无意义的 8 个字节，而 `vtable` 是*唯一*知道
这 8 个字节这一次是什么意思的东西。这就是为什么——你写代码时会看到——每个 vtable 函数都把
`data` 当第一个参数：我们把这 8 个无意义的字节递给那唯一知道怎么读它们的函数。

## 小结：设计走到哪一步了

拼起来，第 2 部分之后我们的 `Bytes` 长这样——第一次带上真实类型，不再是占位符：

```rust
struct Bytes {
    ptr:    NonNull<u8>,      // "哪些字节"：指向这段的开头
    len:    usize,            // "哪些字节"：多长
    data:   *mut (),          // "谁拥有"：8 字节，含义由 vtable 定义
    vtable: &'static Vtable,  // "谁拥有"：用哪套 clone/drop
}

struct Vtable {
    clone: /* 函数指针 */,   // 克隆这一种，就跑这段
    drop:  /* 函数指针 */,   // drop 这一种，就跑这段
}
```

以及三种可能的 `data`/`vtable` 组合：

| vtable          | `data` 装什么       | `drop` 做什么 |
|-----------------|---------------------|---------------|
| `STATIC_VTABLE` | （不用）            | 什么都不做    |
| `OWNED_VTABLE`  | 区域长度（数字）    | 释放          |
| `SHARED_VTABLE` | counter 地址（指针）| 减计数        |

把这张表记在脑子里；到第 5 部分它只改*一*行——`data` 字段的类型——那时我们会看到为什么
`*mut ()` 还不够。（原因藏在 `clone` 里，现在还没露出来。）

## 我们有了什么，第 3 部分接着解决什么

我们现在解决了第 1 部分问题的前一半：单一的 `Bytes` 类型，承载三种不同的清理，靠一个指向三张
预造表之一的 `vtable` 字段，在运行时按值挑对。

但还有后一半，同样重要：*读字节必须仍像 `Arc<[u8]>` 一样廉价。* 在"两个槽"那一节我们已经瞥
见：读操作*不在* vtable 里。但光是"不在 vtable 里"还不够。我们还得把结构体的字段这样排布，使
得读*绝对不*碰 `data` 或 `vtable`，连一次分支都不碰。为什么这种排布胜过一个 `enum`，以及为什
么它让新加的两个字段在热路径上*免费*——就是第 3 部分。

第 3 部分还会引入一种思维方式，它是余下两个最难部分的骨架：每一种拥有内存的方式，追到根上，就
是一个问题——*这块内存被释放了恰好几次？*
