# 第 5 部分——`AtomicPtr`：安全地回写

第 4 部分收尾在一个问题和三条要求上。问题：克隆一个独占的 `Bytes` 时，我们必须*回头改写*原
件，把它升级到共享，否则就 double-free。做这个回写的三条要求：必须有一条通往原件 `data` 字段
的路；必须能透过只读引用写；必须在多个线程同时做时安全。

这一部分把三条都解决。而漂亮之处在于：三条虽来自三个不同的世界，却由同一个对 `data` 的类型选
择解决——把它变成一个*原子*指针（`AtomicPtr`）。这是整个系列最抽象的一部分，所以我们逐条要求地
剖开，而随每一条，对应的并发概念都会作为一个我们真正必须解决的*具体*问题的答案登场，而不是空谈
的理论。

## 为什么用一个原子指针

回想第 4 部分的三条要求，因为值得注意的是它们来自三个不相干的世界。第一条——"必须有一条通往
`b1` 的 `data` 字段的路"——关乎*参数传递*：函数收到的是拷贝还是引用。第二条——"必须能透过只读
引用写"——关乎编译器的*借用规则*。第三条——"必须在多个线程同时做时安全"——关乎硬件的*内存模型*。
三件事在三个不同的层面，谁都不知道谁。

然而三条都由同一个改动解决：把 `data` 的类型从一个普通指针改成一个*原子*指针（`AtomicPtr`）。

回想第 2 部分，`data` 字段眼下的类型是 **`*mut ()`**——一个裸指针，8 字节，"含义待定"。这个类
型*无法*满足上面三条要求：一个 `*mut ()` 传进函数是*当拷贝*传的（第一条落空）；就算有了指向它
的引用，Rust 也*禁止*透过只读引用写（第二条落空）；而从多个线程同时读/写一个 `*mut ()` 是数据
竞争（data race），也就是未定义行为（第三条落空）。

三处落空都由同一个改动修好：把 `data` 的类型从 `*mut ()` 改成 **`AtomicPtr<()>`**——还是那 8
个字节，还是"含义待定"那个角色，但现在是一个*原子*指针。它允许取一个指向它的引用（解决第一
条）。它允许透过只读引用写，靠一个叫 *interior mutability* 的性质（解决第二条）。它提供原子操
作，让多个线程不互相踩踏（解决第三条）。

这值得作为一课单独记下：当有人问"这个字段为什么是原子的？"，正确的答案*不是*笼统的"因为并发"。
在这里，它是三条具体、独立的要求，恰好由同一样东西解决。能认出何时多条不同的要求汇聚到同一个机
制上——那就是系统设计功力的一半。

接下来三节逐条剖开。第一条（取一个引用）是琐碎的——只要改函数签名，传 `&data` 而不是 `data`。
另外两条才是干货，而每条都把我们引向一个并发概念。

## 要求二——透过只读引用写：interior mutability

Rust 里有一条规则，简单到值得背下来：一个只读引用（`&T`）*只能被读*。要透过它写，`T` 内部就
*必须*含有一个叫 `UnsafeCell` 的东西。

`UnsafeCell` 是整个 Rust 里*唯一*允许"透过只读引用改数据"的东西。它是一个由编译器许可、直接钻
穿借用规则的洞。你曾经用来"透过共享引用写"的每一个工具，都是 `UnsafeCell` 加上一条让它安全的纪
律：

- `Mutex` 是 `UnsafeCell` 加"进去之前必须先加锁"。
- `RefCell` 是 `UnsafeCell` 加"运行时数借用次数，违规就 panic"。
- `Cell` 是 `UnsafeCell` 加"只准拷进拷出，绝不出借内部"。
- 而一个原子指针是一个装着指针的 `UnsafeCell`，加"只用 CPU 的原子指令读/写"。

所以当 `clone` 只有一个指向 `b1` 的只读引用、却需要往 `b1.data` 里写时，那个字段*必须*含一个
`UnsafeCell`。一个原子指针正是我们要的：它打开"透过只读引用写"这个洞（要求二），同时把多线程那
部分（要求三）也一并办了。

这里有一个值得记住的对称。`Arc<T>` 同样只给你一个指向其内部的只读引用。这正是*为什么*人人都要
写 `Arc<Mutex<T>>`——`Arc` 管*共享*，`Mutex` 管*写*。`Bytes` 面对的正是这个问题，只是解法不
同：两者都是"共享，且需要写"，但 `Arc<Mutex<Vec>>` 用一把锁（因为 `Vec` 大，没法原子化），而
`Bytes` 用一个原子指针（因为要写的东西恰好 8 字节）。

而这里是值得停一下的点：`Bytes` 为什么能用一个原子操作而不是一把锁？因为要保护的东西*恰好是一
个机器字*（64 位机上 8 字节）。这是一条硬件事实，查一次记住即可，不用推导：一个 64 位 CPU 对恰
好 8 字节或更少的数据，有原子的读、写和"比较并交换（compare-and-swap）"指令。任何大于 8 字节的
东西，*没有哪条指令*能原子地做——那时你就需要一把锁（一把锁在一个标志的保护下顺序地读/写多个机
器字）。因为 `data` 只有 8 字节，它自己就"既是锁又是数据"，旁边不用单独的 `Mutex`。正是这一点
让 `Bytes` 保持小巧、无锁，却仍然线程安全。要升级的东西一旦大于 8 字节，这整个设计就垮了，你就
得退回到用锁。

## 要求三——多个线程同时升级：Send、Sync 和 CAS

Rust 对数据跨越线程边界有两个概念。一个值是"可发送的"（`Send`），如果它被允许*移动*到另一个线
程。一个类型是"可共享的"（`Sync`），如果指向它的引用被允许*被多个线程使用*。编译器会推导出这两
个；而因为 `Bytes` 持有裸指针（Rust 默认把裸指针当作不可发送、不可共享的，因为它对指针很悲
观），所以 `Bytes` 默认*两者都不是*。

但代码库*需要*它们。缓存在多个 worker 之间共享，消息通过 channel 在线程间发送。如果 `Bytes`
不可发送、不可共享，代码根本编译不过——这是一个真实的报错：

```
error[E0277]: `*mut ()` cannot be sent between threads safely
```

所以我们向编译器*承诺* `Bytes` 发送和共享都是安全的。这个承诺为真，因为：payload 不可变（多个
读者不会撞车），而唯一可变的状态——`data`——是原子的。这正是让 `Arc<[u8]>` 可发送、可共享的东
西，而 `Bytes` 有着同样的形状。

但承诺有它的代价。一旦 `Bytes` 可共享，两个线程就能都持有一个指向 `b1`（一个独占区域）的引
用，都调 `clone`。如果我们朴素地升级——读出 `data`，再把新值写进去，分成两步——就会发生这个场
景：

```
线程 1：读 data，看到"未升级"
线程 2：读 data，看到"未升级"        ← 插进中间
线程 1：分配 counter A，写 data = A
线程 2：分配 counter B，写 data = B    ← 覆盖掉 A
```

结果：两个 counter 被造出来，其中一个（A）被丢弃——泄漏，或者若计数逻辑走歪就是 use-after-
free。这是一个经典 bug，叫 *lost update（丢失更新）*——非原子的"读-再-写"那种因覆盖而丢失。两
个分开的步骤留了一道缝，让另一个线程钻进去。

补救办法是一个把"检查"和"写"熔进一个不可分割步骤的操作，叫 *compare-and-swap*，简称 CAS。翻成
人话：

> "喂 `data`，*如果*你还是那个旧值（未升级），那就把自己改成我这个 counter 的指针——而且把这
> 两件事*熔在一起*做，任何线程都插不进中间。但如果别人已经先改了你，那就*别*改，并告诉我你现在
> 装的是什么。"

硬件保证，当多个线程冲进来时，*恰好一个* CAS 胜出。胜者把自己的 counter 装进 `data`；就在那一
刻，`b1` 变成共享（因为 `b1` 和 `data` 这个格子是一体的）。败者收到"别人已经改了"的信号，于是
把自己刚分配的 counter 丢掉，改用胜者的 counter。最终只有一个 counter，内存恰好被释放一次——第
3 部分数数的思维方式又平衡了。

败者那条路里有个要小心的细节：丢掉那个多余的 counter 时，必须丢得*不*触发 payload 的释放——因
为 payload 现在归胜者的 counter 所有。它只释放那个多余块的*外壳*，跳过那个块的 payload 清理。
忘了这个细节，payload 就会被释放两次。

CAS 在这里的角色有个漂亮的名字：它是*线性化点（linearization point）*。尽管两个线程并行冲进
来，CAS 就是那个把混乱变成清晰次序的标记——"谁赢了 CAS，就当作谁先发生"。任何时候你需要"多个竞
争者里恰好一个能做 X"，CAS 就是那个工具，而胜出的标记就是线性化点。

## 要求三（续）——内存序：光"能写"还不够，还得"看到正确的次序"

CAS 只解决了多线程的一半：它保证恰好一个线程*装上* counter。但还有第二重危险，更微妙、且完全独
立——而这里是大多数人觉得最难的地方。我们先把问题立起来，再逐个剖开每一个操作，看看每个各需要什
么强度的同步。

### 问题：写会被重排

升级竞争的胜者做两件事，在*代码里*的顺序是：先初始化 `Shared` 块的内容（往里写内存的原始地址和
长度），然后通过那个写 `data` 的 CAS *发布* `Shared` 块的地址。

问题在于，硬件和编译器都被允许*重排*对内存的写以求更快——它们缓冲、合并、乱序。对单个线程这无
害，因为最终结果看着是对的。但对多个线程，另一个线程可能*以不同于代码的顺序*看到胜者的那些写。

具体的灾难：一个第二线程调 `clone`，读 `data`，看到它已经是 `Shared` 块的地址，于是访问那个块
去把 counter 加一——也就是读它的内容。如果第二线程看到了*那个地址*、却*还没*看到胜者刚初始化的
*内容*——在重排规则下这完全合法——那它就读到一个装满垃圾的 `Shared` 块，之后的一切都是未定义行
为。地址"跑到了"它所指向的内容前面。

我们需要一个保证：*凡是看到了 `Shared` 块地址的，也必须看到它已初始化完毕的内容。* 这就是*内存
序（memory ordering）*的活儿——我们贴在每个原子操作上的"标签"，说明它被允许重排到什么程度。

### 四种强度，以及怎么想象它们

Rust 有四个我们会用到的标签：`Relaxed`、`Acquire`、`Release`、`AcqRel`。中间那两个，最容易想
象成"发布"和"订阅"：

- 一个 **`Release`** 类的**写**是一次*发布*：我在这个操作*之前*写的一切，凡是读到我刚写的这个
  值的人，都会看到。
- 一个 **`Acquire`** 类的**读**是一次*订阅*：一旦我读到那个已发布的值，我也就看到发布者在*发
  布之前*写的一切。
- **`Relaxed`** 意思是"只把这个操作弄成原子的，不承诺相对于别的写的任何次序"——最便宜。
- **`AcqRel`** 意思是"既 `Acquire` 又 `Release`"，用于一个*同时读又写*的操作（比如 CAS，它既
  读旧值又写新值）。

关键：`Release` 和 `Acquire` 只有*成对*、在*同一个变量*上时才起作用。一边发布，一边订阅；这一
对搭起那条把两个线程连起来的次序纽带。缺了一边，这一对就断了，保证也随之消失。

### 逐个剖开 `data` 上的操作

现在应用到升级过程中代码碰 `data` 的那几处，对每一处问：它需要哪个标签，为什么。

**开启 `clone` 的第一次读 `data`。** 在决定要不要升级之前，我们读 `data` 看它现在是什么。标
签：**`Acquire`**。为什么？因为 `data` 可能已经被另一个线程升级过了——它可能已经是一个 `Shared`
块的地址——那样我们就直接进"已共享"分支，去*访问*那个 `Shared` 块（把 counter 加一）。要安全地
访问，我们必须看到它已初始化的内容——所以这次读必须是 `Acquire`，好与那个升级了它的线程的
`Release` 配成一对。

**那个 CAS——这就是"为什么用 AcqRel"的答案。** 一件很多人忽略的事：`compare_exchange` 带*两
个*次序标签，不是一个——一个给*成功*的情况，一个给*失败*的情况。因为一个 CAS 有两个截然不同的结
局，而每个结局需要不同的保证。

- *当 CAS 失败*（别人先升级了）：CAS 把 `data` 的当前值还给我们——就是胜者的 `Shared` 块地
  址。而紧接着我们就会*用*那个地址（把另一个 `Shared` 块的 counter 加一）。也就是说我们即将去
  *访问*一个别的线程初始化的 `Shared` 块——所以失败这一支必须是 **`Acquire`**，理由和那次开启
  的读一模一样。
- *当 CAS 成功*（我们是胜者）：我们刚刚*发布*了那个*我们自己*在上面造好的 `Shared` 块。为了让
  另一个线程之后读到这个地址、去访问那个 `Shared` 块而不撞上垃圾，这次写必须是 **`Release`**。

所以失败这一支需要 `Acquire`，成功这一支需要 `Release`。而这里是关键：Rust 要求*成功*的标签不
得弱于*失败*的标签。但 `Release` 单独*并不*包含 `Acquire`（它们是两个不同的方向——一个管写这
边，一个管读那边）。所以为了让成功这一支既带 `Release`（为它自己的发布），又相对于失败支的
`Acquire` 足够强，它就必须*两者都带*——而那个"既 `Acquire` 又 `Release`"的标签，正是
**`AcqRel`**。

简而言之，给 CAS 用 `AcqRel` 不是为了"保险"而选——它是唯一在同一条指令上同时满足两件事的标签：
败者必须*接收*胜者的 `Shared` 块（`Acquire`），而胜者必须*发布*自己的 `Shared` 块
（`Release`）。

**`drop` 里读 `data`——完全不需要原子操作。** 因为 `drop` 拿的是一个指向该值的*独占*引用（回
想第 4 部分），它确知没有别的线程还持有它——没有竞争，所以一次普通的读就够了。独占引用本身就是没
有数据竞争的证明。这正是为什么 `drop` 的签名拿独占引用、`clone` 拿共享引用：不是风格，而是
"drop 有独占权，clone 没有"。

**那个边角情形：一个常量 `Bytes`。** `data` 是空的，不与任何人同步任何东西——所以对它的每一次
触碰只需要 **`Relaxed`**，最便宜的标签。

### 为什么不干脆用 `SeqCst` 保险

`SeqCst`（顺序一致性）是 Rust 最强的标签——它逼着程序里*每一个* `SeqCst` 操作排进一个所有线程
都认同的单一全局次序。听着安全，很多人"为了稳"就伸手去拿它。但在这里它既*多余*又*昂贵*。多余，
因为我们只需要发布者和接收者之间在单一变量 `data` 上的一条*两两之间*的纽带——并不需要全程序对某
个全局次序达成一致。昂贵，因为 `SeqCst` 通常得插入更强的内存屏障（memory fence），恰恰拖慢了这
整个设计为之存在、要保持快的那条路。选取实际所需的最小强度——在要紧处用
`Acquire`/`Release`/`AcqRel`，在不要紧处用 `Relaxed`——正是把无锁代码写好的一部分。

可带走的原则：`Release` 和 `Acquire` 永远成对、在同一个变量上，把一次"发布"连到一次"订阅"；一
个*同时读又写*、且两个角色都要紧的操作（比如 CAS）需要 `AcqRel`；而任何时候你向另一个线程发布
一个指向刚初始化数据的指针，你*总是*需要这一对——否则数据可能"在指针之后"才到。

## 一个简短的后果：为什么标签改名叫"promotable"

最后一个细节，是"回写"撞上一道界限的直接后果。

升级时，`clone` 能写 `b1.data`（靠那个原子指针），却*不能*写 `b1.vtable`——因为 `vtable` 是
一个普通字段，*没有* interior mutability，而 `clone` 只有一个只读引用。所以升级之后：

```
b1.vtable = 仍是"独占"表           ← 卡死，改不了，现在在撒谎
b1.data   = 已是 Shared 块地址      ← 已改（通过 CAS），说的是真话
```

`b1` 永远通过那张旧表分派，尽管它实际已是共享。所以那张表在它*每次调用的头一条指令*（`clone`
和 `drop` 都是），都必须自问：我的 `data` 现在是一个长度数字（未升级）还是一个 `Shared` 块地址
（已升级）？——再据此分支。正因为这个原因，这个标签*不叫*"独占"，而叫"promotable"——"这个*可能
已经*变成共享了"。

再往深看一点，这是一条普遍规律：那个用来区分的标记*必须活在可变的格子里*（`data`，原子的），
*不能活在不可变的 vtable 指针里*。这是"拥有权在生命中途改变"的必然后果：vtable 指针在值出生的
那一刻就冻住了，所以它不能是动态状态的容身之处。任何时候一个值的状态在它出生*之后*改变，那个状
态的标记就必须坐在*可变*的部分，而不是*不可变*的部分——而在这里，只有 `data` 是可变的。

（一条边注，*不属于*这个模型：`data` 怎么在同样 8 个字节里既装一个长度数字又装一个 `Shared` 块
地址，"promotable"表又怎么区分这两者？有一个借用*最低位*的技巧：一个 `Shared` 块的地址永远是偶
数——因为内存的对齐规则——所以它的最低位永远是 0；我们在往里打包一个数字时把最低位设成 1，只要看
一眼最低位就知道装的是哪种。这纯粹是一个*省空间的优化*——把它换成一个单独的字段来装长度也完全正
确，只是大一个机器字。`bytes` crate 打包这个位是因为它锱铢必较每一个字节；一个用于学习的版本不
必这样。）

## 小结：完整的设计

这里把整个设计并排放一次，作为收尾。和第 2 部分末尾的小结相比，恰好*一*行改了——`data` 的类
型——但整个第 4、5 部分都在解释这一行。

```rust
struct Bytes {
    ptr:    NonNull<u8>,      // "哪些字节"：指向这段的开头
    len:    usize,            // "哪些字节"：多长
    data:   AtomicPtr<()>,    // "谁拥有"：8 个原子字节；第 2 部分是 *mut ()，现在是原子的
    vtable: &'static Vtable,  // "谁拥有"：用哪套 clone/drop
}

struct Vtable {
    clone: unsafe fn(&AtomicPtr<()>, ptr, len) -> Bytes,  // & 好让 clone 能修原件
    drop:  unsafe fn(&mut AtomicPtr<()>, ptr, len),       // &mut：独占，非原子地读
}
```

三种拥有方式，以及 `data` 在每种里装什么：

| vtable              | `data` 装什么                       | `clone` 做什么             | `drop` 做什么 |
|---------------------|-------------------------------------|----------------------------|---------------|
| `STATIC_VTABLE`     | null（不用）                        | 拷贝结构体                 | 什么都不做    |
| `PROMOTABLE_VTABLE` | 长度（数字），*或*升级后 counter 地址 | 若未升级：造 counter，CAS 升到共享；若已升级：把 counter 加一 | 若未升级：释放；若已升级：减计数 |
| `SHARED_VTABLE`     | counter 的地址（真正的指针）        | 把 counter 加一            | 减计数        |

读数据（`deref`、`len`、比较、哈希）只碰 `ptr` + `len`——从不碰 `data` 或 `vtable`——所以它像
`Arc<[u8]>` 一样廉价。`data` + `vtable` 只在 `clone` 或 `drop` 时才登场。这就是整个设计。

从头走到这里，一张图：

```
Arc<[u8]>            P1：counter 与 payload 融为一体 ⇒ freeze 被迫拷贝
   │
   ▼ 要 O(1) freeze ⇒ Bytes 必须"接管"内存，而不是拷贝
Bytes{ ptr, len, data, vtable }
   │  P2：把"拥有"从类型降到一张 vtable（一个类型，三种行为）
   │      data: *mut ()  — 8 字节，"含义待定"
   │  P3：把"哪些字节"(ptr,len) 和"谁拥有"(data,vtable) 分开 ⇒ 读免费
   │      + 思维方式：每块内存被释放几次？(0/1/1)
   │
   ▼ P4：克隆一个独占区域 = double-free
   │      ⇒ promotion：回头改写原件，把它升到共享
   │
   ▼ P5：回写需要 &data + 透过只读引用写 + 线程安全
          ⇒ data: *mut ()  ➜  AtomicPtr<()>
          interior mutability · CAS · Acquire/Release/AcqRel
```

## 带进往后每个问题的五个问题

合上这个系列，忘掉 vtable、原子操作、CAS。真正值得带走的——带进往后关于预写日志（WAL）、关于在
跳表（skiplist）里共享节点、关于缓存数据块的问题，以及任何触及 unsafe、拥有权或优化的设计——是
这五个问题。它们是整个故事浓缩出来的东西。

第一：*每块内存被释放了恰好几次？* 0 是泄漏，2 是 double-free，1 是对的。每个 bug 都归结到这个
数字。

第二：*各种情况之间有什么*不同*？* 只有那不同的才需要分派。相同的就别动它——那正是热路径免费的原
因。

第三：*热路径碰分派了吗？* 碰了就是设计错了。读必须像 `Arc<[u8]>` 一样廉价。

第四：*有没有透过只读引用写？* 有的话就需要 interior mutability。一个光秃秃的只读引用永远只能
读。

第五：*有没有多个线程？* 有的话，用原子操作代替普通读/写；一个"恰好一个胜者"的操作要用 CAS；而
每次你向另一个线程发布一个指向数据的指针，就在同一个变量上用一对 Release/Acquire。

再加三句贯穿全系列、关于怎么想的收尾话。`Drop` 不清理结构体——结构体自己溶解；`Drop` 只撤销一次
分配，所以没分配就没 `Drop`。一个 vtable 是一个从编译期这一层降级成运行时值的类型，用于一个类型
需要多种行为、按值挑选时。而 unsafe 里可怕的 bug 不是那个崩溃的，而是那个正确运行的——来自安全
Rust 的直觉被反转了，错误的默认状态是沉默，所以永远带上 `miri`，逼它开口。

到这里，你脑子里的模型已经足够坐下来把 `Bytes` 从零重新实现一遍——三种拥有方式的四种行为、
`freeze` 操作、以及 promotion——并为每一个选择辩护。剩下的代码细节会在你写的时候自己浮现，因为
你懂了每一个存在的理由。
