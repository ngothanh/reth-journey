**Monday — ARIES undo pass**

- [ ] **Build**: `crates/recovery/src/undo.rs` — `UndoPass` rolls back all txs in `TransactionTable` from analysis,
  walking each tx's chain via the `prev_lsn` field of each WAL record, writing Compensation Log Records (CLRs) so
  undo is idempotent under re-crash. (~total 140 min across 3 phases) **[bar c]**
  - 🔧 **Why this matters**: UNDO is ARIES's crown jewel — rolls back losers without re-doing winners. The
    trick: as you undo a record, you write a CLR describing the undo action. If you crash during undo and
    re-recover, REDO will *redo* the CLRs (idempotent), so no work is lost. This makes recovery
    time-bounded regardless of how many crashes occur. Mohan won the Turing Award for this insight. Mirrors
    ARIES §6. Four specific traps: (1) per-tx processing breaks cross-tx page consistency; (2) undoing a CLR
    toggles state forever; (3) CLR-write / pageLSN-update not coupled loses the "already undone" signal under
    re-crash; (4) per-CLR `wal.append` await kills recovery throughput. A first-attempt impl fails ≥1 test
    below; the debug session is the lesson. Downstream: Tuesday's `Recovery::recover`, W42 txn rollback, W64
    raft log compaction, W74 matching-engine restart, W83 ledger restart, W95 mini-db restart.

  - *Mental model*: UNDO is a single merged-descending-order walk across ALL loser chains simultaneously, not
    a per-tx loop. Each undo step emits a CLR (a redo-only record) so that re-crash + re-recovery replays the
    CLR rather than re-undoing — that is what bounds recovery time under repeated crashes.
  - *Contract*:
    ```text
    pub struct UndoPass<'a> { tt: &'a TransactionTable, wal: &'a Wal }
    impl UndoPass<'_> {
        pub fn run(&self, pages: &mut impl PageProvider) -> Result<UndoReport, Error>;
    }
    // CLR { lsn, tx_id, undo_next_lsn: Option<Lsn>, kind: RecordKind::Clr, undone_lsn, redo_info }
    fn compute_undo(rec: &Record) -> UndoAction; // Insert→Delete, Update→Update(old), Delete→Insert
    ```
    NEVER the solution body — only signatures.
  - *Back-of-envelope*: recovery must process a 1 GiB wal in ≤10s end-to-end (R7 of the facade). At ~64 B/record
    that is ~16M records; UNDO touches only loser records (say 5% = 800k). The dominant cost is CLR durability.
    A naive per-CLR `wal.append().await` blocks on an fsync each CLR — and an fsync that actually flushes a dirty
    page is **~125 µs** on NVMe (the jeff-dean band is ~300 µs/fsync; a single small dirty page sits a bit under
    it). One fsync per CLR ⇒ ~125 µs/CLR ⇒ **~8k CLRs/sec** — *below* the R7 ≥30k/sec bar, so it fails the bar by
    **~4×** and an 800k-loser undo takes ~100s, blowing the 10s budget. The fix: batch CLR appends through the
    existing group-commit, so one fsync covers ~64 CLRs ⇒ ~125 µs / 64 ≈ **~2 µs/CLR amortized** (≈8k→~500k/sec,
    well past the bar). Amortization ratio fsync-per-CLR vs 1-fsync-per-64 ≈ **~64×**; the bar-relevant cliff is
    8k/sec vs the 30k/sec floor = **~4×**. Await the durable-LSN watermark once per batch, not once per record.
  - **Requirements** — write in `crates/recovery/notes/30_undo_design.md`:
    - R1. Process records in **strictly descending LSN order** across ALL losers simultaneously
      (max-heap on per-tx cursor LSN).
    - R2. Every undone record gets a matching CLR with `undo_next_lsn = original.prev_lsn`.
    - R3. CLRs are NEVER undone themselves; explicit kind check at the top of the loop.
    - R4. UNDO ∘ UNDO == UNDO (idempotence under re-recovery).
    - R5. After UNDO, losers' pages reflect "as if never started"; winners untouched.
    - R6. Per tx ending: write Abort/End record after all data records undone.
    - R7. Throughput ≥30k records/sec.
    - R8. 1000 random crash-during-undo simulations all converge.
  - **Design walk-through** D1..Dy — answer in the design doc; no peeking at any reference source until Phase 3:

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  Ordered newbie→expert — the ladder you actually walk.

  - **(NEWBIE) When `tx_with_zero_data_records_no_panic` reports an index-out-of-bounds:**
    - Symptom: panic popping an empty per-tx cursor at the heap root.
    - Why: the loop assumed every loser has ≥1 data record; a Begin+Abort tx has none.
    - Fix: push a tx onto the heap only if its `last_lsn` chain is non-empty; pop guards against exhausted cursors.
    - Muscle: a recovery pass must handle the empty-chain boundary; "every tx has work" is a false assumption.
      Reapplies at: W42 txn empty-transaction abort, W64 raft empty-log snapshot.

  - **(SENIOR) When `descending_lsn_order_across_txs` reports a fetch at LSN 90 after LSN 100:**
    - Symptom: instrumentation logs out-of-order LSN fetches (100,95,90,105,102).
    - Why: UNDO processed T1 completely (100,95,90) before starting T2 (105,102) — per-tx, not merged.
    - Fix: a `BinaryHeap` keyed on each tx's current undo-LSN; pop the max regardless of tx; advance only that
      tx's cursor; loop until all cursors exhausted.
    - Muscle: ARIES UNDO is a merged-descending-order walk across all loser chains; per-tx processing breaks
      cross-tx page consistency. Reapplies at: W42 txn rollback ordering, W67 raft conflict resolution.

  - **(SENIOR) When `undo_idempotent_double_run` / `clr_skipped_in_undo_loop` re-applies undo actions:**
    - Symptom: the second pass undoes already-undone records, corrupting state.
    - Why: CLRs from the first run aren't recognized as "skip" — either the kind check is missing or the skip used
      tx-state (which a mid-undo loser passes).
    - Fix: at the top of the loop, `if record.kind == RecordKind::Clr { cursor.advance_to(record.undo_next_lsn); continue; }`.
      The `undo_next_lsn` points to the record BEFORE the one the CLR undid, so the cursor advances cleanly.
    - Muscle: CLRs make UNDO idempotent ONLY if both the skip-CLR-by-kind rule AND the `undo_next_lsn` pointer are
      correct; tx-state is not a substitute. Reapplies at: W64 raft log compaction, W74 matching-engine restart.

  - **(EXPERT) When `crash_mid_undo_re_run_converges` reports diverged state on 12/1000 trials:**
    - Symptom: crashes mid-undo at specific LSN positions produce different final page bytes.
    - Why: the CLR was written to wal but the page's `pageLSN` wasn't stamped before the crash; re-run sees the CLR,
      thinks the undo happened, but the page still holds the original data.
    - Fix: stamp `page.pageLSN = clr.lsn` under the same page latch that performs the undo, before releasing it;
      re-run applies a CLR only if `page.pageLSN < clr.lsn`.
    - Cost avoided: silent durability hole — re-recovery loses the "already undone" signal (data corruption, not
      just slow). **(bar (c) violation)**
    - Muscle: CLR durability and page state must be coupled under one latch; otherwise re-recovery can't tell
      undone from not-undone. Reapplies at: W42 txn 2PC, W64 raft commit+apply.

  - **(EXPERT — perf) When `bench_30k_records_per_sec` reports 8k/sec (bar (c) violation):**
    - Symptom: ~4× below the 30k/sec bar; perf shows time blocked in the per-CLR `wal.append().await` fsync.
    - Why: every CLR is appended-and-awaited individually; one fsync (~125 µs flushing the dirty page) is paid per
      record instead of being amortized across a batch.
    - Fix: batch CLR appends through the existing group-commit; the loop pipelines a batch, then awaits the
      `durable_lsn` watermark once to cover the whole batch.
    - Cost avoided: ~125 µs/CLR (1 fsync/CLR) → ~2 µs/CLR amortized (1 fsync / 64 CLRs) ≈ **~64× fewer fsyncs**;
      throughput 8k/sec → ~500k/sec, clearing the 30k/sec bar by ~16×; an 800k-loser recovery ~100s → ~2s.
      **(bar (c) violation — blows the 10s recovery budget)**
    - Muscle: recovery phases benefit from the SAME amortization as steady-state ops — group commit applies; never
      one fsync per record on a recovery hot path. Reapplies at: W30 Checkpointer (Tue), W64 raft snapshot install.

    ```text
    pub struct Checkpointer<'a> { wal: &'a Wal, dpt: &'a DirtyPageTable, tt: &'a TransactionTable,

    impl Checkpointer<'_> {
        pub fn checkpoint(&self) -> Result<CheckpointLsn, Error>; // Begin → clone-snapshot → End → MANIFEST
        pub fn maybe_checkpoint(&self, cadence: &Cadence) -> Result<Option<CheckpointLsn>, Error>;
        fn safe_truncation_lsn(&self) -> Lsn; // min(DPT.recLSN, TT.oldest_active.firstLSN, readers.oldest_snapshot)
    }
    ```

    writes blocked — a p99 cliff. Fuzzy: clone under a shared lock held ~50 µs, serialize the clone unlocked ⇒
    writer stall **200 ms → 50 µs = ~4000× cliff**. The MANIFEST update is one fsync (~300 µs on NVMe) + one
    dir-fsync; cheap relative to recovery, mandatory for atomicity.
