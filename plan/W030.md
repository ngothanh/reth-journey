**Monday — ARIES undo pass**

- [ ] **Build**: `crates/recovery/src/undo.rs` — `UndoPass` rolls back all txs in `TransactionTable` from analysis.
  Walks each tx's chain via prevLSN field of each WAL record. Writes Compensation Log Records (CLRs) so undo is
  idempotent under re-crash. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: UNDO is ARIES's crown jewel — rolls back losers without re-doing winners. The
    trick: as you undo a record, you write a CLR describing the undo action. If you crash during undo and
    re-recover, REDO will *redo* the CLRs (idempotent), so no work is lost. This makes recovery
    time-bounded regardless of how many crashes occur. Mohan won the Turing Award for this insight.
    Downstream: Tuesday's `Recovery::recover`, W74 matching-engine restart, W80 ledger, W83 aeron archive,
    W95 mini-db.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: in-flight txs at crash time must be rolled back to "as if
    never started". Naive rollback (just walk prev_lsn backward) is correct ONLY if recovery is never
    re-interrupted. ARIES's CLR scheme makes UNDO itself idempotent — re-crashes during undo are
    bounded by the CLR chain.

  - **Requirements** — write in `crates/recovery/notes/30_undo_design.md`:
    - R1. Process records in **strictly descending LSN order** across ALL losers simultaneously
      (priority queue / max-heap on per-tx cursor).
    - R2. Every undone record gets a matching CLR with `undo_next_lsn = original.prev_lsn`.
    - R3. CLRs are NEVER undone themselves; explicit kind check in the loop.
    - R4. UNDO ∘ UNDO == UNDO (idempotence under re-recovery).
    - R5. After UNDO, losers' pages reflect "as if never started"; winners untouched.
    - R6. Per tx ending: write Abort/End record after all data records undone.
    - R7. Throughput ≥30k records/sec.
    - R8. 1000 random crash-during-undo simulations all converge.

  - **Design walk-through**:
    - D1. Why descending LSN order ACROSS txs (not per-tx)? (Hint: tx T1's record at LSN 100 and T2's
      at LSN 105 — undoing T1 first leaves T2 seeing an inconsistent page intermediate state.)
    - D2. `compute_undo` per RecordKind: Insert→Delete, Update→Update-with-old, Delete→Insert. What
      payload state must the original record carry? (Hint: old value for Update/Delete; nothing extra
      for Insert.)
    - D3. CLR's `undo_next_lsn` — purpose? (Hint: tells re-recovery "this record already undone; skip
      to prev_lsn".)
    - D4. Pre-mortem: undoing a CLR (the bug); what happens? (Hint: re-applies the original record;
      re-recovery toggles state forever.)

  - **Output**: `notes/30_undo_design.md` with R1–R8 + D1–D4 + the per-RecordKind undo table.

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  - **When `descending_lsn_order_across_txs` reports a fetch at LSN 90 after a fetch at LSN 100:**
    - Symptom: instrumentation logs out-of-order LSN fetches.
    - Why: UNDO processed tx T1 completely before starting T2; T1's records were 100, 95, 90; T2's
      records were 105, 102. Processing order: 100, 95, 90, 105, 102 — not descending.
    - Fix: priority queue (BinaryHeap) keyed on current undo-LSN per tx; pop the max LSN regardless of
      which tx; advance only that tx's cursor. The loop continues until all cursors exhausted.
    - Muscle: ARIES UNDO is a merged-descending-order walk across all loser chains; per-tx processing
      breaks cross-tx page consistency. Reapplies at: W42 txn rollback ordering, W67 raft conflict
      resolution.

  - **When `undo_idempotent_double_run` reports the second run re-applied undo actions:**
    - Symptom: second UNDO pass undoes already-undone records, corrupting state.
    - Why: CLRs from the first run aren't being recognized as "skip" by the second run. Either the
      kind check is missing, or the CLR's `undo_next_lsn` field is wrong.
    - Fix: at top of undo loop, `if record.kind == RecordKind::CLR { cursor.advance_to(record.undo_next_lsn);
      continue; }`. CLR's `undo_next_lsn` points to the record BEFORE the one CLR undid, so the
      cursor advances cleanly.
    - Muscle: CLRs make UNDO idempotent ONLY if both the skip-CLR rule AND the undo_next_lsn pointer
      are correct. Reapplies at: W64 raft log compaction, W74 matching-engine restart.

  - **When `crash_mid_undo_re_run_converges` reports diverged state on 12/1000 trials:**
    - Symptom: crashes mid-undo at specific LSN positions produce different final state.
    - Why: CLR was written but page.pageLSN wasn't updated before crash. Re-run sees the CLR (in wal),
      thinks the undo happened, but the page still has the original data.
    - Fix: CLR write + pageLSN update are atomic w.r.t. the page latch. The CLR's lsn is set ON the
      page; if pageLSN matches CLR's lsn, undo was applied. Re-run checks both.
    - Muscle: CLR durability + page state must be coupled; otherwise re-recovery loses the
      "already undone" signal. Reapplies at: W64 raft commit + apply, W42 txn 2PC.

  - **When `bench_30k_records_per_sec` reports 8k/sec:**
    - Symptom: 4× too slow; perf shows time in `wal.append` per CLR.
    - Why: every CLR is appended individually; wal's group commit has min-batch latency.
    - Fix: batch CLR appends via the existing group-commit; UNDO's loop doesn't await per CLR — it
      pipelines a batch, then awaits the durable_lsn watermark to cover the batch.
    - Cost avoided: 4× recovery throughput; 1 GiB wal recovery 40s → 10s.
    - Muscle: recovery phases benefit from the SAME amortization as steady-state operations — group
      commit applies. Reapplies at: W30 Checkpointer, W64 raft snapshot install.

  - **5-year failure mode** (write in `notes/30_undo_followup.md` after green): when MVCC replaces
    ARIES, UNDO becomes "discard the visible-version pointer to the in-flight version" — no CLRs. State
    the migration: `RecoveryStrategy::Undo` trait. Trigger: switching to MVCC versioning.

**Tuesday — `recovery::checkpoint` + ship**

- [ ] **Build**: `crates/recovery/src/checkpoint.rs` — `Checkpointer` writes Begin-Checkpoint and End-Checkpoint WAL
  records with current DPT + TT. Bounds recovery time. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: without checkpoints, recovery time grows with wal size — eventually unbounded.
    Fuzzy checkpoints take a snapshot CONCURRENTLY with running txs (no quiesce), bounding recovery latency
    to ~5 seconds. Production systems can't afford to pause for a clean snapshot. Downstream: drives wal
    truncation; W64 raft snapshot; W95 mini-db.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: recovery scans wal forward from min_rec_lsn; if there's no
    checkpoint, min_rec_lsn = 0 and recovery takes O(uptime). Checkpoints provide periodic snapshots
    so min_rec_lsn = recent_checkpoint_lsn, bounding recovery. Fuzzy = no pause.

  - **Requirements** — write in `crates/recovery/notes/30_checkpoint_design.md`:
    - R1. `Checkpointer::checkpoint` writes BeginCheckpoint, snapshots DPT/TT, writes EndCheckpoint
      with serialized snapshot.
    - R2. DPT/TT snapshots taken WITHOUT pausing txs (fuzzy).
    - R3. `MANIFEST` control file points to latest BeginCheckpoint LSN; updated atomically (temp +
      rename + fsync directory).
    - R4. On recovery, analysis starts from BeginCheckpoint LSN, NOT End — uses End's DPT/TT as priors.
    - R5. Wal truncation: `wal.truncate_below(safe_lsn)` where safe_lsn = min(DPT.recLSN,
      TT.oldest_active.firstLSN, readers.oldest_snapshot).
    - R6. Checkpoint cadence: drive by elapsed time (30s default), wal bytes since last (1 GiB), OR
      dirty page count (10k).
    - R7. Recovery on 1 GiB wal with checkpoint every 30s completes in ≤5s.
    - R8. 1000 random crash-during-checkpoint runs converge correctly.

  - **Design walk-through**:
    - D1. Sharp vs fuzzy: a sharp checkpoint pauses all writes. What's the OLTP cost?
    - D2. MANIFEST torn-write: a power loss mid-write to MANIFEST. Atomicity strategy?
    - D3. Truncation safety: a long-running reader holds an MVCC snapshot at LSN 100; checkpoint wants
      to truncate at 200. What goes wrong if you truncate?
    - D4. Pre-mortem: checkpoint during recovery; what corruption?

  - **Output**: `notes/30_checkpoint_design.md` with R1–R8 + D1–D4 + cadence policy.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: A → R → U is a strict sequence; any other order corrupts state.
    The facade enforces the sequence + propagates errors + writes a final checkpoint so subsequent crashes
    don't re-process the same wal.

  - **Requirements** — write in `crates/recovery/notes/30_recover_design.md`:
    - R1. Strict sequence: Analysis → Redo → Undo → final Checkpoint.
    - R2. Type-state pattern: each phase returns a token consumed by the next; you can't run Redo
      without an Analysis result, can't run Undo without a Redo result.
    - R3. `RecoveryReport` carries per-phase timings (analysis_ms, redo_ms, undo_ms,

    - R5. Recovery is the SOLE entry point during the recovery window; gated by an exclusive flock on
      wal.open.
    - R6. Empty wal: recover is a no-op; returns immediately.
    - R7. 1 GiB wal recovery completes in <10s end-to-end.
    - R8. VOPR-style property test: 1000 fault patterns, all converge.

  #### Phase 3 — Make the tests pass, one failure at a time (~40 min)

  - **When `cycle_full_claim_returns_err` reports SIGBUS instead of Err:**
    - Symptom: claim that would exceed body_size writes anyway and SIGBUSes.
    - Why: `fetch_add(size)` advanced the offset past `body_size` without checking. The reserved range
      is now in mmap-out-of-bounds territory.
    - Fix: CAS-loop the claim: load offset; if `offset + size > body_size`, return Err; else CAS
      (offset, offset+size); retry on CAS failure. `fetch_add` is not safe at the boundary.
    - Muscle: any atomic reservation at a bounded region must bounds-check BEFORE the bump; the bump
      and bound-check are not separately atomic. Reapplies at: W26 segment append, W31 mmap-queue
      term buffer, W77 aeron Publication.

  - **When `reader_sees_ready_flag_synchronization` reports uninit bytes:**
    - Symptom: loom finds a schedule where reader sees the ready flag as "ready" but the payload
      bytes still uninit.
    - Why: writer published ready flag with Relaxed store; consumer's Acquire load on ready flag
      doesn't fence the payload reads.
    - Fix: writer's ready-flag store is `Release`; reader's load is `Acquire`. The pair establishes
      happens-before: all writes before the Release (including payload memcpy) are visible after the
      Acquire.
    - Muscle: per-record ready-flag publishing requires Release-store on writer + Acquire-load on
      reader. Reapplies at: W31 wire schema (already covered), W74 matching-engine MBO publish, W77
      aeron frame publish.

    - Symptom: cycle boundary inconsistent across replicas in different timezones.
    - Why: roll-decision code used `chrono::Local::now()` instead of `chrono::Utc::now()`.
    - Fix: always UTC for time-based rolls; document the policy in module-level doc comments.
    - Muscle: replicated time-based decisions must agree on a single timezone; UTC is the default;

  #### Phase 1 — Problem, requirements, design (~25 min, no code yet)

  - **The problem this primitive solves**: traditional async runtimes (Tokio) work-steal tasks across
    threads; under contention the cache-line ping-pong dominates. Thread-per-core says: pin one OS
    thread to one CPU core; that thread owns its state; cross-thread communication is explicit
    message passing. ScyllaDB beats Cassandra 10× on the same hardware because of this.

    - R2. `ShardLocalState` is `!Send + !Sync` — compiler enforces no leakage.
    - R3. All cross-shard communication via `submit_to(target, f)` — no shared `Arc<Mutex>`.
    - R4. Per-shard executor (`LocalExecutor`) runs to natural quiescence; tasks cooperative-yield.
    - R5. `submit_to` round-trip p50 ≤500 ns, p99 ≤2 µs on same-NUMA.
    - R6. Mailbox is bounded SegQueue (W26) with backpressure on full.
    - R7. Idle path: spin → pause → futex-wait (W4 Backoff ladder).
    - R8. Shutdown protocol: drain → quiesce → exit threads in reverse order.
    - R9. Cross-shard batching (Seastar's `smp::poll_queues`) — one syscall amortizes N sends.
