**Monday — ARIES undo pass**

- [ ] **Build**: `crates/recovery/src/undo.rs` — `UndoPass` rolls back all txs in `TransactionTable` from analysis.
  Walks each tx's chain via prevLSN field of each WAL record. Writes Compensation Log Records (CLRs) so undo is
  idempotent under re-crash. (~105 min)
  - **Why**: UNDO is ARIES's crown jewel. It rolls back losers (in-flight txs at crash time) without re-doing winners. The brilliant trick: as you undo a record, you write a CLR (Compensation Log Record) describing the undo action. If you crash during undo and re-recover, REDO will *redo* the CLRs (idempotent), so no work is lost. This makes recovery TIME-BOUNDED regardless of how many crashes occur. Mohan won the Turing Award for this insight.
  - **Read first**: ARIES paper §3.3 "Undo Pass" — read this 4 times until you can explain the CLR-redo loop without notes. PostgreSQL doesn't do ARIES undo (it uses MVCC tombstones instead — interesting contrast). InnoDB rollback segments are the closest production reference.
  - **Design**:
    ```rust
    pub struct UndoPass<'a, R: Replayer + RandomAccess, P: PageProvider, W: WalWriter> {
        replayer: R,                    // for record fetch by LSN
        pool: &'a mut P,
        wal: &'a mut W,                 // we WRITE CLRs!
        tt: TransactionTable,
        losers: BTreeSet<TxId>,         // Active and Aborted txs from TT
    }
    impl<'a, R, P, W> UndoPass<'a, R, P, W> {
        pub fn run(mut self) -> Result<UndoStats, UndoError> {
            // Build the per-tx undo cursor: for each loser, find its current "to-undo-next" LSN.
            //   - If TT[tx].undo_next_lsn = Some(L), start there (resuming a previous undo).
            //   - Else, start at TT[tx].last_lsn.
            let mut cursors: BTreeMap<TxId, Option<Lsn>> = self.losers.iter()
                .map(|t| (*t, self.tt[t].undo_next_lsn.or(Some(self.tt[t].last_lsn))))
                .collect();
            
            // Process records in DESCENDING LSN order across all losers simultaneously.
            loop {
                let Some((&tx, &Some(lsn))) = cursors.iter().max_by_key(|(_, l)| **l) else { break; };
                let record = self.replayer.fetch(lsn)?;
                if is_clr(record.kind) {
                    // Skip — already undone. Advance to undo_next_lsn from the CLR.
                    cursors.insert(tx, record.undo_next_lsn);
                    continue;
                }
                // Undo the record's effect physically on the page.
                let page_id = extract_page_id(&record.payload);
                let page = self.pool.fetch_exclusive(page_id)?;
                let undo_payload = compute_undo(&record);  // e.g., for Insert: a Delete; for Update: an Update with old value
                apply_undo(page, &undo_payload)?;
                // Write CLR.
                let clr = WalRecord {
                    lsn: 0,                        // assigned by wal
                    kind: RecordKind::CLR,
                    tx_id: Some(tx),
                    prev_lsn: Some(self.tt[&tx].last_lsn),
                    undo_next_lsn: record.prev_lsn, // where to resume undo next
                    payload: undo_payload.into(),
                };
                let clr_lsn = self.wal.append(clr).await?;
                page.set_page_lsn(clr_lsn);
                self.tt.get_mut(&tx).unwrap().last_lsn = clr_lsn;
                // Advance cursor to prev_lsn (or done if None).
                cursors.insert(tx, record.prev_lsn);
                if record.prev_lsn.is_none() {
                    // All records undone — write Abort or End for this tx (TT cleanup).
                    self.wal.append(make_end(tx)).await?;
                    cursors.remove(&tx);
                }
            }
            Ok(UndoStats { txs_undone: self.losers.len() })
        }
    }
    ```
    **Invariants**:
    - UNDO processes records in *strictly descending LSN order* across all losers simultaneously (priority queue or max-heap).
    - Every undone record gets a matching CLR with `undo_next_lsn = original.prev_lsn`.
    - CLRs are *never* undone themselves; their kind is recognized in the undo loop.
    - After UNDO, a winner's pages reflect its committed state; a loser's pages reflect "as if never started".
    - UNDO is idempotent under re-crash: a CLR's existence means "this record was already undone"; re-running UNDO skips that record via the CLR's `undo_next_lsn`.
  - **Build steps**:
    1. (~20 min) Random-access wal fetcher: `Replayer::fetch(lsn) -> Result<WalRecord>` via segment+offset index.
    2. (~25 min) Multi-cursor descending-LSN driver (BTreeMap or BinaryHeap keyed on current undo-LSN).
    3. (~20 min) `compute_undo` per RecordKind: Insert→Delete, Update→Update-with-old, Delete→Insert.
    4. (~15 min) CLR write path; track CLR lsn back into TT.
    5. (~15 min) Per-tx "End" record after all undone.
    6. (~10 min) Tests: 10 losers each with 100 records; undo completes; replay-after-undo matches expected (loser's pages match pre-loser state).
    7. (~15 min) Crash-during-undo: kill UNDO mid-process; re-run from analysis → second pass picks up via undo_next_lsn → final state same as no-crash.
    8. (~10 min) Property: UNDO ∘ UNDO == UNDO (idempotence under re-recovery).
  - **Pitfalls**:
    - *Out-of-order undo across txs*: undoing tx T1's record at LSN 100 before T2's record at LSN 105 means T2 sees inconsistent state mid-undo. **Symptom**: CLR's compute_undo produces wrong value because page intermediate-state. **Fix**: ALWAYS process records in descending LSN order across all losers — no per-tx batching.
    - *Forgetting CLR's undo_next_lsn*: CLR's purpose is to point past the undone record so re-undo skips it. Without it, re-crash redoes the undo. **Symptom**: undo non-idempotent. **Fix**: CLR's `undo_next_lsn = original_record.prev_lsn`.
    - *Undoing CLRs themselves*: a CLR's "I undid record X" entry must NOT be undone — that would re-apply X. **Symptom**: re-recovery toggles state. **Fix**: explicit kind check at top of undo loop; CLRs advance cursor without applying.
    - *Page locks during UNDO*: holding exclusive latch across CLR's wal.append blocks the wal's group commit if wal and pages share the runtime. **Symptom**: deadlock. **Fix**: release latch, append CLR, re-acquire to apply page. Or run UNDO single-threaded with no concurrency; cleaner.
    - *Compute_undo for variable-length updates*: an Update record stores both old and new values; compute_undo just swaps. **Symptom**: corruption if record only stored new. **Fix**: at WRITE time, every Update/Delete payload includes old value for undo. Documented in W26 record schema.
    - *Tx with zero data records (just Begin/Abort)*: undo cursor immediately at Begin, prev_lsn = None, terminate. **Symptom**: panic on empty undo. **Fix**: handle cursor.None as natural termination.
    - *Crash AFTER the Abort/End record but before checkpoint*: TT no longer has this tx, but page may still have its data. **Symptom**: lost undo. **Fix**: only mark tx Aborted in TT after the End record is durable; checkpoint then drops it from TT.
  - **Test scenarios**:
    - 10 in-flight losers, 5 winners; UNDO undoes losers' effects; winners' pages untouched.
    - 100 losers each with 1000 data records: UNDO completes in O(total records).
    - Crash mid-UNDO at random LSN; re-run; final state byte-identical with single-pass UNDO.
    - Adversarial: tx of 1000 records; crash 50 times during its undo; each re-run picks up; eventually completes.
    - Property test: for any (committed, aborted, in-flight) tx mixture, recovery yields exactly the committed effects.
  - **Acceptance**:
    - 1000 random crash-during-undo simulations all converge to correct state.
    - Inheritance ratio ≥ 0.9 vs ARIES paper §3.3.
    - UNDO throughput: ≥ 30k records/sec.
  - **Downstream**: Tuesday wires `Recovery::recover` orchestration; W74 matching-engine restart recovers in-flight orders via this; W80 ledger restart; W83 aeron archive replay; W95 mini-db CAPSTONE re-derives.

**Tuesday — `recovery::checkpoint` + ship**

- [ ] **Build**: `crates/recovery/src/checkpoint.rs` — `Checkpointer` writes Begin-Checkpoint and End-Checkpoint WAL
  records with current DPT + TT. Bounds recovery time. (~105 min)
  - **Why**: Without checkpoints, recovery time grows with wal size — eventually unbounded. Fuzzy checkpoints take a snapshot CONCURRENTLY with running txs (no quiesce), bounding recovery latency to ~5 seconds regardless of uptime. The fuzzy property is critical: production systems can't afford to pause for a clean snapshot.
  - **Read first**: ARIES paper §4 "Checkpoints"; PostgreSQL `src/backend/access/transam/xlog.c::CreateCheckPoint`; the comparison with InnoDB's "sharp" vs "fuzzy" checkpoint modes.
  - **Design**:
    ```rust
    pub struct Checkpointer<'a, W: WalWriter, P: PageProvider> {
        wal: &'a W,
        pool: &'a P,
        dpt_source: Arc<RwLock<DirtyPageTable>>,
        tt_source: Arc<RwLock<TransactionTable>>,
        config: CheckpointConfig,  // { period, max_dirty_pages, max_wal_growth }
    }
    impl<'a, W, P> Checkpointer<'a, W, P> {
        pub async fn checkpoint(&self) -> Result<CheckpointResult, Error> {
            // 1. Write BeginCheckpoint record. Get its LSN = bc_lsn.
            // 2. Concurrently with ongoing txs, snapshot DPT & TT.
            //    (Hold read locks briefly, just to copy maps.)
            // 3. Flush a subset of dirty pages whose pageLSN < some_threshold.
            //    (Optional but speeds up recovery.)
            // 4. Write EndCheckpoint record carrying serialized (DPT, TT). Get LSN = ec_lsn.
            // 5. Record in a control file: latest_checkpoint = bc_lsn.
            //    (Operator-visible; replay starts from here.)
            // 6. Optional: truncate wal segments older than min(DPT.recLSN, TT.oldest_active.firstLSN).
        }
    }
    ```
    **Invariants**:
    - BeginCheckpoint LSN < EndCheckpoint LSN.
    - DPT/TT in EndCheckpoint reflect a state that "happened" between BeginCheckpoint and EndCheckpoint — exact moment is fuzzy.
    - On recovery, analysis starts from BeginCheckpoint LSN (not End), using End's DPT/TT as priors.
    - Control file (`MANIFEST`) is updated atomically (write-temp-rename) — power loss either preserves old checkpoint or commits new.
    - Wal truncation only removes segments whose ALL records are either Committed-and-flushed OR Aborted-and-undone-and-CLR-flushed.
  - **Build steps**:
    1. (~15 min) `BeginCheckpoint` record (empty payload).
    2. (~20 min) `EndCheckpoint` record with serialized DPT (varint-encoded BTreeMap<PageId, Lsn>) and TT.
    3. (~20 min) Concurrent snapshot: brief locks on DPT/TT to copy.
    4. (~15 min) Subset-flush optimization: iterate pool's dirty pages, msync those whose pageLSN < high-water.
    5. (~15 min) Atomic MANIFEST update (`MANIFEST.tmp` + rename).
    6. (~10 min) Wal truncation: compute min safe LSN, call `wal.truncate_below(safe_lsn)`.
    7. (~10 min) Tests: take checkpoint, kill, recover → analysis starts from BeginCheckpoint.
  - **Pitfalls**:
    - *Sharp vs fuzzy*: sharp checkpoint quiesces all writes — fine for batch jobs, disaster for OLTP. **Symptom**: app pauses N ms every checkpoint. **Fix**: fuzzy — snapshot DPT/TT under brief locks, don't pause txs.
    - *MANIFEST atomicity*: writing in-place can leave torn file on crash → no recoverable checkpoint. **Symptom**: post-crash recovery walks wal from genesis. **Fix**: write-temp + atomic rename + fsync the directory.
    - *Truncating too aggressively*: wal truncation that drops records still referenced by some old reader breaks MVCC snapshots. **Symptom**: long-running analytics queries crash. **Fix**: truncation respects min(DPT.recLSN, TT.oldest_active, readers.oldest_snapshot_lsn).
    - *Checkpoint frequency tuning*: too often = wasted writes; too rare = long recovery. **Symptom**: either disk thrash or 10-minute recovery. **Fix**: drive by either (a) elapsed time (default 30s), (b) wal bytes since last (default 1 GiB), (c) dirty-page count (default 10k).
    - *Checkpoint during recovery*: don't take checkpoints during the recover() process — risk of partial state. **Symptom**: corruption. **Fix**: gate Checkpointer behind a "ready" atomic that recover() sets.
  - **Test scenarios**:
    - 1k txs running, checkpoint at random points; crash; recovery converges.
    - Checkpoint with empty DPT (no dirty pages): EndCheckpoint has empty payload.
    - Checkpoint truncation: ensure no record referenced by any TT/DPT entry is dropped.
    - Property: for any (workload, checkpoint_pattern), recovery → same final state as no-checkpoint.
  - **Acceptance**:
    - Recovery time bounded to ~5s on 1 GiB wal with checkpoint every 30s.
    - 1000 random crash-during-checkpoint runs converge correctly.
    - Inheritance ratio ≥ 0.85 vs PostgreSQL fuzzy checkpoint.
  - **Downstream**: drives the wal truncation in W26's `Wal::truncate_below`; W64 raft snapshot uses analogous fuzzy snapshot; W95 mini-db CAPSTONE.
- [ ] **Build**: `crates/recovery/src/lib.rs` —
  `Recovery::recover(wal: &Wal, page_provider: &mut impl PageProvider) -> Result<(), Error>` orchestrating analysis →
  redo → undo. (~105 min)
  - **Why**: The public facade glues Analysis → Redo → Undo in order. It's the single function every storage user calls on startup. Its correctness is the difference between "system boots after crash" and "operator escalates to data recovery." Should be 30 lines of orchestration; the work is all in the three sub-modules.
  - **Read first**: PostgreSQL `src/backend/access/transam/xlog.c::StartupXLOG` (the orchestration); InnoDB `srv0start.cc::srv_start`.
  - **Design**:
    ```rust
    pub struct Recovery;
    impl Recovery {
        pub async fn recover<P: PageProvider, W: WalReadWrite>(
            wal: &W,
            pool: &mut P,
        ) -> Result<RecoveryReport, RecoveryError> {
            // Phase 1: Analysis
            let analysis = AnalysisPass::new(wal.replay()).run()?;
            // Phase 2: Redo
            let redo_stats = RedoPass::new(wal.replay(), pool, &analysis.dpt, analysis.min_rec_lsn).run()?;
            // Phase 3: Undo (only over losers).
            let losers: BTreeSet<TxId> = analysis.tt.iter()
                .filter(|(_, e)| e.status != TxStatus::Committed)
                .map(|(t, _)| *t).collect();
            let undo_stats = UndoPass::new(wal.replay(), pool, wal, analysis.tt, losers).run()?;
            // Phase 4: Final checkpoint (so future crashes don't re-recover).
            Checkpointer::new(wal, pool).checkpoint().await?;
            Ok(RecoveryReport { analysis, redo_stats, undo_stats })
        }
    }
    ```
    **Invariants**:
    - Three phases run in strict order: A → R → U.
    - At end of recovery, no in-flight tx remains; pool state matches "moment of last committed tx's commit LSN."
    - Post-recovery, a final checkpoint is written so subsequent crashes don't re-process the same wal.
    - Recovery is the SOLE entry point; no other code paths run concurrently during recovery.
  - **Build steps**:
    1. (~20 min) `Recovery::recover` orchestrator with the 4-phase sequence.
    2. (~15 min) `RecoveryReport` with timing breakdown (analysis_ms, redo_ms, undo_ms, records_redone, txs_undone).
    3. (~20 min) Integration test: stage a wal with mixed committed/aborted/in-flight txs; recover; verify final state.
    4. (~20 min) End-to-end crash injection: random byte during workload → recover → state byte-identical to "no-crash" baseline (modulo aborted/in-flight tx effects).
    5. (~15 min) Hook into `Wal::open` so storage-trie's `storage_trie::open` calls recover automatically.
    6. (~15 min) Tag `recovery v0.5.0` after green.
  - **Pitfalls**:
    - *Out-of-order phases*: running REDO before ANALYSIS (no DPT, no filter) → over-applies records. **Symptom**: corruption. **Fix**: explicit sequence, type-state pattern preventing skips.
    - *Forgotten final checkpoint*: recover() doesn't checkpoint → next crash re-processes same wal. **Symptom**: recovery takes longer each crash. **Fix**: final checkpoint is part of recover.
    - *Error propagation*: a failure mid-recovery (e.g., page read error) must NOT silently exit. **Symptom**: silent corruption. **Fix**: errors propagate; caller decides retry vs operator escalation.
    - *Concurrent access during recover*: opening Wal twice (e.g., two `Wal::open` calls) → recovery races. **Symptom**: undefined. **Fix**: `Wal::open` takes exclusive flock; second open returns AlreadyInUse.
  - **Test scenarios**:
    - End-to-end: 1000 txs, half committed; SIGKILL at random; recover; final state matches expected.
    - Crash mid-recovery: SIGKILL during recover(); re-run; converges.
    - Empty wal: recover is a no-op; returns immediately.
    - Checkpoint-only wal (no data records since last checkpoint): recover is fast.
    - Long-tail wal (no checkpoint, 100 GB of records): recover succeeds in bounded time (full scan, but completes).
  - **Acceptance**:
    - End-to-end VOPR-style property test: 1000 fault patterns, all converge.
    - Recovery on a 1 GiB wal completes in < 10s.
  - **Downstream**: W30 Saturday wires `storage_trie::open()` to call recover; same pattern used in W64 raft restart, W74 matching restart, W80 ledger restart, W83 aeron archive replay, W95 mini-db. THIS is the universal restart-correctness substrate.

- [ ] [NEW v2] **Build**: `crates/mmap-queue/src/cycle.rs` — `CycleFile { path, mmap: MmapMut, header, write_offset }`. Roll trigger: daily | hourly | size-based. (~60 min)
  - **Why**: Chronicle Queue (net.openhft) is the dominant low-latency JVM IPC queue — used in HFT for sub-microsecond message passing. Its CYCLE FILE concept (one mmap-backed file per time period, rolled at boundaries) gives O(1) reader random access via cycle index + offset, while keeping each file bounded for retention. This is structurally DIFFERENT from wal (W26): wal is append-only crash-recovery journal; mmap-queue is random-access reader/writer queue with multi-consumer support and no centralized fsync barrier.
  - **Read first**: Chronicle Queue Java source `chronicle-queue/src/main/java/net/openhft/chronicle/queue/impl/single/SingleChronicleQueueStore.java` (cycle layout) and `RollCycles.java` (roll-cycle enum). Also Peter Lawrey's blog posts on Chronicle Queue architecture. Compare with Aeron Archive's segment files (also cycle-style).
  - **Design**:
    ```rust
    pub struct CycleFile {
        path: PathBuf,
        file: File,
        mmap: MmapMut,            // PROT_R/W, MAP_SHARED, may be ≥ 1 GiB
        header: &'static CycleHeader,  // first 128 bytes
        // Multi-producer write: atomic claim-and-advance.
        write_offset: AtomicU64,  // bytes from header.body_start
        cycle_id: CycleId,
    }
    #[repr(C, align(64))]
    pub struct CycleHeader {
        magic: [u8; 8],            // b"MMQ-CYC1"
        version: u32,
        flags: u32,
        cycle_id: u64,             // e.g., days since epoch
        first_index: u64,           // monotone index of first record in this cycle
        roll_period_secs: u32,
        body_offset: u32,           // = 128
        body_size: u64,             // total mmap minus header
        sub_index_offset: u64,      // pointer to per-cycle index table (built lazily)
        last_index_offset: AtomicU64,   // points to footer; advances on write
        _reserved: [u8; 56],
    }
    pub enum RollCycle {
        Hourly,                  // ~3600 cycles/day
        Daily,                   // 1 cycle/day
        SizeBased(usize),        // roll when body_offset crosses threshold
    }
    ```
    **Invariants**:
    - Cycle file is fallocated to its max size up front; growth is virtual (sparse on Linux).
    - `write_offset` advances monotonically via `fetch_add` per record.
    - Cycle ID is monotonic; readers can locate by (cycle_id, offset) tuple.
    - Roll boundary: clock-aligned for time-based; size-aligned for size-based.
    - Header magic is the SHA-12 prefix of a known string — checking it rejects accidental opens of unrelated files.
  - **Build steps**:
    1. (~10 min) `CycleHeader` `#[repr(C)]` with explicit field sizes and alignment.
    2. (~10 min) `CycleFile::create(path, cycle_id, roll_period, body_size)` — fallocate + write header + msync.
    3. (~10 min) `CycleFile::open(path)` — mmap, validate header, recover write_offset by scanning records.
    4. (~10 min) Roll-cycle decision: given `now` and `cycle_id`, decide whether to roll. Use chrono or std::time.
    5. (~10 min) `claim_record_space(size)` — atomic `fetch_add` returning `(offset, slice_to_fill)` OR `Err(CycleFull)`.
    6. (~10 min) Tests: create + open + claim + scan; roll trigger.
  - **Pitfalls**:
    - *Time-zone gotchas on roll*: "daily" cycle aligned to UTC vs local time. **Symptom**: cycle boundary inconsistent across replicas in different regions. **Fix**: roll on UTC.
    - *Concurrent writer claim races*: two writers `fetch_add(size)` simultaneously — both succeed, but if their writes collide (overlap), data corruption. **Symptom**: garbled records on heavy concurrency. **Fix**: `fetch_add` reserves the range; writers write strictly within their reserved range. SO LONG AS reservation succeeds, no overlap is possible.
    - *Cycle full mid-record*: writer claims space, but claim crosses body_size. **Symptom**: write into mmap-out-of-bounds → SIGBUS. **Fix**: claim function compares `prev + size <= body_size`; on overflow, return `Err(CycleFull)` *atomically* (CAS-loop the offset).
    - *Sparse-file metadata cost*: fallocate creates a hole; first write to each 4 KiB page allocates physical block — kernel may stutter under burst. **Symptom**: tail latency spikes during ramp-up. **Fix**: `fallocate(FALLOC_FL_ZERO_RANGE)` to eagerly allocate; or write a single byte to each page on open (slow first-open, fast steady-state).
    - *Reader at EOF detection*: a reader scanning records can't tell "next byte is uninitialized junk" vs "next byte is just-written record". **Symptom**: reader spins reading garbage. **Fix**: per-record header has a 4-byte "ready" flag written LAST after CRC; reader sees flag == 0 → wait/spin.
    - *MS_SYNC vs MS_ASYNC*: msync(MS_SYNC) blocks until disk-confirmed; MS_ASYNC schedules but returns immediately. mmap-queue uses MS_ASYNC for throughput (durability handled at higher layer). **Symptom**: throughput surprisingly low if you use MS_SYNC inadvertently. **Fix**: default to MS_ASYNC; expose MS_SYNC only on explicit `sync()` API.
    - *EOF vs roll vs corruption ambiguity*: when reader hits the end of valid records, three causes possible: (1) writer at EOF, (2) cycle about to roll, (3) corruption. **Symptom**: reader can't decide whether to wait or rotate. **Fix**: zero-init body region at fallocate (so all-zero = EOF/uninit, definitely safe); writer's "ready" flag distinguishes uninit from in-flight.
  - **Test scenarios**:
    - 1M records, 100 bytes each, single producer; reader reads all 1M in order.
    - 16 producers + 4 readers concurrent on same cycle: aggregate throughput ≥ 10 M records/sec, no duplicates.
    - Cycle full: claim returns Err, caller rotates to new cycle.
    - Roll at boundary: writers transition cleanly to new cycle without reader noticing (modulo cycle_id field).
    - Crash injection: SIGKILL mid-write; reopen; scan recovers all complete records.
  - **Acceptance**:
    - Single-producer write: ≥ 5 M records/sec.
    - Multi-producer write: ≥ 10 M records/sec at 16 producers.
    - Scan throughput: ≥ 50 M records/sec (cold) / 200 M/sec (warm).
    - Inheritance ratio target ≥ 0.85 vs Chronicle Queue's cycle file format.
  - **Downstream**: W74 matching-engine uses mmap-queue for order ingress (vs wal which is for post-match persistence); W76 marketdata feed-handler reads from queue; W83 aeron archive references this pattern; W85 mmap-queue v0.5 builds excerpt/wire/index modules on this base.

- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/shard.rs` — `Shard { id: ShardId, core_affinity: CoreId, executor: LocalExecutor, mailbox: SegQueue<Task> }`. Pinned to one CPU core via `core_affinity` crate. (~75 min)
  - **Why**: Seastar's "shared-nothing thread-per-core" architecture (used by ScyllaDB, Redpanda) eliminates the cache-line ping-pong of shared-state concurrency: each core owns its own state, communication is by *message passing* across explicit shard boundaries. ScyllaDB beats Cassandra by 10× on the same hardware *because* of this design. For HFT, the only way to hit sub-microsecond p99 is thread-per-core with no shared mutables. Mirroring Seastar precisely matters because every primitive in this runtime composes (or doesn't) with the rest of the ecosystem.
  - **Read first**: Seastar `include/seastar/core/reactor.hh` + `core/smp.hh` (the SMP shard machinery) + `core/sharded.hh` (the `sharded<T>` pattern). Avi Kivity's talk "How Asynchronous Programming Differs in C++ vs ScyllaDB" on YouTube. Glommio (Rust port of Seastar) source `glommio/src/executor/mod.rs` for an existing Rust shape.
  - **Design**:
    ```rust
    pub struct Shard {
        id: ShardId,                       // 0..N where N = num_cores
        core_affinity: CoreId,
        executor: LocalExecutor,           // single-threaded, no work-stealing
        mailbox: SegQueue<RemoteTask>,     // inbound from other shards
        outbox_caches: Vec<MailboxRef>,    // [N] one cache per peer shard for outbound batching
        local_state: UnsafeCell<ShardLocalState>,  // !Sync — only this shard accesses
        stop: AtomicBool,
    }
    pub struct ShardLocalState {
        // Each shard's per-core data structures — NEVER shared across shards.
        epoch_guard_pool: ...,
        timer_wheel: HierarchicalTimerWheel,
        local_stats: LocalCounters,
    }
    pub struct RemoteTask {
        target_shard: ShardId,
        f: Box<dyn FnOnce(&mut ShardLocalState) + Send>,  // executes on target's thread
    }
    impl Shard {
        pub fn spawn_blocking(&self, f: impl FnOnce()) { ... }
        pub fn spawn_local<F: Future + 'static>(&self, fut: F) -> JoinHandle<F::Output>;
        pub async fn submit_to<F, R>(&self, target: ShardId, f: F) -> R
            where F: FnOnce(&mut ShardLocalState) -> R + Send + 'static,
                  R: Send + 'static;
    }
    ```
    **Invariants**:
    - Each shard binds to exactly one CPU core (via `pthread_setaffinity_np` on Linux / `thread_policy_set` on macOS).
    - `ShardLocalState` is `!Send + !Sync` (within the shard) — compiler enforces no leakage.
    - All cross-shard communication goes through `submit_to`; no shared `Arc<Mutex>`.
    - Each shard's executor runs to *natural quiescence* between mailbox polls (no preemption inside a task; tasks must be cooperative-yield).
    - Shard IDs are dense (0..N), matching core IDs after applying any user-specified pin map.
  - **Build steps**:
    1. (~15 min) `Shard::start(id, core_affinity, num_shards)` — spawn an OS thread, pin via `core_affinity::set_for_current`.
    2. (~15 min) Main loop: drain mailbox, poll executor, idle yield with `std::hint::spin_loop()` or `pause` instruction.
    3. (~15 min) `submit_to` API: serialize the closure into the target's mailbox; await result via a oneshot.
    4. (~10 min) Outbound batching: per-peer-shard `MailboxRef` flushes when full or at end of poll cycle (Seastar calls this "smp::poll_queues" or "consumer/producer queues").
    5. (~10 min) `ShardLocalState` with PhantomData<*const ()> to ensure !Send.
    6. (~10 min) Tests: ping-pong between 2 shards; many-to-one fan-in; affinity verified via `sched_getaffinity`.
  - **Pitfalls**:
    - *FnOnce capture pitfalls*: closures sent to other shards must NOT capture `Rc`/`RefCell` (not Send) or shard-local refs (UB). **Symptom**: compile error (good) or UB at runtime (bad if `unsafe impl Send` is forced). **Fix**: trait-object `Box<dyn FnOnce(&mut ShardLocalState) + Send>`; compiler rejects non-Send captures naturally.
    - *Core affinity not actually applied*: setting affinity post-thread-start can fail silently on some platforms. **Symptom**: shards drift across cores under load, p99 latency suffers. **Fix**: set affinity FIRST IN the thread function (top of run()), assert via `sched_getaffinity` returns exactly one CPU.
    - *NUMA-local memory allocation*: a shard pinned to NUMA node 0 should allocate from node 0 memory. **Symptom**: random cross-socket latency spikes. **Fix**: `numactl --cpunodebind=0 --membind=0`; or at thread start, `set_mempolicy(MPOL_BIND, ...)` to local node.
    - *Mailbox unboundedness*: `SegQueue` is unbounded; runaway producer OOMs target shard. **Symptom**: OOM kill. **Fix**: bounded queue with backpressure; on full, sender retries or shed.
    - *Stealing/migration*: OS scheduler can still migrate the thread under contention even with affinity (if affinity is "preferred" not "strict"). **Symptom**: occasional p99 spikes. **Fix**: `SCHED_FIFO` real-time scheduler + `mlockall` to prevent migration on Linux; document privilege requirement.
    - *Quiescence detection*: how does the main loop know "no work to do, idle"? **Symptom**: 100% CPU even when idle. **Fix**: combine mailbox-empty + executor-idle + no-timers checks; descend through spin → pause → futex-wait hierarchy (similar to Seastar's "reactor sleep" with hard wait threshold).
    - *Shutdown ordering*: stopping shard 0 first while shard 1 still sends to it → lost messages. **Symptom**: hang on shutdown. **Fix**: shutdown protocol: drain phase (all submit_to refused; in-flight finish), then quiesce, then exit threads in reverse order.
    - *Hierarchical timer wheel*: each shard needs efficient `sleep_until(deadline)` for many concurrent tasks. **Symptom**: O(N) timer scans dominate. **Fix**: hierarchical timer wheel (HashedWheelTimer) with O(1) insert + O(1) tick.
    - *Yielding across submit_to*: holding a `&mut ShardLocalState` across an `await` is impossible (not Send). **Symptom**: borrow-checker rejects. **Fix**: take snapshot of needed state, drop ref, await, then re-borrow. This is THE major API friction; document it heavily.
