(~total 165 min)
  - **Phase 1 (compact — seal in `notes/125_prune_prediction.md` before coding):**
    - *Prediction (sealed)*: a proposal B's own QC has just become the high-QC, while the commit point still sits *below* B's height (the normal pipelined state). Predict what the predicate `high_qc.height() >= h && !committed_chain_includes(B)` says about B — and whether that is correct. Seal it before reading the traps below.
    - *Back-of-envelope*: terminal-event bookkeeping must be amortized O(1) per event (a `FixedMap` remove + ring push ≈ ~50 ns, 0 allocs); an O(pending) scan per view at 10k outstanding handles ≈ 10k × ~20 ns ≈ **~200 µs/view** of pure overhead — a bar-(c) cliff hiding in a liveness feature.
    - *Pre-mortem (interleaving)*: B proposed at height h → QC(B) forms and becomes high-QC → commit point lags one view → a committed-chain-keyed prune abandons B → client resubmits → B commits next view → the same op executes twice unless downstream idempotency catches it; "never both" is broken at the trait boundary while every unit test on healed schedules stays green.
  - 🔧 **Why this matters**: this is the one place the BFT impl earns the O5 amendment. Under VSR, abandonment = a view-change supersession event (observable). Under BFT, a proposal can be **orphaned-before-slot** (W118 A2) with no fill event — so the core must *actively* prove a handle is dead. The decision rule (cleared as impl-only): a handle's block `B` is **permanently dead iff `high_qc.height() >= B.height` AND `B` is NOT an ancestor-or-self of the high-QC's block** (the Jolteon limbo-bound: given view-monotonic high-QC adoption, no honest leader can extend a block *off the high-QC chain* at-or-below the high-QC's height). The predicate is keyed to the **high-QC chain, NOT the committed chain** — the committed chain lags the high-QC by the pipeline depth, so keying to it misfires (trap 3). The three traps: (1) **false-positive prune (timeout-keyed)** — abandoning a handle during a *temporary* post-view-change limbo where it could still be re-proposed (high-QC has NOT yet passed it) → a spurious `Abandoned` for an op that later commits (violates "never both"); (2) **false-negative / hang** — never deciding a genuinely-orphaned handle is dead → it hangs forever (violates "never neither" — the O5 leak itself); (3) **false-positive prune (wrong-chain-keyed)** — testing `!committed_chain_includes(B)`: a proposal whose OWN QC just became the high-QC satisfies `high_qc.height() >= B.height` (its own height!) while the commit point is still below it → falsely abandoned, then commits one view later → "never both" violated on the happy path. The bounded per-active-view store from W124 (`DetectEquivocation`'s `seen`) is the same structure pruned here as views finalize.
  - *Contract* (signature-level): `struct Outstanding { handle_to_block: FixedMap<ProposalHandle, (Height, Digest)> } fn on_commit_advance(&mut self) { for (h, (ht, dg)) in &self.outstanding { if committed_at(ht).map_or(false, |c| c != dg) || (self.high_qc.height() >= ht && !self.is_ancestor_or_self(dg, self.high_qc.block())) { self.abandon(h); } } } fn abandon(&mut self, h) { self.outstanding.remove(h); self.pending_abandoned.push(h); } // drain_abandoned drains pending_abandoned. NOTE: ancestor-or-self of the HIGH-QC block — never `committed_chain_includes` (the wrong-chain trap).`
  - **Tests (the make-pass card — engineered to trap both failure directions):**
    - `orphaned_before_slot_eventually_abandoned` (the O5 case on the REAL BFT impl) — propose a block, force a pacemaker view-change that extends the high-QC past it (no superseding commit at its slot); assert the handle appears on `drain_abandoned` **exactly once** within a bounded view-count, and the client gets `Err(Abandoned)` not a hang. (The W91 `test_orphaned_proposal_before_slot_is_abandoned` now runs against `DetectEquivocation`+`PipelinedHotStuffView`, not the `DropSlotEveryHeightView` stub.)
    - `temporary_limbo_not_falsely_abandoned` — a proposal in a view that times out but whose block is still extendable by the next leader (high-QC has NOT passed it) is **NOT** abandoned; it commits on the next view → resolves via `drain_committed`, never `drain_abandoned`. Traps the false-positive.
    - `exactly_one_terminal_event_per_handle` — property test over random fault schedules: every `propose`d handle terminates **exactly once** (committed XOR abandoned, never both, never neither) *(over schedules that eventually heal — the replica remains connected to a quorum; matches the W129 scenario-5 phrasing)*. This IS the liveness clause, made executable.
    - 🪤 **trap `block_on_high_qc_chain_but_uncommitted_not_abandoned` (EXPERT)** — drive B so that **B's own QC becomes the high-QC** while the commit point is still below B's height (the ordinary pipelined state); assert B is **NOT** abandoned (`high_qc.height() >= h` holds, but B *is* ancestor-or-self of the high-QC block); B then commits one view later → resolves via `drain_committed` **only**. Traps the committed-chain-keyed predicate (`!committed_chain_includes`) — which falsely abandons exactly this block.
