  - **Read first**:

  - **Design** (Raft state machine, Figure 2):
    ```text
    Persistent state (on all servers, must survive crash):
      current_term: u64                  // latest term seen, monotonic
      voted_for: Option<NodeId>          // candidate this node voted for in current_term
      log: Vec<LogEntry>                 // command + term + index

    Volatile state (all servers):
      commit_index: u64                  // highest log entry known committed
      last_applied: u64                  // highest log entry applied to state machine

    Volatile state (leader only):
      next_index: HashMap<NodeId, u64>   // next log entry to send to each follower
      match_index: HashMap<NodeId, u64>  // highest log entry replicated on each follower

    Roles: Follower | Candidate | Leader
    ```
    **Invariants** (paper §5.4 + Figure 3):
    1. **Election Safety**: at most one leader per term.
    2. **Leader Append-Only**: leaders never overwrite/delete their log entries (only append).
    3. **Log Matching**: if two logs have an entry with same (term, index), all entries up to that index are identical.
    4. **Leader Completeness**: if entry committed in term T, present in all leaders of term > T.
    5. **State Machine Safety**: if a server has applied entry at index i, no other server applies a different entry at same i.
  - **Build steps** (today: paper-only):
    1. (~10 min) Sketch the 3 RPCs from Figure 2: RequestVote (params: term, candidate_id, last_log_index, last_log_term; returns: term, vote_granted) and AppendEntries (params: term, leader_id, prev_log_index, prev_log_term, entries, leader_commit; returns: term, success).
    2. (~10 min) Election rules: candidate increments term; votes for self; broadcasts RequestVote. On majority votes → leader. Election timeout = random 150-300 ms (asymmetric to avoid split votes).
    3. (~10 min) Election restriction (§5.4.1): voter grants vote ONLY IF candidate's log is "at least as up-to-date" as voter's (last_log_term newer OR same term + last_log_index ≥). Prevents leader-completeness violation.
    4. (~10 min) Vote semantics: voted_for is per-term. Reset to None when term increases. Persisted BEFORE replying.
    5. (~5 min) Heartbeat semantics: leader sends empty AppendEntries every ≤ election_timeout/3 to suppress follower elections.
  - **Pitfalls** (named, distributed-systems):
    - *Split votes*: 5-node cluster with synchronized timeouts → all become candidates simultaneously → split votes → no leader. **Symptom**: cluster live-locks at election. **Fix**: RANDOMIZED election timeout in `[150ms, 300ms]`. Critical: random per-NODE (each node samples independently) AND per-ATTEMPT (re-randomize on each election round).
    - *Term confusion (stale leader)*: leader at term 5 partitioned; new leader elected at term 6. Old leader rejoins, sends AppendEntries with term=5. Follower sees term 5 < 6 → reject. But naive impl might accept. **Symptom**: 2-leader scenario; conflicting commits. **Fix**: ALL RPC handlers compare term first: `if rpc.term < self.term { return Err(StaleTerm); }`. If `rpc.term > self.term`, step down to Follower immediately.
    - *Byzantine voting (vote-twice)*: a faulty follower votes for two candidates in same term. **Symptom**: two candidates each get N/2 votes; both think they won. **Fix**: voted_for persisted PERSISTENTLY (durable WAL fsync before vote-grant reply); election term tracked monotonically. Raft is NOT Byzantine-fault-tolerant (use BFT W64+ for that); but persistent voted_for prevents accidental double-vote.
    - *Pre-vote phase missing*: candidate increments term to start election → wins → discovers it's outdated → steps down. Term inflation churns useless. **Symptom**: term churn under unreliable network. **Fix**: implement Pre-Vote extension (Ongaro thesis §9.6): pre-RequestVote without incrementing term, only escalate to real RequestVote if pre-vote majority would grant.
    - *Liveness loss under asymmetric partitions*: node A reachable→B but B unreachable→A. A times out, becomes candidate, increments term repeatedly. Each successful split election forces real leader to step down. **Symptom**: cluster never makes progress despite quorum being available. **Fix**: Pre-Vote + ensure candidate can RECEIVE RequestVote replies before promoting term increment.
  - **Test scenarios** (paper-level reasoning):
    - 5-node cluster, kill leader → election within 1 timeout window. Verify majority of remaining nodes converge on same new leader.
    - Network partition splits 3-2: majority side elects leader, makes progress. Minority side cannot elect leader (no majority of original 5 reachable).
    - Reunite partition: minority's old leader (still at lower term) discovers higher term via heartbeat, steps down.
  - **Acceptance**: paper notes committed; Figure 2 RPC + state summary internalized; pre-vote variant noted as future extension.

- [ ] **Build**: `crates/consensus-raft/src/state.rs` — `Role` enum (Follower, Candidate, Leader).
  `Persistent { current_term, voted_for, log }` and `Volatile { commit_index, last_applied }`. (~150 min)
  - **Why**: State separation (persistent vs volatile) IS the safety boundary. Mixing them = data loss on crash. Persistent fields MUST be fsync'd before any RPC reply that depends on them.
  - *Back-of-envelope* (bar (c) — every RequestVote handler + every leader heartbeat reads/writes RaftState):
    - Workload: 7-node cluster (HFT-typical for failure resilience without overhead), heartbeat 50 ms, election timeout 200-400 ms ⇒ heartbeats: 20/s × 6 followers = 120 sends/s on leader; AppendEntries on a busy node: ~10k ops/s during catchup.
    - `persist_term_and_vote`: 2 × u64 + 1 × Option<NodeId> = ~24 B written, but fsync is the killer — **~10 µs on NVMe, ~100-200 µs on SATA SSD, ~1-10 ms on spinning disk**. This sets the election RTT floor; you cannot vote faster than your fsync.
    - Role transition (`become_follower/candidate/leader`): updates `Role` enum (32-64 B), resets HashMaps; ≈ ~50 ns when maps are pre-allocated; ≈ 500-1000 ns + ~50 ns/peer malloc if HashMaps are freshly allocated on every transition. At 1 transition/s steady-state, this is negligible; under leadership churn (network blips) it spikes.
    - Memory: `RaftState` ≈ ~1-4 KB (depends on log handle + state_machine size); easily fits in L1.
    - Hot path read (`current_term` check in every RPC handler): single u64 load ≈ **0.5-5 ns** depending on cache state. Goes red only if behind a `Mutex<RaftState>` — see perf pitfall.
  - **Design**:
    ```rust
    pub enum Role {
        Follower { leader_id: Option<NodeId>, last_heartbeat: Instant },
        Candidate { votes_received: HashSet<NodeId>, election_started_at: Instant },
        Leader {
            next_index: HashMap<NodeId, u64>,
            match_index: HashMap<NodeId, u64>,
            last_heartbeat_sent: Instant,
        },
    }

    pub struct Persistent {
        pub current_term: u64,
        pub voted_for: Option<NodeId>,
        // log lives in log::LogStorage (wal-backed); persistent owns only its WAL-sync handle
    }

    pub struct Volatile {
        pub commit_index: u64,
        pub last_applied: u64,
    }

    pub struct RaftState<S> {
        pub node_id: NodeId,
        pub role: Role,
        pub persistent: Persistent,
        pub volatile: Volatile,
        pub log: LogStorage,
        pub state_machine: S,
        pub config: RaftConfig,
    }
    ```
    **Invariants**:
    - `persistent.current_term` and `persistent.voted_for` are FSYNC'd before any RequestVote response or election step.
    - `volatile.commit_index` monotonically non-decreasing.
    - `volatile.last_applied ≤ volatile.commit_index` ALWAYS.
    - Role transitions: Follower → Candidate (election timeout); Candidate → Leader (majority votes) or → Follower (higher term seen); Leader → Follower (higher term seen). NEVER: Leader → Candidate directly.
  - **Build steps**:
    1. (~30 min) Role enum with per-state fields.
    2. (~30 min) Persistent struct + wal-backed persist method. Critical: `persist_term_and_vote(&mut self, term, vote) -> Result<(), Error>` must FSYNC before returning.
    3. (~30 min) Volatile struct (no persistence needed).
    4. (~30 min) RaftState top-level + `become_follower(term, leader)`, `become_candidate()`, `become_leader()` methods. Each transition must call `persist_term_and_vote` if term advances.
    5. (~20 min) Tests: simulate crash mid-vote → recovery rejects re-voting in same term (voted_for persisted).
    6. (~10 min) Property: term monotonic across role transitions.
  - **Pitfalls**:
    - *vote-before-fsync*: replying yes to RequestVote before voted_for is on disk → crash → vote forgotten → can vote for different candidate same term → 2 leaders. **Symptom**: split-brain after crash. **Fix**: persist first, ack second.
    - *commit_index regression*: bug allowing commit_index to decrease (e.g., during snapshot install) violates SS Safety. **Symptom**: state machine applies entry then "unapplies". **Fix**: explicit monotonic guard `assert!(new >= self.volatile.commit_index)`.
    - *Role-transition skip*: directly mutating role without via transition method → forgetting to reset volatile leader fields. **Symptom**: stale next_index from previous leadership. **Fix**: all transitions go through `become_*` methods that reset role-specific fields.
    - **Expect to hit (perf) #1 — per-vote fsync without group commit (bar (c) violation)**: `persist_term_and_vote(term, vote)` calls `wal.append + wal.fsync` synchronously per RPC handler invocation. On NVMe (~10 µs/fsync) the leader election RTT floor is ~3 × 10 µs = 30 µs (vote-self fsync + N peer-reply fsyncs); on SATA SSD it's ~600 µs; on a misconfigured fs (no fsync barrier) you get correctness loss. Worse: under churn (network instability triggering repeated elections), the fsync rate climbs and stalls the entire raft thread. **Symptom**: election convergence p99 spikes from ~20 ms to 200+ ms during partition churn; `iostat -x 1` shows the wal device at 100% util with avgqu-sz climbing.
      - Fix: group-commit at the `wal` layer (W26 design): batch concurrent `persist_term_and_vote` calls into a single fsync; callers await a per-batch `Notify`. The wal layer already supports this — the raft code must NOT bypass it with a "convenience" sync-per-call.
      - Cost avoided: ~10 µs/fsync × (batch-size - 1) per election round. For a 7-node cluster batching all 7 vote-state writes into one fsync = ~60 µs saved per election; under churn (100 elections/s peak) = ~6 ms/s CPU, but more importantly removes the iostat queue depth spike.
      - Muscle: fsync is amortizable; if you can batch concurrent durability requests behind a single fsync, do it. The application layer expresses "this MUST be durable before reply"; the wal layer chooses WHEN to actually call fsync.
      - **Reapplies at**: W59 raft AppendEntries log persistence (group-commit per heartbeat tick), W83+ ledger journal writes via io_uring, W90+ ledger checkpoint flush, W74 matching-engine durable command log.
    - **Expect to hit (perf) #2 — `Role::Leader { next_index: HashMap<NodeId, u64> }` re-allocates on every `become_leader` (bar (c) violation)**: each leadership transition allocates fresh `HashMap`s for `next_index` and `match_index`; under leadership churn (network partition healing + Pre-Vote off), this happens dozens of times per minute. Per transition: 2 × HashMap::new + 2 × N inserts ≈ ~100-200 ns + 2 × ~50 ns/peer alloc. **Symptom**: `dhat` shows ~14 allocs per `become_leader` on a 7-node cluster; under chaos testing with network jitter, allocator churn is visible in `perf stat`.
      - Fix: pre-allocate the maps once at `RaftNode::new` as `ArrayVec<(NodeId, u64), MAX_PEERS>` (MAX_PEERS=16 for the workspace) or `HashMap::with_capacity(N)` retained across role transitions; `become_leader` just resets values, no realloc.
      - Cost avoided: ~14 allocs × ~50 ns + ~1 KB cold-memory write per transition × ~100 transitions/min under stress = small in steady state, large in tail; eliminates allocator-lock contention shadow on other raft threads.
      - Muscle: any "transient state that resets on lifecycle event" is a candidate for in-place reset over realloc. Pre-allocate at construction; reset (clear) on transition.
      - **Reapplies at**: W59 raft replication scratch buffers, W64+ bft `voted_blocks_per_view`, W74 matching-engine session-level state on reconnect, W90+ ledger view-change buffers.
  - **Test scenarios**: crash-after-vote test (persist_term_and_vote called, then crash injected before reply); recovery sees voted_for set. Same-term re-vote attempt rejected.

- [ ] **Build**: `crates/consensus-raft/src/rpc.rs` — RequestVote, AppendEntries types. (~150 min)
  - **Why**: RPC types are the wire contract — they MUST be stable across versions or rolling upgrade breaks. They MUST be auth+encrypted (via p2p::noise transport). Schema versioning matters.
  - *Back-of-envelope* (bar (c) — every heartbeat + every AppendEntries flows through encode/decode):
    - Workload: leader heartbeats 20/s × 6 followers = 120 wire encodes/s; under load (10k ops/s) AppendEntries can batch ~100 entries/RPC ⇒ ~100 ops × 20 batches/s × 6 followers = 12k entry-encodes/s.
    - `RequestVote` ≈ 80 B; AppendEntries header ≈ 64 B + entries (~512 B each for tx-sized commands). Per RPC: RLP encode ~50 ns header + ~200 ns/entry × 100 entries = ~20 µs encode per heartbeat. Then Noise encrypt (W54): ~700 ns + ~50 ns/KB ≈ ~5 µs for a 50 KB AppendEntries.
    - At 20 batched RPCs/s/follower × 6 followers = 120 RPCs/s; each ~25 µs encode+encrypt = 3 ms/s CPU on the leader — acceptable, but goes 10× if RLP encoding allocates per field (which the codegen sometimes does in alloy-rlp's older versions).
    - Decode mirrors encode; on the receive side, the follower's path is decode → state-machine apply. The codec must NOT allocate per entry — entries are decoded into a reused `Vec<LogEntry>` scratch buffer owned by the connection.
  - **Design**:
    ```rust
    #[derive(RlpEncodable, RlpDecodable)]
    pub struct RequestVote {
        pub term: u64,
        pub candidate_id: NodeId,
        pub last_log_index: u64,
        pub last_log_term: u64,
    }

    #[derive(RlpEncodable, RlpDecodable)]
    pub struct RequestVoteReply {
        pub term: u64,
        pub vote_granted: bool,
    }

    #[derive(RlpEncodable, RlpDecodable)]
    pub struct AppendEntries {
        pub term: u64,
        pub leader_id: NodeId,
        pub prev_log_index: u64,
        pub prev_log_term: u64,
        pub entries: Vec<LogEntry>,
        pub leader_commit: u64,
    }

    #[derive(RlpEncodable, RlpDecodable)]
    pub struct AppendEntriesReply {
        pub term: u64,
        pub success: bool,
        pub conflict_index: Option<u64>, // optimization §5.3 (skip many entries on conflict)
        pub conflict_term: Option<u64>,
    }
    ```
    **Invariants**:
    - All RPCs carry `term` first — handler MUST compare to self.current_term before processing.
    - `conflict_index/term` is an etcd-style optimization (Section 5.3 alternative): follower returns the index where its log diverges, leader skips to that point instead of decrementing next_index one at a time.
    - RLP encoding ensures cross-version compatibility (add fields by extending struct tail with `Option<_>`).
  - **Build steps**:
    1. (~30 min) Define RequestVote + Reply types with RlpEncodable derive.
    2. (~30 min) AppendEntries + Reply with conflict-index optimization fields.
    3. (~30 min) `RaftRpc` enum wrapping all: `enum RaftRpc { Vote(RequestVote), VoteReply(RequestVoteReply), Append(AppendEntries), AppendReply(AppendEntriesReply) }`.
    4. (~30 min) Property test: encode→decode roundtrip for 1000 random instances.
    5. (~30 min) Backward-compat test: encode old struct, decode new (with extra Option field) → Option = None.
  - **Pitfalls**:
    - *Schema-version breakage*: removing a field or changing type → rolling upgrade impossible. **Symptom**: new node can't decode old peer's messages. **Fix**: only APPEND optional fields; never remove or reorder.
    - *Missing conflict optimization*: without conflict_index, follower with very stale log requires O(log_len) AppendEntries rounds to catch up. **Symptom**: minutes to converge after partition heal. **Fix**: implement conflict-index/term return.
    - **Expect to hit (perf) #1 — `entries: Vec<LogEntry>` decoded per-RPC freshly (bar (c) violation)**: alloy-rlp's `Decodable for Vec<T>` allocates a fresh `Vec` and per-entry `LogEntry { data: Bytes }` allocates fresh `Bytes` (which is ref-counted but the wrapper struct still allocs). For a 100-entry AppendEntries: 1 outer Vec + 100 entry allocs + 100 Bytes refcells ≈ ~200 allocs per RPC, ~2400 allocs/s/follower-leader pair under load. **Symptom**: `dhat` shows `alloy_rlp::Decodable::decode` as a top allocator; `perf stat` shows ~20% IPC degradation in the receive path under sustained load (allocator-lock contention).
      - Fix: implement a custom decoder for `AppendEntries` that decodes into a borrowed `&mut Vec<LogEntry>` from the connection's scratch buffer (cleared, not dropped, between RPCs); use `bytes::Bytes::slice` on the wire frame's `BytesMut` so entry payloads share refcount with the frame buffer (zero-copy).
      - Cost avoided: ~200 allocs × ~50 ns ≈ ~10 µs/RPC × 20 RPCs/s/follower × 6 followers = ~1.2 ms/s CPU on the leader; cumulatively ~7 ms/s across the cluster + the allocator-lock shadow. On hot replication paths this is 3-5% throughput.
      - Muscle: every wire codec on a hot path must support "decode into a borrowed buffer" + zero-copy slicing of the wire frame; the default `Decodable -> Owned` is a bar-(b) shortcut.
      - **Reapplies at**: W55 gossip (already covered W52 Sat perf #2), W64+ bft block-proposal decode, W76+ aeron fragment decode (mandatory there), W94 block-stm txn-set decode.
    - **Expect to hit (perf) #2 — `LogEntry { data: Bytes }` straddles cache lines for index probing (bar (c) violation)**: when the follower applies entries, the hot read is `entry.index` and `entry.term` (8 + 8 = 16 B). If `LogEntry` has layout `{ index: u64, term: u64, data: Bytes, kind: u8 }` ≈ 32 B + padding = ~40 B, two consecutive entries straddle one cache line (~80 B > 64 B), so iterating `entries.iter().filter(|e| e.index > last_applied)` does 2 cache-line loads per entry instead of 1. **Symptom**: criterion bench shows apply-loop ~30% slower than expected pointer-walk; `perf stat` shows ~1.5 L1-misses per entry.
      - Fix: split into hot/cold arrays: `entries_indices: Vec<EntryHeader { index, term, kind, data_offset }>` packed at 16-24 B each (fits 3-4 per cache line) + `entries_data: BytesMut` (the concatenated payloads). Filter/scan operates on the dense header array; data accessed only when actually applying.
      - Cost avoided: ~50% L1 cache-miss reduction on apply-loop scans; at 10k ops/s × 100 entries/scan = 1M iterations/s, saving ~5 ns/iter ≈ 5 ms/s CPU on the apply thread alone.
      - Muscle: data-oriented layout — when iterating to filter on a few hot fields, separate hot fields (small, dense) from cold fields (data payloads). This is the SoA-over-AoS pattern.
      - **Reapplies at**: W74 matching-engine `OrderBook::price_levels` (split price + qty hot from order metadata cold), W76+ aeron `Image::position_array` (positions hot, subscriber-state cold), W94 block-stm `txn_writeset` index.

- [ ] **Build**: `crates/consensus-raft/src/election.rs` — election timeout (150-300 ms randomized), vote casting, term
  increment. (~150 min)
  - **Why (MAX DETAIL — bar c)**: The election loop IS Raft's safety boundary. Get the randomized timeout wrong → split votes. Get the vote-restriction wrong → leader completeness violation → committed data lost. This is the hardest single module to write correctly; etcd, raft-rs, hashicorp/raft each had 3+ election-related bugs in their first year.
  - *Back-of-envelope* (bar (c) — election latency is critical for matching-engine failover SLO; HFT target: ≤ 100 ms p99 leader recovery):
    - Election timeout: 150-300 ms (Ongaro paper) — but HFT shops often run **20-50 ms** with high-quality networks (sub-ms LAN) for fast failover. The matching-engine W74 will demand `election_timeout ≤ 30 ms`.
    - Steady-state CPU per tick: `now.duration_since(*last_heartbeat)` = ~25 ns (vDSO monotonic clock); branch on role + compare; ~30 ns/tick. Tick rate 1 kHz ⇒ ~30 µs/s = ~0.003% CPU. Trivial.
    - Election round (when triggered): `start_election` does (1) term++ + voted_for=self (~5 ns CPU) + (2) `persistent.persist()` ⇒ fsync ~10 µs NVMe (DOMINANT — this is the floor) + (3) broadcast 6 RequestVote RPCs (~5 µs encode/encrypt each, ~30 µs total + transport ~50 µs LAN) ⇒ end-to-end election RTT floor ≈ **~100-200 µs LAN + fsync × 2 (self + winning peer-reply)**. So a fast LAN cluster can elect in ~30 µs * 2 fsync + a few network RTTs ≈ ~150 µs minimum.
    - Hot read of `current_term` (in every RPC handler, ~10k/s): u64 load from L1 ≈ 0.5-1 ns. Goes red if you ever wrap RaftState in Arc<Mutex<_>> — that's a ~25 ns mutex acquire on uncontended + cache-line bounce.
    - `votes_received: HashSet<NodeId>` for 7-node clusters: HashSet on 7 elements is ~50 ns/insert/lookup vs ArrayVec linear scan ~10 ns. Use ArrayVec.

    ```rust
    impl<S: StateMachine> RaftState<S> {
        pub fn tick(&mut self, now: Instant) {
            match &mut self.role {
                Role::Follower { last_heartbeat, .. } => {
                    if now.duration_since(*last_heartbeat) > self.election_timeout {
                        self.start_election(now);
                    }
                }
                Role::Candidate { election_started_at, .. } => {
                    if now.duration_since(*election_started_at) > self.election_timeout {
                        self.start_election(now);  // re-start
                    }
                }
                Role::Leader { last_heartbeat_sent, .. } => {
                    if now.duration_since(*last_heartbeat_sent) > self.heartbeat_interval {
                        self.broadcast_heartbeat();
                    }
                }
            }
        }

        fn start_election(&mut self, now: Instant) {
            self.persistent.current_term += 1;
            self.persistent.voted_for = Some(self.node_id);
            self.persistent.persist().unwrap();  // FSYNC before any RPC
            self.role = Role::Candidate {
                votes_received: HashSet::from([self.node_id]),
                election_started_at: now,
            };
            self.election_timeout = random_in(150..300).milliseconds();  // RE-RANDOMIZE
            // broadcast RequestVote to all peers
            let rpc = RequestVote {
                term: self.persistent.current_term,
                candidate_id: self.node_id,
                last_log_index: self.log.last_index(),
                last_log_term: self.log.last_term(),
            };
            for peer in self.peers() { self.send(peer, RaftRpc::Vote(rpc.clone())); }
        }

        pub fn handle_request_vote(&mut self, rpc: RequestVote) -> RequestVoteReply {
            // Rule 1: if rpc.term > current_term, step down to follower FIRST
            if rpc.term > self.persistent.current_term {
                self.become_follower(rpc.term, None);
            }
            // Rule 2: reject stale-term requests
            if rpc.term < self.persistent.current_term {
                return RequestVoteReply { term: self.persistent.current_term, vote_granted: false };
            }
            // Rule 3: voted_for must be None or candidate
            let can_vote = self.persistent.voted_for.map_or(true, |v| v == rpc.candidate_id);
            // Rule 4: election restriction (§5.4.1)
            let log_ok = (rpc.last_log_term > self.log.last_term())
                || (rpc.last_log_term == self.log.last_term()
                    && rpc.last_log_index >= self.log.last_index());
            let granted = can_vote && log_ok;
            if granted {
                self.persistent.voted_for = Some(rpc.candidate_id);
                self.persistent.persist().unwrap();  // FSYNC before reply
                // reset election timer
                if let Role::Follower { last_heartbeat, .. } = &mut self.role {
                    *last_heartbeat = Instant::now();
                }
            }
            RequestVoteReply { term: self.persistent.current_term, vote_granted: granted }
        }

        pub fn handle_request_vote_reply(&mut self, from: NodeId, reply: RequestVoteReply) {
            // step down if reply has higher term
            if reply.term > self.persistent.current_term {
                self.become_follower(reply.term, None);
                return;
            }
            // collect vote
            if let Role::Candidate { votes_received, .. } = &mut self.role {
                if reply.vote_granted && reply.term == self.persistent.current_term {
                    votes_received.insert(from);
                    if votes_received.len() > self.peers().len() / 2 + 1 {
                        // we won — but check still relevant for current term
                        self.become_leader();
                    }
                }
            }
        }
    }
    ```
    **Invariants**:
    - Term monotonic across all transitions (compile-time-ish: only mutated by `become_follower(higher_term)` and `start_election` which increments).
    - voted_for + current_term FSYNC'd BEFORE any reply that depends on them.
    - Election timeout RE-RANDOMIZED at start of each election (not just once at startup).
    - Election-restriction (Rule 4) checks log-up-to-date BEFORE granting vote.
  - **Build steps** (granular):
    1. (~20 min) `start_election` with term-increment + vote-self + persist + RPC broadcast.
    2. (~20 min) `handle_request_vote` with all 4 rules. Critical: re-randomize timeout on grant.
    3. (~20 min) `handle_request_vote_reply` collects votes; promotes on majority.
    4. (~20 min) `tick(now)` dispatches per-role timeout handling.
    5. (~30 min) Test harness: in-memory 5-node sim with controllable network (drop/delay/reorder). Run 1000 random schedules, verify election safety holds (at most 1 leader per term).
    6. (~20 min) Adversarial test: partition leader; verify minority side cannot elect; reunite; verify old leader steps down.
    7. (~20 min) Random-timeout test: 100 elections, measure split-vote rate. Expect < 5% with 150-300ms randomization on 5 nodes.
  - **Pitfalls** (named, distributed-systems):
    - *Split vote without randomization*: synchronized timeouts → all 5 nodes become candidates simultaneously → 5 vote-for-self, no one gets majority. **Symptom**: live-lock. **Fix**: `rand::thread_rng().gen_range(150..300)` per-node, per-election.
    - *Term confusion*: candidate at term T receives reply with term T+5; if it just collects votes without checking term, advances to leader at term T while a real leader exists at T+5. **Symptom**: two leaders. **Fix**: `if reply.term > current_term: step_down`.
    - *Byzantine accidental double-vote*: process crashes mid-vote; voted_for not yet persisted; on restart, votes again in same term for different candidate. **Symptom**: 2 candidates each get majority (impossible by quorum math but possible under accidental Byzantine). **Fix**: persist voted_for SYNCHRONOUSLY (fsync) before reply.
    - *Heartbeat interval too long*: with election_timeout = 200ms and heartbeat = 150ms, jitter can starve heartbeats below 200ms → spurious elections. **Symptom**: leader churn. **Fix**: heartbeat ≤ election_timeout / 3 (60ms heartbeat for 200ms election).
    - *Election restriction bypass*: granting vote to candidate whose last_log_term is lower → leader completeness violation → committed entry lost. **Symptom**: data loss on partition heal. **Fix**: explicit check `last_log_term` first (NOT just `last_log_index`).
    - **Expect to hit (perf) #1 — `votes_received: HashSet<NodeId>` allocates per election; SmallVec/ArrayVec on 7-node cluster is the right tool (bar (c) violation)**: at 7 nodes, `HashSet::insert` is ~50 ns (bucket compute + hash + insert) + ~50 ns alloc on first insert; total ~300-500 ns per election + ~50 ns alloc overhead. Under churn (Pre-Vote off, repeated elections) this multiplies. Worse: `HashSet::with_capacity(N)` is forgotten 95% of the time → realloc as the set grows from 1 to 5 votes. **Symptom**: `dhat` shows election-flow allocs proportional to election rate; under chaos test injecting partition healing, allocator pressure visible.
      - Fix: `votes_received: ArrayVec<NodeId, MAX_PEERS>` with linear-scan `contains` (~5 ns for 7 elements, faster than HashSet's hash+bucket); pre-allocated at `RaftNode::new`, cleared on `start_election`.
      - Cost avoided: ~300-500 ns per election × ~100 elections/s under churn = ~30-50 µs/s CPU + zero alloc; bigger win is the consistency of latency (no GC-style jitter).
      - Muscle: container choice is workload-dependent — when N is small and bounded (≤ 32 typical), ArrayVec + linear scan beats HashMap/HashSet on both throughput and latency. HashSet pays for itself only beyond N ~ 64.
      - **Reapplies at**: W59 raft `match_index` updates (ArrayVec<(NodeId, u64), MAX_PEERS>), W64+ bft `voted_validators_for_block`, W74 matching-engine `top_n_levels`, W90+ ledger replicas-in-quorum.
    - **Expect to hit (perf) #2 — `tick(now)` called at 1 kHz allocates a fresh `Instant::now()` via `std::time::Instant` (~25 ns vDSO) + 4 branch checks; OK alone, but if the timer wheel uses `Instant::now` PER ROLE rather than once per tick, you 4× the cost (bar (c) violation, latent)**: spec-correct `tick` calls `now.duration_since(*last_heartbeat)` then potentially `Instant::now()` again inside `start_election`, then again inside `broadcast_heartbeat`. Each is ~25 ns vDSO. **Symptom**: at sub-ms timer granularity (HFT election_timeout = 30 ms ⇒ tick rate higher to detect timeouts in time) this scales linearly; on a 16-shard runtime with each shard ticking 1 kHz = 16 × 25 ns × 4 reads = ~1.6 µs/ms = 0.16% CPU on clocks alone.
      - Fix: caller passes `now: Instant` once per tick; `tick`, `start_election`, `broadcast_heartbeat` all take `now: Instant` parameter and reuse the value. Already correct in the design sketch above (`fn tick(&mut self, now: Instant)`) — the perf bug is when downstream code calls `Instant::now()` inside the methods anyway.
      - Cost avoided: ~25 ns × 3 redundant reads/tick × 1 kHz = ~75 µs/s/shard; on 16-shard runtime = ~1.2 ms/s CPU. Trivial individually, but reflects the bar-(c) discipline that EVERY clock read on the hot path is intentional and counted (W003 muscle: `vDSO clock ≈ 25 ns`).
      - Muscle: clock reads are not free; on a hot loop, pass `now: Instant` as a parameter rather than re-reading. The timer wheel pattern (W58+) makes this explicit.
      - **Reapplies at**: W58 timer wheel design (single `Instant::now` per tick wheel rotation), W74 matching-engine `OrderBook::tick(now)`, W76+ aeron flow-control rate-limit, W83+ ledger TigerBeetle-style deterministic clock injection.
