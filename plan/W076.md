  `MediaDriver { shm_dir: PathBuf, conductor: ConductorThread }`. Conductor owns subscription/publication state. (~total 2.5 hrs across 3 phases)
  - 🔧 **Why this matters**: MediaDriver is Aeron's control plane — the daemon that owns all transport state, exposes a CnC (Command-and-Control) file over shared memory, and routes publication/subscription commands. Clients are thin libraries that talk to the driver via the CnC file. This separation lets multiple processes share the network with zero-copy. Downstream consumers: W77 `term_buffer.rs` (built on `AddPublication`), W78 `transport_udp.rs` (sender uses conductor to route outbound), W79 multi-subscriber fan-out, W82 v1.5 SHIP audit.

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: a per-process socket-based messaging stack pays kernel-transition cost per send AND can't share the network across processes. A separate driver daemon that owns the network via shared memory IPC lets dozens of processes do zero-copy publish/subscribe — the publication is just bytes in a shared mmap. The conductor is the single-writer arbiter of that shared state; without it, you have a multi-writer free-for-all.

  - **Requirements** — write in `crates/messaging-aeron/notes/76_media_driver_design.md`:
    - R1. Single-threaded conductor — no internal locks; all command processing serializes through one thread.
    - R2. CnC file: lock-free SPSC ring buffers (to_driver + to_clients), counter metadata, error log; layout matches Aeron's `CncFileDescriptor`.
    - R3. Sender/Receiver are separate threads pinned to dedicated cores; communicate with conductor via ring buffers (NEVER shared mutex state).
    - R4. Driver crash/restart cleanly handles stale shm files (pid + boot-time handshake in CnC header).
    - R5. Ring buffer overflow returns `WouldBlock`; conductor polls at ≥10 kHz to drain.
    - R6. Conductor hot loop: ZERO syscalls per command in steady state (idle ladder = busy-spin → yield → park).
    - R7. CnC `head`/`tail` counters cache-line isolated (`CachePadded`) from each other and from command records.
    - R8. Throughput ≥1M cmd/s through CnC ring; P99 conductor poll latency <100 µs.

  - **Design walk-through** — answer each:
    - D1. Sketch the CnC file layout: 4 KiB header + 1 MiB to_driver ring + 1 MiB to_clients ring + counters region + error log region. Where does each go in the file offset map? Cite Aeron `CncFileDescriptor`'s constants.
    - D2. Conductor poll loop: write the pseudo-code. What's the ladder for when the ring is empty? (Hint: W4 Tue Backoff.) How does that ladder interact with the 10 kHz floor (R5)?
    - D3. CnC ring buffer is SPSC (client → driver, one direction; driver → clients, the other). Why SPSC and not MPSC? (Hint: one CnC pair per client; multi-client = N CnC pairs, not one shared MPSC.)
    - D4. **Pre-mortem (stale shm):** the driver crashes leaving CnC + log files in `/dev/shm`. A new driver starts. What does it find? What does the pid + boot-time handshake in the CnC header let it decide (recover vs error)?
    - D5. **Pre-mortem (cache-line ping-pong):** if `head: AtomicU64` and `tail: AtomicU64` share a cache line with the first command record's bytes, every client claim invalidates the driver's cached `head`. Walk through the MESI sequence: client writes head → invalidates driver's L1 line containing head → driver's next head read pays L2 fetch (~7 ns). At 1M cmd/s, what's the cost?
    - D6. **Pre-mortem (idle CPU burn):** conductor's `epoll_wait(timeout=0)` returns instantly when ring is empty. At 10 kHz polling × 300 ns syscall = 3 ms/sec — fine for one driver. But it pollutes the conductor's L1 working set every iteration. Why does avoiding the syscall (busy-spin then park) preserve cache residency?
    - D7. Cross-process mmap alignment: 32-bit clients vs 64-bit driver. What goes wrong if alignment mismatches? Aeron supports both with painful overlap; we punt to 64-bit only — write the `compile_error!` gate.

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  - **When `conductor_poll_zero_syscalls_under_steady_load` reports ~10k futex/epoll_wait calls per second:**
    - Symptom: `strace -c` shows ~10k `epoll_wait(timeout=0)` calls/sec attributed to the conductor; P99 cmd latency tail jumps from 1 µs to 15 µs on quiet symbols; `perf stat` shows context-switch count climbing under low load.
    - Why: naive conductor poll calls `epoll_wait(timeout=0)` every iteration even when ring is empty — 300 ns syscall × 10 kHz = 3 ms/sec overhead AND each syscall cache-pollutes the conductor's working set, evicting hot L1 state.
    - Fix: idle strategy is the 3-stage ladder from W4 Tue Backoff: (1) busy-spin via `core::hint::spin_loop()` for first ~100 polls (~10 ns/iter); (2) `thread::yield_now()` for next ~10 polls (~1 µs each); (3) park via Parker (W4 Thu) only after sustained idleness. Match Aeron's `BackoffIdleStrategy` exactly. The hot path NEVER calls a syscall; only the cold-park path does.
    - Cost avoided: ~300 ns/poll × 10 kHz = 3 ms/sec/core; restores conductor's L1 cache (~30 KiB) residency; P99 tail collapses from 15 µs to <2 µs.
    - Muscle: the conductor's hot loop must NEVER syscall on the fast path — every kernel transition is a P99 disaster. Reapplies at: W77 term buffer poll, W77 flow control tick, W78 NAK tick, W83 runtime reactor::poll(), W84 deterministic harness scheduler.

  - **When `cnc_layout_head_tail_cache_line_isolated` fails the layout asserts:**
    - Symptom: `offset_of!(CncHeader, tail) - offset_of!(CncHeader, head) == 8` (back-to-back u64s in same line); `perf c2c` flags the first cache line of the mmap as the HITM hotspot.
    - Why: SPSC ring stored `head: AtomicU64`, `tail: AtomicU64`, and command records all within a 64 B span at file head. Client's `tail` write invalidates driver's cached `head` (same line); driver's `head` write invalidates client's cached `tail`. At 1M ops/s × ~7 ns L2 fetch per invalidation = ~14 ms/sec cross-core MESI traffic.
    - Fix: layout CnC header as `head: CachePadded<AtomicU64>` (128 B line on aarch64, 64 B on x86), `tail: CachePadded<AtomicU64>` (separate line), records start on next 128 B boundary. Pin client + conductor threads to sibling cores same NUMA node.
    - Cost avoided: ~7 ns × 2 × 1M ops/s = ~14 ms/sec L2 fetch traffic; restores per-side L1 residency on counters.
    - Muscle: in an SPSC ring, head + tail MUST be on different cache lines from each other and from records — W4 CachePadded is non-negotiable for cross-process rings. Reapplies at: W77 term buffer tail, W77 flow control positions array, W84 archive recorder lag counter.

  - **When `driver_recovers_from_stale_shm_files` reports the new driver overwrote a live driver's file:**
    - Symptom: two drivers started concurrently; the second one truncated the first's CnC file because pid-liveness check was missing; first driver crashes with EBADF.
    - Why: naive recovery deletes any pre-existing files. Without a liveness handshake (pid + boot-time), can't distinguish "stale leftover from crashed driver" from "live driver currently running."
    - Fix: CnC header has `pid: i32 + boot_time_ns: u64 + version_status: u32`. On startup, read existing CnC; `kill(pid, 0)` to test liveness; if liveness fails (ESRCH), recover (unlink + recreate); if liveness passes, exit with error (refuse to clobber). Aeron uses `cncVersionStatus` for the handshake — mirror exactly.
    - Muscle: shared-memory primitives need a liveness handshake before reclaiming; pid alone isn't enough (pid reuse), pid + boot-time is. Reapplies at: W77 IPC publication recovery, W80 ledger journal cross-process recovery, W83 archive recorder startup.

  - **When `driver_throughput_at_least_1m_cmds` reports 600k cmd/s:**
    - Symptom: bench shows ~600k cmd/s vs the 1M target. Flame graph shows ~40% of time in `BTreeMap::entry` on the conductor's publications map.
    - Why: AHashMap lookup per command (~100 ns) on the hot dispatch; under cold cache, ~3 cache misses × 50 ns = 150 ns per lookup.
    - Fix: publications indexed by `PublicationId: u32` (assigned monotonically) into `Vec<Option<Publication>>` (direct array index, ~1 ns L1 load). Active mask is a `BitSet` for branch-prediction-friendly iteration. Same pattern as W77 flow_control positions array.
    - Cost avoided: ~100 ns/cmd × 1M cmd/s = ~100 ms/sec; restores throughput to 1.2M cmd/s headroom.
    - Muscle: monotonic-id key spaces are array-indexed; AHashMap is for the cold control plane. Reapplies at: W77 subscription registry, W79 MBO publish per-symbol lookup, W82 Image session table.

  - **5-year failure mode** (write in `notes/76_media_driver_followup.md` after green): when DPDK / AF_XDP becomes the standard transport, the CnC ring's syscall-free design extends naturally — but the mmap-over-shm assumption breaks (DPDK uses hugepage allocations from its own pool). Migration: CnC layout becomes a `MemRegion` trait with shm + hugepage + DPDK-pool implementations.

  messages. (~total 4 hrs across 3 phases)
  - 🔧 **Why this matters**: A replica offline longer than the leader's truncated log range cannot rejoin via NormalOperation — it needs the *full state* shipped in chunks. State transfer is VSR's analog of Raft InstallSnapshot. Without it, replicas that fall behind become permanently dead. Downstream: W83+ ledger-deterministic adds new replicas to production clusters via state transfer; W76 Thursday's `consensus-vsr v0.5.0` tag depends on this; ledger v1.0 leader-failover SLA.   #### Phase 1 — Problem, requirements, design (~75 min, no code yet)

  - **The problem this primitive solves**: a replica that fell out of the log-retention window has no way to catch up via normal NormalOperation log-shipping (the leader truncated the entries it needs). State transfer is the protocol that ships the FULL state machine snapshot + log suffix in chunks, with checksum integrity, without blocking the sender's hot apply loop.

  - **Requirements** — write in `crates/consensus-vsr/notes/76_state_transfer_design.md`:
    - R1. Two message types: `GetState { view_num, op_num, from }`, `NewState { view_num, op_num, commit_num, log_suffix, snapshot, to }`.
    - R2. Snapshot's `op_num ≤ sender's commit_num` — never ship uncommitted state.
    - R3. State transfer is **idempotent** — repeated NewState messages with same op_num are no-ops.
    - R4. Checksum-verified (blake3) — corrupted snapshot rejected, sender re-asked.
    - R5. Recipient sets `op_num` and `commit_num` together post-restore; never a gap between them.
    - R6. State transfer **only valid when `status == Normal`** — during ViewChange, lagging replicas catch up via the StartView merged log instead.
    - R7. Snapshot construction is **O(1)** (copy-on-write reference) — never blocks the apply loop.
    - R8. Snapshot transfer for 100 MB state completes <5 s loopback (≥20 MB/s).
    - R9. Concurrent NewStates from multiple peers deduped via correlation_id; recipient applies exactly one.
    - R10. Chunked snapshots (>4 MiB): multi-message NewState with `done: bool`; reassembled on recipient.

  - **Design walk-through** — answer each:
    - D1. When does a replica DECIDE to request state transfer? Walk through the trigger from `on_prepare` receiving an op_num way ahead of its own (gap).
    - D2. **Pre-mortem (snapshot blocks apply loop):** apply loop is single-threaded (W80 deterministic SM); a naive `state_machine.snapshot()` that clones a 100 MB account map takes 200 ms — the apply loop blocks for 200,000 ops missed at the 1M ops/s target. Walk through: how does CoW snapshot (e.g., `Arc<MerkleTrie>` head bump) make snapshot O(1)?
    - D3. **Pre-mortem (state transfer during view change):** replica is in ViewChange, but a peer's NewState (for Normal) arrives. Naive handler applies it; now the replica's log has Normal-shape data while status says ViewChange. What invariants break? What's the gate?
    - D4. **Pre-mortem (concurrent NewStates):** replica requests state from 2 peers, both respond. Both NewStates have op_num=N. Naive recipient applies both → ops appended twice. What's the dedup mechanism (Aeron-style correlation_id)?
    - D5. Log-suffix vs snapshot decision: `if (sender.op_num - requester.op_num) <= MAX_LOG_SUFFIX → send log_suffix only; else → send snapshot`. What's MAX_LOG_SUFFIX? Justify from the bandwidth/CPU tradeoff.
    - D6. Chunking: 100 MB snapshot at 4 MiB chunks = 25 messages. Each chunk has `chunk_index, total_chunks, done`. How does recipient assemble? What happens if chunk 10 arrives before chunk 5?
    - D7. Where does state-transfer COST land in the budget? Apply loop ~1 µs/op; state transfer is COLD (rare); snapshot READ on sender is HOT-PATH-ADJACENT (apply still running while snapshot reads). Walk through how CoW gives the sender a stable pointer while apply mutates the live state.
  - **Output**: `notes/76_state_transfer_design.md` with R1–R10 + D1–D7 + the chunk-assembly state diagram.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **When `snapshot_construction_o1_does_not_block_apply` reports a 200 ms apply-loop pause:**
    - Symptom: during a state transfer, apply-loop P99 latency spikes from 1 µs to 200 ms; raft lease expires; spurious view changes triggered; ~200k apply ops missed.
    - Why: naive `state_machine.snapshot()` returns `Vec<u8>` by cloning the entire account map — 100 MB allocation + serialize + checksum = ~200 ms on M2. Apply-loop is single-threaded; blocking it 200 ms ≡ 200k missed ops at 1M ops/s.
    - Fix: copy-on-write snapshot — keep a pointer to current state's persistent data structure (`im::OrdMap` head, or `Arc<MerkleTrie>` head); bump refcount; return pointer in O(1). Sender's chunker reads from snapshot pointer asynchronously WHILE apply-loop continues mutating live state via CoW. Aeron's archive uses mmap-queue offset for exactly this — snapshot IS the durable mmap-queue offset.
    - Cost avoided: ~200 ms blocking per state transfer; ~200k missed apply ops; eliminates view-change incidents triggered by lease expiry.
    - Muscle: snapshot of a hot state machine must be O(1) reference, never O(N) clone. Reapplies at: W83 ledger v0.5 snapshot, W87 VOPR snapshot injection, W88 consensus-vsr v1.0 snapshot for follower catch-up, W92 ledger v1.0 io_uring snapshot.

  - **When `state_transfer_rejected_during_view_change` reports the log got mutated:**
    - Symptom: replica's `status == ViewChange`; NewState arrived; log was modified.
    - Why: handler didn't gate on `status == Normal`. State transfer assumes the protocol's Normal-operation log model — applying it during ViewChange leaves the replica in an inconsistent phase.
    - Fix: `on_new_state` first check: `if self.status != ReplicaStatus::Normal { discard(m); return; }`. During ViewChange, catch-up happens via StartView's merged log (W75), not state transfer.
    - Muscle: every quorum-protocol message handler validates current phase matches message's expected phase. Reapplies at: W75 view_change.rs (the symmetric rule), W87 VOPR fuzzer (drive messages into wrong phases).

  - **When `concurrent_state_transfer_requests_deduplicated` reports ops appended twice:**
    - Symptom: replica requested state from R2 and R3 simultaneously; both responded; both NewStates applied → log has 2× the ops; state_hash diverges from cluster.
    - Why: no correlation_id; recipient blindly applied every NewState that arrived.
    - Fix: track outstanding `GetState` request_id (monotonic per replica); each NewState carries the request_id of the GetState it answers; recipient applies only matching request_id, discards others. Aeron-style correlation. After one successful apply, request_id incremented — stale responses discarded.
    - Muscle: any multi-peer request/response protocol needs a correlation_id to deduplicate responses. Reapplies at: W77 NAK retransmit correlation, W84 archive replay request correlation, W90 consensus-vsr leader-election callbacks.

  - **When `corrupted_snapshot_rejected_and_retried` reports the bad snapshot was applied:**
    - Symptom: bit-flipped snapshot bytes passed through checksum (or checksum wasn't computed); state_machine corrupted; replica diverges silently.
    - Why: `on_new_state` either didn't verify checksum, or used a non-cryptographic checksum (CRC32) that has collision rates high enough for adversarial bit-flips.
    - Fix: blake3 hash over (`snapshot.state_bytes`); compare against `snapshot.checksum`; reject + log error + send GetState again. blake3 is collision-resistant (cryptographic) so adversarial collisions are infeasible.
    - Muscle: durability/integrity of large blobs needs cryptographic hash (blake3, sha2), not CRC32. Reapplies at: W77 NAK frame integrity, W83 archive recorder frame crc (CRC32 OK for transient frames; blake3 for persisted snapshots), W92 ledger v1.0 snapshot integrity.

  - **When `state_transfer_100mb_under_5s_loopback` reports 12 s:**
    - Symptom: 100 MB transfer takes 12 s instead of 5 s target. Profile shows `bincode::deserialize` taking 8 s allocating + parsing per chunk.
    - Why: per-chunk full deserialize (`bincode::deserialize_from(&buf)`) allocates fresh field values for every chunk; 25 chunks × ~300 ms deserialize each = 7.5 s.
    - Fix: chunk format is `[chunk_index: u32, total_chunks: u32, done: bool, state_bytes: [u8; 4 MiB]]` — header is fixed-layout `repr(C)` `ptr::read`-able (~20 ns); state_bytes is appended raw to recipient's accumulating buffer (no per-chunk deserialize). Full deserialize happens ONCE after all chunks received.
    - Cost avoided: ~12 s → ~3 s; meets the 5 s target with headroom.
    - Muscle: streaming/chunked transfer formats use fixed-layout headers + raw byte appends; full deserialize happens once at end. Reapplies at: W83 archive frame format, W92 ledger v1.0 snapshot streaming.

  - **5-year failure mode** (write in `notes/76_state_transfer_followup.md`): when RDMA / DMA-direct transfers become commodity, state transfer chunks via memcpy is wasteful — kernel-bypass RDMA WRITEs deliver the snapshot to the recipient's address space without CPU involvement. Migration: state_transfer becomes an `Op` enum with `Memcpy` (today) and `RdmaWrite` (future) variants.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **When `refresh_latency_p99_under_1us` reports 8 µs at depth 1000:**
    - Symptom: P99 refresh latency 8 µs vs 1 µs target; flame graph shows `core::ptr::copy` dominating (~70% of samples).
    - Why: price-level FIFO stored as `Vec<Order>`; `requeue_iceberg` calls `vec.remove(idx)` which is O(N) — shifts every later element down by one. 1000 resting orders × 8 byte pointer move = ~8 µs per refresh.
    - Fix: intrusive doubly-linked-list per price level. Each `Order` has `prev: SlotIdx, next: SlotIdx` into a `Slab<Order>` (pre-allocated, no per-order alloc). Unlink is O(1): two pointer writes. This is the standard order-book layout (Nasdaq, CME Globex, dYdX v4 all use it).
    - Cost avoided: ~8 µs at 1000-order depth; 10k refreshes/sec on hot symbol = ~80 ms/sec pure shift overhead.
    - Muscle: order-book FIFO must support O(1) middle-remove — `Vec` is wrong, intrusive linked list is right. Reapplies at: W74 lock-free price level cancel, W77 stop ladder remove-on-trigger, W82 v1.5 SHIP audit (asserts no `Vec::remove` in matching hot path), W77 NAK gap-list.

  - **When `no_heap_alloc_on_iceberg_hot_path` reports 20k allocs/sec attributed to MBO publish:**
    - Symptom: dhat shows 20k allocs/sec of 64-128 B chunks; refresh P99 latency 3-5 µs.
    - Why: each refresh emits Cancel + Add (2 events); `bincode::serialize(&MboEvent)` allocates a fresh `Vec<u8>` per event (~200 ns/event); allocator arena lock under contention costs ~50 ns per malloc.
    - Fix: serialize into a pre-allocated `bufpool::PooledBuf` (W12-W14); buffer recycled to pool after aeron `offer()`. MBO envelope is fixed-size (header + payload ≤256 B) so a single pool with 256 B slots covers >99% of events.
    - Cost avoided: ~200 ns × 2 events × 10k refreshes/sec = 4 ms/sec malloc overhead; eliminates jemalloc arena contention; restores L1 D-cache.
    - Muscle: every emit path on a bar-(c) crate uses a buffer pool, never `Vec::new`. Reapplies at: W77 aeron offer, W79 MBO feed publish, W80 ledger journal record serialize, W83 archive recorder.

  - **When `random_refresh_deterministic_across_replicas` reports divergence:**
    - Symptom: replica A's refresh = 80 lots, replica B's = 100 lots, replica C's = 120 lots; state hash diverges.
    - Why: `RefreshRule::Random` calls `thread_rng()` → OS entropy → different per replica.
    - Fix: PRNG seeded from `(order_id, op_num)` — deterministic input → deterministic output. Every replica computes the same refresh size for the same iceberg event.
    - Muscle: deterministic state machines forbid `thread_rng` / `OsRng`; ALL randomness from a seeded `SmallRng` deterministic per scenario. Reapplies at: W77 stop trigger trailing offset, W80 ledger SM, W87 VOPR scenario PRNG, W92 ledger v1.0 SHIP determinism gate.

  - **When `iceberg_refresh_goes_to_back_of_queue` reports front-of-queue priority:**
    - Symptom: refreshed display takes original queue position; iceberg trader gets unlimited free re-priority.
    - Why: refresh updated `display_remaining` in place without moving the order in the linked-list.
    - Fix: refresh = unlink (O(1)) + push_back to FIFO tail (O(1)). New display has fresh queue priority. This matches CME/Nasdaq fairness rules.
    - Muscle: any "reset" of an order's queue position must re-enqueue at the tail. Reapplies at: W82 v1.5 SHIP audit (the same rule for order modification).

  - **When `cancel_mid_refresh_no_phantom_display` reports phantom display in book:**
    - Symptom: trader cancels iceberg while a fill is mid-processing; cancel races with refresh; book ends up with phantom display.
    - Why: fill and refresh aren't atomic — cancel landed between fill and refresh.
    - Fix: process `fill → refresh` atomically inside `Engine::apply` (single thread). Cancel observed after must see post-refresh state. With raft replication (W74), fill+refresh is one log entry.
    - Muscle: order-mutation sequences (fill → refresh, fill → settle) are atomic at the apply-loop boundary; concurrent cancel observes only complete states. Reapplies at: W77 stop trigger (fill → cancel-stops atomic), W80 ledger transfer (debit → credit atomic), W82 v1.5 SHIP audit.

  - **When `mbo_aggregate_equals_engine_mbp_snapshot` proptest finds a divergence:**
    - Symptom: MBO replay reconstructs MBP that has more depth at price P than engine's actual MBP.
    - Why: refresh was emitted as `Modify(total_remaining)` instead of `Cancel(old_visible) + Add(new_visible)`. MBP consumer sees Modify, treats as net-zero on depth, but actual delta was -old + new = same visible only if old==new.
    - Fix: refresh = `Cancel(old_display_qty) + Add(new_display_qty)`. Each event is symmetric on MBP; aggregation matches engine.
    - Muscle: an iceberg's refresh on the wire is two events (Cancel + Add), not one Modify — MBO/MBP equivalence requires it. Reapplies at: W79 mbo_feed.rs (the publishing side), W82 v1.5 SHIP audit (the aggregation invariant).
