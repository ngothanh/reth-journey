  `LinearContract { mark_price, index_price, funding_rate, open_interest }` per TigerBeetle-style integer determinism. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: mirrors a dYdX-V4-style perpetual contract built on TigerBeetle's integer-ledger discipline. Perps are the volume leader on crypto exchanges (Binance, Bybit, dYdX); the contract math (mark-price clamping, funding rates, open-interest accounting) is where exchanges *lose money* — LUNA, FTX, and smaller venues collapsed via mark-price manipulation triggering cascade liquidations. Four traps land below: (1) any `f64` makes the state machine non-deterministic across CPU arches → raft replicas diverge → `matching-engine` v1.0 fails its W74 determinism gate; (2) sign-convention flip on funding = an arbitrage drain; (3) OI treated as a flow not a net-exposure metric inflates risk limits; (4) storing hot fields off-struct blows the ≤5 ns OI budget. **State plainly: your first attempt WILL fail ≥1 test below — the debug session is the lesson.** Downstream: W66 Wed `margin.rs`, W71 funding TWAP + liquidation, W74 matching v1.0 determinism gate, W83+ `ledger-deterministic`, W88 VOPR replay.

  - *Mental model*: a `LinearContract` is the per-symbol risk/funding state machine that every fill and every funding tick mutates; because two raft replicas on different CPU arches must apply the same sequence to byte-identical state, **every arithmetic op must be integer with an explicit denominator** — float is presentation-layer-only.
  - *Contract* (signatures only — never the body):
    ```rust
    struct SignedFrac { num: i128, denom: i128 }      // explicit denom; denom typically 1_000_000 (bps×1e6)
    impl SignedFrac { fn mul(self, x: i128) -> i128;  fn checked_mul(self, x: i128) -> Option<i128>; }
    struct LinearContract {
        symbol: Symbol, mark_price: i64, index_price: i64,
        funding_rate: SignedFrac, funding_interval: u64, next_funding_at: u64,
        open_interest: u64, tick_size: i64, contract_size: i64, max_leverage: u32,
        initial_margin_ratio: SignedFrac, maintenance_margin_ratio: SignedFrac,
    }                                                  // ≤ 2 cache lines (~128 B)
    struct Position { account: AccountId, symbol: Symbol, size: i64, entry_price: i64,
                      margin: u64, funding_paid_cum: i128 }   // signed size: +long / -short
    impl LinearContract {
        fn clamp_mark(&self, book_mid: i64) -> i64;            // clamp(book_mid, index ± max_basis)
        fn funding_rate_from(&self, mark: i64, index: i64) -> SignedFrac;  // clamped premium, pro-rated
        fn apply_funding(&self, pos: &mut Position);           // who-pays-whom by sign
        fn update_oi(&mut self, maker_opening: bool, taker_opening: bool, qty: u64); // 4-case truth table
    }
    ```
  - *Back-of-envelope* (bar (c) — HFT critical path, ≤1 µs/fill total budget): per fill touches `book.bids` (1 line), `contract` (≤2 lines), `position` (1 line). OI update target ≤ **5 ns** = one `u64` add on an already-warm cache line (an L1 hit is 0.5 ns; a HashMap lookup is a hash + ≥1 random L2/L3 fetch ≈ 7-70 ns — **the cliff is 5 ns warm-field vs ~50 ns map = 10×**). Mark clamp target ≤ **3 ns** = two integer compares (branch ~0.5 ns each, predicted). `f64::div` ≈ 10-30 cycles ≈ 3-10 ns vs `i64::div` ≈ 3-5 cycles ≈ 1-1.5 ns; at thousands of ops/fill the float tax is 50-200 ns = **5-20% of the entire fill budget** — before counting the determinism violation.
  - **Requirements** — write in `crates/matching-engine/notes/66_contract_design.md`:
    - R1. `LinearContract { symbol, mark_price, index_price, funding_rate: SignedFrac, funding_interval, next_funding_at, open_interest, tick_size, contract_size, max_leverage, initial_margin_ratio: SignedFrac, maintenance_margin_ratio: SignedFrac }` — `#[repr(C)]`, sized ≤ 2 cache lines (~128 B) so per-fill access touches ≤ 2 L1 fetches.
    - R2. `Position { account, symbol, size: i64, entry_price, margin: u64, funding_paid_cum: i128 }` — signed `size` encodes side (positive long, negative short).
    - R3. **Float ban**: no `f32`/`f64` reachable from `contract.rs` or any perps module. All rates/ratios/premia use `SignedFrac { num: i128, denom: i128 }` with explicit denominator (1e6 for bps×1e6).
    - R4. **Mark-price clamp**: `mark = clamp(book_mid, index ± max_basis)`, `max_basis = 0.5%`. Prevents thin-book manipulation triggering false liquidations.
    - R5. **Funding rate**: from `premium = (mark - index) / index`, clamped to ±0.75% per 8-hour interval, pro-rated to `funding_interval`.
    - R6. **Funding direction invariant**: premium > 0 → longs pay shorts; premium < 0 → shorts pay longs. Sign error = arbitrage exploit.
    - R7. **Open-interest accounting**: OI increases only on net-NEW exposure (both sides opening); offset trades do NOT increment OI; `Σ size` across all positions for a contract = 0 (longs = shorts).
    - R8. **Per-fill budget**: OI update ≤ 5 ns (one `u64` add on a hot line); mark-price clamp ≤ 3 ns (two integer compares).
    - R9. **Determinism gate**: 1000 random trades + funding ticks across two replicas (different CPU arch, different `-march`) → byte-identical `ContractState` snapshots.

  #### Phase 3 — Make the tests pass, one failure at a time (~115 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `contract_size_two_cache_lines` reports 192+ bytes:**
    - Symptom: `size_of::<LinearContract>()` exceeds 128; per-fill access touches a 3rd cache line.
    - Why: field ordering left padding holes (a `u32 max_leverage` between two `i64`s), or you stored a `String symbol`.
    - Fix: `#[repr(C)]`, order fields large→small, intern `symbol` to a `Symbol(u32)`.
    - Cost avoided: one extra L1 miss per cold fill ≈ 7 ns; over a burst that is the difference between in-budget and over (bar (c)).
    - Muscle: hot-path structs are size-budgeted and `repr(C)` with intentional field order. Reapplies at: W66 margin `Account`, W74 matching order, W83 ledger account row.

  - **(EXPERT) (bar (c) violation) When `cross_arch_determinism_x86_vs_arm` reports a 1-cent drift after ~10k funding ticks:**
    - Symptom: x86 and ARM replicas produce divergent `ContractState` snapshots; ~$0.01/position/tick, accumulating; raft replication would diverge once W74 lands.
    - Why: an `f64` somewhere — `funding_rate: f64`, `premium: f64`, or a hidden `(amount as f64 / 1000.0)` for "percentage display". `f64::div` rounds differently across CPUs (FMA/AVX-512 on x86 vs Neon on ARM).
    - Fix: integer-only `SignedFrac { num: i128, denom: i128 }` with explicit denom; all ops `i128::checked_mul` + `checked_div`. Mark clamp = three `i64` ops (~3 ns, deterministic). Add `clippy::disallowed-types = ["f64","f32"]` in `matching-engine/clippy.toml`. The ONLY `f64` allowed is the RPC presentation layer, AFTER state is computed.
    - Cost avoided: ~10-30 cyc/op × thousands/fill ≈ 50-200 ns/fill (5-20% of the 1 µs budget) AND eliminates the determinism violation that would otherwise block matching-engine v1.0 (W74) — one debt resolved at the source = zero re-engineering at W74/W83/W88.
    - Muscle: any value flowing into a deterministic SM (raft apply, VOPR) is integer with explicit denominator; float is wire-format-only. Reapplies at: W66 margin (cross-margin ratio), W71 funding TWAP + liquidation `equity`, W74 `replication.rs` determinism gate, W83+ ledger balance math, W88 VOPR replay.

  - **(SENIOR) When `funding_rate_positive_premium_longs_pay` shows shorts paying longs (sign reversed):**
    - Symptom: positive premium (mark > index) moved balances the wrong way; arbitrage bots would drain OI.
    - Why: sign confusion in `payment = size * mark * rate`. For longs (`size>0`, `rate>0`) payment>0 = they pay; for shorts (`size<0`) payment<0 = they receive — easy to flip.
    - Fix: pin the convention with this exact test and a load-bearing doc-comment at the top of `contract.rs`: "positive funding rate = longs pay shorts (longs are on the expensive side)." Regression-test both signs.
    - Cost avoided: not a latency cost — a correctness/economic one: a flipped sign is a continuous arbitrage drain (unbounded loss), invisible to a green build until it's a live exploit.
    - Muscle: any signed-arithmetic convention in financial code MUST have an explicit unit test pinning the sign — comments are insufficient. Reapplies at: W71 liquidation P&L, W83 ledger debit/credit, W90+ settlement directions.

  - **(SENIOR) When `open_interest_only_on_new_exposure` shows OI inflating to 20 on an offset trade:**
    - Symptom: A buys 10 (OI=10), A sells 10 to B opening short; OI should stay 10 (the SAME 10 contracts changed hands); got 20.
    - Why: the post-fill update unconditionally does `oi += fill_qty`, ignoring whether each side is opening or offsetting.
    - Fix: the 4-case truth table from D6, dispatched pre-trade on both sides' current direction: both opening → `oi += qty`; one offsetting → unchanged; both offsetting → `oi -= qty`. Implement and test all 4.
    - Cost avoided: not latency — risk-limit correctness: inflated OI distorts position caps and insurance-fund sizing.
    - Muscle: OI is a NET-EXPOSURE metric, not a flow metric — increment only on new exposure. Reapplies at: W71 liquidation OI bookkeeping, W90+ settlement OI.

  - **(EXPERT) (bar (c) violation) When `bench_oi_update_under_5ns` reports ~50 ns (and `bench_oi_band_is_plausible` confirms it's real work):**
    - Symptom: per-fill OI update 10× over budget; the negative-control band test passes (so the bench isn't measuring nothing — the cost is genuine).
    - Why: `open_interest` lives in a `HashMap<Symbol, u64>`, OR off the cache-warm struct, OR the 4-case dispatch goes through a vtable.
    - Fix: `open_interest: u64` directly on `LinearContract` (same struct as the order book — already warm). The dispatch is two compares + one add: `if both_opening { oi += qty } else if both_closing { oi -= qty }`. No HashMap, no vtable.
    - Cost avoided: ~45 ns/fill (50 → 5); over a 100k-fill burst that is ~4.5 ms of pure waste, and the HashMap path is also non-deterministic (breaks R9).
    - Muscle: bar-(c) hot path = field-on-struct + branchless/2-branch dispatch; no maps, no vtables. Reapplies at: W66 margin lookup, W71 liquidation queue, W74 matching v1.0.
