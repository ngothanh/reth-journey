  `LinearContract { mark_price, index_price, funding_rate, open_interest }` per TigerBeetle-style determinism. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: perpetual futures (perps) are the volume leader on crypto exchanges (Binance, Bybit, dYdX). The contract math (mark-price clamping, funding rates, open interest accounting) is where exchanges *lose money* when they get it wrong — LUNA, FTX, multiple smaller venues collapsed via mark-price manipulation that triggered cascade liquidations. Get determinism wrong (any `f64`) and your raft replicas diverge by W74 — matching-engine v1.0 fails its determinism gate. Downstream: W66 Wed margin.rs builds on these types; W71 funding TWAP + liquidation logic; W74 matching v1.0 integrates margin checks pre-trade; W83+ ledger-deterministic balance math; W88 VOPR replay determinism rides on the integer-only discipline established here.

  #### Phase 1 — Problem, requirements, design (~55 min, no code yet)

  - **The problem this primitive solves**: a naïve perps implementation uses `f64` for "fractional" quantities (funding rates, margin ratios, premia) because "they're percentages, that's what f64 is for". This is a triple bug: (a) non-deterministic across CPUs (FMA / rounding differs between x86 with AVX-512 and ARM Neon) → raft replicas diverge → consensus fails; (b) `f64::div` ≈ 10-30 cycles vs `i64::div` ≈ 3-5 cycles — wastes a fifth of your per-fill budget; (c) NaN propagation is a silent divergence vector. The fix is integer-only arithmetic with explicit denominators — TigerBeetle's ledger pattern.

  - **Requirements** — write in `crates/matching-engine/notes/66_contract_design.md`:
    - R1. `LinearContract { symbol, mark_price, index_price, funding_rate: SignedFrac, funding_interval, next_funding_at, open_interest, tick_size, contract_size, max_leverage, initial_margin_ratio: SignedFrac, maintenance_margin_ratio: SignedFrac }` — sized to ≤ 2 cache lines (~128 B) so per-fill access touches ≤ 2 L1 fetches.
    - R2. `Position { account, symbol, size: i64, entry_price, margin: u64, funding_paid_cum: SignedQty }` — signed size encodes side (positive long, negative short).
    - R3. **Float ban**: no `f32`/`f64` reachable from contract.rs or any perps module. All rates, ratios, premia use `SignedFrac { num: i128, denom: i128 }` with explicit denominator (typically 1e6 for bps×1e6).
    - R4. **Mark-price clamping**: `mark = clamp(book_mid, index ± max_basis)` where `max_basis = 0.5%`. Prevents thin-book manipulation triggering false liquidations.
    - R5. **Funding rate**: computed from `premium = (mark - index) / index`, clamped to ±0.75% per 8-hour interval. Pro-rated to the actual funding_interval.
    - R6. **Funding direction invariant**: premium > 0 → longs pay shorts. Premium < 0 → shorts pay longs. Sign error = arbitrage exploit.
    - R7. **Open Interest accounting**: OI increases only on net-NEW exposure (both sides opening). Position-offset trades do NOT increment OI. Σ size across all positions for a contract = 0 (longs = shorts).
    - R8. **Per-fill budget**: OI update ≤ 5 ns (one `u64` atomic add on hot cache line). Mark-price clamp ≤ 3 ns (two integer compares).
    - R9. **Determinism gate**: 1000 random trades + funding ticks across two replicas (different CPU arches, different `-march`) → byte-identical `ContractState` snapshots.

  - 🔧 **Why this matters**: margin determines WHO can take a position and WHEN they get liquidated. Get the formulas wrong and the exchange eats the loss when a trader's account goes negative — every major exchange failure (FTX, multiple smaller venues) trace partly to under-margined positions.   #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: a margin check is conceptually simple (compute notional, look up tier, compare equity vs maintenance threshold) but its cost is dominated by *memory layout*. Naïve `Vec<Box<Position>>` for an account's positions causes pointer-chase across ~10 random cache lines = ~1 µs cold — 2× the entire 500 ns budget. The fix is slot-indexed contiguous arrays (TigerBeetle pattern).

  - **Requirements** — write in `crates/matching-engine/notes/66_margin_design.md`:
    - R1. `MarginMode { Isolated, Cross }` — Isolated assigns collateral to a single position; Cross pools across all positions in the account.
    - R2. `initial_margin(notional, leverage) = notional / leverage` (integer division). One i64 divide; ~3 ns.
    - R3. `maintenance_margin(notional, contract)` — tiered: MM% rises with position size to prevent whales from holding massive thin-margin positions. ~6 tiers; lookup ≤ 10 ns.
    - R4. `margin_ratio(position, contract, available_collateral) -> SignedFrac` — equity / maintenance_margin, in SignedFrac (no float). Integer-only arithmetic inherited from W66 Tue contract.rs.
    - R5. `should_liquidate(position, contract, mode, account_balance) -> bool` — returns true when `margin_ratio < 1`. Liquidation price uses MARK price (R4 of W66 Tue), not last-trade (anti-manipulation).
    - R6. **Cross-margin sum cache-friendly**: per-account positions stored in a fixed-cap contiguous array (`[Option<Position>; N_MAX]` with N_MAX = 32) so the sum walks ≤ 32 contiguous cache lines, prefetcher-friendly. No `Vec<Box<Position>>`.
    - R7. **Pre-trade budget**: ≤ 500 ns p99 for the full check (lookup notional + maintenance_margin + cross-sum + ratio compare).
    - R8. **Integer-only**: no float in margin formulas; all rates as SignedFrac.
    - R9. **NUMA-bound**: per-account state lives on the shard's NUMA node (inherits W65 shard fix #1).

  - **Design walk-through** — answer each in your design doc; no peeking at Binance / Bybit margin spec until Phase 3:
    - D1. Sketch the tier table for `maintenance_margin`. Use Binance's reference (e.g., < $50k notional: 0.4% MM; $50k-$250k: 0.5%; ...). Why does MM rise with notional?
    - D2. Tiered lookup: linear scan vs binary search vs precomputed lookup. At 6 tiers, what's the right choice? (Hint: linear scan is fine; branch-predictor friendly; ~10 ns L1.)
    - D3. Per-account storage: pick ONE:
      (a) `Vec<Position>` (heap, reallocates on push),
      (b) `Vec<Box<Position>>` (heap, scattered),
      (c) `[Option<Position>; N_MAX]` (stack, contiguous, slot-indexed),
      (d) `Box<[Position; N_MAX]>` (heap once, contiguous).
      Justify against R6, R7. What's N_MAX (max positions per account)?
    - D4. Cross-margin sum: walk all positions, accumulate `equity = margin + unrealized_pnl + available_collateral`. At 10 positions/account, what's the cost for (a)/(b)/(c)/(d)? Compute warm vs cold-cache.
    - D5. Isolated vs cross dispatch: write the predicate. Isolated treats `available_collateral = 0`; Cross passes the account's pooled collateral. Why does Isolated isolate? (Liquidation of one position doesn't drain the account.)
    - D6. Liquidation price: why MARK and not last-trade? Walk the manipulation attack: thin-book pushes last-trade +5%; under last-trade-based liquidation, all 10× longs liquidate; attacker profits. Under mark-based (clamped at index ± 0.5%), the attack fails.
    - D7. **Pre-mortem #1 (Vec<Box<Position>> pointer-chase)**: write the 4-step trace where storing positions as `Vec<Box<Position>>` causes the cross-margin check to take ~1 µs cold (vs 500 ns budget). Compute the L2/L3/memory miss penalty.
    - D8. **Pre-mortem #2 (last-trade liquidation)**: write the 6-step manipulation trace. State why R5 (MARK-based liquidation) closes the hole.

  - **When `bench_pre_trade_margin_check_under_500ns` reports ~1.2 µs and `bench_cross_margin_sum_cache_friendly` shows ~10 cache misses:**
    - Symptom: pre-trade check is 2.4× over budget. `perf stat -e L1-dcache-load-misses` shows per-position cache misses dominating margin.rs samples. P99 latency spikes when traders come back after idle.
    - Why: storing per-account positions as `Vec<Box<Position>>` (or even `Vec<Position>` reallocated by `push`) means the cross-margin sum walks a heap-scattered list. At 10 positions/account, that's 10 random L2/L3/memory fetches: ~70 ns warm, ~1 µs cold. Cold path IS the common case (account hasn't traded in seconds).
    - Fix: per-account, store positions in a **fixed-cap `[Option<Position>; N_MAX]`** (N_MAX = 32) — contiguous, slot-indexed, no Box. Memory is ~32 × 64 B = 2 KiB = 32 cache lines, prefetched sequentially. For cross-margin, iterate once: ~32 cache lines × ~5 ns = 160 ns warm, ~3 µs cold-first-touch (the first miss is amortized; subsequent positions piggyback on the prefetcher). NUMA-bind the `Account` block to the shard's NUMA node (R9 — inherits W65 shard fix).
    - Cost avoided: ~50-900 ns per pre-trade check on cold path; eliminates `Vec` reallocation churn on position open/close (~50 ns malloc per add eliminated); reduces L1 pressure (contiguous array → 1 prefetch chain vs scattered allocs).
    - Muscle: data on a hot path is slot-indexed contiguous arrays, not `Vec<Box<T>>`. The bound (e.g., N_MAX positions per account) is design discipline, not arbitrary — derived from product spec. Reapplies at: W71 ADL queue (heap entries should be slot-indexed by account), W74 raft commit-table per replica, W83+ ledger account/transfer tables (TigerBeetle's exact pattern — pre-sized pools), W95 mini-db memtable rows.

  - **Design**:
    ```rust
    #[derive(Clone, Debug, RlpEncodable, RlpDecodable)]
    pub struct TempoTransaction {
        pub chain_id: u64,
        pub nonce: u64,
        pub max_fee_per_gas: U256,
        pub max_priority_fee_per_gas: U256,
        pub gas: u64,
        pub calls: Vec<Call>,                       // batched calls — key Tempo feature
        pub fee_token: Address,                     // pay gas in any ERC-20
        pub valid_before: Option<NonZeroU64>,       // timestamp ceiling (HLC ns)
        pub valid_after: Option<NonZeroU64>,        // timestamp floor (HLC ns)
        pub auth: Authorization,                    // EIP-7702-style delegation
    }

    #[derive(Clone, Debug, RlpEncodable, RlpDecodable)]
    pub struct Call {
        pub to: Address,
        pub value: U256,
        pub data: Bytes,
    }

    #[derive(Clone, Debug, RlpEncodable, RlpDecodable)]
    pub struct Authorization {
        pub chain_id: u64,
        pub delegate: Address,                       // contract address taking auth
        pub nonce: u64,
        pub y_parity: u8,
        pub r: U256,
        pub s: U256,
    }

    pub const TEMPO_TX_TYPE: u8 = 0x76;

    impl TempoTransaction {
        pub fn encode_for_signing(&self) -> Bytes {
            let mut out = vec![TEMPO_TX_TYPE];
            let rlp = rlp::encode(self);
            out.extend_from_slice(&rlp);
            out.into()
        }
        pub fn hash_for_signing(&self) -> B256 {
            keccak256(&self.encode_for_signing())
        }
    }
    ```
    **Invariants**:
    - First byte of encoded tx is 0x76 (the type tag). Followed by RLP of struct.
    - chain_id mandatory; replay-protected.
    - calls is ordered; execution applies them in order; revert of any rolls back all.
    - valid_before/valid_after enforce a time-window during which the tx is valid; sourced from `time::HybridLogicalClock` to ensure consensus-friendly across nodes.
    - fee_token = 0x0 means pay gas in native ETH (default).

    3. (~30 min) Encode-for-signing path: prefix 0x76 + RLP.
    4. (~30 min) Hash + sign via secp256k1; verify recovers correct from-address.
    5. (~30 min) Test: hand-construct a tx with known fields, verify encoded bytes match a fixture from tempoxyz/tempo's test data.
    6. (~20 min) Validity-window enforcement: at tx-pool admission, compare to current `HybridLogicalClock::now()`; reject if out-of-window.
  - **Pitfalls** (named, consensus-critical):
    - *Wrong RLP field order*: tempoxyz/tempo defines a SPECIFIC order; deviating breaks compatibility. **Symptom**: tx bytes don't match testnet acceptance. **Fix**: copy field order EXACTLY from upstream; treat RLP layout as wire-protocol-stable.
    - *Type prefix not included in signing*: signing the RLP without the 0x76 prefix → cross-type signature replay (0x02 EIP-1559 tx with same RLP could be valid as 0x76). **Symptom**: cross-type replay attack. **Fix**: hash MUST include type byte.
    - *valid_before timestamps in seconds vs nanoseconds*: HLC is nanoseconds; if you use seconds, time-window math is wrong by 1e9. **Symptom**: txs rejected as out-of-window. **Fix**: explicit unit documentation; type-wrap as `Timestamp(u64 /* ns */)`.
    - *Authorization replay*: same auth used across chains. **Symptom**: cross-chain delegation hijack. **Fix**: chain_id field in Authorization; signature MUST cover it.
    - *Batch atomicity*: calls[0] succeeds, calls[1] reverts — must rollback calls[0]. **Symptom**: partial-execution state corruption. **Fix**: execute all calls in single transaction frame; revert rolls back everything (W50 journaling).
