  - 🔧 **Why this matters**: Cold-start over a 10M-vector index by re-inserting takes minutes/hours; mmap'd graph

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: an in-memory HNSW with 10M vectors costs hours to rebuild from raw
    inserts after a process restart. Without an on-disk snapshot we either keep the process alive forever
    (no rolling deploys, no OOM tolerance) or accept multi-hour cold starts (no autoscale). mmap'd files mean
    `open()` is just `mmap()` + parse a small header; the kernel pages in vectors on demand. Without this,
    every operational primitive that follows — WAL replay, segment management, deploy automation — is moot.

  - **Requirements** — write in `crates/vector-db/notes/103_persist_design.md`:
    - R1. `save(graph, dir)` produces a directory readable by `load(dir)` in a fresh process; recall is
      bit-identical to the in-memory graph.
    - R2. `save()` is atomic w.r.t. crash: a kill -9 mid-save leaves either the prior snapshot intact or no
      snapshot, never a half-written one. Every file is written to `<name>.tmp` + fsync + rename.
    - R3. `load()` mmaps `vectors.bin` and `adjacency.bin` read-only and returns within 200 ms on a 1M-vector
      index (cold OS cache acceptable for the first page; bench reports wall time).
    - R4. `load()` rejects a corrupted file with a structured error (CRC mismatch, length mismatch,
      version mismatch) — never SIGBUS, never silent garbage.
    - R5. Adjacency layout is fixed-size per node per layer (`m_max0` neighbors padded with `u32::MAX`
      sentinel) so a node's neighbors are reachable by `O(1)` index, not a hashmap probe.
    - R6. All on-disk integers are little-endian and decoded via `bytemuck::Pod` — index built on x86 loads
      identically on ARM.
    - R7. After mmap the loader calls `madvise(Random)` so the kernel does not waste I/O on
      sequential readahead.

  - **Design walk-through** — answer each in your design doc; no peeking at Qdrant
    `graph_layers.rs::save/load` or faiss `index_io.cpp` until Phase 3:
    - D1. Directory layout: list every file and what it holds. Which file carries the version + CRCs +
      counts that the other files trust? (Hint: one root-of-trust file is easier to atomic-rename than five.)
    - D2. Self-referential slice problem: `PersistedHnsw` owns the `Mmap` AND a `&[f32]` borrow into it.
      Rust forbids this directly. Name three escape hatches (`ouroboros`, `Box::leak` + `'static`, raw
      pointer + manual Pin) and pick one — justify based on the index's lifetime (open-once, long-lived).
    - D3. CRC: which CRC poly, computed when (during save? lazily on first load? eagerly on every open?),
      stored where? Trade-off — eager-verify costs N MB of I/O on open, lazy-verify risks reading garbage
      on a hot path.
    - D4. Atomic rename order: you have 3 `.tmp` files. In what order do you rename so a crash at any point
      leaves a *coherent* state? (Hint: rename the root-of-trust LAST.)
    - D5. mmap return type: do you mmap once per file or fold everything into one file? Trade-off — one
      file is simpler atomicity, multiple files allow per-section `madvise`.
    - D6. Sentinel choice for "no edge": `u32::MAX` vs `0` vs an explicit length prefix per node. Which
      preserves O(1) random access? Which wastes the most bytes on sparse layers?
    - D7. **Pre-mortem (the load-bearing question)**: write the 5-step interleaving where save() crashes
      after writing `vectors.bin.tmp` and renaming, but BEFORE writing `header.bin`. What does the next
      `load()` see? Convince yourself your rename order survives it. If you cannot write the bad
      interleaving, your atomicity story is wrong.
  - **Output**: `notes/103_persist_design.md` with R1–R7, answers to D1–D7, the directory-layout sketch,
    the rename-order diagram, the pre-mortem trace.

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)

  - **When `save_load_roundtrip_recall_identical` fails to compile with E0515 / lifetime errors:**
    - Symptom: `PersistedHnsw` field `vectors_slice: &[f32]` cannot borrow from `_vectors_mmap` field
      in the same struct — "cannot return value referencing local data".
    - Why: Rust has no language-level self-referential struct; the slice's lifetime must outlive the mmap
      it points into, but they share the struct's lifetime.
    - Fix: pick the escape hatch from D2. For a long-lived open-once index, `Box::leak` of the mmap and
      stashing a `&'static [f32]` is the simplest correct choice; document that `Drop` for `PersistedHnsw`
      reclaims the leak via `Box::from_raw`.
    - Muscle: self-referential structs are a design smell — either erase the lifetime explicitly
      (`'static` + leak + manual Drop) or restructure so the slice is derived on demand from the mmap.
      Reapplies at: W104 segment manager (per-segment mmap), W108 read-only replica mmap sharing.

  - **When `crash_mid_save_leaves_prior_snapshot_intact` finds snapshot B is loaded but `vectors.bin` is
    new and `header.bin` is old:**
    - Symptom: `load()` succeeds but search returns wrong neighbors — header counts disagree with the
      actual vector data.
    - Why: rename order put `vectors.bin.tmp → vectors.bin` BEFORE `header.bin.tmp → header.bin`. A crash
      between them leaves a coherent-looking but mismatched pair.
    - Fix: rename `header.bin` LAST. The header is the root-of-trust; until it's renamed, `load()` sees
      either the old header (which references old `vectors.bin` — but you overwrote it!) or no header.
      Correct fix: write the new snapshot into a new subdir `snapshot.tmp/`, rename the *directory*
      atomically. Directory rename is the single observable.
    - Muscle: atomic "publish" of multi-file state = write to a sibling directory, rename the directory.
      Reapplies at: W104 segment swap, W107 manifest publication, W26 WAL group commit.

  - **When `load_rejects_crc_mismatch` panics with SIGBUS instead of returning Err:**
    - Symptom: `load()` mmaps the file, the CRC check runs *after* we've already constructed a slice over
      the bad bytes; a downstream read SIGBUS-es when it touches a hole that the OS hasn't mapped.
    - Why: CRC verification happened *after* mmap and *after* slice construction. The contract said
      "verify before mmap" but the code mapped first.
    - Fix: read the header (only ~256 bytes) via a normal `File::read` BEFORE mmap; verify the file length
      matches header.expected_size; only then mmap. CRC of body computed by walking the mmap with bounds
      checks (or pread-style chunked verify if you want to avoid mmap on the failing case).
    - Muscle: mmap is a *commitment* — verify length and trust the metadata BEFORE you touch the mapped
      region. Reapplies at: W104 segment open, W108 replica file mapping.

  - **When `cold_start_within_200ms_for_1m_vectors` reports ~2 s instead of ≤ 200 ms:**
    - Symptom: bench wall-time is 10× the threshold; `perf stat` shows ~2M page faults during `load()`.
    - Why: you eagerly walked the entire mmap (e.g. an `iter().sum()` smoke-check) inside `load()`, paging
      in the whole file. mmap's win is *lazy* paging — fault only what you read.
    - Fix: `load()` should ONLY parse the header + run the size + CRC of the header itself. Body CRC, if
      enabled, is gated behind `load_with_verify(true)` and not on the hot path.
    - Cost avoided: ~1.8 s on a 4 GB index — turns a 200 ms open into 200 ms instead of 2 s.
    - Muscle: mmap's value is lazy paging; any "verify the whole file on open" defeats the point.
      Reapplies at: W104 segment open hot path, W108 replica startup.

  - **When `load_rejects_version_mismatch` succeeds but `load_on_arm_matches_x86_bytes` produces garbage f32s:**
    - Symptom: a vector saved as `[1.0, 2.0]` on x86 decodes to `[3.85e-34, 1.10e-26]` when bytes are
      byte-swapped to simulate ARM.
    - Why: you used the host's native endianness implicitly (`*ptr as f32`), not an explicit
      little-endian decoder.
    - Fix: every numeric on disk is explicit little-endian. `bytemuck::cast_slice` is fine on LE hosts;
      on BE hosts you must byte-swap. Simpler: store as `[u8; 4]` and decode via `f32::from_le_bytes`.
    - Muscle: on-disk formats are explicit-endian or they are wrong; "host native" is a portability bug
      waiting to fire on the first ARM CI run. Reapplies at: W104 segment header, W107 manifest format.

  - **When `crash_mid_save_leaves_prior_snapshot_intact` still fails after directory-rename:**
    - Symptom: even with directory rename, after crash the new dir exists but is missing one file;
      `load()` errors out and you lose the prior snapshot because you renamed it away.
    - Why: directory rename was correct, but you removed the OLD snapshot dir BEFORE confirming the new
      one was fsynced and complete. Order: write, fsync each file, fsync the dir, rename, fsync parent
      dir, *then* GC the old.
    - Fix: explicit fsync of each `.tmp` file AND the containing directory after rename; only after that
      is the old snapshot dir safe to delete. Better: don't delete — keep N-1 snapshots and let GC be a
      separate, idempotent operation.
    - Muscle: rename atomicity requires fsync of the parent directory; without it, the rename may not
      survive a power loss. Reapplies at: W104 segment swap, W107 manifest publish.

  - **5-year failure mode** (write in `notes/103_persist_followup.md` after green): when indices grow to
    100 M+ vectors, single-file mmap exhausts virtual address space on 32-bit ARM edge devices AND saturates
    the kernel's `vm.max_map_count`. Migration trigger: sharded snapshot directory with per-shard mmap;
    name the sharding key (vector ID range vs. payload hash) and the page-fault SLO that triggers the cut.

**Tuesday — vector-db: wal for writes**

- [ ] **Build**: insertions write a WAL record (via `wal::Wal`) BEFORE updating graph. Crash recovery replays into
  in-memory graph. (~total 150 min across 3 phases)
  - 🔧 **Why this matters**: snapshots (Monday's `persist.rs`) are infrequent (minutes apart); the gap between
    snapshot and crash must be recoverable. WAL records each insert as an append-only log; recovery replays from
    last snapshot's LSN. Same pattern mini-db uses — direct reuse of `crates/wal/`. Downstream consumers:
    W103 Wed `Txn` wrapper batches multiple inserts into one WAL record; W104 segment manager has per-segment
    WAL; W109 ops runbook references this recovery sequence as the source-of-truth for RTO.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: a snapshot taken at LSN N protects everything up to N; every insert
    after N is in RAM only and lost on crash. Without a WAL, every `insert` either pays a full-snapshot
    fsync cost (unusable) or risks data loss on crash (unacceptable for a database). The WAL is the bridge:
    cheap append-only fsync per insert, durable replay on restart. faiss explicitly has NO WAL — that's a
    differentiator your vector-db ships.

  - **Requirements** — write in `crates/vector-db/notes/103_wal_design.md`:
    - R1. `insert(vec, payload)` MUST fsync the WAL record before mutating the in-memory graph
      (durability-before-visibility ordering).
    - R2. `open(dir)` reconstructs the graph by loading the latest snapshot AND replaying every WAL record
      whose LSN > `snapshot.last_lsn`; final state is bit-identical to pre-crash state.
    - R3. Replay is **deterministic** — same WAL bytes ⇒ same graph topology ⇒ same recall. This forbids
      RNG-driven decisions during replay (level assignment, neighbor pruning ties).
    - R4. Replay throughput ≥ 50k records/sec on a consumer SSD; verified by a bench.
    - R5. A `SnapshotMark { snapshot_lsn }` WAL record is written ONLY after the snapshot directory rename
      succeeds and is fsynced; replay starting before this mark must safely re-apply records the snapshot
      already contains (idempotent replay).
    - R6. WAL is auto-truncated (or marked safe-to-truncate) only after a `SnapshotMark` is durable in the
      WAL itself — never before.
    - R7. `Delete { id }` records leave tombstones during replay, not actual graph deletion (HNSW deletes
      are non-trivial; defer to compaction).
    - R8. Group commit: per-insert fsync amplification is bounded — callers can request `sync_up_to(lsn)`
      to batch fsyncs across concurrent inserts.

  - **Design walk-through** — answer each in your design doc; no peeking at Qdrant
    `segment_builder.rs` until Phase 3:
    - D1. `VectorWalRecord` enum shape: list every variant. Does an `Insert` carry the assigned `level`
      and the assigned `id`, or are those re-derived on replay? (Hint: think about R3.)
    - D2. Encoding: bincode, postcard, or hand-rolled? Argue from on-disk stability — does a `serde`
      derive change break old WALs? How do you version the record schema?
    - D3. Ordering: name the exact sequence of operations inside `insert()`. Where does the WAL fsync
      sit relative to graph mutation, payload write, ID allocation, level assignment?
    - D4. Replay path: does replay call the same `insert()` method, or a parallel `insert_replay()`?
      What's the trade-off? (Hint: R3 + R5 both want determinism, but `insert()` does RNG.)
    - D5. SnapshotMark race: write the 6-step interleaving showing why writing `SnapshotMark` BEFORE
      the snapshot dir rename causes data loss on crash. Then write the safe order.
    - D6. ID stability: explain why "graph re-assigns the next ID" during replay corrupts payload links.
      What's the fix? (Hint: record carries the ID; insert path takes the ID as a parameter.)
    - D7. Group commit hook: how does `insert()` block waiting for `sync_up_to(my_lsn)` without
      serializing all inserts? (Hint: the same Parker primitive from W004 + a per-LSN waiter list.)
    - D8. **Pre-mortem (the load-bearing question)**: write the 5-step interleaving where a process
      crashes between WAL append and the graph mutation. After restart, what does the in-memory state
      contain? What does `recall` look like for that ID? Convince yourself R2 still holds.
  - **Output**: `notes/103_wal_design.md` with R1–R8, answers to D1–D8, sequence diagram for `insert()`,
    SnapshotMark race trace, replay decision tree.

  #### Phase 3 — Make the tests pass, one failure at a time (~75 min)

  - **When `wal_fsync_precedes_graph_mutation` reports the reader sees the new ID before fsync:**
    - Symptom: reader observes `graph.contains(id)` is true while the WAL hook is still blocking the
      fsync — durability lags visibility.
    - Why: code path called `graph.insert(vec)` BEFORE `wal.sync_up_to(lsn)`. The WAL append succeeded
      but the fsync hadn't completed when the in-memory mutation became visible.
    - Fix: strict ordering inside `insert()` — (1) allocate ID + level deterministically, (2)
      `wal.append(record)`, (3) `wal.sync_up_to(lsn)`, (4) ONLY THEN `graph.insert_with_id_and_level(...)`
      and `payload.put(id, ...)`. The fsync is a write barrier between log and memory.
    - Muscle: durability-before-visibility — never expose state that isn't yet on disk. Reapplies at:
      W26 WAL group commit, W104 segment manager swap, W107 manifest commit.

  - **When `replay_is_deterministic` fails — second-run adjacency hash differs from first-run:**
    - Symptom: adjacency hash differs by ~30% of nodes; recall regresses 0.5% after a single replay.
    - Why: `graph.insert()` calls an RNG inside `assign_level()`; replay runs the RNG in a different
      thread-local state and assigns different levels to nodes, changing the search graph topology.
    - Fix: WAL record's `Insert` variant carries `level: u8` and `id: NodeId`. Replay calls
      `graph.insert_with_id_and_level(id, level, vec)` which bypasses the RNG entirely. Live `insert()`
      computes level, records it, then commits.
    - Muscle: deterministic replay forbids RNG in the replay path — capture every RNG-derived decision
      in the log record. Reapplies at: W26 WAL replay, W104 segment rebuild, W74 raft state machine.

  - **When `snapshot_mark_only_after_rename_durable` finds the snapshot dir is renamed but the
    `SnapshotMark` WAL record was lost on crash, and recovery still trusts the snapshot:**
    - Symptom: after crash, `open()` loads the new snapshot (because the dir is there) but skips
      replay of LSNs ≥ snapshot.last_lsn — yet those records were the only durable copy of the new
      inserts between marks. Data loss.
    - Why: code wrote `SnapshotMark` to WAL BEFORE fsyncing the snapshot dir, or trusted dir presence
      alone as the "snapshot is durable" signal.
    - Fix: order is (1) write snapshot files to `snapshot.tmp/`, (2) fsync each file + the tmp dir,
      (3) rename `snapshot.tmp/` → `snapshot/`, (4) fsync parent dir, (5) `wal.append(SnapshotMark)`,
      (6) `wal.sync_up_to(mark_lsn)`. Recovery trusts ONLY records where SnapshotMark is durable in the
      WAL; the snapshot dir alone is suggestive, not authoritative.
    - Muscle: a multi-stage commit needs an explicit durable "commit point" — the SnapshotMark IS that
      point and it lives in the more-frequently-fsynced log. Reapplies at: W104 segment swap,
      W107 manifest commit, W26 group commit boundary.

  - **When `replay_is_idempotent_for_records_in_snapshot` reports 1.1k IDs instead of 1k:**
    - Symptom: replay double-applies the first 100 inserts because the snapshot already contains them
      AND the WAL still contains them.
    - Why: replay starts from `snapshot.last_lsn + 1` is the intended contract, but on a partial
      crash you may not know which mark is authoritative. A safe replay strategy must tolerate
      re-applying records that the snapshot already absorbed.
    - Fix: `graph.insert_with_id_and_level` is idempotent — if the ID already exists with the same
      level and vector hash, it's a no-op. Replay's safety contract: "start from a conservative LSN
      (oldest possibly-missing mark) and let idempotency handle the overlap."
    - Muscle: idempotent operations let replay tolerate ambiguity in the recovery start point.
      Reapplies at: W74 raft log replay, W26 WAL recovery, W104 segment rebuild.

  - **When `replay_throughput_50k_per_sec` reports 5k records/sec:**
    - Symptom: bench wall-time 10× the threshold; profile shows 80% of time in `serde_json` payload
      decode and another 15% in `bincode` deserialize.
    - Why: replay decoded payloads (potentially large JSON) for every record even though the in-memory
      graph only needs the vector and ID; payload restore is a separate concern that could be
      done lazily.
    - Fix: split the WAL record into a fast header (id, level, vector) and a lazy body (payload bytes,
      not decoded until queried). Replay's hot loop decodes only the header.
    - Cost avoided: ~95% of replay time on payload-heavy workloads; brings 100k records from 20 s to ≤ 2 s.
    - Muscle: replay should reconstruct minimum viable state; defer expensive decode until first read.
      Reapplies at: W26 WAL replay, W104 segment load, W107 manifest hydration.

  - **When `group_commit_batches_fsync` reports 16 fsyncs instead of ≤ 4:**
    - Symptom: 16 concurrent inserter threads each call `wal.sync_up_to(my_lsn)` and each triggers a
      distinct fsync syscall.
    - Why: `sync_up_to` either fsyncs unconditionally, or its de-duplication uses a load not a CAS
      (lost-update on the "current synced LSN" → multiple fsyncs win).
    - Fix: leader-election style: the first caller into `sync_up_to(lsn)` becomes the syncer; later
      callers with lsn ≤ leader_lsn just park on a Parker (W004) and wait. Leader fsyncs, updates the
      "durable_lsn" atomic, and unparks everyone whose lsn ≤ durable_lsn.
    - Muscle: group commit = leader-election + parker; never per-caller fsync. Reapplies at: W26 WAL
      group commit, W107 manifest commit batching.

  - **5-year failure mode** (write in `notes/103_wal_followup.md` after green): when write rate
    crosses ~100k inserts/sec sustained, single-WAL fsync becomes the bottleneck even with group
    commit (one disk's IOPS ceiling). Migration trigger: sharded WAL keyed by node-ID range, one fsync
    per shard. Name the cross-shard ordering invariant you'd lose (none, if records are
    independent — but `Delete` referencing an `Insert` in a different shard is a constraint).
