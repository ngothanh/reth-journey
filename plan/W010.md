- [ ] **Concurrency drill #11 of 28 — SPSC ring + false-sharing microbench** (solo, ~300 min, bar (c)). The
  throughput difference between an SPSC ring with `AtomicU64` head/tail on one cache line vs
  `CachePadded<AtomicU64>` head/tail on separate lines is one of the most dramatic measurements in
  concurrency. You will measure it on YOUR machine and reconcile it to the MESI cost model.
  Build `crates/concurrent/src/spsc_ring.rs` — a fixed-capacity single-producer single-consumer ring buffer
  `SpscRing<T, const N: usize>` (N a power of two). Two variants behind cfg flags: one with raw adjacent
  atomics, one with `CachePadded`. Single push/pop per cycle. This is a reusable component (mirrors
  `rtrb::RingBuffer`), consumed by W11 `backpressure`, W26 `wal` ring, W77 aeron term buffer.
  Constraints: no peek at `crossbeam_channel`, `rtrb`, or LMAX Disruptor source until COMPARE.
  - *Back-of-envelope* (bar (c)): one push touches `tail` (store, Release) + reads `head` (load, Acquire);
    one pop touches `head` + reads `tail`. On a single-socket Apple M-series, a cross-core MESI invalidation
    that bounces a line between the producer's and consumer's L1 costs **~7 ns** (same-die L2/SLC round trip),
    vs **~0.5 ns** for an L1-resident hit. If head and tail share ONE line, every push invalidates the line
    the consumer just read and vice-versa: ~2 cross-core bounces per push+pop pair ≈ **~14 ns of pure MESI
    tax per op**, capping throughput near `1 / 14ns ≈ 70M ops/s` minus loop overhead → measured ~40-50M is
    realistic. Pad them onto separate lines and each stays L1-resident on its owner core: the tax drops to
    ~0.5 ns and throughput rises 3-5×. (On an x86 dual-socket server the SAME false sharing crosses the QPI/UPI
    link at **~200 ns** per bounce — a different, much larger cliff; do not conflate the two scenarios.)
  - **Spec**: derive cap=N must be power-of-two from the modulo cost (mask `& (N-1)` vs `% N`). Invariants
    for SPSC: no two values pushed without a pop in between (cap=1 corner); index wraparound preserves order;
    producer never observes its own write through the consumer's view. Predict the throughput ratio between
    unpadded and padded under 2 threads.
  - 🧮 **Paper drill** — write in `notes/10_drill11_drill.md`:
    - D-LAYOUT on `SpscRing<T,8>` head/tail: draw the byte map of the unpadded variant — two adjacent `AtomicU64` at offsets 0 and 8 — and the 128 B (aarch64) / 64 B (x86) cache-line boundary; mark that head and tail share ONE line (the false-sharing hazard) and redraw the `CachePadded` variant with each cursor on its own line.

  - **Compare**: open `rtrb::RingBuffer` source. They pad head/tail AND keep a separate `tail_cached` /
    `head_cached` per side. What's the cached-counter trick and what does it save? (Answer: the producer
    caches the last-seen `head` so it only re-reads the consumer's atomic when its cache says full — turning
    a guaranteed cross-core load into a rare one.)
  - **Symptom card (perf-bearing, bar (c) violation)**:
    - **(EXPERT) Expect to hit (perf) #1 — adjacent `head`/`tail` atomics false-share one cache line
      (bar (c) violation):**
      - Symptom: criterion shows unpadded ~40-50M ops/s vs padded ~150-200M ops/s on M-series; the
        `padded_beats_unpadded_by_at_least_2x` control passes, confirming the gap is real. `perf` (or
        `Instruments` on macOS) shows the unpadded run dominated by cross-core line transitions on the ring's
        head/tail line.
      - Why: producer's Release store to `tail` and consumer's Acquire load of `tail` (and symmetrically
        `head`) live on the SAME cache line; each write forces the other core's copy to Invalid (MESI M→I),
        so the next read is a cross-core miss.
      - Fix: wrap each in `CachePadded<AtomicU64>` (align to 128 B on aarch64, 64 B on x86) so producer-owned
        and consumer-owned counters never share a line.
      - **Cost avoided: ~7 ns cross-core MESI invalidation per atomic access × ~2 contended accesses per
        push+pop ≈ ~14 ns/op of pure coherence tax → a 3-5× throughput loss on single-socket M-series
        (≈ ~200 ns/op = a separate, larger x86 cross-NUMA cliff). (bar (c) violation)**
      - Muscle: any pair of atomics written by different threads needs separate cache lines — pad producer
        and consumer cursors apart. Reapplies at: W11 MPMC head/tail + `backpressure` watermark, W26 WAL
        `write_offset`, W77 aeron `tail_offset`.
  - **Numbers (perf-bearing)**: predict per-op throughput on YOUR single-socket M-series — unpadded

    (M-series = 128 B line, x86 server = 64 B line; ratio differs). Within 30% of measured.
  - **Scale curve (Gap #2)**: measure throughput with exactly 1 producer + 1 consumer (SPSC). Document why
    adding a 2nd producer or 2nd consumer breaks the algorithm (the single-writer-per-cursor invariant is
    what makes the unbounded-counter + Release/Acquire publication sound — two writers on `tail` re-introduce
    a CAS race the algorithm doesn't handle). SPSC is the fixed point.
  - **5-year failure mode** (`notes/10_drill11_followup.md`): when cache-line size changes (Apple Silicon
    went 64→128; future chips may go 256), a hard-coded `#[repr(align(64))]` is wrong. Trigger: deploy on a
    new ISA. Fix: target-arch cfg selection (W4 `chain_head` already does this — confirm).
  - **Production handoff**: this padding rule lands at every shared-counter in the plan; specifically W11

    - Symptom: every keccak path is nibble-reversed within each byte; downstream HashBuilder fixtures all miss.
    - Why: low nibble emitted before high.

    - Muscle: nibble order is big-endian within each byte. Reapplies at: W10 Wed HashBuilder, W20 TrieWalker, W31.
  - **(SENIOR) When `nibbles_hp_encode_leaf_odd` produces the wrong flag:**

    - Why: you treated `is_leaf` and `is_odd` as separate booleans (or XOR'd them), not a 2-bit field.
