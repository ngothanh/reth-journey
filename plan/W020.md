**Monday — MPT deeper theory + `BranchNodeCompact`**

- [ ] Re-read ethereum.org MPT docs + 2-3 blog explanations. (~45 min)
- [ ] **Build**: `crates/eth-trie/src/branch_compact.rs` — BranchNodeCompact mirroring reth_trie. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: a naive MPT branch node carries 16 child hashes (16 × 32 = 512 bytes). 90%+ of
    branches in real Ethereum state are sparse (≤4 children). `reth_trie::BranchNodeCompact` — a bitmask-indexed
    representation that stores only present children — cuts intermediate-trie storage by ~4×. This single
    representation choice dominates trie-db size. Downstream consumers: W20 ProofRetainer (holds these), W22+
    MerkleStage (reads/writes from DB), W31 persistent MPT (serializes to MDBX as the intermediate-trie table).

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: state-root computation walks every dirty path of the MPT. Branch
    nodes are the bulk of intermediate storage. Storing 16 child slots when only 3 are non-null wastes ~80%
    of the bytes — multiplied by ~700M intermediate nodes on a full mainnet state, the difference is hundreds
    of GB. `BranchNodeCompact` uses three 16-bit bitmasks (`state_mask`, `tree_mask`, `hash_mask`) to encode
    "which slots are present" and stores only those slots' hashes packed into a `SmallVec`.

  - **Requirements** — write in `crates/eth-trie/notes/20_branch_compact_design.md`:
    - R1. Struct with `state_mask: u16`, `tree_mask: u16`, `hash_mask: u16`, `hashes: SmallVec<[B256; 4]>`,
      `root_hash: Option<B256>`.
    - R2. Invariant 1: `hash_mask.count_ones() == hashes.len()`.
    - R3. Invariant 2: `tree_mask & !state_mask == 0` (tree-bit must be a subset of state-bit).
    - R4. Invariant 3: `hash_mask & !state_mask == 0` (hash-bit must be a subset of state-bit).
    - R5. Invariant 4: constructor `try_new(state, tree, hash, hashes)` rejects any tuple violating R2/R3/R4
      with a typed error; never panics on malformed input.
    - R6. RLP form (wire/proof representation): 17-element list — 16 child slots + value slot. Empty slots
      encode as `0x80` (RLP empty string).
    - R7. Compact form (DB representation): three u16 masks (little-endian) + length-prefixed Vec<B256>.
      Compact form is what hits MDBX; RLP form is what proofs ship.
    - R8. `iter_children` yields `(nibble: u8, ChildSlot)` in **MSB-first nibble order** (slot 0 first, slot
      15 last).
    - R9. `set_child(nibble, ChildRef)` maintains all three masks consistently — if you set a child, its
      `state_mask` bit MUST flip on; if you set its hash, `hash_mask` flips on.
    - R10. Encode → decode → encode is byte-identical on the compact form (canonical encoding; no
      ambiguity).

  - **Design walk-through** — answer each in your design doc; no peeking at
    `reth/crates/trie/trie/src/nodes/branch.rs` until Phase 3:
    - D1. The 3 masks (`state`, `tree`, `hash`) have a containment relationship — write it out as a Venn
      diagram. Which mask is always the largest? What does it mean if a bit is in `state` but not in `tree`?
      (Hint: that child exists but is *embedded* — inlined into the parent, not stored separately in DB.)
    - D2. The `hashes` field stores hashes "in nibble order, only for bits set in hash_mask". Write the
      indexing formula: given `nibble = 5` and `hash_mask = 0b0000_0000_0010_1100`, what's the index into
      `hashes`? (Hint: `popcount(hash_mask & ((1 << nibble) - 1))`.)
    - D3. The 17th RLP slot — the "value at this branch" slot — exists per yellow paper but is almost
      always empty in modern Ethereum (accounts terminate at leaf nodes, not branch nodes). Why is it
      still required in RLP encoding? What happens if you omit it?
    - D4. Embedded children: a child whose RLP encoding is < 32 bytes is inlined into the parent's RLP
      (not hashed). The threshold is **strictly less than 32**, not `<=`. Why? (Hint: think about what a
      hash IS — keccak256 output is 32 bytes; embedding anything 32 bytes or larger would conflict with
      hash-vs-inline disambiguation.)
    - D5. `SmallVec<[B256; 4]>` inline capacity: 90% of branches have ≤4 hashes after compaction. Bump
      the inline size to 16 — what happens to memory? (Hint: `B256 = 32 B`, so `[B256; 16] = 512 B` on
      the stack per branch node; cache thrash.) Justify the choice of 4.
    - D6. Compact form encoding: write the exact byte layout for `BranchNodeCompact { state_mask: 0x0F00,
      tree_mask: 0x0100, hash_mask: 0x0E00, hashes: [h1, h2, h3] }`. How many bytes total?
    - D7. Pre-mortem: write the bad-input scenario in 4-6 steps where a malformed compact-form blob (e.g.
      `hash_mask` bits don't match `hashes.len()`) gets decoded without error and produces a
      `BranchNodeCompact` that later state-root computation reads with the wrong child hashes — yielding
      a silent consensus fork. If you cannot write the scenario, your `try_new`/`decode` is missing
      the invariant guard.

  - **Output**: `notes/20_branch_compact_design.md` with R1–R10 + answers to D1–D7 + the bad-input scenario.

  #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

  - **When `iter_children_yields_msb_first` yields children in REVERSE order:**
    - Symptom: expected `[2, 5, 7]`, got `[7, 5, 2]`. The iter's bit-scan walks high-to-low.
    - Why: nibble order is MSB-first per yellow paper §C — bit 0 (LSB) of `state_mask` corresponds to
      nibble 0 (the first child); but a naive `(state_mask >> i) & 1` iteration starting at i=15 walks
      backward.
    - Fix: iterate `for i in 0..16 { if (state_mask >> i) & 1 == 1 { yield (i as u8, ...); } }`. Add an
      assertion in the test that compares against a hand-encoded `eth_getProof` fixture.
    - Muscle: nibble ordering in MPT is MSB-first / low-bit-of-mask-first; off-by-one or reversed iteration
      fails every state-root check silently. Reapplies at: W20 walker.rs, W20 state_root.rs, W21 RLP
      compact-path encoding, W31 persistent MPT.

  - **When `compact_decode_rejects_inconsistent_masks` PASSES (decode accepts the bad blob):**
    - Symptom: hand-crafted blob with `hash_mask.count_ones() = 3` and 2 hashes decodes to a
      `BranchNodeCompact { hashes: vec![h1, h2] }` — no error. Later state-root computation reads
      `hashes[2]` and panics on index out of bounds.
    - Why: `compact_decode` reads `state_mask, tree_mask, hash_mask` then reads `len_prefix` hashes —
      but doesn't cross-check `hash_mask.count_ones() == len_prefix`. The two are consistent in valid
      blobs; the decoder trusts.
    - Fix: after reading the masks AND the hash count, assert `hash_mask.count_ones() as usize ==
      hashes.len()`; otherwise return `Err(LengthMismatch)`. This is the same invariant R2 — enforce it
      at the boundary (decode), not just at construction (`try_new`).
    - Muscle: every wire-format invariant must be re-checked at decode time; never assume the producer
      respected it. Reapplies at: W20 walker.rs (cursor invariants), W21 RLP `#[rlp(trailing)]` (decoder
      validates field count), W26 wal `record.rs` (every kind/flag combo re-validated).

  - **When `embedded_child_inline_under_32_bytes` produces an encoding that doesn't match the reth fixture:**
    - Symptom: the parent's encoded bytes contain a 32-byte hash where the test expected the child's raw
      30 bytes. Roots diverge on shallow tries.
    - Why: the encoder branched on `child.encoded_len() <= 32` (or `< 32` but using the wrong size — e.g.
      it counted the RLP header bytes when it should count only the body). The threshold is **strictly
      less than 32**, measured on the FULL encoded form (header + body).
    - Fix: `if child.full_encoded_len() < 32 { write child's bytes inline } else { write keccak(child).bytes() }`.
      Test against the reth fixture at exactly 31, 32, and 33 byte encodings to nail the boundary.
    - Muscle: the inline-vs-hash threshold is a strict-less-than at exactly 32 bytes, measured on the
      full RLP encoding; off-by-one fails consensus on every shallow trie. Reapplies at: W20 state_root.rs
      hash builder, W21 trie RLP encoders.

  - **When `bench_round_trip_5m_per_sec` reports 1.2 M/sec:**
    - Symptom: criterion shows ~800 ns/node round trip. Threshold (≥5M/sec ⇒ ≤200 ns/node) fails 4×.
    - Why: every `BranchNodeCompact` constructed in the bench heap-allocates a new `SmallVec<[B256; 4]>`
      even though the inline capacity should keep it on the stack — OR your `compact_encode` allocates
      a fresh `Vec<u8>` per call instead of writing into a reusable `BufMut`.
    - Fix: (1) verify `SmallVec::new()` for ≤4 hashes is heap-free via `dhat`; (2) make `compact_encode`
      take `&mut impl BufMut` so callers can pool the output buffer. Re-bench.
    - Cost avoided: ~600 ns/node × 100M intermediate nodes per full-state recompute = ~60 sec of pure
      alloc on every state-root walk.
    - Muscle: a hot codec must accept a caller-supplied buffer; allocating per-call destroys throughput
      even with cheap allocators. Reapplies at: W20 state_root.rs, W21 RLP encode helpers, W26 wal
      `record.rs` encode path.

  - **5-year failure mode** (write in `notes/20_branch_compact_followup.md` after green): when reth
    extends `BranchNodeCompact` with a fourth mask (e.g. a "verkle-witness" bit when EIP-6800 ships),

**Tuesday — `TrieStorage` abstraction over `StateCache`**

- [ ] **Refactor**: split TrieStorage into HashedNodeStorage + IntermediateStorage. (~total 80 min across 3 phases)
  - 🔧 **Why this matters**: a persistent MPT stores TWO physically distinct kinds of nodes — (a) hashed-state
    leaves (one row per account/slot) and (b) intermediate branch/extension nodes computed during state-root
    building. Conflating them in one trait forces every consumer to wade through the same K/V soup. reth's split
    allows MerkleStage to rebuild intermediate nodes incrementally from hashed state, never touching account-leaf
    storage. Downstream: W22 MerkleStage (consumes both), W27+ storage-trie::mdbx (implements both atop MDBX),
    W92 block-stm (parallel HashedNodeStorage snapshots).

  #### Phase 1 — Problem, requirements, design (~25 min, no code yet)

  - **The problem this primitive solves**: a single `TrieStorage` trait that lumps account leaves, storage
    leaves, and intermediate branches into one K/V interface makes the "rebuild intermediate from hashed"
    operation untyped — there's no way for the compiler to enforce that MerkleStage only writes intermediate
    nodes, never accidentally mutating hashed state. Splitting the trait makes the source-of-truth direction
    a type-level fact.

  - **Requirements** — write in `crates/eth-trie/notes/20_trie_storage_split_design.md`:
    - R1. `HashedNodeStorage` trait with `get_account`, `get_storage(account, slot)`, `account_cursor()`,
      `storage_cursor(account)`.
    - R2. `IntermediateStorage` trait with `get_branch(path)`, `put_branch(path, node)`,
      `delete_branch(path)`, `account_trie_cursor()`, `storage_trie_cursor(account)`.
    - R3. Load-bearing invariant: `IntermediateStorage` is rebuildable from `HashedNodeStorage` — given any
      `HashedNodeStorage` state, you can construct a fresh `IntermediateStorage` whose state-root matches the
      one maintained incrementally.
    - R4. Cursor keys in `account_trie_cursor` are nibble-prefix-ordered (lex by `Nibbles`).
    - R5. `storage_trie_cursor` is parameterized by `account: B256` — each account has its own storage trie.
    - R6. Hashed table is the source of truth; intermediate is a derived index. Writes go to hashed; W22+
      MerkleStage derives intermediate.
    - R7. In-memory test implementations (`MemoryHashed`, `MemoryIntermediate`) backed by `BTreeMap` to
      exercise the contract before MDBX backing arrives at W27.

  - **Design walk-through** — answer each:
    - D1. Trait method signatures: `&self` for reads, `&mut self` for writes — but in the MerkleStage where
      one thread reads hashed while another writes intermediate, what's the concurrency model? (Hint: defer
      to W22; for now, `&self` reads, `&mut self` writes; downstream wraps with `Arc<RwLock>` or per-shard.)
    - D2. Cursor lifetimes: `fn account_cursor(&self) -> impl Cursor + 'a` ties cursor to storage. Why does
      reth's cursor return *owned* `(Key, Value)` clones instead of borrowed slices? (Hint: nested loops
      with two cursors sharing storage hit borrow-checker walls.)
    - D3. Why parameterize `storage_trie_cursor(account)`? Sketch the alternative (a single global storage
      cursor) and explain why it breaks. (Hint: each account has its OWN storage trie root; a global cursor
      would yield interleaved storage slots from different accounts.)
    - D4. The "rebuildable from hashed" invariant (R3) — how do you TEST it? (Hint: insert 10k accounts via
      Hashed; rebuild Intermediate from scratch via MerkleStage's algorithm; compare to a parallel
      incrementally-maintained version. Both must produce the same root.)
    - D5. Pre-mortem: name the bad refactor that re-conflates the two traits (e.g. a `BulkWriter` extension
      trait that lets MerkleStage write both at once). What goes wrong?

  - **Output**: `notes/20_trie_storage_split_design.md` with R1–R7 + D1–D5 + the two trait skeletons.

**Wednesday — `TrieWalker` cursor**

- [ ] **Build**: `crates/eth-trie/src/walker.rs` — TrieWalker<S: TrieStorage> streaming traversal. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: building a state root requires touching every dirty account's trie path AND only
    those paths — not the whole trie. `TrieWalker` is the streaming cursor that yields paths in lex order,
    skipping subtrees that haven't changed. This is the algorithm that makes incremental MerkleStage tractable
    on a 700M-account state — without it, every block would re-walk the full trie. Downstream: Thursday's
    ProofRetainer (consumes walker output), Friday's StateRoot (drives walker for incremental root), W22
    MerkleStage (glues walker + DB cursor).

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: an incremental state-root computation must (a) yield trie paths
    in lex order so the hash builder receives them in the order yellow paper §C demands; (b) skip any subtree
    not touched by the current block's state changes; (c) report the cached hash of "clean" subtrees so the
    builder doesn't recompute them. Without lex order, the builder produces wrong hashes; without skipping,
    every block is O(state size); without cached-hash reporting, the builder still descends into clean
    subtrees and wastes I/O.

  - **Requirements** — write in `crates/eth-trie/notes/20_walker_design.md`:
    - R1. `TrieWalker<'a, C: TrieCursor>` with `advance() -> Option<Nibbles>`, `hash() -> Option<B256>`,
      `children_are_in_trie() -> bool`.
    - R2. Walker yields paths in **strict lex (nibble-prefix) order** — output is monotone.
    - R3. Walker skips subtrees not in `changes: &'a PrefixSet`.
    - R4. `hash()` reflects the cached hash of the current branch node WHEN its children are clean
      (`tree_mask` bit at current child position is set).
    - R5. `Nibbles` type uses inline `SmallVec<[u8; 64]>` (max trie depth ≈ 64 nibbles — `keccak256` output
      is 32 bytes = 64 nibbles).
    - R6. `PrefixSet` is a sorted `Vec<Nibbles>` of dirty paths; `contains_prefix(nibbles) -> bool` is O(log n)
      via binary search.
    - R7. Empty trie: `advance` returns `None` immediately on a cursor whose `first()` is `None` — never panics.
    - R8. Walker holds an exclusive cursor for its lifetime; concurrent writes to the trie are NOT permitted
      while walker is alive (caller's responsibility).

  - **Design walk-through** — answer each:
    - D1. The walker's `stack: Vec<StackItem>` represents the path from root to current position. Each
      StackItem holds `(Nibbles, BranchNodeCompact, child_index)`. Sketch the advance algorithm: when do
      you push, when do you pop, when do you yield?
    - D2. The `current_key: Nibbles` field tracks the path from root to current cursor position. When you
      pop a stack frame, `current_key` must shrink — by how much? (Hint: each branch frame contributed
      exactly one nibble.)
    - D3. The `PrefixSet` (dirty-path filter): given dirty paths `[[1,2], [5]]`, which nibbles should the
      walker visit for the root branch (depth 0)? (Hint: only children at nibbles 1 and 5, never 0, 2, 3,
      4, 6...15.)
    - D4. `children_are_in_trie()` returns whether the current child position has its `tree_mask` bit set
      — meaning the child is a STORED intermediate node (DB-resident), not an embedded one. The hash
      builder uses this to decide "feed cached hash" vs "descend further". Write the formula.
    - D5. Pre-mortem: name the off-by-one in nibble push/pop that produces walker output containing
      paths the dirty set never asked for. Explain how this corrupts state root.

  - **Output**: `notes/20_walker_design.md` with R1–R8 + D1–D5 + the advance pseudocode.

- [ ] **Build**: `crates/eth-trie/src/proof/retainer.rs` — ProofRetainer mirroring alloy_trie. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: EIP-1186 (`eth_getProof`) demands a Merkle proof of a specific account/slot.
    Naive approach: rebuild the trie, log every node — O(state size) per proof. Real approach: during
    state-root walk, *retain* only the nodes on the requested path. `ProofRetainer` is the side-channel
    observer of the hash builder that captures these nodes. Downstream: Friday's StateRoot orchestrator
    drives retainer alongside walker; Phase 5 RPC `eth_getProof` wraps this.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: a Merkle proof is the ordered list of RLP-encoded nodes from
    root to leaf along a target path. Generating it cheaply requires *observing* the hash builder as it
    constructs the trie root — capturing each node whose path is an ancestor of any proof target. Doing this
    after-the-fact (re-walking the trie per request) is too slow for RPC; doing it inline (as a side-channel
    during the existing state-root walk) is O(targets × tree depth) — bounded.

  - **Requirements** — write in `crates/eth-trie/notes/20_retainer_design.md`:
    - R1. `ProofRetainer::new(targets: Vec<Nibbles>)` — targets are nibble paths to the leaves we want
      proofs for; sorted lex internally.
    - R2. `retain(prefix: &Nibbles, encoded: &[u8])` — called by hash builder for every intermediate node;
      retainer decides whether to keep based on "is `prefix` an ancestor of any target?"
    - R3. Retained nodes are stored as **RLP-encoded bytes** (the wire form), NOT `BranchNodeCompact` (the
      DB form) — clients verify against the wire form.
    - R4. `into_proof() -> Vec<Bytes>` returns nodes in **strict lex order** of their paths (root first).
    - R5. Embedded children (RLP encoding <32 bytes) are NOT separately retained — they live inside the
      parent's encoding. R3+R4 imply this since the embedded child has no separate "path".
    - R6. Non-existence proofs: EIP-1186 also proves an account doesn't exist (returns empty value + path
      to nearest divergence). The retainer must capture the branch where the path diverges.
    - R7. Deterministic ordering: same (targets, trie) → same proof bytes, every call. `BTreeMap` over
      `HashMap` to guarantee.
    - R8. Storage-proof variant: a target inside an account's storage trie produces a separate
      account-proof + storage-proof chain.

  - **Design walk-through** — answer each:
    - D1. "Is prefix an ancestor of any target?" — write the formula. (Hint: `targets.iter().any(|t|
      t.starts_with(prefix))` for inclusion proofs; for non-existence, also retain if `prefix.starts_with(t)`
      at the divergence point.)
    - D2. Optimization: sorted `targets` + binary search makes the ancestor check O(log T) instead of
      O(T). Sketch the bsearch — what predicate?
    - D3. The hash builder hook: where does the retainer plug in? Sketch the callback shape — what
      arguments does the hash builder pass, what does retainer do with them?
    - D4. RLP form vs Compact form: if you retain `BranchNodeCompact` and the client tries to verify by
      `keccak(node) == parent_child_hash`, what goes wrong? (Hint: the hash is computed over RLP bytes,
      not compact bytes; mismatch.)
    - D5. Pre-mortem: write the scenario where a leaf node at the target path is missing from the proof
      (4-6 steps). Hint: targets are paths; the retainer's check is "ancestor of target", which doesn't
      capture the target ITSELF — fix is to retain `prefix == target` too.

  - **Output**: `notes/20_retainer_design.md` with R1–R8 + D1–D5 + the missing-leaf scenario.

    - Symptom: client (separate verifier) rejects with "hash mismatch at node 3". Your proof's

    - Why: you retained `BranchNodeCompact` bytes (DB form) instead of RLP-encoded bytes (wire form).
      The 8-byte difference is the compact form's mask-prefix vs RLP's list-header.
    - Fix: the hash builder emits RLP bytes — pass *those* into `retain`, not the compact form. Wire

      subtrees that share `[1,2,5]` as a non-ancestor.

      range of targets that COULD share a prefix, then check only those. Or: `targets.binary_search_by(|t|
      t.cmp(&prefix))` then walk forward while `t.starts_with(prefix)`.
    - Cost avoided: O(T) → O(log T + matches); at T=100 with 30-deep tries, ~3000× speedup on the
      retain hot path.

      never a linear `any()`. Reapplies at: W20 walker.rs (PrefixSet), W22 MerkleStage.

  - 🔧 **Why this matters**: this is *the* algorithm that determines whether your node accepts or forks. Every

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: a state-root is a 32-byte fingerprint of the entire account+storage
    trie. Recomputing it from scratch on every block (O(700M accounts)) is infeasible — sync would take
    months. Incremental state-root computation visits only dirty paths and feeds cached hashes for clean
    subtrees. The algorithm must be byte-identical to reth/geth/erigon or your node forks at the first block
    after divergence.

  - **Requirements** — write in `crates/eth-trie/notes/20_state_root_design.md`:
    - R1. `StateRoot<S: HashedNodeStorage, I: IntermediateStorage>` with `compute() -> Result<(B256,

    - R4. Account leaves' value is `RLP(Account { nonce, balance, storage_root, code_hash })` — order matters

    - R5. Storage roots are sub-trie roots, computed by recursive call to `compute` on the per-account
      storage trie.
    - R6. Storage root for an account with no storage is `EMPTY_ROOT_HASH` (not `B256::ZERO`).
    - R7. Code hash for accounts with no code is `KECCAK_EMPTY = keccak256("")` (not `B256::ZERO`).
    - R8. Walker's `children_are_in_trie()` true → feed cached hash to hash builder, DO NOT descend.
    - R9. `TrieUpdates` is the set of `(path, new_BranchNodeCompact)` pairs the caller must persist after
      compute returns; allows MerkleStage to commit atomically.
    - R10. Pass `EthereumTests::TrieTests` AND mainnet block 1 reconstruction.

      state machine and not a recursive function? (Hint: streaming input from the walker; can't hold the
      whole trie in memory.)

      does the hashed cursor do? Sketch the interleaving.

    - D5. Pre-mortem: name three places (each different) where `B256::ZERO` could silently substitute for
