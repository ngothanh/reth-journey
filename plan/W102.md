**Monday — vector-db: Scalar Quantization (SQ)**

- [ ] **Build**: `crates/vector-db/src/quantize/sq.rs` — `ScalarQuantizer { min, max, scale }`; f32 → u8; 4× memory reduction with < 2% recall loss. (~total 75 min across 3 phases)
  - 🔧 **Why this matters**: SQ is the simplest quantization — 4× memory reduction with typically < 2% recall loss on normalized embeddings. Foundational for tomorrow's PQ. Downstream: W104 segment manager picks SQ as default; W103 persistence stores SQ-encoded vectors on disk.

  #### Phase 1 — Requirements + design (~20 min)

  - **Requirements** (write in `notes/102mon_sq_design.md`): (R1) train BEFORE encode; (R2) min/max stored per-quantizer (each segment may have own); (R3) asymmetric distance (query unquantized, db quantized) — no recall loss vs symmetric; (R4) clamp inputs to [min, max] for outliers; (R5) recall@10 with SQ on 100k 128-d ≥ 0.93; (R6) storage exactly N*D bytes (4× compression); (R7) SQ-encoded HNSW search ≤ 1.2× slower than unquantized.

  - **Design questions**: (D1) Asymmetric vs symmetric distance: asymmetric (query f32, db u8) decodes db on-the-fly during inner loop; symmetric (both u8) is faster but loses ~5% recall. Pick asymmetric default. (D2) Global vs per-dim min/max: global simpler; per-dim wastes precision when dim ranges differ. v0.5 = global; document. (D3) **Pre-mortem**: training set has one outlier vector with norm 100× others; min/max range stretches; normal values map to a tiny region of [0,255]; precision lost. What guard catches? (Percentile-based min/max: 0.1%/99.9% percentile instead of true min/max.)

  #### Phase 2 — Failing tests

  - [ ] `test_sq_recall_at_10_above_093` — 100k 128-d random, SQ-encoded; vs unquantized ground truth.
  - [ ] `test_sq_memory_exactly_4x_compression` — assert encoded storage = N*D bytes (vs N*D*4 for f32).
  - [ ] `bench_sq_hnsw_search_under_1_2x_unquantized` — SQ+HNSW vs HNSW alone; ratio ≤ 1.2×.
  - [ ] `test_outlier_resilience_with_percentile_training` — corpus with 1% outliers; percentile-trained SQ recall ≥ 0.90.
  - [ ] `test_encode_decode_roundtrip_rmse` — encode then decode; RMSE ≤ scale/2.
  - [ ] `test_asymmetric_distance_matches_full_precision_within_threshold` — asymmetric distance vs f32 distance; ratio within 5%.

  #### Phase 3 — Failure cards

  - **When `test_outlier_resilience_with_percentile_training` reports recall 0.78**: Symptom: one outlier vector with norm 50× others; SQ.min = -50, SQ.max = +50; normal values [-1, +1] mapped to [127, 130] — only 4 of 256 codes used. Why: naive min/max takes true extremes. Fix: percentile-based — sort all training values; min = 0.1 percentile; max = 99.9 percentile. Clip outliers at encode time. Recall recovers to 0.93. Muscle: any quantization training is vulnerable to outliers; percentile-based is the standard fix. Reapplies at: W102 Tue PQ k-means init, every histogram-based encoder.

  - **When `test_asymmetric_distance_matches_full_precision_within_threshold` shows 30% deviation**: Symptom: SQ-decoded distances diverge wildly from f32 distances. Why: encoded query as well as db (symmetric) — double-quantization error. Fix: query stays f32; only db is u8. Distance computation: `(q[i] - (min + db[i]*scale))²` decodes db on-the-fly. Muscle: asymmetric is the default for ALL quantization (SQ, PQ, OPQ). Reapplies at: W102 Tue PQ ADC.

  - **5-year failure mode**: when normalized embeddings become universal (cosine-only), SQ's global min/max wastes precision. Migration: per-dim quantizer (per-axis min/max, 4× more state). Trigger: recall loss > 5%.

  - **Reference material**: faiss `IndexScalarQuantizer.cpp`; Qdrant `lib/segment/src/vector_storage/quantized/`; Guo et al. "Quantization for Nearest Neighbor and Maximum Inner Product Search".

**Tuesday — vector-db: Product Quantization (PQ)**

- [ ] **Build**: `crates/vector-db/src/quantize/pq.rs` — `ProductQuantizer { m, ksub, dsub, codebook }`; train via k-means per subspace; ADC via LUT. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: PQ is THE **interview-load-bearing** quantization. 16× compression with reasonable recall. Asymmetric Distance Computation (ADC) trick — precompute LUT per query, sum from codes — is the magic that makes it fast. Downstream: W104 segment manager (PQ default for cold segments), W103 persistence (serializes codebook + codes).

  #### Phase 1 — Requirements + design (~25 min)

  - **Requirements** (write in `notes/102tue_pq_design.md`): (R1) D % m == 0; (R2) codebook = m × ksub × dsub × 4B (typical 128 KB for 128-d/m=8/ksub=256); (R3) encoded vec = m bytes (16× compression for 128-d → 8 bytes); (R4) ADC: LUT built ONCE per query, reused across all candidate distance computes; (R5) recall@10 ≥ 0.90 at PQ(m=8, ksub=256) on 128-d; (R6) PQ-HNSW search ≤ unquantized HNSW latency (LUT speedup); (R7) trained quantizer serializable; (R8) k-means uses ++init + multi-restart.

  - **Design questions**: (D1) Why does ADC make PQ fast? Naive: each distance compute decodes db code, computes f32 distance — ~128 ops/distance. ADC: precompute query × codebook → LUT[m][ksub] f32 matrix (one-time cost); then per-distance is `sum_{i=0..m} LUT[i][codes[i]]` — m table lookups, m adds — ~16 ops vs 128. (D2) LUT size: m × ksub × 4B = 8 × 256 × 4 = 8 KB at m=8, ksub=256. Fits in L1 (typical 32 KB). Why not larger ksub? (LUT spills L1.) (D3) **Pre-mortem**: random k-means init produces poor centroids; quantization error large; recall tanks to 0.65. What guard? (k-means++ init: probabilistic seeding biased to far-from-existing; 3-10 restarts; pick best by WCSS.)

  #### Phase 2 — Failing tests

  - [ ] `test_pq_recall_at_10_above_090` — 100k SIFT-1M subset; PQ(m=8, ksub=256); recall@10 ≥ 0.90.
  - [ ] `test_pq_storage_8_bytes_per_vec` — encoded size = m bytes (16× for 128-d).
  - [ ] `bench_pq_hnsw_search_no_slower_than_unquantized` — PQ+HNSW vs HNSW; PQ ≤ 1.0× latency.
  - [ ] `test_pq_lut_in_l1_cache` — LUT size = m * ksub * 4 ≤ 16 KB; assert.
  - [ ] `test_kmeans_plusplus_init_improves_recall` — random init vs ++init; ++init recall ≥ 0.05 better.
  - [ ] `test_pq_codebook_serializable` — write codebook to disk; read back; encode result identical.
  - [ ] `test_pq_d_must_divide_m` — `D=129, m=8` returns Err or panics at construction.

  #### Phase 3 — Failure cards

  - **When `test_kmeans_plusplus_init_improves_recall` shows random init at 0.85 and ++init at 0.85 (no improvement)**: Symptom: ++init doesn't help. Why: ++init implemented but only 1 restart; bad initial seed still possible. Fix: 5-10 restarts; pick best by within-cluster sum of squares (WCSS). Add metric `kmeans_final_wcss` for ops visibility. Muscle: probabilistic algorithms need multi-restart + objective selection; single-run is luck-based. Reapplies at: every k-means consumer (W102 SQ percentile training, OPQ rotation).

  - **When `bench_pq_hnsw_search_no_slower_than_unquantized` reports PQ 2× slower**: Symptom: ADC supposed to speed up but bench shows slowdown. Why: LUT rebuilt PER CANDIDATE distance compute (forgot to hoist out of inner loop). Fix: `let lut = quantizer.build_lut(query); for c in candidates { d = quantizer.distance_adc(&lut, c) }` — LUT built ONCE before candidate loop. Muscle: ADC's whole point is LUT amortization; hoisting is non-negotiable. Reapplies at: every quantization with LUT (OPQ, RVQ).

  - **When `test_pq_recall_at_10_above_090` reports 0.78**: Symptom: well under target. Why: subspace correlation — if dims are correlated (typical for non-rotated embeddings), naive PQ wastes codes on redundancy. Fix: OPQ (Ge 2014) rotates the space first to decorrelate; PCA on training set then apply rotation before PQ. v0.5 mention OPQ as known-improvement; v1.0 ships. Alternative for v0.5: better k-means convergence (more iters).

  - **5-year failure mode**: when GPU+matryoshka embeddings make 1-bit quantization viable, PQ becomes obsolete. Migration: BQ (binary quantization) + Hamming distance with SIMD `popcnt`. Trigger: BQ recall ≥ PQ recall at 2× compression.

  - **Reference material**: Jégou, Douze, Schmid 2011 "Product Quantization for Nearest Neighbor Search" (foundational); faiss `IndexPQ.cpp` + `ProductQuantizer.cpp`; Ge et al. 2014 "Optimized Product Quantization" (OPQ, the rotation trick); Qdrant `lib/quantization/src/encoded_vectors_pq.rs`.
- [ ] Test: 128-d → 8 sub-vectors × 8-d, recall@10 ≥ 0.90 at 16× memory reduction. (~30 min)

**Wednesday — vector-db: filtered search via bloom-bitmap**

- [ ] **Build**: `crates/vector-db/src/filter.rs` — `FilterMask` is bitmap/bloom; `Strategy::{Prefilter, Postfilter, Adaptive}` picked per query by selectivity; inline-filter traverses graph through non-matching, admits only matching. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: real vector workloads ALWAYS filter ("similar products in price $X-$Y", "docs by user Z"). Naive search-then-filter blows up tail (search returns 1000, filter keeps 5); naive filter-then-search defeats HNSW. The bitmap + HNSW inline-filter integration is THE interview-load-bearing answer. Downstream: W102 Thu payload storage feeds filter; W104 segment manager merges filters across segments; inline is production default.

  #### Phase 1 — Requirements + design (~25 min)

  - **Requirements** (write in `notes/102wed_filter_design.md`): (R1) Filter trait with `matches(id) -> bool` + `estimated_selectivity() -> f32`; (R2) BitmapFilter (exact) + BloomFilter (over-estimating); (R3) Strategy::pick — Prefilter for sel < 0.01, Postfilter for sel > 0.5, Adaptive between; (R4) Inline filter MUST traverse THROUGH non-matching nodes (else connectivity lost) but only ADMIT matching to result set; (R5) recall@10 ≥ 0.90 across all 3 strategies at sel ∈ {0.01, 0.1, 0.5}; (R6) latency P99 ≤ 5 ms at any selectivity on 1M corpus; (R7) Strategy::pick chooses optimal within 20% in 90% of cases; (R8) Bloom false-positives caught by final exact check.

  - **Design questions**: (D1) Why three strategies? Different selectivity regimes have different optimal paths. Prefilter: enumerate matching IDs, brute-force (efficient when matches small). Postfilter: search wider (expanded_ef), drop non-matching. Adaptive: search with inline filter, traverse through non-matching but admit only matching. (D2) Inline filter graph traversal: critical insight — non-matching nodes are NOT result candidates but ARE traversal hops; their edges lead to matching nodes. Disconnecting traversal at non-matching breaks graph navigability. (D3) **Pre-mortem**: inline filter excludes non-matching from BOTH results AND traversal; matching nodes connected via non-matching become unreachable; recall tanks. What test catches? (Sel 0.5 inline-filter; if recall < unfiltered baseline, traversal is broken.)

  #### Phase 2 — Failing tests

  - [ ] `test_prefilter_recall_at_low_selectivity` — sel=0.001; Prefilter; recall@10 ≥ 0.90.
  - [ ] `test_postfilter_recall_at_high_selectivity` — sel=0.5; Postfilter (expanded ef); recall@10 ≥ 0.90.
  - [ ] `test_adaptive_inline_recall_at_medium` — sel=0.05; Adaptive; recall ≥ 0.90.
  - [ ] `test_strategy_pick_optimal_in_90pct` — 100 random query/filter pairs; assert chosen strategy within 20% of best.
  - [ ] `test_inline_filter_traverses_through_non_matching` — graph where matching nodes only reachable via non-matching; recall ≥ baseline (no filter).
  - [ ] `bench_p99_under_5ms_any_selectivity_1m_corpus` — sel ∈ {0.001, 0.1, 0.5, 0.9}; P99 < 5 ms.
  - [ ] `test_bloom_false_positives_caught_by_exact_check` — BloomFilter over-reports; final exact filter on returned IDs; no false positives in output.

  #### Phase 3 — Failure cards

  - **When `test_inline_filter_traverses_through_non_matching` reports recall 0.30**: Symptom: inline filter destroys recall; matching nodes unreachable. Why: inline filter both excludes non-matching from results AND prunes their edges from traversal; graph fragments. Fix: in search_layer modified for filter, EVERY discovered neighbor is added to visited + traversal; ONLY admission to results-heap is gated by filter.matches. Code: `if visited.insert(n) { candidates.push(...); if filter.matches(n) { results.push(...) } }`. Muscle: filter is on admission, not on traversal; graph connectivity is independent of which nodes are "interesting". Reapplies at: every graph-search-with-predicate (W104 filtered search across segments).

  - **When `test_strategy_pick_optimal_in_90pct` reports 60% accuracy**: Symptom: pick chose Postfilter at sel=0.005 (Prefilter was 100× faster). Why: thresholds for sel boundaries off. Fix: empirically calibrate per workload. Default: sel < 1/sqrt(N) → Prefilter; sel > 0.5 → Postfilter; else Adaptive. Make thresholds configurable for ops tuning. Muscle: heuristic strategies need empirical calibration + ops knobs; default values are a starting point, not a destination.

  - **When `bench_p99_under_5ms_any_selectivity_1m_corpus` reports 50 ms at sel=0.001**: Symptom: P99 100× over budget at very low sel. Why: Postfilter strategy chosen by mistake; expanded_ef = ef/sel = 64/0.001 = 64,000; search visits ~64k candidates. Fix: Strategy::pick selects Prefilter at sel < 0.01; enumerate matching IDs (small set), brute-force. Linear time in matching count, not corpus size.

  - **5-year failure mode**: when filters become compositional (AND of 10 predicates), per-predicate selectivity estimation breaks (correlation between predicates). Migration: query-planner that estimates joint selectivity via co-occurrence stats. Trigger: filter complexity > 3 predicates.

  - **Reference material**: Qdrant `lib/segment/src/index/struct_payload_index.rs`; Pinecone "Filtered Vector Search" blog; Weaviate inverted-index over payloads doc.

**Thursday — vector-db: payload storage via mini-db**

- [ ] **Build**: `crates/vector-db/src/payload.rs` — payload (per-vector JSON metadata) stored in embedded `mini_db::MiniDb`; per-field bitmap indices for filter acceleration. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: **THIS is the inheritance principle in action across crates.** vector-db doesn't need a KV store — mini-db is one. Pulling mini-db as a dep is the simplest proof that the inheritance principle scales across product crates, not just within one. Resume-load-bearing. Downstream: filter.rs consumes BitmapFilter from here; W104 segment manager has one PayloadStore per segment; HNSW search_filtered queries this.

  #### Phase 1 — Requirements + design (~25 min)

  - **Requirements** (write in `notes/102thu_payload_design.md`): (R1) `PayloadStore { db: Arc<MiniDb>, indices: RwLock<HashMap<String, FieldIndex>> }`; (R2) put writes payload to mini-db + maintains per-field bitmap indices; (R3) get returns deserialized JSON; (R4) filter_by_keyword + filter_by_range return BitmapFilter (W102 Wed); (R5) filter_by_keyword P99 ≤ 100 µs on 1M payloads; (R6) index memory ≤ 5% of payload size; (R7) indices rebuildable from payload on restart (no separate WAL); (R8) vector-db has ZERO KV code (cross-crate inheritance proof).

  - **Design questions**: (D1) Why bitmap indices? Each field-value maps to set of NodeIds; intersection = AND of filters; faster than full-table scan. (D2) Roaring bitmaps vs naive: Roaring compresses sparse and dense bitmaps differently; ~5% overhead vs ~30% for naive. (D3) **Pre-mortem**: restart loses in-memory indices; vector-db hangs scanning all of mini-db to rebuild. What guard? (Lazy index rebuild on first filter use OR persist indices to mini-db under separate key namespace.)

  #### Phase 2 — Failing tests

  - [ ] `test_put_get_roundtrip` — 1k payloads put + get returns equal JSON.
  - [ ] `bench_filter_by_keyword_p99_under_100us_1m` — 1M payloads, filter by keyword; P99 < 100 µs.
  - [ ] `test_filter_by_range_returns_correct_ids` — payloads with prices 0-1000; filter [200, 500]; assert IDs match.
  - [ ] `test_index_memory_under_5pct_payload` — index size / payload size ≤ 0.05.
  - [ ] `test_restart_rebuilds_indices` — put 1k payloads, drop, reopen; filter returns correct results.
  - [ ] `test_zero_kv_code_in_vector_db` — grep vector-db for `Wal::`, `LsmTree::`, `Memtable::`; assert 0 hits (all KV goes through mini-db API).
  - [ ] `test_schema_mismatch_logged_not_crashed` — put with price=int then put with price=str; second put doesn't panic; log warning.

  #### Phase 3 — Failure cards

  - **When `test_restart_rebuilds_indices` returns empty filter results**: Symptom: 1k payloads written; drop; reopen; filter_by_keyword returns 0 hits. Why: indices are in-memory; restart loses them; no rebuild on open(). Fix: at open(), scan mini-db (`db.scan(.., ..)`), deserialize each payload, rebuild indices. For 1M payloads ~5 s scan time; acceptable for v0.5. v1.0 persists indices to mini-db under separate namespace `__idx__:`.

  - **When `test_zero_kv_code_in_vector_db` finds `Wal::sync_current` in vector-db**: Symptom: grep hits `Wal::sync_current` in vector-db/src/payload.rs. Why: developer reached into mini-db's internals instead of using public API. Fix: refactor to use `Db::put` (which handles WAL internally). Add CI check: cargo deny on `wal::*`, `lsm_core::*` from vector-db. Muscle: cross-crate inheritance requires API discipline; reaching into internals breaks the boundary. Reapplies at: every cross-crate dep.

  - **When `bench_filter_by_keyword_p99_under_100us_1m` reports 5 ms**: Symptom: 50× over budget. Why: filter clones the entire RoaringBitmap on each call (`bm.clone()`); 1M bitmap ~ 200 KB clone ~ 1 µs per call but lock contention adds 5 ms tail. Fix: return Arc<RoaringBitmap> or borrow with lifetime-tied filter. Re-bench; expect P99 ~50 µs.

  - **5-year failure mode**: when payloads grow to GB-scale per vector (multimodal embeddings + full text), payload-in-mini-db becomes expensive. Migration: payloads stored separately (object store / blob); mini-db holds only NodeId → BlobRef. Trigger: avg payload > 100 KB.
