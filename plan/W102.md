  - *Mental model*: a cascade is a **deterministic fixed-point iteration on the VSR log**. Each round: read the margin signal (W99) under the current mark, rank the under-maintenance accounts, liquidate the worst (reduce-only → book), observe the new mark, repeat. It converges (no eligible accounts), is halted (breaker), or is bounded (depth cap). It is the *same* class of VSR-derived state as the order book and the fund: every replica applying the same committed `MarkTickObserved` reaches the byte-identical `CascadeReport`. The cascade is not "an event loop" — it is a pure function `(book, marginsignal, mark, breaker) → CascadeReport` that the VSR log drives in lockstep.
  - *Contract* (signature only, NEVER the body):
    ```rust
    pub struct CascadeEngine {
        // reuses W100 partial-liq submitter, W99 margin signal reader, W101 fund + breaker; no new storage
    }
    pub struct CascadeReport {
        rounds: u8,                              // ≤ MAX_CASCADE_DEPTH
        liquidated: [LiqStep; MAX_ELIGIBLE],     // fixed-cap, in execution order (worst-margin-first)
        len: u16,
        fund_drawn: i128,                        // micro-USD drawn via the W101 waterfall
        outcome: CascadeOutcome,
    }
    #[derive(Clone, Copy)] pub struct LiqStep { account: AccountId, margin_ratio: i64, notional: i128 }
    #[derive(Clone, Copy)] pub enum CascadeOutcome { Converged, BreakerHalted, BoundReached, Tripwire { shortfall: i128 } }
    impl CascadeEngine {
        pub fn run(&mut self, mark: Price, breaker: &mut CircuitBreaker) -> CascadeReport; // one committed op
    }
    ```
  - *Back-of-envelope* (bar (c) — name the cost): at 100k accounts and ~10 mark ticks/s (§4A capacity), the common case is *zero* eligible accounts per tick (the cascade loop exits round 0). The stress case is a clustered-leverage tick where a few hundred accounts go under at once: ranking ~500 eligibles is a partial-sort `O(k log k)` ≈ ~5k ops (~5µs); each round liquidates the worst handful, re-reads marks incrementally (W99 delta, ~1µs/account), and re-ranks the now-smaller set. The **cliff is determinism, not latency**: a `HashSet` scan costs the same ns but liquidates in seed-random order → different fund draw → split state hash. The **second cliff is boundedness**: a self-amplifying scenario with no depth cap is an unbounded apply-path loop that *stalls VSR commit for every other op* (the whole venue freezes), which is far worse than a slow cascade. Const-bound `MAX_CASCADE_DEPTH = 64` + breaker = the apply path always returns.
  - **The problem this primitive solves**: clustered leverage + a thin book means one liquidation's market-impact can push the mark into the next account's liquidation, and so on — the mechanism behind every real exchange blow-up. The engine must (a) detect the chain deterministically, (b) order it fairly by rule, (c) bound it so the apply path always returns, and (d) absorb the resulting shortfalls through W101's waterfall without ever hitting the tripwire at the declared rate. Two failure categories: **non-determinism** (HashMap iteration / f64 mark math → replicas disagree on order and fund draw) and **unboundedness** (no depth cap / wall-clock bound → apply-path hang or non-reproducible termination). The fix: sorted total-order ranking + integer-only mark/margin math + a const depth bound + the W101 breaker as the in-cascade halt.

    - R1. `CascadeEngine::run` is **VSR-log-derived**: replaying the committed `MarkTickObserved` + the book + the margin signal reproduces the `CascadeReport` byte-identically; the report (or its hash) is in `state_hash()`.
    - R2. **Eligible-set ranking is a total order**: worst-margin-first, ties by `AccountId` ascending. Built via a sorted `Vec`/partial-sort over an explicit slice — **never** HashMap/HashSet iteration. (Determinism gate.)
    - R3. **Integer-only**: mark, margin ratio, notional, fund draw all integer (ticks / bps / micro-USD). No `f64` anywhere (clippy `disallowed-types = ["f64","f32"]` + CI grep).
    - R4. **Bounded**: `rounds <= MAX_CASCADE_DEPTH` (const 64). On bound, `outcome = BoundReached`, the apply path returns cleanly. **No wall-clock / no `Instant` in the loop** (that is non-determinism).
    - R5. **Breaker integration (W101)**: each round consults the circuit breaker; if a per-tick price-band / liquidation-cap is breached, the round halts with `outcome = BreakerHalted` (deterministic, reproducible).
    - R6. **Waterfall integration (W101)**: each liquidation's below-bankruptcy shortfall is absorbed by `InsuranceFund::draw` in waterfall order (position-margin → fund); `fund_drawn` accumulates the integer total.

The fix: const depth bound + breaker; `BoundReached`/`BreakerHalted` always returns.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `cascade_is_bounded` hangs (test times out) instead of returning `BoundReached`:**
    - Symptom: the test never finishes; the self-amplifying scenario loops; CI kills it on timeout.
    - Why: the round loop has a `while still_eligible {}` with no depth counter; a scenario where each liquidation creates exactly one new eligible account has no fixed point.
