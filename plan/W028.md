**Monday — B-tree node design**

- [ ] Design leaf vs internal node layout. (~30 min)
  - **Why**: Page layout dictates everything downstream — split logic, cursor invariants, mmap alignment. A poor layout wastes 30% space (and 30% IOPS) on every read. The LMDB/MDBX layout (slot directory + grow-down records) is canonical because it's variable-length-key-friendly without rebalancing tombstones inside pages.
  - **Read first**: libmdbx `src/page.c::page_split`; CMU 15-445 lecture 6 (B+tree internals); LMDB paper §3.1 (the "slotted page").
  - **Design**:
    ```
    Page (4 KiB):
    +-------------------------------------------------+
    | header(64 B): { flags, num_slots, lower, upper, |
    |                 right_sibling_pgno, pgno }      |
    +-------------------------------------------------+
    | slot_offsets[num_slots]: [u16; num_slots]       | <- grows down toward middle
    |   (each slot points to a record)                |
    |                                                 |
    |               FREE SPACE                        |
    |                                                 |
    | records: ... [last_record] [second_last] ...    | <- grows up toward middle
    +-------------------------------------------------+
    
    Leaf record:    [u16 key_len][key][u16 val_len][val]
    Branch record:  [u16 key_len][key][u32 child_pgno]
    
    Flags: 0x01 LEAF, 0x02 BRANCH, 0x04 OVERFLOW (record spans pages), 0x08 META
    ```
    **Invariants**:
    - `lower <= upper` always; `free = upper - lower`.
    - num_slots == count of slot_offsets entries.
    - Records are in slot order (binary-searchable by key via slots[i].key).
    - Page is min-half-full unless it's the root (post-split → split-the-root produces a 2-key branch).
    - Branch nodes have `num_slots + 1` children: the leftmost child is in the header's `left_pgno` field, slots' child_pgno are right children of their key.
    - Right-sibling pointer for leaves (NOT branches) enables cheap range scans.
  - **Build steps**:
    1. (~10 min) Draw the layout on paper. Verify with byte offsets.
    2. (~10 min) Compute fill-factor for sample workload (avg key 32 bytes, val 200 bytes): fits ~16 leaf records per 4 KiB page.
    3. (~10 min) Document the layout in `crates/storage-trie/src/btree/page.rs` with byte-offset diagram in module doc.
  - **Pitfalls**:
    - *Slot offset overflow*: u16 caps page size at 64 KiB. **Symptom**: silent corruption on 128 KiB pages. **Fix**: enforce 4-16 KiB at config; assert at page open.
    - *Right-sibling for branches*: tempting to add for general traversal, but creates dual-pointer invariants. **Symptom**: split logic doubles in complexity. **Fix**: leaves-only sibling pointer; branches walked via parent backtracking.
    - *Overflow pages*: keys > page_size / 4 must spill to a chain of overflow pages. **Symptom**: panic on large keys. **Fix**: detect at insert; allocate overflow chain; slot points to the head.
    - *Endianness*: u16/u32 in headers must be a fixed endian for cross-platform DB files. **Symptom**: DB unportable. **Fix**: little-endian via `to_le_bytes` everywhere; document.
  - **Test scenarios**: round-trip page encode/decode for fixed fixtures; assert free-space calculation; overflow-page chain for a 5 KiB key.
  - **Acceptance**: layout matches LMDB/MDBX within a factor of 2× space efficiency.
  - **Downstream**: Tuesday's insert, Wednesday's get, Thursday's delete all consume this layout; W31 MPT integration; W95 mini-db replays this design.

**Tuesday — B-tree insert**

- [ ] Insert with node splitting. Unit tests. (~30 min)
  - **Why**: Insertion is the only operation that can grow tree height. Split logic is the most-tested code in any B+tree because off-by-one errors here corrupt the entire tree silently. The "split at median, propagate separator to parent" algorithm is canonical; getting the separator-key choice right is THE invariant.
  - **Read first**: libmdbx `src/page.c::page_split`; CMU 15-445 B+tree split walkthrough; Cormen et al. CLRS §18.2 (B-tree insert).
  - **Design**:
    ```rust
    pub fn insert(&mut self, key: &[u8], val: &[u8]) -> Result<(), InsertError> {
        let path = self.search_to_leaf(key)?;   // stack of (page_id, slot_idx) from root to leaf
        let leaf = path.last().unwrap();
        let leaf_page = self.pool.fetch_exclusive(leaf.page_id)?;
        if leaf_page.has_space_for(key, val) {
            leaf_page.insert_at(leaf.slot_idx, key, val);
            return Ok(());
        }
        // No space → split.
        let (left, right, separator) = leaf_page.split_at_median();
        self.pool.write_page(left)?;
        let new_right_pgno = self.pool.allocate_page()?;
        self.pool.write_page_at(new_right_pgno, right)?;
        // Now insert (separator, new_right_pgno) into parent.
        self.insert_in_parent(path, separator, new_right_pgno)?;
        Ok(())
    }
    ```
    **Invariants**:
    - After insert, every page is between min-half-full and max-capacity.
    - Tree is height-balanced: all leaves at same depth.
    - Keys in any leaf are < first key in right sibling.
    - Branch separator keys equal the leftmost key of their right subtree.
  - **Build steps**:
    1. (~10 min) `search_to_leaf` — walk root→leaf using binary search per page; record path.
    2. (~10 min) `insert_at` — shift slot offsets, append record; update lower/upper.
    3. (~10 min) `split_at_median` — choose median index, copy left half + right half to two new pages, return separator (median key).
    4. (~5 min) `insert_in_parent` — recursive: insert (separator, new_pgno) into parent; if parent splits, recurse upward.
    5. (~5 min) Root-split: if root splits, allocate new root with single-key + two children, bump tree height.
    6. (~10 min) Unit tests: insert in empty tree; insert that triggers leaf split; insert that triggers cascade-to-root.
  - **Pitfalls**:
    - *Off-by-one median*: choosing `num_slots / 2` vs `(num_slots + 1) / 2` shifts the separator. **Symptom**: occasionally a leaf has one key, its sibling has N-1. **Fix**: median = byte-balanced split point (the index where cumulative record size first exceeds page/2).
    - *Separator key copying*: separator is a key in the right page; if you fail to keep a copy in the parent, parent's invariant breaks. **Symptom**: lookups skip subtrees. **Fix**: separator is *copied* into the parent's record slot, not borrowed.
    - *Path invalidation on split*: after split, the path stack's page_ids may no longer point to the right page. **Symptom**: next op operates on stale page. **Fix**: rebuild path or use the returned (left, right) from split to patch the path.
    - *Concurrent reads during split*: a reader holding a cursor sees the page split out from under them. **Symptom**: reader misses records or sees ghost records. **Fix**: split takes exclusive latch on parent + both children; readers held shared latch on path frames; standard "latch crabbing" protocol.
    - *Overflow page during split*: if a record itself is too big to fit in one page, allocate overflow chain BEFORE split — otherwise split logic underestimates record size. **Symptom**: split picks wrong median. **Fix**: spillover detection at record-write time, separate from split.
  - **Test scenarios**:
    - Insert 100k random keys into empty tree → final structure balanced (height ≤ ceil(log_{2k}(N))).
    - Insert keys in sorted order: tree degenerates to bushy right-leaning shape (legal but worst case for splits).
    - Insert keys in reverse order: same.
    - Duplicate key insert: spec'd behavior (reject or replace) — choose REPLACE for MVCC-like semantics.
    - Concurrent inserts 16 threads: final tree has all N records, no corruption.
  - **Acceptance**:
    - 1M random inserts produce a tree where every page is within (min_fill, max_fill).
    - 1M inserts at sustained 200k ops/sec single-threaded.
  - **Downstream**: Wednesday's get and Thursday's delete; W31 MPT puts trie nodes into this B+tree.

**Wednesday — B-tree get**

- [ ] Lookup by key. Range iteration. (~30 min)
  - **Why**: Get is the cheap path — pure read, no allocation, no logging. But cursor-based range iteration must remain valid across writes (the cursor invalidation problem). reth-db's cursor abstraction is built on MDBX's; mimicking it gives you the same ergonomics + the same pitfalls to manage.
  - **Read first**: libmdbx `src/cursor.c` (the cursor state machine); reth `crates/storage/libmdbx-rs/src/cursor.rs` for the Rust wrapper.
  - **Design**:
    ```rust
    pub struct Cursor<'tx> {
        tree: &'tx BTree,
        path: SmallVec<[Frame; 16]>,         // path from root to current leaf
        leaf_slot_idx: u16,                  // current position within leaf
        snapshot_lsn: Lsn,                   // MVCC snapshot anchor
    }
    impl<'tx> Cursor<'tx> {
        pub fn seek(&mut self, key: &[u8]) -> Option<&[u8]>;
        pub fn seek_first(&mut self) -> Option<(&[u8], &[u8])>;
        pub fn next(&mut self) -> Option<(&[u8], &[u8])>;
        pub fn prev(&mut self) -> Option<(&[u8], &[u8])>;
    }
    pub struct Frame { page_id: PageId, slot_idx: u16, slot_count: u16 }
    ```
    **Invariants**:
    - Cursor pinned to an MVCC snapshot: writes after `snapshot_lsn` are NOT visible.
    - On `next()`, advance slot_idx; if past end of leaf, pop frame and advance parent's slot.
    - Range scan walks via right-sibling pointer on leaves (MDBX-style) OR parent-backtrack (LMDB-style).
    - Cursor never holds page latches across `await` points.
  - **Build steps**:
    1. (~10 min) `seek(key)` — search_to_leaf, then binary search within leaf, record slot_idx.
    2. (~10 min) `next` — increment slot_idx; if overflow, backtrack to parent and advance.
    3. (~5 min) `prev` — analogous.
    4. (~5 min) Tests: empty cursor, full scan, prefix range.
  - **Pitfalls**:
    - *Cursor invalidation on split*: cursor's `path` references page_ids that may have split; cursor sees stale slot. **Symptom**: missed or duplicated records during scan-while-writing. **Fix**: cursor takes a snapshot LSN; reads route through MVCC; writes don't mutate visible pages.
    - *Lifetime of slice references*: `&[u8]` borrowed from page is invalidated on next fetch. **Symptom**: borrow checker rejects long-lived references; if forced via unsafe, dangling pointer. **Fix**: cursor's API returns Bytes (Arc'd page reference) — caller can hold across `await`.
    - *Right-sibling staleness*: if leaf is split mid-scan, right-sibling pointer may point to a still-correct-but-not-the-one-you-expected page. **Symptom**: skip a small range. **Fix**: snapshot the right-sibling pointer at cursor-pin time; or use parent-backtrack which avoids sibling pointers entirely.
    - *seek to non-existent key*: spec: position cursor at smallest key >= target. **Symptom**: caller assumes "found exact" when only "found ≥". **Fix**: separate `seek_exact` and `seek_gte`.
  - **Test scenarios**:
    - Insert 100k records, full scan returns all in sorted order.
    - Concurrent: writer inserting keys during reader scan; reader's snapshot keeps it stable.
    - Seek to non-existent key returns next-larger.
    - Seek past end returns None.
  - **Acceptance**:
    - Cursor throughput: ≥ 5 M next() per second on warm cache.
    - Inheritance ratio ≥ 0.85 vs reth-db cursor.
  - **Downstream**: W20's TrieWalker is a thin specialization on top; W22 staged-sync stages scan via cursor; W92 block-stm needs snapshot-consistent read iteration.

**Thursday — B-tree delete**

- [ ] Delete with node merging. (~30 min)
  - **Why**: Delete is the asymmetric twin of insert — pages can shrink below min-fill and must merge with a sibling (or borrow from a sibling) to maintain B+tree invariants. Many real DBs (LMDB included) PUNT on merge — they accept under-filled pages and rely on offline compaction. You're learning to do it properly because it's required for any system with steady-state delete pressure (matching-engine cancellations, LSM compaction).
  - **Read first**: CLRS §18.3 (B-tree delete); libmdbx `src/page.c::page_merge`; "B+tree deletion" by Jannink (1995).
  - **Design**:
    ```rust
    pub fn delete(&mut self, key: &[u8]) -> Result<bool, Error> {
        let path = self.search_to_leaf(key)?;
        let leaf = path.last().unwrap();
        let leaf_page = self.pool.fetch_exclusive(leaf.page_id)?;
        let removed = leaf_page.remove_slot(leaf.slot_idx);
        if !removed { return Ok(false); }
        if leaf_page.is_under_min_fill() && path.len() > 1 {
            self.rebalance_at(path)?;
        }
        Ok(true)
    }
    fn rebalance_at(&mut self, mut path: Path) -> Result<(), Error> {
        loop {
            let (current, parent_frame) = (path.pop().unwrap(), path.last().unwrap());
            // 1. Try borrow from left sibling.
            // 2. Else try borrow from right sibling.
            // 3. Else merge with one sibling; separator key in parent is removed.
            // 4. If parent now under-fill, recurse up. If parent is root with 0 keys, drop root, child becomes new root.
        }
    }
    ```
    **Invariants** (post-delete):
    - Every non-root page is at least min-half-full.
    - Tree remains height-balanced.
    - If root has zero keys, root is replaced by its only child (tree height shrinks by 1).
    - Separator keys in branches still hold the invariant: separator equals leftmost-key of right subtree.
  - **Build steps**:
    1. (~5 min) `remove_slot(idx)` — shift slot_offsets, compact record space lazily (or not at all if we tolerate fragmentation).
    2. (~10 min) `borrow_from_sibling` — move 1 record from sibling to current; update parent's separator.
    3. (~10 min) `merge_with_sibling` — concatenate records into one page, free the sibling's pgno, remove separator from parent.
    4. (~5 min) Recursive call upward if parent becomes under-fill.
    5. (~5 min) Root-collapse on root reaching zero keys.
    6. (~5 min) Tests: delete that doesn't rebalance, that borrows, that merges, that collapses root.
  - **Pitfalls**:
    - *Choosing borrow vs merge*: borrowing is cheaper (no page free) but only works if sibling has spare. **Symptom**: thrashing borrow/return on alternating delete/insert workloads. **Fix**: prefer merge when sibling is also near min-fill (saves a page); prefer borrow when sibling is comfortably full.
    - *Separator key update after borrow*: when borrowing left, new separator is the moved key. When borrowing right, new separator is the next key in the right sibling. Off-by-one fails. **Symptom**: lookups go to wrong subtree. **Fix**: explicit invariant test post-borrow.
    - *Right-sibling pointer maintenance*: merge destroys a page; left sibling's right-pointer must update. **Symptom**: cursor scan crashes mid-range. **Fix**: explicit `left.right_sibling = right.right_sibling` step in merge.
    - *Concurrent readers during merge*: a reader pinned to the merged-away page's pgno crashes. **Symptom**: SIGSEGV on cursor. **Fix**: MVCC snapshot prevents readers from seeing freshly-freed pages; the page is queued for reclamation only after all snapshots that touched it expire (W33 epoch-gc handles this).
    - *Page free races*: freeing a page while another tx wants to allocate it. **Symptom**: allocator hands out a page still referenced. **Fix**: free-list operations are themselves logged in wal; only safe to reuse after checkpoint.
  - **Test scenarios**:
    - Insert 10k, delete all in random order: tree ends empty (or single root page).
    - Insert 10k, delete every other key: tree balanced, no under-fill pages.
    - Delete from a leaf that borrows: assert parent's separator updated, sibling lost one key.
    - Delete that cascades to root collapse: tree height drops by 1.
    - Concurrent delete + scan: scanner snapshot stable.
  - **Acceptance**:
    - Random delete/insert workload of 1M ops keeps tree invariants.
    - Inheritance ratio ≥ 0.8 vs CLRS algorithm (deviating only for MVCC integration).
  - **Downstream**: W31 MPT requires delete to garbage-collect dead trie nodes; W74 matching-engine cancellations exercise this heavily.
