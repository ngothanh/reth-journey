**Monday — B-tree node layout (slotted page)**

- [ ] **Build**: `crates/storage-trie/src/btree/page.rs` — slotted-page encode/decode + free-space accounting + overflow detection. (~total 210 min across 3 phases)
  - 🔧 **Why this matters**: this page layout *is* the on-disk format — every later operation (split, cursor, merge, MVCC) is bookkeeping on top of these byte offsets, and once a DB file exists in the wild the layout is frozen forever. Mirrors libmdbx's slotted page (`MDBX_page` + `node_t`). Three traps: (1) slot-offset width silently caps page size and corrupts large pages; (2) `repr(Rust)` reorders the header so the on-disk image is unportable; (3) free-space math that ignores the slot-directory growth double-counts and lets you overfill a page. First-attempt impls fail ≥1 test below — the debug session is the lesson. Downstream: every other day this week, W31 MPT nodes, W95 mini-db page format.

  #### Phase 1 — Problem, prediction, design (~60 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/storage-trie/notes/28_page_prediction.md`:
    - P1. The type you'd reach for to hold the on-disk header (exact decl line, e.g. `struct Header { ... }` with which `repr`).
    - P2. Predicted leaf-record fan-out for avg key 32 B + val 200 B in a 4 KiB page (a number).
    - P3. Predicted `free_space()` formula in terms of `lower`, `upper` (one expression).

    - P5. List every Phase-2 test you predict your first attempt will FAIL.
  - *Mental model*: a page is a 4 KiB byte slab with a fixed header, a slot directory growing **down** from just-after-the-header, and variable-length records growing **up** from the page tail; the free hole is the gap between them. Binary search runs over the slot directory, not the records.
  - *Contract* (signature-level only — never the body):
    ```rust
    #[repr(C)]
    pub struct PageHeader { flags: u16, num_slots: u16, lower: u16, upper: u16,
                            right_sibling: PageId, pgno: PageId }   // little-endian on disk
    pub struct PageRef<'a> { bytes: &'a [u8] }       // read view over a 4 KiB slab
    pub struct PageMut<'a> { bytes: &'a mut [u8] }   // write view
    impl PageMut<'_> {
        pub fn free_space(&self) -> usize;
        pub fn has_space_for(&self, key: &[u8], val: &[u8]) -> bool;
        pub fn insert_at(&mut self, slot: u16, key: &[u8], val: &[u8]);
        pub fn needs_overflow(&self, rec_len: usize) -> bool;   // rec_len > page/4
    }
    const PAGE_SIZE: usize = 4096;
    bitflags: LEAF=0x01, BRANCH=0x02, OVERFLOW=0x04, META=0x08
    ```
  - *Back-of-envelope*: 4 KiB page, header 16 B, slot 2 B, leaf record `[u16 klen][key][u16 vlen][val]`. For 32 B key + 200 B val a record is 2+32+2+200 = 236 B + 2 B slot = 238 B; `(4096-16)/238 ≈ 17` records/page. A point lookup that hits warm bufpool is ~3 ns (L1) per key compare × log fan-out; a cold page is a ~100 ns main-mem touch or a page fault if not resident — the layout's only job is to keep fan-out high so tree height (and cold touches) stays at 3-4 for billions of keys.
  - **Requirements** R1..R6 — write in `crates/storage-trie/notes/28_page_design.md`:
    - R1. `PageHeader` is `#[repr(C)]`, all multi-byte fields encoded/decoded little-endian via `to_le_bytes`/`from_le_bytes`.
    - R2. Invariant `lower <= upper`; `free_space() == upper - lower`; `lower` points just past the last slot, `upper` points at the first byte of the lowest record.
    - R3. `num_slots` equals the count of `[u16]` slot entries; slots are kept in **key order** (binary-searchable), not insertion order.
    - R4. `has_space_for(key,val)` must charge BOTH the record bytes AND the new 2-byte slot, i.e. needs `rec_len + 2 <= free_space()`.
    - R5. Leaf record `[u16 klen][key][u16 vlen][val]`; branch record `[u16 klen][key][PageId child]`; leftmost branch child lives in the header (not a slot).
    - R6. `needs_overflow(rec_len)` true when `rec_len > PAGE_SIZE/4`; slot then points at an overflow-chain head, record body holds the head `PageId` only.
  - **Design walk-through** D1..D6 — answer in the design doc; no peeking at libmdbx source until Phase 3:
    - D1. Property table of candidate layouts: `Vec<(K,V)>` heap node vs fixed-array node vs slotted page — columns: variable-length keys? in-place split? cache-friendly binary search? mmap-able zero-copy?
    - D2. Walk the byte offsets of inserting one 32 B key into an empty leaf: where does `lower` move, where does `upper` move, what slot value is written?
    - D3. Why does the slot directory grow down and records grow up (instead of both up)? (answer: a single `lower<=upper` check detects full; compaction is only ever on one side.)
    - D4. Endianness: write the exact `from_le_bytes` decode of `num_slots` and explain what a native-endian `transmute` would do on a big-endian reader.
    - D5. **Pre-mortem (load-bearing):** write the EXACT bad sequence: `has_space_for` returns true charging only record bytes (forgot the slot) → `insert_at` writes record at `upper -= rec_len`, slot at `lower += 2` → `lower` now exceeds `upper` by 2 → next read interprets a record byte as a slot offset → out-of-page read. 4-5 lines.
    - D6. **Anti-shortcut audit:** (a) "just `#[derive(Serialize)]` with bincode" — wrong: bincode varint-encodes lengths and isn't a fixed on-disk layout; mmap needs byte-exact offsets. (b) "use `usize` for offsets" — wrong: `usize` is 8 B and platform-width; on-disk must be fixed `u16`. (c) "native-endian `*(self.bytes.as_ptr() as *const Header)`" — wrong: unaligned + endian-dependent + UB.
  - 🧮 **Paper drill** — write in `notes/28_page_drill.md`:
    - D-LAYOUT on a 4 KiB `#[repr(C)] PageHeader` slab holding two 32 B-key + 200 B-val leaf records: draw the byte map — header at 0..16 (flags 0..2, num_slots 2..4, lower 4..6, upper 6..8, right_sibling 8..12, pgno 12..16, all LE u16/PageId), then the slot-directory `[u16]` array growing DOWN from offset 16 and the two records growing UP from offset 4096; mark `lower`/`upper` and the free-space hole between them, and the byte each slot offset points at.
    - D-WALK on inserting key `b"cat"` (klen=3) with val `b"v"` (vlen=1) into an empty leaf: hand-execute the encode byte by byte — write `[03 00][63 61 74][01 00][76]` at `upper -= 8`, write the slot `u16` = that record's start offset at `lower`, advance `lower += 2`; then decode your own bytes back and confirm `free_space() == upper - lower`.

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)
  Ordered newbie → expert.
  - **(NEWBIE) When `page_free_space_charges_slot` reports `consumed 236` instead of 238:**
    - Symptom: assertion fails by exactly 2 bytes.
    - Why: `has_space_for`/`insert_at` charged only the record body and forgot the new slot-directory entry.
    - Fix: every insert costs `rec_len + SLOT_SIZE`; charge both before moving `lower`/`upper`.
    - Muscle: in a slotted page the slot is part of the cost of a record — never account record bytes alone. Reapplies at: W28 Tue split-median sizing, W31 MPT node packing, W95 mini-db page writer.
  - **(NEWBIE) When `page_overflow_detected_for_large_key` panics during a later insert instead of returning true:**
    - Symptom: insert of a 1100 B record panics (slice out of range) rather than routing to overflow.
    - Why: overflow detection happened *inside* split (too late) or not at all; split underestimates the record size.
    - Fix: `needs_overflow` is checked at record-write time, before any space/split decision.
    - Muscle: spillover is a record-write concern, decided before split ever runs. Reapplies at: W28 Tue (split mis-medians without it), W31 large trie values, W34 pruning.
  - **(SENIOR) When `page_header_round_trips_little_endian` reads `[0x01, 0x02]`:**
    - Symptom: bytes are host-endian (big-endian read of `0x0102`), reversed from disk contract.
    - Why: you wrote the field with a native-endian store / `transmute` instead of `to_le_bytes`.
    - Fix: encode/decode every header field with `to_le_bytes`/`from_le_bytes`; never `transmute` a struct onto the buffer.
    - Muscle: an on-disk integer has a chosen endianness independent of the CPU; fix it once (LE) and route every field through it. Reapplies at: W29 wal record headers, W31 MPT node tags, W95 mini-db SSTable footer.
  - **(EXPERT) When `page_offset_width_caps_page_size` lets `65537`/128 KiB through (or rejects the legal `64*1024`):**
    - Symptom: either no error on `open_page_config(65537)` (a record above offset 65 535 later reads garbage) OR `open_page_config(64*1024)` wrongly errors — a `<` vs `<=` off-by-one at the u16 ceiling.
    - Why: slot offsets are `u16` (chosen for density) but the page-size bound wasn't enforced, or was enforced with the wrong comparator so it excludes the exact 65536 ceiling.
    - Fix: assert `4096 <= page_size <= 65536` (inclusive) at config-open; the ceiling is `u16::MAX as usize + 1`, document it next to the `SlotOffset = u16` type and add the `const _` static assert.
    - Cost avoided: silent cross-page corruption (offset wrap) on any DB opened with an oversized page — undetectable until a read returns wrong bytes; or losing the legal 64 KiB page size to a too-strict bound.
    - Muscle: when a type's width bounds a config value, enforce the bound at the boundary, beside the type — and get the inclusive/exclusive edge exactly right (the ceiling is a legal value). Reapplies at: W29 wal segment-offset width, W34 bloom bit-index width, W95 mini-db page-id width.
  - **(SENIOR) When `page_slots_stay_key_ordered` returns `[c, a, b]`:**
    - Symptom: keys come back in insertion order, not sorted.
    - Why: `insert_at` appended a slot at `num_slots` instead of at the binary-search lower-bound position.
    - Fix: compute `slot = lower_bound(key)`, shift the trailing `[u16]` slots up by one, write the new slot there.
    - Muscle: the slot directory — not the records — carries the sort order; inserts splice into it. Reapplies at: W28 Tue split copy, W28 Wed cursor seek, W31 MPT child ordering.

**Tuesday — B-tree insert + node split**

- [ ] **Build**: `crates/storage-trie/src/btree/insert.rs` — `search_to_leaf`, `insert`, `split_at_median`, `insert_in_parent`, root-split. (~total 240 min across 3 phases)
  - 🔧 **Why this matters**: insert is the only op that grows tree height, and split is the single most off-by-one-prone routine in any B+tree — a wrong median or a borrowed-not-copied separator corrupts the whole tree *silently* (lookups quietly skip subtrees, no crash). Mirrors libmdbx `page_split`. Three traps: (1) median index choice; (2) separator must be **copied** into the parent, not referenced; (3) the path stack goes stale the instant a page splits under it. First attempts fail ≥1 test below. Downstream: every record this DB ever stores; W31 MPT inserts trie nodes here; W43-44 storage-trie v1.0.

  #### Phase 1 — Problem, prediction, design (~60 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/storage-trie/notes/28_insert_prediction.md`:
    - P1. The median expression you'd write (`num_slots/2`? `(num_slots+1)/2`? byte-balanced?) — exact line.
    - P2. Predicted tree height for 1M random 32 B keys at ~17 records/leaf (a number; show the log).
    - P3. Predicted outcome of inserting a key whose record won't fit even alone in an empty page.
    - P4. After a leaf split, is your saved `path` (vec of `(PageId, slot)`) still valid for `insert_in_parent`? (yes/no + why)
    - P5. List every Phase-2 test you predict your first attempt will FAIL.
  - *Mental model*: descend root→leaf recording the path; if the leaf has room, splice in; else split the leaf at a balanced point, push the separator (smallest key of the right half) up to the parent, and recurse the split upward — a root split adds a level.
  - *Contract*:
    ```rust
    pub fn insert(&mut self, key: &[u8], val: &[u8]) -> Result<(), InsertError>;
    fn search_to_leaf(&self, key: &[u8]) -> Path;            // Vec<(PageId, slot_idx)>
    fn split_at_median(p: &PageMut) -> (PageMut, PageMut, Vec<u8>);  // (left, right, separator)
    fn insert_in_parent(&mut self, path: Path, sep: Vec<u8>, right: PageId) -> Result<(), InsertError>;
    // Invariant: all leaves at equal depth; every non-root page in [min_fill, max_fill];
    //            branch separator == smallest key of its right subtree.
    ```
  - *Back-of-envelope*: with ~17 records/leaf and ~170 branch entries/page, 1M keys → height `ceil(log_170(1e6)) ≈ 3`. A split copies ≤ half a page (≤2 KiB memcpy ≈ tens of ns) and allocates one page; it happens roughly once per `fan-out` inserts, so amortized split cost is sub-ns/insert — the dominant cost is the 3-4 page touches of the descent, which is why height (not split speed) is what we protect.
  - **Requirements** R1..R6 — `crates/storage-trie/notes/28_insert_design.md`:
    - R1. After any insert every non-root page is within `[min_fill, max_fill]`; all leaves at equal depth.
    - R2. Keys in any leaf are strictly less than the first key of its right sibling.
    - R3. A branch separator equals the **smallest key of its right child subtree** and is stored as a copy in the parent.
    - R4. Split point is **byte-balanced**: the index where cumulative record size first crosses page/2, not blindly `num_slots/2` (records are variable-length).
    - R5. Root split allocates a fresh root with one separator and two children; tree height += 1; old root keeps its pgno semantics per allocator.
    - R6. Duplicate key → REPLACE value in place (MVCC-friendly semantics), not a second slot.
  - **Design walk-through** D1..D6:
    - D1. Property table: recursive split-on-the-way-down (preemptive) vs split-on-the-way-up (this design) — columns: extra splits? latch lifetime? path-staleness risk?
    - D2. Walk a leaf split of 4 records sized [50,3000,50,50] in a 4 KiB page: where is the byte-balanced median vs the count median, and what's the resulting fill imbalance for each?
    - D3. Walk a cascade: leaf splits → parent full → parent splits → was root → new root. Track height.
    - D4. Separator copy: show the two pages after split and the exact bytes the parent gains; show what "borrow a `&[u8]` into the right page" would do when the right page is later written/evicted.
    - D5. **Pre-mortem (load-bearing):** write the EXACT bad sequence: split returns `right` and a new `pgno`; you call `insert_in_parent(path, …)` but `path` still lists the *pre-split* leaf as last; `insert_in_parent` pops the parent frame fine, yet the parent's child-pointer for the split key still points only at the old left page → the separator is inserted but its right child pgno is dropped → the right half is unreachable → 50% of keys vanish from lookups. 4-5 lines.
    - D6. **Anti-shortcut audit:** (a) "median = `num_slots/2`" — wrong here: variable-length records make a count split wildly unbalanced (see D2). (b) "store `&separator` from the right page in the parent" — wrong: the borrow outlives the page write/eviction → stale/dangling. (c) "re-`search_to_leaf` after every split" — wrong: O(height) extra descents per split and still racy under latches; patch the path instead.
  - 🧮 **Paper drill** — write in `notes/28_insert_drill.md`:
    - D-STRUCT on a concrete 4-key leaf `[a→v0, b→v1, c→v2, d→v3]` (each record 200 B, page near-full) that a 5th insert of `e` overflows: hand-execute the split step by step — draw the full leaf, pick the byte-balanced median, redraw as left `[a,b]` + right `[c,d,e]` (or wherever the byte boundary lands), write the separator (right's smallest key `c`) and right's pgno into the parent, redraw the parent branch after the splice; confirm every key still routes to exactly one leaf.
    - D-WALK on a root-split cascade: hand-trace inserting into a tree whose only leaf is full → leaf splits → parent (the old root leaf) has no parent → allocate a fresh root branch with one separator and two children; write the 3-line state after each step and mark where `height += 1`.
    - D-COST on the insert hot path: per-op ledger for a 3-deep tree — descent = 3 page touches (warm L2 7 ns each ≈ 21 ns) + log fan-out key compares (L1 0.5 ns each); split cost = ≤2 KiB memcpy (tens of ns) + one page alloc (~50 ns) amortized over ~17 inserts ≈ sub-ns/insert; state the cliff ratio cold page-fault descent vs warm, and confirm height (not split speed) is the budget.
