    #### Phase 1 — Problem, requirements, design (~70 min, no code yet)

    - **The problem this primitive solves**: a single-process state machine can't survive a crash. Replication via consensus solves that, but the integration is where subtle bugs live: cross-thread queues add P99 tail; client API + commit callback racing on a Mutex serializes the apply loop; idempotency on leader change requires SM-layer support. The contract is: bytes-on-wire are VSR messages; bytes-in-SM are ledger ops; this file is the gap.

    - **Requirements** — write in `crates/ledger-deterministic/notes/91mon_replication_design.md`:
      - R1. `ReplicatedLedger { sm: LedgerSM, replica: NormalReplica, pool: MessagePool, tx_pending: FixedMap<TransferId, oneshot::Sender<TransferResult>> }`.
      - R2. `apply()` invoked ONLY through `on_committed` callback — never directly, even on leader. Followers and leader walk identical code paths.
      - R3. `tx_pending` lives on leader only (followers have no client connections); per-shard thread owns it lock-free (no `Arc<Mutex<_>>`).
      - R4. `on_committed` runs on the same per-shard pinned core as the VSR protocol thread (runtime-thread-per-core W85) — zero cross-thread hop between commit and apply.
      - R5. Sustained throughput ≥ 100 k Transfers/sec on 3-replica loopback; commit P99 < 500 µs.
      - R6. State-hash gossip every N ops; mismatch → `assert_unreachable!("state divergence at op_num={n}, our_hash={h1}, peer_hash={h2}")`.
      - R7. Leader-change handling: on `Status::ViewChange`, drain `tx_pending` with `Err(LeaderChanged)` so clients can retry.
      - R8. Idempotency on retry: SM-layer dedupe by `TransferId`; replaying a committed op is a no-op (returns same result).
      - R9. `tx_pending` leak prevention: TTL eviction per pending entry; periodic sweep on idle.
      - R10. dhat reports 0 allocations in `on_committed` path.

    - **Design walk-through** — answer each; no peeking at TigerBeetle `replica.zig::commit_journal/commit_op_now` until Phase 3:
      - D1. Per-Transfer 3-replica commit timeline (loopback): leader `submit()` (~100 ns encode + push to VSR), VSR Prepare to 2 followers (~3 µs RTT parallel), leader journal-write (~290 ns amortized W90 group-commit), PrepareOk roundtrip (~3 µs), commit→apply (~500 ns W89 static-mem budget), reply to client (~100 ns). Tally: P50 ≈ 7 µs ✓. What dominates P99? (Network tail + group-commit horizon on followers.)
      - D2. Single-shard architecture: VSR replica + ledger SM share one pinned core (W85 runtime-thread-per-core). Why? Cross-core hop costs ~30-100 ns L2-coherency + queue contention; multiplied through f+1 replicas = ~450 ns/Transfer × 100 k/s = ~45 ms/sec. How does in-line invocation (`replica.commit_op_now` calls `self.sm.apply()` directly) eliminate this?
      - D3. `tx_pending` ownership: option A — `Arc<Mutex<HashMap<...>>>` (~25 ns/op uncontended, ~1-10 µs contended). Option B — shard-owned `FixedMap<TransferId, oneshot::Sender<...>>` (zero lock). Why is option A fatal at 200 k accesses/sec (insert on submit + remove on commit)? When does the Mutex contention spike land in P99?
      - D4. Idempotency strategy: client submits op; leader commits + apply; reply lost; client retries with same TransferId. New leader receives; replicates; on apply, SM finds TransferId already in `processed_ids: FixedMap<TransferId, TransferResult>`; returns cached result. What's the size budget for `processed_ids`? (MAX_INFLIGHT + grace window for retries.) How does that interact with `tx_pending`?
      - D5. State-hash gossip: every 1000 ops, leader piggybacks current state_hash on Commit message; follower validates. What happens on mismatch? (Assertion violation — divergence is a correctness disaster, fail loud.) Why include current op_num in gossip? (Mismatch could be follower lagging vs leader corruption — op_num disambiguates.)
      - D6. Leader change: replica state `Status` transitions from `Normal` → `ViewChange`. What happens to in-flight client requests in `tx_pending`? (Limbo — leader can't commit; new leader doesn't know about them.) Drain with `Err(LeaderChanged)`; clients retry against new leader; idempotency makes this safe.
      - D7. Snapshot replication on follower-catchup: leader sends `LedgerSM` snapshot + journal tail from snapshot.op_num to current. How does follower replay deterministically? (Strict op_num order; snapshot tagged with op_num at capture; replay from snapshot.op_num+1 only.)
      - D8. `tx_pending` leak prevention: client disconnects mid-op; `oneshot::Sender` Drop fires but `tx_pending` still holds the entry. How to detect? (TTL per entry: `(submitted_at, sender)`; periodic sweep evicts entries older than 30 s.)
      - D9. **Pre-mortem (load-bearing)**: write the 6-step sequence where leader change + client retry causes double-apply. Scenario: leader L1 commits op X; reply to client lost; client retries against new leader L2; L2 has X in journal but processed_ids was lost on view change. What persists processed_ids across leader change? (It IS the journal — every op's TransferId is in the committed log; follower SM replays them on catchup; idempotency table reconstructed.) Why must it be derived, not separately persisted? (Avoid 2-phase commit between journal and dedupe table.)

    - **Output**: `notes/91mon_replication_design.md` with R1–R10 + D1–D9 + the in-line callback diagram + leader-change handling state diagram.

    #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

    - **When `bench_commit_p99_under_500us_loopback` reports P99 ~1.5 ms:**
      - Symptom: P50 looks fine (~7 µs) but P99 = 1500 µs; over budget by 3×. Profiler shows ~15% time in `crossbeam::channel::send`/`recv`.
      - Why: VSR replica runs on one pinned core (network/protocol thread); ledger SM runs on another ("apply thread"). Each commit crosses cores: cache-line bounce on op payload (~30-100 ns L2-coherency), queue push/pop (~50 ns crossbeam channel), waker fire (~30 ns). Per Transfer × 3 replicas × ~150 ns = ~450 ns/Transfer × 100 k/s = ~45 ms/sec on cross-core hops. P99 inflated by queue-depth-under-burst.
      - Fix: VSR replica + ledger SM share one shard (W85 runtime-thread-per-core). `ReplicatedLedger::on_committed` is called inline on the same thread that processes the commit message — no channel, no waker. Replica's `commit_op_now()` directly invokes `self.sm.apply()` via trait-method dispatch in-line.
      - Cost avoided: ~450 ns/Transfer × 100 k/s = ~45 ms/sec reclaimed; P99 tail variance from queue-depth eliminated. The "follower apply is on the protocol thread" choice is TigerBeetle's design.
      - Muscle: in any "protocol + state machine" design, SM apply lives on the same thread as the protocol's committer. Cross-thread handoffs are protocol bugs that cost real ns AND introduce P99 variance. Reapplies at: W74 matching-engine raft commit → order-book apply, W82 matching-engine MBO feed publication, W100 mini-db CAPSTONE WAL commit → memtable insert.

    - **When `test_no_mutex_in_apply_path` fires on a discovered `Arc<Mutex<HashMap<...>>>`:**
      - Symptom: code review flags `tx_pending: Arc<Mutex<HashMap<TransferId, oneshot::Sender<TransferResult>>>>` — written for "easy concurrent access from submit() and on_committed()".
      - Why: convenience pattern; Mutex acquire ~25 ns uncontended, ~1-10 µs contended. At 100 k op/s × 2 accesses/op (insert on submit, remove on commit) = 200 k Mutex ops/sec × ~25 ns = ~5 ms/sec just on locking; tail exposes 1-10 µs contention spikes in P99.
      - Fix: `tx_pending` is owned by the single shard thread (no Mutex, no Arc). Both `submit()` (which enqueues via shard's mailbox) and `on_committed` (which runs on the shard thread) access it lock-free. Type: `FixedMap<TransferId, oneshot::Sender<TransferResult>>` (W89 Tue). Pre-sized for MAX_INFLIGHT.
      - Cost avoided: ~5 ms/sec lock overhead + ~1-10 µs P99 tail spikes removed.
      - Muscle: thread-per-core architecture (W85) makes `Mutex<Map>` redundant. Any `Mutex` left in the design is a P99 hazard. Audit for any `Arc<Mutex<_>>` in the apply path; replace with shard-owned non-shared state. Reapplies at: W82 matching-engine order-book state, W92 ledger AccountMap, W74 matching-engine PriceLevel, W77 messaging-aeron `Image` state.

    - **When `test_idempotent_replay_after_leader_change` shows double-apply (balance doubled):**
      - Symptom: original submission committed; new leader committed retry; balance went from 100→200 (expected 200→200 — second commit should be no-op).
      - Why: new leader has the op in journal but no `processed_ids` table — replay applies fresh. The dedupe state wasn't reconstructed on view change.
      - Fix: SM-layer dedupe: `processed_ids: FixedMap<TransferId, TransferResult>` is derived from journal replay (not separately persisted). On leader change, new leader replays committed ops; for each `TransferId`, populate `processed_ids` BEFORE calling apply. Next-arrival check: `if processed_ids.contains_key(&op.transfer_id) { return processed_ids[&op.transfer_id]; }`.
      - Muscle: idempotency belongs at the SM layer, derived from the journal (single source of truth). Two-phase commit between journal and dedupe table is fragile. Reapplies at: W100 mini-db client retry idempotency, W82 matching-engine OrderId dedupe.

    - **When `test_state_hash_mismatch_fails_loud` silently continues:**
      - Symptom: deliberate corruption; gossip shows mismatch; no panic, no log, replicas keep diverging.
      - Why: state_hash compare done via `if mine != peer { warn!(...) }`. A warn is not a fail-loud.
      - Fix: state_hash mismatch is a CORRECTNESS DISASTER, not a warning. Use `assert_eq!(mine, peer, "state divergence at op_num={n}")` with op_num + both hashes in panic message. Service crashes; operator paged; root-cause analysis required before restart. This is the bar-(c) invariant.
      - Muscle: state divergence is unrecoverable; the only safe response is fail-loud. Reapplies at: W92 v1.0 SHIP invariant violation, W77 messaging-aeron message-loss assertion, W82 matching-engine order-book consistency.

    - **When `test_tx_pending_ttl_cleanup` shows growing `tx_pending` size after disconnects:**
      - Symptom: 10 k client connects, all disconnect mid-op without consuming results; `tx_pending` size = 10 k 1 hour later.
      - Why: `oneshot::Sender::Drop` fires on client disconnect; ledger never observes; entry sits forever.
      - Fix: entry type `PendingEntry { submitted_at: Instant, sender: oneshot::Sender<TransferResult> }`. Periodic sweep (every 1 s, low-priority): iterate `tx_pending`; evict entries with `submitted_at < now - 30s`. Alternative: every `on_committed`, opportunistically evict 1 old entry from a circular cursor.
      - Muscle: pending-entry maps need a leak prevention strategy; TTL eviction is the simplest. Reapplies at: W100 mini-db request tracking, W82 matching-engine pending-order map.

    - **5-year failure mode** (write in `notes/91mon_replication_followup.md` after green): when client connection counts exceed 1 M concurrent, `FixedMap` size > MAX_INFLIGHT becomes the cap. Migration: per-connection bounded `tx_pending` (per-client cap of N); reject submit if client cap exceeded. Trigger: > 80% utilization of MAX_INFLIGHT for 7 consecutive days.

    #### Phase 1 — Problem, requirements, design (~70 min, no code yet)

    - **The problem this primitive solves**: sequential EVM at ~480 µs/tx caps mainnet at ~520 tx/block-time. Block-stm parallelizes via optimistic execution but requires precise read/write tracking to detect conflicts. Naive `Vec`-backed read/write sets trigger allocator contention across worker threads — invisible in single-threaded benchmarks, fatal at parallel scale (caps 8-core speedup at ~1.5×).

    - **Requirements** — write in `crates/exec-vm/notes/91fri_rwset_design.md`:
      - R1. `RwSet { reads: ArrayVec<(StorageKey, Version), MAX_READS=4096>, writes: ArrayVec<(StorageKey, StorageValue), MAX_WRITES=512> }` — stack-bounded, zero-alloc.
      - R2. `MultiVersionStore { slots: DashMap<StorageKey, BinaryHeap<VersionEntry>> }` — per-key version list.
      - R3. Tx N reads return highest version < N that is `Committed` (not `Estimate`).
      - R4. Tx N writes tagged `(N, incarnation)`; incarnation increments on re-execution.
      - R5. Validation: replay reads; for each `(key, version)` check store's current read-version equals; mismatch = conflict = re-execute.
      - R6. Per-tx RwSet overhead < 200 ns vs sequential exec.
      - R7. 8-core speedup ≥ 2× on low-conflict block; ≤ 20% regression on high-conflict (USDC-heavy) block.
      - R8. Estimate vs Committed: in-progress writes are `Estimate`; reader treats Estimate as dependency (waits or marks dependency); Estimate finalizes to `Committed` on validation pass.
      - R9. Hot-key bypass: per-block heuristic classifies hot keys (from previous block's SSTORE statistics); hot-key access uses per-key `RwLock<(Version, Value)>`, not DashMap.
      - R10. Txs exceeding MAX_READS or MAX_WRITES fall back to sequential exec (rare; 99.9th-pct mainnet tx reads < 500 slots).

    - **Design walk-through** — answer each; no peeking at Aptos block-stm paper or Reth parallel-EVM PR until Phase 3:
      - D1. Per-tx overhead budget: SLOAD reads.push (~5 ns ArrayVec) × ~50 SLOADs = ~250 ns; SSTORE writes.push (~5 ns) × ~10 SSTOREs = ~50 ns; MultiVersionStore read (~30 ns DashMap shard + heap lookup) × 50 = ~1.5 µs; validation replay (~1 µs). Total ~3 µs/tx ≈ 0.6% of 480 µs sequential. What dominates? (DashMap shard lookup.) Where can it shrink? (Hot-key bypass.)
      - D2. Why `ArrayVec` not `Vec`? `Vec::new()` lazy alloc on first push (~50 ns); doublings (4→8→16→32) trigger 4-5 reallocs/tx (~250 ns); each realloc takes jemalloc per-arena lock — serializes parallel workers. Verify with `dhat` on Vec impl; expect ~1000 allocs for 250-tx block.
      - D3. MAX_READS=4096 sizing: 99th-pct mainnet tx reads ~50 slots; 99.9th-pct < 500; outliers (DEX router calls) up to ~3000. Why 4096 and not 8192? (Memory: 4096 × (KeySize + VersionSize) ≈ 200 KB/tx; 250 txs × 200 KB = 50 MB total RwSet memory.) Fallback sequential for outliers — flagged for scheduler.
      - D4. MultiVersionStore: per-key heap is `BinaryHeap<VersionEntry { tx_idx, incarnation, value }>`. Why a heap, not Vec or BTreeMap? (Read needs "highest version < N committed"; heap top-down walk finds it in O(log K) where K = version count per key.) What if a key has 100 versions (rare but possible)?
      - D5. Validation flow: tx N's RwSet was captured during speculative execution. At commit time, replay each (key, version) read; check current MultiVersionStore returns same (key, version). If mismatch (someone in [0, N) wrote with higher version after N read), tx N is invalid; mark for re-execution. What's the re-execute cost? (Full re-run; incarnation++.)
      - D6. Estimate vs Committed: tx N is mid-execution; writes its outputs as `Estimate(N, incarnation)`. Tx M > N reads same key; what does it see? Option A: skip Estimate, return last Committed before N — risk: validates green but M's actual dependency was N's Estimate; invalid result. Option B: return Estimate but mark M as dependent on N; if N invalidates, M invalidates. Pick B; document.
      - D7. Hot-key heuristic: per-block, scan previous block's SSTOREs; count per-key write frequency; top 1% = "hot". Hot-key access bypasses DashMap: `hot_keys: HashMap<StorageKey, RwLock<(Version, Value)>>` populated upfront. Cold-key still uses DashMap. Why? Under a USDC-heavy block, ALL 200/250 txs touch `balanceOf(0xUSDC)` = same DashMap shard = `RwLock<HashMap<...>>` serializes everything; 8 workers see effective parallelism 1.
      - D8. Validation atomicity: validator runs on the scheduler thread (single-threaded). What protects against worker N (re-)writing to MultiVersionStore mid-validation? (Validator's "scan" semantic = read-only snapshot; workers don't write to a tx's slot once it's marked Validating.)
      - D9. **Pre-mortem (load-bearing)**: write the 5-step interleaving where two parallel workers race on a hot key and both produce valid-looking RwSets, but their combined effect violates sequential semantics. Scenario: USDC.balanceOf(Alice); worker A executes tx 1: reads bal=100, writes bal=90; worker B executes tx 2: reads bal=100, writes bal=80. Both validate OK (each saw committed-bal=100); merged result = bal=80 (B's write wins) but sequential would give bal=70 (1's write seen by 2). What detects this? Validation must check tx 2's read-version (committed=100, tx_idx=0) is STILL the highest committed < 2 at validation time; if tx 1 committed in between, tx 2 sees new committed-bal=90; conflict, re-execute.

    - **Output**: `notes/91fri_rwset_design.md` with R1–R10 + D1–D9 + flow diagram of optimistic execution + validation + hot-key bypass strategy.

    #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

    - **When `test_rwset_zero_allocs_per_tx` reports ~1000 allocs for 250-tx block:**
      - Symptom: dhat fires ~4-5 allocs per tx; each at ~50 ns malloc + ~30 ns Drop. Total allocator cost ~80 ns/tx × 250 = ~20 µs/block from malloc alone; PLUS allocator-arena lock contention across 8 workers.
      - Why: you used `reads: Vec::new()`, lazy alloc on first push; `Vec::reserve` doublings on capacity full trigger more allocs. Allocator lock serializes parallel workers.
      - Fix: `reads: ArrayVec<(StorageKey, Version), MAX_READS>` — stack-allocated, fixed-size at compile time. Push is ~5 ns (one bounds check + write). Construction ~10 ns (ArrayVec header zero). Per-tx alloc cost: 0. Worker threads have zero allocator contention. Txs exceeding MAX_READS fall back to sequential exec — flagged "wide-read" for the scheduler.
      - Cost avoided: ~250 ns/tx allocator cost × 250 txs/block × 8 cores = ~500 µs/block reclaimed; plus allocator-arena lock contention eliminated (was capping 8-core speedup at ~1.5× vs 2× target).
      - Muscle: `ArrayVec` (or other stack-bounded collections) on the hot path of any parallel worker — `Vec` introduces serialization through the global allocator that doesn't show in single-threaded benchmarks. Reapplies at: W92 versioned-memory per-slot version cap, W94 exec-vm v1.5 SHIP speedup bench (THE perf line item under "8-core speedup ≥2×"), W82 matching-engine per-shard order queue.

    - **When `test_high_conflict_regression_bounded` shows regression > 50% (USDC-heavy block):**
      - Symptom: synthetic USDC-heavy block runs ~2× SLOWER in 8-core than 1-core; speedup is 0.5×. Profiler: `DashMap::write_internal` at ~80% CPU; 7 workers idle waiting on one shard's RwLock.
      - Why: `MultiVersionStore::slots: DashMap` with default 32 shards. All 200/250 txs touch `balanceOf(0xUSDC)` → same DashMap shard → that shard's `RwLock<HashMap<...>>` serializes everything. 8 workers contend for 1 lock → effective parallelism = 1.
      - Fix: classify "hot keys" upfront from previous blocks' SSTORE statistics (top 1% by write frequency). Populate `hot_keys: HashMap<StorageKey, RwLock<(Version, Value)>>` upfront. Hot-key SLOAD/SSTORE bypass MultiVersionStore entirely. Cold keys still use DashMap. Alternative: `crossbeam_skiplist::SkipMap` with epoch-GC (W37 primitive) — lock-free reads, finer concurrency than DashMap shards.
      - Cost avoided: ~80% CPU stall on hot-key lock → ~5% (cache-coherency cost on per-key atomic version); USDC-heavy block speedup goes from ~0.5× to ~0.9× (within 20% regression bound).
      - Muscle: any "concurrent map" has hot-key tail-latency issues; production-grade parallel exec requires hot-key classification, not just better data structures. Bench should split low-conflict vs high-conflict; honesty about high-conflict caveat is the credibility move. Reapplies at: W92 versioned-memory hot-key heuristic, W94 exec-vm v1.5 SHIP "high-conflict regression bound" gate, W74 matching-engine PriceLevel hot symbol routing.

    - **When `test_validation_detects_conflict` fails to detect the conflict:**
      - Symptom: tx 2 reads K=v1 (initial); tx 1 commits K=v2 between; validation passes tx 2 even though it should re-execute.
      - Why: validation replay checks `read_version == stored_version_at_read_time` but the comparison uses the (cached) version snapshot, not the current store state. Or validation runs against a snapshot taken at exec time, not at validate time.
      - Fix: validation must read the CURRENT MultiVersionStore for each (key, version) in tx 2's reads. If MultiVersionStore now returns version (2, Committed) for K (because tx 1 just committed), but tx 2's RwSet captured version (0, Committed), there's a mismatch → conflict → re-execute tx 2 with incarnation++.
      - Muscle: validation is "did the world change under me?" — must read current state, not a snapshot. Reapplies at: W92 versioned-memory validator, W94 v1.5 SHIP correctness gate.

    - **When `test_multiversion_store_read_returns_highest_committed_lt_n` returns the Estimate value:**
      - Symptom: read at tx_idx=6 with versions [(2, Committed), (5, Estimate), (8, Committed)] returns version 5's value (the Estimate).
      - Why: store walks heap top-down without filtering; Estimate sits between Committed entries.
      - Fix: walk heap entries; skip any with state==Estimate that affects the result. Two options: (a) return highest Committed < N (option from R3, ignores Estimate; simpler but may invalidate later if N depends on M < tx_idx with Estimate); (b) return Estimate but mark M as dependent on N (option from D6). Pick (b); document.
      - Muscle: Estimate semantics propagate dependency — never silently treated as Committed. Reapplies at: W92 versioned-memory Estimate handling, W94 v1.5 SHIP correctness.

    - **When `test_parallel_result_matches_sequential` shows a property-test counterexample (10-tx block with one mismatch):**
      - Symptom: random 10-tx block; parallel exec gives `account.balance == 100`; sequential gives `account.balance == 95`. Five-tx difference.
      - Why: a validation gap — likely Estimate-as-final or hot-key bypass writing the wrong order. Look at the counterexample's tx 4 RwSet; trace which read returned what.
      - Fix: depends on root cause. Most often: validation didn't replay all reads (just the writes); or a tx with MAX_READS overflow was processed in parallel instead of falling back to sequential.
      - Muscle: parallel-exec correctness is property-testable; "looks right under typical load" is not enough — the property test is the truth. Reapplies at: W94 v1.5 SHIP correctness gate, W92 versioned-memory.

Migration: RwSet seeds from AccessList; validation reduces to "did the static AccessList hold?" Trigger: > 50% of mainnet txs include comprehensive AccessLists.
