  - [ ] **Build**: `crates/ledger-deterministic/src/replication.rs` — wire ledger's `apply()` to consensus-vsr's `NormalReplica.commit()` hook. Leader replica applies + replicates; followers apply on commit. (~3 hrs)
    - **Why**: this is the load-bearing integration of v1.0 — without it, ledger is single-process; with it, ledger is a real distributed replicated state machine. Mirror TigerBeetle's structure: leader receives client op → replicates via VSR → all replicas apply on commit. The contract: bytes-on-the-wire are VSR messages; bytes-in-the-state-machine are ledger ops; the gap between is this file.
    - *Back-of-envelope* (target: **100k Transfers/sec sustained 3-replica; commit P99 < 500 µs loopback**):
      Per-Transfer 3-replica commit timeline: leader `submit()` ≈ 100 ns (encode op + push to VSR); VSR Prepare to 2 followers via loopback UDP/IPC ≈ 3 µs RTT (parallel sends, wait for f+1 = 2 acks); leader local journal-write (W90 group-commit) ≈ 290 ns amortized; PrepareOk roundtrip ≈ 3 µs; leader commit → apply ≈ 500 ns (W89 static-mem + W89 FixedMap budget); reply to client ≈ 100 ns. Total P50 ≈ 7 µs ✓; P99 ≈ 50-500 µs depending on (a) network tail, (b) group-commit horizon spike on followers. The load-bearing latency is **followers' apply must run on the same per-shard pinned core** as VSR — any cross-core hop between `on_committed` and `apply()` costs ~30-100 ns L2-coherency + queue contention, multiplying through f+1 replicas. The `runtime-thread-per-core v1.0` (W85) substrate is what makes this achievable.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/replica.zig` `commit_journal()` / `commit_op_now()`; LIONS-VSR §4 "Operation Processing"; your own consensus-vsr `NormalReplica` API.
    - **Design**:
      ```rust
      pub struct ReplicatedLedger {
          sm: LedgerSM,
          replica: NormalReplica,
          pool: MessagePool,
          tx_pending: FixedMap<TransferId, oneshot::Sender<TransferResult>>,
      }
      impl ReplicatedLedger {
          pub fn submit(&mut self, op: LedgerOp) -> impl Future<Output = TransferResult>;
          fn on_committed(&mut self, op_num: OpNum, payload: &[u8]) {
              let op: LedgerOp = decode(payload);
              let result = self.sm.apply(&op);
              if let Some(tx) = self.tx_pending.remove(&op.id()) { tx.send(result).ok(); }
          }
      }
      ```
      **Invariants**: (i) ledger's `apply()` is invoked ONLY through `on_committed` — never directly, even on leader; (ii) leader and follower invoke `apply()` with byte-identical payload in same op-num order → byte-identical state_hash; (iii) `tx_pending` map exists only on leader (followers don't have client connections); (iv) op is durable BEFORE apply (VSR's prepare+quorum ack before commit).
    - **Build steps**: 1. (~15 min) `ReplicatedLedger::new(replica_id, peers, sm)` constructs. 2. (~25 min) `submit(op)`: leader path — assigns TransferId, encodes, calls `replica.client_request()`, registers oneshot in tx_pending, returns Future. 3. (~25 min) `on_committed` callback registered with replica; called by replica when op commits. 4. (~30 min) follower path: same `on_committed` callback fires on commit message receipt; apply identical op. 5. (~25 min) leader change handling: when replica's `Status::View` changes, current leader's tx_pending is in limbo; respond `Err(LeaderChanged)` to those clients. 6. (~25 min) snapshot replication: on follower-catchup, transfer LedgerSM snapshot + journal tail. 7. (~25 min) state_hash gossip: every N ops, replica gossip state_hash; mismatch → invariant violation. 8. (~20 min) tests: 3-replica, drive 100k Transfers via leader, all replicas converge.
    - **Pitfalls**: *Replication-latency tail*: **Symptom**: leader-to-follower-commit p99 hugely worse than apply p99. **Fix**: separate metrics for replication time + apply time; tune VSR batch_size + io_uring journal group-commit. *Ordering across replicas*: **Symptom**: follower applies op X before X-1 due to network reorder. **Fix**: VSR's op_num strictly ordered; followers buffer out-of-order and apply in sequence. *Snapshot-restore safety*: **Symptom**: follower restored from old snapshot; replays journal but state_hash mismatch. **Fix**: snapshot tagged with op_num at capture; replay strictly from snapshot.op_num + 1. *Double-apply on leader-change*: **Symptom**: client retries op after leader change; new leader applies it again. **Fix**: TransferId-based idempotency at SM layer — pure-replay safe. *tx_pending leak*: **Symptom**: client disconnects mid-op; sender drops; pending entry grows. **Fix**: TTL on pending entries; cleanup periodically.
  - **Expect to hit (perf) #1 — `on_committed` running on a different core from `apply()` (bar (c) violation)**: VSR's `NormalReplica` runs the network/protocol thread on one core; ledger's `LedgerSM.apply()` runs on another (the "apply thread"). Each commit crosses cores: cache-line bounce on the op payload (~30-100 ns L2-coherency), queue push/pop (~50 ns if using `crossbeam::channel`), waker fire (~30 ns). Per Transfer × 3 replicas × ~150 ns cross-core overhead = ~450 ns × 100k/s = **45 ms/sec** spent on cross-core hops; P99 commit latency inflated by ~200-500 µs from queue depth under burst. The throughput target (100k/s sustained) becomes contention-bound, not CPU-bound.
    - Fix: VSR replica and ledger SM share **one** shard (runtime-thread-per-core W85). `ReplicatedLedger::on_committed` is called inline on the same thread that processes the commit message — no channel, no waker. The Replica's `commit_op_now()` directly invokes `self.sm.apply()` via a function pointer or trait-method dispatch in-line. The single-threaded apply path is what makes the W92 SHIP-day P99 < 500 µs achievable.
    - Cost avoided: ~450 ns/Transfer × 100k/s = ~45 ms/sec reclaimed; plus the P99 tail variance from queue-depth-under-burst eliminated. The "follower apply is on the protocol thread" choice is exactly TigerBeetle's design — they had the same evolution.
    - Muscle: in any "protocol + state machine" design, the SM apply lives on the same thread as the protocol's committer. Cross-thread handoffs are protocol bugs that cost real ns AND introduce P99 variance. Reapplies at: W74 matching-engine raft commit → order-book apply (must be same shard), W82 matching-engine MBO feed publication (publisher on the same shard as the order book), W100 mini-db CAPSTONE WAL commit → memtable insert (same thread).
  - **Expect to hit (perf) #2 — `tx_pending` map uses `HashMap` with `Mutex`, contended by client API + commit callback (bar (c) violation)**: implementing `tx_pending: Arc<Mutex<HashMap<TransferId, oneshot::Sender<TransferResult>>>>` for "easy concurrent access from submit() and on_committed()." Each access acquires the Mutex (~25 ns uncontended, ~1-10 µs contended). At 100k op/s × 2 accesses/op (insert on submit, remove on commit) = 200k Mutex ops/sec × ~25 ns = 5 ms/sec just on lock acquisition; tail latency exposes ~1-10 µs Mutex contention spikes that land in commit P99.
    - Fix: `tx_pending` is owned by the **single shard thread** (no Mutex, no Arc). Both `submit()` (which enqueues via shard's mailbox) and `on_committed` (which runs on the shard thread) access it lock-free. Type: `FixedMap<TransferId, oneshot::Sender<TransferResult>>` (W89 Tue's fixed open-addressing map). Pre-sized for `MAX_INFLIGHT` Transfers; no rehash, no allocation, deterministic.
    - Cost avoided: ~5 ms/sec lock overhead + ~1-10 µs P99 tail spikes removed. Combined with perf #1, the commit P99 < 500 µs target is achievable.
    - Muscle: thread-per-core architecture (W85) makes `Mutex<Map>` redundant — and any `Mutex` left in the design becomes a P99 hazard. Audit for any `Arc<Mutex<_>>` in the apply path; replace with shard-owned non-shared state. Reapplies at: W82 matching-engine order-book state (shard-owned, no Mutex), W92 ledger AccountMap (shard-owned), W74 matching-engine PriceLevel (shard-owned), W77 messaging-aeron `Image` state (subscriber-shard-owned).
    - **Test scenarios**: 3-replica config, 100k Transfers via leader → all replicas state_hash equal at end. Inject leader kill mid-batch → new leader elected, client retry succeeds. Network partition (leader isolated 5s) → minority blocks, majority re-elects, ops continue. State_hash gossip mismatch test: inject deliberate bug → mismatch detected within N ops.
    - **Acceptance**: 100k Transfers replicated; state_hash equal across replicas; p99 commit < 500μs for local cluster.

- [NEW v2] **exec-vm v1.5: block-stm read/write-set tracking (impl)**
  - [ ] **Build**: `crates/exec-vm/src/parallel/rwset.rs` — per-tx read-set + write-set tracking. (~3 hrs)
    - **Why**: block-stm is the only credible path to a parallel EVM at bar (b). The core invariant: optimistically execute N txs in parallel, track per-tx read-set + write-set, validate at commit; on conflict re-execute. Mirror Aptos's block-stm paper and Reth's parallel-EVM PR (Paradigm). This file is THE building block — without it, no parallel exec.
    - *Back-of-envelope* (target: ≥2× speedup at 8 cores on low-conflict block; **per-tx RwSet overhead < 200 ns** vs sequential exec):
      Sequential mainnet block exec at ~120 ms / 250 txs = ~480 µs/tx. Block-stm adds (a) RwSet `reads.push((key, version))` per SLOAD (~10 ns) × ~50 SLOADs/tx = ~500 ns, (b) `writes.push((key, value))` per SSTORE (~10 ns) × ~10 SSTOREs/tx = ~100 ns, (c) MultiVersionStore lookup per SLOAD (~30 ns BTreeMap range + version pick) × 50 = ~1.5 µs, (d) validation phase (replay reads, compare versions) ~1 µs. Total overhead ~3-4 µs/tx ≈ 1% of sequential exec time ✓. The critical constraint: per-`reads.push`/`writes.push` must NOT allocate. `ArrayVec<(StorageKey, Version), MAX_READS=4096>` is the budget — txs reading more than 4096 slots fall back to sequential exec (rare; 99.9th-pct mainnet tx reads <500 slots).
    - **Read first**: Aptos block-stm paper "Block-STM: Scaling Blockchain Execution by Turning Ordering Curse to a Performance Blessing"; Reth `crates/revm/src/parallel.rs` PR; Diem's `block_stm.rs` original Move implementation.
    - **Design**:
      ```rust
      pub struct RwSet {
          reads: ArrayVec<(StorageKey, Version), MAX_READS>,
          writes: ArrayVec<(StorageKey, StorageValue), MAX_WRITES>,
      }
      pub struct StorageKey { addr: Address, slot: U256 }
      pub struct Version { tx_idx: u32, incarnation: u32 }
      // multi-version data: per StorageKey, list of (Version, Value)
      pub struct MultiVersionStore {
          slots: dashmap::DashMap<StorageKey, BinaryHeap<VersionEntry>>,
      }
      pub struct VersionEntry { tx_idx: u32, incarnation: u32, value: StorageValue }
      ```
      **Invariants**: (i) tx N reads version ≤ N (sees ALL completed earlier writes); (ii) tx N writes are tagged (N, incarnation) — incarnation increments on re-execution; (iii) read-set captures versions read so validator can detect "did anyone in [0, N) write to that key with a higher version after I read it?"; (iv) max size: txns reading more than MAX_READS reject + execute sequentially.
    - **Build steps**: 1. (~15 min) define `RwSet`, `Version`, `StorageKey`. 2. (~30 min) `MultiVersionStore::read(key, tx_idx) -> (Version, Value)` — walk version list, pick highest version < tx_idx that's `Committed` (not `Estimate`). 3. (~30 min) `MultiVersionStore::write(key, tx_idx, incarnation, value)` — insert into heap; if existing entry for (tx_idx, incarnation), replace. 4. (~30 min) `RwSet` instrumentation: revm's `Database` trait wrapped → each `storage()` call appends to reads; each commit appends to writes. 5. (~30 min) validation: replay reads; for each (key, version) check current store's read-version still equals; if not, mark conflict + re-execute. 6. (~25 min) `Estimate` vs `Committed` distinction: tx N in-progress writes are `Estimate`, finalize to `Committed` only after validation. 7. (~10 min) memory: stash incarnations per tx via Vec<RwSet> indexed by tx_idx.
    - **Pitfalls**: *Read-set collapse*: **Symptom**: tx reads 100 storage slots, RwSet grows huge → memory blows up. **Fix**: MAX_READS cap (e.g. 4096), fallback to sequential exec for large reads. *Write-set growth*: **Symptom**: same as above for writes; some contracts write 1000s of slots. **Fix**: MAX_WRITES cap; sequential fallback. *Hot-key contention*: **Symptom**: every tx reads/writes balanceOf(0xUSDC), every parallel exec re-executes due to conflict — speedup < 1×. **Fix**: classify "hot keys" upfront (per-block analysis); group hot-key txs into a sequential subgraph. *Estimate-as-final*: **Symptom**: tx reads Estimate value, commits using it; later that estimate gets invalidated. **Fix**: never return Estimate value to a reader — reader either waits or treats key as dependency.
  - **Expect to hit (perf) #1 — `Vec<(StorageKey, Version)>` `reads`/`writes` allocate on first push (bar (c) violation, hidden)**: instantiating `reads: Vec::new()` lazily and pushing per SLOAD. The first push triggers a 4-element allocation (~50 ns); subsequent doublings (`Vec::reserve` on capacity full) trigger more allocs — at ~50 SLOADs/tx with 4-8-16-32 doubling pattern, that's 4-5 allocs per tx × ~50 ns = ~250 ns per tx in pure malloc cost, AND the allocator contention serializes across the parallel worker threads (jemalloc's per-arena lock).
    - Fix: `reads: ArrayVec<(StorageKey, Version), MAX_READS>` — **stack-allocated**, fixed-size at compile time. Push is ~5 ns (one bounds check + write). Construction is ~10 ns (the ArrayVec header zero). Per-tx RwSet allocation cost: 0. Worker threads have zero allocator contention. Txs exceeding MAX_READS fall back to sequential exec — flagged as "wide-read" tx for the per-block scheduler.
    - Cost avoided: ~250 ns/tx allocator cost × 250 txs/block × 8 cores = ~500 µs/block reclaimed; plus the elimination of allocator-arena lock contention which was capping 8-core speedup at ~1.5× (vs the 2× target).
    - Muscle: `ArrayVec` (or other stack-bounded collections) on the hot path of any parallel worker — `Vec` introduces serialization through the global allocator that doesn't show in single-threaded benchmarks.   - **Expect to hit (perf) #2 — DashMap shard hash collision on hot key (e.g., USDC balanceOf) (bar (c)-ish violation, headlines the "high-conflict caveat")**: `MultiVersionStore::slots: DashMap<StorageKey, BinaryHeap<VersionEntry>>` with default 32 shards. Profile shows `RwLock::write` at ~80% CPU; 7 workers idle waiting for one.

The classification is what keeps high-conflict regression bounded at ≤20% (the W94 acceptance gate).
