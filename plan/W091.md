## Monday — `ConsensusBackbone` trait + the four inner seams (Build, bar c) — Phase 1 design

- [ ] [Venue] **Build (bar (c))**: `crates/consensus-vsr/src/backbone.rs` — the **call-site-facing `ConsensusBackbone` trait** (SM- and consensus-impl-agnostic) PLUS the **four inner seam traits** (`Quorum`, `Authenticator`, `ViewManager`, `EquivocationPolicy`) that a concrete replica composes. The whole point: call sites see only `ConsensusBackbone`; the CFT→BFT delta lives entirely in the four inner seams. (~total 6 hrs; Phase 1 today, Phase 2/3 Tuesday)

  - 🔧 **Why this matters**: this is the single artifact the entire BFT apex (W118–W143) stands on. If `ConsensusBackbone` leaks a quorum constant, an honest-replica assumption, a VSR view-number semantic, or a no-equivocation assumption, then promoting consensus to BFT means rewriting every call site — and the non-optional apex becomes unaffordable. The four traps that kill the seam: (1) baking `f+1`/`2f+1` into a method signature or a `const QUORUM` (BFT needs `2f+1`-of-`3f+1`); (2) a message path with no `verify()` hook (BFT needs signatures — retrofitting auth into the hot path later is the rewrite we're avoiding); (3) exposing VSR `view`/DVC semantics at call sites (BFT's pipelined rotation + timeout-certs differ); (4) assuming a replica never sends two conflicting messages (BFT must detect equivocation). A first cut WILL leak at least one — the Phase-2 "swap-compiles" tests are engineered to catch exactly that.

  - 🔧 **Decomposition prompt (silent test)**: the spec names no consensus protocol. The outer trait must express *propose / committed-notification / commit-point / applied-point / role* with **no quorum, no signature, no view-number, no equivocation** vocabulary. The four inner seams must each isolate exactly one CFT→BFT axis. If you cannot write a `VsrReplica` (CrashQuorum + TrustedPeers + RoundRobinView + AssumeNoEquivocation) AND sketch a `BftReplica` (BftQuorum + SignedPeers + PipelinedHotStuffView + DetectEquivocation) that BOTH implement the SAME outer trait with the SAME call sites — your decomposition leaked an assumption.

  - *Mental model*: there are **two levels**. The **outer trait** `ConsensusBackbone` is what the ledger, the matching engine, and `perp-dex-core` depend on — it speaks only *log positions and commit points*, never *how* consensus is reached. The **four inner seams** are what a concrete replica is *composed from* — each isolates one place where CFT and BFT differ. VSR v1.0 = the four trivial/cheap seam impls; the BFT apex = the four real seam impls. The outer trait is frozen at v1.0 (acceptance #9); the apex only adds new *impls of the inner seams*. The order/event log, the settlement journal, and the replicated SM all ride the outer trait's committed-op stream (the §4A one-log lock) — so they too survive the swap.

  - *Contract* (signature-level only — NEVER the body):
    ```rust
    // ===== OUTER: call-site-facing. consensus-IMPL-agnostic AND SM-agnostic. Frozen at v1.0 + the O5 amendment (W118). =====
    pub struct OpNumber(pub u64);          // COMMIT-TIME-ONLY log position (O5 amendment): appears ONLY on a Commit,
                                           // NEVER returned from propose. Survives VSR op-number AND BFT block-height.
    pub struct ProposalHandle(u64);        // [O5 AMENDMENT] opaque correlation token returned by propose; Copy, PartialEq, Eq.
    pub enum Role { Leader { view: u64 }, Follower { leader: ReplicaId, view: u64 } } // `view` = opaque epoch counter, NOT VSR-specific

    pub trait ConsensusBackbone {
        type Op;                            // the replicated command (Transfer | Order | the venue op union)
        type Commit<'a>: ConsensusCommit<Op = Self::Op> where Self: 'a;  // a committed entry + its proof, opaque to callers
        /// Leader-only. Append `op` to the replicated log; return a correlation HANDLE (NOT a position). Non-blocking.
        /// [O5 AMENDMENT] BFT cannot know the committed OpNumber at propose time (O4 densification assigns it at commit,
        /// and an orphaned proposal never gets one) — so propose returns an opaque handle, not an OpNumber.
        fn propose(&mut self, op: Self::Op) -> Result<ProposalHandle, NotLeader>;
        /// Drain newly-committed entries in strict log order. THE ONLY path an SM applies from.
        fn drain_committed(&mut self, sink: &mut dyn FnMut(Self::Commit<'_>));
        /// [O5 AMENDMENT — the dedicated abandonment surface] Drain proposals that will NEVER commit
        /// (BFT: orphaned-before-slot via pacemaker view-change; VSR: view-change supersession). Liveness guarantee:
        /// every handle terminates EXACTLY ONCE — it appears here XOR in drain_committed (proposal_handle()), never both/neither.
        fn drain_abandoned(&mut self, sink: &mut dyn FnMut(ProposalHandle));
        /// Highest OpNumber PROVEN committed. `finality_status` (acceptance #4) reads ONLY this.
        fn commit_point(&self) -> OpNumber;
        /// Highest OpNumber locally APPLIED to the SM. The read-after-commit projection (acceptance #5) reads this.
        fn applied_point(&self) -> OpNumber;
        fn role(&self) -> Role;             // leadership only — NO quorum size, NO view-change internals leaked
    }
    pub trait ConsensusCommit {
        type Op; fn op_number(&self) -> OpNumber; fn op(&self) -> &Self::Op;
        /// [O5 AMENDMENT] Correlate a commit back to the local proposal: Some(handle) on the proposer, None on
        /// followers / replay. This is how the ledger resolves a pending entry without watching an OpNumber.
        fn proposal_handle(&self) -> Option<ProposalHandle>;
    }

    // ===== INNER seam #1: QUORUM — no constant baked anywhere. =====
    pub trait Quorum {
        fn threshold(&self, n_replicas: usize) -> usize;       // VSR: n/2+1 (f+1 of 2f+1) ; BFT: n − ⌊(n−1)/3⌋ (= n − f;
                                                               //   equals 2f+1 only on the 3f+1 lattice, n=3f+1)
        fn reached(&self, acks: usize, n: usize) -> bool { acks >= self.threshold(n) }
        fn intersection_safe(&self, n: usize) -> bool;         // VSR: any two quorums share ≥1 ; BFT: share ≥1 HONEST
    }
    // ===== INNER seam #2: AUTHENTICATOR — message auth on the transport, present from day one. =====
    pub trait Authenticator {
        type Cred: Copy;                                       // VSR: () or 8-byte MAC ; BFT: signature / partial-sig
        fn authenticate(&self, msg: &[u8]) -> Self::Cred;      // outbound
        fn verify(&self, msg: &[u8], cred: &Self::Cred, from: ReplicaId) -> bool;  // inbound (MUST be on the recv path)
    }
    // ===== INNER seam #3: VIEW MANAGER — leader election + view-change / synchronization. =====
    pub trait ViewManager {
        type ViewMsg;        // VSR: DoViewChange evidence ; BFT: Timeout message — DIFFERENT shapes, so ASSOCIATED (FIX 3)
        type NewViewCert;    // VSR: DVC quorum cert    ; BFT: Timeout-Certificate (TC) — associated, not concrete-shared
        fn leader_for(&self, view: u64, n: usize) -> ReplicaId;            // VSR: view % n ; BFT: pipelined rotation
        fn on_timeout(&mut self, view: u64) -> ViewChangeAction;           // VSR: StartViewChange ; BFT: pacemaker advance
        fn certify_new_view(&self, evidence: &[Self::ViewMsg]) -> Option<Self::NewViewCert>; // VSR: DVC quorum ; BFT: TC
    }
    // FIX 3 rationale: ViewMsg/NewViewCert were concrete shared types — DVC-evidence (VSR) and TC (BFT) differ in shape,
    // so leaving them concrete would make O2 an INTERFACE change at W118. As associated types they are impl-only
    // instantiations: VsrView{ViewMsg=DoViewChange, NewViewCert=DvcQuorumCert}; BftView{ViewMsg=Timeout, NewViewCert=Tc}.
    // ===== INNER seam #4: EQUIVOCATION POLICY — conflicting-message detection, inert under VSR. =====
    pub enum EquivocationVerdict { Ok, Equivocation(Evidence) }
    pub trait EquivocationPolicy {
        /// Called for EVERY (from, view, slot, digest) the backbone observes — on the hot path.
        fn observe(&mut self, from: ReplicaId, view: u64, slot: OpNumber, digest: Digest) -> EquivocationVerdict;
    }

    // ===== A concrete replica is COMPOSED from the four seams. The swap = changing these four type params. =====
    pub struct Replica<SM, Q: Quorum, A: Authenticator, V: ViewManager, E: EquivocationPolicy> { /* ... */ }
    impl<SM, Q, A, V, E> ConsensusBackbone for Replica<SM, Q, A, V, E> { /* ... */ }
    // VSR v1.0 (this week):  Replica<SM, CrashQuorum, TrustedPeers, RoundRobinView, AssumeNoEquivocation>
    // BFT apex (W118-W143):  Replica<SM, BftQuorum,   SignedPeers,  PipelinedHotStuffView, DetectEquivocation>
    ```

  - *Back-of-envelope* (bar (c) — the abstraction MUST be free under VSR): the outer trait is used on the hot path (`drain_committed` per commit; `commit_point`/`applied_point` per projection read). Budget: **0 ns added vs a hand-wired VSR**. The mechanism: `Replica<...>` is **generic** (monomorphized), so `TrustedPeers::verify → true` and `AssumeNoEquivocation::observe → Ok` are `#[inline]` const-folded to nothing — the optimizer deletes the call. The trap: if call sites take `&mut dyn ConsensusBackbone` *and* the four seams are `dyn` too, every `verify`/`observe` is an indirect call (~2–5 ns + a missed inline) × per-message × 100k+/s = ~0.5–1 ms/sec of pure vtable tax, plus it defeats the dead-code elision that makes auth free under VSR. **Resolution: the four inner seams are concrete generic params on `Replica` (monomorphized, zero-cost); only the OUTER `ConsensusBackbone` may be `dyn` at the `perp-dex-core` boundary (one indirect call per commit batch, amortized — acceptable).** Verify with `cargo asm` in Phase 2.

    - R2. **No quorum constant** anywhere in the crate (`grep -nE 'f *\+ *1|2 *\* *f|n */ *2 *\+ *1'` finds matches ONLY inside `impl Quorum for CrashQuorum`/`BftQuorum`, never in `Replica` core or the outer trait).
    - R3. `Quorum::threshold` is the ONLY source of quorum size; `Replica` core calls `self.quorum.reached(acks, n)` — never an inline count comparison.
    - R4. Every inbound consensus message passes through `Authenticator::verify` BEFORE it affects state; every outbound through `authenticate`. (The recv path has exactly one verify call site.)
    - R5. `Authenticator::Cred` is an associated type; `()` for VSR is legal and the verify must monomorphize to `true` with **zero retained instructions** (asm test).
    - R6. Leader identity comes ONLY from `ViewManager::leader_for`; `Replica` never computes `view % n` inline.
    - R7. View-change is driven by `ViewManager::on_timeout` + `certify_new_view`; the outer trait exposes only `role()` (leadership), never the view-change protocol.
    - R8. `EquivocationPolicy::observe` is called on the message path for every `(from, view, slot, digest)`; `AssumeNoEquivocation::observe` returns `Ok` and monomorphizes to nothing (asm test).
    - R9. **Swap test (the headline)**: a `BftStub` = `Replica<NoopSM, BftQuorum, SignedPeersStub, RoundRobinView, DetectEquivocation>` **compiles and satisfies `ConsensusBackbone`** with ZERO change to the trait or to a sample call site (`fn use_consensus<B: ConsensusBackbone>(b: &mut B)`). (BFT is NOT implemented — `SignedPeersStub::verify` may be `todo!()` at runtime; it must TYPE-CHECK.)
    - R10. `SettlementId`, `finality_status`, and the two projection contracts are expressed in terms of `commit_point()` / `applied_point()` — never VSR internals (carried-down v1.0 locks; see Thursday).
    - R11. `OpNumber` is the only log-position type crossing the trait boundary; VSR op-number and BFT height both map onto it (newtype, `Copy`, monotonic).
    - R12. Zero allocations in `drain_committed` / `commit_point` / `applied_point` (dhat).
  - **Design walk-through** D1..D10 — answer in the design doc; no peeking at TigerBeetle/HotStuff source until Phase 3:
    - D1. **Outer-trait surface minimization.** For each of {propose, drain_committed, commit_point, applied_point, role}, write the ONE sentence a call site needs and prove none requires quorum/auth/view/equivocation vocabulary. Where does the commit *proof* live? (Inside `Commit<'_>` as an opaque `Certificate`; callers can pass it on — e.g. to a light client — but never inspect its shape.)
    - D2. **Quorum seam.** Property table: `CrashQuorum::threshold(n) = n/2 + 1`; `BftQuorum::threshold(n) = n − ⌊(n−1)/3⌋` (= n − f; **equals 2f+1 only on the 3f+1 lattice, n=3f+1**). For n=4: VSR→3, BFT→3 (BFT needs n≥4 for f=1). For n=7: VSR→4, BFT→5. For n=5 (off-lattice): VSR→3, BFT→4 — note the textbook 2f+1 form `2*⌊(n-1)/3⌋+1` gives 3 here, and two 3-quorums of 5 can intersect in exactly ONE (possibly Byzantine) node → below the intersection bound. Show the `Replica` core line is `if self.quorum.reached(acks, self.n) { commit }` for BOTH. What breaks if a `const` leaks? (BFT under-counts → commits on f+1 → safety violation under 1 Byzantine.)
    - D3. **Authenticator seam.** VSR `TrustedPeers`: `Cred = ()`, `authenticate → ()`, `verify → true`. BFT `SignedPeers`: `Cred = Signature`, `authenticate → sign(sk, msg)`, `verify → pk[from].verify(msg, sig)`. Show the recv path is `if !self.auth.verify(&buf, &cred, from) { return Drop }` for BOTH — the ONLY change BFT needs is the type param. **Where is the cost?** (Under VSR: zero, monomorphized. Under BFT: a signature verify ~20–50 µs/message — a real hot-path cost the apex's latency target X must absorb; flag as open question O1.)
    - D4. **ViewManager seam.** VSR: `leader_for(view,n) = view % n`; `on_timeout → StartViewChange(view+1)`; `certify_new_view` = DVC quorum of DoViewChange msgs. BFT: `leader_for` = pipelined rotation (leader-per-height); `on_timeout` = pacemaker `advance_round` + broadcast Timeout; `certify_new_view` = a Timeout-Certificate (TC) of `2f+1` Timeouts. Show `role()` returns `Leader{view}`/`Follower{leader,view}` in BOTH. **(FIX 1 — O5 leader-stability leak):** `role()` is **purely informational** (leadership for *routing*); it is **NEVER** the trigger for draining pending state. Under VSR a transition ≈ failover (rare); under BFT pipelined, `leader_for` rotates **leader-per-height**, so `role()` flips every height — draining on a role transition would drop in-flight ops and emit spurious errors on every rotation (type-checks, passes `bft_stub_compiles`, breaks at the W135 swap). Therefore the ledger keys its drain on **op-level abandonment derived from the committed stream** (a proposed `OpNumber` that the log fills with a *different* op = superseded = abandoned), and `role()` transitions are explicitly **NOT** assumed rare.
    - D5. **Equivocation seam.** VSR `AssumeNoEquivocation::observe → Ok` (crash model: replicas don't lie). BFT `DetectEquivocation::observe`: store first `digest` per `(from, view, slot)`; a second *different* digest → `Equivocation(Evidence{from, view, slot, d1, d2})`. Where does the backbone call `observe`? (On every proposal/vote ingest, on the hot path.) Why must the CALL exist under VSR even though it's inert? (So adding BFT is a seam-impl swap, not a new call site threaded through the message path — the exact rewrite we're banning.)
    - D6. **Commit-rule abstraction (the subtle one).** VSR commits op X when `quorum.reached(prepare_oks)`. Pipelined HotStuff commits X only when a *3-chain* (QC→QC→QC) extends it (commit lags by k views). The OUTER trait exposes only `commit_point()` (monotonic) — so the *rule* lives in `Replica` core + the seams. **Does any call site assume propose→commit within one round-trip?** Audit: the ledger `tx_pending` waits for `drain_committed` (no timing assumption ✓); the projection reads `commit_point`/`applied_point` (no timing assumption ✓). Conclusion: the pipeline depth is invisible to call sites — but it changes latency, which is why the apex has a numeric target X. Flag the pipeline-depth question as O2.
    - D7. **Certificate formation = Quorum × Authenticator (the coupling).** Under VSR a "certificate" is just *quorum-many PrepareOk counted* (`Cred = ()`). Under BFT a QC is *quorum-many partial signatures aggregated* (`Cred = Signature`). The seam: `Commit<'_>::certificate()` returns an opaque `Cert` the `Replica` builds from `(quorum, creds)`. Show the builder is generic: `Cert::from_acks(threshold, creds: &[A::Cred])`. What must NOT leak: a `count: usize`-based certificate that a BFT impl can't satisfy. Flag the cert-shape question as O3.
    - D8. **The `dyn` boundary.** `perp-dex-core` holds `Box<dyn ConsensusBackbone<Op = VenueOp>>` (acceptance #9 — depends on the trait). The four inner seams are concrete on the chosen `Replica`. Show: one indirect call per `drain_committed` batch (amortized over the batch) is the ONLY vtable cost; the per-message `verify`/`observe` stay monomorphized inside the impl. Why not `dyn` on the inner seams? (Kills inlining → auth/equivocation no longer free under VSR → bar-(c) violation.)
    - D9. **`OpNumber` mapping.** VSR op-number is contiguous from 1. BFT height may skip (a view with no decision). Does `OpNumber` need to be contiguous for the ledger? (Yes — the journal replay + idempotency rebuild assume contiguity; W74 client_table.) So the BFT impl must *densify* (assign contiguous `OpNumber` to *committed* entries, distinct from BFT height). State this as a constraint the BFT impl must honor; the trait stays clean. Flag as O4.
    - D10. **Pre-mortem (load-bearing — the leak that kills the apex):** write the EXACT trace where a "convenient" outer-trait method `fn on_prepare_ok(&mut self, from: ReplicaId)` (1) makes the ledger call `backbone.on_prepare_ok(...)` directly, (2) bakes the VSR counting model into the call site, (3) so the BFT swap (where commitment is a QC of signatures, not a count of acks) requires changing the ledger — the rewrite acceptance #9 forbids. Then state the fix: the outer trait NEVER exposes ack-counting; commitment is observed only via `drain_committed`/`commit_point`. The four seams own *how* commitment happens.
    - **Anti-shortcut audit** (obvious reach + why wrong HERE):
      - `const QUORUM_F` / inline `acks > n/2` → wrong: BFT needs `2f+1`; the constant is the leak. Use `Quorum::threshold`.
      - skip the `verify` call under VSR "to save a branch" → wrong: BFT must add it to the message path; absent now = a hot-path rewrite later. Keep it; monomorphization makes it free under VSR.
      - `dyn` the four inner seams "for symmetry with the outer trait" → wrong: kills inlining, defeats zero-cost VSR, bar-(c) violation.
      - expose `view_number()`/`prepare_ok()` on the outer trait → wrong: leaks VSR semantics; BFT views differ.
      - a second hot-path log for BFT later → wrong (the v3 trap): the apex is a *backend swap behind this seam*, the log stays the one VSR/BFT log; fan-out reads a projection (W84).
