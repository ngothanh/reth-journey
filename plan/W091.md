    - *Mental model*: `ReplicatedLedger` is the *gap layer* between bytes-on-wire (VSR Prepare/Commit messages) and bytes-in-SM (ledger Transfer ops). The protocol owns ordering and durability; the SM owns determinism and dedupe; this file owns the hand-off — and the hand-off is where the ns and the correctness bugs live.
    - *Contract* (signature-level only — never the body):
      ```rust
      pub struct ReplicatedLedger {
          sm: LedgerSM,
          replica: NormalReplica,
          pool: MessagePool,
          tx_pending: FixedMap<TransferId, PendingEntry>, // leader-only, shard-owned, no Arc/Mutex
      }
      impl ReplicatedLedger {
          /// Client entry point (leader only). Encodes + pushes to VSR; registers tx_pending; returns immediately.
          pub fn submit(&mut self, op: Transfer) -> oneshot::Receiver<TransferResult>;
          /// THE ONLY path that calls sm.apply(). Invoked by the VSR replica on commit, in-line on the shard thread.
          fn on_committed(&mut self, op_num: u64, op: &Transfer);
          fn on_view_change(&mut self, new_view: u64); // drains tx_pending with Err(LeaderChanged)
      }
      struct PendingEntry { submitted_at: Instant, sender: oneshot::Sender<TransferResult> }
      ```
    - *Back-of-envelope* (bar (c)): budget = commit P99 < 500 µs at 100 k Transfers/s. Per-Transfer cross-core hop if apply lives off-thread ≈ cache-line bounce (~30-100 ns L2-coherency) + crossbeam channel push/pop (~50 ns) + waker fire (~30 ns) ≈ **~150 ns/Transfer** × 3 replicas ≈ ~450 ns × 100 k/s = **~45 ms/sec** burned on hops alone, and the queue-depth-under-burst inflates P99 from ~7 µs to ~1.5 ms (a **~200× cliff** at the tail). In-line apply on the protocol thread reclaims all of it. Mutex on `tx_pending`: ~25 ns uncontended × 200 k ops/s (insert+remove) = ~5 ms/sec, with 1-10 µs contention spikes living in P99.

      - R3. `tx_pending` lives on leader only; per-shard thread owns it lock-free (no `Arc<Mutex<_>>`).
      - R4. `on_committed` runs on the same per-shard pinned core as the VSR protocol thread (W85 runtime-thread-per-core) — zero cross-thread hop between commit and apply.
      - R5. Sustained throughput ≥ 100 k Transfers/sec on 3-replica loopback; commit P99 < 500 µs.
      - R6. State-hash gossip every 1000 ops; mismatch → `assert_unreachable!("state divergence at op_num={n}, our_hash={h1}, peer_hash={h2}")`.
      - R7. Leader-change: on `Status::ViewChange`, drain `tx_pending` with `Err(LeaderChanged)` so clients retry.
      - R8. Idempotency on retry: SM-layer dedupe by `TransferId` via `processed_ids` DERIVED from journal replay (not separately persisted); replay of a committed op is a no-op returning the cached result.
      - R9. `tx_pending` leak prevention: TTL eviction per entry; periodic sweep on idle.

    #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

    Ordered newbie → expert — the ladder you actually walk.

    - **(NEWBIE) When `test_apply_only_via_on_committed` fires:**
      - Symptom: instrumentation shows `LedgerSM::apply` called from `submit()` on the leader, before VSR commit.
      - Why: the "leader knows the result, why wait" fast-path — applies locally, then replicates. Followers then apply on commit, so leader and followers diverge if the op is later rejected during view-change.
      - Fix: leader and followers walk ONE path — `submit()` only encodes + pushes to VSR; `apply()` happens exclusively in `on_committed`.
      - Cost avoided: a class of split-brain divergence bugs; no ns cost, this is correctness.
      - Muscle: in a replicated SM, there is exactly one apply path and it is post-commit. Reapplies at: W74 matching-engine raft commit → order-book apply, W100 mini-db WAL commit → memtable insert.

    - **(SENIOR) When `bench_commit_p99_under_500us_loopback` reports P99 ~1.5 ms (P50 ~7 µs):**
      - Symptom: P50 fine, P99 = 1500 µs (3× over); profiler shows ~15% in `crossbeam::channel::send`/`recv`.
      - Why: VSR replica on the network/protocol core; ledger SM on a separate "apply core". Each commit crosses cores: op-payload cache-line bounce (~30-100 ns L2-coherency) + channel push/pop (~50 ns) + waker (~30 ns) ≈ ~150 ns × 3 replicas = ~450 ns/Transfer; queue-depth-under-burst inflates the tail.
      - Fix: VSR replica + ledger SM share one shard (W85). `replica.commit_op_now()` invokes `self.sm.apply()` in-line on the same thread — no channel, no waker.
      - Cost avoided: ~450 ns/Transfer × 100 k/s = ~45 ms/sec reclaimed; ~200× P99 tail cliff (1.5 ms → ~7 µs) closed. **(bar (c) violation)** — the off-thread design disqualifies the crate from its latency bar.
      - Muscle: in any "protocol + state machine" design, SM apply lives on the protocol committer's thread; cross-thread handoffs are protocol bugs that cost real ns AND P99 variance. Reapplies at: W74 matching-engine raft commit → order-book apply, W82 matching-engine MBO feed publication, W100 mini-db WAL commit → memtable insert.

    - **(SENIOR) When `test_no_mutex_in_apply_path` / `test_zero_allocs_on_committed` fire on `Arc<Mutex<HashMap<TransferId, oneshot::Sender>>>`:**
      - Symptom: asm shows a `lock cmpxchg` in `on_committed`; dhat shows HashMap rehash allocs. Written for "easy access from `submit()` and `on_committed`".
      - Why: convenience pattern; Mutex acquire ~25 ns uncontended, 1-10 µs contended. At 100 k op/s × 2 accesses/op = 200 k Mutex ops/s × ~25 ns = ~5 ms/sec on locking; tail exposes 1-10 µs spikes in P99; HashMap growth allocates on the hot path.
      - Fix: shard-owned `tx_pending: FixedMap<TransferId, PendingEntry>` (no Arc, no Mutex), pre-sized for MAX_INFLIGHT. Both `submit()` (via the shard mailbox) and `on_committed` (on the shard thread) access it lock-free, zero-alloc.
      - Cost avoided: ~5 ms/sec lock overhead + 1-10 µs P99 spikes + per-op allocs removed. **(bar (c) violation)**.
      - Muscle: thread-per-core (W85) makes `Mutex<Map>` on the apply path redundant — any one left is a P99 hazard; pre-size maps so the hot path never allocates. Reapplies at: W82 matching-engine order-book state, W92 ledger AccountMap, W74 matching-engine PriceLevel, W77 messaging-aeron `Image` state.

    - **(SENIOR) When `test_leader_change_drains_tx_pending` leaves senders hanging:**
      - Symptom: after forced view-change, the 100 pending `oneshot::Receiver`s never resolve; clients hang forever.
      - Why: view-change transitions `Status` but nothing touches `tx_pending`; the leader can no longer commit those ops and the new leader doesn't know about them.
      - Fix: hook `on_view_change` to drain `tx_pending`, sending `Err(LeaderChanged)` on each sender; clients retry against the new leader (idempotency makes the retry safe).
      - Cost avoided: client-visible hangs; correctness/liveness.
      - Muscle: every limbo state (in-flight at view-change) needs an explicit drain with a retryable error. Reapplies at: W100 mini-db client retry on failover, W82 matching-engine session reset.

    - **(SENIOR) When `test_tx_pending_ttl_cleanup` shows the map growing after disconnects:**
      - Symptom: 10 k clients connect, submit, disconnect without consuming the result; `tx_pending` size stays 10 k an hour later.
      - Why: `oneshot::Sender::Drop` fires on disconnect but the ledger never observes it; the entry sits forever.
      - Fix: `PendingEntry { submitted_at, sender }`; a low-priority sweep (every 1 s, or opportunistic one-eviction per `on_committed` via a circular cursor) evicts entries older than 30 s.
      - Cost avoided: unbounded memory growth → OOM; a leak-prevention strategy is mandatory for any pending map.
      - Muscle: pending-entry maps need an explicit TTL/leak-prevention strategy. Reapplies at: W100 mini-db request tracking, W82 matching-engine pending-order map.

    - **(SENIOR · negative-control) When `test_state_hash_mismatch_fails_loud` silently continues (and/or the clean control panics):**
      - Symptom: deliberate corruption → gossip shows mismatch → no panic, replicas keep diverging. (Or: the clean control panics — the compare is comparing pre-apply snapshots.)
      - Why: compare done via `if mine != peer { warn!() }` — a warn is not fail-loud. (Control false-panic: hashing at the wrong point in the apply cycle.)
      - Fix: `assert_eq!(mine, peer, "state divergence at op_num={n}, our_hash={h1}, peer_hash={h2}")` computed at the post-commit boundary; service crashes, operator paged, root-cause before restart.
      - Cost avoided: silent permanent divergence — the worst bar-(c) failure (undetectable corruption shipped to clients). **(bar (c) violation)**.
      - Muscle: state divergence is unrecoverable; the only safe response is fail-loud — and the negative control proves the detector fires only on real divergence. Reapplies at: W92 v1.0 SHIP invariant violation, W77 messaging-aeron message-loss assertion, W82 matching-engine order-book consistency.

    - **(EXPERT · cross-primitive) When `test_idempotent_replay_after_leader_change` shows double-apply (balance 70 → 40):**
      - Symptom: original committed; new leader committed the retry; balance dropped twice (expected one no-op).
      - Why: new leader has the op in the journal but no `processed_ids` table — the retry applies fresh. The dedupe state wasn't reconstructed on view-change.
      - Fix: `processed_ids: FixedMap<TransferId, TransferResult>` is DERIVED from journal replay. On leader change, the new leader replays committed ops and populates `processed_ids` BEFORE applying any new op; `on_committed` checks `if let Some(r) = processed_ids.get(&op.transfer_id) { return r.clone(); }`.
      - Cost avoided: silent funds-double-spend — a ledger-disqualifying correctness bug. **(bar (c) violation)**.
      - Muscle: idempotency belongs at the SM layer, DERIVED from the journal (single source of truth) — never a separately-persisted table needing 2-phase commit. Reapplies at: W100 mini-db client retry idempotency, W82 matching-engine OrderId dedupe.

    - 🔧 **Why this matters**: mirrors Aptos block-stm `MVMemory` — optimistically execute N txs in parallel, track per-tx read-set + write-set, validate at commit; on conflict re-execute. The 3 traps that bite a first attempt: (1) `Vec`-backed read/write sets that serialize parallel workers through the global allocator (invisible single-threaded, fatal at scale — caps 8-core speedup at ~1.5×); (2) a hot key (USDC `balanceOf`) funneling all workers through one `DashMap` shard lock (8-core runs SLOWER than 1-core); (3) validating against a stale snapshot instead of the current store (misses conflicts → wrong balances). First-attempt impls fail ≥1 Phase-2 test. Downstream consumers: W92 versioned-memory (`MultiVersionStore` extends this), W93 executor (validation phase consumes RwSet), W94 exec-vm v1.5 SHIP (8-core speedup gate).

    #### Phase 1 — Problem, prediction, design (~70 min, no code yet)

    - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/exec-vm/notes/91fri_rwset_prediction.md`:

    - *Mental model*: `RwSet` is a tx's *proof obligation* — "these are the versions I read; if any changed under me, my result is invalid." `MultiVersionStore` is the per-key version ledger that lets the validator check that obligation cheaply. Together they turn "did the world change under me?" into an O(reads) replay.
    - *Contract*:
      ```rust
      pub struct RwSet {
          reads:  ArrayVec<(StorageKey, Version), MAX_READS>,   // MAX_READS = 4096, stack-bounded
          writes: ArrayVec<(StorageKey, StorageValue), MAX_WRITES>, // MAX_WRITES = 512
      }
      pub struct MultiVersionStore { slots: DashMap<StorageKey, BinaryHeap<VersionEntry>> }
      struct VersionEntry { tx_idx: u32, incarnation: u32, value: StorageValue, state: SlotState } // Committed | Estimate
      impl MultiVersionStore {
          fn read(&self, key: StorageKey, by_tx: u32) -> ReadResult; // highest Committed < by_tx, or Estimate-dependency
          fn write(&self, key: StorageKey, by_tx: u32, inc: u32, v: StorageValue);
          fn validate(&self, rwset: &RwSet, tx: u32) -> Validity; // replay reads against CURRENT store
      }
      ```
    - *Back-of-envelope* (bar (b), but the perf is the point): sequential EVM ~480 µs/tx caps mainnet at ~520 tx/block-time. Per-tx RwSet overhead budget < 200 ns. `Vec::push` doublings (4→8→16→32) trigger ~4-5 reallocs/tx (~50 ns malloc each = ~250 ns/tx) and each realloc takes the jemalloc per-arena lock → serializes 8 workers. `ArrayVec::push` ≈ ~5 ns (one bounds check + write), 0 allocs. Hot-key DashMap shard lock: under a USDC-heavy block all 250 txs hit one shard's `RwLock<HashMap>` → effective parallelism = 1 (8-core SLOWER than 1-core).
    - **Requirements** R1..R10 — write in `crates/exec-vm/notes/91fri_rwset_design.md`:
      - R1. `RwSet { reads: ArrayVec<(StorageKey, Version), 4096>, writes: ArrayVec<(StorageKey, StorageValue), 512> }` — stack-bounded, zero-alloc.
      - R2. `MultiVersionStore { slots: DashMap<StorageKey, BinaryHeap<VersionEntry>> }` — per-key version list.
      - R3. Tx N reads return the highest version < N that is `Committed` (not `Estimate`).
      - R4. Tx N writes tagged `(N, incarnation)`; incarnation increments on re-execution.
      - R5. Validation: replay reads; for each `(key, version)` check the store's CURRENT read-version equals; mismatch = conflict = re-execute.
      - R6. Per-tx RwSet overhead < 200 ns vs sequential exec.
      - R7. 8-core speedup ≥ 2× on a low-conflict block; ≤ 20% regression on a high-conflict (USDC-heavy) block.
      - R8. Estimate vs Committed: in-progress writes are `Estimate`; a reader treats Estimate as a dependency (marks dependency, not silent skip); Estimate finalizes to `Committed` on validation pass.
      - R9. Hot-key bypass: per-block heuristic classifies hot keys (from the previous block's SSTORE stats); hot-key access uses a per-key `RwLock<(Version, Value)>`, not the DashMap shard.
      - R10. Txs exceeding MAX_READS / MAX_WRITES fall back to sequential exec (rare; 99.9th-pct mainnet tx reads < 500 slots).
    - **Design walk-through** D1..D9 — answer in the design doc; no peeking at the Aptos paper / Reth PR until Phase 3:
      - D1. Per-tx overhead: ~50 SLOAD × (5 ns ArrayVec push + 30 ns DashMap read) + ~10 SSTORE × 5 ns + ~1 µs validation ≈ ~3 µs/tx ≈ 0.6% of 480 µs. What dominates? (DashMap shard lookup.) Where can it shrink? (Hot-key bypass.)
      - **D2. Property table — read/write set storage** (fill in):

        | Option | allocs/tx | push latency | parallel-worker effect | verdict |
        |---|---|---|---|---|
        | `Vec` | ~4-5 (lazy + doublings) | ~5 ns amortized but realloc spikes | serializes via global allocator lock | fatal |
        | `ArrayVec<_, N>` | 0 | ~5 ns flat | no allocator contact | ✓ |

        Verify the Vec impl's alloc count with dhat (expect ~1000 for a 250-tx block).
      - D3. MAX_READS=4096 sizing: 99th-pct tx reads ~50 slots; 99.9th-pct < 500; DEX-router outliers up to ~3000. Why 4096 not 8192? (Memory: 4096 × (KeySize+VersionSize) ≈ 200 KB/tx; 250 txs ≈ 50 MB total.) Outliers fall back to sequential.
      - D4. `MultiVersionStore` per-key `BinaryHeap<VersionEntry>`. Why a heap not Vec/BTreeMap? (Read needs "highest Committed < N" — heap top-down walk is O(log K).) What if a key has 100 versions?
      - D5. Validation flow: tx N's RwSet captured during speculative exec; at commit, replay each `(key, version)` against the CURRENT store; mismatch (someone in [0,N) wrote with a higher version after N read) → invalid → re-execute (incarnation++).
      - D6. Estimate vs Committed: tx N mid-exec writes `Estimate(N, inc)`; tx M>N reads the same key. Option A: skip Estimate, return last Committed before N (risk: validates green but M's real dependency was N's Estimate → invalid). Option B: return Estimate, mark M dependent on N; if N invalidates, M invalidates. Pick B; document why A is a silent-correctness trap.
      - D7. Hot-key heuristic: per-block scan the previous block's SSTOREs; top 1% by write frequency = "hot"; populate `hot_keys: HashMap<StorageKey, RwLock<(Version, Value)>>` upfront; hot-key SLOAD/SSTORE bypass the DashMap. Why? A USDC-heavy block sends all 200/250 txs through one DashMap shard's `RwLock<HashMap>` → 8 workers see effective parallelism 1.
      - D8. Validation atomicity: the validator runs single-threaded on the scheduler. What stops a worker re-writing a tx's slot mid-validation? (Once a tx is marked `Validating`, workers don't write its slot; the validator's scan is a read-only snapshot.)
      - **D9. Pre-mortem (load-bearing)** — write the EXACT 5-step interleaving where two workers race a hot key and BOTH produce valid-looking RwSets but the merged effect violates sequential semantics: tx1 reads bal=100, writes 90; tx2 reads bal=100, writes 80; both validate against committed=100; merged = 80 but sequential = 70. State the fix invariant: validation must check tx2's read-version (committed, tx_idx=0) is STILL the highest committed < 2 at validate time; if tx1 committed in between, tx2 sees committed=90 → conflict → re-execute.
      - **Anti-shortcut audit**:
        - `Vec` for reads/writes → wrong: lazy alloc + doublings serialize parallel workers through the allocator lock.
        - plain `DashMap` for the store → wrong: a single hot key collapses all parallelism onto one shard lock.
        - validate against the exec-time snapshot → wrong: misses any write that landed between read and validate.
        - treat `Estimate` as `Committed` → wrong: silently drops a real dependency edge → non-deterministic result.
