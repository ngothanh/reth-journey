    #### Phase 1 — Problem, requirements, design (~70 min, no code yet)

    - **The problem this primitive solves**: a single `Box::new`/`HashMap::rehash`/`Vec::realloc` inside `apply()` injects ~50 ns to ~10 ms of allocator latency at unpredictable times. P99 commit latency jumps from <1 µs to **10+ ms** — a **10,000× violation** of v1.0's headline (P99 ≤ 1 µs single-shard). Allocator-driven tail latency cannot be hedged; the only fix is to never allocate. The pool is the artifact that proves this discipline.

    - **Requirements** — write in `crates/ledger-deterministic/notes/89mon_static_mem_design.md`:
      - R1. `TransferPool` allocates `Box<[MaybeUninit<Transfer>; MAX_TRANSFERS]>` (128 MB at 1 M × 128 B) **once** at startup; `acquire()`/`release()` is O(1) with **zero** heap touch.
      - R2. `AccountMap` is open-addressing robin-hood, `Box<[Slot<K,V>; N]>` allocated once; **no rehash, no growth**; `MapFull` returned past load factor 0.85.
      - R3. Hash function is deterministic across replicas (no per-process random seed) — Splitmix64 finalizer of `AccountId.as_u64()` or BLAKE3 truncated.
      - R4. Pool exhaustion surfaces as `Err(ExhaustedErr)` BEFORE `apply()` runs (backpressure path); apply itself never panics on pool exhaustion.
      - R5. dhat audit reports **0 allocations** during a 1 M-Transfer apply loop (preamble allocs excluded).
      - R6. `MaybeUninit<Transfer>` slot is initialized via `slot.write(Transfer::default())` on every `acquire()` — never read uninit.
      - R7. Per-Transfer apply budget: ~180 ns P50, ~400-600 ns P99 (acquire 10 ns + 2× lookup 60 ns + arithmetic 5 ns + 2× update 40 ns + journal 50 ns + state-hash 3 ns + release 10 ns).
      - R8. cargo-deny `disallowed_types = ["std::collections::HashMap", "std::vec::Vec"]` in the `state_machine` module (allowed in tests/setup via `#[allow]`).

    - **Design walk-through** — answer each in your design doc; no peeking at TigerBeetle `state_machine.zig`/`message_pool.zig` until Phase 3:
      - D1. Why is the per-Transfer budget so tight (1 µs P99)? Trace one allocator-free apply path step-by-step (~9 sub-operations) and assign each a nanosecond cost. Which step is the largest budget consumer, and why? Compare with what a single `Box::new` would cost.
      - D2. Pool layout: which of `Vec<Transfer>`, `Box<[MaybeUninit<Transfer>; N]>`, or `Box<[Transfer; N]>` should back the pool? Why `MaybeUninit` over zero-init? What goes wrong if you use `Vec<Transfer>` with `capacity = N`?
      - D3. Free-slot tracking: stack-like `ArrayVec<u32, N>` of free indices, vs `BitSet<N>` of in-use bits, vs both? Write the LIFO `acquire()` flow with each option; which is faster? Which catches double-release?
      - D4. AccountMap slot enum: `enum Slot { Empty, Tombstone, Occupied{...} }` vs `struct Slot { state: u8, hash_top: u32, key, value, probe_dist }`. Compute size_of for each at `K=u128, V=Account(96B)`. Which fits in one cache line? Which causes a 2-line read per probe?
      - D5. Robin-hood vs linear probing: under uniform-random keys at load 0.5 both have ~1.5 avg probe distance. Where do they diverge? Write the variance argument: max probe distance is `O(log N)` for robin-hood vs `O(N)` worst for linear. Which tail (P50, P99, P99.99) is the killer?
      - D6. Hash function: why is `DefaultHasher` (SipHash-1-3) wrong here? List three failures: per-process random seed → replica nondeterminism; 30 ns hash cost; adversarial clustering. What's the smallest hash that hits all three (deterministic + ~3 ns + adversarial-OK)?
      - D7. Pool exhaustion handling: where does the back-pressure check live? At RPC ingress (count `in_flight`)? At Transfer-parse boundary? Inside `acquire()` itself? Answer: pool must be a hard ceiling — `acquire()` returns `None`, caller maps to `Reject(ErrTooManyInFlight)` before `apply()`. Apply never observes pool exhaustion.
      - D8. **Pre-mortem (load-bearing)**: write a 5-step interleaving where a forgotten `release()` on the error path leaks a slot. Over 1 M apply cycles, every 0.01% error rate leaks 100 slots/day → pool exhausted in 27 days. What RAII pattern guarantees release even on panic? (Hint: `PooledTransfer<'a>` with `Drop` → `pool.release(self.slot_id)`.)

    - **When `test_transfer_pool_maybeuninit_no_read_before_write` fires "encountered uninitialized memory":**
      - Symptom: miri reports a read of uninit bytes at the `&mut Transfer` returned by `acquire()`; usually because consumer code reads a field before writing.
      - Why: `MaybeUninit<Transfer>` slots are NOT zero-initialized — the byte pattern is whatever the allocator returned (or stale from a previous use). Returning `&mut` to an uninit slot lets the consumer's first read be UB.
      - Fix: `acquire()` always calls `slot.write(Transfer::default())` then returns `&mut *slot.as_mut_ptr()`. Verify the default ctor is cheap (~5 ns). Alternative: `release()` zeros on return — pick one, document.
      - Muscle: `MaybeUninit` is an unsafe contract; the init-before-read responsibility lives in the pool, not the consumer. Reapplies at: W89 Thu MessagePool's `acquire()` zero-pass, W82 matching-engine Order slot init, W90 io_uring buffer init.

    - **When `test_account_map_robin_hood_bounds_probe_distance` reports max probe distance ~100+:**
      - Symptom: at load 0.5 the average probe is fine (~1.5) but max blows out to 80-150 slots; P99 lookup latency cliff at ~500 ns.
      - Why: you implemented linear probing without the robin-hood swap. Insert clusters when collisions occur and any clustering causes variance explosion at the tail.
      - Fix: in `insert()`, track `new_entry.probe_dist`; at each probe step, if `existing_slot.probe_dist < new_entry.probe_dist`, swap them and continue probing with the displaced entry. Property: max probe distance bounded by `O(log N)` ≈ 24 for 16 M slots.
      - Muscle: in hash tables on the bar-(c) hot path, variance matters more than mean. Robin-hood for the tail discipline; linear probing only acceptable when load factor is permanently low. Reapplies at: W74 matching-engine OrderId→Order map, W94 exec-vm storage-key probe, W90 consensus-vsr replica-state lookup.

    - **When `test_account_map_deterministic_hash_across_processes` fails with different bucket assignments:**
      - Symptom: process A hashes AccountId 0x1234 to bucket 5; process B hashes the same ID to bucket 9847. State_machine outputs match but timing leaks differ, breaking VOPR replay determinism.
      - Why: you used `std::collections::hash_map::DefaultHasher` (SipHash-1-3) which seeds its state from `std::collections::hash_map::RandomState` — randomized per-process.
      - Fix: build a `BuildHasherDefault` over Splitmix64 finalizer of `AccountId.as_u64()` (unit-struct hasher, no per-instance seed) OR BLAKE3-128 truncated to `u64`. Both deterministic, both ~3 ns, both adversarial-OK.
      - Cost avoided: ~27 ns/hash × 2 hashes/Transfer = ~54 ns P50; ~30 µs P99 cliff under adversarial input. VOPR replay is now byte+timing identical.
      - Muscle: pick the hash function deliberately. `DefaultHasher` is wrong for any hot-path map; `HashMap` is wrong for any bar-(c) crate. Reapplies at: W89 Tue FixedMap hash, W94 exec-vm v1.5 storage-key hash, W92 ledger state_hash (BLAKE3), W74 matching-engine OrderId→Order lookup.

    - **When `test_account_map_no_rehash_returns_full_at_load_85` panics on rehash instead of returning `MapFull`:**
      - Symptom: at load 0.85, `insert()` hangs in an infinite robin-hood probe loop OR a rehash attempt allocates new bucket array (~10 ms latency spike).
      - Why: forgot the hard cap; `insert()` keeps probing until it finds an empty slot, which doesn't exist at load 1.0. OR you tried to "be helpful" and added a rehash path.
      - Fix: at top of `insert()`, `if self.len + self.tombstones >= (N * 85) / 100 { return Err(MapFull); }`. No rehash branch exists in the code at all.
      - Cost avoided: 10 ms rehash latency spike → 0 ns; eliminates the P99 cliff that would otherwise dominate the latency histogram. At 100 k Transfers/sec a single rehash drops throughput by 50%+ for the duration.
      - Muscle: bar (c) = static memory = no growable collections on the hot path. Acceptance is "dhat reports 0 allocs" not "we tried to minimize allocs." Reapplies at: every bar-(c) crate from W89 onward.

    - **When `test_pooled_transfer_releases_on_panic` shows leaked slots after a panic-recovery test:**
      - Symptom: after running an apply loop that panics mid-Transfer 1000 times, pool's `in_use_count == 1000` instead of 0.
      - Why: `acquire()` returns a bare `&mut Transfer`; the apply caller is responsible for calling `release()`. On panic, the manual release is skipped.
      - Fix: wrap in RAII `PooledTransfer<'a> { pool: &'a TransferPool, slot_id: u32 }` with `Drop` calling `pool.release(self.slot_id)`. Panic unwind drops the local; pool count restored.
      - Muscle: pool-managed resources need RAII handles to survive panics; manual release is a leak waiting to happen. Reapplies at: W89 Thu MessagePool's `PooledMessage<'a>`, W82 matching-engine Order pool, W90 io_uring buffer pool, W77 messaging-aeron term-slot.

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: at 100 M pps, the kernel network stack itself is the bottleneck: `recv(2)` + skb allocation + protocol-stack walk costs ~500 ns/packet. AF_XDP bypasses by DMA-ing into mmap'd userspace memory (UMEM); userspace polls a ring. Per-packet cost drops to ~15-20 ns — but only if **two hardware co-location invariants** hold: huge pages for UMEM (TLB) and IRQ-affinity to the poller core (IPI). Miss either and AF_XDP runs at ~5 M pps — slower than io_uring.

  - **Requirements** — write in `crates/marketdata-kernelbypass/notes/89tue_af_xdp_design.md`:
    - R1. `AfXdpTransport` holds: `Umem` (mmap'd region), `RxRing`, `FillRing`, `XskSocket`; allocated **once** at startup.
    - R2. UMEM is mmap'd with `MAP_HUGE_2MB`; verified via `/proc/<pid>/smaps` showing `KernelPageSize: 2048 kB`.
    - R3. NIC RX queue IRQ pinned to same core as the poller: `ethtool -X` + `echo <mask> > /proc/irq/<n>/smp_affinity`; poller `core_affinity::set_for_current`.
    - R4. `recv_batch<'a>(&'a mut self, out: &mut ArrayVec<UmemFrame<'a>, N>) -> usize` returns borrowed frames; `UmemFrame::Drop` returns address to `fill_ring` (RAII).
    - R5. Throughput ≥ 50 M pps single-core loss-free on supported NIC; ≤ 0.001% packet loss at saturation.
    - R6. Per-packet cost ≤ 20 ns ring-mechanics (rx_ring read ~5 ns + frame construction ~1 ns + Drop refill ~5 ns + slack).
    - R7. Feature-gated `#[cfg(feature = "af-xdp", target_os = "linux")]`; non-Linux build emits no-op stub; CAP_NET_ADMIN check at startup with operator-friendly error.
    - R8. BPF program (xdp-redirect-to-xskmap) loaded + attached via libbpf-rs; explicit redirect rule — never default DROP.

  - **Design walk-through** — answer each; no peeking at `libxdp` or `xdp-tutorial advanced3-AF_XDP` until Phase 3:
    - D1. Cost budget: trace a single packet end-to-end (NIC → UMEM → app). Which steps the kernel skips (skb alloc, protocol stack); which steps remain (DMA + descriptor write + userspace poll). Tally per-packet ns; how close to the 10 ns "headline" budget?
    - D2. UMEM sizing: NUM_FRAMES × FRAME_SIZE. At 50 M pps × 100 µs in-flight worst case = 5000 frames minimum; 32× safety = 160 k frames × 2 KB = 320 MB UMEM. Justify your chosen number. What goes wrong if FRAME_SIZE is not power-of-two?
    - D3. Ring construction: rx_ring (kernel-producer, user-consumer), fill_ring (user-producer, kernel-consumer), tx_ring (unused for ingress), completion_ring (unused). Draw the data flow showing which side writes which cursor. Why is fill_ring necessary even when not transmitting?
    - D4. BPF program: minimal "xdp-redirect-to-xskmap[queue_idx]". Why does the redirect target a queue index, not the socket directly? What's xskmap, and where does it live?
    - D5. Huge-page TLB math: 64 MB UMEM = 16,384 × 4 KB pages, OR 32 × 2 MB huge pages. L1 TLB capacity ~64 entries. Compute TLB hit rate for each: under random access, what fraction of UMEM reads trigger a TLB miss in the 4 KB case? In the 2 MB case? At ~25 ns/TLB-miss × 100 M pps, what's the throughput cap with 4 KB pages?
    - D6. IRQ affinity: the NIC's RX queue fires an IRQ on some core; the AF_XDP poller runs pinned to some other core. Trace what happens per packet without affinity: IRQ → soft-IRQ → wakeup IPI → poller dispatch. Cost? With affinity (same core)? Why is this "the second biggest setup-time lever"?
    - D7. RAII for UmemFrame: `UmemFrame<'a> { umem: &'a Umem, addr: u64, len: u16 }`. Drop semantics: must return addr to `fill_ring`. What happens if the user drops a million frames without polling? (fill_ring fills, addresses recycle.) What happens if Drop is forgotten? (frame leak, fill_ring drains, kernel stops delivering.)
    - D8. **Pre-mortem (load-bearing)**: write the 5-step sequence where a test passes with small UMEM (fits in L1 TLB) but production runs at 5 M pps despite the same code. What's the missing instrumentation that would have caught it pre-prod? (Hint: `cat /proc/<pid>/smaps` assertion in startup self-test.)

  #### Phase 3 — Make the tests pass, one failure at a time (~100 min)

  - **When `bench_af_xdp_per_packet_cost` reports ~250 ns/packet (vs 20 ns target):**
    - Symptom: bench shows 4 M pps single-core; far below the 50 M pps target. CPU "looks idle" (~30% utilization) because most time is stalled, not executing.
    - Why: UMEM allocated as `Box<[u8; N]>` (4 KB pages); ~93% of UMEM accesses trigger TLB misses (~25 ns each). At 100 M pps target × 25 ns = 2.5 sec/sec of pure TLB-miss latency.

    - Cost avoided: ~25 ns/packet × 100 M pps = 2.5 sec/sec → 0 ns. The single biggest perf lever for AF_XDP at saturation.
    - Muscle: any mmap'd region ≥1 MB that's hot-path-read benefits from huge pages; the TLB is real hardware with low budget at saturation. Reapplies at: W90 io_uring journal file (1 GB pre-allocated + `O_DIRECT` + huge-page-aligned), W90 ledger 128 MB Transfer pool, W82 matching-engine OrderBook backing array, W92 versioned-memory DashMap shards.

  - **When `test_irq_affinity_matches_poller_core` shows IRQ on core 0 and poller on core 4 (5 M pps observed):**

    - Why: NIC RX IRQ fires on whatever core the OS scheduler assigns (typically core 0); AF_XDP poller pinned to core 4. Each packet: IRQ → soft-IRQ → wakeup IPI → poller dispatch. ~500 ns IPI + cache-line bounce per packet.

(a) `ethtool -X rx-flow-hash udp4 sdfn` to direct flows to a specific queue; (b) `echo <core_mask> > /proc/irq/<irq_for_that_queue>/smp_affinity`; (c) poller `core_affinity::set_for_current` to the same core. Combine with busy-polling so the poller wakes on rx_ring cursor advance via in-core read.

    - Muscle: in any kernel-bypass / busy-poll architecture, **co-locate IRQ-source core + NIC RX queue + poller**. Any cross-core hop in the data plane is fatal. Reapplies at: W90 io_uring journal (poller on same core as fsync issuer), W82 matching-engine per-symbol shards (W85 runtime-thread-per-core), W92 ledger replica core pin, W77 messaging-aeron subscriber pin.

      - D1. POOL_SIZE = 1024 justified: at 30 k op/s × 3 messages × ~50 µs in-flight = ~4.5 k outstanding peak. Why not 5 k exactly? (Headroom for partition recovery + reconfiguration burst.) Why not 10 k? (Wasted memory; 1024 × 8 KB = 8 MB is the right ballpark.)
      - D2. Free-list data structure: `ArrayQueue<u32>` (MPMC, ~15 ns/op atomic CAS) vs `ArrayVec<u32, N>` (single-thread, ~3 ns/op no atomic). When does each apply? Document the split: per-replica pool = single-threaded via runtime-thread-per-core (W85) = `ArrayVec`; cross-replica state-transfer pool = shared = `ArrayQueue`.
      - D3. `PooledMessage<'a>` lifetime: ties handle to pool via `&'a MessagePool`. What does this prevent? (PooledMessage outliving pool.) What's the trade-off? (Can't `Send` across threads without scoped lifetimes; OK because runtime-thread-per-core means pool is thread-local.)
      - D4. RAII Drop: `Drop` does `pool.release(self.slab_id)`. What's the worst case if `Drop` is forgotten? (Slot leak.) Can we forget? (Only via `mem::forget` or panic-in-Drop scenarios — both rare and detectable.) What about double-free? (Track `in_flight` bitmask; debug_assert.)
      - D5. Stale-byte leak: explain the bug. Drop releases slab_id; next acquire returns the slot; the new caller forgets to write `cluster_id`; the message sends with the PREVIOUS Transfer's cluster_id; silent cross-cluster corruption. How does zeroing on Drop prevent this? Why not zero on acquire instead? (Either works; Drop-side is failsafe — caller forgetting `acquire().reset()` is more likely than forgetting `Drop`.)
      - D6. Backpressure semantics: `acquire()` returns `None` on exhaustion. Caller maps to `BackPressure` error and stops sending. Why not block? (Blocking on the apply hot path = unbounded latency tail.) Per-destination quota: track `in_flight_per_dest`; exhaustion on one destination doesn't starve others.
      - D7. Per-replica vs shared spec: write the doc comment justifying the split. Single-threaded replica pool = `ArrayVec<u32>` for speed. Cross-replica state-transfer = MPMC `ArrayQueue` because multiple replica threads coordinate. Future maintainer who "unifies" them = perf regression.
      - D8. **Pre-mortem**: write the 5-step interleaving where a partition causes pool exhaustion → sender can't send → can't recover → cascading failure. What's the fix path? (Per-destination quota + reclaim on timeout.)

    #### Phase 3 — Make the tests pass, one failure at a time (~75 min)

    - **When `test_per_replica_no_atomic_in_acquire` shows `lock cmpxchg` in disassembly:**
      - Symptom: `cargo asm consensus_vsr::message_pool::MessagePool::acquire` shows `lock cmpxchg` (x86) or `LDAXR`/`STXR` (aarch64); per-acquire latency ~15 ns instead of target ~3 ns.
      - Why: you used `crossbeam_queue::ArrayQueue<u32>` for the per-replica pool free list; ArrayQueue is MPMC, every op is atomic CAS. But the per-replica pool is touched only from one thread (the replica's pinned thread via W85 runtime-thread-per-core); the atomic is buying nothing.
      - Fix: split the pool implementations. Per-replica: `free_ids: ArrayVec<u32, POOL_SIZE>` with plain `pop()`/`push()` (~3 ns each). Cross-replica state-transfer: keep `ArrayQueue` because it IS shared. Document the split in `MessagePool` doc-comments so future maintainers don't "unify" them.
      - Cost avoided: ~9 ns/lifecycle × 90 k msg/s = ~800 µs/sec reclaimed per replica. Small in absolute terms but every nanosecond compounds in VSR's <500 µs P99 budget.
      - Muscle: atomic ops cost real cycles; use them only where actual sharing exists. Thread-per-core (W85 runtime) deliberately removes the need for atomics on the per-shard hot path — leverage it. Reapplies at: W82 matching-engine per-symbol shard state, W92 ledger per-replica clock advance, W74 matching-engine OrderBook updates.

    - **When `test_pooled_message_drop_zeros_header` shows `cluster_id == 0xDEADBEEF` after re-acquire:**
      - Symptom: a slot is acquired, written with sentinel bytes, dropped; re-acquired (same slot); the sentinel bytes are still there.
      - Why: `Drop` just pushed `slab_id` back to the free list without clearing the slot's contents. Stale bytes leak to the next acquire; if the next caller forgets to write a field, the previous caller's bytes ship.
      - Fix: in `Drop`: `msg.header.zero(); msg.body.clear();` before pushing slab_id. ~30 ns extra per release (one cache-line write for 96 B header + len-to-0 for ArrayVec). Cheap.
      - Cost avoided: not perf-headline but **correctness budget** — a single stale-byte bug under VOPR replay = silent state corruption → assertion violation → days of debug. ~30 ns avoids an entire class of bug.
      - Muscle: pool reuse means stale-byte leak risk; reset on return (or on acquire) is mandatory. Reapplies at: W90 io_uring journal write-fixed buffer (zero on return), W82 matching-engine Order pool, W92 ledger Transfer pool, W77 messaging-aeron term-buffer slot reclamation.

    - **When `test_pool_drop_on_panic` shows leaked slots after the unwind:**
      - Symptom: `catch_unwind` runs a closure that acquires a message then panics; after the closure, pool's `in_flight == 1` instead of 0.
      - Why: `acquire()` returns a bare `&mut VsrMessage` (not a `PooledMessage<'a>`); the caller is responsible for `pool.release(slab_id)` manually. On panic, that explicit call is skipped.
      - Fix: change return type to RAII handle: `pub fn acquire(&self) -> Option<PooledMessage<'_>>` where `PooledMessage<'a> { pool: &'a MessagePool, slab_id: u32, _msg: &'a mut VsrMessage }` with `Drop` calling `pool.release(self.slab_id)`. Panic unwind drops the local; pool count restored.
      - Muscle: pool-managed resources need RAII handles to survive panics. Reapplies at: W89 Mon PooledTransfer, W82 matching-engine Order pool, W90 io_uring buffer pool, W77 term-slot.

    - **When `test_per_destination_quota_isolates_partition` shows all destinations starved by a single partition:**
      - Symptom: dest A is partitioned; in-flight to A fills POOL_SIZE; `acquire()` returns None for messages to dest B (healthy); cascading failure.
      - Why: pool is global to the replica with no per-destination accounting; one partitioned dest can monopolize all slots.
      - Fix: add per-destination quota: `in_flight_per_dest: [AtomicU32; MAX_REPLICAS]` (or `[u32; MAX]` if single-threaded). At acquire-time, check both pool-global and per-dest counts; reject only the offending dest. Add reclaim timeout: in-flight messages older than 100 ms (configurable) are forcibly released. Document in operator runbook.
      - Muscle: shared pools with no per-tenant quota cascade failures; quota per consumer is non-optional in fan-out designs. Reapplies at: W90 io_uring per-fd quota, W77 messaging-aeron per-subscriber credit.

    - **When `test_message_pool_zero_allocs_after_construction` reports a hidden allocation:**
      - Symptom: dhat fires once per acquire with ~24-byte allocation; pool itself is OK but acquire path allocates.
      - Why: `acquire()` is constructing a `Box<PooledMessage>` somewhere, or wrapping the handle in a `Result::Err(String::from("..."))` on the error path that runs surprisingly often. OR you're using `format!()` in a `tracing::debug!` call.
      - Fix: `PooledMessage` is a stack-local struct, not boxed. Error path uses enum variants, not `String`. Tracing uses static format strings only.
      - Muscle: even "obvious" zero-alloc paths leak via error/log/format paths; dhat is the enforcement. Reapplies at: W89 Mon Transfer pool, W90 io_uring submit, W92 v1.0 SHIP audit.
