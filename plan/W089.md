- [NEW v2] **ledger v1.0: static-memory invariants (part 1)**
  - [ ] **Build**: pre-sized pools for in-flight Transfers (max 1M concurrent) — zero heap alloc in apply-loop. (~3 hrs)
    - **Why**: v1.0 hits bar (c). Static memory is the TigerBeetle invariant that gives them their reputation: every memory location is allocated AT STARTUP, and `apply()` never touches the global allocator. The benefit isn't speed (though it is faster) — it's predictability: no allocator latency tail, no OOM in steady state, no fragmentation under burst. Pre-sized pool sized for 1M in-flight transfers is the realistic high-watermark for a Tier-A ledger.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/state_machine.zig` allocator pattern + `lib/tigerbeetle/src/lsm/manifest.zig` for fixed-table sizing; `bumpalo` for arena reference; `slab` Rust crate.
    - **Design**:
      ```rust
      pub struct TransferPool {
          slab: Box<[MaybeUninit<Transfer>; MAX_TRANSFERS]>,     // 1M × 128B = 128MB
          free_list: ArrayVec<u32, MAX_TRANSFERS>,              // indices of free slots
          in_use: BitSet<MAX_TRANSFERS>,
      }
      pub struct AccountMap {
          buckets: Box<[Option<AccountSlot>; MAX_ACCOUNTS]>,    // 16M slots
          // load factor target: 0.75 → effective 12M accounts
      }
      pub struct AccountSlot { id: AccountId, account: Account, version: u32 }
      // open-addressing, robin-hood, no rehash
      ```
      **Invariants**: (i) `Box::new_zeroed()` allocates ONCE at startup; (ii) `apply` panics if pool exhausted (must surface — never silently fail); (iii) `AccountMap` capacity fixed; reaching `0.85` load factor triggers operational warning long before correctness break; (iv) no `Vec::push`, no `HashMap::insert`, no `Box::new` in `apply`.
    - **Build steps**: 1. (~10 min) define `TransferPool::new()` allocating 128MB zeroed once + initializing `free_list` with [0..MAX). 2. (~20 min) `acquire()` pops free slot, marks in_use, returns &mut Transfer + slot_id; `release(slot)` clears in_use, pushes to free_list. 3. (~30 min) `AccountMap` open-addressing impl: hash → bucket → linear probe → robin-hood swap-on-collision. 4. (~25 min) `AccountMap::lookup` / `insert` / `update` — all O(1) avg, O(load_factor / (1-load_factor)) worst. 5. (~20 min) load-factor metric exporter (gauge), warn at 0.75 / error at 0.90. 6. (~20 min) wire into `apply()`: Transfer parses → pool.acquire → mutate accounts via map.update → on commit pool.release. 7. (~25 min) ban allocator calls on hot path: `#[cfg_attr(test, deny(no_alloc_audit))]` lint via `cap` allocator that panics on alloc in test mode. 8. (~30 min) crash-recovery semantics: pool state derived from journal — no separate persistence. 9. (~20 min) write test: 1M Transfers in tight loop, dhat reports 0 allocs during loop (preamble only).
    - **Pitfalls**: *Pool exhaustion under burst*: **Symptom**: pool runs out during burst > 1M concurrent; apply panics; service down. **Fix**: surface exhaustion as backpressure to client (Reject with ErrTooManyInFlight) BEFORE invoking pool.acquire; pool size is hard ceiling. *Hash collisions clustering*: **Symptom**: poor hash distribution → long probe sequences → latency p99 explodes. **Fix**: use BLAKE3-128 truncated as hash (CSPRNG quality), not `DefaultHasher`. *Load-factor surprise*: **Symptom**: accounts grow over time, slowly approach capacity, sudden p99 cliff at 0.9. **Fix**: alarming + operational headroom; document upgrade procedure (snapshot + larger-capacity restore). *MaybeUninit UB*: **Symptom**: reading slot before `acquire` returns wild bytes. **Fix**: `acquire` always `slot.write(Transfer::default())` before returning &mut; never read uninit. *128MB allocation failing on small systems*: **Symptom**: dev test machine OOM. **Fix**: configurable pool size via const generic / env var; default to MAX_TRANSFERS=64k for dev profile.
    - **Test scenarios**: dhat report after `apply(op)` × 1M: 0 allocs. Concurrent burst: 999k acquires + 1k releases → pool reaches 999k in_use, OK. Force 1M+1 → panic with ExhaustedErr. Long run: 100M apply, account count 5M, load factor stays below 0.5.
    - **Acceptance**: dhat 0 hot-path allocs; load_factor metric exported; ledger v1.0 RC built with `--features static-mem` gates this on.
    - **Downstream**: io_uring journal (W90) requires alloc-free apply; VSR replication (W91) batches Transfers through pool; v1.0 SHIP (W92) audit-gate on dhat=0.

- [ ] **Build**: `crates/marketdata-kernelbypass/src/af_xdp.rs` — AF_XDP socket using `xdp` crate. Zero-copy receive
  path; requires CAP_NET_ADMIN. (~150 min)
  - **Why**: AF_XDP is the closest OSS analogue to Solarflare/Onload kernel-bypass: packets DMA directly into userspace memory (UMEM) without traversing the kernel networking stack. For 50M+ pps it crushes both epoll and io_uring. Cost: requires CAP_NET_ADMIN, kernel ≥5.4 with XDP support on the NIC driver. Not all NICs support `XDP_FLAGS_DRV_MODE`; SKB mode falls back to slower path.
  - **Read first**: Linux `Documentation/networking/af_xdp.rst`, `libxdp` source, `xdp-tutorial` repo (advanced3-AF_XDP), Cloudflare's "How we use HW offload for L7" post.
  - **Design**:
    ```rust
    pub struct AfXdpTransport {
        umem: Umem,                              // mmap'd shared memory region
        rx_ring: RxRing,                         // userspace-visible RX queue
        fill_ring: FillRing,                     // app posts UMEM frame addrs for kernel
        tx_ring: TxRing,                         // not used for ingress-only
        completion_ring: CompletionRing,         // not used for ingress-only
        socket: XskSocket,
        frame_size: u32,                         // 2048 or 4096
    }
    impl Transport for AfXdpTransport {
        type Frame<'a> = UmemFrame<'a>;
        fn recv_batch<'a>(&'a mut self, out: &mut ArrayVec<UmemFrame<'a>, N>) -> usize { /*...*/ }
    }
    pub struct UmemFrame<'a> { umem: &'a Umem, addr: u64, len: u16 }
    // Drop returns frame to fill_ring
    ```
    **Invariants**: (i) UMEM is mmap'd ONCE at startup, size = NUM_FRAMES * FRAME_SIZE; (ii) zero-copy: kernel writes into UMEM, userspace reads — no `recv(2)` call; (iii) `UmemFrame` Drop returns addr to `fill_ring` (RAII); (iv) BPF program attached to NIC redirects matching packets to xskmap[queue_idx].
  - **Build steps**: 1. (~10 min) probe XDP support: `bpf_object__find_program_by_name` against kernel features. 2. (~15 min) UMEM setup: `mmap` 64MB anonymous, register via `xsk_umem__create()`. 3. (~20 min) RX ring + fill ring construction with `xsk_socket__create()` and queue_idx. 4. (~15 min) load minimal BPF program (xdp-redirect-to-xskmap) via libbpf-rs; attach to NIC via `bpf_xdp_attach()`. 5. (~25 min) prime fill_ring with all NUM_FRAMES UMEM addrs. 6. (~20 min) `recv_batch`: poll rx_ring, for each descriptor extract addr+len, construct `UmemFrame`. 7. (~15 min) UmemFrame Drop returns addr to fill_ring; assert no double-free. 8. (~15 min) NIC config helper: `set_irq_affinity()`, `disable_rx_coalescing()`, `set_promisc_mode()` as needed. 9. (~15 min) feature-gate `#[cfg(feature = "af-xdp")]`; require `linux` target + privilege probe at startup.
  - **Pitfalls**: *Driver mode unavailable*: **Symptom**: bpf_xdp_attach with DRV_MODE returns EOPNOTSUPP — NIC driver doesn't support native XDP. **Fix**: fallback to SKB_MODE (slower); document required NICs (mlx5, i40e, ice, etc.). *Frame address leak*: **Symptom**: forgot to fill_ring.add() after consuming; fill ring drains; recv stops. **Fix**: RAII Drop on UmemFrame + assertion that fill_ring count stays ≥ NUM_FRAMES/2. *UMEM alignment violation*: **Symptom**: rx_ring entries reference unaligned addresses; kernel rejects. **Fix**: `mmap` with MAP_HUGE_2MB; FRAME_SIZE a power of two. *CAP_NET_ADMIN absent*: **Symptom**: setup silently degrades or panics. **Fix**: explicit `prctl(PR_CAP_AMBIENT)` check at startup; error message points operator to setcap. *Lost packets with XDP_DROP-by-default*: **Symptom**: BPF doesn't have a redirect rule, all packets drop. **Fix**: pre-load and verify BPF program has explicit redirect.
  - **Test scenarios**: 50M pps synthetic via DPDK pktgen or another machine → recv loss <0.001%; Drop-test: drop UmemFrame without consuming → fill_ring count returns to NUM_FRAMES; long run 1h at 50M pps → no FD leak, no UMEM leak.
  - **Acceptance**: 50M pps single-thread loss-free on supported NIC; CPU usage <1 core; comparable bench output to epoll/io_uring in W89 Fri.
  - **Downstream**: feed_handler can use AfXdpTransport for the hot ingress; bench result drives v0.5 SHIP decision (default transport per environment).

- [NEW v2] **ledger v1.0: static-memory invariants (part 2)**
  - [ ] **Build**: account map as fixed-size hash table (open addressing) — no rehash. (~2 hrs)
    - **Why**: HashMap with rehash is incompatible with bar (c) — rehash is a multi-ms allocator-storm and would invalidate latency tail. TigerBeetle uses a fixed-size open-addressing table sized once at startup. No rehash, no Vec growth. Load factor is monitored; capacity is rated and operator-tunable.
    - **Read first**: `hashbrown::raw::RawTable` for SIMD probe reference; Daniel Lemire's "Robin Hood Hashing in Rust"; TigerBeetle `lib/tigerbeetle/src/lsm/grid.zig` table sizing.
    - **Design**:
      ```rust
      pub struct FixedMap<K: Eq + Hash + Copy, V> {
          slots: Box<[Slot<K, V>; N]>,
          len: u32,
          tombstones: u32,
      }
      enum Slot<K, V> { Empty, Tombstone, Occupied { hash_top: u32, key: K, value: V, probe_dist: u16 } }
      impl<K, V> FixedMap<K, V> {
          pub fn insert(&mut self, k: K, v: V) -> Result<(), MapFull>;
          pub fn get(&self, k: &K) -> Option<&V>;
          pub fn remove(&mut self, k: &K) -> Option<V>;
      }
      ```
      **Invariants**: (i) `Box::new()` ONCE at startup, capacity N is const generic; (ii) no rehash — `MapFull` returned when load_factor > 0.85; (iii) robin-hood: minimize variance of probe_dist; (iv) tombstones counted; cleaned on opportunistic scan; (v) hash_top = top 32 bits of hash, used to skip key compare on probe miss.
    - **Build steps**: 1. (~15 min) struct + Box-zeroed allocation. 2. (~25 min) `insert`: hash(K), bucket = hash % N, robin-hood loop: if `slot.probe_dist < new_probe_dist` swap. 3. (~20 min) `get`: hash → bucket → linear probe comparing `hash_top` first, then key. 4. (~15 min) `remove`: write Tombstone; if next slot is Empty, walk back collapsing tombstones (or defer). 5. (~10 min) load_factor + tombstone_ratio metrics. 6. (~10 min) capacity sizing helper: `FixedMap::with_max_keys(max_keys)` → N = next_power_of_two(max_keys * 4/3). 7. (~10 min) deny rehash: compile error if capacity dynamic. 8. (~15 min) unit + property tests: random insert/remove sequence → get matches `BTreeMap` reference.
    - **Pitfalls**: *Insert at load=1.0*: **Symptom**: infinite loop. **Fix**: hard cap at 0.95, return MapFull. *Tombstone accumulation*: **Symptom**: high churn → table looks full of tombstones; get probes every slot. **Fix**: opportunistic rebuild during insert if tombstone_ratio > 0.25; OR forbid remove on hot path. *Hash quality*: **Symptom**: malicious key sequence causes clustering. **Fix**: `BuildHasher` with random seed at startup; for adversarial input use BLAKE3. *Robin-hood swap bug*: **Symptom**: invariant break — distant probe_dist on lookup, get misses. **Fix**: assert probe_dist monotonic during get; property tests with random ops.
    - **Test scenarios**: insert 12M keys into N=16M table → 0 MapFull errors; get all 12M → 100% hit; remove + reinsert sequence → load_factor stable; adversarial keys (hash mod-bucket-grouped) → probe_dist max < 32.
    - **Acceptance**: get p99 < 200ns under 0.5 load factor; no allocs after construction.
    - **Downstream**: used as the AccountMap in ledger v1.0; reusable in matching-engine for OrderId → Order lookup.

- [NEW v2] **consensus-vsr v1.0: zero-alloc message types (part 1)**
  - [ ] **Build**: refactor message types to use `arrayvec::ArrayVec<u8, N>` instead of `Vec<u8>` on hot path. (~3 hrs)
    - **Why**: VSR's hot path is sending Prepare / PrepareOk / Commit messages, each containing the operation payload. With `Vec<u8>`, every message allocates. v1.0 cannot have allocs on the message-send hot path — they introduce nondeterministic latency tails. ArrayVec with a const-generic max size is bounded; matches TigerBeetle's vsr message struct.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/vsr.zig::Message`; `lib/tigerbeetle/src/message_pool.zig`; LIONS-VSR paper §3 message format.
    - **Design**:
      ```rust
      pub const MAX_MESSAGE_BODY: usize = 8192;  // covers max ledger op
      pub struct VsrMessage {
          header: VsrHeader,                    // fixed 96 bytes
          body: ArrayVec<u8, MAX_MESSAGE_BODY>, // up to 8KB inline
      }
      pub struct VsrHeader {
          checksum: u128,
          cluster: u128,
          op: u64,
          view: u32,
          replica_id: u8,
          command: VsrCommand,
          /* ... */
      }
      // VsrMessage is Box::new'd once at startup via MessagePool, then reused
      ```
      **Invariants**: (i) message body bounded by MAX_MESSAGE_BODY — operations larger than this must be chunked at ledger layer; (ii) VsrMessage is reused via pool — never `Box::new` on hot path; (iii) refactor must not change wire format (binary compatibility tests); (iv) header continues to be POD (transmutable).
    - **Build steps**: 1. (~10 min) freeze MAX_MESSAGE_BODY = 8192 (covers ledger Op + max-size repeating batch); document rationale in code. 2. (~20 min) replace `Vec<u8>` body with `ArrayVec<u8, MAX_MESSAGE_BODY>` in `VsrMessage`. 3. (~30 min) update all callsites: `body.push_back` → `body.try_push().ok_or(MsgTooLarge)`. 4. (~30 min) wire-format compat test: encode a VsrMessage via old and new code paths, byte-compare. 5. (~30 min) chunking helper: ledger `apply_batch(ops: &[Op])` splits into ≤MAX_MESSAGE_BODY chunks. 6. (~20 min) bench: messaging hot path before/after, expect 30-50% lower p99 (alloc-driven tail removed). 7. (~25 min) dhat audit on full message send loop: 0 alloc per message. 8. (~15 min) error-path audit: MsgTooLarge propagates cleanly to caller.
    - **Pitfalls**: *Msg-size overflow*: **Symptom**: ledger sends batch > 8KB, VSR rejects with MsgTooLarge, batch stuck. **Fix**: ledger batches itself ≤8KB; OR raise MAX_MESSAGE_BODY (cost: per-replica memory). *ArrayVec stack-blowup*: **Symptom**: VsrMessage now 8KB+96B, stack-allocating a copy blows the stack. **Fix**: VsrMessage always heap-pooled, never local; `#[inline(never)]` on construction. *Wire-format break*: **Symptom**: protocol incompatible across versions. **Fix**: explicit byte-compare test in CI; SemVer break if wire changes. *Header alignment*: **Symptom**: `repr(C)` header followed by ArrayVec changes layout. **Fix**: `repr(C)` only on header; body comes after with explicit serialize.
    - **Test scenarios**: round-trip serialize/deserialize 100k messages → 0 byte diff; alloc audit: 0 allocs on send loop; chunking: 100KB ledger op → 13 chunked VSR messages, ledger reassembles correctly.
    - **Acceptance**: dhat = 0 hot-path allocs; wire compat preserved; bench p99 drops by ≥30%.
    - **Downstream**: message pool (Thursday) reuses these messages; v1.0 SHIP gates on dhat=0.

- [NEW v2] **consensus-vsr v1.0: zero-alloc message types (part 2 — pre-allocated pool)**
  - [ ] **Build**: pre-allocated message pool per replica; allocations only at startup. (~2 hrs)
    - **Why**: VSR replicas send + recv many messages per second. Even with ArrayVec body (Wednesday), allocating the VsrMessage struct itself per message costs. A pool means: fixed N messages allocated at startup, reused indefinitely, freed at shutdown. Tigerbeetle's MessagePool gives bounded memory + predictable latency. The pool also serves as a backpressure mechanism: if no free message available, sender backs off.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/message_pool.zig`; `crossbeam-queue::ArrayQueue` for SPSC reference.
    - **Design**:
      ```rust
      pub struct MessagePool {
          slabs: Box<[VsrMessage; POOL_SIZE]>,        // POOL_SIZE = 1024 per replica
          free_ids: ArrayQueue<u32>,                  // free indices (MPMC)
          in_flight_counter: AtomicU32,
      }
      pub struct PooledMessage<'a> { pool: &'a MessagePool, slab_id: u32 }
      impl<'a> Drop for PooledMessage<'a> { fn drop(&mut self) { /* return to free_ids */ } }
      impl MessagePool {
          pub fn new(size: u32) -> Self;
          pub fn acquire(&self) -> Option<PooledMessage<'_>>;
          pub fn in_flight(&self) -> u32;
      }
      ```
      **Invariants**: (i) `slabs` allocated ONCE at startup; (ii) `acquire()` is O(1) — pop from free queue or None; (iii) RAII Drop returns slab_id to pool; (iv) in_flight_counter is monotonic gauge for observability + backpressure.
    - **Build steps**: 1. (~10 min) `MessagePool::new(size)` allocating `Box<[VsrMessage; POOL_SIZE]>` + ArrayQueue<u32> with all ids. 2. (~15 min) `acquire()` returns `PooledMessage` borrowing from pool; on empty returns None — caller decides backpressure. 3. (~15 min) `PooledMessage::Drop` returns slab_id to ArrayQueue. 4. (~10 min) `in_flight()` exposes counter for metrics. 5. (~15 min) wire VSR send path: `pool.acquire().ok_or(BackPressure)?.write_header(...).write_body(payload)`. 6. (~15 min) dhat audit: 1000 send loops → 0 alloc post-construction. 7. (~15 min) pool exhaustion stress test: hold N messages, try N+1 acquire → None. 8. (~20 min) per-replica vs shared: spec doc on tradeoff (per-replica = bounded memory; shared = better utilization).
    - **Pitfalls**: *Pool exhaustion under partition*: **Symptom**: replica can't send Prepare because all messages stuck in-flight to a partitioned follower. **Fix**: per-destination quota inside pool; OR timeout on in-flight messages > deadline → reclaim. *Double-free*: **Symptom**: pool slab_id pushed twice to free queue, causes double-acquire of same slot. **Fix**: in_flight bitmask guarantees Drop runs only once; debug_assert on bitmask. *PooledMessage outliving pool*: **Symptom**: pool dropped, PooledMessage still alive. **Fix**: lifetime `'a` ties them; Rust borrow-checker enforces. *MPMC queue overhead*: **Symptom**: ArrayQueue has heavier ops than expected. **Fix**: per-replica MessagePool = single-thread → use Vec<u32> directly, no atomic.
    - **Test scenarios**: acquire/release × 1M in tight loop → 0 alloc, no growth; concurrent 4 threads × 250k acquires → all succeed; exhaustion: acquire N times, N+1 returns None; after Drop, in_flight=0.
    - **Acceptance**: dhat 0 allocs after construction; pool exhaustion surfaces cleanly as backpressure.
    - **Downstream**: VSR v1.0 SHIP (W90) gates on this; reconfiguration messages also use pool.
