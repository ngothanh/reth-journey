- [NEW v2] **ledger v1.0: static-memory invariants (part 1)**
  - [ ] **Build**: pre-sized pools for in-flight Transfers (max 1M concurrent) — zero heap alloc in apply-loop. (~3 hrs)
    - **Why**: v1.0 hits bar (c). Static memory is the TigerBeetle invariant that gives them their reputation: every memory location is allocated AT STARTUP, and `apply()` never touches the global allocator. The benefit isn't speed (though it is faster) — it's predictability: no allocator latency tail, no OOM in steady state, no fragmentation under burst. Pre-sized pool sized for 1M in-flight transfers is the realistic high-watermark for a Tier-A ledger.
    - *Back-of-envelope* (ledger v1.0 target: **P99 ≤ 1 µs commit single-shard** — the headline. Single-shard means one apply() invocation must complete in <1 µs P99):
      Budget breakdown for one Transfer apply: pool.acquire ≈ 10 ns (free-list pop + bit-flip); AccountMap.lookup_debit ≈ 30 ns (W89 Tue's open-addressing, ~3 probes × ~10 ns L2 read); AccountMap.lookup_credit ≈ 30 ns; balance arithmetic + invariant check ≈ 5 ns; AccountMap.update_debit ≈ 20 ns (in-place); AccountMap.update_credit ≈ 20 ns; journal append (W90 io_uring buf claim + memcpy ~64 B) ≈ 50 ns; state-hash gossip increment ≈ 3 ns; pool.release ≈ 10 ns; total ~180 ns ✓ (P50). P99 includes: TLB miss on cold account (~30 ns), occasional probe-distance spike (~50 ns), io_uring SQE submit on group-commit boundary (~80 ns) — landing P99 around ~400-600 ns. A **single `Box::new` in this path adds ~50 ns (10% of budget)**; a `HashMap` rehash adds ~10 ms (10,000× over budget); a `Vec::push` that reallocs adds ~100 ns + invalidates the latency tail's predictability. Zero allocation is not "an optimization" — it's the design.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/state_machine.zig` allocator pattern + `lib/tigerbeetle/src/lsm/manifest.zig` for fixed-table sizing; `bumpalo` for arena reference; `slab` Rust crate.
    - **Design**:
      ```rust
      pub struct TransferPool {
          slab: Box<[MaybeUninit<Transfer>; MAX_TRANSFERS]>,     // 1M × 128B = 128MB
          free_list: ArrayVec<u32, MAX_TRANSFERS>,              // indices of free slots
          in_use: BitSet<MAX_TRANSFERS>,
      }
      pub struct AccountMap {
          buckets: Box<[Option<AccountSlot>; MAX_ACCOUNTS]>,    // 16M slots
          // load factor target: 0.75 → effective 12M accounts
      }
      pub struct AccountSlot { id: AccountId, account: Account, version: u32 }
      // open-addressing, robin-hood, no rehash
      ```
      **Invariants**: (i) `Box::new_zeroed()` allocates ONCE at startup; (ii) `apply` panics if pool exhausted (must surface — never silently fail); (iii) `AccountMap` capacity fixed; reaching `0.85` load factor triggers operational warning long before correctness break; (iv) no `Vec::push`, no `HashMap::insert`, no `Box::new` in `apply`.
    - **Build steps**: 1. (~10 min) define `TransferPool::new()` allocating 128MB zeroed once + initializing `free_list` with [0..MAX). 2. (~20 min) `acquire()` pops free slot, marks in_use, returns &mut Transfer + slot_id; `release(slot)` clears in_use, pushes to free_list. 3. (~30 min) `AccountMap` open-addressing impl: hash → bucket → linear probe → robin-hood swap-on-collision. 4. (~25 min) `AccountMap::lookup` / `insert` / `update` — all O(1) avg, O(load_factor / (1-load_factor)) worst. 5. (~20 min) load-factor metric exporter (gauge), warn at 0.75 / error at 0.90. 6. (~20 min) wire into `apply()`: Transfer parses → pool.acquire → mutate accounts via map.update → on commit pool.release. 7. (~25 min) ban allocator calls on hot path: `#[cfg_attr(test, deny(no_alloc_audit))]` lint via `cap` allocator that panics on alloc in test mode. 8. (~30 min) crash-recovery semantics: pool state derived from journal — no separate persistence. 9. (~20 min) write test: 1M Transfers in tight loop, dhat reports 0 allocs during loop (preamble only).
    - **Pitfalls**: *Pool exhaustion under burst*: **Symptom**: pool runs out during burst > 1M concurrent; apply panics; service down. **Fix**: surface exhaustion as backpressure to client (Reject with ErrTooManyInFlight) BEFORE invoking pool.acquire; pool size is hard ceiling. *Hash collisions clustering*: **Symptom**: poor hash distribution → long probe sequences → latency p99 explodes. **Fix**: use BLAKE3-128 truncated as hash (CSPRNG quality), not `DefaultHasher`. *Load-factor surprise*: **Symptom**: accounts grow over time, slowly approach capacity, sudden p99 cliff at 0.9. **Fix**: alarming + operational headroom; document upgrade procedure (snapshot + larger-capacity restore). *MaybeUninit UB*: **Symptom**: reading slot before `acquire` returns wild bytes. **Fix**: `acquire` always `slot.write(Transfer::default())` before returning &mut; never read uninit. *128MB allocation failing on small systems*: **Symptom**: dev test machine OOM. **Fix**: configurable pool size via const generic / env var; default to MAX_TRANSFERS=64k for dev profile.
  - **Expect to hit (perf) #1 — `Vec::push` or `HashMap::insert` *anywhere* in `apply()` (bar (c) violation, fatal)**: a single `tx_pending.insert(id, sender)` using `std::HashMap` on the apply path. At load factor 0.75 the table eventually rehashes — `HashMap::reserve(2 * current_capacity)` allocates a new bucket array (~10 ms for 1M entries: ~50 ns malloc × 1M new buckets + ~5 ns rehash + reinsert per entry). P99 commit latency jumps from <1 µs to **10+ ms** — a **10,000× violation** of the bar. The same applies to `Vec::push` when capacity is reached (`realloc` doubles → ~5 ms for a 1M-element Vec).
    - Fix: zero growable collections in `apply`. (a) `tx_pending: FixedMap<TransferId, oneshot::Sender>` with capacity sized for `MAX_INFLIGHT` (built W89 Tue); (b) `TransferPool` uses `Box<[MaybeUninit<Transfer>; MAX_TRANSFERS]>` allocated **once** at startup; (c) `free_list: ArrayVec<u32, MAX_TRANSFERS>` — never grows; (d) cargo-deny `disallowed_types = ["std::collections::HashMap", "std::vec::Vec"]` in the `ledger-deterministic::state_machine` module (allow `Vec` in tests + setup only via `#[allow]`); (e) dhat audit in CI fails on any apply-path alloc.
    - Cost avoided: ~10 ms rehash latency spike → 0 ns; eliminates the P99 cliff that would otherwise dominate the latency histogram. The 100k Transfers/sec sustained target (W90 acceptance) requires this — a single rehash mid-second drops throughput by 50%+ for the duration.
    - Muscle: bar (c) = static memory = no growable collections on the hot path. The acceptance criterion is **dhat reports 0 allocs in `apply`**, not "we tried to minimize allocs." Reapplies at: W89 Tue ledger FixedMap (the actual fix), W89 Wed VSR ArrayVec body, W89 Thu VSR MessagePool, W90 io_uring journal registered buffers (no per-write malloc), W92 ledger v1.0 SHIP dhat-acceptance gate, W94 exec-vm v1.5 versioned-memory bounded `MAX_VERSIONS=256`.
  - **Expect to hit (perf) #2 — `std::collections::hash_map::DefaultHasher` for AccountMap hash (bar (c) violation: P99 cliff + non-determinism)**: using `DefaultHasher` (SipHash-1-3) for `AccountId` hash. (a) ~30 ns per hash (vs ~3 ns for FxHash or a u64-mix); (b) the seed is randomized per-process, so two replicas hash the same AccountId differently — **bucket layout differs** → probe sequences differ → cache-line residency differs → P99 latency differs across replicas (state_machine output identical, but timing leaks differ, complicating debug); (c) under adversarial input (an attacker who crafts AccountIds to cluster in one bucket), probe sequences degrade from O(1) to O(N), pushing P99 from ~30 ns to ~30 µs.
    - Fix: BLAKE3-128 truncated to `u64`, **or** a hand-mixed `u64` finalizer (`xxhash3` or the Splitmix64 finalizer of `AccountId.as_u64()`). Deterministic, fast (~3 ns), adversarial-resistant. The map's `BuildHasher` is a unit struct — no per-instance random seed. Replicas share bucket layouts; debug across replicas matches byte-for-byte.
    - Cost avoided: ~27 ns/hash × 2 hashes per Transfer (debit + credit) = ~54 ns/apply removed (P50 wins); P99 cliff under adversarial input avoided (~30 µs → ~30 ns probe sequences). For VOPR replay: state_machine output is now bit-identical AND timing-identical across replicas, which catches a class of cache-residency-bug.
    - Muscle: pick the hash function deliberately. `DefaultHasher` is the wrong choice for any hot-path map; `HashMap` itself is the wrong choice for any bar-(c) crate. Reapplies at: W89 Tue FixedMap hash (the same construction), W94 exec-vm v1.5 storage-key hash (storage_key → version-entry lookup), W92 ledger state_hash (BLAKE3 chosen for the same reasons), W74 matching-engine OrderId → Order lookup (FixedMap reuse).
    - **Test scenarios**: dhat report after `apply(op)` × 1M: 0 allocs. Concurrent burst: 999k acquires + 1k releases → pool reaches 999k in_use, OK. Force 1M+1 → panic with ExhaustedErr. Long run: 100M apply, account count 5M, load factor stays below 0.5.
    - **Acceptance**: dhat 0 hot-path allocs; load_factor metric exported; ledger v1.0 RC built with `--features static-mem` gates this on.
    - **Downstream**: io_uring journal (W90) requires alloc-free apply; VSR replication (W91) batches Transfers through pool; v1.0 SHIP (W92) audit-gate on dhat=0.

- [ ] **Build**: `crates/marketdata-kernelbypass/src/af_xdp.rs` — AF_XDP socket using `xdp` crate. Zero-copy receive
  path; requires CAP_NET_ADMIN. (~150 min)
  - **Why**: AF_XDP is the closest OSS analogue to Solarflare/Onload kernel-bypass: packets DMA directly into userspace memory (UMEM) without traversing the kernel networking stack. For 50M+ pps it crushes both epoll and io_uring. Cost: requires CAP_NET_ADMIN, kernel ≥5.4 with XDP support on the NIC driver. Not all NICs support `XDP_FLAGS_DRV_MODE`; SKB mode falls back to slower path.
  - *Back-of-envelope* (AF_XDP target: ≥100M pps single-core; the headline. Budget = **10 ns/packet**):
    AF_XDP's perf model: NIC DMAs the packet directly into a UMEM frame via the descriptor in `fill_ring`; on packet arrival, the kernel writes the descriptor (addr, len) into `rx_ring`; userspace polls `rx_ring` head==tail and consumes. Per-packet cost: `rx_ring` descriptor read ≈ 5-10 ns (single cache-line load from the kernel-shared mmap'd ring); construct `UmemFrame<'a>` ≈ 1 ns (just a struct with addr + len); `fill_ring` add on `UmemFrame::Drop` ≈ 5 ns (one cache-line write back). Total: ~15-20 ns/packet for the ring mechanics; payload read happens lazily at the application layer. To hit 100M pps single-core, the **NIC RX queue must be IRQ-pinned to the same core** (`ethtool -X` + `set_irq_affinity` — otherwise IRQ delivery cost dominates at ~500 ns) and `rx_ring` must be MAP_HUGE_2MB (eliminates TLB misses on the ring walk).
  - **Read first**: Linux `Documentation/networking/af_xdp.rst`, `libxdp` source, `xdp-tutorial` repo (advanced3-AF_XDP), Cloudflare's "How we use HW offload for L7" post.
  - **Design**:
    ```rust
    pub struct AfXdpTransport {
        umem: Umem,                              // mmap'd shared memory region
        rx_ring: RxRing,                         // userspace-visible RX queue
        fill_ring: FillRing,                     // app posts UMEM frame addrs for kernel
        tx_ring: TxRing,                         // not used for ingress-only
        completion_ring: CompletionRing,         // not used for ingress-only
        socket: XskSocket,
        frame_size: u32,                         // 2048 or 4096
    }
    impl Transport for AfXdpTransport {
        type Frame<'a> = UmemFrame<'a>;
        fn recv_batch<'a>(&'a mut self, out: &mut ArrayVec<UmemFrame<'a>, N>) -> usize { /*...*/ }
    }
    pub struct UmemFrame<'a> { umem: &'a Umem, addr: u64, len: u16 }
    // Drop returns frame to fill_ring
    ```
    **Invariants**: (i) UMEM is mmap'd ONCE at startup, size = NUM_FRAMES * FRAME_SIZE; (ii) zero-copy: kernel writes into UMEM, userspace reads — no `recv(2)` call; (iii) `UmemFrame` Drop returns addr to `fill_ring` (RAII); (iv) BPF program attached to NIC redirects matching packets to xskmap[queue_idx].
  - **Build steps**: 1. (~10 min) probe XDP support: `bpf_object__find_program_by_name` against kernel features. 2. (~15 min) UMEM setup: `mmap` 64MB anonymous, register via `xsk_umem__create()`. 3. (~20 min) RX ring + fill ring construction with `xsk_socket__create()` and queue_idx. 4. (~15 min) load minimal BPF program (xdp-redirect-to-xskmap) via libbpf-rs; attach to NIC via `bpf_xdp_attach()`. 5. (~25 min) prime fill_ring with all NUM_FRAMES UMEM addrs. 6. (~20 min) `recv_batch`: poll rx_ring, for each descriptor extract addr+len, construct `UmemFrame`. 7. (~15 min) UmemFrame Drop returns addr to fill_ring; assert no double-free. 8. (~15 min) NIC config helper: `set_irq_affinity()`, `disable_rx_coalescing()`, `set_promisc_mode()` as needed. 9. (~15 min) feature-gate `#[cfg(feature = "af-xdp")]`; require `linux` target + privilege probe at startup.
  - **Pitfalls**: *Driver mode unavailable*: **Symptom**: bpf_xdp_attach with DRV_MODE returns EOPNOTSUPP — NIC driver doesn't support native XDP. **Fix**: fallback to SKB_MODE (slower); document required NICs (mlx5, i40e, ice, etc.). *Frame address leak*: **Symptom**: forgot to fill_ring.add() after consuming; fill ring drains; recv stops. **Fix**: RAII Drop on UmemFrame + assertion that fill_ring count stays ≥ NUM_FRAMES/2. *UMEM alignment violation*: **Symptom**: rx_ring entries reference unaligned addresses; kernel rejects. **Fix**: `mmap` with MAP_HUGE_2MB; FRAME_SIZE a power of two. *CAP_NET_ADMIN absent*: **Symptom**: setup silently degrades or panics. **Fix**: explicit `prctl(PR_CAP_AMBIENT)` check at startup; error message points operator to setcap. *Lost packets with XDP_DROP-by-default*: **Symptom**: BPF doesn't have a redirect rule, all packets drop. **Fix**: pre-load and verify BPF program has explicit redirect.
  - **Expect to hit (perf) #1 — `UMEM` allocated as `Box<[u8; N]>` instead of MAP_HUGE_2MB (bar (c) violation)**: allocating UMEM via the Rust allocator gives 4 KB pages. At 64 MB UMEM = 16,384 pages → 16,384 TLB entries needed for full UMEM residency. L1 TLB on most CPUs holds ~64 entries; L2 TLB ~1500 — so **~93% of UMEM accesses trigger a TLB miss** at ~20-30 ns each. At 100M pps, that's 100M × ~25 ns = 2.5 sec/sec of pure TLB-miss latency — throughput collapses to ~30M pps regardless of all other tuning. The bug doesn't surface in unit tests (small UMEM fits in L1 TLB) — only at full saturation.
    - Fix: `mmap` with `MAP_HUGE_2MB` (or `MAP_HUGE_1GB` if available) → 32 huge pages cover the full 64 MB UMEM, all resident in L1 TLB. Per-packet TLB cost: ~0 ns (L1 TLB hit). Verify with `cat /proc/<pid>/smaps` showing `KernelPageSize: 2048 kB`. Same treatment for `rx_ring`/`fill_ring` (smaller, but still TLB-relevant).
    - Cost avoided: ~25 ns/packet × 100M pps = 2.5 sec/sec → 0 ns. The single biggest perf lever for AF_XDP at saturation; without it, AF_XDP is barely faster than io_uring.
    - Muscle: any mmap'd region ≥1 MB that's hot-path-read benefits from huge pages; the TLB is a real hardware resource with low budget at saturation. Reapplies at: W90 io_uring journal file (1 GB pre-allocated — `O_DIRECT` + huge-page-aligned buffer), W90 ledger v1.0 static-mem 128 MB Transfer pool (`Box::new_zeroed` on a huge-page-backed allocator), W82 matching-engine OrderBook backing array, W92 versioned-memory DashMap shards.
  - **Expect to hit (perf) #2 — NIC RX IRQ on a different core from the AF_XDP poller (bar (c) violation)**: the NIC's RX IRQ fires on whichever core the OS scheduler assigns (typically core 0); the AF_XDP poller runs pinned to core N. Each packet's IRQ → soft-IRQ → wakeup of the poller crosses cores: ~500 ns IPI + cache-line bounce for the rx_ring producer cursor. At 50M pps × 500 ns = 25 sec/sec of cross-core stall — throughput collapses to ~5M pps despite zero-copy. The "real" CPU usage looks low because most time is stalled, not executing.
    - Fix: pin the NIC RX queue IRQ to the same core as the poller: (a) `ethtool -X rx-flow-hash` to direct packets for the multicast group to a specific RX queue; (b) `echo <core_mask> > /proc/irq/<irq_for_that_queue>/smp_affinity`; (c) the AF_XDP poller is pinned to that same core. Per-packet IPI cost: 0 ns (no cross-core wakeup). Combined with `IORING_SETUP_SQPOLL`-style busy-polling, the poller wakes on rx_ring cursor advance via in-core read.
    - Cost avoided: ~500 ns/packet IPI removed → 0; at 50M pps = 25 sec/sec → 0 sec/sec. The single biggest setup-time perf lever after huge pages.
    - Muscle: in a kernel-bypass / busy-poll architecture, **co-locate the IRQ-source core, the NIC RX queue, and the poller** — any cross-core hop in the data plane is fatal. Reapplies at: W90 io_uring journal (poller on same core as fsync-issuing thread), W82 matching-engine shards (per-symbol core pin via runtime-thread-per-core W85), W92 ledger replica pin (one VSR replica per core, no cross-core message passing in the apply hot path), W77 messaging-aeron subscriber pin (Image bound to consumer shard).
  - **Test scenarios**: 50M pps synthetic via DPDK pktgen or another machine → recv loss <0.001%; Drop-test: drop UmemFrame without consuming → fill_ring count returns to NUM_FRAMES; long run 1h at 50M pps → no FD leak, no UMEM leak.
  - **Acceptance**: 50M pps single-thread loss-free on supported NIC; CPU usage <1 core; comparable bench output to epoll/io_uring in W89 Fri.
  - **Downstream**: feed_handler can use AfXdpTransport for the hot ingress; bench result drives v0.5 SHIP decision (default transport per environment).

- [NEW v2] **ledger v1.0: static-memory invariants (part 2)**
  - [ ] **Build**: account map as fixed-size hash table (open addressing) — no rehash. (~2 hrs)
    - **Why**: HashMap with rehash is incompatible with bar (c) — rehash is a multi-ms allocator-storm and would invalidate latency tail. TigerBeetle uses a fixed-size open-addressing table sized once at startup. No rehash, no Vec growth. Load factor is monitored; capacity is rated and operator-tunable.
    - *Back-of-envelope* (FixedMap target: **get P99 < 200 ns at load factor ≤ 0.5**, derives directly from ledger v1.0's 1 µs apply budget — two lookups per Transfer × 200 ns = 400 ns, fits with margin):
      Per-`get` cost: hash ≈ 3 ns (hand-mixed u64 finalizer, the W89 Mon perf #2 fix); bucket calc `hash & (N-1)` ≈ 1 ns; first slot read ≈ 4 ns (L1 if hot, ~7 ns L2 if cold); `hash_top` compare on hit ≈ 1 ns; key compare on `hash_top` match ≈ 2 ns; total ~11 ns on the no-probe path. With robin-hood + load 0.5, average probe distance ≈ 1.5 slots × ~4 ns = ~6 ns extra; P99 probe distance ≈ 16 slots × 4 ns = ~64 ns. Total `get` P99 ~75-200 ns ✓. At load **0.85** (the documented hard cap), P99 probe distance jumps to ~256 slots × 4 ns = ~1 µs — over budget by 5×. **Therefore load factor 0.85 is correct as an emergency cap, but the operational target is 0.5** — 16M slots for 8M accounts max.
    - **Read first**: `hashbrown::raw::RawTable` for SIMD probe reference; Daniel Lemire's "Robin Hood Hashing in Rust"; TigerBeetle `lib/tigerbeetle/src/lsm/grid.zig` table sizing.
    - **Design**:
      ```rust
      pub struct FixedMap<K: Eq + Hash + Copy, V> {
          slots: Box<[Slot<K, V>; N]>,
          len: u32,
          tombstones: u32,
      }
      enum Slot<K, V> { Empty, Tombstone, Occupied { hash_top: u32, key: K, value: V, probe_dist: u16 } }
      impl<K, V> FixedMap<K, V> {
          pub fn insert(&mut self, k: K, v: V) -> Result<(), MapFull>;
          pub fn get(&self, k: &K) -> Option<&V>;
          pub fn remove(&mut self, k: &K) -> Option<V>;
      }
      ```
      **Invariants**: (i) `Box::new()` ONCE at startup, capacity N is const generic; (ii) no rehash — `MapFull` returned when load_factor > 0.85; (iii) robin-hood: minimize variance of probe_dist; (iv) tombstones counted; cleaned on opportunistic scan; (v) hash_top = top 32 bits of hash, used to skip key compare on probe miss.
    - **Build steps**: 1. (~15 min) struct + Box-zeroed allocation. 2. (~25 min) `insert`: hash(K), bucket = hash % N, robin-hood loop: if `slot.probe_dist < new_probe_dist` swap. 3. (~20 min) `get`: hash → bucket → linear probe comparing `hash_top` first, then key. 4. (~15 min) `remove`: write Tombstone; if next slot is Empty, walk back collapsing tombstones (or defer). 5. (~10 min) load_factor + tombstone_ratio metrics. 6. (~10 min) capacity sizing helper: `FixedMap::with_max_keys(max_keys)` → N = next_power_of_two(max_keys * 4/3). 7. (~10 min) deny rehash: compile error if capacity dynamic. 8. (~15 min) unit + property tests: random insert/remove sequence → get matches `BTreeMap` reference.
    - **Pitfalls**: *Insert at load=1.0*: **Symptom**: infinite loop. **Fix**: hard cap at 0.95, return MapFull. *Tombstone accumulation*: **Symptom**: high churn → table looks full of tombstones; get probes every slot. **Fix**: opportunistic rebuild during insert if tombstone_ratio > 0.25; OR forbid remove on hot path. *Hash quality*: **Symptom**: malicious key sequence causes clustering. **Fix**: `BuildHasher` with random seed at startup; for adversarial input use BLAKE3. *Robin-hood swap bug*: **Symptom**: invariant break — distant probe_dist on lookup, get misses. **Fix**: assert probe_dist monotonic during get; property tests with random ops.
  - **Expect to hit (perf) #1 — `Slot<K, V>` enum tag costs an extra cache-line read (bar (c) violation)**: implementing slots as `enum Slot<K, V> { Empty, Tombstone, Occupied { ... } }` looks clean but Rust lays this out as discriminant (1-8 B) + max-variant-payload. For `(K=u128, V=Account)` the slot is ~80 B — straddles a 64 B cache line. Each probe reads 2 cache lines = ~10-14 ns instead of one ~7 ns. At ~3 probes average × 2 cache lines × 7 ns = 42 ns/get; vs the 11 ns achievable with single-line slots — a 4× regression that puts P99 over budget.
    - Fix: separate the state out: `slots: Box<[Slot<K, V>; N]>` where `Slot<K, V> { state: SlotState, hash_top: u32, key: K, value: V, probe_dist: u16 }` with `SlotState: u8 = { 0 = Empty, 1 = Tombstone, 2 = Occupied }`. Order fields by access frequency: `state` + `hash_top` first (probed every step), then `key` (compared on hash_top match), then `value` (read only on hit). Verify with `const _: () = assert!(size_of::<Slot<u128, Account>>() <= 64);`. Or: state-byte array separated from key/value arrays (SoA), so probing only touches the state array — best for very large maps.
    - Cost avoided: ~7 ns/probe cache miss × 3 probes × 2 lookups (debit + credit) = ~42 ns saved per Transfer apply. Combined with perf #2 (hash quality), keeps the AccountMap P99 lookup within budget.
    - Muscle: data layout > algorithm in tight L1-budget code. The `enum` ergonomics tax is real; `#[repr(C)]` + explicit state byte beats `enum` on the hot path. Reapplies at: W74 matching-engine PriceLevel layout (W003 perf #3 reapplication), W94 exec-vm versioned-memory `Entry` enum (same Empty/Estimate/Value choice), W77 messaging-aeron term-buffer header layout, W82 matching-engine OrderId-slot layout.
  - **Expect to hit (perf) #2 — robin-hood swap missing the variance-minimization property (bar (c) violation: P99 cliff)**: implementing insert as "probe until empty, place new entry there" — i.e., linear probing without the robin-hood swap. Under load 0.5 with uniform random keys this performs OK; under any clustering (e.g., a burst of sequential AccountIds), max probe distance grows to ~50-100 slots while average stays ~2. The variance is the killer: P99 lookup jumps from ~50 ns to ~500 ns — over the 200 ns target.
    - Fix: robin-hood — at each probe, if the **existing** slot's `probe_dist < new_entry's probe_dist`, swap them and continue probing with the displaced entry. Property: probe_dist variance is bounded by `O(log N)` (vs `O(N)` linear); max probe dist in a 16M-slot table at load 0.5 is ~16 slots (P99) vs ~100 slots linear. P99 lookup stays within the 200 ns target even under adversarial input.
    - Cost avoided: ~300-500 ns/get on the P99 tail under realistic clustering → ~50 ns. The variance-minimization is what makes the P99 budget achievable; without it, average is fine but tail breaks.
    - Muscle: in any hash table on the bar-(c) hot path, the choice isn't "linear probing or robin-hood" — it's "robin-hood because P99 variance is the load-bearing metric." Reapplies at: W94 exec-vm versioned-memory slot probe (uses skiplist instead, but same variance-minimization argument), W74 matching-engine OrderId → Order map, W90 consensus-vsr replica-state lookup.

      ```rust
      pub struct MessagePool {
          slabs: Box<[VsrMessage; POOL_SIZE]>,        // POOL_SIZE = 1024 per replica
          free_ids: ArrayQueue<u32>,                  // free indices (MPMC)
          in_flight_counter: AtomicU32,
      }
      pub struct PooledMessage<'a> { pool: &'a MessagePool, slab_id: u32 }
      impl<'a> Drop for PooledMessage<'a> { fn drop(&mut self) { /* return to free_ids */ } }
      impl MessagePool {
          pub fn new(size: u32) -> Self;
          pub fn acquire(&self) -> Option<PooledMessage<'_>>;
          pub fn in_flight(&self) -> u32;
      }
      ```
