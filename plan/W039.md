**Monday — `lsm-core` SSTable format**

- [ ] **Build**: `crates/lsm-core/src/sst/mod.rs` —
  `SSTable { blocks: Vec<Block>, index: BlockIndex, bloom: bloom::ClassicBloomFilter, meta: SstMetadata }`. Footer
  encodes index + bloom offsets. (~150 min)
  - **Why**: SSTable is the LSM's on-disk format. The layout — data blocks + index block (first-key-per-data-block) + filter block (bloom) + footer — is the consensus design across LevelDB/RocksDB/Cassandra. The footer is the entry point: fixed-position at end of file, with magic number + offsets to index and bloom. Get the footer wrong and you can't open the file; get the bloom wrong and you eat 100% of unnecessary block reads.
  - *Back-of-envelope*: SSTable file typically 64-256 MB, mmap'd. **Target open + parse < 1 ms** (one mmap call + footer read at last 32 B + parse index + load bloom). Index ≈ 1 KB per 100 K entries (first-key + 8 B offset per data block) — fits in one mmap page. Bloom ≈ 10 bits/key → for 100 K entries, ~125 KB → fits in 2-3 mmap pages, kept resident. Per data block: 4-32 KB. Open is one-shot per SSTable; the cost amortizes over millions of get() ops.
  - **Read first**: RocksDB `table/block_based/block_based_table_builder.cc`; LevelDB `table/format.cc` (Footer format).
  - **Design**:
    ```rust
    pub struct SSTable {
        file: Arc<Mmap>,
        index: BlockIndex,
        bloom: bloom::ClassicBloom,
        meta: SstMetadata,
    }
    #[repr(C)]
    pub struct Footer {
        index_offset: u64,
        index_len: u64,
        bloom_offset: u64,
        bloom_len: u64,
        magic: u64, // SST_MAGIC = 0xF73A_5EBC_88CD_9E10
    }
    pub struct BlockIndex {
        // first_key_per_block[i] is the largest key <= than all keys in block i
        entries: Vec<(Bytes, u64)>, // (first_key, byte_offset)
    }
    ```
    **Invariants**:
    - File layout: [block_0][block_1]...[block_n][bloom_block][index_block][footer]
    - Footer at last `sizeof(Footer)` bytes; magic validates the format.
    - Index entries are sorted by first_key; each contains offset to a data block.
  - **Build steps**:
    1. (~25 min) Footer struct, fixed-size encoding (LE), magic constant.
    2. (~45 min) `open(path) -> Result<SSTable>`: mmap file; read footer; load + parse index + bloom; validate magic.
    3. (~50 min) `BlockIndex`: binary-search by key returning block offset.
    4. (~25 min) Tests: open known-good fixture; reject bad magic; reject truncated.
    5. (~5 min) Doc + commit.
  - **Pitfalls**:
    - *Footer offset confusion*: writing offsets relative to bloom block start vs. file start. **Symptom**: open succeeds but seek goes to wrong bytes. **Fix**: always file-absolute offsets.
    - *Magic mismatch on cross-version files*: SST written by future code version unreadable. **Symptom**: silent open failure. **Fix**: include format_version in footer; reject with typed error.
    - *Mmap address aliasing*: parsing index in-place exposes `&Bytes` borrowed from mmap; iterator outlives the mmap. **Symptom**: UAF on drop. **Fix**: index entries own their key bytes (clone on parse).
  - **Test scenarios**:
    - Round-trip: write SSTable with 10k entries; open + verify metadata.
    - Adversarial: truncate last 32 bytes → open returns InvalidFooter.
    - Bit-flip in magic → typed error, no panic.
  - **Acceptance**: open + parse < 1ms; format documented byte-exactly.
  - **Downstream**: W39 reader, W40 compaction consumer, W95 mini-db.
- [ ] **Build**: `crates/lsm-core/src/sst/builder.rs` — `SstBuilder` streams kvs into blocks, populating bloom + index
  incrementally. (~150 min)
  - **Why**: Builder is the streaming write path: accept sorted KV stream, accumulate into current block until threshold, flush block, record index entry, populate bloom, repeat. Memory bound is one block + bloom + accumulating index — must not require full SST in RAM. The bloom must size for the total entry count, which is unknown at start; you either fix capacity ahead of time (from memtable size) or build, finalize, and rebuild bloom (wasteful).
  - *Back-of-envelope*: streaming write of N sorted KVs into one SSTable. **Target ≥ 500 k entries/sec single-thread**. Memory bound: ONE block in flight (~16 KB) + bloom (~125 KB at 100 K) + accumulating index (~1 KB per 100 K) ≈ **~150 KB total, regardless of N** — flush of a 256 MB memtable holds the same ~150 KB. Disk I/O is sequential write at the NVMe rate (~1-3 GB/sec). fsync at finish (~1 ms NVMe / ~5 ms HDD). The atomic-rename pattern is the crash-safety invariant — see existing pitfall on fsync ordering.
  - **Read first**: RocksDB `table/block_based/block_based_table_builder.cc`.
  - **Design**:
    ```rust
    pub struct SstBuilder {
        out: BufWriter<File>,
        current_block: BlockBuilder,
        index_entries: Vec<(Bytes, u64)>,
        bloom: ClassicBloom, // sized by expected_count
        offset: u64,
        last_key: BytesMut,
        block_size_target: usize, // 4-32 KB
    }
    impl SstBuilder {
        pub fn new(path, expected_count, fpr) -> Self;
        pub fn add(&mut self, key: &[u8], val: ValueOrTombstone) -> Result<()>;
        pub fn finish(self) -> Result<SSTable>;
    }
    ```
    **Invariants**:
    - Adds must be in sorted key order (debug-assert on each add).
    - block_size_target is a soft cap; never split mid-entry.
    - Bloom holds every distinct key (tombstones too, so reads check correctly).
  - **Build steps**:
    1. (~30 min) Builder skeleton + sorted-order assertion.
    2. (~40 min) `add`: append to current block; on threshold, flush block, record index entry, reset block.
    3. (~30 min) `finish`: flush trailing block, write bloom block, write index block, write footer, sync.
    4. (~30 min) Atomic-rename pattern: write to `<file>.tmp`, fsync, rename to `<file>` (crash-atomic).
    5. (~20 min) Tests + bench.
  - **Pitfalls**:
    - *Block split mid-entry*: forgetting to keep entries whole produces unreadable blocks. **Symptom**: decoder panic on first malformed entry. **Fix**: split only after a fully-encoded entry.
    - *Fsync forgotten before rename*: rename without prior fsync can produce a renamed-but-empty file on crash. **Symptom**: corrupted SSTable. **Fix**: fsync data fd, rename, fsync parent dir.
    - *Bloom over-/under-sized*: under → FPR collapse; over → wasted RAM and disk. **Fix**: use the memtable's tracked entry count; round up 10%.
  - **Test scenarios**:
    - Build 1M entries; verify file size matches expected; reopen & probe.
    - Crash sim: kill between data write and rename; recovery sees no .tmp file (or skips it).
  - **Acceptance**: 1M-entry build < 2s; crash-atomic (kill-9 leaves no torn SST).
  - **Downstream**: W39 reader, W40 compaction, W95 mini-db.

**Tuesday — `lsm-core` SST read path**

- [ ] **Build**: `crates/lsm-core/src/sst/reader.rs` — `SstReader` mmap-backed, bloom-filter-first lookup, block-load
  via `bufpool`. (~150 min)
  - **Why**: The SST read path is the dominant read cost for an LSM. Order of operations: (1) bloom check — if negative, skip entirely; (2) binary search index for block; (3) load block (bufpool cache hit) and decode; (4) seek within block. Each layer is a 10-100x filter; missing the bloom layer increases reads by ~100x.
  - *Back-of-envelope*: dominant LSM read cost. **Target negative get (bloom-rejected) < 50 ns** (bloom probe only, no allocator); positive get ≈ ~500 ns warm (bloom + index binary search + block-cache hit + intra-block linear scan within restart group). Block cache hit rate target ≥ 95% in steady state; cache miss is ~50-200 µs SSD random read. The 10:100:1000 filter cascade (bloom → index → block → entry) means a single mis-sized bloom (10× too small) cascades to 10× more I/O.
  - **Read first**: RocksDB `table/block_based/block_based_table_reader.cc::Get`.
  - **Design**:
    ```rust
    pub struct SstReader {
        sst: SSTable,
        block_cache: Arc<bufpool::Cache<u64, Arc<Block>>>, // offset -> decoded
    }
    impl SstReader {
        pub fn get(&self, key: &[u8]) -> Result<Option<ValueOrTombstone>>;
        pub fn iter(&self) -> SstIter<'_>;
        pub fn seek(&self, key: &[u8]) -> SstIter<'_>;
    }
    ```
    **Invariants**:
    - Negative bloom + return None is a hot path; <50ns excluding allocator.
    - Block cache holds decoded blocks; mmap holds raw bytes; bloom is in-memory.
    - Iter yields entries in sorted order; tombstones are visible to caller.
  - **Build steps**:
    1. (~20 min) `get` skeleton: bloom check; on negative, return None.
    2. (~30 min) Binary search index by key; load block (cache or mmap decode).
    3. (~30 min) Seek within block; return value or None if key not present (bloom false positive).
    4. (~30 min) Iterator: stream blocks in order; each block iter is `BlockIterator`.
    5. (~30 min) Tests including the 1M random gets bench.
    6. (~10 min) Doc.
  - **Pitfalls**:
    - *Block cache key collision*: caching by `block_idx` instead of `(sst_id, block_idx)` mixes blocks across SSTs. **Symptom**: wrong data on hot read. **Fix**: cache key includes file-id.
    - *Bloom false positive ignored*: assuming bloom-hit means key-present skips the in-block lookup; you return random value. **Symptom**: corruption. **Fix**: bloom is may-be-present; always verify in-block.
    - *Mmap fault on cold read*: first access to a page is a page fault (slow). **Symptom**: tail latency outliers. **Fix**: optional `MAP_POPULATE`; or background prefetcher.
  - **Test scenarios**:
    - 100k unique keys; 1M get of non-existent keys: ≥99% bloom-rejected.
    - 1M get of existing keys: all return correct value.
    - Concurrent: 16 threads × 100k gets; no data races (cache is shared).
  - **Acceptance**: 1M get on 100k SST < 500ms; bloom hit rate ≥99% for negative lookups.
  - **Downstream**: W40 compaction (read SSTables to merge); W42 txn read path; W95 mini-db.
  - **Expect to hit (perf) #1 — `Mutex<HashMap>` block cache (bar (c) violation)**: caching with `Mutex<HashMap<(SstId, u64), Arc<Block>>>` serializes every block fetch behind one lock. Under heavy read load (16 threads × 100 K gets/sec each), the mutex becomes the read bottleneck even though cache hits should be sub-microsecond.
    - Fix: `dashmap` (sharded concurrent map) or `quick_cache` (concurrent LRU). Cache key includes `SstId` so blocks from different SSTs don't collide. Hot path: shard lookup ≈ ~30 ns uncontended; full lock-free under shard locality.
    - Cost avoided: ~50 ns lock overhead per cache hit × 16 threads × 100 K = ~80 ms/sec aggregate eliminated; removes the read-side scalability ceiling.
    - Muscle: shared read-cache structures use concurrent maps, not mutex-guarded HashMaps. Reapplies at: W14 bufpool page table (DashMap), W42 `txn` read snapshot cache, W74 matching-engine symbol table.
- [ ] Test: write 100k unique keys to SST, read back 1M random gets — bloom rejects ≥99% of non-existent keys. (~30 min)

- [ ] **Build**: `crates/lsm-core/src/write_path.rs` —
  `flush_memtable_to_l0(mem: MemTable, dir: &Path) -> Result<SstReader>`. Wal-backed. (~150 min)
  - **Why**: The flush path is the contract between memtable and persisted state. Until flush completes durably, the WAL is the truth (consume W26 wal); after, the SSTable is the truth and the WAL can be truncated. Get the ordering wrong (truncate WAL before sync) and you lose data on crash. This is the canonical "rotate immutable handle, build new SST, persist, swap, GC" pattern that recurs in every LSM.
  - *Back-of-envelope*: flush is rare (~1/sec under steady writes) but each flush moves up to `memtable_size` (~256 MB) to disk. **Target: 256 MB flush completes in ≤ 1 s** (~256 MB/sec write throughput, NVMe-bound). Flush runs on the background thread — writes against the **active** memtable never wait on flush (the active and immutable memtables are distinct). Manifest update + WAL truncation ordering is the crash-safety invariant (existing pitfall on WAL truncation timing).
  - **Read first**: RocksDB `db/flush_job.cc::Run`; mini-lsm Week 1 Day 6 (force_flush).
  - **Design**:
    ```rust
    pub fn flush_memtable_to_l0(
        mem: Arc<MemTable>, // immutable handle, the rotated memtable
        wal_lsn_high: Lsn,  // highest WAL record covered by this memtable
        dir: &Path,
        manifest: &Manifest,
    ) -> Result<SstReader>;
    ```
    **Invariants**:
    - mem is the previously-rotated immutable memtable (not the active one).
    - After return: SST file exists and is fsynced; manifest references it; WAL up to wal_lsn_high can be truncated.
    - On error: no partial SST visible (atomic-rename); memtable still serves reads.
  - **Build steps**:
    1. (~20 min) Allocate `<sst_id>.sst.tmp`; create `SstBuilder` sized to memtable entry count.
    2. (~30 min) Iterate memtable in order (consumes scan); add to builder.
    3. (~30 min) `finish` builder; fsync file; rename to `<sst_id>.sst`; fsync parent dir.
    4. (~30 min) Update manifest atomically: append `+L0[<sst_id>]` record, fsync manifest log.
    5. (~30 min) Return `SstReader::open`.
    6. (~10 min) Tests.
  - **Pitfalls**:
    - *WAL truncation before manifest fsync*: if you truncate WAL then crash before manifest is durable, on restart neither WAL nor manifest reference the data. **Symptom**: data loss. **Fix**: WAL truncation happens after manifest fsync; treat WAL retention as the safety net.
    - *Manifest write torn*: appending without crash-safe protocol (length-prefix + CRC, replay-from-start) leaves a torn manifest. **Symptom**: open fails or partial state. **Fix**: each manifest record is CRC-checked; replay tolerates tail corruption (truncate at first bad record).
    - *Tombstone elision at L0*: L0 must preserve tombstones (lower levels still hold the value). Eliding tombstones here causes resurrection. **Fix**: tombstone elision only at the bottom level during compaction.
  - **Test scenarios**:
    - Memtable with 10k mixed puts+deletes; flush; open SST; reads return matching values + tombstones.
    - Crash sim: kill between rename and manifest sync; recovery either sees no SST or sees fully-registered SST.
    - Concurrent: write to active memtable while flushing immutable; no interference.
  - **Acceptance**: 1M-entry flush < 2s; crash-safe under kill-9 at any point.
  - **Downstream**: W40 STCS compaction reads flushed L0; W42 txn flush boundary; W95 mini-db.
