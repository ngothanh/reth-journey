**Monday — `lsm-core` SSTable format**

- [ ] **Build**: `crates/lsm-core/src/sst/mod.rs` —
  `SSTable { blocks: Vec<Block>, index: BlockIndex, bloom: bloom::ClassicBloomFilter, meta: SstMetadata }`. Footer
  encodes index + bloom offsets. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: SSTable is the LSM's on-disk format; every downstream (W39 reader, W40 compaction,
    W95 mini-db) opens this file. Footer offset confusion → open succeeds but reads from wrong bytes. Mmap
    aliasing → UAF on drop. Magic mismatch handling determines cross-version migration story.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: on-disk format for an immutable sorted KV table. Footer at fixed
    end position is the entry point; it points to bloom + index blocks; data blocks fill the rest. Layout
    invariants must survive across machine endianness, code versions, and crash-truncation.

  - **Requirements** — write in `crates/lsm-core/notes/39_sstable_design.md`:
    - R1. File layout: `[data_0]…[data_n][bloom_block][index_block][footer]`. Footer at last
      `sizeof(Footer)` bytes.
    - R2. **All offsets are file-absolute** — never relative to a sub-block.
    - R3. Footer carries a magic number (`SST_MAGIC = 0xF73A_5EBC_88CD_9E10`) and a `format_version: u32`;
      cross-version files reject with a typed error.
    - R4. **Mmap safety**: index entries own their key bytes (cloned on parse); never borrow from the mmap
      after parse, otherwise the index outlives the file mapping.
    - R5. `open(path) -> Result<SSTable>`: one mmap, one footer-read (32 B), parse index + bloom, validate
      magic.
    - R6. Open + parse < 1 ms (steady state); amortizes over millions of `get()` calls.
    - R7. Truncated/corrupt files reject with typed errors (`InvalidFooter`, `MagicMismatch`,
      `IndexCorrupt`); never panic.

  - **Design walk-through** — answer each:
    - D1. Why footer at the END of the file (not the beginning)? What does that buy on the write path?
    - D2. Footer fields: `index_offset`, `index_len`, `bloom_offset`, `bloom_len`, `magic`,
      `format_version`. Why fixed-size LE encoding? What's the total size?
    - D3. Mmap lifetime: the file is `Arc<Mmap>` shared across the SSTable's lifetime. What if the
      index borrows from the mmap (`&[u8]`)? When does that go wrong?
    - D4. Magic mismatch behavior: log + return error, or panic? Why never panic on file-format errors
      (cite: a corrupted SST should not take down the process)?
    - D5. format_version migration: write the read-side logic. What does a v1 reader do when it sees a
      v2 file?
    - D6. **Pre-mortem (load-bearing)**: write the offset-confusion trace — footer encodes offsets
      relative to the bloom block start (developer error); reader interprets them as file-absolute;
      seeks to bytes 1-200 of the file (random data) instead of bytes 64M-65M (bloom location).
  - **Output**: `notes/39_sstable_design.md` with R1–R7, D1–D6.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **When `sstable_round_trip_10k_entries` reports random data on seek (open succeeds, reads
    garbage):**
    - Symptom: open completes; first `get(k)` returns garbage; subsequent gets crash on bad varints.
    - Why: footer offset confusion — writing offsets relative to bloom block start vs. file start.
      Open succeeds but seek goes to wrong bytes.
    - Fix: always file-absolute offsets. The writer's `current_offset` counter starts at 0 (file
      start) and accumulates byte-by-byte; footer's `bloom_offset` and `index_offset` are values of
      this counter at the moment those blocks were written.
    - Muscle: any multi-block format must commit to one offset convention and document it at the
      footer. Reapplies at: W77 aeron archive segment offsets, W26 WAL segment offsets.

  - **When `sstable_magic_mismatch_rejects` reports a panic instead of a typed error:**
    - Symptom: flip a magic bit; `open()` panics on `panicked at 'magic mismatch'`. Production cannot
      tolerate a panic on file corruption.
    - Why: SST written by future code version unreadable. Silent open failure (or panic) is wrong;
      the right behavior is a typed error.
    - Fix: include format_version in footer; reject with typed error. Match on magic in `open()`;
      `if magic != SST_MAGIC || version != EXPECTED { return Err(SstError::MagicMismatch { found,
      expected }) }`.
    - Muscle: file-format validation MUST be a typed error, never a panic. Reapplies at: W26 WAL
      header validation, W77 aeron archive header.

  - **When `sstable_index_outlives_mmap_compiles` reports a runtime UAF instead of compile failure:**
    - Symptom: lifetime annotations on `BlockIndex` allow an entry's `&[u8]` to outlive the `Mmap`;
      after `SSTable::drop`, queries via the now-dangling reference UAF.
    - Why: mmap address aliasing — parsing index in-place exposes `&Bytes` borrowed from mmap;
      iterator outlives the mmap.
    - Fix: index entries own their key bytes (clone on parse). `BlockIndex { entries: Vec<(Bytes,
      u64)> }` where `Bytes` is owned (`Bytes::copy_from_slice(&mmap[...])`).
    - Muscle: any structure outliving a mapping must own its bytes, not borrow. Reapplies at: W26
      WAL replay index, W77 aeron archive index.

    SSDs become standard (write only sequentially within a zone), the file layout must respect zone
    boundaries. State the migration: SSTable as zone-aligned segments; trigger when ZNS-only NVMe

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: stream sorted KVs into an immutable on-disk SST while maintaining
    memory bound + crash atomicity. Open question: bloom sizing. The bloom holds all distinct keys, but we
    don't know the count until `finish`; the policy is to use the memtable's tracked count + 10% slack.

  - **Requirements** — write in `crates/lsm-core/notes/39_sstbuilder_design.md`:
    - R1. Memory bounded: 1 block in flight (~16 KB) + bloom (~125 KB) + index (~1 KB / 100 K) — total

    - R2. **Sorted-order discipline** — debug_assert! on every `add` that key > last_key.
    - R3. **Block split only between entries** — never mid-entry; split fires after the current entry
      completes encoding and the block exceeds target.
    - R4. **Crash-atomic finish**: write `.tmp`, fsync data fd, rename to final name, fsync parent dir.
      Kill-9 at any point leaves either no SST or a complete SST.
    - R5. Bloom sized by expected_count (from memtable), rounded up 10%.
    - R6. ≥ 500 k entries/sec single-thread build.
    - R7. 1 M-entry build < 2 s.

  - **Design walk-through** — answer each:

    - D2. The atomic-rename pattern: write the 4 syscalls in order. Why fsync the data fd BEFORE
      rename? Why fsync the PARENT dir AFTER rename?
    - D3. Bloom sizing: at memtable rotation, you know the entry count exactly (or have a 10% upper
      bound). Why round up?
    - D4. Block size target vs hard cap: why "soft" (allow one entry over)? When would a hard cap be
      worse?
    - D5. Crash-recovery sweep on startup: how do you detect orphaned `.tmp` files? Policy: delete
      them, or rename them to final?

      flush; entry's bytes are split across two blocks; decoder panics.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **When `sstbuilder_crash_atomic_no_torn_sst` reports an empty `.sst` after crash:**
    - Symptom: kill -9 between rename and the final fsync; restart shows the `.sst` file exists but
      is 0 bytes (or has the index but no data). On open, magic check fails → file marked corrupt.
    - Why: fsync forgotten before rename — rename without prior fsync can produce a renamed-but-empty
      file on crash. The page cache held the data; rename committed to disk before the data did.
    - Fix: fsync data fd BEFORE rename; rename; fsync parent dir AFTER rename. The parent fsync
      ensures the rename itself is durable; the data fsync ensures the bytes are on the platter
      before the rename promises they are.
    - Muscle: any "write then rename" pattern is "write, fsync data, rename, fsync dir" — both
      fsyncs are load-bearing. Reapplies at: W26 WAL segment rotation, W77 aeron archive segment
      finalize.

  - **When `sstbuilder_block_split_only_between_entries` reports decoder panic on a malformed block:**
    - Symptom: decoder reads a varint, gets a huge length value, panics on out-of-bounds. The block
      was split in the middle of an entry — half the entry's bytes are at the end of block N, half
      at the start of block N+1.
    - Why: forgetting to keep entries whole produces unreadable blocks.
    - Fix: split only after a fully-encoded entry. The check is `if current_block.size() >
      block_size_target && current_block.last_entry_complete()` — both conditions. Soft cap accepts
      one entry of overshoot.
    - Muscle: any size-bounded buffer with structured entries must split between entries, never
      mid-entry. Reapplies at: W26 WAL segment, W77 aeron frame batching.

  - **When `sstbuilder_bloom_size_within_10pct` reports an undersized bloom (50%+ FPR):**
    - Symptom: bloom built for 100 k entries actually holds 130 k (memtable count was a lower
      bound); FPR collapses from 0.01 to 0.4.
    - Why: bloom over-/under-sized — under → FPR collapse; over → wasted RAM and disk.
    - Fix: use the memtable's tracked entry count; round up 10%. The memtable's sharded counter is
      an exact count (it accounts for tombstones too); the +10% slack absorbs the unlikely case where
      the count drifts.
    - Muscle: bloom sizing must round UP — undersizing is a silent FPR cliff. Reapplies at: W34
      bloom-classic sizing, W101 vector-db PQ codebook sizing.

    fsync ordering changes to barrier-flag submissions. State the migration: introduce

**Tuesday — `lsm-core` SST read path**

- [ ] **Build**: `crates/lsm-core/src/sst/reader.rs` — `SstReader` mmap-backed, bloom-filter-first lookup, block-load
  via `bufpool`. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: SST read path is the dominant LSM read cost; the bloom → index → block cascade
    determines whether negative gets are 50 ns or 50 µs. Wrong cache key → silent data corruption across SSTs.
    Wrong cache concurrency → 16-thread read scalability ceiling.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: the SST get path is a filter cascade — bloom (10× filter) → index
    (10× filter) → block (100× filter) → entry. A negative bloom returns None in 50 ns; a positive bloom +
    cache-miss is 50-200 µs disk I/O. The cliff between these two paths drives the LSM's read latency story.

  - **Requirements** — write in `crates/lsm-core/notes/39_sstreader_design.md`:
    - R1. `get(key)` bloom-checks first; on negative, return None in ≤ 50 ns.
    - R2. On positive bloom, binary-search index for block; load block (cache or mmap-decode); seek within
      block.
    - R3. **Bloom hit verifies in-block** — never trust the bloom as proof; always seek within the block.
    - R4. **Cache key includes SstId** — `(SstId, block_offset)` to prevent cross-SST cache collisions.
    - R5. **Cache is concurrent (DashMap/quick_cache)** — never `Mutex<HashMap>`; the cache must be
      lock-free under shard locality.
    - R6. Block cache hit rate ≥ 95% steady state.
    - R7. 1 M get on 100 K SST < 500 ms; bloom hit rate ≥ 99% for negative lookups.

  - **Design walk-through** — answer each:
    - D1. Filter cascade math: bloom 10×, index 10×, block 100×. If bloom is 10× undersized (1 → 0.1
      filter), what's the cascade cost?
    - D2. Cache key: why include SstId? Write the cross-SST collision trace.
    - D3. Concurrent cache choice: DashMap vs quick_cache vs Mutex<HashMap>. Why is Mutex disqualified
      at 16-thread workloads?
    - D4. Mmap fault on cold read — the first read of a page triggers a page fault (~10 µs). When
      does this matter? Mitigation: MAP_POPULATE, or a background prefetcher.
    - D5. Bloom false positive verification: write the `get` flow showing bloom-positive followed by
      in-block seek that returns None.
    - D6. **Pre-mortem (load-bearing)**: write the Mutex<HashMap> cache trace at 16 threads × 100 K
      gets/sec — the lock serializes every cache hit, throughput plateaus. Then write the cache-key
      collision trace where block_idx alone is the key.
  - **Output**: `notes/39_sstreader_design.md` with R1–R7, D1–D6.

  - **When `sstreader_cache_key_cross_sst_no_collision` reports the second SST reading the first
    SST's data:**
    - Symptom: open SST_A and SST_B; both have block at offset 1024; cache returns A's block when
      B's was requested. Silent corruption.
    - Why: caching by `block_idx` instead of `(sst_id, block_idx)` mixes blocks across SSTs.
    - Fix: cache key includes file-id. `block_cache: Cache<(SstId, u64), Arc<Block>>`. SstId is a
      monotonic counter assigned on SST creation.
    - Muscle: cache keys must include enough discriminators to be unique across all callers; never
      assume callers don't collide. Reapplies at: W14 bufpool page-id, W42 txn snapshot cache.

  - **When `bench_sstreader_16_thread_scales` reports a throughput plateau at ~3-4× single-thread:**
    - Symptom: 16-thread bench plateaus at ~500 K gets/sec total; flamegraph shows
      `Mutex<HashMap>::get` as the dominant frame.
    - Why: caching with `Mutex<HashMap<(SstId, u64), Arc<Block>>>` serializes every block fetch
      behind one lock. Under heavy read load (16 threads × 100 K gets/sec each), the mutex becomes
      the read bottleneck even though cache hits should be sub-microsecond.
    - Fix: `dashmap` (sharded concurrent map) or `quick_cache` (concurrent LRU). Cache key includes
      `SstId` so blocks from different SSTs don't collide. Hot path: shard lookup ≈ ~30 ns
      uncontended; full lock-free under shard locality.
    - Cost avoided: ~50 ns lock overhead per cache hit × 16 threads × 100 K = ~80 ms/sec aggregate
      eliminated; removes the read-side scalability ceiling.
    - Muscle: shared read-cache structures use concurrent maps, not mutex-guarded HashMaps.
      Reapplies at: W14 bufpool page table (DashMap), W42 `txn` read snapshot cache, W74
      matching-engine symbol table.

  - **When `sstreader_bloom_false_positive_returns_none` reports a non-existent value returned:**
    - Symptom: a key whose bloom hash collides with a real key returns the colliding key's value
      (or random data). User-visible corruption.
    - Why: assuming bloom-hit means key-present skips the in-block lookup; you return random value.
    - Fix: bloom is may-be-present; always verify in-block. The flow is: bloom returns true → load
      block → seek within block → if found, return value; else return None.
    - Muscle: probabilistic filters are NEVER trusted as proof; they prune. Reapplies at: W34 bloom
      direct use, W101 vector-db filtered-search.

  - **5-year failure mode** (write in `notes/39_sstreader_followup.md` after green): when io_uring

    per-request, mmap-faults disappear. State the migration: introduce `SstReaderUring`; trigger
    when tail latency on cold reads dominates the cache-hit median.

- [ ] **Build**: `crates/lsm-core/src/write_path.rs` —
  `flush_memtable_to_l0(mem: MemTable, dir: &Path) -> Result<SstReader>`. Wal-backed. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: flush is the contract between in-memory and durable state. WAL truncation
    ordering relative to manifest fsync is the crash-safety invariant; get it wrong and you lose committed
    data. This is the canonical "rotate, build, persist, swap, GC" pattern reused at W42 txn flush boundary +
    W95 mini-db.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: the active memtable is rotated to immutable; a background flush
    writes it to an L0 SST, registers via manifest, and (only AFTER manifest fsync) the WAL can be truncated.
    The strict ordering protects against crash: if any step fails, the WAL is the source of truth and replay
    reconstructs.

  - **Requirements** — write in `crates/lsm-core/notes/39_writepath_design.md`:
    - R1. Input: rotated immutable memtable + `wal_lsn_high` (highest WAL LSN covered by this memtable).
    - R2. Output: SstReader for the new L0 SST; manifest references it; WAL truncatable up to `wal_lsn_high`.
    - R3. **Strict ordering**: build SST → fsync SST → fsync parent dir → manifest append → manifest fsync
      → THEN WAL truncation. WAL truncation BEFORE manifest fsync is data loss on crash.
    - R4. **Tombstones survive flush** — L0 must preserve them; elision happens only at the deepest level
      during compaction.
    - R5. **Manifest record is CRC-checked**; replay tolerates tail corruption (truncate at first bad record).
    - R6. Crash-safe at kill-9 at any point: either no SST visible OR fully-registered SST visible.
    - R7. 1 M-entry flush < 2 s; 256 MB flush < 1 s (NVMe-bound).

  - **Design walk-through** — answer each:
    - D1. The 6-step ordering: write it out. Why does WAL truncation come last?
    - D2. The manifest format: length-prefix + CRC. Why CRC? When does it matter?
    - D3. Crash sim: enumerate the 6 windows (between each pair of steps). For each, what does
      recovery see on restart?
    - D4. Tombstone preservation at L0: write the rule. When does elision become legal (cite W40
      STCS bottom-level)?
    - D5. Concurrent writes to active memtable during flush: how is non-interference guaranteed?
    - D6. **Pre-mortem (load-bearing)**: write the WAL-truncated-before-manifest-fsync trace —
      truncate, then crash; manifest replay sees no L0 SST registered; WAL has no records to replay
      from. Data loss.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **When `flush_crash_between_rename_and_manifest_recovery` reports data loss:**
    - Symptom: kill between rename and manifest sync; on restart, the SST file exists but the
      manifest does NOT reference it; the WAL was truncated; recovery has no record of this data.
    - Why: WAL truncation before manifest fsync — if you truncate WAL then crash before manifest is
      durable, on restart neither WAL nor manifest reference the data.
    - Fix: WAL truncation happens after manifest fsync; treat WAL retention as the safety net. The
      ordering is build SST → fsync SST → rename → fsync parent → manifest append → fsync manifest →
      THEN truncate WAL. Each crash window is recoverable from WAL.
    - Muscle: in any "rotate + persist + truncate-log" sequence, the log truncation MUST be the
      LAST step; until it fires, the log is the source of truth. Reapplies at: W26 WAL group commit
      + rotation, W42 txn flush boundary, W77 aeron archive segment commit.

  - **When `flush_manifest_crc_detects_tail_corruption` reports manifest open failure:**
    - Symptom: corrupt the last 4 bytes of manifest; on restart, manifest fails to open with "EOF in
      middle of record"; recovery cannot proceed.
    - Why: manifest write torn — appending without crash-safe protocol (length-prefix + CRC,
      replay-from-start) leaves a torn manifest.
    - Fix: each manifest record is CRC-checked; replay tolerates tail corruption (truncate at first
      bad record). On restart, scan manifest from the start; on CRC mismatch, truncate the file at
      the last-good-record offset; proceed with that state.
    - Muscle: append-only logs with crash tolerance must use length-prefix + CRC + truncate-on-mismatch
      replay. Reapplies at: W26 WAL replay, W77 aeron archive replay.

  - **When `flush_round_trip_with_tombstones` reports tombstones missing:**
    - Symptom: memtable had a delete for key K; flush; open SST; query K returns Value (from a lower
      level) instead of None.
    - Why: tombstone elision at L0 — L0 must preserve tombstones (lower levels still hold the
      value). Eliding tombstones here causes resurrection.
    - Fix: tombstone elision only at the bottom level during compaction. L0 flush writes
