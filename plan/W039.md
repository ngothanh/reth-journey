- [ ] **Build**: `crates/lsm-core/src/sst/mod.rs` —
  `SSTable { file: Arc<Mmap>, index: BlockIndex, bloom: bloom::ClassicBloomFilter, meta: SstMetadata }`. Footer at
  fixed file-end encodes index + bloom offsets + magic + version. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: mirrors mini-lsm `SsTable::open` + RocksDB `BlockBasedTable` footer. SSTable is the LSM's
    on-disk format; every downstream opens this file unchanged (W40 compaction, W42 txn, W95-W100 mini-db). Three traps
    a first attempt walks into: (1) footer offset convention confusion → open succeeds, `get()` reads random bytes;
    (2) index borrowing from the mmap → UAF after `SSTable::drop`; (3) magic/version mismatch handled by panic instead
    of typed error → one corrupt file takes down the whole DB process. State plainly: your first attempt WILL fail at
    least `sstable_round_trip_10k_entries` and `sstable_index_outlives_mmap` — the debug session is the lesson.

  #### Phase 1 — Problem, prediction, design (~45 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/lsm-core/notes/39_sstable_prediction.md`:
    - P1. The primitive you'd reach for to map the file: write the exact import line (`use memmap2::Mmap;`) and
      whether you'd store `Mmap`, `&[u8]`, or `Arc<Mmap>`. Predict which one keeps the index valid for the SSTable's
      whole life.
    - P2. Predict the footer's total byte size given fields {index_offset, index_len, bloom_offset, bloom_len, magic,
      format_version} as fixed-LE. Predict `open()` wall-time for a 256 MB SST (one mmap + one 32-B footer read +
      parse index/bloom). Within 2×.
    - P3. Predict what happens on the FIRST `get(k)` if the writer encoded `bloom_offset` relative to the bloom block
      start but the reader treats it as file-absolute. Exact symptom.
    - P4. Derive-correctness prediction: if `BlockIndex` holds `entries: Vec<(&[u8], u64)>` borrowing from the mmap,
      does it compile? Does it run? When does it break?
    - P5. **List every Phase-2 test you predict your first attempt will fail.** Compare to reality after the tests run.
  - *Mental model*: an SSTable is an immutable, sorted, on-disk KV table. The footer at a fixed end position is the
    single entry point — it points at the bloom + index blocks; data blocks fill the rest. It exists so reads cost
    a bloom-check + binary-search instead of a full scan, and so the file can be mmap'd once and shared read-only
    across every reader thread.
  - *Contract* (signature-level, never the body):
    ```rust
    pub struct SstMetadata { pub id: SstId, pub num_entries: u32, pub min_key: Bytes, pub max_key: Bytes }
    pub struct SSTable { /* file, index, bloom, meta */ }
    impl SSTable {
        pub fn open(path: &Path, id: SstId) -> Result<SSTable, SstError>; // one mmap, one footer read, validate
        pub fn metadata(&self) -> &SstMetadata;
        pub fn block_handle(&self, key: &[u8]) -> Option<BlockHandle>; // binary search index, no I/O
    }
    pub enum SstError { InvalidFooter, MagicMismatch { found: u64, expected: u64 },
                        UnsupportedVersion { found: u32 }, IndexCorrupt }
    ```
  - *Back-of-envelope*: `open()` is amortized over millions of `get()`. Target ≤1 ms steady-state. One mmap syscall
    ≈ 300 ns; the 32-B footer read is already mapped (≈ L2, 7 ns); parsing a 100 K-entry index = 100 K × (varint
    decode + `Bytes::copy_from_slice` of ~16 B) ≈ 100 K × ~30 ns ≈ 3 ms IF you clone every key — so the index must
    be lazy or the keys interned. Cliff: a borrowed index that skips the clones is ~0 ms to build but UAFs on drop
    (300× cheaper, infinitely more wrong). The footer read itself is one cache line; getting its size wrong by 1 byte
    shifts every offset. Reconciling open's two numbers: the bare mmap+footer is sub-µs (~300 ns), but `open` is
    index-parse-bound — cloning a 100 K-entry index costs ~3 ms, so a real `open` lands in the alive-bench's
    `[5 µs, 5 ms]` band; the 300 ns figure is the floor an EMPTY SST would hit, which is exactly why the band's 5 µs
    lower edge fires on a no-op fixture.
  - **Requirements** R1..R7 — write in `crates/lsm-core/notes/39_sstable_design.md`:
    - R1. File layout: `[data_0]…[data_n][bloom_block][index_block][footer]`. Footer occupies the last
      `sizeof(Footer)` bytes.
    - R2. **All offsets are file-absolute** — never relative to a sub-block. Document this AT the footer encoder.
    - R3. Footer carries `magic = SST_MAGIC = 0xF73A_5EBC_88CD_9E10` and `format_version: u32`; cross-version files
      reject with a typed error.
    - R4. **Mmap safety**: index entries OWN their key bytes (`Bytes::copy_from_slice` on parse); never borrow from
      the mmap after parse, or the index outlives the mapping.
    - R5. `open(path, id) -> Result<SSTable>`: one mmap, one footer-read (fixed bytes), parse index + bloom, validate
      magic + version.
    - R6. Open + parse < 1 ms steady state; amortizes over millions of `get()`.
    - R7. Truncated/corrupt files reject with typed errors (`InvalidFooter`, `MagicMismatch`, `UnsupportedVersion`,
      `IndexCorrupt`); never panic.
  - **Design walk-through** D1..D7 — answer in the design doc; no peeking at mini-lsm source until Phase 3:
    - D1. Why footer at the END (not the start)? What does that buy the streaming writer (which doesn't know
      index_offset until all data blocks are written)?
    - D2. Footer fields + why fixed-size LE. Compute the total size. Why does a varint footer break R1?
    - D3. Mmap lifetime: file is `Arc<Mmap>` shared for the SSTable's life. If the index borrows `&[u8]` from the
      mmap, when exactly does that go wrong? (Drop order; `Bytes` returned past `open` scope.)
    - D4. Magic/version mismatch: log + typed error, never panic. Cite: a corrupt SST must not take down the process
      that serves 1000 healthy SSTs.
    - D5. `format_version` migration: write the read-side branch. What does a v1 reader do with a v2 footer?
    - D6. **Primitive table** — enumerate the mapping choices with properties:
      | choice                 | index valid after open? | clones keys? | UAF risk |
      | `&[u8]` slice          | no (borrow ends)        | no           | compile error / lifetime fight |
      | `Mmap` owned in struct | yes                     | optional     | only if index borrows it |
      | `Arc<Mmap>` + owned idx | yes (shareable)         | yes          | none |
    - D7. **Pre-mortem (load-bearing)** — write the EXACT offset-confusion trace:
      ```
      writer:  bloom written at file byte 64_000_000; encodes footer.bloom_offset = 0 (relative to bloom block)
      reader:  open() reads footer.bloom_offset = 0, treats as file-absolute
      reader:  &mmap[0..bloom_len] → reads the FIRST data block bytes as a bloom filter
      get(k):  bloom.contains(k) returns garbage → either false-negative (miss real key) or random block seek
      ```
      Then the **Anti-shortcut audit**: the "obvious" reach for index storage is `&mmap[..]` slices (zero-copy, looks
      fast); wrong HERE because the index must outlive any single `open()` borrow and be shared across reader threads
      via `Arc<SSTable>` — borrows can't cross that boundary. Owned `Bytes` is the only shape that survives.
  - **Output**: `notes/39_sstable_design.md` with R1–R7, D1–D7, the offset-confusion sketch + anti-shortcut audit.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  Ordered newbie→expert — the ladder you actually walk.

  - **(NEWBIE) When `sstable_magic_mismatch_rejects` reports `panicked at 'magic mismatch'`:**
    - Symptom: flipping a magic bit panics instead of returning `Err`. A corrupt SST must not crash the process.
    - Why: `open` used `assert_eq!(magic, SST_MAGIC)` (or `.expect()`); file-format validation became a panic.
    - Fix: match and return a typed error — `if magic != SST_MAGIC { return Err(SstError::MagicMismatch { found: magic, expected: SST_MAGIC }); }`; likewise gate `format_version`.
    - Muscle: file-format validation MUST be a typed error, never a panic — one bad file can't take down 1000 good
      ones. Reapplies at: W26 WAL header validation, W40 SST manifest open, W77 aeron archive header.
  - **(SENIOR) When `sstable_round_trip_10k_entries` returns garbage on the first `get` (open succeeds):**
    - Symptom: `open()` completes clean; first `get(k)` returns garbage; later gets panic on a bad varint length.
    - Why: footer offset-convention drift — writer encoded `bloom_offset`/`index_offset` relative to the sub-block
      start; reader interpreted them as file-absolute, so the seek lands in random data.
    - Fix: commit to file-absolute offsets and document it at the footer encoder. The writer's `current_offset`
      counter starts at 0 (file start) and accumulates byte-by-byte; the footer stores that counter's value at the
      moment each block was written.
    - Muscle: any multi-block format must commit to ONE offset convention and document it at the footer. Reapplies
      at: W40 SST index-block offsets, W26 WAL segment offsets, W77 aeron archive segment offsets.
  - **(EXPERT) When `sstable_index_outlives_mmap` COMPILES (and would UAF) instead of failing:**
    - Symptom: the trybuild "fail" case compiles green; under miri/asan the held handle UAFs after `drop(sst)`.
    - Why: `BlockIndex { entries: Vec<(&'a [u8], u64)> }` borrows key slices from the mmap; the iterator/handle can
      outlive the `Arc<Mmap>`, exposing a dangling pointer.
    - Fix: index entries own their bytes — `BlockIndex { entries: Vec<(Bytes, u64)> }` with
      `Bytes::copy_from_slice(&mmap[off..off+len])` at parse time. Now nothing borrows the mapping.
    - Muscle: any structure that outlives a mapping must OWN its bytes, not borrow them — the borrow checker is the
      test only if the lifetimes are honest. Reapplies at: W14 bufpool frame lifetime, W26 WAL replay index, W40
      compaction merge iterator, W77 aeron archive index.
  - **(EXPERT, negative-control) When `sstable_open_under_1ms_bench_is_alive` reports < 5 µs:**
    - Symptom: the bench passes the ≤1 ms bound but lands at ~80 ns — the plausibility band fires.
    - Why: the bench fixture wrote an empty SST (0 data blocks), so `open` parses a 0-entry index and measures
      nothing. The ≤1 ms assertion alone would have hidden this.
    - Fix: the bench fixture must materialize a real 256 MB SST and the bench asserts `num_entries` matches; only
      then is the timing meaningful.
    - Muscle: every perf bench needs a liveness assertion (plausible band + a "did it actually do the work" check),
      or a green bench can be measuring nothing. Reapplies at: W40 compaction throughput bench, W42 txn commit bench.

  #### 5-year failure mode
  Write in `crates/lsm-core/notes/39_sstable_followup.md` after green: when zoned-storage (ZNS) SSDs become standard
  (writes only sequential within a zone, no in-place footer rewrite), the fixed-end-footer layout breaks because you
  can't seek-write the footer last. TRIGGER: ZNS-only NVMe ships as the default tier in your deployment region.
  Migration (1 line): SSTable becomes zone-aligned segments with the footer in a separate zone-final block written
  by a closing append.

- [ ] **Build**: `crates/lsm-core/src/sst/builder.rs` — `SstBuilder` streams sorted KVs into blocks, populating bloom +
  index incrementally, finishing crash-atomically. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: mirrors mini-lsm `SsTableBuilder`. A streaming SST write must be memory-bounded (1 block
    in flight, not the whole file in RAM) AND crash-atomic (fsync-before-rename, then fsync the dir). Two traps a
    first attempt hits: (1) wrong fsync order → renamed-but-empty `.sst` after a kill -9; (2) block split mid-entry →
    an unreadable block that panics the decoder. State plainly: your first attempt WILL fail
    `sstbuilder_crash_atomic_no_torn_sst` and `sstbuilder_block_split_only_between_entries`.

  #### Phase 1 — Problem, prediction, design (~45 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/lsm-core/notes/39_sstbuilder_prediction.md`:
    - P1. The primitive for buffered file output: `use std::io::BufWriter;` — predict whether `BufWriter::flush`
      alone makes data durable, or whether you also need `File::sync_all`. Which one survives kill -9?
    - P2. Predict peak heap for a 1 M-entry streaming build (1 block ~16 KB + bloom ~125 KB + index ~1 KB/100 K).
      Within 2×.
    - P3. Predict the on-disk state after: write → rename → kill -9 (no fsync). Exact symptom on restart `open`.
    - P4. Predict what the block decoder does if a block is flushed in the middle of an entry (varint length straddles
      the block boundary).
    - P5. **List every Phase-2 test you predict your first attempt will fail.**
  - *Mental model*: `SstBuilder` turns a stream of sorted KVs into one immutable file using O(1) memory, then commits
    it atomically so a crash leaves either no file or a complete file — never a torn one. It exists so a memtable
    flush never buffers the whole table in RAM and never publishes a half-written SST.
  - *Contract*:
    ```rust
    pub struct SstBuilder { /* current block buf, index, bloom, writer, expected_count */ }
    impl SstBuilder {
        pub fn new(dir: &Path, id: SstId, expected_count: u32) -> Result<Self, SstError>;
        pub fn add(&mut self, key: &[u8], value: ValueOrTombstone) -> Result<(), SstError>; // debug_assert sorted
        pub fn finish(self) -> Result<PathBuf, SstError>; // crash-atomic: fsync, rename, fsync dir
    }
    ```
  - *Back-of-envelope*: target ≥ 500 K entries/s single-thread, 1 M-entry build < 2 s. Per entry: varint-encode
    (~5 ns) + memcpy into block buf (~16 B, ~2 ns) + bloom set-bits (k=7 hashes ≈ 7 × ~3 ns ≈ 21 ns) ≈ ~30 ns →
    ~33 M entries/s in CPU; the floor is the `write(2)` syscalls at block-flush (one syscall ~300 ns per ~16 KB
    block = 1000 blocks for 16 MB → 0.3 ms) plus the single `fsync` at finish (~1-10 ms on NVMe). So the build is
    CPU-cheap and fsync-dominated: the cliff is calling fsync per-block (1000× ~5 ms = unusable) vs once at finish.
  - **Requirements** R1..R7 — write in `crates/lsm-core/notes/39_sstbuilder_design.md`:
    - R1. Memory-bounded: 1 block in flight (~16 KB) + bloom (~125 KB) + index (~1 KB / 100 K) ≈ ~150 KB regardless
      of N.
    - R2. **Sorted-order discipline** — `debug_assert!(key > last_key)` on every `add`.
    - R3. **Block split only between entries** — never mid-entry; the split fires AFTER the current entry finishes
      encoding and the block exceeds target (soft cap, one entry of overshoot allowed).
    - R4. **Crash-atomic finish**: write `.tmp`, `sync_all` the data fd, `rename` to final, fsync the parent dir.
      Kill -9 at any point leaves either no SST or a complete SST.
    - R5. Bloom sized by `expected_count` (from memtable), rounded UP 10%.
    - R6. ≥ 500 K entries/s single-thread build.
    - R7. 1 M-entry build < 2 s.
  - **Design walk-through** D1..D7:
    - D1. The streaming `add` pseudocode. When exactly does block flush fire? (After append, if `block.len() >
      target` AND the entry is whole.)
    - D2. The atomic-finish syscalls IN ORDER. Why `sync_all` the data fd BEFORE rename? Why fsync the PARENT dir
      AFTER rename?
    - D3. Bloom sizing: why round UP? (Undersizing → FPR cliff; see the failure card.)
    - D4. Soft vs hard block cap: why allow one entry of overshoot rather than splitting mid-entry?
    - D5. Crash-recovery sweep on startup: how do you detect orphaned `.tmp` files? Policy: delete them (they were
      never durable / never renamed).
    - D6. **Primitive/durability table**:
      | step                 | durable after? | survives kill -9? |
      | `BufWriter::flush`   | no (page cache) | no |
      | `File::sync_all`     | data on platter | yes (data) |
      | `rename`             | dirent in cache | only after dir fsync |
      | parent `fsync`       | dirent durable  | yes (rename) |
    - D7. **Pre-mortem (load-bearing)** — write the EXACT fsync-forgotten trace:
      ```
      add×N → BufWriter buffers → flush() to page cache → rename(.tmp → .sst)  [dir entry in cache]
      kill -9   (page cache lost, dir entry lost OR data lost)
      restart:  .sst exists (rename hit disk first) but is 0 bytes (data never synced)
      open():   footer read fails → InvalidFooter → DATA LOSS for a committed flush
      ```
      Then the mid-entry split trace:
      ```
      block at 16_300 B > 16_384 target check fires mid-entry → flush → entry's last 40 B start next block
      decoder reads block N: varint length = huge → out-of-bounds → panic
      ```
      **Anti-shortcut audit**: the obvious reach is `BufWriter::flush()` at finish (it "writes everything") — wrong
      HERE because flush only pushes to the page cache; durability needs `sync_all` + dir fsync. And the obvious
      block-split is "flush when over target" — wrong HERE because it can fire mid-entry; the check must include
      `last_entry_complete()`.
  - **Output**: `notes/39_sstbuilder_design.md` with R1–R7, D1–D7, both pre-mortem traces + anti-shortcut audit.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **(NEWBIE) When `sstbuilder_sorted_order_panics_on_oob` does NOT panic:**
    - Symptom: out-of-order `add` is accepted silently; later binary-search in the index returns wrong blocks.
    - Why: no sorted-order guard; the index binary search assumes monotonic keys.
    - Fix: `debug_assert!(self.last_key.as_ref().map_or(true, |lk| key > lk.as_slice()), "keys must be added sorted");`
    - Muscle: invariants the rest of the code assumes (here: monotonic keys) must be asserted at the boundary that
      can violate them. Reapplies at: W40 merge-iterator ordering, W42 txn write-set ordering.
  - **(SENIOR) When `sstbuilder_crash_atomic_no_torn_sst` reports a 0-byte `.sst` after crash:**
    - Symptom: kill -9 between rename and the final sync; restart shows the `.sst` exists but is empty (or has the
      index but no data); `open` fails magic/footer → file marked corrupt → data loss for a committed flush.
    - Why: fsync forgotten before rename — `rename` without a prior `sync_all` can publish a renamed-but-empty file
      because the page cache held the data while the directory entry already hit disk.
    - Fix: order is `sync_all` data fd → `rename` → fsync parent dir. The data sync guarantees the bytes are on the
      platter before the rename promises they exist; the dir fsync guarantees the rename itself is durable.

  #### Phase 3 — Make the tests pass, one failure at a time (~125 min)

  - **(SENIOR) When `flush_crash_between_rename_and_manifest_recovery` reports data loss:**
    - Symptom: kill between rename and manifest sync; on restart the SST file exists but the manifest does NOT
      reference it AND the WAL was already truncated — recovery has no record of this data.
    - Why: WAL truncation happened before the manifest fsync; neither source survives the crash window.
    - Fix: truncate the WAL only AFTER manifest fsync; treat WAL retention as the safety net. Order: build SST →
      fsync SST → rename → fsync dir → manifest append → manifest fsync → THEN truncate WAL. Every window is WAL-
      recoverable; orphan SSTs (rename-but-no-manifest) are deleted on the recovery sweep.
    - Muscle: in any "rotate + persist + truncate-log" sequence the log truncation MUST be the LAST step; until it
      fires the log is the source of truth. Reapplies at: W26 WAL group-commit + rotation, W42 txn flush boundary,
      W77 aeron archive segment commit, W95 mini-db flush.
  - **(SENIOR) When `flush_round_trip_with_tombstones` resurrects a deleted key:**
    - Symptom: the memtable had a delete for K; after flush, `get(K)` returns a value (from L2) instead of `None`.
    - Why: tombstone elision at L0 — L0 dropped the tombstone, but lower levels still hold K's old value, so the
      LSM lookup finds it.
    - Fix: write `ValueOrTombstone::Tombstone` as a first-class L0 value; elide tombstones ONLY at the bottom level
      during compaction (W40). Downstream readers see the tombstone and stop the LSM lookup at `None`.
    - Muscle: tombstone elision is per-level — the rule "deepest level only" is correctness-critical; eliding early
      resurrects deletes. Reapplies at: W40 STCS bottom-level tombstone retention, W95 mini-db deletion semantics.
  - **(SENIOR) When `flush_manifest_crc_detects_tail_corruption` fails to open the manifest:**
    - Symptom: corrupting the last 4 bytes makes restart fail with "EOF in middle of record"; recovery can't proceed.
    - Why: the manifest was read as one all-or-nothing blob with no per-record framing.
    - Fix: each record is length-prefixed + CRC; replay scans from the start, and on CRC mismatch truncates the file
      at the last-good-record offset and proceeds with that state.
    - Muscle: append-only logs with crash tolerance use length-prefix + CRC + truncate-on-mismatch replay — partial
      tails are normal, not fatal. Reapplies at: W26 WAL replay, W30 recovery log, W77 aeron archive replay.
  - **(EXPERT, cross-primitive) When `flush_concurrent_active_memtable_no_interference` drops or duplicates an active
    write (or a flushed-snapshot key appears in the active set):**
    - Symptom: post-flush the active count `!= K*N` (a write dropped or duplicated), or `sst.key_set()` contains a
      key that was only ever written to the active memtable after rotation — the SST leaked a live write.
    - Why: the flush read the LIVE active memtable instead of the rotated immutable one — no atomic rotate-before-
      flush, so concurrent writers and the flush reader alias the same map. The flush iterates a map being mutated
      under it (lost/torn writes, or it captures writes that belong to the next memtable).
    - Fix: rotate active→immutable under the single-writer swap BEFORE the flush reads anything; the flush touches
      ONLY the immutable `Arc<MemTable>`, and writers only ever touch the freshly-installed active map. The two never
      alias — `let immut = store.rotate_active_to_immutable(); flush(immut, ..)` runs after the swap publishes a new
      empty active.
    - Muscle: a flush must operate on an immutable rotated snapshot, never the live writer target — rotate, then
      flush the rotated `Arc`, never the active map. Reapplies at: W42 txn flush boundary, W95 mini-db flush.
