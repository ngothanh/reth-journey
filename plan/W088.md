**Monday-Wednesday — ledger VOPR: multi-process scenario runner**

- [ ] **Build**: `crates/ledger-deterministic/src/vopr/runner.rs` — multi-process VOPR runner: a long-lived worker pool (one fork+exec per core) executing scenarios fed as newline-delimited JSON over stdin, returning per-scenario `{seed, final_state_hash, outcome}` JSON on stdout. (~total 4 hrs across 3 phases)
  - 🔧 **Why this matters**: mirrors TigerBeetle's VOPR runner. VOPR's bug-finding power scales linearly with scenarios/second, and a single in-process runner is doubly wrong — one panic kills the whole process (no fault isolation) AND a naive `Command::new(self_exe)`-per-scenario design pays a 5 ms fork+exec tax that becomes ~80% of wall-time. The two traps that bite first attempts: (1) **fork-per-scenario** instead of a long-lived pool; (2) **non-deterministic state-hash** (HashMap iteration / native-endian bytes) that silently forfeits cross-machine reproducibility. A first-attempt impl WILL fail the `worker_pool_one_fork_at_startup` and `state_hash_cross_arch_deterministic` tests below — the debug session is the lesson. Bar (c): VOPR-grade requires a documented, measured scenarios/day throughput. Downstream consumers: W92 ledger v1.0 SHIP determinism gate (this exact runner), W90 consensus-vsr VOPR (plugs into this runner Friday), W95 mini-db LSM property tests.

  #### Phase 1 — Problem, prediction, design (~60 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/ledger-deterministic/notes/88_runner_prediction.md`:
    - P1: the primitive you'd reach for to spawn workers (exact import line, e.g. `use std::process::Command;`) and the map type you'd reach for in the state machine (`std::collections::HashMap`? `BTreeMap`?).
    - P2: predicted fork+exec cost per process (ns/µs?) and predicted per-scenario IPC cost over a pipe.
    - P3: predicted outcome of `Command::new(self_exe).spawn()` once-per-scenario at 100 scenarios — total setup ms and setup-as-%-of-wall.
    - P4: predicted result of hashing `HashMap` iteration order on two runs of the same seed on the same machine; then x86 vs ARM with `to_ne_bytes`.
    - P5: **list every Phase-2 test you predict your first attempt will fail.** Compare to reality after tests run.
  - *Mental model*: a VOPR runner is a work-stealing scheduler over a fixed pool of OS processes; each process is a deterministic sandbox that takes a seed and returns a canonical state hash. Fault isolation (a panicking scenario must not kill siblings) is the reason for processes over threads.
  - *Contract*:
    ```rust
    pub struct Runner { workers: Vec<WorkerProc>, queue: VecDeque<Scenario> }
    pub struct WorkerProc { child: Child, stdin: BufWriter<ChildStdin>, stdout: BufReader<ChildStdout> }
    pub struct Scenario { seed: u64, op_count: u32, fault_script: FaultScript }
    pub struct ScenarioResult { seed: u64, final_state_hash: [u8; 32], outcome: Outcome }
    pub enum Outcome { Passed, Failed { assertion: String }, Timeout }
    impl Runner {
        pub fn spawn_pool(n_workers: usize) -> io::Result<Self>;   // fork+exec ONCE per worker
        pub fn run(&mut self, scenarios: Vec<Scenario>) -> Vec<ScenarioResult>;
    }
    pub fn hash_canonical(sm: &StateMachine) -> [u8; 32];          // single audited function
    ```
  - *Back-of-envelope* (bar (c)): fork+exec ≈ 5 ms (page-table copy + linker + `_start`). At 100 scenarios/run, per-scenario spawn = 5 ms × 100 = **500 ms setup**; for 600 ms median scenarios that is ~80% setup tax — the cliff ratio is **spawn-once 50 µs amortized vs spawn-per-scenario 5 ms = 100×**. Pipe IPC (JSON encode + `write` + decode) ≈ 10 µs/scenario, negligible vs scenario body. Target R5: 100 scenarios in <60 s on 8-core M2 ⇒ ≥140k scenarios/day per machine ⇒ 8-machine fleet ≥1M/day.
  - **Requirements** R1..R9 — write in `crates/ledger-deterministic/notes/88_runner_design.md`:
    - R1. Each worker is a fresh process (`Command::new(self_exe)` with a `--vopr-worker` arg), NOT a thread.
    - R2. Seed S chosen in master → echoed in `ScenarioResult.seed`; re-runnable as `--replay --seed S`.
    - R3. `state_hash` canonical (W83 encoding) so the same seed → same hash on any machine.
    - R4. Workers communicate results via one JSON line on stdout — no shared memory.
    - R5. 100 scenarios in <60 s on 8-core M2 ⇒ ≥140k scenarios/day per machine.
    - R6. Per-scenario wall timeout (60 s) → SIGKILL the worker, record `Timeout`, respawn the worker slot.
    - R7. A panicking scenario is marked `Failed` on first panic and is NOT re-queued.
    - R8. Long-lived worker pool: one fork+exec per core at startup, NOT per scenario.
    - R9. Cross-arch `state_hash` deterministic: BLAKE3 over sorted-by-key, explicit-little-endian bytes.
  - **Design walk-through** D1..D8 — answer in the design doc; do not read TigerBeetle's runner source until Phase 3:
    - D1. Sketch `Runner` + `WorkerProc` + `Scenario`/`ScenarioResult`/`Outcome`.
    - D2. Enumerate the spawn strategies with a property table:

      | strategy | per-scenario cost | fault isolation | determinism | startup cost |
      |---|---|---|---|---|
      | threads (`std::thread`) | ~0 | NONE (one panic aborts process) | shared heap risks order leak | low |
      | `Command::spawn` per scenario | ~5 ms | full | full | none amortized |
      | long-lived process pool (chosen) | ~10 µs IPC | full | full | ~50 µs amortized/worker |

    - D3. **Pre-mortem (load-bearing) — fork-per-scenario:** write the 4-5 line trace. `for s in scenarios { let c = Command::new(self_exe).arg("--vopr-worker").spawn()?; write_scenario(c.stdin, s); let r = read_result(c.stdout); c.wait(); }` → `clone3` + `execve` per iteration → profile dominated by spawn → 1k scenarios/min instead of 16k/min. If you can't write this trace you can't see why the pool exists.
    - D4. **Pre-mortem — HashMap/native-endian in state_hash:** `for (k,v) in sm.accounts.iter() { h.update(k.as_bytes()); h.update(&v.balance.to_ne_bytes()); }`. If `accounts: HashMap`, iteration order varies run-to-run (random seed) → hash differs same machine same seed; if `BTreeMap` it is per-arch stable but `to_ne_bytes` differs x86 vs ARM. Either leaks non-determinism.
    - D5. **Pre-mortem — shared-resource contention:** all scenarios write `/tmp/journal.wal` on one disk → fsync contention serializes "parallel" work. Mitigation: per-worker tmpfs scratch dir, or in-memory journal for sim mode.
    - D6. **Pre-mortem — zombie processes:** SIGKILL'd timed-out workers become zombies; after 10k scenarios the process table fills. Mitigation: `waitpid(WNOHANG)` reaping in the master loop after each respawn.
    - D7. **Pre-mortem — respawn loop:** a scenario that panics on replay gets re-queued → infinite loop. Mitigation: `Failed` scenarios are terminal, never re-queued (R7).
    - D8. **Anti-shortcut audit:** (a) "just use threads" — wrong, no fault isolation, a panic in one scenario unwinds/aborts siblings; (b) "just `Command::spawn` per scenario, it's simpler" — wrong, 100× the per-scenario cost; (c) "`HashMap` is faster than `BTreeMap`" — wrong HERE, the determinism contract outranks the constant factor and the map is hashed once per scenario, not in a hot loop.
  - **Output**: `notes/88_runner_design.md` with R1–R9, D1–D8, the fork-per-scenario bad-trace sketch.

  #### Phase 3 — Make the tests pass, one failure at a time (~140 min)

  Ordered newbie → expert: the ladder you actually walk.

  - **(NEWBIE) When `panicking_scenario_failed_not_requeued` reports `results.len() == 3`:**
    - Symptom: scenario 1 appears twice (or the runner hangs) — the panicking scenario was put back on the queue.
    - Why: the master treats a worker that died/returned error as "scenario not done" and re-queues it.
    - Fix: on a worker reporting `Failed`/exit, mark the scenario terminal and record the result; never re-enqueue. `Timeout` respawns the *worker* but the scenario is still terminal.
    - Cost avoided: an infinite respawn loop that pins a core at 100% and produces zero new coverage (a liveness bug in the test harness itself).
    - Muscle: in any retry/respawn scheduler, distinguish *transient* (respawn the executor) from *terminal* (record and move on) outcomes; conflating them livelocks. Reapplies at: W90 consensus-vsr view-change (a crashed replica respawns; a poisoned op does not retry), W92 ledger v1.0 SHIP soak.
  - **(SENIOR) When `worker_pool_one_fork_at_startup_not_per_scenario` reports `forks == 100+`:**
    - Symptom: profile shows `clone3` + `execve` dominating; ~1k scenarios/min vs ~16k/min target; `forks` counted ≈ scenario count.
    - Why: runner written as "for each scenario: `Command::new(self_exe).spawn()`; write; await; collect." Each fork+exec ≈ 5 ms (page-table copy + dynamic-linker setup + `_start` init). 100 scenarios = 500 ms setup; for 600 ms scenarios that is ~80% setup tax.
    - Fix: `spawn_pool(n)` forks+execs N workers ONCE at startup (~50 µs amortized/worker over the day). Each worker reads newline-delimited `Scenario` JSON from stdin in a loop, runs it, writes `ScenarioResult` JSON, loops. Master keeps a work-stealing queue feeding `stdin` via `BufWriter`. Per-scenario IPC ≈ 10 µs.
    - Cost avoided: **~5 ms spawn × 100 scenarios = ~500 ms/run, ~80% throughput unlock (100× per-scenario)** — drives 100k → 1M scenarios/day (bar (c) violation otherwise: the documented throughput would miss the fleet target).
    - Muscle: in any "do N identical things in parallel" architecture, amortize setup once at startup, never per task. Reapplies at: W90 io_uring journal (ring constructed once, not per write), W82 matching-engine shard workers (per-symbol core-pinning once at startup), W77 messaging-aeron Conductor (one agent per shard, not per publication).
  - **(SENIOR) When `timeout_kills_worker_records_timeout_then_continues` hangs forever:**
    - Symptom: the test never returns; scenario 2 never runs.
    - Why: master does a blocking `child.wait()` / blocking `read_line` with no deadline, so an infinite-loop scenario blocks the whole pool slot indefinitely.
    - Fix: arm a per-scenario 60 s deadline (a timer thread or `poll`/`select` on the pipe with timeout); on expiry `kill(pid, SIGKILL)`, record `Outcome::Timeout`, then `waitpid` and respawn the worker slot.
    - Cost avoided: a single pathological scenario silently halting an overnight 10k-scenario CI run (zero coverage for the night, undetected).
    - Muscle: every blocking wait on an untrusted producer needs a deadline + kill path; "it'll finish eventually" is not a liveness guarantee. Reapplies at: W90 io_uring (submission with completion timeout), W74 consensus-vsr request timers.
  - **(SENIOR) When `no_hashmap_audit` passes even with an injected `HashMap`:**
    - Symptom: the deny test's negative control fails — injecting `HashMap` does NOT trip `cargo deny`.
    - Why: `cargo-deny`'s `disallowed_types` only catches direct type references the lint pass sees; a transitive dep's `HashMap` or an aliased import slips through.
    - Fix: combine `cargo deny` `disallowed_types = ["std::collections::HashMap", "ahash::AHashMap", "fxhash::FxHashMap"]` with a CI `rg 'HashMap|HashSet' crates/ledger-deterministic/src/` audit script, AND keep the golden-hash test as the real backstop.
    - Cost avoided: a silent re-introduction of non-deterministic iteration that passes lint but breaks cross-machine replay (the determinism debt).
    - Muscle: a lint is only trustworthy once its negative control proves it bites; back determinism with a behavioral golden test, not a lint alone. Reapplies at: W88 VSR `no_instant_now_leak` lint (below), W92 ledger v1.0 determinism gate.
  - **(EXPERT) When `state_hash_cross_arch_deterministic` reports order-dependence or ARM≠x86:**
    - Symptom: same-machine hash varies by insertion order, OR x86 hash ≠ ARM golden; cumulative "1M scenarios" count fragments because reproduce-by-seed can't verify across machines.
    - Why: `accounts: HashMap` (run-random iteration) or `to_ne_bytes` (endian-dependent), or a nested `HashSet` field leaking order.
    - Fix: a single audited `hash_canonical(&sm)`: (a) `accounts: BTreeMap<AccountId, Account>` only; (b) BLAKE3 over sorted `(key, fixed-LE-value)` byte stream; (c) every integer via `to_le_bytes`, never `to_ne_bytes`; (d) cargo-deny + rg audit (above) guards regressions; (e) cross-arch CI: x86 + ARM nodes produce identical hash for the same seed.
    - Cost avoided: **forfeits the entire multi-machine fleet** — non-deterministic iteration invalidates cross-machine reproducibility, collapsing 1M/day fleet target back to 140k/machine (bar (c) violation: VOPR-grade requires reproducible-by-seed across the fleet).
    - Muscle: deterministic state-hash = sorted iteration + explicit little-endian + one audited function + a map-type lint. The load-bearing primitive of any reproduce-by-seed system. Reapplies at: W90 consensus-vsr state-transfer (sender + receiver share one canonical hash), W92 ledger v1.0 determinism gate (the 100× replay test), W94 exec-vm v1.5 parallel-vs-sequential equivalence.
  - **(EXPERT) When `no_zombies_after_10k_timeouts` reports >0 zombies:**
    - Symptom: `ps` shows defunct children; after enough churn the process table is exhausted and `spawn_pool`/respawn returns EAGAIN.
    - Why: SIGKILL'd workers are reaped by the kernel into zombie state; the master never `waitpid`s them, so PIDs/zombies accumulate.
    - Fix: after every respawn, drain reapable children with `waitpid(-1, WNOHANG)` in a loop until it returns 0; respawn replaces the slot, reaping recovers the PID.
    - Cost avoided: a slow process-table leak that surfaces only after hours of soak — the worst kind, because it passes the short test and fails the overnight run.
    - Muscle: every process you kill you must also reap; SIGKILL frees the program, `waitpid` frees the PID. Reapplies at: W90 marketdata-kernelbypass helper processes, W92 ledger v1.0 soak harness.

The two traps that bite: (1) **`Instant::now` leak** — one wall-clock read anywhere in VSR invalidates the entire VOPR (same seed → different orderings); (2) **`tokio::sync::mpsc` for SimNetwork** — convenient but non-deterministic across channels AND ~22 ms/scenario IPC.   #### Phase 1 — Problem, prediction, design (~60 min, no code yet)

  - 🎯 **Pre-prediction prompt** (`crates/consensus-vsr/notes/88_vopr_integration_prediction.md`):
    - P1: the primitive you'd reach for to wire replica-to-replica messaging in sim (`tokio::sync::mpsc`? a `BinaryHeap`?), exact import line; and the clock type you'd inject.
    - P2: predicted cost of `Instant::now()` (vDSO) in ns; predicted cost of a `tokio mpsc` send+recv pair in ns.
    - P3: predict the 100-iteration-same-seed replay outcome IF one `Instant::now` leaks in a retry timer (what fraction diverge, and why intermittently).
    - P4: predict whether `tokio mpsc` gives deterministic *cross-channel* ordering.
    - P5: list every Phase-2 test your first attempt will fail.
  - *Mental model*: a deterministic VSR simulator runs all "concurrent" replicas on ONE thread driven by a virtual scheduler; concurrency is SIMULATED, not real. Time only advances when the scheduler decides; messages are delivered in a total order; crash-restart is a state-struct round-trip through the journal.
  - *Contract*:
    ```rust
    pub struct SimClock { now: Cell<SimTime> }          // monotone, jumps only via step()
    pub struct SimNetwork { queue: BinaryHeap<Reverse<(SimTime, u64 /*source*/, u64 /*msg_id*/, Message)>> }
    pub struct VoprReplica { id: ReplicaId, state: ReplicaState, clock: SimClock, journal: Journal }
    pub struct VoprCluster { replicas: Vec<VoprReplica>, net: SimNetwork, clock: SimClock }
    impl VoprCluster {
        pub fn step(&mut self) -> bool;                  // ONLY way time advances; returns false when idle
        pub fn jump_clock(&mut self, by: SimTime);       // force timeouts (view-change)
        pub fn state_hash(&self) -> [u8; 32];            // reuses ledger hash_canonical
    }
    ```
  - *Back-of-envelope* (bar (c)): `Instant::now()` ≈ 25 ns (vDSO) × ~90k messages/scenario = **2–4 ms wall-time per scenario** of pure clock reads (and, worse, non-determinism). `tokio mpsc` send+recv ≈ 250 ns × 90k = **22 ms/scenario IPC**; the `BinaryHeap` virtual scheduler is a few ns per pop, no atomics, no syscalls — cliff ratio **~25× IPC** plus the (priceless) determinism win. Target R6: 100 mixed ledger+VSR scenarios reproduce from seed in <60 s.
  - **Requirements** R1..R8 — write in `crates/consensus-vsr/notes/88_vopr_integration_design.md`:
    - R1. `step()` is the ONLY way time advances.
    - R2. All messages go through `SimNetwork`, which records them and can drop/reorder/duplicate per the fault script.
    - R3. The clock may jump arbitrarily forward but NEVER backward.
    - R4. Crash-restart preserves the journal; a replica restores via journal replay.
    - R5. Determinism: same seed + same scenario script → byte-identical message history.
    - R6. 100 mixed ledger+VSR scenarios reproduce from seed in <60 s wall.
    - R7. NO `Instant::now` / `SystemTime::now` leak from any internal call site.
    - R8. `SimNetwork` is a single-threaded `BinaryHeap` keyed by `SimTime`, total order by `(SimTime, source_id, msg_id)`.
  - **Design walk-through** D1..D7 — answer in the design doc; no peeking at TigerBeetle's simulator until Phase 3:
    - D1. Sketch `VoprReplica` + `VoprCluster` + `SimNetwork` + `SimClock`.
    - D2. Property table of messaging choices:

      | choice | per-msg cost | cross-channel order | determinism | threads |
      |---|---|---|---|---|
      | `tokio::sync::mpsc` | ~250 ns | scheduler-dependent | NO | yes |
      | per-pair `crossbeam` channel | ~80 ns | NO total order | NO | yes |
      | single `BinaryHeap` scheduler (chosen) | ~5 ns | total `(SimTime,src,id)` | YES | one |

    - D3. **Pre-mortem (load-bearing) — `Instant::now` leak:** trace: VSR's `NormalReplica` retry-timer calls `Instant::now()` to decide a resend; under the virtual clock the surface API takes `clock`, but this transitive call reads wall-time → same seed produces different op orderings → 100× replay diverges ~30% of the time (leak fires only on slow runs). Write the 4-5 line trace.
    - D4. **Pre-mortem — `tokio mpsc` ordering:** `SimNetwork: HashMap<(src,dst), UnboundedSender<Message>>`; the scheduler may poll A's mailbox before B's, so identical seeds produce different delivery orders → breaks bit-determinism, independent of latency.
    - D5. **Pre-mortem — unbounded network queue:** under a partition the `SimNetwork` queue grows without bound. Mitigation: bound capacity; drop excess and record (which is itself a fault to inject).
    - D6. **Pre-mortem — view-change non-progress:** a scenario livelocks if quorum can never elect; the sim never terminates. Mitigation: scenario script can `jump_clock(2× timeout)` to force a view-change; step() returns false when idle so the runner can detect a stuck scenario.
    - D7. **Anti-shortcut audit:** (a) "use tokio, the prod path uses it anyway" — wrong, the SIM path must be single-threaded deterministic; keep the API identical but swap the transport; (b) "read `Instant::now` for the retry timer, it's just a timer" — wrong, every time read must flow through `clock`.

  #### Phase 3 — Make the tests pass, one failure at a time (~130 min)

  - **(SENIOR) When `sim_network_total_ordering` finds tokio mpsc:**
    - Symptom: `SimNetwork: HashMap<(ReplicaId,ReplicaId), tokio::sync::mpsc::UnboundedSender<Message>>`; each send ≈ 150 ns (atomic CAS + waker), recv ≈ 100 ns; 90k msgs × 250 ns = 22 ms/scenario IPC. Worse: ordering is FIFO per-channel but non-deterministic across channels.
    - Why: chose a convenient async primitive without thinking about ordering semantics.
    - Fix: `SimNetwork` is a single-threaded `BinaryHeap<Reverse<(SimTime, source_id, msg_id, Message)>>` — one global priority queue keyed by simulated delivery time. The scheduler pops the next message, advances `SimClock` to its delivery time, and hands it to the destination's `on_message`. Total order by `(SimTime, source_id, msg_id)` — bit-deterministic. No tokio, no atomics, no channels.
    - Cost avoided: **~22 ms/scenario IPC removed (~25× the IPC layer)** PLUS the determinism win (a deterministic ordering oracle is non-negotiable for VOPR replay) — bar (c) violation otherwise: the mixed-scenario target is unreachable AND replay is non-deterministic.
    - Muscle: in any deterministic-replay system, "concurrent" entities run on one thread driven by a virtual scheduler — concurrency is SIMULATED, not real (same shape as Jepsen Maelstrom, FoundationDB sim-test, TigerBeetle). Reapplies at: W90 consensus-vsr full deterministic test mode, W92 ledger v1.0 soak (sim mode = single-thread SimNetwork; prod mode = real tokio + UDP, identical API), W94 exec-vm v1.5 block-stm property test (parallel exec scheduled by deterministic order).
  - **(SENIOR) When `partition_2v1_quorum_holds_then_heals` or `leader_crash_view_change_no_loss` livelocks:**
    - Symptom: the scenario never terminates; `step()` keeps being called but nothing commits.
    - Why: after the leader crashes, no replica's view-change timer fires because the virtual clock never advances on its own (R1: only `step()`/`jump_clock` move time).
    - Fix: the scenario script must `jump_clock(2 * VIEW_TIMEOUT)` to fire the view-change timers; `step()` returns `false` when the network queue is empty so the runner detects an idle/stuck cluster and the timeout gate trips.
    - Cost avoided: an overnight scenario that hangs forever, producing zero coverage and masking real bugs.
    - Muscle: in a virtual-time sim, liveness is the scenario author's responsibility — timers don't fire unless you advance the clock; idle detection prevents silent hangs. Reapplies at: W90 consensus-vsr v1.0 reconfiguration scenarios, W92 ledger v1.0 soak.
  - **(EXPERT) When `replay_100_same_seed_identical` diverges intermittently / `no_instant_now_leak_lint` passes the grep but replay still diverges:**
    - Symptom: ~30% of 100 iterations of the same seed yield different final state-hashes; the leak fires only on slow runs because wall-time advanced enough to flip a timer ordering.
    - Why: clock injection is not all-the-way-down — a transitive util (retry timer, rate limiter) calls `Instant::now`, so the leaked clock advances with wall-time and changes op ordering.
    - Fix: (a) cargo-deny `disallowed_methods = ["std::time::Instant::now", "std::time::SystemTime::now"]` for the whole crate; (b) every clock read flows through `clock: SimClock` (prod: `time::Monotonic`; sim: injected); (c) CI audit `rg "Instant::now|SystemTime::now" crates/consensus-vsr/`; (d) keep `replay_100_same_seed_identical` as the regression backstop — the lint catches direct reads, the replay test catches everything.
    - Cost avoided: the entire determinism debt — without it, W88's VSR-side scenario gate and W92's 1M-cumulative gate are unattainable and v1.0 is unshippable (bar (c) violation). Also removes ~2–4 ms/scenario of `Instant::now` calls.
    - Muscle: clock injection in deterministic systems is ALL-OR-NOTHING — one leak invalidates the contract; enforce with cargo-deny + audit + a behavioral replay test (the lint alone is insufficient, exactly as with the runner's HashMap audit). Reapplies at: W90 consensus-vsr v1.0 (prod clock path must also flow through `time::Monotonic`), W92 ledger v1.0 determinism gate, W94 exec-vm v1.5 equivalence.
  - **(EXPERT) When `leader_crash_view_change_no_loss` reports a lost committed op:**
    - Symptom: after view-change, a previously-committed op is missing on the new leader.
    - Why: crash-restart preserved the ledger state but not VSR-specific state (view#, op#, the prepared-but-uncommitted log tail), so the new leader's recovery started from a stale point.
    - Fix: an explicit `ReplicaState { view, op_number, commit_number, log_tail }` struct durably journaled (R4); crash-restart restores VSR state from the journal, not just the SM state.
    - Cost avoided: a correctness bug that VOPR would surface as a state-divergence assertion — exactly the class VOPR exists to catch; missing it forfeits the bar.
    - Muscle: crash-restart must round-trip ALL durable state, not just the application's — protocol metadata is state too. Reapplies at: W90 consensus-vsr v1.0 recovery, W92 ledger v1.0 crash-restart soak.
