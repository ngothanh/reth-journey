- [NEW v2] **Monday-Wednesday — ledger VOPR: scenario runner + reporting**
  - [ ] **Build**: `crates/ledger-deterministic/src/vopr/runner.rs` — multi-process runner: 100 scenarios in parallel per machine. Per-scenario seed + final state hash. (~3 hrs)
    - **Why**: VOPR's bug-finding power scales with scenarios/second. A single-process runner is too slow (one panic per scenario kills the process). Multi-process gives fault isolation: scenario N panicking does not kill scenario N+1, and you can pin one scenario per core. 100 scenarios/machine × 8 machines × 86400s × N steps gets you to 1M scenarios/day by M27.
    - *Back-of-envelope* (runner target: ≥100 scenarios in <60s on 8-core M2 ⇒ ≥140k scenarios/day/machine ⇒ 1M/day on 8-machine fleet):
      Per-scenario wall budget (median) = **600 ms** (W88 v0.7 perf target); 8 cores running in parallel × 86400 s/day / 0.6 s/scenario = 1.15M scenarios/day per machine (theoretical), real-world ~140k after accounting for spawn/IPC overhead. The critical perf line is **IPC overhead per scenario must be << 600 ms**: process spawn ≈ ~5 ms (`fork+exec` on Linux), `sched_setaffinity` ≈ 50 µs, stdout JSON-line parse ≈ 5 µs/result. If spawn happens **per scenario** that's 5 ms × 100 = 500 ms wasted setup — a 25% throughput hit. The fix is the worker pool: spawn N workers **once** at startup, feed them scenarios via stdin/work-stealing. Per-scenario overhead drops to ~10 µs.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/vopr.zig` runner — multi-process spawn, exit-code semantics; Jepsen's process-orchestration in `jepsen.control`.
    - **Design**:
      ```rust
      pub struct Runner {
          workers: ArrayVec<WorkerProc, 128>,
          scenario_queue: Receiver<Scenario>,
          result_sink: Sender<ScenarioResult>,
      }
      pub struct WorkerProc { pid: Pid, stdin: ChildStdin, stdout: BufReader<ChildStdout>, seed: u64 }
      pub struct Scenario { seed: u64, ops: u64, fault_budget: FaultBudget, invariants: u32 /*bitmask*/ }
      pub struct ScenarioResult {
          seed: u64,
          outcome: Outcome,                  // Pass / InvariantViolation / Panic / Timeout
          final_state_hash: [u8; 32],
          ops_executed: u64,
          duration_ms: u64,
      }
      ```
      **Invariants**: (i) each worker is a fresh process (via fork or `Command::new(self_exe)`); (ii) seed S in master → seed S echoed in `ScenarioResult` and can re-run as `--seed S --replay`; (iii) state_hash canonical (W83) → cross-machine reproducibility; (iv) workers communicate result via JSON line on stdout — no shared memory.
    - **Build steps**: 1. (~15 min) Cargo bin target `vopr-worker` reading `Scenario` from argv/stdin, executing, printing `ScenarioResult` JSON to stdout. 2. (~25 min) `Runner::spawn_workers(n)` forks N children pinned to N cores via `sched_setaffinity`. 3. (~30 min) work-stealing scheduler: main loop reads scenarios from queue, dispatches to idle worker. 4. (~25 min) timeout handling: per-scenario deadline (60s wall) → SIGKILL worker, record Timeout outcome, respawn worker. 5. (~20 min) panic outcome: worker process exits non-zero → parse stderr for backtrace, record Panic outcome with seed. 6. (~25 min) repro support: on assertion violation, dump scenario to `vopr_artifacts/seed_<N>.json` for ./vopr-worker --replay re-run. 7. (~20 min) result aggregation: stream of ScenarioResult → counter exporter (Pass/Fail/Timeout per minute). 8. (~10 min) graceful shutdown: SIGTERM workers, drain queue, write summary.
    - **Pitfalls**: *Shared-resource contention across processes*: **Symptom**: scenarios run slow because they all write to /tmp/journal-N.wal on same disk. **Fix**: per-worker tmpfs scratch dir; or in-memory journal for sim. *Hash-of-state non-determinism cross-machine*: **Symptom**: same seed yields different state_hash on different machine architectures. **Fix**: BLAKE3 over canonical-sorted state; ban endianness-specific encoding. *Worker respawn loop*: **Symptom**: panicking-scenario kills worker; respawn picks SAME scenario; infinite loop. **Fix**: scenario marked Failed on first panic, NOT re-queued. *Zombie processes*: **Symptom**: SIGKILL'd workers accumulate as zombies. **Fix**: `waitpid(WNOHANG)` reaping in master loop. *stdin/stdout backpressure*: **Symptom**: worker stdout buffer fills, blocks. **Fix**: line-buffered, master reads asynchronously.
  - **Expect to hit (perf) #1 — fork-per-scenario instead of long-lived worker pool (bar (c) violation)**: implementing the runner as "for each scenario: `Command::new(self_exe).spawn()`; await child; collect result." Each `fork+exec` on Linux is ~5 ms (page-table copy + linker setup + `_start` runtime init). At 100 scenarios = 500 ms of pure spawn overhead; for short scenarios (~600 ms each) that's **~80% setup tax**. Profile shows `clone3` + `execve` dominating; observed throughput ~1k scenarios/min vs target ~16k/min.
    - Fix: spawn N workers **once** at runner startup (one `fork+exec` per core, ~50 ms total amortized over the day). Workers read newline-delimited `Scenario` JSON from stdin in a loop, execute, write `ScenarioResult` JSON to stdout, loop. Master maintains a work-stealing queue feeding stdin via `BufWriter`. Per-scenario IPC cost: ~10 µs (JSON encode + pipe write + decode).
    - Cost avoided: ~5 ms spawn × 100 scenarios = 500 ms saved per 100-scenario run = ~80% throughput unlock. Drives the 100k → 1M scenarios/day scaling.
    - Muscle: in any "do N identical things in parallel" architecture, amortize setup once at startup; never per-task. The same rule applies to thread pools, GPU kernel launches, RDMA QP setup. Reapplies at: W90 io_uring journal (ring construction once at startup, not per write), W82 matching-engine shard workers (per-symbol pinning once at startup), W77 messaging-aeron `Conductor` agent (one per shard, not per publication).
  - **Expect to hit (perf) #2 — `HashMap` / `BTreeMap` iteration in state-hash compute breaks cross-arch determinism (bar (c) violation)**: implementing state-hash as `let mut h = blake3::Hasher::new(); for (k, v) in sm.accounts.iter() { h.update(k.as_bytes()); h.update(&v.balance.to_le_bytes()); }`. If `sm.accounts: HashMap`, iteration order is non-deterministic per-run (random `BuildHasher`); if `BTreeMap`, order is deterministic per-arch BUT `to_le_bytes` on different-endian machines produces different bytes (mitigated by `to_le_bytes` explicit), and any nested `HashSet` field leaks non-determinism. Same seed, same op stream → **different state-hash on different machines** → "1M scenarios" cumulative count fragments because reproducer-by-seed can't be verified cross-machine.
    - Fix: state-hash is over a **canonical-sorted, explicit-endian byte stream**. (a) `accounts: BTreeMap<AccountId, Account>` only; (b) cargo-deny `disallowed_types = ["std::collections::HashMap", "ahash::AHashMap", "fxhash::FxHashMap"]` in the entire `ledger-deterministic` crate; (c) all `to_le_bytes` (not `to_ne_bytes`); (d) BLAKE3 over the sorted (key, fixed-endian-value) byte stream, computed by a single `hash_canonical(&sm)` function audited line-by-line. Cross-arch test in CI: x86 + ARM nodes produce identical state-hash for the same seed.
    - Cost avoided: the entire **determinism debt** — a single non-deterministic iteration invalidates cross-machine reproducibility, which forfeits the multi-machine fleet capability that gets us from 140k/machine to 1M/fleet/day (W88 v0.7 SHIP target) and 100M/fleet/day (W92 v1.0 perf target).
    - Muscle: deterministic state-hash = sorted iteration + explicit endianness + audited single function + cargo-deny on map types. This is the load-bearing primitive of any reproducer-by-seed system. Reapplies at: W90 consensus-vsr state-transfer (sender + receiver use same canonical-hash), W92 ledger v1.0 SHIP determinism gate (the 100x replay test), W92 cross-arch test (the v1.0 acceptance criterion), W94 exec-vm v1.5 parallel-vs-sequential equivalence (same state-hash post-block).
    - **Test scenarios**: 100 known-pass scenarios → 100 Pass results; inject one known-bad apply → expect failures concentrated on scenarios that exercise that code path; soak: 10k scenarios → 0 zombies, 0 leaked file descriptors.
    - **Acceptance**: 100 scenarios in parallel on 8-core M2 in <60s; each result reproducible via `--replay seed=N`; CI integration: nightly job runs 10k scenarios.

  - [ ] **Build**: `crates/consensus-vsr/src/vopr_integration.rs` — exposes deterministic test mode (clock injection + msg ordering) compatible with ledger's VOPR. (~3 hrs)
    - **Why**: ledger v1.0 (W92) will run replicated via consensus-vsr v1.0 (W90). To test the combined system under VOPR, vsr needs the same deterministic-test contract as ledger: injected clock, controllable msg-ordering, controllable crash-restart. This file is the bridge — implements `Replica` against the W84 DetHarness so ledger VOPR scenarios can drive multi-replica scenarios.
    - *Back-of-envelope* (mixed ledger+VSR scenario target: ≥100 scenarios in <60s on 8-core M2 ⇒ same budget as ledger-only):
      A 3-replica VSR scenario simulates ~3× the work of a single-replica ledger scenario (each op flows through 3 SMs). Per-scenario budget = ~1.8 s wall-clock on 1 core, ~600 ms on 3 pinned cores. The dominant cost is **message passing between simulated replicas**: ~3 messages per op × 10k ops × 3 replicas = ~90k messages per scenario. If each message goes through `tokio::sync::mpsc::channel` (~150 ns/send + ~100 ns/recv) = ~22 ms/scenario IPC. With a hand-rolled `SimNetwork: VecDeque<Message>` walked by the scheduler (a single-threaded for-loop, ~5 ns/push + ~5 ns/pop) = ~900 µs/scenario IPC — a **25× win** that's the difference between "100 scenarios in 60s" and "100 scenarios in 90s + missed target." Critical: the SimNetwork's `next_message()` is the **ordering oracle** — its single-threaded nature is what gives determinism, not a perf optimization. Single-threaded sim + bit-deterministic ordering are the same property here.
    - **Read first**: TigerBeetle `lib/tigerbeetle/src/vsr.zig` — esp. `Replica` and `Cluster` sim hooks; LIONS-VSR paper §5 "Recovery"; your own `consensus-vsr` v0.5 from W74 (deterministic mode hooks).
    - **Design**:
      ```rust
      pub struct VoprReplica {
          inner: NormalReplica,                // production VSR replica
          clock: SimClock,                     // injected from harness
          net: SimNetwork,                     // injected, observes/records all msgs
          replica_id: ReplicaId,
      }
      impl VoprReplica {
          pub fn new(id: ReplicaId, harness: &mut DetHarness) -> Self;
          pub fn step(&mut self) -> StepResult;    // single-step deterministic
          pub fn send(&mut self, to: ReplicaId, msg: VsrMessage);
          pub fn recv(&mut self) -> Option<VsrMessage>;
          pub fn crash(&mut self);
          pub fn restart(&mut self);
      }
      pub struct VoprCluster {
          replicas: ArrayVec<VoprReplica, 7>,  // up to 7 = quorum-of-4
          net: SimNetwork,
      }
      ```
      **Invariants**: (i) `step()` is the ONLY way time advances; (ii) all msgs go through `SimNetwork` which records + can drop/reorder/duplicate; (iii) clock can jump arbitrarily forward but never backward; (iv) crash-restart preserves journal; replica restores via journal replay; (v) determinism: same seed + same scenario script → byte-identical msg history.
    - **Build steps**: 1. (~15 min) `VoprReplica` wrapping NormalReplica with hookable clock/net. 2. (~25 min) `SimNetwork::send/recv` — bounded queue per (from, to) pair, fault inject before deliver. 3. (~30 min) clock injection: replace any internal `Instant::now()` with `clock.now()`; gate via `cfg(vopr_mode)`. 4. (~30 min) crash/restart: dump replica's volatile state, restart restores from journal (re-use ledger's recovery semantics for vsr-specific state). 5. (~20 min) ordering oracle hookup: `SimNetwork` consults DetHarness order_oracle when multiple messages are ready. 6. (~25 min) `VoprCluster::run_script` — accept a list of (clock_advance, action) tuples and drive deterministically. 7. (~20 min) VSR-specific invariants: view-change leaves quorum; committed messages never lost; no two leaders in same view. 8. (~15 min) wire into ledger VOPR runner: scenarios that span ledger+vsr.

Reapplies at: W90 consensus-vsr v1.0 (production clock path must also flow through `time::Monotonic`), W92 ledger v1.0 SHIP determinism gate, W94 exec-vm v1.5 parallel-vs-sequential equivalence (no `Instant` in either path).
  - **Expect to hit (perf) #2 — `tokio::sync::mpsc` for `SimNetwork` between simulated replicas (bar (c) violation)**: implementing `SimNetwork` as `HashMap<(ReplicaId, ReplicaId), tokio::sync::mpsc::UnboundedSender<Message>>`. Each `send` is ~150 ns (atomic CAS + waker registration); each `recv.await` is ~100 ns. At 90k messages × ~250 ns IPC = 22 ms per scenario. Worse: `tokio::sync::mpsc` ordering is FIFO **per-channel** but **non-deterministic across channels** — the scheduler may poll replica A's mailbox before B's, breaking bit-determinism.
    - Fix: `SimNetwork` is a **single-threaded** `BinaryHeap<(SimTime, Message)>` (or `BTreeMap<SimTime, Message>`) — one global priority queue keyed by simulated delivery time. The scheduler pops the next message, advances `SimClock` to its delivery time, hands it to the destination replica's `on_message`. Ordering is **total** by `(SimTime, source_id, msg_id)` — bit-deterministic. No tokio, no atomics, no channels.
    - Cost avoided: ~22 ms/scenario IPC removed (~25× speedup of the IPC layer); plus the **determinism win** (a deterministic ordering oracle is non-negotiable for VOPR replay). The mixed ledger+VSR scenarios hit the 100-in-<60s target only with this design.
    - Muscle: in any deterministic-replay system, "concurrent" entities run on a single thread driven by a virtual scheduler — concurrency is *simulated*, not *real*.
