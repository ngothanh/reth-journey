    #### Phase 3 — Make the tests pass, one failure at a time (~140 min)

    - **When `runner_worker_pool_one_fork_at_startup_not_per_scenario` reports per-scenario fork:**
      - Symptom: profile shows `clone3` + `execve` dominating; throughput ~1k scenarios/min vs ~16k/min target.
      - Why: implementing runner as "for each scenario: `Command::new(self_exe).spawn()`; await child; collect result." Each fork+exec ~5 ms (page-table copy + linker setup + `_start` init). At 100 scenarios = 500 ms setup; for 600 ms scenarios that's ~80% setup tax.
      - Fix: spawn N workers ONCE at runner startup (one fork+exec per core, ~50 ms total amortized over day). Workers read newline-delimited Scenario JSON from stdin in loop, execute, write ScenarioResult JSON to stdout, loop. Master maintains work-stealing queue feeding stdin via BufWriter. Per-scenario IPC cost: ~10 µs (JSON encode + pipe write + decode).
      - Cost avoided: ~5 ms spawn × 100 scenarios = 500 ms saved per 100-scenario run = ~80% throughput unlock; drives 100k → 1M scenarios/day.
      - Muscle: in any "do N identical things in parallel" architecture, amortize setup once at startup; never per-task. Reapplies at: W90 io_uring journal (ring construction once at startup, not per write), W82 matching-engine shard workers (per-symbol pinning once at startup), W77 messaging-aeron Conductor agent (one per shard, not per publication).

    - **When `runner_state_hash_cross_arch_deterministic` reports divergence:**
      - Symptom: x86 + ARM produce different state-hash for same seed; "1M scenarios" cumulative count fragments because reproducer-by-seed can't verify cross-machine.
      - Why: state-hash via `let mut h = blake3::Hasher::new(); for (k, v) in sm.accounts.iter() { h.update(k.as_bytes()); h.update(&v.balance.to_le_bytes()); }`. If `sm.accounts: HashMap`, iteration non-deterministic; if BTreeMap, deterministic per-arch BUT `to_le_bytes` on different-endian differs (mitigated explicit); any nested `HashSet` field leaks non-determinism.
      - Fix: state-hash over canonical-sorted explicit-endian byte stream. (a) `accounts: BTreeMap<AccountId, Account>` only; (b) cargo-deny `disallowed_types = ["std::collections::HashMap", "ahash::AHashMap", "fxhash::FxHashMap"]` in entire ledger-deterministic crate; (c) all `to_le_bytes` (not `to_ne_bytes`); (d) BLAKE3 over sorted (key, fixed-endian-value) byte stream, computed by SINGLE `hash_canonical(&sm)` function audited line-by-line. Cross-arch CI: x86 + ARM nodes produce identical state-hash for same seed.
      - Cost avoided: entire determinism debt — non-deterministic iteration invalidates cross-machine reproducibility, which forfeits multi-machine fleet (140k/machine to 1M/fleet/day W88 SHIP, 100M/fleet/day W92 v1.0).
      - Muscle: deterministic state-hash = sorted iteration + explicit endianness + audited single function + cargo-deny on map types. Load-bearing primitive of any reproducer-by-seed system. Reapplies at: W90 consensus-vsr state-transfer (sender + receiver use same canonical-hash), W92 ledger v1.0 SHIP determinism gate (the 100× replay test), W92 cross-arch test, W94 exec-vm v1.5 parallel-vs-sequential equivalence.

    - **5-year failure mode** (write in `notes/88_runner_followup.md`): when scenario count exceeds 100M/day (single fleet), distributed scheduler needed; current single-master design becomes wrong abstraction. Migration: scenario-mod-N sharding across master clusters.

    #### Phase 3 — Make the tests pass, one failure at a time (~140 min)

    - **When `vopr_integration_no_instant_now_leak_lint` fires in consensus-vsr:**
      - Symptom: VSR's NormalReplica internally calls Instant::now in retry-timer or `on_message`'s rate-limiter, even though surface API takes clock. One leak invalidates entire VOPR — same seed produces different op orderings because leaked clock advances with wall-time. 100-iteration replay of same seed yields different final state-hashes ~30% of the time (leak fires only on slow runs).
      - Why: clock injection not all-the-way-down; transitive call to a util function uses wall clock.
      - Fix: (a) cargo-deny `disallowed_methods = ["std::time::Instant::now", "std::time::SystemTime::now"]` in consensus-vsr crate; (b) all clock reads go through `clock: SimClock` (production: monotonic; sim: injected); (c) audit script `rg "Instant::now\|SystemTime::now" crates/consensus-vsr/` in CI; (d) 100× determinism replay test in `vopr_integration.rs::test_replay_100_same_seed` is the regression test.
      - Cost avoided: entire determinism debt — without this discipline, W88 SHIP gate (100k VSR-side scenarios reproducible from seed) and W92 SHIP gate (1M cumulative scenarios) unattainable; v1.0 unshippable. Wall-time: ~25 ns Instant::now (vDSO) × 90k messages/scenario = 2-4 ms wall-time per scenario removed.
      - Muscle: clock injection in deterministic systems is ALL-OR-NOTHING — one leak invalidates contract. CI must enforce via cargo-deny + audit script. Reapplies at: W90 consensus-vsr v1.0 (production clock path must also flow through `time::Monotonic`), W92 ledger v1.0 SHIP determinism gate, W94 exec-vm v1.5 parallel-vs-sequential equivalence.

    - **When `vopr_integration_sim_network_total_ordering` finds tokio mpsc:**
      - Symptom: `SimNetwork: HashMap<(ReplicaId, ReplicaId), tokio::sync::mpsc::UnboundedSender<Message>>`; each send ~150 ns (atomic CAS + waker); 90k messages × ~250 ns = 22 ms/scenario IPC. Worse: tokio mpsc ordering is FIFO per-channel but non-deterministic across channels — scheduler may poll A's mailbox before B's, breaking bit-determinism.
      - Why: chose convenient async primitive without thinking about ordering semantics.
      - Fix: SimNetwork is single-threaded `BinaryHeap<(SimTime, Message)>` (or `BTreeMap<SimTime, Message>`) — one global priority queue keyed by simulated delivery time. Scheduler pops next message, advances SimClock to its delivery time, hands to destination's `on_message`. Ordering is TOTAL by `(SimTime, source_id, msg_id)` — bit-deterministic. No tokio, no atomics, no channels.
      - Cost avoided: ~22 ms/scenario IPC removed (~25× speedup IPC layer); plus determinism win (deterministic ordering oracle non-negotiable for VOPR replay). Mixed ledger+VSR scenarios hit 100-in-<60s target only with this design.
      - Muscle: in any deterministic-replay system, "concurrent" entities run on single thread driven by virtual scheduler — concurrency is SIMULATED, not REAL. Same shape applies to Jepsen Maelstrom, FoundationDB sim-test, TigerBeetle simulator. Reapplies at: W90 consensus-vsr full deterministic test mode, W92 ledger v1.0 SHIP soak test (sim mode uses single-thread SimNetwork; production mode uses real tokio + UDP — both APIs identical), W94 exec-vm v1.5 block-stm property test (parallel exec scheduled by deterministic order).
