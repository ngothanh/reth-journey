  #### Phase 3 — Make the checks pass, one failure at a time (~80 min)

  Ordered newbie→expert — the ladder you actually walk.

  - **(NEWBIE) When `check_direct_dep_count_matches_cargo_toml` reports `reported 0`:**
    - Symptom: the script can't find `[dependencies]` — it greps the workspace root `Cargo.toml` (which has `[workspace.dependencies]`, not `[dependencies]`).
    - Why: workspace root and member manifests have different section names; the script pointed at the wrong file.
    - Fix: resolve each member's manifest path from `cargo metadata --no-deps` (`packages[].manifest_path`), then read that file's `[dependencies]`.
    - Muscle: a workspace has two manifest shapes — never assume "the Cargo.toml." Reapplies at: W144 M36 audit, any future xtask that walks a workspace.

  - **(SENIOR · ANTI-SHORTCUT) When `check_no_transitive_leakage` reports any count ≠ 5 on `matching-engine` (30+ for a full walk, or 6-9 for a partial de-dupe):**
    - Symptom: the script walks `cargo tree` without `--depth 1` (or `cargo metadata` *with* resolve); `matching-engine` reports 30+ when its `Cargo.toml` declares exactly 5. A subtler variant reports 6-9 — the script de-dupes most transitive nodes but still counts a few (or folds in dev-deps), which the old `-lt 10` band wrongly passed.
    - Why: `cargo tree` defaults to the full transitive graph; counting every node measures "what your build resolves to," not "what you chose." Correct as a build inventory, wrong metric for this bar. Partial de-dupe is the same bug halfway done — still not measuring direct intent.
    - Fix: `cargo metadata --no-deps`, read each package's `dependencies` array filtered to `kind==null` (normal deps, excluding dev/build), or `cargo tree --depth 1`. The metric is what YOUR manifest declares — transitive deps come along for the ride. Assert exact equality, never a `< N` ceiling.
    - Muscle: a dependency *audit* measures **direct intent**, not transitive resolution. Reapplies at: W121 blog dep-count claim, W144 M36 audit, every supply-chain review at a tier-A firm.

  - **(SENIOR · CROSS-PRIMITIVE) When `check_workspace_inherited_deps_counted_once` reports a dropped dep:**
    - Symptom: a crate using `serde = { workspace = true }` reports one fewer dep than declared; the naive line-count saw `workspace = true` and skipped it as "not a real version."
    - Why: workspace-inherited deps still ARE direct deps — the version just lives in the workspace manifest. The audit composed with the workspace-inheritance feature and the composition leaked.
    - Fix: count any key in `[dependencies]` regardless of whether its value is a version string, `{ version = .. }`, or `{ workspace = true }`. `cargo metadata --no-deps` already resolves the inherited version — use its `dependencies` array, which lists inherited deps.
    - Muscle: a feature that *resolves* a value elsewhere (workspace inheritance, `default-features`) doesn't change *that the dep is yours*. Reapplies at: W144 M36 audit, any `cargo deny`/SBOM tooling over a workspace.

  - **(EXPERT) When `check_uncategorized_dep_fails_closed` reports the script silently emitted `other` and exited 0:**
