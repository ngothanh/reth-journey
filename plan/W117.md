- [ ] **Đối chiếu (zero-dep audit)**: at the M30 gate, run `cargo tree --no-default-features` per workspace crate; list every external dep with a rationale per crate. Target: ≤10 non-mirror deps per crate (TigerStyle "Zero Dependencies"). Anything without rationale = drop or justify. (~total 180 min across 3 phases)
  - 🔧 **Why this matters**: M30 is the 5-path decision gate (per README). TigerStyle's zero-deps discipline is a load-bearing claim of bar-(c); the audit is the receipt. The audit you produce here is cited by the Q4 bar-(c) audit (Tuesday this week), referenced by the flagship blog post (W121), and re-run at M36 (W144) as the closing comparison metric — three downstream consumers ride on this one artifact being defensible.

  #### Phase 1 — Problem, requirements, design (~55 min, no audit yet)

  - **The problem this primitive solves**: a Rust workspace's dependency count is the cheapest single signal of supply-chain risk, build-time bloat, and "did the author actually understand the primitive or just `cargo add` it?" An audit that conflates direct vs transitive deps, or that lacks a per-dep rationale, becomes noise — every crate "fails" or every crate "passes" with no signal. The audit must produce a per-crate row that a hostile reviewer (a tier-A HFT firm interviewer) can read and form an opinion on in 30 seconds.

  - **Requirements** — write in `notes/zero_dep_audit_M30_design.md`:
    - R1. The audit produces `notes/zero_dep_audit_M30.md` with one row per workspace crate.
    - R2. Each row contains: crate name, **direct** dep count (not transitive), each direct dep name + rationale category (mirror / runtime / serialization / proc-macro / dev-only / other), and a flag column for "review at M36."
    - R3. Direct dep count is sourced from the crate's own `Cargo.toml` `[dependencies]` section, not from `cargo tree` walk depth.
    - R4. Bar-(c) crates (`matching-engine`, `ledger-deterministic`, `messaging-aeron`, `runtime-thread-per-core`, `consensus-vsr`, `mmap-queue`, `marketdata-kernelbypass`) have a hard target ≤10 non-mirror direct deps. Any crate over the bar requires a follow-up issue link in the row.
    - R5. The audit script is **re-runnable**: `cargo xtask zero-dep-audit` (or a shell script in `scripts/`) regenerates the table from scratch in <30s, so M36 can diff against M30 mechanically.
    - R6. Every dep flagged "other" (i.e. not a recognized rationale category) blocks the audit until categorized — the audit fails closed.
    - R7. The audit cites the TigerStyle Zero Dependencies source URL inline (https://tigerstyle.dev/) so a reviewer can resolve "what bar is this against?" without asking.

  - **Design walk-through** — answer each in your design doc; no peeking at the M30 numbers until Phase 3:
    - D1. Where does the dep list come from — `cargo tree --depth 1`, parsing `Cargo.toml` directly, or `cargo metadata --no-deps`? List the pros/cons of each. Which one gives you DIRECT deps only without transitive contamination? Which copes with workspace-inherited deps (`workspace = true`)?
    - D2. What counts as a "mirror" dep vs a non-mirror? Define the rule precisely (hint: a dep is "mirror" iff it implements the upstream module your crate is a mirror of — `crossbeam-utils` is mirror for `concurrent`, `serde` is not). Write the rule so two reviewers would categorize the same crate the same way.
    - D3. Sketch the row schema. Pick a representation (Markdown table vs YAML vs CSV). Which one diffs cleanly in git for the M30→M36 comparison? Which one is reviewer-friendly in a blog post?
    - D4. The "fail closed on uncategorized dep" requirement (R6) — how does the script enforce it? (Hint: a hard-coded categorization map, with the script `exit 1` if any dep is missing from the map.)
    - D5. Workspace crates that are dev-only (e.g. `xtask`, integration test harnesses) — do they count? Why or why not? Write the rule.
    - D6. **Pre-mortem (the load-bearing question)**: write down the *worst* misuse of this audit you can imagine — e.g. a reviewer screenshots one row out of context and posts it as evidence of bar-(c) failure. What property of the row format prevents that? (Hint: every row must be self-contained — name + count + rationale + URL + date — so a screenshot can't strip context.)
  - **Output**: `notes/zero_dep_audit_M30_design.md` with R1–R7 + D1–D6 + the row-schema mock + the categorization rule.

  #### Phase 2 — Write the failing checks (~45 min)

  Write each check below as part of the audit script. All "fail" initially because the script + categorization map don't exist yet — that's expected. Each check exposes one specific failure mode you'll fix in Phase 3.

  - [ ] `check_direct_dep_count_matches_cargo_toml` — for one known crate (`concurrent`), assert the script's reported direct dep count equals the number of lines in `[dependencies]` of `crates/concurrent/Cargo.toml`. Exercises R3.
  - [ ] `check_no_transitive_leakage` — run script against `matching-engine` (which has `tokio` direct + ~30 tokio transitive deps); assert reported count is the direct count (~5), not the inflated transitive count. Exercises R3.
  - [ ] `check_uncategorized_dep_fails_closed` — inject a dep not in the categorization map (e.g. `rand_distr`); assert the script exits non-zero with a clear error naming the dep. Exercises R6.
  - [ ] `check_bar_c_crate_threshold_enforced` — set a bar-(c) crate's dep count to 11 via test fixture; assert the script flags the crate and requires a follow-up-issue link in the row. Exercises R4.
  - [ ] `check_workspace_inherited_deps_counted_once` — a dep declared with `workspace = true` must appear in the row count, not be silently skipped. Exercises R3.

  #### Phase 3 — Make the checks pass, one failure at a time (~80 min)

  - **When `check_no_transitive_leakage` reports a count of 30+ on `matching-engine`:**
    - Symptom: the script walks `cargo tree` without `--depth 1` or uses `cargo metadata` with `resolve` (full graph); `matching-engine` reports 30+ deps when its `Cargo.toml` declares ~5.
    - Why: `cargo tree` defaults to the full transitive graph; counting every node is the wrong metric — it's "what your build resolves to," not "what you chose."
    - Fix: parse `Cargo.toml` directly (e.g. `cargo metadata --no-deps` then read each package's `dependencies` array), OR run `cargo tree --depth 1`. The metric is what YOUR Cargo.toml declares — transitive deps come along for the ride.
    - Muscle: a dependency audit measures **direct intent**, not transitive resolution. Reapplies at: W144 M36 audit, every future supply-chain review you'll do at a tier-A firm.

  - **When `check_uncategorized_dep_fails_closed` reports the script silently emitted "other" for an unknown dep:**
    - Symptom: a new dep was added between M29 and M30; the audit ran, produced a row with `rationale: other`, and exited 0 — no human noticed.
    - Why: the script defaulted to "other" instead of failing on unknown deps. "Fail open" defeats the audit.
    - Fix: hard-code the categorization map; on a dep not in the map, `exit 1` with `error: dep '$NAME' has no rationale; add it to scripts/dep_categories.toml or remove the dep`. The audit fails closed.
    - Muscle: an audit that can pass silently on unknown input is not an audit. Reapplies at: every future supply-chain / SBOM check, the M36 close audit (where new deps are most likely).

  - **When `check_bar_c_crate_threshold_enforced` reports the threshold violation but no follow-up issue:**
    - Symptom: `matching-engine` shows 11 deps in the table; no row column flags it; the audit "passes" because no script logic enforced the bar.
    - Why: the threshold is a documented target but not a script check — humans were supposed to notice. They don't.
    - Fix: in the script, after computing each row, branch on `is_bar_c_crate(name) && non_mirror_direct_count > 10`; require a `followup_issue: <URL>` field in the row, else exit 1 with the failing crate name.
    - Muscle: a target that isn't a script check is a wish. Reapplies at: W144 M36 audit threshold, future bar-(c) crate additions.

  - **When `check_output_is_diffable` reports byte-different output between two runs:**
    - Symptom: re-running produces the same data but reordered (deps in HashMap insertion order); `git diff M30 M36` lights up every row as "changed."
    - Why: HashMap iteration order is non-deterministic; the audit emits rows in dep-resolution order, which varies.
    - Fix: sort crates alphabetically; within each crate, sort deps alphabetically. Use BTreeMap, or sort the Vec before emit. Pin date format (ISO 8601) and use UTC.
    - Muscle: any artifact intended for git-diff comparison must have a stable, deterministic serialization. Reapplies at: W144 M36 audit, any future audits/inventory artifacts.

  - **When `check_row_is_self_contained` reports a row missing the source URL or date:**
    - Symptom: a screenshot of one row from the audit (taken by a hostile interviewer) lacks the TigerStyle citation; the row looks like an arbitrary opinion, not a measured bar against a public standard.
    - Why: the URL and date live in the file header, not in each row. Once decontextualized (screenshot), the bar is unrecoverable.
    - Fix: every row includes the bar source URL + audit date as columns (verbose, but each row stands alone). Yes, it's redundant — that's the point.
    - Muscle: artifacts that may be quoted out of context must carry their bar with them in every row. Reapplies at: blog-post evidence rows (W121), interview portfolio extracts.

  - **5-year failure mode** (write in `notes/zero_dep_audit_M30_followup.md` after green): when the Rust stdlib absorbs more (async-std → stdlib futures, more crypto in stdlib, more `core::net`), several deps currently flagged "mirror" or "runtime" will drop. Migration trigger: when ≥3 deps in the audit become stdlib-equivalent, re-classify them as "stdlib (was: $DEP)" and tighten the bar-(c) threshold from 10 to 7. State the version cutoff (e.g. Rust 1.95+) that triggers the re-classification.
