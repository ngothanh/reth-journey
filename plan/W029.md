**Tuesday — ARIES analysis pass**

- [ ] **Build**: `crates/recovery/src/analysis.rs` — `AnalysisPass<'a, R: Replayer>`. Walks WAL forward from last
  checkpoint LSN. Builds two tables: `DirtyPageTable` (PageId → recovery LSN) and `TransactionTable` (TxId → LastLsn).
  Stops at end of WAL. (~105 min)
  - **Why**: ARIES recovery is the canonical algorithm for crash recovery in DB systems — published 1992, still in use by DB2/Postgres/SQL Server/MySQL InnoDB. Its key contribution is *idempotent replay*: redo phase can be re-run after a re-crash without double-application. The Analysis phase scans the wal forward to determine the WORK SET for redo (which pages might need redo) and undo (which txs were in-flight at crash). Without correct DPT/TT, redo/undo over- or under-applies.
  - **Read first**: Mohan et al. "ARIES: A Transaction Recovery Method..." (1992) — §3 (algorithm), §4 (data structures). The original paper is 70 pages; read §3.1 "Analysis" deeply (~6 pages) and skim the rest. Also Hellerstein & Stonebraker "Readings in Database Systems" §7 for synthesis. PostgreSQL `src/backend/access/transam/xlog.c::StartupXLOG` for a production analysis pass.
  - **Design**:
    ```rust
    pub struct DirtyPageTable(BTreeMap<PageId, Lsn>);  // pageId → recLSN (first LSN that dirtied this page)
    pub struct TransactionTable(BTreeMap<TxId, TxEntry>);
    pub struct TxEntry {
        pub last_lsn: Lsn,
        pub status: TxStatus,     // Active, Committed, Aborted
        pub undo_next_lsn: Option<Lsn>,  // For tracking partial rollback progress
    }
    pub struct AnalysisPass<'a, R: Replayer> {
        replayer: R,
        dpt: DirtyPageTable,
        tt: TransactionTable,
        min_rec_lsn: Lsn,
        start_lsn: Lsn,  // taken from latest BeginCheckpoint record
        _marker: PhantomData<&'a ()>,
    }
    impl<'a, R> AnalysisPass<'a, R> {
        pub fn run(mut self) -> Result<AnalysisResult, AnalysisError> {
            // 1. Find latest BeginCheckpoint LSN; that's start_lsn. (Scan backwards from tail.)
            // 2. Initialize DPT/TT from EndCheckpoint payload (fuzzy snapshot).
            // 3. Replay forward from start_lsn:
            //    - On Begin: TT.insert(tx_id, { last_lsn: lsn, status: Active })
            //    - On Insert/Update/Delete: TT[tx_id].last_lsn = lsn; if page not in DPT: DPT.insert(page_id, lsn)
            //    - On Commit: TT[tx_id].status = Committed
            //    - On Abort: TT[tx_id].status = Aborted
            //    - On CLR: TT[tx_id].undo_next_lsn = record.undo_next_lsn; if page not in DPT: DPT.insert(page_id, lsn)
            //    - On Checkpoint: ignore (fuzzy)
            // 4. min_rec_lsn = min(DPT values), or end_lsn if DPT empty
            // 5. Done; report AnalysisResult { dpt, tt, min_rec_lsn, end_lsn }
        }
    }
    ```
    **Invariants**:
    - DPT contains exactly the pages that *might* have unflushed updates (LSN-greater-than-pageLSN possible).
    - TT contains exactly the txs that were *in some non-terminal state* at end of wal (Active OR Committed-but-pages-might-not-be-flushed).
    - `min_rec_lsn = min over DPT of recLSN`; this is the LSN where REDO starts.
    - Analysis is read-only — no wal writes, no page mutations.
    - Analysis must be idempotent: re-running on same wal yields identical (DPT, TT, min_rec_lsn).
  - **Build steps**:
    1. (~15 min) `DirtyPageTable` and `TransactionTable` data structures with serde for checkpoint payload.
    2. (~15 min) Locate latest BeginCheckpoint: scan wal segments backward; the BeginCheckpoint is the high-water mark; load EndCheckpoint's serialized DPT/TT as starting state.
    3. (~25 min) Forward scan loop: pattern-match each record kind, update DPT/TT.
    4. (~15 min) min_rec_lsn computation.
    5. (~15 min) `AnalysisResult` returned to caller; integration with `Recovery::recover`.
    6. (~20 min) Tests:
       - Crash at random LSNs; analysis produces (DPT, TT) consistent with manual inspection.
       - Property: analysis is idempotent.
       - Boundary: empty wal → empty DPT/TT.
  - **Pitfalls**:
    - *Missing the BeginCheckpoint*: if checkpoint record is in middle of corrupted segment, start from genesis (LSN 0). Very slow. **Symptom**: recovery time minutes instead of seconds. **Fix**: write *two* checkpoint records per checkpoint cycle (primary + backup), separated by ≥ 1 segment.
    - *Treating Checkpoint records as data*: forgetting to special-case Checkpoint kind → DPT polluted with phantom pages. **Symptom**: redo touches pages that don't need it. **Fix**: explicit kind dispatch.
    - *Fuzzy checkpoint*: ARIES checkpoint payload is a SNAPSHOT taken concurrently with txns; some records *between* BeginCheckpoint and EndCheckpoint may be partially reflected. **Symptom**: DPT missing pages. **Fix**: scan from BeginCheckpoint (not End); add to DPT whenever a record's pageId not already present.
    - *CLR overwrite vs union*: CLR for tx T records that we undid some change. If the page CLR touches isn't in DPT, must add it. **Symptom**: redo skips a page that CLR put dirty. **Fix**: `dpt.entry(page_id).or_insert(record.lsn)` — preserves min.
    - *Tx Commit before all data records flushed*: spec'd: Commit's LSN is durable, but its data pages may not be. **Symptom**: redo phase still needs to apply Committed tx's records. **Fix**: don't remove Committed tx from TT until *all its pages* are flushed (which only checkpoint can verify); TT.Committed persists into redo.
  - **Test scenarios**:
    - 100 txs, half committed, half active at end → TT has exactly 50 Committed + 50 Active.
    - Page modified in tx T1 (Aborted) and tx T2 (Committed): DPT has page's recLSN = T1's first write (lower).
    - Crash mid-CLR: re-run analysis sees the partial CLR; idempotent.
    - Wal with no checkpoint: analysis starts at LSN 0; equivalent result.
    - Property: for any wal, analysis result reproducible.
  - **Acceptance**:
    - Inheritance ratio ≥ 0.9 vs ARIES paper §3.1 description.
    - Recovery on 1 GB wal completes in < 10 seconds (single-pass).
    - 1000 random crash-position fuzz tests pass.
  - **Downstream**: Thursday's REDO consumes (DPT, min_rec_lsn); W30 UNDO consumes (TT); W64 raft snapshot loading uses same analysis pattern.

**Thursday — ARIES redo pass**

- [ ] **Build**: `crates/recovery/src/redo.rs` — `RedoPass`. Re-applies every WAL record from min(recoveryLSN) forward
  to a page if pageLSN < recordLSN. Idempotent. (~105 min)
  - **Why**: REDO is the recovery phase that brings page state back to "as of the moment of crash". The critical insight is *physical idempotence via LSN comparison*: a record at LSN L is re-applied to a page only if `page.pageLSN < L`. This guarantees that running REDO multiple times (e.g. on re-crashes) produces the same result. Without LSN-gating, naive replay would double-count updates.
  - **Read first**: ARIES paper §3.2 "Redo Pass"; PostgreSQL `src/backend/access/transam/xlog.c::StartupXLOG` redo loop; InnoDB's redo log apply.
  - **Design**:
    ```rust
    pub struct RedoPass<'a, R: Replayer, P: PageProvider> {
        replayer: R,
        pool: &'a mut P,
        dpt: &'a DirtyPageTable,
        min_rec_lsn: Lsn,
        end_lsn: Lsn,
    }
    impl<'a, R, P> RedoPass<'a, R, P> {
        pub fn run(mut self) -> Result<RedoStats, RedoError> {
            self.replayer.seek_to(self.min_rec_lsn)?;
            let mut applied = 0;
            while let Some(record) = self.replayer.next()? {
                if !is_redoable_kind(record.kind) { continue; }  // only data records
                let page_id = extract_page_id(&record.payload);
                
                // Filter 1: if not in DPT or DPT.recLSN > record.lsn → already flushed before crash. SKIP.
                let Some(rec_lsn) = self.dpt.get(&page_id) else { continue; };
                if record.lsn < *rec_lsn { continue; }
                
                // Filter 2: read page.pageLSN; if >= record.lsn → already applied. SKIP.
                let page = self.pool.fetch_exclusive(page_id)?;
                if page.page_lsn() >= record.lsn { continue; }
                
                // Apply: physical (or physiological) re-application of the record.
                apply_record(page, &record)?;
                page.set_page_lsn(record.lsn);
                applied += 1;
            }
            Ok(RedoStats { applied, end_lsn: self.end_lsn })
        }
    }
    ```
    **Invariants**:
    - REDO applies records in *forward LSN order*.
    - A record is applied iff `page_in_dpt AND record.lsn >= dpt.recLSN AND record.lsn > page.pageLSN`.
    - After REDO, every dirty page's pageLSN ≥ min(record.lsn covering it).
    - REDO is idempotent: re-running on same (wal, page-state) yields same final page-state.
    - REDO does NOT remove committed txs from TT — that's only done after their pages flush + checkpoint records it.
  - **Build steps**:
    1. (~15 min) `Replayer::seek_to(lsn)` — fast-forward to start LSN; binary search across segment first_lsns.
    2. (~20 min) `apply_record` dispatcher per RecordKind: Insert appends slot; Update overwrites; Delete removes; physiological semantics (re-apply by operation, not by raw bytes).
    3. (~15 min) Filter 1 (DPT/recLSN) — skip records older than the page's first dirty point.
    4. (~15 min) Filter 2 (pageLSN comparison) — skip already-applied.
    5. (~10 min) `apply_clr`: CLRs are also redoable; they record undo actions and bump pageLSN.
    6. (~10 min) Tests: crash-mid-redo + re-crash idempotence; replay matches no-crash baseline.
    7. (~20 min) Stress: 1k txs in wal, simulate crash at random byte, redo recovers everything pre-crash committed.
  - **Pitfalls**:
    - *Skipping the pageLSN check*: re-applying every record → doubled inserts, ghost rows. **Symptom**: post-recovery row count wrong. **Fix**: ALWAYS compare record.lsn vs page.pageLSN before mutate.
    - *Wal record physical vs logical*: a "physical" record specifies the exact bytes to write at offset; "logical" records specify "insert key K with value V". Idempotence requires physiological — partial logical (re-applicable but tolerant of partial state). **Symptom**: REDO of a logical Insert duplicates rows. **Fix**: every record carries enough state for physiological replay (e.g., target slot index, not just key).
    - *Page allocation during REDO*: if a wal record allocates a new page, that page must be marked as the same pgno. **Symptom**: redo allocates a different pgno → cross-references in other records break. **Fix**: every alloc record carries the allocated pgno; REDO uses the stored pgno, not the allocator.
    - *DPT filter under-aggressive*: if DPT is incomplete (e.g. lost checkpoint), redo applies more than necessary. **Symptom**: REDO time longer, but still correct. **Fix**: tolerable; correctness > efficiency on recovery path.
    - *Crash during REDO*: re-crash mid-redo must be recoverable. **Symptom**: half-redone state. **Fix**: pageLSN updates are themselves journaled (or fsync at the page level on a periodic boundary so re-run picks up where we left off).
    - *Concurrent reads during recovery*: NONE — recovery is single-threaded, no readers until done. **Fix**: gate Wal/storage open() until Recovery::recover returns Ok.
  - **Test scenarios**:
    - 1000 records crash at byte N, recover, all pre-N records visible.
    - Crash during REDO at random pageLSN update; re-run recover; final state matches single-pass baseline.
    - Property: REDO(REDO(state)) == REDO(state).
    - Adversarial: forged record with very-future LSN (e.g., LSN = u64::MAX); page never had that LSN, so REDO tries to apply; assert apply_record validates record structure (no panic).
  - **Acceptance**:
    - Idempotence property test: 1000 random crash-during-redo points all converge.
    - Inheritance ratio ≥ 0.9 vs ARIES paper §3.2.
    - Recovery throughput: ≥ 50k records/sec applied.
  - **Downstream**: W30 UNDO follows REDO; W64 raft snapshot install uses analogous "fast-forward via stored LSNs" pattern; W74 matching-engine startup; W80 ledger restart.
