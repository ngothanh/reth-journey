**Tuesday — ARIES analysis pass**

- [ ] **Build**: `crates/recovery/src/analysis.rs` — `AnalysisPass<'a, R: Replayer>`. Walks WAL forward from last
  checkpoint LSN. Builds two tables: `DirtyPageTable` (PageId → recovery LSN) and `TransactionTable` (TxId → LastLsn).
  Stops at end of WAL. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: ARIES recovery is the canonical crash-recovery algorithm — published 1992, still
    in use by DB2/Postgres/SQL Server/MySQL InnoDB. Its key contribution is *idempotent replay*. The
    Analysis phase scans the wal forward to determine the WORK SET for redo (which pages might need redo)
    and undo (which txs were in-flight at crash). Without correct DPT/TT, redo/undo over- or under-applies.
    Downstream: Thursday's REDO consumes (DPT, min_rec_lsn); W30 UNDO consumes (TT); W64 raft snapshot
    loading uses same analysis pattern.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: post-crash, a wal contains 100k records but the pages on disk
    reflect only a subset. Without knowing which pages might be stale and which txs were in-flight,
    REDO would re-apply everything (slow + may double-apply over UNDO) and UNDO would have no targets.
    Analysis is the read-only scan that produces the DPT + TT that downstream phases consume.

  - **Requirements** — write in `crates/recovery/notes/29_analysis_design.md`:
    - R1. `DirtyPageTable(BTreeMap<PageId, Lsn>)` — pageId → recLSN (first LSN that dirtied this page).
    - R2. `TransactionTable(BTreeMap<TxId, TxEntry>)` — tx → (last_lsn, status, undo_next_lsn).
    - R3. `AnalysisPass::run` scans forward from latest BeginCheckpoint; updates DPT/TT per record kind.
    - R4. `min_rec_lsn = min over DPT of recLSN` (LSN where REDO starts); end_lsn if DPT empty.
    - R5. Analysis is READ-ONLY: no wal writes, no page mutations.
    - R6. Idempotent: re-running on same wal yields identical (DPT, TT, min_rec_lsn).
    - R7. Recovery on 1 GiB wal completes in <10 seconds (single-pass).
    - R8. 1000 random crash-position fuzz tests pass.

  - **Design walk-through** — answer each:
    - D1. Why start from BeginCheckpoint, not EndCheckpoint? (Hint: fuzzy checkpoint — records between
      Begin and End may be partially reflected.)
    - D2. Record dispatch: write the update rule for each kind (Begin / Insert / Commit / Abort / CLR /
      Checkpoint).
    - D3. Committed-but-not-flushed txs: stay in TT until checkpoint confirms pages flushed. Why?
    - D4. Pre-mortem: missing BeginCheckpoint scenario; how does analysis stay correct?

  - **Output**: `notes/29_analysis_design.md` with R1–R8 + D1–D4 + the per-kind update table.

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  - **When `dpt_keeps_min_rec_lsn` reports `DPT[page] = 100` instead of `50`:**
    - Symptom: DPT entry for the page records the LATER LSN, not the earlier one.
    - Why: update logic was `dpt.insert(page_id, record.lsn)` — overwrites; should be `entry().or_insert()`.
    - Fix: `dpt.entry(page_id).or_insert(record.lsn)` — preserves the MIN per the recLSN definition.
    - Muscle: DPT.recLSN is the EARLIEST LSN that dirtied the page; `or_insert` (insert-if-absent)
      preserves that. `insert` (overwrite) is wrong. Reapplies at: W30 UNDO state-machine, W64 raft
      snapshot install.

  - **When `analysis_idempotent` reports different DPT on second run:**
    - Symptom: second run's DPT contains an extra entry (or fewer).
    - Why: analysis state leaked between runs — `AnalysisPass` was reused without resetting `dpt`/`tt`.
    - Fix: `AnalysisPass::new(replayer)` is the constructor; each call to `run` consumes self (`self`
      moves). State cannot leak.
    - Muscle: analysis state machines must be one-shot (`self` move on run); mutability of state across
      runs admits silent corruption. Reapplies at: W30 RedoPass / UndoPass, W64 raft replay.

  - **When `bench_1gb_wal_under_10s` reports 45 seconds:**
    - Symptom: 4.5× slower than target.
    - Why: BeginCheckpoint scan walks segments from genesis (newest-first scan didn't work because the
      checkpoint scan was implemented as a full forward iteration with "remember the last seen
      BeginCheckpoint" — that's two passes).
    - Fix: BeginCheckpoint scan is BACKWARDS from the wal tail — stop at the first BeginCheckpoint
      found. Forward analysis then starts from that LSN.
    - Cost avoided: 4.5× wall time on recovery; for 100 GiB wal, ~7.5 minutes saved.
    - Muscle: locate-by-marker scans walk in the marker-frequency direction; checkpoints are rare and
      recent, walk backwards from tail. Reapplies at: W30 RedoPass start (seek to min_rec_lsn), W64
      raft snapshot location.

  - **When `vopr_1000_random_crash_positions` reports 50 trials with incorrect TT.status:**
    - Symptom: a tx that should be Active (no Commit record) shows as Committed; analysis incorrectly
      "remembered" a Commit from a re-tried scan.
    - Why: state leakage between iterations of the forward scan; `tt[tx].status = match record.kind {
      Commit => Committed, ... }` doesn't reset status if a CLR or other record arrives after Commit.
    - Fix: state-machine table — given current `tt[tx].status` and the new record's kind, compute the
      valid transition. Disallow invalid transitions (e.g. Commit → Active).
    - Muscle: transaction states form a strict state machine; transitions enforced via a table prevent
      data-corruption-via-out-of-order records. Reapplies at: W30 UNDO loop (CLR vs data record), W64
      raft term state.

  - **5-year failure mode** (write in `notes/29_analysis_followup.md` after green): when MVCC replaces
    ARIES (Postgres-style), the DPT collapses (every version is its own entry); analysis becomes
    "scan visible versions". State the migration: `RecoveryStrategy` trait. Trigger: switching to
    MVCC-style versioned storage.

**Thursday — ARIES redo pass**

- [ ] **Build**: `crates/recovery/src/redo.rs` — `RedoPass`. Re-applies every WAL record from min(recoveryLSN) forward
  to a page if pageLSN < recordLSN. Idempotent. (~total 140 min across 3 phases)
  - 🔧 **Why this matters**: REDO brings page state back to "as of the moment of crash". The critical insight
    is *physical idempotence via LSN comparison*: a record at LSN L is re-applied to a page only if
    `page.pageLSN < L`. This guarantees re-running REDO (e.g. on re-crashes) produces the same result.
    Without LSN-gating, naive replay double-counts updates. Downstream: W30 UNDO follows REDO; W64 raft
    snapshot install; W74 matching-engine startup; W80 ledger restart.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: after Analysis, you have a list of pages that might need
    re-applied records (DPT) and a starting LSN (min_rec_lsn). REDO walks the wal from min_rec_lsn
    forward; for each record, checks (a) is the page in DPT? (b) is the record's LSN >= DPT.recLSN?
    (c) is page.pageLSN < record.lsn? Only if all three: apply the record. The LSN gate is the
    idempotence guarantee.

  - **Requirements** — write in `crates/recovery/notes/29_redo_design.md`:
    - R1. `RedoPass` walks records in forward LSN order from min_rec_lsn to end_lsn.
    - R2. Filter 1: skip if `page_id not in DPT OR record.lsn < DPT.recLSN`.
    - R3. Filter 2: skip if `page.pageLSN >= record.lsn` (already applied).
    - R4. On apply: `apply_record(page, record)` + `page.set_page_lsn(record.lsn)`.
    - R5. REDO is idempotent: `REDO(REDO(state)) == REDO(state)`.
    - R6. CLRs are redoable (re-apply the undo action, bump pageLSN).
    - R7. Recovery throughput ≥50k records/sec applied.
    - R8. 1000 random crash-during-redo positions all converge to same final state.

  - **Design walk-through**:
    - D1. Physical vs logical vs physiological records — which does ARIES require? (Hint: physiological.)
    - D2. Page allocation records: how does REDO get the same pgno as the original alloc? (Hint:
      record carries the alloc'd pgno.)
    - D3. Concurrent reads during recovery — allowed? (Hint: no; gate wal.open() until recover() returns.)
    - D4. Pre-mortem: skipping the pageLSN check; what's the corruption shape?

  - **Output**: `notes/29_redo_design.md` with R1–R8 + D1–D4 + apply_record dispatch table.

  #### Phase 3 — Make the tests pass, one failure at a time (~80 min)

  - **When `redo_skips_already_applied` reports the record WAS applied (doubled state):**
    - Symptom: page had pageLSN=100 but REDO re-applied record at lsn=90; row count is 2× expected.
    - Why: filter 2 (`page.pageLSN >= record.lsn → skip`) was inverted, or the comparison used `<=`
      instead of `<`.
    - Fix: `if page.page_lsn() >= record.lsn { continue; }` — strict inequality on application; equal
      pageLSN means already applied (record applied AT that LSN). The recovery guarantee depends on
      this exact direction.
    - Muscle: idempotent replay's correctness hinges on the strict LSN gate; off-by-one or inverted
      comparison breaks the whole recovery model. Reapplies at: W30 UNDO CLR comparison, W64 raft
      log apply.

  - **When `redo_idempotent_double_run` reports diverged state on second run:**
    - Symptom: REDO produces state S1; running REDO again on S1 produces S2 ≠ S1.
    - Why: `apply_record` was non-idempotent — e.g. it issued an "insert at next slot" which advances
      the slot counter; second apply inserts at a different slot.
    - Fix: physiological semantics — record carries the TARGET slot index. `apply_record` writes to
      THAT slot; if it's already populated with the same value, no-op.
    - Muscle: REDO requires physiological log records (operation + enough state to replay
      idempotently); pure logical or pure physical fail. Reapplies at: W30 UNDO (compute_undo must be
      physiological too), W64 raft log apply.

  - **When `crash_during_redo_1000_runs_converges` reports 30 trials with diverged state:**
    - Symptom: crash mid-REDO at random byte; re-run gets a different final state on 30/1000.
    - Why: REDO's pageLSN updates aren't durable (the page is in BufferPool, not flushed). Re-crash
      sees the old pageLSN; re-applies records that the first run applied. The doubled application
      is what diverges.
    - Fix: REDO is not required to flush after each apply (perf), but it MUST detect "I already applied
      this in a previous attempt" via the pageLSN itself. If the page is dirty in memory but flushed
      pageLSN is stale, you have an inconsistency. Solution: REDO flushes the bufpool periodically
      (e.g. every 1000 records) so a re-crash picks up at the latest flushed pageLSN.
    - Muscle: idempotent replay is only as good as the visibility of its state to future re-runs; flush
      periodically to bound re-work. Reapplies at: W30 UNDO CLR durability, W64 raft snapshot.

  - **When `bench_50k_records_per_sec` reports 8k/sec:**
    - Symptom: 6× too slow; perf shows time in `pool.fetch_exclusive` (latch contention).
    - Why: each record's `fetch_exclusive` acquires + releases a page latch — even single-threaded,
      that's ~200ns/record overhead.
    - Fix: REDO is single-threaded by definition (no readers during recovery). Replace the latch
      acquisition with a direct page pointer cache — once we fetch a page, hold it until we leave it.
    - Cost avoided: ~190ns/record; at 50k/sec, ~9.5ms/sec CPU reclaimed. Recovery on a 1 GiB wal
      drops from 60s to 10s.
    - Muscle: single-writer phases don't pay locking costs; hold page references across multiple
      records without re-fetching. Reapplies at: W30 UNDO loop, W64 raft snapshot install.

  - **5-year failure mode** (write in `notes/29_redo_followup.md` after green): when MVCC replaces
    ARIES (Postgres-style), REDO becomes "promote highest visible version" — no pageLSN gate. State
    the migration: `RecoveryStrategy` trait, `AriesStrategy` and `MvccStrategy` impls. Trigger:
    switching the storage layer to MVCC versioning.
