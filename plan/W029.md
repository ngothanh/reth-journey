**Tuesday — ARIES analysis pass**

- [ ] **Build**: `crates/recovery/src/analysis.rs` — `AnalysisPass<'a, R: Replayer>`. Single forward scan of the WAL from the last `BeginCheckpoint`; produces `DirtyPageTable` (PageId → recLSN) + `TransactionTable` (TxId → entry) + `min_rec_lsn`. (~total 165 min across 3 phases)
  - 🔧 **Why this matters**: mirrors PostgreSQL `StartupXLOG`'s analysis scan + InnoDB `recv_scan_log_recs`. Analysis computes the WORK SET: which pages might need redo (DPT) and which txs were in-flight at crash (TT). First-attempt impls fail ≥1 test below — and the debug session IS the lesson. The 4 traps: **(1)** using `insert` instead of `or_insert` for recLSN (loses the MIN), **(2)** treating TT.status as a free assignment instead of a strict state machine (out-of-order CLR corrupts status), **(3)** locating the checkpoint by forward scan from genesis instead of backward scan from tail (bar (c) perf cliff), **(4)** reusing the pass across runs so state leaks (idempotence break). Downstream: Thursday's REDO consumes `(DPT, min_rec_lsn)`; W30 UNDO consumes `TT`; W64 raft snapshot loading reuses the forward-replay pattern.

  - *Contract* (signature-level — NEVER the body):
    ```rust
    pub struct DirtyPageTable(pub BTreeMap<PageId, Lsn>);   // page -> recLSN (EARLIEST dirtying LSN)
    pub struct TxEntry { pub last_lsn: Lsn, pub status: TxStatus, pub undo_next_lsn: Option<Lsn> }
    pub struct TransactionTable(pub BTreeMap<TxId, TxEntry>);
    pub enum TxStatus { Active, Committed, Aborted }
    pub struct AnalysisResult { pub dpt: DirtyPageTable, pub tt: TransactionTable, pub min_rec_lsn: Lsn }
    impl<'a, R: Replayer> AnalysisPass<'a, R> {
        pub fn new(wal: &'a R) -> Self;
        pub fn run(self) -> AnalysisResult;   // consumes self -> one-shot, no state leak
    }
    ```

Per-record CPU = one branch on record-kind (~5 ns mispredict-bounded) + one BTreeMap probe (log₂(8.4M)≈23 comparisons × ~5 ns L2 ≈ 115 ns) ≈ **~120 ns/record × 8.4M ≈ 1 s CPU**. So <10 s target (R7) needs the single-pass scan; the **cliff** is checkpoint location: backward-from-tail finds it in ~1 page read (~3 ns cached / ~100 µs cold seek) vs forward-from-genesis re-reading the whole 1 GiB to "remember the last BeginCheckpoint" = **a second full pass, ~2× wall time = bar (c) violation**.

  #### Phase 3 — Make the tests pass, one failure at a time (~85 min)

  Ordered newbie → expert — the ladder you actually walk.

  - **(NEWBIE) When `dpt_keeps_min_rec_lsn` reports `DPT[page] = 100` instead of `50`:**
    - Symptom: assertion fails; DPT entry holds the LATER LSN.
    - Why: update logic was `dpt.insert(page_id, record.lsn)` — `insert` overwrites; recLSN must be the MIN.
    - Fix: `dpt.entry(page_id).or_insert(record.lsn);` — insert-if-absent preserves the earliest.
    - Cost avoided: **correctness, not perf — silent data loss**: a too-high recLSN makes REDO start late and SKIP records 50..99, leaving the page permanently stale. `cargo test` on a hand-built WAL would pass; only the min-LSN test bites.
    - Muscle: recLSN is the EARLIEST dirtying LSN; `or_insert` preserves the min, `insert` destroys it. Reapplies at: W30 UNDO `undo_next_lsn` chaining (keep the chain head), W64 raft snapshot install (earliest-index wins).

  - **(SENIOR) When `out_of_order_clr_does_not_resurrect_active` reports `status == Active`:**
    - Symptom: a committed tx is reported Active because a trailing CLR reset its status.
    - Why: status was a free assignment `tt[tx].status = map(record.kind)` — every record clobbers status with no regard to the current state.
    - Fix: a strict transition table — `fn next(cur: TxStatus, kind) -> TxStatus` where `Committed`/`Aborted` are TERMINAL (CLR/Update leave them unchanged). Disallow `Commit → Active`.
    - Cost avoided: **correctness — UNDO would roll back a committed tx** (W30 consumes TT.status); durability violation. Cost: a committed user write silently disappears after recovery.
    - Muscle: transaction status is a state machine with terminal states; enforce transitions via a table, never by last-write-wins assignment. Reapplies at: W30 UNDO loop (CLR vs data record), W64 raft term/role transitions, W74 matching-engine order lifecycle.

  - **(SENIOR) When `analysis_idempotent` reports a different DPT on the second run:**
    - Symptom: second run's DPT has an extra (or missing) entry.
    - Why: analysis state leaked — `AnalysisPass` was built once and `run` took `&mut self`, so `dpt`/`tt` carried over.
    - Fix: `run(self)` consumes `self` (one-shot); the result owns the tables. A fresh `AnalysisPass::new` per run cannot leak.
    - Cost avoided: **correctness — nondeterministic recovery**; fails R6 and breaks the VOPR oracle (you can't compare two runs if the pass is stateful). No perf cost; pure soundness.
    - Muscle: recovery passes are one-shot — move `self` on `run` so the type system forbids reuse. Reapplies at: W30 RedoPass/UndoPass, W64 raft replay, W80 ledger restart.

  - **(EXPERT, perf, bar (c)) When `bench_1gb_wal_under_10s` reports 45 seconds (bar (c) violation):**
    - Symptom: 4.5× over target; `perf` shows ~50% of time in the WAL forward iterator, called twice.
    - Why: the `BeginCheckpoint` location was implemented as a forward scan from genesis remembering the last-seen Begin — that re-reads the entire 1 GiB before the real analysis pass even starts = two full passes.
    - Fix: locate `BeginCheckpoint` by a BACKWARD scan from the WAL tail; stop at the first one found, then run the single forward analysis from that LSN.
    - Cost avoided: **~4.5× wall time** — the redundant 1 GiB pass costs ~1 s CPU + ~1 s I/O *per* recovery; on a 100 GiB ledger WAL that is ~7.5 minutes of avoidable downtime on every cold start. `(bar (c) violation)` — slow recovery breaks the substrate SLA.
    - Muscle: locate-by-rare-marker scans walk in the marker-frequency direction; checkpoints are rare and recent → walk backward from tail. Reapplies at: W30 RedoPass start (seek to min_rec_lsn), W64 raft snapshot location, W80 ledger snapshot seek.

  - **(EXPERT, VOPR) When `vopr_1000_random_crash_positions` reports ~50 trials with a torn-tail divergence:**
    - Symptom: trials whose cut lands mid-record produce an extra/garbled TT or DPT entry vs the valid prefix.
    - Why: the WAL iterator yielded the torn final record (CRC/length mismatch) and analysis processed it as if valid — a half-written record looked like a Commit/Update.
    - Fix: the WAL reader (W26) must stop at the last record whose framing+CRC validates; analysis only ever sees whole, verified records. Make `Replayer::iter` return `Item = Result<Record, Torn>` and break on `Torn`.
    - Cost avoided: **correctness — recovery from a real crash always sees a torn tail**; processing it corrupts the DPT/TT and the divergence is invisible until production. Caught only by VOPR.
    - Muscle: the recovery oracle is "analysis(prefix) == analysis(truncated)"; the torn-tail boundary must be deterministic and verified, not trusted. Reapplies at: W30 REDO/UNDO tail handling, W31 mmap-queue excerpt boundary, W64 raft log tail truncation.

  - **5-year failure mode** (write in `notes/29_analysis_followup.md` after green): when MVCC replaces ARIES (Postgres-style heap-with-version-chains), the DPT model collapses — every tuple version is its own visibility entry and analysis becomes "scan to rebuild the in-flight xid set + dirty-version set". **Trigger**: storage layer switches to versioned tuples (measurable: `storage-trie` adopts copy-on-write pages, W29 Wed onward). **Migration (1 line)**: introduce a `RecoveryStrategy` trait with `AriesStrategy` (this week) and `MvccStrategy` impls; analysis dispatches through it.

**Thursday — ARIES redo pass**

- [ ] **Build**: `crates/recovery/src/redo.rs` — `RedoPass`. Re-applies WAL records from `min_rec_lsn` forward, applying a record to a page iff `page.pageLSN < record.lsn`. Idempotent. (~total 165 min across 3 phases)
  - 🔧 **Why this matters**: mirrors PostgreSQL `redo` loop + InnoDB `recv_apply_hashed_log_recs`. The key insight is *physical idempotence via the LSN gate*: a record at LSN L is applied to a page only if `page.pageLSN < L`, so re-running REDO (after a re-crash mid-recovery) yields the same result. First-attempt impls fail ≥1 test — the debug session is the lesson. The 4 traps: **(1)** inverted/`<=` LSN gate (double-applies state), **(2)** non-physiological `apply_record` (logical "insert at next slot" is non-idempotent), **(3)** re-crash divergence because dirty pageLSNs are never flushed (unbounded re-work), **(4)** per-record page-latch acquisition in a single-threaded phase (bar (c) perf cliff). Downstream: W30 UNDO follows REDO; W64 raft snapshot install; W74 matching-engine startup; W80 ledger restart.

  - *Contract* (signature-level):
    ```rust
    pub trait Replayer {
        fn apply_record(&mut self, page: &mut Page, rec: &Record);  // physiological: rec carries the target slot
        fn fetch_page(&mut self, id: PageId) -> &mut Page;          // returns page with current pageLSN
    }
    pub struct RedoPass<'a, R: Replayer> { /* dpt, min_rec_lsn, wal, replayer */ }
    impl<'a, R: Replayer> RedoPass<'a, R> {
        pub fn new(wal: &'a R, dpt: DirtyPageTable, min_rec_lsn: Lsn) -> Self;
        pub fn run(self);   // applies in place; one-shot
    }
    ```
  - *Back-of-envelope* (bar (c)): ~8.4M records on a 1 GiB WAL. Per applied record: fetch page (cached in bufpool ~3 ns; cold ~100 ns L3 / ~16 µs disk), apply ~tens of ns, set pageLSN ~2 ns. Target ≥50k records/s (R7) ⇒ ≤20 µs/record budget. The **cliff**: a per-record page latch `fetch_exclusive` costs ~25-200 ns acquire+release *each*; at 8.4M records that is ~0.2-1.7 s of pure latching for ZERO benefit — REDO is single-threaded (no concurrent readers during recovery), so the latch is **a bar (c) violation**. Holding a page pointer across consecutive records on the same page avoids it.

    - R3. Filter 2 (LSN gate): skip if `page.pageLSN >= record.lsn` (already applied).
    - R4. On apply: `apply_record(page, rec)` then `page.set_page_lsn(rec.lsn)`.
    - R5. Idempotent: `REDO(REDO(state)) == REDO(state)`.
    - R6. CLRs are redoable (re-apply the compensating action, bump pageLSN).
    - R7. Throughput ≥ 50k records/sec applied (single-threaded).
    - R8. 1000 random crash-during-redo positions all converge to the same final page state.

    - D2. Page-allocation records: how does REDO reproduce the SAME pgno as the original alloc? (the record carries the allocated pgno.)
    - D3. Concurrent reads during recovery — allowed? (No; gate `wal.open()`/reads until `recover()` returns.)
    - D4. **Pre-mortem (load-bearing):** write the 4-5 line trace for the inverted LSN gate — page pageLSN=100, record lsn=90, gate written `<=` → record re-applied → row count doubles. Show the exact wrong line and the doubled state.

    - D6. **Anti-shortcut audit:** (a) `fetch_exclusive` page latch per record — why wrong HERE (single-writer phase, the perf cliff); (b) logical "insert at next free slot" — why wrong (non-idempotent under R5); (c) flushing after every applied record "to be safe" — why wrong (8.4M fsyncs = ~42 minutes at 300 µs each; flush periodically instead).

  #### Phase 3 — Make the tests pass, one failure at a time (~85 min)

  - **(NEWBIE) When `redo_skips_already_applied` reports the record WAS applied (rows = 2):**
    - Symptom: page had pageLSN=100 but REDO re-applied the lsn=90 record; row count doubled.
    - Why: the LSN gate was inverted or used `<=` — `if page.page_lsn() <= rec.lsn { apply }` re-applies at equal/lower LSN.
    - Fix: `if page.page_lsn() >= rec.lsn { continue; }` — strict; equal pageLSN means already applied AT that LSN.
    - Cost avoided: **correctness — silent double-apply of every replayed record**; row counts, balances, trie nodes all corrupt. `cargo test` on a fresh page passes; only the pre-dirtied-page test bites.
    - Muscle: idempotent replay hinges on the exact LSN-gate direction; off-by-one/inverted comparison breaks the whole recovery model. Reapplies at: W30 UNDO CLR `undo_next_lsn` comparison, W64 raft `commitIndex` apply gate, W80 ledger replay.

  - **(SENIOR) When `redo_idempotent_double_run` reports diverged page bytes on the second run:**
    - Symptom: REDO → state S1; REDO again → S2 ≠ S1.
    - Why: `apply_record` was logical/non-idempotent — e.g. "insert at next free slot" advances a slot counter, so the second apply lands in a different slot.
    - Fix: physiological records — the record carries the TARGET slot index; `apply_record` writes THAT slot; re-writing the same value is a no-op.
    - Cost avoided: **correctness — re-crash during recovery permanently corrupts pages** (and breaks the VOPR oracle). No perf cost; pure soundness.
    - Muscle: REDO requires physiological log records (operation + enough replay state); pure logical and pure physical both fail idempotence. Reapplies at: W30 UNDO `compute_undo` must be physiological too, W64 raft state-machine apply.

  - **(SENIOR) When `clr_redoable_bumps_pagelsn` reports pageLSN unchanged after the CLR:**
    - Symptom: CLR at lsn=200 left pageLSN at 150; UNDO (W30) will then re-undo on a re-crash.
    - Why: CLRs were treated as "undo-only" and skipped in REDO; they ARE redoable — they bump pageLSN like any record.
    - Fix: in the redo dispatch, a CLR re-applies its compensating action and sets `page.set_page_lsn(clr.lsn)`.
    - Cost avoided: **correctness — repeated/lost undo across re-crashes**; the ARIES guarantee that undo work is itself logged and never repeated breaks. Reapplies at: W30 UNDO loop (CLR generation), W64 raft.
    - Muscle: CLRs are normal redoable log records that happen to record undo actions; redo them like everything else. Reapplies at: W30 UNDO, W80 ledger compensating entries.

  - **(EXPERT, perf, bar (c)) When `bench_50k_records_per_sec` reports 8k/sec (bar (c) violation):**
    - Symptom: ~6× too slow; `perf` shows the bulk of time in `pool.fetch_exclusive` (page latch acquire/release).
    - Why: each record acquired+released a page latch even though REDO is single-threaded — ~25-200 ns/record of pure overhead.
    - Fix: REDO holds a page pointer/handle and reuses it across consecutive records touching the same page; no latch in the single-writer recovery phase.
    - Cost avoided: **~190 ns/record × 8.4M ≈ 1.6 s** of pure latching; recovery on a 1 GiB WAL drops from ~60 s to ~10 s. `(bar (c) violation)` — single-writer phases must not pay multi-writer locking costs.
    - Muscle: single-writer phases don't pay locking costs; hold the page handle across records instead of re-fetching+re-latching. Reapplies at: W30 UNDO loop, W64 raft snapshot install, W84 runtime shard-local apply.

  - **(EXPERT, VOPR) When `crash_during_redo_1000_runs_converges` reports ~30 trials with diverged state:**
    - Symptom: a re-crash mid-REDO followed by a resume yields a final page differing from the uninterrupted run.
    - Why: dirty pageLSNs lived only in the bufpool and were never flushed, so the resume read a STALE on-disk pageLSN and re-applied records the first attempt had already applied → divergence.
    - Fix: flush the bufpool periodically during REDO (e.g. every 1000 records / on a size threshold) so a resume picks up at the latest durable pageLSN; bounds re-work without per-record fsync.
    - Cost avoided: **correctness — unbounded, divergent re-work on every recovery re-crash**; and avoids the opposite trap (per-record fsync ≈ 8.4M × 300 µs ≈ 42 min). Caught only by VOPR.
    - Muscle: idempotent replay is only as good as the visibility of its progress to future re-runs; flush periodically to make pageLSN durable and bound re-work. Reapplies at: W30 UNDO CLR durability, W64 raft snapshot fsync cadence, W80 ledger checkpoint cadence.
