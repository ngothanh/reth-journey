**Tuesday — MDBX internals: B+tree page format**

- [ ] **Read + reproduce**: `notes/mdbx_btree.md` — B+tree page layout, with the leaf-split and underflow-merge traces drawn by hand. Direct input to the W28 B-tree core build. (~75 min)
  - 🔧 **Why this matters**: MDBX (and LMDB before it) chose a **B+tree** (data only in leaves, separators in branches) over a classic B-tree (data in internal nodes too). The choice is load-bearing for range scans — Ethereum's hashed-state cursor must walk leaves in lex order. In W28 you will *implement* this page format from this note; if the note is vague, W28's tests trap you. Mirror: `libmdbx` Internals → page format. Consumers: W28 B-tree core (copies layout), W31 storage-trie MPT (table sits on these pages), W95 mini-db (replays the algorithms).
  - *Mental model*: a page is a flat 4 KiB byte slab with offsets growing inward from both ends — a key-offset array growing down from the top, node records growing up from the bottom, free "void" in the middle. Insert = consume void; split when the void can't hold the new record. This double-ended-arena layout recurs in every on-disk format you'll build.
  - *Page layout to reproduce in the note* (sketch both leaf and branch, mark the void):
    ```
    Page (MDBX default 4 KiB; also 8/16 KiB):
      header: { num_keys, lower_bound_off, upper_bound_off, flags: leaf|branch|meta|overflow }
      key_offsets: [u16; num_keys]    // grows DOWN from upper_bound
      node_records: ...               // grows UP from lower_bound
        leaf:   [u16 key_size, key_bytes, u16 value_size, value_bytes]
        branch: [u16 key_size, key_bytes, u32 child_pageno]
      free_void = upper_bound_off - lower_bound_off   // the middle gap
    ```
    **Invariants** (write these verbatim, you re-assert them as W28 tests):
    - Every leaf is reachable from the root via the unique B+tree spine.
    - Branch keys are *separators* — the leftmost key of the right subtree, NOT a stored value's key.
    - Leaf siblings are NOT physically next-linked in MDBX/LMDB — cursor walks via parent backtracking, not next-page pointers.
    - A page is min-half-full unless it is the root.
  - 🎯 **Hardened acceptance** (a passive read CANNOT produce these — you must trace):
    - **Leaf-split trace**: insert a key into a full leaf; the note records *exactly* how many pages are allocated (1 new leaf), which keys move to the new leaf, the separator key promoted, and the parent-branch update. State the page count before/after.
    - **Underflow-merge trace**: delete a key dropping a leaf below half-full; the note records the merge target (left sibling), the separator removed from the parent, and the page freed.
    - **Boundary-separator check**: write the one specific key (the leftmost of the right child after a split) and one sentence on why using a *different* key as the separator routes a boundary lookup to the wrong subtree. This is the W28 trap — name it now.
    - **Fill-factor with variable keys**: state the formula `split when free_void < (key_size + value_size + 2*u16 overhead)` and one number — for 32-byte keys + 32-byte values on a 4 KiB page, roughly how many fit (~60, leaving header/offset overhead). The variable-length nature is why "page can hold N keys" is wrong; capacity is byte-driven.
    - **u16-offset ceiling**: note that offsets are `u16`, so a page > 65535 bytes silently truncates → MDBX clamps page size ≤ 64 KiB. Record it as a config-time invariant for W28.
  - **W28 pitfalls captured** (these become W28's failure cards — write them so future-you recognizes the symptom):
    - *Variable-length keys → wrong capacity assumption*: symptom = occasional page overflow on insert; fix = pre-compute insert byte-size, split if `free_void < required`.
    - *Wrong separator after split*: symptom = boundary-key lookups land in the wrong subtree; fix = separator = leftmost key of right child; test exhaustively on the boundary key.
    - *Page > 64 KiB*: symptom = silent truncation via u16 offset wrap; fix = enforce page ≤ 65535 at config time.
  - **Output**: `notes/mdbx_btree.md` exists with the leaf+branch layout diagram, the 4 invariants, the split trace (page counts named), the merge trace, the boundary-separator sentence, and the 3 W28 pitfalls; the file names W28 explicitly as the consumer.

**Wednesday — MDBX internals: MVCC (copy-on-write)**

- [ ] **Read + reproduce**: `notes/mdbx_mvcc.md` — the COW-B+tree + dual-meta MVCC model, with a write-tx page-allocation trace and a long-reader bloat trace. Input to W27 storage-trie write-tx and W29-30 `recovery`. (~75 min)
  - 🔧 **Why this matters**: MDBX/LMDB's killer property — readers never block writers and vice versa — comes from copy-on-write: a write tx mutates *copies* of pages, then atomically flips the meta page. Old readers keep seeing the old root; new readers see the new. This is "concurrent reads with a single writer," the exact architecture you mirror in W27+ storage-trie and integrate with snapshot recovery in W29-30. Mirror: `libmdbx` Internals → MVCC; LMDB paper §3. Consumers: W27 storage-trie write-tx, W29-30 recovery (bar (c)), W95 mini-db.
  - *Mental model*: "the tree is immutable; a write tx builds a NEW spine of copied pages from the modified leaf up to a new root, then publishes it with a single atomic meta-page write." Publishing a pointer that makes a fully-built structure visible at once is the same Release/Acquire publication you drilled in W5 OnceFlag — recognize it.
  - *bar-(c) implication (for W29-30 `recovery`)*: dual-meta validation on open is a hot recovery path. The reclamation scan (find the oldest pinned reader txnid) must be allocation-free and bounded — note this now so W29's recovery build budgets for it.
  - *Design to reproduce in the note*:
    ```
    Meta pages: TWO at fixed pgno 0 and 1 (~4 KiB each).
      meta[i] = { txnid: u64, root_pgno: u32, free_pages: PageList, last_pgno: u32 }

    Write tx:
      1. Begin: start from the meta with the HIGHER valid txnid.
      2. Mutate: every modified page → a NEW page (from free list, else appended).
      3. Commit: write the OTHER meta page with new root + txnid+1; fsync.
      4. Readers' "current" view flips on their next meta read.

    Read tx:
      1. Read meta with highest txnid; PIN its root_pgno + txnid in the reader table.
      2. All reads chase pointers from that pinned root — that page chain is immutable for the reader's life.
      3. The pinned txnid blocks the writer from reclaiming pages the reader still references.
    ```
    **Invariants** (verbatim → W27 tests):
    - At any instant the on-disk tree rooted at each valid meta is consistent (no torn intermediate).
    - A page allocated by write tx W is NEVER visible until W's commit succeeds.
    - Readers register their txnid in a process-shared reader table; the writer scans it for the oldest pinned txnid.
    - Free pages are reclaimed ONLY when no reader is pinned to a txn that still references them.
  - 🎯 **Hardened acceptance** (must trace, not skim):
    - **3-state diagram**: meta[0]-active, meta[1]-active, commit-in-flight — drawn, with the arrow showing which meta a new reader picks in each state.
    - **Write-tx page-allocation trace**: a write tx that splits one leaf — the note states *exactly* which pages become NEW copies (modified leaf, its new sibling, every branch up to a new root) and which become "old-but-still-referenced." Count them for a 3-level tree (answer: leaf + sibling + 2 branches + new root ≈ 5 new pages for a single split-to-root).
    - **Long-reader bloat trace**: one reader pinned at txnid T while 100 write txns commit — the note explains why the free list cannot reclaim pages referenced by T's snapshot, and what the DB-file growth looks like (monotonic until the reader closes). Name the measurable trigger you'd alarm on: `oldest_reader_txnid` lagging `latest_txnid` by > K.
    - **Abort trace**: a write tx allocates 1000 pages then aborts — the note states all 1000 return to the free list (because they were never published by a meta flip).
  - **Consumer pitfalls captured** (→ W27/W29 cards):
    - *Long-running reader = bloat*: symptom = DB grows unbounded under analytics; fix = bound reader lifetime, surface `oldest-reader txnid` (mdbx_env_info), kill stuck readers.
    - *Meta torn write on power loss*: symptom = DB unopenable; fix = dual meta — on open validate both, pick the higher-txnid VALID one (you build this in W26 wal recovery + W29 ARIES).
    - *Reader-table slot contention*: symptom = read-latency tail spikes under many readers; fix = per-thread slot caching (MDBX does this).
  - **Output**: `notes/mdbx_mvcc.md` exists with the 3-state diagram, the write-tx page-allocation trace (page count named), the long-reader bloat trace (+ alarm trigger), the abort trace, and the bar-(c) implication line for W29; names W27 + W29 as consumers.

**Thursday — MDBX internals: Durability (the `wal` design feeder)**

- [ ] **Read + synthesize**: `notes/mdbx_durability.md` — MDBX's 4 sync modes mapped to next week's `wal` v0.1 design choices, with the "why MDBX needs no WAL / when you DO" analysis. **This is the load-bearing note for the W26 `wal` (bar (c)) build.** (~75 min)
  - 🔧 **Why this matters**: MDBX gets ACID *without* a redo WAL — its COW tree + atomic meta flip is the commit barrier. Understanding *why* that works tells you exactly *when* you DO need a separate WAL (W26): sub-tx durability, group commit, streaming durability, replication. Next week you build `wal` v0.1 (bar (c)); this note is its design spec. Mirror: `libmdbx` Internals → Durability + sync-mode flags; ARIES §3 (contrast); SQLite WAL doc (journal-vs-WAL). Consumers: W26 wal v0.1 (bar (c)), W29 recovery, W80 ledger + W83 aeron archive (group-commit reuse).
  - *Mental model*: durability is a spectrum, not a boolean — every engine picks a point on the fsync/throughput curve. MDBX exposes the whole curve as flags; your `wal` will pick a point and a group-commit window. "Where on the curve" is the design decision; the code is downstream of it.
  - *bar-(c) implication (for W26 `wal`)*: the group-commit path is the hot path — batching N records into one fsync. The batch must be assembled with zero per-record allocation and the fsync amortized; the adaptive batch-window logic must not branch-mispredict on every record. Note the targets now: an fsync is ~ms-class (10⁶ ns), so the whole point of group commit is amortizing that one syscall over thousands of records — a per-record syscall (~300 ns each) or a per-record `malloc` (~50 ns each) inside the batch loop is a bar-(c) violation you must design out before W26.
  - *Synthesis to record* (the taxonomy → your wal):
    ```
    MDBX sync modes (decreasing durability):
      SYNC_DURABLE   : fsync every commit. Never lose a committed tx. Slowest.
      NOMETASYNC     : fsync data pages, not meta. May lose last few commits. Faster.
      SAFE_NOSYNC    : no fsync at commit; periodic flush. Crash → lose recent, NEVER corrupt.
      UTTERLY_NOSYNC : no fsync ever. Crash → may corrupt. Ephemeral caches only.

    Why MDBX needs no WAL:
      - Page writes are COW — old pages stay valid until the meta flip.
      - Meta flip is a single aligned page write (the commit barrier).
      - Crash before meta = old state intact; crash after meta = new state intact; no in-between.

    When you DO need a WAL (W26 use cases):
      - Group commit: batch many small writes into ONE fsync.
      - Streaming durability: orders/telemetry need durability BEFORE the final state is known.
      - Replication/replay: a WAL is the natural log to ship to a follower.
    ```
    **Invariants your W26 `wal` must satisfy** (copy verbatim → W26 tests):
    - Every committed record reaches durable storage before its caller sees the LSN.
    - Replay from any LSN yields a deterministic record sequence.
    - A crash mid-write leaves at most ONE partial record at the tail, detectable by checksum.
  - 🎯 **Hardened acceptance** (synthesis, not skim — each row must map MDBX → your decision):
    - **Sync-mode → wal decision table**: 4 rows (the modes above), columns = {durability guarantee, fsync cost, crash outcome, "my wal equivalent / which W26 mode this maps to"}. Every cell concrete.
    - **"Why no WAL" stated as 3 crash cases**: crash-before-meta, crash-after-meta, crash-mid-meta — outcome for each, and which one the dual-meta design rescues.
    - **"When I need a WAL" → 3 named W26 features**: group commit, streaming durability, replication — each one sentence tying to a wal capability.
    - **The fsync-is-not-durable trap, with a number**: note that `fsync` returning does NOT guarantee platters on consumer SSDs with volatile cache; symptom = replicas diverge after power loss; fix = `fdatasync` + (Linux) FUA writes; document the disk-cache assumption. State the cost: an extra durability barrier vs a silent data-loss window.
    - **Group-commit budget line (bar (c))**: one explicit number — "fsync ≈ 1 ms; to keep p99 < 1 ms under 100 producers, the adaptive batch window must be inflight-driven, not a fixed 16 ms timer." This is the W26 perf constraint, written down before W26.
  - **W26 pitfalls captured** (→ W26 failure cards):
    - *fsync ≠ durable platters*: symptom = replicas diverge after power loss; fix = fdatasync + FUA; document the assumption.
    - *Sub-page write not atomic on torn-write disks*: symptom = half-written pages on power loss; fix = checksum every record AND page; on torn write fall back to previous meta.
    - *Group-commit window mis-tuned*: too-wide (16 ms) destroys p99, too-tight destroys throughput; fix = adaptive window driven by inflight count (like reth's bundler).
  - **Output**: `notes/mdbx_durability.md` exists with the 4-row sync-mode→wal table, the 3 crash cases, the 3 named W26 features, the fsync-not-durable trap (+ cost), the bar-(c) group-commit budget line, and the 3 invariants; names W26 wal as the primary consumer.

**Friday — MDBX cursor semantics**

- [ ] **Read + reproduce**: `notes/mdbx_cursor.md` — cursor operations + range-scan semantics, with one scan trace. Input to W27 storage-trie hashed-state iteration. (~50 min)
  - 🔧 **Why this matters**: reth's hashed-state and history tables are walked by *cursors* — `MDBX_FIRST / NEXT / SET_RANGE / PREV / LAST` and the dup-sort variants. Range scans over hashed keys are the dominant read pattern in state-root computation (>75% of block-sealing time per the reth perf blog). A cursor that re-traverses the tree per step instead of holding a position-stack is O(n log n) instead of O(n). Mirror: `libmdbx` Cursor API + `libmdbx-rs` `Cursor`. Consumers: W27 storage-trie iteration, W31 MPT walk, W95 mini-db.
  - *Mental model*: a cursor is a *stack of (page, index) frames* from root to the current leaf slot. NEXT increments the leaf index; on leaf exhaustion it pops to the parent, advances there, and pushes back down — NOT a fresh root-to-leaf descent. That position-stack is why MDBX scans are amortized-O(1)-per-step despite no leaf sibling links.
  - 🎯 **Hardened acceptance** (must trace, not skim):
    - **Op table**: rows = FIRST, LAST, NEXT, PREV, SET (exact), SET_RANGE (≥ key); cols = what it positions to, return on miss, dup-sort behavior if applicable. Every cell concrete.
    - **Range-scan trace**: a 10-key tree across 2 leaves; trace SET_RANGE to a mid-key, then 4× NEXT — the note shows the position-stack at each step and the ONE point where it pops to the parent and descends into the second leaf. This proves you understand why there are no sibling links yet scans stay cheap.
    - **Lex-order claim**: state that keys come back in unsigned lexicographic byte order (the default comparator), and one sentence on why hashed-state keys (32-byte hashes) rely on exactly that.
    - **Cost line**: NEXT within a leaf = index bump (~few ns, warm L1); NEXT crossing a leaf = a parent pop + child push, possibly a cold-page fault (~thousands of ns) — name this so W27 batches/prefetches across leaf boundaries.
  - **Output**: `notes/mdbx_cursor.md` exists with the op table, the SET_RANGE + 4×NEXT position-stack trace (the leaf-cross point marked), the lex-order claim, and the cost line; names W27 as the consumer.
