**Tuesday — MDBX internals: B-tree**

- [ ] B-tree structure section. Compare with B+tree. (~30 min)
  - **Why**: MDBX (and LMDB before it) chose a *B+tree* (data only in leaves, all leaves linked) rather than a classic B-tree (data in internal nodes too). The decision is load-bearing for range scans — Ethereum's hashed-state cursor needs to walk leaves in lex order without re-traversing the tree. Understanding this trade-off prepares your W28 B-tree core decisions.
  - **Read first**: libmdbx documentation `Internals → B+tree page format`. Also CMU 15-445 lecture 7 (B+tree vs B-tree). LMDB paper (Howard Chu) — appendix on page layout.
  - **Design** (note: this is reading-task; design notes for your future W28 build):
    ```
    Page (4 KiB or 8 KiB or 16 KiB, MDBX defaults 4 KiB):
      header: { num_keys, lower_bound_offset, upper_bound_offset, flags (leaf/branch/meta/overflow) }
      key_offsets: [u16; num_keys]   // grows down from upper_bound
      node_records: ...               // grows up from lower_bound
        leaf:    [u16 key_size, key_bytes, u16 value_size, value_bytes]
        branch:  [u16 key_size, key_bytes, u32 child_pageno]
      free_space in middle (the "void" between offsets and records)
    ```
    **Invariants**:
    - Every leaf is reachable from root via the unique B+tree spine.
    - Branch keys are *separators* — leftmost key of right subtree, NOT a value's key.
    - Leaf siblings are NOT physically linked (MDBX/LMDB design — cursor walks via parent backtracking, not next-page pointers).
    - Page is min-half-full unless it's the root.
  - **Build steps** (reading + diagrams):
    1. (~10 min) Sketch page layout on paper for both leaf and branch. Mark the "void".
    2. (~10 min) Walk through an insert that triggers a leaf split — note pages allocated, parent updated.
    3. (~10 min) Walk through a delete that triggers an underflow merge.
  - **Pitfalls** (for W28 implementation):
    - *Variable-length keys*: page can hold variable number of keys; "fill factor" depends on key+value sizes. **Symptom**: occasional page overflow on insert. **Fix**: pre-compute insert size, split if `free_space < required`.
    - *Branch key separators*: easy to use the wrong key as separator after split. **Symptom**: lookups for boundary keys go to wrong subtree. **Fix**: separator is the leftmost key of the right child after split; test exhaustively on boundary.
    - *Pages larger than 64 KiB*: page format uses u16 offsets — clamp to ≤65535. **Symptom**: silent truncation on 128 KiB pages. **Fix**: enforce at config-time; MDBX defaults safe.
  - **Test scenarios** (for W28 build): insert 10k random keys, split/merge invariants hold; cursor scan returns keys in lex order; tree height ≤ log_2k(n) for branching factor 2k.
  - **Acceptance**: 1-page note `notes/mdbx_btree.md` with page-layout diagram + invariants + 3 cited operations (insert, split, scan).
  - **Downstream**: W28 B-tree core build copies this layout; W31 storage-trie MPT uses an MDBX table with these pages underneath; W95 mini-db CAPSTONE replays the algorithms.

**Wednesday — MDBX internals: MVCC**

- [ ] MVCC section. Read tx during write tx. (~45 min)
  - **Why**: MDBX/LMDB's killer feature: readers never block writers and vice versa. Achieved via "copy-on-write B+tree" — a write tx mutates COPIES of pages, then atomically swaps the meta-page. Old readers see the old root; new readers see the new. This is the foundation of "concurrent reads with single writer" used by reth-db, and the architecture you mirror in W27+ storage-trie.
  - **Read first**: libmdbx Internals → MVCC. Also LMDB paper §3 (the COW mechanism). Compare with MVCC papers on Postgres (per-row versioning — different approach).
  - **Design** (notes):
    ```
    Meta pages: TWO at fixed offsets 0 and 1 (page numbers, ~4 KiB each).
      meta[i] = { txnid: u64, root_pageno: u32, free_pages: PageList, last_pgno: u32 }
    
    Write tx:
      1. Begin: pick the meta with HIGHER txnid as starting root.
      2. Mutate: every modified page becomes a NEW page (allocated from free list or appended).
      3. Commit: write the OTHER meta page with updated root and txnid + 1; fsync.
      4. Atomically the readers' "current" view flips on next read of meta.
    
    Read tx:
      1. Read meta with highest txnid; pin its root_pageno.
      2. All reads chase pointers from that root — page chain is immutable for our duration.
      3. Reader's pinned txnid prevents the writer from reclaiming pages reader still references.
    ```
    **Invariants**:
    - At any moment, the on-disk tree rooted at meta[i] is *consistent* (no torn writes).
    - A page allocated by write tx W is *never* visible until W's commit succeeds.
    - Reader transactions track their txnid in a process-shared "reader table"; writer scans this to find oldest pinned txnid.
    - Free pages are reclaimed ONLY when no reader is pinned to a txn that references them.
  - **Build steps** (reading + diagram):
    1. (~15 min) Draw a 3-state diagram: meta[0] active, meta[1] active, commit-in-flight.
    2. (~15 min) Trace a write tx that splits a leaf — how many new pages? Which become "old"?
    3. (~15 min) Trace a long-running reader holding a snapshot while 100 writes complete — free-list growth.
  - **Pitfalls**:
    - *Long-running reader = bloat*: every reader pinned to old txnid prevents reclamation. **Symptom**: DB grows unbounded under analytics workload. **Fix**: bound reader lifetime; expose `mdbx_env_info` to surface oldest-reader txnid; kill stuck readers.
    - *Meta page torn write*: power failure mid-meta-write must NOT corrupt. **Symptom**: DB unopenable. **Fix**: dual meta pages; on open, validate both, pick the higher-txnid valid one. (You build this in W26 wal recovery and W29 ARIES.)
    - *Reader table contention*: process-shared mmap of reader slots. Many concurrent readers contend on slot acquisition. **Symptom**: read latency tail spikes. **Fix**: per-thread slot caching (MDBX does this).
  - **Test scenarios** (for W27+ integration):
    - Spawn 100 readers each holding a snapshot, write 10k records during their lifetimes — snapshots remain consistent.
    - Kill a reader process mid-tx — reader-table slot reclaimed within bounded time.
    - Write tx that allocates 1000 pages then aborts — all 1000 pages return to free list.
  - **Acceptance**: 1-page note `notes/mdbx_mvcc.md` with the 3-state diagram and the 5-pitfall list.
  - **Downstream**: W27 storage-trie write-tx design mirrors this; W29 recovery ARIES integrates with MVCC for snapshot recovery; W95 mini-db CAPSTONE re-derives this design.

**Thursday — MDBX internals: Durability**

- [ ] WAL / sync modes. Crash recovery. **Critical reading** — informs the W26 `wal` crate design. (~30 min)
  - **Why**: MDBX surprisingly does NOT use a WAL by default — its COW-tree + meta-page-flip gives ACID without redo logs. But it offers WAL-LIKE sync modes for durability/throughput trade-offs. Understanding why MDBX gets away without a WAL clarifies *when* you need one (W26): MDBX's atomic unit is a tx (a single meta-flip); for sub-tx durability (per-record), you need a separate WAL.
  - **Read first**: libmdbx Internals → Durability + the `MDBX_SAFE_NOSYNC`, `MDBX_NOMETASYNC`, `MDBX_UTTERLY_NOSYNC` flag docs. ARIES paper §3 for contrast. SQLite WAL doc for journal vs WAL contrast.
  - **Design notes** (synthesis for W26):
    ```
    MDBX modes (decreasing durability):
      SYNC_DURABLE   : fsync at every commit. tx never lost. ~slow.
      NOMETASYNC     : fsync data pages, but not meta. May lose last few commits. Faster meta flips.
      SAFE_NOSYNC    : no fsync at commit; periodic flush. Crash → lose recent commits, NEVER corrupt.
      UTTERLY_NOSYNC : no fsync ever. Crash → may corrupt. For ephemeral caches.
    
    Why MDBX doesn't need a WAL:
      - Page writes are COW — old pages remain valid until meta flip.
      - Meta flip is atomic (single page write, aligned to disk-sector boundary).
      - Commit = "all data pages reach disk, THEN meta page reaches disk."
      - Crash before meta = old state intact. Crash after meta = new state intact.
      - There's no "in-between" state because meta page is the commit barrier.
    
    When you DO need a WAL (your W26 use cases):
      - Group commit: many small writes batched into one fsync (MDBX commits the whole tx).
      - Streaming durability: telemetry/logs/orders need durability BEFORE knowing the final state.
      - Replication/replay: a WAL is the natural log to ship to a follower.
    ```
    **Invariants** (your W26 wal must satisfy):
    - Every committed record has reached durable storage before its caller sees the LSN.
    - Replay from any LSN yields a deterministic sequence of records.
    - Crash mid-write leaves at most ONE partial record at the tail, detectable by checksum.
  - **Pitfalls** (lessons that inform W26 design):
    - *fsync = durable disk?*: false on most consumer SSDs (volatile cache). **Symptom**: replicas diverge after power loss. **Fix**: `fsync` + `fdatasync` + (on Linux) `FUA` writes; document the disk-cache assumption.
    - *Sub-page atomicity*: assuming 4 KiB writes are atomic is false on torn-write disks. **Symptom**: half-written pages on power loss. **Fix**: checksum every record AND every page; on torn-write, fall back to previous meta.
    - *Group commit latency vs throughput*: too-aggressive group commit (16 ms window) destroys p99. Too-tight (no batching) destroys throughput. **Symptom**: throughput plateau at IOPS limit. **Fix**: adaptive batch window driven by inflight count, like reth's bundler.
  - **Test scenarios** (for W26):
    - Crash injection at random byte during fsync — replay finds correct truncation point via checksum.
    - 100 concurrent producers + group commit: throughput scales sublinearly, latency stays under 1 ms p99.
    - Tail-truncation detection: corrupt last 50 bytes of segment, replay stops cleanly.
  - **Acceptance**: 1-page note `notes/mdbx_durability.md` mapping MDBX's 4 sync modes to your W26 design choices.
  - **Downstream**: W26 wal v0.1 design copies this taxonomy; W29 recovery ARIES integrates; W80 ledger durability and W83 aeron archive reuse the group-commit pattern.
