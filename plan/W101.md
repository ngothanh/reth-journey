**Tuesday — vector-db: vector type + distance kernels**

- [ ] **Build**: `crates/vector-db/src/lib.rs` (Vector type) + `crates/vector-db/src/distance.rs` — `Vector<const D: usize>(Box<[f32; D]>)` and a `Distance` marker trait with `L2`, `Dot`, `Cosine`, including a SIMD-accelerated L2 kernel. (~total 110 min across 3 phases)
  - 🔧 **Why this matters**: mirrors `qdrant spaces::metric` and `DenseVector`. The distance fn is the inner loop of BOTH insert and search — it runs `O(ef × M)` times per operation, so a scalar loop vs an AVX2 kernel is the difference between a 30 s and a 4 min build. Two traps live here: (1) the **distance fn must be carried as a type parameter** so a graph built with L2 can never be searched with Cosine (the Friday search test composes against this); (2) cosine without normalization silently returns wrong neighbors. Downstream consumers: W101 Wed/Thu/Fri (every algorithm calls this), W102 quantize (replaces f32 kernel with int8/PQ kernel), W104 segment merge (re-distances during graph rebuild). First-attempt impls fail ≥1 test below — the debug session is the lesson.

  #### Phase 1 — Problem, prediction, design (~30 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `notes/101tue_distance_prediction.md`:
    - P1: the type you'd reach for to hold the vector (exact line — `Box<[f32; D]>` vs `Vec<f32>` vs `[f32; D]`) and why D as a const generic.
    - P2: predicted scalar-L2 latency for D=128 (ns) and predicted AVX2 speedup ratio.
    - P3: predicted result of building a graph with L2 and searching it with Cosine in your first design (compile error / wrong neighbors / panic).
    - P4: will `cosine(a, b)` be correct if you forget to normalize? Predict the failure mode.
    - P5: list every Phase-2 test you predict your first attempt will fail.
  - *Mental model*: a distance kernel + a type-level proof that construction and query use the SAME metric.
  - *Contract*: `pub struct Vector<const D: usize>(Box<[f32; D]>);` and `pub trait Distance { fn dist(a: &[f32], b: &[f32]) -> f32; }` with zero-sized marker types `L2`, `Dot`, `Cosine`. The graph will be `HnswGraph<const D: usize, M: Distance>`. NEVER write the kernel body in the design doc.
  - *Back-of-envelope* (bar (b), but the inner loop matters): D=128 L2 = 128 subs + 128 muls + 127 adds ≈ 383 flops. Scalar ~128 cycles (≈ 40 ns at 3.2 GHz, one mul-add per cycle if FMA, plus a serial dependency chain on the accumulator). AVX2 = 8 lanes → ~16 FMAs + a horizontal reduce ≈ 20-30 cycles (≈ 8 ns). Build calls dist `~ef_c × M × log(N)` ≈ 200 × 16 × 20 ≈ 64k times per insert × 100k inserts = 6.4e9 dist calls. At 40 ns scalar = 256 s; at 8 ns SIMD = 51 s. The SIMD kernel is what keeps the Thursday "build 100k in ≤ 30 s" test reachable. **Cliff: scalar 40 ns vs AVX2 8 ns = 5× on the single hottest path.**
  - **Requirements** R1..R6 — write in `notes/101tue_distance_design.md`:
    - R1: `Vector<D>` heap-allocates exactly `D × 4` bytes for the data (no per-vector Vec header tax).
    - R2: `Distance` is a marker trait; the metric is a *type parameter*, not a runtime enum — a graph's metric is fixed at construction in the type.
    - R3: L2 returns squared distance (skip the `sqrt` — monotone, and sqrt costs ~15-20 cycles per call on the hot path; recall is identical under squared L2).
    - R4: Cosine requires inputs pre-normalized to unit length; provide `Vector::normalized()` and assert unit-length in debug.
    - R5: the AVX2 L2 kernel returns bit-identical (within 1e-4) results to the scalar reference for all D divisible by 8, and falls back to scalar for the tail.
    - R6: SIMD code is `#[cfg(target_feature = "avx2")]`-gated with a runtime `is_x86_feature_detected!` dispatch (no SIGILL on non-AVX2 hosts).
  - **Design walk-through** D1..D4 — answer in the design doc; no peeking at upstream until Phase 3:
    - D1: property table for the vector storage choice (`[f32; D]` inline / `Box<[f32; D]>` / `Vec<f32>`): stack size? heap allocs per vector? Vec header tax (24 B)? cache behavior when stored in a `Vec<Vector<D>>`?
    - D2: type-parameter-metric vs runtime-enum-metric — why the type param prevents the Friday "built-with-L2, queried-with-Cosine" bug *at compile time* instead of via a runtime assert.
    - D3. **Pre-mortem (load-bearing):** write the exact failure trace for the un-normalized cosine bug — `cosine(a,b)` computed as `dot(a,b)` without dividing by `|a||b|`; the 4-line trace showing how a long vector dominates the ranking and the wrong nearest neighbor wins.
    - D4. **Anti-shortcut audit:** the obvious reach is `Vec<f32>` (variable D, no const generic) — one line on why it's wrong HERE (loses compile-time D-match between query and index; reintroduces the header tax × 1M vectors = 24 MB pure overhead). And `f32::sqrt` in L2 — wrong here because squared L2 is rank-equivalent and saves ~20 cyc/call.
  - **Output**: `notes/101tue_distance_design.md` with R1..R6, D1..D4, and the un-normalized-cosine bad trace.

  #### Phase 3 — Make the tests pass, one failure at a time (~40 min)
  Ordered failure cards, newbie first.

  - **(NEWBIE) When `test_cosine_requires_normalization` returns 300 instead of 0:**
    - Symptom: assertion fails, `d = 300`.
    - Why: cosine was implemented as the raw dot product; magnitude was never divided out.
    - Fix: `1.0 - dot(a,b) / (norm(a) * norm(b))`, OR require callers to pass unit vectors and store `Vector::normalized()` at insert (the production choice — normalize once at insert, not every distance call).
    - Muscle: cosine is dot-on-the-unit-sphere; if you skip normalization the longest vector always wins. Reapplies at: W102 quantized cosine (normalize before quantizing), W104 segment merge (re-normalize on re-insert).

  - **(SENIOR) When `test_avx2_l2_matches_scalar` fails for D=130:**
    - Symptom: SIMD result off by the last 2 components' contribution; D divisible by 8 passes, D=130 fails.
    - Why: the AVX2 loop processed `D/8` chunks of 8 and dropped the `D % 8` tail.
    - Fix: after the vectorized chunks, run a scalar remainder loop over `chunks*8..D`; or pad D to a multiple of 8 at the type level.
    - Cost avoided: silently-wrong distances (recall collapse) that pass every D=128 test and only bite on an odd dimension — a green test, wrong index.
    - Muscle: every SIMD kernel needs an explicit scalar tail or a layout that forbids tails. Reapplies at: W102 SIMD quantization kernel, W104 batched re-distance.

  - **(SENIOR) When `metric_mismatch` compiles instead of failing (trybuild green where it should be red):**
    - Symptom: `cargo test --test ui` reports the should-fail case compiled.
    - Why: the metric was modeled as a runtime field (`enum Metric`) instead of a type parameter, so the compiler can't reject the mismatch.
    - Fix: make the metric a generic parameter `HnswGraph<const D: usize, M: Distance>`; `search` is monomorphized over the SAME `M`. Now the mismatch is `E0277` at compile time.
    - Muscle: push invariants the compiler CAN enforce into the type system; a runtime assert is a strictly weaker guard. Reapplies at: W103 typed serialization (metric tag in the header must match the type param), W104 merge (only same-metric segments mergeable).

  - **(SENIOR) When `bench_l2_in_plausible_band` reports 0.1 ns:**
    - Symptom: bench median below 1 ns — implausible for 128 flops.
    - Why: the optimizer DCE'd the call because the result was unused and inputs were const-foldable.
    - Fix: `black_box(&a)`, `black_box(&b)`, and `black_box(result)`. Re-bench; expect scalar ~40 ns, AVX2 ~8 ns.
    - Muscle: a bench that doesn't `black_box` measures nothing; assert a plausible floor so it fails loud. Reapplies at: W102 quantize bench, W103 serialize bench, every criterion harness in this crate.

  #### 5-year failure mode
  Write in `notes/101tue_distance_followup.md` after green: when embeddings move to bf16/int8 by default (storage halved), the f32 kernel is no longer the hot path. TRIGGER: vector store > 50 GB / node forces sub-f32 storage. **Wednesday — vector-db: HNSW graph layer**

- [ ] **Build**: `crates/vector-db/src/hnsw/graph.rs` — `HnswGraph<const D: usize, M: Distance> { layers, vectors, ep, m, ef_construction, ml, next_id }`. Multi-layer NSW data structure per Malkov & Yashunin 2018. (~total 110 min across 3 phases)
  - 🔧 **Why this matters**: mirrors `qdrant graph_layers.rs`. HNSW is the single most interview-load-bearing module of vector-db — every vector-db hire conversation includes "explain HNSW." Build the data structure right and search/insert fall out cleanly. The traps here are (1) the **adjacency-storage choice** (HashMap blows the memory budget 2×), (2) the **layer-assignment distribution** (a one-character bug degenerates the graph to flat O(N) NSW and *every functional test still passes* — only the histogram catches it), and (3) the **id allocator reached through `&self`** — a non-atomic `UnsafeCell<usize>` read-modify-write duplicates ids the moment two builders share it (loom-proven, and UB), where `AtomicU32::fetch_add` does not. Downstream consumers: W101 Thu insert (Alg 1), W101 Fri search (Alg 5), W102 quantize (swaps `Vec<Vector<D>>` → `Vec<QuantizedVector>`), W103 persist (serializes adjacency), W104 segment manager. First-attempt impls fail ≥1 test below.

  #### Phase 1 — Problem, prediction, design (~30 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `notes/101wed_graph_prediction.md`:
    - P1: the type you'd reach for to store layer-0 adjacency (exact line — `HashMap<NodeId, Vec<NodeId>>` vs `Vec<Box<[NodeId]>>`) and predicted bytes/node.
    - P2: predicted total RAM for 1M × 128-d nodes including adjacency (MB).
    - P3: predicted outcome of 16 threads concurrently calling `alloc_id()` (the shared `&self` id source) backed by an `UnsafeCell<usize>` RMW — exact distinct-id count vs the 1.6M expected, and which interleaving loses ids.
    - P4: predict the layer histogram if you compute `ml = M` instead of `ml = 1/ln(M)` (fraction of nodes at layer 0).
    - P5: list every Phase-2 test you predict your first attempt will fail.
  - *Mental model*: a `Vec` of layers; each layer is an adjacency list; a node lives at layer 0 and every layer below its assigned level; the entry point sits at the top.
  - *Contract*:
    ```rust
    pub struct HnswGraph<const D: usize, M: Distance> {
        layers: Vec<Layer>,            // layers[0] = densest, full graph
        vectors: Vec<Vector<D>>,       // external — quantize swaps this in W102
        ep: AtomicU32,                 // entry-point NodeId (or sentinel)
        ep_level: AtomicU32,
        next_id: AtomicU32,
        m: usize, ef_construction: usize, ml: f64,
        _metric: PhantomData<M>,
    }
    pub fn new(cfg: HnswConfig) -> Self;
    pub fn assign_level(&self, rng: &mut impl Rng) -> u32;
    pub fn alloc_id(&self) -> NodeId;     // &self — the id allocator is shared & interior-mutable (AtomicU32::fetch_add)
    pub fn add_node(&mut self, v: Vector<D>) -> NodeId;   // wiring is Thu's insert; calls alloc_id internally
    pub fn neighbors(&self, layer: usize, n: NodeId) -> &[NodeId];
    pub fn entry_point(&self) -> Option<NodeId>;
    ```
    NEVER write the body of `assign_level`, `alloc_id`, or the adjacency mutation in the design doc.
    **Note on `alloc_id(&self)`:** id allocation is deliberately a `&self` interior-mutable step, NOT folded into `&mut self add_node`'s exclusive borrow. Reason: even in v0.5 (single-threaded builder) the id source is the one piece a future concurrent builder (W104) shares first, and modelling it as a shared `&self` `AtomicU32` now means the W104 fine-grained path needs zero re-typing. It also makes the concurrent-id trap below reachable: a naive `UnsafeCell<usize>` allocator handed out through `&self` (the first thing that compiles once a plain `usize` is rejected) races and duplicates ids, where `AtomicU32::fetch_add` does not.
  - *Back-of-envelope* (bar (b) memory budget): 1M × 128-d × 4 B = 512 MB raw vectors (the floor — unavoidable at f32). Adjacency: avg layers/node ≈ 1/(1-1/M) ≈ 1.07, but layer 0 holds 2M neighbors and uppers ~M. With a **flat `Vec<Box<[NodeId]>>`**: layer 0 = 1M × (2M=32 ids × 4 B + 16 B box/slice overhead) ≈ 1M × 144 B ≈ 144 MB; uppers negligible → **~660 MB total**. With **`HashMap<NodeId, Vec<NodeId>>`**: + ~48 B/entry (bucket + control byte amortized + Vec's 24 B header) × ~1.07M entries × layers ≈ +480 MB → **~1.2 GB**. **The container choice is a 1.8× memory cliff** and the R5 600 MB test is what enforces it.
  - **Requirements** R1..R8 — write in `notes/101wed_graph_design.md`:
    - R1: every node appears at layer 0 and ALL layers below its assigned level (downward-closed).
    - R2: `ep` is at the highest layer that contains ≥1 node.
    - R3: neighbor count ≤ M per layer (or `M_max0 = 2M` at layer 0).
    - R4: layer assignment via `floor(-ln(uniform(0,1]) × ml)` with `ml = 1/ln(M)`.
    - R5: `HnswGraph<128>` storing 1M nodes uses ≤ 600 MB for vectors + adjacency *adjacency overhead only ≤ 90 MB on top of the 512 MB vector floor*.
    - R6: `assign_level` distribution matches the paper geometric within ε over 1M samples.
    - R7: accessors are sound under concurrent reads (proptest, no UB).
    - R8: M=16, ef_c=200 defaults give recall ≥ 0.95 (verified Thu/Fri).
  - **Design walk-through** D1..D5 — answer in the design doc; no peeking at upstream until Phase 3:
    - D1: property table for adjacency storage (`HashMap<NodeId,Vec>` / `Vec<Vec>` / `Vec<Box<[NodeId]>>` / flat CSR): bytes/node? cache locality on neighbor scan? grow cost? Why is the flat boxed-slice the right v0.5 pick and CSR the W104 upgrade.
    - D2: why store vectors externally (separate `Vec`) instead of inline in adjacency? (Allows the W102 quantization swap without touching graph code.)
    - D3: why `u32 NodeId`? (32-bit caps a segment at 4 B nodes — sufficient for v0.5 single-node, aligns with W104 segment manager; halves adjacency RAM vs `u64`.)
    - D4: the layer-assignment formula. Why `-ln`? (inverse CDF of the geometric / exponential — produces the geometric tail). Why `1/ln(M)`? (normalizes so expected #layers = log_M(N)).
    - D5. **Pre-mortem (load-bearing):** write the exact 4-line trace where `ml = M` (forgetting the reciprocal-log): `assign_level` returns 0 for ~all nodes → only layer 0 exists → graph is flat NSW → search is O(N) → the 1 ms P99 test (Friday) reports 40 ms. Note that *no functional test catches this* — recall might even be 1.0 on a tiny graph — only the 1M-sample histogram does.
    - D6. **Anti-shortcut audit:** `HashMap` adjacency (the obvious reach) — wrong here: +480 MB and pointer-chasing on the hottest scan. `Vec<RwLock<Layer>>` per layer (the obvious concurrency reach) — wrong for v0.5: insert is single-threaded-builder, so a per-layer lock buys nothing and costs 25 ns/acquire on every neighbor read; defer locking to W104. `UnsafeCell<usize>`/`usize` id counter exposed through `&self alloc_id` (the obvious "it's just a counter, make it compile through &self" reach) — wrong: a non-atomic RMW reached through shared `&self` duplicates ids (and is UB) the instant a second builder appears (W104); use `AtomicU32::fetch_add(Relaxed)`. (Modelling the id source as `&self`-shared now, not `&mut self`-exclusive, is deliberate — it surfaces the race at v0.5 so the W104 concurrent builder inherits a sound primitive.)
  - **Output**: `notes/101wed_graph_design.md` with R1..R8, D1..D6, the `ml = M` degeneration trace.

    ```rust
        let seen = Arc::new(Mutex::new(std::collections::HashSet::new()));
        let mut hs = vec![];
        for _ in 0..16 {
            let (g, seen) = (g.clone(), seen.clone());
            hs.push(std::thread::spawn(move || {
                let mut local = Vec::with_capacity(100_000);
                for _ in 0..100_000 { local.push(g.alloc_id()); }   // &self — contended, NOT serialized
                let mut s = seen.lock().unwrap();
                for id in local { s.insert(id); }                   // dedup happens OUTSIDE the alloc path
            }));
        }
        for h in hs { h.join().unwrap(); }
        // 16 * 100k = 1.6M ids handed out; a correct allocator hands out 1.6M DISTINCT ids.
        assert_eq!(seen.lock().unwrap().len(), 1_600_000,
            "duplicate ids handed out — alloc_id used a non-atomic `UnsafeCell<usize>` RMW reached via &self, \
             not AtomicU32::fetch_add; two threads read the same value and both returned it");
    }
    ```
    The dedup `Mutex` guards only the *result set*, never the allocator: every `alloc_id()` call hits the shared `&self` counter with no serializing lock around the read-modify-write. A plain `usize` won't even compile through `&self` (the compiler's first nudge); the learner reaches for `UnsafeCell<usize>` (or a raw `*mut usize`) to make it compile — and now it races, losing/duplicating ids so the distinct-count comes back < 1.6M. `AtomicU32::fetch_add(1, Relaxed)` is the load-bearing primitive that makes the count exactly 1.6M (and is the *correct* form of interior mutability the `UnsafeCell` was groping for). This is the cross-primitive composition of the W004 atomic-counter lesson with the graph's id source.

  - **(NEWBIE) When `test_search_returns_min_k_available` panics with heap underflow:**
    - Symptom: 5-node graph, `k=10`; `results.peek().unwrap()` returns `None` → panic.
    - Why: the code assumes `ef ≥ k` and the graph has ≥ k nodes.
    - Fix: `let ef = ef.max(k);` at entry; on return take `results.into_sorted_vec().into_iter().take(k)` and never `unwrap` a possibly-empty heap.
    - Muscle: never assume the result set reaches k — return `min(k, available)`. Reapplies at: W102 filtered search (predicate may leave < k), W104 federated merge (a segment may have < k).

  - **(SENIOR) When `test_ef_sweep_monotone_recall` is non-monotone:**
    - Symptom: recall at ef=200 < recall at ef=100.
    - Why: the stop condition is wrong — search terminates when the candidate heap empties instead of when the closest candidate is farther than the worst result; larger ef explores a different (sometimes worse) frontier.
    - Fix: stop when `candidates.peek().dist > results.peek_max().dist` (the closest remaining candidate can't improve results), not when candidates empty.
    - Muscle: best-first search stops on the bound, not on exhaustion. Reapplies at: W104 federated top-k (merge stops on bound), any branch-and-bound.

  - **(SENIOR-perf) When `bench_search_p99_under_1ms_ef64_1m` reports P99 = 8 ms:**
    - Symptom: P99 ~8× over budget; median may look OK, tail is malloc/rehash.
    - Why: (a) `HashSet::new()` allocated per search and rehashed 16→32→…→4096; (b) the neighbor read held a lock per neighbor / re-fetched the slice repeatedly; (c) scalar distance.
    - Fix: (a) reuse a thread-local `Visited` pre-sized to `ef × M × 4` and `clear()` it per search; (b) snapshot the neighbor slice once per node; (c) route distance through Tuesday's SIMD `M::dist`. Re-bench; expect P99 ~800 µs.
    - Cost avoided: ~10 mallocs + ~10 rehashes per search ≈ 7 ms of tail latency on a 1M index at load — the entire P99 budget. (bar (b) perf-regression CI catches this.)
    - Muscle: zero allocation on the hot path; pre-size and reuse scratch state. Reapplies at: W004 backoff scratch, W102 quantize scratch, W104 merge scratch buffers, every per-query hot path.

  - **(SENIOR) When `test_concurrent_search_no_data_race` fails to compile or races:**
    - Symptom: `HnswGraph` isn't `Sync`, or 32-thread search produces non-deterministic results.
    - Why: search took `&mut self` (because the visited set lived in `self`), or interior mutability without proper sharing.
    - Fix: `search(&self, ...)`; the visited scratch is thread-local or stack-local, never `&mut self`. A read-only `&self` search is trivially `Sync`.
    - Muscle: read paths take `&self`; per-call scratch never lives in shared state. Reapplies at: W102 filtered search (also `&self`), W104 federated search (parallel across segments needs `&self`).
