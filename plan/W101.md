**Wednesday — vector-db: HNSW graph layer**

- [ ] **Build**: `crates/vector-db/src/hnsw/graph.rs` — `HnswGraph { layers: Vec<RwLock<Layer>>, vectors, ep, m, ef_construction, ml, ... }`. Multi-layer NSW data structure per Malkov & Yashunin 2018. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: **HNSW is the single most-interview-load-bearing module of vector-db.** Every vector-db hire conversation includes "explain HNSW." Build the data structure right and search/insert fall out cleanly. Downstream consumers: W101 Thu insert (Algorithm 1), W101 Fri search (Algorithm 5), W102 quantize (swaps Vec<Vector<D>> for Vec<QuantizedVector>), W103 persist (serializes adjacency), W104 segment manager.

  #### Phase 1 — Problem, requirements, design (~25 min)

  - **Requirements** (write in `crates/vector-db/notes/101wed_hnsw_graph_design.md`): (R1) Every node appears at layer 0 and ALL layers below its assigned level; (R2) entry-point ep is at highest layer that contains ≥1 node; (R3) neighbor count ≤ M per layer (or M_max0 = 2M at layer 0); (R4) layer assignment via geometric distribution `floor(-ln(uniform(0,1)) * ml)` with `ml = 1/ln(M)`; (R5) HnswGraph<128> stores 1M nodes in ≤ 600 MB RAM; (R6) assign_level distribution matches paper within ε (1M samples histogram); (R7) accessors thread-safe (no UB under proptest); (R8) M=16, ef_c=200 defaults give recall ≥ 0.95.

  - **Design questions**: (D1) Why per-layer RwLock<Layer>? (W101 Thu insert writes one layer at a time; W101 Fri search reads.) (D2) Why store vectors externally (separate Vec) instead of in adjacency? (Allows W102 quantization swap.) (D3) Why u32 NodeId? (32-bit ID limits per-segment capacity to 4B — sufficient for v0.5, aligned with W104 segment manager.) (D4) Layer assignment formula: `floor(-ln(uniform(0,1)) * (1/ln(M)))`. Why -ln? (Inverse CDF of geometric distribution.) Why 1/ln(M)? (Normalizes so expected layer count = log_M(N).) (D5) **Pre-mortem**: rng seed bad → all nodes assigned layer 0; graph degenerates to flat NSW; search becomes O(N). What test catches? (1M samples, histogram check.)

  #### Phase 2 — Failing tests

  - [ ] `test_assign_level_distribution_geometric` — 1M samples; histogram of layer assignments matches geometric (1-1/M) within 5%.
  - [ ] `test_hnsw_graph_memory_under_600mb_1m_nodes` — 1M 128-d nodes; total memory ≤ 600 MB.
  - [ ] `test_concurrent_add_node_no_panic` — 16 threads add 100k vectors; node_count exact.
  - [ ] `test_empty_graph_entry_point_none` — newly-constructed graph: entry_point() = None.
  - [ ] `test_layer_assignment_reproducible_with_seed` — same seed produces same assignment sequence.
  - [ ] `test_ml_value_correct` — assert `ml == 1.0 / (16f64).ln()` exactly.

  #### Phase 3 — Failure cards

  - **When `test_assign_level_distribution_geometric` shows 90% nodes at layer 0 only**: Symptom: layer 0 has 99% nodes; layer 1+ has 1%. Expected geometric tail is ~6% at layer 1, ~0.4% at layer 2. Why: forgot the `-ln` step OR ml computed as `M` instead of `1/ln(M)`. Fix: `let u: f64 = rng.gen_range(0.0..=1.0); (-u.ln() * self.ml).floor() as LayerId` with `ml = 1.0 / (M as f64).ln()`. Muscle: HNSW's correctness rests on this distribution; the test is the only thing guarding against silent degeneration to flat NSW. Reapplies at: any probabilistic data structure (skiplist W37, bloom W34).

  - **When `test_hnsw_graph_memory_under_600mb_1m_nodes` reports 1.2 GB**: Symptom: 1M × 128-d × 4B = 512 MB raw vectors + adjacency overhead = expected ~600 MB; actual 1.2 GB. Why: HashMap<NodeId, Vec<NodeId>> has ~80B/entry overhead (bucket + bucket pointer + Vec header) × 1M × ~6 layers avg = ~480 MB extra. Fix: use `Vec<Option<Box<[NodeId]>>>` indexed by NodeId at layer 0; HashMap only at sparse upper layers. Or `hashbrown::HashMap` (smaller bucket overhead than std).

  - **When `test_concurrent_add_node_no_panic` shows lost increments**: Symptom: 16 threads × 100k adds → node_count = 1.5M instead of 1.6M. Why: `next_id: usize` updated non-atomically; relaxed ordering. Fix: `next_id: AtomicUsize` with `fetch_add(1, Ordering::Relaxed)` (Relaxed sufficient since only contributors of new IDs care). Muscle: atomic counters are the trivial fix for distributed-counter scenarios; relaxed ordering OK when no happens-before needed. Reapplies at: every multi-thread counter.

  - **5-year failure mode**: when nodes exceed 4B per segment (u32 limit), need u64 NodeId migration. Trigger: per-segment count > 2B sustained.

  - **Reference material**: Malkov & Yashunin 2018 (the canonical paper, Algorithms 1-5); hnswlib `hnswalg.h` (reference impl by paper authors); Qdrant `lib/segment/src/index/hnsw_index/graph_layers.rs`; faiss `IndexHNSW.cpp` for M/efConstruction/ef tunables; Pugh 1990 SkipList for layer-level probability distribution.

**Thursday — vector-db: HNSW insert**

- [ ] **Build**: `crates/vector-db/src/hnsw/insert.rs` — multi-layer insert per paper Algorithm 1. M=16, efConstruction=200 defaults. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: insert is the construction pipeline. It calls search (Alg 2) at each layer to find ef closest existing nodes, then connects via M neighbors with heuristic pruning (Alg 4). Inverted-from-search reuse of Alg 2 here is critical — same code, different parameters. Downstream consumers: W101 Fri search (uses search_layer), W103 persistence serializes adjacency built here, W104 segment manager merges multiple HnswGraphs by re-inserting nodes.

  #### Phase 1 — Requirements + design (~25 min)

  - **Requirements** (write in `notes/101thu_insert_design.md`): (R1) insert always succeeds (no rejection); (R2) ep updated atomically only after all layers wired; (R3) neighbor lists capped at M (or M_max0=2M for layer 0); (R4) insert is NOT concurrent-safe in v0.5 (single-threaded construction or lock-the-graph builder pattern); (R5) build 100k 128-d vectors in ≤ 30 s single-thread; (R6) recall@10 ≥ 0.95 after build; (R7) ALWAYS call select_neighbors_heuristic (Alg 4) when neighbor list exceeds M; (R8) BFS from ep reaches ≥ 99% of nodes (graph connectivity invariant).

  - **Design questions**: (D1) Greedy descent vs ef-bounded search: top layers use ef=1 (greedy), target_level downward uses ef_construction. Why? (Upper layers are sparse; ef=1 enough to find a good ep for next layer. Lower layers are dense; need ef_construction width.) (D2) Algorithm 4 heuristic (diversity-preserving) vs Algorithm 3 (raw closest): Alg 4 picks neighbors that don't make new candidate's vector closer to existing neighbor than to the new node. Why does Alg 4 outperform Alg 3 in recall? (Diversity preserves graph navigability; closest-only creates hub-and-spoke that traps search.) (D3) **Pre-mortem**: each insert just appends to neighbor list without pruning; lists grow unbounded; search degrades to O(N) per node. What guard catches this? (Assert `n_list.len() ≤ m_for(layer) * 1.1` after insert.)

  #### Phase 2 — Failing tests

  - [ ] `test_insert_100k_under_30s_single_thread` — build 100k 128-d random vectors; assert wall time ≤ 30 s.
  - [ ] `test_bfs_from_ep_covers_99pct` — after build, BFS from ep reaches ≥ 99% of nodes.
  - [ ] `test_avg_neighbor_count_under_m_1_1` — assert average neighbors/node ≤ M × 1.1 (no overflow).
  - [ ] `test_recall_at_10_after_build` — vs brute-force ground truth on 100 queries; recall@10 ≥ 0.95.
  - [ ] `test_select_neighbors_uses_algorithm_4` — code review + unit test on heuristic vs raw-closest; assert Alg 4 picks diverse set.
  - [ ] `test_ep_promotion_on_higher_level_insert` — insert node at level higher than current ep; ep promoted.
  - [ ] `bench_insert_throughput_5k_per_sec` — single-thread 128-d insert; ≥ 5 k/sec.

  #### Phase 3 — Failure cards

  - **When `test_avg_neighbor_count_under_m_1_1` reports avg = M × 3**: Symptom: after 100k inserts, average neighbor count is 48 (target ≤ 18 for M=16); search becomes O(N). Why: pruning skipped — `n_list.push(id)` without subsequent capacity check. Fix: after `n_list.push(id)`, `if n_list.len() > m_for(layer) { *n_list = select_neighbors_heuristic(&vectors[n], n_list, m_for(layer), layer); }`. Muscle: bounded data structures need explicit cap check after every insert. Reapplies at: every neighbor/edge data structure.

  - **When `test_recall_at_10_after_build` reports recall@10 = 0.78**: Symptom: 22% of queries missing in top-10. Way under 0.95 target. Why: select_neighbors used Algorithm 3 (raw closest), not Algorithm 4 (diversity heuristic). Fix: Alg 4 — for each candidate c sorted by distance, accept iff no already-accepted neighbor is closer to c than c is to the new node. Implementation: walk sorted candidates; for each, check existing-accepted set; accept if "diverse enough." Muscle: HNSW's recall hinges on neighbor diversity, not just closeness. Reapplies at: any graph-based ANN (NSG, NSSG, DiskANN).

  - **When `test_ep_promotion_on_higher_level_insert` shows ep regression**: Symptom: thread A inserts level 5 node; thread B inserts level 6 simultaneously; B wins ep update; A's later write regresses ep back to 5. Why: ep update is `*self.ep.write() = Some(id)` unconditional. Fix: CAS-protect: only update if new_level > current_ep_level. `if target_level > self.ep_level() { CAS update }`. Or for v0.5 single-threaded build: no race.

  - **5-year failure mode**: when build throughput must exceed 50k/sec, single-threaded construction is bottleneck. Migration: fine-grained per-node locking (hnswlib pattern). Trigger: build time > 1 hour for 100M vectors.

**Friday — vector-db: HNSW search**

- [ ] **Build**: `crates/vector-db/src/hnsw/search.rs` — k-NN search per Algorithm 5. ef parameter for recall/latency tradeoff. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: search is what users pay for. Algorithm 5 descends greedily from ep to layer 0, then does ef-bounded best-first at layer 0, returns top-k. Tuning ef at query time trades latency for recall. Downstream consumers: W102 filtered search wraps this with predicate, W104 segment manager federates search across segments via top-k merge.

  #### Phase 1 — Requirements + design (~25 min)

  - **Requirements** (write in `notes/101fri_search_design.md`): (R1) search never modifies graph; (R2) ef ≥ k always (caller validates); (R3) visited set bounds memory to ~ef² (in practice much less); (R4) top-k sorted ascending by distance; (R5) recall@10 ≥ 0.95 at ef=200; (R6) search latency ≤ 1 ms P99 at ef=64 on 1M 128-d; (R7) ef sweep produces monotone recall increase (recall is monotonic non-decreasing in ef); (R8) distance fn at construction matches search-time (assert via marker type).

  - **Design questions**: (D1) Why dual heap? MinDist (candidates, expand smallest distance next) + MaxDist (results, evict largest). Why not single? (Different orderings; candidates want closest, results want furthest for eviction.) (D2) Visited set: HashSet<NodeId>. Capacity hint = ef × M × 4. Why pre-allocate? (Avoid rehash mid-search.) (D3) **Pre-mortem**: search returns < k results when ef = k and graph has < k neighbors of seed — results heap underflows. What guard? (ef = max(ef, k); explicit at search entry.)

  #### Phase 2 — Failing tests

  - [ ] `bench_search_p99_under_1ms_ef64_1m_vectors` — 1M 128-d built; 1k queries at ef=64; P99 < 1 ms.
  - [ ] `test_recall_at_10_above_095_at_ef200` — vs brute-force; recall@10 ≥ 0.95.
  - [ ] `test_ef_sweep_monotone_recall` — ef ∈ {10, 50, 100, 200, 400}; recall monotone non-decreasing.
  - [ ] `test_search_returns_at_least_k_or_all_available` — small graph (5 nodes); k=10; returns 5 not panic.
  - [ ] `test_concurrent_search_no_panic` — 32 threads × 1k searches; no panic, no data race.
  - [ ] `test_distance_fn_matches_construction` — build with L2; query with cosine attempted; compile error or runtime assert.

  #### Phase 3 — Failure cards

  - **When `test_search_returns_at_least_k_or_all_available` panics with heap underflow**: Symptom: tiny graph; k=10 but only 5 nodes; results.peek() returns None; .unwrap() panics. Why: code assumes ef ≥ k and graph has ≥ k nodes. Fix: at entry, `let ef = ef.max(k);`. Handle empty results gracefully (return empty Vec, not panic).

  - **When `test_recall_at_10_above_095_at_ef200` reports 0.83**: Symptom: recall well under target. Why: distance fn at search differs from construction (build used L2, search using cosine without re-normalization). Fix: HnswGraph stores distance fn at construction time as type parameter or runtime field; search uses the same. Marker type pattern: `HnswGraph<D, L2Distance>` vs `HnswGraph<D, CosineDistance>`.

  - **When `bench_search_p99_under_1ms_ef64_1m_vectors` reports P99 = 8 ms**: Symptom: 8× over budget. Why: visited set allocation per search (no pre-allocation hint); HashMap shard contention on adjacency reads; sequential per-neighbor distance calc instead of SIMD batched. Fix: (a) pre-allocate visited with capacity ef × M × 4; (b) snapshot neighbors once per node, release read lock; (c) batch distance calc via SIMD (Tuesday's L2). Re-bench; expect P99 ~800 µs.

  - **When `test_concurrent_search_no_panic` data races**: Symptom: ASan or proptest flags race between search reader and concurrent insert writer. Why: RwLock<Layer> taken inside iteration but released between iterations; insert can mutate mid-search. Fix: search holds read lock for the entire search OR takes a snapshot (cloning adjacency) at start. v0.5 picks read-lock-hold; v1.0 uses epoch-GC for lock-free reads.

  - **5-year failure mode**: when latency budget shrinks below 100 µs (real-time semantic search at 10k qps/core), naive HashSet visited is too slow. Migration: bitset visited indexed by NodeId; cache-friendly. Trigger: P99 > 500 µs at ef=64.

Where does it DIFFER (vector data has no point-in-time MVCC like Cassandra; immutability simpler; merge is graph-rebuild, not key-merge)? (~90 min)
  - 🔧 **Decomposition prompt**: vector-db v0.5 starts scaffolding this week; W104 ships the segment manager. The architectural shape — sealed/active segments with background compaction — is identical to lsm-core (W38-W42 / W95+ mini-db); the data shape is different (HNSW graph, not sorted KV). Documenting the parallels and divergences now means W103's segment-write path inherits the right discipline; the W104 segment-manager ship has a defensible position.
  - 🎯 **Hardened acceptance**:
    - **Parallel table**: rows = lsm-core / Qdrant segments; cols = sealed unit (SSTable / SealedSegment), active unit (Memtable / MutableSegment), compaction trigger (STCS-style size-tiered / size-ratio), merge operation (key-merge / graph-rebuild), tombstone handling (per-key / per-vector-id).
    - **Divergence section**: 3 specific differences: (a) vector segments rebuild HNSW graph on merge (lsm just k-way-merges keys); (b) no point-in-time MVCC needed (vector queries return current snapshot, not historical); (c) deletes are tombstones marked in segment metadata (similar to LSM), but reclaim requires graph rebuild not just compaction.
    - **mini-db inheritance**: vector-db's storage backend uses mini-db; segment files written via mini-db's API. Document the boundary: mini-db handles persistence + WAL, vector-db handles segment lifecycle + graph rebuild.
    - **Cited URLs**: https://qdrant.tech/documentation/concepts/indexing/ (Qdrant segments); ScyllaDB compaction strategies for LSM parallel.
    - **5-year failure mode**: when vector compression matures (1-bit quantization w/ matryoshka embeddings), segment merge cost drops dramatically; the compaction discipline shifts toward more frequent merges. Migration: segment-config parameter for merge-cost-aware tuning.
