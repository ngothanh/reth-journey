  - *Mental model*: the fund is a deterministic accumulator on the VSR log — `apply(fill) → balance += accrual(fill.taker_fee)`. It is the *same* kind of VSR-derived state as the order book (W74): every replica that applies the same committed prefix reaches the byte-identical balance.   - *Contract* (signature only, NEVER the body):
    ```rust
    pub struct InsuranceFund {
        balance: i128,        // micro-USD, signed (can be probed below 0 in tests; tripwire fires first in prod)
        accrual_bps: u16,     // DECLARED param: 1000 = 10% of taker fee. From genesis config, identical on every replica.
    }
    impl InsuranceFund {
        pub fn new(accrual_bps: u16) -> Self;                 // accrual_bps is the declared model param
        pub fn accrue_from_taker_fee(&mut self, taker_fee: i128) -> i128;  // returns amount accrued; integer-only
        pub fn balance(&self) -> i128;
        pub fn draw(&mut self, amount: i128) -> DrawResult;   // Wed's waterfall calls this; never silently goes negative
    }
    pub enum DrawResult { Covered, Tripwire { shortfall: i128 } }   // Tripwire = the v1.5 ADL seam
    ```
  - *Back-of-envelope* (bar (c) — name the cost + sanity the numbers): at 1M orders/sec ingest (§4A capacity target) with ~half taker fills, accrual runs ~500k/sec. Integer `balance += taker_fee * accrual_bps / 10_000` is ~3 ops (~1 ns); at 500k/sec that is ~0.5 ms/sec of CPU — free. The `f64` alternative is not slower, it is *wrong*: `(fee as f64 * 0.10)` rounds differently on x86 FMA vs ARM Neon, so after ~10^6 accruals the balances diverge by ≥1 micro-USD and the cross-replica state hash splits. **The cliff here is correctness, not latency: f64 = silent divergence; integer = byte-identical.** Sanity on P3: 1M fills × ($10k notional × 10 bps fee = $10 = 10^7 µUSD) × 10% accrual = 10^6 × 10^6 µUSD = **10^12 µUSD ≈ $1M accrued** — the fund self-funds at this rate, which is exactly what the tripwire test must confirm.
  - **The problem this primitive solves**: a venue must honor winning traders even when a losing trader's collateral is exhausted below the bankruptcy price. The fund is the capital that absorbs that gap. Two failure categories: (a) **non-determinism** — any `f64` accrual or RNG-sourced rate makes replicas disagree on the fund balance, so the cluster can't agree on whether it's solvent (a correctness catastrophe); (b) **the sensitivity trap** — randomizing the accrual rate per VOPR seed *looks* rigorous but reframes the question into "does some rate survive?" and injects non-determinism into the replicated core. The fix: integer-only accrual + a **declared** rate + a **deterministic external sweep** (re-run the whole core at 5/10/20%, each run internally deterministic).

    - R5. `draw(amount)` returns `Covered` if `balance >= amount` (deducts), else `Tripwire { shortfall }` (deducts to exactly 0, reports the uncovered remainder) — **never silently negative**.

  - **(NEWBIE) When `draw_never_goes_negative_returns_tripwire` lets the balance go to -300_000:**

    - Muscle: money in a replicated SM is integer-only; multiply-before-divide; truncation is the safe direction (under-accrue, never over). Reapplies at: W83 ledger balance math, W99 risk-engine margin math, Wed waterfall.

    ```rust
    pub enum BreakerState { Closed, Open { reason: TripReason, since_tick: u64 } }
    impl LiquidationEngine {
        fn on_seq_tick(&mut self, now: SeqTick);   // advances the window; may trip → forces full recompute
        pub fn breaker_state(&self) -> BreakerState;
    }
    ```
  - *Back-of-envelope* (bar (c)): the breaker checks two counters per mark tick (~10/s) — trivial cost. The load-bearing decision is *what it triggers*: a full portfolio recompute across all accounts (§4A: ~1M recomputes at the 100k-account target), which is exactly why full recompute is *reserved* for breaker/param events and the steady state uses incremental margin (W98). **The breaker is the seam that justifies the incremental-margin hot path: incremental in steady state, full only when the governor trips.**
  - **The problem this primitive solves**: a liquidation cascade can drain the fund faster than accrual replenishes it; without a governor, one bad mark tick could trip the tripwire that the declared rate was sized to never hit. The breaker halts and forces a full, authoritative recompute. Failure categories: (a) **non-deterministic window** (wall-clock) → replicas trip at different ops → divergence; (b) **swallowed tripwire** in tests → the v1.5 ADL trigger condition is lost. The fix: SequenceClock-driven window + declared thresholds + an invariant test that loudly records any tripwire-hit as a v1.5 trigger.
  - **Requirements** R1..R7 — write in `crates/liquidation-engine/notes/101thu_breaker_design.md`:
    - R1. The breaker's rate window is measured in SequenceClock ticks (log-driven), never wall-clock.
    - R2. `max_liqs_per_window` and `max_fund_drawdown_bps_per_window` are declared params (genesis config), identical on every replica.
    - R3. On trip, the breaker halts new liquidations AND signals `risk-engine` to run a full portfolio recompute (the §4A reserved-for-breaker path).
    - R4. The breaker state is VSR-log-derived (in `state_hash()`); replicas trip on the same op.
    - R5. **Tripwire-never-hit invariant**: a test (`tripwire_never_fires_invariant`) runs the canonical + randomized scenarios at the declared 10% rate and asserts the fund's `Tripwire` NEVER fires.
    - R6. If a schedule *does* hit the tripwire, the test fails LOUDLY and records the schedule in `notes/101_v15_adl_trigger_conditions.md` as a defined v1.5 ADL-engagement condition (not swallowed).
    - R7. Cross-replica + cross-arch byte-identical breaker decisions.
  - **Design walk-through** D1..D5 — answer in the design doc:
    - D1. Why SequenceClock ticks, not wall-clock, for the window? (Replicas must trip deterministically on the same op.)
    - D2. What does a trip trigger, and how does it tie to W98's incremental-vs-full recompute? (Trip → full recompute; steady state → incremental.)
    - D3. Why is the tripwire-hit a *recorded v1.5 trigger* and not a test we relax? (It is the §4A v1.0→v1.5 seam — the condition under which ADL must engage; relaxing it would hide the moat's boundary.)
    - D4. **Pre-mortem (load-bearing):** write the 4-line trace where the breaker counts "liquidations in the last 1000ms" via `Instant::now()`: replica A (faster host) sees 40 liqs in its 1000ms wall-window and trips; replica B (slower host) sees 35 and stays closed → they disagree on whether the venue is halted → divergence on the next op. The fix: count liquidations per N SequenceClock ticks.
    - D5. **Anti-shortcut audit:** *"measure the rate with a wall-clock, it's a rate after all"* → wrong: non-deterministic trip → divergence. *"if a test trips the tripwire, just raise the accrual rate and move on"* → wrong: that hides the v1.5 seam; record the schedule as the ADL trigger instead. *"trip only on liq count"* → wrong: a few huge liquidations can drain the fund without a high count; also gate on fund draw-down.
  - **Output**: `notes/101thu_breaker_design.md` with R1..R7, D1..D5, the wall-clock-window divergence trace.
