**Wednesday — vector-db: HNSW graph layer**

- [ ] **Build**: `crates/vector-db/src/hnsw/graph.rs` — `HnswGraph { layers: Vec<Layer>, ep: NodeId }` with
  `Layer { neighbors: HashMap<NodeId, Vec<NodeId>> }`. (~75 min)
  - **Why**: **HNSW is the single most-interview-load-bearing module of vector-db.** Every vector-db hire conversation
    includes "explain HNSW." The multi-layer skip-list-over-NSW design (Malkov & Yashunin 2018) is the dominant ANN
    algorithm. Build the data structure right and search/insert fall out cleanly.
  - **Read first**:
    - Malkov & Yashunin 2018 "Efficient and robust approximate nearest neighbor search using Hierarchical
      Navigable Small World graphs" — Algorithms 1-5. The paper IS the design doc.
    - hnswlib `hnswalg.h` (the canonical implementation by the paper authors). Note: ALL the production HNSWs
      (qdrant, milvus, weaviate, faiss) cite this code as the reference.
    - Qdrant `lib/segment/src/index/hnsw_index/graph_layers.rs` (Rust impl — closest to what we're building).
    - faiss `faiss/IndexHNSW.cpp` for the M, efConstruction, ef tunables.
    - SkipList by Pugh 1990 for the layer-level probability distribution.
  - **Design**: ```rust
    use std::sync::atomic::{AtomicUsize, Ordering};
    use parking_lot::RwLock;

    pub type NodeId = u32;
    pub type LayerId = u8;

    pub struct HnswGraph<const D: usize> {
        // Per-layer adjacency. layers[0] is densest (all nodes); layers[L] is sparsest.
        layers: Vec<RwLock<Layer>>,
        // Vectors stored externally (allows quantization swap). NodeId → Vec<f32; D>.
        vectors: RwLock<Vec<Vector<D>>>,
        // Entry point: highest non-empty layer's representative.
        ep: RwLock<Option<NodeId>>,
        // Parameters.
        m: usize,             // max neighbors per node (typ 16)
        m_max0: usize,        // max neighbors at layer 0 (typ 32 = 2*M)
        ef_construction: usize, // construction-time search width (typ 200)
        ml: f64,              // level normalization, = 1/ln(M)
        max_level: LayerId,
        next_id: AtomicUsize,
        rng: parking_lot::Mutex<rand::rngs::SmallRng>, // for layer sampling
    }

    pub struct Layer {
        // Adjacency: NodeId → fixed-size neighbor array.
        // Use Vec<NodeId> for now; SmallVec<[NodeId; 32]> later for cache locality.
        adjacency: hashbrown::HashMap<NodeId, Vec<NodeId>>,
    }

    impl<const D: usize> HnswGraph<D> {
        pub fn new(m: usize, ef_construction: usize) -> Self { ... }
        pub fn node_count(&self) -> usize { self.next_id.load(Ordering::Relaxed) }
        pub fn entry_point(&self) -> Option<NodeId> { *self.ep.read() }
        // Layer assignment per paper §4: l ~ floor(-ln(uniform(0,1)) * ml).
        pub fn assign_level(&self) -> LayerId {
            let u: f64 = self.rng.lock().random();  // (0, 1]
            (-u.ln() * self.ml).floor() as LayerId
        }
    }
    ```
    **Invariants**:
    - Every node appears at layer 0 and ALL layers below its assigned level. (So if assigned level = 3, node is
      in layers 0, 1, 2, 3.)
    - The entry-point ep is at the highest layer that contains ≥1 node.
    - Neighbor count per node per layer ≤ M (layer ≥ 1) or M_max0 (layer 0). Excess pruned by heuristic (paper
      Algorithm 4).
    - Adjacency is bidirectional in spirit but stored once (insert adds A→B and B→A).
    - Layer assignment is monotone in expectation (lower layers denser). The geometric distribution from -ln(u)*ml
      gives an expected layer count of ~ log_M(N).
  - **Build steps**:
    1. (~10 min) Vector<D> type with const generic dimension; Distance trait stub (cosine/l2/dot).
    2. (~15 min) HnswGraph struct + Layer struct + new() with defaults M=16, ef_c=200.
    3. (~10 min) assign_level() — sanity check: 1M samples should produce layer 0 ~ 100%, layer 5 ~ 0.1%,
       layer 10 ~ 1e-6.
    4. (~15 min) add_node(vec) — allocates NodeId via next_id, pushes vec, returns id. Does NOT yet link
       neighbors (W101 Thu insert step adds linking).
    5. (~10 min) neighbors(node, layer) accessor for the search step.
    6. (~10 min) Smoke test: instantiate, add 1000 nodes, assert node_count == 1000, layer distribution matches
       expectation.
    7. (~5 min) Document M / ef_construction / ef trade-offs in DESIGN.md table.
  - **Pitfalls** (named, deep):
    - *Entry-point degeneration after deletes*: **Symptom**: if the entry-point node is deleted and you don't
      promote a replacement, future searches start at a non-existent ep → either panic or wrong results. **Fix**:
      on delete (out of v0.5 scope, but document), if removed node IS ep, scan all top-layer nodes for a
      replacement; if top layer becomes empty, demote ep_layer. Mark in DESIGN.md as a known limitation v0.5.
      For v0.5: just disable delete or tombstone (mark deleted, search filters out).
    - *Layer skew*: **Symptom**: rng has a bad seed or ml is wrong → all nodes assigned layer 0, graph degenerates
      to flat NSW, search becomes O(N). **Fix**: assert in test that layer distribution matches geometric
      (1-1/M); ml = 1/ln(M) exactly per paper §3.
    - *Recall vs construction-time trade-off*: **Symptom**: M=8 + ef_c=50 → fast build, recall@10 = 0.85; M=32 +
      ef_c=400 → slow build, recall@10 = 0.99. Picking wrong defaults disappoints users. **Fix**: defaults M=16,
      ef_c=200 give recall ≥ 0.95 on standard benchmarks; expose both as config; document the table.
    - *Neighbor list overflow*: **Symptom**: if you don't prune to M neighbors after each insert, the graph
      accumulates unbounded edges, search becomes O(N) per node. **Fix**: insert pipeline (Thu) MUST call
      prune_neighbors per Algorithm 4.
    - *RwLock contention*: **Symptom**: 32-thread parallel insert ends up serializing on Layer write lock →
      throughput tanks. **Fix**: v0.5 keep single Layer lock; v1.0 would shard per-layer or use
      lock-free graph structures (hnswlib uses fine-grained spinlocks per-node).
    - *NodeId space*: **Symptom**: u32 caps at 4B nodes — fine for v0.5, but a 32-bit ID limits per-segment
      capacity. **Fix**: document; per-segment cap aligns with W104 segment manager.
    - *Unbounded vectors storage*: **Symptom**: vectors Vec<Vector<D>> grows in memory, OOM at large scale.
      **Fix**: v0.5 in-memory; W103 adds mmap-backed storage; W104 segment manager splits.
  - **Test scenarios** (adversarial):
    - 1M layer assignments: histogram matches geometric distribution within 5%.
    - Concurrent 16-thread add_node of 100k vectors: no panic, node_count exact.
    - Adversarial layer assignment via seeded RNG: confirm reproducibility for tests.
    - Empty graph: entry_point() = None; search returns empty.
  - **Acceptance**:
    - HnswGraph<128> stores 1M nodes in ≤ 600 MB RAM (raw vectors + adjacency).
    - assign_level distribution matches paper within ε.
    - All accessors thread-safe (no UB under proptest).
    - Documented M/ef trade-off table.
  - **Downstream**:
    - W101 Thu: insert builds on this (Algorithm 1).
    - W101 Fri: search builds on this (Algorithm 5).
    - W102: quantize swaps Vec<Vector<D>> for Vec<QuantizedVector>.
    - W103: persist serializes adjacency + vectors.
    - W104: segment manager wraps multiple HnswGraphs.
    - Interview value: "implemented HNSW from the Malkov paper" is a direct response to "have you done ANN?"

**Thursday — vector-db: HNSW insert**

- [ ] **Build**: `crates/vector-db/src/hnsw/insert.rs` — multi-layer insert per paper Algorithm 1. M = 16,
  efConstruction = 200 defaults. (~75 min)
  - **Why**: Insert is the construction pipeline. It calls search (Alg 2) at each layer to find the ef closest
    existing nodes, then connects via M neighbors with heuristic pruning (Alg 4). Inverted-from-search reuse of
    Alg 2 here is critical — same code, different parameters.
  - **Read first**: Malkov & Yashunin Algorithms 1, 2, 3, 4. hnswlib `addPoint` impl. Qdrant `graph_layers_builder.rs`.
  - **Design**: ```rust
    impl<const D: usize> HnswGraph<D> {
        pub fn insert(&self, vec: Vector<D>) -> NodeId {
            let id = self.add_node(vec.clone());
            let target_level = self.assign_level();
            let ep = match self.entry_point() {
                None => {
                    *self.ep.write() = Some(id);
                    return id;
                }
                Some(ep) => ep,
            };
            let mut curr_ep = ep;
            let curr_level = self.ep_level();  // level of current ep
            // Greedy descent from top layer to target_level + 1 (Alg 1 lines 5-7).
            for layer in (target_level + 1..=curr_level).rev() {
                curr_ep = self.search_layer(&vec, &[curr_ep], 1, layer)[0];
            }
            // From target_level down to 0, do ef-search and connect (Alg 1 lines 8-16).
            for layer in (0..=target_level).rev() {
                let candidates = self.search_layer(&vec, &[curr_ep], self.ef_construction, layer);
                let neighbors = self.select_neighbors_heuristic(&vec, &candidates, self.m_for(layer), layer);
                // Connect id <-> neighbors at this layer.
                let mut l = self.layers[layer as usize].write();
                l.adjacency.insert(id, neighbors.clone());
                for &n in &neighbors {
                    let n_list = l.adjacency.entry(n).or_default();
                    n_list.push(id);
                    if n_list.len() > self.m_for(layer) {
                        // Prune neighbor's list (Alg 4).
                        let pruned = self.select_neighbors_heuristic(
                            &self.vectors.read()[n as usize], n_list, self.m_for(layer), layer
                        );
                        *n_list = pruned;
                    }
                }
                curr_ep = candidates[0];
            }
            // Promote ep if target_level > current.
            if target_level > curr_level {
                *self.ep.write() = Some(id);
            }
            id
        }
    }
    ```
    **Invariants**: insert always succeeds (no rejection); ep updated atomically only after all layers wired;
    neighbor lists capped at M (or M_max0 for layer 0); insert is NOT concurrent-safe in v0.5 (single-threaded
    construction or lock-the-graph builder pattern).
  - **Build steps**: 1. (~10 min) `select_neighbors_heuristic` (Algorithm 4) — the diversity-preserving pruning;
    2. (~15 min) Greedy-descent phase (search_layer with ef=1 at upper layers); 3. (~20 min) Wide-search phase
    (search_layer with ef_construction at target_level downwards); 4. (~10 min) Connection + pruning at each
    layer; 5. (~10 min) Test: insert 100k random vectors single-threaded, confirm graph connectivity (BFS from
    ep reaches > 99% of nodes); 6. (~10 min) Bench: insert throughput ≥ 5k/sec on 128-d vectors single-thread.
  - **Pitfalls** (named):
    - *Skipped pruning*: **Symptom**: each insert just appends to neighbor list; lists grow unbounded; search
      degrades. **Fix**: ALWAYS call select_neighbors_heuristic when neighbor list exceeds M.
    - *Diversity pruning vs simple-closest*: **Symptom**: pruning by raw distance (Alg 3) gives worse recall than
      heuristic (Alg 4). **Fix**: use Algorithm 4 heuristic — pick neighbors that don't make new candidate's
      vector closer to an existing neighbor than to the new node.
    - *Concurrent insert race*: **Symptom**: two threads insert at same layer, both write adjacency, one
      overwrites. **Fix**: v0.5 = single-threaded build (document); v1.0 would do fine-grained per-node locking
      like hnswlib.
    - *Ep promotion race*: **Symptom**: thread A inserts level 5 node, thread B inserts level 6, both try to
      promote ep, B wins but A finishes after — ep regresses. **Fix**: CAS-protect ep update with layer
      comparison: only update if new_level > current_ep_level.
    - *Construction-time vs query-time M asymmetry*: **Symptom**: hnswlib uses different M for build vs query
      paths (M_max vs M); skipping this hurts perf. **Fix**: explicit `m_for(layer)` returning M_max0 at layer
      0, M elsewhere.
  - **Test scenarios**: insert 100k 128-d random vectors; assert BFS from ep covers ≥ 99% of nodes; assert
    average neighbor count ≤ M*1.1.
  - **Acceptance**: build 100k 128-d vectors in ≤ 30s single-thread; recall@10 ≥ 0.95 after build (Friday
    search test).
  - **Downstream**: W101 Friday uses search_layer (shared with insert); W103 persistence serializes adjacency
    built here; W104 segment manager merges multiple HnswGraphs by re-inserting nodes.

**Friday — vector-db: HNSW search**

- [ ] **Build**: `crates/vector-db/src/hnsw/search.rs` — greedy search per Algorithm 5. ef parameter for recall tuning. (~75 min)
  - **Why**: Search is what users pay for. Algorithm 5 (k-NN search) descends greedily from ep to layer 0,
    then does ef-bounded best-first at layer 0, returns top-k. Tuning ef at query time trades latency for recall.
  - **Read first**: Malkov & Yashunin Algorithms 2, 5. hnswlib `searchKnn`. Qdrant
    `lib/segment/src/index/hnsw_index/searcher.rs`.
  - **Design**: ```rust
    impl<const D: usize> HnswGraph<D> {
        pub fn search(&self, query: &Vector<D>, k: usize, ef: usize) -> Vec<(NodeId, f32)> {
            let ep = match self.entry_point() { Some(e) => e, None => return vec![] };
            let mut curr = ep;
            // Greedy descent (Alg 2 with ef=1).
            for layer in (1..=self.ep_level()).rev() {
                curr = self.search_layer(query, &[curr], 1, layer)[0];
            }
            // Wide search at layer 0 with ef.
            let candidates = self.search_layer(query, &[curr], ef.max(k), 0);
            // Return top-k by distance.
            let mut scored: Vec<_> = candidates.into_iter()
                .map(|id| (id, query.distance(&self.vectors.read()[id as usize])))
                .collect();
            scored.sort_unstable_by(|a, b| a.1.partial_cmp(&b.1).unwrap());
            scored.truncate(k);
            scored
        }

        // Algorithm 2: ef-bounded best-first search at a layer.
        fn search_layer(
            &self, query: &Vector<D>, entry_points: &[NodeId], ef: usize, layer: LayerId,
        ) -> Vec<NodeId> {
            let mut visited = hashbrown::HashSet::with_capacity(ef * 4);
            let mut candidates: BinaryHeap<MinDist> = BinaryHeap::new(); // min-heap by distance
            let mut results: BinaryHeap<MaxDist> = BinaryHeap::new();   // max-heap (top of size ef)
            for &ep in entry_points {
                let d = query.distance(&self.vectors.read()[ep as usize]);
                candidates.push(MinDist { id: ep, dist: d });
                results.push(MaxDist { id: ep, dist: d });
                visited.insert(ep);
            }
            while let Some(c) = candidates.pop() {
                let furthest = results.peek().unwrap().dist;
                if c.dist > furthest && results.len() >= ef { break; }
                let neighbors_snapshot = self.layers[layer as usize].read()
                    .adjacency.get(&c.id).cloned().unwrap_or_default();
                let vectors = self.vectors.read();
                for n in neighbors_snapshot {
                    if !visited.insert(n) { continue; }
                    let d = query.distance(&vectors[n as usize]);
                    let furthest = results.peek().map(|m| m.dist).unwrap_or(f32::INFINITY);
                    if d < furthest || results.len() < ef {
                        candidates.push(MinDist { id: n, dist: d });
                        results.push(MaxDist { id: n, dist: d });
                        if results.len() > ef { results.pop(); }
                    }
                }
            }
            results.into_iter().map(|m| m.id).collect()
        }
    }
    ```
    **Invariants**: search never modifies graph; ef ≥ k always (caller validates); visited set bounds memory to
    ~ef^2 (in practice much less); top-k sorted ascending by distance.
  - **Build steps**: 1. (~10 min) MinDist/MaxDist wrapper types for BinaryHeap ordering; 2. (~15 min)
    search_layer (Alg 2) with visited set + dual heap; 3. (~15 min) search() top-level with descent + final
    sort; 4. (~15 min) Test: build 100k 128-d, brute-force ground truth for 100 queries, assert recall@10 ≥
    0.95 at ef=200; 5. (~10 min) Bench: search throughput at ef=64 single-thread, target ≥ 5k qps; 6. (~10
    min) Sweep ef ∈ {10, 50, 100, 200, 400} and chart recall vs latency.
  - **Pitfalls** (named):
    - *Off-by-one ef vs k*: **Symptom**: search returns < k results when ef = k and graph has < k neighbors of
      seed → results heap underflows. **Fix**: ef = max(ef, k); explicit guard.
    - *Stale neighbors snapshot*: **Symptom**: read locks on each iteration cause concurrent writers to block;
      reading once at top and caching is better. But if a write commits mid-search the snapshot is stale.
      **Fix**: v0.5 single-writer-or-readers (RwLock); accept slight staleness in v0.5 read; W103 persistence
      adds proper version snapshot.
    - *Visited set memory*: **Symptom**: at ef=1000 visited grows to 1M entries on dense graph, allocations
      dominate. **Fix**: pre-allocate with capacity ef * M * 4 hint; reuse across calls via thread-local pool.
    - *Distance fn mismatch*: **Symptom**: build uses L2, query uses cosine — graph traversal misleading. **Fix**:
      HnswGraph stores the distance fn at construction; search uses the same one; assert via marker type.
  - **Test scenarios**: 100k vectors, recall@10 ≥ 0.95 at ef=200; ef sweep produces monotone recall increase;
    concurrent search threads no panic.
  - **Acceptance**: recall@10 ≥ 0.95 at ef=200; search latency ≤ 1 ms P99 at ef=64 on 1M 128-d (matches
    hnswlib ballpark).
  - **Downstream**: W102 filtered search wraps this with a predicate; W104 segment manager federates search
    across segments via top-k merge.
