  - 🎯 **Pre-prediction prompt (do this BEFORE reading Phase 2)** — seal answers in `crates/consensus-vsr/notes/73_applied_log_prediction.md`; compare to reality after tests run:

  - *Mental model*: in VSR the **log of prepared ops is the source of truth**; `commit_point` is the highest op-number a replica has both *committed* (quorum-acked) AND *applied* (run through the SM). A reader (matching engine, risk engine, settlement finality) answers "is op N final?" by `N ≤ commit_point()` — **no auxiliary state, no mapping table** (the §4A lock). It must be O(1) because the apply loop and every finality check fire it on the 1M-ops/s hot path.
  - *Contract* (signature-level — NEVER the body):
    ```rust
    pub struct AppliedLog { /* journal_ref, applied, commit_point, applied_index — all private */ }
    impl AppliedLog {
        pub fn on_commit(&mut self, op: u64) -> CommitResult; // advance commit_point contiguously; O(amortized 1)
        pub fn apply(&mut self, op: u64, effect: Effect);     // record applied effect; O(log n) insert, rare-vs-read
        pub fn commit_point(&self) -> u64;                    // O(1) field read — highest APPLIED & committed op
        pub fn is_final(&self, op: u64) -> bool;              // op <= commit_point; the SettlementId finality check
        pub fn snapshot_iter(&self) -> impl Iterator<Item = (&u64, &Effect)>; // BTreeMap order, for state-transfer/snapshot
        fn assert_monotonic(&self, new_point: u64);           // debug_assert commit_point never regresses
    }
    ```
  - *Back-of-envelope* (bar (c)): target ~1M `commit_point()`/`is_final()` calls/sec from the apply loop + finality checks. A field read is ~0.5 ns (L1). A naïve "scan the journal for the highest contiguous committed op" on a 1M-entry log is ~1M visits × ~1 ns hot (cache-miss-heavy on cold tail) ≈ 1 ms/call. **Cliff: 1 ms vs 0.5 ns = ~2,000,000×.** At 1M calls/sec the naïve path is physically impossible (1M × 1 ms = 1000 CPU-seconds/wall-second). `on_commit` fires at the commit cadence (≈ once per committed op, contiguous-advance is amortized O(1) via a cursor); `apply` is O(log n) BTreeMap insert. So the commit-point is maintained on commit, queried for free on read.
  - **Requirements** — write in `crates/consensus-vsr/notes/73_applied_log_design.md`:
    - R1. `AppliedLog { journal_ref, applied, commit_point, applied_index }` — `commit_point` is a cached field, incrementally maintained.
    - R2. **`commit_point()` is O(1)**: a field read, never a journal scan.
    - R3. **Applied, not received**: `commit_point` reflects the highest op that has been **applied to the SM**, not the highest received prepare (`commit_max`). The risk/control plane reads this (§4A read-after-commit-from-local-applied-state).
    - R4. **Monotonic commit-point**: `commit_point` NEVER regresses, including across a view change. Invariant: `new_point ≥ old_point` at every advance site.
    - R5. **Contiguous advance**: `on_commit(op)` advances `commit_point` only across a *contiguous* run of committed ops (no gaps) — a committed op with an uncommitted predecessor does not advance the point.
    - R6. **Deterministic `applied_index` iteration**: `applied_index: BTreeMap<u64, Effect>` (sorted by op-number) — NEVER HashMap. State-transfer/snapshot iterates it.
    - R7. **`is_final(op)` = `op ≤ commit_point()`**: no side mapping table; this is the `SettlementId` finality predicate W103 inherits verbatim.
    - R8. **Apply cost ≤ 200 ns** at a 1M-entry log (BTreeMap insert).
    - R9. **Snapshot determinism**: two replicas applying the same op set produce byte-identical `snapshot_iter()` output (SHA256 equal).
    - R10. **Op-number is snapshot-epoch-relative-ready**: `commit_point`/op-numbers are stored as raw `u64` but the design notes how a `snapshot_epoch` will later qualify them (W75/W103) so identities survive compaction — no representation choice today blocks that.

    - D3. `is_final(op)` flow: one line. Why is "no side mapping table" the whole point? (Identity = position in the log; finality = position ≤ watermark; idempotency falls out free — the §4A `SettlementId` lock.)
    - D4. View-change handoff (preview of W75): a new primary may have a *higher* `commit_max` but `commit_point` still only advances on *apply*. Why must the new view never lower `commit_point`? (Lowering re-applies committed ops → double-fill/double-settle.)
    - D5. Snapshot/state-transfer: `snapshot_iter()` walks `applied_index` in op-number order. Why must this be deterministic across replicas? (W76 state-transfer + W88 VOPR compare snapshots byte-for-byte.)
    - D6. Determinism vector: why is `HashMap` forbidden for `applied_index`? Trace the divergence across two replicas with different `RandomState` seeds taking a snapshot.
    - **D7. Pre-mortem #1 (load-bearing — commit_point re-scans the journal):** write the EXACT 5-step trace where naïve `commit_point()` at 1M calls/sec on a 1M-entry log is physically impossible (1000 CPU-s/wall-s). If you can't write the trace you can't prove the cached watermark prevents it.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  Ordered newbie→expert — the ladder you actually walk.

  - **(NEWBIE) When `lint_no_hashmap_in_applied_log_rs` reports a match on `applied_index: HashMap`:**
    - Symptom: grep finds `HashMap`; lint red before any logic bug shows.
    - Why: the obvious index is `HashMap<u64, Effect>`.
    - Fix: `applied_index: BTreeMap<u64, Effect>`; op-number is the natural sort key.
    - Cost avoided: a divergent-snapshot bug that would otherwise surface only at W76 state-transfer or W88 VOPR; ~$0 here, days later. **(bar (c) violation if shipped.)**
    - Muscle: any structure whose iteration order the deterministic SM observes is BTreeMap from line one. Reapplies at: W74 VSR `client_table`, W74 OrderBook (already BTreeMap), W83+ ledger account map, W88 VOPR replay, W103 `perp-dex-core` projection.
  - **(SENIOR) When `gap_does_not_advance_commit_point` shows the point at 3:**
    - Symptom: op 1 and op 3 committed (op 2 not); `commit_point()` returns 3.
    - Why: `on_commit` set `commit_point = max(committed ops)` instead of advancing across the *contiguous* committed run.
    - Fix: maintain an `applied` cursor; `on_commit(op)` advances `commit_point` only while `commit_point + 1` is both committed AND applied; a gap stalls the watermark.
    - Cost avoided: prevents applying op 3's effect before op 2 — a replay-order violation that forks the SM. **(bar (c) violation.)**
    - Muscle: a commit watermark advances over a *contiguous* prefix, never a max. Reapplies at: W74 VSR `commit_max`→`commit_min` advance, W76 state-transfer, W92 ledger commit.
  - **(SENIOR) When `commit_point_is_applied_not_received` returns 5:**
    - Symptom: op 5 committed (quorum) but not applied; `commit_point()` returns 5; the risk plane reads state the SM hasn't run.
    - Why: `commit_point` was wired to `commit_max` (highest received prepare) instead of the applied cursor.
    - Fix: `commit_point` tracks the **applied** watermark; `commit_max` stays a separate field used only to drive the apply loop, never returned to readers.
    - Cost avoided: prevents a liquidation/settlement decision on un-applied state — exactly the §4A acceptance #5 correctness bug.
    - Muscle: the control/risk plane reads **read-after-commit from local *applied* state**, not received state. Reapplies at: W74 matching apply read, W103 projection control-plane contract, W90 risk-engine per-mark-tick read.
  - **(SENIOR) When `commit_point_never_regresses_across_view_change` shows a backward step:**
    - Symptom: a new view hands a lower `commit_max`; `commit_point` drops; committed ops re-apply.
    - Why: the advance site took the new view's number unconditionally.
    - Fix: `commit_point = max(commit_point, new)` at every advance site; add `debug_assert!(new ≥ self.commit_point)` (R4 invariant `assert_monotonic`).
    - Cost avoided: prevents double-fill / double-settle across view changes — a safety bug, not a perf one. **(bar (c) violation.)**
    - Muscle: consensus watermarks are monotone; assert it at every mutation. Reapplies at: W75 view_change, W76 state-transfer, W92 ledger, W103 `SettlementId` `Final` monotonicity.
  - **(EXPERT — perf #1, bar (c) violation) When `bench_commit_point_under_3ns` reports ~1 ms and `perf record` blames a journal scan:**
    - Symptom: `commit_point()` is ~2,000,000× over budget; at 1M calls/sec it is physically impossible. The W74 matching apply loop and every `is_final` check stall.
    - Why: naïve `commit_point()` scans the journal for the highest contiguous committed op on EVERY call.
    - Fix: cache `commit_point: u64`, advanced incrementally in `on_commit` (amortized O(1) cursor walk); `commit_point()` becomes a field read.
    - Cost avoided: O(n) → O(1); ~1 ms → ~0.5 ns per call; reclaims the entire apply-loop budget. **(bar (c) violation.)**
    - Muscle: queries fired far faster than mutations get a maintained-on-mutation watermark, never a recomputed-on-query scan. Reapplies at: W74 VSR PrepareOk quorum (`BitSet::count_ones`), W83+ ledger balance summary, W103 `finality_status` hot path.
  - **(EXPERT — perf #2 / determinism, bar (c) violation) When `prop_applied_index_deterministic_across_10k_orderings` reports divergent snapshots (and the negative control `hashmap_backed_log_diverges_within_1000_orderings` passes):**
    - Symptom: same op set, different arrival micro-orders, two replicas → different snapshot bytes. Single-node tests pass; multi-replica state-transfer intermittently diverges; seed-dependent.
    - Why: `applied_index: HashMap` iterates in process-random order; `snapshot_iter()` emits effects in a seed-dependent order even though the final applied state is order-independent.
    - Fix: `BTreeMap<u64, Effect>` for `applied_index`; `snapshot_iter()` walks op-number order; the `lint_no_hashmap_*` CI guard prevents regression.
    - Cost avoided: prevents a divergence bug caught only at W76/W88 or in production; BTreeMap lookup ~30 ns vs HashMap ~15 ns, irrelevant against perf #1's savings. **(bar (c) violation if shipped.)**
