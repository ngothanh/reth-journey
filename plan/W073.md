  - *Mental model*: a `ForkTree` is the in-memory DAG of valid-but-not-yet-final BFT blocks; `head()` answers "which leaf is canonical right now?" deterministically and **without ever choosing a branch that contradicts the validator's lock**. It exists because under partial synchrony the network briefly hosts competing valid branches and every honest replica must pick the identical one.
  - *Contract* (signature-level — NEVER the body):
    ```rust
    pub struct BftBlock { pub hash: BlockHash, pub parent: BlockHash, pub height: u64, pub round: u32, pub view: u64, pub qc: Qc }
    pub struct ForkTree { /* nodes, children, finalized, locked, head — all private */ }
    impl ForkTree {
        pub fn insert(&mut self, block: BftBlock) -> Result<(), ForkError>; // O(log n), maintains head
        pub fn re_lock(&mut self, new_locked: BlockHash);                   // O(subtree), rare
        pub fn head(&self) -> BlockHash;                                    // O(1) field read
        pub fn finalized(&self) -> BlockHash;
        fn is_ancestor(&self, anc: BlockHash, desc: BlockHash) -> bool;
    }
    ```
  - *Back-of-envelope* (bar (c)): target 30k `head()` calls/sec from the fcU + matching-engine path. A field read is ~0.5 ns (L1). A naïve descendants walk on a 10k-node tree is ~10k node visits × ~3 ns/visit (cache-miss-heavy pointer chase, ~100 ns main-mem amortized to ~3 ns hot) ≈ 30 µs/call. **Cliff: 30 µs vs 0.5 ns = ~60,000×.** At 30k calls/sec the naïve path burns 30 µs × 30k = ~0.9 s of CPU per wall-second — over-budget before any matching work. `insert` is ~1/sec (block cadence); `re_lock` rarer. So the index is maintained on the rare mutation, queried on the hot read.

  - **(NEWBIE) When `lint_no_hashmap_in_fork_choice_rs` reports a match on `children: HashMap`:**
    - Symptom: grep finds `HashMap`; lint red before any logic bug shows.
    - Why: the obvious children map is `HashMap<BlockHash, Vec<BlockHash>>`.
    - Fix: `children: BTreeMap<BlockHash, SmallVec<[BlockHash; 4]>>`; keep each child list sorted on insert.

  - **(SENIOR) When `lock_respected_against_higher_qc_branch` shows head on the right (higher-QC) branch:**
    - Symptom: validator locked on left; right branch with higher QC arrives; `head()` returns right. The validator now equivocates against its own lock.
    - Why: `head()` picks max-QC across the entire tree instead of restricting to descendants-of-`locked`.
    - Fix: head choice is `max_by(total_order)` over `descendants_of(self.locked)` ONLY; add `debug_assert!(self.is_ancestor(self.locked, self.head))` at every head-update site.
    - Cost avoided: prevents a consensus safety violation (split commit) — catastrophic, not merely slow. **(bar (c) violation.)**
    - Muscle: lock-respecting fork-choice is the BFT safety floor; every head update re-verifies the lock-ancestry invariant. Reapplies at: W68 lock+fork-choice integration, W74 consensus-engine canonicality, W91 consensus-engine v1.0.
  - **(SENIOR) When `three_chain_commit_advances_finalized` finalizes B1 instead of B0:**
    - Symptom: 3-chain rule misfires — finalized advances one block too shallow.
    - Why: the check inspects `grandparent.qc` (parent-of-parent) instead of requiring three CONSECUTIVE QCs back to the great-grandparent.
    - Fix: given B0←B1←B2←B3, finalize B0 iff B3.qc certifies B2 ∧ B2.qc certifies B1 ∧ B1.qc certifies B0; implement `finalize_via_3chain(b3)` walking back exactly three QCs, finalizing only the great-grandparent.
    - Cost avoided: under-finalization stalls the chain; over-finalization (off-by-one the other way) can finalize an unsafe block — a safety bug.
    - Muscle: HotStuff's 3-chain rule is precisely "three consecutive QCs"; count the links explicitly. Reapplies at: W74 consensus-engine, W82 HotStuff variant, W91.
  - **(SENIOR) When `bench_insert_under_100us_at_10k_tree` reports ~1 ms/insert:**
    - Symptom: insert is 10× over budget; flame graph shows an ancestor walk per insert.
    - Why: `insert` re-walks ancestors O(depth)≈10k ops to verify parent existence + height/round consistency.
    - Fix: BTreeMap parent lookup is O(log n); for ancestor checks store a per-block depth/jump-pointer index for O(log depth) `is_ancestor`.
    - Cost avoided: ~1 ms → ~5 µs/insert; reclaims insert budget so it never steals from the `head()` hot path.
    - Muscle: tree operations on a hot path use index structures, not linear walks. Reapplies at: W74 raft log lookups, W83+ ledger account tree, W95 LSM level metadata.
  - **(EXPERT — perf #1, bar (c) violation) When `bench_head_under_3ns` reports ~30 µs and `perf record` blames `descendants_of`:**
    - Symptom: `head()` is ~60,000× over budget; at 30k calls/sec ≈ 0.9 s CPU per wall-second — impossible. Matching-engine v1.0 p99 commit latency blows 50×.
    - Why: naïve `head()` calls `descendants_of(self.locked)` + `max_by` over all descendants on EVERY call. Subtree traversal is the cost driver.
    - Fix: cache `head: BlockHash`, updated incrementally — on `insert(block)` (≈1/sec) if block descends from `locked` AND beats current head on the total order; on `re_lock(new_locked)` (rarer) walk the new locked-subtree once for a fresh head. `head()` becomes a field read.
    - Cost avoided: O(subtree) → O(1); ~30 µs → ~0.5 ns per call; reclaims ~0.9 s/sec of CPU — the entire fork-choice budget. **(bar (c) violation.)**
    - Muscle: queries fired far faster than mutations get a maintained-on-mutation index, never a recomputed-on-query traversal. Reapplies at: W65 precommit threshold, W68 POL detection, W74 VSR PrepareOk quorum (`BitSet::count_ones`), W83+ ledger account-balance summary index, W95 mini-db LSM-level metadata cache.
  - **(EXPERT — perf #2 / determinism, bar (c) violation) When `prop_deterministic_head_across_10k_orderings` reports divergent head sequences (and the negative control `hashmap_backed_tree_diverges_within_1000_orderings` passes):**
    - Symptom: same block set, different micro-orders, two replicas → different head sequences. Single-node tests pass; multi-replica integration intermittently diverges; seed-dependent.
    - Why: `children: HashMap` (or any RandomState-seeded map) iterates in process-random order; intermediate logic (BFS for finalize, first-seen tiebreak) silently diverges even if the final `max_by` is order-independent.
    - Fix: `BTreeMap<BlockHash, SmallVec<BlockHash>>` for `children` and `nodes`; keep child lists sorted; the `lint_no_hashmap_*` CI guard prevents regression.
    - Cost avoided: prevents a divergence bug otherwise caught only at W74 multi-replica integration or in production; BTreeMap lookup ~30 ns vs HashMap ~15 ns, at 30k/sec that's ~450 µs/sec extra — dwarfed by perf #1's savings. **(bar (c) violation if shipped.)**
    - Muscle: any structure whose iteration order the deterministic SM observes is BTreeMap; you buy determinism with ~2× lookup cost. Reapplies at: W73 evidence `verified`, W74 OrderBook (already BTreeMap), W83+ ledger account map, W88 VOPR replay determinism.

  - **(NEWBIE) When `lint_no_hashmap_in_verified_pool` matches `verified: HashMap`:**
    - Symptom: grep finds HashMap on `verified`; lint red.
    - Why: the obvious pool is `verified: HashMap<EvidenceId, Evidence>`.
    - Fix: `verified: BTreeMap<EvidenceId, Evidence>` with `EvidenceId = (height, round, validator_id)`.
    - Cost avoided: a ledger-divergence bug surfacing only at W83 integration. **(bar (c) violation if shipped.)**
    - Muscle: SM-observed iteration order ⇒ BTreeMap from line one. Reapplies at: W73 fork_choice children, W74 VSR client_table, W83+ ledger, W88 VOPR.
  - **(SENIOR — correctness, catastrophic) When `identical_vote_replay_not_flagged` flags the retry as double-sign:**
    - Symptom: a validator legitimately rebroadcasts the same vote; detector emits Evidence; an honest validator becomes slashable.
    - Why: the detector compares a vote hash or just keys on presence, treating identical retries as conflicts.
    - Fix: on `observe`, if `vote_index[(val,h,r,step)] == new_vote` by full CONTENT equality → dedup, return None; only differing content at the same key emits Evidence.
    - Cost avoided: prevents slashing honest stake — a protocol-credibility-ending bug, not a perf issue.
    - Muscle: false-positive slashing is catastrophic; detector predicates must be content-aware, never key-presence. Reapplies at: W74 raft duplicate-message handling, W83+ ledger transaction dedup.
  - **(SENIOR) When `evidence_with_wrong_epoch_rejected` accepts rotated-key evidence:**
    - Symptom: a validator rotated keys; old-key evidence resubmitted; `verify` accepts against the current set's pubkey → wrong validator slashed (or silent fail).
    - Why: `verify` uses the current validator set, but the votes were signed under the OLD set.
    - Fix: every `Evidence` carries `validator_set_id`; `verify` looks up the pubkey from the historical set indexed by that id, retained for `MAX_EVIDENCE_AGE`.
    - Cost avoided: prevents slashing the wrong validator across a rotation boundary — a correctness/credibility bug.
    - Muscle: cryptographic proofs spanning key-rotation boundaries MUST carry the validator-set epoch id. Reapplies at: W83 ledger fraud proofs, W92 VSR view evidence.
  - **(SENIOR) When `pool_memory_bounded_under_ttl` grows unboundedly:**
    - Symptom: submit 1 M old evidence; pool grows monotonically; eventual OOM.
    - Why: TTL eviction unwired, or evicts by wall-clock instead of height (non-deterministic + never fires on replay).
    - Fix: on each height advance, `prune` entries with `evidence.height < current_height - MAX_EVIDENCE_AGE` via BTreeMap range delete (O(log n + k)).
    - Cost avoided: bounded memory; deterministic prune (height, not wall-clock) so replicas evict identically. **(bar (c) violation if wall-clock — non-deterministic.)**
    - Muscle: any append-only pool needs an explicit TTL/compaction keyed on a deterministic clock (height), not wall-time. Reapplies at: W71 ADL queue compaction, W74 OrderBook canceled-order cleanup, W95 LSM compaction.
  - **(EXPERT — perf #1, bar (c) violation) When `bench_verify_batched_under_10us_amortized` reports ~50 µs/evidence:**
    - Symptom: verify is single-message; during a partition-heal evidence flood (~100/sec) it burns ~5–10 ms/sec on one core; p99 spikes.
    - Why: naïve `evidence.verify()` calls `ed25519::verify()` twice serially per Evidence (~50 µs each); "batched" was aspirational.
    - Fix: buffer in `pending: VecDeque<Evidence>`; on len ≥ 8 OR a 1 ms timer, `ed25519::verify_batch(&pubkeys, &msgs, &sigs)`; amortized ~6 µs/msg (≈8×). Move verified entries to `verified`.
    - Cost avoided: ~44 µs/evidence × 100/sec ≈ 4 ms/sec CPU saved; a 10k-evidence flood drains in ~1 s instead of ~10 s. **(bar (c) violation.)**
    - Muscle: bulk crypto verification on intake is always batched — the cross-cutting consensus optimization. Reapplies at: W64/W65/W68 BFT vote intake, W67 raft AppendEntries authenticated mode, W74 VSR PrepareOk batch verify, W83+ ledger transfer-signature batch verify.

    - Why: `verified: HashMap` iterates in process-random order; the slashing pass applies in different orders.
