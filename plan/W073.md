  with locking guarantees agreement under partial sync. (~total 215 min across 3 phases)
  - 🔧 **Why this matters**: a fork-choice rule deterministically selects a single canonical head from a tree of valid blocks. Under BFT locking (W68), the rule MUST respect locks — choosing a non-locked branch when validators are locked elsewhere splits commit. Get the data structure wrong (HashMap children iteration) and replicas diverge silently — the determinism bug surfaces only in 3-replica integration tests, not single-node unit tests. Downstream: W75 consensus-engine fcU handler calls `ForkTree::head`; W74 matching-engine state machine relies on this for canonicality; W83+ ledger uses the same pattern; tier-A interview: "compare LMD-GHOST vs HotStuff fork-choice".

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: a BFT network may briefly host multiple competing valid block branches under partial synchrony. The fork-choice rule picks ONE deterministically, AND respects validators' locks (W68) so the choice doesn't force lock-violations. Done naïvely (re-walk descendants on every `head()` call) the per-call cost is O(tree size) — at 30k calls/sec on a 10k-node tree that's 3 s of CPU per wall-second. Done wrongly (HashMap children) replicas diverge across processes due to RandomState seeds.

  - **Requirements** — write in `crates/consensus-bft/notes/73_fork_choice_design.md`:
    - R1. `BftBlock { hash, parent, height, round, view, qc }` is the on-tree block representation.
    - R2. `ForkTree { nodes, children, finalized, locked, head }` — `head` is cached and incrementally maintained.
    - R3. **Lock-respecting head**: `head` is ALWAYS a descendant of `locked`. Assertion: `is_ancestor(locked, head)`.
    - R4. **Monotonic finalization**: `finalized` is ancestral; once finalized, never reorged.
    - R5. **Deterministic tiebreaks**: (height descending, round ascending, hash lex) — total order, identical on every replica.
    - R6. **Deterministic children iteration**: `children: BTreeMap<BlockHash, SortedVec<BlockHash>>` — NEVER HashMap.
    - R7. **O(1) head()**: cached field, updated incrementally on `insert(block)` and `re_lock(new_locked)`.
    - R8. **Insert reject past finalized**: `insert` rejects blocks with `height ≤ finalized.height` unless ancestor of finalized.
    - R9. **Insert cost ≤ 100 µs** at 10k-node tree.
    - R10. **Property determinism**: 10k random insert orderings of the same block set produce identical head sequences across replicas.

  - **Design walk-through** — answer each in your design doc; no peeking at Tendermint or HotStuff source until Phase 3:
    - D1. Sketch `BftBlock` and `ForkTree`. Why does the tree carry `locked` AND `head` separately?
    - D2. Pseudocode the lock-respecting head choice: among descendants of `locked`, pick max-(height, -round, hash_lex). Why this specific order?
    - D3. Insert flow: 6 numbered steps from `insert(block)` to `head` updated. When does `insert` update `head`? When does it NOT? (Hint: only when the new block descends from `locked` AND beats current head on the total order.)
    - D4. Re-lock flow: 4 numbered steps from `re_lock(new_locked)` to `head` updated. Why is this O(subtree) but only fires on lock changes (~rare)?
    - D5. Finalize (3-chain HotStuff): when does the second-to-second-grandparent become finalized? Draw the 4-block diagram.
    - D6. Determinism vector: why is `HashMap` forbidden for `children`? Trace the divergence scenario across two replicas with different `RandomState` seeds.
    - D7. **Pre-mortem #1 (head re-walks subtree)**: 5-step trace where naïve `head()` at 30k calls/sec on 10k-node tree burns 3 s CPU per wall-second.
    - D8. **Pre-mortem #2 (HashMap divergence)**: 6-step trace where two replicas inserting the same blocks in different micro-orders compute different head sequences. The bug surfaces only in multi-replica integration tests.
  - **Output**: `notes/73_fork_choice_design.md` with R1–R10, D1–D8, the lock-respecting head proof, the determinism analysis.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `bench_head_under_1ns` reports ~100 µs and `perf record` shows `descendants_of` at >50% CPU:**
    - Symptom: `head()` is 5 orders of magnitude over budget. At 30k calls/sec on 10k-node tree, ~300 M node visits/sec ≈ 3 s of CPU per wall-second — impossible. Matching-engine v1.0 p99 commit latency 50× over budget.
    - Why: naïve `head()` calls `self.descendants_of(self.locked)` and `max_by` over all descendants on EVERY call. Subtree traversal is the cost driver.
    - Fix: **cached `head: BlockHash`** field, updated incrementally on `insert(block)` (rare ~1/sec) and on `re_lock(new_locked)` (rarer). On insert: if block descends from locked AND beats current head on total order, update head. On re_lock: walk descendants of new locked once, compute fresh head — paying O(subtree) once per lock change, not per `head()` call. `head() -> BlockHash` becomes simple field read (~1 ns).
    - Cost avoided: O(subtree) → O(1) per `head()` call; at 30k/sec saves ~3 s/sec of CPU; reclaims the entire fork-choice budget.
    - Muscle: queries fired at rates much higher than mutations get a maintained-on-mutation index, not a recomputed-on-query traversal. Reapplies at: W65 precommit threshold, W68 POL detection, W74 VSR PrepareOk quorum (BitSet `count_ones`), W83+ ledger account-balance summary index, W95 mini-db LSM-level metadata cache.

  - **When `prop_deterministic_head_across_10k_orderings` reports divergent head sequences:**
    - Symptom: same block set in different micro-orders on two replicas produces different head sequences. Single-node tests pass; multi-replica integration tests intermittently diverge. Bug is seed-dependent.
    - Why: `children: AHashMap<BlockHash, Vec<BlockHash>>` — AHashMap uses random RandomState per process; iterating `children[parent]` yields different orders on different replicas. Even if `head()` does a final `max_by` (deterministic given fixed input), intermediate logic using iteration order (BFS for finalize, tie-break-by-first-seen) silently diverges.
    - Fix: **`BTreeMap<BlockHash, Vec<BlockHash>>` for `children`** (sorted iteration); for the Vec at each parent, keep sorted on insert (children list small, ~2-5 entries; O(k log k) insert fine). `nodes: BTreeMap<BlockHash, BftBlock>` likewise. Add `lint_no_hashmap_in_fork_choice_rs` CI guard.
    - Cost avoided: prevents divergence bug caught only at W74 multi-replica integration (or production); BTreeMap ~2× slower for lookups (~30 ns vs ~15 ns) but at 30k/sec lookups that's ~450 µs/sec extra — affordable, dwarfed by perf #1's savings.
    - Muscle: any data structure whose iteration order is observable by the deterministic SM is BTreeMap, never HashMap. Cost is paid in lookup speed but determinism is bought. Reapplies at: W74 matching-engine OrderBook bids/asks (already BTreeMap), W74 VSR client_table, W83+ ledger account map iteration, W88 VOPR scenario replay determinism.

  - **When `lock_respected_against_higher_qc_branch` shows head jumping to the right branch:**
    - Symptom: validator locked on left; right branch arrives with higher QC; head returns right. Validator now equivocates with its lock.
    - Why: `head()` picks max-QC across entire tree, not restricted to descendants-of-locked.
    - Fix: head choice is `max_by(total_order)` over `descendants_of(locked)`, NEVER over all blocks. Add invariant assertion `debug_assert!(self.is_ancestor(self.locked, self.head))` to every head update site.
    - Muscle: lock-respecting fork-choice is the BFT safety floor — every head update verifies the lock ancestry invariant. Reapplies at: W68 lock + fork-choice integration, W74 consensus-engine.

  - **When `three_chain_commit_advances_finalized` shows finalized advancing every-other commit:**
    - Symptom: 3-chain rule misfires — finalized doesn't advance when it should.
    - Why: 3-chain check looks at `grandparent.qc` (parent-of-parent) instead of `great-grandparent.qc`. Off-by-one in chain depth.
    - Fix: walk the 3-chain rule explicitly: given B0 ← B1 ← B2 ← B3, B0 is finalized when B3 contains a QC for B2 AND B2 contains a QC for B1 AND B1 contains a QC for B0. Three consecutive QCs. Implement `finalize_via_3chain(b3)` walking back through QCs; finalize the great-grandparent only.
    - Muscle: HotStuff's 3-chain rule is precisely "three consecutive QCs"; off-by-one produces under- or over-finalization. Reapplies at: W74 consensus-engine, W82 HotStuff variant.

  - **When `bench_insert_under_100us_at_10k_tree` reports ~1 ms per insert:**
    - Symptom: insert is 10× over budget. Flame graph shows ancestor walk per insert.
    - Why: `insert` re-walks ancestors to verify parent existence + height/round consistency. Each walk is O(depth) ≈ 10k ops.
    - Fix: BTreeMap parent lookup is O(log n); for ancestor checks use a per-block `cumulative_path_length` field or sparse ancestor index (jump pointers) for O(log depth) queries.
    - Muscle: tree operations on a hot path use index structures, not linear walks. Reapplies at: W74 raft log lookups, W83+ ledger account tree.

  - **5-year failure mode** (write in `notes/73_fork_choice_followup.md` after green): when v2.0 ships ZK-finality (validity rollup-style commits), the fork-choice tree becomes a single linear stream — branches are pruned at the L2 boundary. State the migration: ForkTree becomes a thin shim over a linear ledger; head() is the latest committed block. Trigger: zkEVM rollup integration.

## Tuesday — Engine API full read part 2 + consensus-bft evidence

- [ ] Read Engine API sections 4-6. (~45 min)
- [ ] **Build**: `crates/consensus-bft/src/evidence.rs` — slashable-fault collection. Double-sign detector. Equivocation
  proof. (~total 215 min across 3 phases)
  - 🔧 **Why this matters**: evidence is the cryptographic proof of a Byzantine fault that any node can verify and use to slash the offender's stake. Without evidence, BFT systems have no economic deterrent to misbehavior. The detector must be sound (no false positives — slashing honest validators is catastrophic) AND complete (no missed equivocations). Get the data structure wrong (HashMap iteration in `verified`) and the ledger slashing pass diverges between replicas. Downstream: ledger-deterministic stake slashing reads `EvidencePool::verified`; tier-A interview: "what's the difference between accountable safety and accountable liveness?" — evidence is the *accountable* part.

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: a BFT validator that double-signs (votes for two values in the same h/r) is malicious; the network needs cryptographic proof to slash. The detector lives on the vote-intake hot path (~500 votes/sec burst); a false positive slashes an honest validator catastrophically. Verification involves crypto (slow per single message, fast batched). And the pool's iteration order must be deterministic — replicas applying slashes in different orders diverge ledger state.

  - **Requirements** — write in `crates/consensus-bft/notes/73_evidence_design.md`:
    - R1. `Evidence` enum: `DoubleSignPrevote`, `DoubleSignPrecommit`, `AmnesiacEvidence` (unlock without POL). Each carries the conflicting signed votes as cryptographic proof.
    - R2. **Detector cost ≤ 50 ns** on the per-vote insert hot path — index lookup keyed by `(validator, height, round, type)`.
    - R3. **Sound detector**: same content vote (network retry of identical message) is dedup'd, NOT flagged. Slashable only on differing content at same (h, r, type).
    - R4. **Complete detector**: no missed equivocations across 10k random schedules in property test.
    - R5. **Pure verify**: `Evidence::verify(validator_set)` is signature check + structural check; no I/O; deterministic.
    - R6. **Batched verify**: bursts of evidence intake drained in batches of 8-32 via `ed25519::verify_batch` (~6 µs/msg amortized).
    - R7. **TTL eviction**: evidence older than `MAX_EVIDENCE_AGE` (1 week of heights) is pruned. Pool memory bounded.
    - R8. **Validator-set epoch tracking**: evidence carries `validator_set_id`; `verify` checks pubkey against the right epoch's set (handles key rotation).
    - R9. **Deterministic `verified` iteration**: `verified: BTreeMap<EvidenceId, Evidence>` — NEVER HashMap. EvidenceId sorts as `(height, round, validator_id)`.
    - R10. **Cross-replica determinism**: same evidence stream on two replicas produces byte-identical slashing decisions.

  - **Design walk-through** — answer each in your design doc; no peeking at Tendermint evidence source until Phase 3:
    - D1. Sketch the `Evidence` enum. Why does `DoubleSignPrevote` carry both `vote_a` AND `vote_b`? (Hint: both are needed for off-chain verification — anyone can verify.)
    - D2. Detector index shape: `vote_index: HashMap<(ValidatorId, Height, Round, Step), SignedVote>`. On insert, check if entry exists; if so, compare content; if different, emit Evidence. Why is HashMap OK here (lookup only) but BTreeMap required for `verified` (iteration)?
    - D3. AmnesiacEvidence is harder — it requires lock-history reconstruction. Defer or include? Justify.
    - D4. TTL eviction: tied to height, not wall-clock. Why? When does the prune fire?
    - D5. Validator-set epoch: walk the 5-step trace where a validator legitimately rotates key, old key's evidence resubmitted, wrong validator slashed. Why does `validator_set_id` close this?
    - D6. **Pre-mortem #1 (single-message verify)**: 5-step trace where evidence flood (~100/sec during partition heal) burns ~10 ms/sec of CPU on single-message verify. Compute the impact.
    - D7. **Pre-mortem #2 (HashMap iteration in slashing)**: 5-step trace where two replicas with different AHashMap seeds iterate `verified` in different orders, apply slashes in different orders, and (with compounding slash logic like "5% of remaining balance") arrive at different final balances. Ledger replicas diverge.
  - **Output**: `notes/73_evidence_design.md` with R1–R10, D1–D7, the detector flowchart.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `slashing_order_determinism_across_replicas` reports byte-divergent ledger state:**
    - Symptom: two replicas, same evidence stream, produce different final balances after slashing. Replica A slashes validator X then Y; replica B slashes Y then X. Compounding slash math ("5% of remaining balance") propagates the order dependence into divergent state. Ledger replicas split.
    - Why: `verified: AHashMap<EvidenceId, Evidence>` — iteration is non-deterministic across processes (different RandomState seeds).
    - Fix: `verified: BTreeMap<EvidenceId, Evidence>` where `EvidenceId = (height, round, validator_id)` tuple sorts deterministically. Iteration is bytewise-lexicographic, identical on every replica. The slashing pass applies in canonical order — bit-identical results.
    - Cost avoided: prevents divergence that surfaces at W83+ ledger integration (or production); same "determinism at the source" benefit as W73 fork-choice perf #2 / W74 matching-engine determinism gate.
    - Muscle: cross-replica shared state with iteration semantics is BTreeMap, never HashMap; cost (~2× slower lookup) is the price of determinism — and at evidence rates (~1/wk steady) it's irrelevant. Reapplies at: W73 fork_choice children map, W74 matching-engine OrderBook (already BTreeMap), W83+ ledger account map, W88 VOPR replay determinism.

  - **When `bench_verify_batched_under_10us_amortized` reports ~50 µs per evidence:**
    - Symptom: evidence verify is single-message; during partition-heal-driven evidence flood (~100/sec), burns ~10 ms/sec of CPU on a single core just for verify. P99 spikes during evidence floods.
    - Why: naïve `evidence.verify()` calls `ed25519::verify()` twice per Evidence serially (~50 µs each). The "batched" was aspirational; the code path is single-message.
    - Fix: buffer pending evidence in `pending: VecDeque<Evidence>`; on intake, append; once `pending.len() >= 8` OR a 1 ms timer fires, batch-verify via `ed25519::verify_batch(&pubkeys, &msgs, &sigs)`. Amortized cost drops to ~6 µs/msg (8× speedup). Move verified entries to `verified`.
    - Cost avoided: ~44 µs per evidence × 100/sec ≈ 4 ms/sec of CPU saved during bursts; worst-case verify backlog drain time drops from ~10 s to ~1 s for a 10k-evidence flood.
    - Muscle: any bulk crypto verification on intake should be batched; the cross-cutting consensus crypto optimization. Reapplies at: W64/W65/W68 BFT vote intake, W67 raft AppendEntries authenticated mode, W74 VSR PrepareOk batch verify, W83+ ledger transfer-signature batch verify.

  - **When `identical_vote_replay_not_flagged` shows the second copy flagged as double-sign:**
    - Symptom: validator legitimately rebroadcasts same vote (network retry); detector flags as evidence. Honest validator now slashable. Catastrophic false positive.
    - Why: detector compares vote hash or structure but not content. Identical votes are treated as different.
    - Fix: on insert, if `vote_index[(validator, h, r, type)] == new_vote` (exact content equality, not just hash) → dedup, return without action. If different content → Evidence. Sound, complete: identical = retry, different = double-sign.
    - Muscle: false-positive on slashing is catastrophic; detector predicates must be CONTENT-aware, not just key-presence. Reapplies at: W74 raft duplicate-message handling, W83+ ledger transaction dedup.

  - **When `evidence_with_wrong_epoch_rejected` shows evidence from rotated key accepted:**
    - Symptom: validator rotated their key; old key's evidence resubmitted; `verify` accepts (using current validator set's pubkey, which doesn't match the old signature). Wrong validator slashed (or none; slash silently fails).
    - Why: `verify` uses the current validator set's pubkey, but the evidence was signed under the OLD set. Key rotation invalidates the proof.
    - Fix: every Evidence carries `validator_set_id: u64` — the epoch in which the original votes were signed. `verify` looks up pubkey from the historical validator set indexed by `validator_set_id`. Old sets are retained for `MAX_EVIDENCE_AGE` (matches the TTL window).
    - Muscle: cryptographic proofs spanning key-rotation boundaries MUST carry the validator-set epoch identifier. Reapplies at: every signed-evidence system (W83 ledger fraud proofs, W92 VSR view evidence).

  - **When `pool_memory_bounded_under_ttl` shows pool growing unboundedly:**
    - Symptom: submit 1 M old evidence pieces; pool size monotonically increases; eventually OOM.
    - Why: TTL eviction isn't wired, or evicts by wall-clock instead of height.
    - Fix: on every height advance, prune entries with `evidence.height < current_height - MAX_EVIDENCE_AGE`. Use BTreeMap's range API for O(log n + k) deletion of the obsolete prefix. Test by submitting old evidence + advancing height; assert pool size bounded.
    - Muscle: any append-only pool needs an explicit TTL or compaction policy; laziness alone is unbounded. Reapplies at: W71 ADL queue compaction, W74 matching-engine OrderBook canceled-order cleanup.

  - **5-year failure mode** (write in `notes/73_evidence_followup.md` after green): when v2.0 ships ZK-proof-of-equivocation (validator submits compact proof, not the raw signed votes), the storage cost of Evidence collapses ~100× (a SNARK is ~200 B vs ~10 KB for raw votes). State the migration: `Evidence::ZkProof { proof: Snark, public_inputs }` replaces the raw-vote variants for archived evidence. Trigger: validator-set size > 100 with > 10 evidence/week steady state.
