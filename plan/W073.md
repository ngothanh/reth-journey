## Monday — Engine API full read part 1 + consensus-bft fork-choice

- [ ] Read Engine API spec sections 1-3. (~60 min)
- [ ] **Build**: `crates/consensus-bft/src/fork_choice.rs` — fork-choice rule for chained BFT blocks. Honest validators
  with locking guarantees agreement under partial sync. (~150 min)
  - **Why**: A fork-choice rule deterministically selects a single canonical head from a tree of valid blocks. Under BFT locking (built W68), the rule must respect locks — choosing a non-locked branch when validators are locked elsewhere would split commit. Bar (c): this is the BFT analog of LMD-GHOST for the consensus-engine fork-choice glue (W75).
  - *Back-of-envelope* (bar c): `head()` is called on every Prepare-receive (~30k/sec at v1.0 target) AND on every `insert(block)` (~1 block/sec normally, bursty during catch-up). At a 10k-node tree (24h of blocks), naive walk-from-locked = O(tree size) ≈ 10k node visits × ~10 ns = ~100 µs per call → ~3 sec/sec CPU at 30k/sec call rate → impossible. **`head()` MUST be O(log n) or O(1) amortized** — maintain the head as a derived index updated incrementally on `insert` (inherits the running-tally pattern from W65 precommit perf #2 and W68 lock POL perf #1). Memory: tree node ≈ ~200 B + 2 pointers; 10k nodes ≈ 2 MiB — fits L2 if hot subtree is small (~100 nodes near head). **Iteration order over `descendants_of(locked)` MUST be deterministic** — `AHashMap<BlockHash, Vec<BlockHash>>` for `children` is a determinism trap unless every traversal explicitly sorts; use `BTreeMap` or sorted-vec.
  - **Read first**: Tendermint `consensus/state.go::FinalizeCommit` — Tendermint's "rule" is trivial because finalized blocks are linear, but the underlying lock+POL guarantees it. HotStuff §4 (3-chain rule). Diem (libra) hotstuff fork-choice. For comparison: Ethereum's LMD-GHOST in `lighthouse/consensus/fork_choice/src/fork_choice.rs`.
  - **Design**:
    ```rust
    pub struct BftBlock {
        pub hash: BlockHash,
        pub parent: BlockHash,
        pub height: u64,
        pub round: Round,
        pub view: ViewNum,
        pub qc: QuorumCert,            // certificate from prev round's >2/3 precommits
    }
    pub struct ForkTree {
        nodes: AHashMap<BlockHash, BftBlock>,
        children: AHashMap<BlockHash, Vec<BlockHash>>,
        finalized: BlockHash,
        locked: BlockHash,             // current lock per LockState
        head: BlockHash,                // computed
    }
    impl ForkTree {
        pub fn head(&self) -> BlockHash {
            // Pick highest QC descendant of `locked`. If multiple at same height, lowest round.
            self.descendants_of(self.locked)
                .max_by(|a, b| (a.height, Reverse(a.round)).cmp(&(b.height, Reverse(b.round))))
                .map(|b| b.hash)
                .unwrap_or(self.locked)
        }
        pub fn finalize(&mut self, hash: BlockHash);  // 3-chain rule from HotStuff
    }
    ```
    **Invariants**: (i) `head` is always a descendant of `locked` (lock-respecting). (ii) `finalized` is monotonically ancestral — once finalized, never reorged. (iii) Tiebreaks deterministic (height first, round second, then hash lex). (iv) Genesis is the universal ancestor; tree never holds disconnected components.
  - **Build steps**: 1. (~20 min) Types. 2. (~25 min) `insert(block)` — parent-existence check, child-link update. 3. (~30 min) `head` computation respecting lock. 4. (~30 min) `finalize` with 3-chain (HotStuff) or 2-chain (Tendermint) rule — make it pluggable via trait. 5. (~25 min) Prune ancestors of finalized (storage bound). 6. (~20 min) Tests.
  - **Pitfalls** (named, 3):
    - *Lock-bypass head*: **Symptom**: head selects a fork-branch that doesn't descend from `locked` → validator votes on it → equivocates with its lock. **Fix**: assertion in `head()`: `is_ancestor(locked, head)`. Test by feeding a higher-QC branch outside locked's subtree and verifying head stays.
    - *Tiebreak indeterminism*: **Symptom**: two blocks at same height, same round → different replicas pick different. **Fix**: third tiebreak on `BlockHash` byte-lex order. Property test with synthetic equal-priority blocks.
    - *Reorg past finalized*: **Symptom**: malicious QC for a sibling of a finalized block accepted → finality violated. **Fix**: `insert` rejects blocks whose `height <= finalized.height` unless ancestor of finalized. Add safety invariant assertion.
  - **Test scenarios**: (a) Linear chain — head = tip. (b) Two competing branches, lock on left — head stays on left even if right has higher QC. (c) 3-chain commit → finalize advances. (d) Reorg attempt past finalized → rejected. (e) Property: head computation deterministic across 10k random insert orderings.
  - **Acceptance**: tree ops < 100µs per insert at 10k node tree. Property test passes 10k iterations. Inheritance: lock.rs (W68), AHashMap.
  - **Downstream**: W75 consensus-engine fcU handler calls `ForkTree::head` to determine canonical head. W74 matching-engine state-machine relies on this for "which raft term is canonical" mapping. Tier-A interview: "compare GHOST vs HotStuff fork-choice".
  - **Expect to hit (perf) #1 — `head()` re-walks the descendant subtree on every call (bar (c) violation)**: naive `head()` calls `self.descendants_of(self.locked)` and `max_by` over all descendants. At a 10k-node tree with 30k `head()` calls/sec (matching-engine v1.0 raft path needs the head every Prepare/Apply), that's 300M node visits/sec = ~3s of CPU per second → impossible. Symptom: `perf record` shows `descendants_of` at >50% CPU; matching-engine v1.0 P99 commit latency 50× over budget on a node with sustained block production.
    - Fix: **cached `head: BlockHash`** field, updated *incrementally* on `insert(block)` (the rare event — ~1 block/sec) and on `re_lock(new_locked)` (rarer). On `insert`: if block descends from locked AND has higher (height, lower round) than current head → update head. On `re_lock`: walk descendants of new locked, compute fresh head (paying the O(subtree) cost once per lock change, not per head() call). `head() -> BlockHash` becomes a simple field read (~1 ns).
    - Cost avoided: O(subtree) → O(1) per `head()` call; at 30k/sec saves ~3s/sec of CPU; reclaims the entire fork-choice budget for the consensus protocol.
    - Muscle: queries fired at rates much higher than mutations get a maintained-on-mutation index, not a recomputed-on-query traversal. Reapplies at: W65 precommit threshold (already noted), W68 POL detection (already noted), W74 VSR PrepareOk quorum (BitSet `count_ones`), W83+ ledger account-balance summary index, W95 mini-db LSM-level metadata cache.
  - **Expect to hit (perf) #2 — `AHashMap<BlockHash, Vec<BlockHash>>` non-deterministic children iteration (bar (c) violation, determinism-blocking)**: `AHashMap` uses a random seed per process; iterating `children[parent]` produces different orders on different replicas. Even if `head()` does a final `max_by` (deterministic given a fixed input), any intermediate logic that uses iteration order (e.g., tie-break-by-first-seen, BFS ordering for `finalize` traversal) silently diverges between replicas. This is the SAME trap as W74 matching-engine perf-correctness pitfall #2 — and it hits *before* matching-engine v1.0 ships (W74). Symptom: fork_choice.rs tests pass single-node; 3-replica integration test diverges on QC-tied blocks; the divergence is intermittent and seed-dependent.
    - Fix: **`BTreeMap<BlockHash, Vec<BlockHash>>` for `children`** (sorted iteration); for the `Vec` of children at each parent, sort on insert (children list is small, ~2-5 entries typically — O(k log k) insert is fine). The `nodes: BTreeMap<BlockHash, BftBlock>` map likewise. Add a CI grep: `grep -rn "AHashMap\|HashMap" crates/consensus-bft/src/fork_choice.rs && exit 1` — anti-regression.
    - Cost avoided: prevents the divergence bug that would otherwise be caught only at W74 (or worse, in production); one determinism debt resolved at the source = zero re-engineering at W74/W83. BTreeMap is ~2× slower than AHashMap for lookups (~30 ns vs ~15 ns) but at 30k/sec lookups that's ~450 µs/sec extra — affordable, and dwarfed by perf #1's savings.
    - Muscle: any data structure whose iteration order is observable by the deterministic SM (here: the consensus protocol) is BTreeMap, not HashMap. The cost is paid in lookup speed (~2×) but bought is determinism. Reapplies at: W74 matching-engine OrderBook bids/asks (already BTreeMap by design — confirms pattern), W74 VSR client_table (must be BTreeMap), W83+ ledger account map iteration, W88 VOPR scenario replay determinism.

## Tuesday — Engine API full read part 2 + consensus-bft evidence

- [ ] Read Engine API sections 4-6. (~45 min)
- [ ] **Build**: `crates/consensus-bft/src/evidence.rs` — slashable-fault collection. Double-sign detector. Equivocation
  proof. (~150 min)
  - **Why**: Evidence is the cryptographic proof of a Byzantine fault that any node can verify and use to slash the offender's stake. Without evidence, BFT systems have no economic deterrent to misbehavior. The detector must be sound (no false positives — slashing honest validators is catastrophic) and complete (no missed equivocations).
  - *Back-of-envelope* (bar c): evidence verify is rare (Byzantine faults are rare events) but the **detection** path runs on every vote insert (~500/sec burst, see W65 perf). Per-insert detector cost ≤ 50 ns — just an index lookup keyed by `(validator, height, round, type)` to check for conflicting prior vote. Per-evidence-verify ≈ 100 µs (two ed25519 verifies @ ~50 µs each — see W64 perf #1; **must be batched** when intake is bursty). **Pool memory bounded**: `MAX_EVIDENCE_AGE` × validators × ~500 B/evidence; at 1 week × 21 validators × ~1 evidence/wk (typical) = ~10 KiB — trivial. The trap is the DETECTOR's index — naive `votes: AHashMap<(ValidatorId, Height, Round, Step), Vote>` is non-deterministic for iteration; equivocation flag depends on insert order. Detector must be **insert-once, set-on-conflict** with the conflict flag itself the slashing trigger; iteration order of the index NEVER observable.
  - **Read first**: Tendermint `evidence/pool.go` and `evidence/verify.go`. Cosmos SDK `x/evidence/keeper/infraction.go`. Ethereum's slashing conditions (`consensus/specs/phase0/beacon-chain.md#slashings`) — surround/double-vote conditions.
  - **Design**:
    ```rust
    pub enum Evidence {
        DoubleSignPrevote {
            validator: ValidatorId,
            height: u64,
            round: Round,
            vote_a: SignedVote,
            vote_b: SignedVote,           // same (height, round, type=Prevote), different block_hash
        },
        DoubleSignPrecommit { /* analogous */ },
        AmnesiacEvidence {                // unlock without POL
            validator: ValidatorId,
            locked: SignedVote,            // round r_1, block A
            voted: SignedVote,             // round r_2 > r_1, block B != A, no POL between
        },
    }
    pub struct EvidencePool {
        verified: AHashMap<EvidenceId, Evidence>,
        pending: VecDeque<Evidence>,
    }
    impl Evidence {
        pub fn verify(&self, validator_set: &ValidatorSet) -> Result<()> {
            // 1. signatures both valid under validator's pubkey
            // 2. same (height, round, type), different hashes
            // 3. signed by same validator
        }
    }
    ```
    **Invariants**: (i) `verify()` is pure cryptographic — no I/O, deterministic. (ii) Two distinct evidence pieces for the same `(validator, height, round)` collapse to one (idempotent). (iii) Evidence has TTL — older than `MAX_EVIDENCE_AGE` (e.g., 1 week of heights) is pruned. (iv) Submitting unverified evidence is *itself* not slashable (avoids reflexive griefing).
  - **Build steps**: 1. (~20 min) Types + signing setup (ed25519). 2. (~25 min) `DoubleSignPrevote/Precommit` detection: index votes by `(validator, height, round, type)`, on insert check for conflict. 3. (~30 min) `verify()` — signature check + structural check. 4. (~30 min) AmnesiacEvidence — harder, requires lock-history reconstruction; defer to v1.0 if time-pressed. 5. (~25 min) Pool with TTL + dedupe. 6. (~20 min) Tests.
  - **Pitfalls** (named, 3):
    - *False positive on canonical resign*: **Symptom**: validator legitimately rebroadcasts same vote (network retry), buggy detector sees as double-sign. **Fix**: detector compares *vote content*, not just hash — identical votes are dedup'd, not flagged. Slashable only on `vote_a != vote_b` (different block hash, same slot).
    - *Replay across heights*: **Symptom**: old evidence resubmitted ad nauseam, pool grows unboundedly. **Fix**: TTL eviction + indexed-by-validator dedupe. Bench memory with 10k validators, 1M old evidence pieces.
    - *Signing-key rotation gap*: **Symptom**: validator legitimately rotates key, old key's evidence still admissible — wrong validator slashed. **Fix**: evidence includes `validator_set_id` (epoch); `verify()` checks pubkey against the right epoch's set. Tendermint does this via `evidence/verify.go::VerifyEvidence`.
  - **Test scenarios**: (a) Honest validator votes once → no evidence. (b) Adversary votes for A and B at (h, r) → evidence created, verifies. (c) Replay same evidence → idempotent. (d) Bad signature → reject. (e) Wrong validator set epoch → reject. (f) Fuzz: 10k random vote sequences, evidence count matches Byzantine fault count.
  - **Acceptance**: zero false positives in 100k honest-only trace. 100% detection rate in 1k adversarial traces. Bench: verify <50µs per evidence. Inheritance: ed25519-dalek, AHashMap.
  - **Downstream**: ledger-deterministic stake slashing reads `EvidencePool::verified` to debit validator collateral. Interview: "what's the difference between accountable safety and accountable liveness?" — evidence is the *accountable* part of accountable safety.
  - **Expect to hit (perf) #1 — single-message ed25519 verify on intake (bar (c) violation)**: each newly-received Evidence carries two SignedVotes that each need verify. Naive `evidence.verify()` calls `ed25519::verify()` twice serially — ~100 µs per evidence. During adversarial burst (a coordinated Byzantine validator flood, or a partition-heal scenario where evidence backlog flushes), evidence arrival rate can spike to ~100/sec briefly; that's ~10 ms/sec of CPU on a single core just for verify — visible at P99. Symptom: P99 spike during partition heal; `perf top` shows `ed25519_dalek::verify` at ~10% CPU during evidence floods.
    - Fix: **batched intake verify** — buffer pending evidence in a `pending: VecDeque<Evidence>` (already in the design), drain in batches of up to 32 via `ed25519::verify_batch` (~6 µs/msg amortized vs 50 µs single → ~8× speedup). Apply the same fix as W64 perf #1 (verify-batching is the cross-cutting consensus crypto optimization). On `pool.intake()`: append to `pending`; once `pending.len() >= 8` OR a 1 ms timer fires, batch-verify and move to `verified`.
    - Cost avoided: ~44 µs per evidence × 100/sec = ~4 ms/sec of CPU saved during bursts; brings worst-case verify backlog drain time from ~10s to ~1s for a 10k-evidence flood.
    - Muscle: any bulk crypto verification on intake should be batched (same primitive ed25519, same fix as W64 propose). Reapplies at: W64/W65/W68 BFT vote intake (already noted), W67 raft AppendEntries authenticated mode, W74 VSR PrepareOk batch verify, W83+ ledger transfer-signature batch verify.
  - **Expect to hit (perf) #2 — `AHashMap` iteration in `verified` exposes non-determinism (bar (c) violation, determinism-blocking)**: `verified: AHashMap<EvidenceId, Evidence>` for the pool is fine for lookups but the consuming code (ledger slashing W83+) iterates `verified` to apply slashes in a single block. AHashMap iteration is non-deterministic across processes — replica A slashes validator X then Y, replica B slashes Y then X, resulting in different intermediate states (if the slash logic compounds, e.g., "5% of remaining balance"). Final state diverges; ledger replicas split. Symptom: ledger replicas diverge by ~M21 when first real evidence is processed; the divergence is order-dependent and seed-dependent (depends on `AHashMap`'s `RandomState` seed per process).
    - Fix: `verified: BTreeMap<EvidenceId, Evidence>` where `EvidenceId` sorts deterministically (e.g., `(height, round, validator_id)` tuple). Iteration order is bytewise-lexicographic, identical on every replica. The slashing pass applies in this canonical order — bit-identical results.
    - Cost avoided: prevents the divergence bug that would surface at W83+ ledger integration (or worse, in production); same "resolve determinism at the source" benefit as W73 fork-choice perf #2 / W74 matching-engine determinism gate.
    - Muscle: cross-replica shared state with iteration semantics is BTreeMap, never HashMap; the cost (~2× slower lookup) is the price of determinism — and at evidence rates (~1/wk steady) it's irrelevant. Reapplies at: W73 fork_choice children map (already noted), W74 matching-engine OrderBook (already BTreeMap), W83+ ledger account map, W88 VOPR replay determinism.
