- [ ] **Build**: `crates/concurrent/src/channel/bounded.rs` (extension) — split bounded MPMC's producer claim into two compile-time-selected modes, mirroring Disruptor's `SingleProducerSequencer` (no CAS, plain `fetch_add`) and `MultiProducerSequencer` (CAS loop on `tail`). User opts in at construction. (~150 min)
  - 🔧 **Decomposition prompt**: W11 Tuesday shipped the Vyukov MPMC with a universal CAS-on-claim — correct for arbitrary N producers but expensive at N=1 where no contention exists. Disruptor's design opts in: if you *know* you have one producer (matching-engine BLP, ledger apply-loop, raft leader log append), pay zero CAS cost on send. Two modes side-by-side is the durable artifact: the bench (next bullet) makes the trade-off concrete; today's build is the type-level switch. Without it, every downstream consumer (W26 wal group-commit, W31 mmap-queue appender, W58 matching-engine command bus, W77 aeron Publication) overpays on the single-producer hot path.
  - 🎯 **Hardened acceptance**:
    - **Two types**: `BoundedRing<T, SingleProducer>` and `BoundedRing<T, MultiProducer>` (or const-generic boolean `BoundedRing<T, const SP: bool>`) — picked at construction. Same `Sender` / `Receiver` API surface; the internal `claim()` impl differs.
    - **SingleProducer claim**: `let seq = self.tail.fetch_add(1, Release); write_slot(seq); slot[seq & mask].seq.store(seq + 1, Release);` — one atomic op + slot write + slot-seq publish. No CAS loop.
    - **MultiProducer claim**: today's existing W11 Tuesday CAS loop, unchanged. Reuses the per-slot seq encoding.
    - **Compile-time enforcement**: a `SingleProducer` ring exposed to two threads is a `unsafe { ... }` or a compile error. Choose: either the `Sender<T, SP>` is `!Sync` (the borrow checker prevents sharing) and an explicit `unsafe fn assume_single_producer()` exists for shenanigans, OR `Sender<T, SP>: !Clone` so it cannot be duplicated. Document the choice in module-level comment.
    - **5-year failure mode**: when `AtomicU64::fetch_add` becomes lock-free even under contention on some future ARM extension (`LDADD` on aarch64 already is), the SingleProducer/MultiProducer split may collapse — at that point `MultiProducer` is "two threads racing on the same `fetch_add`" which still works but produces non-FIFO ordering. State the migration: keep both modes for FIFO guarantee; document the relax-ordering option as a third mode.
  - *Mental model*: Disruptor's signature insight — most production hot paths have *one* writer thread. Paying for multi-writer CAS on every send is a 5-10 ns tax × millions of sends/sec = real money. Opting in to "I promise single producer" buys back that tax. The type system makes the promise checkable.
  - *Source*: https://lmax-exchange.github.io/disruptor/disruptor.html (ClaimStrategy section); `SingleProducerSequencer.java` vs `MultiProducerSequencer.java` in the LMAX repo.
  - **Expect to hit #1 — runtime check instead of type-system check**: a `Sequencer { is_single: bool }` field with a runtime `if` in claim. Symptom: claim's hot path has a branch every send (~1 ns + branch misprediction risk); also nothing prevents two threads from calling claim on the same `is_single=true` ring.
    - Fix: the mode is a type parameter (or const-generic), not a field. The compiler monomorphizes both impls; no runtime branch.
    - Muscle: a known-at-construction discriminator belongs in the type system, not in a runtime field. Reapplies at: W14 `bufpool` policy enum vs generic, W77 aeron Publication mode, W74 raft single-vs-multi-region.
  - **Expect to hit #2 — SingleProducer claim with `Relaxed` ordering**: producer writes slot, then `tail.fetch_add(1, Relaxed)`. Consumer observes tail-bump before slot data (weak memory order). Symptom: torn read of slot fields on aarch64; x86 hides.
    - Fix: `tail.fetch_add(1, Release)` (in pre-claim sequencer model) or `slot.seq.store(seq + 1, Release)` (in per-slot model). The publish must be Release; the consumer's load must be Acquire.
    - Muscle: even with one producer, the slot-data → seq-publish happens-before edge needs Release/Acquire pairing. Single-producer optimizes out CAS, never the memory fences. Reapplies at: W26 wal group-commit publish, W31 mmap-queue appender, W77 aeron position publish.
- [ ] **Verify**: criterion bench `crates/concurrent/benches/bounded_claim_modes.rs` — SingleProducer vs MultiProducer at N=1,2,4,8 producers. Find the crossover. (~120 min)
  - 🎯 **Hardened acceptance**:
    - **Bench cells**: `(SP=on, N=1)`, `(SP=on, N=1, ban)` — the ban variant deliberately violates the SingleProducer invariant by spawning 2 threads (test that this is `unsafe`-flagged or compile-rejected, not silently wrong); `(MP, N=1)`, `(MP, N=2)`, `(MP, N=4)`, `(MP, N=8)`.
    - **Crossover finding**: at N=1, SP ≥ 1.5× MP throughput (the CAS savings is the entire delta). At N=2, MP is the only choice (SP would corrupt). Document the explicit decision matrix: "use SingleProducer when you can prove N=1 by code structure; never below."
    - **Disruptor reference**: LMAX paper SingleProducer config @ 26M ops/sec vs MultiProducer at ~10M (1P-1C unicast). Your SP/MP ratio should be in a similar ballpark — within 2× of LMAX's claim.
    - **Black-boxed results write-up**: `crates/concurrent/notes/claim_modes_bench_results.md` — observed ratios + decision matrix. Same format as `atomic_cell_bench_results.md`.
  - **Expect to hit (perf) #1 — bench harness serializes producers via shared barrier**: setting up N producer threads via a `std::sync::Barrier::wait()` before the timed section adds wake-up jitter; the timed section now measures barrier wake + claim, not claim alone.     the values for each. Then open seastar's `counter.hh` — how do they pad? Why their padding constant?
  - **Symptom card**: the cliff (5-10× at N≥8 producers on a single cache line); rule (cache-line
    granularity is the unit of MESI contention; per-thread atomics MUST be on separate lines for linear

  - **5-year failure mode**: cache-line size varies by chip (64 B x86 server, 128 B Apple Silicon, 256 B
    possible future). Hard-coding `align(64)` is fragile. Trigger: cross-arch deploy. Fix: target-arch
    cfg selection (W4 chain_head pattern).
  - **Production handoff**: this measurement directly informs every per-CPU counter in the plan. W74
    matching-engine per-shard counters, W42 LockManager `next_id`, W77 aeron `tail_offset` — all silently
    require CachePadded at the hardened acceptance gate. If your N=16 throughput doesn't scale linearly,
    you missed it.
