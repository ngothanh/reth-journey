- [ ] **Build**: `crates/concurrent/src/channel/bounded.rs` (extension) — split the bounded MPMC ring's producer claim into two **compile-time-selected** modes: `SingleProducer` (no CAS, plain `fetch_add`) and `MultiProducer` (CAS loop on `tail`), dispatched by a type parameter. Design-mirrored on LMAX `SingleProducerSequencer` / `MultiProducerSequencer`; built as an in-workspace extension of the W11 `concurrent` ring (no Disruptor crate). (~total 195 min across 3 phases)
  - 🔧 **Why this matters**: the signature single-producer insight — most hot paths have exactly ONE writer
    (a WAL appender, an mmap-queue tail, an aeron Publication). Paying a CAS on every send when there is no
    contender is pure waste (~5-10 ns per send on x86 `lock cmpxchg`). The two **type-level** modes are the
    durable artifact: SP monomorphizes to a single `fetch_add` (`lock xadd` / `LDADD`), MP keeps the CAS
    retry. First-attempt impls reach for a runtime `is_single: bool` field — that compiles BOTH branches and
    keeps the CAS, so the SP path never actually wins; the asm test below traps exactly that. Downstream: W26
    `wal` group-commit appender, W31 `mmap-queue` appender, W58 matching-engine command bus, W77 aeron
    Publication. First-attempt impls fail ≥1 test below and the debug session IS the lesson.

  - 🎯 **Pre-prediction prompt** — write sealed answers in `notes/12_claim_modes_prediction.md`:

  - *Mental model*: a bounded ring's only producer-side race is which producer owns the next sequence. With
    one producer there is no race, so the claim is an unconditional `fetch_add`; with many, claims must CAS.
    Encode that distinction in the type so the compiler deletes the loop the SP case can't hit.

  - *Contract* (signature-level only — never the body):
    ```rust
    pub struct BoundedRing<T, M: ClaimMode> { /* ring, mask, tail, head, _mode: PhantomData<M> */ }
    pub trait ClaimMode { /* sealed marker: SingleProducer | MultiProducer */ }
    pub struct SingleProducer; pub struct MultiProducer;
    // SP sender is !Sync and !Clone (one producer, statically); MP sender is Sync + Clone.
    impl<T> BoundedRing<T, SingleProducer> { fn try_send(&self, v: T) -> Result<(), T>; }
    impl<T> BoundedRing<T, MultiProducer>  { fn try_send(&self, v: T) -> Result<(), T>; }
    ```

  - *Back-of-envelope* (bar (c)): x86 `lock cmpxchg` (CAS) ≈ 5-10 ns uncontended, ~25 ns contended (mutex-
    class); `lock xadd` (`fetch_add`) ≈ 5-7 ns; ARMv8.1 `LDADD` is one instruction with no retry. So SP saves
    the CAS *retry* and the read-modify-compare overhead — call it ~3-5 ns/send saved uncontended, far more
    under contention where CAS spins. At 10M sends/s that is 30-100 ms/s of CPU reclaimed on one core.
    Cliff: at N≥4 contending producers, a CAS claim can spin several times per send (each retry a full
    `lock` round-trip ~25 ns) — the SP path never spins, so its cost is flat while MP climbs. This is the
    plot the verify bench draws.

  - **Requirements** R1..R7 — write in `notes/12_claim_modes_design.md`:
    - R1. Two monomorphized types via a type parameter: `BoundedRing<T, SingleProducer>` and
      `BoundedRing<T, MultiProducer>` (a sealed `ClaimMode` marker trait; NOT a const-generic `bool` field,
      NOT a runtime enum).
    - R2. SingleProducer claim: `let seq = self.tail.fetch_add(1, Relaxed); write_slot(seq);
      slot[seq & mask].seq.store(seq + 1, Release);` — no CAS loop.
    - R3. MultiProducer claim: CAS loop on `tail` (the existing W11 path), unchanged.
    - R4. Compile-time enforcement: the `SingleProducer` sender is `!Sync` AND `!Clone` (so a second producer
      cannot exist); documented with the exact reason. MP sender is `Sync + Clone`.
    - R5. Type-parameter dispatch, NOT a runtime branch — SP monomorphization must contain zero CAS.
    - R6. Memory ordering: the slot-data write → slot-seq publish is `Release`; the consumer's slot-seq load is
      `Acquire` — even in SP mode. The `tail.fetch_add` itself may be `Relaxed` (no cross-thread ordering rides
      on it in SP mode), but the publish edge must NOT be relaxed.
    - R7. *Source*: LMAX `SingleProducerSequencer` vs `MultiProducerSequencer` (design reference only).

  - **Design walk-through** D1..D3 — answer in `notes/12_claim_modes_design.md`; no peeking at the LMAX
    source until Phase 3:
    - D1. **Primitive property table**: enumerate `fetch_add(Relaxed)` vs `compare_exchange_weak` vs a runtime
      `enum Mode` branch vs a `const SP: bool` field — columns: Sync? emits CAS? monomorphizes? branch in hot
      path? Pick the type-parameter row and say why.
    - D2. **Anti-shortcut audit (load-bearing):** the "obvious" reach is `is_single: bool` checked at runtime
      inside `try_send`. Why wrong HERE: both arms compile in, the SP arm still sits behind a branch the CPU
      must predict, and — worse — a `match` that calls a shared CAS helper keeps the CAS instruction in the SP
      binary entirely. The asm test (`single_producer_claim_no_cas`) is built to catch exactly this. Counter-
      example to write out: show the `is_single` impl's disassembly still contains `cmpxchg`.
    - D3. **Pre-mortem (load-bearing) — the exact bad interleaving:** even with ONE producer, the slot-data →
      seq-publish edge can tear. Write this trace out:
      ```
      Producer (thread A):              Consumer (thread B):
      1. seq = tail.fetch_add(1)
      2. slot[seq&mask].data = payload  (the actual T write)
         -- A is PREEMPTED here, or the
            store is reordered after (3) --
                                        3'. spins reading slot[seq&mask].seq
      3. slot[seq&mask].seq.store(seq+1)
                                        4'. sees seq updated, reads slot.data
                                            -> reads HALF-WRITTEN / stale data
      ```
      Ask: what invariant stops B at step 4' from reading before A's step-2 write is visible? Answer it
      (the `Release` store at A.3 + `Acquire` load at B.3' form a happens-before edge: B cannot observe the
      bumped seq without also observing the data write). This is the invariant `single_producer_loom_release_acquire`
      defends, and it is why SP optimizes out the CAS but NEVER the publish fence.

  #### Phase 1 — Bench design (~30 min)

  - *Back-of-envelope* (bar (c)): on the dev box (a modern x86 core, ~3-4 GHz), an uncontended ring send is a
    handful of cache-resident atomics ≈ 30-60 ns/op → ~15-30M ops/s single-threaded. SP should sit at the top
    of that band; MP at N=1 pays the extra CAS read-compare (~5-10 ns) so it sits ~1.5-2× lower. As N climbs,
    MP's CAS contends (each retry ~25 ns) and throughput drops while SP (still single-writer) holds flat.
  - R1. Cells: (SP, N=1), (MP, N=1), (MP, N=2), (MP, N=4), (MP, N=8).
