  - 🔧 **Why this matters**: Disruptor's signature insight — most hot paths have ONE writer. Paying CAS on
    every send is 5-10ns × millions/sec. Two type-level modes is the durable artifact. Downstream: W26
    wal group-commit, W31 mmap-queue appender, W58 matching-engine command bus, W77 aeron Publication.

  #### Phase 1 — Problem, requirements, design (~45 min)

  - **Requirements** — write in `notes/12_claim_modes_design.md`:
    - R1. Two types: `BoundedRing<T, SingleProducer>` and `BoundedRing<T, MultiProducer>` (or const-generic
      `const SP: bool`).
    - R2. SingleProducer claim: `let seq = self.tail.fetch_add(1, Release); write_slot(seq);
      slot[seq & mask].seq.store(seq + 1, Release);` — no CAS loop.
    - R3. MultiProducer claim: CAS loop (existing W11).
    - R4. Compile-time enforcement: SingleProducer sender is `!Sync` or `!Clone`. Documented.
    - R5. Type-parameter dispatch, NOT runtime branch.
    - R6. Memory ordering: Release on publish, Acquire on consumer load — even in SP mode.
    - R7. *Source*: LMAX SingleProducerSequencer vs MultiProducerSequencer.

  - **Design**:
    - D1. Walk through SP claim byte by byte. Cost?
    - D2. **Pre-mortem**: contributor uses `is_single: bool` runtime field. Counter-example?

  #### Phase 2 — Failing tests (~30 min)

  - [ ] `single_producer_claim_no_cas` — assembly inspection: SP claim's hot path = 1 LDADD + 1 store; no

  - [ ] `single_producer_sender_not_sync` — compile-fail: `let s: &SingleProducerSender = &sender;

  #### Phase 3 — One failure at a time (~120 min)

  - **When `single_producer_claim_no_cas` shows CMPXCHG:**
    - Symptom: SP path compiled to a CAS loop; cost identical to MP.
    - Why: runtime branch on `is_single` field; both branches compiled in.
    - Fix: mode is a type parameter (or const-generic). Monomorphizes; SP impl has no CAS at all.
    - Muscle: known-at-construction discriminator belongs in the type system, NOT runtime field.
      Reapplies at: W14 bufpool policy, W77 aeron Publication, W74 raft single/multi region.

  - **When `single_producer_loom_release_acquire` finds torn read:**
    - Symptom: consumer sees tail-bumped but slot still holds old data (aarch64).
    - Why: Relaxed on the slot-seq store.
    - Fix: `slot.seq.store(seq + 1, Release)` + consumer's Acquire on slot-seq load.
    - Muscle: even with ONE producer, the slot-data → seq-publish happens-before edge needs Release/Acquire.
      Single-producer optimizes out CAS, NEVER the memory fences. Reapplies at: W26 wal group-commit
      publish, W31 mmap-queue appender, W77 aeron position publish.

  - **5-year failure mode**: when ARM `LDADD` becomes the universal lock-free fetch_add, even MP collapses
    to one atomic + FIFO. Migration: add a third "Relaxed-MP" mode that explicitly trades FIFO for
    throughput; document.

    Also run with N=2,4,8 to find where the cliff starts.

  - **Compare**: open `crossbeam_utils::CachePadded` source. Their align is target-arch dependent — note
    the values for each. Then open seastar's `counter.hh` — how do they pad? Why their padding constant?
  - **Symptom card**: the cliff (5-10× at N≥8 producers on a single cache line); rule (cache-line
    granularity is the unit of MESI contention; per-thread atomics MUST be on separate lines for linear
    scaling); reapplies at: every per-CPU counter, every per-shard atomic in W74 matching-engine, W42
    LockManager next_id, W77 aeron tail_offset.
  - **Numbers (perf-bearing)**: predict per-thread fetch_add at N=2 unpadded vs padded (~7 ns vs ~5 ns

  - **5-year failure mode**: cache-line size varies by chip (64 B x86 server, 128 B Apple Silicon, 256 B
    possible future). Hard-coding `align(64)` is fragile. Trigger: cross-arch deploy. Fix: target-arch
    cfg selection (W4 chain_head pattern).
  - **Production handoff**: this measurement directly informs every per-CPU counter in the plan. W74
    matching-engine per-shard counters, W42 LockManager `next_id`, W77 aeron `tail_offset` — all silently
    require CachePadded at the hardened acceptance gate. If your N=16 throughput doesn't scale linearly,
