- [ ] **Build**: `crates/exec-vm/src/interpreter/stack.rs` — 1024-deep Stack mirroring revm_interpreter::Stack. (~total 150 min across 3 phases)
  - 🔧 **Why this matters**: the EVM stack is the SINGLE most-touched structure — every opcode pops and pushes
    here. A bounds bug = consensus split with Geth on every bytecode; an off-by-one in DUP/SWAP = silent wrong
    arithmetic only test vectors catch. Downstream: every opcode handler (W9, W17, W53), W49 revm integration.

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **Requirements** — write in `crates/exec-vm/notes/09_stack_design.md`:
    - R1. `Stack` wraps a `Vec<U256>` pre-sized to 1024 capacity.
    - R2. `push` returns `Err(StackOverflow)` when `len() == 1024`. NEVER grows past.
    - R3. `pop` returns `Err(StackUnderflow)` on empty. NEVER panics.
    - R4. `dup(n)` (1-indexed from top): reads index `len - n`, pushes. Requires `len >= n` AND `len < 1024`.
    - R5. `swap(n)` (1-indexed): exchanges `len-1` with `len-1-n`. Requires `len > n`.
    - R6. Every opcode pre-checks min stack height (ADD = 2, ADDMOD = 3) via `Stack::ensure_n(n)`.

  - **Design**:
    - D1. Why pre-sized Vec? (Hint: avoids reallocation on push.)
    - D2. DUP1 vs DUP2: walk through which slot is duplicated.
    - D3. **Pre-mortem**: contributor writes `stack.push(v)` without the 1024 check. What test catches?

  #### Phase 2 — Write the failing tests (~30 min)

  - [ ] `stack_push_at_1024_overflows` — push 1024 items; the 1025th returns `Err(StackOverflow)`. Exercises R2.
  - [ ] `stack_pop_empty_underflows` — `Stack::new().pop()` returns `Err(StackUnderflow)`, not panic. Exercises R3.
  - [ ] `stack_dup1_duplicates_top` — push `42`; `dup(1)`; top two items are both `42`. Exercises R4.
  - [ ] `stack_dup_n_correct_index` — push 1, 2, 3, 4 (4 is top); `dup(3)`; new top is 2. Exercises R4.
  - [ ] `stack_swap1_exchanges_top_two` — push 1, 2; `swap(1)`; pop yields 1 then 2 (vs original 2 then 1).
    Exercises R5.
  - [ ] `stack_ensure_n_checks_min_height` — `stack.ensure_n(3)` on a 2-item stack returns `Err`. Exercises R6.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)

  - **When `stack_push_at_1024_overflows` silently grows to 1025:**
    - Symptom: `Vec::push` allocates; stack now has 1025 items. Deep contracts diverge from Geth.
    - Why: you used `vec.push(v)` without the precondition check.
    - Fix: `if self.0.len() == 1024 { return Err(StackOverflow) }; self.0.push(v); Ok(())`.
    - Muscle: 1024 is a HARD consensus rule, not a capacity hint. Reapplies at: W17, W49, W53.

  - **When `stack_dup_n_correct_index` returns wrong value:**
    - Symptom: `dup(3)` on `[1, 2, 3, 4]` returns 3 (off-by-one).
    - Why: indexing `len - n - 1` instead of `len - n`.
    - Fix: `let v = self.0[self.0.len() - n]; self.push(v)`. DUP is 1-based from top.
    - Muscle: stack-relative opcodes 1-based from top — translate index ONCE, deliberately. Reapplies at:
      W17, W53.

  - **When `stack_ensure_n_checks_min_height` allows the opcode to proceed:**
    - Symptom: ADD on a 1-item stack tries to pop the second item, hits underflow, panics.
    - Why: no pre-check; pop's `Result` was unwrapped.
    - Fix: `Stack::ensure_n(n)` — `if self.len() < n { return Err(StackUnderflow) }`. Every opcode calls
      this before popping.
    - Muscle: every opcode declares min stack requirement — dispatcher enforces BEFORE body. Reapplies at:
      W17, W53.

  - **5-year failure mode** (`notes/09_stack_followup.md`): when EOF gains static stack-height analysis,
    the runtime checks become redundant (proven by parser). State migration: gate the ensure_n calls
    behind `#[cfg(not(eof_validated))]`. Trigger: when W15/W61 EOF parser ships.

  - 🔧 **Why this matters**: the dispatcher is the EVM's heartbeat. PC advance discipline, PUSH data skipping,
    end-of-bytecode handling — get any wrong and EVERY bytecode misexecutes. Downstream: W9 Tue control, W15 EOF
    parser, W17 opcodes, W49 revm.

  #### Phase 1 — Problem, requirements, design (~30 min)

  - **Requirements** — write in `notes/09_interpreter_design.md`:
    - R1. `Interpreter { pc: usize, bytecode: Bytes, stack: Stack, memory: SharedMemory, gas: Gas,
      instruction_result: InstructionResult }`.
    - R2. Dispatch via `[fn; 256]` table; unknown opcodes route to INVALID handler.
    - R3. `step` advances `pc` by 1 BEFORE the handler runs. Handlers may overwrite `pc` (JUMP/JUMPI).
    - R4. PUSHn handler consumes `n` immediate bytes from `bytecode[pc..pc+n]` and advances `pc += n`.
    - R5. `pc >= bytecode.len()` is implicit STOP, not panic.
    - R6. Run loops `step` until `instruction_result` is set.

  - **Design**:
    - D1. Walk through PUSH1 0x60. Bytecode = [PUSH1, 0x60, ADD]. PC trace?
    - D2. JUMP discipline: handler sets pc absolutely. Run loop must not re-advance.
    - D3. **Pre-mortem**: contributor uses match-based dispatch. Performance vs jump-table?

  - **When `interpreter_push1_advances_pc_correctly` re-executes 0x60 as another opcode:**
    - Symptom: bytecode [PUSH1, 0x60, PUSH1, 0x40, ADD] mis-decodes; pc advances 1 byte after PUSH1
      handler, reads 0x60 as a new opcode (PUSH1 again).
    - Why: PUSH handler didn't advance pc past its immediate.
    - Fix: PUSHn handler reads `bytecode[pc..pc+n]` and does `pc += n` after the read. The outer step
      already advanced pc by 1 (past the opcode byte itself).
    - Muscle: PUSH data is inline — the DECODER, not the run loop, must skip it. Reapplies at: W9 Tue
      JUMPDEST analysis, W15 EOF parser.

  - **When `interpreter_jump_lands_on_target` lands 1 byte past:**
    - Symptom: PUSH1 0x05 JUMP JUMPDEST — after JUMP, pc = 6 not 5.
    - Why: run loop incremented pc AFTER JUMP handler set it absolutely.
    - Fix: ONE place advances pc per step. Either (a) advance pc by 1 before dispatch, and JUMP handlers
      set absolutely; or (b) handlers own their advance, run loop never increments. Pick one.
    - Muscle: exactly ONE place advances pc per step — control-flow handlers and the loop must agree.
      Reapplies at: W9 Tue control, W15 EOF parser.

  - **When `interpreter_past_end_is_stop_not_panic` panics with index OOB:**
    - Symptom: bytecode ends without STOP; pc reaches len(); indexing bytecode[pc] panics.
    - Why: no bounds check.
    - Fix: `if pc >= bytecode.len() { ir = Stop; return }` BEFORE indexing.
    - Muscle: falling off the end of bytecode is a clean STOP, never a panic. Reapplies at: W15 EOF
      parser, W53.

- [ ] **Build**: `crates/exec-vm/src/interpreter/memory.rs` — SharedMemory. mload/mstore/mstore8/resize with quadratic
  gas. (~total 150 min across 3 phases)
  - 🔧 **Why this matters**: memory expansion gas is the spec's DoS prevention — `3*w + w*w/512` MUST match Geth
    to the unit, or every contract's gas accounting drifts. Three traps: charge order, quadratic overflow,
    zero-fill semantics.

  #### Phase 1 — Problem, requirements, design (~30 min)

  - **Requirements** — write in `notes/09_memory_design.md`:
    - R1. `SharedMemory(Vec<u8>)`, length always a multiple of 32.
    - R2. `expansion_cost(offset, size)` = `cost(new_words) - cost(current_words)` where `cost(w) = 3*w +
      w*w/512`.
    - R3. Gas charged BEFORE the access; failure leaves buffer unmodified.
    - R4. `mload(offset)` reads 32 bytes; `mstore` writes 32; `mstore8` writes 1.
    - R5. Out-of-bounds reads see zeros (resize-then-access); never panic.
    - R6. `w*w` computed in u128 to avoid overflow; cap inputs at gas-limit upper bound.

  - **Design**:
    - D1. `new_size_words = (offset + size + 31) / 32`. Worked example for offset=10, size=32.
    - D2. cost(w) for w=0, 1, 10, 1000.
    - D3. **Pre-mortem**: contributor uses u64 for w*w. What's the overflow boundary?

  - [ ] `memory_oob_read_returns_zero` — fresh memory; mload(0) returns 0; no panic.

  - [ ] `memory_quadratic_no_u64_overflow` — w = 10_000 (cap'd); w*w in u128 = 100M; doesn't panic.

  - **When `memory_expansion_cost_matches_yellow_paper` returns wrong cost for w=100:**
    - Symptom: cost(100) = 800 (300 + 500), not 319. Wrong divisor.
    - Why: used `/256` or `/1024` not `/512`.
    - Fix: `let q = (w as u128 * w as u128) / 512; let linear = 3 * w; (linear as u64) + (q as u64)`.
