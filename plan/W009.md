- [ ] **Build**: `crates/exec-vm/src/interpreter/stack.rs` — 1024-deep Stack mirroring revm_interpreter::Stack. (~105 min)
  - *Mental model*: the EVM is a stack machine — every opcode pops its inputs and pushes its outputs from one
    LIFO stack of 256-bit words, capped at exactly 1024 entries. This `Stack` is the single most-touched data
    structure in the interpreter; a bounds bug here is a consensus bug everywhere.
  - *Contract*: `Stack` wraps a `Vec<U256>` (revm uses a fixed-capacity `Vec` pre-sized to 1024). Core ops:
    `push(&mut self, value: U256) -> Result<(), InstructionResult>`, `pop(&mut self) -> Result<U256, _>`,
    `peek(&self, depth: usize) -> Result<U256, _>`, `swap(&mut self, n: usize)`, `dup(&mut self, n: usize)`,
    `len(&self)`. Every fallible op returns `StackOverflow` / `StackUnderflow` rather than panicking.
  - **Expect to hit #1 — pushing past 1024**: a `push` that grows the `Vec` unconditionally. Symptom: a deep
    recursion / DUP-heavy contract grows the stack to 1025+ and your interpreter diverges from Geth, which
    halts with `StackOverflow` at exactly 1024.
    - Fix: `push` checks `len() == 1024` and returns `InstructionResult::StackOverflow` before inserting.
    - Muscle: the 1024 limit is a hard consensus rule, not a capacity hint. Reapplies at: W17 opcode expansion,
      W49 revm integration, W53 full opcode set.
  - **Expect to hit #2 — per-opcode underflow not checked**: relying on `Vec::pop()` returning `Option` but
    then unwrapping, or popping 2 items for ADD without first checking `len() >= 2`. Symptom: a panic
    (`called Option::unwrap on None`) on malformed bytecode instead of a clean `StackUnderflow` halt.
    - Fix: each opcode asserts its required min-stack-height up front (ADD needs 2, ADDMOD needs 3); `pop`
      itself also returns `Result`.
    - Muscle: every opcode declares a min-stack requirement and the dispatcher enforces it before the body
      runs. Reapplies at: W9 Mon arithmetic, W9 Tue comparison, W53 full opcode set.
  - **Expect to hit #3 — DUP/SWAP off-by-one indexing**: `DUP1` duplicates the *top* item (index `len-1`),
    `SWAP1` exchanges the top with the *second* item — but the opcode encodes `n` as 1-based. Symptom:
    `DUP2` duplicates the wrong word; arithmetic on swapped operands gives a wrong-but-plausible result that
    only a test vector catches.
    - Fix: `dup(n)` reads index `len - n` and pushes it; `swap(n)` exchanges `len-1` with `len-1-n`; unit-test
      `DUP1` and `SWAP1` against known bytecode.
    - Muscle: stack-relative opcodes are 1-based from the top — translate the index once, deliberately.
      Reapplies at: W17 opcode expansion, W53 full opcode set.
- [ ] **Build**: `crates/exec-vm/src/instructions/arithmetic.rs` — ADD, SUB, MUL, DIV, MOD. 3 gas/op. (~75 min)
  - *Mental model*: the five base arithmetic opcodes. Every one operates on 256-bit unsigned words with
    *wrapping* semantics — the EVM has no overflow trap, results silently wrap mod 2^256.
  - *Contract*: each opcode is `fn op(interp: &mut Interpreter, host: &mut dyn Host)` — pop two `U256`s, charge
    `gas::VERYLOW` (3), compute, push one `U256`. `ADD/SUB/MUL` wrap mod 2^256; `DIV`/`MOD` are unsigned;
    by-zero returns `0`.
  - **Expect to hit #1 — arithmetic that panics on overflow**: using `a + b` / `a * b` on `U256`. In debug
    builds this panics; in release it may wrap, masking the bug. Symptom: `attempt to add with overflow`
    panic on a contract that adds two large numbers — Geth just wraps.
    - Fix: always use `wrapping_add` / `wrapping_sub` / `wrapping_mul` — never the checked operators.
    - Muscle: EVM 256-bit arithmetic is wrapping by definition; the trapping operators are wrong here.
      Reapplies at: W9 Tue comparison, W17 ADDMOD/MULMOD/EXP, W53 SIGNEXTEND.
  - **Expect to hit #2 — DIV/MOD by zero traps instead of returning 0**: dividing by a zero divisor with
    `checked_div` and treating `None` as a halt. Symptom: a contract doing `x / 0` halts with an error;
    Geth pushes `0` and continues — a consensus divergence.
    - Fix: `if divisor.is_zero() { push 0 }` *before* the division; DIV-by-0 and MOD-by-0 both yield `0`,
      they are never an exceptional halt.
    - Muscle: EVM division by zero is defined to produce zero, not a trap. Reapplies at: W17 SDIV/SMOD,
      W17 ADDMOD/MULMOD, W53 full opcode set.
  - **Expect to hit #3 — operand pop order reversed for SUB/DIV**: SUB computes `a - b` where `a` is the
    *first* word popped (the top of stack) and `b` the second; getting it backwards is invisible for
    commutative ADD/MUL but wrong for SUB/DIV/MOD. Symptom: `5 SUB 3` yields `2^256 - 2` instead of `2`.
    - Fix: pop `a` (top) then `b`; compute `a - b`, `a / b`, `a % b` in that order; test SUB and DIV
      explicitly since ADD/MUL hide the bug.
    - Muscle: for non-commutative opcodes the first-popped word is the left operand. Reapplies at: W17 EXP,
      W17 SDIV/SMOD, W53 SHL/SHR/SAR.
- [ ] **Build**: `crates/exec-vm/src/interpreter/mod.rs` — Interpreter skeleton + step() dispatcher. (~105 min)
  - *Mental model*: the interpreter is the run loop — it holds the program counter, the bytecode, the stack,
    memory, and gas, and `step()` fetches one byte, dispatches to its opcode handler, and advances. This is
    revm's `Interpreter::step` shape.
  - *Contract*: `Interpreter { pc: usize, bytecode: Bytes, stack: Stack, memory: SharedMemory, gas: Gas,
    instruction_result: InstructionResult }`. `fn step(&mut self, host: &mut dyn Host)` fetches `bytecode[pc]`,
    looks it up in a `[fn; 256]` opcode table, runs the handler, and advances `pc`. `fn run(...)` loops `step`
    until `instruction_result` is set. Unknown bytes map to the INVALID handler.
  - *step, roughly*: (1) bounds-check `pc` against bytecode length (past-end = implicit STOP); (2) read
    `opcode = bytecode[pc]`; (3) `pc += 1`; (4) dispatch via the `[fn; 256]` table; (5) the handler mutates
    stack/gas/pc and may set `instruction_result`. Building the table so PUSH handlers can consume their
    immediate data correctly is the real exercise.
  - **Expect to hit #1 — `pc` advanced before vs after the handler**: incrementing `pc` after the handler
    runs, while JUMP's handler *sets* `pc` directly. Symptom: every JUMP lands one byte past its target;
    JUMPDEST validation passes but execution starts mid-opcode.
    - Fix: advance `pc` by 1 *before* dispatch (or have each handler own its own advance); JUMP/JUMPI then
      set `pc` absolutely and the loop must not re-increment it.
    - Muscle: exactly one place advances `pc` per step — control-flow opcodes and the loop must agree.
      Reapplies at: W9 Tue control flow, W15 EOF parser, W53 full opcode set.
  - **Expect to hit #2 — PUSH immediate data executed as opcodes**: a `match`-based dispatch that handles
    PUSH but forgets PUSH consumes the next 1-32 bytes as data. Symptom: `PUSH1 0x60` — the `0x60` is read
    on the next step as another PUSH1 opcode; the whole instruction stream desyncs.
    - Fix: the PUSHn handler reads `n` immediate bytes from `bytecode[pc..pc+n]` and advances `pc` past them.
    - Muscle: PUSH data is inline in the bytecode — the decoder, not the run loop, must skip it. Reapplies at:
      W9 Tue JUMPDEST analysis, W15 EOF parser.
  - **Expect to hit #3 — running off the end of bytecode**: indexing `bytecode[pc]` when `pc` reaches the
    end. Symptom: a panic (`index out of bounds`) on any bytecode that doesn't end in an explicit STOP —
    the EVM treats running past the end as an implicit STOP.
    - Fix: `step` checks `pc >= bytecode.len()` and sets `instruction_result = Stop` before indexing.
    - Muscle: falling off the end of bytecode is a clean STOP, never a panic. Reapplies at: W15 EOF parser,
      W53 full opcode set.

**Tuesday — `SharedMemory` + control flow**

- [ ] **Build**: `crates/exec-vm/src/interpreter/memory.rs` — SharedMemory. mload/mstore/mstore8/resize with quadratic
  gas. (~105 min)
  - *Mental model*: EVM memory is a flat, byte-addressable, zero-initialized array that grows on demand.
    Growth is *not free* — expanding it costs gas that grows quadratically, so a contract can't cheaply
    allocate gigabytes. `SharedMemory` is reth/revm's name for one buffer reused across nested call frames.
  - *Contract*: `SharedMemory` wraps a `Vec<u8>`. `mload(offset) -> U256` reads 32 bytes; `mstore(offset,
    value: U256)` writes 32 bytes; `mstore8(offset, byte)` writes 1 byte. A `resize(new_len)` /
    `expansion_cost(offset, size) -> u64` helper rounds the requested end up to a word boundary and computes
    the marginal gas. Memory length is always a multiple of 32.
  - *expansion gas, roughly*: (1) compute `new_size_words = ceil((offset + size) / 32)`; (2) if
    `new_size_words <= current_size_words`, cost is 0; (3) else `cost(w) = 3*w + w*w/512`, and charge
    `cost(new) - cost(current)`. Charging the *marginal* delta — and charging it before the buffer is
    touched — is the real exercise.
  - **Expect to hit #1 — gas charged after the access (or not word-rounded)**: writing to memory, then
    computing expansion cost from the new length; or charging for `offset+size` bytes without rounding up to
    a 32-byte word. Symptom: a contract that should run out of gas mid-MSTORE instead completes; or gas usage
    is off by a few units versus Geth on any non-word-aligned access.
    - Fix: compute the word-rounded `new_size`, charge the marginal expansion gas, *then* resize and write —
      if the gas charge fails the buffer must never have grown.
    - Muscle: memory expansion gas is charged before the access, on word-rounded sizes. Reapplies at: W9 Wed
      Gas accounting, W17 CALLDATACOPY/CODECOPY, W53 MCOPY.
  - **Expect to hit #2 — quadratic term overflow / wrong divisor**: computing `w*w` where `w` is large enough
    to overflow `u64`, or using the wrong constant (it is `w*w/512`, not `/1024` or `/256`). Symptom: a
    huge memory offset panics with multiply overflow, or gas is consistently double/half of Geth's.
    - Fix: cap the offset/size against the gas limit early (an offset that can't be paid for is an
      out-of-gas halt), and hard-code `cost(w) = 3*w + w*w/512` exactly per the Yellow Paper.
    - Muscle: gas formulas are exact constants from the spec — no approximations, and bound the inputs.
      Reapplies at: W9 Wed Gas, W17 EXP dynamic gas, W53 KECCAK256 word gas.
  - **Expect to hit #3 — out-of-bounds read returns garbage instead of zero**: `mload` past the current
    memory length reading uninitialized or stale bytes. Symptom: an MLOAD just past the high-water mark
    returns nonzero — EVM memory is defined to be zero everywhere it hasn't been written.
    - Fix: any access first resizes the buffer (zero-filling the gap) so every in-range read sees defined,
      zeroed bytes; reads never touch beyond the resized length.
    - Muscle: EVM memory reads always see zeros outside written regions — resize-then-access. Reapplies at:
      W17 RETURNDATACOPY, W53 MCOPY, W49 revm integration.
- [ ] **Build**: `crates/exec-vm/src/instructions/control.rs` — JUMP, JUMPI, JUMPDEST, PC, STOP, INVALID. (~75 min)
  - *Mental model*: the control-flow opcodes. JUMP/JUMPI move the program counter; a jump is only legal if
    its target is a `JUMPDEST` byte (`0x5b`) that the EVM has pre-validated by scanning the bytecode.
  - *Contract*: handlers for `JUMP` (pop target, set `pc`), `JUMPI` (pop target + condition, jump only if
    condition ≠ 0), `JUMPDEST` (no-op, charges 1 gas), `PC` (push current `pc`), `STOP` (set
    `InstructionResult::Stop`), `INVALID` (set `InstructionResult::InvalidFEOpcode`, consume all gas). Needs
    a `jump_table: BitVec` / `[bool]` built once over the bytecode marking valid JUMPDEST positions.
  - **Expect to hit #1 — a JUMPDEST byte inside PUSH data treated as a valid target**: scanning the bytecode
    byte-by-byte for `0x5b` without skipping PUSH immediate data. Symptom: `PUSH1 0x5b` — the `0x5b` is data,
    not an opcode, but your jump table marks it valid; a JUMP there lands mid-instruction and Geth rejects it
    with `BadJumpDestination`. Direct consensus split.
    - Fix: the validity scan walks opcodes; on `PUSHn` it advances the cursor by `n+1` so immediate bytes are
      never inspected — only real `0x5b` *opcodes* get marked.
    - Muscle: JUMPDEST analysis must skip PUSH data — a `0x5b` in an immediate is not a jump target.
      Reapplies at: W15 EOF code-section validation, W53 full opcode set, W49 revm integration.
  - **Expect to hit #2 — jumping to an unmarked / out-of-range target**: setting `pc` from the popped value
    without checking the jump table, or without bounds-checking against bytecode length. Symptom: a contract
    jumps into the middle of an opcode or past the end, executing garbage instead of halting with
    `InvalidJump`.
    - Fix: JUMP/JUMPI verify `target < bytecode.len()` *and* `jump_table[target]` is true; otherwise set
      `InstructionResult::InvalidJump` and halt.
    - Muscle: every jump target is validated against the precomputed JUMPDEST set before `pc` moves.
      Reapplies at: W15 EOF relative jumps (RJUMP), W53 full opcode set.
  - **Expect to hit #3 — JUMPI condition / counter not re-incremented**: JUMPI with a zero condition forgets
    to fall through (leaves `pc` unchanged so the loop never advances), or a taken JUMP gets its `pc`
    re-incremented by the run loop's own `pc += 1`. Symptom: an infinite loop on a not-taken JUMPI, or every
    jump landing one byte off.
    - Fix: JUMPI with condition 0 advances `pc` past itself like a normal opcode; a *taken* jump sets `pc`
      absolutely and signals the loop not to re-increment (consistent with Mon's `step` decision).
    - Muscle: control-flow opcodes own their `pc` update entirely — taken and not-taken paths both explicit.
      Reapplies at: W9 Mon step dispatcher, W15 EOF control flow.
- [ ] **Build**: `crates/exec-vm/src/instructions/comparison.rs` — LT, GT, SLT, SGT, EQ, ISZERO, AND, OR, XOR, NOT. (~75 min)
  - *Mental model*: the comparison and bitwise opcodes. They split into *unsigned* (LT/GT) and *signed*
    (SLT/SGT) — the EVM has no separate signed type, so signed ops reinterpret the same 256-bit word as
    two's-complement. Booleans are returned as `U256` 0 or 1.
  - *Contract*: each opcode pops 1-2 `U256`s, charges `gas::VERYLOW` (3), pushes a `U256`. LT/GT/EQ/ISZERO
    push `0` or `1`. SLT/SGT interpret operands as two's-complement signed 256-bit. AND/OR/XOR/NOT are plain
    bitwise; NOT is unary.
  - **Expect to hit #1 — SLT/SGT done with unsigned comparison**: implementing SLT as plain `a < b` on
    `U256`. Symptom: `-1 SLT 0` returns `0` (false) because as unsigned, `-1` is `2^256-1` which is the
    *largest* value — the signed comparison is inverted for any negative operand.
    - Fix: convert both words to a signed representation (e.g. `I256` / sign-aware compare): test each
      operand's top bit, and order negatives before positives.
    - Muscle: signed EVM opcodes must reinterpret the word as two's-complement — never reuse the unsigned
      compare. Reapplies at: W17 SDIV/SMOD, W53 SAR, W53 SIGNEXTEND.
  - **Expect to hit #2 — ISZERO / boolean result not normalized to 0/1**: ISZERO pushing the operand itself,
    or EQ pushing a bitmask. Symptom: a JUMPI fed by a comparison takes the branch on a "truthy" nonzero
    that isn't `1`; subtle, since JUMPI treats anything nonzero as true but later `EQ` chains break.
    - Fix: every comparison opcode pushes exactly `U256::from(0)` or `U256::from(1)` — a canonical boolean.
    - Muscle: EVM comparison opcodes yield a canonical 0/1, not an arbitrary truthy value. Reapplies at:
      W9 Tue control flow JUMPI, W53 full opcode set.
  - **Expect to hit #3 — operand order swapped for LT/GT/SLT/SGT**: like SUB, these are non-commutative —
    `LT` is `a < b` where `a` is the *first* word popped. Reversing it turns LT into GT. Symptom: every
    loop-bound check runs backwards; a `for` loop in Solidity bytecode never terminates or never starts.
    - Fix: pop `a` (top) then `b`; compute `a < b` for LT, `a > b` for GT; test against known bytecode since
      EQ/AND/OR/XOR hide the bug.
    - Muscle: comparison opcodes are non-commutative — first-popped is the left operand. Reapplies at:
      W9 Mon SUB/DIV, W53 SHL/SHR/SAR.

- [ ] **Build**: `crates/exec-vm/src/interpreter/gas.rs` — Gas { limit, remaining, refunded }. (~105 min)
  - *Mental model*: gas is the EVM's metering and DoS-prevention mechanism — every opcode costs gas, and
    execution halts the instant it runs out. `Gas` is the accumulator the whole interpreter charges against;
    it also tracks *refunds* (gas given back for, e.g., clearing storage), which are applied only at the end.
  - *Contract*: `Gas { limit: u64, remaining: u64, refunded: i64 }`. `fn record_cost(&mut self, cost: u64)
    -> bool` subtracts and returns `false` (out-of-gas) if it would underflow; `fn spent(&self) -> u64` =
    `limit - remaining`; `fn record_refund(&mut self, amount: i64)`; `fn erase_cost` for restoring on a
    failed sub-charge. Refund is `i64` because SSTORE can subtract refund.
  - **Expect to hit #1 — out-of-gas detected by underflow panic**: `remaining -= cost` on a `u64` when
    `cost > remaining`. Symptom: a debug-build panic (`attempt to subtract with overflow`) on any contract
    that exhausts its gas — out-of-gas is a *normal*, expected halt, not a crash.
    - Fix: `record_cost` does a `checked_sub`; on `None` it leaves `remaining` untouched and returns `false`,
      and the caller sets `InstructionResult::OutOfGas`.
    - Muscle: out-of-gas is a checked, expected control-flow outcome — never an arithmetic panic. Reapplies
      at: W9 Wed host opcodes, W17 dynamic-gas opcodes, W53 full opcode set.
  - **Expect to hit #2 — charging gas after the opcode's effect**: an opcode mutates the stack/memory/state
    and *then* calls `record_cost`. Symptom: a contract that should out-of-gas mid-opcode instead completes
    its effect, leaving an inconsistent half-applied state versus Geth.
    - Fix: charge first; if `record_cost` returns `false`, halt before doing any work — gas is a gate, not a
      receipt.
    - Muscle: gas is charged before the effect; a failed charge means nothing happened. Reapplies at: W9 Tue
      memory expansion, W9 Wed SSTORE, W53 full opcode set.
  - **Expect to hit #3 — refund applied immediately or uncapped**: subtracting an SSTORE refund from
    `remaining` mid-execution, or applying the full refund at the end without the cap. Symptom: a contract
    that clears storage appears to *gain* spendable gas mid-run; or the transaction's final gas is too low
    because the refund cap (post-London: `gas_used / 5`) wasn't applied.
    - Fix: accumulate into `refunded` only; apply it once at transaction end, capped at `spent / 5` (EIP-3529).
    - Muscle: refunds accrue separately and are applied once, capped, at the end. Reapplies at: W9 Wed SSTORE,
      W17 SELFDESTRUCT, W50 revm journaling.
- [ ] **Build**: `crates/exec-vm/src/instructions/host.rs` — SSTORE, SLOAD, BALANCE, EXTCODESIZE. `Host` trait
  delegating to eth_storage_cache::StateCache. (~75 min)
  - *Mental model*: opcodes that touch *world state* (storage slots, account balances, code) can't read it
    directly — they go through a `Host` trait. This is revm's design: the interpreter is pure compute; the
    `Host` is the outside world, so the same interpreter runs over a real DB, a test fixture, or a mock.
  - *Contract*: `trait Host` (object-safe — used as `&mut dyn Host`) with `sload(addr, key) -> (U256,
    is_cold)`, `sstore(addr, key, value) -> SStoreResult`, `balance(addr) -> (U256, is_cold)`,
    `code_size(addr) -> (usize, is_cold)`. The four opcode handlers pop their args, call the `Host`, charge
    gas (including the cold/warm surcharge), and push the result. `Host` delegates to
    `eth_storage_cache::StateCache`.
  - **Expect to hit #1 — `Host` made generic instead of a trait object**: declaring handlers as
    `fn op<H: Host>(...)`, so the opcode table can't be a uniform `[fn; 256]`. Symptom: the dispatch table
    won't compile — each monomorphized handler has a different type; or `Box<dyn Host>` is impossible
    because a generic method broke object safety.
    - Fix: `Host` methods take/return only object-safe types; handlers take `&mut dyn Host` (same lesson as
      W5's `Encodable` object-safety pitfall).
    - Muscle: the `Host` boundary must stay object-safe so one interpreter serves every backend. Reapplies
      at: W49 revm integration, W50 journaling, W53 full opcode set.
  - **Expect to hit #2 — cold/warm access surcharge missing**: charging a flat cost for SLOAD/BALANCE/
    EXTCODESIZE. Symptom: post-Berlin (EIP-2929) the *first* access to a slot/account costs 2100/2600 gas,
    later accesses 100; a flat charge mismatches Geth on the second-and-later access — wrong gas, wrong
