- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/reactor.rs` — `Reactor { epoll_fd, ready_queue: SegQueue<Task>, timer_wheel }`. epoll-based event loop. (~120 min)
  - **Why**: Thread-per-core runtimes (Seastar, glommio, monoio) pin one OS thread per CPU and never share work across threads, eliminating cross-core cache traffic and synchronization overhead. The reactor is the per-shard event loop: epoll for I/O, hashed timer wheel for timeouts, lock-free SegQueue for inter-shard messages. This is HFT/matching-engine substrate — under µs-latency budgets, even a single lock crosses the line.
  - **Read first**: Seastar `src/core/reactor.cc` (esp. `reactor::run` and `reactor::poll_once`); glommio `src/sys/source.rs`; monoio reactor implementation.
  - **Design**:
    ```rust
    pub struct Reactor {
        epoll_fd: RawFd,
        ready_queue: VecDeque<Task>, // task ready to run; not shared
        cross_shard_inbox: SegQueue<Task>, // SPSC from other shards
        timer_wheel: HashedTimerWheel,
        shard_id: ShardId,
    }
    impl Reactor {
        pub fn run(&mut self);
        pub fn register_fd(&mut self, fd: RawFd, interest: EpollFlags, waker: Waker);
        pub fn schedule(&mut self, t: Task);
        pub fn schedule_remote(&self, shard: ShardId, t: Task);
    }
    ```
    **Invariants**:
    - `ready_queue` is shard-local; never touched from other threads.
    - `cross_shard_inbox` is SPMC (multiple producers from other shards, single consumer = this shard).
    - epoll wait time is dynamically computed from timer_wheel head.
  - **Build steps**:
    1. (~25 min) `epoll_create1`, `epoll_ctl_add`; basic registration.
    2. (~30 min) Run loop: drain `cross_shard_inbox` → ready; epoll_wait (with timeout = next timer); process events into ready; pop ready → poll task.
    3. (~25 min) Hashed timer wheel (W14 time crate's wheel if available; otherwise simple O(1) insert/expire).
    4. (~25 min) Wake mechanism: arming a fd readiness causes its registered waker to push to ready.
    5. (~15 min) Test: spawn 100k tasks sleeping 1ms across 4 shards; wall-time < 50ms (concurrency proves out).
  - **Pitfalls**:
    - *Cross-shard wake via syscall*: pushing to remote reactor needs to wake it (it's blocked in epoll_wait). **Symptom**: tasks queued but never run. **Fix**: each shard has a self-pipe or `eventfd`; remote producer writes 1 byte to wake the consumer's epoll.
    - *Spurious wake amplification*: every cross-shard message writes to eventfd → epoll_wait wakes for each. **Symptom**: high syscall rate. **Fix**: drain eventfd to 0 after first read; multiple inflight wakes coalesce.
    - *Timer wheel granularity*: too coarse → poor timer precision; too fine → memory. **Fix**: hashed wheel with cascading; 1ms tick is the sweet spot for ms-scale waits.
    - *Task accidentally Send-bound*: if Task: Send, you might cross threads. Thread-per-core wants Task: !Send. **Fix**: enforce !Send in type system; cross-shard uses a Send "envelope" that re-wraps a !Send Task on the destination.
  - **Test scenarios**:
    - 100k tasks × 4 shards sleeping 1ms; wall-time < 50ms (epoll batches efficiently).
    - Cross-shard ping-pong: 1M roundtrips in < 1s (per-roundtrip < 1µs).
    - Stress: every shard at 100% CPU; no shard starves another.
  - **Acceptance**: per-shard 100k tasks/sec scheduling overhead; cross-shard rtt < 1µs.
  - **Downstream**: futures executor (Wed); submit_to (W44); matching-engine reactor backbone (W58+).

- [ ] [NEW v2] **Build**: `crates/runtime-thread-per-core/src/scheduler.rs` — local `LocalExecutor` per shard. No-std futures over a `Waker` that pushes tasks to mailbox. (~150 min)
  - **Why**: A LocalExecutor drives `!Send` futures on one thread. The Waker, when called, schedules the task back into the local ready queue (no cross-thread atomics). This is the perf differentiator vs Tokio's work-stealing — predictable µs latency vs avg-ms-with-tail-spikes throughput.
  - **Read first**: glommio `src/executor.rs`; Tokio's `LocalSet` for contrast; `futures-task` Waker design.
  - **Design**:
    ```rust
    pub struct LocalExecutor {
        reactor: Reactor,
        tasks: Slab<TaskInner>, // task id -> task
    }
    struct TaskInner {
        future: Pin<Box<dyn Future<Output = ()> + 'static>>, // !Send by default
        ready: bool,
    }
    pub fn spawn_local<F: Future<Output = T> + 'static>(f: F) -> JoinHandle<T>;
    pub fn submit_to<F, R>(shard: ShardId, f: F) -> JoinHandle<R>
        where F: FnOnce() -> R + Send + 'static, R: Send + 'static;
    ```
    **Invariants**:
    - LocalExecutor is `!Sync` and `!Send`.
    - Waker for a local task captures only `task_id` + a raw pointer to the executor's ready queue (no Arc).
    - Cross-shard submit serializes via a Send-bounded closure; result returned via oneshot.
  - **Build steps**:
    1. (~30 min) `TaskInner` slab; `spawn_local` allocates a TaskInner, sets ready=true, pushes to ready_queue.
    2. (~40 min) Waker impl: when called, sets `ready=true` on the TaskInner and pushes to ready_queue.
    3. (~30 min) Poll loop integration with reactor: ready_queue drained each tick; `future.as_mut().poll(&mut cx)` with a fresh Waker.
    4. (~30 min) `submit_to` for cross-shard: serializes closure via Box<dyn FnOnce() + Send>; receiving shard re-wraps as a local task.
    5. (~15 min) JoinHandle: oneshot channel between task and awaiter.
    6. (~5 min) Test as below.
  - **Pitfalls**:
    - *Waker outlives executor*: Waker holds raw pointer to executor; executor shutdown leaves Waker dangling. **Symptom**: UAF on late wake. **Fix**: Waker holds an Arc<TaskState> with a flag; shutdown atomically invalidates.
    - *Poll re-entrance*: a future's poll calls into another spawn_local that immediately schedules and runs synchronously; stack overflow. **Fix**: spawn_local enqueues only; poll is yielded to next loop iteration.
    - *Cross-shard latency*: submit_to that allocates an Arc + heap-boxed closure adds overhead. **Fix**: use a typed enum for common cross-shard messages; heap only as fallback.
  - **Test scenarios**:
    - Same-shard spawn + await: 1M roundtrips in < 100ms.
    - Cross-shard submit_to: rtt < 1µs.
    - Miri: no UAF on shutdown with pending Wakers.
  - **Acceptance**: 1M spawn_local/sec per shard; cross-shard submit_to rtt < 1µs.
