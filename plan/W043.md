  - 🔧 **Why this matters**: thread-per-core eliminates cross-core sync overhead; the reactor is the per-shard
    event loop. Cross-shard wake via syscall → tasks queued but never run (hang). Spurious wake amplification
    → high syscall rate (CPU burn). Task accidentally Send-bound → cross-thread leak. Downstream W44
    submit_to, W58+ matching-engine backbone inherit.

  #### Phase 1 — Problem, requirements, design (~40 min, no code yet)

  - **The problem this primitive solves**: one OS thread per CPU, no work-sharing across threads. The
    reactor multiplexes I/O (epoll) + timers (timer wheel) + inter-shard messages (SegQueue + eventfd
    wake). Sub-µs latency budget = no shared locks.

  - **Requirements** — write in `crates/runtime-thread-per-core/notes/43_reactor_design.md`:
    - R1. `ready_queue: VecDeque` shard-local; never shared.
    - R2. `cross_shard_inbox: SegQueue` multi-producer single-consumer (MPSC).
    - R3. **Cross-shard wake via eventfd**: producer writes 1 byte; consumer's epoll_wait returns; consumer
      reads eventfd (to clear) + drains inbox.
    - R4. **Wake coalescing**: drain eventfd to 0 after first read; multiple inflight wakes merge to one
      epoll_wait return.
    - R5. **Task is `!Send`**; cross-shard messages use a Send envelope that re-wraps as !Send on the
      destination.
    - R6. **Hashed timer wheel** (1 ms tick) — O(1) insert/expire; cascading for long timers.
    - R7. epoll wait time dynamically computed from timer wheel head.
    - R8. Per-shard 100 k tasks/sec scheduling; cross-shard rtt < 1 µs.

  - **Design walk-through** — answer each:
    - D1. Why `VecDeque` for ready_queue (not SegQueue)? It's shard-local — what does that buy?
    - D2. eventfd wake: write the producer and consumer sides. Why eventfd over pipe (cite cost)?
    - D3. Spurious wake amplification trace: 100 cross-shard messages → 100 eventfd writes → 100
      epoll_wait wakes (vs 1). What does drain-to-zero do?
    - D4. Task !Send enforcement: write the type-system constraint. What's the Send envelope pattern?
    - D5. Timer wheel: write the hash function. When does cascading fire?
    - D6. **Pre-mortem (load-bearing)**: write the "tasks queued but never run" trace where producer
      pushes to inbox without eventfd wake; consumer blocked in epoll_wait forever. Then write the
      Send-bound leak where Task is accidentally Send and ends up on the wrong thread's queue.

  #### Phase 3 — Make the tests pass, one failure at a time (~105 min)

  - **When `reactor_cross_shard_rtt_under_1us` reports tasks queued but never run:**
    - Symptom: producer shard pushes a task to destination's `cross_shard_inbox`; destination is in
      `epoll_wait` and never wakes; tasks accumulate; test hangs.
    - Why: cross-shard wake via syscall — pushing to remote reactor needs to wake it (it's blocked in
      epoll_wait). Without an explicit wake, the consumer never returns from epoll.
    - Fix: each shard has a self-pipe or `eventfd`; remote producer writes 1 byte to wake the
      consumer's epoll. Sequence: `cross_shard_inbox.push(task); eventfd.write(&1u64);`. Consumer:
      `epoll_wait returns → read(eventfd) → drain(cross_shard_inbox)`.
    - Muscle: any blocking primitive (epoll, futex, condvar) needs an explicit wake source for
      cross-thread producers; "push only" doesn't unblock. Reapplies at: W11 MPMC condvar wake,
      W26 WAL group commit Notify wake.

  - **When `bench_reactor_no_spurious_wake_amplification` reports 100 syscalls per 100 sends:**
    - Symptom: 100 cross-shard messages → 100 eventfd writes → 100 epoll_wait wakes; syscall rate
      under burst saturates one CPU on epoll_wait + read.
    - Why: every cross-shard message writes to eventfd → epoll_wait wakes for each.
    - Fix: drain eventfd to 0 after first read; multiple inflight wakes coalesce. Sequence: epoll_wait
      returns → `let n = read(eventfd, &mut buf)` (returns total count); single drain loop processes
      all pending. Subsequent producer writes during drain bump the counter again; next epoll_wait
      catches them.
    - Muscle: any signal-coalescing primitive (eventfd, signalfd) MUST drain in one read to amortize
      syscall cost. Reapplies at: W44 submit_to wake batching, W77 messaging-aeron credit-grant
      wake.

  - **When `reactor_task_not_send_compile_fail` PASSES (Task is accidentally Send):**
    - Symptom: a `Task<Future<Output = ()> + Send>` compiles when assigned to the shard-local
      `ready_queue`; downstream code can mistakenly cross-thread without going through the envelope.
    - Why: Task accidentally Send-bound — if Task: Send, you might cross threads. Thread-per-core
      wants Task: !Send.
    - Fix: enforce !Send in type system; cross-shard uses a Send "envelope" that re-wraps a !Send
      Task on the destination. `pub struct Task(Box<dyn Future<Output=()> + 'static>);` (no Send
      bound); `pub struct CrossShardEnvelope(Box<dyn FnOnce() -> Task + Send + 'static>);` — the
      envelope is Send, the closure runs on the dest shard to produce the !Send Task.
    - Muscle: thread-per-core type discipline requires `!Send` Tasks + explicit Send envelopes;
      auto-derive can leak Send. Reapplies at: W44 submit_to type bounds, W58 matching-engine
      symbol-shard.

  - **When `reactor_timer_precision_under_2ms` reports ~10 ms jitter:**
    - Symptom: timer fires anywhere from 10 ms to 20 ms after scheduled; expected ≤ 12 ms (10 ms +
      1 ms tick).
    - Why: timer wheel granularity too coarse OR cascading not implemented.
    - Fix: hashed wheel with cascading; 1 ms tick is the sweet spot for ms-scale waits. For waits >
      256 ms, cascade to a higher wheel; for waits < 1 ms, busy-spin (sub-millisecond accuracy isn't
      reachable via epoll_wait timeout).
    - Muscle: timer wheel design = tick interval × levels; precision is bounded by tick.
      Reapplies at: W14 time crate Hlc, W77 aeron flow-control timeouts.

  - **5-year failure mode** (write in `notes/43_reactor_followup.md` after green): when io_uring +
    eventfd-via-io_uring becomes standard, eventfd round-trips drop further. State migration: route
    cross-shard wake through io_uring SQE; trigger when io_uring proves faster than current epoll +
    eventfd path on benchmarks.

  #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

  - **When `scheduler_late_waker_after_shutdown_no_uaf` reports UAF on late wake:**
    - Symptom: task spawns, yields awaiting I/O; executor shut down (Drop); external I/O source fires
      the Waker (it still has the raw pointer); miri "use after free" on the task slot.
    - Why: Waker holds raw pointer to executor; executor shutdown leaves Waker dangling. UAF on late
      wake.
    - Fix: Waker holds an `Arc<TaskState>` with a flag; shutdown atomically invalidates. The Waker's
      wake() function checks `if state.live.load(Acquire) { ... }` before touching the executor; if
      not live, the wake is a no-op. Shutdown sets `live.store(false, Release)` for every TaskState
      before dropping the executor.
    - Muscle: any cross-lifetime reference (raw pointer) needs an explicit liveness check at the
      callee side; shutdown must invalidate before dropping. Reapplies at: W44 submit_to JoinHandle
      lifecycle, W58 matching-engine subscription cleanup.

  - **When `scheduler_recursive_spawn_no_stack_overflow` reports stack overflow:**
    - Symptom: deeply nested `spawn_local` chain → stack overflow at ~10k depth.
    - Why: poll re-entrance — a future's poll calls into another spawn_local that immediately
      schedules AND RUNS synchronously; the stack grows per spawn.
    - Fix: spawn_local enqueues only; poll is yielded to next loop iteration. spawn_local pushes the
      new TaskInner to ready_queue and returns immediately; the new task runs on a later iteration
      of the event loop.
    - Muscle: scheduler primitives must enqueue, never invoke synchronously; sync invocation is a
      stack-overflow time bomb. Reapplies at: W44 submit_to scheduling, W58 matching-engine
      event-driven order processing.

  - **When `bench_scheduler_cross_shard_typed_no_alloc` reports allocations per cross-shard message:**
    - Symptom: every submit_to allocates a `Box<dyn FnOnce() + Send>` ≈ 50 ns; at 1 M/sec ≈ 50 ms/sec
      CPU on allocator; cross-shard rtt rises from ~800 ns to ~1.2 µs.
    - Why: cross-shard latency — submit_to that allocates an Arc + heap-boxed closure adds overhead.
    - Fix: use a typed enum for common cross-shard messages; heap only as fallback. `enum CrossShardMsg
      { Ping, Signal(SignalKind), Data(u64), Boxed(Box<dyn FnOnce() + Send>) }`. Common messages
      (ping, signal, fixed-size data) are stack-allocated in the enum; only arbitrary closures pay
      the Box cost.
    - Muscle: cross-thread channels' messages should be typed enums with a "fallback Box" for
      arbitrary; pure-Box channels pay alloc on every message. Reapplies at: W44 submit_to common
      messages, W58 matching-engine event channel.

  - **5-year failure mode** (write in `notes/43_scheduler_followup.md` after green): when async-await
    overhead reaches zero (compiler-state-machine optimizations), the LocalExecutor's slab + Waker
    machinery can shrink. State migration: when zero-overhead async-await stabilizes, audit the slab
    overhead; consider stackful coroutines if perf-bound.
