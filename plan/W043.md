    - *Mental model*: a Reactor is the single-threaded `while running { epoll_wait(timeout); drain_io(); drain_cross_shard(); fire_timers(); run_ready_queue(); }` loop pinned to one core. Shard-local work never touches an atomic; the *only* cross-core path is the `SegQueue` inbox + an `eventfd` doorbell to break the consumer out of `epoll_wait`.

    - *Contract*: 
      ```rust
      pub struct Reactor { /* epoll_fd: RawFd, eventfd: RawFd, ready_queue: VecDeque<Task>,
                             cross_shard_inbox: SegQueue<Task>, timer_wheel: TimerWheel */ }
      impl Reactor {
          pub fn new(shard_id: usize) -> io::Result<Self>;
          pub fn run(&mut self);                                   // the event loop; returns on stop()
          pub fn wake_handle(&self) -> WakeHandle;                 // Send; holds eventfd dup + inbox ref
          pub fn schedule_local(&mut self, t: Task);              // shard-local enqueue (no atomics)
          pub fn add_timer(&mut self, dur: Duration, t: Task);
      }
      pub struct Task(Box<dyn FnOnce() + 'static>);                // NOTE: no Send bound — !Send by design
      pub struct WakeHandle { /* eventfd_dup: RawFd, inbox: Arc<SegQueue<...>> */ }  // Send + Sync
      ```
      Never write the loop body or the wake sequence here — that's Phase 3.

    - *Back-of-envelope* (bar (c)): per-shard target 100k tasks/sec → 10 µs/task budget; cross-shard rtt target < 1 µs. Jeff-Dean anchors: a syscall ≈ 300 ns, so a *naive* wake (1 `write(eventfd)` + 1 `read(eventfd)` + 1 `epoll_wait` return) ≈ 3 × 300 ns ≈ 900 ns — already at the rtt cliff. The cliff ratio that bites: **100 cross-shard sends with per-message wake = 100 × 900 ns ≈ 90 µs of pure syscall; the same 100 sends with a coalesced single drain ≈ 1 × 900 ns ≈ 0.9 µs — a 100× syscall reduction.** A shard-local `VecDeque::push_back` is ~1-3 ns (no atomic, no syscall) vs a `SegQueue::push` ~25-40 ns (atomic CAS + possible alloc) — that is why R1 keeps the ready_queue local and only the inbox is concurrent. Timer-wheel insert is O(1) ~5 ns vs a `BinaryHeap` push O(log n) ~50 ns at 10k timers.

    - **Requirements** R1–R8 — write in `crates/runtime-thread-per-core/notes/43_reactor_design.md`:
      - R1. `ready_queue: VecDeque<Task>` is **shard-local**; never shared, never atomic. (Buys ~25 ns/op vs SegQueue.)
      - R2. `cross_shard_inbox: SegQueue<Task>` is the **single** MPSC path (many producers, one consumer = this shard).
      - R3. **Cross-shard wake via eventfd**: producer `inbox.push(task); write(eventfd, &1u64)`; consumer's `epoll_wait` returns → `read(eventfd)` to clear → `drain(inbox)`.
      - R4. **Wake coalescing**: a single `read(eventfd)` returns the summed counter; multiple inflight wakes merge to one `epoll_wait` return + one drain.
      - R5. **`Task` is `!Send`**; cross-shard messages travel as a `Send` envelope (`Box<dyn FnOnce()->Task + Send>`) that re-wraps a `!Send` `Task` on the destination.
      - R6. **Hashed timer wheel** (1 ms tick): O(1) insert/expire; cascade long timers (> wheel span) down a level.
      - R7. `epoll_wait` timeout is computed from the timer-wheel head (sleep exactly until the next timer or I/O).
      - R8. Per-shard ≥ 100k tasks/sec scheduling; cross-shard rtt < 1 µs.

    - **Design walk-through** D1–D6 — answer each in the design doc; *no peeking* at Seastar/Glommio source until Phase 3:
      - D1. Property table — enumerate every wake primitive and pick one:
        | primitive | wakes epoll? | syscalls/wake | coalesces? | bytes |
        |---|---|---|---|---|
        | `eventfd` (EFD_NONBLOCK) | yes (in epoll set) | 1 write / 1 read | yes (counter sums) | 8 |
        | self-pipe (`pipe2`) | yes | 1 write / N reads | no (must drain N bytes) | 1/wake |
        | `signalfd` | yes | 1 / 1 | partial | varies |
        | spin on inbox flag | no (epoll still sleeps) | 0 | — | — |
        Justify eventfd: 8-byte counter that sums, single `read` drains all pending → R4.
      - D2. Write the producer side and consumer side of the wake (the *exact* syscall order). Why eventfd over a self-pipe? (Self-pipe needs N reads to drain N wakes; eventfd's counter coalesces to one read — cite R4.)
      - D3. **Spurious-wake amplification trace** (load-bearing): 100 cross-shard messages → if each does `write(eventfd)` and the consumer does one `read` per `epoll_wait` return without draining the inbox fully, you get 100 `epoll_wait` returns. Write the 5-line trace, then write what drain-to-zero (R4) changes.
      - D4. `Task` `!Send` enforcement: write the type-system constraint (`Task(Box<dyn FnOnce() + 'static>)` with **no** `Send` bound). Write the `Send` envelope pattern (`CrossShardEnvelope(Box<dyn FnOnce()->Task + Send>)`) and explain why the *envelope* is Send but the *Task* it produces is not.

      - D6. **Pre-mortem (load-bearing)** — write the EXACT bad interleavings:

    #### Phase 3 — Make the tests pass, one failure at a time (~70 min)

    Read each card *after* you've seen the failure. Newbie first, expert last.

    - **(SENIOR) When `reactor_cross_shard_push_without_wake_hangs_then_passes` hangs (times out):**
      - Symptom: shard 0 `inbox.push(task)` succeeds; shard 1 sits in `epoll_wait(-1)`; `ran` never flips; test killed by CI timeout.
      - Why: pushing to a remote inbox does not wake a thread blocked in `epoll_wait` — the inbox isn't in the epoll set. "Push-only" never unblocks a sleeping consumer.
      - Fix: register `eventfd` in shard 1's epoll set; producer does `inbox.push(task); write(eventfd, &1u64)`; consumer on `epoll_wait` return does `read(eventfd); drain(inbox)`.
      - Cost avoided: **infinite hang (bar (c) liveness violation)** — not "slow," *dead*. Every downstream shard service (matching-engine, ledger) inherits this loop; the bug would deadlock all of them.
      - Muscle: any blocking primitive (epoll, futex, condvar) needs an explicit wake source for cross-thread producers; "push only" doesn't unblock. **Reapplies at: W11 MPMC condvar wake, W26 WAL group-commit Notify wake, W44 submit_to remote wake, W74 matching-engine cross-shard order routing.**

    - **(EXPERT) When `bench_reactor_no_spurious_wake_amplification` reports ~100 wake syscalls per 100 sends:**
      - Symptom: probe counts ~100 `read(eventfd)` + ~100 `epoll_wait` returns for 100 messages; under burst one core saturates on syscall overhead; rtt rises.
      - Why: every cross-shard message does `write(eventfd)` and the consumer reads/handles one wake per `epoll_wait` return without draining the whole inbox in one pass → no coalescing.
      - Fix: on each `epoll_wait` return, do a single `read(eventfd, &mut [u8;8])` (returns the summed counter, resets to 0) then drain the *entire* inbox in one loop; writes arriving during the drain bump the counter and are caught on the next return.
      - Cost avoided: **~90 µs of syscall per 100-message burst → ~0.9 µs (100× reduction)**; ~300 ns × ~99 redundant returns saved (bar (c) violation: per-message syscall blows the < 1 µs rtt budget under load).
      - Muscle: any signal-coalescing doorbell (eventfd/signalfd) MUST drain in one read + one full inbox pass to amortize syscall cost. **Reapplies at: W44 submit_to wake batching, W77/W79 messaging-aeron credit-grant wake coalescing, W85 marketdata batch-drain.**

    - **(NEWBIE→SENIOR) When `reactor_task_not_send_trybuild_emits_exact_error` reports "expected failure, got success" (Task is accidentally `Send`):**
      - Symptom: the compile-fail case *compiles*; trybuild flags the unexpected success; a `Task` can now cross threads onto the wrong shard's `ready_queue`.
      - Why: `Task` was declared as `Box<dyn FnOnce() + Send>` (or the boxed future was `Send`), so `Task: Send` auto-derives and the no-shared-state invariant is unenforceable by the compiler.
      - Fix: drop the `Send` bound — `pub struct Task(Box<dyn FnOnce() + 'static>);` (`!Send`); route all cross-shard work through `CrossShardEnvelope(Box<dyn FnOnce()->Task + Send>)`, whose closure runs on the destination shard to *produce* the `!Send` Task there.
      - Cost avoided: a silent cross-shard data race (the worst HFT bug class — non-deterministic, only under load); compiler now rejects it at the type level (zero runtime cost, infinite debugging cost avoided).
      - Muscle: thread-per-core type discipline requires `!Send` Tasks + an explicit `Send` envelope; never let `Send` auto-derive on the per-shard work unit. **Reapplies at: W44 submit_to type bounds, W58/W74 matching-engine symbol-shard work unit, W83 ledger shard task.**

    - **(SENIOR) When `reactor_timer_precision_under_2ms` reports ~10 ms jitter:**
      - Symptom: a 10 ms timer fires anywhere in [10 ms, 20 ms]; expected ≤ 12 ms.
      - Why: timer-wheel granularity too coarse, OR `epoll_wait` timeout not recomputed from the wheel head (R7), so the loop sleeps a fixed interval and overshoots; OR cascading not implemented for the 10 ms slot.
      - Fix: 1 ms tick wheel; compute `epoll_wait` timeout = ms-until-next-wheel-head; cascade timers beyond the wheel span down a level. Sub-ms waits busy-spin (epoll timeout can't resolve < 1 ms reliably).
      - Cost avoided: 8 ms of unbounded jitter on a 10 ms deadline — for a market-data heartbeat or liquidation timer that is a correctness bug, not a slowdown.
      - Muscle: timer-wheel precision is bounded by `tick`; the loop's sleep must be driven by the wheel head, never a fixed interval. **Reapplies at: W14 time-crate Hlc tick, W77 aeron flow-control timeouts, W83 ledger settlement timers.**

    - **(EXPERT) When `reactor_cross_shard_rtt_under_1us` reports ~1.5 µs:**
      - Symptom: mean rtt ~1.5 µs, above the 1 µs budget, even with correct wake + coalescing.
      - Why: the ping-pong allocates a fresh `Box<dyn FnOnce()>` per message (≈ 50 ns malloc each way) and/or the consumer re-arms epoll every iteration; two syscalls + two mallocs dominate.
      - Fix: pool/reuse the envelope for the hot ping path (typed message, no per-message Box — foreshadows Wed's `CrossShardMsg` enum); keep epoll edge-armed so no re-arm syscall.
      - Cost avoided: 2 × ~50 ns malloc + a redundant `epoll_ctl` ~300 ns ≈ 400 ns/rtt (bar (c) violation: blows the < 1 µs budget).
      - Muscle: on a sub-µs cross-shard path, every malloc and every avoidable syscall is visible — pre-size and reuse. **Reapplies at: W44 submit_to fast path, W58 matching-engine event channel, W85 marketdata poll loop.**

    #### Phase 3 — Make the tests pass, one failure at a time (~120 min)

    - **(EXPERT) When `scheduler_late_waker_after_shutdown_no_uaf` reports UAF under miri:**
      - Symptom: miri "constructing a Pointer to a dead allocation" / "use-after-free" when the external `Waker` fires after the executor is dropped.
      - Why: the `RawWaker` data pointer was a raw `*const LocalExecutor` (or raw slot pointer); shutdown freed the slab; the external holder's `wake()` dereferences freed memory.
      - Fix: the data pointer is `Arc<TaskState>` carrying a `live: AtomicBool`; `wake()` does `if state.live.load(Acquire) { push_ready(state.idx) }` else returns; `Drop for LocalExecutor` stores `live.store(false, Release)` for every task *before* freeing the slab.
      - Cost avoided: a heap UAF (silent corruption / RCE-class bug) — replaced by one Acquire load (~0.5-1 ns) on the wake path. (bar (c): an HFT executor that corrupts on shutdown is disqualifying, not slow.)
      - Muscle: any cross-lifetime reference handed to an external waker needs a liveness flag checked at the callee, and shutdown must invalidate *before* freeing. **Reapplies at: W44 submit_to JoinHandle lifecycle, W74 matching-engine subscription cleanup, W83 ledger task teardown.**

    - **(SENIOR) When `scheduler_recursive_spawn_no_stack_overflow` overflows the stack:**
      - Symptom: SIGSEGV / "thread stack overflow" at ~10k nesting depth.
      - Why: `spawn_local` polls the new future synchronously inside the parent's poll → each spawn adds a stack frame → unbounded recursion.
      - Fix: `spawn_local` only inserts the future into the slab and pushes the index to `ready`, then returns; the new task is polled on a *later* iteration of `run()`.
      - Cost avoided: a stack-overflow time bomb that detonates only at depth (passes small tests, crashes in prod at scale).
      - Muscle: scheduler primitives must enqueue, never invoke synchronously. **Reapplies at: W44 submit_to scheduling, W58/W74 matching-engine event-driven order processing, W83 ledger event loop.**

    - **(EXPERT) When `bench_scheduler_cross_shard_typed_no_alloc` reports allocations per message:**
      - Symptom: counting allocator reports ~1000 allocs for 1000 pings; rtt rises ~800 ns → ~1.2 µs; ~50 ms/sec CPU on malloc at 1 M/sec.
      - Why: `submit_to` boxes every message as `Box<dyn FnOnce()+Send>` — alloc on every send, even a trivial ping.
      - Fix: `enum CrossShardMsg { Ping, Signal(SignalKind), Data(u64), Boxed(Box<dyn FnOnce()+Send>) }`; common variants are stack-sized in the enum (0 alloc); only arbitrary closures pay the `Boxed` cost.
      - Cost avoided: **~50 ns + 1 alloc per message → 0** on the hot path; rtt back under 1 µs (bar (c) violation: per-message malloc blows the budget under load).
      - Muscle: cross-thread channel messages should be typed enums with a `Boxed` fallback, never pure-`Box`. **Reapplies at: W44 submit_to common messages, W58 matching-engine event channel, W83 ledger command enum, W85 marketdata control msgs.**
