- [ ] **Build (bar (b))**: `crates/ops-chaos/src/fault.rs` — `Fault` enum (`KillProcess`, `NetworkPartition`, `LatencyInject`, `PacketDrop`, `DiskFull`, `DiskSlow`, `ClockSkew`, `ResourceLimit`) + RAII `FaultHandle`. (~total 90 min across 3 phases)
  - 🔧 **Why this matters**: mirrors Jepsen `nemesis` (typed, replayable faults) — string-based shell scripts (`ssh node iptables -A …`) are not auditable, not replayable, not idempotent. These are the EXACT faults the §4A acceptance-#2 proof needs (single-node crash/restart with no lost commits) and the acceptance-#7 schedule space (partition + crash + restart while the insurance-fund waterfall runs). The traps a first attempt hits: (1) `Drop` cleanup spawned onto a dead runtime so rules leak — and a leaked partition silently corrupts the NEXT tripwire-search drill's attribution; (2) idempotent inject re-allocates instead of de-duping, double-installing rules; (3) `clock_settime(CLOCK_REALTIME)` poisons the chaos host's own clock — corrupting the very log that proves chaos happened; (4) tag-based recovery deletes by exact rule-spec which shifts position, leaving rules behind. First-attempt impls fail ≥1 Phase-2 test below; the debug session is the lesson.   - *Contract* (signatures only — never the body):
    ```rust
    pub enum Fault {
        KillProcess(Pid),
        NetworkPartition { from: NodeId, to: NodeId },
        LatencyInject { node: NodeId, ms: u32 },
        PacketDrop { node: NodeId, pct: u8 },
        DiskFull(MountPoint),
        DiskSlow { mount: MountPoint, added_ms: u32 },
        ClockSkew { node: NodeId, delta_ms: i64 },
        ResourceLimit { node: NodeId, cpu_pct: u8 },
    }
    pub struct FaultHandle { /* id, tag, recovery closure/spec */ }
    impl Fault   { pub fn inject(&self, ctx: &ChaosCtx) -> io::Result<FaultHandle>; }
    impl FaultHandle { pub fn recover(self) -> io::Result<()>; }
    impl Drop for FaultHandle { /* synchronous cleanup, no runtime dependency */ }
    pub fn cleanup_on_startup(ctx: &ChaosCtx) -> io::Result<usize>; // returns # rules removed
    ```
  - *Back-of-envelope*: an `iptables -A` is a `fork`+`exec`+netfilter write ≈ **1-3 ms per rule** (NOT a 300 ns syscall — it spawns a whole process). A 4-rule partition costs ~8 ms to inject. The cliff: in a Fri/Sat drill asserting "VSR re-converges and the fund recovers within budget after a partition heals," if you forget R7 and DON'T subtract injection cost from latency attribution, the drill measures **8 ms of YOUR injection** on top of the venue — a false positive that could mask (or fake) a tripwire event. That is why the inject-cost metric (R7) is correctness, not vanity.
  - **Requirements** R1..R7 — write in `crates/ops-chaos/notes/108_fault_design.md`:
    - R1. `Fault` is a typed `enum` covering the 8 fault classes (Process, Partition, Latency, Drop, Disk-Full, Disk-Slow, Clock-Skew, Resource).
    - R2. Every `inject` returns a `FaultHandle` that, if dropped without `recover`, runs recovery in its `Drop` impl (RAII), **synchronously**.
    - R3. Faults are idempotent — `inject(same)` twice returns the same handle; `recover(already)` is a no-op.
    - R4. Recovery is exhaustive — partition recovery deletes EVERY iptables rule tagged `OPSCHAOS-<id>`; no rule left behind.
    - R5. Cleanup-on-startup scans `iptables-save` + `tc qdisc show` for `OPSCHAOS-` entries and removes them (covers a crashed previous run).
    - R6. `ClockSkew` does NOT poison the chaos host's clock — applied via time namespace (`setns(CLONE_NEWTIME)`, kernel ≥ 5.6) or `libfaketime` LD_PRELOAD fallback.
    - R7. `chaos_inject_duration_ms{fault_type}` metric emitted per fault so latency attribution can subtract injection cost.

    - Fix: synchronous faults (iptables, tc, dmsetup) recover synchronously — call `Command::new("iptables").arg("-D")…` from `Drop` directly. Only cross-host SSH faults need async; for those register a process-wide deferred-cleanup queue drained by a top-level guard before exit. Never `spawn` into nothing.
    - Cost avoided: a leaked partition silently degrades the next tripwire-search quorum → an un-attributable "tripwire hit" → a day debugging a fund-sizing phantom (the D7 trace).
    - Muscle: `Drop` must not depend on a runtime that may already be gone; synchronous cleanup is simpler and more reliable. Reapplies at: W107 deploy-script cleanup, W109 production shutdown hooks, W110 ops shutdown guard.

  - **(SENIOR) When `idempotent_inject_returns_same_handle` returns two distinct handles (and 8 rules):**
    - Symptom: same fault injected twice yields different `id()`s and 8 iptables rules instead of 4.
    - Why: code allocated a fresh monotonic ID on every inject without consulting a registry of what's already injected.
    - Fix: maintain `injected: HashMap<FaultKey, FaultHandle>` keyed by a canonical hash of variant+params (note P4: a `f64` field would break `Hash`/`Eq` — `LatencyInject.ms` is `u32` on purpose). Look up first; return the existing handle if found.
    - Muscle: idempotency = side-table lookup before allocation; never assume injection is fresh. Reapplies at: Wed scenario-step idempotency, W107 deploy idempotency, W109 runbook re-run safety.

  - **(EXPERT) When `partition_recover_deletes_all_tagged_rules` leaves rules behind after the interleaved insert:**
    - Symptom: 4 rules installed, an unrelated rule inserted at position 1, recover removes 0-2 of the 4.
    - Why: recover ran `iptables -D FORWARD <original-spec>` / by stored line number; iptables matches by exact position and the inserted rule shifted every line number — the stored numbers now point at the wrong (or nonexistent) rules.
    - Fix: recover never reproduces the exact spec or trusts a stored line number. It runs `iptables -L FORWARD --line-numbers | grep OPSCHAOS-<id>` to discover ALL tagged rules at recovery time and deletes them by current line number **in reverse order** (so a delete doesn't invalidate later numbers). Re-grep to verify empty.
    - Cost avoided: a single leaked DROP rule silently half-partitions the next drill → every downstream tripwire-search attribution wrong; debugging it costs hours, not the ~1 ms the correct delete costs.
    - Muscle: position-based commands need reverse-order deletion; tag-based *re-discovery at recovery time* is the only safe cleanup pattern. Reapplies at: Thu runner cleanup, Fri/Sat drill teardown, W109 ops-runbooks tag policies.

  - **(EXPERT) When `cleanup_on_startup_removes_stale_rules` returns Ok but the rule remains:**
    - Symptom: `cleanup_on_startup` returns `Ok(1)` (or 0) but `iptables_rules_tagged()` is still 1.
    - Why: cleanup ran `iptables -L FORWARD | grep OPSCHAOS-` to find rules then fed iptables's *display format* back as a `-D` delete spec — iptables does not accept its own list output as a delete argument.
    - Fix: the auditable round-trip is `iptables-save | grep -v OPSCHAOS- | iptables-restore` (rewrite the table excluding tagged rules), OR `--line-numbers` + reverse-order `-D <N>` as above. Verify with a re-grep; return the count actually removed.
    - Muscle: shelling out to system tools requires knowing their input/output asymmetry; `iptables-save`/`restore` is the auditable round-trip. Reapplies at: W109 cron-based cleanup, Thu runner cleanup.

  - **(EXPERT) When `clockskew_doesnt_affect_host_clock` shows host drift ≥ 5000 ms:**
    - Symptom: `ClockSkew { delta_ms: 5000 }` and the chaos host's own clock jumps 5 s — corrupting the chaos log's timestamps that prove WHEN the tripwire was approached.
    - Why: code called `clock_settime(CLOCK_REALTIME, …)` from the chaos process; `CLOCK_REALTIME` is global, no namespacing.
    - Fix: `setns(target_fd, CLONE_NEWTIME)` to enter the SUT's time namespace BEFORE the syscall (kernel ≥ 5.6). On older kernels fall back to `libfaketime` LD_PRELOAD on the SUT process. A compile-time feature flag picks the strategy.
    - Muscle: any "system" syscall needs namespacing awareness or you poison the host; time/net/PID namespaces are the isolation primitives. Reapplies at: Wed scenario clock semantics, W109 production clock SLA.

  - **(EXPERT, perf — bar (b) but load-bearing) When `inject_cost_metric_lands_in_plausible_band` records ~0 ms:**
    - Symptom: `chaos_inject_duration_ms{Partition}` is 0.0, band assertion fails on the lower bound.
    - Why: the metric was emitted (`histogram.observe`) BEFORE the `Command::new("iptables")` ran — it timed an empty span. The fork+exec cost (~1-3 ms × 4 rules) was never captured.
    - Fix: bracket the *actual* injection: `let t0 = Instant::now(); run_iptables_rules(); metric.observe(t0.elapsed().as_secs_f64()*1000.0);`. The observation must wrap the syscall-spawning work.
    - Cost avoided: ~8 ms of injection cost wrongly attributed to the venue → a drill asserting "fund recovers ≤ 2 ms after heal" sees 10 ms and false-alarms (or, worse, masks a real tripwire approach). (Not a "slow" bug — a *correctness* bug in attribution.)
    - Muscle: measure the span that contains the cost, not the span before it; a back-of-envelope (fork+exec ≈ ms, not 300 ns) tells you 0.0 is impossible and must be a wiring bug. Reapplies at: Fri/Sat tripwire latency attribution, W109 ops-runbook latency attribution, W105 metric-emission ordering.

  - **(SENIOR) When `convergence_budget_overflow_rejected` accepts a 10 s budget into a 5 s gap:**

    - Muscle: validators enforce structural invariants so the runtime can trust the validated input. Reapplies at: Thu runner trusts scenario, W107 deploy-plan validator.

  - **(SENIOR) When `tripwire_assertion_fails_when_fund_exhausted` passes (i.e. wrongly reports OK):**
    - Symptom: fund balance 50k, pending shortfall 200k, but the assertion returns Ok.
    - Why: the assertion compared the fund balance to a *fixed initial balance* threshold rather than to the *next pending shortfall* — the tripwire is "fund can't cover the NEXT shortfall via the waterfall," not "fund below some constant."
    - Fix: `tripwire_hit = (fund_balance + remaining_position_margin) < pending_shortfall` evaluated relative to the declared accrual rate; the assertion fails iff `tripwire_hit`. This is the §4A waterfall (position-margin → fund) tripwire definition.
    - Cost avoided: a green corpus that never actually checks the moat invariant — the worst false confidence for the principal artifact.
    - Muscle: a safety assertion must encode the actual invariant ("covers the next shortfall via the waterfall"), not a convenient proxy constant. Reapplies at: Fri/Sat StateChecker, W109 fund SLO, W119 ADL engage point.

    - Why: the flake sidecar listened only to scenario START events, not END events carrying pass/fail.
    - Fix: `ScenarioResult` emits `chaos_scenario_runs_total{id, outcome="pass|fail"}`; 30-day rate = `rate(fail[30d]) / rate(total[30d])`.
    - Muscle: track outcomes as labeled counters; rates derive from time-windowed PromQL, not in-process tallies. Reapplies at: W109 ops-runbook SLO tracking, W105 metric design.

  - **(EXPERT) When `assertion_failure_snapshot_contains_schedule_and_seed` shows empty `span_ids` / missing seed:**
    - Symptom: snapshot has `metric_trace` but `span_ids: []` and no `seed`/`fault_schedule`, though spans were emitted and the run was seeded.
    - Why: snapshot read `tracing::Span::current()` at the failure moment (which doesn't cross async boundaries), and the runner never threaded the seed/schedule into the result.
    - Fix: tail-sample — keep the last 5 s of all span IDs in a ring buffer and dump on failure regardless of `current()`; AND have the runner record `seed` + the ordered `fault_schedule` into `ScenarioResult::artifacts` so a tripwire HIT is exactly replayable (this replayable schedule IS the v1.5 ADL-trigger definition, §4A acceptance #7).
