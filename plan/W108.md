**Tuesday — ops-chaos: fault types**

- [ ] **Build**: `crates/ops-chaos/src/fault.rs` — Fault enum: `KillProcess(Pid)`,
  `NetworkPartition { from: NodeId, to: NodeId }`, `LatencyInject { ms: u32 }`, `DiskFull(MountPoint)`,
  `ClockSkew { delta_ms: i64 }`. (~45 min)
  - **Why**: ops-chaos is the *only* path to bar-(c) ("infrastructure correctness") evidence. VOPR validates code under
    deterministic-time fault injection; ops-chaos validates the *same* code under *real-world* fault injection (process
    kills, network partitions, clock skew). Faults must be expressible as a typed, replayable enum — string-based
    scripts ("run iptables") are not auditable. Each fault must have a known recovery primitive and an observed
    convergence-time budget, or you get cascading failures where Fault N is injected before recovery from Fault N-1
    completes ("observer effect" — you can't tell what broke what).
  - **Read first**: Jepsen `nemesis.clj` (Knossos check, partition primitives); Maelstrom `lib/net.clj` (deterministic
    delivery model); `chaos-mesh/chaos-mesh` `pkg/chaosdaemon` (Linux fault primitives: tc, iptables, dmsetup,
    `setns`); FoundationDB `flow/Net2.actor.cpp` (sim-mode net layer — *the* reference for deterministic faults).
  - **Design**:
    ```rust
    #[derive(Clone, Debug, Serialize, Deserialize)]
    pub enum Fault {
        // Process-level
        KillProcess { pid: Pid, signal: Signal },     // SIGKILL, SIGTERM, SIGSTOP/SIGCONT
        FreezeProcess { pid: Pid, duration: Duration },
        // Network (per-node-pair, bidirectional unless stated)
        Partition { from: NodeId, to: NodeId, direction: Direction },
        LatencyInject { node: NodeId, mean_ms: u32, jitter_ms: u32 },
        PacketDrop { node: NodeId, loss_pct: f32 },
        PacketReorder { node: NodeId, reorder_pct: f32 },
        BandwidthCap { node: NodeId, mbps: u32 },
        // Disk
        DiskFull { mount: PathBuf, fill_pct: f32 },
        DiskSlow { mount: PathBuf, read_lat_ms: u32, write_lat_ms: u32 },
        DiskCorrupt { mount: PathBuf, byte_range: Range<u64> },  // dmsetup error target
        // Time
        ClockSkew { node: NodeId, delta_ms: i64 },
        ClockJump { node: NodeId, target: SystemTime },  // discontinuity
        // Resource
        CpuStress { node: NodeId, cores: u32, load_pct: u8 },
        MemoryPressure { node: NodeId, mb: u64 },
    }
    pub trait FaultExecutor {
        fn inject(&mut self, f: &Fault) -> Result<FaultHandle, ChaosError>;
        fn recover(&mut self, h: FaultHandle) -> Result<(), ChaosError>;
    }
    ```
    **Invariants**: (1) Every `inject` returns a `FaultHandle` that *must* be eventually `recover`ed; a `Drop` impl on
    `FaultHandle` invokes recovery in a tokio runtime if not called explicitly (RAII). (2) Faults are *idempotent* —
    injecting the same fault twice is a no-op; recovering an already-recovered handle is a no-op. (3) Recovery is
    *exhaustive* — partition recovery must call `iptables -D` for *every* rule the inject installed (use a tag prefix
    `OPSCHAOS-<scenario-id>` for grep-based cleanup on next process startup).
  - **Build steps**:
    1. (~5 min) Enum definition with serde derive; `FaultHandle = u64` (monotonic counter).
    2. (~10 min) `KillProcess` / `FreezeProcess` via `nix::sys::signal::kill`; verify pid exists; reject pid 1.
    3. (~15 min) `Partition` via `iptables -A FORWARD -s <from> -d <to> -j DROP -m comment --comment OPSCHAOS-<id>`;
       `LatencyInject` via `tc qdisc add dev <iface> root netem delay <mean>ms <jitter>ms distribution normal`.
    4. (~10 min) `ClockSkew` via `clock_settime(CLOCK_REALTIME, ...)` *inside a network namespace* so it doesn't
       impact the chaos host itself (huge pitfall otherwise).
    5. (~5 min) Cleanup-on-startup: scan `iptables -L` + `tc qdisc show` for any rule with the `OPSCHAOS-` prefix
       and delete them (handles abrupt exits).
  - **Pitfalls**:
    *RecoveryRaceNextFault*: **Symptom**: chaos drill schedules Fault B at T+5s; Fault A's partition recovery takes
       8s to converge (raft re-syncs); Fault B fires *during* the re-sync, attribution becomes impossible.
       **Fix**: every fault has a *convergence budget* (e.g. raft-partition: 5s); scenario runner blocks for budget +
       a *recovery-acked* probe (poll `/admin/role` until all replicas report consistent leader) before scheduling next.
    *FaultCorrelation*: **Symptom**: "kill leader + partition followers" looks like one bug but is actually two; you
       fix one and the other persists silently. **Fix**: scenario DSL forbids overlapping fault windows on the same
       node-class unless explicitly tagged `concurrent: true`; default is strictly serial.
    *ObserverEffect*: **Symptom**: the act of injecting a fault (e.g. forking iptables) introduces 10ms of host
       latency that the system attributes to its own slow code. **Fix**: chaos host is a *separate* machine from the
       SUT; faults are injected via SSH-to-target or via a co-located daemon with cgroup-isolated CPU; record
       `chaos_inject_duration_ms` per fault and subtract from latency attribution.
    *HostClockPoisoning*: **Symptom**: `ClockSkew` is meant for the SUT but `clock_settime` jumps the chaos host's
       clock too, breaking the scenario log timestamps. **Fix**: enter the SUT's network/time namespace via `setns`
       before issuing the syscall, or use `libfaketime` LD_PRELOAD on the SUT process.
  - **Test scenarios** (adversarial): (a) inject Partition, then crash the chaos process — restart the chaos daemon
    and verify it grep-cleans the stale iptables rules; (b) two scenarios run back-to-back — verify second sees a
    clean fault state (no leftover tc qdisc); (c) inject DiskCorrupt then DiskFull on same mount — verify recovery
    order is reverse of inject (LIFO) and end state is healthy.
  - **Acceptance**: 50 distinct scenarios run end-to-end in CI nightly; per-scenario cleanup verified by grep of
    iptables/tc/dmsetup state pre/post equals empty diff.
  - **Downstream**: scenario DSL (next bullet) composes these; runner schedules them; M30 bar-(c) audit cites the
    list of fault types covered against the FoundationDB / TigerBeetle reference set (8 of 8 should be checked).

**Wednesday — ops-chaos: scenario DSL**

- [ ] **Build**: `crates/ops-chaos/src/scenario.rs` — `Scenario { steps: Vec<ScenarioStep> }`. Step is fault + delay +
  assertion. (~75 min)
  - **Why**: a scenario is a *typed, replayable* recipe — "kill leader at T+0, observe view-change ≤ 500ms at T+δ,
    inject partition at T+5s, observe minority stalls writes". Without a DSL, chaos is shell-scripted ad-hoc; with one,
    chaos becomes regression-tested: every scenario added becomes a permanent guard against the bug it found. This is
    the same discipline as VOPR scenarios in TigerBeetle — the persistent corpus of "things that broke" prevents
    regressions across crates touched after the original fix.
  - **Read first**: Jepsen `nemesis/combined.clj` (compose primitives into a generator); Maelstrom workload spec
    JSON; chaos-mesh `pkg/scheduler/scheduler.go` (workflow / pause semantics); TigerBeetle `src/vopr.zig` (deterministic
    scenario replay with seed + run-length).
  - **Design**:
    ```rust
    pub struct Scenario {
        pub id: ScenarioId,
        pub seed: u64,                  // deterministic when faults are deterministic
        pub steps: Vec<ScenarioStep>,
        pub global_budget: Duration,    // total wall-time cap; abort if exceeded
    }
    pub struct ScenarioStep {
        pub at_offset: Duration,        // when from scenario T+0
        pub fault: Option<Fault>,       // None = pure observation step
        pub assertion: Option<Assertion>, // assertion evaluated at this step
        pub convergence_budget: Duration, // time allotted before next step may inject
    }
    pub enum Assertion {
        QuorumHealthy { cluster: ClusterRef, within: Duration },
        LeaderElected { cluster: ClusterRef, within: Duration },
        NoReplicaDivergence { cluster: ClusterRef },
        LedgerReconciliationZero,
        LatencyP99Under { metric: MetricName, threshold_us: u64 },
        MetricEq { metric: MetricName, expected: f64, tolerance: f64 },
        Custom(Arc<dyn Fn(&MetricSnapshot) -> Result<(), AssertionError> + Send + Sync>),
    }
    ```
    **Invariants**: (1) Steps are sorted by `at_offset` at construction; out-of-order construction is a compile-time
    or load-time error. (2) `convergence_budget` of step N must be ≤ (step N+1's `at_offset` - step N's `at_offset`)
    — otherwise the next fault may fire mid-recovery. (3) Assertions are evaluated *after* convergence_budget elapses,
    not immediately after fault inject.
  - **Build steps**:
    1. (~10 min) Struct definitions with serde for TOML/YAML scenario files; example scenario file in
       `crates/ops-chaos/scenarios/leader-kill.toml`.
    2. (~15 min) Validation pass: enforce step ordering, budget non-overlap; reject scenarios that exceed
       `global_budget`.
    3. (~25 min) Assertion implementations that read the Prometheus registry from W105 (e.g.
       `LatencyP99Under` queries the `shard_busy_us` histogram).
    4. (~15 min) Scenario library: 5 canned scenarios (leader-kill, minority-partition, majority-partition, slow-disk,
       clock-skew) shipped with the crate.
    5. (~10 min) Snapshot serialization of assertion failures: include metric trace + last 5s of span IDs so the
       failure is reproducible.
  - **Pitfalls**:
    *AssertionRaceImmediate*: **Symptom**: assertion checks metric value 100ms after fault injection — too early;
       false-positive failures dominate. **Fix**: enforce `Assertion::within` ≥ system's documented convergence-bound
       (e.g. raft election timeout * 2); reject scenarios with sub-budget assertions in validator.
    *NonDeterministicScenario*: **Symptom**: same scenario passes 9/10 times because of unaccounted-for jitter (CPU
       scheduling, OS noise). **Fix**: require P95-pass not P100-pass for budgets; pin SUT to dedicated cores; record
       seed + per-run flake rate; flake-rate > 1% is a scenario bug, not a SUT bug.
    *BudgetCascade*: **Symptom**: scenario with 10 steps drifts by 500ms total because each step's convergence runs
       to the edge of its budget. **Fix**: absolute scheduling (`at_offset` from scenario T+0) not relative; the
       runner sleeps until `T+0 + at_offset`, skipping ahead if already past (warn).
    *AssertionTooStrict*: **Symptom**: `LatencyP99Under(2us)` was true on the dev box but fails in CI; scenarios
       become noise. **Fix**: assertion thresholds are *per-environment* via a config file
       (`scenarios/env/{dev,ci,rig}.toml`) overriding scenario defaults.
  - **Test scenarios**: (a) malformed scenario (out-of-order steps) — loader rejects with clear error; (b) scenario
    with `convergence_budget == 0` — validator rejects unless assertion is `None`; (c) scenario whose Assertion has
    `Custom(...)` closure — verify the closure is invoked exactly once per matching step.
  - **Acceptance**: 5 canned scenarios in repo, each with ≥3 assertions; CI runs all 5 nightly with green status;
    flake-rate per scenario < 1% over 30-day rolling window.
  - **Downstream**: runner (next bullet) consumes scenarios; ops-runbooks (W109) reference the assertion-failure
    artifacts as the incident-postmortem starting point; M30 bar-(c) audit cites "N distinct scenarios validated".

**Thursday — ops-chaos: runner**

- [ ] **Build**: `crates/ops-chaos/src/runner.rs` — executes scenarios against a live deployment. Logs results. (~75 min)
  - **Why**: the runner is the *event loop* that ties faults, time, and assertions together. The runner's correctness
    is *more important than* any single fault primitive — a buggy runner silently passes scenarios. The runner is also
    the boundary between deterministic-time chaos (in-process tests using a simulated `Clock`) and real-world chaos
    (the rig with `Clock::system()`); both must share code so a green CI scenario maps to a meaningful rig scenario.
  - **Read first**: TigerBeetle `src/vopr/runner.zig` (the simulator main loop — `tick` model, fault scheduling);
    Jepsen `core/src/jepsen/core.clj` (history collection + analysis post-test);
    chaos-mesh `controllers/workflow` (state-machine for workflow steps with retry semantics).
  - **Design**:
    ```rust
    pub struct Runner<C: Clock, E: FaultExecutor> {
        clock: C,
        executor: E,
        metric_source: Arc<dyn MetricSource>,  // reads Prometheus registry
        log: ScenarioLog,                       // append-only, JSON-lines
    }
    impl<C: Clock, E: FaultExecutor> Runner<C, E> {
        pub async fn run(&mut self, scenario: &Scenario) -> ScenarioResult;
    }
    pub struct ScenarioResult {
        pub id: ScenarioId,
        pub seed: u64,
        pub passed: bool,
        pub steps_passed: u32,
        pub steps_failed: u32,
        pub failures: Vec<AssertionFailure>,
        pub artifacts: Vec<PathBuf>,  // pcap, perf record, metric snapshot
    }
    ```
    **Invariants**: (1) Runner is single-threaded per scenario — no parallel steps within a scenario (parallelism via
    multi-scenario harness). (2) On failure: log + collect artifacts + recover all open `FaultHandle`s + return —
    never partial-cleanup. (3) The runner *must* be `panic = abort` or wrap each step in `catch_unwind` to ensure
    fault recovery even on panic in user assertion closures.
  - **Build steps**:
    1. (~10 min) `Clock` trait abstraction: `now()`, `sleep_until(t)`, `advance(d)` (sim only). System impl uses
       `tokio::time`; sim impl uses a sorted heap of pending wakers (re-use the runtime-thread-per-core deterministic
       Clock from earlier weeks).
    2. (~20 min) Main loop: for each step in order, `clock.sleep_until(scenario_start + step.at_offset)`,
       then `executor.inject(step.fault)`, await `step.convergence_budget`, evaluate `step.assertion`.
    3. (~15 min) `AssertionFailure` capture: snapshot metric registry to JSON, capture last 5s of OTLP spans via
       trace-tail-sampler, attach to result.
    4. (~10 min) Artifact collection: on failure, dump `tcpdump -i any` last 30s if pcap enabled in scenario;
       `perf record -p <pid> -F 99 -g` for 5s on the SUT process.
    5. (~15 min) Cleanup path: drop all `FaultHandle`s in reverse-inject order; verify post-state via
       `grep OPSCHAOS- $(iptables-save)` returns empty.
    6. (~5 min) Result printer + exit code: non-zero on any failure; readable summary table for CI logs.
  - **Pitfalls**:
    *PanicLeaksFaults*: **Symptom**: scenario asserts `panic!()` inside `Assertion::Custom`; runner aborts mid-step;
       iptables rules remain in place; next scenario inherits a partition. **Fix**: wrap step body in
       `tokio::task::spawn_blocking` + `catch_unwind`; on panic, route to cleanup path; verify with a test that injects
       a deliberate panic.
    *ClockDriftReal*: **Symptom**: real-clock runner runs a 60-min scenario; cumulative jitter pushes assertions past
       their deadlines. **Fix**: assertions use *deadlines* (`now + within`) not *durations from inject-time*; absolute
       wall-clock comparison.
    *MetricStaleness*: **Symptom**: assertion reads metric registry but the metric hasn't been updated since the
       fault — false-pass. **Fix**: every assertion polls the metric source until *either* a tick newer than the
       inject-time *or* the budget expires; mark assertion as "stale" if budget expires without an update.
    *ConcurrentRunnersStompState*: **Symptom**: CI runs two scenarios in parallel on the same host; iptables rules
       conflict. **Fix**: filesystem lockfile in `/var/run/ops-chaos.lock`; runner refuses to start if held; CI
       parallelism is *across hosts* not within a host.
  - **Test scenarios**: (a) panic inside Assertion::Custom — runner reports failure but cleans up faults; (b) scenario
    exceeds `global_budget` — runner aborts at the cap and reports timeout with full step accounting; (c) two
    runners launched simultaneously on same host — second blocks on lockfile, doesn't run.
  - **Acceptance**: nightly CI runs the 5 canned scenarios; chaos drill on rig (Friday's `kill matching-engine leader`)
    completes with the leader scenario going green; failure-mode artifacts contain at least one usable trace span +
    one metric-snapshot per failed assertion.
  - **Downstream**: ops-runbooks (W109) read `ScenarioResult` artifacts as the alert-postmortem source; the rolling
    chaos-test count feeds the M30 bar-(c) audit (target: 50+ scenarios green for 30 consecutive nights).
