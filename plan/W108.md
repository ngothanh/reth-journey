  #### Phase 1 — Problem, requirements, design (~20 min, no code yet)

  - **The problem this primitive solves**: ad-hoc chaos via shell scripts (`ssh node iptables -A …`) is
    not auditable, not replayable, not idempotent. When chaos leaves state behind (a forgotten iptables
    rule, an undeleted `tc qdisc`), the NEXT test inherits it and you debug the wrong thing. When the
    chaos host's own clock gets skewed (because `clock_settime` is not namespaced), you corrupt the
    very log that proves chaos happened. The `Fault` enum + RAII `FaultHandle` is the answer:
    typed faults with mandatory recovery semantics.

  - **Requirements** — write in `crates/ops-chaos/notes/108_fault_design.md`:
    - R1. `Fault` is a typed `enum` covering the 8 fault classes from the FoundationDB / TigerBeetle
      reference set (Process, Partition, Latency, Drop, Disk-Full, Disk-Slow, Clock-Skew, Resource).
    - R2. Every `inject` returns a `FaultHandle` that, if dropped without `recover`, runs recovery in
      its `Drop` impl (RAII).
    - R3. Faults are idempotent — `inject(same)` twice returns the same handle; `recover(already)` is
      a no-op.
    - R4. Recovery is exhaustive — partition recovery deletes EVERY iptables rule tagged
      `OPSCHAOS-<id>`; no rule is left behind.
    - R5. Cleanup-on-startup: process bootstrap scans `iptables -L` + `tc qdisc show` for `OPSCHAOS-`
      tagged entries and removes them — covers the case where the previous run crashed.
    - R6. `ClockSkew` does NOT poison the chaos host's clock — it is applied via namespace
      (`setns(CLONE_NEWTIME)` on kernel ≥ 5.6 or `libfaketime` LD_PRELOAD).
    - R7. `chaos_inject_duration_ms` metric is emitted per fault so latency attribution can subtract
      injection cost.

  - **Design walk-through** — answer each in your design doc; no peeking at Jepsen `nemesis.clj` or
    chaos-mesh `pkg/chaosdaemon` until Phase 3:
    - D1. Why an enum vs a trait `Fault` with dyn dispatch? Argue from R1 + the audit requirement —
      what does an enum give that a trait doesn't?
    - D2. RAII handle: what does `FaultHandle::Drop` need to do safely? (Hint: cannot call async; must
      spawn or block on a runtime; both have failure modes — design the safer choice.)
    - D3. Idempotency: how do you detect "same fault"? (Hint: hash of the canonical fault repr in a
      side-table keyed by `FaultHandle`.)
    - D4. Tag-based cleanup: every iptables rule has a `-m comment --comment OPSCHAOS-<scenario-id>-<seq>`
      suffix. Why scenario-id AND seq? What does cleanup-on-startup look like (grep + parse)?
    - D5. ClockSkew namespacing: list 3 ways to apply CLOCK_REALTIME skew to ONE process without
      affecting the host. Pick one and justify (portability vs simplicity).
    - D6. Observer effect: chaos injection itself adds latency. How do you subtract it? (Hint: per-fault
      `inject_duration_ms` metric; latency attribution code reads it.)
    - D7. **Pre-mortem (the load-bearing question)**: write the 6-step interleaving where a chaos
      drill (a) injects a Partition with tag `OPSCHAOS-42-1`, (b) chaos process SIGKILL'd before
      recover, (c) operator manually deletes one iptables rule but misses another, (d) next chaos
      drill starts and sees half-partitioned state, attribution to its own faults is impossible.
      Convince yourself R5's cleanup-on-startup catches this.
  - **Output**: `notes/108_fault_design.md` with R1–R7, answers to D1–D7, the enum sketch, the
    iptables tagging convention, the cleanup-on-startup pseudocode.

  #### Phase 3 — Make the tests pass, one failure at a time (~35 min)

  - **When `dropped_handle_runs_recovery` shows iptables rules still present after drop:**
    - Symptom: handle dropped, but `iptables -L FORWARD` still has `OPSCHAOS-...` rules; next test sees
      a stale partition.
    - Why: `FaultHandle::Drop` tried to spawn an async task on a possibly-shutdown tokio runtime;
      spawn silently failed (runtime gone) and rules never deleted.
    - Fix: recovery for synchronous faults (iptables, tc, dmsetup) is itself synchronous — call
      `Command::new("iptables").arg("-D")…` from `Drop` directly. Only async faults (cross-host SSH)
      need a runtime; for those, register a process-wide "deferred cleanup" queue that a top-level
      guard drains before exit. NEVER drop spawn into nothing.
    - Muscle: Drop must not depend on a runtime that may already be gone; synchronous cleanup is
      simpler and more reliable. Reapplies at: W107 deploy script cleanup, W109 production
      shutdown hooks.

  - **When `cleanup_on_startup_removes_stale_rules` doesn't remove the rule:**
    - Symptom: `Fault::cleanup_on_startup()` returns OK but the rule remains.
    - Why: cleanup ran `iptables -L FORWARD | grep OPSCHAOS-` to find rules but then ran
      `iptables -D FORWARD <rule_text>` with the displayed text — iptables doesn't accept its own
      display format as a delete spec.
    - Fix: cleanup runs `iptables-save | grep -v OPSCHAOS- | iptables-restore` (rewrites the table
      excluding tagged rules) OR uses `iptables -L FORWARD --line-numbers` + `iptables -D FORWARD <N>`
      walking in reverse-order. Verify with a re-grep.
    - Muscle: shelling out to system tools needs awareness of their input/output asymmetries;
      iptables-save/restore is the auditable round-trip. Reapplies at: W109 cron-based cleanup,
      W108 Thursday runner cleanup.

  - **When `clockskew_doesnt_affect_host_clock` shows host clock jumped by 5 s:**
    - Symptom: test runs `ClockSkew { delta_ms: 5000 }` and the chaos host's clock jumps too.
    - Why: code called `clock_settime(CLOCK_REALTIME, ...)` from the chaos process; CLOCK_REALTIME is
      a global system clock, no namespacing.
    - Fix: enter the target's time namespace via `setns(CLONE_NEWTIME)` BEFORE the syscall. On older
      kernels (< 5.6) fall back to LD_PRELOAD libfaketime on the SUT process. Compile-time feature
      flag picks the strategy.
    - Muscle: any "system" syscall needs namespacing awareness or you poison the host; time/network/PID
      namespaces are the isolation primitives. Reapplies at: W108 Wed scenario DSL clock semantics,
      W109 production clock SLA.

  - **When `idempotent_inject_returns_same_handle` returns two distinct handles:**
    - Symptom: same fault injected twice yields two different `FaultHandle`s; recovery has to be called
      twice.
    - Why: code allocated a new monotonic ID on every inject without checking a registry of "what's
      already injected".
    - Fix: maintain `injected: HashMap<FaultKey, FaultHandle>` where `FaultKey` is a canonical hash
      of the Fault enum variant + parameters. On inject, look up first; return existing handle if
      found, else allocate.
    - Muscle: idempotency = side-table lookup before allocation; never assume injection is fresh.
      Reapplies at: W108 Wed scenario step idempotency, W107 deploy idempotency.

  - **When `partition_recover_deletes_all_tagged_rules` leaves 2 of 4 rules behind:**
    - Symptom: 4 rules installed, only 2 removed by recover.
    - Why: recover called `iptables -D` with the original rule spec, but iptables matches the spec
      EXACTLY — including the position. Two rules' positions had shifted because another rule was
      inserted between them mid-test.
    - Fix: recover doesn't try to reproduce the exact rule spec. Instead it runs
      `iptables -L FORWARD --line-numbers | grep OPSCHAOS-<id>` to find ALL rules with the scenario tag
      and deletes them by line number (in reverse order so deletes don't invalidate later numbers).
    - Muscle: position-based commands need ordered deletion; tag-based discovery is the only safe
      cleanup pattern. Reapplies at: W108 Thu runner cleanup, W109 ops-runbooks tag policies.

  - **5-year failure mode** (write in `notes/108_fault_followup.md` after green): when chaos runs on
    eBPF-instrumented hosts, iptables becomes legacy — `nftables` or `bpfilter` is the underlying
    primitive. Migration trigger: kernel ≥ 6.x dropping iptables compat. Name the abstraction
    (`NetworkFaultBackend` trait with iptables/nftables/bpf impls) and the cutover discipline.

**Wednesday — ops-chaos: scenario DSL**

- [ ] **Build**: `crates/ops-chaos/src/scenario.rs` — `Scenario { steps: Vec<ScenarioStep> }`. Step is fault + delay +

  - 🔧 **Why this matters**: a scenario is a *typed, replayable* recipe — "kill leader at T+0, observe
    view-change ≤ 500 ms at T+δ, inject partition at T+5s, observe minority stalls writes". Without a
    DSL, chaos is shell-scripted ad-hoc; with one, chaos becomes regression-tested: every scenario
    added becomes a permanent guard against the bug it found. This is the same discipline as VOPR
    scenarios in TigerBeetle — the persistent corpus of "things that broke" prevents regressions
    across crates touched after the original fix. Downstream consumers: W108 Thu runner consumes
    scenarios; W109 ops-runbooks reference assertion-failure artifacts as the incident-postmortem
    starting point; M30 bar-(c) audit cites "N distinct scenarios validated".

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: ad-hoc chaos has no regression value — when a bug is found
    via "we tried killing the leader during a burst", that knowledge dies in a Slack thread. A
    typed scenario codifies the recipe: same seed, same fault sequence, same assertions, repeatable
    forever. Convergence budgets prevent the most common chaos bug: injecting fault N before fault N-1
    has converged, making attribution impossible.

  - **Requirements** — write in `crates/ops-chaos/notes/108_scenario_design.md`:
    - R1. `Scenario` is constructed from a TOML/YAML file OR programmatically; steps are sorted by
      `at_offset` at construction; out-of-order steps are a load-time error.
    - R2. `convergence_budget` of step N ≤ (step N+1's at_offset - step N's at_offset). Validator
      rejects scenarios that violate this — assertion of step N would race with inject of step N+1.
    - R3. Assertions are evaluated AFTER `convergence_budget` elapses, not immediately after inject.
    - R4. Assertion library covers: `QuorumHealthy`, `LeaderElected`, `NoReplicaDivergence`,
      `LedgerReconciliationZero`, `LatencyP99Under`, `MetricEq`, `Custom(Arc<dyn Fn>)`.
    - R5. Assertion thresholds are environment-aware — config file `scenarios/env/{dev,ci,rig}.toml`
      overrides scenario defaults.
    - R6. Flake rate per scenario < 1% over 30-day rolling window — measured, tracked.
    - R7. 5 canned scenarios shipped with the crate (leader-kill, minority-partition,
      majority-partition, slow-disk, clock-skew); each has ≥ 3 assertions.
    - R8. On assertion failure, scenario snapshots include metric trace + last 5 s of span IDs so the
      failure is reproducible.

  - **Design walk-through** — answer each in your design doc; no peeking at Jepsen `nemesis/combined.clj`
    or TigerBeetle `src/vopr.zig` until Phase 3:
    - D1. Scenario serialization: TOML vs YAML vs JSON. Argue from R1 (human-edited) + R6 (CI parses).
      Pick one.
    - D2. Step ordering: how do you enforce "sorted by at_offset" at construction? Builder + final
      validate? Newtype `SortedSteps`?
    - D3. `convergence_budget` enforcement: what's the validator algorithm? (Hint: iterate pairs of
      consecutive steps, assert `step[i].at_offset + step[i].convergence_budget ≤ step[i+1].at_offset`.)
    - D4. Assertion types: enum vs trait `Assertion`? Argue from R4 — Custom needs a closure, suggesting
      enum-with-Box. Trade-offs.
    - D5. Metric source abstraction: how does `LatencyP99Under` query Prometheus? Direct registry
      reference (W105) vs a `MetricSource` trait abstracted for test injection?
    - D6. Environment overrides: how does `scenarios/env/ci.toml` override `LatencyP99Under{2us}` to
      `LatencyP99Under{10us}`? Config layering rules.
    - D7. Flake tracking: where do you record per-scenario pass/fail history? File? Sqlite?
      Prometheus counter? Argue from R6's 30-day window.
    - D8. **Pre-mortem (the load-bearing question)**: write the 6-step interleaving where a scenario
      asserts `LeaderElected within 100 ms` after killing the leader, but the system's documented
      election timeout is 150 ms — the assertion fires within budget on a fast machine (CI) and fails
      on a slow rig. Convince yourself R2 + R3 + R5 prevent this.
  - **Output**: `notes/108_scenario_design.md` with R1–R8, answers to D1–D8, the TOML schema, the
    validator pseudocode, sample assertion bodies.

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)

  - **When `out_of_order_steps_rejected` accepts the bad scenario:**
    - Symptom: scenario loaded with steps `[0, 5, 3]`; validator returned OK; runner sleeps to
      T+5 then T+3, which is past — runner panics on negative duration.
    - Why: validator iterated steps without checking monotonicity; sorting happened later but
      silently.
    - Fix: validator's first pass: `steps.windows(2).all(|w| w[0].at_offset < w[1].at_offset)`. If
      not, return `Err(StepOrder { at: <index> })`. Do NOT silently sort — that masks operator
      errors in the TOML.
    - Muscle: validate, don't silently fix; operator typos in config should fail loudly. Reapplies at:
      W109 ops-runbooks config, W107 deploy-state file parsing.

  - **When `assertion_waits_for_convergence_budget` evaluates before budget elapses:**
    - Symptom: probe records eval_time = inject_time + 50 ms despite budget = 500 ms.
    - Why: assertion fired in the same tokio task as inject; await of budget happened AFTER assertion
      eval.
    - Fix: runner's step loop is strict: `executor.inject(step.fault); clock.sleep(step.convergence_budget);
      step.assertion.evaluate(metrics).await`. Budget elapses BEFORE evaluation.
    - Muscle: ordering matters in chaos — inject, wait for convergence, then assert. Reapplies at:
      W108 Thu runner main loop, W109 ops-runbook step sequencing.

  - **When `env_override_relaxes_threshold` shows the override didn't apply:**
    - Symptom: assertion fired with `2us` threshold despite `env/ci.toml` setting `10us`.
    - Why: config layering merged base + env at scenario LOAD time, but the assertion read a stored
      `threshold_us: 2` that was set at scenario construction (before env load).
    - Fix: assertion stores a reference to the config key (`metric_name`, `threshold_id`) and
      resolves at evaluation time. Or: scenario load takes env layer as input and folds during
      construction so every Assertion ends up with the final threshold. Either works; pick one and
      document.
    - Muscle: config layering is either resolved-at-load OR resolved-at-eval — never mixed; the
      mismatch produces subtle "the value I set in YAML doesn't apply" bugs. Reapplies at: W109
      ops-runbooks config, W105 monitoring alert thresholds.

  - **When `convergence_budget_overflow_rejected` accepts a 10-second budget into a 5-second gap:**
    - Symptom: validator returns OK; runner schedules next inject mid-convergence; assertion attributes
      a real failure to the wrong fault.
    - Why: validator only checked monotonicity, not budget vs gap.
    - Fix: second validator pass: `for i in 0..steps.len()-1 { let gap = steps[i+1].at_offset -
      steps[i].at_offset; if steps[i].convergence_budget > gap { return Err(BudgetOverflow { step: i
      }); } }`.
    - Muscle: validators enforce the structural invariants; the runtime trusts the validated input.
      Reapplies at: W108 Thu runner trusts scenario, W107 deploy plan validator.

  - **When `flake_rate_recorded_per_scenario` records 0% despite 5% deliberate flake:**
    - Symptom: scenario ran 100 times, 5 failed, flake rate recorded as 0.
    - Why: flake-tracking sidecar listened only to scenario START events, not END events with pass/fail.
    - Fix: ScenarioResult emits a `chaos_scenario_runs_total{id, outcome="pass|fail"}` counter.
      30-day flake rate is computed as `rate(fail{...}[30d]) / rate(total{...}[30d])`.
    - Muscle: track outcomes as counters with labels; rates derive from time-windowed PromQL.
      Reapplies at: W109 ops-runbook SLO tracking, W105 metric design.

  - **When `assertion_failure_snapshot_contains_metrics_and_spans` shows empty span_ids:**
    - Symptom: snapshot JSON has empty `span_ids: []` even though spans were emitted during the
      scenario.
    - Why: snapshot collected spans from `tracing::Span::current()` at the moment of failure — but
      the failing assertion ran in a different tokio task than the spans of interest.
    - Fix: scenario runner enables tail-sampling: keep last 5 s of all span IDs in a ring buffer;
      on failure, the buffer's contents are dumped to the snapshot.
    - Muscle: tail-sample by default for debuggability; don't rely on "current" context across
      async boundaries. Reapplies at: W105 tracing bridge sampling, W109 ops-runbook trace dumps.

  - **5-year failure mode** (write in `notes/108_scenario_followup.md` after green): when scenarios
    grow to 100+ steps (full-day chaos schedules), the linear-time validator and single-process
    runner become inadequate. Migration trigger: scenario decomposition into "scenes" (parallel
    sub-scenarios) with explicit inter-scene barriers. Name the new invariant (no cross-scene fault
    overlap) and the merger discipline.

**Thursday — ops-chaos: runner**

- [ ] **Build**: `crates/ops-chaos/src/runner.rs` — executes scenarios against a live deployment. Logs results. (~total 110 min across 3 phases)
  - 🔧 **Why this matters**: the runner is the *event loop* that ties faults, time, and assertions
    together. The runner's correctness is *more important than* any single fault primitive — a buggy
    runner silently passes scenarios. The runner is also the boundary between deterministic-time chaos
    (in-process tests using a simulated `Clock`) and real-world chaos (the rig with `Clock::system()`);
    both must share code so a green CI scenario maps to a meaningful rig scenario. Downstream consumers:
    W108 Friday/Saturday chaos drills use this runner; W109 ops-runbooks read `ScenarioResult` artifacts;
    M30 bar-(c) audit cites 50+ scenarios green for 30 consecutive nights — all run by this struct.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: a buggy runner silently passes broken scenarios — assertions
    that "succeed" because they never ran, or "fail" because the metric was stale. The runner must
    enforce: convergence budgets, metric freshness, cleanup-on-panic, no-parallel-scenario-on-same-host,
    and clock abstraction (sim vs real). If any of these break, every chaos result is suspect.

  - **Requirements** — write in `crates/ops-chaos/notes/108_runner_design.md`:
    - R1. `Clock` trait abstracts sim vs real time: `now()`, `sleep_until(t)`. Sim impl is a sorted heap
      of pending wakers (re-use the runtime-thread-per-core deterministic Clock from earlier weeks).
    - R2. Runner is single-threaded per scenario — steps run strictly serial; parallelism is across
      scenarios via a multi-scenario harness.
    - R3. On step panic (including in `Custom` assertion closures), runner catches and routes to
      cleanup — never leaks faults.
    - R4. On scenario failure, runner collects artifacts: metric snapshot JSON, last 5 s of OTLP
      spans, optional `tcpdump` pcap, optional `perf record`.
    - R5. Cleanup drops all open `FaultHandle`s in REVERSE-inject order (LIFO); post-cleanup state is
      verified by `iptables-save | grep OPSCHAOS-` returning empty.
    - R6. Concurrent runners on same host are forbidden — filesystem lockfile at
      `/var/run/ops-chaos.lock` enforced.
    - R7. Metric staleness check: assertions poll the metric source until either a tick newer than
      inject-time OR the budget expires; mark assertion "stale" if budget expires with no update.
    - R8. Real-clock assertions use absolute deadlines (`inject_at + within`), not relative durations,
      so cumulative jitter doesn't push assertions past their deadlines.
    - R9. Result printer emits non-zero exit code on any failure; readable summary table for CI logs.

  - **Design walk-through** — answer each in your design doc; no peeking at TigerBeetle
    `src/vopr/runner.zig` or chaos-mesh `controllers/workflow` until Phase 3:
    - D1. `Clock` trait: list the 3 methods. How does sim impl `advance()` differ from real impl?
      What's the invariant that sim time only moves forward when something requests it?
    - D2. Panic handling: `tokio::task::spawn_blocking` + `catch_unwind` vs `panic = abort` vs custom
      panic hook. Argue which gives R3 + reliable cleanup. (Hint: `catch_unwind` requires `UnwindSafe`;
      `FnMut` is not.)
    - D3. Artifact collection ordering: when does pcap start (before scenario or before failing step)?
      What's the cost of full-scenario pcap vs tail-sample?
    - D4. Cleanup LIFO: why reverse-inject order? Give a concrete example where order matters (e.g.
      DiskCorrupt + DiskFull on same mount).
    - D5. Lockfile semantics: flock vs PID file vs filesystem rename. R6's "must not run concurrently"
      and "must survive crash" both need to hold.
    - D6. Metric staleness: how do you know a metric was updated since inject_time? Timestamp embedded
      in the metric? A scrape-cycle counter? Trade-offs.
    - D7. Deadline vs duration: walk through the 60-min scenario where step 50 inject is at T+58 min;
      if its assertion deadline is "inject_time + 100ms" vs "T+58:00.1 min", what's the failure mode
      under cumulative jitter?
    - D8. **Pre-mortem (the load-bearing question)**: write the 8-step interleaving where (a) runner
      injects Partition, (b) custom assertion closure panics with a `unwrap()` on missing metric,
      (c) panic bubbles up to the tokio task, (d) task aborts mid-cleanup, (e) iptables rules remain,

  #### Phase 3 — Make the tests pass, one failure at a time (~50 min)

  - **When `panic_in_custom_assertion_triggers_cleanup` leaks iptables rules:**
    - Symptom: test's `iptables -L | grep OPSCHAOS-` shows rules remaining after the panicking
      scenario completes.
    - Why: panic unwound through the runner's main loop; the per-scenario tokio task aborted;
      Drop impls didn't run for `FaultHandle`s because they were owned by the aborted task.
    - Fix: wrap each step body in `std::panic::catch_unwind`. On caught panic, route to cleanup
      path explicitly — iterate the runner's `open_handles: Vec<FaultHandle>` and call `recover()`
      on each in reverse order. Also enable `panic = abort` for the test binary as a backstop.
    - Muscle: panic safety + RAII is hard in async; manage open resources via an explicit collection
      and drain on cleanup. Reapplies at: W109 ops-runbook cleanup, W107 deploy-script cleanup.

  - **When `concurrent_runners_blocked_by_lockfile` shows both runners proceeding:**
    - Symptom: both runner processes acquire "lock" and run scenarios; iptables rules collide.
    - Why: lockfile used a PID file (`echo $$ > /var/run/ops-chaos.lock`); race condition where both
      processes write before either checks.
    - Fix: use `fcntl(F_SETLK)` or `flock` on an FD held for the runner's lifetime. `flock -n 200 ||
      exit 1` in the wrapper. The FD is auto-released on process exit (covers R6's crash case).
    - Muscle: PID files are race-prone; flock-on-fd is the only correct cross-process mutex on POSIX.
      Reapplies at: W109 cron-job locking, W107 deploy lock.

  - **When `stale_metric_marked_stale_not_passed` marks it as PASS:**
    - Symptom: assertion reads metric value (1.0, from 30 s ago), threshold is "≤ 2.0", returns Pass.
      Real system actually has 5.0 right now but the metric hasn't been re-scraped.
    - Why: assertion reads metric value without checking the metric's timestamp.
    - Fix: every metric carries `last_updated_at: Instant`. Assertion polls metric until
      `last_updated_at > inject_time + scrape_interval` OR budget expires. If budget expires first,
      result is `Stale`, not `Pass`.
    - Muscle: stale metric = unknown state ≠ healthy state; treat staleness as a distinct outcome.
      Reapplies at: W109 ops-runbook alert rules, W105 monitoring freshness SLO.

  - **When `cleanup_lifo_order` shows recover called in inject-order (FIFO):**
    - Symptom: cleanup called recover(DiskCorrupt) then recover(DiskFull); but DiskCorrupt depended
      on DiskFull being already-removed; cleanup error.
    - Why: runner's `open_handles` iterated in insertion order (Vec push order = inject order); cleanup
      walked forward.
    - Fix: cleanup walks `open_handles` in reverse — `for handle in open_handles.iter().rev() {
      executor.recover(handle); }`. LIFO undoes most-recent fault first.
    - Muscle: nested resource cleanup is LIFO; same discipline as nested locks or stack-allocated
      RAII. Reapplies at: W107 deploy rollback, W109 ops-runbook unwind.

  - **When `real_clock_assertion_uses_absolute_deadline` fires at relative+0.1 instead of absolute:**
    - Symptom: scenario step 50 took 2 s longer than planned (CPU contention); assertion deadline
      computed as `inject_finished + within` = T+58:02.1, not T+58:00.1. Misses the convergence budget
      because the system actually finished converging at T+58:00.6.
    - Why: deadline was stored as `Duration` from inject; in real-clock runner, inject-finished time
      drifts.
    - Fix: deadline is computed at scenario START as `scenario_start + step.at_offset +
      step.convergence_budget`. Absolute wall-clock; jitter in inject doesn't shift it.
    - Muscle: schedules are absolute, not relative; relative scheduling accumulates jitter.
      Reapplies at: W106 synthetic feed pacing, W109 ops-runbook scheduling.

  - **When `failure_collects_metric_snapshot_and_spans` shows empty spans.json:**
    - Symptom: failure collected metric_snapshot but spans.json is `[]`.
    - Why: tracing-otel batch processor hadn't flushed at the moment of snapshot; spans were in the
      queue but not yet committed.
    - Fix: snapshot path calls `tracing_bridge.force_flush(deadline=2s)` BEFORE reading spans. Or:
      runner maintains its own span-tail-buffer (last 5 s of spans, ring-buffer style); on failure,
      dumps the ring buffer regardless of OTLP state.
    - Muscle: failure capture needs explicit flush of any batched system before reading; don't trust
      "the batch will eventually drain". Reapplies at: W109 ops-runbook incident dump, W105 tracing
      bridge shutdown.
