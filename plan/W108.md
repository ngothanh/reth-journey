  #### Phase 1 — Problem, prediction, design (~25 min, no code yet)

  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/ops-chaos/notes/108_fault_prediction.md`:
    - P1: the primitive you'd reach for to run recovery in `Drop` (exact import line — `std::process::Command`? `tokio::spawn`? a deferred-cleanup queue?).
    - P2: predicted wall-cost of one `iptables -A` invocation (process spawn + exec + kernel netfilter table write) — name it in **µs/ms** and which Jeff-Dean number dominates (syscall 300 ns is NOT it — a `fork+exec` is ~1-3 ms).
    - P3: predicted outcome of `inject(same_fault)` called twice on a naive impl that allocates a fresh monotonic ID each time (how many iptables rules end up installed?).
    - P4: derive-correctness prediction — will `#[derive(PartialEq, Hash)]` on `Fault` give you a usable `FaultKey` for the idempotency side-table, or does a field break it (think `f64` latency, `Arc`)?
    - P5: **list every Phase-2 test you predict your first attempt will fail.** Compare to reality after tests run.
  - *Mental model*: `Fault` is the chaos verb set; `FaultHandle` is the RAII undo token. Inject returns a handle; if the handle drops without an explicit `recover()`, `Drop` MUST still clean up — chaos that leaks state corrupts the next test's attribution.
  - *Contract* (signatures only — never the body):
    ```rust
    pub enum Fault {
        KillProcess(Pid),
        NetworkPartition { from: NodeId, to: NodeId },
        LatencyInject { node: NodeId, ms: u32 },
        PacketDrop { node: NodeId, pct: u8 },
        DiskFull(MountPoint),
        DiskSlow { mount: MountPoint, added_ms: u32 },
        ClockSkew { node: NodeId, delta_ms: i64 },
        ResourceLimit { node: NodeId, cpu_pct: u8 },
    }
    pub struct FaultHandle { /* id, tag, recovery closure/spec */ }
    impl Fault   { pub fn inject(&self, ctx: &ChaosCtx) -> io::Result<FaultHandle>; }
    impl FaultHandle { pub fn recover(self) -> io::Result<()>; }
    impl Drop for FaultHandle { /* synchronous cleanup, no runtime dependency */ }
    pub fn cleanup_on_startup(ctx: &ChaosCtx) -> io::Result<usize>; // returns # rules removed
    ```
  - *Back-of-envelope*: an `iptables -A` is a `fork`+`exec`+netfilter write ≈ **1-3 ms per rule** (NOT a 300 ns syscall — it spawns a whole process). A 4-rule partition costs ~8 ms to inject. The cliff: if you forget R7 and DON'T subtract injection cost from latency attribution, a scenario asserting "p99 ≤ 2 ms after partition" measures **8 ms of YOUR injection** on top of the SUT — a 4× false positive. That is why the inject-cost metric (R7) is correctness, not vanity.
  - **Requirements** R1..R7 — write in `crates/ops-chaos/notes/108_fault_design.md`:
    - R1. `Fault` is a typed `enum` covering the 8 fault classes (Process, Partition, Latency, Drop, Disk-Full, Disk-Slow, Clock-Skew, Resource).
    - R2. Every `inject` returns a `FaultHandle` that, if dropped without `recover`, runs recovery in its `Drop` impl (RAII), **synchronously**.
    - R3. Faults are idempotent — `inject(same)` twice returns the same handle; `recover(already)` is a no-op.
    - R4. Recovery is exhaustive — partition recovery deletes EVERY iptables rule tagged `OPSCHAOS-<id>`; no rule left behind.
    - R5. Cleanup-on-startup scans `iptables-save` + `tc qdisc show` for `OPSCHAOS-` entries and removes them (covers a crashed previous run).
    - R6. `ClockSkew` does NOT poison the chaos host's clock — applied via time namespace (`setns(CLONE_NEWTIME)`, kernel ≥ 5.6) or `libfaketime` LD_PRELOAD fallback.
    - R7. `chaos_inject_duration_ms{fault_type}` metric emitted per fault so latency attribution can subtract injection cost.
  - **Design walk-through** D1..D7 — answer in the design doc; no peeking at Jepsen `nemesis.clj` or chaos-mesh `pkg/chaosdaemon` until Phase 3:
    - D1. Enum vs `trait Fault` with `dyn` dispatch? Argue from R1 + audit: an enum is exhaustively matchable (`match` proves all 8 handled at compile time; the M30 audit greps the enum), serializable for replay, and `Hash`-able for the idempotency key. A trait object is none of these.
    - D2. RAII handle property table — enumerate every recovery mechanism with (Sync? needs-runtime? fails-if-runtime-gone? blocking?):
      | mechanism | sync | needs runtime | leaks if runtime gone | blocking |
      |---|---|---|---|---|
      | `Command::new("iptables").arg("-D")` from Drop | yes | no | no | yes (~ms) |
      | `tokio::spawn(recover())` from Drop | no | yes | **YES** | no |
      | deferred-cleanup queue drained by top-level guard | yes | no | no | yes |
    - D3. Idempotency: `FaultKey` = canonical hash of the variant + params, in a `HashMap<FaultKey, FaultHandle>` side-table. Why hash and not `==` scan? O(1) vs O(n) on every inject.
    - D4. Tagging: every rule gets `-m comment --comment OPSCHAOS-<scenario-id>-<seq>`. Why scenario-id AND seq? scenario-id scopes cleanup to one drill; seq disambiguates the 4 directional rules of one partition.
    - D5. ClockSkew: list 3 ways to skew CLOCK_REALTIME for ONE process without touching the host (time namespace via `setns`; `libfaketime` LD_PRELOAD; a userspace shim VDSO). Pick one + justify (portability vs simplicity).
    - D6. Observer effect: chaos injection adds latency. Subtract it via per-fault `inject_duration_ms` (R7); the attribution code reads it. (See Back-of-envelope.)
    - **D7. Pre-mortem (load-bearing):** write the EXACT 6-line bad trace where (a) drill injects Partition tag `OPSCHAOS-42-1`, (b) chaos process SIGKILL'd before `recover`, (c) operator manually deletes one of the 4 rules, misses 3, (d) next drill starts, (e) sees half-partitioned state, (f) attributes its own (clean) result to those stale rules. Convince yourself R5's cleanup-on-startup catches every line.
  - **Output**: `notes/108_fault_design.md` with R1–R7, D1–D7, the enum sketch, the iptables tagging convention, the cleanup-on-startup pseudocode, the D7 6-line trace.

  #### Phase 3 — Make the tests pass, one failure at a time (~35 min)

  Ordered newbie→expert — the ladder the learner walks.

  - **(NEWBIE) When `dropped_handle_runs_recovery` shows iptables rules still present after drop:**
    - Symptom: handle dropped, `ctx.iptables_rules_tagged()` is non-empty; next test inherits a stale partition.
    - Why: `FaultHandle::Drop` called `tokio::spawn(recover())` on a tokio runtime that the test had already torn down at scope exit; `spawn` returned a `JoinHandle` that was immediately dropped, recovery never ran.
    - Fix: synchronous faults (iptables, tc, dmsetup) recover synchronously — call `Command::new("iptables").arg("-D")…` from `Drop` directly. Only cross-host SSH faults need async; for those register a process-wide deferred-cleanup queue drained by a top-level guard before exit. Never `spawn` into nothing.
    - Muscle: `Drop` must not depend on a runtime that may already be gone; synchronous cleanup is simpler and more reliable. Reapplies at: W107 deploy-script cleanup, W109 production shutdown hooks, W110 ops shutdown guard.

  - **(SENIOR) When `idempotent_inject_returns_same_handle` returns two distinct handles (and 8 rules):**
    - Symptom: same fault injected twice yields different `id()`s and 8 iptables rules instead of 4.
    - Why: code allocated a fresh monotonic ID on every inject without consulting a registry of what's already injected.
    - Fix: maintain `injected: HashMap<FaultKey, FaultHandle>` keyed by a canonical hash of variant+params (note P4: a `f64` field would break `Hash`/`Eq` — `LatencyInject.ms` is `u32` on purpose). Look up first; return the existing handle if found.
    - Muscle: idempotency = side-table lookup before allocation; never assume injection is fresh. Reapplies at: W108 Wed scenario-step idempotency, W107 deploy idempotency, W109 runbook re-run safety.

  - **(EXPERT) When `partition_recover_deletes_all_tagged_rules` leaves rules behind after the interleaved insert:**
    - Symptom: 4 rules installed, an unrelated rule inserted at position 1, recover removes 0-2 of the 4.
    - Why: recover ran `iptables -D FORWARD <original-spec>` / by stored line number; iptables matches by exact position and the inserted rule shifted every line number — the stored numbers now point at the wrong (or nonexistent) rules.
    - Fix: recover never reproduces the exact spec or trusts a stored line number. It runs `iptables -L FORWARD --line-numbers | grep OPSCHAOS-<id>` to discover ALL tagged rules at recovery time and deletes them by current line number **in reverse order** (so a delete doesn't invalidate later numbers). Re-grep to verify empty.
    - Cost avoided: a single leaked DROP rule silently half-partitions the next drill → every downstream attribution wrong; debugging it costs hours, not the ~1 ms the correct delete costs.
    - Muscle: position-based commands need reverse-order deletion; tag-based *re-discovery at recovery time* is the only safe cleanup pattern. Reapplies at: W108 Thu runner cleanup, W109 ops-runbooks tag policies, W107 deploy resource teardown.

  - **(EXPERT) When `cleanup_on_startup_removes_stale_rules` returns Ok but the rule remains:**
    - Symptom: `cleanup_on_startup` returns `Ok(1)` (or 0) but `iptables_rules_tagged()` is still 1.
    - Why: cleanup ran `iptables -L FORWARD | grep OPSCHAOS-` to find rules then fed iptables's *display format* back as a `-D` delete spec — iptables does not accept its own list output as a delete argument.
    - Fix: the auditable round-trip is `iptables-save | grep -v OPSCHAOS- | iptables-restore` (rewrite the table excluding tagged rules), OR `--line-numbers` + reverse-order `-D <N>` as above. Verify with a re-grep; return the count actually removed.
    - Muscle: shelling out to system tools requires knowing their input/output asymmetry; `iptables-save`/`restore` is the auditable round-trip. Reapplies at: W109 cron-based cleanup, W108 Thu runner cleanup.

  - **(EXPERT) When `clockskew_doesnt_affect_host_clock` shows host drift ≥ 5000 ms:**
    - Symptom: `ClockSkew { delta_ms: 5000 }` and the chaos host's own clock jumps 5 s — corrupting the chaos log's timestamps.
    - Why: code called `clock_settime(CLOCK_REALTIME, …)` from the chaos process; `CLOCK_REALTIME` is global, no namespacing.
    - Fix: `setns(target_fd, CLONE_NEWTIME)` to enter the SUT's time namespace BEFORE the syscall (kernel ≥ 5.6). On older kernels fall back to `libfaketime` LD_PRELOAD on the SUT process. A compile-time feature flag picks the strategy.
    - Muscle: any "system" syscall needs namespacing awareness or you poison the host; time/net/PID namespaces are the isolation primitives. Reapplies at: W108 Wed scenario clock semantics, W109 production clock SLA.

  - **(EXPERT, perf — bar (b) but load-bearing) When `inject_cost_metric_lands_in_plausible_band` records ~0 ms:**
    - Symptom: `chaos_inject_duration_ms{Partition}` is 0.0, band assertion fails on the lower bound.
    - Why: the metric was emitted (`histogram.observe`) BEFORE the `Command::new("iptables")` ran — it timed an empty span. The fork+exec cost (~1-3 ms × 4 rules) was never captured.
    - Fix: bracket the *actual* injection: `let t0 = Instant::now(); run_iptables_rules(); metric.observe(t0.elapsed().as_secs_f64()*1000.0);`. The observation must wrap the syscall-spawning work.
    - Cost avoided: ~8 ms of injection cost wrongly attributed to the SUT → a scenario asserting "p99 ≤ 2 ms" sees 10 ms and false-alarms a 5× regression that doesn't exist. (Not a "slow" bug — a *correctness* bug in attribution.)
    - Muscle: measure the span that contains the cost, not the span before it; a back-of-envelope (fork+exec ≈ ms, not 300 ns) tells you 0.0 is impossible and must be a wiring bug. Reapplies at: W109 ops-runbook latency attribution, W105 metric-emission ordering, W106 synthetic-feed pacing cost.

  - *Mental model*: a `Scenario` is a sorted timeline of `(at_offset, fault, convergence_budget, assertion)` steps; the budget is the contract "the system must converge within this window before I assert or move on." It is the regression corpus: every scenario added is a permanent guard against the bug it found.
  - *Contract*:
    ```rust
    pub struct ScenarioStep {
        pub at_offset: Duration,
        pub fault: Fault,
        pub convergence_budget: Duration,
        pub assertion: Assertion,
    }
    pub struct Scenario { steps: Vec<ScenarioStep>, /* sorted, validated */ }
    pub enum Assertion {
        QuorumHealthy, LeaderElected, NoReplicaDivergence, LedgerReconciliationZero,
        LatencyP99Under(Duration), MetricEq { name: String, value: f64 },
        Custom(#[serde(skip)] Option<Arc<dyn Fn(&Metrics) -> bool + Send + Sync>>),
    }
    impl Scenario {
        pub fn from_toml(s: &str, env: &EnvLayer) -> Result<Self, ScenarioError>;
        pub fn validate(&self) -> Result<(), ScenarioError>;
    }
    pub enum ScenarioError { StepOrder { at: usize }, BudgetOverflow { step: usize }, Parse(..) }
    ```

  - **(NEWBIE) When `out_of_order_steps_rejected` accepts the bad scenario:**
    - Symptom: steps `[0,5,3]` loaded OK; at runtime the runner sleeps to T+5 then computes a negative duration to T+3 and panics.

  - **(EXPERT) When `assertion_waits_for_convergence_budget` evaluates at +50 ms instead of +500 ms:**

    ```rust
        fn sleep_until(&self, t: Instant) -> impl Future<Output=()>;

        pub fn sim(clock: SimClock) -> Runner<SimClock>;
        pub fn real() -> io::Result<Runner<SystemClock>>; // acquires /var/run/ops-chaos.lock
        pub fn run(&mut self, s: &Scenario) -> ScenarioResult;
    }
    ```

  #### Phase 3 — Make the tests pass, one failure at a time (~45 min)

  - **(NEWBIE) When `exit_code_nonzero_on_any_failure` returns 0:**
    - Symptom: a 10-step scenario with 1 failing step exits 0; CI goes green on a real failure.
    - Why: the printer summarized results but the process exit code defaulted to 0; the `Outcome::Fail` never propagated to `std::process::exit`.
    - Fix: `let code = if result.any_failure() { 1 } else { 0 }; process::exit(code);`. Outcome must drive the exit.
    - Muscle: a test harness that can't fail CI is worse than none; always wire the failure path to a non-zero exit. Reapplies at: W109 ops-runbook check exit codes, W107 deploy gate.

  - **(EXPERT) When `panic_in_custom_assertion_triggers_cleanup` leaks iptables rules:**
    - Symptom: `iptables -L | grep OPSCHAOS-` non-empty after the panicking scenario; next scenario inherits the partition.
    - Why: the panic unwound through the runner's main loop; the per-scenario tokio task aborted; `Drop` for `FaultHandle`s owned by the aborted task never ran.
    - Fix: wrap each step body in `std::panic::catch_unwind(AssertUnwindSafe(|| …))` (P4: `FnMut` is not `UnwindSafe`, hence the assert wrapper). On a caught panic, route to the explicit cleanup path — iterate `self.open_handles` in reverse and `recover()` each. `panic=abort` in the test binary as a backstop.
    - Muscle: panic-safety + RAII is hard in async; manage open resources in an explicit collection and drain on cleanup, never rely on Drop surviving a task abort. Reapplies at: W109 ops-runbook cleanup, W107 deploy-script cleanup, W108 Tue FaultHandle Drop.

  - **(SENIOR) When `concurrent_runners_blocked_by_lockfile` shows both runners proceeding:**
    - Symptom: both processes "acquire" the lock and run; iptables rules collide.
    - Why: lockfile was a PID file (`echo $$ > /var/run/ops-chaos.lock`); a TOCTOU race where both write before either checks.
    - Fix: `flock(fd, LOCK_EX | LOCK_NB)` on an FD held for the runner's lifetime (or `fcntl(F_SETLK)`). On `WouldBlock`, return `Err`. The FD auto-releases on process exit — covering `lockfile_released_on_crash`.
    - Muscle: PID files are race-prone; `flock`-on-held-FD is the only correct cross-process mutex on POSIX, and it survives crashes for free. Reapplies at: W109 cron-job locking, W107 deploy lock.

  - **(EXPERT) When `stale_metric_marked_stale_not_passed` reports PASS:**
    - Symptom: assertion reads value 1.0 (from 30 s ago), threshold ≤ 2.0, returns Pass — while the live system is actually at 5.0 but the metric hasn't re-scraped.
    - Why: the assertion read the metric value without checking its timestamp.
    - Fix: every metric carries `last_updated_at: Instant`. The assertion polls until `last_updated_at > inject_time + scrape_interval` OR budget expires; if budget wins, outcome is `Stale`.
    - Muscle: a stale metric is unknown state, not healthy state — treat staleness as a distinct outcome. Reapplies at: W109 ops-runbook alert rules, W105 monitoring freshness SLO.

  - **(EXPERT) When `cleanup_lifo_order` recovers FIFO and errors:**
    - Symptom: cleanup calls `recover(DiskFull)` then `recover(DiskSlow)`; DiskSlow's `tc` qdisc removal fails because the mount state it expected was already torn down.
    - Why: `open_handles` was iterated in insertion (inject) order; cleanup walked forward.
    - Fix: cleanup walks `self.open_handles.iter().rev()` — LIFO, undo the most-recent fault first.
    - Muscle: nested resource cleanup is LIFO, same as nested locks or stack RAII. Reapplies at: W107 deploy rollback, W109 ops-runbook unwind, W108 Tue recovery ordering.

  - **(EXPERT) When `real_clock_assertion_uses_absolute_deadline` slides to relative+0.1:**
    - Symptom: step 50 took 2 s longer than planned (CPU contention); the assertion deadline became `inject_finished + within` = T+58:02.1, missing the convergence budget though the system converged at T+58:00.6.
    - Why: the deadline was stored as a `Duration` from inject; in real-clock mode inject-finished time drifts.
    - Fix: deadline computed once at scenario start as `scenario_start + step.at_offset + step.convergence_budget` — absolute wall-clock; inject jitter doesn't shift it.
    - Muscle: schedules are absolute, not relative; relative scheduling accumulates jitter over long runs. Reapplies at: W106 synthetic-feed pacing, W109 ops-runbook scheduling.

  - **(SENIOR) When `failure_collects_metric_snapshot_and_spans` shows empty spans:**
    - Symptom: `artifacts.spans` is empty though spans were emitted.
    - Why: the OTLP batch processor hadn't flushed at snapshot time — spans were queued, not committed.
    - Fix: snapshot calls `tracing_bridge.force_flush(Duration::from_secs(2))` before reading, OR (preferred) the runner keeps its own 5-s span ring buffer (shared with the scenario tail-sampler from Wed) and dumps it regardless of OTLP state.
    - Muscle: failure capture must explicitly flush any batched subsystem before reading; never trust "the batch will eventually drain." Reapplies at: W109 ops-runbook incident dump, W105 tracing-bridge shutdown.
