    init, W74 raft lazy leader-elect.

    - Symptom: every setter allocates a fresh `Box::new(value)` *before* each CAS attempt and drops it on every
      losing retry; under 4 contenders p99 `set` latency balloons to ~150 ns and a heap profiler shows ~N allocs
      per successful set instead of 1.
    - Why: you `Box::into_raw(Box::new(v))` inside the retry loop, so every lost CAS pays a `malloc` + `free` round
      trip that has nothing to do with the actual work — the allocation is hoisted into the hot retry path.
    - Fix: allocate the box ONCE before the loop; on a losing CAS reuse the same raw pointer for the next attempt;
      only the winner's box survives (it is intentionally leaked into the `AtomicPtr`), and a setter that ultimately
      loses does `Box::from_raw` + drop exactly once after the loop exits, never per retry.
    - Cost avoided: ~50 ns `malloc` + ~30 ns `free` per losing retry = ~80 ns/retry; at 4 contenders averaging ~3
      retries that is ~240 ns/op of pure allocator churn, plus heap fragmentation (bar (c) violation — a Layer-1
      substrate set must be O(1) allocations, not O(retries)).
    - Muscle: never allocate inside a CAS retry loop — hoist the allocation above the loop and reuse the raw pointer.
      Reapplies at: W42 txn slot-table lazy init, W65 Disruptor claim loop, W74 raft leader-elect box reuse.
  - **Numbers**: predict CAS-loop iteration count under N concurrent setters (likely log N on amortized);
    p50/p99 CAS latency uncontended (~10 ns) vs 4 contenders (~30-50 ns due to MESI cross-core); drop-cost
