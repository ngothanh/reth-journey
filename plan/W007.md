- [ ] **Concurrency drill #5 of 28 — `AtomicOnce<T>` with concurrent set callers (CAS contention)** (solo, ~5 hrs).
  Re-do drill #1's `OnceFlag<T>` semantics but allow N writers to race for "set the value." Only one wins; the
  losers see `AlreadySet`. The CAS pattern is the muscle.
  Build `crates/concurrent/src/atomic_once.rs` — `AtomicOnce<T> { ptr: AtomicPtr<T> }`. API:

  - 🔧 **Why this matters**: EIP-7702 authorizations are a NEW signed object type — a tuple `(chain_id, address,
    nonce)` signed by the EOA, with a `0x05` MAGIC byte domain-separator. Forget the magic byte and recover yields
    a plausible-but-wrong address (silent bug, not an error); miss the EIP-2 low-s check and signatures are
    malleable. Downstream: W7 Tue (TxEip7702), W49 revm 7702 delegation, W8 receipt.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: an EOA temporarily delegates its code to a contract. The
    Authorization is signed; signing-hash uses a domain-separator (0x05 magic) to prevent reuse as a regular
    tx signature. recover_authority must reconstruct the exact signed bytes byte-for-byte.

  - **Requirements** — write in `crates/eth-consensus/notes/07_eip7702_design.md`:
    - R1. `struct Authorization { chain_id: U256, address: Address, nonce: u64 }`.
    - R2. `signature_hash() = keccak256(0x05 || rlp([chain_id, address, nonce]))` — the MAGIC byte is
      LOAD-BEARING.
    - R3. `struct SignedAuthorization { inner: Authorization, y_parity: u8, r: U256, s: U256 }` — RLP list of
      6 fields.
    - R4. `recover_authority() -> Result<Address, RecoveryError>` — ecrecover with low-s validation
      (EIP-2).
    - R5. chain_id `0` is the WILDCARD (any chain); accept if `chain_id == 0 || chain_id ==
      current_chain_id`.
    - R6. Reject high-s signatures: `s <= secp256k1n / 2` (EIP-2 malleability).
    - R7. `nonce` field preserved byte-exact in codec; execution-time binding to account nonce is the
      consumer's job (documented).

  - **Design walk-through** — answer each:
    - D1. Walk through `signature_hash` byte-by-byte for a sample auth.
    - D2. Why is `0x05` the magic byte? (Hint: domain separation — same auth bytes can't be replayed as
      a tx hash.)
    - D3. ecrecover: low-s check — what's secp256k1n / 2? Why does high-s allow two valid sigs for one
      address?
    - D4. chain_id 0 wildcard: walk through 3 cases: chain_id=0 on mainnet, chain_id=1 on mainnet,
      chain_id=1 on Sepolia. Accept/reject?
    - D5. nonce: 64-bit RLP integer. Why minimal-stripped? Why is execution-binding the consumer's job?
    - D6. **Pre-mortem**: contributor forgets the 0x05 prefix. recover_authority returns A wrong
      address. What test catches it? (Hint: a known fixture from EIP-7702 spec.)
  - **Output**: `notes/07_eip7702_design.md` with R1–R7 + D1–D6.
