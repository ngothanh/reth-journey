- [ ] **Build**: `crates/eth-consensus/src/eip2930.rs` — AccessList. Wire into TxEip1559 + TxEip4844. (~150 min)
  - *Mental model*: EIP-2930 lets a transaction pre-declare which `(address, storage_keys[])` pairs it will touch, so
    those accesses are charged a discounted gas rate. The list is purely a gas-pricing hint, but it is part of the
    signed payload and the tx hash — so it must encode identically everywhere.
  - *Contract*: `struct AccessListItem { address: Address, storage_keys: Vec<B256> }` and
    `struct AccessList(Vec<AccessListItem>)`, both `Encodable`/`Decodable`. An `AccessListItem` is an RLP list of two
    elements: an address (20-byte string) and a list of 32-byte storage keys. `AccessList` is an RLP list of those
    items. Then add an `access_list: AccessList` field to `TxEip1559` and `TxEip4844`.
  - **Expect to hit #1 — empty access list ≠ omitted field**: treating an empty `AccessList` as "leave the field out"
    of the tx encoding. Symptom: every legacy-style or unadorned EIP-1559 tx hash mismatches `cast`/Geth because the
    list slot is missing.
    - Fix: an empty `AccessList` always encodes as the empty RLP list `0xc0` — it occupies a fixed positional slot.
    - Muscle: a fixed-position RLP field is always present; "empty" is a value, not an absence. Reapplies at: W7
      Thursday `TxEnvelope`, W8 Receipt.
  - **Expect to hit #2 — wiring it at the wrong list position**: appending `access_list` after `signature`/`v,r,s`
    or in a different slot than the spec's field order. Symptom: signature recovery yields a wrong sender; the tx is
    rejected as having an invalid signature.
    - Fix: insert `access_list` at the exact spec position (for EIP-1559: after `to,value,input`, before the
      signature fields) and keep struct field order matching the wire order.
    - Muscle: a tx struct's field order IS the signing preimage — placement is consensus-critical. Reapplies at: W7
      Tuesday `TxEip7702`, W8 Receipt.
  - **Expect to hit #3 — storage key not exactly 32 bytes**: decoding a storage key as a variable-length string and
    accepting short/long values. Symptom: a malformed tx with a 31-byte key decodes "successfully", or a leading-zero
    key round-trips non-canonically.
    - Fix: decode each storage key as a fixed `B256` (a 32-byte string) and reject any other length.
    - Muscle: fixed-width consensus fields must assert their exact length on decode. Reapplies at: W7 Wednesday
      `eip7685.rs` request bodies, W10 trie node hashes.

**Tuesday — EIP-7702 `Authorization` + `TxEip7702`**

- [ ] Read EIP-7702 + EIP-7685 specs end-to-end. (~60 min)
- [ ] **Build**: `crates/eth-consensus/src/eip7702.rs` — Authorization, SignedAuthorization, recover_authority. (~150 min)
  - *Mental model*: EIP-7702 lets an EOA temporarily delegate its code to a contract. An `Authorization` is a tuple
    `(chain_id, address, nonce)` signed by the EOA; the *authority* (the signer's address) is recovered from that
    signature. Inside a `TxEip7702` it tells the EVM "set this EOA's code pointer to `address`".
  - *Contract*: `struct Authorization { chain_id: U256, address: Address, nonce: u64 }` with a method
    `signature_hash(&self) -> B256`. `struct SignedAuthorization { inner: Authorization, y_parity: u8, r: U256,
    s: U256 }` (RLP list of 6 fields). `fn recover_authority(&self) -> Result<Address, RecoveryError>` returns the
    signer address.
  - *recover_authority, roughly*: (1) build the signing preimage `MAGIC ++ rlp([chain_id, address, nonce])`;
    (2) keccak256 it to get the message hash; (3) ecrecover with `(y_parity, r, s)`; (4) keccak the recovered
    pubkey, take the low 20 bytes. Step 1's exact preimage is the real exercise.
  - **Expect to hit #1 — missing the 0x05 MAGIC prefix**: hashing `rlp([chain_id, address, nonce])` directly without
    prepending the single byte `0x05`. Symptom: `recover_authority` returns a plausible-looking but wrong address;
    the EVM rejects the delegation or, worse, delegates the wrong account — no error, just a wrong recovered address.
    - Fix: the signing hash is `keccak256(0x05 ++ rlp([chain_id, address, nonce]))`; the MAGIC byte is a
      domain-separator that distinguishes an authorization from a transaction.
    - Muscle: every signed Ethereum object has a domain-separating prefix — recover the wrong preimage and you get a
      wrong address, not an error. Reapplies at: W7 Thursday `TxEnvelope` tx-type prefixes, W8 Receipt.
  - **Expect to hit #2 — chain_id 0 rejected as invalid**: validating `chain_id` against the node's chain and
    rejecting `0`. Symptom: a legitimately cross-chain authorization (`chain_id == 0` = "valid on any chain") is
    dropped; or you accept a non-zero authorization on the wrong chain.
    - Fix: accept the authorization if `chain_id == 0` OR `chain_id == current_chain_id`; `0` is the any-chain
      wildcard, not an error value.
    - Muscle: EIP-7702 chain_id has a wildcard value — `0` means "any chain", check it before the equality test.
      Reapplies at: W13 EIP deep dives, W49 revm integration.
  - **Expect to hit #3 — high-s signature accepted (EIP-2 malleability)**: ecrecover succeeds for an `s` value in the
    upper half of the curve order, so two distinct signatures recover the same authority. Symptom: a malleated
    authorization is accepted; tx/authorization replay or hash-equivocation becomes possible.
    - Fix: reject the authorization unless `s <= secp256k1n / 2` and `y_parity` is 0 or 1 — the EIP-2 low-s rule.
    - Muscle: every signature consensus check must enforce low-s; high-s is malleable. Reapplies at: W7 Thursday
      `TxEnvelope` signature checks, W8 tx pool validation.
  - **Expect to hit #4 — nonce not bound at execution time**: treating the authorization's `nonce` as advisory and
    not checking it equals the authority's current account nonce when the tx executes. Symptom: a stale authorization
    is replayed in a later block, re-delegating an account the owner already moved on from.
    - Fix: the `nonce` field is purely data in the codec, but document that execution MUST require
      `authority.nonce == account.nonce` and increment it — the codec must preserve `nonce` exactly (u64, minimal
      RLP).
    - Muscle: a signed nonce is a replay guard only if execution binds it to live account state. Reapplies at: W49
      revm integration, W50 revm journaling.

  - *Contract*: `struct TxEip7702 { chain_id, nonce, max_priority_fee_per_gas, max_fee_per_gas, gas_limit, to,

    - Muscle: a tx type defined by a list field is only valid when that list is non-empty. Reapplies at: W7 Thursday

- [ ] **Build**: `crates/eth-consensus/src/eip7685.rs` — Request enum + requests_root. (~150 min)
  - *Mental model*: EIP-7685 is a general "execution layer → consensus layer" message channel. A `Request` is a
    typed opaque blob — one type byte followed by type-specific data (deposits, withdrawals, consolidations). The
    block commits to all requests via a single `requests_root` in the header.
  - *Contract*: `enum Request { Deposit(Bytes), Withdrawal(Bytes), Consolidation(Bytes) }` (or a
    `struct Request { request_type: u8, data: Bytes }`), with encode/decode that prepends the type byte. Plus
    `fn requests_root(requests: &[Request]) -> B256` (post-Prague: a flat keccak/hash over the typed request bytes,
    NOT a Merkle-Patricia trie root).
  - **Expect to hit #1 — type byte inside vs outside the hash**: computing `requests_root` over the request data
    without the leading type byte, or hashing each request separately instead of the concatenation. Symptom: the
    header `requests_hash` mismatches Geth — a consensus split at every block with requests.
    - Fix: follow the EIP-7685 commitment exactly — each request contributes `type_byte ++ data`; check whether the
      current spec wants per-type `keccak` then a concatenated hash, or a flat hash, and match it.
    - Muscle: a block-root commitment must hash the exact bytes the spec names, type prefix included. Reapplies at:
      W8 Receipt root, W10 trie roots, W15 EIP-7685 in `exec-vm`.
  - **Expect to hit #2 — empty request list root**: special-casing "no requests" wrongly — using `B256::ZERO`, or
    the empty-trie root, instead of what the spec defines. Symptom: every empty block's header mismatches.
    - Fix: use the spec's defined empty value (post-Prague: the keccak of empty input) — test the zero-request case
      explicitly.
    - Muscle: the empty-collection root is a defined constant, not zero — pin it with a test. Reapplies at: W8
      empty-receipts root, W10 empty-trie root.
  - **Expect to hit #3 — requests not in ascending type order**: encoding requests in insertion order rather than
    sorted by `request_type`. Symptom: a block whose requests are correct but unsorted produces a different root and
    is rejected.
    - Fix: requests in a block must be ordered by ascending `request_type` before the root is computed; enforce and
      assert it.
    - Muscle: ordering is part of a consensus commitment — sort before you hash. Reapplies at: W8 receipt ordering,
      W15 EIP-7685 in `exec-vm`.
- [ ] **Build**: `crates/eth-consensus/src/bytecode.rs` — Bytecode enum. EOF parser skeleton. (~150 min)
  - *Mental model*: `Bytecode` distinguishes the kinds of code an account can hold — legacy EVM bytecode, an
    EIP-7702 delegation pointer, and EOF (EVM Object Format) containers. EOF replaces a raw byte stream with a
    structured, sectioned container that is validated once at deploy time.
  - *Contract*: `enum Bytecode { Legacy(Bytes), Eof(Eof), Eip7702(Address) }`. The EOF skeleton: an `Eof` struct
    holding the parsed `EofHeader` (section sizes) plus the raw `code`, and `fn parse(raw: &[u8]) -> Result<Eof,
    EofError>` that validates the magic, version, and section headers. This week is the *skeleton* — full
    instruction validation lands in W15/W61.
  - *parse, roughly*: (1) check bytes `[0]==0xEF && [1]==0x00` (the `0xEF00` magic); (2) check `[2]` is version
    `0x01`; (3) walk the section headers (`kind`, `size` triples) — types, code, optional container, data — until
    the `0x00` terminator; (4) verify the declared sizes sum to the remaining body length. Step 3, header walking
    without overrunning the buffer, is the real exercise.
  - **Expect to hit #1 — confusing the 0xEF00 magic with the 0xEF reserved-opcode rule**: treating any code starting
    with `0xEF` as EOF. Symptom: a legacy contract whose first byte is `0xEF` (the reserved `INVALID`-adjacent
    opcode, banned for *new* legacy deploys since EIP-3541) is misparsed as a broken EOF container.
    - Fix: EOF requires the exact two-byte prefix `0xEF 0x00`; a lone `0xEF` followed by anything else is legacy
      bytecode (and only EIP-3541-rejected at *new* deploy time, not for existing accounts).
    - Muscle: a magic number is the *full* multi-byte sequence — never branch on its first byte alone. Reapplies at:
      W15 EOF parser in `exec-vm`, W61 EOF implementation.
  - **Expect to hit #2 — version byte not checked / wrong reject**: skipping the `[2]` version check, or rejecting a
    valid `0x01`. Symptom: a future EOFv2 container is silently parsed with v1 rules, or all valid containers fail.
    - Fix: explicitly require version `== 0x01`; return a distinct `EofError::UnsupportedVersion` for anything else.
    - Muscle: a versioned format must validate the version byte before parsing the rest. Reapplies at: W15 EOF
      parser, W61 EOF implementation.
  - **Expect to hit #3 — section-header length overrun**: reading `kind`/`size` fields past the end of a truncated
    container, or trusting a declared section size larger than the remaining bytes. Symptom: a panic on slice
    out-of-bounds, or `parse` returns `Ok` on a container whose body is shorter than its headers claim.
    - Fix: bounds-check before every header field read; after parsing all headers, assert
      `sum(section_sizes) == body.len()` exactly.
    - Muscle: a length-prefixed parser must validate every offset against the buffer before reading. Reapplies at:
      W15 EOF parser in `exec-vm`, W61 EOF implementation.
  - **Expect to hit #4 — missing the section-terminator byte**: not stopping the header walk at the `0x00`
    terminator, or not requiring it to be present. Symptom: the parser reads the data section's first byte as
    another section header, producing a garbage `EofHeader` or an infinite/over-long walk.
    - Fix: the section-header list ends at a single `0x00` terminator byte — require it, and switch to body parsing
      immediately after.
    - Muscle: a header list needs an explicit terminator — never infer "done" from running out of bytes. Reapplies
      at: W15 EOF parser, W61 EOF implementation.

**Thursday — `TxEnvelope` + Second Alloy PR**

- [ ] **Build**: `crates/eth-consensus/src/envelope.rs` — TxEnvelope enum dispatching across all tx types. (~150 min)
  - *Mental model*: `TxEnvelope` is the single type that holds *any* Ethereum transaction. On the wire a typed tx is
    a one-byte type discriminant followed by its RLP body; the envelope's encode/decode is the dispatch layer that
    reads/writes that byte and routes to the right variant — exactly what `alloy-consensus::TxEnvelope` does.
  - *Contract*: `enum TxEnvelope { Legacy(Signed<TxLegacy>), Eip2930(Signed<TxEip2930>), Eip1559(Signed<TxEip1559>),
    Eip4844(Signed<TxEip4844>), Eip7702(Signed<TxEip7702>) }`, `Encodable`/`Decodable`. Encode: legacy emits a bare
    RLP list; every typed tx emits `type_byte ++ rlp(body)`. Decode: peek the first byte — `>= 0xc0` means legacy
    (RLP list prefix), otherwise it's the type discriminant. Plus `fn tx_hash(&self) -> B256` =
    `keccak256(encoded_bytes)`.
  - *decode, roughly*: (1) peek byte 0 without consuming it; (2) if `>= 0xc0`, decode as `TxLegacy`; (3) else match
    the type byte (`0x01..=0x04`), consume it, decode the matching body; (4) reject unknown type bytes. Step 1, the
    non-consuming peek that distinguishes legacy from typed, is the real exercise.
  - **Expect to hit #1 — type byte consumed before legacy detection**: unconditionally reading and discarding byte 0
    as a type discriminant. Symptom: every legacy tx fails to decode (its first byte is part of the RLP list header,
    `>= 0xc0`, not a type), or decodes off-by-one garbage.
    - Fix: peek byte 0; only consume it as a type byte once you've confirmed it is `< 0xc0`. Legacy has no type
      prefix at all.
    - Muscle: typed-vs-untyped union decoding branches on a *peeked* discriminant, never a consumed one. Reapplies
      at: W8 Receipt envelope, W9 `exec-vm` opcode dispatch.
  - **Expect to hit #2 — typed tx wrapped in an extra RLP string**: when the typed tx travels inside a list (e.g. a
    block body or `eth/68` message) it is `0xType ++ body` wrapped as an RLP *byte-string*; encoding it as a bare
    concatenation breaks framing. Symptom: a single tx round-trips but a `Vec<TxEnvelope>` mis-frames — the next tx
    starts at the wrong offset.
    - Fix: match `alloy` — a typed tx as a *standalone* object is raw `type ++ body`; as a *list element* it is that
      blob RLP-encoded as a string. Pick the convention per call site and document it.
    - Muscle: typed-tx framing differs between standalone and list-element contexts — mirror the reference impl.
      Reapplies at: W8 Receipt list encoding, W9 `TxEnvelope` consumers.
  - **Expect to hit #3 — tx_hash over the wrong bytes**: computing `tx_hash` over `rlp(body)` only, omitting the
    type byte (for typed txs) or hashing the inner struct instead of the canonical encoding. Symptom: your tx hashes
    disagree with Etherscan/`cast` for every typed transaction.
    - Fix: `tx_hash = keccak256` of the *full canonical encoding* — `type_byte ++ rlp(body)` for typed, `rlp(list)`
      for legacy.
    - Muscle: a tx hash is keccak of the exact canonical wire bytes, type prefix included. Reapplies at: W8 Receipt
      hashing, W10 trie keys.
  - **Expect to hit #4 — unknown type byte not rejected**: a `_ =>` arm that defaults an unrecognized type byte to a
    known variant. Symptom: a malformed or future-type tx is silently mis-decoded as e.g. EIP-1559 instead of
    erroring.
    - Fix: decode returns `Err(Eip2718Error::UnexpectedType)` for any type byte outside the known set; never default.
    - Muscle: an exhaustive discriminant decode must error on unknown values, not fall through. Reapplies at: W8
      Receipt type dispatch, W13 EIP deep dives.
