- [ ] **Build**: `crates/messaging-aeron/src/term_buffer.rs` — fixed-size (default 1 MiB) ring with frame headers.
  Single writer, single reader per term. Three terms rotate (active, in-recovery, dirty). Lock-free. (~150 min)
  - 🔧 **Decomposition prompt (silent test)**: this spec doesn't name primitives. The negated-length sentinel
    publish, the tail_offset advancement under concurrent claim, the term rotation, the consumer scan-with-
    skip-of-PAD — each silently requires primitives from your W5–W17 toolkit + W4 Backoff/Parker + W26 WAL
    framing. If your 10M-msg/sec p99 budget isn't met, or your loom test exposes torn header, or your
    `perf c2c` shows HITM on tail_offset — your decomposition missed something specific.
  - 🎯 **Hardened acceptance for term_buffer**:
    - **Throughput**: ≥10M msg/sec single-producer at 128 B payload sustained 60s.
    - **Latency distribution**: publish p50 ≤50 ns, p99 ≤200 ns, p99.9 ≤2 µs, p99.99 ≤20 µs.
    - **Scale**: per-publication throughput at N=1,2,4,8 publications (each its own term buffer) on same
      MediaDriver process; aggregate at N=8 must be ≥7× N=1 (per-publication isolation).
    - **Zero allocation under dhat**: publish path produces ZERO heap allocs steady state.
    - **Loom-green**: 1 writer + 1 reader, 4 publishes with assert no torn header (the negated-length
      sentinel must hold under Acquire/Release pair).
    - **No HITM under `perf c2c`**: tail_offset must NOT appear as cache-line HITM hotspot — verify it's
      `CachePadded` on its own line. Failure here = drill #11 not internalized.
    - **Term rotation correctness**: under 100M+ publishes spanning >1000 term rotations, no message lost,
      no readers stuck on PAD frame, no torn rotation.
    - **No syscall on publish hot path**: verified via `strace -c`. fsync/msync calls = 0 on publish (the
      durability path runs separately at Archive in W83 — not term_buffer's job).
    - **Graceful degradation**: when consumer falls behind and 3rd term fills (no rotation possible),
      publisher backpressures via flow control (W77 Tue) — never silently overwrites.
    - **5-year failure mode**: state one shift (NUMA cross-socket publication, term size > L2, weaker
      memory model) that forces redesign.
  - **Why**: The term buffer is the *core data structure of Aeron* — a fixed-size, lock-free, single-producer-multi-consumer ring in shared memory. It bounds memory, enables zero-copy publish/subscribe, and supports NAK-based recovery by retaining old terms. Bar (c) — wrong here = data corruption in production.
  - **Read first**: Aeron `TermAppender.java` (producer), `TermReader.java` (consumer), `TermRebuilder.java` (NAK recovery side). LMAX Disruptor paper (mechanically similar). Martin Thompson's "Single Writer Principle" blog post.
  - **Design**:
    ```rust
    pub const TERM_LEN: usize = 1 << 20;    // 1 MiB; configurable to 64 KiB..1 GiB powers of 2
    pub const FRAME_HEADER_LEN: usize = 32; // matches Aeron HeaderFlyweight

    #[repr(C)]
    pub struct FrameHeader {
        pub length: i32,             // total frame length including this header; negated while writing
        pub version: u8,
        pub flags: u8,               // BEGIN_FRAG | END_FRAG | UNFRAGMENTED
        pub frame_type: u16,         // DATA, PAD, SETUP, NAK, ...
        pub term_offset: i32,
        pub session_id: i32,
        pub stream_id: i32,
        pub term_id: i32,
        pub reserved: i64,
    }

    pub struct TermBuffer {
        pub buf: Mmap,                       // mmap'd shared memory, TERM_LEN bytes
        pub tail_offset: AtomicI32,          // producer's append position
        pub term_id: i32,
    }

    pub struct LogBuffer {
        pub terms: [TermBuffer; 3],          // active, dirty, clean
        pub metadata: LogMetadata,           // partition state in shm header
    }

    impl TermBuffer {
        pub fn try_claim(&self, length: i32) -> Result<i32 /*offset*/, AppendError> {
            // 1. atomic FAA on tail_offset
            // 2. if offset + length > TERM_LEN → write PAD frame, return TermFull
            // 3. write FrameHeader with length = -length (under construction)
            // 4. caller writes payload, then atomic-store length (positive) — publishes the frame
        }
        pub fn commit(&self, offset: i32, length: i32) {
            let header_len_ptr = &self.buf[offset] as *const _ as *mut i32;
            // Memory-ordered store: Release on the length field publishes payload writes
            unsafe { (header_len_ptr as *mut AtomicI32).load_volatile().store(length, Release); }
        }
    }
    ```
    **Invariants**: (i) Tail is monotonic — never decreases within a term. (ii) Frame header `length` is *negated* while writing (CAS sentinel), positive when readable — readers spin/skip on negative. (iii) Term rotation: 3 terms, indexed `active = position % 3`; when active fills, switch to next; the third (oldest) is available for NAK recovery. (iv) Aligned to 32 bytes (frame header is exactly 32; payload align follows). (v) `term_offset + length` never exceeds `TERM_LEN`; on shortfall, PAD frame fills the remainder.
  - **Back-of-envelope**: target P50 publish <50 ns, P99 <200 ns single-producer. Hot path = (i) `AtomicI32::fetch_add` on tail = ~10 ns uncontended (1 cycle x86 LOCK XADD + memory fence ~5 ns), (ii) bounds check ~1 ns (one compare), (iii) write FrameHeader (32 B aligned, one cache line) ~5 ns, (iv) memcpy payload (typical 64-256 B → ~10-30 ns at L1 bandwidth), (v) `AtomicI32::store(length, Release)` ~5 ns = ~50 ns total ideal. P99 buffer covers one TLB miss (~30 ns) or one L2 fetch on the tail counter (~7 ns) under cross-thread invalidation. NO syscall in offer path — `mmap` happens at construction only (~50 µs cost paid once). At 10M msg/s target, 100 ns budget × 1 producer thread × 1 term buffer; rotation cost amortizes (every TERM_LEN bytes = once per 8k messages of 128 B). The negated-length sentinel is the load-bearing CAS: writer's `length = -length` is a Release fence; reader's spin loop must use `Acquire` load else CPU reorders payload reads above the length check (W4 SeqLock pattern).
  - **Build steps**: 1. (~25 min) FrameHeader + repr(C) + #[align(32)]. 2. (~30 min) `Mmap` setup via `memmap2` or raw libc::mmap. 3. (~30 min) `try_claim` FAA + bounds check + PAD path. 4. (~20 min) `commit` with Release ordering. 5. (~20 min) Reader: poll header.length; if positive, consume; if negative, retry; if PAD, skip. 6. (~25 min) Term rotation logic in LogBuffer. 7. (~Tests.)
  - **Pitfalls** (named, 4):
    - *Producer overruns consumer*: **Symptom**: in a single-term setup, producer wraps and overwrites unread frames → consumer reads garbage. **Fix**: three-term rotation. Producer cannot switch to term N+1 until consumer drained term N-1. Flow control (W77 Tue) provides backpressure via subscriber position.
    - *Wrap-around safety*: **Symptom**: tail FAA wraps int32, becomes negative → bounds check fails. **Fix**: use i32 with explicit overflow check (`checked_add`); reset tail to 0 only on term rotation, never via wrap. Aeron uses 31-bit positions explicitly.
    - *Frame alignment*: **Symptom**: payload length not 32-aligned → next frame header starts on misaligned boundary → cache-line split + ARM SIGBUS. **Fix**: `align_up(length, 32)` always. Test with various payload sizes (1, 31, 32, 33, 63 bytes).
    - *Torn header read*: **Symptom**: reader reads `length` between writer's negate-write and final-store-positive → sees corrupt value. **Fix**: reader uses `Acquire` load; writer uses `Release` store. The negate-sentinel pattern means reader spins until length > 0 (valid frame).
  - **Expect to hit (perf) #1 — `fsync()` or `msync()` on every commit (bar (c) violation)**: an instinct to call `msync(MS_SYNC)` or `fsync()` after each frame to "make it durable" turns a 50 ns publish into a ~5 ms disk flush — 100,000× slower. The term buffer is *intentionally not* a durable journal — durability is provided by Archive (W83) on a separate thread. Symptom: publish throughput collapses from 10M msg/s to <1k msg/s; `iostat` shows constant fsync activity; P99 latency tail is dominated by disk seek (~10 ms HDD / ~100 µs NVMe). Fix: term buffer mmaps are `MAP_SHARED` over `/dev/shm` (tmpfs, RAM-backed) — never call sync. Durability is the Archive thread's job, asynchronous on a separate file. Cost avoided: 5 ms/op → 50 ns/op = ~100,000× speedup; restores 10M msg/s target. Muscle: hot-path IPC ring is RAM-only; durability is a SEPARATE pipeline asynchronous to publish. Reapplies at: W77 IPC transport (no sync), W79 MBO feed (no sync — Archive handles it), W83 archive recorder (sync is on the Archive thread, never on publish), W87 VOPR journal (fsync per BATCH, not per op).
  - **Expect to hit (perf) #2 — tail counter shares cache line with payload bytes (bar (c) violation)**: laying out `tail_offset: AtomicI32` at byte 0 of the mmap puts the tail in the same 64 B line as the first frame's header. Every commit by writer (FAA on tail + write to frame header) invalidates the reader's cache of the tail counter; every read of the tail by reader (to detect new frames) invalidates the writer's cache of the first frame. Cross-cache-line ping-pong on the same line costs ~7 ns L2 fetch per access; at 10M ops/sec, ~70 ms/sec of pure MESI traffic. Symptom: bench achieves 3M msg/s instead of 10M; `perf c2c` flags the first cache line of the mmap as the HITM hotspot. Fix: lay out LogMetadata at the START of the file as `tail_offset: CachePadded<AtomicI32>` (128 B aligned, occupies its own line), then `[u8; PADDING]` to push frames to the next 128 B boundary. Even better: separate the tail into its own 4 KiB page (one VMA, zero false sharing with any payload). Cost avoided: ~7 ns × 10M ops/s = ~70 ms/sec of cross-thread L2 fetch; restores cache-resident tail. Muscle: ANY atomic counter touched by multiple threads must be cache-line isolated from any other hot data — the W4 CachePadded principle scales to mmap'd shared memory. Reapplies at: W77 flow control positions array, W79 subscription position cursor, W83 archive recording position, W84 deterministic harness clock counter.
  - **Test scenarios**: (a) Single producer, single consumer, 10M messages — zero loss, P99 latency < 200ns. (b) Term rotation: fill term 0, switch to 1, consumer catches up term 0, term 0 reusable. (c) Producer faster than consumer with backpressure → producer blocks at term boundary (not overwrites). (d) Loom-style concurrency test on header read/write ordering. (e) Misaligned payload sizes — verify next frame still alignedly read.
  - **Acceptance**: bench: P50 publish latency < 50ns, P99 < 200ns single producer. Loom check passes. Inheritance: bufpool (zero-copy payload), no heap allocs in hot path.
  - **Downstream**: W77 Tue flow_control.rs uses term-buffer position for sliding window. W77 Fri transport_ipc.rs is just a term buffer in shm with no UDP. W78 transport_udp.rs sends term frames over the network. W79 subscription.rs fan-outs via multiple readers on same term. - [ ] [NEW v2] **Build**: `crates/matching-engine/src/stop_ladder.rs` — stop trigger ladder: when trade prints at stop
  price, promote stop → market or stop-limit → limit. (~2 hrs)
  - **Why**: Stop orders (and their cousins stop-limit, trailing-stop) are how retail and institutional traders implement risk limits. Trigger semantics are the source of repeated production incidents (e.g., the 2010 Flash Crash amplified by stop cascades). The "ladder" data structure is the canonical efficient implementation — O(log n) trigger eval per print.
  - **Read first**: CME Globex "Stop Order Triggering" specification. Nasdaq INET stop-loss documentation. Bryant/O'Hare 2011 paper on stop-trigger gap risk. dYdX v4 `protocol/x/clob/keeper/orders.go::TriggerOrders`.
  - **Design**:
    ```rust
    pub enum StopType {
        StopMarket,        // trigger → emit market order
        StopLimit { limit_px: Price },
        TrailingStop { trail_offset: u64 /*ticks*/, anchor: AtomicPrice },
    }
    pub struct StopOrder {
        pub id: OrderId,
        pub account: AccountId,
        pub symbol: Symbol,
        pub side: Side,        // side of the FOLLOW-ON order (e.g., stop-loss on long position = sell)
        pub trigger_px: Price,  // for buy-stop: trigger when last_trade >= px; sell-stop: <= px
        pub trigger_kind: TriggerKind,   // LastTrade, BestBid, BestAsk, MarkPrice
        pub stop_type: StopType,
        pub qty: u64,
    }
    pub struct StopLadder {
        // Two sorted maps: one for buy-stops (triggered when price rises), one for sell-stops (when falls)
        pub buy_stops: BTreeMap<Price, Vec<StopOrder>>,    // ascending; triggered when last >= key
        pub sell_stops: BTreeMap<Price, Vec<StopOrder>>,   // descending semantics — triggered when last <= key
    }
    impl StopLadder {
        pub fn on_print(&mut self, sym: Symbol, last_px: Price, trigger_kind: TriggerKind) -> Vec<StopOrder> {
            // Find all stops where trigger condition met, drain them in deterministic order
            let mut triggered = Vec::new();
            while let Some((&px, _)) = self.buy_stops.range(..=last_px).next_back() {
                if last_px >= px {
                    triggered.extend(self.buy_stops.remove(&px).unwrap());
                } else { break; }
            }
            while let Some((&px, _)) = self.sell_stops.range(last_px..).next() {
                if last_px <= px {
                    triggered.extend(self.sell_stops.remove(&px).unwrap());
                } else { break; }
            }
            triggered
        }
    }
    ```
    **Invariants**: (i) BTreeMap iteration order is deterministic — critical for raft replication (W74). (ii) Triggered stops are drained atomically with the print event — no race where stop is still in ladder but its trigger already fired. (iii) Trailing-stop's `anchor` updates on every favorable print, generating a new effective trigger_px. (iv) Trigger is on the *kind* — LastTrade vs BestBid vs Mark — never confuse.
  - **Back-of-envelope**: target 10k stops, single print triggering 100 → <50 µs total. Per-print check on ladder = `BTreeMap::range(..=last_px)` O(log N) ~50 ns for N=10k (depth ~14, each node read ~3 ns cache-resident). Drain k triggered stops = O(k) removes, each O(log N) = ~700 ns/stop × 100 = ~70 µs — already over budget. The real cost is the 100 promotions: each triggered stop must emit a new `MatchCommand::NewOrder` event, which (a) serializes ~64 B (~50 ns via bufpool), (b) gets pushed onto the match queue (~10 ns), (c) eventually traverses the match loop (~1 µs). 100 × 1 µs = 100 µs of cascade — bounded by matching throughput, not the ladder itself. Branch predictor: the `match stop_type` dispatch must be predictable; mixing StopMarket/StopLimit/TrailingStop unpredictably costs ~5 ns mispredict per dispatch (vs ~0.5 ns predicted). Sort the ladder by `stop_type` discriminant within price level if mix is non-uniform. NO floats — all price math integer (W81 circuit breaker discusses).
  - **Build steps**: 1. (~20 min) Types + serde. 2. (~25 min) `add` (insert into appropriate map). 3. (~30 min) `on_print` drain logic with side handling. 4. (~25 min) StopType promotion: triggered Stop emits a new MatchCommand::NewOrder of the corresponding type. 5. (~20 min) Trailing stop anchor update on favorable prints (separate from trigger drain). 6. (~Tue tests.)
  - **Pitfalls** (named, 4):
    - *Ladder ordering with simultaneous triggers*: **Symptom**: a single print triggers 100 stops; promotion order matters (the first promoted may absorb liquidity others would have hit). Non-deterministic order = replica divergence. **Fix**: BTreeMap (sorted) + within-price-level by `(account_id, order_id)` lex order. Cite property test.
    - *Gap-through behavior*: **Symptom**: market gaps from $99 to $101, skipping all $100 stops. Should they trigger on $101 (worse fill) or remain dormant? **Fix**: trigger on first print *crossing* the stop price — all stops at $100 fire on $101 print. Stop-market emits a market order which fills at $101. Stop-limit: if limit is $100, no fill (limit not crossed at $101) — order remains in book until $100 prints. Document this clearly; spec varies by venue.
    - *Trigger-kind mismatch*: **Symptom**: stop set on LastTrade fires from a print, but the order author intended MarkPrice (which lags) → unexpected liquidation. **Fix**: explicit `trigger_kind` field on order; ladder maintains separate ladders per kind. UI/API defaults documented prominently.
    - *Self-trigger cascade*: **Symptom**: triggered stop becomes market order, executes, prints at a new level, triggers more stops → cascade. **Fix**: this is intentional and not buggy, BUT — rate-limit consecutive cascade depth, and/or pair with circuit breakers (W81). Cite Flash Crash post-mortem.
  - **Expect to hit (perf) #1 — `Vec<StopOrder>` clone on drain (bar (c) violation)**: naive `self.buy_stops.remove(&px).unwrap()` returns an owned `Vec<StopOrder>` which is moved into the `triggered` vec — but if any caller writes `triggered.extend(self.buy_stops.get(&px).unwrap().clone())`, you pay O(k) clone of every `StopOrder` (each ~80 B = 80 ns/element memcpy + reference-counted field clones). On a 100-stop trigger, ~8 µs of pure clone overhead. Symptom: `perf` flame graph shows `<StopOrder as Clone>::clone` dominating drain; cascade latency 2× expected. Fix: use `remove` (move semantics) not `get + clone`; the BTreeMap entry is consumed in one O(log N) operation. For the value type, store `Box<StopOrder>` or `SlabIdx<StopOrder>` inside the BTreeMap so the inner Vec contains pointers (8 B moves) rather than full structs. Cost avoided: ~80 ns/clone × 100 stops = ~8 µs per cascade; eliminates 8 KB of transient allocation per trigger event. Muscle: drain operations move, never clone — clone is a bar-(c) red flag in hot path. Reapplies at: W74 lock-free price level drain, W77 NAK gap-list drain, W78 auction matched-orders drain, W80 ledger batch apply.
  - **Test scenarios** (Tue): (a) `stop@100 with last_trade=99` → quiescent. Trade @100 → promote to market. (b) Buy-stop ladder: stops at 100, 101, 102; print at 103 → all three trigger in ascending price order. (c) Gap-through: print at 95, then 110, with stops at 100/105 → both fire on the 110 print (first crossing). (d) Trailing-stop: stop trail 5 ticks below long position high-water; price moves up → anchor updates; price drops 5 ticks → fire. (e) Replica determinism: same print stream → same trigger order across raft replicas.
  - **Acceptance**: O(log n + k) per print where k=triggered count. Bench: 10k stops, single print triggering 100 → < 50µs. Inheritance: bufpool, no heap on hot path. Determinism property 1k random schedules.

- [ ] [NEW v2 mmap-queue v0.5] **Build**: `crates/mmap-queue/src/pretouch.rs` — page-warming worker pre-faults next N
  pages before write hits them. (~90 min)
  - **Why**: When mmap'd files grow, accessing a new page triggers a *minor page fault* — kernel allocates a zero page, maps it in. At ~1µs latency this is fine for batch workloads but devastating for HFT/HPC where P99 hard-real-time matters. Pretouch worker walks future pages, page-faulting them on a *background* thread, so the producer thread never blocks. Chronicle Queue ships this; it's a Tier-A interview discussion.
  - **Read first**: Chronicle Queue `Pretoucher.java` (the canonical implementation). Linux kernel `mm/memory.c::handle_pte_fault` for the cost model. `madvise(MADV_WILLNEED)` semantics in `man madvise(2)`.
  - **Design**:
    ```rust
    pub struct Pretoucher {
        pub mmap: Mmap,
        pub current_tail: AtomicUsize,    // owned by writer
        pub pretouch_ahead: usize,         // pages to pretouch ahead, e.g., 16
        pub page_size: usize,              // typically 4 KiB or 2 MiB hugepage
        pub stop: Arc<AtomicBool>,
    }
    impl Pretoucher {
        pub fn spawn(self: Arc<Self>) -> JoinHandle<()> {
            std::thread::Builder::new()
                .name("mmap-queue-pretoucher".to_string())
                .spawn(move || {
                    while !self.stop.load(Acquire) {
                        let tail = self.current_tail.load(Acquire);
                        let next_page = (tail / self.page_size + 1) * self.page_size;
                        let target = next_page + self.pretouch_ahead * self.page_size;
                        // Walk pages, touching one byte per page to fault them in
                        for p in (next_page..target.min(self.mmap.len())).step_by(self.page_size) {
                            // SAFETY: target is within mmap range; write a zero byte does not corrupt
                            // (we know writer hasn't reached here yet; AND we use volatile to prevent compiler optimizing away)
                            unsafe {
                                let ptr = self.mmap.as_ptr().add(p) as *mut u8;
                                std::ptr::write_volatile(ptr, 0u8);
                            }
                        }
                        // Optional: madvise(WILLNEED) for kernel readahead
                        unsafe {
                            libc::madvise(self.mmap.as_ptr().add(next_page) as *mut _,
                                         self.pretouch_ahead * self.page_size,
                                         libc::MADV_WILLNEED);
                        }
                        std::thread::sleep(Duration::from_micros(100));
                    }
                })
                .unwrap()
        }
    }
    ```
    **Invariants**: (i) Pretoucher only writes BYTES the producer has NOT YET reached — read `current_tail` atomically, walk pages strictly *after* tail. (ii) Page-warm write is volatile + zero — never corrupts data; relies on producer always overwriting. (iii) Pretoucher thread is dedicated, not shared with writer. (iv) Stop is cooperative; pretoucher exits within 100µs of stop signal.
  - **Back-of-envelope**: minor page fault on first touch of a 4 KiB page ≈ 1-3 µs (kernel allocates zero page + maps PTE + invalidates TLB). At 100 µs/page sleep cadence × 16 pages ahead = pretoucher walks ~64 MB/s; producer writing 1 GB/s would catch up unless pretouch_ahead is sized for the write rate. Formula: `pretouch_ahead >= write_rate × pretouch_sleep / page_size`. For 1 GB/s writer + 100 µs sleep + 4 KiB pages: `1e9 × 1e-4 / 4096 = 25 pages` minimum; use 64 for safety margin. With 2 MiB hugepages, fault cost is ~10 µs (allocates 2 MiB zero page) BUT one fault covers 500× the bytes — at 1 GB/s, 2 µs/sec of pretouch overhead vs 250 µs/sec for 4 KiB pages. Hugepages also reduce TLB pressure: 1 GB/s scan over 4 KiB pages = 244k TLB entries touched/sec → constant TLB miss (~50 ns each = 12 ms/sec); hugepages = 488 entries/sec, TLB stays resident. Pretoucher's own write is one byte per page — ~1 ns L1 store; the COST is the page fault on the producer side that pretoucher AVOIDS. Without pretoucher: P99 publish latency includes ~3 µs page fault when producer crosses a page; with pretoucher: page is already warm, producer pays 0 µs.
  - **Build steps**: 1. (~15 min) Pretoucher struct + spawn helper. 2. (~25 min) Page-walk loop with volatile write. 3. (~15 min) `madvise(WILLNEED)` integration (best-effort hint). 4. (~15 min) Stop flag + graceful join. 5. (~20 min) Hugepage detection — if mmap is backed by hugepages (`/sys/kernel/mm/transparent_hugepage`), use 2 MiB stride. (Tests Tuesday.)
  - **Pitfalls** (named, 4):
    - *Page eviction*: **Symptom**: pretoucher warms page N; kernel evicts under memory pressure; producer hits cold page → fault anyway. **Fix**: `mlock` the working set (requires CAP_IPC_LOCK + RLIMIT_MEMLOCK budget) or use hugepages (typically not evicted). Document this as an ops requirement.
    - *NUMA-local pretouch*: **Symptom**: pretouch thread runs on socket 0, producer on socket 1 → faulted pages allocated on socket 0's memory, cross-socket access for every write. **Fix**: pin pretouch thread to a sibling core of the producer (same NUMA node). Use `sched_setaffinity` + `numa_alloc_local`.
    - *When to stop*: **Symptom**: pretouching past EOF (mmap end) → SIGSEGV or no-op faulting beyond file size. **Fix**: clamp target to `mmap.len()`; producer is responsible for `ftruncate`-extending the file before publish; pretoucher follows the extended size.
    - *Producer-overtake race*: **Symptom**: producer faster than pretoucher; tail catches up; pretoucher writes zero into a byte producer JUST wrote → corruption. **Fix**: pretoucher always reads `tail` atomically and operates strictly on pages WHERE no byte has been written. Use `tail + 1 page * PRETOUCH_GAP` as the lower bound, never below it. Property test with loom.
  - **Expect to hit (perf) #1 — `madvise(WILLNEED)` called per page instead of per range (bar (c) violation)**: naively calling `madvise(ptr, page_size, MADV_WILLNEED)` per page in the walk loop = one syscall per page = ~300 ns/page × 64 pages = ~20 µs/iteration of pure syscall overhead — and `madvise` itself walks the page table on each call, costing extra ~1 µs per range. Symptom: pretoucher thread CPU usage saturates a core; `strace -c` shows `madvise` dominating; throughput improvements vs no-pretouch are minimal because pretouch overhead eats the page-fault savings. Fix: call `madvise` ONCE for the entire pretouch range (`madvise(next_page, pretouch_ahead × page_size, MADV_WILLNEED)`) — kernel walks the PTEs in one pass. Or skip `madvise` entirely if the volatile-write already faults pages in (madvise WILLNEED is best-effort hint; the volatile write is authoritative). Cost avoided: 64 syscalls × 300 ns = ~20 µs/iter; ~200 ms/sec at 10 kHz pretoucher tick. Muscle: syscalls amortize over large ranges; never call syscall in a tight per-element loop. Reapplies at: W77 transport_udp sendmmsg (batched 64-at-a-time, not per-packet), W78 NAK retransmit batch, W83 archive recorder fsync (batched), W84 io_uring submission (batched in W89 ledger v1.0).
  - **Test scenarios** (Tue): (a) Cold mmap, producer-only baseline: P99 publish latency includes page-fault tail. (b) With pretoucher: P99 publish latency drops by 5-10x (depending on stride).   - **Why**: Flow control prevents fast publishers from running roughshod over slow subscribers — without it, term buffer overruns drop messages. Tier-A: candidates discuss CC algos (DCTCP, Aeron, TCP cubic).
  - **Read first**: Aeron `MinMulticastFlowControl.java` and `MaxMulticastFlowControl.java` — strategies to handle slow consumers (min = block on slowest, max = ignore stragglers). `StatusMessage.java` for the subscriber-side position broadcast wire format.
  - **Design**:
    ```rust
    pub trait FlowControlStrategy {
        fn position_limit(&self, subscriber_positions: &[u64], window_len: usize) -> u64;
    }
    pub struct MinStrategy;
    impl FlowControlStrategy for MinStrategy {
        fn position_limit(&self, positions: &[u64], window: usize) -> u64 {
            positions.iter().min().copied().unwrap_or(0) + window as u64
        }
    }
    pub struct MaxStrategy { pub slow_threshold: Duration }
    pub struct FlowController {
        pub strategy: Box<dyn FlowControlStrategy>,
        pub subscriber_positions: AHashMap<SubscriberId, (u64, Monotonic)>,  // pos + last-update
        pub window_len: usize,             // bytes; typically 16 MiB
        pub credit_fc: CreditFlowControl,  // from backpressure crate
    }
    impl FlowController {
        pub fn on_status_message(&mut self, sub: SubscriberId, position: u64, ts: Monotonic) {
            self.subscriber_positions.insert(sub, (position, ts));
        }
        pub fn can_publish(&self, current_tail: u64) -> bool {
            let positions: Vec<u64> = self.subscriber_positions.values().map(|(p, _)| *p).collect();
            current_tail <= self.strategy.position_limit(&positions, self.window_len)
        }
        pub fn evict_slow(&mut self, now: Monotonic, threshold: Duration) {
            self.subscriber_positions.retain(|_, (_, ts)| now - *ts < threshold);
        }
    }
    ```
    **Invariants**: (i) `can_publish(tail)` is monotonic in `tail` — once false, remains false until positions advance. (ii) Subscriber positions are wall-clock-independent — `Monotonic` only. (iii) Eviction is *explicit* — a slow subscriber that misses heartbeats is removed from the position set (MaxStrategy) or holds the cluster back (MinStrategy). The choice is configured.
  - **Back-of-envelope**: target `can_publish` <50 ns hot path. With N=10 subscribers, finding `min(positions)` is 10 atomic loads + 9 compares = ~30 ns L1-cache-resident, ~70 ns if scattered across cache lines. Trait-object dispatch via `Box<dyn FlowControlStrategy>` adds 1 vtable load (~5 ns L1, ~50 ns L2 if cold) + 1 indirect call (~5 ns branch mispredict tax). At 10M `try_claim` calls/sec, the flow control check is in the inner loop — every nanosecond counts. Cache layout: positions array as `[CachePadded<AtomicU64>; MAX_SUBS]` (each on its own line) — readers don't cause ping-pong on other subscribers' lines when a subscriber updates. StatusMessage incoming is 1 update/sec/sub typical (Aeron heartbeat default); cost is bounded.
  - **Build steps**: 1. (~20 min) Trait + MinStrategy + MaxStrategy. 2. (~25 min) FlowController with positions map. 3. (~25 min) `on_status_message` handler — wire format follows Aeron StatusMessage (32-byte header + position). 4. (~20 min) `can_publish` integration into TermBuffer::try_claim — refuse claim when over limit. 5. (~15 min) Evict slow subscribers via timeout. 6. (~Tests.)
  - **Pitfalls** (named, 3):
    - *Window collapse*: **Symptom**: one slow subscriber stays at position 0; MinStrategy → window = `[0, window_len]`; entire cluster stalls. **Fix**: configurable timeout for "slow subscriber" → evict from position set (which behaves like MaxStrategy for that sub).   - **Expect to hit (perf) #1 — `Vec<u64>::iter().min()` allocates a Vec per call (bar (c) violation)**: in the design code, `can_publish` collects positions via `let positions: Vec<u64> = self.subscriber_positions.values().map(|(p, _)| *p).collect();` — that's a `Vec::new()` + N pushes (each potentially reallocating) + `iter().min()` + drop = ~200 ns/call (allocator hit + N copies). At 10M `try_claim`/sec, that's 2 ms/sec of pure allocation overhead, and the Vec lives <100 ns → trashes L1 + jemalloc arena. Symptom: heap profile shows constant 64-byte allocations attributed to `can_publish`; bench shows 5M msg/s instead of 10M target. The active-subscriber mask is a `u64` bitmap (max 64 subs) for branch-predictable iteration. Cost avoided: ~200 ns/call × 10M ops/s = 2 ms/sec; eliminates allocator contention; restores cache residency on positions array. Muscle: NEVER `collect::<Vec<_>>` in a hot path — iterate in-place. Reapplies at: W77 NAK gap iteration, W79 MBO publish per-subscriber loop, W82 Image module loss detector iteration, W83 archive recording lag computation.

(c) Same scenario, MaxStrategy with eviction → publisher continues after timeout, stalled subscriber dropped. (d) Subscriber comes back after eviction → must rejoin via setup handshake.

  - **Design**:
    ```rust
    pub struct IpcPublication {
        pub log_file_name: PathBuf,         // /dev/shm/aeron/pub-{session}-{stream}
        pub log_buffer: LogBuffer,           // 3 terms + metadata
        pub session_id: i32,
        pub stream_id: i32,
    }
    pub struct IpcSubscription {
        pub log_buffer: LogBuffer,           // SAME mmap region as publication's
        pub position: AtomicU64,             // consumer's read cursor
    }
    impl IpcPublication {
        pub fn create(driver: &MediaDriver, stream_id: i32) -> Result<Self> {
            let session_id = next_session_id();
            let path = driver.shm_dir.join(format!("pub-{}-{}.log", session_id, stream_id));
            // size = 3 terms + metadata page
            let file = OpenOptions::new().create(true).read(true).write(true).open(&path)?;
            file.set_len(3 * TERM_LEN as u64 + METADATA_LEN as u64)?;
            let mmap = unsafe { MmapOptions::new().populate().map_mut(&file)? };
            // SAFETY: MAP_POPULATE pre-faults pages, avoiding fault on first publish
            Ok(IpcPublication { log_file_name: path, log_buffer: LogBuffer::new(mmap), session_id, stream_id })
        }
        pub fn offer(&self, data: &[u8]) -> Result<i64, OfferError> {
            let active = self.log_buffer.active_term();
            let offset = active.try_claim(FRAME_HEADER_LEN as i32 + data.len() as i32)?;
            // memcpy payload into reserved frame, then commit (Release ordering)
            active.write_payload(offset, data);
            active.commit(offset, data.len() as i32);
            Ok(offset as i64)
        }
    }
    impl IpcSubscription {
        pub fn poll<F: FnMut(&[u8])>(&self, fragment_handler: F) -> usize {
            // Read header at position; if length > 0, dispatch; advance position
        }
    }
    ```
    **Invariants**: (i) Publication and Subscription share the SAME file via mmap — both have read/write maps; producer writes, consumers read (only the Acquire/Release barriers ensure correctness). (ii) No syscalls in `offer` and `poll` hot paths. (iii) `MAP_POPULATE` pre-faults all pages at creation — avoids first-publish latency spike. (iv) Subscription's `position` is *its own* — multi-subscriber fan-out is N independent positions reading the same log.
  - **Back-of-envelope**: P99 single-hop <1 µs target. Path: producer claim (~10 ns FAA) + memcpy 64 B (~10 ns L1) + commit Release (~5 ns) = ~25 ns publish-side; subscriber Acquire load (~5 ns) + memcpy 64 B (~10 ns) + position store (~5 ns) = ~20 ns receive-side = ~45 ns single-hop ideal. P99 1 µs budget covers: one cross-core cache invalidation (~50 ns), one TLB miss (~30 ns), occasional scheduler interference (~500 ns). 10M msg/s throughput requires single-producer thread pinned to a dedicated core; SO_BUSY_POLL not applicable (this is shm, no socket). MAP_POPULATE cost at creation: 1 GiB term × 3 = 3 GiB to populate × ~3 µs/page / 4 KiB = ~2 s startup hang. For large terms, use MAP_HUGE_2MB (huge pages = 1500× faster: ~10 µs per 2 MiB chunk = 15 ms for 3 GiB). Hugepage reservation requires CAP_IPC_LOCK or `/proc/sys/vm/nr_hugepages` configured ahead of time.

(~25 min) `offer` zero-copy claim + memcpy. 4. (~20 min) `IpcSubscription::poll` reader loop. 5. (~15 min) Multi-publisher safety — each pub has its own session_id (single-writer per term). 6.
