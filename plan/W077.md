  #### Phase 1 — Problem, requirements, design (~70 min, no code yet)

  - **The problem this primitive solves**: 10M+ msg/sec single-producer pub/sub at sub-µs latency requires (a) zero copies, (b) zero allocations, (c) zero syscalls, (d) no torn reads under concurrent claim+commit. A naive Vec-of-Vec ring violates all four. The term buffer achieves them via mmap + FAA-tail + negated-length sentinel + 3-term rotation.

  - **Requirements** (the 🎯 Hardened acceptance from above is the requirements list — restating):
    - R1. Throughput ≥10M msg/sec single-producer at 128 B payload sustained 60s.
    - R2. Publish p50 ≤50 ns, p99 ≤200 ns, p99.9 ≤2 µs, p99.99 ≤20 µs.
    - R3. Per-publication scaling: N=8 publications aggregate throughput ≥7× N=1 (per-publication isolation).
    - R4. Zero heap allocs under dhat on publish path steady state.
    - R5. Loom-green: 1 writer + 1 reader, 4 publishes; assert no torn header under negated-length sentinel + Acquire/Release pair.
    - R6. No HITM under `perf c2c` on `tail_offset` (CachePadded on own line).
    - R7. Term rotation correct: 100M+ publishes across 1000+ rotations, no message lost, no readers stuck on PAD, no torn rotation.
    - R8. Zero syscalls on publish hot path (`strace -c` verified; fsync/msync = 0).
    - R9. Graceful degradation when consumer falls behind: 3rd term fills, publisher backpressures via flow control; NEVER silently overwrites.

  - **Design walk-through** — answer each in `notes/77_term_buffer_design.md`:
    - D1. FrameHeader layout: 32 bytes, `repr(C)`, aligned to 32. Sketch each field (length, version, flags, frame_type, term_offset, session_id, stream_id, term_id, reserved). Why `length` is `i32` (negated for sentinel)?

  #### Phase 3 — Make the tests pass, one failure at a time (~110 min)

  - **When `term_buffer_zero_syscalls_on_publish` reports ~1k fsync calls/sec:**
    - Symptom: `strace -c` shows ~1k fsync(2) calls/sec attributed to publisher; throughput collapses from 10M msg/s to ~1k msg/s; `iostat` shows constant fsync activity; P99 latency tail dominated by disk seek.
    - Why: instinct to `msync(MS_SYNC)` or `fsync()` after each frame to "make it durable" turns a 50 ns publish into ~5 ms disk flush — 100,000× slower. Term buffer is INTENTIONALLY not a durable journal — durability is provided by Archive (W83) on separate thread.
    - Fix: term buffer mmaps are `MAP_SHARED` over `/dev/shm` (tmpfs, RAM-backed) — never call sync. Durability is the Archive thread's job, asynchronous on a separate file.
    - Cost avoided: 5 ms/op → 50 ns/op = ~100,000× speedup; restores 10M msg/s target.
    - Muscle: hot-path IPC ring is RAM-only; durability is a SEPARATE pipeline asynchronous to publish. Reapplies at: W77 IPC transport (no sync), W79 MBO feed (no sync — Archive handles it), W83 archive recorder (sync on Archive thread, never publish), W87 VOPR journal (fsync per BATCH, not per op).

  - **When `term_buffer_perf_c2c_no_hitm_on_tail` reports tail_offset as HITM hotspot:**
    - Symptom: bench achieves 3M msg/s instead of 10M; `perf c2c` flags first cache line of mmap as HITM hotspot; cross-cache-line ping-pong on the same line costs ~7 ns L2 fetch per access × 10M ops = ~70 ms/sec.
    - Why: `tail_offset: AtomicI32` at byte 0 of mmap puts tail in same 64 B line as first frame's header. Every writer commit (FAA on tail + write to frame header) invalidates reader's cache of tail; every reader tail-load invalidates writer's cache of first frame.
    - Fix: layout LogMetadata at file start as `tail_offset: CachePadded<AtomicI32>` (128 B aligned, own line), then `[u8; PADDING]` to push frames to next 128 B boundary. Even better: separate tail into its own 4 KiB page (one VMA, zero false sharing with any payload).
    - Cost avoided: ~7 ns × 10M ops/s = ~70 ms/sec cross-thread L2 fetch; restores cache-resident tail.
    - Muscle: ANY atomic counter touched by multiple threads must be cache-line isolated from any other hot data — W4 CachePadded principle scales to mmap'd shared memory. Reapplies at: W77 flow control positions array, W79 subscription position cursor, W83 archive recording position, W84 deterministic harness clock counter.

  - **When `term_buffer_loom_no_torn_header` reports reader seeing negative length:**
    - Symptom: loom interleaving where reader's `header.length` read lands between writer's negate-write and Release-store-positive; reader sees `length = -64` (negated sentinel value).
    - Why: reader doesn't spin on negative length; consumed the corrupt value.
    - Fix: reader's `length` load is `Acquire`; if `length < 0`, retry (spin) — writer is mid-commit. Writer's final-store is `Release` so payload writes are visible to reader's subsequent reads.
    - Muscle: negated-length sentinel pattern requires Acquire-load on reader, Release-store on writer; spin-while-negative is the load-bearing safety net. Reapplies at: W77 flow control sequence counter, W82 Image position cursor, W83 archive frame integrity.

  - **When `term_buffer_term_rotation_100m_messages` reports a stuck reader on PAD frame:**
    - Symptom: reader's position pointing at PAD frame in dirty term; doesn't advance to next term.
    - Why: PAD detection logic missed; treated PAD as data frame with length 0; spin-waiting for valid length forever.
    - Fix: reader detects PAD via `frame_type == PAD`; explicitly rolls cursor to next term's start; releases dirty term for recycling.
    - Muscle: a ring with rotation needs explicit terminal-frame signaling (PAD) that reader handles via roll-to-next, not by length-loop. Reapplies at: W79 subscription term-boundary, W82 Image session-rotation, W83 archive cycle rotation.

  - **When `term_buffer_n8_publications_aggregate_7x_n1` reports 4× scaling:**
    - Symptom: 8 publications achieve only 4× the throughput of 1 (expected 7×); flame graph shows shared mmap region causing cross-publication contention.
    - Why: all 8 publications backed by same mmap file; system-wide page cache lock serializes; NUMA cross-socket if publications land on different sockets.
    - Fix: each publication has its OWN mmap region (separate file per session+stream); pin publication writer thread + corresponding reader thread to same NUMA node. Aeron's `image` model.
    - Muscle: per-publication isolation requires separate mmap regions, NOT shared. Cross-publication independence is a deployment requirement (NUMA affinity). Reapplies at: W77 IPC transport (per-publication file), W79 fan-out, W82 v1.5 SHIP.

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: efficient O(log N + k) trigger evaluation per print, where N = total stops, k = number triggered. Naive linear scan is O(N) per print × millions of prints = quadratic disaster. The BTreeMap-of-vectors data structure gives sorted range queries with deterministic iteration (critical for raft replication).

  - **Requirements** — write in `crates/matching-engine/notes/77_stop_ladder_design.md`:
    - R1. `on_print(sym, last_px, trigger_kind) -> Vec<StopOrder>` returns triggered stops in deterministic price-time order.
    - R2. Buy-stops trigger when `last_px >= trigger_px`; sell-stops when `last_px <= trigger_px`.
    - R3. Gap-through: market gaps $99 → $101 with stops at $100 fires ALL $100 stops on the $101 print (first crossing rule).
    - R4. Trigger types: StopMarket (→ market), StopLimit (→ limit), TrailingStop (anchor updates on favorable prints).
    - R5. Deterministic across raft replicas: BTreeMap iteration + within-price-level by `(account_id, order_id)` lex order.
    - R6. Per-print check ≤50 ns for N=10k stops typical (cache-resident BTreeMap walk).
    - R7. Drain triggered stops in O(k) — `remove` (move), never `get + clone`.
    - R8. NO floats (cross-arch divergence risk); all price math integer i64 ticks.
    - R9. Trigger-kind specific (LastTrade/BestBid/BestAsk/MarkPrice) — separate ladders per kind.
    - R10. Self-trigger cascade rate-limited or paired with circuit breakers (W81).

  - **Design walk-through** — answer each:
    - D1. Sketch `StopLadder { buy_stops: BTreeMap<Price, Vec<StopOrder>>, sell_stops: BTreeMap<Price, Vec<StopOrder>> }`. Why two maps not one with side field?
    - D2. `on_print` walk: for buy_stops, iterate `range(..=last_px).rev()` (descending from triggered region); for each, drain and append. Pseudo-code.
    - D3. **Pre-mortem (Vec::clone on drain):** if `triggered.extend(self.buy_stops.get(&px).unwrap().clone())`, pay O(k) clone of every StopOrder (~80 ns each). For 100 stops, 8 µs of pure clone. Walk through `remove` (move semantics) fix.
    - D4. **Pre-mortem (gap-through):** market prints $95 then $110 with stops at $100, $105. Fire on first crossing ($110) — both fire. Stop-market emits market order filling at $110. Stop-limit with limit $100 doesn't fill (limit not crossed at $110). Document this clearly.
    - D5. **Pre-mortem (cascade):** triggered stop becomes market order, fills, prints at new level, triggers more stops. Cite Flash Crash post-mortem. Rate-limit cascade depth (e.g., max 5 levels per print event).
    - D6. **Pre-mortem (replica determinism):** raft replicas iterate `BTreeMap` deterministically; within price level, sort by `(account_id, order_id)` lex order so multiple stops at same px fire in deterministic order across replicas.

- [ ] [NEW v2 mmap-queue v0.5] **Build**: `crates/mmap-queue/src/pretouch.rs` — page-warming worker pre-faults next N

  - 🔧 **Why this matters**: When mmap'd files grow, accessing a new page triggers a *minor page fault* — kernel allocates a zero page, maps it in. At ~1µs latency this is fine for batch but devastating for HFT/HPC where P99 hard-real-time matters. Chronicle Queue ships this; Tier-A interview discussion. Downstream: W78 mmap-queue + messaging-aeron Archive integration; W79 v0.5 SHIP audit.

  #### Phase 1 — Problem, requirements, design (~45 min, no code yet)

  - **The problem this primitive solves**: a producer writing into a growing mmap pays a page-fault tax (~1-3 µs per 4 KiB page) on first touch — P99 latency includes ~3 µs spikes every 4 KiB of data. A background pretoucher walks pages ahead of the writer, faulting them on its own thread so producer hits warm pages only.

  - **Requirements** — write in `crates/mmap-queue/notes/77_pretouch_design.md`:
    - R1. Pretoucher only writes BYTES the producer has NOT YET reached — reads `current_tail` atomically, walks pages strictly AFTER tail.
    - R2. Page-warm write is **volatile + zero** — never corrupts data; relies on producer always overwriting.
    - R3. Pretoucher thread is dedicated, NOT shared with writer.
    - R4. Stop is cooperative; pretoucher exits within 100 µs of stop signal.
    - R5. `madvise(MADV_WILLNEED)` called ONCE per pretouch range (not per page) — kernel walks PTEs in one pass.
    - R6. Lookahead sized for write rate: `pretouch_ahead >= write_rate × pretouch_sleep / page_size`. For 1 GB/s writer + 100 µs sleep + 4 KiB pages: ≥25 pages; use 64 for safety.
    - R7. Hugepage detection: if mmap backed by `/sys/kernel/mm/transparent_hugepage`, use 2 MiB stride.
    - R8. NUMA-local: pretouch thread pinned to sibling core of producer (same NUMA node).
    - R9. With pretoucher, producer P99 publish latency stays <200 ns under cold cache (vs >5 µs without).

  - **Design walk-through** — answer each:
    - D1. Sketch Pretoucher struct + spawn helper. Where does `current_tail: AtomicUsize` live (shared with writer)?
    - D2. **Pre-mortem (producer overtake):** producer faster than pretoucher; tail catches up; pretoucher writes zero into byte producer JUST wrote → corruption. Walk through the safety rule (tail + 1 page * GAP as lower bound).
    - D3. **Pre-mortem (page eviction):** pretoucher warms page N; kernel evicts under memory pressure; producer hits cold page anyway. Mitigation: `mlock` working set (requires CAP_IPC_LOCK + RLIMIT_MEMLOCK) or hugepages (typically not evicted).
    - D4. **Pre-mortem (NUMA cross-socket):** pretouch thread on socket 0, producer on socket 1 → faulted pages allocated on socket 0's memory; cross-socket access on every write. Fix: pin pretouch to sibling core same NUMA.
    - D5. **Pre-mortem (madvise per page):** naive `madvise(ptr, page_size, MADV_WILLNEED)` per page = 1 syscall per page = ~300 ns × 64 pages = 20 µs/iter syscall overhead. Walk through batch fix.
    - D6. Hugepage math: 2 MiB stride vs 4 KiB stride. 1 GB/s writer = 244k TLB entries/sec for 4 KiB pages (constant miss); 488 entries/sec for 2 MiB (TLB resident).

  - **Output**: `notes/77_pretouch_design.md` with R1–R9 + D1–D6 + the producer/pretoucher ordering diagram.
