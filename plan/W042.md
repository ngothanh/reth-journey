  - *Mental model*: a `Txn` is a state machine + identity + ordering for every transaction.
    Active → Preparing → Committed | Aborted; never backwards. The state CAS is the linearization point for
    commit/abort decisions; the HLC.started_at is the global ordering for OCC validation.

  - *Contract*: `Txn { id: TxId, started_at: Hlc, state: AtomicU8, locks: LockSet, log_records: SmallVec<[Lsn; 8]> }`;
    `fn begin(pool: &TxnPool) -> Arc<Txn>` (slab slot, no alloc); `fn transition(&self, prior: State, new: State) -> Result<(), State>`
    (CAS, returns observed terminal state on loss); `fn commit/abort(&self) -> Result<()>`. State enum `#[repr(u8)]`.

  - *Back-of-envelope* (bar (c)): target 100 k tx/sec sustained, 1 M/sec burst. Naive `Arc::new(Txn)` =
    malloc ~50 ns + refcount cell ~30 ns + free ~30 ns ≈ 80–110 ns/Txn → at 100 k/sec that is 8–11 ms/sec of
    pure allocator CPU AND, worse, allocator-lock contention spikes p99 begin() from ~100 ns to ~500 ns under
    1 M/sec burst (blows the 10 µs commit budget). Slab-pop is a single `SegQueue` CAS ≈ 10–15 ns =
    **5–8× cliff** and a flat tail. State CAS itself: ~7 ns uncontended (one `lock cmpxchg`), the SeqCst
    fence adds a store-buffer drain only on the contended path.

  - **Requirements** — write in `crates/txn/notes/42_lifecycle_design.md`:
    - R1. State enum with explicit `#[repr(u8)]`; backed by AtomicU8.
    - R2. **State transitions monotonic**: every transition is `compare_exchange(prior, new, SeqCst)`;
      loser observes the winner's terminal state.
    - R3. **HLC.started_at monotonic** — stores max(physical, prior_hlc + 1). NTP step back must not move
      started_at backward.
    - R4. **Slab-allocated Txn pool** — no heap alloc per Txn::new(). Pre-allocate max_concurrent_txns slab
      slots; free list via SegQueue<u32>.
    - R5. Lifecycle API: `begin`, `read`, `write`, `prepare`, `commit`, `abort`.
    - R6. log_records append-only; on abort, undo records emit but log_records stays for replay.
    - R7. Long-running txn deadline enforcement — txn manager kills active txns older than deadline.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)
  Ordered newbie-first, expert-last — the ladder you actually walk.

  - **(SENIOR) When `lifecycle_hlc_monotonic_under_ntp_step_back` reports started_at going backward:**
    - Symptom: physical clock steps back 1 s (NTP correction); subsequent Hlc::now() returns a value
      < prior Hlc; OCC validation breaks because the version comparison reverses.
    - Why: HLC monotonicity violated — NTP step back makes `started_at` go backward.
    - Fix: HLC stores max(physical, prior_hlc + 1). On every `now()` call, compare physical clock
      against last-issued HLC; return max + 1 if physical regressed. The HLC's logical component
      absorbs the backward step.
    - Muscle: any system-clock-derived ordering must defend against clock step-backs; max with
      prior value is the canonical fix. Reapplies at: W14 time crate Hlc, W74 matching-engine
      order timestamps.

  - **(SENIOR) When `loom_lifecycle_state_cas_race` reports torn state (two threads see different terminal
    states):**
    - Symptom: 2 threads commit, 2 threads abort concurrently; some observers see Committed, some
      see Aborted; the "winner" is ambiguous.
    - Why: state CAS race — two threads attempt to commit + abort concurrently; without CAS one
      wins ambiguously. Without SeqCst, the loser's observation may not see the winner's terminal
      state.
    - Fix: every transition is `compare_exchange(prior, new, SeqCst)`; loser observes the winner's
      terminal state. On failure, the CAS returns the actual current value — the loser uses that.
    - Cost avoided: torn terminal state = double-commit / double-abort = a durability correctness bug
      (bar (c) violation), not a slowdown; the SeqCst fence costs only a store-buffer drain (~handful of ns)
      on the already-contended path.
    - Muscle: state machines under concurrency need SeqCst CAS at every transition; the loser must
      observe the winner's outcome. Reapplies at: W74 matching-engine order-state transitions, W11
      MPMC closed flag, W67 consensus-raft term-bump CAS.

  - **(EXPERT, anti-shortcut — bar (c) violation) When `bench_lifecycle_no_heap_alloc` reports allocator increments per Txn::new():**
    - Symptom: 100 k cycles → 100 k allocations; flamegraph shows ~8 ms/sec CPU on `malloc_zone_*`;
      under 10× burst load p99 begin() latency jumps from ~100 ns to ~500 ns, blowing the 10 µs
      commit budget.
    - Why: `TxnManager::begin()` does `Arc::new(Txn { ... })` which calls malloc (~50 ns) + Arc
      refcount cell allocation; on drop, free (~30 ns). At 100k tx/sec that's 80 ns × 100k = 8 ms/sec
      of pure allocator time = ~0.8% CPU one core, but symptom is worse: tail latency.
    - Fix: **slab-allocated Txn pool** — pre-allocate `max_concurrent_txns` Txn structs in a
      `Vec<UnsafeCell<Txn>>`; track free list via `crossbeam-queue::SegQueue<u32>` of slot indices.
      `begin()` pops a slot index (~10 ns CAS), resets the Txn fields in place. `Arc::from(raw)` over
      the slab slot. On drop, push index back to free list.
    - Cost avoided: 80 ns/Txn → ~15 ns/Txn = **5× faster**; zero allocator contention; static memory
      invariant (bar (c) requirement for HFT critical path) preserved.
    - Muscle: "pre-allocate the steady-state working set" — if your N-active count has a known
      ceiling, allocate once, recycle slots forever. Reapplies at: W74 matching-engine Order pool,
      W80 ledger Transfer pool, W84 messaging-aeron Image pool, W90 marketdata Tick pool.

  - **5-year failure mode** (write in `notes/42_lifecycle_followup.md` after green): when
    pre-emptible userspace scheduling (PREEMPT_RT, or io_uring-based async schedulers) becomes
    standard, the slab + SegQueue pattern needs to be wait-free, not lock-free. State migration:
    swap to wait-free slot allocator.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)
  Ordered newbie-first, expert-last — the ladder you actually walk.

  - **(SENIOR) When `manager_crash_before_committed_record_recovers_abort` reports the txn marked Committed:**
    - Symptom: kill -9 between state Preparing and Committed-record fsync; on restart, the txn is in
      `active` but the WAL has no Committed record; recovery sees an orphan.
    - Why: remove from active before durable commit — removing then crashing leaves WAL with an
      in-progress txn that no one will abort.
    - Fix: remove only after Committed record is fsynced. Sequence: state CAS Active→Preparing → WAL
      append commit-record → WAL fsync → state CAS Preparing→Committed → release locks → remove from
      active. If crash in window before remove, recovery: scan active in manifest, check WAL for
      committed-record; if missing, abort and clean up.
    - Cost avoided: orphan txns in WAL on crash = a recovery correctness bug (bar (c) violation), not a
      slowdown; the extra ordering costs nothing at runtime.
    - Muscle: durability ordering: durable record FIRST, observability state next, cleanup last.
      Reapplies at: W26 WAL group commit, W74 matching-engine durable-order publish.

  - **(SENIOR) When `manager_dashmap_guard_not_held_across_fsync` reports guard held during fsync:**
    - Symptom: lock-duration instrumentation shows the DashMap entry guard held for ~1 ms during
      WAL fsync; other writers block on the same shard for that ms; under burst, write throughput
      collapses.
    - Why: DashMap entry held during long ops — holding a DashMap entry guard across a WAL fsync
      blocks other writers.
    - Fix: clone `Arc<Txn>` out of the guard before doing work. Pattern: `let txn = { let entry =
