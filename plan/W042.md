- [ ] **Build**: `crates/txn/src/lifecycle.rs` —
  `Txn { id: TxId, started_at: Hlc, state: AtomicState, locks: LockSet, log_records: SmallVec<Lsn> }`. State enum:
  Active, Preparing, Committed, Aborted. (~105 min)
  - **Why**: The Txn struct is the unit of concurrency control. Every mutation passes through it; correctness hinges on a clean state machine. The HLC (Hybrid Logical Clock) timestamp is the global ordering for OCC validation and snapshot reads; AtomicState is the linearization point for commit/abort decisions. State transitions are: Active → Preparing → Committed | Aborted; Committed and Aborted are terminal.
  - *Back-of-envelope*: Txn alloc is per-request — at 100k commits/sec target (≈ matching-engine pre-trade tx volume) that's one Txn struct allocated and dropped every **10 µs**. Per-Txn fields: `id: u64` (8 B) + `started_at: Hlc` (16 B) + `state: AtomicU8` (1 B + padding) + `locks: LockSet` (typically 0-8 keys; SmallVec<8>) + `log_records: SmallVec<Lsn, 32>` + `read_set` + `write_set`. **Total ~256 B/Txn** if stack-allocated; ~256 B + ~50 ns malloc if heap. CAS state transition ≈ **10 ns uncontended**, ~50-100 ns under contention (commit vs abort race). HLC.now() ≈ **30 ns** (atomic monotonic load + max-compare). Implication: the txn struct itself must NOT heap-allocate on the common path — pool the Txn objects (`Arc<Txn>` from a slab) so a 10 µs commit cycle isn't dominated by ~100 ns of alloc+dealloc per cycle.
  - **Read first**: InnoDB `trx0trx.h` (trx_t struct); CockroachDB `pkg/kv/kvserver/txn_log.go`.
  - **Design**:
    ```rust
    #[repr(u8)]
    pub enum TxnState { Active=0, Preparing=1, Committed=2, Aborted=3 }
    pub struct Txn {
        pub id: TxId,
        pub started_at: Hlc,
        pub state: AtomicU8, // TxnState
        pub locks: LockSet,
        pub log_records: SmallVec<Lsn, 32>,
        pub read_set: ReadSet,  // for OCC
        pub write_set: WriteSet, // pending writes
    }
    ```
    **Invariants**:
    - State transitions are monotonic: Active → Preparing → Committed | Aborted; never backwards.
    - HLC.started_at is unique and increases with monotonic real time.
    - log_records is append-only; on abort, undo records are emitted but log_records stays for replay.
  - **Build steps**:
    1. (~20 min) State enum + AtomicU8 transitions via compare_exchange.
    2. (~25 min) TxId allocator: AtomicU64; HLC integration (uses W14 time crate).
    3. (~30 min) ReadSet/WriteSet structs: BTreeMap<Key, (Version, Bytes)>.
    4. (~20 min) Lifecycle API: `begin`, `read`, `write`, `prepare`, `commit`, `abort`.
    5. (~10 min) Property test: state transitions are monotonic under concurrent CAS attempts.
  - **Pitfalls**:
    - *State CAS race*: two threads attempt to commit + abort concurrently; without CAS one wins ambiguously. **Symptom**: torn state. **Fix**: every transition is `compare_exchange(prior, new, SeqCst)`; loser observes the winner's terminal state.
    - *HLC monotonicity violated*: NTP step back makes `started_at` go backward. **Symptom**: OCC validation breaks. **Fix**: HLC stores max(physical, prior_hlc + 1).
    - *Long-running txn holds locks*: forgetting to enforce a deadline causes liveness collapse. **Fix**: txn manager kills active txns older than deadline; aborts with timeout error.
    - **Expect to hit (perf) #1 — heap alloc per Txn::new() (bar (c) violation)**: `TxnManager::begin()` does `Arc::new(Txn { ... })` which calls malloc (~50 ns) + Arc refcount cell allocation; on drop, free (~30 ns). At 100k tx/sec that's 80 ns × 100k = **8 ms/sec of pure allocator time** = ~0.8% CPU one core, but symptom is worse: tail latency. Under burst (10× spike to 1M tx/sec), malloc contention on the system allocator's arena lock spikes per-Txn alloc to 200-500 ns → p99 begin() latency jumps from ~100 ns to ~500 ns, blowing the 10 µs commit budget.
      - Fix: **slab-allocated Txn pool** — pre-allocate `max_concurrent_txns` Txn structs in a `Vec<UnsafeCell<Txn>>`; track free list via `crossbeam-queue::SegQueue<u32>` of slot indices. `begin()` pops a slot index (~10 ns CAS), resets the Txn fields in place. `Arc::from(raw)` over the slab slot. On drop, push index back to free list.
      - Cost avoided: 80 ns/Txn → ~15 ns/Txn = **5× faster**; zero allocator contention; static memory invariant (bar (c) requirement for HFT critical path) preserved.
      - Muscle: "pre-allocate the steady-state working set" — if your N-active count has a known ceiling, allocate once, recycle slots forever. Reapplies at: W74 matching-engine Order pool, W80 ledger Transfer pool, W84 messaging-aeron Image pool, W90 marketdata Tick pool.
  - **Test scenarios**:
    - Property: 100 concurrent threads each CAS-transitioning a single Txn; final state is exactly one of Committed/Aborted; pre-state was always observed correctly.
    - Lifecycle: begin → write → commit; verify LSN appended, locks released.
  - **Acceptance**: 1M begin/commit cycles < 1s; zero state-race in loom.
  - **Downstream**: 2PL (Wed), OCC (Thu), 2PC (W72); ledger txn (W80); matching-engine order-book mutations (W74).
- [ ] **Build**: `crates/txn/src/manager.rs` —
  `TxnManager { next_id: AtomicU64, active: DashMap<TxId, Arc<Txn>>, ... }`. (~105 min)
  - **Why**: The Manager is the registry — every active txn is reachable from here so the deadlock detector can scan the wait-for graph, the lock manager can resolve waits, and a recovery process can replay outstanding txns. DashMap provides per-shard concurrency for begin/end; the next_id atomic is the only true global hotspot.
  - *Back-of-envelope*: at 100k tx/sec, DashMap.insert/.remove is called 200k × /sec. DashMap shards = num_cpus (~16); per-shard mutex acquire ≈ **25 ns uncontended, ~200 ns contended**. Cache footprint: `Entry<TxId, Arc<Txn>>` ≈ 32 B; at 10k concurrent active txns, the table holds ~320 KB — fits in L2 (~1 MB/core) but **straddles cache lines** if not aligned, doubling load cost. next_id fetch_add ≈ **10 ns uncontended, ~100 ns under contention** (16 cores fighting for the cache line); at 100k begin/sec → ~10% of one core spent on `next_id`. Implication: next_id is a **single cache-line hotspot** — must live on its own `CachePadded<AtomicU64>` (W4 muscle) to avoid false sharing with the DashMap shard pointers nearby in `TxnManager`.
  - **Design**:
    ```rust
    pub struct TxnManager {
        next_id: AtomicU64,
        active: DashMap<TxId, Arc<Txn>>,
        clock: Hlc,
        lock_manager: Arc<LockManager>,
        wal: Arc<wal::Wal>,
    }
    impl TxnManager {
        pub fn begin(&self) -> Arc<Txn>;
        pub fn commit(&self, t: Arc<Txn>) -> Result<()>;
        pub fn abort(&self, t: Arc<Txn>) -> Result<()>;
        pub fn active_txns(&self) -> impl Iterator<Item = Arc<Txn>> + '_;
    }
    ```
    **Invariants**:
    - A Txn is in `active` iff its state ∈ {Active, Preparing}.
    - next_id is monotonic; restart picks up from manifest's max_txid + 1.
    - active.len() ≤ max_concurrent_txns (configurable).
  - **Build steps**:
    1. (~20 min) `begin`: bump next_id; create Txn; insert into active.
    2. (~30 min) `commit`: state CAS Active→Preparing; flush WAL prepare; CAS Preparing→Committed; release locks; remove from active.
    3. (~25 min) `abort`: state CAS to Aborted; emit CLRs via recovery::UndoPass; release locks; remove from active.
    4. (~20 min) Iter over active for deadlock detector.
    5. (~10 min) Recovery: scan WAL for txns missing Committed record → abort.
  - **Pitfalls**:
    - *Remove from active before durable commit*: removing then crashing leaves WAL with an in-progress txn that no one will abort. **Fix**: remove only after Committed record is fsynced.
    - *DashMap entry held during long ops*: holding a DashMap entry guard across a WAL fsync blocks other writers. **Fix**: clone Arc<Txn> out of the guard before doing work.
    - **Expect to hit (perf) #1 — false sharing between `next_id` and DashMap shard pointers (bar (c) violation)**: declaring `next_id: AtomicU64` as a regular field places it on the same 64-byte cache line as the DashMap shard pointer array. Every `begin()` does `fetch_add(1)` (writes `next_id`'s line), which invalidates the line on every other core; every `commit()` does `active.remove()` (reads the DashMap shard pointer from the same line) — those readers then take a full L3 / cross-socket roundtrip ≈ **80-200 ns** to refetch. Symptom: `perf stat -e cache-misses,LLC-loads` shows DashMap hot path dominated by L3 cache misses; throughput plateaus at ~50k begin/sec even on 16 cores (linear scaling would give ~1M/sec).
      - Fix: `next_id: CachePadded<AtomicU64>` (W4 pattern, `crossbeam_utils::CachePadded`); place each frequently-mutated atomic on its own 64 (or 128 on M-series) byte line. Same treatment for any `active.len()` cached counter.
      - Cost avoided: ~80 ns → ~10 ns per `begin()` under contention = **8× speedup** at 16-core scale; throughput recovers from 50k to ~800k begin/sec; LLC-loads on the hot path drop ~95%.
      - Muscle: "every atomic that's written hot lives alone on its cache line" — and the corollary, every cold-read field can pack tightly. Reapplies at: W74 matching-engine per-symbol counters, W77 messaging-aeron publication seq, W84 runtime-thread-per-core shard scheduler counters, W90 marketdata RX queue indices.

**Wednesday — `txn` 2PL + deadlock detect + [NEW v2] lsm-core::TWCS: theory + skeleton**

- [ ] **Build**: `crates/txn/src/locks.rs` — `LockManager` with shared/exclusive lock table per key. Wound-Wait deadlock
  prevention (newer transactions wound older ones). (~105 min)
  - **Why**: 2PL (two-phase locking) is the canonical pessimistic concurrency control. Phase 1 acquires locks; phase 2 releases them (only at commit/abort, i.e. strict 2PL). The deadlock-prevention scheme matters: wound-wait (older wounds younger that holds wanted lock) vs wait-die (younger dies if older holds wanted) gives different starvation profiles. We pick wound-wait because long-running older txns shouldn't be aborted — but it means younger txns must handle "wounded" state cleanly.
  - *Back-of-envelope*: average txn acquires ~4 locks before commit. At 100k commits/sec → 400k acquire+release/sec, each ≈ DashMap shard lock (~25 ns) + holders check (~30 ns) + waiters Vec push if contended (~50 ns alloc-free). **Target acquire latency p99 ≤ 200 ns uncontended**. Under heavy contention (hot key — e.g., one account in a payment ledger), the per-key DashMap entry becomes the bottleneck: every acquire serializes on the entry's RwLock; futex-driven contention adds **~300 ns** for the wake. Lock-table memory: at 1M live locks × ~64 B Entry ≈ 64 MB — fits comfortably; but `VecDeque<(TxId, LockMode, Waker)>` for waiters can heap-grow under burst (push 100 waiters in 1 ms → ~5 reallocs).
  - **Read first**: InnoDB `lock0lock.cc` (`lock_rec_lock`); CMU Andy Pavlo's 2PL slides; Bernstein-Hadzilacos-Goodman ch. 3.
  - **Design**:
    ```rust
    pub enum LockMode { Shared, Exclusive }
    pub struct LockManager {
        table: DashMap<Key, LockEntry>,
    }
    pub struct LockEntry {
        holders: Vec<(TxId, LockMode)>,
        waiters: VecDeque<(TxId, LockMode, Waker)>,
    }
    pub enum LockResult { Granted, Wait, Wounded(TxId) }
    impl LockManager {
        pub fn acquire(&self, txid: TxId, key: &Key, mode: LockMode) -> LockResult;
        pub fn release_all(&self, txid: TxId);
    }
    ```
    **Invariants**:
    - Shared locks are compatible with shared; exclusive is exclusive of all.
    - On wound: holder's state CAS to Aborted; releases all locks; waiter is granted.
    - Holders + waiters are atomic per-key (single DashMap entry lock).
  - **Build steps**:
    1. (~25 min) LockEntry data + compatibility matrix.
    2. (~30 min) `acquire`: if compatible → grant; else if holder is older → wound it (CAS Active→Aborted; release locks); else add to waiters; return Wait.
    3. (~25 min) `release_all`: remove txid from holders for every locked key; wake waiters whose mode is now compatible.
    4. (~15 min) Async waker integration: Wait returns a Future the txn awaits.
    5. (~10 min) Tests as listed.
  - **Pitfalls**:
    - *Lock thrashing under wound*: two txns repeatedly wound each other (if both call acquire on same key simultaneously). **Symptom**: livelock. **Fix**: wound is one-shot; once wounded, the wounded txn must abort and retry with a higher ID.
    - *Waiter starvation*: shared-lock convoy forms; exclusive waiter never wakes. **Symptom**: txn waits forever. **Fix**: FIFO waiter queue; once an exclusive waiter is at the head, block new shared grants.
    - *Lock leak on panic*: panic in user code between acquire and commit leaks locks. **Fix**: RAII LockGuard auto-releases on drop.
    - **Expect to hit (perf) #1 — `waiters: VecDeque` heap-growth under burst (bar (c) violation)**: a hot key under burst (1000 txns contending on one account row) pushes 1000 waiters into a single `VecDeque` over ~1 ms; the VecDeque doubles capacity ~10 times (1 → 2 → 4 → 1024), each grow = malloc new buf + memcpy old contents + free old buf. At Vec capacity 512, growth = `malloc(8 KB)` (~80 ns under arena contention) + `memcpy 512 × 32 B` (~150 ns) + `free` (~30 ns) = ~260 ns per grow × 10 grows = **2.6 µs of pure resize overhead** during the burst, and worse: each grow holds the per-key entry lock, blocking *every other* acquire on this key for those 2.6 µs.
      - Fix: `SmallVec<[Waiter; 8]>` for the common case (≤8 waiters); spill to a pre-sized `Vec::with_capacity(max_waiters)` only when contention is detected. Bar (c): use a slab-allocated waiter pool keyed on `next_waiter_id` (no per-waiter heap alloc on the hot path); waiters live in a freelist.
      - Cost avoided: ~2.6 µs/burst → ~50 ns/burst = **50× faster burst handling**; p99 acquire latency drops from ~3 µs under contention to ~300 ns; no lock-entry contention amplification.
      - Muscle: "amortize the data-structure growth cost, or pre-size it" — VecDeque/Vec doubling is great average-case but catastrophic for tail latency. Reapplies at: W74 matching-engine OrderBook price-level queue, W84 runtime-thread-per-core cross-shard inbox, W77 messaging-aeron retransmit buffer.
    - **Expect to hit (perf) #2 — futex syscall per wake on lock release (bar (c) violation)**: `release_all` calls `Waker::wake()` for each waiter whose mode is now compatible. Under Tokio default, this calls into the executor's notify path which ends up in `futex(FUTEX_WAKE)` on Linux (~300 ns) or `pthread_cond_signal` on macOS (~500 ns). At 4 locks released per commit × 100k commits/sec = **400k syscalls/sec = ~120 ms/sec of syscall time = ~12% of one core** burning entirely on wake. Plus: `Waker::wake()` is move-by-value so it `Arc::drop`s internally (~10 ns refcount + maybe free).
      - Fix: batch wakes — `release_all` collects all wakers into a stack-allocated `SmallVec<Waker, 8>`, then drops the lock-entry guard, then iterates wakes outside the lock. For the *cross-shard* path (waiter on different core), use `crossbeam-channel` MPSC with single-element batching: write all wakes as one message, single futex wake at the channel boundary. Reduces syscalls from O(waiters) to O(1) per release.
      - Cost avoided: 4 syscalls × 300 ns → 1 syscall × 300 ns per release = **~75% reduction in syscall time**; ~120 ms/sec → ~30 ms/sec on the wake path; tail latency p99 on release drops from ~2 µs to ~500 ns.
      - Muscle: "syscalls in the hot path are tax — batch them or eliminate them" — every release_all is one logical unit of work; the wake fan-out should be amortized too. Reapplies at: W74 matching-engine fill-notification fan-out, W77 messaging-aeron subscriber notifications, W83 runtime-thread-per-core cross-shard wake batching.
  - **Test scenarios**:
    - 4 txns racing on 4 keys; verify Wound-Wait prevents deadlock; older always wins.
    - Strict 2PL: locks released only at commit/abort, never earlier.
    - Loom: 4-txn 4-key race; no deadlock observed.
  - **Acceptance**: 1M lock/unlock < 500ms; zero deadlocks in loom; zero starvation in stress.
- [ ] **Build**: `crates/txn/src/deadlock.rs` — wait-for graph + cycle detection (Tarjan SCC) as a fallback for explicit
  deadlock detection. (~105 min)
  - **Why**: Wound-Wait prevents deadlock by construction *if* every wait edge follows the age order. But the OCC path doesn't lock; if you mix 2PL and OCC, cycles can form in subtle ways. A periodic detector scans the wait-for graph and breaks cycles by aborting the youngest. Tarjan's SCC runs in O(V+E) which is fine for thousands of active txns.
  - *Back-of-envelope*: detector runs every 100 ms (default). Per-run cost: scan ~10k active txns + ~40k wait edges (avg 4 locks held); Tarjan SCC = O(V+E) = ~50k ops × ~5 ns per (vec push + cmp) = **~250 µs per scan**. Memory: HashMap<TxId, NodeId> for the graph mapping + Vec<Vec<NodeId>> adjacency = ~10k × 64 B + 40k × 16 B ≈ ~1.3 MB — straddles L2 (~1 MB/core) so a fresh scan is cold-cache; SCC walks miss L2 ~60% of the time = ~100 µs of cache-miss time. Scan acquires per-key DashMap read-lock briefly (~25 ns × 40k locks = ~1 ms aggregate, but the detector takes them serially so total scan wall-time ≈ 1-2 ms). Implication: the **HashMap-per-scan allocations** are the hot spot — clearing+rebuilding 10k-entry HashMap allocates ~640 KB each tick.
  - **Read first**: Tarjan 1972 SCC; PostgreSQL `src/backend/storage/lmgr/deadlock.c` (uses a different approach but same idea).
  - **Design**:
    ```rust
    pub struct DeadlockDetector {
        mgr: Arc<TxnManager>,
        interval: Duration,
    }
    impl DeadlockDetector {
        pub fn run_once(&self) -> Vec<TxId> /* victims */;
    }
    fn build_wait_graph(active: &[Arc<Txn>], locks: &LockManager) -> Graph;
    fn tarjan_scc(g: &Graph) -> Vec<Vec<NodeId>>;
    ```
    **Invariants**:
    - Detector is monotone: only adds wait-for edges that are presently valid.
    - Victim choice: within a cycle, kill the youngest (highest TxId).
    - Detector is read-only on lock table; victim abort is a separate atomic action.
  - **Build steps**:
    1. (~25 min) Build wait-for graph: for each waiter (T, K, mode), add edge T → holder(K) (if incompatible).
    2. (~30 min) Tarjan SCC.
    3. (~25 min) For each SCC of size ≥ 2: pick youngest; signal abort via CAS Active→Aborted; release locks.
    4. (~15 min) Scheduler: thread runs `run_once` every `interval`.
    5. (~10 min) Tests as below.
  - **Pitfalls**:
    - *Graph snapshot torn*: building the graph reads lock state non-atomically; a snapshot may show a phantom cycle (edge added after a concurrent release). **Symptom**: false deadlock; aborts a victim that wasn't actually deadlocked. **Fix**: re-validate the cycle before aborting (every edge still present); skip if not.
    - *Detector lag*: interval too long → real deadlocks hang. **Fix**: 100ms default; on-demand trigger from lock acquire timeout.
    - *Abort cascade*: aborting victim T releases locks → grants new wait → new cycle. **Fix**: detector is idempotent; runs again next cycle.
    - **Expect to hit (perf) #1 — per-scan graph allocation churn (bar (c) violation)**: each `run_once` builds a fresh `HashMap<TxId, NodeId>` (~640 KB at 10k txns) + `Vec<Vec<NodeId>>` adjacency (~640 KB) + Tarjan's intermediate `Vec<NodeId>` stacks. Per-scan = ~1.3 MB allocated + 1.3 MB freed = **~2 ms of malloc/memset/free** at 10k txns (linear in active count). The 100 ms tick budget is fine standalone, but the allocation pressure feeds back into the global allocator → contention with foreground `begin()` Arc allocs. Symptom: under deadlock-detection storm (cycles forming/breaking), foreground p99 begin() latency doubles for ~10 ms windows.
      - Fix: **reusable scratch buffers** — `DeadlockDetector` owns persistent `graph: HashMap<TxId, NodeId>`, `adj: Vec<Vec<NodeId>>`, `tarjan_stack: Vec<NodeId>`. `run_once` calls `.clear()` (O(N) but no realloc/free) and reuses capacity. Optional: `BumpAllocator` (per-scan reset arena) for transient nodes — `arena.reset()` at scan end frees all in O(1).
      - Cost avoided: ~2 ms/scan of allocator work → ~50 µs/scan = **40× faster scan**; allocator contention with foreground vanishes; p99 begin() flat-lines.
      - Muscle: "reuse buffers across rounds when the workload is periodic" — anything that runs on a timer should own its scratch space. Reapplies at: W74 matching-engine snapshot serialization scratch buf, W84 runtime reactor per-tick batched events, W92 ledger VOPR per-scenario state.
  - **Test scenarios**:
    - 4 txns in a cycle T1→T2→T3→T4→T1; detector picks youngest (T4) as victim.
    - Mixed 2PL+OCC: OCC-only cycle still detected (OCC tracks wait-for via version conflict graph).
    - No false positive: linear chain with no cycle → no aborts.
  - **Acceptance**: detection latency ≤ 2×interval; zero false positives.

- [ ] [NEW v2] **Build**: `crates/lsm-core/src/compaction/twcs.rs` — `TimeWindowCompactor { window: Duration }`. One SSTable per fully-elapsed window; drop entire window on TTL expiry. (~90 min)
  - **Why**: For time-series workloads (and ledger journals, market data), every record has a timestamp and naturally ages out. TWCS bins SSTables by time window (e.g., 1 hour); when a window is fully elapsed, no new writes go there; when a window age exceeds TTL, the entire window is unlinked — no merge needed, just file deletes. This is dramatically cheaper than STCS/LCS for TTL workloads (write amp ≈ 1, vs ≥ 4 for STCS).
  - **Read first**: Cassandra `TimeWindowCompactionStrategy.java`; Jeff Jirsa's "Introducing TWCS" blog.
  - **Design**:
    ```rust
    pub struct TwcsCompactor {
        window: Duration,    // e.g., 1 hour
        ttl: Duration,       // e.g., 7 days
        windows: BTreeMap<WindowId, Vec<SstReader>>, // sorted by time
        active: WindowId,    // current accepting window
    }
    type WindowId = u64;   // (ts / window_secs)
    ```
    **Invariants**:
    - All entries within an SST have timestamps in [window_start, window_end).
    - Active window receives flushes; non-active windows are immutable.
    - Drop happens when `now - window_end > ttl`.
  - **Build steps**:
    1. (~20 min) Window assignment: on flush, partition memtable by ts/window; emit one SST per window (typically all in active).
    2. (~25 min) Within-window compaction: if window has > N SSTs, run STCS-like merge bounded to that window only (no cross-window).
    3. (~15 min) Window drop: scheduler scans windows; if `now - window_end > ttl`, unlink files atomically via manifest.
    4. (~15 min) Test as below.
    5. (~15 min) Doc + edge cases (clock skew, future timestamps).
  - **Pitfalls**:
    - *Out-of-order writes*: a late-arriving record with timestamp in an already-immutable window must go somewhere. **Symptom**: either it goes to active (breaking invariant) or write is rejected. **Fix**: late writes (within grace period) go to active window; very late writes are rejected with a typed error.
    - *Window granularity wrong*: too small → millions of SSTs; too large → drop granularity is poor. **Fix**: window sized to ttl/100 or coarser based on rate.
    - *Manifest churn on drop*: dropping 1000 windows at once = 1000 manifest records. **Fix**: batch drop in a single manifest record.
  - **Test scenarios**:
    - 1M entries across 10 windows; TTL = 5 windows; after time passes, half the SSTs are dropped without rewrites.
    - Out-of-order: late record arrives; assigned to active or rejected per policy.
  - **Acceptance**: write amp ≈ 1; drop is O(1) per window; TTL respected within 1 window.

**Thursday — `txn` OCC + write phase + [NEW v2] lsm-core::TWCS: drop-window + integration**

- [ ] **Build**: `crates/txn/src/occ.rs` — `OccValidator` validates read-set version stamps at commit. Used for
  read-heavy workloads. (~105 min)
  - **Why**: OCC (Kung & Robinson 1981) trades pessimistic locking for optimistic execution: read freely, track version numbers, validate at commit that no version changed. For read-heavy workloads it dominates 2PL because there are no read locks. The downside: aborts on write-write or read-write conflicts; high abort rate under write contention.
  - *Back-of-envelope*: at 100k OCC commits/sec × avg 20 reads/txn → 2M read-set entries built/sec. Per-entry write to BTreeMap<Key, Version> ≈ **~100 ns** (BTreeMap insert is O(log N) ≈ 6 comparisons × 5 ns + ~50 ns alloc for B+ node split when capacity exceeded). validate() walks read-set in order = ~100 ns × 20 = **~2 µs per commit** of pure validation. Under a serial commit-lock (naive Silo-style), this serializes commits: max throughput = 1 / (commit_latency + validate_latency) ≈ 1 / (5 µs + 2 µs) = **~140k commits/sec single-thread** — already near the 100k target before factoring conflict aborts. Read-set memory: 20 entries × ~64 B ≈ 1.3 KB per Txn — at 10k active OCC txns → ~13 MB read-set memory (L3-resident is fine). Critical: BTreeMap allocates per insert — at 2M inserts/sec, that's 2M × ~50 ns alloc = **100 ms/sec = 10% of one core** burning on BTreeMap node alloc.
  - **Read first**: Kung & Robinson 1981 "On Optimistic Methods for Concurrency Control"; CockroachDB's SSI implementation; Silo paper (Tu et al. 2013).
  - **Design**:
    ```rust
    pub struct OccValidator;
    pub struct ReadSet { versions: BTreeMap<Key, Version> }
    pub struct WriteSet { writes: BTreeMap<Key, Bytes> }
    impl OccValidator {
        pub fn validate(read_set: &ReadSet, store: &impl Versioned) -> bool;
    }
    pub trait Versioned {
        fn current_version(&self, key: &Key) -> Version;
    }
    ```
    **Invariants**:
    - Read-set validation is atomic with respect to the commit point.
    - On validation success, write-set is applied with new version stamps.
    - If validation fails, the txn aborts; reads are discarded.
  - **Build steps**:
    1. (~20 min) ReadSet + WriteSet types; per-read snapshot of `(key, version)`.
    2. (~30 min) `validate`: for each (key, expected_version), confirm current_version == expected_version under a global serial validation lock.
    3. (~30 min) Apply write-set on success: increment version per key; emit WAL records.
    4. (~15 min) Abort path: discard read_set and write_set; no other state to undo (no locks held).
    5. (~10 min) Test: read-only txns never conflict; write-write conflicts abort exactly one.
  - **Pitfalls**:
    - *Validation-write race*: between validate() and apply(), another txn commits same key. **Symptom**: lost update. **Fix**: validate + apply under a serial commit lock OR use 2-phase OCC (Silo-style) with lock-then-validate.
    - *Phantom reads*: range query versions not captured. **Symptom**: anomaly under range-write. **Fix**: track range predicates in read_set (predicate locks).
    - *Memory blowup on long read-set*: read_set grows unboundedly for large scans. **Fix**: cap; spill to disk; or fall back to 2PL.
    - **Expect to hit (perf) #1 — `BTreeMap<Key, Version>` for ReadSet (bar (c) violation)**: per-read insert ≈ 100 ns (BTreeMap log N + allocation amortized), per-validate walk ≈ 100 ns × N. For typical OCC txns of 4-20 reads, BTreeMap's branching overhead is *worse* than a sorted Vec: the cache footprint is fragmented across multiple node allocations (each B-node is ~280 B but reached by indirection). 2M reads/sec × ~50 ns alloc = ~100 ms/sec malloc time; symptom: OCC validation is ~3× slower than the textbook expectation despite "O(log N)" complexity — because constant factors and allocator dominate at N < 64.
      - Fix: `SmallVec<[(Key, Version); 16]>` for ReadSet, sorted on commit. Insert is push (~5 ns); validate sorts in-place (~200 ns for 16 entries) then binary-searches each key in the store. **Zero heap alloc** for common case (N ≤ 16); spill to `Box<[(Key, Version)]>` for large scans. SmallVec is inline-allocated in the Txn struct → no pointer-chase, fits in one cache line for small N.
      - Cost avoided: 100 ns/insert → 5 ns/insert = **20× faster build**; 100 ns/probe → 30 ns/probe (binary search in cache-line-resident array) = **3× faster validate**; zero alloc on hot path.
      - Muscle: "sorted Vec beats BTreeMap up to N ≈ 64" — branchy log-N data structures only pay off at large N. Reapplies at: W74 matching-engine OrderBook level depth (sorted Vec per level), W80 ledger batch read-set, W95 mini-db memtable lookup cache.
  - **Test scenarios**:
    - 16 read-only txns: zero aborts.
    - 16 write-heavy on same key: exactly one commits per epoch; rest abort cleanly.
    - Property: serializability — any committed schedule is equivalent to a serial order.
  - **Acceptance**: read-only throughput ≥ 10x 2PL; abort rate proportional to contention.
- [ ] **Build**: `crates/txn/src/commit.rs` — commit path: prepare WAL record → fsync → mark Committed → release locks.
  Abort path: emit CLRs via `recovery::UndoPass` if necessary. (~105 min)
  - **Why**: Commit/abort is the linearization point — the WAL record's fsync is the durability fence; the state CAS is the observability fence. Order matters: if you mark Committed before WAL fsync, a crash loses the commit but observers saw success → split brain. If you mark Committed after WAL fsync but before locks are released, observers see committed state but other txns are still blocked (correctness preserved, perf hit). Strict order: WAL fsync → state CAS → release locks → remove from active.
  - *Back-of-envelope*: fsync is the dominant cost. **NVMe fsync ≈ 50-200 µs**; SATA SSD ≈ 500-1000 µs; HDD ≈ 5-10 ms. At 100k commits/sec target with single-fsync-per-commit: 100k × 100 µs = **10 sec of fsync time per wall second** — impossible single-thread. Group commit is the only path: at 1000 txns/group × 100 groups/sec × 100 µs fsync = **10 ms of fsync time per second**, with each commit waiting on average ~5 ms for its batch (1000 / 200k group-arrival-rate ≈ 5 ms window). State CAS ≈ **10 ns**; release_all locks (avg 4 locks) ≈ **40 ns × 4 = 160 ns**; remove from DashMap ≈ **25 ns**. Total non-fsync commit cost ≈ ~200 ns; the fsync **dominates by 1000×**. Implication: every µs of fsync-adjacent work (preparing WAL record, signing) MUST be done outside the group-commit's serial fsync window — otherwise it serializes the whole batch.
  - **Read first**: ARIES paper (Mohan 1992); InnoDB `trx0trx.cc::trx_commit_in_memory`.
  - **Design**:
    ```rust
    impl TxnManager {
        pub fn commit(&self, t: Arc<Txn>) -> Result<()> {
            t.state.compare_exchange(Active, Preparing, SeqCst, ...)?;
            self.wal.append_commit(t.id, &t.log_records)?;
            self.wal.fsync()?;
            t.state.store(Committed, Release);
            self.locks.release_all(t.id);
            self.active.remove(&t.id);
            Ok(())
        }
    }
    ```
    **Invariants**:
    - WAL Commit record is durable BEFORE state becomes Committed.
    - Observability of Committed state implies durability.
    - Lock release after state transition (so a concurrent acquire observes the terminal state, not Preparing).
  - **Build steps**:
    1. (~25 min) Commit happy path as above.
    2. (~30 min) Abort path: state CAS Active→Aborted; emit undo records via recovery::UndoPass; fsync WAL abort; release locks.
    3. (~30 min) Group commit: batch many fsyncs (W26 wal Tuesday pattern) — pin txns at Preparing; one shared fsync covers all.
    4. (~10 min) Test: torn-commit recovery (kill between WAL fsync and state CAS → recovery sees committed in WAL, marks Committed).
    5. (~10 min) Doc + tracing.
  - **Pitfalls**:
    - *State before fsync*: race window where observer sees Committed but data isn't durable. **Symptom**: stale read after crash. **Fix**: fsync first; state transition after.
    - *Lock release before state*: another acquire grabs the lock, sees Preparing in the previous holder, aborts based on stale state. **Fix**: state transition is the linearization point; locks held until then.
    - *Group commit unfairness*: late-arriving txns wait for the batch leader's fsync. **Fix**: bound batch wait (1ms typical); large solo commits bypass batching.
    - **Expect to hit (perf) #1 — single-fsync-per-commit instead of group commit (bar (c) violation)**: textbook commit pseudocode reads `wal.append → wal.fsync → state.store(Committed)`, and if implemented literally, every txn issues its own fsync syscall. At NVMe fsync ≈ 100 µs, that caps throughput at **10k commits/sec/disk** — 10× below the 100k target. Worse, each fsync is a `io_uring`/`fdatasync` syscall that takes the disk write queue's lock for the duration; under 16 concurrent committers contending on the same WAL file, throughput collapses to ~5k/sec as the disk queue lock thrashes.
      - Fix: **leader-based group commit** (W26 wal Tuesday pattern). One committer becomes the leader, calls `fsync` once; followers wait on a `Notify` keyed to the LSN of the leader's tail. The first follower-after-fsync wakes all batched followers via single `Notify::notify_waiters()`. Tunable batch window (default 1 ms or 1000 txns, whichever first). Each follower's commit() blocks on `wait_for_lsn(my_tail_lsn)`; the leader does `fsync` + `notify_waiters()` once per batch.
      - Cost avoided: 100 µs/commit fsync → ~5 µs/commit amortized = **20× throughput uplift**; 100k commits/sec achievable on one NVMe; disk queue contention drops to zero.
      - Muscle: "the fsync is the cost — amortize it across as many independent commits as the durability semantics allow" — group commit is the canonical pattern. Reapplies at: W74 matching-engine durable order log batching, W80 ledger journal group fsync, W92 ledger io_uring batched submission, W77 messaging-aeron archive batched fsync.
    - **Expect to hit (perf) #2 — WAL record serialization inside the fsync window (bar (c) violation)**: doing `bincode::serialize(&commit_record)` *inside* the group's serial section blocks all followers; serialization is ~500 ns for a typical commit record (LSN list + checksum), but holding the WAL-write lock for those 500 ns × 1000 followers = **500 µs of serial work per batch** = ~50% throughput loss. Worse, if the serialization allocates (`Vec<u8>` for output buf), the malloc adds another ~80 ns per record, compounding inside the batch.
      - Fix: each txn serializes its commit record into a **thread-local pre-allocated 4 KB buffer** *before* entering the group; the leader's job is purely `concat slabs → writev → fdatasync → notify`. Followers do all CPU work in parallel; the serial section is pure I/O.
      - Cost avoided: 500 µs serial → 0 µs serial per batch; the only serial work is writev + fdatasync; group throughput uplift ~2×.
      - Muscle: "minimize what runs inside a critical section to literally only what must be serialized" — everything precomputable should be done in parallel before the section. Reapplies at: W74 matching-engine order-log batching, W80 ledger journal pre-serialize, W77 messaging-aeron pre-batched publication writes.
  - **Test scenarios**:
    - Kill between fsync and state CAS: recovery replays WAL Commit; final state Committed; observers always see correct outcome.
    - 1000 concurrent commits with group commit: throughput ≥ 5x single-fsync.
    - Loom: state CAS and lock release ordering verified.
  - **Acceptance**: 100k commits/sec with group commit; recovery correct after kill-9 at any point.
