  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: a state machine + identity + ordering for every transaction.
    Active → Preparing → Committed | Aborted; never backwards. The state CAS is the linearization point for
    commit/abort decisions; the HLC.started_at is the global ordering for OCC.

  - **Requirements** — write in `crates/txn/notes/42_lifecycle_design.md`:
    - R1. State enum with explicit `#[repr(u8)]`; backed by AtomicU8.
    - R2. **State transitions monotonic**: every transition is `compare_exchange(prior, new, SeqCst)`;
      loser observes the winner's terminal state.
    - R3. **HLC.started_at monotonic** — stores max(physical, prior_hlc + 1). NTP step back must not move
      started_at backward.
    - R4. **Slab-allocated Txn pool** — no heap alloc per Txn::new(). Pre-allocate max_concurrent_txns slab
      slots; free list via SegQueue<u32>.
    - R5. Lifecycle API: `begin`, `read`, `write`, `prepare`, `commit`, `abort`.
    - R6. log_records append-only; on abort, undo records emit but log_records stays for replay.
    - R7. Long-running txn deadline enforcement — txn manager kills active txns older than deadline.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)

  - **When `bench_lifecycle_no_heap_alloc` reports allocator increments per Txn::new():**
    - Symptom: 100 k cycles → 100 k allocations; flamegraph shows ~8 ms/sec CPU on `malloc_zone_*`;
      under 10× burst load p99 begin() latency jumps from ~100 ns to ~500 ns, blowing the 10 µs
      commit budget.
    - Why: `TxnManager::begin()` does `Arc::new(Txn { ... })` which calls malloc (~50 ns) + Arc
      refcount cell allocation; on drop, free (~30 ns). At 100k tx/sec that's 80 ns × 100k = 8 ms/sec
      of pure allocator time = ~0.8% CPU one core, but symptom is worse: tail latency.
    - Fix: **slab-allocated Txn pool** — pre-allocate `max_concurrent_txns` Txn structs in a
      `Vec<UnsafeCell<Txn>>`; track free list via `crossbeam-queue::SegQueue<u32>` of slot indices.
      `begin()` pops a slot index (~10 ns CAS), resets the Txn fields in place. `Arc::from(raw)` over
      the slab slot. On drop, push index back to free list.
    - Cost avoided: 80 ns/Txn → ~15 ns/Txn = **5× faster**; zero allocator contention; static memory
      invariant (bar (c) requirement for HFT critical path) preserved.
    - Muscle: "pre-allocate the steady-state working set" — if your N-active count has a known
      ceiling, allocate once, recycle slots forever. Reapplies at: W74 matching-engine Order pool,
      W80 ledger Transfer pool, W84 messaging-aeron Image pool, W90 marketdata Tick pool.

  - **When `loom_lifecycle_state_cas_race` reports torn state (two threads see different terminal
    states):**
    - Symptom: 2 threads commit, 2 threads abort concurrently; some observers see Committed, some
      see Aborted; the "winner" is ambiguous.
    - Why: state CAS race — two threads attempt to commit + abort concurrently; without CAS one
      wins ambiguously. Without SeqCst, the loser's observation may not see the winner's terminal
      state.
    - Fix: every transition is `compare_exchange(prior, new, SeqCst)`; loser observes the winner's
      terminal state. On failure, the CAS returns the actual current value — the loser uses that.
    - Muscle: state machines under concurrency need SeqCst CAS at every transition; the loser must
      observe the winner's outcome. Reapplies at: W74 matching-engine order-state transitions, W11
      MPMC closed flag.

  - **When `lifecycle_hlc_monotonic_under_ntp_step_back` reports started_at going backward:**
    - Symptom: physical clock steps back 1 s (NTP correction); subsequent Hlc::now() returns a value
      < prior Hlc; OCC validation breaks because the version comparison reverses.
    - Why: HLC monotonicity violated — NTP step back makes `started_at` go backward.
    - Fix: HLC stores max(physical, prior_hlc + 1). On every `now()` call, compare physical clock
      against last-issued HLC; return max + 1 if physical regressed. The HLC's logical component
      absorbs the backward step.
    - Muscle: any system-clock-derived ordering must defend against clock step-backs; max with
      prior value is the canonical fix. Reapplies at: W14 time crate Hlc, W74 matching-engine
      order timestamps.

  - **5-year failure mode** (write in `notes/42_lifecycle_followup.md` after green): when
    pre-emptible userspace scheduling (PREEMPT_RT, or io_uring-based async schedulers) becomes
    standard, the slab + SegQueue pattern needs to be wait-free, not lock-free. State migration:
    swap to wait-free slot allocator.

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)

  - **When `bench_manager_begin_16_thread_scales` reports plateau at ~50 k/sec:**
    - Symptom: 16-thread aggregate plateaus at ~50 k begin/sec (linear scaling would give ~1 M/sec);
      `perf stat -e cache-misses,LLC-loads` shows DashMap hot path dominated by L3 cache misses.
    - Why: declaring `next_id: AtomicU64` as a regular field places it on the same 64-byte cache line as
      the DashMap shard pointer array. Every `begin()` does `fetch_add(1)` (writes `next_id`'s line),
      which invalidates the line on every other core; every `commit()` does `active.remove()` (reads
      the DashMap shard pointer from the same line) — those readers then take a full L3 / cross-socket
      roundtrip ≈ 80-200 ns to refetch.
    - Fix: `next_id: CachePadded<AtomicU64>` (W4 pattern, `crossbeam_utils::CachePadded`); place each
      frequently-mutated atomic on its own 64 (or 128 on M-series) byte line. Same treatment for any
      `active.len()` cached counter.
    - Cost avoided: ~80 ns → ~10 ns per `begin()` under contention = **8× speedup** at 16-core scale;
      throughput recovers from 50k to ~800k begin/sec; LLC-loads on the hot path drop ~95%.
    - Muscle: "every atomic that's written hot lives alone on its cache line" — and the corollary,
      every cold-read field can pack tightly. Reapplies at: W74 matching-engine per-symbol counters,
      W77 messaging-aeron publication seq, W84 runtime-thread-per-core shard scheduler counters, W90
      marketdata RX queue indices.

  - **When `manager_crash_before_committed_record_recovers_abort` reports the txn marked Committed:**
    - Symptom: kill -9 between state Preparing and Committed-record fsync; on restart, the txn is in
      `active` but the WAL has no Committed record; recovery sees an orphan.
    - Why: remove from active before durable commit — removing then crashing leaves WAL with an
      in-progress txn that no one will abort.
    - Fix: remove only after Committed record is fsynced. Sequence: state CAS Active→Preparing → WAL
      append commit-record → WAL fsync → state CAS Preparing→Committed → release locks → remove from
      active. If crash in window before remove, recovery: scan active in manifest, check WAL for
      committed-record; if missing, abort and clean up.
    - Muscle: durability ordering: durable record FIRST, observability state next, cleanup last.
      Reapplies at: W26 WAL group commit, W74 matching-engine durable-order publish.

  - **When `manager_dashmap_guard_not_held_across_fsync` reports guard held during fsync:**
    - Symptom: lock-duration instrumentation shows the DashMap entry guard held for ~1 ms during
      WAL fsync; other writers block on the same shard for that ms; under burst, write throughput
      collapses.
    - Why: DashMap entry held during long ops — holding a DashMap entry guard across a WAL fsync
      blocks other writers.
    - Fix: clone `Arc<Txn>` out of the guard before doing work. Pattern: `let txn = { let entry =
      active.get(&id); entry.clone() };  // guard dropped; do_work_on(txn);`.
    - Muscle: never hold a sharded-map guard across a slow op; clone the Arc and release the guard.
      Reapplies at: W42 LockManager wait-list, W74 matching-engine order-book shard access.

  - **5-year failure mode** (write in `notes/42_manager_followup.md` after green): when wait-free hash
    maps (e.g. ConcMap with no per-shard locks) stabilize in Rust, the DashMap pattern simplifies.
    State migration: swap DashMap → ConcMap; trigger when wait-free crate ships in 2026+.

- [ ] **Build**: `crates/txn/src/locks.rs` — `LockManager` with shared/exclusive lock table per key. Wound-Wait deadlock
  prevention (newer transactions wound older ones). (~total 155 min across 3 phases)
  - 🔧 **Why this matters**: 2PL is the workhorse of pessimistic concurrency. Wound-Wait prevents deadlock by
    construction (older wounds younger). Wrong fairness → waiter starvation; VecDeque growth under burst →
    50× slower hot-key handling; per-waiter futex syscall → 12% CPU burning on wakes. W74 matching-engine
    order-book, W80 ledger inherit all three patterns.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)

  - **The problem this primitive solves**: shared/exclusive locks per key, deadlock-free via Wound-Wait
    (older wounds younger), strict 2PL semantics (locks released only at commit/abort), waiter wake
    batching to amortize syscalls.

  - **Requirements** — write in `crates/txn/notes/42_locks_design.md`:
    - R1. Shared compatible with Shared; Exclusive exclusive of all.
    - R2. **Wound-Wait**: on conflict, if requester older than holder, wound the holder (CAS state to
      Aborted, release its locks); requester is granted.
    - R3. **Strict 2PL**: locks released only at commit/abort (RAII LockGuard).
    - R4. **FIFO waiter queue**: once an exclusive waiter is at the head, block new shared grants.
    - R5. **Slab-allocated waiter pool**: no per-waiter heap alloc; SmallVec<Waiter; 8> + spill to
      pre-sized Vec.
    - R6. **Batched wakes**: `release_all` collects wakers into stack-allocated SmallVec, drops lock,
      then wakes outside the critical section.
    - R7. Acquire latency p99 ≤ 200 ns uncontended; ≤ 3 µs under contention.
    - R8. Zero deadlocks in loom 4-txn 4-key race; zero starvation in stress.

    - D2. Wound-Wait: write the algorithm. Why does the requester wound the holder (not the other way)?
    - D3. FIFO waiter discipline: how do you ensure an exclusive waiter at the head doesn't get

    - D4. Waiter pool: write the SmallVec spill logic. When is the slab-allocated pool used?

  #### Phase 3 — Make the tests pass, one failure at a time (~90 min)

  - **When `bench_lock_burst_no_vec_growth` reports 10 reallocs per burst:**
    - Symptom: 1000 waiters in 1 ms burst → VecDeque grows ~10 times (1 → 2 → ... → 1024); each grow ~260
      ns under arena contention; total 2.6 µs of pure resize overhead with per-key entry lock held,
      blocking every other acquire on this key.
    - Why: `waiters: VecDeque` heap-growth under burst — VecDeque doubles capacity ~10 times under
      sustained push pressure; each grow holds the per-key entry lock, blocking *every other* acquire on
      this key for those 2.6 µs.
    - Fix: `SmallVec<[Waiter; 8]>` for the common case (≤8 waiters); spill to a pre-sized
      `Vec::with_capacity(max_waiters)` only when contention is detected. Bar (c): use a slab-allocated
      waiter pool keyed on `next_waiter_id` (no per-waiter heap alloc on the hot path); waiters live in
      a freelist.
    - Cost avoided: ~2.6 µs/burst → ~50 ns/burst = **50× faster burst handling**; p99 acquire latency
      drops from ~3 µs under contention to ~300 ns; no lock-entry contention amplification.
    - Muscle: "amortize the data-structure growth cost, or pre-size it" — VecDeque/Vec doubling is great
      average-case but catastrophic for tail latency. Reapplies at: W74 matching-engine OrderBook

  - **When `bench_lock_release_one_syscall` reports 8 futex_wake syscalls:**
    - Symptom: release_all on 8 waiters → 8 futex_wake calls × 300 ns = 2.4 µs of syscall time per
      release; at 4 locks × 100 k commits/sec = 400 k syscalls/sec = ~120 ms/sec = 12% CPU on wakes
      alone.
    - Why: under Tokio default, `Waker::wake()` calls into the executor's notify path which ends up in
      `futex(FUTEX_WAKE)` (~300 ns per call). Plus `Waker::wake()` is move-by-value so it `Arc::drop`s
      internally.
    - Fix: batch wakes — `release_all` collects all wakers into a stack-allocated `SmallVec<Waker, 8>`,
      then drops the lock-entry guard, then iterates wakes outside the lock. For the cross-shard path
      (waiter on different core), use `crossbeam-channel` MPSC with single-element batching: write all
      wakes as one message, single futex wake at the channel boundary. Reduces syscalls from
      O(waiters) to O(1) per release.
    - Cost avoided: 4 syscalls × 300 ns → 1 syscall × 300 ns per release = ~75% reduction in syscall
      time; 120 ms/sec → 30 ms/sec; tail latency p99 on release drops from ~2 µs to ~500 ns.
    - Muscle: "syscalls in the hot path are tax — batch them or eliminate them." Reapplies at: W74
      matching-engine fill-notification fan-out, W77 messaging-aeron subscriber notifications, W83
      runtime-thread-per-core cross-shard wake batching.

  - **When `lock_fifo_exclusive_no_starvation` reports the exclusive waiter waiting forever:**
    - Symptom: exclusive waiter at head; continuous stream of shared requests; shared grants succeed
      (compatible with existing shared holders); exclusive never gets the lock.
    - Why: waiter starvation — shared-lock convoy forms; exclusive waiter never wakes.
    - Fix: FIFO waiter queue; once an exclusive waiter is at the head, block new shared grants. New
      shared requests join the waiter queue behind the exclusive waiter.
    - Muscle: any shared/exclusive lock with waiters needs explicit fairness — without it, the
      exclusive path can starve under read load. Reapplies at: W74 matching-engine read/write order
      book, W14 bufpool page-table RW.

  - **When `lock_wound_wait_older_wins` reports livelock (two txns repeatedly wound each other):**
    - Symptom: T1 (older) and T2 (older relative to each other from different angles?); they ping-pong
      wounds; both abort + retry; cycle.
    - Why: lock thrashing under wound — two txns repeatedly wound each other if both call acquire on
      same key simultaneously.
    - Fix: wound is one-shot; once wounded, the wounded txn must abort and retry with a higher ID
      (so on retry, it's now "younger" relative to anyone who beat it last time). Combined with
      Wound-Wait's "older wins", this guarantees forward progress.
    - Muscle: any deadlock-prevention scheme needs a forward-progress invariant; "older wins" +
      "retry with higher ID" is the canonical pair. Reapplies at: W67 consensus-raft leader election,
      W74 matching-engine order-cancel retry.

    migration: keep LockManager for adversarial workloads; OCC for read-heavy default.

  #### Phase 1 — Problem, requirements, design (~35 min, no code yet)
