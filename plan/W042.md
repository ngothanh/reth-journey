- [ ] **Build**: `crates/txn/src/lifecycle.rs` —
  `Txn { id: TxId, started_at: Hlc, state: AtomicState, locks: LockSet, log_records: SmallVec<Lsn> }`. State enum:
  Active, Preparing, Committed, Aborted. (~105 min)
  - **Why**: The Txn struct is the unit of concurrency control. Every mutation passes through it; correctness hinges on a clean state machine. The HLC (Hybrid Logical Clock) timestamp is the global ordering for OCC validation and snapshot reads; AtomicState is the linearization point for commit/abort decisions. State transitions are: Active → Preparing → Committed | Aborted; Committed and Aborted are terminal.
  - **Read first**: InnoDB `trx0trx.h` (trx_t struct); CockroachDB `pkg/kv/kvserver/txn_log.go`.
  - **Design**:
    ```rust
    #[repr(u8)]
    pub enum TxnState { Active=0, Preparing=1, Committed=2, Aborted=3 }
    pub struct Txn {
        pub id: TxId,
        pub started_at: Hlc,
        pub state: AtomicU8, // TxnState
        pub locks: LockSet,
        pub log_records: SmallVec<Lsn, 32>,
        pub read_set: ReadSet,  // for OCC
        pub write_set: WriteSet, // pending writes
    }
    ```
    **Invariants**:
    - State transitions are monotonic: Active → Preparing → Committed | Aborted; never backwards.
    - HLC.started_at is unique and increases with monotonic real time.
    - log_records is append-only; on abort, undo records are emitted but log_records stays for replay.
  - **Build steps**:
    1. (~20 min) State enum + AtomicU8 transitions via compare_exchange.
    2. (~25 min) TxId allocator: AtomicU64; HLC integration (uses W14 time crate).
    3. (~30 min) ReadSet/WriteSet structs: BTreeMap<Key, (Version, Bytes)>.
    4. (~20 min) Lifecycle API: `begin`, `read`, `write`, `prepare`, `commit`, `abort`.
    5. (~10 min) Property test: state transitions are monotonic under concurrent CAS attempts.
  - **Pitfalls**:
    - *State CAS race*: two threads attempt to commit + abort concurrently; without CAS one wins ambiguously. **Symptom**: torn state. **Fix**: every transition is `compare_exchange(prior, new, SeqCst)`; loser observes the winner's terminal state.
    - *HLC monotonicity violated*: NTP step back makes `started_at` go backward. **Symptom**: OCC validation breaks. **Fix**: HLC stores max(physical, prior_hlc + 1).
    - *Long-running txn holds locks*: forgetting to enforce a deadline causes liveness collapse. **Fix**: txn manager kills active txns older than deadline; aborts with timeout error.
  - **Test scenarios**:
    - Property: 100 concurrent threads each CAS-transitioning a single Txn; final state is exactly one of Committed/Aborted; pre-state was always observed correctly.
    - Lifecycle: begin → write → commit; verify LSN appended, locks released.
  - **Acceptance**: 1M begin/commit cycles < 1s; zero state-race in loom.
  - **Downstream**: 2PL (Wed), OCC (Thu), 2PC (W72); ledger txn (W80); matching-engine order-book mutations (W74).
- [ ] **Build**: `crates/txn/src/manager.rs` —
  `TxnManager { next_id: AtomicU64, active: DashMap<TxId, Arc<Txn>>, ... }`. (~105 min)
  - **Why**: The Manager is the registry — every active txn is reachable from here so the deadlock detector can scan the wait-for graph, the lock manager can resolve waits, and a recovery process can replay outstanding txns. DashMap provides per-shard concurrency for begin/end; the next_id atomic is the only true global hotspot.
  - **Design**:
    ```rust
    pub struct TxnManager {
        next_id: AtomicU64,
        active: DashMap<TxId, Arc<Txn>>,
        clock: Hlc,
        lock_manager: Arc<LockManager>,
        wal: Arc<wal::Wal>,
    }
    impl TxnManager {
        pub fn begin(&self) -> Arc<Txn>;
        pub fn commit(&self, t: Arc<Txn>) -> Result<()>;
        pub fn abort(&self, t: Arc<Txn>) -> Result<()>;
        pub fn active_txns(&self) -> impl Iterator<Item = Arc<Txn>> + '_;
    }
    ```
    **Invariants**:
    - A Txn is in `active` iff its state ∈ {Active, Preparing}.
    - next_id is monotonic; restart picks up from manifest's max_txid + 1.
    - active.len() ≤ max_concurrent_txns (configurable).
  - **Build steps**:
    1. (~20 min) `begin`: bump next_id; create Txn; insert into active.
    2. (~30 min) `commit`: state CAS Active→Preparing; flush WAL prepare; CAS Preparing→Committed; release locks; remove from active.
    3. (~25 min) `abort`: state CAS to Aborted; emit CLRs via recovery::UndoPass; release locks; remove from active.
    4. (~20 min) Iter over active for deadlock detector.
    5. (~10 min) Recovery: scan WAL for txns missing Committed record → abort.
  - **Pitfalls**:
    - *Remove from active before durable commit*: removing then crashing leaves WAL with an in-progress txn that no one will abort. **Fix**: remove only after Committed record is fsynced.
    - *DashMap entry held during long ops*: holding a DashMap entry guard across a WAL fsync blocks other writers. **Fix**: clone Arc<Txn> out of the guard before doing work.

**Wednesday — `txn` 2PL + deadlock detect + [NEW v2] lsm-core::TWCS: theory + skeleton**

- [ ] **Build**: `crates/txn/src/locks.rs` — `LockManager` with shared/exclusive lock table per key. Wound-Wait deadlock
  prevention (newer transactions wound older ones). (~105 min)
  - **Why**: 2PL (two-phase locking) is the canonical pessimistic concurrency control. Phase 1 acquires locks; phase 2 releases them (only at commit/abort, i.e. strict 2PL). The deadlock-prevention scheme matters: wound-wait (older wounds younger that holds wanted lock) vs wait-die (younger dies if older holds wanted) gives different starvation profiles. We pick wound-wait because long-running older txns shouldn't be aborted — but it means younger txns must handle "wounded" state cleanly.
  - **Read first**: InnoDB `lock0lock.cc` (`lock_rec_lock`); CMU Andy Pavlo's 2PL slides; Bernstein-Hadzilacos-Goodman ch. 3.
  - **Design**:
    ```rust
    pub enum LockMode { Shared, Exclusive }
    pub struct LockManager {
        table: DashMap<Key, LockEntry>,
    }
    pub struct LockEntry {
        holders: Vec<(TxId, LockMode)>,
        waiters: VecDeque<(TxId, LockMode, Waker)>,
    }
    pub enum LockResult { Granted, Wait, Wounded(TxId) }
    impl LockManager {
        pub fn acquire(&self, txid: TxId, key: &Key, mode: LockMode) -> LockResult;
        pub fn release_all(&self, txid: TxId);
    }
    ```
    **Invariants**:
    - Shared locks are compatible with shared; exclusive is exclusive of all.
    - On wound: holder's state CAS to Aborted; releases all locks; waiter is granted.
    - Holders + waiters are atomic per-key (single DashMap entry lock).
  - **Build steps**:
    1. (~25 min) LockEntry data + compatibility matrix.
    2. (~30 min) `acquire`: if compatible → grant; else if holder is older → wound it (CAS Active→Aborted; release locks); else add to waiters; return Wait.
    3. (~25 min) `release_all`: remove txid from holders for every locked key; wake waiters whose mode is now compatible.
    4. (~15 min) Async waker integration: Wait returns a Future the txn awaits.
    5. (~10 min) Tests as listed.
  - **Pitfalls**:
    - *Lock thrashing under wound*: two txns repeatedly wound each other (if both call acquire on same key simultaneously). **Symptom**: livelock. **Fix**: wound is one-shot; once wounded, the wounded txn must abort and retry with a higher ID.
    - *Waiter starvation*: shared-lock convoy forms; exclusive waiter never wakes. **Symptom**: txn waits forever. **Fix**: FIFO waiter queue; once an exclusive waiter is at the head, block new shared grants.
    - *Lock leak on panic*: panic in user code between acquire and commit leaks locks. **Fix**: RAII LockGuard auto-releases on drop.
  - **Test scenarios**:
    - 4 txns racing on 4 keys; verify Wound-Wait prevents deadlock; older always wins.
    - Strict 2PL: locks released only at commit/abort, never earlier.
    - Loom: 4-txn 4-key race; no deadlock observed.
  - **Acceptance**: 1M lock/unlock < 500ms; zero deadlocks in loom; zero starvation in stress.
- [ ] **Build**: `crates/txn/src/deadlock.rs` — wait-for graph + cycle detection (Tarjan SCC) as a fallback for explicit
  deadlock detection. (~105 min)
  - **Why**: Wound-Wait prevents deadlock by construction *if* every wait edge follows the age order. But the OCC path doesn't lock; if you mix 2PL and OCC, cycles can form in subtle ways. A periodic detector scans the wait-for graph and breaks cycles by aborting the youngest. Tarjan's SCC runs in O(V+E) which is fine for thousands of active txns.
  - **Read first**: Tarjan 1972 SCC; PostgreSQL `src/backend/storage/lmgr/deadlock.c` (uses a different approach but same idea).
  - **Design**:
    ```rust
    pub struct DeadlockDetector {
        mgr: Arc<TxnManager>,
        interval: Duration,
    }
    impl DeadlockDetector {
        pub fn run_once(&self) -> Vec<TxId> /* victims */;
    }
    fn build_wait_graph(active: &[Arc<Txn>], locks: &LockManager) -> Graph;
    fn tarjan_scc(g: &Graph) -> Vec<Vec<NodeId>>;
    ```
    **Invariants**:
    - Detector is monotone: only adds wait-for edges that are presently valid.
    - Victim choice: within a cycle, kill the youngest (highest TxId).
    - Detector is read-only on lock table; victim abort is a separate atomic action.
  - **Build steps**:
    1. (~25 min) Build wait-for graph: for each waiter (T, K, mode), add edge T → holder(K) (if incompatible).
    2. (~30 min) Tarjan SCC.
    3. (~25 min) For each SCC of size ≥ 2: pick youngest; signal abort via CAS Active→Aborted; release locks.
    4. (~15 min) Scheduler: thread runs `run_once` every `interval`.
    5. (~10 min) Tests as below.
  - **Pitfalls**:
    - *Graph snapshot torn*: building the graph reads lock state non-atomically; a snapshot may show a phantom cycle (edge added after a concurrent release). **Symptom**: false deadlock; aborts a victim that wasn't actually deadlocked. **Fix**: re-validate the cycle before aborting (every edge still present); skip if not.
    - *Detector lag*: interval too long → real deadlocks hang. **Fix**: 100ms default; on-demand trigger from lock acquire timeout.
    - *Abort cascade*: aborting victim T releases locks → grants new wait → new cycle. **Fix**: detector is idempotent; runs again next cycle.
  - **Test scenarios**:
    - 4 txns in a cycle T1→T2→T3→T4→T1; detector picks youngest (T4) as victim.
    - Mixed 2PL+OCC: OCC-only cycle still detected (OCC tracks wait-for via version conflict graph).
    - No false positive: linear chain with no cycle → no aborts.
  - **Acceptance**: detection latency ≤ 2×interval; zero false positives.

- [ ] [NEW v2] Read Cassandra TWCS doc (Time-Window Compaction Strategy — one SSTable per time window). (~30 min)
- [ ] [NEW v2] **Build**: `crates/lsm-core/src/compaction/twcs.rs` — `TimeWindowCompactor { window: Duration }`. One SSTable per fully-elapsed window; drop entire window on TTL expiry. (~90 min)
  - **Why**: For time-series workloads (and ledger journals, market data), every record has a timestamp and naturally ages out. TWCS bins SSTables by time window (e.g., 1 hour); when a window is fully elapsed, no new writes go there; when a window age exceeds TTL, the entire window is unlinked — no merge needed, just file deletes. This is dramatically cheaper than STCS/LCS for TTL workloads (write amp ≈ 1, vs ≥ 4 for STCS).
  - **Read first**: Cassandra `TimeWindowCompactionStrategy.java`; Jeff Jirsa's "Introducing TWCS" blog.
  - **Design**:
    ```rust
    pub struct TwcsCompactor {
        window: Duration,    // e.g., 1 hour
        ttl: Duration,       // e.g., 7 days
        windows: BTreeMap<WindowId, Vec<SstReader>>, // sorted by time
        active: WindowId,    // current accepting window
    }
    type WindowId = u64;   // (ts / window_secs)
    ```
    **Invariants**:
    - All entries within an SST have timestamps in [window_start, window_end).
    - Active window receives flushes; non-active windows are immutable.
    - Drop happens when `now - window_end > ttl`.
  - **Build steps**:
    1. (~20 min) Window assignment: on flush, partition memtable by ts/window; emit one SST per window (typically all in active).
    2. (~25 min) Within-window compaction: if window has > N SSTs, run STCS-like merge bounded to that window only (no cross-window).
    3. (~15 min) Window drop: scheduler scans windows; if `now - window_end > ttl`, unlink files atomically via manifest.
    4. (~15 min) Test as below.
    5. (~15 min) Doc + edge cases (clock skew, future timestamps).
  - **Pitfalls**:
    - *Out-of-order writes*: a late-arriving record with timestamp in an already-immutable window must go somewhere. **Symptom**: either it goes to active (breaking invariant) or write is rejected. **Fix**: late writes (within grace period) go to active window; very late writes are rejected with a typed error.
    - *Window granularity wrong*: too small → millions of SSTs; too large → drop granularity is poor. **Fix**: window sized to ttl/100 or coarser based on rate.
    - *Manifest churn on drop*: dropping 1000 windows at once = 1000 manifest records. **Fix**: batch drop in a single manifest record.
  - **Test scenarios**:
    - 1M entries across 10 windows; TTL = 5 windows; after time passes, half the SSTs are dropped without rewrites.
    - Out-of-order: late record arrives; assigned to active or rejected per policy.
  - **Acceptance**: write amp ≈ 1; drop is O(1) per window; TTL respected within 1 window.

- [ ] **Build**: `crates/txn/src/occ.rs` — `OccValidator` validates read-set version stamps at commit. Used for
  read-heavy workloads. (~105 min)
  - **Why**: OCC (Kung & Robinson 1981) trades pessimistic locking for optimistic execution: read freely, track version numbers, validate at commit that no version changed. For read-heavy workloads it dominates 2PL because there are no read locks. The downside: aborts on write-write or read-write conflicts; high abort rate under write contention.
  - **Read first**: Kung & Robinson 1981 "On Optimistic Methods for Concurrency Control"; CockroachDB's SSI implementation; Silo paper (Tu et al. 2013).
  - **Design**:
    ```rust
    pub struct OccValidator;
    pub struct ReadSet { versions: BTreeMap<Key, Version> }
    pub struct WriteSet { writes: BTreeMap<Key, Bytes> }
    impl OccValidator {
        pub fn validate(read_set: &ReadSet, store: &impl Versioned) -> bool;
    }
    pub trait Versioned {
        fn current_version(&self, key: &Key) -> Version;
    }
    ```
    **Invariants**:
    - Read-set validation is atomic with respect to the commit point.
    - On validation success, write-set is applied with new version stamps.
    - If validation fails, the txn aborts; reads are discarded.
  - **Build steps**:
    1. (~20 min) ReadSet + WriteSet types; per-read snapshot of `(key, version)`.
    2. (~30 min) `validate`: for each (key, expected_version), confirm current_version == expected_version under a global serial validation lock.
    3. (~30 min) Apply write-set on success: increment version per key; emit WAL records.
    4. (~15 min) Abort path: discard read_set and write_set; no other state to undo (no locks held).
    5. (~10 min) Test: read-only txns never conflict; write-write conflicts abort exactly one.
  - **Pitfalls**:
    - *Validation-write race*: between validate() and apply(), another txn commits same key. **Symptom**: lost update. **Fix**: validate + apply under a serial commit lock OR use 2-phase OCC (Silo-style) with lock-then-validate.
    - *Phantom reads*: range query versions not captured. **Symptom**: anomaly under range-write. **Fix**: track range predicates in read_set (predicate locks).
    - *Memory blowup on long read-set*: read_set grows unboundedly for large scans. **Fix**: cap; spill to disk; or fall back to 2PL.
  - **Test scenarios**:
    - 16 read-only txns: zero aborts.
    - 16 write-heavy on same key: exactly one commits per epoch; rest abort cleanly.
    - Property: serializability — any committed schedule is equivalent to a serial order.
  - **Acceptance**: read-only throughput ≥ 10x 2PL; abort rate proportional to contention.
- [ ] **Build**: `crates/txn/src/commit.rs` — commit path: prepare WAL record → fsync → mark Committed → release locks.
  Abort path: emit CLRs via `recovery::UndoPass` if necessary. (~105 min)
  - **Why**: Commit/abort is the linearization point — the WAL record's fsync is the durability fence; the state CAS is the observability fence. Order matters: if you mark Committed before WAL fsync, a crash loses the commit but observers saw success → split brain. If you mark Committed after WAL fsync but before locks are released, observers see committed state but other txns are still blocked (correctness preserved, perf hit). Strict order: WAL fsync → state CAS → release locks → remove from active.
  - **Read first**: ARIES paper (Mohan 1992); InnoDB `trx0trx.cc::trx_commit_in_memory`.
  - **Design**:
    ```rust
    impl TxnManager {
        pub fn commit(&self, t: Arc<Txn>) -> Result<()> {
            t.state.compare_exchange(Active, Preparing, SeqCst, ...)?;
            self.wal.append_commit(t.id, &t.log_records)?;
            self.wal.fsync()?;
            t.state.store(Committed, Release);
            self.locks.release_all(t.id);
            self.active.remove(&t.id);
            Ok(())
        }
    }
    ```
    **Invariants**:
    - WAL Commit record is durable BEFORE state becomes Committed.
    - Observability of Committed state implies durability.
    - Lock release after state transition (so a concurrent acquire observes the terminal state, not Preparing).
  - **Build steps**:
    1. (~25 min) Commit happy path as above.
    2. (~30 min) Abort path: state CAS Active→Aborted; emit undo records via recovery::UndoPass; fsync WAL abort; release locks.
    3. (~30 min) Group commit: batch many fsyncs (W26 wal Tuesday pattern) — pin txns at Preparing; one shared fsync covers all.
    4. (~10 min) Test: torn-commit recovery (kill between WAL fsync and state CAS → recovery sees committed in WAL, marks Committed).
    5. (~10 min) Doc + tracing.
  - **Pitfalls**:
    - *State before fsync*: race window where observer sees Committed but data isn't durable. **Symptom**: stale read after crash. **Fix**: fsync first; state transition after.
    - *Lock release before state*: another acquire grabs the lock, sees Preparing in the previous holder, aborts based on stale state. **Fix**: state transition is the linearization point; locks held until then.
    - *Group commit unfairness*: late-arriving txns wait for the batch leader's fsync. **Fix**: bound batch wait (1ms typical); large solo commits bypass batching.
  - **Test scenarios**:
    - Kill between fsync and state CAS: recovery replays WAL Commit; final state Committed; observers always see correct outcome.
    - 1000 concurrent commits with group commit: throughput ≥ 5x single-fsync.
    - Loom: state CAS and lock release ordering verified.
  - **Acceptance**: 100k commits/sec with group commit; recovery correct after kill-9 at any point.
