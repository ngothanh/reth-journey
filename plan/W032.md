**Monday — MPT proof generation (EIP-1186)**

- [ ] **Build**: `crates/eth-trie/src/proof/retainer.rs` — `ProofRetainer` that captures the ordered RLP node path for a target key during a trie walk. (~total 230 min across 3 phases)
  - 🔧 **Why this matters**: mirrors `reth-trie::proof::ProofRetainer`. An EIP-1186 Merkle proof is the consensus-critical artifact a light client uses to verify a single account/slot WITHOUT the full trie — it is the ordered list of RLP-encoded nodes from root to leaf. Proof generation is **bit-exact**: any deviation in node encoding (inlined vs hashed child, even/odd hex-prefix flag, branch slot ordering) makes a correct verifier reject. Four traps you WILL hit: (1) the inlined-child trap (small nodes are embedded, not hash-referenced), (2) the hex-prefix flag-collision trap, (3) the exclusion-proof terminal trap, (4) the snapshot-consistency trap. First-attempt impls fail ≥1 Phase-2 test below; the debug session IS the lesson. Downstream: W35-36 snapshot-sync verifies via these proofs, W95 mini-db light-client mode.

  #### Phase 1 — Problem, prediction, design (~50 min, no code yet)
  - 🎯 **Pre-prediction prompt** — write sealed answers in `crates/eth-trie/notes/32_proof_retainer_prediction.md`:
    - P1: the data structure you'd reach for to map target-path → ordered nodes (exact type, e.g. `HashMap<Nibbles, Vec<Bytes>>`).
    - P2: predicted proof size in bytes for a 10k-account trie (depth ~4-5 nodes × ~530 B/branch ≈ ?).
    - P3: predicted outcome when the trie walker encounters a branch child small enough to be inlined (< 32 B RLP) — does your retainer store the inlined bytes or a recomputed hash node?
    - P4: predict whether `keccak256(retained_node_bytes)` of node[i+1] equals the i-th node's child reference for ALL i (the verifier's core invariant).
    - P5 = list EVERY Phase-2 test you predict your first attempt will fail.
  - *Mental model*: a proof is a self-authenticating slice of the trie — given the root hash, each node's keccak must match a child reference in its parent, so the chain is tamper-evident down to the leaf.
  - *Contract*:
    ```rust
    pub struct ProofRetainer {
        targets: BTreeSet<Nibbles>,          // prefixes we want proofs for
        proofs: HashMap<Nibbles, Vec<Bytes>>, // target -> root-first ordered RLP nodes
    }
    impl ProofRetainer {
        pub fn new(targets: impl IntoIterator<Item = Nibbles>) -> Self;
        /// Called by the trie walker for each node it serializes. `path` is the
        /// prefix at this node; `rlp` is the EXACT bytes the trie wrote.
        pub fn retain(&mut self, path: &Nibbles, rlp: &[u8]);
        pub fn into_proofs(self) -> HashMap<Nibbles, Vec<Bytes>>;
    }
    ```
  - *Back-of-envelope* (bar (b) — correctness-bound, perf optional): proof gen is a single read-side trie walk, ~depth nodes per target. 10k accounts ⇒ depth ~log16(10000) ≈ 4 nodes; keccak of a 532-byte branch ≈ ~1µs cold. This runs off a read snapshot, not the hot path — so the budget is correctness, not ns. Note the cost ASYMMETRY: a wrong proof is detected only by a downstream verifier, so a layout bug is silent here and loud 30 weeks later.
  - **Requirements** R1..R6 — write in `crates/eth-trie/notes/32_proof_retainer_design.md`:
    - R1. `retain` stores the EXACT byte slice the trie serialized for that node — never a recomputed encoding.
    - R2. Per target, `proofs[target]` is ordered ROOT-FIRST (verifier walks in this order).
    - R3. A node is retained for target T iff its `path` is a prefix of T (an ancestor on T's path).
    - R4. Inlined children (RLP < 32 B, embedded directly in the parent) are NOT separately retained — they already live inside the retained parent's bytes.
    - R5. Exclusion proof: for a target with no leaf, the proof terminates at the deepest node on the path where the key diverges (the verifier proves absence from that node's structure).
    - R6. Proof generation reads a consistent snapshot (one read txn); no writer mutation observed mid-walk.
  - **Design walk-through** D1..D6 — answer in the design doc; no peeking at `reth-trie::proof.rs` until Phase 3:
    - D1. Primitive table: `HashMap<Nibbles,Vec<Bytes>>` vs `BTreeMap` vs `Vec<(Nibbles,Vec<Bytes>)>` — columns: ordered? prefix-query cost? alloc count per target? Choose and justify R2/R3.
    - D2. Walk a 3-node path (branch → extension → leaf). Write the exact retain() call sequence and the resulting `Vec<Bytes>`.
    - D3. **Pre-mortem (load-bearing):** write the EXACT failure trace where a contributor recomputes node bytes with `alloy_rlp::encode(node)` instead of storing the trie's own bytes — show how a hashed-vs-inlined child boundary produces different bytes ⇒ `keccak(node[1]) != child_ref(node[0])`.
    - D4. Inlined-child sketch: draw a branch with one child whose RLP is 31 bytes. Show it is embedded in the branch's RLP, so retaining it separately would be both wrong (R4) AND would break the verifier's hash chain.
    - D5. Exclusion trace: target key `0x12...`, trie has only `0x13...`. Show the walk diverges at the branch on the second nibble; name the terminal node retained.
    - D6. **Anti-shortcut audit:** the "obvious" reach is `alloy_rlp::encode(&node)` to (re)serialize for the proof — wrong HERE because it loses the inline/hash decision the trie already made; you must capture the trie's emitted bytes via the walker callback.

  #### Phase 3 — Make the tests pass, one failure at a time (~110 min)
  Ordered failure cards, newbie first, expert last.
  - **(NEWBIE) When `proof_is_root_first_ordered` reports `proof[0] does not hash to root`:**
    - Symptom: assertion fails; `keccak256(proof[0])` is the leaf hash, not the root.
    - Why: you appended nodes during the walk in unwind order (deepest first) instead of descent order.
    - Fix: push in descent order, or `reverse()` after collecting; the verifier requires root-first.
    - Muscle: a proof's order IS part of its contract — the verifier consumes it as a stream from the root. Reapplies at: W35 snapshot-sync proof streaming, W95 light-client proof replay.
  - **(SENIOR) When `proof_captures_trie_bytes_not_recomputed` reports `captured == recomputed` or recomputed unexpectedly verifies:**
    - Symptom: both byte vectors are equal, OR the re-encoded proof verifies — your retainer re-serialized nodes with `alloy_rlp::encode`.
    - Why: re-encoding loses the trie's inline-vs-hash decision; for nodes whose children are all hashed it happens to match, so the bug hides until a node has an inlined child — then `keccak(parent)` changes and the chain breaks downstream.
    - Fix: capture the EXACT bytes the trie emits via the walker callback (R1); never re-encode for proofs.
    - Muscle: a Merkle proof must carry the producer's own serialized bytes, because the hash commits to those exact bytes — recomputation is a silent forgery of the commitment. Reapplies at: W35 snapshot node serialization, W42 txn undo-record encoding, W95 light-client witness bytes.
  - **(SENIOR) When `exclusion_proof_terminates_at_divergence` returns "key present" or panics:**
    - Symptom: the absence proof is empty, or the verifier treats the terminal as an inclusion.
    - Why: you stopped retaining the moment `path` was no longer a strict prefix, dropping the divergence node that PROVES absence.
    - Fix: retain through the deepest ancestor on the target path; the terminal node's structure (a branch lacking the next nibble, or a leaf with a different remaining key) is the absence witness (R5).
    - Muscle: proof-of-absence is proof-of-structure-at-divergence, not an empty proof. Reapplies at: W34 bloom negative lookups, W95 light-client non-membership.
  - **(EXPERT) When `proof_verifies_after_concurrent_writer` verifies against the wrong root / is internally inconsistent:**
    - Symptom: proof's node[0] hashes to neither the pre- nor post-write root; intermittent across runs.
    - Why: proof gen read live trie nodes while a writer mutated them — torn read across two structural versions.
    - Fix: pin a read snapshot (W29-30 MVCC read txn) at proof start; walk only that version (R6).
    - Cost avoided: nondeterministic consensus artifact (a proof that verifies on neither root is a correctness defect, not just slow).
    - Muscle: a Merkle proof must be cut against ONE consistent version; mixing versions yields a proof of nothing. Reapplies at: W35 snapshot consistency, W42 txn read-snapshot isolation, W95 light-client state-root pinning.
  - **(EXPERT) When `proof_rejects_single_bit_flip` PASSES the flipped proof (negative control fails):**
    - Symptom: the flipped proof still "verifies" — your test (or verifier) isn't checking intermediate hashes.
    - Why: the verifier only checked `keccak(proof[0]) == root` and the final value, skipping the `windows(2)` hash-chain link.
    - Fix: verify EVERY link: node[i] must reference `keccak(node[i+1])`; only then is the chain tamper-evident.
    - Muscle: a Merkle verifier with an unchecked intermediate link is a rubber stamp — the negative control exists to catch exactly this. Reapplies at: W35 snapshot integrity check, W95 light-client verifier hardening.

**Tuesday — Standalone MPT proof verification (the consensus surface)**

- [ ] **Build**: `crates/eth-trie/src/proof/verify.rs` — `verify_proof(root, key, expected, proof)` total, panic-free verifier. (~total 200 min across 3 phases)
  - 🔧 **Why this matters**: mirrors `alloy-trie::proof::verify_proof`. The verifier is the consensus SURFACE — run by every light client and state-witness consumer on UNTRUSTED input. It must be (a) **total**: every malformed input yields a typed error, never a panic (a panic on crafted input is a DOS), and (b) correct against the hash chain. Three traps: (1) panic-on-malformed-RLP, (2) empty-value vs no-entry conflation, (3) the unchecked-intermediate-link rubber stamp. First attempts panic under fuzz or accept forged proofs. Downstream: W35-36 snapshot integrity, W95 mini-db light client.

  #### Phase 1 — Problem, prediction, design (~45 min, no code yet)
  - 🎯 **Pre-prediction prompt** — `crates/eth-trie/notes/32_proof_verify_prediction.md`:
    - P1: the decode primitive you'd reach for (`alloy_rlp::Decodable` — does it return `Result` or can it panic on truncated input?).
    - P2: predicted per-verify latency for a depth-5 proof (5 keccaks ≈ ?µs).
    - P3: predict what happens when `proof` is `[random 200 bytes]` from a fuzzer — panic, error, or accept?
    - P4: how do you distinguish "key maps to empty value `b""`" from "key absent"? (predict the signature.)
    - P5 = list every Phase-2 test your first attempt will fail.
  - *Mental model*: the verifier replays the proof as a deterministic walk from `root`, hashing each node and checking it matches the parent's child reference, ending in either the expected value (inclusion) or a divergence (exclusion).
  - *Contract*:
    ```rust
    pub fn verify_proof(
        root: B256,
        key: &[u8],
        expected: Option<&[u8]>,   // Some(v)=inclusion of v (v may be b""), None=exclusion
        proof: &[Bytes],
    ) -> Result<(), ProofError>;

    #[derive(Debug, PartialEq)]
    pub enum ProofError {
        RootMismatch,
        ValueMismatch,
        NodeHashMismatch { at: usize },
        UnexpectedNode { at: usize },
        BadHexPrefix,
        Rlp(alloy_rlp::Error),
    }
    ```
  - *Back-of-envelope* (bar (b)): a verify is `depth` keccaks + RLP decodes ≈ 5 × ~1µs ≈ ~5µs; happy path should be zero-alloc (proof bytes are borrowed, no Vec growth). Cost focus is robustness, not ns: the dominant risk is a single panic path turning a public RPC into a crash.
  - **Requirements** R1..R6 — write in `notes/32_proof_verify_design.md`:
    - R1. `keccak256(proof[0]) == root` else `RootMismatch`.
    - R2. For each i, the node selected by the key's next nibble(s) must reference `keccak256(proof[i+1])` else `NodeHashMismatch { at: i }`.
    - R3. Inclusion: terminal leaf's value == `expected` (`Some`), `b""` is a valid value distinct from absence.
    - R4. Exclusion (`expected == None`): terminal node proves no leaf at key (branch missing the nibble, or leaf with different remaining key).
    - R5. TOTALITY: every RLP decode `?`-propagates into `ProofError::Rlp`; ZERO `unwrap`/`panic`/`[]` index without bounds.
    - R6. Happy path allocates nothing on the heap (borrow `proof` slices; no `to_vec`).
  - **Design walk-through** D1..D6 — `notes/32_proof_verify_design.md`, no peeking at `alloy-trie` until Phase 3:
    - D1. Decode-primitive table: `alloy_rlp::decode_exact` vs manual header parse — columns: returns Result? bounds-checked? trailing-byte handling? Choose for R5.
    - D2. Walk an inclusion verify for a depth-3 proof; show the nibble consumed at each step and the hash check.
    - D3. **Pre-mortem (load-bearing):** write the 5-line trace where a crafted `proof = [b"\xf8\xff"]` (length prefix claims 255 bytes but slice is 2) feeds a verifier that does `proof[0][2..]` → index-out-of-bounds panic → process abort. This is the DOS.
    - D4. Empty-value trace: key maps to `b""`. Show `expected = Some(b"")` must verify and `expected = None` must FAIL for the same proof — the two are distinct outcomes.
    - D5. Forged-proof trace: attacker swaps an intermediate node for one that hashes differently; show R2 catches it at `NodeHashMismatch { at }`.
    - D6. **Anti-shortcut audit:** the obvious reach is `node.decode().unwrap()` because "the proof comes from our generator" — wrong HERE because the verifier's whole job is to assume the input is hostile; `unwrap` is the bug.
  - **Output**: `notes/32_proof_verify_design.md` with R1..R6, D1..D6, the DOS trace, the empty-value trace.

**Wednesday — MPT delete with structural rebalancing**

- [ ] **Build**: `crates/eth-trie/src/delete.rs` — `Trie::delete(path)` with branch-collapse + extension-merge rebalancing. (~total 220 min across 3 phases)
  - 🔧 **Why this matters**: mirrors go-ethereum `trie/trie.go::{delete, deleteNode}` (and reth's trie mutation). Delete is the most error-prone MPT operation: removing a leaf can leave a branch with a single child, which MUST collapse into an extension/leaf, and adjacent extensions must merge — get it wrong and the root hash diverges from every other client (consensus split). This is where geth/reth historically had bugs. Three traps: (1) branch-with-value collapse data loss, (2) extension-of-extension non-merge, (3) empty-trie sentinel. First attempts diverge from the reference on collapse-heavy delete sequences. Downstream: W34 state pruning (prune = bulk delete), W42 txn rollback (undo emits deletes).

  #### Phase 1 — Problem, prediction, design (~50 min, no code yet)
  - 🎯 **Pre-prediction prompt** — `crates/eth-trie/notes/32_delete_prediction.md`:
    - P1: the return type you'd choose (`Result<Option<Bytes>, TrieError>` — prior value if existed).
    - P2: predict the root hash after `insert(a); insert(b); delete(b)` vs just `insert(a)` — equal or not? Why?
    - P3: predict what a branch with exactly ONE remaining child AND a value should collapse to.
    - P4: predict the root after deleting the LAST key (sentinel = ?).
    - P5 = list every Phase-2 test your first attempt will fail.

  #### Phase 3 — Make the tests pass, one failure at a time (~100 min)
  - **(NEWBIE) When `delete_then_reinsert_root_stable` reports `root0 != root1`:**
    - Symptom: deleting then re-inserting the same key gives a different root than never deleting.
    - Why: your delete left a non-canonical structure (e.g. a branch you should have collapsed); re-insert built on the canonical form, so the two roots diverge.
    - Fix: rebalance on unwind — collapse single-child branches (R2) so the structure is always canonical for a given key set.
    - Muscle: an MPT root is a function of the key SET, not the operation history — any path to the same set must yield the same root. Reapplies at: W34 prune (delete-heavy), W42 txn rollback root equality, W35 state-root determinism.
  - **(SENIOR) When `delete_collapses_branch_to_extension` leaves a 1-child branch:**
    - Symptom: after deleting a sibling, the branch still exists with one child; root diverges from reference.
    - Why: you removed the slot but never checked the post-delete child count to trigger collapse.
    - Fix: after recursion returns, if a value-less branch has exactly 1 child, replace it with that child and prepend the branch nibble to the child's key (R2).
    - Muscle: delete's real work is the UNWIND rebalance, not the descent. Reapplies at: W34 bulk-prune collapse, W42 rollback collapse.
  - **(SENIOR) When `delete_branch_with_value_preserves_value` loses `V`:**
    - Symptom: after deleting the child, `get("0x1")` returns `None` — the branch value vanished.
    - Why: you collapsed a branch-with-value as if it had only children, dropping the value.
    - Fix: a branch with value + 0 children collapses to a Leaf holding the value (R3); a branch with value + 1 child stays a branch (R1) — check `value.is_some()` before collapsing.
    - Muscle: a branch node can carry BOTH a value and children; collapse logic must preserve the value. Reapplies at: W34 prune of value-bearing branches, W42 rollback of partial subtrees.
  - **(EXPERT) When `delete_root_matches_geth_anyorder` diverges mid-sequence:**
    - Symptom: roots match for a while then diverge after a specific delete; legacy single-leaf deletes pass, collapse-heavy ones fail.
    - Why: extension-of-extension not merged (R4) — your collapse produced `Ext(0x1)->Ext(0x2)->Leaf` where the reference has `Ext(0x12)->Leaf`; same logical trie, different canonical form, different hash.
    - Fix: after any collapse that yields an extension whose child is an extension, merge their nibble prefixes recursively (R4).
    - Muscle: canonical MPT structure forbids adjacent extensions — merge on every collapse or the hash diverges. Reapplies at: W35 snapshot canonicalization, W42 rollback structural merge.
  - **(EXPERT) When `delete_then_prove_absence` fails to produce a verifiable absence proof:**
    - Symptom: delete's own tests pass, but proving absence of a deleted key fails (proof references a node that no longer exists, or a dangling node).
    - Why: delete left a structurally-wrong-but-same-hash artifact, or pruned a node still referenced — the proof walk hits a dead reference.
    - Fix: ensure delete removes orphaned nodes AND collapses canonically so every surviving path is provable (R1-R4); add the cross-crate assertion to CI.
    - Muscle: a mutation is correct only if the resulting trie is still PROVABLE end-to-end; cross-primitive tests catch the structural debt a local root check misses. Reapplies at: W35 snapshot prune+prove, W95 light-client post-mutation witnesses.
