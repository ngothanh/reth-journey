**Monday — Yellow Paper §4 + `Header` + concurrency drill #3**

- [ ] **Concurrency drill #3 of 28 — Dekker's two-flag mutual exclusion (Release-Acquire is NOT enough)** (solo,
  ~5 hrs). The drill that breaks the most-common student mistake: "Release+Acquire ≈ SeqCst, basically." It
  isn't, and you'll feel why.
  Build `crates/concurrent/src/dekker.rs` — two-thread Dekker's mutual exclusion using only two `AtomicBool`
  flags (no atomic counter, no fetch_add, no Mutex). Each thread sets its own flag, peeks at the other, decides
  whether to enter the critical section. Workload: 2 threads each entering the CS many times.
  Constraints: no peek at Mara Bos Ch 3 §3.5 (SeqCst), no peek at `std::sync::atomic::fence`, no peek at any
  Dekker's reference impl until COMPARE.
  - **Spec**: invariant "at most one thread inside CS at any time". Pick a shared counter inside the CS that
    only one thread should mutate at a time; predict the byte pattern observable if BOTH enter. Justify why
    you think Release on the set + Acquire on the peek will be enough (you will be wrong — write WHY you'd
    expect it to work; that's the lesson).
  - **Build**: implement with Release on each set, Acquire on each peek. Smoke-test single-thread.
  - **Loom**: 2-thread test asserting "shared counter incremented exactly N times across both threads" (no
    lost or double increments). It WILL fail. Now: ONE iteration only is allowed. Don't reach for SeqCst yet —
    first try `fence(SeqCst)` between the set and the peek on each side, and predict whether that's enough
    (it is — but understand why before measuring). Then try the SeqCst-store/load variant and reason about
    the difference in cost.
  - **Compare**: open Mara Bos Ch 3 §3.5 + `std::sync::atomic::fence` docs. Why is StoreLoad the only
    barrier that Release-Acquire don't provide? What hardware instruction does `fence(SeqCst)` emit on x86
    vs aarch64?
  - **Symptom card** (`notes/06_drill3_symptom.md`): the bug shape ("both threads observed the other's flag
    as still-false"); the rule (Release-Acquire pairs do NOT prevent StoreLoad reordering); reapplies at:
    W74 VSR quorum (two-flag-style ack counting), W83 ledger 2PC vote.

    consensus split.
  - *Contract*: `struct Header { parent_hash: B256, ommers_hash: B256, beneficiary: Address, state_root: B256,
    transactions_root: B256, receipts_root: B256, logs_bloom: Bloom, difficulty: U256, number: u64, gas_limit: u64,
    gas_used: u64, timestamp: u64, extra_data: Bytes, mix_hash: B256, nonce: B64, base_fee_per_gas: Option<u64>,
    withdrawals_root: Option<B256>, blob_gas_used: Option<u64>, excess_blob_gas: Option<u64>,

    RlpDecodable)]` from W5 Friday; add `fn hash_slow(&self) -> B256` = keccak of the RLP encoding.
  - **Expect to hit #1 — field declaration order is the wire format**: the derive emits fields in source order, so
    the post-Merge fields MUST follow the pre-Merge ones in exactly the canonical sequence. Symptom: no compile
    error — only `cast block --raw` mismatches and a wrong block hash.
    - Fix: copy the field order verbatim from `alloy_consensus::Header`; never sort or "tidy" it.
    - Muscle: in a derive-encoded consensus struct, field order IS the protocol. Reapplies at: W6 tx structs, W8
      Receipt, W13 `eth-consensus` deepening.
  - **Expect to hit #2 — optional trailing fields encoded as `None` placeholders**: pre-London headers have no
    `base_fee_per_gas`; encoding `None` as an empty string instead of omitting the field entirely. Symptom: a
    Frontier-era header gets a 16th list element and the hash mismatches every node.
    - Fix: trailing `Option` fields are *omitted* from the list when `None` — the list length itself signals which
      fork the header is from; only emit a field once any later field is `Some`.
    - Muscle: header optional fields are presence-by-omission, gated by hard-fork activation. Reapplies at: W7
      EIP-7685 requests_hash, W13 fork-aware decoding.
  - **Expect to hit #3 — `nonce` and `logs_bloom` width**: encoding `nonce` (an 8-byte `B64`) or the 256-byte
    `logs_bloom` as a minimal-length integer. Symptom: a header with a leading-zero nonce loses bytes; bloom
    round-trips short.
    - Fix: `nonce` is a fixed 8-byte string and `logs_bloom` a fixed 256-byte string — fixed-width byte arrays, NOT
      integers; only `number`/`gas_*`/`timestamp` are minimal big-endian.
    - Muscle: distinguish RLP integers (minimal) from fixed-width byte fields (no stripping). Reapplies at: W6 tx
      `chain_id`/`v` vs `r`/`s`, W8 receipt bloom.

    - Muscle: an absent address is the empty RLP string, distinct from the zero address. Reapplies at: W8 receipt

  - **Expect to hit #3 — `chain_id` optional on legacy, mandatory on typed**: pre-EIP-155 legacy txs have no

**Wednesday — EIP-1559 + EIP-4844 fee math + concurrency drill #4**

- [ ] **Concurrency drill #4 of 28 — RMW happens-before (`fetch_add` and the data it implies)** (solo, ~5 hrs).
  Most people think "`fetch_add` is atomic so it's safe." The interesting question is what it does for
  *associated data* written before the RMW.
  Build `crates/concurrent/src/seq_counter.rs` — a `SeqCounter { next: AtomicU64 }` that issues monotonic IDs
  to a writer who then publishes an associated piece of data (e.g. a slot in a side array). Multiple writers
  call `claim() -> u64` (the RMW), then write `data[id % N] = payload`. A reader does the inverse: reads the
  counter, then reads data at the same index. The question: which Ordering on the RMW makes the reader see
  the writer's payload-write?
  Constraints: no peek at `crossbeam_utils::Backoff`, `std::sync::atomic::fetch_*` docs beyond signatures,
  or the W4 chain_head SeqLock until COMPARE.
  - **Spec**: invariant "reader who observes counter ≥ N has visibility into data[i] for all i < N". Predict
    what `fetch_add(1, Relaxed)` provides vs `fetch_add(1, AcqRel)`. Pick a multi-field payload type.
  - **Build**: implement with `fetch_add(1, Relaxed)` on the claim and `Relaxed` on the data store and counter
    read. Smoke-test single-thread.
  - **Loom**: 2-writer + 1-reader test where reader observes counter == 2 and asserts both slots have correct
    payloads. The naive impl fails. Iterate ONE change at a time, max 3 attempts. Key question to answer in
    your notes: is `AcqRel` on the RMW + `Acquire` on the reader's counter load sufficient, or do you need
    a `Release` fence between the data store and the next RMW?
  - **Compare**: open `std::sync::atomic` docs on `fetch_add` ordering semantics; open the Disruptor blog
    post on "Publishing via the cursor." Note: a RMW with AcqRel has the unique property that its `Release`
    half publishes ALL prior stores, not just stores to the same atomic. Why does that matter for this drill?
  - **Symptom card**: the bug; the rule ("a RMW with AcqRel synchronizes with a load-Acquire on the same
    atomic + makes all prior stores visible"); reapplies at: W4 Backoff seq, W11 MPMC seq, W26 WAL
    write_offset, W77 aeron tail_offset.



- [ ] Read EIP-1559 + EIP-4844 specs. (~60 min)
- [ ] **Build**: `crates/eth-consensus/src/eip1559.rs` — calc_next_block_base_fee. (~150 min)
  - *Mental model*: EIP-1559 makes the base fee a deterministic function of the *parent* block — if the parent
    used more than the gas target, the base fee rises; less, it falls; exactly target, it holds. Every node must
    compute the identical `u64` or the chain forks.
  - *Contract*: `fn calc_next_block_base_fee(parent_gas_used: u64, parent_gas_limit: u64, parent_base_fee: u64,
    base_fee_params: BaseFeeParams) -> u64` where `BaseFeeParams { max_change_denominator: u64, elasticity_multiplier:
    u64 }` (8 and 2 on mainnet). Gas target = `parent_gas_limit / elasticity_multiplier`.
  - *calc, roughly*: (1) gas_target = limit / elasticity; (2) if used == target, return parent_base_fee unchanged;
    (3) if used > target, delta = `max(parent_base_fee * (used - target) / target / max_change_denominator, 1)`,
    return parent + delta; (4) if used < target, delta = `parent_base_fee * (target - used) / target /
    max_change_denominator`, return parent - delta. The intermediate `parent_base_fee * gas_delta` product is the
    real exercise — it overflows `u64`.
  - **Expect to hit #1 — the `base_fee * gas_delta` product overflows u64**: `parent_base_fee` (up to ~10^12) times
    `gas_used_delta` (up to ~10^7) is ~10^19 — larger than `u64::MAX` (~1.8×10^19) at the extremes. Symptom: debug
    build panics `attempt to multiply with overflow`; release build silently wraps to a tiny base fee — instant
    consensus split.
    - Fix: do the numerator in `u128` (or `U256`), divide back down, then narrow to `u64`.
    - Muscle: any `a * b` of two protocol-sized values needs a wider intermediate type. Reapplies at: W6 EIP-4844
      blob fee, W8 receipt cumulative gas, W9 exec-vm gas metering.
  - **Expect to hit #2 — truncating division drops the delta or rounds the wrong way**: integer division floors,
    so for a *rising* base fee a small overage can floor the delta to 0 — but the spec mandates a minimum increase
    of 1 wei; meanwhile the *falling* case must also floor (never round up). Symptom: base fee gets stuck and never
    rises under light-but-positive load; or it falls too slowly.
    - Fix: increase path applies `max(computed_delta, 1)`; decrease path uses plain floor division with no `max`.
    - Muscle: rounding direction is asymmetric and spec-defined — increases floor-then-`max(.,1)`, decreases floor.
      Reapplies at: W6 EIP-4844 excess blob gas, W17 gas refund math.
  - **Expect to hit #3 — the `used == target` branch and divide-by-zero**: folding the equal case into the
    increase/decrease branches, or computing `gas_target` as 0 when `gas_limit` is tiny then dividing by it.
    Symptom: an off-by-one drift on target-exactly blocks, or a panic on a degenerate genesis/test config.
    - Fix: handle `used == target` as an explicit early return of `parent_base_fee`; guard `gas_target == 0`.
    - Muscle: a piecewise formula needs every branch — including the boundary and the degenerate input — handled
      explicitly. Reapplies at: W6 EIP-4844 fee branches, W13 fork-transition base fee.
- [ ] **Build**: `crates/eth-consensus/src/eip4844.rs` — calc_excess_blob_gas, calc_blob_fee. (~150 min)
  - *Mental model*: EIP-4844 runs a second, independent fee market for blob data. `excess_blob_gas` is a running
    counter (carried in the header) of how much blob gas has been consumed *above* target across history; the blob
    base fee is an exponential function of that excess. Like base fee, every node must agree to the wei.
  - *Contract*: `fn calc_excess_blob_gas(parent_excess_blob_gas: u64, parent_blob_gas_used: u64) -> u64` and
    `fn calc_blob_fee(excess_blob_gas: u64) -> u128`. Constants: `TARGET_BLOB_GAS_PER_BLOCK` (393216 =
    3 blobs × 131072), `MIN_BLOB_BASE_FEE` (1), `BLOB_BASE_FEE_UPDATE_FRACTION` (3338477). Blob fee =
    `fake_exponential(MIN_BLOB_BASE_FEE, excess_blob_gas, BLOB_BASE_FEE_UPDATE_FRACTION)`.
  - *fake_exponential, roughly*: approximate `factor * e^(numerator/denominator)` via a Taylor series — (1) `i = 1`,
    `output = 0`, `accum = factor * denominator`; (2) loop: `output += accum`, `accum = accum * numerator /
    (denominator * i)`, `i += 1`, until `accum == 0`; (3) return `output / denominator`. Keeping every intermediate
    from overflowing is the real exercise.
  - **Expect to hit #1 — `calc_excess_blob_gas` underflow on the subtraction**: the update is
    `parent_excess + parent_used - TARGET`, but if `parent_excess + parent_used < TARGET` the `- TARGET` underflows
    `u64`. Symptom: debug panic `attempt to subtract with overflow`; release wraps to ~1.8×10^19 and the blob fee
    explodes to astronomical values — consensus split.
    - Fix: `saturating_sub` — `(parent_excess + parent_used).saturating_sub(TARGET_BLOB_GAS_PER_BLOCK)`; excess
      blob gas floors at 0.
    - Muscle: a counter that "tracks the surplus" must saturate at zero, never wrap. Reapplies at: W6 EIP-1559
      base-fee decrease, W8 receipt gas accounting.
  - **Expect to hit #2 — `fake_exponential` accumulator overflows mid-series**: `accum = accum * numerator` grows
    enormously before the `/ denominator` brings it back down; in `u64` it wraps and the series diverges. Symptom:
    blob fee jumps to a wrong value or panics only for large `excess_blob_gas` — small inputs look fine, so it
    passes naive tests.
    - Fix: run the whole accumulator and `output` in `U256` (or at least `u128`); only the final result narrows.
    - Muscle: an iterative product-then-divide needs a wide accumulator for the *intermediate*, not just the
      result. Reapplies at: W6 EIP-1559 product, W9 exec-vm `EXP` opcode.
  - **Expect to hit #3 — wrong loop termination / off-by-one on the series**: terminating on a fixed iteration
    count, or on `output` no longer changing instead of on `accum == 0`. Symptom: the approximation differs from
    Geth by a few wei at certain `excess_blob_gas` values — passes round-trip tests, fails cross-client fixtures.
    - Fix: loop *exactly* until `accum` reaches 0 by integer division; the term order (`output += accum` before
      updating `accum`) must match the spec pseudocode line-for-line.
    - Muscle: a consensus approximation is defined by its exact algorithm, not its mathematical limit — copy the
      pseudocode literally. Reapplies at: W13 fork fee transitions, W49 revm fee comparison.
  - **Expect to hit #4 — `MIN_BLOB_BASE_FEE` floor dropped**: returning the raw `fake_exponential` output, which
    for `excess_blob_gas == 0` would be 0. Symptom: a quiet blob market reports a 0 blob base fee instead of 1.
    - Fix: `fake_exponential` already starts from `factor = MIN_BLOB_BASE_FEE = 1`, so the first series term yields
      the floor — verify it never returns below 1.
    - Muscle: every fee market has a hard minimum baked into the formula's starting factor. Reapplies at: W6
      EIP-1559 minimum delta, W13 fee floors.

- [ ] **Build**: `crates/time/src/monotonic.rs` — `Monotonic(u64)` newtype over
  `std::time::Instant::elapsed_since_anchor`. Anchor set once at process start. `now() -> Monotonic` is the universal
  monotonic source for the entire workspace from this week forward. (~75 min)
  - *Mental model*: a cheap, copyable monotonic timestamp — nanoseconds elapsed since a process-start anchor — that
    can never go backwards even if the wall clock is adjusted. It's the clock for timeouts, rate limiters, and
    latency measurement everywhere downstream.
  - *Contract*: `struct Monotonic(u64)` (nanos since anchor); `fn now() -> Monotonic`; a one-time anchor
    `Instant` set lazily; `impl Sub for Monotonic -> Duration` and ordering derives.
  - *Back-of-envelope*: this is the universal clock — every timeout, rate-limiter poll, latency measurement,
    metric, and event stamp in the workspace calls it. **~1 M+ calls/sec on a busy node.** Cost: on Linux,
    `Instant::now()` → vDSO `clock_gettime(CLOCK_MONOTONIC)` ≈ ~25 ns. On Apple Silicon (your dev machine),
    `mach_absolute_time` ≈ ~5 ns. Both avoid a full syscall (~300 ns) via the kernel's vDSO/commpage fast
    path. Target: **`Monotonic::now()` compiles to a single vDSO call + one subtract** — no extra logic, no
    allocations, no synchronization beyond a relaxed anchor load (~1 ns).
  - **Expect to hit #1 — the anchor is re-initialized per call**: computing `Instant::now()` as the anchor inside
    `now()` itself, so every reading is ~0. Symptom: every `Monotonic` value is near-zero; durations between two
    `now()` calls are nonsense.
    - Fix: store the anchor in a `OnceLock<Instant>` (or `LazyLock`) set exactly once at first use.
    - Muscle: a "time since process start" anchor must be captured once and shared. Reapplies at: W11
      `backpressure`, W58 timer wheel epoch.
  - **Expect to hit #2 — using `SystemTime` instead of `Instant`**: backing the clock with `SystemTime` so it
    tracks wall time. Symptom: a clock adjustment (NTP step, manual change) makes `now()` jump or go backwards,
    breaking every timeout that assumed monotonicity.
    - Fix: back `Monotonic` with `std::time::Instant`, which is guaranteed non-decreasing.
    - Muscle: monotonic and wall-clock are different clocks — timeouts and rate math use monotonic only. Reapplies
      at: W6 HLC wall component, W26 `wal` fsync timing, W58 runtime timers.
  - **Expect to hit (perf) #1 — `Instant::now()` falling off the vDSO fast path (bar (c) violation)**: on a
    misconfigured container or unusual platform, `clock_gettime` takes the kernel-trap path (~300 ns) instead
    of vDSO's ~25 ns — a **12× regression on the universal clock** that the entire workspace calls. Symptom:
    `cargo flamegraph` shows `_clock_gettime` / `syscall` time inside `now()`; p99 latency inflates uniformly
    across every component that timestamps anything.
    - Fix: verify on each target platform that vDSO is being used (`strace -c -e trace=clock_gettime` should
      show ~0 calls under normal load on Linux). On Linux containers, ensure `CLOCK_MONOTONIC` is in the
      vDSO whitelist. On bare-metal HFT setups (W58+), pin to a kernel that exposes the fast clock; document
      in `DESIGN.md`.
    - Cost avoided: ~275 ns per `now()` (12× speedup); at 1 M `now()`/sec that's ~275 ms/sec of
      otherwise-invisible kernel time recovered.
    - Muscle: the universal clock is on every hot path — its fast-path must be verified per target, never
      assumed. Reapplies at: W58 matching-engine event timestamps, W76 messaging-aeron message timestamps,
      W80 ledger apply timestamps.
- [ ] **Build**: `crates/time/src/lamport.rs` — `LamportClock { counter: AtomicU64 }`. `tick() -> u64` increments +
  returns. `observe(other: u64)` sets counter to max(self+1, other+1). (~75 min)
  - *Mental model*: a Lamport logical clock — a shared `AtomicU64` that gives a *causal* ordering of events across
    threads (and later nodes). `tick()` stamps a local event; `observe()` merges in a timestamp seen on an
    incoming message so causality is preserved.
  - *Contract*: `struct LamportClock { counter: AtomicU64 }`; `fn tick(&self) -> u64` — atomically increment and
    return the new value; `fn observe(&self, other: u64) -> u64` — advance the counter to `max(current, other) + 1`
    and return it.
  - *observe, roughly*: (1) load current; (2) compute `new = max(current, other) + 1`; (3) install `new` only if
    the counter hasn't changed under you; (4) on failure, retry from (1). Step 3 — the compare-and-swap loop — is
    the real exercise.
  - *Back-of-envelope*: `tick()` is called on every causally-ordered event — in a deterministic SM (W80
    ledger) that's every transaction, 100 k - 1 M /sec. Cost: `fetch_add(1, AcqRel)` ≈ ~10 ns uncontended,
    scales to ~100+ ns under heavy single-line contention. Target: single `fetch_add`, no CAS loop, no
    allocation. `observe()` is rarer (cross-thread / cross-node message receipt) — CAS loop is acceptable
    there. Hot intra-process events use `tick`; only inbound boundaries call `observe`.
  - **Expect to hit #1 — `observe` as load-then-store races**: implementing `observe` as a plain `load()` then
    `store()`. Symptom: two threads both read counter=5, both store 9, one increment is lost — the clock goes
    *backwards* relative to an event it already issued, breaking total order.
    - Fix: a `compare_exchange_weak` CAS loop — recompute `max(.)+1` from the freshly observed value each retry.
    - Muscle: read-modify-write on shared state is a CAS loop, never load-then-store. Reapplies at: W6 HLC update,
      W42 `txn` distributed ordering, W56 `consensus-raft` term updates.
  - **Expect to hit #2 — `Relaxed` ordering loses the happens-before edge**: using `Ordering::Relaxed` on
    `tick`/`observe`, so a Lamport stamp is visible before the data the event produced. Symptom: a reader sees a
    higher timestamp than the payload it's supposed to order — the clock no longer reflects causality.
    - Fix: use `AcqRel` on the CAS (`Acquire` on the load side, `Release` on the store side) so the timestamp
      publishes a happens-before edge with the event's data.
    - Muscle: a logical clock's ordering only means something if its memory ordering carries the data with it.
      Reapplies at: W6 HLC, W42 `txn`, W56 raft log ordering.
  - **Expect to hit #3 — `fetch_add` overflow / non-strict monotonicity**: assuming a `u64` counter can't wrap, or
    a `tick` that returns the value *before* incrementing so two events share a stamp. Symptom: in a long-running
    soak two distinct events get the same Lamport time; total order collapses to a partial order.
    - Fix: `tick` returns the *post-increment* value (`fetch_add(1, ..) + 1`); document that `u64` exhaustion is
      effectively unreachable but the API is "strictly increasing per call."
    - Muscle: a clock used for total order must hand out a strictly unique, increasing value every call. Reapplies
      at: W42 `txn` MVCC versions, W65 Disruptor sequence.
  - **Expect to hit #4 — `observe` not idempotent under equal input**: `observe(other)` where `other <= current`
    still bumps the counter, so merely *seeing* an old timestamp inflates the clock. Symptom: the clock drifts
    upward from redundant message receipts; gaps in stamps grow unboundedly.
    - Fix: `new = max(current, other) + 1` already handles this — but verify `observe(small_old_value)` still only
      advances by the local `+1`, never by `other`.
    - Muscle: clock-merge is `max` then a single local increment — receiving stale time must not over-advance.
      Reapplies at: W6 HLC merge, W42 `txn` timestamp gossip.
  - **Expect to hit (perf) #1 — CAS contention storm under N writers (bar (c) violation)**: `observe()` uses
    `compare_exchange` in a loop. With N threads observing simultaneously (a multi-shard runtime where every
    shard stamps incoming messages from any other shard), CAS retries scale as **O(N²)** on the hot cache
    line — at 16 threads, throughput collapses to ~1/16 of single-threaded. Symptom: criterion `tick`/`observe`
    bench shows throughput peaking at ~2 threads then degrading.
    - Fix: for known multi-writer workloads, use `fetch_max` (single atomic op, no retry loop) instead of CAS,
      OR shard the clock per writer (per-core Lamport counters reconciled at message boundaries — the
      runtime-thread-per-core pattern, W30+).
    - Cost avoided: linear vs quadratic-with-N degradation; ~10 ns per op vs ~100+ ns under 16-way contention.
    - Muscle: any hot atomic on a single cache line scales as O(N²) under contention; find a single-op
      primitive (`fetch_max`, `fetch_add`) or shard the state. Reapplies at: W11 MPMC head/tail (sharded by
      `CachePadded`), W42 `txn` version counter, W76 aeron flow control credit.

  - *Mental model*: a Hybrid Logical Clock combines a physical wall-clock reading with a Lamport-style logical
    counter — timestamps stay close to real time *and* preserve causality even when wall clocks are slightly
    skewed. This week is a stub; the full causal-update path lands at W42.
  - *Contract*: `struct HybridLogicalClock { wall: AtomicU64, logical: AtomicU64 }`; `struct Hlc { ms_since_epoch:
    u64, logical: u64 }` (Copy, Ord); `fn now(&self) -> Hlc`. `Hlc` orders lexically — wall first, then logical.
  - *now, roughly*: (1) read physical wall time in ms; (2) load the stored `(wall, logical)`; (3) if physical >
    stored wall, the new stamp is `(physical, 0)`; else it's `(stored wall, stored logical + 1)`; (4) CAS the pair
    back. Doing (4) as one atomic update of *both* fields is the real exercise.
  - *Back-of-envelope*: HLC `now()` ≈ wall-clock read (~25 ns vDSO) + one CAS on the packed atomic (~10 ns
    uncontended) ≈ **~35-50 ns**. Compare to Lamport `tick()` ≈ 10 ns. **HLC is 3-5× the cost of Lamport** —
    that's the price of cross-node causal+physical ordering. Use HLC only where you need both: cross-node
    message stamping (W42 `txn` distributed), state-machine snapshots that must order across replicas
    (W80+ ledger). Hot intra-process paths use Lamport or pure Monotonic.

    separate atomics. Symptom: a concurrent reader observes a torn pair — a new `wall` with a stale `logical` — and
    two events compare equal or out of order; non-deterministic, rare, brutal to debug.
    - Fix: pack `(wall_ms, logical)` into a single `u64` (e.g. 48 bits wall + 16 bits logical) or one `AtomicU64`
      holding the encoded pair, and CAS that one word.
    - Muscle: a multi-field value that must update atomically is one atomic word, not several. Reapplies at: W42
      `txn` HLC full impl, W4 `AtomicCell`, W76 `consensus-vsr` view+op pair.
  - **Expect to hit #2 — physical clock goes backwards and the logical part doesn't absorb it**: NTP steps the
    wall clock back; `now()` sees `physical < stored_wall` but the code still trusts `physical`. Symptom: HLC
    timestamps go backwards across an NTP correction — the one thing an HLC exists to prevent.
    - Fix: when `physical <= stored_wall`, keep `stored_wall` and increment `logical`; the logical counter is what
      absorbs backward wall jumps.
    - Muscle: an HLC's logical field exists precisely to mask physical-clock regressions — never bypass it.
      Reapplies at: W42 `txn` cross-node ordering, W56 raft leader timestamps.
  - **Expect to hit #3 — `now()` not strictly monotonic on a single node**: two `now()` calls within the same
    millisecond return the *same* `Hlc` because the logical part wasn't bumped on equal-wall. Symptom: two local
    events get an identical HLC; they can't be totally ordered.
    - Fix: equal-wall path always returns `logical + 1`; only a strictly-greater physical reading resets logical to
      0.
    - Muscle: even a hybrid clock must guarantee strict local monotonicity per call. Reapplies at: W42 `txn`
      version stamps, W6 Lamport `tick`.
  - **Expect to hit (perf) #1 — HLC on every hot-path event where Lamport would suffice (bar (c) violation)**:
    a hot loop stamps every event with HLC despite only needing local causal order. Symptom: `cargo flamegraph`
    shows `clock_gettime` taking ~10% of CPU; the wall-clock read is dwarfing every actual unit of work.
    - Fix: tier clocks by use site — Lamport for intra-process events, HLC only at cross-node boundaries
      (inter-node send/receive). Build an explicit "boundary" abstraction so the tier choice is at the call
      site, not the type.
    - Cost avoided: ~25-40 ns per stamp event vs Lamport's ~10 ns; at 1 M events/sec ≈ ~30 ms/sec of CPU
      reclaimed for actual work.
    - Muscle: pick the cheapest clock that meets the semantic need — Monotonic for durations, Lamport for
      in-process causality, HLC for cross-node, wall-clock only for human-facing display. Reapplies at: W42
      `txn` boundary clock choice, W76 aeron message stamping, W80 ledger event order.
