- [ ] **Concurrency drill #3 of 28 — Dekker's two-flag mutual exclusion (Release-Acquire is NOT enough)** (solo,
  ~5 hrs). The drill that breaks the most-common student mistake: "Release+Acquire ≈ SeqCst, basically." It
  isn't, and you'll feel why.
  Build `crates/concurrent/src/dekker.rs` — two-thread Dekker's mutual exclusion using only two `AtomicBool`
  flags (no atomic counter, no fetch_add, no Mutex). Each thread sets its own flag, peeks at the other, decides
  whether to enter the critical section. Workload: 2 threads each entering the CS many times.
  Constraints: no peek at Mara Bos Ch 3 §3.5 (SeqCst), no peek at `std::sync::atomic::fence`, no peek at any
  Dekker's reference impl until COMPARE.
  - **Spec**: invariant "at most one thread inside CS at any time". Pick a shared counter inside the CS that
    only one thread should mutate at a time; predict the byte pattern observable if BOTH enter. Justify why
    you think Release on the set + Acquire on the peek will be enough (you will be wrong — write WHY you'd
    expect it to work; that's the lesson).
  - **Build**: implement with Release on each set, Acquire on each peek. Smoke-test single-thread.
  - **Loom**: 2-thread test asserting "shared counter incremented exactly N times across both threads" (no
    lost or double increments). It WILL fail. Now: ONE iteration only is allowed. Don't reach for SeqCst yet —
    first try `fence(SeqCst)` between the set and the peek on each side, and predict whether that's enough
    (it is — but understand why before measuring). Then try the SeqCst-store/load variant and reason about
    the difference in cost.
  - **Compare**: open Mara Bos Ch 3 §3.5 + `std::sync::atomic::fence` docs. Why is StoreLoad the only
    barrier that Release-Acquire don't provide? What hardware instruction does `fence(SeqCst)` emit on x86
    vs aarch64?
  - **Symptom card** (`notes/06_drill3_symptom.md`): the bug shape ("both threads observed the other's flag
    as still-false"); the rule (Release-Acquire pairs do NOT prevent StoreLoad reordering); reapplies at:
    W74 VSR quorum (two-flag-style ack counting), W83 ledger 2PC vote.
  - **Numbers**: predict the per-CS cost difference: Release-Acquire (~0 ns x86, ~5 ns aarch64) vs
    `fence(SeqCst)` (~10-20 ns x86 `MFENCE`, ~20-30 ns aarch64 `DMB ish`) vs SeqCst load/store (slightly
    more — full fence on both). Measure with 2 threads doing 1M CS-enters each. Within 30% or explain.
  - **5-year failure mode**: SC fence cost rises with cross-NUMA / many-socket designs (current 1-socket =
    fast MFENCE; 2-socket NUMA = ~3× cost). Trigger: deployment moves to 2-socket. Fix: redesign to avoid
    SC entirely via single-writer ownership (drill #14's sharding) or per-shard locks.
  - **Production handoff**: the SC-required two-flag pattern lands at W74 VSR quorum-ack counting (every
    Prepare/PrepareOk involves a "did N replicas ack?" check that's structurally Dekker-shaped) and W83
    ledger 2PC vote. You'll learn to AVOID SC by restructuring — e.g. per-replica ack slots indexed by

  #### Phase 1 — Problem, requirements, design (~60 min, no code yet)

  - **The problem this primitive solves**: each Ethereum hard fork added fields to Header (London → base_fee,
    Shanghai → withdrawals_root, Cancun → blob fields + beacon_root, Prague → requests_hash). The on-wire encoding
    is a single RLP list whose **length signals which fork the header is from**. Optional fields are
    presence-by-omission, not None-as-placeholder. The struct must round-trip every mainnet block from genesis to
    Prague, byte-for-byte.

    - R5. `difficulty: U256` is an RLP integer (minimal). Post-Merge this is always 0 (encoded as empty string).
    - R6. `fn hash_slow(&self) -> B256` returns keccak256 of the RLP encoding of the Header.

  - **When `header_nonce_is_fixed_8_bytes` produces `[0x80]` for a zero nonce:**
    - Symptom: the nonce field encodes as empty string (minimal-stripped zero). Block hash mismatches every
      genesis-era block.
    - Why: you let the derive treat `B64` as a `u64` (minimal-stripped integer). `B64` is a fixed 8-byte
      string — like B256 — never an integer.

      `Bloom` (256 bytes) and `mix_hash` (32 bytes).

  #### Phase 1 — Problem, requirements, design (~30 min, no code yet)

  - **The problem this primitive solves**: in a distributed/concurrent system, events occur on different
    threads/nodes. A Lamport clock gives a partial-to-total causal order: every local event ticks the
    counter; receiving a message from another logical clock `observes` it (counter = max(self, other) + 1).
    The resulting stamps respect happens-before: if event A causally precedes B, A's stamp < B's stamp.

  - **Requirements** — write in `crates/time/notes/06_lamport_design.md`:
    - R1. `struct LamportClock { counter: AtomicU64 }`.
    - R2. `fn tick(&self) -> u64` atomically increments and returns the new value. Single `fetch_add(1,
      AcqRel) + 1`. No CAS loop.
    - R3. `fn observe(&self, other: u64) -> u64` advances counter to `max(current, other) + 1` and returns
      it. CAS loop OR `fetch_max(other, AcqRel)` followed by `fetch_add(1, AcqRel) + 1`.
    - R4. Memory ordering is `AcqRel` on every op — the stamp must publish a happens-before edge with the
      event's data; bare `Relaxed` breaks causality.
    - R5. `tick` returns the POST-increment value (strictly unique per call).
    - R6. `observe(old_value)` where `old_value <= current` still advances by only `+1` (no over-bump).
    - R7. Under N-writer contention, `observe` uses `fetch_max` (O(N) total) instead of CAS loop (O(N²)).

  - **Design walk-through** — answer each:

      `Acquire` on the read side guarantee for the data published before the producer's `Release`?
    - D2. Walk through `observe(other)` as a CAS loop: 4-step pseudocode. Now walk through the
      `fetch_max(other, AcqRel)` + `fetch_add(1, AcqRel) + 1` version. Why is the 2nd version `fetch_max`

    - D4. CAS contention storm: N=16 threads each calling `observe`. Why does CAS-loop scale O(N²)? Why

  - 🔧 **Why this matters**: every tx in mempool, every tx in a block, every RPC response carries `Signed<Tx>`.

    protection check uses it. Computing it over the wrong bytes (unsigned vs signed; with vs without type byte;

  #### Phase 1 — Problem, requirements, design (~50 min, no code yet)

  - **The problem this primitive solves**: a transaction's identity is its hash, but it has TWO hashes — the
    SIGNING hash (keccak of unsigned encoding; what the signer signed) and the TRANSACTION hash (keccak of full
    signed encoding; what mempool/RPC use as identity). Computing them with the same code path silently
    conflates them; the difference is a few bytes (the signature) but mainnet rejects mismatches. Hash must
    be cached (computing keccak over 200-byte encoded form is ~1 µs; every RPC and mempool lookup needs it).

  - **Requirements** — write in `crates/eth-consensus/notes/06_signed_design.md`:
    - R1. `struct Signed<T> { tx: T, signature: Signature, hash: OnceLock<B256> }`.
    - R2. `fn signing_hash(&self) -> B256` — keccak of unsigned encoding (type byte + RLP of tx fields, no
      signature).
    - R3. `fn hash(&self) -> B256` — keccak of FULL signed EIP-2718 encoding (type byte + RLP of tx fields +
      signature fields). Cached in `OnceLock`.
    - R4. `fn recover_signer(&self) -> Result<Address, RecoveryError>` — ECDSA recover using `signing_hash`
      + signature.
    - R5. `Signed<T>` is IMMUTABLE after construction. No `&mut T` accessor; mutation = consume + re-sign.
    - R6. Signature parity normalized to `y_parity: bool` internally; convert to legacy `v` (27/28 or
      EIP-155 `chain_id*2+35/36`) only at legacy-tx encode time.
    - R7. Encoding emits EIP-2718 typed envelope when `T: TxType::is_typed()`, bare RLP for legacy.
    - R8. Hash matches `cast tx <hash> --json | jq .hash` for ≥3 mainnet txs (one per type).

  - **Design walk-through** — answer each:
    - D1. Walk through the encoding for a 1559 tx hash: what bytes are hashed? (Hint: `0x02 || rlp([chain_id,
      nonce, …, value, data, access_list, y_parity, r, s])`.)
    - D2. Walk through the signing hash for the SAME tx: what bytes are hashed? (Hint: same as D1 but
      without `y_parity, r, s`.) Show the byte-level difference.
    - D3. Legacy v vs typed y_parity: EIP-155 v = `chain_id * 2 + 35 + y_parity`. Walk through `v = 38`

      tx_mut(&mut self) -> &mut T`? (Hint: API design + doc + lint.)
    - D5. Hash domain separation: typed txs use type-byte-prefix-keccak; legacy uses bare-RLP-keccak. Two
      domains. What ensures you never mix them? (Hint: the encode function dispatches on tx type.)
    - D6. recover_signer: ECDSA-recover takes `(message_hash, signature) -> public_key`; derive address
