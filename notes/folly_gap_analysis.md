# folly gap analysis — what is in folly and not in PRODUCT_TREE

Six parallel source reads (2026-10-03): five agents over folly's subsystems, each having
read `plan/PRODUCT_TREE.md` in full first, plus one completeness critic whose job was to
delete false positives rather than add to the list.

**Raw: 50 candidate gaps. After the critic: 12 false positives removed, and the list was
inflated by multiple-counting — FlatCombining reported 3x, wake-economy 3x,
CacheLocality 2x. ~24 distinct techniques survive.**

A gap is only listed if folly has a *technique* the plan does not cover under any name.
folly's `Baton` is not a gap because the plan has `Parker`. Each is marked core / borrow /
arguable by the plan's own §0 rule, and add-to-plan / note-only / skip.

FALSE POSITIVES in the candidate list — drop these.

1. [synchronization] SanitizeThread.h / TSAN annotations — FP. The plan's toolchain is Miri + loom + proptest (§5); Rust's ThreadSanitizer is nightly-only, has no stable annotate_rwlock_acquired/annotate_benign_race equivalent, and does not do lock-order analysis on custom primitives, so there is nothing to build and no number changes. The transferable half ("declare the deliberate race, don't suppress the file") is already how the plan uses Miri.
2. [memory-containers] Hint.h compiler_must_not_predict — FP. Rust's `black_box` is an opaque identity function and already does BOTH jobs in one primitive: on an input it defeats constant-folding and branch-shape specialization, on an output it defeats elision. folly needs two only because doNotOptimizeAway is consume-only. The residual content (feeding one input N times measures a warm predictor, so the p99 is fiction) is benchmark methodology already owned by latency-lab's coordinated-omission work — one note line, not a work item. plan/ already uses black_box in 31 files.
3. [stats-experimental] TDigest / DigestBuilder / QuantileEstimator — FP. §5 borrows hdrhistogram and states the reason ("log-linear bucketing is a real data structure, but it is not on the critical path"); hdrhistogram is also mergeable across shards, which is the property the candidate leans on. The genuine differentiator — relative error at p99.9 with ~100 centroids — changes no P4/P5 claim, because those claims are p99/p99.9 at microsecond resolution where HDR is exact. The per-CPU buffering + try_lock-then-reselect-stripe half is already the CacheLocality candidate.
4. [stats-experimental] IsAvalanchingHasher + mix64 finalizers — FP. The defect it fixes is C++-specific (std::hash<uint64_t> being the conforming identity). Rust's Hash/Hasher split forces an explicit hasher choice, the plan's keys are already-avalanched 32-byte keccak digests or dense integer ids, and reference/W089 already mandates a splitmix64 finalizer — for determinism, which is the stronger reason.
5. [synchronization] MicroLock / PicoSpinLock (sub-byte locks) — FP, and the candidate contains its own refutation: folly's numbers say the smallest lock is SLOWER uncontended than std::mutex (27.06 vs 25.18 ns) and worse contended. The only forcing reason is a byte budget, and the plan's byte-budget sites (B+tree page header, order struct) all have room for a 4-byte latch. **folly/synchronization/EventCount.h (Vyukov eventcount; also the value-or-waiterlist union in folly/synchronization/LifoSem.h LifoSemHead)**  
`add-to-plan` · `core` · ~12 h

- **Technique:** Lock-free blocking handoff: pack {epoch | waiter-count} into one 64-bit word so the producer's notify is a single fetch_add that issues no syscall and takes no lock when nobody is parked, and the waiter closes the lost-wakeup window with a publish-then-recheck protocol (prepareWait -> test condition -> cancelWait | wait(key)) instead of a mutex. Guarantee to prove: if prepareWait returns before notifyAll, the subsequent wait must complete.
- **Forced by:** Every lock-free structure eventually needs to block, and the naive answer (mutex + condvar) puts a lock acquisition back on the producer's hot path — destroying the lock-freedom the structure was built for. folly's doNotify is `val_.fetch_add(kAddEpoch, acq_rel)` and only calls futexWake `if (prev & kWaiterMask)`; the no-waiters case is one uncontended RMW. The epoch exists because a plain flag cannot distinguish "nothing happened" from "something happened and was consumed".
- **Plan has:** Closest: `Parker`/`Unparker` (crates/concurrent/src/parker.rs) and `Condvar`. Parker is a 1:1 thread handoff — it cannot express "N consumers parked on one ring, wake exactly one". Condvar requires the mutex. The plan's third option, `WaitList` + `Mutex<State>`, is what `Semaphore::add_permits` uses (crates/concurrent/src/semaphore.rs:166) and it takes the mutex unconditionally even when the waiter list is empty. W011.md R4/D5 specifies the blocking design for the MPMC ring as "Backoff ladder -> Parker" and test `mpmc_recv_on_empty_blocks_via_parker`, which works for 1 consumer and quietly has no answer for N. So the plan has three wait primitives and none with the property that matters: notify costs one fetch_add and zero syscalls when idle.
- **Consumers:** P4 hot path — PRODUCT_TREE §2 P4 v1 puts SPSC/MPMC rings between pipeline stages; an idle downstream stage must park without burning a core, and notify sits on every push at ~1M msg/s. `runtime-thread-per-core` idle-worker park (P4 v1, P5). `concurrent` channel + select, still unwritten (§9). `backpressure::BoundedBuffer` (P3/P4/P5). Setup-path only for P1/P2.

**folly/synchronization/ThrottledLifoSem.h (and StripedThrottledLifoSem.h for the stripe-affinity variant)**  
`add-to-plan` · `core` · ~18 h

- **Technique:** Wake-rate throttling: rate-limit wakeups rather than issuing one per posted item. At most one sleeping waiter is in a distinguished `waking` state; when woken it immediately re-sleeps until lastWakeTime + wakeUpInterval so value can accumulate and already-running threads can drain the burst. If the value was consumed meanwhile it goes back to sleep without ever returning to the caller. Measured quantity: wakeups per task, not throughput.
- **Forced by:** folly's stated motivating case: a thread-pool queue fed a burst of tasks that each take hundreds of nanoseconds. Waking a thread costs microseconds, so waking one thread per task makes the pool slower than running the burst serially on the already-hot thread. Note the asymmetry folly is careful about: when posts are spaced further apart than wakeUpInterval, or when there is more value than waiters, throttling adds exactly zero latency — so it is free in the regimes it does not help.
- **Plan has:** Nothing. `backpressure` (BackpressureStrategy/BoundedBuffer) governs what happens to *producers* when a queue fills — a different axis entirely. W030.md's shard-per-core vs work-stealing memo covers task *placement*, never wake policy. The plan's Backoff ladder (crates/concurrent/src/backoff.rs) delays the *waiter's* decision to park; throttling delays the *poster's* decision to wake, and the two are independent. `concept_cadence.md:35` closes the "futex/parking/blocking" muscle on park-side work only. No bench anywhere measures wakes-per-item.
- **Consumers:** `runtime-thread-per-core` task queue — hot path, P4 v1 and P5. P5's apply/replication pipeline where small messages arrive in bursts. Directly relevant to P4's p99 tick-to-trade budget: an unthrottled wake per message is a microsecond-scale event inside a budget the plan declares in nanoseconds.

**folly/synchronization/FlatCombining.h (Hendler/Incze/Shavit/Tzafrir SPAA 2010) and the combinable-critical-section mode of folly/synchronization/DistributedMutex.h**  
`add-to-plan` · `core` · ~25 h

- **Technique:** Combining / delegation instead of mutual exclusion: a thread that finds the lock contended publishes a request record in its *own* cache line and waits on its own flag; the current holder walks the publication list and executes everyone's operation while the shared data stays resident in one core's cache. The shared cache line migrates once per combining round instead of once per thread. Two further wins folly names: lock release/acquire leaves the critical path entirely, and "smart combining" lets K operations cost less than K separate ones (folly's example: K delete_mins on a priority queue in O(K + log N) rather than O(K log N)).
- **Forced by:** The plateau folly's DistributedMutex header describes: past a point, shrinking the critical section stops buying concurrency because the synchronization and scheduling overhead *is* the critical path. Combining moves that breaking point down to the cost of a hardware atomic. folly's measured claim, from the DistributedMutex header: combinable mode is >10x the small locks, ~6x std::mutex, 2-3x flat combining, and faster than std::atomic<> on some workloads.
- **Plan has:** The plan has exactly one combining instance and does not recognise it as one: WAL group commit (W026.md:900, "Always combine"), where one thread fsyncs for many. That is combining as a domain trick, not as a general lock-replacement protocol — there is no publication record, no combiner election, no record lifecycle. The plan's three answers to contention are shard-by-key / thread-per-core single writer (P4 v1, W065), lock-free structures (MPMC, SegQueue, skiplist), and CachePadded (W004). Combining is a fourth answer and it is specifically the one that applies where the other three fail: a *small* critical section on state that *cannot* be partitioned by key.
- **Consumers:** P1 v1.5 hot path — the buffer pool's global free-frame list and LRU-K victim selection during parallel storage-root computation: every worker wants "give me a free frame", ~20ns critical section, not shardable without stranding memory (bufpool's ShardedCache routes by first-byte-of-key, which does not shard a free list). P4 hot path — per-account position/STP update on fill, which crosses symbol shards by construction. P5 — liquidation priority queue (the smart-combining delete_min case literally).

**folly/SharedMutex.h (deferred readers) + its dependency folly/concurrency/CacheLocality.h AccessSpreader**  
`add-to-plan` · `core` · ~10 h

- **Technique:** Two separable things. (a) Per-core stripe index: get "which core am I on" cheaply (getcpu / rdtscp aux, cached in TLS, with a TLS-assigned pseudo-core fallback) so any striped structure can index by *core* rather than by key. (b) Deferred readers: shared-mode acquire writes a per-core slot drawn from one small global table rather than a shared counter, so concurrent readers never ping-pong a line; writers scan the table and "inline" deferred readers; a Token tells unlock which slot to clear; and crucially deferral is switched on only after concurrency is actually observed (kNumSharedToStartDeferring), because a shared stripe table makes any lock's writer conflict with any other lock's readers.
- **Forced by:** The cache-coherence fact folly spends two paragraphs on: a reader-writer lock requires a *write* to acquire in shared mode, which invalidates the lock's line in every other core — so an rwlock often beats a plain mutex by nothing at all. folly's numbers: deferred readers scale linearly and go up to two orders of magnitude faster than RWSpinLock under heavy read contention, at the cost of ~5ns extra when uncontended. The per-lock cost of naive striping (16 L1 caches x 64B = 1024 bytes per lock) is why the stripe table is global and shared across all instances, which in turn is why conditional deferral exists.
- **Plan has:** W013.md:19 names this exact wall as trap (3): "the reader-count CAS itself becomes the contention point at high reader fan-out" — and then the Phase-3 fix list offers only Backoff (cuts CPU burn, not line migration) and repr(C) padding (separates lock from payload, not reader from reader). The wall is named and the step past it is never built, which is the one shape PRODUCT_TREE §2 says should never happen. W027.md:309 and W097.md hand it off to "ArcSwap or a TLS cache" as a mention, never a component. Separately, nothing in the plan can answer "which core am I on": W065/W110 pin threads to cores and allocate NUMA-locally, but a pinned thread still has to be *told* its core id; bufpool::ShardedCache shards by key; latency-lab's per-shard recorders are handed their index. grep for getcpu/rdtscp/AccessSpreader across plan/, notes/ and crates/ returns nothing.
- **Consumers:** (a) per-core stripe index: `runtime-thread-per-core` setup + `bufpool` hot path (P1, P4, P5) — it is the missing primitive under every striped counter the plan will want. (b) deferred readers: P1 v1.5 MVCC reader fan-out, P5 risk-engine 16-shard read fan-out. Hot path both.

**folly/synchronization/SanitizeThread.h (annotate_rwlock_acquired/released, annotate_benign_race_sized, annotate_ignore_reads_begin/end) and the TSAN note at the head of folly/SharedMutex.h**  
`add-to-plan` · `arguable` · ~10 h

- **Technique:** Make a hand-written primitive legible to a race detector: annotate your custom lock so the detector treats it as a lock (which turns on whole-program lock-inversion analysis), declare your deliberate races explicitly rather than suppressing the whole file, and bracket speculative reads that are known-racy-by-design. folly also documents the failure mode of doing this: SharedMutexReadPriority is left *un*annotated because TSAN's lock-order heuristic assumes two lock_shared calls are ordered, which floods the reader-priority variant with false positives.
- **Forced by:** loom and Miri verify one primitive in isolation, at model speed. A race detector is the only tool in this family that runs on the *assembled* system at close to real speed, and the only one that finds lock-order inversions *between two different hand-written locks*. But it cannot know your lock is a lock, and it cannot know which of your races you meant — so an unannotated hand-rolled primitive makes it unusable, which is why the annotation API exists at all.
- **Plan has:** The plan's tool ladder is loom (interleavings) + Miri (UB/leak) + proptest + asm probes, with the evidence hierarchy happens-before > loom > Miri > asm (reference_concurrent_test_checklist). TSAN is absent from the ladder and from §5's borrow list. Two live consequences. First, the SeqLock is sitting at "6/6 green but payload still non-atomic" — a non-atomic payload read racing a writer is precisely the benign-race-by-design case, and it needs a *named* annotation, not a blanket suppression. Second, P1 v1.5 composes MVCC + bufpool pin/unpin + page latches: that is three hand-written locks in one call graph, the classic lock-inversion surface, and nothing in the plan can currently detect an inversion across them (loom models one primitive; a 3-lock call graph at realistic depth is out of loom's reach).
- **Consumers:** Cross-cutting. Highest value as an acceptance gate on P1 v1.5 (3 interacting hand-written locks) and on P5's replica (long-running assembled system). The tool is borrowed (-Zsanitizer=thread); what has to be built is the annotation seam inside concurrent's Mutex/RwLock/SeqLock and one CI lane. Changes what gets *measured*: "TSAN-clean under the acceptance workload" is a claim the plan cannot currently make.

**folly/synchronization/ParkingLot.h**  
`add-to-plan` · `arguable` · ~10 h

- **Technique:** Address-keyed userspace wait queues: a global table of 4096 buckets keyed by an arbitrary 64-bit key, with two levels of locking — a per-bucket mutex guarding the list, and a per-node mutex+condvar+bool for the actual wakeup. The split is what makes wakeups precise without holding the bucket lock across the wake (no thundering herd). The unpark callback returns Retain/Remove x Continue/Break per node *while the bucket lock is held*, which is what lets a lock implement its handoff policy atomically with the dequeue.
- **Forced by:** futex is 32 bits wide, and that width is a hard floor on how small a lock can be — folly's MicroLock header says this outright: its uint8_t state forces atomic_wait through ParkingLot, making a 1-byte lock *slower* under contention than a 4-byte std::mutex. A userspace parking lot decouples "what you block on" from "what the kernel can wait on", which is also how DistributedMutex blocks on a pointer-width word.
- **Plan has:** The plan blocks on the real futex via the atomic_wait crate (crates/concurrent/src/rw_lock.rs:24, parker.rs). On Linux that is the kernel's parking lot, so for 32-bit state words the plan has this for free and does not need to rebuild it. The gap is verification, not performance: loom cannot model a futex, so rw_lock.rs:26-39 and parker.rs:26 both compile in a `#[cfg(loom)]` stub that fakes wait/wake as a spin. Every loom model of the plan's blocking primitives therefore runs with the blocking path replaced. **folly/synchronization/LifoSem.h (wake policy) and its exact-wakeup accounting**  
`add-to-plan` · `core` · ~5 h

- **Technique:** LIFO wake order with exact wakeups: wake the most-recently-parked waiter, because its cache and TLB are warmest and — the part that actually pays — it may not have reached futex_wait yet, so the wake costs zero syscalls. Combined with exact accounting (post conveys one unit either into the value or directly to one specific waiter, never both), which is why folly can claim fewer system calls than sem_t.
- **Forced by:** When all waiters are interchangeable (a thread pool, a stage consumer), fairness buys nothing and costs cache warmth plus a syscall per wake. folly's framing is explicit: LifoSem's wakeup policy is "intended to maximize performance rather than fairness". DistributedMutex makes the same choice and then bounds the unfairness — its contention chains are LIFO, but a chain is broken whenever a wakeup is scheduled, so the LIFO-ness is bounded by the number of concurrently-failed acquisitions rather than being unbounded starvation.
- **Plan has:** crates/concurrent/src/semaphore.rs is FIFO by construction (WaitList::pop_front) and the whole build ladder was barging -> fair -> cancel -> close -> intrusive — fairness was the goal and LIFO was never the alternative considered. No bench anywhere counts syscalls per wake or measures wake-to-run latency as a function of wake order. rw_lock.rs:160 does the opposite (futex_wake_all on the reader word). This is a variant of something the plan builds rather than a missing component, which is why it is cheap: the technique is a wake-policy A/B on the existing WaitList plus the measurement that justifies choosing one.
- **Consumers:** `runtime-thread-per-core` worker pool and P4's stage consumers (hot path) — the two places where waiters are genuinely interchangeable. Explicitly NOT for P5 consensus or P1's txn lock manager, where the plan's fairness is the correct choice; the deliverable is knowing which regime you are in and having the number to prove it.

**folly/synchronization/DistributedMutex.h — hardware timestamp publishing (the TimePublishing template parameter, default true)**  
`note-only` · `core`

- **Technique:** Preemption detection by timestamp publishing: each waiter writes a hardware timestamp into its wait node, so the thread performing a handoff can tell that its chosen successor was descheduled and skip it rather than handing the lock to a thread that is not running.
- **Forced by:** folly states the failure precisely: waking waiters one-by-one down a queue "does not scale well when the number of threads goes past the number of cores", at which point preemption produces elevated acquisition latencies — the lock-waiter-preemption / convoy problem. Handing a lock to a preempted thread stalls everyone behind it for a scheduling quantum, which is a tail-latency event orders of magnitude past the mean.
- **Plan has:** The plan's answer to preemption is structural: thread-per-core with pinning (W065, W110), i.e. threads == cores, so nobody is preempted. That answer is correct for P4 and genuinely removes the problem there, which is why this is note-only rather than add-to-plan. It does not hold where the plan runs unpinned — P3 on tokio, and P5's replicas on shared hosts (W110 pins the apply thread and the risk recompute thread, not the rest). The plan has rdtsc in `time` already, so the ingredient exists; what is missing is the idea that a timestamp in a wait node is a preemption oracle. Worth one named pitfall in the Mutex/WaitList notes and in P5's tail-latency analysis, not a build.
- **Consumers:** P5 (replica apply path on an unpinned host), P3 (tokio-hosted node). Tail-latency concern, not throughput.

**folly/MicroLock.h (2-bit lock in a byte, 6 bits of user payload, lockAndLoad/unlockAndStore) and folly/synchronization/PicoSpinLock.h (lock on one bit of an existing integer)**

**folly/executors/Codel.h (class Codel, overloaded()/getLoad()/getSloughTimeout()) together with folly/executors/ThreadPoolExecutor.h (Task::enqueueTime_, Task::Expiration{expiration, expireCallback}, and ProcessedTaskInfo{waitTime = dequeue - enqueue, expired, runTime})**  
`add-to-plan` · `core` · ~12 h

- **Technique:** Delay-based load shedding: admission control driven by measured time-in-queue (sojourn time), not by queue occupancy. Timestamp on enqueue; on dequeue compute wait = now - enqueue; track min-wait over a rolling interval; if min-wait stayed above a target for the whole interval the system is persistently (not transiently) backed up, so expire any item whose own wait exceeds a slough timeout (2x target) instead of serving it stale. Per-item deadline with an expire-callback is the same idea at item granularity.
- **Forced by:** Bufferbloat, transplanted from routers to request queues. A bounded queue tells you nothing about latency: a 1024-slot queue drained at 50k/s is never 'full', yet every item in it is ~20 ms old. Under overload the useful work is to discard the items that are already too late to matter and keep the queue drained, so the items you do serve are fresh. Shedding on depth either sheds during harmless bursts or never sheds at all, depending on how the capacity was guessed; shedding on delay is self-tuning and needs no capacity guess.
- **Plan has:** crates/backpressure/src/strategy.rs is the whole backpressure crate: BackpressureStrategy + BoundedBuffer<T> + PushOutcome<T>, with try_push/pop. That is capacity-based — the signal is 'the queue is full', and the responses are drop-oldest / drop-newest / block. §6 maps 'backpressure' to P3 node I/O. The nearest thing elsewhere is W040's dual-watermark credit scheme reserving a foreground I/O budget against LSM compaction (W040:271,439) — domain-specific to compaction, not a shared primitive, and still occupancy-based. Grepping plan/ and crates/ for codel, shed, sojourn, queueing delay, admission returns no mechanism. No queue item anywhere in the plan carries an enqueue timestamp, so wait-time is not merely unshed, it is unmeasured — and 'wait vs run' is the decomposition that tells you whether a p99 came from the queue or from the work.
- **Consumers:** P4 hot path (gateway admission: under a burst, rejecting an order is correct and matching a 20 ms-stale one is not — real venues do exactly this, and it is a venue-correctness property, not a perf tweak). P5 hot path (replica ingress ahead of the consensus round; also the natural place to express 'this request cannot meet its deadline, fail it now'). P3 setup-to-warm (txpool intake and Engine API under a sync-storm). P1 v2 / P2 v1.5 parallel work pools get the wait-vs-run decomposition for free from the same instrument.

**folly/synchronization/ThrottledLifoSem.h (wakeUpInterval, the single kWakingBit waiter, LIFO waiters_ intrusive list) and folly/synchronization/LifoSem.h (approximately-LIFO wakeup, 'exact wakeups, so it often requires fewer system calls'), consumed by folly/executors/task_queue/PriorityLifoSemMPMCQueue.h and documented as the policy choice in folly/executors/CPUThreadPoolExecutor.h's class comment**  
`add-to-plan` · `core` · ~24 h

- **Technique:** Wake-economy as an explicit queue policy, on two axes. (a) LIFO wake order: hand the permit to the most-recently-parked consumer, so a small hot set of workers absorbs the load and the rest stay parked and cold (their stacks and caches stay evicted, and in folly's case get madvised away). (b) Throttled wake: when a permit is posted and a waiter would have to be woken, delay that wake by up to wakeUpInterval and let at most one waiter be in a 'waking' state; if an already-running consumer drains the value during the delay, nobody is woken at all. Cost is zero in the two regimes that matter — posts spaced further apart than the interval wake immediately, and a saturated pool has more value than waiters so there is nothing to throttle.
- **Forced by:** A burst of sub-microsecond tasks into an idle N-thread pool makes the wakeups cost more than the work: a futex wake plus scheduler plus cold-cache restart is hundreds of ns to low us against a task of ~100 ns, and FIFO fairness actively maximizes the damage by rotating through every thread so none stays warm. folly's own comment names the case: 'if a burst of very small tasks (order of hundreds of nanoseconds each) is enqueued, it may be beneficial to have a single thread process all the tasks sequentially'.
- **Plan has:** crates/concurrent/src/semaphore.rs is strict FIFO by construction — State{waiters: WaitList, permits, closed}, and release pops waiters.pop_front(). The whole async-semaphore ladder recorded in memory (barging -> fair -> cancel -> close -> intrusive) travels the *fairness* axis, which is the opposite direction from this. The plan's wake-economy work is entirely producer-side: W043/W044 coalesce eventfd writes so N cross-shard sends amortize to one syscall (W043:60, W044:205-206, the 100x syscall-reduction back-of-envelope). Nothing in the plan reduces the number of *consumers* woken, delays a wake to let a running consumer absorb the work, or treats wake order as a cache-locality decision. Grepping plan/ and crates/ for 'lifo' hits only undo-log replay order and object-pool free-lists — never wake order. §6's 'Lock-free MPMC (Vyukov), SegQueue, skiplist' row is queue mechanics; the wake policy layered on top of a queue is a separate thing and has no row.
- **Consumers:** P1 v2 hot path (parallel storage root: hashing one changed subtrie is a short task, and a 16-thread pool woken for 3 subtries pays 13 pointless wakeups per block). P2 v1.5 hot path (block-STM: re-execution tasks are short and bursty — exactly folly's motivating case). P4 v1 setup/off-path (the pinned shards never park, but the snapshot/replay/admin pool does). P5 same shape as P2. Also: the plan drops rayon for the hand-written runtime-thread-per-core (§5), and this is one of the places rayon's tuned wake policy is silently carrying the plan today — swapping in a FIFO semaphore could regress the parallel-root bench and the cause would be invisible without this axis named.

**folly/io/async/AsyncSocket.h (ErrMessageCallback::errMessage(const cmsghdr&), ByteEventHelper::processCmsg, kMaxAttemptsEnableByteEvents, WriteRequestTag, the FOLLY_HAVE_SO_TIMESTAMPING guard) and folly/io/async/observer/AsyncSocketObserverInterface.h (ByteEvent{Type: WRITE/SCHED/TX/ACK, size_t offset}, PrewriteRequest with its split-the-write-at-this-byte-offset merge logic)**  
`add-to-plan` · `arguable` · ~16 h

- **Technique:** Egress latency attribution via kernel and NIC transmit timestamps keyed to a byte offset. Enable SO_TIMESTAMPING, tag the exact byte you care about (splitting the write at that offset if needed so the timestamp lands on a known boundary), then drain the socket error queue and parse SCM_TSTAMP_SCHED / _SND / ACK cmsgs back into (byte offset, event kind, timestamp) triples. The result decomposes the egress path into: userspace handed it off -> kernel scheduled it -> NIC took it -> peer ACKed it.
- **Forced by:** Userspace timestamps bound the egress path from the outside and attribute nothing inside it. When a response's p99 is bad, the question is whether the socket buffer was full, whether the qdisc held it, whether the NIC was busy, or whether the peer was slow — and those have four different fixes. The kernel will tell you, per byte, but only through the error queue, and only if the write was tagged before it went out.
- **Plan has:** latency-lab (W021-W024) is HdrHistogram + Gil Tene coordinated-omission correction + PMU counters + rdtsc; its tick-to-trade API is literally record(tick_tsc, trade_tsc) (W024:307,236) — two userspace TSC reads bracketing the application. time::HardwareTimestamp (W006:1157) is a *clock-source* seam (PTPClock at W85, TSCClock at W89): it decides where 'now' comes from, not where the bytes were. W086/W089 cover the receive side thoroughly (io_uring multishot, provided-buffer rings, AF_XDP). Grepping plan/ for SO_TIMESTAMPING, SCM_TSTAMP, hwtstamp, wire-to-wire, error queue returns nothing. Net effect: P4's acceptance test is 'p99 tick-to-trade under a declared budget', and as instrumented the measurement starts at first-userspace-read and stops at last-userspace-write — it excludes the kernel and NIC half of the TX path, which on an un-bypassed socket is usually the larger half. The budget is declared and asserted rather than measured end to end.
- **Consumers:** P4 v1-v1.5 (directly: this is what makes the §1 acceptance test auditable instead of asserted; also the honest baseline the AF_XDP-vs-io_uring-vs-epoll ranking in W089 Fri needs, since without it the three transports are compared only on the part of the path they share). P5 (replica-to-replica round-trip attribution: distinguishing a slow replica from a slow network is the single most common distributed-debugging question, and VSR view-change tuning depends on the answer). **folly/io/async/AtomicNotificationQueue.h (getMaxReadAtOnce/setMaxReadAtOnce, 'Executes one round of tasks', and the AtomicNotificationQueueTaskStatus discard path that deliberately does not count against the round budget) plus folly/io/async/EventBase.h Options::setLoopCallbacksTimeslice (a time-based rather than count-based budget, explicitly 'does not apply to runBeforeLoop() and runAfterLoop()')**  
`add-to-plan` · `core` · ~4 h

- **Technique:** Bounded work per event-loop iteration. Each ready source gets a budget — a count of items or a slice of wall time — and the loop moves on when the budget is spent even if that source still has work, so every source is reached every iteration. The budget is a liveness mechanism, and the choice of count-vs-time plus which callbacks are exempt from it is the policy.
- **Forced by:** Drain-until-empty is only correct if the producer is slower than the consumer. Once it is not, the loop never leaves the first source: epoll is not re-entered, the timer wheel is not ticked, and the shard livelocks while looking perfectly busy. - **Plan has:** W043 R1-R7 define the reactor as {epoll_fd, ready_queue: VecDeque<Task>, cross_shard_inbox: SegQueue<Task>, eventfd, timer_wheel}, with R7 computing the epoll_wait timeout from the timer-wheel head. Grepping W043/W044/W058/W066 for starvation, drain budget, max-batch, batch-limit, fairness returns only *cost* budgets (ns/op, 10 us/task, p99 < 2 us) — never a work budget per iteration. The plan does name compaction/vacuum/snapshot starvation as a muscle to reapply (W058:333) but has no mechanism for it at the loop level, which is where P4's and P5's shards live.
- **Consumers:** P4 v1 hot path and P5 hot path (the per-shard reactor loop: a sustained cross-shard sender from a busy symbol shard can starve that shard's own socket reads and its settlement/IOC timers — and a starved timer wheel in P5 is a spurious view change). **folly/io/async/EventBase.h — class SmoothLoopTime (addSample(total, busy), getTimeSmoothed), the loopSample(int64_t busyTime, int64_t idleTime) observer hook, and setMaxLatency(microseconds, Func maxLatencyCob); also folly/io/async/EventBasePoller.h Stats (totalWait/minWait/maxWait vs totalBusy/minBusy/maxBusy, totalWakeups vs totalNumEvents)**  
`add-to-plan` · `arguable` · ~6 h

- **Technique:** Self-measuring event loop: each iteration records busy time and idle time, an exponentially-smoothed busy/total ratio gives a live utilization estimate, and a max-latency tripwire fires a callback the moment one iteration's busy time exceeds a declared bound. Events-per-wakeup (totalNumEvents / totalWakeups) is the companion ratio — it says whether batching is actually happening.
- **Forced by:** Utilization is the leading indicator that a percentile is the lagging one. It is also the input a delay-based shedder and a wake-throttle need in order to make a decision, and the tripwire turns 'something occasionally stalls the loop' from a statistical observation into a stack trace at the moment it happens.

- **Consumers:** P4 v1-v1.5 (per-shard utilization is what turns 'sustained N msg/s at p99 under budget' from a single measured point into a headroom claim; the max-latency tripwire catches the rare multi-us stall that HdrHistogram only reports as a number). P5 (a saturated replica loop is the usual root cause behind consensus timeouts, and currently nothing would say so). P1 v2/P2 v1.5 worker loops. Measurement path. **folly/io/IOBuf.h (the headroom/data/tailroom layout with buffer()/data()/tail()/bufferEnd(), prependChain/appendChain circular chain, coalesce(), unshare(), cloneOne(), fillIov(), takeOwnership(ptr, len, FreeFunction, userData)) and folly/io/IOBufQueue.h (preallocate(min,newAlloc,max)/postallocate(n), WritableRangeCache, Options::cacheChainLength, split/trimStart)**  
`note-only` · `borrow`

- **Technique:** Three separable things. (a) Headroom: a buffer reserves space *before* its data, so each protocol layer prepends its header in place instead of copying the payload forward. (b) Chained non-contiguous buffers presented as one logical byte range, written with a single gather syscall via fillIov, split and cloned at arbitrary offsets without copying, and coalesced only when some consumer genuinely needs contiguity. (c) preallocate/postallocate: ask for a writable tail of at least min bytes, write an unknown amount into it, then declare how much was used — so neither the over-copy of a guessed-small buffer nor the waste of a guessed-large one happens.
- **Forced by:** Layered protocols and partial reads. Encoding a framed message bottom-up without headroom copies the payload once per layer; reassembling a frame that straddles two reads without chaining copies it again; and a decoder that must hand a sub-range to a parser either copies or needs refcounted views. folly's answer makes all three zero-copy and lets the refcount live in the allocation.
- **Plan has:** crates/eth-primitives/src/bytes_mut.rs is tail-only — new/reserve/extend_from_slice/as_slice/freeze, no prepend and no notion of headroom; grepping crates/ and plan/ for headroom or prepend returns nothing. eth-primitives is marked 'DONE, FROZEN' in §3, and §5 explicitly deletes codec layers, so this is partly a deliberate boundary rather than an oversight. The plan's own answer for the one place it bites is W054:214: caller-owned scratch slices, send(&mut self, pt, ct_out) / recv(..., pt_out), wired to a per-connection BytesMut ring or a pooled bufpool buffer — a coherent design that sidesteps chains entirely by pre-sizing one contiguous buffer per connection. W064:604 covers serialize-once-scatter via sendmmsg, which is many *messages* in one syscall, not many *fragments* of one message. W087:233 already has the right instinct in the Aeron try_claim / IORING_OP_WRITE_FIXED 'the claim slot IS the message' muscle — encode directly into the destination — which is headroom's cousin and is the reason this is note-only rather than add-to-plan.
- **Consumers:** P3 only, and only on the RLPx frame path (frame header + two MACs around a ciphertext is the textbook headroom case). P5's messaging-aeron term buffer already uses the claim-in-place pattern, and P4's ingress borrows from the io_uring provided-buffer ring, so neither needs chains. Worth one paragraph in the W054/W052 design note recording why pooled contiguous scratch was chosen over a chained buffer (the trade is: chains avoid a copy on reassembly, pre-sized scratch avoids pointer-chasing and refcount traffic on every read — for a node holding ~50 peers the second is almost certainly right, but the plan should say so deliberately rather than by default).

**folly/io/async/HHWheelTimer.h — std::array<std::size_t, (WHEEL_SIZE/sizeof(size_t))/8> bitmap_ alongside WHEEL_BITS=8 / WHEEL_SIZE=256 across four levels, plus cascadeTimers() and the Divider that replaces the tick division with a multiply-by-reciprocal**  
`note-only` · `core`

- **Technique:** A bitmap of non-empty wheel slots, so 'when does the next timer fire' is a word scan over 4 words rather than a walk over 256 slots. Separately: reciprocal multiplication instead of integer division on the now->tick conversion that runs every loop iteration.

**folly/container/SparseByteSet.h (the byte-domain case of the general technique; Aho-Hopcroft-Ullman / Briggs-Torczon sparse set)**  
`add-to-plan` · `core` · ~4 h

- **Technique:** Sparse set: a dense array of members plus a sparse index array over a bounded key universe. O(1) insert / contains / remove, O(1) clear by setting size=0 with no zeroing, and iteration that walks the dense array contiguously in insertion order. Zero hashing, zero allocation after one startup array, fully deterministic iteration order.
- **Forced by:** folly's comment is explicit: the constructor zeros only two bytes, add and contains are constant time non-amortized, the whole capacity is inline so it never allocates. It exists because std::bitset<256> pays a 32-byte memset on every clear and cannot enumerate its members without scanning the whole universe. The pressure is a set that is built small, scanned, and thrown away millions of times per second.
- **Plan has:** Zero hits for sparse set / sparse_set / dense-plus-sparse anywhere in PRODUCT_TREE.md, concept_cadence.md, rebuild_ladder.md, notes/, or the 142-file reference archive. The plan has the adjacent pieces but not this one: bitsets for vote tallies (W065 count_ones), ArrayVec/SmallVec for bounded buffers (W058/W083/W100), FixedMap robin-hood for lookup (W089), and the determinism rule 'HashMap iteration order is banned, use sorted/FixedMap iteration' (W060, W083, W093). Every one of those is a different trade: the bitset cannot enumerate members cheaply, ArrayVec gives O(n) contains, FixedMap pays a hash plus a probe and clearing it is O(capacity), and sorting to get determinism costs n log n per clear-and-rebuild cycle. Sparse set gives all four properties at once (O(1) membership, O(1) clear, contiguous enumeration, deterministic order) and the plan never names it.
- **Consumers:** P1 hot: PrefixSet is exactly this shape (the set of trie paths changed this block, rebuilt and cleared every block, then walked in order by TrieWalker). **folly/container/WeightedEvictingCacheMap.h (ImplicitlyWeightedEvictingCacheMap + WeightedEvictingCacheMap) over folly/container/EvictingCacheMap.h**  
`add-to-plan` · `core` · ~6 h

- **Technique:** Weight-budgeted eviction: the cache holds a total-weight accumulator and a weight function over (key, value), and evicts in LRU order until total weight is under a byte budget, rather than until entry count is under a count budget. Plus EvictingCacheMap's clearSize (evict a batch of N per overflow to amortize the eviction walk) and the pruneHook seam.
- **Forced by:** folly's comment names the motive directly: 'if TKey and TValue are std::string, the weight could be the sum of the string sizes so that the total weight approximates the total memory usage.' A count-based LRU over variable-size values cannot bound memory at all; the resident set is count x worst-case-value-size, which is the number that OOMs you.
- **Plan has:** The plan has LRU-K, pin/unpin, dirty tracking and sharding (PRODUCT_TREE 2 row P1 v1.5, 6 row 'Buffer pool LRU-K'), and the existing crate implements them. **folly/lang/Hint.h — compiler_must_not_predict, as a named primitive distinct from compiler_must_not_elide**  
`add-to-plan` · `core` · ~3 h

- **Technique:** Two-sided benchmark hygiene. One primitive stops the compiler deleting a computation whose result is unused (must_not_elide, Rust's black_box). **folly/container/heap_vector_types.h (heap_vector_map / heap_vector_set)**  
`add-to-plan` · `core` · ~5 h

- **Technique:** Eytzinger (level-order / implicit-heap) layout of a sorted array, so that lookup is a forward walk through successive cache lines that compiles to cmov instead of a branchy binary search jumping around the array. Cost: insert/erase and in-order traversal get slower, so the structure wants batch construction and lookup-dominant workloads.
- **Forced by:** folly states the two reasons and the measured result: (1) 'the container is traversed sequentially instead of binary search that jumps around the sorted vector', (2) 'the branches in a binary search are mispredicted resulting in hardware penalty while using heap lookup search the branch can be avoided by using cmov'. 'We observed look up operations are up to 2X faster than sorted_vector_map.' Same memory footprint as the sorted vector — the win is layout only.
- **Plan has:** The plan reasons hard about sorted-vector-versus-tree and about branchlessness, but never about the layout inside the sorted run. W042 lands the muscle 'sorted Vec beats BTreeMap up to N approx 64' and even explains why ('the cache footprint is fragmented across'), W025 costs a B+tree NEXT crossing a leaf, W015 and W034 drill branchless table lookup and branchless nibble extraction. None of them ask whether the keys inside a node should be stored in sorted order at all. Zero hits for Eytzinger, level-order, van Emde Boas, or branchless search in the whole plan; cmov appears only in the W034 counting-bloom saturation context. The plan's B+tree work item (W028, PRODUCT_TREE 6 row 'B+tree split/merge, cursors, dupsort') specifies split/merge/cursor/dupsort and is silent on intra-node search.
- **Consumers:** P1 hot, the single hottest inner loop of the storage engine: every get and every cursor seek does one intra-node key search per level, over the 100-500 keys in a 4-16 KiB node. Also P4 hot (the fixed tier table W066 scans linearly over 6 entries — correctly, and that linear-versus-Eytzinger crossover point is the thing to measure) and P1 v2's sparse-trie branch selection.

**folly/container/F14.md + folly/container/detail/F14Table.h — chunked SoA tag vector with SIMD group filter, and overflow counters as reference-counted tombstones**  
`add-to-plan` · `arguable` · ~8 h

- **Technique:** Split the hash table's metadata from its entries: pack one byte of secondary hash (a tag) per slot into a single 16-byte aligned vector at the head of a 14-slot chunk, and compare the needle's tag against all 14 at once (SSE2 _mm_cmpeq_epi8 on x86_64, NEON on aarch64). One cache line of tags filters 14 candidate keys, so a failing lookup usually performs zero key comparisons and a hit usually performs exactly one. That filtering is what permits a 12/14 max load factor with an expected find-hit probe length of 1.04. Separately: instead of tombstones, each chunk keeps a count of keys it displaced, decremented on erase — an earlier probe exit that self-cleans under a steady insert/erase mix.
- **Forced by:** folly's stated motive is moving the space/time curve rather than trading along it: 'improving memory efficiency and performance when compared to most of the existing algorithms'. The chunk argument is the reverse birthday paradox (overflowing a 14-capacity bucket is far rarer than overflowing a 1-capacity bucket even though per-pair collisions get likelier), and 'tags cause keys to be densely packed into the bottom of a chunk and filter all memory accesses to the portions of a chunk that are not used' — i.e. the tags are also what makes small tables cheap.
- **Plan has:** The plan hand-writes exactly one open-addressed map (W089 AccountMap, FixedMap) and it is thorough: robin-hood versus linear probing with the max-probe-distance variance argument (D5), a deterministic unit-struct hasher for replica-identical replay (D6, R3), fixed capacity and no rehash (R2), and a stored partial hash in the slot — D4 offers `struct Slot { state: u8, hash_top: u32, key, value, probe_dist }`. So partial-hash filtering and tombstone-free deletion are both covered. What is not covered is the layout decision: D4 asks 'Which causes a 2-line read per probe?' and offers only two array-of-structs answers, both of which straddle lines at K=u128, V=Account(96B). The chunked structure-of-arrays answer — tags in their own contiguous vector, entries elsewhere, one SIMD compare per chunk — is not among the options, and the load-factor headroom it buys (12/14 instead of the plan's 0.85 cap in R2) is never raised. Zero hits for F14, swiss, open addressing, movemask, or SIMD-in-a-hash-table context across the plan. Note this is a 'change the one map you already write', not 'write a second map' — law 1 forbids the latter.
- **Consumers:** P4 hot: W060's own cost model names `order_index.insert` at 30-50 ns as 'killer #2' of the 1000 ns per-order budget, and order_index is hit on every cancel and amend. P2 hot: block-STM VersionedMemory keyed lookup, probed once per storage read per incarnation. P5 hot: the W089 AccountMap itself, two lookups per transfer inside a ~180 ns p50 budget. P1: hashed-cursor and StateCache probes.

**folly/container/F14.md section 'RANDOMIZED BEHAVIOR IN DEBUG BUILDS' (implemented in F14Table.h / F14Policy.h)**  
`add-to-plan` · `core` · ~3 h

- **Technique:** Make unspecified behaviour actively hostile in debug and sanitizer builds so that latent dependence on it fails in tests instead of in production. F14 randomizes the relationship between insertion order and iteration order in debug builds, so two identically-built maps iterate differently; and under ASAN it performs randomized extra rehashes, so any code holding a reference across an insert is caught.
- **Forced by:** folly's words: 'This randomness is designed to expose bugs during test that might otherwise only occur in production.' The insight is that a guarantee you did not make will be depended on anyway unless you make depending on it fail. Note the deliberate escape hatch: a reserve(size()+n) exempts the next n insertions, so the discipline has a declared-intent opt-out rather than being all-or-nothing.
- **Plan has:** The plan's determinism machinery is large and entirely prohibition-shaped: ban the nondeterministic thing and enumerate replacements. W083 D4 and W093 D-DET build nondeterminism ledgers (HashMap iteration order, thread_rng, Instant::now, allocator pointer placement, f64) each mapped to a deterministic replacement; W089 R8 adds cargo-deny disallowed_types for std HashMap and Vec in the state_machine module; W087 bans HashMap and ahash outright. Prohibition catches the constructs you thought of. It does not catch latent dependence on order inside the structures you did write — the plan's own FixedMap, TransferPool, ArrayVec and slab all have unspecified behaviour of their own (slot reuse order, iteration order over occupied slots, free-list LIFO order) and nothing anywhere makes a test fail for depending on it. Zero hits for adversarial randomization of this kind; the closest is W060's 'first attempts pass locally and fail on CI with a 1-in-100M seed-replay drift', which is precisely the bug this technique converts into a first-run failure. The complement is cheap in Rust: a debug_assertions-only per-run permutation seed for FixedMap iteration, and a pool that under debug hands back a deliberately non-LIFO free slot.
- **Consumers:** P5 hot gate: the cluster VOPR and the 'every replica replays to bit-identical state' acceptance test, plus W087's three disciplines. P1 and P2 gates: the state-root and state-diff determinism tests. Test-harness path, not a product hot path, but it is upstream of the plan's two hardest-to-fake acceptance tests.

**folly/container/small_vector.h — kMayCopyWholeInlineStorage / kShouldCopyWholeInlineStorageTrivial (and the isExtern flag packed into the MSB of size_)**  
`note-only` · `borrow`

- **Technique:** Inline-capacity containers have O(N) move and copy cost, not O(1), where N is the declared inline capacity rather than the live length. folly leans into it: when the inline buffer is trivially copyable and at most half a cache line, it unconditionally memcpys the whole buffer, because one branchless fixed-size copy beats a length-dependent loop; above that threshold it copies only the live prefix. Separately, the heap/inline discriminator lives in the top bit of the size field, so the container pays no extra word for it.
- **Forced by:** The size thresholds are keyed to hardware_constructive_interference_size, i.e. the choice is made on cache-line arithmetic. The pressure is that small_vector is passed and returned constantly, and a 'small' vector with a generous inline capacity is expensive to move even when empty.
- **Plan has:** The plan borrows SmallVec and ArrayVec rather than writing them, which section 0 endorses — this is not a request to hand-write one. The gap is in the cost model, not the component. The plan's bar-(c) back-of-envelope discipline covers allocation cost, cache lines touched, and branch mispredicts, but never the move cost of an inline buffer, and it puts large inline buffers in hot return positions: W100's contract is `-> (LiqOrderBatch, SmallVec<[Shortfall; 64]>, Option<CircuitBreaker>)` inside a 250 microsecond per-tick budget, and W061 D1 asks whether fills should be `Vec`, `SmallVec<[_; N]>`, or caller-provided `&mut Vec` scratch and picks N 'from the fill-count histogram (p50, p99, p99.9)' — sizing N from the tail is exactly the reasoning that makes the common-case move expensive. W061 does separately note 'SmallVec spill in the p99 tail' as a trap, so the spill cost is on the radar and the move cost is not. - **Consumers:** P5 hot (W100 liquidation tick, W061/W060 fill batches), P4 hot (match result returns). Hot path, but it is a cost-model and design-review line rather than a component.

**folly/IndexedMemPool.h — NumLocalLists=32 local free lists with LocalListLimit=200 bulk spill to a globalHead_ tagged pointer, selected by AccessSpreader**  
`note-only` · `core`

- **Technique:** A pooled-object free list that is per-CPU-ish rather than global: each thread takes and returns objects from its own bounded local list, and only when a local list overflows or empties does a bulk transfer happen against the shared tagged-pointer list. The bulk transfer amortizes the contended CAS over ~200 objects, and the design specifically targets the asymmetric case where objects are produced on one core and consumed on another (folly: 'allows items to be efficiently recirculated from consumers to producers'). Capacity accounting has to be inflated to cover objects stranded in other threads' local lists, which is why maxIndexForCapacity exists.
- **Forced by:** Contention. A single lock-free free list is one cache line every core CASes on, so under an asymmetric produce/consume flow it becomes the bottleneck and the pool's acquire cost stops being ~10 ns. The magazine/depot shape (same idea as a jemalloc tcache) is the standard answer.
- **Plan has:** The plan has the neighbouring pieces: per-shard pools in a thread-per-core runtime (W074 'per-shard slab::Slab<SkipListNode> arena'), a sharded cache, a cross-shard MPMC channel (W057), and single-threaded static pools (W089 TransferPool). What it never addresses is a pool whose acquire and release happen on different cores. I could not find a hot consumer that definitely has that shape: W060's order pool and W089's TransferPool both acquire and release inside one shard. The candidates are the off-shard ones — the aeron term-buffer claim-slot pool (W076/W077), the marketdata frame ring (W085), and WAL record buffers acquired by a shard and released by the single fsync thread. If any of those pools ends up with producer and consumer on different cores, the plan's per-shard-pool assumption silently becomes a one-directional drain, and the bounded-local-list-plus-bulk-spill design is the fix. Reporting as a note because I cannot name a consumer where this is certain, and inventing a second pool design for a hypothetical would not pass section 0.
- **Consumers:** P4 setup-to-hot, conditional: the aeron claim-slot pool and the marketdata frame ring, if their acquire and release sit on different cores. P1 the WAL record buffer pool under group commit. Not a gap at all if every pool stays shard-local, which is the plan's intent.

**folly/memory/Malloc.h — goodMallocSize/nallocx, smartRealloc, jemallocMinInPlaceExpandable, plus Arena's ArenaAllocatorTraits::goodSize hook**  
`note-only` · `borrow`

- **Technique:** Two allocator-aware sizing moves. (1) Round every request up to the allocator's real size class (nallocx) so you get the slack you are already paying for, and let an arena's block size be chosen by the allocator rather than by a round decimal number. (2) smartRealloc's slack heuristic: realloc copies the whole capacity because it does not know the live size, so when slack exceeds a third of the buffer, an explicit malloc plus memcpy of only the live bytes plus free beats realloc; below that, realloc is worth trying for in-place coalescing.
- **Forced by:** Both are about the gap between what you asked for and what the allocator actually gave you — wasted resident bytes in case (1), wasted copy bandwidth in case (2).
- **Plan has:** Nothing in the plan mentions size classes, usable size, goodMallocSize, or growth-factor-versus-size-class interaction (zero hits). The plan's answer to allocation is stronger and mostly makes this moot: never allocate on the hot path (W058, W060, W089 R5 with a dhat zero-allocation assertion). That subsumes the growth question entirely for hot paths. Where it does not subsume it is footprint: the plan asserts RSS gates (W044 <= 4 GB at 100M keys, W074 <= 2 GB at 10M orders) while sizing its one-shot startup allocations with round numbers, so some fraction of every pool and arena is slack the allocator charges for and the plan never counts. Honest read: this is a line in a footprint audit, not a step. Rust's Vec already reallocs via RawVec, and the smartRealloc heuristic has no natural home in a plan that bans hot-path growth.
- **Consumers:** P5 setup (W089's 128 MB TransferPool), P1 setup (pager and bufpool block sizing) — both startup-only, feeding the RSS acceptance gates rather than any latency number.

**folly/synchronization/FlatCombining.h (+ its client folly/concurrency/container/FlatCombiningPriorityQueue.h)**  
`add-to-plan` · `core` · ~50 h

- **Technique:** Delegation / combining as a synchronization strategy: a thread that finds the lock contended does not wait for the lock — it publishes a *request record* into a CAS-pushed publication list and spins on a per-record completion flag; whichever thread holds the lock becomes the combiner and executes everyone's operations against one sequential data structure. Three separable sub-techniques: (a) try_lock-first fast path, delegate only on contention, so the uncontended cost is exactly a mutex; (b) publication-list hygiene — idle records are unlinked after kIdleThreshold passes and the requester/combiner race is closed by a Dekker-shaped seq_cst store-load fence pair (setValid→fence→isDisconnected on the requester, setDisconnected→fence→isValid on the combiner), so cost is O(active threads) not O(registered threads); (c) SMART combining — the combiner's batch is a *semantic* batch, not just an I/O batch: K delete_mins in O(K + log N) instead of O(K log N), N dirty page-ids deduped in one pass. Also the dedicated-combiner-thread vs any-thread-combiner trade (latency+throughput under high contention vs no burned core and no wake latency under low contention).
- **Forced by:** A coarse mutex serialises the operation AND pays the lock handoff: every acquire/release migrates the lock word and the data structure's hot lines between cores, so the cache-coherence traffic, not the critical section, is the cost. Combining removes the acquire/release from the critical path entirely (the data stays resident on the combiner's core) and turns N cache-line migrations into one. Hendler/Incze/Shavit/Tzafrir, SPAA 2010.
- **Plan has:** Closest: (1) `wal/src/group_commit.rs` (W026) — a dedicated flush thread drains a SegQueue, batches up to max_batch=1024 records, one fsync, waiters park. That is literally FlatCombining's dedicated-combiner variant with maxOps=max_batch — but the plan treats it as a WAL-specific durability trick, never names the general primitive, and never builds the no-dedicated-thread variant or smart combining. (2) `bufpool` DirtyPageTracker (W014 R1) = `[Mutex<HashSet<PageId>>; N]` and `ShardedCache<N>` — the plan always reaches for sharded-mutex when a sequential structure gets contended; combining is the other answer and the plan has no vocabulary for it. (3) `concurrent::OnceFlag` already exists and is exactly folly's SaturatingSemaphore, so the per-record flags are free. Greps returning ZERO across plan/, notes/ and crates/: "flat combin", "FlatCombin", "combiner", "combining", "Hendler", "Shavit", "publication list" (the one hit is an Aeron active-publication list, unrelated). The 24 "delegat" hits are all code-structure delegation (façade forwards to module), not the concurrency technique. This is also a live violation of the plan's own Law 1 ("every primitive gets written exactly once"): group commit, VSR client-request batching (P5), and a combined LRU-touch are the same primitive under three names.
- **Consumers:** P1 ethdb — bufpool DirtyPageTracker and the LRU-K recency list (hot: every page `get` mutates shared recency state; the measurable A/B is sharded-mutex vs flat-combined, and only the combiner can dedupe a whole batch in one pass, which the sharded version cannot); `wal` group commit becomes a client rather than a bespoke implementation (hot, amortised). P5 perp-dex-core — consensus client-request batching and ledger apply (hot). P4 matching-engine — NOT the book itself (thread-per-core shard-by-symbol has one writer, so FC buys nothing there); its value for P4 is as the *measured alternative* to thread-per-core, which the plan currently cannot state in numbers.

**folly/stats/detail/BufferedStat.h (BufferedSlidingWindow / BufferedMultiSlidingWindow) + folly/stats/BucketedTimeSeries.h + folly/stats/MultiLevelTimeSeries.h**  
`add-to-plan` · `core` · ~22 h

- **Technique:** Time-rotating window of aggregates: a circular array of fixed-count buckets that advances when a timestamp past the current expiry arrives, so the aggregate answers "over the last W" rather than "since process start". Four distinct pieces: (a) lazy, writer-driven rotation — the FIRST appender past the expiry does the rotation, and a reader can force it via update(), so there is no timer thread; (b) the partial-head-bucket contract — elapsed() returns 590..600 for a 600 s/10-bucket window because the oldest bucket is partially expired, and rate() must divide by *actual* elapsed, not nominal, or it under-reports after every rotation; (c) multi-level (1 min / 15 min / 60 min / all-time) hierarchy driven off ONE shared write buffer, so N windows cost one record not N; (d) the rotation itself is a latency spike landing on whichever thread crosses the boundary, which is why folly puts it behind a SharedMutex with an AtomicTimePoint expiry probe on the fast path.
- **Forced by:** An all-time histogram's p99 is a monotone high-water mark: it is polluted by warmup and never recovers from a single stall, so it cannot function as a regression watchdog or a live SLO. A fixed-window p99 is the number an operator and a CI gate can both act on.
- **Plan has:** `latency-lab` (W021 hist.rs, W024 Report façade) is all-time only: the API is `record` / `record_correct` / `value_at_quantile` / `merge` / `snapshot` ("freezes the histogram"), static-mem, pre-sized at `Recorder::new`, never grows. There is no reset, no rotation, no window, no multi-level — greps for window/rolling/rotate in W021 and W024 return nothing of this kind. Yet W111 §499 asks latency-lab to be "a permanent regression watchdog" for the mark-tick p99.99, and §6 routes it to "every bar-(c) bench" — an all-time histogram makes that watchdog nearly inert, and it is the same failure shape the plan already dramatises for coordinated omission in W024 D6 ("1 bad sample among millions → p99.99 looks ~fine"), just caused by time rather than by omission. Adjacent-but-different plan items: the W071 TWAP calculator is a time-weighted sliding window with a correct half-open boundary test (so the *boundary* discipline is exercised once, in a domain crate) and W077 FlowController is a sliding window over subscriber positions, not time. Neither is a rotating-bucket aggregate, and neither lives in latency-lab. W110 §37 worries that a Grafana `histogram_quantile` rate-window shorter than the burst period under-reports the tail — that is the consumer-side symptom of exactly this missing primitive.
- **Consumers:** P4 v1.5 (hot — the sustained-load p99 tick-to-trade under a declared budget, which is P4's entire acceptance test, and the CI regression gate); P5 W111 mark-tick p99.99 watchdog (hot); every bar-(c) bench per §6. The record path is the constraint that makes this a design fight rather than a transcription: latency-lab's record path must stay zero-alloc and lock-free, so folly's SharedMutex rotation is NOT importable — the rotation needs a double-buffer / epoch swap, which is the actual lesson.

**folly/compression/elias_fano/EliasFanoCoding.h (with folly/compression/Select64.h, CodingDetail.h)**  
`note-only` · `borrow`

- **Technique:** Quasi-succinct coding of a monotone non-decreasing integer sequence (Vigna, arxiv:1206.4300): split each value into low bits (packed, fixed width = floor(log2(upperBound/size))) and high bits (unary in a bitvector), giving ~N·(2 + log2(U/N)) bits total; random access by `select` on the upper bitvector. The part with an actual design decision is the acceleration layer: two independent pointer densities — a *skip quantum* (value-indexed: find the element ≥ v) and a *forward quantum* (rank-indexed: find the i-th element) — each trading index memory against the length of the broadword scan, plus the upper-first vs lower-first layout choice for cache behaviour on the two access patterns.
- **Forced by:** A dense u64-per-row offset index costs 64 bits to store a value whose entropy is ~8 bits, and at real scale the index stops fitting in RAM — so you either page the index (defeating its purpose) or scan.
- **Plan has:** The plan has zero succinct-structure coverage: "elias", "succinct", "select1", "rank/select" all return 0 hits across plan/, notes/ and crates/. Two places the plan has already specified a dense index and sized it without naming the wall: (1) W036 R3 — snapshot export carries "an offset index (one u64 byte-offset per row)", and its own back-of-envelope says 100k accounts → ~800 KB index; extrapolate to the 250M-account mainnet state the same section sizes at ~27 GB payload and the index alone is ~2 GB, which the section does not compute. Elias-Fano on that sequence (U≈27e9, N=250e6 → ~8.8 bits/offset) is ~273 MB — a ~7.3× reduction with O(1) access. (2) W064 R3 — the log-distributed sparse offset index solves the same problem the other way (sample every 4 KiB, scan forward); the plan therefore knows exactly one of the two answers and never compares them. Note the mirror target already uses this: reth's static-file/NippyJar offset index is a monotone u64 sequence, which is why §6's P3 v1.5 "static files" row lands here too.
- **Consumers:** P1 ethdb (setup/offline — snapshot export/import index build and lookup); P3 v1.5 static files (setup, then read path); P5 `query-columnar` (read path — the same structure indexes row-group offsets).

**folly/concurrency/memory/TLRefCount.h**  
`note-only` · `core`

- **Technique:** Biased reference counting with a one-way LOCAL→GLOBAL mode flip. In LOCAL mode every increment/decrement is a plain non-atomic load+store into a per-thread counter plus an `asymmetric_thread_fence_light` (zero instructions on Linux). When somebody needs the true count, `useGlobal()` flips state to GLOBAL_TRANSITION, pays ONE `asymmetric_thread_fence_heavy` (membarrier PRIVATE_EXPEDITED), then drains every thread's local counter into the global atomic and flips to GLOBAL. The non-obvious part is the drain protocol: a `shared_ptr<void> collectGuard_` acts as a latch that both prevents new LocalRefCounts from registering and tells the collector when all existing ones have been collected (loop until the weak_ptr expires), plus an `inUpdate_` spin that stops a thread from touching a count whose owner object may already have been destroyed by the drain reaching zero.
- **Forced by:** An atomic increment on a hot shared refcount is a cache-line migration per acquire; under many cores the count, not the work, is the bottleneck. Sharding alone makes the count fast but UNREADABLE — you cannot cheaply ask "is it zero?". The mode flip is what buys back readability without putting an atomic back on the fast path.
- **Plan has:** notes/smr_inventory.md ALREADY catalogues both neighbours properly: line 143-146 covers asymmetric fences / membarrier PRIVATE_EXPEDITED in depth (and line 290 schedules it: "hazard crate stage 3 ... make the fence asymmetric and measure the delta — the single most instructive benchmark in the whole area"), and line 190-191 covers folly CoreCachedSharedPtr / ReadMostlySharedPtr sharded refcounts. So asymmetric fences are NOT a gap and sharded refcounts are NOT a gap. The residual gap is narrow and precise: the inventory's own precondition line for CoreCachedSharedPtr says "only the *acquire* is sharded ... the pattern only works when references are acquired-and-dropped locally" — and the mode-flip-plus-drain is exactly the mechanism that lifts that restriction. The inventory has no entry for it (0 hits for "TLRefCount", "mode flip", "GLOBAL_TRANSITION"). Separately, W033's epoch-pin design doc states "SeqCst fence ≈ 10-20 ns on x86 — expensive but it's CORRECTNESS here, not perf; you do not get to weaken it", which the asymmetric-fence technique falsifies; W016's follow-up note already flags this as a deferred migration, so the two documents disagree and the W033 sentence should be softened when the fence work lands.
- **Consumers:** P1 ethdb (bufpool page pin/unpin — a refcount touched on every page access); P4/P5 (hot shared snapshot/config pointers). All hot path. But every one of these sits inside the `reclaim` crate's existing scope, so this is a one-entry amendment to an inventory the user already wrote, not new build hours.

**folly/stats/TDigest.h + folly/stats/DigestBuilder.h + folly/stats/QuantileEstimator.h**  
`note-only` · `arguable`

- **Technique:** Mergeable tail-biased quantile sketch: adaptive centroids whose density is set by a scaling function k(q,delta) chosen so that dk/dq → inf at BOTH q=0 and q=1 (giving accuracy at p0.1 and p99.9 for ~100 centroids) and dk/dq(q) = dk/dq(1-q) (so upper and lower tails are equally accurate). folly substitutes sqrt for the paper's arcsin on exactly those three properties. Around it: DigestBuilder buffers raw doubles per-CPU (AccessSpreader-striped, try_lock then invalidate-cached-stripe-and-retry on thread migration) and merges into a digest only every bufferSize values, because the merge is the expensive part; QuantileEstimator/BufferedStat then compose that with time windows.
- **Forced by:** The record path of a sketch whose accuracy adapts to the data is expensive, so you buffer; and the bucket layout is a *designed* function of the quantile rather than a fixed log-linear grid, so accuracy concentrates where you actually read.
- **Plan has:** The plan hand-writes HdrHistogram in latency-lab (W021: log-linear bucket/sub-bucket layout, record = one counter increment, value_at_quantile returns the bucket UPPER bound, bucket-aligned merge, zero-alloc). For LATENCY that is strictly the better tool and this is not a gap — folly's whole buffer-then-merge stack exists only because TDigest's record is expensive and HdrHistogram's is not, and the per-CPU AccessSpreader striping is dominated by the plan's per-shard Recorder in a thread-per-core design (no lock at all, vs folly's try_lock). The one transferable idea the plan does not have: the plan takes log-linear bucketing as GIVEN (W021 R3 is the bucket-index formula; D3 asks why the upper bound, never why this density). TDigest's k(q) reframes that as a design choice with stated properties — a one-paragraph addition to the W021 mental model, not a build. Second, narrower place it could earn real hours: §6 routes "Columnar / vectorized scan, zone maps" to `query-columnar` for P5 analytics; a per-row-group quantile sketch upgrades a zone map from "can I skip this block" to "estimate this predicate's selectivity", which is the next step there and currently unplanned.
- **Consumers:** P5 `query-columnar` only, and off the hot path (index build at write time, selectivity estimate at plan time). Not P4, not P1.

**folly/hash/Hash.h — IsAvalanchingHasher<H,K> trait + moremur_mix64 / lowbias_mix32 finalizers + hash_128_to_64 / commutative_hash_128_to_64**  
`note-only` · `borrow`

- **Technique:** Make "does this hasher avalanche?" a compile-time property of the hasher, so any structure that maps a hash onto a smaller space (mask, modulo, shard index) can insert a bit-mixing finalizer only when needed. Folly's documented rationale: the standard only promises low collisions on the WHOLE hash value, so std::hash<uint64_t> being the identity is conforming yet useless for `h & (N-1)`; real-world keys are also not uniform over the domain. Plus: hash_combine over a sequence via hash_128_to_64, and an order-independent commutative combiner for sets.
- **Forced by:** Taking a subset of B bits from a non-avalanching hash gives a collision rate far worse than 1/2^B on real keys, which silently becomes shard skew or probe-chain blowup rather than a wrong answer.
- **Plan has:** No coverage under any name: "avalanch", "bit mix", "hash_combine", "128to64", "moremur" all return 0 hits. The plan does not build a hash table (uses std/DashMap), so the probe-chain half does not apply — but the key→shard half does, and it already has a live instance: crates/bufpool/src/sharded_cache.rs:109 is `fn shard_for(&self, addr: &Address) -> ... { let idx = addr.0[0] as usize % N; ... }`. That is correct for keccak-derived mainnet addresses (byte 0 is avalanched) but it (a) throws away 19 of 20 bytes and (b) sends every low-numbered test fixture address — address!("0x...01"), "0x...02" — into shard 0, so any benchmark or soak test built from synthetic addresses measures a single-shard lock, i.e. it silently measures the un-sharded design. W014 R1's `page % N` for DirtyPageTracker is the same shape on sequential keys (fine there, round-robin). The transferable discipline the plan lacks: whenever a key becomes a shard/bucket index, state in one line why the bits being used are avalanched for THIS key type, and assert distribution in a test.
- **Consumers:** P1 ethdb (bufpool ShardedCache, DirtyPageTracker — setup-time choice, hot-path consequence); P4/P5 (shard-by-key routing in runtime-thread-per-core; symbol ids are dense ints, so fine, but the discipline is what makes that a stated fact rather than luck).

**folly/concurrency/container/RelaxedConcurrentPriorityQueue.h (the Mound algorithm — Liu & Spear, ICPP 2012)**  
`skip` · `core`

- **Technique:** Relaxed-consistency concurrent priority queue: a heap whose every node is a sorted linked list (so push picks a random bottom leaf and binary-searches the list), with a shared pop-buffer holding one popped root list so subsequent pops are a fetch_add into that buffer and only one swap-down happens per batch. Deliberately trades exact-min for scalability (PopBatch>0 returns an approximate min), stabilises list length via tuned pruning/merging thresholds, and protects optimistic reads with hazard pointers behind a test-test-and-set spinlock.
- **Forced by:** An exact concurrent pop-min is a single contention point by definition; relaxing the order guarantee to k-approximate is the only way to make it scale.
- **Plan has:** Not covered (0 hits for "Mound"; `concurrent` has skiplist / MPMC / SegQueue, and priority structures appear only as single-owner `BinaryHeap` — W030 ARIES undo, W038 LSM merge iterator, W119 ADL ranking — or a fixed-cap intrusive skiplist). But I am reporting this as a genuine SKIP rather than a gap, because two of the plan's own invariants rule it out: (1) P5 requires bit-identical replay across replicas, and W119 explicitly demands deterministic iteration order for the ADL pop sequence — a relaxed queue's pop order is nondeterministic by construction, so it is not merely unnecessary but forbidden on every path that reaches a replicated log; (2) P4/P5 are thread-per-core shard-by-key, which removes the shared-priority-structure contention this exists to solve. Its blocking protocol ("one producer wakes exactly one consumer, producer never blocks") is already covered by `concurrent`'s Semaphore + Parker. Recording it so the question does not get re-asked.
- **Consumers:** None. No P1-P5 path wants an approximate pop-min.

**folly/concurrency/ConcurrentHashMap.h + folly/concurrency/detail/ConcurrentHashMap-detail.h (BucketTable::rehash, Buckets::retire, NodeT : hazptr_obj_base_linked)**  
`add-to-plan` · `core` · ~60 h

- **Technique:** Concurrent hash map whose READ path takes no lock at all: readers protect the bucket table and the node chain with an SMR handle (hazptr/epoch) and traverse with plain loads; writers take a lock on 1-of-2^ShardBits segments. Growth is publish-a-new-table-then-retire-the-old (never stop-the-world, never invalidate an iterator), with link-counting on nodes so the resize can share node chains between the old and the new table instead of copying them. Lock granularity (segment count) is decoupled from hash granularity (bucket count).
- **Forced by:** A shard-locked map (DashMap, tbb::concurrent_hash_map) serializes on the shard RwLock, so a skewed key distribution collapses effective parallelism to ~1 no matter how many shards exist: all the traffic for one hot key is in one shard. folly's answer is to remove the read side from the lock entirely — readers of a hot key never contend with its writers, only writers contend — and to make resize a pointer publish + deferred reclaim so the map can be used where the final size is unknown.
- **Plan has:** The plan has every ingredient and no map. `reclaim` (hazard pointers + epoch) is a planned Layer-1 crate; `notes/smr_inventory.md` already inventories `folly hazptr_obj_base_linked (link counting)` — with no client anywhere in the plan that needs link counting. `concurrent` lists skiplist as the only concurrent associative container (ordered, pointer-chased, wrong shape for a storage-key index). `FixedMap` (reference/W089.md) is the open-addressed robin-hood map, but it is single-threaded `&mut self`, fixed capacity, no rehash — deliberately so. The actual hot-path concurrent map is BORROWED: reference/W092.md R1 is literally `VersionedMemory { slots: DashMap<StorageKey, VersionedSlot> }`. This is not an oversight the plan is unaware of — W092 P3/D9 pre-predict the failure ("under a USDC-heavy block all writes hit one DashMap shard's lock → effective parallelism = 1") and W093 line 243 lists "hot-key versioned_memory/DashMap contention" as a root cause of the speedup shortfall. The only fix the plan offers is a workaround inside the borrowed structure ("hot keys get their own slot path"). So the technique is absent, the wall it removes is already written down, and §0 law 3 ("borrow first, write later — when writing it blocks the acceptance test") is satisfied: the W094 ≥2× 8-core speedup gate is the acceptance test, and the borrowed map's contention is what caps it.
- **Consumers:** P2 exec-vm v1.5 — HOT PATH, the one that matters: `versioned_memory` read is budgeted <100 ns at 12M reads/s and gates the W094 speedup acceptance. Also P3 txpool (by-hash / by-sender indices, concurrent insert from network threads + read from the sync pipeline) — hot. P1 v2 parallel storage root, if the sparse-trie node map is shared across the rayon workers — hot. Setup-path only for P5.

**folly/detail/TurnSequencer.h (tryWaitForTurn: kSpinUsingHardwareClock, kMinSpinLimit=200cy, kMaxSpinLimit=20000cy, EMA update `prevThresh + (target-prevThresh)/8`), consumed by folly/MPMCQueue.h and folly/concurrency/container/LockFreeRingBuffer.h**  
`add-to-plan` · `core` · ~12 h

- **Technique:** Measure the spin budget in CYCLES with rdtsc, not in loop iterations, and learn it at runtime: on each wait, if the spin succeeded, fold the measured elapsed cycles (×2 for slack) into a shared cutoff with an exponential moving average (α=7/8), clamped to [200, 20000] cycles; if the wait hit the max, snap the cutoff to the floor (spinning was pointless). Re-probe periodically at the max to re-sample. The cutoff word is stored ONCE per structure and passed in by the caller — not per slot (never converges, costs memory) and not per thread (no sharing of what was learned) — and separate cutoffs are kept for read vs write paths.
- **Forced by:** The spin-hint instruction's cost is not a portable constant. folly's own comment: "On x86 the latency of a spin loop varies dramatically across architectures due to changes in the PAUSE instruction. Skylake increases the latency by about a factor of 15 compared to previous architectures. To work around this, on x86 we measure spins using RDTSC rather than a loop counter." A hardcoded iteration count therefore buys a wildly different time budget per target, and the right budget is "about one futex round trip", which is itself a machine property.
- **Plan has:** The plan covers spin-then-yield-then-park (`concurrent/src/backoff.rs`, W008 drill #8) and has rdtsc in the `time` crate. What it does not have is runtime calibration — and the plan's own source documents that as an open hole rather than a solved one. backoff.rs's module doc measures the exact problem on the user's own hardware (`spin_loop()` = ~1 ns PAUSE on x86 vs **12.2 ns** `isb SY` on Apple Silicon; `yield_now()` = 4.6 µs) and concludes that the shared `SPIN_LIMIT = 6` gives a 64 ns burst on x86 and a 784 ns burst on aarch64, so "at the capped burst the caller only re-tests its condition every 784 ns… A wait satisfied 10 ns into the final burst goes unnoticed for the remaining ~774 ns… It is NOT harmless for a latency-sensitive waiter whose condition resolves somewhere in the 100 ns - 1 µs band." Its prescription is a hand-tuned per-target constant ("≈2-3 on aarch64"); folly's is to stop guessing and measure. The 100 ns–1 µs band the plan names as the danger zone is precisely P4's p99 tick-to-trade band, and a per-target constant does not survive the next microarchitecture.
- **Consumers:** P4 v1 — HOT PATH: every waiter on the SPSC/MPMC stage rings and on the shard mutexes; the ~774 ns unnoticed-wait window is a direct p99 tick-to-trade contributor, and the plan already commits to a declared p99 budget as the acceptance test. Also P1 v1.5 group-commit waiters (hot), P5 apply-loop and VSR message-pool waiters (hot). Cheapest fix in this list relative to what it protects.

**folly/synchronization/FlatCombining.h (Rec publication records with valid_/done_/disconnected_ SaturatingSemaphores, dedicated-vs-opportunistic combiner, custom Req for smart combining) + folly/concurrency/container/FlatCombiningPriorityQueue.h**  
`add-to-plan` · `core` · ~24 h

- **Technique:** Replace a contended lock on a SEQUENTIAL data structure with a publication protocol: a thread that finds the lock taken writes its operation into its own cache-line-aligned request record and waits; whoever holds the lock (or a dedicated combiner thread) sweeps the publication list and executes everyone's operations in one pass, then marks each record done. Two distinct wins: (a) the data structure is touched by one core at a time so its cache lines never migrate, and the lock acquire/release leaves the critical path entirely; (b) SMART COMBINING — the combiner sees K requests at once and can fuse them, so K delete_min on a heap cost O(K + log N) instead of O(K log N). Stale records are pruned by age so the publication-list scan stays proportional to active threads, not threads-ever.
- **Forced by:** Hendler/Incze/Shavit/Tzafrir (SPAA 2010) observed that for many structures the cost of concurrency is cache-coherence traffic, not the lock itself, and that a sequential structure driven by a single rotating owner beats a hand-written lock-free version. It is the answer for structures that CANNOT be sharded because their operations need global state (a heap's min, a global LRU victim, a free list).
- **Plan has:** The plan has exactly two answers to a contended structure, both well covered: shard it (reference/W011.md drill #14, measured — single counter ~3-5M ops/s at N=16 vs sharded ~30-40M, with "hierarchical aggregation" named as the 5-year escape) or make it lock-free (MPMC, SegQueue, skiplist). Flat combining is the third answer and appears nowhere: zero hits for "flat combin", "combining", "publication list", "combiner" across plan/. The nearest thing is WAL group commit (§6 "Group commit, WAL segments, checksums"), which is the same idea applied to one specific syscall — one thread fsyncs for everybody — but group commit is hardcoded to the WAL, has no request-record protocol, no combiner election, and no smart-combining generalization. The gap is the generic lock-replacement protocol and, more importantly, the measurement: W011's scale curve has two lines where it should have three, and the plan picks sharding for `bufpool`'s eviction (`ShardedCache`) by reflex, accepting the LRU-K accuracy loss that sharding forces, without ever considering the branch that keeps the structure global.
- **Consumers:** P1 v1.5 — HOT PATH: bufpool LRU-K victim selection is the textbook case (global victim choice cannot be sharded without losing the K-distance accuracy the whole LRU-K exercise exists to buy; a combiner keeps one global clock and fuses K pin/evict requests into one pass). P4 v1 setup/cold path: any cross-shard structure that resists sharding. P1/P5 `txn` LockManager wait queues — hot under convoy. Lower confidence than the first two gaps: build it once, A/B it against the already-planned sharded version on bufpool eviction, and keep it only if it wins — but the A/B itself is the deliverable, because "shard it" is currently an unexamined default.

**folly/concurrency/container/LockFreeRingBuffer.h (+ detail::RingBufferSlot wrapping folly/detail/TurnSequencer.h, RingBufferTrivialStorage, internalBufferLocation())**  
`note-only` · `arguable`

- **Technique:** An overwriting broadcast ring where each SLOT carries its own sequence counter (even = stable, odd = write in progress) rather than the ring carrying one global sequence. Writers take an absolute ticket by fetch_add (so MULTIPLE concurrent writers are allowed) and block only on a writer a full lap behind; readers address any absolute position in a logically unbounded stream, can block on a position not yet written, and always fail cleanly on a position already overwritten. Separately: internalBufferLocation() exposes the raw slab so the ring doubles as an in-memory flight recorder recoverable from a core dump after a crash.
- **Forced by:** Per-slot sequencing means a reader of slot k is unaffected by writes to slot k+1 — with one global seqlock, every write invalidates every in-flight read, so a single-sequence snapshot structure does not scale to a stream. The never-block-the-writer rule is what lets a latency-critical producer fan out to observers of unknown speed.
- **Plan has:** Mostly covered, under two different names, which is why this is note-only rather than a build. The product-level need is served by reference/W079.md `subscription.rs`: Aeron's Subscription/Image model — one shared term buffer, N independent position cursors, "slow subscribers don't block fast ones (configurable LagPolicy)", R2 "subscriber poll does NOT free term-buffer slots — only term rotation does" (i.e. the writer overwrites and the lagging reader is detected). And the plan has `SeqLock<T: Pod>` (global sequence, single writer) plus the Vyukov MPMC ring (per-slot sequence, blocking-when-full). What is genuinely untaken is one composition and one framing: (1) per-slot sequence applied to OVERWRITE/snapshot semantics with concurrent writers — the plan has per-slot-seq for a blocking queue and global-seq for a snapshot, never the diagonal; (2) the ring-as-crash-dump-flight-recorder use, where the point is not throughput but that the last N events survive into the core file (zero hits for "core dump"/"crash dump"/"flight recorder" in plan/). Neither changes what P4/P5 ship — Aeron Image already carries the fan-out and both of the plan's overwriting producers are single-writer per shard.
- **Consumers:** P4 v1.5 latency-lab (flight recorder surviving into a core dump — setup/diagnostic path, not hot), P4 book-snapshot fan-out and P5 analytics-plane bounded-staleness reads (both already served by Aeron Image). One measurement worth stealing even without the build: per-slot vs global sequence for the book snapshot under a concurrent-reader storm.

**folly/concurrency/container/SingleWriterFixedHashMap.h**  
`note-only` · `arguable`

- **Technique:** A fixed-capacity open-addressed map that admits ONE writer plus wait-free concurrent read-only lookup AND iteration, with no SMR at all: slot values are `std::atomic<Value>` (statically required lock-free) and keys are required trivial so readers can load them data-race-free while insert/erase run. The load-bearing invariant is unobvious: a TOMBSTONED slot may only ever be reused by THE SAME KEY — so that once a key occupies a slot it can never occupy another for the map's lifetime, which is what guarantees a concurrent iterator never observes the same key twice. Growth is by copy-construction into a larger map plus publish (the copy is guaranteed to leave ≥1 empty slot), so growth never mutates what readers are traversing.
- **Forced by:** An open-addressed map with a concurrent reader has a hazard a single-threaded one does not: a key that moves between slots during probe-chain repair can be seen twice, or missed, by an iterator that has already passed its new position. Pinning a key to its first slot forever trades a little space (tombstones accumulate, cleared only at copy time) for a free, allocation-free, reclamation-free concurrent read side.
- **Plan has:** The plan's `FixedMap` (reference/W089.md) is the same structure — fixed capacity, open addressing, robin-hood probing, never rehashes, `MapFull` past load 0.85, deterministic BuildHasher — but it is strictly single-threaded `&mut self`, and robin-hood probing is specifically a design where keys DO get displaced between slots, i.e. the one that breaks a concurrent iterator hardest. The plan's concurrent-read-of-single-writer-state answers are `SeqLock<T: Pod>` (scalars only — W060 uses it for best_bid/best_ask) and immutable-plus-`ArcSwap` (W097 R2/D2, correct for rarely-changing params, impossible for a 100k-account table mutated on every fill). The plan avoids needing this at all by colocating: `runtime-thread-per-core` shards by account/symbol so the reader IS the writer thread, and cross-thread observers get an event stream (Aeron MBO feed) instead of a live map — a legitimate and arguably better design. So: note-only. But the invariant is worth writing into FixedMap's doc comment as a tripwire, because "add a concurrent reader to FixedMap" looks harmless and silently breaks iteration the moment robin-hood displaces a key.
- **Consumers:** P4 v0.5/v1 (shard-local OrderId→Order index read by a snapshot/telemetry thread) and P5 W097–W099 (risk reading the 100k-account position table per mark tick) — both currently resolved by shard colocation, so neither is a hot-path requirement today.

**folly/concurrency/CacheLocality.h (CacheLocality::readFromSysfsTree, AccessSpreader::current/cachedCurrent, Getcpu::resolveVdsoFunc, LLCAccessSpreader, coreMalloc/CoreAllocator/CoreAllocatorGuard) + folly/concurrency/CoreCachedSharedPtr.h, folly/ThreadCachedInt.h, folly/concurrency/SingletonRelaxedCounter.h**  
`note-only` · `borrow`

- **Technique:** Three related pieces. (1) Discover the real cache topology at startup by parsing /sys/devices/system/cpu/cpu*/cache/index*/{type,shared_cpu_list} into "how many caches exist at each level" + "which CPUs share each one", then precompute a cpu→stripe table so that when you ask for N stripes the stripe boundaries fall on actual cache boundaries (N=2 on a dual socket gives you one socket per stripe; N=numCpus/2 gives perfect L1 spreading under SMT). (2) Select the stripe by CPU rather than by thread: `getcpu` via vDSO (~12-22 ns), amortized to ~2 ns by caching the CPU in a TLS slot for 32 calls. The point is that the number of stripes is bounded by CORE COUNT, not by threads-ever-created. (3) `coreMalloc(size, numStripes, stripe)` — a per-stripe arena that hands out SUB-cacheline allocations while still guaranteeing no false sharing across stripes, so many independent striped objects can each hold a 4-byte per-core counter without each one burning a full 64-byte line.

Keying on the CPU bounds both.
- **Plan has:** Partly covered, by hand rather than programmatically. The plan shards by producer index / worker id / key hash and pads with `CachePadded` (W011 drill #14 measures the single-counter collapse and ships `[CachePadded<AtomicU64>; N]`; W065 R2 sets `num_shards = num_cores or num_NUMA_local_cores`), and it covers affinity and NUMA empirically at the tuning stage (W110: `perf stat -e cache-misses,LLC-load-misses`, `taskset`, `numactl --membind`, IRQ-affinity isolation). For the pinned thread-per-core products this is a non-issue (pinned thread ≡ CPU, and the shard count is a deployment constant). - **Consumers:** P1 v2 / P2 v1.5 / P4 / P5 — all of them consume `reclaim`, so the registry-scan bound is shared. ## Gaps the critic found that the five missed


**folly/lang/Align.h — hardware_destructive_interference_size = (kIsArchArm || kIsArchS390X) ? 64 : 128, and the SEPARATE hardware_constructive_interference_size = 64**  
`add-to-plan` · `core` · ~5 h

- **Technique:** Two different cache-geometry constants for two opposite jobs. (a) Destructive: how far apart to push things so concurrent writers never interfere — and the answer on x86_64 is 128, not 64, because adjacent cache-LINE PAIRS interfere under heavy atomic RMW (folly's comment: 'Microbenchmarks indicate that pairs of cache lines also see destructive interference under heavy use of atomic operations, as observed for atomic increment on Sandy Bridge'). (b) Constructive: how much you can pack TOGETHER and still get for free on one fetch — 64 — which is the positive half of the same cost model and drives field grouping in a hot struct.
- **Forced by:** The L2 spatial/adjacent-line prefetcher pulls 128-byte pairs on Intel, so two atomics 64 B apart still ping-pong even though they are in different lines. folly measured it on atomic increment and hardcoded 128 for everything that is not ARM/s390x. crossbeam-utils made the identical call for the identical reason.
- **Plan has:** §6 row 'False sharing, CachePadded, MESI cost model → concurrent' exists and CachePadded is WRITTEN. But crates/concurrent/src/cache_padded.rs has the arch mapping INVERTED relative to folly and crossbeam: `#[cfg_attr(target_arch = "x86_64", repr(align(64)))]`, 128 only for aarch64/powerpc64, and the doc comment attributes the prefetcher-pair rationale to aarch64 alone ('x86_64: 64 B. Standard cache-line size.'). The measured 6x false-sharing cliff in notes/cache_padded_bench_results.md was therefore taken on the arch that is padded correctly. There is also no constructive constant anywhere in the plan — no named idea of 'pack these co-read fields into one line'.
- **Consumers:** P4 hot (ring head/tail cursors, PriceLevel, Disruptor cursor, aeron term counters — the file names all four reapply sites), P1 hot (bufpool shard counters, B+tree node header field grouping), P2/P3/P5 via `concurrent`. It is the one crate in all five products.

**folly/algorithm/StableRadixSort.h (stable_radix_sort, with stable_radix_sort_keys::{FloatKey, IntegralKey, IdentityKey})**  
`add-to-plan` · `core` · ~12 h

- **Technique:** Sort fixed-width keys in k passes of counting sort over alternating buffers — O(n) with k = sizeof(key)/digit, stable by construction because LSD order preserves earlier passes. Plus the order-preserving bijections that make non-unsigned keys radix-sortable: flip the sign bit for signed ints; for IEEE floats flip all bits when negative and only the sign bit when positive, so -inf→0x00.., -0.0→0x7F.., +inf→0xFF... The design surface is digit width (8 bits = one 256-entry cache-resident histogram) against pass count, the mandatory scratch buffer, and the crossover below which a comparison sort wins.
- **Forced by:** Comparison sort costs n·log n branchy compares with unpredictable moves; for a fixed-width key you can pay k linear passes with sequential writes instead. At 1M keys that is ~20 compares/element versus 4-8 histogram passes.
- **Plan has:** §6 has NO sort row at all. P1 v0.5 is specified as 'HashBuilder (sorted stream)' — the plan commits to consuming a sorted stream and never says how the stream is produced. reference/W083 has the only hot sort in the plan and it is a bar-(c) budget item: `scratch.clear(); scratch.extend(iter); scratch.sort_unstable(); blake3(..)` over ~1M tuples, with the whole analysis spent on allocation (pre-allocated scratch) and none on the sort's own cost. The only 'radix' hits in plan/ are radix-TRIE path compression (W033), a different thing entirely.
- **Consumers:** P1, per-block on the state-root critical path (sorting changed-account/slot hashes before HashBuilder — 32-byte keys, so the interesting variant is radix on a prefix plus a comparison tail) and B+tree bulk load. P5 hot in the VOPR loop: W099 computes the honest seeds/sec rate from the cost of state_hash, and that cost contains this sort.

**folly/container/IntrusiveHeap.h (IntrusiveHeapNode with parent_/left_/right_ + kUnlinked sentinel; skew heap, Sleator-Tarjan, top-down meld)**  
`add-to-plan` · `core` · ~16 h

- **Technique:** A priority structure whose nodes live INSIDE the payload object (three pointers, plus parent_ so a node knows where it hangs), giving O(log n) amortized erase or re-key of an ARBITRARY node with zero allocation and zero tombstones. Everything — push, pop, erase, update — is expressed as meld of two subheaps, so there is no array, no index bookkeeping, and isLinked() is a single pointer compare against a sentinel.
- **Forced by:** An array heap can only cheaply touch the root; to cancel or re-price an entry you either keep a side index (and pay to maintain it) or push a tombstone and compact later (and pay unbounded memory). Embedding the node kills both: the object you already own IS its own heap handle.
- **Plan has:** The plan names the exact failure mode this fixes and then reaches for the weaker fix. reference/W071 (ADL/liquidation queue, bar (c), ≤100 ns p99 on every position-changing fill) lists as its three traps: '(1) lazy-invalidation BinaryHeap is correct but memory-unbounded — stale entries accumulate to OOM without compaction; (2) pop_highest_rank -> Vec allocates per cascade burst; (3) BinaryHeap ties pop in run-dependent order, so two replicas diverge' — and resolves (1) with compaction. reference/W014 (LRU-K) independently records 'BTreeSet/BinaryHeap-per-touch rebuilds the priority structure, allocating a node each time'. reference/W060 pre-allocates a fixed BinaryHeap and slab-interns indices. Three separate work items hit the same wall; §6 has no priority-structure row and no intrusive-heap technique. The two concurrent-priority-queue candidates in the list above do not cover this: those are about contention, this is about arbitrary-node mutation in a single-writer shard.
- **Consumers:** P5 hot (ADL ranking by profit × leverage, re-keyed on every fill; liquidation queue), P4 hot (stop/trigger orders keyed by price, cancelled far more often than they fire), P1 hot (bufpool LRU-K — backward-k-distance is a decrease-key on an arbitrary page).

**folly/concurrency/DynamicBoundedQueue.h (debit_ / credit_ / transfer_ on three separate alignas(Align) lines, threshold = capacity/10, WeightFn, reset-capacity)**  
`add-to-plan` · `core` · ~20 h

- **Technique:** Make a bounded queue's capacity check scale by splitting the counter so that no line is written by both sides: producers only fetch_add `debit_`, consumers only fetch_add `credit_`, and the two reconcile in BULK — a consumer pushes accumulated credit into a third word `transfer_` and futex-wakes blocked producers only when credit crosses capacity/10. Three deliberate design choices fall out: (1) producers 'use fetch_add to add to the debit variable and subtract if it exceeded capacity, rather than using compare_exchange to avoid overshooting' — one uncontended RMW instead of a CAS loop, paid for by a WEAKENED contract ('~10% slack... precise capacity is not guaranteed and cannot be relied on for synchronization; i.e., this queue cannot be used as a semaphore'); (2) admission by element WEIGHT (bytes) rather than count, weights counting toward capacity without affecting FIFO order; (3) capacity is adjustable at runtime specifically 'to prevent deadlock by allowing users to temporarily increase capacity substantially to guarantee accommodating producer requests that cannot wait'.
- **Forced by:** A single shared size counter on a bounded queue is a worse contention point than the queue itself: every enqueue and every dequeue RMWs the same line, so the bound costs more than the data movement. And a count bound is the wrong bound when elements vary in size by 100x.
- **Plan has:** `backpressure` is written and is exactly `BackpressureStrategy` + `BoundedBuffer` + `PushOutcome` (crates/backpressure/src/lib.rs). §6's only backpressure row is 'Async, Pin, Future state machines, backpressure → P3 node I/O; backpressure'. Nothing in the plan addresses how the capacity check itself scales, byte-weighted admission, a deliberately approximate capacity contract, or raising capacity to break a deadlock. It never came up because the MPMC ring is fixed-capacity with per-slot sequences, where the bound is implicit in the ring geometry — so this gap is invisible from the ring and only appears on the unbounded/segmented side (SegQueue, which the plan has).
- **Consumers:** P3 hot (txpool ingress and per-peer queues — a txpool's real bound is bytes, which is what reth bounds; and the plan caps P3 at 'hold the tip', which is precisely the regime where a count bound misbehaves), P4 hot (stage-to-stage queues in the v1 pipeline), P5 hot (client order-submission admission).

**folly/hash/Checksum.h — crc32_combine / crc32c_combine / crc32c_combine_seed**  
`add-to-plan` · `arguable` · ~6 h

- **Technique:** CRC is linear over GF(2), so the CRC of a concatenation is computable from (crc1, crc2, len2) alone, in O(log len2), without re-touching any bytes. That turns a checksum from a sequential scan into a reduction: checksum pieces in parallel, or out of order, or checksum each record once where it is produced and FOLD the records into a frame/segment checksum at commit time. folly states the cost of not having it — the naive equivalent (xor plus a CRC over a zero buffer of len2) is ~10x slower — and crc32c_combine_seed exists because the plain combine is only valid for a 0 starting checksum.
- **Forced by:** Any format that nests checksums (record inside frame inside segment) otherwise pays a second full pass over the payload at the outer level, and that second pass usually sits inside a critical section.
- **Plan has:** Hardware CRC32C is covered well and explicitly: reference/W083 has the 12x software-vs-hardware cliff (~250 ns vs ~20 ns per 256 B), the `_mm_crc32_u64` / `__crc32d` intrinsics, runtime-dispatch rejected, and an EXPERT disasm test asserting the instruction is actually emitted. The COMBINE algebra appears nowhere in plan/ (zero hits), and §6's row is only 'Group commit, WAL segments, checksums → wal → P1 v1'. So the plan knows how fast a CRC is and not that CRCs compose.
- **Consumers:** P1 hot, on the group-commit critical path: N threads each hand a record to the committer. With combine, each producer CRCs its own record off the critical path and the committer folds N u32s; without it the committer re-scans the batch inside the commit — ~83 µs per MB even at hardware speed, against the very group-commit latency the P1 v1 step is measured on. P5 hot-ish (chunked state transfer: verify and re-verify chunks without rescanning the whole snapshot). This is really a FORMAT decision — does the WAL frame carry a per-record CRC that composes — which has to be made before the writer is written, not after.

**folly/synchronization/AsymmetricThreadFence.h (asymmetric_thread_fence_light / _heavy) over folly/portability/SysMembarrier.h**  
`add-to-plan` · `core` · ~10 h

- **Technique:** Split a bidirectional fence into two halves with different prices. The LIGHT half, on the frequent side, compiles to nothing but a compiler barrier (`asm_volatile_memory()` on Linux — zero instructions). The HEAVY half, on the rare side, pays membarrier(MEMBARRIER_CMD_PRIVATE_EXPEDITED) and is DEFINED to interact with every light fence as if both had been full fences. The contract is precisely scoped: a light fence does not interact with another light fence, nor with a normal fence, nor directly with an atomic op in another thread — only with a heavy one. (p1202r4.)
- **Forced by:** On a read-mostly protocol the reader's SeqCst store/fence is the entire per-operation cost; the writer runs 10^4 times less often. Asymmetric fencing moves 100% of the ordering cost onto the writer.
- **Plan has:** Named exactly once in the whole plan, and filed as not-now: reference/W016's five-year-followup note says 'pin overhead matters at extreme rates (>50M ops/s) where the SeqCst fence becomes visible in profile. TRIGGER: ... Migration: per-NUMA epoch counters + asymmetric fence (process-wide membarrier on the advancer, plain load on readers)'. It is not in §6, and the `reclaim` crate scope in §9 does not mention it. The reason that filing is wrong: §9 says `reclaim` exists as its own crate 'because the two schemes must be swappable behind one interface for the A/B bench to isolate reclamation from layout' — and the dominant per-op cost on BOTH read paths is the ordering instruction (hazard pointer's protect store, epoch's pin fence). An A/B that fences both sides fully is measuring the wrong axis, so this is not a later optimisation of the bench, it is a condition on the bench meaning anything.
- **Consumers:** P1 hot (bufpool page reclaim), P4 hot (price-level reclaim), P5 hot (ledger/state SMR) — all via `reclaim`, whose two implementations plus Treiber-stack second client are the next thing to be written per §9. Also a measurement caveat worth knowing up front: membarrier is Linux-only, so on the darwin/arm64 dev machine the heavy side degrades to a real fence and the light side to a real fence too — the A/B number is only credible on Linux.

**folly/test/DeterministicSchedule.h — `static int getcpu(unsigned* cpu, unsigned* node, void*)` as a member of the scheduler ('Deterministic implementation of getcpu'), alongside setAuxChk (an invariant hook run after EVERY shared access) and the ThreadTimestamps vector clocks (acqRelOrder_ / acqFenceOrder_ / relFenceOrder_)**  
`add-to-plan` · `borrow` · ~4 h

- **Technique:** If a data structure stripes by core, then the core id is an INPUT to its behaviour, so a seeded replayable concurrency test has to put getcpu under the scheduler's control too — otherwise the same seed does not reproduce the same run and a failing case is not replayable. folly makes this explicit by shipping a virtualized getcpu next to the virtualized atomics and futexes, which in turn forces the design rule that stripe selection must go through an injectable seam rather than calling sched_getcpu directly. The second separable piece is setAuxChk: a global-invariant callback invoked after every single shared access, so a broken invariant is caught at the access that broke it rather than at the end of the run.
- **Forced by:** Interception has to be total. folly's scheduler intercepts atomics, fences (including the asymmetric ones), futex wait/wake, semaphores, thread create/join/exit — and getcpu, because CacheLocality's AccessSpreader is pervasive in the same code being tested.
- **Plan has:** The scheduler itself IS covered — reference/W011 and W004 both name shuttle as the escape hatch when loom's exhaustive search runs out ('when ARM/Power edge cases arise, switch to shuttle (random scheduling) or formal (TLA+)'), and §5 already borrows loom/criterion/proptest, so adding shuttle is in-pattern. What is absent is the stripe-selector consequence. The plan has at least three stripe-by-X structures — bufpool's ShardedCache (written), `reclaim`'s 'one shared immortal per-thread registry' (§9, next to be written), and runtime-thread-per-core — and nothing anywhere says their selector must be injectable. Note this is also the precondition for the five agents' CacheLocality/AccessSpreader candidate being testable at all: adopting per-core striping without this makes every striped structure's concurrency test non-replayable.
- **Consumers:** P1 (bufpool shards), P4/P5 (`runtime-thread-per-core`, per-core reclaim registry). Test path only — but it decides whether a failing seed replays, which is the entire value of the harness, and it is a type-level decision that is expensive to retrofit across already-written code.

**folly/logging/AsyncLogWriter.h (kDefaultMaxBufferSize, setMaxBufferSize, DiscardCallback, flush, cleanup) + folly/logging/RateLimiter.h (IntervalRateLimiter::check)**  
`add-to-plan` · `core` · ~14 h

- **Technique:** Diagnostic logging that cannot perturb the producer, as three separable mechanisms. (a) A BYTE-bounded in-memory buffer drained by a dedicated I/O thread, and on overflow messages are DISCARDED and COUNTED, with 'N messages discarded' emitted once the drain catches up — an explicit, measurable loss contract instead of either unbounded memory or a blocked producer ('logging I/O can never slow down or block your normal program operation'), and folly states the price in the same breath: on crash you lose whatever has not drained. (b) A rate limiter whose value is its FAST PATH: once the current window is saturated it returns false off a relaxed load and skips the contended fetch_add entirely — 'Fast path: when the current interval is saturated, skip the contended RMW on count_' — and it reads chrono::coarse_steady_clock, not a fine clock, because a log-rate check must not cost a real clock read. (c) An explicitly non-token-bucket window policy: N per fixed interval, burst accepted at the window start, nothing smoothed — chosen because for logs you want the first N of a storm, not a trickle through it.
- **Forced by:** An exchange or a replica emits diagnostics from its hottest loop. Synchronous logging couples p99 to disk; unbounded buffering converts a slow disk into an OOM; and an unthrottled limiter makes the throttle itself the contention point during exactly the storm it exists for.
- **Plan has:** Three near-misses, none of them this. `log-distributed` is a Kafka-style partitioned log — a product, not diagnostics. `latency-lab` is measurement (HdrHistogram, rdtsc, coordinated omission). `wal` is durability. reference/W105 shows the plan already takes observability-perturbation seriously, with a metrics test asserting 'the apply-thread p99.99 is within 1% of its no-scrape baseline' — which is exactly why the hole is conspicuous: the plan has a perturbation budget for metrics scraping and no story at all for TEXT diagnostics out of the P4/P5 apply loop, which will certainly have them (every reject, cancel, self-trade-prevention and liquidation wants a line).
- **Consumers:** P4 hot (apply loop, under the declared tick-to-trade budget — and the drop-and-count contract is what lets the claim survive), P5 hot (replica apply path; note the loss contract must be stated per-replica or logs stop being comparable across replicas), P1 off-path (recovery diagnostics).

**folly/tracing/StaticTracepoint.h — FOLLY_SDT, FOLLY_SDT_WITH_SEMAPHORE, FOLLY_SDT_IS_ENABLED + StaticTracepoint-ELF.h**  
`note-only` · `borrow`

- **Technique:** An instrumentation point that costs one 5-byte nop when nobody is listening, with its argument locations recorded in an ELF .note.stapsdt section so an external tool (bpftrace / perf / eBPF) can patch the nop and read the arguments out of a RUNNING, unmodified, fully optimized binary. The non-obvious second half is the semaphore variant: a 2-byte refcount the tracer increments, so `if (FOLLY_SDT_IS_ENABLED(..))` lets you skip the argument COMPUTATION, not just the probe — which is what makes an expensive-to-derive probe argument free when untraced.
- **Forced by:** You want the measurement in the shipped configuration, not in a bench binary, and you want adding a probe to be a decision you can defer to runtime.
- **Plan has:** All of the plan's instrumentation is compiled-in and read from a bench harness: `latency-lab` (HdrHistogram, coordinated omission, rdtsc, perf), W105 Prometheus scraping. 'tracepoint' and 'usdt' have zero hits in plan/; 'bpf' appears 3 times incidentally. §2 Law 4 says every step is measured not asserted, and P4's acceptance test is a p99 under a declared budget — a probe attachable to the running engine is how that claim survives outside the bench.
- **Consumers:** P4 and P5, hot-path probe sites (fill, reject, commit) but zero-cost when untraced; the semaphore trick is what keeps it that way.

**folly/detail/MemoryIdler.h — getVariationTimeout (idleTimeout .. idleTimeout × 1.5, default ±50%, 'Endpoints using this idle timeout might randomly wait longer to avoid synchronizing their flushes') + flushLocalMallocCaches / unmapUnusedStack with kDefaultStackToRetain**  
`note-only` · `arguable`

- **Technique:** Two things, and the transferable one is the jitter. (a) When many independent actors share the same periodic deadline, randomize each one's timeout by a fraction of itself, because otherwise they converge into a convoy and every period becomes a synchronized spike — folly jitters a thread-pool idle timeout by up to +50% purely for this. (b) When parking for a long time, hand memory back: madvise away the unused part of the stack and flush the thread-local malloc caches, retaining kDefaultStackToRetain bytes so the wakeup does not immediately take a page fault — an explicit, tunable trade between reclaimed memory and wake latency.
- **Forced by:** A LIFO/throttled thread pool leaves a long tail of threads parked for minutes; their stacks and malloc caches are pure waste. And identical timeouts across N actors turn a smooth load into N-sized bursts.
- **Plan has:** `Backoff` covers spin backoff (a different axis); reference/W106 covers seeded PRNG sub-streams for workload jitter; reference/W058's timer wheel covers cascade amortization. Nothing covers desynchronizing periodic background work by jittering the period itself, and nothing covers the retain-N-bytes trade on park. Partially shadowed by the ThrottledLifoSem/LifoSem candidates above, which mention madvise in passing without naming either mechanism.
- **Consumers:** P1 off-path (buffer-pool flushers, WAL segment rotation across shards), P5 off-path (replica background work — note the consensus-timeout case is already covered, since randomized view-change timeouts are part of the BFT spec the plan builds).
